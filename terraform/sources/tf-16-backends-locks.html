Backend и locking: кто имеет право записать следующую память

State хранится в одном согласованном месте, а изменяющие операции должны получать предусмотренную блокировку. Git review контролирует текст конфигурации, но не сериализует apply.

Local backend не означает отсутствие lock

По умолчанию state local backend находится в terraform.tfstate рабочего каталога. Local backend использует системные API для locking; дополнительный файл информации о блокировке помогает диагностике, но он не весь механизм. Просто удалить lock-info файл не равно безопасно освободить живой OS lock. Если два процесса обращаются к одному поддерживаемому local state, второй должен ждать либо отказать согласно команде/timeout.

terraform plan -lock-timeout=0s
terraform plan -lock-timeout=10s

При занятом state первый вызов обычно быстро сообщает отказ, второй даёт время закончить текущую операцию. При свободном state они не должны различаться содержанием плана только из-за timeout. -lock=false выключает защиту там, где опция поддерживается; это не лечение очереди. Конкурирующая запись может потерять association и породить двойное управление. В нашем тесте первый apply удерживает local lock ограниченной задержкой gate; второй plan действительно получает отказ, затем нормальная работа продолжается после завершения первого.

Удалённое хранение и удалённое исполнение

Remote state — state в backend вне рабочего каталога. Terraform backend type remote, использующий HCP Terraform/Terraform Enterprise, — конкретная интеграция, а не имя всех сетевых хранилищ. Хранение в S3 само по себе не переносит выполнение provider на отдельный сервер: обычный CLI продолжает работать там, где запущен. У управляемых runs есть собственная модель remote execution, очереди, доступа и логов.

Backend type, параметры адреса state и workspace образуют границу выбора памяти. В случае ошибочного key или workspace можно получить пустой state и план создания существующей инфраструктуры. Поэтому в CI фиксируют не только branch, но и backend identity, workspace и фактическую учётную запись provider. Root configurations разных сред часто разумно разделять по правам и жизненному циклу, а не маскировать одним переменным именем.

Пример S3 как проверяемый рецепт

terraform {
  backend "s3" {
    bucket       = "YOUR_OWN_PREPARED_BUCKET"
    key          = "learning/service/terraform.tfstate"
    region       = "YOUR_REGION"
    use_lockfile = true
    encrypt      = true
  }
}

Рецепт не исполнялся и ничего не создаёт на хосте/в облаке. Для CLI 1.17.1 официальная документация поддерживает use_lockfile; доступ к state object и lock object настраивается отдельно. Версионирование bucket полезно для восстановления. Точный IAM, key prefixes, KMS и аудит проверяют по документации S3 backend и собственной системе. encrypt=true не выдаёт правильных прав и не защищает скачанный plaintext state на ноутбуке. Старые схемы DynamoDB locking и миграции имеют отдельные версии/ограничения; не включайте их по устаревшему блогу без сверки.

Одинаковый lock не означает одинаковый внешний объект

Условный опыт: A и B читают одну lineage L, serial 42. A получает lock, B с timeout 1 с отказывает, не выполняя свои действия. A сохраняет snapshot 43 и освобождает lock. Повтор B начинает новый план от 43; сохранённый план от 42 требует отдельной проверки актуальности. Числа условны, serial не счётчик ресурсов. Отрицательный случай — A выбрал key learning/a, B выбрал learning/b: locks теперь разные. Если оба state направлены на один API-объект X17, оба могут законно получить собственный lock и конфликтовать в API. Защищаемая сущность — один state; единственное владение X17 задают отдельно. Область блокировки.

Миграция backend — перенос ответственности

terraform init -migrate-state
terraform init -reconfigure

Первый режим предназначен для переноса существующего state в новую backend configuration и требует проверки источника/назначения. Второй отбрасывает прежнее сохранённое знание настройки backend и инициализируется по текущей конфигурации, не выполняя такую миграцию автоматически. Они не взаимозаменяемы. Перед переносом остановите конкурирующие runs, сохраните защищённую копию, проверьте lineage/serial и полный plan из нового места. Если отобразился пустой state, сначала проверьте destination, не запускайте create.

Командный процесс вокруг lock

Lock защищает один state от одновременных поддерживаемых операций, но не запрещает администратору менять API вручную и не создаёт distributed transaction между двумя states. Нужны единый владелец state, проверенный канал apply и запрет параллельных apply той же конфигурации вне процесса. Один lock может удерживаться долго из-за API; CI-очередь поверх него делает ожидание управляемым и связывает review с конкретным saved plan.

terraform force-unlock LOCK_ID используется только после подтверждения, что владелец блокировки прекратил работу и lock действительно осиротел, с учётом возможностей backend. Lock ID защищает от случайного освобождения другого lock, но не заменяет расследование. Local system lock обычно нельзя разблокировать из другого процесса этим способом. Сначала найдите действующий run/process, согласуйте остановку и проверьте state; не завершайте чужие процессы по совету из учебника.
