Drift и import: наблюдать, принять или вернуть управление

Drift — расхождение фактического объекта с ожидаемой конфигурацией/сохранённым знанием. Возможность его обнаружения ограничена Read-логикой provider и видимыми ему полями.

Разобрать расхождение на три решения

Представьте VM с size small в config и medium в API после ручного изменения. Сначала обычный plan читает текущее значение и предлагает возврат к small, если provider поддерживает это действие. Команда должна решить: вернуть config; изменить config на medium и принять намерение; либо сознательно передать поле другой системе через договор владения. ignore_changes — третий инженерный выбор с ценой невидимого для correction drift, а не универсальный способ получить зелёный plan.

Refresh-only план предлагает обновить state/outputs без обычного приведения объекта к config. Он полезен, когда согласованное внешнее изменение уже выполнено и нужно зафиксировать наблюдение. Но если config остаётся small, следующий обычный plan по-прежнему может предложить вернуть small. Принятие наблюдения и изменение желаемого — разные события.

Четыре записи одного условного внешнего объекта

В следующем примере provider умеет читать и менять size без замены. Объект X17 уже существует, а оператор снаружи сменил small на medium. Значения условны; это разбор решений по правилам plan, не выполненный вызов API и не существующий тип ресурса нашей лаборатории.

Файл, которого provider не знает

python3 -c 'from pathlib import Path; Path("rendered-api.json").write_text("changed outside Terraform\n")'
terraform plan -detailed-exitcode
terraform plan -replace='terraform_data.service["api"]' -out=repair.tfplan
terraform apply repair.tfplan

Команды выполняются только внутри помеченного стенда. Первый plan остаётся пустым в реально проверенном сценарии: Read terraform_data исследует свой input/output в state, а не сторонний файл. Replacement заново запускает writer и возвращает файл как creation effect. Это намеренно неудобный механизм: он меняет resource ID и может потребовать изменения зависимых записей. Нельзя рекламировать такое упражнение как пример полноценного управления файлами. Реальный тип файла должен иметь schema и Read, которые сравнивают нужные байты; его отдельная совместимость проверяется как у любого внешнего provider.

Import не создаёт прошлое

Import связывает существующий внешний объект с управляемым адресом. Он не переносит все зависимости, не доказывает пригодность конфигурации и не восстанавливает содержимое дисков. Поддержка import и формат идентификатора определяются resource/provider. После import план может предложить update или replacement, если HCL не описывает фактическую конфигурацию. Такой diff надо исследовать до apply.

# Форма декларативного import, ID здесь символический.
import {
  to = example_instance.api
  id = "provider-specific-object-id"
}
resource "example_instance" "api" {
  # Требуются настоящий provider, его schema и совместимые аргументы.
}

Это статическая схема интерфейса, тип example_instance не существует в лаборатории. Подготовьте карту: address → provider/source/version → account/region → фактическая identity → проверяемые атрибуты. Затем обычный plan показывает import вместе с последующими изменениями. Конфигурационные import blocks хранят намерение в review; imperative terraform import ADDRESS ID сразу меняет state при подходящем provider, не заменяя полный lifecycle review.

Отдельный реальный fixture labs/fixtures/address выполняет removed с destroy=false, затем возвращает прежний HCL и получает plan на create. После этого import block связывает terraform_data.owned с сохранённым ID, а конфигурация возвращает input. У встроенного ресурса import восстанавливает минимальную association по ID, не извлекает прежние данные из внешней системы. Это проверено CLI 1.17.1 и согласуется с importDataStore в исходниках; оно не подтверждает импорт VM или обнаружение потерянного облачного объекта.

Import, moved и removed отвечают разным вопросам

ДействиеДоПосле
importОбъект существует, association здесь отсутствуетИзвестная identity присоединена к адресу
movedAssociation есть по старому адресуТот же управляемый объект по новому адресу
removed destroy=falseAssociation есть и объект управляетсяОбъект оставлен, association забыта
destroyAssociation и управляемый объект существуютProvider выполняет удаление; при успехе association убирается

Смена Git-ветки после applied moved не записывает обратный moved. Возврат требует явного соответствия текущего и желаемого адреса. После removed возврат чаще требует import по фактической identity, а не простой отмены строки. Если поле ресурса по внешнему API immutable, новый конфиг может запланировать replacement даже после правильного import; связь с правильным объектом ещё не делает желаемое изменение безвредным.

Data source и пределы наблюдения

Data source, источник данных, читает сведения без управления его созданием и удалением. Если его аргументы неизвестны или связано изменяемое условие, чтение откладывается до apply и потребитель получает unknown в плане. Внешний API может возвращать неполную картину или сведения, ещё не отражающие недавние изменения; фильтр по неуникальному имени может выбрать не тот объект или дать отказ. Для критичного договора предпочитайте стабильный идентификатор и проверяйте account/region, а не совпадение display name.
