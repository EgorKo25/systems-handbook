Какую задачу решаем

Команда хочет получить два экземпляра сервиса с известными адресами, сетью и правилами доступа. Описание желаемого состояния хранится как текст. Но текст сам не создаёт машину: программа Terraform CLI читает его, строит зависимости, обращается к адаптерам конкретных систем и сохраняет связь между декларациями и фактическими объектами. CLI — command line interface, интерфейс командной строки. Provider, провайдер, — адаптер, который знает схему ресурса и операции внешнего API. Resource, управляемый ресурс, — объявление объекта; resource instance, экземпляр ресурса, — отдельный объект по конкретному адресу. State, состояние Terraform, — сохранённая память об этих связях и наблюдаемых атрибутах.

Слово association в документации означает соответствие: Terraform связывает адрес из конфигурации с идентичностью фактического объекта. Это связь в его памяти state. Она позволяет найти прежний объект для следующего действия; одинаковая строка имени или IP такой связи сама не создаёт.

Успешный apply означает завершение запланированных действий в границах Terraform и provider. Это ещё не доказательство готовности приложения для пользователя. Виртуальная машина может существовать, но SSH не отвечать; порт открыт, но схема базы ещё не совместима. Поэтому мы прослеживаем инициатора, входы, вызовы, изменения и критерий приёмки отдельно для каждого слоя.

Первичные источники и границы подтверждения

Книга языка объясняет, какие значения известны и когда. Книга исполнения показывает, как из ссылок получается граф и как provider участвует в plan. Книга модулей связывает интерфейс с адресами и миграцией. Книга состояния рассматривает отказ и совместную работу как нормальную часть жизни системы. Эксплуатационные главы добавляют измерения, офлайн-перенос и договор с инструментом настройки ОС. Читать удобно последовательно; для аварии начните с главы о восстановлении, но не исполняйте её рецепты без определения backend и владельца.

Честный фундамент практики

Лаборатория использует встроенный terraform_data: он хранит входное значение и участвует в жизненном цикле, не создаёт VM, сеть или процесс сервера. Отдельный учебный provisioner, однократное действие при создании ресурса, пишет два JSON-файла в выбранной постоянной учебной области. Эти файлы специально показывают границу ответственности: наличие записи в state не делает файл управляемым объектом с чтением drift. Ни локальный стенд, ни схемы в браузере не подменяют запуск настоящего cloud/provider API.

Рабочая область сохраняется между упражнениями. Команды подготовки не перезаписывают существующий каталог, ошибка apply не вызывает reset. Снимок и восстановление — отдельные действия с сохранением предыдущей копии. Автоматический тест создаёт собственную временную область и удаляет её после серии проверок; он не является командой продолжения читательского стенда.

Выбор версии — инженерный вход

Начните с официальной страницы установки, затем откройте каталог конкретного выпуска и его release notes. Выберите стабильную версию, совместимую с существующим state, провайдерами и правилами команды. В этой редакции базовый CLI зафиксирован на 1.17.1; это воспроизводимый вход, а не обещание, что будущий последний выпуск подходит любому проекту. Номер CLI, версия языка provider protocol, версия provider и версия модуля — разные величины. required_version проверяет CLI; provider не обновляется от одного нового бинарника.

На Linux uname -m помогает определить архитектуру: x86_64 соответствует linux_amd64, aarch64 — linux_arm64. Архив Windows содержит terraform.exe; Linux-бинарник не запускается обычной командой Windows. Контейнер переносит часть среды, но не меняет полномочия API-учётных данных. В рецепте ниже нужны Bash, curl, GnuPG, awk, unzip и sha256sum в личной VM. Полный отпечаток ожидаемого основного ключа уже сверён для этого выпуска; перед другим выпуском его получают по доверенному независимому каналу до запуска сценария. Установка пакетов ОС здесь не выполняется.

Загрузка и цепочка проверки

tf_verified_install() {
  bash <<'TF_INSTALL'
set -euo pipefail
TF_RELEASE=1.17.1
TF_PACKAGE=terraform_${TF_RELEASE}_linux_amd64.zip
TF_PRIMARY=C874011F0AB405110D02105534365D9472D7468F
mkdir -p "$HOME/terraform-learning/download" "$HOME/terraform-learning/bin"
cd "$HOME/terraform-learning/download"
curl --fail --location --output "$TF_PACKAGE" \
  "https://releases.hashicorp.com/terraform/$TF_RELEASE/$TF_PACKAGE"
curl --fail --location --remote-name \
  "https://releases.hashicorp.com/terraform/$TF_RELEASE/terraform_${TF_RELEASE}_SHA256SUMS"
curl --fail --location --remote-name \
  "https://releases.hashicorp.com/terraform/$TF_RELEASE/terraform_${TF_RELEASE}_SHA256SUMS.sig"
curl --fail --location --output hashicorp.asc \
  https://www.hashicorp.com/.well-known/pgp-key.txt
mkdir -m 700 gpg
gpg --homedir "$PWD/gpg" --import hashicorp.asc
gpg --homedir "$PWD/gpg" --fingerprint
status=$(gpg --homedir "$PWD/gpg" --status-fd 1 --verify \
  "terraform_${TF_RELEASE}_SHA256SUMS.sig" "terraform_${TF_RELEASE}_SHA256SUMS")
printf '%s\n' "$status" | awk -v primary="$TF_PRIMARY" \
  '$1 == "[GNUPG:]" && $2 == "VALIDSIG" && $NF == primary { ok=1 }
   END { exit !ok }'
awk -v package="$TF_PACKAGE" \
  '$2 == package || $2 == "*" package { print; n++ }
   END { if (n != 1) exit 1 }' \
  "terraform_${TF_RELEASE}_SHA256SUMS" | sha256sum --check -
unzip "$TF_PACKAGE" terraform -d "$HOME/terraform-learning/bin"
TF_INSTALL
}
if tf_verified_install; then
  export PATH="$HOME/terraform-learning/bin:$PATH"
  command -v terraform
  terraform version
  terraform version -json
else
  printf '%s\n' 'Установка остановлена: CLI не запускается.' >&2
fi

--fail превращает HTTP-ошибку в неуспешный код, --location разрешает перенаправления, --output задаёт локальное имя; без него ZIP попадёт в stdout. Подпись проверяет файл ожидаемых сумм, а сумма связывает выбранный архив с этим файлом. Случайная сумма с того же недоверенного носителя не доказывает происхождение. Отпечаток ключа сверяют с официальным материалом по независимому доверенному каналу; не назначают доверие только ради исчезновения предупреждения GPG.

Для реально проверенного выпуска основной fingerprint: C874 011F 0AB4 0511 0D02 1055 3436 5D94 72D7 468F. Подпись сделана подключом 374E C75B 4859 1360 4A83 1CC7 C820 C6D5 CD27 AB87. Сроки и ключи могут меняться; перед другим выпуском перечитайте официальную проверку бинарников. Сообщение Good signature при неизвестном локальном доверии означает криптографически верную подпись данным ключом; вопрос принадлежности ключа решается отдельно. Несовпадение суммы — остановка, не повод распаковать другой файл наугад.

Распаковка и приёмка

Переход к распаковке находится внутри проверяемого сценария. Внешняя оболочка добавляет каталог в PATH и запускает CLI только после его успеха. Новый процесс Bash включает остановку при ошибке и проверку конвейеров; отказ GPG, неподходящий основной ключ, отсутствие единственной строки суммы выбранного ZIP или несовпадение суммы не достигают unzip. Существующий каталог gpg здесь вызывает отказ: для повторения сначала исследуйте прежние файлы, затем выберите отдельный собственный каталог загрузки.

Сравните обычный и JSON-вывод: первый удобен человеку, второй представляет сведения о версии как JSON для программы. Проверяйте именно terraform_version и platform, не фиксированный порядок строк. command -v помогает обнаружить прежний binary раньше в PATH. Ошибка Exec format error указывает на несовместимый формат/архитектуру, Permission denied — на права исполнения либо ограничения монтирования. Права на бинарник не дают прав на чужую инфраструктуру.

Что появится в ОС и что взять офлайн

Terraform CLI — конечный процесс на время команды; обычный local backend не требует постоянного демона или открытого серверного порта. Внешние providers могут запускаться дочерними процессами и обращаться по сети к registry/API. Пользовательский CLI-конфиг находится в ~/.terraformrc на Unix, в Windows — %APPDATA%/terraform.rc; переменная TF_CLI_CONFIG_FILE выбирает другой файл. Не переносите туда реальные токены для публичной демонстрации. Для лаборатории достаточно бинарника, исходников и Python; нет внешнего provider-пакета. Для другой конфигурации офлайн нужны также модули, платформенные пакеты providers, lock file, CLI-конфиг mirror и доверенный материал проверки. Один ZIP Terraform их не содержит.

Контрольные вопросы приёмки: известны источник и сумма; запускается нужная версия; собственный каталог доступен для записи; terraform init и terraform validate проходят на первом примере. Отсутствие связи с cloud не ошибка этого фундамента: VM мы пока не создавали.

Как прочитать конфигурацию до первого запуска

Файлы .tf написаны на HCL — языке описания конфигурации. Блок resource "terraform_data" "service" { ... } объявляет ресурс типа terraform_data с локальным именем service; строки внутри задают его аргументы. Это описание желаемого состояния, а не последовательность shell-команд. variable "services" объявляет вход, а var.services читает его значение. Здесь это соответствие имён api/worker их портам и меткам сборки. for_each создаёт отдельный экземпляр для каждого ключа; each.value означает значение текущего элемента. Поэтому два имени дают два адреса, которые можно наблюдать независимо.

Модуль — каталог связанных файлов конфигурации с объявленными входами и выходами. Корневой модуль — каталог, из которого запускают Terraform; блок module подключает дочерний. Выход output публикует вычисленное значение для читателя или другого модуля. В полном примере дочерний receipt хранит две записи, а отдельный gate служит контрольной точкой намеренного отказа. Они тоже ресурсы, поэтому в первом state будет пять адресов. Их назначение подробнее разберём после наблюдения первого запуска; ни один из этих объектов не является виртуальной машиной.

Подготовить один стенд

Начните из каталога тома terraform/, где находится labs/. Используйте копию каталога labs/ из тома. python3 нужен только для собственных локальных сценариев; встроенный provider Terraform не скачивается. Выберите новый постоянный путь в собственном домашнем каталоге. Далее TF_LAB_ROOT всегда указывает на этот же каталог; не меняйте его при каждом шаге.

TF_LAB_TOOLS="$PWD/labs"
umask 077
mkdir -p "$HOME/terraform-learning/stands" "$HOME/terraform-learning/snapshots"
TF_LAB_ROOT="$HOME/terraform-learning/stands/foundation"
TF_LAB_SNAPSHOT="$HOME/terraform-learning/snapshots/foundation-checkpoint-1"
printf 'tools=%s\nroot=%s\nsnapshot=%s\n' "$TF_LAB_TOOLS" "$TF_LAB_ROOT" "$TF_LAB_SNAPSHOT"
if python3 "$TF_LAB_TOOLS/lab.py" prepare "$TF_LAB_ROOT"; then
  cd "$TF_LAB_ROOT" &&
  terraform init -input=false &&
  terraform fmt -check -recursive &&
  terraform validate &&
  terraform plan -out=first.tfplan &&
  terraform show first.tfplan &&
  terraform apply first.tfplan &&
  terraform state list &&
  terraform output -json contract &&
  terraform plan -detailed-exitcode
else
  printf '%s\n' 'Подготовка отказала; дальнейшие Terraform-команды не выполнены.' >&2
fi

Сохраните три напечатанных абсолютных пути в собственной заметке. В новом терминале присвойте переменным эти же значения, затем перейдите в TF_LAB_ROOT; повторный mktemp создал бы другой стенд. Рабочая область и контрольная точка находятся в постоянных каталогах, вне /tmp. Подготовка создаёт только отсутствующий foundation; заранее создавать сам этот каталог не нужно. Сохраните также путь и версию CLI, тип backend local и наличие маркера: это паспорт именно вашего стенда. Резерв на том же диске переживает очистку /tmp, но не отказ диска; собственную проверенную копию переносите отдельно. prepare создаёт только новый каталог и файл-маркер. Повторный prepare завершается отказом, сохраняя предыдущую работу. Для продолжения перейдите в прежний каталог. init готовит backend и локальный модуль modules/receipt. fmt -check проверяет оформление, ничего не исправляя; validate проверяет структуру и согласование типов. Plan без apply не создаёт учебные resource instances. Apply сохранённого файла выполняет уже выбранные действия без обычного вопроса подтверждения; просмотр файла перед этим существенен.

Минимальная механика

resource "terraform_data" "service" {
  for_each         = var.services
  input            = each.value
  triggers_replace = each.value.build
}
output "ids" {
  value = { for k, s in terraform_data.service : k => s.id }
}

Это сокращённый фрагмент, полный пример находится в labs. Для api и worker образуются два адреса terraform_data.service["api"] и terraform_data.service["worker"]. Input содержит порт и метку сборки. Встроенный terraform_data присваивает ID и сохраняет input как output. Локальный модуль создаёт ещё две записи контракта, gate — пятую контрольную запись. Поэтому число адресов больше двух. Никакой сокет 8080 не открывается: число port пока только значение в state.

Provisioner полного примера получает JSON через environment и вызывает write_receipt.py. Скрипт проверяет маркер и имя, затем записывает rendered-api.json и rendered-worker.json только в корне стенда. Этот одноразовый эффект позволяет наблюдать байты файлов, но terraform_data не умеет читать эти файлы как состояние ресурса. Изменение файла вручную не обязано дать plan с изменениями. Это ограничение используется в упражнении, а не скрывается.

Карта файлов

 | Объект | Кто пишет | Зачем и как хранить

 | main.tf, modules/receipt/main.tf | Автор | Декларации, интерфейс, зависимости; версионируются.

 | *.tfvars, *.auto.tfvars.json | Автор/автоматизация | Значения входов; секретные варианты не публикуют.

 | .terraform/ | init | Инициализация backend, индекс модулей, внешние пакеты providers при наличии; не общий переносимый state.

 | .terraform.lock.hcl | init/providers lock | Выбор внешних providers и допустимые checksums; при одном built-in provider может отсутствовать.

 | terraform.tfstate и backup | CLI/backend | Текущая и резервная память local backend; чувствительны, не добавляются в Git.

 | *.tfplan | plan -out | Сохранённый план с конфигурацией и данными; требует контроля доступа.

 | rendered-*.json | Учебный provisioner | Локальный эффект создания; существование файла не доказывает его актуальность.

Коды завершения и первое расхождение

У обычного terraform plan код 0 может означать успешный план с изменениями. У terraform plan -detailed-exitcode код 0 означает отсутствие изменений, 2 — успешный непустой diff, 1 — ошибку. В shell с set -e значение 2 требует явной обработки; нельзя назвать его провалом provider. Первый запуск в пустом state даёт непустой plan; после apply следующий план должен стать пустым. Это реально проверяется тестом. Точный UUID и длительность заранее не фиксируются.

Если validate не видит локальный модуль, проверьте, скопирован ли весь foundation, и выполнен ли init. Если writer сообщил отсутствие маркера, исследуйте текущий каталог, не удаляйте проверку безопасности. При аварии сохраните конфиг, команду, stderr и state; следующий apply продолжает известное состояние. Отдельная глава объясняет, что делать после частичного выполнения.

Сначала разбор, затем интерпретация

В resource "terraform_data" "service" { input = var.services } resource — тип блока, следующие две строки в кавычках — его метки, input — аргумент. Скобки ограничивают тело. HCL сам не знает, что такое сеть или terraform_data: это смысл Terraform и схемы provider. Комментарии и порядок блоков в файле не образуют последовательность shell. Все обычные .tf файлы одного модуля читаются вместе; имена main.tf и outputs.tf помогают людям, но не задают порядок действий. Подкаталог сам не подключается как модуль.

Синтаксическая ошибка, ошибка типа и отказ внешнего API происходят в разные моменты. Пропущенная закрывающая скобка обнаруживается до вызова provider. Число не того диапазона может пройти тип number, но остановиться validation. Допустимый порт может быть занят на реальной машине — это уже свойство целевой системы, которого один parser не проверяет.

Примитивы и структурные типы

string — строка Unicode, number — число в модели значений Terraform, bool — true или false. У числа нет смысла «миллисекунды» без договора; timeout_ms = 500 и timeout_seconds = 500 равны как числа, но различны как инженерные входы. Не считайте number машинным int64 и не используйте его для байтовой точности протокола без проверки внешней схемы.

 | Тип | Что фиксирует | Пример

 | list(T) | Упорядоченную последовательность одного типа | list(string), повторения разрешены

 | set(T) | Неупорядоченное множество уникальных элементов | toset(["api", "api", "worker"]) содержит два имени

 | map(T) | Строковые ключи и однотипные значения | Имя сервиса → объект настроек

 | tuple([...]) | Тип каждой позиции | tuple([string, number])

 | object({...}) | Имена и типы полей | object({port=number, build=string})

Литерал ["api", 8080] естественно имеет tuple-форму, а {port=8080, build="b1"} — object-форму. Преобразование к list/map происходит при согласовании с требуемым типом и может преобразовать элементы. Если ожидается list(string), число 8080 может стать строкой; это удобно на границе, но опасно как скрытая нормализация неверного входа. Преобразование объекта к более узкому object может отбросить дополнительные атрибуты. Поэтому опечатка в лишнем поле не всегда обнаруживается так, как ожидает автор.

Схема сервиса как точный договор

В следующем типе optional отмечает необязательное поле объекта; второй аргумент задаёт значение по умолчанию. Например optional(bool, true) подставляет true и при пропуске enabled, и при явном null. Это правило преобразования входа, а не отдельная операция над инфраструктурой.

variable "services" {
  type = map(object({
    port    = number
    build   = string
    enabled = optional(bool, true)
    tags    = optional(map(string), {})
  }))
}

Ключ map — стабильная идентичность экземпляра; port и build — данные. optional позволяет не передавать поле и задаёт предсказуемое значение по умолчанию. Это не означает, что любой отсутствующий ключ внешнего JSON автоматически допустим. Вход сначала преобразуется к указанному типу. При вложенных optional-объектах проверьте поведение и для пропуска, и для явно переданного null. Простой интерфейс с двумя полями легче совместимо развивать, чем свободная map(any), смысл которой скрыт в десятках выражений.

any — не универсальный runtime-тип значения. В type constraint это просьба подобрать конкретный совместимый тип. Для передачи непрозрачного JSON допустим any вместе с jsonencode, если модуль не исследует структуру. Если вы читаете var.options.port, объявите структуру; иначе ошибка уедет от входной границы к случайному обращению внутри модуля.

Null, пустое значение и отсутствие

null означает отсутствие конкретного значения; это не пустая строка, не ноль и не пустая коллекция. Для аргумента ресурса null обычно ведёт себя как пропуск аргумента, после чего применяются default и требования схемы. Но provider может предъявить свои условия. [] явно задаёт пустую последовательность, {} — пустую структуру; они могут означать удалить все правила, тогда как null — оставить значение по умолчанию. Такая разница особенно опасна для доступа и списков подсетей.

У variable есть nullable = false, если null нельзя принимать на границе. Он не делает все вложенные поля непустыми. Для строк отдельно проверяют trimspace, для набора — длину, для чисел — целочисленность и диапазон. Ошибка вида «value must not be null» должна назвать требование, которое нарушено, а не предлагать пользователю изучать внутренний local.

Один объект: пропуск, null и пустая строка

Для объявленной выше схемы передайте services = {api = {port = 8080, build = "b1", enabled = null}}. После преобразования var.services["api"].enabled равен true: у optional указан ненулевой default. Пропуск enabled даёт тот же результат, явный false сохраняется. Но build = null не становится строкой "b1": обязательность поля и запрет null — разные требования. В foundation проверка непустого build должна диагностировать и null, а не вычислять trimspace от отсутствующего значения.

Предскажите tolist(["api", 8080]): оба элемента согласуются как строки, результат — ["api", "8080"]. Отрицательный случай tolist(["api", []]) не имеет общего типа элементов и должен дать ошибку. Для object({port=number}) вход {port=8080, porrt=9000} теряет лишнее поле porrt при преобразовании; поэтому отсутствие ошибки не подтверждает правильность всех написанных имён. В foundation у services есть default и nullable=false: null всего корневого services выбирает default, но null вложенного build остаётся недопустимым. Это предсказания по правилам типов CLI 1.17, а не новые измерения. Правила преобразования и optional.

> tolist(["api", 8080])
> toset(["api", "api", "worker"])
> null == ""
> length({api = 8080, worker = 8081})

Console вычисляет выражения в контексте конфигурации и state; это не shell, exit завершает его. Сначала предскажите тип и число элементов, затем сравните реальный ответ CLI. Не считайте порядок печати set договором порядка исполнения. For — выражение над коллекцией

Дальше показаны отдельные фрагменты языка, а не последовательные изменения основного main.tf. Поле enabled принадлежит расширенной схеме services из главы о типах; в начальном стенде такого поля нет. Для вычисления этих фрагментов нужны объявленные входы именно этой схемы. Не вставляйте их в рабочий стенд, сохранив прежний тип services: обращение к несуществующему полю даст ошибку.

locals {
  ports = [for name, s in var.services : s.port if s.enabled]
  routes = {
    for name, s in var.services : name => {
      endpoint = "127.0.0.1:${s.port}"
      build    = s.build
    } if s.enabled
  }
  by_port = { for name, s in var.services : tostring(s.port) => name... }
}

Квадратные скобки создают последовательность результатов; фигурные — объект с вычисленными ключами. if фильтрует элементы, а не запускает отдельные ресурсы. Повтор ключа объекта обычно ошибка. Троеточие после значения включает grouping mode — группировку нескольких имён в список для одного ключа, здесь порта. Это полезно для поиска конфликтов: два имени на одном порту будут видны одной группой, а не затрут друг друга. Порядок полученного списка и key sorting проверяют перед использованием как порядкового контракта.

Условия и функции

condition ? a : b выбирает значение, но обе ветви должны иметь согласуемые типы. Условие не разрешает произвольные синтаксические ошибки в невыбранной ветви. Если ветви «строка» и «число» согласуются как строки, дальнейший потребитель получает именно строку. Явная tostring или единая object-схема делает намерение видимым. Не стройте коллекции из магии неявных преобразований.

lookup выбирает ключ с default, try возвращает первое выражение без динамической ошибки, can проверяет, удалось ли вычисление. Они не исправляют недопустимую ссылку на несуществующий resource block и не означают «пока unknown, возьми default». Unknown может быть корректным результатом без ошибки. Сосредоточьте нормализацию внешних данных в одном local, затем используйте строгие значения. Try вокруг каждой строки прячет ошибки и делает эксплуатацию непредсказуемой.

Следующий фрагмент требует заранее созданного services.json, например {"timeout_seconds":20}, и отдельного входа tags со следующим объявлением. Это иллюстрация функций: основной стенд эти дополнительные входы и файл сам не создаёт.

variable "tags" {
  type    = map(string)
  default = {}
}

locals {
  source  = jsondecode(file("services.json"))
  timeout = try(tonumber(local.source.timeout_seconds), 15)
  names   = sort(keys(var.services))
  merged  = merge({owner = "lab"}, var.tags)
}

file читает уже существующий файл при вычислении; он не ждёт provisioner только потому, что тот позже создаст такой путь. Функция не участвует в графе как управляемый ресурс. Для шаблона используйте templatefile с явной map переменных; для детерминированного diff — стабильные входы. timestamp() меняется между запусками и способен дать постоянный diff. Не добавляйте текущее время в triggers только для «актуальности» без намерения каждый раз выполнять эффект.

Unknown — обещание значения с типом

Unknown, неизвестное значение, означает: тип/структура частично известны, конкретные данные появятся после действий. В первом plan UUID terraform_data неизвестен, но ключи map api и worker уже известны. Поэтому можно построить по ключам два зависимых экземпляра, даже если значения их input содержат unknown. Если же UUID сделан ключом for_each, Terraform не знает адресов будущих экземпляров и обычный plan откажет. Это различие между неизвестным содержимым и неизвестной формой графа.

Над неизвестным значением некоторые результаты всё же известны: объект с полем id неизвестного содержания остаётся объектом с известным именем поля. length списка с тремя неизвестными элементами может быть известной тройкой. Но фильтр, решение которого зависит от unknown, делает размер результата неизвестным. Сохраняйте стабильные ключи из конфигурации и передавайте поздние идентификаторы в values.

Отдельно проверить ошибку, null и unknown

В первом плане fixture unknown-good адрес terraform_data.consumer["primary"] уже определён. Выражение try(terraform_data.source.id, "fallback") остаётся неизвестным: чтение объявленного id не является ошибкой. После создания source тот же потребитель получает фактическую строку ID. Иной случай: для известного local.source = {} чтение отсутствующего local.source.timeout_seconds внутри try даёт fallback 15 из примера выше. Если поле существует и равно null, tonumber(null) даёт null, поэтому try также не выберет 15. Для выбора значения при null нужен явно иной смысл, например coalesce после согласования типов.

Самопроверка: почему нельзя исправить unknown-ключ for_each обёрткой try? Ответ: успешное вычисление неизвестного значения не создаёт известный ключ. А ссылка на вообще необъявленный local не становится допустимой благодаря try: это ошибка конфигурации. Область обработки ошибок try.

Sensitive — ограничение отображения

Чувствительная метка sensitive распространяется на результаты вычисления и помогает скрывать вывод CLI. Это не криптографический контейнер и не означает, что значение отсутствует в state/plan. Чувствительный список имён нельзя бездумно использовать как ключи ресурсов: адреса видны в планах и журналах. nonsensitive снимает метку после осмысленного решения автора, но не удаляет секрет из байтов. Эфемерные значения и write-only arguments имеют отдельную поддержку CLI/provider и ограничения контекстов; они не делают обычные arguments эфемерными задним числом.

Validation проверяет смысл входа

  type     = number
  nullable = false
  validation {
    condition = var.port >= 1024 && var.port <= 65535 && floor(var.port) == var.port
    error_message = "port: целое число от 1024 до 65535 для учебного непривилегированного сервиса."
  }
}
variable "stage" {
  type    = string
  default = "dev"
  validation {
    condition     = contains(["dev", "test"], var.stage)
    error_message = "stage должен быть dev или test в этом стенде."
  }
}

Тип number сам по себе не отвергает дробь. Здесь validation фиксирует единицы и допустимую область упражнения, а не универсальное правило всех TCP-портов. Проверка не доказывает свободность порта и не выдаёт OS-права. Для map сервисов проверьте каждый элемент через alltrue, при необходимости уникальность портов через длины distinct и исходной последовательности. Непустой build тоже самостоятельное требование, если от него зависит замена объекта.

Local — имя вычисления

locals не является изменяемой переменной Go. Это именованные выражения, которые вычисляются по зависимостям. Сколько бы блоков locals ни было, ссылаться нужно через local.name. Цикл a = local.b + 1, b = local.a + 1 не имеет первого значения и недопустим. Разделяйте исходный input, нормализованную структуру и итоговый контракт. Повторять три почти одинаковых for-выражения труднее проверять, чем назвать один вычисленный объект.

Но local не кэш для внешнего HTTP-запроса, не транзакционная таблица и не способ управлять временем выполнения. Значение с unknown остаётся unknown настолько, насколько требует его выражение. Избыточные преобразования map → list → map теряют связь со стабильными ключами и усложняют понимание плана.

Output — опубликованная граница

output "contract" {
  description = "Версионируемый учебный договор для потребителя; не SSH-секреты."
  value = {
    schema_version = 1
    services = {
      for name, s in terraform_data.service : name => {
        resource_id = s.id
        port        = s.output.port
      }
    }
  }
}

Root outputs попадают в state и читаются terraform output; child outputs нужны вызывающему модулю. Выходное имя и тип — публичный интерфейс. Смена port на listen_port ломает потребителя даже при отсутствии замены VM. Избегайте output целого resource object «на всякий случай»: он связывает потребителя со схемой provider и может включить чувствительные данные. terraform output -json удобен автоматизации, но раскрывает значения sensitive outputs; права на stdout/артефакт должны быть соответствующими.

Где условие останавливает действие

Variable validation проверяет вход, precondition — условие до соответствующей операции, postcondition — условие по полученному результату. Они могут обнаружить несоответствие и остановить дальнейшие зависимые действия, но не откатят уже созданные объекты. check предназначен для проверки предположений и выдаёт предупреждения при невыполненном утверждении в обычных операциях; он не заменяет блокирующую precondition для обязательного требования. При unknown часть условий может быть отложена до apply. Всегда называйте момент, в который условие получает все данные.

Для теста интерфейса достаточно входов: граница/вне границы, null/пропуск, пустая map, повтор порта, unknown-значение из ресурса. terraform test может выполнять реальные apply и требует изоляции; mock provider проверяет определённую логику модуля, не фактическое API. В практикуме реальные CLI-проверки работают только с terraform_data и собственными файлами.

Count делает адресом индекс

resource "terraform_data" "slot" {
  count = length(var.names)
  input = var.names[count.index]
}

Если names = ["api", "worker", "batch"], адреса оканчиваются на [0], [1], [2]. Удаление первого имени смещает значения двух остальных индексов. Terraform сопоставляет существующие объекты по адресу, поэтому изменение списка может выглядеть как изменение нескольких экземпляров вместо простого удаления api. Конкретные update/replacement зависят от схемы ресурса. Count подходит, когда индекс действительно часть модели, либо для нуля/одного необязательного объекта с пониманием адреса [0].

Сравните count = var.enabled ? 1 : 0 и for_each = var.enabled ? {main = true} : {}. В первом случае потребитель обращается к списку, во втором — к map с ключом main. Оба варианта меняют наличие объекта; это не просто скрытие строки вывода. Если enabled неизвестен до apply, Terraform может не суметь определить набор экземпляров.

Что именно меняется после удаления api

Fixture collection начинается с ["api", "worker", "batch"]. У terraform_data.indexed сохранены [0]→api, [1]→worker, [2]→batch. При входе ["worker", "batch"] план этой схемы содержит update [0] api→worker, update [1] worker→batch и delete [2]. Их идентичности не следуют за именем сервиса: сохраняются индексы. У параллельного keyed с for_each = toset(var.names) исчезает только ["api"]; ["worker"] и ["batch"] получают no-op. Именно эти actions проверяет сохранённый check_language.py. Если вместо input менялся бы атрибут с требованием замены, цена сдвига была бы другой.

For_each делает адресом ключ

resource "terraform_data" "service" {
  for_each = var.services
  input    = { port = each.value.port, build = each.value.build }
}

С map имена api и worker стабильны независимо от порядка текста. Удаление worker удаляет соответствующий экземпляр, изменение api.port сохраняет адрес api. Но переименование ключа api → edge без moved — удаление старого и создание нового адреса, даже если значение совпало. Имена выбирают по долговременной предметной идентичности, не по IP, случайному UUID или текущей позиции в файле.

For_each принимает map или set(string); список строк не преобразуется в set автоматически. Используйте toset только если потеря повторений и порядка соответствует задаче. Для set each.key и each.value совпадают. Для map значения могут оставаться неизвестными, если ключи определены. Чувствительные значения как полный for_each недопустимы, когда через них раскрылись бы ключи/идентичности. Отделите публичные ключи от закрытых данных; снятие sensitivity не должно раскрыть секретные имена.

Связать наборы без лишних барьеров

module "receipt" {
  source = "./modules/receipt"
  values = {
    for name, s in terraform_data.service : name => {
      id = s.id
      port = s.output.port
      build = s.output.build
    }
  }
}

Это один экземпляр модуля, внутри которого два экземпляра record. Альтернатива — module "receipt" { for_each = var.services ... }: тогда адрес включает module.receipt["api"]. В обоих случаях делайте graph из устойчивых имен и передавайте ID в содержимом. Ссылка на конкретный service связывает данные; общий depends_on на весь модуль способен задержать и те записи, которые фактически не используют изменяемый ресурс.

Dynamic генерирует вложенную конфигурацию

Dynamic block не создаёт самостоятельного resource address. Он раскрывает повторяющиеся вложенные блоки, предусмотренные схемой конкретного provider, например правила rule в гипотетическом ресурсе firewall. Блок ниже — только форма языка; для выполнения нужен реальный тип с такой схемой.

dynamic "rule" {
  for_each = var.rules
  iterator = item
  content {
    port   = item.value.port
    source = item.value.source
  }
}

iterator переименовывает локальное имя для читаемости вложенных циклов. Нельзя сгенерировать через dynamic произвольный resource, module или мета-блок lifecycle: Terraform должен понимать некоторые части до вычисления обычных expressions. Если аргумент схемы ожидает list(object), передайте for-выражение как значение, а не придумывайте nested block. Разница argument/block определяется provider schema.

Проверяем цену формы графа

Сначала выпишите ожидаемые адреса двух вариантов на бумаге, затем посмотрите terraform state list и JSON-план после удаления первого элемента. Измеряйте не только строку «N to change», но какие action адреса получили. Для реального облака каждый лишний replacement имеет длительность, квоты и потенциальную недоступность. В terraform_data это дешёвый опыт, в VM — изменение рабочего объекта. Миграцию count → for_each проводят через явные moved с известным соответствием старого индекса новому ключу, а не через надежду, что Terraform распознает одинаковое имя.

Приёмка и диагностика init

Что подготавливает init

terraform init исследует корневую конфигурацию, настраивает backend, получает дочерние модули и устанавливает требуемые внешние providers. Backend — механизм хранения state и, если поддерживается, блокировки. Это не provider ресурса. Для local backend состояние остаётся файлом; для remote backend нужна отдельная конфигурация доступа. Init может обращаться в сеть ещё до plan, даже если ресурсы создавать пока не собирались. В лаборатории источник модуля локальный и provider встроенный, поэтому подготовленные исходники и binary достаточны для исполнения без registry.

required_providers связывает локальное имя с полным source address и ограничением версии. В hashicorp/aws опущен стандартный hostname registry; полная идентичность имеет три части hostname/namespace/type. Provider block с тем же локальным именем задаёт конфигурацию подключения, например регион и credential chain. Версия устанавливаемого плагина определяется совокупностью constraints модулей и lock file, а не полем региона.

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}
provider "aws" { region = "eu-central-1" }

Это только пример разделения source/configuration, не лаборатория AWS и не рекомендация покупать ресурс. Он требует проверки конкретной совместимости версии provider, учётных данных и схемы. Версия ~> 6.0 допускает обновления внутри major 6; для воспроизводимости выбранный пакет и hashes фиксирует lock file. В 1.17 появились дополнительные возможности вычислений в provider requirements; фундамент использует обычные явные строки, чтобы источник и constraints были видны при review.

Процесс и протокол

Для обычного внешнего provider Terraform CLI запускает установленный plugin как отдельный процесс. Plugin — исполняемое расширение, а не произвольная загружаемая .so библиотека. Совместимость определяется в том числе версией Terraform Plugin Protocol. Документированный современный протокол использует gRPC и определения Protocol Buffers; protocol 5 и 6 — разные основные варианты интерфейса. Это граница взаимодействия Core/provider, не сетевой API облака. Provider может иметь собственный SDK, HTTP retry и authentication к внешнему сервису.

Что схема сообщает, а чего не сообщает

Schema — описание формы значений. Required требует аргумент, optional допускает пропуск, computed разрешает provider получить значение при исполнении. Проверка схемы отвергнет строку там, где требуется объект; она не проверит, что учётная запись имеет доступ к выбранному объекту. В libvirt-адаптере это уже дало конкретное различие: boot_devices должен содержать объекты [{dev="hd"}], а не строки ["hd"].

RPC — вызов операции между процессами Core и внешнего provider. Для мысленного разбора одного изменения предположим прежний объект X17 и новую конфигурацию. ReadResource возвращает наблюдение; PlanResourceChange получает прежние и предлагаемые значения и может потребовать replacement; ApplyResourceChange получает согласованный план и возвращает новое состояние вместе с диагностикой. Отсутствующий объект в прежнем состоянии (null) обозначает создание; null вместо всего планируемого объекта — удаление. Это не число ноль и не пустой список действий. Неизвестные computed-значения уточняются при выполнении. Это описание сообщений, а не запись реального сетевого обмена нашего встроенного provider. Операции RPC.

Provider не вправе молча заменить уже согласованное известное значение произвольным другим: несовместимый результат может дать ошибку согласованности. Если API нормализует данные, схема и планирование должны учитывать это заранее. Настройка региона или alias не меняет этих требований. Согласованность плана и результата.

Сначала Core получает schema: какие resource/data source типы существуют, какие arguments required/optional/computed, где nested attributes. Затем конфигурация проверяется и значения готовятся в соответствии с этой схемой. На conceptual path встречаются RPC GetProviderSchema, проверки конфигурации, ReadResource, PlanResourceChange, ApplyResourceChange. Реальное число/порядок вызовов зависит от операции, графа, версии protocol и provider. На этой странице нет выдуманного дампа protobuf, номера TCP-порта или обещания одного RPC на один ресурс. Канонический интерфейс смотрите в исходниках protocol выбранного CLI.

terraform_data — исключение лаборатории: он поставляется встроенным provider terraform.io/builtin/terraform, поэтому упражнение не подтверждает запуск внешнего provider process. Посмотреть схему можно настоящей командой terraform providers schema -json. Это поможет отличить проверенную модель Core от реального сетевого адаптера. Появление слова provider в схеме не доказывает HTTP-запрос к облаку.

Кто владеет чем

Core отвечает за выражения, адреса, связи, согласование плана и сохранённого state. Provider определяет возможности объекта, выясняет его текущие атрибуты и выполняет операции внешней системы. Внешняя система решает, действительно ли создан объект и какие ограничения действуют. Если API принял запрос асинхронно, provider может ждать готовности до своего timeout. Даже после успешного ответа отложенная согласованность способна влиять на следующий запрос; правильная retry/wait логика обычно относится к provider, а не к декоративному depends_on.

Приёмка и диагностика init

terraform init -input=false
terraform providers
terraform providers schema -json
terraform init -input=false -lockfile=readonly

Сравните первый и последний вызов: обычный init может записать новый выбор providers, readonly требует сохранить существующий lock file и отказывает при необходимом изменении. Он не делает весь рабочий каталог read-only и не заменяет доступ к package source. Ошибки DNS/TLS, несовместимость constraints и checksum mismatch имеют разные причины. Не решайте отказ суммы удалением lock file без расследования: это уничтожает ожидаемую границу доверия. При смене backend init попросит явную миграцию/переконфигурацию; эти режимы разобраны в книге state.

При этом api и worker не ссылаются друг на друга и могут быть готовы одновременно. Граф — ориентированный набор вершин и отношений «потребитель зависит от поставщика»; ацикличность означает отсутствие замкнутой цепочки взаимного ожидания. На рисунке направление подписано действием: не смешивайте стрелку потока данных и стрелку внутреннего dependency graph.

resource "terraform_data" "source" { input = "b1" }
resource "terraform_data" "consumer" {
  input = { source_id = terraform_data.source.id }
}

В первом plan source.id unknown. Consumer уже имеет известный адрес и object с известным полем source_id, поэтому его создание можно запланировать. После применения source provider возвращает ID, Core уточняет значение и передаёт потребителю. Unknown не случайный null и не строка «known after apply»: последняя — человекочитаемое представление состояния знания.

Когда unknown мешает построить граф

resource "terraform_data" "bad" {
  for_each = toset([terraform_data.source.id])
  input    = each.key
}
# Пригодная форма: ключ из конфигурации, поздний ID в значении.

  input    = each.value
}

В bad будущий ID определяет адрес, поэтому неизвестен сам набор экземпляров. В good адрес заканчивается на ["primary"] и уже определён. Регулярное лечение через отдельный target-apply скрывает неудачный интерфейс: при следующем создании проблема возвращается. Измените форму данных так, чтобы адреса определялись намерением пользователя. Если флаг создания зависит от удалённого факта, выберите отдельную управленческую границу с явным входом, а не обещайте вычисление, которого первый plan не имеет.

Depends_on не передаёт байты

depends_on задаёт дополнительное отношение порядка для скрытой семантической связи. Например потребитель не использует атрибут политики доступа напрямую, но операция внешней системы требует окончания настройки политики. Если есть естественная ссылка на нужный ID, предпочтите её. Зависимость от целого module block заставляет учитывать более широкую область и может откладывать data source Read до apply, расширяя unknown и diff.

Завершение предшествующей операции по provider contract не равно готовности приложения принять пользовательский запрос. Зависимость не проверяет TCP, SSH или содержимое миграции. Более того, два независимых ресурса, пишущих одно внешнее поле через разные APIs, не станут безопасными только от -parallelism=1: порядок готовых вершин не обещает нужную предметную последовательность, а владелец поля всё ещё раздвоен. Устраните конфликт владения, затем добавляйте обоснованные связи.

Цикл надо разорвать по смыслу

resource "terraform_data" "a" { input = terraform_data.b.output }
resource "terraform_data" "b" { input = terraform_data.a.output }

Нет первого законченного значения: каждый объект требует другой до своего действия. Перестановка блоков и увеличение parallelism не помогают. Частая реальная версия — «сетевое правило требует адрес сервиса, а сервис целиком depends_on это правило». Разделите создание identity/пустого контейнера и последующую настройку связи, если API допускает такое разделение. Либо передайте один параметр снаружи. Решение зависит от границы объектов, не от синтаксиса скобок.

Граф как диагностический инструмент

terraform graph -type=plan > plan.dot
terraform plan -parallelism=1
terraform plan -parallelism=10

Graph выдаёт DOT, текстовое описание графа; просмотр через Graphviz — отдельный необязательный инструмент. DOT не является измеренной трассой и не показывает реальную задержку API. Два plan сравнивают при одном state/config и одинаковой внешней нагрузке. Ограничение parallelism сужает число одновременно обрабатываемых операций графа, но не гарантирует один HTTP-запрос: внутри provider могут быть retry, страницы списка и свои workers. Цена лишней связи — увеличение критического пути; цена отсутствующей связи — потенциальная гонка и неверный объект.

Критерии review

Три представления объекта

Configuration описывает желаемое. Prior state хранит предыдущее известное соответствие адреса и объекта. Refresh, обновление наблюдения, просит provider прочитать фактический объект и уточняет известные атрибуты. Plan использует эти данные и правила provider, чтобы предложить create/update/delete/replacement/no-op. Если объекта нет, Read может сообщить исчезновение, и plan предложит создать его заново. Если API недоступно, ошибка чтения не означает, что объект удалён.

Обычный plan по умолчанию читает управляемые объекты перед сравнением. Сокращение refresh меняет качество наблюдения; это отдельный компромисс, а не бесплатное ускорение. -refresh=false использует прежнее знание и способен пропустить внешний drift. Новая в 1.17 возможность -minimal-refresh имеет собственную область и не используется как основание проверки отсутствия drift в этом томе. Две команды с разными режимами наблюдения сравнивают как разные эксперименты.

Сохранённое решение

terraform plan -out=review.tfplan
terraform show review.tfplan
terraform show -json review.tfplan > review.json
terraform apply review.tfplan

-out пишет непрозрачный файл, не просто красивый текст. Он содержит конфигурацию, значения и данные, нужные для выполнения, включая sensitive. Человекочитаемый вывод может скрывать секрет; JSON и бинарный файл требуют защищённого хранения. Plan file не универсальный переносимый формат между версиями CLI. Проверьте точную версию, lock file, backend, рабочее окружение и происхождение файла. Не исполняйте plan, присланный недоверенной стороной: сохранённый план может включать вредный provider/provisioner вход.

Apply без имени файла сначала строит новый план и обычно запрашивает подтверждение. Apply с именем выполняет сохранённое решение; дополнительное -auto-approve для него не является новым review. Если state изменился после создания плана, CLI отказывает как stale. В лаборатории один apply меняет gate_revision, после чего прежний saved plan действительно отклоняется. Повторите plan и review, не обходите проверку serial.

Прочитать одно действие в JSON-плане

В сохранённом плане ищите элемент resource_changes по точному address. Для изменения input.port 8080→8180 при прежнем build у нашего terraform_data ожидается change.actions = ["update"]; при изменении triggers_replace b1→b2 — ["delete","create"] без create_before_destroy. В before находятся прежние значения, в after — известная часть предполагаемого результата. Объект after_unknown отмечает неизвестные поля: null в after без проверки этого объекта нельзя автоматически читать как намеренное удаление значения.

Отрицательный случай: plan успешно записан, затем другой apply изменил state. Совпадение имени файла review.tfplan с согласованным именем не делает план актуальным. Нужен отказ stale и новое решение. А неизменность state не является вечной блокировкой внешнего API между plan и apply; сторонний оператор всё ещё может изменить объект. Поля представления плана.

Не транзакция всех ресурсов

Apply проходит готовые операции графа. Provider получает согласованное прежнее известное состояние, planned values и config; после фактических действий возвращает новое состояние или диагностику. Успех api и ошибка worker возможны в одном запуске. Core сохраняет известные выполненные изменения, а завершение с кодом 1 не превращает их в несуществующие. Нет общего rollback, который гарантированно удалит все новые ресурсы и восстановит прежние данные внешних систем. Даже удаление созданной VM не отменяет внешнюю отправку сообщения или миграцию БД.

В нашем опыте gate зависит от сервисов, поэтому намеренная ошибка gate наступает после изменения service. Затем state содержит build b2, а gate после неуспешного provisioner создания помечен tainted, «требует замены». Исправление причины и новый apply используют тот же state. Tainted — не признак, что вся конфигурация потеряна. Сначала читайте фактический план следующего запуска, особенно proposed replacement.

  triggers_replace = var.build
}

Эксперимент: сначала измените только port, затем build. В первом случае ID остаётся, во втором меняется. В лаборатории provisioner создания не перезапускается при обычном input update: rendered-файл остаётся с прежним port. Это реальная демонстрация, почему произвольный shell не превращается в полноценный declarative provider. Для управляемого файла нужен тип, чей Read умеет наблюдать содержимое, либо другой ответственный механизм.

Порядок замены

lifecycle {
  create_before_destroy = true
}

По умолчанию замена часто удаляет прежний объект до создания нового. Create_before_destroy просит сначала создать замену, затем удалить старое. Реальный API должен разрешать их сосуществование: уникальное имя, квота, адрес и привязки могут помешать. Две одновременно существующие VM ещё не означают корректное переключение трафика и миграцию данных. Нужны отдельные readiness/rollout границы.

Правило распространяется на необходимые ресурсы, от которых зависит замена и может сохраняться в state; простое снятие строки не гарантирует, что все связанные объекты вернутся к прежнему порядку. При пересоздании с таким lifecycle destroy-time provisioner имеет дополнительные ограничения. Не используйте его как единственный механизм обязательного снятия внешней регистрации. Наш тест сравнивает action order двух настоящих планов и проверяет изменение delete/create → create/delete, но не изображает отказоустойчивый cloud rollout.

Config: b2 + create_before_destroy; Старый объект: A ещё есть; Новый объект: B создан; Provider/API: create → delete; State: B новый, A до удаления; Потребитель: маршрут ещё проверить

Новый случай: исходный A; B нет → A и B сосуществуют. Нужны свободные квоты, уникальные имена и отдельный договор данных.

5. Новая identity входит в state

Prevent_destroy ограничен существующей декларацией

lifecycle {
  prevent_destroy = true
}

Пока эта resource-конфигурация присутствует, Terraform отвергает план её destroy/replacement. В тесте -replace даёт настоящий отказ. Но удаление всего resource block удаляет и правило: оставшийся объект в state может быть запланирован к уничтожению. Prevent_destroy не внешняя ACL, не backup и не запрет администратору нажать Delete в cloud console. Для критичных данных нужны защита внешней системы, права и проверенное восстановление.

Ignore_changes делит владение

lifecycle {
  ignore_changes = [input.port]
}

Фрагмент показывает форму обращения к атрибуту; его применимость определяется точной схемой ресурса. При создании аргумент учитывается, при последующих сравнениях выбранные изменения игнорируются. Это допустимо, если поле сознательно управляется другой системой, например autoscaler задаёт размер. Цена — Terraform перестаёт возвращать его к своему исходному значению; опечатка в желаемом значении тоже может не привести к ожидаемому update. all скрывает особенно широкий класс изменений. Сначала запишите, кто единственный владелец каждого поля.

Условия и связанные замены

replace_triggered_by привязывает замену к изменению другого управляемого ресурса/атрибута. Для простого значения удобно промежуточное terraform_data, но каждая добавленная вершина — новая часть графа и state. Значения lifecycle обрабатываются рано и имеют ограничения по произвольным expressions: это не место для сложного вычисления «сейчас случайно защитить базу».

Data source читает внешний объект и не имеет полного create/update/destroy lifecycle управляемого ресурса. Его чтение может быть отложено до apply, если аргументы unknown или зависимости меняются. Не путайте «объект найден» с «Terraform теперь владеет его удалением». Import переносит в управление при явном соответствии; data source остаётся наблюдением.

Возврат после ошибочного lifecycle

Если replacement ещё не применён, исправьте конфигурацию и создайте новый plan. Если новый объект создан, а старый destroy не закончен, сохраните state и исследуйте текущие/deposed объекты и внешние identities. Не удаляйте запись state ради чистого вывода: потеря связи не удаляет фактический объект и усложняет повтор. Git checkout возвращает текст, но не откатывает применённый lifecycle, UUID, данные или serial. Возврат — новый проверенный план либо отдельное восстановление данных.

Root и child читают разные области имён

Root module — каталог, в котором начинается команда. Child module подключается через module block. Каждый имеет собственные variable, local, resource и output имена. В дочернем модуле var.values не является автоматически вход корневого модуля того же имени. Вызов обязан передать значение. Снаружи доступны объявленные outputs, а не произвольные внутренние resource addresses как API выражений.

module "receipt" {
  source = "./modules/receipt"
  values = {
    for name, s in terraform_data.service : name => {
      id = s.id, port = s.output.port, build = s.output.build
    }
  }
}
output "contract" { value = module.receipt.values }

Внутри receipt находится resource "terraform_data" "record" { for_each = var.values ... }. Адрес api-записи — module.receipt.terraform_data.record["api"]. Source задаёт, где взять код; имя receipt в module block участвует в адресе. Перемещение каталога source без смены внутренней структуры и instance path — иное действие, чем переименование вызова receipt → registry. Второе меняет адреса и требует миграции.

Один большой map или много module instances

Если for_each стоит на resource внутри одного module, outputs обычно агрегируют map. Если for_each стоит на module, получится module.receipt["api"].terraform_data.record. Выбор определяется независимостью ответственности и удобством интерфейса, не длиной записи. Отдельный module instance не получает автоматически отдельный backend, lock или процесс. Все дочерние модули обычной root-конфигурации сохраняются в том же state и участвуют в одном plan.

Входной object должен описывать потребность модуля: например subnet_id, image_id, size, labels. Передача целого объекта другого provider связывает два интерфейса и его computed/sensitive поля. Модуль «Go-сервис» может принимать утверждённый образ и договор сети, не создавая внутри всё облако от организации до DNS. Чем больше несвязанных полномочий он объединяет, тем сложнее review, повторный запуск и разделение ответственности.

Функциональная зависимость предпочтительнее общего барьера

Когда output модуля выводится непосредственно из нужного resource attribute, зависимость естественно проходит через это выражение. Если output просто возвращает вход, зависимый может не ждать необходимого внутреннего действия. При скрытой связи добавляют осмысленный depends_on на output/вызов с пониманием его ширины. Не объявляйте весь network module зависимостью каждого service по привычке: это расширит unknown, отложенное чтение и критический путь.

Проектирование изменяемого интерфейса

Для каждого input опишите тип, единицы, default, nullable, допустимые комбинации и владение. Для output — назначение, sensitivity, стабильность структуры и совместимость. Два boolean, которые запрещены одновременно, лучше заменить одним enum-подобным string с validation. Набор arbitrary extra_config часто превращается в скрытый API provider без внятной поддержки. Публичный input обязателен только если у пользователя действительно есть инженерный выбор; иначе внутренний local делает модуль проще.

Тестируют не число строк, а договор: пустой и непустой набор, неизвестные ID в значениях, устойчивые ключи, некорректные порты, несколько module instances, изменение default и outputs. Терраформ-тест с mock provider не проверит доступность выбранного image_id в регионе, а настоящий apply может создать платные объекты. Наш receipt тестируется реальным built-in provider и не заявляет совместимость с облачным API.

Размер модуля и размер state

Модуль — организационная единица, не способ убрать стоимость объектов. Обёртка над десятью тысячами ресурсов оставляет десять тысяч schema/evaluation/Read операций и большой state. Разделение на отдельные состояния root-конфигураций меняет locking, доступ и отказ, но требует контрактов и порядка выпуска. Перед разделением измерьте время загрузки, вычисление графа, Read и API, чтобы не обменять одну очередь на множество неявных зависимостей.

Договор child module

Каждый модуль объявляет собственный required_providers, включая точный source address. Совпадение короткого имени не доказывает совпадение package identity: два namespace могут иметь разные providers с похожим именем. Ограничения всех потребителей должны иметь пересечение. Root обычно выбирает политику допустимых обновлений и настройки подключения; child объявляет минимальные совместимые требования и нужные configuration aliases.

# В дочернем модуле, пример интерфейса AWS без запуска.
terraform {
  required_providers {
    aws = {
      source = "hashicorp/aws"
      configuration_aliases = [aws.replica]
    }
  }
}
# Обычные ресурсы child используют aws.
# Ресурс replica явно выбирает provider = aws.replica.

configuration_aliases сообщает, какие именованные конфигурации child ожидает от вызывающего модуля. Этот список не создаёт credentials, регион, соединение или provider instance с готовыми полномочиями. Для внешнего provider отдельный required_providers в child нужен и тогда, когда настройки передаются из root. Это часть интерфейса, не дублирование секретов.

Вызывающий root связывает имена

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}
provider "aws" { region = "eu-central-1" }
provider "aws" {
  alias  = "backup"
  region = "eu-west-1"
}
module "storage" {
  source = "./modules/storage"
  providers = {
    aws         = aws
    aws.replica = aws.backup
  }
}

Слева в map — имена, ожидаемые child; справа — root configurations. aws.replica внутри child связан с aws.backup снаружи; одинакового имени alias не требуется. Обе используют установленный пакет hashicorp/aws одной выбранной версии. Provider configurations не обычные значения HCL: нельзя передать credentials объектом в var и считать его ссылкой на provider. Provider meta-argument требует предусмотренной формы ссылки.

Default configurations могут наследоваться обычным путём; alias автоматически не наследуется как нужный child alias. При явной providers map делайте все требуемые связи видимыми и проверяйте terraform providers и validate. Если в root существуют только aliased configurations, Terraform может иметь подразумеваемую пустую конфигурацию по умолчанию; ресурс без provider reference способен получить недостающие настройки. Поэтому отсутствие явной связи проверяют до apply, не по неожиданному региону объекта после него.

Почему credentials живут снаружи

Reusable child не должен обычно содержать собственные provider blocks. Такой legacy-стиль усложняет удаление: state хранит сведения о конфигурации provider, нужной для работы с объектами, а удаление вызова может убрать её раньше destroy. Кроме того, модули с собственными provider configurations имеют ограничения сочетания с count/for_each/depends_on. Настраивайте подключения на границе корневого модуля и передавайте aliases, оставляя настройки существовать до завершения операций над объектами.

Provider credentials берутся по официальной цепочке конкретного provider: окружение, workload identity, файлы профилей и прочие поддерживаемые источники. У каждого свои приоритеты и срок действия; не выдумывайте универсальный token argument. Намерение «вторая учётная запись» должно быть подтверждено чтением фактической identity до создания ресурса, например provider-specific data source или безопасной read-only командой API. Alias backup сам не доказывает, кому принадлежат полномочия.

Миграция alias и package

Переименование configuration alias, смена provider source и перенос ресурса в другой аккаунт — разные операции. state replace-provider меняет association с source address provider и не означает физическую миграцию VM в другое облако. Прежде чем удалять старую configuration, изучите state references и полный plan. Для cross-account объекта часто нужен новый объект/перенос данных и явная смена управления; присвоение нового региона не перемещает диски без стоимости.

Примеры AWS на этой странице — статический разбор интерфейса. Лаборатория 1.17.1 не скачивает aws, не выполняет его schema и не создаёт облачные ресурсы. Проверку адаптера проводите отдельно по главе о VM-контракте.

Откуда пришёл код

source = "./modules/receipt" использует каталог рядом с вызывающим модулем и версионируется вместе с ним. Registry module source имеет форму namespace/name/provider и может иметь version constraint. Git source с ref фиксирует revision; branch и tag могут двигаться по политике сервера, полный commit даёт более точный идентификатор кода. Путь subdirectory и query ref имеют свой синтаксис, который проверяют по официальным module sources, а не копируют из произвольного URL.

module "network" {
  source  = "example/network/platform"
  version = "~> 2.4.0"
}
# Пример формы Git source; адрес .invalid намеренно не выполняется.
module "service" {
  source = "git::https://git.example.invalid/team/infra.git//modules/service?ref=FULL_COMMIT"
}

version предназначен для registry modules, не заменяет Git ref. .terraform.lock.hcl фиксирует providers, а не окончательный content hash всех удалённых modules. Поэтому проверка повторяемости включает точную версию/commit модуля и происхождение исходников отдельно. Init -upgrade может выбрать новый подходящий module release и provider selection по constraints. Сравнивайте изменения кода, plan и state schema; не называйте это «только обновить кэш».

Переименование блока без разрушения объекта

# После переименования resource service в node:
moved {
  from = terraform_data.service
  to   = terraform_data.node
}

Блок сообщает соответствие старых и новых адресов. В нашем реальном тесте оба for_each экземпляра сохранили ID, план показал перенос, apply записал новые addresses. Если просто переименовать resource в HCL, Terraform обычно увидит отсутствие старой декларации и новую декларацию — destroy/create. Moved нужен, когда это тот же объект по новой структуре, а не когда вы хотите новый экземпляр с иным lifecycle.

Для count → for_each сопоставляют каждый instance: from = terraform_data.slot[0], to = terraform_data.node["api"]. Для переноса внутрь child from root address указывает to = module.service.terraform_data.node["api"]. Адреса зависят от фактического исходного состояния; выдуманное соответствие может присвоить одному логическому имени чужой объект. Сначала state list/show и карта ID, затем migration. Кавычки shell вокруг CLI-адреса сохраняют квадратные скобки и кавычки ключа.

Проверяем карту адресов, а не похожий текст

Пусть state до переноса знает terraform_data.slot[0] → ID-A и terraform_data.slot[1] → ID-W; ID-A и ID-W здесь условные подписи прежних идентичностей. После двух moved ожидаем terraform_data.node["api"] → ID-A и terraform_data.node["worker"] → ID-W, без create/delete. Если перепутать назначения, план может сохранить оба ID, но присвоить api бывший worker. Поэтому проверки «число объектов равно двум» и «оба ID сохранились» недостаточно: сравнивают пары имя→ID до и после. Если целевой адрес уже занят другой identity, перенос не следует считать слиянием объектов; сначала исследуют конфликт и строят однозначную карту.

История переходов нужна пропускающим версии

Если v1 имел a, v2 — b, v3 — c, цепочка moved a→b и b→c позволяет обновиться с более старой версии при поддерживаемом сценарии. Удаление старой migration — потенциально несовместимое изменение, даже если все разработчики уже видят только c в своих локальных тестах. Храните пояснение, зачем перенос сделан, и проверяйте upgrade по старому state fixture без внешних объектов. Не публикуйте реальные state с секретами ради тестов.

Removed и отказ от управления

removed {
  from = terraform_data.retired
  lifecycle { destroy = false }
}

Removed block делает намерение удаления из управления reviewable в plan. destroy = false оставляет внешний объект, забывая его association; без корректной политики destroy поведение будет иным. Не путайте это с удалением ресурса в API. После применения Git checkout старого HCL не восстанавливает утраченную association: старый адрес отсутствует в state, и следующий plan может предложить создать новый объект. Для возврата нужен import/move/восстановление по известной identity и проверенному плану.

State mv как аварийный инструмент

terraform state mv сразу меняет память, а не публикует совместимую migration в коде. Он полезен для согласованной разовой операции с lock и backup, когда командный процесс это разрешает. Но другие участники должны получить соответствующий HCL одновременно. Иначе новый plan на старом commit может вернуть противоположное намерение. Конфигурационный moved предпочтителен для распространяемого обновления модуля, потому что сохраняет переход в review и повторном запуске.

Для terraform_data ID — сгенерированное значение встроенного ресурса. Для других providers historical id может быть строкой, составным кодом или дополнительным атрибутом. Зачем память, если можно спросить API

В облаке могут существовать сотни одинаково названных объектов. Из одного HCL resource ... "api" нельзя безопасно узнать, какой из них Terraform раньше создал и должен обновлять. State сохраняет association, последние известные атрибуты и метаданные, включая зависимости и связь с provider configuration, которые нужны при удалении уже отсутствующего в config объекта. Чтение API не заменяет это соответствие.

Кроме того, state помогает передавать outputs и планировать связанные действия. Но он не архив содержимого дисков, не backup базы, не история всех конфигураций и не источник доступных полномочий. Утерянный state можно иногда восстановить import по проверенной карте identities, но это отдельная операция сверки. Создать пустой state и нажать apply в существующей инфраструктуре — риск получить дубликаты и конфликт имен.

Две метки файла

Lineage — идентификатор линии истории state. Он помогает отличить независимые состояния, даже если у них одинаковые адреса. Serial — номер последовательного изменения snapshot в этой линии, а не дата, номер Git-коммита или число ресурсов. После изменения state serial обычно растёт; не используйте ожидаемую величину +1 как контракт числа всех внутренних записей. CLI и backend сверяют совместимость/актуальность в поддерживаемых операциях.

umask 077
(set -o noclobber; terraform state pull > protected-state-copy.json)

terraform state show 'terraform_data.service["api"]'

Команды рассчитаны на Bash. Сразу проверьте код завершения каждого сохранения; неуспешный вызов мог оставить новый пустой или неполный файл, который нельзя считать резервом. Для следующей копии выберите новое имя и сохраните предыдущую.

State pull возвращает сырой state для служебной работы, а show -json даёт документированный JSON view с format_version. Внутренняя структура raw state не является стабильным API для собственного редактора. Не меняйте serial вручную ради обхода stale plan или push refusal. Файлы из примера чувствительны; redirects создают их с правами, зависящими от umask, поэтому заранее задайте закрытый каталог и umask 077.

Read не обязательно пишет state

Обычный plan обновляет наблюдение для расчёта, но его просмотр не следует считать подтверждённым commit всех новых данных в backend. Refresh-only apply явно принимает наблюдение. Управляющие state-команды и apply имеют свои записи; это важно при сравнении serial. Saved plan привязан к исходному state и при intervening change может быть отвергнут. В тесте stale-план создаётся до другого apply, а затем действительно не исполняется.

Частичное знание после отказа

После частичного apply state содержит подтверждённые результаты отдельных операций. Неизвестно, успел ли API завершить запрос перед сетевым обрывом; provider должен определить ситуацию при следующем Read/retry в своей поддерживаемой модели. Если CLI не смог сохранить state после внешних изменений, его аварийное сообщение и локальный recovery file становятся важными свидетельствами. Их защищают и сохраняют, а не заменяют пустым файлом. Повторять создание вслепую нельзя: объект может уже существовать.

Один объект — один владелец

Два разных state, управляющих одной VM или одним внешним полем, создают конфликт даже при правильных отдельных locks. У каждого backend свой serial/lineage, и оба процесса могут считать свой plan законным. Нужна единая карта владения. При переносе между states блокируют оба процесса, сохраняют копии, планируют association и проверяют отсутствие одновременного управления. Git-ветка не выделяет новый безопасный экземпляр инфраструктуры: при одинаковом backend она читает те же объекты.

Import связывает существующий внешний объект с управляемым адресом. Он не переносит все зависимости, не доказывает пригодность конфигурации и не восстанавливает содержимое дисков. Поддержка import и формат идентификатора определяются resource/provider. После import план может предложить update или replacement, если HCL не описывает фактическую конфигурацию.   to = example_instance.api
  id = "provider-specific-object-id"
}
resource "example_instance" "api" {

Это статическая схема интерфейса, тип example_instance не существует в лаборатории. Import, moved и removed отвечают разным вопросам

 | Действие | До | После

 | import | Объект существует, association здесь отсутствует | Известная identity присоединена к адресу

 | moved | Association есть по старому адресу | Тот же управляемый объект по новому адресу

 | removed destroy=false | Association есть и объект управляется | Объект оставлен, association забыта

 | destroy | Association и управляемый объект существуют | Provider выполняет удаление; при успехе association убирается

Смена Git-ветки после applied moved не записывает обратный moved. Возврат требует явного соответствия текущего и желаемого адреса. После removed возврат чаще требует import по фактической identity, а не простой отмены строки. Если поле ресурса по внешнему API immutable, новый конфиг может запланировать replacement даже после правильного import; связь с правильным объектом ещё не делает желаемое изменение безвредным.

Data source и пределы наблюдения

Data source, источник данных, читает сведения без управления его созданием и удалением. Если его аргументы неизвестны или связано изменяемое условие, чтение откладывается до apply и потребитель получает unknown в плане. Внешний API может возвращать неполную/с отложенной согласованностью картину; фильтр по неуникальному имени может выбрать не тот объект или дать отказ. Для критичного договора предпочитайте стабильный идентификатор и проверяйте account/region, а не совпадение display name.

Local backend не означает отсутствие lock

По умолчанию state local backend находится в terraform.tfstate рабочего каталога. Local backend использует системные API для locking; дополнительный файл информации о блокировке помогает диагностике, но он не весь механизм. terraform plan -lock-timeout=10s

B: готов к start → не допущен. lock=false может создать потерю обновления, а не ускорить согласование.

4. A записал результаты

Подтверждённые изменения должны попасть в память.

Действует: Run A/Core.

Run A: сохраняет; Run B: не записывает; Backend lock: owner A; State: S43; Внешние объекты: новые объекты/атрибуты; Git revision: config revision сохранён

Snapshot: S42 → S43. При ошибке записи сохраняют recovery evidence.

5. A освободил lock

Только после завершения соответствующей операции B может продолжить.

Действует: Run A/backend.

Run A: завершён; Run B: может повторить; Backend lock: свободен; State: S43; Внешние объекты: результаты A; Git revision: без блокировки

Владелец: A → нет владельца. Force-unlock живого A нарушил бы эту границу.

6. B должен пересмотреть решение

Новый plan читает текущую память; старый saved plan от 42 может быть stale.

Действует: Run B.

Run A: закончил; Run B: новый plan/review; Backend lock: по следующей операции; State: S43; Внешние объекты: Read для B; Git revision: нужный revision проверен

Актуальность: план на 42 → план на 43. Очередь не гарантирует применимости ранее согласованного плана.

Удалённое хранение и удалённое исполнение

Remote state — state в backend вне рабочего каталога. Terraform backend type remote, использующий HCP Terraform/Terraform Enterprise, — конкретная интеграция, а не имя всех сетевых хранилищ. Хранение в S3 само по себе не переносит выполнение provider на отдельный сервер: обычный CLI продолжает работать там, где запущен. У управляемых runs есть собственная модель remote execution, очереди, доступа и логов.

Backend type, параметры адреса state и workspace образуют границу выбора памяти. В случае ошибочного key или workspace можно получить пустой state и план создания существующей инфраструктуры. Поэтому в CI фиксируют не только branch, но и backend identity, workspace и фактическую учётную запись provider. Root configurations разных сред часто разумно разделять по правам и жизненному циклу, а не маскировать одним переменным именем.

Пример S3 как проверяемый рецепт

terraform {
  backend "s3" {
    bucket       = "YOUR_OWN_PREPARED_BUCKET"
    key          = "learning/service/terraform.tfstate"
    region       = "YOUR_REGION"
    use_lockfile = true
    encrypt      = true
  }
}

Рецепт не исполнялся и ничего не создаёт на хосте/в облаке. Для CLI 1.17.1 официальная документация поддерживает use_lockfile; доступ к state object и lock object настраивается отдельно. Версионирование bucket полезно для восстановления. Точный IAM, key prefixes, KMS и аудит проверяют по документации S3 backend и собственной системе. encrypt=true не выдаёт правильных прав и не защищает скачанный plaintext state на ноутбуке. Старые схемы DynamoDB locking и миграции имеют отдельные версии/ограничения; не включайте их по устаревшему блогу без сверки.

Одинаковый lock не означает одинаковый внешний объект

Условный опыт: A и B читают одну lineage L, serial 42. A получает lock, B с timeout 1 с отказывает, не выполняя свои действия. A сохраняет snapshot 43 и освобождает lock. Повтор B начинает новый план от 43; сохранённый план от 42 требует отдельной проверки актуальности. Числа условны, serial не счётчик ресурсов. Отрицательный случай — A выбрал key learning/a, B выбрал learning/b: locks теперь разные. Если оба state направлены на один API-объект X17, оба могут законно получить собственный lock и конфликтовать в API. Защищаемая сущность — один state; единственное владение X17 задают отдельно. Область блокировки.

Миграция backend — перенос ответственности

terraform init -migrate-state
terraform init -reconfigure

Первый режим предназначен для переноса существующего state в новую backend configuration и требует проверки источника/назначения. Второй отбрасывает прежнее сохранённое знание настройки backend и инициализируется по текущей конфигурации, не выполняя такую миграцию автоматически. Они не взаимозаменяемы. Перед переносом остановите конкурирующие runs, сохраните защищённую копию, проверьте lineage/serial и полный plan из нового места. Если отобразился пустой state, сначала проверьте destination, не запускайте create.

Командный процесс вокруг lock

Lock защищает один state от одновременных поддерживаемых операций, но не запрещает администратору менять API вручную и не создаёт distributed transaction между двумя states. Нужны единый владелец state, проверенный канал apply и запрет параллельных apply той же конфигурации вне процесса. Один lock может удерживаться долго из-за API; CI-очередь поверх него делает ожидание управляемым и связывает review с конкретным saved plan.

terraform force-unlock LOCK_ID используется только после подтверждения, что владелец блокировки прекратил работу и lock действительно осиротел, с учётом возможностей backend. Lock ID защищает от случайного освобождения другого lock, но не заменяет расследование. Local system lock обычно нельзя разблокировать из другого процесса этим способом. Сначала найдите действующий run/process, согласуйте остановку и проверьте state; не завершайте чужие процессы по совету из учебника.

Отказ операции и отказ записи state — разные случаи

В учебном gate-отказе provider уже вернул новые service ID, а local state сохранён: следующий plan видит эти результаты. Другой сценарий — внешний API создал X17, provider вернул его, но backend отклонил запись. Старый backend snapshot ещё не доказывает отсутствие X17. Сохраните выданный CLI recovery-файл и диагностику, остановите конкурентов, сравните фактическую identity с последним snapshot. Далее выбирают документированное восстановление записи либо import после сверки; повтор create наугад способен создать второй объект. Если соединение оборвалось до ответа API, даже итог создания пока неизвестен — нужен предусмотренный provider способ чтения.

Проверка понимания: достаточно ли вернуть вчерашний state, чтобы вернуть прежние байты диска? Нет. State возвращает соответствия и записанные атрибуты; диск возвращают из отдельной копии данных с проверкой приложения. Пример X17 условный и не был выполнен через внешний API. Восстановление state.

Нижний serial — важный отказ

umask 077
(set -o noclobber; terraform state pull > before-recovery.json)
# Только когда собственная контрольная точка уже создана, а state после неё изменён:
terraform state push "$TF_LAB_SNAPSHOT/terraform.tfstate"

TF_LAB_SNAPSHOT — путь, сохранённый при подготовке в главе 2. Копию по этому пути создаёт следующая секция или шаг 2 практикума; до её создания команду push выполнять нечем. Сначала проверьте успешное сохранение before-recovery.json; noclobber защищает прежнюю копию, но не делает неуспешный вывод пригодным резервом. Отказ старого serial можно наблюдать лишь после новых изменений state: подробная цепочка находится в шагах 2–9 практикума. В тесте push старого snapshot отвергнут из-за более низкого serial. Аналогично проверяется lineage независимого state. Отказ говорит: вы пытаетесь заменить более новую память старой или чужой. Не меняйте JSON и не добавляйте force автоматически. В реальной системе после старого snapshot могли появиться/исчезнуть объекты; возврат памяти не возвращает их физически. План восстановления включает карту внешних изменений, поддержку backend version restore и согласованную остановку конкурентов.

Явный возврат учебной области

# Выполнять при отсутствии работающих Terraform-команд.
python3 "$TF_LAB_TOOLS/lab.py" snapshot "$TF_LAB_ROOT" "$TF_LAB_SNAPSHOT"
# Позже, после осознанного выбора именно этой копии:
if python3 "$TF_LAB_TOOLS/lab.py" restore "$TF_LAB_ROOT" "$TF_LAB_SNAPSHOT"; then
  cd "$TF_LAB_ROOT" &&
  terraform init -input=false &&
  terraform plan
else
  printf '%s\n' 'Restore отказал; дальнейшие Terraform-команды не выполнены.' >&2
fi

Если этот собственный snapshot уже создан, не выполняйте сохранение повторно: проверьте его происхождение и выберите его явно. Для другой контрольной точки присвойте TF_LAB_SNAPSHOT новый постоянный путь. Скрипт предназначен только для local-only terraform_data стенда. Он проверяет marker и checksums, отказывается перезаписывать существующий snapshot и сохраняет прежний каталог как sibling *.before-restore. Возвращаются source, state и учебные файлы вместе. Это не рецепт rollback облака и не защита от живого параллельного процесса: reader обязан остановить команды; lock-info — дополнительная проверка, а не distributed freeze. Восстановление из недоверенного архива тоже опасно: источник должен быть собственным и защищённым.

Sensitive, ephemeral и write-only

sensitive=true редактирует отображение и переносит метку по выражениям; обычные сохранённые значения остаются в state/plan. terraform output -json, state pull и JSON plan могут раскрыть их. Эфемерные значения, поддерживаемые с Terraform 1.10, исключаются из обычного сохранения в state/plan в разрешённых контекстах; это свойство конкретной ephemeral variable/output/resource, а не всего графа. Write-only resource arguments доступны с 1.11 при реализации provider и не сохраняют такое argument value обычным путём. Их версии, взаимосвязанные version arguments и допустимые выражения проверяются по schema/provider docs.

Исключение argument из сохранения не запрещает provider явно сохранять производный результат в другом атрибуте. Например новый store.input у terraform_data является write-only, но значение по назначению копируется в store.output или sensitive_output и сохраняется там. Поэтому безопасность оценивают по полной схеме потока данных, а не по одному слову write-only. Foundation использует обычный input и не выдаёт его за secret store.

Эти механизмы не предотвращают утечку из shell, debug log, внешнего API или stdout provisioner. Не вводите реальные секреты в лабораторию, не печатайте весь environment. TF_LOG включают на короткий диагностический интервал с закрытым местом для вывода и последующей очисткой по политике; подробный trace может содержать чувствительные значения. Отдельная безопасная машинная identity с минимальными полномочиями лучше постоянного персонального admin token в конфигурации.

Constraints и lock file

= 1.17.1 фиксирует CLI в лаборатории. ~> 2.4.0 допускает версии начиная с 2.4.0 до 2.5.0, ~> 2.4 — до 3.0.0. Запятая объединяет условия пересечением. Если root требует < 3.0, а child >= 3.0, подходящего provider нет; init должен отказать. Ослабление ограничения без проверки совместимости не устраняет техническое противоречие.

.terraform.lock.hcl хранит выбранные версии внешних providers и допустимые hashes. Он не фиксирует CLI binary, state version, credentials и все modules. h1: и zh: — разные виды checksums в поддерживаемой модели пакетов, а не строки, которые следует дописывать вручную при mismatch. Проверка подписи provider release, источник получения hashes и первый доверенный выбор важны: слепое принятие впервые скачанного пакета не создаёт доказанного доверия.

Обычный init и сознательный upgrade

terraform init -lockfile=readonly
terraform init -upgrade
terraform providers lock -platform=linux_amd64 -platform=windows_amd64

Readonly сохраняет существующий выбор и отказывает при необходимости обновить lock. Upgrade пересматривает подходящий выбор в пределах constraints и может обновить providers/modules; diff lock и исходников читают как изменение зависимости. Providers lock получает checksums для перечисленных целевых платформ по предусмотренному источнику. Это подготовка доверенного набора, не установка binary Windows в Linux и не проверка работы provider на Windows. В лаборатории с built-in provider внешнего package lock может вообще не быть — не создавайте фиктивный hash, чтобы файл выглядел «как у взрослых».

Cache и mirror не одно

Plugin cache — оптимизация повторных установок уже выбранных пакетов. Он не утверждает происхождение и не всегда является полностью автономным источником provider discovery. Filesystem/network mirror — заранее подготовленный источник установки с определённой структурой и политикой доступа. Не размещайте cache и filesystem mirror в одном каталоге. Ограничения concurrent writers и пути cache проверяйте по CLI docs; один общий writable cache в CI может стать источником гонок.

# На доверенной подключённой машине для конкретной конфигурации:
terraform providers lock -platform=linux_amd64
terraform providers mirror -platform=linux_amd64 ./provider-mirror

После подготовки переносят mirror вместе с проверенным lock file, исходниками, точными modules и CLI. На изолированной машине отдельный TF_CLI_CONFIG_FILE выбирает installation policy. В Unix пример относительного авторского расположения заменяется абсолютным путём собственной offline-копии:

provider_installation {
  filesystem_mirror {
    path    = "/YOUR/OFFLINE/provider-mirror"
    include = ["registry.terraform.io/*/*"]
  }
}

Здесь нет direct fallback: отсутствующий пакет должен дать понятный отказ, а не незаметно потребовать сеть. Пример рассчитан на заранее выбранные registry sources; иные hostnames добавляются сознательно. Provider mirror не скачивает исходники remote modules за вас. Registry/Git modules надо получить и проверить отдельно, либо подготовить reviewable local copies с объяснением происхождения. .terraform/modules — служебный working cache, а не долговечный каталог поставки.

Проверка настоящего офлайна

В личной VM запретите выход по её собственной сетевой политике либо используйте подготовленную изолированную среду, затем создайте новый рабочий каталог, init и validate. Проверка на уже инициализированном каталоге с полным cache слабее: отсутствующая dependency может остаться незамеченной. Для этой книги реальная foundation цепочка не требует сети после получения CLI и исходников, потому что provider встроен, module local. Это не результат firewall-теста всех внешних providers.

Маршрут обновления

Сначала protected backup и release notes CLI/provider; затем новый binary в отдельном пользовательском каталоге, проверка sums/signature, validate/test на безопасной копии, plan и review. Provider может обновлять schema в state; возврат старого binary/lock не гарантирует чтение нового state. Для отката нужна проверенная совместимость или согласованное восстановление с учётом внешних изменений. Обновляйте по одной осмысленной оси: CLI отдельно от крупного module refactor легче диагностировать. Saved plans старой версии заново строят и согласуют, не переносят как универсальный артефакт через upgrade.

Из чего состоит время

Разделите первую инициализацию без подготовленного кэша, загрузку config/modules, получение provider schema, вычисление выражений/графа, Read внешнего API, построение diff, операции apply и запись state. Wall time, прошедшее календарное время команды, включает ожидание сети и lock. CPU time — время работы на CPU; низкий CPU при долгой команде часто означает ожидание, но без трассы нельзя решить, ждём ли API, диск, lock или backoff retry. RSS, resident set size, — наблюдаемая резидентная память процесса, не только Go heap. Внешний provider process потребляет память отдельно от Core.

Queue time, время в очереди CI/lock, отделяйте от фактического исполнения. Если 10-минутная задача пять минут ждала допуск, увеличение parallelism самого Terraform не сократит эти пять минут. Измеряйте с одной границей начала/конца, используйте секунды, байты, запросы/с и число объектов. Без единиц цифры «plan 500» бесполезны.

Локальная база без API

python3 "$TF_LAB_TOOLS/benchmark.py" --terraform terraform \
  --counts 10,100 --repeats 5 --report own-benchmark.json

Benchmark создаёт свою временную область с 10 и 100 terraform_data instances, делает init, один apply и пять пустых plan, затем убирает только свою область. Он не меняет продолжаемый reader state и не покупает ресурсы. Реальный запуск этой редакции: linux_amd64, CLI 1.17.1, local backend, встроенный provider, default parallelism, без внешнего API; время первой инициализации без подготовленного кэша исключено. Для 10 объектов медиана plan около 0,0228 с, диапазон 0,0217–0,0232 с, state 5460 байт. Для 100 — около 0,0525 с, диапазон 0,0515–0,0585 с, state 51541 байт. Полные наблюдения сохранены в labs/benchmark-results.json.

Это маленькая локальная серия на конкретной машине при текущей нагрузке, а не оценка производительности облака. Пять наблюдений недостаточны для устойчивого p95; мы показываем median/min/max и сами измерения. Более крупный граф увеличил стоимость, но эксперимент не отделял CPU, аллокации и диск, поэтому не доказывает единственную причину. Два размера не обосновывают универсальную линейную формулу на миллион объектов.

Найти ограничение контролируемым опытом

 | Гипотеза | Сравнение | Нужное наблюдение

 | Преобладает ожидание сети/API | Один и тот же state, normal plan; затем только диагностическое сравнение без refresh | Read durations, запросы, retry, throttling. Второй план слабее по наблюдению.

 | Преобладает CPU/вычисление | Те же объекты и схема, более простое выражение/меньше повторов | CPU time, Core RSS, одинаковый action diff.

 | Преобладает доступ к удалённому state | Измерить download/upload отдельно без изменения владения | Размер, network throughput/latency, backend timings.

 | Лишние зависимости | Удалить только обоснованно избыточный edge | Критический путь, unknown и отложенное чтение; не только число ресурсов.

 | Очередь и quota | Несколько parallelism при одинаковых inputs | Длительность, errors, p50/p95 API, частота 429, retries.

Обычный Linux /usr/bin/time -v terraform plan помогает наблюдать wall/user/system/RSS, но поведение суммирования дочерних процессов зависит от инструмента/ОС. Для provider нужны отдельные метрики процесса/API. Trace лог включайте кратковременно и защищайте; большое журналирование само меняет диск/CPU и измеряемое время. Для удалённых систем сначала используйте безопасные журналы/метрики provider API, не запускайте нагрузочный опыт в рабочей среде.

Parallelism не бесплатные запросы

terraform plan -parallelism=1
terraform plan -parallelism=10

При независимых операциях второй план может перекрыть ожидание. Но API имеет quotas, provider — pools и retries, backend — одну запись state. Если 10 workers увеличили throttling и хвост задержек, 5 могут быть быстрее и устойчивее. Число operations Core не равно числу HTTP requests: один Read может выполнять pagination или polling. Условия опыта включают accounts, регион, размеры объектов, наличие уже подготовленного кэша и внешнюю нагрузку; значения с разных конфигураций не сравнивают как изменение одной ручки.

Посчитать нижнюю границу до настройки parallelism

Условная задача без сети: независимые операции A=2 с и B=3 с, затем C=1 с после обеих. С одним рабочим местом минимальное время 2+3+1=6 с; с двумя — max(2,3)+1=4 с. Третье место не сократит цепочку B→C длиной 4 с. Это расчёт по заданным длительностям, не измерение Terraform. Он объясняет, какое перекрытие вообще возможно. Если API добавил B ещё 5 с повторного ожидания, нижняя граница стала max(2,8)+1=9 с: рост parallelism не устраняет эту причину.

Для сохранённой серии median(100)/median(10) ≈2,30 при десятикратном числе экземпляров, а размер state вырос примерно в 9,44 раза. Эти отношения можно пересчитать из JSON; они не доказывают ни линейной сложности, ни предела CPU. Для вывода о причине не хватает отдельных CPU/RSS/I/O и API-наблюдений. Готовность операций и ограничение параллельности.

Цена больших modules и разбиения

Крупный root state увеличивает graph/state/read стоимость и область единственного lock. Разделение по independent lifecycle и доступу сокращает общую блокировку, но добавляет версии контрактов и порядок зависимостей между разными root-конфигурациями. Чтение чужого remote state может требовать доступа ко всему snapshot, даже если в выражении используются outputs; для узкого договора иногда лучше отдельная публикация выбранных несекретных полей. Выбирайте границы по владельцу ресурса и границам отказа, затем проверяйте измерением.

Четыре владельца

Domain в libvirt — запись виртуальной машины с её UUID, дисками и интерфейсами. UUID отличает объект от похожего имени. Bootstrap — заранее подготовленные условия первого входа: пользователь гостя, его public key и сетевые настройки. Подлинность SSH-сервера проверяют по его host key, ключу самого сервера; знание IP её не доказывает. Association ниже означает сохранённое соответствие адреса Terraform этому объекту.

Terraform Core строит plan и управляет state. Provider libvirt переводит операции в libvirt. Libvirt/QEMU создаёт/запускает domain и работает с диском. Гостевая ОС загружается и предоставляет SSH/application endpoints. Отдельный инструмент конфигурации, например Ansible, настраивает пакеты, systemd и Go-службу поверх пригодного доступа. Существование UUID domain не доказывает загрузку ОС, успешное SSH или готовность /health.

В labs/adapters/libvirt/ находится отдельный рецепт для личной Linux VM: CLI 1.17.1, community provider dmacvicar/libvirt = 0.9.9, системное подключение qemu:///system внутри этой VM. Схема сверена с документацией tag v0.9.9. Новая 0.9 модель использует os/devices как объектные arguments; старые примеры provider нельзя механически смешивать с ней. Наличие пакета под macOS ещё не означает, что там автоматически есть пригодный local Linux hypervisor.

Что делает конкретный рецепт

provider "libvirt" { uri = "qemu:///system" }
resource "libvirt_domain" "api" {
  name        = "tf-handbook-api"
  type        = "qemu"
  running     = var.start_guest
  memory      = 1024
  memory_unit = "MiB"
  vcpu        = 1
  # Полные os/devices, путь к своему диску и частная сеть — в adapter main.tf.
}

Начальное start_guest=false задаёт создание описания без обещания boot. Для выполнения нужны уже подготовленные собственные image_path и network_name. Образ — расходуемая личная копия, которой не пользуется другая VM. QEMU будет менять диск при запуске; путь в аргументе не делает исходный файл автоматически Terraform-managed volume. Рецепт не создаёт и не перенастраивает сеть, storage pool или host service. Type qemu не обещает аппаратное ускорение KVM; при nested virtualization пригодность определяется host/guest возможностями отдельно.

Версия 0.9.9 в собственных docs помечает remote qemu+ssh URI как ещё не реализованный путь. Поэтому рецепт запускается внутри личной VM, а не обещает управление любым удалённым libvirt по SSH. Приёмка совместимости: точный пакет provider/checksums; terraform init -backend=false, schema -json, validate; далее read-only проверка URI и libvirt/QEMU versions на собственной VM. Создание domain, запуск гостя и SSH в этой редакции не выполнялись. Реально выполнены init без backend, validate и providers schema -json, в том числе повтор с локальным mirror: все завершились кодом 0. Validate обнаружил неточность upstream-примера boot_devices: требуется список объектов с dev, а не список строк. Адаптер исправлен по реальной схеме; соединение с libvirt не выполнялось. Результаты находятся в ПРОВЕРКИ.txt.

Согласовать libvirt, сеть и формат диска

У libvirt пользовательская session и system — разные области управления. Обычная сеть default, созданная системным libvirt, не становится доступной через qemu:///session. Наш профиль использует system внутри личной Linux VM; это отдельная подготовленная учебная ОС, которой разрешено управлять собственным гипервизором. При необходимости в ней получают пакеты libvirt/QEMU из доверенного репозитория Ubuntu, настраивают разрешённый доступ пользователя и создают собственную именованную сеть. Подготовка сети — осознанное административное действие этой VM; adapter её не создаёт. Последовательность и проверки указаны в README адаптера.

До plan во всех virsh-командах указывают тот же URI qemu:///system. Проверяют текущую identity, версии, capabilities, список сетей и net-info своей сети. Отсутствующая или неактивная сеть — незавершённая подготовка, а не повод заменить URI на session. Образ предварительно исследуют через qemu-img info: расширение .qcow2 не доказывает формат. В devices.disks явно задан driver name=qemu/type=qcow2; это инструкция гипервизору о формате байтов, а не изменение имени файла. Пользователь процесса QEMU должен иметь доступ к расходуемой копии и её каталогам по политике ОС.

Контракт адресов и доступа

Потребителю настройки передают schema_version, стабильное логическое имя api/worker, provider идентификатор/UUID для сопоставления, проверенный address/port, ssh_user, способ получения host key и ссылку на защищённый credential mechanism. Не передают private SSH key в публичный root output. Адрес получают из предусмотренного источника DHCP/guest agent/сети и сверяют с UUID/MAC; нельзя выводить IP как строку из name VM. DNS-запись тоже должна иметь понятного владельца и время обновления.

{
  "schema_version": 1,
  "hosts": {
    "api": {
      "resource_identity": "provider-specific-identity",
      "address": "192.0.2.10",
      "ssh_port": 22,
      "ssh_user": "prepared-in-image",
      "host_key_source": "verified-private-bootstrap"
    }
  }
}

Это схема договора с документационным IP, не реальный доступ и не сгенерированный inventory. Образ должен заранее иметь согласованный bootstrap: пользователь, public key, host-key procedure и сетевые предпосылки. Terraform-output с правильным типом ещё не подтверждает достижимость из controller. Сначала проверяют маршрут/TCP, затем host identity/SSH, затем ОС и службу. Ошибку Permission denied не лечат бесконечным replacement VM без проверки пользователя/ключа.

Переход к сохраняемому стенду Ansible

В томе Ansible адреса попадают в частный inventory/hosts.yml, а counter_a/counter_b остаются именами двух узлов. Учебные api/worker в foundation — ключи локального контракта; запись "port": 8080 в JSON не означает, что такой процесс или VM уже существуют. Поставляемый libvirt adapter описывает только один domain api и выводит UUID/name. Он не создаёт пару узлов Ansible, не получает автоматически адрес и не генерирует inventory.

Когда собственная VM действительно загружена, сверьте её UUID/диск/адрес с журналом инфраструктуры и проверьте SSH от той учётной записи controller, которой будет запускаться Ansible. Только затем заполните ansible_host, ansible_user, при необходимости ansible_port и фактический ansible_python_interpreter. SSH host key проверяется отдельно; он не выводится из IP. Начните с ansible-inventory --graph, обычного SSH и read-only id по рецепту Ansible. Для полного двухмашинного выпуска нужны две отдельно подготовленные цели с разными дисками и личностями.

В паспорте связи храните Terraform root/backend и адрес ресурса, UUID/диск VM, inventory-имя, release/SHA и путь прикладных данных. State запоминает объект инфраструктуры; /var/lib/counter/count.txt содержит данные приложения на гостевом диске. Возврат старого state не возвращает прежние байты гостя. Snapshot VM и прикладной резерв принимаются по своим критериям; следующие упражнения сохраняют уже выбранные каталоги и диски.

Связать логическое имя с наблюдённым адресом

Для одного созданного собственного domain запишите выбранное inventory-имя и UUID из Terraform output. Через тот же qemu:///system получите virsh domuuid ИМЯ_DOMAIN, затем virsh domiflist UUID, указывая --connect qemu:///system перед подкомандой. Сравните UUID и MAC интерфейса. В выбранной managed-сети чтение virsh net-dhcp-leases ИМЯ_СЕТИ MAC с тем же --connect позволяет связать DHCP-адрес именно с этим MAC, если сеть действительно выдала lease. Отсутствие lease не разрешает угадывать адрес: проверьте загрузку и настройку гостя по его консоли или предусмотренному guest-agent пути.

Только наблюдённый адрес попадает в ansible_host выбранного имени; для второго counter_b повторяют проверку его отдельного UUID/MAC/диска. Строка 192.0.2.10 выше — пример формата, её не копируют как результат измерения. SSH host key сверяют через собственный доверенный bootstrap/консоль, затем проверяют SSH от controller. Так одна таблица имя→UUID→MAC→IP связывает два инструмента, не выдавая совпадение имени за доказательство личности. Эти проверки VM здесь остаются неисполненным рецептом; формы команд описаны в официальной справке virsh.

Кто меняет Go-службу

Terraform удобно управляет lifetime VM, сети, дисков и адресными associations. Ansible удобно управляет повторяемой настройкой ОС через выбранное соединение. Их полномочия могут пересекаться; выберите единственного владельца файла/службы/правила. Если Terraform provisioner создания пишет конфиг, а Ansible меняет тот же файл, новый Terraform apply может ничего не заметить — мы уже видели этот предел локально. Отдельное состояние инструмента не делает конфликт безопасным.

Для выпуска бинарника договор дополняют версией/хешем артефакта и ready check. Terraform VM replacement не откатывает схему БД; Ansible повторный запуск не восстанавливает потерянный volume. Возврат включает жизненный цикл инфраструктуры, настройку и данные по отдельным процедурам. Подробная модель задач и SSH относится к самостоятельному тому Ansible; здесь остаётся явная граница передачи.

TF_LAB_TOOLS="$PWD/labs"
umask 077
mkdir -p "$HOME/terraform-learning/stands" "$HOME/terraform-learning/snapshots"

TF_LAB_SNAPSHOT="$HOME/terraform-learning/snapshots/foundation-checkpoint-1"
if python3 "$TF_LAB_TOOLS/lab.py" prepare "$TF_LAB_ROOT"; then
  cd "$TF_LAB_ROOT" &&
  terraform init -input=false &&
  terraform validate &&
  terraform plan -out=first.tfplan &&
  terraform show first.tfplan &&
  terraform apply first.tfplan &&
  terraform state list &&
  terraform output -json contract &&
  terraform plan -detailed-exitcode

fi

План первой конфигурации создаёт пять terraform_data instances: два service, два record в receipt, один gate. Последующий detailed plan должен вернуть 0. Сохраните вывод IDs в защищённой заметке. Если вы получили другую конфигурацию/число адресов, найдите причину до продолжения. Здесь нет работающего Go-сервера: port является данными.

2. Явно сохранить контрольную точку

python3 "$TF_LAB_TOOLS/lab.py" snapshot "$TF_LAB_ROOT" "$TF_LAB_SNAPSHOT"

Если подходящая исходная контрольная точка уже создана в главе восстановления, проверьте её происхождение и используйте её без повторного snapshot. Существующий файл не перезаписывают; для другой точки выбирают новое имя TF_LAB_SNAPSHOT в постоянном snapshots/. Все Terraform-команды остановлены. Snapshot включает исходники, state и rendered-файлы; cache/providers и saved plans не переносятся. Существующая копия не перезаписывается. Это snapshot целого local-only упражнения, не backup облака. После этого дальше работаем в прежнем TF_LAB_ROOT.

3. Наблюдать слепую зону

python3 -c 'from pathlib import Path; Path("rendered-api.json").write_text("outside change\n")'
terraform plan -detailed-exitcode
terraform plan -replace='terraform_data.service["api"]' -out=repair.tfplan
terraform show repair.tfplan
terraform apply repair.tfplan

Ожидаем пустой первый plan несмотря на изменённые байты: файл не является управляемым объектом с собственным Read. Replacement создаёт новый ID api и запускает writer. Это намеренный дорогой способ исправления учебного эффекта. Сравните worker ID: независимый service не должен быть заменён только из-за repair api. Если effect writer падает, исправьте причину в той же области.

4. Изменить input без replacement

python3 - <<'PYDATA'
import json
from pathlib import Path
services = {"api": {"port": 8180, "build": "b1"},
            "worker": {"port": 8081, "build": "b1"}}
Path("case.auto.tfvars.json").write_text(json.dumps({"services": services}) + "\n")
PYDATA
terraform plan -out=input.tfplan
terraform apply input.tfplan
terraform output -json contract
cat rendered-api.json

ID api остаётся, output port стал 8180, а файл writer остался с предыдущим port 8080. Provisioner выполнялся при создании, обычный update его не повторяет. Сопоставьте три наблюдения: config, state output, файл. Не пытайтесь добиться их равенства удалением state.

Сравнить state и файл отдельным читателем

Утилита observe.py читает уже построенное JSON-представление state из stdin и rendered-файлы своего помеченного каталога. Она не запускает Terraform, не обращается к provider и ничего не записывает. В Bash:

set -o pipefail
terraform show -json | python3 "$TF_LAB_TOOLS/observe.py" --root "$TF_LAB_ROOT"

После стандартного шага 4 строка api должна содержать state.port=8180, receipt.port=8080 и receipt_matches=false; ID сравните со своей заметкой до update. Worker остаётся совпадающим. Это осмысленное расхождение, а не потеря состояния. При отсутствии файла receipt=null и совпадение false; ошибочный JSON файла даёт отказ чтения. После замены b2 writer снова запишет текущее значение, но после partial apply сначала смотрят фактические resource state: корневой output не обязан уже содержать все промежуточные результаты.

Для отдельной проверки вычислений без CLI и без записи запустите python3 -B "$TF_LAB_TOOLS/mechanism_model.py". Это фиксированная учебная модель с условными ID, не замена настоящим проверкам check.py и не интерпретатор HCL. Не передавайте её условные ID в import/state-команды.

5. Перенести адрес

В main.tf переименуйте resource block service в node и все ссылки terraform_data.service в terraform_data.node; затем добавьте отдельный moved, у которого from остаётся старым адресом:

moved {
  from = terraform_data.service
  to   = terraform_data.node
}

terraform plan -out=move.tfplan
terraform show move.tfplan
terraform apply move.tfplan
terraform state list
terraform output -json contract

Проверяйте сохранение обоих ID. Не создавайте два разных resource blocks со старыми и новыми именами одновременно. Moved применяется как migration, а не как «создать ещё одну копию». С этого упражнения адреса в командах замены оканчиваются на node. Возврат Git-текста без обратной migration не возвращает applied association.

6. Получить настоящий lock conflict

В первом терминале того же стенда выполните bounded hold. Он создаёт/заменяет только gate:

terraform apply -auto-approve -var=gate_revision=lock-run -var=hold_seconds=10

Во втором терминале задайте тот же TF_LAB_ROOT, перейдите в него и пока первый run работает выполните:

cd "$TF_LAB_ROOT"
terraform plan -lock-timeout=1s

Ожидается отказ из-за занятого state, не повод ставить lock=false. Дождитесь окончания первого, повторите обычный plan; переопределение через CLI gate_revision не было сохранено в tfvars, поэтому возможно предлагаемое возвращение к default g1. Либо осознанно примите его, либо запишите выбранную revision в файл. Автоматический check согласует входы перед следующим шагом.

7. Увидеть stale saved plan

terraform plan -var=gate_revision=saved-intent -out=stale.tfplan
terraform apply -auto-approve -var=gate_revision=intervening
terraform apply stale.tfplan

Последний apply должен отказать как устаревший: state между plan и apply изменён. Не обходите это force/редактированием serial. Сделайте новый plan по текущему намерению. Saved plan не разрешение игнорировать изменения команды.

8. Частичный apply и продолжение

В существующем case.auto.tfvars.json измените build обоих services на b2 и добавьте два поля верхнего уровня. JSON использует двоеточие между именем и значением; запись с HCL-знаком равенства здесь неверна. После стандартного шага 4 весь файл выглядит так (если вы сами меняли порты, сохраните свои значения):

{
  "services": {
    "api": {"port": 8180, "build": "b2"},
    "worker": {"port": 8081, "build": "b2"}
  },
  "gate_revision": "fail-run",
  "fail_gate": true
}

Не создавайте второй auto.tfvars с конфликтующими входами: исправьте прежний файл, предварительно сохранив его копию под именем, которое не оканчивается на .tfvars/.auto.tfvars.json. Затем:

terraform plan -out=partial.tfplan
terraform apply partial.tfplan
terraform state show 'terraform_data.node["api"]'
terraform state show terraform_data.gate

Это намеренный отказ gate с кодом скрипта 7 и общим кодом Terraform 1. Предшествующие services уже заменены; gate tainted. Исправьте только fail_gate на false, затем новый plan, review и apply. Следующий detailed plan должен стать пустым. Reset, новый каталог или удаление .terraform.tfstate здесь уничтожили бы предмет опыта.

9. Проверить запрещённый короткий путь и выполнить явный возврат

terraform state push "$TF_LAB_SNAPSHOT/terraform.tfstate"

После этих изменений старый serial меньше текущего, push должен отказать. Скопируйте сообщение в заметку, не добавляйте force. Для local-only учебного rollback остановите все команды и вызовите предусмотренный полный restore:

if python3 "$TF_LAB_TOOLS/lab.py" restore "$TF_LAB_ROOT" "$TF_LAB_SNAPSHOT"; then
  cd "$TF_LAB_ROOT" &&
  terraform init -input=false &&
  terraform plan -detailed-exitcode
else
  printf '%s\n' 'Restore отказал; дальнейшие Terraform-команды не выполнены.' >&2
fi

После успешного restore вернулись source/state/files точки 1, поэтому блок снова service, builds b1. Прежняя развитая область сохранена в *.before-restore. Если копия уже существует, manager откажет, чтобы вы сначала разобрались с предыдущим возвратом. Для удалённых объектов этот способ не предназначен.

10. Снять лабораторию и проверить отдельно

terraform plan -destroy -out=own-cleanup.tfplan
terraform show own-cleanup.tfplan
terraform apply own-cleanup.tfplan
terraform state list

Проверьте marker, каталог и адреса до cleanup. Terraform_data не владеет rendered-файлами через Read/Delete, поэтому файлы могут остаться. Их хранение/удаление — явное решение владельца учебной области после исследования. Для повторения авторских тестов из каталога тома запустите python3 labs/check.py --terraform terraform: тест сам создаёт отдельную область, проходит цепочку и убирает её, не продолжая и не уничтожая вашу.

Матрица отказов

 | Наблюдение | Граница | Следующий безопасный шаг

 | Invalid for_each argument | Неизвестные ключи графа | Сделать ключи частью config, оставить ID в values.

 | Checksum mismatch | Установка зависимости | Проверить package source/hash, не удалять lock вслепую.

 | Error acquiring state lock | Конкурирующая операция | Найти владельца и дождаться/согласовать; не обходить lock.

 | Saved plan is stale | Состояние изменилось | Новый plan и review.

 | Plan пуст, файл неправильный | Файл вне provider Read | Исправить ответственность за управление, а не доверять зелёному status.

 | Apply failed, IDs поменялись | Частичное выполнение | Сохранить state, исследовать фактические результаты, продолжить.

Язык и интерфейсы

Для типов/преобразований нужны types и constraints; для knowledge propagation — references. Для адресов и масштаба — for_each, count, dynamic. Каждая глава языка связывает это с собственным конфигом и возможным отказом.

Исполнение и память

Граф, Plugin Protocol и JSON view ограничивают точность модели: нарисованные сообщения — логические переходы, не дамп network packets. Для exact RPC fields смотрите versioned definitions. Встроенный terraform_data не подтверждает запуск внешнего plugin process.

State-линия опирается на purpose, locking, push checks, local backend и S3 backend. Import/removed/lifecycle уточняются по import, removed, lifecycle. Secrets-линия сверяется с sensitive, ephemeral и write-only.

Зависимости и VM-адаптер

Lock file, installation methods/cache, mirror описывают поставку пакетов. VM-рецепт привязан к dmacvicar/libvirt 0.9.9 и его domain schema. Это первичный проект community provider, не встроенная универсальная VM-функция Terraform.

Том XVIII · Справочник

Словарь · TerraformПонятия и их связь с наблюдаемыми механизмами · 1577 слов

Словарь в боковой панели также ищет определения во всех остальных томах.

Terraform CLI

Конечный процесс командной строки, который читает конфигурацию, вычисляет граф, вызывает providers и работает с выбранным backend. Не является гипервизором.

HCL

HashiCorp Configuration Language — язык структуры блоков, аргументов и выражений. Terraform задаёт смысл своих блоков и привлекает схемы providers.

Provider

Провайдер — адаптер с типами/схемами объектов и операциями чтения/изменения определённой внешней системы. Встроенный terraform provider не создаёт универсальные VM.

Provider source address

Идентичность пакета вида hostname/namespace/type; короткое локальное имя внутри модуля не заменяет полный источник.

Provider configuration

Набор настроек подключения установленного provider, например регион и поддерживаемый способ получения полномочий. Не тождественен версии пакета.

Alias

Дополнительное имя provider configuration. Позволяет передать разные наборы настроек при том же выбранном provider binary.

configuration_aliases

Объявление в required_providers child-модуля, какие именованные конфигурации provider он ожидает. Само не создаёт настройки или credentials.

Plugin

Отдельное исполняемое расширение внешнего provider. Обычно запускается CLI дочерним процессом; встроенный terraform_data этого процесса не требует.

RPC

Remote procedure call — вызов операции через границу компонентов. Terraform Plugin Protocol определяет вызовы Core/provider; это другой интерфейс, чем API облака.

Protocol Buffers

Язык описания схем сообщений и соответствующая инфраструктура сериализации. В Terraform protocol определения описывают поля RPC, но не заменяют объяснение последовательности операций.

gRPC

Технология RPC, используемая современным Terraform Plugin Protocol вместе с определениями Protocol Buffers. Схема в книге показывает логические вызовы, не байтовый дамп.

Schema

Схема — описание типов, аргументов, вложенности и required/optional/computed свойств объекта. Ограничивает допустимую конфигурацию provider.

Resource

Управляемый ресурс — объявление объекта, чей жизненный цикл Terraform ведёт через provider. Один блок с count/for_each может дать несколько экземпляров.

Resource instance

Отдельный экземпляр ресурса с определённым module path и индексом/ключом. Именно его адрес сопоставляется с объектом в state.

Resource address

Адрес Terraform, например module.app.terraform_data.node["api"]. Организует конфигурационную идентичность, не является IP и не равен автоматически provider ID.

Resource identity

Представление фактической идентичности объекта по схеме provider. Может быть структурированным; поддержка и связь с историческим id зависят от provider/version.

Data source

Источник данных, который читает сведения об объекте без полного ownership его создания/удаления. Чтение может быть отложено до apply.

Module

Каталог согласованных деклараций с входными variables и опубликованными outputs. Обычный child расширяет граф/state root, не получает отдельный backend автоматически.

Root module

Каталог, откуда начинается операция CLI; задаёт backend и получает корневые входы из поддерживаемых источников.

Child module

Подключённый module block каталог со своей областью имён и requirement providers. Получает входы через аргументы вызова.

Module instance

Конкретный вызов модуля; при for_each/count адрес включает ключ или индекс. Переименование вызова меняет путь внутренних resource addresses.

Variable

Объявленный вход модуля с type constraint, default, validation и другими условиями. Child не наследует root tfvars автоматически.

Local

Именованное выражение local.name. Не изменяемая переменная и не средство задать порядок исполнения.

Output

Опубликованное значение модуля. Root output хранится в state и читается CLI; child output доступен caller через module.name.output.

Type constraint

Ограничение допустимого типа входа; Terraform может преобразовать значение к совместимому типу. any просит подобрать конкретный тип, а не отменяет типизацию.

List

Упорядоченная последовательность элементов одного согласованного типа. Индекс может стать частью identity при count.

Set

Неупорядоченное множество уникальных элементов. Преобразование списка удаляет повторы и не сохраняет договор порядка.

Map

Отображение строковых ключей в значения одного согласованного типа; устойчивые ключи удобны для for_each.

Object

Значение с именованными полями и их отдельными типами. Преобразование к более узкому object может отбросить дополнительные атрибуты.

Tuple

Последовательность с типом каждой позиции. Литерал списка сначала может иметь tuple-форму до согласования с требуемым list.

Null

Отсутствие конкретного значения. Отличается от нуля, пустой строки и пустой коллекции; пропуск аргумента определяется также схемой.

Unknown

Корректное, ещё неизвестное значение с известными свойствами типа/формы. Поздний ID в map value допустим там, где неизвестный for_each key мешает определить адреса.

Sensitive

Метка чувствительности для ограничения отображения и распространения по выражениям. Обычные values всё ещё могут храниться в plaintext state/plan.

Ephemeral value

Эфемерное значение, доступное во время исполнения, но исключённое из обычного сохранения в plan/state в допустимых контекстах. Требует поддерживаемой версии/конструкции.

Write-only argument

Поддерживаемый provider аргумент, значение которого не сохраняется обычным образом в plan/state. CLI 1.11+ и schema/provider support обязательны.

Validation

Проверка смысла входного значения, например целочисленности порта. Не доказывает готовность внешней системы.

Precondition

Блокирующее условие перед соответствующей операцией, когда данные доступны. Не откатывает уже выполненные действия других ресурсов.

Postcondition

Условие по результату операции/чтения. Ошибка ограничивает дальнейшие зависимые действия, но не является общей транзакцией.

Check block

Проверка предположений с предупреждением при failed assertion в обычных операциях. Не замена блокирующей precondition для обязательного требования.

Count

Мета-аргумент количества экземпляров с индексами. Изменение порядка исходного списка может изменить смысл существующих адресов.

For_each

Мета-аргумент создания экземпляров по известным ключам map или set(string). Поздние ID лучше передавать значениями, не ключами.

Dynamic block

Генерация повторяющихся вложенных блоков, предусмотренных schema. Не создаёт самостоятельные ресурсы и не генерирует произвольный lifecycle.

Dependency graph

Ориентированный граф зависимостей вычисления/действий. Порядок текста файлов не задаёт порядок готовых независимых вершин.

DAG

Directed acyclic graph — ориентированный граф без циклов взаимной зависимости. Цикл требует изменения модели, а не перестановки блоков.

Depends_on

Явная дополнительная зависимость для скрытой семантической связи. Не переносит данные и не доказывает готовность приложения.

Race

Гонка — результат зависит от несогласованного порядка действий над общим внешним состоянием. Один lock state не защищает от второго независимого state или ручного API.

Refresh

Обновление наблюдения о ресурсах через provider Read. Ошибка API не означает исчезновение объекта; качество плана зависит от полноты наблюдения.

Plan

Вычисленное предложение действий с before/after и неизвестными значениями. Успешный plan ещё не исполнение изменений.

Saved plan

Непрозрачный чувствительный файл решения с входами/данными, привязанный к определённому state и совместимой CLI-среде. Недоверенный файл нельзя считать безопасным текстом.

Apply

Исполнение действий плана и сохранение известных результатов. Не является общей транзакцией с автоматическим rollback всех внешних изменений.

State

Память Terraform об associations адресов/объектов и известных атрибутах/метаданных. Не backup дисков или базы приложения.

Lineage

Идентификатор линии истории state. Отличает независимые состояния с похожими адресами.

Serial

Последовательная версия snapshot внутри lineage; не время и не число ресурсов. Lower serial push и устаревший saved plan должны рассматриваться как конфликт истории.

Backend

Механизм хранения state и предусмотренных операций/locking. Отличается от provider управляемых ресурсов.

Locking

Согласованный допуск к state во время операций. Возможности зависят от backend; Git review не заменяет блокировку.

Workspace

Выбор отдельного state в поддерживаемой модели backend. Не гарантирует отдельные полномочия, аккаунт или безопасную среду только из-за имени.

Drift

Расхождение фактического объекта с ожидаемой конфигурацией/прежним наблюдением. Видимость ограничена Read-логикой provider.

Import

Связывание уже существующего объекта с управляемым адресом по поддерживаемой provider identity. Не гарантирует пригодности HCL и отсутствия subsequent replacement.

Moved block

Декларативное соответствие старого и нового адреса одного управляемого объекта. После применения Git checkout сам не пишет обратный перенос.

Removed block

Декларативное удаление из управления с явной политикой destroy. destroy=false сохраняет внешний объект, забывая association.

Lifecycle

Правила Terraform вокруг создания/изменения/замены/удаления. Не предоставляют внешнему API отсутствующую операцию и не заменяют backup.

Replacement

Замена экземпляра с изменением фактической identity, когда update на месте не выбран/невозможен. План содержит delete/create либо create/delete.

Create_before_destroy

Правило сначала создать замену, затем удалить прежний объект. Требует допуска сосуществования по именам, квотам, данным и доступу.

Prevent_destroy

Запрет Terraform-плана destroy/replacement при присутствующей декларации с правилом. Удаление всего resource block удаляет эту защиту.

Ignore_changes

Осознанное исключение выбранных атрибутов из последующего сравнения для correction. Делит владение и скрывает соответствующий drift от исправления Terraform.

Tainted

Метка экземпляра, для которого требуется замена, например после неуспешного creation provisioner. Не означает потери всего state.

Deposed object

Прежний объект, сохранённый в lifecycle/state при некоторых заменах до окончания удаления. Требует сверки identity, а не ручной очистки памяти.

Provisioner

Дополнительное действие, например local-exec, связанное с lifecycle. Произвольный shell не получает автоматически schema/Read/idempotency управляемого ресурса.

Lock file

Файл .terraform.lock.hcl с выбранными версиями внешних providers и допустимыми checksums. Не фиксирует все modules, CLI и credentials.

Checksum

Контрольный хеш байтов, сравниваемый с доверенно ожидаемым значением. Без подтверждения происхождения ожидаемой суммы не доказывает автора.

SHA-256

Криптографический хеш 256 бит. Проверяет совпадение выбранного архива с проверенным release manifest.

GPG signature

Криптографическая подпись, проверяемая данным ключом. Good signature не решает автоматически вопрос доверия к принадлежности ключа.

Fingerprint

Полный отпечаток публичного ключа. Сверяется с доверенным источником; короткий key ID не заменяет эту проверку.

Version constraint

Условие допустимых версий. Пересечение условий всех modules должно иметь подходящий provider release.

Plugin cache

Повторно используемые установленные provider packages для ускорения init. Не заменяет mirror/discovery и доверенный lock.

Provider mirror

Подготовленный источник provider packages с поддерживаемой структурой для установки. Не получает автоматически remote modules.

Rollback

Явный возврат к выбранному состоянию с проверкой внешних данных и совместимости. Возврат текста Git и памяти не откатывает сам по себе API-изменения.

RPO

Recovery point objective — допустимая потеря последних изменений по времени. Для state и данных приложения могут быть разные цели.

RTO

Recovery time objective — допустимое время восстановления услуги, включая доступ к инструментам, копиям и проверку результата.

Wall time

Прошедшее время команды, включающее ожидания API, диска, lock и планирования CPU.

CPU time

Время исполнения на процессоре; отличается от wall time и может отдельно учитываться у Core/provider processes.

RSS

Resident set size — резидентные страницы памяти процесса. Не равно только Go heap и требует осторожности при суммировании процессов.

Parallelism

Ограничение одновременно обрабатываемых операций графа. Не тождественно числу HTTP requests или гарантии пропорционального ускорения.

Throttling

Ограничение интенсивности запросов внешним API. Retry/backoff при большом parallelism может увеличить итоговое время.

Backoff

Увеличение/изменение ожидания между повторными запросами по политике клиента. Делает длительность операции больше времени одного ответа.

Critical path

Критический путь — самая длинная необходимая цепочка действий графа с учётом фактических задержек и ресурсов.

Libvirt domain

Объект определения/жизни VM в libvirt. UUID domain не доказывает загрузку ОС, адрес SSH или готовность Go-сервиса.

Ownership

Ответственность за управление конкретным объектом или полем. Два независимых владельца могут конфликтовать даже с раздельными корректными state locks.

Readiness

Проверенная готовность объекта/службы к заданному использованию. Существование VM или открытый порт — более узкие признаки.
