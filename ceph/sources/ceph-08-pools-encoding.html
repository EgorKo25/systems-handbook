Как правило пула выбирает места и задаёт цену восстановления

Пул задаёт способ защиты объектов, а CRUSH выбирает устройства, на которых должны находиться копии или кодированные части. Рассмотрим карту с четырьмя host в двух rack, прочитаем её правило и вычислим работу после потери одного host. Механизм и названия полей относятся к Ceph Tentacle 20.2.4.

Какие сведения участвуют в размещении

В главе о пути записи клиент уже получил номер PG и seed размещения — числовой вход выбора OSD. Теперь нужно задать допустимые места и способ выбора. CRUSH map содержит устройства, иерархию их расположения, правила и параметры алгоритма. Она не содержит текущие байты объектов и не выбирает согласованную историю PG.

MON принимают изменения управляющего состояния и распространяют OSDMap. В её кодированное представление входит CRUSH map. Клиенты и OSD получают согласованные версии карты и вычисляют назначение локально. Текстовое представление CRUSH удобно для чтения: в нём числа связаны с именами host, rack и правил. Сам по себе отредактированный текст ещё не меняет карту, принятую MON. Новая OSDMap может изменить состояние OSD или временное назначение PG, оставив дерево CRUSH прежним.

Параметры, меняющие вычисление CRUSH, называются tunables. EC profile — набор параметров erasure coding, кодирования с восстановлением утраченных частей. Их значения и действия разберём после топологии.

Прочитаем небольшую топологию

Bucket в CRUSH — внутренний узел дерева, объединяющий устройства или другие узлы. Это отдельное значение слова bucket; контейнер объектов S3 к этому дереву не относится. Тип bucket описывает уровень группировки: host объединяет OSD машины, rack — машины стойки, root — выбранное верхнее поддерево. Тип не обнаруживает физические связи автоматически: если две машины питаются от одного блока, а карта изображает независимые стойки, алгоритм будет использовать именно записанную топологию.

Ниже задан новый расчётный пример с корнем study, пятью OSD и четырьмя host. Он не изменяет таблицу пула 7 из предыдущих глав. Здесь OSD ID 0–4 назначены автором, объёмы выражены в TiB: один TiB равен 1024 GiB, один GiB — 2 в степени 30 байт. Все показанные связи и размеры являются входами расчёта, а не выгрузкой состояния настоящего кластера.

Перенос имени между строками без сохранения смысла ID способен изменить размещение.

Вес, ёмкость и занятые байты — разные входы

Вес CRUSH задаёт относительную долю размещения. В примере единице веса соответствует один TiB объявленной сырой ёмкости. Это выбранное соответствие с обычной единицей CRUSH, а не измерение свободного места. Внутри реализации вес хранится как число с 16 дробными битами: 1 соответствует 65536, 0.5 — 32768. Напечатанные десятичные числа являются представлением этих значений.

При одинаковой роли в правиле устройство веса 1 получает большую долю выборов, чем устройство веса 0.5. Нельзя из этого вывести точные 2:1 занятых байтов на маленьком наборе PG. Две PG могут содержать разные объёмы, а требование разных host ограничивает допустимые сочетания. Внутри a0 равные веса делят выбор между 0 и 1; на более высоких уровнях выбираются поддеревья с их весами. Сравнивать только размеры двух листьев, игнорируя дерево и правило, недостаточно.

Фактическая занятость получается после размещения конкретных объектов и работы BlueStore. Алгоритм CRUSH не проверяет перед каждым выбором свободные GiB и очередь диска. Заполнение влияет на возможность выполнить запись и backfill через отдельные состояния и ограничения. Поэтому увеличение CRUSH weight заполненного устройства не создаёт на нём место. Оно может, наоборот, направить к нему больше PG.

Кроме основного веса существуют альтернативные weight sets: наборы весов для расчёта размещения. Вариант compat общий, per-pool относится к отдельному пулу и может различать позиции результата. Balancer — модуль MGR, вычисляющий поправки распределения, — может использовать такие механизмы или явные переназначения PG. В нашем расчёте альтернативных weight sets и поправок balancer нет. Их наличие в настоящем кластере нужно читать отдельно от основной колонки CRUSH weight.

Веса и альтернативные наборы: единицы веса, weight sets; преобразование в fixed point.

Класс устройства сужает дерево

Device class — метка устройства, которую правило может использовать как фильтр. hdd, ssd и nvme описывают выбранный класс; метка сама не измеряет скорость и не резервирует устройство одному пулу. Если один пул выбирает ssd, а другой не ограничивает класс, оба могут размещаться на том же SSD.

Для класса Ceph строит shadow tree — производное дерево, содержащее только устройства этого класса и необходимые родительские bucket. Физические OSD остаются теми же: hdd-копия дерева не создаёт второй osd.0 или дополнительные байты. Производные bucket получают свои ID; не нужно угадывать их по ID обычных родителей.

Правило с тремя копиями по разным host может использовать hdd-поддерево. Для ssd-поддерева оно не получит три допустимых host, даже если osd.1 совершенно пуст. Наличие известного класса и существующего корня позволяет создать правило, но не доказывает достаточность доменов для каждого пула. Неизвестный класс или корень без устройств данного класса дают другую проблему: конструктор правила отклоняет такой вход.

Правило выполняется как последовательность шагов

Выберем replicated pool study-repl с числовым ID 11, size=3, min_size=2 и crush_rule=12. Replicated означает хранение полных копий. Параметры PG здесь остаются фиксированными. Числа и имена заданы для следующего расчёта; создание нового пула не обязано выдать ID 11. Правило 12 имеет следующую выбранную форму:

rule study-host {
    id 12
    type replicated
    step take study
    step chooseleaf firstn 0 type host
    step emit
}

ID 12 связывает запись пула с этим правилом. Type replicated задаёт тип правила, но число копий берётся из size пула. TAKE помещает выбранный корень study в рабочий список. CHOOSELEAF выбирает разные bucket типа host и внутри каждого — лист OSD. В числе 0 здесь записана инструкция запросить столько мест, сколько передал вызывающий код; для нашего пула это три. EMIT переносит полученные OSD в выходной список правила и очищает рабочий список. Ни один из этих шагов не переносит payload по сети.

CHOOSE отличается от CHOOSELEAF тем, что останавливается на выбранном типе. Например, шаг choose firstn 2 type rack вернул бы два bucket rack, после чего отдельный шаг должен выбрать OSD внутри каждого. Шаг chooseleaf firstn 0 type rack сразу вернул бы по OSD из трёх разных rack. В study есть только два rack, поэтому выполнить последнее требование полностью невозможно. Добавление ещё десяти дисков в rack-a не добавит третью стойку.

Firstn и indep определяют работу с позициями результата. Firstn подходит для полных копий: если один кандидат исключён, следующие найденные участники могут сдвинуться. У кодированных частей позиции различают содержимое, поэтому обычное EC-правило использует indep: замена ищется для нужной позиции. Не заполненная после попыток позиция может остаться CRUSH_ITEM_NONE — специальной отметкой отсутствующего устройства. Она не означает OSD с таким именем.

Для выбора только hdd в TAKE добавляется class hdd, и код разрешает это имя в корень соответствующего shadow tree. Для размещения по rack меняется тип в CHOOSELEAF. Изменение этих строк меняет множество допустимых мест; оно не меняет физическое расположение уже записанных байтов мгновенно.

Шаги: исполнение TAKE, CHOOSE, CHOOSELEAF и EMIT; indep и незаполненные позиции; построение обычного правила.

Как straw2 получает кандидата и зачем повторяет выбор

При неизменных входах CRUSH возвращает одинаковый результат. В bucket straw2 для каждого ребёнка вычисляется хеш от seed, ID ребёнка и номера попытки. Через целочисленное приближение логарифма и деление на вес получается оценка draw; выбирается наибольшая. Больший вес увеличивает вероятность выигрыша по множеству seed. Здесь нет генератора случайных чисел, заново выбирающего место при каждом чтении объекта.

Выигрыш внутри bucket ещё не означает принятие конечного OSD. При спуске к host кандидат может совпасть с уже выбранным host. У выбранного host может не найтись допустимого листа; лист может иметь нулевой коэффициент участия OSDMap. Тогда меняются счётчики попыток и повторяется соответствующий спуск. Эти счётчики участвуют в хешировании. Повтор не означает обращение к MON за разрешением и не означает поиск первого диска с достаточным свободным местом.

Для пояснения ограничений зададим вручную последовательность предложений 0,1,2,3. При требовании трёх разных host принимается 0, затем 1 отклоняется, поскольку оба находятся в a0. После 2 и 3 получается [0,2,3]. Это проверка заданной последовательности по топологии. Настоящий straw2 должен сам вычислить предложения на каждом уровне; наша последовательность его хеши не воспроизводит.

Выберем для карты параметры семейства jewel, реализованные в v20.2.4, с straw_calc_version=1. Все bucket примера используют straw2. Имя jewel обозначает совместимый набор поведения, а не версию запущенного Ceph. Значения нового или унаследованного настоящего кластера нужно читать из его карты.

Сам короткий результат не доказывает математическую невозможность; для нашего примера невозможность трёх разных rack следует отдельно из наличия всего двух rack.

Этот путь нужен, например, при EC profile с crush-osds-per-failure-domain больше 1. Он предъявляет отдельное требование поддержки CRUSH_MSR клиентами и OSD. Подстановка такого профиля изменит алгоритм и смысл допускаемых потерь; наша модель MSR не выполняет.

От seed к обслуживающему составу

Переход имени в PG, роль pg_num и pgp_num уже рассчитаны в главе 05. Здесь продолжим с готового seed. OSDMap берёт crush_rule и size пула, вызывает правило, передаёт коэффициенты участия OSD и применимые альтернативные веса. Результат назовём raw placement — исходным списком OSD до следующих поправок OSDMap. Правило ничего не знает о последнем подтверждённом изменении объектов.

Pg_upmap задаёт явное назначение PG, pg_upmap_items — замены отдельных участников, pg_upmap_primaries — поправку выбора primary. Эти overlays — дополнительные поправки — хранятся в OSDMap отдельно от правила. Primary_affinity задаёт предпочтение роли primary. Pg_temp позволяет использовать временный состав; primary_temp отдельно переопределяет primary. Эти сведения нужно учитывать при объяснении расхождения между расчётом одного правила и действующими up/acting. Глава 06 разбирает, как пригодность участников ограничивает переход к работе; временное назначение не создаёт отсутствующие данные.

Есть ещё один вес: OSDMap weight, коэффициент участия OSD, обычно от 0 до 1. Значение 0 означает out и исключает лист в mapper. Значение 1 допускает полное участие. При промежуточном значении сравнение детерминированного хеша с порогом исключает OSD для части seed. Это отдельный вход по отношению к ёмкостному весу 0.5 или 1 в дереве. Изменение CRUSH weight меняет веса дерева и суммы родителей; изменение коэффициента OSDMap оставляет номинальные веса дерева прежними. Down при сохранном in не равен out: raw ещё может содержать этот OSD, а последующая обработка уберёт недоступного участника из up.

В replicated pool обработка down сдвигает оставшиеся OSD в списке. В обычном EC pool позиции надо сохранить: на месте down может остаться CRUSH_ITEM_NONE. Иначе позиция одной кодированной части стала бы обозначать другую часть. В обоих случаях состояние PG после новой карты определяется дальнейшим протоколом, а не длиной напечатанного списка.

Вызов правила и overlays: raw, upmap и обработка down; временный состав и primary; is_out и коэффициент участия.

Что защищают size и домен отказа

Для study-repl size=3 означает три полных экземпляра объекта. Min_size=2 ограничивает допустимый обслуживающий состав; назначение истории, локальные commit и подтверждение записи разобраны в главах 05/06. Уменьшение min_size не добавляет независимых мест и не изменяет правило выбора. Если правило требует три разных host, два OSD одного host не могут заполнить две его позиции.

Политика для studyДостаточность топологииСледствие отказа
Три полные копии, разные host, без классаЧетыре допустимых host; тройку можно разместить.После безвозвратной потери a0 остаются три host для восстановления трёх копий.
Три полные копии, разные rackВсего два rack; третьего места нет.Свободные TiB внутри этих rack не выполнят требование третьей стойки.

Разные host в одной стойке защищают от выбранного отказа машины, но не обещают сохранение трёх независимых копий при потере стойки. Если два участника оказались в rack-a, её потеря одновременно уберёт две копии. Модель отказа должна соответствовать реально общим питанию, сети и гипервизору. Запись rack в дереве сама по себе не доказывает физическую независимость.

Что меняет кодирование K/M

Erasure coding хранит части объекта, позволяющие восстановить его при отсутствии части устройств. K обозначает число частей данных, M — число дополнительных кодированных частей. Для выбранного здесь Reed–Solomon любые K согласованных пригодных частей позволяют восстановить данные; всего мест требуется K+M. Часть на определённой позиции называется shard. Она отличается от полной реплики: один shard обычно не содержит весь объект.

Зафиксируем пример profile study-ec-2-1. Plugin isa — реализация через ISA-L; technique reed_sol_van выбирает вариант Reed–Solomon с матрицей Вандермонда. Для расчёта выбраны K=2, M=1 и stripe_unit=4096 байт. Crush-root=study задаёт исходное поддерево, crush-failure-domain=host — разные host для частей. Фильтра класса нет. Это выбранные параметры, не содержание профиля default.

profile study-ec-2-1:
    plugin=isa
    technique=reed_sol_van
    k=2
    m=1
    stripe_unit=4096
    crush-root=study
    crush-failure-domain=host

pool study-ec:
    type=erasure
    erasure_code_profile=study-ec-2-1
    size=3
    min_size=3  # явно выбранное условие этого примера
    crush_rule=13
    allow_ec_optimizations=false

Stripe — полоса логических данных, разложенная по K частям. Назовём две части данных D0 и D1, а кодированную часть — P0. Stripe_unit задаёт размер порции в одной части за полосу; stripe_width равна K×stripe_unit. Здесь полоса содержит 8192 логических байта: диапазон [0,4096) первой полосы идёт в D0, [4096,8192) — в D1, затем вычисляется P0. Диапазон [8192,12288) следующей полосы снова идёт в D0. Поэтому D0 не следует понимать как первые два MiB четырёхмегабайтного объекта, непрерывно отделённые от остальных.

Полный объект 4 MiB содержит 4194304/8192=512 таких полос. Каждая часть содержит 512×4096=2097152 байта, то есть 2 MiB. Вместе D0, D1 и P0 занимают 6 MiB payload. Отношение к исходным 4 MiB равно (K+M)/K=1.5. У size=3 replicated pool те же 4 MiB дают 12 MiB payload. Метаданные, выравнивание, локальное усиление записи и временные данные восстановления в обе суммы не включены.

Для обычного EC-правила конструктор v20.2.4 добавляет свои пределы попыток. Следующая форма показывает правило 13, соответствующее выбранному профилю, без MSR и дополнительных политик:

rule study-ec-host {
    id 13
    type erasure
    step set_chooseleaf_tries 5
    step set_choose_tries 100
    step take study
    step chooseleaf indep 0 type host
    step emit
}

Первые два шага переопределяют пределы поиска листа и внешнего выбора. TAKE и EMIT имеют прежний смысл. INDEP сохраняет позиции D0/D1/P0. Число 0 запрашивает size=3 места. Параметры crush-* профиля служат входом создания правила, а действующее назначение использует crush_rule пула. Если позже пулу назначили другое правило, печать прежнего profile не доказывает, что он всё ещё размещается по прежнему домену.

Size этого EC pool получается из K+M, а не задаёт число полных копий. Min_size=3 выбран здесь явно: после потери одного shard обычный IO ждёт восстановления достаточного состава, хотя две сохранные части позволяют выполнить recovery. Это не автоматическое значение для 2+1: код создания v20.2.4 вычисляет K+min(1,M−1), то есть 2. Документация рекомендует min_size не меньше K+1. Возможность математически восстановить данные по двум частям и разрешение новых операций — разные условия. История и корректность этих частей тоже должны быть установлены протоколом.

Для трёх частей по host наша топология подходит. Если D0 находится на a0, D1 на a1, P0 на b0, потеря rack-a уберёт сразу две части. Оставшегося одного shard недостаточно для K=2. Механизм M=1 защищает от потери одной части в этом размещении; перенос названия host на rack без появления третьей стойки не исправляет пример.

Profile задаётся при создании EC pool. Для смены K/M и формата кодирования требуется другой пул и перенос данных, а не изменение одного числа у существующих объектов. EC pool не поддерживает omap — объектную карту ключей и значений. Поэтому RBD и CephFS используют отдельные replicated metadata pools, а EC могут выбрать для данных. Частичные перезаписи требуют allow_ec_overwrites на BlueStore. Расчёт относится к полной записи, без этих дополнительных операций.

В Tentacle есть allow_ec_optimizations, меняющий хранение новых данных и поведение небольших IO. Его нельзя выключить после включения; поддерживаются определённые plugin/technique и требуется подходящая версия всех MON/OSD. Наше false сохраняет обычный путь без этих оптимизаций. Из рассчитанных 6 MiB нельзя вывести расход произвольных малых объектов и случайных перезаписей в другом режиме.

Профиль, полосы и ISA: Erasure code profiles, ISA plugin; пять шагов обычного indep-правила; исходные size/min_size EC; recovery при K частях и рекомендация min_size; omap, overwrites и optimizations.

Изменение карты ещё не переносит объекты

Добавление устройства, изменение веса или правила заставляет участников пересчитать назначения по новой карте. При фиксированных PG и неизменном содержимом новые копии нужны там, где изменился набор мест данной PG. Объекты PG с прежним назначением из-за одного получения карты не переписываются. Смена только роли primary в replicated pool также не требует заново копировать все уже согласованные полные экземпляры.

У straw2 изменение веса непосредственного ребёнка сохраняет оценки остальных детей: в одном таком выборе перенос идёт к изменённому ребёнку или от него. Но дерево имеет несколько уровней, а выбор нескольких доменов содержит повторы и ограничения. Нельзя из локального свойства сделать обещание «при любой правке карты изменится только один OSD». Добавление диска в b0 меняет его суммарный вес и выбор на родительских уровнях. Изменение всех tunables или правила может затронуть много PG.

Новый OSD внутри b0 увеличит ёмкость и число листьев, но не число host или rack. Новый host внутри rack-b добавит домен host, но не rack. Изменение класса сузит или расширит shadow tree. Смена правила с host на rack в нашем примере при size=3 даст невыполнимое требование: до такого изменения нужно изменить исходную топологию или политику. Копирование данных не может исправить отсутствие допустимого места.

Для расчёта потери a0 зададим четыре PG study-repl, каждая с 128 GiB логических данных. Все объекты плотные, несжатые, по 4 MiB; снимков, общих данных, новых записей и других отказов в расчёте нет. Назначения ниже заданы вручную допустимыми последовательностями кандидатов из сопровождающей модели. Это не результат straw2 или трасса изменения настоящего CRUSH.

Готовность текущего acting, сохранность истории и необходимость ожиданий устанавливает peering. Новое присутствие 4 в целевом списке не означает, что у него уже есть 128 GiB этой PG.

Когда достаточно recovery и когда требуется backfill

После согласования истории primary знает, какие объекты отстали и откуда получить нужные версии. Recovery использует эти сведения для ограниченного восстановления. Если вернулся тот же сохранный OSD и PG log ещё покрывает пропуск, изменившихся объектов может оказаться мало, как в примере одной замены из главы 06. Источником служит участник с нужным согласованным состоянием, целью — участник с недостающей копией или частью. Живой процесс без этой версии источником не становится.

Пустой получатель или недостаточный диапазон log требуют backfill: сопоставления состава PG по диапазонам внутреннего порядка объектов. Диапазон обхода PG не является диапазоном байтов одного объекта. Primary и получатель собирают сводки объектов и версий, продвигают положение обхода и определяют дальнейшую работу. В имени сообщения SCAN_GET_DIGEST слово digest означает такую сводку; из него не следует вычисление SHA256 каждого payload.

Принятая история и сводка источникаСводка получателя в том же диапазонеОбычное действие backfill
Объект и нужная версия присутствуютТа же версияСохранить имеющийся экземпляр; повторный перенос payload по этому сравнению не нужен.
Объект и нужная версия присутствуютВерсия отличается или объекта нетПодготовить перенос требуемого состояния.
В согласованном диапазоне объекта уже нетСтарая запись ещё присутствуетУдалить лишнее состояние в рамках согласованного восстановления.

Равенство версий в сводке не заменяет проверку целостности устройством и scrub. Между обходами клиент может создать или изменить объект, поэтому код обновляет диапазоны и координирует текущие записи. Один проход списка имён без истории и синхронизации не выполняет работу backfill.

Переносу нужны разрешения на фоновую работу и место у конкретной цели. Для backfill запрашиваются локальное и удалённые reservations — допуски ограниченного числа параллельных работ. Слово reservation здесь относится к очереди работ, а не к гарантированному резервированию всех будущих GiB на носителе. Заполнение цели может остановить backfill, хотя на другом OSD много свободного места. Состояния ожидания и backfill_toofull поэтому нужно отличать от отсутствия источника unfound.

Во время обычного изменения размещения старая пригодная копия может сохраняться до готовности новой. Мгновенный расход места способен превысить конечный. При безвозвратной потере a0 в нашем расчёте старые носители уже недоступны: восстановление возвращает потерянную защиту из оставшихся копий. До его завершения нужные PG располагают меньшей защитой от следующего отказа. Оставлять их degraded ради скорости приложения означает продлевать именно это состояние.

Сопоставление диапазонов и версий: инварианты backfill, keep, replace, push и remove; запрос удалённых reservations; выбор источника pull.

Ёмкость и время для выбранных четырёх PG

Пользовательские данные занимают 4×128=512 GiB. Три полные копии дают 1536 GiB payload на 4096 GiB сырой ёмкости, в среднем 37.5%. По заданной таблице распределение неравномерно: 0 хранит две PG, 1 — одну, остальные — по три. Это следствие выбранных строк, не предсказание распределения по весам CRUSH.

Потеря a0 убирает 384 GiB копий. На каждом уцелевшем OSD нужно добавить 128 GiB. Его расчётный остаток до переноса равен 1024−384=640 GiB, после — 512 GiB. Это остаток модели payload: в реальности нужны также метаданные, место для временной работы и соблюдение действующих ограничений заполнения. При трёх оставшихся host правило ещё может восстановить size=3. После потери ещё одного host этого числа доменов уже не будет.

Выберем источники: для 11.0 OSD 2 передаёт копию OSD 4, для 11.1 OSD 3 — OSD 2, для 11.2 OSD 4 — OSD 3. Они уже содержат нужные версии по условиям примера. Получается 384 GiB чтений payload источников, столько же записи у целей и 384 GiB меж-OSD передачи. Из неё 256 GiB пересекает rack-a/rack-b, а 128 GiB проходит между host rack-b. Здесь одни переданные байты считаются один раз, без сложения RX и TX двух концов.

Три из четырёх PG меняют набор, но требуется одна новая копия их объектов. Поэтому 75% затронутых PG не означают перенос 75% всех 1536 GiB копий: в примере переносится 384/1536=25%. При объектах по 4 MiB это 3×128×1024/4=98304 новых экземпляра. Размер отдельного сообщения или число физических IO из этого количества не выводятся.

Зададим условные суммарные пределы именно для этой работы: чтение источников 160 MiB/s, запись целей 128 MiB/s, общая сеть для всех трёх потоков 96 MiB/s. Нижняя оценка времени по каждому ресурсу равна объёму, делённому на его скорость: 2457.6, 3072 и 4096 секунд. Самая большая — 4096 секунд, то есть 68 минут 16 секунд; сеть является узким местом этой модели. Эти скорости не измерены и не описывают конкретные устройства.

Нельзя сложить три времени как обязательные последовательные стадии: чтение, передача и запись могут перекрываться. Нельзя и обещать завершение за 4096 секунд. Оценка исключает обнаружение отказа, peering, ожидание допусков, сканирование, служебный IO, локальное усиление записи и конкурирующие запросы. Путь физической записи и различия границ её измерения остаются в главе BlueStore.

Почему восстановление EC требует других чтений

Вернёмся к одному объекту 4 MiB в study-ec. Для расчёта разместим D0 на 0, D1 на 2, P0 на 3. После потери 0 выберем 4 для D0. Каждый shard занимает 2 MiB. Обычное восстановление утраченного D0 читает две пригодные части D1 и P0 общим объёмом 4 MiB, вычисляет недостающую часть и записывает 2 MiB на цель. Один сохранившийся shard нельзя просто целиком скопировать под именем D0.

Выберем координатором восстановления OSD 2: он читает свой D1, получает 2 MiB P0 от 3 и передаёт вычисленные 2 MiB D0 на 4. Для этого выбранного размещения расчётный меж-OSD payload равен 4 MiB; чтения payload равны 4 MiB, запись цели — 2 MiB. При другом координаторе, числе целей, коде или повторных чтениях передачи будут другими. Это учёт выбранного пути данных, не сетевая трасса и не исполнение кодека ISA.

В обычном EC backend код получает пригодные части, вызывает decode, готовит PushOp для отсутствующих shard и продолжает работу порциями с сохранением прогресса. Помимо чтения, сети и записи появляется CPU-работа декодирования и расход памяти на буферы. Восстановление нескольких частей может использовать общие прочитанные данные; умножение расхода одного случая на M не является универсальной моделью. Когда нет необходимых согласованных частей, дополнительные CPU и пустой диск не создадут источник.

Обычный EC-путь при выключенных optimizations: выбор backend; приём частей и decode; порции чтения, PushOp и завершение.

Что регулирует конкуренцию с запросами приложения

Foreground означает операции приложения, для которых читатель ждёт результат. Background — фоновую работу OSD, например recovery, backfill и scrub. Они используют общие CPU, сеть и устройства. Scheduler — планировщик очереди — выбирает следующую работу к исполнению. В этой главе рассматривается обычный OSD с BlueStore и явно выбранными osd_op_queue=mclock_scheduler, osd_mclock_profile=balanced, osd_op_queue_cut_off=high. В v20.2.4 это исходные значения соответствующих options; у действующего OSD они могли быть изменены.

MClock различает client, background_recovery и background_best_effort. Для каждого класса reservation задаёт резервируемую скорость обслуживания в модели стоимости, weight — относительное участие в оставшемся ресурсе, limit — верхний предел в той же модели. В balanced исходные тройки (reservation, weight, limit) равны (0.5,1,MAX), (0.5,1,MAX), (0.05,2,0.9). Это параметры планировщика; их нельзя читать как разбиение физического диска на три независимых раздела или как обещание p99.

Исходное поле стоимости операции называется item_cost. Планировщик учитывает его и цену одного IO, рассчитанную по настроенным bandwidth и IOPS носителя. Например, при условных 256 MiB/s и 1024 IO/s цена одного IO равна 256 KiB. Код выбирает максимум между стоимостью операции и этой ценой: операция с item_cost=4 KiB получает 256 KiB учётной стоимости, с item_cost=4 MiB — 4 MiB. Это арифметический пример функции, а не измеренный расход носителя. Ошибка в оценке мощности устройства изменяет смысл долей и ограничений.

Очередь делится на внутренние части OSD, называемые здесь queue shards. Они не являются EC shard с D0/D1/P0. У каждой такой очереди свой планировщик. После передачи операции в исполнение mClock уже не выбирает заново каждый её дисковый IO. Ограничения BlueStore на объём находящейся в работе записи действуют следующим уровнем. Общий физический backend нескольких VM, перегруженная сеть или CPU декодирования не превращаются от наличия mClock в независимые ресурсы.

ПараметрыЧто ограничивают или выбирают в v20.2.4
osd_mclock_profileBuilt-in balanced/high_client_ops/high_recovery_ops либо custom. Built-in управляет нижними reservation/weight/limit; попытки отдельно менять их отклоняются восстановлением параметров профиля.
osd_mclock_max_capacity_iops_hdd/ssd; osd_mclock_max_sequential_bandwidth_hdd/ssdМощность устройства для расчёта стоимости. Это входы модели планировщика, не счётчики уже выполненного IO.

При mClock выбранный OSD сбрасывает перечисленные в коде recovery sleep и другие фоновые sleep в ноль. Поэтому старый совет увеличивать osd_recovery_sleep не описывает регулирование этой конфигурации. Увеличение параллелизма тоже не означает автоматическое ускорение: если уже насыщен общий источник, добавляются ожидающие работы и конкуренция с приложением. Изменение оценивают по действующим параметрам и наблюдениям одной и той же нагрузки.

Профиль и учёт стоимости: перевод долей в cost/second, мощность, profiles и scaled cost, защита параметров built-in; выбор recovery_max_active, limits и sleep; очереди и BlueStore throttles.

Какой приоритет получает выбранное чтение EC recovery

Не все сообщения идут через регулируемую очередь. В v20.2.4 код enqueue выделяет immediate — срочный класс, — а также сообщения с приоритетом не ниже cutoff в отдельную строгую очередь. Она выбирается прежде обычной очереди mClock. Для выбранного high cutoff равен CEPH_MSG_PRIO_HIGH=196. Поэтому обещание ограничить весь сетевой recovery одним профилем было бы сильнее реализованного механизма.

Проследим производителя чтения из обычного EC-пути. Выберем восстановление PG с признаком undersized, без принудительного восстановления (forced), и сохраняем mclock_scheduler. get_recovery_op_priority возвращает 15. PrimaryLogPG передаёт это значение в run_recovery_op; ECSwitch при allow_ec_optimizations=false направляет вызов в ECBackendL. Его dispatch_recovery_messages передаёт 15 в ReadPipeline; при создании MOSDECSubOpRead значение устанавливается через set_priority. Имя типа сообщения на принимающей стороне — MSG_OSD_EC_READ.

Приёмный PGOpItem сначала проверяет priority не выше FORCED=20. Для 15 это условие выполнено. Затем priority_to_scheduler_class сравнивает его с HIGH=196 и DEGRADED=10: 15 меньше 196, но не меньше 10, поэтому получается background_recovery. В enqueue 15 также ниже выбранного cutoff=196; сообщение поступает в регулируемую очередь. Если состав уже не undersized, но PG degraded, тот же производитель вернёт 10 и получится тот же класс. Если нет обоих признаков и forced, значение 5 ведёт к background_best_effort. Это разбор конкретных ветвей кода, а не результат наблюдения очереди настоящего OSD.

Клиентское EC-чтение с приоритетом вне диапазона recovery этой ветвью не ограничивается и попадает в immediate; EC sub-operation writes и ответы также имеют свои срочные пути. В том же pinned mclock-config-ref.rst сохранилось предупреждение, что EC recovery reads обходят mClock через immediate. Однако приведённая классификация OpSchedulerItem.h уже содержит иную ветвь для recovery priority. Это расхождение документации и кода одного тега. Для описанного вызова следует указанная ветвь производителя и приёмника; из неё не следуют ограничение всех сообщений EC и верхний предел задержки обычных запросов. Срочный поток выбирается раньше регулируемой очереди, а уже исполняемая работа находится за пределами этого выбора.

Вся выбранная передача приоритета: 15/10/5 и условие mClock, вызов run_recovery_op, выбор обычного backend, передача в ReadPipeline, сохранение priority и set_priority; приём: порог класса, MSG_OSD_EC_READ, enqueue; high cutoff, HIGH=196; отличающееся предупреждение pinned documentation.

Какие наблюдения различают причины задержки

Сначала сравнивают желаемое размещение, текущий состав и готовность данных. Затем оценивают работу, которую этот переход создаёт на источниках и целях. Следующие формы запросов читают состояние уже существующего принятого кластера. Имена и PG ID заменяются фактическими значениями этого кластера.

ceph osd crush dump --format json-pretty
ceph osd crush rule dump study-host
ceph osd crush tree --show-shadow
ceph osd pool get study-repl all
ceph osd erasure-code-profile get study-ec-2-1
ceph osd dump --format json-pretty
ceph osd df tree
ceph pg 11.0 query

Crush dump показывает структуру, веса и tunables; rule dump — конкретные шаги. Show-shadow помогает проверить фильтр класса. Pool get связывает пул с правилом и политикой защиты. Osd dump нужен для состояния OSD и overlays. Osd df tree сопоставляет объявленные веса с фактической занятостью. Pg query показывает состояние одной PG, up/acting, историю и текущую стадию recovery. Ни один из этих снимков отдельно не подтверждает чтение всех пользовательских данных.

НаблюдениеЧто проверять следующим
Мест меньше sizeКорень, класс, число допустимых доменов, OSDMap weights, down, правила и пределы попыток.
Up отличается от actingВременное назначение, состояние peering и пригодность текущего primary; не удалять pg_temp ради совпадения колонок.
Есть цель, но backfill ждётReservations, заполнение именно цели, флаги подавления работы, доступность источника и состояние PG.
Идёт перенос, а приложение замедлилосьОчереди источников и целей, эффективный scheduler/profile, ограничения параллелизма, disk IO, сеть, CPU и память в одном временном окне.
Перенос закончился, но данные подозрительныОтдельное чтение контрольных данных и проверку целостности; clean не заменяет испытание backup/restore.

Объём логических операций приложения, меж-OSD payload и физические байты устройства считают отдельно. Для задержки сохраняют одну границу end-to-end, включая ожидания и повторные попытки, и отдельно показывают ошибки. P95/p99 вычисляют по соответствующему распределению; среднее и усреднение p99 разных OSD его не заменяют. Снижение скорости восстановления может улучшить текущую задержку, но увеличивает время с неполной защитой. Решение требует обоих наблюдений: поведения приложения и прогресса возвращения защиты.

Чтение состояний: Monitoring OSDs and PGs; MClock Config Reference v20.2.4. Объектная проверка продолжается в малой практике RADOS.
