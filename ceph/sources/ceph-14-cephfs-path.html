Имя файла, разрешение кэша и путь его байтов

CephFS добавляет файловую семантику. Для её понимания нужно различать метаданные, содержимое и два разных смысла capabilities.

Открыть файл

Путь /reports/day-1.txt состоит из имён каталогов и файла. Inode — внутреннее описание файлового объекта: его идентичность и свойства. Каталог связывает имена с такими объектами. MDS обслуживает операции над этими файловыми метаданными, а их устойчивое представление хранится в RADOS.

Клиент запрашивает необходимые сведения у MDS. Получив layout — правило расположения данных файла, — он обращается к OSD за содержимым. MDS не обязан пересылать каждый байт файла между приложением и носителем. При этом недоступность требуемой файловой координации может препятствовать файловой операции даже при живых OSD.

Два смысла caps

CephX capabilities задают полномочия удостоверения клиента: к каким данным и операциям ему разрешён доступ. Inode capabilities в протоколе CephFS — выдаваемые MDS временные разрешения держать или изменять определённые данные и метаданные в кэше клиента. Первое относится к авторизации, второе — к согласованию распределённого кэша.

Когда другому участнику нужен конфликтующий доступ, MDS отзывает соответствующее разрешение. Клиент должен вернуть его и передать необходимые обновления. Задержка такого клиента может тормозить операции других клиентов. Поэтому медленный metadata request нельзя автоматически объяснять медленным диском данных.

Кэш, журнал и границы авторизации

MDS хранит рабочее представление метаданных в памяти, а journal фиксирует изменения для предусмотренного восстановления. Журнал не является самодостаточной внешней копией всех файлов. Восстановление MDS и восстановление содержимого имеют разные входы и проверки.

Ограничение MDS по пути управляет файловой иерархией. Оно не должно ошибочно объявляться полным ограничением любого прямого обращения клиента к RADOS. Для изоляции недоверенных клиентов проверяют также layout, namespace и OSD capabilities.

Первоисточники: distributed metadata cache, CephFS client capabilities и path restriction. Команды создания и монтирования относятся к следующей фазе после подготовки отдельного клиента.

Имя не является адресом данных

Запрос open начинается с имени, но inode имеет собственный номер. Два имени через hard link могут ссылаться на один inode. Rename меняет связи имён в каталогах, а не обязательно переносит все data objects файла. MDS кэширует dentries — записи соответствия имени inode — и сами inode. Клиент получает результат поиска и разрешения кэша; открытый файл не обязан заново обходить всю иерархию перед каждым чтением.

Устойчивые metadata и журнал MDS находятся в metadata pool RADOS. Содержимое файлов находится в data pools. Потеря metadata pool может оставить байты объектов без пригодного файлового дерева. Наличие здоровых data PG не доказывает, что имена файлов можно восстановить без дополнительного состояния. Metadata pool требует replicated-защиты; EC допускается для подходящего data pool с BlueStore и разрешёнными перезаписями, но не заменяет metadata pool.

Точный layout одного файла

Layout задаёт pool/pool_namespace, object_size, stripe_unit и stripe_count. Размер объекта — предел порции RADOS, stripe_unit — размер очередного чередующегося блока файла, stripe_count — число объектов в полосе. При простом object_size=stripe_unit=4 MiB и stripe_count=1 смещение 10 MiB даёт объект 2 и 2 MiB внутри, как в простом RBD-примере.

Изменим только layout: object_size=4 MiB, stripe_unit=1 MiB, stripe_count=2. Файл сначала кладёт 1 MiB в объект 0, затем 1 MiB в объект 1, затем следующие MiB снова в 0 и 1 до заполнения обоих 4 MiB. Байт 5 MiB+64 лежит в шестой порции по 1 MiB, то есть в объекте 1, по смещению 2 MiB+64. После 8 MiB начинается пара объектов 2 и 3. Это вычисление заданного layout, не dump работающей CephFS.

Поля видны через virtual xattrs — расширенные свойства, вычисляемые файловой системой. getfattr -n ceph.file.layout FILE читает layout. Изменять layout можно у пустого файла и с соответствующим правом p; изменение layout каталога задаёт наследование для новых файлов, не перемещает автоматически уже записанные данные всех потомков.

От write к fsync

Приложение может получить успех write после изменения клиентского кэша. Для устойчивости оно вызывает fsync; клиент должен завершить требуемую запись данных на OSD и согласовать необходимые metadata. Приложение, закрывающее файл без нужного протокола синхронизации, не может выводить сохранность после внезапной гибели клиента из одного успешного write. При rename отдельно учитывается устойчивость изменений каталогов, которую требует протокол приложения.

Рассмотрим запись новых 4 KiB в конец файла. У клиента меняются байты и представление размера; OSD получают объектные изменения по layout, MDS должен получить относящиеся к inode обновления. Inode cap определяет, кто временно вправе держать такое состояние. Это распределённая координация: одного наблюдения latency диска данных недостаточно, если fsync ждёт MDS.

Что измерить

Разделите два опыта. Первый многократно читает уже открытый большой файл: основная нагрузка связана с data IO и кэшами. Второй создаёт много маленьких файлов и выполняет lookup/stat: растёт работа MDS и metadata pool. Укажите число файлов, размер, число клиентов, прогретость кэша и границу измерения. Сравнивать их MiB/s как одну «скорость CephFS» нельзя.

Задание: оба data pool здоровы, но open нового имени завис. Что проверять первым? Состояние MDS, metadata pool, клиентские сессии и outstanding requests. Прямое чтение известного объекта через rados обходит файловую координацию и не является эквивалентом успешного open.
