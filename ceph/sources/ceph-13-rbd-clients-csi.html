Клиент RBD: ключ, lock и право продолжить запись

Доступ к image требует совместимого клиента и полномочий. После отказа прежнего писателя дополнительно нужно исключить его возврат к записи одновременно с новым.

Отдельное удостоверение

CephX entity client.rbdstudy обозначает клиента Ceph; это не имя Linux-пользователя. MON проверяет ключ и выдаёт билеты, OSD применяют capabilities — полномочия на указанный пул. Для RBD применяется profile rbd, который включает нужные операции RBD и возможность blocklist. Blocklist запрещает OSD обслуживать прежнего клиента по новой карте.

В ceph1 с административной c и новым защищённым каталогом credentials-01 создайте отдельный ключ только если entity отсутствует. Сначала c auth get client.rbdstudy должен подтвердить именно отсутствие, а не сетевую ошибку. Keyring — файл секрета, его нельзя коммитить в книгу.

umask 077
set -o noclobber
mkdir -m 0700 "$HOME/ceph-study/credentials-01"
cd "$HOME/ceph-study/credentials-01"
c auth get-or-create client.rbdstudy \
 mon 'profile rbd' mgr 'profile rbd pool=rbdstudy' \
 osd 'profile rbd pool=rbdstudy' > ceph.client.rbdstudy.keyring

Get-or-create не гарантирует обновления неверных старых прав, поэтому проверка отсутствия до него существенна. После создания сравните c auth get с ожидаемым ограничением pool=rbdstudy; полный вывод содержит секрет, его не включают в диагностику для публикации. Отрицательная проверка этим клиентом к чужому пулу должна дать отказ. Разрешения на сеть и файлы клиентской машины проверяются отдельно.

Передача exclusive-lock

В image с feature exclusive-lock один librbd-клиент получает право изменять его служебное состояние. При запросе другого клиента текущий владелец штатно прекращает новые записи, сбрасывает кэш и отдаёт lock. По умолчанию это кооперативная передача: два приложения способны поочерёдно писать в один image. Lock не делает ext4 распределённой файловой системой и не согласует файловые кэши двух машин.

Если старый клиент исчез без освобождения lock, новый должен избежать ситуации, когда старый оживёт и продолжит запись. Monitor публикует blocklist в OSDMap; после распространения необходимого состояния новый клиент может сломать старый lock и получить свой. Одно наблюдение, что TCP не отвечает, недостаточно для исключения прежнего писателя. Не удаляйте lock вручную без установленного fencing — запрета доступа прежнего участника к общему ресурсу.

Почему kernel map отложен

Userspace rbd из закреплённого образа использует librbd этого выпуска. Krbd — драйвер блочного устройства ядра Linux — принадлежит ядру клиентского узла. Перед map проверяются точное ядро и backports, CephX aes256k, image features, CRUSH tunables и совместимость файловой системы. Снижение защиты ключей ради старого клиента не является этапом этой лаборатории.

Только после отдельного принятия клиента можно показывать /dev/rbdN или /dev/nbdN приложению. Имя устройства не фиксировано и не является разрешением выполнить mkfs. Первые главы намеренно обходятся import/export без kernel map, mount и форматирования дисков основной ОС.

CSI: кто владеет каким состоянием

CSI — интерфейс взаимодействия оркестратора контейнеров с драйвером хранилища. В Kubernetes controller-часть Ceph CSI создаёт image по запросу тома; node-часть на выбранном узле подключает его и передаёт контейнеру. Состояние Kubernetes PV/PVC, image RBD, CephX credentials и mount узла принадлежат разным системам. Удаление Pod не обязано удалять image; это зависит от владельца тома и reclaim policy.

Этот том не поставляет произвольный CSI manifest с admin keyring. Для реального подключения нужны принятые версии Kubernetes и Ceph CSI, отдельный pool, ограниченные credentials и правила удаления. Проверка включает создание файла приложением, пересоздание Pod на другом узле, чтение checksum и проверку, что прежний узел более не пишет. Доступность PG сама по себе не доказывает корректный mount в Pod.

Задание: старый клиент вернулся после network partition, а новый успешно подключил тот же image. Какая проверка нужна? Установить, что прежний клиент действительно лишён доступа на уровне OSD/карты, а не только что новый процесс получил локальное имя устройства.
