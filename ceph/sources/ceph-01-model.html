Кто хранит байты и кто согласует карту

До первой команды состояния определим участников, объекты и путь одной записи. Названия процессов после этого будут обозначать конкретные обязанности.

Узел, кластер и служба

Узел, по-английски node, — машина, на которой работают процессы Ceph. В нашем стенде узлом будет Linux VM. Кластер — согласованная совокупность таких участников с общей идентичностью и правилами хранения. Долгоживущий обслуживающий процесс называют daemon, или демоном. На одном узле могут работать несколько демонов, поэтому число узлов и число процессов различаются.

Кластер получает FSID — уникальный идентификатор его экземпляра. Два кластера с похожими именами узлов и одинаковыми номерами OSD не становятся одним кластером. FSID нужен в том числе для различения их каталогов и служб на машине.

Что именно сохраняется

Внутренний объект хранения — именованная порция двоичных данных с относящимися к ней метаданными. Метаданные описывают данные, например их свойства или сведения об изменениях. Pool, или пул, — логическая область объектов с выбранной политикой размещения и защиты. Контекст обращения включает пул и пространство имён: одно человеческое имя объекта само по себе ещё не задаёт единственный адрес во всём кластере.

RADOS расшифровывается как Reliable Autonomic Distributed Object Store. В книге это название основания Ceph, которое хранит такие объекты, размещает их части или копии и обслуживает операции над ними. Объект S3, файл CephFS и RADOS object относятся к разным уровням: одному большому S3-объекту могут соответствовать несколько внутренних объектов RADOS.

Роли процессов

РольОтветственностьЧего из неё не следует
OSD — Object Storage Daemon Обслуживает операции над размещёнными данными и участвует в их защите; в нашем профиле один OSD использует один отдельный диск. Живой процесс ещё не означает, что каждая его PG готова.
MON — Monitor Участвует в согласовании управляющего состояния и карт. MON не пересылает каждую запись приложения на диски.
MGR — Manager Собирает эксплуатационные сведения и исполняет модули, в том числе управление размещением служб. Доступный MGR не доказывает доступность всех объектов.
MDS — Metadata Server Управляет файловыми метаданными CephFS. Обычные данные файлов не обязаны проходить через MDS.
RGW — RADOS Gateway Принимает объектные API-запросы, включая поддерживаемые операции S3, и переводит их в работу с RADOS. Наличие S3 API не обещает все возможности AWS S3.

Группа размещения и версия карты

PG, Placement Group, — группа размещения: промежуточная единица, с которой Ceph связывает множество объектов одного пула. Вместо отдельного согласования назначения каждого объекта система управляет группами. Объект вычислительно относится к PG, а выбранная PG — к набору OSD. Создание PG и изменение их количества выполняются кластером по настройкам пула; это не каталог, который создаёт пользователь командой mkdir.

Карта содержит сведения, необходимые участникам для работы: например, известные OSD, их состояние и параметры пулов. Epoch — возрастающий номер версии определённой карты. У OSD map и MON map свои последовательности версий. Номер epoch не является номером пользовательской записи или общим временем всех событий.

Одна запись до ответа

Клиент с разрешённым доступом получает у MON необходимые карты. Для обращения к RADOS он определяет PG и её обслуживающий OSD. Primary — OSD, который координирует работу данной PG и принимает инициированные клиентом записи. В реплицируемом пуле primary передаёт запись остальным участвующим OSD. У каждого из них есть собственный путь сохранения на носитель.

После предусмотренного протоколом устойчивого сохранения primary может подтвердить операцию клиенту. При обычной репликации нельзя переводить min_size как «достаточно любых двух ответов из трёх»: это ограничение допуска работы PG, а подтверждение записи связано с её действующим составом и протоколом. Переходы при отказе разберём отдельно.

У приложения через RGW первый адрес другой: оно отправляет HTTPS-запрос шлюзу. Уже RGW становится клиентом RADOS. У CephFS файловые метаданные обслуживает MDS, а передача данных файла использует OSD. Поэтому схема «всё идёт через MON» не описывает ни один из этих путей.

Почему большинство MON не равно доступности данных

Кворум — достаточное для согласования большинство участников. У трёх MON большинство составляют два. Но эти два процесса могут быть живы в ситуации, когда необходимые данные PG остались на недоступных OSD. Тогда управление картой продолжается, а конкретный запрос данных обслужить нельзя. Доступность нужно проверять для требуемой PG и интерфейса.

Первоисточники: архитектура, PG, primary, acting и подтверждение, MON. Учебный проект и примеры отказов придуманы для книги.

Почему локальный диск не решает распределённую задачу

Один диск отвечает одному компьютеру. Если два клиента должны видеть одни данные после гибели этого компьютера, байты приходится хранить в нескольких местах и согласовывать изменения. Дополнительные копии помогают пережить предусмотренный отказ, но требуют сети, свободной ёмкости, времени восстановления и решения, какой состав вправе отвечать. Копия по сети с ошибкой приложения остаётся копией той же ошибки.

Клиент — программа, обращающаяся к сервису хранения; в RADOS это может быть библиотека приложения, в S3 — HTTP-программа, а RGW становится клиентом RADOS. Серверная роль и клиентская ОС не совпадают: HTTP-клиент Windows может работать с RGW без native Ceph driver Windows. Реализации протоколов и их совместимость проверяются отдельно.

Локальный и сетевой путь имеют разные состояния

IP-адрес определяет сетевой узел, TCP-порт — принимающий процесс на этом адресе. Listener — сокет, который ждёт входящее соединение. Доступный порт не доказывает, что PG принята для IO. Systemd — диспетчер служб гостевой Linux ОС; Podman создаёт контейнерные процессы с выбранным образом. Контейнер использует ядро гостевой ОС и не создаёт ей дополнительную RAM или иной физический диск.

В Ceph public network называется клиентская сторона сети. Слово public не требует доступа из Интернета. На ней клиент обращается к MON и OSD. Отдельная cluster network может переносить меж-OSD работу; в малом стенде используется одна закрытая сеть. Потеря связи, отказ процесса и уничтожение носителя различаются: сохранившийся диск может вернуться, но изолированный процесс не знает всех новых карт.

Что означает устойчивость

Подтверждённая запись должна переживать предусмотренные отказы при выполненных условиях протокола и устройств. Успех write в кэш процесса или энергозависимый кэш диска не доказывает этого сам по себе. Flush требует передать данные до нужной устойчивой границы. В VM результат зависит также от гипервизора и физического backend. Поэтому контрольное чтение сразу после записи и восстановление после сбоя — разные упражнения.

Время операции включает обработку клиента, сеть, очередь, координацию PG и локальные устройства участников. При size=3 primary организует три локальных транзакции; быстрая одна копия не отменяет ожидание требуемых остальных. Задержка не равна размеру объекта, делённому на пропускную способность: для малых запросов очередь и служебные переходы могут преобладать.

Два независимых решения о доступности

Кворум MON выбирает согласованное управляющее состояние. PG устанавливает свою историю и готовность данных. На трёх MON два образуют большинство, но одна нужная PG может оставаться unavailable. И наоборот, потеря одного MON в здоровом трёх-MON составе не означает исчезновения всех data copies. Проверять следует нужный запрос, карту и конкретную PG.

Перед установкой попробуйте объяснить потерю одного узла в дереве из четырёх host по одному OSD. У кластера останутся три физических носителя, но число доступных копий каждой PG зависит от её состава, карты, истории и допуска IO. Формула «живых дисков ≥ min_size» этого решения не описывает; расчёт одной PG разобран в главах 05–06.
