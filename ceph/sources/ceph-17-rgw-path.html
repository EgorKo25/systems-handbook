Что происходит между PUT и видимым объектом

RGW переводит S3-запрос в несколько связанных структур RADOS. Протокол S3 и внутренний объект Ceph здесь разделены явно.

Входной адрес и удостоверение

Endpoint — адрес конкретного объектного сервиса. Для нашего проекта будет выбран собственный HTTPS endpoint RGW, отдельный от AWS и MinIO. Клиент подписывает запрос SigV4 с выбранными адресацией, region и учётными данными. Подробный расчёт подписи относится к S3-тому; здесь исследуется, что делает именно RGW после приёма запроса.

S3 user RGW имеет access key и secret key. Сам демон RGW обращается к Ceph с собственным CephX-удостоверением. Передача client.admin в Go-программу не является способом настроить S3-доступ.

Три вида состояния

RGW хранит служебные metadata, индекс bucket и полезные данные. Bucket — именованная область S3-объектов, key — имя объекта в этой области. Индекс помогает обслуживать перечисление. Его части, index shards, являются внутренними объектами с упорядоченными записями, а не отдельными S3 buckets.

Один S3-объект может состоять из head и tail objects RADOS. Head содержит описание размещения и другие свойства; tails несут дополнительные части содержимого. Manifest связывает это внутреннее представление. Приложение получает S3-объект, а не право изменять эти структуры вручную через rados.

Видимость записи и индекс

Для обычного индексируемого bucket запись данных и запись индекса относятся к разным RADOS objects. RGW согласует их через подготовку индексной операции, запись или удаление head и завершение индексной операции. Head записывается последним в представлении объекта и служит точкой его атомарной видимости.

Незавершённая запись индекса не означает, что LIST обязан возвращать случайное старое состояние. При перечислении pending entries проверяются по head. Документация RGW определяет read-after-write consistency после успешного ответа, включая последующие GET, HEAD и ListObjectsV2. Это утверждение относится к предусмотренному локальному пути RGW; его нельзя переносить на чтение из отстающей другой зоны multisite.

Проверить именно выбранную реализацию

RGW поддерживает базовую модель S3, но таблица возможностей содержит различия: например, bucket replication ограничена зонами, а набор canned ACL отличается. Для опыта фиксируют Ceph 20.2.4, конфигурацию bucket, наличие versioning и конкретные запросы. Совместимый SDK не превращает сервер в AWS S3.

В 20.2.4 усилена проверка signed headers SigV4. Общий object-study client должен подписывать необходимые host и x-amz- заголовки. Параметр ослабления проверки в новом стенде не включается. Ошибка подписи расследуется по endpoint, адресации, времени и подписанным данным.

Первоисточники: layout, read-after-write и index transaction, границы S3 API, S3 users, SigV4 в 20.2.4.

Операция индекса не равна транзакции всех объектов

Для обычного indexed bucket RGW хранит запись индекса в OMAP объекта bucket-index shard. OMAP — упорядоченная карта служебных ключей и значений внутри RADOS object. Подготовка index transaction ставит pending-состояние для имени и tag операции. Затем записывается head с manifest данных; после успеха complete обновляет индекс. Одна операция RADOS не может атомарно изменить независимые head и index objects, поэтому требуются эти фазы и согласование listing.

Если RGW умер после head, но до complete, другой RGW при LIST проверяет pending entry по состоянию head и посылает dir suggest — предложение уточнить индекс. Это механизм завершения согласованной видимости, а не повод вручную переписать OMAP. После успешного локального PUT документация RGW требует read-after-write для последующих GET/HEAD/LIST: результат не должен возвращать предшествующее записанному состояние, хотя конкурентный более поздний write/delete может уже изменить ответ.

Версия S3 и внутренняя версия PG

В bucket с versioning каждая версия имеет собственный head, имя которого связано с key и version ID. Дополнительный object logical head, OLH, указывает текущее состояние имени. Index содержит записи версий и журнал изменений OLH, по которому его представление сводится с индексом. Version ID — идентификатор API-состояния, а не eversion вида 100'41 из журнала PG. Три RADOS replicas одной версии API не являются тремя версиями S3.

Delete marker в versioned bucket меняет текущее видимое состояние, не обязан стирать все старые версии. Чтобы проверить восстановление, нужны выбранные version IDs и чтение именно нужной версии. Нельзя считать ETag универсальной SHA-256 содержимого: multipart, шифрование и серверные варианты меняют его смысл.

Масштабирование индекса и цена малых объектов

Shard — часть bucket index, выбираемая по хешу имени. Больше shards распределяет изменения по нескольким RADOS objects, но listing требует собрать результаты, а resharding переносит индексное состояние. Число shards не задаёт напрямую число OSD или PG. Миллион объектов по 1 KiB даёт около 0.954 GiB payload, но служебные записи, head, index и минимум размещения могут занимать существенную дополнительную ёмкость. Коэффициент без измеренного layout и счётчиков здесь не придумывается.

Задание: PUT получил timeout, затем LIST показывает имя. Это доказывает наличие текущей записи, но не доказывает, что она создана именно нашей попыткой. Для принятия нужны длина, ожидаемый checksum, operation ID и при наличии version ID чтение выбранного состояния. Успешный LIST сам по себе не является backup.
