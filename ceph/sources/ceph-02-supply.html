Получение пакета и закрепление контейнера

Выпуск, пакет управления и образ демонов проверяются раздельно. До запуска служб у нас должны появиться сохранённые входы, результаты проверок и одна неизменяемая ссылка на контейнер.

Что устанавливается на узел

Cephadm управляет systemd — диспетчером служб Linux — и программой запуска контейнеров; здесь выбран Podman. Пакет cephadm устанавливается в гостевую ОС. Демоны Ceph запускаются из контейнера. Версия cephadm и версия программы в образе могут различаться, поэтому проверяются обе. Копирование одного cephadm.py из дерева исходников не создаёт автономный cephadm: этот файл импортирует другие модули выбранного дерева.

Том закрепляет Ceph Tentacle v20.2.4. Выпуск опубликован 19 августа 2026 года. Номер выбран для разбора исходников и упражнений; он не объявляется вечной рекомендацией или новейшим выпуском. Перед реальным развёртыванием администратор повторно оценивает исправления безопасности и поддержку ветки. Плавающая страница releases может перенаправлять в development-документацию; она не заменяет tag и release notes выбранного point release.

В 20.2.4 появился тип CephX-ключа aes256k. CephX — аутентификация клиентов и демонов с собственными ключами и билетами MON. Клиент ядра и программа из контейнера имеют разные реализации CephX. Выпуск ядра без нужного перенесённого в старую ветку исправления (backport) может не принять новый ключ: первые опыты используют userspace-программы из закреплённого контейнера. Указанный в общей таблице минимум ядра RBD не подтверждает совместимость с aes256k.

Подпись, хеш и источник доверия

Криптографическая подпись InRelease связывает метаданные репозитория с release key. Gpgv проверяет эту подпись. SHA-256 локальных файлов — контрольное значение их байтов; оно обнаруживает последующее изменение относительно сохранённого значения, но само по себе не удостоверяет издателя. APT проверяет подписанные метаданные и хеши получаемых пакетов через signed-by. Не отключайте проверку TLS или подписи, если получение завершилось отказом.

Для начального доверия выбран полный fingerprint release key: 08B73419AC32B4E966C1A330E84AC2C0460F3994. Сверьте его с первоисточником через независимо доверенный путь. Скрипт new-supply.sh проверяет весь listing ключей: ровно один primary key с этим fingerprint; его subkeys допустимы. Второй primary key отвергается, поскольку gpgv доверял бы и ему в том же keyring.

Tag quay.io/ceph/ceph:v20.2.4 — имя версии образа. Digest quay.io/ceph/ceph@sha256:… закрепляет содержимое, выбранное при pull для архитектуры amd64. Реальное значение нельзя получить арифметикой или придумать в учебнике: Скрипт runtime-accept-once.sh извлекает его, повторно получает образ по digest и проверяет версию исполняемой программы Ceph внутри образа. Этот способ закрепляет полученные через официальный registry и TLS байты; он не является проверкой publisher attestation образа.

Для каждого прохождения создаётся новый собственный каталог поколения. Файл результата, или квитанция, содержит статус завершённых проверок. Он создаётся последним; его отсутствие означает незавершённый этап, а не разрешение повторить изменяющую команду. Имена -01 не увеличиваются автоматически. Существующий каталог, symlink или чужой owner останавливает скрипт первоначального создания. Частичные входы сохраняют для расследования; данные не удаляют ради повторного запуска.

Работа с поставленным исходником

На отдельной учебной VM от student, имеющего sudo, исходники labs должны находиться в новом собственном каталоге ~/ceph-book/labs. Это копия файлов книги, не состояние кластера. Перед запуском прочтите new-supply.sh и runtime-accept-once.sh. Первый не публикует системные APT files; второй использует только два выбранных пути: /usr/share/keyrings/ceph-study-20.2.4.gpg и /etc/apt/sources.list.d/ceph-study-20.2.4.list. Уже существующее назначение допускается только при равенстве байтов.

В этой главе команды первоначального создания не запускаются. Единственное место их первого выполнения — следующая глава, после подготовки VM, пакетов и времени. Здесь рассматриваются их входы и проверки. Вернувшись к уже принятому стенду, используйте повторный вход, а не повторяйте первоначальное создание каталогов.

Эти скрипты не выводят заранее известный digest. Успех каждой стадии проверяется по её receipt и manifests; проверка этих рецептов на реальных программах ещё требуется. APT version может содержать epoch и packaging revision: проверяется версия самого Ceph 20.2.4 перед дистрибутивной частью и точная установленная строка версии. Наличие репозитория Jammy не доказывает, что конкретная VM успешно проверила подпись или получила пакет. Offline-комплект требует ещё самих пакетов с зависимостями, образа и испытания без сети; одна книга его не заменяет.

Повторный вход не вызывает curl, apt install, pull, keygen или bootstrap. Он проверяет сохранённые manifests и текущую установленную версию cephadm. При несовпадении расследуйте изменение; не выполняйте автоматический downgrade.

Как прочитать результат проверки после следующей главы

После завершения соответствующего этапа главы 03 в supply-20.2.4-01 команда gpgv записывает диагностику в signature-check.txt. В условном успешном выводе строка Good signature from указывает на подпись переданным ключом; конкретное имя пользователя ключа и язык сообщения могут отличаться. Доверие начинается с проверенного fingerprint, а не с текста имени. Ненулевой код gpgv останавливает скрипт, и SIGNATURE-ACCEPTED.txt не создаётся. Само наличие InRelease не означает успешную проверку.

cd "$HOME/ceph-study/supply-20.2.4-01"
sha256sum --check SHA256SUMS.signature
gpgv --keyring "$PWD/ceph-release.gpg" InRelease

Условный вывод sha256sum содержит release.asc: OK, ceph-release.gpg: OK и InRelease: OK. Каждая строка относится к байтам своего файла. FAILED или отсутствие файла дают ненулевой код: сохранённые входы уже не совпадают с контрольными значениями. Это не проверка подписи; поэтому после неё отдельно вызван gpgv. Эти строки показывают ожидаемый формат, а не результат выполненного здесь получения.

Упражнение: где оборвался этап

Имеются InRelease и SHA256SUMS.signature, но нет SIGNATURE-ACCEPTED.txt. Можно ли публиковать keyring? Нет: файл контрольных значений не удостоверяет завершение проверки подписи. Если RUNTIME-ACCEPTED есть, но версия dpkg-query изменилась, reentry тоже должен остановиться. Это сохраняет связь выбранного инструмента с принятыми наблюдениями.
