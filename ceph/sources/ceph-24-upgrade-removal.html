Обновление и вывод узла без потери нужной истории

Обновление меняет программы и иногда форматы или ключи. Удаление узла меняет доступные копии. В обоих случаях сначала проверяют условия продолжения и заранее принимают путь восстановления.

Что закреплено в этой книге

Разбор относится к Tentacle 20.2.4. Новая версия не выбирается автоматически по latest tag. Для конкретного перехода администратор читает release notes обоих концов и поддерживаемый upgrade path, принимает новый image digest и совместимость cephadm/клиентов, сохраняет конфигурацию, версии и внешний backup. Скрипт первоначальной установки из главы 03 намеренно отказывает, если установлен другой cephadm; он не является скриптом upgrade.

В reentered Bash исходного кластера сохраните c versions, c status, c health detail, c orch ls, c orch ps, состав MON/MGR и состояния pools/PG. Учитываются все интерфейсы: MDS active ranks, RGW multisite, kernel clients и RBD features. Один healthy small pool не доказывает готовность остальных.

Порядок cephadm

Orchestrator обновляет службы в предусмотренном порядке, начиная с MGR и MON, затем остальные демоны. Он проверяет, допустимо ли вывести очередного участника. Для upgrade требуется standby MGR; один MGR малого стенда не образует такой профиль. Недоступный host может приостановить процесс. План изменения MDS также учитывает max_mds и возможное сокращение активных ranks: это влияет на доступную производительность metadata.

После отдельного принятия новой версии файл ~/ceph-study/upgrade-approved-01/image.txt должен содержать одну проверенную immutable reference. Это обязательный новый вход, которого ранняя лаборатория не создаёт. Не подставляйте старый digest 20.2.4 как будто это новый выпуск. Команды управления имеют вид:

target_image=$(cat "$HOME/ceph-study/upgrade-approved-01/image.txt")
c orch upgrade check --image "$target_image"
c orch upgrade start --image "$target_image"
c orch upgrade status

Start выполняют только после принятого check и отдельного окна работ. Pause приостанавливает дальнейшие действия, resume продолжает, stop прекращает текущий процесс управления. Они не откатывают уже обновлённые демоны или изменённые форматы. Универсальное обещание downgrade здесь не даётся.

CephX и клиентские ключи

20.2.4 ввёл aes256k и дополнительные health checks ротации. Cephadm автоматизирует предусмотренную ротацию daemon keys, но client keys требуют отдельного решения и проверки клиентов. Наличие CephX keyring не доказывает поддержку его типа старым kernel client. Сначала принимаются совместимые клиенты, затем выполняется выбранная процедура ротации с сохранением доступа и последующим отказом старых ключей.

В multisite обновление версий RGW имеет отдельные условия совместимости подписи; release notes могут требовать временной настройки именно для upgrade-перехода старой multisite-системы. Это не основание включать ослабление SigV4 в новом однозонном стенде. Каждый такой переход читается по конкретным release notes.

Вывести OSD и host

Перед выводом нужен достаточный запас ёмкости и допустимых failure domains. Out меняет размещение и запускает перенос затронутого содержимого. Удалять устройство можно после принятого завершения предусмотренного drain и проверки safe-to-destroy выбранного OSD, а не по отсутствию процесса в ps. Номер берут из фактического инвентаря и сверяют с диском.

На трёх hosts size=3 после вывода одного некуда вернуть третью копию. На четырёх hosts такая возможность существует, но PG ещё должны согласовать историю и закончить перенос. Только после проверки контрольных данных и удаления нужных служб рассматривается host removal. Zap и purge являются разрушительными действиями и в первом стенде не используются как средство «починить статус».

Приёмка после изменения

Проверьте распределение версий c versions, actual image каждого daemon, MON quorum, активный/standby MGR, PG и интерфейсные probes. Read-probe-02 читает прежний RADOS-объект без повторного PUT. Для RBD/CephFS/RGW используются прежние данные и свои credentials. Новое успешное создание пустого объекта не проверяет сохранность старых.
