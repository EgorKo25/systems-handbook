MinIO: кто принял объект и почему ему можно ответить

В личной VM запустим MinIO, отправим ему текстовый файл и прочитаем сохранённое содержимое клиентом mc. Затем остановим сервер, запустим его с прежним каталогом данных и снова сравним полученные байты с исходным файлом. По ходу разберём, что сохраняет сервер и какие сведения остаются только у клиента.

Зачем приложению отдельный сервер

Представим сервис, который принимает документы. В сетевом запросе приходят байты документа и несколько описательных полей. Сервис может записать их в собственный каталог, но тогда ему придётся самостоятельно решить, кто получает доступ, как искать документы по имени, что означает повторная загрузка и как другой экземпляр приложения прочитает тот же результат. Объектный сервер переносит эти обязанности за отдельный сетевой интерфейс.

Метаданные — сведения об объекте, например тип содержимого, размер и служебные параметры. Они описывают объект, но не заменяют его тело с пользовательскими байтами.

Объект — именованное содержимое вместе с метаданными. Содержимое называют body, то есть телом объекта. Bucket — область имён и правил, которую создаёт владелец доступа. Key — строковое имя внутри bucket. Например, у bucket handbook-minio может быть key project/manifest.txt. Косая черта помогает группировать имена по префиксу; она не обещает файловую систему с каталогами, блокировкой файлов и атомарным переименованием дерева.

Как клиент обращается к MinIO

HTTP — протокол обмена запросом и ответом. Клиент открывает соединение к адресу и порту endpoint, например https://127.0.0.1:19000. Схема https означает HTTP внутри TLS: сначала проверяется сертификат сервера и защищается соединение. Метод PUT просит записать тело, GET — прочитать его, HEAD — получить сведения без тела ответа, DELETE — изменить состояние удаления. URL path выбирает bucket/key при используемой здесь адресации с bucket в пути.

Заголовки — именованные поля сообщения. Content-Type описывает содержимое, Content-Length задаёт число bytes тела; пользовательские поля объекта передаются с префиксом x-amz-meta-. Авторизация S3 Signature Version 4 связывает выбранные метод, путь, заголовки и hash тела с credentials клиента. Сервер MinIO отдельно проверяет эту подпись и policy. TLS-доверие к серверу не даёт клиенту права записывать любой key.

Например, проекция нашего будущего PUT имеет метод PUT и путь /handbook-minio/project/manifest.txt, тип text/plain и Content-Length 35. Следом идут 35 bytes fixture с двумя LF. SDK или mc строят полный подписанный HTTP-запрос; эта проекция не является готовой командой с пропущенным secret. Ответ содержит HTTP status и служебные поля. Успешный PUT и полученные metadata затем проверяются отдельным GET и побайтовым сравнением.

Health endpoint /minio/health/cluster — другой запрос того же сервера: он помогает проверить готовность выбранного серверного пути, но не читает наш объект. Если ответ потерян по timeout, клиенту неизвестно, успел ли сервер закрепить PUT. Эту неоднозначность позже рассматриваем вместе с версиями, не выводим отсутствие объекта из отсутствия ответа.

MinIO Server — процесс, который принимает поддерживаемые S3-запросы и управляет собственным форматом хранения. mc — отдельная клиентская программа: она отправляет запросы серверу и может работать также с локальными файлами. Go SDK — библиотека, которую разработчик включает в приложение. SDK не заменяет процесс хранения. Если приложение завершилось, долговечность объекта определяется сервером и его хранилищем, а не существованием Go-структуры в памяти.

Две линии, которые нельзя смешивать

Официальные источники проверены повторно 2 ноября 2026 года. Исходный MinIO OSS под AGPLv3 больше не сопровождается. Репозиторий Server архивирован 25 апреля 2026 года, репозиторий mc — 14 июля. Сохранённый исходный код можно изучать и собирать на условиях его лицензии, но наличие исходников не означает наличие будущего исправления уязвимости.

В этом томе основной воспроизводимый учебный маршрут закреплён за архивными исходниками Server RELEASE.2025-10-15T17-29-55Z и mc RELEASE.2025-08-13T08-35-41Z. Это исследовательский стенд для собственных данных в личной VM. Современная AIStor рассматривается отдельно: у неё другая лицензия, способ получения и границы тарифов. Нельзя добавить переменную окружения и считать архивный OSS-сервер поддерживаемой AIStor-поставкой.

AIStor Free допускает одиночный узел. Некоторые действия дальнейшего эксплуатационного маршрута требуют платного издания: в частности, replication, server-side encryption и удаление конкретной версии. Поэтому рядом с такими действиями будет указана применимая линия реализации и требуемая лицензия.

В расчётах KiB = 1024 байта, MiB = 1024², GiB = 1024³; MB и GB при десятичном обозначении равны 10⁶ и 10⁹ байт. Время запроса измеряется от начала действия клиента до принятого результата, а не только работой диска.

Один проект между упражнениями

Рабочее состояние располагается в $HOME/minio-study. Сначала получим исходники и соберём две программы. Затем создадим собственное доверие TLS, запустим сервер на loopback, установим клиентский доступ и сохраним первый объект. Дальше у того же проекта появятся версии, отдельный прикладной доступ, преднамеренные ошибки и восстановление на другую цель. Каждая глава продолжает предыдущее состояние. Команды автоматического reset здесь нет.

Математика erasure coding объясняется на явно заданных наборах дисков. Начальный сервер использует одну область хранения и не имеет избыточности. Его успешный GET не будет выдаваться за испытание кластера, а несколько каталогов одного SSD — за несколько независимых дисков.

Модель HTTP, подписи SigV4 и базовые состояния объектов подробно разобраны в томе S3. Здесь мы прослеживаем конкретный сервер: как он выбирает erasure set, записывает shards и metadata, проверяет quorum и возвращает ответ.

Как продолжать после первого объекта

После настройки сначала отделим прикладной доступ и историю версий, затем проследим запись и чтение конкретной реализации: object IO. Номер 08 не задаёт порядок чтения: этот механизм предшествует healing/scanner. Далее изучим изменение pools, операционные отказы, восстановление отдельной копии и стоимость ресурсов. Самостоятельный опыт заканчивается чтением восстановленных bytes и выбранных версий, не наличием запущенного процесса.
