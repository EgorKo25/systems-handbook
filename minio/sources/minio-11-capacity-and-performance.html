Сколько байтов и времени требует выбранная защита

Разложим ёмкость и стоимость запросов на тело, кодированные shards, checksums, metadata и сохранённые версии. Затем выберем измеряемые величины, чтобы отделить подтверждённую полезную работу от фоновых IO и неудачных попыток.

Сначала объект, затем сумма дисков

Полезный объём — bytes приложения, а raw capacity — доступные устройствам bytes. Для одной большой обычной версии с N=K+P идеальная доля K/N. У четырёх одинаковых дисков по 100 GiB и K=2,P=2 сумма raw равна 400 GiB, идеальный payload — 200 GiB. Это потолок простой арифметики, не обещание сервера: служебные данные, резерв свободного места, разные размеры дисков и неравномерное заполнение уменьшают принимаемый объём.

Минимально необходимое свободное место проверяется для подходящих дисков/sets, не только по общей сумме. Более крупный диск рядом с меньшим не превращает каждую stripe в независимый произвольный набор bytes. Если планировщик направляет key в заполненный set, пустые диски другого set не являются его parity. Заполненный filesystem также влияет на создание временных файлов и metadata; аварийный запас нужен до достижения 100%.

Для планирования отдельно выбирают рабочий резерв. Например, если от идеальных 200 GiB оставить 25% под рост и операции, бюджет текущего payload равен 150 GiB. Число 25% — условие этого расчёта, не утверждение о константе MinIO. Сами server reserve checks следует смотреть по закреплённой версии, выбранному filesystem и ошибке операции.

Округление и hash bytes

Внешний shard stream обычного одного part можно оценить по размеру erasure block B: q=floor(S/B), r=S mod B, payload одного shard = q×ceil(B/K)+ceil(r/K). При r=0 последнее слагаемое равно 0. Число ненулевых chunks c=q+[r>0]. Для выбранной в healing-главе streaming bitrot модели hash длиной h=32 B добавляется к каждому chunk, поэтому полный поток одного endpoint равен payload+c×h. Сумма N таких потоков ещё не включает xl.meta и filesystem overhead.

При N=4,K=2,P=2,B=1 MiB,S=4 MiB: один shard payload = 2 MiB, четыре hashes занимают 128 B, stream = 2097280 B; все четыре — 8389120 B. Это логическое содержимое streams, не измеренные device writes. Контроллер, filesystem, журнал, sector alignment, кэш и повторные записи могут добавить другие IO.

При N=8,K=4,B=1 MiB размер S=1 MiB даёт 2097152 B payload и 256 B hashes, всего 2097408 B. Увеличение тела до 1 MiB+1 B создаёт второй chunk: payload становится 2097160 B, hashes — 512 B, всего 2097672 B. Рост на один байт приложения добавил 264 B streams в этой модели. Для малых inline objects применяется другой путь: нельзя механически прибавлять внешние hash streams к любому байту маленького объекта.

Версии, multipart, lifecycle и внешний tier

Включённое versioning сохраняет несколько тел одного key. Если три большие версии имеют одинаковый размер S и одинаковый layout, грубый payload budget становится 3×S×N/K до их отдельной metadata. Delete marker обычно не содержит такого тела, но остаётся записью истории. Удаление current key не освобождает автоматически все старые версии. Незавершённые multipart uploads и временные данные также расходуют место, пока не завершены или не очищены подходящим серверным путём.

Lifecycle — сохранённые правила обработки объектов по времени и состоянию. Их выполнение происходит позже обходом, не в момент записи policy. Планируя reclaim, наблюдают действительное исчезновение выбранных версий и освобождение места. Tiering переносит тело во внешний storage, оставляя локальные сведения для доступа; local used bytes уменьшаются, но общая стоимость включает внешний объект, запросы, сеть и доступные credentials. В начальном стенде правила lifecycle, tier и KMS не настраиваются.

Почему одинаковый Content-Length даёт разную нагрузку

Последовательный PUT большого тела платит за чтение клиента, TLS/подпись, hash, кодирование, запись нескольких streams и metadata. Много маленьких объектов добавляют больше lookup, объектов metadata и отдельных завершений на те же полезные bytes. GET здорового объекта читает выбранные data shards; degraded GET может читать другие пригодные shards, проверять hashes и декодировать. Range-запрос возвращает меньше тела, но границы blocks/checksums могут заставить прочитать больше bytes, чем отдано клиенту.

Условный сетевой пример: coordinator находится на одном из четырёх узлов N=4,K=2; один shard локален, три удалены. Для записи большой версии S каждый удалённый shard несёт примерно S/2 payload, суммарный исходящий shard payload coordinator — 1.5S. Если единственный ограничивающий интерфейс имеет номинальные 1 Gbit/s = 125000000 B/s, то только эта составляющая даёт предел логического потока 125000000/1.5 ≈ 83333333 B/s. Это расчёт верхней границы до протокольных расходов, TLS, metadata, исходного клиентского трафика и диска; он не является результатом benchmark и не обещает такую скорость.

Если все endpoints — пути одного SSD, сетевой межузловой трафик исчезает, но все shards конкурируют на одном устройстве и исчезнут вместе при его отказе. Если исходный поток клиента тоже проходит через тот же интерфейс, надо считать оба направления и фактический duplex. При healing место источников и target определяет, какие bytes действительно пересекут сеть. Пример 07 отдельно считает source reads, target writes и сеть для своей конкретной топологии.

Конкуренция, память и очередь

Concurrency — число одновременно выполняемых запросов. Увеличение его скрывает отдельные задержки и может поднять throughput до насыщения CPU, сети или диска. После насыщения растёт очередь, время ожидания и число deadline failures. Модель L=λW связывает среднее число задач в устойчивой системе L, средний завершённый поток λ задач/с и среднее время W секунд; она не вычисляет p99 и неприменима как обещание для растущей без границ очереди.

Буферы — только часть памяти. Если бы каждый из 32 запросов одновременно держал все N shard chunks одного B=1 MiB,K=2,N=4 блока, эти буферы заняли бы 32×4×512 KiB=64 MiB. Это явно заданная учебная схема владения буферами, не измеренный MinIO RSS. Реальная программа использует pools, goroutines, metadata, Go heap/GC, TLS и другие выделения. RSS процесса отличается от heap, а page cache и память гостевой VM учитываются отдельно.

Поэтому профиль 8–16 GiB хоста начинается с одного небольшого потока и последовательной сборки. RAM не создаёт независимых дисков. Нельзя назначать одновременно весь ресурс нескольким тяжёлым службам или обещать многоузловой HA-тест только по сумме гигабайт. Увеличивают один параметр за опыт, сохраняя выбранный объект и исходное серверное состояние.

В throughput входят только подтверждённые полезные bytes / длительность всего выбранного окна. Ошибки и unknown PUT учитывают отдельно. Нельзя добавлять bytes неподтверждённой попытки и ещё раз её успешного повтора как два полезных объекта. GET принят лишь после полного чтения и проверки bytes; один HTTP 200 с оборванным Body не является завершённым чтением.

Записывайте индивидуальные end-to-end длительности завершённых запросов и отдельно причины отказа. Среднее, p50, p95 и p99 отвечают на разные вопросы. Percentile вычисляется по выбранному распределению и определению; его нельзя восстановить из среднего или усреднить между узлами. Например, у узла A два наблюдения 1 и 100 ms, у B — 98 наблюдений по 2 ms. По nearest-rank p99 A=100 ms, B=2 ms, а объединённый p99=2 ms, не 51 ms. Это синтетический набор, не задержки MinIO.

Контролируемое сравнение без выдуманного результата

Для своего личного стенда сначала примите первый объект и выберите фиксированный fixture. Измерьте последовательный PUT/GET с собственными новыми ключами, отдельно учитывая появляющиеся версии и цену cleanup. Затем измените только concurrency. Для опыта scanner/healing на отдельном принятом erasure-стенде сохраните тот же размер, TLS/checksum/retry/cache режим; сравните foreground latency и суммарные IO до и во время фоновой работы. Нельзя запускать repair на единственном резерве ради графика.

Серверные counters помогают объяснить итог, но их граница может отличаться от клиентской: shards и hashes не равны S3 bytes. Проверяйте units метрики, labels, histogram buckets, сброс counter при restart и стоимость scrape. Логи и admin info дают причины ошибок, но не заменяют распределение времён клиента. Публикуйте профиль и реальные сырые измерения после собственного опыта, не заранее выбранные MiB/s или p99.

Вычисляемые упражнения

В каталоге minio/ копии книги выполните только чистую модель: она не читает runtime и не обращается к сети.

python3 -B labs/capacity_model.py
python3 -B labs/healing_scanner_model.py

Первый script проверяет округление +1 B, hash overhead, интервальный выбор 20/60 и синтетические quantiles. Второй сохраняет принятый пример healing с отдельными source/target IO. Ожидается PASS assertions; это не Reed–Solomon, HighwayHash, scanner или benchmark настоящего сервера. Измените S и K в собственной копии модели и предскажите, где появится новый chunk. Для N=8,K=4,B=1 MiB ответ +1 B разобран выше; у другого K ступень изменится.

Источники выбранного поколения: округление shards, stream checksums, buffer pools и space selection, метрики.
