Когда копии расходятся: bitrot, scanner и healing

При GET MinIO может исключить повреждённый shard и восстановить запрошенные байты из оставшихся исправных частей. Клиент получит содержимое, хотя повреждённая часть на диске ещё требует замены. Healing записывает восстановленные части на нужные endpoints. Сервер учитывает результат для каждой цели отдельно: успешная запись одной части не завершает восстановление другой, если там возникла ошибка.

Путь от HTTP body до публикации xl.meta и последующего GET разобран в главе записи и чтения. Здесь продолжим с обнаружением повреждения и записью восстановленных частей на выбранные endpoints.

Далее рассматривается архивный OSS Server commit 9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a. Имена функций, режимов и полей относятся к нему. Сохраняемый одноendpointный стенд предыдущих глав не превращается в распределённый кластер от чтения этой модели.

Какие байты нужно вернуть на диск

Возьмём одну сохранённую версию V с одним part 1 длиной S=4 194 304 байта, то есть 4 MiB. Part — часть версии, чей номер и размер записаны в metadata, служебных сведениях об объекте. Тело не сжато, не зашифровано и не перенесено во внешнее хранилище; кодированные данные лежат отдельными файлами, а не inline внутри xl.meta. Эти условия позволяют считать байты без дополнительных преобразований.

У версии один erasure set, группа совместно кодируемых endpoints: N=4, K=2 data shards и P=2 parity shards. Endpoint — адресуемая сервером область хранения. Shard — пронумерованный кодированный поток части. Parity вычисляется из data и позволяет восстановить недостающие фрагменты при достаточном числе пригодных источников. Здесь E1–E4 находятся на отдельных физических дисках узлов A–D; диск узла D называется D1. K обозначает число data shards, а D в имени узла остаётся именем узла.

В metadata V записан erasure block size B=1 048 576 байт. Block — порция входного part за один проход кодера. Она даёт четыре shard-фрагмента, вместе называемые stripe. Chunk здесь — один такой фрагмент в потоке конкретного shard. При K=2 полный block даёт chunk длиной 524 288 байт. Четыре blocks образуют по 2 097 152 байта shard payload на endpoint. Payload означает кодированные байты без hashes и metadata. Деление здесь точное, поэтому padding, дополнения нулевыми байтами, нет.

Зафиксируем distribution [1,2,3,4], перестановку номеров shards по endpoints: E1/E2 содержат data, E3/E4 — parity. Это явная предпосылка сцены, а не вычисленное размещение по имени key. При HighwayHash256S перед каждым chunk лежит 32-байтовый hash, контрольное значение его байтов. Один поток имеет вид hash0 | chunk0 | hash1 | chunk1 | hash2 | chunk2 | hash3 | chunk3. Его длина — 2 097 280 байт; сумма четырёх — 8 389 120 байт. Из них 8 MiB составляет shard payload и 512 байт — hashes. xl.meta, каталоги и выделенные filesystem блоки сюда не входят.

Источники: размеры shards, запись hash и chunk.

Почему размер файла не заменяет проверку содержимого

Bit rot здесь означает повреждение сохранённых байтов. Сервер ищет его проверкой целостности; отсутствие файла и изменение содержимого требуют разных проверок.

Normal scan для отдельного non-inline part вызывает CheckParts. Локальный checkPart смотрит путь, проверяет, что он не является каталогом, и выявляет размер меньше ожидаемого shard payload. Он не читает весь payload и не сравнивает hashes; файл прежней длины с изменённым байтом способен пройти этот этап. По этому результату нельзя утверждать, что проверено содержимое part.

Deep scan вызывает VerifyFile. Storage endpoint читает hash и следующий chunk, заново считает hash и сравнивает значения. При HighwayHash256S проверяется также ожидаемый размер потока с hashes. Несовпадение даёт errFileCorrupt. Reader обычного GET тоже проверяет прочитанные chunks; он не передаёт обнаруженные повреждённые байты декодеру как исправные. Проверенный диапазон не говорит о ещё не прочитанных chunks.

Inline данные уже получены вместе с metadata: в checkObjectWithAllParts их bitrotVerify выполняется и в normal режиме. Поэтому правило «normal никогда не проверяет байты» для этой реализации неверно. Delete marker, версия без тела, и remote-версия с данными во внешнем хранилище проходят другие ветви; приведённые далее расходы относятся к нашему локальному part.

Checksum отвечает на вопрос о совпадении сохранённых байтов и контрольного значения. Она не выбирает нужную историю: две разные версии могут иметь исправные, но разные тела. У HighwayHash здесь встроенный публично известный ключ из bitrot.go. Это обнаружение повреждения, а не аутентификация автора данных: знающий алгоритм может пересчитать hash. SigV4 проверяет подпись запроса, TLS защищает соединение, а приложение отдельно сравнивает принятое тело с ожидаемым.

Источники: checkPart и CheckParts, VerifyFile, inline и выбор режима, ключ и алгоритмы, bitrotVerify, reader chunks.

Откуда появляются задания scanner

Data scanner обходит namespace, пространство имён bucket/key, и собирает сведения об объёме и версиях. Он также исполняет выбранные проверки healing, lifecycle и replication. Lifecycle задаёт срок хранения или перенос версий; replication копирует их в другую цель. Эти действия объясняют, почему обход не является только чтением данных для поиска bitrot.

runDataScanner получает лидерскую блокировку, читает сохранённый номер цикла и вызывает NSScanner. Верхний слой запускает работу по sets всех pools и объединяет usage cache, дерево сохранённых счётчиков. Внутри set nsScanner раздаёт buckets через общую очередь работникам доступных дисков; новые buckets идут раньше уже известных. Конкретный bucket берёт один работник очереди. Это не требование прочитать его payload на каждом endpoint в каждом цикле.

На storage endpoint NSScanner ищет xl.meta или файл старого формата xl.json, читает metadata и превращает найденные версии в ObjectInfo, сведения о версии для объектного слоя, включая VersionID и размер. Далее applyActions рассматривает версии по отдельности. Для выбранной проверки applyHealing передаёт именно VersionID этой версии в HealObject. У удаляемой lifecycle-версии может оказаться другое действие вместо healing. В HealObject пустой versionID преобразуется в буквальную null-версию; это не обещание ремонта самой новой версии при любой форме вызова.

Cache позволяет не перечитывать каждую ветку целиком. У скомпактированной ветки хранятся суммарные счётчики потомков. Для известных таких веток применяется отбор по hash и номеру цикла с dataUsageUpdateDirCycles=16; пропущенная ветка переносит прежние totals. Для выбора healing используется другая часть того же hash: modAlt сравнивает её остаток с номером цикла, а healObjectSelectProb равен 1024. При предварительном отборе ветки делитель objectHealProbDiv согласует эти два шага.

Это детерминированный отбор по hash и циклу, а не независимый бросок монеты для каждого запроса. Если healing выключен для прохода через SkipHealing или диск уже помечен Healing, shouldHeal не разрешает обычную проверку. Отдельная ветвь abandonedChildren, ранее известных, но не найденных сейчас имён, проверяет другие диски и может поставить найденные версии в фоновую работу. Поэтому отсутствие имени на одном диске не читается сразу как доказательство удаления всего объекта.

Источники: цикл и его сохранение, работа по sets, очередь buckets и cache, metadata и версии, отбор веток, выбор item, mod и modAlt, ранее найденные имена, null и повтор deep.

Как выбирается normal или deep

Параметр heal:bitrotscan и переменная MINIO_HEAL_BITROTSCAN разбираются кодом закреплённого поколения. Значение off даёт BitrotScanCycle=-1, on — 0; запись вида 1m означает один 30-дневный месяц, а не одну минуту. Положительное число месяцев задаёт интервал. Это описание формата, а не команда изменения настроек стенда; default в исходниках — off.

getCycleScanMode возвращает normal при -1 и deep при 0. Для положительного интервала deep выбирается, пока разность currentCycle и BitrotStartCycle меньше 1024, либо когда прошедшее время превысило интервал. Иначе выбирается normal. При переходе в deep сохраняются BitrotStartTime, BitrotStartCycle и CurrentScanMode. Режим цикла и выбор объекта — два отдельных условия: deep не отменяет отбор items по hash.

При выбранном item applyHealing создаёт HealOpts со ScanMode и Remove=true. Это путь, способный менять storage. Даже DryRun не следует описывать как безусловно неизменяющее чтение: внутри healObject некоторые ветви deleteIfDangling находятся до проверки DryRun. Успешный цикл и обновлённый usage cache не доказывают чтение всех байтов всех версий. Числа 16 и 1024 не задают крайний срок полного scrub, проверки содержимого всего хранилища.

Источники: цикл, default и месяцы, getCycleScanMode, переход режима, HealOpts scanner, metadata и DryRun.

Как healing выбирает версию и источники

Перед дорогим чтением HealObject выполняет быстрый опрос metadata. В рабочем healObject сервер обычно берёт блокировку bucket/key и заново вызывает readAllFileInfo для выбранного VersionID. Вариант NoLock предназначен для вызывающего пути, который сам обеспечивает нужную блокировку. Данные опроса в RAM ещё не являются выбранным телом объекта. FileInfo — структура сведений об одной версии. Она содержит VersionID, DataDir — имя области её shard-данных, erasure-параметры и список Parts.

objectQuorumFromMeta получает K и P из доступных согласуемых metadata этой версии. Затем listOnlineDisks выбирает группу по общему ModTime, времени версии; предусмотрен запасной путь по ETag с общим VersionID. pickValidFileInfo вызывает findFileInfoInQuorum. Для нашего локального несжатого V эта функция группирует описание по XLV1, номерам и размерам parts, K/P и distribution после отбора по ModTime либо ETag. Index конкретного endpoint и его shard data при этом различаются. Более позднее время одного файла или один исправный hash не заменяют эти проверки.

Для V в нашей модели read quorum R=K=2; обычный PUT при K=P требовал W=3. Healing восстанавливает уже выбранную версию. Условие K пригодных shards проверяется для каждого нужного блока. Два ответа с разными версиями либо два неправильных номера shard не дают двух уравнений для V. Если metadata не позволяют выбрать версию или у part больше P непригодных участников, путь не может обычно восстановить тело. Код рассматривает и deleteIfDangling, обработку признанного невосстановимым остатка; для сохранения повреждённых файлов без изменений нужна отдельная копия: этот изменяющий storage путь сам по себе её не создаёт.

checkObjectWithAllParts сопоставляет metadata с выбранным описанием, проверяет распределение и получает результаты по каждому part каждого endpoint. В основном пути сравниваются ModTime и DataDir; в запасном пути — ETag. Далее normal/deep выбирает CheckParts или VerifyFile. Источники для данного part создаются только там, где его результат равен checkPartSuccess. Нормальная лёгкая проверка ещё не исключила скрытое повреждение: bitrot reader повторно проверит реально прочитанные chunks.

Источники: блокировка и metadata, pickValidFileInfo, R и W, VersionID перед запасным ETag, listOnlineDisks, проверка parts, невосстановимый остаток.

Как определяются цели

Функция shouldHealObjectOnDisk отвечает отдельно для каждого участника. Отсутствующее описание V, повреждённая metadata или описание, не совпавшее с выбранным FileInfo, делают доступный endpoint кандидатом на обновление. Недостающий либо corrupt part также требует записи. Здесь stale означает устаревшие или неподходящие сведения о рассматриваемой версии, а не просто «давно не трогавшийся файл». FileInfo.Equals учитывает время, erasure-параметры, признаки compression, encryption и transition.

Ошибка errDiskNotFound даёт состояние Offline и не создаёт пишущую цель: серверу некуда отправить новые данные. Если E4 вновь доступен, но V у него отсутствует, новая попытка может включить его как Missing. Если вернулся прежний диск с исправной V, эта копия проходит проверки и не требует автоматической перезаписи только из-за самого факта временного отключения.

В результате HealResultItem указываются Bucket, Object, VersionID, DiskCount, DataBlocks, ParityBlocks и списки Before.Drives / After.Drives. В каждом элементе важны Endpoint и State. Известные причины превращаются в DriveStateMissing, DriveStateCorrupt, DriveStateOffline или DriveStateOk; неизвестная ошибка сохраняет неизвестное состояние с причиной. Формат native CLI здесь не имитируется. Before и After относятся к этому вызову и выбранной версии, а не к проверке всех объектов диска.

Источники: shouldHealObjectOnDisk, FileInfo.Equals, состояния, списки целей и результатов.

Почему GET может закончиться раньше восстановления

В этой схеме явно принята distribution [1,2,3,4]: E1/E2 содержат data shards, E3/E4 — parity. Пусть E4 недоступен, а chunk на E3 не прошёл checksum. Исправные E1/E2 уже содержат оба data shards, поэтому GET может собрать тело без вычисления отсутствующих data shards. Запись parity на E3/E4 остаётся отдельной работой. В главе записи и чтения показан другой случай: GET получает data из одной пары parity shards.

Для этой сцены reader E3 действительно был вызван и обнаружил несовпадение. В другой последовательности успешный GET может ограничиться E1/E2 и вообще не прочитать E3. Если HTTP-клиент принял все байты V, это подтверждает результат данного чтения. Для записи на E3 требуется другой вызов, новое согласование metadata и завершение целевого IO.

В read path, когда запрошенная часть передана целиком, но decoder сообщил missing/corrupt source, код может добавить PartialOperation в MRF. Эта структура содержит Bucket, Object, VersionID, SetIndex, PoolIndex, Queued и BitrotScan. Последний признак выбирает deep для фонового вызова, если причиной был bitrot. GET при этом может завершиться успешно. Добавление задания не означает, что его цель уже восстановлена.

MRF имеет очередь на 100 000 элементов. addPartialOp не ждёт свободного места: при заполненной либо закрываемой очереди добавление может быть пропущено. В этом коде есть сохранение оставшейся очереди при штатном shutdown и загрузка list.bin при старте; это не durable-журнал каждого принятого задания. Обработка элемента очереди и последующие scanner/drive-heal дают разные возможности снова найти проблему. Из них не получается обещание срока или доставки каждого задания после любого аварийного завершения процесса.

Источники: GET и addPartialOp, поля и очередь, сохранение и загрузка, выбор режима MRF.

От источников до временных целевых байтов

Продолжим с доступным E4. Представим, что deep-проверка V нашла corrupt part на E3 и отсутствие V на E4. У E1/E2 metadata согласованы, все chunks выбранного part исправны; E4 уже доступен для записи в ожидаемой позиции set. Это две выбранные цели. Списки sources, targets и FileInfo переставляются по distribution, чтобы позиция в erasure-массиве обозначала номер shard.

Для каждой цели cleanFileInfo копирует согласованное описание V и очищает локальные Index, checksums и inline Data. Оригинальная копия metadata источника сохраняется отдельно, чтобы читать его прежние DataDir и checksum-параметры. Для обычного нового формата dstDataDir остаётся DataDir V; отдельный migrateDataDir нужен для миграции старого формата XLV1. Временной операции присваивается собственный UUID U.

Цикл проходит parts V. Reader источника читает его part.N и проверяет hash каждого полученного chunk. Erasure.Heal вызывает parallelReader, получает K пригодных фрагментов и DecodeDataAndParityBlocks. При наших E1/E2 data уже есть: нужно вычислить parity для E3/E4. При других пригодных номерах shards сначала восстанавливаются недостающие data, затем parity. Размеры, номера и конечное поле задаёт кодер выбранной версии; учебная матрица из главы 08 не подменяет библиотечную.

Writers создаются только для выбранных целей. Для non-inline данные идут во временный part .minio.sys/tmp/U/DataDir/part.1 данного endpoint. Bitrot writer заново добавляет hash перед каждым новым chunk. Для inline вместо отдельного файла заполняется буфер в RAM, который позже попадёт в xl.meta. Здесь один corrupt chunk делает целевой part непригодным; рассматриваемая ветвь переписывает полный shard part, а не только один повреждённый байт.

Внутри Erasure.Heal multiWriter имеет writeQuorum=1. Это порог продолжения записи доступных целей существующей V, а не замена W=3 для обычного PUT. Если один writer отказал, другой ещё может получить восстановленные байты. Если ни одна цель больше не принимает данные, продолжать этот repair нечем.

Если normal-проверка пропустила скрытый bitrot, source reader может обнаружить его уже при восстановлении. Erasure.Heal способен получить достаточные другие фрагменты и записать временные байты, но вернуть сохранённый errFileCorrupt. Внешний healObject закрывает readers/writers и при этой ошибке возвращается до публикации. Обёртка HealObject после errFileCorrupt в normal повторяет работу в deep, чтобы заново выбрать пригодные sources и targets. Наличие временных байтов первого прохода не является завершённым repair.

Источники: порядок, metadata, readers и writers, Erasure.Heal, ошибки записи и Close, normal с повтором deep.

Close, публикация и результат каждой цели

После обработки part код закрывает writers. Возвращённая ошибка Close исключает соответствующую цель из дальнейших parts и публикации. У streamingBitrotWriter.Close есть две операции: закрыть промежуточный writer и дождаться фонового CreateFile. Он возвращает сохранённый результат первого закрытия, а после ожидания не читает результат CreateFile заново. Поэтому ожидание фоновой функции и передача каждой поздней ошибки Fdatasync или Close storage-файла — разные свойства. Здесь действует то же уточнение, что в главе 08.

Целям, оставшимся после parts, выставляются номер shard Index и признак SetHealing. Затем healObject последовательно вызывает StorageAPI.RenameData. Это этап публикации восстановленных данных и metadata по отдельным endpoints. Только после успешного вызова для данной цели её After.Drives.State становится DriveStateOk. Этот цикл не вызывает общий renameData обычного PUT с W=3. Общий момент атомарной публикации всех целей из него не следует.

Предположим, E3 вернул ошибку Close, а E4 прошёл Close и RenameData. В ответе E4 станет OK, E3 сохранит прежнее не-OK состояние, например Corrupt. Если других ошибок нет, функция может вернуть nil — отсутствие общей ошибки. При этом E3 ещё не восстановлен. Поэтому нужно читать After по нужному Endpoint. В другом случае E3 успел опубликоваться, а RenameData E4 вернул ошибку: функция возвращает ошибку, но уже успешная публикация E3 не откатывается общим rollback.

Повтор заново выбирает V и актуальное состояние endpoints. Успешный E4 больше не обязан входить в targets; E3 может получить новую временную запись и затем публикацию. Удалять данные E4, менять private xl.meta или создавать пустой каталог на месте неподтверждённой цели для «выравнивания» состояния не требуется. В исходниках есть очистка временной операции, но отложенный вызов удаления, defer, ставится после цикла parts; ранний выход до него не даёт основания обещать отсутствие оставшихся временных файлов.

Источники: возвращённый Close, Flush буфера, Fdatasync и Close файла, исключение целей и публикация.

Вернулся endpoint или заменён физический носитель

Временный сетевой отказ может скрыть прежний исправный диск. После его возвращения сервер снова читает format и metadata: возврат доступности сам по себе не говорит, какие versions он успел пропустить. Для V он может оказаться исправным источником, устаревшей копией или доступной целью с отсутствующими данными.

Физическая замена меняет накопитель, но адрес endpoint может остаться прежним. В format.json поле Erasure.This задаёт логическую идентичность позиции среди Erasure.Sets. GetDiskID проверяет format и соответствие set/disk позиции. В ветви newHealFormatSets новый unformatted носитель получает ожидаемый Erasure.This из reference format этой позиции. Следовательно, появление того же UUID не доказывает, что вернулся тот же физический накопитель; это не аппаратный serial number.

saveFormatErasure публикует новый format и при заданном healID создаёт healing tracker. Этот tracker хранит ID диска, отдельный HealID операции, PoolIndex, SetIndex, DiskIndex, Endpoint, Started и LastUpdate. При загрузке его ID сравнивается с GetDiskID. Копирование чужого tracker или ручная перестановка format не являются способами продолжить восстановление.

Автоматический monitor локального узла вызывает HealFormat, а затем healFreshDisk. Обход выполняет узел, к которому подключён заменённый диск, для соответствующего set. Сначала нужна пригодная reference format в quorum; при несогласованном format код отказывает. Ни совпавший путь, ни пустой новый filesystem не являются восстановленными объектами.

Источники: GetDiskID и позиция, newHealFormatSets, format и tracker, HealFormat, tracker ID, локальный monitor.

Чем прогресс замены диска отличается от очереди MRF

healFreshDisk сохраняет очередь QueuedBuckets; tracker запоминает текущие Bucket/Object, HealedBuckets и счётчики. ResumeItemsHealed, ResumeItemsFailed и другие Resume-поля возвращают счётчики к началу возобновляемого bucket. Повторный обход части уже обработанной работы возможен: сохранённая контрольная точка не означает отдельную транзакцию для каждого объекта.

healErasureSet начинает normal scan, перечисляет versions и вызывает HealObject. Новые версии с ModTime после Started и версии, выбранные lifecycle для удаления, могут быть пропущены (skipped). Успех конкретной версии дополнительно требует After.Drives[tracker.DiskIndex].State=DriveStateOk. Поэтому общий nil от HealObject не подменяет результат нужной цели. ItemsHealed/BytesDone, ItemsFailed/BytesFailed и ItemsSkipped/BytesSkipped учитываются отдельно. Эти Bytes относятся к учитываемым версиям, а не к измерению всех physical shard reads и writes.

Если ItemsFailed больше нуля и RetryAttempts меньше 4, healFreshDisk увеличивает RetryAttempts, сбрасывает рабочие счётчики и возвращает errRetryHealing. После исчерпания этой ветви ошибки остаются в счётчиках; tracker с тем же HealID может получить Finished=true. Поэтому Finished означает окончание этого обхода, включая вариант с оставшимися failed items. Он не заменяет проверку нужной V и её целей.

Scanner ищет объекты по namespace и cache; MRF обрабатывает задания известных partial operations; fresh-disk heal перечисляет данные set ради конкретного заменённого диска. Foreground GET может только обнаружить проблему и дать повод для фонового вызова. Эти инициаторы используют общий механизм работы с V, но их очереди, критерии пропуска и счётчики различаются.

Источники: поля tracker, учёт и сохранение, resume, версии и результат нужного диска, повтор и Finished.

Сколько IO требует исправление V

Посчитаем отдельный deep-проход с последующим repair, когда E4 уже доступен, но V у него нет. На E1/E2 все четыре chunks исправны; у E3 ошибка в последнем chunk, поэтому до её обнаружения прочитан весь его поток. Проверка трёх потоков читает 6 MiB payload и 384 байта hashes: 6 291 840 байт. Опрос metadata E4 сообщает отсутствие V; чтения его part нет.

Далее sources E1/E2 читаются для восстановления: ещё 4 MiB payload и 256 байт hashes, всего 4 194 560 байт. Writers E3/E4 получают столько же суммарно. Итого для этой последовательности — 14 MiB payload и 896 байт hashes, 14 680 960 байт чтения и записи shard-потоков. Hash вычисляется для 12 проверенных chunks первого прохода, 8 source chunks repair и 8 новых target chunks: 28 вычислений на chunks по 512 KiB. Кодирование обрабатывает четыре stripes.

Это счётчик байтов на выбранных storage-путях. Он не равен фактическому чтению и записи накопителя, device IO: filesystem metadata, выравнивание, упреждающее чтение, кэширование данных, повторные ошибки и временное сосуществование файлов меняют обращения к устройствам. Если повреждение обнаружено раньше, VerifyFile может прочитать меньше; если sources меняются или попытка повторяется, работа растёт.

Зафиксируем и место исполнения: healer работает на D, источники E1/E2 находятся на A/B, E3 — на C, E4 — локальный новый диск D1. Удалённый вызов метода, RPC VerifyFile, исполняет проверку на storage endpoint и возвращает статусы parts, поэтому первые 6 MiB payload не обязаны пересекать сеть к D. При repair к D приходят потоки E1/E2, 4 194 560 байт; к C уходит поток E3, 2 097 280 байт. Поток E4 пишется локально. Получаем 6 291 840 сетевых байт shard-потоков без RPC, metadata, HTTP/TLS framing и повторов. При другом месте healer или совмещении endpoints на узле этот расчёт меняется.

Если в ту же пару sources приходит полный обычный клиентский (foreground) GET V и он читает E1/E2, эти sources дополнительно обслужат ещё 4 194 560 байт. Вместе с source-проходом repair это 8 389 120 байт вместо 4 194 560 для одного GET, до прочих расходов. Это сравнение объёма двух работ. Из удвоения байтов не следует удвоение latency: cache, очереди и расположение IO могут дать другую зависимость. Успешный E4 и повтор только E3 также требуют раздельного учёта: один новый source-проход и запись E3 — ещё 6 291 840 байт без новой предварительной deep-проверки.

Для большого набора, где требуется вернуть 1 TiB именно shard payload на одну цель при K=2, один идеальный полный проход требует 2 TiB source payload reads и 1 TiB target payload writes. Это не 1 TiB логических объектов. Время можно оценивать только по измеренным доступным скоростям нужных ресурсов и количеству повторов; непроверенные MiB/s сюда не подставляются.

Источники: RPC VerifyFile, проверка на endpoint, source stream, передача writer, обработка stripes.

Пересчитать отбор, частичный результат и байты в RAM

Код ниже моделирует только названные условия. Синтетический 64-битовый hash уже задан числом; xxhash реального key здесь не вычисляется. На неизменном, посещаемом в каждом нужном цикле имени он показывает два уровня отбора, но не срок scanner. Функция publish получает наблюдаемые результаты Close и RenameData; она не воспроизводит storage, metadata quorum или crash recovery.

"""Teaching model: selection, per-target publication and byte accounting.
No MinIO calls, sockets, files, HighwayHash or xxhash implementation.
"""
from math import ceil

MiB = 1 << 20
S, B, K, N, H = 4 * MiB, MiB, 2, 4, 32
blocks = [min(B, S - offset) for offset in range(0, S, B)]
widths = [ceil(length / K) for length in blocks]
payload = sum(widths)
hash_bytes = len(blocks) * H
stream = payload + hash_bytes
assert blocks == [MiB] * 4
assert widths == [MiB // 2] * 4
assert payload == 2 * MiB and hash_bytes == 128
assert N * stream == 8389120

# E4 is available but has no V. E3's last chunk has a bad hash.
deep_reads = 3 * stream
source_reads = K * stream
target_writes = 2 * stream
network = source_reads + stream  # healer D; E1/E2 remote; E3 remote; E4 local
assert deep_reads == 6291840
assert source_reads == target_writes == 4194560
assert deep_reads + source_reads + target_writes == 14680960
assert network == 6291840
assert 2 * source_reads == 8389120  # repair sources plus one foreground GET
assert source_reads + stream == 6291840  # another pass, only E3 is target
assert 3*4 + 2*4 + 2*4 == 28  # chunk hashes computed

def cycle_mode(config, cycle, start_cycle, elapsed):
    if config == -1:
        return "normal"
    if config == 0:
        return "deep"
    return "deep" if cycle - start_cycle < 1024 or elapsed > config else "normal"

assert cycle_mode(-1, 0, 0, 0) == "normal"
assert cycle_mode(0, 5000, 0, 0) == "deep"
assert cycle_mode(100, 1023, 0, 0) == "deep"
assert cycle_mode(100, 1024, 0, 100) == "normal"
assert cycle_mode(100, 1024, 0, 101) == "deep"

def selected(hash64, cycle, compact=False, skip=False):
    # hash64 is a supplied synthetic xxhash result, not calculated from a key.
    low = hash64 & 0xffffffff
    high = (hash64 >> 32) & 0xffffffff
    divisor = 16 if compact else 1
    if skip or (compact and low % 16 != cycle % 16):
        return False
    return high % (1024 // divisor) == (cycle // divisor) % (1024 // divisor)

fake_hash = (93 << 32) | 37
ordinary = [c for c in range(1024) if selected(fake_hash, c)]
compacted = [c for c in range(1024) if selected(fake_hash, c, compact=True)]
assert ordinary == [93] and compacted == [469]
assert not selected(fake_hash, 93, skip=True)

def publish(before, close_results, rename_results, decode_error=False):
    # Only observable return values are modeled. No claim that Close carries
    # every late error from a storage goroutine.
    after = dict(before)
    if decode_error:
        return after, "decode error"
    candidates = [name for name in before if close_results[name] is None]
    if not candidates:
        return after, "all targets failed"
    for name in candidates:
        if rename_results[name] is not None:
            return after, "rename error"
        after[name] = "ok"
    return after, None

before = {"E3": "corrupt", "E4": "missing"}
after, error = publish(before, {"E3": "returned close error", "E4": None},
                       {"E4": None})
assert after == {"E3": "corrupt", "E4": "ok"} and error is None
again, error = publish({"E3": after["E3"]}, {"E3": None}, {"E3": None})
assert again == {"E3": "ok"} and error is None
partial, error = publish(before, {"E3": None, "E4": None},
                         {"E3": None, "E4": "error"})
assert partial == {"E3": "ok", "E4": "missing"} and error == "rename error"
early, error = publish(before, {"E3": None, "E4": None}, {},
                       decode_error=True)
assert early == before and error == "decode error"

print("streams:", stream, "four streams:", N * stream)
print("deep/source/target:", deep_reads, source_reads, target_writes)
print("total:", deep_reads + source_reads + target_writes, "network:", network)
print("synthetic selection cycles:", ordinary, compacted)
print("partial:", after, "retry:", again, "rename failure:", partial)

Как наблюдать влияние на обычные запросы

Сопоставляйте ход scan/heal с end-to-end временем обычных PUT/GET, числом завершённых запросов, ошибками и unknown исходами. Для сравнения нужны одинаковые размеры объектов, concurrency, состояние cache, TLS, проверки checksum и SDK retries. Latency измеряется от выбранного начала операции до принятия полного результата, включая тело GET. По отдельности полезны занятость устройств, глубина очереди, объёмы source reads и target writes, CPU hash/decode и сеть между указанными узлами.

В throughput приложения входят подтверждённые логические байты. Внутренние bytes tracker и сумма shard-потоков отвечают на другие вопросы и не складываются с ним как «ещё один полезный результат». p99 получают из распределения длительностей: его нельзя вывести из среднего, сложить либо усреднить процентили узлов. Сокращение очереди за окно также нужно читать вместе с новыми заданиями, skipped/failed и доступностью целей.

В коде scannerSleeper и healSleeper вводят задержки; отдельные пути могут ждать снижения числа HTTP-запросов. Это механизмы снижения конкуренции, а не резерв определённого числа IOPS или гарантия foreground latency. Численные скорости и p99 в этой главе не выдаются за измеренные результаты.

Источники: dynamicSleeper, ожидание HTTP IO.

Числа N=4 и K=2 относятся к одному set выбранной версии. Если E1/E2 — каталоги одного SSD, один отказ убирает сразу два endpoints; три потерянных endpoints оставляют меньше K. Четыре VM на одном ноутбуке также имеют общие накопитель, питание и гипервизор. У нашей схемы физические диски разные; дополнительная независимость питания остаётся условием размещения.

Erasure coding использует сохранившуюся избыточность. Оно не возвращает окончательно удалённую историю, не исправляет правильно записанные, но ошибочные данные приложения и не заменяет backup. Дополнительные shards не возвращают утраченный ключ шифрования. Сохраняемый стенд книги имеет один endpoint с P=0: здесь нет второго источника для такого восстановления. Четырёхendpointная сцена — вычисленная модель; административный запуск healing и повреждение private server data в упражнение этого стенда не добавляются.
