От имени объекта до достаточного числа ответов

Одна версия объекта кодируется внутри выбранной группы хранения. Числа ниже относятся к этой группе, а не ко всем дискам организации.

Storage endpoint — адрес области хранения, переданной серверу: например, локальный путь или URL пути на другом узле. Путь обозначает место подключения, устройство хранит байты, узел исполняет процесс. Один узел может обслуживать несколько endpoints, а несколько путей могут находиться на одном физическом устройстве.

Числа кворума ниже являются необходимыми численными условиями для обычной непустой версии. Они не гарантируют успешное чтение без доступной сети, пригодных shards и согласованной metadata выбранной версии. Полезная доля ёмкости равна K/N, коэффициент расхода — N/K; metadata, округление, небольшие объекты и внешние tiers в эту идеальную оценку не входят.

Где заканчивается запрос клиента

Клиент передаёт адрес сервера, bucket, key, заголовки и тело. TLS сначала защищает соединение и позволяет клиенту проверить личность сервера. Затем сервер проверяет поддерживаемую подпись и полномочия операции. Наличие правильной подписи не означает разрешение записывать в любой bucket: подпись устанавливает связь запроса с credentials, а политика ограничивает допустимые действия.

После этих проверок объектный слой выбирает место хранения. Pool — группа ресурсов, добавленная серверу как единица размещения. Внутри pool находятся erasure sets. Erasure set — устойчиво заданная группа endpoints, между которыми кодируется одна версия объекта. Диск, входящий в другой set, не становится автоматически дополнительным ответчиком для quorum текущего объекта.

В простом стенде один pool и один set, поэтому выбора между группами нет. В более сложной конфигурации сервер отдельно выбирает pool, а внутри него получает индекс set из имени объекта. В закреплённом коде GetObjectNInfo передаёт object в getHashedSet; алгоритм зависит от формата deployment. Поэтому нельзя обещать, что произвольный самописный CRC по строке bucket/key воспроизведёт размещение современного deployment.

Что кодируется

Пусть в set находятся N endpoints. Для выбранной версии объекта сервер использует K data shards и P parity shards, причём N=K+P. Shard — фрагмент кодированного представления. Data shards содержат разделённые данные; parity shards содержат математическую избыточность. Это не P полных резервных копий файла.

Реализация использует Reed–Solomon. При наличии любых K пригодных shards одной кодированной версии можно восстановить её данные. «Пригодных» означает не только доступных по сети: важны целостность фрагмента и согласованная metadata. Повреждённый shard, который не проходит проверку, нельзя засчитать как ещё один корректный ответ.

Для большого объекта полезная доля сырой ёмкости приблизительно равна K/N, а коэффициент записи — N/K. При K=4 и P=4 доля равна половине, а кодированное содержимое занимает примерно двойной объём. Это оценка без файловой metadata, checksums, округления блоков, старых версий, незавершённых multipart uploads и свободного места для дальнейшей работы.

Числа относятся к конкретному поколению

В Server RELEASE.2025-10-15T17-29-55Z функция DefaultParityBlocks для новой конфигурации выбирает 0 при одном endpoint, 1 при двух или трёх, 2 при четырёх или пяти, 3 при шести или семи и 4 для остальных допустимых размеров set. Поэтому утверждение «по умолчанию всегда половина дисков» для этой функции неверно. Старый текст docs/erasure/README.md ещё содержит такое упрощение.

Quorum — минимальное достаточное число согласованных ответов. Для рассматриваемого объекта read quorum равен K. Write quorum равен K, кроме симметричного случая K=P: тогда требуется K+1. При восьми endpoints четыре сохранившихся shards могут позволить чтение старой версии, но для записи с layout 4+4 недостаточно четырёх ответов. Дополнительный голос не позволяет двум изолированным половинам такого set независимо подтверждать запись.

Почему новая запись при отказах может получить другой layout

Storage class — выбранное правило избыточности новой записи. Tier — другое хранилище, куда сервер может перенести тело объекта. Inline data — небольшое тело, сохранённое вместе с metadata. Эти варианты требуют собственных ветвей расчёта.

Режим availability в закреплённой реализации предпочитает сохранить доступность новых записей: при заранее недоступных endpoints он может увеличить число parity shards. Например, при N=16, исходном P=4 и четырёх недоступных endpoints новый обычный PUT может получить P=8, K=8 и write quorum 9. Уже сохранённые версии от этого не меняются. Это уточнение не относится к исходному расчёту здорового set.

Восемь мегабайт на восьми endpoints

Возьмём учебную версию длиной 8 MiB, N=8, K=4, P=4. Для расчёта зададим блок кодирования 1 MiB. Каждый блок делится на четыре фрагмента по 256 KiB, затем вычисляются четыре parity-фрагмента такого же размера. В объекте восемь блоков. Один endpoint получает 8×256 KiB=2 MiB shard data, все восемь — 16 MiB. Контрольные суммы и metadata добавят собственный расход.

Формула размера одного shard в этом расчёте: floor(S/B)×ceil(B/K)+ceil((S mod B)/K), где S — длина объекта, B — размер блока. Она объясняет, почему для произвольного размера и K результат нельзя всегда заменить ровно S/K.

При отказе одного endpoint остаются семь пригодных shards: старую версию можно читать. При отказе ещё двух остаются пять, что всё ещё достаточно для чтения и write quorum 5 этого layout. При четырёх потерях остаются четыре: данные старой версии ещё восстановимы при пригодной metadata, но запись 4+4 не получает quorum. Пятая потеря оставляет три shards: этого меньше K.

Размещение определяет, сколько shards исчезнет при одном отказе. Если восемь endpoints — каталоги одного SSD, отказ этого SSD оставит ноль доступных shards. Если четыре endpoints находятся на одном узле, потеря узла оставит четыре. Для рассмотренной версии с K=4 и P=4 этого численно достаточно для чтения при согласованных метаданных и исправных shards, но недостаточно для write quorum 5. Такую группу ресурсов с общей причиной отказа называют failure domain, или областью отказа. При выборе дисков и узлов нужно проверять, сколько endpoints теряет каждая такая группа.

При S = 1 MiB + 1 байт, N=8, K=4, P=4 и B=1 MiB каждый shard содержит 262144 + ceil(1/4) = 262145 байт payload; все восемь — 2097160 байт до checksums и metadata. Последний блок добавил восемь сохранённых байт ради одного нового байта тела: деление и округление выполняются по блокам.

Metadata участвует в сохранении объекта

Сервер хранит сведения о версии и её кодировании: размеры, время, distribution, K/P, checksums и другие поля. В выбранном формате используется xl.meta. Данные небольшой версии могут быть встроены в этот файл; более крупные parts могут находиться в каталоге данных версии. Поэтому даже на одиночном диске object key не следует понимать как обычный файл с теми же байтами.

PUT проходит через временную запись кодированных частей, формирование metadata и операцию закрепления результата на достаточном числе endpoints. Успех клиенту возвращается после успешного серверного пути. Чтение собирает metadata, определяет пригодную версию и quorum, выбирает доступные shards и при необходимости восстанавливает отсутствующие данные.

Если клиент получил timeout, он знает только, что вовремя не получил однозначного ответа. Сервер мог не закончить запись, а мог закончить её и потерять соединение до доставки ответа. При включённом versioning слепой повтор способен создать ещё одну версию. Позднее мы будем сверять version ID, размер и собственный хеш содержимого; ETag безусловным MD5 не считаем.

Закреплённые исходники: выбор pool, выбор set, parity defaults, quorums и особые ветви, кодирование и размер shard, PUT и degraded parity, формат metadata.
