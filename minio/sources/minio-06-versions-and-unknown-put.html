Версия существует отдельно от последнего ответа клиента

Продолжаем тот же handbook-minio. Изменяющие опыты этой главы относятся к закреплённой OSS-реализации. Для AIStor отдельно проверяется лицензия: version-specific deletion недоступно в Free.

Три разных действия над одним key

При включённом versioning новый PUT создаёт новую версию. Version ID выдаёт сервер; клиент сохраняет его как идентификатор результата. Предыдущая версия остаётся noncurrent — не текущей, но всё ещё существующей.

DELETE без versionId создаёт delete marker — текущую отметку удаления. Обычное чтение key больше не возвращает прежнее тело, хотя старые версии могут оставаться доступными по ID. DELETE с конкретным versionId удаляет выбранную версию или выбранный marker. Это другое действие с другой судьбой данных.

ШагТекущий результатЧто сохраняется
Первый PUTV1Тело V1
Второй PUTV2Тела V1 и V2
DELETE без IDMarker MV1, V2 и M
Удалить именно MСнова V2V1 и V2; M удалён

V1/V2/M в таблице — обозначения, не готовые ID для копирования. В опыте используются только ID собственного сервера. Удаление marker не отменяет произвольные записи после контрольной точки.

Фиксируем исходную версию до изменения

Работаем во втором терминале той же VM с owner alias lab. HTTPS health должен успешно пройти прежде изменяющего блока. Helper object-study для этого опыта не требуется.

version_id() {
    python3 -B - "$1" <<'PY'

data = json.load(open(sys.argv[1]))
value = data.get("versionID", "")

}

Dry-run и настоящий DELETE сравниваются без reset

Dry-run получает исходное состояние с текущей V2, но не выполняет удаление. Следом проверяем, что current version ID прежний. Затем DELETE без ID выполняется на том же состоянии.

"${MC[@]}" rm --dry-run lab/handbook-minio/project/manifest.txt
"${MC[@]}" --json stat lab/handbook-minio/project/manifest.txt > "$EX/after-dry-run.json"
test "$(version_id "$EX/after-dry-run.json")" = "$V2"

В закреплённом mc команда cat сначала запрашивает сведения об объекте. Текущий delete marker преобразуется в ObjectMissing; до чтения тела команда не доходит. Здесь ожидается отказ lookup с сообщением Object does not exist. Сохранённый ответ DELETE подтверждает marker M, а чтение V2 по ID возвращает прежние байты. Проверки используются вместе: одно сообщение ObjectMissing само по себе не устанавливает причину отсутствия текущего тела.

Осознанно удаляем только собственный marker

Следующий шаг изменяет историю: выбранный marker M удаляется. Тела V1/V2 сохраняются. Перед выполнением сверяем M с сохранённым ответом и списком версий. В опыте нет параллельного writer и lifecycle.

"${MC[@]}" rm --version-id "$M" \
  lab/handbook-minio/project/manifest.txt

"${MC[@]}" --json stat lab/handbook-minio/project/manifest.txt > "$EX/after-marker-removal.json"
test "$(version_id "$EX/after-marker-removal.json")" = "$V2"

"${MC[@]}" cat lab/handbook-minio/project/manifest.txt > "$EX/revealed-v2.txt"
cmp "$EX/manifest-v2.txt" "$EX/revealed-v2.txt"
finish_stage

Это управление версиями собственного учебного объекта, не восстановление резервной копии. Если вместо M передать V1, удалится тело V1. Поэтому в коде нет выбора «первой строки ls», массового --versions --recursive и автоматической очистки.

Timeout записи не является ответом «объект не сохранён»

Представим PUT с operation ID O. Клиент отправил тело, сервер закрепил новую версию V3, но ответ потерялся. Клиент завершился по deadline. Он знает, что не получил подтверждение, но не знает, закончилась ли запись до разрыва соединения.

Новый PUT того же тела в versioned bucket способен создать V4. Даже при одинаковых байтах это другая версия. Retry внутри SDK также входит в этот анализ; один вызов прикладного метода не обязательно равен одному HTTP-запросу.

Для воспроизводимого исследования до отправки сохраняют намерение: endpoint identity, bucket/key, operation ID, длину и собственный SHA-256 тела. Operation ID передают как x-amz-meta-operation-id. Это metadata для сопоставления, а не серверный ключ идемпотентности.

После неоднозначного исхода сначала прекращаются зависимые изменения. Перечисляются все версии нужного key, с учётом пагинации и delete markers. Кандидат проверяется по metadata operation ID, затем читается по конкретному version ID и сравнивается с исходными байтами. Обычный HEAD текущего key недостаточен: другой writer мог создать более новую версию, а DELETE — текущий marker.

НаблюдениеДопустимый вывод
Один кандидат O, совпали байтыНайдена сохранённая версия намерения; фиксируем её ID
Несколько совпавших версий OЕсть дубли; exactly-once не достигнуто
Совпал O, байты другиеНарушен договор намерения; остановка и расследование
Кандидат пока не найденНет подтверждения в данном наблюдении; это не доказательство, что старый запрос уже не сможет завершиться

Отсутствие кандидата разрешает автоматический retry только при дополнительном прикладном договоре: например, заранее выбранном уникальном key с проверенным create-only либо согласованном durable журнале операций. В повторах одного намерения сохраняются тот же key, operation ID и исходные bytes; новый key каждой попытки создаёт другой объект. После unknown или 412 сначала ищут результат. Create-only сам по себе не обеспечивает exactly-once. Политика повторов не выводится из одного timeout.

Как читать exit code и receipt object-study

В согласованном v1 exit 0 означает подтверждённый результат, 2 — validation до отправки, 3 — явный отказ сервиса, 4 — transport/deadline/cancel с неизвестным исходом PUT, 5 — локальный I/O, integrity либо final commit failure. Эти коды ещё требуют проверки реализации на настоящем сервере.

Exit code описывает причину завершения, outcome — подтверждённость серверной операции. Код 3 может сочетаться с unknown: предыдущая попытка могла записать объект, повтор получил 412. По консервативному SPEC v1 неуспешный PUT после HTTPClient.Do имеет unknown. Ошибка открытия или предварительного хеширования source до отправки означает rejected. Код 5 возможен после подтверждённого PUT: ошибка закрытия локального source не отменяет серверную запись. При GET ошибка fsync каталога после hard link может оставить полное конечное имя; повтор поверх него запрещён.

Helper добавляет подписанный x-amz-meta-operation-id и возвращает operation_id в очищенном receipt. Но процесс может погибнуть до receipt; тогда ID может быть утрачен. В v1 не обещаны durable intent journal и exactly-once. Нельзя описывать receipt как уже существующую защиту от всех неоднозначных исходов.
