Принять резерв чтением восстановленной истории

Сделаем закрытую копию остановленного одиночного стенда, восстановим её в другой каталог и прочитаем V1/V2 без новой загрузки. Так различаются сохранённый процессом объект, лишняя копия shards и независимый резерв.

Что именно нужно восстановить

Erasure parity исправляет ограниченное число потерянных shards внутри deployment. Она не возвращает версию, которую разрешённо удалили, и не защищает от потери всех устройств, общего питания или украденных credentials. Versioning сохраняет историю лишь пока её версии существуют и доступны. Репликация в другой сервер переносит данные по своим правилам, включая возможные удаления и задержку; она не автоматически является неизменяемой резервной копией.

Резерв выбирают под задачу: какие buckets, все или только текущие версии, delete markers, пользовательская metadata, IAM, bucket policy, lifecycle, уведомления, конфигурация, внешние ключи шифрования. Обычный GET текущего key возвращает только выбранное тело. Простое копирование текущих объектов через клиент не обещает сохранить историю, marker stack, version ID и административные настройки.

В этом упражнении используется ровно прежний один процесс с одним data, без внешнего KMS и tiering. Копируется весь остановленный LAB_ROOT, включая data/.minio.sys, TLS, secrets, mc, fixtures, exercises, binaries и сведения происхождения. Это приватная копия, а не публичный переносимый том. В ней есть root password, service-account secret и CA key. Её нельзя прикладывать к source manifest или отправлять в Git.

Почему копирование требует остановки

Во время PUT сервер публикует данные и metadata на отдельных endpoints; scanner, lifecycle и healing тоже меняют состояние. Последовательное чтение дерева работающего сервера может взять xl.meta до изменения и part после изменения. Хеш каждого скопированного файла ещё не доказывает, что все файлы относятся к одному согласованному моменту. Наша предпосылка — сервер полностью остановлен, иных процессов и внешних writers к тому же data нет.

В первом терминале нажмите Ctrl-C и дождитесь возврата оболочки. Не запускайте run-server.sh снова до завершения копирования. Во втором терминале прекратите клиенты. Это управляемое действие владельца единственного учебного процесса; helper не убивает процессы и не определяет автоматически, что файловая система quiescent, то есть больше не изменяется. Для distributed deployment остановки одного frontend недостаточно, а копирование отдельных дисков в разное время не заменяет согласованный backup-план.

Пределы собственного cold_copy.py

Исходник labs/cold_copy.py входит в том. Он не вызывает MinIO API. Snapshot читает дерево, отвергает ссылки и специальные файлы, считает размер и SHA-256 каждого обычного файла, копирует в новый отдельный каталог и сверяет содержимое. В конце появляются собственные _snapshot_manifest.json и _snapshot_COMPLETE. Manifest — список относительных имён, размеров и хешей; он не содержит сами credentials. Но и имена объектов могут быть чувствительны, поэтому весь каталог остаётся закрытым.

Restore сначала проверяет snapshot, затем создаёт другое новое дерево и копирует файлы, не включая служебные manifest/COMPLETE самого snapshot. Предыдущий LAB_ROOT не перезаписывается. Ошибка оставляет частичную цель для разбора; повтор в неё отвергается. Helper не удаляет её автоматически и не предлагает reset. Проверка SHA выявляет расхождение с выбранным manifest, но не аутентифицирует резерв от администратора, способного заменить и bytes, и manifest.

Копирование файлов и fsync отдельных файлов не являются snapshot-транзакцией файловой системы или испытанием сбоя питания. Здесь проверяется согласованная по условию остановки копия и её логическая читаемость после restore. Долговечность каталога на конкретном устройстве, независимый backup-носитель, шифрование хранения и контроль доступа требуют отдельной приёмки. Две папки одного SSD не переживут его физический отказ.

Подготовить источник программы и новую цель

Сначала перейдите в каталог minio/ вашей копии книги: в нём должен находиться labs/cold_copy.py. Это путь исходника helper, не каталог runtime. Работает тот же обычный пользователь личной Linux VM; обе резервные цели находятся в его домашней области. Перед запуском убедитесь, что свободного места достаточно для двух полных копий LAB_ROOT сверх оригинала. Архивы Go и кэши тоже входят в эту простую полную копию; объём не равен сумме S3 body.

set +x
set -euo pipefail
set -C
umask 077
BOOK_LABS="$PWD/labs"
test -f "$BOOK_LABS/cold_copy.py"
source "$HOME/minio-study/enter.sh"
test -f "$LAB_ROOT/.setup/versions-v2/COMPLETE"
BACKUP_PARENT="$HOME/minio-backups"
mkdir -p -- "$BACKUP_PARENT"
chmod 700 "$BACKUP_PARENT"
SNAPSHOT="$BACKUP_PARENT/cold-v2"
RESTORED="$HOME/minio-restored-v2"
test ! -e "$SNAPSHOT"
test ! -L "$SNAPSHOT"
test ! -e "$RESTORED"
test ! -L "$RESTORED"
python3 -B "$BOOK_LABS/cold_copy.py" --help

--help только объясняет три действия helper. snapshot SOURCE DEST создаёт новую копию, verify SOURCE сверяет готовый snapshot, restore SOURCE DEST создаёт новый runtime. SOURCE/DEST обязаны быть отдельными деревьями; вложенную цель helper отвергает, чтобы не копировать резерв внутрь самого себя. Python -B запрещает создание bytecode cache.

Snapshot и проверка до запуска восстановленного сервера

Следующий блок выполняется только после подтверждённой остановки исходного сервера. Он читает LAB_ROOT и пишет исключительно новые snapshot/restore цели. Нативное выполнение этого рецепта при подготовке книги не производилось.

python3 -B "$BOOK_LABS/cold_copy.py" snapshot "$LAB_ROOT" "$SNAPSHOT"
python3 -B "$BOOK_LABS/cold_copy.py" verify "$SNAPSHOT"
python3 -B "$BOOK_LABS/cold_copy.py" restore "$SNAPSHOT" "$RESTORED"

Ожидаются три успешных кода и соответствующие status snapshot-copied, verified, restore-copied. Счётчик files относится к файлам дерева, не к S3 objects или versions. При отказе чтения, ссылке, расхождении хеша либо существующей цели прекращаются зависимые действия. Не редактируйте manifest так, чтобы он согласился с ошибочной копией. Сначала определите, нарушена ли остановка источника, доступ или носитель.

Один адрес, один активный процесс

Исходный сервер остаётся остановленным. В первом терминале запускаем только восстановленную копию; её скрипт вычисляет LAB_ROOT по собственному расположению, поэтому использует новый data и TLS. API остаётся 127.0.0.1:19000. Если оригинал занимает порт, стартовать второй процесс на том же порту нельзя; смена случайного data ради обхода ошибки тоже не принимается за restore.

"$HOME/minio-restored-v2/run-server.sh" >> "$HOME/minio-restored-v2/logs/restore-server.log" 2>&1

Терминал занят foreground сервером. Во втором терминале заново задаём переменные, не полагаясь на прежний EX или функцию version_id из главы о версиях. Весь дальнейший ввод берётся из восстановленного корня.

source "$HOME/minio-restored-v2/enter.sh"
cd "$LAB_ROOT"
curl --fail --silent --show-error --connect-timeout 2 --max-time 5 \
  --cacert "$LAB_ROOT/tls/ca.crt" --output /dev/null \
  https://127.0.0.1:19000/minio/health/cluster

read_version_id() {
    python3 -B - "$1" <<'PY'
import json, sys, uuid
with open(sys.argv[1]) as stream:
    row = json.load(stream)
value = row.get("versionID")
if row.get("status") != "success" or not isinstance(value, str):
    raise SystemExit("Saved version result is not confirmed")
uuid.UUID(value)
print(value)
PY
}
V1="$(read_version_id "$LAB_ROOT/exercises/versions-v2/v1.json")"
V2="$(read_version_id "$LAB_ROOT/exercises/versions-v2/v2.json")"
"${MC[@]}" cat --version-id "$V1" lab/handbook-minio/project/manifest.txt \
  > "$LAB_ROOT/downloads/restored-v1.txt"
"${MC[@]}" cat --version-id "$V2" lab/handbook-minio/project/manifest.txt \
  > "$LAB_ROOT/downloads/restored-v2.txt"
cmp "$LAB_ROOT/fixtures/manifest-v1.txt" "$LAB_ROOT/downloads/restored-v1.txt"
cmp "$LAB_ROOT/exercises/versions-v2/manifest-v2.txt" "$LAB_ROOT/downloads/restored-v2.txt"
"${MC[@]}" cat app/handbook-minio/project/client-note.txt \
  > "$LAB_ROOT/downloads/restored-client-note.txt"
cmp "$LAB_ROOT/exercises/access-v1/client-note-v1.txt" \
  "$LAB_ROOT/downloads/restored-client-note.txt"

Два UUID обозначают именно прежние версии. Два cmp проверяют тела V1/V2, а третий GET использует сохранённый ограниченный service account и проверяет отдельный 41-байтовый fixture. В восстановленную цель перед этими чтениями ничего не загружается. Так проверяется сохранение истории, доступа и bytes из резервной копии, а не способность нового пустого сервера принять повторный PUT. Успех этих fixtures не доказывает полную проверку всех объектов большого deployment.

Какие изменения не вернутся

RPO — допустимая потеря изменений относительно выбранной контрольной точки. Если после cold-v2 оригинал получил V3, этот snapshot её не содержит. Возврат к нему не отменяет существование V3 на других клиентах и не сливает две истории автоматически. RTO — время восстановления требуемого обслуживания: получение копии, проверка, запуск, TLS/IAM и чтение нужных данных. Одно время копирования не равно RTO.

Текущий опыт не создаёт внешнего KMS. При server-side encryption за пределами профиля нужны доступные ключи и их политика: сохранённый ciphertext без ключа не возвращает plaintext. При tiering часть тела может находиться во внешнем хранилище; копия только локальных metadata не включает удалённые bytes. Резерв bucket policy без user identity и секретов также не создаёт рабочий доступ.

Программное обновление — отдельное изменение формата и поведения. Сначала сохраняют выбранный бинарник, source commit и резерв; затем на отдельной восстановленной цели проверяют чтение исторических версий и операции новой версии. Успешный запуск новой программы не доказывает возможность обратного запуска старой поверх уже изменённых данных. Для архивного OSS нет обещанного будущего vendor security patch; миграция на другую реализацию требует проверки S3-семантики и истории.

Задание и разбор отказов

Изменяемый пример выполняют на отдельной копии snapshot, не на единственном резерве: поменяйте один байт заранее выбранного несекретного fixture-файла. verify должен отказать по inventory; это модель повреждения копии, не bitrot MinIO shard. Обратное восстановление исходных bytes должно вернуть успешную проверку. Изменение только manifest ради PASS запрещено смыслом опыта. Неполный snapshot без COMPLETE и restore в существующий каталог также должны отвергаться.

После упражнений остановите восстановленный foreground сервер и сохраните обе цели для сравнения. Для возврата к оригиналу запускается только его прежний run-server.sh, затем повторяется health/read; никакой автоматический restore поверх оригинала не выполняется. Разрешённая поздняя очистка требует сначала выбрать, какая проверенная независимая копия остаётся; книга не даёт массовую команду rm -rf по вычисленному пути.

Опорные механизмы: локальное хранение, xl.meta и версии, версионное состояние. cold_copy.py — собственный helper этой книги; его чтение и pure-проверки не являются native backup/restore MinIO.
