Изменить размещение, сохранив историю объекта

Добавление ёмкости меняет выбор новых записей. Перенос уже сохранённых версий требует другой работы: прочитать выбранную версию, записать её в другой pool и лишь затем решать, можно ли убрать исходник. Разберём эти состояния в архивном OSS commit 9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a.

Pool не является дополнительным голосом одного объекта

В модели set quorum относится к endpoints одной кодированной версии. Pool объединяет один или несколько sets, но объект не распределяет свои K+P shards по всем pools сразу. Если в pool A у выбранного set не хватает пригодных shards, свободный пустой pool B не содержит недостающие байты. Добавление оборудования не восстанавливает утраченное содержимое.

Сохранённый format задаёт принадлежность endpoints, порядок sets, идентичность deployment и дисков. При старте сервер сопоставляет переданную топологию с прочитанным форматом. Все pools одного deployment должны согласовать deployment ID и допустимую parity. Изменить список путей существующего set как произвольный RAID-массив нельзя. Перезапуск с прежними аргументами, замена отказавшего носителя и добавление нового pool — три разных операции.

В distributed варианте один и тот же полный список endpoints передают всем участникам; HTTP-путь обозначает область конкретного узла. Имена должны разрешаться с каждого узла, сертификаты покрывать эти имена, root credentials совпадать, системное время и версии программ согласовываться. Loopback 127.0.0.1 на другом узле обозначает уже другую машину. Наш исходный стенд имеет один процесс и один data; никакие команды далее не превращают его в четыре независимых узла.

Как выбирается pool новой записи

Для обычного выбора места реализация получает сведения о дисках того set, куда объект попал бы внутри каждого pool. Непригодные по доступному месту кандидаты получают нулевой вес; приостановленные и участвующие в исходящем rebalance pools исключаются из такого выбора. У оставшихся оценивается свободная ёмкость с учётом числа sets. Затем случайное число выбирает интервал весов: pool с большим пригодным свободным пространством получает больше новых записей. Это распределение запросов, не обещание точного чередования и не преобразование старых объектов.

Учебный пример: у A вес 20 GiB, у B 60 GiB. Из диапазона 0..79 интервалы 0..19 выбирают A, 20..79 — B: вероятности 1/4 и 3/4. Последовательность четырёх PUT не обязана дать ровно один A и три B. Реальные веса не равны сумме надписей на корпусах: сервер проверяет выбранные sets, доступность и резерв. Ключ существующего объекта, история в нескольких pools и data movement имеют дополнительные ветви; эту модель нельзя использовать как собственный router записей.

Почему расширение не является rebalance

При добавлении нового pool новые объекты могут начать занимать его, тогда как старые версии остаются в прежнем месте. Дисбаланс заполнения будет уменьшаться только по мере подходящих новых записей и удалений. Rebalance — отдельная фоновая операция перемещения существующего состояния. Decommission выводит выбранный pool из обслуживания и также требует переноса; это не синоним rebalance и не разрешение отключить диски сразу после ответа команды.

Для учебного изменения топологии сначала нужна отдельная VM-топология с собственными пустыми устройствами и сохранённым списком всех исходных endpoints. Одинаковые каталоги одного SSD могут проверить обработку аргументов, но теряют всё вместе при отказе SSD. Здесь не предлагается hot-plug, форматирование дисков или смена аргументов нашего сохраняемого стенда. Такой шаг выполняют после inventory устройств, проверенного резерва и отдельного расчёта failure domains.

С чего начинает rebalance выбранного поколения

Admin handler проверяет разрешение RebalanceAdminAction и направляет начало к первому узлу первого pool, чтобы согласовать параллельные запросы. На одном pool он отвечает NotImplemented. Одновременно выполняемый decommission и уже начатый rebalance дают отдельные отказы. Лишь после этих проверок получается список buckets и создаётся metadata операции.

В rebalance.bin сохраняются ID операции, целевая доля свободного места PercentFreeGoal и массив PoolStats. У записи pool есть исходные свободные байты InitFreeSpace, ёмкость InitCapacity, очередь Buckets, уже обработанные RebalancedBuckets, последний bucket/object, счётчики объектов/версий/байтов, Participating и Info со временем/статусом. Поля владельцем меняет сервер. Ручное удаление rebalance.bin ради исчезновения ошибки может оторвать управление от уже перенесённых данных.

Цель вычисляется как сумма свободных байтов / сумма ёмкостей в начале. Участниками исходящего переноса становятся pools с меньшей долей свободного места, чем цель. Например, A: ёмкость 100 GiB, свободно 20; B: 100 GiB, свободно 80. Общая цель 100/200 = 0.5; A должен освободить примерно 30 GiB, а B принять соответствующее кодированное содержимое. Это расчёт фиксированного состояния. Параллельные PUT/DELETE, размеры версий, metadata и проверки места меняют фактическое движение; доля не обязана стать ровно 50%.

StartRebalance запускает работу на первом узле участвующего pool. Внутри имеются workers, обход sets и периодическое сохранение progress. Сохранённый start ID подтверждает принятие задания, не чтение всех объектов и не окончание переноса. Статусы Started, Stopped, Completed и Failed описывают разные этапы; ответ stop инициирует отмену контекста, а не общую транзакцию rollback.

От списка имён к конкретным версиям

Обход получает metadata записей со своих online-дисков и разрешает частичные ответы. Listing quorum этого пути равен (N+1)/2 с целочисленным делением; это условие объединения списка, а не универсальный read quorum тела. Для N=4 получается 2. Обнаруженное имя ещё не доказывает, что последующее GetObjectNInfo получит пригодные K shards требуемой версии.

Список версий одного key обрабатывается в обратном порядке, чтобы построить стек истории у получателя. Для каждой версии учитываются version ID, время, пользовательская metadata и специальные состояния. Удалённая приложением версия может исчезнуть между listing и чтением; это допустимая гонка, а не повод создать другую версию по последнему GET. Перенесённые во внешний tier версии и lifecycle-expired объекты имеют отдельные ветви и могут пропускаться. Retention, replication и lifecycle нужно проверять до изменения, не после неожиданного отсутствия версии.

Один перенос тела: источник, получатель, удаление исходника

Обычный путь открывает reader конкретной version ID в исходном set. Этот reader выполняет проверки и реконструкцию из object IO. rebalanceObject передаёт поток PutObject с DataMovement=true и SrcPoolIdx, сохраняя version ID, MTime, пользовательскую metadata и ETag. Это не обычный клиентский PUT, который произвольно создаёт новую версию. Для multipart сохраняется структура частей: NewMultipartUpload, PutObjectPart для каждой части и CompleteMultipartUpload; неудачная незавершённая загрузка имеет собственную очистку.

Получатель проходит свой путь временных parts, checksums, metadata и публикации по endpoints. Он может получить ошибку чтения источника, недостаток места, write quorum или отмену. Следовательно, факт прочитанного исходника или вызова PutObject не даёт основания сразу удалить исходные bytes. Код повторяет отдельные попытки и различает disappeared version, конфликт data movement и настоящий отказ.

В rebalanceBucket счётчик rebalanced увеличивается после принятого пути версии. Исходный key со всем стеком удаляется оптимизированным DeletePrefixObject лишь при rebalanced == числу обнаруженных версий. При ошибке до этого условия исходная история не удаляется этой финальной ветвью. Это объяснение условия конкретного кода, не обещание общей атомарности между pools или отсутствия частичного размещения при падении процесса. Ошибка source cleanup после успешного переноса тоже возможна: обе копии требуют дальнейшего согласования сервером.

Delete marker передаётся как marker с прежними version ID/временем и data-movement опциями. Marker не имеет обычного тела для Reed–Solomon. Единственный оставшийся marker может обрабатываться без переноса payload. Поэтому число объектов, число версий и число перенесённых байтов нельзя считать одной величиной.

Как читать progress без ложной точности

В этом поколении rebalanceStats.update добавляет оценку on-disk size как fi.Size × (K+P) / K для обычной версии. Это арифметическая оценка кодированного размера; в ней нет точного округления каждого блока, hash headers, файловой metadata и device write amplification. Поле Bytes в rebalance status не обязано совпасть с S3 Content-Length и не является измерением реальных записей block device.

checkIfRebalanceDone сравнивает оценку (InitFreeSpace + Bytes) / InitCapacity с PercentFreeGoal и использует допуск 0.05. Это пять процентных пунктов доли, а не гарантия свободного резерва на всех дисках и не точный процент завершённых objects. CLI summary берёт максимальное elapsed/ETA среди pools; ETA остаётся оценкой. Нельзя из 0s to completion вывести отсутствие незавершённых IO или проверить пригодность всех старых версий.

Наблюдение на продолжаемом стенде

После успешной настройки прежнего стенда используйте второй терминал той же VM. alias lab имеет owner-доступ, TLS CA загружен через enter.sh. Следующие команды только читают состояние; output сохраняется в новом закрытом этапе. Если этап уже есть, сначала просмотрите прежний результат, не создавайте новую копию под тем же именем.

source "$HOME/minio-study/enter.sh"
cd "$LAB_ROOT"
begin_stage operations-v1 "$LAB_ROOT/exercises/operations-v1"
EX="$LAB_ROOT/exercises/operations-v1"
mkdir -- "$EX"
"${MC[@]}" --json admin info lab > "$EX/admin-info.private.json" 2> "$EX/admin-info.private.err"
"${MC[@]}" --help > "$EX/mc-help.txt"
"${MC[@]}" admin rebalance start --help > "$EX/rebalance-start-help.txt"
"${MC[@]}" admin rebalance status --help > "$EX/rebalance-status-help.txt"
finish_stage

admin info сообщает состояние deployment, не выполняет heal. JSON может содержать внутренние адреса и сохраняется приватно. Для нашего единственного pool start rebalance не является упражнением на перенос: handler отверг бы его до запуска. На отдельной принятой multi-pool топологии синтаксис start/status — mc [ROOT_FLAGS] admin rebalance start ALIAS и ... status ALIAS; root config-dir остаётся до admin. Сначала принимаются backup и capacity, затем составляется план изменения, а после start сверяются ID, per-pool status, ошибки и чтение выбранных версий. Не переносите команды такого плана в single-endpoint data.

Упражнение на бумаге: после переноса двух из трёх версий третья не читается из источника. Где существуют данные? Первые две могут быть опубликованы у получателя, третья остаётся только в источнике; условие финального удаления всего стека не выполнено. Повтор должен опираться на согласованные metadata/version и причины отказа, а не на копирование каталога xl.meta вручную. Healing исправляет части выбранного размещения; rebalance меняет pool. Они конкурируют за ресурсы, но решают разные задачи.

Точное поколение: pool space и выбор, admin checks/start, metadata, workers и перенос версий, start CLI, status counters.
