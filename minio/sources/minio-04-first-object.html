Первый объект должен пережить новый процесс

Сервер предыдущей главы уже работает в первом терминале. Этот маршрут выполняется во втором терминале той же VM.

Сначала проверяем готовность

Подключаем созданный enter.sh. Проверяем HTTPS с собственным CA и серверную готовность к записи. Открытый TCP-порт или ответ liveness сами по себе не доказывают доступность bucket и данных.

set -euo pipefail
source "$HOME/minio-study/enter.sh"
curl --fail --silent --show-error --connect-timeout 2 --max-time 5 \
  --cacert "$LAB_ROOT/tls/ca.crt" --output /dev/null \
  https://127.0.0.1:19000/minio/health/cluster

Ожидается код 0. При connection refused сначала проверяем процесс и listener, при certificate error — доверие, срок и IP в SAN, при HTTP 503 — состояние сервера. При любом отказе следующий изменяющий блок не выполняем.

Alias — сохранённое клиентское подключение

Alias lab связывает имя с endpoint, credentials и параметрами адресации. Они сохраняются в отдельном каталоге mc. API S3v4 выбирает подпись Signature Version 4. Path on требует адресацию с bucket в пути: https://127.0.0.1:19000/bucket/key. Для loopback не нужен отдельный DNS на каждый bucket.

В закреплённом mc alias set умеет прочитать access key и secret key из двух строк stdin, когда они не переданы аргументами. Так пароль не появляется в argv команды. Bash tracing для этого блока включать нельзя.

begin_stage root-alias
cat "$LAB_ROOT/secrets/root-user" "$LAB_ROOT/secrets/root-password" |
  "${MC[@]}" alias set --api S3v4 --path on lab https://127.0.0.1:19000 \
    > "$SETUP_STAGE/stdout.private" \
    2> "$SETUP_STAGE/stderr.private"
finish_stage

Ожидается успешное добавление alias с кодом 0. Это подтверждает настройку клиента, но ещё не доказывает запись объекта. config.json в mc содержит секретный материал и не включается в публичный экспорт.

Создаём bucket до объекта

Bucket создаёт клиент с соответствующими полномочиями. Versioning — хранение отдельных версий одного key. Включим его до первой загрузки: повторный PUT затем будет создавать новую версию, а не служить безобидным повтором проверки.

"${MC[@]}" mb lab/handbook-minio
"${MC[@]}" version enable lab/handbook-minio
"${MC[@]}" version info lab/handbook-minio

Все команды должны завершиться с кодом 0; info должен сообщить включённое versioning. При повторном прохождении bucket уже может существовать. Тогда не удаляем его и не добавляем --ignore-existing вслепую: возвращаемся к журналу своего состояния и проверяем, тот ли это проект. Отказ enabling versioning останавливает загрузку.

У входа и результата разные файлы

test ! -e "$LAB_ROOT/fixtures/manifest-v1.txt"
printf 'project=handbook-storage\nedition=1\n' \
  > "$LAB_ROOT/fixtures/manifest-v1.txt"

"${MC[@]}" cp "$LAB_ROOT/fixtures/manifest-v1.txt" \
  lab/handbook-minio/project/manifest.txt

"${MC[@]}" stat lab/handbook-minio/project/manifest.txt
"${MC[@]}" cat lab/handbook-minio/project/manifest.txt \
  > "$LAB_ROOT/downloads/manifest-first-read.txt"

cmp "$LAB_ROOT/fixtures/manifest-v1.txt" \
  "$LAB_ROOT/downloads/manifest-first-read.txt"

Первая строка fixture содержит 25 байт с LF, вторая — 10: stat должен показать size 35. Version ID выдаёт собственный сервер; готовый ID из книги не подставляется.

cp получает локальный файл и передаёт его серверу. stat запрашивает сведения об объекте; фиксируем размер и version ID собственного результата. cat читает тело обратно. cmp проверяет точное совпадение байтов и возвращает 0 только при совпадении. Успешный stat без cmp не доказывает, что возвращено требуемое содержимое.

Файл manifest-v1 остаётся эталоном, downloads — отдельной целью. Не загружаем результат поверх эталона и не удаляем предыдущую версию перед следующим упражнением. Если cmp сообщает различие, останавливаем дальнейшие изменения и исследуем размер, key, version ID и выбранный endpoint.

Новый процесс, прежние данные

В первом терминале останавливаем MinIO обычным Ctrl-C и ждём возврата оболочки. Каталоги остаются на диске. Затем запускаем тот же run-server.sh повторно с тем же data. Во втором терминале снова выполняем HTTPS health check и только после успеха читаем объект, не делая перед чтением нового cp.

"${MC[@]}" cat lab/handbook-minio/project/manifest.txt \
  > "$LAB_ROOT/downloads/manifest-after-restart.txt"
cmp "$LAB_ROOT/fixtures/manifest-v1.txt" \
  "$LAB_ROOT/downloads/manifest-after-restart.txt"

Критерий сохранения состояния: новый процесс возвращает те же байты из прежнего хранилища без повторной загрузки. Это ещё не backup/restore и не испытание отказа диска. Для проверки резерва позднее понадобится другая цель, собственная конфигурация доступа и доказательство восстановления требуемых версий.

Граница с Go-клиентом

Позже этот же bucket будет использовать общий object-study из s3/labs/object-client. Сначала установим и проверим этот helper по его инструкции и создадим ограниченный прикладной доступ. Профиль MinIO будет явно задавать backend=minio, endpoint=https://127.0.0.1:19000, region=us-east-1, bucket=handbook-minio и path-style addressing, а также собственный credentials profile и CA. Root credentials в Go-сервис не передаём.

Общий клиент сравнивает наблюдаемое S3-поведение, но не обещает одинаковые server-side guarantees MinIO, RGW и AWS. Если helper не поддерживает отдельный CA или обязательную операцию этого опыта, сначала дорабатывается и проверяется его договор; параметры не угадываются по похожей CLI.

Источники: server health semantics, alias set и stdin credentials, создание bucket, команды versioning.
