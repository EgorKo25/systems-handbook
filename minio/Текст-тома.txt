Зачем приложению отдельный сервер

Представим сервис, который принимает документы. В сетевом запросе приходят
байты документа и несколько описательных полей. Сервис может записать
их в собственный каталог, но тогда ему придётся самостоятельно решить,
кто получает доступ, как искать документы по имени, что означает
повторная загрузка и как другой экземпляр приложения прочитает тот же
результат. Объектный сервер переносит эти обязанности за отдельный
сетевой интерфейс.

Метаданные — сведения об объекте, например тип содержимого,
размер и служебные параметры. Они описывают объект, но не заменяют
его тело с пользовательскими байтами.

Объект — именованное содержимое вместе с метаданными. Содержимое
называют body, то есть телом объекта. Bucket — область имён и правил,
которую создаёт владелец доступа. Key — строковое имя внутри bucket.
Например, у bucket handbook-minio может быть key
project/manifest.txt. Косая черта помогает группировать
имена по префиксу; она не обещает файловую систему с каталогами,
блокировкой файлов и атомарным переименованием дерева.

Как клиент обращается к MinIO

HTTP — протокол обмена запросом и ответом. Клиент открывает соединение к адресу и порту endpoint, например https://127.0.0.1:19000. Схема https означает HTTP внутри TLS: сначала проверяется сертификат сервера и защищается соединение. Метод PUT просит записать тело, GET — прочитать его, HEAD — получить сведения без тела ответа, DELETE — изменить состояние удаления. URL path выбирает bucket/key при используемой здесь адресации с bucket в пути.

Заголовки — именованные поля сообщения. Content-Type описывает содержимое, Content-Length задаёт число bytes тела; пользовательские поля объекта передаются с префиксом x-amz-meta-. Авторизация S3 Signature Version 4 связывает выбранные метод, путь, заголовки и hash тела с credentials клиента. Сервер MinIO отдельно проверяет эту подпись и policy. TLS-доверие к серверу не даёт клиенту права записывать любой key.

Например, проекция нашего будущего PUT имеет метод PUT и путь /handbook-minio/project/manifest.txt, тип text/plain и Content-Length 35. Следом идут 35 bytes fixture с двумя LF. SDK или mc строят полный подписанный HTTP-запрос; эта проекция не является готовой командой с пропущенным secret. Ответ содержит HTTP status и служебные поля. Успешный PUT и полученные metadata затем проверяются отдельным GET и побайтовым сравнением.

Health endpoint /minio/health/cluster — другой запрос того же сервера: он помогает проверить готовность выбранного серверного пути, но не читает наш объект. Если ответ потерян по timeout, клиенту неизвестно, успел ли сервер закрепить PUT. Эту неоднозначность позже рассматриваем вместе с версиями, не выводим отсутствие объекта из отсутствия ответа.

MinIO Server — процесс, который принимает поддерживаемые S3-запросы
и управляет собственным форматом хранения. mc — отдельная
клиентская программа: она отправляет запросы серверу и может работать
также с локальными файлами. Go SDK — библиотека, которую разработчик
включает в приложение. SDK не заменяет процесс хранения. Если приложение
завершилось, долговечность объекта определяется сервером и его
хранилищем, а не существованием Go-структуры в памяти.

Две линии, которые нельзя смешивать

Официальные источники проверены повторно 2 ноября 2026 года. Исходный MinIO OSS
под AGPLv3 больше не сопровождается. Репозиторий Server архивирован
25 апреля 2026 года, репозиторий mc — 14 июля. Сохранённый исходный код
можно изучать и собирать на условиях его лицензии, но наличие исходников
не означает наличие будущего исправления уязвимости.

В этом томе основной воспроизводимый учебный маршрут закреплён за

Нельзя добавить переменную окружения и считать архивный OSS-сервер

Рабочее состояние располагается в
$HOME/minio-study. Сначала получим исходники и соберём
две программы. Затем создадим собственное доверие TLS, запустим сервер
на loopback, установим клиентский доступ и сохраним первый объект.
Дальше у того же проекта появятся версии, отдельный прикладной доступ,
преднамеренные ошибки и восстановление на другую цель. Каждая глава
продолжает предыдущее состояние. Команды автоматического reset здесь нет.

Математика erasure coding объясняется на явно заданных наборах
дисков. Начальный сервер использует одну область хранения и не имеет
избыточности. Его успешный GET не будет выдаваться за испытание кластера,
а несколько каталогов одного SSD — за несколько независимых дисков.

Модель HTTP, подписи SigV4 и базовые состояния объектов подробно
разобраны в томе S3. Здесь мы
прослеживаем конкретный сервер: как он выбирает erasure set, записывает
shards и metadata, проверяет quorum и возвращает ответ.

Как продолжать после первого объекта

После настройки сначала отделим прикладной доступ и историю версий, затем проследим запись и чтение конкретной реализации: object IO. Номер 08 не задаёт порядок чтения: этот механизм предшествует healing/scanner. Далее изучим изменение pools, операционные отказы, восстановление отдельной копии и стоимость ресурсов. Самостоятельный опыт заканчивается чтением восстановленных bytes и выбранных версий, не наличием запущенного процесса.

Metadata участвует в сохранении объекта

Storage endpoint — адрес области хранения, переданной серверу:
например, локальный путь или URL пути на другом узле. Путь обозначает
место подключения, устройство хранит байты, узел исполняет процесс.
Один узел может обслуживать несколько endpoints, а несколько путей
могут находиться на одном физическом устройстве.

Числа кворума ниже являются необходимыми численными условиями для
обычной непустой версии. Они не гарантируют успешное чтение без
доступной сети, пригодных shards и согласованной metadata выбранной
версии. Полезная доля ёмкости равна K/N, коэффициент расхода — N/K;
metadata, округление, небольшие объекты и внешние tiers в эту идеальную
оценку не входят.

Где заканчивается запрос клиента

Клиент передаёт адрес сервера, bucket, key, заголовки и тело.
TLS сначала защищает соединение и позволяет клиенту проверить личность
сервера. Затем сервер проверяет поддерживаемую подпись и полномочия
операции. Наличие правильной подписи не означает разрешение записывать
в любой bucket: подпись устанавливает связь запроса с credentials,
а политика ограничивает допустимые действия.

После этих проверок объектный слой выбирает место хранения.
Pool — группа ресурсов, добавленная серверу как единица размещения.
Внутри pool находятся erasure sets. Erasure set — устойчиво заданная
группа endpoints, между которыми кодируется одна версия объекта.
Диск, входящий в другой set, не становится автоматически дополнительным
ответчиком для quorum текущего объекта.

В простом стенде один pool и один set, поэтому выбора между группами
нет. В более сложной конфигурации сервер отдельно выбирает pool,
а внутри него получает индекс set из имени объекта. В закреплённом
коде GetObjectNInfo передаёт object в getHashedSet; алгоритм зависит
от формата deployment. Поэтому нельзя обещать, что произвольный
самописный CRC по строке bucket/key воспроизведёт размещение
современного deployment.

Что кодируется

Пусть в set находятся N endpoints. Для выбранной версии объекта
сервер использует K data shards и P parity shards, причём N=K+P.
Shard — фрагмент кодированного представления. Data shards содержат
разделённые данные; parity shards содержат математическую
избыточность. Это не P полных резервных копий файла.

Реализация использует Reed–Solomon. При наличии любых K пригодных
shards одной кодированной версии можно восстановить её данные.
«Пригодных» означает не только доступных по сети: важны целостность
фрагмента и согласованная metadata. Повреждённый shard, который не
проходит проверку, нельзя засчитать как ещё один корректный ответ.

Для большого объекта полезная доля сырой ёмкости приблизительно
равна K/N, а коэффициент записи — N/K. При K=4 и P=4 доля равна
половине, а кодированное содержимое занимает примерно двойной объём.
Это оценка без файловой metadata, checksums, округления блоков,
старых версий, незавершённых multipart uploads и свободного места
для дальнейшей работы.

Числа относятся к конкретному поколению

В Server RELEASE.2025-10-15T17-29-55Z функция DefaultParityBlocks
для новой конфигурации выбирает 0 при одном endpoint, 1 при двух
или трёх, 2 при четырёх или пяти, 3 при шести или семи и 4 для
остальных допустимых размеров set. Поэтому утверждение «по умолчанию
всегда половина дисков» для этой функции неверно. Старый текст
docs/erasure/README.md ещё содержит такое упрощение.

Следующая таблица описывает обычный непустой объект, полностью
созданный при доступных endpoints. Нет tiering, delete marker,
явно изменённого storage class и изменения parity при деградации.

 | N | P | K | Полезная доля
 | Read quorum | Write quorum этого layout

 | 4 | 2 | 2 | 50% | 2 | 3

 | 8 | 4 | 4 | 50% | 4 | 5

 | 16 | 4 | 12 | 75% | 12 | 12

 | 16, явно EC:8 | 8 | 8 | 50% | 8 | 9

Quorum — минимальное достаточное число согласованных ответов.
Для рассматриваемого объекта read quorum равен K. Write quorum равен
K, кроме симметричного случая K=P: тогда требуется K+1. При восьми
endpoints четыре сохранившихся shards могут позволить чтение старой
версии, но для записи с layout 4+4 недостаточно четырёх ответов.
Дополнительный голос не позволяет двум изолированным половинам
такого set независимо подтверждать запись.

Почему новая запись при отказах может получить другой layout

Storage class — выбранное правило избыточности новой записи.
Tier — другое хранилище, куда сервер может перенести тело объекта.
Inline data — небольшое тело, сохранённое вместе с metadata.
Эти варианты требуют собственных ветвей расчёта.

Режим availability в закреплённой реализации предпочитает сохранить
доступность новых записей: при заранее недоступных endpoints он может
увеличить число parity shards. Например, при N=16, исходном P=4 и
четырёх недоступных endpoints новый обычный PUT может получить P=8,
K=8 и write quorum 9. Уже сохранённые версии от этого не меняются.
Это уточнение не относится к исходному расчёту здорового set.

1. Все доступны

Четыре пригодных endpoints превышают оба порога.

Действует: Server.

Клиент: запрос; Server: считает ответы; Set 4: 4 online; Read: 4 ≥ 2; Write: 4 ≥ 3

Пригодные ответы: нет запроса → 4. Все endpoints отвечают согласованно.

2. Потерян один endpoint

Остаётся три; чтение и запись ещё имеют quorum.

Действует: Отказ устройства.

Клиент: повторный запрос; Server: учитывает отказ; Set 4: 3 online; Read: 3 ≥ 2; Write: 3 ≥ 3

Доступность: 4 → 3. Один endpoint перестал давать пригодный ответ.

3. Потерян второй endpoint

Два shards достаточны для чтения этой версии, но не для подтверждения записи 2+2.

Действует: Server.

Клиент: GET или PUT; Server: разделяет решения; Set 4: 2 online; Read: 2 ≥ 2: возможно; Write: 2 < 3: отказ

Ответ: обе операции возможны → read возможно, write отказ. Пороги операций различаются.

4. Остаётся один

Одного shard меньше K: эта модель больше не может восстановить тело.

Действует: Server.

Клиент: GET; Server: не придумывает данные; Set 4: 1 online; Read: 1 < 2: отказ; Write: 1 < 3: отказ

Пригодные shards: 2 → 1. Недостаточно данных для декодирования.

Восемь мегабайт на восьми endpoints

Возьмём учебную версию длиной 8 MiB, N=8, K=4, P=4. Для расчёта
зададим блок кодирования 1 MiB. Каждый блок делится на четыре
фрагмента по 256 KiB, затем вычисляются четыре parity-фрагмента
такого же размера. В объекте восемь блоков. Один endpoint получает
8×256 KiB=2 MiB shard data, все восемь — 16 MiB. Контрольные суммы
и metadata добавят собственный расход.

Формула размера одного shard в этом расчёте:
floor(S/B)×ceil(B/K)+ceil((S mod B)/K), где S — длина объекта,
B — размер блока. Она объясняет, почему для произвольного размера
и K результат нельзя всегда заменить ровно S/K.

При отказе одного endpoint остаются семь пригодных shards:
старую версию можно читать. При отказе ещё двух остаются пять,
что всё ещё достаточно для чтения и write quorum 5 этого layout.
При четырёх потерях остаются четыре: данные старой версии ещё
восстановимы при пригодной metadata, но запись 4+4 не получает
quorum. Пятая потеря оставляет три shards: этого меньше K.

Размещение определяет, сколько shards исчезнет при одном отказе.
Если восемь endpoints — каталоги одного SSD, отказ этого SSD
оставит ноль доступных shards. Если четыре endpoints находятся
на одном узле, потеря узла оставит четыре. Для рассмотренной версии
с K=4 и P=4 этого численно достаточно для чтения при согласованных
метаданных и исправных shards, но недостаточно для write quorum 5.
Такую группу ресурсов с общей причиной отказа называют failure
domain, или областью отказа. При выборе дисков и узлов нужно
проверять, сколько endpoints теряет каждая такая группа.

При S = 1 MiB + 1 байт, N=8, K=4, P=4 и B=1 MiB каждый shard содержит 262144 + ceil(1/4) = 262145 байт payload; все восемь — 2097160 байт до checksums и metadata. Последний блок добавил восемь сохранённых байт ради одного нового байта тела: деление и округление выполняются по блокам.

Metadata участвует в сохранении объекта

Сервер хранит сведения о версии и её кодировании: размеры,
время, distribution, K/P, checksums и другие поля. В выбранном
формате используется xl.meta. Данные небольшой версии могут быть
встроены в этот файл; более крупные parts могут находиться в каталоге
данных версии. Поэтому даже на одиночном диске object key не следует
понимать как обычный файл с теми же байтами.

PUT проходит через временную запись кодированных частей,
формирование metadata и операцию закрепления результата на
достаточном числе endpoints. Успех клиенту возвращается после
успешного серверного пути. Чтение собирает metadata, определяет
пригодную версию и quorum, выбирает доступные shards и при
необходимости восстанавливает отсутствующие данные.

Если клиент получил timeout, он знает только, что вовремя не получил
однозначного ответа. Сервер мог не закончить запись, а мог закончить
её и потерять соединение до доставки ответа. При включённом
versioning слепой повтор способен создать ещё одну версию. Позднее
мы будем сверять version ID, размер и собственный хеш содержимого;
ETag безусловным MD5 не считаем.

Ресурсы учебного профиля

Для машины с 8 GiB RAM предлагается одна личная VM с 2 vCPU,
4 GiB RAM и хотя бы 20 GiB свободного диска. На машине с 16 GiB
можно выделить VM 6–8 GiB RAM и 2–4 vCPU. Это предлагаемый бюджет
для небольшого учебного потока, а не проверенный vendor minimum.
Сборку и нагрузку сначала выполняем последовательно. Остальные
тяжёлые серверы книги в это время останавливаем.

Начальный профиль имеет один процесс MinIO и один каталог данных.

или VM. Для физического erasure-опыта понадобятся отдельные устройства

не создаёт.

Рецепт предназначен для личной Linux amd64 VM с правом записи. При подготовке книги загрузка, сборка и native help не исполнялись; ниже отделены ожидаемые результаты читательского запуска от проверок источников.

Почему HTTPS требует доверия

TLS шифрует сетевой обмен и позволяет проверить, к какому серверу
обратился клиент. Сертификат связывает открытый ключ с именем или IP.
CA — удостоверяющая сторона, которой клиент доверяет подтвердить
эту связь. Для изолированного опыта создадим собственный CA,
а затем подпишем им сертификат localhost и 127.0.0.1. Установка
этого CA в системное хранилище VM не требуется.

begin_stage tls \
  "$LAB_ROOT/secrets/ca.key" \
  "$LAB_ROOT/tls/ca.crt" \
  "$LAB_ROOT/tls/ca.srl" \
  "$LAB_ROOT/tls/private.key" \
  "$LAB_ROOT/tls/server.csr" \
  "$LAB_ROOT/tls/server.ext" \
  "$LAB_ROOT/tls/public.crt" \
  "$LAB_ROOT/mc/certs/CAs/study-ca.crt"

openssl req -x509 -newkey rsa:3072 -nodes -sha256 -days 30 \
  -keyout "$LAB_ROOT/secrets/ca.key" -out "$LAB_ROOT/tls/ca.crt" \
  -subj '/CN=MinIO study CA' \
  -addext 'basicConstraints=critical,CA:TRUE' \
  -addext 'keyUsage=critical,keyCertSign,cRLSign'

openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -keyout "$LAB_ROOT/tls/private.key" -out "$LAB_ROOT/tls/server.csr" \
  -subj '/CN=localhost'

cat > "$LAB_ROOT/tls/server.ext" <<'EXT'
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:localhost,IP:127.0.0.1
EXT

openssl x509 -req -in "$LAB_ROOT/tls/server.csr" \
  -CA "$LAB_ROOT/tls/ca.crt" -CAkey "$LAB_ROOT/secrets/ca.key" \
  -CAserial "$LAB_ROOT/tls/ca.srl" -CAcreateserial -days 30 -sha256 \
  -extfile "$LAB_ROOT/tls/server.ext" -out "$LAB_ROOT/tls/public.crt"

openssl verify -CAfile "$LAB_ROOT/tls/ca.crt" \
  -verify_ip 127.0.0.1 "$LAB_ROOT/tls/public.crt"
openssl verify -CAfile "$LAB_ROOT/tls/ca.crt" \
  -verify_hostname localhost "$LAB_ROOT/tls/public.crt"

байтов и возвращает 0 только при совпадении. Успешный stat без cmp
не доказывает, что возвращено требуемое содержимое.

версию перед следующим упражнением. Если cmp сообщает различие,
останавливаем дальнейшие изменения и исследуем размер, key,
version ID и выбранный endpoint.

Credentials отвечают за личность, policy — за допустимые действия

Access key — идентификатор доступа, secret key — секрет для подписи
запросов. Policy — документ с разрешёнными действиями и ресурсами.
Service account — отдельная пара credentials, связанная с parent
account. В выбранном поколении его embedded policy дополнительно
сужает права parent; она не должна расширять их.

В этом опыте parent study-admin является root owner сервера.
Закреплённый код распознаёт такой service account как owner-derived:
права parent разрешены по умолчанию. Затем embedded session policy
ограничивает действия самого service account. При её проверке
признак owner снимается, поэтому приложение получает только
перечисленные разрешения. Для service account обычного пользователя
код дополнительно проверяет действующие права parent.

Приложению разрешим читать, записывать и перечислять объекты только
в handbook-minio. Оно не сможет создавать bucket, удалять объекты,
менять IAM или перечислять все buckets сервера. Звёздочка в Resource
ниже охватывает имена объектов одного bucket; Action wildcard нет.

Почему mc cat требует отдельного действия чтения версии

Обычный SDK GET /bucket/key без versionId проверяется как
s3:GetObject. Закреплённый mc cat сначала получает metadata,
запоминает обнаруженный version ID и затем делает GET с versionId.
Для такого запроса требуется s3:GetObjectVersion. Это объясняет
добавление конкретного action; расширять policy до s3:* ради
исчезновения ошибки не нужно.

Три разных действия над одним key

При включённом versioning новый PUT создаёт новую версию.
Version ID выдаёт сервер; клиент сохраняет его как идентификатор
результата. Предыдущая версия остаётся noncurrent — не текущей,
но всё ещё существующей.

DELETE без versionId создаёт delete marker — текущую отметку
удаления. Обычное чтение key больше не возвращает прежнее тело,
хотя старые версии могут оставаться доступными по ID. DELETE с
конкретным versionId удаляет выбранную версию или выбранный marker.
Это другое действие с другой судьбой данных.

 | Шаг | Текущий результат | Что сохраняется

 | Первый PUT | V1 | Тело V1

 | Второй PUT | V2 | Тела V1 и V2

 | DELETE без ID | Marker M | V1, V2 и M

 | Удалить именно M | Снова V2 | V1 и V2; M удалён

V1/V2/M в таблице — обозначения, не готовые ID для копирования.
В опыте используются только ID собственного сервера. Удаление
marker не отменяет произвольные записи после контрольной точки.

Timeout записи не является ответом «объект не сохранён»

Представим PUT с operation ID O. Клиент отправил тело, сервер
закрепил новую версию V3, но ответ потерялся. Клиент завершился
по deadline. Он знает, что не получил подтверждение, но не знает,
закончилась ли запись до разрыва соединения.

Новый PUT того же тела в versioned bucket способен создать V4.
Даже при одинаковых байтах это другая версия. Retry внутри SDK
также входит в этот анализ; один вызов прикладного метода не
обязательно равен одному HTTP-запросу.

Для воспроизводимого исследования до отправки сохраняют намерение:
endpoint identity, bucket/key, operation ID, длину и собственный
SHA-256 тела. Operation ID передают как
x-amz-meta-operation-id. Это metadata для сопоставления, а не
серверный ключ идемпотентности.

После неоднозначного исхода сначала прекращаются зависимые
изменения. Перечисляются все версии нужного key, с учётом пагинации
и delete markers. Кандидат проверяется по metadata operation ID,
затем читается по конкретному version ID и сравнивается с исходными
байтами. Обычный HEAD текущего key недостаточен: другой writer мог
создать более новую версию, а DELETE — текущий marker.

 | Наблюдение | Допустимый вывод

 | Один кандидат O, совпали байты | Найдена сохранённая версия намерения; фиксируем её ID

 | Несколько совпавших версий O | Есть дубли; exactly-once не достигнуто

 | Совпал O, байты другие | Нарушен договор намерения; остановка и расследование

 | Кандидат пока не найден | Нет подтверждения в данном наблюдении; это не доказательство, что старый запрос уже не сможет завершиться

Отсутствие кандидата разрешает автоматический retry только при
дополнительном прикладном договоре: например, заранее выбранном уникальном key
с проверенным create-only либо согласованном durable журнале
операций. В повторах одного намерения сохраняются тот же key,
operation ID и исходные bytes; новый key каждой попытки создаёт другой
объект. После unknown или 412 сначала ищут результат. Create-only
сам по себе не обеспечивает exactly-once. Политика повторов не выводится из одного timeout.

Как читать exit code и receipt object-study

В согласованном v1 exit 0 означает подтверждённый результат,
2 — validation до отправки, 3 — явный отказ сервиса, 4 —
transport/deadline/cancel с неизвестным исходом PUT, 5 — локальный
I/O, integrity либо final commit failure. Эти коды ещё требуют
проверки реализации на настоящем сервере.

Exit code описывает причину завершения, outcome — подтверждённость серверной операции. Код 3 может сочетаться с unknown: предыдущая попытка могла записать объект, повтор получил 412. По консервативному SPEC v1 неуспешный PUT после HTTPClient.Do имеет unknown. Ошибка открытия или предварительного хеширования source до отправки означает rejected. Код 5 возможен после подтверждённого PUT: ошибка закрытия локального source не отменяет серверную запись. При GET ошибка fsync каталога после hard link может оставить полное конечное имя; повтор поверх него запрещён.

Helper добавляет подписанный x-amz-meta-operation-id и возвращает
operation_id в очищенном receipt. Но процесс может погибнуть до
receipt; тогда ID может быть утрачен. В v1 не обещаны durable intent
journal и exactly-once. Нельзя описывать receipt как уже существующую
защиту от всех неоднозначных исходов.

HTTP-handler читает поток, а не получает готовый файл

PutObjectHandler получает bucket и key из URL,
проверяет Content-Length, поддерживаемые заголовки, подпись и право
PutObject. Ветка обычного запроса берёт тело из r.Body.
Это поток чтения: байты ещё могут приходить по сети, когда сервер
уже обработал их начало.

Handler оборачивает поток в hash.Reader. При чтении
тот считает длину и требуемые контрольные суммы. Если клиент передал
проверяемую контрольную сумму, несовпадение возвращается как ошибка чтения.
Часть проверок завершается при EOF — признаке конца входного потока.
Поэтому получение последнего сетевого пакета ещё не означает, что
сервер принял весь объект. Подготовленный PutObjReader передаётся
в объектный слой вместе с параметрами версии и пользовательскими
метаданными.

Метаданные запроса, например Content-Type и operation-id,
хранятся в серверных структурах в RAM до формирования записи версии.
Условие If-Match или If-None-Match превращается в проверку текущего
объекта. Для такого PUT код берёт блокировку имени до проверки.
Безусловный PUT может сначала кодировать тело во временную область,
а блокировку bucket/key получить перед добавлением V в метаданные объекта.
UUID — генерируемый 128-битовый идентификатор. Отдельный временный UUID
каждой записи задаёт ей собственное имя каталога.

Источники:
PutObjectHandler,
проверки Reader.Read,
условия и ранняя блокировка.

Pool, set и номер shard выбираются разными действиями

В модели с одним pool запрос сразу попадает в него. При нескольких
pools код сначала проверяет сведения о существующем объекте и ошибки
его поиска. В обычной ветви PUT он может выбрать pool для новой записи
через getAvailablePoolIdx. Выбор учитывает доступное место
и состояние pools; среди пригодных вариантов используется случайный
выбор с весом доступной ёмкости. Поэтому правило «все версии key
навсегда лежат в одном pool» из этой функции не следует.

Внутри выбранного pool функция getHashedSet(object)
выбирает set. Используется алгоритм из формата deployment:
в закреплённом коде есть CRCMOD и варианты SIPMOD. В нашем примере
set один. Сервер получает его список StorageAPI — интерфейсов
к областям хранения. Для локального диска операция исполняется
в его storage-реализации; удалённый endpoint обслуживает процесс
соответствующего узла. Клиентский S3 URL указывает на принимающий
сервер, а storage endpoint обозначает область хранения внутри
серверной топологии.

Отдельная перестановка distribution задаёт номера shards на
позициях endpoints. newFileInfo получает
handbook-minio/project/manifest.txt и вызывает
hashOrder для N=4. Для этой строки CRC32 равен
0x87b9ae59, остаток деления на 4 равен 1,
distribution получается [3,4,1,2].
E1 получает shard 3, E2 — shard 4, E3 — shard 1, E4 — shard 2.
Для кодера/декодера порядок endpoints становится
[E3,E4,E1,E2].

Этот расчёт distribution использует полный bucket/key,
переданный в newFileInfo. Индекс set выше вычислялся другим вызовом
и с другим назначением. При последующем чтении distribution берётся
из метаданных выбранной версии, чтобы номер полученных байтов
оставался известен даже после изменения текущих настроек.

Источники:
взвешенный выбор pool,
getPoolIdx,
выбор set,
newFileInfo,
hashOrder.

Какие сведения нужны одной версии

putObject выбирает K и P для новой записи,
создаёт version ID при включённом versioning и отдельный UUID
DataDir. Version ID идентифицирует версию S3, DataDir называет
серверную область её данных; эти UUID не обязаны совпадать.
Ещё один UUID U именует временную операцию.

 | Поле в FileInfo | Смысл в этом PUT

 | VersionID | Идентификатор V, который позднее вернётся клиенту.

 | DataDir | Имя T каталога данных; для inline отдельный каталог с телом не требуется.

 | Erasure.DataBlocks / ParityBlocks | K=2 и P=2 для этой версии.

 | Erasure.BlockSize | Размер B входного блока кодирования.

 | Erasure.Distribution / Index | Перестановка endpoints и номер shard данного участника.

 | Parts | Номера и размеры частей; у рассматриваемого single PUT один part 1.

 | Size / ModTime / Metadata | Принятый размер, время версии и поля вроде Content-Type и ETag.

 | Data | Буфер кодированных inline-байтов данного участника, если выбран inline-путь.

На этом шаге FileInfo и массив отдельных FileInfo по endpoints
находятся в RAM. В сериализованном xlMetaV2Object поля ErasureM и
ErasureN сохраняют соответственно K и P; обозначение N в математике
главы означает их сумму. Номер Index и shard data у участников
разные, хотя VersionID, размеры parts, K/P и distribution должны
описывать одну версию.

При K=P=2 write quorum W равен 3. Для обычной data version
формула W=K, а при K=P добавляется один ответ. При отказах,
уже обнаруженных до выбора layout, режим availability может повысить P;
это разобрано в главе о модели.
Здесь отказ E4 произойдёт позднее, поэтому исходный layout 2+2
остаётся тем же.

Части, blocks, chunks и контрольные суммы

У новой версии newFileInfo задаёт
B=1 048 576 байт, то есть 1 MiB. Erasure.Encode
читает до B входных байтов, вызывает Split и Encode библиотеки,
затем передаёт N фрагментов writers. Split делает K последовательных
data shards одинаковой длины ceil(L/K), то есть L/K с округлением
вверх до целого, где L — фактическая длина данного блока; недостающие байты последнего data shard дополняются
нулём. Такое дополнение называется padding. Исходная длина
позволит исключить эти нули при GET. Parity вычисляется для
дополненных данных.

У body длиной 2 MiB+1 будут два полных блока и один блок длиной
1 байт. При K=2 каждый полный блок даёт по 524 288 байт на shard,
последний — по 1 байту. Payload здесь — кодированные байты
без контрольных сумм и метаданных. Каждый endpoint должен получить
1 048 577 байт shard payload. Весь набор из четырёх shards
содержит 4 194 308 таких байтов: data с одним байтом padding
и parity той же суммарной длины.

Bitrot writer защищает каждый переданный фрагмент отдельно.
Chunk — фрагмент одного shard за проход кодирования. Hash —
контрольное значение, вычисленное из его байтов. Для выбранного
HighwayHash256S перед chunk записывается 32-байтовый hash,
затем payload chunk. Получается поток
hash0 | chunk0 | hash1 | chunk1 | hash2 | chunk2.
В примере это 96 байт hashes на endpoint, 384 на четыре.
Полный расход четырёх shard-потоков —
4 194 692 байта до xl.meta, каталогов и распределения блоков filesystem.

Это вычисленные длины. Полезные байты HTTP body, shard payload,
hashes и выделенные filesystem блоки учитываются раздельно.
При успешной записи только на трёх endpoints фактический расход
также зависит от того, сколько временных байтов успел записать
четвёртый и удалось ли их убрать.

В RAM используются буферы входных blocks, кодированных shards,
metadata и записи к storage. Большой body не требуется целиком
держать в одном Go slice; код обрабатывает его блоками и может
использовать read-ahead. Из B нельзя вывести общий расход RAM:
одновременно существуют буферы нескольких путей и нескольких запросов.

Источники:
blockSizeV2,
Encode,
NewErasure, EncodeData и ShardFileSize,
Split зависимости v1.12.4,
потоковый bitrot writer,
DefaultBitrotAlgorithm.

Записанные chunks ещё не являются опубликованной версией

Если тело хранится отдельно от xl.meta, далее назовём этот путь
non-inline. Его writer создаёт временные данные под
.minio.sys/tmp/U/T/part.1 на соответствующем endpoint.
U относится к операции, T — к DataDir версии. Фоновый writer
читает данные из буфера, а storage CreateFile создаёт файл
с запретом заменить уже существующий файл. В закреплённой
writeAllDirect после копирования проверяется записанная длина,
выполняется Fdatasync и проверяется результат Close. Fdatasync
запрашивает у ОС синхронизацию данных файла и необходимых для них
служебных сведений. Фактическая устойчивость при пропадании питания зависит также
от filesystem и контроллера накопителя.

multiWriter запоминает ошибку каждого writer.
Неисправный writer исключается из следующих проходов. Для каждого
блока Encode должен сохранить write quorum; после Encode
putObject закрывает writers и отдельно проверяет
quorum возвращённых результатов Close. Затем проверяется, что прочитано не меньше
заявленной длины body. Ошибка hash.Reader тоже прерывает Encode.
До этих проверок сервер не переходит к RenameData.

Допустим, E4 перестал принимать данные, а E1, E2 и E3 успешно
дописали и закрыли свои потоки. W=3 выполнен. Данные на этих
трёх endpoints пока находятся во временной области; наличие там
байтов ещё не добавило V в публичный xl.meta объекта.
Сервер заканчивает FileInfo: записывает размер part, время,
метаданные и сведения о версии.

Для non-inline part streamingBitrotWriter.Close сначала
закрывает промежуточный writer, затем ждёт завершения фонового
вызова CreateFile. Внутри CreateFile функция writeAllDirect
проверяет длину и возвращает ошибки Fdatasync и Close файла.
Однако streamingBitrotWriter.Close сохраняет результат закрытия
промежуточного writer до ожидания и после Wait возвращает именно
его; результат CreateFile после ожидания он заново не читает.
Поэтому ожидание CreateFile само по себе не доказывает, что каждая
поздняя ошибка Fdatasync или Close попадёт в close quorum.
Затем общий код вызывает RenameData на участниках: данные и метаданные
публикуются по отдельным endpoints, после чего возвращённые результаты
сопоставляются с write quorum.

Источники:
multiWriter,
streamingBitrotWriter.Close,
Flush и закрытие ring buffer,
temporary writers, close и FileInfo,
CreateFile и writeAllDirect.

Разобрать по шагам

Временные chunks, публикация V и последующий GET

Проследите одну условную версию V. Сначала E4 теряется во время PUT; после принятия V повреждается chunk на E3.
Условия этого примера

Один pool и один set; N=4, K=2, P=2, W=3, R=2. Single PUT, S=2 MiB+1, B=1 MiB, non-inline. Layout выбран до отказа E4. Distribution [3,4,1,2]: E1/E2 хранят parity, E3/E4 — data. Для GET metadata V на E1/E2 согласованы, их chunks исправны. В этом GET reader E3 был вызван и обнаружил ошибку hash. Каждый endpoint в модели находится на отдельном физическом диске своего узла. Это модель, не топология запущенного стенда.

1. Запрос принят к обработке

Handler проверил запрос. V и T созданы в RAM; новая версия ещё не опубликована.

Действует: MinIO PUT.

S3-клиент: отправляет body; HTTP / ObjectLayer: проверки запроса пройдены; Erasure + bitrot: готов читать blocks; Временная область: новые потоки ещё не закончены; Описание V: FileInfo V в RAM; E1 / E2 / E3 / E4: V ещё нет в публичном xl.meta

Состояние V: нет новой версии → подготовлена в RAM. Создание VersionID не равнозначно публикации на storage.

2. Encode и close прошли на трёх endpoints

E4 отказал после выбора layout. E1/E2/E3 сохранили chunks во временной области; W=3 выполнен для этого этапа.

Действует: Erasure writers.

S3-клиент: ещё ждёт ответ; HTTP / ObjectLayer: ещё не вернул ObjectInfo; Erasure + bitrot: Encode и close quorum приняты; Временная область: E1/E2/E3 готовы; E4 ошибся; Описание V: размеры и metadata V заполнены; E1 / E2 / E3 / E4: публичная V ещё не добавлена

Пригодные временные потоки: пишутся → 3. Проверка этих writers предшествует RenameData.

3. V опубликована

DataDir и xl.meta опубликованы на E1/E2/E3. Код принял write quorum RenameData.

Действует: RenameData.

S3-клиент: ещё может не получить ответ; HTTP / ObjectLayer: ObjectInfo V подготовлен; Erasure + bitrot: кодирование завершено; Временная область: пригодные данные перемещены; Описание V: xl.meta с V на трёх endpoints; E1 / E2 / E3 / E4: E1:shard3; E2:shard4; E3:shard1; E4:нет V

Публикации V: 0 → 3, W=3. Участники публикуют отдельно; четвёртый endpoint ещё требует восстановления.

4. Подтверждение дошло клиенту

В этой ветви успешный ответ действительно получен. При потере соединения знание клиента было бы другим.

Действует: HTTP handler.

S3-клиент: PUT подтверждён; сохранён ID V; HTTP / ObjectLayer: успешный ответ отправлен; Erasure + bitrot: работа PUT закончена; Временная область: cleanup временной области; Описание V: V опубликована; E1 / E2 / E3 / E4: три участника содержат V

Знание клиента: ждёт ответ → подтверждённая V. Момент серверной публикации и получение HTTP-ответа разделены.

5. GET исключил повреждённый chunk

После PUT chunk на E3 испортился, E4 всё ещё без V. E1/E2 дают пригодные parity chunks и согласованную metadata V.

Действует: MinIO GET.

S3-клиент: запросил V; HTTP / ObjectLayer: GET читает выбранную версию; Erasure + bitrot: shard1 непригоден; shard2 недоступен; shard3/4 проверены; Временная область: новый repair ещё не выполнялся; Описание V: read quorum V получен; E1 / E2 / E3 / E4: E1/E2:источники; E3:bad chunk; E4:нет V

Пригодные chunks: ожидаются → 2 parity chunks. R=K=2 достаточно при согласованной metadata и правильных номерах shards.

6. GET вернул V, копии ещё не восстановлены

Декодер восстановил data shards в RAM и отдал S байт. Выявленный bitrot может поставить V в фоновую очередь.

Действует: Erasure decoder.

S3-клиент: в модели получены все байты V; HTTP / ObjectLayer: передал S байт; Erasure + bitrot: data shards восстановлены в RAM; Временная область: нет опубликованной записи healing; Описание V: описание V не заменено новым PUT; E1 / E2 / E3 / E4: E3 всё ещё повреждён; E4 всё ещё без V

Результат GET: нужно тело → S байт V. Реконструкция ответа не подтверждает RenameData ни одной цели healing.

Что меняется при публикации

Публикацией здесь называется изменение, после которого
серверные метаданные объекта ссылаются на новую версию V и её данные.
Под блокировкой имени renameData вызывает
StorageAPI.RenameData у пригодных endpoints.
Внутри локального xlStorage.RenameData сервер читает
прежний xl.meta, добавляет описание V и сериализует обновлённый
набор версий. Общий xl.meta может описывать несколько версий;
отдельные каталоги T хранят их non-inline данные.

У каждого non-inline участника сначала записывается новый
временный U/xl.meta, затем каталог данных
U/T перемещается к объекту, и после этого временный
xl.meta заменяет публичный
handbook-minio/project/manifest.txt/xl.meta.
Конечный part находится по относительному пути
handbook-minio/project/manifest.txt/T/part.1.
Все пути отсчитываются от корня соответствующего storage endpoint.

Порядок нужен для чтения: опубликованное описание V должно
указывать на её подготовленные данные. Несколько перемещений
на нескольких endpoints выполняются отдельно. Если три RenameData
завершились успешно, W=3 выполнен, хотя E4 ещё не содержит V.
Если успешных публикаций меньше W, общий код пытается отменить
успешные записи через DeleteVersion с UndoWrite. Ошибки этой
очистки не превращают её в гарантированный общий rollback;
на дисках могут оставаться частичные результаты.

Рассмотрим один возможный остаток при известном модели ID V.
RenameData прошёл только на E1/E2: это 2, меньше W=3.
Пусть попытка UndoWrite на них не удалила V, их метаданные V
согласованы, а оба полных parity shard читаются и проходят hash.
После возврата PUT с ошибкой и освобождения блокировки запрос
именно V может получить тело из этих двух источников при R=2.
FastGetObjInfo — опция быстрого поиска сведений об объекте —
в этом примере выключена. Попытки чтения metadata завершены:
E1/E2 вернули V, E3 — отсутствие V, E4 — ошибку недоступности.
Успешное чтение здесь зависит от перечисленных ответов metadata
и выбора V. Для GET без ID сервер отдельно выбирает и согласует
текущую версию; этот пример его результат не устанавливает.
ID V задан моделью; клиент, потерявший ответ, может его не знать.

После успешного renameData вызывается commitRenameDataDir.
Если заменялась прежняя версия null и получен oldDataDir,
эта функция удаляет старую область данных с отдельной проверкой
ошибок. Поэтому её ошибка может вернуться уже после публикации
новых метаданных. У рассматриваемой новой версии V с новым VersionID
oldDataDir пуст.

Затем объектный слой возвращает ObjectInfo. HTTP-handler
устанавливает ETag и version ID и доходит до отправки успешного
ответа. Клиент получает подтверждение только если этот ответ
дошёл до него. Успешный ответ означает принятие сервером
предусмотренных проверок записи, а не наличие N исправных shards
или один общий атомарный syscall на объект. Набор IO зависит
от inline/non-inline пути, размера xl.meta, filesystem и storage.

Источники:
renameData и UndoWrite,
xlStorage.RenameData,
последние проверки PUT,
commitRenameDataDir,
ObjectInfo и HTTP-ответ.

Короткий manifest проходит inline-ветвь

Inline означает хранение кодированных байтов рядом с описанием
версии внутри xl.meta. Выбор делается по ожидаемому размеру shard,
а не только по длине HTTP body. В закреплённой настройке исходный
inline block равен 128 KiB; для versioned записи ShouldInline
использует одну восьмую этого значения, 16 KiB. Настроенное
значение может быть другим.

Поэтому 35-байтовый manifest на исходном одноendpointном стенде
может попасть в inline: K=1, его shard payload равен 35 байтам.
При потоковом HighwayHash256S один chunk добавляет 32 байта hash.
Эти 67 байт являются содержимым inline-буфера данного участника;
размер самого xl.meta больше и зависит также от полей и других
версий.

Вместо CreateFile для part writer наполняет bytes.Buffer
в RAM. После Encode его байты присваиваются FileInfo.Data.
AddVersion помещает их во внутреннее inline-хранилище версии,
а AppendTo добавляет это хранилище к сериализованному xl.meta.
RenameData сохраняет новый xl.meta; ветвь перемещения отдельного
DataDir для такого тела пропускается. Описание part 1 в metadata
при этом остаётся. На endpoint не обязательно появится отдельный
файл с исходными 35 байтами.

Checksum входного HTTP body, hash каждого bitrot chunk
и проверка сериализованных метаданных защищают разные байты.
ETag, возвращённый приложению, также нельзя безусловно считать
ни bitrot hash, ни собственным SHA-256 исходного файла.

Источники:
ShouldInline и InlineBlock,
inline writers,
AddVersion,
AppendTo.

GET сначала выбирает версию

Продолжим чтением той же V. Клиент указывает её version ID;
сервер проверяет запрос и полномочия. При нескольких pools код
получает сведения о версии из pools и выбирает подходящий результат;
внутри pool обращается к set этого key. Это поиск уже сохранённого
объекта, а не повторный выбор pool по свободному месту.

getObjectFileInfo запрашивает ReadVersion для
явного ID. Без ID читаются xl.meta и выбирается текущая версия;
при необходимости pickLatestQuorumFilesInfo согласует сведения
из списков версий. Текущий delete marker и чтение конкретного V
разобраны в предыдущей
главе. Здесь V — обычная data version с телом.

Сначала objectQuorumFromMeta устанавливает quorum по доступным
метаданным. Для рассматриваемого layout read quorum R равен K=2.
listOnlineDisks и pickValidFileInfo затем ищут согласованный
вариант: учитываются время либо предусмотренное кодом запасное сопоставление по ETag,
список parts, их размеры, K/P и distribution. Перед чтением
отбрасываются неподходящие metadata и endpoints.

Два ответа от дисков ещё не дают два пригодных shard. Например,
описание V на одном диске и описание другой версии на втором
нельзя соединить как части V. Разная distribution назначила бы
байтам другие номера. Напротив, метаданные двух пригодных участников
не обязаны совпадать побайтово: Index и inline shard data у них
свои. Код согласует нужные свойства версии.

В быстром пути есть отдельный стартовый порог minDisks,
рассчитанный до знания layout. В симметричном случае он увеличен
на один. Этот порог управляет ожиданием ответов; окончательный
read quorum вычисляется из metadata. Число K в декодере не следует
подменять этим предварительным порогом.

Согласование metadata происходит под блокировкой имени.
При inline выбранные данные уже находятся в RAM, и блокировку
можно освободить после подготовки reader. Для non-inline чтения
код передаёт освобождение блокировки в cleanup reader.
Это позволяет читать данные выбранной версии с нужным временем
жизни ресурсов.

От hash на носителе до байтов HTTP-ответа

getObjectWithFileInfo переставляет endpoints по
сохранённым номерам shards, определяет parts для нужного диапазона
и создаёт bitrot readers. Для inline reader использует сохранённый
буфер Data, для non-inline — поток файла part.N. При Range-запросе
всё равно могут потребоваться выровненные chunks; кодер затем
отдаёт только требуемый диапазон логических байтов.

Bitrot reader читает сохранённый hash и payload chunk,
вычисляет hash заново и сравнивает. При несовпадении возвращается
errFileCorrupt. Ошибка чтения, отсутствующий файл или повреждённый
chunk исключают этот reader; parallelReader пробует другие,
пока не получит K пригодных фрагментов либо исчерпает источники.
Он не передаёт заведомо повреждённый chunk декодеру как правильный.

В нашем распределении E1/E2 содержат parity shards, E3/E4 —
data shards. После PUT E4 не получил V. Предположим, позднее chunk
на E3 перестал проходить hash. В рассматриваемом GET код
обратился к reader E3 и обнаружил это несовпадение.
Метаданные V на E1/E2 пригодны,
оба их parity chunks проходят проверку. Из них кодер восстанавливает
два data shards в RAM. Для каждого блока writeDataBlocks соединяет
data shards в исходном порядке и исключает padding по известной
логической длине.

Результат через reader/pipe передаётся HTTP-handler и затем
клиенту. Все 2 097 153 байта V могут быть прочитаны, хотя файлы
E3 и E4 ещё не восстановлены. Если восстановлены все запрошенные
байты, а ошибка относилась к missing/corrupt parts, код может
поставить partial operation в MRF — фоновую очередь повторного
восстановления — и завершить это чтение успешно.

Поздняя ошибка чтения имеет другой результат. Если HTTP-handler
ещё не отправил headers или body, он может вернуть S3 error.
После начала ответа заменить уже отправленный статус новым нельзя:
клиент должен заметить оборванный поток или ошибку проверки тела.
Поэтому принятие GET включает чтение до конца и сравнение байтов,
как в первом roundtrip.

Описанный путь относится к пригодной выбранной V. В других ветвях
этой реализации GET может инициировать lifecycle expiry или проверку
и удаление невосстановимого остатка при недостаточных metadata.
Поэтому GET нельзя считать универсальной процедурой снятия
неизменяемого снимка повреждённого server data.

Источники:
getObjectWithFileInfo и MRF,

Вычислим две stripes на семи байтах

Для видимого расчёта возьмём body MinIO!\n:
семь байтов 4d 69 6e 49 4f 21 0a.
Все значения далее записаны в hex. Уменьшим учебный B до 5 байт
и оставим K=2, P=2. Это самостоятельная модель кодирования;
матрицу выбранной в
go.mod
библиотеки klauspost/reedsolomon v1.12.4 мы здесь не воспроизводим и побайтового совпадения parity не заявляем.

Символом поля служит один байт; GF(2^8) содержит 256 таких
значений. Биты байта задают коэффициенты полинома: коэффициент
при x^i равен биту номера i. Нумерация начинается с 0 у младшего
разряда. Поэтому 02 соответствует x, а 80 — x^7. Коэффициенты равны 0
или 1. Их сложение выполняется через XOR: в разряде получается 1,
когда два исходных бита различаются. Вычитание здесь совпадает
со сложением. Например, 4d XOR 49 = 04.

При умножении сначала перемножают полиномы, затем берут остаток
по выбранному неприводимому полиному x^8+x^4+x^3+x^2+1,
записанному как 0x11d. Он не раскладывается на произведение
полиномов меньшей положительной степени с коэффициентами 0 и 1.
При таком выборе каждый ненулевой элемент имеет обратный:
их произведение равно 01. Например, 02·80 даёт x^8, а после
уменьшения по выбранному полиному остаётся x^4+x^3+x^2+1,
то есть 1d.
Арифметика конечного поля.

Для каждой позиции двух data shards x и y выбираем матрицу G:

          x   y
shard 1 [ 1   0 ]   = x
shard 2 [ 0   1 ]   = y
shard 3 [ 1   1 ]   = x XOR y
shard 4 [ 1   2 ]   = x XOR (02 · y)

Первые две строки сохраняют data, следующие вычисляют parity.
Для двух строк (a,b) и (c,d) определитель вычисляется как
a·d XOR b·c с умножением в этом поле. У любой пары строк он ненулевой,
поэтому любые два исправных shards дают два независимых уравнения
для x и y. Слово «независимых» здесь имеет вычислимый смысл:
обратная матрица пары существует.

 | Stripe | Входные байты | Shard 1 | Shard 2 | Shard 3 | Shard 4

 | 0 | 4d 69 6e 49 4f | 4d 69 6e | 49 4f 00 | 04 26 6e | df f7 6e

 | 1 | 21 0a | 21 | 0a | 2b | 35

В первой stripe ceil(5/2)=3 байта на shard: добавлен один
нулевой байт. Во второй ceil(2/2)=1, padding нет.
Потоки payload по номерам shards получаются такими:

shard 1: 4d 69 6e | 21
shard 2: 49 4f 00 | 0a
shard 3: 04 26 6e | 2b
shard 4: df f7 6e | 35

Всего data payload 8 байт, parity payload ещё 8: 16 байт
против семи входных. Из девяти добавленных байтов один — padding
в data, восемь — parity. Если применить уже вычисленную
distribution [3,4,1,2], E1 получит поток shard 3, E2 — shard 4,
E3 — shard 1, E4 — shard 2.

Условно добавим потоковый 32-байтовый hash перед каждым chunk
каждого endpoint. Две stripes дают восемь hashes: 256 байт,
а вместе с payload — 272 байта. Значения самих hashes в этой
модели не вычисляются; посчитаны их длины. xl.meta, filesystem
и временное сосуществование файлов сюда не включены.

Восстановление только из parity

Пусть доступны shard 3 и shard 4; обозначим их байты p и q.
Определитель их матрицы равен 02 XOR 01 = 03.
Обратный к 03 элемент поля равен f4, поскольку 03·f4=01.
Получаем y=f4·(p XOR q), затем x=p XOR y.

позиция 0: p=04, q=df
p XOR q = db
y = f4 · db = 49
x = 04 XOR 49 = 4d

позиция 1: p=26, q=f7 → y=4f, x=69
позиция 2: p=6e, q=6e → y=00, x=6e
stripe 1: p=2b, q=35 → y=0a, x=21

Восстановленные data shards первой stripe соединяются как
4d 69 6e 49 4f 00. Известная длина блока 5 убирает
последний 00. Вторая stripe даёт 21 0a.
Результат снова 4d 69 6e 49 4f 21 0a.

Одного parity shard недостаточно для однозначного результата.
Например, body MinIO!\n и LinHO!\n
дают в этой модели один и тот же полный shard 3
04 26 6e 2b. Проверка его hash подтвердила бы именно
эти сохранённые байты, но не выбрала бы между двумя исходными body.
Второе независимое уравнение поступает из другого пригодного shard.

У реального B=1 MiB этот семибайтовый body образует одну stripe:
K=2 даёт по 4 байта shard payload, те же 16 байт суммарно,
но только четыре hashes, 128 байт. Получается 144 байта потоков
до metadata, а при стандартном inline-выборе они сохранялись бы
в xl.meta. Учебный B=5 нужен для расчёта двух stripes; он не
является настройкой нашего MinIO и меняет число контрольных сумм.
У реального большого body V размеры выше вычислены с B=1 MiB.

Повторить арифметику без MinIO

Этот Python-код использует только стандартную библиотеку и RAM.
Он печатает shards двух stripes и проверяет восстановление из каждой
пары. Сетевых запросов и файловых операций здесь нет.

from itertools import combinations

def mul(a, b):
    result = 0
    while b:
        if b & 1:
            result ^= a
        b >>= 1
        a <<= 1
        if a & 0x100:
            a ^= 0x11d
    return result

def inv(a):
    if a == 0:
        raise ValueError("zero has no inverse")
    result, base, exponent = 1, a, 254
    while exponent:
        if exponent & 1:
            result = mul(result, base)
        base = mul(base, base)
        exponent >>= 1
    return result

G = ((1, 0), (0, 1), (1, 1), (1, 2))
body, B = b"MinIO!\n", 5
stripes = []
for offset in range(0, len(body), B):
    block = body[offset:offset+B]
    width = (len(block) + 1) // 2
    padded = block + bytes(2*width - len(block))
    x, y = padded[:width], padded[width:]
    shards = [
        bytes(mul(a, u) ^ mul(b, v) for u, v in zip(x, y))
        for a, b in G
    ]
    stripes.append((len(block), shards))
    print([part.hex() for part in shards])

def restore(pair, shards):
    a, b = G[pair[0]]
    c, d = G[pair[1]]
    scale = inv(mul(a, d) ^ mul(b, c))
    left, right = shards[pair[0]], shards[pair[1]]
    x = bytes(mul(scale, mul(d, u) ^ mul(b, v))
              for u, v in zip(left, right))
    y = bytes(mul(scale, mul(c, u) ^ mul(a, v))
              for u, v in zip(left, right))
    return x + y

for pair in combinations(range(4), 2):
    recovered = b"".join(restore(pair, shards)[:length]
                         for length, shards in stripes)
    assert recovered == body
assert mul(3, inv(3)) == 1 and inv(3) == 0xf4
assert all(mul(a, inv(a)) == 1 for a in range(1, 256))
assert sum(len(s) for _, stripe in stripes for s in stripe) == 16
print("6 surviving pairs recover the original 7 bytes")

Восстановленные байты и восстановленный endpoint

GET в рассмотренной ошибке создал нужные data shards в RAM
и передал их клиенту. Для возвращения копии на E3 либо E4
нужен другой путь: healing выбранной версии заново выбирает
метаданные и источники, восстанавливает нужные data/parity shards,
записывает их во временное место, проверяет writers и публикует
результат через RenameData на выбранной цели.

Цель E4 сначала должна снова стать доступной. Успех записи E3
не подтверждает запись E4: состояние каждой цели учитывается
отдельно. Scanner может обнаружить объект для проверки и
восстановления, но не участвует обязательным шагом между каждым
PUT и его HTTP-ответом. Выбор scan mode, прогресс замены диска,
bitrot и стоимость такого IO продолжаются в
главе healing/scanner.

Источники:

Безусловный повтор PUT в versioned bucket может создать следующую
версию с теми же байтами. Create-only повтор использует тот же key;
после сохранённой первой попытки он может получить 412.
Последний отказ не устанавливает исход первой попытки.
Для сопоставления нужны сохранённое намерение, operation ID,
конкретная версия и прочитанные байты — как в
главе о timeout.

В расчёте N=4 относится к одному set. Четыре пути одного SSD
теряются вместе с SSD; четыре независимых имени не создают
четыре физических источника. Числа R=2 и W=3 описывают этот layout
пригодной версии, а успешность операции дополнительно зависит
от согласованных metadata, целостности прочитанных chunks
и завершения storage IO.

Какие байты нужно вернуть на диск

Возьмём одну сохранённую версию V с одним part 1 длиной
S=4 194 304 байта, то есть 4 MiB. Part — часть версии, чей номер
и размер записаны в metadata, служебных сведениях об объекте.
Тело не сжато, не зашифровано и не перенесено во внешнее хранилище;
кодированные данные лежат отдельными файлами, а не inline внутри
xl.meta. Эти условия позволяют считать байты без дополнительных
преобразований.

У версии один erasure set, группа совместно кодируемых endpoints:
N=4, K=2 data shards и P=2 parity shards. Endpoint — адресуемая
сервером область хранения. Shard — пронумерованный кодированный
поток части. Parity вычисляется из data и позволяет восстановить
недостающие фрагменты при достаточном числе пригодных источников.
Здесь E1–E4 находятся на отдельных физических дисках узлов A–D;
диск узла D называется D1. K обозначает число data shards, а D
в имени узла остаётся именем узла.

В metadata V записан erasure block size B=1 048 576 байт.
Block — порция входного part за один проход кодера. Она даёт
четыре shard-фрагмента, вместе называемые stripe. Chunk здесь —
один такой фрагмент в потоке конкретного shard. При K=2 полный
block даёт chunk длиной 524 288 байт. Четыре blocks образуют
по 2 097 152 байта shard payload на endpoint. Payload означает
кодированные байты без hashes и metadata. Деление здесь точное,
поэтому padding, дополнения нулевыми байтами, нет.

Зафиксируем distribution [1,2,3,4], перестановку номеров shards
по endpoints: E1/E2 содержат data, E3/E4 — parity. Это явная
предпосылка сцены, а не вычисленное размещение по имени key.
При HighwayHash256S перед каждым chunk лежит 32-байтовый hash,
контрольное значение его байтов. Один поток имеет вид
hash0 | chunk0 | hash1 | chunk1 | hash2 | chunk2 | hash3 | chunk3.
Его длина — 2 097 280 байт; сумма четырёх — 8 389 120 байт.
Из них 8 MiB составляет shard payload и 512 байт — hashes.
xl.meta, каталоги и выделенные filesystem блоки сюда не входят.

Источники:
размеры shards,
запись hash и chunk.

Почему размер файла не заменяет проверку содержимого

Bit rot здесь означает повреждение сохранённых байтов.
Сервер ищет его проверкой целостности; отсутствие файла
и изменение содержимого требуют разных проверок.

Normal scan для отдельного non-inline part вызывает CheckParts.
Локальный checkPart смотрит путь, проверяет, что он не является
каталогом, и выявляет размер меньше ожидаемого shard payload.
Он не читает весь payload и не сравнивает hashes; файл прежней
длины с изменённым байтом способен пройти этот этап. По этому
результату нельзя утверждать, что проверено содержимое part.

Deep scan вызывает VerifyFile. Storage endpoint читает
hash и следующий chunk, заново считает hash и сравнивает значения.
При HighwayHash256S проверяется также ожидаемый размер потока
с hashes. Несовпадение даёт errFileCorrupt. Reader обычного GET
тоже проверяет прочитанные chunks; он не передаёт обнаруженные
повреждённые байты декодеру как исправные. Проверенный диапазон
не говорит о ещё не прочитанных chunks.

Inline данные уже получены вместе с metadata: в
checkObjectWithAllParts их bitrotVerify выполняется и в normal
режиме. Поэтому правило «normal никогда не проверяет байты»
для этой реализации неверно. Delete marker, версия без тела,
и remote-версия с данными во внешнем хранилище проходят другие
ветви; приведённые далее расходы относятся к нашему локальному part.

Checksum отвечает на вопрос о совпадении сохранённых байтов
и контрольного значения. Она не выбирает нужную историю:
две разные версии могут иметь исправные, но разные тела.
У HighwayHash здесь встроенный публично известный ключ из
bitrot.go. Это обнаружение повреждения, а не аутентификация
автора данных: знающий алгоритм может пересчитать hash.
SigV4 проверяет подпись запроса, TLS защищает соединение,
а приложение отдельно сравнивает принятое тело с ожидаемым.

Источники:
checkPart и CheckParts,
VerifyFile,
inline и выбор режима,
ключ и алгоритмы,

Откуда появляются задания scanner

Data scanner обходит namespace, пространство имён bucket/key,
и собирает сведения об объёме и версиях. Он также исполняет
выбранные проверки healing, lifecycle и replication.
Lifecycle задаёт срок хранения или перенос версий; replication
копирует их в другую цель. Эти действия объясняют, почему обход
не является только чтением данных для поиска bitrot.

runDataScanner получает лидерскую блокировку, читает сохранённый
номер цикла и вызывает NSScanner. Верхний слой запускает работу
по sets всех pools и объединяет usage cache, дерево сохранённых
счётчиков. Внутри set nsScanner раздаёт buckets через общую очередь
работникам доступных дисков; новые buckets идут раньше уже известных.
Конкретный bucket берёт один работник очереди. Это не требование
прочитать его payload на каждом endpoint в каждом цикле.

На storage endpoint NSScanner ищет xl.meta или файл старого формата xl.json,
читает metadata и превращает найденные версии в ObjectInfo,
сведения о версии для объектного слоя, включая VersionID и размер.
Далее applyActions рассматривает версии по отдельности. Для
выбранной проверки applyHealing передаёт именно VersionID этой
версии в HealObject. У удаляемой lifecycle-версии может оказаться
другое действие вместо healing. В HealObject пустой versionID
преобразуется в буквальную null-версию; это не обещание ремонта
самой новой версии при любой форме вызова.

Cache позволяет не перечитывать каждую ветку целиком. У
скомпактированной ветки хранятся суммарные счётчики потомков.
Для известных таких веток применяется отбор по hash и номеру
цикла с dataUsageUpdateDirCycles=16; пропущенная ветка переносит
прежние totals. Для выбора healing используется другая часть
того же hash: modAlt сравнивает её остаток с номером цикла,
а healObjectSelectProb равен 1024. При предварительном отборе
ветки делитель objectHealProbDiv согласует эти два шага.

Это детерминированный отбор по hash и циклу, а не независимый
бросок монеты для каждого запроса. Если healing выключен для
прохода через SkipHealing или диск уже помечен Healing,
shouldHeal не разрешает обычную проверку. Отдельная ветвь
abandonedChildren, ранее известных, но не найденных сейчас имён,
проверяет другие диски и может поставить найденные версии в
фоновую работу. Поэтому отсутствие имени на одном диске
не читается сразу как доказательство удаления всего объекта.

цикл и его сохранение,

выбор item,

Как выбирается normal или deep

Параметр heal:bitrotscan и переменная MINIO_HEAL_BITROTSCAN
разбираются кодом закреплённого поколения. Значение off даёт
BitrotScanCycle=-1, on — 0; запись вида 1m означает один
30-дневный месяц, а не одну минуту. Положительное число месяцев
задаёт интервал. Это описание формата, а не команда изменения
настроек стенда; default в исходниках — off.

getCycleScanMode возвращает normal при -1 и deep при 0.
Для положительного интервала deep выбирается, пока разность
currentCycle и BitrotStartCycle меньше 1024, либо когда
прошедшее время превысило интервал. Иначе выбирается normal.
При переходе в deep сохраняются BitrotStartTime,
BitrotStartCycle и CurrentScanMode. Режим цикла и выбор объекта
— два отдельных условия: deep не отменяет отбор items по hash.

При выбранном item applyHealing создаёт HealOpts со ScanMode
и Remove=true. Это путь, способный менять storage. Даже DryRun
не следует описывать как безусловно неизменяющее чтение:
внутри healObject некоторые ветви deleteIfDangling находятся
до проверки DryRun. Успешный цикл и обновлённый usage cache
не доказывают чтение всех байтов всех версий. Числа 16 и 1024
не задают крайний срок полного scrub, проверки содержимого
всего хранилища.

Источники:

Как healing выбирает версию и источники

Перед дорогим чтением HealObject выполняет быстрый опрос
metadata. В рабочем healObject сервер обычно берёт блокировку
bucket/key и заново вызывает readAllFileInfo для выбранного
VersionID. Вариант NoLock предназначен для вызывающего пути,
который сам обеспечивает нужную блокировку. Данные опроса
в RAM ещё не являются выбранным телом объекта. FileInfo — структура
сведений об одной версии. Она содержит VersionID, DataDir — имя
области её shard-данных, erasure-параметры и список Parts.

objectQuorumFromMeta получает K и P из доступных согласуемых
metadata этой версии. Затем listOnlineDisks выбирает группу по
общему ModTime, времени версии; предусмотрен запасной путь по
ETag с общим VersionID. pickValidFileInfo вызывает findFileInfoInQuorum. Для нашего
локального несжатого V эта функция группирует описание по XLV1,
номерам и размерам parts, K/P и distribution после отбора по
ModTime либо ETag. Index конкретного endpoint и его shard data
при этом различаются.
Более позднее время одного файла или один исправный hash
не заменяют эти проверки.

Для V в нашей модели read quorum R=K=2; обычный PUT при K=P
требовал W=3. Healing восстанавливает уже выбранную версию.
Условие K пригодных shards проверяется для каждого нужного блока.
Два ответа с разными версиями либо два неправильных номера shard
не дают двух уравнений для V. Если metadata не позволяют выбрать
версию или у part больше P непригодных участников, путь не может
обычно восстановить тело. Код рассматривает и deleteIfDangling,
обработку признанного невосстановимым остатка; для сохранения повреждённых файлов без изменений нужна отдельная
копия: этот изменяющий storage путь сам по себе её не создаёт.

checkObjectWithAllParts сопоставляет metadata с выбранным
описанием, проверяет распределение и получает результаты по
каждому part каждого endpoint. В основном пути сравниваются
ModTime и DataDir; в запасном пути — ETag. Далее normal/deep
выбирает CheckParts или VerifyFile. Источники для данного part
создаются только там, где его результат равен checkPartSuccess.
Нормальная лёгкая проверка ещё не исключила скрытое повреждение:
bitrot reader повторно проверит реально прочитанные chunks.

Источники:
блокировка и metadata,
pickValidFileInfo,
R и W,
VersionID перед запасным ETag,
listOnlineDisks,
проверка parts,
невосстановимый остаток.

Как определяются цели

Функция shouldHealObjectOnDisk отвечает отдельно для каждого
участника. Отсутствующее описание V, повреждённая metadata или
описание, не совпавшее с выбранным FileInfo, делают доступный
endpoint кандидатом на обновление. Недостающий либо corrupt part
также требует записи. Здесь stale означает устаревшие или
неподходящие сведения о рассматриваемой версии, а не просто
«давно не трогавшийся файл». FileInfo.Equals учитывает время,
erasure-параметры, признаки compression, encryption и transition.

Ошибка errDiskNotFound даёт состояние Offline и не создаёт
пишущую цель: серверу некуда отправить новые данные. Если E4
вновь доступен, но V у него отсутствует, новая попытка может
включить его как Missing. Если вернулся прежний диск с исправной V,
эта копия проходит проверки и не требует автоматической перезаписи
только из-за самого факта временного отключения.

В результате HealResultItem указываются Bucket, Object,
VersionID, DiskCount, DataBlocks, ParityBlocks и списки
Before.Drives / After.Drives. В каждом элементе важны Endpoint
и State. Известные причины превращаются в DriveStateMissing,
DriveStateCorrupt, DriveStateOffline или DriveStateOk;
неизвестная ошибка сохраняет неизвестное состояние с причиной.
Формат native CLI здесь не имитируется. Before и After относятся
к этому вызову и выбранной версии, а не к проверке всех объектов диска.

Источники:
shouldHealObjectOnDisk,
FileInfo.Equals,
состояния,
списки целей и результатов.

Почему GET может закончиться раньше восстановления

В этой схеме явно принята distribution [1,2,3,4]:
E1/E2 содержат data shards, E3/E4 — parity. Пусть E4 недоступен,
а chunk на E3 не прошёл checksum. Исправные E1/E2 уже содержат
оба data shards, поэтому GET может собрать тело без вычисления
отсутствующих data shards. Запись parity на E3/E4 остаётся
отдельной работой. В главе записи и чтения показан другой случай:
GET получает data из одной пары parity shards.

Для этой сцены reader E3 действительно был вызван и обнаружил
несовпадение. В другой последовательности успешный GET может
ограничиться E1/E2 и вообще не прочитать E3. Если HTTP-клиент
принял все байты V, это подтверждает результат данного чтения.
Для записи на E3 требуется другой вызов, новое согласование
metadata и завершение целевого IO.

В read path, когда запрошенная часть передана целиком, но decoder
сообщил missing/corrupt source, код может добавить PartialOperation
в MRF. Эта структура содержит Bucket, Object, VersionID,
SetIndex, PoolIndex, Queued и BitrotScan. Последний признак
выбирает deep для фонового вызова, если причиной был bitrot.
GET при этом может завершиться успешно. Добавление задания
не означает, что его цель уже восстановлена.

MRF имеет очередь на 100 000 элементов. addPartialOp не ждёт
свободного места: при заполненной либо закрываемой очереди
добавление может быть пропущено. В этом коде есть сохранение
оставшейся очереди при штатном shutdown и загрузка list.bin
при старте; это не durable-журнал каждого принятого задания.
Обработка элемента очереди и последующие scanner/drive-heal
дают разные возможности снова найти проблему. Из них не
получается обещание срока или доставки каждого задания после
любого аварийного завершения процесса.

GET и addPartialOp,
поля и очередь,

От источников до временных целевых байтов

Продолжим с доступным E4. Представим, что deep-проверка V
нашла corrupt part на E3 и отсутствие V на E4. У E1/E2 metadata
согласованы, все chunks выбранного part исправны; E4 уже доступен
для записи в ожидаемой позиции set. Это две выбранные цели.
Списки sources, targets и FileInfo переставляются по distribution,
чтобы позиция в erasure-массиве обозначала номер shard.

Для каждой цели cleanFileInfo копирует согласованное описание
V и очищает локальные Index, checksums и inline Data. Оригинальная
копия metadata источника сохраняется отдельно, чтобы читать его
прежние DataDir и checksum-параметры. Для обычного нового формата
dstDataDir остаётся DataDir V; отдельный migrateDataDir нужен
для миграции старого формата XLV1. Временной операции присваивается собственный UUID U.

Цикл проходит parts V. Reader источника читает его part.N
и проверяет hash каждого полученного chunk. Erasure.Heal
вызывает parallelReader, получает K пригодных фрагментов и
DecodeDataAndParityBlocks. При наших E1/E2 data уже есть:
нужно вычислить parity для E3/E4. При других пригодных номерах
shards сначала восстанавливаются недостающие data, затем parity.
Размеры, номера и конечное поле задаёт кодер выбранной версии;
учебная матрица из главы 08 не подменяет библиотечную.

Writers создаются только для выбранных целей. Для non-inline
данные идут во временный part
.minio.sys/tmp/U/DataDir/part.1 данного endpoint.
Bitrot writer заново добавляет hash перед каждым новым chunk.
Для inline вместо отдельного файла заполняется буфер в RAM,
который позже попадёт в xl.meta. Здесь один corrupt chunk делает
целевой part непригодным; рассматриваемая ветвь переписывает
полный shard part, а не только один повреждённый байт.

Внутри Erasure.Heal multiWriter имеет writeQuorum=1. Это порог
продолжения записи доступных целей существующей V, а не замена
W=3 для обычного PUT. Если один writer отказал, другой ещё может
получить восстановленные байты. Если ни одна цель больше не
принимает данные, продолжать этот repair нечем.

Если normal-проверка пропустила скрытый bitrot, source reader
может обнаружить его уже при восстановлении. Erasure.Heal
способен получить достаточные другие фрагменты и записать временные
байты, но вернуть сохранённый errFileCorrupt. Внешний healObject
закрывает readers/writers и при этой ошибке возвращается до
публикации. Обёртка HealObject после errFileCorrupt в normal
повторяет работу в deep, чтобы заново выбрать пригодные sources
и targets. Наличие временных байтов первого прохода не является
завершённым repair.

Источники:
порядок, metadata, readers и writers,
Erasure.Heal,
ошибки записи и Close,
normal с повтором deep.

Close, публикация и результат каждой цели

После обработки part код закрывает writers. Возвращённая
ошибка Close исключает соответствующую цель из дальнейших parts
и публикации. У streamingBitrotWriter.Close есть две операции:
закрыть промежуточный writer и дождаться фонового CreateFile.
Он возвращает сохранённый результат первого закрытия, а после
ожидания не читает результат CreateFile заново. Поэтому ожидание
фоновой функции и передача каждой поздней ошибки Fdatasync или
Close storage-файла — разные свойства. Здесь действует то же
уточнение, что в главе 08.

Целям, оставшимся после parts, выставляются номер shard Index
и признак SetHealing. Затем healObject последовательно вызывает
StorageAPI.RenameData. Это этап публикации восстановленных данных
и metadata по отдельным endpoints. Только после успешного вызова
для данной цели её After.Drives.State становится DriveStateOk.
Этот цикл не вызывает общий renameData обычного PUT с W=3.
Общий момент атомарной публикации всех целей из него не следует.

Предположим, E3 вернул ошибку Close, а E4 прошёл Close и
RenameData. В ответе E4 станет OK, E3 сохранит прежнее не-OK
состояние, например Corrupt. Если других ошибок нет, функция
может вернуть nil — отсутствие общей ошибки. При этом E3 ещё
не восстановлен. Поэтому нужно читать
After по нужному Endpoint. В другом случае E3 успел опубликоваться,
а RenameData E4 вернул ошибку: функция возвращает ошибку,
но уже успешная публикация E3 не откатывается общим rollback.

Повтор заново выбирает V и актуальное состояние endpoints.
Успешный E4 больше не обязан входить в targets; E3 может получить
новую временную запись и затем публикацию. Удалять данные E4,
менять private xl.meta или создавать пустой каталог на месте
неподтверждённой цели для «выравнивания» состояния не требуется.
В исходниках есть очистка временной операции, но отложенный вызов удаления, defer,
ставится после цикла parts; ранний выход до него не даёт основания
обещать отсутствие оставшихся временных файлов.

Источники:
возвращённый Close,
Flush буфера,
Fdatasync и Close файла,
исключение целей и публикация.

Вернулся endpoint или заменён физический носитель

Временный сетевой отказ может скрыть прежний исправный диск.
После его возвращения сервер снова читает format и metadata:
возврат доступности сам по себе не говорит, какие versions он
успел пропустить. Для V он может оказаться исправным источником,
устаревшей копией или доступной целью с отсутствующими данными.

Физическая замена меняет накопитель, но адрес endpoint может
остаться прежним. В format.json поле Erasure.This задаёт
логическую идентичность позиции среди Erasure.Sets. GetDiskID
проверяет format и соответствие set/disk позиции. В ветви
newHealFormatSets новый unformatted носитель получает ожидаемый
Erasure.This из reference format этой позиции. Следовательно,
появление того же UUID не доказывает, что вернулся тот же
физический накопитель; это не аппаратный serial number.

saveFormatErasure публикует новый format и при заданном healID
создаёт healing tracker. Этот tracker хранит ID диска, отдельный
HealID операции, PoolIndex, SetIndex, DiskIndex, Endpoint,
Started и LastUpdate. При загрузке его ID сравнивается с GetDiskID.
Копирование чужого tracker или ручная перестановка format не являются
способами продолжить восстановление.

Автоматический monitor локального узла вызывает HealFormat,
а затем healFreshDisk. Обход выполняет узел, к которому подключён
заменённый диск, для соответствующего set. Сначала нужна пригодная
reference format в quorum; при несогласованном format код отказывает.
Ни совпавший путь, ни пустой новый filesystem не являются
восстановленными объектами.

Источники:
GetDiskID и позиция,
newHealFormatSets,
format и tracker,
HealFormat,
tracker ID,
локальный monitor.

Чем прогресс замены диска отличается от очереди MRF

healFreshDisk сохраняет очередь QueuedBuckets; tracker
запоминает текущие Bucket/Object, HealedBuckets и счётчики.
ResumeItemsHealed, ResumeItemsFailed и другие Resume-поля
возвращают счётчики к началу возобновляемого bucket. Повторный
обход части уже обработанной работы возможен: сохранённая контрольная точка не
означает отдельную транзакцию для каждого объекта.

healErasureSet начинает normal scan, перечисляет versions
и вызывает HealObject. Новые версии с ModTime после Started
и версии, выбранные lifecycle для удаления, могут быть пропущены (skipped).
Успех конкретной версии дополнительно требует
After.Drives[tracker.DiskIndex].State=DriveStateOk. Поэтому
общий nil от HealObject не подменяет результат нужной цели.
ItemsHealed/BytesDone, ItemsFailed/BytesFailed и
ItemsSkipped/BytesSkipped учитываются отдельно. Эти Bytes
относятся к учитываемым версиям, а не к измерению всех physical
shard reads и writes.

Если ItemsFailed больше нуля и RetryAttempts меньше 4,
healFreshDisk увеличивает RetryAttempts, сбрасывает рабочие
счётчики и возвращает errRetryHealing. После исчерпания этой
ветви ошибки остаются в счётчиках; tracker с тем же HealID
может получить Finished=true. Поэтому Finished означает
окончание этого обхода, включая вариант с оставшимися failed
items. Он не заменяет проверку нужной V и её целей.

Scanner ищет объекты по namespace и cache; MRF обрабатывает
задания известных partial operations; fresh-disk heal перечисляет
данные set ради конкретного заменённого диска. Foreground GET
может только обнаружить проблему и дать повод для фонового
вызова. Эти инициаторы используют общий механизм работы с V,
но их очереди, критерии пропуска и счётчики различаются.

Источники:
поля tracker,
учёт и сохранение,
resume,
версии и результат нужного диска,
повтор и Finished.

Сколько IO требует исправление V

Посчитаем отдельный deep-проход с последующим repair, когда
E4 уже доступен, но V у него нет. На E1/E2 все четыре chunks
исправны; у E3 ошибка в последнем chunk, поэтому до её обнаружения
прочитан весь его поток. Проверка трёх потоков читает
6 MiB payload и 384 байта hashes: 6 291 840 байт.
Опрос metadata E4 сообщает отсутствие V; чтения его part нет.

Далее sources E1/E2 читаются для восстановления: ещё
4 MiB payload и 256 байт hashes, всего 4 194 560 байт.
Writers E3/E4 получают столько же суммарно. Итого для этой
последовательности — 14 MiB payload и 896 байт hashes,
14 680 960 байт чтения и записи shard-потоков. Hash вычисляется
для 12 проверенных chunks первого прохода, 8 source chunks
repair и 8 новых target chunks: 28 вычислений на chunks
по 512 KiB. Кодирование обрабатывает четыре stripes.

Это счётчик байтов на выбранных storage-путях. Он не равен фактическому чтению и записи
накопителя, device IO: filesystem metadata, выравнивание, упреждающее чтение,
кэширование данных, повторные ошибки и временное сосуществование файлов
меняют обращения к устройствам. Если повреждение обнаружено
раньше, VerifyFile может прочитать меньше; если sources меняются
или попытка повторяется, работа растёт.

Зафиксируем и место исполнения: healer работает на D,
источники E1/E2 находятся на A/B, E3 — на C, E4 — локальный
новый диск D1. Удалённый вызов метода, RPC VerifyFile,
исполняет проверку на storage endpoint и возвращает статусы parts, поэтому первые 6 MiB
payload не обязаны пересекать сеть к D. При repair к D приходят
потоки E1/E2, 4 194 560 байт; к C уходит поток E3,
2 097 280 байт. Поток E4 пишется локально. Получаем
6 291 840 сетевых байт shard-потоков без RPC, metadata,
HTTP/TLS framing и повторов. При другом месте healer или
совмещении endpoints на узле этот расчёт меняется.

Если в ту же пару sources приходит полный обычный клиентский
(foreground) GET V
и он читает E1/E2, эти sources дополнительно обслужат ещё
4 194 560 байт. Вместе с source-проходом repair это
8 389 120 байт вместо 4 194 560 для одного GET, до прочих расходов.
Это сравнение объёма двух работ. Из удвоения байтов не следует
удвоение latency: cache, очереди и расположение IO могут дать
другую зависимость. Успешный E4 и повтор только E3 также требуют
раздельного учёта: один новый source-проход и запись E3 — ещё
6 291 840 байт без новой предварительной deep-проверки.

Для большого набора, где требуется вернуть 1 TiB именно
shard payload на одну цель при K=2, один идеальный полный
проход требует 2 TiB source payload reads и 1 TiB target
payload writes. Это не 1 TiB логических объектов. Время можно
оценивать только по измеренным доступным скоростям нужных
ресурсов и количеству повторов; непроверенные MiB/s сюда
не подставляются.

Источники:
RPC VerifyFile,
проверка на endpoint,
source stream,
передача writer,
обработка stripes.

Пересчитать отбор, частичный результат и байты в RAM

Код ниже моделирует только названные условия. Синтетический
64-битовый hash уже задан числом; xxhash реального key здесь
не вычисляется. На неизменном, посещаемом в каждом нужном цикле
имени он показывает два уровня отбора, но не срок scanner.
Функция publish получает наблюдаемые результаты Close и RenameData;
она не воспроизводит storage, metadata quorum или crash recovery.

"""Teaching model: selection, per-target publication and byte accounting.
No MinIO calls, sockets, files, HighwayHash or xxhash implementation.
"""
from math import ceil

MiB = 1 << 20
S, B, K, N, H = 4 * MiB, MiB, 2, 4, 32
blocks = [min(B, S - offset) for offset in range(0, S, B)]
widths = [ceil(length / K) for length in blocks]
payload = sum(widths)
hash_bytes = len(blocks) * H
stream = payload + hash_bytes
assert blocks == [MiB] * 4
assert widths == [MiB // 2] * 4
assert payload == 2 * MiB and hash_bytes == 128
assert N * stream == 8389120

# E4 is available but has no V. E3's last chunk has a bad hash.
deep_reads = 3 * stream
source_reads = K * stream
target_writes = 2 * stream
network = source_reads + stream  # healer D; E1/E2 remote; E3 remote; E4 local
assert deep_reads == 6291840
assert source_reads == target_writes == 4194560
assert deep_reads + source_reads + target_writes == 14680960
assert network == 6291840
assert 2 * source_reads == 8389120  # repair sources plus one foreground GET
assert source_reads + stream == 6291840  # another pass, only E3 is target
assert 3*4 + 2*4 + 2*4 == 28  # chunk hashes computed

def cycle_mode(config, cycle, start_cycle, elapsed):
    if config == -1:
        return "normal"
    if config == 0:
        return "deep"
    return "deep" if cycle - start_cycle < 1024 or elapsed > config else "normal"

assert cycle_mode(-1, 0, 0, 0) == "normal"
assert cycle_mode(0, 5000, 0, 0) == "deep"
assert cycle_mode(100, 1023, 0, 0) == "deep"
assert cycle_mode(100, 1024, 0, 100) == "normal"
assert cycle_mode(100, 1024, 0, 101) == "deep"

def selected(hash64, cycle, compact=False, skip=False):
    # hash64 is a supplied synthetic xxhash result, not calculated from a key.
    low = hash64 & 0xffffffff
    high = (hash64 >> 32) & 0xffffffff
    divisor = 16 if compact else 1
    if skip or (compact and low % 16 != cycle % 16):
        return False
    return high % (1024 // divisor) == (cycle // divisor) % (1024 // divisor)

fake_hash = (93 << 32) | 37
ordinary = [c for c in range(1024) if selected(fake_hash, c)]
compacted = [c for c in range(1024) if selected(fake_hash, c, compact=True)]
assert ordinary == [93] and compacted == [469]
assert not selected(fake_hash, 93, skip=True)

def publish(before, close_results, rename_results, decode_error=False):
    # Only observable return values are modeled. No claim that Close carries
    # every late error from a storage goroutine.
    after = dict(before)
    if decode_error:
        return after, "decode error"
    candidates = [name for name in before if close_results[name] is None]
    if not candidates:
        return after, "all targets failed"
    for name in candidates:
        if rename_results[name] is not None:
            return after, "rename error"
        after[name] = "ok"
    return after, None

before = {"E3": "corrupt", "E4": "missing"}
after, error = publish(before, {"E3": "returned close error", "E4": None},
                       {"E4": None})
assert after == {"E3": "corrupt", "E4": "ok"} and error is None
again, error = publish({"E3": after["E3"]}, {"E3": None}, {"E3": None})
assert again == {"E3": "ok"} and error is None
partial, error = publish(before, {"E3": None, "E4": None},
                         {"E3": None, "E4": "error"})
assert partial == {"E3": "ok", "E4": "missing"} and error == "rename error"
early, error = publish(before, {"E3": None, "E4": None}, {},
                       decode_error=True)
assert early == before and error == "decode error"

print("streams:", stream, "four streams:", N * stream)
print("deep/source/target:", deep_reads, source_reads, target_writes)
print("total:", deep_reads + source_reads + target_writes, "network:", network)
print("synthetic selection cycles:", ordinary, compacted)
print("partial:", after, "retry:", again, "rename failure:", partial)

Как наблюдать влияние на обычные запросы

Сопоставляйте ход scan/heal с end-to-end временем обычных PUT/GET,
числом завершённых запросов, ошибками и unknown исходами.
Для сравнения нужны одинаковые размеры объектов, concurrency,
состояние cache, TLS, проверки checksum и SDK retries.
Latency измеряется от выбранного начала операции до принятия
полного результата, включая тело GET. По отдельности полезны
занятость устройств, глубина очереди, объёмы source reads и
target writes, CPU hash/decode и сеть между указанными узлами.

В throughput приложения входят подтверждённые логические
байты. Внутренние bytes tracker и сумма shard-потоков отвечают
на другие вопросы и не складываются с ним как «ещё один полезный
результат». p99 получают из распределения длительностей:
его нельзя вывести из среднего, сложить либо усреднить
процентили узлов. Сокращение очереди за окно также нужно читать
вместе с новыми заданиями, skipped/failed и доступностью целей.

В коде scannerSleeper и healSleeper вводят задержки; отдельные
пути могут ждать снижения числа HTTP-запросов. Это механизмы
снижения конкуренции, а не резерв определённого числа IOPS
или гарантия foreground latency. Численные скорости и p99
в этой главе не выдаются за измеренные результаты.

Источники:
dynamicSleeper,
ожидание HTTP IO.

Числа N=4 и K=2 относятся к одному set выбранной версии.
Если E1/E2 — каталоги одного SSD, один отказ убирает сразу два
endpoints; три потерянных endpoints оставляют меньше K.
Четыре VM на одном ноутбуке также имеют общие накопитель,
питание и гипервизор. У нашей схемы физические диски разные;
дополнительная независимость питания остаётся условием размещения.

Erasure coding использует сохранившуюся избыточность.
Оно не возвращает окончательно удалённую историю, не исправляет
правильно записанные, но ошибочные данные приложения и не заменяет
backup. Дополнительные shards не возвращают утраченный ключ
шифрования. Сохраняемый стенд книги имеет один endpoint с P=0:
здесь нет второго источника для такого восстановления.
Четырёхendpointная сцена — вычисленная модель; административный
запуск healing и повреждение private server data в упражнение
этого стенда не добавляются.

Pool не является дополнительным голосом одного объекта

В модели set quorum относится к endpoints одной кодированной версии. Pool объединяет один или несколько sets, но объект не распределяет свои K+P shards по всем pools сразу. Если в pool A у выбранного set не хватает пригодных shards, свободный пустой pool B не содержит недостающие байты. Добавление оборудования не восстанавливает утраченное содержимое.

Сохранённый format задаёт принадлежность endpoints, порядок sets, идентичность deployment и дисков. При старте сервер сопоставляет переданную топологию с прочитанным форматом. Все pools одного deployment должны согласовать deployment ID и допустимую parity. Изменить список путей существующего set как произвольный RAID-массив нельзя. Перезапуск с прежними аргументами, замена отказавшего носителя и добавление нового pool — три разных операции.

В distributed варианте один и тот же полный список endpoints передают всем участникам; HTTP-путь обозначает область конкретного узла. Имена должны разрешаться с каждого узла, сертификаты покрывать эти имена, root credentials совпадать, системное время и версии программ согласовываться. Loopback 127.0.0.1 на другом узле обозначает уже другую машину. Наш исходный стенд имеет один процесс и один data; никакие команды далее не превращают его в четыре независимых узла.

Как выбирается pool новой записи

Для обычного выбора места реализация получает сведения о дисках того set, куда объект попал бы внутри каждого pool. Непригодные по доступному месту кандидаты получают нулевой вес; приостановленные и участвующие в исходящем rebalance pools исключаются из такого выбора. У оставшихся оценивается свободная ёмкость с учётом числа sets. Затем случайное число выбирает интервал весов: pool с большим пригодным свободным пространством получает больше новых записей. Это распределение запросов, не обещание точного чередования и не преобразование старых объектов.

Учебный пример: у A вес 20 GiB, у B 60 GiB. Из диапазона 0..79 интервалы 0..19 выбирают A, 20..79 — B: вероятности 1/4 и 3/4. Последовательность четырёх PUT не обязана дать ровно один A и три B. Реальные веса не равны сумме надписей на корпусах: сервер проверяет выбранные sets, доступность и резерв. Ключ существующего объекта, история в нескольких pools и data movement имеют дополнительные ветви; эту модель нельзя использовать как собственный router записей.

Почему расширение не является rebalance

При добавлении нового pool новые объекты могут начать занимать его, тогда как старые версии остаются в прежнем месте. Дисбаланс заполнения будет уменьшаться только по мере подходящих новых записей и удалений. Rebalance — отдельная фоновая операция перемещения существующего состояния. Decommission выводит выбранный pool из обслуживания и также требует переноса; это не синоним rebalance и не разрешение отключить диски сразу после ответа команды.

Для учебного изменения топологии сначала нужна отдельная VM-топология с собственными пустыми устройствами и сохранённым списком всех исходных endpoints. Одинаковые каталоги одного SSD могут проверить обработку аргументов, но теряют всё вместе при отказе SSD. Здесь не предлагается hot-plug, форматирование дисков или смена аргументов нашего сохраняемого стенда. Такой шаг выполняют после inventory устройств, проверенного резерва и отдельного расчёта failure domains.

С чего начинает rebalance выбранного поколения

Admin handler проверяет разрешение RebalanceAdminAction и направляет начало к первому узлу первого pool, чтобы согласовать параллельные запросы. На одном pool он отвечает NotImplemented. Одновременно выполняемый decommission и уже начатый rebalance дают отдельные отказы. Лишь после этих проверок получается список buckets и создаётся metadata операции.

В rebalance.bin сохраняются ID операции, целевая доля свободного места PercentFreeGoal и массив PoolStats. У записи pool есть исходные свободные байты InitFreeSpace, ёмкость InitCapacity, очередь Buckets, уже обработанные RebalancedBuckets, последний bucket/object, счётчики объектов/версий/байтов, Participating и Info со временем/статусом. Поля владельцем меняет сервер. Ручное удаление rebalance.bin ради исчезновения ошибки может оторвать управление от уже перенесённых данных.

Цель вычисляется как сумма свободных байтов / сумма ёмкостей в начале. Участниками исходящего переноса становятся pools с меньшей долей свободного места, чем цель. Например, A: ёмкость 100 GiB, свободно 20; B: 100 GiB, свободно 80. Общая цель 100/200 = 0.5; A должен освободить примерно 30 GiB, а B принять соответствующее кодированное содержимое. Это расчёт фиксированного состояния. Параллельные PUT/DELETE, размеры версий, metadata и проверки места меняют фактическое движение; доля не обязана стать ровно 50%.

StartRebalance запускает работу на первом узле участвующего pool. Внутри имеются workers, обход sets и периодическое сохранение progress. Сохранённый start ID подтверждает принятие задания, не чтение всех объектов и не окончание переноса. Статусы Started, Stopped, Completed и Failed описывают разные этапы; ответ stop инициирует отмену контекста, а не общую транзакцию rollback.

От списка имён к конкретным версиям

Обход получает metadata записей со своих online-дисков и разрешает частичные ответы. Listing quorum этого пути равен (N+1)/2 с целочисленным делением; это условие объединения списка, а не универсальный read quorum тела. Для N=4 получается 2. Обнаруженное имя ещё не доказывает, что последующее GetObjectNInfo получит пригодные K shards требуемой версии.

Список версий одного key обрабатывается в обратном порядке, чтобы построить стек истории у получателя. Для каждой версии учитываются version ID, время, пользовательская metadata и специальные состояния. Удалённая приложением версия может исчезнуть между listing и чтением; это допустимая гонка, а не повод создать другую версию по последнему GET. Перенесённые во внешний tier версии и lifecycle-expired объекты имеют отдельные ветви и могут пропускаться. Retention, replication и lifecycle нужно проверять до изменения, не после неожиданного отсутствия версии.

Один перенос тела: источник, получатель, удаление исходника

Обычный путь открывает reader конкретной version ID в исходном set. Этот reader выполняет проверки и реконструкцию из object IO. rebalanceObject передаёт поток PutObject с DataMovement=true и SrcPoolIdx, сохраняя version ID, MTime, пользовательскую metadata и ETag. Это не обычный клиентский PUT, который произвольно создаёт новую версию. Для multipart сохраняется структура частей: NewMultipartUpload, PutObjectPart для каждой части и CompleteMultipartUpload; неудачная незавершённая загрузка имеет собственную очистку.

Получатель проходит свой путь временных parts, checksums, metadata и публикации по endpoints. Он может получить ошибку чтения источника, недостаток места, write quorum или отмену. Следовательно, факт прочитанного исходника или вызова PutObject не даёт основания сразу удалить исходные bytes. Код повторяет отдельные попытки и различает disappeared version, конфликт data movement и настоящий отказ.

В rebalanceBucket счётчик rebalanced увеличивается после принятого пути версии. Исходный key со всем стеком удаляется оптимизированным DeletePrefixObject лишь при rebalanced == числу обнаруженных версий. При ошибке до этого условия исходная история не удаляется этой финальной ветвью. Это объяснение условия конкретного кода, не обещание общей атомарности между pools или отсутствия частичного размещения при падении процесса. Ошибка source cleanup после успешного переноса тоже возможна: обе копии требуют дальнейшего согласования сервером.

Delete marker передаётся как marker с прежними version ID/временем и data-movement опциями. Marker не имеет обычного тела для Reed–Solomon. Единственный оставшийся marker может обрабатываться без переноса payload. Поэтому число объектов, число версий и число перенесённых байтов нельзя считать одной величиной.

Как читать progress без ложной точности

В этом поколении rebalanceStats.update добавляет оценку on-disk size как fi.Size × (K+P) / K для обычной версии. Это арифметическая оценка кодированного размера; в ней нет точного округления каждого блока, hash headers, файловой metadata и device write amplification. Поле Bytes в rebalance status не обязано совпасть с S3 Content-Length и не является измерением реальных записей block device.

checkIfRebalanceDone сравнивает оценку (InitFreeSpace + Bytes) / InitCapacity с PercentFreeGoal и использует допуск 0.05. Это пять процентных пунктов доли, а не гарантия свободного резерва на всех дисках и не точный процент завершённых objects. CLI summary берёт максимальное elapsed/ETA среди pools; ETA остаётся оценкой. Нельзя из 0s to completion вывести отсутствие незавершённых IO или проверить пригодность всех старых версий.

Наблюдение на продолжаемом стенде

После успешной настройки прежнего стенда используйте второй терминал той же VM. alias lab имеет owner-доступ, TLS CA загружен через enter.sh. Следующие команды только читают состояние; output сохраняется в новом закрытом этапе. Если этап уже есть, сначала просмотрите прежний результат, не создавайте новую копию под тем же именем.

source "$HOME/minio-study/enter.sh"
cd "$LAB_ROOT"
begin_stage operations-v1 "$LAB_ROOT/exercises/operations-v1"
EX="$LAB_ROOT/exercises/operations-v1"
mkdir -- "$EX"
"${MC[@]}" --json admin info lab > "$EX/admin-info.private.json" 2> "$EX/admin-info.private.err"
"${MC[@]}" --help > "$EX/mc-help.txt"
"${MC[@]}" admin rebalance start --help > "$EX/rebalance-start-help.txt"
"${MC[@]}" admin rebalance status --help > "$EX/rebalance-status-help.txt"
finish_stage

admin info сообщает состояние deployment, не выполняет heal. JSON может содержать внутренние адреса и сохраняется приватно. Для нашего единственного pool start rebalance не является упражнением на перенос: handler отверг бы его до запуска. На отдельной принятой multi-pool топологии синтаксис start/status — mc [ROOT_FLAGS] admin rebalance start ALIAS и ... status ALIAS; root config-dir остаётся до admin. Сначала принимаются backup и capacity, затем составляется план изменения, а после start сверяются ID, per-pool status, ошибки и чтение выбранных версий. Не переносите команды такого плана в single-endpoint data.

Диагностика отказа без reset

 | Наблюдение | Что проверять | Что не исправляет причину

 | Новый pool пуст, старый полон | Старые версии не переносились; placement новых записей и фильтр доступного места | Один restart без переноса

 | Есть место, PUT отказал | Пригодность выбранного set, quorum, reserve, IAM, версия и полная ошибка | Сумма свободных байтов других sets

 | Start ID есть, bytes не растут | Статус участников, source reader, target write, listing/metadata errors | Повторный start без reconciliation

 | Stop принят | Сохранённое StoppedAt, прекращение workers и дальнейших IO | Предположение об откате уже опубликованных версий

Упражнение на бумаге: после переноса двух из трёх версий третья не читается из источника. Где существуют данные? Первые две могут быть опубликованы у получателя, третья остаётся только в источнике; условие финального удаления всего стека не выполнено. Повтор должен опираться на согласованные metadata/version и причины отказа, а не на копирование каталога xl.meta вручную. Healing исправляет части выбранного размещения; rebalance меняет pool. Они конкурируют за ресурсы, но решают разные задачи.

Что именно нужно восстановить

Erasure parity исправляет ограниченное число потерянных shards внутри deployment. Она не возвращает версию, которую разрешённо удалили, и не защищает от потери всех устройств, общего питания или украденных credentials. Versioning сохраняет историю лишь пока её версии существуют и доступны. Репликация в другой сервер переносит данные по своим правилам, включая возможные удаления и задержку; она не автоматически является неизменяемой резервной копией.

Резерв выбирают под задачу: какие buckets, все или только текущие версии, delete markers, пользовательская metadata, IAM, bucket policy, lifecycle, уведомления, конфигурация, внешние ключи шифрования. Обычный GET текущего key возвращает только выбранное тело. Простое копирование текущих объектов через клиент не обещает сохранить историю, marker stack, version ID и административные настройки.

В этом упражнении используется ровно прежний один процесс с одним data, без внешнего KMS и tiering. Копируется весь остановленный LAB_ROOT, включая data/.minio.sys, TLS, secrets, mc, fixtures, exercises, binaries и сведения происхождения. Это приватная копия, а не публичный переносимый том. В ней есть root password, service-account secret и CA key. Её нельзя прикладывать к source manifest или отправлять в Git.

Почему копирование требует остановки

Во время PUT сервер публикует данные и metadata на отдельных endpoints; scanner, lifecycle и healing тоже меняют состояние. Последовательное чтение дерева работающего сервера может взять xl.meta до изменения и part после изменения. Хеш каждого скопированного файла ещё не доказывает, что все файлы относятся к одному согласованному моменту. Наша предпосылка — сервер полностью остановлен, иных процессов и внешних writers к тому же data нет.

В первом терминале нажмите Ctrl-C и дождитесь возврата оболочки. Не запускайте run-server.sh снова до завершения копирования. Во втором терминале прекратите клиенты. Это управляемое действие владельца единственного учебного процесса; helper не убивает процессы и не определяет автоматически, что файловая система quiescent, то есть больше не изменяется. Для distributed deployment остановки одного frontend недостаточно, а копирование отдельных дисков в разное время не заменяет согласованный backup-план.

Пределы собственного cold_copy.py

Исходник labs/cold_copy.py входит в том. Он не вызывает MinIO API. Snapshot читает дерево, отвергает ссылки и специальные файлы, считает размер и SHA-256 каждого обычного файла, копирует в новый отдельный каталог и сверяет содержимое. В конце появляются собственные _snapshot_manifest.json и _snapshot_COMPLETE. Manifest — список относительных имён, размеров и хешей; он не содержит сами credentials. Но и имена объектов могут быть чувствительны, поэтому весь каталог остаётся закрытым.

Restore сначала проверяет snapshot, затем создаёт другое новое дерево и копирует файлы, не включая служебные manifest/COMPLETE самого snapshot. Предыдущий LAB_ROOT не перезаписывается. Ошибка оставляет частичную цель для разбора; повтор в неё отвергается. Helper не удаляет её автоматически и не предлагает reset. Проверка SHA выявляет расхождение с выбранным manifest, но не аутентифицирует резерв от администратора, способного заменить и bytes, и manifest.

Копирование файлов и fsync отдельных файлов не являются snapshot-транзакцией файловой системы или испытанием сбоя питания. Здесь проверяется согласованная по условию остановки копия и её логическая читаемость после restore. Долговечность каталога на конкретном устройстве, независимый backup-носитель, шифрование хранения и контроль доступа требуют отдельной приёмки. Две папки одного SSD не переживут его физический отказ.

Подготовить источник программы и новую цель

Сначала перейдите в каталог minio/ вашей копии книги: в нём должен находиться labs/cold_copy.py. Это путь исходника helper, не каталог runtime. Работает тот же обычный пользователь личной Linux VM; обе резервные цели находятся в его домашней области. Перед запуском убедитесь, что свободного места достаточно для двух полных копий LAB_ROOT сверх оригинала. Архивы Go и кэши тоже входят в эту простую полную копию; объём не равен сумме S3 body.

set +x
set -euo pipefail
set -C
umask 077
BOOK_LABS="$PWD/labs"
test -f "$BOOK_LABS/cold_copy.py"
source "$HOME/minio-study/enter.sh"
test -f "$LAB_ROOT/.setup/versions-v2/COMPLETE"
BACKUP_PARENT="$HOME/minio-backups"
mkdir -p -- "$BACKUP_PARENT"
chmod 700 "$BACKUP_PARENT"
SNAPSHOT="$BACKUP_PARENT/cold-v2"
RESTORED="$HOME/minio-restored-v2"
test ! -e "$SNAPSHOT"
test ! -L "$SNAPSHOT"
test ! -e "$RESTORED"
test ! -L "$RESTORED"
python3 -B "$BOOK_LABS/cold_copy.py" --help

--help только объясняет три действия helper. snapshot SOURCE DEST создаёт новую копию, verify SOURCE сверяет готовый snapshot, restore SOURCE DEST создаёт новый runtime. SOURCE/DEST обязаны быть отдельными деревьями; вложенную цель helper отвергает, чтобы не копировать резерв внутрь самого себя. Python -B запрещает создание bytecode cache.

Snapshot и проверка до запуска восстановленного сервера

Следующий блок выполняется только после подтверждённой остановки исходного сервера. Он читает LAB_ROOT и пишет исключительно новые snapshot/restore цели. Нативное выполнение этого рецепта при подготовке книги не производилось.

python3 -B "$BOOK_LABS/cold_copy.py" snapshot "$LAB_ROOT" "$SNAPSHOT"
python3 -B "$BOOK_LABS/cold_copy.py" verify "$SNAPSHOT"
python3 -B "$BOOK_LABS/cold_copy.py" restore "$SNAPSHOT" "$RESTORED"

Ожидаются три успешных кода и соответствующие status snapshot-copied, verified, restore-copied. Счётчик files относится к файлам дерева, не к S3 objects или versions. При отказе чтения, ссылке, расхождении хеша либо существующей цели прекращаются зависимые действия. Не редактируйте manifest так, чтобы он согласился с ошибочной копией. Сначала определите, нарушена ли остановка источника, доступ или носитель.

Один адрес, один активный процесс

Исходный сервер остаётся остановленным. В первом терминале запускаем только восстановленную копию; её скрипт вычисляет LAB_ROOT по собственному расположению, поэтому использует новый data и TLS. API остаётся 127.0.0.1:19000. Если оригинал занимает порт, стартовать второй процесс на том же порту нельзя; смена случайного data ради обхода ошибки тоже не принимается за restore.

"$HOME/minio-restored-v2/run-server.sh" >> "$HOME/minio-restored-v2/logs/restore-server.log" 2>&1

Терминал занят foreground сервером. Во втором терминале заново задаём переменные, не полагаясь на прежний EX или функцию version_id из главы о версиях. Весь дальнейший ввод берётся из восстановленного корня.

source "$HOME/minio-restored-v2/enter.sh"

Какие изменения не вернутся

RPO — допустимая потеря изменений относительно выбранной контрольной точки. Если после cold-v2 оригинал получил V3, этот snapshot её не содержит. Возврат к нему не отменяет существование V3 на других клиентах и не сливает две истории автоматически. RTO — время восстановления требуемого обслуживания: получение копии, проверка, запуск, TLS/IAM и чтение нужных данных. Одно время копирования не равно RTO.

Текущий опыт не создаёт внешнего KMS. При server-side encryption за пределами профиля нужны доступные ключи и их политика: сохранённый ciphertext без ключа не возвращает plaintext. При tiering часть тела может находиться во внешнем хранилище; копия только локальных metadata не включает удалённые bytes. Резерв bucket policy без user identity и секретов также не создаёт рабочий доступ.

Программное обновление — отдельное изменение формата и поведения. Сначала сохраняют выбранный бинарник, source commit и резерв; затем на отдельной восстановленной цели проверяют чтение исторических версий и операции новой версии. Успешный запуск новой программы не доказывает возможность обратного запуска старой поверх уже изменённых данных. Для архивного OSS нет обещанного будущего vendor security patch; миграция на другую реализацию требует проверки S3-семантики и истории.

Задание и разбор отказов

Изменяемый пример выполняют на отдельной копии snapshot, не на единственном резерве: поменяйте один байт заранее выбранного несекретного fixture-файла. verify должен отказать по inventory; это модель повреждения копии, не bitrot MinIO shard. Обратное восстановление исходных bytes должно вернуть успешную проверку. Изменение только manifest ради PASS запрещено смыслом опыта. Неполный snapshot без COMPLETE и restore в существующий каталог также должны отвергаться.

После упражнений остановите восстановленный foreground сервер и сохраните обе цели для сравнения. Для возврата к оригиналу запускается только его прежний run-server.sh, затем повторяется health/read; никакой автоматический restore поверх оригинала не выполняется. Разрешённая поздняя очистка требует сначала выбрать, какая проверенная независимая копия остаётся; книга не даёт массовую команду rm -rf по вычисленному пути.

Сначала объект, затем сумма дисков

Полезный объём — bytes приложения, а raw capacity — доступные устройствам bytes. Для одной большой обычной версии с N=K+P идеальная доля K/N. У четырёх одинаковых дисков по 100 GiB и K=2,P=2 сумма raw равна 400 GiB, идеальный payload — 200 GiB. Это потолок простой арифметики, не обещание сервера: служебные данные, резерв свободного места, разные размеры дисков и неравномерное заполнение уменьшают принимаемый объём.

Минимально необходимое свободное место проверяется для подходящих дисков/sets, не только по общей сумме. Более крупный диск рядом с меньшим не превращает каждую stripe в независимый произвольный набор bytes. Если планировщик направляет key в заполненный set, пустые диски другого set не являются его parity. Заполненный filesystem также влияет на создание временных файлов и metadata; аварийный запас нужен до достижения 100%.

Для планирования отдельно выбирают рабочий резерв. Например, если от идеальных 200 GiB оставить 25% под рост и операции, бюджет текущего payload равен 150 GiB. Число 25% — условие этого расчёта, не утверждение о константе MinIO. Сами server reserve checks следует смотреть по закреплённой версии, выбранному filesystem и ошибке операции.

Округление и hash bytes

Внешний shard stream обычного одного part можно оценить по размеру erasure block B: q=floor(S/B), r=S mod B, payload одного shard = q×ceil(B/K)+ceil(r/K). При r=0 последнее слагаемое равно 0. Число ненулевых chunks c=q+[r>0]. Для выбранной в healing-главе streaming bitrot модели hash длиной h=32 B добавляется к каждому chunk, поэтому полный поток одного endpoint равен payload+c×h. Сумма N таких потоков ещё не включает xl.meta и filesystem overhead.

При N=4,K=2,P=2,B=1 MiB,S=4 MiB: один shard payload = 2 MiB, четыре hashes занимают 128 B, stream = 2097280 B; все четыре — 8389120 B. Это логическое содержимое streams, не измеренные device writes. Контроллер, filesystem, журнал, sector alignment, кэш и повторные записи могут добавить другие IO.

При N=8,K=4,B=1 MiB размер S=1 MiB даёт 2097152 B payload и 256 B hashes, всего 2097408 B. Увеличение тела до 1 MiB+1 B создаёт второй chunk: payload становится 2097160 B, hashes — 512 B, всего 2097672 B. Рост на один байт приложения добавил 264 B streams в этой модели. Для малых inline objects применяется другой путь: нельзя механически прибавлять внешние hash streams к любому байту маленького объекта.

Версии, multipart, lifecycle и внешний tier

Включённое versioning сохраняет несколько тел одного key. Если три большие версии имеют одинаковый размер S и одинаковый layout, грубый payload budget становится 3×S×N/K до их отдельной metadata. Delete marker обычно не содержит такого тела, но остаётся записью истории. Удаление current key не освобождает автоматически все старые версии. Незавершённые multipart uploads и временные данные также расходуют место, пока не завершены или не очищены подходящим серверным путём.

Lifecycle — сохранённые правила обработки объектов по времени и состоянию. Их выполнение происходит позже обходом, не в момент записи policy. Планируя reclaim, наблюдают действительное исчезновение выбранных версий и освобождение места. Tiering переносит тело во внешний storage, оставляя локальные сведения для доступа; local used bytes уменьшаются, но общая стоимость включает внешний объект, запросы, сеть и доступные credentials. В начальном стенде правила lifecycle, tier и KMS не настраиваются.

Почему одинаковый Content-Length даёт разную нагрузку

Последовательный PUT большого тела платит за чтение клиента, TLS/подпись, hash, кодирование, запись нескольких streams и metadata. Много маленьких объектов добавляют больше lookup, объектов metadata и отдельных завершений на те же полезные bytes. GET здорового объекта читает выбранные data shards; degraded GET может читать другие пригодные shards, проверять hashes и декодировать. Range-запрос возвращает меньше тела, но границы blocks/checksums могут заставить прочитать больше bytes, чем отдано клиенту.

Условный сетевой пример: coordinator находится на одном из четырёх узлов N=4,K=2; один shard локален, три удалены. Для записи большой версии S каждый удалённый shard несёт примерно S/2 payload, суммарный исходящий shard payload coordinator — 1.5S. Если единственный ограничивающий интерфейс имеет номинальные 1 Gbit/s = 125000000 B/s, то только эта составляющая даёт предел логического потока 125000000/1.5 ≈ 83333333 B/s. Это расчёт верхней границы до протокольных расходов, TLS, metadata, исходного клиентского трафика и диска; он не является результатом benchmark и не обещает такую скорость.

Если все endpoints — пути одного SSD, сетевой межузловой трафик исчезает, но все shards конкурируют на одном устройстве и исчезнут вместе при его отказе. Если исходный поток клиента тоже проходит через тот же интерфейс, надо считать оба направления и фактический duplex. При healing место источников и target определяет, какие bytes действительно пересекут сеть. Пример 07 отдельно считает source reads, target writes и сеть для своей конкретной топологии.

Конкуренция, память и очередь

Concurrency — число одновременно выполняемых запросов. Увеличение его скрывает отдельные задержки и может поднять throughput до насыщения CPU, сети или диска. После насыщения растёт очередь, время ожидания и число deadline failures. Модель L=λW связывает среднее число задач в устойчивой системе L, средний завершённый поток λ задач/с и среднее время W секунд; она не вычисляет p99 и неприменима как обещание для растущей без границ очереди.

Буферы — только часть памяти. Если бы каждый из 32 запросов одновременно держал все N shard chunks одного B=1 MiB,K=2,N=4 блока, эти буферы заняли бы 32×4×512 KiB=64 MiB. Это явно заданная учебная схема владения буферами, не измеренный MinIO RSS. Реальная программа использует pools, goroutines, metadata, Go heap/GC, TLS и другие выделения. RSS процесса отличается от heap, а page cache и память гостевой VM учитываются отдельно.

Поэтому профиль 8–16 GiB хоста начинается с одного небольшого потока и последовательной сборки. RAM не создаёт независимых дисков. Нельзя назначать одновременно весь ресурс нескольким тяжёлым службам или обещать многоузловой HA-тест только по сумме гигабайт. Увеличивают один параметр за опыт, сохраняя выбранный объект и исходное серверное состояние.

Что фиксировать перед измерением

 | Поле опыта | Зачем оно нужно

 | Server/mc/SDK commit и бинарный hash | Поведение и retry зависят от реализации

 | Размер/число объектов, версии, layout, concurrency | Определяют объём работы и очереди

 | Холодный или прогретый cache | Различает чтение устройства и попадание в память

 | TLS, checksum, retry, timeout | Определяют CPU и число фактических запросов

 | Начало/конец end-to-end интервала | Отделяет принятие bytes от получения заголовков

 | Scanner/healing/rebalance, фоновая нагрузка | Конкурируют за тот же диск, сеть и CPU

В throughput входят только подтверждённые полезные bytes / длительность всего выбранного окна. Ошибки и unknown PUT учитывают отдельно. Нельзя добавлять bytes неподтверждённой попытки и ещё раз её успешного повтора как два полезных объекта. GET принят лишь после полного чтения и проверки bytes; один HTTP 200 с оборванным Body не является завершённым чтением.

Записывайте индивидуальные end-to-end длительности завершённых запросов и отдельно причины отказа. Среднее, p50, p95 и p99 отвечают на разные вопросы. Percentile вычисляется по выбранному распределению и определению; его нельзя восстановить из среднего или усреднить между узлами. Например, у узла A два наблюдения 1 и 100 ms, у B — 98 наблюдений по 2 ms. По nearest-rank p99 A=100 ms, B=2 ms, а объединённый p99=2 ms, не 51 ms. Это синтетический набор, не задержки MinIO.

Контролируемое сравнение без выдуманного результата

Для своего личного стенда сначала примите первый объект и выберите фиксированный fixture. Измерьте последовательный PUT/GET с собственными новыми ключами, отдельно учитывая появляющиеся версии и цену cleanup. Затем измените только concurrency. Для опыта scanner/healing на отдельном принятом erasure-стенде сохраните тот же размер, TLS/checksum/retry/cache режим; сравните foreground latency и суммарные IO до и во время фоновой работы. Нельзя запускать repair на единственном резерве ради графика.

Серверные counters помогают объяснить итог, но их граница может отличаться от клиентской: shards и hashes не равны S3 bytes. Проверяйте units метрики, labels, histogram buckets, сброс counter при restart и стоимость scrape. Логи и admin info дают причины ошибок, но не заменяют распределение времён клиента. Публикуйте профиль и реальные сырые измерения после собственного опыта, не заранее выбранные MiB/s или p99.

SAN

Поле сертификата с допустимыми именами/IP; URL клиента должен ему соответствовать.

Access key

Идентификатор credentials; не secret для вычисления подписи.

Secret key

Закрытое значение для подписи запросов; info service account не возвращает потерянный secret.

Policy

Документ разрешений над действиями и ресурсами; неперечисленное действие не становится разрешённым от наличия credentials.

Service account

Отдельные credentials, связанные с parent; embedded policy ограничивает их действия.

ARN

Строковая идентичность ресурса в совместимом policy; сама не выбирает сетевой endpoint.

Scanner

Фоновый обход сохранённого состояния; выбор режима и задания проверки не равен немедленному deep scan всех bytes.

MRF

Очередь последующих попыток исправления неполных операций; её наличие не означает завершённый repair.

Rebalance

Перемещение подходящих сохранённых версий между pools для выбранной цели заполнения.

Decommission

Управляемый вывод pool с переносом данных; назначение нового места не означает завершённый перенос.

RPO

Допустимая потеря изменений относительно контрольной точки резерва.

RTO

Время восстановления требуемого обслуживания, включая проверку доступа и данных.

Throughput

Подтверждённая полезная работа за выбранный интервал; ошибки/unknown и физические shard IO учитываются отдельно.

Percentile

Квантиль распределения наблюдений по указанному определению; percentiles узлов не усредняют для общего результата.

Concurrency

Число одновременных запросов, влияющее на очередь, ресурсы и ошибки.

Toolchain

Компилятор и сопутствующие инструменты выбранной версии; исторический Go не является обещанием текущей поддержки.

Checksum

Вычисленное по bytes значение проверки целостности; при отсутствии доверенного эталона не доказывает подлинность.
