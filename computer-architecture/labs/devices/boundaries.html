Две самостоятельные сцены: firmware ownership и вложенное преобразование. Это не настоящая UEFI, hypervisor или полная ISA; абсолютные host адреса отличаются от исходной М32 явно.

К модели DMA

UEFI-подобная передача владения

Следующий шаг проходит platform memory → обнаружение → loader image → GetMemoryMap → ExitBootServices → kernel entry. Key 5/6 — символическая версия, не обещание последовательного номера настоящей MapKey. Дополнительная allocation после карты делает captured key устаревшей: Exit должен отказать. Уже первая попытка ExitBootServices может частично остановить обычные Boot Services: после отказа модель разрешает лишь memory allocation, получение карты и retry, а console/device вызов отклоняет.

Проверить другие порядки и отказы
    

    М32-VM1: GVA → GPA → host PA
    GVA 00402200 через гостевой Sv32 требует сначала прочитать rootPTE по GPA 8004, затем leafPTE по GPA 9008, затем обратиться к GPA 2200. Абстрактные соответствия адресов, mappings, второй ступени задают страницы 8→18, 9→19, 2→5 и дают физические адреса host 18004, 19008, 5200. Это другой профиль с host областью 1 MiB. G-stage таблицы предполагаются подготовленными; их настоящий формат Sv32x4 не эмулируется.
    Изменить один допуск до начала
      Изменение соответствия адресов (mapping) после начала сцены отклоняется, чтобы не скрыть необходимость invalidation. Для другого варианта сохраните JSON и явно начните новый сценарий.
      

      Текстовый/печатный путь
      Boot: map5 → allocation/map6 → exit5 отказ с restricted state → обычный Boot Service уже запрещён → getmap6 → exit6 успех → Boot Service отказ. VM: root GPA 8004→host 18004 → leaf GPA 9008→host 19008 → result GPA 2200→host 5200. При missing root mapping отказ возникает раньше чтения guest PTE; при запрете data write перевод отклоняет целевую запись; массива RAM в этой сцене нет.
