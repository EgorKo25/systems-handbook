Сетевой контроллер: от сигнала до буфера RAM

Кадр проходит физический приём, аппаратную проверку, очередь и DMA прежде, чем программный сетевой стек сможет прочитать его байты.

PHY и MAC делают разную работу

В предыдущей главе устройство записывало данные в RAM через PCIe Memory Write. Теперь источником байтов будет сетевой порт LAN743x. Проследим один Ethernet-кадр длиной 128 байт, включая FCS, от порта до буфера, который выделил драйвер. Сетевой контроллер, NIC, связывает этот порт с хостом.

Физический приёмопередатчик PHY восстанавливает цифровой поток из сигнала, а блок канального уровня MAC выделяет кадр из потока. При выбранных настройках аппаратная проверка пропускает этот кадр: адрес назначения подходит фильтру, а полученный FCS, поле контрольной суммы кадра, совпадает с контрольной суммой, рассчитанной алгоритмом CRC. Если настроен фильтр VLAN, решение приёма зависит и от метки виртуальной локальной сети. Здесь контроллер проверяет условия канального приёма. После передачи в сетевой стек пакет может быть отброшен по другим причинам, например из-за правила межсетевого экрана или отсутствия сокета для порта назначения.

Внутренняя очередь поглощает разницу скоростей

Пока Ethernet приносит кадр, PCIe или RAM могут быть заняты. Контроллер использует FIFO — first in, first out, буфер с последовательным изъятием. Его конечная ёмкость означает, что поток нельзя бесконечно принимать без доступных host buffers. Пример реального чипа LAN7430/LAN7431 из datasheet DS00002631D имеет отдельные RX/TX DMA пути и каналы; его конкретные четыре RX-канала приёма и один TX-канал передачи не являются правилом любого NIC. PHY, MAC, FIFO и DMA могут быть частями одной микросхемы, но их функции остаются различными.

Host заранее выделяет буферы, создаёт receive descriptors с адресами/размерами и передаёт их контроллеру. Контроллер выбирает пригодный descriptor, переносит данные и возвращает status/length. Если кадр больше одного буфера, поддержанный формат может использовать несколько descriptors и признак последней части. CPU должен обработать все нужные части прежде, чем назвать кадр полным. Длина DMA-буфера и длина полезного кадра не обязаны совпадать.

Реальный RX descriptor: LAN743x, AN2948 revision B

Рассмотрим 16-байтный описатель принимаемых данных LAN743x по Microchip AN2948 DS00002948B, таблицы 378–381. Четыре слова DWORD размером 32 бита начинаются со смещений 0, 4, 8 и 12 байт. OWN в бите 15 слова DWORD0 передаёт владение: 1 — контроллеру приёма RX DMAC, 0 — host. BUFLENGTH в битах 13:0 задаёт вместимость буфера перед передачей, а после возврата — число использованных байтов. Байты 4..7 содержат RADDRL, 8..11 RADDRH; 12..15 зарезервированы до передачи. После возврата описатель без дополнительной extension-записи содержит FS в бите 31, LS в бите 30, FRMLENGTH в битах 29:16, OWN=0 в бите 15 и EXT=0 в бите 14. FS/LS обозначают первую/последнюю часть кадра. Вместо адресов в DWORD1/2 появляются статус, контрольная сумма и данные VLAN; DWORD3 содержит RSS hash — хеш, число, вычисленное из выбранных полей заголовков. Receive-side scaling, RSS, использует его для выбора очереди приёма; подробнее этот путь разобран ниже.

Для слота 0 подготовим буфер вместимостью 512 байт с DMA-адресом 6000h. Получатся показанные ниже 16 байт little-endian. DW0=00008200h: OWN=1 и BUFLENGTH=0200h. Старшие биты адреса нулевые. По DMA-адресу 6000h начинается область данных. Последний доступный байт буфера имеет адрес 61FFh. Сам описатель занимает 16 байт в кольце.

offset00  00 82 00 00  00 60 00 00  00 00 00 00  00 00 00 00
          OWN/len      RADDRL      RADDRH       reserved

Кадр длиной 128 байт помещается в один буфер. DMA заполняет диапазон 6000..607Fh; оставшиеся 384 байта вместимости не входят в кадр. В этом примере не добавляются байты выравнивания, VLAN/FCS не удаляются, extension-записи нет; размер 128 B в этом профиле включает сохранённый FCS. Тогда при успешном приёме FS=1, LS=1, FRMLENGTH=128, BUFLENGTH=128 и OWN=0 дают DWORD0=C0800080h. Это число описывает только DWORD0. До чтения кадра host проверяет также статус RXSTATUS в другом слове и соответствующие флаги ошибок. Один флаг OWN не доказывает исправность кадра. Для 512 B кадра при вместимости буфера 256 байт нужны описатели первой и последней частей; первая часть сама по себе ещё не полный кадр.

Драйвер хранит отдельное соответствие «номер слота → буфер». При возврате описателя адресные слова заменяются статусом, поэтому драйвер находит буфер по своей таблице. AN2948 §11.2.4 разрешает опрашивать OWN в системной памяти, чтобы узнать, вернула ли аппаратура буфер. Драйвер может также использовать предусмотренную запись индекса головы в память. Чтение регистра RX_HEAD само по себе не гарантирует, что процессор уже видит запись описателя и данные. Перед доступом CPU драйвер соблюдает правила видимости DMA для платформы.

Один оборот ring и исчерпание буферов

Возьмём канал RX 0, длину кольца 4, расстояние DSPACE=16 байт и базу 3000h. Четыре слота находятся по адресам 3000/3010/3020/3030. Выбранное поле поддерживает такую малую длину. RX_CFG_B0.RX_RING_LEN задаёт 4; RX_BASE_ADDRH/L задают 0/3000. Поля меняют в исходном состоянии DMA, разрешающем настройку, не поверх работающего канала. Аппаратура использует HEAD/TAIL как индексы, не байтовые адреса; address(slot)=base+slot×DSPACE.

При HEAD=TAIL интерфейс считает ring пустым. Публикация сразу всех четырёх слотов с TAIL 0 выглядела бы пустотой: один слот оставлен различителем. Уменьшить TAIL и забрать уже аппаратные descriptors назад нельзя; остановка/reset канала имеют свой протокол. При кадре в 600 байт и буферах по 512 байт одному кадру понадобятся два опубликованных описателя. Трёх доступных слотов хватит лишь на один такой кадр целиком. Объединение уведомлений IRQ может объединить несколько completions в одно уведомление; счётчик IRQ не равен числу кадров.

Полный receive-путь

На схеме переходите кнопкой «Дальше →». Первые четыре кадра показывают путь одного кадра, затем схема показывает, что произойдёт при исчерпании кольца. Это подготовленные состояния. Кадр на проводе, операции DMA и прерывания не разыгрываются движком. Штатный кодировщик рассчитывает числа для полей описателя.

  1. «Host подготовил кольцо». Драйвер заполнил адрес и вместимость каждого из трёх буферов, установил OWN=1 и опубликовал TAIL=3. Текущая голова HEAD=0. Слот 0 принадлежит RX DMAC, блоку передачи принятых данных.
  2. «Приём кадра». Кадр прошёл выбранные проверки MAC и ждёт передачи из внутреннего буфера. RAM хоста пока содержит прежние байты. Теперь RX DMAC может взять опубликованный описатель 0.
  3. «DMA данных». RX DMAC использует DMA-адрес из описателя и пишет 128 байт в буфер посредством PCIe Memory Write. При включённом IOMMU для устройства должно быть разрешено писать весь затронутый диапазон. Пока OWN=1, драйвер ждёт возврата описателя.
  4. «Возврат описателя». После записи буфера контроллер записывает результат в кольцо. В слоте 0 видим DWORD0=0xC0800080, OWN=0 и границы одного кадра FS=1, LS=1. Драйвер находит буфер, сверяет длину и признаки ошибок. Прерывание при разрешённой доставке может привлечь внимание к новым результатам. В Linux оно обычно планирует опрос NAPI: драйвер читает готовые описатели с заданным пределом работы за один вызов. Он может обнаружить несколько кадров за один опрос. Linux 6.12, NAPI.
  5. Передача кадра и освобождение буфера. Эта часть следует за возвратом описателя и вынесена из схемы первого кадра. Если стек ещё использует буфер, драйвер может опубликовать новый свободный буфер для следующего приёма. Старый можно переиспользовать, когда прежний потребитель больше к нему не обращается. Перед публикацией адресные поля, вместимость и OWN заполняются заново.

Точка наблюдения меняет ответ на вопрос «виден ли кадр». Внешний анализатор линии наблюдает передачу до фильтров контроллера хоста. Драйвер видит возвращённый RX-описатель и байты буфера. Локальный захват в сетевом стеке видит то, что дошло до точки захвата после драйвера. Например, если контроллеру поручили удалить FCS, этих четырёх байтов уже не будет в буфере. Если MAC отбросил кадр до DMA, локальный захват его не получит. Даже кадр, видимый в захвате, может не дойти до приложения: последующие проверки адресов, протокола и правил доступа происходят выше.

На передаче host создаёт payload, описатели и публикацию. DMA читает host RAM, контроллер готовит кадр и передаёт через PHY. Возврат TX descriptor означает установленный datasheet этап; его нельзя без проверки назвать подтверждением получения удалённым приложением. Даже факт отправки последнего символа не доказывает доставку кадра соседу, а кадр соседу не доказывает подтверждение TCP. Прикладная надёжность потребует других уровней.

Разделение очередей и аппаратная помощь

Распределение RSS направляет входные потоки между очередями по хешу выбранных заголовочных полей. Hash — вычисляемое число для выбора, не гарантия равного количества работы и не криптографическая защита. Очереди дают возможность параллельной обработки, но один поток может остаться в одной очереди, и skew нагрузит её сильнее остальных. Привязка очередей к CPU и политика обработки — операционная система; аппаратный механизм лишь предоставляет выбор и идентификаторы.

Checksum offload передаёт контроллеру расчёт/проверку определённых контрольных сумм. Segmentation offload позволяет host передать крупный логический набор для аппаратного формирования нескольких кадров. Поэтому захват данных в разных точках пути может показывать разные размеры и незаполненные checksum до offload. Успех одного offload не доказывает корректность остальных; формат descriptor и supported capabilities читают у конкретного устройства.

Где теряются данные и время

Нет свободных host descriptors — аппаратуре некуда DMA-писать следующий кадр. Заполнен FIFO — возникают потери или предусмотренное управление потоком, которое зависит от среды/настроек. Драйвер долго не возвращает buffers — очередь исчерпывается, хотя line rate и PCIe исправны. Ошибка IOMMU блокирует DMA, даже если PHY link up. Много маленьких кадров даёт высокий packets/s при умеренных bytes/s и большую стоимость descriptors/IRQ на каждый полезный байт.

Для отдельного примера 1 Gb/s Ethernet выберем полный дуплекс: обе стороны могут передавать одновременно. Минимальный кадр занимает 64 B. Перед ним передаются 7 B preamble, преамбулы для синхронизации приёмника, и 1 B SFD, Start Frame Delimiter, маркера начала кадра. Между кадрами нужен IFG, Inter-Frame Gap, интервал длительностью 96 времён передачи одного бита. Это время соответствует 12 байтам при той же скорости; оно не означает передачу ещё 12 байт кадра. Поэтому временной бюджет равен (64+7+1)×8+96=672 битовым временам, или 84 байтовым временам. Получаем 1·10⁹ bit/s ÷672≈1.488·10⁶ кадров/с. Устройство и приложение имеют дополнительные ограничения; в 64 B уже входят канальные поля, а заголовки высших уровней уменьшают полезные данные. Размеры преамбулы и SFD показаны в Microchip AN1120, DS01120A, рис. 3–4. Это расчёт выбранного режима. В следующей главе посмотрим, какие данные передаёт другой контроллер, когда хост запрашивает логический блок накопителя.

Первичный пример аппаратуры: LAN7430/LAN7431 DS00002631D, разделы 6.8–6.9 DMA/FIFO; Microchip AN2948, register/descriptor details. Привязка к реальной модели устройства не означает её наличие или native тест на машине автора.
