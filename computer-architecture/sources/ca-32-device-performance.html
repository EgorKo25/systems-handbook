Очереди и измерение устройств: где теряется время

Полезная пропускная способность, задержка и цена устойчивости требуют одинаковой нагрузки и одинаковой точки завершения.

Разделить времена прежде сравнения

Для одного запроса определим t0 — host начал подготовку, t1 — опубликовал, t2 — контроллер принял работу, t3 — transfer/обработка закончились, t4 — completion виден host, t5 — приложение получило результат. Latency t5−t0 включает программные и аппаратные участки; device latency t3−t2 — меньшую часть. Для persistent write может потребоваться t6 — completion flush/FUA. Сравнивать t4 одного режима с t6 другого без подписи неправильно.

Throughput — число/объём успешных завершений за интервал. IOPS измеряется в operations/s, bandwidth — B/s, latency — s/op или её долях для отдельных запросов. Для 4096 B каждой операции 100000 IOPS даёт 409600000 B/s ≈409.6 MB/s или 390.625 MiB/s. Десятичный MB содержит 10⁶ B, MiB — 2²⁰ B; число не изменилось, единица изменилась. Если часть операций failed, их нельзя незаметно посчитать полезной работой.

Глубина очереди скрывает ожидание

Queue depth — число одновременно незавершённых запросов в выбранной области. При QD1 следующий запрос начинается после предыдущего, поэтому latency ограничивает throughput даже при свободной линии. При достаточной независимой работе несколько запросов перекрывают ожидание. Но после насыщения обслуживающего ресурса новые запросы добавляют главным образом queueing delay, а не полезную полосу.

Закон Литтла L=λ·W связывает среднее число запросов L в стабильной системе, среднюю скорость завершения λ в 1/s и среднее время пребывания W в s. При 100000 op/s и 100 µs =0.0001 s получаем L=10 запросов. Это средние в одном окне/области при согласованном учёте входа/выхода и без неограниченного роста очереди. Оно не доказывает, что заданная глубина 10 гарантирует 100000 IOPS или что p99 равен 100 µs.

Последовательный bandwidth и случайные IOPS — разные нагрузки

Указывают размер transfer, random/sequential адреса, read/write смесь, working set, заполненность SSD, число queues и outstanding, duration, кэширование и durability. Working set — набор адресов, активно используемый в данном окне. Он может поместиться в device/host cache, и тогда опыт измерит cache path вместо предполагаемого media. Для SSD начальный свободный резерв и steady-state garbage collection меняют результат. Для HDD случайные LBA заставляют платить seek/rotation.

Один большой transfer снижает число descriptors/doorbells/completions на полезный byte, но увеличивает занятую память и может задержать короткие запросы. Много queues облегчает параллелизм, но требует больше памяти, CPU polling/IRQ и структуры согласования. Распределение на разные CPU может увеличить удалённые обращения NUMA, где время доступа зависит от размещения памяти относительно CPU; близость controller, buffers и processing важна. Политика размещения — OS; измеряемый аппаратный путь должен быть указан.

Ограничитель ищут по всей цепочке

Для NIC путь ограничен line rate, packet rate MAC, FIFO/descriptors, PCIe payload и host memory/CPU. Для NVMe — host publication, PCIe outstanding/read credits, controller scheduling, NAND channels/FTL и flush semantics. Самое большое число в рекламе одного звена не становится пропускной способностью последовательного пути. Если независимые stages перекрываются, итог определяется bottleneck и буферами, а полная latency остаётся суммой пути конкретного запроса.

Пример верхней оценки: x4Gen3 после 128b/130b около 3.938 GB/s до TLP overhead. Если NAND устойчиво обслуживает 1 GB/s выбранной write нагрузки, увеличение link без изменения NAND не даёт 4 GB/s этой записи. Если QD1 ждёт 200 µs на 4 KiB, предельная последовательная скорость по этому ожиданию около 5000 op/s·4096 B ≈20.48 MB/s, даже если оба предела намного выше. Уменьшение каждого ожидания и увеличение параллелизма решают разные причины.

Распределение и стоимость наблюдения

Среднее скрывает хвост: редкие GC, retries, power-state wake-up и очереди дают выбросы. p99 — граница выбранной процедуры расчёта, ниже/равно которой находятся примерно 99% наблюдений; при nearest-rank берут элемент ceil(0.99N) отсортированных измерений. При N=1000 это 990-й; при N=10 оценка практически сводится к максимуму и ненадёжна для выводов о редких задержках. Метод, окно и количество наблюдений должны сопровождать число.

Источник времени должен быть пригоден для интервала и согласован с точкой измерения. Такты CPU не переводят во время по случайной текущей частоте в GHz, особенно при DVFS и разных тактовых доменах. Чтение counters, tracing и частый polling сами потребляют ресурс, меняют cache/шину и способны повлиять на результат. Включение подробного tracing и сравнение с выключенным без учёта стоимости не даёт сопоставимого сравнения A/B.

Изменяемый опыт без настоящего устройства

В моделях можно сравнить число смысловых переходов до completion/durable и предсказать, какие байты сохранятся после потери питания. Эти шаги не имеют калиброванных наносекунд, поэтому из них нельзя построить «скорость NVMe» или выбрать реальный SSD. Pure tests проверяют инварианты и отрицательные случаи; настоящий benchmark, если появится в дальнейшей практике, требует уже установленных инструментов, собственных удаляемых учебных данных и отдельного разрешённого оборудования.

Для самостоятельного бумажного расчёта оставьте 4 KiB/200 µs, измените только число незавершённых запросов 1→4 и предположите идеально независимое обслуживание без общего bottleneck. Верхняя оценка станет 20000 op/s. Затем добавьте предел 10000 op/s контроллера: ожидаемое увеличение останавливается на нём, дальнейшая очередь увеличит W. Обязательно подпишите предпосылки идеального перекрытия — это изменяемая модель, не полученный аппаратный результат.

Первичные интерфейсы для определения точек: NVMe completion; NIC DMA/FIFO; PCIe request/completion. Формулы и расчёты здесь оригинальны и получены вычислением, без измерения оборудования.
