Внеочередное исполнение и фиксация результата

Готовое число, принятая команда и запись, которую увидело другое ядро, — три разных события.

Выполнить независимое, пока старшее ждёт

В предыдущей главе ADDI ждала число от LW. Теперь между ними есть ещё одна команда, B. Она прибавляет 7 к постоянному x0 и записывает результат для x8. У B есть оба входа, пока A ждёт память. В учебной трассе B вычисляет 7 первой, а ядро принимает её результат после A. Такой порядок работы возможен при внеочередном выполнении (out-of-order, OoO).

C по-прежнему зависит от ответа памяти. Перед загрузкой в x6 было 99, но C должна прибавить 1 к значению, полученному командой A. D использует уже результат C и готовую базу x5.

Переименование снимает конфликт имён

Перед запуском модели x6 указывает на физический регистр P2 со значением 99, а x8 — на P3 со значением 0. Для каждого нового результата переименование выделяет отдельное место. A получает P10 для x6, B получает P11 для x8, C получает P12 для следующего x6. Признак готовности сообщает, можно ли уже читать число из выделенного места.

Таблица RAT хранит последние назначения, которые получают следующие команды. Принятая таблица отдельно хранит соответствия на подтверждённой границе программы. При назначении C сначала берёт из RAT вход x6 → P10, после чего меняет назначение x6 на P12. Поэтому C будет ждать P10, а следующая за ней D — P12. Список свободных регистров показывает, какие физические места ещё можно назначить.

Когда B записывает 7 в P11, она помечает P11 как готовый. A ещё не получила ответа, поэтому P10 остаётся неготовым. После ответа памяти A записывает в P10 число 42, C читает его и получает 43 в P12. Разные физические места позволяют хранить обе версии x6 одновременно. Связь C с результатом A остаётся. Если свободные места исчерпаны, назначение новых результатов приостанавливается.

Retirement удерживает порядок принятия

Буфер переупорядочения (ROB) хранит записи в порядке программы. В его голове находится самая старая непринятая команда. Retirement, или commit, происходит, когда запись в голове готова и у неё нет исключения. В этот момент принятое соответствие регистра меняется на новое.

После события execute B в P11 уже лежит 7, а в принятой таблице x8 по-прежнему указывает на P3 со значением 0. Перед B в голове ROB стоит A, а её результат ещё не готов. Даже execute A только помечает A готовой. При commit A из головы уходит A и принятый x6 становится равен 42. Теперь голова — B. Только при commit B принятое соответствие x8 меняется с P3 на P11 и число 7 становится архитектурно видимым.

После принятия B число 43 уже готово в P12, но принятый x6 пока указывает на P10 с числом 42. Следующее событие commit C переключает x6 на P12 и освобождает P10. Старшие команды к этому моменту уже приняты, а команды после C получили её новое назначение. При повторном выделении места признак готовности сбрасывается.

Отказ A: отмена ссылок и возвращение ресурсов

В варианте с отказом памяти B успевает записать 7 в P11. A получает access-fault в голове ROB. Вместо принятия сцена отменяет A и младшие B, C и D. RAT восстанавливается из принятой таблицы, поэтому x6 остаётся равным 99, x8 остаётся равным 0, а память по 2200 сохраняет ноль. P10, P11 и P12 снова свободны.

При точном исключении обработчик получает состояние после принятых старших команд. В BOOM адрес и причина исключения передаются обработчику после отмены незавершённой работы. Учебная трасса заканчивается сразу после восстановления таблиц. Реальному ядру также нужно отличать ответы отменённых запросов от ответов текущих операций, чтобы поздний ответ не записал старое значение в повторно выделенный регистр.

Запись принята — когда другое ядро увидит 43?

D берёт число 43 из P12 и подготавливает в буфере записей адрес 0x2200 и байты 2B 00 00 00. Событие commit D выставляет committed=true и убирает D из ROB. В этот момент строка памяти по 0x2200 в модели ещё содержит 0.

Затем отдельное событие drain отправляет разрешённую запись из буфера. После него в памяти модели лежит 43. Поле otherCoreObserved остаётся пустым. Срок, в который другое ядро увидит запись, зависит от пути по системе памяти и согласования копий. Собственная загрузка в ядре с подходящим обходом может раньше получить значение из буфера записей. Обращения к устройствам требуют особой осторожности, поскольку уже отправленная запись может вызвать необратимое действие.

Предсказание и спекуляция

Предсказатель переходов выбирает предполагаемое продолжение до известного результата условия. Спекуляция — работа при ещё не подтверждённом предположении. Возьмём двухбитный насыщающийся счётчик: значение ограничено 0…3; увеличение 3 оставляет 3, уменьшение 0 оставляет 0. Состояния 0/1 предсказывают «не взят», 2/3 — «взят». После фактического взятого перехода прибавляем 1, после невзятого вычитаем 1. В этой сцене счётчик обновляется по каждому фактическому исходу.

ДоПрогнозПосле N, не взятПосле T, взят
0: уверенно NN01
1: слабо NN02
2: слабо TT13
3: уверенно TT23

Возьмём BNE по PC1108 из главы о переходах: цель 1104, продолжение 110C, исходы трёх проверок T,T,N. Начальный счётчик 1 сначала предсказывает 110C и ошибается: правильный PC1104, счётчик становится 2. Вторая проверка предсказывает 1104 правильно и переводит 2→3. Третья предсказывает 1104 ошибочно: правильный PC110C, счётчик 3→2. Итого две ошибки из трёх в этом коротком входе. При начальном 0 получим 0→1→2→1 и три ошибки. Число ошибок здесь относится только к последовательности T,T,N.

Направление и адрес цели — разные сведения. BTB, branch target buffer, — таблица ранее известных целей, выбираемая по адресу команды с проверкой нужных признаков. Если счётчик правильно выбрал T, но сохранённая цель устарела и равна 1110 вместо 1104, выборка всё равно идёт неверно. В нашем ограниченном примере запись {PC1108→1104} подготовлена; заменив её на 1110, наблюдаем ошибку адреса при верном направлении. Если выбрано T, но цели нет, модель отмечает прогноз недоступным. При N адрес PC+4 известен и без записи BTB.

Отмена неверного пути

Пусть первая проверка предсказала 110C, и младшая команда по 110C получила физический регистр P14. У перехода сохранена контрольная копия RAT и список выделений после него. Когда вычислен фактический исход T, управление отмечает ошибку, направляет выборку на 1104, отменяет младшие ROB/очереди и возвращает P14. Старшие A/B не отменяются лишь потому, что ещё выполняются. Сам переход при отсутствии своего исключения остаётся правильной командой программы.

Ресурсы возвратятся, но потраченные слоты, энергия и время не вернутся. Могут сохраниться изменения кэша и обученное состояние предсказателя. Политика обновления предсказателей/истории различается; модель предсказателя обновляет счётчик по фактическому исходу. Сам неверный путь разбирается отдельным примером выше. Эти внутренние следы могут менять время последующих обращений, хотя принятые регистровые результаты неверной ветки отсутствуют.

Практика к этому примеру

Откройте «OoO: ответ A, затем принятие». В готовой таблице сравните строки execute B, commit A и commit B. Сцена фиксирует порядок назначений, вычислений и принятия. Строки обозначают события без длительности в тактах. Для BOOM документация описывает тот же принцип приёма с головы ROB, причём за такт ядро может принять несколько готовых записей. Номера P2…P13 и четыре команды относятся к учебной трассе. Следующая глава введёт счётчики принятых инструкций и тактов, чтобы по измерениям посчитать стоимость заданной работы.
