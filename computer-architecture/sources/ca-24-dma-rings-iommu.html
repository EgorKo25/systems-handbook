DMA, очереди дескрипторов и IOMMU

Контроллер может передавать данные без копирования каждого слова CPU. Для этого ему нужен адрес, допустимый диапазон и понятный протокол принадлежности.

DMA не исполняет приложение вместо CPU

Вернёмся к READ из двух предыдущих глав. В ca‑22 контроллер перенёс блок LBA 7, а в ca‑23 процессор получил уведомление о завершении. Теперь повторим то же чтение с включённой трансляцией адресов устройства. Контроллер узнает длину и адрес буфера из описателя. Проследим, почему значение адреса в описателе изменилось, хотя 512 байт должны попасть в прежний физический буфер.

Описатель: адрес, длина и принадлежность

Управляющая программа подготавливает поля op: READ, lba: 7, length: 512 и адрес назначения в address. Поле device: 1 задаёт инициатора обращения для модели. При owner: host программа ещё может исправить адрес. Публикация делает поля доступными контроллеру, передаёт владение и уведомляет устройство через дверной звонок. В сцене это одно действие. После него owner: device, и модель отклоняет редактирование. Сам адрес будет проверен на следующем шаге DMA.

В М32-I/O1 описатель — один объект состояния. В реальном интерфейсе устройство может читать бинарный описатель из очереди в RAM. Кольцо — конечный массив, в котором после последнего слота индекс снова указывает на первый. Например, после индекса 3 в кольце из четырёх слотов идёт 0. Равенство индексов чтения и записи само по себе не объясняет, свободен ли слот. Это определяет протокол конкретного устройства, например через бит очередного оборота, счётчики или правило оставлять один слот пустым.

Когда разрешено несколько незавершённых заданий, управляющей программе надо сопоставить запись завершения с тем заданием, которое её породило. Если интерфейс допускает завершение не по порядку, одного номера текущего слота может быть недостаточно. Буфер сохраняют до прекращения доступа устройства. Тайм-аут ожидания в программе сам по себе не отменяет передачу.

CPU VA не становится DMA-адресом

В профиле Sv32 из главы о MMU процессор обращается к входу через VA 0x00402000. Его таблицы страниц переводят этот адрес в PA 0x2000. В базовой сцене М32-I/O1 адрес DMA совпадает с PA. С включённым IOMMU контроллер получает IOVA 0x4000, адрес в пространстве устройства. Для перевода выбирается контекст инициатора. Значение satp текущего процесса для этого автоматически не берётся.

На реальной платформе DMA-адрес для буфера получают через интерфейс ОС. Например, драйвер Linux передаёт пригодный адрес CPU-буфера в dma_map_single(), проверяет результат отдельно через dma_mapping_error() и передаёт устройству полученный dma_addr_t. Выравнивание и совпадение младших битов двух адресов сами по себе ничего не говорят о пригодности VA для устройства. Linux 6.12, CPU and DMA addresses.

В сцене для устройства 1 заданы две записи. Диапазон IOVA 0x4000…0x41FF переводится в PA 0x2000…0x21FF и разрешает запись памяти. Команда READ читает накопитель, поэтому IOMMU нужна именно эта запись. Диапазон IOVA 0x4200…0x43FF переводится в PA 0x2200…0x23FF и разрешает чтение памяти для команды WRITE накопителя.

Где находятся байты и когда их можно читать

Успешный READ использует смещение внутри записи для устройства 1. Формула в модели выглядит так: PA = 0x2000 + (IOVA − 0x4000). Первый байт приходит в 0x2000, последний — в 0x21FF. Для проверки полной передачи удобно считать правую границу исключённой: 0x4000 + 512 = 0x4200 на стороне устройства и 0x2000 + 512 = 0x2200 на стороне RAM.

Карта совмещает два учебных профиля. Стрелка CPU взята из Sv32, а передача IOVA — из М32-I/O1. М32-I/O1 применяет только свою плоскую таблицу. В этой сцене дверной звонок представлен отметкой DBELL=1 в журнале. Условный адрес 0xF000 из ca‑22 поясняет карту регистров устройства. Обращение к этому адресу движок не исполняет.

Отдельный расчёт размещения кольца. Пусть для кольца выделены 64 байта непрерывной RAM начиная с PA R=3000h, а для устройства это выделение доступно с DMA-адреса D=8000h. Это дополнительное условие примера allocation, выделения памяти и её DMA-отображения; оно не добавляет запись в плоский список двух отображений данных М32-I/O1. Выберем четыре слота по 16 байт, не определяя их бинарные поля. Слот i начинается по PA R+i×16 и DMA-адресу D+i×16. CPU VA этого выделения здесь не задан.

Последний слот занимает PA 3030..303Fh; всё кольцо — PA 3000..303Fh. После слота 3 следующий индекс (3+1) mod 4 равен 0. Размер шага в 16 байт и этот оборот описывают геометрию, но не говорят, свободен ли слот: для этого по-прежнему нужен протокол публикации и завершения. Указатель на основание очереди передают контроллеру отдельно от адреса буфера внутри записи. М32-I/O1 такую настройку и чтение записей кольца не исполняет.

prepare-read
owner=host, published=false; completion отсутствует. Вход PA 2000..21FF содержит 512 нулей; CPU ещё может исправить описатель.
publish
owner=device, published=true. Вход не изменён; позднее редактирование описателя отклоняется.
dma-read
owner=device; completion всё ещё отсутствует. Вход содержит 2A 00 00 00 и 508 нулей.
complete-read
owner=completed, published=false; SUCCESS, bytes=512; IRQ pending=1. Данные уже переданы; способ их видимости CPU принят условием модели.
observe
CPU проверяет completion опросом или в обработчике; readObserved=true. Теперь разрешён следующий CPU-урок. При входе в обработчик сначала нужен возврат из него.

Входная область становится доступна для следующего шага CPU после наблюдения записи завершения. В сцене READ меняет только вход. Позднее CPU читает четыре байта и записывает четыре байта результата по 0x2200…0x2203. Полный 512-байтовый блок для обратной записи готовится отдельной кнопкой.

Граница диапазона и устаревший перевод

При «3 · DMA READ 512 B» модель сначала ищет одну запись для устройства 1, покрывающую весь диапазон, затем проверяет право записи. Для 0x4000 и длины 512 обе проверки проходят. Если начать с 0x4001, последний запрошенный байт окажется по 0x4200, уже вне разрешённой записи. При 0x4200 весь диапазон попадает во вторую запись, но та разрешает только чтение. Если вставить CPU VA 0x00402000, подходящей записи для такого начала нет. Во всех трёх случаях отказ происходит до изменений RAM. В тестах движка отдельно проверены другой инициатор и допустимый диапазон длиной лишь 511 байт.

Настоящий контроллер может разбить передачу 512 B на несколько транзакций. IOMMU проверяет адреса и права обращений устройства; отказ поздней транзакции не обещает откат уже записанных прежними транзакциями байтов. Например, первая часть буфера могла обновиться до обнаружения отсутствующего отображения следующей страницы. В RISC-V IOMMU 1.0.1 §2.3 мост передаёт на трансляцию аппаратный идентификатор инициатора, адрес, направление и число байтов. В реальном интерфейсе идентификатор приходит от тракта ввода-вывода, тогда как сцене его даёт поле device. Переносимые байты идут по тракту данных моста. Из этого интерфейса нельзя вывести атомарную запись целого сектора.

При включённом преобразовании отсутствие нужного отображения вызывает fault устройства. Это отдельный путь от CPU page fault приложения. Состояние контроллера и очереди после отказа определяется платформой; программе требуется предусмотренная обработка восстановления. Аппаратная проверка не переотправляет исходную заявку автоматически и не делает повреждённый частичным переносом буфер пригодным для потребителя.

IOMMU может кэшировать переводы. Изменить таблицу в RAM недостаточно для гарантии, что следующий запрос не использует старую запись: нужны предусмотренные invalidation/fence и завершение этих управляющих операций. Прежде чем освободить буфер или передать его другому владельцу, надо прекратить старые DMA и убрать пригодность старых переводов по правилам платформы. После reset устройства старые неполученные completion также нельзя безусловно принимать как новый успех.

Coherent и non-coherent DMA

При согласованном с кэшами DMA аппаратная система обеспечивает видимость общих данных, а управляющая программа по-прежнему должна опубликовать поля до уведомления. На несогласованной платформе при READ накопитель уже мог изменить RAM, а CPU ещё видеть старую линию в кэше. Перед чтением буфера применяют предусмотренное платформой обслуживание кэша. Барьер управляет порядком доступов, поэтому требования к видимости и упорядочению проверяют отдельно.

В Linux 6.12 для повторно используемого потокового, streaming, DMA-буфера dma_sync_*_for_cpu выполняют после передачи перед доступом CPU, а требуемый dma_sync_*_for_device — перед новым доступом устройства. Эти вызовы учитывают направление и платформу; DMA mapping, cache sync и барьер порядка решают разные задачи. Окончание ожидания CPU не является окончанием DMA. Перед unmap и освобождением буфера устройство должно закончить доступ.

dma_wmb и dma_rmb в Linux упорядочивают соответствующие доступы к совместно используемой DMA-памяти. Они не дают общей гарантии порядка для MMIO. Запись doorbell требует подходящего I/O accessor, функции доступа к регистру, и правил конкретной платформы. Поэтому схему «поля → публикация → doorbell» нельзя реализовать произвольным сохранением в C и одним DMA-барьером. Это различие прямо указано в Linux 6.12, Explicit kernel barriers, dma_*().

Эти различия разобраны в Linux 6.12, Dynamic DMA mapping Guide: CPU and DMA addresses, Types of DMA mappings, Using Streaming DMA mappings. Здесь использованы правила адресации и видимости; исполняемого драйвера Linux в модели нет.

Практика к этому примеру

Откройте М32-I/O1 с исходным состоянием. Если READ из ca‑23 ещё открыт, сохраните его кнопкой «Скачать JSON», прежде чем начинать новый опыт. В «Другой порядок и ошибки» отметьте «Явный IOMMU-профиль: IOVA 4000→PA 2000; IOVA 4200→PA 2200» до нажатия «1 · Подготовить READ». Строка Descriptor покажет address: 16384, то есть 0x4000, length: 512 и owner: host.

До публикации можно ввести адрес в поле «Адрес HOST descriptor» и применить его кнопкой «Изменить адрес до передачи OWN». Сохраните подготовленное состояние через «Скачать JSON», чтобы вернуться к нему для каждого варианта. В штатном варианте оставьте 0x4000. Нажмите «2 · Опубликовать descriptor», попробуйте изменить адрес и проверьте отказ при owner: device. Затем «3 · DMA READ 512 B» заполнит входной буфер. Только «4 · READ completion» добавит ответ READ / SUCCESS / 512. Для сравнения загрузите прежний JSON перед публикацией, задайте 0x00402000, 0x4001 или 0x4200, затем снова опубликуйте и попробуйте DMA. По сообщению различите отсутствие отображения целого диапазона и запрет направления.
