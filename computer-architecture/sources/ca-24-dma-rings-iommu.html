DMA, кольца и IOMMU: кто владеет байтами

Контроллер может передавать данные без копирования каждого слова CPU. Для этого ему нужен адрес, допустимый диапазон и понятный протокол принадлежности.

DMA не исполняет приложение вместо CPU

DMA, direct memory access, — прямой доступ устройства к памяти через аппаратный путь. Процессор готовит управление, а контроллер выдаёт запросы чтения/записи памяти и передаёт байты. Передача DMA размером 512 байт не означает 512 отдельных load/store-инструкций нашей программы. Bus mastering означает способность устройства выступать инициатором транзакций; это не привилегированный режим CPU и не право исполнять произвольный код в его регистрах.

В сквозном чтении descriptor указывает READ LBA 7,512 B и PA 2000. Контроллер считывает сектор, затем инициирует DMA writes в PA 2000..21FF. Первые 4 B становятся 2A 00 00 00, оставшиеся 508 — нули. CPU позднее делает LW, читающую 4 байта, ADDI и SW, записывающую 4 байта в PA 2200..2203. Результат 43 в RAM не создаёт автоматически новый 512 B выходной сектор. Отдельная подготовка 512-байтного буфера копирует хвост исходного сектора и заменяет только первые 4 B; в модели этот шаг имеет собственную кнопку и журнал.

Для сравнения объёма работы: программное копирование тех же 512 байт выровненными 32-битными словами потребует 128 загрузок и 128 записей, плюс управление циклом. DMA освобождает CPU от этих 256 инструкций копирования, но данные всё равно проходят межсоединение и память; добавляются настройка, описатели и обработка результата. При очень малом буфере их цена может перевесить выгоду. Пять исходных инструкций М32 не выполняют это копирование.

Описатель: адрес, длина и принадлежность

Небольшой учебный descriptor имеет operation, lba, address, length, requester и owner. Реальный формат может быть упакован в бинарные поля, содержать несколько адресов и специальные status bits. Поля создаёт управляющая программа в своей памяти, затем публикует контроллеру. Owner=host означает, что программа ещё может их исправить; owner=device запрещает такое редактирование до возвращения по принятому протоколу. Это логическое правило совместной работы, которое аппаратно не обязано предотвращать каждую ошибочную CPU-запись.

Ring, «кольцо», — очередь в массиве ограниченного размера с возвратом индекса в начало. Producer, «производитель», публикует новые элементы; consumer, «потребитель», забирает. Например, в кольце из 4 слотов индексы 0,1,2,3,0 повторяются. Равные head/tail сами по себе неоднозначны: это может быть пустота или полное кольцо после оборота. Дополнительный phase/owner bit, счётчики или правило оставлять один пустой слот разрешают неоднозначность. Нельзя скопировать одно правило в любой datasheet: каждый интерфейс задаёт собственное.

После публикации 3 описателей потребитель может завершить их не тем же временным порядком, если интерфейс разрешает. Нужны идентификаторы задания и корректное сопоставление completion. Повторное использование слота до обработки прежнего завершения создаёт риск принять старый результат за новый. Срок жизни DMA-буфера должен включать всю передачу, а не только момент постановки задания. Отменить ожидание в приложении ещё не значит, что контроллер перестал писать по переданному адресу.

CPU VA не становится DMA-адресом

Глава MMU уже разделила CPU virtual address и physical address. При Sv32 VA 00402000 преобразуется в PA 2000 таблицами CPU. Устройство не обязано видеть этот же CPU VA и не использует автоматически satp текущей программы. Записать 00402000 в descriptor «потому что CPU так обращается к буферу» — ошибка выбора адресного пространства. На простой платформе DMA-address может совпадать с PA, на другой есть смещение/окно, а с IOMMU применяется собственное преобразование.

IOMMU, input/output memory management unit, — аппаратная проверка и преобразование адресов обращений устройств. IOVA, I/O virtual address, относится к этому пути. Таблицы/контексты определяют, какие адреса и направления допускаются для идентичности requester. CPU MMU проверяет инструкцию CPU, IOMMU — транзакцию устройства; один блок не заменяет другой. Программное создание mapping и выбор того, кому выделить буфер, относятся к операционной системе или monitor, а проверка отображения — аппаратный механизм.

В дополнительном профиле М32-I/O1 IOVA 4000..41FF → PA 2000..21FF допускает устройству 1 записывать RAM при READ накопителя. IOVA 4200..43FF → PA 2200..23FF допускает тому же устройству читать RAM при WRITE накопителя. Слова READ/WRITE команды накопителя и направление доступа к RAM противоположны: «читать диск» требует «писать RAM». Эту таблицу нужно читать по двум участникам, иначе разрешение легко выдать в неверную сторону.

Граница диапазона и устаревший перевод

В М32-I/O1 перед переносом проверяется весь диапазон 512 B. Это предварительная проверка целой учебной заявки: отображение на 511 байт не покрывает последний байт, поэтому модель отклонит действие до изменения RAM. Requester другого устройства также не получает разрешение по одному совпадению IOVA. Такой порядок позволяет отдельно наблюдать адрес, длину и право в конечной модели.

Настоящий контроллер может разбить передачу 512 B на несколько транзакций. IOMMU проверяет адреса и права обращений устройства; отказ поздней транзакции не обещает откат уже записанных прежними транзакциями байтов. Например, первая часть буфера могла обновиться до обнаружения отсутствующего отображения следующей страницы. В RISC-V IOMMU 1.0.1 §2.3 мост передаёт запрос преобразования с идентичностью, адресом, направлением и числом байтов; сами данные через IOMMU не проходят. Из этого интерфейса нельзя вывести атомарную запись целого сектора.

При включённом преобразовании отсутствие нужного отображения вызывает fault устройства. Это отдельный путь от CPU page fault приложения. Состояние контроллера и очереди после отказа определяется платформой; программе требуется предусмотренная обработка восстановления. Аппаратная проверка не переотправляет исходную заявку автоматически и не делает повреждённый частичным переносом буфер пригодным для потребителя.

IOMMU может кэшировать переводы. Изменить таблицу в RAM недостаточно для гарантии, что следующий запрос не использует старую запись: нужны предусмотренные invalidation/fence и завершение этих управляющих операций. Прежде чем освободить буфер или передать его другому владельцу, надо прекратить старые DMA и убрать пригодность старых переводов по правилам платформы. После reset устройства старые неполученные completion также нельзя безусловно принимать как новый успех.

Coherent и non-coherent DMA

DMA coherence означает согласованную видимость с CPU caches на данной платформе. При coherent DMA аппаратная система обеспечивает нужное взаимодействие, но правила публикации descriptor/doorbell и ownership всё равно остаются. При non-coherent DMA CPU может читать старую cache line, пока устройство уже изменило RAM, или устройство — прочитать старую RAM, пока CPU держит dirty data в cache. Тогда требуются документированные операции очистки/инвалидации в нужном направлении и порядке. Точный API драйвера будет в томах OS/Linux; слово «барьер» само не выполняет всю cache maintenance.

В модели включите IOMMU до подготовки задания. Адрес 4000 допустим, CPU VA 00402000 — нет; редактирование после publish тоже отклоняется. Тесты модели отдельно проверяют чужой requester и запрещённое направление, неполный диапазон и выход PA за RAM. Эти проверки не являются испытанием настоящего IOMMU. В источниках выбран RISC-V IOMMU 1.0.1. Модель хранит плоский список отображений вместо многоуровневых таблиц этого стандарта.
