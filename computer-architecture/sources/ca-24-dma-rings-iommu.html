DMA, кольца и IOMMU: кто владеет байтами

Контроллер может передавать данные без копирования каждого слова CPU. Для этого ему нужен адрес, допустимый диапазон и понятный протокол принадлежности.

DMA не исполняет приложение вместо CPU

DMA, direct memory access, — прямой доступ устройства к памяти через аппаратный путь. Процессор готовит управление, а контроллер выдаёт запросы чтения/записи памяти и передаёт байты. Передача DMA размером 512 байт не означает 512 отдельных load/store-инструкций нашей программы. Bus mastering означает способность устройства выступать инициатором транзакций; это не привилегированный режим CPU и не право исполнять произвольный код в его регистрах.

В сквозном чтении описатель задания указывает READ LBA 7, длину 512 B и PA 2000h. Контроллер считывает сектор, затем инициирует DMA writes в PA 2000..21FF. Первые 4 B становятся 2A 00 00 00, оставшиеся 508 — нули. CPU позднее делает LW, читающую 4 байта, ADDI и SW, записывающую 4 байта в PA 2200..2203. Результат 43 в RAM не создаёт автоматически новый 512 B выходной сектор. Отдельная подготовка 512-байтного буфера копирует хвост исходного сектора и заменяет только первые 4 B; в модели этот шаг имеет собственную кнопку и журнал.

Для сравнения объёма работы: программное копирование тех же 512 байт выровненными 32-битными словами потребует 128 загрузок и 128 записей, плюс управление циклом. DMA освобождает CPU от этих 256 инструкций копирования, но данные всё равно проходят межсоединение и память; добавляются настройка, описатели и обработка результата. При очень малом буфере их цена может перевесить выгоду. Пять исходных инструкций М32 не выполняют это копирование.

Описатель: адрес, длина и принадлежность

Небольшой учебный descriptor, описатель задания, в М32-I/O1 имеет поля op, lba, address, length, device и owner. Поле device задаёт requester — идентичность устройства-инициатора. Модель хранит один объект JavaScript с логическим состоянием owner; байтовая упаковка, физический адрес кольца и аппаратный OWN-бит для него не заданы. Реальный формат может быть упакован в бинарные поля, содержать несколько адресов и специальные status bits. Поля создаёт управляющая программа в своей памяти, затем публикует контроллеру. Owner=host означает, что программа ещё может их исправить; owner=device запрещает такое редактирование до возвращения по принятому протоколу. Это логическое правило совместной работы, которое аппаратно не обязано предотвращать каждую ошибочную CPU-запись.

Ring, «кольцо», — очередь в массиве ограниченного размера с возвратом индекса в начало. Producer, «производитель», публикует новые элементы; consumer, «потребитель», забирает. Например, в кольце из 4 слотов индексы 0,1,2,3,0 повторяются. Равные head/tail сами по себе неоднозначны: это может быть пустота или полное кольцо после оборота. Дополнительный phase/owner bit, счётчики или правило оставлять один пустой слот разрешают неоднозначность. Нельзя скопировать одно правило в любой datasheet: каждый интерфейс задаёт собственное.

После публикации 3 описателей потребитель может завершить их не тем же временным порядком, если интерфейс разрешает. Нужны идентификаторы задания и корректное сопоставление completion — сообщения о завершении задания. Повторное использование слота до обработки прежнего завершения создаёт риск принять старый результат за новый. Срок жизни DMA-буфера должен включать всю передачу, а не только момент постановки задания. Отменить ожидание в приложении ещё не значит, что контроллер перестал писать по переданному адресу.

CPU VA не становится DMA-адресом

Глава MMU уже разделила CPU virtual address и physical address. При Sv32 VA 00402000 преобразуется в PA 2000 таблицами CPU. Устройство не обязано видеть этот же CPU VA и не использует автоматически satp текущей программы. Записать 00402000 в descriptor «потому что CPU так обращается к буферу» — ошибка выбора адресного пространства. На простой платформе DMA-address может совпадать с PA, на другой есть смещение/окно, а с IOMMU применяется собственное преобразование.

IOMMU, input/output memory management unit, — аппаратная проверка и преобразование адресов обращений устройств. IOVA, I/O virtual address, относится к этому пути. Таблицы/контексты определяют, какие адреса и направления допускаются для идентичности requester. CPU MMU проверяет инструкцию CPU, IOMMU — транзакцию устройства; один блок не заменяет другой. Программное создание отображения, mapping, и выбор того, кому выделить буфер, относятся к операционной системе или monitor, а проверка отображения — аппаратный механизм.

В дополнительном профиле М32-I/O1 IOVA 4000..41FF → PA 2000..21FF допускает устройству 1 записывать RAM при READ накопителя. IOVA 4200..43FF → PA 2200..23FF допускает тому же устройству читать RAM при WRITE накопителя. Слова READ/WRITE команды накопителя и направление доступа к RAM противоположны: «читать диск» требует «писать RAM». Эту таблицу нужно читать по двум участникам, иначе разрешение легко выдать в неверную сторону.

Где находятся байты и когда их можно читать

На следующей карте выбран READ из LBA 7 длиной 512 байт с включённым IOMMU. Обозначение READ относится к накопителю: устройство получает сектор и пишет его в RAM. В поле address находится IOVA 4000h, а не CPU VA 00402000h. Плоская запись модели для устройства 1 даёт PA = 2000h + (IOVA − 4000h). Поэтому последний байт заявки 41FFh попадает в PA 21FFh; конец диапазона, не включённый в передачу, равен IOVA 4200h и PA 2200h. В этой записи разрешена запись RAM, но запрещено её чтение устройством.

Карта совмещает адреса из двух согласованных учебных профилей: CPU Sv32 обращается к входу через VA 00402000h, М32-I/O1 выполняет DMA к той же физической области через IOVA 4000h. Сам engine.js не обходит таблицы CPU и не хранит RAM-копию описателя. Слово «кольцо» выше описывает возможную организацию очереди настоящего интерфейса. Адрес его основания, размер записи и способ возврата слота задаёт выбранное устройство; вывести их из полей этого объекта нельзя.

Переход publish означает подготовленную видимость полей, передачу управления и doorbell — уведомление контроллера о новом задании. Отдельный MMIO-адрес doorbell модель не задаёт. Статус completed ещё не означает, что CPU наблюдал результат: для этого есть следующий переход observe.

Отдельный пример размещения, не память engine. Пусть для кольца выделены 64 байта непрерывной RAM начиная с PA R=3000h, а для устройства это выделение доступно с DMA-адреса D=8000h. Это дополнительное условие примера allocation, выделения памяти и её DMA-отображения; оно не добавляет запись в плоский список двух отображений данных М32-I/O1. Выберем четыре слота по 16 байт, не определяя их бинарные поля. Слот i начинается по PA R+i×16 и DMA-адресу D+i×16. CPU VA этого выделения здесь не задан.

Последний слот занимает PA 3030..303Fh; всё кольцо — PA 3000..303Fh. После слота 3 следующий индекс (3+1) mod 4 равен 0. Размер шага в 16 байт и этот оборот описывают геометрию, но не говорят, свободен ли слот: для этого по-прежнему нужен протокол публикации и завершения. Указатель на основание очереди передают контроллеру отдельно от адреса буфера внутри записи. М32-I/O1 такую настройку и чтение записей кольца не исполняет.

prepare-read
owner=host, published=false; completion отсутствует. Вход PA 2000..21FF содержит 512 нулей; CPU ещё может исправить описатель.
publish
owner=device, published=true. Вход не изменён; позднее редактирование описателя отклоняется.
dma-read
owner=device; completion всё ещё отсутствует. Вход содержит 2A 00 00 00 и 508 нулей.
complete-read
owner=completed, published=false; SUCCESS, bytes=512; IRQ pending=1. Данные уже переданы; способ их видимости CPU принят условием модели.
observe
CPU проверяет completion опросом или в обработчике; readObserved=true. Теперь разрешён следующий CPU-урок. При входе в обработчик сначала нужен возврат из него.

Смысл передачи владения — исключить одновременное изменение задания или повторное использование его буфера. Успех публикации ещё не означает переноса данных, а изменившиеся байты ещё не заменяют completion. В М32-I/O1 попытка observe между dma-read и complete-read отказывает, хотя в RAM уже есть 42. После наблюдения результата CPU читает только 4 байта. Выход PA 2200..23FF этим READ не меняется; последующая SW изменит лишь PA 2200..2203, а хвост выходного сектора готовится отдельным действием.

Граница диапазона и устаревший перевод

В М32-I/O1 перед переносом проверяется весь диапазон 512 B. Это предварительная проверка целой учебной заявки: отображение на 511 байт не покрывает последний байт, поэтому модель отклонит действие до изменения RAM. Requester другого устройства также не получает разрешение по одному совпадению IOVA. Такой порядок позволяет отдельно наблюдать адрес, длину и право в конечной модели.

Настоящий контроллер может разбить передачу 512 B на несколько транзакций. IOMMU проверяет адреса и права обращений устройства; отказ поздней транзакции не обещает откат уже записанных прежними транзакциями байтов. Например, первая часть буфера могла обновиться до обнаружения отсутствующего отображения следующей страницы. В RISC-V IOMMU 1.0.1 §2.3 мост передаёт запрос преобразования с идентичностью, адресом, направлением и числом байтов; сами данные через IOMMU не проходят. Из этого интерфейса нельзя вывести атомарную запись целого сектора.

При включённом преобразовании отсутствие нужного отображения вызывает fault устройства. Это отдельный путь от CPU page fault приложения. Состояние контроллера и очереди после отказа определяется платформой; программе требуется предусмотренная обработка восстановления. Аппаратная проверка не переотправляет исходную заявку автоматически и не делает повреждённый частичным переносом буфер пригодным для потребителя.

IOMMU может кэшировать переводы. Изменить таблицу в RAM недостаточно для гарантии, что следующий запрос не использует старую запись: нужны предусмотренные invalidation/fence и завершение этих управляющих операций. Прежде чем освободить буфер или передать его другому владельцу, надо прекратить старые DMA и убрать пригодность старых переводов по правилам платформы. После reset устройства старые неполученные completion также нельзя безусловно принимать как новый успех.

Coherent и non-coherent DMA

DMA coherence означает согласованную видимость с CPU caches на данной платформе. При coherent DMA аппаратная система обеспечивает нужное взаимодействие, но правила публикации descriptor/doorbell и ownership всё равно остаются. При non-coherent DMA CPU может читать старую cache line, пока устройство уже изменило RAM, или устройство — прочитать старую RAM, пока CPU держит dirty data в cache. Тогда требуются документированные операции очистки/инвалидации в нужном направлении и порядке. Точный API драйвера будет в томах OS/Linux; слово «барьер» само не выполняет всё обслуживание кэша.

Барьер порядка ограничивает перестановку доступов; он не обязан очищать грязные строки кэша. Даже coherent-память требует правильного порядка «поля описателя → признак публикации → уведомление». При non-coherent DMA cache maintenance, обслуживание кэша, обеспечивает требуемую видимость: перед чтением устройством обновлённые CPU данные должны стать доступны DMA; после записи устройством CPU не должен использовать старую кэшированную копию. Точный набор операций задаёт платформа.

В Linux 6.12 dma_map_* создаёт пригодное DMA-отображение и возвращает DMA-адрес; ошибку mapping проверяют до публикации. Для повторно используемого потокового, streaming, DMA-буфера dma_sync_*_for_cpu выполняют после передачи перед доступом CPU, а требуемый dma_sync_*_for_device — перед новым доступом устройства. Эти вызовы учитывают направление и платформу; DMA mapping, cache sync и барьер порядка решают разные задачи. Окончание ожидания CPU не является окончанием DMA. Перед unmap и освобождением буфера устройство должно закончить доступ.

dma_wmb и dma_rmb в Linux упорядочивают соответствующие доступы к совместно используемой DMA-памяти. Они не дают общей гарантии порядка для MMIO. Запись doorbell требует подходящего I/O accessor, функции доступа к регистру, и правил конкретной платформы. Поэтому схему «поля → публикация → doorbell» нельзя реализовать произвольным сохранением в C и одним DMA-барьером. Это различие прямо указано в Linux 6.12, Explicit kernel barriers, dma_*().

Эти различия разобраны в Linux 6.12, Dynamic DMA mapping Guide: CPU and DMA addresses, Types of DMA mappings, Using Streaming DMA mappings. Здесь использованы правила адресации и видимости; исполняемого драйвера Linux в модели нет.

В модели включите IOMMU до подготовки задания. Адрес 4000 допустим, CPU VA 00402000 — нет; редактирование после publish тоже отклоняется. Тесты модели отдельно проверяют чужой requester и запрещённое направление, неполный диапазон и выход PA за RAM. Эти проверки не являются испытанием настоящего IOMMU. В источниках выбран RISC-V IOMMU 1.0.1. Модель хранит плоский список отображений вместо многоуровневых таблиц этого стандарта.
