Firmware и загрузка: кто исполняется раньше ядра

После reset процессор не угадывает имя программы. Платформа предоставляет начальную точку, подготавливает оборудование и передаёт управление загрузчику, затем ядру с предусмотренными параметрами.

Reset — определённое начальное состояние

Reset приводит части системы к документированному исходному состоянию. CPU начинает с определённого платформой адреса/состояния, а не произвольной точки оставшейся RAM. Firmware, «встроенное программное обеспечение», — код раннего управления платформой, доступный по этому начальному пути, например из flash/ROM. Оно остаётся программой: читает регистры, выполняет ветвления, проверяет ошибки. Физическое наличие firmware в чипе не делает её безошибочной или автоматически доверенной.

Конкретный x86 reset vector, AArch64 boot protocol и RISC-V reset address имеют разные правила. В RISC-V M-mode является исходным наиболее привилегированным режимом, но конкретное размещение reset firmware определяется платформой. М32 с готовым кодом PA 1000 — подготовленное учебное состояние после нужных действий размещения; это не описание power-on любого RISC-V чипа. Нельзя считать загрузку браузерного JSON реальной прошивкой CPU.

Память ещё нужно сделать пригодной

Контроллер DRAM должен получить допустимые параметры и согласовать работу с модулями. Memory training — процедура поиска пригодных временных/электрических условий обмена на конкретной плате/скорости. Она не равна созданию таблиц virtual memory. До её завершения ранний код может использовать ROM, внутреннюю SRAM или специфический временный режим. Разные платформы имеют разную последовательность; UEFI specification не определяет единственный алгоритм training каждого DIMM.

Затем обнаруживаются доступные области памяти и устройства, назначаются ресурсы, настраиваются минимальные пути чтения. Обнаружение PCIe использует конфигурационные обращения, а доступ к загрузочному накопителю — driver/protocol firmware. Данные, которые будущему ядру надо знать, передаются через предусмотренные структуры: например, UEFI tables, ACPI или device tree по конкретному протоколу загрузки. Таблица описания оборудования не является самим драйвером и не делает устройство готовым принять любой DMA.

UEFI: интерфейс служб, а не синоним всей ранней электроники

UEFI 2.11 задаёт интерфейсы между firmware и загружаемыми UEFI images. Image — исполнимый объект подходящего формата и machine type. Boot manager выбирает запись загрузки по настройкам и доступным путям; OS loader, загрузчик ОС, подготавливает код и данные будущего ядра. Успешно прочитать bytes файла недостаточно: image должен быть проверен, размещён, при необходимости relocated и запущен с допустимыми параметрами. Формат исполнимого объекта и таблицы размещения будут также нужны в томе OS.

Boot Services предоставляют функции, пригодные до передачи владения окружением загрузки. Runtime Services — другой набор с отдельными условиями, часть которого может использоваться после перехода. Нельзя продолжать вызывать произвольный firmware allocator или disk Boot Service после ExitBootServices. После этого перехода Boot Services прекращают предоставлять выделение памяти и доступ к устройствам для загрузчика.

Memory map и MapKey

GetMemoryMap возвращает список областей с типом, начальным physical address, числом страниц и атрибутами, а также параметры размера/версии descriptor и MapKey. Размер descriptor передаётся явно: нельзя идти по массиву с произвольно угаданным sizeof старой структуры. MapKey — идентификатор текущей версии карты; это не ключ шифрования и не пароль. Пока firmware владеет этой картой, вызывающая image использует память, выделенную ей по правилам Boot Services.

Loader получает карту и ключ K. Если после этого выделение памяти изменило карту, прежний K уже не подтверждает актуальную версию. ExitBootServices с устаревшим key должен отказать; loader получает новую карту и повторяет допустимую последовательность. После первой попытки ExitBootServices firmware уже может частично остановить Boot Services, даже если получен отказ. Поэтому loader не возвращается к обычным console/device APIs и не делает Print ради диагностики; он ограничивается предусмотренными Memory Allocation Services и GetMemoryMap/повтором ExitBootServices. Отказ не обещает полного отката интерфейса к состоянию до вызова. Самая наглядная гонка — print/вспомогательный вызов, который неявно выделил память между получением карты и exit. Поэтому изменение набора вызовов влияет на корректность передачи, даже если адрес ядра прежний.

После успешного ExitBootServices управляющая программа принимает ответственность за дальнейшую работу и допустимое использование памяти по типам/атрибутам. Firmware runtime regions и другие зарезервированные области нельзя безусловно включить в свободный пул. Переход к kernel entry включает отдельный конкретный ABI: режим CPU, карты адресов, регистры/указатели параметров, состояние interrupts и cache по выбранному boot protocol. UEFI не задаёт одну универсальную register layout для каждого произвольного ядра.

Размер буфера карты и последняя допустимая петля

GetMemoryMap получает размер предоставленного буфера через MemoryMapSize и сообщает требуемый размер при EFI_BUFFER_TOO_SMALL. EFI_MEMORY_DESCRIPTOR — запись с типом, физическим начальным адресом, числом страниц и атрибутами; DescriptorSize сообщает шаг между записями данной версии. Его нельзя заменить на размер локальной C-структуры или считать, что map всегда массив фиксированных 40 B. DescriptorVersion также проверяется по принятому ABI. Фактическая длина карты и вместимость предоставленного буфера могут различаться.

Числовой пример не layout реальной машины: текущая карта имеет 10 записей, DescriptorSize=48 байт, требуется 480 B. Запрос с буфером 320 байт даёт BUFFER_TOO_SMALL и нужный размер 480. Выделение нового буфера само способно расширить карту: допустим стало 11×48=528 B. Поэтому выделить ровно прежние 480 B и сразу ждать success нельзя. Загрузчик выделяет место с запасом для дополнительных записей, снова передаёт реальную вместимость и проверяет статус, полученную длину и MapKey. Величина запаса зависит от работы загрузчика. Если места снова мало, допустимое выделение и повтор продолжаются до успеха либо явной ошибки ресурсов.

Получив карту, загрузчик сохраняет вместе буфер, MemoryMapSize, MapKey, DescriptorSize/Version и избегает новых ненужных выделений. Число записей вычисляется с проверкой длины и шага. При обходе указатель увеличивается на DescriptorSize; чтение за MemoryMapSize недопустимо. Затем ExitBootServices(ImageHandle, MapKey). При EFI_INVALID_PARAMETER обновляем map и повторяем EBS; после первой попытки уже действует ограничение предыдущего раздела, поэтому console Print/device calls не вклиниваются в retry. Успех не означает, что все memory types стали RAM для свободного использования: RuntimeServices/резервированные области сохраняют свои условия.

В модели M32-BOUND1 первая попытка EBS с устаревшей MapKey оставляет запись об отказе и ограничивает последующие вызовы. Это ошибка с изменением состояния: прежний набор доступных служб не восстанавливается. После неё разрешены получение карты, предусмотренные операции памяти и retry; произвольный вызов Boot Service отклоняется. Карта реального компьютера и её двоичный буфер в модели не строятся.

Подпись загрузчика и смысл доверия

Secure Boot проверяет допустимость загружаемых images по установленной политике ключей/подписей/запретов. PK, platform key, связан с владельцем политики; KEK разрешает определённые обновления key databases; db/dbx описывают доверенное и отозванное согласно интерфейсу. Это разные роли, не четыре названия одного секретного ключа. В книгу не включены настоящие ключи платформы и нет инструкции менять настройки рабочего firmware.

Подпись подтверждает происхождение/допуск конкретного объекта по принятой цепочке. Она не доказывает отсутствие уязвимостей, пригодность конфигурации или сохранность пользовательских файлов. Measured boot записывает измерения выбранных объектов в защищённую цепочку/регистры для дальнейшей проверки; измерение и запрет запуска имеют разные цели. Повреждённая firmware, ошибочные доверенные ключи или неисправный recovery path требуют собственного анализа. Обновление firmware является отдельной чувствительной операцией и здесь на хосте не выполняется.

Изменяемый пример передачи владения

В текстовом сценарии есть карта с символическим ключом 5, выделенные loader pages и kernel image. Получить карту 5 → выделить ещё page → карта 6 → ExitBootServices(key5) даёт отказ. Повторно получить карту 6 → ExitBootServices(key6) даёт успех; последующие Boot Service вызовы недопустимы. Сравните оба варианта в модели границ. Числа 5/6 символические; настоящая MapKey не обещана последовательным счётчиком. Модель не вызывает UEFI, не читает boot variables и не меняет настройки компьютера.

Первичные интерфейсы: UEFI 2.11 Boot Services: GetMemoryMap/ExitBootServices; Boot Manager; Secure Boot.
