Шины и адресация устройств

При чтении с накопителя процессор сначала записывает число в регистр контроллера. Затем сам контроллер переносит 512 байт в память. Проследим, по каким адресам идут эти обращения и откуда программа узнаёт, что чтение завершилось.

Как контроллер получает запись

Устройство принимает сигналы или хранит данные. Например, накопитель хранит блоки, а его контроллер управляет чтением и записью. Интерфейс контроллера задаёт, по каким адресам программа может отдавать команды и читать состояние. Схема декодирования адреса выбирает получателя обращения.

Запрос идёт по межсоединению, которое связывает процессор, память и контроллеры. В запросе нужно передать адрес, вид операции и, при записи, данные. На общей шине для этого могут использоваться группы проводников. В пакетном межсоединении адрес, вид операции и данные могут быть полями одного пакета, который проходит через коммутаторы.

Регистры в адресном пространстве

Запись в регистр doorbell сообщает контроллеру о готовых заданиях. Из регистра состояния программа узнаёт, например, закончилась ли операция. Иногда чтение регистра сбрасывает признак события, а запись единицы очищает отдельный бит. Перед обращением нужно проверить документацию регистра: она задаёт допустимую ширину и выравнивание, порядок байтов и эффект чтения или записи.

При memory-mapped I/O (MMIO) адреса регистров устройства входят в адресное пространство процессора. Инструкция записи по такому адресу отправляет запрос контроллеру. При записи в обычную область памяти запрос относится к RAM. Для этих областей могут действовать разные правила кэширования и порядка доступа. У x86 есть также отдельное пространство портов ввода-вывода с инструкциями IN и OUT.

В примере 0xF000 — адрес регистра DBELL. Запись значения 1 сообщает контроллеру, что готово новое задание. Адрес 0x2000 относится к RAM: туда контроллер запишет прочитанный блок. Оба адреса условны.

Описатель команды READ

Программа готовит команду в очереди заданий. Описатель (descriptor) хранит параметры команды: операцию, адрес буфера и длину. Буфер — область памяти для передаваемых байтов. Правило принадлежности (ownership) определяет, кто сейчас вправе менять описатель или буфер. Если программа перепишет поля после передачи описателя контроллеру, тот может прочитать часть прежних полей и часть новых.

Здесь описатель содержит READ, номер блока LBA=7, длину 512 и адрес буфера 0x2000. LBA (logical block address) — номер логического блока на накопителе. Контроллер прочитает блок 7 и запишет байты по адресам 0x2000…0x21FF. Первые четыре байта блока — 2A 00 00 00, остальные 508 — нули.

Порядок публикации описателя

К моменту передачи описателя контроллеру его поля должны быть видимы устройству. После передачи программа обновляет DBELL. Если уведомление придёт раньше полей, контроллер может взять прежний адрес буфера или длину. Барьер порядка ограничивает, в какой последовательности наблюдатель может увидеть обращения. Конкретные правила задаёт платформа.

DMA, direct memory access, означает передачу, в которой контроллер сам инициирует обращения к памяти вместо копирования каждого слова инструкциями CPU. Порядок обращений CPU, согласованность DMA с кэшем CPU и доставка MMIO-записи требуют отдельных действий. В RISC-V FENCE задаёт категории предшествующих и последующих обращений к памяти и I/O. Например, если платформа классифицирует подготовку полей описателя как записи в память W, а дверной звонок как запись в устройство O, FENCE W,O упорядочивает эти обращения. Операции с кэшем и подтверждение окончания команды требуют собственных действий. Этот барьер также не задаёт момент доставки прерывания по отдельному сигнальному пути.

Cache maintenance — документированные операции очистки или инвалидации нужных строк кэша. Например, перед чтением буфера устройством на несогласованной платформе может требоваться передать изменённую копию из кэша CPU в доступную устройству память. Для команды чтения устройство пишет буфер. На несогласованной платформе перед тем, как процессор воспользуется результатом, драйвер применяет предусмотренные правила синхронизации буфера, чтобы видеть новые байты. Эти обязанности драйвера описаны в руководстве Linux по DMA. В разобранном примере считаем, что нужные данные уже видимы в каждом переходе.

Posted MMIO write может быть принят и буферизован в передающем пути, пока запись ещё не достигла регистра устройства. Если платформа и руководство контроллера требуют убедиться в доставке, управляющая программа сначала выполняет такую запись, затем читает предусмотренный для этого регистр того же устройства. Это readback, контрольное чтение после записи; произвольный регистр с побочным эффектом для него не подходит. Ответ на контрольное чтение появляется после доставки предшествующей записи в случаях, предусмотренных интерфейсом. Пример последовательности write→read приведён в официальном описании доступа к устройствам Linux; конкретный программный API рассматривается в томе Linux. Доставка MMIO-записи ещё не завершает задание: контроллер позднее сообщает completion — запись о результате команды со статусом.

На схеме tail обозначает указатель конца очереди. Если протокол позволяет одним обновлением указателя опубликовать три готовых элемента, достаточно одной записи в doorbell вместо трёх. Первое задание при этом ждёт подготовки двух остальных.

Проверьте себя. Достаточно ли увидеть 2A по адресу 0x2000, чтобы считать команду завершённой? В каком направлении идёт DMA при READ?

Ответ

Байт виден уже на третьем шаге. Завершение определяют по записи результата на четвёртом. Накопитель служит источником, поэтому контроллер записывает данные в RAM.

Повторить четыре шага в браузере

Откройте модель М32-I/O1. В исходном состоянии строка IOMMU показывает direct PA: контроллер получает физический адрес без трансляции. IOMMU (input-output memory management unit) проверяет и при необходимости преобразует адреса, которыми пользуется устройство. Нажимайте «Следующий шаг» по одному разу и сверяйтесь с таблицей.

  1. «Подготовить READ». В строке Descriptor появляются op: READ, address: 8192 (это 0x2000), length: 512, lba: 7, device: 1 и owner: host. Это описание команды для контроллера с номером 1. Пока им владеет отправитель.
  2. «Опубликовать READ descriptor». Модель одним переходом делает поля доступными устройству, меняет владельца на device и отмечает DBELL=1. В строке Control/doorbell видно «OWN=device; опубликовано». По адресу 0xF000 в учебной карте идёт уведомление о готовой работе. Поля READ остаются в описателе, входной буфер ещё пуст, Completion отсутствует.
  3. «Выполнить DMA READ512B». Контроллер берёт 512 байт из LBA 7 и пишет их по 0x2000…0x21FF. Обратите внимание на направление: READ относится к накопителю, поэтому в физическую память устройство пишет. Теперь во входном буфере видно 2A 00 00 00, а в строке Completion по-прежнему «нет».
  4. «Опубликовать READ completion». Контроллер выдаёт ответ {"op":"READ","status":"SUCCESS","bytes":512}. В этой сцене передано всего одно задание, поэтому ответ не содержит отдельного номера команды. Данные уже лежат во входном буфере, а в строке IRQ только появляется pending=true. Вход в обработчик будет отдельным шагом.

Модель показывает состояния запроса и буфера. Доставку записи в DBELL она отдельно не отслеживает.

В следующей главе проследим путь запроса прерывания от контроллера до первой инструкции обработчика.
