Секторы, страницы и блоки накопителей

Одинаковая команда чтения скрывает различное устройство HDD и NAND SSD. Разберём адрес, движение данных и цену перезаписи.

Сначала логический интерфейс

Сетевой контроллер из предыдущей главы получал кадр с линии. Накопитель начинает чтение по команде хоста. В М32-I/O1 хост просит один логический блок по LBA 7. LBA выбирает номер, а формат устройства определяет размер блока. В нашем опыте это 512 байт. Успешное чтение возвращает столько байтов независимо от того, откуда контроллер их взял. Первые четыре байта составляют слово 2A 00 00 00; остальные 508 нулевые.

Ни номер LBA, ни длина ответа сами по себе не сообщают, где данные лежат внутри устройства. Хост видит адресуемый диапазон. Контроллер выбирает физическое место, а файловая система отдельно решает, какие диапазоны относятся к файлу.

HDD: механика входит в задержку

Возьмём SATA HDD Seagate BarraCuda ST1000DM010. По руководству он вращается со скоростью 7200 об/мин и показывает хосту блоки по 512 байт при физическом секторе 4096 байт. Этот формат называют 512e: восемь логических блоков помещаются в один физический сектор. Если LBA 0 выровнен по его началу, LBA 7 занимает байты 3584…4095 первого физического сектора. Это смещение внутри выбранного сектора. Номер дорожки и поверхности из одного LBA хосту неизвестен. Seagate BarraCuda Product Manual, rev. G, §2.2–2.4.

Если блока нет в кэше, контроллер подводит головку к нужной дорожке, ждёт, пока сектор пройдёт под головкой, читает и проверяет записанные данные. Из считанного физического сектора он возвращает хосту запрошенные 512 байт. Для записи тех же 512 байт может потребоваться сохранить остальные семь логических блоков: прочитать прежнее содержимое, заменить нужную часть и записать физический сектор целиком. Конкретное выполнение зависит от кэша и от того, какие части сектора уже подготовлены к записи.

При 7200 об/мин один оборот занимает 60 с / 7200 ≈ 8,33 мс. При равномерно случайной начальной фазе ожидание нужного участка в среднем составляет половину оборота, около 4,17 мс. Это только ожидание поворота. Полную задержку определяют также перемещение головки, очередь, передача и возможные повторы. Попадание в кэш убирает механическую часть для этого чтения.

NAND: чтение, программирование и стирание

У NVMe SSD Micron 7450 с NAND переключаемый размер логического блока составляет 512 или 4096 байт. Выбираем формат 512 байт, чтобы тот же запрос READ LBA 7 имел прежний размер ответа. Контроллер ищет действующее отображение LBA, читает данные из NAND, если нужного блока нет в кэше, и извлекает запрошенные байты перед передачей хосту. При формате 4096 байт тот же номер обозначал бы уже другой диапазон логических байтов. Ни один из этих размеров не задаёт размер NAND-страницы. Micron 7450 Technical Product Specification, rev. C.

NAND-страница — единица чтения и программирования массива NAND. Блок стирания включает несколько страниц. Перезаписывать старую страницу как ячейку RAM нельзя: повторное использование требует стирания блока по правилам чипа. Прошивка устройства обычно записывает обновлённые данные в свободное место. FTL, слой трансляции флеш-памяти, хранит сведения, по которым логический номер находит актуальную копию. Старое место освобождается по правилам сборки мусора. Производители указанных накопителей не раскрывают физическое место нашего LBA; конкретные страницы ниже принадлежат учебной схеме.

Маленькая FTL-таблица: два erase blocks

Отделим оригинальную модель FTL-2×4 от настоящей firmware. В ней два блока A/B по четыре страницы, одна страница вмещает ровно одну нашу логическую единицу; это намеренно выбранная геометрия для счёта, настоящая NAND-страница SSD обычно крупнее этой учебной единицы. У каждой страницы есть состояние: стёрта/свободна, запрограммирована и актуальна, запрограммирована и уже не нужна. Таблица mapping хранит номер текущей страницы для LBA; данные и таблица размещения сохраняются отдельно. Исходно map={7:A0,8:A1,9:A2}; A0 содержит 42, A1/A2 — другие нужные значения. A3 и B0..B3 стёрты. На схеме переходите кнопкой «Дальше →». Сначала READ LBA 7 выбирает A0 и даёт 42. В кадре «Новые данные LBA 7» значение 43 уже в B0, однако READ по таблице всё ещё выбирает A0. Только кадр «Обновление таблицы» направляет следующий READ в B0.

Invalid означает, что прежнее запрограммированное содержимое уже не требуется текущей таблицей. Физическое стирание ещё не произошло. Нельзя записать новую страницу поверх A0 лишь потому, что карта отвернулась от неё. Нельзя стереть A после двух перезаписей, пока A2 остаётся единственной актуальной копией LBA 9. Копирование сохраняет неизменяемый пользователем LBA 9 и занимает время и ресурс программирования. В выбранном окне две записи страниц от host вызвали три программирования страниц данных: WAFdata=3/2=1.5. Записи метаданных, стирание и начальная загрузка здесь не посчитаны. Vendor counter может включать их и показывать другое отношение.

Сбой между записью данных и обновлением таблицы

Рассмотрим B0 с 43. Если страница данных уже записана, но сохранённая таблица ещё указывает A0, восстановление прочитает 42; B0 может стать orphan — недостижимой страницей, которую процедура восстановления должна распознать. Если mapping объявлен новым до сохранения данных, он может вести к недописанной/повреждённой странице. Если новый map жил лишь в энергозависимой RAM, исчезновение питания потеряет именно выбор версии, хотя 43 физически присутствует. Если стирание A началось до устойчивой карты/проверенной новой копии 9, можно потерять единственное пригодное значение 9.

Реальная FTL решает это собственными номерами версий, контрольными суммами, журналами/контрольными точками, порядком записи и/или PLP. Реализация определяет конкретные структуры и атомарные этапы. Табличное «согласовать map» является явным договором нашей конечной модели, а не обещанием, что NAND атомарно переписывает произвольную FTL-таблицу. Даже контрольная сумма позволяет обнаружить часть повреждений, но не выбрать свежую версию без правил восстановления. Для мысленного сравнения представьте, что LBA 9 уже признан ненужным до сборки мусора. Тогда перенос A2 в B2 отпадает, и в том же окне коэффициент усиления записи равен 2/2=1. Схема показывает исходный случай, где LBA 9 надо сохранить.

Сборка мусора и усиление записи

Garbage collection, «сборка мусора», освобождает erase block: ещё нужные страницы переносятся, старые/непригодные отбрасываются, затем целый block стирается и возвращается в запас. Это реальная внутренняя работа, конкурирующая с запросами host за channels, chips и время. Wear leveling, «выравнивание износа», распределяет циклы program/erase, чтобы отдельная горячая область не исчерпала ресурс слишком рано. Переносы могут происходить даже без новой логической версии файла.

Write amplification, усиление записи, удобно определить как объём NAND-программирования, делённый на объём host writes в одном окне при одинаковых единицах. Host записал 1 GiB, NAND запрограммирована на 2.5 GiB — коэффициент 2.5, безразмерный. Он зависит от нагрузки, свободного резерва, заполненности, размещения и фоновой работы; нельзя считать любое отклонение от 1 неисправностью. Разные vendor counters имеют свои определения, поэтому сравнивать их без datasheet рискованно.

Deallocate/Trim сообщает, что определённый логический диапазон больше не нужен. Это может помочь FTL не переносить ненужные страницы, но не является универсальной командой немедленного физического стирания всех копий. Поведение последующего read deallocated range определяется устройством/форматом, а удаление записи каталога файла само по себе не тождественно этой команде. Безопасное удаление секретов — отдельный контракт sanitize/crypto erase и резервов, не следствие обычной перезаписи четырёх байтов.

Страница NAND, LBA и атомарность

Логический блок, физический сектор HDD, страница NAND и единица атомарной записи описывают разные границы. Например, устойчивость после потери питания и гарантия «прочтём целиком старую или целиком новую версию» задаются разными условиями. Размер LBA сам по себе не даёт обеих гарантий.

Изменённая страница и обновлённая таблица должны пережить сбой вместе настолько, чтобы после запуска устройство могло найти записанные данные. При включённом энергозависимом кэше успешный Write может появиться до этого момента. В NVMe Base 2.1 успешный Flush доводит данные и метаданные до энергонезависимого состояния для указанной области логических блоков, namespace. Он распространяется на команды в этой области, уже завершённые контроллером до подачи Flush. Команда накопителю не записывает данные, пока они находятся только в памяти ОС. Для этого нужен отдельный договор приложения с ОС. NVMe Base 2.1, §7.2.

У SATA BarraCuda команда записи кэша называется Flush Cache или Flush Cache Extended в наборе ATA. В учебном М32-I/O1 после WRITE / SUCCESS новое слово 43 ещё лежит в энергозависимом кэше устройства, а устойчивый LBA 7 содержит 42. Сам запрос FLUSH это не меняет. Только FLUSH / SUCCESS отмечает переход к устойчивой копии 43. Схема FTL выше объясняет, почему для этого мало запрограммировать B0. Она не исполняет команду Flush. В следующей главе проследим, как хост подаёт эту команду через очередь NVMe и узнаёт об успехе.

Первичные описания: Microchip NAND Flash Organization; Samsung, NAND/placement/garbage collection; NVM Command Set1.1, logical blocks и atomicity. Конкретные geometry/ресурс одного чипа не объявлены свойствами всех SSD.
