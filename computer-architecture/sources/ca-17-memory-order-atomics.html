Порядок памяти: очередь, наблюдение и атомарное изменение

Почему согласованные копии ещё не дают программе нужного порядка

Три разных порядка

Порядок программы — последовательность её операций в выбранном представлении. Порядок исполнения — порядок внутренних аппаратных действий: ожидания, выдачи запросов и вычислений могут перекрываться. Наблюдаемый порядок — какие значения допускается увидеть участникам. Модель памяти архитектуры задаёт допустимые наблюдения, а не единственную временную диаграмму всех транзисторов. Компилятор тоже преобразует исходную программу по правилам языка; машинный код и текст программы не объявляются тождественными без проверки.

Когерентность из предыдущей главы согласует версии одного места. Memory ordering, порядок памяти, добавляет ограничения между обращениями, в том числе к разным местам. Нельзя доказать правила многоядерной машины по нашей последовательной программе из пяти операций: у неё нет двух участников, публикации данных и конкурирующих наблюдений.

Последовательная согласованность, sequential consistency или SC, — модель, в которой все операции можно расположить в одной общей последовательности, сохранив порядок каждого участника, а чтение получает последнее предшествующее значение своего адреса. Такое ограничение упрощает рассуждение о программе; реальный CPU может поддерживать другую модель. Более слабые модели допускают некоторые дополнительные наблюдения ради перекрытия работы; им всё равно нужны строгие правила.

Полный опыт SB-FIFO-2C

Введём отдельный учебный профиль: две переменные x и y первоначально 0. Это не буфер 42 М32. У ядра 0 программа store x=1; load y→r0; у ядра 1 store y=1; load x→r1. У каждого собственная FIFO-очередь записей: записи выходят из неё в порядке поступления. Store может попасть в очередь, а следующая загрузка другого адреса — прочитать общее состояние раньше выхода записи. Drain обозначает отдельный переход передачи головы очереди в общую память.

Никакая переменная не увидела записи в противоположном порядке: у каждой всего одна запись. Следовательно, когерентность не нарушена. Однако общей SC-последовательности для результата 0,0 нет. Чтение y=0 требует поставить его до store y=1; порядок ядра 0 ставит store x=1 перед этим чтением. Аналогично порядок ядра 1 требует store y=1 перед load x=0, который должен предшествовать store x=1. Получается цикл строгих предшествований, невозможный в одной линейной последовательности.

Очередь не выдаёт произвольные устаревшие данные самому писателю: зависимая загрузка своего адреса обычно должна учитывать собственную ещё не переданную запись согласно выбранной архитектуре. Подстановка из очереди называется forwarding. В этом опыте загрузки обращаются к другим адресам, поэтому чужое значение из собственной очереди подставить нельзя. Не следует объяснять результат 0,0 тем, что CPU «забыл своё присваивание».

Ожидание на границе и все конечные результаты

Барьер порядка, memory fence, добавляет определённые ограничения между группами обращений. Для нашей малой модели выберем точное правило: между store и load ядро ждёт опустошения своей предшествующей очереди записи. Тогда хотя бы одна запись должна стать общей прежде, чем обе загрузки закончатся;0,0 исключается. Это модельное правило, а не определение всех инструкций с названием fence.

Движок SB-FIFO-2C перечисляет все достижимые конечные состояния конечного графа переходов: без ожидания результаты 0,0;0,1;1,0;1,1; с выбранным ожиданием 0,1;1,0;1,1. Финальное состояние требует завершить обе программы и опустошить очереди. Поэтому 0,0 не спутан с незаконченным выполнением, в котором запись просто никогда не передали.

Наблюдение здесь — множество разрешённых результатов и конкретная последовательность переходов-свидетель для каждого. Частота результата 0,0 не вычисляется: модель не задаёт вероятности выбора ядра и длительности действий. Перебор 34 достижимых состояний без fence и 20 с ним относится к этому конечному графу; он не проверяет все архитектурные модели памяти. Один реальный запуск, даже давший нужный результат миллион раз, также не доказывает запрет другого допустимого наблюдения.

Откройте сцену порядка. Выполните store обоих ядер, затем оба load, затем оба drain. Получатся 0,0 и конечная память 1,1. Явно начните вариант с fence и повторите попытку: load до собственного drain будет отклонён без изменения состояния. После drain можно продолжить. Изменено только правило ожидания, исходные нули и программы сохраняются.

Неделимость одной операции не собирает несколько операций в одну

Атомарность означает неделимость операции относительно указанных наблюдателей и размера. Для выровненного слова выбранная ISA может гарантировать, что читатель не увидит смесь половин старого и нового значения. Это не означает, что отдельно выполненные load, сложение и store образуют единую атомарную операцию. Не существует общей гарантии для любого размера, выравнивания, типа памяти и перехода границы страницы.

Разберём потерю обновления. Оба ядра читают общий счётчик 42. Ядро 0 вычисляет 43; ядро 1 независимо вычисляет 43. Их stores последовательно получают исключительное право и оба записывают 43. Все отдельные чтения/записи могут быть атомарными, MESI работает правильно, но конечное значение 43, а ожидали 44. Нужна операция read-modify-write, RMW: чтение, изменение и сохранение как одна неделимая операция указанного объекта.

В отдельной сцене «Атомарный счётчик» сначала прочитайте счётчик обоими ядрами, затем выполните обе обычные записи: увидите 43. Сохраните результат, затем явно начните заново и выберите «атомарно увеличить» у обоих участников: первая операция 42→43, вторая 43→44. У контроллера сцены каждая atomic-команда исполняется одним неделимым переходом. Движок меняет одно числовое поле; машинные инструкции здесь не декодируются.

Атомарное изменение может требовать исключительного права кэша и ожидания других участников; «одна инструкция» не означает «один такт». При высокой конкуренции одна линия последовательно переходит между писателями. Замена обычного сложения на atomic устраняет конкретную потерю обновления, но не создаёт неограниченную пропускную способность и не защищает автоматически соседнюю структуру данных.

Acquire и release связывают публикацию

Другой опыт: писатель сначала готовит payload=43, затем публикует flag=1. Читатель ждёт flag и после него читает payload. Release, публикация с упорядочением предшествующих действий, и acquire, приём с упорядочением последующих действий, задают требуемую связь по правилам выбранного языка/ISA. Существенно, чтобы acquire-чтение увидело именно соответствующую release-публикацию; простое наличие этих слов где-то в программе недостаточно.

В абстрактном корректно синхронизированном варианте запись payload предшествует release flag, acquire получает 1 из этой публикации, а чтение payload идёт после acquire. Такая связь обеспечивает требуемую видимость payload при выполнении указанных правил синхронизации. Если читатель получил старый flag=0, он ещё не принял эту публикацию и не получил её гарантию. Если flag изменяется атомарно, но без необходимого упорядочения, неделимость флага сама не устанавливает порядок payload.

У языка есть собственная модель памяти. Гонка данных — конкурирующие обращения к одному объекту, хотя бы одно записывает, без требуемой языком синхронизации. Нельзя переписать малый аппаратный опыт (litmus) обычными несинхронизированными переменными произвольного языка и считать все его результаты измерением ISA: язык может не давать такой программе определённого смысла. Наши кнопки меняют явную математическую структуру, поэтому этот опыт не зависит от оптимизатора и потоков браузера.

Что действительно задаёт RISC-V

Выбранная первичная спецификация — RVWMO2.0 в библиотеке v20260120. Она определяет допустимые наблюдения через глобальный порядок памяти и сохраняемую часть порядка программы, зависимости, ограничения синхронизации и допустимые источники значений загрузок. Это значительно богаче двух однобуферных ядер. Учебная очередь показывает одну причинную возможность, а не выводит формальные аксиомы RVWMO.

Расширение RISC-V A2.1 предоставляет атомарные операции. AMO, atomic memory operation, задаёт чтение и изменение одной инструкцией; биты aq/rl добавляют ограничения acquire/release для соответствующего домена памяти. У пары LR/SC, load-reserved/store-conditional, LR создаёт аппаратное наблюдение за областью резервирования, а SC пытается записать при допустимом сохранении резерва: результат 0 означает успех, ненулевой — неудачу. Область резервирования не обязана равняться нашей 16 B линии; программа должна учитывать отказ и корректно повторять операцию по условиям ISA.

Резервирование не является бессрочной блокировкой для программы. Конкурирующая запись и другие определённые события могут сделать SC неуспешной. Повтор требует заново получить актуальное значение, а не слепо сохранить старое 43. Гарантии продвижения заданы для определённых ограниченных последовательностей LR/SC; нельзя обещать успех каждого произвольного цикла. Полная эмуляция AMO, LR/SC и языковых отображений не входит в нашу сцену.

RISC-V FENCE различает множества предшествующих и последующих обращений; для устройств у него важны отдельные категории ввода/вывода. Упорядочить обращения не значит очистить все CPU cache, обновить преобразования адресов или заставить накопитель сохранить сектор после питания. SFENCE.VMA согласует изменения таблиц с последующим использованием переводов на текущем участнике; её действие разберём вместе с таблицами страниц.

Границы опыта

Наши измеримые величины — число достижимых состояний, завершённые результаты регистров, содержимое очередей и счётчик 42/43/44. Здесь нет времени настоящих ядер, автоматической генерации машинного кода и статистики редкого аппаратного исхода. SC, когерентность, атомарность, acquire/release и устойчивое сохранение различаются по предмету гарантии. В опыте 0,0 объясняется двумя непустыми очередями, а 43 вместо 44 — двумя чтениями одного старого счётчика. Эти причины требуют разных исправлений.
