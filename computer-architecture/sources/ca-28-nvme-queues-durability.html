Очереди NVMe и завершение записи

Прочитаем 42 из LBA 7, подготовим запись 43 и проследим, в какой момент это значение переживёт потерю питания устройства.

Интерфейс контроллера и носитель

В предыдущей главе таблица FTL связала логический блок с местом во флеш-памяти. Теперь проследим, как драйвер просит накопитель прочитать этот блок. NVM Express (NVMe) определяет команды, очереди и ответы между хостом (компьютером, на котором работает драйвер) и контроллером. В нашем примере накопитель использует NAND, а транзакции между контроллером и памятью хоста идут по PCIe. Драйвер выбирает пространство имён NVMe (namespace), то есть набор адресуемых блоков со своим форматом и идентификатором NSID. Внутреннее расположение выбранного блока определяет контроллер.

Числовой пример опирается на три согласованные редакции от 5 августа 2024 года. Base 2.1 описывает состояние контроллера и очередей. NVM Command Set 1.1 определяет команды чтения и записи. PCIe Transport 1.1 задаёт регистры, через которые драйвер сообщает контроллеру о продвижении очередей. Ссылки на конкретные разделы приведены в конце главы.

Как очереди соединяют host и контроллер

Очередь отправки (submission queue, SQ) содержит описания команд. Очередь завершений (completion queue, CQ) содержит результаты. В рассматриваемом случае обе лежат в памяти хоста и доступны контроллеру через прямой доступ к памяти (DMA). Драйвер заполняет запись команды (SQE) и обеспечивает её видимость для устройства. Затем он записывает новый индекс хвоста SQ в регистр уведомления (doorbell). Регистр расположен в адресном пространстве устройств, доступном через отображение ввода-вывода в память (MMIO). По изменению хвоста контроллер узнаёт, сколько записей доступно для обработки.

Контроллер может завершить независимо поставленные команды в другом порядке. Чтобы найти запрос по записи о завершении (CQE), драйвер использует номер SQ и идентификатор команды. Индекс головы CQ, который драйвер записывает в другой регистр уведомления, освобождает обработанные слоты результатов. Для проверки свежести конкретной записи служит бит фазы P.

В выбранном формате описание команды занимает 16 слов по 4 байта, всего 64 байта. Запись результата состоит из четырёх слов, 16 байт. Данные сектора размером 512 байт находятся в отдельном буфере. Поле PRP/SGL указывает страницы/сегменты буфера данных в поддержанном формате. PRP, physical region page, — механизм указания областей данных; SGL, scatter-gather list, — описание нескольких сегментов. Наивно поместить CPU VA в PRP не означает настроить DMA mapping. Отображение DMA-адресов и согласование размеров страниц выполняются по правилам транспорта и платформы.

До первой SQE: как контроллер получает административные очереди

Рассмотрим только memory-based NVMe over PCIe и уже выполненную подготовку транспорта: функция обнаружена, MMIO BAR доступен, разрешён корректный DMA, отображения памяти созданы, буферы остаются выделенными до окончания обращения. Числа ниже описывают подготовленный учебный профиль. Properties — поля управления и состояния интерфейса. Смещение ниже считается от начала окна регистров. Привилегированная программа записывает настройки, контроллер сообщает статус готовности.

До EN=1 выбираем CSS=0, MPS=0, AMS=0 и CRIME=0 в поддержанном режиме готовности. Сначала CC=0, затем устанавливаем EN=1; ждём RDY=1, проверяя CFS и предел времени выбранного режима. CAP.TO имеет единицу 500 ms; Base 2.1 также имеет регистр CRTO и режимы готовности с носителем/независимо от носителя, поэтому старую простую формулу нельзя безусловно применять к любому новому контроллеру. Если срок истёк, настройка останавливается: следующие команды не публикуются.

Через административную очередь выполняются Identify Controller и нужные Identify Namespace: по их ответам проверяем размеры записей, активный NSID 1, формат 512 байт без отдельных метаданных и поддержку используемых возможностей. Только после проверки этих ответов задаём IOSQES=6, IOCQES=4, то есть 64 B/16 B, до создания очередей I/O. При сохранении остальных выбранных битов CC=00460001h. Set Features Number of Queues согласует доступное число очередей; затем Create I/O CQ создаёт CQ 2 по DMA-адресу 5000. После её успешного завершения Create I/O SQ создаёт SQ 2 по адресу 6000 и связывает её с CQ 2. Обе базы выровнены по 4 KiB, очереди имеют по четыре слота. До создания CQ2 драйвер обнуляет в ней биты фазы. Здесь разобраны порядок и поля настройки по Base 2.1 §3.5.1; двоичные записи административных команд не реализованы helper-функцией.

Попытка Create SQ до существующей CQ, неподдержанный MPS или неверные размеры записей имеют ветку отказа; нельзя переходить к Read после ошибочного результата административной команды. Успех EN/RDY сам по себе не подтвердил формат namespace. Политика выбора числа очередей и их привязки к CPU выполняется ОС; аппаратная причина последовательности — контроллер должен знать, где брать команды, куда возвращать результаты и как читать каждую запись.

Конкретная команда Read

В общем формате команды CDW0 содержит код операции opcode и идентификатор команды CID, NSID выбирает namespace, указатель данных задаёт буфер, CDW10/11 содержат начальный LBA, CDW12 — число блоков и управляющие биты. Dword — 32-битное слово, не обязательно логический сектор. В NVM Command Set Read имеет opcode=02h, Write — 01h. NLB, number of logical blocks, в этих командах кодируется нулевой базой: NLB=0 означает один блок, NLB=1 — два, а не запрос нулевой длины.

PRP1, PRP2 и граница страницы

Размер страницы памяти контроллера задаётся CC.MPS и может отличаться от страницы виртуальной памяти CPU. У PRP1 для этих команд допускается смещение в первой странице, кратное четырём байтам. Адрес 2200h даёт смещение 200h, то есть 512 байт. До конца страницы остаётся 3584 байта, поэтому весь 512-байтный буфер записи помещается в ней. Для отдельного примера PRP1=2F00 при передаче 512 байт первая страница даёт 100h=256 B, ещё 256 B нужны из второй: PRP2=7000 может указать другую выровненную страницу. Две порции данных размещены в разных страницах: непрерывность физического диапазона 2F00..30FF не требуется.

Если после первой частичной страницы нужно больше одной полной страницы, PRP2 представляет указатель на PRP List, массив 64-битных адресов следующих страниц данных. Указатель списка должен быть кратен 8 байтам; первый список может начинаться с ненулевым смещением в странице. Адреса самих страниц данных выровнены по размеру страницы контроллера. Если список продолжается за пределами страницы, последний предусмотренный элемент связывает следующую страницу списка по правилам стандарта. Нельзя одновременно читать PRP2 как адрес второй страницы данных и адрес массива адресов.

Пример дополнительного профиля размещения: PRP1=2F00, длина 8704 байта →256 B первой страницы, затем 8448 B =4096+4096+256. PRP2=6010 указывает выровненный по 8 байтам список с адресами 7000, 9000, B000. Страницы списка и данных должны оставаться доступными для DMA до конца обращения. Поставить CPU VA 00402000 вместо подготовленного DMA-адреса нельзя. Включённый IOMMU может преобразовывать IOVA устройства, но использует отдельные таблицы, а не обход CPU satp по умолчанию.

Буквальные 16 B completion и оборот кольца

В нашем одиночном чтении контроллер успел извлечь один SQE, поэтому у CQE поле SQHD=1. Контроллер кладёт запись в слот 0 очереди CQ2 и выставляет P=1. Первые восемь байтов в этом примере нулевые. На смещениях 8, 10, 12 и 14 расположены два байта головы SQ, номера SQ, CID и статуса соответственно. Младший бит статуса равен P, поэтому слово 0001h здесь означает свежую запись первого оборота с SC=0 и SCT=0, то есть успешное завершение.

offset00: 00 00 00 00 00 00 00 00 01 00 02 00 11 00 01 00
         DW0         DW1         SQHD  SQID  CID   STATUS

SQHD сообщает, до какого слота контроллер продвинул чтение SQ на момент подготовки CQE. По этому полю драйвер может вернуть извлечённые слоты SQ в оборот. У извлечённой команды ещё может идти передача данных, поэтому её буфер и CID остаются заняты до завершения этой команды. Для текущей CQE драйвер сначала проверяет P в слоте под головой, затем находит запрос по паре SQID/CID и читает код статуса SC и его категорию SCT. При ошибке он не использует буфер как результат удачного чтения. DNR (do not retry) указывает, что повтор той же команды, вероятно, снова завершится ошибкой.

Драйвер обнуляет P во всех слотах CQ до её создания. В первом проходе контроллер пишет P=1, а драйвер ожидает 1 в слоте под своей текущей головой. Контроллер переключает записываемую фазу, когда его хвост переходит со слота 3 к слоту 0. Драйвер переключает ожидаемую фазу при таком же переходе своей головы. Если после оборота в слоте 0 сохранился P=1, драйвер ждёт новую запись с P=0, даже если старый CID выглядит знакомым. Пока драйвер не сообщит о продвижении головы, контроллер не может занимать необработанные слоты повторно. Заполненная CQ способна задержать работу связанных с ней SQ.

На карте ниже контроллер уже передал блок и положил CQE в слот 0. Драйвер ещё не освободил этот слот. В RAM по адресу 2000h находятся 512 байт данных, по 5000h — запись результата, по 6000h — всё ещё видимые байты уже извлечённой команды. Эти три участка памяти живут по разным правилам. Полный ход чтения приведён после карты.

Два doorbell и время жизни буфера

В SQ2 четыре слота по 64 байта начинаются по адресам 6000h, 6040h, 6080h и 60C0h. В CQ2 четыре слота по 16 байт начинаются по 5000h, 5010h, 5020h и 5030h. Для этого примера выберем CAP.DSTRD=0. Соседние регистры уведомления тогда идут с шагом 4 << DSTRD, то есть четыре байта. Нумерация начинается с 1000h и для каждой очереди отводятся два регистра. У очереди 2 хвост SQ находится по смещению 1000h + 4 × 4 = 1010h, а голова CQ по 1000h + 5 × 4 = 1014h от начала окна регистров контроллера.

  1. Драйвер записывает 64 байта команды Read с CID 0011h в слот SQ2[0] по адресу 6000h. Он подготавливает DMA-отображение принимающего буфера 2000h…21FFh. После того как устройство может увидеть запись, драйвер пишет 1 в регистр 1010h. Хвост указывает на следующий слот.
  2. Контроллер видит новую границу очереди и читает SQE по DMA. Из записи он получает NSID 1, LBA 7, длину 512 байт и адрес назначения 2000h. Читает блок накопителя и по DMA записывает 512 байт в RAM хоста. Первые четыре байта в нашем примере равны 2A 00 00 00.
  3. Контроллер помещает 16 байт результата в CQ2[0] по адресу 5000h. Уведомление о прерывании (IRQ) побуждает драйвер проверить очередь. Драйвер также может периодически проверять её в цикле (polling). В любом случае он подтверждает свежую фазу, сопоставляет SQID/CID, проверяет статус и соблюдает правила видимости данных DMA данной платформы. Затем он может прочитать число 42 из буфера.
  4. После обработки результата драйвер передвигает голову CQ и пишет 1 в регистр 1014h. Теперь контроллер вправе в будущем занять слот результата повторно. Запись индекса в MMIO занимает четыре байта. Сами 512 байт блока уже переданы между контроллером и отдельным буфером RAM.

Нельзя освободить/переиспользовать буфер и CID после одного лишь tail doorbell или host timeout. Пока незавершённый DMA не остановлен/не завершён по правилам транспорта/контроллера, контроллер ещё может писать в прежний адрес, уже отданный другому владельцу. Отмена ожидания приложения и принятие abort/reset устройством различаются. Восстановление включает прекращение старого DMA, согласованное состояние очередей, инвалидацию отображений по необходимости и только затем повторное использование памяти. Отмена ожидания сама по себе старый DMA не останавливает.

Файл NVMe-LAYOUT32 кодирует только выбранные поля/PRP-граничные случаи и читает CQE; тесты сверяют байты, несовпадение phase/CID, error/DNR, выравнивания и отказ при неподдержанном продолжении списка. Функции кодируют данные и не отправляют команды накопителю.

У выбранной Read контроллер логически считывает 64 байта SQE, передаёт 512 байт данных и записывает 16 байт CQE: сумма этих трёх областей равна 592 байтам. Doorbell, чтения CPU, обходы IOMMU и протокольные заголовки сюда не включены. Это счёт описанных операций интерфейса памяти, а не измеренный трафик DRAM или NAND. Увеличение payload уменьшает долю фиксированных 80 байт SQE/CQE, но требует большего буфера и может дольше занимать контроллер.

От числа 42 в RAM к буферу записи с числом 43

После удачного чтения процессор получает 42, прибавляет 1 и записывает 2B 00 00 00 по адресам 2200h…2203h. Пять инструкций урока заканчиваются на EBREAK и оставляют остальные 508 байт выходного буфера в прежнем состоянии. Отдельная операция копирует исходный хвост из 2004h…21FFh в 2204h…23FFh. Теперь буфер содержит весь новый блок, а первые четыре байта хранят 43.

Продолжим теми же очередями, без других заявок. Драйвер заполняет SQ2[1] по 6040h. Для Write задаёт opcode=01h, CID=0012h, NSID=1, SLBA=7, NLB=0 и PRP1=2200h. В обычной записи FUA=0. Когда контроллеру доступны SQE и данные в буфере, драйвер пишет хвост 2 в 1010h. Контроллер читает SQE, затем по DMA читает 512 байт из RAM хоста. В выбранном режиме он может принять их в энергозависимый кэш и уже сообщить об успехе. Для этой Write драйвер ожидает CQ2[1] по 5010h с SQHD=2, SQID=2, CID=0012h, P=1 и успешным статусом. После обработки CQE он записывает голову 2 в 1014h.

Четыре точки вместо одного «готово»

Acceptance — контроллер принял запрос или байты по определённому интерфейсу. Data transfer complete — нужные байты DMA уже переданы. Command completion — опубликован результат с успехом/ошибкой по правилам команды и настроек. Durable — данные и необходимые для их нахождения метаданные находятся в предусмотренном энергонезависимом хранилище. Например, FUA сближает успешное завершение Write и сохранение её данных; обычная Write с энергозависимым кэшем может разделять эти события.

При включённом энергозависимом кэше записи обычная Write может завершиться, пока новая версия находится в памяти контроллера. Сразу следующий read может вернуть 43 из этого кэша, хотя после потери питания останется 42. Поэтому «прочитал обратно» проверяет текущую видимость, но не достаточен как power-fail test. Power-loss protection, PLP, — аппаратные средства и средства firmware для сохранения принятых данных/метаданных при исчезновении питания; наличие одного конденсатора на фотографии ещё не доказывает заявленную область гарантии.

В этом примере кэш энергозависимой записи включён. Для Flush стандарт требует сохранить данные и метаданные команд указанного пространства имён, которые контроллер завершил до отправки Flush. Контроллер вправе сохранить и другие данные. Поэтому драйвер дожидается успешного CQE нашей Write, прежде чем отправлять Flush. Если опубликовать Flush, пока Write ещё выполняется, её данные могут остаться за пределами гарантированной группы. При отсутствии или отключении такого кэша Flush не меняет состояние данных. Специальный NSID FFFFFFFFh зависит от поля поведения Flush в Identify Controller. Для опыта достаточно назначить NSID 1.

Драйвер кладёт Flush в SQ2[2] по 6080h и пишет хвост 3 в 1010h. Код 00h означает Flush в наборе команд этой I/O-очереди. У команды свой CID 0013h и NSID 1. Она не передаёт пользовательский блок через DMA, поэтому указатели данных в примере нулевые. Драйвер отдельно ждёт свежую CQE в CQ2[2] по 5020h с SQID=2, CID=0013h, P=1 и успешным статусом, после чего освобождает слот записью головы 3 по 1014h. Успех этой команды подтверждает сохранность прежней Write в оговорённой области. Атомарность группы записей Flush не устанавливает.

У одной Write можно задать FUA=1 (force unit access). Это бит 30 в CDW12. При остальных нулях слово 00000000h станет 40000000h, а байты 30h…33h станут 00 00 00 40. Размер блока останется прежним. Контроллер должен сохранить данные и метаданные именно этой Write до её успешного завершения. Порядок относительно остальных команд это поле не задаёт.

Вызов fsync — программный контракт OS/файловой системы с данными и метаданными файла. Между ним и командой устройства могут быть журнал, несколько Write, несколько namespaces/устройств, RAID и кэши нижних уровней. Для реализации fsync вся эта последовательность должна довести нужные данные до требуемой точки сохранения. Один бит FUA в отдельной команде ещё не показывает, что сохранены все файловые метаданные. Успех Read из кэша, успешная обычная Write и успешный нужный Flush отвечают на разные вопросы.

Изменяемый опыт и ошибки

Практика к этому примеру

Откройте М32-I/O1. В сцене есть один описатель команды и одно поле результата. Действия «Опубликовать READ descriptor» и «Опубликовать WRITE descriptor» передают описатель устройству. Числовые индексы NVMe, смена P, байты PRP и обработка FUA в этой сцене отсутствуют. Их проверяйте по записям и карте выше. Цикл чтения сцены включает доставку IRQ, наблюдение результата, подтверждение прерывания и возврат к программе.

  1. Кнопкой «Следующий шаг» дойдите до «Опубликовать WRITE completion». В панели байтов носитель начинается с 2A 00 00 00, кэш устройства с 2B 00 00 00. Скачайте JSON этого состояния.
  2. Нажмите «Запросить FLUSH». Оба значения ещё прежние. Нажмите «Потеря питания устройства». Кэш исчезнет, носитель по-прежнему начинается с 2A 00 00 00.
  3. Загрузите свой JSON и снова запросите Flush. Выполните следующий шаг «Завершить FLUSH до durable» и убедитесь, что носитель теперь начинается с 2B 00 00 00. После повторной потери питания устройства это значение останется. Сцена сохраняет RAM хоста для сравнения. Опыт показывает потерю питания устройства с заданным кэшем, свойства реального SSD из него не следуют.

Completion может содержать error: неверный namespace, LBA вне диапазона, media/integrity error, неподдержанный формат. Timeout host означает отсутствие принятого результата к deadline. Команда могла уже изменить устройство, поэтому слепой повтор не является универсальной recovery-процедурой. Сброс очередей меняет состояние незавершённых команд; повторное использование CID/буфера требует завершения старой возможности DMA. Восстановление драйвера и гарантии файловых операций рассматривает том об ОС.

Глубина очереди скрывает latency за параллельными запросами, но не создаёт бесконечную полосу NAND/PCIe. Большая очередь увеличивает ожидание и tail latency при насыщении. Команды flush/FUA могут менять возможное переупорядочение и цену подтверждения; сравнивать IOPS до/после без одинаковой durability-гарантии — сравнивать разные услуги.

Наше первое чтение начиналось с уже обнаруженной PCIe-функции и доступной RAM. В следующей главе вернёмся к сбросу машины и проследим, как микропрограмма готовит платформу к работе загрузчика и ядра.
