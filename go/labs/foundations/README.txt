Личный стенд основ Go: главы 14–17 и 46–47

Профиль: Linux amd64, Bash, Python 3.10+, уже установленный Go 1.27.3.
Пользователь обычный: все выходы принадлежат ему. Подготовка не скачивает Go,
не меняет go env -w, не пишет в clone и не запускает сетевую службу.
Сначала в главе 14 выберите полный путь к bin/go, затем из корня клона:
  python3 go/labs/foundations/prepare.py --go "$GO_BIN_DIR/go" --root "$HOME/handbook-lab/go-foundations"
  source "$HOME/handbook-lab/go-foundations/env.sh"
В новом терминале достаточно source той же env.sh. Проверка: go version;
go env GOCACHE GOMODCACHE GOPATH GOTOOLCHAIN. Нужны собственные каталоги
cache и значение local. Уже существующий root вызывает отказ: ничего не
перезаписывается. Для нового независимого опыта выберите другое НОВОЕ имя.
Не удаляйте прежний стенд ради повторного чтения.

Внутри LAB:
service/ — копия исходного сервиса; test/build/-version не слушают порт.
fixtures/front/ — отдельный module, lib/, cmd/inspect/, sample/.
fixtures/generics/ — Add для int, Count, int64; demo будет локальным выходом.
fixtures/cases/ — каждый .go компилируется ОТДЕЛЬНО прямым compile; пакет
целиком заведомо некорректен. Это сохранённые отрицательные входы.
fixtures/mvs/{root,a,b,c} — весь локальный граф MVS без proxy.
fixtures/cacheaction/ — lib.Scale и main, архивные build ID и тёплый build.
fixtures/zip/ — данные для stable_zip.py из главы 16.
out/ — журналы и одноразовые результаты; cache/ — три разных кэша/пути Go.
Все относительные пути главы отсчитываются от указанного там cd.
Команды mkdir/cp и перенаправление > создают/заменяют только названный выход
в этом личном стенде. Перед повторным опытом сохраните нужный журнал под
другим именем; не используйте этот стенд для единственной копии своего кода.

Go.mod сервиса и fixtures задаёт go 1.25.0, а проверяемый инструмент —
Go 1.27.3. С GOTOOLCHAIN=local отсутствующая/слишком старая версия вызывает
ошибку, а не загрузку другой. GOPROXY=off запрещает получение зависимостей,
GOSUMDB=off здесь допустим потому, что внешних архивов модулей нет. Для
публичных зависимостей используйте правила proxy/sumdb главы 15.

Каждая ожидаемая ошибка в cases оставляет исходники рабочей программы
нетронутыми. Успешная компиляция/сборка проверяется кодом 0, отрицательная —
ненулевым кодом и конкретным сообщением. Нельзя запускать оставшийся от
прошлого опыта бинарник после новой ошибки сборки.
