Проверки, отчёты и артефакты: как не получить ложный зелёный запуск

Успешный конвейер должен подтверждать определённые свойства продукта. Разделим проверки по наблюдаемому поведению, сохраним смысл ошибок через оболочку и разберём, почему файл отчёта не равен выполненному тесту.

Каждая проверка отвечает на определённый вопрос

Проверка синтаксиса устанавливает, что инструмент смог разобрать программу. Модульный тест исследует небольшую часть логики в выбранных условиях. Интеграционный тест проверяет совместную работу компонентов: например, приложение действительно подключилось к тестовой базе и выполнило запрос. Проверка упаковки исследует полученный файл, а проверка запуска из пакета — возможность воспользоваться доставляемым содержимым. Эти уровни дополняют друг друга, потому что наблюдают разные границы.

Можно успешно протестировать исходный каталог и забыть положить в архив шаблон ответа. Можно получить корректный ZIP с программой, которая использует отсутствующую системную библиотеку. Можно проверить HTTP-код 200 и не заметить неверный результат расчёта в теле. Поэтому формулируют конкретное утверждение: какой вход подаётся, какое наблюдение ожидается, что завершает действие ошибкой. Количество тестов само по себе не описывает силу этих утверждений.

Для нашей Go-службы полезна короткая цепочка: тесты обработчика; статические проверки; сборка; проверка бинарника и манифеста; запуск сохранённого бинарника из отдельного каталога; запрос к loopback и проверка ответа; гарантированное завершение дочернего процесса. Последний шаг важен: забытые процессы занимают порты, и следующий запуск может проверить старую программу. Тестовая база, если она нужна, получает отдельное имя и предсказуемую очистку.

Что реально выполняет go test

Go находит тестовые файлы, компилирует подходящие варианты пакетов и создаёт тестовый исполняемый файл. Он включает Test-функции, примеры и предусмотренную обвязку. go test ./... выбирает пакеты текущего модуля по шаблону; -run 'TestGreet' ограничивает исполняемые тестовые имена регулярным выражением. Успешная команда с неверным фильтром может выполнить ноль нужных тестов. Поэтому при создании конвейера полезно сопоставить список случаев и ожидаемое число, а также проверить отрицательный сценарий.

В internal/httpapp тест через httptest.NewRecorder передаёт обработчику искусственный запрос и читает статус, заголовки и тело. Он быстро проверяет правила /greet без отдельного слушающего процесса. Это хороший модульный уровень, но он не доказывает правильность флагов main, разрешение DNS, TLS-сертификаты или штатное завершение службы. Интеграционный тест добавляет настоящую выбранную границу, а не просто слово Integration в имени.

go test -count=1 ./...
go test -count=1 -run 'TestGreet' -v ./internal/httpapp
go vet ./...
go test -count=1 -coverprofile=coverage.out ./...
go tool cover -func=coverage.out

-count=1 отключает кэш результатов, -v показывает отдельные случаи, -coverprofile сохраняет профиль покрытия. cover -func читает этот файл и показывает покрытие по функциям. Покрытие означает исполнение инструментированных участков, а не доказательство всех логических ветвей и условий. Высокий процент совместим с неверными утверждениями в тестах. Например, запрос прошёл через обработчик, но тест проверил только отсутствие ошибки чтения, не сравнив тело.

go vet ищет определённые подозрительные конструкции статически. Это не исполнение программы и не полный поиск всех дефектов. go test сам может запускать предусмотренный набор vet-проверок, однако отдельный явный этап полезен как понятное требование. Состав анализаторов связан с версией toolchain; у Go 1.27 появился дополнительный стандартный контроль использования API, слишком нового для заявленной версии. Изменение версии Go способно изменить диагностику без правки исходников.

Гонки и нестабильные тесты

CGO_ENABLED=1 go test -race -count=1 ./... включает детектор гонок данных на поддерживаемой платформе с нужным внешним C-компилятором. Он инструментирует выполнение и наблюдает несогласованные обращения к памяти. Это другой бинарник и другие затраты, чем у выпуска CGO_ENABLED=0. Нельзя считать ускорением обычной процедуры удаление -race, если проверка гонок была обязательной. Нельзя и запускать его с CGO_ENABLED=0, игнорировать отказ и объявлять тестирование выполненным.

Отсутствие сообщения race означает отсутствие обнаруженной гонки в исполненных путях и расписаниях данного опыта, а не формальное доказательство всех возможных чередований. -shuffle=on меняет порядок тестов и печатает воспроизводимое начальное значение, -shuffle=ЧИСЛО позволяет повторить выбранный порядок. -count=10 помогает исследовать повторяемость. Если тест зависит от оставленного глобального состояния, другой порядок может выявить проблему. Повторная удача после провала ещё не исправление причины: результат сначала классифицируют и сохраняют.

Три канала результата

Автоматизация получает код завершения, машинный отчёт и человекочитаемый журнал. Код сообщает общий успех действия. Отчёт позволяет показать, какие проверки выполнялись и как менялись их длительности. Журнал объясняет причину. Если код нулевой, но обязательный отчёт отсутствует, это может означать, что тесты вообще не стартовали. Если отчёт есть, но принадлежит прошлому запуску, интерфейс покажет красивую чужую историю. Поэтому отчёты создают заново в известном каталоге и связывают с текущим запуском.

JUnit XML — распространённый формат обмена сведениями о тестах. Слово JUnit в имени не требует, чтобы приложение было написано на Java. Один производитель отчёта записывает XML, другой инструмент читает случаи, длительности и ошибки. У разных производителей есть расширения и различия, поэтому совместимость проверяют на реальном парсере. Стандартный go test -json выдаёт поток JSON-событий, а не JUnit XML; для передачи в JUnit plugin нужен явно выбранный и проверенный преобразователь формата.

<testsuite name="demo" tests="2" failures="1" errors="0" skipped="0">
  <testcase classname="test_app.Response" name="test_health" time="0.003" />
  <testcase classname="test_app.Response" name="test_total" time="0.002">
    <failure message="expected 12, received 11">Проверка суммы не прошла</failure>
  </testcase>
</testsuite>

Это иллюстрация контракта, а не настоящий отчёт выполненных здесь тестов. testcase описывает отдельный случай; failure — несоответствие ожиданию; errors обычно отделяют от таких несоответствий, но точное сопоставление задаёт производитель. XML должен быть корректно экранирован: сырые символы из исключения могут сломать отчёт. Число в атрибуте tests нельзя считать доказательством исполнения без доверия к производителю и проверки целостности процесса.

Поток go test -json не является одним большим JSON-массивом

go test -json -count=1 ./... > reports/go-test.jsonl

Каталог reports должен быть заранее создан для текущего запуска. Вывод содержит отдельные JSON-объекты на строках: пакет, имя теста при наличии, действие, время, текст и другие доступные поля. Событие output — строка журнала, а не окончательный результат. Событие fail может относиться к отдельному тесту либо пакету. Ошибка сборки до создания тестового процесса тоже должна остаться неуспехом. У Go 1.27 возможны дополнительные поля типа выходной строки; совместимый обработчик не должен падать только из-за неизвестного необязательного поля.

Преобразователь в XML должен учитывать иерархию пакетов и подтестов, пропуски, ошибки подготовки, завершение потока и незавершённые случаи при аварии. Простая замена кавычек на теги не сохраняет этот договор. Главное — не придумать успешное завершение случая, для которого процесс был убит до финального события. Производитель отчёта и его версия становятся инструментами конвейера; они тоже требуют примера с известным провалом и проверки принятия формата Jenkins.

Код завершения go test сохраняется отдельно от успешности преобразования. Можно получить корректный XML, содержащий провал, либо сломанный отчёт после успешного теста. В первом случае тестовая ошибка не должна исчезнуть, во втором потеря обязательного свидетельства должна быть заметна. Для начального автономного маршрута достаточно исходного JSONL и честного кода команды; если XML-преобразователь не поставлен и не проверен, не следует выдавать его публикацию за выполненный шаг.

Как Jenkins читает отчёт

При установленном JUnit plugin шаг junit testResults: 'reports/*.xml', allowEmptyResults: false читает совпавшие отчёты из workspace. Маска должна выбирать именно XML данного формата, а не все файлы проекта. Запрет пустого результата помогает заметить неверный путь и ситуацию, когда тестовая программа не создала отчёт. Обнаруженные неуспешные тесты могут дать состояние UNSTABLE; это требует явной политики допуска выпуска. UNSTABLE не следует автоматически трактовать как «всё нормально».

Шаг публикации отчёта удобно выполнять в завершающем блоке, чтобы детали сохранились и при неуспехе тестовой команды. Но основное решение об ошибке нельзя потерять: неудачные тесты и ошибка публикации отчёта — разные события. Для простого Go-конвейера достаточно честного ненулевого завершения go test и журнала. Добавлять JUnit стоит, когда нужны история случаев и удобная навигация, вместе с настоящим поддерживаемым генератором, а не фиктивным XML с заранее проставленным успехом.

Оболочка умеет скрывать ошибку

go test -count=1 -v ./... 2>&1 | tee tests.log

Такая запись выглядит удобной: 2>&1 направляет поток ошибок туда же, куда направлен обычный вывод; | передаёт объединённый поток в tee; tee копирует его на экран и в файл. Но в обычной POSIX-оболочке код конвейера определяется последней командой. Тесты могут завершиться ошибкой, а tee успешно запишет журнал и вернёт ноль. Jenkins увидит успех, если автор не сохранил нужный статус.

В простом случае уберите трубу и используйте уже имеющийся журнал Jenkins. Если копия обязательна и на агенте есть Bash, можно явно выбрать его и включить соответствующее поведение:

sh '''#!/usr/bin/env bash
set -euo pipefail
go test -count=1 -v ./... 2>&1 | tee tests.log
'''

Строка выбора интерпретатора должна идти первой, без предшествующей пустой строки. -e завершает сценарий при ряде необработанных ошибок; у него есть исключения по синтаксическому контексту, поэтому это не универсальное доказательство. -u считает обращение к незаданной переменной ошибкой. -o pipefail меняет код конвейера: ненулевой статус участника больше не теряется за успешным tee. Это возможность Bash; нельзя без проверки переносить её в любой /bin/sh. Флаг -v выше принадлежит go test, а не Bash.

Честный конвейер вывода Go

Файл с JSON не обязан содержать stderr сборочного инструмента в том же формате. Сохранение обоих каналов через 2>&1 удобно для человека, но может смешать не-JSON диагностику с машинным потоком. Если нужен парсер JSONL, стандартные потоки сохраняют отдельно либо используют предусмотренный инструментом договор. Журнал и отчёт должны оставаться читаемыми даже при синтаксической ошибке программы. Отсутствие ожидаемого сообщения об окончании рассматривают как неопределённый либо ошибочный исход, а не как успех.

У команды с pipefail всё равно есть несколько участников. Go мог успешно исполнить тесты, а tee — не записать файл из-за заполненного диска. Тогда общий шаг тоже неуспешен, но причина другая. Для точной автоматизации читают отдельные статусы в выбранной оболочке либо обходятся перенаправлением в файл с явным сохранением кода go test. Нельзя привязать слово ERROR только к одному каналу: фактический код, файл и последовательность событий читаются вместе.

Отделяем сохранённый продукт от ускорителя

Кэш позволяет восстановить вычислимые промежуточные результаты. Артефакт выпуска — конкретные утверждённые байты, на которые ссылаются доставка и восстановление. Сроки хранения отличаются: кэш удаляют ради места, выпуск сохраняют по принятой политике поддержки. Отчёт тестов тоже артефакт запуска, но он не заменяет сам пакет. В описании выпуска нужно знать, где находятся оба и какой пакет проверялся.

Сохраняйте разумный минимальный комплект: доставляемый файл, его SHA-256, идентичность исходников и зависимостей, описание конфигурации сборки, результаты обязательных проверок. Диагностические журналы могут иметь иной срок хранения и более узкий доступ. Не архивируйте весь workspace автоматически: там бывают токены, локальные ключи, временные данные и огромные кэши. Явный список файлов понятнее и уменьшает риск случайной публикации.

Наконец, проверьте сам механизм отказа. Измените ожидаемый результат одного учебного теста и убедитесь, что конвейер не допускает выпуск. Уберите обязательный файл из упаковки и убедитесь, что проверка пакета это замечает. Такой опыт показывает, что барьер действительно работает. Он ценнее ещё одного повторения неизменного успешного запуска, которое только подтверждает уже известный счастливый путь.

Проверить именно доставляемый Go-бинарник

После сборки читают manifest, вычисляют SHA-256 файла заново, проверяют target и ожидаемую Version, затем запускают этот путь с -version. Дымовой HTTP-опыт должен обращаться к дочернему процессу данного запуска: если порт занят, запуск обязан отказать, а не молча принять ответ старой службы. Наблюдают код процесса, ожидаемый JSON и его version, ограничивают время ожидания и в завершающем блоке останавливают именно созданный процесс. Так проверка не оставляет фоновую службу, влияющую на следующий прогон.

Отдельный отрицательный опыт полезнее искусственно большого числа тестов. Подмените ожидаемую Version либо байт артефакта и убедитесь, что проверка пары останавливает выпуск. Переименуйте обязательное поле JSON и убедитесь, что тест читает его смысл, а не только HTTP 200. Сделайте фильтр -run несуществующим и посмотрите отличие от реального исполнения. Затем верните изменения. Все эти опыты выполняют в собственной учебной копии; они проверяют устройство барьера, а не создают новую производственную политику.

Отказ инструмента и обнаруженный дефект — разные наблюдения

Синтаксическая ошибка может не позволить создать тестовый бинарник. Тайм-аут go test -timeout=30s означает, что пакет не завершил предусмотренное выполнение за бюджет; это не то же, что явный assert о неверном ответе. Убитый агент может оставить незавершённый JSONL. В каждом случае выпуск должен остановиться по принятому договору, но текст отчёта и путь расследования различаются. Преобразователь не должен скрывать build failure только потому, что не получил ни одного события Test с fail.

Для случайных и конкурентных дефектов одного входного примера мало. Подтесты позволяют перечислить классы входов: пустое имя, длинное UTF-8-имя, неподходящий метод, правильный JSON и неверный маршрут. Проверка длины строки в байтах отличается от числа видимых символов: в нашей службе предел 128 относится к UTF-8-байтам. Для такого условия полезна пара собственных русских строк с известной байтовой длиной. Тест обязан доказывать выбранный договор, а не просто повторять ту же ошибочную формулу другим вызовом.

Фаззинг, fuzzing, подаёт автоматически изменяемые входы и сохраняет найденные контрпримеры. У Go он требует специально написанной Fuzz-функции и явного бюджета запуска, а не возникает из флага обычных Test-функций. Найденный случай сначала превращают в воспроизводимую регрессионную проверку. Отсутствие находок за минуту не является доказательством для всех входов; это полезный дополнительный способ исследовать большой простор значений. В фактические проверки текущей службы запуск отдельной фаззинг-кампании не включался.

Чтобы отрицательный опыт был содержательным, изменяют ожидаемое поведение, а не подделывают XML с failures=1. Иначе проверяется только интерфейс отображения отчёта, а не способность теста обнаружить дефект программы. Эти оба опыта могут быть полезны, но их результаты нужно назвать точно. То же относится к smoke: ответ на loopback доказывает локальную границу, а не работу через внешний балансировщик и TLS.

Форматирование тоже нуждается в правильном барьере

gofmt -l cmd internal печатает имена требующих форматирования файлов; один код завершения не заменяет проверку непустого списка. В CI можно сохранить список отдельно, остановиться при ошибке самого gofmt и затем объявить неуспех, если файл списка непуст. Флаг -w, напротив, правит исходники. Автоматически отформатировать каталог и не проверить Git diff — значит скрыть рассогласование утверждённого снимка с реально собранными входами.

Такой случай повторяет общую модель главы: форматный анализатор, его структурированный результат и решение о выпуске — разные участники. Правильный код завершения возникает из точного договора, а не из надежды, что любое отсутствие аварии является успешной проверкой. Негативный форматирующий опыт проводят на одной собственной строке и затем возвращают её, проверяя работу барьера.

Для Go: test, vet, -json и кэш, модель тестов и benchmarks, тестирование HTTP-обработчиков, детектор гонок, изменения Go 1.27. JSONL и JUnit — разные форматы; встроенного преобразования между ними здесь не обещается.

Первичные источники

Jenkins JUnit plugin: чтение результатов и пустые отчёты; Jenkins sh: ошибка шага и returnStatus; Bash: коды завершения конвейеров и pipefail; Python unittest: исполнитель тестов. Пример XML описывает формат данных, не выдаёт искусственно созданный файл за выполненную проверку.
