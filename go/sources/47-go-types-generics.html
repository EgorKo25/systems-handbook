47. Типы и обобщения: от ограничения до машинной реализации

Параметр типа задаёт допустимые подстановки типов. Shape — форма общего машинного тела для совместимых подстановок; dictionary — передаваемые этому телу сведения о конкретной подстановке. Различие между правилами языка и устройством компилятора позволяет объяснить ошибки, размер двоичного файла и стоимость вызова без мифов о том, что любое обобщение обязательно бесплатно или обязательно исследует типы и значения во время исполнения через механизм reflection.

Файлы и версия опыта

Продолжаем с env.sh главы 14. Выполните cd "$LAB/fixtures/generics": здесь находятся собственный go.mod и main.go с Add, приведённым ниже. Используется Go 1.27.3, linux/amd64, GOAMD64=v1; внешних модулей нет. Бинарник demo и символы относятся только к этому выпуску и выбранным флагам. Обычный пользователь пишет результаты в свой стенд.

Идентичность, представление и допустимые операции

Тип отвечает сразу на несколько вопросов. Он определяет множество допустимых значений и операций, правила присваивания и доступные методы. Представление в памяти связано с типом, но не заменяет его идентичность. Объявление type Count int создаёт самостоятельный именованный тип; совпадение размера с int не разрешает автоматически все смешанные присваивания. Псевдоним через знак равенства устроен иначе: это другое имя того же типа, а не новое определение.

Компилятор обязан проверять эти различия до выбора инструкций. Если две переменные занимают по восемь байт, из этого не следует, что их можно складывать по любому правилу. И наоборот, несколько различных типов могут использовать похожую машинную последовательность после того, как корректность конкретной операции уже доказана. Разделение семантической идентичности и общей реализации является одним из ключей к пониманию дженериков Go.

Underlying type: отношение типов, а не совпадение размера

type Count int объявляет новый именованный тип; его основной тип (underlying type по спецификации) — int. В цепочке type Other Count основной тип Other тоже int. Напротив, type Alias = int объявляет другое имя самого int: Alias и int тождественны. Это отношения языка. На нашей amd64 int и int64 имеют по 64 бита, но ~int допускает Count и не допускает int64: совпавший размер хранения не делает основные типы одинаковыми. В объединении ~int | ~int64 присутствуют оба множества.

Ограничение определяет допустимые операции тела

В записи Add[T ~int | ~int64] параметр T может быть заменён типом, удовлетворяющим соответствующему множеству. Знак тильды задаёт множество типов с указанным основным типом, поэтому Count с основным int подходит. Без тильды простое перечисление int | int64 было бы более узким. Само тело Add должно быть допустимо для всех разрешённых вариантов, а не только для первого вызова, который случайно написан ниже.

Если ограничение заменить на any, выражение a+b перестанет быть обоснованным: не все допустимые типы имеют сложение. Ошибка появляется при проверке обобщённого определения. Это не обещание отложить выбор операции до исполнения и не поиск подходящего метода по строковому имени. Ограничение является частью статического договора, который помогает компилятору отвергать невозможные программы до запуска.

package main
type Count int
//go:noinline
func Add[T ~int | ~int64](a, b T) T { return a + b }
func main() {
    println(Add(2, 3))
    println(Add(Count(4), Count(5)))
    println(Add(int64(6), int64(7)))
}

Модуль с этим main.go уже находится в личном fixtures/generics. Три строки результата равны 5, 9 и 13. Директива noinline здесь удерживает отдельные тела для исследования, а не улучшает приложение. Без неё компилятор вправе встроить короткие вызовы и удалить часть видимых символов, после чего поиск по имени перестанет показывать интересующий механизм.

Вывод аргументов типа и явная конкретизация

В Add(2,3) типовой аргумент выводится из обычных аргументов и правил языка. Можно записать Add[int](2,3), сделав выбор явным. Это не создаёт новую ветвь выполнения по значению строки "int": компилятор уже на этапе сборки знает конкретную подстановку. Если аргументы не позволяют получить согласованную подстановку, следует разобраться в ограничении и типах входа, а не ожидать динамического угадывания.

Попробуйте Add("x","y"). Синтаксически вызов похож на предыдущий, но string не входит в выбранное множество. В выполненной отрицательной проверке компилятор отклонил такой вызов. Теперь расширьте ограничение строками и предскажите, какие свойства сложения перестанут быть общими математически. Оператор допускается, но его смысл для строк — конкатенация, поэтому числовое доказательство алгоритма нельзя переносить автоматически.

Type set не равен значению интерфейса

Множество типов, type set, определяет, какие типы удовлетворяют интерфейсу. Интерфейс с объединением типов или термом ~int можно использовать только как ограничение параметра типа; переменную такого интерфейсного типа объявлять нельзя. Это важное отличие от интерфейса с методами, значение которого хранит конкретную реализацию. В первом случае описывается множество возможных статических подстановок. Во втором во время исполнения существует значение интерфейса с конкретным динамическим типом и данными.

Отсюда следует полезный диагностический вопрос: исследуем ли мы ограничение при компиляции или объект интерфейса во время работы? Слова «это же интерфейс» без уточнения скрывают два механизма. Требование comparable тоже не является готовым алгоритмом хеширования: оно ограничивает допустимость операций сравнения, а реализация карты и вычисление хеша имеют дополнительные внутренние детали.

Shape: общее тело для совместимых подстановок

Компилятор Go 1.27.3 использует внутренние формы, называемые shape. Они позволяют разделять машинную реализацию между некоторыми подстановками, когда соответствующие операции и представления совместимы. Это не публичный контракт языка о точном количестве сгенерированных функций. Группировка зависит от типа, операций, архитектуры и версии. Нельзя определить её только по числу байтов значения.

go build -gcflags=-l -o demo .
go tool nm -size demo
go tool objdump -s main.main demo

Параметр -l у компилятора отключает встраивание в исследуемом пакете. nm перечисляет символы готового файла. В нашем опыте были видны тела с именами main.Add[go.shape.int] и main.Add[go.shape.int64]. Вызовы с int и Count использовали общую форму int, тогда как для int64 существовала другая форма. Это наблюдение конкретной программы на amd64, а не правило «все одинаковые по размеру типы всегда объединяются».

Какие байты кода приходится хранить

В nm -size первая колонка — адрес символа, вторая — размер в байтах, затем класс и имя. Ищите main.Add[go.shape.int], main.Add[go.shape.int64] и три main..dict.Add[…] для int, main.Count и int64. В проверке с отключённым встраиванием два вызова int и Count использовали одно тело shape.int, но разные словари. В objdump -s main.main видны загрузки адресов словарей и CALL к телу shape; третий вызов направлен к shape.int64. В изолированном повторе Go 1.27.3 оба тела имели по 5 байт, три словаря — по 8 байт. Это размеры этих символов, без утверждения о сумме всего ELF с выравниванием и метаданными. Адреса и размеры следующей сборки нужно читать из собственного вывода.

Совместное тело уменьшает число копий машинного кода для этих двух подстановок, но словарь занимает данные и может передаваться дополнительным аргументом. Число символов и их размер — наблюдение байтов, не время вызова в наносекундах. Для Add словарь может не потребовать полезной работы внутри тела; для операций с методами или типовой информацией использование будет другим. Для сравнения обычного встраивания сначала сделайте отдельную копию модуля, снимите там директиву //go:noinline и соберите go build -o demo-inline .. Затем снова прочитайте nm/objdump: часть вызовов может исчезнуть после оптимизации. В исходном demo директива остаётся, иначе сравнивались бы сразу два изменения.

Dictionary: дополнительные сведения конкретизации

Одного общего тела может быть недостаточно: некоторые действия требуют сведений о конкретном типе, его методах или связанных производных типах. Dictionary, то есть словарь конкретизации, предоставляет такие сведения. В таблице символов опыта присутствовали отдельные объекты ..dict.Add[int] и ..dict.Add[main.Count]. Их наличие позволяет понять, как общее тело сохраняет знание о разных исходных подстановках.

Словарь здесь не map[string]any и не универсальный поиск операции по тексту при каждом сложении. Это сгенерированные компилятором структуры и ссылки с известной организацией. Часть сведений может оказаться не нужна после оптимизаций. Отсюда нельзя вывести фиксированную накладную стоимость каждого generic-вызова: сначала нужно посмотреть конкретное тело, способ передачи сведений и результат встраивания.

Как связаны compile-time и runtime dictionaries

В noder/reader.go проверенной версии встречаются словари, используемые при чтении и конкретизации внутреннего представления, а также создание словарей, требуемых готовой программе. Одно и то же слово dictionary поэтому не всегда обозначает один объект в исполняемом файле. При чтении исходников важно следить, кто владеет структурой: процесс компилятора или создаваемое приложение.

Временная структура компилятора может содержать ссылки на его внутренние типы и индексы сериализованных данных. Runtime-словарь должен быть представлен пригодными для приложения символами и данными. Путать эти уровни опасно при оценке памяти: объём типов в процессе compile не равен объёму постоянно живущих объектов приложения. Профиль памяти компилятора и профиль памяти службы отвечают на разные вопросы.

Интерфейсное значение и упаковка

Когда конкретное значение передаётся как any или интерфейс с методами, программе нужно сохранить сведения о динамическом типе и доступе к данным. Для непустого интерфейса используется информация, связывающая конкретный тип с требуемыми методами. Слово boxing означает такую упаковку значения в интерфейсное представление. Оно не доказывает обязательное выделение нового объекта в куче при каждом присваивании.

Место хранения зависит от времени жизни, размера, конкретного значения и оптимизаций. Компилятор может устранить упаковку, оставить данные на стеке или воспользоваться специальной реализацией преобразования. Если интерфейс уходит в долгоживущее хранилище, ограничения становятся другими. Исследуйте -m=2 и фактические выделения памяти вместо правила «любой interface всегда выделяет память». Обратное правило «интерфейс всегда два слова, значит бесплатный» тоже игнорирует работу с данными.

Методы и динамический вызов

Вызов метода через интерфейс может требовать получения адреса реализации из соответствующей таблицы. Если конкретный тип доказан статически, компилятор способен девиртуализировать вызов, то есть заменить косвенное обращение известным прямым. Далее возможны встраивание и другие упрощения. Поэтому сравнение исходного синтаксиса интерфейсного и прямого вызова ещё не измеряет стоимость двух разных машинных механизмов: после оптимизации они могут совпасть.

Для чистого опыта сначала сохраните отдельные тела через noinline и проверьте вывод. Затем снимите ограничение и повторите исследование. Так можно увидеть как исходную границу вызова, так и разрешённое компилятором её устранение. Главное — не выдавать искусственно запрещённую оптимизацию за производственную характеристику языка. Цена абстракции определяется фактически оставшейся работой.

Почему не стоит обещать мономорфизацию всего

Термин мономорфизация обычно означает создание специализированной реализации для конкретного набора типов. Реальная стратегия Go сочетает формы, словари, обёртки и оптимизации. Поэтому фраза «дженерики полностью копируются для каждого типа» неверно объясняет наблюдаемые общие тела, а фраза «всё происходит через интерфейс» скрывает статическую проверку и специализированный код операций.

Оценивать следует несколько затрат: число конкретизаций в компиляции, объём машинного текста, размер вспомогательных данных, время вызова и влияние на встраивание. Уменьшение одного показателя может увеличить другой. Общее тело экономит машинный текст, но иногда требует дополнительного контекста; агрессивная специализация может улучшить локальную оптимизацию, увеличив размер программы и давление на кэш инструкций.

Экспорт обобщённого определения

Если generic-функция находится в другом пакете, импортирующему компилятору нужны сведения, достаточные для требуемых подстановок. Именно поэтому экспортные данные содержат не только имена доступных функций. Unified IR позволяет передавать необходимое тело и типовые сведения. Изменение такого тела способно повлиять на машинную реализацию зависимого пакета даже без изменения видимой сигнатуры.

Это помогает понять поведение кэша сборки: совпадение списка экспортированных имён недостаточно для доказательства, что ранее полученный код зависимого пакета можно использовать без проверки входов. Организатор сборки управляет более полной зависимостью. При разработке собственных генераторов и систем сборки не подменяйте её самодельным сравнением текстовых заголовков функций.

Ошибки эксперимента и чтение результатов

Если nm не показывает ожидаемую функцию, сначала проверьте, вызывается ли она, не встроена ли и не удалена ли связывателем. Если -gcflags передан только другой цели, исследуемый пакет мог собраться с обычными параметрами. Если изучается архив пакета, его набор символов отличается от набора окончательного файла: удаление недостижимого кода происходит позднее.

Имена со скобками являются шаблонными символами для некоторых командных оболочек и регулярных выражений. При фильтрации вывода обязательно учитывайте уровень обработки: оболочка, фильтр и инструмент могут понимать скобки по-разному. Самый простой первый шаг — сохранить полный вывод nm учебного файла и искать буквальное имя. Не добавляйте сложный регулярный фильтр до подтверждения исходных данных.

Практика выбора представления

Реализуйте одну операцию тремя способами: прямой функцией int, обобщением с подходящим ограничением и интерфейсом с методом. Проверьте одинаковый результат на пустом, коротком и длинном входе. Затем отдельно исследуйте сообщения встраивания, символы и машинный вызов. Только после этого запускайте серии benchmark с одинаковыми входами. Такая последовательность объясняет, почему результаты отличаются, и защищает от измерения устранённой компилятором работы.

Для интерфейсного варианта добавьте второй конкретный тип, который выбирается по входным данным. Это изменит доступное доказательство девиртуализации. Для generic-варианта добавьте несколько именованных типов и посмотрите, изменилось ли число shape-тел. Для прямого варианта проверьте удобство сопровождения копий. Решение должно учитывать не только наносекунды одного вызова, но и выражаемость ограничения, риск ошибки и стоимость сборки.

Нулевое значение и операции над параметром

Параметр типа не отменяет правило нулевого значения. Внутри функции можно объявить var zero T и получить нулевое значение конкретной подстановки. При этом запись T{} подходит не для всякого ограничения: литерал должен быть допустим для всех входящих типов. Компилятор проверяет общую возможность операции, а не рассматривает только текущее место вызова. Такой пример особенно полезен после работы исключительно со структурами, где фигурные скобки казались универсальным способом создания значения.

То же относится к nil. Если множество допустимых типов включает int, нельзя возвращать nil как произвольное T. Правильность функции зависит от её договора, а не от того, что два существующих вызова используют указатели. Вместо расширения ограничения до any ради удобства подумайте, действительно ли алгоритм умеет работать со всем новым множеством. Слабое ограничение способно сделать полезные операции недопустимыми, а слишком узкое вынудит вызывающего выполнять ненужные преобразования.

Указатели, методы и сохранение идентичности

Набор методов типа T и указателя *T может различаться. Обобщённое ограничение с методами проверяется по установленным правилам реализации интерфейса; автоматическое взятие адреса в обычном выражении вызова не превращается в универсальное доказательство выполнения ограничения. Если конкретизация не принимается, сначала выпишите требуемый метод и фактический набор методов переданного типа. Это даёт объяснение точнее, чем изменение всех параметров на указатели наугад.

Возвращаемое значение Add(Count(4),Count(5)) сохраняет тип Count, а не становится просто int из-за совместного shape-тела. Именно это позволяет отделить общую реализацию от публичного смысла. Проверьте присваивание результата переменной Count, а затем попытку прямого присваивания переменной другого именованного типа с тем же базовым int. Отказ второго варианта показывает, что разделение машинного кода не стирает типовую дисциплину программы.

Эти дополнительные упражнения относятся к семантике и могут быть проверены обычной сборкой без benchmark. Измерять скорость до установления правильного договора бессмысленно: быстрое решение другой задачи не является оптимизацией исходной программы. Сначала определите допустимые значения и результаты, затем выбирайте представление и только после этого оценивайте стоимость фактически полученной реализации.

Ещё один полезный контроль — изменить только тип константного аргумента, не меняя его числовое значение. Разница между нетипизированной константой и явно преобразованным значением может повлиять на вывод T. Если изменилось сообщение компилятора, запишите точные статические типы аргументов до и после: одинаковая печать числа во время исполнения не означает одинаковый типовой вход конкретизации.

В этой главе фактически проверены результаты трёх подстановок, наличие shape-тел и словарей в Linux amd64 и отказ неподходящего строкового вызова. Универсальная оценка ускорения, обязательной упаковки или числа инструкций из этих опытов не следует. Для другого тела и версии требуется повторить тот же маршрут наблюдения.
