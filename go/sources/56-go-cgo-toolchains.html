56. Cgo и внешняя цепочка: где заканчивается самодостаточность Go

Вызов C связывает два языка, два соглашения памяти и несколько инструментов. Соберём маленькую функцию через GCC, исследуем зависимость libc и намеренно проверим отказ без компилятора. Затем разберём pkg-config, флаги, cross-build и условия переносимости, которые один успешный go build не доказывает.

Import C обозначает специальный механизм

Псевдопакет C не является обычным модулем, который надо скачать. Его обрабатывает cgo: читает подготовительную C-часть, выясняет необходимые типы и имена и создаёт промежуточные Go- и C-файлы. Далее работают компиляторы соответствующих языков и связывание. Поэтому ошибка может относиться к Go, препроцессору C, компилятору C или linker, хотя пользователь запустил одну команду.

Сначала определите этап по сообщению и командам -x. Не следует чинить missing header редактированием go.mod, а неопределённый C-символ — преобразованием типов в Go наугад. Внешняя библиотека требует своего комплекта: заголовков для компиляции, объектов для связывания и иногда динамического файла для запуска. Наличие одного из трёх не гарантирует остальные.

Полный опыт с одной C-функцией

В projects/ch56 уже лежит main.go ниже. Комментарий непосредственно перед import "C" является preamble, то есть подготовительным C-текстом. Здесь определена статическая функция, поэтому внешняя сторонняя библиотека не нужна. Требуется установленная подходящая цепочка C.

Поставленный исходник: $LABROOT/projects/ch56. Читайте его как текст файла.

package main
/*
static int twice(int x) { return 2*x; }
*/
import "C"
func main() { println(int(C.twice(21))) }

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch56, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки. C/GCC должен уже существовать; иначе пропустите внешний режим, ничего не устанавливая.

cd "$LABROOT/projects/ch56" || exit 1
CGO_ENABLED=1 CC=gcc go build -x -o c-demo . || exit 1
./c-demo || exit 1
CGO_ENABLED=1 CC=gcc go build -ldflags=-linkmode=external -o c-external . || exit 1
readelf -dW c-demo || exit 1

В реальной Linux amd64 серии с системным GCC программа вывела 42, внешний режим также собрался, а динамические записи содержали libc.so.6. Даже собственная маленькая C-функция оказалась в программе с требованиями внешнего окружения. Это наблюдение конкретной цепочки, а не обязательный состав зависимостей всех cgo-программ.

Скаляр проходит через конкретный generated frame

Расширенный projects/cgolab содержит main.go и bridge.c; его команды будут ниже. В сохранённом WORK этого cgolab _cgo_gotypes.go определил _Ctype_int=int32 и _Cfunc_twice(p0)(r1). Обёртка передаёт runtime.cgocall адрес C-перехода и uintptr(&p0). В main.cgo2.c соответствующий frame занимает 16 байт: int p0 на смещении 0,4 байта padding, int r на смещении 8, ещё 4 байта padding. Значение 21 записано как 15 00 00 00, результат 42 — 2a 00 00 00; padding не является результатом вычисления. C-wrapper читает p0, вызывает twice, записывает r; сам внутренний хеш в имени _cgo_…_Cfunc_twice зависит от входов генерации.

Runtime.cgocall вызывает entersyscall, чтобы ожидание C не удерживало обычное Go-исполнение и не мешало GC, затем asmcgocall переключается на системный стек m.g0 и вызывает GCC-скомпилированную обёртку по C ABI. После C-вызова asmcgocall возвращает исходный стек горутины, cgocall делает exitsyscall и при необходимости ждёт возможности продолжить Go с соблюдением GOMAXPROCS. Go-обёртка возвращает r1 вызывающему коду. При вложенном обратном вызове (callback, C вызывает Go) стек горутины может измениться; generated C-wrapper получает _cgo_topofstack до/после и корректирует адрес frame перед записью результата. Это реальные производители/потребители из нашего WORK, а не чтение C.int прямо из произвольного регистра ABIInternal.

Первый короткий пример ch56 печатает 42 через встроенную println: в закреплённой реализации этот диагностический вывод идёт в stderr. Поэтому пустой stdout при коде 0 не означает, что twice не исполнилась. Расширенный cgolab использует fmt.Printf в stdout и проверяет скаляр/массив/callback отдельно. Сборочный -x также печатается в stderr, поэтому журнал сборки и вывод исполнения сохраняются разными файлами.

Разрешённый byte-buffer показан в cgolab: []byte{1,2,3} передаётся как unsigned char* и размер 3 в synchronous sum_bytes; C возвращает 6 и не сохраняет указатель. Во время вызова backing array не содержит Go-указателей и не теряет время жизни; после возврата право C пользоваться адресом заканчивается. Runtime.Pinner — объект явного закрепления допустимого Go-хранения на заданный срок. Он мог бы обеспечить более долгий период закрепления допустимого объекта при явно согласованном владении, но Unpin разрешён только после прекращения C-доступа. Сам объект Pinner также должен оставаться живым всё время, пока C хранит Go-указатель: одного сохранённого числового адреса недостаточно. При завершении последнего использования runtime.KeepAlive(pinner) может явно продлить его живость до этой точки; он не вызывает Pin и не заменяет согласованное прекращение C-доступа. Это требование закреплено в runtime/pinner.go Go 1.27.3. Handle — номер регистрации связи с Go-значением; Handle.Delete вместо этого удаляет регистрацию значения; он не освобождает C.CString и не открепляет память Pinner. В данном fixture отложенного C-доступа нет.

Ветка badpointer выполняется только в собственном коротком ребёнке, с явно заданным GODEBUG=cgocheck=1 закреплённой версии. Проверено именно обнаружение вложенного незакреплённого Go-указателя; все возможные ошибки указателей этим режимом не обнаруживаются. Возврат pointer после конца владения остаётся ошибкой, даже если одна проверка его не заметила. Источник перехода: cgocall.go.

CGO_ENABLED выбирает набор файлов

При выключенном cgo файлы с import "C" не участвуют в соответствующей сборке. Это следует воспринимать как ограничение выбора файлов, а не как команду заменить C-вызов чистой реализацией Go. Если других подходящих файлов нет, пакет вообще не имеет собираемого содержимого. В нашей отрицательной проверке CGO_ENABLED=0 дал сообщение, что ограничения исключают все Go-файлы.

Библиотека может специально предоставлять альтернативный файл для режима без cgo. Тогда результат и возможности зависят от её договора. Нельзя обещать, что выключение cgo безболезненно для любого проекта. Сначала посмотрите выбранные файлы и тесты обоих вариантов, затем оценивайте переносимость и функциональные различия.

CC указывает реально нужный инструмент

Переменная CC задаёт компилятор C. Если она указывает на отсутствующую программу, сборка должна содержательно отказать. В серии использован искусственный путь compiler-that-does-not-exist и подтверждён ненулевой результат с упоминанием этого имени. Параметр -a применялся только в отрицательном временном стенде, чтобы кэш не скрыл необходимость повторного C-вызова.

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch56, входы приведены выше и поставлены в fixtures. Намеренный отказ: неверный CC даёт ненулевой код; удачный c-demo сохраняется. После диагностики верните CC=gcc. C/GCC должен уже существовать; иначе пропустите внешний режим, ничего не устанавливая.

cd "$LABROOT/projects/ch56" || exit 1
CGO_ENABLED=1 CC=compiler-that-does-not-exist go build -a -o missing .

Флаг -a принуждает перестроить соответствующие пакеты и может стоить заметного времени. Его не следует добавлять ко всем обычным сборкам ради уверенности. Для расследования сначала выясните, использовался ли готовый результат и какой инструмент требовался. Кэши этого опыта принадлежат личному стенду; глобальные кэши и настройки Go не меняются.

Входы моста, владение буфером и запрещённая ссылка

В projects/cgolab поставлены main.go и bridge.c. На нашем стенде уже имелись GCC13.3.0 и glibc-цепочка; pkg-config отсутствовал. Установка не выполнялась. При передаче C.int(21) генератор создаёт Go-обёртку, структуру аргументов и C-функцию перехода. В сохранённом WORK видны main.cgo1.go, main.cgo2.c, _cgo_gotypes.go, _cgo_export.h и объект C. Runtime cgocall организует выход из обычного Go-исполнения к C ABI и возвращение; это дополнительная работа на каждый переход, даже когда C-функция только умножает на 2.

В нашем linux/amd64 профиле C.int имеет 4 байта, Go int —8; неявная передача указателя на []int как int* была бы ошибкой формата. В fixture xs имеет тип []C.int{1,2,3}; C.sum_ints получает адрес первого элемента и отдельную длину 3, возвращая 6. Срезный заголовок Go не передаётся как C-массив. У такого backing array нет вложенных Go-указателей, C использует его синхронно и не сохраняет после возврата; KeepAlive подчёркивает конец нужного времени жизни. Для пустого среза &xs[0] недопустим: требуется отдельная ветвь с nil и длиной 0.

C.CString копирует строку в C-хранилище с завершающим нулём; C.free освобождает эту копию. Встроенный NUL в Go-строке обрывает чтение C-строки раньше длины Go; для двоичных данных нужен указатель+явная длина. Сохранённая C-стороной ссылка требует отдельного срока владения. Номер uintptr не закрепляет объект: правила runtime.Pinner касаются памяти и всех передаваемых вложенных ссылок, а не только внешнего адреса. Строку/срез как заголовок с внутренним указателем нельзя произвольно сделать долговечной C-структурой.

Для callback bridge.c вызывает экспортированную GoValue, передавая числовой runtime/cgo.Handle. Go создаёт регистрацию NewHandle для функции x+1, callback извлекает Value, после синхронного возврата вызывающий делает Delete. Получено 42 для 41. Удалённый handle больше нельзя использовать. В preamble оставлены объявления внешнего bridge; его определение лежит в отдельном bridge.c, чтобы //export не размножил внешнее определение в двух C-файлах. Этот опыт не создаёт чужих потоков и не проверяет асинхронные callbacks.

Обычный пользователь, cwd cgolab; существующий gcc выбирается только для этих команд. Ожидается 0 и bytes=6 и twice=42 sum=6 callback=42 C.int=4 Go.int=8. При отсутствии gcc остановитесь и читайте сгенерированные файлы как сохранённый материал; заменять системный компилятор или скачивать sysroot не требуется.

cd "$LABROOT/projects/cgolab" || exit 1
CGO_ENABLED=1 CC=gcc "$GO" build -work -x -o "$LABROOT/out/cgo" . 2>"$LABROOT/reports/cgo-build.txt" || exit 1
"$LABROOT/out/cgo" || exit 1
readelf -W -l -d "$LABROOT/out/cgo" || exit 1

Отдельная команда GODEBUG=cgocheck=1 "$LABROOT/out/cgo" badpointer намеренно передаёт &Box, внутри которого находится незакреплённый Go-указатель. Нативно получена panic «Go pointer to unpinned Go pointer», код 2; это ожидаемый отказ, после него основной файл и исходник сохранены. Исправление — изменить передачу/владение, а не отключать cgocheck. CGO_ENABLED=0 исключает этот main.go; неверный CC с -a даёт отказ до появления нового binary. Смешанный ELF зависит от указанного интерпретатора и библиотек целевой среды: один GOARCH не подготавливает cross C compiler. Правила и генерируемые входы закреплены cgo/doc.go, вход runtime — cgocall.go.

Флаги компиляции и связывания разделены

#cgo CFLAGS задаёт параметры компиляции C, CPPFLAGS — препроцессора, LDFLAGS — связывания; для других языков предусмотрены отдельные группы. Путь к заголовку через -I не заменяет библиотеку через -l. Если заголовок найден и C-файл скомпилирован, undefined symbol при связывании означает следующий этап, а не повтор той же ошибки поиска файла.

Поясняющий фрагмент/схема; частичное дополнение не является отдельным готовым файлом.

/*
#cgo CFLAGS: -I${SRCDIR}/include
#cgo LDFLAGS: -L${SRCDIR}/lib -ldemo
#include "demo.h"
*/
import "C"

Это схема собственного расширения, не готовая библиотека из текущего стенда. SRCDIR обозначает каталог исходника в предусмотренной обработке cgo. Для выполнения понадобятся действительно созданные include/demo.h и подходящая libdemo. Объявление флагов не скачивает их и не подтверждает совместимость двоичного файла.

Ограничения флагов и окружение

Cgo ограничивает допустимые аргументы некоторых директив. Дополнительные разрешения задаются отдельными переменными с регулярными выражениями и требуют осознанного выбора. Массовое разрешение всего ради исчезновения ошибки скрывает причину и расширяет доверие к полученным настройкам. Сначала прочитайте конкретный отвергнутый параметр и установите, зачем он нужен.

Переменные окружения CGO_CFLAGS и родственные добавляют параметры и имеют свои правила. Они могут стать скрытым входом сборки, который не виден в репозитории. Для воспроизводимости фиксируйте их либо используйте согласованные пакетные директивы. Успех в терминале с давно установленными флагами не доказывает, что рецепт работает на чистой машине.

Pkg-config даёт сведения об установленной библиотеке

Pkg-config читает описания пакетов внешних библиотек и возвращает необходимые параметры. Директива #cgo pkg-config: demo может получить пути и флаги по имени. Это не менеджер установки библиотеки и не механизм Go Modules. Если программа pkg-config отсутствует или не видит описание demo.pc, нужные сведения не появятся сами.

В нашей среде pkg-config отсутствует и этот маршрут не исполнялся. Он объяснён как отдельная зависимость. При cross-build особенно важно, какие именно описания читаются: параметры библиотек машины сборки не обязаны подходить целевой архитектуре. Правильный sysroot и путь метаданных являются частью инструментальной цепочки.

Cross-build требует C-компилятор цели

Чистый Go часто способен создать файл другой GOOS/GOARCH установленным набором инструментов. Для cgo дополнительно нужен подходящий компилятор C, заголовки и библиотеки цели. Установка GOARCH=arm64 не превращает обычный amd64 GCC в cross-compiler. Он может создать объект неправильной архитектуры либо отвергнуть аргументы.

Нужно определить target triple, ABI, системные заголовки и способ связывания. Затем проверить объект и окончательный файл статическими инструментами и запустить в соответствующей среде. В данной серии не было C cross-compiler и исполнения на arm64, поэтому переносимость примера на такую цель остаётся непроверенной.

Glibc и musl — разные условия

Динамическая зависимость libc.so.6 из опыта связана с использованной glibc-цепочкой. Минимальный контейнер с другой библиотекой может не иметь требуемого загрузчика и совместимых символов. Имя операционной системы Linux само по себе не устанавливает совпадение пользовательской среды. Это особенно заметно при переносе executable между базовыми образами.

Если нужна musl-сборка, подготавливают соответствующую цепочку и проверяют все внешние зависимости в ней. Параметр статического связывания тоже не гарантирует успех любой библиотеки: могут отсутствовать статические архивы или существовать дополнительные ограничения. Здесь musl и полностью статическая cgo-сборка не выполнялись.

Внешний linker и диагностика зависимостей

Явный -linkmode=external позволил проверить участие внешней цепочки на нашей машине. Конкретные команды видны через -x, а итоговые требования — через заголовки и динамические записи ELF. Эти наблюдения дополняют друг друга: команда сообщает процесс сборки, таблица файла — свойства полученного результата. Одно не заменяет другое.

При ошибке загрузки сначала посмотрите интерпретатор и NEEDED-записи. При ошибке связывания — переданные объекты и библиотеки. При ошибке компиляции — заголовки и флаги. Такой порядок сохраняет причинную связь и предотвращает бесконечное добавление -L и -I в надежде случайно исправить проблему другого уровня.

Стоимость перехода и размер порции работы

Граница Go/C требует предусмотренной подготовки состояния, поэтому частый вызов ничтожной операции может оказаться дорогим относительно полезной работы. Иногда лучше передавать массив и выполнять больше работы за один переход. Но крупная порция может ухудшить отзывчивость, увеличить временную память и усложнить отмену. Оптимизация должна учитывать весь договор операции.

Числовой twice удобен для проверки механизма, но его нельзя использовать как доказательство скорости настоящего C-алгоритма. Для сравнения нужны одинаковые входы, проверенный результат и серии по размерам. Время отдельного запуска c-demo включает старт процесса и runtime, поэтому не измеряет наносекундную цену одного перехода.

Эксплуатационный комплект

При доставке cgo-программы запишите Go toolchain, C-компилятор, ABI, набор внешних библиотек и целевую среду. Для автономной работы заранее подготовьте необходимые файлы и проверьте запуск без сети. Установка Docker или наличие go в PATH не являются достаточными условиями: отдельный GCC, заголовки и динамический загрузчик могут отсутствовать.

Если нужен минимальный режим без внешней цепочки, предоставьте проверенную альтернативу и явно опишите ограничения. Это инженерное решение интерфейса, а не магический флаг. Пользователь должен заранее понимать, сможет ли он только читать учебный пример, собрать его или полноценно выполнить на выбранном компьютере.

Промежуточные файлы как свидетельство механизма

Параметр go build -work сохраняет временный каталог сборки и печатает его расположение. Вместе с -x это позволяет увидеть сгенерированные мосты и конкретные вызовы инструментов. Для собственного опыта используйте отдельный каталог и не публикуйте автоматически весь вывод: пути и окружение могут содержать лишние сведения. После исследования сохранённые временные данные удаляются осознанно, отдельно от исходников проекта.

Не редактируйте такой сгенерированный файл как постоянное исправление программы. При следующей сборке он будет создан заново. Если ошибка связана с отсутствующим объявлением C, исправлять нужно исходный preamble или заголовок. Если мост показывает неожиданный тип, найдите его происхождение в целевом C ABI. Это отличает исследование результата генератора от поддерживаемого входа сборки.

Обратный вызов и повторное определение символа

При экспорте Go-функции для C возникают дополнительные ограничения организации preamble. Один и тот же текст может попасть в несколько создаваемых C-файлов. Если в нём находится обычное определение внешней функции, linker способен увидеть дублирование. Поэтому объявления и определения нужно размещать согласно договору cgo, а не копировать удачный preamble из примера без обратного экспорта.

Минимальный twice не содержит callback. Расширенный cgolab проверил синхронный возврат через GoValue и Handle; отдельные C-потоки, асинхронные вызовы и длительное удержание требуют других условий. При расширении лаборатории сохраняйте каждый новый переход как самостоятельную проверяемую ступень.

Кэш и внешняя библиотека

Если внешняя библиотека заменена вне обычного набора отслеживаемых исходников, нельзя автоматически считать любой старый кэш достаточным доказательством нового связывания. Сначала установите, что именно передаётся команде, какие файлы изменились и как организатор учитывает эти входы. Диагностическая перестройка в временном кэше помогает исключить влияние прошлого результата без разрушения личной среды.

Для выпуска лучше объявить версии внешних зависимостей и хранить воспроизводимый рецепт их подготовки. Наличие пакета на рабочем компьютере разработчика не является таким рецептом. Эта дисциплина особенно важна для автономного тренажёра: перед отключением сети нужно проверить весь комплект, а не только успешный запуск давно собранного executable.

Сохраняйте также границу ответственности: заголовок описывает интерфейс, библиотека реализует символ, загрузчик обеспечивает запуск, а приложение соблюдает владение данными. Когда эти роли записаны явно, сообщение каждого инструмента становится проверяемой подсказкой, а не поводом менять весь рецепт сборки одновременно.

Проверяйте соответствие выбранной целевой среде.

Граница испытаний

Проверены вызов собственной C-функции с результатом 42, внешний режим связывания, зависимость libc и отказы без CC и при отключённом cgo. Дополнительно проверены byte-buffer+len, CString/free, синхронный Handle callback и конкретный отказ cgocheck=1. Не проверялись pkg-config, musl, cross C compiler, callback из отдельного C-потока и длительное удержание указателей. Эти темы описывают необходимые договоры и будущие самостоятельные опыты, а не выполненные платформенные испытания.
