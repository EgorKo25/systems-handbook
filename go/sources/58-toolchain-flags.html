Флаги цепочки Go: от аргумента до наблюдаемого изменения

Одинаковое имя параметра ещё не означает одинакового действия. Научимся находить его владельца, передавать значение через нужную границу и проверять результат. Встроенные карточки охватывают открытые флаги шести инструментов закреплённого Go 1.27.3; внутренние диагностические пространства рассматриваем отдельно.

Сначала установить, кто читает аргумент

У команды go build роль организатора: найти модуль и пакеты, выбрать исходники, проверить кэш действий, вызвать компилятор, ассемблер, генератор связки с C и компоновщик. Компилятор compile получает уже подготовленный отдельный пакет; компоновщик link соединяет совместимые объекты и библиотеки. Ни один из них сам не выполняет весь модульный протокол команды go. Поэтому строка go build -N не означает «отключить оптимизацию»: организатор такого собственного флага не принимает.

Начинайте с четырёх вопросов: какой процесс разбирает имя; какое значение ожидается; к каким пакетам оно применяется; какой наблюдаемый результат должен измениться. Например, -p=1 у build ограничивает параллельные сборочные действия, а -p=example.org/flaglab у compile задаёт импортную идентичность пакета. -c у test только собирает тестовую программу, у compile задаёт параллелизм внутри пакета, у link печатает граф вызовов. Регистр тоже значим: compiler -C меняет диагностику колонок, driver -C меняет каталог.

Перед опытом сохраните go version, go env GOOS GOARCH GOROOT GOTOOLCHAIN и версию нужного инструмента, например go tool compile -V=full. Последний вариант печатает расширенную идентичность compile и завершает процесс. go help build, go help testflag и go tool compile -help описывают именно установленную цепочку. Ненулевой статус у некоторых низкоуровневых справок предусмотрен их интерфейсом; не путайте его с неуспешной сборкой приложения.

Подпись -o <путь> обозначает обязательное значение: допустимы -o out/app и -o=out/app. У логического флага другой разбор: -race=false выключает режим, но -race false оставляет отдельное слово false, которое может оказаться именем пакета. Счётные флаги compile тоже принимают присоединённое значение: -m=2 задаёт уровень, -N=false сбрасывает переключатель. Наличие равенства и кавычек здесь влияет на маршрут аргумента, а не только на оформление.

Малый модуль, на котором видны различия

Опыты ниже предназначены для отдельного нового каталога на Linux/amd64 с установленным Go1.27.3. Не подставляйте путь рабочего проекта. Создайте flaglab, войдите в него, создайте out и сохраните следующие файлы. Минимальная версия языка в go.mod не скачивает старый Go и не меняет версию установленного компилятора.

# go.mod
module example.org/flaglab

go 1.25.0

// sum.go
package main

func Add(a, b int) int { return a + b }

// main.go
package main

import "fmt"

var Version = "dev"

func main() { fmt.Println(Add(2, 3), Version) }

// sum_test.go
package main

import "testing"

func TestAdd(t *testing.T) {
    t.Run("positive", func(t *testing.T) {
        if got := Add(2, 3); got != 5 { t.Fatalf("got %d", got) }
    })
}

func BenchmarkAdd(b *testing.B) {
    for b.Loop() { _ = Add(2, 3) }
}

func FuzzAdd(f *testing.F) {
    f.Add(1, 2)
    f.Fuzz(func(t *testing.T, a, b int) {
        if Add(a, b) != Add(b, a) { t.Fatal("not commutative") }
    })
}

Для локального опыта можно установить GOENV=off, чтобы не читать пользовательский файл настроек Go, GOWORK=off, чтобы родительский go.work не объединял модули, GOTOOLCHAIN=local, чтобы не выбирать скачиваемую цепочку, и GOPROXY=off, чтобы запретить загрузку модулей через proxy. Это разные границы: readonly у go.mod не запрещает сеть, а отключённый proxy не изолирует произвольный исполняемый тест. Здесь внешних зависимостей нет; стандартные пакеты берутся из установленного Go и при необходимости компилируются локально.

go build -o ./out/app .
./out/app
go build -ldflags='-X main.Version=1.2.0' -o ./out/versioned .
./out/versioned
go test -count=1 -run='^TestAdd$/^positive$' -v .

Первая программа выводит 5 dev, вторая — 5 1.2.0. Внешний -o назначает выходной путь, внутренний -X меняет допустимую строковую переменную на стадии link. У test -count=1 заставляет исполнить проверки заново, сохранив возможность взять готовые объекты из кэша сборки. -run выбирает тест/подслучай регулярными выражениями; -v показывает их события. Это три разных изменения, проверяемые разными наблюдениями.

Передача через gcflags, asmflags и ldflags

Значение -gcflags имеет грамматику [шаблон_пакета=]список_аргументов. Один аргумент оболочки содержит несколько аргументов следующего процесса. В Linux-оболочке одинарные кавычки сохраняют пробелы до разбора командой go. Например:

go build -gcflags='example.org/flaglab=-N -l' -o ./out/debug .
go build -gcflags='example.org/flaglab=-m=2' -o ./out/explained .
go build -gcflags='all=-m' -gcflags='example.org/flaglab=-m=2' .

-N отключает оптимизации, -l отдельно отключает встраивание, -m=2 печатает подробные решения оптимизатора. Без шаблона параметры получают явно указанные в командной строке пакеты. Шаблон all охватывает также зависимости, поэтому может дать огромный журнал и другую стоимость сборки. Если правил несколько, для пакета действует последнее подходящее; списки не складываются. В третьем примере свой пакет получает -m=2, остальные — -m.

Аналогично -asmflags направляет параметры Go-ассемблеру, -ldflags — Go-компоновщику, -gccgoflags — альтернативному gccgo. Для C-компоновщика существует ещё один переход: Go link читает -extldflags и передаёт вложенный список внешнему системному инструменту. Команда go build -ldflags='-linkmode=external -extldflags "-Wl,-z,now"' . требует подходящей ELF/C-среды. Вложенные двойные кавычки сохраняются благодаря внешним одинарным; -Wl понимает C-драйвер, а не compile. Этот платформенный пример не объявляется проверенным на всех ОС.

Объекту недостаточно имени main.a

Прямой import-free опыт действительно мал: go tool compile -p example.org/flaglab -pack -o out/sum.a sum.go. Здесь -p задаёт идентичность, -pack выбирает пакетный архив, -o — файл. Архив содержит функцию Add, но не подготовку runtime, исполняемый main и все его импорты. Добавление main.go с fmt уже требует сведений о совместимых архивных зависимостях.

Следующий маршрут полностью подготавливает такой контекст средствами установленного go. Все команды выполняются в том же отдельном модуле. Не меняйте GOOS/GOARCH, инструментирование и прочие настройки между действиями:

go list -deps -export -f '{{if .Export}}packagefile {{.ImportPath}}={{.Export}}{{end}}' . > importcfg.link
go tool compile -importcfg=importcfg.link -p main -pack -o main.a sum.go main.go
go tool link -importcfg=importcfg.link -o ./out/direct-app main.a
./out/direct-app

go list описывает пакеты; -deps включает транзитивные зависимости, -export обеспечивает их экспортные архивы, -f форматирует записи шаблоном. Поле Export даёт реальный путь архива. Перенаправление > выполняет оболочка. Полученный importcfg.link связывает импортный путь с файлом пакета; пустые строки здесь допустимы. Формат подходит нашему простому набору без специальных importmap, embed и cgo. Он не является универсальным генератором полной конфигурации любого проекта.

Теперь прямые карточки с importcfg.link и main.a имеют реальные входы. Для сложной сборки используйте go build -work -x: -x печатает исполняемые команды, -work сохраняет промежуточный каталог с точными конфигурациями. Сравните его с -n, печатающим план без исполнения. Сохранённые архивы зависят от версии, архитектуры, режимов и флагов; перенос произвольного старого importcfg на другую машину не восстанавливает эти предпосылки.

У ассемблера и cgo собственные входы

Для amd64 сохраните отдельно ret.s. Не оставляйте его среди исходников обычного модуля без согласованного Go-объявления и понимания ABI — соглашения передачи аргументов и результатов между машинными функциями.

#include "textflag.h"
TEXT ·Ret(SB), NOSPLIT, $0-0
    RET

go tool asm -I "$(go env GOROOT)/pkg/include" -p example.org/flaglab -S -o out/ret.o ret.s
go tool asm -gensymabis -I "$(go env GOROOT)/pkg/include" -p example.org/flaglab -o out/symabis ret.s

Подстановка $(...) принадлежит оболочке; go env GOROOT возвращает корень установки. -I находит textflag.h, -S показывает инструкции и байты. -gensymabis вместо обычного объекта создаёт ABI-таблицу для compiler -symabis. Таблица и объект — разные результаты одной стадии. Для ARM64 этот исходник не обещан рабочим: набор инструкций и согласование ABI проверяются для цели отдельно.

cgo сначала генерирует связующие исходники и анализирует C-типы. В отдельном каталоге с установленным C-компилятором создайте demo.go:

package demo
/*
static int twice(int x) { return x * 2; }
*/
import "C"

func Twice(x int) int { return int(C.twice(C.int(x))) }

mkdir cgo-out
go tool cgo -debug-gcc -objdir=./cgo-out demo.go

-debug-gcc показывает фактические вызовы C-компилятора, -objdir выбирает каталог вспомогательных файлов. Получение demo.cgo1.go и demo.cgo2.c ещё не означает создание программы: полная цепочка должна скомпилировать Go/C, согласовать динамические импорты и выполнить link. Режим -dynimport принимает уже подготовленный объект, а не demo.go. Если нужен его настоящий вход _cgo_.o, берите его из сохранённого WORK полного cgo-build, не создавайте пустой файл с подходящим именем.

Особая ловушка автоматических перечней: строки -fgo-pkgpath и -fgo-prefix встречаются в help cgo как упоминания параметров gccgo. Сам cgo их не принимает. Его соответствующие параметры называются -gccgopkgpath и -gccgoprefix. В справочнике поэтому 20 реальных cgo-флагов, а не 22 найденных поиском слов с дефисом.

Внутренняя диагностика: грамматика вместо магического рецепта

У compiler -d отдельное пространство имён. go tool compile -d help печатает селекторы установленной версии, go tool compile -d ssa/help — правила SSA, внутреннего представления с однократным присваиванием каждой версии значения. Флаг верхнего уровня конечен; комбинаций селекторов, имён функций и значений существенно больше. Полный охват верхних флагов не означает поддержку каждой произвольной комбинации внутренних настроек.

ФормаОбласть и наблюдениеПример
key[=value],key[=value]Наблюдения, проверки или изменение конкретного преобразования; тип значения определяется селектором.-d=checkptr=1
ssa/phase/on или offВключение/выключение конкретного прохода, если такой режим ему разрешён; изменение может сломать предпосылки следующей стадии.-d=ssa/check/on
ssa/phase/time или memВремя/память прохода компилятора, а не приложения.-d=ssa/all/time
ssa/phase/debug=N, stats, testПодробность, статистика, внутренние проверки; поддержка зависит от прохода.-d=ssa/prove/debug=2
ssa/phase/dump=FunctionВыгрузка выбранной функции в файл с именем прохода и функции.-d=ssa/genssa/dump=Add
ssa/check/seed=NЗерно внутренней проверочной рандомизации, полезное для повторения дефекта компилятора.-d=ssa/check/seed=1234

Для обычных ключей различайте наблюдение ABI/замыканий/барьеров записи, переключение преобразований, PGO, проверку инвариантов, управление памятью самого компилятора и выбор подмножества по хешу. Для SSA all разрешает time/mem/dump, не любой флаг; genssa поддерживает dump, intrinsics — свой ограниченный набор. Пропущенное значение часто означает 1, но не заменяет обязательное имя функции у dump. Наличие селектора в help не делает его стабильным контрактом языка.

Как пользоваться полной карточкой без перебора всех переключателей

У шести карточек 264 реальные записи: build33, test65 с наследуемыми параметрами, compile69, link60, asm17, cgo20. В карточке у каждого флага есть действие, условия выбора, пример и ожидаемое наблюдение. Открывайте её по команде в тексте или через встроенный поиск. Выбирайте один изменяемый фактор: например, сначала сравните -l через -m, затем отдельно измерьте нагрузку. Не объявляйте изменение быстрым только потому, что бинарник стал меньше или в журнале стало меньше строк.

Профили compile/link относятся к процессам сборки; cpuprofile у test — к тестовой программе. -race, -asan, -msan требуют поддерживаемой среды и согласования стадий. Внутренние -B, -wb=false, -f, -g могут отключать проверки или гарантии: наличие объяснения не делает их нормальным способом ускорить службу. Флаг с верным синтаксисом может быть неприменим к конкретной цели.

Опорные источники: compile, link, asm, cgo, исходники Go1.27.3. Офлайн-снимки инвентаря и help build позволяют сверить именно закреплённую версию. Набор проверенных здесь опытов ограничен Linux/amd64; платформенные карточки объясняют контракт, а не заявляют выполнение на Windows/macOS и всех санитайзерах.
