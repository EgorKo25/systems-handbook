Лаборатория компилятора: от проверяемого вопроса до машинной инструкции

Откроем рабочие файлы настоящей сборки, повторим компиляцию и линковку, сопоставим сообщения об оптимизации с промежуточным представлением и выполнением программы. Версия стенда — Go 1.27.3, цель linux/amd64 с GOAMD64=v1. Каждый инструмент отвечает на свой вопрос; совпадение нескольких наблюдений даёт более сильное объяснение, чем один внушительный листинг.

Сначала построить опыт, затем выбирать прибор

Предположим, разработчик увидел return &v и решил, что вызов обязательно выделяет память в куче. Проверим именно это утверждение. Для начала фиксируем исходник, версию компилятора, параметры цели и способ вызова. Затем отдельно смотрим решение компилятора, наличие операции в машинном коде и число выделений при выполнении. Нельзя подменить последнюю величину временем сборки или количеством строк в диагностике.

Команды ниже рассчитаны на Bash и отдельный учебный каталог. Переменная GO должна содержать абсолютный путь к установленному go версии 1.27.3. Создаём временные исходники и отдельные кэши; GOENV=off исключает пользовательский файл настроек Go, GOTOOLCHAIN=local запрещает автоматический выбор другого инструментария, GOWORK=off исключает внешнюю рабочую область. GOPROXY=off подходит этому опыту: все импорты принадлежат стандартной библиотеке или нашему модулю. Проверки контрольных сумм зависимостей для реального проекта этим способом не отключают.

labroot=$(mktemp -d)
cd "$labroot"
export GOENV=off GOTOOLCHAIN=local GOWORK=off GOFLAGS=''
export GOPROXY=off GOMAXPROCS=2 CGO_ENABLED=0
export GOOS=linux GOARCH=amd64 GOAMD64=v1
export GOCACHE="$labroot/cache" GOPATH="$labroot/path"
export GOMODCACHE="$labroot/modules" GOTMPDIR="$labroot/tmp"
mkdir -p src/lab "$GOTMPDIR"
cd src
"$GO" version
"$GO" mod init example.org/compilerlab
"$GO" mod edit -go=1.25.0

mktemp -d создаёт каталог с уникальным именем. Кавычки сохраняют путь одним аргументом. mod init записывает имя нового модуля, а mod edit -go=1.25.0 задаёт минимальную версию и версию языка из go.mod; выполняется всё тем же Go 1.27.3. Никакой службе или системной установке этот пример не нужен. После завершения каталог можно удалить, предварительно сохранив нужные диагностические файлы.

В lab/lab.go поместим маленькие функции. Директива //go:noinline перед Use сохраняет саму функцию как отдельный вызов; она не запрещает встроить Ptr внутрь её тела. Аналогичная директива у Select упрощает поиск функции в диагностике.

package lab
func Ptr(v int) *int { return &v }
//go:noinline
func Use(v int) int { return *Ptr(v) }
//go:noinline
func Select(xs []int, i int, left bool) int {
    j := i
    if !left { j = i + 1 }
    if j < 0 || j >= len(xs) { return -1 }
    return xs[j]
}
//go:noinline
func Unchecked(xs []int, i int) int { return xs[i] }

В корневом main.go достаточно объявить package main, импортировать example.org/compilerlab/lab и вызвать из main выражение println(lab.Use(4), lab.Select([]int{10,20}, 0, true)). Встроенная println здесь нужна только для короткого проверочного результата; это не библиотека для формата прикладных журналов. Проверенные значения — 4 10.

WORK: проследить входы и сохранить улики

"$GO" build -work -x -o app . 2>build.log

-work печатает путь WORK=... и оставляет временное дерево после завершения. -x печатает выполняемые команды, -o app выбирает итоговый файл, точка выбирает пакет текущего каталога. Номера каталогов b001, b002 — внутренние идентификаторы действий этой сборки; жёстко подставлять их из чужого примера нельзя. Переходите к каталогу по команде компиляции с -p example.org/compilerlab/lab, затем к команде с -p main.

Внутри найдётся importcfg — конфигурация разрешения импортов для конкретного действия. Строка packagefile путь=архив связывает импорт с уже выбранным скомпилированным архивом; importmap, если присутствует, перенаправляет имя импорта. Здесь зафиксирован результат работы команды Go с модулями, стандартной библиотекой и графом пакетов. Компилятор не начинает заново выполнять алгоритм выбора версий из go.mod. Архив _pkg_.a содержит вход для следующих компиляций и линковщика; наличие файла ещё не означает, что это готовый исполняемый ELF.

В пакете без ассемблера go_asm.h может отсутствовать. Чтобы увидеть происхождение этого файла, добавьте к lab.go объявления type Pair struct { A, B int64 }, const Scale = 3 и func AddAsm(a, b int64) int64. В lab/add_amd64.s запишите следующий собственный ассемблерный фрагмент. Суффикс имени ограничивает файл архитектурой amd64.

#include "textflag.h"
TEXT ·AddAsm(SB),NOSPLIT,$0-24
    MOVQ a+0(FP), AX
    ADDQ b+8(FP), AX
    MOVQ AX, ret+16(FP)
    RET

Это функция с соглашением ABI0 для написанного вручную Go-ассемблера: два восьмибайтовых аргумента и восьмибайтовый результат занимают 24 байта аргументной области. $0-24 задаёт нулевую локальную область и её размер аргументов, FP — символическую базу аргументов, а не прямое обещание регистра процессора. NOSPLIT взят из заголовка textflag.h; для этого короткого фрагмента не вставляется обычная проверка роста стека. Менять это соглашение по аналогии с ассемблером C нельзя.

Повторите сборку после изменения. Теперь компилятор получает -asmhdr и создаёт заголовок с определениями наподобие const_Scale 3, Pair__size 16, Pair_A 0, Pair_B 8. Ассемблер получает пути поиска заголовков через -I, создаёт объект add_amd64.o, затем упаковщик добавляет его в архив пакета. Подготовительный запуск ассемблера с -gensymabis создаёт сведения о соглашениях вызова для компилятора. Это наблюдаемые связи файлов, а не требование иметь заголовок в каждом Go-пакете. Разбор соглашений вызова дан в отдельной главе; здесь достаточно проследить производителя и потребителя.

Прямой compile и link: не терять подготовленные входы

Команда go tool compile компилирует перечисленные исходные файлы одного пакета. Она не заменяет go build с его выбором файлов по ограничениям сборки, поиском зависимостей, запуском ассемблера и упаковкой. Поэтому первый корректный прямой опыт — повторение реально напечатанной команды, пока сохранённый WORK и кэш существуют.

Скопируйте из журнала полную команду компиляции main, замените в ней только аргумент -o на main-replay.a и выполните её из указанного журналом рабочего каталога. Раскройте обозначение $WORK в реальный сохранённый путь. Сохраните -p main, -importcfg, версию языка, набор файлов и остальные напечатанные параметры. Затем скопируйте команду link, заменив её выход на app-replay и последний входной архив на main-replay.a.

# Схема аргументов; пути и остальные параметры берутся из build.log.
"$GO" tool compile -p main -pack -importcfg /путь/из/WORK/importcfg \
    -o main-replay.a ./main.go
"$GO" tool link -importcfg /путь/из/WORK/importcfg.link \
    -o app-replay main-replay.a

Эти две строки объясняют устройство, а не являются готовой заменой полного журнала. -p задаёт идентичность пакета, -pack выбирает выходной архив, -importcfg передаёт подготовленные зависимости, -o именует результат. Для пакета с ассемблером прямой повтор одной команды compile ещё не добавит новый .o упаковщиком. Для go:embed дополнительно понадобится созданный сборщиком embedcfg. На нашем опыте повтор compile/link выдал тот же проверочный результат; равенство вывода не доказывает побайтового равенства бинарников.

Встраивание и уход значения в кучу: три независимых наблюдения

"$GO" build '-gcflags=example.org/compilerlab/lab=-m=2' ./lab
"$GO" build '-gcflags=example.org/compilerlab/lab=-m' ./lab

-gcflags адресует параметры компилятору выбранного пакета. Шаблон до знака равенства ограничивает воздействие нашим lab; форма all=... изменила бы также зависимости. Внешние кавычки сохраняют весь аргумент. -m включает сообщения о решениях оптимизатора, -m=2 повышает подробность. Эти сообщения относятся к компиляции, не к каждому вызову запущенного приложения.

В проверке Go 1.27.3 видны возможность встроить Ptr, фактическое встраивание её вызова в Use и сообщение moved to heap: v для самостоятельного тела Ptr. Противоречия нет: самостоятельная функция должна вернуть живой адрес после своего завершения, а встроенный участок внутри Use немедленно разыменовывает указатель и возвращает число. Судьба значения в этих двух контекстах различается. Ищите позицию исходника и цепочку объяснения, а не одно слово escapes во всём журнале.

В lab/lab_test.go объявите пакет lab, импорт testing, глобальное целое Result и функцию ниже. Глобальный числовой результат не даёт удалить наблюдаемый эффект, но не сохраняет исследуемый указатель. b.Loop организует измерительный цикл.

var Result int
func BenchmarkUse(b *testing.B) {
    for b.Loop() { Result = Use(42) }
}

"$GO" test '-run=^$' -bench=BenchmarkUse -benchmem -count=1 ./lab
"$GO" test '-run=^$' -bench=BenchmarkUse -benchmem -count=1 \
    '-gcflags=example.org/compilerlab/lab=-l' ./lab

-run=^$ исключает обычные тесты по регулярному выражению имён; -bench выбирает бенчмарк, -benchmem добавляет статистику выделений, -count=1 исключает повторное использование готового результата тестового запуска. Вторая команда передаёт компилятору -l, отключающий встраивание только для нашего пакета. В проведённом опыте первый вариант дал 0 B/op, 0 allocs/op, второй — 8 B/op, 1 allocs/op. Размер относится к восьмибайтовому int этой цели. Время в наносекундах зависит от стенда и здесь не служит нормой производительности.

Параметр -N отключает оптимизации; сочетание -N -l полезно для отладчика, когда нужно менее преобразованное исполнение. Оно меняет исследуемую программу. Сравнивать такой результат с промышленной сборкой и объявлять найденную разницу свойством исходного алгоритма некорректно. Для нашей гипотезы достаточно отдельно отключить встраивание и повторить остальные условия.

SSA: сравнить представления до и после доказательства

SSA — форма промежуточного представления с единственным присваиванием каждому значению. Нам нужен конкретный вопрос: остаётся ли дополнительная проверка границ у xs[j], если выше уже проверен диапазон j? Сначала получаем список возможностей установленной версии.

"$GO" tool compile -d help
"$GO" tool compile -d=ssa/help
mkdir -p "$labroot/ssa"
GOSSAFUNC=Select GOSSADIR="$labroot/ssa" "$GO" build \
    '-gcflags=example.org/compilerlab/lab=-d=ssa/build/dump=Select,ssa/prove/dump=Select,ssa/check_bce/debug=1' ./lab

-d выбирает внутренние диагностические настройки. Первая справка перечисляет именованные селекторы, например closure, nil, wb, pgodebug; их значения и смысл различаются. Вторая описывает семейство ssa/фаза/параметр. Здесь build/dump=Select сохраняет представление функции после построения, prove/dump=Select — после прохода доказательства свойств, а check_bce/debug=1 сообщает оставшиеся операции проверки границ. Запятые объединяют настройки одного аргумента -d.

GOSSAFUNC=Select выбирает функцию для HTML-наблюдения, GOSSADIR задаёт каталог диагностических файлов. В этом опыте появились текстовые Select_01__build.dump, Select_02__prove.dump и HTML с именем, содержащим путь пакета и Select,1. Последняя часть связана с внутренним именованием; лучше открыть путь, напечатанный самой командой. HTML работает локально и позволяет сопоставить строки исходника, значения и последовательные проходы без интернета.

В начальном дампе наблюдалось Phi, выбирающее значение j из двух предшествующих ветвей, и IsInBounds перед загрузкой элемента. Функция слияния Phi описывает зависимость результата от пути управления; это ещё не конкретная процессорная инструкция. После prove операция IsInBounds у Select отсутствовала: до загрузки уже установлены нижняя и верхняя границы. У Unchecked диагностика сохранила Found IsInBounds. Отсутствие этой строки у одной функции имеет смысл только при подтверждении, что она действительно перекомпилировалась и что выбран нужный пакет.

Нельзя вывести отсюда, что любая предварительная проверка убирает любую последующую: оптимизатор должен связать именно эти значения и пути управления. Попробуйте заменить индекс на результат непрозрачного вызова или изменить срез между проверкой и чтением. Сначала сформулируйте, какое доказательство утрачивается, затем откройте оба дампа. Так читают поведение установленного компилятора, не превращая конкретный проход в обещание языка Go.

Инвентаризация диагностик и пределы сочетаний

Общий список имён фаз и список параметров не образуют таблицу всех допустимых сочетаний. В 1.27.3 ssa/all поддерживает time, mem, dump; у intrinsics доступны on/off/debug, у genssa — dump. Для build есть debug/test/stats/dump. Остальные проходы имеют свои проверки; часть необходимых преобразований вообще нельзя отключить. Источник истины для необычного случая — обработчик настроек конкретной версии, затем короткий опыт с проверкой кода завершения.

Встроенная справка может упрощать деталь реализации: проверенная версия создаёт имена текстовых файлов в порядке «функция, номер, фаза», хотя шаблон в кратком описании перечисляет компоненты иначе. Поэтому лаборатория фиксирует фактические имена, версию и содержимое, а не строит автоматизацию на догадке. Снимок справки и полный перечень флагов хранятся рядом с книгой в labs/toolchain-reference/; для иной версии их следует получить заново.

Ассемблер компилятора и байты готового файла

"$GO" build '-gcflags=example.org/compilerlab/lab=-S' ./lab
"$GO" tool objdump -s 'example.org/compilerlab/lab.Use' ./app

Компиляторный -S печатает листинг создаваемого кода с символами и служебными данными. objdump разбирает уже существующий объект или исполняемый файл; -s здесь фильтрует символы регулярным выражением. Это другой флаг другой программы. В нашем итоговом бинарнике Use состояла из RET с байтом c3: аргумент и результат занимают AX, отдельная загрузка даже не потребовалась. Одна инструкция объясняет конкретное тело, но ничего сама по себе не говорит о сетевых ожиданиях или стоимости остальных функций сервиса.

Сохраняйте рядом с листингом точную команду создания бинарника. Если открыть старый app после сборки только ./lab, objdump честно покажет старый файл. Изменение исходника не переписывает ранее созданный исполняемый артефакт автоматически. Проверка времени, размера, хеша и версии сборки устраняет эту распространённую ошибку опыта.

Практика: доказать изменение, не потеряв причинную связь

Сохраните два исходника и команды. Для каждого варианта запишите версию Go, цель, параметры, результат -m=2, выбранный SSA-дамп, нужный участок objdump и статистику бенчмарка. Меняйте один вход. Для утверждения о выделениях нужны измеренные выделения; для утверждения об устранённой проверке — соответствующий участок представления или кода. Если результаты расходятся с ожиданием, проверьте кэш, адресованный пакет и свежесть бинарника раньше, чем придумывать объяснение оптимизатора.

Первичные материалы: команда compile, устройство компилятора, обработка SSA-диагностик и запись дампов, выбор GOSSAFUNC, objdump, сборщик и тестовый запуск. Версионные детали в главе дополнительно проверены локальным исходным кодом и исполняемыми файлами Go 1.27.3.
