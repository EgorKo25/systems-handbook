54. Память и GC: от решения компилятора до сканирования кучи

Число выделений, объём живых данных и длительность обработки связаны, но не тождественны. На двух пакетах значений увидим 129 и одно выделение, затем разберём распределитель, указатели, барьер записи и Green Tea в Go 1.27.3. Цель — объяснять измерения, а не стремиться к нулю любой ценой.

Сначала определить четыре разных величины

Выделенный за период объём показывает поток создаваемых данных. Живая куча показывает данные, которые ещё нужны после определённого момента. Рабочая память процесса включает также стеки, runtime, отображения и другие части. Задержка операции зависит от полезной работы и сопутствующих затрат. Уменьшение одной величины не доказывает пропорционального уменьшения остальных.

Например, быстро создаваемые временные объекты могут давать большой поток выделений и небольшую живую кучу. Один сохранённый буфер способен удерживать много памяти при малом числе выделений. Поэтому перед оптимизацией задайте вопрос: ограничены CPU, пиковая память, пауза, стабильная задержка или стоимость контейнера? От ответа зависит, какие данные нужно собирать.

Полный опыт с массивом значений и указателей

В projects/ch54 уже лежит memory_test.go ниже. Здесь оба варианта формируют 128 чисел, но первый возвращает указатели на самостоятельные значения, а второй хранит числа непосредственно в общем срезе. Глобальные переменные явно сохраняют результат, чтобы исследовалась действительно переживающая итерацию структура.

Поставленный исходник: $LABROOT/projects/ch54. Читайте его как текст файла.

package memory
import "testing"
var Pointers []*int
var Values []int
func PointerBatch(n int) []*int {
    r := make([]*int, n)
    for i := range r { v := i; r[i] = &v }
    return r
}
func ValueBatch(n int) []int {
    r := make([]int, n)
    for i := range r { r[i] = i }
    return r
}
func BenchmarkPointers(b *testing.B) {
    for b.Loop() { Pointers = PointerBatch(128) }
}
func BenchmarkValues(b *testing.B) {
    for b.Loop() { Values = ValueBatch(128) }
}
func TestAllocs(t *testing.T) {
    p := testing.AllocsPerRun(20, func() { Pointers=PointerBatch(128) })
    v := testing.AllocsPerRun(20, func() { Values=ValueBatch(128) })
    t.Logf("pointers %.0f values %.0f", p, v)
    if p <= v { t.Fatal("expected more pointer objects") }
}

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch54, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

cd "$LABROOT/projects/ch54" || exit 1
go test -v -run TestAllocs || exit 1
go test -run='^$' -bench=. -benchmem -benchtime=50ms -count=3 || exit 1

В выполненном Go 1.27.3 опыт показал pointers 129 values 1. У первого варианта есть хранение среза указателей и множество отдельных целых, у второго — общее хранение чисел. Значение 129 не является законом для всех указательных структур: оно относится к данным исходникам и параметрам. Проверка лишь утверждает важное относительное различие.

Флаги и единицы измерения

-run выбирает обычные тесты, поэтому шаблон ^$ исключает их из измерительной команды. -bench выбирает benchmark, -benchmem добавляет байты и число выделений на операцию. -benchtime задаёт длительность отдельного измерения, а -count повторяет серию. Короткие 50ms удобны для учебной проверки механизма; серьёзный выбор требует более устойчивых серий и подходящей нагрузки.

ns/op относится к определённой операции benchmark, а не к одному элементу автоматически. Здесь операция — создание пакета из 128 чисел. B/op показывает выделенный объём, а не остаток живой памяти после GC. allocs/op считает выделения, но не число системных вызовов и не число физических страниц. Единицы следует записывать вместе с определением операции.

Что компилятор уже решил

Адрес v сохраняется в возвращаемой структуре, поэтому значения должны пережить локальную итерацию. Escape analysis помогает выбрать корректное размещение. В ValueBatch числа находятся непосредственно в общем backing array, отдельного адресуемого объекта для каждого элемента алгоритм не требует. Разница начинается с представления и времени жизни, а не с настройки частоты GC.

При этом представления не всегда взаимозаменяемы. Если вызывающей стороне нужна самостоятельная идентичность объекта, совместное изменение через разные ссылки или возможность nil для элемента, []int не является полной заменой []*int. Оптимизация допустима только после проверки такого договора. Числовое совпадение первой печати не доказывает эквивалентность всех будущих операций.

От запроса байтов до свободного места в span

Span — описание непрерывной группы страниц кучи и размещённых в ней слотов объектов. Mcache — локальный запас таких span. У Go 1.27.3 этот запас принадлежит P — ресурсу планировщика, который нужен потоку для исполнения обычного Go-кода. P ссылается на mcache; поток M и текущая горутина G — отдельные объекты. В mcache.alloc выбранный spanClass объединяет размер и признак noscan. Noscan означает, что данные объекта не содержат Go-указателей, которые должен обходить GC. Массив int и массив *int имеют разные требования даже при одинаковом числе байтов.

Для конкретного запроса 33 байт без указателей выбирается 48-байтовый класс. Span описывает непрерывную группу страниц runtime, размер элемента elemsize и битовую карту занятости (bitmap). В частом пути allocator выбирает свободный слот текущего span, обновляет индекс свободного места freeindex и число занятых слотов allocCount, обеспечивает нулевое исходное содержимое и возвращает адрес. Когда слоты закончились, mcache.refill получает подходящий span через mcentral — общий запас span данного класса; тот может потребовать sweep старого span или получить страницы у mheap, менеджера страниц кучи. Если подходящих страниц нет, mheap расширяет обеспеченную область через ОС. Получение span распределяет стоимость синхронизации между многими объектами.

Внутренняя страница Go heap здесь равна 8192 байтам; страница Linux из auxv равна 4096. Это разные единицы учёта. Крупный запрос 64 KiB без указателей занимает span из восьми внутренних страниц и проходит к mheap, обходя обычный малый mcache-класс. Для сканируемых объектов учитываются заголовки и данные о типах, поэтому фактическая граница малого пути выражена через MaxSmallSize−MallocHeaderSize, а не произвольное округлённое «около 32 К». В этом выпуске включён SizeSpecializedMalloc: компилятор/runtime могут выбрать специализированный малый путь; организация классов и refill остаётся причиной расхода, но одна универсальная цепочка вызовов для каждого new не обещается.

Для крошечного восьмибайтового int без указателей tiny allocator способен объединить два запроса в один 16-байтовый блок: tinyoffset 0→8→16. Следующий запрос потребует новый блок. Подобъекты освобождаются вместе, когда весь tiny-блок недостижим. Статистика логических выделений учитывает и подобъекты; 129 allocs/op у PointerBatch не означают 129 системных запросов или 129 самостоятельных 16-байтовых блоков. Данные [128]*int требуют сканирования ссылок, тогда как []int хранит числа одним backing array. Реально получены 129 против 1 allocs/op, как и предсказывает код; их размеры и длительности не равны RSS.

Указатели влияют на сканирование

Сборщику нужно находить ссылки на другие объекты. Данные без указателей не требуют такого же поиска внутренних ссылок, как структуры со множеством указательных полей. Два одинаковых по размеру буфера могут иметь разную стоимость сканирования. Кроме числа объектов существенны связность, расположение и объём указательных областей.

В нашем опыте срез указателей образует граф из общего массива и отдельных значений. Массив целых хранит полезные данные плотнее и не содержит ссылку на каждый элемент. Это может улучшить локальность и уменьшить работу GC, но конкретное ускорение требует измерения. Сам тест AllocsPerRun доказывает только число выделений, а не полный выигрыш сканирования.

Один адрес нужен до возврата, другой сохраняется глобально

Возьмём уже поставленные Read, Borrow и Save из главы 48. В Borrow(7) функция Read получает адрес того же v и успевает прочитать его до возврата Borrow. В Save(9) адрес сохраняется в Global. Компилятор заранее выбирает для такого адресуемого v хранение, переживающее вызов; действующий стековый объект не переносится в кучу задним числом после возврата.

Достижимый объект можно найти, переходя по живым указателям от корней сборщика мусора, GC. Корни включают необходимые ссылки стеков, глобальных данных и runtime. Остаточные биты старого адреса в уже ненужной ячейке сами по себе не образуют такую живую ссылку.

var Global *int

//go:noinline
func Read(p *int) int { return *p }

//go:noinline
func Borrow(v int) int { return Read(&v) }

//go:noinline
func Save(v int) { Global = &v }

Mark и sweep

Сборка мусора устанавливает, какие объекты достижимы от корней, а затем делает недостижимое хранение доступным для повторного использования. Корни включают необходимое состояние стеков, глобальных данных и runtime. Маркировка и сканирование являются связанными действиями: пометить объект как найденный недостаточно, если внутри него ещё нужно найти ссылки.

Go выполняет значительную часть этой работы конкурентно с приложением. Но «конкурентный» не означает полное отсутствие остановок и CPU-затрат. Есть служебные переходы фаз, фоновая работа и участие создающего объекты кода. Оценивать следует распределение затрат и задержек, а не только одну самую короткую паузу.

Ожидающая горутина тоже может удерживать объект

Горутина — выполняемая runtime задача со своим стеком. Канал chan T передаёт значения типа T и согласует отправителя с получателем. У make(chan Message) ёмкость равна нулю: отправке нужен соответствующий приём, заранее сложить Message в буфер нельзя. Такое согласование называют встречей, или rendezvous. Внутренний объект канала при этом существует: он хранит, в частности, очереди ожидающих операций.

В реализации Go горутина обозначается G, системный поток — M. Чтобы исполнять обычный Go-код, M нужен ресурс планировщика P. Ожидание канала переводит G в waiting и позволяет исполнять другую работу. Runnable означает готовность к выбору планировщиком; running — уже исполняемый код. Ни ожидание, ни пробуждение не означают, что стек горутины и нужные ей указатели исчезли.

package main

import "runtime"

type Message struct {
    N int
    P *int
}

func main() {
    ch := make(chan Message)
    gate := make(chan struct{})
    done := make(chan [2]int)
    p := new(int)
    *p = 7
    src := Message{N: 41, P: p}

    go func() {
        m := <-ch
        <-gate
        m.N++
        *m.P = 9
        done <- [2]int{m.N, *m.P}
    }()

    ch <- src
    p = nil
    src.P = nil
    runtime.GC()
    close(gate)
    out := <-done
    println(src.N, out[0], out[1])
}

Gate здесь передаёт пустую структуру и лишь задерживает получателя перед использованием m.P; после закрытия приём из него возвращает нулевое значение struct{} без отдельной отправки. Done возвращает два числа после изменения объекта. Ожидаемые числа при печати — 41, 42, 9. Это новый небольшой пример для рассуждения, а не выполненный компиляторный или нагрузочный опыт. Явная runtime.GC() задаёт диагностическую границу и добавляет работу; так не следует устраивать каждую операцию приложения.

Green Tea в проверенной версии

Green Tea включён по умолчанию в Go 1.27.3 и накапливает обнаруженные объекты по span: marks показывают обнаружение, scans — уже обработанные; очередь span и сравнение этих наборов позволяют обходить несколько соседних объектов вместе. Например, marks={1,3,4}, scans={1} требует обработать 3 и 4, не 1 заново. Соседство может улучшить доступ к данным и метаданным, но выигрыш зависит от графа. Это поясняющий набор номеров, не запись реальных runtime-адресов нашего процесса. Точная организация закреплена исходником Green Tea; allocator — malloc.go, барьер — mbarrier.go.

Какая ссылка потерялась бы без барьера

Пусть сборщик уже просканировал стек S, а объект A ещё ждёт сканирования и содержит единственную ссылку на пока неотмеченный B. Приложение читает B в локальную переменную S и очищает A.slot. Позже сборщик сканирует A: ссылки на B уже нет; стек S повторно не сканируется на этом шаге. B всё ещё нужен приложению, но обход мог бы его потерять. Удаляющая часть барьера обрабатывает старое значение A.slot до затирания и отмечает B.

Обратный порядок требует вставляющей части: ещё не просканированный стек содержит C, приложение записывает C в уже просканированный A, затем теряет старую стековую ссылку до сканирования стека. Отметка нового C до публикации сохраняет достижимость. В поясняющем алгоритме mbarrier.go: shade(old); если стек серый — shade(new); затем запись. Shade — отметить обнаруженный объект и организовать его последующее сканирование. Цвета обозначают состояние обхода, а не байты в объекте. Реальный быстрый путь избегает дорогой проверки цвета объекта и передаёт старый/новый указатели в буфер барьера.

Наш Publish(p) проверяет runtime.writeBarrier; при включённом барьере вызывает gcWriteBarrier2, записывает новый p и прежний Published в буфер через R11, затем меняет Published. При выключенном проходит к обычной записи. Барьер сам по себе не является пользовательским mutex и не устраняет data race. У новых объектов во время маркировки другой протокол начальной отметки; целочисленная запись не создаёт такое же ребро графа указателей. У GC есть стоимость проверки, заполнения/слива буфера и сканирования удержанного графа.

Assist и связь выделений с задержкой

При интенсивном выделении приложение может участвовать в работе сборщика через механизм помощи. Поэтому CPU-стоимость GC не всегда видна только в отдельных фоновых горутинах. Слишком быстрый поток новых данных относительно доступного бюджета требует соответствующего прогресса маркировки. Это один из способов, которым распределение памяти влияет на задержку обработки запроса.

Но один всплеск времени не доказывает assist. Нужен профиль и runtime-метрики с временным контекстом. В нашей маленькой серии не моделировалась производственная конкуренция и не измерялись хвостовые задержки сервиса. Мы установили разницу представления, а причинное объяснение конкретной задержки потребует дополнительных наблюдений.

Цель роста и мягкий предел в байтах

В gcController.commit исходная цель равна L+(L+R)×GOGC/100, где L — отмеченная живая куча предыдущего цикла, R — учтённое сканирование стеков и глобальных данных. При L=8 MiB и R=2 MiB получаем 18 MiB для 100,13 MiB для 50 и 28 MiB для 200. 1 MiB=1048576 байт. Затем действуют минимальная цель, ограничения sweep, pacer и предел памяти; начало цикла обычно раньше цели, чтобы маркировка успела закончиться. Это не расписание «GC ровно при 18 MiB».

Определение учтённой для GOMEMLIMIT runtime-памяти — MemStats.Sys−MemStats.HeapReleased, эквивалентно /memory/classes/total:bytes минус /memory/classes/heap/released:bytes. Включены управляемая куча, стеки и служебные структуры Go; память C, внешние mmap и часть памяти ОС не включены. Предел мягкий: живые данные нельзя безопасно уничтожить ради числа, а runtime ограничивает долю CPU, расходуемую на бесполезно частую GC. При слишком тесном пределе возможны превышение, задержки assist и последующий отказ внешнего жёсткого лимита. GOMEMLIMIT не является пределом RSS.

Собственная cmd/gc удерживает 128 блоков по 64 KiB (8 MiB), делает одну явную GC перед измерением, затем запрашивает 4096 блоков по 16 KiB (64 MiB) с удержанием только последнего. Снимки метрик до/после отделяют уже случившуюся подготовку. В отдельных нативных процессах число новых циклов было 17/8/4 при GOGC50/100/200 и 39 при 100+GOMEMLIMIT16 MiB; CPU assist за измеренную фазу — примерно 0.000396/0.000236/0.000143/0.000771 CPU-секунды. Это один ограниченный опыт на машину, а не p99 приложения. Видимое elapsed отличалось из-за прогрева и планирования; ряд не доказывает, что меньший GOGC всегда быстрее.

Обычный пользователь, cwd compilerlab, вход cmd/gc/main.go. Ожидается 0 и JSON с before/after. При ошибке сборки не запускайте предыдущий файл. Слишком малые GOMEMLIMIT для этого упражнения не выбирайте; 16 MiB оставляет опыт ограниченным, а вся нагрузка задана кодом.

cd "$LABROOT/projects/compilerlab" || exit 1
"$GO" build -o "$LABROOT/out/gc" ./cmd/gc || exit 1
GOGC=50 "$LABROOT/out/gc" || exit 1
GOGC=100 "$LABROOT/out/gc" || exit 1
GOGC=200 "$LABROOT/out/gc" || exit 1
GOGC=100 GOMEMLIMIT=16MiB "$LABROOT/out/gc" || exit 1

Меньше выделений не всегда быстрее

Переиспользование большого буфера может сократить число выделений, но увеличить удерживаемую память и стоимость очистки. Общий пул может добавить синхронизацию. Передача структуры по значению может устранить объект, добавив копирование. Индексная структура без указателей может выиграть в сканировании, но усложнить доступ. Каждый вариант меняет несколько ресурсов.

Для решения фиксируйте полезную работу, объём входа и жизненный цикл. Сравните CPU, B/op, allocs/op, живую память и нужную задержку. Если один показатель улучшился, а другой ухудшился, это не обязательно ошибка: нужно выбрать вариант, подходящий ограничениям продукта. Учебная цель — понимать этот обмен, а не собирать минимальный счётчик.

Удержание большого массива маленьким срезом

Небольшой срез может продолжать ссылаться на большой общий backing array. Число элементов среза не обязательно описывает удерживаемый объём. Если небольшой фрагмент сохраняется надолго, иногда полезно скопировать его в самостоятельное хранение. Это добавляет выделение сейчас, но может освободить значительно больше памяти позже.

Такой случай прямо опровергает универсальную цель «уменьшать allocations всегда». Проверять нужно длительность удержания и размер исходного массива. Для короткого локального использования копирование может быть лишним. Для долгоживущего результата оно способно оказаться выгодным. Разница определяется временем жизни, а не одним синтаксическим правилом про copy.

Как продолжить эксперимент корректно

Сначала добавьте проверку содержимого обеих структур на нескольких размерах. Затем изменяйте только число элементов и наблюдайте зависимость выделений и байтов. После этого можно исследовать длительно сохранённую структуру и повторное создание с удалением старых ссылок. Эти сценарии дают разные живые наборы, даже если исходная функция одна и та же.

Не вызывайте принудительный GC внутри каждого измеряемого действия, если рабочая операция так не устроена. Это изменит задачу и скроет естественный режим. Принудительная сборка может быть полезной границей отдельного диагностического опыта, но её стоимость нужно объявить. Также не смешивайте серию с профилированием памяти и обычную серию без указания режима.

Посмотреть путь барьера в собственном объекте

В projects/ch54/barrier уже есть минимальный barrier.go без импортов. Глобальный указатель может удерживать объект после возврата Publish, поэтому запись в него является удобным примером взаимодействия с графом кучи. Здесь исследуется сгенерированный код, а не частота фактического выполнения медленного пути.

Поставленный исходник: $LABROOT/projects/ch54/barrier. Читайте его как текст файла.

package barrier
var Published *int
func Publish(p *int) { Published = p }

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch54/barrier, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

cd "$LABROOT/projects/ch54/barrier" || exit 1
go tool compile -S -o "$LABROOT/out/barrier.o" barrier.go || exit 1

Найдите проверку режима runtime.writeBarrier и соответствующий путь runtime.gcWriteBarrier. Смысл развилки состоит в том, что дополнительная работа нужна в определённом состоянии сборщика. По наличию обоих путей нельзя заключить, что каждая Publish всегда выполняет весь барьерный обработчик. Это такой же принцип чтения машинного кода, как различение успешного пути индекса и пути panic.

Замените указатель на int и сравните вывод. Данные могут по-прежнему сохраняться глобально, но сборщику не требуется считать числовое поле ссылкой на объект. Затем сравните глобальную запись с локальной переменной, которая не покидает функцию. Эти изменения отделяют тип данных от времени жизни и помогают понять, какие сведения компилятор использует для выбора действия.

Ошибки чтения профиля памяти

Профиль выделений и профиль удерживаемых объектов отвечают на разные вопросы. Горячая функция может создавать много временных данных, которые затем исчезают; долгоживущий кэш может редко выделять, но удерживать большую долю памяти. Перед поиском виновника проверьте выбранный вид профиля и единицу. Название функции наверху одного представления не означает автоматически основной источник устойчивой памяти.

Также учитывайте накопительный характер счётчиков. Если число выделенных байтов выросло, это не означает, что столько же байтов осталось живыми. Для сравнения интервалов нужны разности подходящих счётчиков, а для живого набора — соответствующая граница наблюдения. Сочетание этих данных с известным жизненным циклом запроса даёт причинное объяснение и помогает выбрать исправление без случайной настройки runtime.

Для каждого такого опыта сохраняйте момент наблюдения относительно завершения операции и возможного цикла GC. Без временной границы два корректных числа могут описывать разные состояния и создавать видимость противоречия. Проверка жизненного цикла важнее попытки немедленно подобрать универсальную настройку.
