Инкрементальная сборка и кэш: ускорение без подмены результата

Быстрая сборка полезна, только если она выдаёт результат нужных входов. Проследим, как система решает пропустить действие, из чего складывается ключ кэша и почему высокий процент попаданий иногда скрывает устаревшую программу.

Как Go находит пригодный результат прежней работы

Полная сборка исполняет все необходимые действия заново. Инкрементальная использует сведения о прошлых действиях и повторяет только те, для которых могли измениться результаты. Условие корректности звучит строго: пропущенное действие при выполнении сейчас должно было бы дать допустимый тот же выход. Например, изменение lib.Scale с 3 на 4 меняет константу, которую использует main. Старое имя пакета не позволяет оставить прежний бинарник. А изменение README, который программа не читает и не встраивает, само по себе не обязано менять архив пакета.

Простейшее правило по времени изменения сравнивает даты входов и выхода. Оно быстрое, но предполагает корректные часы и сохранность дат. Копирование с сохранением времени, грубая точность файловой системы или изменение содержимого с восстановлением старой даты нарушают предположение. Сравнение содержимого через хеш устойчивее к таким случаям, однако требует прочитать данные и всё равно не обнаруживает вход, о котором вообще не знает правило. Самая дорогая ошибка здесь — неполная модель зависимостей, а не слабый выбор хеш-функции.

У Go несколько разных предметов кэширования

GOCACHE задаёт кэш результатов сборочных действий и связанных данных тестирования. GOMODCACHE хранит полученные версии модулей и описания. Первый помогает не повторять компиляцию подходящего пакета, второй — не скачивать уже имеющиеся исходники. Прогретый модульный кэш при пустом build-кэше всё ещё требует компиляции. Прогретый build-кэш не делает доступной неизвестную версию модуля, которую понадобилось разрешить после изменения go.mod.

В первом холодном запуске стандартная библиотека тоже может требовать подготовки подходящих кэшируемых данных. Сравнивать такой запуск с повтором без указания состояния бессмысленно: «программа стала собираться за секунду» может означать только устранение первоначальной работы. Сам бинарник выпуска не должен существовать исключительно в GOCACHE: этот каталог обслуживается и очищается как ускоритель. Доставляемый dist/handbook-service сохраняют отдельно с манифестом.

Ключ описывает действие, а не удобное название ветки

Следующий Python-фрагмент — схема ключа собственного упаковщика ZIP из главы 16. Он не исполняет сборку Go и не вычисляет её action ID. Для его отдельного исполнения выполните cd "$LAB/fixtures/zip", сохраните код как key-model.py и запустите python3 key-model.py. Он читает два существующих входа и выводит хеш описания, не сохраняя результат сборки. Реальные идентификаторы Go получим в следующем опыте из его архивов.

Представим действие упаковки. Его ключ может быть хешем канонического описания: версия схемы ключа, хеш сценария упаковки, отсортированные имена и хеши входных файлов, параметры формата, идентичность существенных инструментов. «Каноническое» означает единственный способ сериализовать одни и те же данные: фиксированные кодировка, порядок полей и разделители. Простое склеивание строк без границ опасно: пары (ab, c) и (a, bc) дают одинаковое abc, хотя входы разные.

import hashlib
import json
from pathlib import Path

description = {
    "schema": 1,
    "action": "zip-stored-v1",
    "tool": "our-builder-v1",
    "inputs": [[name, hashlib.sha256(Path(name).read_bytes()).hexdigest()]
               for name in sorted(("app.py", "README.txt"))],
    "options": {"mode": "0644", "date": "2000-01-01"},
}
encoded = json.dumps(description, sort_keys=True,
                     separators=(",", ":"), ensure_ascii=True).encode("ascii")
key = hashlib.sha256(encoded).hexdigest()
print(key)

Это схема построения ключа собственного упаковщика: хеши получены из фактических байтов двух файлов. sort_keys=True упорядочивает ключи объектов JSON; для списков порядок нужно определить отдельно. separators убирает необязательные пробелы, ensure_ascii=True делает представление строк независимым от прямой записи не-ASCII символов. Полученный хеш обозначает выбранное описание. Он ничего не сообщает о полноте самого описания и о том, кто записал файл в хранилище.

Название ветки main не подходит в качестве единственного ключа: оно меняет значение при новых коммитах. Полный идентификатор коммита тоже не всегда достаточен: незакоммиченный вход, внешняя зависимость или отличающийся инструмент могут изменить результат. С другой стороны, включение в ключ всех файлов репозитория создаёт лишние промахи: исправление документации пересобирает несвязанный модуль. Правильная граница определяется действительными зависимостями действия.

Что входит в вычисление Go

При выборе результата пакета значимы выбранные исходники, инструмент, параметры, целевая платформа и подходящие результаты импортов. Изменение GOOS или -race создаёт другую задачу. Тестовые исходники влияют на тестовый бинарник, но не должны автоматически означать, что обычный пакет с неизменившимися GoFiles получил новые программные байты. Команда go строит более точные ключи действий, чем архив всего каталога по имени ветки.

Собственная внешняя обвязка может добавить ещё один слой. Например, Jenkins сохраняет весь GOCACHE как ускоряющий объект. Ключ такой передачи должен учитывать совместимость платформ и toolchain, но окончательную допустимость каждой записи по входам всё равно оценивает Go. Если вместо штатного кэша сохраняется готовый dist по одному имени main, новые флаги Version легко приведут к выдаче старого продукта. Не нужно приписывать встроенному Go те ошибки, которые внесла внешняя схема восстановления каталога.

С CGO есть конкретная граница: изменения внешних C-библиотек не всегда обнаруживаются штатным build-кэшем как ожидаемое изменение входа. Официальная справка рекомендует в таком случае принудительное перестроение или явную очистку. Это не основание регулярно очищать всё у pure-Go проекта. Сначала выясняют, какие данные изменились вне модели и какой результат мог стать неподходящим.

Пакет, архив и action ID на одном локальном входе

В личном $LAB/fixtures/cacheaction есть main.go и lib/lib.go. Main печатает lib.Value(), а lib возвращает const Scale = 3. Модуль использует только эти файлы и стандартный runtime. Откройте Bash с env.sh; все следующие выходы принадлежат этому пользователю. -x пишет журнал запуска инструментов в stderr; 2> направляет этот поток в названный файл, а обычный вывод JSON перенаправляется через >.

cd "$LAB/fixtures/cacheaction"
go list -json ./lib > "$LAB/out/lib-input.json"
go build -x -work -o app . 2> "$LAB/out/cache-first.log"
archive="$(go list -export -f '{{.Export}}' ./lib)"
go tool buildid "$archive"
go build -x -o app . 2> "$LAB/out/cache-warm.log"
./app

Программа должна напечатать 3. В JSON поля Dir, ImportPath, GoFiles и Imports показывают каталог, имя пакета, выбранный lib.go и его импорты, если они есть. У lib без импортов поле Imports может отсутствовать. ImportMap появляется при переотображении импортных путей; отсутствие поля в этом простом пакете не означает неизвестные зависимости. go list -export готовит архив и печатает его Export. go tool buildid этого архива выдаёт две части через /: action ID описывает действие, content ID — идентичность результата для зависимых действий. Это не буквальные полные SHA-256 имена записей внутреннего кэша и не хеш всей директории.

При неизменённых входах тёплый журнал не должен содержать нового запуска compile/link: прежний app уже пригоден. Не определяйте это только по короткому времени команды. Теперь получите архив с другим флагом, не меняя исходник: go list -export -gcflags=example.invalid/cacheaction/lib=-l -f '{{.Export}}' ./lib; передайте его напечатанный путь go tool buildid. Отключение встраивания — другой вход compile и другой action ID. Вернитесь к обычным флагам, затем редактором измените только Scale=3 на Scale=4 и повторите блок в новые журналы. Ожидаются другой build ID архива, повторные нужные compile/link и число 4. Верните 3 и пересоберите: доступны прежние результаты для прежних входов.

Потребителю main важны сведения и результат импорта lib; при подстановке экспортируемой константы меняется его код. Не всякое изменение зависимого пакета требует пересоздать каждый несвязанный пакет стандартной библиотеки. В проверке Go 1.27.3 изменение Scale действительно изменило обе части build ID lib; другой флаг также изменил их. Конкретные строки ID зависят от расположения и инструмента, поэтому сравнивайте сохранённые строки своего запуска. Ошибка go list или build означает остановку опыта: пустой archive либо старый app не заменяет успешное получение нового результата.

Попадание в кэш — процедура проверки

У штатного дискового кэша Go 1.27.3 несколько операций чтения. DiskCache.Get по action ID открывает небольшую запись, проверяет её длину, заголовок, записанный идентификатор, формат output ID, неотрицательный размер и время. Успешный Get сам по себе ещё не гарантирует наличие файла результата. GetFile дополнительно ищет файл по output ID и проверяет его размер; он не пересчитывает SHA-256 всего архива при каждом таком чтении. GetBytes для небольшого содержимого читает байты и сравнивает SHA-256 с output ID, а GetMmap проверяет длину отображённого содержимого. Поэтому нельзя приписывать любому попаданию обязательное полное хеширование каждого выхода.

Отсутствующая или неполная запись даёт промах соответствующего чтения. Специальный GODEBUG=gocacheverify=1 заставляет Get отказаться от обычного попадания; при записи заново вычисленного результата Go проверяет его совпадение с прежним. Это отдельный диагностический режим, существенно дороже штатного поиска. Для внешнего хранилища автор отдельно определяет проверки целостности и права записи: один факт найденного имени не делает вход доверенным. Конкретные операции выше проверяются в cache.go выпуска 1.27.3.

Для публикации записи полезно сначала писать во временный объект и делать её видимой после полной записи. Иначе второй агент способен прочитать половину архива. Одновременная сборка одинакового ключа обычно допустима, если оба результата обязаны совпадать; несовпадение — сигнал недетерминированности или неверного ключа. Пытаться «победить гонку» выбором последнего записавшего агента означает скрыть важную неисправность.

В распределённом кэше важны границы доверия. Сборка непроверенной внешней ветки не должна иметь право заменить результаты, которые затем использует выпуск. Раздельные пространства имён, ограничение записи и проверка происхождения уменьшают риск. Файлы из кэша остаются исполняемыми входами следующего действия: название «ускоритель» не делает их безвредными. В то же время пропавший кэш обязан ухудшать скорость, а не лишать возможности собрать продукт.

Кэш успешного теста отличается от кэша его компиляции

В режиме списка пакетов, например go test ./..., Go умеет повторно использовать успешный результат тестирования при выполнении условий кэширования. В выводе появляется (cached). Это означает, что тестовые функции для этого пакета в данном вызове не обязаны были исполняться заново. Кэшируются подходящие успешные исходы, а не универсальная истина «у программы нет ошибки».

Команда учитывает тестовый бинарник, допустимые флаги и наблюдаемые ею зависимости выполнения, включая некоторые чтения файлов и окружения. Однако внешняя база, сетевой ответ и произвольное состояние сервиса не превращаются автоматически в достоверно описанный снимок. Если тест предназначен проверить текущее внешнее состояние, повторно использованный прежний успех может не отвечать его задаче. Такой тест должен иметь отдельный договор и запуск без кэша результатов.

Откройте env.sh главы 14, затем cd "$LAB/service". Этот модуль не использует сеть. Тесты вызывают HTTP-обработчик через httptest.ResponseRecorder в памяти и не открывают порт. При первом успешном go test ./... результат подходящего пакета можно сохранить; второй неизменённый запуск должен показать (cached). В строке пакета время в секундах относится к тесту, а не ко всей стеновой длительности команды со сборкой.

go test ./...
go test ./...
go test -count=1 ./...
go clean -testcache
go test ./...

Второй подходящий вызов может показать cached. -count=1 явно отключает повторное использование результата, заставляя выполнить тесты один раз; он не требует заново компилировать всю стандартную библиотеку. clean -testcache аннулирует сохранённые результаты тестов, сохраняя смысл отдельного build-кэша. Обычный go test без списка пакетов работает в локальном режиме с другими условиями кэширования: при сравнении экспериментов форму вызова фиксируют.

Четыре разных тёплых состояния

Для обычного Go различайте полученные архивы модулей в GOMODCACHE, результаты компиляции в GOCACHE, сохранённый успешный результат теста и файловый кэш ОС, ускоряющий чтение тех же данных из памяти. Временный $WORK/bNNN/ из -work полезен для исследования запуска, но его сохранение не является обычным механизмом инкрементальной сборки следующей команды. Следующий go build ищет пригодные действия в GOCACHE; он не обязан обходить оставленный каталог WORK в поиске объектников.

При измерении явно задайте опыт: новый рабочий каталог и пустой кэш действий; новый каталог и доступный удалённый кэш; повтор в том же каталоге; изменение одного значимого файла. Последний опыт особенно важен: система должна пересчитать затронутый выход и оставить подходящие независимые результаты. Полностью неизменный повтор проверяет только самый лёгкий случай и почти ничего не говорит о корректности инвалидирования.

Матрица для повторяемого измерения

Полезны как минимум четыре подписи опыта: модули отсутствуют и build-кэш пуст; модули есть, build-кэш пуст; сборочные результаты есть, тесты запускаются с -count=1; сборочные результаты и допустимый тестовый успех повторно используются. Добавьте ещё тёплый page cache операционной системы: повторное чтение архива из RAM не равно первому чтению диска. Во всех случаях исходники и флаги могут быть одинаковыми, а длительность — совершенно разной.

Наш автономный go-service не имеет внешних модулей, поэтому первый слой проще: отсутствие GOMODCACHE не создаёт сетевой загрузки. Но компиляция стандартных и собственных пакетов всё ещё даёт холодную работу. Стороннее приложение с большим графом модулей имеет другое распределение затрат. Переносить отношение времён маленькой службы на большой сервис нельзя; переносится метод выделения слоёв.

Цена попадания и цена промаха

Пусть действие занимает 40 секунд. Подготовка ключа занимает 1 секунду; получение готового выхода — ещё 3; при промахе после вычисления ключа надо выполнить действие и потратить 2 секунды на запись. При доле попаданий h = 0,7 ожидаемое время равно 1 + 0,7 × 3 + 0,3 × (40 + 2) = 15,7 секунды. Это модель последовательного действия без перекрытия передачи с вычислением. Экономия относительно 40 секунд равна 24,3 секунды на действие, но сервер, хранение и сеть тоже имеют стоимость.

У действия длиной 0,2 секунды те же расходы делают кэш бессмысленным. У большого выходного файла передача способна быть дороже вычисления. Поэтому оценивают не только долю попаданий, но и сохранённое время на критическом пути, байты передачи, объём хранения и нагрузку на хранилище. Высокая доля попаданий в дешёвые действия может соседствовать с медленной сборкой, если единственный дорогой последовательный узел всегда пересчитывается.

Очистка имеет конкретный предмет

Следующий блок относится только к личным путям из env.sh. Сначала прочитайте их в выводе go env; если там общий кэш другого проекта, вернитесь к настройке стенда до очистки. clean -testcache заставляет заново выполнить тесты; clean -cache удаляет сохранённые результаты сборки и увеличит следующую работу, включая стандартную библиотеку. Исходники и go.mod эти две команды не чинят.

go env GOCACHE GOMODCACHE
go clean -testcache
go clean -cache
go mod verify

clean -cache очищает выбранный build-кэш, -testcache касается результатов тестов. clean -modcache удаляет загруженный модульный кэш и на следующей сборке может потребовать получения данных; на машине без интернета это меняет доступность входов. Поэтому для эксперимента назначают новые временные GOCACHE/GOMODCACHE, а не уничтожают пользовательские данные ради общего рецепта. Свойства одного слоя нельзя проверить очисткой другого.

Накладные расходы попадания включают вычисление ключей, чтение служебных данных, восстановление файлов и иногда распаковку внешнего сохранённого кэша. Пусть действие стоит 20 секунд, получение подходящего результата — 2 секунды, а общий поиск и упаковка кэша съедает 8 секунд. При доле пригодных попаданий 50 процентов грубая оценка уже равна 8 + 0,5×2 + 0,5×20 = 19 секундам до прочих расходов. Большой процент попаданий в журнале сам по себе не доказывает полезного ускорения конвейера.

Как обнаружить неверную экономию

Периодически сравнивайте результат обычной сборки с независимой полной сборкой выбранного снимка. Включайте изменения шаблонов, флагов, зависимостей и инструментов в проверки модели ключей. Полезен отрицательный опыт: специально поменять значимый вход и убедиться, что затронутый результат пересчитан. Другой опыт — удалить ускоряющее хранилище и подтвердить получение такого же артефакта. Это проверка причинной связи, а не дополнительный прогон ради числа тестов.

Кэш и доставляемый артефакт имеют разный жизненный цикл. Кэш можно вытеснять по давности, размеру и цене восстановления. Выпущенный файл сохраняют по требованиям доставки и восстановления; пересборка старой версии спустя год может быть нежелательна даже при хорошей воспроизводимости. Когда выпуск ссылается только на временный объект кэша, очистка ускорителя неожиданно превращается в потерю продукта. В главе о проверках разделим эти два вида хранения на уровне конвейера.

Диагностика решения Go

GODEBUG=gocachetest=1 go test ./...
GODEBUG=gocachehash=1 go build ./cmd/handbook-service
GODEBUG=gocacheverify=1 go build ./cmd/handbook-service

gocachetest печатает причины решений о повторном использовании тестового исхода. gocachehash раскрывает входы вычисления ключей и может создать большой журнал. gocacheverify заставляет пересчитать результаты с проверкой против существующих записей вместо обычного доверия попаданию. Это специальные диагностические режимы: их длительности не сравнивают со штатным прогретым build как будто условия одинаковы.

Проведите отрицательный опыт: измените строку Version через -ldflags и убедитесь, что новый артефакт печатает новое значение. Измените _test.go и посмотрите, какие действия повторились. Верните изменение и проверьте допустимое повторное использование прежних результатов. Потом сравните сборку с отдельным пустым GOCACHE. Если все случаи дают один старый бинарник, сначала исследуйте, действительно ли запускали нужную команду и читали новый выходной путь, а не объявляйте кэш Go сломанным по одному имени файла.

GOCACHEPROG позволяет подключить внешнюю программу кэша по специальному протоколу. Это отдельный участник и дополнительная граница доверия; она не возникает только от архивирования каталога Jenkins. В данном томе этот протокол не реализуется. Мы используем штатные локальные кэши с изолированными путями и реальные проверки результата, не выдавая синтетическую иллюстрацию про язык сообщения за буквальный формат action ID Go.

Что нельзя заключить из надписи cached

Допустимое попадание сообщает, что выбранный механизм повторно использовал результат по своим правилам. Оно не говорит, сколько времени сэкономлено: поиск мог быть дорогим, а первоначальное действие — дешёвым. Оно не гарантирует, что пакет всё ещё нужен именно этой команде, если вы читаете журнал другого запуска. И оно не доказывает отсутствие побочных входов собственного теста. Для сравнения нужны идентичность команды, ревизия, окружение и конкретный предмет результата.

Наблюдение помогает разделить две ошибки. Если Go корректно пересобрал пакет, но упаковщик взял старый dist, проблема после сборки. Если внешний кэш восстановил отчёт прошлого запуска под маской reports/*.xml, проблема в свидетельстве тестирования. Если текущий тест обращается к изменившейся внешней базе, прежний успешный результат может быть неприменим к этой задаче. Все три ситуации выглядят как «кэш дал старое», но исправляются на разных границах. Добавление ещё одного случайного номера в каждый ключ лишь выключит повторное использование, не объяснив устройство сбоя.

Для дополнительной схемы с LANGUAGE исходник генератора и все поля ключей доступны в $LAB/fixtures/greeting-model.py. Из любого каталога стенда выполните python3 "$LAB/fixtures/greeting-model.py": он ничего не меняет, а печатает полные хеши, 13 байт русского ответа и 6 байт английского. В схеме 1 оба языка имеют один ключ, в схеме 2 — разные. Это собственный Python-генератор с намеренно неполным ключом, отдельно от реальных Go action/content ID выше.

Использованный вход и просто существующая переменная

У тестового кэша есть механизм наблюдения некоторых чтений файлов и окружения. Это точнее ключа «все переменные машины», но не равно регистрации любого события внешнего мира. Собственный тест, читающий os.Getenv, позволяет исследовать, как изменение использованного значения влияет на решение; переменная, которую тест вообще не читал, имеет другой смысл. Журнал gocachetest помогает проверить эту гипотезу, вместо полного удаления кэшей после каждого запуска.

Если тест проверяет состояние удалённой очереди, содержимое этой очереди не превращается в отслеженный файл только потому, что адрес взят из переменной. Ключу может быть известен адрес, но не текущее удалённое состояние. Для проверки живой среды выбирают другой договор запуска, например -count=1, и сохраняют фактическое наблюдение. Точный инструмент не избавляет автора теста от выбора предмета проверки.

Go: go help cache, clean, test и переменные окружения, параметры GODEBUG. Перечень и смысл диагностических режимов дополнительно проверены через локальную справку Go 1.27.3. Иллюстрация с неполным ключом в этой главе описывает общий инвариант, а не внутреннюю ошибку штатного Go.

Первичные источники и модель

Bazel: удалённый кэш действий и выходов; Python: параметры сериализации JSON; Python: вычисление хешей. Формулы стоимости, пример ключа и диагностические опыты — самостоятельная учебная модель; конкретный сборщик может использовать иной протокол и другие правила допустимости кэша.
