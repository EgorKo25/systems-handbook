57. Оптимизация как расследование: код, доказательства и серии измерений

Соединим инструменты книги в один маршрут: сформулировать задачу, проверить результат, прочитать решения компилятора, увидеть машинный путь и измерить его стоимость. Три случая — форма цикла, время жизни объекта и представление данных — покажут, как получить полезный вывод без универсальных обещаний по одному benchmark.

Начать с наблюдаемой проблемы

Слова «код медленный» не определяют, что исправлять. Нужны операция, размер входа, допустимый результат и ресурсное ограничение. Для службы это может быть задержка конкретного запроса или CPU на единицу работы, для сборочной системы — длительность compile, для контейнера — пиковая память. Изменение без такой цели легко улучшает красивое, но несущественное число.

Первый вопрос — сколько выбранный участок добавляет к измеряемой операции. CPU-профиль показывает распределение процессорной работы, а время ожидания сети устанавливают отдельным наблюдением. Пусть последовательная обработка запроса занимает 10 мс: 8 мс ожидания и 2 мс вычисления. Если вычисление ускорить вдвое, новое время будет 8 + 1 = 9 мс: экономия 1 мс, или 10%, а ускорение всей операции — 10/9 ≈ 1,11 раза. Это условный расчёт при неизменных ожидании и объёме работы. Долю CPU-профиля нельзя без проверки подставить вместо доли полной задержки, особенно при перекрытии операций и очередях.

Полный первый случай: две формы суммирования

Модуль example.invalid/cases и cases_test.go уже поставлены в projects/ch57. Подготовка данных находится до измеряемого цикла, результат сохраняется числом. Оба алгоритма должны выполнить одинаковое суммирование, а отдельный тест подтверждает простейшую функциональную договорённость.

Поставленный исходник: $LABROOT/projects/ch57. Читайте его как текст файла.

package cases
import "testing"
var Sink int
func SumIndex(xs []int) int {
    n := 0
    for i := 0; i < len(xs); i++ { n += xs[i] }
    return n
}
func SumRange(xs []int) int {
    n := 0
    for _, x := range xs { n += x }
    return n
}
func BenchmarkIndex(b *testing.B) {
    xs := make([]int, 1024)
    for i := range xs { xs[i] = i }
    for b.Loop() { Sink = SumIndex(xs) }
}
func BenchmarkRange(b *testing.B) {
    xs := make([]int, 1024)
    for i := range xs { xs[i] = i }
    for b.Loop() { Sink = SumRange(xs) }
}
func TestAgreement(t *testing.T) {
    xs := []int{1, -2, 3, 4}
    if SumIndex(xs) != 6 || SumRange(xs) != 6 { t.Fatal("wrong sum") }
}

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch57, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

cd "$LABROOT/projects/ch57" || exit 1
GOENV=off GOTOOLCHAIN=local GOMAXPROCS=2 \
go test -run=TestAgreement -bench=. -benchmem -benchtime=50ms -count=3

Переменные ограничивают персональные настройки, автоматический выбор другого toolchain и параллелизм runtime. Они действуют на этот запуск Bash. -run выбирает функциональный контроль, -bench запускает измерения, -benchmem добавляет выделения, -benchtime задаёт короткое окно, -count повторяет его. Никакие личные настройки go env -w не меняются.

Что действительно показала серия

Оба варианта прошли тест и показали 0 B/op и 0 allocs/op. В одном сохранённом запуске Index находился примерно в диапазоне 294.3–303.1 ns/op, Range — 239.6–270.7 ns/op. Это три коротких измерения на конкретном Linux amd64 компьютере и Go 1.27.3. Они показывают наблюдаемое различие данного образца, но недостаточны для правила «range всегда быстрее индекса».

Для устойчивого решения нужны более длинные серии, размеры входов и проверка машинного результата. Отдельно учитывайте, что b.Loop является частью инструментария выбранной версии и организует измеряемую область. Если другая версия не поддерживает этот API, её альтернативный benchmark нужно описать отдельно, не сравнивая молча разные рецепты.

Сначала проверить договор алгоритма

Добавьте пустой срез, один элемент, отрицательные значения и размер, близкий реальной задаче. Для целых чисел учитывайте допустимый диапазон и переполнение. Для плавающих значений перестановка порядка суммирования может менять округление. Две функции, совпавшие на четырёх маленьких числах, ещё не доказаны эквивалентными для произвольного предметного договора.

Если оптимизация меняет порядок доступа или конкурентное использование данных, требуется дополнительная проверка. Benchmark не является доказательством отсутствия гонки и не заменяет тест ошибки. Только после установления допустимого поведения имеет смысл выбирать более дешёвую реализацию. Иначе измеряется скорость неправильного ответа.

Диагностика и ассемблер для первого случая

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch57, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

cd "$LABROOT/projects/ch57" || exit 1
go test -c -gcflags='-l -m=2' -o cases.test || exit 1
go tool objdump -s 'example.invalid/cases.Sum(Index|Range)$' cases.test || exit 1

-c создаёт тестовый executable без его обычного запуска. -l удерживает отдельные функции для чтения, -m=2 печатает сведения оптимизации и размещения. Такой диагностический результат отличается от исходной измерительной сборки, где встраивание не запрещалось. Поэтому его используют для объяснения отдельных тел, а окончательное измерение повторяют с обычными параметрами.

В обоих безопасных циклах необходимо проверить отсутствие дополнительного пути panic для каждого элемента. Ранее в отдельной Sum уже наблюдалось использование условия цикла как доказательства границы. Затем сравните число накопителей, обновление счётчика и обращения к памяти. Одного отсутствия panic недостаточно для вывода, что два тела полностью совпадают или имеют одинаковую стоимость.

Независимый ответ и серия по размеру входа

В compilerlab обе Sum-функции намеренно noinline: сравниваем самостоятельные тела, сохраняем возвращённое число в Result. Входы имеют длины 0,1,16,1024,65536; элемент i равен i%17−8. Полный цикл из 17 чисел даёт 0. Для остатка r=n%17 независимый ожидаемый ответ равен r(r−1)/2−8r. TestValues проверяет каждую длину этой формулой, а не вызовом второй функции с таким же возможным дефектом.

Обычный пользователь, cwd compilerlab. После успешных тестов сохраняются две серии по 5 повторений ×50ms, с обычными флагами и с -l только у собственного пакета. Оба варианта сохраняют noinline функции, поэтому -l здесь не должен быть объяснён исчезновением noinline-директивы. При расхождении результата не переходите к сравнению времени.

cd "$LABROOT/projects/compilerlab" || exit 1
"$GO" test -run='^TestValues$' -count=1 ./lab || exit 1
"$GO" test -run='^$' -bench='^BenchmarkSum/' -benchmem -benchtime=50ms -count=5 ./lab \
  >"$LABROOT/reports/sum-normal.txt" || exit 1
"$GO" test -run='^$' -bench='^BenchmarkSum/' -benchmem -benchtime=50ms -count=5 \
  '-gcflags=example.org/compilerlab/lab=-l' ./lab >"$LABROOT/reports/sum-noinline.txt" || exit 1
python3 "$VOLUME/labs/compiler-runtime/observe.py" stats "$LABROOT/reports/sum-normal.txt" || exit 1

В каждом образце записаны фактические N и ns/op. При n=65536 исходный массив занимает 524288 байт на цели с int размером 8 байт; это размер полезных элементов, не измеренный размер аппаратного кэша. Обе функции не создают новых объектов в цикле:0 B/op и 0 allocs/op согласуются с кодом. Малый n сильнее проявляет стоимость вызова/обвязки; большой — работу чтения и сложения. Даже при одинаковых телах время может различаться из-за выравнивания, порядка, планирования и измерительной обвязки.

Ранний пример Index/Range без noinline в этой главе исследует другую ситуацию, где встраивание допускается. Его три короткие выборки показывают только факт тех запусков. Они не устанавливают правило, что range быстрее индекса. Для нового решения полезно чередовать серии AB и BA, сохранять исходники/флаги и проверять машинный код обоих мест вызова. PGO, race, профили и -N нельзя незаметно добавлять только одному варианту. Если выделения неожиданно появились, сначала проследите новое удержание результата/замыкания и изменившееся время жизни.

Второй случай: объект, который не обязан переживать вызов

Возьмём Local и Keep из главы о средней части. Первая создаёт int через new, возвращает число и не сохраняет адрес. Вторая возвращает адрес, который затем удерживается. Диагностика показывала возможность встраивания Local, фактическое раскрытие и разные решения времени жизни. Эта причинная цепочка объясняет, почему одинаковое слово new не задаёт одинаковый ресурсный путь.

Поясняющий фрагмент/схема; частичное дополнение не является отдельным готовым файлом.

func Local(n int) int {
    p := new(int)
    *p = n
    return *p
}
//go:noinline
func Keep(n int) *int {
    p := new(int)
    *p = n
    return p
}

Для функционально честного сравнения нужно определить, требуется ли вызывающему указатель или только значение. Если нужен долгоживущий разделяемый объект, Local не является заменой. Если нужно число, изменение API может устранить ненужное требование времени жизни. Хорошая оптимизация начинается с договора, а компилятор помогает реализовать разрешённую более простую задачу.

Как проверить машинную гипотезу второго случая

Соберите минимальную программу с наблюдаемыми результатами и изучите -m=2. Затем найдите, остались ли соответствующие вызовы распределения в нужном теле. Если функция встроена, ищите её работу в вызывающем коде. Нельзя объявить выделение устранённым только потому, что отдельный символ исчез: его реализация могла переместиться.

После этого измерьте выбранную реальную операцию через allocations и длительность. В данной серии для Local/Keep выполнена диагностическая проверка, но отдельное численное benchmark-преимущество не публикуется. Это честная граница: механизм наблюдался, универсальная экономия ещё не измерена. Такой отчёт полезнее выдуманного процента ускорения.

Третий случай: множество указателей или плотные данные

PointerBatch и ValueBatch создавали 128 чисел разными представлениями. Выполненная проверка дала 129 выделений против одного, а повторённые benchmark сохранили различие. Здесь причина видна в структуре: самостоятельные адресуемые значения и массив указателей требуют другой организации, чем общее хранение int. Изменение представления затрагивает также локальность и работу GC.

Но указатели могут быть частью необходимой семантики: nil, совместное изменение и идентичность объектов. Если они требуются, простая замена на значения нарушит договор. Иногда подходящим вариантом становятся индексы или отдельная таблица владения, но это уже самостоятельное проектирование. Его проверяют функционально и по жизненному циклу, а не только повторяют удачное число allocs/op.

Единицы benchmark

ns/op относится к одному определённому действию benchmark. Для Sum это обход 1024 элементов, для PointerBatch — создание 128 объектов и внешней структуры. Сравнивать их числа напрямую бессмысленно. Можно дополнительно вычислить время на элемент или пропускную способность, но нужно сохранить исходный размер и постоянную стоимость операции.

Выделенные байты на операцию не равны живому объёму после завершения. Нулевые выделения не означают отсутствия доступа к памяти, а меньшие выделения не гарантируют меньшей длительности. В отчёте полезно держать эти оси рядом, чтобы читатель видел обмен ресурсами. Одно красивое число не должно скрывать ухудшение другой важной характеристики.

Разделение подготовки и измеряемой работы

Создание входного среза расположено до b.Loop, потому что здесь измеряется суммирование уже существующих данных. Если производственная операция обязана создавать данные каждый раз, её полный benchmark должен включать и подготовку. Оба режима могут быть полезны, но отвечают на разные вопросы. Ошибка возникает, когда один режим выдают за другой.

Также не следует помещать печать, запись файла и случайную генерацию в горячую область, если они не являются частью задачи. Иначе результат будет преимущественно измерять эти действия. Но если реальная цель — сериализация и вывод, исключать их ради красивой арифметики тоже неправильно. Граница должна следовать определению операции.

Шум и серия

Фоновая нагрузка, частота процессора, температурный режим, планирование и кэши меняют короткие результаты. Несколько повторов помогают увидеть разброс, но не устраняют автоматически все систематические смещения. Полезно чередовать порядок вариантов, сохранять исходные строки и не выбрасывать неудобные наблюдения без установленной причины.

Если различие мало относительно разброса, вывод должен оставаться неопределённым. Более длинное измерение и повторная независимая серия могут прояснить ситуацию. Но увеличение длительности нерепрезентативного входа не делает его реальной нагрузкой. Сначала проверяют смысл эксперимента, затем повышают статистическую устойчивость.

Профилирование после локального улучшения

После устранения одной затраты ведущим становится другой участок. Повторный профиль показывает, действительно ли общая задача улучшилась и куда переместилась стоимость. Если локальный benchmark выиграл, а запрос не изменился, возможно, выбранный участок занимал слишком малую долю либо добавился иной ресурсный обмен. Это не повод скрывать итог.

Профиль CPU не объясняет всю задержку ожидания. Память, блокировки и внешние операции требуют соответствующих наблюдений. Цепочка расследования должна завершаться метрикой исходной задачи, а не только успехом самого удобного инструмента. Иначе получается оптимизация отчёта вместо программы.

Изменение компилятора как независимый фактор

Новый Go может иначе встроить функцию, расположить цикл или удалить проверку. Поэтому сохраняйте версию и команды рядом с исходником benchmark. Сравнение версий выполняйте при одинаковом доступном окружении и входах. Если меняется API тестирования или целевая архитектура, это нужно объявить как дополнительное отличие.

Изменение текста диагностики не обязательно означает ухудшение. Проверьте реальный результат и машинный путь. И наоборот, исчезновение предупреждения не гарантирует улучшения общей задачи. Смысл книги в причинном маршруте, который можно повторить после обновления, а не в заучивании одной фразы текущего compile.

Цена сложности

Ручная оптимизация может усложнить поддержку, добавить условия и затруднить проверку. Даже измеренный небольшой выигрыш не всегда стоит такого обмена. Оцените частоту операции, масштаб экономии и риск ошибки. Для редко выполняемой административной утилиты понятный код иногда полезнее сложной микрооптимизации, а для горячего внутреннего цикла требования могут быть другими.

Сохраняйте простой вариант как контроль и тесты свойств результата. Это облегчает повторную оценку после смены Go или нагрузки. Если компилятор позже научился делать то же автоматически, ручной обходной путь можно удалить на основании нового сравнения. Оптимизация не обязана становиться вечным наследием проекта.

Самое полезное противоречие этой серии

В отдельной диагностической сборке с отключённым встраиванием тела SumIndex и SumRange имели одинаковую последовательность машинных байтов. Отличались их адреса и подписи исходных строк, но арифметика, загрузка элемента, обновление счётчика и переход совпадали. Оба не имели отдельного пути panic. Это реальное наблюдение заставляет осторожнее читать различие коротких benchmark, а не объявлять один исходный синтаксис принципиально более дешёвым.

Однако диагностическая сборка использовала -l, а первоначальная измерительная — обычные оптимизации. Следовательно, сравнение отдельных тел не доказывает тождество всех измеряемых оболочек. Следующий осмысленный шаг — сопоставить фактические BenchmarkIndex и BenchmarkRange в исходной измерительной сборке либо повторить согласованную серию с тем же запретом встраивания. Только после этого можно разбирать расположение, форму встроенного цикла и системный шум.

Такой результат является успехом исследования: обнаружена граница слишком простого объяснения. Нельзя одновременно использовать удобный диагностический режим как точную копию обычного исполнения и забывать, что он изменяет код. Запишите оба набора параметров и не подменяйте недостающий опыт уверенным рассказом о преимуществах range. Подтверждённые факты здесь — корректность, нулевые выделения, короткая серия и совпадение отдельных тел при объявленном режиме.

Критерий завершённого опыта

Хороший результат содержит исходную проблему, входы, проверенный смысл, минимальное изменение, наблюдение компилятора, машинное объяснение и серию измерений. Отдельно указывается, какой вывод остаётся за пределами данных. Это позволяет другому человеку повторить проверку и отделить устойчивый механизм от случайного расположения или фона.

В этой серии реально проверены оба суммирования, повторённые измерения и отсутствие выделений; в соседних опытах — диагностика Local/Keep и представления PointerBatch/ValueBatch. Производственная нагрузка, длительные хвостовые задержки и другие архитектуры не тестировались. Примеры составляют инструментарий для собственного обоснованного решения, а не таблицу обязательных победителей.

Первоисточники Go 1.27.3: измерительный API, машинные преобразования, решения времени жизни, профили, официальная карта диагностики.
