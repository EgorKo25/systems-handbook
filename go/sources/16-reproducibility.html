Воспроизводимая сборка: одинаковые исходники, одинаковые байты

Два приложения могут вести себя одинаково и при этом иметь разные контрольные суммы. Научимся различать полезную повторяемость, функциональную эквивалентность и побайтовую воспроизводимость; затем получим одинаковый Go-бинарник в разных каталогах. Отдельный опыт с ZIP позволит разобрать метаданные контейнера.

Что именно мы обещаем повторить

Повторяемая команда — ещё не воспроизводимый результат. «Два раза выполнили без ошибки», «два раза прошли тесты» и «два раза получили один SHA-256» отвечают на разные вопросы. Тесты наблюдают выбранные свойства поведения. Побайтовое сравнение устанавливает равенство конкретных выходных файлов. Утверждение о воспроизводимой сборке всегда содержит область: какие входы зафиксированы, какие различия среды допускаются и какие выходы сравниваются. Нельзя распространить опыт с одним архивом на все версии упаковщика и все операционные системы без проверки.

Например, две страницы HTML отличаются только пробелом в комментарии. Браузер показывает их одинаково, но файлы различаются. Два ZIP содержат одинаковый app.py, но разное время записи элемента — снова разные байты. Это не обязательно ошибка приложения; это помеха проверке происхождения результата. Если независимая сборка должна подтвердить доставленный артефакт, шум от часов, путей и случайного порядка мешает отличить ожидаемое изменение от постороннего.

Какие входы фиксирует опыт Go

Фиксируем один набор исходников go-service, содержимое go.mod, версию Go 1.27.3, целевую Linux/amd64 с GOAMD64=v1 и CGO_ENABLED=0. Обе сборки используют одинаковые -mod=readonly -trimpath -buildvcs=false и строку -ldflags=-X main.Version=1.0.0. Меняем только абсолютный путь копии и время файлов, используем отдельные новые кэши. Сравниваем байты dist/handbook-service, а не журналы, которые закономерно содержат разные пути и длительности.

Такая проверка устанавливает ограниченное свойство: для указанных входов и изменённых факторов результаты совпали. Она не доказывает равенство выпусков другого компилятора, CGO-сборки или Windows. Если даже один из этих входов изменён, несовпадение может быть ожидаемым и полезным. Например, новая строка версии должна изменить бинарник. Проверка воспроизводимости не требует всегда получать один файл независимо от содержательных изменений.

Манифест рядом с бинарником тоже является результатом, но у него отдельный договор. Поля source_revision и source_dirty зависят от происхождения копии: два каталога с одинаковыми Go-файлами могут иметь разные Git-метаданные. Тест бинарного равенства при buildvcs=false не обещает равенство таких описаний. Для проверки всей пары готовят две независимые копии одной утверждённой ревизии с одинаковым состоянием и сравнивают стабильные поля; сведения о конкретном запуске хранят отдельно.

Где появляется недетерминированность

Детерминированное действие при одинаковых определённых входах выдаёт одинаковый результат. Нарушение часто приходит через неучтённый вход. Генератор вставил текущее время, перечисление каталога вернуло файлы в другом порядке, компилятор записал абсолютный путь в отладочную информацию, утилита сортировала строки по другой локали. Случайный идентификатор запуска, имя пользователя, режим доступа, перевод строки и версия сжимающей библиотеки способны изменить сохранённый файл без видимого изменения деловой логики.

Архив особенно нагляден: в нём есть содержимое каждого элемента и метаданные контейнера. Наивное добавление файла переносит время и платформенные свойства с файловой системы. Даже исправив время, можно оставить другой порядок записей или отличающиеся атрибуты прав. Сжатие добавляет ещё один алгоритм и его реализацию. Поэтому наш первый опыт вообще не сжимает данные: размер будет больше, зато проще увидеть причинную связь между входами и байтами.

Какие источники различия убирают флаги Go

Без trimpath компилятор может записывать файловые пути в отладочные данные и таблицы, используемые стековыми трассировками. Два одинаковых файла в /tmp/a и /tmp/b тогда способны дать разные выходы. -trimpath нормализует относящиеся к инструментам файловые пути; он не ищет и не заменяет произвольную строку "/tmp/a", которую сам разработчик поместил в константу программы. Содержательные данные остаются входами.

Автоматические сведения VCS включают доступные ревизию, время и признак изменённости. -buildvcs=false исключает их автоматическое встраивание. Это удобно для отдельного внешнего манифеста, но становится потерей наблюдаемости, если затем нигде не записать происхождение. Альтернативный договор — строить из чистой известной ревизии с требуемым встроенным VCS и сравнивать именно такие сборки. Нельзя в одном случае брать незаписанный каталог, в другом tag, а затем объяснять отличие только «шумом компилятора».

-ldflags тоже входит в действие. Строка -X main.Version=1.0.1 задаёт другой продукт, даже когда исходники одинаковы. Флаги удаления отладочной информации -s -w могут уменьшить размер, но меняют возможности диагностики; они не являются обязательной магией воспроизводимости. Ручное обнуление build ID через параметр компоновщика также не стоит добавлять без причины. Детерминированный идентификатор, полученный из определённых входов, совместим с равенством байтов и полезен инструментам.

Минимальная Go-проверка до упаковки

Откройте Bash с env.sh главы 14 и выполните cd "$LAB/service". Ниже создаются только два личных выхода first и second; в этой сессии уже выбраны Go 1.27.3, linux/amd64/v1 и отдельные кэши. Выполняйте команды по одной и продолжайте сравнение лишь после кода 0 обеих сборок.

CGO_ENABLED=0 GOOS=linux GOARCH=amd64 GOAMD64=v1 \
  go build -mod=readonly -trimpath -buildvcs=false \
  '-ldflags=-X main.Version=1.0.0' -o first ./cmd/handbook-service
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 GOAMD64=v1 \
  go build -mod=readonly -trimpath -buildvcs=false \
  '-ldflags=-X main.Version=1.0.0' -o second ./cmd/handbook-service
python3 -c 'import pathlib,hashlib; a=pathlib.Path("first").read_bytes(); b=pathlib.Path("second").read_bytes(); print(a==b,hashlib.sha256(a).hexdigest())'
go version -m first
go tool buildid first

Два вызова в одном каталоге — первая проверка команд, а не достаточная независимость: они делят кэш. Далее повторяют действие в двух созданных копиях с отдельными GOCACHE и GOMODCACHE. В собственном опыте это делалось во временных каталогах с GOENV=off, GOTOOLCHAIN=local, GOWORK=off, GOPROXY=off и GOMAXPROCS=2. Имена first и second задают места выхода; само их различие не обязано встраиваться в бинарник при данном договоре. Полученный хеш зависит от фактических исходников и не заменяется заранее придуманной строкой.

Вспомогательная tools/build.py создаёт Go-бинарник и manifest, задавая те же основные условия. Её Python-процесс не компилирует программу сам: он запускает выбранный go, читает выходные байты и вычисляет SHA-256. Возвращённый ноль без ожидаемого бинарника не является успехом обвязки. В свою очередь одинаковый SHA двух файлов не доказывает, что в них сохранена нужная строка Version: это проверяется запуском именно выбранного артефакта с -version.

Почему CGO и toolchain требуют отдельного опыта

С CGO в набор входов входят C-компилятор, заголовки, библиотечные файлы, параметры компоновки и целевая libc. Две машины с одинаковым Go могут получить разные результаты. Даже если бинарник запускается на обеих, разные отладочные пути или версии внешней библиотеки мешают побайтовому равенству. Поэтому подтверждённый здесь pure-Go опыт не распространяется на CGO. Кросс-компиляция с CGO также требует подходящего внешнего toolchain; одной смены GOOS недостаточно.

Выбранный toolchain включает стандартную библиотеку и реализацию runtime. Директива go 1.25.0 не означает, что Go 1.25 и 1.27.3 обязаны произвести одинаковый машинный код. Она задаёт совместимость и минимальные требования, а новые инструменты меняют оптимизации и реализацию библиотек. Для расследования сохраняют фактический go version и встроенные build settings. GODEBUG и директивы совместимости могут влиять на поведение runtime; их рассматривают как часть договора, а не как универсальный способ сделать любой результат одинаковым.

Следующий ZIP — отдельный опыт структуры контейнера. Он нужен, если бинарник дополнительно упаковывается для доставки: одинаковая программа внутри двух архивов ещё не означает одинаковый архив.

Два расположения исходников и два пустых кэша

Предыдущие first и second проверяют повтор в одном каталоге. Для влияния абсолютного пути нужны две отдельные копии. В Bash главы 14 создайте два ранее отсутствовавших каталога; cp -R копирует исходники, а не изменяет первоначальный сервис. Если имя уже существует, остановитесь и выберите новое, чтобы не смешать состояния.

cd "$LAB"
test ! -e repro-a && test ! -e repro-b && cp -R service repro-a && cp -R service repro-b
cd "$LAB/repro-a"
GOCACHE="$LAB/repro-a-cache" go build -mod=readonly -trimpath -buildvcs=false   '-ldflags=-X main.Version=1.0.0' -o app ./cmd/handbook-service
cd "$LAB/repro-b"
GOCACHE="$LAB/repro-b-cache" go build -mod=readonly -trimpath -buildvcs=false   '-ldflags=-X main.Version=1.0.0' -o app ./cmd/handbook-service
python3 -c 'import os,pathlib,hashlib; r=pathlib.Path(os.environ["LAB"]); a=(r/"repro-a/app").read_bytes(); b=(r/"repro-b/app").read_bytes(); print("equal", a==b, "bytes",len(a)); print(hashlib.sha256(a).hexdigest())'

После успешных сборок ожидается equal True. Размер измеряется в байтах; SHA-256 относится к вашему конкретному результату. У двух процессов одинаковые GOOS/GOARCH/GOAMD64 и версия, а GOCACHE начинается с пустых разных каталогов. Это сильнее простого тёплого повторения, хотя оба опыта всё ещё на одном хосте и одном toolchain. Измените только main.Version=1.0.0 на 2.0.0 при сборке repro-b: сравнение должно стать False, а ./app -version из repro-b — вывести 2.0.0. Верните флаг 1.0.0 и пересоберите перед дальнейшим сравнением. При ненулевом коде сборки прекращайте сравнение: старый app не свидетельствует об успехе нового входа.

Для следующего ZIP-примера перейдите в $LAB/fixtures/zip: там уже лежат README.txt и app.py. Сохраните показанный далее код как stable_zip.py в этом каталоге. Python создаёт first.zip и second.zip рядом с ними; он не упаковывает весь стенд или кэши.

Минимальный детерминированный ZIP

Следующий самостоятельный файл stable_zip.py рассчитан на обычный Python 3 со стандартной библиотекой. Он упаковывает только app.py и README.txt из текущего каталога. Выход задаётся аргументом. Два маленьких входа уже подготовлены в fixtures/zip; сам stable_zip.py сохраните из блока ниже. Эти данные нужны для разбора структуры ZIP и не входят в исполняемый файл Go-службы. В примере намеренно нет обхода всех файлов: временный мусор, секреты и сам предыдущий архив не должны незаметно попасть в результат.

from pathlib import Path
import stat
import sys
import zipfile

members = ("README.txt", "app.py")
with zipfile.ZipFile(sys.argv[1], "w") as archive:
    for name in sorted(members):
        payload = Path(name).read_bytes()
        info = zipfile.ZipInfo(name, (2000, 1, 1, 0, 0, 0))
        info.create_system = 3
        info.external_attr = (stat.S_IFREG | 0o644) << 16
        info.compress_type = zipfile.ZIP_STORED
        info.extra = b""
        info.comment = b""
        archive.writestr(info, payload)
    archive.comment = b""

read_bytes() читает исходные байты: программа не меняет кодировку и окончания строк. sorted фиксирует порядок имён. ZipInfo явно задаёт имя и дату; 2000 год попадает в допустимый традиционным ZIP диапазон. Значение create_system = 3 объявляет Unix-формат атрибутов независимо от машины сборки. Старшая половина external_attr получает тип обычного файла и права 0644: владелец читает и пишет, остальные читают. Сдвиг на 16 помещает эти биты в соответствующую часть поля. Это описание внутри архива, а не изменение прав исходного файла.

ZIP_STORED сохраняет данные без сжатия; пустые дополнительные поля и комментарии исключают ещё один канал различий. Режим "w" создаёт новый архив вместо дописывания к старому. Здесь нет текущего времени, абсолютных путей и обращения к сети. Не следует, однако, обещать этими строками воспроизводимость произвольного приложения: генератор, который заранее создал разные app.py, останется источником отличий. Мы нормализовали контейнер, а не все возможные входные данные.

Этот самостоятельный ZIP-опыт не заменяет основной Go-сборщик. В нынешнем маршруте labs/service/tools/build.py создаёт исполняемый файл и JSON-манифест; он не принимает интерфейс stable_zip.py и не производит handbook-demo.zip. Рабочий каталог fixtures/zip отделяет упаковку от сборки сервиса и его кэшей.

python3 stable_zip.py first.zip
python3 stable_zip.py second.zip
python3 -c 'import hashlib,pathlib; a=pathlib.Path("first.zip").read_bytes(); b=pathlib.Path("second.zip").read_bytes(); print(a == b); print(hashlib.sha256(a).hexdigest())'

-c выполняет переданную строку как Python-код. Ожидается True, затем шестнадцатеричный SHA-256. Само значение зависит от содержимого двух исходных файлов. Существеннее повторить упаковку в двух независимых каталогах с одинаковыми входными байтами, но разными временем файлов и правами. Для данного упаковщика результат должен совпасть. Если изменится хотя бы один байт app.py, совпадения требовать уже нельзя. Прямая проверка a == b в маленьком опыте сравнивает сами байты; хеш удобен для передачи идентификатора большого файла.

Время происхождения вместо времени запуска

Иногда продукту действительно нужна дата. Тогда выбирают осмысленный фиксированный вход: время утверждённого снимка исходников либо дату выпуска. Соглашение SOURCE_DATE_EPOCH передаёт число секунд от начала Unix-эпохи. Оно действует только на инструменты, которые его поддерживают; объявление переменной не перехватывает произвольные обращения к часам. Свой генератор должен явно прочитать её и согласованно использовать UTC. Записывать текущее время «для удобства», а затем ожидать одинаковый файл противоречиво.

Традиционное время ZIP имеет ограничения представления, включая допустимые годы и двухсекундную точность. Если переносите произвольную дату в такой формат, заранее определите проверку диапазона и нормализацию. Молчаливая подстановка сегодняшнего дня после ошибки уничтожит ожидаемое свойство. Фиксированная дата в учебном примере честно означает техническую нормализацию; фактическое время запуска сохраняют в отдельном отчёте CI, который не объявляют воспроизводимым артефактом.

Дата является входом только там, где её действительно читают

Обычная Go-сборка не обязана вставлять время каждого запуска в main.Version или другое пользовательское поле. Это часто делает собственная обвязка, например передавая текущую дату через -X. Если нужен штамп выпуска, он должен происходить из выбранного стабильного источника, а реальное время действия остаётся в журнале. Переменная SOURCE_DATE_EPOCH не перехватывает все часы компилятора и пользовательского генератора автоматически. В нашем build.py текущая дата не добавляется в бинарник.

Встроенные ресурсы и генерация остаются содержимыми входами

Директива //go:embed помещает выбранные ресурсы в результат компиляции. Например, шаблон assets/page.html перестаёт быть внешним файлом времени исполнения, но не перестаёт влиять на результат: изменение его байта должно изменить соответствующую сборку. Выбор производится по правилам embed относительно каталога пакета. Нельзя считать его произвольным рекурсивным копированием любых соседних каталогов и путей с .. . Для проверки происхождения сохраняют и сам исходный ресурс, и схему его выбора.

Если ресурс генерируется, нужно воспроизвести предварительное действие. Два одинаковых main.go с разными сгенерированными данными не являются одинаковыми полными входами. Генератор мог записать текущее время, случайно изменить порядок элементов или прочитать внешний сервис. Включение -trimpath не исправляет такие различия: это флаг обработки путей, а не универсальная нормализация полезной нагрузки. Сначала сравнивают входы генерации, затем его выход, затем архив пакета и конечный бинарник.

Различать причинный эксперимент и случайное совпадение

Меняйте по одному фактору. Сначала два разных каталога с одинаковыми входами и флагами. Затем новая строка Version при прежней платформе: ожидается другое значение и другие байты. Затем другой GOARCH: ожидается другой машинный формат/код, а успешность запуска в прежней среде уже не требование. Затем новый toolchain: совпадение может случиться, но не входит в исходное обещание. Такой ряд одновременно проверяет неизменность при несущественном факторе и чувствительность к существенному.

Хеш всего manifest.json может меняться из-за специально сохранённого происхождения, тогда как бинарник остаётся одинаковым. Это не повод удалять неудобные сведения из манифеста. Разделите стабильное описание продукта и наблюдения конкретного запуска, определите сравниваемые поля и проверьте их смысл. Выпуск не становится прозрачнее, если ради красивой одинаковой строки скрыть source_dirty=true или неизвестную ревизию. Известные различия объясняют, а неизвестные исследуют.

Как расследовать различие

Сначала убедитесь, что сравниваются одинаковые категории выходов: архив приложения с архивом приложения, а не с журналом запуска. Затем сравните перечень элементов, их содержимое и метаданные. Если содержимое одинаково, ищите порядок, время, комментарии, права и сжатие. Если отличается сам текст, ищите генерацию, кодировки, путь или окружение. Изменяйте по одному фактору: временной каталог, часовой пояс, порядок создания файлов. Такой опыт превращает случайное несовпадение в проверяемую гипотезу.

Изолированный контейнер облегчает фиксацию инструментов, но не гарантирует результата: внутри него остаются часы, сетевые ответы и случайность. И наоборот, два обычных каталога на одной машине могут успешно подтвердить ограниченную воспроизводимость простой упаковки. В протоколе опыта укажите фактические версии, входы и изменённые факторы. Равенство двух сборок с общим отравленным кэшем также слабее независимого повторения: оба запуска могли взять один и тот же чужой выход, ничего не пересобрав.

Побайтовое равенство не является полной проверкой безопасности. Детерминированно собираемая ошибочная программа остаётся ошибочной; одинаковый вредоносный компилятор способен дать одинаковый вредоносный выход. Сила воспроизводимости в дополнительном проверяемом отношении между утверждёнными входами и доставленным файлом. Для этого нужны известные входы, доверенная процедура их получения и независимость проверки, а не только красивая строка контрольной суммы.

Фиксировать параметры, которые меняют машинную цель

Два вызова с одинаковыми GOOS и GOARCH могут различаться уровнем GOAMD64, набором экспериментов и инструментирующими флагами. Проверка гонок данных через -race, измерение покрытия кода тестами через -cover, отладочные -N/-l и оптимизация по профилю прежних выполнений (PGO, profile-guided optimization) задают другие действия и способны изменить байты результата. Поэтому подпись «linux/amd64, тот же Git» ещё не полный протокол. Нельзя сравнить инструментированный тестовый бинарник с обычным выпуском и назвать расхождение недетерминированностью.

Для небольшого Go-опыта без CGO достаточно узкого явного набора и фактической версии toolchain. По мере добавления CGO или PGO договор расширяется: внешний компилятор, библиотеки и профиль тоже становятся входами. Если в документе они не указаны, честный вывод ограничивается прежним опытом. Воспроизводимость усиливается перечислением действительных причин результата, а не обещанием, что один trimpath устранит любые различия любых сборок.

Для основного Go-опыта: воспроизводимость Go toolchain, trimpath, buildvcs и сведения сборки, параметры компоновщика, фактический выбор версии.

Первичные источники ZIP-опыта

Python zipfile: ZipInfo, атрибуты и запись элементов; Reproducible Builds: время в выходах; Спецификация SOURCE_DATE_EPOCH; Абсолютные пути как источник различий; Вариации среды сборки. Пример ZIP проверяется как собственный опыт; применение сжатия и других версий инструментов требует отдельного подтверждения.
