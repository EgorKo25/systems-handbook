Сборка Go: от пакета к исполняемому файлу

Проследим, как команда go выбирает файлы, проверяет зависимости, компилирует пакеты и связывает бинарник. Сборка учебной службы будет настоящей; Python останется только вспомогательной записью манифеста.

Первый запуск: выбрать Go и подготовить личные файлы

Практический профиль этой части — Linux на amd64, Bash и Python 3.10 или новее. Bash исполняет строки команд; cd меняет текущий каталог, от которого считаются относительные пути. $HOME — домашний каталог обычного пользователя. Все команды ниже выполняет этот пользователь; права администратора не нужны. Сначала нужен уже установленный комплект toolchain: программа go, компилятор, линковщик, стандартная библиотека и их исходники одного выпуска.

Найдите каталог bin именно Go 1.27.3 для Linux amd64. Если комплекта ещё нет, на официальной странице выпусков выберите архив go1.27.3.linux-amd64.tar.gz, сверьте SHA-256 — контрольную сумму всех байтов скачанного файла — со строкой этого файла на странице и распакуйте его в новый личный каталог, например $HOME/toolchains/go1.27.3. Внутри него должен оказаться bin/go; если архив создаёт дополнительный уровень go/, укажите его в пути. Не накладывайте архив поверх старого комплекта: смешанные инструменты и стандартная библиотека могут сообщить несовместимость формата. Процедура официальной установки описана здесь; используйте личный новый каталог вместо системного. Дальнейшие опыты ничего не скачивают.

Откройте терминал Bash в корне сохранённого клона, где есть go/labs/foundations/prepare.py. В первой строке подставьте найденный абсолютный путь к bin. Кавычки сохраняют путь одним аргументом даже с пробелами. Скрипт сначала проверит точную версию, затем скопирует сервис и все маленькие модули в постоянный личный каталог. Существующий каталог он откажется перезаписывать. Исходники в клоне останутся исходным образцом.

GO_BIN_DIR="$HOME/toolchains/go1.27.3/bin"
python3 go/labs/foundations/prepare.py --go "$GO_BIN_DIR/go"   --root "$HOME/handbook-lab/go-foundations"
source "$HOME/handbook-lab/go-foundations/env.sh"
go version
go env GOOS GOARCH GOTOOLCHAIN GOCACHE GOMODCACHE GOPATH
cd "$LAB/service"
mkdir -p dist

Успех подготовки — строка Prepared и код 0. Затем ожидаются go version go1.27.3 linux/amd64, цель linux/amd64, local и три личных пути внутри $HOME/handbook-lab/go-foundations/cache. При root already exists сохраните прежний стенд и выполните только source его env.sh; для независимого опыта выберите другое новое имя root. При неверном пути или версии исправьте GO_BIN_DIR до подготовки. Если source или проверка версии не прошли, следующие команды сборки пока не выполняйте.

source читает настройки в текущую оболочку. export в этом файле передаёт их дочерним процессам. Переменная LAB называет личный стенд; добавленный в начало PATH каталог выбирает нужную программу go. GOENV=off исключает сохранённые через go env -w настройки; GOWORK=off исключает родительский go.work; GOTOOLCHAIN=local запрещает автоматическую загрузку другого Go. Пустые GOFLAGS и GOEXPERIMENT убирают унаследованные добавки. GOCACHE хранит результаты сборки, GOMODCACHE — полученные модули, GOPATH — личный рабочий путь инструментов; это разные назначения. TMPDIR и более приоритетный для Go GOTMPDIR тоже расположены внутри стенда. GO111MODULE=on выбирает модули; пустой GOCACHEPROG оставляет штатный дисковый кэш, пустой GODEBUG — обычный режим, GOFIPS140=off — стандартную криптографическую реализацию профиля. Для этих модулей без внешних архивов выставлены GOPROXY=off и GOSUMDB=off. Публичные зависимости требуют проверки из главы 15.

В новом терминале снова выполните source "$HOME/handbook-lab/go-foundations/env.sh" и нужный cd. Настройки не записаны в профиль оболочки или глобальное состояние Go. Файлы service/, fixtures/, out/ и cache/ принадлежат вам. Следующие блоки называют свой каталог явно. Команды с перенаправлением > заменяют только указанный журнал или выход; сохраняйте нужный предыдущий результат под другим именем. Полная карта файлов находится в README стенда.

У сборки есть входы, исполнители и выходы

Наш основной проект расположен в labs/service. Его модуль называется example.org/handbook-service. Пакет cmd/handbook-service содержит точку входа main, а internal/httpapp — HTTP-обработчик. В go.mod указано go 1.25.0; проверенный исполнитель сборки — Go 1.27.3 для Linux/amd64. Минимальная версия языка и фактически выбранная версия инструментов — разные значения. Никакого обращения к example.org для собственных пакетов этого основного модуля не требуется: путь служит их пространством имён.

Исходный файл на диске — вход компилятора, а не работающая служба. Команда go build создаёт исполняемый файл, но не запускает его. При запуске операционная система создаёт процесс, загружает сегменты программы, формирует аргументы и окружение. Только этот процесс открывает сокет, читает конфигурацию и обслуживает HTTP. Снимок Git, бинарник и процесс имеют разные идентичности и сроки жизни. Новый коммит без повторной сборки не изменит уже сохранённый бинарник; новый бинарник без перезапуска не заменит код работающего процесса.

Артефактом называем сохранённый выход действия. Для этого маршрута это dist/handbook-service и описание dist/manifest.json. Первый содержит машинный код и нужные части среды выполнения Go; второй связывает выход с условиями сборки. Успешный компилятор ещё не доказывает правильность ответа /greet. Это устанавливают отдельные проверки. Обычный Python 3 нужен сценарию tools/build.py только для организации запуска и записи JSON, а для исполнения полученной службы Python не требуется.

Полная модель действия имеет вид выход = F(исходники, версии модулей, toolchain, флаги, target, окружение). Toolchain — комплект компилятора, ассемблера, компоновщика и стандартной библиотеки. Target — выбранная платформа результата: операционная система, архитектура и её уровень возможностей. Скрытые файлы генератора, путь локальной замены модуля, CGO-библиотека и встроенный ресурс тоже могут быть входами. Начинать расследование сбоя нужно с восстановления этого набора, а не с общего слова «CI».

Компиляция, связывание и интерпретация

Пакет Go — набор подходящих исходных файлов одного каталога с общим именем package. Команда go сначала определяет модуль и рабочую область, разрешает импорты, применяет ограничения сборки и выбирает файлы для платформы. Файл с суффиксом _windows.go не войдёт в linux-сборку. Строка //go:build может дополнительно зависеть от тегов и окружения. Файлы _test.go не входят в обычный бинарник. Два одинаковых каталога при разных GOOS, GOARCH или тегах могут означать разные наборы входов.

Компилятор разбирает синтаксис и типы выбранного пакета, читает экспортные сведения импортов, выполняет оптимизации и формирует объектное представление. Для обычной цепочки gc результат пакета помещается в архив .a, включающий данные компиляции и сведения, нужные последующим инструментам. Это не исходный ZIP и не уже готовая служба. Пакет с теми же исходниками, но другими импортами или флагами может требовать другого результата. Предкомпилированные данные не объявляют универсальными для любой версии Go.

Компоновщик, linker, начинает с main, разрешает символы пакетов и формирует конечный файл формата платформы: обычно ELF на Linux, PE на Windows, Mach-O на macOS. Он может не включить недостижимые части кода, поэтому сумма размеров архивов пакетов не равна размеру бинарника. Среда выполнения Go включает планирование горутин, сборку мусора и другие функции; она поставляется с выбранным toolchain и является частью результата. Её наличие не означает, что целевая машина должна отдельно устанавливать команду go.

Каталог — $LAB/service после подготовки выше; входы — go.mod, cmd/handbook-service/main.go и internal/httpapp/*.go. Следующие команды ничего не запускают как службу: list читает пакеты, build создаёт файл в личном out/.

go list -f '{{.ImportPath}} {{.Name}} {{join .GoFiles ","}}' ./cmd/handbook-service ./internal/httpapp
go list -deps ./cmd/handbook-service
go build -x -work -o "$LAB/out/handbook-observe" ./cmd/handbook-service

list исследует выбранные пакеты; -f задаёт шаблон вывода: путь импорта, имя и список Go-файлов. -deps добавляет зависимости пакета, включая стандартную библиотеку. У build -x печатает запускаемые действия, -work показывает и оставляет временный рабочий каталог, -o задаёт выход. Используйте свой отдельный путь, если имя $LAB/out/handbook-observe уже занято. На прогретом кэше компилятор может не запускаться: это ожидаемый результат, а не отсутствие этапов в устройстве сборки.

Что видно между compile и link

В оставленном каталоге встречаются importcfg, importcfg.link, архивы пакетов и служебные файлы. Строка вида packagefile ПУТЬ=АРХИВ связывает имя импорта с выбранным скомпилированным представлением. Компилятор не должен сам случайно находить «какую-нибудь библиотеку» в домашнем каталоге. Команда go строит это соответствие на основании разрешённых модулей и графа. Формат и размещение временных файлов — внутренние детали версии инструментов; их полезно читать для диагностики, но не использовать как стабильный интерфейс собственного упаковщика.

Ключ действия, action ID, описывает входы конкретного вычисления для кэша. Build ID — связанный идентификатор сборочного результата, который инструменты могут записать в архив или бинарник. Это не SHA-256 доставленного файла и не идентификатор Git-коммита. go tool buildid "$LAB/out/handbook-observe" читает build ID, а go version -m "$LAB/out/handbook-observe" — доступные встроенные сведения о сборке и модулях. Для проверки передачи всех байтов вычисляют отдельную контрольную сумму. Нельзя подменить все три уровня одним числом.

Что компилятор делает с выбранными файлами пакета

После разбора синтаксиса получается дерево конструкций программы. Проверка типов устанавливает допустимость обращений, преобразований, интерфейсов и операций до исполнения. Затем внутреннее представление преобразуется к форме, удобной для анализа потока данных и оптимизаций. В SSA, static single assignment, каждое внутреннее значение определяется единственным присваиванием; это не требование писать пользовательский код без переменных, а способ представления внутри компилятора. По нему выполняются преобразования и выбор машинных инструкций. Подробное устройство этих фаз рассматривается в главах46–52 этой книги.

Успех ранней фазы не обещает успеха следующей. Синтаксически правильный файл может не пройти проверку типов, правильный пакет — не найти импорт, а набор пакетов — не связаться из-за отсутствующего символа или несовместимого CGO-входа. Поэтому в диагностике называют инструмент и последнюю подтверждённую фазу. Сообщение компоновщика об отсутствующем символе не исправляют повторной загрузкой случайного модуля, если фактически выбрали не тот набор файлов по build constraints.

Обычный Go-код не использует обязательную интерпретацию байткода на машине пользователя: этот маршрут заканчивается машинным исполняемым файлом. При этом runtime остаётся частью исполнения и может динамически распределять память и планировать горутины. Предварительная компиляция не означает отсутствие работы при запуске. Инициализация пакетов, чтение конфигурации и создание пулов могут определять заметную задержку готовности, хотя компилятор уже давно завершился.

Область флага и два разбора аргумента

go build '-gcflags=example.org/handbook-service/internal/httpapp=-m=2' ./cmd/handbook-service
go build '-gcflags=all=-N -l' -o "$LAB/out/debug-service" ./cmd/handbook-service

-gcflags передаёт параметры компиляторам выбранных пакетов. До знака равенства может стоять шаблон пакета; all= распространяет действие и на зависимости. В первом вызове -m=2 запрашивает подробную оптимизационную диагностику выбранного пакета, включая решения о размещении и встраивании. Это наблюдение текущего компилятора, а не обещание вечного размещения переменной на стеке. Во втором -N отключает оптимизации, -l — встраивание для отладочной цели. Такой бинарник не используют как доказательство скорости обычного выпуска.

Сначала Bash разбирает внешние кавычки и формирует один аргумент -gcflags. Затем команда go разбирает внутренний список параметров для компилятора. Аналогично -ldflags передаёт список компоновщику. Если снять внешние кавычки у all=-N -l, -l может попасть уже на уровень go build, где имеет иной либо недопустимый смысл. Команда, управляющая фазами, и исполняемый ею инструмент имеют разные пространства флагов.

-X относится к подходящей строковой переменной компонуемого пакета. В нашем main это var Version = "dev". Константа языка или произвольное значение, вычисляемое пользовательской функцией, не является тем же интерфейсом подстановки. Чтобы доказать результат, запускают построенный файл с -version; простое присутствие строки -X в журнале не подтверждает выбранный путь пакета и фактически доставленный бинарник.

Структура исходников влияет на объём повторной работы

Go компилирует пакет как единицу, поэтому разбиение одного пакета на десять файлов не обязательно даёт десять независимых кэшируемых компиляций. Большой часто меняющийся пакет может тянуть заметную повторную работу. Но механическое превращение каждого файла в отдельный пакет увеличит граф, экспортные границы и организационные затраты. Оптимизацию структуры подтверждают трассировкой действий на типичных изменениях, а не только общим количеством каталогов.

Импорты должны образовывать допустимый ациклический граф пакетов: A→B→A не становится приемлемым от того, что вызов одной функции редкий. Каталог internal ограничивает круг допустимых импортирующих пакетов по положению в дереве путей; это проверка инструмента, а не сетевой контроль доступа. Экспортные сведения, в том числе необходимые для оптимизации тела, могут влиять на потребителей. Поэтому «изменил только внутреннюю функцию — ничего рядом не должно пересобираться» проверяют наблюдением конкретной версии, не принимают за универсальный закон.

Граф действий вместо длинного списка команд

internal/httpapp + его импорты → compile → архив пакета ─┐
cmd/handbook-service + импорты → compile → main-архив ───┼→ link → бинарник
toolchain + target + параметры ─────────────────────────┘
исходники + _test.go → тестовый бинарник → выполнение тестов
бинарник + условия сборки → manifest → проверка пары → выпуск

Импорт создаёт зависимость данных: пакет-потребитель требует подходящие сведения пакета-поставщика. Команда go может выполнять независимые действия параллельно. Флаг -p 2 ограничивает число одновременно выполняемых программ сборки пакетов; переменная GOMAXPROCS=2 ограничивает доступный Go-процессам параллелизм исполнения. Это связанные, но не одинаковые регуляторы. Большее число одновременно компилируемых пакетов может увеличить пик памяти и замедлить машину из-за конкуренции, даже если ядер много.

Модульный тест и сборка выпуска могут использовать многие одинаковые архивы из кэша, но это разные действия. go test обычно создаёт специальный тестовый исполняемый файл, содержащий тестовые функции и обвязку. Проверка обработчика через httptest не является запуском доставленного процесса с его разбором флагов и обработкой сигналов. Поэтому в графе нужен отдельный дымовой запуск, smoke test, именно артефакта: версия, старт на loopback, запрос и штатное завершение. Он ждёт сборку и не заменяет подробных тестов пакета.

Управляющая зависимость отличается от передачи данных. Сборка бинарника не обязана ждать статический анализ, но публикация обязана дождаться его успешного результата, если он принят как условие выпуска. Если нарисовать только стрелки файлов, легко выпустить бинарник раньше окончания проверок. Если записать всё последовательно без причины, теряется полезный параллелизм. Правильное расписание следует из явных данных и условий, а не из декоративного количества стадий.

Go: команда управляет сборкой пакетов

В поставленном tools/build.py параметры выбраны явно: CGO_ENABLED=0, GOOS=linux, GOARCH=amd64, GOAMD64=v1. CGO — механизм взаимодействия Go с C; отключение исключает эту ветку сборки для подходящего проекта. Флаг -mod=readonly запрещает неявно переписывать описание зависимостей, -trimpath убирает зависимые от места сборки записываемые файловые пути, -buildvcs=false отключает автоматическую запись сведений VCS внутрь бинарника. Отключение VCS не означает отказ от происхождения: ревизия записывается отдельным проверяемым манифестом.

Продолжаем в $LAB/service, где уже создан личный dist/. -mod=readonly запрещает необходимые правки go.mod; он не обещает неизменность всех кэшей или go.sum. Успешная сборка возвращает 0. При ошибке не запускайте одноимённый файл от прежней сборки: сначала исправьте указанный вход и получите новый успешный результат.

CGO_ENABLED=0 GOOS=linux GOARCH=amd64 GOAMD64=v1 \
  go build -mod=readonly -trimpath -buildvcs=false \
  '-ldflags=-X main.Version=1.0.0' \
  -o dist/handbook-service ./cmd/handbook-service
go version -m dist/handbook-service
./dist/handbook-service -version
python3 tools/build.py --goos linux --goarch amd64 --version 1.0.0

-ldflags передаёт список параметров компоновщику. Внутреннее -X main.Version=1.0.0 устанавливает подходящую строковую переменную main.Version. Это параметр сборки, поэтому другой номер версии закономерно меняет выход. Одинарные кавычки сохраняют весь аргумент вместе с пробелом. Флаг -version уже принадлежит нашей службе, а не команде go: он печатает встроенную строку и завершает процесс. У вспомогательного Python-сценария свои --goos, --goarch и --version, значения которых превращаются в условия описанного действия.

Сценарий создаёт каталоги dist и .lab-cache внутри копии учебного проекта. Он не изменяет глобальные настройки Go. Путь к go можно передать через HANDBOOK_GO; это удобно для отдельно распакованного проверенного toolchain. Манифест содержит фактическую версию, флаги, target, размер, SHA-256, source_revision и source_dirty. Если проект не является самостоятельным Git-репозиторием, ревизия может быть null, а dirty=true: обвязка честно не выдумывает чистый коммит чужого родительского каталога. Для формального выпуска эти поля проверяют как условия приёмки.

Сравнение с Maven и другими цепочками

У Java Maven организует фазы, плагины, разрешение зависимостей и упаковку JAR; выполнение требует соответствующей JVM. У Go основная команда уже знает модель пакетов, тестов и модулей. В обоих случаях необходимо фиксировать версии инструментов и описание действия. Название команды не доказывает автономность артефакта: JAR может требовать внешние зависимости, а Go-бинарник с CGO — динамические библиотеки. Maven не является обязательной установкой этого практикума.

Как увидеть действие глазами операционной системы

Команда go сама является процессом и создаёт дочерние процессы инструментов. Каждый получает аргументы, файловые дескрипторы, переменные и рабочий каталог. Диагностический -x показывает часть этой организации на уровне команд; наблюдение процессов и файлов операционной системой даёт другой срез. Большое число строк не равно большому времени: тысячи дешёвых действий могут завершиться быстрее одного дорогого связывания. Сначала сопоставляют действие, вход, выход и длительность.

Временный каталог может хранить много промежуточных данных. -work специально запрещает его обычное удаление после завершения, поэтому после исследования его убирают как собственный диагностический выход. Путь к нему не должен случайно попасть в долгоживущий договор выпуска. Чтение importcfg помогает доказать, какой архив был выбран; включать этот временный файл в артефакт обычно бессмысленно, потому что его абсолютные пути относятся к машине сборки.

Когда «у меня собирается» перестаёт быть аргументом

На компьютере разработчика может действовать go.work с локальной заменой модуля, пользовательский GOFLAGS либо автоматически выбранный другой toolchain. На агенте получатся другие входы. Для повторения записывают go version и выбранные значения go env -json GOVERSION GOMOD GOWORK GOOS GOARCH GOAMD64 CGO_ENABLED GOTOOLCHAIN. Это явный безопасный перечень, а не выгрузка всех переменных с токенами. Наличие go.mod в Git ещё не означает совпадение локальных replacements, файлов генерации и рабочего снимка.

Для диагностического опыта выполняют сборку в новой копии с GOENV=off, GOTOOLCHAIN=local, GOWORK=off, явными каталогами кэшей и нужными флагами. GOENV=off отключает пользовательский файл значений go env -w, но не отменяет все переменные процесса. GOTOOLCHAIN=local выбирает встроенный комплект и не разрешает автоматически скачать более новый. GOPROXY=off пригоден нашему проекту со стандартной библиотекой; проект с внешними модулями требует предварительно подготовленного доверенного набора. Нельзя объявить отсутствие сети общей причиной успешной сборки, если входы не были сохранены.

Файл и пакет не являются одинаковым аргументом

go build ./cmd/handbook-service выбирает пакет с его подходящими файлами. go build cmd/handbook-service/main.go задаёт явный список файлов и иной договор, исключая неуказанные соседние исходники. В простом однофайловом main оба случая могут выглядеть одинаково, но после добавления helper.go первый продолжит видеть пакет, а второй способен получить undefined. Такой сбой не доказывает повреждение кэша: изменился предмет команды.

Аналогично ./... — шаблон выбора пакетов, а не команда запуска всей службы. Массовая проверка компилируемости и изготовление конкретного доставляемого файла — разные требования к выходам. Для выпуска указывают main-пакет и путь -o, затем проверяют новый файл. Для обзора графа применяют list. Это даёт ясный ответ даже тогда, когда в одном модуле лежат несколько утилит cmd, каждая со своим main.

Первоисточники: go build, list, env и условия сборки, компилятор, компоновщик, выбор toolchain, модули. Команды и устройство временных файлов сопоставлялись с собственными опытами Go 1.27.3; это не публичный стабильный API внутренних каталогов.
