53. ELF и запуск: путь от файла к main

Готовый executable ещё должен быть распознан системой, отображён в память и передан runtime. На Linux amd64 исследуем заголовки, сегменты, зависимости и отладочные сведения. Сравнение обычного, облегчённого и PIE-файла покажет, почему размер на диске не равен рабочей памяти.

Запуск — новая граница после связывания

Команда оболочки находит файл и просит систему выполнить его. Ядро проверяет формат, целевую архитектуру и доступные условия запуска, затем создаёт образ процесса. Для некоторых файлов дополнительно требуется динамический загрузчик. Только после начальной подготовки выполнение приходит к входу программы и инициализации runtime. Пользовательская main находится дальше по этому пути.

Поэтому сообщение об отсутствии файла при запуске не всегда означает, что самого executable нет. Отсутствовать может требуемый интерпретатор ELF. Ошибка архитектуры, права выполнения и недоступная динамическая библиотека являются другими причинами. Расследование начинается с формата и заголовков, а не с повторной сборки исходника случайными параметрами.

Полная небольшая программа

Небольшой вариант main.go уже лежит в projects/ch53. В примере нет импорта C и внешних пакетов. Для сравнения собираются три новых файла, чтобы исходный результат сохранялся и можно было проверить каждое изменение независимо.

Поставленный исходник: $LABROOT/projects/ch53. Читайте его как текст файла.

package main
//go:noinline
func Answer(x int) int { return x + 1 }
func main() { println(Answer(41)) }

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch53, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

cd "$LABROOT/projects/ch53" || exit 1
CGO_ENABLED=0 go build -o demo . || exit 1
CGO_ENABLED=0 go build -ldflags='-s -w' -o demo-small . || exit 1
CGO_ENABLED=0 go build -buildmode=pie -o demo-pie . || exit 1
readelf -hW demo || exit 1
readelf -lW demo || exit 1
readelf -SW demo || exit 1
readelf -hW demo-pie || exit 1

readelf входит в отдельный набор инструментов, а не гарантирован одной установкой Go. Параметр -h показывает заголовок, -l — программные заголовки сегментов, -S — таблицу секций, -W выбирает широкий вывод. Каждый вариант отвечает на свой вопрос. В нашей Linux-среде инструмент доступен и соответствующие проверки выполнены.

Что показала реальная серия

У обычного чистого Go-файла проверенной серии тип ELF был EXEC, существовали LOAD-сегменты и отсутствовал INTERP. У варианта -buildmode=pie тип был DYN. У облегчённого файла отсутствовала секция .debug_info, присутствовавшая в обычном. Размер контрольного машинного примера уменьшился с 1 908 515 до 1 233 056 байт. Эти числа относятся к конкретному исходнику и Go 1.27.3, а не задают постоянную цену любой Go-программы.

Сравнение типов EXEC и DYN не доказывает само по себе наличие зависимости от libc. Динамическое положение образа, динамические библиотеки и интерпретатор являются связанными, но разными свойствами. Для каждого смотрят соответствующее поле или таблицу. Именно поэтому одного вывода file часто недостаточно для полного объяснения переносимости.

Заголовок описывает, как читать файл

Начальные сведения ELF позволяют определить класс адресов, порядок байтов, целевую машину, тип и расположение таблиц. Точка входа указывает адрес начала предусмотренного исполнения образа. Это не текстовое имя main.go и не обязательный адрес пользовательской main. Установка неверной архитектуры не исправляется переименованием файла или добавлением права выполнения.

Для самостоятельного продолжения сопоставьте machine, class и entry в readelf -hW. Затем найдите соответствующий входной символ через go tool nm, если таблица символов сохранена. Такой маршрут связывает абстрактное поле заголовка с конкретным стартовым кодом runtime. Он полезнее догадки, что система начинает выполнение с первой функции исходника.

Секция и сегмент решают разные задачи

Секции описывают логические части содержимого, удобные инструментам связывания и анализа. Сегменты описывают области, важные для загрузки образа в память. Несколько секций могут входить в один сегмент, а не каждая диагностическая секция обязана отображаться в рабочее адресное пространство. Таблица соответствия в readelf -lW помогает увидеть это различие на конкретном результате.

Поэтому удаление большой отладочной секции способно уменьшить файл на диске заметнее, чем постоянную рабочую память процесса. Она могла вообще не быть частью загружаемых областей. Для точного вывода сопоставьте её флаги и сегментное размещение, затем измерьте процесс. Формула «размер executable минус размер executable после strip равен сэкономленной RAM» неверна.

LOAD и разрешения

Загружаемые области имеют размеры в файле и памяти, адреса, выравнивание и разрешения. Код обычно не должен одновременно быть произвольно записываемыми пользовательскими данными. Разделение чтения, записи и исполнения помогает системе организовать защиту страниц. На рисунке это удобно представить как несколько отображений одного файла с разными свойствами, а не копирование всего файла в один одинаковый буфер.

Часть памяти может требоваться без соответствующих сохранённых байтов, например для начально нулевых данных. Разница файлового и размеров в памяти поэтому содержательна. И наоборот, наличие байтов в файле не означает, что они все немедленно физически прочитаны при старте. Подкачка и страничная организация добавляют следующий уровень, который нужно отличать от описания ELF.

Собственный ELF: от файлового байта к виртуальному адресу

Возьмём сохранённый $LABROOT/out/compiler из главы 50, созданный Go 1.27.3/amd64/v1 с CGO_ENABLED=0, -trimpath и -buildvcs=false. В нашем опыте это ELF64 little-endian, e_machine=62 (x86-64), e_type=2 (EXEC), e_entry=0x4807c0. Начало 7f 45 4c 46 02 01 01 00 сообщает формат, 64-битный класс и порядок байтов. e_phoff=64, e_phentsize=56, e_phnum=6: программные заголовки занимают [64,400). Они описывают загрузку; таблица секций нужна анализаторам и linker и начинается отдельно.

PT_LOADp_offset / p_vaddrp_filesz / p_memszp_align / права
Код0 / 0x4000000xa90b1 / 0xa90b10x1000 / R E
Неизменяемые данные0xaa000 / 0x4aa0000xd6918 / 0xd69180x1000 / R
Изменяемые данные0x181000 / 0x5810000x9da0 / 0x408e80x1000 / RW

Все величины таблицы шестнадцатеричные. p_offset — начало в файле; p_vaddr — предусмотренный виртуальный адрес; p_filesz — число файловых байтов; p_memsz — длина области в памяти; p_align — требуемое согласование. Для страницы 4096 проверяем p_offset mod 4096 = p_vaddr mod 4096; здесь оба остатка нулевые. В RW-сегменте байт файла 0x181234 соответствует 0x581000+(0x181234−0x181000)=0x581234. Это координата в виртуальном пространстве, а не адрес RAM на плате.

Файловые данные RW заканчиваются на 0x181000+0x9da0=0x18ada0 (конец исключён). В памяти это 0x58ada0. Дальше до 0x581000+0x408e8=0x5c18e8 должны быть начальные нули: 0x36b48 = 224072 байта. Начало нулевой части находится внутри страницы [0x58a000,0x58b000); её остаток 0x260=608 байт зануляется, следующие страницы получают анонимное нулевое содержимое. Наличие в файле отладочных байтов по более поздним смещениям не превращает их в начальное содержимое BSS: сегмент ограничен p_filesz. p_memsz и число реально затронутых физических страниц различаются.

Обычный пользователь; cwd compilerlab; compiler уже создан, readelf — существующий необязательный GNU-инструмент. Python-разборщик рядом с книгой проверяет границы файла и p_filesz≤p_memsz без исполнения ELF. Укажите путь к клону в VOLUME, сохранённый в главе 48. Код 0 ожидается у трёх строк; если readelf отсутствует, используйте вывод Python и не устанавливайте его ради чтения.

python3 -B "$VOLUME/labs/compiler-runtime/observe.py" elf "$LABROOT/out/compiler" || exit 1
if command -v readelf >/dev/null 2>&1; then
  readelf -W -h -l "$LABROOT/out/compiler" || exit 1
else
  printf 'readelf отсутствует; используйте уже полученный разбор Python\n' >&2
fi
"$LABROOT/out/compiler" maps || exit 1

Наличие readelf проверяется до вызова: при его отсутствии блок сохраняет результат Python-разбора и продолжает предусмотренное наблюдение maps. При установленном, но завершившемся с ошибкой readelf выполнение останавливается: повреждение файла не маскируется отсутствием необязательного инструмента. -B запрещает Python создавать файлы байткода. maps читает только /proc/self/maps и /proc/self/auxv собственного ребёнка. В нативном результате файловые отображения были 0x400000–0x4aa000 r-x, 0x4aa000–0x581000 r--, 0x581000–0x58b000 rw-, затем анонимный RW до 0x5c2000. Конец округлён по странице. Адреса кучи и системного стека в другом запуске могут отличаться. Здесь отсутствует PT_INTERP: перед Go нет отдельного ELF-интерпретатора. Cgo-образ с ним требует наличия указанного пути в целевой системе.

Интерпретатор динамического образа

INTERP задаёт путь к требуемому динамическому загрузчику. Если он отсутствует в минимальном контейнере, наличие самого приложения не помогает. В нашем чистом Go executable такого сегмента не было, а отдельная cgo-серия показала зависимость от libc.so.6. Эти наблюдения объясняют, почему два файла, созданные одним go build на одной машине, могут иметь разные требования к окружению.

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch53, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

Команда позволяет искать интерпретатор и сегменты. Динамические записи и NEEDED-библиотеки будут проверены командой readelf -d в главе 56 на собственном cgo-файле. Не пытайтесь по отсутствию таблицы у статического примера заключить, что readelf неисправен: у разных видов образа набор сведений различается.

Поиск библиотеки и переносимость

Имя требуемой библиотеки и путь к её фактическому файлу могут различаться. Динамический загрузчик использует правила системы и параметры образа. Не следует лечить каждый отказ глобальным изменением LD_LIBRARY_PATH: оно влияет на поиск и может подменить больше зависимостей, чем предполагалось. Сначала установите, какая библиотека требуется и каким способом её должен предоставлять целевой пакет или образ.

Версия libc и совместимость символов также имеют значение. Файл, собранный с glibc, не становится автоматически подходящим минимальной musl-среде. Если нужна такая цель, подготавливают соответствующую инструментальную цепочку и проверяют запуск в ней. В этой серии musl не использовалась, поэтому переносимость между этими средами здесь не объявлена доказанной.

Начальный стек, auxv и первая горутина

После успешного execve ядро передаёт управление входу образа с подготовленными аргументами и стеком. В этом Linux/amd64 профиле на SP лежит argc — число аргументов, далее argv — адреса строк аргументов до NULL, затем envp — адреса строк окружения до NULL и пары auxiliary vector, auxv. Это дополнительные числовые параметры от загрузки. Наше наблюдение: AT_PHDR(3)=0x400040, AT_PHENT(4)=0x38 (56), AT_PHNUM(5)=6, AT_PAGESZ(6)=0x1000, AT_BASE(7)=0, AT_ENTRY(9)=0x4807c0. Они согласуются с ELF. AT_BASE=0 здесь означает отсутствие базы отдельного интерпретатора; AT_ENTRY не является адресом пользовательской main.

_rt0_amd64_linux переходит в _rt0_amd64. Тот читает argc из 0(SP), вычисляет argv=SP+8 и передаёт их runtime.rt0_go. Далее стартовый код задаёт g0 — служебную горутину с системным стеком — и m0, запись первого системного потока; проверяет машину, вызывает args, osinit, schedinit, создаёт горутину с runtime.main через newproc и входит в mstart. Планировщик запускает эту горутину; runtime.main выполняет необходимую runtime/пакетную инициализацию, затем main.main. Пока выполняются эти действия, сам факт успешного exec ещё не подтверждает готовность HTTP-службы.

Стек входа процесса и управляемые стеки горутин поэтому не надо считать одним фиксированным объектом. g0 нужен служебному коду, пользовательская main выполняется по правилам runtime. Для внешне связанного cgo-приложения C startup входит через символ main и передаёт argc/argv по C ABI; порядок до этого места отличается. Профили PIE и C-shared также требуют своего стартового пути. Точная цепь показана в rt0_linux_amd64.s, asm_amd64.s и proc.go.

При смене исходника или флагов таблицу надо получить заново; фиксированные адреса выше принадлежат одному сохранённому артефакту. Испорченный magic либо обрезанный program header должен остановить observe.py до вычислений. Запуск чужой архитектуры и отсутствие интерпретатора диагностируют отдельно от прикладной ошибки init. Теория диапазонов и отложенных страниц уже разобрана в ОС: адресные пространства, замена образа — в жизненном цикле, сохранение открытых ссылок — в открытых файлах. Здесь связаны именно эти действия с файлами и стартом Go.

PIE и положение образа

Позиционно независимый executable допускает выбранный механизм размещения с перемещаемой базой. Это полезно для системных механизмов рандомизации адресного пространства. Но -buildmode=pie не является универсальным флагом ускорения и не заменяет проверку зависимостей. Он меняет свойства результата и иногда способ формирования адресов, что требует собственного измерения для конкретной задачи.

Выполненная проверка установила тип DYN у созданного PIE. Она не исследовала распределение адресов по серии запусков и не подтверждала все варианты поддержки на других платформах. Если требуется доказать рандомизацию, нужно отдельно наблюдать собственный процесс в контролируемой среде. Заголовок подтверждает форму файла, а не весь набор фактически включённых системных политик.

DWARF нужен для объяснения исполнения

Отладочные сведения связывают машинные адреса с исходниками, типами и местами хранения. Оптимизация делает соответствие сложнее: переменная может исчезнуть, значение переместиться, функция встроиться. Поэтому наличие DWARF не обещает отладчику простую копию исходных объектов в любой точке. Но без нужных сведений возможности подробного анализа существенно сокращаются.

Параметр linker -w отключает генерацию DWARF, а -s убирает предусмотренную таблицу символов и отладочные сведения; в используемом договоре -s подразумевает и соответствующее отключение DWARF. Явная пара -s -w часто встречается в рецептах. Она влияет на удобство диагностики и размер, а не доказывает более быстрые арифметические инструкции приложения.

Почему после удаления отладки стек ещё возможен

Runtime Go хранит необходимые ему сведения о функциях и позициях отдельно от полного набора DWARF. Поэтому облегчённая сборка может продолжать печатать полезный стек panic. Это не означает сохранения всех возможностей внешнего отладчика и не доказывает, что произвольный символический инструмент увидит тот же объём информации, что раньше.

Проверьте собственный учебный panic в обычной и облегчённой версии и сравните состав вывода. Сохраните оба результата вместе с командами. Такое расширение показывает различие механизмов на практике, но не должно смешиваться с измерением размера исходного успешного примера: изменение кода само по себе меняет набор функций и данных.

Наблюдаемость выпуска

Если распространяется облегчённый файл, команда должна заранее определить, как расследовать его сбой. Полезно хранить точный исходный коммит, параметры, toolchain, контрольную сумму и подходящие диагностические артефакты. Случайная локальная пересборка после инцидента может получить другой адресный расклад. Даже одинаковая версия продукта не гарантирует побайтное соответствие.

Отдельно учитывайте пути исходников. -trimpath помогает убрать локальное расположение, но не создаёт архив исходников и не восстанавливает их по одному имени. Для автономной работы полезно иметь проверенный набор самой книги и её учебных примеров, а для выпуска — контролируемое хранилище его свидетельств. Диагностика должна опираться на конкретный файл, а не на память разработчика.

Не исполнять неизвестное ради просмотра формата

Для определения заголовков достаточно статического чтения собственным readelf. Разбор неизвестного файла не требует его запуска. В упражнениях используются только созданные нами образцы. Инструменты, способные обращаться к загрузчику или исполнять часть процесса, выбирают осознанно; привычка запускать всё ради строки о зависимостях излишня, если нужные записи уже доступны статически.

Это также делает проверку повторяемой без изменения системы. Серия не устанавливает библиотеки, не меняет системный загрузчик и не подключается к чужим процессам. Ошибку отсутствующего компонента можно моделировать отдельным подготовленным окружением, но нельзя ради учебного опыта удалять или переименовывать системные файлы рабочего компьютера.

Когда измерять время запуска

Для короткой командной утилиты стартовая задержка может составлять значительную долю общего времени. Для долгоживущей службы она часто менее важна, чем обработка запросов. Холодное чтение с накопителя, файловый кэш, динамические зависимости и инициализация приложения влияют по-разному. Измеряйте серии запусков и отдельно определяйте, что считается началом и готовностью.

Размер файла полезен для оценки доставки и хранения. Время первого запуска и устойчивая память полезны для других решений. Удаление DWARF может помочь копированию на флэшку, но не устранить медленный init или дорогое соединение с базой. Хорошая оптимизация выбирает метрику, связанную с реальной проблемой, и проверяет соответствующую причину.

Разобрать отказ по слоям

Удобная последовательность расследования состоит из четырёх отдельных вопросов. Существует ли доступный для выполнения файл? Соответствует ли его формат и архитектура системе? Доступны ли объявленные загрузчик и библиотеки? Начал ли работать runtime и само приложение? Каждый положительный ответ переводит поиск к следующему уровню. Если приложение уже напечатало собственный init, предшествующая загрузка хотя бы для этого запуска состоялась.

Не следует одновременно менять GOARCH, CGO_ENABLED, права и набор библиотек: после успешного результата станет непонятно, что исправило исходный отказ. Сохраните отвергаемый файл и минимальное сообщение, измените один установленный фактор и повторите. Если нужна другая архитектура, сначала соберите соответствующий результат, затем проверяйте его в подходящей среде. Сам факт появления файла после cross-build не означает возможности запустить его на машине сборки.

Завершённый отчёт связывает конкретный executable с конкретной целевой системой. Он не обещает универсальной переносимости по слову Go. Такой подход экономит время при переносе на другой компьютер: необходимые условия видны заранее, а отсутствие компонента не превращается в загадочную ошибку исходного приложения.

При этом корректный запуск ещё не устанавливает прикладную готовность. Служба может после main читать конфигурацию, создавать соединения и прогревать кэши. Для сравнения времени доставки и старта полезно отдельно отмечать конец exec-подготовки и момент готовности обслужить запрос. Иначе оптимизация ELF будет оцениваться по задержке удалённой базы, а изменение сетевого окружения ошибочно приписываться linker.

Для автономного тренажёра это различие позволяет создать честный контроль: сначала запустить маленький собственный executable без внешних соединений, затем добавить заранее объявленную инициализацию. Каждый новый уровень получает отдельное наблюдение. Не требуется вмешиваться в рабочие службы системы, чтобы исследовать весь путь.
