49. SSA: значения, блоки и доказательство лишней проверки

Чтобы оптимизировать программу, компилятор переводит её в форму, где происхождение каждого значения явно, а возможные пути выполнения образуют граф. На небольшом суммировании разберём блоки, phi, зависимости памяти и удаление проверок границ. Номера узлов и порядок проходов относятся к Go 1.27.3.

Зачем присваиванию понадобилось другое представление

В исходнике переменная n может много раз получать новое значение. Для человека это удобная запись алгоритма. Для доказательства того, какое значение используется в конкретном месте, удобнее дать каждому результату отдельное имя. Static Single Assignment означает форму с единственным определением каждого именованного значения. Изменение исходной переменной представляется созданием следующего значения, а не разрушением единственного прошлого.

Такой подход упрощает поиск одинаковых вычислений, распространение констант и установление зависимости. Но SSA не является ещё одним языком, который процессор выполняет непосредственно. Это внутренний граф компилятора. В нём могут существовать операции, не имеющие отдельной машинной инструкции, а несколько узлов позднее объединяются в одну инструкцию выбранной архитектуры.

Базовый блок и поток управления

Базовый блок содержит последовательность вычислений с определённым входом и переходом в конце. У условного блока возможны разные продолжения, у выхода функции их нет. Петля образует обратное ребро графа. Такой рисунок позволяет отделить зависимость по данным от вопроса, какие вычисления вообще достижимы при данном условии.

Блоки нумеруются для удобства диагностики. Номер b3 не означает третью строку исходника и не обязан сохраняться после оптимизации. Если проход удалил ветку или разделил путь ошибки, форма графа изменится. Для сопоставления используйте смысл операции, позиции исходника и связи между узлами, а не запоминание точных номеров из чужого изображения.

Phi выбирает значение по пришедшему ребру

После if переменная может иметь результат из одной из двух ветвей. В SSA это выражается phi-узлом: его вход выбирается в зависимости от предшествующего блока. Это не обычная функция Go и не обязательный вызов во время исполнения. Поздние стадии могут реализовать выбор перемещениями, условной инструкцией или самой организацией переходов.

Поясняющий фрагмент/схема; частичное дополнение не является отдельным готовым файлом.

if flag { n = a } else { n = b }
// смысл после соединения:
// n_join = Phi(n_from_true, n_from_false)

У цикла phi часто соединяет начальное значение с результатом предыдущей итерации. Для счётчика это ноль и очередное i+1, для суммы — начальный ноль и новая сумма. Если смотреть только отдельную строку Phi без предшественников, легко перепутать, какой аргумент соответствует какому пути. Всегда сначала найдите входящие рёбра блока.

Память тоже имеет порядок зависимостей

Недостаточно отслеживать только целые числа: чтения и записи в память нельзя произвольно переставлять. Внутренняя SSA Go использует значение памяти, через которое связывает операции с соответствующими эффектами. Запись создаёт новое состояние зависимости, последующее чтение получает нужный вход. Это способ выразить порядок внутри компилятора, а не выделяемый приложением объект с названием memory.

Обычный арифметический узел может не зависеть от памяти. Вызов с побочными эффектами и запись через указатель требуют учитывать её изменение. Если компилятор доказал, что конкретная запись никем не наблюдается, её можно удалить. Но простое отсутствие чтения той же переменной по текстовому имени не является достаточным доказательством: доступ может происходить через другой указатель или вызов.

Phi на каждой итерации и зависимость от памяти

В сохраняемом compilerlab функция SumIndex имеет s=0 и i=0. Реальный SumIndex_02__prove.dump содержит b2 с предшественниками b1 и b4: v10=Phi v7 v26 для i, v31=Phi v7 v23 для s. v7 — ноль из входа; v26 — i+1 из тела; v23 — сумма из тела. Для xs={2,4,6} состояния на входе проверки цикла таковы:

Предшественник b2Выбранные i,sУсловие i<3Следующее изменение
b10,0trueLoad xs[0]=2 → s=2, i=1
b41,2truexs[1]=4 → s=6, i=2
b42,6truexs[2]=6 → s=12, i=3
b43,12falseRet 12

Аргумент Phi выбирается по ребру, по которому пришли в блок. При новом вызове граф тот же, а значения другие; компилятор не разворачивает эту таблицу до известных трёх итераций для всех срезов. На допустимом пути i неотрицателен и меньше длины; prove заменил ветвь дополнительного IsInBounds на First. В тексте после prove ещё могут временно находиться недостижимые блоки, которые удалит следующий проход.

Память тоже имеет SSA-зависимость. В Mem(p) записи *p=1; a:=*p; *p=2; return a+*p логически образуют m0→Store1→m1→Load1→Store2→m2→Load2. Нельзя объединить два Load только по равному адресу p: второй читает другое состояние памяти. После доказательства известных значений наш машинный код оставил запись 2 и результат 3. Это допустимо, потому что между действиями нет наблюдателя или вызова; добавление неизвестного вызова меняет доступное доказательство.

Для собственных дампов: обычный пользователь, cwd compilerlab, существующий lab.go и отдельный каталог reports/ssa. Код 0 подтверждает завершённую компиляцию; ошибки -d сначала сверяйте со справкой этой версии. При попадании в кэш диагностический текст мог не быть создан заново, поэтому свежему опыту назначается отдельный GOCACHE, сохраняя общий стенд.

cd "$LABROOT/projects/compilerlab" || exit 1
mkdir -p "$LABROOT/reports/ssa" || exit 1
SSA_CACHE="$LABROOT/cache/ssa-observation-01"
if test -e "$SSA_CACHE"; then
  printf '%s\n' 'Для нового опыта выберите новое имя SSA_CACHE, например ssa-observation-02.' >&2
  exit 1
fi
GOCACHE="$SSA_CACHE" GOSSAFUNC=Select GOSSADIR="$LABROOT/reports/ssa" \
"$GO" build '-gcflags=example.org/compilerlab/lab=-d=ssa/build/dump=Select,ssa/prove/dump=Select,ssa/build/dump=SumIndex,ssa/prove/dump=SumIndex,ssa/check_bce/debug=1' ./lab || exit 1

Текстовые dump создаются в cwd, HTML — в GOSSADIR; их имена печатает инструмент. Модель на схеме использует фактические v/b Go 1.27.3, но эти номера не входят в язык. Контроль Unchecked сохраняет проверку, а TestValues вызывает её с −1 и требует panic. Меняя условие на i<=len(xs), получите дополнительную плохую итерацию; исправление — вернуть строгое сравнение, а не отключить проверки через -B. Источники: prove, checkbce.

Полный опыт: безопасный цикл и произвольный индекс

В подготовленном projects/ch49 уже лежат go.mod и main.go ниже. Оба обращения к срезу должны соблюдать правила языка, но у первого граница выводится из самого цикла, а у второго индекс передаётся независимо. Различие станет видно и в диагностике, и в коде пути ошибки.

Поставленный исходник: $LABROOT/projects/ch49. Читайте его как текст файла.

package main
//go:noinline
func Sum(xs []int) int {
    n := 0
    for i := 0; i < len(xs); i++ { n += xs[i] }
    return n
}
//go:noinline
func At(xs []int, i int) int { return xs[i] }
func main() {
    println(Sum([]int{1, 2, 3}))
    println(At([]int{9}, 0))
}

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch49, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

cd "$LABROOT/projects/ch49" || exit 1
GOSSAFUNC=Sum go build -gcflags=-d=ssa/check_bce/debug -o demo . || exit 1
go tool objdump -s 'main.(Sum|At)$' demo || exit 1

Переменная GOSSAFUNC выбирает исследуемую функцию; в проверенном запуске создан файл ssa.html. Параметр -d=ssa/check_bce/debug включает специальную диагностику оставшихся проверок границ, а не общий журнал всех доказательств. Команда objdump показывает инструкции уже связанного файла, -s фильтрует имена символов регулярным выражением. Кавычки сохраняют шаблон для инструмента.

Что действительно наблюдалось

В Go 1.27.3 HTML содержал промежуточные формы с Phi и стадии нижнего преобразования. Диагностика сообщила Found IsInBounds у произвольного xs[i] в At. В инструкции Sum не требовался отдельный переход к обработчику ошибки для каждого обращения внутри корректного цикла. У At сохранилось сравнение индекса с длиной и переход в runtime.panicBounds. Именно такое имя обработчика наблюдалось в этом выпуске; старые тексты часто показывают panicIndex.

Отсутствие сообщения о Sum не означает, что доступ к памяти стал незащищённым. Компилятор получил доказательство из условий входа в тело цикла. Если i начинается с нуля, увеличивается допустимым образом и тело выполняется только при i<len(xs), соответствующее обращение удовлетворяет границе. Проверка не исчезает по желанию пользователя: её необходимость доказана другим уже существующим условием.

Проход prove и известные отношения

Доказательство может использовать факты, полученные на конкретном пути: сравнение уже выполнено, индекс неотрицателен, длина имеет нужную границу. Проход prove применяет такие отношения для упрощения условий и проверок. Но он ограничен реализацией, а не обязан решать произвольную математическую теорему о программе. Более запутанная, хотя логически эквивалентная запись иногда оставляет дополнительную проверку.

Это повод исследовать читаемость и форму входных инвариантов, а не заменять безопасный Go указателями unsafe. Выделите простой контрольный пример, изменяйте одно отношение за раз и наблюдайте, что компилятор смог доказать. Ручное дублирование проверок может облегчить доказательство в одном месте и добавить работу в другом; итог оценивается по всему пути.

Порядок проходов влияет на доступные возможности

В исходниках ssa/compile.go проверенного выпуска перечислены ранняя очистка, общие оптимизации, устранение одинаковых выражений, prove, дополнительные преобразования, удаление мёртвого кода, обработка барьеров записи, lowering и поздние проходы. Точный список длиннее этой схемы. Его смысл в том, что один проход создаёт возможности для следующего, поэтому некоторые действия повторяются после изменения графа.

Например, после доказательства ложности условия становится недостижимым целый блок, который затем можно удалить. После объединения одинаковых выражений две записи могут оказаться обращением к одному месту. Поздняя обработка видит уже машинные ограничения. Команда отключения случайного обязательного прохода не является безопасным способом «проверить быстрее»: часть проходов нужна для корректной формы результата.

Как читать ssa.html по одному вопросу

Сначала сформулируйте вопрос: откуда берётся сумма, сохранилась ли проверка или появился ли вызов. Затем найдите соответствующую позицию исходника и проследите узел через несколько стадий. Не пытайтесь сразу понять весь HTML. Для суммирования полезно начать с phi накопителя, потом найти сложение и обратное ребро. Для границы — найти сравнение длины и блок panic.

Сопоставляйте раннюю и позднюю форму. Исчезновение узла может означать константное свёртывание, замену другой операцией или удаление недостижимой ветки. Оно не обязано означать, что исходный эффект потерян. Окончательный ассемблер помогает завершить проверку, но тоже требует понимания того, как инструкции кодируют сравнение и адрес памяти.

Общие подвыражения и побочные эффекты

Если выражение x+y вычисляется дважды при неизменных входах, результаты можно объединить. Если между вычислениями изменилось место памяти, прочитанное через указатель, доказательство сложнее. Внешне одинаковые строки исходника не гарантируют одинаковое значение. Связи памяти и сведения об эффектах помогают ограничить такую оптимизацию корректными случаями.

Добавьте в собственный пример две загрузки через указатель, а между ними известную запись. Затем замените запись вызовом неизвестной по месту функции. Сначала вручную предскажите требуемый результат. После этого ищите загрузки в SSA. Такой опыт учит не выдавать каждую повторную инструкцию за промах оптимизатора: иногда повторное чтение необходимо для правильного поведения.

Удаление мёртвого кода и наблюдаемый результат

Вычисление, результат которого не влияет на требуемое поведение, может исчезнуть. Особенно легко получить такой benchmark, который создаёт локальный результат и тут же его выбрасывает. Тогда измеряется не задуманный алгоритм, а оставшаяся после оптимизации оболочка. Контрольный результат, тест правильности и чтение сгенерированного тела помогают обнаружить проблему.

Но добавление глобального указателя ради удержания результата способно изменить анализ времени жизни. Средство наблюдения должно соответствовать реальной операции. Если исследуется суммирование, сохраняйте числовую сумму. Если исследуется передача долгоживущего объекта, сохраняйте объект. Одним универсальным Sink любого типа нельзя без искажения описать все варианты.

SSA и порядок вычисления ошибок

Оптимизация должна сохранять определённое языком поведение, включая необходимые ошибки и побочные эффекты. Нельзя просто поднять произвольный доступ к элементу до проверки пустого среза, если это создаёт новый panic на допустимом пути. При чтении графа обратите внимание, какие блоки доминируют над доступом: путь к операции должен проходить через требуемые условия.

Доминирование означает, что любой путь от входа к выбранному блоку проходит через другой указанный блок. Это свойство графа помогает обосновать, что факт уже установлен до использования. Оно не говорит, какая ветка чаще исполняется; частота относится к профилю и эвристикам размещения. Правильность и вероятная стоимость являются разными осями анализа.

Изменение условия как отрицательная проверка

Измените цикл на i<=len(xs) и предскажите результат на непустом входе. Теперь последнее обращение требует ошибочного индекса, поэтому программа должна завершиться panic, если этот путь достигнут. Успешная оптимизация не имеет права сделать ошибочный алгоритм корректным суммированием по собственной догадке. Верните исходное условие после опыта и снова проверьте обе формы.

Другой вариант — обращение xs[i+1] при прежней границе i<len(xs). Оно тоже не становится безопасным от наличия цикла. Требуется другое условие или организация алгоритма. Сопоставление таких близких случаев показывает, что компилятор доказывает конкретные отношения, а не снимает проверки со всех массивных операций внутри for.

Диагностические флаги являются инструментом версии

Список -d и отдельный ssa/help следует получать у установленного compile. Имена проходов, уровень подробности и доступные способы вывода меняются. В учебном отчёте сохраняют использованную команду и версию. Если новый выпуск не принимает флаг, сначала сверяют его help, а не отключают случайный соседний проход по похожему названию.

Создание HTML добавляет диагностическую работу и большой файл. Его удобно использовать для причинного объяснения, но время такой компиляции не следует сравнивать с обычной сборкой как равные режимы. Для измерения стоимости приложения соберите отдельный файл без дампа. Для измерения стоимости компилятора отдельно определите, включена ли диагностическая запись.

От узлов к эффективности программы

Удаление проверки может уменьшить работу горячего цикла, но его влияние зависит от остальных затрат: чтения памяти, размера входа, предсказания переходов и конкуренции за ресурсы. Если цикл упирается в пропускную способность памяти, экономия одной инструкции может почти не изменить длительность. Преимущество объясняют сочетанием машинного результата и измерения, а не числом исчезнувших узлов.

Воспроизводимая серия должна включать проверку суммы, несколько длин среза и одинаковые условия запуска. Сохраняйте ns/op, число обработанных элементов и параметры сборки. Среднее время на элемент удобно для сравнения размеров, но короткие входы сильнее зависят от постоянной стоимости вызова. Не переносите вывод одного размера на всю область работы сервиса.

Почему phi не обязана остаться инструкцией

В раннем графе phi является удобным описанием выбора. Перед окончательным распределением регистров компилятор должен согласовать, в каком физическом месте находится значение на каждом входящем ребре. Иногда оба варианта уже могут использовать один регистр, иногда потребуется перемещение. Наличие phi в HTML поэтому нельзя прямо перевести в число дополнительных тактов. Сначала следует пройти до поздней формы и увидеть, какая работа действительно осталась.

У цикла ситуация особенно интересна: регистр накопителя может хранить последовательные значения суммы, хотя SSA описывала их разными именами. Это не нарушение принципа единственного определения, потому что принцип относится к промежуточному представлению, а не к вечной уникальности аппаратного регистра. После распределения регистров физическое место переиспользуется для значений, времена жизни которых позволяют это сделать.

Живость и давление на регистры

Значение считается нужным, пока существует путь до его последующего использования без подходящей замены. Чем больше одновременно нужных значений, тем труднее разместить их в конечном наборе регистров. Иногда оптимизация уменьшает число вычислений, но продлевает время жизни общего результата. Тогда экономия арифметики может сопровождаться дополнительными сохранениями. Для объяснения такого случая полезны сразу граф значений и поздний машинный результат.

Добавьте к циклу несколько независимых накопителей и убедитесь, что они используются в возвращаемом результате. Сначала ожидайте роста числа одновременно живых значений. Затем посмотрите, появились ли стековые сохранения и как изменилась длина тела. Не каждое обращение к SP означает выделение в куче: это отдельная тема организации регистров и кадра функции, которая продолжена в следующей главе.

Этот опыт следует выполнять отдельно от сравнения исходного Sum, сохраняя его как контрольную точку. Если одновременно изменить число накопителей, форму условия и тип элемента, станет трудно объяснить различие. Сильная лаборатория строится из независимых вмешательств: одно изменённое свойство, заранее сформулированное ожидание, наблюдение и честное указание того, что оно ещё не доказало.
