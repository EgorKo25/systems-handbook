52. Связыватель: как пакеты становятся одним исполняемым образом

Компилятор создаёт части программы, но адреса и состав окончательного файла определяются позднее. Проследим архивы, символы, перемещения и удаление недостижимых функций. Отдельно различим внутреннее связывание Go, внешний системный инструмент и идентификатор сборки.

Зачем нужен отдельный этап

Пакет можно скомпилировать, ещё не зная окончательный адрес каждой вызываемой функции из зависимостей. В объектном результате остаются определения, ссылки и правила последующего исправления соответствующих мест. Связыватель объединяет доступные части, определяет необходимые символы, размещает секции и подготавливает формат выбранной операционной системы. Его работа отличается от проверки типов и от запуска приложения.

Для разработчика это разделение объясняет несколько классов ошибок. Исходник может быть синтаксически и типово корректным, но требуемый символ не окажется доступен при связывании. Возможна несовместимость объектного формата или режима сборки. Наконец, успешно связанный файл может не запуститься из-за отсутствующего загрузчика системы. Последний отказ относится уже к следующей границе.

Архив пакета и объектный код Go

Архив .a является контейнером членов, используемых инструментами Go. В нём могут находиться экспортные сведения и объектный код. Собственный объектный формат Go не следует автоматически принимать за ELF только потому, что целевая платформа Linux. Формат определён в cmd/internal/goobj и понимается соответствующими инструментами компиляции, просмотра и связывания.

В проверенной версии заголовки и блоки описывают определения символов, зависимости, данные, вспомогательные сведения и перемещения. Конкретное двоичное устройство является внутренним. Для изучения используйте go tool pack, nm и objdump, а не редактирование байтов кэша. Имя файла .a описывает контейнер, но не гарантирует совместимость произвольного архива другого компилятора.

Символ задаёт именованную сущность

Символ может обозначать функцию, данные или служебную сущность. Определение предоставляет содержимое, ссылка требует найти соответствующую цель. Учитываются также сведения ABI и другие свойства. При связывании имя main.Keep помогает человеку, но внутреннее разрешение использует более богатую модель, чем простой поиск строки во всех файлах.

Вывод nm показывает тип, адрес и имя в удобной форме. Он полезен для сравнения стадий, но не является полным доказательством всех отношений. Некоторые сущности объединяются, становятся анонимнее или удаляются. После удаления таблиц символов возможности инструмента также меняются, хотя программа продолжает работать с необходимыми ей метаданными runtime.

Полный опыт с нужной и ненужной функцией

Программа и go.mod уже лежат в projects/ch52. Обе функции явно запрещено встраивать, чтобы исчезновение Dead нельзя было объяснить одним лишь раскрытием её тела. Важное различие: Keep вызывается из main, а Dead не участвует в достижимом поведении.

Поставленный исходник: $LABROOT/projects/ch52. Читайте его как текст файла.

package main
//go:noinline
func Keep(x int) int { return x + 1 }
//go:noinline
func Dead() int { return 123456 }
func main() { println(Keep(7)) }

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch52, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

cd "$LABROOT/projects/ch52" || exit 1
go tool compile -p main -pack -o main.a main.go || exit 1
go tool nm main.a || exit 1
go build -o demo . || exit 1
go tool nm demo || exit 1

Параметр -p задаёт идентичность компилируемого пакета, -pack выбирает архивный результат, -o задаёт новый файл. В выполненной серии аналогичная Dead присутствовала в архиве compile и отсутствовала в окончательном executable, тогда как вызываемая функция сохранялась. Это прямое сравнение стадий показывает работу связывателя, а не предположение по одному отсутствующему имени.

Достижимость определяет необходимый набор

Связыватель начинает с нужных корней и следует по ссылкам. Для обычной программы важны вход исполнения, main, инициализация и специальные требования runtime. Если функция не достигается из нужного набора и не обязана сохраняться по дополнительным правилам, её код может быть исключён. Такой проход уменьшает файл и иногда время загрузки, но не меняет смысл достижимых операций.

Отражение, методы интерфейсов, режимы библиотек и экспортируемые входы усложняют граф. Поэтому «нигде не написан прямой вызов» ещё не означает ненужность функции. Реализация deadcode.go учитывает дополнительные отношения. Для исследовательского примера достаточно простой функции без таких связей, а для реального размера проекта требуется понять, что удерживает конкретный символ.

Перемещение исправляет зависимое место

Relocation, или перемещение, описывает место данных или инструкции, которое нужно скорректировать после выбора расположения цели. Например, вызов может требовать относительного смещения до функции, а таблица — адреса данных. Связыватель получает тип операции, цель и добавку, затем формирует нужное значение с учётом архитектурных ограничений.

Это не копирование исходного файла в другую директорию. Термин относится к зависимости машинного содержимого от размещения. Некоторые перемещения разрешаются при окончательном связывании, другие могут потребовать обработки загрузчиком в динамической программе. Конкретный набор зависит от формата, режима и внешних библиотек. Успешное обычное связывание не доказывает отсутствия всех будущих динамических действий.

Одна relocation и вычисление окончательной цели

Здесь используем другой поставленный пример: $LABROOT/projects/compilerlab/lab/lab.go, где Across вызывает Mix; это не функции из ch52/main.go. Следующие адреса относятся к сохранённому авторскому наблюдению одного бинарника Go 1.27.3. В compiler -S вызов Mix внутри Across ещё содержит нулевые четыре байта смещения и запись rel 25+4 t=R_CALL …Mix+0. Число 25 — смещение поля relocation от начала Across, длина 4 — размер исправляемого поля. Оно следует за opcode E8 на смещении 24. После размещения linker записал в нашем ELF по 0x48c938 байты e8 83 ff ff ff. Little-endian int32 FFFFFF83 равен −125. CALL rel32 считает цель относительно следующей инструкции: 0x48c938+5−125=0x48c8c0, то есть адрес Mix из nm. Изменение расположения функции меняет это поле, сохраняя связь с символом.

У нового flaglab main.go импортирует fmt. Самостоятельный compile без importcfg закономерно отказывает «could not import fmt»: у него нет задания построить дерево зависимостей. Успешная прямая цепочка сначала просит драйвер подготовить экспортные архивы. Обычный пользователь, cwd $LABROOT/projects/flaglab, выходы исключительно в своём out; ожидается 0. Ошибка любого шага останавливает цепочку.

cd "$LABROOT/projects/flaglab" || exit 1
"$GO" list -deps -export -f '{{if .Export}}packagefile {{.ImportPath}}={{.Export}}{{end}}' . >"$LABROOT/out/importcfg" || exit 1
"$GO" tool compile -p main -pack -importcfg "$LABROOT/out/importcfg" \
  -o "$LABROOT/out/main.a" main.go || exit 1
"$GO" tool nm "$LABROOT/out/main.a" || exit 1
"$GO" tool link -importcfg "$LABROOT/out/importcfg" -o "$LABROOT/out/flag-direct" "$LABROOT/out/main.a" || exit 1
"$LABROOT/out/flag-direct" || exit 1

Вывод dev 22 проверяет этот файл. Keep и Dead присутствуют в пакетном архиве; в executable Keep достижима из main, Dead не нужна. Рёбра инициализации и сведения интерфейсов тоже могут удерживать код: поиск текстового CALL в main не заменяет граф linker. Уменьшение текста способно уменьшить размер и работу загрузки, но время запуска зависит также от init, отображений и ввода-вывода.

Отдельный отказ без подготовленных runtime-архивов можно получить, указав link только main.a без importcfg. Неудачный выход не делает старый executable новым и не является поводом переименовать его в выпуск. Исправление — вернуть подготовленный importcfg, сохраняя версию/GOOS/GOARCH. Внешний режим исследуется после главы cgo с уже имеющимся GCC, а не командой установки системных библиотек. Формат перемещений закреплён objabi, расчёт amd64 — link/amd64.

Символ main.Caller в модели начинается на 0x401000. Запись Go R_CALL задаёт смещение поля от начала этого символа Off=0x11, размер Size=4, цель main.Keep и добавку Add=0. Адрес цели S известен после размещения. Процессор AMD64 считает относительный переход от следующей инструкции, то есть от конца четырёхбайтного поля P. Go linker вычисляет S + Add − (P + 4) и проверяет, помещается ли результат в знаковое 32-битное число. На рисунке записывается 107: 6b 00 00 00. Это те же четыре байта по file 0x1011…0x1014; opcode e8 по 0x1010 остаётся прежним. Если разместить Keep на 16 байт дальше, значение станет 123 = 0x7b и поле — 7b 00 00 00. Неисправленное нулевое поле в такой модели указывало бы на следующую инструкцию, а не на Keep.

Кто выполняет исправление. При внутреннем связывании обычного случая это делает Go linker. Внешний режим создаёт промежуточный go.o и передаёт нужные оставшиеся перемещения системной цепочке; он не обязывает оставлять внешнему инструменту каждый вызов внутри уже известной секции. Для переданного наружу AMD64 R_CALL к обычному ELF-символу обработчик выбирает R_X86_64_PC32. Формула ELF использует адрес начала поля P; добавка −4 учитывает его длину и даёт ту же разность. Динамически импортированная функция может идти через R_X86_64_PLT32: PLT — таблица промежуточных переходов к функциям динамических библиотек. Этот отдельный путь на рисунке не изображён. Поэтому Go-перемещение в пакетном объекте, запись перемещения в промежуточном ELF и исправленные байты окончательного файла — разные представления одного связывания. Подробности сверены с relocsym Go 1.27.3, elfreloc1 AMD64 и hostlinksetup; это сверка исходников, не новый native run.

Порядок размещения и адреса

Секции кода и данных получают адреса с нужным выравниванием и разрешениями. Отдельно создаются таблицы, необходимые runtime, отражению и диагностике. Изменение состава зависимостей может сдвинуть адрес ранее неизменённой функции. Поэтому адрес в одном objdump удобен для этого файла, но не является долговечным идентификатором исходной операции.

При сопоставлении профиля с двоичным файлом нужен именно соответствующий результат сборки. Похожий исходник или та же версия программы без точного файла могут дать неверное разрешение адресов. Сохранение идентификатора и артефакта является частью практической наблюдаемости, а не необязательным дополнением к сборке.

Внутреннее и внешнее связывание

Внутренний режим означает, что Go linker сам выполняет предусмотренную работу окончательного связывания. Во внешнем он взаимодействует с системным linker и компиляторной цепочкой платформы. Необходимость зависит от целевой системы, режима и используемых внешних объектов. Наличие cgo не следует объяснять правилом «всегда вызывается один и тот же внешний ld» без проверки фактического запуска.

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch52, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки. C/GCC должен уже существовать; иначе пропустите внешний режим, ничего не устанавливая.

cd "$LABROOT/projects/ch52" || exit 1
go build -x -o demo . || exit 1
CGO_ENABLED=1 CC=gcc go build -ldflags=-linkmode=external -o demo-external . || exit 1

Первый -x показывает организацию команд. Во втором -ldflags передаёт параметр linker, а -linkmode=external явно выбирает внешний режим. В серии он реально проверен на отдельной cgo-программе с GCC. Для чистого примера без настроенной внешней цепочки такой запрос может потребовать дополнительные компоненты; не обещайте его успешность на любом компьютере.

Режим сборки меняет договор результата

Обычное приложение, позиционно независимый executable и библиотека для C имеют разные требования к экспорту, входу и размещению. Параметр -buildmode выбирает такой договор, а не просто косметическую упаковку одних байтов. Поддержка конкретного режима зависит от платформы и инструментария. Список доступных вариантов следует сверять с установленным Go и целевой системой.

Например, файл c-shared предназначен для взаимодействия через определённый внешний интерфейс и требует корректного окружения загрузки. Его нельзя считать обычным executable с переименованным расширением. Аналогично plugin имеет ограничения совместимости и связывания, которые не исчезают от совпадения имени пакета. Учебная серия здесь проверяла обычный executable, PIE и внешний режим cgo, а не все библиотечные формы.

Build ID и контрольная сумма отвечают на разные вопросы

Build ID — идентификатор, используемый инструментами сборки и результатами Go для связи стадий и артефактов. Его можно посмотреть через go tool buildid demo. Он полезен при поиске соответствующей сборки, но не заменяет выбранную криптографическую контрольную сумму всего распространяемого файла и политику доверия к нему. Изменение файла нужно проверять тем свидетельством, которое охватывает требуемые байты.

Обычный пользователь, подготовленный личный стенд из главы 48; cwd $LABROOT/projects/ch52, входы приведены выше и поставлены в fixtures. Ожидается код 0 у каждой команды. При ненулевом коде остановитесь, сохраните stderr и исправьте указанный вход; прежний бинарник не считается результатом новой сборки.

cd "$LABROOT/projects/ch52" || exit 1
go tool buildid demo || exit 1
go version -m demo || exit 1

Первая команда в опыте вернула непустой идентификатор. Вторая показывает доступные сведения о версии и сборке. Это удобно для расследования, но не устанавливает автоматически, кто собрал программу и из какого доверенного источника пришёл файл. Для такой связи нужны происхождение сборки и проверяемая цепочка публикации.

Повторное использование кэша

Не каждый go build повторяет compile и link. Организатор сборки сравнивает значимые входы и использует подходящие результаты. Поэтому время второго запуска может быть значительно меньше без какого-либо ускорения самого связывателя. Для измерения разделяйте холодное построение, повторную сборку и запуск уже готового файла. Флаг -x помогает понять, какие процессы реально выполнялись.

Ручное удаление личного кэша ради опыта не требуется. Достаточно направить GOCACHE в отдельный временный каталог и сравнить его первый и следующий прогоны. В нашей серии также изолированы GOMODCACHE и GOPATH, а сетевое получение выключено. Все зависимости примеров — стандартная библиотека и собственные файлы.

Данные инициализации тоже удерживают код

Пакет может выполнять init, даже если его отдельные экспортированные функции не вызываются напрямую из main. Связь инициализации делает часть кода необходимой. Удаление неиспользуемой функции не даёт права удалить требуемый побочный эффект импортированного пакета. Это объясняет, почему простой подсчёт явных вызовов main не предсказывает полный состав executable.

Для самостоятельного опыта добавьте пакет с init, печатающим учебную метку, и импортируйте его по установленным правилам. Сначала проверьте наблюдаемый запуск, затем исследуйте символы и задачу инициализации. Такой пример соединяет переднюю часть компилятора с поздним графом достижимости и показывает, почему метаданные пакета являются частью итоговой программы.

Ошибки undefined и duplicate

Неопределённый символ означает, что требуемая цель не разрешена в предоставленном наборе и правилах связывания. Причиной может быть отсутствующий внешний объект, неправильный режим, несовпадающее имя или несовместимая организация ABI. Начинайте с полного имени, этапа и фактических команд. Изменение исходной функции наугад может скрыть, но не объяснить причину.

Дублирующее определение указывает на другой класс проблемы: несколько источников предлагают конфликтующие сущности. Для смешанной сборки это бывает связано с повторным включением C-объекта или определением в заголовке. Отдельно проверьте, какие файлы созданы и кем переданы linker. Список исходников Go не всегда описывает все внешние входы.

Удаление отладки и реальные размеры

Параметры -s и -w управляют удалением определённых символических и отладочных сведений. В проверенной машине вариант с -ldflags='-s -w' был меньше обычного. Это не означает удаления всего, что помогает runtime строить стек: программе сохраняются необходимые собственные метаданные. Подробно формат ELF и роль DWARF разобраны в следующей главе.

Размер файла, объём виртуального отображения и фактически занятые физические страницы различаются. Экономия на диске может быть полезна для доставки, но не обязана в той же пропорции снижать рабочую память. Если цель — уменьшение RSS службы, измеряйте её после запуска на определённой нагрузке и объясняйте состав памяти отдельно от контейнера executable.

Практическая оценка эффективности связывания

Для большого проекта фиксируйте количество пакетов, объём входных объектов, выбранный режим, версию и параметры. Измеряйте пиковую память и длительность linker отдельно, если именно он стал ограничением сборки. Одно большое значение времени go test может быть выполнением тестов или компиляцией стандартной библиотеки в свежем кэше, а не связыванием.

Не добавляйте случайные флаги ради уменьшения числа секунд без понимания результата. Потеря диагностических сведений, смена внешней цепочки и изменение режима влияют на дальнейшую эксплуатацию. Выбирайте изменение по цели: размер доставки, скорость сборки, требования совместимости либо удобство расследования. Для каждой цели нужен свой проверочный критерий.

Два разных вида удаления

Сравните отсутствие Dead и отсутствие .debug_info после другой сборки. В первом случае удалён ненужный для исполнения код. Во втором удалено определённое вспомогательное описание уже существующего кода. Это разные действия над разными частями результата. Программа может содержать полезную функцию без полной отладочной информации или сохранять отладочную информацию только для достигнутого набора функций.

Такое разделение помогает сформулировать политику выпусков. Можно хранить полную диагностическую сборку в контролируемом хранилище и распространять облегчённый вариант, но тогда нужно доказать соответствие артефактов и способ расследования. Нельзя просто взять похожий файл, собранный позже с другими параметрами, и считать его точным источником адресов прежнего процесса. Идентификатор, исходники и рецепт должны сохранять проверяемую связь.

Рефлексия как причина неожиданного удержания

Когда код работает с методами через отражение, linker должен учитывать возможность вызовов, которые не видны простым поиском прямой инструкции CALL в main. В проверенной реализации для этого есть отдельные сведения о достигнутых типах и методах. Это не означает, что любая рефлексия обязательно сохраняет всю программу; точный эффект зависит от доступных доказательств и используемых операций.

Для исследования размера начните с собственного минимального типа с несколькими методами и постепенно добавляйте конкретный отражательный доступ. Сравните таблицу символов до и после, сохранив одинаковый режим. Если цель — уменьшить реальное приложение, найдите удерживающую связь, а не удаляйте импорт только потому, что он кажется большим. Содержательный результат должен объяснять, какая возможность вызова исчезла и почему теперь код допустимо исключить.

Для каждого вывода сохраняйте точный набор входов и стадию наблюдения. Архив пакета, готовый файл и образ запущенного процесса представляют разные состояния одной сборочной цепочки.
