46. Передняя часть компилятора: как текст становится проверенной программой

Между файлом main.go и машинными инструкциями существует несколько разных представлений. Разберём, какое из них отвечает за синтаксис, какое знает типы, как компилятор читает зависимости и почему компилятор обрабатывает пакет целиком. Внутренние имена и порядок стадий относятся к исходникам Go 1.27.3.

Подготовленные входы этой главы

Нужен личный стенд главы 14 и его env.sh. В новом терминале сначала прочитайте этот файл через source, затем выполните cd "$LAB/fixtures/front". Здесь уже есть go.mod с module example.invalid/front, main.go, lib/lib.go, sample/sample.go и cmd/inspect/main.go. Имя example.invalid обозначает собственный модуль: из сети он не получается. go 1.25.0 задаёт минимальные правила модуля, исполняемый комплект остаётся 1.27.3. Не выполняйте go build . в корне service: там нет Go-файлов корневого пакета, только подкаталоги.

Первые команды читают эти файлы и создают бинарник front в текущем личном каталоге. При ненулевом коде не запускайте оставшийся бинарник. Ошибки версии исправляются выбором установленного Go, ошибки пути — переходом в существующий front; go mod init в случайном каталоге здесь не нужен.

Сначала выбрать правильный уровень наблюдения

Команда go build выполняет работу организатора сборки. Она выбирает файлы по целевой системе и ограничениям сборки, определяет граф импортов, ищет результаты в кэше и запускает необходимые инструменты. Команда compile получает уже выбранные исходники одного пакета и сведения о зависимостях. Поэтому строка «компилятор не нашёл пакет» может скрывать ошибку организации входов, а не ошибку языка. Прямой запуск go tool compile над произвольным main.go не повторяет автоматически всю работу go build.

Полезная модель начинается с разделения трёх вопросов: какие файлы участвуют, допустим ли их совместный смысл и какой машинный код этому смыслу соответствует. Изменение GOOS может исключить файл раньше синтаксического разбора. Неверное выражение в исключённом файле не доказывает, что компилятор умеет его принимать. Для воспроизводимого опыта записывайте версию инструмента, целевую архитектуру, команду и фактический список исходников.

go version
go env GOOS GOARCH GOTOOLCHAIN
go list -f '{{.GoFiles}}' .
go build -x .

version показывает выбранный инструмент, env — значимые параметры, list — файлы выбранного пакета. Параметр -x печатает запускаемые команды, но кэш может исключить запуск compile при повторной сборке. Отсутствие строки компилятора в таком выводе не означает, что исходник исполнился без компиляции: подходящий результат мог быть получен раньше.

Лексемы: смысл не равен последовательности символов

Лексический анализ превращает байты исходника в последовательность лексем: имён, ключевых слов, литералов, операторов и разделителей. Позиция каждой лексемы нужна для диагностики. Текст внутри строкового литерала не становится оператором только потому, что содержит знак плюс. Комментарий обычно не участвует в выражении, но определённые директивы и ограничения сборки имеют специально установленный смысл для инструментария.

Автоматическая вставка точек с запятой объясняет некоторые ошибки переноса строки. Это правило языка, применяемое при разборе лексем, а не догадка редактора о красивом оформлении. Если открывающая фигурная скобка поставлена после неожиданного переноса, сообщение о синтаксисе может указывать на место, где последовательность уже невозможно продолжить. Исправление стоит начинать с первой ошибки и ближайшего предшествующего контекста, поскольку последующие сообщения нередко являются её следствием.

Синтаксическое дерево описывает форму

Парсер распознаёт объявления, выражения и операторы по грамматике. Абстрактное синтаксическое дерево (abstract syntax tree, AST) сохраняет их вложенность: у сложения есть левый и правый операнды, у вызова — вызываемое выражение и аргументы, у функции — параметры и тело. Сам факт существования корректного узла сложения ещё не определяет, можно ли складывать данные операнды. Это задача следующего уровня.

В Go 1.27.3 компилятор использует внутренний пакет cmd/compile/internal/syntax. Наличие доступных библиотек go/parser и go/ast не означает, что стандартный компилятор строит именно их структуры. Эти публичные библиотеки удобны для инструментов анализа исходников, но внутренние структуры могут развиваться независимо. Утилита, показывающая go/ast, демонстрирует полезное дерево языка, а не гарантированный снимок памяти compile.

Один текст в трёх представлениях

Откройте sample/sample.go. Его третья строка — var Answer = Twice(3) + 1. Байт + — ASCII 0x2B; число 3 записано байтом 0x33, а не двоичным целым значением 3 в машинном регистре. Сканер выдаёт на строке 3 лексемы var, имя Answer, =, имя Twice, (, целочисленный литерал 3, ), +, литерал 1 и вставленную точку с запятой. Их позиции начинаются с колонки 1, 5, 12, 14, 19, 20, 21, 23 и 25. Вставленная точка с запятой имеет текст новой строки: исходник не обязан содержать её отдельный байт.

Дерево правой части имеет корень BinaryExpr(+), слева CallExpr(Twice, 3), справа BasicLit(1). Имя Twice разрешается в объявленную функцию func(n int) int. Нетипизированный литерал 3 допустим как int-аргумент; результат вызова имеет тип int, поэтому 1 также допустима справа сложения, а Answer выводится как int. Вызов пользовательской функции не является константным выражением языка: хотя мы понимаем, что ответ равен 7, у него нет compile-time constant value в таблице go/types. Если написать const Answer = Twice(3) + 1, компилятор отклонит такой инициализатор константы.

В том же front запустите публичный инструмент ниже. go/scanner, go/parser и go/types принадлежат стандартной библиотеке; исходник утилиты доступен в cmd/inspect/main.go. Она печатает позиции лексем, определения/использования имён и вычисленные типы. Последовательность AST → проверенные сведения удобна для чтения; структуры внутреннего compile показаны отдельно в объяснении Types2.

go run ./cmd/inspect sample/sample.go

Ожидаются строки def Answer -> var example.invalid/front/sample.Answer int, call type=int constant=<nil> и binary + type=int constant=<nil>. Здесь <nil> означает отсутствие константного значения у выражения в инструменте, а не значение переменной Answer. Измените литерал 3 на 4: дерево и типы сохранятся, текст лексемы изменится, а при исполнении соответствующего выражения получится 9. Затем верните файл из сохранённого образца. Замена 3 на строку "3" сохранит форму вызова, но проверка типов отклонит аргумент; до машинных инструкций этот вход не дойдёт.

Имена, области видимости и типы

После распознавания формы нужно установить, на какой объект ссылается каждое имя. Объявленная внутри функции переменная может затенить пакетное имя. Использование имени до подходящего объявления, повторное объявление и несовместимое присваивание относятся к разным правилам. Таблица областей видимости связывает имена с объектами, а сведения о типах позволяют проверить допустимость операций и вызовов.

Компилятор не обязан запускать программу, чтобы отклонить var Number int = "text". Он знает объявленный тип переменной и тип выражения справа и проверяет правило присваивания. При этом выражение с корректными типами всё ещё может завершиться panic во время исполнения, например при обращении по динамическому индексу вне длины среза. Успешная проверка типов обеспечивает определённый набор гарантий, но не доказывает произвольную бизнес-логику.

// type.go
package bad
var Number int = "text"

// отдельный файл syntax.go
package bad
func Broken( { }

Эти входы уже сохранены раздельно как $LAB/fixtures/cases/type.go и syntax.go. Компилируйте каждый отдельно, из front, с явным новым выходом: go tool compile -o "$LAB/out/type.o" "$LAB/fixtures/cases/type.go" и аналогично syntax.go → syntax.o. Оба вызова должны вернуть ненулевой код; сразу после каждого в Bash echo $? показывает код последней команды. Не запускайте go build над всем каталогом cases: он намеренно содержит несколько независимых ошибок. В выполненной проверке go tool compile type.go отклонил несовместимое значение, а compile syntax.go сообщил синтаксическую ошибку. Эти два отрицательных опыта важны: они показывают разные границы обработки, хотя обе команды возвращают ненулевой код и не создают пригодный результат.

Почему перенос скобки меняет результат

В cases/semicolon.go после func Broken() стоит перевод строки, а { начинается на следующей. После ) сканер вставляет точку с запятой ;, для объявления функции такая последовательность перед телом недопустима. Отдельный вызов go tool compile -o "$LAB/out/semicolon.o" "$LAB/fixtures/cases/semicolon.go" должен завершиться синтаксической ошибкой. Перенос { на строку сигнатуры устраняет её. Сохраните исправленную копию в out/semicolon-fixed.go, скомпилируйте её с новым выходом и сравните коды: 0 означает, что данный минимальный пакет принят. Исправление не требует менять тип Number в другом отрицательном примере.

Types2 и внутренние типы компилятора

В исходниках проверенного выпуска первая полная проверка использует types2 вместе с внутренним синтаксическим деревом. Сведения включают определения, использования, выбранные методы, области и подстановки параметров типов. Они нужны не только для сообщений об ошибках: последующие преобразования должны знать, какое действие соответствует каждому выражению. Например, одинаково написанное индексирование карты и среза требует разной реализации.

Дальнейшие стадии работают со своими структурами ir и types. Переход нельзя представлять как простое переименование AST. При нём создаются дополнительные узлы, сведения об операциях и связи, удобные для оптимизации. В Unified IR используется сериализованное представление проверенного кода. Это позволяет согласовать загрузку пакетов, тел функций и сведений, необходимых для встраивания и обобщённых функций.

Пакет как единица компиляции

Несколько файлов одной директории обычно образуют один пакет. Они совместно объявляют пакетные объекты, хотя импортированные имена имеют файловую область. Перенос import из одного файла в другой не делает короткое имя пакета автоматически видимым во всех соседних файлах. Именно поэтому ошибка undefined может появиться после механического разбиения файла, даже когда граф зависимостей проекта остался прежним.

Компилятор проверяет совместный набор выбранных файлов. Дублирующее объявление может находиться в другом файле, который добавился из-за целевой платформы или флага tags. При расследовании следует сначала получить список файлов и проверить ограничения, затем искать конфликт имён. Иначе чтение только открытого редактором main.go создаёт ложную картину входа компилятора.

Импорт переносит знания, а не исполняет библиотеку

Чтобы проверить обращение к переменной lib.Value, компилятору нужны сведения об экспортированном имени и его типе. Для эффективного последующего кода могут понадобиться тела подходящих для встраивания функций, информация об утечке параметров и тела обобщённых функций для будущей конкретизации. Скомпилированный пакет поэтому содержит больше, чем машинные инструкции. Export data — специально предназначенные для других компиляций сведения.

Чтение этих данных при сборке не является исполнением init импортируемого пакета. Инициализация относится к запуску уже построенной программы. Компилятор и организатор сборки работают со своими файлами и процессами; приложение начинает собственный жизненный цикл позже. Разделение особенно полезно при разборе сообщения, появившегося во время go run: эта команда сначала собирает, а потом запускает результат.

Рабочий каталог остаётся $LAB/fixtures/front. Первая строка готовит архив зависимости и сохраняет напечатанный путь в переменную Bash; кавычки во второй сохраняют его одним аргументом. Файлы в кэше только читаются.

archive="$(go list -export -f '{{.Export}}' ./lib)"
go tool pack t "$archive"

Флаг -export просит подготовить сведения экспорта, а шаблон выводит путь к соответствующему результату. В опыте архив содержал __.PKGDEF. Это наблюдение формата конкретного инструментария, а не приглашение изменять файлы кэша вручную. Имена служебных членов и двоичное кодирование не являются стабильным пользовательским интерфейсом для самостоятельного редактирования.

Полный небольшой опыт с инициализацией

В подготовленном front уже лежат два следующих файла. Откройте их перед запуском и сопоставьте объявления с кодом; при ручном создании используйте тот же go.mod с go 1.25.0. В подкаталоге lib находится первый файл, в корне — второй. Адрес example.invalid здесь только имя собственного модуля; загрузки из сети не требуется.

// lib/lib.go
package lib
var Value = initialize()
func initialize() int { println("lib-var"); return 7 }
func init() { println("lib-init") }

// main.go
package main
import "example.invalid/front/lib"
var X = initialize()
func initialize() int { println("main-var"); return lib.Value }
func init() { println("main-init") }
func main() { println("main", X) }

Перед запуском предскажите, может ли main-var появиться раньше lib-init. Затем выполните go run . В проверке Go 1.27.3 порядок был lib-var, lib-init, main-var, main-init, main 7. Встроенная println предназначена здесь для маленького наблюдения; её поток и формат не следует превращать в интерфейс прикладного журнала. В автоматическом опыте этот вывод читался из стандартного потока ошибок.

Смысл последовательности в зависимости пакетов: импортируемый пакет инициализируется раньше импортирующего. Внутри пакета учитываются зависимости пакетных переменных, затем выполняются init-функции. Нельзя распространять этот пример на произвольный порядок отдельных объявлений в разных файлах, не разобрав правила зависимости и порядок передачи файлов инструменту. Цикл инициализации является ошибкой, а не просьбой к runtime выбрать удачный случайный порядок.

Сгенерированная задача инициализации

В проверенных исходниках gc/main.go вызывает построение задачи инициализации пакета после обработки встраивания и до дальнейшей генерации. Это помогает связать правило языка с механизмом: в двоичном результате существуют сведения и функции, обеспечивающие нужный порядок запуска. Не каждый исходный инициализатор обязан превратиться в самостоятельный вызов: статически вычислимые данные могут быть размещены непосредственно в образе.

Добавьте вычисление простой константы и сравните его с вызовом initialize, имеющим побочный эффект печати. Оптимизация вправе упростить первое, но обязана сохранить наблюдаемый эффект второго. При чтении ассемблера задавайте вопрос о требуемом поведении, а не ищите обязательное взаимно однозначное соответствие каждой строке исходника. Между ними уже произошли проверки и преобразования.

Позиции, trimpath и диагностика

Позиции исходника проходят через разные представления, чтобы ошибка, стек и отладчик могли вернуться к понятному месту. Но путь в двоичном файле не обязан совпадать с абсолютным путём разработчика. Параметр сборки -trimpath убирает определённую зависимость результата от локального расположения. Это влияет на воспроизводимость и сведения об исходниках, а не отменяет необходимость хранить сам текст для расследования.

Директива //line способна изменить сообщаемое логическое расположение. Поэтому странный путь в сообщении иногда связан со сгенерированным кодом, а не с тем, что компилятор тайно прочёл неизвестный файл. Проверьте фактические входы, генератор и директивы до поиска в файловой системе. Сгенерированный исходник остаётся входом компилятора и должен удовлетворять тем же проверкам языка.

Как исследовать собственный пакет без шума всей библиотеки

Флаги -gcflags передаются компилятору, но область их применения имеет значение. Запрос all=... затрагивает зависимости и может породить огромный журнал. Для первого исследования выбирайте конкретный пакет. Вариант -gcflags=-W печатает внутреннее представление после проверки, а -m=2 объясняет некоторые решения оптимизации. Состав вывода является диагностикой версии, поэтому автоматический тест не должен без необходимости сравнивать весь текст побайтно.

При ошибке импорта прямого compile выясните, нужен ли importcfg и подготовленный архив зависимости. Для обычной разработки проще позволить go build организовать эти входы. Прямой инструмент полезен в минимальном опыте без импортов или при осознанном воспроизведении команды из -x. Добавление случайных каталогов и копирование архивов разных версий способно создать несовместимость, которую неверно принять за ошибку исходного Go.

Эксперимент с циклом и границей видимости

После успешного запуска измените только пакетные объявления: пусть X вычисляется через Y, а Y через X. Сначала нарисуйте две стрелки зависимости и сформулируйте, с какой переменной вообще можно начать. Ответа нет, поэтому ожидается ошибка инициализационного цикла при сборке. Такой отказ отличается от бесконечной рекурсии функции во время исполнения: до запуска приложения дело здесь не доходит. Верните исходный файл после наблюдения, чтобы следующие опыты не наследовали специально созданную ошибку.

Теперь перенесите обращение к переменной lib.Value в новый файл main_extra.go и оставьте import только в main.go. Пакетное имя X остаётся общим для файлов, а короткое импортированное имя lib в новом файле не появляется. Добавление собственного import исправляет видимость. Если редактор автоматически добавил его за вас, сравните сохранённые байты перед запуском: иначе автоматическая помощь скроет исследуемый механизм. Эти два изменения дают независимые отрицательные проверки правил, которые успешный первоначальный пример сам по себе не демонстрировал.

В следующем варианте добавьте файл с ограничением сборки для другой операционной системы и повторите go list. Убедитесь, что файл отсутствует среди выбранных входов на текущей платформе. Из этого нельзя заключать, что содержащийся в нём текст проверен. Полезная стратегия проекта — отдельно собирать существенные целевые наборы, а не считать единственный успешный локальный запуск доказательством корректности всех сочетаний файлов.

Совместимость языка и совместимость данных инструментов

Строка go в go.mod влияет на применимые правила языка и работу инструментария, но не превращает произвольные архивы разных компиляторов в совместимые. Экспортные сведения содержат внутренний формат, рассчитанный на соответствующий набор инструментов. При переносе готового кэша недостаточно совпадения имени пакета. Организатор сборки учитывает входы и версию, а ручное смешивание файлов обходит эту проверяемую связь.

Различайте также ошибку версии языка и отсутствие самого toolchain. В первом случае существующий compile понимает вход, но применяет заданные ограничения. Во втором нужная программа ещё не выбрана или недоступна. Переменная GOTOOLCHAIN=local в автономном опыте запрещает незаметно заменить исследуемый инструмент автоматически загруженным. Это делает отказ содержательным: читатель видит реальную границу установленной версии и может сопоставить её с исходниками книги.

Стоимость передней части и границы вывода

Большие графы типов, многочисленные конкретизации и объёмные экспортные сведения увеличивают работу даже до генерации инструкций. Измеряйте холодную сборку отдельно от повторного использования кэша, а время компиляции пакета — отдельно от связывания и запуска тестов. Один медленный go test не доказывает дорогой парсер: значительная часть времени могла уйти на выполнение самих тестов.

Проверочный маршрут заканчивается конкретными свидетельствами: выбранные файлы известны, синтаксическая и типовая ошибки различены, экспортный архив найден, порядок инициализации наблюдён. Это фундамент следующих глав: сначала программа получает определённый смысл, затем компилятор ищет более эффективную реализацию этого смысла. Ни скорость, ни отсутствие panic не следуют из одного факта успешной передней проверки.

Первоисточники версии: syntax, types2, noder и Unified IR, порядок стадий, правила инициализации языка. Опыты выполнены на Linux amd64; внутреннее представление не является обещанием совместимости между выпусками.
