55. PGO: как профиль исполнения становится входом следующей сборки

Компилятор видит возможные пути, а профиль показывает, какие из них были частыми на конкретной нагрузке. Profile-guided optimization использует это свидетельство при выборе преобразований. Разберём сбор собственного CPU-профиля, default.pgo, проверку результата и ошибки переноса выводов между нагрузками.

Профиль сообщает частоту, а не меняет смысл

Без сведений исполнения компилятор использует статические доказательства и эвристики. Профиль добавляет информацию о горячих функциях и связях вызова. Это может изменить решения о встраивании и других оптимизациях, но не даёт разрешения нарушить правила языка на редко наблюдавшемся пути. Редкая ветка остаётся допустимой частью программы, даже если за время записи она не встретилась.

PGO не является автоматическим запоминанием результата прошлых запросов и не заменяет прикладной кэш. Профиль используется во время новой сборки, а созданный executable затем работает обычным образом. Поэтому результат должен хранить связь с использованными исходниками и профилем как дополнительным входом. Отсутствующий или неожиданно заменённый профиль способен изменить машинный результат без изменения Go-файлов.

Полный пример с контролируемой горячей функцией

В новом модуле example.invalid/profile сохраните main.go и main_test.go. Здесь Work выполняет известную вычислительную работу и удерживается отдельной функцией ради устойчивого наблюдения в профиле. Пример специально не изображает реальную службу и не открывает сетевой диагностический интерфейс.

// main.go
package main
var Sink uint64
//go:noinline
func Work(x uint64) uint64 {
    for j := 0; j < 1000; j++ { x = x*1664525 + 1013904223 }
    return x
}
func main() {
    for i := 0; i < 1000; i++ { Sink = Work(uint64(i)) }
    println(Sink)
}

// main_test.go
package main
import "testing"
func BenchmarkWork(b *testing.B) {
    for b.Loop() { Sink = Work(Sink) }
}
go test -run='^$' -bench=BenchmarkWork -benchtime=400ms -cpuprofile=cpu.pprof
go tool pprof -top -nodecount=8 cpu.pprof

-cpuprofile записывает CPU-профиль собственного тестового процесса. -run исключает обычные тесты, -bench выбирает нужное упражнение, -benchtime задаёт короткую длительность. Pprof -top показывает сводку, а -nodecount ограничивает число строк. Эти параметры не подключаются к чужому процессу и не требуют внешнего сервера.

Реально полученное наблюдение

В нашей серии профиль имел ненулевой размер и содержал выборки example.invalid/profile.Work. Один записанный запуск дал 430ms выборок и относил их к этой функции. Такое распределение ожидаемо для искусственного теста, где почти вся измеряемая работа находится в одном месте. Оно не означает, что реальная программа будет иметь такой же профиль или что получено ускорение на определённый процент.

Имя в pprof оказалось полным путём пакета, а не только main.Work из некоторых листингов. Это полезное напоминание: формат отображаемых имён зависит от контекста инструмента. При автоматической проверке лучше искать осмысленный символ и структуру профиля, чем требовать случайное точное написание из другого примера.

Flat и cumulative

Плоская стоимость относится к работе, непосредственно приписанной функции. Накопительная включает также её потомков по стеку. Высокая cumulative у верхнего обработчика не доказывает, что арифметика находится именно в его теле: он мог вызвать дорогую зависимость. Для оптимизации сначала нужно найти, где фактически выполняется работа и через какие связи она достигается.

Проценты зависят от состава записанных выборок. Если одна функция занимает почти всё время искусственного benchmark, это характеристика данной нагрузки. После оптимизации другой участок может стать ведущим. Поэтому полезно сохранять абсолютную длительность, число выборок и условия записи вместе с относительными процентами.

Подготовка default.pgo

Скопируйте созданный профиль в default.pgo внутри каталога main-пакета. Для собственной учебной среды удобно воспользоваться обычным копированием файла. PGO в режиме auto обнаруживает предусмотренное имя и использует профиль для сборки. Само расширение не превращает произвольный текст в подходящие данные: формат должен быть корректным.

cp cpu.pprof default.pgo
go build -pgo=off -o baseline .
go build -pgo=auto -o guided .
./baseline
./guided

Параметр off явно исключает PGO, auto выбирает автоматическое обнаружение. Можно также задать явный путь профиля. В выполненной проверке оба варианта успешно собраны и вывели одинаковый результат. Это функциональный контроль и подтверждение принятия профиля. Из одинакового результата и успешной сборки ещё не следует измеренное преимущество guided.

Почему учебный noinline ограничивает эффект

Директива у Work помогает сохранить наблюдаемый символ, но запрещает встраивание именно этой функции. Если хочется исследовать профильное изменение решения о встраивании, нужен другой вариант без запрета и с подходящей стоимостью тела. Нельзя поставить noinline, затем ждать от PGO нарушения явного запрета и объявлять механизм бесполезным из-за отсутствия такого действия.

Правильный порядок — сначала проверить сбор и использование профиля на устойчивом образце, затем создать самостоятельный пример конкретной оптимизации. В нём сохраняют обычную и профильную диагностику, машинный код и серии измерений. Каждое свидетельство отвечает на отдельный вопрос: профиль принят, преобразование произошло, поведение сохранилось и наблюдаемая стоимость изменилась.

Отрицательная проверка формата

Создайте отдельный invalid.pgo с обычной фразой и передайте -pgo=invalid.pgo. В выполненной серии сборка завершилась ошибкой. Этот опыт показывает, что вход действительно разбирается как профиль, а не молча игнорируется по имени. Не заменяйте им проверку реального default.pgo: отрицательный контроль должен оставаться отдельным файлом и отдельной командой.

При отказе настоящего профиля сначала проверьте путь, формат, непустой состав и версию инструментов. Не следует сразу выключать PGO навсегда или переименовывать данные другого вида в .pgo. CPU-профиль, профиль кучи и произвольный журнал имеют разные структуры и смысл, хотя все могут называться профилями в разговоре.

Представительность важнее удобства сбора

Профиль одного короткого запуска может отражать прогрев, единственный тип запроса или редкую фоновую задачу. Компилятор получит именно это распределение как свидетельство. Поэтому сначала определяют, какую работу будущий выпуск должен обслуживать: размеры входов, пути запросов, долю ошибок и режим конкуренции. Иначе оптимизация будет направлена на удобный для записи, но несущественный сценарий.

Для службы профили собирают на собственных контролируемых процессах по установленной процедуре. В учебной серии используются только искусственные данные и свой benchmark. Она не обращается к рабочим адресам и не извлекает профиль чужой программы. Когда появится реальная нагрузка, её состав следует описать до сравнения результатов, а не подбирать после желаемого выигрыша.

Смещение выборки

Sampling, то есть выборочное наблюдение, не измеряет каждую инструкцию отдельно. Короткие события и редкие пути могут быть представлены слабо. Системные условия и длительность записи влияют на устойчивость оценок. Отсутствие функции среди нескольких верхних строк не означает отсутствия её затрат: она могла находиться ниже ограничения nodecount или вне достаточного числа выборок.

Повторите сбор и сопоставьте распределения. Если основной горячий участок скачет между несвязанными задачами, профиль может быть недостаточно устойчивым либо сама нагрузка неоднородна. Решение о дополнительной записи должно опираться на этот вопрос. Бессмысленно увеличивать длительность одного нерепрезентативного сценария, надеясь, что он начнёт представлять другую работу.

Изменение исходников и соответствие профиля

Профиль относится к определённой версии и расположению вызовов. После изменений часть сведений может соответствовать новому коду хуже. Поддержка некоторого переноса не означает, что любой старый профиль одинаково полезен. Храните исходный коммит, версию инструмента, рецепт записи и характеристику нагрузки рядом с профилем как объявленные метаданные.

При крупной перестройке горячего пути нужно рассмотреть повторный сбор. При маленьком изменении можно сначала проверить, какие данные использованы и что показывают измерения. Не делайте возраст профиля единственным критерием: важнее соответствие работе и структуре программы. Но отсутствие этого соответствия нельзя скрывать удобной формулировкой «профиль у нас уже есть».

Как сравнивать baseline и guided

Сначала постройте оба варианта из одинакового исходного состояния и одинаковой цепочкой. Затем выполните функциональные тесты. После этого запускайте серии на одной нагрузке с чередованием порядка, если фоновые условия могут дрейфовать. Записывайте длительность, выделения и необходимые ресурсные показатели. Одно удачное измерение guided после холодного baseline не даёт устойчивого вывода.

PGO может изменить размер машинного текста и время сборки, поэтому измеряйте также то, что важно для доставки и инфраструктуры. Улучшение CPU полезно, пока не нарушены ограничения памяти, задержки и совместимости. Итогом является решение по конкретной системе, а не обязанность всегда включать любое средство оптимизации без проверки.

Профиль и воспроизводимость сборки

Профиль становится входом наряду с исходниками и параметрами. Если default.pgo меняется без фиксации, одинаковый коммит Go-кода может дать другой результат. Для воспроизводимого выпуска нужно знать конкретные байты профиля и способ выбора. Режим auto удобен, но скрытое наличие файла в рабочем дереве не должно становиться неучтённым фактором.

Сохраните контрольную сумму профиля и отметьте, был ли он получен из доверенного источника. Это не требование публиковать все внутренние сведения нагрузки. Доступ и состав метаданных выбирают осознанно, поскольку профиль может раскрывать названия функций, пути и структуру работы. Учебный профиль содержит только наши искусственные имена.

Слияние разных нагрузок требует определения веса

Если несколько профилей объединяются, соотношение их вкладов должно отражать выбранную цель. Длинная запись редкого сценария может доминировать над короткой записью типичной работы. Простое объединение файлов не доказывает представительность итогового распределения. Сначала определяют, что означает вес: время работы, частота запросов или иной осмысленный показатель.

Для неоднородной службы полезно отдельно сохранить результаты по важным сценариям после сборки. Средний выигрыш может скрыть ухудшение редкой, но критичной операции. Это относится к любому профилированию: оптимизация общего CPU и соблюдение максимальной допустимой задержки являются разными ограничениями, которые нужно проверить совместно.

PGO не заменяет алгоритмическое решение

Если программа выполняет лишний обход миллионов записей, профиль поможет увидеть его частоту, но не обязан превратить неправильную структуру алгоритма в нужную. Изменение объёма работы часто важнее тонкой настройки встраивания. Сначала стоит убрать доказанно ненужные действия и проверить корректность, затем использовать профиль для оставшихся существенных затрат.

Также нельзя считать PGO лекарством от сетевого ожидания, блокировок и медленного диска по одному CPU-профилю. Если процесс почти не использует CPU в критичной задержке, нужна другая диагностика. Выбирайте инструмент по ресурсу, ограничивающему задачу. Сильный отчёт показывает, почему именно профиль процессора подходит найденной проблеме.

Повторная проверка после выпуска

Если нагрузка изменилась, прежний результат следует переоценить. Полезно сохранить базовый вариант, условия сравнения и процедуру отката конкретной оптимизационной сборки. Это не означает обязательную постоянную запись профилей. Достаточно понятного основания, при каких изменениях системы нужно повторить измерения и какие показатели должны оставаться приемлемыми.

Для самостоятельного продолжения добавьте второй путь WorkCold с иной стоимостью и управляйте долей вызовов. Сначала создайте два разных профиля, затем сравните соответствующие сборки на обоих распределениях. Такой опыт показывает смещение нагрузки без заимствования чужих данных. Не объявляйте результат выполненным до сохранения собственных измерений.

Горячее ребро вызова важнее одного имени функции

Компилятору полезна не только общая сумма времени функции, но и связь конкретного места вызова с конкретной реализацией. В pgoir проверенного выпуска строится взвешенный граф: узлы описывают функции, а рёбра — вызовы с профильным весом и сведениями о месте. Две строки, вызывающие один интерфейс, могут иметь разное распределение реализаций и потому разные основания для преобразования.

Если большая доля вызовов метода идёт к одному конкретному типу, возможна условная девиртуализация. На горячем варианте выполняется прямой вызов, а для остальных сохраняется общий путь. Предварительная проверка типа нужна именно потому, что профиль не доказывает отсутствие других допустимых значений. Редкая реализация не должна потеряться только из-за недостатка выборок.

исходно:  интерфейсный вызов ──► любая допустимая реализация
после:    проверка горячего типа
          ├─ совпал ──► известный прямой вызов
          └─ другой ─► прежний общий вызов

Основная выгода такого преобразования может заключаться в следующем встраивании прямого вызова. Тогда открываются константы, локальные значения и другие возможности. Но сама проверка тоже стоит работы и увеличивает код. Поэтому выбор делается по профильному основанию и ограничениям компилятора, а не для любого интерфейса подряд. Это описание механизма из исходников; отдельный тест его срабатывания в текущей серии не проводился.

Проверить именно выбранную гипотезу

Для будущего опыта создайте интерфейс проверки числа с двумя собственными реализациями и управляйте их долей в одном месте вызова. Сначала сделайте распределение сильно смещённым, затем почти равномерным. Сохраните профили отдельно, чтобы имя default.pgo случайно не подменило выбранный вход. Для каждого результата проверьте оба конкретных типа функционально, включая редкий путь.

После сборки найдите диагностическое сообщение и машинную развилку, а затем измерьте обе нагрузки. Если преобразование не произошло, это тоже содержательный результат: нужно исследовать достаточность профиля, соответствие вызовов и ограничения реализации. Нельзя заменять отсутствие наблюдения обещанием, что современный компилятор наверняка всё сделал. Такой порядок связывает теорию PGO с проверяемым конкретным изменением.

Отдельно проверьте, что профиль содержит именно устойчивую обработку, если цель связана с ней. Долгий прогрев может занять почти всю короткую запись, и тогда вес получат создание таблиц или загрузка данных. Для командной утилиты это может быть правильным объектом оптимизации, а для постоянно работающей службы — случайным смещением. Единого правила «всегда исключать старт» нет: граница записи должна соответствовать выбранному сценарию.

Сохраните это решение в описании входа профиля. Тогда следующий автор сборки сможет повторить эксперимент и понять, почему распределение отличается от профиля, снятого сразу после запуска процесса.

Граница подтверждения

В данной серии реально созданы CPU-профиль, сводка pprof, default.pgo, варианты auto и off с одинаковым результатом, а также отказ на неверном формате. Производственный выигрыш и конкретная PGO-девиртуализация не измерялись. Пример проверяет инструментальный путь и учит строить следующий содержательный эксперимент.

Источники: официальный маршрут PGO, загрузка профильных сведений, профильная девиртуализация, решения встраивания, запись профиля, инструмент pprof.
