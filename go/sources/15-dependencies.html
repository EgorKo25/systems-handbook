Модули Go: выбор версии, получение и проверка

Установим, как из go.mod получается выбранный граф модулей, почему go.sum не является lock-файлом и что нужно подготовить для повторной сборки без сети.

Разрешение зависимостей — задача с ограничениями

Пакет и модуль — разные единицы. Пакет обычно соответствует каталогу совместно компилируемых Go-файлов. Модуль объединяет пакеты с общим путём, версией и go.mod. Импорт example.org/handbook-service/internal/httpapp выбирает пакет внутри нашего основного модуля; сторонний импорт может потребовать другой модуль. Версия выбирается для модуля, а затем из него читаются нужные пакеты. Поэтому число строк import, число пакетов go list -deps и число модулей go list -m all обычно различается.

Директива require задаёт минимальное требование версии конкретного пути модуля. Алгоритм MVS, minimal version selection — минимальный согласованный выбор версий, обходит граф требований и для каждого пути сохраняет наибольшую из требуемых минимальных версий. Слово «минимальный» не означает взять самую старую существующую версию и не означает автоматически обновиться до последней опубликованной. Получается минимальная сборочная выборка, удовлетворяющая известным нижним границам.

наш модуль → transport v1.2.0 → codec v1.3.0
наш модуль → storage   v1.1.0 → codec v1.5.0
Выбрано для codec: v1.5.0, а не v1.3.0 и не неизвестная «latest».

Здесь имена сокращены для рисунка. У каждой реально выбранной версии собственный go.mod, поэтому обход может открыть дополнительные требования и повысить ещё одну границу. Результат проверяют go list -m all, а рёбра — go mod graph. -m переключает list с пакетов на модули, all выбирает сборочный список. graph показывает требования, а не только уже импортированные в main пакеты. Список скачанных когда-то версий в GOMODCACHE ещё не является выбранным графом сегодняшней сборки.

Модель опирается на совместимость внутри основного пути модуля. Для несовместимого второго основного выпуска обычно нужен путь с /v2, чтобы две линии могли сосуществовать как разные зависимости. MVS не является универсальным решателем произвольных диапазонов «выше 1.2, но ниже 1.4, кроме двух выпусков». Если библиотека нарушила обещанную совместимость, удачно выбранное число версии не исправит её API. Нужно исследовать изменение, выбрать совместимые требования и проверить собственную программу.

Pruning и lazy loading уменьшают чтение, а не меняют смысл

Современная модульная система умеет отсекать ненужные части графа, module graph pruning, и лениво загружать описания зависимостей, lazy loading. Благодаря дополнительным явным требованиям в go.mod ей не всегда нужно читать всю историю требований всех транзитивных пакетов для простой команды. Директива go влияет на соответствующие правила. Отсутствие обращения к некоторому модулю в журнале одного запуска не означает, что он не может потребоваться другой целевой платформе или тестам.

Команда go mod tidy приводит описания к требованиям реально учитываемых пакетов и тестов по собственным правилам обхода. Это не просто сортировка. Она может добавить indirect-требования и контрольные суммы либо убрать больше не нужное. Пометка // indirect говорит о характере требования в описании, а не о недоверенной библиотеке. Изменения tidy читают как изменение входов сборки и сохраняют в Git вместе с причиной. На проверочном агенте удобен go mod tidy -diff: он показывает требуемые изменения без записи и даёт проверочный ненулевой исход, если согласованности нет.

Декларация, фиксация, доступность, доверие

go.mod содержит путь модуля, минимальную версию Go, требования и управляющие директивы. go.sum содержит известные проверки содержимого конкретных версий модулей и их файлов go.mod. Строки для одной версии и для её /go.mod имеют разные предметы проверки. Префикс h1: обозначает определённую схему хеширования нормализованного содержимого, а не обещание, что записан SHA-256 скачанного ZIP-файла в его транспортном виде.

go.sum не выбирает версии как типичный lock-файл. В нём могут оставаться проверки нескольких версий и описаний, которые потребовались для разрешения графа. Сам выбор определяется требованиями и правилами MVS. И наоборот, отсутствие go.sum у нашего проекта только со стандартной библиотекой нормально: нет внешних версий, для которых понадобились записи. Нельзя создавать пустой файл ради внешнего сходства с другим проектом и считать фиксацию выполненной.

Контрольная сумма устанавливает, что полученные данные совпадают с ожидаемым содержимым данной версии. Доступность требует иметь сами байты — в доверенном кэше, vendor или подготовленном зеркале. Проверенная сумма не поможет восстановить отсутствующий архив без источника. Происхождение ожидаемой суммы тоже имеет значение: если новый неизвестный модуль и его новую сумму принесли одним недоверенным каналом без независимой проверки, сам факт равенства этих двух данных не создаёт дополнительного доверия.

Прокси и база контрольных сумм

GOPROXY задаёт последовательность источников модулей. Запятая между адресами означает переход к следующему при предусмотренном ответе «не найдено», обычно HTTP 404 или 410. Вертикальная черта разрешает переход и при других ошибках. Следовательно, proxy-a,proxy-b и proxy-a|proxy-b различаются при тайм-ауте либо запрете доступа первого. Если это не учесть, ожидание от зеркала не совпадёт с реальной причиной остановки.

direct означает обращение к исходным системам контроля версий по правилам поиска модуля, а не работу без сети. off запрещает поиск через прокси и нужен для явной проверки достаточности подготовленных локальных входов. База контрольных сумм задаётся GOSUMDB; она является отдельным механизмом проверки опубликованного содержимого. Прокси доставляет байты, база помогает проверять соответствие ожидаемой версии. Не надо отключать GOSUMDB ради устранения ошибки, не разобрав несоответствие.

GOPRIVATE задаёт шаблоны префиксов частных модулей и влияет на значения по умолчанию для обхода публичного прокси и базы сумм. GONOPROXY и GONOSUMDB позволяют управлять этими двумя решениями отдельно. Например, частный корпоративный прокси может обслуживать приватные пути, поэтому бездумно наследованное правило обхода прокси помешает нужной схеме. Эти переменные не выдают учётные данные автоматически и не подтверждают авторство любого ответа внутреннего сервера. В книге используются вымышленные пути и локальные примеры.

Пример установки из подготовленного набора

В нашем основном go-service сторонних модулей нет. Для первой автономной сборки необходимы исходники и полноценный Go toolchain со стандартной библиотекой. Команда GOPROXY=off go build ./cmd/handbook-service не должна скачивать пакеты. Это свойство именно данного набора входов. Для другого приложения сначала в среде с доступом получают согласованный граф, проверяют версии и сохраняют необходимые исходники модулей. Затем отдельно проверяют холодную сборку с запрещённым сетевым получением.

go list -m all
go mod graph
go mod download -json
go mod verify
go build -mod=readonly ./cmd/handbook-service

download получает выбранные модульные данные в кэш; -json печатает машинные сведения, включая пути и доступные суммы. Он не собирает программу и не запускает её тесты. verify проверяет, что загруженные версии в локальном модульном кэше не были изменены после получения; он не является общим сканером правильности собственного основного модуля и локальных replacements. -mod=readonly запрещает неявные изменения go.mod при сборке, но его нельзя трактовать как общий запрет любой записи в go.sum, кэши или выходные файлы.

Vendor как другой способ доставки входов

go mod vendor создаёт каталог копий нужных пакетов зависимостей и файл vendor/modules.txt. Это материализация выбранного набора, которую можно хранить и передавать по принятой политике. -mod=vendor явно выбирает такую сборку; при подходящей директиве go и существующем vendor этот режим может применяться по умолчанию. Несоответствие vendor описанию модуля должно быть исправлено как изменение входов, а не скрыто переключением флага.

Vendor и GOMODCACHE не взаимозаменяемые деревья. Первый ориентирован на выбранный проект, второй может содержать много модулей и версий с собственной служебной структурой. Vendor не обязан содержать весь исходный репозиторий зависимости, все её тесты и любые будущие платформенные нужды. После подготовки автономного набора повторяют именно требуемые команды и targets. Успех linux/amd64 не доказывает наличие всех входов для windows/arm64 с другими ограничениями сборки.

Сборочные зависимости тоже являются зависимостями

Генератор протокола, инструмент миграций, анализатор и версия компилятора способны менять результат даже без прямого импорта из приложения. go generate запускает описанные авторами команды, а не автоматически безопасную фазу go build. Обычная сборка сама не обязана обновить сгенерированные исходники. Если генерация требуется, нужно зафиксировать инструмент, входную схему и порядок действия, затем проверить отсутствие непредусмотренных изменений. Случайный установленный у разработчика генератор latest — скрытая зависимость.

Выбор Go регулируют сам исполняемый go, директива go и предпочтение toolchain, а также GOTOOLCHAIN. Начиная с современных выпусков директива go — требование минимальной версии, а не просто комментарий о намерении автора. GOTOOLCHAIN=local запрещает автоматическую смену на скачанный новый комплект: при слишком новом требовании команда откажет. Это предсказуемый исход автономного опыта. auto может выбрать или получить более новый toolchain, поэтому фактическую версию следует записать после выбора, а не только посмотреть имя первоначального файла в PATH.

Replace, exclude и retract отвечают на разные вопросы

replace подменяет источник выбранного модуля другой версией или локальным каталогом. Замена сама по себе не добавляет зависимость в граф вместо require. При локальном каталоге нужно иметь и его байты: путь ../shared не окажется волшебным образом внутри Git-клона приложения. go.sum обычно не защищает произвольно изменяемый локальный каталог так же, как скачанную модульную версию. Манифест происхождения должен учитывать такой вход отдельно.

exclude исключает конкретную версию из допустимого рассмотрения по правилам основной конфигурации. retract сообщает, что автор модуля отозвал опубликованный выпуск из нормального выбора обновлений. Это уведомление не стирает уже существующий tag и не обязано ломать сборку, явно закреплённую на отозванной версии. Смысл исправления сначала выясняют по сообщению автора, а затем обновляют требования и тестируют изменения.

Рабочая область Go и сравнение моделей

Необязательное сравнение моделей

В Maven dependencyManagement управляет версиями объявленных зависимостей, а не автоматически включает каждую библиотеку в приложение. В Go replace также не следует путать с require. Аналогия полезна для отделения «откуда брать», «какую версию выбрать» и «что действительно используется», но алгоритмы Maven и MVS различны. Главный маршрут этого тома использует Go, а Maven для повторения опыта не нужен.

Go work: несколько основных модулей

Файл go.work может объединить несколько модулей как рабочую область. Директивы use делают их основными для этой области, а собственные replace способны изменить выбор источников. Это удобно для совместной разработки службы и библиотеки, но скрытая рабочая область выше каталога проекта меняет контекст сборки. go env GOWORK показывает выбранный файл; GOWORK=off отключает область для изолированного опыта. Отключение не отменяет replace самого go.mod.

На машине автора go work use мог подключить свежую библиотеку из соседнего каталога, а в Git службы осталась старая зависимость. Поэтому успешный локальный тест ещё не доказывает сборку опубликованного модуля. Перед выпуском проверяют оба договора: ожидаемую рабочую область разработки и отдельный воспроизводимый модуль. Файл go.work может быть осознанной частью общего проекта, но тогда его пути и все указанные исходники должны входить в передаваемый набор.

Один выбранный граф, несколько исходных требований

В локальном проверочном опыте были созданы модули a, b и c. Основной root требовал a@v1.0.0 и b@v1.0.0; a требовал c@v1.3.0, b — c@v1.5.0. Все источники заменены собственными соседними каталогами, поэтому GOPROXY=off не мешал опыту. После tidy команда list -m all выбрала c@v1.5.0, а graph сохранила оба исходных ребра требований. Это точное различие между графом ограничений и итоговым сборочным списком.

require (
    example.org/a v1.0.0
    example.org/b v1.0.0
)
replace example.org/a => ../a
replace example.org/b => ../b
replace example.org/c => ../c

Фрагмент предназначен для собственного root-модуля с существующими каталогами a, b, c и их go.mod. Он не добавляется в основной handbook-service. Версионные метки в графе остаются требованиями, хотя содержимое подменено локально. Успешный verify в таком опыте не проверил неизменяемость наших каталогов: он лишь не нашёл проблем у своего предмета проверки. Такой отрицательный пример полезен, потому что не позволяет объявить одну зелёную команду общей гарантией всех входов.

Replace и exclude зависимого модуля не следует считать автоматически действующей политикой основного проекта. Основная конфигурация и рабочая область определяют подходящие подстановки. Поэтому при переносе библиотеки из её собственного каталога в зависимость службы поведение может измениться: её личная локальная замена не переехала как универсальный приказ всем потребителям. Граф и выбранные Dir/Replace сведения list -m -json помогают выяснить, какие байты реально использовались.

Дополнительные каналы неявных настроек

GOFLAGS добавляет флаги по умолчанию к подходящим вызовам go. GOENV определяет пользовательский файл значений, записанных go env -w. Они могут включить vendor, изменить режим модулей или диагностические флаги без явного появления в коротком сценарии. Для воспроизводимого запуска достаточно не стирать пользовательскую конфигурацию, а задать контролируемое окружение процесса и записать существенные значения. GOENV=off не нейтрализует уже установленный GOFLAGS; это два разных входа.

Флаг -modfile=alternate.mod выбирает альтернативное описание модуля и соответствующий alternate.sum по правилам команды. Он полезен для некоторых инструментов, но создаёт ещё один вход, который легко забыть сохранить. Проверка только обычного go.mod тогда не описывает действие. Аналогично автоматическая смена toolchain может потребовать сеть даже при уже загруженных библиотечных модулях: сохранность зависимостей и доступность требуемого компилятора проверяются отдельно.

Как обновлять зависимости без замораживания навсегда

Обновление делают явным изменением входов: выбранная версия, изменение графа, новые суммы, совместимость API и поведение тестов. go get модуль@версия меняет требования, а не просто печатает доступный пакет. После него изучают go.mod/go.sum, go list -m all и результат тестов. Нельзя считать сохранённую сумму доказательством отсутствия регрессии. Отдельная задача анализа уязвимостей тоже не заменяет функциональные проверки и не следует автоматически из go mod verify.

Подготовленный автономный набор имеет срок полезности: новые исправления не приходят в него без явного обновления. При этом «всегда latest» уничтожает воспроизводимость прежнего выбора. Практическое решение — хранить проверенный граф и артефакты выпусков, а обновления проводить регулярно отдельными изменениями с наблюдаемым результатом. Для нашей лаборатории все упражнения стандартной библиотеки выполняются без внешних скачиваний; механизм чужих версий демонстрируется отдельными локальными модулями, не подменяя этим реальную проверку публичного прокси.

Минимальная версия и предпочтение инструмента

Строка go 1.25.0 влияет на допустимые языковые и модульные правила, но не требует побайтового совпадения с компилятором 1.25.0. Директива toolchain может сообщить предпочтительный комплект для работы в основном контексте; более новый допустимый go не обязан по ней откатиться назад. Поэтому для воспроизводимого эксперимента явно выбраны бинарник Go 1.27.3 и GOTOOLCHAIN=local, а не только красивое число в go.mod.

Простой отрицательный опыт — модуль с требованием go 1.99.0 и тот же локальный toolchain. Команда должна отказать, не скачивая неизвестный новый комплект. В нашем проверочном сценарии такой отказ наблюдался. Это полезный предсказуемый исход автономного режима. Его не надо обходить удалением строки go без проверки кода: слишком новое требование может отражать реальные конструкции языка, библиотечный API или правила модуля.

Первоисточники: Go Modules Reference, директивы go.mod, выбор toolchain, mod, work, list и режимы получения, совместимость модулей. Публичная сеть, отказы зеркал и частная авторизация не воспроизводились; правила сопоставлены с официальной документацией, а собственные графы проверялись локально.
