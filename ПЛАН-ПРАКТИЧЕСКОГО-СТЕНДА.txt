ПЛАН ЕДИНОГО ПРАКТИЧЕСКОГО СТЕНДА
31 октября 2026. Проект решений; общий стенд ещё не реализован.

РЕШЕНИЯ И ТЕКУЩИЙ ВЫБОР
Пользователь выбрал единый стенд для всей библиотеки: сети, Linux,
Bash, PostgreSQL, кэширование, Redis и Memcached. Предпочтение — Docker.
Уточнён полный охват: ручное развёртывание, CI/CD, blue-green, диски
и inode, Ansible, Terraform, мониторинг и Kubernetes. Эти темы входят
в общую программу, даже если соответствующие тома ещё не написаны.
Обсуждается облачная виртуальная машина как место запуска Docker.
Аренда сервера, покупка тарифа и установка ПО пока не выполнялись.

Основная архитектура: Linux + Docker Engine + Compose. Её можно
развернуть дома либо на облачной VM. Облако снимает локальную нагрузку
и позволяет продолжать занятия с разных устройств, но требует сети.
Практики с самостоятельной ОС получают отдельный VM-профиль.
Это заменяет прежнее решение от 28 октября начинать с трёх QEMU-машин.

Локальный и облачный запуск требуют отдельной проверки ресурсов.
Наблюдения свободной RAM и /dev/kvm на одном компьютере не являются
универсальным системным требованием книги.

Один мир означает общие данные, конфигурацию и историю упражнений.
Запускать одновременно все службы и все кластеры не требуется.
Сценарий включает только необходимые роли. Следующая глава использует
результат предыдущей; запуск новой главы сам по себе ничего не сбрасывает.

ОБЛАКО: ЧТО ПОДХОДИТ
Присланные Хост-0/1/3 — тарифы хостинга сайтов. Для этого продукта
документация REG.RU указывает отсутствие root и поддержки Docker.
Такой хостинг может публиковать книгу, но не подходит для нашего стенда.

Небольшая облачная VM с 1 vCPU, 1 ГБ RAM и 10 ГБ диска подходит
для отдельного опыта, но не принимается за базу полного стенда.
Ubuntu 26.04 LTS входит в текущий официальный список Docker Engine.

Оценка проекта: 1 ГБ / 10 ГБ годятся для ограниченного ознакомительного
опыта, но не принимаются за целевой ресурс единого стенда. На диске
должны помещаться ОС, образы, данные, журналы и контрольные точки.
Память нужна ОС, Docker, клиенту, службам и запасу на пики операций.

Ориентиры для испытания, а не измеренные системные требования:
- экономный последовательный профиль: 2 vCPU, 4 ГБ RAM, 40 ГБ SSD;
- профиль с запасом для реплик: 4 vCPU, 8 ГБ RAM, 60–80 ГБ SSD.
Эти бюджеты относятся к первым сценариям Compose. Они не описывают
полный набор CI-сервера, сборщиков, registry, Kubernetes и мониторинга.
Окончательный выбор — после измерения реального первого сценария.
Производительность vCPU зависит от условий провайдера.

Расширение ресурсов планируется по этапам:
- Начало: одна VM для Linux/Compose, небольшого приложения и данных.
- CI/CD: отдельная роль runner; сборка не должна искажать измерения
  приложения. Собственный GitLab + registry — отдельный профиль.
  На малом бюджете можно изучать pipelines с внешним GitLab и своим
  runner, но это не заменяет практику установки собственного CI-сервера.
- Kubernetes API: временный kind-кластер внутри Docker для начальных
  объектов; несколько node-контейнеров не дают независимых машин.
- Эксплуатация Kubernetes: отдельные VM, начально один control-plane
  и два worker. kubeadm указывает от 2 GiB RAM на машину и от 2 CPU
  на control-plane; это нижняя граница запуска, не бюджет всего стека.
  Память приложений, мониторинга, сборки и запас считаются отдельно.
- Отказоустойчивый control-plane — последующий профиль с несколькими
  управляющими узлами; один control-plane не считается HA.

Роли — логические. Не каждая требует постоянно оплачиваемой отдельной VM.
Рабочие данные, код, state и копии храним независимо от временных узлов.
Создание/удаление учебного окружения не должно удалять управление и state.
Срок хранения образов, метрик и артефактов ограничиваем явно, исходя
из учебной задачи и дискового бюджета. Временные VM создаются на занятие,
но остановка не равна освобождению всех оплачиваемых ресурсов.

Для аренды проверяем root/sudo, Docker, доступную консоль при поломке
SSH, способ восстановления и изменения тарифа, стоимость IP, диска,
копий и трафика. У REG.облака остановка VM не обнуляет расходы на диск/IP.
Для первого испытания подходит почасовая оплата без длинного обязательства.

Для GRUB, ядра и восстановления создаём отдельную временную VM.
Она не должна быть тем же сервером, который хранит основной учебный мир.
Для начальных опытов с ФС/LVM можно использовать отдельные файловые
образы через loop devices внутри Linux VM. Это реальная работа Linux
с блочными устройствами, но она не проверяет дисковый API провайдера.
Дополнительные облачные диски и вложенная виртуализация проверяются
отдельно: наличие KVM у провайдера не обещает /dev/kvm внутри гостя.
Можно арендовать отдельные VM вместо вложенных. Их сеть и оплата
будут частью отдельного профиля. Обычный VM-снимок не считается
автоматически согласованной резервной копией работающей БД.

Terraform у Рег.облака существует: поставщик публикует regcloud,
source = tf.reg.cloud/regru/regcloud, с примерами server и ssh_key.
Последняя версия, схема всех ресурсов, доступность в выбранном регионе,
управление отдельными дисками и приватными сетями ещё не испытаны.
До выбора постоянного тарифа провести короткое оплачиваемое испытание
либо использовать подтверждённый тестовый период: создать VM через provider, прочитать её,
получить пустой повторный plan, изменить поддерживаемый параметр,
удалить только тестовые ресурсы. Это будущая проверка, сейчас не выполнена.
Общий OpenStack-provider не назначается только по слову OpenStack
в названии региона; нужен доступ к соответствующему API и учётным данным.

ДОСТУП И КАРТА МИРА
Локальный запуск: книга + установленный Docker Engine/Compose.
Облачный запуск: книга на компьютере → SSH → Linux VM → Compose.
Docker на рабочем компьютере для второго варианта не нужен.
Наличие разрешённого SSH-клиента либо браузерной консоли и доступ
из рабочей сети надо проверить. Браузерный интерфейс стенда ещё не создан.
Облачный режим не работает офлайн. Офлайн остаются книга и подготовленный
локальный вариант с заранее загруженными образами.

Основные учебные роли:
клиент → учебная сеть A → маршрутизатор → сеть B → сервер/приложение
                                                            ↓
                                                        PostgreSQL
                                                            ↑
                               приложение → Redis или Memcached

Маршрутизатор включается для сетевых заданий. Реплики, Sentinel,
Redis Cluster, сбор метрик и генератор нагрузки включаются по сценарию.
Между сетями A и B не должно быть скрытого прямого пути через общий bridge.
Для обычного упражнения с приложением отдельный маршрутизатор не обязателен.
Управление контейнерами через docker exec не зависит от исправности
учебного маршрута. Настоящий SSH изучается отдельным заданием.

На облачной VM БД и кэши доступны внутри учебной сети. Порты интерфейса
управления публикуются на loopback и доступны через SSH-туннель;
браузерный доступ без туннеля потребует отдельного HTTPS-входа с авторизацией.
Клиент Redis Cluster запускается в сети с доступом ко всем объявленным
адресам узлов; публикация одного порта не решает маршрутизацию кластера.

ГРАНИЦЫ DOCKER И ВИРТУАЛЬНЫХ МАШИН
Обычные контейнеры:
- Bash, скрипты, файлы, права, пользователи, процессы, сигналы;
- HTTP, DNS, TLS, приложения, PostgreSQL, Redis, Memcached;
- роли, ACL, клиентская авторизация, репликация, протоколы кластеров;
- копии данных приложений и восстановление из них.

Контейнеры с настройками конкретного задания:
- маршрутизация, NAT, firewall, tcpdump, задержки/потери пакетов;
- лимиты CPU/RAM, OOM контейнера, часть cgroup/sysctl и трассировки.
Выдаём только необходимые capabilities/устройства нужным узлам.
Универсальный --privileged не является базовым способом запуска.
Старые ip netns add-скрипты нельзя считать готовыми для одного NET_ADMIN:
создание/mount пространства имён может требовать дополнительных прав.
Предпочитаем контейнер на роль и проверяем конкретный сценарий.

Отдельная VM для полноценного системного упражнения:
- своё ядро, его загрузка, GRUB/initramfs, kernel panic, восстановление ОС;
- systemd в контексте загрузки всей системы;
- отдельные виртуальные диски, разделы, LVM/RAID и восстановление ФС.
Часть systemd/mount/loop-device опытов возможна в специальных контейнерах.
Причина отдельной VM — нужная модель ОС и изоляция её поломки.
Контейнеры используют общее ядро.

Один хост с несколькими контейнерами не создаёт независимые физические
зоны отказа. Даже несколько облачных VM не доказывают разнесение по
физическим серверам без условий размещения от провайдера.
Остановка процесса, сетевой разрыв и отключение питания — разные опыты.
Нагрузочный результат стенда описывает его CPU, память, диск и соседей;
он не является обещанием производственного предела технологии.

ЧТО СОХРАНЯЕТСЯ
У мира есть ID, версия сценария и отдельный Compose project.
Явно объявляются постоянные учебные файлы, конфигурация, данные БД,
отчёты, захваты пакетов и результаты проверок.

stop/start сохраняет файловый слой существующего контейнера.
Удаление/пересоздание контейнера уничтожает его собственный слой;
named volumes и рабочие конфигурации хранятся отдельно.
Ручной apt install или правка произвольного /etc не считаются
автоматически переносимым прогрессом. Изменения пакетов фиксируются
в рецепте образа, нужные конфиги — в объявленных постоянных файлах.
Задания на установку ОС/пакетов могут использовать сохраняемую VM.

Значения Memcached после перезапуска исчезают по смыслу технологии.
У Redis сохранность определяется выбранными RDB/AOF и условиями сбоя.
Учебная контрольная точка сохраняет данные на диске, а не всю RAM,
открытые соединения и незаписанные маршруты.

Контрольная точка первой версии:
1. Остановить поступление записей и корректно остановить связанные службы.
2. Сохранить конфигурацию и объявленные данные всего связанного мира.
3. Записать manifest: версии, архитектуру, image digest, seed, состав файлов.
4. Проверить полноту и контрольные суммы, затем опубликовать готовую точку.
Прерванное сохранение не уничтожает предыдущую пригодную точку.
Копирование работающего PGDATA и docker commit не заменяют эту процедуру:
commit не включает volumes. Настоящие online-backup — отдельная практика.

Восстановление по умолчанию создаёт отдельную копию мира.
Сброс требует явного указания мира/упражнения; обычная остановка его
не выполняет. Общий docker volume prune для управления стендом не нужен.
В первой версии разрешаем одну активную копию, чтобы не удваивать ресурсы.
Копия на диске той же VM помогает откату, но не защищает от потери VM:
переносимый экспорт хранится вне неё.

КАК УСТРОЕНО УПРАЖНЕНИЕ
Каждое задание содержит:
- решаемую проблему и причину появления технологии;
- необходимые знания, роли, исходное состояние и ограничения ресурсов;
- задачу ученика и наблюдаемые признаки результата;
- схему текущего пути данных и объяснение изменения состояния;
- команды с разбором параметров и термины со ссылками в словарь;
- независимую проверку, подсказки, разбор и способ восстановления;
- отчёт с измерениями и границами того, что эксперимент доказывает.

Проверка читает результат, а не ищет единственную введённую команду.
Она не должна выполнять задачу за ученика. Например, проверяем успешный
доступ разрешённой роли и отказ запрещённой, а не наличие строки GRANT.
Проверки времени и скорости не требуют фиксированного QPS на любом железе.

Для кэша используем одно небольшое приложение и один источник PostgreSQL.
Сначала измеряем вариант без кэша, затем Redis и Memcached на одинаковых
данных/запросах. Фиксируем интенсивность, распределение ключей, размеры
значений, попадания/промахи, p50/p95/p99, ошибки, запросы к источнику,
CPU, RAM, вытеснения и сетевой обмен. Отдельно холодный запуск, прогрев,
устаревание, invalidation, stampede, отказ и восстановление клиента.
Интерпретируем выигрыш вместе с ценой памяти и допустимым устареванием.
Порог внедрения выводим из бюджета источника и требуемых задержек.

ОДИН ПРОЕКТ ДЛЯ ВСЕГО ЦИКЛА
Предлагаемый учебный продукт — небольшой каталог с API, PostgreSQL
как источником данных и подключаемым Redis либо Memcached.
Есть версии приложения v1/v2, миграции схемы, воспроизводимые данные,
проверка готовности, генератор запросов и заранее предусмотренные ошибки.

Роли на расширенном этапе:
- управление: Git, Terraform state, Ansible inventory и результаты;
- доставка: CI-сервер, runner и registry образов;
- приложение: входной Nginx, blue и green, PostgreSQL и выбранный кэш;
- наблюдение: Prometheus, Grafana, Alertmanager, затем сбор журналов;
- системный опыт: временная Linux VM и отдельные учебные диски;
- Kubernetes: control-plane и workers, включаемые на соответствующем этапе.

Сначала ученик руками получает работающий результат и разбирает каждый
шаг. Затем пишет Bash-скрипт или конфигурацию подходящего инструмента,
проверяет повторный запуск и восстановление после намеренной ошибки.
Автоматизация не подменяет объяснение пакетов, файлов, прав и сети.

РУЧНОЕ РАЗВЁРТЫВАНИЕ И BLUE-GREEN
Сначала установка приложения как службы, затем контейнерный вариант.
Проверяем входной адрес, TLS, доступ к данным, журнал, readiness и версию.
Blue-green — две версии приложения, одна получает основной трафик:
1. Blue обслуживает запросы; сохраняем базовые ошибки и задержки.
2. Запускаем Green, направляем туда отдельные проверочные запросы.
3. Проверяем готовность, зависимости и совместимость схемы/кэша.
4. Переключаем маршрут на Green и наблюдаем реальные запросы.
5. При заданном ухудшении возвращаем маршрут на Blue.
6. Завершаем старые соединения и только затем останавливаем старую версию.

Первая реализация через Nginx и два экземпляра, без Kubernetes.
Повторная — в Kubernetes через раздельные Deployments и выбор Service.
Это не то же самое, что штатное rolling update одного Deployment.
Отдельно рассматриваем прогрев, фоновые задачи, сессии, долгие соединения.
Откат трафика не откатывает записи пользователей и схему PostgreSQL.
Поэтому миграция сначала добавляет совместимые структуры, обе версии
работают с ними, а удаление старых структур выполняется после окна отката.
Проверка: поток запросов фиксирует версию, ошибки и задержки на всём
переключении. Green, не прошедшая предварительную проверку, не получает
основной трафик; деградация после переключения вызывает возврат на Blue.

CI/CD ОТ РУЧНЫХ КОМАНД ДО PIPELINE
Рабочая цепочка: commit → тесты → сборка → образ с digest → registry →
тестовое окружение → проверка → развёртывание Green → проверка →
переключение → наблюдение → при необходимости возврат Blue.
Сначала каждый шаг выполняется отдельно, затем переносится в pipeline.
CI автоматически проверяет и собирает изменения. Continuous delivery
готовит проверенный выпуск с ручным решением о развёртывании;
continuous deployment добавляет автоматический выпуск при выполнении правил.

Темы практики: runner и его исполнитель, рабочий каталог, переменные,
учётные данные с ограниченным доступом, кэш сборки против артефактов,
реестр образов, фиксация версий, зависимости jobs, параллельность,
тайм-ауты, повторный запуск и запрет одновременных конфликтующих deploy.
Один и тот же собранный образ продвигается между окружениями.
State/данные БД не считаются частью образа приложения.
Доступ runner к Docker-хосту учитывается как полномочие управления хостом.
Сценарии ошибок: не прошёл тест, недоступен registry, прервана сборка,
не готова новая версия, два одновременных pipeline, неуспешный rollback.
Полностью собственные GitLab/runner/registry предусматриваются отдельным
развёртыванием с измерением их ресурсов и резервным копированием.

ANSIBLE
Ручную настройку переводим в inventory, playbooks, roles, templates,
handlers и переменные окружений. Включаем установку пакетов, пользователей,
SSH, конфигурации служб, TLS, продуктов и последовательное обновление узлов.
Проверяем поддерживаемые check/diff, права become и хранение секретов.
Ключевой опыт: повторное применение к неизменённому окружению не делает
ненужных изменений; внесённое вручную расхождение обнаруживается
и исправляется. Проверка поведения продукта независима от changed=0.
Результат: чистая учебная VM получает известную работающую конфигурацию.

TERRAFORM
Terraform создаёт ресурсы через API, Ansible настраивает ОС/продукты.
Связываем output адресов/ролей с Ansible inventory.
Учим init/plan/apply, зависимости, переменные, outputs, версии provider,
модули, import, drift, изменение/замену ресурсов и destroy.
State хранится отдельно от удаляемого стенда; для совместной работы
выбираем backend с поддержкой блокировки и проверяем её поведение.
Не объявляем Terraform универсальной системой установки пакетов.
Не называем API-вызовы в local-exec полноценной поддержкой облака provider.
Проверка: повторный plan пуст; ручное расхождение видно; экземпляр
пересоздан из кода, а необходимые данные восстановлены из объявленной копии.
Перед изменением диска различаем изменение ресурса облака и расширение
раздела/LVM/ФС в госте: выполнение одного не доказывает выполнение другого.

ДИСКИ, ФАЙЛОВЫЕ СИСТЕМЫ И INODE
Работаем на отдельном учебном устройстве, не на корневом диске стенда.
Диагностика: lsblk, findmnt, df -h, df -i, blkid, сведения о PV/VG/LV.
Расширение разбирается по слоям:
диск → раздел (если есть) → PV (если LVM) → VG → LV → файловая система.
Увеличенный существующий PV и добавленный новый PV требуют разных действий.
Сначала отдельно показываем каждый слой; потом автоматизируем процедуру.
ФС проверяется по доступной ёмкости, содержимому и возможности записи.

Опыт с inode:
1. Создать маленькую ext4 с заведомо ограниченным числом inode.
2. Измерить свободные блоки/inode; создать много пустых файлов на ней.
3. Получить ENOSPC при свободных байтах и исчерпанных inode.
4. Сравнить с заполнением блоков и с квотой; восстановить запись после очистки.
5. В отдельной ветви увеличить ФС и увидеть рост общего числа inode.
6. Создать ФС того же размера с другой плотностью inode и перенести данные.
7. Проверить права, владельцев, содержимое и требуемые links/ACL/xattrs;
   переключить приложение, сохранив старую копию для отката.

ext4: отношение bytes-per-inode задаётся при создании ФС и не меняется
на существующей ФС. Расширение добавляет inode с исходным соотношением.
Размер записи inode (-I) и число байтов на inode (-i) — разные параметры.
XFS: inode выделяются динамически, действует ограничение доли пространства;
его изменение и рост ФС изучаются отдельно. Запас не бесконечен.
Команды mkfs не применяются к устройству с нужными живыми данными.
Копирование работающей БД требует её согласованного backup-сценария.
Переносимость образов/loop не означает проверку облачного volume API.

МОНИТОРИНГ И РАЗБОР АВАРИЙ
Наблюдение начинается с журналов и метрик первого приложения. Затем
добавляем Prometheus, node_exporter, экспортёры БД/кэша, Grafana
и Alertmanager. Отдельно — сбор журналов и связь событий по request ID;
распределённые трассировки включаем при появлении нескольких сервисов.

Измеряем пользовательские задержки/ошибки и состояние зависимостей:
CPU/ожидание CPU, RAM/лимиты/OOM, дисковые байты/inode/I/O, сеть,
соединения и блокировки БД, hit ratio, eviction, replication lag.
Настраиваем правила, окно наблюдения, группировку и устранение повторов.
Определяем SLI, целевой SLO и бюджет ошибок на примере данного API.
Следим за числом временных рядов, частотой сбора и сроком хранения:
сам мониторинг расходует CPU, RAM и диск.

Практика: спровоцировать конкретный отказ → получить ожидаемое
оповещение → найти причину → устранить → увидеть восстановление.
Обязательны заполнение блоков, исчерпание inode, остановка сервиса,
плохой выпуск, недоступность кэша и перегрузка источника.
Красивый dashboard без проверенного обнаружения аварии не завершает задание.

KUBERNETES
Тот же продукт переносится из Compose; данные/миграции переносятся
явно, а не обещаются автоматически совместимыми между средами.
Первый профиль kind: Pod, Deployment, Service, ConfigMap, Secret,
probes, requests/limits, rollout/rollback. Узлы kind — контейнеры.
Это подходит для API и схем размещения, но не заменяет независимые ОС.

Следующий профиль: отдельные VM, kubeadm, containerd, CNI, DNS,
сетевой доступ, volumes и согласованный путь входящего трафика.
Один control-plane + два worker позволяют изучить размещение,
cordon/drain, отказ worker и ограничение доступных ресурсов.
Условие продолжения сервиса — достаточные реплики, ресурсы оставшихся
узлов и доступные данные; само наличие Kubernetes этого не гарантирует.
Для проверки NetworkPolicy нужен поддерживающий её CNI.
Ingress/Gateway требует соответствующего контроллера, HPA — источника
нужных метрик. Установка объектов API без этих компонентов не даёт функции.

StorageClass, PV/PVC, CSI и расширение PVC разбираются по слоям.
Возможность расширения определяется driver/StorageClass и хранилищем;
рост PVC не считается автоматически доступным на любом провайдере.
Диск одного узла может препятствовать запуску workload на другом.
Далее: Helm, RBAC, ограничение доступа, обновление узлов, резервирование
и восстановление etcd и приложения, затем HA control-plane и GitOps.
Копия etcd не включает автоматически содержимое volumes приложения.

ПЕРВЫЙ СКВОЗНОЙ ПРОДУКТОВЫЙ СЦЕНАРИЙ (ЭТАП 2)
Он следует за техническим прототипом сохранения/восстановления мира.
Запустить v1 каталога, создать записи, сохранить мир; развернуть v2
рядом и переключить запросы вручную. Внести ошибку v2 и вернуть v1,
не потеряв пользовательские записи. Зафиксировать команды, проверки
и измерения. После этого автоматизировать тот же выпуск средствами
Bash/CI и Ansible, затем воспроизвести инфраструктуру Terraform.
Так каждый новый инструмент решает уже наблюдавшуюся задачу.

ЧТО УЖЕ ЕСТЬ В БИБЛИОТЕКЕ
Есть проверенные отдельные эксперименты, но общего Compose-стенда нет.
Большинство runner-скриптов создают временное окружение, сами выполняют
опыт, проверяют его и очищают. Их надо разделить на подготовку,
самостоятельное упражнение и проверку результата.

Сети: PCAP, TCP/TLS, DHCP/DNS, реальные проверки NAT.
namespace-lab.sh имеет лишь зафиксированную синтаксическую проверку.
Linux: процессы, FD, COW, сигналы, pipe, epoll, fsync, cgroup/PSI и др.
Bash: 18 опытов, 137 проверок; временные файлы пока не образуют общий мир.
PostgreSQL: SQL, транзакции, WAL, backup/PITR, репликация.
--keep сохраняет остановленные данные; сетевой доступ требует адаптации.
Кэш: 110 реальных проверок плюс модели вытеснения и ресурсов.
--manual ждёт Enter, но после выхода удаляет окружение.

Текущие отчёты не подтверждают работоспособность будущих Docker-образов.
Версии в прежних испытаниях не назначаются автоматически версиями стенда.
Не испытаны в общем стенде: Memcached SASL/современный proxy,
разделение сети Redis, возврат старого primary Sentinel, измерение
времени восстановления клиента, PostgreSQL failover/fencing.
Источники состояния: */labs/README.txt, */ПРОВЕРКИ.txt и отчёты опытов.

ЭТАПЫ И КРИТЕРИИ ГОТОВНОСТИ
Этап 0. Первый технический прототип: основа практики.
Два последовательных задания, сохраняемый мир, независимая проверка,
контрольная точка, копия для поломки и восстановление. Измерить ресурсы.
Интерфейс книги добавляется после проверки жизненного цикла.

Этап 1. Linux, Bash, сеть и хранилище.
Реальные роли клиент/сервер, затем маршрутизация/NAT, DNS/TLS.
Постоянные конфиги, systemd на VM, отдельная дисковая практика.
Готовность: исправить сломанный маршрут, сохранить изменения после
перезапуска, расширить учебную ФС и объяснить ENOSPC по inode.

Этап 2. Приложение, PostgreSQL, Redis и Memcached.
Существующие проверки адаптируются к самостоятельной практике.
Измерить исходный сервис, внедрить кэш, объяснить цену и выигрыш.
Выполнить ручной blue-green, плохой выпуск и возврат трафика.
Готовность: наблюдаемые проверки доступа, данных и поведения клиента.

Этап 3. Git и CI/CD.
Повторить ручную доставку pipeline, настроить runner и registry.
Готовность: плохой commit не выпускается; конкретный образ доходит
до тестового окружения и Green; проверены переключение и rollback.
Отдельная задача — развернуть и восстановить собственный CI-сервер.

Этап 4. Ansible и Terraform.
Сначала воспроизвести ручную конфигурацию на чистой VM через Ansible.
Затем создать VM через Terraform и передать её в Ansible.
Готовность: повторяемый результат, пустой plan при отсутствии изменений,
обнаружение drift, сохранность state, ограниченная область destroy.
После этого соединить инфраструктурный pipeline с процессом выпуска.

Этап 5. Наблюдение и эксплуатация.
Метрики есть с начала; теперь развернуть полноценные dashboards,
правила и доставку оповещений, определить SLO, хранение и стоимость.
Готовность: предусмотренная авария обнаружена и объяснена по данным,
исправление подтверждено; проверена потеря самой системы наблюдения.

Этап 6. Репликация и отказы.
PostgreSQL replication, Redis Sentinel/Cluster, распределение Memcached.
Проверить сетевой разрыв, отказ процесса, возврат узла, переключение
клиента и границу сохранности. Измерить профиль и время восстановления.

Этап 7. Kubernetes.
Сначала kind и объекты API, затем несколько VM и эксплуатация узлов.
Готовность: тот же продукт выпускается, наблюдается и восстанавливается;
проверен отказ worker и объяснена зависимость от хранилища/резервов.
Отдельные следующие задачи — HA control-plane, GitOps и обновления.

РЕАЛИЗАЦИЯ И ВОСПРОИЗВОДИМОСТЬ
Начинаем с обычного Compose и небольших скриптов, без собственной
сложной платформы. Возможная оболочка: up, stop, shell, check,
save, restore, reset. Эти команды пока проектируются, не реализованы.

Фиксируем архитектуру, базовые образы по digest, версии инструментов,
seed данных и формат мира. Офлайн-пакет включает все образы и материалы;
запуск не должен неожиданно скачивать зависимости. Локальный Linux Engine
и Docker Desktop проверяются раздельно; устройство их сетей отличается.

Git должен хранить исходники сценариев, образы-рецепты, проверки
и фиксацию версий. Данные БД, секреты, локальные архивы и прогресс туда
не входят. Публичная версия книги ведётся в репозитории systems-handbook.
Покупка инфраструктуры, публикация книги и перенос Практикума не входят
в нынешнюю работу. Практикум остаётся отложен по просьбе пользователя.
