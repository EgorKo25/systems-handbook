От запроса к ответу: что видит каждый участник

Один HTTP-запрос и три точки наблюдения

Клиент отправил запрос на создание документа. В захвате видно подтверждение TCP, но страница всё ещё ждёт ответа. Можно ли уже сказать, что сервер создал документ? Чтобы ответить, проследим один запрос от памяти клиента до ответа приложения.

Какой запрос отправляем

Учебный сервер слушает TCP-порт 7000 на адресе 198.51.100.20. Соединение уже открыто. Клиент подготовил запрос HTTP с телом {"id":"A"}. Здесь HTTP открыт для разбора: в защищённом соединении TLS шифрует запрос до того, как байты попадут в TCP. Адреса в примере предназначены для документации.

Что отдаёт клиент

В нашем примере клиент передал заголовки, а затем отдельным вызовом send() записал тело в открытый сокет. Вызов вернул 10: ядро приняло все десять байтов тела. Это результат местной операции. В следующей главе мы увидим, как передать остаток при частичной записи и почему принятые байты могут ещё ждать на клиенте.

Как узнать порт в захвате

В строке HTTP Host: app.lab.test:7000 цифры порта передаются как текст: 37 30 30 30. В поле назначения TCP тот же номер занимает два байта: 1b 58. Сначала идёт старший байт. Чтобы восстановить число, умножьте 0x1b (27) на 256 и прибавьте 0x58 (88). Получится 7000. Если перепутать порядок, получится 22555.

Когда браузер разговаривает с прокси, номер в строке Host может отличаться от номера TCP-порта самого прокси. Первый читает HTTP-сервер, второй нужен TCP на принимающем узле. Словарь тома объясняет шестнадцатеричную запись и сетевой порядок байтов.

Как сервер узнаёт конец тела

В этом запросе HTTP клиент указал Content-Length: 10. Сервер сначала находит конец заголовков, затем читает десять байтов тела. Они могут прийти частями. Если вместо латинской A записать кириллическую Я в UTF-8, тело займёт одиннадцать байтов: d0 af заменят один байт 41. Если оставить длину 10, сервер получит по объявленной границе тело без закрывающей фигурной скобки.

Сервер получил только первые шесть байтов заявленного десятибайтного тела. Сколько ещё ему нужно для разбора полного тела?

Ответ

Четыре байта. Если соединение закроется раньше, HTTP-получатель обнаружит неполное сообщение.

Границы сообщения на разных участках

HTTP видит одно сообщение. TCP может разбить его байты по нескольким сегментам. Каждый из них обычно переносится внутри IP-пакета; на одном Ethernet-участке пакет переносит кадр. Ниже показан случай без фрагментации, с одним сегментом внутри пакета и одним пакетом внутри кадра.

Почему адрес сервера и адрес ближайшего узла различаются

Если сервер за маршрутизатором, на первом кабеле кадр адресован маршрутизатору. Вложенный IP-пакет всё ещё адресован серверу. Затем маршрутизатор выберет следующий участок и отправит пакет в новом кадре. Схему размещения этих адресов разобрали выше; как Linux выбирает ближайший узел, посмотрим на выводе команды выбора маршрута.

Что уже подтверждено

send() вернул число на клиенте. TCP-подтверждение из захвата означает, что принимающий TCP принял соответствующие байты потока. Серверное приложение может ещё ждать свою очередь на выполнение. О результате операции судят по ответу приложения: если API возвращает 201 Created с идентификатором, сервер сообщает о создании документа по контракту этого API.

Для расследования задержки запишите время отправки запроса и первого байта ответа. Затем отдельно сопоставьте TCP-обмен и время обработки на сервере. Один только интервал до ответа включает и передачу, и ожидание в приложении.

Где начать поиск сбоя

Если клиент ещё не записал все байты, начните с пути внутри отправителя. Если кадр ушёл, но запрос не виден на сервере, проследите кадр, маршрут и подтверждения TCP. Если запрос дошёл и TCP его подтвердил, проверьте приём на сервере и затем журнал приложения.
