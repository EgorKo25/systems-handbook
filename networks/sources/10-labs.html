Практикум рассчитан на чтение без интернета. У каждого опыта есть вопрос до запуска, ожидаемые наблюдения и их подробный разбор. Если на объекте нельзя выполнять команды или нужной утилиты нет, сначала решите задачу на бумаге, затем откройте ответ. Приведённого вывода достаточно, чтобы проследить ход опыта и проверить рассуждение.

Первые шесть опытов обходятся чтением состояния, файлами и локальным адресом 127.0.0.1. Два последних — дополнительные опыты в новых изолированных сетевых пространствах Linux. Никакие сценарии не запускаются при открытии книги. Сохранённый PCAP является искусственным примером и не содержит перехваченных учётных данных или трафика объекта.

Опыт 1. Подготовить автономное рабочее место

Предсказание. Для чтения захвата обязательно ли устанавливать Wireshark, программу графического анализа сетевых записей? Если имя сервера не разрешается, помешает ли это читать уже сохранённые IP-адреса в файле?

Откройте терминал в каталоге labs, который расположен рядом с учебником. Его памятка с командами тоже доступна без интернета. Следующая команда проверяет наличие программ. command -v сообщает, какую команду оболочка запустит под указанным именем: например, найдёт путь к исполняемому файлу в каталогах поиска. Здесь её результат используется только для проверки наличия; установка программ не выполняется.

for tool in python3 ip ss tcpdump tc; do
  if command -v "$tool" >/dev/null 2>&1; then
    printf '%s: есть\n' "$tool"
  else
    printf '%s: отсутствует\n' "$tool"
  fi
done
python3 --version

Разберём оболочку этой проверки. for tool in …; do …; done повторяет действия для каждого имени из списка. На каждой итерации переменная tool содержит одно имя, а запись "$tool" подставляет его одним аргументом. Конструкция if …; then …; else …; fi выбирает ветвь по коду завершения команды: ноль ведёт к then, ненулевой результат — к else. Команда printf печатает строку: %s заменяется именем программы, \n переводит строку.

Запись >/dev/null скрывает обычный вывод проверки, направляя его в специальный приёмник. Запись 2>&1 направляет туда же поток ошибок: число 2 обозначает стандартный поток ошибок, 1 — стандартный вывод. Порядок этих перенаправлений здесь существенен: сначала выбран приёмник для обычного вывода, затем к нему присоединён поток ошибок. Сведения о наличии программы печатает наша собственная строка printf. После цикла python3 --version отдельно выводит версию Python.

Пример возможного вывода:

python3: есть
ip: есть
ss: есть
tcpdump: отсутствует
tc: отсутствует
Python 3.12.3

Строка python3: есть означает, что можно выполнить разбор PCAP и опыт с локальным сокетом. Наличие ip позволяет читать адреса, маршруты и соседей; ss — состояние сокетов. Отсутствие tcpdump не мешает приложенному разборщику: он использует только стандартные модули Python. Отсутствие tc, утилиты управления очередями передачи, исключает только дополнительную демонстрацию искусственных потерь. Версия Python может отличаться; номер выше приведён как пример, а не условие совпадения до последней цифры.

Проверьте наличие учебных файлов:

python3 - <<'PY'
from pathlib import Path
for name in ["document-flow-http.pcap", "inspect-pcap.py",
             "loopback-framing.py", "namespace-lab.sh"]:
    p = Path(name)
    print(name, "найден" if p.is_file() else "НЕ НАЙДЕН")
PY

Здесь Path(name) обозначает путь относительно текущего каталога. Если все файлы «не найдены», сначала проверьте, в каком каталоге открыт терминал. Команда pwd выводит этот каталог. Введённый между маркерами PY текст оболочка передаёт программе Python через стандартный ввод. Запись python3 - просит прочитать программу именно оттуда. Этот способ передачи многострочного текста называется встроенным документом оболочки; отдельный файл программы создавать не требуется.

Если интересно самостоятельно воспроизвести эталон, в этом же каталоге есть make-example-pcap.py. Команда python3 make-example-pcap.py создаёт три результата — PCAP, текстовый разбор и карту полей — в новом временном каталоге и печатает его путь. Команда python3 make-example-pcap.py --output-dir ./my-generated-example использует указанный новый каталог. Он не должен существовать заранее: генератор откажется перезаписывать готовые материалы. Сеть ему не нужна; подготовленные файлы в labs сохраняются.

Ответ на предсказание

Готовую запись можно прочитать приложенной программой Python; Wireshark — ещё один способ её просмотра. Для анализа числовых адресов DNS не требуется. Автоматическое разрешение имён при просмотре записи может создавать лишнее ожидание; дальше у tcpdump указан параметр, запрещающий такие запросы. Если Python отсутствует, используйте приведённые в книге схемы, таблицы и текстовый разбор кадров: они содержат значения, необходимые для решения задач.

Опыт 2. Почему шесть отправок не означают шесть сообщений

Предсказание. Клиент сделал шесть вызовов отправки. Сколько раз сервер должен вызвать чтение? Может ли один вызов чтения получить половину числа, обозначающего длину сообщения? Можно ли получать ответ после завершения собственного направления отправки?

Запустите локальный пример:

python3 loopback-framing.py

Программа открывает слушающий сокет только на 127.0.0.1, адресе этого же компьютера. Номер порта выбирает ядро из свободных, поэтому не требуется освобождать фиксированный порт. Один поток исполнения играет сервер, другой — клиент. Данные проходят через TCP-стек операционной системы, но не через физическую карту, коммутатор или маршрутизатор. Это настоящий опыт с сокетами, а не опыт с электрическим сигналом Ethernet.

Путь: клиент 127.0.0.1 -> TCP ядра -> сервер 127.0.0.1
Клиент: 6 вызовов sendall; в потоке 19 байт
Сервер: сообщение 1 = b'HELLO'; сообщение 2 = b'WORLD!'
Сервер: recv после двух сообщений = b'' (конец клиентского потока)
Клиент: после shutdown(SHUT_WR) всё ещё получил b'OK'
Проверено: длины, содержимое, два направления и завершение

Первая строка указывает границу опыта: связь замыкается внутри ядра одного компьютера. Вторая считает вызовы функции Python sendall, а не TCP-сегменты и не системные вызовы ядра. Функция может выполнять повторные внутренние отправки, пока не передаст все переданные ей байты либо не встретит ошибку. Шесть вызовов выбраны так, чтобы разрезать данные посреди обозначения длины и посреди тела сообщения.

Наш прикладной протокол намеренно прост: перед каждым сообщением стоят четыре байта его длины в сетевом порядке. За числом 5 идут пять байтов HELLO; за числом 6 — шесть байтов WORLD!. Всего 4 + 5 + 4 + 6 = 19 байтов. TCP сохраняет их порядок, а сервер восстанавливает сообщения по собственному правилу. Строка с двумя сообщениями проверяет содержимое после восстановления, не делает предположений о размере отдельных результатов чтения.

Ключевая функция сервера выглядит так:

def receive_exact(sock, size):
    result = bytearray()
    while len(result) < size:
        part = sock.recv(size - len(result))
        if not part:
            raise EOFError("Поток закончился раньше полного сообщения")
        result.extend(part)
    return bytes(result)

bytearray() создаёт изменяемый накопитель байтов. Условие цикла означает «пока накоплено меньше необходимого». В recv передаётся верхняя граница требуемого количества, а не обещание получить ровно столько. Если надо четыре байта, функция может получить сначала один, затем три; она повторит чтение. Пустая последовательность b'' при положительном запрошенном размере обозначает конец принимаемого потока, а не обычную временную паузу. Для временной паузы блокирующее чтение ждёт, а при настроенном пределе ожидания сообщает ошибку ожидания.

После двух сообщений клиент вызывает shutdown(SHUT_WR): сообщает, что в своём направлении больше данных не пришлёт. Это отличается от немедленного уничтожения обеих сторон общения. Сервер дочитывает поток до конца и отправляет сообщение OK обратно; клиент его принимает. Строка с b'' показывает конец клиентского направления, следующая — ещё работающее обратное направление. Это практическое проявление двух независимых половин TCP.

В программе ограничена максимальная прикладная длина — 1024 байта. Это предел одного сообщения нашего учебного протокола. Без проверки размера ошибочное поле длины могло бы заставить сервер выделить слишком много памяти или долго ждать отсутствующие данные. TCP позволяет передать большой файл, но допустимый размер прикладного сообщения и реакцию на его нарушение определяет само приложение.

Ответ на предсказание

Количество чтений заранее не определяется количеством отправок. Одна отправка может потребовать нескольких чтений, несколько отправок — попасть в одно. Сервер обязан выдерживать частичное получение даже четырёхбайтного поля длины. После закрытия направления записи получать встречные данные можно. Если заменить накопление одним sock.recv(4), пример иногда будет случайно работать, но общий алгоритм станет неверным: локальная скорость и удачное планирование потоков не являются гарантией протокола.

Дополнительная задача. В первой длине пришли байты 00 00, затем пауза, затем 00 05. Что должна делать функция? А если вместо второй порции пришёл конец потока?

Разбор

В первом случае накопить первые два байта, продолжить ожидание ещё двух, затем прочитать пять байтов тела. Во втором случае сообщить об оборванном сообщении. Нельзя дополнять длину случайными нулями, принимать отсутствующие байты за длину ноль или считать такую ситуацию успешным окончанием полноценного сообщения.

Опыт 3. Найти сокет и маршрут, не меняя настройки

Предсказание. Если известен адрес сервера, как узнать выбранные интерфейс и исходный адрес без отправки HTTP? Почему прослушивающий сокет и установленное соединение могут иметь один локальный порт, но разные строки в выводе?

ip -br address
ip route get 198.51.100.20
ip -s link
ss -ltn
ss -tn
ss -tin
cat /proc/net/sockstat

Эти команды читают состояние. Они не добавляют адресов и маршрутов. Адрес 198.51.100.20 остаётся документационным примером; запрос ip route get просит ядро рассчитать маршрут, а не подключается к этому адресу. Чтобы узнать путь к своему настоящему серверу ДО, подставьте его известный числовой адрес.

Рассмотрим условный результат из нашей топологии:

198.51.100.20 via 192.0.2.1 dev c0 src 192.0.2.10
    cache

via 192.0.2.1 — следующий узел, которому надо передать пакет. dev c0 — выходной сетевой интерфейс. src 192.0.2.10 — исходный адрес, который ядро выбрало бы при обычных условиях этого запроса маршрута. Английское cache означает «кеш», сохранённый результат. В данном выводе слово относится к результату поиска маршрута ядром. DNS хранит соответствия имён и адресов отдельно. На реальном компьютере вывод может отличаться из-за правил маршрутизации, виртуальных сетей и нескольких исходных адресов.

В ss -ltn буква l выбирает слушающие сокеты, t — TCP, n запрещает подменять числа именами. В ss -tn показаны обычные TCP-соединения. Параметр i просит дополнительные сведения TCP, если они доступны. Пример двух разных состояний:

LISTEN 0 128 0.0.0.0:7000       0.0.0.0:*
ESTAB  0   0 192.0.2.10:49152   198.51.100.20:7000

LISTEN означает ожидание новых соединений. 0.0.0.0:7000 в этой строке — привязка ко всем локальным IPv4-адресам в данном сетевом пространстве. Звёздочка у встречной стороны показывает отсутствие конкретного собеседника у слушателя. ESTAB означает установленное соединение с указанными адресами и портами обеих сторон. Выше приведены два отдельных примера: слушатель на сервере и соединение на клиенте. После принятия соединения серверный слушатель продолжает ждать следующих клиентов, а отдельный принятый сокет обслуживает текущего клиента. У слушателя и принятого сокета локальный порт службы совпадает.

Числа очередей надо читать с учётом состояния. Для установленного соединения Recv-Q обычно показывает число принятых байтов, ещё не забранных приложением, Send-Q — число байтов, переданных приложением отправляющему TCP, но ещё не подтверждённых встречной стороной. Часть этих байтов может пока ожидать отправки в сеть. Для слушателя Recv-Q показывает число соединений, ожидающих принятия приложением, а Send-Q — предел этой очереди. Таким образом, «128» у слушателя измеряется в соединениях. Дополнительный вывод зависит от версии утилиты и ядра.

Команда ip -s link выводит счётчики интерфейса: принятые и переданные пакеты и байты, ошибки и отбрасывания. Это накопленные числа, а не автоматически скорость «байтов в секунду». Для оценки скорости нужны два измерения и разность, делённая на прошедшее время. Один отброшенный пакет в общем счётчике не доказывает, что потерялся именно наш запрос. /proc/net/sockstat даёт общие сведения об использовании сокетов; это не список сообщений приложения.

Ответ на предсказание

Маршрут можно спросить у ядра отдельно от сетевого обмена. Слушатель описывает место приёма новых соединений, а принятый сокет — конкретный разговор. Общий порт службы не делает их одним объектом. Если в ss не виден процесс другого пользователя, это может быть ограничением прав просмотра; отсутствие имени процесса не равно отсутствию сокета. Для основной задачи не требуется запускать все команды от root.

Опыт 4. Прочитать готовый захват без сетевого доступа

Предсказание. Какой ACK должен следовать за запросом длиной 73 байта с SEQ 1001? Почему кадр без данных занимает 60 байтов, а не 54?

python3 inspect-pcap.py --verify-example

Скрипт открывает локальный файл и последовательно разбирает общий заголовок PCAP, заголовки записей, Ethernet, IPv4 и TCP. Он не подключается к серверу. Для удобства чтения ниже оставлены главные колонки результата; полный вывод дополнительно содержит адреса и флаги.

№   SEQ    ACK    данные  IP  TCP  доп.
1   1000      0       0  OK   OK     6
2   9000   1001       0  OK   OK     6
3   1001   9001       0  OK   OK     6
4   1001   9001      73  OK   OK     0
5   9001   1074       0  OK   OK     6
6   9001   1074     106  OK   OK     0
7   9107   1074       0  OK   OK     6
8   1074   9108       0  OK   OK     6
9   1074   9108       0  OK   OK     6
10  9108   1075       0  OK   OK     6
Проверено: 10 кадров, длины, обе контрольные суммы, SEQ/ACK, HTTP.

Колонки IP и TCP содержат результаты двух независимых вычислений сумм. «Доп.» — число байтов Ethernet-дополнения за границей IP. Строка 4 несёт 73 прикладных байта, поэтому строка 5 подтверждает 1001 + 73 = 1074. Строка 6 приносит 106 встречных байтов. В строке 7 сервер завершает своё направление в позиции 9107; подтверждение становится 9108. В строке 9 своё направление заканчивает клиент в позиции 1074, поэтому последнее подтверждение равно 1075.

Режим --verify-example проверяет именно наш эталон. Его нельзя использовать как универсальный критерий правильности любого чужого захвата. Разборщик намеренно понимает ограниченный формат: классический PCAP с микросекундной временной отметкой, Ethernet II без VLAN, IPv4 и нефрагментированный TCP. PCAPNG — другой, более развитый формат хранения записей; Linux cooked capture — служебное представление канального заголовка Linux вместо настоящего Ethernet-заголовка. Если файл использует их, туннель или IPv6, отказ учебного скрипта ничего не говорит о корректности самого трафика.

Если tcpdump уже установлен, тот же файл можно посмотреть этой консольной программой анализа сетевых записей:

tcpdump -nn -S -r document-flow-http.pcap
tcpdump -nn -S -XX -r document-flow-http.pcap 'tcp port 7000'

-r читает файл вместо захвата с интерфейса. -nn сохраняет числовые адреса и порты, поэтому не нужны DNS и справочник имён служб. -S показывает абсолютные номера SEQ/ACK: они совпадут с книгой. Без него анализатор может использовать относительные номера для удобства. -XX добавляет шестнадцатеричную запись вместе с канальным заголовком. Выражение в одинарных кавычках выбирает TCP с участием порта 7000; оно не ищет число 7000 в тексте HTTP.

Ответ на предсказание

Ожидаемый ACK — 1074: байты до номера 1073 включительно приняты, следующий ожидаемый имеет номер 1074. Шесть байтов дополнения доводят Ethernet-кадр без FCS с 54 до минимальных 60 байтов. Это дополнение находится за пределами IP-пакета и не передаётся HTTP. Чтобы определить длину TCP-данных, из объявленной длины IP вычитают длины IP- и TCP-заголовков. У чистого подтверждения результат равен нулю.

Опыт 5. Изменить один байт копии и понять область защиты

Предсказание. Если изменить букву G в GET, но оставить заголовки прежними, какая проверка перестанет сходиться: IP, TCP, обе или ни одна? Станет ли от этого IP-адрес другим?

Опыт работает только с временной копией файла. Он не отправляет повреждённый пакет в сеть и не меняет исходный учебный захват:

python3 - <<'PY'
from pathlib import Path
import struct, tempfile, subprocess, sys
data = bytearray(Path("document-flow-http.pcap").read_bytes())
pos = 24
for number in range(1, 5):
    size = struct.unpack_from("<I", data, pos + 8)[0]
    start = pos + 16
    if number == 4:
        assert data[start + 54] == ord("G")
        data[start + 54] ^= 1
        break
    pos = start + size
with tempfile.TemporaryDirectory(prefix="dfbook-") as folder:
    copy = Path(folder) / "changed.pcap"
    copy.write_bytes(data)
    subprocess.run([sys.executable, "inspect-pcap.py", str(copy)], check=True)
PY

bytearray позволяет изменить один байт в памяти. Первые 24 байта — общий заголовок нашего PCAP. Затем каждая запись имеет 16-байтный заголовок и указанную в нём длину кадра. Цикл доходит до четвёртой записи, а смещение 54 относится уже к началу Ethernet внутри этой записи. Проверка assert убеждается, что там действительно буква G. Операция ^= 1 меняет младший разряд: код 47 превращается в 46, букву F. Временный каталог автоматически удаляется после разбора.

У четвёртой строки станет IP OK, TCP BAD: OK обозначает успешную проверку, BAD — несовпадение вычисленной суммы с записанной. В отображении прикладных данных появится FET /api/session…. IP-заголовок не менялся, поэтому его отдельная сумма по-прежнему верна. TCP проверяет и данные, поэтому его прежняя сумма больше не соответствует содержимому. Адреса, порты и длины останутся прежними.

Учебный разборщик читает файл для исследования и специально показывает данные даже при неверной сумме. Это позволяет найти изменённый байт и понять причину ошибки проверки. Принимающий TCP, обнаруживший несовпадение контрольной суммы, отбрасывает сегмент. В результате повреждённые байты не добавляются в поток, который читает приложение.

Ответ на предсказание

Откажет TCP-проверка, IP-проверка останется успешной. Если пересчитать TCP-сумму после намеренного изменения, обе проверки снова сойдутся, хотя смысл запроса изменён. Именно поэтому контрольная сумма не является криптографической защитой от подмены. У настоящего локального захвата к объяснению BAD надо добавить возможное аппаратное вычисление суммы после точки захвата; у этого созданного файла такой причины нет.

Опыт 6. Расследование по наблюдениям

Этот опыт полностью решается чтением. Для каждого случая сначала укажите, до какого участника или уровня данные доказанно дошли. Затем перечислите возможные причины остановки и выберите наблюдение, по которому их удастся различить.

Случай А. В исходящем захвате виден SYN, затем его повторы. SYN + ACK и RST не видны. Приложение сообщает об истечении ожидания. Доказано ли, что сервер выключен?

Разбор

Доказано лишь, что в этой точке видна отправка SYN и не виден подходящий ответ. Возможны недоступность сервера, потеря прямого пакета, потеря обратного ответа, фильтрация, неверный маршрут либо другая точка захвата. Следующий хороший шаг — посмотреть приём на стороне сервера или ближайшей доступной границе, а также проверить выбранный маршрут и соседей. Выключенный сервер — гипотеза, а не содержание наблюдения. Проверка ping может добавить сведения об ICMP, но не заменяет проверку TCP-порта.

Случай Б. В ответ на SYN пришёл RST + ACK, приложение сразу пишет «соединение отклонено». Чем это отличается от случая А?

Разбор

Получен явный отрицательный ответ, поэтому это другая картина, чем молчание до предела ожидания. Частая причина — отсутствие слушателя на нужном адресе и порту. Но ответ может формировать и промежуточный фильтр. Надо проверить серверный слушатель через ss -ltn, адрес привязки, порт, службу и журналы, а при необходимости установить источник отрицательного ответа по наблюдениям с двух сторон. Быстрая ошибка и тайм-аут требуют разных первых гипотез.

Случай В. Рукопожатие завершилось, запрос подтверждён ACK 1074, HTTP-ответа долго нет. Можно ли считать, что проблема уже точно в базе данных?

Разбор

Подтверждение доказывает доставку непрерывных TCP-данных до принимающего стека, а не выполнение обработчика. Приложение могло не прочитать сокет, ожидать ещё заголовки из-за ошибки формирования сообщения, стоять в очереди, ждать базу или файловое хранилище. Следующий шаг — сопоставить серверный сокет, процесс и журнал запроса. Если данные накоплены в очереди приёма и не забираются, это одна граница проблемы; если обработчик начал работу и ждёт запрос к базе — другая. База является возможным продолжением расследования, а не выводом из ACK.

Случай Г. Клиент получил HTTP 500 и текст ошибки. «Сеть сломалась» — подходящее итоговое объяснение?

Разбор

Прикладной ответ уже прошёл обратно до клиента. По крайней мере обмен для этого запроса состоялся. Код 500 обозначает ошибку обработки на уровне HTTP, причины нужно искать в приложении и зависимостях. Сетевая проблема между приложением и его базой всё ещё возможна, но это другой участок и другой разговор. Нельзя из HTTP 500 заключить, что клиент не может соединиться с веб-службой: соединение уже произошло.

Запишите для каждого случая четыре строки: «Наблюдение», «Что оно доказывает», «Что ещё не известно», «Следующая проверка». Для выбранной проверки поясните, какие результаты ожидаются при каждой из рассматриваемых причин. Так можно проверить ход рассуждения до изменения настроек.

Опыт 7. Дополнительно: две сети и один маршрутизатор внутри Linux

Теперь можно воспроизвести топологию из байтового разбора. Сетевое пространство имён — изолированная сетевая среда ядра: у неё собственные интерфейсы, маршруты, соседи и ряд сетевых настроек. Это не три физических компьютера и не три отдельных ядра. Пара виртуальных Ethernet-интерфейсов veth соединяет два таких пространства: передача через один конец становится приёмом на другом.

Этот опыт требует Linux с поддержкой пространств имён и veth, права создавать новые пространства, команды ip, python3 и sysctl. Последняя читает или меняет параметры ядра; наш сценарий использует её внутри созданного сетевого пространства. Нужны административные полномочия пользователя root, которые здесь запрашивает команда sudo. Сценарий находится в namespace-lab.sh. Его стоит сначала прочитать целиком. Он создаёт три пространства с уникальным префиксом dfbook-…, размещает оба конца виртуальных соединений сразу внутри них, задаёт только учебные адреса и два конкретных обратных маршрута. Пересылка IP включается только внутри нового пространства маршрутизатора.

sudo bash namespace-lab.sh --run

sudo здесь нужен для создания изоляции. Сценарий не добавляет маршрут по умолчанию компьютеру, не меняет физические интерфейсы, не правит общий межсетевой экран и не включает пересылку IP в основном пространстве хоста. При завершении или обычном прерывании обработчик очистки удаляет только созданные этим запуском пространства. Если среда запрещает создание пространств, изучите приведённый ниже вывод. Для выполнения опыта в таком случае понадобится другая учебная среда с поддержкой этих механизмов.

Предсказание. Какой MAC появится в таблице соседей клиента после успешного HTTP: сервера или маршрутизатора? Нужен ли клиенту общий маршрут по умолчанию для связи с единственной известной удалённой подсетью?

Значимая часть ожидаемого вывода:

Маршрут клиента:
198.51.100.20 via 192.0.2.1 dev c0 src 192.0.2.10
Маршрут сервера обратно:
192.0.2.10 via 198.51.100.1 dev s0 src 198.51.100.20
Клиент получил: HTTP/1.1 200 OK
Сосед клиента (MAC маршрутизатора):
192.0.2.1 dev c0 lladdr 02:00:00:00:00:01 REACHABLE
Клиент получил: HTTP/1.1 200 OK
Опыты завершены; временные пространства удаляются.

Уникальные имена пространств и порядок строк сервера и клиента могут отличаться из-за параллельной работы. REACHABLE означает недавно подтверждённую достижимость соседа. STALE означает, что запись ещё есть, но её подтверждение уже не считается свежим; перед дальнейшим использованием стек при необходимости проверит достижимость. Появление STALE само по себе не означает поломку. Ключевой результат — сосед 192.0.2.1 с MAC 02:00:00:00:00:01, потому что именно его интерфейс доступен клиенту на ближайшем участке.

Прямой маршрут клиенту задан к 198.51.100.0/24, обратный серверу — к 192.0.2.0/24. Общий маршрут по умолчанию не требуется: обе нужные удалённые подсети описаны явно. Маршрутизатор имеет две непосредственно подключённые сети. Без обратного пути успешная передача SYN в одну сторону ещё не дала бы завершённого рукопожатия.

Сервер этого опыта отвечает коротким телом OK\n, а не JSON из искусственного PCAP. Живой TCP-стек сам выбирает начальные номера, параметры, временные порты, количество сегментов и время подтверждений. Поэтому совпадать должны причинные отношения, а не все байты эталона. Этот опыт демонстрирует выбор следующего узла и двусторонность пути; точную арифметику фиксированных заголовков проверяет предыдущий файл.

Ответ на предсказание

В таблице соседей клиента будет ближайший маршрутизатор. Адрес сервера находится вне подсети клиента, поэтому клиент не обязан узнавать серверный MAC. Общий маршрут не нужен, достаточно конкретного пути. Успешные два HTTP-ответа подтверждают работоспособность созданного прямого и обратного пути в пределах виртуального опыта.

Опыт 8. Дополнительно: отличить молчание сети от отказа службы

При наличии tc тот же сценарий умеет искусственно отбросить все исходящие передачи на клиентском виртуальном интерфейсе. Все изменения очереди происходят только внутри нового пространства клиента. Запуск отдельного опыта:

sudo bash namespace-lab.sh --run --loss

Сначала выполняется успешный запрос. Затем в изолированном клиенте к интерфейсу c0 добавляется очередь с правилом потери 100%. Следующее соединение не завершается за две секунды, потому что его SYN не проходит этот участок. Потом искусственная очередь удаляется, и повторная попытка снова получает ответ. Важные строки:

Клиент получил: HTTP/1.1 200 OK
Ожидаемо: SYN потерян, соединение не установлено за 2 секунды
… netem … loss 100% …
… dropped …
Клиент получил: HTTP/1.1 200 OK

Две секунды — предел ожидания клиентской программы в этом опыте, а не универсальное время отказа TCP. Число повторов SYN зависит от ядра и времени. netem — название механизма имитации условий сети. Его счётчик dropped, «отброшено», показывает потери в созданной нами очереди. Если механизм имитации недоступен, tc сообщит об этом; обычный режим без --loss остаётся отдельным вариантом.

В этом опыте сервер не получил новую попытку установления соединения: SYN был отброшен на клиентском интерфейсе. Ожидание завершилось в клиентской программе, а ответ сервера вообще не формировался. Причина известна, поскольку мы сами задали потери. В незнакомой сети похожий предел ожидания может иметь другие причины; для их различения нужны дополнительные наблюдения, как в предыдущем опыте.

Итоговая задача. Если вместо потерь остановить слушающую службу, оставив путь рабочим, какой результат ожидается? А если оставить слушатель, но не читать и не отвечать после принятия?

Разбор

При отсутствии слушателя и отсутствии фильтра, скрывающего отказ, обычный TCP-хост ответит RST, и установление будет отклонено быстро. При работающем слушателе рукопожатие может завершиться, но приложение затем не выдаст HTTP-ответ; запрос при этом способен быть подтверждён TCP. Это три разные границы: не прошёл SYN, пришёл явный отказ, установленное соединение не продвинулось на прикладном уровне.

Проверка учебных материалов и условия запуска

Для поставляемого искусственного захвата программно проверены количество кадров, длины Ethernet/IP/TCP, обе контрольные суммы, номера последовательности, подтверждения и содержимое HTTP. Локальная программа с двумя сообщениями выполнена: восстановление частичных данных, конец направления и встречный ответ проверяются встроенными проверками самой программы. Необязательный сценарий пространств имён проверен на синтаксис оболочки; доступность его механизмов зависит от ядра и прав на вашем компьютере. Основная часть практикума не требует запускать его.

Первичные справочники для дальнейшего чтения: стандартный модуль socket в Python, сетевые пространства имён Linux, команда ip route, команда ss, механизм имитации сети netem. Эти ссылки не нужны для прохождения опытов: необходимые команды, ожидаемые результаты и объяснения уже находятся в книге.
