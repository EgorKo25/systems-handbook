OSPFv2: от Hello до базы одной области

Состояния соседей, две формы LSA и исчезновение одного маршрутизатора

В главе о маршрутизации мы разобрали поля Hello. Теперь выясним, почему на одном Ethernet два соседа остаются в 2-Way, хотя оба видят одну топологию, и что изменится в базе, если один из них перестанет отвечать.

Четыре маршрутизатора и один Ethernet

Коммутатор соединяет четыре порта без разделения на разные сегменты. На каждом маршрутизаторе этот интерфейс настроен как OSPF broadcast, то есть сеть с общей рассылкой, в области 0. Маска /24, HelloInterval 10 с, RouterDeadInterval 40 с и параметры аутентификации совпадают. У каждого маршрутизатора ещё есть интерфейс обратной петли (loopback), чей /32 объявляется в той же области. Выборы завершились: A стал назначенным маршрутизатором (DR), B — резервным назначенным (BDR). Приоритет 0 у C и D исключает их из выборов. Позднее появление маршрутизатора с большим приоритетом само по себе не смещает действующего DR.

Router ID — идентификатор маршрутизатора в OSPF. Для простоты мы вручную назначили ему то же значение, что и адресу loopback. В Hello поля DR и BDR содержат IPv4-адреса интерфейсов DR и BDR на этом Ethernet, а список соседей — Router ID.

Что изменилось между Init и Full

Состояние относится к конкретному соседу на конкретном интерфейсе. Обозначение «C видит D в Init» описывает запись у C. Запись у D о C в этот момент может быть другой. Двусторонняя связь начинается, когда получатель находит свой Router ID в Hello соседа. Смежность (adjacency) — отношение, при котором пара синхронизирует базы. На общем Ethernet её строят пары с DR или BDR. Остальные пары могут весь срок работы оставаться в 2-Way.

СостояниеКак его распознать
DownПодтверждённого контакта нет. Так же заканчивается ожидание после последнего принятого Hello, если истёк таймер неактивности.
InitПолучен допустимый Hello, но локального Router ID пока нет в его списке соседей.
2-WayПолучатель увидел себя в Hello. C и D остаются здесь. У пары A и D то же событие может сразу запустить ExStart, поэтому отдельной строки 2-Way в снимке может не быть.
ExStartПара договаривается по пакетам Database Description (DD) о начальной последовательности и ведущем обмена. Ведущий определяется большим Router ID, поэтому здесь D может вести обмен с A, хотя A — DR.
ExchangeDD несут заголовки объявлений LSA, то есть опись базы. Получатель запрашивает записи, которых у него нет или чья локальная копия старее.
LoadingОписи уже обменяны, но остались запросы. Link State Request (LSR) запрашивает запись, Link State Update (LSU) доставляет полный LSA. Link State Acknowledgment (LSAck) подтверждает получение при распространении LSA. При пустом списке запросов после Exchange пара может сразу перейти в Full.
FullОбмен описаниями закончен, нужные записи получены. Последующие изменения распространяются по смежностям.

Attempt тоже есть в автомате RFC, но используется для настраиваемого соседа на неброадкастной сети NBMA. В данном Ethernet-сценарии этого состояния нет.

В таблице пять смежностей. Представь, что D только включился, а C уже работает. C примет первый Hello D и отметит Init, если не увидит себя в списке. Как только C увидит свой Router ID в принятом Hello от D, соседство перейдёт в 2-Way. Тем временем D получит опись базы от A и B. Если после обмена описями D ещё ждёт записи от A, на его стороне будет Loading. После получения записей D достигнет Full с A. C узнает о новых записях по своим смежностям с A или B. Для получения общей топологии ему не требуется входить в Full с D.

Из чего складывается граф области

LSDB (база состояния связей) хранит объявления LSA. В базе области экземпляр записи ищут по тройке «тип LSA, Link State ID, Advertising Router». Последнее поле указывает Router ID автора. Для записи с тем же ключом номер последовательности, контрольная сумма и возраст участвуют в сравнении экземпляров. Поэтому два последовательных объявления об одном сегменте занимают один ключ, даже когда список подключённых маршрутизаторов поменялся.

Каждый маршрутизатор выпускает Router-LSA, тип 1. В нашем случае у каждого две записи внутри объявления. Связь с транзитной сетью имеет внутренний тип связи 2. Её Link ID равен IPv4-адресу DR на Ethernet, а Link Data — адресу собственного Ethernet-интерфейса. Тупиковая связь к loopback имеет внутренний тип 3: Link ID равен адресу loopback, Link Data — маске 255.255.255.255, стоимость равна 0. Тип связи внутри Router-LSA и тип самого объявления — разные поля.

Network-LSA, тип 2, выпускает DR, когда у него есть хотя бы один сосед в Full. Здесь ключ равен (2, 10.0.0.1, 192.0.2.1), маска 255.255.255.0, список подключённых Router ID — 192.0.2.1, 192.0.2.2, 192.0.2.3, 192.0.2.4. DR включает себя и соседей в Full. BDR в этом состоянии собственного Type 2 для сегмента не выпускает.

В установившемся состоянии у каждого из четырёх маршрутизаторов здесь пять записей LSDB. Для расчёта кратчайшего пути Type 1 задают рёбра от маршрутизаторов к общей вершине N, а Type 2 — обратные рёбра от N с нулевой стоимостью. На первом этапе SPF связь между маршрутизатором и общей сетью учитывают, когда LSA обеих вершин описывают её с двух сторон. Тупиковую сеть loopback добавляют на втором этапе из Router-LSA уже достижимого маршрутизатора. Например, из C к loopback D стоимость равна 30 + 0 + 0 = 30. Ожидаемый IP следующего перехода на общем Ethernet — 10.0.0.4. Роль DR определяет обмен объявлениями, поэтому пользовательский IP-пакет не обязан идти через A.

Два исхода тишины после последнего Hello

После полной сходимости D перестаёт отправлять Hello. Соседи продолжат работу, коммутатор сохраняет их физические соединения. Считай от последнего принятого Hello D. В первом случае в t = 30 с приходит допустимое Hello D, всё ещё содержащее Router ID соседей. Во втором случае к t = 41 с от D ничего не пришло, таймер уже истёк, а обновлённый Type 2 успел распространиться. D исчез внезапно и не отзывал свой Type 1. Какие строки в таблицах сохранятся, и что случится с маршрутом из C к 192.0.2.4/32?

Разбор обоих исходов

В первом случае таймер соседей обновляется до истечения. Состояния и список Type 2 сохраняются, маршрут имеет стоимость 30. Во втором случае записи о D переходят в Down и могут исчезнуть из вывода соседей. A остаётся DR и заново публикует тот же ключ Type 2 со списком A, B, C. Type 1 от D может ещё оставаться в LSDB до старения. Он не даёт достижимости D из C, поскольку у N уже нет обратной связи с D. В этой схеме других путей нет, поэтому OSPF-маршрут к loopback D исчезает.

Для автономной проверки сохрани следующий код в своей записываемой папке как ospf-area.py. Запусти python3 ospf-area.py 30 и python3 ospf-area.py 41 от обычного пользователя. Значение до 40 означает своевременно полученное взаимное Hello, значение после 40 — наблюдение после истечения таймера и распространения новой записи. Точное совпадение с моментом истечения в опыте пропущено, поскольку порядок событий при равенстве важен.

from itertools import combinations
from sys import argv

observed = int(argv[1])
if observed < 0 or observed == 40:
    raise SystemExit("Choose 0..39 (valid Hello) or >40 (expired timer)")

routers = "ABCD"
ids = {r: f"192.0.2.{i}" for i, r in enumerate(routers, 1)}
ips = {r: f"10.0.0.{i}" for i, r in enumerate(routers, 1)}
costs = dict(zip(routers, (10, 20, 30, 40)))
dr, bdr = "A", "B"
alive = set(routers if observed < 40 else "ABC")

def neighbor(left, right):
    if not {left, right} <= alive:
        return "Down"
    return "Full" if {left, right} & {dr, bdr} else "2-Way"

for left, right in combinations(routers, 2):
    print(left, right, neighbor(left, right))

# Retain D's last Type 1 in the snapshot, even when D is down.
for r in routers:
    print("Type 1:", ids[r], "transit", ips[dr], ips[r], costs[r],
          "stub", ids[r] + "/32", 0)

members = {dr} | {r for r in routers if r != dr and neighbor(dr, r) == "Full"}
print("Type 2 key:", (2, ips[dr], ids[dr]), "mask: 255.255.255.0")
print("Type 2 members:", " ".join(sorted(members)))
if {"C", "D"} <= members:
    print(f"C to D: cost {costs['C']}, via {ips['D']}")
else:
    print("C to D: absent")

Первый запуск выдаёт пять пар Full и одну пару 2-Way, строку Type 2 members: A B C D и C to D: cost 30, via 10.0.0.4. Второй выдаёт три пары Full, три пары Down, Type 2 members: A B C и C to D: absent. В обоих запусках напечатаны четыре Type 1, включая возможную ещё не состарившуюся запись D. Во втором запуске пары с D показывают состояние со стороны оставшихся маршрутизаторов.

Это расчёт по правилам для заданного Ethernet и выбранных моментов наблюдения. Он не запускает OSPF, не генерирует пакеты и не оценивает задержку. В реализации состояние смотрят у указанных участников, ключи и экземпляры — в дампе LSDB, а фактическую потерю трафика — серией запросов к loopback. Для опыта со временем отсчёт ведут от последнего принятого Hello, затем отдельно отмечают исчезновение соседа, изменение Type 2 и удаление маршрута. В следующей главе разберём, из каких составляющих получается измеренная задержка передачи.
