Теперь проследим обработку запроса по исходникам ДО, которые мы скопировали. Разберём роли браузера, Apache, отдельной программы обработки и базы данных, а затем выберем наблюдения для каждого этапа. На работающем сервере эту схему сопоставляют с активной конфигурацией, адресами и журналами.

1. Что известно из исходников, а что ещё нужно проверить

В локальной копии проекта /home/documents/document-flow файл README.md описывает веб-сервер Apache, который отдаёт браузерную часть приложения и вызывает отдельные программы обработки запросов по правилу CGI. Их назначение и способ запуска разберём ниже. Конфигурация services/backend/config/astra/apache.conf содержит виртуальный узел на порту 7000, а правило для /api/session направляет запрос к session-get.cgi. В файле программы services/backend/cmd/cgi/session-get/main.go вызывается cgi.Serve(handler). Это проверенные факты содержимого копии от 27 октября 2026 года.

Виртуальный узел — набор правил, по которым один экземпляр Apache обслуживает выбранное имя или адрес и порт. Для приёма соединений Apache также должен слушать нужный порт. На работающей машине проверяют, какие файлы конфигурации подключены, какие сокеты слушают и какой обработчик указан в журнале конкретного запроса. Так схема из исходников связывается с фактической обработкой.

2. Браузер: от действия пользователя до запроса

Фронтенд — часть приложения, которая работает с интерфейсом пользователя; здесь это код и ресурсы, загружаемые браузером. Серверная часть, часто называемая backend, выполняет обработку на сервере. Нажатие кнопки сначала запускает код интерфейса. Он может изменить экран вообще без сети либо создать запрос. Панель сети в инструментах разработчика браузера позволяет увидеть, какое действие произошло в действительности.

Панель сети браузера показывает прикладную операцию: URL, метод, заголовки, тело, статус и длительность. Несколько запросов могут проходить по одному уже установленному соединению, а один запрос — передаваться несколькими сегментами TCP. Поэтому одной строке HTTP-запроса в браузере может соответствовать несколько строк пакетов в tcpdump. Панель браузера помогает исследовать действия приложения, а запись пакетов — их передачу по сети.

Наш учебный запрос GET /api/session специально мал и читаем. api в пути — принятое обозначение программного интерфейса приложения: обращаясь к нему, браузер запрашивает данные или действия серверной части. В реальном доменном обмене могут появиться ответ 401 с предложением подтвердить личность, повтор запроса с токеном — служебными данными аутентификации — и затем ответ приложения. Для анализа такого случая нужно сопоставить всю последовательность запросов и ответов. Код 401 может быть ожидаемым этапом проверки личности.

3. Apache принимает HTTP-запрос и выбирает обработчик

Веб-сервер принимает HTTP и решает, что делать с запросом: отдать файл, вызвать обработчик, перенаправить или отказать. Apache читает поток, выделяет сообщение и сопоставляет имя узла и путь с конфигурацией. Число 7000 используется TCP для выбора сокета, а путь /api/session разбирается позже на уровне HTTP. Маршрутизатору между компьютерами этот путь обычно не нужен.

Фрагменты из конфигурации исходников:
<VirtualHost *:7000>
    ServerName app.lab.example.test
    DocumentRoot /opt/document-flow
    ...
    ScriptAlias /cgi-bin/ /opt/build/cgi-bin/
    ...
    RewriteRule ^/api/session$ /cgi-bin/session-get.cgi [PT,L]

ServerName задаёт имя виртуального узла. DocumentRoot — базовый каталог статических файлов: готовых файлов, содержимое которых сервер отправляет браузеру. ScriptAlias связывает начало пути /cgi-bin/ с каталогом программ CGI. Правило RewriteRule преобразует путь /api/session в /cgi-bin/session-get.cgi для внутренней обработки Apache. Признак PT, сокращение от pass through, «передать дальше», передаёт получившийся путь следующему этапу сопоставления, где может сработать ScriptAlias. Признак L, от last, «последнее», завершает текущий проход набора правил. Браузер продолжает обращаться к прежнему адресу, а Apache выбирает программу внутри сервера.

Apache может вернуть HTTP 500, если CGI завершился неудачно или выдал ответ, который веб-сервер не смог обработать. Клиент в этом случае уже получил прикладное сообщение об ошибке. Следующий шаг — установить, какая программа была вызвана, как она завершилась и что записала в журнал.

4. CGI: как веб-сервер передаёт запрос программе

CGI расшифровывается как Common Gateway Interface, общий шлюзовой интерфейс. Это соглашение о взаимодействии веб-сервера с отдельной программой. В классической модели веб-сервер запускает обработчик, передаёт сведения о запросе через переменные окружения и тело через стандартный ввод, а ответ читает из стандартного вывода. Процесс CGI не обязан самостоятельно слушать порт 7000.

Окружение процесса — набор именованных текстовых значений, переданных ему при запуске. REQUEST_METHOD сообщает метод, QUERY_STRING — часть после вопросительного знака, CONTENT_LENGTH — размер тела. Стандартный ввод и стандартный вывод — заранее открытые каналы процесса. Обычно их называют stdin и stdout. Стандартный поток ошибок, stderr, предназначен для диагностики. Эти названия относятся к интерфейсам процесса, а не к отдельным сетевым портам.

В программе сеанса сначала читается конфигурация, настраивается журналирование и вызывается cgiutil.OpenDatabase. Затем собирается обработчик пользователя и запускается cgi.Serve. Следовательно, отсутствие ответа может быть связано с подготовкой базы ещё до прикладного обработчика. Запись TCP, подтверждающая доставку GET, не доказывает успешность любого из этих внутренних шагов. Общее поведение CGI проверено по руководству Apache по CGI и документации библиотеки Go.

5. Обращение к базе — отдельное сетевое взаимодействие

Для работы с PostgreSQL CGI использует библиотеку pgx. Библиотека здесь — готовый программный код, который формирует обращения к базе и разбирает её ответы. В исходнике internal/cgiutil/database.go разбирается строка подключения и создаётся пул соединений. Строка подключения задаёт адрес и другие параметры обращения к базе. Пул — управляемый набор соединений, которые код может временно брать для запросов. Время его жизни ограничено процессом. Если каждый CGI запускается отдельно и завершается после обработки, следующий процесс создаёт собственный пул. Само создание объекта пула и фактическое установление конкретного соединения следует различать; сетевую попытку определяют по сокетам и записи пакетов.

В этом обмене сервер ДО играет роль клиента базы. Для исходящего соединения ОС обычно выбирает свободный временный порт. Назначение — настроенный адрес и порт PostgreSQL. Это отдельное соединение между серверной программой и базой, со своими TCP-состояниями, номерами последовательности и подтверждениями. Оно остаётся отдельным и тогда, когда программа обращается к базе от имени пользователя браузера.

Браузер:49152  → Apache:7000        соединение A
Apache        → CGI                 локальный интерфейс процесса
CGI:временный → PostgreSQL:порт БД   соединение B
CGI stdout    → Apache              локальный ответ
Apache:7000   → Браузер:49152        обратное направление A

Порт базы берётся из действующей конфигурации; 5432 — распространённое значение по умолчанию, которое можно изменить. После установления соединения сервер проверяет личность и права доступа. SQL — язык запросов к базе данных; права SQL определяют допустимые действия пользователя над её объектами. Дополнительно ОС может учитывать мандатный контекст — атрибуты процесса, используемые при обязательной проверке доступа к ресурсам. В записи пакетов соединения B устанавливают, дошёл ли обмен до ответа PostgreSQL. Содержание ответа и журналы затем помогают различить отказ проверки личности, недостаточные права и ошибку выполнения запроса.

Проверки выполняют по порядку обработки запроса. Если CGI получил от базы отказ в выполнении SQL, исследуют причину этого отказа по сообщению и журналам. Если на сервере нет входящего SYN, сначала прослеживают сетевой путь к серверу. Каждое наблюдение определяет, на каком этапе искать следующий факт.

Задержка в 10 секунд

Запрос появился в журнале доступа, но полный ответ возвращается через десять секунд. Соединение с базой устанавливается лишь через девять секунд после начала процесса. Что нужно выяснить следующим?

Подробный разбор

Нужно определить, где процесс провёл эти девять секунд: разрешение имени базы, подготовка учётных данных для подтверждения личности, попытки соединения по нескольким адресам, ожидание локальной службы идентификации или другая инициализация. Позднее установление соединения ещё не объясняет длительность выполнения SQL: запрос мог пока вообще не передаваться базе. Сопоставление времени запуска процесса, сетевых попыток и сообщений журнала позволит найти этап задержки. Время записей на разных машинах сравнивают с учётом возможного расхождения часов.
