4. Как пакет находит следующий компьютер

Представим, что программа уже знает адрес сервера: 198.51.100.20. Она создала сокет и попросила отправить данные. Кабель компьютера соединён только с ближайшим коммутатором; отдельного провода до сервера нет. Ядру предстоит ответить на три разных вопроса: через какой интерфейс выпустить пакет, какому соседу вручить его сейчас и каким канальным адресом обозначить этого соседа. Адрес конечной цели и адрес следующего получателя решают разные задачи. Они совпадают по смыслу лишь тогда, когда цель непосредственно достижима в данном канальном сегменте.

В этой главе адреса 192.0.2.0/24, 198.51.100.0/24 и 203.0.113.0/24 служат учебными обозначениями. В опытах на реальном компьютере следует подставлять адреса своего стенда. Приведённые выводы показывают, как читать результат команды; фактические значения зависят от настройки компьютера.

4.1. Адрес, маска и префикс: посчитать своими руками

Адрес IPv4 — 32 бита, обычно записанные четырьмя десятичными числами по восемь бит. Точка разделяет байты записи, а не физические сети. Число 192 — это двоичное 11000000; адрес 192.0.2.10 — последовательность 11000000 00000000 00000010 00001010. Маска говорит, сколько начальных битов относится к общему префиксу. Запись /24 означает 24 начальные единицы маски и восемь последующих нулей. Это маска 255.255.255.0.

Чтобы проверить принадлежность сети, нужно выполнить побитовое «И» адреса и маски. Единица маски сохраняет соответствующий бит адреса, ноль его обнуляет. Затем результат сравнивают с префиксом маршрута. Число после / обозначает длину общей начальной части адресов. Такой способ записи относится к CIDR, то есть бесклассовой междоменной маршрутизации: длину префикса задают явно, вместо того чтобы выводить её из старого класса адреса A, B или C. Основание: RFC 4632.

Адрес 192.0.2.139: 11000000 00000000 00000010 10001011
Маска /26:         11111111 11111111 11111111 11000000
Побитовое И:       11000000 00000000 00000010 10000000
Сеть:              192.0.2.128/26

Младшие 6 битов: от 000000 до 111111 → 64 адреса
Диапазон блока: 192.0.2.128 ... 192.0.2.191
Обычная IPv4-подсеть: .128 — адрес сети; .191 — широковещательный
Обычно назначаемые узлам адреса: .129 ... .190

Почему шаг равен 64? В последнем байте осталось шесть переменных битов: 2⁶ = 64. Начала блоков — 0, 64, 128, 192. Адрес .139 попадает в третий блок. Правило «вычесть два адреса» применимо к обычной широковещательной подсети IPv4; специальные случаи /31 для связи двух маршрутизаторов и /32 для одного адреса устроены иначе. Маска принадлежит настройке интерфейса и маршрутам; в обычном заголовке IPv4 её нет. Получатель пакета не узнаёт маску отправителя из самого пакета.

Проверка расчёта: считает ли 192.0.2.139/26 адрес 192.0.2.200 соседом?

Побитовое «И» для .139 даёт .128, для .200 — .192. Общий /26-префикс различается. При обычной настройке понадобится маршрут через шлюз. Но окончательное решение принимает таблица маршрутов: специальный маршрут непосредственно через интерфейс способен изменить поведение. Поэтому после расчёта подсети нужно посмотреть фактическое решение таблицы маршрутов.

4.2. Маршрут — инструкция для одного следующего шага

Таблица маршрутов содержит условия и действия. Условие «назначение входит в этот префикс» сопоставляется с адресом назначения пакета. Действие задаёт выходной интерфейс и, если нужно, адрес следующего маршрутизатора. Шлюз по умолчанию — обычный маршрут с префиксом длины ноль: он подходит любому адресу, но проигрывает более конкретному совпадению. Внутри выбранной таблицы выбирается наиболее длинный подходящий префикс. Если таких маршрутов несколько, в выборе может участвовать метрика: численная оценка предпочтительности маршрута, обозначенная в выводе словом metric. При прочих равных обычно предпочитается меньшее значение. До сравнения метрик нужно установить, какие маршруты имеют одинаково подходящий префикс. Подробности: ip-route(8).

ip -4 route show
192.0.2.0/24 dev enp1s0 proto kernel scope link src 192.0.2.10
198.51.100.0/24 via 192.0.2.1 dev enp1s0 metric 50
198.51.100.20/32 via 192.0.2.254 dev enp1s0 metric 900
default via 192.0.2.1 dev enp1s0 metric 100

Для 198.51.100.20 подходят /32, /24 и /0. Выиграет /32, несмотря на метрику 900: этот маршрут описывает ровно один нужный адрес. Для 198.51.100.21 останется /24 через .1. Для 192.0.2.80 выберется непосредственно подключённая сеть: ядро станет искать канальный адрес самого .80. Для внешнего 203.0.113.90 сработает default, то есть маршрут по умолчанию. Ключевое слово via обозначает промежуточного получателя, dev — интерфейс, src — предпочтительный исходный адрес для локально создаваемого пакета. Запись proto kernel означает, что маршрут создан ядром, обычно при назначении адреса интерфейсу; scope link указывает достижимость непосредственно через данный канал.

Linux способен иметь несколько таблиц. Сначала правила маршрутизации могут выбрать таблицу по исходному адресу, метке пакета, интерфейсу или другим признакам. Таким образом, сначала правило определяет, в какой таблице искать маршрут, а затем выполняется поиск внутри этой таблицы. Для конкретной передачи полезно изучить и правила, и итоговое решение. Приоритет правила определяет порядок проверки правил, метрика маршрута — выбор среди подходящих маршрутов. Правила выбора таблиц: ip-rule(8).

ip rule show
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default
ip route get 198.51.100.20 from 192.0.2.10
198.51.100.20 via 192.0.2.1 dev enp1s0 src 192.0.2.10

Последний вывод относится к простому стенду без специального /32 из предыдущего примера. Команда get ничего не посылает серверу: она спрашивает ядро о решении. Если процесс явно привязал сокет к адресу или интерфейсу, либо пакет получает метку, результат нужно запрашивать с соответствующими параметрами. После получения маршрута остаётся проверить достижимость выбранного соседа: наличие инструкции пересылки само по себе ещё не обеспечивает передачу кадра.

4.3. Узнать канальный адрес: разговор ARP

Допустим, выбран шлюз 192.0.2.1, но его Ethernet-адрес неизвестен. Ядро не может записать IP-адрес в поле Ethernet: это другое поле с другим размером. Протокол разрешения адресов ARP сопоставляет IPv4-адрес ближайшего соседа его канальному адресу. При начальном поиске неизвестного MAC запрос идёт широковещательным Ethernet-кадром; ARP не вложен в IP и не проходит через обычную IP-маршрутизацию. При проверке уже известного соседа возможен одноадресный ARP-запрос: широковещательность не является обязательным свойством любого сообщения ARP. Поэтому спрашивать ARP непосредственно про удалённый сервер обычно бессмысленно. Формат: RFC 826.

Поле ARPРазмер, байтПример и смысл для принимающего узла
Тип оборудования21: используются Ethernet-адреса.
Тип сетевого протокола20x0800: разрешаем адрес IPv4.
Длины аппаратного и сетевого адресов1 + 16 и 4: столько байтов читать дальше для каждого адреса.
Операция21 — вопрос; 2 — ответ.
Аппаратный адрес отправителя602:00:00:00:00:10: кто спрашивает.
IPv4 отправителя4192.0.2.10: чей адрес предлагает запомнить запрос.
Аппаратный адрес цели6В вопросе обычно нули: именно его ещё выясняют.
IPv4 цели4192.0.2.1: владелец этого адреса должен ответить.
Ethernet: 02:00:00:00:00:10 → ff:ff:ff:ff:ff:ff, тип 0x0806
ARP: кто имеет 192.0.2.1? сообщить 192.0.2.10

Ethernet: 02:00:00:00:00:01 → 02:00:00:00:00:10, тип 0x0806
ARP: 192.0.2.1 находится по адресу 02:00:00:00:00:01

Коммутатор разошлёт вопрос в пределах соответствующего широковещательного домена. Узлы прочитают его, а владелец адреса ответит. Ответ позволяет завершить запись в таблице соседей и выпустить ожидающий IP-пакет. ARP не устанавливает личность криптографически: присланное соответствие требует доверия к локальному сегменту. Именно поэтому чужой ложный ответ способен подменить следующего получателя при отсутствии дополнительной защиты.

Каждое соответствие в таблице соседей имеет состояние, отражающее, насколько недавно подтверждалась достижимость узла. INCOMPLETE — разрешение началось, адреса ещё нет. REACHABLE — есть недавнее подтверждение достижимости. STALE — адрес известен, свежего подтверждения нет; такую запись можно использовать, при необходимости проверяя достижимость. Затем возможны DELAY и PROBE: ожидание и активная проверка. FAILED означает неудачу разрешения или проверки. Точные таймеры зависят от настройки ядра. Состояния и команды: ip-neighbour(8).

ip neigh show dev enp1s0
192.0.2.1 lladdr 02:00:00:00:00:01 REACHABLE
sudo tcpdump -eni enp1s0 arp
ARP, Request who-has 192.0.2.1 tell 192.0.2.10
ARP, Reply 192.0.2.1 is-at 02:00:00:00:00:01
Есть маршрут, но шлюз всё время INCOMPLETE. Где искать?

Сначала следует проверить канальный участок: интерфейс поднят, правильный VLAN, верная подсеть, шлюз действительно подключён к этому сегменту. Затем нужно посмотреть, выходит ли ARP-запрос и приходит ли ответ. TCP-порт приложения пока не участвует: ядро ещё не умеет адресовать Ethernet-кадр шлюзу. Отсутствие ответа в одном захвате нужно соотнести с местом захвата и возможной фильтрацией.

ARP целиком: запрос и ответ в байтах

Разберём тот же шлюз на уровне реальных байтов. Клиент уже знает, что сервер 198.51.100.20 надо достигать через 192.0.2.1. Известны собственные адреса клиента: IPv4 192.0.2.10 и MAC 02:00:00:00:00:10. В таблице соседей клиента пока отсутствует пригодная запись шлюза. В этом примере начальные условия заданы явно: получение имени и настройку IP считаем уже выполненными.

Подготовлены два полных учебных кадра: ARP-запрос и ответ в файле PCAP. Его можно открыть анализатором трафика или прочитать приложенным Python-скриптом без доступа к сети. Это отдельный файл: десять кадров HTTP из главы 7 показывают обмен после определения канального адреса.

Запрос клиента, 60 байт в записи:

0000  ff ff ff ff ff ff 02 00 00 00 00 10 08 06 00 01
0010  08 00 06 04 00 01 02 00 00 00 00 10 c0 00 02 0a
0020  00 00 00 00 00 00 c0 00 02 01 00 00 00 00 00 00
0030  00 00 00 00 00 00 00 00 00 00 00 00

Слева указано шестнадцатеричное смещение от начала Ethernet-кадра: строка 0010 начинается с шестнадцатого байта. Первые четырнадцать байтов принадлежат Ethernet. Дальше начинаются двадцать восемь байтов ARP, а затем восемнадцать байтов дополнения Ethernet.

Смещение от начала кадраБайты запросаЧто они означают и кто их использует
0–5, 6 байтff ff ff ff ff ffMAC назначения Ethernet: широковещательный адрес. Коммутатор передаёт кадр по подходящим выходным портам данного VLAN, а узлы получают возможность проверить, относится ли вопрос к ним.
6–11, 6 байт02 00 00 00 00 10MAC отправляющего интерфейса клиента. Коммутатор использует его при обучении: этот адрес находится за входным портом.
12–13, 2 байта08 06Тип содержимого Ethernet, EtherType = 0x0806. Получатель выбирает обработчик ARP.
14–15, 2 байта00 01Тип оборудования в ARP: значение 1 означает Ethernet. Вместе с длинами адресов задаёт способ чтения дальнейших полей.
16–17, 2 байта08 00Тип разрешаемого сетевого адреса: 0x0800 означает IPv4. Здесь указано, для каких сетевых адресов ищется соответствие.
18, 1 байт06Длина одного аппаратного адреса: шесть байтов. Получатель знает, сколько прочитать для каждого MAC.

22–27, 6 байт02 00 00 00 00 10Аппаратный адрес отправителя внутри ARP. Владелец искомого IP использует его для ответа и записи о соседе.

32–37, 6 байт00 00 00 00 00 00Аппаратный адрес цели пока неизвестен. В нашем запросе поле заполнено нулями. В корректном запросе нашего примера целевой IPv4 позволяет шлюзу узнать свой адрес, а нулевой целевой MAC этому не мешает. Реальный узел также проверяет формат, операцию и свою политику ответов: например, arp_ignore в Linux может запретить ответ даже для локального IPv4.
38–41, 4 байтаc0 00 02 01Целевой IPv4: 192.0.2.1. Именно это значение сравнивает со своими адресами принимающий узел.
42–59, 18 байтНулевые байтыДополнение Ethernet до минимальной длины. В нашем файле выбраны нули. Формат ARP уже закончился; его граница вычисляется по длинам адресов.

Сумма размеров ARP получается из восьми байтов начальных полей и двух пар адресов: 8 + 2×6 + 2×4 = 28. Ethernet переносит минимум 46 байт содержимого: поэтому к 28 прибавляются 18. С канальным заголовком выходит 14 + 28 + 18 = 60 байт. На линии поле FCS добавляет ещё четыре, и размер от первого MAC до конца FCS становится 64 байта. Наш PCAP хранит кадры без FCS; именно поэтому анализатор показывает 60.

В кадре два разных поля со значениями 08 06 и 08 00. Первое находится в Ethernet и выбирает ARP как обработчик содержимого. Второе находится внутри ARP и сообщает, что искомое соответствие относится к IPv4. После него идут поля ARP, определённые его форматом. Полный IP-заголовок в данном кадре отсутствует.

Также различаются два канальных адреса назначения. Шесть ff в Ethernet обеспечивают доставку вопроса участникам сегмента. Шесть нулей в целевом аппаратном поле ARP обозначают ещё неизвестный адрес. Передающий интерфейс отправляет широковещательный кадр по первому из этих полей; нули из ARP не выбирают физического получателя.

Ответ шлюза, тоже 60 байт в записи:

0000  02 00 00 00 00 10 02 00 00 00 00 01 08 06 00 01
0010  08 00 06 04 00 02 02 00 00 00 00 01 c0 00 02 01
0020  02 00 00 00 00 10 c0 00 02 0a 00 00 00 00 00 00
0030  00 00 00 00 00 00 00 00 00 00 00 00

В ответе MAC назначения Ethernet стал 02:00:00:00:00:10: шлюз уже знает, кто задал вопрос. MAC источника стал адресом шлюза 02:00:00:00:00:01. Код операции по смещению 20 изменился на 00 02. В полях отправителя ARP шлюз помещает собственную пару 192.0.2.1 → 02:00:00:00:00:01, а в полях цели — пару клиента. Эти изменения удобно сопоставлять в двух дампах построчно.

Клиент проверяет формат и обрабатывает полученное соответствие адресов по правилам своей ОС. Для ожидаемого ответа появляется пригодная запись соседа, после чего ядро может передать ожидающий IP-пакет. Ethernet-назначением следующего кадра будет MAC шлюза, а IP-назначением вложенного пакета останется сервер 198.51.100.20.

Коммутатор выполняет собственную работу: изучает исходный MAC каждого пришедшего кадра и выбирает выходные порты. На запросе он узнаёт сторону клиента; на ответе — сторону шлюза. Таблица коммутатора связывает MAC с портом. Таблица соседей клиента связывает IP с MAC на конкретном интерфейсе. Так один обмен заполняет разные сведения у разных участников.

# Из каталога книги, без подключения к сети:
python3 labs/inspect-arp.py

# Если установлен tcpdump:
tcpdump -enn -r labs/arp-request-reply.pcap arp

В первой команде скрипт читает учебный файл, печатает оба типа операции, адреса и дамп. Во второй -r выбирает файл, -e добавляет канальный заголовок, -nn оставляет адреса и номера числовыми, а arp отбирает ARP. Команды читают запись и не отправляют запросов в сеть. inspect-arp.py рассчитан на приложенный простой формат Ethernet/IPv4 ARP; его входные проверки описаны в коде.

    Request who-has 192.0.2.1 tell 192.0.2.10, length 46
02:00:00:00:00:01 > 02:00:00:00:00:10, ethertype ARP (0x0806), length 60:
    Reply 192.0.2.1 is-at 02:00:00:00:00:01, length 46

В этом выводе Request who-has … tell … означает «запрос: у кого адрес …, сообщить узлу …», а Reply … is-at … — «ответ: сетевой адрес … соответствует канальному адресу …». Число length 60 относится ко всему записанному Ethernet-кадру без FCS. Последнее length 46 в таком выводе tcpdump включает содержимое Ethernet с дополнением: 28 + 18. Собственные поля ARP по-прежнему занимают 28 байт. Границу определяют формат и длины адресов, а не одна подпись length в сводной строке анализатора.

Что изменится, если клиент обращается к 192.0.2.20 в своей /24?

При обычном напрямую подключённом маршруте клиент ищет канальный адрес самого 192.0.2.20. В запросе меняется целевой IPv4 по смещению 38; владельцем, который должен ответить, становится этот узел. Собственные адреса клиента и широковещательный MAC запроса сохраняются. Внешний адрес сервера и IP шлюза из прежней задачи в таком запросе не участвуют.

Почему в ARP нет контрольной суммы, похожей на TCP?

У сообщения ARP собственное поле контрольной суммы не предусмотрено. При переносе в Ethernet целостность всего кадра проверяет канальный механизм FCS. Проверка охватывает и байты ARP. Вычисление FCS помогает обнаруживать повреждение передачи; доверие к объявленной паре адресов определяется другими условиями, включая защиту локального сегмента.

Проверка занятости адреса и объявление своего адреса

При проверке предполагаемого IPv4 узел может отправить ARP с IPv4 отправителя 0.0.0.0, указав проверяемый адрес как цель. Это называется пробой адреса, ARP Probe. При объявлении уже используемого адреса, ARP Announcement, сетевой адрес отправителя и цели совпадает. Такие сообщения помогают обнаруживать конфликты адресов. Поэтому необычный ARP в захвате нужно разбирать по операции и обеим парам адресов, а не только по английской строке Request. Правила описаны в RFC 5227.

Поведение одноадресных проб и ограничений ответов: ucast_solicit и arp_ignore в документации ядра. Наличие IP на машине не отменяет настройки интерфейса и политики.

1. IP выбирает следующий узел

Поиск маршрута возвращает шлюз 192.0.2.1 на локальном интерфейсе. Удалённый IP назначения остаётся 198.51.100.20. ARP понадобится для доставки кадра именно до следующего узла.

Действует: Маршрутизация IPv4 в ядре клиента.

Клиент: next hop = 192.0.2.1; Ethernet-сегмент: Кадра ещё нет; Шлюз: Ожидает трафик

  • Адрес для ARP: ещё не выбран → 192.0.2.1. Его задаёт результат маршрутизации, а не имя сервера.
  • Назначение IP: 198.51.100.20. Конечный сетевой адрес сервера.
  • Следующий узел: 192.0.2.1. Канальному уровню нужен MAC этого локального соседа.

2. В кеше нет соответствия

Подсистема соседей не знает MAC адреса 192.0.2.1. Исходный IP-пакет ждёт разрешения адреса; он не вложен в ARP-запрос.

Действует: Подсистема соседей клиента.

Клиент: 192.0.2.1 → MAC неизвестен; Ethernet-сегмент: Ожидается ARP; Шлюз: MAC 02:00:00:00:00:01

  • Состояние доставки: есть маршрут → не хватает MAC соседа. Настроенный маршрут ещё не означает, что канальный адрес известен.
  • Ожидающий пакет: IPv4 → 198.51.100.20. Данные приложения не становятся полезной нагрузкой ARP.
  • Запись соседа: 192.0.2.1 → ?. Ключ включает интерфейс: одинаковые IP могут существовать в разных сетевых пространствах и канальных сетях.

3. Клиент формирует запрос

Ethernet назначение ff:ff:ff:ff:ff:ff доставляет запрос участникам этого сегмента. Внутри ARP клиент указывает свои MAC и IP и спрашивает о 192.0.2.1. Здесь неизвестный целевой MAC заполнен нулями.

Действует: ARP клиента.

Клиент: Отправил op=1; Ethernet-сегмент: Широковещательная доставка; Шлюз: Может получить запрос

  • EtherType: для исходного IP было бы 0x0800 → 0x0806. ARP — отдельный протокол канального уровня, не IPv4-пакет.
  • Ethernet · 14 байт: dst ff:ff:ff:ff:ff:ff. Источник 02:00:00:00:00:10, EtherType 0x0806 означает ARP.
  • ARP · 28 байт: op=1 · who has 192.0.2.1. HTYPE=1, PTYPE=0x0800, HLEN=6, PLEN=4, opcode=1; затем SHA/SPA/THA/TPA — адреса отправителя и цели.
  • Дополнение · 18 байт: 42 → 60 байт. Минимальная длина Ethernet-кадра без FCS — 60 байт; 14+28=42 дополняется 18 байтами. С FCS будет 64; преамбула и интервалы сюда не входят.

4. Шлюз узнаёт себя в поле цели

Получатели Ethernet проверяют ARP. Для шлюза TPA=192.0.2.1 совпадает с его IPv4-адресом. Он может ответить и использовать адреса отправителя для обновления соответствия соседа.

Действует: ARP шлюза.

Клиент: Ждёт MAC; Ethernet-сегмент: ARP не проходит через IP-роутер; Шлюз: TPA совпал с моим IP

  • Кто должен ответить: все получили кадр → владелец 192.0.2.1. Получить широковещательный кадр и быть целью ARP — разные условия.
  • Адреса отправителя: SHA=…:10 · SPA=192.0.2.10. SHA — Sender Hardware Address, канальный адрес отправителя; SPA — его протокольный адрес.
  • Адреса цели: THA=00:00:00:00:00:00 · TPA=192.0.2.1. THA — Target Hardware Address; TPA — Target Protocol Address. Решение ответить опирается на протокольный адрес цели.

5. Возвращается одноадресный ответ

Шлюз посылает Ethernet-кадр на MAC клиента. ARP opcode=2 сообщает: 192.0.2.1 находится по адресу 02:00:00:00:00:01. Клиент извлекает соответствие из полей отправителя ответа.

Действует: ARP шлюза и подсистема соседей клиента.

Клиент: 192.0.2.1 → 02:…:01; Ethernet-сегмент: Одноадресный ответ; Шлюз: Отправил op=2

  • Кеш клиента: 192.0.2.1 → ? → 192.0.2.1 → 02:00:00:00:00:01. ARP не удостоверяет личность криптографически. Полученный ответ сам по себе не доказывает, что сосед доверенный.
  • Ethernet: dst 02:00:00:00:00:10. Адрес получателя ответа известен из запроса.
  • ARP Reply: SHA=02:00:00:00:00:01. SPA=192.0.2.1; THA=02:00:00:00:00:10; TPA=192.0.2.10. Opcode передаётся как 00 02 — старший байт первым.

6. Теперь отправляется ожидавший IP-пакет

Клиент формирует новый Ethernet-кадр с EtherType 0x0800. MAC назначения относится к шлюзу, а IP назначения внутри по-прежнему относится к серверу. Далее шлюз выполняет собственный поиск маршрута.

Действует: Канальный тракт отправки клиента.

Клиент: IP-пакет отправлен шлюзу; Ethernet-сегмент: Теперь Ethernet / IPv4; Шлюз: Дальше — свой маршрут

  • Содержимое кадра: ARP-запрос / ответ → исходный IPv4-пакет. Это разные кадры и разные EtherType; ARP лишь подготовил адрес доставки.
  • Внешний конверт: MAC dst = 02:00:00:00:00:01. Действует только на текущем Ethernet-участке.
  • Внутренний адрес: IP dst = 198.51.100.20. Изучение MAC шлюза не заменяет сетевой адрес получателя.

Проверить по первоисточнику: RFC 826: поля и обработка ARP · ip-neighbour: таблица соседей Linux. Внешние ссылки требуют интернета; объяснение и схема сохранены целиком.

4.4. Что именно находится в заголовке IPv4

Заголовок — набор битовых полей перед полезной нагрузкой. Минимальный размер — 20 байт. Ниже размеры указаны в битах; один байт содержит восемь битов. Часть полей заполняет исходное ядро, часть меняют маршрутизаторы. Слова «полезная нагрузка» относительны: для IP ею является весь TCP-сегмент с его собственным заголовком.

Формат полей определён в RFC 791; современное разделение DSCP/ECN — в RFC 2474 и RFC 3168. Контрольная сумма помогает обнаруживать случайное повреждение заголовка. Для защиты от намеренного изменения нужны криптографические механизмы: отправитель ложного пакета способен вычислить и правильную обычную сумму. В современных сетях TTL работает прежде всего как ограничение числа переходов через маршрутизаторы. Значение DSCP приобретает практический смысл при настроенных правилах обслуживания; на границе сети устройство может заменить метку согласно своей политике.

Увидеть поля можно в программе анализа трафика Wireshark, раскрыв раздел Internet Protocol Version 4 — «межсетевой протокол версии 4». В tcpdump -nvv видны длина, TTL, идентификатор, флаги и протокол; -X добавит байты. Если смотреть исходящий пакет до аппаратного вычисления контрольной суммы, анализатор иногда покажет ещё не готовую сумму. В этом случае нужно сопоставить захват на отправителе и получателе. Пометка incorrect означает «неверная»: до вывода о повреждении следует установить, в какой момент анализатор увидел пакет.

45 00 00 54 12 34 40 00 40 06 3c 1e c0 00 02 0a c6 33 64 14

Это самостоятельно рассчитанный учебный заголовок из таблицы. Первый байт 0x45 содержит два поля: старшие четыре бита 4 — версия; младшие 5 — длина в четырёхбайтовых единицах. 0x0054 — 84 в десятичной записи. 0x1234 — идентификатор. В 0x4000 установлен DF, смещение равно нулю. 0x40 — TTL 64, 0x06 — TCP. Следующие два байта — сумма 0x3c1e. Последние восемь байтов переводятся в 192.0.2.10 и 198.51.100.20. Важен порядок байтов: старший идёт первым, поэтому 0x0054 — 84, а не 21504.

При тех же остальных полях и TTL 63 сумма станет 0x3d1e; при TTL 62 — 0x3e1e. Это сумма только заголовка IPv4. Её проверка складывает 16-битные слова с переносом и инверсией; содержимое 44 байтов приложения на неё не влияет. Если удлинить заголовок параметрами, изменится и набор суммируемых слов.

4.5. Один пакет через два маршрутизатора

A 192.0.2.10/24
  │ локальная сеть 192.0.2.0/24
R1: 192.0.2.1 / 203.0.113.1
  │ транзитная сеть 203.0.113.0/30
R2: 203.0.113.2 / 198.51.100.1
  │ сеть сервера 198.51.100.0/24
B 198.51.100.20/24

Предположим, что маршруты настроены в обе стороны, пересылка разрешена, трансляции адресов нет. На A исходный TTL равен 64. Ядро определяет шлюз R1, получает его MAC по ARP и строит первый кадр. R1 принимает Ethernet-кадр на свой адрес, извлекает пакет, решает, что цель находится за R2, уменьшает TTL, обновляет сумму заголовка и создаёт новый кадр. На R2 повторяется та же логика, но следующий сосед — уже конечный B. Требования к пересылке и уменьшению TTL описывает RFC 1812.

КаналMAC источника → назначенияIP источника → назначенияTTL на выходе
A → R102:00:00:00:00:10 → 02:00:00:00:00:01192.0.2.10 → 198.51.100.2064
R1 → R202:00:00:01:00:01 → 02:00:00:01:00:02192.0.2.10 → 198.51.100.2063
R2 → B02:00:00:02:00:01 → 02:00:00:02:00:20192.0.2.10 → 198.51.100.2062

Канальные адреса здесь вымышлены, но закономерность реальна. У каждого интерфейса маршрутизатора собственный адрес. Старый Ethernet-заголовок не путешествует внутри нового автоматически. TCP-порты, номера последовательности и данные сохраняются, если нет дополнительного преобразования; контрольная сумма TCP из-за обычного изменения TTL не меняется. Ethernet-проверка кадра создаётся заново для нового кадра. Обычный коммутатор внутри одного такого участка TTL не уменьшает.

Ответ B начинается как новый пакет: адрес B становится источником, адрес A — назначением; исходный TTL выбирает система B. B должен иметь маршрут к A, а каждый промежуточный маршрутизатор — к соответствующему следующему шагу. Маршруты обратного направления должны быть настроены независимо от маршрутов A → B. На реальной сети ответ может идти через другие устройства. Поэтому «запрос виден на сервере» и «ответ получен клиентом» — два разных проверяемых события.

4.6. Пакет не помещается: MTU, дробление и поиск размера

Максимальная единица передачи, MTU, — предельный размер сетевого пакета, который допускает конкретный интерфейс или путь в рассматриваемой модели. Для обычного Ethernet часто настроено 1500 байт IP-пакета. Это не 1500 байт текста приложения: из них придётся вычесть IP и транспортный заголовки. У пути есть минимальный предел среди всех участков. Туннель может добавить внешние заголовки и уменьшить допустимый внутренний размер.

IPv4 допускает дробление. Например, 4000 байт IP-пакета при заголовке 20 байт содержат 3980 байт нагрузки. При MTU 1500 и разрешённом дроблении можно получить нагрузки 1480, 1480 и 1020 байт: смещения 0, 185 и 370, поскольку единица смещения равна восьми байтам. Общие длины фрагментов будут 1500, 1500 и 1040. У первых двух MF=1, у последнего MF=0. Собирать исходное сообщение должен конечный получатель; потеря одного фрагмента мешает получить целое.

При установленном DF маршрутизатор не может так раздробить пакет. Если размер слишком велик, он сообщает отправителю о необходимости меньшего размера через ICMP. Поиск максимального размера пакета для пути называется PMTUD, то есть обнаружением максимальной единицы передачи на пути. Отправитель уменьшает предполагаемый предел и заново формирует передачу. Механизм IPv4 описан в RFC 1191. В IPv6 промежуточные маршрутизаторы не дробят пакеты: источник получает сообщение Packet Too Big, то есть «пакет слишком большой». Механизм IPv6: RFC 8201.

Характерный случай: маленькие сообщения установления TCP-соединения проходят, короткий запрос проходит, большой ответ зависает. На пути есть туннель с меньшим пределом, а сообщение о размере не доходит обратно. Повторные большие пакеты снова теряются. Так возникает «чёрная дыра» определения размера: отправитель продолжает посылать пакеты, которые путь не пропускает, и не получает объяснения, позволяющего уменьшить их. Транспортные механизмы могут обнаруживать предел пробами и подтверждениями без полной зависимости от ICMP; такой подход называется PLPMTUD — обнаружением допустимого размера средствами пакетного уровня. Отправитель делает пробные передачи выбранного размера и по подтверждениям определяет, прошли ли они. Пример для датаграммных транспортов: RFC 8899.

Расчёт: сколько данных TCP помещается при MTU 1500?

При IPv4 без параметров и TCP без параметров: 1500 − 20 − 20 = 1460 байт. При IPv6 с базовым заголовком и тем же TCP: 1500 − 40 − 20 = 1440. Если присутствуют TCP-параметры, заголовки расширений IPv6 или дополнительные оболочки, полезного места меньше. Эти расчёты объясняют размер, но не обещают, что любой вызов отправки будет разбит именно на такие куски.

4.7. ICMP: обратная связь, которую нужно правильно понимать

ICMP, протокол управляющих сообщений межсетевого уровня, передаёт сведения о доставке и диагностические сообщения. Программа ping использует запрос эха Echo Request и ответ эха Echo Reply: получатель возвращает данные запроса отправителю. Программа traceroute строит трассировку пути, отправляя пробные пакеты с последовательно растущим пределом переходов и сопоставляя ответы об истечении TTL. Ошибка часто содержит начало исходного пакета, чтобы получатель мог сопоставить её со своей передачей. Форматы IPv4 описаны в RFC 792.

Получение диагностического ответа зависит от ограничений частоты, фильтров и обратного пути. Поэтому часть проб может остаться без ответа, хотя маршрутизатор продолжает пересылать обычные пакеты. Звёздочка в трассировке означает отсутствие ожидаемого ответа, а не доказанное отсутствие пересылки. Успешный ping подтверждает лишь прохождение конкретного обмена ICMP. Он не проверяет, слушает ли TCP-порт 7000 приложение, правильно ли настроен сертификат и существует ли нужная HTTP-страница.

4.8. IPv6: что меняется, а что остаётся

IPv6 сохраняет идею назначения, следующего шага и маршрутов, но адрес увеличен до 128 бит. В записи 2001:db8:1::10 двоеточия разделяют 16-битные группы; двойное двоеточие один раз сокращает последовательность нулевых групп. Базовый заголовок занимает 40 байт. Понятия маски и наиболее длинного подходящего префикса остаются полезны.

В базовом заголовке нет контрольной суммы и полей дробления. Необходимые дополнительные сведения размещают в заголовках расширений. Отсутствие суммы IP не отменяет контрольные суммы транспортов и проверки канального уровня. Формат и правила фрагментации определяет RFC 8200.

Вместо ARP используется обнаружение соседей NDP поверх ICMPv6. Сообщение Neighbor Solicitation, то есть запрос сведений о соседе, позволяет узнать его канальный адрес и участвует в проверке достижимости. Neighbor Advertisement, объявление соседа, сообщает соответствие IPv6- и канального адресов. При первоначальном разрешении адреса запрос обычно отправляют специальной группе получателей, вычисленной из адреса цели; это сокращает число узлов, которым нужно разбирать сообщение. Объявление маршрутизатора RA, от Router Advertisement, сообщает сведения о доступных префиксах и самом маршрутизаторе. Запрос RS, от Router Solicitation, позволяет узлу попросить маршрутизаторы прислать объявление, не ожидая очередной периодической отправки. Для адреса, действующего только в пределах канала, нужно указать интерфейс: одинаковый fe80::1 может существовать в разных сегментах, поэтому запись вроде fe80::1%enp1s0 уточняет область. Обнаружение соседей: RFC 4861.

Автоматическая настройка адреса без отдельной выдачи сервером называется SLAAC — автоматической настройкой адреса без отслеживания состояния сервером. Узел получает разрешённый для этого префикс из RA, формирует адрес и проверяет, не занят ли он. Младшую часть адреса узел может формировать разными способами; например, с использованием устойчивого вычисленного идентификатора или временного значения. Поэтому её следует рассматривать отдельно от MAC-адреса. Проверка дубликата и сроки действительности адресов входят в жизненный цикл настройки. Процедура: RFC 4862.

DHCPv6 способен выдавать адреса и параметры отдельным обменом, но стандартный выбор маршрутизатора по умолчанию относится к RA/NDP. Поэтому «сервер DHCPv6 ответил» и «есть рабочий IPv6-маршрут» не равнозначны. Изолированная блокировка ICMPv6 способна нарушить базовые механизмы сети. DHCPv6: RFC 8415.

ip -6 addr show dev enp1s0
ip -6 route show
ip -6 neigh show
sudo tcpdump -ni enp1s0 icmp6
Проверка понимания: что нужно знать до построения Ethernet-кадра?

Нужно выбрать адрес назначения IP, подходящий маршрут и следующий соседний узел, затем получить его канальный адрес на выбранном интерфейсе. Для IPv4 это часто ARP, для IPv6 — NDP. Адрес удалённого сервера остаётся внутри IP-пакета, а Ethernet-назначение описывает ближайшую доставку. Для каждого из трёх участков схемы можно отдельно указать конечный IP-адрес и ближайшего получателя кадра. Такое сопоставление показывает, как доставка одного IP-пакета складывается из отдельных канальных передач.

Для самостоятельного опыта можно выбрать два адреса и маску, вычислить общий префикс и нарисовать следующий шаг для прямой доставки и доставки через шлюз. Затем сравнить расчёт с ip route get, таблицей ip neigh и захватом пакетов. При расхождении нужно выяснить, какое правило маршрутизации или состояние соседа не было учтено в расчёте.

Посчитать префикс самому

Поменяйте адрес, длину префикса и назначение. Операция И сохраняет только разряды, в которых маска равна единице. Это модель одного напрямую подключённого префикса.
