Теперь можно собрать несколько уже знакомых механизмов в работающую сеть: выбор маршрута, поиск соседа, пересылку, изменение адресов и проверку разрешений. Цель этой главы — уметь объяснить судьбу каждого пакета. Поднятая сеть станет проверкой объяснения: заранее названные адреса должны появиться у сервера, обратный пакет должен пройти ожидаемый путь, а специально запрещённое соединение должно остановиться у конкретного правила.

Здесь NAT, от Network Address Translation, означает преобразование сетевых адресов. На практике рассматриваемые правила могут изменять также номера транспортных портов. SNAT, Source NAT, меняет сведения об источнике; DNAT, Destination NAT, — о получателе. Запоминайте, с какой стороны рассматривается пакет: получатель исходящего запроса становится отправителем ответа, поэтому обратное преобразование затронет другое поле.

Адреса этого стенда назначаются вручную: C имеет 10.77.10.10, I — 10.77.10.20. В примере DHCP для побайтового разбора клиенту выдавался 10.77.10.100. Это отдельные учебные конфигурации одной выбранной подсети; состояние DHCP не требуется для запуска данного стенда.

1. Пять компьютеров, у каждого своя таблица маршрутов

Вместо подключения учебного стенда к интернету создадим пять изолированных сетевых пространств Linux. Каждое такое пространство получает собственные интерфейсы, адреса, маршруты, сокеты и сетевые правила. Все пять используют одно ядро и общий диск, но для изучения обычного пути IPv4-пакета ведут себя как отдельные узлы. Пространство имён по-английски называется namespace; в командах ip netns последние пять букв сокращают выражение «сетевое пространство имён». Механизм изоляции описан в руководстве network_namespaces(7).

C: клиент 10.77.10.10/24 ─┐
                          ├─ G: мост lan0 10.77.10.1/24
I: служба 10.77.10.20/24 ─┘       wan0 198.18.0.2/24
                                      │
                              U: down0 198.18.0.1/24
                                   up0 198.18.1.1/24
                                      │
                               S: eth0 198.18.1.20/24
                                  HTTP, порт 8080

Буквы обозначают роли: C — клиент, I — внутренний сервер, G — наш шлюз, U — вышестоящий маршрутизатор, S — внешний сервер. Внутренняя служба I слушает TCP-порт 7000. Сервер S слушает TCP-порт 8080. Слово «внешний» здесь описывает положение относительно G. Адреса 198.18.0.0/15 выделены для испытаний сетевого оборудования в RFC 2544; они удобны в замкнутом стенде и не изображают выданный провайдером публичный адрес. К компьютеру читателя ни один учебный интерфейс не подключён.

УзелНепосредственно подключённые сетиСледующий маршрутизатор для остальных адресов
C и I10.77.10.0/2410.77.10.1
G10.77.10.0/24; 198.18.0.0/24198.18.0.1
U198.18.0.0/24; 198.18.1.0/24Отсутствует

У U намеренно нет маршрута в 10.77.10.0/24. Это главное условие первого опыта. Возможность C отправить пакет в сторону S ещё не сообщает, сможет ли S доставить ответ. Каждый маршрутизатор принимает самостоятельное решение по адресу назначения того пакета, который сейчас обрабатывает. Будущий ответ никто заранее не прокладывает по памяти Ethernet-коммутатора.

2. Сначала пройдём путь без изменения адреса

Пусть C открывает TCP-соединение из порта 41001 к 198.18.1.20:8080. Его первое сообщение SYN имеет пару концов 10.77.10.10:41001 → 198.18.1.20:8080. Сопоставление адреса получателя с таблицей маршрутов C выбирает шлюз 10.77.10.1. ARP выясняет MAC-адрес этого шлюза. Ethernet-кадр адресуется G, хотя IP-пакет внутри адресуется S. Адрес шлюза не подставляется в поле IP-получателя.

G принимает свой Ethernet-кадр, извлекает IP-пакет и определяет, что 198.18.1.20 находится за U. Если пересылка разрешена и фильтр допускает пакет, G уменьшает TTL и отправляет новый кадр на wan0. U получает его на down0, выбирает непосредственно подключённую сеть 198.18.1.0/24 и передаёт S. При обычной маршрутизации IP-источник остаётся 10.77.10.10, а исходный TCP-порт — 41001. На каждом Ethernet-участке меняются окружающие пакет MAC-адреса.

S находит слушающий сокет, создаёт состояние соединения и готовит SYN+ACK: 198.18.1.20:8080 → 10.77.10.10:41001. Для получателя вне своей подсети S выбирает U. У U нет ни маршрута к 10.77.10.0/24, ни маршрута по умолчанию. Доставка ответа заканчивается здесь. Клиент спустя время повторяет SYN; каждый повтор воспроизводит тот же разрыв обратного пути. Отсутствие HTTP-ответа в этой ситуации ещё не доказывает ошибку HTTP-сервера.

Один способ исправления — сообщить U маршрут 10.77.10.0/24 via 198.18.0.2. Тогда обычная маршрутизация обеспечит оба направления. Другой способ — представить запрос с источником, уже известным U: 198.18.0.2. Второй способ и проверим через SNAT. Выбор между ними определяется устройством сети: можете ли вы настраивать вышестоящий маршрутизатор, должны ли адреса внутренних узлов быть видимы снаружи, требуется ли разделить несколько одинаковых внутренних адресных пространств.

Проверьте рассуждение. На C есть правильный маршрут по умолчанию. На S тоже. Почему этого оказалось недостаточно?

Разбор

Маршруты концов определяют только их ближайший следующий шаг. Ответ дошёл до U, а дальнейшее решение принимает таблица U. В этой таблице отсутствует подходящий префикс для адреса клиента. Весь путь работоспособен, когда каждое промежуточное решение успешно в каждом направлении.

3. Что шлюз запоминает о соединении

Для TCP различение обменов требует как минимум протокола и четырёх чисел: адресов и портов двух сторон. Такая пятёрка называется five-tuple, то есть «пятёрка признаков». Два клиента могут выбрать одинаковый локальный порт 41002: их внутренние адреса различаются, поэтому исходные пятёрки различны. После преобразования обоих адресов в один внешний адрес шлюз должен сохранить различимость обменов и для внешнего сервера.

В Linux учётом занимается conntrack, сокращение от connection tracking, «отслеживание соединений». Это часть ядра. Она сопоставляет пакет известному обмену, хранит сведения о двух направлениях и сроки существования записи. Пользовательская программа с таким же именем, если установлена, позволяет читать и менять эти записи; наличие программы отдельно от наличия механизма в ядре. Для UDP ядро также хранит временную запись обмена, хотя установления соединения по правилам TCP у UDP нет.

Для исходящего соединения C через SNAT запоминаем две пятёрки. Исходное направление, в инструментах original, описывает первое обращение до преобразования: TCP, 10.77.10.10:41002 → 198.18.1.20:8080. Ответное направление, reply, описывает пакет, который шлюз ожидает с другой стороны: TCP, 198.18.1.20:8080 → 198.18.0.2:41002. При необходимости внешний порт окажется другим. Различие преобразования только адресов и преобразования адресов вместе с портами описано в RFC 3022. По второму описанию ядро узнает ответ и восстанавливает получателя 10.77.10.10:41002.

Эту связь удобно представить записью «внешний конец 198.18.0.2:41002 соответствует внутреннему 10.77.10.10:41002 в обмене с S». Реальная структура ядра содержит больше сведений: состояние протокола, признаки преобразования, время до удаления, иногда служебные метки. Изображённая запись достаточна для вычисления адресов нашего опыта, но не заменяет устройство всей таблицы.

Состояния фильтра new, established, related, invalid означают соответственно новый отслеживаемый обмен, обмен с замеченным ответным направлением, связанный с уже известным обменом пакет и пакет, который механизму не удалось корректно отнести к допустимому состоянию. Эти состояния проверяет ядро, а не текст в HTTP-заголовке. Значение established в conntrack следует отличать от одноимённого состояния TCP-сокета: оно определяется логикой учёта пакетов и может появиться при наблюдении ответного направления раньше полного TCP-рукопожатия.

4. В какой момент изменяется пакет

Netfilter — подсистема точек обработки сетевых пакетов в ядре Linux. nftables — средство задания правил для этой обработки; команда nft загружает правила в ядро. Название hook означает «точка подключения»: это место в пути пакета, где вызывается привязанная к нему цепочка. Chain, «цепочка», — упорядоченный набор правил. Table, «таблица», — именованная группа цепочек и связанных объектов.

Получение кадра
      ↓
prerouting: обработка перед решением о маршруте, здесь DNAT
      ↓
Выбор маршрута уже по преобразованному адресу назначения
      ├─ адрес принадлежит G → input → локальный сокет G
      └─ нужен другой узел   → forward → postrouting → выходной интерфейс
                                            ↑
                                  здесь исходящий SNAT

Имена точек переводятся по смыслу: prerouting — до маршрутизации, input — доставка самому узлу, forward — пересылка через узел, postrouting — после выбора маршрута. Локально созданный процессом G пакет начинает сетевую обработку по другой ветви, через output, «выход локально созданного пакета». Поэтому проверка сайта с самого G исследует другой начальный путь, чем обращение C через G.

У базовой цепочки указаны тип, точка подключения и приоритет. Тип filter используется для решений разрешить или отбросить. Тип nat создаёт преобразование для нового обмена. Приоритет задаёт порядок вызовов в одной точке: меньшее число выполняется раньше. Имена dstnat, filter, srcnat обозначают стандартные приоритеты −100, 0 и 100. Сначала преобразованный получатель становится известен выбору маршрута; после выбора интерфейса можно подобрать исходящий адрес.

Это объясняет важную строку будущего фильтра: разрешение опубликованной службы в forward сравнивает получателя с 10.77.10.20 и портом 7000. К этому моменту DNAT уже обработал первоначальное 198.18.0.2:8080. Если написать здесь только проверку порта 8080, правило не совпадёт с нашим преобразованным пакетом. Дополнительно можно обратиться к исходным значениям записи conntrack, если нужно проверить именно внешний адрес обращения.

Семантика цепочек NAT отличается: правила выбирают привязку по первому пакету нового обмена. Следующие пакеты получают преобразование по сохранённой записи. Поэтому счётчик внутри правила NAT обычно считает создание привязок, а не объём всего трафика. Это поведение прямо определено в руководстве проекта nftables по NAT. Фильтрующие правила проверяются на проходящих через них пакетах; в стенде не включено ускоренное перенаправление потоков, которое меняло бы наблюдаемый путь.

5. Читаем создание стенда по шагам

Полный воспроизводимый сценарий находится в файле nat-lab.sh. Сначала разберём его существенные действия вручную. Команды ниже показывают последовательность устройства одного и того же стенда; переменные C, I, G, U, S получают уникальные имена внутри сценария. Для отдельного ручного опыта используйте ту же защитную оболочку и обработчик очистки из файла. Обычный запуск всего файла описан после разбора. Само чтение книги команды не выполняет.

Строка ip netns add "$C" создаёт пространство клиента. ip -n "$C" link set dev lo up включает в нём петлевой интерфейс. Опция -n сокращает -netns: следующие действия относятся к указанному сетевому пространству. Запись ip netns exec "$G" команда запускает целую программу внутри пространства G. Так там выполняются nft, сервер и изменение сетевых параметров. Оба способа сохраняют адреса, маршруты и правила рабочего компьютера отдельно от опыта.

ip -n "$C" link add eth0 type veth peer name lc netns "$G"
ip -n "$I" link add eth0 type veth peer name li netns "$G"
ip -n "$G" link add wan0 type veth peer name down0 netns "$U"
ip -n "$U" link add up0 type veth peer name eth0 netns "$S"
ip -n "$G" link add lan0 type bridge
ip -n "$G" link set dev lc master lan0
ip -n "$G" link set dev li master lan0

veth — виртуальная пара Ethernet-интерфейсов. peer означает второй конец пары. Кадр, отправленный в один конец, появляется на другом. Это программный аналог соединённых сетевых карт для целей данного опыта. Первый конец сразу создаётся в C, второй — сразу в G; временный провод к основной сети компьютера не возникает. Имена lc и li относятся к двум портам G.

bridge — мост, выполняющий переключение Ethernet-кадров между присоединёнными портами. master lan0 присоединяет порт к мосту. Адрес 10.77.10.1/24 назначается интерфейсу моста lan0. Порты lc и li отдельных IPv4-адресов не получают. Для пакета, который маршрутизирует G между внутренней и внешней сетями, логическим входным интерфейсом внутренней сети служит lan0.

ip -n "$C" address add 10.77.10.10/24 dev eth0
ip -n "$I" address add 10.77.10.20/24 dev eth0
ip -n "$G" address add 10.77.10.1/24 dev lan0
ip -n "$G" address add 198.18.0.2/24 dev wan0
ip -n "$U" address add 198.18.0.1/24 dev down0
ip -n "$U" address add 198.18.1.1/24 dev up0
ip -n "$S" address add 198.18.1.20/24 dev eth0

После назначения адреса ядро обычно создаёт маршрут к соответствующей непосредственно подключённой сети. Затем сценарий поднимает каждый интерфейс через link set dev имя up. Число после косой черты задаёт длину сетевого префикса, поэтому C считает I непосредственным соседом, а S — удалённым получателем. Далее добавляются четыре маршрута по умолчанию:

ip -n "$C" route add default via 10.77.10.1
ip -n "$I" route add default via 10.77.10.1
ip -n "$G" route add default via 198.18.0.1
ip -n "$S" route add default via 198.18.1.1
ip netns exec "$G" sysctl -w net.ipv4.ip_forward=1
ip netns exec "$U" sysctl -w net.ipv4.ip_forward=1

default означает префикс 0.0.0.0/0, подходящий при отсутствии более точного маршрута. via указывает адрес следующего маршрутизатора, который должен быть достижим на выбранном канальном участке. Параметр ip_forward=1 разрешает ядру пересылать IPv4-пакеты между интерфейсами. Он меняет роль узла, а разрешения для конкретных пакетов задаёт фильтр. В Linux изменение ip_forward сбрасывает ряд сетевых параметров к значениям соответствующей роли; поэтому уточняющие настройки сценарий задаёт после него. Подробность подтверждена документацией сетевых параметров ядра.

Команды ip -n "$C" route get 198.18.1.20 и ip -n "$U" route get 10.77.10.10 запрашивают решение маршрутизации без HTTP-запроса. Первая должна назвать шлюз 10.77.10.1, вторая — сообщить об отсутствии пути. Формат route get, включая проверку пересылаемого пакета с параметрами from и iif, описан в ip-route(8).

6. Разрешения задаются отдельно для каждого пути

Перед изменением адресов определим, какие соединения вообще разрешены. В стенде клиентам внутренней сети разрешена одна внешняя служба S:8080; с S разрешена опубликованная служба I:7000; из внутренней сети разрешено обращение к публикации через внешний адрес G. Для остальных новых пересылаемых соединений действует запрет. Такой небольшой набор позволяет в опыте вычислить результат каждого правила.

table inet lab_filter {
  chain input {
    type filter hook input priority filter; policy drop;
    iifname "lo" accept
    ct state invalid drop
    ct state established,related accept
    ip protocol icmp icmp type {
      echo-request, destination-unreachable,
      time-exceeded, parameter-problem
    } accept
  }
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state invalid drop
    ct state established,related accept
    iifname "lan0" oifname "wan0" ip saddr 10.77.10.0/24 \
      ip daddr 198.18.1.20 tcp dport 8080 ct state new accept
    iifname "wan0" oifname "lan0" ip saddr 198.18.1.20 \
      ip daddr 10.77.10.20 tcp dport 7000 \
      ct status dnat ct state new accept
    iifname "lan0" oifname "lan0" ip saddr 10.77.10.0/24 \
      ip daddr 10.77.10.20 tcp dport 7000 \
      ct status dnat ct state new accept
  }
}

Переносы с обратной косой чертой в примере объединяют одну длинную строку. inet обозначает семейство таблицы, способное обрабатывать IPv4 и IPv6. IPv4-условия явно начинаются с ip; они сами по себе не разрешают новые IPv6-соединения. В сценарии NAT размещён в отдельной таблице семейства ip, применимой к IPv4. IPv6 требует собственного проекта адресации, маршрутов и разрешений; наличие IPv4-NAT не задаёт их автоматически.

policy drop — политика «отбросить», если ни одно правило не вынесло разрешающее решение. accept разрешает в данной цепочке дальнейшую обработку. При наличии других базовых цепочек они также могут принять решение; стенд создаёт собственное пустое пространство, где дополнительных цепочек нет. iifname сравнивает имя входного интерфейса, oifname — выходного. saddr — адрес источника, daddr — получателя, dport — порт получателя. Все условия одной строки должны совпасть.

Строка ct state invalid drop сначала отбрасывает непригодное состояние. Затем ct state established,related accept пропускает известное ответное движение и связанные сообщения. Новый запрос должен пройти одно из точных разрешений ниже. Благодаря этому само наличие состояния в ядре не превращается в разрешение для любого нового внешнего обращения.

Условие ct status dnat проверяет признак выполненного преобразования назначения. Это дополнение к адресу I и порту 7000: публикация разрешается только для соединений, для которых создано соответствующее преобразование. Прямой пакет с WAN к I:7000 не совпадёт с этой строкой, даже если вышестоящий маршрутизатор умеет доставлять внутреннюю сеть. Точная грамматика выражений ct и назначение status приведены в справочнике nft.

Цепочка input защищает сам G: это другая область, чем проходящий через него трафик. Разрешён петлевой интерфейс lo, ответы и перечисленные сообщения ICMP. Английские имена обозначают запрос эха, недостижимость, истечение времени жизни и ошибку параметров. В опыте на G нет DNS- и DHCP-служб. Если настоящий шлюз должен обслуживать DNS, отдельно проектируют входящие запросы TCP/UDP к порту 53 из нужных сетей. Для DHCPv4 проверяют обмен UDP-портов 67 и 68, включая начальные широковещательные сообщения. Просто добавить эти номера во все цепочки означало бы потерять смысл границ.

7. SNAT: исходящий запрос и симметричный ответ

table ip lab_nat {
  chain prerouting {
    type nat hook prerouting priority dstnat; policy accept;
  }
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "wan0" ip saddr 10.77.10.0/24 \
      ip daddr 198.18.1.20 tcp dport 8080 snat to 198.18.0.2
  }
}

В этом правиле источник меняется только у подходящего обмена, выходящего через wan0. Для запроса C с портом 41002 внешний S увидит 198.18.0.2:41002, если этот порт удалось сохранить. Выбранный адрес назначен G на внешнем интерфейсе, поэтому U уже знает маршрут к нему как к непосредственно подключённому соседу.

Место наблюденияИсточникПолучатель
C отправляет запрос; G принимает его из LAN10.77.10.10:41002198.18.1.20:8080
G отправляет запрос в WAN; S принимает198.18.0.2:41002198.18.1.20:8080
S отправляет ответ; G принимает из WAN198.18.1.20:8080198.18.0.2:41002
G отправляет ответ в LAN; C принимает198.18.1.20:808010.77.10.10:41002

У входящего ответа ядро восстанавливает адрес назначения ещё до окончательного решения о его доставке. Поэтому пакет, пришедший на внешний адрес G, после обратного преобразования направляется через forward к C. Обратная операция получается из записи соединения. Отдельное правило DNAT «для всех ответов на порт 41002» создавать не требуется.

Изменение IPv4-адреса требует корректировки контрольной суммы IPv4-заголовка. TCP-проверка также включает адреса из псевдозаголовка и транспортные порты, поэтому нуждается в соответствующей корректировке. Данные HTTP в данном примере сохраняются. Приложение S извлекает адрес клиента из принятого сокета и показывает уже преобразованное значение. По одному этому адресу оно не различит C и другого внутреннего клиента за тем же G.

Если внешний адрес назначается динамически, вместо явного snat to 198.18.0.2 применяют masquerade, «маскировку»: адрес выбирается по выходному интерфейсу. В одном и том же условии выбирают подходящую операцию, а не ставят обе последовательно. Статический SNAT удобен для фиксированного адреса и точного понимания результата; динамическая маскировка учитывает смену внешнего адреса. Публикации и уже существующие соединения при смене адреса всё равно требуют отдельного внимания.

SNAT: один поток до шлюза, после шлюза и на обратном пути

Клиент 10.10.0.2:49152 подключается к 198.51.100.20:7000. Шлюз выпускает этот поток как 203.0.113.5:40000. Проследим преобразования обоих направлений.

Условия этого примера

Учебная модель IPv4/TCP без фрагментации, туннелей и изменения прикладных данных. Маршруты, пересылка и разрешающие правила уже настроены; оба направления проходят через один шлюз. Порт 40000 выбран свободным для примера: SNAT не обязан всегда менять порт. conntrack — подсистема отслеживания потоков Linux, а не TCP-стек конечного участника. Точные внутренние структуры и аппаратное ускорение здесь не изображены.

1. Клиент создаёт исходный поток

TCP клиента отправляет сегмент с собственным адресом и портом. Адрес назначения — сервер. MAC и TTL зависят от текущего участка и маршрута; здесь рассматриваем отдельно сетевые адреса и TCP-порты.

Действует: TCP/IP клиента.

Внутренний клиент: 10.10.0.2:49152 → сервер; Шлюз с SNAT: Нового соответствия ещё нет; Сервер: Слушает TCP/7000

  • Ключ потока: ещё не наблюдался шлюзом → TCP + два IP + два порта. Транспортный протокол важен: одинаковые числа портов UDP и TCP не делают потоки одинаковыми.
  • Источник: 10.10.0.2:49152. Внутренний конец потока.
  • Назначение: 198.51.100.20:7000. Внешний конец потока.

2. Первый пакет выбирает преобразование

После маршрутизации в выходной точке SNAT правило для первого пакета выбирает внешнее соответствие. Подсистема отслеживания связывает исходное направление и ожидаемое обратное. Разрешение пересылки проверяется правилами фильтрации отдельно.

Действует: NAT и conntrack шлюза.

Внутренний клиент: Исходный адрес не изменился; Шлюз с SNAT: 10.10.0.2:49152 ↔ …:40000; Сервер: Ещё не получил сегмент

  • Состояние преобразования: отсутствует → связь двух направлений. В stateful NAT соответствие выбирается для потока. Изменение NAT-правила не обязательно изменит уже существующее соответствие.
  • Внутренний конец: 10.10.0.2:49152. Исходный источник, который надо восстановить на ответе.
  • Внешний конец: 203.0.113.5:40000. Свободное отображение для выбранного потока; не обещание, что все потоки получат этот порт.

3. На внешнюю сторону выходит изменённый пакет

Шлюз заменяет источник. TCP SEQ, ACK и полезные данные этой модели сохраняются. Из-за адреса и порта требуется обновить контрольную сумму TCP, а из-за IPv4-адреса — сумму IP-заголовка. Маршрутизация также уменьшает TTL.

Действует: Тракт пересылки шлюза.

Внутренний клиент: Знает свой исходный поток; Шлюз с SNAT: Выходит как 203.0.113.5:40000; Сервер: Видит внешний конец

  • IPv4 src: 10.10.0.2 → 203.0.113.5. Меняется сетевой источник.
  • TCP src port: 49152 → 40000. В этом соответствии выбран другой порт; возможна и трансляция с сохранением порта.
  • SEQ и данные: номера и байты клиента → те же номера и байты. Обычный SNAT без прикладного помощника не переписывает этот TCP-поток.
  • Источник после SNAT: 203.0.113.5:40000. Именно этот конец видит сервер.
  • Назначение после SNAT: 198.51.100.20:7000. SNAT источника сам по себе не меняет получателя.
  • TCP-псевдозаголовок: Содержит IP-адреса. Он участвует в расчёте TCP checksum, но не является отдельной передаваемой частью TCP-заголовка.

4. Сервер отвечает видимому ему концу

Сервер создаёт ответ от 198.51.100.20:7000 к 203.0.113.5:40000. Он не обязан знать адрес 10.10.0.2. Возвратный маршрут должен привести ответ к шлюзу, который хранит это соответствие.

Действует: TCP/IP сервера.

Внутренний клиент: Ждёт ответ сервера; Шлюз с SNAT: Ищет обратный ключ; Сервер: Ответ → 203.0.113.5:40000

  • Направление: клиент → сервер → сервер → внешний конец NAT. Ответ не создаётся с адресом частного клиента в поле назначения: тот адрес серверу не виден.
  • Источник ответа: 198.51.100.20:7000. Тот же серверный конец, но обратное направление.
  • Назначение ответа: 203.0.113.5:40000. Сервер отвечает на источник, который был в полученном сегменте.

5. Шлюз восстанавливает внутреннее назначение

conntrack распознаёт обратное направление. До поиска маршрута пересылаемого ответа обратное преобразование меняет назначение на 10.10.0.2:49152. Отдельное правило DNAT для ответа к уже существующему SNAT-потоку не требуется.

Действует: NAT шлюза.

Внутренний клиент: Ответ пока в шлюзе; Шлюз с SNAT: dst восстановлен: 10.10.0.2:49152; Сервер: Своё TCP-состояние

  • IPv4 dst: 203.0.113.5 → 10.10.0.2. Обратная операция исходного SNAT выглядит как изменение назначения.
  • TCP dst port: 40000 → 49152. Порт восстановлен из состояния; контрольные суммы обновляются соответственно.
  • Назначение до преобразования: 203.0.113.5:40000. Ожидаемый внешний адрес и порт ответного направления.
  • Назначение после преобразования: 10.10.0.2:49152. Далее маршрут выбирается для восстановленного внутреннего адреса.

6. Клиент получает ответ своего TCP-собеседника

Внутри сети пакет снова имеет серверный источник 198.51.100.20:7000 и клиентское назначение 10.10.0.2:49152. Конечный TCP-стек проверяет свой поток. Удаление состояния NAT или смена обратного пути может нарушить этот обмен.

Действует: IP-пересылка шлюза и TCP клиента.

Внутренний клиент: Получил ответ от сервера; Шлюз с SNAT: Хранит состояние потока; Сервер: Видит 203.0.113.5:40000

  • Связь потоков: две разные пары концов на сторонах → одно состояние трансляции. NAT не означает завершение TCP на шлюзе. TCP-прокси создавал бы два отдельных соединения и имел бы другую механику.
  • Что видит клиент: 198.51.100.20:7000 → 10.10.0.2:49152. Адреса согласованы с сокетом клиента.
  • Что видит сервер: 203.0.113.5:40000 ↔ 198.51.100.20:7000. Иной вид того же проходящего через шлюз обмена.

Проверить по первоисточнику: RFC 3022 §4: адреса, порты и суммы · nftables: stateful NAT и первый пакет. Внешние ссылки требуют интернета; объяснение и схема сохранены целиком.

8. DNAT: внешняя точка входа ведёт к внутренней службе

Теперь S становится клиентом и обращается к 198.18.0.2:8080. Прежде чем G решит, что пакет адресован ему самому, в prerouting меняется получатель:

iifname "wan0" ip saddr 198.18.1.20 \
  ip daddr 198.18.0.2 tcp dport 8080 dnat to 10.77.10.20:7000

Начальная пара 198.18.1.20:42001 → 198.18.0.2:8080 превращается в 198.18.1.20:42001 → 10.77.10.20:7000. Маршрут ведёт на lan0. Фильтр проверяет уже внутренний адрес и порт, а также признак dnat. Если разрешение совпало, I получает SYN и видит настоящего для этого стенда внешнего клиента S. Преобразования источника в прямом направлении здесь нет.

Ответ I имеет пару 10.77.10.20:7000 → 198.18.1.20:42001. Адрес S находится вне подсети I, поэтому ответ идёт через шлюз G. В записи соединения известно, что внешняя сторона открывала соединение к 198.18.0.2:8080. На выходе G обратное преобразование меняет источник ответа на эту точку. Клиент S получает ожидаемое 198.18.0.2:8080 → 198.18.1.20:42001.

Полезно нарисовать обе пары conntrack: исходная S:42001 → G:8080, ответная I:7000 → S:42001. Адрес и порт сервиса в них различаются; этим запись описывает DNAT. Сохраняется один TCP-обмен, а не создаются два независимых прикладных соединения. G не разбирает HTTP-запрос и не открывает к I новый TCP-сокет от своего имени. Сервер-посредник прикладного уровня действует иначе и может, например, завершать TLS или добавлять заголовки; это уже другая архитектура.

У настоящей публикации заранее определяют доступность внешнего адреса. Если WAN G находится за ещё одним NAT, внешний клиент обращается к адресу вышестоящего устройства. Тогда преобразование или маршрут на этом устройстве тоже должны доставить пакет G. Записанное только на G правило не способно изменить судьбу пакета, который до G не дошёл. Диагностика начинается с места фактического появления первого SYN.

9. Внутренний клиент обращается через внешний адрес

Пусть C использует ту же точку публикации 198.18.0.2:8080, что и внешние клиенты. Такое обращение часто называют hairpin NAT: «разворот через NAT», по форме пути внутрь и обратно. Требования к этому поведению для TCP рассматриваются в RFC 5382, раздел 7.2. Внутреннее разрешение DNS может направлять клиентов сразу к внутреннему адресу — это отдельный вариант проектирования. Здесь специально проверим внешний адрес.

Добавим DNAT для входа из lan0. Пакет C:41003 → G:8080 станет C:41003 → I:7000 и выйдет обратно через тот же логический интерфейс lan0. Поэтому фильтру нужна строка с iifname "lan0" oifname "lan0". Запрет пересылки между одинаковыми интерфейсами сломал бы этот маршрут ещё до отправки I.

Но даже при разрешении остаётся более тонкая проблема. I видит источник 10.77.10.10, лежащий в его собственной подсети. Для ответа он выбирает прямую передачу C, узнаёт его MAC через ARP и отправляет I:7000 → C:41003. Мост G переключает Ethernet-кадр между портами. Этот обычный переключаемый путь не требует IP-маршрутизации через G. Обратное преобразование на маршрутизируемом пути не выполняется.

C ожидал SYN+ACK от 198.18.0.2:8080, а увидел отправителя 10.77.10.20:7000. Это другая пара концов. Сопоставить такой сегмент ожидающему соединению он не может. Исправим путь ответа целевым SNAT:

iifname "lan0" oifname "lan0" ip saddr 10.77.10.0/24 \
  ip daddr 10.77.10.20 tcp dport 7000 ct status dnat \
  snat to 10.77.10.1

Теперь I получает 10.77.10.1:41004 → 10.77.10.20:7000 и отвечает G. Запись соединения описывает сразу две операции: изменение назначения и источника. На обратном пути ядро восстанавливает получателя C и источник публикации G:8080. C получает именно ту пару, с которой связывался. Цена этой схемы видна приложению: I видит клиентом 10.77.10.1. Сведения о конкретном внутреннем клиенте нужно получать из наблюдений на шлюзе либо выбирать другую архитектуру доступа.

В Linux существует дополнительный путь обработки переключаемых кадров через модуль br_netfilter, то есть подключение мостового движения к некоторым IP-точкам Netfilter. Для однозначности опыта сценарий отключает соответствующие мостовые переключатели только внутри G, если они доступны. Получается простой мост для обычного обмена C–I и обычная маршрутизация для пути через IP-шлюз. Это позволяет наблюдать именно разобранную причину неудачного ответа.

10. Порты, сроки жизни и повторные попытки

Допустим, C и ещё один внутренний узел одновременно открыли соединения к S:8080 из порта 41002. До NAT адреса источников различаются. После сведения к одному внешнему адресу полные внешние пятёрки совпали бы. Ядро подбирает свободное транспортное представление, обычно изменяя порт одного обмена. У ответа на внешний порт 53001 тогда восстанавливается внутренний 41002 нужного узла. Сохранение исходного порта удобно, но считать его гарантией нельзя.

У каждой записи конечный срок жизни. TCP-состояния, успешный обмен, закрытие и тишина влияют на время хранения. У UDP отсутствие ответов также не позволяет хранить запись вечно. После удаления записи случайный поздний пакет больше не получает прежнюю привязку автоматически. Если правила допускают только известное ответное движение, такой пакет может быть отброшен. При переполнении таблицы ядро теряет возможность учитывать новые обмены; симптомы напоминают случайные проблемы соединения при исправных маршрутах.

Изменение текста NAT-правила не переписывает уже созданные привязки. Поэтому в сценарии каждый следующий опыт использует новый исходный TCP-порт: 41001, 41002, 41003, 41004. Пятёрка меняется, создаётся новая запись, новые правила получают свой первый пакет. Иначе исследователь способен увидеть старое поведение после правильного изменения конфигурации и ошибочно решить, что правило не применяется.

Перезапускать всю таблицу учёта рабочего маршрутизатора ради проверки одного соединения означает затронуть остальные действующие обмены. В лаборатории допустимо удалять собственное пространство целиком. В работающей сети проверку строят на новом соединении и при необходимости адресном управлении конкретной записью. При чтении счётчиков также фиксируют момент их обнуления и создание новых соединений. Ноль у нового NAT-правила ещё может означать, что исследуемый поток был создан раньше.

11. Связанные ошибки, фрагменты и проверка источника

Когда промежуточный маршрутизатор отправляет ICMP-ошибку, она содержит часть пакета, вызвавшего проблему. Например, сообщение о недоступности порта UDP включает исходный IP-заголовок и начало транспортных данных. Ядро может сопоставить вложенный пакет записи conntrack и отметить ошибку как related, «связанную». Для NAT важны как внешние поля ICMP-пакета, так и сведения об адресах внутри процитированного пакета: отправившее приложение должно узнать свой обмен после обратного преобразования.

Поэтому разрешение нужных ошибок — часть работоспособности сети. Если скрыть сообщение о слишком большом пакете на пути с меньшим MTU, маленькие запросы могут работать, а передача крупных данных зависать. Сама успешная загрузка короткого ответа из этого стенда не проверяет все размеры пакетов. Практический следующий опыт — уменьшить MTU на одном учебном участке, предсказать сообщение ICMP и проследить изменение размера передаваемых данных.

Фрагмент IPv4 после первого обычно не содержит TCP- или UDP-портов: они остались в начальном фрагменте. Поэтому обработка NAT и учёт обменов требуют согласованной обработки фрагментов. Обычный отслеживаемый путь Linux использует механизмы дефрагментации до важных операций учёта. Нельзя рассуждать так, будто каждый отдельно полученный фрагмент всегда содержит полную пятёрку. Это особенно заметно при захвате: в одном месте наблюдения видны исходные фрагменты, в другом — уже результат их сборки.

Ещё одна проверка Linux — rp_filter, от reverse path filter, «проверка обратного пути». Строгий режим 1 проверяет, совпадает ли входной интерфейс с лучшим обратным маршрутом к источнику. Свободный режим 2 требует наличия какого-либо маршрута к источнику. Режим 0 отключает эту проверку. При нескольких выходах и асимметричном движении, когда запрос и ответ идут разными путями, строгий режим способен отбросить корректный для проекта пакет ещё до ожидаемого наблюдения.

Для первого опыта отсутствие маршрута U к C должно мешать именно ответу. Поэтому сценарий явно задаёт режим 0 внутри учебных пространств. Иначе наследованный режим 2 способен остановить уже исходный запрос с источником C на U: обратного маршрута к C нет. На настоящем шлюзе режим выбирают вместе с моделью маршрутизации и защитой от подмены источников. Нужно проверять значения и для all, и для входного интерфейса: ядро использует большее из соответствующих значений.

12. Запускаем воспроизводимый опыт без интернета

Откройте терминал в папке labs рядом с книгой. Сначала прочитайте файл, затем посмотрите справку и запустите опыт:

bash nat-lab.sh --help
bash nat-lab.sh --run

Без --run сценарий печатает справку. Сначала проверяется наличие необходимых программ: ip, nft, python3, sysctl, mktemp. Установка и скачивание не выполняются. Если обычный пользователь имеет право создавать пользовательские пространства Linux, сценарий перезапускает себя через unshare -Urnm. unshare создаёт отдельный контекст изоляции; -U создаёт пользовательское пространство, -r отображает текущего пользователя в его администратора, -n отделяет сеть, -m — точки монтирования.

Статус администратора действует внутри нового пользовательского пространства. Затем распространение монтирований делается частным и внутри этого контекста поверх /run монтируется временная файловая система. Там создаётся каталог имён сетевых пространств. Основной /run компьютера остаётся в его прежнем контексте. Если система запрещает пользовательские пространства или нужные возможности ядра недоступны, сценарий завершится с объяснением. Отказ возможности — самостоятельный результат проверки среды, а не доказательство ошибки правил NAT.

Внутри стенда создаются три небольшие HTTP-службы стандартной библиотекой Python. S сообщает увиденный адрес клиента. I делает то же самое для опубликованной службы. На C дополнительно слушает порт 9090: так проверка запрета WAN доказывает работу фильтра при действительно существующей службе, а не случайное отсутствие слушающего сокета. Клиент Python задаёт исходный адрес и порт, ждёт ответ ограниченное время и проверяет содержимое.

Имена всех пространств получают уникальный префикс запуска. Сценарий ведёт список успешно созданных пространств, запоминает идентификаторы собственных серверов и время их создания. При штатном выходе, прерывании Ctrl+C или ошибке он завершает эти процессы и удаляет зарегистрированные пространства. Сравнение времени создания защищает от совпадения с позднее повторно использованным номером процесса. Системные процессы по имени не завершаются. Сетевые настройки выполняются только с явным именем нового пространства.

Непосредственный запуск с правами root в собственной учебной виртуальной машине также возможен, если пользовательская изоляция запрещена. Сценарий всё равно создаёт отдельные именованные сетевые пространства и применяет правила только внутри G. Для чтения учебника выполнение стенда вообще не требуется: следующие результаты позволяют пройти рассуждение на бумаге.

13. Ожидаемые результаты и фактическая проверка

ЭтапЧто проверяетсяОжидаемое наблюдение
1Решение U о пути к CСообщение Network is unreachable: сеть недостижима

peer означает «другая сторона соединения»; поле отчёта берётся из адреса принятого сервером сокета. local — локальный адрес сервера, peer_port — наблюдаемый исходный порт клиента. HTTP-код 200 сообщает об успешном прикладном ответе. Сами значения адресов доказывают конкретное преобразование сильнее, чем одна строка «соединение успешно».

Фактически проверено при подготовке этой версии 27 октября 2026 года: сценарий целиком выполнен на Linux обычным пользователем через unshare -Urnm. Все семь этапов прошли. До SNAT и до исправления внутреннего разворота наблюдалось превышение времени ожидания. После SNAT внешний сервер показал 198.18.0.2, после DNAT внутренний сервер показал 198.18.1.20, после исправления разворота — 10.77.10.1. Проверка нового внешнего входа увеличила запрещающий счётчик. Сценарий завершился штатной очисткой.

Перед проверкой запрещённого входа в U временно добавляется маршрут к внутренней сети. Иначе пакет остановился бы на U, а счётчик G остался бы нулевым. После опыта маршрут удаляется. Это важная конструкция проверки: сначала обеспечить достижимость места, которое должно отказать, затем подтвердить отказ именно там. Просто ждать неудачного соединения для доказательства работы межсетевого экрана недостаточно.

На этапе 3 отдельно проверено: счётчик создания исходящих NAT-привязок равен 1, а счётчик пакетов цепочки forward больше 1. Успешное TCP-соединение уже требует SYN, SYN+ACK и ACK, затем передаёт запрос и ответ. Поэтому один прирост NAT-счётчика совместим с несколькими пакетами. Точное число пакетов и байтов зависит от разбиения данных и времени наблюдения, поэтому сценарий проверяет отношение, а не хрупкое равенство одному заранее выбранному числу.

14. Искать первое несовпадение с предсказанием

Представим, что внешний запрос не работает. Первое проверяемое утверждение: SYN появился у WAN G. Если нет, исследуются адрес назначения, маршрут до G и вышестоящее устройство. Если появился, следующий вопрос — сработало ли новое DNAT-преобразование. Далее проверяются адрес после преобразования, выбранный выходной интерфейс, разрешение в forward, ARP для I и наличие SYN у I. Каждый шаг проверяет одну конкретную границу.

Успешный приход SYN на I ещё оставляет обратный путь. Проверяются слушающий сокет, появление SYN+ACK, таблица маршрутов I, адрес следующего узла, приход ответа на G и его внешний вид после обратного преобразования. Если SYN+ACK уходит прямо C при обращении через внешний адрес, уже известно, почему соединение не складывается. Если ответ выходит с правильной парой, но не достигает клиента, исследование продолжается за G.

ip -n "$G" -br address
ip -n "$G" route show
ip -n "$I" route get 198.18.1.20
ip -n "$G" neigh show
ip netns exec "$I" ss -ltn
ip netns exec "$G" nft list ruleset
ip netns exec "$G" tcpdump -ni wan0 'tcp port 8080'
ip netns exec "$G" tcpdump -ni lan0 'tcp port 7000'

Эти команды относятся к живому ручному стенду с сохранёнными значениями переменных. Автоматический сценарий удаляет его после завершения. ss -ltn показывает слушающие TCP-сокеты без разрешения имён. У tcpdump опция -n сохраняет числовые адреса, -i выбирает интерфейс. Команда захвата не обязательна для сценария. Два захвата показывают разные пары адресов одного обмена; сопоставлять их помогают порты, номера TCP и время.

Для точного разбора правил nft имеет механизм трассировки: пакет помечают meta nftrace set 1, а события читают через nft monitor trace. Слово trace означает последовательный след прохождения. Включать след стоит для узко выбранного пакета в собственном стенде: все пакеты сразу дадут длинный поток. Содержимое правил, интерфейсы и значения счётчиков сохраняют до изменения конфигурации, чтобы наблюдение можно было связать с действовавшим набором.

15. Перенос на постоянный шлюз и проверка изменения

Временные команды устанавливают текущее состояние ядра. После перезагрузки понадобятся средства постоянной настройки конкретной системы: назначение адресов, поднятие интерфейсов, маршруты, разрешение пересылки и загрузка фильтра. Их порядок и владельца определяют заранее. Например, сетевой менеджер способен восстановить собственные маршруты поверх ручных, а отдельная программа управления экраном — пересобрать правила. На шлюзе должен быть понятен источник итоговой конфигурации.

Перед применением файл правил проверяют командой nft --check --file файл в нужном пространстве. Проверка выявляет синтаксические и часть смысловых ошибок ядра, но не доказывает правильность адресного плана и обратного пути. Затем файл загружается как единая транзакция командой nft --file файл. В стенде flush ruleset очищает только заведомо собственный пустой G. При переносе в действующую систему сначала изучают уже существующие таблицы и владельцев: такая строка удаляет весь набор правил выбранного сетевого пространства.

Для изменения удалённого шлюза продумывают возврат до загрузки нового файла: сохраняют текущую конфигурацию, обеспечивают локальный или иной независимый доступ и готовят отложенное восстановление. После применения сначала проверяют административный доступ, затем разрешённые новые соединения, ответное движение, запреты и крупные передачи. Только после подтверждения отменяют восстановление и сохраняют постоянную настройку. Конкретный способ отложенного возврата зависит от системы управления устройством.

У аппаратного маршрутизатора тем же понятиям соответствуют внутренний и внешний интерфейсы, таблица маршрутов, таблица состояний, преобразование источника, публикация назначения и правила пересылки. Названия пунктов и порядок обработки зависят от платформы. Вы уже можете проверить документацию содержательно: видит ли правило исходный адрес назначения или преобразованный, где применяется фильтр, есть ли разворот, сохраняет ли публикация адрес клиента, что происходит с действующими записями при смене правил.

Итоговая задача. I перенесён в отдельную подсеть за другим маршрутизатором. SNAT разворота удалили, и обращение C через внешний адрес внезапно продолжило работать. Какие условия могли это объяснить?

Разбор

Ответ I к C теперь может проходить через G вследствие нового адресного плана и маршрутов. Тогда G видит ответное направление и выполняет обратное DNAT без дополнительного изменения источника запроса. Нужно нарисовать именно новые маршруты: отдельная подсеть сама по себе не гарантирует прохождение через G. Работоспособность объясняет путь обоих направлений и сохранённая запись, а не название функции в интерфейсе устройства.

Такое рассуждение переносится на другие сетевые задачи. Для любого обмена сначала фиксируются исходные значения, затем путь обработки и изменения на каждой границе. После этого для ответа выполняется самостоятельный проход. Команды становятся способом проверить модель: они показывают, какой маршрут выбран, какое правило совпало и какую пару адресов действительно увидела принимающая программа.
