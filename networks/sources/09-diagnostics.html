Диагностика помогает установить причину наблюдаемого сбоя. За сообщением «не работает сеть» могут стоять отсутствие сигнала, ошибочный маршрут, закрытый порт, неудачная аутентификация или неправильный ответ приложения. Проверку выбирают так, чтобы её результаты позволяли различить возможные причины и определить следующий шаг.

1. Как превращать наблюдение в доказательство

Сначала записывают точное действие: с какой машины, каким пользователем, по какому имени, адресу, порту и протоколу; что ожидали и что получили; когда это было. «Открыл сайт» хуже, чем «в 12:04 клиент 192.0.2.10 обратился HTTP к app.lab.test:7000/api/session и получил 403». Во втором случае понятен как минимум достигнутый уровень: кто-то смог вернуть HTTP-ответ.

Затем отделяют наблюдение от объяснения. Наблюдение: три SYN ушли, ответа в данной точке записи нет. Гипотезы: запрос потерялся дальше; сервер не отвечает; ответ пошёл другим путём; фильтр молча удаляет трафик; выбранная точка записи не видит обратное направление. Формулировка «сервер выключен» пока сильнее имеющихся данных.

Контролируемое сравнение меняет одно условие. Одинаковый URL с разными DNS-ответами сравнивает выбор адреса. Обращение по IP одновременно может поменять DNS, HTTP Host, имя сертификата и имя службы Kerberos. Такое сравнение полезно только если явно учесть каждое изменение. Иначе «по IP работает» не сообщает, какой именно из четырёх факторов виноват.

Инструмент тоже участник эксперимента. Он может разрешать имена, использовать прокси из окружения, иметь собственное хранилище сертификатов и выполнять запрос под другим пользователем. Прокси — промежуточная служба, принимающая обращение клиента и выполняющая следующий обмен от его имени; наличие такого посредника меняет путь и точки возможного отказа. Настройки браузера не обязаны совпадать с настройками curl. Сначала устанавливают, совпали ли условия, потом сравнивают результаты.

2. Как читать команды и их вывод

Командная оболочка — программа, которая разбирает введённую строку и запускает другие программы. В примере ip -br address слово ip — имя программы, -br — её параметр сокращённого вывода, address — выбираемый объект. Знак доллара в чужом руководстве часто изображает приглашение оболочки; копировать его не нужно. Здесь команды показаны без приглашения.

Одинарные кавычки обычно передают содержимое буквально в оболочке Linux. Поэтому фильтр 'tcp port 7000' становится одним аргументом tcpdump, а не тремя независимыми параметрами. Обратная косая черта в самом конце строки переносит команду на следующую строку; после неё не должно быть случайного пробела. Символ вертикальной черты | направляет вывод первой программы на вход следующей. Перенаправление > записывает вывод в файл: создаёт его, если файла ещё нет, или заменяет прежнее содержимое.

Код завершения — небольшое число, сообщаемое программой вызывающей оболочке. Ноль обычно означает, что программа считает своё действие успешным. Это не всегда успех исследуемой системы: curl по умолчанию способен успешно получить HTTP 500 и завершиться с нулём. Успешно доставленный ответ об ошибке остаётся ошибкой приложения.

Ниже выводы помечены как учебные. Имена интерфейсов, адреса, счётчики и права просмотра на объекте будут другими. Не нужно заставлять действующую систему совпасть с иллюстрацией.

3. Сначала установить локальный контекст

hostname
id
ip -br link
ip -br address
ip route get 198.51.100.20

hostname сообщает имя машины; id — пользователя и группы текущего процесса. Это важно, если команду вводят внутри SSH-сеанса — защищённого удалённого сеанса командной оболочки: она исполняется на удалённой машине. ip -br link сокращённо показывает интерфейсы и их состояние, ip -br address — адреса. Наличие адреса не гарантирует исправный канал, а включённый интерфейс не гарантирует адрес или маршрут.

Учебный вывод:
lo       UNKNOWN 127.0.0.1/8 ::1/128
ens18    UP      192.0.2.10/24

198.51.100.20 via 192.0.2.1 dev ens18 src 192.0.2.10 uid 1000

lo — внутренний интерфейс обратной связи; его состояние UNKNOWN само по себе не авария. ens18 — имя второго интерфейса. В результате выбора маршрута via указывает ближайший шлюз, dev — интерфейс, src — предполагаемый исходный адрес. Это расчёт маршрута ядром, а не пробная доставка пакета серверу. Сосед ещё может не отвечать, а фильтр — запрещать передачу.

Если приложение привязано к конкретному исходному адресу, использует отдельное сетевое пространство или служебные метки пакетов ядра, обычный запрос маршрута из вашей оболочки может дать другой результат. Метка здесь — дополнительное внутреннее значение, по которому Linux способен выбрать правило маршрутизации; отдельного поля для неё в IP-заголовке нет. В таких случаях проверяют правила командой ip rule show, выбранные таблицы и сетевое пространство приложения. Важно воспроизвести условия именно того процесса, обмен которого исследуется.

4. Проверить ближайшего соседа и линию

ip neigh show dev ens18
ip -s link show dev ens18
ethtool ens18

Таблица соседей связывает IP ближайшего узла с канальным адресом. Запись 192.0.2.1 lladdr 02:00:00:00:00:01 STALE означает, что адрес известен, но подтверждение достижимости устарело. Слово lladdr обозначает канальный адрес, здесь MAC. Состояние STALE, «устаревшее», допускает использование известного адреса; затем ядро при необходимости проверяет достижимость. FAILED, «не удалось», означает, что проверка соседа закончилась неуспешно. В этом случае сначала выясняют, почему не удаётся связаться с ближайшим узлом, и только после восстановления этого обмена переходят к HTTP.

Статистика интерфейса содержит накопительные счётчики. Один большой общий счётчик ошибок за год менее полезен, чем его рост за минуту воспроизводимого сбоя. Запишите значения до и после. Отбрасывание из-за отсутствия буфера и повреждение кадра в линии имеют разные причины; подробные счётчики драйвера смотрят через ethtool -S ens18, если инструмент установлен и предоставляет нужные данные.

Команда ethtool ens18 показывает сведения о соединении, которые предоставляет устройство и его драйвер. Для физического Ethernet это могут быть скорость, наличие сигнала и режим дуплекса — возможность одновременной передачи в обоих направлениях. У виртуальной карты набор сведений другой: отдельного кабеля за ней может вообще не быть. Поэтому смысл каждого показателя уточняют по типу интерфейса.

5. Кто слушает порт и чего ждёт соединение

ss -ltn
ss -tn
ss -tin
ss -ltnp

ss показывает сведения о сокетах. Параметр -l выбирает слушающие, -t — TCP, -n оставляет адреса и порты числовыми, -i добавляет внутренние сведения TCP, -p просит данные о процессах. Без достаточных прав чужой процесс может быть скрыт. Это не доказывает отсутствие владельца сокета.

Учебный вывод:
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN 0      128    0.0.0.0:7000       0.0.0.0:*
ESTAB  0      73     192.0.2.10:49152   198.51.100.20:7000

LISTEN — ожидание новых соединений, ESTAB — установленное соединение. У слушателя Recv-Q показывает число установленных соединений, ожидающих принятия приложением, а Send-Q — предел этой очереди. Для установленного TCP Recv-Q обычно показывает доступные байты, ожидающие чтения приложением, а Send-Q — байты, принятые в отправляющий TCP, но ещё не подтверждённые: среди них могут быть и пока не выпущенные в сеть. Точные дополнительные показатели зависят от версии ss и ядра. Нельзя механически сравнивать две строки как одинаковые величины.

0.0.0.0:7000 у слушателя означает привязку ко всем локальным IPv4-адресам в данном сетевом контексте. Привязка 127.0.0.1:7000 ограничивает доступ обратной связью: удалённый клиент не попадает туда прямым обращением к внешнему адресу машины. IPv6-слушатель [::]:7000 требует отдельной проверки настроек двойного стека; по одной строке не всегда можно обещать приём IPv4.

Растущая Recv-Q у установленного сокета наводит на медленное чтение приложением. Растущая Send-Q означает незавершённую сетевую передачу с точки зрения подтверждений, но причиной могут быть потери, закрывающееся окно получателя или другие ограничения. Только дополнительные сведения о времени, повторных передачах и противоположной стороне позволяют различить варианты. Названия и флаги проверены по справочнику ss.

6. Что именно показывает запись пакетов

Захват трафика — запись сообщений, доступных инструменту в выбранной точке. Команда tcpdump просит ядро передавать ей копии этих сообщений. На клиенте можно наблюдать сообщения у его интерфейса; чтобы выяснить, что дошло до сервера, нужна запись у сервера или на промежуточном участке. Обычный порт коммутатора получает только предназначенные ему кадры и часть общих рассылок, поэтому подключённый к нему анализатор не видит весь обмен в VLAN.

sudo tcpdump -ni ens18 -s 0 -c 50 'host 198.51.100.20 and tcp port 7000'
tcpdump -nn -tttt -vv -r labs/document-flow-http.pcap

Первая команда записывает обмен на указанном интерфейсе и обычно требует дополнительных прав. -i ens18 выбирает интерфейс, -n отключает преобразование адресов в имена, -s 0 просит сохранять пакет целиком в пределах возможностей захвата, -c 50 завершает работу после 50 пакетов, прошедших фильтр. Фильтр оставляет обмен с указанным адресом и TCP-портом. Удвоенный параметр -nn дополнительно сохраняет числовые обозначения портов и протоколов вместо справочных имён. Вторая команда читает наш готовый файл. -r задаёт имя файла, -tttt добавляет дату и время, -vv — подробности заголовков.

Если фильтр слишком узкий, из него исчезнут DNS, ARP и сообщения ICMP о проблемах доставки. Пустая запись TCP тогда совместима с неудачным разрешением имени. Сначала выберите вопрос, затем фильтр. Чтобы увидеть, как определяется сосед, нужен ARP. Чтобы расследовать ограничения размера, может понадобиться ICMP. Универсального одного выражения для всех случаев нет.

Метка времени записи зависит от источника отметки и точки наблюдения. Обработка процессором и аппаратные часы карты — разные источники времени. Даже два захвата с миллисекундной разницей нельзя напрямую вычитать как сетевую задержку без понимания синхронизации часов. Отдельные механизмы Linux описаны в документации временных отметок.

На отправляющей машине карта иногда должна досчитать контрольную сумму позже, чем ядро скопировало данные в захват. Инструмент тогда показывает «неверную» сумму у кадра, который на линии будет правильным. Аналогично запись до аппаратного разделения крупного блока может показать размер больше обычной MTU. Это повод сравнить точки и режимы обработки, а не немедленно объявлять сеть повреждённой. В нашем синтетическом pcap суммы уже рассчитаны программно и проверены.

7. Читать последовательность, а не одну строку

HTTP 401/403/500Получен ответ на уровне HTTPДля 401 — порядок проверки личности; для 403 — причину отказа в доступе; для 500 — ошибку серверной обработки. Во всех случаях сначала устанавливают, какой сервер или посредник сформировал ответ

RST — признак сброса TCP-соединения. Отсутствие слушателя обычно приводит к такому отказу; похожий ответ может сформировать и фильтр с активным отклонением. Английское сообщение timeout означает истечение срока ожидания. В этом случае клиент не получил ожидаемый результат вовремя. Явный отказ и отсутствие ответа задают разные направления проверки; точную причину устанавливают по слушающим сокетам, маршрутам, фильтрам и записям с обеих сторон.

Сервер получил запрос, почему клиент ждёт?

На сервере есть входящий HTTP-запрос, его TCP-подтверждение ушло. Через десять секунд ответа нет. Коллега предлагает менять MTU.

Разбор порядка проверки

Полный маленький запрос уже принят транспортом. Сначала следует установить, прочитан ли он обработчиком, какой процесс занят запросом и не ждёт ли он базу, Kerberos, файл или блокировку. Проблема дальнейшей передачи ответа возможна, если сервер его действительно сформировал; это подтвердит обратный трафик. Менять MTU без такого различения — менять условие, связи которого с наблюдением пока нет.

8. Отдельно измерять разрешение имени, соединение и ответ

curl --connect-timeout 5 --max-time 15 \
  -o /dev/null -sS \
  -w 'HTTP=%{http_code} DNS=%{time_namelookup} CONNECT=%{time_connect} FIRST=%{time_starttransfer} TOTAL=%{time_total}\n' \
  'http://app.lab.test:7000/api/session'

--connect-timeout ограничивает фазу установления соединения, --max-time — всю операцию. -o /dev/null направляет тело в специальный приёмник, который его отбрасывает; -sS убирает обычный индикатор, сохраняя сообщения ошибок. -w задаёт формат итоговых показателей. Это обычный HTTP-запрос, который может попасть в журналы и пройти обработку; адрес здесь учебный.

Времена — накопительные отметки от начала операции, а не независимые длительности фаз. Подпись DNS означает момент окончания поиска имени, CONNECT — окончания подключения, FIRST — появления первого байта ответа, TOTAL — окончания операции. При простом новом прямом соединении разность CONNECT−DNS приблизительно выделяет установление TCP, FIRST−CONNECT включает дальнейшую подготовку и ожидание первого байта. При HTTPS прибавляется установка TLS, при прокси и повторно используемых соединениях интерпретация меняется. Нельзя сложить все выведенные числа и назвать сумму временем запроса. Значение FIRST не равно чистому времени SQL.

Чтобы проверить определённый адрес, сохранив имя HTTP-узла, curl умеет --resolve app.lab.test:7000:198.51.100.20. Эта опция подменяет сопоставление имени с адресом для указанной пары имени и порта в данном запуске. URL продолжает содержать имя; для HTTPS оно продолжает участвовать в проверке. Это точнее грубой замены имени в URL на IP. Однако такое действие ещё не воспроизводит выбор адресов браузером или настройки прокси. Параметры и их ограничения сверены со справочником curl.

9. Три законченных расследования

Случай А: «сайт открывается только на сервере»

На самом сервере ответ получается по 127.0.0.1:7000. С клиента при обращении к внешнему адресу приходит отказ. Проверяем на сервере ss -ltn: слушатель привязан только к 127.0.0.1. Локальный запрос подтверждает, что обработчик принимает обращения через обратную связь. Для внешнего доступа требуется другая точка приёма. Сверяем схему приложения: возможно, перед обработчиком должен находиться прокси, принимающий внешние запросы. Тогда проверять нужно его слушающий сокет и передачу запроса локальному обработчику. Если же служба должна принимать внешние соединения самостоятельно, проверяют её адрес привязки.

Случай Б: «иногда тормозит, ping нормальный»

На сервере во время сбоя растёт число занятых обработчиков, на клиенте RTT остаётся прежним. Захват показывает быструю передачу запроса и паузу до ответа. Это направляет расследование к времени обслуживания, а не только к линии. Проверяем очереди приложения, зависимость от базы и медленного файлового хранилища. Если одновременно идёт копирование и RTT под нагрузкой тоже растёт, добавляется гипотеза очереди узкого канала. Успешный ping без нагрузки не исключает очередь под нагрузкой.

Случай В: «маленькая страница работает, файл не скачивается»

Начало соединения и маленький ответ проходят. В передаче файла повторяется одна и та же большая часть последовательности. Сопоставляем захват на двух концах и ограничения размера пути. Если большие пакеты пропадают на участке с меньшей допустимой длиной, а сообщения об этом не возвращаются, отправитель может повторять неподходящий размер. Но похожая картина возникает при потере под нагрузкой или фильтрации содержимого. Чёткое различение даёт зависимость от размера и точки исчезновения, а не само слово «скачивание».

10. Как оставить запись, полезную после возвращения

Краткий протокол содержит цель проверки; время с часовым поясом; машины и роли участников; исходный и конечный адреса и порты; точную команду; код завершения; выдержку вывода; точку захвата; версию инструмента, если её поведение важно; наблюдение и отдельно гипотезу. Успешные соседние проверки также полезны: они показывают, какие границы уже пройдены.

Секретные токены, пользовательские документы и содержимое рабочих запросов не нужны для большинства учебных выводов. В этой книге все записи синтетические. На реальном объекте объём и место хранения диагностических материалов выбирают по установленному порядку. Технически главное — сохранять достаточные поля для сопоставления одного обмена, не заменяя доказательства многословным пересказом.

Дополнительно: справка установленной программы man tcpdump, man ip-route, man ss доступна без интернета, если соответствующие справочные страницы установлены. В книге разъяснены все используемые параметры; наличие этих страниц не требуется для чтения.

10. Счётчик, скорость и место потери: одна запись за две минуты

Пусть счётчик переданных байтов интерфейса был 100000000 в 10:00:00 и 220000000 в 10:01:00. За 60 секунд прирост составил 120000000 байт, то есть 120000000×8/60=16000000 бит/с, 16 Мбит/с. Это средний темп на границах именно этого счётчика. Его 220 Мбайт нельзя делить на минуту, если начало накопления неизвестно. Аналогично нулевой прирост за минуту не запрещает более ранние ошибки.

После перезапуска устройства второй снимок может оказаться меньше первого. Отрицательный темп не является направлением передачи: произошли сброс, смена объекта, оборачивание ограниченного счётчика либо ошибка сопоставления. Идентифицируйте интерфейс и контекст, учитывайте время старта. Для программных интервалов используют монотонные часы — источник времени, который не скачет от ручной установки календаря. Для сопоставления журналов разных машин дополнительно нужна синхронизация календарных часов и оценка её точности.

Доля потерь требует общего определения входа и выхода. Если в синтетическом прогоне отправили 100000 уникально пронумерованных UDP-сообщений, а получатель увидел 99900 разных номеров после окончания допустимого ожидания, потеря по этому критерию — 0,1%. Повторы и переупорядочивание обрабатываются отдельно. Делить счётчик отбрасываний всех протоколов интерфейса на число полезных сообщений приложения нельзя без доказательства, что числитель и знаменатель относятся к одной популяции. Счётчик dropped в программе захвата может означать потерю наблюдения в буфере захвата, а не потерю пакета на линии. Это основание проверить полноту записи.

11. Разложить время HTTP-запроса, сохранив его смысл

curl --silent --show-error --output /dev/null \
  --write-out 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total} code=%{http_code}\n' \
  https://app.lab.test/health

Это форма наблюдения за одним выбранным URL. Имя и путь заменяются на разрешённую проверку собственного сервиса. --silent убирает индикатор хода, --show-error возвращает сообщение при ошибке даже в тихом режиме; --output /dev/null не печатает тело; --write-out задаёт итоговые поля. Проверка TLS остаётся включённой. Успешный код процесса curl и HTTP-код рассматриваются отдельно: без соответствующего параметра отказ HTTP может не быть отказом самой передачи.

Большинство перечисленных времён — накопленные отметки от начала операции, а не независимые длительности этапов. В простом новом HTTPS-соединении без прокси и перенаправлений получены учебные секунды: dns=0.004, connect=0.014, tls=0.044, first=0.124, total=0.144. Тогда после разрешения имени до окончания подключения прошло примерно 10 мс; от подключения до окончания TLS — 30 мс; от готового TLS до первого байта ответа — 80 мс; после первого байта до конца — 20 мс. Последние 80 мс включают передачу запроса, сетевой путь, очереди и серверную работу; это не изолированное время SQL или CPU сервера.

Если соединение переиспользовано, был прокси, перенаправление, HTTP/3, перекрытие этапов либо несколько адресов-кандидатов, простая разность может иметь другой смысл. Нулевое время этапа не означает бесконечно быстрый новый TLS: новый этап мог вообще не выполняться. Сначала сохраните контекст и установите, какой обмен произошёл. Поля и их границы определены в руководстве curl, --write-out. Для точной серверной фазы нужны собственные отметки приложения и общий идентификатор запроса, а для долгих операций — раздельные этапы ожидания соединения, SQL, файла и отправки тела.

Заметки хранятся только в этом браузере. Их можно выгрузить кнопкой в оглавлении.
