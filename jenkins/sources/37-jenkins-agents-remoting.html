Агенты и Remoting: как команда добирается до другой машины

Разберём установление канала, идентичность агента, передачу команд и файлов, запуск процессов и обрыв связи. SSH и WebSocket здесь являются способами транспорта, а не взаимозаменяемыми названиями всей архитектуры.

Сначала запускается агентская JVM

В Jenkins узел описывает доступную среду выполнения: имя, метки, каталог и количество исполнителей. На удалённой стороне работает Java-процесс агента. Библиотека Remoting предоставляет канал между этим процессом и контроллером; по нему передаются управляющие вызовы, данные и результаты. Сборочная команда затем запускается уже как отдельный процесс ОС агента. Следовательно, есть минимум две цепочки ошибок: управление и сам рабочий процесс.

Агенту нужна Java, совместимая с контроллером и используемым выпуском Remoting. Самый понятный учебный выбор — Java 21 по обе стороны зафиксированного Jenkins. Go и Git нужны для приложения, Python — для небольшого сценария метаданных. Успешное подключение JVM не проверяет их наличие. Метка handbook-local лишь разрешает планировщику выбирать этот узел; администратор отвечает за то, что метка соответствует реальным инструментам и свойствам.

Нулевое число исполнителей встроенного узла не запрещает контроллеру выполнять собственную логику Groovy Pipeline. Оно запрещает размещать обычные сборочные процессы на встроенном узле. Контроллер остаётся управляющим приложением с потоками, памятью и работой по сохранению графа. Агент переносит рабочие команды, но не превращает весь Jenkins в распределённый интерпретатор Groovy.

Кто инициирует соединение

Для SSH-способа контроллер связывается с SSH-сервером машины агента, проверяет её ключ, аутентифицируется и запускает необходимый агентский процесс. После запуска управление Jenkins использует Remoting поверх полученного транспорта. Это требует достижимости SSH-порта с контроллера и правильно настроенных прав удалённого пользователя. «Не удалось запустить агент по SSH» надо разложить на DNS, соединение, проверку ключа, аутентификацию, поиск Java и запуск Remoting.

Inbound означает, что агент сам инициирует подключение к контроллеру. Название описывает взгляд со стороны контроллера: к нему приходит соединение. Агент получает имя и секрет конкретной регистрации. В TCP-варианте сначала по HTTP получают сведения о канале, затем устанавливают отдельное соединение с портом агентов. Доступ к веб-странице не доказывает доступность второго порта. Открывать наугад много портов не нужно: выбирают один предусмотренный способ.

WebSocket-вариант использует обновление HTTP-соединения и позволяет обойтись без отдельного TCP-порта агентов. Это удобно за корректно настроенным обратным прокси. Но протокол не устраняет требования аутентификации, совместимости Remoting и сохранения соединения прокси. Таймаут промежуточного устройства может разрывать рабочий канал, даже если обычные короткие запросы к интерфейсу проходят.

Читаем команду запуска целиком

java -Xms32m -Xmx128m -jar "$JENKINS_LAB_ROOT/agent.jar" \
  -url http://127.0.0.1:18080/ \
  -name handbook-agent -secret "@$JENKINS_LAB_ROOT/agent-secret.txt" \
  -webSocket -workDir "$JENKINS_LAB_ROOT/agent-home"

Это команда отдельного локального агента лаборатории после создания узла и получения его секрета. До -jar задаются размеры Java-кучи; 128 MiB — учебная граница для агента малого опыта, а не вся память Python-сборки. После имени JAR идут аргументы Remoting. -url задаёт адрес контроллера; -name должен совпасть с зарегистрированным именем узла; -secret передаёт доказательство права подключиться под этим именем.

Префикс @ означает чтение аргумента из файла, поэтому значение секрета не написано прямо в строке запуска. Это уменьшает его распространение через историю команд и список аргументов процессов; файл всё равно требует ограничения доступа. -webSocket выбирает соответствующий транспорт, -workDir задаёт внутренний каталог Remoting для журналов, кэша классов и метаданных. Он не является автоматическим указанием текущего каталога каждой сборочной команды. Для актуального агентского JAR смотрят -help: параметры разных поколений могут отличаться.

agent.jar получают от используемого контроллера по адресу /jnlpJars/agent.jar, а не берут случайную старую копию из другого стенда. Историческое название пути не означает, что запускается Java Web Start. Старые инструкции с javaws не описывают выбранный современный механизм. Секрет узла не является паролем пользователя браузера и не должен передаваться в книгу, общий журнал или открытый репозиторий.

Что проходит по установленному каналу

Контроллер запрашивает действия в контексте агента: проверить путь, создать каталог, запустить процесс, прочитать файл, передать результат. Для работы библиотека поддерживает удалённые вызовы и необходимые данные, включая загрузку применимых классов. Канал не является простым терминалом SSH, в который весь Jenkins печатает строки. Поэтому произвольный SSH-вход на машину и здоровый канал Jenkins — разные проверки.

После шага sh агент запускает оболочку с рабочим каталогом и окружением. Оболочка создаёт Python-процесс. Его стандартный вывод и код завершения наблюдаются инфраструктурой шага. Поддержка долговременной задачи оставляет служебное состояние на стороне агента, чтобы контроллер мог продолжать наблюдение после некоторых перезапусков. Копирование большого результата, поток журнала и сообщения управления разделяют транспортные и вычислительные ресурсы; огромный вывод способен стать заметной статьёй нагрузки.

Передача файла не означает перенос семантики среды. Архив Python с исходниками можно доставить на другой агент, но установленное виртуальное окружение с абсолютными путями и бинарными расширениями не обязано заработать на другой платформе. То же относится к правам файлов, архитектуре и внешним сокетам. Выходные данные передают по определённому контракту; нужные инструменты предоставляют целевой среде отдельно.

Какие каталоги принадлежат агенту

Удалённый корневой каталог узла используется Jenkins для размещения рабочих данных; внутренняя папка Remoting содержит собственные кэши и журналы. В пределах узла Jenkins выделяет workspace задания. При конкуренции могут появляться варианты имени с суффиксом, поэтому жёстко записывать привычный абсолютный путь в сценарий ненадёжно. Пользуйтесь текущим каталогом шага и предусмотренными механизмами dir или ws.

Два исполнителя на одном агенте обычно работают под одной учётной записью ОС. Разные workspace защищают от случайного совпадения относительных путей, но не запрещают процессу читать соседние каталоги доступного пользователя. Для недоверенных проектов требуется более сильная изоляция: отдельные учётные записи, машины или управляемые временные среды с ограниченными правами. Наш домашний контроллер и агент под одним пользователем учат протоколу, но не являются защитной виртуальной машиной.

Жизненный цикл агента определяет, что останется после выполнения. Постоянный узел сохраняет кэши и может ускорять повторный запуск, но также сохраняет случайные остатки. Одноразовый узел уменьшает зависимость от прошлого состояния, если его создание действительно задаёт все нужные входы. Ни один выбор не заменяет сохранение артефактов вне временного workspace.

Что означает «агент отключился»

Обрыв канала лишает контроллер возможности надёжно наблюдать удалённую сторону. Он не доказывает, что ядро ОС уже завершило дочерний процесс, и не отменяет выполненный сетевой запрос. Процесс мог продолжать писать файл; команда могла завершиться, а сообщение об успехе потерялось. Поэтому перед повтором действия нужно определить, допустим ли повтор и как проверить уже существующий результат.

Некоторые шаги способны дождаться восстановления соединения и продолжить наблюдение, если агент и его служебные файлы сохранились. Если временная машина уничтожена или её каталог потерян, ожидание не вернёт данные. Поведение зависит от шага, конфигурации и вида отказа. Практическая проверка должна отдельно моделировать короткую потерю связи, перезапуск контроллера и потерю агента; это три разных утверждения о восстановлении.

При диагностике сначала смотрят журнал запуска агента и точную причину отключения. Далее проверяют совместимость Java, правильность URL и имени, секрет, TLS и прокси. Если соединение установлено, но агент регулярно теряется под нагрузкой, сопоставляют время обрыва с GC, загрузкой диска, памятью и сетевыми таймаутами. Увеличение всех таймаутов без такой связи лишь удлиняет ожидание реального отказа.

Проверяем среду командой, а не названием узла

Первое задание на новом агенте должно вывести безопасные сведения: имя узла Jenkins, рабочий каталог, версии Git и Python, создать и прочитать небольшой временный файл, завершиться и сохранить контрольный результат. Не выводите всё окружение: там могут оказаться credentials. Затем выполните отрицательный опыт — задайте несуществующую метку и убедитесь, что команда не начала работу на случайном узле.

После корректного подключения измеряют отдельно время выделения, подготовки workspace, исполнения и передачи результатов. Если маленькая Python-команда работает быстро, но архивирование большого файла занимает минуты, искать нужно канал и хранилище. Если узел онлайн, но нет свободного подходящего слота, это очередь. Такая послойная диагностика превращает надпись Offline из загадки в конкретную проверяемую цепочку.

Почему команда вручную работает, а на агенте нет

Интерактивный терминал может читать профиль пользователя, где добавлен Go в PATH. Агентская JVM, запущенная раньше, получила свою копию окружения и не узнает о последующем export. Jenkins может также запускать неинтерактивную оболочку без тех же файлов инициализации. Поэтому начните с фактического поиска программы и вывода go version именно в шаге задания, затем сравните с терминалом. Установка второй случайной копии Go усложнит расхождение.

Похожая ситуация возникает с файлами: относительный путь SOURCE_REPO может работать при ручном запуске из домашней папки, а на агенте разрешиться от workspace. Локальная лаборатория требует явного абсолютного пути к собственному репозиторию и проверяет его наличие. Удалённый агент на другой машине не увидит домашнюю файловую систему контроллера по совпадающей строке пути. Для него нужен сетевой SCM или отдельно организованная доставка.

Сравните также пользователя ОС, права на каталог, кодировку вывода и целевую архитектуру. Собранный для Linux amd64 файл может существовать и иметь верный хеш, но не запускаться нативно на ARM. Это не повреждение Remoting. Успешная связь подтверждает канал управления, а применимость команды подтверждается контрактом среды.

Завершает настройку небольшой опыт повторного подключения: штатно остановите учебный агент, увидьте очередь, затем верните его с теми же именем, секретом и workDir. Проверьте, что задание получило ожидаемый узел и нужный Go. Не расширяйте результат этого опыта до потери диска или аварии питания: сохранность каталогов была существенным условием.

Секрет inbound-узла связан с его именем и контроллером. Простое удаление регистрации и создание такого же имени не следует считать гарантированным отзывом скомпрометированного значения: документация Remoting описывает устойчивую связь секрета. При реальной утечке нужен предусмотренный способ замены и новое доверенное подключение; сохранённый старый файл не должен продолжать давать неожиданный доступ. В учебном опыте секрет хранится только в своей закрытой папке.

Официальные источники

Назначение Remoting; Inbound, WebSocket и аргументы из файла; Внутренний workDir Remoting; Узлы, метки и исполнители; Порты и транспорты; Границы контроллера и агентов. Локальный запуск демонстрирует управление, а не изоляцию недоверенного кода.
