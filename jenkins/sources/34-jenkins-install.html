Устанавливаем Jenkins осмысленно: JVM, WAR, адреса и первый запуск

Разберём, что именно начинает работать после команды Java, где появляется состояние сервера и почему правильный порт ещё не означает готовность сборочной системы. Учебный вариант живёт в отдельном каталоге домашнего Linux и доступен только с этого компьютера.

Из каких программ складывается установка

Jenkins — Java-приложение, которому нужна совместимая виртуальная машина Java, JVM. Она загружает классы, исполняет байтовый код, управляет памятью и потоками. WAR — архив веб-приложения; официальная самостоятельная поставка Jenkins включает оболочку Winstone и серверный контейнер Jetty. Поэтому отдельный Apache Tomcat для выбранного способа не требуется. Браузер обращается по HTTP к слушающему сокету этого процесса, контейнер принимает запрос, а код Jenkins проверяет пользователя и выполняет обработчик.

Для зафиксированного здесь LTS Jenkins 2.580.2 подходят Java 21 и 25 согласно проверенной политике поддержки. LTS означает ветку с длительным сопровождением, а не обещание вечной совместимости плагинов. Java 17 для этой поставки уже не поддерживается. Требования Java относятся и к контроллеру, и к агентам. Приложение, которое они собирают, может использовать другую целевую версию через отдельно выбранный инструмент; JVM управления Jenkins и компилятор проекта не обязаны совпадать.

Пакет операционной системы обычно добавляет служебного пользователя, сервис, каталоги и интеграцию с журналом. Самостоятельный WAR оставляет эти решения человеку: запуск из терминала, переменная каталога состояния, явные адрес и порт. Это удобно для обратимого опыта, потому что не требуется менять службы компьютера. Однако слово «самостоятельный» относится к запуску веб-приложения, а не к полноте среды сборки: Git, Go, агенты и плагины для Pipeline нужно подготовить отдельно.

Получение дистрибутива и проверка выбранного выпуска

Установка начинается с выбора конкретного выпуска и способа его получения. Для повторяемого опыта нужен адрес с номером версии, а не ссылка, которая завтра укажет на другой файл. Официальный адрес WAR этой лаборатории: https://get.jenkins.io/war-stable/2.580.2/jenkins.war. Узел загрузки может перенаправить на зеркало. Такое перенаправление является частью доставки; после неё всё равно проверяется полный SHA-256 относительно заранее одобренного значения.

curl --fail --location --show-error \
  --output "$JENKINS_LAB_ROOT/downloads/jenkins-2.580.2.war" \
  https://get.jenkins.io/war-stable/2.580.2/jenkins.war

Команда относится к предварительной подготовке при наличии сети. --fail превращает ошибочный HTTP-статус в неуспех команды, --location разрешает предусмотренное перенаправление, --show-error сохраняет диагностику, --output задаёт имя файла. Каталог должен существовать. Скачанный HTML с сообщением прокси не становится WAR от правильного расширения. При обрыве или сомнительном результате повторяют получение и полную проверку, не продолжают установку по одному существованию пути.

Launcher лаборатории сравнивает SHA-256 с зафиксированным d98032d2401c540a35613a82ed358921fcf3166d5e6eaaaf60a7941845be3251. Контрольная сумма подтверждает равенство ожидаемым байтам. Доверие к ожидаемому значению устанавливается отдельно через официальный источник и сохранённое описание поставки. Если неизвестный источник одновременно дал файл и его новый хеш, соответствие между ними не доказывает происхождение. В автономной работе сохраните и проверенный файл, и безопасное описание версии.

Сам по себе WAR не содержит установленную Java. Поэтому сначала выполняют java -version и сравнивают результат с поддержкой выбранного Jenkins. Если хочется пользоваться jcmd и другими диагностическими программами, удобен полный JDK, а не только минимальная среда исполнения. Это выбор инструментов самой платформы; разработка Go-приложения не требует изучить Java-сборщик Maven.

Что подготовить на домашнем Ubuntu 24

Для нашего переносимого каталога достаточно совместимой Java, Git, Go, Python и Bash. Если Java отсутствует, на собственном Ubuntu с административными правами можно подготовить её пакетами ОС: sudo apt update, затем sudo apt install fontconfig openjdk-21-jdk. Первая команда обновляет локальные сведения репозиториев, вторая устанавливает выбранные пакеты и необходимые зависимости; sudo выполняет административное действие. Установка JDK даёт также диагностические инструменты. Эти команды меняют домашний компьютер и не входят в режим чтения с флэшки на рабочем Windows.

Если программы уже установлены, не требуется переустанавливать их ради книги. Проверьте фактический путь поиска и версии в терминале контроллера и отдельно агента. Go можно иметь в отдельном пользовательском каталоге и добавить его bin в окружение запуска агента. Переменная в одном открытом терминале не меняет окружение уже работающего Java-процесса: после такой подготовки агент запускают с нужным PATH.

Нужен и дисковый запас: WAR, распакованные ресурсы, плагины, их зависимости, история и кэш компиляции существуют одновременно. Размер самого исходного Go-проекта почти ничего не говорит о полном расходе. Перед первым опытом выберите отдельное место с понятным владельцем, а после нескольких запусков измерьте, какие каталоги растут. Одного свободного гигабайта «по минимальным требованиям» недостаточно считать гарантией удобной долговременной работы.

Есть другой способ — постоянный пакет Jenkins из официального Debian-stable-репозитория. Он создаёт служебного пользователя и интеграцию systemd. Подпись репозитория и ключ настраивают по актуальной официальной инструкции; в проверенной на дату книги инструкции используется ключ 2026 года. Старые команды с истёкшим ключом могут перестать работать. Для первого экономного опыта эта установка не обязательна: выбранный WAR запускается явно и не добавляет автозагрузку службы.

Командная строка имеет две границы разбора

JENKINS_HOME="$JENKINS_LAB_ROOT/controller-home" \
java -Xms128m -Xmx512m -Djava.awt.headless=true \
  -jar "$JENKINS_LAB_ROOT/downloads/jenkins-2.580.2.war" \
  --httpListenAddress=127.0.0.1 --httpPort=18080 \
  --webroot="$JENKINS_LAB_ROOT/controller-war"

Переменная JENKINS_LAB_ROOT должна заранее обозначать отдельный учебный каталог. Присваивание JENKINS_HOME=... перед командой передаёт выбранное значение этому процессу. Это не изменение домашнего каталога пользователя. До -jar расположены параметры JVM: -Xms128m задаёт начальный размер управляемой кучи, -Xmx512m — максимальный; -Djava.awt.headless=true задаёт системное свойство Java для работы без графического устройства. -jar выбирает исполняемый архив.

После имени WAR идут параметры серверного приложения. --httpListenAddress=127.0.0.1 ограничивает привязку петлевым адресом IPv4; --httpPort=18080 выбирает непривилегированный TCP-порт. --webroot указывает каталог развёрнутых ресурсов WAR. Он отличается от JENKINS_HOME: веб-ресурсы можно повторно развернуть из дистрибутива, а в домашнем каталоге Jenkins находятся задания, пользователи и секреты. Перестановка аргументов через границу -jar меняет того, кто их разбирает.

512 MiB — учебный предел Java-кучи для небольшого опыта, а не предел всей памяти процесса. Дополнительно нужны метаданные классов, стеки потоков, буферы, машинный код JVM и память системных библиотек. Агент и Python-процессы живут отдельно. Поэтому на компьютере с 8 GiB нельзя вычесть только 512 MiB и считать остальное свободным для сборок. Расход проверяют по процессам и общей памяти ОС; рост числа плагинов меняет базовую стоимость контроллера.

Адрес, порт и публичный URL отвечают на разные вопросы

ЗначениеГде используетсяНаблюдаемое следствие
Адрес привязкиОС при создании слушающего сокетаНа каких интерфейсах принимаются соединения
TCP-портТранспорт при доставке к процессуКакой слушатель получает соединение
Jenkins URLЛогика Jenkins, ссылки, интеграцииКакие адреса выдаются пользователю и агентам
Префикс путиHTTP-маршрутизацияНачинаются ли пути, например, с /jenkins

Изменение --httpPort не переписывает автоматически Jenkins URL в настройках. Если браузер открыл новый порт, а письма или сведения агенту содержат старый адрес, нужно проверить именно URL сервера. В учебной схеме он равен http://127.0.0.1:18080/. localhost способен разрешаться и в IPv6, поэтому при привязке только к IPv4 для первого опыта удобнее указать явный 127.0.0.1.

Обратный прокси принимает внешний запрос и передаёт его Jenkins. Тогда внешний HTTPS-адрес и внутренний HTTP-порт могут различаться. Прокси должен согласованно передавать схему, имя узла, путь и заголовки, а для WebSocket — поддерживать обновление соединения. Случайное переписывание только части путей приводит к работающей стартовой странице и сломанным перенаправлениям или агентам. Для локального стенда прокси не нужен; вводить его стоит, когда понятны обе стороны соединения.

Конкретный разбор адреса за прокси

Представим собственную тестовую публикацию https://ci.example.invalid/jenkins/; домен здесь намеренно показательный. Браузер устанавливает TLS с прокси на порту 443, а прокси обращается к http://127.0.0.1:18080/jenkins/. Jenkins запущен с --prefix=/jenkins, и его настроенный Jenkins URL содержит внешний HTTPS-адрес с тем же префиксом. Это три согласованных факта: место приёма внешнего соединения, внутренний маршрут и адрес, который приложение сообщает обратно.

Запрос страницы задания приходит извне как /jenkins/job/demo/. Если прокси удалит /jenkins, а сервер ожидает этот префикс, внутренний обработчик может не найти путь. Если страница открылась, но ответ перенаправляет браузер на внутренний HTTP-адрес, проверьте внешний URL и передаваемые сведения о схеме и узле. Cookie с неправильной областью пути может создать видимость, что пользователь постоянно теряет вход. Это ошибки согласования HTTP-контекста, а не причина менять пароль администратора.

WebSocket добавляет долгоживущее соединение с предусмотренным обновлением протокола. Прокси, который прекрасно обслуживает короткие страницы, способен не пропустить нужные заголовки либо разрывать соединение по таймауту. Поэтому после настройки проверяют не только стартовую страницу, но и вход, перенаправления, ресурсы, URL задания и реальное подключение агента. Точный конфигурационный синтаксис берут из официального раздела для своего прокси, учитывая TLS и выбранный путь.

Пока внешняя публикация не нужна, сохраните петлевую привязку домашнего опыта и прямой URL. Изучение прокси можно выполнить отдельным следующим упражнением с понятной исходной точкой. Изменение адреса слушателя, URL, пути и сертификата одновременно затрудняет локализацию: при отказе неизвестно, какое отношение нарушено. Сначала фиксируют работающий прямой маршрут, затем добавляют один промежуточный слой и сравнивают запрос и ответ.

Что происходит до готового интерфейса

JVM проверяет возможность загрузить классы, сервер разворачивает ресурсы, Jenkins определяет домашний каталог и начинает инициализацию. Загружаются конфигурация, пользователи, плагины, узлы и задания; плагины добавляют расширения и могут читать собственные данные. Открытый TCP-порт появляется не обязательно в тот же момент, когда все эти действия завершились. При запуске браузер может видеть страницу ожидания. Повторять запуск второй JVM в надежде «ускорить» первую нельзя: две копии не должны одновременно управлять одним состоянием.

Первый запуск нового каталога включает мастер настройки. Начальный пароль сохраняется в secrets/initialAdminPassword внутри выбранного дома Jenkins и может выводиться в журнал. Это локальный секрет разблокировки, а не пароль для публикации в книге. После разблокировки создают собственную учебную учётную запись, сохраняют контроль доступа и выбирают плагины. Не отключайте аутентификацию для удобства лаборатории: петлевой интерфейс ограничивает сеть, но не превращает любой локальный процесс в доверенного пользователя.

Установка предложенного набора плагинов требует сети и может добавить много компонентов. Для автономного опыта нужно заранее подготовить фактически используемый набор с зависимостями. Сообщение «плагин установлен» ещё не всегда означает, что новая функциональность загружена без перезапуска. После завершения проверяют состояние компонентов и доступность нужного типа задания. Один WAR предоставляет основу сервера, но сам по себе не обещает наличие Declarative Pipeline, JUnit и интеграций с серверами Git.

Мастер первоначальной настройки по шагам

На странице Unlock Jenkins введите начальный пароль именно из выбранного controller-home. Если запусков несколько, пароль другого экземпляра не подойдёт. Далее выберите осмысленный набор плагинов: рекомендуемый набор удобен для общего знакомства, а выборочный лучше показывает зависимости нашего малого стенда. Откройте информацию о каждом главном компоненте; число отмеченных вами пунктов может быть меньше итогового числа устанавливаемых зависимостей.

Если загрузка плагина отказала, сохраните название, требуемую версию и ошибку. Не переходите к вставке Jenkinsfile в надежде, что отсутствующий шаг появится сам. Можно закончить базовую настройку и подготовить компоненты через менеджер позже, но до первого Pipeline надо подтвердить активный состав. Ошибки сети, сертификата и требования к версии ядра имеют разные решения. Повтор установки без чтения причины способен лишь повторить тот же отказ.

На шаге создания пользователя задайте собственные учебные имя и пароль. Используйте отдельную учётную запись, чтобы не зависеть от одноразового значения разблокировки. Затем настройте Jenkins URL и сохраните результат. Если интерфейс предлагает перезапуск для завершения установки, выполните его и дождитесь повторной готовности. Проверьте вход заново; заполненная форма до остановки ещё не подтверждает, что настройки корректно прочитаны при старте.

Первичная настройка доступа сразу после мастера

В разделе Security проверьте security realm и authorization strategy. Security realm — источник учётных записей и способ установить личность вошедшего. Authorization strategy — правила, какие действия этой личности разрешены над заданиями и настройками. Для одного домашнего владельца подходит встроенная база пользователей и понятная стратегия, оставляющая управление только вошедшему пользователю. Не включайте свободную регистрацию посторонних. В рабочей общей системе роли и права разделяются подробнее; это развивается в главе о доверии, но первоначальная установка уже должна иметь известного владельца и запрещать анонимное администрирование.

Откройте приватное окно браузера и проверьте, что без своей сессии нельзя изменить конфигурацию или запустить произвольную команду. Основное окно оставьте открытым, пока убеждаетесь в правильности настройки, чтобы не потерять рабочий путь управления из-за опечатки. Это проверка созданной стратегии, а не просьба ослабить её. Сохраните свои учётные данные отдельно от публичного материала.

CSRF-защиту оставляют включённой. Она использует маркер crumb для применимых изменяющих запросов и защищает действие от использования браузерной сессии чужой страницей. Отказ crumb позднее диагностируют по сессии и способу аутентификации клиента; отключение общей защиты не является необходимым этапом установки. Отдельный inbound TCP-порт также остаётся отключённым в нашем WebSocket-маршруте.

После этого в Nodes настройте встроенному узлу ноль executor. До подключения отдельного агента задание, которому нужен узел, будет ждать — это ожидаемое состояние. Не возвращайте сборки на контроллер только ради зелёного первого примера. Следующий этап состоит в подготовке и аутентификации агента с явными инструментами; его локальный процесс не должен случайно получить другой Go или другой домашний каталог.

Если Jenkins работает как системная служба

В пакетном варианте сначала исследуют systemctl cat jenkins: команда показывает основной unit и дополнения. Для изменения используют systemctl edit jenkins, создающий drop-in-конфигурацию, а не правку поставляемого файлом пакета описания. В секции [Service] могут задаваться JAVA_OPTS, параметры Jenkins и путь состояния. При последующем обновлении пакета такое дополнение сохраняется отдельно от основной поставки.

Окружение интерактивного терминала не обязано совпадать с окружением службы. Установленный под личным пользователем Go не станет доступным служебному пользователю автоматически. Команды systemctl status jenkins и journalctl -u jenkins.service показывают соответственно состояние службы и её журнал; -u выбирает unit. У ручного WAR эти источники другие. Выберите один способ управления экземпляром, чтобы случайно не запустить второй сервер с тем же портом или каталогом.

Как отличить ошибки запуска

Ошибка несовместимой версии класса указывает на цепочку Java и загружаемого компонента. Сначала проверяют java -version в том же терминале, из которого стартует сервер; -version выводит используемую JVM и завершает команду. Не следует судить о ней по когда-то установленному пакету: поиск по PATH мог выбрать другую программу. Для агента версию проверяют отдельно на его машине.

Ошибка привязки порта означает, что процесс не смог открыть нужный локальный слушатель. Возможные причины — занятый адрес и порт, отсутствие указанного адреса либо недостаточные права для привилегированного порта. Это происходит до пользовательского HTTP-запроса. Если сокет слушает, но браузер получает отказ или перенаправление, исследуют уже маршрут, HTTP, аутентификацию и URL. Если UI отвечает, но сборка ждёт, переходят к агентам и очереди: это следующий слой.

При недостатке прав на домашний каталог будут ошибки создания или чтения файлов. Запускать весь Jenkins от root ради устранения такой ошибки неправильно: сначала определяют владельца отдельного каталога и нужного пользователя процесса. Если вместо прежних заданий снова появился мастер первоначальной настройки, прежде всего сравните фактический JENKINS_HOME. Смена каталога часто выглядит как потеря данных, хотя старое состояние осталось в другом месте.

Первый проверяемый результат установки

Для учебной установки зафиксируйте версию WAR, его проверенный SHA-256, версию Java, полный путь к состоянию, адрес привязки, порт и набор плагинов. Затем подтвердите, что вход под своей учётной записью работает, а анонимный пользователь не получает управление. Встроенному узлу контроллера назначьте ноль исполнителей и подключите отдельный агент; до подключения ожидающая сборка должна оставаться в очереди. Этот результат важнее просто открывшегося логотипа.

Останавливайте стенд штатным завершением процесса после окончания нужных запусков. При следующем старте используйте тот же домашний каталог: задания и история сохранятся. Новый каталог означает новый экземпляр, даже если WAR, порт и имя окна совпадают. Пошаговая лаборатория в конце книги показывает именно такой повторяемый запуск, затем проверяет очередь, неудачную сборку, артефакты и продолжение Pipeline после перезапуска.

Перед первым отключением сети завершите полный путь до маленькой сборки, затем штатно перезапустите тот же каталог. Так выявляются незавершённая установка, забытый плагин и зависимость от окружения прежнего терминала. Сохранённый файл WAR и открытая страница сами по себе этот путь не подтверждают.

Проверенный повторный запуск связывает установку, выбранный каталог и фактическое сохранение первичной настройки в одну наблюдаемую процедуру.
