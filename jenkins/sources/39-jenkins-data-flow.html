Данные конвейера: параметры, окружение, секреты, файлы и отчёты

Разберём, по каким каналам информация проходит между пользователем, контроллером и агентами. У каждого канала собственные правила подстановки, срок жизни и способ проверки; смешение этих правил создаёт ложные результаты и утечки.

Параметр запуска становится входом сборки

Параметры позволяют выбрать разрешённый режим, версию или назначение запуска. Значения доступны управляющему коду через params, а применимые параметры могут передаваться процессам через окружение. Но строка от пользователя не является автоматически проверенной командой. Сначала определяют допустимый смысл: имя режима из короткого списка, идентификатор объекта, логическое значение. Затем проверяют его и только после этого используют как аргумент конкретного инструмента.

Если одна сборка получает MODE=debug, а другая MODE=release, это два набора входов, даже при одинаковом коммите. Значимый режим следует сохранять в описании происхождения и включать в ключ кэша затронутого действия. Иначе можно получить выпускной файл из результата отладки. Параметры, не влияющие на байты, тоже могут влиять на процедуру допуска: выбор окружения доставки не должен случайно обходить обязательную проверку.

Тип выбора в интерфейсе удобнее свободного текста, когда вариантов действительно мало. Но считать интерфейс единственным барьером не следует: API и изменение конфигурации создают другие пути. Проверяемое правило должно существовать там, где значение принимается для действия. Пароль не следует передавать как обычный текстовый параметр; для секретов предусмотрено отдельное хранилище и ограниченная область связывания.

Окружение процесса — копия, а не общая память

Когда Jenkins запускает оболочку, она получает набор переменных окружения. Дочерняя Python-программа наследует их; её изменения не переписывают окружение родительской JVM. Аналогично export внутри одного шага sh не гарантирует сохранение значения в следующем отдельном шаге. Для передачи между шагами используют предусмотренную область environment, withEnv, управляющее значение или явный файл. Нужно выбрать один контракт, а не надеяться на продолжение той же интерактивной оболочки.

withEnv(['REPORT_MODE=compact']) {
    sh 'python3 tools/report.py'
}

В этом фрагменте предполагается собственная программа report.py, которая читает REPORT_MODE; в шаблоне лаборатории её нет. withEnv задаёт окружение для вложенных шагов. Он не меняет системный профиль пользователя и не устанавливает программу. Подобные переменные документируют вместе с интерфейсом проекта: ожидаемые значения, значение по умолчанию и поведение при ошибке.

Весь набор окружения не следует печатать ради диагностики. Лучше вывести конкретные безопасные значения: режим, версию Python, относительный путь и идентификатор коммита. Значение PATH объясняет поиск программ, но может содержать внутренние пути. Локаль и режим кодировки влияют на чтение текста; для бинарного архива берут байтовые операции. Каждая такая настройка является частью среды, которую требуется объяснить при расхождении результатов.

У строки может быть несколько интерпретаторов

Текст в Jenkinsfile сначала разбирает Groovy, затем при вызове sh его разбирает оболочка, а аргументы получает Python или другая программа. Подстановка Groovy и подстановка оболочки — разные события. Сборка строки команды из непроверенного значения способна изменить структуру команды ещё до запуска ожидаемого инструмента. Правильное заключение в кавычки на одном уровне не исправляет произвольную интерпретацию на другом.

Для секретов обычно передают буквальный сценарий в одинарных кавычках Groovy и позволяют оболочке читать заданную переменную окружения. Для пользовательского режима лучше заранее ограничить набор значений и передать значение как один процитированный аргумент. Но и один аргумент может быть опасен, если целевой инструмент принимает его за опцию. Разделитель --, когда он поддерживается конкретной программой, отделяет параметры от имён. Его нельзя считать универсальной командой всех утилит.

Есть и менее опасная, но частая ошибка: последовательность \n в многострочной строке Groovy может превратиться в перевод строки до передачи вложенному Python-коду. Поэтому пример проверки комплекта в этой книге использует chr(10) для ожидаемого LF. Смысл не в необычном предпочтении записи, а в явном прохождении через два языка. При ошибке синтаксиса исследуют реально переданный сценарий без секретов и определяют, на каком уровне текст изменился.

Credentials связывают секрет с узкой областью

Запись credentials имеет тип и идентификатор: секретный текст, имя и пароль, закрытый ключ или секретный файл. Шаг связывания выбирает подходящий обработчик и предоставляет значение вложенной операции. Идентификатор записи не является самим секретом. Доступ определяется областью хранилища, контекстом задания и правами; наличие ID в файле не означает, что любой проект вправе получить значение.

Область связывания желательно делать короткой: получить токен только на время запроса публикации, а не на весь тестовый конвейер. Тогда меньше дочерних процессов получают секрет и меньше возможностей случайно его вывести. Маскирование журнала — дополнительная мера, но не механизм изоляции: программа с доступом к токену может его преобразовать, записать в файл или отправить наружу. Поэтому недоверенный исходник не должен исполняться в контексте выпуска с такими правами.

Секретный файл обычно материализуется как временный файл, путь к которому получает шаг. Нельзя случайно переместить его в область, доступную через просмотр workspace или архивируемую маску. Особенно внимательно изучают вложенность dir и связывания. После завершения проверяют, какие файлы остались и что реально сохранено. Зашифрованное хранение на контроллере и безопасное использование на агенте являются разными задачами.

stash переносит файлы, а не среду исполнения

stash сохраняет выбранные файлы под именем для дальнейших участков того же запуска; unstash восстанавливает их в текущий workspace. Это мост между агентами или стадиями. Сохраняют явную маску и решают, допустим ли пустой результат. Восстановление в непустой каталог может смешать новые файлы со старыми, поэтому получателю полезен заранее определённый чистый каталог.

stash name: 'prepared-source', includes: 'generated/*.json', allowEmpty: false
// На другом выделенном агенте:
dir('incoming') {
    deleteDir()
    unstash 'prepared-source'
}

Это самостоятельная схема обмена, не команда нашего двухфайлового шаблона. includes выбирает файлы относительно текущего workspace, allowEmpty: false не разрешает молча сохранить отсутствие ожидаемого выхода. Вложенный deleteDir очищает именно incoming. Stash не переносит работающую базу, открытый TCP-сеанс и содержимое памяти Python. Для больших данных оценивают упаковку, передачу и используемый менеджер хранения: бесконечное число крупных stash способно сделать контроллер узким местом.

Артефакт и отчёт имеют разных потребителей

archiveArtifacts сохраняет выбранные выходные файлы для обращения после завершения запуска. Это не публикация сервиса и не доказательство прохождения тестов. Маска выбирает существующие пути, а отдельная проверка устанавливает, что состав правильный. Если перечислены три шаблона, запрет полностью пустого результата сам по себе не требует присутствия каждого из трёх файлов. Поэтому наш конвейер сначала читает и проверяет весь комплект, затем архивирует его.

JUnit XML предназначен для потребителя тестовых результатов. Jenkins JUnit plugin читает случаи и ошибки, строит историю и может отметить запуск как UNSTABLE. Генератор отчёта должен действительно выполнить тесты и корректно завершиться; наличие XML не заменяет этот факт. Стандартный unittest Python не выдаёт JUnit XML сам по себе, поэтому основной стенд использует честный код завершения и журнал без выдуманного отчёта.

Неуспешные тесты, синтаксическая ошибка JSON и недоступность хранилища артефактов требуют разных диагнозов. Стадия может закончить вычисление успешно, но не сохранить результат. Выпуск, которому нужен сохранённый файл, в таком случае не готов. Принятие результата должно быть привязано к завершению всех нужных действий, а не только к последней строке тестового вывода.

Прослеживаем один комплект до потребителя

Главный Go-сборщик сохраняет бинарный файл и JSON-манифест: размер, полный SHA-256, версию приложения, фактический Go, флаги, цель, исходный коммит, чистоту дерева и хеш самого сценария. При -buildvcs=false происхождение намеренно находится снаружи. Новый пустой коммит способен изменить внешний source_revision без изменения бинарных байтов. Поэтому одинаковый продукт и одинаковая история сборки — разные утверждения.

Проверка комплекта сравнивает манифест с самим файлом и текущим снимком. Она должна отказать при повреждённом бинарнике, неверной версии, другом инструменте или изменённой рабочей копии. Валидатор не просто красиво форматирует JSON. Ошибка разбора JSON тоже означает, что обязательные метаданные не приняты; копирование такого файла в архив не исправляет контракт.

После передачи сохранённого комплекта другой стороне она получает ожидаемый полный хеш по доверенному каналу и сверяет файл. Для запуска нужны подходящий Python и известная конфигурация. Наименование задания или зелёный цвет не заменяют эту проверку идентичности. Так параметры, окружение, файлы и отчёты образуют одну прослеживаемую цепочку, у которой можно независимо исследовать каждый переход.

Проверка потока данных через намеренную подмену

Возьмите завершённый учебный комплект и отдельно измените один байт бинарного файла, не меняя манифест. Проверка полного SHA-256 должна отказать. Затем восстановите файл и измените в JSON только source_revision: должна отказать проверка происхождения. Третий опыт — новый исходный коммит без пересборки: совпадение старого бинарного хеша не разрешает выдавать старый манифест за запись нового запуска. Эти случаи исследуют разные связи.

Если одновременно заменить файл и его объявленный хеш, внутренняя проверка равенства пройдёт. Для ответа на вопрос о доверии нужен ожидаемый идентификатор из утверждённой записи и проверяемая процедура сборки. Поэтому хеш, подпись и код завершения нельзя употреблять как синонимы. Каждый из них наблюдает определённое отношение, а полная процедура связывает эти отношения.

Файлы отчётов тоже требуют происхождения. Старая папка reports, оставшаяся в workspace, способна дать историю тестов, которые сейчас не выполнялись. Очистка в начале и явное создание обязательного результата уменьшают риск. Маска архивирования должна выбирать продукт текущего запуска, а не любой подходящий файл с прошлого раза. Сохранение нужного результата заканчивается только после подтверждения хранилища.

Для передачи между томами и упражнениями сохраняйте простые контракты: UTF-8 JSON с версией формата, имена разрешённых файлов, полные хеши, понятные коды ошибок. Это позволяет исследовать выход обычными инструментами без живого сервера Jenkins. Изменение формата делают явно, чтобы старый потребитель отказал понятно, а не молча истолковал новые поля иначе.

При разборе манифеста проверяйте версию формата до использования полей. Имя выходного файла сопоставляют с разрешённым контрактом, а не безусловно используют произвольный путь из чужого JSON. Это превращает файл метаданных в явный интерфейс с определённым отказом, а не в источник неограниченных команд.
