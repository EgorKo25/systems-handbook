Multibranch и SCM: от изменения Git до правильного запуска

Изменение в репозитории должно привести к проверке определённого снимка с определённым уровнем доверия. Проследим обнаружение ветки, чтение Jenkinsfile, выбор ревизии, webhook, опрос и передачу статуса обратно серверу исходников.

Один репозиторий порождает несколько заданий

В обычном Pipeline администратор создаёт задание и задаёт источник программы управления. Multibranch Pipeline добавляет уровень обнаружения: он исследует настроенный источник SCM и создаёт дочерние задания для подходящих веток с Jenkinsfile. SCM означает систему управления исходниками. Родительский объект знает, где искать ветки и какие правила применять; дочерний объект хранит историю запусков конкретной обнаруженной сущности.

Индексирование — исследование источника для обновления этого набора. Оно может обнаружить новую ветку, изменение Jenkinsfile или исчезновение ранее существовавшей ветки. Индексирование и выполнение сборки являются разными действиями. Длинное время до появления задания может приходиться на API сервера Git, обход репозиториев и ограничения запросов, а вовсе не на ожидание executor для Go-компиляции.

Organization Folder расширяет идею до множества репозиториев организации. Он обнаруживает проекты, а внутри них — ветки и запросы изменений. Удобство автоматического создания повышает значение правил фильтрации и удаления: один новый репозиторий способен автоматически добавить много заданий, историю и сетевые запросы. Состав нужно наблюдать, особенно когда количество веток растёт быстрее числа исполнителей.

Подключаем первый собственный репозиторий

Для этого варианта уже нужен доступный по сети Git-сервер и собственный репозиторий службы, подготовленной в главе Jenkinsfile. На контроллере установлены Pipeline, Multibranch и Git plugin, а агент linux-go проверен с Git, Go и Python. На Git-сервере основная ветка называется main, в её корне закоммичен Jenkinsfile. Если пока есть только папка на диске, не включайте глобальный обход защиты: пройдите ручную локальную лабораторию, а сетевой источник добавьте позднее.

  1. В Jenkins выберите New Item, задайте отдельное имя go-service-multibranch и тип Multibranch Pipeline. Это родитель, не обычное задание Pipeline.
  2. В Branch Sources добавьте источник Git и URL именно своего учебного репозитория. Для закрытого источника заранее создайте запись credentials с доступом на чтение: для SSH это ключ и имя пользователя, для HTTPS — поддерживаемая сервером форма имени и токена. Здесь выбирается идентификатор записи; секрет в URL или Jenkinsfile не пишут. Контроллер должен обнаруживать ветки, агент — получать их содержимое.
  3. В Build Configuration оставьте получение Jenkinsfile из SCM и путь Jenkinsfile относительно корня репозитория. Для первой проверки ограничьте обнаружение веток ожидаемой main, если интерфейс источника предоставляет такой фильтр. Не подключайте секрет публикации к этому опыту.
  4. Сохраните настройку и запустите Scan Multibranch Pipeline Now. Сначала прочитайте журнал сканирования: обнаружен ли URL, видна ли ветка и найден ли файл. Затем откройте созданное дочернее задание main и его запуск.
  5. Сопоставьте фактический коммит в журнале получения исходников с коммитом сервера. На основной ветке после успешных стадий должны быть доступны два артефакта: бинарный файл и манифест. Если запуск ждёт метку linux-go, исправляют соответствие агента, а не возвращают исполнители контроллеру.

Названия отдельных полей меняются с локализацией и расширением источника, но созданные объекты остаются теми же: родитель → источник веток → дочернее задание → запуск. Обычный Git-источник обнаруживает ветки; специальное понимание запросов слияния и их доверия даёт соответствующий Branch Source. Если сканирование не прошло, ещё нет основания отлаживать go test: сохраните первую ошибку доступа, сертификата, URL или поиска файла и исправьте этот этап до следующего сканирования.

Имя ветки и идентичность снимка

Имя main — изменяемая ссылка. Пока задача ждала в очереди, оно могло переместиться. Поэтому важно знать, какая ревизия связана с конкретным событием и контекстом запуска. Встроенное checkout scm использует описание SCM текущего задания; оно помогает сохранить связь между выбранным Jenkinsfile и проверяемыми исходниками. Самодельное клонирование «самой свежей main» в начале каждого шага может нарушить эту связь.

Условия when { branch 'main' } опираются на контекст многоветочного задания. Переменная BRANCH_NAME обозначает обнаруженную ветку или соответствующую сущность в используемой интеграции. Она не является полным хешем коммита. Не следует присваивать BRANCH_NAME=main вручную ради получения выпускных прав: право доставки должно зависеть от доверенного контекста, а не от произвольной строки среды.

Для запроса изменения интеграция может собирать саму предложенную ревизию либо подготовленное слияние с целевой веткой. Во втором случае проверяется совместимость комбинации, но идентификатор результата отличается от исходного коммита автора. Сохраните фактический HEAD и сведения о режиме. Иначе статус «проверено» будет выглядеть относящимся к одним байтам, хотя тесты работали с другими.

Webhook сообщает событие, но ещё не исполняет код

Webhook — HTTP-уведомление, которое сервер исходников отправляет Jenkins при событии. Сначала источник формирует запрос, затем сеть и прокси доставляют его нужному обработчику, интеграция проверяет допустимость и определяет связанные задания. После этого может начаться индексирование или планирование запуска. Код Go начнёт исполняться позже на подходящем агенте. Успешная HTTP-доставка события не подтверждает успех всех следующих этапов.

Обработчик и способ проверки подлинности зависят от установленного плагина и поставщика SCM. Некоторые интеграции используют подписанное тело или общий секрет. Нельзя переносить имя заголовка из документации одного сервера Git на другой. Секрет webhook ограничивает приём ложных уведомлений, но не делает присланный исходник доверенным для выполнения с выпускными credentials. Это разные границы доверия.

При диагностике сохраните идентификатор доставки события, HTTP-результат, момент индексирования, номер очереди и фактическую ревизию запуска. Тогда видно, потерялось ли уведомление, не подошёл ли фильтр, возникла ли задержка API или просто ждёт агент. Проверка только последнего журнала сборки не поможет, если новая сборка вообще не была создана. Событие с повторной доставкой также должно обрабатываться по понятной политике, без неконтролируемого размножения внешних выпусков.

Опрос меняет направление инициативы

Polling означает, что Jenkins сам периодически исследует источник на изменения. Расписание задаёт частоту проверки, а не приказ безусловно пересобрать всё. Прямой плановый запуск по времени и опрос SCM различаются: первый создаёт работу независимо от изменения исходников, второй сначала ищет основание. На экране оба способны выглядеть как регулярные события, поэтому важно читать именно тип триггера.

Частый опрос сотен репозиториев создаёт запросы к SCM и нагрузку на контроллер. Условная частота раз в минуту для 600 источников может дать около 600 проверок в минуту до дополнительных запросов обнаружения. API поставщика может ограничивать интенсивность; тогда задержка будет расти при свободных агентах. Хешированный элемент расписания Jenkins распределяет моменты запусков по заданиям, но не уменьшает автоматически общее число запросов.

Webhook и периодическое исследование можно сочетать: уведомление уменьшает обычную задержку, а редкое сканирование помогает обнаружить пропущенное событие. Конкретную политику выбирают по доступности источника и цене проверки. В автономной локальной лаборатории внешнего сервера SCM нет, поэтому такие уведомления не имитируются фиктивным успехом; там сборку запускают вручную на локальном Git-снимке.

Чтение Jenkinsfile и получение всех исходников

Интеграция может получить Jenkinsfile через облегчённое чтение, не создавая полный рабочий каталог на агенте. Это уменьшает подготовительную работу, но зависит от возможностей SCM и настроек. Затем обычный checkout получает данные для сборки. Наличие прочитанного Jenkinsfile не доказывает, что весь репозиторий уже доступен в workspace или что его зависимости скачаны.

Нужно согласовать доверие к управляющему файлу и к исполняемым исходникам. Если внешний автор вправе менять Jenkinsfile и сразу получает доступ к токену публикации, он управляет командой, которой этот токен доступен. Даже если Jenkinsfile берётся из доверенной ветки, вызов непроверенного теста из предлагаемого изменения всё ещё исполняет чужой код на агенте. Защита должна охватывать оба пути.

Сканирующие credentials нужны контроллеру для обнаружения репозиториев и веток через API. Credentials получения исходников нужны для checkout. Выпускной токен нужен только для доставки утверждённого артефакта. Использовать один максимально привилегированный секрет для всех трёх ролей удобно лишь внешне: любая ошибка расширяет последствия. Разделите права и области видимости, затем проверьте, что непроверенное изменение не получает секрет, которого ему не требуется.

Локальный репозиторий требует отдельного решения

Git plugin ограничивает некоторые формы получения из локальных файловых путей, поскольку такая конфигурация на общем сервере способна дать доступ к данным самого контроллера. Глобальное включение ALLOW_LOCAL_CHECKOUT ради одной домашней демонстрации изменяет границу всего экземпляра. Наш локальный маршрут использует другой явный контракт: доверенный пользователь указывает собственный учебный репозиторий, а обычный Git на агенте копирует его через sh.

Это маршрут лаборатории с одним владельцем машины и без выпускных секретов, а не обход защиты для общего сервера. Он не исследует Multibranch и не притворяется сетевым checkout. Основная глава Jenkinsfile отдельно показывает checkout scm в настоящем многоветочном контексте. Различие сделано видимым, чтобы читатель не перенёс параметры учебного локального источника в чужую рабочую инфраструктуру.

Удаление ветки и история запусков

Когда ветка исчезает, родительский проект должен решить судьбу дочернего задания и его истории. Политика осиротевших элементов может удерживать историю ограниченное время или удалять её. Это касается и сохранённых внутри задания артефактов. Если единственная копия выпуска находится в истории временной ветки, удаление ветки способно неожиданно удалить путь к продукту. Утверждённые выпуски сохраняют по отдельной политике.

Внешний статус проверки также имеет срок актуальности. Новый коммит делает предыдущий успешный запуск свидетельством для старой ревизии. Изменение целевой ветки способно повлиять на проверку подготовленного слияния даже без изменения ветки автора. Поэтому принятие изменения должно связывать нужный режим проверки с конкретными актуальными входами, а не с последней зелёной записью по похожему имени.

Как убедиться, что автоматизация проверяет нужное

Создайте безвредное изменение в отдельной ветке и проследите всю цепочку: обнаружение, дочернее задание, запуск, фактический HEAD, результат теста и статус на SCM. Затем внесите намеренно падающий тест и убедитесь, что статус изменился именно у новой ревизии. После исправления сравните номера и хеши. Такой опыт проверяет причинную связь, которую обычный успешный запуск не показывает.

Дополнительно проверьте доверие: учебная ветка без выпускных полномочий не должна выполнять доставку, даже если пытается изменить параметры. Удаление ветки должно действовать по известной политике хранения. Потеря webhook должна диагностироваться по событиям, а не лечиться ручным повтором непонятного релиза. В результате многоветочная автоматизация становится объяснимой системой преобразования конкретных исходников, а не потоком случайных зелёных индикаторов.

Расхождение Jenkinsfile и собираемого кода

Рассмотрим типичную ошибку собственного checkout: событие относится к C1, Jenkinsfile прочитан из C1, задача долго ждёт, а shell-команда клонирует текущее имя main уже в C2. Тесты честно проходят на C2. Если статус отправлен по контексту исходного события, пользователь может принять успех за проверку C1. При этом ни сеть, ни Git, ни тестовый исполнитель не обязаны сообщить ошибку: нарушена связывающая договорённость автоматизации.

Исправление состоит в явном выборе и сохранении ревизии. Получаемый снимок должен соответствовать контексту, по которому будет принято решение. Сравнение фактического HEAD с ожидаемым значением обнаруживает подмену, а отчёт фиксирует её для расследования. Если интеграция намеренно проверяет подготовленное слияние, сохраняют и этот режим, и его реальный идентификатор. Нельзя ограничиться названием ветки в красивой строке журнала.

После изменения цели запроса пересмотрите и доверие. Ветка с похожим именем из внешнего репозитория не становится основной веткой вашей организации. Условия выпуска должны учитывать источник и политику интеграции. Пользовательский параметр, который позволяет подставить произвольный репозиторий, не должен наследовать выпускной токен только из-за совпадения строкового имени main.

Такой мысленный опыт удобно проверить на безвредной локальной модели двух указателей и затем на тестовой интеграции SCM. Он учит искать причинную связь между событием и байтами, а не только успешность каждой отдельной команды. Настоящие webhooks и внешние Branch Source в автономной лаборатории этой поставки не испытывались.

Подтверждение обработки webhook на стороне HTTP стоит хранить отдельно от итога задания. Источник мог получить успешный ответ, после которого запуск отклонён фильтром или ждёт ресурс. Повторная отправка уведомления в такой ситуации не ускоряет уже поставленную задачу и может добавить дубликат. Сначала найдите соответствующую запись события и ожидаемую ревизию.

Официальные источники

Multibranch и Organization Folder; Контекст веток Pipeline; Git plugin: получение, опрос и локальные пути; SCM credentials и доверие; Условия branch и триггеры. Возможности pull request зависят от конкретного Branch Source plugin; универсальный протокол его внутренних API здесь не выдуман.
