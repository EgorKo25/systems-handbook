Репозитории: учётные данные и доверие к стороне

Разрешённый URL, пароль и проверенный сертификат отвечают на разные вопросы.

Четыре независимые проверки

AppProject разрешает источник по правилам sourceRepos; repo-server должен установить соединение, удостоверить сервер и предъявить подходящие учётные данные. Затем он должен найти нужную ревизию и путь. «Репозиторий запрещён», «сертификат неизвестен», «отказ аутентификации» и «ревизия не существует» имеют разные причины. Отключение проверки TLS не исправляет неправильную политику проекта и лишает соединение удостоверенной стороны.

HTTPS проверяет цепочку сертификата и имя хоста; SSH проверяет ключ хоста через known_hosts. CA — удостоверяющий центр, подписывающий сертификат; добавлять следует доверенный корень или согласованную цепочку, а не случайный сертификат, скачанный через уже недоверенное соединение. SSH known_hosts содержит открытые ключи сервера, не закрытый ключ пользователя. Отпечаток проверяют через независимый доверенный канал до подключения.

Где хранятся секреты

Декларативная запись репозитория — Kubernetes Secret в пространстве Argo с меткой argocd.argoproj.io/secret-type=repository. Шаблон учётных данных repo-creds позволяет переиспользовать набор для префикса URL; выбирается наиболее специфичный подходящий префикс. Собственные учётные данные записи репозитория имеют значение: не рассчитывайте, что подходящий шаблон молча заменит их. Project-scoped запись ограничивается проектом, но Kubernetes Secret всё равно требует строгих прав чтения.

Base64 в поле data — кодирование, не шифрование. Токен в открытом Git или в командной строке может попасть в историю shell, журнал и список процессов. Учебные файлы содержат только фиктивный адрес и публичную политику; реальные ключи и пароли держат в private либо доставляют согласованным менеджером секретов. Экспорт управляющего контура тоже содержит эти данные и наследует тот же уровень конфиденциальности.

При ротации Git-токена проверьте новую запись с конкретной ревизией, затем убедитесь, что она используется серверным путём, и лишь потом отзывайте старую. Тёплый кэш манифестов может скрыть неработающий новый доступ. Проверка должна потребовать реального чтения нужного источника; один прежний Healthy этого не устанавливает. Отдельно сохраните время и результат отзыва. Значения Secret в журнал приёмки не включают.

Подключение собственного источника

Для публичного собственного HTTPS-репозитория достаточно URL и действующей цепочки TLS. Если Git-сервис требует окончание .git, укажите его явно: перенаправление, допустимое для браузера, не обязательно повторяется клиентом Argo. Для SSH в книге используется полный ssh:// URL, который однозначно разбирается подготовщиком. Адрес репозитория и полный коммит задаёт владелец своей рабочей копии; книга не создаёт внешних репозиториев и не делает push от его имени.

"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" \
  --argocd-context handbook repo list

argocd repo list показывает зарегистрированные записи и состояние соединения через сервер. argocd repo add добавляет запись; флаги --username/--password, --ssh-private-key-path и --type задают разные протоколы и содержимое. Не вставляйте пароль в публикуемый пример. --insecure-skip-server-verification убирает проверку сервера и не является обычным шагом этой книги. argocd cert add-tls и argocd cert add-ssh изменяют доверенные данные установки; сначала проверяют происхождение входного файла.

Секреты для образов — другая доставка

Пароль Git не используется kubelet для скачивания ledger-api. ImagePullSecret находится в целевом namespace и относится к реестру контейнеров; репозиторные учётные данные Argo относятся к получению исходников. Ошибка ImagePullBackOff при успешном рендеринге не исправляется повторным repo add. Для локального kind образ надо загрузить в тот же выбранный кластер на нужные узлы; для VM — обеспечить доступ к собственному реестру. Не меняйте тег 0.1.0 на иные байты без новой версии.

Зависимости и утечка полномочий

Helm passCredentials способен передавать учётные данные шире исходного домена при загрузке зависимостей; разрешайте это только после проверки всех получателей. Удалённая база Kustomize или dependency чарта может потребовать ещё один хост и отдельное доверие. Подпись Git-коммита удостоверяет автора в рамках доверенной политики, а не доступность образа и не безопасность ролей Kubernetes. Закреплённая SHA без проверки доверенного пути публикации решает лишь часть задачи.

Пользовательский генератор и встроенные инструменты обрабатывают данные репозитория на repo-server. Ограничивайте его права, сетевой доступ, файловую систему и источники; не передавайте привилегированные токены недоверенному плагину. Проектное ограничение destination не является песочницей исполнения исходного кода.

Команды и проверенные формы

Открываемая справка этой главы: argocd repo add, argocd repo list, argocd repo get, argocd repo rm. В карточках разобраны назначение, отдельные флаги, сочетания и предел доказательства. Полный путь в исполняемых блоках выбирает проверенную программу; каноническое имя здесь открывает ту же команду в справочнике.
