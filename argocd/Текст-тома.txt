Зачем нужен ещё один управляющий процесс

GitOps — подход, в котором описанное и версионируемое желаемое состояние хранится в источнике, обычно Git, а программный контроллер регулярно сравнивает его с фактом и выполняет разрешённые изменения. Git — журнал исходников и решений, а не контейнерный реестр и не резервная копия базы приложения. Argo CD, Continuous Delivery — непрерывная доставка, реализует такой контур для Kubernetes. Он получает описание из Git, превращает его в манифесты, сравнивает с API и по политике синхронизирует ресурсы.

Манифест — документ желаемого объекта программного интерфейса API. Kubernetes сохраняет объект, а его контроллеры постепенно согласуют факт с требованием: Deployment создаёт ReplicaSet и Pod, узел запускает контейнер, приложение отвечает по HTTP. Контроллер — программа, которая повторяет наблюдение и корректировку, а не один вызов командной строки. Поэтому «коммит принят», «манифест получен», «объект принят API», «Pod готов» и «прикладной запрос успешен» — пять разных доказательств.

Первичные источники и пределы этой редакции

Сначала определяем модель GitOps и получаем проверенную поставку. Затем устанавливаем собственный управляющий контур и создаём одно приложение. Внутренняя книга прослеживает получение исходников, рендеринг — вычисление текста по шаблонам, сравнение, синхронизацию и оценку здоровья. После этого разбираем ApplicationSet, репозитории и права. Эксплуатационная книга связывает резерв, отказ сети, высокую доступность и измерение затрат. Практикум сохраняет один стенд без скрытого сброса.

Механику Kubernetes объясняет соседний том; язык и жизненный цикл обычного Helm — том Helm; идентичность коммитов и работа веток — том Git. Здесь показано, что именно добавляет Argo CD между этими механизмами. Его использование Helm для рендеринга не превращает приложение автоматически в обычный Helm-релиз.

Один сервис, разные владельцы

Приложение ledger-api слушает 8080; /livez проверяет живой обработчик, /readyz — готовность к трафику, /api/hello возвращает JSON.service и JSON.message. MESSAGE задаёт строку ответа. Исходники в labs/service совпадают с уже введённым сервисом Kubernetes: тег ledger-api:0.1.0 не обозначает новый случайный бинарник. В Argo CD создаём отдельный Application ledger-gitops и пространство имён gitops-lab. Пространство имён, namespace, отделяет имена и область ряда прав, но не гарантирует полной изоляции.

У этого приложения свои имена Deployment/Service ledger-gitops и создаваемые ConfigMap ledger-settings с суффиксом хеша. Оно не захватывает Helm-релиз ledger из helm-lab и не меняет ресурсы lab соседней книги. Владельцем прикладных объектов становится один Application, владельцем его спецификации сначала читатель; позже ApplicationSet получает отдельные имена и назначения. Совместное управление одним полем разными системами вводится только как явное диагностическое упражнение.

Что проверено в редакции

Локально реально запускались CLI Argo CD 3.5.6, Kustomize 5.8.1 и Helm 4.2.1, соответствующие встроенным средствам выбранного выпуска. Проверены правила доступа RBAC, структурные схемы CRD, рендеринг, устойчивость байтов, сохранение конфигурации при следующем изменении, отрицательные примеры и Go-тесты. RBAC — управление доступом через роли. CRD — определение собственного API Kubernetes; Application, AppProject и ApplicationSet создаются через такие определения.

Кластер и сервер Argo CD автором этого тома не запускались. Установка, настоящая синхронизация, оценка здоровья, экспорт и восстановление ниже — рецепты личного стенда с критериями приёмки. Схемы внутри книги — фиксированные пошаговые модели, не сервер в браузере. Полный протокол и границы лежат в ПРОВЕРКИ.txt, рабочие файлы — в практикуме.

Источники и версия

Четыре независимые идентичности

Коммит Git связывает дерево файлов и историю родителей; его полный идентификатор закрепляет исходники. Образ контейнера хранится отдельно в реестре, а дайджест определяет содержимое манифеста образа. Kubernetes-объект имеет группу API, вид, пространство имён, имя и UID — идентификатор конкретного создания. Application Argo CD связывает источник, назначение и политику; его имя не заменяет ни идентификатор коммита, ни UID Pod.

Два коммита могут ссылаться на тот же образ с разной конфигурацией; один тег образа при разрешённой перезаписи может ссылаться на разные байты. Повторное создание Deployment с тем же именем даёт другой UID. Поэтому выпуск записывают набором: коммит конфигурации, версия и параметры средства рендеринга, дайджесты образов, назначение и состояние операции. Слово «версия» без указания объекта слишком неопределённо для восстановления.

Что является единицей изменения

В примере есть три документа: Deployment, Service и ConfigMap. Идентичность документа для сопоставления — группа API, вид, namespace и имя. У Service группа пустая, вид Service, namespace gitops-lab, имя ledger-gitops. У Deployment группа apps, а остальные имена те же. Это два объекта, хотя имя совпало. Поле metadata.uid появляется при создании в Kubernetes: после удаления и создания того же имени новый UID позволяет отличить новую жизнь объекта от прежней.

Желаемое описание не содержит каждого будущего Pod. Deployment задаёт шаблон и две реплики; контроллер Deployment создаёт ReplicaSet, а тот — Pod. Поэтому согласование Argo заканчивается не копированием Git-файла на узел. Сначала изменяется объект API, затем другие контроллеры создают зависимые объекты, затем kubelet запускает контейнер. Временный третий Pod при maxSurge=1 соответствует разрешённой замене двух реплик. Он сам по себе не означает, что Argo прочитал replicas=3.

Одинаковый коммит не гарантирует одинаковые документы, если генерация читает незакреплённую удалённую базу или случайное значение. Запись выпуска связывает коммит, параметры рендеринга и выбранные образы. Для расследования сохраняют также фактическую ревизию из status.sync.revision: ветка main в spec и разрешённый полный коммит в status отвечают на разные вопросы.

Согласование вместо постоянного push из CI

В модели, где задание CI отправляет kubectl apply, полномочия изменения кластера принадлежат заданию и временный запуск определяет момент действия. В GitOps контроллер живёт постоянно и получает желаемое описание независимо от срока жизни задания. CI по-прежнему компилирует, проверяет и публикует артефакт; изменение конфигурационного Git становится отдельным решением о доставке. Контроллеру нужен доступ к Git и кластеру, но ему не требуется пересобирать Go-приложение.

Периодический опрос Git и уведомление веб-обработчиком — разные пути узнать о возможном изменении. Веб-обработчик, webhook, принимает событие и ускоряет обновление наблюдения; он не делает событие доверенным манифестом сам по себе. После уведомления Argo всё равно проверяет источник, получает ревизию и вычисляет результат. Потерянное уведомление не должно делать систему навсегда слепой: периодическое согласование остаётся важным механизмом.

Сравнить не значит применить

Состояние Synced означает, что наблюдаемое представление соответствует вычисленному желаемому по правилам сравнения. OutOfSync означает отличие. Health, здоровье ресурса, — другая ось: Healthy, Progressing, Degraded, Missing, Suspended, Unknown. Приложение бывает Synced и Degraded: неправильный путь пробы уже принят и потому совпадает с Git, но Pod не готов. Бывает Healthy и OutOfSync: старое приложение обслуживает трафик, хотя новый коммит ещё не применён.

Операция синхронизации имеет собственные фазы и результат. Она может применить ConfigMap и отказать на Deployment из-за неизменяемого поля. Следующая итерация видит новое частичное состояние, а не автоматически исходную систему. Регулярный запуск не делает произвольную миграцию идемпотентной: идемпотентность — свойство повтора без нежелательного дополнительного эффекта, которое надо доказывать отдельно.

Граница автоматического исправления

Self-heal, самовосстановление управляемых объектов, разрешает вернуть их к Git после ручного изменения. Prune, удаление лишних управляемых ресурсов, разрешает уничтожать объекты, исчезнувшие из желаемого набора. AllowEmpty разрешает пустой целевой набор в соответствующей автоматической политике. Это независимые решения; включение автоматической синхронизации не подразумевает все три. Сначала практикум использует ручное применение без удаления.

Git не хранит записи внешней БД. Возврат коммита может вернуть строку конфигурации и образ, но не отменит уже проведённый платёж или удаление столбца. Прикладная обратимость требует совместимых версий схемы, резервных копий и процедуры восстановления. Даже если контроллер умеет повторить манифест, он не знает бизнес-границу безопасного отката без явно заданного протокола.

Как проверить пользу

Сравните время обнаружения дрейфа, восстановления после разрешённого исправления и выяснения владельца изменения. Запишите окно опроса, задержку очереди, время рендеринга, API и готовности отдельно. Если приложение редко изменяется и единственный владелец способен надёжно вести небольшой журнал, дополнительный управляющий контур имеет заметную цену эксплуатации. Если много окружений расходятся и ручной дрейф трудно обнаружить, воспроизводимые входы и автоматическое сравнение дают измеримую пользу.

Выбранная линия

На 1 ноября 2026 стабильная линия этой книги — Argo CD 3.5.6 от 20 октября 2026;3.6.0-rc4 является предварительным выпуском, а не выбранной основной поставкой. Параллельный исправляющий релиз старой ветки может оказаться выше в списке GitHub — это не причина принять его за новую основную версию. Официальная матрица для 3.5 перечисляет Kubernetes 1.36,1.35,1.34,1.33. Наш личный стенд соседней книги использует kubeadm 1.36.6 либо kind 0.33.0 с Kubernetes 1.36.4. Матрица означает проверку проекта на minor-ветках, не фактическую приёмку вашего кластера.

Argo CD — открытый проект Apache-2.0; многопользовательская установка и сокращённая Core являются вариантами развёртывания, а не обещанием коммерческих изданий с одинаковым составом. В книге используется официальный многопользовательский комплект без высокой доступности. Core убирает часть API/интерфейса и модель доступа меняется; оператор или коммерческий сервис вокруг Argo имеет собственную поставку и договор поддержки. Их возможности нельзя переносить на upstream автоматически.

Получить CLI в частную папку

CLI, Command Line Interface, — интерфейс командной строки. Следующие команды выполняются обычным пользователем в личной Linux-VM, не требуют root, не создают службу и не меняют системный PATH. Постоянный каталог LAB_ROOT сохраняется между упражнениями и не находится в /tmp.

Откройте терминал в каталоге argocd/labs полученной книги. Это исходная папка; рабочую копию создаём один раз и дальше продолжаем её. Следующий блок — отдельный подпроцесс с остановкой при ошибке. Он откажет, если work уже существует: повторное упражнение не должно затирать изменения.

export LAB_ROOT="$HOME/handbook-argocd"
(
  set -euo pipefail
  umask 077
  test -f prepare_bundle.py
  mkdir -p "$LAB_ROOT/private" "$LAB_ROOT/evidence"
  test ! -e "$LAB_ROOT/work"
  cp -a . "$LAB_ROOT/work"
  python3 "$LAB_ROOT/work/prepare_bundle.py" --output "$LAB_ROOT/bundle"
  bash "$LAB_ROOT/work/scripts/prepare-tools.sh"
)

Подготовщик получает CLI, install.yaml и два архива инструментов, сверяет SHA каждого и только после этого prepare-tools.sh распаковывает строго названные файлы. Ошибка скачивания или суммы не допускает исполнения. Вернуться после прерванной подготовки можно через отдельную проверку каталога и --verify-only; рабочее дерево не удаляют для повтора. Полный порядок и частичные отказы разобраны в README лаборатории.

export ARGOCD_BIN="$LAB_ROOT/tools/runtime-3.5.6/argocd"
export HELM_BIN="$LAB_ROOT/tools/runtime-3.5.6/helm/linux-amd64/helm"
export KUSTOMIZE_BIN="$LAB_ROOT/tools/runtime-3.5.6/kustomize/kustomize"
"$ARGOCD_BIN" version --client --short

Каноническая команда argocd version с --client и --short выводит только версию CLI без обращения к серверу. Авторский результат: argocd: v3.5.6+c2b1e30; сумма официального файла db9d17b70593d3f86a4dcf08d9ebbb85a42e995426ac5f928b737260656102d3 совпала с cli_checksums.txt и GitHub digest. Архивы и программа не записываются в публичную книгу. Прямой путь сохраняет выбор проверенного бинарника и не меняет PATH системы.

Подготовить чтение и проверку файлов

Prepare_bundle.py использует стандартную библиотеку Python. Configure.py и структурные тесты дополнительно читают YAML и JSON Schema. Для них создаём личное окружение venv, каталог отдельного интерпретатора и библиотек, без изменения системного Python. Автор проверил Python3.12.3, PyYAML6.0.1 и jsonschema4.10.3; версии закреплены в requirements.txt. Для установки библиотек нужен доступ к доверенному индексу либо заранее сохранённые пакеты wheels.

(
  set -euo pipefail
  test ! -e "$LAB_ROOT/venv"
  python3 -m venv "$LAB_ROOT/venv"
  "$LAB_ROOT/venv/bin/python" -m pip install -r "$LAB_ROOT/work/requirements.txt"
)

У существующего venv сначала проверяют состояние; отказ test не разрешает удалять его вместе с изменениями. Далее команды Python для Configure/check используют этот явный интерпретатор. Go нужен только для теста и самостоятельной сборки сервиса; его имеющийся путь читатель задаёт в GO_BIN. Ничего в комплекте не скачивает и не устанавливает Go автоматически.

Хеш и удостоверенное происхождение

SHA-256 проверяет содержимое относительно доверенно полученного ожидания. Архив и изменяемая рядом сумма могли бы быть подменены вместе. Проект публикует подписи образов cosign и сведения происхождения сборки, provenance; их проверка связывает байты с доверенной личностью процесса выпуска. Cosign — инструмент проверки подписанных артефактов; доверенная личность и издатель сертификата задаются отдельно. Эта редакция реально проверила SHA и официальный release, но не выполняла cosign/SLSA-проверку. SLSA — набор требований к защищённости цепочки сборки; название уровня не доказывает безопасные прикладные права манифеста.

Встроенные Helm и Kustomize

Prepare_bundle.py создаёт install.yaml и контрольную опись, но не применяет их. Файл kubeconfig берётся из собственного стенда Kubernetes и должен уже существовать; он содержит полномочия и может запускать программу получения токена.

Для kind выбирают kind-handbook один раз, сохраняя тот же учебный кластер между заданиями. Preflight.sh работает отдельным Bash-процессом с set -euo pipefail: ошибка версии, чтения файла или права завершает только этот процесс ненулевым кодом. Installer повторяет preflight сам, поэтому случайный запуск установки после ошибки проверки тоже не продолжится. Интерактивная оболочка пользователя не закрывается. Применить закреплённый комплект

bash "$LAB_ROOT/work/scripts/install.sh"

Это рецепт, не установка, выполненная автором. Install.sh сначала проверяет комплект и права, создаёт только отсутствующие собственные namespaces с меткой владельца и отказывается использовать чужой существующий namespace. Затем последовательно выполняет dry-run, apply и ожидания; каждый отказ прекращает процесс. Повтор не сбрасывает стенд. Исходник скрипта надо просмотреть перед исполнением. --server-side применяет поля на сервере и избегает большой last-applied аннотации у CRD. Пробный запуск проверяет текущий допуск API без штатного сохранения; он не доказывает последующее скачивание образов или готовность. --force-conflicts, встречающийся в кратком upstream-примере, здесь не добавляется автоматически: на новой личной установке конфликт требует выяснить владельца полей. Повтор не удаляет историю и данные существующей установки.

kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" -n argocd get pod,service

CRD Established подтверждает регистрацию API, Available Deployment — готовность соответствующего контроллера, отдельная проверка StatefulSet нужна application-controller. При ImagePullBackOff исследуйте доступ узла к реестру, при Pending — ресурсы и планирование, при CrashLoopBackOff — журнал конкретного контейнера. Увеличение ожидания не исправляет неверную архитектуру образа. Наличие Service не доказывает доступный сервер.

Что именно подтверждают ожидания установки

CustomResourceDefinition, сокращённо CRD, регистрирует новый вид объекта в Kubernetes API. Условие Established у CRD applications.argoproj.io означает готовность API-схемы Application; оно ничего не сообщает о работающем application-controller. Роль ClusterRole описывает разрешённые действия, ClusterRoleBinding связывает её со служебной учётной записью ServiceAccount. Именно её токен использует процесс контроллера внутри Pod. Права пользователя, установившего манифест, не передаются всем Pod автоматически.

Available у Deployment означает выполнение его собственного критерия доступности. StatefulSet хранит иную модель реплик с устойчивыми именами; в выбранном install.yaml так запускается application-controller. Поэтому installer ждёт его отдельно. После успеха ожиданий проверьте состав Pod и фактические imageID: имя тега в манифесте — ещё не наблюдение загруженного образа. Увидев Pending, смотрите события планировщика; у ImagePullBackOff — причину получения образа; у перезапуска процесса — logs конкретного контейнера.

API-сервер Argo и repo-server доступны внутри кластера через Service. Port-forward временно соединяет локальный порт с выбранным Pod через Kubernetes API. Его готовность не проверяет маршрут repo-server→Git и не создаёт постоянную внешнюю точку доступа. Остановленный port-forward разрывает пользовательский канал, а уже работающие контроллеры продолжают свои циклы.

Доверенный локальный канал

kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" -n argocd \
  port-forward --address 127.0.0.1 service/argocd-server 8443:443

Процесс занимает только локальный порт 8443 до Ctrl+C. В другом терминале экспортируйте открытый сертификат сервера через уже доверенный Kubernetes API. Стандартный сертификат 3.5.6 создаётся с localhost в SAN — списке допустимых имён; реальное содержимое всё равно проверяют. Закрытый tls.key не экспортируется. Для внешнего доступа позже нужны свой DNS, проверяемый сертификат, обратный прокси и корректная поддержка gRPC, протокола вызовов CLI.

bash "$LAB_ROOT/work/scripts/first-login.sh"

Если установлен внешний argocd-server-tls или имя отличается, берут сертификат соответствующего владельца и проверяют его цепочку. Пустой файл или несовпадающее имя — остановка проверки, а не повод отключить TLS. --insecure пропустил бы проверку сертификата и домена; --plaintext выключил бы TLS. Это разные ослабления и ни одно не нужно для обычного доверенного канала этой линии.

Получить начальные права и сменить пароль

argocd admin initial-password получает начальный пароль через Kubernetes, argocd login создаёт сессию Argo, argocd account update-password меняет пароль. First-login.sh снова проверяет готовность сервера,прерывается при ошибке сертификата,начального пароля или login и только после успешного входа вызывает смену пароля. Скрипт предназначен первому входу и не сбрасывает пароль при повторе. Начальный пароль выводится в терминал и вводится интерактивно при login; его не помещают в Git, argv или пример журнала. Update-password запрашивает текущий и новый пароль. --name задаёт имя сохранённого подключения Argo; --argocd-context затем выбирает его. --context у admin-команды выбирал Kubernetes, это другой интерфейс. Файл argocd-config хранит чувствительный сеанс в private, не в репозитории приложения. После смены проверяют новый вход и отдельно решают судьбу начального Secret по upstream-рекомендации; источник данных приложения от этого не сбрасывается.

Где хранится достоверное состояние

Application, AppProject, ApplicationSet, конфигурационные ConfigMap и Secrets — объекты Kubernetes. Достоверное состояние их хранения обеспечивает Kubernetes API и его хранилище etcd, описанное отдельно. Argo CD не требует собственной PostgreSQL/MySQL-базы для истории приложений. Redis используется как ускоряющее хранилище кэша и координационных данных соответствующих компонентов. Потеря кэша заставляет восстанавливать наблюдения и вычисления, но не должна считаться равной потере Git и всех API-объектов.

Вместе с тем фраза «всё в Git» неполна. В Git может не быть регистраций кластеров, ключей подписи сеансов, хешей локальных паролей, репозиторных учётных данных, текущей операции и внешней базы приложения. Поэтому резервируют согласованный набор API-объектов и конфиденциальной конфигурации, а данные приложения — отдельно. Снимок Redis не является основной резервной копией управляющего контура.

Кто за что отвечает

Сервер программного интерфейса, API server или argocd-server, обслуживает веб-интерфейс и CLI, проверяет личность и правила Argo RBAC, читает спецификации и инициирует операции. Repo-server получает исходники, кэширует рабочие копии и результаты, запускает средства генерации манифестов. Application-controller наблюдает Application и целевой кластер, запрашивает манифесты, вычисляет различия и здоровье, выполняет разрешённые операции. ApplicationSet-controller создаёт и корректирует дочерние Application по генератору и шаблону.

Dex — служба объединения внешних способов входа, которая может участвовать в SSO, едином входе. При прямом OIDC-подключении роль Dex меняется или компонент не используется; это не база паролей всех пользователей. OIDC — протокол идентификации поверх OAuth2. Notifications-controller присутствует в типовой поставке как отдельная возможность уведомлений; эта книга не создаёт внешних получателей и не посылает сообщения. Контроллер приложений работает и без пользовательского браузера.

Файлы, каталоги и порты

Клиентская конфигурация находится в выбранном --config и не совпадает с server ConfigMap. В образе repo-server команды helm/kustomize находятся в /usr/local/bin, доверенные SSH-ключи сервера представлены через /app/config/ssh, TLS и GPG — через соответствующие /app/config каталоги. Рабочие копии и временные файлы генерации могут лежать в /tmp контейнера; это расход диска и памяти узла, а не постоянный Git-источник. Перезапуск может потерять локальную копию и заставить повторить загрузку.

Стандартный API-сервис публикует 80/443 на серверный 8080, repo-server использует 8081, Redis6379. Метрики контроллера и других компонентов слушают отдельные порты; точный список смотрят в закреплённом install.yaml и командах get service. Внутренние порты не требуется публиковать в интернет. Сбой связи controller→repo-server отличается от отсутствующего Pod приложения; доступны разные журналы и метрики.

Из Git до API

Предположим, Application отслеживает ветку main. Очередное согласование разрешает ссылку в конкретный коммит, repo-server проверяет доступ и получает дерево. Определяет выбранное средство генерации и путь, загружает допустимые зависимости, вычисляет манифесты с параметрами и возможностями целевого API. Контроллер получает документы, нормализует сравнимое представление и сопоставляет идентичности ресурсов с кэшем фактического кластера. OutOfSync — результат сравнения, а не приказ автоматически менять.

При разрешённой операции контроллер определяет порядок фаз и волн, выполняет проверки проекта и обращается к API целевого кластера. API ещё может отказать в полномочиях, схеме, политике допуска или неизменяемом поле. После принятия Kubernetes-контроллеры создают процессы, а Argo наблюдает их состояния и вычисляет здоровье. Наблюдаемое состояние status Application хранит в том числе ход и результат операции. Каждое обращение и наблюдение асинхронно: данные имеют возраст, а следующий проход может увидеть более новый факт.

Два рабочих цикла и сохранённый запрос

Проверка состояния и операция синхронизации выполняют разную работу. Событие об изменении Application или наблюдаемого ресурса помещает приложение в очередь проверки. Работник берёт его, получает целевые документы и состояние кластера, затем обновляет status. Наличие записи в очереди не означает отдельный процесс на каждое событие: повторные события могут объединяться, пока приложение уже ожидает обработки. Очередь помогает повторить работу после временной ошибки и ограничить число одновременных вычислений.

Ручной запрос sync сохраняет параметры операции в поле operation самого Application. В status.operationState контроллер записывает принятую операцию, phase, startedAt, finishedAt, message и результат отдельных ресурсов syncResult.resources. Читатель может сопоставить запрошенную ревизию, инициатора и завершение. Running означает продолжающуюся работу, Succeeded — выполненные условия этой операции, Failed или Error требуют разбора сообщения и уже изменённых ресурсов. Последний результат остаётся наблюдением о конкретной операции, а не текущим запретом всему приложению работать.

Кластерный кэш пополняется чтением и наблюдением API целевого Kubernetes. Он содержит объекты, а не байты образов на узлах. Repo-server хранит рабочие Git-копии и вычисленные манифесты; Redis обслуживает используемые компонентами кэшированные данные. Эти копии можно пересоздать лишь при доступных первичных источниках и полномочиях. Если после рестарта недоступен Git, прежний результат в UI не превращается в подтверждение нового сравнения. Сверяйте время наблюдения, conditions, revision и состояние соединения с назначением.

Кэш, очередь и ошибка

Кэш манифестов экономит повторную генерацию одинаковых входов, кэш ресурсов экономит запросы к API, очередь разделяет обнаружение изменения и выполнение работы. Возраст кэша, перегруженный repo-server и очередь могут увеличить задержку даже при свободном CPU приложения. Принудительное обновление наблюдения и очистка кэша манифестов — разные действия; --refresh и --hard-refresh нельзя считать синонимами.

Если Git недоступен, уже запущенные Pod продолжают жить по своим контроллерам Kubernetes. Новый желаемый набор может стать неизвестным, а сравнение — ошибкой получения, не нулём объектов для удаления. Если недоступен целевой API, Git по-прежнему читается, но применение и наблюдение факта задерживаются. Если остановлен Argo, Kubernetes поддерживает ранее созданные ресурсы, однако новые изменения Git и исправление дрейфа ждут восстановления контура. Что создаёт Application

Application — API-объект Argo CD, связывающий источник манифестов, целевой кластер и пространство имён, проект и политику синхронизации. Его spec — желаемая спецификация, status — наблюдение контроллера. Условие condition внутри наблюдения описывает отдельный факт или ошибку. Поле operation содержит запрос на действие, operationState — ход и результат соответствующей операции. Создание объекта не доказывает, что источник доступен, проект разрешает ресурсы или приложение готово.

Наш Application ledger-gitops хранится в argocd, а ресурсы отправляет в gitops-lab того же кластера. Это разные пространства имён. Источник — собственный Git-репозиторий с путём apps/ledger/overlays/lab. TargetRevision сначала полный коммит, не плавающая ветка. Server https://kubernetes.default.svc означает доступ к API из управляющего контура; это не localhost клиента и не URL веб-интерфейса Argo.

Проект не является namespace

AppProject ограничивает допустимые источники, назначения и виды ресурсов; проект ledger разрешает один свой репозиторий и gitops-lab. Список ресурсов уровня кластера пуст, допустимы только названные виды прикладных объектов. Он не создаёт Kubernetes namespace и не заменяет Kubernetes RBAC служебной учётной записи контроллера. Нужны обе границы: политика Argo проверяет допустимость приложения, API проверяет реального исполнителя.

Стандартный проект default из установки обычно широк. Дать пользователю право создавать приложения с произвольным источником и назначением argocd значит потенциально позволить менять управляющий контур. Поэтому учебный проект не использует wildcard для всего кластера, а право менять AppProject принадлежит владельцу. Допуск sourceRepos сам по себе не даёт repo-server пароль к репозиторию.

Прочитать спецификацию по полям

 | Поле нашего Application | Кто его использует | Как проверить смысл

 | metadata.namespace: argocd | Kubernetes хранит сам Application здесь. | kubectl get application в gitops-lab его не найдёт.

 | spec.project: ledger | Argo проверяет ограничения AppProject. | Сопоставить URL, назначение и виды документов с проектом.

 | source.repoURL, targetRevision, path | Repo-server получает дерево и выбирает каталог внутри коммита. | Путь apps начинается от корня Git; локальный cwd клиента его не меняет.

 | destination.server либо destination.name | Контроллер выбирает зарегистрированный целевой кластер. | Задают один способ выбора. Адрес Argo API сюда не подставляют.

 | destination.namespace: gitops-lab | Подставляется namespaced-ресурсам без собственного metadata.namespace. | Явное пространство в исходном документе сохраняет своё значение.

 | revisionHistoryLimit: 10 | Ограничивает сохраняемую историю доставок. | Старые записи могут исчезнуть; Git и образы должны сохраняться отдельно.

Spec задаёт запрос пользователя, а status.sync.comparedTo показывает, с каким описанием выполнялось наблюдение. После изменения spec старая запись status может ещё относиться к прежней цели. Сначала дождитесь нового сравнения, затем делайте вывод о новом коммите. Conditions с типом ошибки источника не заменяются догадкой по цвету значка здоровья.

Подготовить проверяемые файлы

В labs/bootstrap лежат шаблоны с example.invalid и фиктивным коммитом, чтобы они не приняли чужой адрес за готовый. После создания собственного репозитория и публикации нужного дерева определите его полный коммит. Configure.py только создаёт два файла в новом каталоге, проверяет форму входов и отказывается молча перезаписывать существующую конфигурацию.

"$LAB_ROOT/venv/bin/python" "$LAB_ROOT/work/configure.py" --repo "$LAB_REPO_URL" --revision "$LAB_COMMIT" \
  --output "$LAB_ROOT/bootstrap-initial"

LAB_REPO_URL и LAB_COMMIT читатель задаёт из своего существующего репозитория. --revision принимает полный 40-символьный идентификатор; строка из одних цифр в YAML должна оставаться строкой, а не числом. Структурный тест этой редакции действительно поймал такую ошибку в ранней заготовке. Форма HTTPS/ssh:// не гарантирует доступ; рабочая проверка связи repo-server выполняется отдельно до синхронизации.

bash "$LAB_ROOT/work/scripts/first-app.sh"

First-app.sh проверяет готовность сервера и прекращается при первом отказе dry-run/apply. Сначала проект, затем приложение: файл не используется до создания. На этом шаге automated.enabled=false, prune/selfHeal/allowEmpty=false, финализатор удаления ресурсов не задан. Приложение наблюдается, но не должно автоматически применять манифесты. FailOnSharedResource=true заставляет операцию отказать при ресурсе, уже отслеживаемом другим Application; это дополнительная защита, не универсальный детектор всех ручных владельцев.

Наблюдать до применения

"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" \
  --argocd-context handbook app get ledger-gitops --refresh --output yaml
"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" \
  --argocd-context handbook app manifests ledger-gitops

Get показывает источник, назначение, условия ошибок и сравнение; manifests получает вычисленный целевой текст через сервер. Это не локальная команда Kustomize и не снимок работающих Pod. При недоступном источнике сначала исправляют URL, ревизию, путь или учётные данные. Нельзя продолжать sync после ошибки генерации и считать пустой файл допустимым набором для prune.

Имена и владение

Манифесты создают только ledger-gitops и ConfigMap в gitops-lab; соседний Helm управляет ledger-ledger-api в helm-lab. Argo использует аннотационное отслеживание по умолчанию в 3.5, а Helm хранит свою историю и аннотации. Не копируйте чужую tracking-id и не включайте одинаковую пару вид/пространство/имя в два Application. Совпадение имени контейнерного образа допустимо: тот же проверенный артефакт может работать в двух независимых окружениях.

Команды и проверенные формы

Открываемая справка этой главы: argocd app create, argocd proj get. В карточках разобраны назначение, отдельные флаги, сочетания и предел доказательства. Полный путь в исполняемых блоках выбирает проверенную программу; каноническое имя здесь открывает ту же команду в справочнике.

Репозиторий ещё не набор объектов

Рендеринг — вычисление конечных документов Kubernetes из исходных файлов и параметров. Repo-server получает конкретную ревизию, выбирает каталог и средство генерации, запускает его и возвращает документы. Controller затем сопоставляет их с наблюдаемыми объектами. Доступный Git-коммит с ошибочным путём и корректный путь с ошибочным шаблоном — разные отказы. Ни один из них не следует интерпретировать как разрешение удалить все ресурсы.

Обычный каталог YAML читается как документы; Kustomize обнаруживается по kustomization.yaml; Helm — по Chart.yaml. Явная секция источника может выбирать средство и его параметры, поэтому полезно проверять фактическую спецификацию Application. Пользовательский модуль генерации, Config Management Plugin, запускает дополнительную программу: это отдельная граница исполнения кода и доверия, а не способ автоматически починить любой YAML.

Наш исходный путь

База apps/ledger/base задаёт Deployment, Service и генератор ConfigMap. Набор изменений overlays/lab задаёт пространство gitops-lab и заменяет MESSAGE. Kustomize добавляет к имени ConfigMap хеш данных и переписывает ссылку в шаблоне Pod. Изменение MESSAGE меняет ссылку, следовательно меняется шаблон Pod и Kubernetes начинает замену Pod. Уже запущенный процесс не получает новое окружение от редактирования ConfigMap; связь через имя обеспечивает новый запуск.

"$KUSTOMIZE_BIN" build "$LAB_ROOT/work/gitops/apps/ledger/overlays/lab" \
  > "$LAB_ROOT/evidence/desired-local.yaml"

Это настоящее локальное вычисление Kustomize 5.8.1, не вызов Argo. Отсутствие запроса к API означает также отсутствие проверки прав, admission-проверок, доступности образа и готовности. В tests сравниваются селекторы Service/Deployment, порт 8080, имя ConfigMap и поле MESSAGE; простой нулевой код не заменяет эти проверки.

Helm внутри Argo

Argo использует Helm как генератор через template. Он не создаёт Helm-релиз, не пишет историю sh.helm.release и не выполняет Helm upgrade/rollback. Историю и жизненный цикл ведёт Argo. Chart version обозначает пакет, appVersion — метаданные приложения, Application targetRevision для Git — ревизию репозитория; одинаковое написание version не связывает эти сущности.

Порядок переопределения Helm в Argo: значения чарта, valueFiles, строковое поле values, структурированное valuesObject, параметры parameters. Правый источник выигрывает; в списке valueFiles более поздний файл важнее раннего. Значения не становятся строками лишь от кавычек оболочки: forceString в параметре заставляет передать строку. Подробный разбор типов относится к книге Helm, но проверять нужно именно итоговый YAML и схему используемого чарта.

Встроенный Helm 4.2.1 закреплён поставкой Argo 3.5.6. Селектор helm.version с историческим v3 не запускает отдельный Helm 3: исходный код этой версии принимает v3/v4 и запускает один helm. Пример renderers/helm в labs — отдельная маленькая проверка интерфейса рендеринга, выдающая один ConfigMap. Это не второй источник того же полного приложения и не перенос соседнего Helm-релиза под управление Argo.

"$HELM_BIN" lint "$LAB_ROOT/work/renderers/helm" --strict &&
"$HELM_BIN" template ledger-gitops-render "$LAB_ROOT/work/renderers/helm" \
  --namespace gitops-lab > "$LAB_ROOT/evidence/helm-local.yaml"

Локальный template может отличаться от repo-server из-за версий, доступных API, параметров releaseName/namespace, зависимостей и окружения. Если chart использует случайные значения, повторный рендер может постоянно давать различие. Случайный пароль при каждом сравнении — плохая модель постоянного секрета. Чтение существующего кластера функцией lookup также нельзя считать воспроизводимым входом локального template.

Проследить изменение MESSAGE до нового процесса

Исходная ConfigMap называется ledger-settings, но её окончательное имя вычисляет Kustomize. При C1 и MESSAGE=A генератор выдаёт имя с одним суффиксом; при C2 и MESSAGE=B — с другим. Суффикс здесь обозначим H1/H2: это условные подписи, не обещание конкретного алгоритма или длины хеша. В Deployment меняется envFrom.configMapRef.name с ledger-settings-H1 на ledger-settings-H2. Поле находится внутри spec.template, поэтому Deployment создаёт новый ReplicaSet.

Новому Pod kubelet передаёт MESSAGE=B при создании окружения контейнера. Старый Pod сохраняет своё окружение MESSAGE=A даже после удаления или изменения исходной ConfigMap. Удалять старую ConfigMap до проверки смены Pod опасно для последующего запуска старого шаблона: он ещё может ссылаться на H1. Результат рендеринга даёт возможность предсказать обе изменённые идентичности; работа кластера подтверждается отдельно.

Для Helm источником типов является также values.schema.json чарта. Значение message=true имеет тип bool и отвергается нашей схемой, хотя сам YAML допустим. Строка «true» проходит проверку строки. Сохраняйте итоговый YAML и значения входов: неверный тип, несовместимая схема и недоступная dependency требуют разных исправлений.

Несколько источников и зависимости

Application.spec.sources задаёт несколько источников вместо единственного source. Ссылка ref связывает источник значений с префиксом $values в valueFiles; путь после него считается от корня соответствующего репозитория. Указанный path может дополнительно включить генерацию ресурсов из этого источника. При повторении одинаковой идентичности ресурса последний источник выигрывает, появляется RepeatedResourceWarning. Это явное переопределение с риском, а не безусловное структурное объединение документов.

Ссылки Helm dependency и удалённые базы Kustomize расширяют вход за пределы основного Git-коммита. Закрепите версии, суммы и доступность всех зависимостей. Универсальный источник OCI и репозиторий Helm OCI используют разные поля и форматы пути; OCI — протокол хранения артефактов, а не доказательство, что любой архив является Helm-чартом. Закрепление digest и проверка доверия нужны независимо от удобного тега.

Где проходит предел локального доказательства

Реальные проверки labs используют Kustomize 5.8.1 и Helm 4.2.1 из закреплённой поставки. Они не утверждают, что вызвали контейнер repo-server или Argo API. Команда app manifests требует сервер и доступное приложение; app diff --local тоже получает серверное состояние. Название local задаёт источник желаемых файлов, а не обещание полностью автономной команды. Полный результат сравнения получают только на собственном сервере с сохранёнными входами.

Что сравнивается

Различие, diff, — результат сравнения желаемого и наблюдаемого представлений ресурса. Идентичность включает группу API, вид, пространство имён и имя. API-версия влияет на преобразования, но смена версии одного вида не обязана создавать новый логический ресурс. Наблюдаемые объекты поступают из кэша кластера; желаемые вычисляет repo-server. Сначала проверяют свежесть и происхождение обеих сторон, затем смысл различия.

Простой текстовый diff видит порядок полей, форматирование и отсутствующее поле так же, как изменение значения. Argo нормализует документы и учитывает API-преобразования; механизм сравнения имеет собственные настройки. Поэтому git diff --no-index в labs доказывает изменение текста, но не повторяет алгоритм Argo. При добавлении серверного сравнения API может выполнить dry-run и изменяющие admission-компоненты: это уже запрос к кластеру, а не чистая функция от двух файлов.

Три стратегии расчёта различия

Admission — обработка запроса Kubernetes API перед сохранением: проверяющий validating-webhook может отказать, изменяющий mutating-webhook — преобразовать документ. ResourceVersion — служебная версия живого API-объекта, не Git-коммит. Эти понятия понадобятся для серверного сравнения.

Для стратегии Legacy нужны три входа: желаемый объект D, живой L и прежняя конфигурация A из аннотации last-applied-configuration. Третий вход помогает отличать поле, которое автор удалил из своего описания, от поля, которого он никогда не задавал. Отсутствие поля в D само по себе ещё не означает «удалить любое такое поле из L». Порядок YAML-ключей и серверные значения по умолчанию также мешают обычному текстовому сравнению.

Structured-Merge Diff использует сведения о принадлежности полей; в документации 3.5.6 этот вариант заменяется Server-Side Diff из-за ограничений, в частности у CRD со значениями по умолчанию. Server-Side Diff получает прогноз живого объекта через пробный Server-Side Apply в API и сравнивает прогноз с L. Результат кэшируется; изменение ревизии, спецификации, resourceVersion или запрос refresh заставляет его пересчитать. Для ещё не существующего ресурса этот серверный путь не вызывается.

Расчёт различия и применение разделены. ServerSideDiff=true настраивает сравнение; ServerSideApply=true выбирает способ изменяющей операции sync. Включение одного не означает выполнения другого. Проверяющие admission-webhooks могут обнаружить ошибку уже при серверном сравнении. Учёт изменений mutating-webhooks отдельно включается IncludeMutationWebhook=true. Эти правила закреплены в описании стратегий 3.5.6.

Три описания одного Deployment

HPA, HorizontalPodAutoscaler, — контроллер Kubernetes, изменяющий число реплик по метрикам. Здесь его изменение показано отдельно от изменения образа автором Git.

Три описания одного DeploymentУсловные входы сравнения: Git D, прежняя last-applied A и живой Kubernetes L. Образ изменён автором, число реплик изменено HPA. Это не результат работающего Argo.

Текстовая модель: в D и A две реплики, в L три; образ в D — условный 0.2.0, в A и L — 0.1.0. Одинаковая подсветка различия ещё не выбирает владельца replicas. Legacy использует D/L/A, серверное сравнение получает прогноз API, а sync применяет выбранный способ отдельно. Фигура не предсказывает универсальный patch или статус для любых настроек. Для HPA согласуйте управление полем по следующей главе о владении.

Состояние синхронизации

Состояние синхронизации, sync status, отвечает на вопрос о соответствии управляемых ресурсов цели. Synced означает совпадение в рамках правил сравнения, OutOfSync — найденное различие, Unknown — сравнение не получено достоверно. Условие, condition, сообщает отдельную проблему: например, ComparisonError при ошибке генерации. Это не то же самое, что состояние запущенной операции operationState или фаза Pod. Неудачная операция может оставаться в истории после последующего восстановления готовности.

Состояние здоровья

Health, оценка работоспособности ресурса, строится по правилам конкретного вида. Для Deployment учитываются наблюдённое поколение и состояние реплик; для Job — завершение. Healthy, Progressing, Degraded, Suspended, Missing и Unknown — разные результаты такой оценки. У произвольного CRD может не быть встроенного проверяющего правила; пользовательская Lua-проверка является кодом с отдельной ответственностью.

 | Сравнение | Готовность | Причина и следующий вопрос

 | Synced | Healthy | Документы совпали и правила готовности выполнены; проверить прикладной HTTP-ответ.

 | Synced | Degraded | Git сам описывает неисправное состояние либо процесс отказал; изучить Pod и события.

 | OutOfSync | Healthy | Старый работающий набор отличается от цели; оценить изменение перед sync.

 | Unknown | Unknown или последнее значение | Нет достоверного сравнения; проверить доступ и генерацию, не запускать удаление вслепую.

Как наблюдать без ложного успеха

"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" \
  --argocd-context handbook app get ledger-gitops --refresh --output yaml
"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" \
  --argocd-context handbook app diff ledger-gitops

Refresh запрашивает обновление сравнения; hard-refresh дополнительно инвалидирует кэш целевых манифестов. Ни один флаг не равен применению. Для app diff код 0 означает отсутствие различия, --diff-exit-code по умолчанию задаёт 1 при различиях. Общая ошибка соединения или вычисления — другой случай: сценарий должен различать результат, stderr и тип команды, а не считать любой ненулевой код безопасным «есть изменение». --exit-code=false отключает именно различие как ненулевой результат, не исправляет отказ API.

App diff --local КАТАЛОГ подменяет локальную сторону сравнения и всё равно требует серверное приложение. --server-side-generate передаёт локальные файлы для серверной генерации; это отдельная передача файлов через API и требует доверия к серверу. Ни один из этих вариантов не исполнен автором на кластере. Встроенные автономные проверки книги вызывают сами рендереры.

Реальный локальный отрицательный опыт изолировал HOME и --config, не задавал сервер и вызвал app diff с --local на существующем каталоге. CLI завершился с кодом1: Argo CD server address unspecified. Это проверка отсутствия автономного пути, а не выполненное сравнение с настоящим кластером; не переносите этот конкретный код на все другие общие ошибки.

Игнорирование и владение полем

IgnoreDifferences исключает указанные пути JSON, выражения jq или поля, управляемые названными менеджерами, из сравнения. Это не автоматически исключение из применения. RespectIgnoreDifferences=true распространяет правило на подготовку синхронизации существующего ресурса; при первом создании исходного живого объекта нет. Слишком широкое игнорирование скрывает реальные изменения и требует письменной причины.

Если HorizontalPodAutoscaler управляет количеством реплик, одновременно фиксировать spec.replicas в Git и постоянно возвращать его selfHeal означает конкуренцию. Выберите владельца поля, уберите лишнее управление или задайте точечное правило. Списки Kubernetes имеют собственную семантику объединения и нормализации; менять порядок вслепую по текстовому diff недостаточно. Управляемые поля managedFields — данные API о менеджерах, не список доверенных людей.

Прикладной тест остаётся отдельным

Readiness /readyz проверяет способность данного Pod принимать трафик, Service требует подходящего селектора и адресов готовых Pod. HTTP /api/hello дополнительно подтверждает полный путь и MESSAGE нужной версии. Healthy не проверяет пользовательскую бизнес-операцию и не является резервной копией данных. В практикуме намеренно испорченный путь readiness позволяет увидеть, что принятый Deployment и доступный старый Service не означают успешную замену всех Pod.

Сначала ручная операция

Синхронизация — операция приближения набора ресурсов к выбранной цели. Запрос проходит Argo RBAC и ограничения AppProject, затем контроллер выполняет план применения и ожидает нужные состояния. Ресурсы меняются несколькими API-запросами; частичный отказ возможен между ними. OperationState хранит ход операции, но не превращает несколько запросов в транзакцию с автоматическим возвратом внешних данных.

После получения манифестов и просмотра различий первая учебная операция выполняется без prune. Имя приложения и контекст указываются явно. Время app sync --timeout — целое число секунд, а не строка длительности Helm 180s.

"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" \
  --argocd-context handbook app sync ledger-gitops --timeout 180

--dry-run у app sync запрашивает серверную операцию пробного применения; это не автономный Helm template. --async возвращает управление до окончания операции: нулевой код такого запроса доказывает принятие, не готовность. --revision задаёт явную ревизию операции; если spec продолжает следить за другой целью, последующая сверка снова увидит её. Для устойчивой смены цели изменяют декларативный источник Application.

Нативная отрицательная проверка3.5.6 подтверждает границу ещё до API: --timeout 180s и --timeout -1 дают код1 и сообщение ParseUint invalid syntax. Строка180s подходит некоторым другим инструментам, но здесь тип uint требует неотрицательное целое число. Правильное180 означает180 секунд; успешность самой операции этим локальным разбором не проверялась.

Ожидание — отдельное условие

"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" \
  --argocd-context handbook app wait ledger-gitops --sync --health --timeout 180

--sync ждёт соответствия, --health — здоровья; совместное использование требует обоих условий. --operation относится к завершению операции, --degraded позволяет ожидать неисправное состояние в диагностике, но не означает успех поставки. При тайм-ауте сначала получают app get и события Kubernetes: прекращение ожидания CLI не обязательно отменило текущую серверную операцию. Terminate-op — явное действие с отдельным правом; оно не откатывает уже принятые объекты.

Что включает автоматизация

Spec.syncPolicy.automated.enabled=false выключает автоматические операции даже при prune=true или selfHeal=true. Отсутствующее или null-значение enabled при существующем automated трактуется как включённое; automated:{} тоже включает. Отсутствие секции automated отличается от присутствующего пустого объекта. Явное false в исходном примере защищает первый просмотр. Включение автоматизации должно быть видимым изменением собственной конфигурации, а не скрытым побочным результатом CLI.

 | Поле | Отдельное разрешение | Условие и следствие

 | prune | Удалять отслеживаемые объекты, отсутствующие в цели. | Не разрешает пустую цель без allowEmpty.

 | selfHeal | Исправлять отклонения живых объектов при той же ревизии. | Не исправляет неисправную цель в Git.

 | allowEmpty | Допустить автоматическое опустошение набора при prune. | Не превращает ошибку генерации в законную пустую цель.

 | retry | Повторять неудачную операцию по заданному расписанию. | Не заменяет selfHeal и не делает необратимые hooks безопасными.

Автосинхронизация обычно выполняет одну попытку для сочетания коммита и параметров; неудачное сочетание не повторяется бесконечно само. Политика retry задаёт число попыток и нарастающую задержку, selfHeal допускает повторное исправление той же цели. В 3.5 стандартная задержка self-heal — 5 секунд; цикл проверки Git по умолчанию 120 секунд плюс случайная добавка до 60 секунд. Webhook ускоряет обнаружение, но не отменяет периодическую проверку и не удостоверяет доступность репозитория.

При полном закреплённом targetRevision новый коммит ветки сам по себе не меняет цель. Для следующего задания либо меняют этот идентификатор в том же Application, либо осознанно переходят на свою ветку. У нескольких источников изменение другого источника способно вызвать автосинхронизацию и затронуть живое отклонение даже при selfHeal=false. Не рассматривайте один флаг вне общей модели источников.

Посчитать повтор и прочитать его состояние

У retry в поставленном automated-policy.yaml заданы limit=3, duration=5s, factor=2, maxDuration=30s. Это бюджет повторов неудачной операции, а не постоянный опрос Git. В арифметической модели с тремя повторами паузы составят min(5×2⁰,30)=5, min(5×2¹,30)=10 и min(5×2²,30)=20 секунд. Сумма пауз — 35 секунд; длительность самих попыток в неё не входит. При factor=4 паузы станут 5,20,30 и дадут 55 секунд. Поэтому maxDuration ограничивает отдельную паузу, а не полное время поставки.

Для разбора конкретного повтора читайте status.operationState.retryCount, phase, message и syncResult.resources. Если ConfigMap уже применена, а Job завершился ошибкой, следующая попытка начнётся при существующей ConfigMap и с возможными внешними эффектами Job. Повторный HTTP-запрос read-only теста и повторный перевод денег имеют разную семантику. Retry.refresh=true дополнительно разрешает взять новую ревизию: тогда это уже новая цель, которую надо записать рядом с результатом, а не обозначить старым C2.

Модель пауз ничего не обещает о реальном расписании процесса: очередь, API и время выполнения добавляют задержку. На личном стенде сначала выполните ошибку readiness без автоматизации, сохраните первое состояние, исправьте Git и лишь затем сравнивайте сценарий с ограниченными повторами. Не включайте одновременно selfHeal, prune и retry ради одного наблюдения.

Выбор ресурсов и удаление

--resource ГРУППА:ВИД:ИМЯ ограничивает ручную операцию выбранными ресурсами; пустая группа в :Service:ledger-gitops значима. Выборочная синхронизация пропускает hooks и не создаёт обычную полную запись истории. Sync option ApplyOutOfSyncOnly=true — другой механизм: в 3.5 hooks продолжают выполняться, история сохраняется. Экономия запросов не является разрешением пропустить проверки запуска.

--prune у ручной команды явно разрешает удаление лишних отслеживаемых объектов. В нашем Kustomize изменение MESSAGE создаёт новое имя ConfigMap; без prune старые ConfigMap остаются. Сначала проверьте, какие имена больше не нужны и на какие ещё ссылаются работающие Pod. PruneLast=true откладывает удаление до неявной последней волны после остальных готовых ресурсов, но не спасает от неверно заданной цели.

Окно синхронизации

Sync window — календарное ограничение операций в AppProject. Указываются расписание, длительность, часовой пояс и отбор приложений; запрет может блокировать автоматическую и ручную операцию, а manualSync задаёт отдельное исключение. Разрешение окна не даёт пользователю отсутствующее право sync. Проверяйте одновременно время сервера, выбранный часовой пояс и отбор по имени/пространству/кластеру; это политика запуска, не ограничение времени уже работающего Pod.

Фаза и волна

Фаза определяет роль ресурса в операции: PreSync перед обычными ресурсами, Sync во время основного применения, PostSync после успешной синхронизации и здоровья, SyncFail при неудаче. В 3.5.6 есть также PreDelete перед удалением ресурсов приложения и PostDelete после их удаления; это фазы удаления, не обычного sync. Hook — ресурс с аннотацией argocd.argoproj.io/hook, который контроллер исполняет в соответствующей фазе. Обычный ресурс без такой аннотации относится к основному применению.

Волна, sync wave, — целое число в аннотации argocd.argoproj.io/sync-wave; допускаются отрицательные числа, по умолчанию 0. Приоритет: фаза, затем волна, затем вид ресурса и имя. PreSync с волной 10 не становится позднее обычного Sync с волной-10: граница фаз старше номера. Внутри применения сначала выбирается самая ранняя волна с несоответствующим или нездоровым ресурсом; следующая волна ждёт продвижения предыдущей.

Стандартная задержка между волнами — 2 секунды, настраиваемая ARGOCD_SYNC_WAVE_DELAY. Это пауза для реакции контроллеров, а не доказательство, что внешняя система стала готовой. Здоровье и собственные проверки нужны всё равно. При удалении порядок волн обратный: сначала более высокие номера. Ошибка удаления ранней для этого порядка волны может удержать остальные.

Прочитать остановку по конкретному ресурсу

В рассматриваемом примере PreSync Job находится в волне 10, ConfigMap — в Sync/−1, Deployment — в Sync/0, HTTP Job — в PostSync/5. Сортировать четыре числа как один список нельзя: сначала завершается фаза PreSync. После ConfigMap контроллер применяет Deployment, затем наблюдает готовность. Если новое поколение Deployment не готово, PostSync Job ещё не должен начинать проверку.

Две секунды между волнами дают другим контроллерам время увидеть изменения. Это не оценка нужной длительности миграции и не замена барьеру здоровья. Отказ ранней волны оставляет уже применённые объекты на месте. При удалении через prune волны обходятся в обратном направлении: высокий номер удаляется раньше низкого. Исправление ошибки удаления и повтор продолжаются при фактическом частичном состоянии.

PreDelete Job при неуспехе может удерживать удаление приложения; исправный PostDelete запускается после удаления ресурсов. Сохраните журналы и состояние Job до уборки. Удалять объект hook, не выяснив его внешний эффект, опасно: следующее создание может повторно выполнить миграцию, даже если предыдущая успела изменить БД перед обрывом ответа.

t0…t5 — порядок, не секунды

Сначала заканчивается PreSync, хотя его волна 10 численно выше −1. Затем идут ConfigMap и Deployment. Неверная readiness удерживает PostSync; старые готовые Pod могут продолжать обслуживать Service. C4 исправляет цель новой операцией, которая повторно проходит необходимые фазы. Пример PreSync условный; поставленный необязательный HTTP Job — PostSync/5. Это схема причин, а не выполненный журнал.

Одна проверка после сервиса

Файл fixtures/post-sync-test.yaml описывает Job, выполняющий HTTP-запрос к Service ledger-gitops и пути /api/hello. Его PostSync означает, что до проверки должны успешно завершиться обычные ресурсы и их оценка готовности. Волна 5 упорядочивает его относительно других PostSync-hooks. Для выполнения нужен образ busybox:1.37.0, сеть и разрешённый AppProject вид Job; автор не скачивал этот образ и не запускал Job на кластере.

metadata:
  name: ledger-http-test
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/sync-wave: "5"
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation,HookSucceeded

Повтор именованного hook определяется политикой удаления. При отсутствии явной политики Argo 3.5.6 подразумевает BeforeHookCreation: прежний одноимённый объект удаляется перед новым созданием. HookSucceeded очищает результат при успешной синхронизации; завершившийся PreSync не обязан исчезнуть немедленно, пока дальнейшие фазы ещё идут. При generateName каждый запуск получает новое имя; без политики уборки результаты накапливаются. Job TTL и удаление hook — разные механизмы: слишком раннее внешнее удаление может осложнить наблюдение результата. Сохраните нужные журналы до уборки.

Почему миграция не является откатом данных

PreSync часто выбирают для миграции схемы прикладной БД. У самой Argo CD нет придуманной SQL-базы, но у приложения она может быть. Завершившийся Job мог изменить внешнее хранилище навсегда; последующий отказ Deployment не возвращает эти байты. Повтор операции может повторить hook, поэтому миграция должна быть идемпотентной либо иметь безопасную проверку уже выполненной версии. Одна аннотация волны этого не обеспечивает.

SyncFail-hook помогает собрать диагностику или выполнить заранее спроектированную компенсацию. Его отказ не превращается в успешную операцию и не гарантирует возврат всех внешних эффектов. PostDelete срабатывает в жизненном цикле удаления, а не как обычный PostSync. Нельзя использовать удаление Application как универсальную процедуру резервного копирования.

Намеренный отказ readiness

После исправного первого запуска практикум меняет в том же дереве только readiness на /missing-readyz. Deployment принимается API, новый Pod запускает тот же процесс и получает 404 на проверке. Старые готовые Pod при RollingUpdate и maxUnavailable=0 могут продолжать обслуживать Service, а приложение останется Progressing или дойдёт до Degraded по правилу Deployment. PostSync не должен перескочить незавершённую готовность.

Если поменять одновременно селектор Service, образ и готовность, причинность станет неясной. Поэтому одно задание изменяет одну границу, сохраняет предыдущую MESSAGE и доказательства. Возврат выполняется новым исправляющим изменением того же дерева, без удаления namespace и без переустановки Argo. История операции должна показать различие между «текст принят», «новые Pod готовы» и «HTTP-проверка прошла».

Ограничения отбора

Выборочная синхронизация --resource не запускает hooks. Это особенно важно, если человек рассчитывает на обязательный PreSync-тест безопасности или миграцию. ApplyOutOfSyncOnly=true у политики — не синоним этого выбора: hooks и запись истории в 3.5 сохраняются. Skip-hook намеренно пропускается; это не способ оставить незавершённый Job как успешное доказательство. Helm-аннотации hooks частично переводятся Argo, но привычный Helm test не следует считать автоматически той же фазой: смешанную модель нужно проверять по таблице поддерживаемых hooks выбранной версии.

Как Argo узнаёт свои ресурсы

Отслеживание ресурсов связывает живой объект с Application. В линии 3.5 по умолчанию используется annotation: argocd.argoproj.io/tracking-id несёт идентификатор приложения, группу/вид и пространство/имя. Режим label ограничен длиной и конкурирует с другими инструментами за app.kubernetes.io/instance; annotation+label оставляет метку для совместимости, а отслеживает по аннотации. Поэтому наличие красивой метки само по себе не доказывает владельца.

InstallationID отделяет несколько установок Argo в одном кластере дополнительной аннотацией. Это не превращает одновременное управление одной идентичностью в безопасное. Скопированный tracking-id от чужого ресурса может исказить учёт; несамоссылочные аннотации тоже имеют особую семантику. Основная граница практикума проще: отдельный namespace gitops-lab, отдельные имена ledger-gitops и один Application. Соседний Helm-релиз не усыновляется.

Два вида владельца

OwnerReference — Kubernetes-ссылка, по которой сборщик мусора удаляет зависимые объекты. Tracking annotation — связь для учёта Argo. Это разные механизмы. ReplicaSet и Pod принадлежат Deployment через собственную цепочку ownerReferences; Argo обычно управляет Deployment, а не напрямую всеми его Pod. Принудительно добавить Application как владельца чужого Pod означает изменить модель Kubernetes, а не исправить сравнение.

FailOnSharedResource=true останавливает синхронизацию, если целевой объект уже отслеживается другим Application. Это полезная дополнительная проверка, но не реестр всех ручных администраторов, Helm-релизов и операторов. Если объект не имеет Argo tracking, отсутствие конфликта не означает согласие его владельца на захват. Сверьте назначение, имена и существующие метаданные до первого sync.

Способ применения и конфликты полей

Обычное клиентское применение использует сохранённую конфигурацию last-applied. Серверное применение, Server-Side Apply или SSA, ведёт в managedFields принадлежность отдельных полей менеджерам. В Argo 3.5 опция ServerSideApply=true вызывает kubectl apply --server-side --force-conflicts: контроллер способен отобрать конфликтующее поле. Это существенное отличие от осторожного ручного server-side dry-run установки без --force-conflicts.

Сначала решают, кто должен управлять replicas, image или полем оператора. Автоматически отбирать их при каждом цикле — способ устроить борьбу контроллеров. RespectIgnoreDifferences и точечное исключение применяют осознанно и только к нужному пути. Validate=false может пропустить клиентскую проверку неполного документа, но API и admission по-прежнему вправе отказать; отсутствие проверки не делает поле допустимым.

 | Опция | Действие | Риск

 | ServerSideApply=true | Применение с серверным учётом полей и принятием конфликтов в этой версии. | Перехват поля у другого менеджера.

 | Replace=true | Замена либо создание вместо apply; имеет приоритет над SSA. | Полная замена отправляемого описания; неизменяемое поле может привести к отказу. Само Replace=true не обещает delete/create.

 | Force=true,Replace=true | Удаление и создание ресурса. | Потеря идентичности, кратковременный разрыв и возможная потеря данных.

Разобрать владение одним полем

Пусть Git содержит spec.replicas=2, а HorizontalPodAutoscaler, HPA, вычислил три реплики и записал spec.replicas=3. HPA — контроллер изменения масштаба по метрикам; это не отдельный механизм рестарта Pod. Если Argo постоянно возвращает 2, контроллеры спорят об одном поле. Tracking-id отвечает, к какому Application относится Deployment, но не распределяет spec.replicas между управляющими.

При SSA запись metadata.managedFields показывает менеджера и набор управляемых им полей. В имени менеджера нет доказательства доверия; это техническая принадлежность изменения. Обычный конфликт сообщает, что другой менеджер владеет полем. Реализация SSA в выбранном Argo принимает конфликт через force-conflicts, поэтому спор не обязательно проявится как отказ: поле может перейти Argo. Решение принимают до включения selfHeal.

Если число реплик действительно принадлежит HPA, уберите его из желаемого описания по согласованной процедуре владения либо настройте узкое исключение /spec/replicas и его действие при синхронизации. JSON Pointer — запись пути к полю, здесь через spec к replicas. Для ключа с косой чертой внутри имени используется экранирование ~1, для тильды — ~0. Игнорирование всего spec одновременно скрывает изменения образа и пробы; это уже потеря контроля над полезной частью Deployment.

Prune и Delete имеют разный повод

Prune удаляет отслеживаемое, исчезнувшее из желаемого набора при синхронизации. Удаление Application — отдельный повод. Ресурсная опция Prune=false удерживает объект при очистке лишних, Delete=false — при удалении приложения. Значение confirm требует отдельного подтверждения соответствующего удаления; эти настройки нельзя взаимозаменять. Временное удержание старой ConfigMap полезно для расследования, но бессрочное исключение превращает Git в неполное описание.

Финализатор resources-finalizer.argocd.argoproj.io удерживает Application, пока контроллер не удалит управляемые ресурсы; вариант /background выбирает фоновую схему. Наш первоначальный YAML финализатор не содержит. Однако команда app delete по умолчанию выполняет каскадное удаление и способна задать финализатор: нельзя судить о результате CLI только по исходному YAML. Здесь намеренно нет команды удаления рабочего приложения. Сначала выберите, сохраняются ли workloads, секреты и данные, и проверьте фактический объект.

Namespace — ресурс с большим радиусом действия

CreateNamespace=true может создавать целевое пространство, а managedNamespaceMetadata менять его метаданные. Удаление namespace уничтожает все находящиеся внутри объекты, включая созданные другим способом. Поэтому личные namespaces создаёт владелец стенда, проект не разрешает вид Namespace, а установочные сценарии требуют собственную метку существующего argocd. Нельзя стирать общий namespace для исправления одного приложения.

Если финализатор завис из-за недоступного кластера, прежде устанавливают состояние назначения и цель удаления. Удалить строку финализатора — обход ожидания, а не доказательство уборки: живые ресурсы могут остаться. Для восстановления управления сохраняют список идентичностей и метаданных; дальнейшая процедура зависит от того, должны ли эти объекты продолжить работу.

Команды и проверенные формы

Открываемая справка этой главы: argocd app delete. В карточках разобраны назначение, отдельные флаги, сочетания и предел доказательства. Полный путь в исполняемых блоках выбирает проверенную программу; каноническое имя здесь открывает ту же команду в справочнике.

Источники и версия

Управляется уже не один объект

ApplicationSet — API-объект, из параметров и шаблона порождающий несколько Application. Его контроллер согласует эти дочерние объекты; application-controller затем согласует workloads каждого приложения. Успешное вычисление списка не означает доступность Git, разрешённость проекта или готовность Deployment. Изменить дочерний Application вручную часто недостаточно: генератор вернёт поле к своему шаблону.

Генератор list получает явно заданные элементы; Git-генератор читает каталоги или файлы; clusters выбирает зарегистрированные кластеры. Matrix образует сочетания результатов, Merge соединяет по указанным ключам. Два источника по 10 элементов в Matrix могут дать 100 приложений. Прежде разрешения применения посчитайте множество имён и назначений; конфликт имён — ошибка модели, а не повод добавить случайность.

Наш необязательный второй маршрут

Исходный ledger-gitops остаётся тем же. Дополнительный ledger-fleet создаёт только ledger-practice и ledger-review в пространствах gitops-fleet-practice и gitops-fleet-review, под отдельным проектом ledger-fleet. Нельзя направить их в gitops-lab с теми же именами: так два приложения начнут управлять одними объектами. Для fleet используется apps/ledger/base, где namespace отсутствует. Набор overlays/lab с жёстким gitops-lab сюда не подходит: destination.namespace не является универсальной заменой уже указанного namespace каждого документа.

В bootstrap/applicationset.template.yaml включены goTemplate=true и goTemplateOptions=[missingkey=error]. Подстановка {{ .environment }} требует точного существующего ключа; ошибка должна останавливать генерацию, а не давать незаметное пустое имя. Шаблонизация применяется по строковым полям: выражением в строке нельзя произвольно превратить булево поле API в bool. Условия между несколькими полями также нельзя считать единым исполняемым текстовым шаблоном.

spec:
  goTemplate: true
  goTemplateOptions: [missingkey=error]
  generators:
    - list:
        elements:
          - environment: practice
            namespace: gitops-fleet-practice
          - environment: review
            namespace: gitops-fleet-review
  syncPolicy:
    applicationsSync: create-update
    preserveResourcesOnDeletion: true

Это фрагмент, не полный объект для apply. Полный шаблон требует собственного URL/коммита и разрешающего проекта. Конфигурацию fleet готовят отдельным набором файлов, сохраняют в своём Git и сначала просматривают. Локальная структурная проверка книги проверяет типы, фиксированный путь и отсутствие namespace в базе; она не исполняет настоящий ApplicationSet controller. Команда argocd appset generate требует сервер, даже если исходный файл расположен локально.

Каждая строка вычисляется независимо: range, начатый в одном поле, не может закончиться в другом. normalize приводит строку к допустимому имени DNS, но не гарантирует уникальность двух разных входов после преобразования. Для необязательного параметра официальный пример использует {{ dig "nameSuffix" "" . }}: функция сама выполняет поиск с заданным запасным значением. Простое чтение отсутствующего ключа до передачи результата в default при missingkey=error уже может завершиться ошибкой; наличие default в конце цепочки не отменяет порядок вычисления.

Политики двух уровней

ApplicationsSync=create-update позволяет создавать и обновлять дочерние Application и запрещает их обычное удаление контроллером ApplicationSet. Это не автоматическая запретительная политика для Kubernetes garbage collector: дочерние объекты имеют ownerReferences на набор. При удалении самого ApplicationSet сборщик мусора может удалить детей независимо от этой политики. Отдельное preserveResourcesOnDeletion=true не добавляет детям ресурсный финализатор Argo, чтобы удаление Application не каскадировало workloads через него.

При preserveResourcesOnDeletion=false обычно формируется цепь: удалён ApplicationSet, Kubernetes удаляет дочерний Application, его финализатор удаляет прикладные ресурсы. Удаление набора с cascade=orphan разрывает первую связь, но уже оставшиеся у детей финализаторы не исчезают: последующее удаление ребёнка ещё способно удалить workloads. Перед уборкой проверьте реальные metadata.ownerReferences и finalizers каждого уровня.

Автоматическая синхронизация workloads задаётся в template.spec.syncPolicy дочернего Application. Политика ApplicationSet, управляющая существованием Application, её не заменяет. В нашей заготовке automated.enabled=false: генерация нескольких приложений не должна неожиданно начать несколько поставок. Временно выключить auto только в дочернем объекте ненадёжно без согласованного исключения изменений: родитель способен вернуть поле.

Область политики тоже проверяется. В стандартном контроллере 3.5.6 глобальный --policy по умолчанию пустой, поэтому разрешено переопределение через applicationsSync. Если администратор явно задал --policy, разрешение --enable-policy-override по умолчанию становится false: поле отдельного ApplicationSet может не определять поведение. Проверьте фактические аргументы контейнера, переменные окружения и параметры controller ConfigMap. В одном описании help осталось имя allow-policy-override, но зарегистрированный флаг называется enable-policy-override; ориентируются на регистрацию и реальный бинарник.

Перед удалением проверить три конкретных объекта

Сначала прочитайте ApplicationSet ledger-fleet, затем два дочерних Application ledger-practice и ledger-review. У ребёнка metadata.ownerReferences указывает UID набора, а metadata.finalizers показывает, будет ли Argo дополнительно очищать workloads. Не подставляйте UID из другого создания с тем же именем. Проверка должна касаться фактического объекта после работы контроллера, а не только шаблона в Git.

При create-update удаление элемента из list не является разрешением ApplicationSet-controller удалить ранее созданного ребёнка. Поэтому сохранённый Application может продолжить управлять своим Deployment. Но удаление самого набора включает Kubernetes garbage collector по ownerReferences. PreserveResourcesOnDeletion=true меняет добавление ресурсного финализатора детям; это не общий запрет на любой delete. Операция orphan сохраняет детей, однако не снимает с них уже существующие финализаторы.

Для изменения состава fleet заранее запишите ожидаемые имена и назначения. AppProject разрешает источник по правилам sourceRepos; repo-server должен установить соединение, удостоверить сервер и предъявить подходящие учётные данные. Затем он должен найти нужную ревизию и путь. «Репозиторий запрещён», «сертификат неизвестен», «отказ аутентификации» и «ревизия не существует» имеют разные причины. Отключение проверки TLS не исправляет неправильную политику проекта и лишает соединение удостоверенной стороны.

HTTPS проверяет цепочку сертификата и имя хоста; SSH проверяет ключ хоста через known_hosts. CA — удостоверяющий центр, подписывающий сертификат; добавлять следует доверенный корень или согласованную цепочку, а не случайный сертификат, скачанный через уже недоверенное соединение. SSH known_hosts содержит открытые ключи сервера, не закрытый ключ пользователя. Отпечаток проверяют через независимый доверенный канал до подключения.

Где хранятся секреты

Декларативная запись репозитория — Kubernetes Secret в пространстве Argo с меткой argocd.argoproj.io/secret-type=repository. Шаблон учётных данных repo-creds позволяет переиспользовать набор для префикса URL; выбирается наиболее специфичный подходящий префикс. Собственные учётные данные записи репозитория имеют значение: не рассчитывайте, что подходящий шаблон молча заменит их. Project-scoped запись ограничивается проектом, но Kubernetes Secret всё равно требует строгих прав чтения.

Base64 в поле data — кодирование, не шифрование. Токен в открытом Git или в командной строке может попасть в историю shell, журнал и список процессов. Учебные файлы содержат только фиктивный адрес и публичную политику; реальные ключи и пароли держат в private либо доставляют согласованным менеджером секретов. Экспорт управляющего контура тоже содержит эти данные и наследует тот же уровень конфиденциальности.

Проверить путь полномочий до ротации

 | Участок | Материал | Кто его использует

 | CLI → Argo API | Пользовательский сеанс и доверенный сертификат Argo. | Клиент и argocd-server.

 | Repo-server → Git HTTPS | CA репозитория и его токен либо другой настроенный способ входа. | Repo-server; браузер пользователя не передаёт ему свой Git-сеанс.

 | Repo-server → Git SSH | Открытый ключ хоста в known_hosts и отдельный закрытый ключ клиента. | SSH-клиент repo-server.

 | Controller → целевой Kubernetes | Внутренняя служебная учётная запись либо зарегистрированный кластерный доступ. | Application-controller.

 | Узел → реестр образов | Доверие реестру и imagePullSecret выбранного namespace. | Kubelet и среда контейнеров на узле.

При ротации Git-токена проверьте новую запись с конкретной ревизией, затем убедитесь, что она используется серверным путём, и лишь потом отзывайте старую. Тёплый кэш манифестов может скрыть неработающий новый доступ. Проверка должна потребовать реального чтения нужного источника; один прежний Healthy этого не устанавливает. Отдельно сохраните время и результат отзыва. Значения Secret в журнал приёмки не включают.

Для публичного собственного HTTPS-репозитория достаточно URL и действующей цепочки TLS. Три уровня решения

Аутентификация устанавливает личность пользователя или токена. Авторизация решает, может ли эта личность выполнить действие. Argo RBAC — ролевая политика для API Argo; Kubernetes RBAC отдельно ограничивает права служебных учётных записей и зарегистрированных кластерных доступов. Успешный вход не означает право sync, а разрешённый sync не гарантирует, что Kubernetes примет нужный вид объекта.

SSO, единый вход, передаёт личность и группы от настроенного поставщика через OIDC или Dex. OIDC — протокол удостоверения личности поверх OAuth2; Dex выступает посредником для поддерживаемых источников. Issuer обозначает доверенного издателя утверждения о личности, audience — получателя, для которого оно выпущено. Claims — поля этого утверждения, например идентификатор пользователя и группы. Сервер проверяет подпись, издателя, получателя и срок действия, а затем использует проверенные значения для правил доступа. Название группы из произвольного неподписанного ввода не становится полномочием. Локальный admin нужен для первого входа; после проверки независимой административной учётной записи его обычно отключают по своей процедуре.

Читать CSV как правило

Файл rbac/policy.csv — собственная небольшая политика. Строка p связывает роль, ресурс Argo, действие, объект и эффект allow/deny; строка g связывает субъекта с ролью. Объект applications записывается как проект/имя, здесь ledger/ledger-gitops. Это не путь файловой системы и не Kubernetes namespace. Значение default role даёт базовые права всем аутентифицированным пользователям, поэтому широкая policy.default способна отменить смысл вашей узкой роли.

p, role:observer, applications, get, ledger/*, allow
p, role:deployer, applications, get, ledger/*, allow
p, role:deployer, applications, sync, ledger/ledger-gitops, allow
p, role:deployer, applications, delete, ledger/*, deny
g, reader, role:observer
g, releaser, role:deployer

Чтение get разрешено обеим ролям для всех приложений проекта ledger по шаблону ledger/*. Синхронизация sync разрешена deployer только для ledger/ledger-gitops; delete запрещён ему для всего ledger/*. Звёздочка меняет область правила, а не имя namespace.

Совпадение зависит от настроенного режима glob/regex. При glob разделитель / не делает сегменты автоматически безопасными; задавайте полную проверяемую форму. Явный deny имеет приоритет среди правил. Для действий над дочерними ресурсами в 3.x изменялась модель наследования update/delete; не переносите широкую политику 2.x без проверки. Get, sync, override, exec и logs — разные действия. Право override способно подменять локальную сторону операции и требует отдельного решения.

Почему default allow не отменяется персональным deny

Сначала учитываются базовые права policy.default. Если эта роль разрешает действие, последующее deny пользователя не отнимает уже выданный базовый доступ. Поэтому role:readonly для всех и персональный запрет get не создают закрытый проект. При включённом users.anonymous.enabled те же базовые права доступны даже без входа. В нашем файле role:none не содержит разрешающих правил; нужные разрешения выдаются отдельным ролям.

После проверки базового доступа Argo сопоставляет субъект и его группы с персональными и ролевыми правилами. Среди применимых правил этого этапа deny выигрывает у allow; порядок строк CSV не задаёт «последнее правило побеждает». Для reader сначала находится g→role:observer, затем get соответствует ledger/*. Для sync разрешающей строки нет, поэтому результат No. Для releaser найдено sync allow, но delete попадает под явный deny.

Проверяйте отдельно get, sync, logs и exec: чтение Application не разрешает запуск команды в контейнере. В режиме приложений вне namespace Argo меняется и форма объекта политики на проект/namespace-приложения/имя. Наши двухчастные ledger/ledger-gitops рассчитаны на Application в argocd. Правила закреплены в RBAC 3.5.6.

Настоящая локальная проверка с ограниченной границей

argocd admin settings rbac validate проверяет синтаксис, argocd admin settings rbac can вычисляет решение. В 3.5.6 даже --policy-file строит Kubernetes REST-конфигурацию. Поэтому пустой изолированный kubeconfig и фиктивный локальный --server с токеном нужны для предсказуемой настройки клиента; реальный запрос в выбранном файловом пути не выполняется. Labs/check.py подтверждает это ловушкой loopback: число обращений равно 0.

(
  set -euo pipefail
  cd "$LAB_ROOT/work"
  mkdir -p "$LAB_ROOT/private/offline-rbac"
  : > "$LAB_ROOT/private/offline-rbac/empty-kubeconfig"
  "$ARGOCD_BIN" --config "$LAB_ROOT/private/offline-rbac/client" \
    admin settings rbac validate --policy-file rbac/policy.csv \
    --kubeconfig "$LAB_ROOT/private/offline-rbac/empty-kubeconfig" \
    --server http://127.0.0.1:1 --token offline-dummy
)

Это отдельный подпроцесс Bash: ошибка останавливает его, а не закрывает интерактивный shell. Порт 1 выбран без предположения о работающем сервисе; значение токена не секрет. Автоматический тест использует выделенный динамический порт и считает обращения. В режиме без --policy-file команда уже может читать ConfigMap настоящего кластера: там нужны явный kubeconfig, правильный --context и реальные права.

 | Локальное решение | stdout | Код

 | reader/get ledger/ledger-gitops | Yes | 0

 | reader/sync того же | No | 1

 | releaser/sync того же | Yes | 0

 | releaser/delete того же | No | 1

 | releaser/sync другого проекта | No | 1

--use-builtin-policy=false исключает встроенные правила из изолированной проверки; в реально установленной системе нужно проверить и базовую роль, и группы, и проектные роли. Для проверки ожидаемого deny оболочка должна явно принять код 1, а не запускать следующий опасный шаг после любого отказа. -- завершает разбор флагов: субъект --reader после него остаётся операндом. Путь с пробелами передаётся одним аргументом в кавычках.

Три разных context

Глобальный --argocd-context выбирает сохранённую сессию Argo в файле --config. Глобальный --kube-context относится к Kubernetes при core/port-forward режимах. Локальный --context команд admin выбирает Kubernetes-контекст их клиента. У admin также локальный --server означает Kubernetes API, затеняя глобальный --server адреса Argo. Используйте каноническую форму с локальными флагами после конечной команды: так смысл виден и человеку, и справочнику.

Отрицательная проверка настоящего CLI: --context handbook-admin перед app get отвергается как unknown flag с кодом1 ещё до подключения. В этом маршруте нужен --argocd-context либо применимый глобальный --kube-context; локальный admin --context не становится универсальным только от одинакового слова «контекст».

У обеих конечных команд argocd admin settings rbac validate и argocd admin settings rbac can локальный --kubeconfig принимает путь к существующему Kubernetes-файлу, а --context — имя уже существующего контекста внутри него. Это не имя файла и не сохранённая сессия Argo. В автономном примере выше файл пуст, поэтому --context опущен; при указании неизвестного имени фабрика клиента должна отказать. Для именованного личного файла используйте уже подготовленные LAB_KUBECONFIG/LAB_CONTEXT, располагая эти флаги после validate или can.

Каноническая позиция после конечной команды делает значение явным. Настоящий Cobra допускает некоторые локальные флаги и раньше, но читательский распознаватель ещё не обещает верный смысл всех таких форм. В частности, ранний --server перед admin может подсветиться как глобальный адрес Argo, хотя нативная конечная admin-команда использует его как адрес Kubernetes. Для упражнений сохраняйте показанную локальную позицию; наличие подсветки не заменяет разбор реального CLI.

Токены и кластерные права

Проектная роль может выдать ограниченный JWT-токен, argocd proj role create-token; срок действия задаётся --expires-in. JWT — подписанное утверждение, не зашифрованный контейнер для секрета. Сохраните токен приватно, ограничьте срок и проверьте отзыв. Восстановление argocd-secret влияет на ключи подписи, сессии и доверие; потеря ключа не лечится копированием случайного нового секрета.

argocd cluster add способен создавать служебную учётную запись и широкие Kubernetes-роли в выбранном кластере. Здесь эта команда не исполняется: используется внутреннее назначение и заранее проверенные полномочия личного контура. На внешнем кластере минимальный набор прав подбирают по видам и пространствам приложения, отдельно от удобства регистрации. Нельзя считать доступ к UI достаточной изоляцией от привилегированного назначения.

Сначала определить потерю

История приложения хранит успешные синхронизации и их входы, но не является снимком дисков приложения. Откат, rollback, применяет прежнюю цель из истории. Возврат Git новым коммитом сохраняет декларативную причину изменения и обычно лучше сочетается с GitOps. Удалённый файл, изменённая схема БД и потерянный приватный ключ требуют разных средств восстановления; ни один номер истории не возвращает все эти байты.

Для Application с включённой автоматической синхронизацией штатный rollback запрещён. Выключить auto недостаточно, если ApplicationSet или родитель тут же вернёт поле. Согласуйте владельца конфигурации, остановите изменение источника, оцените совместимость старого бинарника с новыми данными и только затем выбирайте историю. argocd app history показывает записи, argocd app rollback требует конкретный идентификатор истории и сервер. Автор их на кластере не выполнял.

Что действительно нужно сохранить

Argo CD не требует SQL-базы для собственного состояния. Kubernetes API/etcd хранит Application, AppProject, ApplicationSet, ConfigMap и Secret управляющего пространства. Redis служит кэшем и координационной частью поставки, его содержимое не заменяет первичные объекты. Git хранит намерение только в той мере, в какой нужная конфигурация действительно туда записана; вручную добавленный токен репозитория из Git заново не появится.

Резерв включает конфигурацию и секреты Argo, ключи подписи/серверные значения argocd-secret, учётные данные Git и зарегистрированных кластеров, доверенные CA/SSH-ключи хостов и настройки SSO. При внешнем менеджере секретов нужны также его доступ, политика и восстановимая версия значения. Для приложения отдельно нужны PVC/БД, согласованный способ снимка и прикладная проверка. Снимок etcd владельца Kubernetes — отдельная процедура с собственными правами и совместимостью.

Экспорт не считать готовым резервом по одному коду

argocd admin export читает выбранный namespace Kubernetes через kubeconfig; --argocd-context для этой задачи не заменяет локальный --context. --namespace обязателен по смыслу процедуры: неверное пространство способно дать неполный или не тот экспорт без ожидаемого отказа. Выход содержит секреты, поэтому каталог и файл имеют закрытые права, хранение и передача зашифрованы по выбранной политике.

(
  set -euo pipefail
  umask 077
  set -o noclobber
  : "${LAB_KUBECONFIG:?}" "${LAB_CONTEXT:?}" "${LAB_ROOT:?}" "${ARGOCD_BIN:?}"
  test -f "$LAB_KUBECONFIG"
  test ! -e "$LAB_ROOT/private/argocd-export.yaml"
  "$ARGOCD_BIN" admin export --kubeconfig "$LAB_KUBECONFIG" \
    --context "$LAB_CONTEXT" --namespace argocd \
    > "$LAB_ROOT/private/argocd-export.yaml.part"
  test -s "$LAB_ROOT/private/argocd-export.yaml.part"
  mv "$LAB_ROOT/private/argocd-export.yaml.part" "$LAB_ROOT/private/argocd-export.yaml"
)

Это образец первого экспорта в новый файл для собственного установленного сервера, не авторский результат. Повторный резерв получает новое явное имя: существующий файл не перезаписывается. Ненулевой export не публикует файл как готовый; .part остаётся для приватной диагностики. Далее владелец проверяет список видов, namespace, присутствие требуемых Secret и читаемость зашифрованной резервной копии. Непустой файл всё ещё может быть неполным. Контрольная сумма проверяет байты, а не достаточность восстановления.

Опись резерва и точка согласованности

Перед экспортом составьте приватную опись: какие Application/ApplicationSet и AppProject существуют, какие регистрации репозиториев и кластеров нужны, где лежат CA, known_hosts и настройки входа. Запишите версию установки, полный коммит конфигурации и UID исходного kube-system. В описи достаточно имён и назначений; значения Secret остаются в защищённом резерве. После экспорта сопоставьте ожидаемый состав с документами файла. Если объект отсутствует, его надо восстановить отдельным согласованным способом; добавление случайного Secret с похожим именем не воспроизводит ключ.

Export читает несколько объектов и не создаёт общую транзакцию Git, Kubernetes и БД приложения. Если во время чтения меняются токен, ApplicationSet и цель приложения, резерв может сочетать разные моменты. Для воспроизводимого учебного опыта сначала остановите изменения конфигурации и сохраните время начала/конца. Данные приложения резервируются по собственному протоколу: для PostgreSQL это согласованная копия и необходимый WAL, для файлов — выбранная точка сохранения и проверка чтения.

Карантин нужен даже для корректного резерва: восстановленные cluster Secrets могут снова дать доступ к старому назначению. Отключённый автоматический sync не отменяет уже сохранённый запрос operation, удаление с финализатором или работу ApplicationSet. До включения application-controller просмотрите также operation, metadata.deletionTimestamp и finalizers каждого восстановленного Application. Возврат notifications-controller откладывается до проверки получателей и разрешённых каналов.

Восстанавливать сначала в изоляции

argocd admin import изменяет объекты назначения и не является безопасной проверкой чтения файла. Сначала поднимают изолированный контур той же закреплённой версии, явно выбирают новый Kubernetes-контекст, блокируют опасные назначения и автоматическую синхронизацию. Восстановленный Application с прежним адресом сервера/пространством назначения и действующими учётными данными способен начать менять настоящий кластер; отсутствие привычного UI не делает его безвредным.

Конкретный карантин предшествует импорту. Подготовьте отдельный новый личный кластер, запишите его адрес API и UID пространства kube-system через независимо выбранный доступ. Установите тот же 3.5.6 без приложений и явно пометьте собственный namespace argocd как handbook.example/restore=quarantine. Сценарий карантина требует RESTORE_KUBECONFIG, RESTORE_CONTEXT, RESTORE_EXPECTED_SERVER и RESTORE_EXPECTED_CLUSTER_UID; сравнивает адрес API, новый UID и UID исходного кластера. Если исходный кластер недоступен при аварии, передайте SOURCE_CLUSTER_UID из заранее сохранённого доверенного журнала: сценарий тогда не читает старый API. Если журнал отсутствует, сначала независимо установите личность прежней и новой цели; придуманная строка не является проверкой. Совпадение имени context само по себе не является проверкой изоляции.

До импорта остановить application-controller (StatefulSet), applicationset-controller и notifications-controller (Deployment), задав replicas=0, и дождаться отсутствия их Pod. Если они снова появляются из-за другого владельца конфигурации, импорт не начинать. Сценарий проверяет именно исчезновение Pod, не только принятие scale.

Владелец дополнительно ограничивает сетевой доступ новой среды к старым назначениям и сохраняет независимый Kubernetes-доступ. Notifications-controller также остановлен: восстановленные аннотации/состояния и конфигурация уведомлений не должны отправить внешние сообщения. Импорт выполнять только с новыми явными kubeconfig/context/namespace; сам сценарий карантина import не вызывает.

При остановленных контроллерах проверить все Application destination.server/name/namespace, все cluster Secrets с удалёнными учётными данными, AppProject destinations, автоматические политики и шаблоны ApplicationSet. Старые удалённые доступы не должны оставаться действующими случайно.

Сначала исправить владельцев и назначения под тестовую среду, отключить автоматическую синхронизацию и генерацию лишних детей; ещё раз проверить, что все три контроллера не запущены. Затем разрешить только строго выбранное тестовое приложение. Запуск application-controller отдельно от генератора позволяет не породить весь прежний набор сразу.

После проверки тестового источника, синхронизации и HTTP решать о поэтапном возврате остальных приложений. Контроллеры не включаются автоматически из нашего сценария.

Проверка резерва включает вход с нужной учётной записью, доверие к Git, доступность закреплённых ревизий, корректные ограничения проектов, назначение кластеров и намеренно контролируемую синхронизацию тестового приложения. Измеряют время от начала до подтверждённого HTTP-ответа и допустимый интервал потери данных. Время загрузки Pod не равно полному времени восстановления услуги. Отдельно проверяют отзыв старых токенов и то, какие сессии должны остаться действительными после восстановления ключей.

Обновление версии и самоуправление

Перед обновлением читают руководство перехода выбранной пары версий, совместимость Kubernetes и изменения CRD/RBAC/рендереров. Новый Helm или Kustomize способен изменить целевые документы без коммита приложения; сравнение эталонных рендеров — отдельный обязательный вход проверки. Обновление CRD и последующий возврат Deployment не гарантируют обратную совместимость сохранённых объектов.

Если Argo управляет собственной установкой, ошибочный источник может лишить инструмента восстановления. Сохраняйте ручной закреплённый комплект и независимый Kubernetes-доступ владельца, затем отдельно проектируйте передачу владения. Не включайте install.yaml этой книги в произвольный Application поверх ручной установки: это миграция управления и полей, требующая предварительного сравнения. Учебная первая установка сознательно остаётся отдельным основанием.

Источники и версия

Разложить задержку

Время от Git-коммита до готового HTTP-ответа складывается из обнаружения ревизии, очереди, получения Git, рендеринга, сравнения, применения API, ожидания Kubernetes и прикладной проверки. Один быстрый helm template не измеряет весь путь. Накапливающаяся очередь может давать высокую задержку при низком среднем времени отдельного вычисления; тайм-аут клиента не доказывает перегрузку repo-server.

Кэш repo-server хранит результаты генерации и данные репозиториев; кэш кластера уменьшает повторное чтение API. Redis ускоряет обмен и хранение кэшированных результатов, но не становится первичной SQL-базой. Жёсткое обновление чаще заставляет заново вычислять результат и может увеличить нагрузку. Повсеместный hard-refresh при каждой ошибке скрывает причину и меняет измеряемый режим.

Метрики с единицами

В 3.5 argocd_app_reconcile — гистограмма времени согласования в секундах; argocd_git_request_duration_seconds — гистограмма времени Git-запросов. argocd_app_k8s_request_total считает запросы Kubernetes, argocd_git_request_total — Git. argocd_repo_pending_request_total, несмотря на окончание total, документирован как текущее измерение, gauge: текущее число запросов, ожидающих блокировку репозитория. Тип проверяют по описанию и /metrics, а не угадывают по имени.

Гистограмма хранит корзины, сумму и число наблюдений; 95-й процентиль, p95, оценивают по скорости изменения корзин за выбранный интервал. Оценка p95 описывает границу, ниже которой находится около95% наблюдений, при выбранной точности корзин. Счётчик после перезапуска может сброситься, поэтому разность абсолютных показаний не всегда корректна. Сопоставляйте время, метки приложения/кластера и перезапуски компонентов. Endpoint метрик доступен отдельным Service/портам; публиковать его наружу без ограничения доступа не требуется для этого практикума.

Насыщение разных компонентов

Repo-server расходует CPU на генерацию, память на большие деревья и процессы, временный диск на checkout и зависимости. Увеличение числа параллельных генераций сокращает очередь только пока хватает этих ресурсов. Большой монорепозиторий может сериализовать работу на блокировке; поток наблюдения и кэш не делают бесконечные Git-файлы бесплатными. Отдельные источники, закреплённые зависимости и детерминированная генерация часто полезнее случайного увеличения всех лимитов.

Application-controller имеет очереди проверки состояния и операций. Больше работников может упереться в лимиты Kubernetes API, сеть и память кэша. Шардирование распределяет кластеры между экземплярами контроллера; это не универсальное разбиение каждого Application одного огромного кластера поровну. Алгоритм и выбранные реплики фиксируют по фактической конфигурации версии. Если один кластер доминирует, сначала измеряют его API и размер наблюдаемого множества.

Отделить очередь от медленного исполнения

Рассмотрим расчётную модель одного работника: обработка занимает 0,2 секунды, значит его предельная пропускная способность — 1/0,2=5 задач/с. Если устойчиво приходят 8 задач/с, очередь растёт примерно на 3 задачи/с, то есть на 180 за минуту. Даже после прекращения входного потока для этих 180 задач потребуется ещё около 36 секунд работы. Это арифметика модели с постоянным временем, без объединения событий; реальные очереди контроллера объединяют повторы и требуют наблюдения.

Увеличение работников с одного до двух в этой модели даёт вычислительную ёмкость 10 задач/с. Но при общем ограничении Git или Kubernetes API в 5 задач/с удвоение работников только увеличит одновременные ожидания и память. На сервере сопоставляйте размер очереди и возраст задания со временем самого reconcile, ожиданием блокировки репозитория, ошибками API и CPU/RSS. Для большого кластера память кэша зависит от числа и размеров наблюдаемых объектов, а не только от количества Application.

Для сравнения снимите одинаковое окно до и после одного изменения. Counter Git-запросов переводят в запросы/с; gauge ожидающих запросов читают как число в моменте; гистограмму времени — в секундах за окно. Суммирование процентилей разных процессов не даёт процентиль общего пути. Внешняя отметка «коммит C2 доступен» и подтверждённый HTTP-ответ полезны для измерения всей доставки, а метрики компонентов объясняют, где накопилась задержка.

Высокая доступность не равна двум Pod

HA, высокая доступность, — способность сохранить услугу при оговорённом отказе. Официальная HA-поставка отличается компонентами, Redis-архитектурой и распределением реплик. Её требования к размещению, в том числе правилам разнесения Pod, anti-affinity, и числу узлов, надо проверить до применения: три Pod на одном узле не переживают его потерю. Установка без HA в книге не превращается в HA от увеличения replicas у server.

Repo-server может масштабироваться горизонтально, но кэши и зависимости остаются входами отказа. API-server Argo должен иметь согласованные секреты и настройки. Контроллер использует лидерство/распределение по своей модели. NetworkPolicy, доступ к Redis, DNS, Git и API должны соответствовать топологии; недоступность одного канала часто выглядит как зависшее приложение. Автоматическое восстановление Pod не доказывает восстановление доверенных ключей и внешнего Git.

Три значения «без сети»

Локальная проверка файлов без Argo API, продолжение работы уже созданных Pod при потере Git и установка в изолированной сети — разные режимы. В первом достаточно закреплённых рендереров и исходников. Во втором работающие ресурсы остаются под Kubernetes, но новые сравнения и поставки ограничены доступностью источника. В третьем нужны все файлы, образы, доверие, DNS и внутренние сервисы; наличие одного argocd-linux-amd64 не делает комплект автономным.

Каталог LAB_ROOT постоянен и не находится в /tmp. В нём отдельно сохраняются tools, bundle, work, private, evidence. Временный каталог автоматического теста допустим потому, что не содержит реального кластера и не объявляется постоянным стендом. Потеря каталога work не должна означать потерю неопубликованных изменений; коммиты и рабочие изменения сохраняет владелец собственной копии. Приватные credentials не попадают в публичный архив книги.

Подготовщик комплекта

Bundle-lock.json фиксирует URL и SHA для CLI, install.yaml, Helm 4.2.1 и Kustomize 5.8.1. Prepare_bundle.py скачивает их только в новый пустой каталог, потоково сверяет байты и переименовывает файл лишь после успеха. Повторный --verify-only не качает и не исполняет файл. Несовпадение хеша, незавершённая загрузка и непустой каталог имеют явный отказ; сценарий установки сам вызывает проверку до изменений API.

python3 "$LAB_ROOT/work/prepare_bundle.py" \
  --output "$LAB_ROOT/bundle" --verify-only

Сам подготовщик не проверяет подписи cosign и не скачивает образы. Это честная граница этой редакции. Манифест содержит Argo, Dex и Redis, дополнительно нужны образ ledger-api и образ необязательного hook. Для каждой архитектуры сохраните digest, слои, порядок загрузки и доверенный способ доставки. Не смешивайте сумму Helm-архива с digest контейнерного образа: это разные байтовые объекты.

Git и зависимости внутри изолированной сети

Зеркало Git должно сохранять доступность выбранного полного коммита и всех нужных объектов; наличие имени ветки без объекта не достаточно. Repo-server должен достигать зеркала по разрешённому протоколу с внутренними CA/known_hosts. Замена URL требует явного изменения AppProject и Application, а не только DNS-обмана. Часы сервера влияют на TLS и сроки токенов; правильные байты при неверном времени могут оставаться недоступными.

Helm dependency, плагины и удалённые базы Kustomize тоже требуют предварительной доставки. Установка из локального install.yaml всё равно заставит kubelet получать образы, если они не загружены в доступный реестр или на нужные узлы. ImagePullPolicy и архитектура важны для фактического выбора; случайный образ с тем же тегом на одной машине не даёт воспроизводимого результата всего кластера.

Проверить комплект холодным стартом

Опись автономного комплекта должна сопоставлять файл или образ с потребителем. install.yaml читает kubectl, но образы Argo/Dex/Redis получает каждый нужный узел. Исходные Git-объекты читает repo-server; OCI-слои образа приложения получает среда контейнеров. Сертификаты сервера Git нужны repo-server, а сертификаты реестра — узлам. Наличие каждого элемента в одной папке ещё не подключает его соответствующему процессу.

Сначала подтвердите доступность полного коммита и зависимостей внутри выбранной сети. Затем в отдельном разрешённом опыте проверьте запуск при пустых кэшах инструментов и узлов. Тёплый стенд способен работать за счёт давно сохранённого образа, хотя восстановить его после потери узла уже нечем. Для каждой архитектуры учитывают свои manifest/digest и слои; архив amd64 не становится образом arm64 от изменения имени файла.

Что происходит при разрыве связи

Недоступный Git не останавливает уже работающий Deployment сам по себе. Controller может иметь прежние данные в кэше, но это не разрешение обещать бесконечную автономную сверку: срок кэша, рестарт компонентов и доступность ревизии меняют ситуацию. Ошибка генерации или чтения источника должна стать ошибкой сравнения, а не допустимым пустым набором для очистки. Включать allowEmpty в ответ на недоступность Git особенно опасно по смыслу политики.

При недоступном Kubernetes API Argo не знает достоверное новое состояние назначения. Старые показания UI не равны текущей готовности; сохраните время наблюдения. При отказе Redis возможны повторные вычисления и временные сбои, но резервировать только Redis бессмысленно для восстановления конфигурации. При утрате Kubernetes/etcd требуется восстановить первичные объекты, ключи и доступы, а не искать SQL dump несуществующей базы.

Автономная проверка, которую можно повторить

После однократной доверенной доставки инструментов labs/check.py не обращается к Argo/Kubernetes и не делает Git commit/push. Он выполняет настоящие CLI-проверки политики, рендеринг, структурные схемы и тест Go-сервиса; ловушка соединения подтверждает 0 запросов файлового RBAC-пути. Отдельные fake-client тесты проверяют остановку Bash-сценариев при отказе первого kubectl, но не моделируют готовность настоящего кластера.

Сохраните журнал версий, контрольные суммы, локальный целевой YAML и результаты. Для доказательства полной автономной установки нужен другой опыт в собственном изолированном кластере: запрет внешнего трафика, установка из внутреннего комплекта, рестарт с пустыми кэшами, восстановление из резерва и прикладной HTTP-тест. Здесь он описан как следующий этап, не отмечен как исполненный.

Установите, какой CLI и сервер используются, какой --config хранит сессию Argo и какие LAB_KUBECONFIG/LAB_CONTEXT выбирают Kubernetes. Две команды с одинаковым именем приложения на разных серверах — два разных опыта. Запишите время и версию; старое наблюдение кэша не выдавайте за актуальную готовность. В приватном журнале исключите токены, содержимое Secret и парольные аргументы.

"$ARGOCD_BIN" version --client --short
"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" context
"$ARGOCD_BIN" --config "$LAB_ROOT/private/argocd-config" \
  --argocd-context handbook app get ledger-gitops --refresh --output yaml

argocd context перечисляет либо переключает сохранённые подключения по грамматике команды; --config нужен, чтобы не читать случайную конфигурацию HOME. argocd app get получает спецификацию и наблюдение; --hard-refresh дополнительно очищает целевой кэш, поэтому его вводят после сохранения исходной картины. argocd app list полезен для отбора --project ledger, но отсутствие строки может означать ограничение RBAC, а не удаление Deployment.

 | Нарушенная граница | Проверка | Чего избегать

 | Клиент→Argo API | Адрес, локальный канал, сертификат, срок сеанса, Argo RBAC. | Не отключать TLS ради маскировки неверного имени.

Первые данные, потом действие

kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" \
  -n gitops-lab get deployment,pod,service,configmap
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" \
  -n gitops-lab describe deployment ledger-gitops
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" \
  -n gitops-lab get events --sort-by=.metadata.creationTimestamp

Describe показывает условия и события конкретного ресурса. Журналы приложения, repo-server и application-controller отвечают на разные вопросы; используйте фактическое имя Pod и контейнера из предыдущего get, не вставляйте выдуманный суффикс. Events имеют срок хранения, а logs --previous полезен только при сохранённом предыдущем контейнере. Сначала сохраните необходимое, потом перезапускайте.

При ComparisonError ищут источник и генерацию; при Forbidden — реальную личность и правило нужного API; при Synced/Degraded — готовность и события ресурса. Ошибка сертификата Git и TLS браузера Argo относятся к разным соединениям. Нулевой код локального RBAC validate подтверждает синтаксис файла, а не права текущего токена на установленном сервере.

Неудачная операция и продолжающееся исполнение

argocd app terminate-op прекращает операцию Argo, но не отменяет уже применённый ConfigMap или внешний эффект hook. Удалить неготовый Pod означает дать Deployment создать следующий по тому же неисправному шаблону. Изменить Git и дождаться новой цели обычно точнее, чем многократно нажимать sync на том же ошибочном сочетании. Повтор с retry имеет смысл при временном отказе и безопасном повторении действий.

Для старого ConfigMap, лишнего после смены хеша, отдельно проверяют tracking-id, ссылки Pod и план prune. Для зависшего удаления — финализатор и доступность назначения. Снятие финализатора обрывает ожидание, но может оставить живые ресурсы; это должно быть осознанным изменением процедуры, а не первым универсальным лечением.

Как читать авторские результаты

Реальный results.json содержит локальные версии, группы проверок, наблюдённое число запросов и измерение Kustomize. Fake kubectl тесты проверяют управление Bash: четыре сценария прекращаются на первом отказе с кодом 43 и не доходят до мутации или login. Они не создают поддельный успешный кластер. Проверка upstream CRD через jsonschema не исполняет admission, defaults, CEL и правила проектов.

При расширении своего стенда добавляйте в evidence отдельные записи для установки, чтения источника, server-side diff, sync, готовности, HTTP, восстановления и нагрузки. Только реально выполненные пункты получают отметку исполнения. План аварийного опыта и ожидаемый вывод полезны для учёбы, но должны оставаться помеченными ожиданиями, пока собственное наблюдение не сохранено.

Команды и проверенные формы

Открываемая справка этой главы: argocd app list, argocd app terminate-op. В карточках разобраны назначение, отдельные флаги, сочетания и предел доказательства. Полный путь в исполняемых блоках выбирает проверенную программу; каноническое имя здесь открывает ту же команду в справочнике.

Запишите версии клиента/сервера, готовые компоненты и выбранные contexts без токенов. Ошибка TLS не решается привычным --insecure.

Если образ ещё не получен в предыдущем томе

Этот необязательный путь нужен только владельцу личной Linux/amd64 VM с уже установленными Go 1.27.3, C-инструментарием для race detector и Docker Engine. Установку этих средств выполняют по томам Go и Docker до упражнения. GO_BIN — абсолютный путь проверенного Go; LAB_DOCKER_CONTEXT — заранее проверенный Docker-контекст своего движка. Рецепт не устанавливает Docker и не выбирает случайный текущий движок. При готовом ledger-api:0.1.0 из Kubernetes этот блок пропускают и используют прежний артефакт.

Самостоятельная сборка получает отдельный тег ledger-api:argocd-local-1, чтобы не переписать 0.1.0 другими байтами. Каталог сборки новый, а исходники work/service сохраняются. Скобки изолируют Bash-процесс: при первом отказе сборка и публикация следующего шага прекращаются.

(

  : "${LAB_ROOT:?}" "${GO_BIN:?}" "${LAB_DOCKER_CONTEXT:?}"
  test -x "$GO_BIN"
  test "$("$GO_BIN" version)" = 'go version go1.27.3 linux/amd64'
  docker --context "$LAB_DOCKER_CONTEXT" version >/dev/null
  if docker --context "$LAB_DOCKER_CONTEXT" image inspect ledger-api:argocd-local-1 >/dev/null 2>&1; then
    echo 'Image already exists; preserve it and inspect its identity.' >&2
    exit 1
  fi
  cd "$LAB_ROOT/work/service"
  test ! -e "$LAB_ROOT/artifacts/argocd-local-1"
  test ! -L "$LAB_ROOT/artifacts/argocd-local-1"

  mkdir "$LAB_ROOT/artifacts/argocd-local-1"
  export GOENV=off GOTOOLCHAIN=local GOWORK=off GOFLAGS= GOPROXY=off
  export GOOS=linux GOARCH=amd64 GOAMD64=v1 GOEXPERIMENT=

  CGO_ENABLED=0 GOOS=linux GOARCH=amd64 GOAMD64=v1 "$GO_BIN" build \

  cp Dockerfile "$LAB_ROOT/artifacts/argocd-local-1/Dockerfile"
  docker --context "$LAB_DOCKER_CONTEXT" build --platform linux/amd64 \
    --tag ledger-api:argocd-local-1 "$LAB_ROOT/artifacts/argocd-local-1"
  docker --context "$LAB_DOCKER_CONTEXT" image inspect ledger-api:argocd-local-1
)

Race detector проверяет исполняемые пути тестов; итоговый бинарник собирается отдельно с CGO_ENABLED=0. -mod=readonly запрещает незаметное изменение модульных файлов, -trimpath убирает пути рабочей копии из записанных позиций, -buildvcs=false отключает автоматическую запись VCS-метаданных. Dockerfile копирует бинарник в scratch и запускает UID/GID 65532; компилятор внутрь образа не попадает. Успешный build ещё не загрузил образ на узлы Kubernetes. При отказе сохраняются созданный каталог и журналы; для нового опыта согласованно выбирают новый суффикс каталога и тега, а не сбрасывают весь стенд.

Для этого варианта в своём overlays/lab/kustomization.yaml добавьте преобразование images с name=ledger-api и newTag=argocd-local-1. Отрендерьте дерево и проверьте точное image в Deployment до C1. Существующие MESSAGE, namespace и ссылки ConfigMap сохраняются. Если используете kind, загрузите этот новый тег в тот же кластер handbook средствами его уже настроенного движка; VM-профиль требует доставки на нужные узлы или в собственный доступный реестр. Запишите image ID/digest и платформу. Блок дан как рецепт; редактор не собирал и не запускал этот вариант.

Задание 3: опубликовать именно своё дерево

Содержимое work/gitops становится деревом собственного конфигурационного репозитория: каталог apps находится в его корне. Не публикуйте private, bundle, клиентскую конфигурацию и результаты с секретами. Читатель создаёт коммит C1 и проверяет, что он доступен repo-server; книга не выполняет Git commit/push. Если требуется заново собирать ledger-api:0.1.0, используйте неизменённый service и тот же контракт MESSAGE/JSON.message. Другие байты получают новую версию и явную правку image.

Задайте LAB_REPO_URL и полный LAB_COMMIT=C1. Configure.py через Python выбранного окружения создаёт bootstrap-initial с собственным URL и строковой ревизией. Прочитайте project.yaml и application.yaml; убедитесь в одном разрешённом назначении и automated.enabled=false. First-app.sh создаёт проект перед приложением и останавливается на ошибке. До sync изучите argocd app get, argocd app manifests и argocd app diff. Их результаты получает настоящий сервер, в отличие от предыдущего локального Kustomize.

Задание 4: первая ручная поставка

После отсутствия ошибок источника выполните argocd app sync без prune и дождитесь argocd app wait с --sync --health. Проверьте Deployment, готовые endpoints Service и HTTP /api/hello через отдельный loopback port-forward приложения. JSON должен содержать service=ledger-api и message=Hello from GitOps lab. Проверка HTTP доказывает путь до процесса, а не только принятый YAML.

kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" \
  -n gitops-lab port-forward --address 127.0.0.1 service/ledger-gitops 18080:80

В другом терминале curl --fail http://127.0.0.1:18080/api/hello. Порт 18080 отличается от 8080 процесса и 80 Service: локальное перенаправление устанавливает связь между ними. Ctrl+C завершает только этот канал. При отсутствии образа исправляют доставку артефакта в выбранный кластер, а не переименовывают службу и не включают prune.

Задание 5: следующая конфигурация без сброса

В той же рабочей копии измените только строку MESSAGE в overlays/lab/kustomization.yaml, локально отрендерите и опубликуйте C2. Сохраните C1 и цель Application. При закреплённом C1 новый коммит не должен неожиданно примениться; отдельно измените targetRevision на C2 в собственном управляющем файле либо командой argocd app set с --revision. Получите различие, синхронизируйте и снова проверьте JSON.message.

Хеш ConfigMap и ссылка шаблона Pod изменятся. Старые ConfigMap без prune остаются: перечислите их и определите, какие ещё нужны прежним Pod. Только после этого отдельно рассмотрите --prune. Сохранение исправного старого Pod во время RollingUpdate не означает, что новые Pod уже готовы; оцените обе группы.

Задание 6: отказ, объяснение и исправление

В то же дерево добавьте fixtures/not-ready.patch.yaml через patches Kustomize, опубликуйте C3 и переведите прежний Application на C3. MESSAGE от C2 сохраняется. Новый путь /missing-readyz даёт 404, поэтому операция не должна успешно пройти условие здоровья. Запишите sync status, health, operationState, Deployment conditions и доступность старого HTTP отдельно. Верните корректный путь новым коммитом C4, сохранив остальную конфигурацию; не удаляйте namespace и не переустанавливайте Argo.

Лишь после этого включают необязательную автоматизацию или отдельный fleet. Для fleet подготовьте configure.py --fleet в новом bootstrap-fleet, создайте два собственных namespace с такой же проверкой владельца и просмотрите другой проект/назначения. Первоначальный ledger-gitops не переносится. Удаление необязательного набора сначала разбирают по ownerReferences/finalizers, затем выполняют осознанно, сохраняя данные.

Как подтверждалось поведение

Версии инструментов взяты из hack/tool-versions.sh и установщиков закреплённого tag; значения сумм сверены с первичными опубликованными данными. CLI-справка получена настоящим --help с приватными HOME/--config/KUBECONFIG. Каждая объявленная форма флага проверяется у своей команды, унаследованные и локальные формы различаются. Встроенный CLI Cobra принимает локальный admin --server даже перед словами admin settings; для ясности книга показывает каноническую форму после конечной команды. Возможная неполнота читательского распознавателя не меняет грамматику бинарника.

Поле helm.version проверено не догадкой по номеру архива, а util/helm/cmd.go: пустое значение, v3 и v4 ведут к одному helm. Отслеживание аннотацией, особенности SSA, автоматизация, волны и ApplicationSet удаление связаны с руководством 3.5. Локальный RBAC проверен реальным клиентом и loopback-ловушкой без запросов. Схемы Application/AppProject/ApplicationSet извлечены из install.yaml и сопровождаются Apache-2.0 и указанием происхождения.

Что доказано локально

Проверены стабильные байты двух одинаковых Kustomize-рендеров, связность Service/Deployment/ConfigMap, смена хеша при изменении MESSAGE, сохранение MESSAGE при следующем отказе readiness, Helm lint/template и отрицательная schema-проверка, структурные положительные/отрицательные API-примеры, CLI-политики allow/deny и границы аргументов. Go-тесты с race detector проверяют контракт HTTP, конкурентность и завершение активного запроса перед выходом. Это содержательные проверки наблюдаемого поведения, не механическое сравнение исходника с самим собой.

Что требует собственного сервера

Не выполнялись установка Argo, создание реального Application, генерация ApplicationSet контроллером, server-side diff, sync/dry-run sync, health, hooks, prune/delete, настоящий rollback, admin export/import, HA и нагрузочный кластерный опыт. Для них даны последовательность и критерии приёмки, но нет вымышленных журналов успеха. Cosign/SLSA-проверка подписи и загрузка образов также не отмечены выполненными. Измеренные миллисекунды относятся только к локальному Kustomize.

Словарь в боковой панели также ищет определения во всех остальных томах.

GitOps

Подход, при котором версионируемое желаемое состояние получается из доверенного источника, а контроллер сравнивает его с фактом и по политике согласует ресурсы.

Continuous Delivery

Непрерывная доставка: подготовка и управляемый перенос проверенного изменения к исполнению. Не равна обязательному автоматическому выпуску каждого коммита.

Argo CD

Контроллер и интерфейсы доставки приложений в Kubernetes из декларативного источника. Не компилирует автоматически Go и не заменяет Kubernetes.

CLI

Command Line Interface — интерфейс командной строки. Оболочка передаёт массив строк argv, а конкретная программа разбирает их по собственной грамматике.

API

Application Programming Interface — программный интерфейс. API Argo и Kubernetes имеют разные адреса, личности и правила доступа.

Commit

Коммит Git фиксирует дерево файлов и родителей. Полная ревизия конфигурации отличается от дайджеста контейнерного образа.

Desired state

Желаемое состояние: вычисленный набор объектов и полей, которые должен поддерживать контроллер. Не равно исходным файлам до рендеринга.

Live state

Фактическое наблюдаемое состояние API. Имеет возраст кэша и может содержать поля, добавленные сервером или другими контроллерами.

Reconciliation

Согласование состояния: повторяемый цикл наблюдения, сравнения и разрешённой корректировки. Не является общей транзакцией ресурсов и БД.

Drift

Дрейф — отличие фактических объектов от требуемых. Для корректировки нужен определённый владелец и разрешённая политика.

Application

API-объект Argo с источником, назначением, проектом, политикой и наблюдаемым состоянием приложения.

AppProject

Граница разрешённых источников, кластеров, пространств имён и видов ресурсов для приложений. Не заменяет Kubernetes RBAC.

ApplicationSet

Объект генерации дочерних Application по списку входов и шаблону. Его жизненный цикл может вызвать удаление дочерних приложений и ресурсов.

Spec

Желаемая спецификация API-объекта. Статус контроллера хранится отдельно и не должен редактироваться как желаемая конфигурация.

Status

Наблюдение и результат работы контроллера: сравнение, здоровье, условия ошибок и операция. Это не резервная копия данных приложения.

Operation

Запрос и исполнение действия Argo, например синхронизации. Частичный успех API-запросов может пережить ошибку всей операции.

Sync

Синхронизация вычисленного целевого набора с API. Её успех не заменяет проверку бизнес-операции приложения.

Synced

Сравниваемое представление соответствует желаемому согласно правилам нормализации. Приложение при этом может быть нездоровым.

OutOfSync

Наблюдается различие желаемого и фактического набора. Само состояние не является разрешением автоматически изменить кластер.

Health

Оценка работоспособности ресурса по наблюдаемым полям и правилам. Отдельна от совпадения манифестов и точного HTTP-результата.

Healthy

Ресурс соответствует своей проверке здоровья. Не доказывает бизнес-корректность за пределами этого правила.

Degraded

Оценка ухудшенного состояния ресурса, например неуспешного продвижения Deployment. Не означает, что все старые Pod уже перестали обслуживать трафик.

Progressing

Контроллер считает, что ресурс ещё движется к готовности. Причина может быть нормальным стартом или внешним ограничением.

Repo-server

Компонент получения исходников и генерации манифестов. Его CPU, диск, сеть, доверие и учётные данные отделены от приложения.

Application-controller

Контроллер наблюдения приложений/кластеров, сравнения, здоровья и операций. Продолжает работать без открытого браузера.

Redis

Ускоряющее хранилище кэша соответствующих компонентов Argo. Не является вымышленной обязательной SQL-базой достоверного состояния.

Dex

Компонент объединения внешних способов входа. Может использоваться для SSO, но не обязателен при каждой прямой OIDC-схеме.

SSO

Single Sign-On — единый вход через доверенного поставщика личности. Успешная аутентификация не означает административных разрешений.

OIDC

OpenID Connect — протокол идентификации поверх OAuth2. Группы/субъекты из claims должны сопоставляться ограниченным ролям.

RBAC

Role-Based Access Control — разрешения через роли. Argo RBAC и Kubernetes RBAC проверяются разными системами.

Casbin policy

Форма правил доступа Argo: строки p описывают разрешение/запрет, g связывают субъект с ролью. Локальная проверка полезна до применения.

Default role

Роль по умолчанию, права которой получают вошедшие пользователи. Чрезмерно широкие исходные права нельзя считать безопасно ограниченными последующими ролями.

Kubeconfig

Файл кластеров, личностей и контекстов Kubernetes. Может запускать доверенную программу получения токена; не совпадает с конфигурацией сеанса CLI Argo.

Argo context

Именованное подключение CLI к Argo API, выбираемое --argocd-context. Отличается от --context у kubectl/admin-команд.

Namespace

Пространство имён Kubernetes отделяет имена и область ряда прав. Не гарантирует полной изоляции и не ограничивает общие CRD само по себе.

CRD

CustomResourceDefinition — определение собственного API Kubernetes. Удаление может уничтожить все его экземпляры, включая приложения нескольких владельцев.

Manifest

Манифест — документ API-объекта. Исходный текст и нормализованное сравниваемое представление могут различаться.

Rendering

Рендеринг — получение манифестов выбранным инструментом и параметрами. Не равен допуску API или выполнению синхронизации.

Helm rendering

Исполнение шаблонов chart для получения текста. Argo обычно управляет результатом сам и не создаёт обычную Helm-историю релиза.

Kustomize

Преобразование структурированных манифестов через базу, генераторы и наборы изменений. Версия инструмента влияет на вычисленные байты.

ConfigMap generator

Механизм Kustomize, создающий ConfigMap с суффиксом хеша и обновляющий известные ссылки. Изменение ссылки меняет шаблон Pod.

Multi-source application

Приложение с несколькими источниками. Порядок источников и повторяющиеся идентичности объектов могут влиять на окончательный набор.

Normalization

Нормализация — приведение сравниваемых объектов по правилам Argo и API. Не тождественна простому git diff двух YAML-файлов.

IgnoreDifferences

Исключение отдельных различий из сравнения. По умолчанию не означает, что применяемое поле вообще перестало управляться Argo.

Server-side diff

Сравнение с участием серверного пробного применения. Требует API и совместимых разрешений; не является локальным Kustomize build.

SSA

Server-Side Apply — серверное применение с принадлежностью полей управляющим. В выбранном Argo используется с force-conflicts по проверенному исходнику/документации.

ManagedFields

Kubernetes-метаданные управляющих полями. Конфликт полей отличается от идентичности владельца Application.

Self-heal

Автоматическое исправление управляемого дрейфа обратно к желаемому состоянию. Не ремонтирует физический диск или внешнюю БД.

Prune

Удаление управляемых ресурсов, отсутствующих в желаемом наборе. Отдельно разрешается для операции или автоматической политики.

AllowEmpty

Разрешение пустого целевого набора при соответствующей автоматической синхронизации. Не следует включать как лечение ошибки генерации.

Sync window

Окно политики, разрешающее либо запрещающее синхронизацию по расписанию и условиям. Не является гарантией прикладной доступности.

Selective sync

Синхронизация явно выбранных ресурсов, не полного приложения. Hooks не выполняются, история имеет ограничения; отличается от ApplyOutOfSyncOnly.

ApplyOutOfSyncOnly

Опция синхронизации только отличающихся ресурсов полного приложения. В 3.5 обработчики всё ещё выполняются и операция записывается в историю.

Sync phase

Фаза PreSync/Sync/PostSync/SyncFail и других поддержанных событий. Сначала выбирается фаза, затем волна и порядок ресурсов.

Sync wave

Числовая волна порядка внутри фазы. Меньшая идёт раньше; здоровье ранней волны может заблокировать продвижение.

Hook

Ресурс специальной фазы Argo, часто Job. Удаление объекта обработчика не отменяет внешние действия мигратора.

Hook deletion policy

Правило удаления обработчика до повторного создания, после успеха или ошибки. Не является откатом данных.

Tracking annotation

Аннотация argocd.argoproj.io/tracking-id, связывающая ресурс с приложением. В 3.5 аннотационный метод является основным по умолчанию.

Installation ID

Идентификатор установки Argo для различения управляющих контуров в одном кластере. Не делает безопасным совместное управление одним полем.

Finalizer

Финализатор задерживает окончательное удаление объекта до работы ответственного контроллера. Не является резервной копией.

OwnerReferences

Ссылки владельца Kubernetes для сборки мусора. ApplicationSet использует их для дочерних Application; они не равны tracking-id прикладного ресурса.

Replace

Замена объекта вместо обычного применения полей. Может менять доступность и требует понимания неизменяемых полей/идентичности.

Force

Принудительный способ применения с риском удаления и пересоздания. Не является универсальной починкой любого конфликта.

Repository credentials

Учётные данные чтения Git/Helm/OCI-источника repo-server. Отличаются от пароля пользователя UI и imagePullSecret узла.

Known hosts

Доверенные SSH-ключи сервера. Автоматически увиденный ключ без независимой проверки не устанавливает доверия.

TLS

Transport Layer Security — защита канала и проверка личности сервера. Разные каналы могут иметь разные доверенные CA.

CA

Certification Authority — удостоверяющая сторона/материал доверия сертификатам. Корневые сертификаты клиента, repo-server и узла независимы.

SAN

Subject Alternative Name — допустимые имена/адреса сертификата. Доверенный сертификат с другим именем всё равно не проходит проверку адреса.

gRPC

Протокол удалённых вызовов, используемый CLI Argo. Прокси должен поддерживать нужный транспорт; gRPC-web является отдельным адаптером.

OCI

Open Container Initiative — семейство форматов и протоколов артефактов. OCI-source Argo и Helm OCI chart имеют разные правила задания пути/ревизии.

Image digest

Идентификатор содержимого манифеста контейнерного образа. Не равен Git-коммиту конфигурации или версии chart.

SHA-256

Хеш содержимого в 256 бит. Проверяет байты относительно доверенного ожидания, не сам по себе полномочия издателя.

Cosign

Инструмент подписания/проверки артефактов. Проверка требует доверенной личности издателя и параметров цепочки сертификатов.

Provenance

Сведения о том, какими входами и процессом создан артефакт. Хеш, подпись и смысл процесса сборки — разные доказательства.

SLSA

Supply-chain Levels for Software Artifacts — требования к защищённости цепочки сборки. Уровень не анализирует прикладные полномочия манифеста.

HA

High Availability — высокая доступность при заданных отказах. Реплики контроллера, Redis и приложения решают разные задачи.

Sharding

Разделение работы между экземплярами контроллера, например по кластерам. Не равно репликации всех данных в общую SQL-базу.

Cache

Кэш повторно используемых результатов/наблюдений. Возраст и ключи важны; не заменяет источник и согласованную резервную копию.

Webhook

Веб-обработчик уведомления об изменении. Ускоряет проверку источника, но не заменяет получение доверенной ревизии.

Polling

Периодический опрос источника. Интервал и случайная добавка влияют на задержку обнаружения и нагрузку.

RSS

Resident Set Size — резидентная память процесса. Не равна всему размеру Git-репозитория или одной куче Go.

QPS

Queries Per Second — запросы в секунду в заданной границе. Ограничение клиента и ёмкость API-сервера не одинаковы.

RPO

Recovery Point Objective — допустимая потеря последних данных по времени. Git и export Argo не заменяют резерв БД/PVC.

RTO

Recovery Time Objective — допустимое время возврата услуги, включая инструменты, доступ, данные и прикладную приёмку.

Rollback

Откат к прежним входам/истории. При включённом autosync обычный rollback приложения запрещён; Git остаётся источником будущего согласования.

Idempotence

Идемпотентность — повтор действия без нежелательного дополнительного эффекта. Не следует предполагать её у миграции БД или внешнего API.

Offline bundle

Подготовленный комплект байтов и инструментов. Чтение HTML офлайн, работа без Git и повторная установка без сети — разные режимы.

Last-applied configuration

Сохранённое прежнее описание объекта в аннотации kubectl.kubernetes.io/last-applied-configuration. Вместе с желаемым и живым объектами участвует в Legacy diff; не является снимком всех полей и внешних данных.

ResourceVersion

Служебная версия наблюдаемого объекта Kubernetes. Меняется при его изменении и используется для чтения/наблюдения; это не Git-коммит и не номер образа.

Admission

Проверки и преобразования запроса Kubernetes API перед сохранением. Проверяющий webhook может отказать, изменяющий — добавить или изменить поля.

JSON Pointer

Путь к значению JSON: /spec/replicas выбирает replicas внутри spec. В имени ключа ~0 обозначает тильду, ~1 — косую черту.

HPA

HorizontalPodAutoscaler — контроллер Kubernetes, меняющий число реплик по метрикам. Его управление replicas необходимо согласовать с желаемой конфигурацией Argo.

ServiceAccount

Служебная учётная запись Kubernetes для процессов. RoleBinding либо ClusterRoleBinding связывает её с разрешениями; права установившего манифест пользователя автоматически ей не передаются.

ReplicaSet

Контроллер поддержания требуемого числа Pod по шаблону. Deployment создаёт и меняет ReplicaSet при обновлении шаблона.

StatefulSet

Контроллер реплик с устойчивыми именами и предусмотренной моделью идентичности. В выбранной установке так запускается application-controller; его готовность проверяется отдельно.

Backoff

Пауза перед повторной попыткой. Начальная длительность, множитель и верхний предел задают отдельные паузы; время выполнения попыток увеличивает полную длительность операции.

Restore quarantine

Изолированная цель восстановления: проверены кластер и назначение, контроллеры изменений остановлены, прежние доступы и сохранённые операции пересмотрены до возобновления.
