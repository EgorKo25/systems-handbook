Среда и граница опыта

Исходный код можно заменить файлом предыдущей сборки. База данных к этому моменту уже приняла новые записи, изменила ограничения и потеряла удалённые столбцы. Эта асимметрия определяет весь том. Мы построим личный сервис записок на Go, проведём его через изменение представления текста, остановим несколько опасных выпусков и проверим резерв на другой базе.

Миграция — именованное, сохраняемое в проекте действие изменения структуры или данных базы. Flyway — программа, которая сопоставляет эти действия со своей таблицей уже принятых действий и исполняет подходящие следующие. Она не выбирает безопасный смысл SQL за автора. CLI — интерфейс командной строки, отдельный процесс для запуска команд. Основной маршрут использует открытый Flyway OSS 13.12.0 и PostgreSQL 18.6. Java нужна самому CLI; приложение остаётся Go, Maven не участвует.

Книга I объясняет участников и даёт принятый экземпляр. Книга II прослеживает путь от имени файла до commit и истории. Книга III разбирает живой выпуск, длительную обработку данных и конфликтующие процессы. Книга IV учит принимать существующую базу, восстанавливаться и измерять стоимость. Словарь помогает вспомнить уже введённые понятия.

Среда и граница опыта

Все команды рассчитаны на Bash в личной Linux VM/домашней Linux-системе, обычного владельца стенда, Python 3.12+, подготовленные PostgreSQL 18.6 с OpenSSL и Go 1.27.3. Чтение на рабочем Windows не требует установки. Для лаборатории там нужна отдельная личная Linux VM. Корень проекта — $HOME/handbook-lab/flyway; постоянный кластер — $HOME/handbook-lab/pg18. Не запускайте несколько тяжёлых томов одновременно на машине с 8–16 GiB.

Файлы labs/README.txt и ПРОВЕРКИ.txt отделяют исполненное автором от рецепта читателю. Образовательные схемы показывают заданные состояния: они не выполняют SQL, не измеряют сервер и не изображают терминал. У каждой схемы есть текстовые шаги для печати и чтения без JavaScript.

Не требуется запускать том Vault. Оба тома описывают один договор PostgreSQL: handbook/app, владелец flyway_owner, роль прав приложения app_runtime. Каждый может быть прочитан отдельно. Общая база возможна только после явной сверки адреса, владельцев и состояния; скрипты этого тома создают новый собственный кластер и не присоединяются к чужим данным.

Почему один SQL-файл ещё не процесс выпуска

Схема базы в широком смысле — описание таблиц, столбцов, ограничений и других объектов. В PostgreSQL отдельное слово schema также называет пространство имён вроде app; это уточнение пригодится при установке. Ограничение проверяет допустимость значений/связей; индекс — дополнительная структура поиска строк, которую сервер поддерживает при записи. Данные — строки внутри этих объектов. При первом выпуске сервис сохраняет записку в app.notes.body. Во втором выпуске он хочет читать title. Замена Go-файла не создаёт столбец. Ручной ALTER TABLE на одной машине не сообщает второй машине, что произошло. Повторный CREATE TABLE способен остановиться ошибкой, а повторная загрузка справочника — удвоить строки.

Решение начинает с идентичности действия: файл V1__create_notes.sql означает переход к версии 1, а не произвольный SQL из почтового сообщения. Flyway читает опубликованный набор файлов и таблицу flyway_meta.flyway_schema_history на конкретной целевой базе. Эта служебная таблица — schema history, история миграций. Программа создаёт и обновляет её от имени владельца миграций. У каждой базы своя история; общий Git-репозиторий не превращает две базы в одну.

DDL — SQL изменения структуры, например создание столбца. DML — изменение строк, например заполнение нового столбца. Оба вида могут входить в миграцию. Важен не суффикс SQL, а переход с предусловиями, последствиями и проверкой. Запись успеха в history подтверждает выполнение по модели Flyway, но не доказывает правильность бизнес-правила и не подтверждает отсутствие ручных изменений после запуска.

Три ответственности

Автор миграции задаёт SQL и совместимость. Flyway разрешает имена файлов, проверяет известную историю, выбирает следующие действия и координирует своих исполнителей. PostgreSQL проверяет права, блокировки, ограничения, выполняет запросы и фиксирует изменения. Отдельный Go-процесс продолжает принимать запросы. Его пул соединений, подготовленные запросы и старые транзакции переживают время старта Flyway.

Транзакция — группа операций PostgreSQL, принимаемая целиком командой commit либо отменяемая rollback. Это локальная гарантия базы. Переключение балансировщика на новую Go-сборку и commit миграции не образуют общей транзакции. Если база изменилась, а приложение не запустилось, требуется заранее предусмотренный совместимый путь.

Две идентичности, которые нельзя путать

Версия приложения v2 и версия миграции 2 принадлежат разным последовательностям. Один выпуск может содержать несколько миграций, а долгий backfill — заполнение нового представления для старых строк — выполняться между выпусками. Поэтому допуск приложения проверяет требуемые возможности схемы, а не равенство красивых номеров.

Checksum, контрольная сумма, помогает заметить изменение известного текста. Это не подпись автора и не доказательство происхождения SQL. Доверие к выпуску обеспечивают проверенный источник CLI, рецензирование SQL, закреплённая ревизия проекта и защищённый канал доставки. Для файлов выпуска отдельно пригоден SHA-256. История Flyway использует другой алгоритм и другой договор, разобранный далее.

Практический вопрос перед каждым выпуском: «какие приложения и строки уже существуют, какие останутся после первой ошибки и кто сможет продолжить работу?» Ответ «Flyway откатит всё» не годится без проверки конкретных SQL и границы транзакции.

Версия и издание

CLI — интерфейс командной строки: короткоживущий процесс читает настройки, соединяется с базой, выполняет команду и завершается. JRE, Java Runtime Environment, исполняет Java-код этого процесса. JDBC, Java Database Connectivity, — интерфейс Java к драйверу базы. Драйвер PostgreSQL преобразует операции JDBC в сетевые сообщения PostgreSQL. Наличие Go на машине не заменяет JRE или JDBC.

На 1 ноября 2026 года официальный GitHub release flyway-13.12.0 опубликован 30 октября. Для Linux x86-64 выбран flyway-commandline-13.12.0-linux-x64.tar.gz, 384624596 байт, SHA-256 e332704f4bbb16baba4ac565a822ccb24354003a284deaa11668c1be77013c34. Сумма сверена с digest официального release asset и реально полученным архивом. При иной архитектуре этот архив непригоден; выбирают свой asset и его ожидаемый digest. Не заменяют номер в URL без повторной проверки.

Открытая сборка сообщает Flyway OSS Edition 13.12.0. Её Flyway-код распространяется по Apache 2.0; JRE, драйверы и дополнительные библиотеки имеют собственные лицензии. Архив Redgate с их сайта — отдельная поставка, способная содержать закрытые функции и требовать EULA/лицензию. Бесплатный режим Redgate и открытая поставка — разные составы файлов. Учебный маршрут не требует авторизации Redgate и не принимает EULA за читателя.

 | SQL versioned/repeatable; info, validate, migrate, baseline, repair, clean | Есть в проверенном OSS CLI; clean запрещён настройкой стенда.

Личная установка без системных изменений

Следующий блок: Bash, обычный пользователь, cwd — домашний каталог. Предпосылки: Linux x86-64, заранее установленные curl, tar, sha256sum, доступ к официальному GitHub, достаточно диска. Каталог версии ещё не существует. Архив и исполняемые файлы остаются в личном $HOME/opt, вне каталога книги.

В Bash set -euo pipefail останавливает эту последовательность при отказе обычной команды, обращении к незаданной переменной или отказе участника конвейера. mkdir -p создаёт отсутствующие родительские каталоги; существующий downloads сохраняется.

set -euo pipefail
mkdir -p "$HOME/opt/downloads"
cd "$HOME/opt/downloads"
curl -4 --fail --location --connect-timeout 15 --max-time 300 \
  https://github.com/flyway/flyway/releases/download/flyway-13.12.0/flyway-commandline-13.12.0-linux-x64.tar.gz \
  --output flyway-commandline-13.12.0-linux-x64.tar.gz
printf '%s  %s\n' e332704f4bbb16baba4ac565a822ccb24354003a284deaa11668c1be77013c34 \
  flyway-commandline-13.12.0-linux-x64.tar.gz | sha256sum --check -
test ! -e "$HOME/opt/flyway-13.12.0"
tar -xzf flyway-commandline-13.12.0-linux-x64.tar.gz -C "$HOME/opt"
export PATH="$HOME/opt/flyway-13.12.0:$PATH"
flyway -v

--fail останавливает получение на HTTP-ошибке; --location следует официальному перенаправлению asset; -4 выбирает IPv4 и не отключает TLS. Проверка суммы должна дать OK, все команды — код 0. Ненулевая сумма, отсутствующий tar или уже занятый каталог останавливают блок до распаковки; ничего не «исправляют» пропуском проверки. Предупреждение об отсутствующей sql при -v не означает отказ Java: рабочая location будет задана проектом. PATH действует в этой оболочке; в новой его задают снова.

У curl --connect-timeout 15 ограничивает установление соединения 15 секундами, --max-time 300 — весь перенос 300 секундами, --output называет локальный файл. sha256sum --check - читает ожидаемую пару «сумма и имя» со stdin, заданную printf; ошибка суммы даёт ненулевой код. test ! -e требует отсутствия каталога версии. У tar -xzf означает извлечь gzip-архив из следующего файла, а -C выбирает каталог извлечения. Эти параметры меняют файлы личной установки, не создают базу.

В проверенном архиве находятся Temurin JRE 25.0.5+8 и drivers/postgresql-42.7.14.jar. Это наблюдение состава данного asset, а не обещание для ZIP без JRE или другой платформы. Файл драйвера не является сервером PostgreSQL. Для offline-дня сохраняют весь каталог версии с jre/, lib/, drivers/, licenses/, а не один shell-launcher. В launcher этой поставки первым проверяется FLYWAY_JAVA_CMD; иначе выбирается исполняемый jre/bin/java рядом с CLI. Только при отсутствии встроенной Java используются JAVA_HOME/bin/java либо java из PATH. Поэтому одного изменения JAVA_HOME недостаточно, чтобы заменить JRE полного архива. Перед переносом проверяют сам launcher и итоговый flyway -v.

Договор экземпляра

Кластер PostgreSQL здесь означает один серверный процесс с каталогом данных PGDATA и несколькими базами; это не обещание нескольких узлов. База handbook содержит схему app — пространство имён объектов. Пользователь ОС владеет файлами процесса; роль PostgreSQL — отдельный объект прав внутри сервера. Сходство имён не связывает эти личности автоматически.

 | Место/личность | Назначение

 | $HOME/handbook-lab/flyway | Скопированные SQL, конфигурация, Go; .private/runtime.json с паролями режима 0600; backups/ и app/bin/ локально.

 | $HOME/handbook-lab/pg18 | PGDATA=data/, postgresql.log, private TLS; сохраняется между занятиями.

 | 127.0.0.1:15432 | Единственный TCP listener PostgreSQL. 18080 — HTTP Go, тоже loopback.

 | lab_admin | Начальная superuser-роль; только bootstrap и наблюдение личного кластера.

 | flyway_owner | LOGIN без superuser/CREATEROLE; владелец app, flyway_meta и объектов миграций/history.

 | app_runtime / app_local | NOLOGIN-набор прикладных прав / LOGIN-член этого набора. Нет CREATE в app и доступа к history.

TLS защищает соединение и проверяет сервер по доверенному сертификату. Личный CA — удостоверяющий сертификат; его публичная часть нужна JDBC/Go, а закрытый ключ хранится приватно. SAN — имя/адрес внутри серверного сертификата: здесь IP 127.0.0.1. verify-full проверяет цепочку и SAN. Пароль аутентифицируется по SCRAM-SHA-256; это отдельная задача от TLS. Тест с sslmode=disable проверяет SQL на loopback, но не проверяет этот защищённый профиль.

Подготовить файлы и зависимости до запуска

Нужна подготовленная личная установка PostgreSQL 18.6 с OpenSSL, содержащая initdb, postgres, pg_ctl, psql, createdb, pg_dump, pg_restore. Получение и сборка PostgreSQL объясняются в томе PostgreSQL; здесь не предполагается, что сервер установился вместе с Flyway. Поместите её в $HOME/opt/postgresql-18.6. До готовности этого предусловия запуск остановится. Системную службу или чужой сервер для опыта не используем.

Блок: Bash обычного владельца, cwd — каталог flyway/ переносимой книги. Предпосылки: предыдущая установка CLI, OpenSSL CLI и PostgreSQL bin по указанному пути; целевые два каталога ещё отсутствуют. cp -R рекурсивно копирует каталог labs со скрытыми файлами, включая .gitignore. Параметры --pg-bin и --flyway передают helper полные пути к уже проверенным программам; они их не скачивают.

set -euo pipefail
mkdir -p "$HOME/handbook-lab"
test ! -e "$HOME/handbook-lab/flyway"
cp -R labs "$HOME/handbook-lab/flyway"
cd "$HOME/handbook-lab/flyway"
python3 lab.py configure --pg-bin "$HOME/opt/postgresql-18.6/bin" \
  --flyway "$HOME/opt/flyway-13.12.0/flyway"
python3 lab.py start
python3 lab.py bootstrap

Код 0 каждого шага допускает следующий. configure проверяет версию/bin, запрещает root и существующий PG-корень, создаёт случайные пароли и маркер владения. start создаёт новый PGDATA, короткоживущий файл начального пароля удаляет после initdb, создаёт личный CA и запускает только свой pg_ctl -D. Занятый порт приводит к отказу старта; чужой процесс не останавливают. Для другого порта его задают configure --port до первого старта и сохраняют новый договор.

Приёмка печатает PostgreSQL 18.6, lab_admin, 127.0.0.1 и выбранный порт; TLS-запрос должен показать t и протокол. Ошибка сертификата/пароля/готовности останавливает bootstrap. При незавершённом init сохраняют журнал и исследуют состояние: повторный configure не стирает каталог. Сертификаты учебные: серверный действует 14 дней, CA 30. Для продолжения через месяц нужны осознанное перевыпускание, перезапуск и обновлённое доверие, а не отключение проверки.

Bootstrap создаёт роли и обе схемы, но не прикладные таблицы. Права будущим объектам определяет именно создающий их владелец: ALTER DEFAULT PRIVILEGES от lab_admin не настраивает будущие объекты flyway_owner. Если history лежала бы вместе с прикладными таблицами, широкий default GRANT в той же схеме дал бы права и на неё. Поэтому metadata вынесена в flyway_meta, а любые правила будущих прикладных прав ограничиваются IN SCHEMA app. В helper default privileges пока только снимают публичные права; V1 выдаёт конкретные разрешения notes и sequences явно.

Обнаружение до исполнения

Location — объявленная область поиска ресурсов. В стенде это filesystem:migrations: рекурсивное чтение каталога относительно рабочего проекта. Versioned и repeatable

Versioned означает «с версией»: V2__expand_title.sql. V — префикс, 2 — числовая версия, двойное подчёркивание — разделитель, остаток — описание. Версия 1.10 идёт после 1.2, в отличие от сортировки строк; underscore в версии также разделяет части. Выберите одну командную схему нумерации и ловите конфликт до merge. Одна успешно принятая versioned-миграция обычно больше не исполняется. Существующий текст не переписывают ради следующего изменения: добавляют новую V-миграцию.

Repeatable, повторяемая миграция, имеет имя R__note_count.sql, описание и checksum, но не номер версии. После всех подходящих versioned выполняются новые/изменённые R в порядке описания. Каждый новый checksum даёт новый факт исполнения; старый становится Superseded. В стенде R создаёт представление — сохранённый SQL-запрос app.note_count. CREATE OR REPLACE VIEW допускает повторение в пределах правил PostgreSQL. Произвольный INSERT в R без защиты удваивал бы данные.

Repeatable обязана работать на каждом target, который команда реально использует. Если R читает title, она упадёт на базе target=1. Поэтому выбранная R зависит только от таблицы notes и count, доступных с V1. Понижение target не возвращает старый вариант R.

Placeholders и текст

Placeholder — обозначение вроде ${tenant}, заменяемое значением до передачи SQL. Это текстовая подстановка, а не параметр prepared statement. Недоверенное значение может изменить грамматику SQL; пароль не следует встраивать в миграцию таким способом. Для имён схем здесь применены явные app., чтобы не зависеть от неочевидного search_path.

Стандартный checksum SQL в этой версии — CRC32 от прочитанных строк UTF-8 с удалением BOM первой строки и без байтов окончания строк. Поэтому переход LF↔CRLF сам по себе не обязан менять checksum; изменение комментария обычно меняет. У versioned-ресурса checksum вычисляется по исходному тексту: смена placeholder сама по себе не меняет принятую V-контрольную сумму и не запускает V повторно. Одинаковая CRC поэтому не доказывает одинаковую итоговую SQL-семантику на разных окружениях. Для R Flyway учитывает заменённые значения, чтобы изменение placeholder могло вызвать повтор. Нативный опыт сменил word=one на word=two: таблица из V осталась с one, а R-представление стало показывать two; число R-исполнений выросло до двух. Не включайте текущее время ради принудительного повторения без понимания цены.

Проверенный исходник: ChecksumCalculator 13.12.0. Этот алгоритм удобен для обнаружения случайного изменения, но 32-битная CRC не защищает от умышленной подмены и не измеряет происхождение файла. Сохранение утверждённого SQL и ревизии выпуска остаётся необходимым.

Разобрать два checksum-эксперимента

Первый опыт сохраняет SQL и меняет только представление файла: к началу добавлен UTF-8 BOM, окончания строк LF заменены CRLF. Чтение строк снимает эти отличия, поэтому validate остаётся успешным. Затем к исходному файлу добавлен комментарий. CRC учитывает его символы, хотя SQL-эффект не изменился; validate получает checksum mismatch. Это показывает границу нормализации: Flyway не вычисляет семантический хеш SQL и не «игнорирует все пробелы и комментарии». После возвращения исходных байтов проверка проходит без repair.

Второй опыт содержит V1 с INSERT значения '${word}' и R с представлением SELECT '${word}'::text. При word=one обе исполняются. При следующем migrate с word=two versioned checksum остаётся прежней: ресурс V вычисляется по исходному тексту, поэтому строка one не переписывается. У R resolver подставляет значение перед checksum, видит отличие и выполняет новую редакцию view: оно показывает two. История содержит один V1 и два исполнения R. Это проверено настоящей CLI 13.12.0, а условие в исходнике — repeatable && placeholderReplacement в SqlMigrationResolver.

Следствие для выпуска: environment-specific placeholder в V может дать разные объекты при одинаковой зарегистрированной CRC. Для R смена значения — потенциальное новое исполнение, даже если файл не менялся. Если подстановка отключена, действует другая ветка resolver; пример с включённой подстановкой не доказывает её поведение. Контроль исходного релиза, настроек и последствий нужен вместе, а не вместо друг друга.

SQL проходит несколько разных разборов

Ресурс после текстовой подстановки попадает в PostgreSQL-диалект parser Flyway: он выделяет SQL statements, учитывает строки, комментарии и dollar quoting и классифицирует известные операции по допустимости транзакции. Statement — отдельная команда SQL. Полученные команды передаются через JDBC PostgreSQL-серверу; это не запуск программы psql. Уже сервер разбирает SQL-грамматику, проверяет объекты/права и при необходимости исполняет тело процедурного языка.

Dollar quoting — ограничение строкового тела парой $$…$$ или одинаковыми именованными тегами $body$…$body$. В PostgreSQLParser 13.12.0 такой текст считывается как один строковый токен до совпавшего тега. Поэтому внутренние точки с запятой тела DO не становятся границами отдельных JDBC-команд. Парсер также распознаёт определённые конструкции BEGIN ATOMIC и специальный путь COPY FROM STDIN. Это поддержка конкретного диалекта, а не обещание, что любой script любого клиента пригоден JDBC.

Следующий блок — содержимое уже созданного файла labs/experiments/parser/V1__dollar_quoted.sql. Его исполняет только tests/edges.py в новой собственной parser_case от flyway_owner, cwd копии лаборатории, с word=parsed и отдельной history. Предпосылки — принятые CLI/PG/TLS этого harness. Это не шаг изменения продолжаемой handbook. Ожидается код 0: одна строка semicolon; parsed и функция, возвращающая argument;parsed. При ненулевом коде зависимые проверки останавливаются и сохраняется отдельный test root.

CREATE TABLE app.parser_probe (message text NOT NULL);
DO $body$
DECLARE
    message text := 'semicolon; ${word}';
BEGIN
    INSERT INTO app.parser_probe VALUES (message);
END
$body$;
CREATE FUNCTION app.parser_echo(text) RETURNS text
LANGUAGE sql AS $function$
    SELECT $1 || ';${word}'
$function$;
COMMENT ON TABLE app.parser_probe IS 'literal; not a new statement';

${word} — текстовая подстановка Flyway, выполняемая даже внутри этого dollar-quoted SQL-тела. $1 внутри определения SQL-функции — первый аргумент PostgreSQL-функции, который интерпретирует сервер при вызове. В Go-запросе VALUES($1) значение передаёт Go-драйвер отдельным параметром вызова. В обычной миграции INSERT … VALUES($1) никакое значение не привязано автоматически: проверенная связка Flyway 13.12.0/JDBC 42.7.14 получила SQLSTATE 08P01 с сообщением о нуле значений для одного параметра. Это наблюдённый результат режима драйвера, а не универсальный код для любой отправки такого SQL. Flyway placeholder и параметр сервера не взаимозаменяемы.

Файл с \set тоже не становится сценарием psql: этот клиентский метаоператор не имеет JDBC-эквивалента; отдельная отрицательная V2 получила 42601, а строка после него не была вставлена. Успешная функция с semicolon не означает поддержку всех meta-команд, а специальный COPY-путь не добавляет универсальный shell. Не используйте некавыченный heredoc для записи $$ и ${word}: Bash может подставить PID/переменную ещё до Flyway. В книге SQL уже лежит отдельными файлами.

Граница проверена по PostgreSQLParser и ParserSqlScript. В томе не утверждается точный набор wire-сообщений/байтов JDBC для каждого SQL: это зависит от драйвера и его режима, и такой трассировки мы не выполняли.

Участники по порядку

argv — массив аргументов после обработки оболочкой. Bash убирает кавычки и разделяет слова; Flyway уже не видит исходные кавычки. Launcher выбирает Java и classpath, то есть набор Java-компонентов. CLI разбирает команду и настройки, resolver обнаруживает ресурсы. Ошибка имени, неизвестной настройки или отсутствующего файла может остановить процесс до DDL.

JDBC-драйвер открывает TCP к 127.0.0.1:15432, проверяет TLS по CA/SAN, а затем проходит аутентификацию роли flyway_owner. PostgreSQL проверяет право CONNECT и контекст схемы. Flyway читает возможности PostgreSQL и history, валидирует соответствие файлов принятой истории. Он не загружает всё приложение Go в Java и не обращается к его HTTP-порту.

Критическая область истории

Блокировка — координационное состояние сервера, заставляющее конфликтующие операции ждать или отказать. Для PostgreSQL Flyway использует advisory lock: прикладную блокировку с ключом, выбранным инструментом по объекту истории. Она нужна, чтобы два согласованно настроенных Flyway-процесса не решили одновременно исполнить одно pending-действие. После получения блокировки исполнитель обновляет сведения истории и повторно выбирает то, что ещё нужно выполнить. Решение info, полученное минуту назад, не является бронью следующей миграции.

В исходнике 13.12.0 PostgreSQLAdvisoryLockTemplate применяет pg_try_advisory_xact_lock для транзакционной настройки либо pg_try_advisory_lock для сессионной, повторяет попытки в заданном бюджете и освобождает сессионный lock в finally. Дефолт — транзакционная блокировка. Наш conf явно выбирает сессионную, поскольку V5 создаёт индекс CONCURRENTLY; это официально рекомендованная настройка для этой операции.

Сессионная означает «до явного unlock либо завершения соединения»; транзакционная — «до конца владеющей транзакции». У Flyway могут быть служебное и рабочее соединения, и нельзя отождествлять всю работу Java с одной транзакцией одного соединения. Упрощённое правило «SQL и history фиксируются вместе» верно для обычной успешной транзакционной миграции PostgreSQL, но требует уточнения для нетранзакционных действий и частичных отказов.

Исполнение и ответ

Для подходящей транзакционной SQL-миграции Flyway начинает транзакцию, отправляет подготовленные SQL statements, PostgreSQL получает нужные объектные блокировки, меняет страницы/системный каталог и пишет WAL. WAL — журнал предзаписи для восстановления принятых изменений после сбоя. Результат записывается в history; commit делает переход видимым другим транзакциям по правилам PostgreSQL. После выбранного набора Flyway освобождает координацию и возвращает код процесса/отчёт.

Если JDBC потерял ответ commit, оператор не знает результат только по ошибке клиента. После восстановления соединения сверяют history, реальные объекты и данные. Нельзя повторять нетранзакционный INSERT на основании «консоль не напечатала успех». Коды 13.12.0 различают семейства ошибок; автоматизация требует нулевой код и нужную проверку состояния, а не универсальный конкретный номер 1.

Где заканчивается advisory lock

Приложение Go и ручной SQL не обязаны запрашивать ключ Flyway и потому не ждут этот lock автоматически. Их конфликт с ALTER TABLE регулируют обычные PostgreSQL DDL locks на таблицах/индексах. Если два Flyway используют разные history table или разные схемы, они могут получить разные advisory keys и всё равно менять одну notes. Поэтому единый договор ownership, history и locations — часть выпуска, а не косметика CLI.

Источники: реализация lock, особенности PostgreSQL.

Что хранится на сервере

Flyway создаёт flyway_meta.flyway_schema_history, потому что defaultSchema задан явно. Схема flyway_meta отделена от app: приложение не получает даже USAGE в служебном пространстве. Смена table или defaultSchema не переносит историю автоматически. Новый адрес истории может сделать применённые файлы «новыми» и привести к повторному DDL. Такой перенос проектируют отдельно с резервом и проверкой.

 | Столбец | Смысл

 | success | Флаг зарегистрированного успеха. Сам по себе не описывает полноту данных, ограничения и ручной drift после исполнения.

Таблицу читают для расследования, но не обновляют вручную. DELETE FROM history не удалит созданную таблицу notes, а изменение checksum не выполнит новый SQL. Для штатных переходов предназначены команды Flyway, каждая с собственными последствиями.

Info сопоставляет две стороны

Pending — обнаруженный ресурс, ещё не принятый и допустимый для исполнения. Success — успешно принятая миграция, известная текущим ресурсам. Above Target — новый файл выше выбранного target. Below Baseline — действие, покрытое принятой базовой отметкой. Out of Order — версия исполнена позже большей версии. Это вычисляемые состояния сопоставления; их не следует искать как отдельный универсальный текстовый столбец state в history.

Missing означает, что принятой записи больше нет среди ресурсов текущих locations. Future — в базе есть принятые версии новее доступного набора выпуска. Ignored относится к файлу, который текущая политика не собирается выполнять, например поздно добавленной меньшей версии при outOfOrder=false. Failed виден, если факт неуспеха удалось сохранить. У PostgreSQL транзакционный провал часто откатывает и DDL, и новую history-запись; отсутствие Failed в таблице не доказывает отсутствие попытки. Журнал запуска нужен отдельно.

Для R изменённый ресурс становится Outdated, а предыдущая принятая редакция — Superseded. После нового успеха последняя редакция снова актуальна. Deleted означает служебную отметку repair об отсутствующем ресурсе, а не удалённые прикладные данные.

Не следует включать пароль, полный частный JSON или отладочный дамп окружения. Источники и приоритет

Precedence — порядок выбора при нескольких значениях одного параметра. По текущей документации: CLI выше переменных окружения, затем stdin, файлы конфигурации, defaults. Для автоматически найденных файлов приоритет уменьшается от workingDirectory к executionDir, домашнему каталогу и installDir/conf. В одном каталоге flyway.user.toml выше flyway.toml. Это не означает, что любой user-файл ниже по дереву победит любой project-файл.

Современный формат TOML описывает таблицы вроде [flyway] и именованные [environments.lab]; старый CONF — строки flyway.key=value. Смешанный список TOML+CONF в configFiles отвергается. Явный выбор одного формата переключает режим и исключает другой; автоматическое обнаружение предпочитает TOML. Учебный проект сознательно использует один явный CONF, а не зависит от файлов домашнего каталога.

Перед вызовом wrapper удаляет унаследованные FLYWAY_* и PostgreSQL-переменные, затем выдаёт дочернему процессу выбранные URL/роль/пароль. -configFiles=полный-путь выбирает ровно проектный файл. CLI-параметр выше окружения, поэтому wrapper допускает только учебный список параметров и запрещает URL/user/password/config/locations/table/schema-переопределения. Адрес и migration-роль дополнительно закреплены его собственными CLI-аргументами. Прямой CLI имеет более широкие полномочия, чем этот helper. Примеры не разрешают использовать wrapper как универсальный клиент рабочей базы.

CLI не является POSIX по предположению

Проверенный help задаёт параметры как -key=value. flyway migrate -target=2 и flyway -target=2 migrate принимаются, но это не основание придумывать --target 2. Путь с пробелом передают одним argv-элементом: "-configFiles=/home/me/lab copy/flyway.conf". Кавычки обрабатывает Bash; Java получает весь аргумент без кавычек.

-X включает отладку, -q уменьшает вывод, -outputType=json выбирает JSON там, где команда его поддерживает. Help имеет формы help, -h, --help, -?; версия — version, -v, --version. Двойной дефис -- не объявлен help как универсальная граница operands: его нельзя переносить из привычек другой CLI.

Настройки с точками и интерфейс справочника

flyway.postgresql.transactional.lock=false в CONF и -postgresql.transactional.lock=false в CLI обозначают выбор сессионного advisory lock. Это реальное имя настройки, а не параметр PostgreSQL-сервера. Парсер справочника сохраняет полное имя с точками: поиск CLI-команды с этим параметром открывает его пояснение. В продолжаемом стенде настройка хранится в явном CONF; его wrapper запрещает переопределять её через CLI. Прямой официальный CLI принимает эту форму, но выполняется только с заранее проверенным адресом и конфигурацией собственной базы.

Как доказать переопределение

При одном исходном состоянии target=1, файлах V1–V6 и default target latest команда info с -target=2 показывает V2 доступной, V3–V6 Above Target. Без параметра следующие версии видны Pending. Migrate с target=2 принимает только V2, а повтор с тем же target не добавляет ещё один V2. Другая проверка — объявить неверный URL в частном окружении и правильный CLI URL; её выполняют лишь на изолированном кластере без пересылки секретов. Авторский native harness сравнивает именно такие состояния, а не счётчик найденных форм help.

Не используйте -X как публичный артефакт без просмотра: эффективные настройки, пути и SQL способны содержать чувствительные данные. Подробный журнал остаётся приватным; в публичном результате достаточно кода и проверенных несекретных утверждений. Источник порядка: Configuration Precedence.

Info — наблюдение, validate — допуск известной истории

flyway info строит обзор из history и ресурсов; он не исполняет pending SQL и не доказывает, что future-migration безопасна. flyway validate проверяет согласованность известных миграций: checksum, имя/тип/описание и допустимые состояния. В 13.12.0 самостоятельный validate также отвергает Pending. Перед запланированным новым шагом мы явно передаём -ignoreMigrationPatterns=*:pending; после завершения всех файлов обычный validate проходит. Внутренняя проверка validateOnMigrate допускает предназначенные к исполнению Pending, поэтому это не тот же режим, что отдельная команда. Ни один из них не выполняет SELECT бизнес-инвариантов по всем строкам и не сравнивает каждый объект PostgreSQL с эталоном. Ручной DROP INDEX может оставаться за пределами этой проверки.

validateOnMigrate=true включён явно. При несовпадении принятого V1 процесс должен закончиться ненулевым кодом до следующего DDL. Штатное исправление случайной правки — вернуть принятый текст и создать новую V-миграцию для новой задачи. Автоматический repair перед каждым migrate уничтожает полезный сигнал: серверная history начинает соглашаться с изменённым файлом без исполнения его нового смысла.

Target ограничивает будущее

Target — верхняя целевая версия для обработки. migrate -target=2 с базы V1 применит V2 и подходящие R. Тот же вызов с базы V6 не удалит V3–V6 и не восстановит body. Target ниже текущего — не rollback. В коммерческой команде undo target участвует в другой операции; одинаковое имя параметра не означает одинаковую судьбу данных.

Out of order и ignore

Out-of-order — исполнение поздно появившейся меньшей версии после большей. Если V1.5 добавлена после V6, при обычной политике она не является очередным линейным шагом. -outOfOrder=true позволяет её выполнить и записать с поздним rank. Итоговая база теперь получена порядком V1,V2,…,V6,V1.5; чистая база с теми же файлами получит V1,V1.5,V2,…,V6. SQL должен давать допустимый результат в обоих порядках, что не следует из номера файла.

Ретроспективная миграция, меняющая body, после V6 упадёт: столбец уже удалён. Установка outOfOrder не воскрешает старую схему. Для production обычно проще новый V7 с явными текущими предусловиями. Лабораторный V1_5 лишь ставит COMMENT на существующую notes, чтобы показать порядок без потери строк.

ignoreMigrationPatterns задаёт пары тип:состояние, например *:future. В OSS 13.12.0 параметр доступен. Это исключение из валидации по выбранным состояниям, а не исполнение пропущенного SQL и не доказательство совместимости. Default *:future позволяет старому набору файлов встречать более новую history; для строгой проверки его можно очистить пустым значением. Следует понимать, какой сценарий deploy/rollback такое ужесточение запретит. Repair при missing использует свои условия, описанные отдельно.

Обычная граница — одна миграция

В PostgreSQL многие DDL, включая CREATE TABLE и обычный ALTER TABLE, можно откатить. По умолчанию Flyway оборачивает подходящую миграцию в транзакцию. Если V2 упала после ADD COLUMN, rollback возвращает её начальную схему. Успешная V1 из предыдущей транзакции остаётся. Даже два файла в одном migrate не означают общей атомарности всего выпуска.

group=true просит общую транзакцию для подходящего набора pending. Это увеличивает длительность удержания locks и объём незавершённых изменений. Если набор включает операцию, не допускающую transaction block, группирование не превращает её в транзакционную. mixed=true разрешает предусмотренное смешение, но платой может быть исполнение миграции без транзакции. Не следует включать mixed глобально ради исчезновения ошибки парсера.

CREATE INDEX CONCURRENTLY

Обычный CREATE INDEX блокирует записи на значимую часть построения. CONCURRENTLY снижает этот конфликт ценой нескольких фаз и ожиданий старых транзакций/снимков. PostgreSQL запрещает его внутри transaction block. Поэтому V5 вынесена в отдельный файл, рядом находится V5__index_title.sql.conf с executeInTransaction=false. Это имя соседнего файла, а не ещё одна миграция.

В глобальном конфиге отдельно выбран сессионный advisory lock. Иначе транзакционная блокировка самого Flyway способна конфликтовать с ожиданиями concurrent index build. Это два независимых решения: где выполняется SQL и как удерживается координация исполнителей. SET LOCAL действует внутри транзакции; в V5 используются обычные SET, поскольку общей transaction block нет. Соединение после команды завершается, поэтому эти настройки не переходят к Go-пулу.

Частичный результат требует осмотра

У V5 может остаться невалидный индекс. Он занимает диск и способен увеличивать стоимость записей, хотя планировщик не использует его как обычный valid index. Проверяют pg_index.indisvalid, indisready, реальное определение и history. Слепое CREATE INDEX IF NOT EXISTS может «успешно» пропустить неправильный/invalid объект по имени. Сначала выясняют факт и допустимый способ удаления/перестроения; repair не ремонтирует индекс.

В experiments/ два V7-файла создают таблицу и дважды вставляют одинаковый primary key. Транзакционный опыт должен оставить исходную базу без probe-таблицы. Нетранзакционный оставляет таблицу и первую строку; при доступном сервере Flyway регистрирует Failed. Если соединение погибло до записи результата, history может не содержать даже этого факта. Эксперименты не входят в обычную location и не запускаются на продолжаемом читательском экземпляре.

Что не откатывает PostgreSQL

Файлы, HTTP-запросы callback и действия внешнего скрипта не становятся частью транзакции PostgreSQL. Выданные sequence-значения могут образовать пропуски после rollback. Переименование Go binary не отменяет commit DDL. Поэтому «rollback прошёл» всегда уточняют объектом: транзакция SQL, версия приложения, история инструмента или вся база на контрольную точку.

Выпуск по воротам допуска

Gate — контрольная точка с проверяемым условием: например, NULL title больше нет. Drain — прекращение поступления запросов в старый экземпляр и ожидание завершения уже принятых запросов/транзакций. Завершившийся старый процесс и учтённые фоновые jobs позволяют перейти к переносу данных; одного запуска нового процесса недостаточно.

Оставить работающим v1, выполнить только V2. Быстрое добавление nullable-столбца тоже требует DDL lock; при timeout остановить выпуск и найти блокирующую транзакцию.

Проверить v2 на подготовленной копии, затем заменить Go-процесс; в учебном binary выбирается соответствующий режим. На большом сервисе старые и новые экземпляры могут сосуществовать. В учебном одном процессе Ctrl-C/start создаёт краткий перерыв; это честная остановка, а не «zero downtime».

Доказать отсутствие v1-писателей: drain запросов, завершение старых jobs/транзакций и учёт фоновых импортов. Иначе новые NULL title будут возникать после любого backfill.

Пакетно заполнить старые строки; повторить проверку NULL после прекращения v1. Принять V3, защищающую новые записи, и V4, проверяющую старые.

Отдельно построить V5-индекс, принять его valid-состояние. Индекс не является обязательным условием корректности title. Учебный GET сортирует по id и не обещает ускорения от индекса title; V5 даёт отдельный наблюдаемый опыт CONCURRENTLY. В реальном сервисе такой индекс выбирают под конкретный запрос.

Переключить весь сервис на v3. Выдержать выбранное окно наблюдения/возврата v2, проверить фоновых клиентов, затем отдельным решением применить V6.

Где заканчивается возможность возврата

До V3 v1 способен продолжать писать body, но его новые строки требуют повторного переноса. После V3 возврат v1 уже отвергает записи. После V6 возврат v2 тоже некорректен: body отсутствует. Восстановить пустой столбец в новой V7 недостаточно, если v3-записи после V6 не содержат прежнего представления. Нужно определить преобразование всех новых строк и совместимость ограничения.

Contract удаляет body с его содержимым из текущей модели. PostgreSQL физически освобождает место по своим правилам; логическая потеря доступа к данным наступает при DDL. Нельзя считать наличие старых байтов на диске стратегией отката. Точка возврата обеспечивается принятым backup/restore либо заранее написанным обратным совместимым переходом.

В CI отдельное migration job с узкой ролью проще контролировать, чем миграции в каждом процессе Go. Но один job не делает release атомарным: между базой и приложением всё равно нужны указанные ворота. Адрес базы и release SQL должны быть закреплены до выдачи credentials. Успех healthz проверяет соединение, а не всю матрицу совместимости; дополнительно выполняют прикладные чтение/запись.

Почему backfill живёт отдельно

Backfill — заполнение нового представления для уже существующих строк. Блокировка строки, row lock, не даёт другой транзакции одновременно изменить эту строку несовместимым способом. Один UPDATE миллиона строк удерживает такие блокировки до commit — фиксации транзакции, создаёт WAL и старые версии строк, увеличивает работу vacuum, то есть очистки устаревших версий, и реплик. Помещение такого UPDATE в V2 удлиняет lock/transaction-бюджет выпуска. Здесь операция вынесена в сохраняемый, возобновляемый job между V2 и V3.

Worker — выполняющий пакеты процесс helper — выбирает не более 200 id с NULL title, упорядочивает их и берёт FOR UPDATE SKIP LOCKED: блокирует выбранные строки, пропуская уже занятые. UPDATE повторно требует NULL, поэтому повторное выполнение не переписывает уже принятый title. Каждый пакет — отдельная SQL-команда с commit, затем пауза 20 ms. Это ограничение размера пакета, а не гарантированный предел WAL/секунду; размер text и нагрузка различаются.

SKIP LOCKED позволяет worker не застревать, но «получил 0 строк» не доказывает глобальное завершение: нужные строки могли быть заняты. Helper после цикла считает все NULL и отказывает, если остались. Он также не исправляет ненулевой, но неверный title. В реальном преобразовании нужны версия алгоритма, инвариант значения и устойчивый checkpoint; здесь идемпотентное копирование даёт простой повтор по NULL.

Очередь DDL тоже влияет на сервис

Долгая транзакция v1 с открытым SELECT может удерживать AccessShareLock. ALTER TABLE запрашивает конфликтующий AccessExclusiveLock и ждёт. Новые запросы способны оказаться за ожидающим DDL, образуя очередь и рост HTTP-задержки. Малое время самого ALTER после получения lock не равно малому влиянию выпуска. Нужны lock_timeout, короткие транзакции приложения и наблюдение очереди.

Таблица pg_stat_progress_create_index помогает видеть фазу concurrent build. Он может ждать завершения старых snapshot даже после прохода по страницам. Ограничение statement_timeout обрывает общий SQL, а lock_timeout — конкретные ожидания lock; lockRetryCount относится только к координации Flyway, не к этим PostgreSQL-таймерам. Эти три бюджета нельзя называть одним «таймаутом миграции».

Операция добавления nullable без DEFAULT обычно обходится без полного переписывания heap, однако всё равно требует каталожных изменений и locks. Цена backfill/индекса зависит от размера строк, свободного диска, WAL и параллельной нагрузки. Экономию измеряют на копии репрезентативного объёма; 1000 коротких учебных строк не представляют production.

Baseline принимает утверждение о начальном состоянии

Baseline, базовая отметка, применяется при принятии уже существующей базы под управление. Администратор сначала доказывает соответствие объектов/данных ожидаемому начальному состоянию, сохраняет резерв, затем flyway baseline -baselineVersion=1 создаёт историю с отметкой: предыдущие версии не нужно выполнять. Команда не исполняет V1 и не проверяет автоматически, что каждая таблица V1 уже существует в правильном виде.

Пустая база с baseline=1 не получает notes: следующий migrate начнёт выше отметки и V2 упадёт. Непустая неверная база с notes без body тоже не станет корректной после baseline. Новую чистую цель обычно строят полным рядом V-миграций. B-миграция, SQL-сценарий создания начального состояния для новой цели, — другой ресурс и другой механизм; запись команды baseline не является его исполнением. Основной стенд использует V1 и не подменяет имитацией исполненную историю.

baselineOnMigrate=false сохраняет защиту от случайного попадания в неподготовленную непустую схему. Автоматический baseline на «похожей» базе может молча пропустить SQL; его не включают глобально ради первого успешного запуска.

Почему B2 — другой механизм

В дополнительном native-опыте новая база имела пустые app/flyway_meta. Команда baseline с baselineVersion=1 успешно записала тип BASELINE, но to_regclass('app.notes') по-прежнему вернул NULL. Попытка V2 не нашла notes. Успех metadata-операции не создал исходную схему; это намеренно неправильное исходное утверждение, проверенное только на отдельной цели.

В другой новой базе использован набор V1 (создать cumulative с id), V2 (добавить value), B2__cumulative_state.sql (сразу создать эти два столбца) и V3 (следующий комментарий). Обычный migrate в проверенном OSS 13.12.0 выполнил SQL B2, затем V3. В history записаны именно B2/V3; строк об исполнении V1/V2 нет. Здесь B2 не команда принятия существующего состояния, а исполняемый кумулятивный SQL для нового экземпляра. Новый объект действительно возник.

Согласно договору baseline migrations, новая цель выбирает поздний подходящий базовый ресурс, а уже управляемая история продолжает обычные V-переходы и игнорирует добавленные B. Сохраняют ранние V, пока они нужны существующим экземплярам. Эквивалентность полного V-ряда и B-снимка принимается сверкой объектов, начальных данных, владельцев и прав; одинаковые строки history не требуются и не ожидаются. Выгрузка только CREATE TABLE без справочников/ограничений/прав может не представлять состояние версии.

Оба fixture лежат отдельно в experiments; продолжаемая handbook остаётся на исходном V1→V6 пути. Создание B-файла не исправляет неверно выбранную baselineVersion существующего production. Не требуется коммерческий undo, чтобы пользоваться проверенным здесь B-исполнением, но автоматическая генерация B и дополнительные средства сравнения относятся к отдельной матрице продукта. Этот опыт не выдаёт лицензию на них.

Repair чинит соответствие журнала

flyway repair способен удалить записи failed, согласовать checksums/descriptions/types с доступными файлами и пометить missing как deleted. Он не выполняет новый SQL изменённого V1, не заполняет title, не удаляет частично созданную таблицу, не делает invalid index valid. Успех repair означает завершение операции над history, после которого нужен осмотр объектов и новое решение о запуске.

Repair должен получить тот же полный набор locations, что migrate. Случайно пустой каталог способен превратить отсутствие файлов в утверждение Deleted. Поэтому до repair сохраняют history, снимок ресурсов/сумм, читают info, выясняют фактический DDL/DML и определяют план согласования. Это вмешательство с рецензируемой причиной, а не стандартный пролог CI.

Учебный нетранзакционный V7 оставляет partial_probe с первой строкой. После repair Failed-запись удаляется, но SELECT строки продолжает её видеть. Только осознанная очистка/компенсация тестового объекта и исправленный SQL делают повтор допустимым. На рабочей таблице такой «DROP и повтор» мог бы потерять пользовательские данные; нужна предметная стратегия.

Undo — отдельная функция Teams

flyway undo относится к Teams и не входит в выбранный OSS. Автор пишет U-файл для соответствующей V; инструмент не выводит надёжный обратный SQL из любого текста. Undo работает с успешно принятыми versioned-миграциями, в обратном порядке исполнения, и не отменяет repeatable автоматически. DROP COLUMN с пользовательскими данными не становится обратимым от создания пустого столбца. Коммерческая доступность функции не заменяет принятую репетицию её последствия.

Флаг --allow-pending относится к helper: он явно разрешает ещё не применённые файлы при validate контрольной точки. Например, у резерва V5 файл V6 остаётся Pending. URL или чужое имя базы через этот action передать нельзя.

set -euo pipefail
cd "$HOME/handbook-lab/flyway"
python3 lab.py restore-check --allow-pending

Ожидается код 0, текущая версия V5 и Pending V6, если dump сделан после индекса. Несовпадение checksum остаётся отказом; при исчезновении handbook_restore helper отказывает вместо обращения к исходной handbook. Без --allow-pending самостоятельный validate требует отсутствия Pending. Команда не выполняет migrate и не переключает приложение. Сопоставьте её history с сохранённой проверкой исходника на момент snapshot; сравнение с исходником уже после V6 должно показать ожидаемое расхождение версии.

1. Контрольная точка

На время учебной сверки писатели остановлены, строки и history согласованы.

Действует: Оператор.

handbook: 1000 строк/V5; Custom dump: ещё нет; handbook_restore: ещё нет; Go: остановлен

Точка: живой поток → T. В реальном concurrent dump используется согласованный snapshot.

2. Получен dump

Создан файл без владельцев/ACL; роли ещё вне него.

Действует: pg_dump.

handbook: 1000/V5; Custom dump: 1000/V5 в T; handbook_restore: нет; Go: не переключён

Резерв: нет файла → есть dump. Наличие файла ещё не означает принятую поставку.

3. Восстановлено

Другой database получает объекты/history; права возвращаются явно.

Действует: pg_restore.

handbook: не overwrite; Custom dump: сохранён; handbook_restore: 1000/V5; Go: проверяет новую цель

Цель: не существует → восстановлена. Не затираем исходник при репетиции.

4. После снимка

Исходник принимает новую строку, которой нет в старом dump.

Действует: Go.

handbook: 1001/V5; Custom dump: всё ещё1000; handbook_restore: 1000/V5; Go: пишет в исходник

Данные: точка T → T+1 на исходнике. Старый dump не содержит будущую запись.

5. Решение о переключении

Сверяют данные/history/ACL/версию и принимают судьбу T+1.

Действует: Оператор.

handbook: сохранён; Custom dump: не изменён; handbook_restore: принят T; Go: только после решения

RPO: не определён → новые строки вне точки. Rollback binary не решает эту потерю.

Что произойдёт с новыми строками

Если после snapshot исходный сервис принял записку 1002, она остаётся в исходной handbook, но её нет в восстановленной handbook_restore. Переключение приложения на восстановленную цель потеряет доступ к этой записи, пока её отдельно не перенесут/восстановят из дальнейшего журнала. Это и есть выбранный RPO, допустимая потеря по времени/данным. RTO — требуемое время возврата сервиса, включающее обнаружение, доступ к резерву, восстановление, сверку и переключение, а не только секунды pg_restore.

Физический backup и восстановление по WAL до момента времени — другой путь, подробно разобранный в PostgreSQL. Он не получается из одного custom dump. Реплика не заменяет резерв от ошибочного DROP, который она тоже применит. Возврат одного Go binary сохраняет текущие schema/data/history и не является восстановлением контрольной точки.

После restore принимают результат restore-check и прикладную проверку нужного релиза на новой цели. Не запускают default migrate автоматически: он может сразу изменить только что принятую точку. Если переезжает Vault, его snapshot/leases и PG-роли согласуются отдельным планом; общей атомарной резервной операции здесь нет.

Задать эксперимент до чисел

Нагрузка описывается числом строк, распределением размеров text, долей записей/чтений, числом клиентов, длительностью транзакций и размером машины. Окно измерения должно включать baseline до миграции, сам переход и восстановление нормальной очереди после. Сравнение V2 на 1000 строк с индексом на миллионе строк не измеряет преимущество флага. Выбранные flags сравнивают на одинаковой исходной точке, возвращённой отдельным restore.

Полная длительность запуска CLI включает старт JVM, обнаружение файлов, TLS/JDBC, validate, ожидание advisory/DDL и SQL. В history execution_time — миллисекунды конкретной миграции; это не задержка первого HTTP-запроса. Для настоящего приложения измеряют отдельно успешные/ошибочные ответы, throughput в запросах/секунду и распределение latency, включая p50/p95/p99 и размер выборки. Процентиль p95 — порог, в который уложились 95% наблюдённых задержек; p50 соответствует середине выборки, p99 описывает более редкий медленный край. Публикуют также число запросов и длительность окна: три быстрых ответа не дают устойчивой оценки p99. Универсального «нормального p99» нет: он следует из договора сервиса.

Lock-wait, WAL и диск

Для lock-wait сохраняют моменты запроса/получения lock либо наблюдают ждущие запросы и blockers с достаточной частотой. log_lock_waits=on и deadlock_timeout=200ms включены в личном стенде, но лог охватывает только ожидания, пересёкшие выбранный порог. Разница общего elapsed и execution_time — не точное время lock: туда входит и старт процесса.

Разница pg_current_wal_lsn() до/после через pg_wal_lsn_diff даёт байты WAL кластера в окне. Фоновые записи, checkpoints и другие базы мешают приписать всё одному UPDATE. pg_total_relation_size включает heap — основное хранение строк, индексы и TOAST — отдельное хранение больших значений; размер dump — сжатое логическое представление и не равен месту работающей базы. pg_stat_database.temp_bytes отражает временные файлы соответствующего счётчика; это не весь временный RSS процесса Java.

Большой backfill увеличивает WAL, dirty pages, dead tuples и задержку реплики; маленькие пакеты увеличивают число round trips/commits. Batch=200 здесь иллюстрирует компромисс, а не оптимум. Dirty pages — изменённые страницы в памяти до записи на диск; dead tuples — устаревшие версии строк, которые позднее сможет убрать vacuum. Round trip означает обмен клиент–сервер; больше пакетов требует больше обменов и commits. Следят за CPU, RSS — текущими резидентными в физической памяти страницами JVM/Go/PostgreSQL, свободным диском, задержкой I/O и пропускной способностью. При нехватке диска rollback и concurrent index cleanup тоже требуют времени.

Малый опыт с занятым остатком

В дополнительной собственной базе после V2 было ровно три коротких строки. Другая транзакция удерживала id1; batch=2 перенёс id2,3, затем вернул пустую порцию. Helper сообщил updated=2, remaining_nulls=1, seconds=0.058 и отказал. После снятия блокировки повтор сообщил updated=1, remaining_nulls=0, seconds=0.062; контроль значений подтвердил равенство body/title. В окне обоих запусков измерено 608 B WAL. Это одна малая выборка с локальными TLS-подключениями и фоновыми записями кластера; делить 3 на эту длительность ради оценки production throughput нельзя.

Отдельный опыт проверял прекращение писателей. Реальный POST v2 ждал relation lock; после SIGTERM старый Go main выходил, не дождавшись Shutdown, и клиент получал RemoteDisconnected. Исправленный процесс оставался жив на проверке через 250 ms, после освобождения lock завершил INSERT и вернул HTTP 201. Из этих двух POST в базе сохранилась только запись исправленного процесса; три исходные строки остались. Этот факт проверяет drain одного запроса в пределах пятисекундного бюджета, а не гарантирует сохранность всех запросов при аварии питания или SIGKILL. При неопределённом ответе всё равно сверяют базу.

Согласованность — тоже результат

Перед contract проверяют не только время: remaining NULL=0, запрет новых некорректных строк, validated constraint, valid индекс, нужная версия Go и отсутствие старых писателей. Count строк не доказывает сохранность значений: к нему добавляют сравнение исходного/нового представления и предметные выборки. Для больших наборов используют воспроизводимые агрегаты/диапазоны и отдельный контроль ошибок преобразования.

Сложность добавляется ради измеримой необходимости. Если согласованная короткая остановка на личном сервисе укладывается в договор, staging нескольких версий и dual-write могут быть дороже поддержки, чем сама операция. Решение принимают по данным, объёму и допустимому окну, а не по обязательному лозунгу «без простоя».

Офлайн-комплект

HTML читатель, главы, схемы и справочник не требуют CDN, онлайн-шрифтов или fetch. Но чтение без сети не означает установленный Flyway. Для автономной лаборатории заранее сохраняют официальный полный каталог CLI и лицензии, PostgreSQL/OpenSSL runtime, Python, Go toolchain, module cache либо vendor-зависимости, файлы стенда и отдельно принятый backup. Архив с launcher без JRE/JDBC не принят реальным offline migrate.

Секретные .private/, PGDATA, TLS keys, dumps и binaries исключены из public/экспорта. labs/.gitignore — подсказка Git, а не криптографическая защита и не универсальная политика exporter. Экспортёр должен явно сохранять публичные helper dotfiles и исключать частные каталоги. Проверяют actual file list, а не наличие слова offline в имени ZIP.

Для Go перед отключением сети можно из cwd app выполнить go mod vendor после принятой загрузки, сохранить vendor приватно и собирать go build -mod=vendor. Текущий app-build использует -mod=readonly с module cache; это другой путь. Указанный GOPROXY=off опыт имеет смысл только с уже подготовленными зависимостями и локальным toolchain. Он не доказывает доступность DNS/сети: он специально их не использует.

Новый Flyway распаковывают рядом, проверяют release notes, лицензии, help/поддержку PostgreSQL/JRE и исходный набор на восстановленной копии. После обновления history может получить новый формат/типы; возврат старой CLI не гарантируется. Изменение JDBC способно изменить TLS/SQL-разбор. Версия Go-приложения независима от версии инструмента миграций.

Следующая сессия начинается с python3 lab.py start, затем read-only info/inspect. Повторная seed не является обязательным шагом. Повтор configure откажет и тем самым защитит долговременное состояние. Новое задание начинает с фактической контрольной точки, а не с предполагаемого номера главы.

Словарь · FlywayПонятия и их связь с наблюдаемыми механизмами · 1587 слов

Словарь в боковой панели также ищет определения во всех остальных томах.

Миграция БД

Сохраняемое именованное действие перехода структуры или данных. Файл должен иметь предусловия, последствия и проверку; его версия независима от номера Go-релиза.

Flyway

Короткоживущий исполнитель управляемых миграций: сопоставляет обнаруженные ресурсы и schema history конкретной базы, координирует свои процессы и выполняет выбранные действия.

Flyway OSS

Открытая поставка Flyway. В книге закреплена 13.12.0; её состав/команды отличаются от коммерческой Redgate-поставки и не дают Teams-лицензию.

CLI

Command-line interface, интерфейс командной строки. Shell-launcher запускает Java; CLI получает уже разделённый оболочкой argv.

JRE

Java Runtime Environment, среда исполнения Java-кода CLI. Она не нужна Go binary; полный выбранный Linux-архив содержит свою Temurin JRE.

JDBC

Java Database Connectivity, интерфейс Java к драйверу БД. Драйвер PostgreSQL устанавливает соединение/передаёт SQL серверу.

JDBC URL

Строка адреса и параметров JDBC. Включает базу и TLS-режим; её интерпретирует драйвер из среды процесса CLI, а не браузер книги.

Схема PostgreSQL

Пространство имён объектов внутри одной базы. app хранит прикладные объекты, flyway_meta — служебную history; defaultSchema не переносит их автоматически.

Schema history

Служебная таблица Flyway с порядком и сведениями принятых действий. Она не является резервом строк приложения и не хранит универсальный столбец состояния info.

Installed rank

installed_rank задаёт порядок записанных действий, а version — номер ресурса. Поздняя меньшая версия получает больший rank; сортировка истории по версии скрыла бы порядок исполнения.

Success

Вычисляемое info-состояние известной успешно принятой миграции. success=true в history не доказывает сохранность всех бизнес-инвариантов после ручных изменений.

Failed

Неуспешная попытка, зарегистрированная в history. Транзакционный rollback PostgreSQL часто удаляет вместе с DDL и новую запись результата; отсутствие Failed не доказывает отсутствие попытки.

Outdated

Repeatable-ресурс изменился относительно последней принятой редакции и подлежит повтору. Предыдущая редакция после нового успеха станет Superseded.

Deleted

Служебная отметка repair об отсутствующем ресурсе. Она не означает DROP прикладных объектов и не возвращает SQL-данные.

Below Baseline

Ресурс покрыт принятой начальной отметкой, поэтому не исполняется как новый. Это не свидетельство, что его SQL когда-либо выполнялся на этой базе.

Ignored

Обнаруженный ресурс, который обычный порядок не допускает к исполнению, например поздняя меньшая версия. OutOfOrder меняет выбор будущего действия, а не пересортировывает прошлые commits.

Target

Верхняя целевая версия обработки миграций. На базе V6 target=2 не удаляет V3–V6; у команды undo то же имя участвует в другой операции.

Precedence

Приоритет выбора одной настройки из нескольких источников. CLI выше environment/файла; явный configFiles устраняет случайную зависимость от домашнего конфига.

JVM

Java Virtual Machine, процесс исполнения Java-байткода CLI. Его старт/память входят в стоимость запуска и отличаются от Go runtime приложения.

argv

Массив аргументов, который программа получает после обработки оболочкой. Кавычки shell не доходят до Flyway, но сохраняют пробелы внутри одного аргумента.

TOML

Современный структурированный формат конфигурации Flyway с таблицами и окружениями. Смешанный список TOML/CONF отвергается, а явный выбор формата меняет режим загрузки.

CONF

Старый формат строк flyway.key=value. В проекте выбран явным configFiles. Настройка PostgreSQL с точками хранится здесь как flyway.postgresql.transactional.lock=false; CLI использует полное имя -postgresql.transactional.lock=false.

JDBC driver

Конкретная библиотека между JDBC API и протоколом PostgreSQL. Наличие JAR не запускает сервер; версия драйвера влияет на TLS/auth и совместимость.

CRC normalization

При расчёте стандартной SQL CRC Flyway13.12 читает строки, снимает BOM первой и не добавляет окончания строк. Поэтому LF↔CRLF может оставить сумму прежней; криптографического происхождения это не даёт.

SQL statement

Отдельная SQL-команда. Flyway выделяет statements диалектным parser, затем JDBC передаёт их серверу; semicolon внутри dollar-quoted тела не является границей внешней команды.

Dollar quoting

Строковое тело PostgreSQL между одинаковыми $$ или $tag$ границами. Flyway PostgreSQLParser учитывает его при разбиении statements; это не placeholder-подстановка.

UTF-8 BOM

Необязательный маркер кодировки в начале ресурса. Его снятие при checksum не означает игнорирование произвольных комментариев/пробелов.

Baseline migration

Кумулятивный исполняемый B-ресурс построения новой цели. Отличен от команды baseline, которая лишь записывает принятую отметку существующего состояния.

psql meta-command

Действие клиента psql, например \set. Flyway/JDBC не запускают psql и не обязаны понимать его клиентский язык.

PostgreSQL $1

Позиционный параметр в определённом серверном контексте, например тело SQL-функции или параметризованный вызов драйвера. В миграции значения не привязываются автоматически и это не ${placeholder}.

lock_timeout

PostgreSQL-бюджет ожидания блокировки SQL. Он не ограничивает retries advisory lock Flyway и не является полным временем запуска JVM.

statement_timeout

PostgreSQL-бюджет выполнения SQL statement, включая его ожидания. Прерывание не объясняет автоматически судьбу ранее принятых нетранзакционных statements.

lockRetryCount

Бюджет повторов координационной блокировки Flyway. Не повторяет произвольно DML после неопределённого результата и не исправляет конфликт DDL с Go-транзакцией.

Versioned migration

Миграция с уникальной версией, например V2__expand_title.sql. После успеха её текст сохраняют неизменным; следующее изменение оформляют новым действием.

Repeatable migration

Миграция R__description.sql без версии. Новая/изменившая checksum редакция выполняется после подходящих versioned, в порядке описания.

Resolver

Компонент, превращающий найденный ресурс в описание миграции: тип, версия, описание, путь и checksum. Обнаружение ещё не исполняет SQL.

Location

Объявленная область поиска миграций. filesystem:migrations относится к каталогу проекта; неверный cwd способен изменить набор ресурсов.

Checksum Flyway

Контрольная сумма ресурса для обнаружения изменения. Стандартный SQL checksum13.12 использует CRC32 с нормализацией строк/BOM; это не подпись происхождения.

CRC32

32-битная контрольная сумма; пригодна для обнаружения случайных изменений по договору инструмента, но не для криптографической аутентичности.

Placeholder

Обозначение, заменяемое текстом до исполнения SQL. Не равно параметру prepared statement и требует контроля доверия к значению.

Pending

Вычисляемое info-состояние найденной, ещё не принятой и подходящей миграции. Это не обязательная строка/значение в history.

Above Target

Новая versioned-миграция выше выбранной верхней версии. Понижение target не откатывает уже принятые действия.

Missing

Принятая миграция не обнаружена в текущих locations. Сначала проверяют полноту релиза и cwd, а не запускают repair вслепую.

Future

В базе есть версии новее доступного набора SQL. Допуск этой ситуации не доказывает совместимость старого приложения с новой схемой.

Superseded

Предыдущая редакция repeatable, заменённая последующей принятой редакцией. Не означает возврат прикладных данных.

Out-of-order

Исполнение меньшей версии после большей. Порядок исполнения и порядок номеров расходятся; свежая и обновлённая база могут получить разные последовательности SQL.

Baseline

Служебная отметка принятого начального состояния существующей базы. Команда не исполняет ранние V-файлы и не доказывает соответствие их объектам.

Repair

Операция согласования schema history: failed/missing/checksums/descriptions/types. Она не чинит частичный SQL-результат, строки или invalid index.

Undo

Команда Teams для авторских обратных U-миграций versioned-действий. Не входит в OSS13.12 и не восстанавливает автоматически удалённые данные.

Clean

Удаление объектов выбранных управляемых схем. В продолжаемом стенде запрещено cleanDisabled=true; это не штатный откат выпуска.

Advisory lock

Прикладная блокировка PostgreSQL по ключу. Flyway согласует с ней своих исполнителей; ручной SQL и приложение не обязаны участвовать в этом протоколе.

Транзакционный advisory lock

Блокировка, удерживаемая до конца владеющей транзакции. Дефолт Flyway PostgreSQL; может мешать CREATE INDEX CONCURRENTLY.

Сессионный advisory lock

Блокировка до unlock или закрытия сессии. В стенде выбран параметром postgresql.transactional.lock=false отдельно от настройки транзакционности SQL.

DDL lock

Объектная блокировка PostgreSQL при изменении структуры. Отлична от lock истории Flyway; способна конфликтовать с обычной транзакцией Go-приложения.

DDL

Data Definition Language, SQL определения структуры: CREATE/ALTER/DROP. Многие DDL PostgreSQL транзакционны, но есть исключения.

DML

Data Manipulation Language, операции над строками, например INSERT/UPDATE. Их корректный повтор зависит от ключей и смысла действия.

Транзакция

Граница совместного принятия или отмены SQL-операций одной базы. Не объединяет автоматически rollout Go и внешние callbacks.

Transactional DDL

DDL, который конкретная СУБД может откатить в транзакции. PostgreSQL CREATE TABLE не означает, что CREATE INDEX CONCURRENTLY допустим внутри transaction block.

Execute in transaction

Настройка границы исполнения SQL. executeInTransaction=false для V5 вынесена в соседний .sql.conf; это не настройка lock-инструмента.

Expand/contract

Процесс совместимого изменения: добавить новое, перевести код/данные, затем удалить старое после прекращения его использования.

Dual write

Поддержание двух представлений при записи. В примере оба поля записываются одним SQL; независимые записи в разные системы такой атомарности не получают.

Backfill

Перенос уже существующих строк в новое представление. Пакетный повтор по NULL ограничивает транзакцию, но требует проверки пропущенных/параллельных строк.

SKIP LOCKED

Способ пропустить занятые выбранные строки при блокирующем чтении. Нулевая порция не доказывает, что все подходящие строки обработаны.

NOT VALID

Создать поддерживающее эту возможность ограничение без полной проверки старых строк. Новые изменения уже должны его соблюдать; VALIDATE проверяет старые.

Concurrent index build

Построение индекса PostgreSQL с CONCURRENTLY. Снижает конфликт с записями ценой фаз/ожиданий и может оставить invalid index после ошибки.

WAL

Write-ahead log, журнал предзаписи PostgreSQL. Его байты в окне отражают изменения всего кластера, а не автоматически только одну миграцию.

SQLSTATE

Код причины SQL-ошибки. 55P03 и57014 помогают различать серверные lock/statement timeout; потеря клиентского ответа требует отдельного расследования.

TLS verify-full

Проверка цепочки серверного сертификата и ожидаемого имени/SAN. SCRAM проверяет пароль отдельно; sslmode=disable не тестирует эту защиту.

SCRAM-SHA-256

Метод парольной аутентификации PostgreSQL. Не назначает права таблицам и не заменяет шифрование транспорта.

Default privileges

Правила прав будущих объектов, задаваемые для создающей роли и области. Они не меняют права существующих объектов и не равны GRANT от другого владельца.

RPO

Допустимая потеря данных относительно точки восстановления. Новые строки после dump отсутствуют на восстановленной цели без дополнительного переноса/WAL-плана.

RTO

Требуемое время возврата работоспособного сервиса: доступ к резерву, restore, сверка и переключение. Не только длительность команды pg_restore.

Логический backup

Выгрузка объектов/строк через логическую модель базы. pg_dump одной базы не сохраняет весь кластер ролей, TLS-файлы и внешний runtime.

Drain

Прекращение новых запросов к старому экземпляру и ожидание уже принятых запросов/транзакций. Завершение main до окончания Shutdown нарушает этот шаг выпуска.

Gate выпуска

Контрольная точка с конкретным условием продолжения. После v2 это нулевое число NULL и равенство body/title; после начала title-only записи сравнение двух полей уже неприменимо.

Процентиль задержки

Порог распределения измеренных задержек: p95 охватывает 95% наблюдений. Вместе с ним нужны число запросов и окно; малая выборка не доказывает стабильный production p99.

RSS

Resident set size, объём резидентных физических страниц процесса. Это не размер dump и не весь объём адресного пространства JVM.

TOAST

Механизм PostgreSQL для больших значений, например text. Дополнительное хранение входит в pg_total_relation_size, поэтому этот размер шире одного основного файла таблицы.

Блокировка строки

Row lock удерживает выбранную строку от несовместимого изменения другой транзакцией. SKIP LOCKED позволяет worker пройти мимо такой строки, но остаток работы надо проверить отдельно.

Drift

Расхождение фактических объектов с ожидаемой моделью после ручных/чужих действий. Обычный validate checksum не является полным детектором этого расхождения.
