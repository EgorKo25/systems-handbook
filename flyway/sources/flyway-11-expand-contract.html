Expand/contract: два представления данных и три выпуска Go

Совместимость строят через промежуточное состояние, в котором старый процесс ещё имеет смысл.

Матрица прежде команды migrate

Expand — сначала добавить новую возможность схемы, сохранив нужную старому коду. Contract — удалить старую возможность после прекращения её использования. Между ними находится перенос данных и выпуска приложений. Эта стратегия требует места под оба представления и осознанной цены переходного периода.

ПриложениеЧтение/записьДопустимая схема
v1Читает/пишет body.V1–V2. После V3 старые INSERT с NULL title будут отвергаться.
v2Читает COALESCE(title,body); пишет одно значение в оба столбца.V2–V5. После V6 SQL обращается к удалённому body и отказывает.
v3Читает/пишет только title.После завершённого backfill и V3/V4; технически body уже nullable с V2. Совместима с V6.

Это не универсальная схема переименования: здесь body/title означают один и тот же полный текст. Если новое поле выражало бы другую бизнес-сущность, копирование не было бы корректным преобразованием. Dual write — запись двух представлений одним SQL/одной транзакцией — в данном сервисе атомарна. Две независимые HTTP-записи в разные системы не получили бы ту же гарантию.

Переключить учебную SQL-ветвь

В app/main.go три варианта запросов собраны в один binary; параметр app-run v2 задаёт запускаемому Go-процессу APP_RELEASE=v2. Запуск заменяет сам Python-процесс через exec: Go сохраняет его PID и группу терминала, поэтому Ctrl-C поступает непосредственно Go, без раннего завершения дочернего процесса Python-обёрткой. Он не меняет ранее запущенный экземпляр и не исполняет миграции. Такой выбор делает три состояния доступными в одном личном практикуме. Для настоящих разных сборок отдельно сохраняют исходники, binary и их ревизии.

После принятой V2 остановите v1 через Ctrl-C в её терминале и дождитесь завершения app-run. Из того же cwd и от того же владельца запустите ниже: PostgreSQL и app/bin/notes уже существуют, title добавлен. Долгоживущая команда занимает терминал. В другой оболочке повторите чтение/POST из главы 04; ответ новой записи должен содержать release=v2 и HTTP 201. При отказе запуска/SQL следующий шаг выпуска не выполняют.

set -euo pipefail
cd "$HOME/handbook-lab/flyway"
python3 lab.py app-run v2

После backfill, V3/V4 и V5 из следующей главы сначала прекратите v2 таким же способом. Следующий отдельный запуск допустим только при заполненном title и принятом ограничении. Он выбирает SQL title-only; не удаляет body. До V6 в другой оболочке должны пройти её чтение и POST 201 с release=v3. Если процесс не завершился за бюджет Shutdown, исследуйте его журнал и незавершённые запросы, прежде чем объявлять старых писателей отсутствующими.

set -euo pipefail
cd "$HOME/handbook-lab/flyway"
python3 lab.py app-run v3

Выпуск по воротам допуска

Gate — контрольная точка с проверяемым условием: например, NULL title больше нет. Drain — прекращение поступления запросов в старый экземпляр и ожидание завершения уже принятых запросов/транзакций. Завершившийся старый процесс и учтённые фоновые jobs позволяют перейти к переносу данных; одного запуска нового процесса недостаточно.

  1. Оставить работающим v1, выполнить только V2. Быстрое добавление nullable-столбца тоже требует DDL lock; при timeout остановить выпуск и найти блокирующую транзакцию.
  2. Проверить v2 на подготовленной копии, затем заменить Go-процесс; в учебном binary выбирается соответствующий режим. На большом сервисе старые и новые экземпляры могут сосуществовать. В учебном одном процессе Ctrl-C/start создаёт краткий перерыв; это честная остановка, а не «zero downtime».
  3. Доказать отсутствие v1-писателей: drain запросов, завершение старых jobs/транзакций и учёт фоновых импортов. Иначе новые NULL title будут возникать после любого backfill.
  4. Пакетно заполнить старые строки; повторить проверку NULL после прекращения v1. Принять V3, защищающую новые записи, и V4, проверяющую старые.
  5. Отдельно построить V5-индекс, принять его valid-состояние. Индекс не является обязательным условием корректности title. Учебный GET сортирует по id и не обещает ускорения от индекса title; V5 даёт отдельный наблюдаемый опыт CONCURRENTLY. В реальном сервисе такой индекс выбирают под конкретный запрос.
  6. Переключить весь сервис на v3. Выдержать выбранное окно наблюдения/возврата v2, проверить фоновых клиентов, затем отдельным решением применить V6.

Где заканчивается возможность возврата

До V3 v1 способен продолжать писать body, но его новые строки требуют повторного переноса. После V3 возврат v1 уже отвергает записи. После V6 возврат v2 тоже некорректен: body отсутствует. Восстановить пустой столбец в новой V7 недостаточно, если v3-записи после V6 не содержат прежнего представления. Нужно определить преобразование всех новых строк и совместимость ограничения.

Contract удаляет body с его содержимым из текущей модели. PostgreSQL физически освобождает место по своим правилам; логическая потеря доступа к данным наступает при DDL. Нельзя считать наличие старых байтов на диске стратегией отката. Точка возврата обеспечивается принятым backup/restore либо заранее написанным обратным совместимым переходом.

В CI отдельное migration job с узкой ролью проще контролировать, чем миграции в каждом процессе Go. Но один job не делает release атомарным: между базой и приложением всё равно нужны указанные ворота. Адрес базы и release SQL должны быть закреплены до выдачи credentials. Успех healthz проверяет соединение, а не всю матрицу совместимости; дополнительно выполняют прикладные чтение/запись.
