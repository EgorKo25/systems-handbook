Доставка, обновление и автономное продолжение

Переносимая книга, готовый runtime и принятый резерв имеют разные составы.

Что нужно доставить

В релиз базы входят неизменяемый набор migration SQL, конфигурация без секретов, версия CLI/драйвера, ожидаемые суммы и инструкция допустимого target. Код Go собирают отдельным артефактом. Нельзя выдавать unreviewed ветке пароль flyway_owner лишь потому, что validate прошёл на пустой базе: SQL из этой ветки сможет удалить данные.

Migration job сначала доказывает адрес/версию сервера и принадлежность history; затем validate/info; затем исполняет ровно утверждённый шаг; затем сверяет инварианты. После ненулевого кода зависимые rollout/backfill/contract останавливаются. Повтор job заново исследует результат предыдущего запуска, особенно после сетевого обрыва. Модель «repair; migrate; всегда продолжить» противоречит этому допуску.

Офлайн-комплект

HTML читатель, главы, схемы и справочник не требуют CDN, онлайн-шрифтов или fetch. Но чтение без сети не означает установленный Flyway. Для автономной лаборатории заранее сохраняют официальный полный каталог CLI и лицензии, PostgreSQL/OpenSSL runtime, Python, Go toolchain, module cache либо vendor-зависимости, файлы стенда и отдельно принятый backup. Архив с launcher без JRE/JDBC не принят реальным offline migrate.

Секретные .private/, PGDATA, TLS keys, dumps и binaries исключены из public/экспорта. labs/.gitignore — подсказка Git, а не криптографическая защита и не универсальная политика exporter. Экспортёр должен явно сохранять публичные helper dotfiles и исключать частные каталоги. Проверяют actual file list, а не наличие слова offline в имени ZIP.

Для Go перед отключением сети можно из cwd app выполнить go mod vendor после принятой загрузки, сохранить vendor приватно и собирать go build -mod=vendor. Текущий app-build использует -mod=readonly с module cache; это другой путь. Указанный GOPROXY=off опыт имеет смысл только с уже подготовленными зависимостями и локальным toolchain. Он не доказывает доступность DNS/сети: он специально их не использует.

Обновить инструмент без подмены состояния

Новый Flyway распаковывают рядом, проверяют release notes, лицензии, help/поддержку PostgreSQL/JRE и исходный набор на восстановленной копии. После обновления history может получить новый формат/типы; возврат старой CLI не гарантируется. Изменение JDBC способно изменить TLS/SQL-разбор. Версия Go-приложения независима от версии инструмента миграций.

Постоянный сервер продолжают lab.py start с существующей конфигурацией/маркером. Скрипт не создаёт заново schema и не re-seed данные при каждом старте. Останавливают только своё PGDATA через lab.py stop; исходные SQL и backup сохраняются. Если маркер/пароль потерян, не создают автоматически новую историю поверх старых таблиц: сначала восстанавливают управление по собственному плану.

Контроль переносимости

Нужно отдельно проверить Linux permissions, архитектуру исполняемых файлов, пути к CA, выбранный порт и наличие всех Go modules. Путь, встроенный в приватный runtime.json, отражает прежнюю машину и требует осознанного переноса; его нельзя публиковать как универсальную конфигурацию. Связь с Vault не означает общий секретный файл: его динамические роли используют тот же договор app_runtime, но имеют другой жизненный цикл.

Авторская приёмка отличает реальный native SQL, статическую проверку HTML/ссылок, production parser и ещё не выполненный перенос на чистую VM. Эти уровни нельзя объединять в одно «всё работает offline». Конкретный остаток и команды воспроизведения собраны в READY/ПРОВЕРКИ.
