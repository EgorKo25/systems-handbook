Резерв принимается восстановлением другой цели

Сохраняем app, history, роли, версии и судьбу записей после контрольной точки.

Что находится внутри и снаружи dump

Логический dump — выгрузка объектов и строк через SQL-представление. PostgreSQL pg_dump использует согласованный снимок одной базы: concurrent writes не делают смесь произвольных моментов, но новые записи после точки снимка туда не входят. Нужен весь handbook, включая app и flyway_meta, а не только notes. Файлы CLI, migration release, роль/секреты, TLS, конфигурация сервера и Go binary — отдельные части комплекта.

В helper dump формата custom создаётся без владельцев и ACL, чтобы принимающая цель назначалась осознанно. Поэтому права восстанавливаются явными командами отдельно. Роли создаются bootstrap, приложение на резервную базу автоматически не переключается. Секретный runtime.json не публикуют вместе с SQL, но его защищённое хранение/перевыпускание нужно включить в личный план восстановления.

Создать и принять контрольную точку

Блок: Bash владельца личного проекта, cwd проекта; работающий PostgreSQL, принятый target и существующая notes/history. Для простой учебной сверки остановите Go-писателя и фоновые jobs; исходная база сохраняется. Потребуется место под dump и вторую базу. Helper создаёт новый файл режима 0600 и отказывает при совпадении имени.

set -euo pipefail
cd "$HOME/handbook-lab/flyway"
python3 lab.py sql --file check-restore.sql
python3 lab.py snapshot

Snapshot печатает точный путь, размер в байтах и длительность. После успешного кода 0 подставьте именно этот путь вместо примера ниже; файл должен существовать. Следующий блок использует уже существующие private credentials lab_admin только для создания другой базы; pg_restore исполняет объекты с ролью flyway_owner. handbook_restore до блока должна отсутствовать; при наличии helper отказывает, не затирает её.

set -euo pipefail
cd "$HOME/handbook-lab/flyway"
python3 lab.py restore backups/handbook-YYYYMMDDTHHMMSS.dump
python3 lab.py sql --database handbook_restore --file check-restore.sql
python3 lab.py sql --database handbook_restore --role app --file check-restore-app.sql

Заменённый путь — единственный ввод читателя в этом блоке; буквальное YYYY… даст отказ до создания цели. Приёмка сравнивает count/id fingerprint, сохранённые поля/значения, ranks/checksums/success history и valid индексы. app-проверка делает разрешённое чтение и отдельно доказывает отсутствие metadata-прав; допуск UPDATE проверяется нулевым обновлением WHERE false в транзакции с rollback. Такой запрос проверяет права без изменения строк; запись конкретного прикладного значения требует отдельной проверки приложения на новой цели. Одно успешное pg_restore не заменяет эти проверки. При отказе не продолжают deploy и сохраняют новую цель для расследования.

Сверить восстановленную history тем же набором SQL

После успешного restore, из того же cwd и от того же владельца, выполните следующий read-only шаг. Флаг --allow-pending относится к helper: он явно разрешает ещё не применённые файлы при validate контрольной точки. Например, у резерва V5 файл V6 остаётся Pending. Helper сначала проверяет существование именно handbook_restore, затем запускает info и validate с её фиксированным JDBC-адресом, прежней migration-ролью и тем же CONF/каталогом migrations. URL или чужое имя базы через этот action передать нельзя.

set -euo pipefail
cd "$HOME/handbook-lab/flyway"
python3 lab.py restore-check --allow-pending

Ожидается код 0, текущая версия V5 и Pending V6, если dump сделан после индекса. Несовпадение checksum остаётся отказом; при исчезновении handbook_restore helper отказывает вместо обращения к исходной handbook. Без --allow-pending самостоятельный validate требует отсутствия Pending. Команда не выполняет migrate и не переключает приложение. Сопоставьте её history с сохранённой проверкой исходника на момент snapshot; сравнение с исходником уже после V6 должно показать ожидаемое расхождение версии.

Что произойдёт с новыми строками

Если после snapshot исходный сервис принял записку 1002, она остаётся в исходной handbook, но её нет в восстановленной handbook_restore. Переключение приложения на восстановленную цель потеряет доступ к этой записи, пока её отдельно не перенесут/восстановят из дальнейшего журнала. Это и есть выбранный RPO, допустимая потеря по времени/данным. RTO — требуемое время возврата сервиса, включающее обнаружение, доступ к резерву, восстановление, сверку и переключение, а не только секунды pg_restore.

Физический backup и восстановление по WAL до момента времени — другой путь, подробно разобранный в PostgreSQL. Он не получается из одного custom dump. Реплика не заменяет резерв от ошибочного DROP, который она тоже применит. Возврат одного Go binary сохраняет текущие schema/data/history и не является восстановлением контрольной точки.

После restore принимают результат restore-check и прикладную проверку нужного релиза на новой цели. Не запускают default migrate автоматически: он может сразу изменить только что принятую точку. Если переезжает Vault, его snapshot/leases и PG-роли согласуются отдельным планом; общей атомарной резервной операции здесь нет.
