История — таблица фактов и вычисляемые состояния

Строка history и слово Pending в info относятся к разным уровням наблюдения.

Что хранится на сервере

Flyway создаёт flyway_meta.flyway_schema_history, потому что defaultSchema задан явно. Схема flyway_meta отделена от app: приложение не получает даже USAGE в служебном пространстве. Смена table или defaultSchema не переносит историю автоматически. Новый адрес истории может сделать применённые файлы «новыми» и привести к повторному DDL. Такой перенос проектируют отдельно с резервом и проверкой.

СтолбецСмысл
installed_rankЦелочисленный порядок записей об исполнении. Не равен версии; поздняя V1.5 может иметь rank после V6.
versionСтроковое представление версии V. Для repeatable — NULL.
description / type / scriptОписание из имени, тип события/миграции, ресурс. В history встречаются не только обычные SQL, но и BASELINE/DELETE и другие служебные типы.
checksumПринятая контрольная сумма; NULL допустим для типов, где её нет. Это signed 32-bit integer, не SHA-256 архива.
installed_by / installed_onЗаписанная личность и серверный timestamp исполнения. installedBy способен переопределить имя; поле не является неподделываемой подписью CI.
execution_timeИзмеренная длительность миграции в миллисекундах. Не полный бюджет выпуска и не распределение задержек HTTP.
successФлаг зарегистрированного успеха. Сам по себе не описывает полноту данных, ограничения и ручной drift после исполнения.

Таблицу читают для расследования, но не обновляют вручную. DELETE FROM history не удалит созданную таблицу notes, а изменение checksum не выполнит новый SQL. Для штатных переходов предназначены команды Flyway, каждая с собственными последствиями.

Info сопоставляет две стороны

Pending — обнаруженный ресурс, ещё не принятый и допустимый для исполнения. Success — успешно принятая миграция, известная текущим ресурсам. Above Target — новый файл выше выбранного target. Below Baseline — действие, покрытое принятой базовой отметкой. Out of Order — версия исполнена позже большей версии. Это вычисляемые состояния сопоставления; их не следует искать как отдельный универсальный текстовый столбец state в history.

Missing означает, что принятой записи больше нет среди ресурсов текущих locations. Future — в базе есть принятые версии новее доступного набора выпуска. Ignored относится к файлу, который текущая политика не собирается выполнять, например поздно добавленной меньшей версии при outOfOrder=false. Failed виден, если факт неуспеха удалось сохранить. У PostgreSQL транзакционный провал часто откатывает и DDL, и новую history-запись; отсутствие Failed в таблице не доказывает отсутствие попытки. Журнал запуска нужен отдельно.

Для R изменённый ресурс становится Outdated, а предыдущая принятая редакция — Superseded. После нового успеха последняя редакция снова актуальна. Deleted означает служебную отметку repair об отсутствующем ресурсе, а не удалённые прикладные данные.

На пустой цели target=1 принимает сначала V1, затем R. Поэтому у R rank=2 и version=NULL; у последующей V2 rank=3. Число 3 в rank не превращает V2 в версию 3. Для неизменённых файлов книги checksum V1 равна 1528097600, R — −1073421979, V2 — −143682903: отрицательный знак возникает из хранения 32-битного CRC в signed integer. Независимый расчёт нормализованных UTF-8 строк и новая native-выборка дали те же значения.

После migrate target=2 новые файлы V3–V6 дают Pending в info без соответствующих history-строк. Повтор target=2 не добавляет rank 4 для уже принятой V2. Если затем изменить комментарий V1, его записанная строка останется прежней, а validate обнаружит расхождение с новым checksum ресурса. Фактический текст следующего SQL ещё не исполняется. Столбец success=true у старых строк тоже остаётся true: отказ проверки не переписывает прошлый успех.

Сохранить достаточное свидетельство

Для выпуска сохраняют версию/издание CLI, ревизию SQL, эффективные несекретные настройки, адрес/имя базы, info до/после и код процесса. Не следует включать пароль, полный частный JSON или отладочный дамп окружения. Если миграцию выполняет flyway_owner, installed_by будет этим пользователем; имя Git-коммита не возникнет в таблице само.

Read-only inspect.sql в главе первого выпуска печатает историю по rank и проверяет права app_local. Для самостоятельного анализа колонок можно использовать каталог PostgreSQL, но основным интерфейсом сопоставления остаётся flyway info. Резерв должен включать и app, и flyway_meta: восстановленная notes без соответствующей history не является продолжением того же управляемого экземпляра.
