Довести один сервис до contract и принять новый экземпляр из резерва.

Контрольные точки

В книге уже созданы все исполняемые файлы; README перечисляет их роли. Основной маршрут: установка CLI → configure/start/bootstrap → V1+R → Go v1 → V2 → Go v2 и завершение v1 → backfill → V3 → V4 → V5 → Go v3 → резерв/restore → V6. Каждый gate имеет ожидаемый код и состояние в предыдущих главах. Не заменяйте весь маршрут одной командой default migrate: она перескочит через человеческие условия совместимости.

Перед V6 должны быть приняты v3 чтение и запись, завершены все v2-процессы/старые SQL jobs, сохранён и восстановлен резерв до contract. Этот блок исполняют в Bash обычного владельца, cwd личного проекта, пока Go v3 может работать. Существующий V6 удаляет body; после успеха старый v2 уже недопустим.

set -euo pipefail
cd "$HOME/handbook-lab/flyway"
python3 lab.py flyway validate '-ignoreMigrationPatterns=*:pending'
python3 lab.py flyway migrate -target=6
python3 lab.py request --text 'Запись после contract'
python3 lab.py request
python3 lab.py sql --file inspect.sql

Ожидаются код 0, V6 Success, POST 201 и новые строки в GET. Если POST дал неопределённый результат/503, не запускают следующее изменение и не повторяют запись автоматически: смотрят базу и логи сервиса. Этот учебный сервис не реализует идемпотентный ключ запросов; обратная доставка записей после disaster recovery потребует его в реальном продукте.

Задания с доказательством

  1. На отдельной тестовой копии измените комментарий принятого V1. Зафиксируйте checksum mismatch и отсутствие нового DDL. Верните точные байты; validate снова должен пройти без repair.
  2. На двух копиях одинакового исходного состояния сравните target=2 и latest. Назовите не только число строк history, но и совместимость старого приложения.
  3. Запустите две независимые CLI над slow V7. Докажите advisory lock и один результат; отдельно создайте DDL wait за транзакцией app, укажите другой тип lock.
  4. Сравните transactional/nontransactional failure. Снимите наличие probe-таблицы, число строк и history до/после repair. Объясните, какую часть repair не выполнил.
  5. Примите резерв на handbook_restore. Добавьте новую строку только в исходную цель и докажите её отсутствие в восстановленной; опишите RPO без выдуманного нулевого значения.
  6. При отключённом получении новых зависимостей проверьте уже подготовленный CLI/Go. Назовите, какие результаты относятся к SQL, а какие лишь к статической книге.

Автоматические безопасные испытания

tests/static.py проверяет источники, IDs, конфиги, ссылки и отсутствие бинарников/ключей. tests/parser.js использует именно production command_reference_parser.js. tests/native.py принимает пути Flyway/PostgreSQL/Go и новый private root, создаёт собственный изолированный кластер и выполняет содержательные SQL/Go/restore-сценарии. Они не устанавливают системные пакеты и не трогают читательский PGDATA. Вызовы и фактические результаты — в ПРОВЕРКИ.

Для ручного завершения сессии сначала Ctrl-C в терминале Go, затем, из cwd проекта и от его владельца, выполните ниже. Предпосылка: свой PostgreSQL запущен; файлы/данные сохраняются. Ожидаемый код — 0. Если сервер уже остановлен, pg_ctl может вернуть ненулевой код; это повод посмотреть status/журнал своего PGDATA, а не останавливать иной процесс по номеру порта.

set -euo pipefail
cd "$HOME/handbook-lab/flyway"
python3 lab.py stop

Следующая сессия начинается с python3 lab.py start, затем read-only info/inspect. Повторная seed не является обязательным шагом. Повтор configure откажет и тем самым защитит долговременное состояние. Новое задание начинает с фактической контрольной точки, а не с предполагаемого номера главы.
