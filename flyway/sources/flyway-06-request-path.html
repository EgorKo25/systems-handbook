Как Flyway выполняет миграцию V2

Проследим, когда в app.notes появляется title и по какой записи повторный запуск пропускает V2.

Участники по порядку

После первого выпуска в базе уже есть app.notes и представление app.note_count. В каталоге проекта появился файл V2__expand_title.sql. Предыдущая глава показала, как Flyway распознаёт в имени версию 2. Продолжайте после первого выпуска в своей рабочей копии labs/, где лежат lab.py, flyway.conf и migrations/. Собственная база должна быть запущена и уже содержать V1 и R. Обёртка передаст CLI частные настройки подключения; выполните в этом каталоге:

python3 lab.py flyway migrate -target=2

Если V2 уже принята с теми же файлами, команда проверит историю и пропустит её.

Bash запускает lab.py. Обёртка читает сохранённое подключение и передаёт отдельные аргументы migrate и -target=2 стартовому скрипту Flyway. Скрипт запускает Java, а Flyway читает настройки и ищет миграции. Драйвер JDBC подключается к PostgreSQL на 127.0.0.1:15432, проверяет сертификат сервера и проходит аутентификацию как flyway_owner. Теперь Flyway может сопоставить найденные файлы со строками таблицы flyway_meta.flyway_schema_history.

Критическая область истории

Представьте, что два процесса Flyway одновременно нашли V2 и оба собираются выполнить ALTER TABLE. Перед выбором очередной миграции каждый запрашивает у PostgreSQL advisory lock с ключом, рассчитанным по таблице истории. Если ключ занят первым процессом, второй повторяет запрос в пределах lockRetryCount. Получив ключ, Flyway перечитывает историю. Если первый процесс уже зафиксировал V2, второму незачем снова добавлять title.

С настройками стенда (group=false) Flyway освобождает блокировку после каждой миграции и при следующем выборе снова запрашивает её. Стенд задаёт flyway.postgresql.transactional.lock=false: PostgreSQL держит сессионную блокировку до явного освобождения ключа либо до закрытия соединения. Такая настройка нужна позже, когда V5 выполняет CREATE INDEX CONCURRENTLY. V2 по-прежнему выполняется в транзакции. Правила для обоих видов advisory lock есть в словаре.

Исполнение и ответ

Вот команды из V2__expand_title.sql. Flyway передаёт их PostgreSQL внутри транзакции. SET LOCAL задаёт предел ожидания при получении блокировки в этой транзакции.

SET LOCAL lock_timeout = '2s';
ALTER TABLE app.notes ADD COLUMN title text;
ALTER TABLE app.notes ALTER COLUMN body DROP NOT NULL;

Пока транзакция открыта, PostgreSQL добавляет столбец title и снимает требование NOT NULL с body. Flyway вставляет строку с version=2 и success=true. При COMMIT PostgreSQL фиксирует оба изменения схемы и строку истории вместе. У старых заметок в title пока NULL: в файле нет команды, которая заполнила бы новый столбец.

Если первый запуск завершился после фиксации V2, повтор той же команды с теми же файлами оставит в истории одну строку V2. Если соединение оборвалось в момент COMMIT, клиенту может быть неизвестно, успел ли сервер зафиксировать транзакцию. После восстановления подключения проверьте три признака: строку V2 с success=true, наличие title и снятый NOT NULL с body. В следующей главе показано, как прочитать строку истории и сопоставить её с выводом info.

Прочитать результат V2 после восстановления связи

В той же рабочей копии, при доступной собственной базе, выполните этот читающий запрос через функции lab.py. Он использует сохранённое подключение к handbook и ничего не меняет.

python3 - <<'PY'
import lab
config = lab.load()
result = lab.sql(config, """
SELECT label, result FROM (
  SELECT 0 AS position, version AS label,
         CASE WHEN success THEN 't' ELSE 'f' END AS result
  FROM flyway_meta.flyway_schema_history WHERE version = '2'
  UNION ALL
  SELECT 1, column_name, is_nullable
  FROM information_schema.columns
  WHERE table_schema = 'app' AND table_name = 'notes'
    AND column_name IN ('body', 'title')
) AS observed ORDER BY position, label;
""", capture=True)
print(result.stdout, end="")
PY

После успешного V2 ожидается:

2|t
body|YES
title|YES

Запрос читает историю и столбцы в одном снимке базы. Если исходная транзакция ещё работает, этот снимок может предшествовать её фиксации. Делать вывод об откате можно после подтверждённого завершения той транзакции. После отката V2 в исходном стенде строки версии 2 и столбца title нет, остаётся body|NO. Если результаты смешаны, остановитесь и сохраните журнал и выборку: другие миграции или ручные изменения требуют отдельного разбора. Переписывание истории не приведёт столбцы к нужному состоянию.

Где заканчивается advisory lock

Обычный SELECT приложения не запрашивает ключ Flyway. Если читающая транзакция ещё открыта, она может удерживать на app.notes блокировку ACCESS SHARE. Для ALTER TABLE из V2 PostgreSQL нужна ACCESS EXCLUSIVE. Даже с полученным ключом истории Flyway будет ждать освобождения таблицы. Если ожидание получения блокировки превысит заданные две секунды, PostgreSQL прервёт команду. При откате V2 в истории по-прежнему не будет строки о её успешном выполнении. В главе о параллельных выпусках этот случай разобран с наблюдением блокировок.

Оба процесса Flyway согласуют выбор V2, пока используют одну таблицу истории в одной базе. Если настроить разные таблицы истории, процессы могут получить разные ключи и всё равно попытаться изменить одну app.notes.

Исходники Flyway 13.12.0 показывают выбор миграции под блокировкой и запрос и освобождение ключа. Режимы блокировки таблиц перечислены в документации PostgreSQL.
