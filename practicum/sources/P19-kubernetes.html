STUDY-19: Перенести знакомый сервис в Kubernetes

Доступ: Сначала временный local kind в Linux VM; эксплуатационные VM и HA отдельными этапами.

Наблюдаемый симптом: Pod Running не гарантирует readiness, доступность сервиса или сохранность данных.

Доказательства результата: DNS/service/ingress/probes/resources/storage/rollout наблюдаемы; отказ узла и ограничение single control plane объяснены.

Возврат: Backup данных и manifests, безопасный rollback deployment; deletion cluster не считается backup.

Исходное состояние подготовлено в заданиях: P15-jenkins-delivery, P16-ansible, P13-observability.

Контрольные точки выключенного мира: before-p19-kubernetes перед работой и done-p19-kubernetes после проверок. Это сохранение дискового состояния, без открытых сеансов и памяти процессов.

Начальная оценка памяти гостя: 6144 МиБ. Это бюджет для проверки состава ролей, а не измеренное требование и не гарантия достаточности для всех служб вместе.

Первая установка Kubernetes через kind: заранее собрать автономный комплект

Продолжается прежний продукт и его артефакт. Docker Engine должен быть уже осмысленно установлен внутри Linux-гостя: соответствующая первая установка разобрана в стадии платформы GitLab, которая в маршруте книги идёт раньше. Если этот этап пропущен, сначала выполни только её подготовку Docker, а не пытайся запустить kind неизвестным daemon. Docker Desktop на рабочий Windows не устанавливается как побочный эффект этого задания.

Дома найди официальный релиз kind и kubectl для Linux. Выбери совместимую пару и поддержанный образом kind выпуск Kubernetes, проверь опубликованные суммы. По offline-руководству kind сохрани точный node image с digest, слои приложения и диагностического образа. Строки имён в YAML не содержат эти байты.

Установи бинарники в выбранный tools-каталог, проверь версии и Docker. Загрузку архивов образов выполняй в Docker того же гостя. Создай собственный kind-config с одним исходным узлом, явным loopback API endpoint и ресурсным бюджетом. До команды create проверь kind get clusters: если study уже существует, продолжается он, новый create не нужен. Загрузи выбранные образы на узлы kind предусмотренной командой.

Настрой отдельный kubeconfig/контекст kind-study и namespace study; проверь ready узлы, системный DNS и один новый Pod. Затем добавляй Deployment/Service продукта из разбора, readiness и отрицательный неверный образ. Рабочий kubeconfig другого кластера не участвует. В паспорт входят kind/kubectl/node digest, config, kubeconfig с секретным доступом, загрузка образов, namespaces, данные и резерв.

На следующий день запускаются те же контейнеры узлов и сохраняемые данные; kind delete cluster не является выходом из главы. Перед первой поездкой проверь холодный старт без интернета. Управляющее состояние внутри узлов, PVC и внешний резерв — разные слои; потеря общего гостя остаётся общим отказом.

Как подойти к работе

Переноси в Kubernetes уже знакомый продукт: тот же контракт HTTP, данные, конфигурацию, версионный артефакт, проверки и способ возврата. Иначе непонятно, вызвана ошибка оркестратором или приложением, которое раньше никогда не работало. Начальная задача — проследить путь от принятого API описания до готовой реплики и клиентского запроса.

Для первого опыта подходит kind, который запускает узлы Kubernetes в контейнерах Linux-гостя. Несколько таких узлов разделяют ядро и ресурсы VM. Это полезная модель управления Pod и сетью, но потеря общего гостя остановит все узлы сразу. Следующий эксплуатационный этап с отдельными VM и самостоятельными отказами имеет другой состав, бюджет и процедуры.

До отключения интернета подготавливаются сам kind, kubectl, совместимый закреплённый образ узла и образы приложения/диагностики. Файл с именем образа не содержит его слои. Образ в Docker хоста не обязан автоматически присутствовать во внутренних container runtime узлов kind; его надо загрузить предусмотренным способом. Запиши, какой набор образов и архитектур действительно проверен автономно.

Ресурсный профиль сначала сверяется с этапом оценки. Помимо приложения нужны API-сервер, хранилище состояния, служба DNS и остальные компоненты. Три GiB, предусмотренные для последовательного Docker-профиля, не объявляются достаточными для любого Kubernetes-сценария. Начни с минимального состава, измерь память, CPU, диск и время старта; дополнительные узлы, мониторинг и базы добавляй по доказанной потребности.

Успешный kubectl apply означает принятие описания, а не готовую услугу. Контроллеры постепенно приводят наблюдаемое состояние к желаемому. Pod может ожидать планирования, образа, монтирования, запуска или готовности. Отдельно исследуется путь через Service, DNS, входной прокси и приложение. Одна проверка Running не подтверждает все эти границы.

Связанные теоретические главы: Linux · Как собирается контейнер, Сети · DNS: от имени до ответа, Go · Выпуск и восстановление: какие именно байты работают.

Подсказки · открыть после своей попытки
  1. Перед каждой серией проверь контекст и namespace. Для личного kind используется явный --context kind-study; рабочие кластеры в упражнение не входят.
  2. kubectl ... get pods -o wide показывает размещение и адреса; describe pod — состояние и события. Журнал процесса и ошибка планирования относятся к разным стадиям.
  3. Проверь, что labels Pod совпадают с selector Service. Наличие Service без готовых конечных адресов не создаёт работающее приложение.
  4. Readiness определяет готовность принимать работу. Liveness управляет решением о восстановлении процесса. Если внешняя БД недоступна, бездумный liveness может перезапускать исправный процесс и усиливать аварию.
  5. Сначала вызывай приложение непосредственно доступным способом, потом проверяй Service/DNS/Ingress отдельно. Port-forward к Service выбирает Pod и не доказывает прохождение обычного пути через ClusterIP и DNS.
Разбор и проверка результата

Подготовленный ранее Linux-бинарник исходного Go-сервиса может быть основой собственного минимального образа. Для такого опыта нужен совместимый Linux/архитектурный результат с отключённой зависимостью от C, что уже разбирается в книге Go. Пример Dockerfile для личной копии проекта:

FROM scratch
COPY dist/handbook-service /service
USER 65532:65532
ENTRYPOINT ["/service"]
CMD ["-listen", "0.0.0.0:8087"]

В образ копируется проверенный артефакт. Числовой непривилегированный UID не требует записи в passwd для данного приложения. Адрес 0.0.0.0 здесь относится к интерфейсам контейнера: loopback внутри него не предоставил бы сокет другим Pod. Образ scratch не содержит оболочку, сертификаты и диагностические программы. Неудачный kubectl exec ... -- sh в таком образе не означает, что сам HTTP-процесс отсутствует.

Перед созданием кластера запиши полный подготовленный образ узла в KIND_NODE_IMAGE. Например, имя и digest берутся из сохранённого манифеста совместимого выпуска, а не из случайной статьи. Команда ниже требует заполненного значения:

kind create cluster --name study --image "${KIND_NODE_IMAGE:?choose prepared node image}" --wait 120s
kind load docker-image study-service:lab-v1 --name study
kubectl --context kind-study create namespace study

--name отделяет этот кластер от других, --image выбирает подготовленный образ узла, --wait задаёт ожидание начальной готовности с единицей времени. Вторая команда предполагает, что собственный образ уже собран в Docker гостя с указанным тегом. Запиши его digest и исходный манифест: красивое имя тега само не фиксирует байты.

В Deployment укажи namespace study, labels приложения, совпадающий selector, контейнерный порт 8087 и свой образ. Для автономного опыта можно явно выбрать imagePullPolicy: Never после загрузки на узлы: отсутствие образа тогда становится наблюдаемой ошибкой, а не неожиданным скачиванием. Настрой readiness HTTP GET /healthz на порт 8087. Requests и limits подбери из измерений; выбранные числа записывают условия опыта, а не универсальную норму Go-приложения.

Service выбирает labels приложения и направляет свой порт на targetPort 8087. Проверь его конечные адреса и запрос из подготовленного диагностического Pod в том же разрешённом сегменте. При стандартном cluster domain kind имя вида study-service.study.svc.cluster.local разрешается через кластерный DNS. Затем добавь входной маршрут для внешнего учебного клиента и проверь его отдельно. Успех локального port-forward остаётся полезным диагностическим сигналом, но не заменяет эту проверку.

Теперь выпусти неисправный вариант из задания blue-green. Наблюдай создание новых реплик, readiness, события и клиентские ответы. rollout status проверяет ход управляемого изменения, а rollout undo может вернуть доступную прежнюю ревизию Deployment. Это не отменяет изменения данных, внешних эффектов или удалённого хранилища. Проверка реального договора greet по-прежнему нужна при зелёном health.

Намеренно останови одну реплику и сравни это с остановкой узла, затем с потерей всей VM. Исследуй, что остаётся доступным и на каком ресурсе существует состояние. PVC — заявка на постоянное хранилище — не означает автоматически независимый диск и резерв. Данные на узле контейнерного кластера могут зависеть от его жизненного цикла. Перед удалением временного кластера восстанови сохранённые данные отдельно и докажи их пригодность.

Внешний договор, manifest, политики доступа, измерения, доказательства восстановления и найденные ограничения завершают первый перенос. После этого можно обоснованно переходить к нескольким VM, настройке kubeadm, отказоустойчивому управляющему контуру, Helm и GitOps. Эти следующие профили не выдаются за уже поднятый стенд. Первоисточники: создание kind и загрузка образов, Deployment, Service, проверки состояния.
