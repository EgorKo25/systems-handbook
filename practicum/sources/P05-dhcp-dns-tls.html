Заявка и исходные условия

STUDY-05: Адрес есть, имя или сертификат не работают

Доступ: Разрешены DNS/DHCP/TLS только внутри учебной зоны .test; внешний скан не нужен.

Наблюдаемый симптом: Ошибки имени смешаны с отказом TCP; сертификат проверяется не тем trust store.

Доказательства результата: Отдельно доказаны адрес/route, DNS-ответ, TCP, SNI/имя/цепочка сертификата и срок. HTTP по IP не выдаётся за проверку TLS.

Возврат: Вернуть DHCP/DNS конфиг из Git, тестовые ключи не коммитить.

Исходное состояние подготовлено в заданиях: P03-packet-path, P04-vlan-routing.

Контрольные точки выключенного мира: before-p05-dhcp-dns-tls перед работой и done-p05-dhcp-dns-tls после проверок. Это сохранение дискового состояния, без открытых сеансов и памяти процессов.

Начальная оценка памяти гостя: 2048 МиБ. Это бюджет для проверки состава ролей, а не измеренное требование и не гарантия достаточности для всех служб вместе.

Подготовлен рецепт. Есть рецепт DHCP/DNS для модели Cisco; отдельную службу TLS ещё предстоит собрать и проверить. Полный запуск этого сценария на QEMU и Windows пока не подтверждён.

Перед первой попыткой. Если механизм ещё не знаком, сначала прочитайте связанные главы: Сети · DHCP: получить сетевую конфигурацию, Сети · DNS: от имени до ответа, Сети · TLS: установить защищённый канал. Ниже упражнение использует эти основы; открытие подсказок не заменяет первоначального знакомства с инструментом.

Впервые настроить выдачу адресов, имена и свой TLS

В существующем .pkt продолжаются те же маршрутизаторы и Server: это не новая сеть. DHCP-пул и DNS-запись вводятся после проверки маршрута, а не вместе с его сбросом. До каждой добавки запиши действительные адреса и состояние аренды. Получение адреса не доказывает работу DNS или защищённого имени.

Для настоящего Linux-прохода дома найди официальное описание dnsmasq и руководство OpenSSL; подготовь подходящие dnsmasq-base, dnsutils, openssl и curl из подписанного репозитория своей Ubuntu. dnsmasq-base выбран как бинарник без обязательного запуска системной службы. Сверь версии и комплект зависимостей, затем установи автономно в того же гостя.

До старта dnsmasq определи namespace, интерфейс, адрес слушателя, DHCP-диапазон и исключения, маршрутизатор, домен, DNS-запись, файл аренд и журнал. Размещай собственные файлы в /srv/study/dns; не заменяй настройки systemd-resolved хоста и не запускай второй DHCP-сервер в чужом сегменте. Проверь dnsmasq --test с собственным conf-file, затем один явно выбранный процесс в учебной сети. Просмотри аренду и DNS-ответ от этого адреса, сравни запрос с правильным и неправильным именем.

Для TLS создай свою учебную CA и серверный ключ в закрытом каталоге /srv/study/tls; впиши фактическое имя сервиса в Subject Alternative Name. Настрой выбранный тестовый HTTPS-процесс с этими файлами. Клиент использует curl --cacert с конкретным CA-файлом внутри гостя; устанавливать корневой CA в рабочий Windows не требуется. Правильное имя должно пройти проверку, неправильное — отвергнуться. Нельзя заменять этот критерий curl -k. Паспорт содержит издателя/имя/срок сертификата и пути ключей, но не их содержимое; lease-файл, DNS-конфиг и CA продолжаются в следующих заданиях. Интегрированный постоянный DNS/TLS-профиль пока требует вашего фактического запуска.

Как подойти к работе

«Сайт не открывается» разбирается на разные договорённости

Пользователь сообщает об одном симптоме, но путь запроса включает получение адреса, выбор маршрута, разрешение имени, TCP, TLS и приложение. Каждый этап имеет свои данные и свои часы. Ошибочный DHCP может выдать неверный DNS; неверный DNS направит к чужому серверу; исправный TCP доведёт до TLS, где не совпадёт имя сертификата. Универсальный «проверил ping» не разделяет эти случаи.

Начальная часть выполняется в подготовленной Packet Tracer-схеме. R1 раздаёт параметры VLAN 10/20, DNS на Server содержит запись app.study.test, HTTP включается отдельной службой. После перехода клиента со статического адреса на DHCP его адрес может измениться. Сначала прочитайте фактическую выдачу, а уже затем ищите старый адрес в захвате или ACL. «Я помню, там было .10» не является текущим состоянием.

Получив адрес, спросите, для чего клиенту каждый параметр. Маска определяет представление о локальной сети; шлюз нужен к удалённым подсетям; DNS превращает имя в адрес. DNS-сервер не обязан быть шлюзом. DHCP lease не гарантирует доступность выданного DNS. Успешный HTTP по числовому IP не проверяет имя, а успешное разрешение имени не доказывает работающий TCP-порт.

TLS исследуем в настоящем Linux, а не объявляем, что простой Python HTTP server уже умеет HTTPS. Ни сертификат, ни слушающий TLS-сокет в исходной VM автоматически не созданы. Ниже приведён самостоятельный гостевой рецепт для учебного самоподписанного сертификата. Он не моделирует полностью публичный удостоверяющий центр, отзыв и автоматическое обновление; зато изолирует проверку доверия, имени и адреса назначения.

Сеть и доверие следует менять по одному условию. Если сразу исправить DNS, отключить проверку сертификата и поменять порт, вы получите зелёную страницу, но не узнаете причину. Особенно вредно оставлять curl -k как рабочее решение: команда может показать, что TCP/TLS-сервер отвечает, но уже не подтверждает подлинность сертификата. Сохраните такой опыт только как явно ослабленный диагностический тест, затем верните полноценную проверку.

Проверьте также время. Сертификат имеет начало и окончание действия, а машина после переноса или восстановления может показывать неожиданные часы. Не исправляйте ошибку срока отключением проверки. Сначала сопоставьте часы клиента с временем и сроками, реально указанными в сертификате. Затем выясните источник времени в изолированном мире: без интернета внешний сервер синхронизации недоступен. Такая неисправность важна именно для переносного стенда, хотя сама сеть и ключи при ней могут быть совершенно исправны.

Подсказки · открыть после своей попытки

Три развилки

  1. Если адрес не получен, наблюдайте DHCP в VLAN клиента и запись о выданном адресе на R1. Сложный TLS пока не участвует.
  2. Если по IP HTTP работает, а по имени нет, сравните DNS-параметр клиента, запрашиваемое имя и фактический A-ответ. Не очищайте все настройки сразу.
  3. Если HTTPS отвечает с ошибкой проверки, сохраните текст ошибки: неизвестный издатель, имя и срок — разные причины. Проверьте также часы гостя.
  4. Для отделения DNS от TLS используйте curl --resolve: оно задаёт адрес подключения, сохраняя имя URL для проверки сертификата.
Разбор и проверка результата

Эталон разделения уровней

В Packet Tracer примените R1-dhcp-add.cfg, переключите нужный клиент на DHCP, посмотрите show ip dhcp binding. Для выдачи важны идентификатор обмена, идентификатор клиента и параметры, а не только четыре знакомые буквы DORA. Затем сравните открытие http://10.44.30.10 и http://app.study.test. Намеренно неверный DNS у одного клиента должен сломать имя, сохранив исправную IP-связность. Верните параметр после доказательства.

Для TLS сначала подготовьте реальный Linux-netlab и проверьте наличие OpenSSL в госте. Ниже отдельный первый опыт с самоподписанным серверным сертификатом: клиент доверяет ему непосредственно. Это ещё не цепочка «собственный CA → выданный серверу сертификат» из полного плана установки. Не заменяйте этими файлами уже подготовленный CA и его серверные сертификаты. Файлы создаются один раз в отдельном личном каталоге гостя, вне Git; закрытый ключ не публикуется. Если app.key или app.crt уже существуют, сначала исследуйте их имя и срок, а не перезаписывайте следующей командой. Двухдневный срок выбран специально для короткого опыта; позднее истечение требует явного обновления, а не смены доверия наугад.

mkdir -p "$HOME/study-tls"
cd "$HOME/study-tls"
umask 077
openssl req -x509 -newkey rsa:2048 -sha256 -noenc -days 2 \
  -keyout app.key -out app.crt -subj '/CN=app.study.test' \
  -addext 'subjectAltName=DNS:app.study.test'
sudo ip netns exec study-server openssl s_server \
  -accept 10.44.30.10:8443 -cert app.crt -key app.key -www

Это гостевой демонстрационный сервер в текущем терминале. req -x509 создаёт самоподписанный сертификат, -newkey — новую пару ключей, -days ограничивает срок, -addext добавляет расширение SAN с допустимым именем сервера. -noenc оставляет учебный ключ без парольного шифрования; umask 077 ограничивает права создаваемых файлов. Это осознанный локальный опыт, не готовая политика хранения ключей рабочего сервиса.

sudo ip netns exec study-client curl -v \
  --cacert app.crt \
  --resolve app.study.test:8443:10.44.30.10 \
  https://app.study.test:8443/

--cacert явно задаёт доверенный файл для этого запроса, не устанавливая глобальный сертификат в ОС. --resolve заменяет разрешение конкретной пары имя:порт, а не меняет URL на IP. Поэтому проверяется имя app.study.test, и оно же передаётся как SNI — имя запрашиваемого сервера внутри TLS, если этот механизм применяется. Относительный app.crt должен быть доступен из текущего каталога; сетевое пространство имён не даёт отдельную файловую систему.

Повторите запрос без --cacert, затем с другим именем URL и соответствующим --resolve на тот же IP. Ожидайте разных ошибок доверия и имени, не записывайте их как одну «TLS сломан». Зафиксируйте version OpenSSL/curl, часы и реальный ответ. После опыта остановите s_server и сохраните конфиги без ключа. В этой подготовке команды ещё не исполнены в новом госте; результатом приёмки станет ваш настоящий протокол проверки, а не заранее напечатанный успешный вывод.

Назначение параметров проверяется по OpenSSL req и руководству curl. Для другого выпуска сначала проверьте наличие опций, затем адаптируйте пример.
