В P15 выпуск проверяли по клиентскому ответу и хешу. Теперь у тебя есть вручную настроенный сервер, журнал изменений и внешний способ проверить службу. Теперь надо получить то же полезное состояние на чистой копии. Команды из истории оболочки — исходные свидетельства, но ещё не полное описание. В них могли остаться случайные пути, забытые предварительные файлы, интерактивные ответы и действия, которые уже не нужны.

Составь договор узла: пользователь службы, каталог программы, права, конфигурация, описание запуска и состояние сокета. Затем отдели данные приложения от управляемых файлов. Повторная настройка может возвращать владельца конфигурации, но не должна перезаписывать рабочую базу тестовым содержимым. Бинарник доставляется из проверенного выпуска; его сборка на каждом целевом сервере не появляется как скрытый шаг управления.

В inventory выбери один учебный узел и параметры подключения; в playbook опиши операции с его файлами. Перед массовым применением проверь, куда разрешилось имя и под каким пользователем будет соединение. become означает переход к привилегированной роли и задаётся только там, где это требуется операцией.

Первый playbook может устанавливать каталог и файл настройки, а не сразу управлять всей ОС. Выбери состояние, проверяемое модулем: файл существует с такими байтами и правами. У каждой задачи должны быть вход и ожидаемый эффект. Оболочечный вызов, который при каждом запуске дописывает строку в файл, не станет идемпотентным только оттого, что помещён в YAML.

Проведи четыре опыта: применение на чистой копии, повтор без изменений, управляемое изменение одного параметра и ручной дрейф с последующим обнаружением. В примере ниже проверяй файл: его содержимое, владельца и права. Когда служба начнёт читать этот файл, добавь клиентскую проверку из P15. Счётчик changed=0 показывает, что задачи больше ничего не меняют; исправность службы проверяется отдельно.

  1. Начни с ansible-inventory -i inventory.ini --graph. -i выбирает конкретный файл, --graph показывает состав групп. Сверь узлы с паспортом личного мира.
  2. ansible-playbook -i inventory.ini service.yml --syntax-check проверяет разбор описания, но не устанавливает достижимость и полномочия целевого сервера.
  3. --check --diff --limit app показывает прогноз поддерживаемых задач для выбранной группы. Секретный шаблон не должен попадать в diff; поддержка check у модулей и условных действий различается.
  4. В расширенном playbook с handler проверь, что изменение нужного файла вызывает reload, а неизменённый запуск не перезапускает службу. В приведённом ниже примере handler ещё нет.
  5. Оставь аварийный вход. Playbook, который меняет SSH и сетевой доступ, проверяется на отдельной копии с рабочей консолью и контролем следующего подключения.

Ниже небольшой самостоятельный пример для каталога внутри гостя. Он не устанавливает весь продукт, а даёт наблюдаемое управляемое состояние:

Первую проверку выполняй в своей Linux VM, на отдельной ветке сохранённого мира. Создай inventory.ini; локальный тип соединения означает именно этот гость, в котором запущен Ansible. Не запускай пример из рабочей ОС компьютера.

[app]
study-app ansible_connection=local

Сохрани следующий playbook как service.yml. Проверка чистой ветки — отдельный опыт воспроизводимости; основной диск со всеми прежними задачами остаётся сохранённым.

---
- name: Study configuration contract
  hosts: app
  become: true
  tasks:
    - name: Keep study service directory
      ansible.builtin.file:
        path: /etc/study-service
        state: directory
        owner: root
        group: root
        mode: '0755'
    - name: Keep service endpoint configuration
      ansible.builtin.copy:
        dest: /etc/study-service/listen.conf
        content: "listen=127.0.0.1:8087\n"
        owner: root
        group: root
        mode: '0644'

hosts выбирает группу, а не любой доступный адрес. Полное имя модуля указывает его происхождение. state: directory требует каталог, content задаёт точные байты файла. Права записаны строкой, чтобы не зависеть от интерпретации числа YAML-парсером. Этот файл пока не читает исходный Go-сервис: подключение файла к реальному запуску службы — отдельное изменение, которое надо явно реализовать и проверить.

ansible-inventory -i inventory.ini --graph
ansible-playbook -i inventory.ini service.yml --syntax-check
ansible-playbook -i inventory.ini service.yml --check --diff --limit app --ask-become-pass
ansible-playbook -i inventory.ini service.yml --limit app --ask-become-pass

Последняя команда действительно применяет задачи; предыдущий прогноз не заменяет её. После первого --check --diff на пустой цели проверь, появился ли каталог. В локальном опыте с Ansible Core 2.21.5 обе задачи предсказали изменения, но каталог остался отсутствующим. Если другой модуль пытается читать результат предыдущей задачи, прогноз может остановиться: каталог ещё не создан. --ask-become-pass запрашивает пароль для повышения прав, не записывая его в inventory. После локального опыта замени соединение на SSH к уже настроенному учебному узлу: задай его действительный адрес, пользователя, порт и ключ из паспорта. Повтори прежние проверки через разрешённый путь, включая бастион, если он требуется; работа локального модуля не доказывает доступность удалённой машины.

После первого успешного применения проверь файл и каталог в учебном госте:

sudo stat -c '%U:%G %a %n' /etc/study-service /etc/study-service/listen.conf
sudo cat /etc/study-service/listen.conf

Ожидаются root:root 755 для каталога, root:root 644 для файла и строка listen=127.0.0.1:8087. При исходном отсутствии объектов задачи должны сообщить изменения; если они уже существовали с нужным состоянием, первый результат может отличаться. Повтори обычную команду: при неизменных входах и окружении ожидается changed=0. Сверь файл снова; счётчик относится к задачам этого запуска, а не ко всей системе.

Теперь замени 8087 на 8088 в service.yml и примени playbook. Ожидай changed=1 и строку listen=127.0.0.1:8088. Затем на отдельной учебной ветке вручную замени 8088 на 8099 в listen.conf, не меняя playbook. Повтори --check --diff: для поддерживаемого copy ожидается показанное различие, но файл от одного прогноза не восстанавливается. Обычное применение должно вернуть listen=127.0.0.1:8088; затем ещё раз проверь содержимое, владельца и права и повтори запуск до changed=0. Ошибка доступа, неподходящий узел или неожиданный diff останавливают опыт до применения. Этот файл не подключён к Go-сервису, поэтому клиентский ответ и reload пока не являются доказательством его применения. Если задача всегда считает себя изменившейся, исследуй её семантику, метки времени, результат шаблонизации и внешние входы.

Для настоящего описания службы добавь доставку бинарника, пользователя, unit и проверку здоровья. Handler reload должен зависеть от тех файлов, которые реально влияют на процесс. Если изменение требует нового исполняемого образа, одного перечитывания конфигурации может быть недостаточно. Последовательность daemon-reload, смены файла, перезапуска и проверки согласуй с systemd и договором приложения.

Режим проверки не является изолированной копией системы. Задачи могут быть явно настроены на обычное исполнение даже при check, а результаты предыдущих предполагаемых изменений могут отсутствовать. Сначала прочитай используемые модули и условия, затем делай вывод о безопасности прогноза. Для нескольких узлов добавь небольшие последовательные партии и условие остановки после плохой проверки, чтобы не разнести одну ошибку сразу на весь мир.

В отчёт войдут версия Ansible, перечень узлов, ревизия описания, четыре результата опытов; если файл подключён к службе, приложи и результаты клиентских проверок. Секреты и закрытые ключи находятся вне Git. Первоисточник: возможности и ограничения check/diff. Полный профиль Ansible ещё не развёрнут и не запускался в этой версии стенда.
