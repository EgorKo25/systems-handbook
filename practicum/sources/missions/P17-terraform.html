Раздели два договора. Создать VM, сеть или диск — работа с ресурсом платформы. Настроить пользователя и службу внутри уже работающей ОС — изменение гостя. У этих действий разные учётные данные, наблюдения и способы возврата. В предыдущем задании Ansible получил существующий адрес; теперь надо описать, откуда взялся сам узел и какое состояние должно пережить его замену.

Terraform строит предполагаемые действия из описания, сохранённой карты ресурсов и наблюдений через провайдер. Провайдер — программный компонент, который обращается к API выбранной платформы. Пока поставщик ресурса не выбран и не подготовлен, код с красивым названием VM ничего не создаёт. Для личного мира отдельно фиксируются версия Terraform, источник и версия провайдера, его зависимости для автономного запуска и полномочия учётной записи.

Начни с карты собственности: какие объекты принадлежат именно учебному проекту, какие уже существуют и кем управляются. Диск с PostgreSQL и временный узел не обязаны иметь один жизненный цикл. Замена машины из-за нового образа не должна незаметно означать удаление данных. Название ресурса в коде — адрес объекта в модели Terraform, а не просто отображаемое имя в панели; изменение адреса может требовать явного переноса связи.

State, состояние Terraform, хранит соответствия адресов модели внешним объектам и дополнительные сведения. Потеря state не удаляет действительный сервер, но лишает управление этой картой. Скопированное старое state не возвращает внешний мир назад во времени. Согласованное восстановление сначала выясняет, что реально существует и какие операции успели завершиться, а затем восстанавливает владение и необходимую карту.

Результат задания — не факт выполнения apply. Нужно объяснить план, получить предсказуемый объект, выполнить настройку гостя и те же клиентские проверки, получить пустой повторный план и исследовать ручное изменение. После этого проверяется безопасная замена временного узла с сохранением выбранных данных. Платный ресурс создаётся только после отдельного выбора провайдера, тарифа и полномочий.

  1. terraform init подготавливает рабочий каталог и зависимости. Автономный запуск требует заранее подготовленного источника провайдеров и соответствующих платформе файлов; lock-файл сам не содержит исполняемые плагины.
  2. terraform fmt -check проверяет оформление; terraform validate — допустимость конфигурации на своём уровне. Ни одна команда не подтверждает, что учётная запись имеет нужные права или в облаке есть свободный ресурс.
  3. terraform plan -out=change.plan сохраняет конкретный план, terraform show change.plan показывает его. Обработай план как чувствительный файл: скрытое отображение секрета не гарантирует отсутствия его в данных.
  4. Перед terraform apply change.plan проверь ожидаемые создание, изменение и замену, адреса ресурсов, учётную запись и состояние данных. Более позднее изменение среды может сделать прежние предположения неверными.
  5. Не снимай блокировку только из-за ожидания. Выясни владельца и факт работающей операции. Запуск двух писателей против одного state создаёт проблему независимо от правильности каждого описания.

Первую механику состояния можно разобрать без платного облака и внешнего провайдера. В отдельной папке гостя следующий пример использует встроенный terraform_data:

Сохраните его в main.tf. Это HCL, язык описания Terraform: resource объявляет управляемый объект, первая строковая метка задаёт тип, вторая — локальное имя. Вместе они образуют адрес terraform_data.service_contract. Фигурные скобки задают блок, имя = значение — аргумент, вложенное значение input здесь является объектом из двух строк. Блок output показывает значение с указанного атрибута созданного ресурса. Это не Bash и не инструкция создать сервер по записанному адресу. Используйте установленный выпуск Terraform с поддержкой terraform_data; программа и выбранные зависимости подготовлены до первого init.

resource "terraform_data" "service_contract" {
  input = {
    endpoint = "10.44.30.10:8087"
    role     = "study-service"
  }
}

output "service_contract" {
  value = terraform_data.service_contract.output
}

Здесь сохраняется значение в жизненном цикле ресурса Terraform. Не создаются VM, адрес, маршрут и слушатель. Это специально ограниченный опыт: init, plan, apply, повторный plan и исследование terraform state list/terraform state show terraform_data.service_contract. Измени входной адрес и предскажи план до запуска. Такая модель помогает увидеть, какие сведения известны до исполнения и что сохраняется после него, но не подменяет следующий опыт с настоящим ресурсом.

Для полного задания выбери доступный локальный или облачный провайдер и один временный объект. Зафиксируй его устойчивый идентификатор и пометь принадлежность личному стенду. Сохрани зависимости до отключения интернета. Создай объект, дождись фактической готовности, передай его адрес в inventory Ansible и выполни прежние проверки. Повторный Terraform plan проверяет ресурсы платформы, а повторный Ansible — управляемые свойства гостя; один результат не доказывает другой.

Внеси небольшое изменение вне Terraform через собственный управляющий интерфейс платформы. Следующий план должен обнаружить или осмысленно учесть его в зависимости от описания и поведения провайдера. Изменение файлов самого state вручную не является реалистичным моделированием дрейфа машины. Если объект существовал заранее, разбор импорта должен связать его идентификатор с правильным адресом ресурса и сопровождаться конфигурацией, соответствующей реальности.

Отдельный опыт замены проводится только над временной копией. Прочитай в плане, какое свойство требует пересоздания. Проверь расположение данных и наличие настоящего восстановления. Защита от удаления, если используется, предотвращает определённый переход в модели, но не становится резервной копией и не спасает от всех действий администратора платформы. Для диска и базы сохраняется самостоятельный договор хранения.

Согласуй доступ к state и его блокировке. При нескольких исполнителях нужен backend с предусмотренной координацией; разные backends поддерживают её по-разному. Локальный state для одного изолированного опыта допустим, но его нельзя автоматически объявить совместной системой управления. Не коммить state, сохранённые планы и реальные ключи в публичный Git. Метка sensitive влияет на отображение значений, а не сама шифрует все файлы.

Заверши проверкой плана удаления только собственных временных объектов. Сначала просматривается план и сохранность данных; удаление не является универсальной кнопкой возврата. В отчёте должны быть ревизия описания, версии, идентификаторы, затронутые ресурсы, результат повторного плана и фактическая процедура восстановления. Источники: состояние, хранение, блокировка, встроенная учебная модель. Провайдер личного стенда пока не выбран.
