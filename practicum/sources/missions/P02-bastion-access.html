Кто открывает соединение к внутреннему серверу

В P01 клиент входил в учебную VM через 127.0.0.1:2222. В P02 этот порт ведёт на новую учебную VM, бастион. Она подключена к внутренней сети и может открыть TCP-соединение к серверу приложения. По этому каналу клиент на ноутбуке устанавливает второй сеанс SSH и сам проверяет ключ конечного сервера.

Для задания нужно отдельно подготовить две VM. Контроллер из P01 запускает одну VM. Сохраните её диск и учётную запись: эту машину можно использовать как сервер приложения. Вторую VM подготовьте как бастион с отдельными учётной записью и ключом узла. Оставьте доступ к консолям обеих машин.

У бастиона есть вход с хоста через 127.0.0.1:2222 и интерфейс 10.44.30.2/24 во внутреннем сегменте. У сервера приложения есть интерфейс 10.44.30.10/24 в том же сегменте. Сегмент изолирован от рабочей сети. У конечной машины уберите проброс порта P01 перед приёмкой: на хосте должен остаться только вход через бастион.

Доступность 10.44.30.10:22 с bastion — одна проверка; отсутствие прямого пути с клиента — другая. Отказ прямого доступа не доказывается одной командой ping: ICMP и TCP могут фильтроваться по-разному. Нужны схема виртуальных устройств, список опубликованных портов и ограниченный TCP-тест. Сканировать внешние диапазоны или корпоративную сеть для этого задания не требуется.

Сформулируйте ограничение до настройки: кому, откуда, на какой узел и какой порт разрешено подключение. Отдельно укажите, кто выдаёт доступ и кто способен вернуть его после ошибки. Слова «доступа нет» без этих четырёх координат бесполезны: у пользователя может отсутствовать прямой маршрут, но существовать разрешённый туннель; у администратора может быть консоль, но не право читать данные приложения. Проверяем конкретную границу, не абстрактную закрытость всей машины.

Сначала выясните, на каком переходе отказ

  1. Проверьте отдельную аутентификацию на bastion. У ограниченного jump-пользователя интерактивная оболочка может быть намеренно запрещена; подтверждение личности и запуск shell — разные стадии. Если до первой не дошли, ошибка целевого сервера пока не наблюдалась.
  2. Попросите инструктора проверить с bastion адрес, маршрут и TCP к конкретному 10.44.30.10:22 либо используйте отдельный явно выданный диагностический доступ. Ограниченный jump-пользователь из разбора не имеет shell и не может выполнить там ip или nc. Его собственное наблюдение — результат открытия разрешённого SSH-канала и подробный вывод клиента. Разрешение имени назначения может выполняться не там, где вы ожидаете; сначала используйте известный адрес.
  3. Посмотрите, разрешает ли sshd bastion локальное TCP forwarding. Право на shell само по себе не является документированным разрешением ProxyJump.
  4. Различайте отказ открыть канал, отказ проверить host key приложения и отказ войти пользователем приложения. В подробном выводе SSH это разные события.

Пример клиента и границы его доказательства

После подготовки двухмашинного профиля создайте файл private/ssh_config в личном комплекте. Пример выполняется из его корня; заранее подготовьте каталоги и пользовательские ключи. Отдельный runtime/known_hosts_p02 не смешивает ключ нового бастиона с сервером P01 на том же адресе и порту:

Host study-bastion
    HostName 127.0.0.1
    Port 2222
    User jump
    IdentityFile ./runtime/private/jump_ed25519
    IdentitiesOnly yes
    UserKnownHostsFile ./runtime/known_hosts_p02
    GlobalKnownHostsFile none
    StrictHostKeyChecking ask

Host study-app
    HostName 10.44.30.10
    Port 22
    User student
    IdentityFile ./runtime/private/app_ed25519
    IdentitiesOnly yes
    ProxyJump study-bastion
    UserKnownHostsFile ./runtime/known_hosts_p02
    GlobalKnownHostsFile none
    StrictHostKeyChecking ask
ssh -F ./private/ssh_config -v study-app hostname

-F загружает указанный файл. В нём Host задаёт имя, по которому клиент выбирает блок настроек, а HostName — адрес подключения. Прежде чем запускать команду, выпишите алгоритм и отпечаток ключа каждой VM через её консоль, как в P01. StrictHostKeyChecking ask попросит подтвердить новый ключ, а GlobalKnownHostsFile none оставит в качестве источника доверия указанный файл упражнения.

  1. Клиент приходит через 127.0.0.1:2222 на бастион. При первом соединении сравните его ключ с результатом из консоли бастиона. После проверки узла его SSH-сервер проверяет ключ пользователя jump.
  2. SSH-сервер бастиона проверяет разрешение открыть соединение к 10.44.30.10:22. Если канал открыт, клиент на ноутбуке начинает новый SSH-обмен с конечной VM через этот канал.
  3. По запросу клиента отдельно сверьте ключ конечной VM. Затем её SSH-сервер проверяет пользователя student и его ключ. Оба закрытых ключа используются на ноутбуке. Полученное после входа имя из hostname должно совпасть с именем из консоли конечной VM.

Прервите подключение при несовпадении любого отпечатка. Если обмен остановился раньше, ищите последнюю стадию в выводе -v: отказ открыть канал на бастионе и отказ войти пользователем на конечную VM возникают в разных местах.

В будущем профиле отдельный пользователь jump на bastion может получить такой ограниченный фрагмент sshd config:

Match User jump
    AllowTcpForwarding local
    PermitOpen 10.44.30.10:22
    AllowAgentForwarding no
    X11Forwarding no
    PermitTTY no
    MaxSessions 0

Здесь local означает forwarding с точки зрения SSH-клиента; через него работает прыжок. PermitOpen ограничивает назначение канала, MaxSessions 0 запрещает shell/login/subsystem-сеансы, сохраняя forwarding. Одно PermitTTY no не запрещает исполнение команд без терминала. Если оставить пользователю произвольный shell и возможность запускать свои программы, запрет одной встроенной функции forwarding не превращается в полную сетевую изоляцию. Конфигурацию надо проверять на установленном выпуске OpenSSH Server, включая наследование других директив и Match.

Применение начинается с sshd -t и сохранённой rescue-консоли. Затем проверьте новый разрешённый вход, запрещённое forwarding к иному порту, отказ интерактивного shell у jump и независимую авторизацию student на приложении. Не закрывайте последний рабочий сеанс до завершения этих проверок.

Приёмка — не снимок одного успешного терминала. Нужны: опубликован только management bastion; приложение не имеет прямой публикации; через ProxyJump выполнена безопасная команда вроде hostname; незарегистрированный пользовательский ключ отклонён при отдельной пробе без других методов входа; запрещённое назначение не открывается; инструктор способен вернуть настройки через консоль. В отчёте сохраните роли, fingerprint и наблюдения без закрытых ключей. Холодную точку делайте для обеих выключенных машин как одной связанной группы. В следующей главе исследуется маршрут пакета в отдельной модели Linux; её адреса совпадают с частью этого примера, но сами сети не объединяются.
