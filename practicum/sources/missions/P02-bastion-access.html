Маршрут управления не обязан совпадать с прямым доступом

Внутренний сервер не опубликован на ноутбуке, но это ещё не означает поломку. У администратора есть разрешённый вход на bastion — промежуточный узел управления. Тот видит закрытую сеть и может открыть соединение к целевому SSH. Клиент организует второй защищённый сеанс через этот канал. Требуется доказать, что работает именно эта схема, а не случайно открытый наружу порт.

Разделите три вида доступа. Консоль гипервизора позволяет инструктору восстановить машину. SSH на bastion даёт право пользоваться точкой входа. SSH на приложении проверяет уже отдельного пользователя целевого сервера. Одно право не должно автоматически превращаться во все остальные. Два пользователя могут иметь одинаковое имя, но это две проверки в разных ОС. Ключ узла bastion и ключ узла приложения клиент проверяет отдельно.

Этот профиль ещё предстоит развернуть. Нынешний контроллер запускает одну VM с localhost SSH; он не создаёт автоматически второй сервер, интерфейсы и ограничивающие правила. Три namespace из netlab тоже не являются тремя отдельными компьютерами с независимыми файловыми системами. Поэтому ниже дан точный контракт будущего опыта и конфигурация клиента. До подготовки ролей честный результат — «профиль не готов», а не симуляция успешного ProxyJump.

Для первого варианта инструктор создаёт две отдельные VM. У bastion есть management-интерфейс с опубликованным на хосте 127.0.0.1:2222 и внутренний интерфейс 10.44.30.2/24. У приложения только внутренний 10.44.30.10/24, без hostfwd, bridge в LAN и второго скрытого management-порта. Внутренний сегмент реализуется средствами разрешённого гипервизора и не соединяется с рабочей сетью. Бюджет памяти уточняется после запуска, обе машины не обязаны содержать полный стек.

Доступность 10.44.30.10:22 с bastion — одна проверка; отсутствие прямого пути с клиента — другая. Отказ прямого доступа не доказывается одной командой ping: ICMP и TCP могут фильтроваться по-разному. Нужны схема виртуальных устройств, список опубликованных портов и ограниченный TCP-тест. Сканировать внешние диапазоны или корпоративную сеть для этого задания не требуется.

Сформулируйте ограничение до настройки: кому, откуда, на какой узел и какой порт разрешено подключение. Отдельно укажите, кто выдаёт доступ и кто способен вернуть его после ошибки. Слова «доступа нет» без этих четырёх координат бесполезны: у пользователя может отсутствовать прямой маршрут, но существовать разрешённый туннель; у администратора может быть консоль, но не право читать данные приложения. Проверяем конкретную границу, не абстрактную закрытость всей машины.

Сначала выясните, на каком переходе отказ

  1. Проверьте отдельную аутентификацию на bastion. У ограниченного jump-пользователя интерактивная оболочка может быть намеренно запрещена; подтверждение личности и запуск shell — разные стадии. Если до первой не дошли, ошибка целевого сервера пока не наблюдалась.
  2. С bastion проверьте адрес, маршрут и TCP к конкретному 10.44.30.10:22. Разрешение имени назначения может выполняться не там, где вы ожидаете; сначала используйте известный адрес.
  3. Посмотрите, разрешает ли sshd bastion локальное TCP forwarding. Право на shell само по себе не является документированным разрешением ProxyJump.
  4. Различайте отказ открыть канал, отказ проверить host key приложения и отказ войти пользователем приложения. В подробном выводе SSH это разные события.

Пример клиента и границы его доказательства

Создайте отдельный клиентский файл в личном каталоге, не меняя глобальный SSH config рабочего компьютера. Пути к ключам и known_hosts должны указывать на ваш разрешённый каталог; пример предполагает запуск из корня личного комплекта:

Host study-bastion
    HostName 127.0.0.1
    Port 2222
    User jump
    IdentityFile ./runtime/private/jump_ed25519
    IdentitiesOnly yes
    UserKnownHostsFile ./runtime/known_hosts

Host study-app
    HostName 10.44.30.10
    Port 22
    User student
    IdentityFile ./runtime/private/app_ed25519
    IdentitiesOnly yes
    ProxyJump study-bastion
    UserKnownHostsFile ./runtime/known_hosts
ssh -F ./private/ssh_config -v study-app

-F выбирает этот конфиг. Host — локальный псевдоним, HostName — реальное назначение; совпадать им необязательно. ProxyJump указывает промежуточный вход. Закрытый ключ приложения остаётся у клиента: для такого пути не надо копировать его на bastion и включать agent forwarding. Однако сам bastion остаётся важной границей доверия и может нарушать доступность канала.

В будущем профиле отдельный пользователь jump на bastion может получить такой ограниченный фрагмент sshd config:

Match User jump
    AllowTcpForwarding local
    PermitOpen 10.44.30.10:22
    AllowAgentForwarding no
    X11Forwarding no
    PermitTTY no
    MaxSessions 0

Здесь local означает forwarding с точки зрения SSH-клиента; через него работает прыжок. PermitOpen ограничивает назначение канала, MaxSessions 0 запрещает shell/login/subsystem-сеансы, сохраняя forwarding. Одно PermitTTY no не запрещает исполнение команд без терминала. Если оставить пользователю произвольный shell и возможность запускать свои программы, запрет одной встроенной функции forwarding не превращается в полную сетевую изоляцию. Конфигурацию надо проверять на установленном выпуске OpenSSH Server, включая наследование других директив и Match.

Применение начинается с sshd -t и сохранённой rescue-консоли. Затем проверьте новый разрешённый вход, запрещённое forwarding к иному порту, отказ интерактивного shell у jump и независимую авторизацию student на приложении. Не закрывайте последний рабочий сеанс до завершения этих проверок.

Приёмка — не снимок одного успешного терминала. Нужны: опубликован только management bastion; приложение не имеет прямой публикации; через ProxyJump выполнена безопасная команда вроде hostname; неверный пользовательский ключ отклонён; запрещённое назначение не открывается; инструктор способен вернуть настройки через консоль. В отчёте сохраните роли, fingerprint и наблюдения без закрытых ключей. Холодную точку делайте для обеих выключенных машин как одной связанной группы.
