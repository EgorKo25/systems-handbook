Работающий процесс — ещё не доступная служба

У задания две фазы доступа. Сначала исполнитель видит только клиентский сервисный порт и выданные журналы; он записывает запрос, время, ошибку и гипотезу. Команды ip netns exec, ss, запуск сервера и захват ниже относятся ко второй фазе, когда инструктор после этих наблюдений явно выдал shell-доступ и нужные права внутри гостя. Если стенд готовит один человек, сначала под ролью инструктора создайте исходный HTTP-процесс, затем исследуйте его со стороны клиента и отметьте смену роли. Наличие своей консоли владельца не считается доказательством диагностики через первоначальный ограниченный доступ.

На сервере есть PID, команда запуска не завершилась, монитор процесса зелёный. Клиент при этом не получает страницу. Необходимо разделить существование процесса, наличие слушающего сокета, сетевую достижимость и правильный прикладной ответ. Каждое следующее утверждение сильнее предыдущего. Даже HTTP 200 не доказывает, что ответило нужное приложение с нужной версией.

В этом опыте у сервера только учебный адрес 10.44.30.10; клиент находится в другой /24 за router. Сначала подтвердите маршрут предыдущего задания. Затем исследуйте, к какому адресу привязан слушающий сокет. 127.0.0.1 означает loopback конкретного сетевого пространства имён, а не «этот сервер доступен отовсюду». 0.0.0.0 у слушающего IPv4-сокета означает все локальные IPv4-адреса данного пространства; это не адрес, который следует выдавать клиенту как назначение.

Воспроизведение выполняется настоящим Python HTTP server внутри Linux-гостя. Он нужен как маленький прозрачный объект диагностики, а не как production-сервер. Запускайте его из отдельного пустого учебного каталога: стандартный сервер публикует содержимое текущего каталога. Домашние документы, ключи и дампы не должны случайно стать тестовой веб-страницей. Сам QEMU по умолчанию не публикует этот 8080 на LAN, но границу доступа всё равно надо уметь объяснять.

Наблюдайте путь из двух точек: локально в namespace сервера и с клиента. Если loopback-запрос успешен, а запрос к серверному IP отвергается, это ценная развилка. Если SYN доходит, но следует RST, TCP-стек отвечает; если нет ответа, причин больше. Если TCP установлен, но HTTP вернул 404, маршрут уже выполнил свою работу, а вы расследуете URL/файлы/приложение. Не перезапускайте маршрутизатор для исправления неверного пути страницы.

Отдельный вопрос — постоянный запуск. Процесс переднего плана, который вы видите в терминале, не обязан пережить его закрытие или перезагрузку. Для системной службы позже потребуются модуль запуска systemd, пользователь, рабочий каталог, окружение, правила перезапуска и журнал. Но systemd не должен скрыть непонимание исходной команды. Сначала запустите её вручную, докажите сокет и ответ, только потом перенесите команду в модуль запуска.

Проверьте и содержимое ответа. В вашей сети могут одновременно жить старая версия, временный сервер и прокси. Ответ с правильного порта не гарантирует нужную программу. Контрольная строка версии и ожидаемый путь запроса дают простое прикладное доказательство. Позже в P10 его дополнит проверка зависимости от базы; пока достаточно не спутать страницу списка файлов с готовым приложением. Это помогает обнаруживать ошибочные выпуски, которые внешне выглядят доступными.

Неизвестный отказ сужается одним фактом за раз

  1. В том ли сетевом пространстве имён запущен процесс? ss в основном гостевом стеке не показывает автоматически все слушающие сокеты других пространств имён.
  2. Сравните запрос к 127.0.0.1:8080 и 10.44.30.10:8080 внутри server. Затем сделайте второй запрос с client.
  3. В захвате различайте отсутствие SYN, SYN без ответа, RST, установленное соединение и HTTP-ошибку. У этих наблюдений разные следующие проверки.
  4. Сначала исправьте адрес привязки, сохранив прежний маршрут. Если меняете два слоя сразу, доказать конкретную причину сложнее.

Воспроизводимый неправильный адрес привязки

После подготовки netlab создайте отдельный каталог внутри гостя и тестовый файл с узнаваемым содержимым. В первом терминале запустите заведомо локальный слушающий сокет:

mkdir -p "$HOME/study-http"
cd "$HOME/study-http"
printf '%s\n' 'study-service version=bind-lab' > index.html
sudo ip netns exec study-server python3 -m http.server 8080 --bind 127.0.0.1

В другом гостевом терминале:

sudo ip netns exec study-server ss -lntp
sudo ip netns exec study-server curl -v --max-time 3 http://127.0.0.1:8080/
sudo ip netns exec study-client curl -v --max-time 3 http://10.44.30.10:8080/

--max-time ограничивает общее время попытки, поэтому ошибочная конфигурация не оставляет упражнение ждать неопределённо. Успешный loopback и отказ с клиента здесь ожидаемы. Сохраните exit status сразу после команды: следующая команда перезапишет $?. Не подменяйте результат фразой «curl не работает» — запишите, на какой стадии произошёл отказ.

В первом терминале остановите сервер Ctrl+C и повторите ту же команду с --bind 10.44.30.10. Повторный клиентский запрос должен получить наш узнаваемый текст, если маршрут исправен. Это гипотеза для реального прогона, не заранее измеренный результат. Проверьте также старый loopback: после привязки только к конкретному IP он уже не обязан обслуживаться. Такой отрицательный тест показывает, что адрес привязки действительно имеет смысл.

Для трассы используйте tcpdump -ni study-r1 'tcp port 8080' внутри router. SYN, SYN/ACK и ACK создают TCP-соединение; HTTP-ответ возникает позже. Если вы смотрите только ICMP, прикладной обмен туда не попадёт. Если нужен текст незашифрованного HTTP, отдельный -A показывает печатную часть, но не превращает произвольные TCP-сегменты в гарантированно целый запрос: данные могут делиться на сегменты.

Переход к постоянному сервису начинается с точной рабочей команды и её пользователя. Для модуля запуска нужны абсолютный путь исполняемого файла, доступный рабочий каталог и разрешения на чтение файлов. Журнал сервиса и его состояние помогают найти ошибку запуска; ss подтверждает слушающий сокет; запрос клиента подтверждает поведение. Это три независимых доказательства. Если модуль active, а нужного сокета нет, читайте его тип и логи вместо общего «systemd зелёный».

В дальнейшем Go-сервис заменит временный Python, а PostgreSQL добавит локальный сокет Unix. Там файловый путь выбирает адрес подключения, но передаётся сетеподобный поток между процессами; права каталога и выбранное сетевое пространство имён становятся ещё одним слоем доступа. Здесь не надо открывать PostgreSQL раньше, чем вы научились отличать процесс от слушающего сокета. Сохраните исходный ошибочный адрес привязки, исправление, отрицательный тест и новую контрольную точку после корректного завершения сервера.
