Первый доступ: не перепутать сервер с его сетью

Вам передали машину, но фраза «сервер установлен» ещё не отвечает на вопросы, где заканчивается установщик, с какого диска загружается система и существует ли вообще путь для SSH. До первой сетевой команды нарисуйте границу: физический компьютер запускает QEMU, QEMU предоставляет виртуальный диск и сетевое устройство, внутри загрузилась другая ОС. Команда в её консоли меняет гостя. Та же команда в терминале Ubuntu-хоста меняет домашний компьютер. Сходство приглашений оболочки эту границу не отменяет.

Начните с карточки принятия узла: архитектура, версия ОС, диск загрузки, имя пользователя, интерфейсы, адреса и способ аварийного входа. Пароли и закрытые ключи в карточку не включайте. Сведения должны получиться из наблюдений, а не из подписи на схеме. Один виртуальный интерфейс с адресом ещё не означает доступность сервера с другого компьютера: QEMU может скрывать его за пользовательской сетью и пропускать только явно опубликованный localhost-порт.

Первоначальная консоль нужна именно тогда, когда сеть ещё неизвестна. Графическое окно установщика позволяет поставить систему; последовательная консоль затем даёт вход без графического рабочего стола. Это каналы управления, а не обход ограничения упражнения. В будущих заданиях доступ к ним будет отдельной ролью инструктора: обычный пользователь расследует отказ через выданный путь, а инструктор сохраняет возможность восстановить стенд после ошибочного firewall.

Сначала проверьте состояние подготовки. В каталоге labs-personal/vm команда python3 world.py doctor только читает окружение. Отсутствие QEMU — настоящий блокер загрузки, а не ошибка будущего Linux. Наличие /dev/kvm и доступность его для пользователя тоже разные наблюдения. Сейчас поставляется рецепт и управляющий код; образ гостя не включён, его загрузка ещё не испытана. Порядок подготовки позволяет пройти этот этап дома с проверенным официальным ISO.

После создания мира команда python3 world.py start --console window открывает экран VM для первоначального входа и восстановления сети; предварительно её можно посмотреть с --dry-run. Обычный start использует последовательную консоль в текущем терминале. Для оконного варианта нужна сборка QEMU с работающим графическим выводом; реальное окно пока не проверено. Не запускайте вторую копию уже работающего диска ради смены консоли: сначала штатно выключите гостя.

Не стремитесь исправить всё одним действием. Отсутствующий SSH, неправильная сеть и неверный пароль дают разные признаки. До изменения запишите гипотезу и ожидаемый результат: например, «служба не установлена; после установки появится слушающий сокет на 22» или «сокет есть, но QEMU не опубликовал порт; внутри гостя соединение работает, с хоста нет». Так первое включение становится расследованием, а не серией случайных перезапусков.

Ещё один полезный отрицательный результат: выключенная VM не должна продолжать отвечать как прежний сервер. Если после её выключения на том же порту по-прежнему есть SSH, вы общаетесь с другим процессом. Это повод сверить владельца порта и ключ узла, а не поздравлять себя с устойчивостью. Для первого дня такая простая проверка лучше сложной автоматизации, основанной на неверной карте.

Подсказки по степени вмешательства

  1. Убедитесь, что видите приглашение установленной ОС, а не установщика, firmware или monitor QEMU. Monitor управляет виртуальным питанием и устройствами; он не исполняет Bash.
  2. Сверьте источник трёх наблюдений: hostnamectl, lsblk, ip -brief address. Получите их именно в гостевой консоли.
  3. Проверьте сначала службу и слушающий сокет, затем опубликованный путь через QEMU. Не меняйте пароль, если TCP до службы ещё не доходит.
  4. Перед изменением сетевого доступа сохраните консоль. Закрывать единственный действующий вход ради проверки нового — ненужный способ усложнить упражнение.

Разбор и достаточные доказательства

hostnamectl
cat /etc/os-release
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
ip -brief address
ip route show
systemctl status ssh --no-pager
sudo ss -lntp

lsblk показывает дерево блочных устройств; явный список -o выбирает нужные столбцы. Смотрите одновременно размер, тип, файловую систему и точку монтирования: имя vda само по себе не означает, что его можно форматировать. ip -brief сокращает представление адресов, но не заменяет таблицу маршрутов. У ss флаги -l, -n, -t, -p выбирают слушающие TCP-сокеты, числовые адреса и информацию о процессах; без прав часть сведений о процессе может отсутствовать.

Если ssh.service не найден, установка OpenSSH Server внутри гостя — разумная следующая операция. Если служба failed, сначала прочитайте журнал. Если active, но нужного сокета нет, исследуйте настройки и способ активации. Не считайте точное имя процесса или один зелёный статус универсальным доказательством: в Ubuntu возможна активация через сокетный модуль systemd. Существенно, кто принимает соединение на ожидаемом адресе и что происходит при настоящем запросе.

В текущем профиле адрес гостя обычно выдаёт DHCP QEMU. Подключение хоста направлено на 127.0.0.1:2222, откуда QEMU передаёт TCP на гостевой 22. Адрес 10.0.2.15 не становится адресом рабочего компьютера. Успех подключения по loopback не доказывает доступ из локальной сети — он намеренно ограничен одним хостом.

Приёмка включает новый SSH-сеанс, сверку ключа сервера через консоль и восстановление после выключения. Завершите гостя командой sudo poweroff, дождитесь выхода QEMU, затем сохраните clean-base с --guest-stopped. Обычный выход из SSH не выключает ОС. Закрытое окно QEMU не доказывает согласованного завершения БД. После следующего запуска повторите минимальную проверку: нужный диск загрузился, сохранённый файл на месте, второй вход работает. Это и есть первая проверенная точка вашего мира.
