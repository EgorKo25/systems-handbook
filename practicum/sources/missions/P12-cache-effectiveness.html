Сначала определить, что разрешено ускорять

Кэш — восстановимая копия, а не автоматически новый источник истины. В заявке нужно назвать ключ, содержимое, владельца исходных данных и допустимую давность ответа. Попадание, hit, означает, что нужная копия найдена; промах, miss, требует обращения к источнику либо другой выбранной реакции. Попадание не доказывает актуальность. Если ускоренный ответ возвращает старую цену после подтверждённого изменения, это может быть ошибкой контракта даже при превосходном среднем времени.

Текущий учебный Go-сервис имеет только healthz и greet и не использует PostgreSQL или Redis. Задание не притворяется, что к нему уже прикручен кэш. Здесь есть независимая ручная проверка семантики Redis и будущий контракт интеграции приложения. Настоящий сравнительный прогон станет следующим изменением продукта: драйвер, ключи, сериализация, метрики, таймауты, обход кэша и тест свежести добавляются и проверяются явно.

Рабочий набор и одинаковая единица сравнения

Зафиксируйте состав запросов и распределение ключей. Рабочий набор — данные, востребованные в выбранном интервале, а не весь объём базы. Повторение одного ключа и равномерное чтение миллиона разных ключей создают разную локальность. Холодный запуск, прогрев и установившийся режим измеряют отдельно. Сравниваемые прогоны сохраняют ту же последовательность запросов и тот же критерий корректности; различаются только изучаемым изменением.

Учебная выборка: без кэша 10 000 запросов заняли по 20 мс. Во втором искусственном наборе 9800 попаданий заняли по 1 мс, 100 обычных промахов — по 21 мс, 100 медленных — по 201 мс. Среднее стало (9800+2100+20100)/10000=3,2 мс, доля попаданий 98%. По правилу ближайшего ранга p99 — наблюдение номер 9900, то есть 21 мс, а p99,9 — номер 9990, то есть 201 мс. Среднее улучшилось, хвост ухудшился. Эти числа сконструированы для проверки интерпретации, а не измерены на вашей VM.

При одном обращении к источнику на каждый промах число таких чтений сократилось с 10 000 до 200. Но серверные повторы, фоновые обновления, проверки версий и записи могут добавить работу. Общая метрика hit rate Redis считает не HTTP-операции приложения, а соответствующие обращения к ключам. Несколько GET на один запрос и другие клиенты меняют знаменатель. Нужны собственные метрики попыток, правильных результатов, обращений к источнику и ошибок.

Где измерять цену

Предположим, источник допускает 20 одинаковых по стоимости операций/с, а требуется 200 чтений/с и две записи/с. Для чтений остаётся 18 операций/с; при одном чтении источника на промах нужно h ≥ 1−18/200=0,91. При 98% получится четыре промаха плюс две записи, всего шесть операций/с. Это расчётная модель с одинаковой стоимостью; если запись дороже, надо считать спрос на ограничивающий ресурс, а не складывать разные операции как одинаковые.

Для CPU, то есть процессорного времени, памяти и сети нужен отдельный бюджет. Копия добавляет сериализацию, обмен с кэшем, служебные структуры, процесс и сопровождение. Значение maxmemory ограничивает определённый учёт Redis, а не полный RSS, резидентную память процесса. Сверяйте лимит, используемую память, RSS, число вытеснений и размер настоящего рабочего набора. Практическая методика дана в расчёте эффективности, а гонки копии — в схемах чтения и инвалидации.

Подсказка 1: «срок ещё есть» не значит «данные свежие»

TTL — оставшееся время жизни копии. Он отсчитывается от операции её установки, а исходная запись могла измениться сразу после неё. Для некоторых данных допустима такая давность; для других нужна дополнительная согласованность. Сначала сформулируйте контракт, потом выбирайте механизм.

Подсказка 2: удаление после COMMIT тоже имеет гонку

Читатель успел получить старые данные из базы, остановился перед SET, писатель зафиксировал новые и удалил ключ, читатель продолжил и вернул старую версию в пустой кэш. Два успешных действия писателя не отменяют ранее начатое заполнение. Нарисуйте события двух участников, прежде чем объявлять последовательность безопасной.

Подсказка 3: что случится при одном горячем промахе

Если одновременно отсутствующий ключ читают 100 клиентов, простая схема разрешает 100 загрузок. Объединение запросов, single-flight, оставляет одного исполнителя и ожидающих тот же результат; область его действия может быть только одним процессом. Другие экземпляры приложения требуют общей координации либо иной рассчитанной защиты источника.

Продолжить свой установленный экземпляр

Основной опыт выполняется на том же Redis, который вы самостоятельно установили и настроили в личной VM. Из паспорта берутся фактические адрес, порт, ACL-пользователь, каталог конфигурации и данных, способ запуска и политика сохранения. Запишите версию, PID и run_id из INFO server: повторное подключение к тому же порту ещё не доказывает, что это прежний процесс. Если экземпляр уже существует, продолжайте его; не создавайте новый пустой сервер ради красивого вывода.

Параметры ниже задаются в текущем гостевом терминале по собственному паспорту, не копируются с чужого стенда. Пример предполагает настроенного ACL-пользователя с паролем и разрешениями для своих ключей. Если профиль использует TLS, дополнительно передайте --tls и свой доверенный --cacert, сохраняя проверку сертификата.

redis-cli \
  -h "${STUDY_REDIS_HOST:?Укажи адрес своего Redis из паспорта}" \
  -p "${STUDY_REDIS_PORT:?Укажи порт своего Redis из паспорта}" \
  --user "${STUDY_REDIS_USER:?Укажи своего ACL-пользователя}" \
  --askpass

-h/-p выбирают адрес и порт, --user — личность ACL Redis, а не пользователя Linux. --askpass запрашивает пароль интерактивно, не сохраняя его в аргументах процесса. Проверка ${имя:?сообщение} останавливает команду при незаданном параметре, вместо подключения к умолчанию. Выполните PING, ACL WHOAMI и доступные вашему пользователю INFO server/persistence. Не расширяйте права только потому, что закрыт административный INFO или CONFIG: нужные сведения может проверить владелец. Работайте лишь с ключами lab:p12, без FLUSHALL.

SET lab:p12:card:42 '{"version":1,"body":"old"}' PX 2000
GET lab:p12:card:42
PTTL lab:p12:card:42
MEMORY USAGE lab:p12:card:42
INFO stats
INFO memory

PX 2000 задаёт срок в миллисекундах. PTTL показывает остаток в тех же единицах; он не обязан быть ровно 2000 после ввода команды. −1 означает существующий ключ без срока, −2 — отсутствие ключа. После более двух секунд с момента SET следующий GET должен не вернуть старое значение. Обычный SET без срока сбрасывает прежний TTL; для сохранения существующего срока есть KEEPTTL. MEMORY USAGE оценивает расход конкретного объекта с накладными расходами, а не только длину JSON.

INFO stats содержит накопленные keyspace_hits и keyspace_misses. Снимите начало и конец интервала и считайте разности, не делите одно число за всё время процесса на число запросов последней минуты. Для приложения дополнительно нужны результаты проверки актуальности: Redis не знает, соответствует ли найденная строка новой версии записи PostgreSQL. INFO memory и внешний RSS также имеют разные границы учёта.

При переходе к следующей части не очищайте конфигурацию, журнал и данные. Для Redis отдельно решите, что сохраняют выбранные RDB/AOF и штатная остановка. У Memcached тот же установленный экземпляр означает прежнюю конфигурацию и границы доступа, а не обещание сохранения содержимого RAM после перезапуска. Это свойство технологии, не повод незаметно пересоздать весь учебный мир. Результаты и ошибки остаются в журнале задания и на диске гостя.

Дополнительный одноразовый опыт с прежним runner

python3 cache/labs/live.py --manual из корня книги создаёт отдельные временные Redis/Memcached и ждёт Enter, затем очищает своё окружение. Это дополнительный опыт семантики, а не продолжение установленного экземпляра. Его порты и каталоги не берутся за паспорт основного мира, изменения туда не сохраняются для следующих глав. При занятом порту не подключайтесь наугад к уже работающей службе. Устройство runner описано в лабораторной инструкции.

Воспроизвести опасную последовательность вручную

Для независимого примера в access_lab создайте app.cache_cards(id bigint PRIMARY KEY, version bigint NOT NULL, body text NOT NULL) и строку (42,1,'old') от владельца app_owner; затем выдайте нужные SELECT/UPDATE только учебным ролям. В P10 владелец создан с NOLOGIN, поэтому прямой вход psql -U app_owner закономерно запрещён. Войдите прежним административным пользователем через частный сокет и порт, выполните SET ROLE app_owner;, создайте объекты, затем RESET ROLE; и нужные GRANT. При повторе сначала прочитайте существующую таблицу и её данные, не пересоздавайте её ради строки из примера. Это новая таблица опыта, не скрытая готовая часть Go-сервиса. В терминале A подключитесь разрешённой app_ro, прочитайте строку из базы и запишите результат, но пока не заполняйте кэш; терминал B использует app_rw с выданным UPDATE.

В терминале B выполните BEGIN; UPDATE app.cache_cards SET version=version+1, body='new' WHERE id=42; COMMIT;, затем в Redis DEL lab:p12:card:42. Теперь A продолжает работу со своей старой копией: SET lab:p12:card:42 '{"version":1,"body":"old"}' PX 60000. Сопоставьте SELECT и GET: источник уже версии 2, а недавно заполненный ключ версии 1 с почти минутой срока. Результат не зависит от тайного сбоя сервера — достаточно такого порядка успешных действий.

Этот опыт опровергает безусловное «удалить после записи всегда достаточно». Решение зависит от требуемой согласованности: допустимая давность с TTL, сериализация заполнения с записью либо протокол версий, не позволяющий старому заполнению пройти после новой версии. Простая проверка версии перед SET оставляет ещё одно окно между проверкой и записью; гарантию надо обеспечивать в выбранной общей точке координации. Подробные варианты разбираются в теоретическом томе, а изменение приложения должно иметь тест именно этой перестановки.

Принять улучшение и проверить отказ

Будущая интеграция сравнивается до и после на одном наборе: правильные ответы, их p95/p99, полный темп, обращения к базе, память и CPU. Отдельный сценарий одновременно запрашивает один истёкший ключ и считает фактические загрузки. Затем ограниченно отключается только свой кэш: приложение должно завершать попытку обращения по таймауту и следовать выбранной политике. Безусловно отправить весь поток в уже перегруженную базу — не безопасное восстановление само по себе.

Для возврата нужен переключатель обхода или прежний выпуск, сохраняющий исходную базу и совместимость данных. В журнале отмечаются прогрев, ограничение памяти, политика вытеснения, точность свежести, отрицательные проверки и ещё не подтверждённые свойства. Вывод «98% попаданий» недостаточен; вывод «при заданной работе снизили нагрузку источника, выдержали срок и сохранили контракт данных» проверяем. Официальные уточнения: SET, TTL, INFO.
