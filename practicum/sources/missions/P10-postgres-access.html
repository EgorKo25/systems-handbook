Один psql может идти по разным путям

В заявке недостаточно сказать «PostgreSQL запущен». Нужны точка подключения, роль, база, правило проверки личности и права на объект. Unix-сокет — локальная точка обмена между процессами через ядро ОС; обычно она видна как специальный файл в каталоге. Это не TCP-порт на сетевом интерфейсе. У libpq, клиентской библиотеки PostgreSQL, отсутствие host в обычной Unix-среде выбирает сокет по умолчанию. Сначала также проверьте переменные PGHOST, PGPORT, PGUSER, PGDATABASE и выбранную service-конфигурацию: они могут изменить значения.

Без явного user обычно берётся имя пользователя ОС; без dbname — имя выбранной роли. Поэтому psql может искать базу student под ролью student, а psql -h 127.0.0.1 -U app_rw -d access_lab — совершенно другой вход. -h /путь/к/каталогу выбирает Unix-сокет; -h 127.0.0.1 выбирает TCP. Имя localhost может разрешиться сначала в IPv6, поэтому для первого контролируемого опыта используем числовой адрес.

Проверка личности, authentication, устанавливает, кем может войти клиент. Проверка полномочий, authorization, определяет допустимые действия уже вошедшей роли. Метод peer на Unix-сокете сопоставляет удостоверенное ядром имя пользователя ОС с ролью, непосредственно либо через явно настроенную карту. Он не проверяет пароль роли. SCRAM-SHA-256 — парольный механизм с обменом доказательствами; пароль не следует писать в строке подключения, книге или истории команд.

Сначала первый подходящий маршрут проверки, потом пароль

В pg_hba.conf, файле правил клиентской аутентификации, выбирается первая подходящая строка по типу подключения, базе, роли и адресу клиента. Если её метод не прошёл, сервер не продолжает поиск «более удобной» строки ниже. local относится к Unix-сокетам, host — к TCP. Разрешающая строка выше запрета делает нижний запрет бесполезным для совпавших подключений. trust не является способом «починить пароль»: он устраняет доказательство личности для попавших под правило клиентов.

Даже правильная HBA-строка не создаёт сетевого слушателя. listen_addresses выбирает адреса привязки сервера, порт задаётся отдельно, затем возможны сетевые фильтры. Прослушивание 127.0.0.1 не делает службу доступной с другой VM. Изменение HBA обычно перечитывается, а изменение listen_addresses требует перезапуска. После pg_reload_conf() нужен новый вход и проверка журналов; успешная отправка сигнала не равна доказательству принятия всех новых строк. Подробности находятся в клиентском протоколе и главе о личности и правах.

Подсказка 1: какое сообщение относится к какой границе

«Нет такого файла сокета» возникает до SQL-прав. Connection refused означает отсутствие подходящего слушателя или отказ на сетевой границе. Ошибка peer не исправляется выдачей SELECT. Permission denied for table подтверждает более поздний этап: вход уже состоялся, но объектное действие запрещено.

Подсказка 2: как не потерять административный вход

Оставьте отдельный проверенный локальный путь владельца учебного кластера и консоль. Сначала проверьте синтаксис нового файла, затем перечитайте его, затем новым сеансом проверьте разрешённый и запрещённый случаи. Не закрывайте единственную сессию до проверки замены.

Подсказка 3: почему одной таблицы прав мало

Для обращения к таблице могут требоваться CONNECT на базу, USAGE на схему и права на таблицу. Автоматическое значение из отдельной последовательности может потребовать её USAGE. Права по умолчанию задаются для будущих объектов конкретного создающего владельца и не переписывают уже созданные.

Создать собственный опыт, а не открыть рабочую базу

В Ubuntu и PGDG серверные бинарники обычно лежат в каталоге выбранной основной версии, например /usr/lib/postgresql/18/bin, и initdb может отсутствовать в обычном PATH даже после установки пакета. Найдите каталог поставки по составу установленного пакета, сверьте initdb --version, postgres --version, pg_ctl --version и psql --version. Для выбранной пакетной ветки 18 можно в этом терминале задать export PATH="/usr/lib/postgresql/18/bin:$PATH"; для другой поставки используйте её записанный полный путь. Выбор бинарника должен предшествовать чтению PG_VERSION и первому initdb. Установка клиента psql отдельно не означает наличия сервера.

Команды выполняются обычным пользователем в учебной Linux VM с заранее установленными совместимыми бинарниками PostgreSQL. Сам /srv/study подготовлен от root и не обязан разрешать запись student. Поэтому новый каталог экземпляра создаётся отдельным административным действием. Не запускайте initdb от root и не исправляйте доступ рекурсивной сменой владельца всего /srv.

if test -e /srv/study/pg-access; then
  printf '%s\n' 'Каталог уже существует: проверяем и продолжаем свой экземпляр, не меняем владельца автоматически.'
else
  sudo install -d -m 0700 -o "$(id -un)" -g "$(id -gn)" /srv/study/pg-access
fi
stat -c '%U %G %a %n' /srv/study/pg-access

install -d создаёт каталог, -m задаёт режим, -o и -g — владельца и группу обычного пользователя, от которого вызван sudo. Вычисления id выполняет его оболочка до sudo. Если путь уже существовал, блок ничего в нём не меняет. Продолжайте лишь после проверки владельца, назначения и версии существующего кластера. Чужой или непонятный каталог не присваивают себе ради прохождения задания.

umask 077
mkdir -p /srv/study/pg-access/socket
cd /srv/study/pg-access
if test -f data/PG_VERSION; then
  printf '%s\n' 'Существующий кластер: читаем его конфигурацию и продолжаем, initdb не выполняется.'
else
  initdb -D data --auth-local=peer --auth-host=scram-sha-256
fi

-D выбирает каталог данных. Первый initdb создаёт административную роль с именем текущего пользователя ОС, если -U не задан; это согласуется с peer при следующем локальном входе. Явные auth-параметры задают начальные методы. Наличие PG_VERSION не доказывает исправность сервера, оно лишь запрещает нам выдавать повторную инициализацию за продолжение. Неполный непонятный data также не удаляем: initdb откажется от непустого каталога, после чего надо исследовать причину. Для впервые созданного экземпляра в data/postgresql.conf задайте порт 55440, listen_addresses='127.0.0.1' и unix_socket_directories='/srv/study/pg-access/socket'. У существующего прочитайте и сохраните фактические параметры из паспорта. Каталог сокета должен существовать. Затем:

pg_ctl -D data -l server.log start
psql -X -h /srv/study/pg-access/socket -p 55440 -U "$(id -un)" -d postgres

-l направляет серверный журнал в файл, -X исключает влияние пользовательского psqlrc. -U "$(id -un)" явно выбирает созданного initdb администратора с именем текущего пользователя ОС; это исключает случайный PGUSER. В psql выполните SHOW config_file;, SHOW hba_file;, SHOW listen_addresses;, SHOW port; и \conninfo. Используйте обнаруженные пути. Пакетная установка ОС может хранить конфигурацию вне PGDATA; наш ручной опыт не доказывает расположение файлов другой поставки.

Следующий блок — первая настройка нового экземпляра. Если роли или access_lab уже существуют, сначала сверяются их владельцы и права с паспортом; повторное выполнение всех CREATE не является продолжением занятия. Для нового экземпляра выйдите из диагностического psql через \q, сохраните блок в приватный файл bootstrap-access.sql текущего каталога и выполняйте его как единый сценарий с остановкой при ошибке.

CREATE ROLE app_owner NOLOGIN;
CREATE ROLE app_rw LOGIN;
CREATE ROLE app_ro LOGIN;
SET password_encryption = 'scram-sha-256';
\password app_rw
\password app_ro
CREATE DATABASE access_lab OWNER app_owner;
\connect access_lab
REVOKE ALL ON DATABASE access_lab FROM PUBLIC;
GRANT CONNECT ON DATABASE access_lab TO app_rw, app_ro;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
CREATE SCHEMA app AUTHORIZATION app_owner;
SET ROLE app_owner;
CREATE TABLE app.items (
  id bigserial PRIMARY KEY,
  body text NOT NULL
);
RESET ROLE;
GRANT USAGE ON SCHEMA app TO app_rw, app_ro;
GRANT SELECT ON app.items TO app_ro;
GRANT SELECT, INSERT, UPDATE, DELETE ON app.items TO app_rw;
GRANT USAGE ON SEQUENCE app.items_id_seq TO app_rw;
psql -X -v ON_ERROR_STOP=1 \
  -h /srv/study/pg-access/socket -p 55440 -U "$(id -un)" \
  -d postgres -f bootstrap-access.sql

-f читает SQL из указанного файла, а -v ON_ERROR_STOP=1 прекращает сценарий после SQL-ошибки и возвращает неуспех. Два \password запрашивают секреты в личном терминале. Сценарий не объединён одной транзакцией: CREATE DATABASE её не допускает. Поэтому при отказе часть объектов уже может существовать; сохраните первую ошибку и исследуйте состояние, не удаляйте кластер и не запускайте весь файл вслепую снова. К настройке HBA переходят только после приёмки фактических ролей, базы, схемы и таблицы.

\password запрашивает новый секрет интерактивно; не вставляйте его в SQL-пример. Владелец app_owner не может напрямую войти, роли чтения и изменения не получают SUPERUSER, CREATEDB или членство во владельце. Таблица создаётся после SET ROLE именно от app_owner. Для будущих таблиц при необходимости отдельно настраивают ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app; это не заменяет показанные GRANT существующим объектам.

Сузить и проверить маршрут входа

После завершения файлового bootstrap снова откройте административный psql явным сокетом, портом 55440, своим пользователем ОС и базой postgres, как в диагностической команде выше. Этот сеанс нужен для проверки HBA и перечитывания конфигурации; не закрывайте его до проверки новых соединений.

Сохраните исходный HBA-файл этого частного кластера и разместите правила приложения до общей локальной строки. Для нашего опыта достаточно:

local access_lab app_rw                  scram-sha-256
local access_lab app_ro                  scram-sha-256
host  access_lab app_rw 127.0.0.1/32      scram-sha-256
host  access_lab app_ro 127.0.0.1/32      scram-sha-256
local all        all                    peer
host  all        all    127.0.0.1/32     reject

Маска /32 выбирает ровно один IPv4-адрес, а не всю подсеть. Последняя строка отвергает остальные TCP-входы с этого адреса; она не ограничивает прослушивание сети сама по себе. В административном сеансе исследуйте SELECT rule_number, type, database, user_name, address, auth_method, error FROM pg_hba_file_rules ORDER BY rule_number;, затем SELECT pg_reload_conf();. Ненулевое поле error требует исправления. Не переносите этот файл в системный кластер.

Новыми сеансами подключите app_rw и app_ro через 127.0.0.1:55440 к access_lab, используя psql -X -h 127.0.0.1 -p 55440 -U app_rw -d access_lab. Пароль вводится в запрос клиента. Выполните SELECT current_user, session_user, inet_client_addr(), inet_server_addr(), inet_server_port();. Повторите явным Unix-сокетом: сетевые адреса станут NULL, а HBA выберет local-правило.

Под app_rw вставьте строку с INSERT INTO app.items(body) VALUES ('probe') RETURNING id;. app_ro должна прочитать её, но INSERT должен завершиться отказом в правах. app_rw не должна создавать базы или входить как владелец. Неправильный пароль должен приводить к отказу, а попытка другой роли по TCP — попадать под reject. Зафиксируйте каждую границу отдельно. Существующий Go-сервис не подключён к этой таблице: добавление драйвера, пула соединений, таймаутов и операций станет самостоятельным изменением программы. После опыта остановите только свой кластер: pg_ctl -D data -m fast stop.

Это подготовленный ручной сценарий; его выполнение здесь не заявляется. Для уже записанных реальных наблюдений используйте автономную лабораторию PostgreSQL. Официальные правила: HBA и параметры подключения libpq.
