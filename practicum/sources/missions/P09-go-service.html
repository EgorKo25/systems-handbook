Устанавливаем собственный продукт поверх работающего маршрута

В P06 временный Python-сервер помог различить процесс, сокет и HTTP-ответ. Теперь его заменяет настоящий Go-проект handbook-service. Он отвечает JSON на /healthz и /greet?name=..., выводит версию флагом -version и штатно завершает HTTP-службу по SIGTERM. У него пока нет PostgreSQL, Redis или внешних модулей. Следующие задания будут добавлять именно новые свойства, не предполагая их существующими.

Скопируйте проект в самостоятельный личный Git-репозиторий внутри гостя и сохраните исходную версию. Коммит создавайте своей безопасной идентичностью. Проверьте корень Git: сборщик записывает ревизию только когда проект действительно является корнем репозитория, иначе честно сохраняет отсутствие такой привязки и dirty-состояние. Не стройте release из случайного подкаталога флэшки с неизвестными локальными правками.

Разделить три разных времени

Под словом «медленно» здесь скрываются холодная компиляция, повторная сборка и обработка HTTP. Сборка запускает компилятор и линковщик; запрос к уже работающему бинарнику этих действий не выполняет. Кэш Go уменьшает часть повторных вычислений. Не смешивайте первый запуск с пустым кэшем и работу сервера под нагрузкой в один показатель «скорость Go».

Запишите toolchain, GOOS/GOARCH, режим CGO, флаги и исходную ревизию. Для совместимого Go выполните go test -count=1 ./...; -count=1 требует нового выполнения тестов, оставляя полезный кэш компиляции. Затем используйте python3 tools/build.py --version 1.0.0. Сборщик по умолчанию создаёт Linux/amd64. На ARM64 задайте предусмотренный --goarch arm64. Успешная кросс-компиляция для другой архитектуры не обещает возможность запустить результат на текущей машине.

Инструменты и стандартная библиотека должны быть подготовлены до автономной работы. GOTOOLCHAIN=local запрещает незаметную подгрузку другой версии Go, GOPROXY=off запрещает получение модулей. Для этого проекта без внешних зависимостей такой договор подходит. Для будущего проекта с зависимостями сначала материализуют полный нужный состав, иначе «нет интернета» станет ожидаемым отказом подготовки, а не поводом отключить проверку.

Происхождение проверяется по нескольким свидетельствам

В dist появляются handbook-service и manifest.json. Manifest содержит размер, SHA-256, версию, toolchain, целевые настройки, флаги, ревизию, dirty и хеш самого build.py. SHA бинарника и SHA коммита описывают разные объекты. Ключ -buildvcs=false отключает автоматическое VCS-встраивание; поэтому отсутствие vcs.revision в go version -m согласуется с явным manifest, а не является само по себе ошибкой.

Сравните две чистые копии того же коммита в разных каталогах с одним toolchain и одинаковыми параметрами. -trimpath нормализует определённые пути; это помогает выбранному примеру воспроизводиться. Если бинарники различаются, установите отличающийся вход, а не объявляйте любой различающийся SHA повреждением. Версия линковки, toolchain, архитектура, генератор и внешние библиотеки способны намеренно менять результат.

Выпуск не подменяет сеть

Запускайте новый бинарник отдельно от прежней службы, на явно выбранном адресе и порту. По умолчанию он слушает 127.0.0.1:8087. Для клиентского доступа требуется осмысленный адрес роли приложения и правила сети. Если роль пока реализована namespace, вход в него и понижение прав запуска требуют отдельного корректного рецепта; не запускайте Go-службу от root только ради удобства привязки. В самостоятельной VM используйте обычного непривилегированного пользователя и непривилегированный порт.

Нагрузочное исследование начинается после обычных запросов и версии. Зафиксируйте, откуда генерируется поток, его интенсивность, параллелизм, длительность, долю ошибок и распределение задержек. HTTP-тест обработчика в памяти не измеряет сетевой маршрут. Первый пик GC или прогрев ОС может менять короткую серию; несколько запросов curl не объявляются полноценным benchmark. Позднейшая задача P21 о ресурсах углубляет именно эти границы измерения.

Развилки исследования

  1. Exec format error: сравните цель manifest с ОС и архитектурой исполнителя. Это другой слой, чем ошибка теста.
  2. source_dirty=true: проверьте корень Git, status и то, что реально закоммичено. Не меняйте JSON вручную ради красивой строки.
  3. На loopback работает, клиенту недоступно: вернитесь к привязке сокета и маршруту P06. Компилятор уже создал исполняемый процесс.
  4. Одинаковый коммит дал другой SHA: проверьте версию, toolchain, цель и флаги до догадок о повреждении.
  5. Сервис «падает под нагрузкой»: отличите код выхода, сигнал, OOM, перезапуск службы и исчерпание клиентского лимита. Сохраните журнал и временную границу.

Путь от чистого снимка до ответа

git status --short
go version
go env GOHOSTOS GOHOSTARCH
go test -count=1 ./...
python3 tools/build.py --version 1.0.0
./dist/handbook-service -version
go version -m dist/handbook-service
go tool buildid dist/handbook-service

Команды относятся к корню личной копии. buildid исследует внутренний идентификатор Go-сборки и не заменяет SHA-256 всего файла. Прочитайте manifest, самостоятельно вычислите хеш бинарника, сравните source_revision с HEAD и source_dirty с реальным status. Если инструмент Go не в PATH, используйте подготовленный полный путь или предусмотренный HANDBOOK_GO для build.py; это не повод менять системный Go через go env -w.

В отдельном терминале запустите ./dist/handbook-service -listen 127.0.0.1:8087. Из той же VM:

curl --fail --show-error --max-time 3 http://127.0.0.1:8087/healthz
curl --fail --show-error --max-time 3 'http://127.0.0.1:8087/greet?name=Go'

Для версии 1.0.0 ожидается JSON с message:"ok" и version:"1.0.0" на healthz, а на greet сообщение Hello, Go!. Порядок ключей/пробелы не являются сетевым контрактом; проверяйте значения JSON. Отрицательные случаи: POST к этим маршрутам возвращает 405, слишком длинное имя — 400. Ограничение name равно 128 байтам UTF-8, а не числу видимых букв. Неверный запрос не должен завершать весь процесс.

Две контрольные точки вместо замены на месте

Сохраните комплект текущего выпуска в отдельном каталоге и не затирайте предыдущий бинарник. Измените greeting в своей ветке, обновите тест и соберите новый номер версии. Повторите проверки, затем переключите выбранный экземпляр по процедуре выпуска. Предыдущий каталог даёт возможность вернуть приложение при совместимой конфигурации; будущая БД потребует отдельного анализа возврата данных. Сам manifest не запускает rollback.

Штатно остановите процесс Ctrl+C и наблюдайте завершение. После переноса команды в systemd должны сохраниться пользователь, полный путь, рабочий каталог, параметры и журнал, а не только имя службы. Проверка systemctl status дополняется сокетом и клиентским JSON. Для следующего этапа сохраните исходный commit, оба комплекта, точный способ старта, наблюдения холодной/повторной сборки и проверенные HTTP-свойства.
