Меняется система управления, продукт остаётся тем же

В этом задании используйте тот же handbook-service с /healthz, /greet и -version. Маленький echo из отдельного тома GitLab нужен для самостоятельного изучения CI, но не заменяет продукт накопленного практикума. Сохраняются исходники, контракт, история выпуска, релизы blue/green и критерии клиента. Меняется платформа, управляющая проверками и артефактами.

Сначала определите профиль ресурсов. Собственный GitLab — многокомпонентная платформа с PostgreSQL, Redis, Gitaly и веб-службами; Runner — отдельная исполняющая роль. На домашней машине с 8 ГБ нельзя обещать комфортную одновременную работу всех ранее изученных систем. Остановите ненужный Jenkins-профиль, зафиксировав его состояние. Использование GitLab.com с личным Runner — допустимый отдельный опыт сервиса, но не доказательство установки и восстановления своего GitLab. Выбранную границу запишите до сравнения результатов.

Адреса и права до YAML

По главе установки задайте один понятный внешний URL. Проверьте DNS, маршрут и доверенный TLS из браузера, с Runner manager и из окружения helper/job. localhost у них обозначает разные места. Успешный вход администратора из браузера не устанавливает доверенный CA в контейнере задания. Отдельно создайте обычную личность проекта и ограниченную конфигурацию Runner; его private config.toml не попадает в Git.

Часть симптомов заявки появляется до исполнения кода. Pending при online Runner может означать несовпадение tags, protected-условий, области проекта или отсутствие свободного слота. Запишите требуемые метки job и полный разрешённый набор кандидатов. Наличие метки personal-go — утверждение администратора о среде, а не команда установить Go. Проверка gitlab-runner verify подтверждает связь регистрации и сервера, но не создание Docker-контейнера и не возможность получить образ.

Переносить смысл конвейера, а не названия стадий

У Jenkins основной сценарий проверяет чистый HEAD, toolchain и manifest. Новый GitLab CI должен сохранить эти утверждения. Стадии можно назвать иначе, но обязательный тест не исчезает из графа от удобного rules:changes, а build не берёт случайный dist из cache. Передача между GitLab job делается явно через artifact producer. Для длительного выпуска нужен зафиксированный пакет либо сохранённый артефакт известного job с понятным сроком.

В этом опыте удобен один граф check → build → verify. Unit и vet могут работать параллельно при двух подходящих слотах; build ждёт обязательные проверки, verify получает его manifest и бинарник. Доставка в blue/green добавляется только после успешной проверки данных. Пересборка внутри verify или deploy нарушила бы утверждение «выпущены именно проверенные байты». Корректность двух независимых сборок исследуется отдельно.

Доверенный ref и недоверенная правка

Конвейер выполняет код проекта, включая изменяемый CI-файл. Участник, способный изменить script, способен использовать все полученные этим script ресурсы. Не выдавайте выпускной секрет обычному MR только потому, что тесты якобы «должны его использовать». Для тестов HTTP без БД credentials вообще не нужны. Отдельный release-доступ связывают с доверенным ref, областью Runner и защищённым окружением согласно возможностям установленного выпуска.

Не передавайте Docker socket job по умолчанию. Для Go-компиляции он не нужен; его получение может дать управление контейнерами и томами хоста. privileged также не является условием обычного build. На первом выделенном личном Runner известный непривилегированный образ Go+Python и один слот дают прозрачный путь наблюдения. Для кода посторонних участников потребуются более строгие границы и отдельный анализ, не просто новая метка.

Разделите путь на проверяемые границы

  1. Push принят: есть ли pipeline вообще? Посмотрите source, workflow и ошибки создания графа до Runner.
  2. Job pending: существует ли допустимый кандидат с полным набором tags и нужным protected-контекстом?
  3. Preparing executor: доступен ли закреплённый образ именно Docker-хосту? Это иной путь, чем HTTPS браузера.
  4. Verify не видит файл: посмотрите artifact build, needs, paths, срок и права. Cache не должен стать запасным обязательным каналом.
  5. Зелёный pipeline выпустил другой код: сравните commit, job ID, SHA manifest, файл в release-каталоге и клиентскую версию.
  6. Fork/MR предложил новый script: какие именно секреты и сеть получит процесс? Masked-вывод не запрещает чтение значения кодом.

Минимальный граф для существующего продукта

В собственном GitLab-проекте корнем репозитория должен быть именно service. Не отправляйте туда всю энциклопедию ради одной лаборатории. Настройте закреплённый Go+Python образ и подходящий Runner; затем проверьте CI Lint. Следующий фрагмент показывает передачу данных, а правила событий, timeout и проверка manifest дополняются из собственного явного договора:

stages: [check, build, verify]

default:
  image: $LAB_GO_PYTHON_IMAGE
  tags: [personal-go]

unit:
  stage: check
  script:
    - go test -count=1 ./...

vet:
  stage: check
  script:
    - go vet ./...

build:
  stage: build
  script:
    - python3 tools/build.py --version 1.0.0
  artifacts:
    paths: [dist/handbook-service, dist/manifest.json]
    expire_in: 7 days

verify:
  stage: verify
  needs:
    - job: build
      artifacts: true
  script:
    - python3 tools/verify-release.py

default связывает каждое задание с заранее подготовленной средой и меткой personal-go; без этой связи специально ограниченный метками Runner может оставить job в pending. LAB_GO_PYTHON_IMAGE — несекретная проектная переменная с реальным закреплённым образом. Если вы продолжаете первый Shell-вариант из тома GitLab, удалите только строку image и сохраните тот же Runner с установленными Go и Python. go vet исследует определённые подозрительные конструкции статически, не заменяя исполнения тестов. Проверки unit и vet обе обязательны перед build.

Готовая собственная проверка приложена как verify_go_release.py. Скопируйте её в tools/verify-release.py личного Go-проекта и закоммитьте перед сборкой. Она сверяет format, binary, bytes, SHA, version, target, flags, source_revision/dirty, build_script_sha256 и фактический toolchain, затем запускает -version. HEAD читается из действительно самостоятельного корня проекта; CI_COMMIT_SHA проверяется как заявленное значение, а не принимается за доказанную историю. Любое расхождение даёт ненулевой код без пересборки. Значение версии по умолчанию — 1.0.0; новый выпуск задаёт одинаковую версию build и --expected-version verifier.

На первом реальном запуске сохраните source события, commit SHA, IDs build/verify и скачанный manifest. Убедитесь, что новая среда verify действительно получила artifact build, а прежний workspace не делает видимость файла случайной. Затем сломайте тест: build не должен пройти обычным путём. Отдельно уберите artifact path либо повредите полученную копию: verify должен отказаться. После исправления этих отрицательных опытов можно присоединить проверенную доставку P14 с последовательным доступом к одному окружению.

Проверка событий и управления

Повторите таблицу из тома GitLab: push ветки без MR, push при открытом MR, MR pipeline, тег, web и при необходимости schedule. Для каждого заранее предскажите число графов и обязательных job. На один commit могут законно существовать разные pipeline источники, но дублирующий branch/MR запуск увеличивает расход без нового свидетельства. Создание child pipeline отдельно меняет source потомка на parent_pipeline; правила, разрешающие только push, не подходят ему автоматически.

Остановите свой manager и создайте новую работу; верните его и наблюдайте переход pending → подготовка → script → сохранение результата. Затем дайте job неподходящую метку: online остаётся, но выполнения нет. Верните конфигурацию. Эти два отрицательных опыта доказывают разницу доступности менеджера и matching, подбора кандидата. Они не требуют выдачи дополнительных привилегий или изменения рабочего компьютера.

Состояние платформы тоже становится частью мира

Сохраните проектный Git отдельно, затем подготовьте согласованную копию GitLab данных, конфигурации, secrets и внешних backend согласно разбору восстановления. Проверьте возврат на изолированной той же точной версии/редакции и расшифровку соответствующих полей. Repo clone сохраняет исходники, но не MR, роли, артефакты и приватные настройки. После обновления требуются поддерживаемый upgrade path и завершённые background migrations; новый тег образа не заменяет процедуру.

Итог задания — свой объяснимый путь от события до работающего выпуска и точка возврата платформы. Полный GitLab в переносимом VM-профиле пока не был запущен и не называется проверенным стендом. Локальные Go-проверки из книги подтверждают лишь собственные процессы и артефакты. В своём отчёте пометьте реальные серверные наблюдения по мере исполнения, сохраняя единственный развивающийся продукт между занятиями.
