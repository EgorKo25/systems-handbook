Два независимых вопроса: кому верить и кому входить

SSH устанавливает защищённое соединение и проверяет несколько разных сущностей. Клиенту надо убедиться, что отвечает нужный сервер. Серверу — что пользователь имеет право войти. Ключ узла и ключ пользователя не взаимозаменяемы: первый хранится у сервера и сверяется клиентом, второй принадлежит пользователю и подтверждает его доступ. Успешное принятие fingerprint не исправляет неверную учётную запись; правильный пользовательский ключ не оправдывает неожиданно изменившийся ключ узла.

Перед началом выпишите путь соединения: SSH-клиент на хосте → localhost-порт QEMU → сетевой интерфейс гостя → слушающий сокет → проверка имени пользователя и метода аутентификации → запуск сеанса. В каждой точке возможен свой отказ. Сообщение connection refused обычно появляется раньше проверки пароля; permission denied означает, что обмен дошёл существенно дальше. Timeout сам по себе не называет виновника: наблюдение может соответствовать маршруту, фильтру, зависанию или неверному адресу.

У нас адрес управления привязан к одному компьютеру. Различные учебные VM могут по очереди пользоваться 127.0.0.1:2222, поэтому важно сохранить понятную привязку ключей к миру. Храните файл known_hosts в личном каталоге стенда и фиксируйте, какой мир использует этот порт. При восстановлении того же диска ключ обычно тот же; новая установка закономерно может иметь другой. Но сообщение клиента надо объяснить, а не скрыть опцией, отключающей проверку.

Заказчик хочет удобного входа, но удобство не равно раздаче root-пароля и копированию закрытого ключа на сервер. Свой открытый ключ можно добавить выбранному пользователю внутри гостя, закрытый остаётся у клиента. Если ключ лежит на переносном носителе, парольная фраза особенно полезна: разрешения FAT/exFAT не дают ту же модель защиты файла, что Linux. На рабочем компьютере всё равно требуется разрешённый клиент и разрешённое обращение с личными ключами.

Разделяйте восстановление и постоянную эксплуатацию. Консоль позволяет исправить доступ после ошибки; рабочий путь должен стабильно подтверждаться новым соединением. Не отключайте старый метод входа, пока не проверили новый из второго терминала. Проверка в текущем уже авторизованном сеансе почти ничего не говорит о том, сможет ли сервер принять следующий.

Если соединение не устанавливается

  1. Проверьте, работает ли QEMU и тот ли порт указан в выводе контроллера. SSH с -p 22 обращается к SSH хоста, если он там есть; это не наш гостевой 2222.
  2. Включите -v у клиента и найдите последнюю подтверждённую стадию. Не публикуйте полный диагностический журнал без просмотра: в нём есть пути, имена пользователей и адреса.
  3. Сверьте fingerprint через уже доверенную консоль гостя. Не заменяйте проверку автоматическим StrictHostKeyChecking=no.
  4. Если сервер доступен, проверьте выбранного пользователя, его authorized_keys, права и журнал. Не ищите сетевую проблему в ситуации, где сервер уже явно отказал в аутентификации.

Контрольный порядок

В гостевой консоли получите отпечаток конкретного открытого ключа узла:

sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

-l выводит fingerprint, -f выбирает файл. Мы читаем публичный файл, не копируем закрытый ключ. Если Ed25519-ключ отсутствует, сначала выясните, какие host keys реально настроены; команда не требует создавать новый ключ при каждом упражнении.

В каталоге стенда на клиенте пример запроса выглядит так:

ssh -v -p 2222 \
  -o UserKnownHostsFile=runtime/known_hosts \
  student@127.0.0.1

-v добавляет диагностику; -p задаёт TCP-порт. -o передаёт отдельную настройку клиента, здесь — собственный файл доверенных ключей. Относительный путь относится к текущему каталогу клиента; он не создаётся в госте. Сначала подготовьте каталог runtime. В Windows PowerShell обратная косая черта не служит переносом строки: введите команду одной строкой. Смысл параметров от оболочки не меняется.

Если нужен отдельный пользовательский ключ, создайте его дома в личном каталоге и добавьте только публичную часть в ~student/.ssh/authorized_keys гостя. Выбор ключа клиентом задаёт -i; IdentitiesOnly=yes ограничивает попытки явно указанными ключами вместо перебора всего содержимого агента ключей. Не вводите закрытую часть в учебный терминал страницы. После установки проверьте новый сеанс и лог сервера. Для Ubuntu полезен sudo journalctl -u ssh --since '10 minutes ago' --no-pager; при активации через сокет дополнительно исследуйте соответствующий сокетный модуль systemd.

После изменения серверной конфигурации выполните sudo /usr/sbin/sshd -t. Это синтаксическая проверка, не доказательство работоспособности маршрута или ключа. Затем примените конфигурацию поддерживаемым для своего unit способом и проверьте второй вход. Ошибки допуска, ключа и транспорта должны остаться отдельными отрицательными тестами: чужой ключ не проходит, ошибочный fingerprint не принимается молча, непубликуемый порт не открывается наружу.

В журнал задания положите версию клиента, выбранные адрес и порт, публичный отпечаток ключа, причину исходного отказа и доказательство нового входа. Сам пароль, содержимое закрытого ключа и полный дамп окружения там не нужны. После холодного переноса нового диска повторите проверку доверия: один и тот же localhost на другом компьютере всё равно представляет конкретный учебный сервер, а не абстрактный «безопасный адрес».

Точное поведение опций сверяется с руководством OpenSSH и установленной версией клиента. В этой подготовке настоящий SSH-сеанс к новой VM ещё не выполнялся.
