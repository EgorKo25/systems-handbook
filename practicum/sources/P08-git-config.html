Вернуть управляемую конфигурацию

После ручных исправлений неизвестно, чем узел отличается от рабочего состояния.

Заявка и исходные условия

STUDY-08: Вернуть управляемую конфигурацию

Доступ: Личный репозиторий в госте; ключи/диски/дампы не Git.

Наблюдаемый симптом: Есть локальные изменения и ошибочный commit, требуется восстановить конфиг без потери новых данных.

Доказательства результата: Чистый diff понятен, ошибка найдена, нужная версия применена; проверка результата независима от текста команды.

Возврат: Сохранить рабочее дерево/патч, использовать отдельную ветку и точку before-config-repair.

Исходное состояние подготовлено в заданиях: P06-service-socket.

Контрольные точки выключенного мира: before-p08-git-config перед работой и done-p08-git-config после проверок. Это сохранение дискового состояния, без открытых сеансов и памяти процессов.

Начальная оценка памяти гостя: 1024 МиБ. Это бюджет для проверки состава ролей, а не измеренное требование и не гарантия достаточности для всех служб вместе.

Этап развития стенда. Условие и разбор подготовлены; нужные роли и ограничения доступа ещё предстоит развернуть и проверить. Их работоспособность этим текстом не подтверждается.

Первая установка Git и первая собственная история конфигурации

Дома найди официальные варианты установки Git. Для нашего Linux-гостя выбери пакет Ubuntu и сохрани точную версию/зависимости для offline-установки; Windows-клиент нужен только если ты отдельно решил работать им на разрешённом компьютере. Не копируй рабочую пользовательскую конфигурацию вместе с личной историей.

После установки проверь git --version и git config --show-origin --list. Создай один личный репозиторий для изучаемых конфигов, затем задай identity именно локально этому репозиторию. Для публичного GitHub используй noreply, не рабочую почту. Проверь имя и email автора и коммитера до первой публикации. Секреты, диски VM, дампы и generated runtime не добавляй: ignore задаётся до первого git add, а уже отслеживаемый секрет игнорированием не удаляется из истории.

Сначала зафиксируй реальное текущее состояние SSH/сети/службы с их рабочими и ещё неисправными частями. Git хранит записанные файлы; он не захватывает живую таблицу маршрутов или весь диск автоматически. Скопируй нужные конфиги осмысленно и запиши, откуда применяются именно они. Для каждого следующего изменения сохраняются diff, проверка синтаксиса и наблюдение службы.

В паспорт Git войдут путь единственного основного репозитория, локальная identity, ветка, remotes, правила исключений и способ независимого резерва. Закрытие терминала не требует git init заново. При неизвестной ошибке сначала status/log/diff, затем исправление отдельным понятным commit; reset к исходному состоянию не является обязательным началом главы. Инициализация Git-репозитория не заменяет резерв данных PostgreSQL или выключенного qcow2.

Как подойти к работе

Сохранить факты до изменения истории

На узле лежат отслеживаемый файл конфигурации, ошибочный коммит и ещё не закоммиченные полезные правки. Рядом живут данные приложения и журнал работы. Первая задача — установить, что именно сохраняет Git. Он не является резервом всех файлов сервера. Если приложение создало новую запись в каталоге данных, команда возврата коммита не должна стирать её вместе с конфигурацией.

Работайте с личным учебным репозиторием внутри гостя, отдельно от исходников этой энциклопедии. Для примера договоримся о config/server.env с параметром адреса службы и notes/repair.txt с полезной незавершённой записью. Данные и секреты находятся за пределами этого репозитория. Эти имена — модель организации, а не обещание, что предыдущий этап уже создал именно такие файлы. Если на вашем узле другой формат, найдите его фактический путь и сохраните ту же границу операции.

Начните с git status --short, git diff, git diff --cached и git log --oneline --decorate -8. Первая команда показывает краткие состояния, следующие две сравнивают разные пары: рабочее дерево с индексом и индекс с HEAD. Индекс — подготовленный будущий снимок, а не синоним текущего файла. Поэтому одна полезная строка может уже быть staged, а другая — существовать только в рабочем дереве. Сохранённый патч только одного diff не охватывает всё автоматически.

Сделайте защищённую копию нужного рабочего дерева либо два отдельных патча с понятным назначением. git diff --binary сохраняет в патче поддерживаемое представление бинарных изменений, но не включает новые неотслеживаемые файлы от одного своего имени. Их надо учесть отдельно. Не коммитите найденный приватный ключ ради «страховочной ветки»: сначала перенесите секрет в его правильное место. Файл .gitignore влияет на обычное добавление неотслеживаемых путей и не удаляет уже сохранённый секрет из истории.

Найти первую неверную версию

Заявленный симптом — отказ клиента после ручной правки — ещё не доказывает, что проблема в последнем коммите. Сопоставьте изменение конфигурации с сокетом и ответом из P06. Посмотрите историю нужного пути через git log -p -- config/server.env. -- отделяет путь от параметров и ревизий. Затем прочитайте прежний файл, например git show HEAD~1:config/server.env. Это вывод содержимого без переключения всего дерева. HEAD~1 — первый родитель HEAD; его выбор требует проверить граф истории, особенно после merge.

Отдельно спросите, опубликован ли ошибочный коммит. Если им уже пользуются другие участники или будущие этапы, история наблюдаема ими. Новый исправляющий коммит и переписывание прежнего коммита — разные договоры. Для этой заявки полезнее понятное сохранение истории: вернуть нужный параметр новым изменением либо выполнить осмысленный revert. git reset --hard не нужен для доказательства причины и способен уничтожить незавершённую работу, которую просили сохранить.

Git хранит текст; служба читает свою конфигурацию

Возврат файла в рабочем дереве не означает применения настройки работающим процессом. Сервис мог уже прочитать прежнее значение при старте либо использовать другой путь. После изменения исследуйте механизм reload/restart именно этой службы и её журнал. Повторите клиентский запрос из разрешённой точки, проверьте адрес слушателя и правильное содержимое ответа. Чистый git diff доказывает согласование файлов относительно выбранного коммита, а не правильность сетевого поведения.

На следующем этапе Go-проект получит собственный manifest с идентичностью исходников. Для его source_dirty=false нужна самостоятельная чистая Git-копия, а не подкаталог чужого большого репозитория. Уже сейчас привыкайте проверять git rev-parse --show-toplevel перед изменением истории: ошибочно выбранный корень — реальный способ затронуть совсем другой проект.

Подсказки · открыть после своей попытки

Вопросы перед командой восстановления

  1. Что находится только в рабочем дереве, что в индексе, что в commit? Учитывает ли ваша страховка каждое нужное состояние?
  2. Какая именно строка соответствует наблюдаемому неправильному сокету? Найдите её происхождение через историю одного пути.
  3. Нужно вернуть весь прошлый файл или одну настройку? В прошлом файле могут отсутствовать полезные новые параметры.
  4. Уже опубликованную ошибку обычно удобнее исправить новым commit. Не меняйте весь граф, если задача касается одного параметра.
  5. Как убедиться, что процесс прочитал исправленный файл? Пара «Git status чист — значит сервис исправен» не содержит прикладной проверки.
Разбор и проверка результата

Один вариант решения без потери соседней работы

В учебной копии создайте отдельную ветку исследования, сохранив предварительно незавершённые данные. Имя ветки не является копией неотслеживаемых файлов и не заменяет страховку рабочего дерева. Убедитесь, что все следующие пути находятся в нужном корне:

git rev-parse --show-toplevel
git status --short
git switch -c repair/service-listen
git log -p -5 -- config/server.env
git show HEAD~1:config/server.env

switch -c создаёт и переключает ветку; оно может сохранить допустимые локальные изменения, поэтому проверьте status ещё раз. Если весь прежний файл действительно соответствует требованию, используйте git restore --source=HEAD~1 --worktree -- config/server.env. Если требуется лишь строка, сначала выведите прежнее содержимое и отредактируйте только её. Затем сравните текущий diff с ожидаемой небольшой правкой. Не восстанавливайте каталог целиком, когда задача относится к одному файлу.

git diff -- config/server.env
git add -- config/server.env
git diff --cached -- config/server.env
git status --short

Добавьте только исправляемый путь и проверьте подготовленный снимок. Полезная запись notes должна остаться в том же состоянии, в котором вы намеревались её сохранить; новые данные службы вне репозитория вообще не участвуют в этой операции. Commit создавайте с явной личной идентичностью учебного репозитория, а не унаследованным рабочим email. Для публичного проекта используйте свой безопасный noreply-адрес. Настройка автора и коммитера относится к метаданным Git, а не к SSH-личности сервера.

Если ошибочный commit менял только эту настройку и опубликован, альтернативой служит git revert ИДЕНТИФИКАТОР. Команда создаёт обратное изменение и может получить конфликт, когда последующие изменения затронули те же места. Разрешая конфликт, сохраните смысл текущих нужных параметров; автоматический выбор всей стороны не является доказанным решением. Обратный commit также должен пройти те же прикладные проверки.

Независимое доказательство

Запишите фактический путь конфигурации службы, способ применения и наблюдаемый сокет после него. Из точки клиента выполните тот же запрос, который ранее не работал, с ограничением времени и узнаваемым содержимым ответа. Проверьте, что неожиданный старый адрес больше не обслуживается, если это часть требования. Сохраните исходный и исправленный diff, новый commit, статус незавершённых notes и отсутствие изменения данных. Это замыкает цепочку от причины в тексте до поведения работающего процесса.

Что передать следующему этапу

Сохрани отчёт по рабочему методу: исходные наблюдения, проверенную причину, изменения, положительные и отрицательные проверки и способ возврата. Затем выключи гость и создай точку done-p08-git-config. Новая глава использует этот результат; её открытие ничего не сбрасывает.
