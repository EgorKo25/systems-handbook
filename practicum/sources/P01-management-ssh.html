После консоли нужен повторяемый безопасный вход с личного компьютера.

Заявка и исходные условия

STUDY-01: Управление по SSH и доверие к узлу

Доступ: Только localhost management через QEMU 2222; известный ключ сверяется из консоли.

Наблюдаемый симптом: TCP доступен, но вход не проходит либо меняется fingerprint.

Доказательства результата: Вход своим пользователем, объяснение ключа узла и ключа пользователя; root-пароль не передаётся в командной строке.

Возврат: Не отключать консоль до второго независимого входа; вернуть прошлый sshd config.

Исходное состояние подготовлено в заданиях: P00-rescue-bootstrap.

Контрольные точки выключенного мира: before-p01-management-ssh перед работой и done-p01-management-ssh после проверок. Это сохранение дискового состояния, без открытых сеансов и памяти процессов.

Начальная оценка памяти гостя: 1024 МиБ. Это бюджет для проверки состава ролей, а не измеренное требование и не гарантия достаточности для всех служб вместе.

Подготовлен рецепт. Подготовлен рецепт SSH; вход на настоящем госте ещё не проверен. Полный запуск этого сценария на QEMU и Windows пока не подтверждён.

Первая установка OpenSSH и собственная настройка входа

Продолжай установленного Linux-гостя P00 через консоль. Сервер OpenSSH добавляется сейчас, а не подразумевается готовым. Дома найди официальную инструкцию Ubuntu и сверь названия openssh-server и openssh-client с каталогом пакетов своей версии ОС.

Для автономной установки пакетов используем один договор. В том же сохраняемом госте обнови подписанные индексы APT, посмотри apt-cache policy нужного пакета, выбери точную версию и через apt-get --download-only подготовь его и требуемые изменения зависимостей. Сохрани deb-файлы и проверенные метаданные в личный комплект стадии. Другая ОС или другая архитектура не являются равной средой. Проверь полноту комплекта заранее: на работе установка с --no-download должна обходиться без обращения к сети и завершаться ошибкой при отсутствии зависимости. Подпись APT относится к цепочке метаданных и хешей пакетов, а не к произвольному deb с форума.

После установки в госте выясни способ активации ssh.service/ssh.socket, расположение sshd_config и включаемых файлов; посмотри systemctl status ssh и ss -ltnp. Используй обычного пользователя из P00; подготовь его каталог .ssh и authorized_keys с подходящим владельцем и правами. Ключ клиента создаётся и хранится в личном комплекте; закрытая часть на сервер не копируется. Сверь fingerprint серверного ключа через консоль до первого доверенного подключения.

Проверь sshd -t перед применением конфигурации и sshd -T для её итоговых значений с учётом подходящего контекста Match. Сохрани открытый аварийный сеанс, перечитай или перезапусти именно свою службу и новым сеансом проверь вход. Проверь отказ незарегистрированного ключа отдельно от возможного входа по паролю: отключи другие методы только в проверочном клиенте и изучи результат. После этого можно осознанно ограничивать парольный вход и пользователей; не отключай единственный работающий способ раньше приёмки замены.

В паспорт SSH добавь версию пакета, ключ узла/fingerprint, активный unit, файлы Include, адрес/порт гостя, отдельный loopback-порт QEMU на хосте, разрешённого пользователя, known_hosts, путь журналов journalctl -u ssh. Штатная остановка VM не удаляет ключи и authorized_keys. Следующие главы используют тот же вход; изменение host key сначала расследуют, а не лечат удалением known_hosts. Правила управления пакетами: документация Ubuntu APT.

Как подойти к работе

Как консольный вход становится сетевым

В P00 вы вошли через консоль и проверили файл после перезапуска. Теперь с того же компьютера войдите в гостевую ОС по SSH под своим обычным пользователем. Сначала из консоли снимите отпечаток ключа узла. При первом соединении клиент покажет отпечаток сервера, который ему ответил. После сверки сервер проверит уже ваш ключ пользователя и откроет сеанс.

Клиент подключается к 127.0.0.1:2222 на хосте. QEMU пересылает соединение на TCP-порт SSH внутри гостя. Если клиент сразу пишет Connection refused, начните с проброса порта и слушающего сокета. Сообщение Permission denied (publickey) появляется после обмена с SSH-сервером. Тогда ищите причину в выбранном имени пользователя, ключе или правилах входа. При тайм-ауте по одному сообщению нельзя определить, где потерялся ответ.

Записи о доверенных ключах храните в каталоге конкретной учебной VM. Две разные VM могут по очереди занимать порт 2222, но показывать разные ключи. Если при запуске того же диска клиент видит другой ключ узла, вернитесь в консоль гостя и выясните причину. Консоль оставьте открытой до успешного входа из второго терминала.

Подсказки · открыть после своей попытки

Если соединение не устанавливается

  1. Проверьте, работает ли QEMU и тот ли порт указан в выводе контроллера. SSH с -p 22 обращается к SSH хоста, если он там есть; это не наш гостевой 2222.
  2. Включите -v у клиента и найдите последнюю подтверждённую стадию. Не публикуйте полный диагностический журнал без просмотра: в нём есть пути, имена пользователей и адреса.
  3. Сверьте fingerprint через уже доверенную консоль гостя. Не заменяйте проверку автоматическим StrictHostKeyChecking=no.
  4. Если сервер доступен, проверьте выбранного пользователя, его authorized_keys, права и журнал. Не ищите сетевую проблему в ситуации, где сервер уже явно отказал в аутентификации.
Разбор и проверка результата

Контрольный порядок

В гостевой консоли получите отпечаток конкретного открытого ключа узла:

sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

-l выводит fingerprint, -f выбирает файл. Мы читаем публичный файл, не копируем закрытый ключ. Если Ed25519-ключ отсутствует, сначала выясните, какие host keys реально настроены; команда не требует создавать новый ключ при каждом упражнении.

В каталоге стенда на клиенте пример запроса выглядит так. student — условное имя: замените его именем своего обычного пользователя, созданного в P00, а не создавайте новую учётную запись только ради совпадения строки. Подготовьте клиентский каталог runtime; внутри гостя он не нужен.

ssh -v -F none -p 2222 \
  -o UserKnownHostsFile=runtime/known_hosts -o GlobalKnownHostsFile=none \
  student@127.0.0.1

-v выводит этапы соединения, -p выбирает порт, а -o UserKnownHostsFile указывает файл доверенных ключей на клиенте. Сравните алгоритм и отпечаток из запроса SSH с результатом команды в консоли. Прерывайте вход при несовпадении. В PowerShell введите команду одной строкой без обратных косых черт в конце строк.

Создайте отдельный клиентский ключ в личном каталоге. Добавьте в ~student/.ssh/authorized_keys гостя только его публичную часть, отдельной строкой. Подставьте имя своего пользователя вместо student. Закрытый ключ остаётся на клиенте. Если трогали конфигурацию сервера, выполните sudo /usr/sbin/sshd -t и исправьте обнаруженные ошибки до применения настроек. Консоль сохранит доступ, если в новом сетевом сеансе вход не получится.

После сверки ключа узла запустите пробу с разрешённым пользовательским ключом. Укажите свой путь в IdentityFile и проверьте, что файл читается. Эта команда рассчитана на OpenSSH, поддерживающий -F none.

ssh -v -F none -p 2222 \
  -o UserKnownHostsFile=runtime/known_hosts -o GlobalKnownHostsFile=none \
  -o StrictHostKeyChecking=yes \
  -o PreferredAuthentications=publickey \
  -o IdentitiesOnly=yes -o IdentityAgent=none \
  -o IdentityFile=runtime/private/p01_ed25519 student@127.0.0.1

-F none исключает настройки из файлов клиента. PreferredAuthentications=publickey оставляет вход по ключу, а IdentityFile указывает файл ключа. IdentitiesOnly=yes ограничивает выбор настроенными ключами, IdentityAgent=none отключает обращение к агенту. GlobalKnownHostsFile=none вместе с указанным UserKnownHostsFile оставляет для этой пробы только записи учебного стенда. StrictHostKeyChecking=yes требует уже известный ключ узла. После входа выполните whoami и hostname и сравните обе строки с выводом из консоли.

Повторите ту же команду с другим своим ключом, для которого публичная часть не добавлена в гостя. По -v убедитесь, что клиент дошёл до отправки именно этого ключа. Ожидаемый итог — Permission denied (publickey). В госте сопоставьте время попытки с журналом sudo journalctl -u ssh --since '10 minutes ago' --no-pager. Эта проба показывает отказ по ключу при выбранном методе. Для проверки политики парольного входа нужна отдельная попытка с явно выбранным парольным методом.

В журнале задания запишите порт, открытый отпечаток ключа узла, результат разрешённого входа и результат пробы с другим ключом. Пароли и закрытые ключи храните отдельно от журнала.

Опции клиента описаны в ssh(1) и ssh_config(5).
