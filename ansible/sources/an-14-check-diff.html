Check и diff: прогноз с ограниченным контрактом

Dry run полезен, когда известно, что именно умеет прогнозировать каждый модуль. Это не безопасная транзакция с вычисленным будущим миром.

Сравнимые вызовы

Для первой проверки используйте уже подготовленную копию labs/local и сохранённые переменные её README, как в главе 7. Выполните начальный apply версии 0.1.0, если его ещё не было, и запишите содержимое файлов. Теперь кандидатом будет 0.2.0: первая команда ниже только прогнозирует, вторая применяет это же изменение. Это реальная файловая лаборатория без systemd и без sudo. После неё VM-сценарий разбирается отдельно с собственным inventory и release-vars.yml.

ansible-playbook site.yml -e @"$ANSIBLE_LAB_ROOT/vars.json" --limit counter_a -e counter_release=0.2.0 --check --diff
ansible-playbook site.yml -e @"$ANSIBLE_LAB_ROOT/vars.json" --limit counter_a -e counter_release=0.2.0 --diff

В первом вызове --check просит поддерживающие его действия сообщить предполагаемое изменение; второй реально применяет. --diff просит показать различия у поддерживающих действий, но не включает check. Простой --diff способен изменить систему. Аналогично --syntax-check проверяет структуру, а --list-tasks перечисляет известные задачи; ни один из этих флагов не подтверждает доступность SSH или работоспособность приложения.

Для copy/template check сравнивает текущий файл с кандидатом, но не создаёт всю будущую ОС для последующих задач. Если первая задача только прогнозирует создание каталога, следующая может не найти его. Если skipped command должен был получить register.stdout, условие ниже не получает настоящего результата команды. Поэтому check на уже подготовленном стенде часто информативнее check на пустой VM, но и тогда остаётся прогнозом. В тестовом образце сначала реально создают корень и исходное состояние, затем проверяют изменение версии без записи.

Уровень поддержки — свойство действия

В ansible-doc смотрят Attributes: check_mode и diff_mode, а не предполагают поддержку по слову «модуль». Command имеет частичную check-семантику через creates/removes; без них обычный запуск в check пропускается. Shell не может в общем случае понять последствия произвольного кода. Собственный модуль обязан сам реализовать чтение состояния, прогноз и запрет записи при module.check_mode; один supports_check_mode=True не делает реализацию правильной.

- name: Observe current version even during check
  ansible.builtin.command:
    argv: ['/opt/counter/current/counter', '--version']
  changed_when: false
  check_mode: false

Это намеренно выполняемое чтение даже при глобальном check. У него должен быть доказанный безопасный контракт. Для команды «reset data» такое исключение уничтожило бы смысл preview. Задача с check_mode: false, lookup/plugin и внешнее API могут совершать действия в глобальном check; поэтому один флаг не является границей доверия к чужому playbook.

Что может утечь через diff

Diff может показать старый и новый пароль, токен или частный ключ. У секретного шаблона ставят diff: false и no_log: true, конечные owner/group/mode и безопасные временные каталоги. Но no_log не удаляет секрет из файлов назначения, внешнего журнала приложения и собственных callback-плагинов с ошибочным поведением. Не передают секрет через CLI-аргументы или debug ради проверки маскирования. Криптографическое хранилище на диске и журнал исполнения решают разные угрозы.

Проверка прогноза

Испытание состоит из четырёх наблюдений: hash/mtime исходного файла; check с изменённой desired version; тот же hash/mtime после check; реальное apply и изменение нужного поля. Затем повтор apply обязан не изменять файл при стабильных входах. Наш lab-check сохраняет эти свидетельства и дополнительно проверяет diff собственного модуля без раскрытия секретов. Для check на чистом состоянии ошибки зависимостей не маскируются: такой режим описывается как ограниченный.

Прогноз не гарантирует, что через минуту останется тот же репозиторий пакетов, свободный диск, API quota или значение inventory. Между check и apply читается новое состояние. В Ansible нет универсального сохранённого атомарного плана для всех ресурсов. Для критического выпуска фиксируют артефакт, inventory-состав и входы, затем заново проверяют предпосылки перед переключением. Официальные границы: check/diff, command, сверено 01.11.2026.
