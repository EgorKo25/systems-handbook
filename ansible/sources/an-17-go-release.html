Выпуск Go: один артефакт, постоянные данные, явный возврат

Установка файла не равна продвижению работающей версии. Workflow сохраняет прежние config/link и подтверждает процесс до следующей VM.

Что является выпуском

В авторском сервисе /version отвечает встроенной строкой build, GET /counter читает count, POST /counter увеличивает и сохраняет его. /healthz подтверждает живой обработчик; это не внешний аудит долговечности диска. Проверка --check-config FILE разбирает JSON, отвергает неизвестные поля и не создаёт data/listener. --version не открывает config. Приложение работает одним процессом, защищает конкурентные обращения mutex — механизмом взаимного исключения, допускающим изменение счётчика одним обработчиком за раз. Данные — целое uint64 от 0 до 2⁶⁴−1 с завершающим переводом строки. Два сервера имеют независимые файлы: у них нет общей кластерной БД.

При SIGTERM/SIGINT сервер закрывает слушатель и ждёт завершения активных HTTP-запросов до пяти секунд в главном пути программы. Возврат Serve с ErrServerClosed сам по себе не означает, что Shutdown закончил ожидание. При исчерпании срока соединения закрываются, а завершение сообщается как ошибка: незавершённый запрос не выдаётся за успешный. Отдельный тест удерживает настоящий loopback HTTP-запрос, начинает остановку и подтверждает сохранение счётчика перед возвратом; ещё один проверяет конечный предел ожидания. Это не тест power loss или systemd. Основание: контракт net/http Shutdown.

Следующие две команды выполняют в исходном ansible/labs/service, где лежат go.mod и main.go, а не в рабочей VM-копии labs/vm. Используйте отдельный терминал сборки; каталог проекта VM и его inventory остаются прежними. После сборки в counter_artifact передаётся абсолютный путь полученного файла controller.

CGO_ENABLED=0 GOTOOLCHAIN=local GOOS=linux GOARCH=amd64 \
  go build -trimpath -ldflags='-X main.version=0.1.0' -o counter-0.1.0 .
sha256sum counter-0.1.0

Команду выполняют в service-каталоге на выбранном Go toolchain. CGO_ENABLED=0 исключает cgo для этого проекта, GOOS/GOARCH выбирают target, -trimpath уменьшает включение исходных путей, -ldflags передаёт линковщику строку версии. Версия toolchain, исходный commit, flags, платформа, размер и SHA фиксируются в manifest. Нельзя собирать заново независимо на каждой VM и затем утверждать, что доставлен один проверенный бинарник. SHA сравнивает байты, а доверие к исходникам/сборке требует своей цепочки.

Каталоги и фазы

Символическая ссылка, symlink, — имя файла с путём к другому объекту. current выбирает каталог установленной версии; изменение ссылки не перемещает постоянные данные и не перезапускает уже работающий процесс. Stage, подготовка выпуска, означает размещение и проверку новой версии до её активации. Активация меняет выбранную ссылку/настройки, затем перезапуск заставляет процесс прочитать новый выбор. Эти фазы позволяют сохранить прежний каталог и отдельно проверить результат.

Папка релиза не владеет данными. Роль создаёт account/каталоги и unit; systemd запускает процесс как counter с ограниченным writable path. До первой записи на управляемую систему отдельный stat на controller проверяет SHA-256 исходного regular file с delegate_to: localhost и become: false. Stage копирует бинарник только в ещё отсутствующий файл новой версии и проверяет target SHA-256 и --version. Если версия уже существует, её байты обязаны совпасть с ожидаемыми; иной checksum отвергается до copy. Если существующие байты уже верны, copy пропускается; отдельный file восстанавливает только owner/group/mode. Повреждённый исходник controller поэтому не переписывает действующий релиз даже при повторе. Новая копия проверяется на target до переключения ссылки. Пример рассчитан на одного писателя; параллельный второй controller потребует отдельной блокировки.

Переход от stage к готовности

До изменения workflow фиксирует текущий symlink, читает прежний несекретный config и, если сервис уже есть, читает его count. Затем валидирует новый config staged-бинарником, устанавливает unit/config, переключает current, flush handlers и обеспечивает started. Проверяет loopback /version до ожидаемого значения и /counter: count не меньше наблюдённого до выпуска. Serial=1 не пускает следующую VM до окончания этой последовательности. Небольшая пауза доступности одной VM допустима для этого личного стенда; без балансировщика и прикладного контракта нельзя обещать непрерывную доступность клиентов.

Повтор при неизменных файлах не уведомляет handlers, а state: started не перезапускает уже работающий процесс. Так базовая идемпотентность сохраняется. После обрыва между switch и handler файл может уже быть новым, а процесс старым. Для такого состояния предусмотрен явный counter_force_restart: true: он намеренно перезапускает процесс и даёт changed. Восстановление — осознанное действие с наблюдением, не скрытая гарантия notify.

Например, до выпуска у A current → releases/0.1.0, HTTP сообщает 0.1.0, а count равен условному 41. После доставки 0.2.0 каталог новой версии уже существует, но процесс ещё 0.1.0. После замены current/config и до flush диск выбирает 0.2.0, а обслуживающий процесс всё ещё может отвечать 0.1.0. После restart ответ 0.2.0 при count ≥41 подтверждает конкретный переход. Сумма нового бинарника, ссылка на него и HTTP-ответ — три разных наблюдения; один changed=0 не подменяет их. При обычном повторе без различий очередь пустая; при прерывании прежнего запуска это может потребовать явного restart, описанного ниже.

Частичный отказ

При обычном failed внутри block rescue возвращает config и current, перезапускает прежний процесс и проверяет готовность, прежнюю HTTP-версию и count не меньше исходного, затем явно fail останавливает весь rollout. При первой неудачной установке прежней версии нет: убирается только новый current/config, служба останавливается, data-каталог сохраняется. Подготовленные release-каталоги не очищаются автоматически: они полезны для разбора и повторного запуска. Проверка готовности после возврата не доказывает правильность всех прикладных результатов; человек сверяет manifest и count.

Unreachable, питание VM, kill controller и ошибка вне блока не обязаны выполнять rescue. Сначала читают реальное состояние через консоль/SSH, затем выбирают desired version и restart. Если версия приложения изменила формат данных, возврат бинарника может стать невозможным без миграции/резерва. Здесь обе версии используют один формат, migrations отсутствуют; универсальный rollback данных не обещается. Snapshot данных снимают явно при остановленном писателе, а restore понимают как потерю записей после снимка. Полный выполняемый рецепт — VM README, он не объявлен реально испытанным на двух машинах.

Граница с Terraform и наблюдением

Это разделение инструментов, а не готовый переход между лабораториями книги. Локальный Terraform-практикум создаёт запись receipt через terraform_data и не создаёт VM, адреса или SSH-доступ для этого выпуска. В Prometheus-практикуме используется другой Go-сервис на порту 18080; наш «Счётчик» на loopback:8080 остаётся отдельным приложением. Чтобы объединить их, потребовались бы явно реализованные инфраструктура, inventory и наблюдаемые метрики; здесь такое объединение не заявляется.

Terraform может подготовить инфраструктуру и передать адреса/идентичности; Ansible получает проверенный inventory и договор SSH/Python, а не извлекает тайно root-доступ из файла state. Доступы передают защищённым каналом, не публикуют в outputs для общего чтения. Наблюдение приложения после выпуска нужно независимо от инструмента доставки: ожидаемая версия, доступность, сохранённые данные и ресурсная стоимость. В этом томе нет реализации соседнего Terraform-тома или системы мониторинга: контракт достаточен, чтобы разделить ответственность.
