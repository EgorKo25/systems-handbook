Переменные: происхождение, приоритет и время

Одна строка значения может пройти через defaults, inventory, task vars и extra vars. Надёжная конфигурация позволяет объяснить победителя без угадывания.

Приоритет не равен порядку чтения файла

Variable precedence — правила выбора значения при конфликте определений одного имени. Отдельно существует приоритет категорий поведения: config → обычные CLI-опции → keywords playbook → variables → прямое назначение параметров применимого plugin. Например, cfg remote_user=alice, CLI -u bob, play keyword remote_user: carol, inventory ansible_user: dana дадут соединение как dana. -e ansible_user=erin перекроет её extra variable. Флаг -u не означает «самый сильный источник».

Внутри variables полезная восходящая карта такова: role defaults; inventory group/host vars; facts и кэшируемые set_fact; play vars, vars_prompt и vars_files; role vars; block vars; task vars; include_vars; присвоенные во время исполнения set_fact/register; role/include params; extra vars. Это карта основных классов, а не замена полной таблицы: у inventory есть собственные уровни файлов/групп, у кэшируемого set_fact — две копии. При споре сверяются с таблицей конкретной версии и маленьким воспроизводимым play, а не добавляют новый override.

Конкретный конфликт в роли

ИсточникЗначение counter_portРоль определения
roles/counter/defaults/main.yml8080Публичное значение по умолчанию
group_vars/counters.yml8081Параметр группы стенда
host_vars/counter_a.yml8082Исключение узла
play vars8083Параметр этого play
task vars8084Только задача
extra vars JSON8085Параметр всего запуска

В задаче с task vars без extra vars победит 8084; в соседней задаче того же play — 8083. С JSON -e '{"counter_port":8085}' обе увидят 8085 как integer. Если неожиданно положить counter_port в role vars, обычный inventory уже не сможет переопределить интерфейс роли. Поэтому настраиваемые значения помещают в defaults, а не пытаются лечить каждый узел extra vars. Параметр, переданный include_role, также имеет свой высокий приоритет; его нужно считать частью явного вызова роли.

Для исполнимого сравнения используем локальный комплект labs/local, а не неподготовленные VM. Откройте его README и один раз подготовьте свой закрытый корень, vars.json, PATH и ANSIBLE_CONFIG. Затем перейдите в копию local, где cfg выбирает существующий inventory.ini. Последний вызов ниже дополнительно задаёт ожидаемый результат и признак extra-case: это вход проверки самой fixture, без них её assertions по умолчанию ждут обычную ветку. Они не меняют приоритет counter_port. Каталоги и данные предыдущего local-упражнения остаются.

ansible-playbook precedence.yml -e @"$ANSIBLE_LAB_ROOT/vars.json"
ansible-playbook precedence.yml -e @"$ANSIBLE_LAB_ROOT/vars.json" -e '{"counter_port":8085,"counter_expected_port":8085,"extra_case":true}'

Эта пара запусков должна отличаться только входом extra vars. Сравнивают сообщения/сохранённые результаты, а не реальные открытые порты: тестовый образец не запускает сервер. Наш labs/local/precedence.yml содержит проверки этого конфликта. Если число проверок неожиданно стало истинным из-за extra vars, тесты сами могут потерять силу; в тестовом образце ожидаемое значение задаётся отдельным явным контрактом.

Область и момент вычисления

Play vars принадлежат play. Task vars принадлежат вызову задачи. Inventory variables, facts, register и set_fact связаны с конкретным host и доступны через hostvars в рамках нужного контекста; extra vars действуют на весь запуск. Это не общая изменяемая память controller: два host с одним именем переменной имеют свои значения. hostvars['counter_b']['service_version'] имеет смысл только если значение уже определено/получено. Порядок plays и стратегии влияет на доступность runtime-результатов.

Обычная переменная, содержащая Jinja-выражение, вычисляется при использовании в текущем доступном контексте; нельзя считать её снимком на момент чтения YAML. set_fact присваивает вычисленный результат в момент выполнения задачи. Если сначала set_fact: selected: '{{ release }}', затем источник release меняется, selected не обязан пересчитаться сам. Этот эффект полезен для сохранения прежнего пути перед выпуском, но опасен при скрытом кэшировании динамического адреса.

Данные отдельно от политики соединения

Имена ansible_connection, ansible_user, ansible_become и ansible_python_interpreter имеют специальный смысл. Их нельзя незаметно смешивать с пользовательским mapping сервиса. Prefix counter_ защищает интерфейс роли от случайного ключа port другого компонента. Магические переменные вроде inventory_hostname, groups и ansible_play_hosts_all описывают контекст; не пытаются записывать в них свои данные. inventory_hostname не равен автоматически DNS-имени ОС.

Не объединяют весь мир в vars: '{{ hostvars }}'. Для передачи роли достаточно маленького типизированного mapping, например release version, SHA-256, listen и data path. Диагностический след отвечает на четыре вопроса: кто определил, какой приоритет, для какого host, когда вычислено. Официальные правила на 01.11.2026: variable precedence и общие категории. Секретные значения в этот след не выводят.
