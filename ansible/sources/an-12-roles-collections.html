Роли и коллекции: интерфейс большой конфигурации

Структура каталогов полезна, когда задаёт понятные входы, выходы и владельца состояния. Дробление каждого файла на роль само по себе этого не даёт.

Роль как договор

Role, роль, группирует связанные задачи, handlers, defaults, templates и файлы по установленной структуре. Для «Счётчика» роль базовой настройки владеет пользователем, каталогами, config и systemd unit. Выпуск бинарника — отдельный workflow, поскольку его частичный отказ требует своего возврата. Публичные входы имеют prefix counter_, типы, defaults и валидацию. Выходы — явно управляемые пути и свойства, а не неявное изменение всего hostvars.

roles/gosvc/
  defaults/main.yml
  tasks/main.yml
  handlers/main.yml
  templates/config.json.j2
  templates/counter.service.j2
  meta/argument_specs.yml

defaults имеет низкий приоритет и подходит для настраиваемых входов. vars имеет высокий приоритет и используется редко для внутренних инвариантов; обязательный неизменный путь лучше прямо валидировать. meta/argument_specs.yml описывает аргументы роли для встроенной проверки; assert дополняет её межполевыми условиями, например «data path вне каталогов выпусков». files хранит байты без шаблонизации, templates — Jinja-источники. Секреты не включают в роль даже если их потом перекрывает Vault.

Зависимости и время вызова

Секция roles play и import_role дают статическую композицию. include_role позволяет runtime-выбор, loop и контроль публикации defaults/vars через поддерживаемые параметры вроде public. При чтении чужой роли выясняют, где её переменные становятся видимыми; не рассчитывают на историческое значение defaults для другой версии core. Зависимости в meta/main.yml могут выполнять другие роли до текущей; параметры и механизм дедупликации определяют повтор. Не используют скрытую dependency для необратимой миграции БД при каждом включении роли. Явная задача workflow лучше показывает такой переход.

Разделение ролей оценивают по владению ресурсом. Если две роли обе редактируют один config и обе перезапускают процесс, они конкурируют даже в одном последовательном play. Если роль принимает сотню неструктурированных toggles, клиент не может понять поддерживаемые комбинации. Один mapping с документацией, типами и ограниченным числом режимов легче проверять. Слишком глубокая цепочка dependencies увеличивает количество скрытых задач и время диагностики.

Collection и полное имя

FQCN, fully qualified collection name, полное имя объекта вида ansible.builtin.copy, включает namespace, collection и module/plugin. Короткое copy зависит от контекста поиска; явное имя уменьшает неоднозначность и связывает текст с правильной документацией. Для своей коллекции путь выглядит ansible_collections/lab/counter/plugins/modules/counter_config.py; модуль вызывается lab.counter.counter_config. Локальный library/ подходит лабораторному модулю, но не заменяет пакетный интерфейс команды.

collections:
  - name: community.general
    version: '11.4.0'

Это пример точной фиксации версии, а не зависимость упражнений и не утверждение, что указанная версия подходит всякой ОС. Сам номер подтверждён официальным релизом 11.4.0 при сверке 01.11.2026. Перед применением выбирают существующий релиз по его release notes, requirements и поддержке core. ansible-galaxy collection install -r collections.yml -p ./collections пишет в выбранный каталог; этот путь включают в конфигурацию поиска. ansible-galaxy collection list показывает установленные экземпляры по путям. Две версии в разных каталогах не означают одновременный выбор по одному номеру: порядок поиска может затенить ожидаемую. Полный пакет ansible также способен привнести другую версию.

Например, lab.counter.counter_config выбирает код из коллекции, найденной на controller; путь /etc/counter/config.json в аргументе относится к месту исполнения модуля. Файл roles/gosvc/templates/config.json.j2 ищется в роли, а не рядом с удалённым config. Если после установки второй коллекции изменился выбор кода, сначала сверяют ansible-galaxy collection list, пути из ansible --version и локальный ansible-doc. Наличие нужного tarball в офлайн-каталоге ещё не означает, что он установлен в выбранном пути поиска. Исправление пути не должно подменять уже принятый набор зависимостей без повторной проверки.

Совместимость и доверие к расширениям

У коллекции собственный requires_ansible, Python-зависимости и условия модулей. Поддерживаемый core не гарантирует совместимость каждой коллекции; наоборот, установка коллекции не обновляет произвольную библиотеку на target. Galaxy/Automation Hub распространяют код; подпись проверяет определённую цепочку доверия, если она настроена и доступна, но не делает операции безопасными по смыслу. Ревью включает action/filter/lookup plugins: они исполняются на controller с доступом к его файлам и credentials.

Для повторяемого комплекта сохраняют requirements с точными версиями, tarballs, хеши, описания dependencies, lock Python и target OS manifest. В томе нет внешних коллекций: все исполняемые тестовые образцы используют встроенные модули и один авторский локальный модуль. Это уменьшает число независимых источников вариации и делает офлайн-проверку понятной. Официальные контракты: roles, collections guide, сверено 01.11.2026.
