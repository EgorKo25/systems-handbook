Facts, register и set_fact: наблюдение и память

Результат задачи и факт об ОС различаются происхождением и сроком достоверности. Кэш ускоряет чтение, но сохраняет вчерашнюю картину.

Сбор facts

Facts — собранные сведения о target: ОС, интерфейсах, памяти и других поддерживаемых свойствах. По умолчанию play часто начинается с Gathering Facts, вызова setup. Это удалённая работа: Python, чтение ОС и передача JSON. ansible_facts['distribution'] описывает наблюдённую систему, но не означает автоматически совместимость любого пакета. Назначение интерфейса по «первому адресу» хрупко при нескольких сетях. В роли проверяют конкретные требования, а в inventory задают адрес нужного соединения.

- name: Observe only required operating system facts
  ansible.builtin.setup:
    gather_subset:
      - '!all'
      - '!min'
      - distribution
    filter:
      - ansible_distribution*

gather_subset выбирает группы реально собираемых данных. filter ограничивает возвращаемые keys и не гарантирует столь же сильного уменьшения стоимости самого сбора. Если facts не нужны, ставят gather_facts: false, а не скрывают строку вывода обработчика событий. Для сравнения замеряют тот же inventory без сборки, с обычной сборкой и с subset; отделяют холодный SSH от времени setup.

Register хранит ответ, а не текст терминала

- name: Inspect existing config
  ansible.builtin.stat:
    path: '{{ counter_root }}/config.json'
    checksum_algorithm: sha256
  register: counter_before

- name: Assert expected type
  ansible.builtin.assert:
    that:
      - not counter_before.stat.exists or counter_before.stat.isreg

register связывает полный результат задачи с host. У stat это mapping со stat, у command есть rc/stdout/stderr, у loop появляется results — список отдельных результатов. Поле stdout не универсально. Неуспешная или skipped задача тоже может оставить результат с соответствующим признаком; прежде доступа к полям учитывают ветку. Проверки result is failed, is skipped, is changed читают состояние результата, а не наличие произвольного ключа.

В loop успешная итерация не отменяет неуспешную соседнюю. Для именования используют loop_control.loop_var, чтобы вложенная роль не перетёрла item. Результат цикла исследуют по каждому item; общий changed станет true, если изменился хотя бы один элемент. Уведомление handler от loop также основано на общем changed, поэтому перезапуск может быть нужен хотя бы из-за одного файла.

Переменная есть, а измерения нет

В VM-рецепте counter_old_config заполняется задачей slurp только при существующем старом файле. На первой установке задача пропущена: register может существовать с skipped: true, но не содержит ожидаемого content. Поэтому rescue читает counter_old_config.content только под тем же условием counter_old_config_stat.stat.exists. Проверка одного counter_old_config is defined не доказывает, что файл был прочитан. Так же при loop содержимое лежит в отдельных results; нельзя брать один общий stdout и считать его ответом всех узлов.

Факт ОС и HTTP-ответ тоже имеют разное время: setup наблюдал архитектуру до выпуска, register от /version наблюдает процесс после перезапуска. Обновление файла facts не переписывает прежний register. Для решения «можно переходить к B» нужен новый ответ A после flush, а не сохранённое до выпуска число. Если ответа нет, состояние неизвестно; оно не становится нулевой версией или пустым счётчиком.

Set_fact фиксирует вычисление

set_fact создаёт связанную с host переменную в момент задачи. Она подходит для снимка старой версии перед изменением, нормализованного списка или результата выбора. Не стоит заменять ею все vars: вычисление становится событием, и зависимость от порядка скрывается. cacheable: true одновременно создаёт высокоприоритетную host-переменную текущего запуска и более низкоприоритетную копию в ansible_facts, пригодную для настроенного fact cache. На следующем запуске остаётся только кэшируемая семантика, поэтому приоритет может измениться. meta: clear_facts удаляет facts/кэшируемую копию, но не обязательно высокоприоритетную host-копию текущего set_fact.

- name: Remember chosen release for later plays
  ansible.builtin.set_fact:
    counter_observed_release: '{{ version_probe.stdout | trim }}'
    cacheable: false

Это runtime-память запуска, не новая запись в inventory и не журнал развёртывания. При падении controller позднее значение не восстановится волшебно. Для операционного решения сохраняют отдельный release manifest и наблюдённое состояние цели; при повторе заново опрашивают текущий symlink и ответ процесса.

Fact cache и ложная свежесть

По умолчанию memory cache живёт только в текущем запуске. Дисковый plugin, например jsonfile, требует явных путей, прав и срока. Кэш может содержать адреса, данные файлов и результаты custom facts; он не должен быть общедоступным. TTL, time to live, срок пригодности, ограничивает возраст записи, но не гарантирует соответствие ОС после изменения. Host с тем же inventory-именем после пересоздания может получить старые факты. Версию/идентичность машины учитывают при очистке и повторном сборе.

Кэш полезен для просмотра сведений других узлов, но не заменяет синхронизацию выпуска. Перед критическим решением — например, выбирать нужный бинарник по архитектуре — получают свежий факт либо передают проверенный контракт платформы. На схеме и в локальном тестовом образце facts выключены, чтобы не собирать сведения хоста пользователя.
