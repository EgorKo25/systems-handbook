Конфигурация и inventory: кто попадёт под действие

Адрес узла, имя в данных, группа и переменная соединения — разные части договора. Ошибка выбора опаснее ошибки отдельного модуля.

Как находится конфигурация

ansible.cfg — INI-файл поведения движка. Порядок поиска: переменная окружения ANSIBLE_CONFIG, затем файл в текущем каталоге, затем ~/.ansible.cfg, затем /etc/ansible/ansible.cfg. Используется первый найденный, файлы не сливаются. Автоматическое чтение из world-writable текущего каталога отключено: соседний пользователь мог бы подложить plugin или команду. Явный ANSIBLE_CONFIG — осознанный выбор доверенного файла, а не средство сделать чужой каталог безопасным.

ansible --version
ansible-config dump --only-changed
ansible-config view

показывает эффективные настройки и происхождение, view — содержимое выбранного файла, а --version — его путь. Если после перехода в каталог изменилось поведение, сначала сравнивают эти свидетельства. Настройка окружения перекрывает cfg, обычные CLI-опции перекрывают настройки; playbook keywords и затем variables могут перекрыть CLI. Например, -u deploy уступит inventory-переменной ansible_user: operator. Параметр -e ansible_user=deploy — extra variable с гораздо более высоким приоритетом. Полная модель разобрана в книге переменных.

Статический состав сохраняемого стенда

Сначала подготовьте файлы проекта. Скопируйте весь ansible/labs/vm из своей локальной копии книги в личный каталог работы; это исходники настройки, а не созданные VM. Рабочим каталогом следующих inventory-команд будет эта копия vm. В ней уже есть ansible.cfg, site.yml и роль roles/gosvc. Скопируйте inventory/hosts.example.yml в inventory/hosts.yml один раз и замените адреса своими после подготовки VM. Не подменяйте этот файл при следующем занятии. До готовности SSH и артефакта ограничимся просмотром состава.

Inventory ниже записан в YAML. Пока достаточно трёх правил чтения: имя: значение задаёт поле; отступ вкладывает его в родительский объект; поля children, hosts, vars обозначают вложенные группы, узлы и переменные. Здесь ansible_user — учётная запись входа на управляемой ОС, ansible_python_interpreter — абсолютный путь её Python. Это имена параметров Ansible, не команды оболочки. Подробный язык данных и типы разберёт глава YAML; первичную структуру можно проверить уже сейчас без исполнения задач.

all:
  children:
    lab:
      children:
        counters:
          hosts:
            counter_a:
              ansible_host: 192.0.2.11
            counter_b:
              ansible_host: 192.0.2.12
      vars:
        ansible_user: deploy
        ansible_python_interpreter: /usr/bin/python3

Адреса 192.0.2.0/24 — диапазон примеров документации; в VM-рецепте их заменяют адресами своих машин. counter_a — устойчивое inventory-имя, ansible_host — адрес соединения. Изменение адреса не обязано менять логическое имя. Два имени с одним IP не создают две независимые машины: они способны одновременно менять один файл. Группа counters входит в lab; узел может состоять в нескольких группах, а их переменные сводятся для узла. all содержит всех, ungrouped — узлы без других групп. Имена окружений лучше разнести по inventory-каталогам с отдельными group_vars и явным -i.

ansible-inventory -i inventory/hosts.yml --graph
ansible-inventory -i inventory/hosts.yml --host counter_a
ansible-playbook -i inventory/hosts.yml site.yml --list-hosts
ansible-playbook -i inventory/hosts.yml site.yml --limit counter_a --list-hosts

не выполняет задач; --host показывает сведённые inventory-переменные, которые могут содержать секреты. --list-hosts учитывает plays и limit, но не является пробным выполнением. --limit сужает множество, выбранное hosts, а не расширяет его. До изменения сравнивают запуск без limit с ограниченным: ожидаемые два имени против одного. Pattern 'lab:&counters:!maintenance' означает пересечение и исключение; кавычки защищают специальные символы от оболочки. Пустая выборка не доказывает исправность роли: возможно, она вообще не исполнялась.

Одно имя, три разных ответа

Для counter_a сначала решается, попал ли он в выборку: группа counters содержит A и B, а --limit counter_a оставляет A. Затем inventory даёт адрес ansible_host и пользователя ansible_user. Наконец, при исполнении конкретной задачи движок добавляет play/task/extra variables. Поэтому ansible-inventory --host counter_a полезен для первого слоя данных, но не обязан показать будущий task override. Например, inventory задаёт порт приложения 8082, play — 8083, а одна задача — 8084: просмотр inventory остаётся 8082, хотя аргумент той задачи равен 8084. Порт приложения здесь не меняет SSH-порт.

Для чтения относительного пути также нужен владелец настройки. Значение inventory = ./inventory/hosts.yml из выбранного ansible.cfg разрешается относительно этого cfg; аргумент CLI -i inventory/hosts.yml относится к текущему рабочему каталогу. Они совпадают в своей VM-копии проекта и способны разойтись после cd. Сохраните вместе абсолютный путь cfg, рабочий каталог и команду. Если A исчез из вывода, сначала исправьте источник/выборку, затем снова проверьте одно ожидаемое имя; не принимайте пустой recap за успешную настройку.

Переменные и несколько источников

group_vars/all.yml, group_vars/counters.yml и host_vars/counter_a.yml отделяют параметры от состава. Host vars конкретнее group vars; дочерняя группа перекрывает родительскую. Для групп одинакового уровня действуют правила слияния и порядок, включая ansible_group_priority, задаваемый в inventory-источнике. Не строят критический интерфейс на случайном алфавите групп: конфликт устраняют в явном месте. При нескольких -i важен порядок источников. Проверяют конечные значения и сохраняют команду вызова, не только последний YAML.

По умолчанию словари с одинаковым именем заменяются, а не глубоко объединяются. Параметры service_defaults и service_override безопаснее объединить явно фильтром combine с задокументированной глубиной и правилами списков, чем глобально менять hash_behaviour. Для воспроизводимости читатель должен увидеть, какие ключи реально получились.

Динамический состав и граница доверия

Dynamic inventory строится plugin из API (программного интерфейса внешней системы) или другого источника в момент загрузки. Это не автоматическое обнаружение всего интернета. Его конфигурация выбирает учётные данные, фильтры, имена, группы и кэш. Legacy inventory-script выводит JSON по протоколу --list/--host; современные плагины могут собирать hostvars эффективнее. Успешный ответ API не доказывает правильность фильтра окружения. Перед изменением сохраняют обезличенный состав, проверяют стабильность имён и причины исчезновения узла. Кэш состава и fact cache решают разные задачи; устаревший inventory может отправить задачу прежнему владельцу адреса.

Полученные inventory-данные влияют на connection, become и пути. Поэтому чужой файл inventory — активный вход автоматизации, а не безобидная адресная книга. Прогон inventory и шаблонов возможен без SSH, но lookup/plugin способен делать сеть уже на controller. Для локальных проверок тома inventory фиксирован, plugins сторонних источников не используются.
