Jinja: вычисление данных на управляющей стороне

Шаблон строит аргументы и файлы. Его источник, момент вычисления и итоговый тип так же важны, как написанное выражение.

Выражение, оператор и результат

Jinja — шаблонизатор, который вычисляет выражения в контексте переменных. {{ expression }} вставляет результат, {% if ... %} управляет выводом шаблона, {# ... #} — комментарий. В when, failed_when и changed_when уже ожидается выражение: дополнительные {{ }} не нужны. В core 2.19+ проверки корректности и доверия шаблонов стали строже; случайно непустая строка больше не должна играть роль осмысленного boolean-условия. Для core 2.21.5 используем явные сравнения и типизированные входы.

vars:
  counter_defaults: {listen: '127.0.0.1:8080', feature: false}
  counter_override: {feature: true}
  counter_effective: '{{ counter_defaults | combine(counter_override) }}'
tasks:
  - name: Verify feature contract
    ansible.builtin.assert:
      that:
        - counter_effective['feature'] is boolean
  - name: Choose enabled path
    ansible.builtin.debug:
      msg: 'feature enabled'
    when: counter_effective['feature']

combine строит новый mapping; при одинаковом ключе правый mapping перекрывает левый. По умолчанию это не обещание рекурсивного merge произвольной структуры. Для вложенных словарей задают recursive=true, для списков — выбранный list_merge, затем отдельно проверяют результат. Большой универсальный merge затрудняет объяснение происхождения одного значения. Обращение obj['items'] избегает конфликта ключа items с методом mapping при точечной записи.

Undefined, null и намеренное отсутствие

Undefined означает, что имени/ключа нет в доступном контексте. Null — существующее пустое значение; false, 0, пустая строка и пустой список также разные допустимые данные. var | default('fallback') заменяет undefined. default('fallback', true) заменяет и false-like значения: это может испортить законный false для feature. Обязательное поле лучше проверить is defined, типом и ограничениями; молчаливый fallback для адреса production опасен. mandatory делает отсутствие явной ошибкой, но также не проверяет диапазон порта.

- name: Create directory with optional owner
  ansible.builtin.file:
    path: '{{ counter_root }}'
    state: directory
    owner: '{{ counter_owner | default(omit) }}'
    mode: '0750'

omit — специальное значение, указывающее не передавать параметр модулю, а не строка, которую надо записать в файл. После default(omit) цепочка других фильтров может сломать это намерение; для сложного преобразования лучше заранее выбрать ветку и проверить данные. Не путают отсутствие owner с явным требованием поставить owner в null. Строка '{{ another }}' в недоверенных полученных данных не должна превращаться в автоматически исполняемый второй шаблон.

Фильтры, tests и lookups

Filter преобразует значение: int, to_json, dict2items, selectattr, map. Test проверяет свойство: is mapping, is defined, is failed. Lookup обращается к внешнему источнику на controller; это может быть файл, environment или API, и результат имеет границы доверия/доступности. lookup('env', 'TOKEN') читает окружение controller, а не target. Шаблон может сделать сетевой lookup ещё до SSH; поэтому «только check» не значит «никаких внешних обращений».

Структурированные файлы надёжнее строить сериализатором, а не вручную расставлять JSON-кавычки:

{{ {'listen': counter_listen,
    'data_file': counter_data_file,
    'message': counter_message} | to_nice_json }}

Фильтр экранирует кавычки и переносы в строках. Итог всё равно валидируют самим приложением перед заменой файла. quote помогает shell-аргументу определённого формата, но не является HTML-, SQL- или JSON-экранированием. to_yaml меняет представление, а не автоматически проверяет контракт приложения. При вычислении коллекций полезно явно материализовать результат | list, когда следующий модуль ожидает список.

Один перевод строки проходит два языка

Пусть counter_message — строка из двух строк текста: Первая, LF, Вторая. В YAML-блоке |- внутренний LF сохраняется, а завершающий отсутствует. Фильтр to_nice_json записывает внутренний LF внутри JSON-строки двумя печатными знаками \n: байты 0x5c и 0x6e. Когда Go разбирает JSON, поле Message снова содержит LF 0x0a. Нельзя заменить эти два знака физическим LF внутри JSON-кавычек: это уже недопустимый JSON. Перевод строки после закрывающей фигурной скобки — отдельный разделитель документа.

В учебном модуле есть ещё один слой: чтение UTF-8-текста нормализует CRLF/CR в LF до сравнения строк. Поэтому одинаковый результат после разбора не доказывает одинаковые исходные байты. Если нужен именно побайтовый контракт, его надо реализовать чтением байтов и отдельно проверить; нынешний модуль обещает сравнение текста и прав. Так ошибка сериализации, нормализация чтения и семантика приложения остаются различимыми.

Стоимость шаблонизации и диагностика

Если для каждого из N узлов шаблон каждый раз просматривает hostvars всех N узлов, объём работы способен приблизиться к N². Большой JSON в -vvv увеличивает память и риск утечки. Измеряют controller CPU и время рендера на фиксированном наборе данных, затем выносят действительно общую нормализацию в отдельный этап. set_fact может зафиксировать вычисление, но меняет время и область значения: его нельзя добавлять как невидимую оптимизацию без проверки смысла.

При ошибке начинают с конкретного имени, его типа и источника; в несекретном тестовом образце выводят type_debug и маленький фрагмент структуры. Не печатают весь hostvars ради одного порта.
