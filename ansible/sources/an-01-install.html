Получение, фиксация и приёмка инструмента

Установка — цепочка доверия и совместимости. Ansible CLI, Python, коллекции и Python-библиотеки образуют разные слои комплекта.

Что именно скачивается

ansible-core содержит движок, CLI — command-line interface, командный интерфейс — и встроенные модули/плагины. Пакет ansible добавляет отобранные community-коллекции, но не превращается в сервер с обязательной БД. Collection, коллекция, — именованная поставка модулей, плагинов и ролей вида namespace.name. Номер полного пакета, core и коллекции нельзя сравнивать как версии одной программы. Даже если команда найдена, нужный модуль сторонней коллекции может отсутствовать.

На Linux-controller нужен совместимый Python и его библиотеки. На обычном Linux-target нужен SSH-сервер, POSIX-оболочка и поддерживаемый Python для Python-модулей; сам пакет Ansible туда не ставится. Конкретный модуль может потребовать дополнительные Python-библиотеки на той стороне, где он исполняется. Например, библиотека API для действия к внешнему API на управляющей машине нужна controller, а драйвер БД для удалённого модуля — тому Python на target, который запускает модуль. Установка через другой pip часто оставляет нужный интерпретатор без зависимости. Исключения вроде raw и сетевых плагинов не отменяют требования обычных модулей.

Выбор и происхождение

Официальная инструкция установки ведёт к PyPI и репозиторию ansible/ansible. В PyPI выбирают точный релиз и имя файла, сверяют Python и хеш SHA-256 — 256-битную контрольную сумму содержимого. Для ansible_core-2.21.5-py3-none-any.whl на дату сверки опубликован SHA-256 08886f9f3e23d129aa98a01271c4a47833516e1cb7c737a246788cb474f41222. Wheel — готовый Python-пакет; это не исполняемый образ ОС. PyPI отмечает отсутствие provenance-аттестаций у этих файлов. Поэтому нельзя обещать проверенную подпись, которой поставка не содержит. HTTPS, официальная ссылка, отдельно сохранённая доверенная сумма и контроль источника уменьшают разные риски; сумма с того же подменённого зеркала происхождение не доказывает.

Установка в личной Linux-VM

Python — интерпретатор, который исполняет код Ansible. До следующих строк в своей Ubuntu 24.04 проверьте python3.12 --version; если программы нет, получите пакеты python3.12 и python3.12-venv штатным APT из доверенного репозитория своей VM. Пакеты и их зависимости готовят до офлайна. Готовый wheel Ansible не содержит интерпретатор и пакеты ОС. Каталог ansible-lab-tools ниже создаётся один раз; при возвращении используйте уже подготовленное окружение и сначала сверьте его версию. Это сохраняет прежний набор зависимостей.

python3.12 --version
python3.12 -m venv "$HOME/ansible-lab-tools"
"$HOME/ansible-lab-tools/bin/python" -m pip install 'ansible-core==2.21.5'
"$HOME/ansible-lab-tools/bin/ansible" --version
"$HOME/ansible-lab-tools/bin/ansible-doc" ansible.builtin.copy

Это рецепт для личной VM, а не предложение менять системный Python рабочего компьютера. -m venv создаёт изолированное окружение; -m pip выбирает pip этого Python; == запрещает незаметную замену core. У некоторых дистрибутивов venv поставляется отдельным пакетом ОС: его устанавливают в VM штатным менеджером после проверки репозитория. Нужные команды затем вызывают полным путём либо добавляют bin окружения в PATH текущей оболочки. Путь в выводе доказывает, какой executable и Python используются; там же видны config file, пути модулей и коллекций.

Одна фиксация core не фиксирует транзитивные зависимости. После разрешения в испытанном окружении сохраняют версии всех Python-пакетов, исходные ссылки, хеши и платформу. Замораживание pip freeze фиксирует версии, но само по себе не добавляет хеши и не проверяет источник. Не сохраняют в публичный lock приватный URL с токеном. Приёмка включает импорт CLI, чтение документации модуля и настоящий local-вызов ping: это Python/Ansible-проверка, не ICMP-пакет (Internet Control Message Protocol, протокол служебных сообщений IP-сети).

ansible localhost -i 'localhost,' -c local -m ansible.builtin.ping \
  -e ansible_python_interpreter="$HOME/ansible-lab-tools/bin/python"
ansible-galaxy collection list
ansible-config dump --only-changed

-e передаёт дополнительную переменную запуска: здесь ansible_python_interpreter выбирает Python, которым локальный модуль будет исполнен. Путь относится к этой же машине и должен существовать. Подробные правила переменных появятся после первого наблюдаемого вызова. Запятая делает строку inventory-списком, -c local выбирает локальное соединение, -m задаёт модуль. В этом вызове -i 'localhost,' создаёт explicit localhost — обычную явно объявленную inventory-запись, поэтому Python задаётся явно. Implicit localhost появляется при обращении к localhost, отсутствующему в inventory: движок сам даёт ему local connection и Python управляющего процесса. Явная запись снимает эти implicit defaults; одно имя localhost не гарантирует выбор нужного интерпретатора. Ответ pong подтверждает выполнение модуля; он не доказывает SSH и sudo. Ошибки ImportError, unsupported Python и отсутствующей коллекции требуют разных исправлений.

Процессы, каталоги, порты и офлайн

Обычный CLI живёт во время запуска; постоянный Ansible daemon ему не нужен. Controller создаёт рабочие процессы, локальные временные файлы и SSH ControlPath-сокеты. Target обычно принимает SSH на настроенном порту, часто 22, и размещает временный модуль в пользовательском временном каталоге; служба «Счётчик» слушает свой 8080 только там, где мы это явно настроили. Каталоги проекта, venv, collections, SSH-ключи, временные файлы и fact cache имеют разных владельцев и режимы доступа. Ограничение прав каталога коллекций существенно: plugin — исполняемый код controller.

Офлайн-комплект собирают заранее на совместимой платформе: python -m pip download --only-binary=:all: --dest wheelhouse -r requirements.lock, затем создают проверенный хеш-манифест всех wheels. Для установки используют --no-index --find-links wheelhouse --require-hashes и lock с точными версиями и хешами всех зависимостей. Если binary wheel для платформы отсутствует, сборку зависимостей рассматривают отдельно; wheel Linux x86-64 не универсален. В комплект включён hash-lock проверенных Python-зависимостей для CPython 3.12/Linux x86_64. Он не универсален для macOS/ARM/другой версии Python; для них комплект разрешают и проверяют заново. Установка этого набора из локального wheelhouse с --no-index --require-hashes реально проверена, физическое отключение сети не моделировалось. Коллекции получают ansible-galaxy collection download -r collections.yml -p collection-cache; сохраняют tarballs, dependency requirements, подписи если доступны и проверенные суммы. Сам tarball не содержит произвольные Python-зависимости и пакеты ОС. Копируют также документацию, роль, Go-бинарник с манифестом, пакеты целевой ОС и правила SSH trust. Приёмку комплекта проводят в отдельной VM с отключённым внешним доступом; успешная загрузка на онлайн-controller ещё не является офлайн-тестом.
