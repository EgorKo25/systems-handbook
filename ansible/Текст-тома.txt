Сначала проследить одну задачу

На управляющей машине лежит шаблон, на двух личных Linux-машинах работает Go-сервис «Счётчик». Мы хотим изменить адрес прослушивания и сохранить накопленные данные. Строка state: present не перемещает байты сама. Ansible читает перечень машин, выбирает участников, вычисляет аргументы задачи, находит реализацию действия, соединяется с ОС, запускает код с определёнными правами и получает структурированный ответ. Затем решает, считать ли действие изменением и требуется ли отложенный перезапуск. Между новым файлом и полезным ответом сервиса остаются загрузка конфигурации, запуск процесса и прикладная проверка.

Controller, или управляющий узел, — машина с процессом ansible-playbook. Target, или управляемый узел, — машина, над состоянием которой выполняется действие. Inventory — именованный состав узлов и групп с параметрами доступа. Playbook — YAML-документ с упорядоченными plays; play связывает выборку узлов с задачами. Task, задача, — вызов действия с аргументами и правилами исполнения. Module, модуль, — код ограниченной операции: проверить файл, установить пакет или вызвать API. Plugin, подключаемый компонент, расширяет движок: например, соединение SSH или выбор стратегии. Эти границы объясняют, почему ошибка шаблона возникает на controller, а запрет записи в каталог — на target.

Два уровня практики и одно состояние

В комплекте labs есть локальная файловая лаборатория: два inventory-имени обозначают один процессный хост, но пишут в разные подкаталоги выбранного временного корня. Она действительно проверяет сравнение состояния, handlers, check/diff, ошибки и собственный модуль. Она не проверяет SSH, sudo, сетевую изоляцию, systemd или доступность двух независимых ОС. Для этих свойств есть отдельный рецепт двух личных VM — виртуальных машин. Упражнения продолжают тот же стенд, а не стирают данные перед каждым запуском. Снимок, откат и удаление обозначены отдельными действиями.

Тестовый образец, fixture, — контролируемый набор данных и ожидаемых результатов; он не изображает неподнятый сетевой стенд. Среда исполнения, runtime, — интерпретатор/бинарник с зависимостями. Нарисованные состояния и условные числа также имеют собственные границы. Реально исполненные проверки перечислены в журнале проверок. На страницах нет скрытого исполнения команд: браузерная схема показывает фиксированный сценарий. Факт changed=0 означает лишь отсутствие изменения по контракту вызванных задач. Доступность приложения, сохранение данных и доверие к его бинарнику доказываются отдельными наблюдениями.

Что именно скачивается

ansible-core содержит движок, CLI — command-line interface, командный интерфейс — и встроенные модули/плагины. Пакет ansible добавляет отобранные community-коллекции, но не превращается в сервер с обязательной БД. Collection, коллекция, — именованная поставка модулей, плагинов и ролей вида namespace.name. Номер полного пакета, core и коллекции нельзя сравнивать как версии одной программы. Даже если команда найдена, нужный модуль сторонней коллекции может отсутствовать.

На Linux-controller нужен совместимый Python и его библиотеки. На обычном Linux-target нужен SSH-сервер, POSIX-оболочка и поддерживаемый Python для Python-модулей; сам пакет Ansible туда не ставится. Конкретный модуль может потребовать дополнительные Python-библиотеки на той стороне, где он исполняется. Например, библиотека API для действия к внешнему API на управляющей машине нужна controller, а драйвер БД для удалённого модуля — тому Python на target, который запускает модуль. Установка через другой pip часто оставляет нужный интерпретатор без зависимости. Исключения вроде raw и сетевых плагинов не отменяют требования обычных модулей.

Выбор и происхождение

Официальная инструкция установки ведёт к PyPI и репозиторию ansible/ansible. В PyPI выбирают точный релиз и имя файла, сверяют Python и хеш SHA-256 — 256-битную контрольную сумму содержимого. Для ansible_core-2.21.5-py3-none-any.whl на дату сверки опубликован SHA-256 08886f9f3e23d129aa98a01271c4a47833516e1cb7c737a246788cb474f41222. Wheel — готовый Python-пакет; это не исполняемый образ ОС. PyPI отмечает отсутствие provenance-аттестаций у этих файлов. Поэтому нельзя обещать проверенную подпись, которой поставка не содержит. HTTPS, официальная ссылка, отдельно сохранённая доверенная сумма и контроль источника уменьшают разные риски; сумма с того же подменённого зеркала происхождение не доказывает.

Установка в личной Linux-VM

Python — интерпретатор, который исполняет код Ansible. До следующих строк в своей Ubuntu 24.04 проверьте python3.12 --version; если программы нет, получите пакеты python3.12 и python3.12-venv штатным APT из доверенного репозитория своей VM. Пакеты и их зависимости готовят до офлайна. Готовый wheel Ansible не содержит интерпретатор и пакеты ОС. Каталог ansible-lab-tools ниже создаётся один раз; при возвращении используйте уже подготовленное окружение и сначала сверьте его версию. Это сохраняет прежний набор зависимостей.

python3.12 --version
python3.12 -m venv "$HOME/ansible-lab-tools"
"$HOME/ansible-lab-tools/bin/python" -m pip install 'ansible-core==2.21.5'
"$HOME/ansible-lab-tools/bin/ansible" --version
"$HOME/ansible-lab-tools/bin/ansible-doc" ansible.builtin.copy

Это рецепт для личной VM, а не предложение менять системный Python рабочего компьютера. -m venv создаёт изолированное окружение; -m pip выбирает pip этого Python; == запрещает незаметную замену core. У некоторых дистрибутивов venv поставляется отдельным пакетом ОС: его устанавливают в VM штатным менеджером после проверки репозитория. Нужные команды затем вызывают полным путём либо добавляют bin окружения в PATH текущей оболочки. Путь в выводе ansible --version доказывает, какой executable и Python используются; там же видны config file, пути модулей и коллекций.

Одна фиксация core не фиксирует транзитивные зависимости. После разрешения в испытанном окружении сохраняют версии всех Python-пакетов, исходные ссылки, хеши и платформу. Замораживание pip freeze фиксирует версии, но само по себе не добавляет хеши и не проверяет источник. Не сохраняют в публичный lock приватный URL с токеном. Приёмка включает импорт CLI, чтение документации модуля и настоящий local-вызов ping: это Python/Ansible-проверка, не ICMP-пакет (Internet Control Message Protocol, протокол служебных сообщений IP-сети).

ansible localhost -i 'localhost,' -c local -m ansible.builtin.ping \
  -e ansible_python_interpreter="$HOME/ansible-lab-tools/bin/python"
ansible-galaxy collection list
ansible-config dump --only-changed

-e передаёт дополнительную переменную запуска: здесь ansible_python_interpreter выбирает Python, которым локальный модуль будет исполнен. Путь относится к этой же машине и должен существовать. Подробные правила переменных появятся после первого наблюдаемого вызова. Запятая делает строку inventory-списком, -c local выбирает локальное соединение, -m задаёт модуль. В этом вызове -i 'localhost,' создаёт explicit localhost — обычную явно объявленную inventory-запись, поэтому Python задаётся явно. Implicit localhost появляется при обращении к localhost, отсутствующему в inventory: движок сам даёт ему local connection и Python управляющего процесса. Явная запись снимает эти implicit defaults; одно имя localhost не гарантирует выбор нужного интерпретатора. Ответ pong подтверждает выполнение модуля; он не доказывает SSH и sudo. Ошибки ImportError, unsupported Python и отсутствующей коллекции требуют разных исправлений.

Процессы, каталоги, порты и офлайн

Обычный CLI живёт во время запуска; постоянный Ansible daemon ему не нужен. Controller создаёт рабочие процессы, локальные временные файлы и SSH ControlPath-сокеты. Target обычно принимает SSH на настроенном порту, часто 22, и размещает временный модуль в пользовательском временном каталоге; служба «Счётчик» слушает свой 8080 только там, где мы это явно настроили. Каталоги проекта, venv, collections, SSH-ключи, временные файлы и fact cache имеют разных владельцев и режимы доступа. Ограничение прав каталога коллекций существенно: plugin — исполняемый код controller.

Офлайн-комплект собирают заранее на совместимой платформе: python -m pip download --only-binary=:all: --dest wheelhouse -r requirements.lock, затем создают проверенный хеш-манифест всех wheels. Для установки используют --no-index --find-links wheelhouse --require-hashes и lock с точными версиями и хешами всех зависимостей. Если binary wheel для платформы отсутствует, сборку зависимостей рассматривают отдельно; wheel Linux x86-64 не универсален. В комплект включён hash-lock проверенных Python-зависимостей для CPython 3.12/Linux x86_64. Он не универсален для macOS/ARM/другой версии Python; для них комплект разрешают и проверяют заново. Установка этого набора из локального wheelhouse с --no-index --require-hashes реально проверена, физическое отключение сети не моделировалось. Коллекции получают ansible-galaxy collection download -r collections.yml -p collection-cache; сохраняют tarballs, dependency requirements, подписи если доступны и проверенные суммы. Сам tarball не содержит произвольные Python-зависимости и пакеты ОС. Копируют также документацию, роль, Go-бинарник с манифестом, пакеты целевой ОС и правила SSH trust. Приёмку комплекта проводят в отдельной VM с отключённым внешним доступом; успешная загрузка на онлайн-controller ещё не является офлайн-тестом.

Как находится конфигурация

ansible.cfg — INI-файл поведения движка. Порядок поиска: переменная окружения ANSIBLE_CONFIG, затем файл в текущем каталоге, затем ~/.ansible.cfg, затем /etc/ansible/ansible.cfg. Используется первый найденный, файлы не сливаются. Автоматическое чтение из world-writable текущего каталога отключено: соседний пользователь мог бы подложить plugin или команду. Явный ANSIBLE_CONFIG — осознанный выбор доверенного файла, а не средство сделать чужой каталог безопасным.

ansible --version
ansible-config dump --only-changed
ansible-config view

dump показывает эффективные настройки и происхождение, view — содержимое выбранного файла, а --version — его путь. Если после перехода в каталог изменилось поведение, сначала сравнивают эти свидетельства. Настройка окружения перекрывает cfg, обычные CLI-опции перекрывают настройки; playbook keywords и затем variables могут перекрыть CLI. Например, -u deploy уступит inventory-переменной ansible_user: operator. Параметр -e ansible_user=deploy — extra variable с гораздо более высоким приоритетом. Полная модель разобрана в книге переменных.

Статический состав сохраняемого стенда

Сначала подготовьте файлы проекта. Скопируйте весь ansible/labs/vm из своей локальной копии книги в личный каталог работы; это исходники настройки, а не созданные VM. Рабочим каталогом следующих inventory-команд будет эта копия vm. В ней уже есть ansible.cfg, site.yml и роль roles/gosvc. Скопируйте inventory/hosts.example.yml в inventory/hosts.yml один раз и замените адреса своими после подготовки VM. Не подменяйте этот файл при следующем занятии. До готовности SSH и артефакта ограничимся просмотром состава.

Inventory ниже записан в YAML. Пока достаточно трёх правил чтения: имя: значение задаёт поле; отступ вкладывает его в родительский объект; поля children, hosts, vars обозначают вложенные группы, узлы и переменные. Здесь ansible_user — учётная запись входа на управляемой ОС, ansible_python_interpreter — абсолютный путь её Python. Это имена параметров Ansible, не команды оболочки. Подробный язык данных и типы разберёт глава YAML; первичную структуру можно проверить уже сейчас без исполнения задач.

all:
  children:
    lab:
      children:
        counters:
          hosts:
            counter_a:
              ansible_host: 192.0.2.11
            counter_b:
              ansible_host: 192.0.2.12
      vars:
        ansible_user: deploy
        ansible_python_interpreter: /usr/bin/python3

Адреса 192.0.2.0/24 — диапазон примеров документации; в VM-рецепте их заменяют адресами своих машин. counter_a — устойчивое inventory-имя, ansible_host — адрес соединения. Изменение адреса не обязано менять логическое имя. Два имени с одним IP не создают две независимые машины: они способны одновременно менять один файл. Группа counters входит в lab; узел может состоять в нескольких группах, а их переменные сводятся для узла. all содержит всех, ungrouped — узлы без других групп. Имена окружений лучше разнести по inventory-каталогам с отдельными group_vars и явным -i.

ansible-inventory -i inventory/hosts.yml --graph
ansible-inventory -i inventory/hosts.yml --host counter_a
ansible-playbook -i inventory/hosts.yml site.yml --list-hosts
ansible-playbook -i inventory/hosts.yml site.yml --limit counter_a --list-hosts

Граф не выполняет задач; --host показывает сведённые inventory-переменные, которые могут содержать секреты. --list-hosts учитывает plays и limit, но не является пробным выполнением. --limit сужает множество, выбранное hosts, а не расширяет его. До изменения сравнивают запуск без limit с ограниченным: ожидаемые два имени против одного. Pattern 'lab:&counters:!maintenance' означает пересечение и исключение; кавычки защищают специальные символы от оболочки. Пустая выборка не доказывает исправность роли: возможно, она вообще не исполнялась.

Одно имя, три разных ответа

Для counter_a сначала решается, попал ли он в выборку: группа counters содержит A и B, а --limit counter_a оставляет A. Затем inventory даёт адрес ansible_host и пользователя ansible_user. Наконец, при исполнении конкретной задачи движок добавляет play/task/extra variables. Поэтому ansible-inventory --host counter_a полезен для первого слоя данных, но не обязан показать будущий task override. Например, inventory задаёт порт приложения 8082, play — 8083, а одна задача — 8084: просмотр inventory остаётся 8082, хотя аргумент той задачи равен 8084. Порт приложения здесь не меняет SSH-порт.

Для чтения относительного пути также нужен владелец настройки. Значение inventory = ./inventory/hosts.yml из выбранного ansible.cfg разрешается относительно этого cfg; аргумент CLI -i inventory/hosts.yml относится к текущему рабочему каталогу. Они совпадают в своей VM-копии проекта и способны разойтись после cd. Сохраните вместе абсолютный путь cfg, рабочий каталог и команду. Если A исчез из вывода, сначала исправьте источник/выборку, затем снова проверьте одно ожидаемое имя; не принимайте пустой recap за успешную настройку.

Переменные и несколько источников

group_vars/all.yml, group_vars/counters.yml и host_vars/counter_a.yml отделяют параметры от состава. Host vars конкретнее group vars; дочерняя группа перекрывает родительскую. Для групп одинакового уровня действуют правила слияния и порядок, включая ansible_group_priority, задаваемый в inventory-источнике. Не строят критический интерфейс на случайном алфавите групп: конфликт устраняют в явном месте. При нескольких -i важен порядок источников. Проверяют конечные значения и сохраняют команду вызова, не только последний YAML.

По умолчанию словари с одинаковым именем заменяются, а не глубоко объединяются. Параметры service_defaults и service_override безопаснее объединить явно фильтром combine с задокументированной глубиной и правилами списков, чем глобально менять hash_behaviour. Для воспроизводимости читатель должен увидеть, какие ключи реально получились.

Динамический состав и граница доверия

Dynamic inventory строится plugin из API (программного интерфейса внешней системы) или другого источника в момент загрузки. Это не автоматическое обнаружение всего интернета. Его конфигурация выбирает учётные данные, фильтры, имена, группы и кэш. Legacy inventory-script выводит JSON по протоколу --list/--host; современные плагины могут собирать hostvars эффективнее. Успешный ответ API не доказывает правильность фильтра окружения. Перед изменением сохраняют обезличенный состав, проверяют стабильность имён и причины исчезновения узла. Кэш состава и fact cache решают разные задачи; устаревший inventory может отправить задачу прежнему владельцу адреса.

Полученные inventory-данные влияют на connection, become и пути. Поэтому чужой файл inventory — активный вход автоматизации, а не безобидная адресная книга. Прогон inventory и шаблонов возможен без SSH, но lookup/plugin способен делать сеть уже на controller. Для локальных проверок тома inventory фиксирован, plugins сторонних источников не используются. Сверка правил: configuration и inventory guide, 01.11.2026; CLI-опции уточняют в документации установленного core 2.21.5.

От имени узла до канала

На этом шаге каждая target-VM уже должна существовать. В её доверенной консоли подготовьте поддерживаемые Python, OpenSSH server и sudo штатными пакетами ОС, создайте выбранного пользователя deploy и установите его проверенный публичный ключ. Например, в своей Ubuntu VM пакеты получают командой sudo apt install openssh-server python3 sudo после обновления списка пакетов; имена/версии сверяют для выбранной ОС. Служба SSH должна быть запущена и слушать доступный в личной сети адрес. Проверка systemctl status ssh относится к Ubuntu; другое семейство может называть службу sshd. До Ansible проверьте вход обычным SSH и необходимые полномочия sudo. Закрытый ключ остаётся на controller. В этой книге нет команды, создающей VM или автоматически превращающей произвольную машину в доверенную цель.

SSH, Secure Shell, устанавливает защищённый канал к серверу. Controller получает адрес из inventory, выбирает connection plugin и запускает SSH-клиент. Клиент проверяет ключ сервера, затем доказывает право входа пользователем, например подписью закрытым ключом. Только после этого удалённая оболочка сможет запустить Python. Публичный ключ пользователя в authorized_keys даёт допуск к учётной записи; запись ключа сервера в known_hosts подтверждает, с какой машиной установлен канал. Это противоположные стороны доверия. Пароль закрытого ключа защищает файл; пароль sudo относится к повышению прав; они не взаимозаменяемы.

ssh -o BatchMode=yes deploy@192.0.2.11 'id; python3 --version'
ansible counter_a -i inventory/hosts.yml -m ansible.builtin.ping -vvv
ansible counter_a -i inventory/hosts.yml -m ansible.builtin.command -a 'id' --become

Первый запуск — рецепт только своей VM; BatchMode=yes запрещает неожиданное интерактивное ожидание пароля. id показывает UID/GID — числовые идентификаторы пользователя/группы процесса, а Python — доступный executable. -vvv добавляет сведения о соединении, выбранных путях и командах; вывод перед передачей очищают от адресов, имён и секретных аргументов. ping исполняет модуль, а не ICMP echo. Если обычный SSH работает, но ping не работает, проверяют выбранный Python, shell, temporary directory, передачу файла и зависимости. Не надо сначала выключать host key checking.

Первое доверие и смена ключа

Fingerprint, отпечаток ключа, получают через доверенную консоль своей VM либо заранее подписанный реестр. ssh-keyscan лишь снимает предъявленный по сети ключ, поэтому сам по себе не доказывает подлинность. После сверки ключ сохраняют в отдельный known_hosts учебного окружения. При несовпадении устанавливают причину: пересоздание своей VM, смена адреса либо атака. Массовое удаление known_hosts превращает обнаруженную проблему в молчаливое новое доверие. Закрытые ключи хранят с правами только владельца, не помещают в Git, используют ssh-agent с понятным временем жизни. Agent forwarding открывает цели возможность использовать агент; он не нужен для обычного подключения controller к target.

Отдельный файл доверия используется только если клиенту указан его путь. После ручной сверки ключей сохраните частный known_hosts своей VM-копии и задайте в её ansible.cfg под [ssh_connection] параметр ssh_common_args = -o UserKnownHostsFile=/АБСОЛЮТНЫЙ/ПУТЬ/К/known_hosts -o StrictHostKeyChecking=yes. Подставьте существующий путь без пробелов и проверьте его владельца; общую ~/.ssh/config менять не требуется. Для ручного SSH используйте те же два -o. Само создание файла рядом с inventory не выбирает его автоматически. Другая запись параметра в inventory или extra vars способна перекрыть cfg: при диагностике проверьте фактическую SSH-команду в защищённом выводе -vvv.

Выбор Python и начальная подготовка

Interpreter discovery — поиск подходящего Python при первом Python-модуле. ansible_python_interpreter: /usr/bin/python3 фиксирует путь и отключает угадывание для этого узла. Путь может существовать, но указывать на неподдерживаемую версию или окружение без нужной библиотеки. Controller Python и target Python независимы. В local play удобно привязать target к ansible_playbook_python, то есть Python управляющего процесса. Ошибка discovery не должна исправляться symlink системного Python без понимания пакетов ОС.

raw способен выполнить минимальную команду через соединение без Python-модуля; это помогает подготовить Python в новой личной VM. Но он не даёт универсальной идемпотентности, переносимости или автоматической проверки менеджера пакетов. В этом томе Python готовят при создании VM и отдельно принимают до роли. Для начальной подготовки фиксируют семейство/версию ОС, репозитории и допустимые права, затем возвращаются к обычным модулям.

Become — смена контекста, а не второй SSH

become: true разрешает механизм повышения/смены пользователя; become_user выбирает целевую учётную запись, но сам по себе не включает become. Метод по умолчанию часто sudo; точное значение видно в config/plugin docs. -b включает become, -K запрашивает его пароль. -k запрашивает пароль соединения и решает другую задачу. Проверяют две одинаковые команды id без -b и с ним: ожидается разный effective UID — действующий числовой идентификатор пользователя, а не новый TCP-сервер.

Для записи в /etc, управления systemd и создания системного пользователя нужны соответствующие полномочия. Для чтения HTTP-адреса проверки готовности root не нужен. HTTP (Hypertext Transfer Protocol) — протокол запросов и ответов приложения. Применять become ко всему play удобно, но расширяет поверхность последствий и меняет окружение, HOME, доступ к файлам и временному модулю. При переходе между двумя непривилегированными пользователями временный модуль должен стать читаемым получателю: Ansible использует доступные механизмы прав/ACL. Разрешать world-readable temporary files ради обхода ошибки опасно, особенно с секретными аргументами. Исправляют владельца, группу и возможности ОС.

Входы управляющего процесса

Для чтения раннего примера достаточно двух понятий языка. YAML хранит данные задачи с полями и отступами. Jinja — обработчик текстовых шаблонов: например, {{ counter_port }} заменяется значением переменной counter_port. Он работает на controller, поэтому недоступное имя может остановить задачу до SSH. template готовит файл из такого шаблона; параметры src и dest выбирают исходный шаблон и конечный файл. Следующий листинг — одна задача внутри роли; полный play и подготовка её файлов находятся в VM-комплекте. После устройства исполнения разберём YAML/Jinja подробно.

ansible-playbook читает конфигурацию, inventory, playbook, роли и коллекции. После выбора hosts и --limit у play получается множество участников. Strategy plugin определяет, какой готовый task/host сейчас передать исполнителю. Для каждого узла контекст содержит переменные соединения и задачи. Шаблоны аргументов и условия обычно вычисляются на controller, поэтому Jinja-ошибка возникает до запуска удалённого Python. Lookup plugin, например lookup('file', 'settings.txt'), читает файл на controller; он отличается от Jinja filter, преобразующего уже полученное значение. Для чтения файла target используют действие вроде ansible.builtin.slurp и разбирают его результат. Удалённый hosts не переносит lookup на target.

- name: Publish counter settings
  ansible.builtin.template:
    src: config.json.j2
    dest: /etc/counter/config.json
    owner: root
    group: counter
    mode: '0640'
    validate: '/opt/counter/current/counter --check-config %s'
  notify: Restart counter

Action plugin — управляющая часть действия. У template она рендерит Jinja на controller, а затем организует сравнение и доставку. Connection plugin предоставляет канал; shell plugin учитывает соглашения оболочки; become plugin меняет привилегии. Для обычного Python-модуля core собирает пакет исполняемого кода и данных (payload) с нужными module_utils и аргументами. Он может доставляться через временный файл или, при поддерживаемом pipelining, через стандартный ввод интерпретатора. Нельзя считать, что каждая задача делает новый TCP-handshake либо всегда оставляет на диске одинаковый скрипт: это зависит от transport и действия.

Шаблон, кандидат и модуль — разные файлы

В примере src: config.json.j2 принадлежит роли на controller. После подстановки, например counter_listen = '127.0.0.1:8080', Jinja выдаёт конкретный JSON; на target не требуется Jinja и не передаётся весь playbook для исполнения. Временная обёртка Python содержит код модуля и аргументы запуска. Временный кандидат конфигурации содержит уже другие байты — содержимое будущего /etc/counter/config.json. В раннем листинге его читает бинарник по /opt/counter/current/counter; на первой установке этот путь ещё отсутствует. В полном VM-рецепте validate вызывает уже подготовленный releases/{{ counter_release }}/counter до переключения current. Ошибка «неизвестное поле JSON» относится к кандидату, ошибка «Python not found» — к исполнению обёртки, а undefined counter_listen возникает ещё на controller.

Если validator отказал, конечный config должен остаться прежним и уведомление о его успешной замене не возникает. Если замена прошла, но SSH-ответ потерян, конечный файл уже может быть новым: отсутствие ответа не означает отсутствие записи. При повторе модуль снова сравнит состояние; для работающего процесса затем всё равно нужна отдельная проверка. Подробный предметный разрез двух временных файлов приведён в главе о собственном модуле; там явно выбран режим без pipelining.

Что выполняется на target

Удалённая оболочка/интерпретатор запускает код с effective UID выбранного контекста. Модуль проверяет текущее состояние, вычисляет нужное действие, проверяет аргументы и пытается изменить ресурс. Для шаблона конечные байты — обычный файл, не Jinja на target. validate проверяет временный кандидат до замены назначения; %s заменяется путём кандидата, строка не исполняется как произвольный shell pipeline. Важна возможность кандидата работать с абсолютными путями и заданным пользователем. Ошибка валидации должна оставить прежний конечный файл, но не является полной транзакцией над другими задачами.

Модуль возвращает JSON — JavaScript Object Notation, структурированный текст — с полями результата: например, changed, сведения о файле, failed или msg. Командные модули также возвращают rc, stdout и stderr. Случайный debug print в stdout своего модуля способен испортить протокол. Connection/action может преобразовать ответ и добавить метаданные. Затем controller применяет changed_when/failed_when, сохраняет register, уведомляет handler при итоговом changed и отдаёт событие callback-плагинам — обработчикам событий исполнения. Обработчик отвечает за вывод; цвет терминала не является исходным состоянием ОС.

Изменение, отказ и итог

ok означает успешное выполнение по контракту задачи; changed — утверждение задачи о различии/действии. skipped — условие или режим исключил исполнение; unreachable — не удалось обычным образом обратиться к узлу; failed — задача признана неуспешной. rescued и ignored показывают обработанные ошибки, а не отсутствие инцидентов. Recap суммирует события, а не выполняет независимый аудит файлов и процессов. Успешная команда с неверным бизнес-эффектом даст успешный recap, если мы не написали проверку.

Handler — задача, отложенно вызываемая по уведомлению об изменении. Если файл изменился и процесс ещё работает со старым config, промежуточное состояние необходимо увидеть. Уведомление ещё не перезапуск. При обычном завершении нужного участка play handlers выполняются; при отказе поведение зависит от места и политики. Затем независимая HTTP-проверка (HTTP, Hypertext Transfer Protocol, — протокол запросов и ответов) подтверждает версию и готовность. Действует: Модуль и ОС.

Входы: 0.2; Controller: ждёт; Канал: активен; Python target: замена прошла; Файл: 0.2; Результат: ещё в пути

Файл: 0.1 → 0.2. Реальная запись отличается от check-прогноза.

5. Ответ принят

JSON сообщает changed=true. Action и changed_when формируют окончательный результат.

Действует: Модуль → controller.

Входы: 0.2; Controller: результат принят; Канал: ответ получен; Python target: закончен; Файл: 0.2; Результат: changed=true

Свидетельство: ответа нет → changed=true. Потеря ответа могла бы оставить новый файл при неизвестном результате.

6. Handler только ожидает

Notify поставил перезапуск в очередь host. Процесс пока может читать прежний config из памяти.

Действует: Controller.

Входы: 0.2; Controller: restart ожидает; Канал: свободен; Python target: закончен; Файл: 0.2; Результат: notify принят

Процесс: версия config 0.1 → всё ещё может быть 0.1. Изменение файла не перезапуск.

7. После flush проверяется приложение

Handler применил изменение; отдельный HTTP-запрос должен подтвердить ожидаемую версию и данные.

Действует: Handler и проверочная task.

Входы: 0.2; Controller: проверяет; Канал: новый запрос; Python target: restart завершён; Файл: 0.2; Результат: version/count наблюдены

Приёмка: только changed → проверена версия/данные. Recap суммирует события, но не заменяет прикладной проверки.

Что делает декларацию идемпотентной

Идемпотентность — повторное приведение к тому же желаемому состоянию не создаёт нового изменения при неизменных входах и окружении. Для copy нужны стабильные байты, права и владелец; шаблон с текущим временем каждый раз меняется. Для package: state=present нужна корректная модель пакета, но политика latest зависит от меняющегося репозитория. Для command: echo ... такой модели нет; changed_when: false меняет отчёт, а не делает операцию безопасной. creates предотвращает запуск при наличии файла, но не доказывает целостность и соответствие версии этого файла. Настоящий контракт проверяет текущее состояние и отличает нужное изменение от уже выполненного.

Идемпотентность также не равна транзакции, отсутствию гонок и исправности сервиса. Два controller могут одновременно прочесть старый файл и принять разные решения. Здесь один владелец изменения, последовательный выпуск и явные прикладные проверки. Общий механизм сверён с архитектурой модулей; детали TaskExecutor привязаны к исходнику v2.21.5, 01.11.2026.

Три слоя чтения

YAML — язык записи данных. Parser превращает текст в scalars, sequences и mappings: отдельные значения, упорядоченные списки и отображения ключ→значение. Ansible затем интерпретирует структуру как plays/tasks, а Jinja вычисляет выражения внутри допустимых значений. Ни YAML, ни строка с state: started сами не запускают службу. При ошибке полезно установить слой: недопустимый отступ, неизвестный keyword задачи или неправильный аргумент уже найденного модуля.

---
- name: Prepare persistent counters
  hosts: counters
  gather_facts: false
  vars:
    counter_port: 8080
    counter_enabled: true
    counter_features:
      - health
      - persistence
    counter_limits:
      queue: 32
  tasks:
    - name: Check typed inputs
      ansible.builtin.assert:
        that:
          - counter_port is integer
          - counter_enabled is boolean
          - counter_features is sequence and counter_features is not string and counter_features is not mapping
          - counter_limits is mapping

Верхний - создаёт список plays, следующий уровень — mapping одного play. tasks содержит список задач, а that — список Jinja-условий. Табуляцию для отступов не используют. Отступом можно непреднамеренно перенести vars с play на task: документ останется грамматичным, но область значений изменится. В одной задаче должен быть один вызов action; notify и when — keywords, а не параметры модуля.

Значение не равно его написанию

8080 — integer, '8080' — строка, true — boolean, null — явное пустое значение. Отсутствующий ключ отличается от ключа с null; default без второго аргумента реагирует на undefined, а не на любой пустой вид. Для переносимости пишут true/false, а не неоднозначные yes/on, избегают неявных дат и ведущих нулей. Режим файла задают строкой '0640': иначе YAML может передать integer, а модуль интерпретирует его как числовую маску с неожиданным основанием. Передача через -e enabled=false даёт строку в key=value-формате; файл YAML/JSON или JSON-строка сохраняет boolean.

Ключи mapping должны быть уникальны. Повтор vars или mode способен привести к предупреждению и потере первого значения; наличие warning следует считать дефектом входа. Порядок tasks значим. Порядок ключей параметров не является планом исполнения модуля. YAML anchor/alias сокращает повтор данных, но не создаёт role, вызов функции или зависимость задач. Merge-ключ YAML не заменяет осмысленное слияние переменных разных уровней Ansible.

Проверка is sequence сама по себе слишком широка для списка возможностей: строка также является последовательностью. Поэтому выше исключены string и mapping. У числа порта важен такой же порядок: сначала подтвердить integer, затем проверить 1 <= counter_port <= 65535, и лишь после этого передавать значение приложению. Строка 'eighty' не должна молча превращаться фильтром int в 0. Ошибка входа должна оставить прежний config, а исправление — заменить неверное значение в том же сохранённом файле переменных, не создать новый стенд.

Кавычки и блоки

vars:
  config_path: '{{ counter_root }}/config.json'
  windows_example: 'C:\data\counter'
  literal_help: |
    Первая строка.
    Вторая строка.
  folded_help: >-
    Этот длинный текст
    сворачивается в строку.

Значение, начинающееся с {{, заключают в кавычки, чтобы YAML не принял его за flow mapping. Одинарные кавычки удобны для буквального backslash; двойные включают YAML escape-последовательности. Внутренняя одинарная кавычка удваивается. | сохраняет переносы, > обычно сворачивает их в пробелы, - после индикатора убирает завершающий перевод строки. Для конфигурации сервиса лишний newline может быть безразличен, для checksum — это другой байт. Двоеточие с пробелом и # в plain scalar имеют синтаксический смысл, поэтому сообщения и URL с неоднозначными символами лучше явно цитировать.

- name: Validate candidate without shell expansion

Но command в современных core может разворачивать переменные окружения в аргументах; если требуется буквальный $NAME, проверяют параметр expand_argument_vars конкретной версии и отключают разворачивание. Shell нужен, когда действительно требуется pipeline/redirect; тогда надо учитывать уже три синтаксиса: YAML, Jinja и удалённую shell. Экранирование одного слоя не защищает остальные.

ansible-playbook --syntax-check проверяет доступную структуру и статические зависимости, но не каждое runtime-значение. В начале роли проверяют типы/диапазоны через assert или role argument_specs. Для поля порта разумно требовать integer, 1–65535 и выбранную политику bind; преобразование любой строки в integer не заменяет валидации входа. Выражение, оператор и результат

Jinja — шаблонизатор, который вычисляет выражения в контексте переменных. {{ expression }} вставляет результат, {% if ... %} управляет выводом шаблона, {# ... #} — комментарий. В when, failed_when и changed_when уже ожидается выражение: дополнительные {{ }} не нужны. В core 2.19+ проверки корректности и доверия шаблонов стали строже; случайно непустая строка больше не должна играть роль осмысленного boolean-условия. Для core 2.21.5 используем явные сравнения и типизированные входы.

vars:
  counter_defaults: {listen: '127.0.0.1:8080', feature: false}
  counter_override: {feature: true}
  counter_effective: '{{ counter_defaults | combine(counter_override) }}'
tasks:
  - name: Verify feature contract
    ansible.builtin.assert:
      that:
        - counter_effective['feature'] is boolean
  - name: Choose enabled path
    ansible.builtin.debug:
      msg: 'feature enabled'
    when: counter_effective['feature']

combine строит новый mapping; при одинаковом ключе правый mapping перекрывает левый. По умолчанию это не обещание рекурсивного merge произвольной структуры. Для вложенных словарей задают recursive=true, для списков — выбранный list_merge, затем отдельно проверяют результат. Большой универсальный merge затрудняет объяснение происхождения одного значения. Обращение obj['items'] избегает конфликта ключа items с методом mapping при точечной записи.

Undefined, null и намеренное отсутствие

Undefined означает, что имени/ключа нет в доступном контексте. Null — существующее пустое значение; false, 0, пустая строка и пустой список также разные допустимые данные. var | default('fallback') заменяет undefined. default('fallback', true) заменяет и false-like значения: это может испортить законный false для feature. Обязательное поле лучше проверить is defined, типом и ограничениями; молчаливый fallback для адреса production опасен. mandatory делает отсутствие явной ошибкой, но также не проверяет диапазон порта.

- name: Create directory with optional owner
  ansible.builtin.file:
    path: '{{ counter_root }}'
    state: directory
    owner: '{{ counter_owner | default(omit) }}'
    mode: '0750'

omit — специальное значение, указывающее не передавать параметр модулю, а не строка, которую надо записать в файл. После default(omit) цепочка других фильтров может сломать это намерение; для сложного преобразования лучше заранее выбрать ветку и проверить данные. Не путают отсутствие owner с явным требованием поставить owner в null. Строка '{{ another }}' в недоверенных полученных данных не должна превращаться в автоматически исполняемый второй шаблон.

Фильтры, tests и lookups

Filter преобразует значение: int, to_json, dict2items, selectattr, map. Test проверяет свойство: is mapping, is defined, is failed. Lookup обращается к внешнему источнику на controller; это может быть файл, environment или API, и результат имеет границы доверия/доступности. lookup('env', 'TOKEN') читает окружение controller, а не target. Шаблон может сделать сетевой lookup ещё до SSH; поэтому «только check» не значит «никаких внешних обращений».

Структурированные файлы надёжнее строить сериализатором, а не вручную расставлять JSON-кавычки:

{{ {'listen': counter_listen,
    'data_file': counter_data_file,
    'message': counter_message} | to_nice_json }}

Фильтр экранирует кавычки и переносы в строках. Итог всё равно валидируют самим приложением перед заменой файла. quote помогает shell-аргументу определённого формата, но не является HTML-, SQL- или JSON-экранированием. to_yaml меняет представление, а не автоматически проверяет контракт приложения. При вычислении коллекций полезно явно материализовать результат | list, когда следующий модуль ожидает список.

Один перевод строки проходит два языка

Пусть counter_message — строка из двух строк текста: Первая, LF, Вторая. В YAML-блоке |- внутренний LF сохраняется, а завершающий отсутствует. Фильтр to_nice_json записывает внутренний LF внутри JSON-строки двумя печатными знаками \n: байты 0x5c и 0x6e. Когда Go разбирает JSON, поле Message снова содержит LF 0x0a. Нельзя заменить эти два знака физическим LF внутри JSON-кавычек: это уже недопустимый JSON. Перевод строки после закрывающей фигурной скобки — отдельный разделитель документа.

В учебном модуле есть ещё один слой: чтение UTF-8-текста нормализует CRLF/CR в LF до сравнения строк. Поэтому одинаковый результат после разбора не доказывает одинаковые исходные байты. Если нужен именно побайтовый контракт, его надо реализовать чтением байтов и отдельно проверить; нынешний модуль обещает сравнение текста и прав. Так ошибка сериализации, нормализация чтения и семантика приложения остаются различимыми.

Стоимость шаблонизации и диагностика

Если для каждого из N узлов шаблон каждый раз просматривает hostvars всех N узлов, объём работы способен приблизиться к N². Большой JSON в -vvv увеличивает память и риск утечки. Измеряют controller CPU и время рендера на фиксированном наборе данных, затем выносят действительно общую нормализацию в отдельный этап. set_fact может зафиксировать вычисление, но меняет время и область значения: его нельзя добавлять как невидимую оптимизацию без проверки смысла.

При ошибке начинают с конкретного имени, его типа и источника; в несекретном тестовом образце выводят type_debug и маленький фрагмент структуры. Не печатают весь hostvars ради одного порта. Сверено 01.11.2026: templating, изменения 2.19; это также причина прогонять роли при обновлении, даже если YAML не менялся.

Приоритет не равен порядку чтения файла

Variable precedence — правила выбора значения при конфликте определений одного имени. Отдельно существует приоритет категорий поведения: config → обычные CLI-опции → keywords playbook → variables → прямое назначение параметров применимого plugin. Например, cfg remote_user=alice, CLI -u bob, play keyword remote_user: carol, inventory ansible_user: dana дадут соединение как dana. -e ansible_user=erin перекроет её extra variable. Флаг -u не означает «самый сильный источник».

Внутри variables полезная восходящая карта такова: role defaults; inventory group/host vars; facts и кэшируемые set_fact; play vars, vars_prompt и vars_files; role vars; block vars; task vars; include_vars; присвоенные во время исполнения set_fact/register; role/include params; extra vars. Это карта основных классов, а не замена полной таблицы: у inventory есть собственные уровни файлов/групп, у кэшируемого set_fact — две копии. При споре сверяются с таблицей конкретной версии и маленьким воспроизводимым play, а не добавляют новый override.

Конкретный конфликт в роли

 | Источник | Значение counter_port | Роль определения

 | roles/counter/defaults/main.yml | 8080 | Публичное значение по умолчанию

 | group_vars/counters.yml | 8081 | Параметр группы стенда

Поэтому настраиваемые значения помещают в defaults, а не пытаются лечить каждый узел extra vars. Область и момент вычисления

Play vars принадлежат play. Task vars принадлежат вызову задачи. Inventory variables, facts, register и set_fact связаны с конкретным host и доступны через hostvars в рамках нужного контекста; extra vars действуют на весь запуск. Это не общая изменяемая память controller: два host с одним именем переменной имеют свои значения. hostvars['counter_b']['service_version'] имеет смысл только если значение уже определено/получено. Порядок plays и стратегии влияет на доступность runtime-результатов.

Обычная переменная, содержащая Jinja-выражение, вычисляется при использовании в текущем доступном контексте; нельзя считать её снимком на момент чтения YAML. set_fact присваивает вычисленный результат в момент выполнения задачи. Если сначала set_fact: selected: '{{ release }}', затем источник release меняется, selected не обязан пересчитаться сам. Этот эффект полезен для сохранения прежнего пути перед выпуском, но опасен при скрытом кэшировании динамического адреса.

Данные отдельно от политики соединения

Имена ansible_connection, ansible_user, ansible_become и ansible_python_interpreter имеют специальный смысл. Их нельзя незаметно смешивать с пользовательским mapping сервиса. Prefix counter_ защищает интерфейс роли от случайного ключа port другого компонента. Магические переменные вроде inventory_hostname, groups и ansible_play_hosts_all описывают контекст; не пытаются записывать в них свои данные. inventory_hostname не равен автоматически DNS-имени ОС.

Не объединяют весь мир в vars: '{{ hostvars }}'. Для передачи роли достаточно маленького типизированного mapping, например release version, SHA-256, listen и data path. Диагностический след отвечает на четыре вопроса: кто определил, какой приоритет, для какого host, когда вычислено. Официальные правила на 01.11.2026: variable precedence и общие категории. Сбор facts

Facts — собранные сведения о target: ОС, интерфейсах, памяти и других поддерживаемых свойствах. По умолчанию play часто начинается с Gathering Facts, вызова setup. Это удалённая работа: Python, чтение ОС и передача JSON. ansible_facts['distribution'] описывает наблюдённую систему, но не означает автоматически совместимость любого пакета. Назначение интерфейса по «первому адресу» хрупко при нескольких сетях. В роли проверяют конкретные требования, а в inventory задают адрес нужного соединения.

- name: Observe only required operating system facts
  ansible.builtin.setup:
    gather_subset:
      - '!all'
      - '!min'
      - distribution
    filter:
      - ansible_distribution*

gather_subset выбирает группы реально собираемых данных. filter ограничивает возвращаемые keys и не гарантирует столь же сильного уменьшения стоимости самого сбора. Если facts не нужны, ставят gather_facts: false, а не скрывают строку вывода обработчика событий. Для сравнения замеряют тот же inventory без сборки, с обычной сборкой и с subset; отделяют холодный SSH от времени setup.

Register хранит ответ, а не текст терминала

- name: Inspect existing config
  ansible.builtin.stat:
    path: '{{ counter_root }}/config.json'
    checksum_algorithm: sha256
  register: counter_before

- name: Assert expected type
  ansible.builtin.assert:
    that:
      - not counter_before.stat.exists or counter_before.stat.isreg

register связывает полный результат задачи с host. У stat это mapping со stat, у command есть rc/stdout/stderr, у loop появляется results — список отдельных результатов. Поле stdout не универсально. Неуспешная или skipped задача тоже может оставить результат с соответствующим признаком; прежде доступа к полям учитывают ветку. Проверки result is failed, is skipped, is changed читают состояние результата, а не наличие произвольного ключа.

В loop успешная итерация не отменяет неуспешную соседнюю. Для именования используют loop_control.loop_var, чтобы вложенная роль не перетёрла item. Результат цикла исследуют по каждому item; общий changed станет true, если изменился хотя бы один элемент. Уведомление handler от loop также основано на общем changed, поэтому перезапуск может быть нужен хотя бы из-за одного файла.

Переменная есть, а измерения нет

В VM-рецепте counter_old_config заполняется задачей slurp только при существующем старом файле. На первой установке задача пропущена: register может существовать с skipped: true, но не содержит ожидаемого content. Поэтому rescue читает counter_old_config.content только под тем же условием counter_old_config_stat.stat.exists. Проверка одного counter_old_config is defined не доказывает, что файл был прочитан. Так же при loop содержимое лежит в отдельных results; нельзя брать один общий stdout и считать его ответом всех узлов.

Факт ОС и HTTP-ответ тоже имеют разное время: setup наблюдал архитектуру до выпуска, register от /version наблюдает процесс после перезапуска. Обновление файла facts не переписывает прежний register. Для решения «можно переходить к B» нужен новый ответ A после flush, а не сохранённое до выпуска число. Если ответа нет, состояние неизвестно; оно не становится нулевой версией или пустым счётчиком.

Set_fact фиксирует вычисление

set_fact создаёт связанную с host переменную в момент задачи. Она подходит для снимка старой версии перед изменением, нормализованного списка или результата выбора. Не стоит заменять ею все vars: вычисление становится событием, и зависимость от порядка скрывается. cacheable: true одновременно создаёт высокоприоритетную host-переменную текущего запуска и более низкоприоритетную копию в ansible_facts, пригодную для настроенного fact cache. На следующем запуске остаётся только кэшируемая семантика, поэтому приоритет может измениться. meta: clear_facts удаляет facts/кэшируемую копию, но не обязательно высокоприоритетную host-копию текущего set_fact.

- name: Remember chosen release for later plays
  ansible.builtin.set_fact:
    counter_observed_release: '{{ version_probe.stdout | trim }}'
    cacheable: false

Это runtime-память запуска, не новая запись в inventory и не журнал развёртывания. При падении controller позднее значение не восстановится волшебно. Для операционного решения сохраняют отдельный release manifest и наблюдённое состояние цели; при повторе заново опрашивают текущий symlink и ответ процесса.

Fact cache и ложная свежесть

По умолчанию memory cache живёт только в текущем запуске. Дисковый plugin, например jsonfile, требует явных путей, прав и срока. Кэш может содержать адреса, данные файлов и результаты custom facts; он не должен быть общедоступным. TTL, time to live, срок пригодности, ограничивает возраст записи, но не гарантирует соответствие ОС после изменения. Host с тем же inventory-именем после пересоздания может получить старые факты. Версию/идентичность машины учитывают при очистке и повторном сборе.

Кэш полезен для просмотра сведений других узлов, но не заменяет синхронизацию выпуска. Перед критическим решением — например, выбирать нужный бинарник по архитектуре — получают свежий факт либо передают проверенный контракт платформы. На схеме и в локальном тестовом образце facts выключены, чтобы не собирать сведения хоста пользователя. Сверено 01.11.2026: set_fact и facts/cache; при обновлении проверяют и cache plugin, а не только имя переменной.

When и типизированные условия

- name: Install only on declared operating system family
  ansible.builtin.assert:
    that:
      - ansible_facts['os_family'] == 'Debian'
      - counter_enabled is boolean

- name: Explain selected branch
  ansible.builtin.debug:
    msg: 'Counter is enabled'
  when: counter_enabled

when вычисляется для каждого host и при loop для каждого item. Список условий означает логическое AND; для OR пишут явное выражение a or b. Непустая строка 'false' не должна служить boolean-флагом. Если строковый интерфейс неизбежен, допускаемые значения проверяют и нормализуют явно, затем используют boolean. Слишком широкий default(false) способен скрыть опечатку обязательного имени. В core 2.21.5 строгие проверки условий помогают обнаруживать такие ошибки.

Цикл — последовательность вызовов, не batch API

- name: Create release directories
  ansible.builtin.file:
    path: '{{ counter_root }}/{{ counter_dir }}'
    state: directory
    mode: '0750'
  loop:
    - data
    - releases
  loop_control:
    loop_var: counter_dir
    label: '{{ counter_dir }}'

Каждая итерация может отдельно соединяться/исполнять модуль и возвращать результат. Если модуль принимает список пакетов, один вызов со списком обычно лучше N отдельных вызовов менеджера пакетов; это также избегает лишних блокировок. label уменьшает видимый шум, но не является защитой секрета. Для секрета нужны no_log, защита конечного файла и проверка прочих каналов.

Changed_when и failed_when

- name: Validate installed binary
  ansible.builtin.command:
    argv: ['/opt/counter/current/counter', '--version']
  register: counter_version
  changed_when: false
  failed_when: counter_version.rc != 0 or
               counter_version.stdout | trim != counter_expected_version

Проверочная команда не изменяет ресурс по нашему контракту, поэтому false у changed_when обоснован. Это не универсальная наклейка на опасный shell. Команда может вернуть rc=0 и неправильную версию; failed_when связывает технический код с требованием. Список нескольких failed_when — AND, поэтому два независимых вида отказа объединяют через OR одной строкой. Правило failed_when: false без последующего assert превращает реальный отказ в зелёную запись.

Повторять наблюдение, а не повреждение

- name: Wait for expected version on its own VM
  ansible.builtin.uri:
    url: http://127.0.0.1:8080/version
    return_content: true
    timeout: 2
  register: counter_probe
  until: counter_probe.status == 200 and
         counter_probe.content | trim == counter_expected_version
  retries: 10
  delay: 1
  changed_when: false

until повторяет задачу до истинного условия или исчерпания попыток; retries/delay задают предел и паузу. Здесь повторяется безопасное чтение. Повтор команды «прибавить значение» без idempotency key может повторить изменение, если ответ потерялся. timeout HTTP-запроса — не полный deadline play. Регистрируют фактическую длительность и число попыток. Доступный socket ещё не доказывает ожидаемую версию и сохранность данных.

Для закреплённого TaskExecutor 2.21.5 retries: 10 допускает исходный вызов и ещё десять повторов: не более 11 исполнений с десятью паузами по 1 секунде. Условный ответ 503, затем 200 со старой версией, затем 200 с ожидаемой завершит задачу на третьем исполнении. Если каждое чтение в отдельной модели занимает ровно 2 секунды, этот путь занимает 2+1+2+1+2=8 секунд; это расчёт, не сетевой замер. Параметр uri timeout не ограничивает весь путь задачи вместе с SSH, обработкой и паузами, поэтому 11×2+10×1=32 секунды также не универсальный deadline. Считайте исполнения по журналу: служебное поле attempts при исчерпании в этой версии не заменяет независимый счётчик вызовов.

Block, rescue и always

block объединяет задачи и наследуемые keywords; rescue выполняется при обычном failed в блоке; always — завершающий участок при нормальной обработке этого блока. Unreachable, синтаксическая ошибка или внезапное завершение controller не являются обычным failed, для которого обещается rescue/always. Это не finally распределённой транзакции. Если rescue успешно завершился, Ansible может продолжить play; критический выпуск после возврата явно завершают fail, чтобы следующий batch не пошёл как успешный.

- block:
    - name: Deliberate rejection in file fixture
      ansible.builtin.fail:
        msg: 'Rejected candidate, old state is retained'
  rescue:
    - name: Record observed rejection
      ansible.builtin.set_fact:
        counter_rejected: true
  always:
    - name: Verify branch was observed
      ansible.builtin.assert:
        that: counter_rejected | default(false)

Этот тестовый образец намеренно принимает ошибку как проверяемую ветку и ничего не восстанавливает автоматически. В реальном выпуске rescue сначала определяет, что успело измениться, затем возвращает прежний symlink/config и проверяет процесс. ignore_errors продолжает после failed, но не лечит причину; ignore_unreachable относится к другой границе. Применяют их только если следующий шаг сознательно разбирает результат. Для общего стопа есть any_errors_fatal, а допустимый процент отказа оценивают с учётом batch и строгого условия превышения. Официальная модель: error handling, 01.11.2026.

Уведомление и выполнение

Обычная задача с notify ставит handler в ожидающие только при итоговом changed: true. Несколько уведомлений одного handler до очередного flush сливаются в одно выполнение. Порядок определяется объявлением handlers, а не порядком notify. Имя handler должно быть однозначным в play; совпадение имён между ролями способно затенить предыдущий. listen задаёт тему: несколько handlers слушают общий сигнал, сохраняя собственные имена. Тема — удобная связь, но не граф зависимостей.

tasks:
  - name: Install unit
    ansible.builtin.template:
      src: counter.service.j2
      dest: /etc/systemd/system/counter.service
      mode: '0644'
    notify: Reload counter unit
  - name: Install configuration
    ansible.builtin.template:
      src: config.json.j2
      dest: /etc/counter/config.json
      mode: '0640'
    notify: Restart counter
  - name: Apply pending changes before health check
    ansible.builtin.meta: flush_handlers
handlers:
  - name: Reload counter unit
    ansible.builtin.systemd_service:
      daemon_reload: true
  - name: Restart counter
    ansible.builtin.systemd_service:
      name: counter
      state: restarted

Reload unit объявлен раньше Restart, поэтому при обоих уведомлениях systemd перечитает описание перед перезапуском. Но если изменился только unit и он не уведомил Restart, daemon-reload сам по себе не гарантирует перезапуска процесса. В рабочей роли оба существенных изменения уведомляют нужную тему или цепочку, и порядок проверяют отдельно. state: started обеспечивает запущенность, но не перезапускает уже работающий процесс после смены config. Это типичная причина зелёного recap со старой версией в ответе.

Где проходят точки flush

Движок запускает handlers в предусмотренных точках после секций play, в частности после pre_tasks, обычных roles/tasks и post_tasks. meta: flush_handlers принудительно выполняет накопленное в текущей точке. После него тот же handler может быть вновь уведомлён и выполнен позднее — «один раз» относится к очереди до flush, а не навсегда ко всему play. Для проверки готовности перед переходом к следующему batch нужен явный причинный порядок: изменение → flush → наблюдение версии/данных.

Отказ после изменённого файла

Обычно при последующем failed на host его ожидающий handler может не выполниться. На диске новый config, в памяти старый процесс; повторный запуск может увидеть тот же файл и уже не получить новое notify. force_handlers заставляет выполнять уведомлённые handlers даже после обычных отказов, но unreachable и потеря машины всё равно ограничивают возможность исполнения. Кроме того, принудительный restart с частично подготовленными файлами может ухудшить состояние. Поэтому политика должна соответствовать фазам: сначала проверить кандидаты, затем переключить согласованный комплект, применить, проверить.

При повторном запуске после оборванного выпуска не полагаются только на «файл изменился». Проверяют, что реально запущено, и имеют явное действие применения/возврата. В нашем VM-рецепте обычное применение использует handlers с явным flush внутри контролируемого блока; для восстановления потерянного уведомления есть отдельный принудительный перезапуск. Это делает восстановление после потери уведомления видимым. В локальном тестовом образце handler пишет неизменяющийся маркер «applied»; это проверяет доставку уведомления, но не изображает systemd.

Цена отложенного действия

Если десять шаблонов меняют один сервис, один restart вместо десяти уменьшает простой и лишнюю работу. Но большая очередь отложенных действий расширяет промежуток несогласованности. Сравнивают число фактических перезапусков, длительность недоступности и время от записи до применения; условные «10× быстрее» без замера не приводят. У сервиса с медленным стартом выигрыш может быть значителен, а у независимых конфигураций объединение слишком большого числа действий затруднит диагностику.

Фактический порядок проверяют по журналу обработчика событий и конечному процессу: после смены одного config handler один; после двух одновременно — по одному на объявление; после идемпотентного повтора — ни одного; после failure — документированная ветка. Правила сверены 01.11.2026 по официальной главе handlers. Пошаговая модель показывает три отдельных состояния: файл, ожидающее уведомление, обслуживающий процесс.

Два момента

import_tasks статически подставляет список задач при обработке playbook; импортированные задачи видны движку заранее. include_tasks остаётся runtime-действием: файл раскрывается, когда очередь дошла до include для конкретного host. Это не разница «сеть/без сети». Для имени статического файла нужны доступные на этапе раскрытия данные; результат предыдущей runtime-задачи не годится. Динамический include может выбирать файл по уже собранному факту или register, но полный список вложенных задач заранее увидеть нельзя.

- name: Static preparation
  ansible.builtin.import_tasks: prepare.yml
  when: counter_prepare | default(true)

- name: Dynamic release steps
  ansible.builtin.include_tasks: 'release_{{ counter_method }}.yml'
  when: counter_release_enabled

Условия import наследуются каждой вложенной задаче и вычисляются перед её исполнением. Условие include проверяет сам include в момент входа, а не автоматически каждую вложенную задачу. Это особенно видно, если внутри меняется переменная условия. Пусть перед import ready отсутствует, а первая подставленная задача делает set_fact: ready=true. С when: ready is not defined первая исполнится, а следующая импортированная задача уже будет пропущена. Для include тот же gate проверится один раз до входа; обе внутренние задачи смогут пройти. После import последовательность состоит уже из двух задач с одинаковым условием; после include сначала принимается решение о входе, затем исполняется тело. Замена одного keyword другим меняет наблюдаемый путь.

Повтор использования и циклы

На dynamic include можно повесить loop и вызвать один task-file для каждого элемента. На static import loop не поддерживается таким же образом: после раскрытия нет единичного runtime-вызова всего файла. Вложенные loops получают отдельные loop_var. Импорт playbook — import_playbook — связывает целые plays на верхнем уровне; include_playbook как общего динамического аналога нет. Роли также имеют import_role и include_role с разными моментами загрузки и видимостью параметров.

Tags — фильтр исполнения, не система зависимостей

- name: Enter release workflow
  ansible.builtin.include_tasks:
    file: release.yml
    apply:
      tags: [release]
  tags: [release]

Tags, метки задач, позволяют выбрать часть исполнения через --tags и --skip-tags. Для static import метки наследуются вложенными задачами. У dynamic include метка на include только допускает вход; для дочерних задач её передают через apply или явно ставят внутри. Если включить только release, а подготовка каталога имела метку bootstrap (начальная подготовка), движок не восстановит зависимость автоматически. always и never — специальные правила отбора, которые надо проверить вместе со skip-tags; слово always не означает безусловного выполнения при падении процесса.

Эти два запуска только показывают структуру и метки, не выполняя выпуск и не проверяя его готовность. Отбор release из учебного фрагмента выше имеет смысл лишь после подготовки соответствующего размеченного task-file; он не является следующим шагом готового VM-рецепта. Не добавляйте метки в этот рецепт только ради совпадения примера.

Сравнимые list-запуски показывают статически известную картину. Вложенные dynamic задачи не обещаются полным планом ни в --list-tasks, ни в --list-tags. --start-at-task также не универсален для динамического содержимого и может пропустить обязательные вычисления перед выбранной задачей. Для восстановления безопаснее повторить идемпотентный play с ограниченным inventory, чем прыгать в середину по имени без контекста.

Наблюдаемый эксперимент

labs/local/reuse.yml содержит static и dynamic gate с разными именами переменных. Assertions подтверждают: static вторая задача пропущена после изменения gate; dynamic вторая исполнена, потому что решение о входе уже принято. Файловая лаборатория не сбрасывается; тестовый образец использует отдельные runtime-факты, не трогая данные сервиса. Затем читатель сравнивает list-tasks и фактический журнал событий. Такой опыт показывает момент раскрытия лучше, чем правило «include гибче».

Слишком много динамического выбора уменьшает обзор программы и усложняет объяснение tags/handlers. Статический import удобен для стабильной композиции; dynamic include — для действительного runtime-ветвления. Принцип — минимальное время принятия решения, которое соответствует нужным данным. Роль как договор

Role, роль, группирует связанные задачи, handlers, defaults, templates и файлы по установленной структуре. Для «Счётчика» роль базовой настройки владеет пользователем, каталогами, config и systemd unit. Выпуск бинарника — отдельный workflow, поскольку его частичный отказ требует своего возврата. Публичные входы имеют prefix counter_, типы, defaults и валидацию. Выходы — явно управляемые пути и свойства, а не неявное изменение всего hostvars.

roles/gosvc/
  defaults/main.yml
  tasks/main.yml
  handlers/main.yml
  templates/config.json.j2
  templates/counter.service.j2
  meta/argument_specs.yml

defaults имеет низкий приоритет и подходит для настраиваемых входов. vars имеет высокий приоритет и используется редко для внутренних инвариантов; обязательный неизменный путь лучше прямо валидировать. meta/argument_specs.yml описывает аргументы роли для встроенной проверки; assert дополняет её межполевыми условиями, например «data path вне каталогов выпусков». files хранит байты без шаблонизации, templates — Jinja-источники. Секреты не включают в роль даже если их потом перекрывает Vault.

Зависимости и время вызова

Секция roles play и import_role дают статическую композицию. include_role позволяет runtime-выбор, loop и контроль публикации defaults/vars через поддерживаемые параметры вроде public. При чтении чужой роли выясняют, где её переменные становятся видимыми; не рассчитывают на историческое значение defaults для другой версии core. Зависимости в meta/main.yml могут выполнять другие роли до текущей; параметры и механизм дедупликации определяют повтор. Не используют скрытую dependency для необратимой миграции БД при каждом включении роли. Явная задача workflow лучше показывает такой переход.

Разделение ролей оценивают по владению ресурсом. Если две роли обе редактируют один config и обе перезапускают процесс, они конкурируют даже в одном последовательном play. Если роль принимает сотню неструктурированных toggles, клиент не может понять поддерживаемые комбинации. Один mapping с документацией, типами и ограниченным числом режимов легче проверять. Слишком глубокая цепочка dependencies увеличивает количество скрытых задач и время диагностики.

Collection и полное имя

FQCN, fully qualified collection name, полное имя объекта вида ansible.builtin.copy, включает namespace, collection и module/plugin. Короткое copy зависит от контекста поиска; явное имя уменьшает неоднозначность и связывает текст с правильной документацией. Для своей коллекции путь выглядит ansible_collections/lab/counter/plugins/modules/counter_config.py; модуль вызывается lab.counter.counter_config. Локальный library/ подходит лабораторному модулю, но не заменяет пакетный интерфейс команды.

collections:
  - name: community.general
    version: '11.4.0'

Это пример точной фиксации версии, а не зависимость упражнений и не утверждение, что указанная версия подходит всякой ОС. Сам номер подтверждён официальным релизом 11.4.0 при сверке 01.11.2026. Перед применением выбирают существующий релиз по его release notes, requirements и поддержке core. ansible-galaxy collection install -r collections.yml -p ./collections пишет в выбранный каталог; этот путь включают в конфигурацию поиска. ansible-galaxy collection list показывает установленные экземпляры по путям. Две версии в разных каталогах не означают одновременный выбор по одному номеру: порядок поиска может затенить ожидаемую. Полный пакет ansible также способен привнести другую версию.

Например, lab.counter.counter_config выбирает код из коллекции, найденной на controller; путь /etc/counter/config.json в аргументе относится к месту исполнения модуля. Файл roles/gosvc/templates/config.json.j2 ищется в роли, а не рядом с удалённым config. Если после установки второй коллекции изменился выбор кода, сначала сверяют ansible-galaxy collection list, пути из ansible --version и локальный ansible-doc. Наличие нужного tarball в офлайн-каталоге ещё не означает, что он установлен в выбранном пути поиска. Исправление пути не должно подменять уже принятый набор зависимостей без повторной проверки.

Совместимость и доверие к расширениям

У коллекции собственный requires_ansible, Python-зависимости и условия модулей. Поддерживаемый core не гарантирует совместимость каждой коллекции; наоборот, установка коллекции не обновляет произвольную библиотеку на target. Galaxy/Automation Hub распространяют код; подпись проверяет определённую цепочку доверия, если она настроена и доступна, но не делает операции безопасными по смыслу. Ревью включает action/filter/lookup plugins: они исполняются на controller с доступом к его файлам и credentials.

Для повторяемого комплекта сохраняют requirements с точными версиями, tarballs, хеши, описания dependencies, lock Python и target OS manifest. В томе нет внешних коллекций: все исполняемые тестовые образцы используют встроенные модули и один авторский локальный модуль. Это уменьшает число независимых источников вариации и делает офлайн-проверку понятной. Официальные контракты: roles, collections guide, сверено 01.11.2026.

Три разных размера

forks — предел рабочих процессов controller для параллельного исполнения задач. serial — размер batch, группы узлов, которая проходит play прежде следующей. Strategy — правило продвижения задач внутри допустимых участников. При стандартной linear текущую задачу выполняют на batch, затем идут к следующей; быстрый host ждёт медленного на границе задачи. При free host может уйти вперёд независимо; общий контекст, handlers и run_once требуют дополнительного внимания. throttle ограничивает параллельность определённой задачи/блока и не может превысить более жёсткий предел forks/batch.

- name: Roll forward one personal VM at a time
  hosts: counters
  serial: 1
  strategy: linear
  any_errors_fatal: true
  tasks:
    - name: Stage release
      ansible.builtin.include_tasks: release.yml

С двумя VM и serial=1 первая проходит подготовку → переключение → перезапуск → проверку готовности целиком. Если она не прошла проверку готовности и workflow завершился failed, вторая не должна начинать выпуск. Установка forks=20 не делает этот выпуск быстрее: batch содержит одного участника. При serial=2 два узла могут одновременно потерять доступность. Размер выбирают по резерву мощности, реальному поведению клиентов и независимости данных, а не по числу CPU (центральных процессоров) controller. Даже serial=1 не обещает zero downtime одному экземпляру.

Handlers в batch

Уведомления учитываются для host. Первый batch заканчивает свои предусмотренные точки handlers до перехода к следующему. Но health-task, размещённая до неявного flush, может проверить ещё старый процесс. Поэтому внутри выпуска ставят явный flush или явно выполняют перезапуск до проверки готовности. pre_tasks, roles/tasks и post_tasks образуют свои фазы; нельзя рассуждать, будто все handlers всего play обязательно выполняются лишь однажды после последней машины.

Рассмотрим A и B: A получил новый config и ожидает restart, B ещё старый. После flush A процесс загрузил новый config; только успешная проверка версии и сохранённого счётчика допускает B. При отказе A возвращают прежние config/symlink, подтверждают старый сервис и завершают выпуск failed. Даже успешный возврат не разрешает продолжить B без осмысленного решения. Эта последовательность нарисована в схеме handlers/serial и реально частично проверяется файловым тестовым образцом; сетевой VM-рецепт отдельно не объявляется испытанным.

Точный порядок файлов, очереди и процесса показан на временном разрезе в главе handlers. B там остаётся вне текущего batch; пунктир означает ожидание, а не фоновое исполнение. После отказа проверка возврата A нужна для восстановления сервиса, но финальный fail всё равно запрещает автоматически начинать B. Успешное rescue без этого fail означало бы другую политику продолжения.

Delegation меняет место, а не host-идентичность задачи

Базовый «Счётчик» слушает только loopback каждой VM, поэтому controller не подключится прямо к ansible_host:8080. Локальную готовность проверяют обычной задачей uri на target. Для опыта delegation после установки сервиса откройте из controller отдельный доверенный SSH-туннель к counter_a: ssh -N -L 127.0.0.1:18081:127.0.0.1:8080 deploy@АДРЕС_СВОЕЙ_VM. -N оставляет только перенаправление, -L создаёт локальный порт 18081, а правый 127.0.0.1 относится к VM. Подставьте её реальный адрес и дождитесь установки SSH; этот терминал остаётся занят. В следующем фрагменте явно ограничьте play/запуск узлом counter_a: один туннель не проверяет counter_b.

- name: Check target from controller network perspective
  ansible.builtin.uri:
    url: 'http://127.0.0.1:18081/healthz'
  delegate_to: localhost
  become: false
  changed_when: false

delegate_to выполняет действие через другой узел. inventory_hostname сохраняет имя исходного участника, но параметры connection, Python и become берутся в контексте делегированного host согласно правилам delegation. Для переменных исходной машины надёжнее явно обращаться через hostvars. delegate_facts: true связывает собранные facts с делегатом, а не с исходным host. Не все действия используют соединение: debug/include/add_host исполняются управляющим механизмом и не превращаются в удалённую операцию от delegate_to.

Если 30 hosts делегируют запись одного файла localhost, они всё ещё способны писать параллельно. Один физический адрес не является mutex. Для общей записи выбирают один task с агрегированными данными, throttle=1 либо внешнюю блокировку с понятным владельцем. Результаты проверки готовности с controller и с target различаются: loopback URI на target подтверждает локальную службу, делегированная проверка — доступ через нужную сеть. Полезно иметь обе, а не путать их результат.

Run_once и асинхронная работа

run_once выполняет задачу на одном host текущего batch и распространяет применимые результаты на участников batch. При serial задача может исполниться снова в следующем batch. Для действия ровно один раз по всему заданному play используют отдельный play на явном управляющем узле либо условие на выбранного участника с проверенной стратегией. В free нельзя переносить гарантии linear без проверки. Миграция БД не должна опираться на случайный «первый host» из динамического inventory.

async и poll дают иной жизненный цикл: poll=0 может вернуть ID фоновой работы до её завершения. Это не подтверждение успеха; нужен async_status, предел ожидания и учёт cleanup/повтора. Check mode и async имеют ограничения. Для короткого выпуска тома фоновые операции не нужны: они усложняют доказательство завершения. Основные правила сверены по strategies и delegation, 01.11.2026.

ansible-playbook site.yml -e @"$ANSIBLE_LAB_ROOT/vars.json" --limit counter_a -e counter_release=0.2.0 --check --diff

Простой --diff способен изменить систему. Аналогично --syntax-check проверяет структуру, а --list-tasks перечисляет известные задачи; ни один из этих флагов не подтверждает доступность SSH или работоспособность приложения.

Поэтому check на уже подготовленном стенде часто информативнее check на пустой VM, но и тогда остаётся прогнозом. В тестовом образце сначала реально создают корень и исходное состояние, затем проверяют изменение версии без записи.

Уровень поддержки — свойство действия

В ansible-doc смотрят Attributes: check_mode и diff_mode, а не предполагают поддержку по слову «модуль». Собственный модуль обязан сам реализовать чтение состояния, прогноз и запрет записи при module.check_mode; один supports_check_mode=True не делает реализацию правильной.

- name: Observe current version even during check
  ansible.builtin.command:

  changed_when: false
  check_mode: false

Это намеренно выполняемое чтение даже при глобальном check. У него должен быть доказанный безопасный контракт. Для команды «reset data» такое исключение уничтожило бы смысл preview. Задача с check_mode: false, lookup/plugin и внешнее API могут совершать действия в глобальном check; поэтому один флаг не является границей доверия к чужому playbook.

Что может утечь через diff

Diff может показать старый и новый пароль, токен или частный ключ. У секретного шаблона ставят diff: false и no_log: true, конечные owner/group/mode и безопасные временные каталоги. Но no_log не удаляет секрет из файлов назначения, внешнего журнала приложения и собственных callback-плагинов с ошибочным поведением. Не передают секрет через CLI-аргументы или debug ради проверки маскирования. Криптографическое хранилище на диске и журнал исполнения решают разные угрозы.

Проверка прогноза

Испытание состоит из четырёх наблюдений: hash/mtime исходного файла; check с изменённой desired version; тот же hash/mtime после check; реальное apply и изменение нужного поля. Затем повтор apply обязан не изменять файл при стабильных входах. Наш lab-check сохраняет эти свидетельства и дополнительно проверяет diff собственного модуля без раскрытия секретов. Для check на чистом состоянии ошибки зависимостей не маскируются: такой режим описывается как ограниченный.

Прогноз не гарантирует, что через минуту останется тот же репозиторий пакетов, свободный диск, API quota или значение inventory. Между check и apply читается новое состояние. В Ansible нет универсального сохранённого атомарного плана для всех ресурсов. Для критического выпуска фиксируют артефакт, inventory-состав и входы, затем заново проверяют предпосылки перед переключением. Официальные границы: check/diff, command, сверено 01.11.2026.

Vault защищает сохранённое содержимое

Ansible Vault шифрует файлы/переменные до использования. Пароль или password-client получает controller, который затем расшифровывает нужные данные. В память и аргументы модуля попадёт открытое значение; конечное приложение также должно его получить. Поэтому Vault защищает data at rest, данные в сохранённом виде, а не автоматически все журналы и каналы исполнения. Шифротекст в Git и пароль рядом в Git дают ложную защиту.

Для опыта возьмите свою VM-копию проекта из главы 2, сначала создайте личный каталог inventory/group_vars/counters с доступом только владельцу и сохраните в Vault заведомо учебное, не действительное значение. В редакторе нужен YAML mapping, например counter_demo_secret: training-only. У готового «Счётчика» нет потребителя этого параметра: опыт проверяет создание, чтение и изменение шифротекста. Фрагмент доставки credentials ниже показывает договор отдельного приложения, для него ещё нужен собственный шаблон credentials.json.j2 и поддержка формата самим сервисом.

ansible-vault create --vault-id lab@prompt inventory/group_vars/counters/vault.yml
ansible-vault edit --vault-id lab@prompt inventory/group_vars/counters/vault.yml
ansible-playbook -i inventory/hosts.yml site.yml --vault-id lab@prompt

Vault prompt запрашивает пароль интерактивно; label lab помогает выбирать источник, но не является самодостаточной криптографической границей окружения. Несколько vault-id требуют политики сопоставления. view выводит plaintext в терминал, decrypt оставляет plaintext-файл, rekey меняет защищающий пароль у шифротекста. Rekey не отзывает уже раскрытый токен приложения: его ротируют в самой целевой системе.

Редактор при edit может создавать swap/backup, индексацию и временные копии. Ограничивают каталог, настройки редактора и права; закрывают запись терминала/трансляцию. Password file должен быть частным и не включаться в export; executable password-client — код, которому доверяют доступ к менеджеру секретов. В нашем комплекте нет секретов, Vault-файлов и password-client, а тесты Vault не требуют действительного доступа к чужой системе.

Доставка секрета

- name: Install private service credentials in personal VM
  ansible.builtin.template:
    src: credentials.json.j2
    dest: /etc/counter/credentials.json
    owner: root
    group: counter
    mode: '0640'
  no_log: true
  diff: false

Здесь защита вывода, защита сохранённого файла и минимально нужный читатель заданы отдельно. Не делают credentials частью Environment= в unit, если это оставляет значение в предсказуемо читаемом описании/диагностике. Способ передачи выбирают по поддержке приложения и ОС. No_log применяется к чувствительной задаче; соседний debug var=hostvars способен вновь показать тот же секрет. loop_control.label уменьшает имя item, но не заменяет no_log.

Для доставки одного значения проследите владельцев: шифротекст лежит на controller; password-client даёт пароль процессу Ansible; после расшифрования Jinja получает строку; модуль переносит результат на target; файл с режимом 0640 доступен root и группе counter; процесс counter читает его. no_log скрывает предусмотренный вывод задачи, а diff: false запрещает показ старого и нового текста. Ни одно из этих полей не меняет содержимое конечного файла. Если секрет отозван владельцем API, прежний файл всё ещё содержит старые байты, но доступ по ним должен быть уже запрещён: это отдельное наблюдение при ротации.

Кому доверяется запуск

Playbook — программа с полномочиями controller и разрешённого become. Ревью файлов tasks без review filters/lookups/action plugins недостаточно: plugin может исполнять Python на controller ещё до удалённого действия. Требования коллекции, cfg, inventory и переменные connection также относятся к исполняемому контексту. Не запускают чужую роль с агентом SSH и Vault-паролем ради простого «посмотреть, что она делает». Check/diff не изолирует недоверенный код.

Узкий deploy-пользователь и отдельный ключ ограничивают обычный доступ, но возможность sudo для произвольного модуля часто близка к полномочиям root. Разрешение одной команды sudo по фиксированному пути плохо сочетается с временными Ansible-модулями: нужна осмысленная модель прав, а не бессмысленный allowlist случайного temporary filename. Для собственного модуля рассматривают аргументы как недоверенные данные, проверяют пути и не строят shell-строку из значений.

Ротация и след

При утечке прекращают дальнейшую выдачу, отзывают/ротируют секрет у его владельца, проверяют конечные файлы и доступ к logs/artifacts, затем меняют материал Vault и ключи по фактической области. Переписывание Git-истории само по себе не отзывает секрет. Отчёт сохраняет время, затронутые идентичности и выполненные проверки без plaintext. Журнал автоматизации нужен для причины и результата, но не должен стать копией всей памяти controller.

Компромисс наблюдаемости: слишком агрессивный no_log скрывает причину отказа, поэтому выделяют несекретные checks типов/доступа и безопасные codes. Не выводят частично замаскированный secret как доказательство. Официальная граница Vault проверена 01.11.2026: Vault guide; повышенные права — become guide.

Зачем не shell

Нужно сохранять точный JSON-object с release, message, listen и data_file. Shell-скрипт с echo и перенаправлением переписывает файл каждый раз, трудно различает malformed исходник и отсутствие файла, теряет типы и требует нескольких уровней quoting. Встроенный template/copy уже хорошо решает обычную доставку конфигурации. Собственный counter_config в практикуме нужен как учебный разбор интерфейса: он читает/валидирует существующий объект, формирует канонические байты, сравнивает режим доступа и отдельно реализует check/diff. Для production мы сначала предпочли бы поддерживаемый builtin, если его контракт достаточен.

Аргументы и наблюдение

module = AnsibleModule(
    argument_spec=dict(
        path=dict(type='path', required=True),
        config=dict(type='dict', required=True),
        mode=dict(type='str', default='0640')),
    supports_check_mode=True)

AnsibleModule из module_utils разбирает аргументы и предоставляет нормализованный ответ. path должен быть абсолютным, parent уже существовать. Существующий destination проверяется lstat: допускается только regular file, symlink отвергается. Существующий файл открывается как UTF-8-текст. Параметр newline не задан, поэтому open использует newline=None и преобразует переводы строк CRLF и CR в LF. Затем json.loads(before) разбирает прочитанную строку, а isinstance(old, dict) требует объект в корне. Полученный словарь old служит только для этой проверки; сравнение состояния ниже использует исходную прочитанную строку before. Такая проверка не задаёт схему полей. Стандартный анализатор Python также принимает NaN и Infinity, а при повторяющихся именах полей сохраняет последнее значение; текущий модуль не запрещает эти случаи при чтении. Ошибка декодирования UTF-8, ошибка разбора или другой тип корня приводят к failed до записи, с сохранением существующего файла. Отсутствующий файл означает новое создание. Режим — ограниченная octal-строка без специальных bits.

Желаемый config преобразуется в строку after: ключи сортируются, вложенность выделяется двумя пробелами, не-ASCII-символы сохраняются, в конце добавляется LF. При этой сериализации allow_nan=False отвергает нечисловое значение NaN и бесконечности; отказ происходит до записи. Далее changed = before != after or previous_mode != mode сравнивает две строки и режим доступа. Поэтому одинаковые JSON-объекты с разным количеством пробелов или порядком ключей могут дать changed=true. Но различие исходных байтов само по себе не гарантирует изменения: если в канонически оформленном файле заменить все LF на CRLF, сохранив права, чтение восстановит прежнюю строку before. Она совпадёт с after, модуль вернёт changed=false, и даже реальный запуск оставит CRLF на диске. Повтор с той же прочитанной строкой и режимом доступа также не создаёт изменения. Вход config описывает полный желаемый объект: при записи поля, отсутствующие в нём, не переносятся из старого объекта.

Diff возвращается только когда движок запросил module._diff; в нём нет секретов этого тестового образца. Секретный модуль потребовал бы no_log для чувствительных options и собственной политики diff. Нельзя сначала создать временный файл с desired secret, а затем сказать «check ничего не изменил».

При реальном изменении temporary file создаётся в том же каталоге, получает mode до публикации, затем содержимое flush/fsync и заменяет destination через os.replace. Пример не делает directory fsync после rename, не гарантирует долговечность при потере питания и не сохраняет ACL/xattrs/owner исходного файла. Он рассчитан на одного писателя в частном parent. Проверка lstat и последующая запись не защищают от злонамеренной гонки замены parent. Эти ограничения — причина не объявлять учебный модуль production-заменой copy.

Сначала управляющий core формирует обёртку с кодом модуля, вспомогательными модулями и аргументами. Коды завершения процессов и поля JSON проверяют отдельно.

Ответ и ошибки

exit_json печатает протокольный JSON и завершает модуль; fail_json возвращает явный отказ с причиной. Никаких print для отладки в stdout. Ожидаемые OSError/ValueError/TypeError превращаются в failed с полезным сообщением, временный кандидат удаляется в finally. Если rename прошёл, но ответ потерялся, повтор прочтёт опубликованный файл и станет no-op. Если write не удался до rename, прежний destination должен остаться, хотя полноценные disk-full/power-loss эксперименты здесь не выполнялись.

В авторском сервисе /version отвечает встроенной строкой build, GET /counter читает count, POST /counter увеличивает и сохраняет его. /healthz подтверждает живой обработчик; это не внешний аудит долговечности диска. Приложение работает одним процессом, защищает конкурентные обращения mutex — механизмом взаимного исключения, допускающим изменение счётчика одним обработчиком за раз. Данные — целое uint64 от 0 до 2⁶⁴−1 с завершающим переводом строки. Два сервера имеют независимые файлы: у них нет общей кластерной БД.

При SIGTERM/SIGINT сервер закрывает слушатель и ждёт завершения активных HTTP-запросов до пяти секунд в главном пути программы. Возврат Serve с ErrServerClosed сам по себе не означает, что Shutdown закончил ожидание. При исчерпании срока соединения закрываются, а завершение сообщается как ошибка: незавершённый запрос не выдаётся за успешный. Отдельный тест удерживает настоящий loopback HTTP-запрос, начинает остановку и подтверждает сохранение счётчика перед возвратом; ещё один проверяет конечный предел ожидания. Это не тест power loss или systemd. Основание: контракт net/http Shutdown.

Следующие две команды выполняют в исходном ansible/labs/service, где лежат go.mod и main.go, а не в рабочей VM-копии labs/vm.   go build -trimpath -ldflags='-X main.version=0.1.0' -o counter-0.1.0 .

Команду выполняют в service-каталоге на выбранном Go toolchain. CGO_ENABLED=0 исключает cgo для этого проекта, GOOS/GOARCH выбирают target, -trimpath уменьшает включение исходных путей, -ldflags передаёт линковщику строку версии. Версия toolchain, исходный commit, flags, платформа, размер и SHA фиксируются в manifest. Нельзя собирать заново независимо на каждой VM и затем утверждать, что доставлен один проверенный бинарник. SHA сравнивает байты, а доверие к исходникам/сборке требует своей цепочки.

Каталоги и фазы

Символическая ссылка, symlink, — имя файла с путём к другому объекту. current выбирает каталог установленной версии; изменение ссылки не перемещает постоянные данные и не перезапускает уже работающий процесс. Stage, подготовка выпуска, означает размещение и проверку новой версии до её активации. Активация меняет выбранную ссылку/настройки, затем перезапуск заставляет процесс прочитать новый выбор. Эти фазы позволяют сохранить прежний каталог и отдельно проверить результат.

 | Путь личной VM | Смысл | Право изменения

 | /opt/counter/releases/0.1.0/counter | Неизменяемые байты версии | Оператор с become; процесс читает/исполняет

 | /opt/counter/current | Symlink активного выбора | Workflow переключения

 | /etc/counter/config.json | Проверенные настройки | root пишет, counter читает

 | /var/lib/counter/count.txt | Постоянные данные | Пользователь counter

 | /etc/systemd/system/counter.service | Описание процесса | root; systemd применяет после reload

Папка релиза не владеет данными. Роль создаёт account/каталоги и unit; systemd запускает процесс как counter с ограниченным writable path. До первой записи на управляемую систему отдельный stat на controller проверяет SHA-256 исходного regular file с delegate_to: localhost и become: false. Stage копирует бинарник только в ещё отсутствующий файл новой версии и проверяет target SHA-256 и --version. Если версия уже существует, её байты обязаны совпасть с ожидаемыми; иной checksum отвергается до copy. Если существующие байты уже верны, copy пропускается; отдельный file восстанавливает только owner/group/mode. Повреждённый исходник controller поэтому не переписывает действующий релиз даже при повторе. Новая копия проверяется на target до переключения ссылки. Пример рассчитан на одного писателя; параллельный второй controller потребует отдельной блокировки.

Переход от stage к готовности

До изменения workflow фиксирует текущий symlink, читает прежний несекретный config и, если сервис уже есть, читает его count. Затем валидирует новый config staged-бинарником, устанавливает unit/config, переключает current, flush handlers и обеспечивает started. Проверяет loopback /version до ожидаемого значения и /counter: count не меньше наблюдённого до выпуска. Serial=1 не пускает следующую VM до окончания этой последовательности. Небольшая пауза доступности одной VM допустима для этого личного стенда; без балансировщика и прикладного контракта нельзя обещать непрерывную доступность клиентов.

Повтор при неизменных файлах не уведомляет handlers, а state: started не перезапускает уже работающий процесс. Так базовая идемпотентность сохраняется. После обрыва между switch и handler файл может уже быть новым, а процесс старым. Для такого состояния предусмотрен явный counter_force_restart: true: он намеренно перезапускает процесс и даёт changed. Восстановление — осознанное действие с наблюдением, не скрытая гарантия notify.

Например, до выпуска у A current → releases/0.1.0, HTTP сообщает 0.1.0, а count равен условному 41. После доставки 0.2.0 каталог новой версии уже существует, но процесс ещё 0.1.0. После замены current/config и до flush диск выбирает 0.2.0, а обслуживающий процесс всё ещё может отвечать 0.1.0. После restart ответ 0.2.0 при count ≥41 подтверждает конкретный переход. Сумма нового бинарника, ссылка на него и HTTP-ответ — три разных наблюдения; один changed=0 не подменяет их. При обычном повторе без различий очередь пустая; при прерывании прежнего запуска это может потребовать явного restart, описанного ниже.

Частичный отказ

При обычном failed внутри block rescue возвращает config и current, перезапускает прежний процесс и проверяет готовность, прежнюю HTTP-версию и count не меньше исходного, затем явно fail останавливает весь rollout. При первой неудачной установке прежней версии нет: убирается только новый current/config, служба останавливается, data-каталог сохраняется. Подготовленные release-каталоги не очищаются автоматически: они полезны для разбора и повторного запуска. Проверка готовности после возврата не доказывает правильность всех прикладных результатов; человек сверяет manifest и count.

Unreachable, питание VM, kill controller и ошибка вне блока не обязаны выполнять rescue. Сначала читают реальное состояние через консоль/SSH, затем выбирают desired version и restart. Если версия приложения изменила формат данных, возврат бинарника может стать невозможным без миграции/резерва. Здесь обе версии используют один формат, migrations отсутствуют; универсальный rollback данных не обещается. Snapshot данных снимают явно при остановленном писателе, а restore понимают как потерю записей после снимка. Полный выполняемый рецепт — VM README, он не объявлен реально испытанным на двух машинах.

Граница с Terraform и наблюдением

Это разделение инструментов, а не готовый переход между лабораториями книги. Локальный Terraform-практикум создаёт запись receipt через terraform_data и не создаёт VM, адреса или SSH-доступ для этого выпуска. В Prometheus-практикуме используется другой Go-сервис на порту 18080; наш «Счётчик» на loopback:8080 остаётся отдельным приложением. Чтобы объединить их, потребовались бы явно реализованные инфраструктура, inventory и наблюдаемые метрики; здесь такое объединение не заявляется.

Terraform может подготовить инфраструктуру и передать адреса/идентичности; Ansible получает проверенный inventory и договор SSH/Python, а не извлекает тайно root-доступ из файла state. Доступы передают защищённым каналом, не публикуют в outputs для общего чтения. Наблюдение приложения после выпуска нужно независимо от инструмента доставки: ожидаемая версия, доступность, сохранённые данные и ресурсная стоимость. В этом томе нет реализации соседнего Terraform-тома или системы мониторинга: контракт достаточен, чтобы разделить ответственность.

Оператор: нет процесса CLI; Releases: 0.1+0.2; Current: 0.2; Config: 0.2; Процесс: 0.1; Данные: 41

Идемпотентные file/template могут не дать notify. Version probe обнаруживает старый процесс.

Действует: Новый controller.

Оператор: осматривает; Releases: не меняются; Current: 0.2 unchanged; Config: 0.2 unchanged; Процесс: 0.1 обнаружена; Данные: 41

Слои свидетельств

Статическая проверка разбирает YAML, metadata, ссылки и аргументы. Syntax-check загружает известную структуру playbook и зависимости. Local integration запускает настоящий core и модули в временной файловой системе. VM integration проверяет SSH, Python target, sudo, package/service manager, порты и независимость ОС. Application acceptance читает ожидаемую версию и постоянные данные. Эти слои дополняют друг друга, а не образуют один условный «тест пройден».

Для команд ниже рабочий каталог — сохранённая копия ansible/labs/local с выбранным её ansible.cfg, inventory и переменными из README. Путь ../../tests/lab_check.py относится к полной исходной копии тома; если копировали только local, откройте отдельный терминал в исходном ansible/ и вызовите python3 tests/lab_check.py. Это автоматический тест с собственными временными файлами, не команда продолжения reader-стенда.

ansible-playbook site.yml --syntax-check
ansible-playbook site.yml --list-hosts
ansible-doc -M ./library counter_config
python3 ../../tests/lab_check.py --ansible-bin /путь/к/изолированному/bin

Последний путь выбирается для уже подготовленной среды исполнения; скрипт ничего не устанавливает. Он требует core 2.21.5 этой редакции и ограничивает соединение local. --keep сохраняет только новый private temporary root для разбора логов; по умолчанию он удаляет свой корень в finally. Это cleanup автоматического теста, а не reset долгоживущего reader lab. Факт удалённого temp не мешает обычным упражнениям сохранять их отдельный корень.

Изменение и повтор — разные тесты

Первый apply проверяет появление нужных файлов, поля JSON и handler-marker. Затем test отдельно пишет count=41 и сохраняет hash+mtime файлов. Повтор не должен изменить config/data/marker и должен дать changed=0 на обоих aliases. Таким образом test замечает шаблон с timestamp и непреднамеренный перезапуск handler, а не просто читает stdout. Для preview версия меняется на 0.2.0 с check/diff: в выводе ожидается прогноз, а hash/mtime остаются прежними. Реальный apply 0.2.0 меняет config/marker, сохраняя count; явный возврат 0.1.0 также не сбрасывает count.

У custom module отдельные тестовые образцы для mode drift, malformed JSON и symlink. Последние два должны failed без перезаписи исходных байтов. Это проверяет значимые опасные ветки. Assertions языка проверяют task/play/extra priority, момент set_fact, static/dynamic gate и run_once при serial=1. Образец отказа намеренно вызывает fail и подтверждает rescue/always; его rescued=1 не является незамеченным сбоем лаборатории. Vault roundtrip работает с временным тестовым plaintext/password и не печатает их.

Отдельный tests/stage_check.py извлекает настоящие задачи проверки/копирования из VM-рецепта и выполняет их local только в своём временном каталоге, заменив owner/group на UID/GID тестирующего пользователя. Проверены повреждённый source, изменение source после предварительной проверки, неверный SHA нового файла, корректный новый файл и исправление mode существующего. Сохранность прежних байтов наблюдается независимо. Это проверяет компонент доставки, но не SSH, become, роль начальной подготовки или systemd.

Роль на личной VM

VM-тесты должны начинаться с поддерживаемой ОС и snapshot, затем пройти install→повтор→config change→release→ошибка→возврат→reboot. Не восстанавливают snapshot автоматически перед каждым шагом, иначе пропадёт проверка drift и повторного запуска. Snapshot используется явно для контролируемого исходного состояния или возврата после опыта, с указанием, какие новые данные будут потеряны. Успех на контейнере без systemd не проверяет unit, boot, sudo и SSH trust.

Molecule — отдельный инструмент организации сценариев роли и драйверов окружения; он не является частью обязательного core и не создаёт универсальную VM без выбранного driver/provider. Ansible-lint проверяет правила стиля/практики, но ложное отсутствие изменений можно получить и с идеальным style. Для публикуемой collection ansible-test запускает свои sanity/unit/integration-контракты; его версия должна соответствовать дереву коллекции и поддерживаемому core. Здесь эти внешние инструменты не ставились и их результаты не заявляются.

Разложить длительность

Наблюдаемое wall time — время по часам от начала до конца — включает загрузку inventory/plugins, вычисление данных, ожидание свободного worker, установление/переиспользование соединения, подготовку/передачу пакета исполняемых данных, выполнение модуля, ожидание внешней системы и сбор результата. Сумма длительностей задач на разных hosts может превышать wall time из-за параллельности. CPU seconds, секунды процессорной работы, не равны wall seconds: ожидание сети почти не использует CPU. RSS — resident set size, резидентная память процесса — не равна объёму Python-объектов и не суммируется бездумно при shared pages.

В собственном стенде фиксируют core/Python, inventory, число задач, bytes файлов, состояние SSH connection cache, факт первого/повторного apply и загрузку машин. Затем не менее нескольких одинаковых прогонов записывают median и хвост, например p95 при достаточном количестве наблюдений. p95 из пяти запусков не устойчивое свойство; показывают сами числа/разброс. Не включают первый прогрев в одну группу с тёплыми повторениями, если это меняет смысл.

SSH и передача

Первый ssh ... true на личную VM с заранее проверенным ключом измеряет setup/authentication плюс короткую команду. Повтор с теми же ControlMaster/ControlPersist условиями показывает выигрыш reuse. Перезапуск общего SSH-сервера ради теста не нужен. Время ansible.builtin.ping добавляет путь модуля, но не равно чистой сети. Копирование фиксированного файла измеряют отдельно, контролируя размер в MiB и полосу в MiB/s; для крошечного файла latency может доминировать над throughput. -vvv полезен для границ, но сам добавляет форматирование/вывод.

Pipelining сокращает ряд операций передачи/временных файлов для поддерживаемых модулей, передавая код через канал запуска. Это не «все задачи без диска» и не компрессия произвольного copy. Его совместимость с become и политикой TTY проверяют на своей ОС; исторический requiretty у sudo может мешать. Сравнивают одинаковый read-only play с ANSIBLE_PIPELINING=false и true, сохранив остальные параметры. Не меняют одновременно forks, gathering и network, иначе причина выигрыша неразличима.

Gathering, шаблоны и granularity

Если 200 задач только кладут один файл, тысяча мелких calls может стоить больше передачи самих байтов. Используют пакетные параметры модулей, нормализуют данные один раз и избегают O(N²)-обхода hostvars в каждом шаблоне. Выключение gather_facts допустимо, если нужные данные заданы проверенным контрактом, либо собирается subset. Fact cache сокращает повторный сбор ценой устаревания и защиты дополнительного хранилища. Разница «без facts быстрее» не оправдывает выбор неправильной архитектуры бинарника по старому кэшу.

Forks — верхняя граница, а не обещанная скорость

Файл observe.yml не создаётся сам. Сохраните в своей VM-копии проекта следующий небольшой play, который только получает идентичность и версию Python, без become:

- name: Measure an unchanged read-only call
  hosts: counters
  gather_facts: false
  become: false
  tasks:
    - name: Read process identity
      ansible.builtin.command:
        argv: [id]
      changed_when: false
    - name: Read Python version
      ansible.builtin.command:
        argv: [/usr/bin/python3, --version]
      changed_when: false

Сначала прочитайте состав узлов и подтвердите SSH/Python из главы 3. Этот сценарий использует два последовательных чтения на каждом узле; наблюдаемый выигрыш ограничен числом независимых targets. На двух VM forks=8 не создаст восемь машин. Затем сравните:

ansible-playbook -i inventory/hosts.yml observe.yml --forks 2
ansible-playbook -i inventory/hosts.yml observe.yml --forks 8

Сравнение проводят на read-only observe.yml со стабильным составом, не на перезапускающем сервис выпуске. Controller расходует CPU на YAML/Jinja/JSON, оперативную память (RAM, random-access memory) на workers/hostvars, descriptors и сеть на соединения. Target расходует CPU/RAM/disk и слоты внешних систем. Пакетный менеджер одной ОС сериализуется lock; API имеет собственный rate limit. Повышение forks может перевести bottleneck в controller RAM, DNS, SSH-server limits или shared registry. У serial=1 максимум один target в batch, поэтому forks=8 часто ничего не меняет.

Условный расчёт: 20 независимых hosts, 10 одинаковых задач, каждая требует примерно 150 ms latency+50 ms исполнения, без variance/overhead. При идеальных 5 workers нижняя оценка порядка 20×10×0.2/5=8 s. Это модель, не результат запуска. Если один host отвечает 8 s на каждой задаче, linear-барьеры и хвост ломают такую оценку. Free может уменьшить ожидание быстрых hosts ценой иной синхронизации; batching может быть ограничен требованиями доступности. Сначала наблюдают распределение по host/task.

Почему сумма работ не равна длительности

Возьмём отдельную расчётную модель: две задачи, два узла A/B, два свободных worker, без SSH/CPU-накладных расходов. Длительности A равны 0.2 и 2.0 секунды, B — 2.0 и 0.2 секунды. При linear первая задача заканчивается для обоих в 2.0; вторая — ещё через 2.0: wall time 4.0 секунды. При free A заканчивает в 0.2+2.0=2.2, B — в 2.0+0.2=2.2: wall time 2.2 секунды. Сумма занятости исполнителей в обоих случаях 4.4 секунды; это длительности задач, не CPU seconds. При serial=1 play целиком пройдёт A, затем B, и получится 4.4 секунды при любой величине forks ≥1.

Здесь free ускоряет только снятием барьера между независимыми задачами. Если вторая задача B должна читать результат первой задачи A, менять стратегию по этой арифметике нельзя без явного согласования. Для существующих двух VM сравнение forks=2 и 8 проверяет отсутствие дополнительных участников; чтобы отдельно увидеть ограничение worker, сравните также forks=1 с 2 на том же read-only observe.yml. Запишите фактические времена, а не переносите модельные 4.0/2.2 на SSH.

Выбрать следующее изменение

 | Свидетельство | Вероятный предел | Контролируемое изменение

 | Высокий wall, низкий CPU, холодный SSH медленнее | Setup/latency | Проверить reuse, затем pipelining

 | Controller CPU занят, target простаивает | Шаблоны/JSON/plugins | Уменьшить данные/повторные вычисления

Карта отказа

Drift, дрейф, — расхождение между желаемым и наблюдаемым состоянием после внешнего изменения. Источник может быть легитимным hotfix, автоматикой другого владельца, ошибкой диска или атакой. Idempotent apply часто устранит drift, но сначала нужно понять, не содержит ли он единственной копии важного изменения. Для config сохраняют diff, для данных не применяют шаблон «как было в Git». У config и stateful data разные политики владения.

 | Место | Что могло успеть | Проверка перед повтором

 | До соединения | Ничего на target; controller мог сделать lookup | Inventory, config, trust и доступность

 | Во время модуля | Изменение выполнено, ответ потерян | Независимо прочитать файл/ресурс

 | После config до handler | Новый файл, старый процесс | Хеш настроек и версия работающего процесса

 | После переключения до проверки готовности | Новый выбор, неизвестная готовность | Link, unit, journal, HTTP, count

 | Во время rescue | Возврат частично выполнен | Все элементы состояния, не только failed task

Повторить ограниченно

ansible-playbook -i inventory/hosts.yml site.yml --list-hosts --limit counter_a
ansible-playbook -i inventory/hosts.yml site.yml --limit counter_a -e @release-vars.yml --check --diff
ansible-playbook -i inventory/hosts.yml site.yml --limit counter_a -e @release-vars.yml -b -K

Limit выбирает проблемный host, а не произвольную строку из ошибочного вывода. Check предварительно информирует при поддерживаемых задачах; в VM-рецепте staged binary/пользователь на пустой системе не моделируются полностью. Полный повтор безопасен лишь в пределах честных контрактов модулей. Создание пользователя идемпотентно относительно модели account; «отправить уведомление» или «увеличить count» не становится идемпотентным от нового вызова Ansible.

--start-at-task способен пропустить вычисление facts, сохранение previous version и подготовку каталогов. Автоматический retry-file содержит только выборку, но не snapshot переменных/времени/ресурса. Поэтому сохранённый manifest и журнал причин важнее короткой команды повторения. Не запускают два controller на один набор каталогов выпусков без lock — Ansible сам не является распределённой блокировкой всей среды.

Продолжение на следующий день начинается с сохранённых путей: тот же cfg, inventory-имена, release-vars с прежними trusted SHA и private key/known_hosts. На target отдельно прочитайте current, config, HTTP version и count; записанное вчера значение — предыдущая точка сравнения, не описание нынешнего процесса. Если переменная shell с путём пропала, восстановите её из своей частной заметки и проверьте существование корня. Не запускайте mktemp повторно ради «исправления» отсутствующего пути: это создаст новый стенд и скроет старое состояние. Если /tmp был очищен, восстановление сохранённой копии — отдельное действие; без копии прежние данные нельзя объявить сохранившимися.

Резерв комплекта и данных

Для восстановления инструмента нужны исходные playbooks/roles, exact dependencies, lock/hashes, inventory без потери стабильных имён, config, Vault ciphertext и отдельный доступ к ключам/паролям, известные host fingerprints. Для сервиса дополнительно нужны binaries/manifests, config, unit и согласованный резерв данных. Секретные ключи и приватный inventory не включают в публичный HTML/export. Единственная копия Vault-пароля на потерянном controller делает шифротекст бесполезным.

В «Счётчике» каждый POST атомарно публикует новое содержимое и синхронизирует файл/каталог. Это не shared-storage protocol и не защита от двух процессов с одним data_file: у них независимая память, и значения потеряются. Поэтому systemd запускает один экземпляр, snapshot снимается при остановленном писателе, а restore испытывается отдельно. После restore проверяют число, режим/владельца и способность выполнить следующий POST; успешное копирование backup недостаточно.

Обновление controller и targets

Новый core испытывают в новом окружении рядом со старым. Читают porting guides всех пересекаемых major-линий; особенно templating changes 2.19, требования Python 2.20/2.21 и изменения коллекций. Устанавливать core новее ради одного target без проверки старых ОС нельзя: поддержка target Python может сузиться. Сначала статические и локальные проверки, затем клон личной VM и только после явной приёмки рабочий учебный стенд. Возврат toolchain возможен, пока сохранён прежний комплект и новые задачи не сделали несовместимые изменения данных.

Минимальный отчёт инцидента

Отчёт фиксирует выбранные hosts, версии инструментов/артефакта, последнее подтверждённое состояние, фактические изменения, ошибку, попытку возврата и её проверку. Разделяет «модуль вернул changed», «SHA совпал», «процесс ответил version» и «count не уменьшился». Не принимает none/неполученный ответ за ноль. Такой след позволяет продолжить утром с той же машины, а не начинать новый стенд для сокрытия причины. Категории ошибок сверены с error handling, 01.11.2026.

Маршрут local

Откройте local README и подготовьте isolated core 2.21.5 по первой книге. Выберите один созданный вами корень /tmp/ansible-reader-lab-*, сохраните путь в частной заметке, задайте local/remote temporary paths под ним и vars с проверенным Python. Inventory содержит counter_a/counter_b с local connection; они не являются отдельными ОС. Не добавляйте become. Сначала graph и list-hosts, затем первый apply.

Начальная конфигурация. Прочитайте config.json, applied.json и data/count.txt для каждого alias. Объясните, какая задача создала каждый файл, что уведомило handler и почему маркер читается после flush.

Повтор. До повторного apply сохраните hash и mtime. Добейтесь changed=0 и неизменности данных. Если файл меняется, найдите источник нестабильных байтов, а не скройте его changed_when.

Сохранение данных. Запишите count=41 как имитацию прикладной записи. Повторите play. Почему force=false у seed не даёт применить «7» повторно? Что он не проверяет относительно корректности 41?

Прогноз. С desired release=0.2.0 исполните check/diff. Зафиксируйте ожидаемый diff и отсутствие изменения файлов/mtime. Потом apply без check: config и marker меняются, count сохраняется.

Drift. Поменяйте mode config на 0644. Сравните check и apply. Затем сделайте сохранённую копию config и внесите malformed JSON. Модуль обязан отказать, сохранив дефектный файл для разбора. Восстановите корректную копию явным действием и повторите.

Возврат. Примените release=0.1.0. Проверьте не только строку версии, но и count=41. Возврат конфигурации не равен возврату накопленных данных.

Язык как наблюдаемый эксперимент

precedence.yml запускают без extra vars, затем с JSON {"counter_port":8085,"counter_expected_port":8085,"extra_case":true}, как в точных командах главы 7. Объясняют значения 8084 в task context и 8083 в следующей задаче, затем 8085 в обеих. Frozen set_fact сохраняет прежний результат при новом task value=9090. reuse.yml показывает статическое наследование gate и динамическое решение о входе. Не следует исправлять ожидаемый skipped: это суть опыта. serial.yml подтверждает run_once на каждый one-host batch. failure.yml показывает намеренный failed→rescue→always; в recap ожидается rescued, а не невидимая идеальная история.

При несовпадении сначала прочитайте actual CLI/core version, выбранный cfg и inventory. Не редактируйте tests под нужный вывод. Ошибка undefined — повод определить источник/время, mode mismatch — числовое представление/права, malformed — валидность данных. Полезно записать одну гипотезу, один изменённый вход и новое наблюдение: это отделяет диагностику от случайного перебора параметров.

Multi-VM продолжение

По отдельному рецепту подготовьте две личные Linux VM. Сохраняйте inventory-имена, account, data paths и release manifests. Принимайте SSH, Python и become до запуска роли. Сначала один host, затем весь inventory с serial=1. Получите HTTP count, выполните несколько POST, обновите бинарник с новым SHA и убедитесь, что count не уменьшился. Из-за независимых data_file сравнивайте каждую VM с её прежним значением, а не требуйте равенства A и B.

Для отказа сначала используйте неверный expected SHA: он должен остановить действие до подмены существующего релиза. Затем ошибку config, которую поймает validate. Наконец, только при наличии VM snapshot и понятной консоли, отдельно исследуйте обрыв между переключением/обработчиком и проверкой готовности. Не выдавайте этот опыт за результат локальных тестовых образцов. Сохраняйте сведения о фактическом частичном состоянии и выбирайте явный restart/rollback. Снимок VM — отдельный выбор читателя с понятной потерей новых данных при restore.

Измерение и итоговая приёмка

На тех же VM измерьте холодный/тёплый SSH, обычный gather_facts и выключенный, pipelining false/true, forks=2/4 при безопасном read-only play. Запишите условия, wall time, controller CPU/RSS и target disk/network, а также разброс нескольких прогонов. Не включайте release restart в эксперимент на чистую latency. Выберите одно улучшение с измеренной причиной и объясните его стоимость, например stale cache или большая concurrency.

Готовый отчёт отвечает: какие версии и источники использованы; какие hosts реально участвовали; какие состояния сохранились; почему повтор no-op; какой отказ обнаружен и исправлен; что доказали check/diff/health; как восстановлен прежний выпуск; какие механизмы остались неиспытанными. Автоматический lab-check проверяет исходники в отдельном временном корне и не заменяет этот собственный операционный отчёт.

Словарь в боковой панели также ищет определения во всех остальных томах.

Ansible

Система автоматизации: управляющий процесс читает состав узлов и задачи, вычисляет аргументы и организует действия через выбранные плагины. У обычного CLI нет обязательной постоянно работающей службы или БД.

ansible-core

Минимальная поставка движка, CLI и встроенной коллекции. Её версия независима от номера полного community-пакета ansible.

Controller

Управляющий узел, где запущен Ansible, вычисляются шаблоны и исполняются управляющие плагины. Это отдельная сторона от target.

Target

Управляемая система, над ресурсами которой выполняется действие. Обычный Linux-target использует SSH, оболочку и Python, но не требует установки полного Ansible.

Inventory

Именованный состав узлов, групп и связанных параметров. Адрес соединения и inventory-имя не обязаны совпадать.

Dynamic inventory

Состав, получаемый plugin/script из внешнего источника при загрузке. Его фильтры, кэш и стабильность имён входят в договор безопасности.

Playbook

YAML-список plays, описывающих выборку узлов и упорядоченное исполнение задач. Это программа автоматизации с полномочиями запускающего пользователя.

Play

Участок playbook с hosts, контекстом и последовательностью задач/ролей. При serial проходит по очередным batches.

Task

Задача: вызов action с аргументами, условиями и политикой обработки результата для конкретного host.

Module

Повторно используемый код ограниченной операции с входными аргументами и структурированным результатом. Часто исполняется на target, иногда через иной контекст.

Plugin

Подключаемый компонент движка: соединение, действие, стратегия, фильтр, lookup или обработчик событий. Может выполнять код на controller.

Action plugin

Управляющая часть действия: например, template рендерит файл на controller и организует доставку/сравнение на target.

Connection plugin

Реализация канала исполнения и передачи данных, например SSH или local. Выбор местоположения не меняет автоматически смысл аргументов.

Callback

Обработчик событий исполнения и вывода. Он получает результаты и может форматировать/сохранять их; цвет терминала не является независимым аудитом ОС.

SSH

Secure Shell: протокол защищённого удалённого доступа с проверкой сервера и аутентификацией клиента. Доверие к host key отличается от допуска пользовательского ключа.

Host key

Ключ SSH-сервера, по которому клиент проверяет идентичность узла. Его fingerprint нужно получить через доверенный канал.

Fingerprint

Короткое представление хеша ключа. Позволяет сверить предъявленную идентичность с доверенно ожидаемой.

known_hosts

Клиентский реестр известных ключей SSH-серверов. Удаление записи не доказывает допустимость нового ключа.

authorized_keys

Реестр допустимых открытых пользовательских ключей для входа в учётную запись SSH-сервера.

SSH agent

Процесс, предоставляющий операции с загруженными закрытыми ключами без передачи самих ключевых файлов каждой программе. Доступ к агенту также чувствителен.

Become

Механизм смены effective пользователя через существующую политику ОС, например sudo. Не является вторым сетевым соединением.

UID

User identifier — числовой идентификатор пользователя ОС. Effective UID определяет права исполняемого процесса.

GID

Group identifier — числовой идентификатор группы ОС; участвует в проверке доступа к файлам.

ACL

Access control list — дополнительный список правил доступа. Простой mode не описывает все возможные ACL и extended attributes.

POSIX

Семейство стандартов интерфейсов Unix-подобных систем. В этом томе упоминается прежде всего как договор оболочки и процессов.

YAML

Текстовый формат отображений, списков и скаляров. Сначала парсер строит данные, затем Ansible интерпретирует их структуру.

Scalar

Отдельное значение данных, например строка, число, boolean или null; отличается от списка и mapping.

Mapping

Отображение уникальных ключей в значения. В YAML записывается через key: value; совпадающее имя переменной другого уровня может заменить весь mapping.

Boolean

Логический тип true/false. Строка с текстом false — другой тип и требует явной политики преобразования.

Null

Явное пустое значение существующего ключа. Отличается от отсутствующего, undefined-ключа и от false/0/пустой строки.

Jinja

Шаблонизатор выражений и файлов. В Ansible обычное вычисление выполняется на controller в доступном контексте переменных.

Undefined

Имя или ключ отсутствует в доступном контексте. default без второго true заменяет именно undefined, а не всякое пустое значение.

Filter

Преобразование уже полученного значения в Jinja, например to_json или combine. Не тождественно lookup, получающему данные из источника.

Jinja test

Проверка свойства значения, например is integer, is defined или is mapping. Возвращает логическое решение для выражения.

Lookup

Плагин получения данных на controller, например из файла или API. Не читает автоматически файл target от удалённого hosts.

omit

Специальное значение Ansible, означающее не передавать параметр действия. Не является строкой для записи в конечный файл.

Variable precedence

Правила выбора определения переменной при конфликте источников. Приоритет, область host/task/play и момент вычисления нужно рассматривать вместе.

Extra vars

Переменные всего запуска, переданные через -e/--extra-vars, с высоким приоритетом. key=value обычно даёт строки; YAML/JSON сохраняет типы.

Facts

Наблюдённые сведения о target или связанные с ним runtime-данные. Их достоверность зависит от времени и способа получения.

Register

Сохранение структурированного результата задачи в переменную host. Набор полей зависит от action; stdout существует не у каждого модуля.

set_fact

Действие присваивания вычисленного значения переменной host в момент исполнения. cacheable создаёт также копию для fact cache с иной последующей семантикой приоритета.

Fact cache

Хранилище собранных фактов между обращениями/запусками. Ускоряет получение ценой устаревания и дополнительной защиты чувствительных данных.

TTL

Time to live — ограничение времени пригодности кэш-записи. Не доказывает, что система не изменилась раньше истечения срока.

Handler

Отложенная задача, уведомляемая итоговым changed. Несколько уведомлений до flush обычно объединяются; порядок задаётся объявлением.

Notify

Запрос запуска handler или слушателя темы после изменения. Сам по себе не означает уже выполненного перезапуска.

Flush

Применительно к handlers — выполнение накопленной очереди в явной или неявной точке. После него возможны новые уведомления.

Idempotence

Идемпотентность: повтор того же приведения при стабильных входах/окружении не создаёт дополнительного изменения. Не равна транзакции и не гарантирует health.

Changed

Утверждение задачи об изменении по её контракту либо changed_when. Не является самостоятельным доказательством изменения процесса или доступности приложения.

Failed

Задача признана неуспешной по ответу/коду/failed_when. Отличается от недоступности transport и от намеренно skipped исполнения.

Unreachable

Не удалось обычным образом обратиться к host/исполнить обмен. Для такого состояния не обещается обработка обычным block/rescue.

Recap

Итоговые счётчики событий исполнения по host. Это отчёт движка, а не независимый полный аудит желаемого состояния.

Import

Статическое раскрытие reusable задач/ролей/plays. Унаследованное условие может проверяться каждой подставленной задачей.

Include

Динамический runtime-вход в reusable задачи/роль. Условие входа не тождественно автоматически условию каждой дочерней задачи.

Role

Роль: структура связанных задач, defaults, handlers, files/templates и metadata с публичным интерфейсом входов.

Collection

Именованная поставка модулей, плагинов и ролей namespace.name с собственной версией и совместимостью core.

FQCN

Fully qualified collection name — полное имя объекта namespace.collection.object, уменьшающее неоднозначность разрешения коротких имён.

Tags

Метки отбора задач при запуске. Не создают граф обязательных зависимостей и не гарантируют подготовку пропущенной фазы.

Block

Группа задач с наследуемым контекстом и секциями rescue/always. Не является распределённой транзакцией.

Rescue

Ветка обработки обычного failed внутри block. Не гарантируется при unreachable, синтаксической ошибке или исчезновении controller.

Serial

Размер batch узлов, проходящих play прежде следующей группы. Отличается от предела workers forks.

Batch

Текущая группа участников play при serial. run_once может выполняться заново в каждом batch.

Forks

Предел рабочих процессов controller для параллельных действий. Не заменяет измерение CPU/RAM/network и не снимает внешние блокировки.

Strategy

Правило продвижения готовых задач по hosts. Linear использует границы задач, free позволяет host продвигаться независимо.

Throttle

Локальное ограничение параллельности задачи/блока; остаётся под общими ограничениями forks и batch.

Delegation

Выполнение действия через другой узел при сохранении исходной host-идентичности задачи. Не сериализует общий ресурс автоматически.

run_once

Выполнить задачу на одном участнике текущего batch с соответствующим распространением результата. Не обещает один запуск на весь serial play.

Check mode

Прогноз поддерживающих actions без обычной записи. Не моделирует всю будущую ОС и не изолирует чужой код от побочных эффектов.

Diff mode

Запрос сравнения до/после у поддерживающего action. Сам по себе не отключает реальное изменение и способен раскрыть секреты.

Vault

Средство шифрования файлов/переменных в сохранённом виде. После расшифрования вывод, память и конечные файлы требуют отдельной защиты.

no_log

Keyword сокрытия чувствительного результата задачи в предусмотренных каналах вывода Ansible. Не стирает секрет из приложения, файлов и сторонних журналов.

Pipelining

Способ сократить ряд передач/temporary files при исполнении поддерживаемых модулей через канал интерпретатора. Не отменяет всё файловое/сетевое действие.

ControlPersist

Механизм OpenSSH сохранения управляющего соединения для последующих сессий. Меняет стоимость тёплого SSH относительно холодного.

JSON

JavaScript Object Notation — структурированный текст объектов, массивов и скаляров. Модули используют его для ответа, сервис — для конфигурации/API.

CLI

Command-line interface — командный интерфейс программы. Обычная CLI-опция и extra variable имеют разные категории приоритета.

API

Application programming interface — договор программного взаимодействия. Удалённый ресурс может иметь свои ошибки, лимиты и права независимо от Ansible.

HTTP

Hypertext Transfer Protocol — протокол запросов и ответов; в примере используется для чтения версии и состояния Go-сервиса.

VM

Virtual machine — виртуальная машина, отдельная гостевая ОС. Два local aliases одной ОС не являются двумя VM.

Fixture

Контролируемый тестовый образец данных/состояния с известными ожиданиями. Не означает, что сетевой стенд был действительно развёрнут.

Runtime

Среда исполнения программы: интерпретатор/бинарник и нужные зависимости. Версии controller и target runtime могут различаться.

Payload

Пакет данных/кода, подготовленный для передачи и исполнения. В механике Ansible это не всегда один и тот же постоянный файл.

Bootstrap

Начальная подготовка минимальных зависимостей, например Python/пользователя VM, прежде обычной конфигурации модулями.

Health check

Проверка выбранного свойства работоспособности. Живой HTTP-handler, ожидаемая версия, сеть и сохранение данных — разные свойства.

Drift

Дрейф — расхождение наблюдаемого состояния с желаемым после внешнего изменения. Перед устранением определяют владельца и ценность изменения.

Manifest

Манифест происхождения/идентичности выпуска: версия, байты, checksum, платформа, исходники и параметры сборки. Сам требует доверенного хранения.

SHA-256

Криптографическая контрольная сумма байтов. Совпадение с доверенной ожидаемой суммой проверяет целостность, но не само по себе добросовестность автора.

Provenance

Проверяемые сведения о происхождении поставки/артефакта. Отсутствующую аттестацию нельзя заменить обещанием, что хеш является подписью.

Symlink

Символическая ссылка файловой системы на другой путь. Переключение current меняет выбор бинарника, но не автоматически работающий процесс.

RSS

Resident set size — объём резидентных страниц процесса в памяти. Не равен только Python heap, требует осторожности при shared pages.

Latency

Задержка одного действия/ответа. Отличается от throughput — объёма работы за единицу времени.

p95

Квантиль 95-го процентиля: примерно 95% наблюдений не больше него в заданной выборке/модели. Малое число запусков даёт неустойчивую оценку хвоста.

Wall time

Длительность по часам от начала до конца, включая ожидание. Не равна сумме CPU seconds параллельных процессов.

CPU

Central processing unit — центральный процессор. CPU seconds измеряют использованную процессорную работу, wall time также включает ожидание.

RAM

Random-access memory — оперативная память. Рост числа workers может увеличить память controller и привести к вытеснению/ошибкам вместо ускорения.

ICMP

Internet Control Message Protocol — протокол служебных сообщений IP. Ansible ping исполняет модуль и не является ICMP echo.

TCP

Transmission Control Protocol — транспорт над IP с упорядоченным потоком байтов. SSH обычно использует TCP, но успешный TCP-connect не доказывает аутентификацию и исполнение модуля.

UTF-8

Кодировка Unicode переменной длины для представления текста байтами. Смена представления/newline меняет точный checksum файла.
