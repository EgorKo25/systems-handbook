POSTGRESQL: АВТОНОМНЫЕ ОПЫТЫ

Эти файлы не используют рабочую базу ДО и не устанавливают системные службы.

1. Без работающего PostgreSQL

  python3 inspect-storage.py --bundled

Читаются только приложенные файлы observed/page-0.bin, wal-insert.bin и
wal-commit.bin. Проверяются размеры, границы и CRC32C записей WAL.
Разбор относится к реальной little-endian сборке PostgreSQL 18.6.
Это не универсальный читатель всех сегментов и всех версий формата.

В общей сборке учебника дополнительно добавляется каталог byte-check:

  python3 byte-check/byte-check.py --demo

Он независимо проверяет также 16-битную контрольную сумму страницы по
исходному алгоритму PostgreSQL. См. byte-check/README.txt.

2. Настоящий частный кластер

  python3 postgres-lab.py --help
  python3 postgres-lab.py --run --pg-bin /абсолютный/путь/PostgreSQL18/bin --keep

Нужен обычный пользователь Linux/Unix, Python 3, подготовленная установка
PostgreSQL 18 с postgres, initdb, pg_ctl, psql, pg_dump, pg_restore,
pg_basebackup, pg_waldump и расширением pageinspect той же сборки.
pg_verifybackup используется, если присутствует.

Серверные бинарники не включены в этот набор: они зависят от платформы
и библиотек. Исследовать сохранённые результаты можно без них.

Без --run программа показывает справку и ничего не создаёт.
Кластер создаётся в новом /tmp/pgbook-..., TCP отключён.
Используются только собственные Unix-сокеты и собственные базы.
Перед завершением программа пытается остановить все учтённые ею экземпляры
через pg_ctl stop с ожиданием результата. Каталог удаляется только после
успешных опытов и подтверждённой остановки каждого экземпляра, если нет --keep.
С --keep успешно остановленные файлы и результаты остаются для следующего
просмотра; повторный запуск программы создаёт другой новый каталог.

Ошибка опыта или подготовки сохраняет каталог независимо от --keep.
Если pg_ctl stop завершился с ошибкой, не был найден или истекло время ожидания,
остановка не подтверждена: программа сообщает об отказе, возвращает ненулевой
код и не удаляет данные, сокеты, серверные журналы и results.json. Если отчёт удаётся записать, в results.json
добавляются незавершённые остановки и их ошибки. Программа пытается
остановить остальные собственные экземпляры, но не называет проблемный сервер
остановленным. Ненулевой результат сам по себе не доказывает ни работу, ни
отсутствие сервера. Не удаляйте этот каталог и не запускайте поверх него initdb:
сохраните напечатанную диагностику и исследуйте только указанный собственный
экземпляр штатными средствами PostgreSQL. Полное успешное завершение печатается
после очистки. Отказ записи results.json тоже запрещает удаление каталога;
если ошибка возникла уже при удалении остановленного стенда, сохраняется
оставшаяся часть каталога и сообщается ненулевой результат.

Правила ожидания и таймаута pg_ctl 18:
https://www.postgresql.org/docs/18/app-pg-ctl.html
После таймаута операция может ещё завершиться в фоне; каталог сохраняется,
пока состояние не установлено. Этот пример не повышает права и не останавливает
системную службу PostgreSQL.

Для чтения состояния выберите тот же bin из --pg-bin и точный путь из
cleanup.stop_errors[].data_directory в results.json. В следующем примере
обе строки — места для ваших значений, их нельзя выполнять без замены:

  PG_BIN='/абсолютный/путь/PostgreSQL18/bin'
  LAB_DATA='/tmp/pgbook-ВАШЕ-ИМЯ/data'
  "$PG_BIN/pg_ctl" -D "$LAB_DATA" status

status не удаляет файлы: код 0 означает найденный работающий сервер, 3 — сервер
не работает, 4 — нет доступного подходящего каталога. Это отдельная диагностика;
автоматического перехода к удалению нет. Журналы server*.log и results.json
остаются в напечатанном корне стенда. Повтор --run создаёт новый мир, а не
продолжает прежние 16 опытов; сохранённый мир используют для осмотра и
осознанных отдельных действий, не для повторного initdb поверх его данных.

16 проверок: NULL; ограничения/ROLLBACK; JOIN/окна; каталоги; роли/RLS;
RR-снимок; RC-снимки; SSI/40001; lock_timeout/55P03; deadlock/40P01;
VACUUM/ctid; EXPLAIN; страница; WAL; pg_dump/restore;
pg_basebackup/pg_verifybackup/PITR/аварийный перезапуск.

3. Сохранённые наблюдения

observed/results.json          Настоящий запуск всех 16 опытов: PASS.
observed/page-0.bin            Страница 8192 байта собственной таблицы.
observed/page-header.json      Поля, подтверждённые pageinspect и чтением файла.
observed/wal-records.txt       Настоящий вывод pg_waldump.
observed/wal-insert.bin        Собранная запись WAL INSERT, 194 байта.
observed/wal-commit.bin        Собранная запись WAL COMMIT, 34 байта.
observed/wal-crc-verification.json  Независимая проверка двух CRC32C.
observed/decoded-storage.json  Вывод приложенного читающего декодера.
observed/explain.json          Настоящий план с ANALYZE/BUFFERS.
observed/aio-settings.txt      SHOW/pg_stat_io отдельного собственного кластера.
observed/btree-pages.txt       Настоящие bt_metap и bt_page_stats.
observed/restore-server.log    Достижение именованной точки восстановления.
observed/server-after-crash.log  Аварийное восстановление после immediate stop.

LSN, OID, PID, время и план относятся к конкретному запуску и могут отличаться.
Все проверки проводились на PostgreSQL 18.6. PostgreSQL 11/Astra в опытах не
запускался; различия описаны в тексте и требуют проверки конкретной поставки.

4. Проверка отказа очистки без PostgreSQL

Из этого каталога labs, рядом с postgres-lab.py:

  python3 -B test_cleanup.py

Это 13 проверок управляющего кода. Они используют только собственные временные
файлы и подставной pg_ctl, в том числе отказ с кодом 7. Настоящий сервер не
запускается; модель не доказывает остановку PostgreSQL на вашей машине.

Дополнительно: python3 -I -B test_experiment_errors.py — 10 проверок
сохранения первичной ошибки, когда запись отчёта тоже завершается отказом.
Они используют собственные временные файлы и модель управляющего кода;
PostgreSQL не запускается. Обе проверки запускаются при публикации книги.
