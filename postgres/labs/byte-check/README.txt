ПОБАЙТОВАЯ ПРОВЕРКА СТРАНИЦЫ И ДВУХ ЗАПИСЕЙ WAL

Для запуска нужен только Python 3. PostgreSQL и сеть не нужны.
Из каталога этого файла:

    python3 byte-check.py --demo

Программа только читает три приложенных файла. Для каждого она выводит
сохранённую и вычисленную суммы, а затем сумму копии с изменённым битом.
Исходный файл при таком сравнении остаётся прежним.

Образы получены на собственном изолированном кластере PostgreSQL 18.6,
x86-64, little-endian. Это учебные значения (1, abc), (2, def), затем
вставка (3, wal-visible). Номера транзакций и LSN относятся к этому запуску.

1. СТРАНИЦА

page-0.bin содержит ровно 8192 байта нулевого блока обычной таблицы.
Поле pd_checksum занимает байты 8 и 9. Оно было записано при CHECKPOINT.
Для расчёта его временно обнуляют в копии, чтобы результат не зависел
от прежней суммы. Для страницы используется номер блока 0.

Алгоритм хранит 32 накопителя, начальные значения BASE взяты из
checksum_impl.h PostgreSQL. Каждая группа из 32 четырёхбайтовых слов
обновляет все накопители. За 64 прохода участвует вся страница:
32 × 4 × 64 = 8192 байта. Для каждого накопителя:

    t = старый_накопитель XOR очередное_слово
    новый = ((t × 16777619) XOR (t >> 17)) mod 2^32

Затем выполняются ещё два прохода с нулевыми словами. Все накопители
объединяются XOR, примешивается номер блока, результат сокращается:

    checksum16 = (значение mod 65535) + 1

Ноль намеренно исключён. Номер блока позволяет обнаруживать часть
ошибок, когда правильные байты попали на другое место. 16-битная сумма
имеет ограниченное число вариантов и возможные совпадения; по ней
проверяют повреждение блока, а прикладные ограничения проверяет SQL.

В приложенном образе сохранено 29693. Независимый расчёт Python даёт
29693; исходная C-функция pg_checksum_page из версии 18.6 тоже дала
29693. Изменение младшего бита байта 128 даёт 33583 обоими способами.

2. WAL

wal-insert.bin содержит одну собранную запись длиной 194 байта,
начало 0/1CB1438. wal-commit.bin содержит запись COMMIT длиной
34 байта, начало 0/1CB1500. Внутри этих образов нет заголовков
страниц WAL: обе реальные записи не пересекали границу страницы.
Целый сегмент WAL требует отдельного обхода страниц и продолжений.

Фиксированный заголовок записи занимает 24 байта. CRC32C лежит
по смещению 20, длина 4. CRC означает циклический избыточный код;
суффикс C обозначает вариант с полиномом Кастаньоли. В побитовой
отражённой реализации используется константа 0x82F63B78.

Начальный накопитель — 0xffffffff. Каждый байт складывается с ним
через XOR, затем восемь раз выполняются сдвиг вправо и условный XOR
с полиномом, если вытесненный младший бит равен 1. В конце накопитель
инвертируется через XOR с 0xffffffff. Переполнение обычного знакового
целого здесь не является частью формата: код явно работает с битами.

Порядок подачи байтов именно этой проверки PostgreSQL:
сначала всё после фиксированного заголовка (начиная с 24), затем
байты заголовка 0…19. Два байта выравнивания 18 и 19 включены;
само поле CRC 20…23 исключено. Заголовки страниц WAL исключены,
а описания блоков, сохранённый образ и данные операции включены.

Результаты:
INSERT: 0xdb1a13de; при изменении младшего бита последнего байта 0xd6106e33.
COMMIT: 0x2f90e23e; при таком изменении 0x229a9fd3.

3. КАК ПРОСЛЕДИТЬ ЭТО В КНИГЕ

Глава о хранении показывает все поля страницы и обеих версий строк.
Глава о WAL показывает каждое поле двух записей. Нажимайте на байт,
сопоставляйте смещение с Python-распаковкой и проверяйте длины.
Заголовок страницы таблицы хранит LSN двумя 32-битными половинами
(сначала старшая), а xl_prev записи WAL — обычным 64-битным значением.
Совпадающая длина полей не делает их двоичную раскладку одинаковой.
