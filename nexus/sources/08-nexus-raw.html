Raw: проверяемый Go-бинарник, manifest и download

Готовая программа передаётся как набор точных файлов, а не как исходный module proxy

Продолжаем тот же стенд: ledger уже опубликован, в собственной копии labs/service выполнены tidy/test/verify с окружением главы клиента. Администратор в Repository → Repositories создаёт raw-candidates и raw-releases типа Raw Hosted, выбирает существующий lab-hosted и запрет повторной записи release paths, если поле доступно выбранному recipe. После сохранения добавляет к ролям именно этих repositories права из главы доступа: ci-publisher пишет candidates, release-verifier читает candidates, release-promoter читает candidates и пишет releases, reader читает releases. Начните с пустых repositories; подстановка admin вместо недостающей роли не проверяет эту подготовку.

Команды сборки ниже выполняются в cd "$lab_root/labs/service" в том же выделенном терминале. Путь dist относится к этой рабочей копии. Go и системные CA уже подготовлены; дистрибутив Nexus не содержит компилятор вашей программы.

Почему нужны и модуль, и бинарник

Go hosted отдаёт исходники для toolchain клиента. Raw hosted хранит произвольно организованные файлы и подходит для готовой программы, checksums и manifest, описания выпуска. Он не интерпретирует go.mod как Go proxy и не создаёт @v endpoints из обычной загрузки файла. Если эксплуатационной машине нужен один заранее проверенный pulse, ей не обязательно иметь компилятор. Но тогда выпуск обязан явно указать платформу, версию, размер и идентичность программы.

mkdir -p dist
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -buildvcs=false \
  -ldflags='-X main.version=1.0.0' \
  -o dist/pulse-linux-amd64 ./cmd/pulse
go version -m dist/pulse-linux-amd64
sha256sum dist/pulse-linux-amd64

GOOS/GOARCH выбирают целевую ОС/архитектуру; кросс-собранный Linux ELF не запускается автоматически на Windows. CGO_ENABLED=0 исключает cgo в поддерживаемых пакетах, но не обещает совместимость с любой средой или отсутствие зависимостей вроде CA/DNS. -trimpath убирает выбранные пути исходников из build output; -buildvcs=false выключает автоматическую VCS stamp, поэтому исходный commit надо сохранить в manifest отдельным доверенным полем. Без trimpath личные пути могут попасть в артефакт. -X main.version=1.0.0 меняет строковую переменную main.version при линковке; это не версия модуля ledger.

Сравните сборку с -ldflags='-X main.version=1.0.0' и без него в разных файлах: pulse -version покажет 1.0.0 против development. Изменяется программа, поэтому хеши отличаются. Утверждение о reproducible build, воспроизводимой сборке, требует одинаковых существенных входов, toolchain и флагов и отдельного повторного опыта. Одного совпадения version string недостаточно. В нашем локальном тесте бинарник собирался и запускался как Linux/amd64; перенос на другую платформу не проверялся.

Структура выпуска и неизменяемый путь

В raw-candidates используем путь pulse/1.0.0/linux-amd64/ с тремя файлами: pulse-linux-amd64, manifest.json, SHA256SUMS. Manifest содержит schema, version, file, size_bytes, sha256, toolchain, source_module, target и версии module inputs. В реальном процессе добавляют commit и идентификатор доверенного CI build. Поля не должны притворяться выполненной проверкой: нет commit — значит нет заявления о конкретном commit. Локальный fixture сохраняет только известные ему сведения.

Сначала создайте все три локальных файла. После сборки из labs/service вернитесь в рабочий корень и выполните:

cd "$lab_root" || exit
python3 labs/artifacts.py manifest --binary labs/service/dist/pulse-linux-amd64 \
  --version 1.0.0 --toolchain "$(go version)" --input-version v1.0.0 \
  --output labs/service/dist/manifest.json || exit
(cd labs/service/dist && sha256sum pulse-linux-amd64 > SHA256SUMS) || exit
python3 labs/artifacts.py verify --manifest labs/service/dist/manifest.json \
  --directory labs/service/dist || exit
cd "$lab_root/labs/service" || exit

Выполняйте следующий шаг только при успехе предыдущего. Manifest output создаётся как новый файл; существующий manifest не перезаписывается. При повторном занятии сначала проверьте уже сохранённый комплект. Для нового build используйте отдельный каталог и новый version path. Флаг --input-version сообщает известную вам выбранную версию ledger; helper не читает module graph из бинарника. Поля source_module и target заданы для нашего опыта, а --toolchain сохраняет переданную строку. До утверждения происхождения сопоставьте их с go version -m и реально выполненной командой сборки. Чтение этих строк из JSON само не проверяет платформу или процесс сборки.

curl --fail-with-body --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/publisher.netrc" \
  --upload-file dist/pulse-linux-amd64 \
  https://nexus.lab.example/repository/raw-candidates/pulse/1.0.0/linux-amd64/pulse-linux-amd64
curl --fail-with-body --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/publisher.netrc" \
  --upload-file dist/manifest.json \
  https://nexus.lab.example/repository/raw-candidates/pulse/1.0.0/linux-amd64/manifest.json

Аналогично передаётся SHA256SUMS. Это отдельные HTTP-операции, не атомарная публикация целого каталога. Чтобы consumer не увидел половину release, сначала загружают файлы, затем проверяют их чтение отдельной ролью и лишь последним шагом обновляют доверенный release record/указатель, или публикуют единый проверяемый архив. В учебной схеме version path считается доступным к продвижению только после проверки полного списка. Не используйте latest как единственное имя результата.

Адрес raw-releases в следующем запросе станет доступен после продвижения главы 11. Сейчас создан только candidate: его читает release-verifier из raw-candidates с собственным файлом учётных данных. Не открывайте candidates обычному reader ради предварительного GET и не считайте ожидаемое отсутствие ещё не выпущенного 1.0.0 неисправностью хранения.

Загрузка до исполнения

curl --fail --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/reader.netrc" --output downloaded-pulse \
  https://nexus.lab.example/repository/raw-releases/pulse/1.0.0/linux-amd64/pulse-linux-amd64
sha256sum downloaded-pulse

Полученный файл сначала проверяется, затем получает executable bit и запускается в нужной среде. Имя в checksum list должно соответствовать локальному имени либо проверка явно сопоставляет их; переименование в downloaded-pulse не делает строку pulse-linux-amd64 подходящей для слепого sha256sum -c. Manifest из того же неподтверждённого источника обнаруживает случайную порчу, но не доказывает происхождение, если атакующий способен заменить оба файла. Доверенный подписанный manifest, контролируемый CI record и право публикации создают опору ожидаемого хеша.

Учебный artifacts.py verify ограничивает имя basename, запрещает symlink и требует обычный файл, затем сравнивает размер и SHA-256. Это ограниченный проверяющий инструмент, не sandbox для исполнения недоверенной программы. Он не реализует защиту от гонки между проверкой и запуском в каталоге, изменяемом другим писателем. Для установки используют каталог, закрытый на запись посторонним, и атомарное продвижение проверенного файла. В тесте проверяется порча с сохранённым размером, чтобы доказать необходимость хеша сверх размера.

Удаление — действие API, не rm в blobs

Для ошибочного тестового кандидата сначала получите точный asset ID через search/assets и сверните pagination. Затем API выбранной версии допускает DELETE /service/rest/v1/assets/{id}. Удаляющая роль отделена от publisher; dry-run для произвольного DELETE не предполагается. Сначала сравните repository, path, ожидаемую сумму и связь с release record. Удаление component может затронуть несколько assets, поэтому его scope проверяют отдельно. Выпущенный релиз удаляется только по принятой retention-политике; учебная неисправность не оправдывает удаление истории.
