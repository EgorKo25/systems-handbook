Контейнерный registry: tag, digest и публикация образа

OCI расширяет модель артефактов, но не превращает любую загрузку в образ

Какой формат выбран

В CE 3.97.3 доступны Docker repositories и новый native OCI recipe, появившийся в 3.94. OCI, Open Container Initiative — открытые спецификации образов и их распределения. Для нового учебного oci-internal используем OCI hosted и path-based routing; не подменяем его Docker recipe с connector port и не переносим все настройки между ними. По OCI Repositories поддерживаются hosted/proxy/group. Точная пригодность клиентов, referrers и форматов подписей требует приёмки выбранных версий.

Registry хранит manifest, документ ссылок на config и layers; layer, слой содержимого файловой системы; image index, список платформенных manifest. Digest идентифицирует точные байты соответствующего объекта, например sha256:... манифеста. Tag — изменяемое имя, ссылающееся на manifest/index. Digest одного слоя, SHA-256 raw-бинарника и digest multi-platform index относятся к разным байтам и не должны подставляться друг вместо друга.

Путь registry отличается от raw

Для path-based OCI адрес клиента имеет вид nexus.lab.example/oci-internal/team/pulse:1.0.0; сегмент /repository/ в имени образа не добавляется. Клиент registry использует API /v2/ с маршрутизацией Nexus. Для OCI активируется OCI Bearer Token Realm; для старого Docker recipe — Docker Bearer Token Realm. Realm, источник и способ установления личности, выбирается согласно формату. Успешный login ещё не доказывает push scope к нужному namespace. Subdomain routing имеет отдельное Pro entitlement, право редакции; оно не предполагается у CE.

docker login nexus.lab.example --username ci-pulse --password-stdin
docker tag pulse:1.0.0 nexus.lab.example/oci-internal/team/pulse:1.0.0
docker push nexus.lab.example/oci-internal/team/pulse:1.0.0
docker pull nexus.lab.example/oci-internal/team/pulse@sha256:EXPECTED_MANIFEST_DIGEST

Это рецепт для подготовленного личного Docker-клиента, образа и Nexus, не выполненный авторский тест. --password-stdin читает credential из защищённого входа/менеджера секретов, а не хранит его в аргументе; сама команда без поданного stdin ожидает ввод. tag создаёт локальное имя, не загружает слой. push передаёт нужные blobs, затем manifest/tag, поэтому возможен частичный эффект до финального подтверждения. Последний digest — placeholder, его заменяют реальным проверенным значением из результата и чтения registry. Строку с EXPECTED нельзя выдавать за запускаемую успешную команду.

Ни Docker daemon, ни registry здесь не устанавливались. Чтобы собрать контейнер для собственного pulse, сначала приготовьте доверенный базовый image по digest либо подходящий минимальный runtime contract, положите тот же проверенный бинарник и нужные runtime-данные. Сборка image меняет контейнерный manifest; это отдельный release object со своей проверкой. Raw checksum бинарника остаётся полезным входом provenance, сведений о происхождении, но не заменяет image digest.

Bearer challenge не равен anonymous allow

Клиент обращается к /v2/, получает challenge, узнаёт token service и scope, затем предъявляет credential, получает ограниченный токен и повторяет запрос. Поэтому 401 на первом registry probe может быть нормальной частью протокола; окончательный неуспех после credential — другое состояние. Reverse proxy обязан сохранить challenge и внешние адреса. Если token service указывает внутренний localhost, внешний клиент не сможет завершить обмен, даже когда UI открывается по HTTPS.

Для anonymous pull недостаточно снять флажок password requirement в произвольном месте: нужна согласованная анонимная личность, read scope и правильный realm. Проверяйте новый клиент без сохранённого login отдельно от служебного издателя. Content selector для image namespace должен учитывать служебные пути manifest/layers и базовый /v2/; правило для одного красивого tag URL может ломать push. Исправление 3.97.3 касается Docker push с одними selector permissions, поэтому перенос на старую версию требует отдельной сверки.

Чем измерять и что сохранять

Registry часто передаёт уже существующие слои только однажды. Request hit ratio и byte hit ratio снова различаются. Для образа 200 MiB со слоем приложения 12 MiB изменение одного слоя может передать около 12 MiB плюс metadata при общих сохранённых остальных слоях; это условный пример, не обещание точного сетевого объёма из-за сжатия, платформ и повторов. Для promotion записывайте digest исходного и целевого manifest, platform и список referrers. Копирование между registry инструментом может перекодировать manifest; совпадение tag не доказывает совпадения digest.
