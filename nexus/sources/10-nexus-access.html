Личность, роль и граница публикации

Разрешения складываются; второй узкий grant не отменяет первый широкий

Authentication раньше authorization

Authentication, аутентификация, устанавливает, кто обращается: локальный user, внешний каталог или токен поддержанного realm. Authorization, авторизация, решает, разрешено ли этой личности действие над данным ресурсом. Realm — подключаемый источник/механизм аутентификации, а не роль. Role — набор privileges, элементарных разрешений; privilege содержит формат, repository, действие либо другую область управления. Включение LDAP realm не наделяет всех пользователей правом публиковать.

В нашем CE стенде остаются Local Authenticating Realm и обычные локальные users для администратора, reader, ci-publisher, release-verifier и release-promoter. Служебная учётная запись — отдельный local user, используемый автоматизацией, а не общий admin-пароль. Нативные Service Account Tokens sat.* 3.97 — отдельная функция: официальная страница маркирует её Pro/Pro+/Cloud. Расширение поддержки всех форматов в notes не означает доступность SAT в выбранной CE. User Token Realm тоже имеет редакционные ограничения. Для CE рецепт использует узкий local user, защищённый secret store CI и ротацию пароля.

Не удаляйте все активные realms и сохраняйте аварийную локальную административную личность. Имя, совпадающее в локальном и внешнем источнике, требует проверки порядка realm. Изменение внешнего group mapping может менять эффективные роли после обновления сессий/кэшей. Проверяйте действия новой отдельной сессией, а не только открытой вкладкой admin, которая скрывает недостаток полномочий будущего клиента.

Названия встроенных привилегий вида nx-repository-view-raw-raw-candidates-add, ...-edit, ...-read, ...-browse, ...-delete генерируются для формата/репозитория. Внутренний permission string разделяется двоеточиями, например nexus:repository-view:raw:raw-candidates:read; это другой синтаксис представления. Не выдавайте nx-all только потому, что первый PUT получил 403. Формат может требовать сочетания add/edit из-за метода/обновления metadata: сначала выясните необходимый набор по точному запросу и минимальному позитивному тесту.

Privileges дают разрешения аддитивно. Если одна роль даёт raw:*, другая с selector только /pulse/ не сужает первую. Сначала удаляют избыточный общий grant, затем проверяют положительный и отрицательный пути. Удобная человеческая метка «read-only» не имеет силы, если вложенная роль содержит delete. Периодический review должен раскрывать весь effective набор, включая inherited и default roles.

Content selector ограничивает адресуемую область

Content selector — выражение отбора содержимого, которое связывается с отдельной privilege, а затем ролью. Для raw кандидатов разумный базовый CSEL, content selector expression language — язык условий отбора, имеет вид format == "raw" and path =^ "/pulse/". =^ означает prefix; path включает ведущий слеш. Префикс /pulse/ не совпадает с /pulsex/, в отличие от небрежного /pulse. Для Go basic support поддерживает format/path, не выдуманные go.team поля.

Selector — не автоматическое понимание всего формата. List/metadata/ZIP могут иметь разные пути, upload Go идёт на /v1.0.0.zip, а координата модуля извлекается из тела. Поэтому selector по красивому пути module download нельзя объявить доказанной защитой Go upload namespace без испытания точной версии. Для этого учебного publisher выбран отдельный go-internal repository; строгую многокомандную namespace-публикацию проектируют после негативного теста чужого модуля. Regex, regular expression — регулярное выражение, полезно только когда prefix недостаточен; сложные вложенные повторения могут дороже выполнять запросы и осложняют review.

Anonymous и group расширяют аудиторию

Если анонимное чтение включено, anonymous user получает конкретные роли. Широкая роль read всех repositories открывает и будущие hosted, если её wildcard охватит их. Начните с отключённого anonymous; для намеренно открытого public cache дайте только выбранный endpoint. Права на go-all открывают содержимое member через group. Reader может получить internal module через group без прямого read go-internal; это штатная семантика, а не доказательство обхода. Нельзя включать закрытый repository в общедоступную группу без review.

Позитивные/негативные тесты выполняйте credential каждой роли: GET known release, PUT нового кандидата, PUT чужого пути, GET кандидата reader, DELETE точного тестового asset publisher. Предварительно пометьте одноразовые данные и сохраните резерв. Ожидаемый отказ проверяют по отсутствию эффекта и по ответу; только HTTP-код недостаточен, если передний прокси переписал ошибку. Запросы без credential и с неверным credential — разные тесты; anonymous fallback иногда меняет наблюдаемый результат.

Upstream credentials и следы утечки

Учётные данные Nexus→upstream задаются у proxy/HTTP client и не должны уходить Go-клиентам. Это отдельный secret с разрешением чтения upstream. Не пересылайте входной Authorization пользователя на произвольный remote. Redirect на другой host, access logs, trace HTTP, support ZIP и CI artifacts могут расширить аудиторию секрета. Маскирование в UI не предотвращает код job, который прочитал и отправил пароль. Ротация включает изменение секрета, обновление клиентов, проверку новой личности и отзыв старого значения, а не лишь переименование файла.

Аудит, audit — сохранённая история действий, должен отвечать кто/что/когда/где с ограничением доступа и сроком. Request log не всегда содержит прикладной результат; audit событие не всегда означает доступные байты. В 3.97.1+ persistence audit events по умолчанию выключена по notes ветки, поэтому нельзя обещать существование полной таблицы аудита без настройки. Проверьте фактический output и retention.
