Hosted, proxy и group на пути реального запроса

Кэширование имеет состояние, срок и причины отказа

Три роли repository

Hosted принимает ваши публикации и является источником этих версий. Proxy обращается к настроенному remote storage, внешнему upstream, и сохраняет полученное для повторного чтения. Group даёт клиенту один endpoint перед упорядоченными участниками. Эти роли не означают три независимые полные копии пакетов: group маршрутизирует и может формировать форматные metadata, а участники сохраняют своё содержимое. Публикация Go в нашем стенде идёт прямо в hosted go-internal, получение — через go-all. Нельзя предполагать, что любой group принимает upload или автоматически выбирает куда его записать.

Создать хранилища до выбора repository

У администратора откройте Settings → Blob Stores в Nexus One UI либо Settings → Repository → Blob Stores в Classic UI. Создайте два объекта типа File: lab-hosted с абсолютным Path /srv/nexus-data/blobs/lab-hosted и lab-cache с Path /srv/nexus-data/blobs/lab-cache. Родитель доступен пользователю nexus; каталог не занят другим blob store. После сохранения проверьте показанные Path и State, затем запишите их. Такой выбор держит оба учебных хранилища внутри data-dir и определяет охват резервного копирования. Если вы выбрали внешний Path, резерв data-dir его не охватывает.

Имя в форме repository выбирает уже созданный blob store. Оно не создаёт отдельный диск и не резервирует ёмкость. Soft Quota — порог предупреждения: при его превышении хранилище само не прекращает запись. Поэтому кроме предупреждения нужно наблюдать свободное место файловой системы. Не переименовывайте каталоги после создания, пытаясь таким способом перенести хранилище. Поля и создание Blob Store сверены 2 ноября 2026.

Создайте go-public типа Go proxy с remote https://proxy.golang.org и blob store lab-cache; go-internal типа Go hosted с lab-hosted; go-all типа Go group с порядком internal, public. Это рецепт CE 3.97.3, подтверждённый доступностью Go. Форма настройки может отличаться в Nexus One UI и Classic UI. Сохраните экспорт конфигурации точной версии. Не подменяйте отсутствующий recipe generic raw.

Подготовить личности для следующих запросов

Аутентификация устанавливает имя обратившегося, а роль выдаёт ему набор разрешений. В Security → Roles администратор создаёт роли стенда, в Security → Users — отдельных local users и назначает им эти роли. Anonymous пока выключен. Для reader выдайте read/browse только go-all, позже добавьте raw-releases. Для ci-publisher — необходимые add/edit действия только go-internal, позже raw-candidates. Для release-verifier — только чтение candidates; для release-promoter — чтение candidates и запись releases. Привилегии raw добавляются после создания этих repositories в главе raw. Не выбирайте wildcard всех будущих репозиториев. Формат может требовать edit при PUT; минимальный рабочий набор сверяется положительной загрузкой и отказом чужого пути.

Имена пользователей и имена файлов отличаются: publisher.netrc хранит ci-publisher, reader.netrc — reader, verifier.netrc — release-verifier, promoter.netrc — release-promoter. На своём клиенте в рабочем корне создайте закрытый каталог lab-secrets с правами 0700. В частном редакторе создайте там отдельный файл каждой личности с правами 0600. Формат одного файла reader.netrc:

machine nexus.lab.example
login reader
password ЗАМЕНИТЬ_НА_ПАРОЛЬ_ЭТОГО_ПОЛЬЗОВАТЕЛЯ

Строка password выше — описание места под секрет, а не работающий пароль. Для этого простого netrc-примера используйте сгенерированный пароль без пробельных символов; возможные правила кавычек разных клиентов здесь не предполагаются. Host после machine должен точно соответствовать реальному HTTPS URL, без схемы, порта и пути. Секреты не добавляйте в Git, ZIP модуля, backup книги и публичный отчёт. Далее команда curl --netrc-file "$lab_root/lab-secrets/reader.netrc" ... явно выбирает reader; имя файла само не меняет роль на сервере. Подробный разбор привилегий и негативных проверок дан в главе доступа.

Промах и попадание

Чистый Go-клиент запрашивает известную версию публичного модуля через URL go-public. На cold miss сервер ещё не имеет asset: после авторизации он вызывает remote, проверяет TLS и форматный ответ, сохраняет байты/metadata и отвечает клиенту. На hit следующий запрос может получить сохранённое содержимое без повторной передачи всего файла upstream. Но hit не равен «никогда нет внешнего запроса»: возраст записи может потребовать revalidation, повторной проверки актуальности. Условный GET с ETag либо Last-Modified допускает ответ 304 без полного тела, если формат/remote это поддерживает.

У client cache и Nexus cache разные владельцы. Два последовательных go build в одной рабочей копии могут вообще не направить второй запрос в Nexus: Go уже имеет модуль в GOMODCACHE. Для измерения серверного hit нужен новый клиентский module cache с теми же координатами и уже тёплым Nexus. Для измерения miss нужны заранее выбранные ещё не кэшированные координаты либо отдельный proxy в копии стенда. Удаление общего production cache ради графика недопустимо.

Возраст содержимого и возраст знания

Maximum Component Age задаёт время до проверки изменения компонента, Maximum Metadata Age — знания о версиях/индексах. В интерфейсе значения в минутах: 1440 min = 24 h. -1 для component age отключает проверку redeploy, 0 требует проверять изменения при каждом запросе; для component metadata учитывается более долгий из этих сроков. Это поведение описано в Configurable Repository Fields; форматные особенности проверяют на выбранном recipe, а не переносят буквально с Maven snapshot на любой протокол.

Представим, что bytes версии immutable, неизменяемой, а список версий расширяется каждый час. Файл v1.0.0 может оставаться правильным годами, но @v/list устаревает через минуты. Уменьшение metadata age помогает увидеть v1.0.1 быстрее, ценой запросов upstream. Уменьшение component age для каждого неизменяемого ZIP может добавить сеть без пользы. Если upstream нарушает неизменяемость v1.0.0, обновлённый кэш уже не исправляет доверие: клиенты с go.sum должны отвергнуть другую сумму.

Negative cache хранит отсутствие

Negative cache — отрицательный кэш — запоминает, что ресурс отсутствовал. Клиент в 10:00 спросил v1.0.1 и получил 404; upstream опубликовал её в 10:02; Nexus может продолжать отвечать из отрицательного кэша до истечения TTL, time to live — срока жизни записи. Это не обязательно проблема роли и не обязательно DNS. Сравните прямой контролируемый запрос upstream и тот же путь через proxy, время первой ошибки, TTL и серверный журнал. При закрытых координатах не направляйте прямую проверку в публичный интернет.

Invalidate cache делает сохранённое знание просроченным для последующей проверки; это не удаление всех blob и не немедленное скачивание всего remote. Клиентский кэш тоже может сохранить прежнее знание, поэтому после invalidation эксперимент должен контролировать обе стороны. Отключение negative cache повышает частоту запросов к upstream при опечатках и может привести к rate limiting. Для быстро публикуемого собственного upstream разумнее отдельный измеренный TTL, например 2 min как условие лаборатории, а не универсальные ноль или сутки.

Group создаёт политику видимости

Если два hosted содержат одинаковый module path/version с разными байтами, порядок участников становится конфликтом доверия. «Внутренний раньше публичного» не является полной защитой от dependency confusion, подмены внутренней зависимости внешней: ошибочный внутренний 404 может отправить поиск дальше. Выделяйте собственный namespace, routing rules при поддержке и проверке формата, отдельный приватный путь без внешнего fallback и неизменяемые версии. Запрос приватной координаты не должен молча уходить публичному proxy.

Права на group позволяют читать содержимое участников через group, даже если прямой endpoint участника этой личности не разрешён. Состав group поэтому относится к политике доступа. Перед добавлением нового внутреннего member проверьте, кому открыт общий адрес. Отдельно проверьте 401/403 от upstream: credential Nexus→remote отличается от credential Go→Nexus, их нельзя лечить одним общим admin-паролем.

Эксперимент и единицы

Для 100 загрузок ZIP по 8 MiB соберите клиентскую duration, байты upstream, серверное время и HTTP-коды. Если miss медианно занимает 1.6 s, hit 0.12 s, а warm Go вообще не делает HTTP, это три разных опыта. Доля попаданий считается по определённым server requests, не по количеству команд build. При 80 hit и 20 miss request hit ratio равен 0.8; byte hit ratio может быть иным, если промахнулись самые большие файлы. Увеличение диска помогает удерживать полезный working set, набор часто читаемых объектов; оно не сокращает TLS handshake клиента при каждом соединении и не исправляет блокировку БД.
