Первая публикация собственного Go-модуля

ZIP становится форматными metadata; чистый клиент проверяет именно опубликованную координату

Публикуем исходники один раз

В go.mod ledger находится module path example.invalid/Acme/ledger. Вызов go test ./... в этом корне проверяет собственную функцию Message; внешних зависимостей нет. ./... — шаблон пакетов под текущим каталогом в рамках модульных границ; это не команда публикации. Тест утверждает предсказуемый результат функции, но не загружает пакет в Nexus и не доказывает доверие к серверу.

Сначала зафиксируйте исходный commit и toolchain в своём журнале. Упакуйте ровно те файлы, которые должны стать версией v1.0.0. Для этого малого проекта python3 labs/artifacts.py module --output ./lab-work/proxy создаёт воспроизводимый ZIP и статические протокольные fixtures. Путь архива получится lab-work/proxy/example.invalid/!acme/ledger/@v/v1.0.0.zip. Внутри — example.invalid/Acme/ledger@v1.0.0/go.mod, ledger.go и ledger_test.go. Не включаются credential, workspace cache и чужие каталоги.

Упаковщик использует allowlist, список разрешённых имён, только для этого учебного модуля. Для произвольного репозитория нужен проверенный инструмент на базе x/mod/zip: правила Go исключают некоторые служебные и вложенные области, запрещают неподдерживаемые имена и ограничивают размеры. Обычный zip -r . может захватить секреты, .git, symlinks и nested module и не гарантирует пригодности module ZIP. Перед публикацией смотрите listing и содержимое go.mod, а не только расширение файла.

Проверку исходника выполняйте в своём выделенном Go-терминале. Сначала cd "$lab_root/labs/module/ledger" и GOPROXY=off go test ./...; у этого модуля нет внешних зависимостей. Затем вернитесь в рабочий корень cd "$lab_root" и запустите упаковщик. Он читает только три обычных файла выбранного ledger, проверяет объявленный module path и создаёт новую числовую версию major 1. Это намеренно ограниченный формат опыта.

Именно Go hosted выбранной версии

Согласно Go CLI Usage, hosted upload доступен с 3.93, а Create a Go Repository описывает Go recipe. В CE 3.97.3 отправляем ZIP через PUT в /repository/go-internal/v1.0.0.zip. Серверный формат извлекает модульную идентичность и создаёт ответы протокола для клиента. Это не raw repository с вручную выложенным go.mod и не произвольный REST components multipart, поля которого нельзя переносить из Maven.

curl --fail-with-body --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/publisher.netrc" \
  --upload-file 'lab-work/proxy/example.invalid/!acme/ledger/@v/v1.0.0.zip' \
  --dump-header publish.headers \
  https://nexus.lab.example/repository/go-internal/v1.0.0.zip

--upload-file для HTTP выбирает PUT и передаёт файл; дополнительное -X PUT не нужно. --fail-with-body оставляет полезное тело HTTP-ошибки и возвращает ненулевой статус; это флаг curl 7.76+. Если ваша curl старее, выберите поддерживаемый --fail и отдельное контролируемое сохранение диагностики. Файл publisher.netrc хранит credential только издателя, с правами 0600. Не подставляйте пароль прямо в -u user:password в истории оболочки. При 401 проверьте аутентификацию, при 403 роль, при 404 имя/recipe/путь, при 4xx format validation — ZIP prefix, go.mod и версию; точный ответ запишите с серверной версией.

Официальная страница на дату проверки содержит в одном описании prefix знак &, тогда как протокол Go и примеры требуют @. Здесь осознанно выбран module@version/, и пригодность архива подтверждена реальным Go 1.27.3 на локальном HTTP-fixture. Это не подтверждение самого Nexus upload: серверный рецепт должен пройти отдельную приёмку. Наши источники и границы исполнения не скрывают это различие.

Приёмка с другого клиентского состояния

Через учётную запись reader скачайте .info/.mod/.zip по go-all и проверьте, что go.mod объявляет исходный module path. Создайте новую рабочую копию service из labs без replace и отдельный module cache. Команда go mod tidy должна получить ledger v1.0.0 через адрес Nexus, сформировать go.sum и не обратиться direct к example.invalid. Потом go test ./..., go mod verify и go build ./cmd/pulse подтверждают разные стадии: разрешение графа, тестирование, состояние cache и компиляцию.

Вернитесь в cd "$lab_root/labs/service". В том же терминале остаются exports из главы клиента, включая NETRC reader и проверенный CA. Для наблюдаемого первого получения выберите ещё не использованный модульный кэш:

export GOMODCACHE="$lab_root/lab-work/client-after-publish-mods"
go mod download -json example.invalid/Acme/ledger@v1.0.0 || exit
go mod tidy || exit
go test ./... || exit
go mod verify

GOMODCACHE здесь абсолютный путь внутри рабочей копии, полученный из lab_root; Go создаст нужную структуру с правами текущего клиента. При повторении используйте другой новый каталог, сохраняя известные go.mod/go.sum. Это меняет клиентский кэш, а не опубликованную версию. Не делайте go clean -modcache в общей личной среде ради опыта. Зафиксируйте request.log Nexus и суммы полученных файлов: новая директория даёт наблюдать передачу с сервера, а повтор в тёплой директории не доказывает server hit.

go mod tidy
go mod tidy -diff

Первый запуск изменяет рабочие go.mod/go.sum при необходимости. Второй на поддержанном Go показывает необходимые изменения без записи и возвращает проверочный отказ, если они нужны; после первого успешного tidy ожидается пустое изменение. Оба могут нуждаться в получении metadata. Это сравнение проверяет состояние описания зависимостей, не публикацию.

Выпускаем исправление без переписывания прошлого

Для исправления сделайте отдельную копию трёх исходных файлов в lab-work/ledger-v1.0.1, измените функцию и соответствующий тест и выполните в ней GOPROXY=off go test ./.... Module path остаётся прежним: patch-версия не добавляет /v2 к импорту. Из рабочего корня выполните python3 labs/artifacts.py module --source lab-work/ledger-v1.0.1 --version v1.0.1 --output lab-work/proxy. Новый ZIP будет .../@v/v1.0.1.zip с prefix example.invalid/Acme/ledger@v1.0.1/; старые .zip/.mod/.info v1.0.0 останутся прежними, а list будет содержать обе версии. Упаковщик отвергнет существующие файлы версии. Его фиксированное Time — учебная metadata, не время найденного Git-коммита. При ошибке записи возможен неполный новый набор: сохраните его для разбора и повторите в новом выходном каталоге, вместо перезаписи прошлого выпуска.

Проверьте ZIP новым локальным Go-клиентом, затем PUT той же формой, но с версией v1.0.1 и новым файлом. После публикации go get example.invalid/Acme/ledger@v1.0.1 в отдельной потребительской копии меняет go.mod/go.sum. Старая копия с require v1.0.0 должна сохранить прежние функцию и сумму. Если затем собираете службу, запишите реально выбранную версию ledger в manifest через --input-version; значение по умолчанию v1.0.0 не обнаруживает обновление автоматически.

Повторная публикация v1.0.0 другими байтами должна быть запрещена политикой Disable Redeploy, если она доступна для recipe, и правами publisher без лишнего edit/delete; фактическую семантику HTTP PUT проверяйте. Когда формат требует edit даже для первого PUT, нельзя механически убрать это право и объявить процесс работающим: ограничьте repository, путь и deployment policy, затем проведите позитивный/негативный тесты. Версионная неизменяемость — совместный договор сервера и процесса команды.
