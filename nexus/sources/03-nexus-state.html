Метаданные, component, asset и blob: где живёт выпуск

Один URL связывает логическую координату с физическими байтами

Четыре разных объекта

Coordinate, координата — идентичность в правилах конкретного формата. Для Go это module path и version, для Maven — groupId/artifactId/version с дополнительными типом и classifier, для raw — выбранный путь файла. Component, компонент — логическая единица формата, например версия модуля с несколькими файлами представления. Asset, ресурс — адресуемое содержимое, например v1.0.0.mod либо конкретный ZIP. Blob, двоичный объект — сохранённые байты с внутренней идентичностью хранилища. Один component не обязан соответствовать одному asset; количество HTTP-запросов тоже не равно количеству component.

При чтении .../ledger/@v/v1.0.0.zip сервер сначала выбирает repository и формат, проверяет доступ, разрешает логический путь и находит metadata asset. Запись связывает repository/path/форматные поля с blob reference — ссылкой на объект выбранного blob store. Затем хранилище возвращает поток байтов. В БД находятся метаданные и конфигурация, в blob store — содержимое. Это причинная модель уровня продукта; точные SQL table/column и layout bucket не являются публичным договором для ручного редактирования.

У файлового backend в data-dir видны служебные каталоги, файлы содержимого и свойств. Имена не следует трактовать как прямое отображение публичного URL. Файловый менеджер не знает транзакций Nexus, индексов и связей. Копирование ZIP непосредственно в папку blobs не публикует Go-модуль. Ручное удаление файла не выполняет корректное удаление asset и может оставить dangling reference, висячую ссылку из метаданных.

Например, логическая запись raw asset описывает repository raw-candidates, path pulse/1.0.0/linux-amd64/manifest.json, размер N bytes, checksum и непрозрачную ссылку B1 на содержимое. N считается по сохранённым байтам, а не по числу символов JSON: русская буква в UTF-8 может занимать больше одного байта. Другой asset pulse-linux-amd64 имеет свой размер, checksum и ссылку B2. Это пример связей, а не опубликованная SQL-схема Nexus: поле с именем B1 нельзя искать как файл blobs/B1. Когда GET находит metadata, но B2 утрачен, список может по-прежнему показывать выпуск, однако серверу нечем заполнить тело ответа. Обратная ситуация, B2 без metadata, оставляет байты на диске без доступного клиенту прежнего пути.

Как читать переходы. Сначала поддержанная операция удаления меняет состояние каталога; форматные задачи могут отдельно находить больше не нужные assets. На рисунке второй момент уже предполагает, что сам blob отмечен к удалению. Удаление одной ссылки само по себе этого не доказывает: например, у Docker/OCI надо учитывать связи manifests и слоёв. Для File backend физические байты убирает отдельное успешно выполненное Admin - Compact blob store выбранного хранилища, когда прошёл заданный период Blobs Older Than. Ноль убирает дополнительное окно ожидания, но не запускает задачу автоматически. Ни отсутствие URL, ни пропажа строки поиска не измеряют освобождённое место.

У этой схемы нет действия «восстановить»: мягкое удаление не заменяет проверенный резерв. Как подготовить согласованные метаданные и blobs, разобрано в главе о восстановлении, а выбор удаления и редакционные ограничения — в главе об очистке. Разделение lab-hosted и lab-cache даёт понятные политики ёмкости и резерва. Потерянный public proxy cache иногда можно заново наполнить из upstream; собственный единственный hosted release из интернета не вернётся. Но и кэш может содержать исчезнувшую публичную версию: «можно скачать снова» — предположение, которое проверяют условиями upstream. Разделение каталогов не обеспечивает резерв автоматически и не позволяет безусловно терять metadata.

Загрузка как несколько эффектов

Предположим CI отправил raw-файл. TLS и аутентификация проходят до принятия действия. Сервер проверяет repository policy, путь, media type — тип содержимого HTTP, и ограничения формата. Поток записывается в blob store, рассчитываются контрольные значения, обновляются metadata. Затем запрос завершается HTTP-ответом. Это логические фазы, а не обещание одной общей ACID-транзакции файловой системы и БД. Разрыв соединения на последнем шаге допускает неоднозначность: сервер мог сохранить объект, а клиент не получить подтверждение.

Поэтому повтор после timeout начинается с чтения координаты и сравнения ожидаемого хеша. Если файл уже существует и совпадает, действие могло завершиться. Если политика Disable Redeploy запрещает повтор, 400/409 либо иной документированный форматный ответ не стоит лечить включением перезаписи на всём repository. Сначала выясняют состояние. Фактический код точной версии фиксируют приёмкой. Для учебного release повтор того же имени с другими байтами должен отвергаться политикой и процессом публикации.

Поиск и скачивание дают разные свидетельства

Следующий запрос пригодится после создания raw-candidates и публикации файла в главе raw. Сейчас repository ещё может отсутствовать. Для него нужна личность с чтением candidates: в нашем процессе это release-promoter, а не обычный reader, которому candidates закрыты. Файл promoter.netrc готовится по рецепту клиентских учётных данных ниже; здесь сначала разберём смысл запроса. 401, пустой список до публикации и отказ reader не являются потерей blob.

curl --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/promoter.netrc" --fail --show-error --get \
  --data-urlencode repository=raw-candidates \
  https://nexus.lab.example/service/rest/v1/search/assets

--get помещает параметры в query string, --data-urlencode кодирует значение безопаснее ручной конкатенации. Ответ items содержит assets и continuationToken; ненулевой token требует следующего запроса с теми же критериями и этим token, пока не вернётся null. Первая страница не полный инвентарь. Asset ID — непрозрачная строка API, не имя blob-файла и не идентификатор, который переносим между восстановленными экземплярами. Поиск зависит от прав и состояния metadata; отсутствие строки не доказывает отсутствие байтов.

Приёмка конкретного release использует известный прямой download URL, размер и SHA-256 из доверенного manifest. GET должен вернуть ожидаемые байты. Ответ 200 HTML login page или страница прокси вместо бинарника обнаруживается проверкой размера/хеша и content type. MIME, Multipurpose Internet Mail Extensions — соглашение о типе содержимого — помогает интерпретации, но строка application/octet-stream сама не доказывает корректность программы. Хеш вычисляется по реально загруженному файлу.
