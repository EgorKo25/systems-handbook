Как читать доказательства

У команды есть исходники службы pulse, но выпуском становится конкретный исполняемый файл. Git хранит историю исходников; CI, continuous integration, то есть непрерывная интеграция, выполняет проверки и сборку; Nexus Repository принимает и раздаёт пакеты и двоичные результаты по протоколам клиентов. Если сервер сборки потерян, опубликованный выпуск должен оставаться доступным. Если публикация изменила байты уже известной версии, воспроизводимость сломана, даже когда все три интерфейса показывают зелёный статус.

Здесь изучается Sonatype Nexus Repository Community Edition 3.97.3-01, собственный экземпляр, один узел, встроенная H2 и файловые blob stores — хранилища двоичных объектов. Проверка официальной страницы загрузки и release notes выполнена 1 ноября 2026. Это явный учебный выбор, а не обещание поддержки любой будущей поставки. Nexus Repository Core из открытого исходного дерева и бинарная Community Edition имеют разный состав форматов. Nexus IQ/Lifecycle оценивает состав и политики приложений; его интеграция не превращает Repository в анализатор всего кода. JFrog Artifactory — другой продукт с другим API. Названия не взаимозаменяемы.

В 3.97 нельзя умолчать о связности. CE требует подтверждения базовой телеметрии; при длительной невозможности её отправки действует десятидневный льготный период, после которого экземпляр переходит в read-only. У CE нет поддерживаемого переключателя обхода. Учебник, поиск, схемы и локальные проверки читаются и исполняются без внешней сети при заранее подготовленном Go. Бессрочный изолированный Nexus CE 3.97.3 этим не обещается. Для отключённой площадки нужен отдельно согласованный поддерживаемый вариант поставщика. Официальные условия телеметрии.

Договор стенда

Имя VM условно nexus-lab, внешний адрес https://nexus.lab.example. Домен — пример для собственной зоны, а не готовый публичный сервис. Путь приложения /opt/sonatype/nexus-3.97.3-01, ссылка /opt/sonatype/nexus, data-dir /srv/nexus-data. Два файловых blob store называются lab-hosted и lab-cache; путь каждого записывается в журнал стенда. Они переживают остановку процесса. Репозитории go-internal, go-public, go-all, raw-candidates, raw-releases, позже oci-internal создаются один раз, затем изменяются осмысленно.

Собственный исходный модуль example.invalid/Acme/ledger@v1.0.0 использует заглавную букву специально: различим module path, путь ZIP и escaped путь HTTP. Служба example.invalid/shop/pulse потребляет его и становится бинарником pulse-linux-amd64. Версия исходного модуля и версия службы — разные координаты. Локальный пакет labs/ содержит исходники и проверку реальным Go. HTTP-fixture там является минимальным набором файлов протокола для исследования клиента, не реализацией Nexus, ролей или кэширования.

Рабочая копия и два компьютера

Команды python3 labs/... выполняйте из отдельной доступной на запись копии каталога этого тома Nexus: в ней рядом находятся labs/ и index.html. Каталог sources/ есть только в полной авторской копии; для выполнения упражнений он не требуется. Назовём её рабочим корнем. Откройте Bash в этом каталоге и сохраните его абсолютный путь: lab_root="$(pwd -P)". Переменная принадлежит текущей оболочке; после нового входа снова перейдите в ту же копию и задайте её заново. Не копируйте исходные labs поверх уже изменённых данных следующего занятия. Получится постоянное дерево: labs/module/ledger — исходник библиотеки, labs/service — потребитель, lab-work/proxy — упаковки версий, lab-work/client-a-mods — отдельный клиентский кэш.

Клиент с Go и curl может быть вашим личным Linux-компьютером; Nexus и команды sudo находятся в отдельной VM. Файл, созданный клиентом, не появляется на VM до явного переноса. Конфиги из labs/config нужно скопировать на VM, а пути в них относятся к её файловой системе. На Windows используйте заранее подготовленную собственную Linux-среду для этих Bash-рецептов; чтение книги в браузере само её не создаёт. Режим L удаляет только собственную временную область проверки, режим N сохраняет рабочую копию и сервер между занятиями.

Как читать доказательства

Фраза «рецепт VM» означает инструкции, которые читатель исполняет на собственной подготовленной VM; сервер Nexus при авторской проверке не запускался. «Выполнено локально» означает реальный процесс, запрос loopback HTTP или проверку файла, описанные в ПРОВЕРКИ.txt. Схемы — конечные авторские модели с перечисленными допущениями, а не сетевой захват настоящего сервера. Карточки команд открываются нажатием на имя команды в коде; они описывают флаги и предел результата. Ни схема, ни успешно разобранный JSON не подтверждают работу системы без приёмки.

После каждой главы сохраняйте короткую запись: исходное состояние, действие, идентификаторы изменённых объектов, ожидаемые и наблюдаемые HTTP-коды, хеши, время и способ возврата. Обычное окончание занятия — штатная остановка, а не удаление data-dir. Намеренно повреждается только копия локального артефакта или выделенный восстановленный стенд. Публикации v1.0.0 и 1.0.0 не перезаписываются ради повторения упражнения.

Выбор начинается до команды запуска

Откройте официальную страницу Download, выберите Linux x86-64, зафиксируйте полное имя nexus-3.97.3-01-linux-x86_64.tar.gz, дату, URL и SHA-256. На 1 ноября 2026 страница указывает 3.97.3; notes ветки 3.97 датируют исправление 27 октября. Бинарная CE подходит для Go hosted/proxy/group и raw. Поддержку HA, high availability — работы нескольких узлов с согласованным состоянием, здесь не предполагаем. Открытый проект Core ограничивает набор форматов; самостоятельная сборка из него не эквивалентна CE.

Поставка содержит рекомендуемую JVM, Java Virtual Machine — среду исполнения Java; ветка требует Java 21. Установка случайной системной Java 17 не удовлетворяет этому условию. По официальным требованиям размер выбирают по профилю нагрузки. Для небольшого учебного опыта резервируем, как собственное допущение, 4 vCPU, 16 GiB RAM, 50 GiB свободного локального SSD и место под отдельный резерв. Это стартовый бюджет, не минимальная гарантия. Этот бюджет VM требует отдельной машины либо хоста с запасом сверх 16 GiB: домашний компьютер с 8–16 GiB RAM не сможет одновременно выделить его гостевой ОС и себе. На таком компьютере сначала выполните реальную локальную Go-часть, а сервер перенесите на подходящее личное железо; меньший профиль не объявляется поддержанным без проверки требований именно версии. Размер всех артефактов и копий должен в него помещаться; рост request queue при свободном CPU может указывать на диск, сеть или внешнее ожидание.

curl --fail --show-error --location \
  --output nexus-3.97.3-01-linux-x86_64.tar.gz \
  https://download.sonatype.com/nexus/3/nexus-3.97.3-01-linux-x86_64.tar.gz
curl --fail --show-error --location \
  --output nexus-3.97.3-01-linux-x86_64.tar.gz.sha256 \
  https://download.sonatype.com/nexus/3/nexus-3.97.3-01-linux-x86_64.tar.gz.sha256

--fail делает HTTP-ошибку ошибкой процесса; без него тело страницы 404 можно сохранить как архив. --location разрешает перенаправление, --output выбирает имя файла, --show-error сохраняет объяснение отказа. При проверке происхождения переходы должны оставаться в доверенной цепочке источника. SHA-256, криптографический хеш, сравнивают с ожидаемым значением из доверенно полученного официального источника. Сумма, которую злоумышленник свободно заменяет рядом с архивом, происхождения не доказывает. MD5/SHA-1 на странице не выбираем как современное доказательство целостности. Подпись проверяют только если для выбранного артефакта действительно опубликованы подпись и проверенный ключ; нельзя придумывать файл ASC по аналогии с migrator.

sha256sum nexus-3.97.3-01-linux-x86_64.tar.gz
cat nexus-3.97.3-01-linux-x86_64.tar.gz.sha256
tar -tzf nexus-3.97.3-01-linux-x86_64.tar.gz

Первые две команды дают сравнимые хеши. Если checksum-файл содержит одну сумму без имени, его нельзя слепо подавать в sha256sum --check: сначала сформируйте запись «ожидаемая сумма, два пробела, точное имя». tar -t показывает состав без распаковки; -z включает gzip, -f задаёт файл. На этом этапе смотрят корневой каталог, архитектуру, комплект JVM и отсутствие неожиданного пути. Распаковку выполняют только после совпадения суммы, в выделенный каталог своей VM.

Что подготовить в отключённой сети

В комплект переноса включите архив и проверенную сумму, release notes и инструкции точной версии, ОС-пакеты и зависимости для VM, средства TLS, CA — certificate authority, удостоверяющую сторону доверия, установочный Go и его checksum, исходники labs, необходимые внешние модули и данные checksum database, если она используется. Для контейнерного варианта понадобились бы также daemon, образы и их digest, а не одна команда pull. Перенос файлов позволяет установить программное обеспечение без загрузки; политика базовой телеметрии CE 3.97.3 остаётся отдельной границей. Не отключайте проверку суммы и TLS ради офлайна.

Пользователь и два вида каталогов

Следующие команды — рецепт только для собственной VM. Создайте системного пользователя nexus без интерактивного входа, каталоги приложения и данных. Например, администратор VM выполняет useradd --system --home /srv/nexus-data --shell /usr/sbin/nologin nexus, затем install -d -o nexus -g nexus -m 0750 /srv/nexus-data. Имя группы и путь nologin сверяют с ОС. --system выбирает служебную учётную запись; её UID не должен совпасть с случайной личностью при восстановлении на другую VM.

Распакуйте проверенный архив в /opt/sonatype, создайте ссылку nexus на каталог этой версии. Распределение прав должно позволять launcher писать нужные служебные файлы; data-dir доступен на запись пользователю nexus. Не применяйте рекурсивное chmod 777. Зафиксируйте владельцев, режимы и фактические каталоги. В bin/nexus.vmoptions задайте согласованные абсолютные пути -Dkaraf.data=/srv/nexus-data, -Dkaraf.log=/srv/nexus-data/log, -Djava.io.tmpdir=/srv/nexus-data/tmp, создайте эти каталоги с нужным владельцем. Не добавляйте дубли параметров в конец: измените существующие строки и сохраните исходный файл. Комплектная JVM и фактические аргументы процесса проверяются после запуска.

В /srv/nexus-data/etc/nexus.properties положите учебную конфигурацию: приложение слушает только 127.0.0.1:8081. application-host ограничивает адрес HTTP connector; application-port задаёт порт, nexus-context-path=/ — корень URL. Каталог etc создайте до первого запуска. Не редактируйте defaults поставки ради постоянной настройки: при обновлении они принадлежат новой версии.

Последовательность команд в личной VM

Предполагается, что проверенный архив уже находится в текущем каталоге VM, служебная учётная запись создана, путь /opt/sonatype ранее не использовался другим экземпляром. Эти операции исполняет администратор своей VM. sudo здесь лишь явная граница прав; команды не предназначены для рабочего хоста.

sudo install -d -o root -g root -m 0755 /opt/sonatype
sudo tar -xzf nexus-3.97.3-01-linux-x86_64.tar.gz -C /opt/sonatype
sudo ln -s /opt/sonatype/nexus-3.97.3-01 /opt/sonatype/nexus
sudo chown -R nexus:nexus /opt/sonatype/nexus-3.97.3-01
sudo install -d -o nexus -g nexus -m 0750 \
  /srv/nexus-data/etc /srv/nexus-data/log /srv/nexus-data/tmp
sudo -u nexus /opt/sonatype/nexus/bin/nexus run

tar -x извлекает выбранный архив, -C меняет каталог назначения. ln -s создаёт ссылку без принудительной замены существующего пути. Владение launcher-каталогом у nexus в этом простом стенде даёт возможность записи PID; в более строгой поставке разделяют неизменяемое приложение и отдельный PID-dir по документации. Перед последней командой уже должны быть отредактированы vmoptions и nexus.properties, как описано выше. Повторная распаковка поверх работающей версии не является обновлением. На первом запуске Ctrl+C запрашивает завершение foreground; дождитесь остановки JVM, проверьте status и отсутствие слушателя перед запуском systemd.

На компьютере читателя ssh -N -L 18081:127.0.0.1:8081 vm-user@nexus-vm создаёт туннель до своей VM с проверенным SSH host key. -N не запускает удалённую shell, -L связывает локальный 18081 с loopback-портом на VM. Условные vm-user/nexus-vm заменяют собственными именами. Откройте http://127.0.0.1:18081 локально; HTTP-участок до VM защищён SSH. Туннель не открывает backend всем клиентам. Для удалённых автоматических Go-клиентов далее нужен общий проверенный HTTPS.

Запуск и служба

Предыдущая команда sudo -u nexus ... run уже заняла один терминал VM. Не вводите второй run. Пока первый процесс работает, откройте второй SSH-сеанс к той же VM и выполните наблюдения:

sudo -u nexus /opt/sonatype/nexus/bin/nexus status
curl --fail --show-error http://127.0.0.1:8081/service/rest/v1/status

Первый запуск выполняется от nexus в foreground, переднем плане, для наблюдения bootstrap — первоначальной подготовки приложения и данных; он меняет data-dir, создаёт БД и первоначальное состояние. Не запускайте параллельно службу над теми же данными. status исследует launcher/process, HTTP endpoint — способность приложения ответить. Оба результата слабее успешной загрузки и скачивания пакета. Если процесс исчез, смотрят log/nexus.log, JVM logs, права на tmp/db, свободное место и занятой порт. Молчание до появления журнала часто означает проблему launcher/доступа, не ошибку repository format.

После штатной остановки foreground настройте systemd unit по официальному контракту службы. Type=forking согласуется с bin/nexus start, который запускает фоновой процесс. WorkingDirectory фиксирует контекст относительных путей, User/Group задают права, TimeoutSec=600 оставляет время на bootstrap/остановку, LimitNOFILE=65536 — бюджет открытых файлов, а не настройка throughput. В VM администратор выполняет systemctl daemon-reload, затем systemctl start nexus. enable включает будущую автозагрузку и является отдельным решением. journalctl -u nexus -n 100 --no-pager ограничивает просмотр, а прикладной журнал всё равно находится в data-dir.

В этом стенде итоговый unit сохраняется как /etc/systemd/system/nexus.service на VM, а не остаётся только файлом в копии книги. Посмотрите systemctl show nexus --property=FragmentPath --value: он должен назвать этот файл. Вывод параметров systemd не сообщает, какие приложения запущены вручную вне unit; не оставляйте такой второй launcher после перехода к службе.

Первый вход и приёмка

Первоначальный пароль admin находится в $data-dir/admin.password. Читайте его только в частном терминале или через защищённый способ VM; не помещайте в командную строку, screenshot и историю CI. Для первого входа до TLS используйте SSH-туннель с локальным браузером, затем настройте HTTPS по следующей главе. Войдите через этот защищённый маршрут, смените пароль, завершите onboarding, прочитайте и подтвердите обязательные условия телеметрии как осмысленное административное действие. Anonymous access — анонимный доступ — пока отключите; позднее выдадим конкретное чтение. Создайте личного администратора и отдельного обычного читателя. Сохраните аварийный путь входа локального realm — источника установления личности.

Приёмка состоит из четырёх наблюдений: экземпляр сообщает выбранную версию; обычный пользователь читает разрешённый тестовый asset — адресуемый файл; тот же пользователь не публикует без права; после systemctl stop nexus и start сохранены репозиторий, учётные записи и checksum файла. Не удаляйте data-dir, чтобы получить «чистый» вход. Реальные ответы записывайте в журнал стенда, включая дату и версию. Авторская проверка этого тома установку Nexus не выполняла; её пределы перечислены в протоколе.

Кто произносит localhost

У браузера, Go-процесса CI, reverse proxy и самого Nexus могут быть разные сетевые пространства. localhost относится к процессу, который разрешает это имя. В выбранном стенде TLS — Transport Layer Security, защищённый транспорт — завершается на NGINX собственной VM по https://nexus.lab.example:443, затем прокси передаёт HTTP на 127.0.0.1:8081. Клиенту доступен внешний адрес; backend не публикуется в рабочую сеть. Сертификат должен содержать имя nexus.lab.example, а доверие к его издателю настроено у браузера, curl и Go независимо.

Внешний прокси здесь не является Nexus proxy repository. Первый маршрутизирует HTTP вход; второй хранит содержимое внешнего пакетного репозитория. Поэтому исправный NGINX не означает исправного скачивания зависимости. На proxy miss, промахе содержимого, уже Nexus начинает новое TLS-соединение к https://proxy.golang.org. Оно пользуется DNS, маршрутом, системным HTTP proxy и trust store сервера Nexus, а не компьютера разработчика.

 | Инициатор | URL/назначение | Что проверяет

 | Go CI | https://nexus.lab.example/repository/go-all/… | Свой CA, имя сервера, затем личность и read

 | NGINX | http://127.0.0.1:8081/… | Маршрут на той же VM, точность заголовков и таймауты

 | Nexus go-public | https://proxy.golang.org/… | Свой trust store, upstream TLS и ответ формата

 | Nexus telemetry | Официальные telemetry endpoints CE | Отдельная исходящая доступность и status/check

Довести личный стенд от SSH до HTTPS

Первый вход по SSH-туннелю из главы установки не требует готового публичного сертификата. Для общей лабораторной зоны подготовьте DNS либо отдельную запись hosts на каждом личном клиенте, указывающую nexus.lab.example на IP своей VM. Не редактируйте рабочий DNS. Следующий вариант создаёт личную CA и сертификат на VM; openssl и NGINX должны быть установлены из подписанного пакетного репозитория выбранной гостевой ОС. Для Debian/Ubuntu в личной VM это sudo apt-get update, затем sudo apt-get install nginx openssl. Пакеты и зависимости переносятся заранее, если VM не имеет пакетной сети.

umask 077
mkdir -p lab-tls
cd lab-tls
openssl req -x509 -newkey rsa:3072 -nodes -days 365 \
  -keyout ca.key -out ca.pem -subj /CN=Nexus-Lab-CA \
  -addext basicConstraints=critical,CA:TRUE \
  -addext keyUsage=critical,keyCertSign,cRLSign
openssl req -new -newkey rsa:3072 -nodes \
  -keyout key.pem -out server.csr -subj /CN=nexus.lab.example
printf '%s\n' 'subjectAltName=DNS:nexus.lab.example' \
  'extendedKeyUsage=serverAuth' 'keyUsage=digitalSignature,keyEncipherment' \
  > server.ext
openssl x509 -req -in server.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
  -out server.pem -days 30 -sha256 -extfile server.ext
cat server.pem ca.pem > fullchain.pem
openssl x509 -in server.pem -noout -subject -dates -ext subjectAltName

Это рецепт учебной CA, а не публичная инфраструктура сертификатов. umask 077 ограничивает новые файлы владельцем; -nodes оставляет ключ без парольного шифрования, поэтому закрытые ca.key/key.pem требуют защиты и резервирования. CSR, certificate signing request — запрос подписи сертификата, не является закрытым ключом. SAN, subject alternative name — имя назначения сертификата, должен совпасть с URL. -days 30 задаёт короткий учебный срок серверного сертификата: запишите дату обновления. После подписи ca.key уберите с сетевого сервера в защищённое место; клиентам передают только ca.pem после сверки fingerprint по независимому доверенному каналу.

Администратор VM создаёт /etc/nexus-tls, помещает key.pem с владельцем root и правами 0600, fullchain.pem — 0644; NGINX master читает ключ при старте. Положите фрагмент labs/config/nginx.conf в /etc/nginx/conf.d/nexus.conf на своей VM как отдельный virtual host, проверьте sudo nginx -t и только после успешной проверки выполните sudo systemctl reload nginx. Сохраните предыдущую конфигурацию. Пример не меняет firewall хоста: доступ 443 ограничивается правилами вашей VM/сети. На curl сначала используйте --cacert ca.pem; в Go нет прямого аналога этого флага у mod download, поэтому CA помещают в доверенное хранилище только выделенного клиента/контейнера либо используют SSL_CERT_FILE в поддерживаемой Unix-среде конкретного Go и проверяют результат. Браузер импортирует публичную CA своим способом. Не устанавливайте личную CA глобально на рабочие устройства без принятой политики.

Если CA создана на VM, подготовьте на личном клиенте в рабочем корне каталог lab-secrets с правами 0700 и перенесите туда только публичный ca.pem, сверив его SHA-256 через доверенный SSH-сеанс. Ключи ca.key и key.pem клиенту не нужны. Для выбранного Debian/Ubuntu-клиента можно создать собственный bundle, не меняя системное доверие: в рабочем корне выполните cat /etc/ssl/certs/ca-certificates.crt lab-secrets/ca.pem > lab-secrets/ca-bundle.pem и убедитесь в успешном завершении. Здесь первый файл — установленный пакетный набор CA; путь для другой ОС нужно определить отдельно. В выделенном учебном терминале export SSL_CERT_FILE="$lab_root/lab-secrets/ca-bundle.pem" задаёт файл доверия Go, а curl получает этот же файл через --cacert. Сохранение публичных корней нужно для внешней checksum database: один сертификат учебной CA не заменяет весь набор требуемого доверия. После закрытия этого терминала экспорт не меняет родительское окружение.

Согласованный обратный прокси

Фрагмент NGINX — рецепт VM, предполагающий уже установленный NGINX и подготовленный ключ. Значение proxy_set_header Host $host передаёт внешнее имя, X-Forwarded-Proto https сообщает исходную схему, X-Forwarded-For $remote_addr в этой одношаговой топологии перезаписывает недоверенный клиентский заголовок. HTTP Forwarded Headers capability Nexus должна быть включена при таком размещении; backend нужно ограничить сетевой границей, чтобы произвольный клиент не подделывал доверенный путь. Дополнительные load balancer и proxy меняют эту схему и требуют явного списка доверенных переходов.

client_max_body_size 256m — собственный учебный предел HTTP body. Он подходит только пока наш бинарник и ZIP меньше предела; ошибка 413 может возникнуть раньше Nexus. proxy_read_timeout 300s относится к ожиданию чтения от upstream, не к универсальной пятиминутной длительности всей загрузки. Большие файлы требуют согласования лимитов, buffering, свободного временного диска, скорости клиента и поведения разрыва. Прежде чем увеличить timeout в десять раз, сравните размер, длительность и места ожидания. Рецепт не разрешает неограниченный upload из интернета.

curl --show-error --fail --head https://nexus.lab.example/
curl --show-error --fail --cacert ca.pem \
  https://nexus.lab.example/service/rest/v1/status
curl --show-error --dump-header headers.txt --output body.bin \
  https://nexus.lab.example/repository/go-all/example.invalid/!acme/ledger/@v/v1.0.0.info

--head делает HEAD: сервер может обработать его иначе, чем GET, поэтому это слабая проверка возможности загрузки тела. --cacert задаёт проверенный CA для конкретного curl; вариант без флага использует обычное хранилище доверия. Сравнение помогает локализовать отсутствующий CA. --dump-header сохраняет заголовки отдельно от тела. Без --fail последний запуск намеренно позволяет исследовать тело ошибки; HTTP-код читают из headers.txt. Этот файл может содержать чувствительные headers, не публикуйте его без просмотра. -k исключает проверку сертификата и не является исправлением TLS.

Перенаправление — ещё один запрос

HTTP 301/302/307/308 указывают другое местоположение, но не доказывают наличие файла. curl --location следует Location; без него сохранится ответ перенаправления. Не используйте --location-trusted в обычной диагностике: передача credential на другой host расширяет доверие. Проверяйте схему, имя и возможность достичь конечного хранилища из реального клиента. Upstream может отдать подписанный URL object storage; некорректное нормализованное экранирование пути ломает подпись. Нельзя повсеместно заменять двойные слеши или декодировать все проценты «для красоты».

Для Go важно сохранить ! escaping регистра, сегмент @v, версию и расширение. URI, Uniform Resource Identifier — адрес ресурса, обрабатывает несколько компонентов, и каждый может внести ошибку. Разберите последовательность: raw bytes запроса клиента; URI входного журнала; URL, отправленный Nexus upstream; конечный HTTP-код. Если имя модуля содержит заглавную букву, запись %21acme в журнале может быть URL-представлением !acme, а не другим модулем. Нельзя считать разные текстовые формы журнала доказательством разных хранимых координат.

no such host требует проверки DNS именно у инициатора. connection refused означает отсутствие доступного слушателя или явный отказ TCP; пароль ещё не передан. Ошибка x509 относится к цепочке, имени или сроку TLS. HTTP 401 требует аутентификации, 403 — разрешений уже определённой личности либо дополнительной политики, 404 может означать путь/отсутствие и иногда скрытие существования. 502/504 от NGINX могут указывать на backend или timeout; это не автоматически код Nexus. Сопоставляйте access log прокси, request.log Nexus и прикладной журнал по времени, методу и пути.

Четыре разных объекта

Coordinate, координата — идентичность в правилах конкретного формата. Для Go это module path и version, для Maven — groupId/artifactId/version с дополнительными типом и classifier, для raw — выбранный путь файла. Component, компонент — логическая единица формата, например версия модуля с несколькими файлами представления. Asset, ресурс — адресуемое содержимое, например v1.0.0.mod либо конкретный ZIP. Blob, двоичный объект — сохранённые байты с внутренней идентичностью хранилища. Один component не обязан соответствовать одному asset; количество HTTP-запросов тоже не равно количеству component.

При чтении .../ledger/@v/v1.0.0.zip сервер сначала выбирает repository и формат, проверяет доступ, разрешает логический путь и находит metadata asset. Запись связывает repository/path/форматные поля с blob reference — ссылкой на объект выбранного blob store. Затем хранилище возвращает поток байтов. В БД находятся метаданные и конфигурация, в blob store — содержимое. Это причинная модель уровня продукта; точные SQL table/column и layout bucket не являются публичным договором для ручного редактирования.

У файлового backend в data-dir видны служебные каталоги, файлы содержимого и свойств. Имена не следует трактовать как прямое отображение публичного URL. Файловый менеджер не знает транзакций Nexus, индексов и связей. Копирование ZIP непосредственно в папку blobs не публикует Go-модуль. Ручное удаление файла не выполняет корректное удаление asset и может оставить dangling reference, висячую ссылку из метаданных.

Например, логическая запись raw asset описывает repository raw-candidates, path pulse/1.0.0/linux-amd64/manifest.json, размер N bytes, checksum и непрозрачную ссылку B1 на содержимое. N считается по сохранённым байтам, а не по числу символов JSON: русская буква в UTF-8 может занимать больше одного байта. Другой asset pulse-linux-amd64 имеет свой размер, checksum и ссылку B2. Это пример связей, а не опубликованная SQL-схема Nexus: поле с именем B1 нельзя искать как файл blobs/B1. Когда GET находит metadata, но B2 утрачен, список может по-прежнему показывать выпуск, однако серверу нечем заполнить тело ответа. Обратная ситуация, B2 без metadata, оставляет байты на диске без доступного клиенту прежнего пути.

Один ZIP: от записи каталога до окончательного удаления байтов
Учебная карта: component ledger версии v1.0.0 связан с assets info, mod и zip. Запись zip содержит ссылку на blob B. B — условное обозначение, не хеш или имя файла. После мягкого удаления blob обычное чтение прекращено, но байты остаются. Отдельная успешная compaction может убрать их после окна удержания.

Это карта связей, а не схема SQL-таблиц. B — условная метка внутреннего объекта; SHA-256 скачанного ZIP проверяет его содержимое, но не задаёт имя blob-файла. Другие assets показаны для различения component и asset; их внутреннее размещение здесь не развёрнуто.

Как читать переходы. Сначала поддержанная операция удаления меняет состояние каталога; форматные задачи могут отдельно находить больше не нужные assets. На рисунке второй момент уже предполагает, что сам blob отмечен к удалению. Удаление одной ссылки само по себе этого не доказывает: например, у Docker/OCI надо учитывать связи manifests и слоёв. Для File backend физические байты убирает отдельное успешно выполненное Admin - Compact blob store выбранного хранилища, когда прошёл заданный период Blobs Older Than. Ноль убирает дополнительное окно ожидания, но не запускает задачу автоматически. Ни отсутствие URL, ни пропажа строки поиска не измеряют освобождённое место.

У этой схемы нет действия «восстановить»: мягкое удаление не заменяет проверенный резерв. Как подготовить согласованные метаданные и blobs, разобрано в главе о восстановлении, а выбор удаления и редакционные ограничения — в главе об очистке. Загрузка как несколько эффектов

Предположим CI отправил raw-файл. TLS и аутентификация проходят до принятия действия. Сервер проверяет repository policy, путь, media type — тип содержимого HTTP, и ограничения формата. Поток записывается в blob store, рассчитываются контрольные значения, обновляются metadata. Затем запрос завершается HTTP-ответом. Это логические фазы, а не обещание одной общей ACID-транзакции файловой системы и БД. Разрыв соединения на последнем шаге допускает неоднозначность: сервер мог сохранить объект, а клиент не получить подтверждение.

Поэтому повтор после timeout начинается с чтения координаты и сравнения ожидаемого хеша. Если файл уже существует и совпадает, действие могло завершиться. Если политика Disable Redeploy запрещает повтор, 400/409 либо иной документированный форматный ответ не стоит лечить включением перезаписи на всём repository. Сначала выясняют состояние. Фактический код точной версии фиксируют приёмкой. Для учебного release повтор того же имени с другими байтами должен отвергаться политикой и процессом публикации.

Поиск и скачивание дают разные свидетельства

Следующий запрос пригодится после создания raw-candidates и публикации файла в главе raw. Сейчас repository ещё может отсутствовать. Для него нужна личность с чтением candidates: в нашем процессе это release-promoter, а не обычный reader, которому candidates закрыты. Файл promoter.netrc готовится по рецепту клиентских учётных данных ниже; здесь сначала разберём смысл запроса. 401, пустой список до публикации и отказ reader не являются потерей blob.

curl --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/promoter.netrc" --fail --show-error --get \
  --data-urlencode repository=raw-candidates \
  https://nexus.lab.example/service/rest/v1/search/assets

--get помещает параметры в query string, --data-urlencode кодирует значение безопаснее ручной конкатенации. Ответ items содержит assets и continuationToken; ненулевой token требует следующего запроса с теми же критериями и этим token, пока не вернётся null. Первая страница не полный инвентарь. Asset ID — непрозрачная строка API, не имя blob-файла и не идентификатор, который переносим между восстановленными экземплярами. Поиск зависит от прав и состояния metadata; отсутствие строки не доказывает отсутствие байтов.

Приёмка конкретного release использует известный прямой download URL, размер и SHA-256 из доверенного manifest. GET должен вернуть ожидаемые байты. Ответ 200 HTML login page или страница прокси вместо бинарника обнаруживается проверкой размера/хеша и content type. MIME, Multipurpose Internet Mail Extensions — соглашение о типе содержимого — помогает интерпретации, но строка application/octet-stream сама не доказывает корректность программы. Хеш вычисляется по реально загруженному файлу.

Три роли repository

Hosted принимает ваши публикации и является источником этих версий. Proxy обращается к настроенному remote storage, внешнему upstream, и сохраняет полученное для повторного чтения. Group даёт клиенту один endpoint перед упорядоченными участниками. Эти роли не означают три независимые полные копии пакетов: group маршрутизирует и может формировать форматные metadata, а участники сохраняют своё содержимое. Публикация Go в нашем стенде идёт прямо в hosted go-internal, получение — через go-all. Нельзя предполагать, что любой group принимает upload или автоматически выбирает куда его записать.

Создать хранилища до выбора repository

У администратора откройте Settings → Blob Stores в Nexus One UI либо Settings → Repository → Blob Stores в Classic UI. Создайте два объекта типа File: lab-hosted с абсолютным Path /srv/nexus-data/blobs/lab-hosted и lab-cache с Path /srv/nexus-data/blobs/lab-cache. Родитель доступен пользователю nexus; каталог не занят другим blob store. После сохранения проверьте показанные Path и State, затем запишите их. Такой выбор держит оба учебных хранилища внутри data-dir и определяет охват резервного копирования. Если вы выбрали внешний Path, резерв data-dir его не охватывает.

Имя в форме repository выбирает уже созданный blob store. Оно не создаёт отдельный диск и не резервирует ёмкость. Soft Quota — порог предупреждения: при его превышении хранилище само не прекращает запись. Поэтому кроме предупреждения нужно наблюдать свободное место файловой системы. Не переименовывайте каталоги после создания, пытаясь таким способом перенести хранилище. Поля и создание Blob Store сверены 2 ноября 2026.

Создайте go-public типа Go proxy с remote https://proxy.golang.org и blob store lab-cache; go-internal типа Go hosted с lab-hosted; go-all типа Go group с порядком internal, public. Это рецепт CE 3.97.3, подтверждённый доступностью Go. Форма настройки может отличаться в Nexus One UI и Classic UI. Сохраните экспорт конфигурации точной версии. Не подменяйте отсутствующий recipe generic raw.

Подготовить личности для следующих запросов

Аутентификация устанавливает имя обратившегося, а роль выдаёт ему набор разрешений. В Security → Roles администратор создаёт роли стенда, в Security → Users — отдельных local users и назначает им эти роли. Anonymous пока выключен. Для reader выдайте read/browse только go-all, позже добавьте raw-releases. Для ci-publisher — необходимые add/edit действия только go-internal, позже raw-candidates. Для release-verifier — только чтение candidates; для release-promoter — чтение candidates и запись releases. Привилегии raw добавляются после создания этих repositories в главе raw. Не выбирайте wildcard всех будущих репозиториев. Формат может требовать edit при PUT; минимальный рабочий набор сверяется положительной загрузкой и отказом чужого пути.

Имена пользователей и имена файлов отличаются: publisher.netrc хранит ci-publisher, reader.netrc — reader, verifier.netrc — release-verifier, promoter.netrc — release-promoter. На своём клиенте в рабочем корне создайте закрытый каталог lab-secrets с правами 0700. В частном редакторе создайте там отдельный файл каждой личности с правами 0600. Формат одного файла reader.netrc:

machine nexus.lab.example
login reader
password ЗАМЕНИТЬ_НА_ПАРОЛЬ_ЭТОГО_ПОЛЬЗОВАТЕЛЯ

Строка password выше — описание места под секрет, а не работающий пароль. Для этого простого netrc-примера используйте сгенерированный пароль без пробельных символов; возможные правила кавычек разных клиентов здесь не предполагаются. Host после machine должен точно соответствовать реальному HTTPS URL, без схемы, порта и пути. Секреты не добавляйте в Git, ZIP модуля, backup книги и публичный отчёт. Далее команда curl --netrc-file "$lab_root/lab-secrets/reader.netrc" ... явно выбирает reader; имя файла само не меняет роль на сервере. Подробный разбор привилегий и негативных проверок дан в главе доступа.

Промах и попадание

Чистый Go-клиент запрашивает известную версию публичного модуля через URL go-public. На cold miss сервер ещё не имеет asset: после авторизации он вызывает remote, проверяет TLS и форматный ответ, сохраняет байты/metadata и отвечает клиенту. На hit следующий запрос может получить сохранённое содержимое без повторной передачи всего файла upstream. Но hit не равен «никогда нет внешнего запроса»: возраст записи может потребовать revalidation, повторной проверки актуальности. Условный GET с ETag либо Last-Modified допускает ответ 304 без полного тела, если формат/remote это поддерживает.

У client cache и Nexus cache разные владельцы. Два последовательных go build в одной рабочей копии могут вообще не направить второй запрос в Nexus: Go уже имеет модуль в GOMODCACHE. Для измерения серверного hit нужен новый клиентский module cache с теми же координатами и уже тёплым Nexus. Для измерения miss нужны заранее выбранные ещё не кэшированные координаты либо отдельный proxy в копии стенда. Удаление общего production cache ради графика недопустимо.

1. Первый клиент ещё пуст

Go действительно обращается в Nexus; отсутствие локального ZIP делает запрос наблюдаемым.

Действует: Go.

Go-клиент: нет v1; Nexus proxy: получен GET; Upstream: доступен; Metadata DB: нет asset; Blob store: нет bytes; Второй Go: не запущен

Запрос: только команда build → HTTP GET в Nexus. Тёплый client cache мог бы исключить этот запрос.

2. Нет достаточного asset

Proxy проверяет metadata и cache policy. В заданных условиях это cold miss.

Действует: Nexus.

Go-клиент: ждёт; Nexus proxy: miss; Upstream: доступен; Metadata DB: нет ссылки; Blob store: нет bytes; Второй Go: пуст

Знание: не проверено → asset отсутствует. Успешная авторизация не создаёт содержимое.

3. Сервер обращается наружу

Теперь инициатор соединения — Nexus, с собственными DNS/TLS и credentials.

Действует: Nexus HTTP client.

Go-клиент: ждёт; Nexus proxy: GET remote; Upstream: 200 + ZIP; Metadata DB: ещё нет завершённого asset; Blob store: запись впереди; Второй Go: пуст

Инициатор: Go → Nexus → Nexus → upstream. TLS клиента не доказывает серверное доверие к remote.

4. Сохранена связь с байтами

Логические bytes и metadata образуют читаемый asset. Это упрощение фаз, не общий distributed commit.

Действует: Nexus.

Go-клиент: получает ZIP; Nexus proxy: cache заполнен; Upstream: передал тело; Metadata DB: coordinate → B1; Blob store: B1 сохранён; Второй Go: пуст

Состояние: нет содержимого → metadata + B1. Потеря любой части меняет дальнейшее чтение.

5. Другой чистый клиент спрашивает то же

Этот Go не имеет client cache; серверное содержимое ещё свежее.

Действует: Второй Go.

Go-клиент: свой cache тёплый; Nexus proxy: fresh hit; Upstream: не нужен для этого шага; Metadata DB: B1; Blob store: B1; Второй Go: GET v1

Условие опыта: первый клиент тёплый → второй cache пуст. Так разделяются client hit и server hit.

6. Ответ из blob store

Без истёкшего TTL и других условий remote в модели не вызывается повторно.

Действует: Nexus.

Go-клиент: v1 есть; Nexus proxy: hit завершён; Upstream: нового GET нет; Metadata DB: B1; Blob store: B1 прочитан; Второй Go: проверяет ZIP/sum

Передача: нужен файл → байты B1 получены. При revalidation возможен другой внешний путь, разобранный в тексте.

Возраст содержимого и возраст знания

Maximum Component Age задаёт время до проверки изменения компонента, Maximum Metadata Age — знания о версиях/индексах. В интерфейсе значения в минутах: 1440 min = 24 h. -1 для component age отключает проверку redeploy, 0 требует проверять изменения при каждом запросе; для component metadata учитывается более долгий из этих сроков. Это поведение описано в Configurable Repository Fields; форматные особенности проверяют на выбранном recipe, а не переносят буквально с Maven snapshot на любой протокол.

Представим, что bytes версии immutable, неизменяемой, а список версий расширяется каждый час. Файл v1.0.0 может оставаться правильным годами, но @v/list устаревает через минуты. Уменьшение metadata age помогает увидеть v1.0.1 быстрее, ценой запросов upstream. Уменьшение component age для каждого неизменяемого ZIP может добавить сеть без пользы. Если upstream нарушает неизменяемость v1.0.0, обновлённый кэш уже не исправляет доверие: клиенты с go.sum должны отвергнуть другую сумму.

Negative cache хранит отсутствие

Negative cache — отрицательный кэш — запоминает, что ресурс отсутствовал. Клиент в 10:00 спросил v1.0.1 и получил 404; upstream опубликовал её в 10:02; Nexus может продолжать отвечать из отрицательного кэша до истечения TTL, time to live — срока жизни записи. Это не обязательно проблема роли и не обязательно DNS. Сравните прямой контролируемый запрос upstream и тот же путь через proxy, время первой ошибки, TTL и серверный журнал. При закрытых координатах не направляйте прямую проверку в публичный интернет.

Invalidate cache делает сохранённое знание просроченным для последующей проверки; это не удаление всех blob и не немедленное скачивание всего remote. Клиентский кэш тоже может сохранить прежнее знание, поэтому после invalidation эксперимент должен контролировать обе стороны. Отключение negative cache повышает частоту запросов к upstream при опечатках и может привести к rate limiting. Для быстро публикуемого собственного upstream разумнее отдельный измеренный TTL, например 2 min как условие лаборатории, а не универсальные ноль или сутки.

Group создаёт политику видимости

Если два hosted содержат одинаковый module path/version с разными байтами, порядок участников становится конфликтом доверия. «Внутренний раньше публичного» не является полной защитой от dependency confusion, подмены внутренней зависимости внешней: ошибочный внутренний 404 может отправить поиск дальше. Выделяйте собственный namespace, routing rules при поддержке и проверке формата, отдельный приватный путь без внешнего fallback и неизменяемые версии. Запрос приватной координаты не должен молча уходить публичному proxy.

Права на group позволяют читать содержимое участников через group, даже если прямой endpoint участника этой личности не разрешён. Состав group поэтому относится к политике доступа. Перед добавлением нового внутреннего member проверьте, кому открыт общий адрес. Отдельно проверьте 401/403 от upstream: credential Nexus→remote отличается от credential Go→Nexus, их нельзя лечить одним общим admin-паролем.

Эксперимент и единицы

Для 100 загрузок ZIP по 8 MiB соберите клиентскую duration, байты upstream, серверное время и HTTP-коды. Если miss медианно занимает 1.6 s, hit 0.12 s, а warm Go вообще не делает HTTP, это три разных опыта. Доля попаданий считается по определённым server requests, не по количеству команд build. При 80 hit и 20 miss request hit ratio равен 0.8; byte hit ratio может быть иным, если промахнулись самые большие файлы. Увеличение диска помогает удерживать полезный working set, набор часто читаемых объектов; оно не сокращает TLS handshake клиента при каждом соединении и не исправляет блокировку БД.

Module path не адрес репозитория Nexus

Go module — набор пакетов с корневым go.mod и module path, идентификатором пространства импортов. Наша библиотека объявляет module example.invalid/Acme/ledger. После размещения в Nexus импорт в программе остаётся example.invalid/Acme/ledger; он не становится nexus.lab.example/repository/go-internal/.... GOPROXY задаёт транспорт получения, а module directive и require — логическую идентичность. Домен example.invalid зарезервирован для примеров, поэтому direct-доступ к нему в этом практикуме намеренно не работает.

У модуля может быть вложенный путь: example.invalid/Acme/ledger имеет два сегмента после домена. Это один module path, а пакет example.invalid/Acme/ledger/report обычно лежит в подпапке того же модуля. Но отдельный go.mod в report создаёт границу nested module: упаковка родителя не должна захватывать его как обычные файлы. До создания ZIP решают, что именно публикуется. Нельзя угадать корень модуля только по глубине импортируемого пакета. В нашем fixture есть ровно один корень и allowlist трёх файлов.

Регистронезависимое хранилище требует escaping

Для URL протокола заглавная ASCII-буква заменяется на ! и соответствующую строчную: Acme становится !acme. Это не просто приведение всего имени к lower case: Acme и acme должны остаться различимы. Для нашего модуля escaped path равен example.invalid/!acme/ledger. HTTP-клиент может дополнительно percent-encode в URL символ ! как %21. Это второй слой кодирования; module escaping и URL encoding нельзя путать.

Версии тоже escape-ятся, если допустимая каноническая версия содержит заглавные prerelease буквы. В 3.97 release notes отдельно исправлен Go hosted resolution такого случая. Здесь основной fixture использует обычную v1.0.0, а не заявляет тест этого серверного исправления. В ZIP prefix остаётся исходный, не escaped module path, с @ и канонической версией: example.invalid/Acme/ledger@v1.0.0/. Это различие проверяется настоящим Go-клиентом.

 | /@latest | Сведения о выбранной latest версии, когда нужны | Разрешение latest; необязательный вызов при явной фиксированной версии

Конкретная команда не обязана вызывать все endpoints в одном фиксированном порядке. Для явно известного @v1.0.0 версия уже задана; в авторском HTTP-опыте go mod tidy запросил .zip, .mod и .info, не @v/list. Параллелизм и порядок меняются по версии Go, состоянию кэша и задаче. Схема ниже показывает возможные зависимости, а не обещает сетевой trace каждого go build.

curl --fail --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/reader.netrc" \
  'https://nexus.lab.example/repository/go-all/example.invalid/!acme/ledger/@v/v1.0.0.info'
curl --fail --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/reader.netrc" --output ledger.zip \
  'https://nexus.lab.example/repository/go-all/example.invalid/!acme/ledger/@v/v1.0.0.zip'

Одинарные кавычки сохраняют специальные символы оболочки, включая ! в интерактивных shell. В первом запросе тело — JSON metadata; во втором ZIP сохраняется в файл. Успешная передача ZIP curl ещё не доказывает пригодность module layout, выбранность версии в графе или наличие корректного go.sum. Это проверяет клиент следующей главы.

Версия, pseudo-version и major suffix

Semantic Versioning, SemVer — соглашение major.minor.patch о совместимости. Для Go запись v1.0.0 включает v. Нормальный module path для major v2+ заканчивается /v2 и используется в импортах; публикация v2 под прежней v1-координатой не обходит эти правила. Pseudo-version связывает ревизию VCS, version control system — системы контроля версий, с версионным порядком; это не произвольная строка с сегодняшней датой. Настоящую pseudo-version получает Go по известной ревизии, проверяя допустимость, а не человек набирает «похожий» timestamp.

Maven SNAPSHOT — изменяемая линия с форматными metadata и timestamped artifacts; Go не получает аналогичную гарантию от суффикса SNAPSHOT. Повторная запись v1.0.0 нарушает договор клиентов, даже если Nexus разрешил redeploy. Нужен v1.0.1. OCI tag тоже не эквивалентен версии Go: tag — указатель, digest — идентичность содержимого манифеста.

ZIP, h1 и SHA-256 — разные уровни

Хеш скачанного ZIP как файла зависит от его точных байтов, включая ZIP metadata и способ сжатия. Go h1: для модуля вычисляется по канонизированному набору имён и содержимого файлов, поэтому может совпадать у разных ZIP-представлений того же набора исходников. Сумма .../go.mod h1:... относится отдельно к go.mod. Не сравнивайте h1-текст с hex-выводом sha256sum ZIP как будто это одинаковая величина. Наш raw manifest использует именно SHA-256 бинарника, который передаём без перекодирования.

Первичные механизмы: Go Modules Reference: module proxy, реализация proxy клиента Go, проверка загрузки Go. Проверены 1 ноября 2026; локальные наблюдения относятся к Go 1.27.3. Для универсального упаковщика следует пользоваться golang.org/x/mod/zip выбранной версии; наш allowlist fixture не обрабатывает все правила symlink, vendor, nested modules и лимитов произвольного проекта.

Пройти h1 до отдельных байтов

Сравним две загрузки одной версии, не полагаясь на название алгоритма. В h1_walk.py есть маленький авторский модуль example.invalid/bytes/lab@v1.0.0 из двух файлов. Это отдельная пробирка для проверки сумм: она не заменяет сохраняющийся модуль ledger и не меняет его версии. Скрипт создаёт файлы только во временном каталоге и запускает настоящий Go с транспортом file://. Nexus и внешняя база контрольных сумм в опыте не участвуют.

Ниже точная запись содержимого как Python bytes: \n обозначает один байт LF, а кавычки и префикс b в сам файл не входят. Так видно, есть ли пустая строка и перенос в конце:

go.mod:    b'module example.invalid/bytes/lab\n\ngo 1.26\n'
answer.go: b'package lab\n\nconst Answer = 42\n'

Внутри ZIP имена начинаются с example.invalid/bytes/lab@v1.0.0/. Для каждого имени берём SHA-256 несжатого содержимого файла. Затем сортируем полные имена и для каждого записываем строку: шестнадцатеричная сумма, ровно два пробела, имя, один байт LF. В нашем опыте сводка содержит именно такие байты; переносы видимого блока соответствуют LF:

620c264d1538a90b3f4c27536399e5886f558ab8709eae0bf64dda6d6538ed6d  example.invalid/bytes/lab@v1.0.0/answer.go
456732f081ccefc9344a62431f7fd18c588cc485f389ca46b46b26c650b41c7b  example.invalid/bytes/lab@v1.0.0/go.mod

Вычисляем SHA-256 всей этой сводки, кодируем полученные 32 байта стандартным Base64 и добавляем префикс h1:. Base64 — текстовое представление байтов; оно не добавляет шифрования или доверия. В результате настоящий Go 1.27.3 и отдельное авторское вычисление получили:

h1:7WKrdRtFSF2meIj8osij3sbHmCEeLUaVlF+YlHBJ8dE=

Важно сохранить имена, пробелы и завершающие LF. Сумма сводки, в которой между колонками один пробел, будет другой. Смена окончания строки исходника с LF на CRLF тоже меняет содержимое и его сумму. Вычисление по распакованному каталогу с уже преобразованными редактором файлами не доказывает сумму первоначальной загрузки. Сам учебный скрипт работает с объектами bytes, последовательностями байтов, и не переписывает исходники под окончания строк ОС.

Почему строка /go.mod даёт другое h1

Go может получить описание зависимостей раньше всего исходного модуля. Поэтому в go.sum встречаются две отдельные записи: сумма модуля и сумма его go.mod. Для второй используется дерево из одного файла с именем go.mod, без префикса module@version. Даже при тех же байтах go.mod сводка теперь состоит из одной строки:

456732f081ccefc9344a62431f7fd18c588cc485f389ca46b46b26c650b41c7b  go.mod

После того же внешнего SHA-256 и Base64 получаем h1:UQlMCAh2EnFYrq3F/83ATd8bFMfx8DSuczv6vSHAQ6I=. Две записи нашего go.sum выглядят так:

example.invalid/bytes/lab v1.0.0 h1:7WKrdRtFSF2meIj8osij3sbHmCEeLUaVlF+YlHBJ8dE=
example.invalid/bytes/lab v1.0.0/go.mod h1:UQlMCAh2EnFYrq3F/83ATd8bFMfx8DSuczv6vSHAQ6I=

Суффикс /go.mod здесь часть обозначения проверяемого объекта, а не ещё одна версия пакета. Наличие только этой строки не утверждает, что исходный ZIP уже скачан и проверен. Несколько версий одного модуля в go.sum также не означают, что все они одновременно выбраны для сборки: выбранный граф смотрят отдельно через команды Go. Файл сумм отвечает на другой вопрос.

Пять опытов: что именно изменилось

 | Опыт | Изменение | Реальный результат

 | A | Первоначальный ZIP, два известных файла | Go вернул Sum и GoModSum, совпавшие с независимым вычислением

 | B | Те же имена и байты; другой порядок ZIP entries, даты и сжатие | SHA-256 архива изменился, h1 сохранился; прежний go.sum принят

 | C | В answer.go число 42 заменено на 43, версия оставлена v1.0.0; прежний go.sum сохранён | Чистый клиент завершился с checksum mismatch и SECURITY ERROR

 | D | Те же изменённые исходники, но у нового клиента ещё нет доверенной записи, а приватный путь исключён из внешней checksum database | Клиент принял впервые полученное содержимое и записал новую сумму

 | E | Байты не менялись, answer.go переименован в renamed.go | h1 изменился: имя файла участвует в сводке

В сохранённом авторском запуске архив A занимает 409 байт и имеет SHA-256 4c6cd2c79dd40ab2bc1567dab8fe132a6ffbc6cf83b005e25fe4e9ec277ecddd. У B — 413 байт и c3d5a6d830d5a77fef97c748db37c291766817c8be43d1a44abe7794971e5b04. Другая реализация ZIP/сжатия может дать другие архивные байты; при тех же именах и содержимом проверяемый h1 остаётся прежним. Следовательно, равный h1 — конкретное утверждение о наборе имён и содержимого, а не о тождестве всех байтов архивной упаковки. Сумма raw-бинарника из доверенного release manifest проверяет именно байты бинарника; её не заменяют этим h1.

Опыт C сохраняет старый go.sum, но использует новый GOMODCACHE, чтобы ответ не пришёл из прежнего клиентского кэша. Иначе можно ошибочно решить, что проверили серверную замену, хотя сеть и новый ZIP вообще не участвовали. Опыт D объясняет границу первого получения: алгоритм хеширования сам не знает, кто имел право выпустить эти исходники. Приватный модуль, исключённый из внешней базы сумм, должен получить исходное доверие другим способом — через проверенный канал публикации, review, закреплённую доверенную сумму и правила репозитория. Существующий go.sum после этого ограничивает незаметную замену.

Повторить и правильно прочитать отказ

python3 labs/h1_walk.py --go /path/to/prepared/go --output h1-results.json

Путь замените на собственный подготовленный исполняемый Go. Скрипт не скачивает toolchain, не вызывает shell и не запускает сервер. Он задаёт GOENV=off, чтобы не читать постоянные настройки Go, GOWORK=off, чтобы не подхватить родительский workspace, и GOTOOLCHAIN=local, чтобы не искать новую toolchain в интернете. GOPROXY указывает на временный file:// набор файлов. Для example.invalid явно заданы GONOPROXY=none и GONOSUMDB=example.invalid: берём модуль из этого proxy и не раскрываем учебный частный путь внешней базе сумм. Это ограничение собственного опыта, а не рецепт отключения проверок для публичных зависимостей.

Каждый клиент получает отдельный временный cache. Команда go mod download -json даёт машинно читаемые поля Sum и GoModSum при успешном получении. В наблюдавшемся отказе целостности Go завершился раньше вывода JSON: stdout был пуст, сообщение находилось в stderr и код процесса был ненулевым. Поэтому обработчик результата сначала учитывает код завершения и наличие данных; флаг -json не гарантирует JSON при каждом фатальном отказе. Учебный скрипт намеренно проверяет оба вида результата.

Вывод содержит пять passed-проверок и точные сводки. Если опыт не проходит, сначала смотрят версию локального Go, возможность чтения file:// и диагностический текст. Не исправляйте checksum mismatch удалением go.sum в настоящем проекте: это как раз превращает ситуацию C в D, где исчезло ранее закреплённое ожидание. Сначала сравните доверенную версию исходников, историю публикации и ответы серверов. Для изменённого модуля обычно выпускается новая версия; кто именно нарушил прежнюю координату, устанавливается отдельно.

Эта пробирка проверяет конкретный клиент и известные корректные файлы. Она не реализует все ограничения произвольного module ZIP, не проверяет серверную транзакцию Nexus и не доказывает отсутствие уязвимостей в принятом коде. Формальные правила и реализация: dirhash в Go 1.27.3, проверка подлинности модулей. Реальный опыт и первоисточники сверены 1 ноября 2026 года.

Настройка процесса прежде постоянной конфигурации

GOPROXY задаёт источники получения модулей. GOPRIVATE задаёт шаблоны префиксов приватных module paths и служит значением по умолчанию для GONOPROXY и GONOSUMDB. GONOPROXY выбирает, какие модули получать в обход proxy; GONOSUMDB — какие не проверять через публичную checksum database, журнал контрольных сумм. GOSUMDB задаёт доверенную базу, её имя/ключ и при необходимости адрес обращения. Эти переменные решают разные задачи. «Приватный» не означает «получать через Nexus» без дополнительного выбора.

Откройте отдельный Bash-терминал для Nexus, перейдите в рабочий корень своей копии и задайте lab_root="$(pwd -P)". К этому моменту подготовлены HTTPS и файл reader из главы repository. Следующие export сохраняют окружение этой оболочки для всех последующих tidy/test/build, а не только одной команды. Файлы кэшей принадлежат опыту; постоянный go env -w не используется. Сам download внутренней версии выполните после её публикации в следующей главе: до этого отсутствие v1.0.0 ожидаемо.

export GOENV=off GOWORK=off GOTOOLCHAIN=local GOAUTH=netrc
export GOPROXY=https://nexus.lab.example/repository/go-all/
export GOPRIVATE=example.invalid GONOPROXY=none
export GONOSUMDB=example.invalid GOSUMDB=sum.golang.org
export NETRC="$lab_root/lab-secrets/reader.netrc"
export GOMODCACHE="$lab_root/lab-work/client-a-mods"
export GOCACHE="$lab_root/lab-work/client-a-build"
cd "$lab_root/labs/service" || exit
go mod download -json example.invalid/Acme/ledger@v1.0.0

export передаёт значения дочерним Go-процессам, пока открыт этот терминал. Запись NAME=value go ... без export действовала бы только на одну команду; следующий tidy мог бы уйти к обычному публичному источнику. GOENV=off исключает файл постоянных пользовательских Go-настроек, GOWORK=off — случайный родительский workspace. GONOPROXY=none переопределяет наследование от GOPRIVATE: внутренний модуль тоже получает Nexus. GONOSUMDB=example.invalid исключает только учебный префикс из внешнего журнала; публичные модули сохраняют проверку. NETRC сообщает Go абсолютный путь к файлу учётных данных. Один лишь лежащий рядом reader.netrc Go не выбирает. Шаблоны приватности сопоставляются с префиксами module paths по правилам Go, а не с URL, содержащим https.

При GOPRIVATE=example.invalid без отдельного GONOPROXY Go по умолчанию пойдёт direct, напрямую к системе исходников/metadata модуля, минуя Nexus. В нашем зарезервированном домене это завершится ошибкой, даже если нужная версия уже опубликована в go-internal. Установка GONOSUMDB=* или GOSUMDB=off для всей команды убирает внешнюю проверку и публичных модулей; это не нейтральный способ «не кэшировать sumdb». Сохраняйте отдельный узкий список исключений и доверенное go.sum.

Запятая и вертикальная черта меняют политику отказа

GOPROXY='https://nexus.lab.example/repository/go-all/,direct' go mod download
GOPROXY='https://nexus.lab.example/repository/go-all/|direct' go mod download

Запятая допускает следующий источник при 404 Not Found или 410 Gone. При 401/403 и 5xx обычная comma-цепочка останавливается: авторизация или неисправность не объявлены отсутствием версии. Вертикальная черта разрешает fallback при любой ошибке запроса источника, включая отказ доступа или недоступность. direct означает прямое разрешение из VCS, а не «ещё один URL Nexus». off запрещает обращение к источникам модулей; уже имеющиеся локальные входы могут оставаться достаточными.

 | Ответ первого источника | Через запятую | Через | | Смысл риска

 | 404 / 410 | Переходит дальше | Переходит дальше | Имя приватного модуля может уйти следующему источнику

 | 401 / 403 | Останавливается | Переходит дальше | Проверка policy может быть обойдена альтернативным источником

 | 500 и другие ошибки | Останавливается | Переходит дальше | Повышается доступность, но расширяется путь доверия

Таблица проверена реальным Go 1.27.3 на двух локальных HTTP servers с отдельным чистым GOMODCACHE для каждого случая. Это проверка клиентской политики, не доказательство кодов, которые Nexus вернёт при конкретной настройке. Для закрытого namespace используйте только контролируемый endpoint без внешнего fallback. Один общий public proxy после внутреннего endpoint не знает, что имя должно оставаться тайной. Group routing внутри Nexus и fallback списка Go — два разных уровня, исследуйте оба.

Учебный example.invalid не содержит настоящего закрытого имени, поэтому здесь исследуется go-all. Его internal-first порядок не гарантирует приватность: если внутренний member ответит отсутствием, group может обратиться к go-public. Настройки GOPRIVATE/GONOSUMDB управляют Go-клиентом и не запрещают этот серверный запрос. Для настоящих закрытых координат используйте выделенный внутренний endpoint без публичного member и выдайте reader чтение именно этого endpoint. Перед переносом настоящего namespace проверьте на искусственном имени, что исходящего запроса нет.

1. Чистый cache

Результат нельзя получить из предыдущего опыта.

Действует: Harness.

Go command: задан список; Первый endpoint: готов; Separator policy: comma; Второй endpoint: готов; Module cache: пуст

Условие: случайный cache → новый каталог. Без этого requests второго источника не доказывают policy.

2. Первый отвечает 404

Отсутствие допускает comma fallback.

Действует: Первый HTTP server.

Go command: ждёт; Первый endpoint: 404; Separator policy: comma: not found; Второй endpoint: пока не запрошен; Module cache: пуст

Ответ: GET отправлен → 404 Not Found. Это оговорённое отсутствие, а не неправильный пароль.

3. Comma идёт дальше

Второй endpoint действительно получает запрос, затем Go проверяет fixture.

Действует: Go.

Go command: download успешен; Первый endpoint: 404; Separator policy: fallback разрешён; Второй endpoint: GET наблюдался; Module cache: module v1

Наблюдение: второго GET нет → второй GET есть. Переход может раскрыть приватный module path следующему источнику.

4. Новый case: 403 + comma

С новым cache первый источник отказывает в действии.

Действует: Go.

Go command: download ошибка; Первый endpoint: 403; Separator policy: comma: stop; Второй endpoint: не запрошен; Module cache: пуст

Политика: 404 допускает → 403 останавливает. Authorization error нельзя автоматически назвать отсутствием.

5. Ещё один case: 403 + pipe

Вертикальная черта сознательно расширяет класс ошибок для перехода.

Действует: Go.

Go command: получает со второго; Первый endpoint: 403; Separator policy: pipe: any error; Второй endpoint: GET наблюдался; Module cache: загрузка

Separator: comma → pipe. Повышает доступность и меняет границу enforcement/приватности.

6. Сохранены реальные результаты

Так же проверены 410, 401 и 500; без внешней сети.

Действует: Harness.

Go command: матрица завершена; Первый endpoint: разные statuses; Separator policy: сравнено 10 cases; Второй endpoint: requests учтены; Module cache: изолированы

Доказательство: описание поведения → checks в results.json. Это доказательство Go-клиента выбранной версии, не Nexus deployments.

Что доказывает go.sum

go.sum хранит ожидаемые суммы для module/version и go.mod. Это не lock-файл всего build: выбранный граф задают go.mod и правила разрешения версии; в go.sum могут оставаться дополнительные записи. При первой загрузке публичного модуля Go при необходимости получает запись из checksum database и проверяет криптографически проверяемый журнал. Nexus Go proxy хранит исходные файлы; это не автоматически сервер checksum database. Официальная настройка допускает отдельный raw proxy к sum.golang.org для доставки журнала, но такой raw — транспорт checksum protocol, а не Go hosted module repository.

Приватный модуль не обязан существовать в публичном sumdb. Тогда первоначальному trusted hash нужна другая опора: проверенная публикация, доступ, review исходников и сохранённое go.sum. После того как trusted go.sum есть, GONOSUMDB не разрешает молча заменить версию. Локальная проверка изменила ledger.go внутри пригодного ZIP и получила checksum mismatch на чистом клиенте с прежним go.sum. Удалять строку суммы, чтобы «сборка прошла», означает принять другие байты без объяснения. Сначала расследуйте publisher, URI, кэш и исходный ожидаемый выпуск.

go mod download -json example.invalid/Acme/ledger@v1.0.0
go mod verify
GOPROXY=off go mod verify
go env GOPROXY GOPRIVATE GONOPROXY GONOSUMDB GOSUMDB

go mod verify пересчитывает суммы загруженного ZIP и распакованного каталога и сравнивает их с хешами, сохранёнными в кэше при загрузке. Он не скачивает заново исходники отсутствующего модуля ради проверки содержимого и не является подписью издателя. Однако для построения списка выбранных модулей команда может получить недостающие go.mod, проверить их через go.sum и добавить недостающие строки в go.sum. Поэтому вариант с GOPROXY=off ограничивает такой путь получения и может отказать, если локальных metadata недостаточно. Успех обоих запусков в уже подготовленном опыте не доказывает, что verify вообще никогда не использует сеть. download -json сообщает локальные Info/GoMod/Zip/Dir, Sum/GoModSum либо Error; проверяйте также код завершения и stderr. go env показывает эффективное окружение, а go env -w изменил бы постоянную настройку.

Credential и чистый клиент

Для HTTPS храните служебные credential в отдельном nexus.netrc с правами 0600 либо в предусмотренном credential helper. netrc сопоставляет machine с host, не с конкретным repository path; это надо учитывать, когда один host обслуживает разные доверенные области. В Go 1.24+ механизм GOAUTH управляет получением credential; GOAUTH=netrc выбирает netrc, а GOAUTH=off выключает этот механизм. В нашем loopback fixture нет аутентификации и GOAUTH=off защищает опыт от случайного чтения личных секретов. Рецепт Nexus использует реальный HTTPS и узкую CI-личность.

«Чистый клиент» — новый GOMODCACHE, сохранённые исходники/go.mod/go.sum и контролируемые GOPROXY/GOENV/GOTOOLCHAIN. Это не удаление всего пользовательского ~/go. Создайте отдельный временный каталог и передайте его как GOMODCACHE; GOCACHE отдельно хранит результаты компиляции. Без GOTOOLCHAIN=local требуемая go directive может вызвать загрузку toolchain и добавить сетевой путь, который ошибочно примут за скачивание библиотеки. Локальный тест использует подготовленный Go 1.27.3 и не ходит во внешний интернет.

Первичные источники: Private modules, клиентский fallback, sumdb client, GOAUTH, дата сверки 1 ноября 2026. Примеры Sonatype настройки sumdb сопоставлены с правилами Go; выключение суммы для всех модулей здесь не рекомендуется.

Именно Go hosted выбранной версии

Согласно Go CLI Usage, hosted upload доступен с 3.93, а Create a Go Repository описывает Go recipe. В CE 3.97.3 отправляем ZIP через PUT в /repository/go-internal/v1.0.0.zip. Серверный формат извлекает модульную идентичность и создаёт ответы протокола для клиента. Это не raw repository с вручную выложенным go.mod и не произвольный REST components multipart, поля которого нельзя переносить из Maven.

curl --fail-with-body --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/publisher.netrc" \
  --upload-file 'lab-work/proxy/example.invalid/!acme/ledger/@v/v1.0.0.zip' \
  --dump-header publish.headers \
  https://nexus.lab.example/repository/go-internal/v1.0.0.zip

--upload-file для HTTP выбирает PUT и передаёт файл; дополнительное -X PUT не нужно. --fail-with-body оставляет полезное тело HTTP-ошибки и возвращает ненулевой статус; это флаг curl 7.76+. Если ваша curl старее, выберите поддерживаемый --fail и отдельное контролируемое сохранение диагностики. Файл publisher.netrc хранит credential только издателя, с правами 0600. Не подставляйте пароль прямо в -u user:password в истории оболочки. При 401 проверьте аутентификацию, при 403 роль, при 404 имя/recipe/путь, при 4xx format validation — ZIP prefix, go.mod и версию; точный ответ запишите с серверной версией.

Официальная страница на дату проверки содержит в одном описании prefix знак &, тогда как протокол Go и примеры требуют @. Здесь осознанно выбран module@version/, и пригодность архива подтверждена реальным Go 1.27.3 на локальном HTTP-fixture. Это не подтверждение самого Nexus upload: серверный рецепт должен пройти отдельную приёмку. Наши источники и границы исполнения не скрывают это различие.

Почему нужны и модуль, и бинарник

Go hosted отдаёт исходники для toolchain клиента. Raw hosted хранит произвольно организованные файлы и подходит для готовой программы, checksums и manifest, описания выпуска. Он не интерпретирует go.mod как Go proxy и не создаёт @v endpoints из обычной загрузки файла. Если эксплуатационной машине нужен один заранее проверенный pulse, ей не обязательно иметь компилятор. Но тогда выпуск обязан явно указать платформу, версию, размер и идентичность программы.

mkdir -p dist
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -buildvcs=false \
  -ldflags='-X main.version=1.0.0' \
  -o dist/pulse-linux-amd64 ./cmd/pulse
go version -m dist/pulse-linux-amd64
sha256sum dist/pulse-linux-amd64

GOOS/GOARCH выбирают целевую ОС/архитектуру; кросс-собранный Linux ELF не запускается автоматически на Windows. CGO_ENABLED=0 исключает cgo в поддерживаемых пакетах, но не обещает совместимость с любой средой или отсутствие зависимостей вроде CA/DNS. -trimpath убирает выбранные пути исходников из build output; -buildvcs=false выключает автоматическую VCS stamp, поэтому исходный commit надо сохранить в manifest отдельным доверенным полем. Без trimpath личные пути могут попасть в артефакт. -X main.version=1.0.0 меняет строковую переменную main.version при линковке; это не версия модуля ledger.

Сравните сборку с -ldflags='-X main.version=1.0.0' и без него в разных файлах: pulse -version покажет 1.0.0 против development. Изменяется программа, поэтому хеши отличаются. Утверждение о reproducible build, воспроизводимой сборке, требует одинаковых существенных входов, toolchain и флагов и отдельного повторного опыта. Одного совпадения version string недостаточно. В нашем локальном тесте бинарник собирался и запускался как Linux/amd64; перенос на другую платформу не проверялся.

Структура выпуска и неизменяемый путь

В raw-candidates используем путь pulse/1.0.0/linux-amd64/ с тремя файлами: pulse-linux-amd64, manifest.json, SHA256SUMS. Manifest содержит schema, version, file, size_bytes, sha256, toolchain, source_module, target и версии module inputs. В реальном процессе добавляют commit и идентификатор доверенного CI build. Поля не должны притворяться выполненной проверкой: нет commit — значит нет заявления о конкретном commit. Локальный fixture сохраняет только известные ему сведения.

Сначала создайте все три локальных файла. После сборки из labs/service вернитесь в рабочий корень и выполните:

cd "$lab_root" || exit
python3 labs/artifacts.py manifest --binary labs/service/dist/pulse-linux-amd64 \
  --version 1.0.0 --toolchain "$(go version)" --input-version v1.0.0 \
  --output labs/service/dist/manifest.json || exit
(cd labs/service/dist && sha256sum pulse-linux-amd64 > SHA256SUMS) || exit
python3 labs/artifacts.py verify --manifest labs/service/dist/manifest.json \
  --directory labs/service/dist || exit
cd "$lab_root/labs/service" || exit

Выполняйте следующий шаг только при успехе предыдущего. Manifest output создаётся как новый файл; существующий manifest не перезаписывается. При повторном занятии сначала проверьте уже сохранённый комплект. Для нового build используйте отдельный каталог и новый version path. Флаг --input-version сообщает известную вам выбранную версию ledger; helper не читает module graph из бинарника. Поля source_module и target заданы для нашего опыта, а --toolchain сохраняет переданную строку. До утверждения происхождения сопоставьте их с go version -m и реально выполненной командой сборки. Чтение этих строк из JSON само не проверяет платформу или процесс сборки.

curl --fail-with-body --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/publisher.netrc" \
  --upload-file dist/pulse-linux-amd64 \
  https://nexus.lab.example/repository/raw-candidates/pulse/1.0.0/linux-amd64/pulse-linux-amd64
curl --fail-with-body --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/publisher.netrc" \
  --upload-file dist/manifest.json \
  https://nexus.lab.example/repository/raw-candidates/pulse/1.0.0/linux-amd64/manifest.json

Аналогично передаётся SHA256SUMS. Это отдельные HTTP-операции, не атомарная публикация целого каталога. Чтобы consumer не увидел половину release, сначала загружают файлы, затем проверяют их чтение отдельной ролью и лишь последним шагом обновляют доверенный release record/указатель, или публикуют единый проверяемый архив. В учебной схеме version path считается доступным к продвижению только после проверки полного списка. Не используйте latest как единственное имя результата.

Адрес raw-releases в следующем запросе станет доступен после продвижения главы 11. Сейчас создан только candidate: его читает release-verifier из raw-candidates с собственным файлом учётных данных. Не открывайте candidates обычному reader ради предварительного GET и не считайте ожидаемое отсутствие ещё не выпущенного 1.0.0 неисправностью хранения.

Загрузка до исполнения

curl --fail --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/reader.netrc" --output downloaded-pulse \
  https://nexus.lab.example/repository/raw-releases/pulse/1.0.0/linux-amd64/pulse-linux-amd64
sha256sum downloaded-pulse

Полученный файл сначала проверяется, затем получает executable bit и запускается в нужной среде. Имя в checksum list должно соответствовать локальному имени либо проверка явно сопоставляет их; переименование в downloaded-pulse не делает строку pulse-linux-amd64 подходящей для слепого sha256sum -c. Manifest из того же неподтверждённого источника обнаруживает случайную порчу, но не доказывает происхождение, если атакующий способен заменить оба файла. Доверенный подписанный manifest, контролируемый CI record и право публикации создают опору ожидаемого хеша.

Учебный artifacts.py verify ограничивает имя basename, запрещает symlink и требует обычный файл, затем сравнивает размер и SHA-256. Это ограниченный проверяющий инструмент, не sandbox для исполнения недоверенной программы. Он не реализует защиту от гонки между проверкой и запуском в каталоге, изменяемом другим писателем. Для установки используют каталог, закрытый на запись посторонним, и атомарное продвижение проверенного файла. В тесте проверяется порча с сохранённым размером, чтобы доказать необходимость хеша сверх размера.

Удаление — действие API, не rm в blobs

Для ошибочного тестового кандидата сначала получите точный asset ID через search/assets и сверните pagination. Затем API выбранной версии допускает DELETE /service/rest/v1/assets/{id}. Удаляющая роль отделена от publisher; dry-run для произвольного DELETE не предполагается. Сначала сравните repository, path, ожидаемую сумму и связь с release record. Удаление component может затронуть несколько assets, поэтому его scope проверяют отдельно. Выпущенный релиз удаляется только по принятой retention-политике; учебная неисправность не оправдывает удаление истории.

Какой формат выбран

В CE 3.97.3 доступны Docker repositories и новый native OCI recipe, появившийся в 3.94. OCI, Open Container Initiative — открытые спецификации образов и их распределения. Для нового учебного oci-internal используем OCI hosted и path-based routing; не подменяем его Docker recipe с connector port и не переносим все настройки между ними. По OCI Repositories поддерживаются hosted/proxy/group. Точная пригодность клиентов, referrers и форматов подписей требует приёмки выбранных версий.

Registry хранит manifest, документ ссылок на config и layers; layer, слой содержимого файловой системы; image index, список платформенных manifest. Digest идентифицирует точные байты соответствующего объекта, например sha256:... манифеста. Tag — изменяемое имя, ссылающееся на manifest/index. Digest одного слоя, SHA-256 raw-бинарника и digest multi-platform index относятся к разным байтам и не должны подставляться друг вместо друга.

Путь registry отличается от raw

Для path-based OCI адрес клиента имеет вид nexus.lab.example/oci-internal/team/pulse:1.0.0; сегмент /repository/ в имени образа не добавляется. Клиент registry использует API /v2/ с маршрутизацией Nexus. Для OCI активируется OCI Bearer Token Realm; для старого Docker recipe — Docker Bearer Token Realm. Realm, источник и способ установления личности, выбирается согласно формату. Успешный login ещё не доказывает push scope к нужному namespace. Subdomain routing имеет отдельное Pro entitlement, право редакции; оно не предполагается у CE.

docker login nexus.lab.example --username ci-pulse --password-stdin
docker tag pulse:1.0.0 nexus.lab.example/oci-internal/team/pulse:1.0.0
docker push nexus.lab.example/oci-internal/team/pulse:1.0.0
docker pull nexus.lab.example/oci-internal/team/pulse@sha256:EXPECTED_MANIFEST_DIGEST

Это рецепт для подготовленного личного Docker-клиента, образа и Nexus, не выполненный авторский тест. --password-stdin читает credential из защищённого входа/менеджера секретов, а не хранит его в аргументе; сама команда без поданного stdin ожидает ввод. tag создаёт локальное имя, не загружает слой. push передаёт нужные blobs, затем manifest/tag, поэтому возможен частичный эффект до финального подтверждения. Последний digest — placeholder, его заменяют реальным проверенным значением из результата и чтения registry. Строку с EXPECTED нельзя выдавать за запускаемую успешную команду.

Ни Docker daemon, ни registry здесь не устанавливались. Чтобы собрать контейнер для собственного pulse, сначала приготовьте доверенный базовый image по digest либо подходящий минимальный runtime contract, положите тот же проверенный бинарник и нужные runtime-данные. Сборка image меняет контейнерный manifest; это отдельный release object со своей проверкой. Raw checksum бинарника остаётся полезным входом provenance, сведений о происхождении, но не заменяет image digest.

Bearer challenge не равен anonymous allow

Клиент обращается к /v2/, получает challenge, узнаёт token service и scope, затем предъявляет credential, получает ограниченный токен и повторяет запрос. Поэтому 401 на первом registry probe может быть нормальной частью протокола; окончательный неуспех после credential — другое состояние. Reverse proxy обязан сохранить challenge и внешние адреса. Если token service указывает внутренний localhost, внешний клиент не сможет завершить обмен, даже когда UI открывается по HTTPS.

Для anonymous pull недостаточно снять флажок password requirement в произвольном месте: нужна согласованная анонимная личность, read scope и правильный realm. Проверяйте новый клиент без сохранённого login отдельно от служебного издателя. Content selector для image namespace должен учитывать служебные пути manifest/layers и базовый /v2/; правило для одного красивого tag URL может ломать push. Исправление 3.97.3 касается Docker push с одними selector permissions, поэтому перенос на старую версию требует отдельной сверки.

Чем измерять и что сохранять

Registry часто передаёт уже существующие слои только однажды. Request hit ratio и byte hit ratio снова различаются. Для образа 200 MiB со слоем приложения 12 MiB изменение одного слоя может передать около 12 MiB плюс metadata при общих сохранённых остальных слоях; это условный пример, не обещание точного сетевого объёма из-за сжатия, платформ и повторов. Для promotion записывайте digest исходного и целевого manifest, platform и список referrers. Копирование между registry инструментом может перекодировать manifest; совпадение tag не доказывает совпадения digest.

Upstream credentials и следы утечки

Authentication раньше authorization

Authentication, аутентификация, устанавливает, кто обращается: локальный user, внешний каталог или токен поддержанного realm. Authorization, авторизация, решает, разрешено ли этой личности действие над данным ресурсом. Realm — подключаемый источник/механизм аутентификации, а не роль. Role — набор privileges, элементарных разрешений; privilege содержит формат, repository, действие либо другую область управления. Включение LDAP realm не наделяет всех пользователей правом публиковать.

В нашем CE стенде остаются Local Authenticating Realm и обычные локальные users для администратора, reader, ci-publisher, release-verifier и release-promoter. Служебная учётная запись — отдельный local user, используемый автоматизацией, а не общий admin-пароль. Нативные Service Account Tokens sat.* 3.97 — отдельная функция: официальная страница маркирует её Pro/Pro+/Cloud. Расширение поддержки всех форматов в notes не означает доступность SAT в выбранной CE. User Token Realm тоже имеет редакционные ограничения. Для CE рецепт использует узкий local user, защищённый secret store CI и ротацию пароля.

Не удаляйте все активные realms и сохраняйте аварийную локальную административную личность. Имя, совпадающее в локальном и внешнем источнике, требует проверки порядка realm. Изменение внешнего group mapping может менять эффективные роли после обновления сессий/кэшей. Проверяйте действия новой отдельной сессией, а не только открытой вкладкой admin, которая скрывает недостаток полномочий будущего клиента.

Матрица действий стенда

 | Личность | Разрешённый путь | Что отдельно запрещено

 | reader | read/browse go-all и raw-releases | Upload в hosted, удаление, настройки, raw-candidates

 | ci-publisher | Необходимые format actions только go-internal и raw-candidates | raw-releases, управление пользователями, cleanup, delete

 | release-verifier | Чтение raw-candidates для проверки полного комплекта | Публикация releases, удаление, управление users

 | release-promoter | Чтение согласованного candidate; запись в raw-releases | Сборка по произвольному коду, общие административные права

 | maintenance | Конкретные нужные tasks и наблюдения | Публикация от лица developer без причины

 | admin | Настройка экземпляра и аварийные операции | Обычные CI job не получают его credential

Названия встроенных привилегий вида nx-repository-view-raw-raw-candidates-add, ...-edit, ...-read, ...-browse, ...-delete генерируются для формата/репозитория. Внутренний permission string разделяется двоеточиями, например nexus:repository-view:raw:raw-candidates:read; это другой синтаксис представления. Не выдавайте nx-all только потому, что первый PUT получил 403. Формат может требовать сочетания add/edit из-за метода/обновления metadata: сначала выясните необходимый набор по точному запросу и минимальному позитивному тесту.

Privileges дают разрешения аддитивно. Если одна роль даёт raw:*, другая с selector только /pulse/ не сужает первую. Сначала удаляют избыточный общий grant, затем проверяют положительный и отрицательный пути. Удобная человеческая метка «read-only» не имеет силы, если вложенная роль содержит delete. Периодический review должен раскрывать весь effective набор, включая inherited и default roles.

Content selector ограничивает адресуемую область

Content selector — выражение отбора содержимого, которое связывается с отдельной privilege, а затем ролью. Для raw кандидатов разумный базовый CSEL, content selector expression language — язык условий отбора, имеет вид format == "raw" and path =^ "/pulse/". =^ означает prefix; path включает ведущий слеш. Префикс /pulse/ не совпадает с /pulsex/, в отличие от небрежного /pulse. Для Go basic support поддерживает format/path, не выдуманные go.team поля.

Selector — не автоматическое понимание всего формата. List/metadata/ZIP могут иметь разные пути, upload Go идёт на /v1.0.0.zip, а координата модуля извлекается из тела. Поэтому selector по красивому пути module download нельзя объявить доказанной защитой Go upload namespace без испытания точной версии. Для этого учебного publisher выбран отдельный go-internal repository; строгую многокомандную namespace-публикацию проектируют после негативного теста чужого модуля. Regex, regular expression — регулярное выражение, полезно только когда prefix недостаточен; сложные вложенные повторения могут дороже выполнять запросы и осложняют review.

Anonymous и group расширяют аудиторию

Если анонимное чтение включено, anonymous user получает конкретные роли. Широкая роль read всех repositories открывает и будущие hosted, если её wildcard охватит их. Начните с отключённого anonymous; для намеренно открытого public cache дайте только выбранный endpoint. Права на go-all открывают содержимое member через group. Reader может получить internal module через group без прямого read go-internal; это штатная семантика, а не доказательство обхода. Нельзя включать закрытый repository в общедоступную группу без review.

Позитивные/негативные тесты выполняйте credential каждой роли: GET known release, PUT нового кандидата, PUT чужого пути, GET кандидата reader, DELETE точного тестового asset publisher. Предварительно пометьте одноразовые данные и сохраните резерв. Ожидаемый отказ проверяют по отсутствию эффекта и по ответу; только HTTP-код недостаточен, если передний прокси переписал ошибку. Запросы без credential и с неверным credential — разные тесты; anonymous fallback иногда меняет наблюдаемый результат.

4. Нужен remote fetch

Proxy miss выбирает исходящий HTTP client с собственным credential.

Действует: Proxy.

Go reader: ждёт; TLS proxy: ждёт backend; Nexus identity: reader не меняется; Group endpoint: member miss; Proxy client: remote-user; Закрытый upstream: запрос впереди

Credential: reader → Nexus → remote-user → upstream. Входной пароль нельзя произвольно пересылать наружу.

5. Upstream решает отдельно

403 от remote не исправляется выдачей Nexus reader прав администратора.

Действует: Remote.

Go reader: ждёт ответ; TLS proxy: ждёт; Nexus identity: reader read; Group endpoint: ждёт member; Proxy client: свой TLS/remote auth; Закрытый upstream: разрешение своей области

Граница: Nexus разрешил read → remote проверил свою личность. Участники имеют независимые ACL и trust stores.

6. Аудит фиксирует нужную область

Сопоставляют request и server diagnostics без публикации secrets.

Действует: Оператор.

Go reader: получил ответ; TLS proxy: status/elapsed; Nexus identity: reader действие; Group endpoint: выбранный member; Proxy client: upstream status; Закрытый upstream: свой журнал

Расследование: один код без причины → два направления запроса. Logs не должны становиться каналом credential leakage.

Upstream credentials и следы утечки

Учётные данные Nexus→upstream задаются у proxy/HTTP client и не должны уходить Go-клиентам. Это отдельный secret с разрешением чтения upstream. Не пересылайте входной Authorization пользователя на произвольный remote. Redirect на другой host, access logs, trace HTTP, support ZIP и CI artifacts могут расширить аудиторию секрета. Маскирование в UI не предотвращает код job, который прочитал и отправил пароль. Ротация включает изменение секрета, обновление клиентов, проверку новой личности и отзыв старого значения, а не лишь переименование файла.

Аудит, audit — сохранённая история действий, должен отвечать кто/что/когда/где с ограничением доступа и сроком. Request log не всегда содержит прикладной результат; audit событие не всегда означает доступные байты. В 3.97.1+ persistence audit events по умолчанию выключена по notes ветки, поэтому нельзя обещать существование полной таблицы аудита без настройки. Проверьте фактический output и retention. Что именно допускается к доставке

Build — конкретное вычисление программы из исходников, module graph, toolchain, флагов и среды. Выпуск — выбранный результат этого вычисления с неизменяемой идентичностью и договором использования. Если stage протестировал H1, а production заново выполнил go build того же tag и получил H2, проверка stage автоматически к H2 не переносится. Даже когда воспроизводимая сборка ожидается, её надо подтвердить равенством, а не предполагать по имени commit.

В нашем процессе CI создаёт candidate 1.0.0, сохраняет бинарник, manifest и checksum, затем отдельный verify job получает их в новом каталоге от имени release-verifier с чтением candidates, проверяет trusted expected hash и запускает tests/smoke. Smoke test, короткая проверка базовых функций, включает -version, /healthz, /version и /hello у запущенной программы в выделенной среде. Проверка целостности выполняется до исполнения. Verify сохраняет доказательство с hash H1 и идентификатором job; promoter получает именно H1. Объявление approved не должно указывать на изменяемое latest.

Пять разных хранилищ

 | Объект | Основная задача | Почему не заменяет остальные

 | GOCACHE/CI cache | Ускорить повтор вычисления | Можно потерять; не обязательный канал доставки

 | Job artifact | Передать результат конкретного job | Имеет срок/доступ CI и может исчезнуть до поддержки release

 | Hosted repository | Долго хранить именованный выпуск для клиентов | Не хранит автоматически всю историю CI и резерв отдельно

 | Proxy cache | Сократить обращения к внешнему источнику | Наличие кешированной копии не формулирует retention собственного release

 | Backup | Вернуть согласованное состояние после потери | Не является обычным клиентским package endpoint

Checksum подтверждает равенство байтов при известном ожидаемом значении. Подпись manifest связывает это значение с ключом издателя; её доверие зависит от распространения ключа, срока и отзыва. Provenance — сведения о происхождении, включая inputs и процесс сборки; её правдивость зависит от CI identity и доверенного исполнения. SBOM, software bill of materials — перечень составляющих, описывает состав, но сам не разрешает выпуск. Эти доказательства дополняют друг друга, а не становятся одним словом «безопасно».

2. Candidate сохранён

Файл и metadata выпуска переданы на определённый path.

Действует: CI.

CI build: завершён; Raw candidates: H1 + manifest; Verify job: готов к чтению; Promoter: ждёт; Raw releases: нет; Consumer: нет

Хранение: workspace CI → repository candidate. CI cache не используется как обязательный release channel.

Новая среда проверяет trusted hash до исполнения и затем smoke.

CI build: готов; Raw candidates: H1; Verify job: hash/smoke H1; Promoter: ждёт decision; Raw releases: нет; Consumer: нет

Допуск: upload успешен → проверен H1. Проверка относится к hash, а не изменяемому latest.

4. Promoter получил решение и файл

У promoter нет необходимости пересобирать source.

Действует: Promoter.

CI build: не вызывается; Raw candidates: H1; Verify job: approved H1; Promoter: проверил H1; Raw releases: подготовка; Consumer: ждёт

Вход: номер версии → bytes и решение H1. Новый случайный rebuild создал бы другой предмет проверки.

5. Конечный path проверен

После отдельных upload проверяется полнота комплекта, затем release record.

Действует: Promoter.

CI build: готов; Raw candidates: H1 сохранён; Verify job: approved; Promoter: конечный hash H1; Raw releases: H1 + manifest; Consumer: допущен

Публикация: несколько HTTP эффектов → полный проверенный комплект. Три PUT не общая атомарная операция.

6. Consumer проверяет H1

Среда доставки получает тот же файл, не просто строку 1.0.0.

Действует: Consumer.

CI build: не нужен; Raw candidates: по retention; Verify job: evidence сохранено; Promoter: готов; Raw releases: не перезаписывается; Consumer: hash H1 совпал

Идентичность: имя release → равенство bytes. Откат программы отдельно от возврата данных приложения.

Перенос raw без выдуманного copy API

Не обещаем CE универсальный server-side staging/copy API для всех форматов. Наш portable путь: promoter скачивает выбранные файлы из raw-candidates в закрытый временный каталог, проверяет manifest и ожидаемое решение verify, загружает эти же файлы в новый неизменяемый raw-releases path и снова скачивает конечный URL под reader. Хеш конечного бинарника должен равняться H1. Изменение target path не должно менять тело бинарника. Нет общего атомарного commit трёх HTTP uploads, поэтому release record публикуется последним после проверки комплекта.

Сеть 100 Mbit/s даёт теоретический максимум 12.5 MB/s до накладных расходов. Перенос 80 MiB через скачать+загрузить читает и пишет около двух тел объёма, и promoter может стать сетевым ограничением. Для нескольких тысяч releases выбирают поддерживаемый форматный механизм по редакции и измерениям. Но оптимизация не должна терять доказательство совпадения. После timeout сначала проверьте destination coordinate/hash; слепой новый build для повтора меняет предмет операции.

Указатель среды и откат

Deployment record, запись доставки, для staging/production содержит version, artifact URL, SHA-256 и конфигурацию среды. Переключение pointer на 1.0.0 после приёмки 1.0.1 — откат бинарника. Оно не возвращает данные приложения к прежней схеме. Если новая программа уже выполнила необратимую миграцию, старый бинарник может не запуститься. Резерв БД приложения и стратегия совместимых миграций относятся к самому приложению, а backup Nexus сохраняет артефакты и metadata Nexus. Не путайте их ответственность.

Для восстановления доступности raw releases запрещайте обычному CI удалять старые approved версии и следите за удержанием их зависимостей/образов. Release без оставшегося manifest, сертификата подписи либо runtime image может оказаться непригодным через год. Контракт хранения задаётся сроком поддержки, а не только числом последних версий. Учебная политика сохраняет 1.0.0 весь практикум, даже после выпуска исправления.

Критерии успешного опыта

Три независимых client directories получают один hash H1: verify, promoter и target verification. Попытка publisher записать raw-releases отвергается; повторная публикация 1.0.0 другими байтами не допускается; новый 1.0.1 существует параллельно. Если manifest и бинарник не совпали, выпуск останавливается до запуска. Это собственный процесс поверх подтверждённых raw операций и прав, а не заявленная встроенная feature Nexus. Расписание и ресурсы

Удержание начинается с договора потребителей

Cleanup policy, политика очистки, выбирает содержимое по возрасту, использованию и доступным форматным критериям; task, фоновое задание, выполняет работу. Наличие policy в UI не доказывает, что подходящее task когда-либо завершилось успешно. Возраст upload, последний download и отсутствие последнего download — разные значения. Редко используемый аварийный release всё ещё может быть обязательным для rollback. Поддерживаемый offline клиент не обязан регулярно обращаться за каждым файлом, чтобы напомнить серверу о его ценности.

Сначала задайте классы: raw-releases хранится весь срок поддержки, raw-candidates — до решения о выпуске плюс ограниченный период расследования, go-internal — по контракту всех поддерживаемых приложений, public proxy cache — по измеренному working set и возможностям повторного получения. Не назначайте одну политику всем repositories ради одинакового интерфейса. Условные 30 days без download для candidates — правило конкретной команды, не рекомендация удалять любой production artifact через месяц.

Доступность возможностей не универсальна

Точная матрица редакции важна и для обслуживания. Cleanup Policies на дату проверки маркирует материал Pro/Pro+/Cloud; «Retain Select Versions» прямо требует Pro и PostgreSQL. Поэтому наш CE/H2 маршрут не зависит от поля «оставить N версий» и не утверждает его наличие. Если в установленном CE доступны базовые cleanup policies/tasks, проверьте конкретный набор критериев в UI/API и негативный fixture перед использованием. Если их нет, ограниченный процесс удаления отобранных тестовых candidates через поддержанный API остаётся явным отдельным действием с review. Это граница документации/редакции, а не повод включать скрытую функцию.

Для поддержанной редакции последовательность такова: создать policy с конкретным format и критериями, назначить её выбранному repository, получить preview, проверить точные paths и исключения, сделать согласованный backup, запустить подходящее cleanup task, сверить результат, затем отдельно принять решение о compaction. Критерии одной policy обычно объединяют условия отбора, а несколько назначенных policies могут расширять набор удаления; проверьте фактическую семантику версии на fixtures. Не предполагайте, что добавление второй policy всегда сужает первую.

Soft delete и compaction

Soft delete, мягкое удаление, помечает сущность/объект как удалённый для обычного доступа, не обязательно немедленно убирая все физические байты. Файл может исчезнуть из поиска и GET, но df всё ещё показывает тот же занятый объём. Compaction, уплотнение/окончательное удаление отмеченного, возвращает физическое место backend. Для поддержанных файловых blob stores есть Admin - Compact blob store; поле Blobs Older Than задаёт период удержания мягко удалённых blobs перед hard delete. Значение 0 не оставляет такого дополнительного окна.

Обычный rm в blobs обходит эти связи. Если диск заполнен, удаление случайного blob по размеру может испортить approved release и оставить DB pointer на отсутствующий объект. Сначала ограничивают новые публикации, собирают сведения о файловых системах, logs/tmp/cache и задачах, сохраняют диагностику, затем освобождают только действительно допустимую область согласованной операцией. Увеличение диска даёт время, но не исправляет отсутствие retention и наблюдения.

Preview не гарантирует будущий результат

Preview — снимок отбора в данный момент. Между ним и task могли появиться новые версии, скачивания либо изменения policy. Сохраните время, query/config и список, установите окно обслуживания, остановите конфликтующие изменения насколько нужно. Проверьте маленький disposable repository, а не единственный archive releases. Собственный эксперимент: две test coordinates A/B, A соответствует условию, B нет; после task A не читается, B читается; после compaction уменьшаются физические байты с учётом задержки/учёта, но восстановление A теперь требует backup.

Отчёт «deleted components: 10» не равен освобождённым 10 GiB. Размеры assets отличаются; несколько manifests могут ссылаться на общие слои, format tasks сначала удаляют ссылки, потом orphaned layers. Для Docker/OCI применяются форматные правила. Особенно осторожно с образами, используемыми только по digest без tag: «нет тега» не равно «никем не используется». Сохраняйте inventory фактически доставленных digest и сверяйте задачу конкретного формата.

Расписание и ресурсы

Резерв, compaction, metadata rebuild и массовые downloads конкурируют за диск, IOPS — число операций ввода-вывода в секунду, и CPU. Если ночной cleanup увеличил p95 клиента с 150 ms до 900 ms при той же сети, сравните latency диска и queue depth, глубину очереди операций, до/во время/после task. Перенос task в другое окно может быть дешевле добавления JVM heap. Дополнительный heap не ускорит медленный storage, когда запрос ждёт I/O. Оставьте запас свободного места под временные объекты и сам backup, прежде чем запускать тяжёлое обслуживание.

Сначала определите границу времени

Latency, задержка, — время от выбранного начала до выбранного завершения. Для клиента различимы DNS, TCP connect, TLS handshake, ожидание первых байтов и полная передача. Для Nexus — очередь обработчика, авторизация, metadata lookup, upstream ожидание, blob I/O и отправка. Throughput, пропускная способность, — завершённые requests/s либо bytes/s за интервал, при определённой смеси. Один 2 KiB .info и 400 MiB image layer не равноценны, даже если оба считаются одним запросом.

curl --fail --show-error --cacert "$lab_root/lab-secrets/ca-bundle.pem" --netrc-file "$lab_root/lab-secrets/reader.netrc" --output /dev/null \
  --write-out 'code=%{http_code} connect=%{time_connect}s tls=%{time_appconnect}s first=%{time_starttransfer}s total=%{time_total}s bytes=%{size_download}\n' \
  https://nexus.lab.example/repository/raw-releases/pulse/1.0.0/linux-amd64/pulse-linux-amd64

--output /dev/null отбрасывает тело после получения и не проверяет его hash, поэтому этот вызов — измерение передачи, а не финальная приёмка release. Времена curl кумулятивны от старта: time_appconnect - time_connect приближённо выделяет TLS для соответствующего нового соединения; переиспользование и redirects усложняют трактовку. --write-out печатает выбранные поля, не меняя сервер. Запишите client location, файл/размер, число соединений, upstream/cache state и наличие прокси.

Матрица опыта вместо одной команды

Выберите фиксированные 20 объектов двух размеров, например 64 KiB metadata bundle и 8 MiB ZIP, и 1/4/8 параллельных клиентов как собственные условия. Первый набор — новые client caches и холодный выделенный proxy. Второй — новые client caches, тёплый Nexus. Третий — тёплые client caches, та же команда Go. Последний может почти не нагружать сервер, поэтому отсутствие запросов — существенный результат, а не «нулевая серверная latency». Не меняйте одновременно размер VM, TTL и параллелизм, иначе причина улучшения потеряется.

Соберите median, p95 и ошибки по каждому классу, не смешивая тысячи быстрых .info с редкими огромными layers. p95 — значение, ниже которого находится примерно 95% выбранных наблюдений; при 10 запросах оценка хвоста нестабильна. Повторите серию с достаточным числом запросов, но не пытайтесь превратить учебный стенд в нагрузочную атаку. CE лимит 100000 requests/day включает много форматных запросов на одно действие; рабочий build может затронуть больше чем один asset. Используйте Usage Center и пределы своего теста.

 | Наблюдение | Проверка гипотезы | Осмысленное изменение

 | Miss медленный, hit быстрый, локальный диск свободен | Измерить upstream latency, TLS, rate limits и bytes | Удерживать полезный cache, исправить remote path/connectivity, не покупать CPU наугад

 | Hit тоже медленный, растут disk latency/queue | Сопоставить blob/db I/O и concurrent tasks | Перенести задачи, подобрать storage/IOPS, разделить конкурирующие области

 | Длинные JVM pauses, heap близок к пределу | GC logs, allocation, live set, out-of-memory и concurrency | Устранить лишний объём/параллелизм, затем подобрать memory budget

 | CPU насыщен без I/O ожидания | Профиль CPU по разрешённой методике, TLS/compression/queries | Уменьшить тяжёлую работу либо добавить CPU после подтверждения

 | Низкий CPU, заполнена очередь запросов | Threads ждут DB/network/disk/locks; downstream медленный | Исправить задерживающую зависимость, а не бесконечно увеличивать threads

Heap, управляемая Java-куча, не равен RSS процесса, resident set size — резидентной памяти ОС. Есть direct buffers, stacks потоков, JVM metadata, code cache и страницы filesystem cache. GC, garbage collection — сборка мусора, возвращает память внутри управляемой модели, но не является compaction blob store. Увеличение Xmx без оставшегося места для off-heap и ОС может вызвать OOM, out of memory — нехватку памяти, при меньших паузах до аварии. Сравнивайте потребление процесса, лимит VM, swap и I/O, а не один график heap.

Не копируйте heap values из старой статьи как универсальные. В vmoptions Xms, начальный heap, Xmx, максимальный, и MaxDirectMemorySize меняют согласованно по документации runtime. После изменения нужен перезапуск и та же серия запросов. Если CPU не занят, а каждый miss ждёт remote 2 s, добавление 4 GiB heap не сокращает обязательную сеть. Добавление потоков увеличивает одновременно открытые соединения, DB work и buffers; длина очереди может лишь переместиться.

Простые расчёты с явными условиями

Предположим устойчиво поступает 20 requests/s, среднее время внутри сервера 0.25 s, ошибок и растущей очереди нет. По закону Литтла среднее число запросов внутри этой границы около L = λ × W = 20 × 0.25 = 5 requests. Это не рекомендация поставить ровно пять threads: реальные хвосты, external waits, смесь и внутренние работы меняют потребность. Если поступает 50 requests/s, а завершается 40, очередь растёт примерно на 10 requests каждую секунду; никакой стационарный расчёт со старым W эту перегрузку не устраняет.

Если в cache ежедневно добавляется 2 GiB новых уникальных blobs и удерживается 30 days, простая оценка 60 GiB не включает metadata, logs, tmp, мягко удалённое содержимое, резерв и запас. При backup ещё на том же диске пик может быть больше двойного объёма. Отдельно оцените restore throughput: возврат 120 GiB при реальных 40 MiB/s занимает около 51 min только для копирования, до проверки БД/запуска/скачиваний. Подмена GiB на GB меняет расчёт: 1 GiB = 2^30 bytes, 1 GB = 10^9 bytes.

Сигналы и право их чтения

GET /service/rest/v1/status/check требует соответствующей metrics read privilege и возвращает зарегистрированные health checks. Код 200 не гарантирует healthy каждого check; особенно читайте Baseline Telemetry. Metrics data endpoint актуальной ветки /service/rest/metrics/data отличается от старого /service/metrics/data. Схему полей берите с точной версии, не выдумывайте названия Prometheus metrics. Request.log, nexus.log и tasks.log отвечают на разные вопросы; trace/debug включает больше данных и должен иметь ограниченное окно и доступ.

Что считаем восстановленным

RPO, recovery point objective — допустимая потеря последних изменений по времени. RTO, recovery time objective — допустимое время возвращения услуги. Если backup сделан вчера, новый опубликованный сегодня внутренний модуль может отсутствовать: это вопрос RPO, а не latency restore. Если данные скопированы за час, но ещё два часа исправляли CA/права и проверяли artifacts, RTO включает все три часа. Успех — не только открывшийся UI: читатель получает нужные версии и те же хеши, неправильная роль получает отказ.

Для нашего standalone H2 наиболее понятный согласованный путь — штатно остановить Nexus, убедиться, что JVM завершилась, затем скопировать полный data-dir, все внешние файловые blob stores, изменённые конфигурации install-dir, нужные secrets/keystores/node identity и запись проверенного дистрибутива. БД и blobs в этот момент неподвижны. Это собственное окно обслуживания: новые uploads не принимаются. Не называйте копию живого nexus.mv.db согласованной только потому, что cp вернул 0.

Рецепт cold backup H2

Ниже команды исполняются администратором только своей VM. Путь назначения — отдельный mounted backup volume с достаточным местом; имена и права проверены заранее. rsync должен быть установлен в VM. Пустая строка path либо ошибка mount не должна направить backup на тот же заполненный root filesystem.

В cold_backup.sh сохранена последовательность для выбранных путей стенда: оба File blob store внутри data-dir, полный install-dir, unit, NGINX и TLS. Перенесите этот собственный скрипт на VM и прочтите его до запуска. Установлены Bash, systemd, rsync и mountpoint из util-linux; /mnt/nexus-backup уже смонтирован на отдельное подготовленное хранилище. Из каталога, куда перенесён файл, администратор выполняет:

sudo bash cold_backup.sh snap-001

Скрипт проверяет обязательные пути и mount до остановки, отказывается использовать существующий snap-001 и создаёт закрытый каталог с отметкой INCOMPLETE. Ошибка systemctl stop прерывает выполнение до копирования. После успешного stop дополнительно требуются ActiveState=inactive и MainPID=0; проверяется KillMode=control-group. Эти наблюдения относятся к процессам данного unit. Они не доказывают отсутствие JVM, которую администратор запустил вручную вне службы, поэтому рецепт предполагает единственного writer, запускаемого только через этот unit, и отсутствие параллельного старта. Если это условие неизвестно, выясните его до холодного резерва.

Каждый rsync проверяется явно, без зависимости от особенностей set -e. При отказе частичная копия остаётся INCOMPLETE, а сервер не перезапускается автоматически посреди незавершённой последовательности. Исправьте причину, сохраните диагностику и примите отдельное решение о возобновлении исходной службы; такой каталог не считается пригодным резервом. Для новой попытки выберите новый номер, не смешивайте старое и новое состояние. Даже отметка COPIED означает только успешное копирование: согласованность и пригодность доказываются изолированным restore и клиентской приёмкой.

rsync -a рекурсивно сохраняет обычные атрибуты, ссылки и состав, --numeric-ids сохраняет числовые UID/GID, а trailing slash у source выбирает содержимое каталога. Эта команда не добавляет автоматически ACL/xattrs/sparse-семантику; при их использовании нужен соответствующий согласованный способ копирования. Здесь нет --delete. Скрипт не проверяет смысл всех backend-конфигураций, свободное место наперёд или независимость носителя: выбранные пути, достаточная ёмкость, внешний носитель и отсутствие сторонних writers проверяются администратором до запуска.

Рецепт охватывает blob stores только внутри data-dir. При внешнем Path, PostgreSQL, object storage или другом install-dir его нужно заменить поддержанной процедурой для фактического экземпляра, а не запускать без изменения. В нашем варианте копируется весь install-dir с JVM и изменёнными vmoptions, поэтому учитывайте дополнительный объём и длительность. TLS-копия содержит закрытый ключ сервера и требует доступа только администратора и шифрования резерва. Сохраните перечень файлов и хеши в защищённом месте, отдельно проверьте возврат прав на другой VM. Ни успешный rsync, ни backup на том же физическом диске не защищают от отказа этого диска.

Ограничены writers и JVM штатно завершилась.

Прежняя версия приложения и права подготовлены до открытия состояния.

Возврат: повреждённая/пустая копия → metadata + bytes T1. Нельзя собрать самый новый DB и самый старый blob store без плана reconcile.

5. Запущена копия

Проверены startup и конфигурация; data-dir открыт только одним H2 процессом.

Действует: Nexus.

RTO: копирование окончено → приёмка услуги окончена. Сеть, TLS и права входят во время возврата услуги.

Почему H2 task не равно полный backup

Admin - Backup H2 Database создаёт backup БД и временно приостанавливает её запись, но не сохраняет содержимое blob stores. Backup and Restore H2 Database рекомендует регулярный offline backup и возврат соответствующих blobs с тем же моментом. Если DB snapshot содержит запись нового asset, а blobs snapshot сделан до upload, GET получит metadata о несуществующем объекте. Если blobs новее БД, могут остаться bytes без доступной через metadata координаты. Автоматическое «выбрать самые новые файлы из разных резервов» не возвращает согласованность.

Внешний PostgreSQL меняет процедуру: нужен поддержанный PostgreSQL backup/restore, параметры подключения и согласованное покрытие blob stores, а не копирование H2 db folder. Возможности PITR, point-in-time recovery — возврата БД к моменту времени, относятся к БД и её журналам, но сами не возвращают object storage к тому же состоянию. Инструкция этого стенда не обещает универсальный online snapshot для любого backend и HA.

Restore в изолированную копию

Создайте другую личную VM/диски без доступа старых CI writers. Получите тот же проверенный дистрибутив и Java, заведите совместимый UID/GID, верните data-dir и внешние blob paths при остановленном Nexus, сохранённые конфиги и нужный ключевой материал. Node ID файлы $data-dir/keystores/node/ учитываются согласно инструкции восстановления. Отредактируйте только обязательные адреса новой изолированной копии, исключив конфликт с исходным URL и исходящими изменяющими интеграциями. Один data-dir не открывается двумя процессами H2.

Не направляйте reader на копию до приёмки. Проверьте startup/schema, версию, список repositories/roles, известный direct asset GET и SHA-256, новый чистый Go client с сохранённым go.sum, отрицательный publish от reader. Сравните количество/идентичность выбранных critical releases и прочитайте образ по digest, если он входил в контракт резерва. Только после этого решают переключить DNS/proxy и разрешить writers. Устаревшие service credential или TLS могут остановить клиентов после технически успешного restore; это тоже часть RTO.

Какое metadata можно вывести заново

Отделяйте потерю bytes от потери производного представления. Дерево Browse показывает навигацию по имеющимся metadata. Если direct GET известного пути проходит и SHA совпадает, а ветка UI не видна, это не повод удалять blob или импортировать все bytes заново. Сначала проверяют роль/search criteria, затем при подтверждённом дефекте производного дерева рассматривают Repair - Rebuild repository browse. Поиск имеет отдельное перестроение Repair - Rebuild repository search. В текущем SQL-поколении нельзя переносить инструкции настройки Elasticsearch из старой статьи.

Если metadata asset отсутствует, а blob с достаточными атрибутами существует, нужен уже другой класс восстановления. В современной линии Repair - Data Repair Plan формирует план несогласованностей, а отдельное исполнение применяет выбранные изменения. Старый reconcile component database заменён этим механизмом; не выбирайте старую задачу только по знакомому имени. Recovery mode, специальное состояние восстановления, рекомендуется для исполнения reconciliation, чтобы ограничить конфликтующие изменения. Вначале читают план и его scope, сохраняют backup и фиксируют, какие records/bytes он затронет.

Например, browse rebuild не восстановит отсутствующий ledger ZIP: он строит навигационную структуру из доступного состояния, а не компилирует исходники из checksum. Reconciliation тоже не обращает SHA-256 обратно в файл. При исчезнувшем hosted blob требуется источник правильных bytes. Успех задачи «завершено» проверяйте отдельно known direct GET, поиском и чистым Go-клиентом: эти результаты показывают разные слои. Форматные metadata вроде Maven maven-metadata.xml имеют собственные правила; их не выдают за общий rebuild для Go.

Первичный контракт Data Repair Tasks сверён 1 ноября 2026. Перестроение и repair сервера в авторских опытах не исполнялись; это решение для согласованного maintenance, а не обычная nightly-оптимизация.

Повреждённый объект: не уничтожить свидетельство

Если metadata существует, но чтение выдаёт missing blob/checksum mismatch, ограничьте запись/cleanup затронутой области, сохраните logs и согласованную копию повреждённого состояния для расследования. Сравните known-good backup, hash от trusted publisher и доступность upstream. Для proxy иногда возможен контролируемый повторный fetch, для hosted единственной копии нужен backup или исходный approved artifact. Новый rebuild того же source не доказывает восстановление старых байтов.

Repair/reconcile tasks исправляют определённые несогласованности и способны удалять записи. Они не создают потерянные исходные байты из хеша. Tasks рекомендует repair по совету Sonatype; с 3.83–3.89.1 известны опасные версии некоторых задач, исправленные позже. Наша ветка новее, но это не отменяет backup, план и review. Локальное упражнение возвращает бинарник из файловой копии и подтверждает прежний hash; оно не заявляет исполненный restore H2. Полный VM restore остаётся отдельно отмеченным рецептом.

Версия — часть состояния

Зафиксируйте source/target версии, редакцию и entitlement, Java, ОС/архитектуру, backend DB, blob stores, plugins и используемые форматы. Сначала прочитайте target release notes, known issues, supported upgrade path и security advisories, затем скачивайте. Нельзя утверждать, что любая 3.x стартует над любыми историческими данными 3.x. Старый OrientDB требует особого migration path; наш новый H2 стенд не является проверкой миграции существующей старой организации.

CE 3.97.3 включает Go hosted/group и OCI; переход с версии, где recipe отсутствует, не переносится в прошлое простым копированием каталогов. Открытый Core и CE могут отличаться составом форматов; смена дистрибутива не нейтральна. H2 предназначена для небольшого standalone, не HA. PostgreSQL доступен по матрице современной CE, но HA и прочие возможности имеют отдельные условия редакции. «У нас есть PostgreSQL» не означает «нам разрешён и поддержан кластер Nexus».

Подготовьте репетицию до production

Восстановите согласованный backup в изоляции, запретите старые writers, воспроизведите target upgrade. Измерьте downtime, migration time, размер временного пространства, startup и клиентские smoke tests. Сохраните logs и фактическую версию схемы/приложения по поддержанной диагностике. Эта репетиция отвечает, помещается ли maintenance window в RTO, а не только «умеем ли мы распаковать tar». Тест API без реальной БД не проверяет migration.

В production заранее подготовьте target install-dir и его checksum, перенесите только осмысленные custom настройки, сравните новые defaults и JVM требования. Не заменяйте новый nexus-default.properties целиком старым файлом. Остановите сервис штатно, снимите финальный согласованный резерв со всеми областями, проверьте его, затем переключите symlink/конфигурацию на новую поставку и запустите. Существование нового Java-процесса ещё не подтверждает завершённую миграцию и читабельность старого release.

Почему symlink назад может быть недостаточно

При старте новая версия может изменить schema/metadata. Если после этого просто вернуть ссылку /opt/sonatype/nexus на старый код, он может не понимать новое состояние. Граница rollback определяется документированной совместимостью данных. Надёжный возврат после неуспешного upgrade при отсутствии поддержанного downgrade — остановить новую версию и восстановить весь согласованный предшествующий snapshot с соответствующим старым дистрибутивом. Публикации после snapshot теряются либо должны быть отдельно перенесены поддержанным способом; нельзя одновременно обещать возврат в прошлое и сохранение всех новых записей без плана.

Запишите критерии abort до окна: startup дольше допустимого времени, схема не завершилась, critical GET hash отличается, reader получил publish, пропали Go coordinates, telemetry unhealthy по непредвиденной причине. Время на диагностику ограничьте так, чтобы остался бюджет полного restore. «Ещё десять минут» повторённое шесть раз может уничтожить всё RTO при нетронутом backup.

Миграция H2 → PostgreSQL — отдельный проект

Внешняя БД уменьшает некоторые эксплуатационные ограничения и добавляет собственные: версию PostgreSQL, ownership database/schema, расширения, backup/PITR, network latency, TLS и secret rotation. По текущей инструкции PostgreSQL пользователь Nexus должен быть владельцем БД, требуется pg_trgm; параметры, encoding/locale и schema выбирают по документам совместимости. Не применяйте пример CREATE DATABASE со случайной locale на существующем production cluster. Для миграции используйте поддержанный migrator точной линии, а не ручной export произвольных таблиц.

Стоимость отдельного PostgreSQL — дополнительное наблюдение, обслуживание, storage и план отказа. При небольшом личном учебном workload это может быть неоправданным усложнением; при требованиях к поддерживаемой production-модели H2 может оказаться неподходящей изначально. Решение принимают по поддержке и RPO/RTO, не только по средней скорости запроса. Ни установка PostgreSQL, ни migrator в авторских проверках не выполнялись.

Новое требование может быть сетевым

В 3.97 базовая телеметрия стала обязательной с подтверждением; изменение версии может добавить operational dependency даже когда все artifacts закэшированы. Изолированная площадка должна пересмотреть выбранную редакцию и договор работы, не обходить requirement и не оставаться на случайной старой версии, объявив её бессрочно безопасной. Проверяйте status/check содержательно: HTTP 200 не гарантирует healthy Baseline Telemetry. Поддерживаемую offline/disconnected модель уточняют у поставщика до изменения production.

Данные обновления сверены 1 ноября 2026: notes 3.97, database options, feature matrix. Эта глава даёт процедуру принятия и проверки, а не выдаёт неисполненный upgrade за успешный опыт.

Два режима с честной границей

Режим L — локальный Go/HTTP/file опыт. Нужны Python 3 и подготовленный Go, сеть только loopback. local_client.py создаёт собственный TemporaryDirectory, удаляемый после опыта, не изменяет личный go env и не читает netrc. Внутри одного прогона состояние развивается последовательно: источник, публикация fixture, чистый клиент, тёплый клиент без upstream, ошибки HTTP, порча ZIP, доверенный build, manifest и restore файла. Этот disposable опыт нужен для доказательства клиентских механизмов, он не является основным сохраняющимся сервером.

Режим N — личная VM с CE 3.97.3, установленная первой книгой. Её data-dir и releases сохраняются между занятиями. Нужны достаточные ресурсы и согласованная исходящая связь телеметрии, доверенный TLS, пространство под резерв, рабочие reader/publisher/promoter. Ничего не устанавливайте на рабочий хост автоматически. Если полный сервер не помещается на домашнем компьютере, выполните L, изучите N как рецепт и разверните N на подходящем личном стенде позднее. Отсутствующий ресурс не маскируется «успешным» JSON.

python3 labs/tests/local_client.py --go /path/to/prepared/go \
  --report ./local-results.json

Путь после --go заменяется подготовленным исполняемым файлом, не переписывает системный PATH. --report создаёт только выбранный отчёт. В авторском прогоне использован Go 1.27.3 Linux/amd64. Сохранённый results.json содержит реальные проверки и HTTP paths; сетевые порты выбираются динамически и не должны совпадать между прогонами. Скорость loopback не служит sizing Nexus.

N0. Зафиксировать начальную точку

После установки запишите version/edition, Java, IP/DNS, install/data paths, blob store paths, effective service user, listening ports, доступный disk/RAM. Приёмка должна включать restart с сохранением логина/пустого repository и первую проверку HTTP. Создайте snap-001 согласно recovery chapter и убедитесь, что знаете, где лежат DB и blobs. Ещё нет ни внутреннего module release, ни approved бинарника. Этот snapshot не возвращается автоматически в конце упражнения.

N1. Создать форматы и роли

В UI создайте файловые lab-hosted и lab-cache с известными путями; Go hosted go-internal, proxy go-public → proxy.golang.org, group go-all с internal первым. Raw hosted raw-candidates/raw-releases получают lab-hosted и политику без повторной записи известных release paths. Не используйте Maven recipe ради похожего слова «version». Создайте reader, ci-publisher, release-verifier, release-promoter и роли из главы доступа. Сохраните конфигурацию и отдельно секреты в защищённом месте, а в журнале — только имена и ожидаемые права.

Сначала простая negative проверка: reader получает известный разрешённый файл после появления; publisher не управляет users; anonymous не видит закрытые candidates. Не выдавайте всем admin, чтобы ускорить подготовку: следующий отказ тогда окажется непроверяемым. Если GUI не показывает заявленный формат, проверьте edition, version и distribution, а не загружайте Go ZIP в raw и называйте это исправлением.

N2. Опубликовать библиотеку

Работайте из рабочего корня своей сохраняемой копии тома, где находится labs/. Запустите тест модуля ledger, сформируйте ZIP python3 labs/artifacts.py module --output ./lab-work/proxy, проверьте prefix и go.mod. PUT из главы публикации направьте в go-internal/v1.0.0.zip с publisher.netrc. Сохраните код ответа и direct URL, затем reader скачивает .info/.mod/.zip через go-all. Поиск asset может подтвердить сохранённую coordinate, но решающее доказательство клиента — успешный go mod download на новом GOMODCACHE с require v1.0.0 и без replace.

Состояние после N2: версия v1.0.0 существует на сервере и в журнале упражнения; source commit/ZIP checksum записаны; данные VM не сбрасываются. Если повторяете после успешной публикации, сначала прочитайте и сравните существующий объект. Для изменённого исходника выбирается новая версия, а не перезаписывается v1.0.0.

N3. Построить и сохранить candidate

В том же выделенном терминале из главы клиента проверьте NETRC, GOPROXY, GOMODCACHE и доверие TLS. В labs/service выполните tidy/test/verify и сборку главы raw. Если этот этап уже сделан, проверьте сохранённые файлы вместо их перезаписи. Для первой сборки перейдите в рабочий корень и выполните python3 labs/artifacts.py manifest --binary labs/service/dist/pulse-linux-amd64 --version 1.0.0 --toolchain "$(go version)" --input-version v1.0.0 --output labs/service/dist/manifest.json. Строка toolchain и выбранный ledger передаются helper явно; target linux/amd64 и source_module относятся к нашему конкретному build-рецепту и не обнаруживаются helper автоматически.

Из рабочего корня команда (cd labs/service/dist && sha256sum pulse-linux-amd64 > SHA256SUMS) создаёт сумму с правильным локальным basename. Затем python3 labs/artifacts.py verify --manifest labs/service/dist/manifest.json --directory labs/service/dist проверяет комплект. При ошибке не продолжайте upload. Три файла публикуются в raw-candidates/pulse/1.0.0/linux-amd64/. Reader доступа к candidates не имеет: verify скачивает их с отдельным verifier.netrc, promoter — с promoter.netrc. Проверка до запуска опирается на ранее принятое ожидаемое значение, а не на любой manifest с совпавшим именем.

N4. Чистый клиент и исчезнувший upstream

Для public proxy выберите небольшую разрешённую публичную coordinate, зафиксируйте её и сначала получите через Nexus в новый клиентский cache. Затем в выделенной копии стенда/контролируемом upstream отключите только upstream-доступ этого опыта, сохранив telemetry и служебные подключения. Повторите в другом новом client cache ту же coordinate; тёплый Nexus должен либо отдать достаточное содержимое по своей политике, либо показать документированную границу revalidation. Нельзя объявить успех по тёплому Go cache. Новая никогда не загружавшаяся версия при недоступном upstream должна отказать, а не магически появиться.

Состояние до и после включает TTL/negative cache и время. Если Nexus требует актуализацию истёкшего metadata, возможна зависимость от remote даже при наличии ZIP. Зафиксируйте запросы и поведение, не меняйте TTL на -1 задним числом и не объявляйте предыдущий эксперимент успешным. В режиме L показано только исчезновение HTTP-fixture и сохранение локального module cache, не серверный cache hit.

N5. Ошибочная роль и неверное отсутствие

Отдельной тестовой CI-личности выдайте только read raw-candidates, затем попытайтесь PUT нового одноразового пути. Ожидается отказ без появления asset. Добавьте минимальные необходимые publish grants и повторите тот же запрос; проверьте download и отсутствие delete. Верните исходно задуманную роль, записав изменение. Нельзя «исправить» ошибку выдачей admin и закончить на зелёном PUT. На локальных двух HTTP servers проверена именно матрица comma/pipe 401/403/404/410/500; Nexus role engine не моделировался.

N6. Promotion

Verify скачивает candidate в новый каталог, проверяет checksum/размер, запускает -version и HTTP smoke на loopback с ограниченным временем. Promoter переносит те же файлы в raw-releases и проверяет hash H1 с reader. Публикуется release record. Дальнейшая сборка pulse 1.0.1 не заменяет объект 1.0.0. Сравните снапшот и текущий inventory: новые component/assets и bytes объясняются конкретными действиями.

N7. Повреждение и restore

Порчу файла упражняйте сначала в L: изменяется байт копии бинарника без изменения размера, verifier отвергает её до исполнения, backup copy возвращает прежнюю сумму. Для настоящего Nexus используйте только отдельный изолированный restore snap-002 после публикации, остановленный перед fault injection; не повреждайте основной lab-hosted. Удаление/изменение произвольного blob требует заранее известной связи и плана и здесь не автоматизировано. Без понимания layout достаточно безопасного restore полного согласованного snapshot и клиентской проверки, а не рискованного rm наугад.

На копии убедитесь, что metadata+blob restore возвращает v1.0.0 и pulse 1.0.0 с прежними sums и ролями. Наличие списка в UI без successful GET не считается восстановлением. Измерьте начало/конец outage, копирование, startup и приёмку; сравните с RPO/RTO. Основной стенд остаётся сохранённым, snapshots и copy не удаляются автоматически.

N8. Эксплуатационная заявка

Симптом: «из CI v1.0.1 не видна, с ноутбука видна». Приложите effective GOPROXY/GOPRIVATE без credential, точную coordinate, свежий cache либо доказательство его состояния, HTTP-код и время, DNS/TLS инициатора, role и group membership. Проверьте private bypass, негативный cache, разный endpoint и новую client sum, затем выберите одно исправление и повторите исходный опыт. «Перезапустили всё» не объясняет причину и может скрыть её до следующего выпуска.

Повторная сверка GOAUTH для Go 1.27.3 подтверждает выбор NETRC, а раздел go mod verify — возможность получения go.mod для выбора версий. Python 3.12 selectors описывает ожидание готовности Unix pipe; Windows pipe этим способом не поддерживается. KillMode systemd относится к процессам конкретного unit. Это основания новых исходных рецептов, а не новые выполненные опыты Nexus, JVM или VM.

Чего источники не доказывают

Наличие API в общей reference не доказывает entitlement конкретной редакции, а feature matrix не проверяет ваши TLS/права/пути. Сборка Go с локальными fixtures не подтверждает Go hosted upload Nexus. Проверенный YAML/INI/nginx fragment не доказывает работу служб. Рецепты требуют VM приёмки и записи фактических ответов; локальная проверка не подменяет её.

Том XII · Источники и справочник

Словарь · Nexus RepositoryПонятия и их связь с наблюдаемыми механизмами · 1727 слов

Словарь в боковой панели также ищет определения во всех остальных томах.

Nexus Repository

Сервер хранения и доставки артефактов по протоколам форматов. Не исполняет автоматически CI job и не заменяет Git-историю исходников.

Community Edition · CE

Бинарная редакция Sonatype Nexus Repository с доступными форматами и операционными ограничениями. Для 3.97.3 учтены usage limits и обязательная base telemetry.

Nexus Repository Core

Открытое исходное дерево с собственным составом форматов. Сборка Core не равна полной бинарной Community Edition.

Nexus IQ / Lifecycle

Отдельный продукт оценки компонентов и политик. Интеграция с ним не означает наличие всех функций анализа у Repository CE.

Артефакт · artifact

Сохранённый результат или вход разработки: исходный пакет, бинарник, образ, manifest. Его идентичность определяется форматом и точными байтами.

Coordinate

Координата содержимого по правилам формата, например module path + version у Go. Не обязательно совпадает с физическим именем файла blob store.

Component

Логическая сущность формата, которая может включать несколько assets. Счётчик components не равен числу HTTP requests или файлов на диске.

Asset

Адресуемый ресурс репозитория, например конкретный ZIP или go.mod. Metadata связывает его с физическим blob.

Blob

Сохранённый двоичный объект с внутренней идентичностью. Ручное копирование файла в blobs не создаёт корректную публикацию.

Blob store

Backend хранения содержимого, например File. Доступность других backend зависит от версии/редакции; БД metadata резервируется отдельно и согласованно.

Blob reference

Связь metadata asset с идентичностью объекта в blob store. Потеря объекта оставляет логическую запись, которую нельзя успешно скачать.

Metadata

Сведения о координатах, связях и свойствах содержимого; также форматные списки версий. Это не сами исходные/двоичные байты всех artifacts.

Install-dir

Каталог версионного приложения и комплектной JVM. Его замена должна согласовываться с миграциями постоянных данных.

Data-dir

Каталог постоянного состояния Nexus: DB, настройки и типично blobs/журналы. Не удаляется при обычном завершении занятия.

H2

Встроенная БД небольшого standalone Nexus. Наш рецепт использует cold backup при штатной остановке; H2 не даёт HA Nexus.

PostgreSQL

Внешняя SQL БД с отдельным жизненным циклом, сетью, credentials и резервом. Наличие PostgreSQL само не даёт entitlement на HA.

Hosted repository

Репозиторий публикаций, для которых ваш экземпляр является источником. Обычная публикация направляется в конкретный hosted endpoint.

Proxy repository

Репозиторий, получающий и кэширующий форматное содержимое из remote upstream. Не то же самое, что входной reverse proxy.

Group repository

Общий endpoint перед участниками одного совместимого формата. Порядок members и разрешения group определяют видимость содержимого.

Recipe

Поддержанное сочетание формата и типа repository, например Go hosted. Generic raw не становится Go recipe от имени каталога.

Upstream

Внешний источник, к которому Nexus proxy обращается за содержимым. Его DNS, TLS, пароль и доступность относятся к исходящему пути сервера.

Reverse proxy

Входной HTTP посредник перед Nexus, например NGINX. Передаёт маршрут/заголовки и может завершать TLS, ограничивать body и timeout.

Endpoint

Адрес и интерфейс обращения. Открытый TCP порт, успешный HTTP probe и удачное чтение asset — разные уровни свидетельств.

Cache hit / miss

Наличие либо отсутствие достаточного сохранённого содержимого в выбранной границе кэша. Тёплый Go-клиент может вовсе не запросить Nexus.

Revalidation

Повторная проверка актуальности сохранённого содержимого у upstream. Возможна без повторной передачи полного тела, если протокол это поддерживает.

Negative cache

Кэш знания об отсутствии ресурса. Уже появившаяся upstream версия может оставаться невидимой до TTL либо контролируемой invalidation.

TTL

Time to live — срок жизни записи/знания. У Nexus соответствующие cache age поля задаются в минутах; это не retention резервной копии.

Invalidation

Признание кэшированного знания просроченным для последующей проверки. Не обязательно удаляет все физические bytes и не скачивает весь upstream сразу.

HTTP

Hypertext Transfer Protocol — прикладной протокол запросов/ответов с методами, адресами, заголовками и статусом. Успех транспорта не равен проверке бизнес-содержимого.

URI / URL

Идентификатор/адрес ресурса. Слои module escaping и percent encoding могут отличаться при одной логической координате.

TLS

Transport Layer Security — защищённый транспорт с проверкой сервера по имени и цепочке доверия. Проверка клиента к Nexus и Nexus к upstream независимы.

CA

Certification Authority — удостоверяющая сторона доверия сертификату. Публичный сертификат CA можно передать клиенту, закрытый ключ CA — нет.

Trust store

Набор доверенных удостоверяющих материалов конкретного процесса/среды. Доверие браузера не автоматически передаётся Go или JVM.

SAN

Subject Alternative Name — поле имён сертификата. Имя назначения URL должно соответствовать сертификату, а не только красивому CN.

CSR

Certificate Signing Request — запрос подписи сертификата с открытым ключом и полями. Не содержит и не заменяет закрытый ключ сервера.

Loopback

Локальная сеть процесса/пространства имён, например 127.0.0.1. В разных VM или контейнерах означает разных участников.

JVM

Java Virtual Machine — среда исполнения Java-приложения. Для Nexus 3.97.3 требуется Java 21; комплектная JVM проверяется отдельно от системной.

Bootstrap

Первоначальная подготовка процесса и постоянных данных. Живой launcher во время bootstrap ещё не гарантирует готовность API/репозиториев.

Heap

Управляемая куча JVM. Не включает всю резидентную память процесса, direct buffers и filesystem cache ОС.

GC

Garbage collection — сборка мусора управляемой памяти. Отличается от удаления blobs и не возвращает место артефактов на диске.

Module path

Логическое имя Go-модуля из go.mod. Не заменяется адресом Nexus при смене транспорта GOPROXY.

Nested module

Вложенный корень с собственным go.mod. Не является просто пакетом родителя; упаковка родительского модуля должна уважать эту границу.

Go module proxy protocol

Файловые представления версии .info/.mod/.zip, список @v/list и другие предусмотренные запросы. Raw бинарник не реализует этот протокол.

Escaping module path

Замена заглавной ASCII-буквы на ! плюс строчную для путей proxy. Сохраняет различие Acme и acme на регистронезависимых хранилищах.

GOPROXY

Источники получения Go-модулей и политика перехода между ними. Запятая и | по-разному обрабатывают HTTP errors.

GOPRIVATE

Шаблоны приватных префиксов module paths. По умолчанию влияют на GONOPROXY и GONOSUMDB, но не являются самим адресом Nexus.

GONOPROXY

Выбор модулей для direct получения в обход proxy. Значение none позволяет явно использовать Nexus и для GOPRIVATE namespace.

GONOSUMDB

Выбор модулей, исключённых из внешней checksum database. Не отменяет уже сохранённые ожидания go.sum.

GOSUMDB

Доверенная checksum database Go: имя/ключ и адрес. Отдельная граница проверки, не автоматически часть Go proxy Nexus.

GOAUTH

Механизм Go получения credentials для поддержанных запросов. В локальных тестах off, в HTTPS рецепте netrc/выбранный helper.

GOMODCACHE

Клиентский каталог загруженных модулей и их представлений. Изолируется для опытов без очистки личного cache.

GOCACHE

Каталог сохранённых результатов вычислений Go build. Отличается от module downloads и серверного cache Nexus.

GOTOOLCHAIN

Правило выбора/доставки toolchain Go. Local запрещает автоматический поиск другой toolchain в наших опытах.

go.sum

Сохранённые ожидаемые суммы известных module/version и go.mod. Не единственный lock графа и не подпись издателя исходников.

h1

Go-представление SHA-256 канонической сводки имён и содержимого файлов через Base64. Не равно SHA-256 точных ZIP bytes.

Checksum database

Криптографически проверяемый журнал ожидаемых сумм Go-модулей. Приватный исключённый путь требует иной исходной опоры доверия.

SHA-256

Криптографический хеш с 256-битным результатом. Проверяет совпадение bytes с доверенным ожиданием, но не создаёт доверие к произвольно заменяемой сумме.

Base64

Текстовое представление байтов. Не является шифрованием или подписью; у h1 представляет 32 bytes внешнего SHA-256.

SemVer

Semantic Versioning — соглашение major.minor.patch о совместимости. Для Go каноническая версия включает v; major v2+ требует согласованного module path.

Pseudo-version

Каноническая Go-версия, связывающая ревизию VCS и версионный порядок. Её не конструируют случайным timestamp вручную.

SNAPSHOT

Специфичная Maven изменяемая линия версии с форматными metadata. Не переносится автоматически в Go или OCI.

Content type / MIME

Объявленный тип HTTP-содержимого. Полезен для протокола/проверок, но не доказывает целостность и происхождение файла.

Deployment policy

Правило hosted-публикации, например запрет redeploy. Проверяется вместе с правами и форматной семантикой upload.

Immutable release

Версия, чьи байты после допуска не перезаписываются. Новое содержимое получает новую идентичность.

Manifest выпуска

Доверенная запись версии, файла, размера, хеша, платформы и inputs. Свободно заменяемый manifest не доказывает происхождение.

Provenance

Сведения о происхождении артефакта: входы, toolchain и процесс. Подлинность утверждения зависит от доверия к издателю/CI.

Promotion

Продвижение выбранных проверенных bytes к следующей среде без случайной пересборки. Подтверждается совпадением содержимого на конечном адресе.

SBOM

Software Bill of Materials — перечень составляющих. Описывает состав и не подменяет решение о допустимости выпуска.

OCI

Open Container Initiative — спецификации образов и распределения artifacts. Native OCI recipe не тождественен старому Docker recipe.

Registry

Сервер хранения/передачи image manifests и blobs. Не запускает контейнеры сам.

Image manifest

Документ OCI/Docker с ссылками на config/layers. Его digest относится к этому документу, а не прямо к raw-бинарнику приложения.

Image index

Документ ссылок на платформенные manifests. Digest index и digest Linux/amd64 manifest — разные идентичности.

Tag / digest

Tag — изменяемый указатель registry, digest — идентичность конкретного содержимого по хешу. Совпадение tag не доказывает совпадения bytes.

Realm

Источник/механизм аутентификации Nexus. Отдельно от роли; отключение всех realms способно лишить доступа администратора.

User / role / privilege

Личность, набор разрешений и отдельный grant действия/области. Разрешения ролей складываются; узкая роль не запрещает широкий grant другой.

Content selector / CSEL

Выражение отбора содержимого, связываемое с privilege. Поддержанные поля и upload-path semantics зависят от формата.

Anonymous access

Доступ без явных credentials от имени настроенной anonymous identity. Её роли должны быть намеренно узкими.

Service account

Машинная личность CI. В CE примера это local user с узкой ролью; нативные SAT 3.97 имеют отдельную доступность редакции.

Audit

История действий с инициатором/временем/объектом. Прикладной аудит, request log и metrics не имеют одинакового смысла и retention.

Cleanup policy / task

Правило отбора и исполняющее фоновое задание. Наличие конфигурации не доказывает успешный запуск и освобождённые bytes.

Soft delete

Пометка удаления для обычного доступа без немедленного физического освобождения всех bytes. Не заменяет независимый backup.

Compaction

Окончательное удаление помеченных blobs для возврата места. После этого восстановление требует подходящей резервной копии.

Rebuild / repair

Перестроение производных metadata либо исправление определённой несогласованности. Не создаёт потерянные исходные bytes и требует отдельного плана/резерва.

Latency / throughput

Задержка одной работы и количество завершённой работы за время. Требуют одинаковой границы и известной смеси запросов.

p95

Приблизительный 95-й процентиль наблюдений. Малое число запросов и смешанные классы делают хвост трудно интерпретируемым.

IOPS

Input/output operations per second — число операций ввода-вывода за секунду. Не равно объёму MiB/s и не описывает latency без размера/смеси.

RSS / OOM

Resident set size — резидентная память процесса; out of memory — нехватка соответствующего бюджета. Оба не описываются одним размером JVM heap.

RPO / RTO

Допустимая временная потеря данных и допустимое время возвращения услуги. Restore включает копирование, startup, доверие/права и клиентскую приёмку.

Cold backup

Копия при штатно остановленном приложении. Для H2 позволяет зафиксировать DB и соответствующие blobs без текущих writers.

Rollback boundary

Граница, после которой возврат старого кода недостаточен из-за изменений данных. Может потребоваться полное восстановление предшествующего snapshot.

Base telemetry

Обязательная в Nexus 3.97 передача базовых usage metrics. CE имеет ограниченный grace period и не поддерживает произвольный exemption switch.

NETRC

Переменная с путём к файлу учётных данных для Go GOAUTH=netrc. Внутри machine выбирает host; путь repository не является областью этого сопоставления.

GOENV / GOWORK

GOENV=off исключает постоянный пользовательский файл Go-настроек; GOWORK=off отключает обнаружение workspace. Экспорт в учебном терминале не переписывает пользовательские файлы.

INCOMPLETE snapshot

Метка неполной файловой копии cold_backup.sh. Она сохраняет частичный результат для расследования; ни она, ни COPIED не являются результатом проверки restore.
