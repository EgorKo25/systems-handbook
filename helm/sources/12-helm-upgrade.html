Upgrade: новые значения и частичное состояние

История, применение объектов и наследование параметров объясняются на конкретных входах.

Upgrade не стирает прошлое

Upgrade загружает нынешний релиз и новый чарт, выбирает итоговые параметры, рендерит целевой манифест, применяет ресурсы и создаёт новую ревизию. Статус pending-upgrade защищает от обычного параллельного запуска над тем же релизом; это не распределённая транзакция всех объектов. Сбой CLI после отдельных запросов может оставить изменённый ConfigMap, новый ReplicaSet, прежние Pod и метаданные failed/pending. Старые ревизии сохраняются согласно history-max и служат журналом желаемых манифестов, а не снимком всех текущих состояний.

После неудачи различайте последнюю запись и последнюю развёрнутую запись. В реализации 4.3.1 сначала читается наибольший номер истории. Если его статус pending, обычный upgrade отказывает как при незавершённой операции. Если последняя запись failed, но в истории есть deployed, текущей основой для прежнего Manifest и повторного использования параметров становится deployed. При этом номер новой попытки всё равно равен последнему номеру плюс один. Когда deployed нет, предусмотрен отдельный путь для последних failed или superseded. Это не совет удалять pending Secret: сначала определите, продолжает ли прежний клиент или hook работу.

ЗаписьНаблюдаемое состояниеСледующий обычный upgrade
Ревизия 1: deployed, MESSAGE=oldСохранённая успешная конфигурацияОснова current при последующей failed 2

Неявное поведение параметров зависит от нового ввода

Обозначим D1 — исходные значения старого чарта, D2 — нового; U1 — сохранённый набор пользовательских параметров; N — новые -f/--set. В реализации 4.3.1 без специальных флагов при пустом N копируется U1, затем объединяется с D2. При непустом N старый U1 сам по себе не копируется. Поэтому добавление одного --set способно потерять прежнее пользовательское переопределение другого ключа. Утверждение «upgrade всегда сохраняет параметры» неверно.

РежимОснова и приоритетПроверяемый эффект
Без флагов, N пустD2 + U1Новые defaults и прежние пользовательские параметры
Без флагов, N непустD2 + NU1 может исчезнуть
--reset-valuesD2 + NИгнорирует U1
--reuse-valuesСтарое объединённое дерево D1+U1, затем NНовые defaults могут не войти
--reset-then-reuse-valuesD2 + U1 + NНовые defaults, прежние и новые переопределения

Это упрощённая запись для отображений совместимых типов; null и схема добавляют ограничения. Reset-values имеет приоритет над reuse-values, оба заставляют reset-then-reuse игнорироваться. Не комбинируйте конфликтующие флаги ради угадывания результата. Поведение подтверждено чтением pkg/action/upgrade.go 4.3.1; настоящие обновления кластера в этой редакции не выполнялись.

Сравнимый опыт

Пусть прошлый пользовательский набор задавал replicaCount=3 и message=old. Новый чарт по умолчанию даёт message=new-default, N содержит только replicaCount=2. С reset-values получится message=new-default; с reuse-values — old; с reset-then-reuse тоже old, но для совершенно нового ключа D2 последний режим сохранит новое исходное значение без наследования старого объединённого дерева. Схема в главе о параметрах показывает сам процесс объединения шагами; в этой главе схема прослеживает частичный отказ применения.

helm upgrade ledger ./chart --reset-values -f environment.yaml \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab --wait=watcher --timeout 180s
helm upgrade ledger ./chart --reuse-values --set replicaCount=2 \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab --dry-run=server --hide-secret

Это сравнение намерений, не инструкция последовательно исполнять две разные политики выпуска. В основной линии предпочтительны полный версионируемый environment.yaml и явный reset-values: результат восстанавливается из входов без поиска случайной истории CLI. Перед изменением сохраните пользовательские параметры через get values без --all и отдельно вычисленные с --all, манифест и историю в защищённую папку.

Для сохранённого U1 в формулах важна именно выбранная current release, а не произвольный последний вывод терминала. Сравните helm get values ledger --revision 1 и helm get values ledger --revision 2 с явными kubeconfig, context и namespace из установочной главы. Эти два чтения не меняют приложение. Если failed 2 содержит нужное новое сообщение, перенесите его осознанно в environment.yaml; не рассчитывайте, что следующий вызов без этого файла унаследует неудачную попытку.

Серверное применение и владение полями

SSA, Server-Side Apply, — серверное применение: клиент передаёт желаемые поля и имя управляющего полями, а API ведёт managedFields. Конкурирующие владельцы могут вызвать конфликт. Helm 4 при установке по умолчанию использует server-side=true; при обновлении и откате server-side=auto наследует метод прошлого релиза, включая клиентское применение Helm 3. Поэтому новый CLI не переводит автоматически каждый исторический релиз на SSA. --server-side=true/false задаёт выбор явно; смена требует проверки принадлежности полей и пробного запуска.

Конфликт SSA отличается от ошибки принадлежности объекта релизу Helm по меткам и аннотациям. --force-conflicts отнимает конфликтующие поля у другого управляющего; --force-replace заменяет ресурсы и способен изменить идентичность или вызвать недоступность. --take-ownership обходит проверку принадлежности существующих объектов и даёт Helm возможность позднее удалить их. Ни один из этих флагов не является универсальной починкой обновления. Выясните владельца, неизменяемые поля и судьбу данных до действия.

Ошибка и автоматический откат

helm upgrade ledger ./chart --reset-values -f environment.yaml \
  --rollback-on-failure --timeout 180s --history-max 20 \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab

В 4.3.1 rollback-on-failure включает watcher, если оставлен hookOnly, и при неудаче пытается вернуться к предыдущему успешному релизу. Это компенсирующее действие с собственными ошибками API и обработчиков, а не атомарная отмена. До возврата часть ресурсов и внешние побочные эффекты уже могли измениться. Cleanup-on-fail разрешает удаление новых ресурсов неудачного обновления; он не возвращает запись в БД и не уничтожает все внешние эффекты обработчика.

Сломанный readinessPath=/missing-readyz создаёт новый Pod с живым процессом, но проба готовности получает 404. При maxUnavailable=0 старый готовый Pod может сохранить обслуживание, а обновление дойдёт до предельного времени. После исправления пробы следующий upgrade восстанавливает обновление экземпляров без удаления релиза или сброса. Измеряйте принятие API-запросов, готовые реплики и долю ошибок HTTP отдельно: failed в истории не означает, что все прежние пользователи уже потеряли доступ.
