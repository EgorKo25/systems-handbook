Что делает Helm

CLI (Command Line Interface) — интерфейс командной строки. API (Application Programming Interface) — программный интерфейс запросов Kubernetes. Namespace — пространство имён, отделяющее имена и область ряда прав объектов. Манифест — документ желаемого объекта API. Pod — совместно планируемая единица контейнеров, Deployment — контроллер обновления набора Pod. Эти понятия подробно разобраны в соседнем томе Kubernetes.

Helm — клиентский инструмент доставки Kubernetes-объектов из пакета chart, далее «чарт», и управления историей именованного release, далее «релиза». Чарт содержит описание версии, параметры и шаблоны текста. Релиз — конкретное применение чарта с именем, namespace и последовательностью ревизий. Один архив можно установить дважды под разными именами; ресурсы должны получать разные имена и не конфликтовать за внешнее состояние.

Разработчик изменяет сообщение Go-сервиса. Values превращаются в структуру данных, шаблон создаёт ConfigMap, Helm отправляет объект API, контроллер Deployment создаёт новые Pod, Go читает окружение и HTTP-клиент получает новое сообщение. Успех каждого перехода требует отдельного доказательства. Корректный YAML не обещает разрешения API. Принятый объект не обещает готового Pod. Ready Pod не доказывает бизнес-операцию. История Helm хранит описание действия, а не резервную копию данных приложения.

Источники, проверенные факты и дальнейшие границы

Сначала устанавливаем клиент и проводим границу локальной работы. Книга о данных последовательно разбирает values, типы, контекст Go templates, функции, области видимости и сериализацию YAML. Затем изучаем зависимости, пакеты и доверие. Книга о релизе прослеживает install, upgrade, hooks, rollback и uninstall через наблюдаемые состояния. Практикум связывает главы одним приложением; справочник команд открывается из выделенных команд в тексте, словарь объясняет термины отдельно от механики.

Том Kubernetes нужен до первого кластерного упражнения: Helm пользуется API и контроллерами, но не создаёт планировщик, контейнерный runtime, сеть CNI или StorageClass. Читатель Go узнает синтаксис text/template, однако шаблон Helm не является произвольной Go-программой: нельзя импортировать пакет и вызвать os.ReadFile.

Постоянный стенд

Приложение ledger-api слушает 8080: /livez проверяет живой обработчик, /readyz — готовность, /api/hello возвращает JSON с полями service и message. Копия исходников в labs/service совпадает с Kubernetes-томом: один image tag ledger-api:0.1.0 не должен означать две разные программы. MESSAGE — значение сообщения. API_TOKEN в chart демонстрирует доставку Secret; приложение его не использует для аутентификации.

Chart ledger-api, release ledger, namespace helm-lab сохраняются весь практикум. Namespace Kubernetes-упражнений — отдельный lab. Итоговое имя Deployment и Service — ledger-ledger-api. Контракт личного кластера: kubeadm Kubernetes 1.36.6, context handbook-admin; компактный профиль kind 0.33.0 с Kubernetes 1.36.4, context kind-handbook. Это разные patch одной minor-ветки API. Наш chart сознательно ограничен >=1.36.0 <1.38.0; ограничение не означает, что сам Helm работает только с этими версиями.

Границы выполненного

Редакция реально проверена официальным Helm 4.3.1 локально: lint, template, parsed YAML assertions, schema negative tests, merge, файлы, типы, dependency lock/build, package и Go-контракт. Настоящий кластер не запускался. Install/upgrade/test/rollback ниже — рецепты для подготовленного личного стенда с критериями приёмки. Схемы — фиксированные объяснительные модели, которые не посылают запросов. Примеры будущего вывода прямо обозначаются ожидаемыми, не выдаются за журнал запуска.

Локальные тесты создают временные копии для намеренных ошибок; основной chart не сбрасывается. Читатель хранит свою рабочую копию, values и журнал ревизий. Возврат к снимку и uninstall — отдельные действия с описанными последствиями. Готовые файлы открываются через ссылки практикума и протокола проверок.

Версию выбирают явно

На дату проверки текущая основная ветка — Helm 4, стабильный выпуск 4.3.1 от 15 октября 2026. Параллельная Helm 3.22.1 находится в режиме исправлений безопасности до 11 ноября 2026; обычные bug fixes закончились 8 июля. Helm 2 с Tiller не является моделью этой книги. Фиксация версии делает опыт воспроизводимым, но не отменяет последующее обновление исправлений.

Основная линия использует CLI 4.3.1 и стабильный chart API v2. Экспериментальный chart API v3 не включаем. В четвёртой ветке новый install по умолчанию применяет server-side apply, ожидание принимает стратегию, а --rollback-on-failure заменяет имя --atomic. Старые флаги могут распознаваться с deprecation warning; новая автоматизация использует актуальные имена. Отдельная глава объясняет миграцию существующего релиза Helm 3.

Скачивание и проверка binary

На официальной странице release выбирают ОС и архитектуру; Linux amd64 и arm64 содержат разные машинные инструкции. CLI не устанавливает кластер или службу. Следующие команды предназначены для личной VM или отдельного каталога пользователя; root и глобальная смена PATH не нужны.

prepare_helm_client() (
    os="$(uname -s)" || exit 1
    arch="$(uname -m)" || exit 1
    test "$os" = Linux || exit 1
    test "$arch" = x86_64 || exit 1
    mkdir -p "$HOME/handbook-tools" || exit 1
    mkdir "$HOME/handbook-tools/helm-4.3.1" || exit 1
    cd "$HOME/handbook-tools/helm-4.3.1" || exit 1
    curl --fail --location --proto '=https' --tlsv1.2 \
      https://get.helm.sh/helm-v4.3.1-linux-amd64.tar.gz \
      --output helm-v4.3.1-linux-amd64.tar.gz || exit 1
    printf '%s  %s\n' \
      0403a88ae20913d11b10a2467b50087721fea7581736da6b9d3992f5357fe54b \
      helm-v4.3.1-linux-amd64.tar.gz > expected.sha256 || exit 1
    sha256sum --check expected.sha256 || exit 1
    tar -tzf helm-v4.3.1-linux-amd64.tar.gz || exit 1
    tar -xzf helm-v4.3.1-linux-amd64.tar.gz || exit 1
)
prepare_helm_client &&
export HELM_BIN="$HOME/handbook-tools/helm-4.3.1/linux-amd64/helm" &&
"$HELM_BIN" version --short

Это только профиль Linux x86_64 и первая установка в новый каталог. Для другой ОС или архитектуры выбирают соответствующую официальную поставку и её сумму. Существующий каталог вызывает отказ: при следующем занятии используйте уже проверенный бинарник, не перезаписывайте его этой процедурой. Каждый отказ останавливает подготовку до следующего действия; повреждённая частичная папка остаётся для осмотра. Функция выполняется в дочерней оболочке, поэтому текущий каталог пользователя не меняется. HELM_BIN задаётся только после успеха подготовки.

curl --fail возвращает ненулевой код на HTTP-ошибке, --location следует redirect, --output выбирает файл. Это скачивание, не запуск shell с сайта. Ожидаемая SHA-256 выше сверена с official release для конкретного Linux amd64 архива. Реальный опыт дал OK и v4.3.1+gc0d08d0. SHA-256 — хеш содержимого, не доказательство личности издателя сам по себе. Архив и заменяемая рядом сумма могли бы быть подменены вместе; доверенное получение ожидаемой суммы остаётся условием проверки.

Release публикует GPG signatures. Команда gpg --verify АРХИВ.asc АРХИВ проверяет подпись после установления доверенного fingerprint ключа выпускающего. Импорт произвольного ключа с того же зеркала доверия не добавляет. В этой редакции действительно сопоставлены SHA и official release; GPG-проверка binary не выполнялась. Подпись chart — другой объект и отдельный процесс.

Дальше короткое имя helm предполагает выбранный проверенный executable. В своей текущей оболочке можно определить helm() { "$HELM_BIN" "$@"; }; функция не меняет системную установку. Архив распаковывайте в пустой частный каталог после просмотра tar -t.

Каталоги и процессы

helm env
helm version
helm plugin list

helm env показывает фактические пути. HELM_CONFIG_HOME хранит, например, repositories.yaml и registry credentials; HELM_CACHE_HOME — скачанные индексы и кэш; HELM_DATA_HOME — пользовательские данные/плагины. Пути зависят от ОС и XDG. Наличие кэша не доказывает готовность офлайн. Клиент живёт во время команды, сам не держит постоянно слушающий порт и по HTTPS обращается к API. Port-forward позже создаёт отдельный процесс kubectl с локальным портом.

Kubeconfig и context

Kubeconfig связывает clusters, users и contexts. Context выбирает endpoint, личность и namespace по умолчанию. Exec credential plugin из файла способен запускать программу, поэтому kubeconfig должен быть доверенным. Здесь используется отдельный учебный файл, который не меняет current-context пользователя. Отсутствие доступа диагностируют как endpoint/TLS/authn/authz, а не лечат отключением проверки сертификата.

export LAB_KUBECONFIG="$HOME/handbook-lab/kubeconfig"
export LAB_CONTEXT=handbook-admin
export LAB_NAMESPACE=helm-lab
kubectl --kubeconfig "$LAB_KUBECONFIG" config get-contexts
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" version
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" \
  auth can-i create deployments.apps --namespace "$LAB_NAMESPACE"

Для kind выбирают kind-handbook. Флаги Helm: --kubeconfig, --kube-context, --namespace; kubectl использует --context. Namespace создаёт владелец кластера заранее. Роль должна разрешать chart resources, чтение для wait, создание тестовых Pod и чтение/запись release Secrets. Create namespaces — отдельное cluster-scoped право, требуемое --create-namespace. Не выдавайте cluster-admin ради forbidden: установите конкретные resource/verb/namespace и личность запроса.

Значения выше — входы, которые нужно сверить со своим стендом: файл kubeconfig должен уже существовать, context должен присутствовать именно в нём, а namespace helm-lab должен быть создан владельцем кластера. Проверка ниже ничего не создаёт и не переключает общий current-context. Если какой-либо запрос отказал, установку не продолжают: NotFound пространства имён, TLS-ошибка и Forbidden требуют разных исправлений.

test -f "$LAB_KUBECONFIG" || exit 1
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" get namespace "$LAB_NAMESPACE" &&
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" --namespace "$LAB_NAMESPACE" auth can-i create secrets

Последняя команда проверяет только create Secrets. Она не заменяет проверку чтения, обновления и списка release Secrets, операций над ресурсами чарта, чтения/watch для ожидания и прав тестового Pod. Если namespace ещё нет, владелец своего кластера создаёт его отдельно командой kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" create namespace helm-lab, затем повторяет проверку. Релизный пользователь не получает cluster-admin от того, что умеет читать это пространство имён.

Совместимость и offline

Helm 4.3.1 собран с Kubernetes client libraries 0.37.1; политика поддержки Kubernetes проверяется отдельно от API chart. Выбранная 1.36 находится в поддерживаемом диапазоне этого клиента. Объект с удалённым apiVersion не станет допустимым от одного нового Helm. Для офлайна нужны binary+сумма+доверенные signature keys, полный chart с dependency archives, values, все workload/hook images для нужной архитектуры и способ загрузки в registry/nodes. Локальный render без сети подтверждает лишь часть этого перечня.

Четыре разных доказательства

Render — получение текста из templates и значений. До сохранения объекта Kubernetes API отдельно устанавливает личность клиента, проверяет его право выполнить действие, структуру объекта и политики. Admission controllers — участники этой обработки, способные изменить допустимые части объекта или отклонить запрос; они не заменяют аутентификацию и RBAC. Readiness — состояние рабочей нагрузки, из которого Kubernetes решает, готов ли экземпляр обслуживать трафик. Прикладной успех — правильный результат требуемой операции сервиса. У этих проверок разные входы и участники. YAML-parser может принять строку nonsense в поле CPU, но API отвергнет неправильную quantity. Принятый Deployment может создать Pod, который не запланируется из-за requests или не скачает image.

Подготовка и внешние входы

CLI разбирает имя, ссылку chart и флаги; выбирает environment и Kubernetes client. Загрузчик получает каталог/архив/HTTP/OCI package, читает metadata, defaults и dependencies. Файлы -f и семейства --set образуют user config; Helm coalescing объединяет его с defaults и subcharts. Schema проверяет полученные values. Capabilities предоставляет версию Kubernetes и доступные API: локально это модель, на сервере — discovery. Go templates выдают байты, Helm выделяет обычные manifests, hooks и NOTES.

Post-renderer — постобработчик, меняющий готовые manifests перед отправкой. В Helm 4 это именованный plugin; рецепт Helm 3 с произвольным executable-path не является командой основной ветки. Plugin — новый вход и граница доверия, он способен читать Secret и добавлять ресурсы. Проверяйте именно результат после него. В основном chart plugins не нужны.

При настоящем install CRD из crds/ может устанавливаться до discovery и обычных шаблонов. CRD, CustomResourceDefinition, определяет собственный API. Поэтому весь install не всегда является сначала чистым render, потом первым изменением API. Наш chart без CRD; этот факт делает локальные опыты проще. Pre-install hooks тоже не превращают операцию в транзакцию.

История и частичная операция

Helm строит API objects, добавляет metadata принадлежности, проверяет конфликты, сохраняет pending-install, запускает pre-install hooks, применяет обычные resources, ждёт согласно strategy, выполняет post-install hooks и сохраняет deployed либо failed. Revision — номер действия в истории release. Эти переходы идут разными API-запросами: отказ между ними оставляет частичное состояние. Общей транзакции для manifests, release record и базы приложения нет.

Default storage driver — Kubernetes Secrets namespace релиза. Типичная запись sh.helm.release.v1.ledger.v1 типа helm.sh/release.v1 содержит chart, user config, rendered manifest, hooks и status. Реализация кодирует JSON release → gzip → base64; API Secret дополнительно представляет data как base64. Это кодирование, не шифрование. Читатель release Secrets может увидеть значения и секреты старых ревизий. Другие drivers, например SQL, требуют отдельной модели доступа и резерва.

В записи релиза находятся разные виды состояния. Name и Namespace выбирают релиз; Version — номер ревизии. Chart сохраняет пакет, Config — пользовательские параметры, а Manifest — уже полученный текст обычных ресурсов. Hooks содержит выделенные обработчики и сведения об их выполнении. Info.Status и описание сообщают, на какой стадии закончилось действие; ApplyMethod фиксирует способ применения. Пользовательские Config и объединённые Values различаются: defaults могут происходить из сохранённого чарта. Manifest не хранит содержимое файлов PVC, текущее состояние процесса или весь живой объект API.

Для Secrets-драйвера у объекта sh.helm.release.v1.ledger.v2 есть метки owner=helm, name=ledger, version=2 и status=pending-upgrade; поле data.release содержит закодированное представление записи. Namespace объекта остаётся helm-lab. Пока команда ещё выполняется, эта запись уже может существовать. Поэтому наблюдаемый pending означает сохранённую стадию операции, а не подтверждение, что все нужные объекты созданы или что старые Pod остановлены.

Номер новой ревизии, сохранение её записи и применение ресурсов — отдельные действия. До создания записи могут отказать загрузка, schema, render, проверка имён и доступа. После её создания могут отказать hook, один из API-запросов или ожидание. Если финальное обновление записи не удалось либо процесс оборвался, данные истории могут отставать от уже изменённых объектов. При расследовании сравнивают release record, живые ресурсы и результат HTTP, сохраняя эту разницу.

Dry-run: где заканчивается проверка

helm install ledger ./chart --namespace helm-lab \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --dry-run=client
helm install ledger ./chart --namespace helm-lab \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --dry-run=client --debug --hide-secret

Оба запуска подготавливают release без установки. Во втором больше диагностики и скрыты Secret-документы dry-run. Пароль всё равно может находиться в NOTES, ConfigMap, annotation, ошибке или выводе plugin; --hide-secret не очищает произвольную чувствительную строку. Даже без --debug dry-run способен вывести Secret. Храните output в защищённом каталоге и не публикуйте raw CI log.

В 4.3.1 --dry-run=server требует API, discovery, разрешает lookup и проверку существующих ресурсов. Но install.go возвращает release из ветки isDryRun до performInstall и KubeClient.Create обычных объектов. Общая строка help о server simulation поэтому не доказывает принятие каждого будущего объекта admission webhook. Для этой границы выполните kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" --namespace helm-lab apply --server-side --dry-run=server -f rendered.yaml в своём context. Даже этот результат относится к текущему состоянию; CRD, hooks и конкурентные изменения добавляют различия между проверкой и применением.

Wait и timeout

helm install ledger ./chart --namespace helm-lab \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --wait=watcher --timeout 180s
helm install ledger ./chart --namespace helm-lab \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --wait=hookOnly --timeout 180s

Это две альтернативы первого install, не последовательность повторной установки в одно имя. Watcher ожидает resource readiness; hookOnly ограничивает ожидание hooks, и команда может закончиться до готовности Deployment. Один --wait без значения выбирает watcher, отсутствие флага — hookOnly. Legacy сохраняет прежний механизм ожидания. --wait-for-jobs добавляет завершение обычных Jobs к wait; hook Job и так блокирует свою фазу. --timeout задаёт бюджет отдельной Kubernetes-операции/ожидания, включая hooks, а не универсальный deadline всей команды и бизнес-запроса.

Время CLI включает package/network, discovery, render, API и wait. Сравните прогретый локальный template с server dry-run, затем настоящий upgrade с events. Если template занимает 30 мс, а wait длится 120 с из-за ImagePullBackOff, увеличение CPU клиента не исправит registry. Если гигантский chart долго сериализуется, сначала измерьте локальные CPU/RSS, число objects и bytes, затем обсуждайте API QPS.

Chart.yaml задаёт name, SemVer version, строковое appVersion, type, kubeVersion и dependencies. SemVer — Semantic Versioning, соглашение major.minor.patch с дополнительными частями. Chart version относится к интерфейсу и содержимому пакета; appVersion — информативная строка приложения и сама не меняет image Deployment. Image tag — отдельный указатель registry, digest — идентификатор содержимого манифеста. Одинаковые цифры 0.1.0 не делают эти три сущности одним объектом.

Values задают defaults, но сами не запрещают произвольный ввод. Schema — JSON Schema, контракт типов и ограничений. Templates проходят через engine; файл с начальным подчёркиванием содержит helpers и не печатается как отдельный ресурс. NOTES.txt выводит пояснение, не исполняется как shell. Files — включённые обычные bytes, доступные .Files.Get. CRD размещается отдельно и имеет особый lifecycle.

Что исключает helmignore

.helmignore похож на gitignore, но не равен ему; нельзя переносить все правила отрицания и ** без проверки. Исключение из Git не гарантирует исключения из chart package. Не кладите kubeconfig, credentials и rendered Secrets внутрь chart. Проверяйте tar -tzf и конкретные members. Результат package складывайте вне исходного каталога.

Реальный отрицательный опыт редакции: широкое правило *.tgz исключило dependency archive из charts/, после чего template сообщил missing dependency. Исправлено хранением готовых packages снаружи и удалением широкого правила. Dependency build создал файл, но loader имел право исключить его; это разные доказательства. Лабораторный test отдельно проверяет точные bytes operator-note.txt и отсутствие заведомо исключённого test-secret.private во временной копии.

Schema — входная граница, а не scheduler

{"type":"object", "properties": {
  "replicaCount":{"type":"integer","minimum":1,"maximum":6},
  "config":{"type":"object","required":["message"],
    "properties":{"message":{"type":"string","minLength":1}}}
}}

Это сокращённый пример; полный файл в labs/chart. Schema проверяет объединённые values; overlay — файл частичных переопределений поверх предыдущих параметров — может не содержать key, предоставленный defaults. Required JSON Schema проверяет присутствие key; template-функция required проверяет непустоту, это разные правила. Schema не узнает свободную память nodes, существование Secret или подлинность registry digest.

Внутри image/config/service и других interfaces additionalProperties=false ловит опечатки. Корень оставлен расширяемым для отдельного dependency-упражнения: при строгом корне нужно перечислить global и subchart keys. CPU/memory оставлены строковыми quantity; API проверит их грамматику и соотношение requests/limits. Самодельная regex редко воспроизводит все правила Kubernetes.

helm lint ./chart --strict --kube-version 1.36.6
helm lint ./chart --strict --kube-version 1.36.6 -f fixtures/wrong-replicas.yaml

Первый запуск проходит, второй отвергает строку "3" вместо integer. --strict превращает lint warnings в ошибки, но не запускает Pod. --skip-schema-validation отключил бы защиту, не исправив ввод. Такие флаги допустимы как точный диагностический опыт или управляемая миграция, а не обход неизвестной ошибки CI.

Capabilities и версии API

.Capabilities.KubeVersion сообщает версию, .Capabilities.APIVersions.Has — наличие API. Локальный --kube-version меняет модель версии, --api-versions добавляет моделируемую capability; CRD или controller они не устанавливают. Для Gateway API номер Kubernetes сам по себе не доказывает наличие CRD. Наш chart использует стабильные apps/v1 и v1. При удалении key, изменении типа, selector или dependency повышают chart version и документируют миграцию. Уже опубликованную 0.1.0 нельзя перезаписать другими bytes: кэши, provenance и журнал выпуска рассчитывают на неизменность.

Первичные источники и версия

Вход проходит несколько языков

В helm template ledger ./chart --set config.message=hello оболочка сначала формирует argv — массив строк, переданный процессу. Анализатор strvals разбирает точки как вложенность и значение по правилам Helm. Движок получает отображение ключей в значения, а не кусок исходного YAML. Вспомогательный шаблон печатает MESSAGE через quote; Kubernetes хранит строку в ConfigMap, envFrom передаёт её процессу, Go читает os.Getenv. На каждом переходе важно знать: перед нами байты, строка или структурированное значение.

YAML — текстовый формат отображений, последовательностей и скаляров, то есть простых значений. JSON — другой текстовый формат объектов, массивов, строк, чисел, логических значений и null. Кавычки YAML фиксируют строку, но после разбора информация о стиле кавычек обычно исчезает. В Go параметры представлены отображениями (map), срезами (slice) и простыми типами. Конкретный числовой тип зависит от пути загрузки и версии анализатора. Для интерфейса надёжнее требование integer в схеме, чем предположение, что каждое число обязательно будет int64.

 | Вход values | Тип/смысл | Следующий шаг

 | replicaCount: 3 | Числовой скаляр, схема integer | Вывести без quote в spec.replicas

 | replicaCount: "3" | Строка | Наша схема отвергает

 | flag: false | Логическое значение, значимое выключение | Функция default с запасным true затрёт выбор

 | image.tag: "0012" | Строковый идентификатор | Сохранить ведущие нули

 | extraEnv: [] | Пустой список | Заменяет прежний список

 | config: null | Удаление исходного ключа при объединении | Обязательный интерфейс нарушен

Отображения объединяются, списки заменяются

Исходные requests содержат cpu:50m и memory:32Mi. Набор переопределений, задающий только requests.cpu:100m, сохраняет память. Следующий набор меняет только явно присутствующие ключи. Новый extraEnv заменяет список целиком, а не объединяется по имени элемента. Объединение параметров не является стратегическим слиянием объектов Kubernetes. Если нужны независимые добавления по имени, проектируйте отображение и стабильный порядок его ключей при выводе; если важна последовательность, оставляйте список с осознанной заменой.

helm template ledger ./chart --kube-version 1.36.6 \
  -f fixtures/prod.yaml -f fixtures/last.yaml
helm template ledger ./chart --kube-version 1.36.6 \
  -f fixtures/last.yaml -f fixtures/prod.yaml

Реально проверено: первый Deployment получает одну реплику и сообщение «Last file wins», второй — три и «Production-like lab». Оба сохраняют requests.memory:32Mi и requests.cpu:100m, потому что last.yaml не задаёт CPU. Правило «правый побеждает» относится к конфликтующему ключу и не уничтожает прежнее дерево полностью. Смена отображения на скаляр вызывает предупреждение объединения или отказ схемы; это не точечное удаление вложенного значения.

Три поля от файла до строки манифеста

Запускаем команду из helm/labs, где уже есть chart/ и fixtures/. Реплики задаёт целое replicaCount, сообщение — строка config.message, порт контейнера — целое service.targetPort. Покажем только эти три поля; остальные параметры чарта продолжают участвовать в проверке и выводе.

helm template ledger ./chart \
  --namespace helm-lab --kube-version 1.36.6 \
  -f fixtures/prod.yaml -f fixtures/last.yaml
Модель по поставляемым файлам и реализации Helm 4.3.1. template печатает результат локально, ledger задаёт имя релиза, ./chart — каталог пакета, -f — очередной файл параметров. --kube-version задаёт версию Kubernetes для возможностей шаблонов, но не подключает настоящий API-сервер. Рендер Helm этим рисунком не исполнялся; ниже вычислено ожидаемое объединение обычных отображений и скаляров выбранных файлов.

В первых трёх строках таблицы показано содержимое каждого источника отдельно. «—» означает отсутствие ключа в данном файле: это не строковое значение и не null. Последняя строка показывает результат слияния.

 | Источник | Реплики | Сообщение | Порт

 | chart/values.yaml | Реплики2 | Сообщение"Hello from Helm" | Порт8080

 | fixtures/prod.yaml · первый -f | Реплики3 | Сообщение"Production-like lab" | Порт—

 | fixtures/last.yaml · второй -f | Реплики1 | Сообщение"Last file wins" | Порт—

 | Итог: дерево .Values | Реплики1 | Сообщение"Last file wins" | Порт8080

Скаляр, явно заданный поздним файлом, заменил прежнее значение. Отсутствующий targetPort его не удалил: вложенное отображение service сохранило исходный порт. После объединения схема требует для реплик целое число, для сообщения строку, для порта именно 8080. Успешная проверка этого дерева ещё не проверяет будущие объекты API.

① .Values.replicaCount → Deployment

{{ .Values.replicaCount }} в deployment.yaml выводит replicas: 1. Значение остаётся числом; кавычки превратили бы его в строку YAML.

② .Values.config.message → ConfigMap

Именованный фрагмент ledger.configData находится в _helpers.tpl. Он выводит MESSAGE: {{ .Values.config.message | quote }}; configmap.yaml вставляет этот фрагмент в data с отступом 2. Функция quote добавляет кавычки: MESSAGE: "Last file wins".

③ .Values.service.targetPort → поле контейнера

В deployment.yaml выражение {{ .Values.service.targetPort }} даёт containerPort: 8080. Сами эти цифры не открывают сокет: процесс приложения должен слушать нужный адрес и порт.

Отдельный вход: --namespace helm-lab устанавливает .Release.Namespace="helm-lab", а не добавляет ключ в .Values. Выбранные шаблоны не печатают metadata.namespace. Локальный helm template не создаёт пространство имён и не отправляет объекты в кластер; при установке пространство имён задают самой команде управления релизом.

Для проверки измените только порядок двух -f: ожидаются реплики 3, сообщение "Production-like lab" и прежний порт 8080. Строки результатов выше относятся к разным объектам и не составляют отдельный готовый YAML-документ.

Порядок файлов Helm 4.3.1; слияние значений чарта. Все значения и связи с шаблонами взяты из собственного учебного chart.

Семейства --set

helm template ledger ./chart --kube-version 1.36.6 --set replicaCount=3
helm template ledger ./chart --kube-version 1.36.6 --set-string replicaCount=3

Первый запуск даёт целое число 3 и проходит. Второй гарантирует строку "3" и завершается ошибкой схемы. Одинарные кавычки оболочки в --set 'replicaCount=3' защищают аргумент, но не делают значение строкой для Helm. Для строкового тега, длинного идентификатора или переменной окружения используйте --set-string либо явно строковый YAML. Анализатор --set принимает true/false как логические значения, а обычные целые числа — в поддерживаемой целочисленной форме; не переносите на него все неявные правила YAML.

helm template ledger ./chart --kube-version 1.36.6 \
  --set-json 'extraEnv=[{"name":"TRACE","value":"true"}]'
helm template ledger ./chart --kube-version 1.36.6 \
  --set-json 'extraEnv=[{"name":"TRACE","value":true}]'

Первый JSON даёт строковое поле value, второй — логическое и отвергается схемой. --set-json удобен для сложных объектов и списков, а в 4.3.1 поддерживает также полный JSON-объект без формы ключ=значение. --set-file читает файл в строку вместе с конечным LF, байтом перевода строки, без разбора YAML. --set-file credentials.token=fixtures/token.txt сохраняет байты учебного токена; b64enc и обратное декодирование в тесте доказывают сохранность LF. --set-literal в выбранном CLI принимает буквальную правую часть с меньшим разбором специальных символов; сложный стабильный интерфейс обычно понятнее в файле.

Порядок между семействами флагов

Реализация 4.3.1 обрабатывает все -f, затем --set-json, --set, --set-string, --set-file и --set-literal. Внутри семейства действует правый повтор. Поэтому перестановка разных семейств в командной строке не обязана менять приоритет. Это факт конкретной реализации, который стоит повторно проверить при смене основной версии.

helm template ledger ./chart --kube-version 1.36.6 \
  --set-string config.message=text --set-json 'config.message="json"'
helm template ledger ./chart --kube-version 1.36.6 \
  --set-json 'config.message="json"' --set-string config.message=text

Оба проверенных запуска дают MESSAGE:"text". Устраните конфликтующие источники: проверка изменения не должна требовать помнить внутренний порядок анализатора. Для выпуска храните полный файл параметров окружения и отдельное короткое переопределение неизменяемого дайджеста образа. Много перекрывающих флагов затрудняет восстановление: история оболочки недостаточна как журнал конечной конфигурации.

Точки, запятые и скобки

helm template ledger ./chart --kube-version 1.36.6 \
  --set 'extraLabels.handbook\.example/owner=reader'
helm template ledger ./chart --kube-version 1.36.6 \
  --set-json 'extraLabels={"handbook.example/owner":"reader"}'

Оба способа создают один ключ метки handbook.example/owner. Обратная косая черта защищает точку от Helm, одинарные кавычки оболочки сохраняют саму черту. Без неё получилось бы вложенное отображение, отвергнутое схемой строковых меток. Запятая strvals разделяет присваивания, квадратные скобки задают индекс; JSON и файлы часто уменьшают число уровней экранирования. Секрет в argv попадает в историю, журнал или наблюдение процессов. --set-file убирает содержимое из argv, но оно по-прежнему может попасть в хранилище релиза и результат рендеринга.

False, ноль, nil и отсутствие

Отсутствующий ключ, null, пустая строка, 0 и false — разные намерения, но функции empty/default/required сближают их. При объединении null удаляет исходный ключ, а required схемы затем может отказать. Для необязательного логического параметра исходное значение лучше задавать в values.yaml, а схемой проверять тип и наличие. Выражение default true .Values.flag заменит законный false на true; hasKey отличает наличие ключа от истинности по правилу непустоты. Эта ловушка проверена отдельным диагностическим чартом. Основной сервис не использует искусственный READY: его неготовность моделируется неверным путём пробы.

Большое дерево параметров имеет цену комбинаций. Три независимых логических поля допускают до восьми сочетаний, шесть — до 64. Взаимоисключающие create/existingSecret проверяются явным условием с fail, а не обещанием в README. Измеряйте число поддержанных сочетаний, скорость отрицательной обратной связи и понятность ошибки. Возможность включить всё вместе не означает корректного продукта.

Шаблон — текст с действиями между {{ и }}. Движок сначала разбирает синтаксис этих действий, затем исполняет их с переданными данными и функциями, записывая байты. Обычный текст копируется как есть. Анализатор YAML видит результат позже. Поэтому корректная программа шаблона может напечатать неверный YAML, а правильный YAML — неверный объект API. Нельзя исправить синтаксис {{ if }} значением из -f: такая программа ещё не дошла до исполнения.

Это язык text/template с расширениями Helm и Sprig, а не произвольный Go. Нет import, обычных объявлений Go, арифметических операторов в привычной форме и доступа к любому файлу ОС. Вызовы идут без скобок и запятых Go; ключи с необычными символами читают через index. Sprig — библиотека вспомогательных функций, а не новый исполнитель программ. Часы, случайные значения и lookup добавляют внешние входы, поэтому не все выражения являются чистыми преобразованиями параметров.

Dot и объекты Helm

Точка — текущий контекст. На верхнем уровне Helm предоставляет Values, Release, Chart, Capabilities, Files, Template. Путь .Values.config.message проходит дерево данных; это не глобальная переменная с точками в имени. Release содержит Name, Namespace, Revision, Service, IsInstall, IsUpgrade. Chart — метаданные пакета, а не действующий Deployment. Capabilities — модель возможностей API, а не обещание готового контроллера.

{{ .Values.config.message }}
{{ .Values.config.message | quote }}
{{ printf "%s/%s" .Release.Namespace .Release.Name | quote }}

Первое действие печатает строку без защиты: hello: world способно изменить структуру YAML. Второе выдаёт строку в кавычках. Третье форматирует два значения, затем цитирует. Литералы внутри действий следуют синтаксису Go templates, а не YAML. Не оборачивайте quote ещё раз внешними кавычками: получится двойное цитирование в выходном тексте.

Pipeline передаёт значение последним

Pipeline, конвейер выражений, связывает команды символом |. Результат слева становится последним аргументом справа: "x" | repeat 3 означает repeat(3,"x"), а .Values.key | default "fallback" — default("fallback",value). Это не передача байтов Unix pipe между процессами, а передача значения Go между функциями. Тип остаётся числом, отображением или логическим значением, пока функция не сериализует его в строку.

Quote возвращает текст строки, toYaml — строку YAML, fromYaml разбирает YAML обратно в структуру, int преобразует поддерживаемый вход. Приведение не заменяет схему: ведущие нули идентификатора, неверная строка и переполнение могут потерять смысл. Величина CPU 50m не равна числу 50 с удалённой буквой. Функция с возвращённой ошибкой или соответствующим аварийным завершением прерывает исполнение, но не каждое преобразование сообщает ошибку таким способом. В Helm 4.3.1 int от строки not-an-int возвращает 0, а fromYaml от неверного YAML возвращает отображение с ключом Error. Локальные тесты проверяют эти мягкие результаты. Для последовательности есть отдельная fromYamlArray; fromYaml рассчитана на отображение. Проверяйте тип, Error и контракт входа, а не маскируйте ошибку приведением. При настоящем отказе вывод бывает частичным, поэтому код завершения всё равно обязателен к проверке.

Reflection и сравнение

{{ kindOf .Values.replicaCount }}
{{ typeOf .Values.replicaCount }}
{{ kindIs "bool" .Values.flag }}
{{ eq .Values.flag false }}

Kind сообщает категорию отражения типов Go, typeOf — конкретное имя типа. Диагностический вывод удобно помещать во временную ConfigMap через quote. Не печатайте весь Values в комментарий настоящего чарта: комментарии сохраняют секретные байты. Eq/ne/lt/le/gt/ge не сравнивают произвольные типы автоматически; строка "3" и число 3 способны дать incompatible types. Для структур есть deepEqual. Структурное равенство и равенство сериализованных байтов — разные проверки.

Пустота и явная проверка условия

False, 0, пустая строка, отображение и список длины 0, а также nil считаются пустыми в соответствующих условиях. Поэтому required не годится как проверка «число задано», если 0 разрешён. Схема minimum проверяет число, hasKey — наличие ключа, fail — явную ошибку прикладного контракта. Required полезен для непустого credentials.token при create=true: так делает основной чарт. Само наличие ключа token с пустой строкой не даёт пригодного секрета.

{{- if not (hasKey .Values "flag") -}}
{{- fail "flag must be explicitly present" -}}
{{- end -}}
value: {{ .Values.flag | toString | quote }}

В основном интерфейсе схема уже выполняет эту работу; не надо дублировать каждое правило. Цепочка .Values.optional.child.name | default "x" не гарантирует защиты от nil: левый аргумент вычисляется раньше default. Используйте dig по отображению, default dict для необязательного родителя или последовательные проверки; неверный тип родителя всё равно должен быть отклонён.

Сравнение на настоящем движке: empty (dict) даёт true, empty (dict "k" "v") — false; empty (list) даёт true, empty (list 1) — false. Пустота коллекции определяется её длиной, а не самим фактом отображения или списка.

Тесты реально создают сломанный шаблон и ожидают ошибку разбора. Другой пример подтверждает kindOf false=bool, default true false=true, строковый тип результата include. Это работа настоящего Helm, а не браузерная реализация языка. Для воспроизводимости фиксируйте Helm, байты зависимостей, имя и пространство имён релиза, возможности API, значения и постобработчик. Уберите now, randAlphaNum и генерацию ключей из стабильного рендеринга: случайный пароль при обновлении меняет приложение и остаётся в прошлых метаданных. Внешними Secret надо управлять явно.

If сохраняет точку, with меняет её

{{- if .Values.persistence.enabled }}
name: {{ .Release.Name }}
{{- end }}
{{- with .Values.resources }}
{{ toYaml . }}
{{- end }}

If проверяет непустоту условия и сохраняет контекст. With исполняет тело только при непустом аргументе и делает аргумент точкой. Внутри второго блока .requests означает resources.requests, а .Release отсутствует. После end прежняя точка возвращается. Если отображение пусто, поле может исчезнуть полностью; решите, является это необязательным интерфейсом или ошибкой ввода. Отступы исходника не показывают стек контекста.

На старте шаблона переменная $ обозначает переданный корень. Внутри with/range $.Release.Name достигает начального контекста Helm. При вызове именованного шаблона корнем становится переданный ему аргумент. Правило «$ всегда весь Helm» неверно для include с dict. В include "x" (dict "root" $ "item" .) вспомогательный шаблон видит отображение, путь к Helm — .root.Release.Name, а $.Release там отсутствует.

Range и переменные

{{- $root := . -}}
{{- range $index, $entry := .Values.extraEnv }}
- name: {{ $entry.name | quote }}
  value: {{ $entry.value | quote }}
{{- end }}

Для списка первая переменная — индекс 0,1,..., вторая — элемент. Для отображения — ключ и значение. Точка внутри range становится текущим элементом даже при наличии имён; .Release ищет поле у объекта переменной окружения и ошибается. $root сохраняет внешний контекст. У range есть else для пустой коллекции с исходной точкой. Если вывод должен содержать [] вместо отсутствия поля, это записывают явно.

Go template упорядочивает отображения с подходящими простыми ключами при range, однако Sprig keys возвращает список, для которого нужен sortAlpha, если порядок значим. Не стройте порядок миграций БД на обходе отображений. Для последовательности используйте список, для адресуемого интерфейса — отображение, для зависимых действий — отдельный граф. Рендеринг всех файлов чарта не означает последовательного исполнения контроллеров Kubernetes в порядке текста.

Область и затенение

{{- $message := "base" -}}
{{- if .Values.persistence.enabled -}}
  {{- $message = "storage" -}}
{{- end -}}

:= объявляет переменную, = меняет существующую. Повторное := во вложенном блоке способно затенить имя и оставить внешний $message прежним. Переменная из тела range не живёт после end. Именованный шаблон не наследует переменные вызывающего: передавайте необходимые данные аргументом. Малое отображение с root/item показывает зависимости лучше, чем неявное чтение всего Values.

Условие описывает контракт

{{- if and .Values.credentials.create .Values.credentials.existingSecret -}}
{{- fail "credentials.create and existingSecret are mutually exclusive" -}}
{{- end -}}

Create — логическое значение, existingSecret — строка; непустое имя одновременно с create=true отвергается до API. Пустой existingSecret при create=false допустим: учётные данные необязательны. Это доставка тестовой переменной, а не аутентификация сервиса. Проверка persistence требует одну реплику и выбирает Recreate; правило соответствует упражнению, а не универсальному смыслу RWO.

With extraLabels печатает пользовательское отображение, но явная проверка запрещает ключи app.kubernetes.io/name и app.kubernetes.io/instance. Селектор Deployment должен совпадать с метками Pod и оставаться стабильным. Очень аккуратный вспомогательный шаблон способен успешно исполниться и при этом оторвать Service от конечных точек. Поэтому проверки разобранного YAML сравнивают селекторы независимо от формы исходника.

Опыт со стеком

Во временной ConfigMap напечатайте kindOf . и $.Release.Name до with, затем внутри with items=[a,b]. Замените аргумент include на dict и сравните .Release.Name с .root.Release.Name. Текущие тесты проверяют rootRelease=ledger внутри with, а схема ниже дополнительно показывает передачу dict. Это фиксированная модель, не работающий отладчик: кнопки меняют шаг, не исполняют шаблон. Для ошибки важнее понять объект перед точкой, чем добавить ещё один символ $ наугад.

1. Верхний уровень

. и $ обозначают исходный объект Helm.

Действует: Engine.

Helm root: . = $; With: не открыт; Range: не открыт; Аргумент: нет; Helper: не вызван; Текст: нет

Контекст: нет → Release/Values. Данные переданы движком.

2. Внутри with

. стало resources, $ осталось первоначальным корнем.

Действует: With.

Helm root: $ → Helm; With: . → resources; Range: не открыт; Аргумент: нет; Helper: не вызван; Текст: нет

Dot: Helm → resources. $.Release.Name доступно, .Release.Name уже нет.

3. Внутри range

После выхода из with range делает точкой один элемент extraEnv.

Действует: Range.

Helm root: $root → Helm; With: закрыт; Range: . → {name,value}; Аргумент: нет; Helper: не вызван; Текст: нет

Dot: Helm → элемент списка. Индекс и элемент можно связать переменными.

4. Передан явный dict

В аргумент включены root и item; helper не наследует лексические переменные.

Действует: Include.

Helm root: ссылка в root; With: закрыт; Range: элемент; Аргумент: root+item; Helper: . = $ = dict; Текст: в работе

Корень helper: Helm вызывающего → переданный dict. Теперь путь к релизу .root.Release.Name.

5. Возвращена строка

Include всегда даёт string; напечатанное false не стало bool.

Действует: Helper.

Helm root: не изменён; With: закрыт; Range: продолжится; Аргумент: не мутируется; Helper: завершён; Текст: string

Тип: данные и действия → строковый результат. nindent форматирует текст, if проверит его непустоту.

{{- $_ := set $copy "handbook.example/part" "api" -}}
{{ toYaml $copy }}

Dict создаёт отображение, list — список. Get читает значение по ключу, hasKey проверяет наличие, index обращается к отображению или списку, dig проходит вложенные отображения с запасным значением. Get отсутствующего ключа не позволяет отличить его от явно пустой строки. Set/unset меняют отображение и возвращают его; $_ подавляет ненужный вывод. Без присваивания результат set может напечататься в YAML.

Merge предпочитает исходное отображение назначения, mergeOverwrite — правые источники. Они не обещают независимой глубокой копии вложенных отображений: два интерфейса способны ссылаться на одну структуру. DeepCopy перед изменением исключает такую связь. Лучше не менять .Values вовсе: иначе второй вспомогательный шаблон в другом файле зависит от порядка исполнения первого. Append/concat работают со списками, но не объединяют объекты Kubernetes по name.

Files и размер

.Files.Get читает байты включённого файла чарта, а не произвольный путь ОС. Файлы шаблонов, исключённые .helmignore и внешние файлы недоступны этим способом. Files.Glob выбирает набор, AsConfig сериализует строковые значения, AsSecrets кодирует байты в base64. Файлы не исполняются как шаблоны без tpl. Размеры ресурсов ограничены API/etcd, Secret обычно не может превышать 1 MiB. Чарт и содержимое дополнительно хранятся в метаданных релиза. Большой встроенный исполняемый файл лучше доставлять образом или артефактом, а не ConfigMap.

Наш operator-note выводится многострочным скаляром и намеренно не входит в checksum/config: процесс читает только MESSAGE. Если заметка станет реально читаемой конфигурацией, измените контракт контрольной суммы и проверку. Стабильный хеш не доказывает полноту набора хешируемых входов. Внешний Secret также не меняет контрольную сумму чарта: перезапуск процесса с новым окружением должен иметь отдельный план.

Tpl — новый уровень исполнения

# Только отдельный опыт:
# values: messageTemplate: '{{ .Release.Name }}'
message: {{ tpl .Values.messageTemplate . | quote }}

Tpl исполняет строку как шаблон с выбранным контекстом. Автор параметров получает способность обращаться к функциям и другим данным, а при рендеринге с сервером — к lookup. Ограниченное отображение уменьшает видимость, но не превращает язык в доказанную изолированную среду. Не принимайте tpl от недоверенного пользователя в задании доставки с широкими правами. В основном чарте MESSAGE — обычная строка; второй уровень исполнения не нужен и не скрывает новые входы от проверки изменения.

Lookup и внешнее состояние

{{- $object := lookup "v1" "ConfigMap" .Release.Namespace "existing-settings" -}}
{{- if $object -}}
# object зависит от текущего API и permissions.
{{- end -}}

Lookup обращается к API по apiVersion/kind/namespace/name. Пустой name запрашивает список с items, непустой — один объект. Not found и forbidden различны: ошибка доступа завершает рендеринг. Клиентский template не получает настоящий результат API; серверный пробный запуск допускает чтение. Поэтому чарт, создающий пароль «только если lookup не нашёл Secret», даёт разные манифесты локально и на сервере и зависит от прав. Это ухудшает сравнимость пробного и настоящего обновления.

Явный credentials.existingSecret с документированным ключом token оставляет байты на стороне Kubernetes и делает интерфейс чарта прозрачнее. Helm не читает содержимое для SecretKeyRef. Kubernetes позже обрабатывает ссылку при запуске Pod. Наличие Secret не доказывает правильный токен или работоспособность приложения. Малые вспомогательные шаблоны полезны для стабильных имён, селекторов и сериализации; гигантская условная фабрика рабочих нагрузок усложняет проверку изменения. Измеряйте вложенность, размер вывода и время проверочных примеров до оптимизации include.

Отступы относятся к результату

resources:
  {{- toYaml .Values.resources | nindent 2 }}

ToYaml сериализует структуру в строку. Indent 2 добавляет каждой строке два пробела; nindent сначала добавляет LF, байт перевода строки, затем отступ. Левая отметка {{- удаляет пробельные байты слева, включая LF после двоеточия; nindent возвращает необходимую строку. Число пробелов зависит от места в итоговом документе: resources контейнера в нашем Deployment выводится с nindent 12. Бездумное копирование nindent 2 в любую глубину ломает структуру.

Range меняет точку, но не отступы YAML. Каждый элемент списка должен начинаться дефисом в правильной колонке, вложенные ключи — глубже. Смотрите вывод --show-only, разбирайте YAML и проверяйте точные пути. Show-only ограничивает печать и не гарантирует игнорирование ошибки в другом загруженном шаблоне: чарт сначала должен исполниться.

Удаление пробелов по краям действия

key: value
{{- if .Values.enabled -}}
next: yes
{{- end -}}

Это намеренно опасный фрагмент: удаление пробелов с двух сторон способно склеить строки. {{- 3 }} означает удаление пробелов и число 3, {{-3 }} — отрицательный литерал. Практичный подход — удалять пробелы у управляющих действий, вставлять блоки через nindent, затем просматривать результат. Определять корректность по отступам исходника нельзя.

Тип выбирается по API

ConfigMap.data, env.value, метки и аннотации — строки; READY:false без quote стал бы логическим значением YAML и не соответствовал API. Replicas и containerPort — целые числа, там quote создаёт ошибочную строку. Величины CPU/памяти обычно печатают строками 50m/32Mi. «Цитировать всё» так же неверно, как не цитировать ничего. Нецитированный скаляр имеет собственную грамматику: двоеточие с пробелом создаёт отображение, # после пробела начинает комментарий, некоторые слова и числовые формы получают неявный тип.

Для тега образа "1.0" явная строка сохраняет идентичность. Якоря YAML разворачиваются анализатором и обычно не остаются живыми ссылками в данных Go; изменение одного ключа после объединения не обязано обновить другой по старому якорю. YAML — формат входа, а не исполняемая система зависимостей.

Многострочные bytes

data:
  note: |-
    first line
    second line

Вертикальная черта сохраняет LF, сворачиваемый скаляр > складывает многие переводы строк в пробелы. Суффикс - удаляет конечный LF, + сохраняет дополнительные LF, отсутствие суффикса оставляет один завершающий перевод. Токен из --set-file содержит исходный LF, пока вы явно его не удалили. Нельзя автоматически обрезать все секретные байты. Наш тест сравнивает декодированный Secret с read_bytes, поэтому ловит невидимое изменение окончания.

Документы и дубликаты

Разделитель --- начинает документ. Вывод Helm содержит комментарии Source, возможные пустые документы и обработчики. Тесты выбирают объект по kind/name и пропускают null, а не полагаются на порядковый номер. Дубликаты ключей опасны: ряд анализаторов оставляет последний без ошибки. Для серьёзного конвейера используйте анализатор с отказом на дубликатах; затем проверяйте уникальность group/version/kind/namespace/name. Постобработчик способен изменить уже проверенный вывод — проверки утверждений должны применяться и к окончательным байтам.

Байтовое и структурное равенство

Байтовая воспроизводимость включает порядок и комментарии, структурная допускает различия представления одного дерева объектов. Тесты проверяют оба свойства: два обычных template одинаковы как строки, а рендеринг каталога и tgz равен как разобранные объекты. Архив package может содержать время в заголовках tar, поэтому равенство манифестов не выдаётся за одинаковую SHA архивов. Для продвижения выпуска передавайте тот же проверенный tgz, а не создавайте новый пакет между окружениями.

helm template ledger ./chart --namespace helm-lab --kube-version 1.36.6 \
  --show-only templates/configmap.yaml
helm template ledger ./chart --namespace helm-lab --kube-version 1.36.6 \
  --debug > rendered.yaml

Первый запуск сокращает вывод, второй даёт диагностический контекст и требует защиты файла при Secret. Номер строки ошибки YAML часто относится к полученному документу, не шаблону; сначала найдите Source. Проверка yamllint исходника с незаменёнными действиями не доказывает итоговый YAML. Локальная синтаксическая проверка честно дополняется допуском API и наблюдением нагрузки: ни одна из них не заменяет другую.

Зависимость — код, а не только версия

Зависимость чарта — включаемый пакет со своими шаблонами, исходными параметрами и схемой. Дочерний чарт приложения создаёт ресурсы, библиотечный чарт предоставляет вспомогательные шаблоны без собственных рабочих нагрузок. Они входят в одну операцию релиза; ошибка одной зависимости блокирует рендеринг или оставляет частично изменённый набор. Umbrella chart, чарт-оболочка нескольких зависимостей, удобен только при действительно связанных жизненных циклах. Сборка БД, брокера сообщений и API в один релиз не создаёт общую транзакцию данных.

dependencies:
  - name: lab-labels
    version: 0.1.0
    repository: file://../lab-labels

Этот фрагмент применяется в отдельной временной копии к библиотеке из labs/dependency. Основной чарт не требует зависимости и работает офлайн. File:// разрешает локальный путь относительно чарта. HTTP-зависимость использует зарегистрированный репозиторий или URL, OCI — ссылку реестра. Ограничение версии может допускать диапазон, но реально выбранные версии фиксируют файлом блокировки и сохранёнными архивами.

Update и build — разные намерения

helm dependency update ./chart-copy
helm dependency build ./chart-copy
helm dependency list ./chart-copy

Update разрешает ограничения Chart.yaml, получает зависимости в charts/ и создаёт либо обновляет Chart.lock. Build при наличии файла блокировки восстанавливает набор из него, не выбирая новые версии. Без файла блокировки build способен заново разрешить зависимости, поэтому наличие файла — существенная проверка конвейера. List показывает объявленные зависимости и состояние, но не доказывает подлинность байтов или работоспособность приложений.

Дайджест Chart.lock связывает описание и выбранный набор зависимостей; он не является подписью каждого .tgz. Сохраняйте контрольные суммы и подписи самих архивов. В HTTP-репозитории перезаписываемая версия могла бы отдавать другие байты. Файл блокировки не заменяет неизменность репозитория и доверенную подпись. Локальный тест удаляет charts/ только временной копии и восстанавливает библиотеку; байты Chart.lock остаются равными, разобранные манифесты совпадают. Рабочая копия читателя не удаляется.

Scoped values и global

Родитель передаёт параметры дочернему чарту под ключом имени зависимости; внутри дочернего пакета это поддерево становится собственным .Values без родительского префикса. Произвольные параметры родителя ему недоступны. Явно выделенное поддерево global доступно нескольким чартам по договорённости. Global не является переменной ОС или настройкой всего кластера — это область параметров одного рендеринга.

# Parent values для условного child с именем cache:
cache:
  replicaCount: 1
global:
  imageRegistry: registry.example.invalid

Дочерний пакет увидит .Values.replicaCount=1 и .Values.global.imageRegistry, но обязан сам использовать global при формировании ссылки образа. Дублирование одной настройки в родителе, дочернем пакете и global порождает неочевидный приоритет; документируйте один источник. Имена вспомогательных шаблонов общие для дерева, поэтому библиотечный префикс и версия важны даже при отдельных параметрах.

Alias, conditions и tags

Alias, псевдоним, позволяет включить один пакет под двумя именами с отдельными поддеревьями параметров; ресурсы всё равно должны избегать фиксированных имён. Condition, условие включения, — путь логического значения в параметрах. Tags, теги группировки, объединяют зависимости. При заданном применимом condition оно имеет приоритет над tags; в списке путей условий существенен первый найденный подходящий путь по правилам Helm. Это не произвольное правило «любой false выключает всё».

# Пример metadata отдельного зависимого chart, не основной ledger:
- name: worker
  alias: reports
  version: 1.2.3
  repository: https://charts.example.invalid
  condition: reports.enabled
  tags: [background]

В параметрах родителя нужен reports.enabled логического типа. Tags размещают на предусмотренном верхнем уровне, не в произвольном global. Import-values переносит экспортированные дочерние значения либо выбранный путь в путь родителя до рендеринга. Это преобразование интерфейса, а не возврат данных уже работающего приложения. Импорт может конфликтовать с исходными значениями или схемой; фиксируйте путь и проверяйте итоговое дерево.

Практический выбор

Если оператор и приложение обновляются с разным темпом, имеют разные права и владельцев, разделите релизы. Библиотека стабильных меток уместна и дешева. Измеряйте загрузку зависимостей, число объектов, размер записи релиза и сложность отката. После обновления Chart.lock проверяющий должен увидеть версии, контрольные суммы и манифесты, а не только новый дайджест. Офлайн требует реальных архивов: один файл блокировки без байтов не обслужит установку.

Package не является сборкой Go

helm package ./chart --destination ./dist
helm show chart ./dist/ledger-api-0.1.0.tgz
helm show values ./dist/ledger-api-0.1.0.tgz
helm template ledger ./dist/ledger-api-0.1.0.tgz \
  --namespace helm-lab --kube-version 1.36.6

Package создаёт архив чарта, не компилирует приложение и не загружает контейнерные образы. Имя архива содержит name/version метаданных. --version меняет версию пакета, --app-version — информативное поле, но ни один не меняет автоматически тег образа шаблона. Каталог назначения вне чарта исключает самовложение архивов. Show читает пакет, template исполняет его. Тесты сравнивают разобранные объекты каталога и tgz, отдельно точные байты включённого файла.

HTTP chart repository

HTTP-репозиторий чартов — каталог HTTP(S) с index.yaml и архивами по URL. Repo add сохраняет имя и адрес у клиента, repo update скачивает индекс, search repo ищет в локальном индексе. Старый индекс способен показывать устаревшую версию; обновление индекса не доказывает неизменность архива по URL. Такой сервер не является API Kubernetes или хранилищем истории релиза.

helm repo add handbook https://charts.example.invalid
helm repo update handbook
helm search repo handbook/ledger-api --versions
helm pull handbook/ledger-api --version 0.1.0 --destination ./dist

Example.invalid — намеренный заполнитель адреса своего сервера, а не рабочее публичное хранилище. --version фиксирует пакет вместо выбора последней подходящей версии. Pull без --untar сохраняет архив, с --untar распаковывает, но доверия не добавляет. Для публикации своего HTTP-репозитория helm repo index ./dist --url https://charts.example.invalid создаёт индекс в личной промежуточной папке; его публикуют согласованно с архивами. --merge существующего индекса не восстанавливает неизвестные версии сервера.

OCI registry

OCI, Open Container Initiative, — семейство форматов и протоколов артефактов с адресацией по содержимому. Чарт в OCI-реестре хранится артефактом, но не становится запускаемым образом. Дайджест чарта и дайджест образа определяют разные манифесты. Тег удобен как версия, дайджест связывает запрос с содержимым; доверие к издателю остаётся отдельной задачей.

printf '%s' "$REGISTRY_PASSWORD" | \
  helm registry login registry.example.invalid \
  --username "$REGISTRY_USER" --password-stdin
helm push ./dist/ledger-api-0.1.0.tgz \
  oci://registry.example.invalid/handbook
helm pull oci://registry.example.invalid/handbook/ledger-api \
  --version 0.1.0 --destination ./downloaded

В Helm 4 registry login принимает domain[:port], а не полный URL со схемой и путём. --password-stdin уменьшает утечку в argv, но файл учётных данных надо защищать. Push получает созданный tgz; конечные имя и версия берутся из метаданных, поэтому к адресу назначения не дописывают произвольный тег как у docker push. В 4.x чарт можно установить по OCI-дайджесту: его берут из ответа своего реестра или доверенного описания, а не из учебного фиктивного хеша. --plain-http и --insecure-skip-tls-verify ослабляют транспортную проверку и не исправляют неизвестную причину ошибки TLS.

Provenance и доверие

Provenance — сведения о происхождении и проверяемая связь подписи с содержимым. Классический .prov — подписанный OpenPGP-документ с метаданными и хешем архива. Проверка связывает подпись с выбранным ключом и байтами; право ключа выпускать боевой пакет задаёт политика доверия. Подпись не анализирует шаблоны, обработчики, полномочия и уязвимости образа.

helm package ./chart --destination ./signed \
  --sign --key 'HANDBOOK SIGNER' --keyring ./private-signing-keyring.gpg
helm verify ./signed/ledger-api-0.1.0.tgz --keyring ./trusted-public.gpg
helm pull handbook/ledger-api --version 0.1.0 --verify \
  --keyring ./trusted-public.gpg --destination ./verified

Это рецепт со своими подготовленными ключами; подпись редакцией не выполнялась. --verify требует доступного .prov и успешной проверки, а не наличия файла рядом. Закрытый ключ не кладут в чарт, журнал конвейера или переносимую книгу. Подписывающий ключ и доверенное кольцо открытых ключей — разные материалы и права. OCI способен переносить слой происхождения, но поведение конкретного реестра проверяют отдельно: произвольная подпись реестра не обязана поддерживаться helm verify.

Для kind загрузите свой образ локально, для VM доставьте в личный реестр или CRI по соседнему тому.

Продвижение релиза переносит тот же чарт и содержимое образа между окружениями с явно различными параметрами. Не пересобирайте приложение после теста под тем же тегом. Хеш параметров и итоговые манифесты сохраняйте защищённо вместе с временем, пространством имён, контекстом и ревизией. Рабочая папка — ваша копия labs; chart и namespace не сбрасываются между упражнениями. Наш scratch image не содержит shell, CA bundle и debug tools: приложение только HTTP, это осознанный минимальный контракт.

(
    cd service || exit 1
    mkdir -p bin || exit 1
    CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build \
      -trimpath -o bin/ledger-api . || exit 1
    docker build -t ledger-api:0.1.0 . || exit 1
)

Скобки создают дочернюю оболочку: после сборки вы остаетесь в рабочей папке labs, где находятся chart и fixtures. Если компилятор отказал, docker build не запускается со старым оставшимся бинарником. GOARCH выбирают под узлы; этот блок показывает только amd64.

Эти команды сборки предназначены личной VM/контейнерной среде, не запускаются автоматически тестами книги. -trimpath удаляет зависимые от путей записи сборки, CGO_ENABLED=0 позволяет static Go без внешней libc. GOARCH должен соответствовать nodes; ошибку exec format error нельзя исправить --wait timeout. Для kind выполните kind load docker-image ledger-api:0.1.0 --name handbook в своём compact-профиле. Для kubeadm image должен быть в доступном nodes registry; подставьте repository и digest своего опубликованного образа в отдельный values. Docker клиента не равен containerd nodes, поэтому docker images на ноутбуке не доказывает наличие image в кластере.

Сделать local review

Один файл environment.yaml станет сохранённым источником параметров для проверки и установки. Создайте его из defaults только при первом занятии; существующий файл сохраняется. Режим оболочки set -C запрещает перенаправлению молча затереть уже появившийся файл. Просмотрите его перед рендерингом. Значения ожидаемого ответа ниже относятся к неизменённой исходной копии: две реплики и MESSAGE=Hello from Helm.

if test -e environment.yaml || test -L environment.yaml; then
    printf '%s\n' 'Using existing environment.yaml; inspect it before changing the release.'
else
    (set -C; cat chart/values.yaml > environment.yaml) || exit 1
fi

helm lint ./chart --strict --kube-version 1.36.6 -f environment.yaml &&
helm template ledger ./chart --namespace helm-lab --kube-version 1.36.6 \
  -f environment.yaml > rendered.yaml &&
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" \
  --namespace helm-lab apply --server-side --dry-run=server -f rendered.yaml

Lint и template локальны. Последняя команда требует API и проверяет текущий server-side admission с правами текущей личности; test-hook Pod в rendered stream тоже проверится как обычный документ, но не будет исполнен. Dry-run создания CRD и последующего CR в одной пачке имеет особые ограничения, которых наш chart не создаёт. Просмотрите resources, selectors, image, requests и namespace до настоящего install.

Проверяются именно те chart и environment.yaml, которые будут переданы install. Между просмотром rendered.yaml и установкой не меняйте эти файлы или зависимости. Helm install снова рендерит чарт, а не читает rendered.yaml: файл служит материалом проверки, а не уже применяемым пакетом. В нашем чарте нет now, случайной генерации, lookup или post-renderer; с такими внешними входами совпадение отдельного render и install потребовало бы дополнительного контроля.

Upgrade не стирает прошлое

Upgrade загружает нынешний релиз и новый чарт, выбирает итоговые параметры, рендерит целевой манифест, применяет ресурсы и создаёт новую ревизию. Статус pending-upgrade защищает от обычного параллельного запуска над тем же релизом; это не распределённая транзакция всех объектов. Сбой CLI после отдельных запросов может оставить изменённый ConfigMap, новый ReplicaSet, прежние Pod и метаданные failed/pending. Старые ревизии сохраняются согласно history-max и служат журналом желаемых манифестов, а не снимком всех текущих состояний.

После неудачи различайте последнюю запись и последнюю развёрнутую запись. В реализации 4.3.1 сначала читается наибольший номер истории. Если его статус pending, обычный upgrade отказывает как при незавершённой операции. Если последняя запись failed, но в истории есть deployed, текущей основой для прежнего Manifest и повторного использования параметров становится deployed. При этом номер новой попытки всё равно равен последнему номеру плюс один. Когда deployed нет, предусмотрен отдельный путь для последних failed или superseded. Это не совет удалять pending Secret: сначала определите, продолжает ли прежний клиент или hook работу.

 | Запись | Наблюдаемое состояние | Следующий обычный upgrade

 | Ревизия 1: deployed, MESSAGE=old | Сохранённая успешная конфигурация | Основа current при последующей failed 2

 | Ревизия 2: failed, MESSAGE=new | Часть ресурсов могла уже измениться | Следующий номер — 3; reuse не означает автоматическое принятие параметров failed 2

 | Ревизия 2: pending-upgrade | Завершение прежней операции не установлено | Новый upgrade отказывает; сначала исследуют владельца действия и объекты

Неявное поведение параметров зависит от нового ввода

Обозначим D1 — исходные значения старого чарта, D2 — нового; U1 — сохранённый набор пользовательских параметров; N — новые -f/--set. В реализации 4.3.1 без специальных флагов при пустом N копируется U1, затем объединяется с D2. При непустом N старый U1 сам по себе не копируется. Поэтому добавление одного --set способно потерять прежнее пользовательское переопределение другого ключа. Утверждение «upgrade всегда сохраняет параметры» неверно.

 | Режим | Основа и приоритет | Проверяемый эффект

 | Без флагов, N пуст | D2 + U1 | Новые defaults и прежние пользовательские параметры

 | Без флагов, N непуст | D2 + N | U1 может исчезнуть

 | --reset-values | D2 + N | Игнорирует U1

 | --reuse-values | Старое объединённое дерево D1+U1, затем N | Новые defaults могут не войти

 | --reset-then-reuse-values | D2 + U1 + N | Новые defaults, прежние и новые переопределения

Это упрощённая запись для отображений совместимых типов; null и схема добавляют ограничения. Reset-values имеет приоритет над reuse-values, оба заставляют reset-then-reuse игнорироваться. Не комбинируйте конфликтующие флаги ради угадывания результата. Поведение подтверждено чтением pkg/action/upgrade.go 4.3.1; настоящие обновления кластера в этой редакции не выполнялись.

Сравнимый опыт

Пусть прошлый пользовательский набор задавал replicaCount=3 и message=old. Новый чарт по умолчанию даёт message=new-default, N содержит только replicaCount=2. С reset-values получится message=new-default; с reuse-values — old; с reset-then-reuse тоже old, но для совершенно нового ключа D2 последний режим сохранит новое исходное значение без наследования старого объединённого дерева. Схема в главе о параметрах показывает сам процесс объединения шагами; в этой главе схема прослеживает частичный отказ применения.

helm upgrade ledger ./chart --reset-values -f environment.yaml \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab --wait=watcher --timeout 180s
helm upgrade ledger ./chart --reuse-values --set replicaCount=2 \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab --dry-run=server --hide-secret

Это сравнение намерений, не инструкция последовательно исполнять две разные политики выпуска. В основной линии предпочтительны полный версионируемый environment.yaml и явный reset-values: результат восстанавливается из входов без поиска случайной истории CLI. Перед изменением сохраните пользовательские параметры через get values без --all и отдельно вычисленные с --all, манифест и историю в защищённую папку.

Для сохранённого U1 в формулах важна именно выбранная current release, а не произвольный последний вывод терминала. Сравните helm get values ledger --revision 1 и helm get values ledger --revision 2 с явными kubeconfig, context и namespace из установочной главы. Эти два чтения не меняют приложение. Если failed 2 содержит нужное новое сообщение, перенесите его осознанно в environment.yaml; не рассчитывайте, что следующий вызов без этого файла унаследует неудачную попытку.

Серверное применение и владение полями

SSA, Server-Side Apply, — серверное применение: клиент передаёт желаемые поля и имя управляющего полями, а API ведёт managedFields. Конкурирующие владельцы могут вызвать конфликт. Helm 4 при установке по умолчанию использует server-side=true; при обновлении и откате server-side=auto наследует метод прошлого релиза, включая клиентское применение Helm 3. Поэтому новый CLI не переводит автоматически каждый исторический релиз на SSA. --server-side=true/false задаёт выбор явно; смена требует проверки принадлежности полей и пробного запуска.

Конфликт SSA отличается от ошибки принадлежности объекта релизу Helm по меткам и аннотациям. --force-conflicts отнимает конфликтующие поля у другого управляющего; --force-replace заменяет ресурсы и способен изменить идентичность или вызвать недоступность. --take-ownership обходит проверку принадлежности существующих объектов и даёт Helm возможность позднее удалить их. Ни один из этих флагов не является универсальной починкой обновления. Выясните владельца, неизменяемые поля и судьбу данных до действия.

  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab

В 4.3.1 rollback-on-failure включает watcher, если оставлен hookOnly, и при неудаче пытается вернуться к предыдущему успешному релизу. Это компенсирующее действие с собственными ошибками API и обработчиков, а не атомарная отмена. До возврата часть ресурсов и внешние побочные эффекты уже могли измениться. Cleanup-on-fail разрешает удаление новых ресурсов неудачного обновления; он не возвращает запись в БД и не уничтожает все внешние эффекты обработчика.

Сломанный readinessPath=/missing-readyz создаёт новый Pod с живым процессом, но проба готовности получает 404. При maxUnavailable=0 старый готовый Pod может сохранить обслуживание, а обновление дойдёт до предельного времени. После исправления пробы следующий upgrade восстанавливает обновление экземпляров без удаления релиза или сброса. Измеряйте принятие API-запросов, готовые реплики и долю ошибок HTTP отдельно: failed в истории не означает, что все прежние пользователи уже потеряли доступ.

Hook — ресурс с особым событием

Hook, обработчик события Helm, — шаблон ресурса Kubernetes с аннотацией helm.sh/hook. События включают pre/post-install, pre/post-upgrade, pre/post-rollback, pre/post-delete и test. Helm выделяет их из обычных манифестов и выполняет в соответствующей фазе. Job или Pod обработчика блокирует фазу до завершения; прочие виды имеют свои условия готовности. Имя pre-install не означает «до любого изменения»: CRD могли быть установлены раньше.

Вес обработчика — целое число в строковой аннотации. Меньший вес выполняется раньше, отрицательные числа допустимы. При одинаковом весе есть дальнейшие правила сортировки, поэтому значимую зависимость миграций не оставляют имени файла. Чарт и дочерние пакеты способны добавлять обработчики; родитель не получает автоматического запрета всех обработчиков зависимостей. Проверяйте helm get hooks и исходники каждого пакета до выдачи полномочий.

metadata:
  annotations:
    helm.sh/hook: pre-upgrade
    helm.sh/hook-weight: "-10"
    helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded

Это иллюстрация отдельного Job, а не скрытая миграция основного ledger. Before-hook-creation удаляет прошлый одноимённый обработчик перед созданием; hook-succeeded — после успеха, hook-failed — после неудачи. Без явно заданной политики действует before-hook-creation. Эти правила управляют ресурсом Job/Pod, но не созданными им записями БД. TTL, время до автоматического удаления Job, также очищает объект, а не отменяет его действие.

У hook есть два наблюдаемых состояния: запись о выполнении внутри релиза и сам объект Pod или Job в Kubernetes. Перед созданием нового запуска Helm применяет before-hook-creation к прежнему объекту, строит новый ресурс, записывает время начала и стадию Running, затем посылает Create и ожидает завершения. После ответа обновляются время конца и результат Succeeded либо Failed; во время неясного исхода возможен Unknown. Удаление успешного Pod по hook-succeeded не стирает уже отправленные запросы к внешней системе и не делает журнал Pod долговременным. После потери ответа нельзя вывести из одного отсутствующего Pod, выполнялась ли миграция: проверяют запись hook, события и версию в самой БД.

Тест чарта — настоящий запуск в кластере

Основной чарт содержит Pod с hook:test, вызывающий wget через DNS Service. Это отдельный клиентский образ busybox:1.37.0; для офлайна его тоже доставляют и фиксируют дайджест. Приложение scratch не содержит wget, поэтому запуск curl внутри приложения здесь невозможен. Тестовый Pod имеет непривилегированный UID, запрет повышения прав, seccomp RuntimeDefault и не получает автоматический токен ServiceAccount; при политиках сети надо разрешить его трафик.

helm test ledger --kubeconfig "$LAB_KUBECONFIG" \
  --kube-context "$LAB_CONTEXT" --namespace helm-lab --logs --timeout 60s
helm get hooks ledger --kubeconfig "$LAB_KUBECONFIG" \
  --kube-context "$LAB_CONTEXT" --namespace helm-lab

Test не запускается автоматически от helm lint или template. Он создаёт и наблюдает Pod обработчика в кластере: нужны права create/get/watch/delete Pod и доступ к образу. --logs просит журналы результата и в 4.3.1 получает их после завершения тестов до очистки. Политика hook-succeeded затем удаляет успешный Pod, поэтому долговременные доказательства сохраняйте отдельно. Неудачный Pod остаётся для диагностики, before-hook-creation удалит его перед повтором. Журнал способен раскрыть данные приложения и секреты.

Нынешний тест wget проверяет успешный HTTP-код /api/hello через DNS и Service. Он не проверяет все поля JSON и не моделирует внешних клиентов через Ingress; расширять его надо по контракту приложения. Локальные тесты Go отдельно разбирают JSON.message и готовность. Зелёный обработчик с HTTP 200 не доказывает точное содержимое ответа, если тест его не сравнивал.

Миграция базы как самостоятельный протокол

Job миграции перед обновлением может изменить схему до запуска новой программы. Если затем образ не скачался, откат вернёт старый Deployment, но программа может быть несовместима с новой схемой. Надёжный порядок начинается с резерва и проверенного восстановления, затем совместимого расширения схемы: добавить поле без удаления старого, доставить совместимую программу, перенести данные и только позднее убрать старое. Однократное выполнение не гарантировано: повтор после потери ответа требует идемпотентности мигратора и учёта версии в самой БД.

Не давайте Job миграции общий административный токен кластера, если ему нужен только сетевой доступ к БД. Секрет доставки и права API — разные границы доверия. Если миграция занимает 15 минут, штатное предельное время 5 минут не означает её безопасной отмены. После ошибки проверьте, продолжает ли Job работать, какие транзакции зафиксированы и допустим ли повтор. --no-hooks пропускает протокол и меняет действие, а не просто ускоряет тот же выпуск.

Проверки и цена hooks

Измеряйте ожидание планировщика, загрузку образа и саму миграцию отдельно. Огромный образ с малым скриптом способен тратить основное окно на передачу. HTTP-тест тоже может ждать Pending из-за квот пространства имён. В этой редакции рендеринг и аннотации теста проверены реально, кластерное исполнение обработчиков не выполнялось. Наличие аннотации в YAML не объявлено доказательством запуска.

Rollback создаёт следующее событие

Rollback, откат, берёт сохранённые чарт, параметры и манифесты выбранной ревизии и применяет их как новую ревизию. История не перематывается и номер не уменьшается. После успешной ревизии 1 и неудачной 2 откат к 1 создаёт ревизию 3. Источник желаемого состояния старый, время действия и последствия новые. Номер ревизии Helm не равен номеру ReplicaSet Deployment.

В выбранной реализации rollback переносит сохранённые Manifest, Config, Chart и Hooks целевой ревизии в новую запись. Обычные шаблоны не исполняются заново с нынешним каталогом chart, новыми defaults или новым результатом lookup. Сначала API-клиент должен суметь разобрать старые и целевые manifests, затем выполняются hooks и обновление ресурсов. Поэтому изменение локального файла после выпуска не меняет цель отката, а удалённый API или новый admission policy всё ещё способны её отвергнуть. Сам hook при повторном запуске может сделать новый внешний запрос: сохранённый текст не означает сохранённый результат его прежнего действия.

helm history ledger --kubeconfig "$LAB_KUBECONFIG" \
  --kube-context "$LAB_CONTEXT" --namespace helm-lab
helm rollback ledger 1 --wait=watcher --timeout 180s \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab

Аргумент 1 выбирают только после проверки истории своего релиза: это пример цели, не совет всегда откатывать к первой. Без цели или с 0 CLI выбирает предыдущую по правилам команды, что менее понятно после нескольких отказов. Проверьте status/history, текущий образ, готовые конечные точки и HTTP.message. --no-hooks пропускает обработчики отката; --cleanup-on-fail разрешает удаление новых ресурсов неудачного отката. Они меняют последствия и не заменяют резерв данных.

Граница обратимости

Откат манифестов способен вернуть образ и строку ConfigMap. Он не возвращает содержимое PVC, удалённую таблицу, внешний эффект API, отправленное письмо или Secret, изменённый вне Helm. Старый тег мог быть перезаписан: для воспроизводимости нужен дайджест образа. Удалённая версия API способна сделать сохранённый старый манифест неприменимым на обновлённом кластере. История есть, но восстановление всё равно может отказать.

Автоматический rollback-on-failure — та же компенсирующая последовательность с собственными отказами. При недоступном API, отозванных полномочиях или зависшем обработчике восстановление не гарантируется. Сначала установите реальные объекты и состояние внешних данных, потом выбирайте цель. Удаление Secret истории ради снятия pending не исправляет приложение и может потерять связь с частичным состоянием. Ручная аварийная коррекция метаданных требует защищённой копии и понимания конкретной реализации.

Uninstall и история

helm uninstall ledger --keep-history --wait=watcher --timeout 180s \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab

Это заключительное отдельное упражнение, не подготовка следующей главы. Uninstall запускает обработчики удаления, удаляет обычные управляемые ресурсы и по умолчанию очищает историю. --keep-history сохраняет запись uninstalled, но не оставляет работающим приложение. Пространство имён, созданное через --create-namespace, обычно не удаляется автоматически. Cascade выбирает распространение удаления через ownerReferences: background, foreground и orphan имеют разную судьбу дочерних объектов и сроки наблюдения. Это не удаление всего пространства имён.

Имя удалённого релиза с сохранённой историей нельзя бездумно переиспользовать; install --replace предназначен для соответствующего случая и отмечен CLI как рискованный. --keep-history полезен для аудита, но сохраняет старые конфиденциальные параметры. History-max ограничивает историю осмысленно;0 означает отсутствие лимита и растущий объём, а не отключённую историю.

Keep оставляет ответственность владельцу

Аннотация helm.sh/resource-policy: keep нашей необязательной PVC просит Helm сохранить ресурс при удалении. Это оставшийся объект с отдельной ответственностью: аннотации принадлежности могут столкнуться с новой установкой. Keep не делает резерв, не гарантирует Retain тома PV и не защищает от пользователя с delete. Запишите имя PVC, том и физическое хранилище, reclaimPolicy, снимки и порядок повторного подключения.

Ресурсы обработчиков управляются иначе, чем обычные манифесты: для очистки нужны политики удаления, TTL или отдельные действия. Пространство имён, CRD, объекты оператора и данные внешних служб способны пережить релиз. До удаления составьте список своих ресурсов и данных, после сравните его с фактом. Удалять пространство имён ради сломанной ревизии нельзя без оценки сохранённых PVC и журнала.

CRD lifecycle

Файлы crds/ устанавливаются до обычных шаблонов, не шаблонизируются и не обновляются либо удаляются обычным жизненным циклом Helm как Deployment. Это сознательная граница защиты от потери собственных ресурсов API. --skip-crds пропускает установку и не исправляет отсутствующий API. Обновление схемы CRD, обработчиков преобразования, storedVersions и миграция объектов требуют отдельного плана владельца API. Удаление CRD способно удалить все экземпляры, включая данные нескольких релизов; пространство имён приложения не ограничивает общий CRD.

Наш чарт CRD не содержит. При добавлении зависимости-оператора отдельно документируйте владельца CRD, порядок установки/обновления и восстановление собственных ресурсов. Связь принадлежности Helm через метки и аннотации не равна Kubernetes ownerReferences, управляющей сборкой мусора. --take-ownership не переводит автоматически всю модель данных к новому владельцу безопасным способом.

Резерв и проверка восстановления

Минимальный журнал: точный архив чарта и подпись, пользовательские и вычисленные параметры, манифесты в защищённом виде, история, дайджест образа и внешние данные. Резерв Secrets/etcd входит в стратегию Kubernetes, резерв БД/PVC — приложения. Восстановление в отдельном пространстве имён или кластере должно доказать чтение данных и HTTP-контракт. RPO — допустимая потеря последних данных по времени; RTO — время возврата услуги, включая получение образов, прав, данных и проверку. Наличие tgz не задаёт ни один показатель автоматически.

Данные: B → B. Удаление hook Job не отменяет миграцию.

4. Rollback вернул imagev1

Создана revision3 со старым манифестом, но БД по-прежнемуB.

Действует: Helm.

Ревизии: v3 rollback; Миграция: прошлый эффект есть; Манифест: imagev1; Данные: B; Программа: совместимость неизвестна; Резерв: снимокA

Откат: manifestv2 → manifestv1. Старый код может не понимать новую схему.

5. Восстановление выбирают отдельно

Либо заранее совместимая схемаB, либо проверенное восстановление/миграция с оценкой потери новых данных.

Действует: Владелец данных.

Ревизии: не источник данных; Миграция: протокол известен; Манифест: выбран совместимый; Данные: восстановлено по плану; Программа: проверено чтение; Резерв: RPO/RTO измерены

Успех: старый image запущен → услуга и данные проверены. Нужен прикладной критерий, не только deployed.

Service и selector

Deployment задаёт желаемый шаблон Pod, ReplicaSet поддерживает число экземпляров, kubelet запускает контейнер. Service с портом 80 и targetPort:http направляет трафик на именованный containerPort8080 подходящих готовых Pod. ContainerPort сам не открывает порт ОС: приложение обязано слушать :8080. Стабильные метки селектора зависят от имени чарта и релиза, а не версии чарта. При смене пакета селектор не должен случайно стать конфликтующим неизменяемым полем или перестать находить Pod.

Чарт получает имя ledger-ledger-api через вспомогательный шаблон. Упрощённый trunc 63 не является универсальным решением уникальности длинных имён: разные имена способны обрезаться одинаково. Наши короткие фиксированные имена исключают эту коллизию; для публичного чарта проектируйте схему с проверкой или хеш-суффиксом. Имя релиза, DNS Service и имя приложения — разные идентичности.

Readiness, liveness и завершение

Проба готовности /readyz регулирует участие Pod в готовых конечных точках, проба жизнеспособности /livez — решение о перезапуске зависшего контейнера. При недоступной внешней БД безусловное падение liveness способно перезапускать все экземпляры и усиливать отказ. Готовность и обработку ограниченного режима определяют отдельно. Пробу запуска добавляют при действительно долгом старте, чтобы liveness не убивал процесс заранее. Задержки и пороги выбирают по измеренному старту и отказу, а не универсальному числу.

В учебном сервисе готовность становится false в начале завершения. Main получает SIGTERM через signal.NotifyContext, сервер прекращает принимать новые соединения, Shutdown ждёт активные запросы в своём временном бюджете, затем main завершается. Тест удерживает настоящий активный HTTP-запрос каналом, отменяет контекст, проверяет, что серверная функция ещё не вернулась, освобождает обработчик и получает полный ответ. Это проверка причинного свойства штатного завершения. TerminationGracePeriodSeconds=20 должен покрывать собственный восьмисекундный бюджет и накладные задержки, но распространение удаления конечной точки тоже требует измерения.

Resources и rollout

Запросы ресурсов requests CPU 50m и memory 32Mi участвуют в планировании, но не обещают фактический расход. 50m означает 0.05 CPU,32Mi —33554432 байта. Ограничения limits CPU 500m/memory 128Mi ограничивают исполнение: нехватка памяти способна вызвать OOMKill, квота CPU — замедление. Увеличение replicaCount умножает запросы и нагрузку, но не обязательно пропускную способность при общей БД. Максимум 6 в схеме — учебная защита от случайного масштабирования, а не оценка ёмкости кластера.

Обновление без постоянного локального состояния использует maxSurge1/maxUnavailable0: при двух репликах временно понадобится третья до завершения старых. Условный расчёт запросов планировщику: (2+1)×50m=150m CPU и (2+1)×32Mi=96Mi RAM для контейнеров приложения, без системных накладных затрат. Если места нет, новый Pod останется Pending. Уменьшение предельного времени не решает дефицит; запросы меняют после измерения потребления, а не ради зелёного статуса.

ConfigMap и Secret

ConfigMap хранит MESSAGE, envFrom копирует его в окружение при создании контейнера. Изменение объекта не обновляет os.Getenv запущенного процесса. Поэтому checksum/config от сериализованного MESSAGE помещён в аннотации шаблона Pod: изменение значимых байтов создаёт новый шаблон и обновляет экземпляры. Смена replicaCount не меняет этот хеш. Operator-note не вызывает перезапуска по нынешнему контракту: приложение её не читает.

Credentials.create создаёт Secret с data.token через b64enc, existingSecret ссылается на заранее созданный Secret. Это взаимоисключающие режимы. Токен внешнего Secret не читается Helm и не входит в контрольную сумму; его смена требует отдельного перезапуска или обновления конфигурации процесса. Созданный чартом токен входит в checksum/credentials и метаданные релиза. Контрольная сумма не шифрует слабый токен: по ней можно угадывать малое пространство значений. API_TOKEN здесь только демонстрирует доставку переменной окружения; аутентификация /api/hello не реализована.

Необязательная PVC: отдельный учебный режим

По умолчанию /data использует emptyDir. Необязательный постоянный режим создаёт PVC ReadWriteOnce с аннотацией keep. Наш Go-сервис не записывает туда прикладные данные: упражнение демонстрирует связывание и монтирование, а отдельный инспектор оставляет учебный маркер. Переход false→true не переносит файлы прежнего emptyDir. Helm не является средством миграции файлов.

При persistence=true проверка требует replicaCount 1, стратегия становится Recreate: старый Pod удаляется до нового. RWO ограничивает чтение и запись одним узлом согласно контракту тома, а не обязательно одним Pod. Прежний RollingUpdate с surge 1 мог зависнуть на Multi-Attach при планировании на другой узел. Recreate допускает перерыв обслуживания и не обещает мгновенного отсоединения и монтирования. Поддержка доступа, прав, ёмкость и топология проверяются на настоящем стенде.

Для основного kubeadm-стенда есть конкретный адаптер статического local PV: владелец своей VM wk1 создаёт /srv/handbook/helm-ledger-data с UID/GID 65532; владелец кластера применяет отдельные StorageClass helm-local и PV helm-ledger-local ёмкостью 256Mi с Retain и привязкой к wk1. Fixtures/storage.yaml запрашивает 128Mi этого класса. Это отдельный каталог и том, не занятые лабораторией Kubernetes. Класс kubernetes.io/no-provisioner не требует CSI и сам не выделяет диск. Профиль выбирают до первого PVC: storageClassName существующего запроса обычно неизменяем. Для kind или CSI нужен другой реально подготовленный профиль.

Сохраняемая PVC переживает удаление релиза, но Retain и keep не делают резервную копию. Статический локальный том привязывает данные к диску wk1: потеря узла не исправится простым переносом Pod. Смена размера в параметрах не гарантирует поддержку уменьшения или расширения. Настоящая БД требует собственного жизненного цикла данных, резерва, проверки восстановления и при необходимости StatefulSet или оператора. Добавление хранилища без потребности увеличивает цену восстановления.

Ошибка загрузки пакета находится до рендеринга; ошибка схемы — до API; forbidden — на границе прав; immutable field — в модели объекта; Pending — у планировщика или данных; отказ готовности — при исполнении приложения. В Helm 4.3.1 команда list без фильтров выбирает все состояния релизов. Обычно она показывает актуальную запись каждого релиза, а не все его прежние ревизии: для них служит history. Флаги --failed, --pending и --uninstalled сужают вывод; несколько таких фильтров объединяются как ИЛИ. Pending охватывает незавершённые install, upgrade и rollback. Uninstalled виден, только если метаданные удаления сохранены; удалённую историю команда не восстанавливает. Флага --all у list этой версии нет. Не путайте его с корректным helm get values --all, который добавляет вычисленные параметры и defaults. Отсутствие строки требует проверить namespace, права и ограничения выдачи. По умолчанию list возвращает не более 256 элементов: для большой области доступа проверяют также max/offset и фильтры. JSON удобен для сохранения и сравнения, но не проверяет готовность приложения. History --max ограничивает число показываемых ревизий, history-max команды upgrade — число сохраняемых. События способны исчезнуть из-за срока хранения, поэтому их сохраняют во время отказа. Describe Deployment не заменяет исследование конкретного Pod с ошибкой загрузки образа или монтирования.

helm list --namespace helm-lab --failed --pending \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --output json

Сохранённое и живое состояние

Get manifest — сохранённый текст Helm, kubectl get -o yaml — текущий объект API с дополнениями сервера, состоянием и возможным ручным дрейфом. Разность файлов не является прямым списком изменений чарта без нормализации серверных полей. --revision у get values/manifest выбирает историческую запись и не переносит кластер назад. Идентичность объекта Kubernetes включает UID: после удаления и создания то же имя обозначает другой объект.

Метод измерения

Определите границу: полное время CLI с запуском процесса, его CPU, пиковая RSS, размер манифестов, число объектов, время обнаружения API, запросов и ожидания. Не смешивайте первое скачивание зависимостей с прогретым рендерингом. Выполните серию одинаковых локальных template после прогрева, сохраните входы и распределение, затем меняйте один фактор. Десять запусков показывают порядок величины, но не надёжный p99. Отчёт содержит условия и существенные версии.

Разделите время выпуска на наблюдаемые интервалы: начало CLI → готовый локальный manifest; отправка объектов → принятие API; появление нового Pod → получение образа и запуск; запуск → readiness; готовность → проверенный HTTP. Эти интервалы могут перекрываться, поэтому нельзя механически складывать длительности независимых событий из разных часов. Для сравнения сохраняют одну версию чарта, значения, число объектов и их суммарные байты, состояние кэша, число реплик и нагрузку приложения. Если при тех же входах локальный render занимает 30 мс, а rollout 90 секунд, сначала проверяют Events, состояния Pod и загрузку образов. Ускорение шаблона на 10 мс не устранит 89 секунд ожидания registry.

Реальный контрольный запуск редакции: Helm 4.3.1, чарт без сетевых зависимостей,4 документа с тестовым Pod,3929 байт,10 последовательных запусков процесса и рендеринга; медиана около 26 мс, минимум 25 мс, максимум 31 мс. Это измерение конкретной машины и серии, не порог всех чартов. Точный отчёт последнего запуска может измениться при повторе. Длительность API, планирования, загрузки образа, ожидания и приложения здесь не измерялась.

Если время почти линейно растёт с числом однотипных объектов, ограничение может быть в шаблонах, сериализации или API-запросах. При низком CPU и большом полном времени ищите сеть, ограничение частоты запросов, DNS и ожидание ресурсов. При росте RSS с большим встроенным файлом уменьшайте содержимое чарта и копируемые строки. QPS/burst-limit меняют нагрузку на API; повышать их без наблюдения задержек и отказов сервера нельзя. Пользовательскую задержку приложения измеряют HTTP-запросом отдельно от успешности обновления.

Цена checksum и rollout

Пусть настройки меняются 40 раз в день, реплик две, полный перезапуск занимает 8 с, а новый образ передаётся только при изменении дайджеста. Хеширование времени в аннотации вызовет 40 бесполезных обновлений, хотя конфигурация не менялась. Хеш значимых байтов MESSAGE вызовет только необходимые. Это условный пример: реальное время и долю ошибок проверяют под нагрузкой. Сравните контрольную сумму при изменении заметки, сообщения и replicaCount. Тесты доказывают структурные отношения YAML, но не стоимость реального перезапуска.

Восстановление после неудачи

При неверном readinessPath сохраните наблюдения, верните правильный путь следующим обновлением и наблюдайте ReplicaSet. При отказе прав исправьте минимальную роль через владельца стенда, не переключайтесь на случайный административный контекст. При недоступном API дождитесь восстановления и исследуйте частичные изменения. При нарушенной БД сначала решайте совместимость данных и резервирование, потом выбирайте ревизию Helm. Такой порядок ограничивает повторное повреждение и сохраняет журнал причин.

Проверки module lookup не являются общим запретом сети для любого кода.

Задание 1: предсказать merge до запуска

Сначала рукой выпишите replicas, MESSAGE, requests.cpu/memory для prod→last и last→prod. Затем сравните template и parsed assertions. Проверьте --set replicaCount=3 против --set-string. Ошибку schema не обходите: исправьте тип входа. Во временной копии добавьте optional bool и подтвердите, что default true затрёт false. Закончите объяснением, какое значение существовало на каждом этапе: argv, map, template-string, YAML scalar, API field.

Задание 2: испортить шаблон, не разрушая стенд

Создайте временную копию chart и внесите {{ if }} без pipeline, затем неправильный nindent, затем обращение .Release внутри range extraEnv. Каждая ошибка должна попасть на свою фазу parse/execution/YAML. Checker автоматически воспроизводит parse case; остальные рецепты разбирают порядок диагностики. Не переносите заведомо сломанную копию в основной release. Исправление должно объяснить контекст и bytes, а не просто «снова стало зелёным».

Задание 3: пакет и dependency

Package основной chart, проверьте member и checksum, сравните parsed output каталога/архива. В отдельной копии добавьте file:// library, выполните dependency update, сохраните lock, удалите только копию charts и выполните build. Затем намеренно исключите *.tgz в helmignore: определите, почему существующий архив не виден loader. Основной chart остаётся без внешних dependencies, а учебный release сохраняет прежний набор объектов.

Задание 4: revision1 и HTTP

Подготовьте image и свой кластер по главе первого release, создайте namespace/минимальные права через владельца стенда. Создайте environment.yaml один раз по процедуре первого release и сохраняйте его между заданиями. Если файл уже есть, перечитайте его, а не копируйте defaults поверх своей работы. Во всех local review, install и upgrade используйте именно этот файл. Выполните local render, server admission dry-run, install с wait, status/history, endpoints и curl. Критерий: revision1 deployed, нужные ready replicas, JSON.message соответствует environment. Если без реального кластера — задание остаётся невыполненным, даже если все local tests прошли.

Задание 5: revision2 меняет конфигурацию

Измените только config.message в environment.yaml, затем upgrade --reset-values -f environment.yaml --wait=watcher с тем же именем/context/namespace. До запуска предскажите: config hash меняется, Pod template меняется, selector нет. После: новая Helm revision, новый ReplicaSet, MESSAGE в HTTP обновился. Смена replicaCount отдельно меняет scale, но не config checksum. Не пересобирайте image ради одного конфигурационного значения.

Перед намеренной поломкой запишите две разные исходные точки: последнюю deployed ревизию и значения текущего HTTP-ответа. После failed upgrade отдельно сохраните новую failed запись и фактические ConfigMap, шаблон Deployment, старые и новые Pod. Затем восстановите environment.yaml следующим upgrade и объясните, от какой записи взяты старые параметры и почему номер продолжил расти. Проверка задания — совпадение предсказанной причины с этими объектами, а не только исчезновение failed из краткого списка.

Задание 6: controlled readiness failure

helm upgrade ledger ./chart --reset-values -f environment.yaml \
  -f fixtures/not-ready.yaml --wait=watcher --timeout 45s \
  --kubeconfig "$LAB_KUBECONFIG" --kube-context "$LAB_CONTEXT" \
  --namespace helm-lab

Это намеренно неудачный выпуск на своём учебном release. Новый probe получает 404 с /missing-readyz; liveness остаётся 200. Сохраните history/events/Pod description и HTTP старого экземпляра. Ожидается timeout и failed revision, а при доступной ёмкости/старых ready Pod обслуживание может сохраниться. Восстановите следующим upgrade без последнего overlay: полный environment.yaml задаст /readyz. Не выполняйте uninstall и не удаляйте namespace. Отдельный повтор с rollback-on-failure покажет компенсирующую revision; он имеет смысл только после понимания первого отказа.

Задание 7: права и Secret

На отдельной ограниченной личности своего стенда удалите из выданной роли одно необходимое право чтения или создания тестового Pod, заранее согласовав изменение с владельцем. Используйте отдельный kubeconfig, а не переключайте общий context. Зафиксируйте forbidden resource/verb и восстановите минимальную роль. Для Secret используйте только dummy-token fixtures: create=true + --set-file, затем decoded bytes/LF и checksum. Убедитесь, что API_TOKEN не реализует auth; не называйте endpoint закрытым.

Задание 8: PVC и явные данные

Выберите профиль хранилища до первого создания PVC. Для основного kubeadm-стенда сначала выполните подготовку отдельного статического local PV владельцами VM и кластера: отдельный каталог wk1, класс helm-local без динамического выделения, том 256Mi с Retain. Затем fixtures/storage.yaml запросит 128Mi, одну реплику и Recreate. Этот адаптер не требует CSI и не использует соседний ledger-local. Для kind нужен иной подготовленный профиль. Подтвердите Bound и Pod на wk1; Pending до первого потребителя при WaitForFirstConsumer допустим. Приложение данные не пишет: после явной остановки Deployment отдельный Pod-инспектор записывает UUID-маркер и выводит его. Удалите только инспектор, повторите чтение и сравните тот же маркер. Верните приложение тем же обновлением Helm, устранив осознанный дрейф replicas 0. Удаление PVC/PV или каталога между чтениями — другой эксперимент; keep не резервирует данные.

Задание 9: восстановление и финальная очистка

После истории минимум из успешного и неудачного upgrade выберите успешную revision, сравните её image/config, выполните rollback и проверьте новую revision/HTTP. Только в конце практикума выполните uninstall --keep-history и проверьте оставшиеся namespace, test hooks и PVC keep. Запишите, что нужно для повторной установки с сохранённым claim. Удаление данных — отдельное решение читателя; книга не выполняет его автоматически.

Три независимых перехода

Обновление CLI, чарта и приложения — три разных изменения. Начните с копии истории, параметров и точных пакетов; выполните локальный рендеринг старого чарта новым проверенным клиентом и сравните структуру. Затем проверьте обнаружение и допуск API на своём стенде, после этого планируйте изменение релиза. Не совмещайте смену основной версии Helm, CRD оператора и необратимую миграцию БД в один непрозрачный шаг.

 | Helm 3 привычка | Основная линия Helm 4.3.1 | Почему важно

 | --atomic | --rollback-on-failure | Название не обещает транзакции данных

 | --force | --force-replace | Это замена ресурса с возможным outage

 | --wait как bool | watcher/hookOnly/legacy | Сравнивают конкретную strategy

 | Post-render executable path | Post-render plugin name | Иной контракт подключения

 | Registry login полный URL | Domain[:port] | Не тот же аргумент

 | Всегда client-side apply | Новый install SSA; upgrade auto наследует метод | CLI upgrade сам не переводит old release на SSA

 | Chart API v2 | Остаётся стабильным | Не требуется экспериментальный v3

Плагины и SDK, программная библиотека разработчика, требуют отдельной проверки совместимости. Новый путь импорта модуля Helm/v4 — не только замена имени исполняемого файла. Функции и стандартный чарт v2 сохраняют основную модель, но обработка ошибок, сериализация и новые возможности API могут изменить вывод. При смене стратегии ожидания определите отслеживаемые ресурсы и нужные RBAC list/watch. Совместимость конкретного чарта доказывается проверочными примерами и пробным развёртыванием, а не общей фразой о поддержке.

Кто получает какие полномочия

Автор чарта определяет возможные ресурсы и обработчики API. Автор параметров способен менять образ, команду, ссылки Secret, а при tpl — исполнять выражения шаблона. Клиент Helm и плагины действуют с локальными правами пользователя и kubeconfig. Личность API-клиента управляет ресурсами и историей релиза. ServiceAccount приложения — отдельная личность внутри Pod. Учётные данные реестра чартов и imagePullSecrets для загрузки образов — тоже разные. Смешение границ даёт избыточные права и непонятные forbidden.

В нашем чарте automountServiceAccountToken=false, контейнеру запрещено повышение привилегий, корневая файловая система доступна только для чтения, UID 65532. Эти настройки сужают права процесса, но не делают пространство имён полной границей безопасности и не проверяют происхождение образа. Запрет записи не защищает от чтения токена из окружения; Secret истории тоже содержит параметры. Реальные учётные данные не помещают в примеры, проверки и публичный отчёт об ошибке.

Review конечных манифестов

Проверьте ресурсы уровня кластера, hostPath/privileged/hostNetwork, RoleBinding/ClusterRoleBinding, токены ServiceAccount, обработчики с командами и сетевыми вызовами, внешние адреса, CRD и постоянные данные. Это конкретная проверка полномочий пакета, не запрет сложных чартов. Доверенная подпись не подтверждает разумность настроек. Постобработчик проходит ту же проверку: он меняет окончательные байты.

Воспроизводимое сопровождение

В журнале выпуска хранят совместимый набор: CLI Helm и плагины, хеши чарта и зависимостей, Chart.lock, параметры, версию Kubernetes/API, дайджесты образов, методы применения и ожидания, план резерва и совместимости данных. После исправления безопасности повторяют важные локальные проверки и пробный жизненный цикл. Срок поддержки ветки проверяют перед установкой, не принимая дату книги как вечный факт. Малый понятный чарт дешевле сопровождать и восстанавливать; сложность добавляют под измеренную потребность.

Ключевые факты

Официальный release4.3.1 и SHA Linux amd64 — release page; реально скачанный executable сообщил v4.3.1+gc0d08d0.

Текущая major4 и срок security-only ветки 3 — overview и EOL.

Порядок семейств --set — MergeValues, дополнительно реальный fixture.

Условия reset/reuse/default upgrade — reuseValues; cluster upgrade не выполнялся.

Граница install dry-run — RunWithContext; возврат до изменения обычных ресурсов объяснён отдельно.

JSON→gzip→base64 release storage — encoding source; кодирование не названо шифрованием.

Контекст языка — спецификация text/template, расширения — engine Helm.

Что не доказано этой редакцией

Реального Kubernetes-кластера не было: не исполнены admission, install/upgrade, wait watcher на настоящих workloads, запуск hooks, rollback, PVC binding/attach и lifecycle CRD. Не выполнены remote OCI push/login, подпись chart собственным key и GPG-проверка binary. Их рецепты имеют явные входы и критерии, но не выдуманный журнал успеха. Полный список выполненного и ограничений — в ПРОВЕРКИ.txt и машинном отчёте.

Разумное продолжение

Первый следующий эксперимент — тот же ledger release на личном kind/kubeadm по соседнему тому: последовательно установить, нарушить readiness, исправить, проверить test hook и rollback. Только после этих наблюдений стоит добавлять operator, CRD, admission policies или непростую БД. GitOps-controller позже может вызывать Helm render и иметь собственную историю применения; такая история не автоматически равна обычному release storage Helm. Это отдельная модель ownership и согласования состояния, а не дополнительный флаг текущего CLI.

Том XXIV · Справочник

Словарь · HelmПонятия и их связь с наблюдаемыми механизмами · 1775 слов

Словарь в боковой панели также ищет определения во всех остальных томах.

Helm

Клиентский инструмент получения Kubernetes-манифестов из пакетов и управления историей именованных релизов. Не является кластером, планировщиком или резервной копией приложения.

CLI

Command Line Interface — интерфейс командной строки. Оболочка передаёт процессу массив строк argv; затем CLI разбирает их согласно правилам конкретной версии.

API

Application Programming Interface — программный интерфейс. Kubernetes API принимает запросы над объектами; его успех отделён от последующего исполнения контроллеров.

Chart

Чарт — пакет Helm с метаданными, параметрами, шаблонами и при необходимости зависимостями. Один пакет может породить несколько независимых релизов.

Release

Релиз — именованное применение чарта с конфигурацией и историей ревизий в определённом пространстве имён и кластере.

Revision

Ревизия — номер действия в истории релиза Helm. Откат создаёт следующую ревизию, а не уменьшает номер.

Manifest

Манифест — текстовое описание объекта API. Сохранённый манифест Helm и текущее состояние объекта Kubernetes могут различаться.

Rendering

Рендеринг — исполнение шаблонов с данными и получение текста. Его успех не доказывает принятие API или работоспособность приложения.

Admission

Этап обработки запроса Kubernetes после установления личности и проверки полномочий. Admission controllers могут изменить допустимые части объекта или отклонить действие по политике; этот этап отделён от аутентификации, RBAC и последующей работы контроллеров workloads.

Reconciliation

Согласование состояния — повторная работа контроллера для приближения наблюдаемого состояния к желаемому. Helm не заменяет контроллер Deployment.

Namespace

Пространство имён Kubernetes ограничивает имена и область ряда объектов/прав. Само по себе не является полной изоляцией безопасности.

Kubeconfig

Файл описания кластеров, личностей и контекстов доступа. Может запускать доверенный credential plugin; обращаться с ним следует как с полномочиями.

Context

Контекст kubeconfig связывает кластер, личность и пространство имён по умолчанию. В Go templates context означает переданный текущий объект данных.

Dot

Точка в Go template — текущий объект вычисления. With и range меняют его, if сохраняет.

Root

Корень шаблона, первоначально связанный с $. Внутри include корнем становится явно переданный аргумент, который не обязан быть целым объектом Helm.

Values

Дерево параметров чарта после загрузки пользовательских входов и объединения со значениями по умолчанию. Не является текстом исходного YAML.

Coalescing

Объединение значений Helm с настройками чарта и дочерних пакетов. Отображения объединяются рекурсивно, скаляры и списки заменяются; null имеет смысл удаления ключа.

Map

Отображение ключей в значения. Значение по ключу и наличие самого ключа — разные свойства; для второго используют hasKey.

List

Упорядоченный список. Новый список values заменяет прежний целиком, не объединяется по Kubernetes name.

Scalar

Скаляр — одно простое значение: строка, число, логическое значение или null. Похожее написание строкового и числового скаляра не делает типы равными.

YAML

Текстовый формат отображений, списков и скаляров. Парсер получает структуру; YAML сам не исполняет Go template или shell.

JSON

Текстовый формат структурированных данных с явно различаемыми строками, числами, логическими значениями, массивами, объектами и null.

JSON Schema

Схема ограничений структуры и типов JSON-совместимых данных. В Helm проверяет итоговые values, но не доступную ёмкость узлов или существование образа.

Empty

Правило пустоты шаблонных функций: nil, false, ноль и пустые строки/коллекции могут считаться пустыми. Default способен заменить законный false.

Nil

Отсутствующее значение соответствующего типа Go. Доступ по цепочке через nil-родителя способен завершить исполнение шаблона до default.

Default

Значение по умолчанию; одноимённая функция выбирает запасной вариант при пустоте входа. Для логических значений безопаснее явные defaults в values и схема типов.

Required

Функция шаблона, отказывающая при пустом значении с сообщением. Не равна required JSON Schema, которое проверяет наличие свойства.

Fail

Явное завершение исполнения шаблона ошибкой контракта, например при несовместимых режимах credentials.create и existingSecret.

Pipeline

Конвейер выражений Go template. Результат слева передаётся последним аргументом следующей функции, а не по Unix pipe в другой процесс.

Scope

Область видимости переменной и текущего контекста. Переменная из тела range не становится автоматически доступной после end.

Define

Объявление именованного шаблона. Имена общие в загруженном дереве чартов, поэтому нужен устойчивый префикс.

Include

Функция Helm, возвращающая результат именованного шаблона как строку. Даже напечатанное false становится непустой строкой для if.

Template action

Вызов именованного шаблона, пишущий прямо в выходной поток. Отличается от include, результат которого можно передать функции.

Sprig

Библиотека вспомогательных функций шаблонов, значительная часть которой доступна в Helm. Не превращает template в произвольную Go-программу.

Dict

Создаваемое функцией dict отображение. Set и unset меняют его; при общей вложенной структуре нужна осознанная глубокая копия.

Deep copy

Глубокое копирование структуры, разрывающее совместное использование вложенных отображений перед мутацией.

ToYaml

Сериализация значения в строку YAML. После неё pipeline передаёт текст, а не исходное отображение.

Nindent

Добавление перевода строки и заданного отступа к каждой строке текста. Число пробелов определяется местом итогового YAML.

Whitespace trim

Удаление пробельных байтов около action через {{- и -}}. Может склеить две YAML-строки и изменить смысл результата.

LF

Line feed — байт перевода строки 0x0A. Конечный LF из set-file является частью значения, пока его явно не преобразовали.

Tpl

Исполнение строки как шаблона с переданным контекстом. Расширяет возможности автора values и ухудшает предсказуемость, если вход недоверенный.

Lookup

Функция чтения Kubernetes API при разрешённом взаимодействии с сервером. Результат зависит от состояния и полномочий; forbidden отличается от отсутствующего объекта.

Capabilities

Предоставляемая Helm модель версии Kubernetes и известных API. Локальные флаги моделируют её, но не устанавливают CRD или контроллер.

Post-renderer

Постобработчик готовых манифестов. В Helm 4 подключается как плагин и должен проверяться вместе с окончательным результатом.

SemVer

Semantic Versioning — соглашение major.minor.patch с дополнительными частями. Версия пакета и приложения имеют независимые контракты.

AppVersion

Информативная строка версии приложения в Chart.yaml. Не меняет image tag в шаблоне автоматически.

Subchart

Дочерний чарт с собственными параметрами и схемой, включаемый в общий релиз. Не получает произвольные параметры родителя.

Library chart

Пакет типа library с общими вспомогательными шаблонами без самостоятельных Kubernetes-манифестов.

Alias

Другое имя включённой зависимости, позволяющее иметь отдельное поддерево values для нескольких включений одного чарта.

Global values

Явно выделенное поддерево global, доступное нескольким чартам по соглашению. Не является глобальной переменной ОС или настройкой всего кластера.

Import-values

Перенос экспортированных или явно выбранных значений дочернего чарта в путь родителя до рендеринга. Не читает данные работающего приложения.

Chart.lock

Файл выбранного набора зависимостей и связанного дайджеста. Не является подписью каждого архива зависимости.

OCI

Open Container Initiative — семейство форматов/протоколов артефактов. Helm chart в OCI registry отличается от запускаемого контейнерного образа.

Tag

Тег — именованный указатель в реестре. Если политика допускает перезапись, одно имя может позднее обозначать другие байты.

Digest

Дайджест — идентификатор содержимого на основе хеша. Дайджест чарта и дайджест образа относятся к разным манифестам.

SHA-256

Криптографический хеш байтов в 256-битное значение. Проверка с доверенным ожиданием устанавливает целостность, но не сама по себе полномочия издателя.

Provenance

Сведения и проверяемая связь происхождения артефакта. Классическая подпись .prov связывает метаданные чарта и хеш архива с ключом OpenPGP.

Fingerprint

Отпечаток криптографического ключа. Для проверки подписи его доверенное получение отделено от скачивания произвольного ключа рядом с архивом.

OpenPGP

Формат криптографических ключей/подписей, используемый классической Helm provenance. Наличие подписи не доказывает безопасные privileges шаблонов.

TLS

Transport Layer Security — защита канала и проверка идентичности сервера согласно доверенным сертификатам. Отключение проверки не исправляет неизвестную причину отказа.

Dry-run

Пробный запуск без сохранения предусмотренных изменений. Точная граница зависит от команды и версии; Helm server mode не следует без проверки приравнивать к admission всех объектов.

SSA

Server-Side Apply — серверное применение с учётом владельцев полей. Конфликт управляющих полями отличается от проверки принадлежности объекта релизу Helm.

ManagedFields

Метаданные Kubernetes о менеджерах и управляемых полях. Не являются журналом бизнес-операций или копией данных.

Ownership Helm

Связь объекта с release name/namespace через согласованные labels и annotations. Не равна Kubernetes ownerReferences и не отменяет существующие данные.

Hook

Обработчик события Helm, обычно Job или Pod с аннотацией helm.sh/hook. Его внешний эффект не отменяется удалением самого Job.

Hook weight

Целочисленный вес порядка обработчиков: меньший выполняется раньше. Значимое требование порядка не оставляют случайной сортировке имён.

Hook delete policy

Правило удаления ресурса обработчика до повторного создания, после успеха или после ошибки. Не является откатом его внешних действий.

Readiness

Готовность экземпляра принимать трафик. Ошибка проверки исключает его из готовых конечных точек, но не обязательно перезапускает контейнер.

Liveness

Проверка жизнеспособности контейнера. Её отказ может вызвать перезапуск и поэтому отличается от временной неготовности внешней БД.

Probe

Проба Kubernetes — периодическая проверка контейнера. Path, порт, thresholds и смысл ответа должны соответствовать приложению.

Pod

Совместно планируемая единица контейнеров Kubernetes с общей сетью и рядом общих ресурсов. Не равна одному постоянному процессу.

Deployment

Контроллер желаемого набора Pod через ReplicaSet и обновления их шаблона. Не является самим приложением или резервной копией.

ReplicaSet

Контроллер числа Pod, подходящих по селектору. При обновлении Deployment новые и старые ReplicaSets могут сосуществовать.

Service

Стабильная сетевая точка Kubernetes, выбирающая готовые Pod по селектору и задающая порты. ContainerPort сам не запускает слушающий процесс.

EndpointSlice

API-объект набора конечных точек Service. Помогает отличить отсутствие готовых backend от ошибки самого HTTP-обработчика.

ConfigMap

Kubernetes-объект строковой/двоичной конфигурации. EnvFrom копирует данные при создании контейнера; старый процесс не перечитывает окружение от изменения объекта.

Secret

Объект конфиденциальных параметров Kubernetes. Base64 — кодирование; реальные гарантии требуют RBAC, защиты хранения и обращения с выводом.

RBAC

Role-Based Access Control — управление разрешениями через роли и привязки личностей. Для Helm нужны также полномочия хранения metadata и наблюдения готовности.

ServiceAccount

Личность приложения внутри Kubernetes. Её токен и kubeconfig клиента Helm относятся к разным доверительным границам.

Requests

Запрашиваемые ресурсы для планирования и ряда политик Kubernetes. Не равны фактическому расходу CPU/памяти.

Limits

Ограничения использования ресурсов. Память может привести к OOMKill, CPU quota — к ограничению времени исполнения.

Millicpu

Тысячная доля CPU. 50m означает 0.05 CPU; это другая единица, чем миллисекунды задержки.

Mi

Мебибайт — 2^20 байтов. Не равен десятичному мегабайту.

RSS

Resident Set Size — объём резидентной памяти процесса. Не равен только Go-куче или всем данным chart на диске.

OOMKill

Завершение контейнера при нарушении допустимого потребления памяти в соответствующей границе. Увеличение timeout Helm не устраняет причину.

PVC

PersistentVolumeClaim — запрос постоянного хранилища. Связывание требует подходящего PV или подготовленного динамического provisioner. Монтирование выполняет механизм выбранного типа тома; статический local PV нашего упражнения не требует установки CSI.

PV

PersistentVolume — ресурс предоставленного постоянного тома. ReclaimPolicy определяет судьбу тома после освобождения claim, отдельно от Helm keep.

RWO

ReadWriteOnce — режим доступа, обычно ограничивающий запись одним узлом. Не обещает ровно один Pod и не является механизмом репликации БД.

CSI

Container Storage Interface — интерфейс драйверов контейнерного хранилища. Подключение, монтирование и поддержка снимков зависят от драйвера.

CRD

CustomResourceDefinition — определение собственного Kubernetes API. Его удаление может затронуть все экземпляры ресурса нескольких релизов.

Rollback

Откат желаемых manifests выбранной ревизии через новое действие Helm. Не возвращает автоматически данные PVC, схему БД или внешние эффекты.

Idempotence

Идемпотентность — свойство повторного действия приводить к требуемому состоянию без лишнего эффекта. У произвольного migration Job её надо доказывать.

Drift

Дрейф — отличие фактического состояния от описанного. Get manifest Helm показывает сохранённое намерение, не обязательно текущий объект API.

Graceful shutdown

Штатное завершение: прекратить новую работу, отметить неготовность и дождаться активных запросов в заданном бюджете до выхода процесса.

RPO

Recovery Point Objective — допустимая потеря последних данных по времени. Определяется резервированием/согласованностью, а не наличием истории Helm.

RTO

Recovery Time Objective — допустимое время восстановления услуги, включая инструменты, права, образы, данные и прикладную проверку.

p99

Оценка 99-го процентиля измерений. Серия из десяти запусков недостаточна для устойчивого вывода о редком хвосте задержки.
