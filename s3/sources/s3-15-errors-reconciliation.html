Ошибка запроса и неизвестный исход записи

Проследим, в какой точке теряется знание о результате и почему повтор, проверка хеша и восстановление требуют разных решений.

Пять разных точек остановки

Рассмотрим один путь записи: программа проверила конфигурацию, прочитала источник, отправила запрос, сервер изменил состояние, клиент получил подтверждение. Остановка в каждой точке означает разное.

Если файл источника не открывается до отправки, helper знает, что этот S3-запрос ещё не начат. Если сервер вернул понятный отказ условия, клиент получил отрицательное решение этой попытки. Предыдущая попытка SDK могла уже сохранить объект и потерять ответ. Если соединение оборвалось после возможного принятия тела, результата может не быть у клиента, хотя состояние уже изменено на сервере.

Поэтому неизвестный исход означает отсутствие достаточного подтверждения, а не отдельную серверную команду «неизвестно». В receipt он называется unknown. Программа не имеет права заменить его удобным предположением об отсутствии записи.

Завершение клиентского ожидания также не является командой отката. Истечение deadline прекращает предусмотренное ожидание и передачу на стороне клиента. Оно не доказывает, что сервер вернул прежнее состояние. Отдельная операция очистки тоже может завершиться ошибкой.

Что означает идемпотентность

Идемпотентность в HTTP описывает ожидаемый эффект повторения одинакового запроса на состояние адресуемого ресурса. Это не обещание одинакового количества записей журнала, сетевых байтов или сохранённых версий.

Допустим, приложение дважды записало одни байты под один ключ без условия. Текущее содержимое может оказаться тем же самым. Но при включённом versioning сервер способен сохранить несколько версий. Плата за операции и история тоже не обязаны совпасть с однократным вызовом.

Таким образом, нужно различать три вопроса: совпадает ли текущее содержимое, сколько версий появилось и сколько раз приложение считает выполненной свою бизнес-операцию. Ответ на первый не определяет два остальных.

В helper v1 запись требует либо create-only, либо If-Match. Удаление условия после ошибки изменило бы смысл операции. Дополнительный внешний цикл повторов не включён по умолчанию поверх retry SDK.

Уникальное имя операции помогает наблюдать, но не создаёт exactly-once

Operation ID — случайный идентификатор одной прикладной попытки, выбранный клиентом до отправки. Он отличается от request ID, который сервер может выдать для конкретного сетевого запроса. В пределах внутренних повторов SDK operation ID остаётся тем же, а серверные request ID могут различаться.

В исходниках helper выбран 128-битный случайный идентификатор в шестнадцатеричной записи. PUT передаёт его как метаданные operation-id; в HTTP это соответствует полю семейства x-amz-meta-*. Подписывание должно включать необходимые передаваемые поля. Receipt сохраняет operation ID и ожидаемую характеристику исходного тела.

После тайм-аута программа может искать наблюдаемое состояние с этим идентификатором. Но метаданные не являются неотчуждаемым свидетельством авторства: уполномоченная программа способна скопировать их вместе с объектом. А другой писатель может уже заменить наше состояние.

Если процесс погиб до сохранения receipt, идентификатор, находившийся только в памяти, может быть утрачен. В v1 нет durable intent — постоянной записи намерения до dispatch. Dispatch здесь означает передачу HTTP-запроса клиенту через Do со стороны SDK; attempts считает эти вызовы, а не все передачи Transport. Поэтому клиент не обещает exactly-once, то есть ровно одно выполнение прикладной операции при любых повторах и отказах.

Как проверять неизвестный результат

Reconciliation, согласование наблюдаемого результата с намерением, начинается с сохранённых входов: цель, ключ, operation ID, ожидаемые размер и хеш. Оно не начинается с немедленного удаления объекта или снятия условия записи.

Если HEAD вернул идентификатор обычной сохранённой версии, успешный GET этой версии позволяет получить её тело вместе с её метаданными. Для AWS это относится к сохранённой data version с ID, отличным от буквальной строки null: новый PUT не заменяет её тело под тем же ID. Версию всё ещё могут удалить, а доступ к ней — запретить. Для совместимого сервера эти свойства проверяют по выбранной реализации.

В AWS при suspended versioning новый PUT получает ID null. Следующий PUT того же ключа может заменить эту null-version, сохранив тот же ID. Поэтому HEAD с version ID null и последующий GET с versionId=null могут прочитать разные состояния. Такой ID не фиксирует неизменную редакцию.

В receipt отсутствие полученного значения и буквальный ID представляются по-разному:

{"version_id": null}
{"version_id": "null"}

Первая запись содержит JSON null, вторая — строку сервера. Строку "null" клиент не преобразует в отсутствие значения. CLI продолжает принимать её как version ID.

Совпадение operation ID и ожидаемых байтов в выбранной версии позволяет сказать: «наблюдалась запись с этими признаками». Оно ещё не доказывает единственность версии или отсутствие других эффектов. Несколько версий с тем же operation ID могут оказаться следствием повторных отправок.

Если текущая версия имеет другой operation ID, первоначальный PUT всё равно мог ранее завершиться, а затем быть перезаписан. Если GET вернул те же байты без подходящей связи с операцией, это может быть запись другого клиента. Один хеш содержимого не устанавливает авторство.

Поиск истории версий не входит в CLI v1. На этом этапе helper должен честно оставить результат неизвестным и остановить зависимые изменения. Будущий инструмент исследования истории добавляется как отдельная проверенная возможность, а не выдумывается в примере команд.

Почему старый ETag не является номером транзакции

ETag — непрозрачная метка сервера. Она используется как validator, значение для проверки предусмотренного условия о состоянии объекта. Клиент хранит его непрозрачно, включая кавычки, и не предполагает, что это всегда MD5 или уникальный номер версии.

Два писателя могут прочитать один ETag. Первый условно меняет объект. Условие второго после этого может быть отвергнуто. Это предотвращает слепую замену замеченного чужого изменения, но не создаёт транзакции над другими ключами.

Есть и случай ABA: содержимое A сменилось на B, а затем снова стало A. Validator может повториться. Сравнение одного ETag тогда не обязано обнаружить промежуточную историю. Если приложению нужна идентичность сохранённой версии, оно использует предусмотренный сервером version ID.

После потерянного подтверждения create-only последующий ответ 412 может означать и нашу ранее завершённую запись, и существование чужой записи. После If-Match отказ может возникнуть после изменения нами или другим писателем. Ни один из этих ответов не разрешает без анализа повторить запрос уже без условия.

Чтение заканчивается после тела

GET может вернуть заголовки и объект потока раньше, чем получены все байты. Контекст запроса должен оставаться действующим до окончания чтения тела. Ветка, которая сразу отменяет его после возврата GetObject, обрывает собственную загрузку.

Ограничитель io.LimitReader(N) предоставляет не больше N байтов. Успешное копирование этих N байтов само по себе не отличает объект ровно такого размера от начала более длинного объекта. Поэтому после достижения предела нужен контроль окончания.

N — верхний предел, не ожидаемый размер. Клиент ограничивает чтение тела N+1 байтами: дополнительный байт обнаруживает превышение N и не публикуется. Если известная ContentLength превышает N, он отказывает раньше. При принятии сравниваются фактическая длина с известной ContentLength, завершение Body без ошибки и результат проверки checksum SDK. Body представляет тело ответа, а не всё соединение; при Content-Length: 14 HTTP-клиент сам ограничивает его четырнадцатью байтами.

EOF, End of File, сообщает о завершении потока. Go Read может одновременно вернуть n > 0 и EOF: сначала учитывают n байтов, затем конец. Получить 13 байтов с EOF при max-bytes=14 допустимо по пределу, но для нашей fixture, исходного тестового набора hello-v1, это неверные размер и хеш. Ошибка checksum при полном чтении остаётся ошибкой и не превращается в принятую копию.

Checksum, контрольная сумма, помогает сверить содержимое с ожидаемым значением. Локально вычисленный хеш без доверенного ожидаемого значения лишь описывает полученные байты. Серверная проверка SDK и сверка с собственным исходным тестовым набором — разные подтверждения; receipt не должен смешивать их.

Когда появляется итоговый файл

Запись идёт во временный файл в том же приватном каталоге, где будет итоговое имя. Только после успешного чтения, необходимых проверок, синхронизации и закрытия создаётся итоговое имя. Предыдущая принятая копия не используется как промежуточный output.

На выбранной Linux-файловой системе публикация выполняется созданием hardlink в новое имя. Hardlink, жёсткая ссылка, — дополнительное имя того же файла. Создание ссылки не заменяет уже существующее имя. Предварительная проверка существования нужна для ранней понятной ошибки, но окончательную защиту обеспечивает сама операция публикации.

Сбой до публикации оставляет итоговое имя отсутствующим, а временный файл подлежит адресной очистке. Сбой синхронизации каталога после публикации — другой случай: полное содержимое уже может быть видно под итоговым именем, но подтверждение локальной устойчивости не получено. Ненулевой exit code поэтому не всегда означает отсутствие файла.

После crash может остаться собственный файл с окончанием .part. Он не становится принятой копией от смены расширения. Его судьбу определяют по конкретной операции и проверкам; автоматическое удаление всех похожих имён способно уничтожить другой незавершённый опыт.

Как действовать по коду завершения

Код завершения описывает причину остановки, а outcome — что подтверждено об операции. Поэтому их читают вместе.

КодПричинаЧто проверить
0Операция и требуемая локальная стадия завершены.outcome=confirmed, размер, хеш и выбранная версия.
2Ошибка грамматики, конфигурации или профиля до отправки.Исправить входы; не угадывать другой endpoint.
3Последний доступный явный отказ службы.Статус и service_code; для PUT после возможной отправки outcome всё равно unknown.
4Сеть, deadline, отмена либо неподтверждённое завершение вызова.Для возможного PUT не считать отсутствие ответа отсутствием записи.
5Локальный ввод/вывод, чтение Body, checksum, публикация или вывод receipt.Стадию: до отправки, после неё или после появления итогового имени.

Ошибка открытия или предварительного хеширования source до отправки означает rejected. Ошибка чтения source после возможной отправки PUT оставляет unknown, даже при коде 5. У подтверждённого PUT сбой последующего закрытия source даёт код 5 при outcome=confirmed. Сбой записи самой квитанции тоже не отменяет уже выполненную операцию.

Например, попытка 1 записала объект и потеряла ответ, повтор SDK получил 412. Квитанция может содержать http_status=412, exit code=3 и outcome=unknown. Счётчик Do не раскрывает все внутренние переподключения Transport, поэтому mapper не делает из последнего отказа доказательство rejected всей записи. Внешний повтор не добавляют, условие не снимают.

Общий deadline конечен, но он не является универсальным способом принудительно прервать любую файловую операцию ОС. Учебный источник и output находятся на собственной локальной файловой системе. Поведение сетевого диска, зависшего устройства и произвольного блокирующего io.Writer не обещается этим малым клиентом.

Приёмочный тест должен проверить и результат, и границу знания. «Получен timeout и helper сохранил unknown» — полезный результат. «Timeout доказывает отсутствие записи» — уже неверное заключение. Именно это различие позволяет продолжать опыт без случайного уничтожения данных.

Что сохранить перед следующим действием

Сохраните квитанцию, ожидаемый хеш и длину, ключ и известный version ID, состояние versioning и время своего наблюдения. При unknown не удаляйте объект «для чистоты опыта»: это может удалить единственный след принятой записи или чужую новую current version. Проверка конкретной обычной версии и её operation-id полезнее повторного безусловного PUT. CLI v1 не ищет историю; оператор использует отдельное принятое средство и правила главы 09.

Путь output и все его родительские каталоги должны оставаться под контролем учебного пользователя. No-clobber защищает существующее конечное имя, но этот малый Linux-клиент не защищает каталог от конкурентной подмены чужим пользователем. После сбоя fsync каталога проверьте уже возможное конечное имя и его полные байты; не перезапускайте GET поверх него.

Повторяемые сценарии главы 16 отделяют состояние сервера в модели от знания клиента. Так видно, почему одинаковый timeout совместим и с принятой записью, и с её отсутствием.

HTTP idempotence; S3 conditional writes; mutable null-version; Go Reader и EOF. Локальная публикация — выбранная процедура helper, не свойство сервера S3.
