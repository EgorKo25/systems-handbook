Что хранится под именем объекта

Приложение хранит два отчёта под одним именем. Какие данные нужны, чтобы получить именно первую редакцию?

Какую задачу решает объектное хранение

Служба принимает байты отчёта и выбранное приложением имя. Позднее другая машина посылает запрос с тем же именем и получает байты обратно. Чтобы говорить о двух редакциях одного отчёта, отделим его имя от хранимого содержимого.

Наш клиент — программа, которая отправляет запрос. Сервер проверяет и выполняет его. При чтении он использует три входа: адрес службы, имя корзины и ключ внутри неё.

Из чего складывается обращение к объекту

У отчёта сохраним тело — байты файла — и тип содержимого text/plain. При чтении клиент получит тело и сведения о нём. Серверу не требуется разбирать строки отчёта, чтобы сохранить их и вернуть.

Поместим отчёт в корзину study-s3. До записи уполномоченный пользователь создаёт её и настраивает доступ. Другое приложение сможет прочитать отчёт, только если выберет эту же корзину на нужном сервере и пройдёт проверку прав. Имя study-s3 в примере не означает, что оно свободно в AWS.

Записывающая программа выбрала ключ reports/2026/november.txt. Две разные корзины могут содержать этот ключ с разными отчётами. Поэтому к строке ключа клиент добавляет адрес службы и имя корзины.

Приложение может передать метаданные: например, тип text/plain и собственное поле revision=2. Поле поможет читателю выбрать обработчик отчёта. Но если приложение отправило старое тело с новой меткой, сервер не обязан искать в тексте вторую редакцию: эти две части должен согласовать автор записи.

При включённом хранении версий повторная запись под тем же ключом оставит в истории отдельную редакцию. AWS выдаёт её идентификатор в ответе. Клиент сохраняет эту строку целиком; восстановить по ней время записи, порядковый номер или хеш содержимого нельзя.

Для списка годовых отчётов приложение может отобрать ключи с общим началом reports/2026/. В результат попадут reports/2026/a.txt и reports/2026/b.txt. Для базовой модели корзины общего назначения такой запрос отбирает строки по префиксу; существование отдельного каталога reports ему не требуется.

Почему косая черта не создаёт файловую систему

В файловой системе каталог участвует в разрешении пути и обычно является самостоятельным объектом. Файловая программа может открыть файл, переместить имя или заменить часть содержимого через операции своей файловой системы. Их атомарность и права зависят от конкретной системы и способа обращения к ней.

В объектном интерфейсе строка reports/2026/a.txt целиком служит ключом. Косые черты удобны людям и операциям отбора по префиксу. Они не превращают сервер в POSIX-файловую систему. Операция переименования POSIX не появляется у S3 от похожего изображения дерева в веб-консоли.

Если программа реализует перенос объекта как «скопировать под новым ключом, затем удалить старый», она выполняет несколько операций. Между ними могут появиться два имени. После отказа может сохраниться только часть задуманного процесса. Читатели другого ключа не обязаны ждать окончания всего переноса. Поэтому прикладное действие «переименовать отчёт» сначала нужно определить через допустимые промежуточные состояния.

Если программе нужен диск для собственной файловой системы, она обращается к блочному устройству: задаёт номер блока и читает или пишет его байты. В S3 служба сама выбирает, где лежат данные; приложение обращается к ним по имени объекта.

Один сохраняемый пример

Будем развивать набор object-lab/v1. В выбранной ASCII-записи латинские буквы, цифры, дефис и пробел занимают по одному байту. Завершим строку байтом перевода строки 0A (LF). Первая редакция содержит тринадцать печатных байтов и LF, всего четырнадцать байтов: object-lab v1 и один завершающий перевод строки. Её ключ — lessons/2026-11/hello +%.txt. Пробел, плюс и процент выбраны намеренно: позднее мы увидим, как строковое имя превращается в байты сетевого адреса.

Вторая редакция также содержит четырнадцать байтов, но заканчивается строкой v2. Наличие двух локальных редакций ещё не означает, что сервер хранит обе. Это определяется режимом версий и результатами операций.

Допустим, в корзине включено версионирование и обе записи успешно подтверждены: первой сервер присвоил условный идентификатор V1, второй — V2. Обычное чтение по ключу выберет текущую редакцию V2. Чтобы запросить первую, клиент передаст тот же ключ и идентификатор V1; затем сравнит полученные байты с сохранённым исходником. Имена V1 и V2 здесь придуманы для примера: реальные идентификаторы нельзя вычислять или упорядочивать по их написанию.

PutObject — операция S3 для записи объекта. В AWS успешный обычный PutObject сохраняет объект целиком; частично добавленный объект не является результатом успешной операции. Однако потерянный ответ создаёт другую ситуацию: клиент может не знать, была ли запись завершена. «Мы не получили подтверждение» и «сервер ничего не изменил» — разные утверждения.

История и текущее имя

При включённом S3 Versioning новая запись того же ключа создаёт новую версию. Предыдущая остаётся в истории. Обычное удаление без выбора версии добавляет delete marker — маркер удаления, который становится текущим состоянием имени. Чтение текущего объекта тогда получает ответ об отсутствии, хотя прежние версии могут сохраняться.

Удаление выбранной версии — отдельная операция с отдельными правами и последствиями. Оно может окончательно убрать именно эту версию. Поэтому количество видимых текущих ключей не показывает весь занятый объём, а отсутствие ключа в обычном списке не доказывает отсутствие восстанавливаемых данных.

Наш журнал опыта будет связывать ключ, идентификатор версии и проверенные байты. Восстановление будем принимать чтением на отдельной цели. Само наличие нескольких версий или второй корзины ещё не подтверждает, что приложение сумеет получить нужное содержимое с имеющимися правами и ключами шифрования.

Исходные байты и публикация набора

6f 62 6a 65 63 74 2d 6c 61 62 20 76 31 0a
o  b  j  e  c  t  -  l  a  b     v  1  LF

Последний 0A входит в объект; имя локального файла — нет. Во второй редакции меняется только 31 на 32. Для первого тела SHA-256 в шестнадцатеричной записи равен 874160ebe2d9a6a82abdec1966f3be5be4e0db5d575d4d00953c66baf6e30897. Если полученные байты отличаются, совпадение длины ещё не подтвердит сохранность. Можно сравнить файл с исходником побайтно либо вычислить его SHA-256 и сравнить с доверенным значением выше. Совпадение хешей даёт сильное свидетельство совпадения, но не математическое доказательство: разные входы теоретически могут иметь один хеш. Ожидаемый хеш необходимо получать из доверенного источника: подмена и файла, и ожидаемого значения таким сравнением не обнаруживается.

Сильная согласованность AWS S3 для чтения и получения списка объектов после успешных объектных записей не создаёт транзакцию для двух ключей report и index. Если сначала записать report, а затем index, сбой между запросами оставит новый отчёт со старым индексом. Вариант приложения — неизменяемые тела под разными ключами и маленький manifest, перечень выбранных версий, который условно меняется последним. Пока возможны читатели старого manifest, его тела ещё нельзя удалять. Алгоритм публикации набора и последующая очистка принадлежат приложению.
