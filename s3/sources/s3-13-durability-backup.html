Что останется после ошибки, удаления и потери доступа

Объект читается сразу после PUT, но это ещё не план восстановления. Проследим судьбу четырнадцати байтов, если приложение испортит текущую версию, оператор удалит историю или второй экземпляр данных ещё не успеет появиться.

Три разных свойства хранения

Согласованность определяет, какое состояние видит чтение после записи. Сохранность, durability, относится к удержанию принятых данных при отказах. Доступность, availability, относится к возможности выполнить обращение в нужный момент. Старую версию можно сохранить, но временно не иметь к ней доступа из-за сети или отозванных прав. Немедленно видимый ошибочный PUT может быть одновременно согласованным и совершенно непригодным приложению.

Для AWS S3 Standard опубликованы проектные годовые показатели сохранности 99.999999999% и доступности 99.99%. AWS описывает избыточное размещение ряда классов хранения как минимум в трёх Availability Zones — зонах доступности региона. One Zone-IA устроен иначе. Эти сведения относятся к названным классам облачной службы; они не описывают количество копий у произвольного S3-compatible сервера. См. data protection in Amazon S3.

Из процента нельзя вывести, что конкретный DELETE будет отменён, что ошибки приложения невозможны или что простой всегда короче определённого интервала. Успешное удаление — разрешённое изменение состояния, а не потеря устройства. Гарантии службы не восстанавливают версии, которые владелец сам окончательно удалил. Для MinIO и RGW отдельно выбирают топологию, диски, кворумы, резервирование и процедуру проверки восстановления.

Сначала определим, что надо восстановить

В 12:00 приложение успешно записало hello-v1: 14 байтов, SHA-256 874160ebe2d9a6a82abdec1966f3be5be4e0db5d575d4d00953c66baf6e30897, metadata operation-id=op-a. В 12:03 ошибочная версия стала текущей. Технически обе записи могут быть успешны. При включённом versioning исходная редакция v1 остаётся кандидатом на восстановление, если её не удалили, не истёк срок хранения и сохранились права чтения.

Рабочая ведомость восстановления, manifest, фиксирует корзину, ключ, обычный сохранённый version ID, размер, собственный хеш тела, нужные приложению metadata и связь с набором данных. Добавляют сведения о шифровании и о том, где получить доступ к необходимому ключу; сами секретные ключи в ведомость не записывают. Если отчёт состоит из нескольких объектов, ведомость указывает выбранную версию каждого. Один список текущих ключей такой снимок не задаёт.

Вторая копия должна находиться там, где ошибка исходного приложения не может уничтожить её теми же полномочиями. Это может быть отдельная корзина под другой административной учёткой или отдельный аккаунт. Название backup/ в том же доступном приложению префиксе не создаёт такого разделения. Необходимые данные и доступ к ключам проверяются независимо от исходной службы.

Копирование ещё должно закончиться

Репликация — поддерживаемое службой копирование по правилу в другую корзину. В AWS live replication работает асинхронно: успешный исходный PUT и готовность реплики — разные события. Правило для новых записей не означает автоматического переноса всей старой истории; для существующих объектов предусмотрена отдельная Batch Replication. См. replication.

Нельзя также заменять всё слово «удаление» одной стрелкой к реплике. Для современных правил с Filter передача delete markers настраивается отдельно; окончательное удаление исходной версии по её ID не удаляет соответствующую реплику. Конфигурации корзины, включая Lifecycle, не копируются просто как тела объектов. Настройки источника и приёмника проверяют отдельно по правилам того, что реплицируется.

Для нашего ручного опыта независимая копия считается проверенной только после GET из приёмника, сверки 14 байтов, собственного SHA-256 и нужных метаданных. Если приёмник выдаёт иной version ID, его сохраняют отдельно; совпадение ID нельзя требовать от произвольной процедуры копирования. Ошибка при копировании не разрешает пометить строку ведомости как готовую. Helper v1 не выполняет репликацию и не перечисляет историю: это процедура оператора с принятым для цели инструментом.

Пусть подтверждённая копия обновляется каждые десять минут и каждая партия завершается за две минуты. При успешном расписании исходная запись сразу после начала партии может не попасть в неё, попасть в следующую и стать проверенной до двенадцати минут спустя. Это расчёт для выбранного расписания, без учёта пропущенных запусков, а не измеренная задержка AWS. Ошибка партии должна увеличивать наблюдаемый возраст последней готовой копии, а не оставлять зелёный индикатор «job запущен».

Не дать уборке уничтожить нужную версию

Lifecycle — правила службы для переходов между классами и удаления по условиям возраста. В Enabled-корзине обычное expiration текущей data version добавляет delete marker; удаление noncurrent versions задаётся отдельно и может окончательно уничтожить историю. В Suspended-корзине null-version требует особой осторожности: её замена не создаёт новую неизменную редакцию. Правила действуют и на уже существующие объекты, подходящие по условиям. См. expiration.

Практический расчёт начинает не с «храним неделю», а с максимального времени обнаружения ошибки. Если ошибку замечают через девять дней, семидневная история не закрывает эту задачу. К сроку добавляют время расследования и восстановления, а правила noncurrent expiration проверяют на конкретных версиях. Автоматическое удаление незавершённых multipart uploads решает другую задачу и не заменяет retention объектов.

Object Lock защищает указанную версию от предусмотренных удаления и перезаписи в течение retention period или legal hold. Retention period задаёт срок, legal hold удерживает версию до явного снятия. Функция требует Enabled versioning; защищённая версия не запрещает создание новой версии или delete marker над ней. В governance есть специальный путь обхода уполномоченным субъектом; compliance ограничивает изменение срока и удаление строже. Это разные режимы, их нельзя свести к одному флагу «backup защищён». См. Object Lock.

Учебный опыт не включает включение необратимых настроек retention в чужом аккаунте. Для своей системы оператор документирует срок, режим, круг субъектов, способ чтения защищённой версии и тест восстановления. Наличие lock не исправляет изначально неверные байты. Ведомость с хешем нужна и для защищённых версий.

Восстановление заканчивается работой приложения

RPO, recovery point objective, — допустимая потеря свежести данных при восстановлении. RTO, recovery time objective, — допустимое время восстановления работы. В расписании выше расчётный возраст проверенной копии — до двенадцати минут при всех успешных запусках. Это ещё не RTO: нужно получить доступ, выбрать набор версий, прочитать тела, проверить хеши и подключить их к программе.

Разберём упражнение для hello-v1. Выбираем сохранённую обычную версию из ведомости, скачиваем её в новое имя, проверяем длину и SHA-256. Если приложение ожидает current под прежним ключом, оператор отдельно выполняет разрешённую запись проверенных байтов с выбранным условием. Новая current version не становится по ID старой v1. Затем приложение действительно открывает восстановленный отчёт. Проверка одного HEAD не проверяет расшифровку и чтение всех байтов.

Время замеряют от объявленного начала восстановления до успешной прикладной проверки. В журнал включают неудачные запросы, восстановление доступа и ожидание доступности архивного класса. Показатель «скачивание заняло секунду» не заменяет время всей процедуры. Исходный объект не удаляют ради демонстрации, пока независимая копия не прошла проверку и ответственность за опыт не определена.

Для собственного стенда повторяют тот же вопрос: какая копия переживёт выбранный отказ и кто сможет её прочитать. Ответ дают принятая топология и проведённый restore-test; слово S3 в названии API не определяет ни срок хранения, ни число устройств, ни резервные копии.
