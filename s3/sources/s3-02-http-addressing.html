Как имя объекта становится сетевым запросом

До загрузки объекта разберём адрес, защищённое соединение, заголовки и ответ: именно эти части затем участвуют в подписи и диагностике.

Запрос и ответ

HTTP, Hypertext Transfer Protocol, — протокол обмена запросами и ответами. Клиент выбирает действие и адрес ресурса, отправляет дополнительные поля и при необходимости тело. Сервер возвращает код результата, поля ответа и иногда тело ответа.

Метод — обозначение действия в запросе. В S3 метод PUT используется для записи, GET — для получения представления объекта, HEAD — для получения сведений без тела объекта, DELETE — для удаления по правилам выбранной операции. Список объектов получается отдельной операцией интерфейса; это не чтение файлового каталога.

Заголовок — именованное поле сообщения. Например, Content-Type сообщает тип передаваемого содержимого, а Content-Length — предусмотренную длину тела в байтах. Некоторые заголовки задают условие выполнения, другие участвуют в аутентификации. Значение поля и название поля — разные части: регистр букв в названии заголовка не следует переносить на значение.

Код состояния — число в ответе, например 200, 403 или 412. Он помогает выбрать дальнейшую ветку программы, но его недостаточно для полного разбора S3-операции. Клиент должен также понимать формат ответа и код ошибки службы. CompleteMultipartUpload, сборка ранее загруженных частей, может начать ответ HTTP 200, а затем сообщить ошибку в XML-теле; последовательность разобрана в главе multipart.

Удобно читать обмен в двух направлениях. Сначала: «Какие байты и условия отправил клиент?» Затем: «Что именно подтвердил сервер и до какого места клиент прочитал ответ?» Успех установления соединения, получение заголовков и получение всего объекта — разные события.

SDK, Software Development Kit, — библиотеки для вызова программного интерфейса. AWS SDK for Go v2 строит HTTP-запрос, подписывает его и разбирает ответ. Адрес и профиль нашей программы задаются явно.

Из чего состоит адрес

URI, Uniform Resource Identifier, — запись идентификатора ресурса. Для наших сетевых обращений удобно выделять схему, имя узла и порт, путь и строку параметров. URL является используемым здесь адресом обращения к ресурсу.

В записи https://storage.example.test:9443/study-s3/report.txt?versionId=v1 схема — https, узел — storage.example.test, порт — 9443, путь — /study-s3/report.txt, параметр — versionId=v1. Это учебный разбор адреса; он не утверждает существование такого сервера.

Endpoint, или конечная точка, — выбранный адрес службы. DNS, Domain Name System, — система разрешения доменных имён, через которую клиент обычно получает сетевые адреса узла. Успешное разрешение имени ещё не проверяет ни доступность порта, ни сертификат, ни права к корзине.

Region, или регион, — область размещения и обслуживания ресурса в модели провайдера. В AWS регион участвует также в выборе точки обращения и области подписи. У совместимого сервера строка региона может иметь другое эксплуатационное значение. Подставлять произвольное значение только потому, что SDK требует строку, нельзя: нужно согласовать его с конфигурацией конкретной цели.

Два способа указать корзину

При path-style, адресации через путь, корзина находится в начале пути: https://s3.us-west-2.amazonaws.com/study-s3/report.txt. При virtual-hosted style, адресации через имя узла, корзина входит в имя: https://study-s3.s3.us-west-2.amazonaws.com/report.txt.

Это меняет не только внешний вид строки. Во втором случае клиент разрешает другое доменное имя и проверяет сертификат для этого имени. Подпись также связывается с другим значением узла и другим путём. После вычисления подписи переставить корзину между ними уже нельзя.

Документация AWS на дату проверки описывает оба способа для корзин общего назначения. Это не универсальное правило для всех типов корзин: например, directory buckets требуют предусмотренных для них конечных точек и не поддерживают path-style. Данный том не использует их как базовый учебный профиль.

Для собственного сервера virtual-hosted style требует соответствующего разрешения имён и TLS-конфигурации. Одного параметра SDK недостаточно, чтобы имя study-s3.storage.example.test появилось в DNS или в сертификате. В лабораториях MinIO и RGW способ адресации задаётся явно после установки самого сервера.

Что защищает HTTPS

TLS, Transport Layer Security, — протокол защиты транспортного соединения. При обычном обращении HTTPS клиент проверяет личность сервера по сертификату и доверенной цепочке, а затем защищает передаваемые данные от чтения и изменения в пути.

Сертификат связывает удостоверяемое имя с открытым ключом. Соответствующий закрытый ключ сервер хранит у себя. В полном сертификатном рукопожатии TLS 1.3 сервер подтверждает владение им подписью CertificateVerify. Клиент проверяет имя и доверенную цепочку. Удостоверяющий центр, CA, участвует в цепочке доверия. У личного учебного сервера может быть собственный CA, который нужно явно передать клиенту. Выключение проверки сертификата не является настройкой доверия.

TLS не решает, имеет ли приложение право перезаписать отчёт. Эту проверку выполняет объектная служба по своей модели доступа. И наоборот: корректная подпись S3-запроса не скрывает его тело от наблюдателя незашифрованного соединения. Для удалённых целей наш клиент требует HTTPS; незашифрованный транспорт допускается только как явно выбранное исключение на loopback учебного стенда.

Ключ — это данные, а не готовая строка URL

Вернёмся к ключу lessons/2026-11/hello +%.txt. В адресе байты пробела, плюса и процента должны быть представлены по правилам кодирования. Для рассматриваемого пути получится окончание hello%20%2B%25.txt.

Запись %20 в таком адресе представляет байт пробела. Но если исходный ключ содержит три буквальных символа %20, процент нужно закодировать ещё как данные: получится %2520. Поэтому контракт нашего клиента принимает исходный ключ и поручает построение запроса SDK. Пользователь не должен предварительно «подготавливать URL» в аргументе ключа.

Аналогично, ключи a/b и a%2Fb различаются. У второго в имени присутствуют процент, цифра и буква. Кодирование их пути нельзя заменять общим исправлением строк или повторным декодированием.

У S3 есть ещё существенная граница: путь объекта не нормализуется как обычный файловый путь. Ключ a//b не следует превращать в a/b. Вызов функции очистки пути способен обратиться к другому имени ещё до того, как начнётся проверка подписи.

Почему перенаправление требует внимания

Перенаправление — ответ, предлагающий обратиться по другому адресу. Например, первоначальная точка обращения может не соответствовать региону корзины. Но подпись уже связана с методом, адресуемым ресурсом и выбранными полями запроса. Нельзя считать, что перенос старого заголовка аутентификации на произвольный новый узел сохранит смысл операции.

Для AWS клиент получает регион и endpoint из описания выбранной цели; SDK применяет к ним правила адресации корзины. Для MinIO и RGW он получает разные явные endpoints. В учебном HTTP-клиенте автоматический переход по HTTP-перенаправлению запрещён; такой ответ становится наблюдаемым результатом. Исправление региона или адреса происходит до нового подписывания, а не подменой уже отправленного запроса.

Порядок соединения и чтения

DNS возвращает IP-адрес по имени; TTL задаёт срок кэширования DNS-записи. TCP, протокол упорядоченной передачи потока байтов, устанавливает соединение с портом, выбирающим службу узла. Затем TLS согласует защиту и проверяет сервер. После этого передаются HTTP-поля и тело. Ошибка DNS не является отказом S3 в доступе; ошибка сертификата не является HTTP 403.

127.0.0.1 — loopback сетевого окружения самого клиента. Если RGW работает в другой VM, это не его адрес. Для HTTPS по IP сертификат должен удостоверять этот IP, а не только постороннее доменное имя. Добавление CA не выключает проверку имени.

В HTTP/1.1 начальная строка и заголовки заканчиваются CRLF, байтами 0D 0A. Пустая строка отделяет их от тела. Наше тело имеет собственный LF 0A; он входит в Content-Length: 14. HTTP/2 использует фреймы и не передаёт заголовки в таком текстовом виде. Канонические строки SigV4 разделяются LF по отдельным правилам: менять ради них CRLF сетевого сообщения нельзя.

GET предоставляет поток тела; получение заголовков ещё не завершает получение объекта. HEAD тела объекта не передаёт, хотя Content-Length описывает его размер. Подробный путь до принятого файла находится в главе операций.
