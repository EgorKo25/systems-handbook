Проверка байтов: длина, checksum, ETag и подпись

Разберём четыре разных числа, которые могут встретиться рядом с одним объектом, и проверим, какие из них действительно сопоставимы.

Что именно сравнивают

SigV4 — механизм подписи выбранных частей запроса. Его полный расчёт будет в главе 06; здесь отделим характеристику тела от подписи запроса.

Checksum — вычисляемая характеристика последовательности байтов для обнаружения повреждения. Алгоритм принимает тело, а результат имеет определённый размер. SHA-256 выдаёт 32 байта, CRC32 — четыре. Равенство размера файла не проверяет его содержимое: тело из четырнадцати нулей и наша fixture имеют одинаковую длину. Хеш полученной копии становится проверкой только при сравнении с ожидаемым значением из доверенного источника.

ETag — выданная сервером непрозрачная метка для операций над состоянием объекта. Version ID — идентификатор сохранённой версии. Ни один из них не следует безусловно интерпретировать как SHA-256. В некоторых режимах single-part загрузки ETag связан с MD5; multipart, шифрование и реализация сервера меняют допустимые выводы. Программа хранит ETag вместе с кавычками и использует как предусмотренный validator, значение условия.

32 байта и две записи одного SHA-256

Хеш hello-v1 в hex, шестнадцатеричной записи, занимает 64 ASCII-символа: каждый байт представлен двумя цифрами. Base64 — другое текстовое кодирование тех же 32 байтов, по 6 бит на символ, с завершающим заполнением. Здесь это 44 символа. Кодирование хеша не меняет алгоритм и не хеширует тело заново.

body length: 14
SHA-256 hex:
874160ebe2d9a6a82abdec1966f3be5be4e0db5d575d4d00953c66baf6e30897
SHA-256 Base64:
h0Fg6+LZpqgqvewZZvO+W+Tg211XXU0AlTxmuvbjCJc=

Для payload hash SigV4 выбран hex. Для поля S3 ChecksumSHA256 выбран Base64 бинарного результата хеширования. Ошибка «Base64 от 64 печатных hex-символов» даёт совершенно другое значение. Кавычки ETag не являются Base64-обрамлением. В квитанции checksum хранится вместе с algorithm, encoding и scope: без этих полей строка неоднозначна.

Три места проверки одной загрузки

Первое — исходный файл: helper предварительно считает его SHA-256 и размер. Второе — передача на сервер: PutObject содержит явный ChecksumSHA256, и принимающая сторона может сверить полученные байты. Третье — чтение: SDK получает checksum, поток полностью читается, а копия сравнивается с fixture. При смене source между предварительным чтением и отправкой предварительный хеш больше не описывает фактическое тело; источник следует держать неизменяемым на время опыта. Серверный отказ checksum не превращается в успешную загрузку от того, что локальный файл ранее имел хороший хеш.

В выбранном SDK автоматические integrity defaults появились с S3 module v1.74.1: без явно выбранного алгоритма он рассчитывает CRC32 для загрузки. Наш snapshot S3 v1.114.0 новее этой границы. Helper передаёт собственный предварительно вычисленный SHA-256; нельзя объяснять любой встретившийся CRC32 как свойство самого объекта или отключать проверки общим «совместимым» профилем.

Полный объект и составная характеристика

При multipart нужно различать хеш всей последовательности байтов и composite checksum, составленный по правилам выбранного алгоритма из частей. SHA256(part1 || part2) обычно не равен SHA256(SHA256(part1) || SHA256(part2)). Символ || означает конкатенацию, соединение последовательностей без разделителя. Дополнительный суффикс с количеством частей также нельзя сравнивать с Base64 простого full-object хеша.

В receipt FULL_OBJECT помечается как full-object; COMPOSITE — отдельно. Неизвестное поле типа остаётся unknown. Это полезнее, чем угадать тип по длине строки. По произвольному Range серверный checksum полного объекта не становится checksum выбранных шести байтов. Для диапазона нужна своя ожидаемая характеристика или проверка после сборки полного объекта.

Когда проверка ещё не завершена

SDK может обнаружить checksum error только в конце чтения Body. Если приложение получило первые десять байтов и остановилось, отсутствие ошибки до этого места ничего не подтверждает о последних четырёх. EOF, конец потока, не проверяет криптографический хеш самостоятельно; он лишь позволяет завершить вычисление и сверку. При ошибке чтения, checksum или закрытия промежуточный output не публикуется как принятая копия.

В некоторых SDK checksum передаётся в trailing headers, полях после потокового тела, а не обычным заголовком до тела. Тогда меняются framing, способ отделения полезных байтов от служебных частей потока, и набор служебных полей. Это отдельная ось совместимости: native-приёмка фиксирует версию SDK, алгоритм, payload-signing и streaming/trailer mode. Сервер, принимающий обычный Content-Length PUT, не доказал поддержку всех streaming-вариантов.

Изменяемый пример

Запустите из корня копии книги python3 -B s3/labs/storage_models.py checksums. Подкоманда checksums ничего не пишет и не посылает: печатает длины и хеши вариантов тела. Предскажите результат замены LF на CRLF: длина становится 15, хеш меняется. Удаление LF даёт 13 байтов; это другое полное тело, хотя текстовый редактор может показать ту же строку. Модель также проверяет отличие Base64 от бинарного хеша и Base64 от его печатной hex-записи.

В сетевом опыте считайте checksum исходного файла до запроса и принятой копии после него. При несовпадении сохраняйте оба безопасных значения, размер, request ID и выбранную версию. Не снимайте проверку ради зелёного результата: сначала установите, изменились ли байты, алгоритм, представление либо область checksum.

Go SDK integrity defaults; full/composite и trailing checksums; Base64; SHA-256. Конкретные режимы совместимого endpoint измеряются отдельно.
