Текущее имя, сохранённые версии и маркеры удаления

Построим историю одного ключа и разберём, какие операции скрывают тело, какие удаляют его и что меняется при suspended versioning.

Одна таблица истории

Versioning — режим сохранения нескольких состояний объекта под одним ключом. Version ID выдаёт сервер; он не обязан содержать номер или дату. Возьмём синтетические обозначения v1, v2 и m3. После двух успешных PUT при Enabled существуют две версии данных, последняя является текущей. DELETE без versionId добавляет delete marker — запись об удалённости текущего имени.

Маркер не содержит прежнее тело. Если удалить только m3 с указанием versionId, текущей снова станет v2. Если вместо этого удалить v2, маркер останется текущим и обычный GET по-прежнему не выдаст тело. Удаление выбранной data version окончательно убирает именно её при разрешённых настройках и правах; versioning не отменяет такое удаление.

Выбор версии в протоколе и программе

GetObject с query versionId обращается к выбранной версии. Version ID кодируется как значение query, исходный плюс не заменяется пробелом. Успешный ответ возвращает тело и metadata этой версии. Для выбранного delete marker AWS возвращает 405 с соответствующими полями; обычное чтение при текущем marker ведёт себя как удалённый объект. Не трактуйте marker как нулевой файл.

В helper параметр --version-id поддержан только get/head. Его ставят после имени команды и до --. Пример с реальным записанным ID выполняется после базового опыта: object-study --config FILE --target ID get --version-id SAVED --output NEWFILE --max-bytes 14 -- KEY. FILE, ID, SAVED, NEWFILE и KEY заменяются своими сохранёнными значениями; флаги не выбирают версию по времени или по ETag.

Когда строка null изменяема

У AWS после включения версии нельзя вернуться к состоянию «никогда не включалось»; режим можно приостановить, Suspended. Новые PUT тогда используют буквальный version ID "null". Предыдущая null-version того же ключа заменяется. Обычные сохранённые non-null версии остаются. Поэтому GET versionId=null не фиксирует неизменяемую редакцию: между HEAD и GET тело этой версии могло поменяться.

receipt: "version_id": null     — значение не получено
receipt: "version_id": "null"   — сервер вернул буквальный ID
suspended: PUT A → "null"; PUT B → "null"
GET versionId=null → B

JSON null и строка "null" — разные представления. CLI принимает строку и не превращает её в отсутствие параметра. При Suspended DELETE без versionId удаляет имеющуюся null data version и ставит null marker; non-null история сохраняется. Позднейшее удаление marker может открыть старую data version. Это ещё одна причина проверять историю, а не только текущий статус ключа.

Повтор удаления после неизвестного исхода

В Enabled первая DELETE могла создать m3 и потерять ответ. Повтор простой DELETE создаёт ещё один marker m4. Удаление m4 не восстанавливает v2, потому что m3 всё ещё скрывает её. В never-versioned bucket простой DELETE удаляет текущее тело; если между попытками конкурент записал новое тело, слепой повтор может удалить уже его. Модель этих двух случаев находится в object_operations.py.

Указание точного version ID уменьшает неопределённость выбранного объекта, но не создаёт общий exactly-once протокол. После потери ответа нужно выяснить, существует ли выбранная версия, с какими правами выполнена проверка и не была ли она удалена другим участником. GET 403 без прав перечисления не является подтверждением удаления.

Перечень истории и восстановление

ListObjectVersions отличается от ListObjectsV2: он возвращает Versions и DeleteMarkers, а для продолжения использует пару KeyMarker/VersionIdMarker из ответа. Одинаковый key встречается много раз. Продолжать только по последнему key недостаточно, если страница закончилась посреди его истории. Записывайте version ID, IsLatest, тип записи, размер и время вместе с сохранённым результатом обхода списка; конкурентные изменения не превращают многостраничный обход в транзакцию.

Для восстановления прочитайте выбранную data version в новую копию и проверьте хеш. Если нужно вернуть её как current, это новая запись или CopyObject выбранной версии, а не магическое изменение указателя истории без новой операции. Сначала проверьте доступ, стоимость и retention. Наличие старых версий не заменяет отдельную резервную копию, которую не может удалить тот же потерянный аккаунт.

Упражнение с продолжением

Из корня книги выполните python3 -B s3/labs/object_operations.py. Модель показывает два marker после потерянного DELETE и повторения, затем раздельное удаление marker и data version. Для собственного сохранённого состояния используйте state-модель главы упражнений: её JSON помещает mode и историю одного синтетического ключа в явное представление. Сравните режимы enabled, suspended и unversioned до запуска следующего действия; имена v1/m3 в модели не обещают формат ID настоящего сервера.
