Условие и диапазон: выбрать состояние до передачи байтов

Два писателя, кэш и возобновляемая загрузка используют разные условия. Проследим, какое состояние сервер проверяет и что должен сохранить клиент.

Почему HEAD перед PUT не закрывает гонку

Гонка — зависимость результата от взаимного порядка действий участников. Пусть A и B получили HEAD с ETag "E1". A записал новое тело. Если B отправит обычный PUT, его прежний HEAD не участвует в решении сервера и запись A может быть заменена. Условный запрос переносит проверку ожидаемого состояния в саму операцию записи.

ПорядокКлиент AКлиент BТекущее тело
1HEAD → "E1"HEAD → "E1"v1
2PUT If-Match: "E1" → успехожидаетv2, ETag "E2"
3готовPUT If-Match: "E1" → отказv2

Здесь E1/E2 — учебные непрозрачные значения. Кавычки входят в синтаксис entity-tag. В AWS отказ несовпавшего условия обычно представлен 412 Precondition Failed; конкурирующее удаление может потребовать другой ветки, включая 409/404 по правилам операции. Условие не создаёт транзакции между разными ключами. После отказа B должен получить новое состояние и заново решить прикладную задачу, а не молча повторить уже без If-Match.

Create-only и потерянное подтверждение

If-None-Match: * на PutObject означает создание только при отсутствии текущего объекта. Это сильнее отдельной проверки отсутствия через HEAD. Если текущим состоянием versioned ключа является delete marker, AWS допускает новую create-only запись. Исторические версии при этом могут существовать.

Первый PUT мог пройти, а ответ потеряться. SDK повторяет ту же create-only операцию и получает 412. Этот ответ относится к повторной попытке; логическая операция остаётся unknown, пока не найдено подходящее состояние. Поле metadata operation-id помогает сопоставлению, но не обеспечивает exactly-once — ровно одно выполнение прикладной операции при отказах и повторах. Подробный путь восстановления находится в главе 15.

Helper v1 требует ровно одно условие: --create-only либо --if-match ETAG. Эту развилку нельзя заменить параметром «перезаписать при ошибке». Идентификатор операции сохраняется между внутренними повторениями SDK. Сам клиент дополнительных внешних повторов не добавляет.

Проверка кэша при чтении

Кэш — ранее полученная копия, которую клиент хочет использовать повторно. Условный GET с If-None-Match: "E1" при совпадении текущего ETag может вернуть 304 Not Modified без нового тела. Тогда нужно уже иметь подходящую локальную копию; 304 не создаёт её. GET с If-Match требует именно ожидаемый validator и при его несовпадении отвергается. Validator — значение, по которому сервер проверяет состояние представления. Ниже рассмотрим приоритет условия по ETag над датой.

ETag и дата в одном GET

В HTTP strong validator, сильный валидатор, различает изменения данных представления. Weak validator, слабый, допускает эквивалентные представления и имеет префикс W/ перед кавычками entity-tag. В правилах RFC If-Match использует сильное сравнение, If-None-Match — слабое; слабый тег нельзя превращать в сильный простым удалением W/. Наши примеры S3 сохраняют фактический ETag ответа вместе с кавычками и не выводят его из MD5. См. RFC 9110 §8.8 и §13.2.2.

Для существующего доступного объекта и полного GET без Range таблица показывает условия AWS GetObject. В столбце даты «нет» означает, что условие даты само по себе было бы ложным. Ошибки подписи, прав и отсутствующего объекта здесь исключены; это не таблица всех возможных ответов.

Пусть Last-Modified объекта — Mon, 02 Nov 2026 12:00:00 GMT, а его ETag — "E1". В запросе If-Match: "E1" и If-Unmodified-Since: Mon, 02 Nov 2026 11:59:00 GMT первая проверка истинна, вторая ложна: объект менялся после 11:59. Это всё равно 200, а не логическое И с результатом 412. В запросе If-None-Match: "E1" с If-Modified-Since на те же 11:59 дата говорит «менялся», но совпавший ETag даёт 304. Обе конфликтующие пары прямо описаны в GetObject: URI request parameters.

Дата модификации имеет другую точность и назначение, чем идентификатор версии; она не становится уникальным номером записи. Helper v1 не добавляет условные GET-флаги и If-Range. Для его чтения выбранной версии используется только существующий --version-id; таблица объясняет протокол для отдельного принятого клиента.

Шесть байтов из четырнадцати

Range — поле запроса выбранного байтового интервала. В Range: bytes=0-5 обе границы включены, поэтому длина равна 5−0+1=6. Для тела hello-v1 это байты object. Корректный ответ частичного чтения содержит 206 Partial Content, Content-Range: bytes 0-5/14 и Content-Length: 6. Число 14 — размер полного представления, а не длина этого ответа.

Range: bytes=0-5
If-Match: "E1"

HTTP/1.1 206 Partial Content
Content-Range: bytes 0-5/14
Content-Length: 6

object

Это фрагменты полей и тела для объяснения; они не являются готовой неподписанной командой. Полный запрос подписывается заново с фактическим host и ключом. Наша программа object-study не имеет флага --range. AWS GetObject поддерживает один диапазон в одном запросе; множественные интервалы через запятую не следует переносить сюда из произвольного HTTP-сервера.

Range: bytes=14- для четырнадцатибайтового тела начинается за последним байтом и не удовлетворяется: ожидается 416. Range: bytes=13- возвращает один LF, а суффикс bytes=-1 тоже выбирает последний байт. Точный разбор зависит от текущего размера и ответа сервера; клиент проверяет Content-Range и число полученных байтов, а не принимает любое 200 за требуемый 206.

Как собрать большую копию без смешения редакций

Пусть файл читается двумя диапазонами. После первого другой писатель меняет текущий объект. Если второй запрос не связывается с той же сохранённой версией или validator, клиент может склеить куски разных тел. Равенство общей длины эту ошибку не обнаружит. Сохраните конкретный non-null version ID при поддержанной версии либо применяйте If-Match и проверяйте ETag каждого ответа. В случае ABA одного повторившегося ETag недостаточно для знания всей истории.

Сборка идёт в новый локальный файл, где известны смещения, покрытые диапазоны и ожидаемая полная длина. После последнего диапазона вычисляется хеш полного тела и только затем оно публикуется. Частичный файл не считается завершённым из-за красивого имени. Если подтверждённая версия исчезла или условие отказало, продолжение с текущим объектом начинает другой опыт; прежние куски не следует использовать автоматически.

Проверка без сервера

python3 -B s3/labs/storage_models.py ranges проверяет интервалы на нашей fixture. Сначала предскажите шесть байтов и ответ для начала 14. Затем модель демонстрирует смешанную сборку v1/v2: локальные длины совпадают, а полный хеш отличается. Это проверка арифметики и инварианта одной версии, а не S3 server conformance test.
