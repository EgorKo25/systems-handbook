PUT, GET и DELETE: тело, текущий объект и история

Запишем 14 байтов под одним ключом, прочитаем их обратно и проследим, что удаление меняет в корзине с сохранением версий. Затем повторим этот путь с потерянными ответами и оборванным чтением.

Какие байты и какой объект мы передаём

Возьмём fixture из первой главы: заранее заданные тестовые байты object-lab v1\n. Здесь \n обозначает один LF, байт перевода строки 0a, а не два печатных знака. Тринадцать предшествующих символов входят в ASCII — таблицу кодирования, в которой каждый из этих латинских символов, цифр, дефиса и пробела занимает один байт. Поэтому тело содержит ровно 14 байтов:

6f 62 6a 65 63 74 2d 6c 61 62 20 76 31 0a
 o  b  j  e  c  t  -  l  a  b     v  1 LF

Корзина называется study-s3, ключ — lessons/2026-11/hello +%.txt. Ключ выбирает объект внутри корзины; его косые черты не требуют создания каталогов на сервере. При адресации с корзиной в пути начало адреса будет /study-s3/lessons/2026-11/hello%20%2B%25.txt: пробел закодирован как %20, буквальный плюс — как %2B, процент — как %25. Тело при этом не кодируется в проценты и остаётся теми же 14 байтами.

К телу добавим пользовательские метаданные — пару имени и значения, сохранённую вместе с объектом: operation-id=00000000000000000000000000000001. Это выбранный приложением номер одной логической записи. В HTTP-запросе такое имя получает префикс x-amz-meta-; при чтении префикс возвращается. Сервер не обязан устранять повторные PUT по этому номеру. Номер нужен приложению для последующего сопоставления. Пользовательские метаданные S3.

Ниже вручную составлены сообщения HTTP/1.1 с публичными вымышленными учётными данными из главы s3-06-signature: access key AKIDEXAMPLE, secret s3-lab-only-not-a-real-secret, регион us-east-1, служба s3, без session token. Это разбор протокола, а не команды для отправки. 127.0.0.1:19000 продолжает учебный вектор предыдущей главы и обозначает сетевое окружение самого клиента. Он не является endpoint AWS или адресом RGW в другой VM. Все ответы, ETag, version ID и request ID в примере сконструированы. Показаны минимальные сообщения для разбора; реальная служба может добавить другие заголовки.

В печатных блоках строки заголовков показаны обычными переносами. Для получения байтов HTTP каждую такую строку, включая пустую строку между заголовками и телом, заканчивают CRLF — двумя байтами 0d 0a. У тела только свой последний LF. В каноническом запросе SigV4 разделителем остаётся один LF, как в главе 06. Смешение этих двух представлений изменит подпись или тело. Формат сообщения HTTP/1.1.

PUT: условие, тело и подтверждение

Создадим объект, только если у ключа сейчас нет тела объекта. Условие If-None-Match: * проверяет сервер во время записи. Предварительный HEAD с ответом «нет объекта» этого условия не заменяет: между HEAD и PUT другой клиент мог бы создать объект.

PUT /study-s3/lessons/2026-11/hello%20%2B%25.txt HTTP/1.1
host: 127.0.0.1:19000
x-amz-content-sha256: 874160ebe2d9a6a82abdec1966f3be5be4e0db5d575d4d00953c66baf6e30897
x-amz-date: 20261101T090000Z
content-type: text/plain
if-none-match: *
x-amz-meta-operation-id: 00000000000000000000000000000001
x-amz-checksum-sha256: h0Fg6+LZpqgqvewZZvO+W+Tg211XXU0AlTxmuvbjCJc=
content-length: 14
authorization: AWS4-HMAC-SHA256 Credential=AKIDEXAMPLE/20261101/us-east-1/s3/aws4_request, SignedHeaders=content-type;host;if-none-match;x-amz-checksum-sha256;x-amz-content-sha256;x-amz-date;x-amz-meta-operation-id, Signature=db8d8bd200fa19f16b17fdf4c83820543e44e4f9db054245f249f67dcec27d38

object-lab v1

PUT выбирает операцию записи; HTTP/1.1 задаёт формат сообщения. В первой строке нет query-параметров. host содержит адрес и порт получателя, участвующие в подписи. content-length: 14 сообщает длину передаваемого тела, без строки запроса, заголовков и разделяющего CRLF. content-type: text/plain описывает тело как обычный текст; он сам не меняет кодировку и не добавляет LF. В исходниках helper v1 для файлов выбран application/octet-stream, то есть произвольные байты. Поэтому данный учебный запрос не является побайтовым дампом helper.

x-amz-content-sha256 содержит 32 байта SHA-256 тела в виде 64 шестнадцатеричных знаков. Поле x-amz-checksum-sha256 представляет те же 32 байта в Base64: это способ записи бинарных данных печатными знаками, здесь 44 знака с завершающим =. Первое значение участвует в SigV4, второе явно просит службу проверить контрольную сумму загружаемого объекта. Сам заголовок checksum также включён в нашу подпись. Для одиночного PutObject это checksum всего тела. Multipart upload — загрузка объекта отдельными частями с последующим завершением; у неё возможна составная checksum, полученная из checksum частей. Проверка checksum при загрузке.

x-amz-date — время подписывания в UTC: 1 ноября 2026 года, 09:00:00. Поле Authorization непрерывно, без добавленных переносов внутри значения. В его Credential после access key записан scope 20261101/us-east-1/s3/aws4_request. SignedHeaders перечисляет семь подписанных имён; Signature содержит вычисленный HMAC. Алгоритм вывода ключа остаётся тем же, что в главе 06. Здесь добавлены checksum и operation-id, поэтому изменились канонический запрос и окончательная подпись. content-length в выбранный список не включён.

Для проверки именно нового примера канонический запрос приведён целиком. После последнего хеша завершающего LF нет; между каноническими заголовками и их списком есть одна пустая строка.

PUT
/study-s3/lessons/2026-11/hello%20%2B%25.txt

content-type:text/plain
host:127.0.0.1:19000
if-none-match:*

Это полностью заданный HMAC-вектор, который можно пересчитать без обращения к службе. Изменение If-None-Match, номера операции, времени или хотя бы одного байта тела требует новой подписи. SigV4 с подписью заголовков.

Принимаем для дальнейшего разбора такой ответ:

HTTP/1.1 200 OK
Date: Sun, 01 Nov 2026 09:00:00 GMT
Content-Length: 0
ETag: "study-etag-v1"
x-amz-version-id: study-v1
x-amz-checksum-sha256: h0Fg6+LZpqgqvewZZvO+W+Tg211XXU0AlTxmuvbjCJc=
x-amz-checksum-type: FULL_OBJECT
x-amz-request-id: study-put-1

200 означает успешный PutObject. Content-Length: 0 относится к пустому телу этого ответа; оно не означает, что был сохранён пустой объект. Date — время формирования ответа в HTTP-формате с GMT. x-amz-request-id — номер запроса, выданный сервером для диагностики; он не является номером версии или нашего намерения записи. ETag — непрозрачная метка объекта, которую можно вернуть в предусмотренном условии. Кавычки являются частью показанного значения заголовка. Формат "study-etag-v1" выбран для примера: по нему не вычисляют контрольную сумму.

x-amz-version-id: study-v1 сообщает присвоенный сервером идентификатор версии. В этом основном сценарии AWS general purpose bucket имеет включённое versioning, то есть сохраняет отдельные версии записей. FULL_OBJECT уточняет, что checksum относится ко всему телу. Ответ PUT не обязан повторять пользовательские метаданные; позже прочитаем их через HEAD и GET. Согласно AWS, успешный PutObject сохраняет объект целиком; частичный объект результатом успешного PUT не становится. PutObject.

В этой точке на сервере есть версия с телом длиной 14 байтов, типом содержимого, checksum и operation-id; текущий ключ указывает на неё. Из ответа клиент узнал version ID, ETag и request ID. После полученного успешного ответа AWS обеспечивает согласованное чтение записанного состояния. Одновременная более поздняя запись может снова поменять текущий ключ; несколько обращений к текущему ключу не составляют одного снимка. Обновление одного ключа атомарно: чтение не должно собирать начало старого тела с концом нового. Эти свойства описывают наблюдаемое поведение AWS, а не устройство его внутренних дисков, реплик или протокола фиксации. Модель согласованности Amazon S3.

Один ключ проходит через три разных представления

Схема показывает корзину с включённым versioning, то есть Enabled. Маркер удаления — версия без тела, которая скрывает текущий объект от обычного GET ключа. Стрелка записи меняет серверное состояние, стрелка чтения переносит выбранное тело к клиенту. Получение заголовков и появление нового локального имени — разные шаги.

[fixture: 14 байтов + operation-id]
          |
          | PUT, If-None-Match: *
          v
[текущий key → v1; история: v1]
          |
          | HEAD: ETag, version ID, checksum, operation-id; тела нет
          | GET versionId=v1: заголовки + поток 14 байтов
          v
[временный локальный файл]
          |
          | полное чтение + длина + checksum + закрытие потока
          | синхронизировать файл → закрыть → создать новое имя
          | синхронизировать каталог
          v
[новое принятое имя output]

серверный key → v1 -----PUT------→ v2 --DELETE без ID--→ marker m1
история       [v1]                  [v2,v1]              [m1,v2,v1]
GET key       тело v1               тело v2              404
GET ID=v1     тело v1               тело v1              тело v1

Скопированное тело не делает локальный файл принятой копией до окончания проверок и публикации имени. Текущий маркер на сервере, напротив, меняет обычный GET ключа, но не стирает сохранённое тело v1. Эти два изменения происходят в разных местах и проверяются по-разному.

HEAD выбирает сведения, GET передаёт тело

Сначала запросим текущий объект методом HEAD. Поле x-amz-checksum-mode: ENABLED запрашивает сохранённую checksum. У самого запроса нет тела, поэтому его x-amz-content-sha256 — SHA-256 пустой последовательности. Это не SHA-256 загруженного объекта.

HEAD /study-s3/lessons/2026-11/hello%20%2B%25.txt HTTP/1.1
host: 127.0.0.1:19000
x-amz-content-sha256: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
x-amz-date: 20261101T090005Z
x-amz-checksum-mode: ENABLED
authorization: AWS4-HMAC-SHA256 Credential=AKIDEXAMPLE/20261101/us-east-1/s3/aws4_request, SignedHeaders=host;x-amz-checksum-mode;x-amz-content-sha256;x-amz-date, Signature=8dd192870261662dfc0977885ca8f55fb8cb082019abed3ea9722bc29e540410


HTTP/1.1 200 OK
Date: Sun, 01 Nov 2026 09:00:05 GMT
Content-Length: 14
Content-Type: text/plain
Last-Modified: Sun, 01 Nov 2026 09:00:00 GMT
ETag: "study-etag-v1"
x-amz-version-id: study-v1
x-amz-meta-operation-id: 00000000000000000000000000000001
x-amz-checksum-sha256: h0Fg6+LZpqgqvewZZvO+W+Tg211XXU0AlTxmuvbjCJc=
x-amz-checksum-type: FULL_OBJECT
x-amz-request-id: study-head-1

У ответа HEAD нет тела. Здесь Content-Length: 14 сообщает размер тела, которое передал бы соответствующий GET, а не количество байтов после пустой строки ответа HEAD. Last-Modified описывает время изменения выбранного объекта; его нельзя подменять полем Date, относящимся к ответу. Content-Type, ETag, version ID, checksum и пользовательский operation-id относятся к выбранной версии. HEAD позволяет сравнить эти сведения без скачивания тела, но сам не проверяет, что клиент сумеет полностью прочитать и сохранить 14 байтов. HeadObject, Семантика HEAD.

Теперь запросим конкретную сохранённую версию, указав versionId=study-v1 в query. Query входит в подпись. Это отдельный запрос; его время и подпись вычислены заново.

GET /study-s3/lessons/2026-11/hello%20%2B%25.txt?versionId=study-v1 HTTP/1.1
host: 127.0.0.1:19000
x-amz-content-sha256: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
x-amz-date: 20261101T090010Z
x-amz-checksum-mode: ENABLED
authorization: AWS4-HMAC-SHA256 Credential=AKIDEXAMPLE/20261101/us-east-1/s3/aws4_request, SignedHeaders=host;x-amz-checksum-mode;x-amz-content-sha256;x-amz-date, Signature=a76e5a7630877c258b2dd78ab19d846485a5b02743174b50c1f5f54eb6f50f17


HTTP/1.1 200 OK
Date: Sun, 01 Nov 2026 09:00:10 GMT
Content-Length: 14
Content-Type: text/plain
Last-Modified: Sun, 01 Nov 2026 09:00:00 GMT
ETag: "study-etag-v1"
x-amz-version-id: study-v1
x-amz-meta-operation-id: 00000000000000000000000000000001
x-amz-checksum-sha256: h0Fg6+LZpqgqvewZZvO+W+Tg211XXU0AlTxmuvbjCJc=
x-amz-checksum-type: FULL_OBJECT

object-lab v1

После пустой строки передаются те самые 14 байтов, включая LF. Сравниваем не только 200: полученная длина должна быть 14, SHA-256 тела — 874160ebe2d9a6a82abdec1966f3be5be4e0db5d575d4d00953c66baf6e30897, а operation-id — номер нашей записи. Сохранённая версия AWS с ID, отличным от строки null, выбирает одно тело с его пользовательскими метаданными даже после смены текущей версии, пока выбранная версия существует и доступна. Такие ID будем называть non-null. Её могут окончательно удалить; чтение также требует подходящих прав и, при шифровании, доступа к ключу. Получение выбранной версии.

Для доступа к текущему объекту AWS проверяет s3:GetObject, а для выбранной версии — s3:GetObjectVersion. Отсутствующий текущий ключ обычно различается как 404, если у вызывающего есть s3:ListBucket, и 403 без этого разрешения. Поэтому одиночный 403 нельзя читать как подтверждение наличия или отсутствия тела. У HEAD ошибки часто доступны только как HTTP-статус без подробного тела ошибки. GetObject и разрешения, Ошибки HeadObject.

Есть и другое условие чтения: If-None-Match с конкретным ETag просит передать тело, только если текущая метка отличается. Если клиент уже имеет принятую локальную копию с "study-etag-v1", протокольный запрос может выглядеть так:

GET /study-s3/lessons/2026-11/hello%20%2B%25.txt HTTP/1.1
host: 127.0.0.1:19000
x-amz-content-sha256: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
x-amz-date: 20261101T090015Z
if-none-match: "study-etag-v1"
authorization: AWS4-HMAC-SHA256 Credential=AKIDEXAMPLE/20261101/us-east-1/s3/aws4_request, SignedHeaders=host;if-none-match;x-amz-content-sha256;x-amz-date, Signature=e51e40a0a98c5649c00040a414632a4d48991f6ec9c466ecbe5a5df4b7e63c8c


HTTP/1.1 304 Not Modified
Date: Sun, 01 Nov 2026 09:00:15 GMT
ETag: "study-etag-v1"
x-amz-request-id: study-get-conditional-1

304 не содержит тела и разрешает использовать ранее сохранённое представление по правилам условного чтения. Он не создаёт локальную копию, если её прежде не было. Другое условие, If-Match: "study-etag-v1", передало бы тело только при совпадении метки, иначе дало бы 412. В этих примерах используется одно условие; правила сочетания нескольких условий нужно рассматривать отдельно. Helper v1 не имеет флагов условного GET: этот обмен объясняет протокол. Условия GetObject.

От ответа GET до нового локального файла

SDK — библиотека, которая преобразует вызов Go в запрос службы. В исходниках helper вызывающий код задаёт bucket, исходный key, предел размера и необязательный version ID. SDK кодирует адрес, добавляет нужные заголовки, вычисляет SigV4 из выбранных credentials и передаёт запрос HTTP-клиенту. HTTP-клиент устанавливает соединение, проверяет TLS для HTTPS, отправляет сообщение и разбирает ответ. Сервер проверяет подпись, разрешения, условие и данные; конкретный порядок его внутренних стадий этим описанием не задаётся.

При GetObject возврат структуры результата и Body ещё не означает успешное получение тела: Body — поток, из которого программа продолжает читать. EOF сообщает, что поток закончился. В Go последнее чтение может вернуть одновременно несколько байтов и EOF; программа сначала учитывает эти байты, затем обрабатывает признак конца потока. Ошибка транспорта или несовпадение checksum могут проявиться при этом чтении, уже после получения заголовков. SDK проверяет возвращённую поддерживаемую checksum при запрошенном режиме; отсутствие checksum в ответе не превращается в выполненную проверку. Полное чтение до EOF и закрытие Body выполняет вызывающий код. Проверка checksum в Go SDK.

Для нашей загрузки возьмём N=14. Это верхний предел, а не требование получить ровно N для любого объекта. Полный объект длиной 13 байтов уложился бы в предел, но не совпал бы с данной fixture. Ответ с объявленным Content-Length: 14 и только десятью полученными байтами не проходит проверку длины. В примере десять байтов — object-lab; оставшиеся v1\n потерялись. HTTP-клиент может сообщить обрыв раньше, но вызывающий код дополнительно сравнивает известную длину ответа с фактически скопированной. Верхний предел N проверяют по потоку Body: после N байтов helper пытается прочитать ещё один. Дополнительный байт означает превышение предела, а EOF без дополнительных байтов — конец потока. Это нужно и для ответа с неизвестной длиной. В показанном HTTP/1.1-ответе Content-Length: 14 уже ограничивает Body четырнадцатью байтами. Такое чтение не проверяет, остались ли за телом лишние байты в сетевом соединении. Неполные сообщения HTTP/1.1.

Путь файла output и его каталоги должны контролироваться учебным пользователем. В Linux-реализации helper новое тело сначала попадает во временный файл того же каталога. До публикации проверяются полный ответ 200 без частичного диапазона, ограничение N, известный Content-Length, EOF, checksum и закрытие Body. Если служба вернула SHA-256 с типом FULL_OBJECT, он отдельно сравнивается с локальным SHA-256. Составную checksum multipart нельзя сравнивать с обычным SHA-256 всех байтов.

После проверок helper синхронизирует и закрывает временный файл, создаёт конечное имя через hard link — ещё одно имя того же файла — без замены уже существующего имени, затем синхронизирует каталог. При обрыве на десятом байте конечное имя не публикуется. При ошибке checksum после четырнадцатого байта оно также не публикуется. Существовавший output не перезаписывается. Есть более поздняя точка ошибки: если link уже создан, но синхронизация каталога не удалась, полное конечное имя уже может быть видно. Код 5 сообщает локальную ошибку; повторно писать поверх этого имени helper не должен. Приёмка файла требует успешного завершения всей выбранной последовательности, включая сохранение имени.

Квитанция helper, receipt, записана в JSON — текстовом формате с именованными полями. Она содержит выбранные сведения о последнем ответе и локальном чтении. HTTP-статус 200 может остаться в квитанции неудачного GET: сервер уже прислал заголовки, а поток оборвался позже. Поля local_bytes и local_sha256_hex читают вместе с outcome и кодом завершения. SHA-256 из самостоятельно заданной fixture сравнивается с принятым результатом отдельно; совпавшая длина сама по себе не устанавливает совпадение содержимого.

Следующий PUT меняет текущую версию

Изменим один байт тела: цифру 1 на 2. object-lab v2\n по-прежнему содержит 14 байтов, но его SHA-256 равен ff0761e2751da943e831d1d4b5538e9a4ba9e6e5fc1e65a5cc2d7c21dd46b9fa. Условие If-Match связывает замену с известным ETag текущего объекта. Оно не выбирает version ID для записи поверх сохранённой старой версии.

PUT /study-s3/lessons/2026-11/hello%20%2B%25.txt HTTP/1.1
host: 127.0.0.1:19000
x-amz-content-sha256: ff0761e2751da943e831d1d4b5538e9a4ba9e6e5fc1e65a5cc2d7c21dd46b9fa
x-amz-date: 20261101T090100Z
content-type: text/plain
if-match: "study-etag-v1"
x-amz-meta-operation-id: 00000000000000000000000000000002
x-amz-checksum-sha256: /wdh4nUdqUPoMdHUtVOOmkup5uX8HmWlzC18Id1Gufo=
content-length: 14
authorization: AWS4-HMAC-SHA256 Credential=AKIDEXAMPLE/20261101/us-east-1/s3/aws4_request, SignedHeaders=content-type;host;if-match;x-amz-checksum-sha256;x-amz-content-sha256;x-amz-date;x-amz-meta-operation-id, Signature=9996ada4545c7d4a1cdb01e8a8598e570f8ce489bb0515cd1b7e8a0a90cd1b98

object-lab v2

HTTP/1.1 200 OK
Date: Sun, 01 Nov 2026 09:01:00 GMT
Content-Length: 0
ETag: "study-etag-v2"
x-amz-version-id: study-v2
x-amz-checksum-sha256: /wdh4nUdqUPoMdHUtVOOmkup5uX8HmWlzC18Id1Gufo=
x-amz-checksum-type: FULL_OBJECT
x-amz-request-id: study-put-2

Поменялись условие, SHA-256 тела, checksum, operation-id, время и подпись. Остальные поля имеют прежний смысл. Вторая запись снова передаёт целое тело и свой набор пользовательских метаданных. PUT не дописывает 14 байтов к прежним четырнадцати: размер новой версии остаётся 14, а не 28. При включённом versioning версия study-v1 остаётся, новой текущей становится study-v2. GET без query теперь выбирает v2, а GET ?versionId=study-v1 продолжает выбирать v1. При несовпадении текущего ETag условный PUT получает 412. Если текущего объекта нет или текущая версия является delete marker, AWS для If-Match возвращает 404; при конкурирующих изменениях возможен и 409. Поведение условной записи.

ETag проверяет предусмотренное сервером условие, но не является уникальным номером события. Если состояния сменились A → B → A, метка может вернуться к прежнему значению. Этот случай называют ABA: сравниваемое значение совпало, хотя между чтением и записью были изменения. Поэтому If-Match не подтверждает, что никто не писал со времени нашего HEAD, и не заменяет номер операции или историю версий.

PUT сохранился, но ответ потерян

Вернёмся к первой записи. До запроса ключ отсутствовал. Первая попытка create-only дошла до службы и создала study-v1 с operation-id ...0001. Ответ 200 потерялся. Для клиента это ошибка соединения, хотя сервер уже хранит все 14 байтов.

клиент                        служба: текущая версия
PUT If-None-Match: *   ------> study-v1, operation-id ...0001
                       <--X-- 200, version-id study-v1
повтор того же условия ------> study-v1 уже существует
                       <------ 412 Precondition Failed

SDK может выполнять внутренние повторы подходящих ошибок в пределах общего времени операции; в исходниках helper задано максимум три попытки SDK. При повторе остаются тело, условие и operation-id, а подпись может вычисляться заново для отправляемого запроса. Последний 412 говорит об отказе повторной попытки, но не отменяет первый PUT. Повторы и тайм-ауты Go SDK.

Для этого случая квитанция логической PUT-операции может содержать "http_status": 412, код завершения 3 и "outcome": "unknown". Поле attempts считает вызовы HTTPClient.Do на стороне SDK, а не все передачи по сети: HTTP-транспорт может выполнять собственные переподключения. Поэтому обработчик квитанции helper консервативно оставляет unknown у неудачного PUT после любой возможной отправки, даже если последним получен понятный отказ. Ошибка открытия или предварительного хеширования локального файла-источника source до отправки даёт rejected. Ошибка чтения source после возможной отправки тоже оставляет unknown: локальная причина не доказывает, что сервер ничего не сохранил.

После неизвестного исхода сначала прекращают новые записи этого опыта под тем же ключом. Затем читают метаданные и тело доступных версий, сопоставляя точный ключ, operation-id, длину и SHA-256 с подготовленной записью. Для обычной сохранённой non-null версии найденный ID позволяет повторять чтение одного тела с его метаданными, пока версия доступна. Если другой клиент уже сменил текущий объект, одного текущего HEAD будет мало: искомая версия могла стать предыдущей. GET и совпавший хеш без operation-id показывают нужные байты, но другой клиент мог записать такие же. Operation-id тоже является данными приложения: его уникальность и отсутствие чужого повторного использования — предпосылки сопоставления.

Helper v1 генерирует номер до вызова PUT и возвращает его в receipt; он не записывает устойчивый журнал намерений перед отправкой. Если процесс погиб до сохранения квитанции, у пользователя может не остаться номера для уверенного сопоставления. Новые автоматические повторы без условия этого не исправляют: при versioning они способны добавить сохранённые версии. HTTP-идемпотентность PUT описывает предполагаемый эффект повторного запроса на целевой ресурс, но не обещает одну запись в истории и не устанавливает авторство найденных байтов. Идемпотентные методы HTTP. Подробный порядок действий после ошибок продолжается в s3-15-errors-reconciliation.

DELETE: скрыть текущий ключ или удалить выбранную версию

Delete marker, маркер удаления, — отдельная запись версии без тела объекта. Когда она текущая, обычное чтение ключа видит удаление; более старые версии при этом могут сохраняться. В исходном Enabled-сценарии после двух PUT история, от новой записи к старой, выглядит как [study-v2, study-v1]. Следующий DELETE не содержит versionId. В helper v1 команды DELETE нет: ниже только протокольная иллюстрация.

DELETE /study-s3/lessons/2026-11/hello%20%2B%25.txt HTTP/1.1
host: 127.0.0.1:19000
x-amz-content-sha256: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
x-amz-date: 20261101T090200Z
authorization: AWS4-HMAC-SHA256 Credential=AKIDEXAMPLE/20261101/us-east-1/s3/aws4_request, SignedHeaders=host;x-amz-content-sha256;x-amz-date, Signature=08c9285831c7db1b26c2ec501c3db115bc12f3a7eb36fcbd6edbdbc5d72cf10c


HTTP/1.1 204 No Content
Date: Sun, 01 Nov 2026 09:02:00 GMT
x-amz-delete-marker: true
x-amz-version-id: study-marker-m1
x-amz-request-id: study-delete-1

204 означает успешную операцию без тела ответа. По HTTP в таком ответе Content-Length не передаётся. x-amz-delete-marker: true и version ID сообщают о созданном маркере. История становится [study-marker-m1, study-v2, study-v1]. Тела v2 и v1 не удалены этим простым DELETE. DeleteObject, Content-Length в ответах без тела.

GET или HEAD текущего ключа теперь получает 404 с x-amz-delete-marker: true. Запрос выбранного study-v1 по-прежнему может вернуть тело. Если же явно запросить сам study-marker-m1 через GET или HEAD, AWS вернёт 405, заголовок delete-marker и Last-Modified: у выбранной записи нет тела объекта для такого чтения. Маркер не равен пустому объекту: объект с нулём байтов можно успешно прочитать, а текущий маркер обозначает отсутствие текущего тела. Чтение delete marker.

Чтобы убрать именно маркер и снова сделать v2 текущей, нужен DELETE с его version ID:

DELETE /study-s3/lessons/2026-11/hello%20%2B%25.txt?versionId=study-marker-m1 HTTP/1.1
host: 127.0.0.1:19000
x-amz-content-sha256: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
x-amz-date: 20261101T090205Z
authorization: AWS4-HMAC-SHA256 Credential=AKIDEXAMPLE/20261101/us-east-1/s3/aws4_request, SignedHeaders=host;x-amz-content-sha256;x-amz-date, Signature=e6043136a7deaaf0588a321636139e16d49664c1ec0343d9f1ebf6993bf01779


HTTP/1.1 204 No Content
Date: Sun, 01 Nov 2026 09:02:05 GMT
x-amz-delete-marker: true
x-amz-version-id: study-marker-m1
x-amz-request-id: study-delete-marker-1

Теперь true описывает удалённую запись-маркер. Запись study-marker-m1 окончательно убрана; текущей становится v2, история снова [study-v2, study-v1]. Простой повтор DELETE без versionId имел бы другой эффект: он создал бы новый маркер. Именно выбранный query-параметр делает эти операции разными. Удаление выбранного маркера.

Тот же метод с versionId=study-v1 окончательно удалял бы данные v1, а не создавал маркер поверх них. Подстановка другого query требует новой подписи; подпись удаления маркера для этого не подходит. Для такого удаления AWS проверяет s3:DeleteObjectVersion, для простого DELETE — s3:DeleteObject. Действующие правила хранения и защиты объектов могут запрещать окончательное удаление. Отказ 403 или иной ошибки нужно разбирать как результат конкретного обращения, а не как успешное удаление. Удаление версий, Разрешения DeleteObject.

Что меняется без versioning и при Suspended

До сих пор использовалась корзина AWS general purpose с состоянием versioning Enabled. Это настройка корзины; расширение файла, SDK и слово backend в JSON helper её не включают. Для одного ключа различаются следующие случаи.

Состояние корзиныСледующий PUTDELETE без versionId
Versioning никогда не включалосьЗаменяет текущее тело; история прежних записей средствами versioning не сохраняется.Удаляет текущее тело окончательно; маркера версии нет.
EnabledСоздаёт новую версию с присвоенным ID; прежние сохраняются.Создаёт новый текущий маркер; прежние тела сохраняются.
Suspended после включения versioningСоздаёт версию с буквальным ID null или заменяет существующую null-версию; сохранённые non-null версии остаются.Убирает существующее тело null-версии, если оно есть, и устанавливает текущий null-маркер; non-null версии сохраняются.

Например, при Suspended история [null: v2, study-v1: v1] после нового PUT становится [null: v3, study-v1: v1]. Тело v2 из null-слота заменено; GET ?versionId=null уже получает v3. Последующий простой DELETE заменяет этот слот маркером: [null: marker, study-v1: v1]. Если null-слота ещё нет, DELETE добавляет null-маркер, сохраняя существующие non-null версии. Эти переходы задаются именно правилами AWS для Suspended. PUT при Suspended, DELETE при Suspended.

В receipt нужно различать JSON "version_id": null — значение ID не получено — и "version_id": "null" — сервер передал буквальную строку ID. Вторую строку нельзя превращать в JSON null. Она также не закрепляет неизменное состояние: при Suspended этот слот перезаписывается. HEAD с ID "null", а затем GET этого ID не гарантируют одно и то же тело при конкурирующем PUT. DELETE с versionId=null тоже обращается к этому изменяемому слоту, поэтому при конкуренции может затронуть уже другое тело.

Условия записи проверяют текущее состояние. В Enabled-корзине If-None-Match * может успешно создать новое тело поверх текущего маркера, хотя более старые версии по-прежнему существуют. Такое условие означает «сейчас нет текущего тела», а не «этот ключ никогда раньше не использовался».

DELETE потерял ответ: проверяем состояние и историю

Пусть Enabled-корзина содержит [study-v2, study-v1]. Первый простой DELETE создаёт study-marker-m1, но его ответ теряется. Повтор простого DELETE создаёт ещё один маркер, study-marker-m2. Текущий GET после обеих попыток даёт одинаковое «нет текущего тела», а история различается:

до DELETE             [v2, v1]
первая запись         [m1, v2, v1]       ответ потерян
повтор без versionId  [m2, m1, v2, v1]
GET текущего          404
DELETE versionId=m2   [m1, v2, v1]       GET всё ещё 404

Удаление только m2 не восстанавливает v2: под ним остаётся m1. Нельзя автоматически удалять все обнаруженные маркеры ради появления тела — это уже новые изменения состояния, которые могут нарушить намерение другого клиента. Сначала выясняют, требовалось скрыть текущий ключ, сохранить историю или окончательно убрать конкретную версию. Затем выбирают только те изменения, которые соответствуют этой задаче.

Для проверки истории AWS предоставляет ListObjectVersions, отдельную операцию с разрешением s3:ListBucketVersions. Она возвращает записи Version и DeleteMarker с key, version ID, LastModified и IsLatest. Prefix отбирает начало ключа, поэтому результат дополнительно фильтруют по точному ключу, включая его пробел, плюс и процент. При усечённой странице продолжают с обеими возвращёнными метками NextKeyMarker и NextVersionIdMarker. Страницы, полученные при параллельных изменениях, нельзя считать единым снимком всей истории: такую гарантию здесь не предполагаем. Helper v1 историю не перечисляет. ListObjectVersions.

Один 404 текущего GET после потерянного DELETE не сообщает, сколько маркеров создано и кто их создал. У простого DELETE из этого примера нет operation-id в новой записи-маркере. Набор ID и времени из истории может помочь сопоставлению с внешним журналом, но сам по себе не устанавливает автора запроса. После потерянного ответа на DELETE выбранной обычной non-null версии проверяют наличие именно этого ID, а не только текущего ключа; отсутствие ID показывает наблюдаемое состояние, но не доказывает, какая из конкурировавших операций его удалила.

В корзине без versioning повтор DELETE ещё опаснее для конкурирующей новой записи: первый DELETE мог убрать v1, другой клиент мог записать v2, а повтор простого DELETE уберёт уже v2. В Suspended ту же проблему нельзя решить запоминанием ID null, потому что его слот изменяем. AWS также описывает условный DELETE с If-Match для general purpose buckets; он сравнивает ETag, но не превращает эту метку в уникальный номер события. В helper v1 такого маршрута нет. Потерянное подтверждение поэтому разбирают через требуемый результат, выбранную версию, доступные сведения и возможную конкуренцию, а не через слепой повтор метода.

Что переносится на совместимый endpoint

Вымышленные HTTP-сообщения показывают формат запроса и различие текущего ключа, выбранной версии и локального файла. Правила versioning, условий, маркеров и согласованности выше взяты из документации AWS для general purpose buckets. Для MinIO или RGW название S3 API не подтверждает каждый из этих результатов: проверяют конкретную принятую версию сервера, настройку корзины, учётную запись и поддерживаемые checksum. Параметр backend helper только выбирает конфигурацию цели.

Исходники helper v1 предусматривают put, head и get; PUT ограничен одним телом до 64 MiB и требует create-only либо If-Match. GET запрашивает полный объект, предел N и новое имя output. Подготовленные HTTP-примеры DELETE, перечисление истории и условный GET не расширяют этот интерфейс. Если endpoint не принимает выбранную checksum или условие, результат сохраняют как ошибку этого режима. Убирать условие или незаметно отключать проверку ради успешного ответа означало бы выполнить уже другой опыт.
