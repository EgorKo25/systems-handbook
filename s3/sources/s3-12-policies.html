Кто вправе читать, заменять и удалять

У приложения есть ключ доступа, но оно всё равно получает AccessDenied. Разберём, какое действие оно просит разрешить, к какому ресурсу относится запрос и почему разрешение списка не заменяет разрешения чтения.

От проверенной подписи к решению о доступе

Подпись из главы 06 позволяет проверить подписанные части запроса и связать его с учётными данными. Затем служба решает, разрешено ли действие. Principal — субъект обращения: например, IAM role, роль AWS, сеанс которой использует приложение. Policy, политика доступа, — документ с правилами разрешения или запрета. Правило относится к действию, ресурсу и, при необходимости, условиям запроса.

В AWS политика, прикреплённая к роли, называется identity-based: она задаёт права этого субъекта. Bucket policy прикреплена к корзине и является resource-based; она также указывает субъекта в Principal. Наш следующий документ — первый вид. В нём нет Principal, поскольку субъект выбирается прикреплением документа к отдельной учебной роли. Не вставляйте этот текст как bucket policy.

При оценке прав AWS учитывает применимые политики; явный Deny имеет преимущество над Allow. Для обычной роли без подходящего разрешения действие запрещено. Одного найденного Allow недостаточно для разбора всех ситуаций: ограничения организации, permissions boundary роли, session policy и политики ресурсов тоже могут участвовать. Это причина проверять конкретный principal и ресурс, а не искать слово Allow во всех JSON. Полная логика описана в IAM: policy evaluation.

Здесь IAM — служба AWS Identity and Access Management. Совместимый сервер может распознавать похожий JSON, но иметь другой набор действий и условий. Работу политики AWS нельзя переносить на MinIO или RGW только по совпадению синтаксиса.

Два ресурса для одного приложения

Пусть учебная корзина уже создана и называется study-reports-20261102. Приложению принадлежат только ключи с префиксом lessons/. Оно должно записывать новые тела, читать текущие и выбранные версии, получать список своего префикса. Удаление, изменение настроек корзины и выдача чужих прав ему не нужны. Это отдельная от администратора роль; облачная консоль для её работы не требуется.

ARN, Amazon Resource Name, — строковое имя ресурса AWS. У корзины и объектов разные ARN: arn:aws:s3:::study-reports-20261102 обозначает корзину, а суффикс /lessons/* — множество объектных ключей. Звёздочка здесь символ шаблона политики, не часть ключа. Дата Version задаёт редакцию языка IAM, а не срок действия разрешения.

Документ ниже — конкретный шаблон для этой роли в собственном аккаунте. Перед прикреплением замените имя корзины в обоих Resource на своё принятое имя. Изменение политики выполняет администратор через IAM; helper object-study не устанавливает политики.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOwnPrefix",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::study-reports-20261102",
      "Condition": {
        "StringLike": {"s3:prefix": ["lessons/", "lessons/*"]}
      }
    },
    {
      "Sid": "ReadWriteOwnObjects",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:GetObjectVersion", "s3:PutObject"],
      "Resource": "arn:aws:s3:::study-reports-20261102/lessons/*"
    }
  ]
}

Sid — удобная метка правила. Effect говорит Allow; Action называет разрешённые действия. Первое правило действует на корзину: ListObjectsV2 с prefix=lessons/ удовлетворяет StringLike. Запрос списка с пустым prefix этому правилу не удовлетворяет. Второе правило относится к объектам: lessons/a разрешён, private/a — нет. Для HEAD текущего объекта используется разрешение GetObject, а для обращения к указанной версии — GetObjectVersion.

Условие s3:prefix проверяет параметр списка. Оно само по себе не ограничивает GET: у GET нет такого параметра. Именно второе Resource ограничивает объектные операции нужным префиксом. Официальные примеры identity-based policies S3 показывают разделение объектных и корзинных действий. Дополнительные полномочия для навигации консоли здесь намеренно не выдаются.

Нет разрешения DeleteObjectVersion — приложение не должно уничтожать сохранённые редакции. Нет ListBucketVersions — оно не может исследовать всю историю по этому документу. Эти действия при необходимости получает отдельный оператор восстановления. Прикладное правило create-only остаётся в клиенте; данный Allow для PutObject сам по себе не запрещает другому клиенту той же роли выполнить безусловный PUT.

Как проверить правило, не расширяя его вслепую

Сначала подготовьте объект lessons/access-test, запишите его version ID и SHA-256. Проверки ниже относятся к отдельной роли с этим единственным разрешением, без дополнительных Allow и Deny. Это ожидаемые решения политики, а не записанные ответы работающего стенда.

Запрос ролиОжидаемое решение и причина
GET lessons/access-testРазрешён вторым правилом.
GET той же сохранённой версииРазрешён GetObjectVersion; версия должна существовать.
GET private/access-testНет подходящего объектного Resource.
ListObjectsV2 prefix=lessons/Разрешён первым правилом.
ListObjectsV2 prefix=""Условие первого правила не выполнено.
DELETE с versionIdНет DeleteObjectVersion.

Успешное решение о доступе ещё не означает успешную операцию: условный PUT может вернуть 412, объект — отсутствовать, версия — быть delete marker. Для реальной проверки записывают действие, ресурс, HTTP status, request ID и очищенную квитанцию. Не сохраняют Authorization, session token или подписанный URL. Для ошибочного GET нельзя по одному 403 заключать, что ключ существует: GetObject связывает ответ на отсутствующий ключ с наличием ListBucket.

В клиенте v1 нет команды списка. Его put/head/get пригодны для объектных строк этой таблицы после подготовки собственного endpoint. Остальные проверки выполняет администратор принятым инструментом AWS или своей реализации; не нужно придумывать подкоманду list у object-study.

Почему разрешённый GET может не расшифроваться

TLS защищает передачу между клиентом и endpoint. Server-side encryption, шифрование на стороне службы, относится к сохранённым данным. SSE-S3 использует ключи, которыми управляет S3; SSE-KMS использует AWS Key Management Service, отдельную службу управления ключами. Эти механизмы решают другую задачу, чем SigV4.

Для SSE-KMS разрешение S3 не заменяет разрешений KMS: запись требует GenerateDataKey, чтение — Decrypt; для multipart нужны оба. Доступность нужного ключа и его policy входят в путь восстановления. Нельзя объявить резервную копию пригодной, проверив только список ключей S3. См. SSE-KMS: permissions. Helper не передаёт новые флаги KMS: шифрование его цели определяется принятой конфигурацией корзины.

Частная корзина и отдельная учётка очистки

Для учебной цели сохраняют Block Public Access и не добавляют публичный Principal "*". Block Public Access ограничивает публичные разрешения; он не даёт приложению недостающий Allow. Современная настройка Bucket owner enforced отключает ACL; не нужно добавлять заголовок ACL ради исправления AccessDenied. ACL — исторический список доступа к объекту, отличный от разобранных политик.

Учётка уборки с правом удаления версий хранится отдельно от приложения. Администратор проверяет правила Lifecycle — автоматических переходов и удаления по возрасту. Bucket policy с Deny удаления не является выключателем Lifecycle: AWS отдельно предупреждает, что такие действия не отменяются этой политикой. Поэтому восстановление зависит и от настроек срока хранения, рассмотренных в следующей главе. См. bucket policies и Lifecycle.

После опыта не выдавайте роли AdministratorAccess, чтобы «всё заработало». Сопоставьте отказ с конкретным действием, ARN, условием и субъектом. После исправления повторите разрешённый запрос и соседний запрещённый: успешный lessons/a при всё ещё запрещённом private/a показывает, что исправлено именно нужное правило.
