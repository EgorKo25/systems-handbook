Повторяемые опыты: сохранить состояние и объяснить результат

Выполним операции на маленькой модели одного ключа, сохраним каждое состояние и сравним видимое клиенту с полной историей. Затем проверим байты, диапазоны и план большой загрузки.

Что запускается

storage_models.py — исходный Python-скрипт из labs. Он использует только стандартную библиотеку, не открывает соединений и не записывает файлы. Файлы в упражнениях создаёт перенаправление вашей оболочки. Модель не эмулирует IAM, сеть, диски, SDK retry или все ошибки AWS; её status — выбранный модельный ответ, не полученный HTTP-пакет.

State хранит историю одного синтетического ключа. enabled добавляет отдельные ID v0001, v0002; suspended заменяет буквальную null-version; unversioned хранит только текущее тело. Эти простые имена выбраны для чтения: настоящий version ID непрозрачен. Поле body_base64 хранит тело как Base64 в JSON. Модельный ETag с префиксом toy- — собственная метка, не правило вычисления ETag сервера.

Каждая команда выводит JSON и завершается кодом 0 при успехе. Ошибка входа и неуспешная assert-проверка завершают процесс ненулевым кодом. Assert проверяет булево выражение и при ложном результате возбуждает AssertionError. Python -O, -OO или PYTHONOPTIMIZE могли бы удалить assert; guard по __debug__ прекращает такую работу до объявления PASS. Поэтому используйте приведённый обычный запуск без оптимизации.

Сначала запустите полную проверку модели из корня исходников книги. -B запрещает запись bytecode; check выполняет все шесть групп и печатает checks: PASS: pure teaching models. Большой multipart fixture создаётся блоками в памяти, а не файлом на диске.

python3 -B s3/labs/storage_models.py check

Отдельно воспроизводятся прежние модели: sigv4_vectors.py пересчитывает подпись, object_operations.py проверяет переходы из главы 07. Их запуски тоже не отправляют запросов.

python3 -B s3/labs/sigv4_vectors.py
python3 -B s3/labs/object_operations.py

Эти программы проверяют математические и программные утверждения на синтетических входах. Успех не означает успешной сборки Go helper, проверки сертификата или приёмки AWS/MinIO/RGW.

Опыт 1: PUT завершился, ответ потерян

Используйте лабораторный каталог из главы 03. Все имена ниже новые. Bash set -C включает noclobber: перенаправление > отказывает, если файл уже существует. Не отключайте его ради повторного запуска поверх сохранённой истории. Если имя занято, выберите другой префикс для всего опыта. Состояние модели не содержит credentials.

state-init создаёт документ с schema_version, state и result. --mode выбирает модель versioning. Документ сохраняется в первый файл; сервер здесь не создаётся.

LAB="$HOME/object-study-lab"
set -C
python3 -B s3/labs/storage_models.py state-init --mode enabled > "$LAB/receipts/model-00.json"

У state.history ожидается пустой список, next_id=1, result=null. Перед следующим шагом откройте этот JSON. Введите запрос путём --event: op называет модельное действие, body — строку, condition=create требует отсутствия текущего тела, operation_id связывает наши наблюдения, lose_reply=true скрывает ответ после изменения модели. Два знака backslash-n внутри JSON кодируют один LF после разбора.

python3 -B s3/labs/storage_models.py state-step --event '{"op":"put","body":"object-lab v1\n","condition":"create","operation_id":"op-a","lose_reply":true}' < "$LAB/receipts/model-00.json" > "$LAB/receipts/model-01.json"

Стандартный ввод читает предыдущий документ целиком; стандартный вывод даёт новый. Так опыт можно продолжить после закрытия терминала. Во втором файле история уже содержит v0001, но result.outcome=unknown и status=null. Это полная учебная картина. Настоящий клиент, потерявший ответ, не получает такую внутреннюю историю в своей квитанции.

Предскажите следующий результат. Повторяем ту же create-only запись и тот же operation ID, но теперь не теряем ответ. Условие не снимается.

python3 -B s3/labs/storage_models.py state-step --event '{"op":"put","body":"object-lab v1\n","condition":"create","operation_id":"op-a"}' < "$LAB/receipts/model-01.json" > "$LAB/receipts/model-02.json"
Разбор

Статус отдельного модельного запроса равен 412, result.scope=single_model_request, история не изменилась. Поле rejected относится только к этому явно рассмотренному запросу модели. Исход всей логической операции клиента после потерянного ответа остаётся unknown: в настоящем receipt PUT mapper не заменяет его на rejected по последнему 412. Нужна сверка состояния, а не безусловная перезапись.

В модели мы знаем ID v0001. Получим его и сравним байты с намерением. В реальной системе такой ID сначала надо получить из достоверного ответа либо найти в истории отдельным инструментом.

python3 -B s3/labs/storage_models.py state-step --event '{"op":"get","version_id":"v0001"}' < "$LAB/receipts/model-02.json" > "$LAB/receipts/model-03.json"

Ожидаются status=200, operation_id=op-a, bytes=14 и sha256_hex=874160ebe2d9a6a82abdec1966f3be5be4e0db5d575d4d00953c66baf6e30897. Совпадение показывает наблюдаемую версию с нужными признаками. Оно не обещает единственность бизнес-операции и не заменяет durable intent: helper до отправки не сохраняет намерение в отдельный постоянный журнал.

Опыт 2: повтор DELETE изменил историю

Теперь удалим текущий ключ в Enabled-модели с потерянным ответом и повторим DELETE. Удаление не содержит version_id, поэтому каждый запрос добавляет свой marker. Оба шага сохраняют отдельные документы.

python3 -B s3/labs/storage_models.py state-step --event '{"op":"delete","lose_reply":true}' < "$LAB/receipts/model-03.json" > "$LAB/receipts/model-04.json"
python3 -B s3/labs/storage_models.py state-step --event '{"op":"delete"}' < "$LAB/receipts/model-04.json" > "$LAB/receipts/model-05.json"

Проверьте порядок history: v0003 marker, v0002 marker, v0001 data. Далее убираем только последний marker по ID; это другая операция, чем DELETE текущего ключа.

python3 -B s3/labs/storage_models.py state-step --event '{"op":"delete","version_id":"v0003"}' < "$LAB/receipts/model-05.json" > "$LAB/receipts/model-06.json"
python3 -B s3/labs/storage_models.py state-step --event '{"op":"get"}' < "$LAB/receipts/model-06.json" > "$LAB/receipts/model-07.json"
Почему обычный GET всё ещё не вернул тело

Текущим остался v0002 marker, поэтому модель даёт 404. Удаление одного marker не означает, что под ним сразу data version. GET с version_id=v0001 всё ещё может прочитать сохранённые байты. В реальном AWS ответы зависят также от прав; модель не проверяет IAM. Нельзя применять эту последовательность к рабочей корзине по одним красивым ID из учебного примера.

Проверьте отрицательный вход: поменяйте имя поля version_id на versionId. Скрипт должен отказать как неизвестному полю. Такой отказ проверяет формат нашей модели; он не сообщает ничего о формате AWS query, где как раз используется versionId.

Опыт 3: одинаковый ID, разные байты

Режим scenarios печатает готовые состояния для потерянного PUT, двух markers и Suspended-модели. Он нужен, чтобы сверить решение до ручного редактирования событий.

python3 -B s3/labs/storage_models.py scenarios

Сравните null_version_before и null_version_after: ID в обоих случаях "null", но body_base64, operation_id и ETag изменились. Вторая запись использует condition=match с прежней модельной меткой. Совпадение строкового ID не фиксирует неизменное тело. JSON null, отсутствие значения, по-прежнему отличается от строки "null".

Для самостоятельного продолжения создайте отдельный state-init --mode suspended, выполните первый PUT с condition=create, затем второй с condition=match и фактическим etag из первого JSON. Скопируйте кавычки ETag как часть JSON-строки с экранированием. Подмена его на "wrong" должна дать 412 и оставить history побайтно прежней после сериализации в том же формате. После DELETE null data удаляется и остаётся null marker; обычный GET её не возвращает.

Опыт 4: одинаковая длина не гарантирует нужное тело

checksums сравнивает исходные 14 байтов, 15 после замены LF на CRLF и 13 после удаления LF. ranges проверяет bytes=0-5, начало 14 за концом, последний байт и суффикс длины один. Сначала выпишите ожидаемые длины, затем запускайте.

python3 -B s3/labs/storage_models.py checksums
python3 -B s3/labs/storage_models.py ranges

В выводе ranges mixed_same_length — склейка первых шести байтов v1 и остатка другого четырнадцатибайтового тела OBJECT-LAB V2 с LF. Получившаяся длина равна 14, но SHA-256 не совпадает ни с одним полным исходным телом. Клиент должен связать диапазоны с одной версией и проверить полный ожидаемый хеш. Сам предел max-bytes=14 этого не делает.

Для сетевого object-study повторите принятый GET из главы 04 в новое имя. Затем попросите тот же ключ с --max-bytes 13 и другим новым output. Успех не ожидается: либо отказ по известной длине, либо обнаружение лишнего байта. Отсутствие итогового имени проверяется отдельно от кода. Если оно уже существовало до опыта, клиент обязан его сохранить.

Обрыв и checksum error проверяют при приёмке с управляемым источником Body либо принятым стендом с отказом. Вручную убивать произвольную VM для этого упражнения не требуется. Важно увидеть, что частичный файл не публикуется как принятая копия. Локальный сбой sync каталога после публикации — отдельный случай, в котором конечное имя уже может существовать.

Опыт 5: части, страницы и расходы

multipart пересчитывает 17 MiB по формуле byte[i]=i mod 251, три части и их Base64 SHA-256. Сверьте offsets 0/8388608/16777216 и длины 8388608/8388608/1048576. Состояние показывает, что part 1 с новым ETag заменяет старый part 1 того же upload, а завершение использует новый ETag. Флагов multipart у helper нет.

python3 -B s3/labs/storage_models.py multipart
python3 -B s3/labs/storage_models.py listing
python3 -B s3/labs/storage_models.py budget

В listing неподвижный набор даёт две страницы: [a/1,a/2], затем [a/sub/3]. С delimiter=/ последняя запись становится CommonPrefixes a/sub/, а не третьим телом в Contents. Поле toy_index_mutation_duplicate показывает проблему простого индексного обхода при вставке до текущей позиции. Это не алгоритм непрозрачных ContinuationToken AWS и не записанный ответ S3.

В budget проверьте, что повтор части увеличил загрузку на 8388608 байтов и количество API-вызовов с проверкой с 7 до 8. Не прибавляйте к этому «ещё 17 MiB чтения» дважды: в upload_bytes оно вообще не включено. Если оцениваете полный сетевой опыт, GET добавляется отдельно. Полученный расчёт сравнивают с объявленным составом операций, не с неизмеренным throughput сервера.

Что сохранить после упражнений

Оставьте исходные Python/Go sources, версии runtime и SDK, JSON каждого перехода и результаты хеширования. Для native-части добавьте очищенные receipts, режим checksum, TLS/endpoint и фактический build list. Эти данные позволяют другому читателю повторить именно опыт, а не догадаться о параметрах по последнему скриншоту.

Уборка адресная. Модельные JSON удаляются только по собственным именам. В настоящем versioned bucket текущий список не показывает всю историю: оператор отдельно сверяет versions/delete markers и незавершённые uploads своего префикса. Object-study их не перечисляет и не удаляет. Если доступно только чтение, оставьте владельцу точную ведомость; не просите расширенный доступ ко всей корзине ради удобства уборки.

Завершённое упражнение содержит предсказание, сохранённые входы, фактический результат и объяснение расхождения. Unknown остаётся допустимым фактическим результатом до установления нужного состояния. Его нельзя превратить в подтверждённое отсутствие записи правкой отчёта.
