Multipart: части, незавершённая загрузка и публикация объекта

Передадим 17 MiB тремя частями, сохраним upload ID и отличим принятые части от завершённого объекта.

Зачем делить передачу

Обычный PUT передаёт тело в одной операции. После сетевого отказа большой передачи повторение может снова прочитать весь source. Multipart upload — протокол, в котором сервер хранит части одной незавершённой загрузки. Клиент может повторить одну часть и загрузить несколько частей параллельно. Он также должен управлять upload ID, результатами каждой части и отдельным завершением.

В AWS выбранные part numbers находятся в диапазоне 1..10000; размер части от 5 MiB до 5 GiB, последняя может быть меньше 5 MiB. MiB = 1048576 байтов, GiB = 1073741824 байта. Лимиты и поддержанные checksum-режимы проверяются по выбранной службе. Наш объект мал для практической необходимости multipart: 17 MiB выбраны для наблюдаемой арифметики и трёх частей.

Однозначные исходные байты

В позиции i, начиная с нуля, байт равен i mod 251 — остатку деления i на 251. Значения 0..250 повторяются; это бинарное тело, не текст UTF-8. Общий размер 17×1048576=17825792 B. Разбиение сохраняет непрерывные интервалы исходного тела, без повторения первого шаблона с нуля в каждой части.

Три фазы протокола

  1. CreateMultipartUpload: POST с query uploads. Сервер возвращает UploadId. При создании задаются metadata и режим checksum будущего объекта. Клиент сохраняет bucket, key, upload ID и параметры до последующих действий.
  2. UploadPart: PUT с query partNumber и uploadId. Тело — выбранная непрерывная часть source. Успех части возвращает её ETag и выбранный checksum. Это подтверждение части конкретной загрузки, ещё не GET текущего объекта.
  3. CompleteMultipartUpload: POST с uploadId и XML-перечнем выбранных part numbers, ETag и необходимых checksum. Части в перечне идут по возрастанию номеров; наш профиль использует последовательные 1,2,3. Успех сборки создаёт объект.

Ниже показаны только имена операций и структурные поля. UPLOAD и E1..E3 — непрозрачные синтетические значения, не настоящие токены. Это не готовые неподписанные сетевые команды. Каждый фактический запрос требует своей SigV4, тела, региона, адреса и разрешений. Object-study v1 multipart не реализует.

CreateMultipartUpload:
  POST /study-s3/large.bin?uploads
  metadata operation-id = synthetic-op
  response: UploadId = UPLOAD

UploadPart:
  PUT /study-s3/large.bin?partNumber=2&uploadId=UPLOAD
  body: bytes [8388608,16777216)
  response: ETag = "E2"

CompleteMultipartUpload:
  POST /study-s3/large.bin?uploadId=UPLOAD
  parts: [(1,"E1"), (2,"E2"), (3,"E3")]

Квадратные/круглые границы [a,b) в записи интервала означают включённое начало и исключённый конец: длина второй части 16777216−8388608. Query кодируется по исходным строкам, а не конкатенацией непрозрачного upload ID в URL. Старое Authorization после изменения partNumber использовать нельзя.

Что меняется при повторе части

Часть с номером 2 внутри того же upload ID можно загрузить повторно: поздняя успешная загрузка этого номера заменяет прежнюю часть. Клиент должен сохранить новый ETag. Если параллельно повторить один номер с разными байтами и затем завершить по случайно сохранённому ответу, можно выбрать не ту версию части или получить InvalidPart. Уникальность логической операции и неизменяемость source важны до распараллеливания.

После потерянного ответа UploadPart список частей помогает увидеть принятый номер, но для reconciliation сопоставляются размер и предусмотренные checksums, а не один номер. ListParts также разбит на страницы. Не считайте первый список полным, если ответ требует продолжения. Для Complete используйте собственный проверенный перечень результатов частей; обновление списка и завершение не образуют одну транзакцию.

HTTP 200 и незавершённая сборка

CompleteMultipartUpload может начать ответ с 200 и передавать пробелы, пока работает. Ошибка может прийти в XML-теле после этого начала. Нужно дочитать и разобрать результат операции. SDK, поддерживающий эту ветку, выполняет её сам; произвольная программа, считающая успехом только строку статуса, ошибётся.

Если ответ полного завершения потерян, текущий объект мог уже появиться. Повтор Complete может увидеть отсутствие upload ID; это не доказывает, что сборка не прошла. Проверьте версию и метаданные опубликованного объекта, полный размер и хеш. Условие If-None-Match или If-Match при Complete относится к состоянию конечного ключа; оно не добавляет транзакцию между загрузкой частей и чужими PUT. При конкурентном конфликте AWS различает ветки повторения: для Complete при определённых 409 требуется начать новую multipart загрузку, а не бесконечно повторять старый upload ID.

Отмена и оплата промежуточного состояния

AbortMultipartUpload прекращает выбранную незавершённую загрузку. Перед ним остановите или дождитесь работников UploadPart. Уже выполняющиеся части могут завершаться во время abort; для освобождения всех частей может потребоваться повторная адресная проверка и отмена по правилам AWS. Удаление текущего объекта само по себе не является отменой другого upload ID.

За сохранённые незавершённые части возможна плата, пока загрузка не завершена или не отменена. Правило Lifecycle AbortIncompleteMultipartUpload позволяет управлять забытыми загрузками; это не синхронная команда приложения. В журнале сохраняйте upload ID до подтверждённого завершения либо очистки. Не отменяйте все найденные uploads общего bucket: другой клиент мог продолжать полезную работу.

Цена параллелизма

Для трёх частей без повторов нужны минимум пять запросов: create, три part PUT и complete. Проверка HEAD+GET добавляет ещё два. Повтор одной 8 MiB части увеличивает переданные прикладные байты с 17 до 25 MiB, хотя финальный объект по-прежнему 17 MiB. Четыре workers с буфером 8 MiB могут потребовать около 32 MiB буферов только под части; SDK и TLS добавят свои расходы. Это расчёт бюджета памяти, а не измерение RSS.

Контролируйте число одновременно незавершённых запросов, лимиты файлов и общий deadline. Десять тысяч частей по одному worker не означают десять тысяч соединений. Сравнение производительности с одним PUT должно иметь одинаковое содержимое, checksum и критерий завершения.
