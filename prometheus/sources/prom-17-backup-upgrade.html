Резерв, удаление, восстановление и обновление

Перезапуск, snapshot, резервная копия и rollback решают разные задачи. Проверяем восстановление в отдельном каталоге.

Что входит в состояние

TSDB хранит samples, а конфигурация/правила/служебные параметры определяют их сбор и смысл. Резерв включает согласованную копию данных, YAML/rule files, версию бинарника, параметры запуска, источники зависимостей и права. Внешние credentials хранятся отдельно с доступом по назначению. Потерянная rule definition делает даже сохранённую recording series менее объяснимой. Набор файлов с диска ещё не является проверенным резервом, пока вы не восстановили и не запросили известный диапазон.

Snapshot через явное административное разрешение

Параметр запуска нельзя добавить уже работающему процессу отправкой запроса. Для ручного стенда сначала запишите его текущие аргументы и исторический запрос, штатно остановите сервер, затем запустите тот же каталог данных с дополнительным флагом ниже. Запуск остаётся на переднем плане; обе команды curl выполняются из второго терминала после успешной readiness-проверки. Если вы ранее перешли к systemd, изменяйте аргументы своей службы и перезапускайте её с прежним /var/lib/prometheus: ручной пример с data иначе откроет старую копию истории. Не включайте административный API на другом экземпляре по ошибке.

bin/prometheus --config.file=config/prometheus.yml --storage.tsdb.path=data --web.listen-address=127.0.0.1:9090 --storage.tsdb.retention.time=7d --web.enable-admin-api

Во втором терминале начните в том же prom-lab. Сначала сохраните ответ snapshot с head; отдельный файл для skip_head не позволит случайно подставить его вместо полного снимка. При неуспешном curl не переходите к следующему шагу. Последующие команды используют Python 3 только для чтения JSON-ответа, не для доступа к TSDB.

curl --fail --request POST --output evidence/snapshot-head.json http://127.0.0.1:9090/api/v1/admin/tsdb/snapshot
cat evidence/snapshot-head.json
curl --fail --request POST --output evidence/snapshot-no-head.json 'http://127.0.0.1:9090/api/v1/admin/tsdb/snapshot?skip_head=true'
cat evidence/snapshot-no-head.json

Первый запрос по умолчанию включает head; второй явно пропускает последние ещё не оформленные в обычные блоки данные. Сравните полученные временные границы на копиях: экономия времени/места имеет цену потери свежего интервала. API возвращает имя snapshot в data/snapshots/. Снимок использует локальное хранение и может опираться на hard links для блоков; утрата этого же устройства уничтожит и его. Скопируйте завершённый snapshot в другое хранилище и проверьте доступность/целостность.

Без --web.enable-admin-api запрос должен отказать; это ожидаемая проверка. Флаг добавляет и опасные административные действия, поэтому не включается базовым примером. Loopback сам по себе не заменяет доверие ко всем локальным процессам. --web.enable-lifecycle управляет другим набором endpoints и не равен admin API. Сравнение флагов подтверждается prometheus --help выбранной версии, а контракт snapshot — HTTP API3.13.

После получения и проверки копий штатно остановите этот ручной процесс и верните команду первого запуска с теми же config/data, loopback и retention 7d, убрав только --web.enable-admin-api. Затем дождитесь readiness и повторите исторический запрос. Если административный доступ оставлен осознанно, зафиксируйте это как отдельную настройку стенда. Для systemd меняют профиль и перезапускают свою службу; ручную копию параллельно не запускают.

Восстановление и точка возврата

Следующий опыт относится к ручному prom-lab/data того же обычного пользователя. Для перенесённой systemd-базы сначала получите её snapshot и согласованные права отдельно: не подменяйте путь молча. Здесь ещё нет процесса восстановления. Создадим отдельный restore-data и конфигурацию без scrapes, rules, remote_write и уведомлений. Файл evidence/snapshot-head.json получен предыдущим запросом; поле data.name называет каталог внутри data/snapshots, а не новый путь основной базы.

Начните во втором терминале в prom-lab. Блок выполняется в дочерней оболочке: явный отказ прерывает подготовку, основной сервер продолжает работать. Непустой прежний опыт не перезаписывается: если restore-data или новый config уже есть, сначала осмотрите их и выберите новое имя во всех последующих командах. После частичного сбоя копирования этот блок намеренно не продолжит поверх оставшегося каталога.

(
snapshot_name=$(python3 -c 'import json,sys; r=json.load(sys.stdin); assert r["status"]=="success"; n=r["data"]["name"]; assert isinstance(n,str) and n not in ("",".","..") and "/" not in n and "\\" not in n and not any(c.isspace() for c in n); print(n)' < evidence/snapshot-head.json) || exit 1
test -d "data/snapshots/$snapshot_name" || exit 1
test ! -e restore-data || exit 1
test ! -e config/restore-empty.yml || exit 1
mkdir restore-data || exit 1
cp -a "data/snapshots/$snapshot_name/." restore-data/ || exit 1
printf 'global:\n  scrape_interval: 15s\nscrape_configs: []\n' > config/restore-empty.yml || exit 1
bin/promtool check config config/restore-empty.yml || exit 1
)

После успешного завершения блока в том же cwd запустите восстановленную копию на переднем плане. Порт 19090 должен быть свободен; основной процесс остаётся на 9090. Параметр retention.time=7d ограничивает и эту копию: для старого резерва выбирают срок, сохраняющий нужный исторический диапазон, до запуска.

bin/prometheus --config.file=config/restore-empty.yml --storage.tsdb.path=restore-data --web.listen-address=127.0.0.1:19090 --storage.tsdb.retention.time=7d

В третьем терминале из prom-lab выполните bin/promtool check ready --url=http://127.0.0.1:19090, затем повторите тот же исторический query и time, которые записали до snapshot, заменив в URL только 9090 на 19090. Например, в команде из главы времени сохраняются --data-urlencode 'query=…' и --data-urlencode 'time=…'; многоточия здесь обозначают ваши записанные аргументы, не готовую команду. Сверьте полный набор labels, sample timestamp и value из data.result, а не время получения HTTP-ответа. Пустой result не считается успехом восстановления ненулевого ряда.

Критерий опыта — совпадение заранее выбранного результата и readiness новой копии при отсутствии её targets. Остановите только foreground-копию на 19090 через Ctrl+C и дождитесь её выхода. restore-data, evidence и основной data сохраняются. Ни один шаг не запускает два сервера на одном каталоге и не отправляет внешних уведомлений.

Альтернатива — штатно остановить сервер и скопировать весь data directory без конкурентных изменений, затем проверить копию. Произвольное копирование файлов работающей TSDB может застать несогласованное состояние; исключение WAL/head даёт согласованные закрытые блоки ценой свежести согласно storage docs. Memory snapshot при shutdown и административный snapshot для резерва — разные механизмы. Откат не выполняется автоматически: читатель явно выбирает snapshot и признаёт утрату более позднего интервала.

Удаление не является редактированием каждого файла

Delete series API с admin flag помечает интервалы tombstones; физическое освобождение может ждать compaction/clean_tombstones. Удаление по слишком широкому matcher затронет много исторических рядов. Команда не возвращает данные назад; возврат только из подходящего резерва и с учётом новых данных. Не публикуем шаблон удаления «всего» как способ начать упражнение: последовательный стенд сохраняет историю. Для одноразового теста удаляется только собственный временный каталог после завершения процессов.

Обновление как контролируемое изменение формата и поведения

Зафиксируйте текущую версию, аргументы, размер данных и baseline запросов; прочитайте release/migration notes целевой версии. Сохраните конфигурацию и согласованный резерв, проверив восстановление. Проверьте новым promtool YAML/fixtures, затем запустите новый бинарник на копии данных без внешних действий. Сверьте ready/replay, известные queries, native compatibility, rules и warnings. Лишь затем меняйте основной экземпляр своей VM. latest не задаёт воспроизводимый upgrade path.

Rollback бинарника поверх данных, уже записанных более новой версией, не обещан автоматически: TSDB features и WAL encoding могут измениться. Безопасная точка возврата — старый бинарник плюс сохранённая совместимая копия состояния до обновления; новые samples после неё требуют отдельного решения. Перед миграцией 3.x из 2.x особенно читают migration guide. Два бинарника одной архитектуры могут запускаться, но это не доказательство одинакового смысла запросов.
