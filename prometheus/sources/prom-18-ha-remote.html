HA, remote write/read и границы локального сервера

Независимое наблюдение повышает доступность, но не создаёт общую TSDB и не гарантирует отсутствие потерь.

Две копии — два независимых наблюдения

HA, high availability, высокая доступность, для пары Prometheus обычно означает два самостоятельных сервера, которые опрашивают одни targets, вычисляют rules и хранят собственные данные. Между ними нет встроенного согласования append или репликации локальных blocks. Scrape times отличаются; один может пропустить sample, другой нет. Общий NFS-каталог data для двух процессов не превращает их в кластер и нарушает модель эксклюзивного доступа. У каждого свои диски/каталоги и параметры отказа.

External labels, например cluster=home и replica=a/b, помогают внешнему хранилищу различить источники. Deduplication, устранение дублирующих наблюдений, выполняет поддерживающая это внешняя система по своему контракту replica labels и выбора samples. Простое суммирование обоих экземпляров удвоит requests/s; среднее не восстановит пропуски и выравнивание. Для alert delivery replica label также должна быть согласована с договором Alertmanager, иначе одинаковый symptom может стать двумя разными alert identities. Это отдельная настройка, не побочный эффект запуска второго сервера.

Remote write: от WAL к сети

Remote write передаёт samples/metadata во внешнее совместимое хранилище. Локальный процесс читает журнал, распределяет работу по очередям/shards, кодирует и отправляет batches; receiver подтверждает/отказывает согласно протоколу. Shard здесь — часть параллельной передачи, не локальный TSDB partition с независимым ownership. Backpressure, обратное давление, возникает, когда приёмник или сеть медленнее производителя: очередь растёт, reader отстаёт, задержка increases. Локально доступная метрика не обязана уже присутствовать в remote destination.

Наблюдайте отправленные/неуспешные/повторные samples, pending, shard count, queue latency и разность актуального времени и highest sent timestamp; точные имена проверьте на /metrics своей версии. Различайте retries от retryable failures и окончательный reject из-за неподдерживаемого типа/невалидных labels/допустимого возраста. Успех HTTP не доказывает долговечность receiver сверх его контракта. Native histograms, exemplars и remote write1.x/2.x требуют совместимости обеих сторон; переименование message type не добавляет приёмнику поддержку.

Расчёт задержки и потери

Условный producer даёт 400 samples/s, сеть не работала 10m: backlog порядка 240000 samples без учёта metadata. После восстановления receiver принимает 800 samples/s при продолжающемся producer400/s, чистая скорость сокращения очереди 400/s, идеальное время догоняния 10m. Если receiver может только 500/s, чистая 100/s и время 40m. Это оценки без batch overhead, retries и ограничений: узкое место измеряют на реальной паре.

Увеличение capacity/max_shards расходует RAM и сетевые/CPU ресурсы, но не создаёт бесконечного durable буфера. Reader зависит от жизненного цикла WAL и настроек очереди/допустимого возраста; достаточно долгое отставание может потерять ещё не отправленные samples. Нельзя обещать конкретное универсальное окно «ровно два часа гарантировано»: версия, agent/server mode, truncation и настройки влияют на границы. Проверяйте отказ на тестовом receiver и известном диапазоне, а профиль 3.13 сверяйте с remote write tuning и спецификацией 2.0.

Remote read и соседние договоры

Remote read предоставляет storage samples из внешнего источника, а не автоматически переносит весь PromQL engine на receiver. Большой raw выборке по-прежнему нужны сеть, декодирование и память query process; streamed variants меняют транспорт, но не смысл дорогого запроса. Внешние системы могут иметь собственный query frontend и язык/оптимизации — их возможности не следует приписывать самому Prometheus.

Grafana обращается к query/query_range API и передаёт time/step; её переменная или autoscale может изменить стоимость выражения. OTel metrics должны согласовать temporality (cumulative/delta), resource-to-label mapping, единицы и кардинальность; бездумное копирование всех resource attributes создаёт churn. Logs и traces дают контекст отдельных событий, но не делают metrics event log. Agent mode предназначен для сбора/пересылки и имеет другие возможности локального хранения/запросов; его нельзя заменить тем же названием процесса в рецепте полноценного query-сервера.
