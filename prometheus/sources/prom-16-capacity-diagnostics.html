Ёмкость и диагностика: ряды, samples и узкое место

Расчёты задают порядок величины, затем измерения на собственном профиле проверяют предположения.

Кардинальность как произведение допустимых значений

Для 50 экземпляров,8 routes,5 классов code и трёх независимых значений region верхняя оценка counter series —50×8×5×3=6000, если все сочетания действительно возникают. Не каждая label перемножается независимо: если instance однозначно определяет region, фактическое произведение меньше. Classic histogram с 10 конечными границами создаёт 13 series на label set;50×8×13=5200 при labels только instance/route. Добавление code с 5 значениями поднимет оценку до 26000. Сначала проверьте, нужен ли код ответа в latency distribution.

Пусть 6000 стабильных float series собираются каждые 15 секунд: это 6000/15=400 samples/s. Семь суток — 604800 секунд, то есть 241920000 samples. Для учебного расчёта зададим 1.8 bytes/sample только для сжатых данных samples; здесь это не измерение. Произведение равно 435456000 bytes = 435.456 MB ≈ 0.406 GiB. Index, labels, метаданные, WAL/head, native buckets, резерв и место для compaction добавляются отдельно. Измеренный размер всего каталога нельзя назвать размером одного payload: у него другой состав. В GiB делят на 2³⁰, в GB — на 10⁹; смешивать их в лимите нельзя.

Расчёт нужен до нагрузочного опыта, чтобы поймать ошибку масштаба. Затем сравнивают du -sb data на двух состояниях после одинаковых фаз compaction и делят прирост на реально appended samples. WAL может доминировать первые часы, поэтому оценка bytes/sample по первому минутному каталогу неверна для retention30d. RAM также не выводится из единого «байт на sample»: active series, labels, chunks, query working set, Go GC и filesystem cache имеют разную зависимость.

Четыре конкурирующих пути

Высокий CPU может быть regex matching, декодирование chunks, GC или collector; само значение CPU не выбирает лечение. Высокий RSS не доказывает leak. Высокая disk latency при низком throughput может означать мелкие синхронные операции или конкуренцию. Queueing увеличивает tail latency даже при умеренном среднем использовании. Снимите baseline до изменения и меняйте одну причину за опыт; если одновременно уменьшить cardinality, увеличить RAM и изменить interval, результат трудно объяснить.

Запрос с малым ответом и большой ценой

sum(rate(all_requests_total[1h])) возвращает один элемент, но читает данные каждого выбранного series за час. Для 100,000 series при 15s interval это порядка 24 млн входных samples на один момент без учёта оптимизаций; диапазон умножает работу и переиспользование по механике движка. Маленький JSON не означает дешёвый запрос. Narrow matchers, осмысленные окна и recording rules полезнее слепого увеличения timeout. Query concurrency/timeout/max-samples — границы отказа и защиты ресурсов, а не бесплатное ускорение.

Сравните range query на 1h при step 15s и 1m:241 против 61 моментов при выровненных границах. Запишите длительность, response bytes и CPU с одинаковыми входными данными. Если график нужен только для тенденции часа, более частая сетка может не дать полезной информации. Если нужно поймать короткий пик gauge, слишком редкий step его пропустит. Цена детализации привязана к задаче, а не к максимальному разрешению дисплея.

Практическая последовательность отказа

Сначала определите границу: ready ли процесс; успешен ли reload; есть ли target; что говорит last scrape error; есть ли samples; не исключил ли matcher; не пусто ли окно rate; нет ли many-to-many; не мешает ли stale. Затем сравните ресурсы с baseline. promtool tsdb analyze на согласованной копии помогает увидеть labels/churn, query log — реальные выражения и параметры, process metrics — процесс. Не публикуйте полный query log без просмотра: matchers могут содержать чувствительные labels. Метрика нагрузки не является разрешением отключать контроль доступа.
