PromQL I: тип каждого выражения и выбор рядов

Прежде чем считать скорость или процент, определяем набор идентичностей и тип входа.

Четыре типа, а не четыре вида графиков

PromQL — язык выражений: маленькие выражения соединяются операторами и функциями в более крупное. up выбирает метрику, up{job="go-lab"} уточняет набор по метке, а sum(up{job="go-lab"}) вычисляет сумму выбранных значений. Здесь ещё не нужно знать всю библиотеку функций. Сначала научимся отвечать на три вопроса о каждом фрагменте: какие ряды он получает, к какому времени относится результат и какого он типа. Обозначение T ниже — выбранный момент вычисления, а не имя метки или значение температуры.

ТипПримерСмысл на T
Scalar60, time()Одно число без labels.
String"lab"Строковое значение; почти не используется как корень полезного запроса.
Instant vectorup{job="go-lab"}Набор рядов, по одному выбранному значению на ряд.
Range vectorlab_requests_total[5m]Для каждого ряда набор исходных samples внутри окна.

Instant vector не означает «только физически записанные ровно в T точки». Selector может выбрать более ранний sample согласно lookback, но результат вычисления относится к T. Range vector не означает «нарисовать график»: это тип аргумента функции, например rate. Range query API многократно вычисляет scalar/instant-vector выражение; сам metric[5m] не является допустимым корнем range query. Instant query API допускает и range-vector корень для исследования исходного окна.

scalar(vector(7)) даёт 7; vector(7) даёт один элемент instant vector с пустыми labels. scalar(up) даёт число только если вектор содержит ровно один float-элемент, иначе NaN. Это не удобный способ «заставить query работать» при нескольких целях: он меняет семантику и может скрыть неправильную выборку.

Matchers как логика над labels

Для ручной выборки возьмём q{job="api",zone="a"}=10, q{job="api",zone="b"}=20 и q{job="worker"}=30. Условие q{job="api",zone!="b"} оставит только первое. q{zone!="b"} оставит первое и worker без zone. q{zone=""} выберет worker. q{zone=~"a|b"} выберет первые два; regex закреплён на весь label value, поэтому "a" не совпадает с "aa", а ".*a.*" совпадает.

Matchers в одной паре фигурных скобок соединяются логическим И; два условия на одну label тоже применяются одновременно. {job=~".*"} без имени метрики недопустим, поскольку все matchers могут совпасть с пустой строкой. {job=~".+"} допустим, но потенциально выберет много рядов. Сначала исследуйте конкретную метрику и labels, затем расширяйте запрос. {__name__=~"lab_.*"} — выбор нескольких имён, но их значения могут иметь разные единицы, которые нельзя складывать лишь из-за префикса.

Выводим результат прежде запуска

В labs/fixtures/promql.yml есть три ряда q с этими labels. Перед promtool test rules запишите ожидаемые labels и значения. Полезен порядок: имя → matchers → отсутствие labels → время → функция. Если после matcher остались ноль рядов, умножение на 100 их не создаст. Если остались два, scalar не выберет «первый». Порядок строк выдачи не является надёжной идентичностью; сравнивайте labels.

Метрики с float и native histogram могут сосуществовать в одном vector. Допустимость функции определяется каждым sample type; предупреждения API могут указывать на исключённые элементы. HTTP 200 и status=success не гарантируют, что не было warnings/infos. Читайте весь ответ, а не только result. Базовые типы и selector grammar зафиксированы в PromQL basics 3.13; пределы исполнения — в query API.
