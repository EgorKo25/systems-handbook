Сбор: цели, обнаружение, переименование и исчезновение

Разделяем выбор сетевой цели до запроса и преобразование полученных образцов перед записью.

Одна попытка опроса

Target, цель сбора, — конкретный endpoint с набором меток и настройками. Job объединяет цели с общим способом сбора, instance обычно идентифицирует адрес. Scrape manager поддерживает расписание, инициирует HTTP GET, ожидает ответ не дольше timeout, проверяет протокол и разбирает samples. В успешной попытке появляются метрики цели и служебные ряды up, scrape_duration_seconds, scrape_samples_scraped, scrape_samples_post_metric_relabeling. up=1 означает успешный сбор endpoint, а не правильность business-функции приложения.

В стенде interval=15s, timeout=5s. Timeout не может превышать interval. Уменьшение interval до 5s повышает временное разрешение и число samples примерно втрое при прежнем наборе рядов; оно также втрое чаще запускает collector в приложении. Увеличение timeout с 1s до 5s помогает пережить известную задержку, но дольше занимает сетевые ресурсы и позже обнаруживает отказ. Сравнивают два запуска под одинаковой нагрузкой по duration, CPU exporter, числу ошибок и bytes, а не лишь исчезновению красного значка.

Discovery и target relabeling

Service discovery, обнаружение служб, производит список кандидатов с метаданными. Статический список проще для одной VM; file_sd_configs позволяет другому локальному процессу атомарно публиковать JSON (JavaScript Object Notation, формат структурированных объектов/массивов) с адресами. Discovery не проверяет, что endpoint отвечает и что сертификат верен. Встроенные метки __address__, __scheme__, __metrics_path__ определяют HTTP-запрос. __meta_... доступны на стадии обнаружения, но без копирования в обычную label не сохранятся в рядах.

scrape_configs:
  - job_name: personal-nodes
    file_sd_configs:
      - files: [targets/nodes.json]
    relabel_configs:
      - source_labels: [environment]
        regex: lab
        action: keep
      - source_labels: [__address__]
        target_label: instance
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: node_network_receive_drop_total
        action: drop

relabel_configs выполняются до scrape и могут исключить цель целиком. Здесь остаются только targets с environment=lab; regex в relabeling закреплён на границах. metric_relabel_configs работают над разобранными samples перед ingestion: приведённое удаление одной семьи не экономит сеть и работу exporter, зато уменьшает запись. Это лишь демонстрация различия стадий; удалять drop counter в реальном стенде без обоснования не нужно. Автоматически сгенерированный up не подвергается metric relabeling. Не удаляйте различающие labels так, чтобы два samples с разными смыслами столкнулись в одной идентичности.

JSON для file discovery содержит, например, [{"targets":["node-a.lab.example:9100"],"labels":{"environment":"lab"}}]. Это условный адрес собственной VM. Генератор пишет временный файл в том же filesystem и переименовывает его; читатель не должен видеть полунаписанный JSON. Для подключения машины отдельно выбирают и проверяют node_exporter, его версию, права, collectors и сетевой доступ. Открывать exporter в Интернет ради сбора личной машины не требуется: используйте личную сеть и аутентифицированный защищённый канал. Подробный рецепт подключения даёт официальное руководство.

Ошибки, stale и отсутствие цели

Если известный target не отвечает, up=0; прежние значения прикладных рядов не становятся нулями. Staleness, устаревание серии, означает прекращение её участия в instant selectors после специального stale marker. При неуспешном scrape прежние серии этого target помечаются устаревшими. Если успешный endpoint перестал возвращать отдельную серию, она также завершается. Если target исчез из discovery, отдельный механизм откладывает stale markers примерно на два интервала; это даёт возможность цели вернуться, и точную задержку нельзя принимать за SLA.

Перезапуск в этот промежуток и источники с явными timestamps имеют дополнительные условия; fallback lookback всё равно ограничивает поиск старых samples. Поэтому алерт up == 0 не обнаруживает навсегда удалённую из discovery цель: ряд up исчезает. Для ожидаемого фиксированного job нужен, например, absent_over_time(up{job="go-lab"}[2m]), а для изменяемого набора машин — отдельный inventory expected targets. Сравнение «сколько ожидали» и «сколько наблюдаем» требует внешнего знания, которое невозможно вывести из пустого списка.

Приёмка изменения

Сначала promtool check config, затем reload и проверка prometheus_config_last_reload_successful и Targets API /api/v1/targets. Сохраните снимок labels до/после relabeling, последний scrape error и число samples. Изменение instance создаёт новые ряды; старые не переименовываются задним числом. Весь основной цикл конфигурации 3.13 описан в versioned reference.
