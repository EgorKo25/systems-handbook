Instrumentation Go: контракт метрики и цена наблюдения

Добавляем измерение в один сохраняемый сервис, ограничиваем labels и разбираем конкуренцию между запросом, сбором и сериализацией.

Где начинается измерение

Здесь впервые нужен компилятор Go. Его получение, проверка поставки и модули разобраны в томе Go; подготовьте их до офлайна. В установочной главе вы уже скопировали весь labs/go-service в prom-lab/go-service. Исходник main.go содержит HTTP-сервер, go.mod описывает модуль и закреплённую версию клиента метрик, go.sum помогает проверять содержимое зависимостей. Сначала в этой папке выполняют go mod download при наличии сети либо используют заранее подготовленные зависимости. Только после этого доступны тесты и сборка ниже; открытие HTML-книги само не устанавливает Go и библиотеки.

До чтения кода нужны три вида измерения. Счётчик counter накапливает завершённые события. Текущее значение gauge может увеличиваться и уменьшаться: число работ в обработке растёт при входе и падает при выходе. Гистограмма histogram раскладывает длительности по границам интервалов, чтобы позднее получить распределение. CounterVec и HistogramVec — семейства таких измерений с одинаковым именем, но разными допустимыми наборами меток. Один набор route,code выбирает один конкретный счётчик. Точный формат гистограммы и стоимость её границ разберёт следующая глава.

Instrumentation, инструментирование, — код, который делает состояние приложения наблюдаемым. В labs/go-service обработчик /work увеличивает число выполняющихся работ при входе, выполняет ограниченную задержку, формирует статус и после работы записывает counter и histogram. Время измеряется через time.Now/time.Since: для длительности Go использует монотонную составляющую времени, когда она доступна. Метрика имеет suffix _seconds, а не скрытые миллисекунды.

requests := prometheus.NewCounterVec(prometheus.CounterOpts{
    Name: "lab_requests_total", Help: "Completed work requests.",
}, []string{"route", "code"})
duration := prometheus.NewHistogramVec(prometheus.HistogramOpts{
    Name: "lab_request_duration_seconds", Help: "Completed work duration.",
    Buckets: []float64{.01, .05, .1, .3, 1},
}, []string{"route"})

Route здесь всегда /work, code только 200 или 500. Входной query parameter может попросить ошибку, но не копируется в labels. Сначала описывают допустимые значения, затем создают серии. Если выбирать сырой r.URL.String(), клиент сможет создавать новые идентичности каждым URL. Нормализованный шаблон маршрута /users/{id} сохраняет полезную группировку и ограничивает кардинальность.

Registry и HTTP endpoint

Registry, реестр collectors, хранит согласованные описания метрик. Пример создаёт отдельный NewRegistry и явно регистрирует NewGoCollector, NewProcessCollector и собственные метрики. Ошибка повторной регистрации обнаруживается при запуске; нельзя создавать и регистрировать counter на каждый запрос. promhttp.HandlerFor получает реестр, собирает семейства метрик и сериализует HTTP-ответ с корректным Content-Type. Scraper работает параллельно пользовательским обработчикам.

Методы стандартных counters/gauges/histograms client_golang безопасны для конкурентного использования. Это не делает безопасным произвольный пользовательский map внутри custom collector: его состояние нужно синхронизировать отдельно. Снимок нескольких метрик не является общей транзакцией приложения; gauge inflight может быть прочитан в один момент, counter в другой. Не выводите из разности таких значений строгий баланс бизнес-транзакций без собственного согласованного источника.

go_goroutines, показатели GC/heap и process_cpu_seconds_total, process_resident_memory_bytes отвечают на разные вопросы. RSS включает резидентные страницы процесса, а Go heap — только часть памяти. CPU counter в секундах делят через rate на секунды wall time, прошедшего реального времени: результат выражает использованные CPU cores в среднем. Значение 1.4 допустимо для многопоточного процесса; умножение на 100 без объяснения числа доступных CPU вводит в заблуждение.

При Ctrl+C пример закрывает listener через Server.Shutdown и ждёт завершения этой функции, не только возврата Serve. Активным обычным HTTP-обработчикам дан предел 5 секунд; по истечении срока ошибка записывается в журнал и процесс выходит. Это ограниченная попытка завершить работу, а не обещание доставки ответа каждому клиенту. Ожидание важно: Serve возвращает ErrServerClosed сразу при начале shutdown, когда обработчики ещё могут работать. Такое разделение описано в документации Go.

Инициализация и нулевые ряды

Пример заранее вызывает WithLabelValues для двух допустимых кодов и фиксированного route. Это создаёт нулевые счётчики до первого запроса, поэтому отсутствие 500 не превращается в отсутствие series. Если измеряемый набор динамический, preinitialization может сама породить слишком много рядов. Инициализируйте только осмысленный конечный набор, а не декартово произведение всех возможных внешних ID. Перезапуск процесса сбрасывает counters; Prometheus сохраняет старые значения и обрабатывает видимый reset при вычислении скорости.

Эксперимент со стоимостью

Начните в сохранённом prom-lab, в отдельном терминале, где не работает foreground-сервер. Зависимости уже подготовлены предыдущим шагом. Следующие команды переходят в Go-проект, проверяют и собирают его, затем явно возвращают оболочку в корень стенда. При ошибке остановитесь и прочитайте вывод; не продолжайте к запуску старого бинарника.

cd go-service
go test -race ./...
go build -o ../bin/lab-service .
go test -bench BenchmarkObserve -benchmem -count=5
cd ..

Benchmark сопоставляет наблюдение histogram с заранее выбранным handle и вариант, каждый раз ищущий его через WithLabelValues. Это два пути измерения накладных расходов. Nanoseconds и выделения памяти относятся к данному toolchain и CPU; универсального норматива здесь нет. Для запуска из восстановленного cwd prom-lab используйте bin/lab-service -port 18080; он займёт этот терминал до остановки.

Затем под одной и той же нагрузкой измерьте CPU/RSS/GC и задержку приложения без частых scrapes и при 15s/5s interval. Проверяйте отдельно стоимость Observe, перечисления collectors и сериализации большого ответа. Custom collector, синхронно читающий медленную БД на каждом scrape, способен исчерпать timeout и сам нагрузить зависимость. Кэш такого collector меняет свежесть данных: экспортируйте возраст/успех последнего обновления и отделяйте его от успешности HTTP. Интерфейсы и ограничения закреплены за client_golang v1.23.2.
