PromQL V: арифметика, сравнения и сопоставление labels

Vector matching — договор соединения по идентичности, а не автоматическое деление строк «по позиции».

Арифметика и фильтрация

Для float samples v * 100 умножает каждое значение; scalar не имеет labels. v / 0 может дать ±Inf или NaN по floating-point правилам; пустой вектор останется пустым. По умолчанию сравнение фильтрует: up == 0 возвращает только элементы со значением 0, сохраняя их значение 0. Alert rule считает наличие элемента истинным условием, поэтому нулевое значение такого результата всё равно активирует алерт. up == bool 0 возвращает 0/1 для каждого сравнимого элемента; это полезно для арифметики, но прямое использование такого выражения как алерта активирует и элементы с 0.

Сравнение двух scalars требует bool. NaN == NaN ложно; проверка v != v выделяет обычный float NaN. Нельзя заменить этим контроль missing data: отсутствующий ряд не участвует в сравнении. Арифметические операции обычно удаляют metric name; не полагайтесь на имя левого counter как на описание новой доли. Дайте recording rule новое имя с правильными единицами.

На native fixture count4,sum5 получаем histogram_count(nh * 2)=8, histogram_count(nh / 2)=2, histogram_sum(nh + nh)=10. Выражение 2 / nh пусто, а не выдаёт обратную среднюю длительность; для такой величины нужно сначала осмысленно извлечь scalar-valued показатель. У nh == bool nh результат 1. Эти случаи проверены настоящим promtool, поэтому допустимость операции не угадывается по рисунку histogram. Отрицательные populations непригодны как обычная экспортируемая метрика; арифметическое промежуточное состояние не означает допустимость записи recording rule.

One-to-one matching

В следующем отдельном числовом примере errors и requests — уже рассчитанные скорости за одно окно в requests/s, не сырые counters. Их отношение безразмерно. Это заданный набор для объяснения ключа; ниже глава явно перейдёт к другому набору из fixture.

Пусть errors{job="api",instance="a",code="500"}=2, errors{job="api",instance="b",code="500"}=3, а requests{job="api",instance="a"}=10, requests{job="api",instance="b"}=30. Голое errors / requests не находит пар: слева есть code. errors / ignoring(code) requests сопоставляет по всем labels кроме code (имя метрики в обычном arithmetic matching не учитывается) и получает 0.2 и 0.1. on(job,instance) явно ограничивает ключ этими двумя labels. Это ключ соединения, не список полей, которые нужно дописать.

Если слева теперь есть code=400 и 500 для каждой instance, ключу соответствуют два левых элемента и один правый. Нужен many-to-one договор errors / on(job,instance) group_left requests. group_left означает «слева множество», а не направление стрелки в пользовательском интерфейсе. group_right применим к симметричной ситуации, когда множество справа. В стороне «один» ключ обязан быть уникальным; если requests имеет ещё два region для той же instance, запрос должен отказать с ошибкой cardinality, а не молча выбрать одну строку.

Перенос метаданных

rate(lab_requests_total[5m])
  * on(job,instance) group_left(team)
    target_info

Условие опыта: target_info имеет значение 1, ровно один ряд на job/instance и стабильную label team. Умножение сохраняет числовую скорость и переносит team со стороны «один». Если target_info отсутствует, левый ряд тоже исчезает: арифметический join не является SQL left outer join. Если metadata обновлялась и две team одновременно видимы, uniqueness нарушается. Проверьте count by(job,instance)(target_info) и время/staleness исходника. В отдельной fixture-модели метрика errors заранее задана как скорость в requests/s: два кода для instance=a имеют значения 2 и 1. Единственный target_info для a имеет team=blue и значение 1. Поэтому тест errors * on(job,instance) group_left(team) target_info ожидает 2 и 1 requests/s с team=blue; live counter сервиса в этом тесте не участвует.

Запрос a * on(k) group_left(extra) b не должен порождать дублирующие полные label sets; group modifiers не разрешают произвольный many-to-many Cartesian product. Они применяются к arithmetic/comparison, не к set operators. Точная судьба metric name зависит от операции и modifiers, особенно у comparison с on/group_right; лучше проверять labels в fixtures, а не переносить привычку из одного примера.

Множества

and оставляет левые элементы с совпадающим ключом справа, значения справа не участвуют. unless оставляет левые без совпадения, or объединяет: левые имеют приоритет для совпавших label sets. Поэтому left and right — не логическое перемножение их чисел. В up and on(instance) maintenance наличие maintenance=0 всё равно считается наличием элемента. Для исключения именно активного maintenance сначала фильтруйте maintenance == 1.

Set matching допускает many-to-many, поскольку не создаёт арифметические пары. Оно позволяет заполнять ожидаемые нули через правильно маркированное множество и исключать известные состояния, но может скрывать отсутствие наблюдения. Прежде сложной формулы выпишите таблицу ключей слева и справа, проверьте uniqueness и укажите, какие ряды должны исчезнуть. Так ошибка many-to-many превращается в проверяемый контракт данных.
