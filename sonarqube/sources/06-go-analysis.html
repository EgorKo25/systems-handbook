Go от теста до показателя: события, покрытие и правильные входы

Получим реальные отчёты знакомого HTTP-сервиса и разберём их до байтового формата. Поймём, почему исполненный оператор, пройденная проверка и доказанное требование не одно и то же.

Один проект, один снимок исходников

Пример — модуль example.org/handbook-service из тома Go. cmd/handbook-service запускает HTTP-сервер, internal/httpapp создаёт обработчики. /healthz принимает GET и возвращает JSON, /greet нормализует имя, подставляет reader при пустом значении и отклоняет имя длиннее 128 UTF-8 байт. Поле Version позволяет связать ответ с выбранной сборкой. Это те же интерфейсы, с которыми работает сквозной практикум.

Скопируйте исходники в свою подготовленную рабочую область, сохраните собственный коммит и не изменяйте файлы между получением отчётов и анализом. Отчёт от C17 рядом с исходниками C18 — несогласованный вход. Простая одинаковая строка имени ветки не подтверждает идентичность дерева: ветка сдвигается. Для серьёзного CI используются checkout конкретной ревизии и артефакты этого же конвейера, а не общий каталог «последние тесты».

Получение нативных отчётов

mkdir -p reports
go test -count=1 -json -covermode=atomic -coverprofile=reports/coverage.out ./... > reports/test.jsonl
go vet ./...
go tool cover -func=reports/coverage.out

./... выбирает пакеты рекурсивно относительно текущего Go-модуля. -count=1 отключает повторное использование кэшированного успешного тестового результата для этого запуска. -json выводит поток событий, а -coverprofile указывает файл покрытия. -covermode=atomic использует атомарные счётчики инструментированных блоков: счётчики корректно обновляются при параллельном исполнении, но их обновление добавляет накладные расходы. Это измерение охвата, а не нормальный запуск для сравнения скорости сервиса.

Прямое перенаправление > не меняет код возврата go test. Если добавить | tee, без осмысленного pipefail итогом конвейера может стать успешный код tee, хотя тесты упали. В CI ошибка тестов должна остановить обязательный путь; отчёт при этом полезно сохранить через artifacts:when:always. Предоставленная программа prepare_reports.py вызывает реальные Go-процессы без такой трубы, сохраняет оба кода и возвращает ненулевой итог при отказе тестов или vet. Перед запуском удаляет свои старые отчёты, чтобы отказ не выглядел свежим успехом.

Программа предназначена для этого обычного pure-Go примера: явно отключает GOWORK и cgo, очищает GOFLAGS, запрещает автоматическое переключение toolchain через GOTOOLCHAIN=local. Она не устанавливает Go и не объявляет любую чужую сборку эквивалентной. Параметры --project и --go выбирают корень и инструмент. reports-manifest.json содержит версию, команду, результаты и хеши файлов; это локальная запись, а не подписанное свидетельство происхождения и не серверный quality gate.

Как читать JSONL тестов

JSONL — последовательность JSON-объектов, обычно по одному на строку. В go test -json событие может содержать Time, Action, Package, Test, Elapsed, Output. Имена полей чувствительны к регистру. Событие run начинает проверку, output передаёт её текст, pass/fail/skip завершают соответствующий объект. Не каждое событие имеет Test: завершение всего пакета отличается от завершения одного подтеста. Порядок вывода разных параллельных проверок может перемежаться.

{"Action":"run","Package":"example.org/handbook-service/internal/httpapp","Test":"TestHandler/long"}
{"Action":"output","Package":"example.org/handbook-service/internal/httpapp","Test":"TestHandler/long","Output":"=== RUN   TestHandler/long\n"}
{"Action":"pass","Package":"example.org/handbook-service/internal/httpapp","Test":"TestHandler/long","Elapsed":0}

Это сокращённая схема формата, не журнал объявленного живого анализа. JSON-строка содержит экранированный \n; он становится переводом строки внутри значения Output после разбора JSON. Присутствие слова PASS в произвольном Output не заменяет структурированное завершение и код процесса. Пакет может упасть при сборке или тестовой подготовке до появления обычного Test-события. Поэтому проверка только числа «успешных тестов» пропускает важный тип отказа.

Sonar использует sonar.go.tests.reportPaths=reports/test.jsonl для поддерживаемого нативного отчёта исполнения Go. Это не JUnit XML: переименование расширения не меняет грамматику. Для JUnit-интерфейса CI нужен отдельный корректный преобразователь, а не тот же файл с другим суффиксом. И отчёт исполнения, и отчёт покрытия необходимо создать до сканера: он не запускает ваши Go-тесты вместо вас.

Разбор профиля покрытия

mode: atomic
example.org/handbook-service/internal/httpapp/handler.go:18.3,22.4 3 1

Первая строка задаёт режим счётчика. Далее путь до файла и координаты участка: начало строка 18/столбец 3, конец 22/4; затем число операторов в инструментированном блоке и счётчик попаданий. Строка примера иллюстрирует грамматику, конкретные координаты вашего файла покажет настоящий запуск. Несколько исходных строк могут относиться к одному блоку, одна строка может содержать несколько логических операций. Отсюда ограничение: «строка подсвечена как исполненная» не означает, что пройдены все комбинации её условий.

Go показывает долю операторов в выбранной инструментированной области. Sonar рассчитывает свои показатели строк/условий по импортированным данным и собственной модели. Не следует ожидать равенства любого показателя с любым процентом go tool cover без сравнения определений. Для нативного Go-отчёта не надо придумывать отсутствующую полноценную метрику покрытия всех ветвей. Команда go tool cover -html=reports/coverage.out -o reports/coverage.html даёт отдельную локальную картину Go; HTML не передают как coverage.out.

Без -coverpkg тестовый запуск инструментирует пакеты по обычным правилам команды. При интеграционном тесте, вызывающем другие пакеты, можно намеренно расширить область, например -coverpkg=./..., но тогда меняются знаменатель и стоимость. Повторяемые серии сравнивают с одинаковыми флагами, платформой и набором пакетов. Смешивать покрытия разных ревизий простой конкатенацией опасно: координаты и смысл блоков могут уже отличаться.

Почему 100% всё ещё оставляет вопросы

В обработчике есть if len(name) > 128. Тесты для короткой строки и 129 ASCII-байт выполнят обе стороны этого сравнения. Ошибочная замена на >= 128 также пройдёт эти два теста, хотя строка ровно 128 байт теперь неправильно отклоняется. Покрытие может остаться тем же. Нужны граничные проверки 127/128/129 байт и проверка требуемого статуса; это знание договора интерфейса, которого счётчик попаданий не создаёт.

Добавьте Unicode-случаи. len(string) в Go считает байты, а не видимые символы; 65 двухбайтных кириллических букв дадут 130 байт. При требовании «максимум 128UTF-8 байт» это ожидаемый отказ. При требовании «128 символов» тот же код воплощает другой договор, и нужно сначала определить, что считается символом: байт, Unicode code point или графема. Анализатор не вправе угадать за вас продуктовую семантику.

В существующем наборе TestHandler проверяются методы, отсутствующий маршрут, пустое/пробельное имя, Unicode, длинная строка, заголовок Allow, JSON и версия в успешном ответе. Тест не является испытанием завершения процесса main, границ времени HTTP или сохранения соединений при SIGTERM. Расширяя тесты, назовите новое наблюдаемое свойство. Девять похожих проверок одного успешного ответа не дают того же охвата требований, что один правильно выбранный отрицательный случай.

Vet, race и зависимости

go vet исследует подозрительные конструкции по собственным правилам и работает отдельно от Sonar. Его ненулевой код должен учитываться независимо, даже если импорт его находок не настроен. Некоторые внешние отчёты можно импортировать поддерживаемым адаптером, но это не превращает GoVet-правила в обычные правила профиля Sonar. Не устанавливайте заброшенный линтер только потому, что он упомянут в старой таблице импорта; современный инструмент и его формат требуют отдельного подтверждения.

go test -race ./... добавляет динамическое обнаружение определённых гонок в реально исполненных путях. Ему нужны поддерживаемая платформа и соответствующая cgo/toolchain-среда. Наш prepare_reports намеренно не заявляет race-проверку, потому что в его pure-Go профиле CGO_ENABLED=0. Успех обычных тестов или атомарный счётчик покрытия не равен запуску race detector. Уязвимости зависимостей, например через govulncheck, тоже имеют отдельную модель достижимости, базу и дату; доступность соответствующей функции Sonar проверяется по выбранной поставке.

Приёмка импорта на настоящем сервере

После локально успешных тестов запустите сканер в том же дереве. Убедитесь по журналу, что импортёр увидел ожидаемые файлы, пути разрешились, go.mod не исключён и нет предупреждений о несовпадающих строках. На машине сканера должен быть Go для импорта покрытия согласно документации Go-анализатора; отдельный job с готовым отчётом не гарантирует наличия Go в scanner image. В интерфейсе сравните количество тестов, область покрываемого кода и намеренно непокрытую ветку с локальным представлением. Потом удалите покрытие в своём опыте и подтвердите, что отсутствие отчёта распознано, а не принято за «всё хорошо».
