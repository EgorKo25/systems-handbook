Что именно мы хотим получить

Kubernetes — система управления контейнерными нагрузками через API, то есть программный интерфейс операций над объектами. Автор описывает желаемое состояние, а независимые управляющие циклы сближают с ним наблюдаемое. Это не удалённый вызов «запусти Linux-процесс». Запись Deployment может уже находиться в хранилище, пока Pod ещё не назначен машине; Pod может быть назначен, но образ недоступен; процесс может работать, но Service не направляет к нему трафик. Поэтому доказательство проходит четыре границы: API принял объект, контроллер создал нужные объекты, node исполнил программу, клиент получил правильный ответ.

Control plane — управляющая часть: API server принимает запросы, etcd хранит состояние, scheduler выбирает node, controllers выполняют согласование. Node — зарегистрированная вычислительная машина, где kubelet организует исполнение Pods через container runtime. Контейнерный runtime — служба управления образами и контейнерами; здесь containerd. Pod — объект совместно размещаемых контейнеров с общей сетевой средой и указанными томами. Он не равен одному процессу, образу, VM или серверу приложения. Эти различия будут выводиться из конкретных изменений файлов, объектов и пакетов.

Какие объекты встретятся в первом запуске

Deployment — сохранённое описание взаимозаменяемых экземпляров программы и правил их обновления. Его контроллер создаёт ReplicaSet, а тот поддерживает нужное число Pods. Service — отдельный объект с постоянным именем и портом; его selector, условие выбора по меткам, связывает этот адрес с готовыми Pods. Метка app: ledger-api в наших файлах — обычная пара «ключ: значение», а не имя процесса. ConfigMap хранит несекретные настройки, которые программа получает при запуске. Это краткое знакомство позволит прочитать первые файлы; далее мы разберём, кто именно выполняет каждый переход.

Предполагаются уже разобранные Linux-процесс, TCP-соединение, файловая система, права и контейнерный образ. Если эти слова пока обозначают лишь знакомые названия, сначала вернитесь к томам Linux, Сети, Bash и Go. Образ — упакованные файлы и описание запуска; контейнер — их конкретное исполнение на узле. Kubernetes управляет такими исполнениями, но не собирает Go-код вместо компилятора.

Сначала выбираем стенд и сохраняем его состояние. Книга API объясняет идентичность, хранение, watch и конфликты управления. Книга исполнения проходит от scheduler до сигналов процессу Go. Сеть рассматривается отдельно: адреса, конкретный VXLAN/iptables путь, DNS, политики и внешний вход. Данные и доверие объясняют две границы, которые не спасает автоматический перезапуск. Эксплуатация связывает наблюдение, бюджет ресурсов, обновление и восстановление. Сквозные заявки требуют исправлять свой стенд, сохраняя UID, версии и данные между опытами.

Два честных стенда и один договор приложения

Основной путь — Ubuntu 24.04 в личных Linux-VM, kubeadm 1.36.6, containerd 2.4.2, Calico 3.33.0 в режиме VXLAN, kube-proxy iptables. Компактный путь — kind 0.33.0 с node image Kubernetes 1.36.4. Это разные patch и разные сетевые реализации. На машине с 8 GiB разумны один небольшой node или локальные тесты без кластера; несколько VM с резервом для ОС и IDE обычно требуют 16 GiB и последовательного включения других служб. Три control-plane и база на том же ноутбуке не превращаются в независимые зоны отказа.

ledger-api слушает TCP 8080 и предоставляет GET /livez, /readyz, /api/hello. Манифесты Kubernetes живут в namespace lab; Helm использует отдельный helm-lab и release ledger. Namespace — область имён и часть области действия политик, а не самостоятельная VM или автоматическая стена безопасности. Каждая команда явно получает выбранный context: handbook-admin либо kind-handbook. Context в kubeconfig связывает кластер, личность и namespace; он не является отдельным кластером.

Одна рабочая копия и сохранённые результаты

Скопируйте каталог kubernetes/labs из книги в собственную постоянную папку, например $HOME/handbook-lab/kubernetes/labs, вместе со всеми вложенными файлами. Книга может лежать на флэшке или открываться по HTTP; путь веб-страницы не становится рабочим каталогом терминала. Файлы стенда надо получить отдельно из исходников книги либо её полного офлайн-набора. Папку labs копируют один раз; при продолжении занятия возвращаются в неё, сохраняя изменённые файлы и журнал.

export K8S_LAB_ROOT="$HOME/handbook-lab/kubernetes/labs"
cd "$K8S_LAB_ROOT" || exit 1
test -f vm/kubeadm.yaml && test -f manifests/10-app.yaml && test -f service/main.go

Если проверка файлов неуспешна, следующий шаг не выполняют. В новой оболочке повторяют export и cd, а не копирование поверх старого каталога. Дальнейшие относительные пути vm/…, manifests/…, service/… отсчитываются от этой папки. Команды здесь записаны для Bash в личной Linux-среде. На рабочей Windows браузер читает книгу, а VM-команды исполняются через SSH в вашей машине стенда. Не направляйте их в системную оболочку рабочего компьютера.

Выбранный LAB_CONTEXT задаётся после установки кластера. K8S_LAB_ROOT хранит путь к файлам, LAB_CONTEXT — имя подключения; одна переменная не заменяет другую. При переносе компьютера переменные создают заново, а kubeconfig, исходники и состояние кластера сохраняют предусмотренным для них способом.

Как читать команды и доказательства

Выделение команды вроде kubectl get открывает штатную карточку справочника; карточки содержат аргументы, флаги, эффекты и ошибки. Команды с sudo, systemctl, swapoff, mount, iptables, crictl, ctr и сетевыми изменениями в этой книге предназначены исключительно для своей подготовленной VM. При создании книги они не исполнялись на компьютере пользователя. Локально действительно проверены Go, разобран YAML, проверена форма объектов по официальному OpenAPI и байты офлайн-набора. Это не свидетельства работы кластера; точный протокол находится в ПРОВЕРКИ.txt.

Интерактивные схемы — автономные пошаговые модели фиксированных сценариев. Они показывают инициатора, направление и переход состояния, не устанавливают службы и не отправляют запросов. В тексте у сложных понятий есть первоисточник и объяснение; словарь служит повторению. Дата редакции — 1 ноября 2026. Latest endpoint на эту дату показал 1.37.2; выбранная линия 1.36.6 зафиксирована ради воспроизводимости и не объявляется самой новой.

kubeadm создаёт предусмотренный upstream Kubernetes control plane и присоединяет nodes; он не создаёт VM, не устанавливает за вас containerd и не выбирает CNI. CNI, Container Network Interface, — договор передачи runtime сетевому плагину параметров sandbox и получения сетевого результата. Calico реализует IP-связность и NetworkPolicy. CRI, Container Runtime Interface, — gRPC-интерфейс kubelet к runtime, через который запрашиваются sandbox, образы и контейнеры. CSI, Container Storage Interface, относится к управлению хранилищем и не участвует в выборе IP Pod.

 | Среда | Что реально получаем | Цена и ограничение

 | kubeadm в VM | Отдельные Linux-ядра, systemd, containerd, kubelet; ясные диски и сетевые интерфейсы | Ресурсы каждой VM, ручной CNI/backup/upgrade; лучший путь для изучения node и восстановления

 | kind | Nodes как контейнеры с kubelet/containerd внутри, реальный API и controllers | Общее ядро хоста, nested cgroups, зависимость от Docker/Podman и особый внешний доступ; перезапуск контейнера не моделирует потерю физического сервера

 | minikube | Локальный кластер с выбранным VM/container driver и набором addons | Поведение зависит от driver; tunnel и mount — дополнительные процессы, автоматические addons могут скрыть зависимости

 | k3s | Компактный Kubernetes-дистрибутив со своей упаковкой и defaults | Обычно bundled runtime/CNI/ingress и собственный lifecycle; single-server datastore не обязательно etcd, команды kubeadm к нему неприменимы

При 8 GiB всей машины начните с kind одним node и лимита памяти VM/container engine около 3–4 GiB, если ОС и IDE помещаются в остаток. Это начальная гипотеза, а не гарантия. При 16 GiB можно выделить cp1 2 vCPU/2.5 GiB и wk1 2 vCPU/2.5 GiB, оставив примерно 11 GiB до учёта гипервизора и прочих программ. На каждую VM планируем диск 25 GiB thin, затем измеряем фактически занятое. Нельзя складывать виртуальные размеры файлов и считать их свободной RAM. Одновременные image pulls и сборки могут исчерпать диск или вызвать memory pressure при маленьком приложении.

Фиксируем версии и происхождение

На 01.11.2026 stable.txt показал Kubernetes v1.37.2, stable-1.36.txt — v1.36.6. Для VM выбран второй; kubeadm, kubelet и kubectl фиксируем одним patch. Официальные release endpoints дали containerd v2.4.2, runc v1.5.2, reference CNI plugins v1.9.1, Calico v3.33.0 и kind v0.33.0. Calico 3.33 официально тестируется с Kubernetes 1.35/1.36/1.37. Это проверка опубликованной совместимости, не выполненный интеграционный тест нашей пары VM. Аппаратная архитектура amd64/arm64 должна совпадать у ОС, бинарника и образа.

curl -fL -o kubectl https://dl.k8s.io/release/v1.36.6/bin/linux/amd64/kubectl
curl -fL -o kubectl.sha256 https://dl.k8s.io/release/v1.36.6/bin/linux/amd64/kubectl.sha256
printf '%s  kubectl
' "$(cat kubectl.sha256)" | sha256sum -c -
chmod +x ./kubectl
./kubectl version --client -o yaml

-f завершает curl ошибкой на HTTP-ошибке, -L следует redirect, -o задаёт файл. Сумма проверяет целостность относительно доверенно полученного значения; если атакующий заменил и бинарник, и сумму, арифметика не докажет происхождение. Сохраняйте TLS-цепочку доверия, официальный URL, release notes, опубликованные подписи/attestations там, где они предоставлены, и отдельно подтверждённую сумму. Не запускайте скачанное до проверки. На Windows используют официальный kubectl.exe той же версии, Get-FileHash -Algorithm SHA256 и собственный kubeconfig; кластер остаётся Linux-кластером.

Что должно доехать без сети

Офлайн-набор содержит Ubuntu ISO с суммами и подписью поставщика, все .deb зависимости выбранного ОС/архитектуры, kubelet/kubeadm/kubectl и kubernetes-cni/cri-tools в согласованной версии, containerd/runc и systemd unit, CNI binaries, точный Calico manifest, все его images, control-plane/CoreDNS/pause/etcd images из kubeadm config images list --config vm/kubeadm.yaml, собственный Go binary/image, диагностический образ, исходники, Python wheels при необходимости и документацию. Kubernetes пакеты получают из отдельного minor-репозитория pkgs.k8s.io; legacy apt.kubernetes.io не используем.

Собирать .deb нужно на отдельной staging-VM с тем же Ubuntu 24.04 и архитектурой: чистая машина выявляет транзитивные зависимости. apt-get --download-only на машине, где всё уже установлено, может не скачать нужные зависимости. Запишите версии через apt-cache policy и dpkg-query; перенесите подписанные repository metadata либо сформируйте проверяемый локальный набор. Точный суффикс Debian package revision выбирается из реального репозитория, не угадывается по версии upstream.

kubeadm config images list --config vm/kubeadm.yaml > kubeadm-images.txt
python3 bundle_manifest.py create /path/to/staged-bundle
python3 bundle_manifest.py verify /path/to/staged-bundle

Первый вызов перечисляет ожидаемые ссылки конкретной конфигурации, а не скачивает images. В VM ctr --namespace k8s.io images export сохраняет подготовленные образы, images import загружает их на каждый нужный node. namespace containerd k8s.io — пространство metadata runtime, оно не равно Kubernetes namespace lab. OCI archive и Docker save не следует считать одним форматом без проверки импортера. Наш bundle_manifest.py записывает размер и SHA-256 каждого файла и обнаруживает повреждение, но не подтверждает подпись издателя. Реальный критерий полноты — повторить bootstrap и запуск приложения на изолированной VM с отключённым внешним доступом; здесь этот опыт не выполнен.

Сначала карта адресов, прав и дисков

Создайте cp1 и wk1 из проверенного Ubuntu 24.04 ISO. У каждой уникальны hostname, MAC и product_uuid. Пример private-сети: cp1 192.168.56.10, wk1 192.168.56.11, имя cp1.lab.internal разрешается на обеих VM и клиенте. Это пример, который надо проверить на пересечение с домашней LAN/VPN/WSL/Docker. PodCIDR 10.244.0.0/16 и ServiceCIDR 10.96.0.0/16 тоже не должны пересекаться с внешними маршрутами и друг с другом. CIDR — адресный префикс; /16 обозначает фиксированные первые 16 бит IPv4, а не количество машин.

Сделайте снимок чистых выключенных VM и запишите ресурсы, версии ядра, диски, время, DNS, routes и свободное место. Снимок двух работающих etcd VM не равен согласованному backup приложения. В выбранном базовом варианте один cp1: его потеря останавливает новые API-изменения и согласование, хотя уже запущенное приложение на wk1 может некоторое время отвечать. Порт TCP 6443 доступен только доверенным клиентам/nodes, kubelet TCP 10250 — control plane; etcd 2379/2380 только соответствующим control-plane членам. VXLAN UDP 4789 — только между nodes. Не открывайте все порты всем ради прохождения join.

Подготовить node, не меняя рабочий компьютер

Внутри обеих VM включают нужные kernel modules overlay и br_netfilter, IPv4 forwarding и согласуют netfilter с CNI; проверяют синхронизацию времени и отсутствие конфликтующего firewall/NetworkManager. Файл системных параметров в VM должен пережить reboot. Для этого учебного профиля swap отключён в VM и исключён из её fstab; failSwapOn: true делает неожиданно включённый swap явным отказом. Kubernetes поддерживает отдельные режимы Linux swap при условиях версии, но эта книга не смешивает их с базовым стендом. swapon --show — чтение; swapoff -a — меняющая операция только на своей VM после проверки RAM.

uname -r
stat -fc %T /sys/fs/cgroup
swapon --show
ip -brief address
ip route
sudo modprobe overlay
sudo modprobe br_netfilter
# Only inside the personal VM; persist reviewed equivalents in /etc/sysctl.d/.
sudo sysctl -w net.ipv4.ip_forward=1
sudo sysctl -w net.bridge.bridge-nf-call-iptables=1

Ожидаем cgroup2fs на Ubuntu с cgroup v2. cgroup — иерархия учёта и ограничения ресурсов Linux. kubelet и containerd используют systemd-драйвер, иначе две программы могут считать ресурсную иерархию по-разному. Файл containerd.toml использует config version 3 и plugin path containerd 2.x, а не старую секцию 1.x. CRI не должен быть в disabled_plugins. sandbox image pause:3.10.2 согласован с исходником kubeadm v1.36.6. Служба containerd хранит persistent content/snapshots в /var/lib/containerd, runtime socket/state — в /run/containerd; kubelet state — /var/lib/kubelet. Два интерфейса VM: API address и kubelet InternalIP

В InitConfiguration fixture cp1 явно задан kubeletExtraArgs node-ip=192.168.56.10. На wk1 перед join создайте /etc/default/kubelet со строкой KUBELET_EXTRA_ARGS=--node-ip=192.168.56.11, как показано в INSTALL.txt, и проверьте package systemd drop-in через systemctl cat kubelet. Сохранение, остановка и честный отказ

Сохраняйте один cluster handbook весь практикум. kind delete cluster --name handbook уничтожает nodes и их локальные данные; повторное create создаёт новый cluster с новыми UID, сертификатами и пустым etcd. Перед обслуживанием сохраняйте нужные object manifests, секреты безопасно и отдельные backup данных, проверяйте restart. Запрос начинается раньше YAML

kubectl apply читает YAML, преобразует в структурированные значения, определяет Group/Version/Resource и отправляет HTTPS-запрос. apiVersion задаёт представление, kind — тип объекта, metadata.name — имя в области ресурса. Для Deployment ledger-api путь включает /apis/apps/v1/namespaces/lab/deployments/ledger-api. Group apps группирует API; namespaced resource и cluster-scoped Node имеют разные URL и права. GVK, Group Version Kind, — идентификатор формы, GVR, Group Version Resource, — маршрутизируемая коллекция.

Webhook — отдельный HTTPS-обработчик, к которому API server обращается в предусмотренной точке admission. Он получает описание запрашиваемого действия и возвращает решение, а mutating webhook может также предложить изменение объекта. Вызов webhook добавляет ещё одно соединение, задержку и возможный отказ; код приложения ledger-api на этом этапе ещё не запускается. Политика failurePolicy: Fail требует отклонить запрос, когда соответствующий вызов webhook не выполнен, а не считать отсутствие ответа разрешением.

API server проверяет TLS/аутентификацию, устанавливает username/groups, выполняет авторизацию операции и admission, то есть предусмотренную политику допуска/изменения объекта. Authentication, установление личности, не равно RBAC-разрешению. Для mutating-запроса decoding/conversion/defaulting, mutating admission и validating admission/validation образуют pipeline; точные внутренние точки зависят от вида запроса и resource strategy. Не считайте их одной общей shell-командой. Mutating webhook может добавить поля, validating webhook может отказать, недоступный webhook с Fail может остановить изменения. Поэтому схема API→etcd намеренно не обещает один сетевой запрос и универсальный порядок всех внутренних функций.

Schema, defaulting и storage version

Schema — описание допустимой структуры/типов полей; validation проверяет структурные и смысловые ограничения. Defaulting добавляет предусмотренные значения отсутствующих полей. Строка "80" в Service.port не становится автоматически числом 80 только от знакомого смысла. kubectl explain deployment.spec.template показывает серверную схему; локальный YAML parser знает лишь синтаксис. Сохранённый объект может иметь defaulted поля, admission mutations, UID, timestamps, resourceVersion и managedFields, которых не было во входном файле.

Storage version — версия представления, в которой API server хранит данный вид ресурса; запросить объект можно в другой обслуживаемой версии через conversion. Для встроенных ресурсов это внутренняя реализация API server, для CRD важны served/storage версии и conversion webhook. CRD, CustomResourceDefinition, регистрирует новый API-тип; установка CRD не запускает контроллер и не обеспечивает его семантику. Перед удалением обслуживаемой версии надо обновить клиентов и сохранённые объекты по supported migration path. Смена apiVersion в одном локальном YAML не переписывает всё хранилище.

Идентичность и конкурентная запись

UID — уникальная идентичность экземпляра объекта. Удалённый и созданный заново Pod с тем же name имеет новый UID; ссылки владельца и контроль удаления должны различать их. resourceVersion — непрозрачный маркер версии состояния, предназначенный для concurrency/watch, а не число секунд, глобальный счётчик бизнес-событий или пригодное для арифметики поле. PUT с устаревшим resourceVersion обычно получает 409 Conflict: другой клиент уже изменил объект. Клиент перечитывает, заново вычисляет изменение и повторяет, не перезаписывает чужую работу вслепую. generation отражает изменения желаемой спецификации для поддерживающих ресурсов; observedGeneration в status показывает, какую generation обработал контроллер.

etcd и quorum

etcd — распределённое согласованное key-value хранилище. API server сериализует ресурсы и выполняет операции с ним; обычный controller не пишет напрямую в etcd. Raft — протокол согласования журнала между членами etcd. Quorum, большинство, для N членов равен floor(N/2)+1. Три члена допускают потерю одного, пять — двух; два всё ещё требуют два и не дают выигрыша доступности над одним. Лидер подтверждает запись после предусмотренного согласования большинства; медленный fsync/сеть влияют на задержку записи и выборы лидера. Больше членов может ухудшать latency, а копии на одном диске не дают независимости отказов.

Один cp1 содержит один etcd: нет quorum-запаса. API server может обслуживать чтение из cache в предусмотренных режимах, но отсутствие достаточного etcd не делает кластер надёжно изменяемым. Уже запущенные контейнеры не обязаны остановиться от потери API; новые назначения и восстановление контроллерами будут недоступны. Не редактируйте etcd ключи руками: обойдёте validation, ownership и версии. Backup etcd нужен для управляющего состояния, application backup — для байтов в PVC и внешних системах.

kubectl --context "$LAB_CONTEXT" -n lab get deployment ledger-api -o yaml
kubectl --context "$LAB_CONTEXT" -n lab get pod -l app=ledger-api -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.metadata.uid}{" "}{.metadata.resourceVersion}{"\n"}{end}'
kubectl --context "$LAB_CONTEXT" explain deployment.spec.template.spec.containers

Снимите UID и resourceVersion до и после rollout. Новый ReplicaSet/Pod и новый process PID — три разные идентичности. Вывод YAML может содержать credentials и environment, поэтому сохраняйте только осмысленный диагностический фрагмент. API latency измеряют отдельно от времени rollout status: первый отражает принятие/чтение, второй включает scheduler, images, process и probes.

Один optimistic-concurrency конфликт, разобранный до ответа

На отдельном ConfigMap concurrency-demo клиент A прочитал data.mode=blue и opaque resourceVersion R1. Клиент B прочитал тот же R1, записал mode=green и получил новую версию R2. Если A отправит PUT с R1 и новым data.note, server не может предположить, что A видел green: ответ 409 Conflict защищает последнюю запись. Это не обязательно RBAC403 или schema422. HTTP-форма ниже — условный разбор протокола, буквы R1/R2 не настоящие numeric resourceVersions и не готовый curl token.

A: GET /api/v1/namespaces/lab/configmaps/concurrency-demo
   <- 200 {metadata:{name:"concurrency-demo",resourceVersion:"R1"},data:{mode:"blue"}}
B: PUT same URL, resourceVersion="R1", data.mode="green"
   <- 200, resourceVersion="R2"
A: PUT same URL, resourceVersion="R1", data.note="checked"
   <- 409 Conflict, Status.reason="Conflict"
A: GET same URL -> R2, recompute intent while preserving mode="green"
A: PUT with current resourceVersion and recomputed fields -> success if no new writer

Практический опыт выполняется на отдельном ConfigMap, чтобы не затронуть конфигурацию приложения. Ниже функция Bash создаёт только новый lab/concurrency-demo и отдельный каталог доказательств. Если объект уже есть после прошлого опыта, create откажет: сначала прочтите его текущее значение и старый журнал, затем либо продолжайте разбор, либо осознанно удалите только этот учебный ConfigMap. Namespace и приложение не пересоздают.

concurrency_demo() {
  : "${LAB_CONTEXT:?Сначала выберите context личного стенда}"
  : "${K8S_LAB_ROOT:?Сначала задайте путь к сохранённым файлам}"
  cd "$K8S_LAB_ROOT" || return 1
  mkdir -p evidence || return 1
  local work
  work=$(mktemp -d "$K8S_LAB_ROOT/evidence/concurrency.XXXXXXXX") || return 1
  kubectl --context "$LAB_CONTEXT" -n lab create configmap concurrency-demo --from-literal=mode=blue || return 1
  kubectl --context "$LAB_CONTEXT" -n lab get configmap concurrency-demo -o json > "$work/a.json" || return 1
  kubectl --context "$LAB_CONTEXT" -n lab patch configmap concurrency-demo --type=merge -p '{"data":{"mode":"green"}}' || return 1
  printf 'Старая полная версия: %s\n' "$work/a.json"
  if kubectl --context "$LAB_CONTEXT" -n lab replace -f "$work/a.json"; then
    printf 'Неожиданный успех: остановитесь и проверьте, менялся ли объект.\n' >&2
    return 1
  fi
  printf 'Прочтите отказ: нужен Conflict из-за устаревшей версии, а не любая ошибка.\n'
  kubectl --context "$LAB_CONTEXT" -n lab get configmap concurrency-demo -o yaml || return 1
}
concurrency_demo

В a.json осталось значение blue и старая metadata.resourceVersion; patch сохранил green и новую версию. Replace посылает прежний снимок целиком, поэтому сервер должен отклонить его как устаревший. Forbidden означает отсутствие прав, NotFound — другое имя или отсутствие объекта, ошибка проверки структуры — неверную форму. Ни один из этих отказов не доказывает проверку конкурентной записи. Файл и текущий объект сохраняются для сравнения.

После подтверждённого конфликта перечитайте объект и заново вычислите своё изменение. Если намерение — добавить note=checked, не меняя mode, узкий merge patch kubectl --context "$LAB_CONTEXT" -n lab patch configmap concurrency-demo --type=merge -p '{"data":{"note":"checked"}}' сохранит green при отсутствии другого писателя этого ключа. Для изменения, зависящего от прочитанного значения, нужен повтор read → проверка условия → update с текущей версией; при новом конфликте повтор ограничивают числом попыток и задержкой. Разные объекты Kubernetes не образуют общей транзакции приложения.

Ответ success содержит server object, а не обещание Pod: после 200 Deployment change контроллер ещё только увидит generation. Временная линия принятия хранится отдельно от линии observedGeneration/PodScheduled/containerStarted/Ready. Так можно объяснить пользователю «изменение сохранено, доставка ещё ждёт registry» без ложного утверждения о работающем процессе.

Как клиент узнаёт изменение

List получает набор объектов и resourceVersion коллекции. Watch продолжает наблюдение изменений от допустимой версии: ADDED/MODIFIED/DELETED и предусмотренные служебные события. Это не долговечная бизнес-очередь с бесконечным retention. История etcd/watch cache ограничена; слишком старая версия может дать 410 Gone/Expired, после чего клиент выполняет новый list и восстанавливает наблюдение. Bookmark обозначает продвижение наблюдения, а не отдельный workload. При больших наборах pagination и streaming list уменьшают пики, но требуют согласованной клиентской реализации.

Informer в client-go — механизм list/watch и локального cache объектов с обработчиками. Рабочая очередь контроллера обычно содержит ключи namespace/name, объединяет повторные уведомления и ограничивает retry. Событие сообщает «перепроверь», а не «сделай именно один раз ровно эту операцию». Cache может отставать от последней собственной записи: controller должен терпеть повтор, NotFound и conflict. Нельзя строить алгоритм, который корректен только при мгновенном read-your-write через произвольный informer.

Apply управляет полями

Client-side apply хранит предыдущую конфигурацию в last-applied annotation и вычисляет patch клиентом. Server-side apply, SSA, передаёт declarative intent API server, который ведёт field ownership в managedFields. Field manager — имя участника управления, например handbook; оно не является отдельной RBAC-личностью. Два manager могут владеть разными полями одного объекта. При попытке изменить поле другого manager сервер возвращает conflict, если нет разрешённого принудительного захвата. Merge списков определяется схемой: список containers с map key name отличается от atomic-списка.

kubectl --context "$LAB_CONTEXT" -n lab apply --server-side --field-manager=handbook -f manifests/10-app.yaml
kubectl --context "$LAB_CONTEXT" -n lab get deployment ledger-api -o yaml --show-managed-fields
kubectl --context "$LAB_CONTEXT" -n lab diff --server-side --field-manager=handbook -f manifests/10-app.yaml
kubectl --context "$LAB_CONTEXT" -n lab apply --server-side --field-manager=experiment --dry-run=server -f manifests/10-app.yaml

Первая команда меняет API и ownership. Вторая лишь читает; managedFields может значительно увеличить вывод. Diff показывает предполагаемые отличия, причём exit 1 означает найденную разницу, а не обязательно неисправность; exit больше 1 — ошибка. Server dry-run проходит серверные проверки и применимые admission без сохранения объекта. Client dry-run не подтверждает серверную schema/admission/RBAC и всё ещё может требовать discovery в зависимости от операции. Dry-run не запускает scheduler, не скачивает image и не доказывает readiness.

Сравните обычный SSA с --force-conflicts только на выделенном учебном ConfigMap: второй отнимает ownership конфликтующих полей. Это действие не исправляет ошибку проектирования двух владельцев. Если HPA управляет replicas, стабильный declarative manifest обычно не должен постоянно возвращать своё replicas; если Helm владеет Deployment, kubectl-упражнение не должно перехватывать его поля. Namespace helm-lab отделён именно ради жизненных циклов, но два инструмента всё равно можно ошибочно направить на один объект.

HPA, горизонтальный автоподстройщик количества экземпляров, позже будет менять spec.replicas Deployment по измерениям. Уже сейчас важно различить двух писателей: ваш файл задаёт постоянные поля приложения, а HPA вычисляет число реплик. При включении HPA поле replicas передают ему осознанно; очередной apply старого файла с replicas: 1 способен вмешаться в масштабирование. В этой части HPA ещё не установлен.

Patch, replace и удаление

JSON Patch — последовательность операций над JSON pointer; JSON Merge Patch заменяет значения по правилам merge, а strategic merge применим к поддерживающим встроенным типам. Это разные семантики списков. kubectl patch --type=json с индексом containers/0 хрупок, если список поменялся; для точного эксперимента сначала проверяют name и полный объект. Replace PUT отправляет полную желаемую форму и resourceVersion; это не более безопасный apply. Delete с UID precondition защищает от удаления нового одноимённого экземпляра. Force delete удаляет объект без ожидания фактического подтверждения остановки процесса: на недоступном node процесс может продолжать жить.

Цена наблюдения

Один kubectl get pods --watch открывает длительное наблюдение вместо частого полного list. Это полезно для короткой диагностики, но тысячи watchers тоже потребляют память/соединения/API CPU. Удаление полезных status полей ради «оптимизации» без измерения ухудшает диагностику; сначала найдите конкретный объём и источник частой записи.

SSA на одном ключе и watch после потери истории

ManagerA отправляет ConfigMap data.color=blue через apply-patch+yaml с fieldManager=bookA. В managedFields появляется manager bookA, operation Apply и fieldsV1, включающий путь к data.color. ManagerB отправляет тот же ключ=green с fieldManager=bookB. Без force сервер сообщает field conflict с владельцем/путём; это отдельный смысл 409 от stale resourceVersion, хотя HTTP-code одинаков. С одинаковым blue возможна совместная ownership по правилам SSA. Нельзя разбирать один 409 только по числу: смотрите Status.details/message и тип операции.

Оба намерения поставляются как отдельные файлы: ownership-a.yaml содержит blue, ownership-b.yaml — green. У них одинаковые apiVersion, kind, namespace и name, поэтому это два описания одного ConfigMap. В первом опыте объекта ещё не должно быть; если он сохранился после прошлого занятия, сначала прочтите его managedFields и журнал, а не объявляйте новый запуск чистым.

kubectl --context "$LAB_CONTEXT" -n lab apply --server-side --field-manager=bookA -f vm/ownership-a.yaml
kubectl --context "$LAB_CONTEXT" -n lab get configmap ownership-demo -o yaml --show-managed-fields
kubectl --context "$LAB_CONTEXT" -n lab apply --server-side --field-manager=bookB -f vm/ownership-b.yaml
kubectl --context "$LAB_CONTEXT" -n lab get configmap ownership-demo -o yaml --show-managed-fields

Первый apply должен успешно сохранить blue. Третий должен получить именно конфликт поля data.color с bookA; отсутствие прав, недоступность API или ошибка файла означают другой опыт. Сверьте, что после отказа значение осталось blue. Оба apply здесь выполняет одна удостоверенная личность: меняется только имя управляющего полями, а не пользователь RBAC. Для осознанной передачи на этом отдельном объекте повторите третью команду с --force-conflicts, убедитесь в green и владении bookB, затем верните blue через такой же явный захват bookA. Именно этот последний шаг возвращает исходное распределение управления; обычный apply bookA до передачи обратно может конфликтовать. Namespace, приложение и остальные поля не удаляются.

Последний apply с новым значением должен встретить conflict при сохранённой ownership bookA. --force-conflicts разрешил бы передачу поля bookB и фактическую смену green, но тогда bookA при следующем обычном apply уже конфликтовал бы. Удаление поля из intent manager может удалить значение, если никто другой им не владеет и нет иных препятствий; «не упомянул» не всегда означает «оставил как было». Именно поэтому не стоит применять kubectl-export с server metadata как собственный чистый desired manifest.

Для watch клиент сначала получил list с collection resourceVersion W100, затем долго был offline. За это время история до W100 была compacted. Запрос watch resourceVersion=W100 получает 410, потому что сервер не может честно воспроизвести полный интервал. Правильный клиент не придумывает пропущенные события и не увеличивает W100 на 1. Он делает новый list, получает current objects и W900, перестраивает cache/очередь и продолжает watch от W900. Объект, созданный и удалённый целиком в пропуске, может не появиться в новом list: watch не служит финансовым event ledger.

Поведение можно исследовать на своих clients без намеренного вмешательства в etcd compaction живого кластера. Не настраивайте агрессивный retention только ради 410 на основном стенде. Локальная пошаговая схема показывает этот случай как модель; реальное наличие 410 не заявлено в протоколе проверок. Informer relist/resync/retry — механизмы восстановления наблюдения, а не доказательство exactly-once внешних side effects.

Один reconcile вместо волшебной транзакции

Reconciliation, согласование, — цикл «прочитай желаемое и наблюдаемое, вычисли разницу, выполни ограниченное действие, проверь позже». Deployment controller управляет ReplicaSet, ReplicaSet controller — нужным числом Pods, kubelet — локальным исполнением назначенного Pod. Между ними нет общей транзакции «два экземпляра приложения готовы». Если API принял Deployment replicas=2, а namespace quota допускает один Pod, desired остаётся два, actual может быть один и condition объяснит отказ.

Идемпотентное действие можно повторить без неправильного дополнительного эффекта. Создание дочернего объекта должно иметь детерминированную идентичность/проверку наличия; внешний платёж нельзя бездумно повторять после сетевого timeout. Kubernetes Job не обещает exactly-once бизнес-действие: возможны повторные Pods и неопределённость результата при отказе. Для Go-разработчика это та же проблема, что idempotency key в API внешней системы. Успех HTTP-запроса контроллера и успех внешней операции могут расходиться.

Владение не определяется именем

ownerReferences связывает объект с конкретным UID владельца, kind/apiVersion/name и ролью controller. Garbage collector, сборщик зависимых ресурсов, использует этот граф при удалении. Label app=ledger-api нужен selector и организации; он сам не делает объект дочерним и не выдаёт права. Namespaced owner references имеют ограничения областей; нельзя сделать произвольную меж namespace зависимость и ждать корректной сборки. Controller owner и SSA field ownership — разные отношения: первый о жизненном цикле объекта, второй о полях.

При cascade=background владелец удаляется, зависимые объекты убираются асинхронно. Foreground удерживает удаление владельца до обработки зависимых согласно блокирующим ссылкам. Orphan сохраняет зависимые объекты. Выбирайте по ожидаемой судьбе данных и наблюдайте, а не считайте delete мгновенной рекурсивной shell-командой. Удаление Deployment не удаляет произвольный Secret с таким же label, и удаление namespace может затронуть множество системных связей.

Finalizer — обещание cleanup

Finalizer — строковый ключ в metadata.finalizers, который требует завершить определённый cleanup до окончательного удаления. API устанавливает deletionTimestamp, объект остаётся доступен, controller выполняет, например, удаление внешнего диска, затем убирает свой ключ. API server не знает бизнес-смысл произвольного ключа и не выполняет cleanup вместо контроллера. Застрявший Terminating часто означает отсутствующий controller, недоступную внешнюю систему или неверные права.

Нельзя просто удалить все finalizers ради зелёного интерфейса: можно потерять сведения об оставшемся диске либо снять защиту активно используемого PVC. Сначала прочитайте ключ, owner, conditions, события, журнал соответствующего controller и реальное внешнее состояние. На отдельном учебном ConfigMap можно добавить собственный inert finalizer, наблюдать deletionTimestamp после delete и вручную снять только его как осознанное завершение модели. Это не пример восстановления CSI-диска.

Наблюдаемый контракт контроллера

Status — сообщение контроллера о наблюдении, spec — желаемая конфигурация. Condition содержит type/status/reason/message и время перехода, но один condition не является полным журналом истории. Events — ограниченные по хранению диагностические записи, их отсутствие не доказывает отсутствие отказа. Сопоставляйте generation и observedGeneration, ReplicaSet revisions, Pod conditions и фактический HTTP. Контроллер может отставать, API может быть перегружен, а внешнее действие занимать время.

Scheduler наблюдает Pods без spec.nodeName. Scheduling cycle получает снимок cluster state и выполняет фильтры допустимости: ресурсы, selector/affinity, taints, доступность томов и другие plugins. Requests и limits имеют разные адресаты

Request — заявка для планирования и распределения ресурса; limit — верхняя граница исполнения, применяемая runtime/Linux при соответствующем ресурсе. CPU 50m означает 0.05 CPU единицы, где одна CPU примерно соответствует одному логическому ядру доступной машины. Memory 32Mi — 32×2²⁰ байт; 32M — 32×10⁶, это разные величины. Scheduler суммирует requests вместе с накладными расходами и особыми правилами init/sidecars, а не текущий RSS процесса. Allocatable node — доступный workloads бюджет после резервов и ограничений, не вся физическая RAM.

Пример: node allocatable 1500m CPU и 2 GiB, уже назначено requests 1200m/1.5 GiB. Новый Pod 400m/128Mi не проходит CPU даже при фактической загрузке 5%. Уменьшить request без измерения — риск переподписать CPU; добавить память не решит CPU filter. Limits CPU может приводить к throttling, ограничениям доступного CPU-времени, без перезапуска. Memory limit при невозможности освободить память может привести к OOM kill. Реальное потребление, request и limit надо видеть тремя отдельными рядами.

Заявки занимают 1200m из 1500m, измеренная работа — 75m
Две отдельные шкалы одной и той же мощности узла. Вверху учтённые requests занимают 1200m, свободно 300m. Запрос нового Pod на 400m длиннее остатка на 100m. Внизу измеренная работа занимает только 75m. Этот маленький расход не освобождает заявку для планировщика.

Изменить одно условие мысленно

Если другая нагрузка освобождает request 100m, остаток становится 400m и новый Pod может пройти именно CPU-фильтр. Если уменьшается только её фактическая работа с 75m до 20m, прежний учёт requests остаётся 1200m и CPU-фильтр продолжает отказывать. Даже пройденный CPU-фильтр не снимает taints, ограничения тома и affinity.

Affinity, taints и topology

nodeSelector требует совпадения labels node. Required node affinity — логическое условие обязательного выбора; preferred — предпочтение при scoring. Pod affinity/anti-affinity выражает отношение к размещению других Pods с учётом topologyKey. Taint помечает node нежелательным/недопустимым для Pods без подходящей toleration. Toleration разрешает терпеть taint, но не направляет Pod именно на этот node. NoSchedule влияет на новые назначения, NoExecute может также эвакуировать уже назначенные Pods по условиям/tolerationSeconds. Control-plane taint оставляем в VM-профиле с worker; не убираем его просто ради доступного места без пересчёта резерва.

Topology spread constraints задают допустимый skew распределения по доменам, например kubernetes.io/hostname. Два replicas на одном node переживают сбой одного процесса, но не его VM. Required anti-affinity на двух replicas при одном допустимом worker закономерно оставляет один Pending. Называть это «ошибкой Kubernetes» неверно: требования несовместимы с топологией. Для небольшого стенда используйте preferred или второй реальный worker и объясните компромисс. Labels topology — вход доверия: kubelet не должен иметь возможность сам назначить себе защищённую метку изоляции.

Preemption и граница исправления

Priority определяет относительную важность Pod при очереди и возможной preemption, вытеснении менее приоритетных Pods ради допустимого размещения. Это не мгновенное получение CPU и не гарантированный обход всех constraints. Affinity/volume topology могут оставлять задачу невыполнимой после вытеснения; PDB учитывается best effort при preemption, не даёт абсолютного запрета. Не выдавайте обычному учебному приложению системный priorityClass ради ускорения.

kubelet не является scheduler

kubelet — node agent. Он наблюдает назначенные этому node Pods, также читает локальные static Pod manifests, согласует их исполнение и публикует status/Node conditions. Scheduler выбрал wk1, но не запустил там процесс сам. Static Pods control plane kubeadm запускаются kubelet из /etc/kubernetes/manifests; mirror Pod в API показывает их состояние, но удаление mirror-объекта не удаляет локальный manifest и не останавливает систему навсегда. Не кладите backup YAML в эту директорию: kubelet может попытаться исполнять и его.

Граница CRI и sandbox

Для нового Pod kubelet подготавливает credentials/volumes, вызывает CRI runtime service. RunPodSandbox создаёт среду Pod, включая сетевой namespace и инфраструктурную pause-задачу в обычном Linux containerd-профиле. Network namespace — отдельные interfaces/routes/ports Linux, а не обязательно отдельное ядро. Контейнеры Pod обычно разделяют Pod network namespace, поэтому localhost:8080 одного контейнера доступен соседу в том же Pod. Два контейнера, слушающие тот же адрес/порт в одном Pod, конфликтуют. PID namespace не разделяется между обычными контейнерами автоматически; shareProcessNamespace — отдельная настройка.

Runtime вызывает CNI ADD с container ID, namespace path, interface name и сетевой конфигурацией. Плагин/IPAM выделяет IP, создаёт veth (парный виртуальный Ethernet-интерфейс), routes и возвращает результат. IPAM, IP address management, — управление выдачей адресов. containerd не придумывает всю сеть сам, kube-proxy не создаёт Pod veth. Если CNI отсутствует, sandbox может не подготовиться, хотя image приложения уже лежит на диске. FailedCreatePodSandBox направляет диагностику к kubelet/runtime/CNI, а не к функции main Go.

Образ, rootfs, shim и runc

Image pull обращается к registry, получает manifest и blobs по digest, проверяет content и распаковывает filesystem snapshots. Tag — изменяемое имя, digest — идентичность конкретного содержимого manifest. Snapshotter containerd, здесь overlayfs, подготавливает rootfs из слоёв и writable layer. Затем runtime v2 shim поддерживает жизнь задачи и stdio/reaping независимо от краткоживущего вызова runc. runc использует OCI runtime specification — описание процесса, namespaces, mounts, capabilities и cgroups — для создания Linux-процесса. OCI image specification описывает другой объект: упаковку образа. Не называйте оба формата одним Dockerfile.

От контейнера к процессу ведут PID и cgroup path. От Pod к контейнеру — containerStatuses.containerID. В контейнере PID 1 относится к его PID namespace; на node у того же процесса другой PID. Mount namespace определяет видимость mounts, UTS — hostname, IPC — механизмы межпроцессного обмена, user namespace при поддержке меняет отображение UID. Эти границы не заменяют seccomp, capabilities и защиту ядра. Один hostPath или privileged может существенно разрушить ожидаемую изоляцию.

# Read-only diagnostics inside your own node VM:
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock pods
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps -a
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock inspect CONTAINER_ID
sudo ctr --namespace k8s.io images list
sudo journalctl -u kubelet --since '-10 min'
sudo journalctl -u containerd --since '-10 min'

crictl разговаривает с CRI и показывает взгляд kubelet-compatible runtime. ctr — низкоуровневый клиент containerd; обход kubelet при ручном удалении task не становится корректным Kubernetes rollout. Inspect/logs могут раскрывать environment и пути. Разделяйте ImagePullBackOff, CreateContainerConfigError, sandbox/network, runtime create и terminated exit code. Одинаковый красный Pod в интерфейсе может иметь пять разных причин.

Измеряем холодный и тёплый старт

Разделите время: очередь scheduler, pull manifest/blobs, unpack, sandbox CNI, mounts CSI, create/start process, startup/readiness probes. В «холодном» опыте образ отсутствует только в личном подготовленном node; в «тёплом» уже сохранён. Не очищайте весь /var/lib/containerd ради теста. Фазы, состояния и restart

Pod phase Pending/Running/Succeeded/Failed/Unknown — грубая сводка, не полный state machine всех процессов. У каждого container state Waiting/Running/Terminated есть reason, exit code и timestamps; Pod conditions показывают отдельные признаки PodScheduled, Initialized, ContainersReady, Ready и предусмотренные readiness gates. Running допускает контейнер, который стартует, перезапускается или не готов. CrashLoopBackOff — отображаемая причина задержки повторных стартов, а не отдельная Pod phase.

restartPolicy на обычном Pod задаёт Always/OnFailure/Never для соответствующих контейнеров. Deployment использует Always; Job — Never или OnFailure по своей семантике. kubelet может перезапустить контейнер в том же Pod UID и сетевой среде, увеличив restartCount. Если VM потеряна, controller создаёт другой Pod на другом допустимом node: старый UID не переносится. Путь writable layer контейнера и emptyDir имеют разные сроки: emptyDir переживает рестарт контейнера внутри живого Pod, но не удаление самого Pod. PersistentVolume существует по отдельному lifecycle.

Startup, readiness и liveness задают разные вопросы

Startup probe даёт программе время первоначально стать работоспособной и блокирует liveness/readiness до своего успеха. Liveness — свидетельство, что контейнеру нужен перезапуск при систематическом отказе выбранной проверки. Readiness — готовность получать трафик данного Service; отрицательная readiness обычно исключает endpoint из готовых, но сама не перезапускает контейнер. Если API зависимости временно недоступен, liveness, зависящий от него, может устроить restart storm без пользы. Readiness проверяет только необходимые для обещанной операции зависимости, иначе частичный сбой выключит весь сервис.

Наш Go /livez возвращает 200, пока handler может исполняться; /readyz управляется готовностью приложения. Это учебный stateless сервис без внешней БД. HTTP 200 не доказывает отсутствие deadlock в другой goroutine или корректность бизнес-данных. Порог startup 30×2s в YAML — приблизительный бюджет числа неудач с периодом, а не точная гарантия запуска ровно через 60s; scheduling/timeout и фазирование влияют на время. failureThreshold и periodSeconds должны быть выведены из измеренного распределения старта и допустимого recovery, не скопированы как универсальные числа.

Именованный порт http в каждой проверке разрешается в containerPort: 8080. Указание containerPort само не создаёт listener: его открывает Go через net.Listen. Поле timeoutSeconds не задано, поэтому сервер добавляет стандартное значение 1 секунда. В общем случае HTTP-коды от 200 до 399 считаются успехом такой проверки; наши обработчики возвращают 200 либо, у выключенной readiness, 503. Probe проверяет ответ узлу, а не внешний путь клиента через DNS и Gateway.

В опыте с неверным /missing-readyz Go отвечает 404 только readiness. У нового Pod можно одновременно увидеть Running, успешную liveness, нулевой restartCount и Ready=false. Если заменить также liveness на неверный путь, появится другой механизм — рестарт после порога ошибок. Сравнивайте timestamp начала контейнера, restartCount и UID Pod: эти поля покажут, какой именно переход произошёл.

Init и restartable sidecar в выбранной линии

Обычные initContainers выполняются до application containers последовательно и должны завершиться успешно. Они удобны для короткой подготовки файла/проверки, но бесконечное ожидание внешней БД может удерживать Pod в Init без видимого процесса приложения. Native sidecar определяется как initContainer с restartPolicy: Always; эта возможность stable с Kubernetes 1.33 и действует в 1.36. Такой контейнер может продолжать работать после инициализации и участвует в определённом порядке запуска/остановки и учёте ресурсов. Это отличается от «просто второго обычного container».

Не вычисляйте request Pod простым сложением всех init и main: Kubernetes учитывает последовательные init, перекрывающиеся restartable sidecars, overhead и поддерживаемые resource semantics. Сначала посмотрите итоговый объект и документацию версии. Sidecar log-agent нужен лишь при наличии подтверждённой задачи: kubelet уже собирает stdout/stderr контейнеров. Ещё один контейнер добавляет память, images, startup и доверие, даже если его конфигурация занимает три строки.

SIGTERM, endpoint и grace period

Удаление устанавливает deletionTimestamp и запускает завершение. Kubelet выполняет preStop, если он предусмотрен и применим, затем посылает stop signal процессу; по окончании grace period оставшиеся процессы принудительно убиваются. preStop расходует тот же общий бюджет, поэтому sleep 20 при grace 15 не создаёт ещё 20 секунд. EndpointSlice отмечает terminating endpoint и readiness меняется по правилам; распространение до всех dataplanes и внешних load balancers не мгновенно. Удаление Pod и прекращение всех клиентских соединений — разные события.

Go-бинарник запускается напрямую как ENTRYPOINT, получает SIGTERM через signal.NotifyContext, снимает внутреннюю readiness и вызывает http.Server.Shutdown с бюджетом 8s; YAML даёт 15s grace. Shutdown закрывает listeners и ожидает активные запросы, но не откатывает уже записанные данные и не ждёт бесконечные hijacked/WebSocket соединения автоматически. Здесь нет preStop: мы не маскируем механикой sleep неопределённый внешний drain. Для настоящих долгих операций измерьте длительность, ограничьте deadline, обеспечьте idempotency и согласуйте максимальное время запроса с grace.

kubectl --context "$LAB_CONTEXT" -n lab get pod -l app=ledger-api -w
kubectl --context "$LAB_CONTEXT" -n lab logs POD_NAME -c api --previous
kubectl --context "$LAB_CONTEXT" -n lab rollout restart deployment/ledger-api
kubectl --context "$LAB_CONTEXT" -n lab rollout status deployment/ledger-api --timeout=120s

Previous читает доступный журнал предыдущего экземпляра контейнера, а не все версии приложения за месяц. Rollout restart меняет Pod template annotation и вызывает замену Pods, даже если image tag прежний; данные/внешние операции от этого не возвращаются. Сравните UID, restartCount и ReplicaSet до/после: рестарт контейнера и rollout дают различную картину.

Deployment и ReplicaSet для stateless HTTP

ReplicaSet поддерживает число подходящих Pods по selector. Deployment управляет набором ReplicaSets и rollout Pod template. Наш ledger-api не хранит уникального локального бизнес-состояния, поэтому новая реплика взаимозаменяема. Изменение image/env/resources в template создаёт новую revision/ReplicaSet; изменение replicas обычно масштабирует существующий набор. Selector Deployment должен совпадать с template labels и у существующего Deployment в существенной части неизменяем. Не делайте selector зависящим от version: иначе каждый выпуск требует менять идентичность охвата.

RollingUpdate с maxSurge=1/maxUnavailable=0 при одном replica требует временного места для двух Pods. При полном node rollout может остановиться Pending, сохраняя старый рабочий Pod. Это ожидаемая цена минимизации добровольной недоступности. Recreate сначала останавливает старые и допускает явный перерыв; иногда нужен для несовместимого доступа к единственному диску. progressDeadlineSeconds отмечает отсутствие прогресса condition, а не выполняет автоматический rollback. rollout undo возвращает старую Pod template, не ConfigMap content, миграцию БД или удалённые данные.

StatefulSet сохраняет связь имени и тома

StatefulSet даёт устойчивые имена Pod с ordinal, предусмотренный порядок создания/обновления и связь volumeClaimTemplates с экземпляром. Headless Service, clusterIP: None, используется для сетевой идентичности/обнаружения отдельных Pods. Это полезно для программ, которым действительно нужна идентичность участника. Stable DNS не означает неизменный IP. PVC могут сохраняться после удаления Pod/StatefulSet в зависимости от retention policy; это защищает данные от простого rollout, но требует учёта оставшихся дисков.

Минимальное отличие от Deployment: kind: StatefulSet, spec.serviceName, selector/template и volumeClaimTemplates; также создаётся headless Service. Но набор из трёх Pods базы не создаёт репликацию данных сам: приложение должно иметь свой consensus/replication/bootstrap и backup. При отказе node RWO-disk может ждать detach/fencing, а local PV вообще остаётся на старой VM. Насильственное удаление старого Pod без fencing рискует получить два писателя одной идентичности.

DaemonSet следует за nodes

DaemonSet обеспечивает экземпляр агента на каждом подходящем node согласно selector/affinity/taints и политике обновления. Подходит CNI, log collector, node exporter; не служит простой заменой Deployment replicas=N. Новый допустимый node получает Pod, удалённый теряет его. Часто агенту нужны host mounts/privileges, что расширяет доверие: компрометация CNI DaemonSet близка к компрометации node. При ошибке «есть на двух nodes из трёх» изучайте selector, tolerations и status desired/current/available, а не только общий список Pods.

Job и CronJob не дают exactly-once

Job управляет завершением заданного числа успешных выполнений; completions и parallelism задают требуемую работу и допустимую параллельность. backoffLimit ограничивает повторные ошибки, activeDeadlineSeconds — время активности по своей семантике. Pod template использует restartPolicy Never/OnFailure. TTL (time to live, срок жизни) после finished — отдельная политика удаления диагностических объектов, её не ставим слишком короткой перед исследованием. При timeout внешней записи клиент мог не получить ответ после успешного действия, поэтому повтор Job должен быть безопасен на уровне приложения.

CronJob создаёт Jobs по расписанию, а не держит один cron-процесс в Pod. schedule: "*/5 * * * *" задаёт период, timeZone: Etc/UTC — явную временную зону, concurrencyPolicy: Forbid запрещает перекрытие именно Jobs этого CronJob при предусмотренных условиях; Replace заменяет активный запуск, Allow допускает. startingDeadlineSeconds определяет опоздание, history limits — сохранение объектов. Перевод часов, downtime controller и приостановка влияют на пропущенные запуски. Это не система гарантий банковского расписания без собственного ledger/idempotency.

Выбираем по требованию, затем проверяем цену

 | Требование | Минимальный механизм | Что проверить при отказе

 | Взаимозаменяемый HTTP | Deployment + Service | ReplicaSet conditions, probes, image, свободное место для surge

 | Личность участника/свой диск | StatefulSet + Service/PVC | Ordinal, PVC topology, detach, состояние самого приложения

 | Конечная работа | Job | Exit code, retries, дедупликация внешнего эффекта

Число объектов — тоже стоимость: 1000 коротких Jobs создают Pods, Events, status writes и cleanup, даже при секунде CPU каждый. Измеряйте API rate, время очереди и долю инфраструктурных действий. Иногда один внешний scheduler с устойчивой очередью проще. Kubernetes оправдан, когда его lifecycle и policy решают реальную задачу, а не только добавляют ещё одну конфигурацию.

workload-patterns.yaml содержит действительные отдельные спецификации ReplicaSet, StatefulSet с headless Service, DaemonSet и CronJob; Pod, Deployment и Job уже даны в основном наборе. Выбирайте один документ и исследуйте его lifecycle; основной ledger-api Deployment не удаляется.

У ReplicaSet минимальный управляющий договор — replicas, selector и template. У StatefulSet дополнительно serviceName и volumeClaimTemplates: создаваемый claim data-ledger-member-0 связывает конкретный ordinal с диском. Ему нужен свободный совместимый PV; уже Bound ledger-local не станет вторым независимым диском, и Pending здесь объясняется отсутствием capacity. Go-сервис не пишет /data: форма показывает mount/identity, а реальные bytes проверяет отдельный writer Job. У DaemonSet нет replicas: количество выводится из допустимых nodes. Демонстрационный HTTP-agent показывает placement, но не является рекомендацией развернуть обычный API по одному на каждом node.

CronJob содержит schedule, timeZone, concurrencyPolicy и jobTemplate с конечной командой, а не бесконечный Deployment. Forbid относится к Jobs одного CronJob; ручной отдельный Job может выполняться параллельно. Сравните ownerReferences CronJob→Job→Pod, Completed status и history limits. Файл прошёл статическую форму OpenAPI, но создания/запуска контроллеров автором не было. Не включайте CronJob до подготовки BusyBox digest в offline runtime.

Environment и projected files

ConfigMap хранит не секретные key/value данные. Наш ledger-config содержит MESSAGE; envFrom подставляет его в environment контейнера при создании процесса. Уже запущенный процесс не получает новое значение от обновления ConfigMap. Чтобы применить новую environment-конфигурацию, создают новые Pods через осмысленный rollout. Если ConfigMap смонтирован как volume, kubelet обновляет projected content с eventual задержкой по своему sync/cache механизму; приложение должно перечитать файл и обработать атомарную смену. SubPath mount не получает обычных автоматических обновлений ConfigMap. Это три разных механизма, у них разное доказательство успеха.

kubectl --context "$LAB_CONTEXT" -n lab get configmap ledger-config -o yaml
kubectl --context "$LAB_CONTEXT" -n lab patch configmap ledger-config --type=merge -p '{"data":{"MESSAGE":"second configuration"}}'
# Existing env still carries the previous value; observe /api/hello first.
kubectl --context "$LAB_CONTEXT" -n lab rollout restart deployment/ledger-api
kubectl --context "$LAB_CONTEXT" -n lab rollout status deployment/ledger-api --timeout=120s

Patch меняет отдельный объект, restart меняет template workload и создаёт новые процессы; только прикладной ответ подтверждает, что процесс прочитал MESSAGE. Для воспроизводимых выпусков удобно versioned/immutable ConfigMap с именем от содержимого и обновлением ссылки в template. Тогда rollback template возвращает ссылку на старую конфигурацию, пока старый объект сохранён. Checksum annotation в Helm — способ инициировать rollout, но его вводит chart; Kubernetes не вычисляет её автоматически.

Secret и чувствительные байты

Secret — API-объект для небольших чувствительных данных с особыми conventions/types и механизмами доставки. Base64 в data — кодирование, не шифрование. stringData удобно для ввода plaintext, но его применение с SSA имеет особенности; не помещайте настоящие секреты в примеры/Git/лог diff. По умолчанию Kubernetes Secret не означает шифрование etcd at rest: администратор отдельно настраивает EncryptionConfiguration/KMS и выполняет миграцию уже записанных объектов. Backup etcd без такой защиты также содержит чувствительные данные.

Environment секрет читается процессом и может утечь через diagnostics, crash dump, exec, логирование конфигурации. Volume требует прав и защиты node. Доступ create Pods часто позволяет получить namespace Secrets косвенно, даже без прямого get secrets. Секрет не становится безопасным от создания второго namespace с тем же паролем. Для лаборатории используйте явное выдуманное значение и изучите форму; реальный API token выпускайте ограниченным и короткоживущим, не сохраняйте в тексте книги.

ServiceAccount — identity, не Linux uid

ServiceAccount представляет workload identity для API. Поле serviceAccountName выбирает её, а Linux runAsUser задаёт совсем другую личность внутри ОС. Современные projected ServiceAccount tokens выдаются TokenRequest API с audience и временем действия; это не обязательно вечный Secret token старых версий. Audience ограничивает предназначенный получатель, expiration — срок, но похищенный допустимый token до отзыва/истечения остаётся credential. Наша служба вообще не обращается к Kubernetes API, поэтому automountServiceAccountToken=false задан и на ServiceAccount, и в Pod.

Конфигурация как часть контракта выпуска

Зафиксируйте image digest, config identity, public ports, Service selectors, resource settings и требуемые API. Отдельно опишите migration/rollback данных. Image tag 0.1.0 должен обозначать одни подготовленные байты в нашем учебном переходе Kubernetes→Helm; нельзя собрать другой бинарник с другим environment-контрактом под тем же tag и считать это тем же выпуском. В registry предпочтителен digest; локальный kind tag допустим как явно ограниченная доставка, пока вы контролируете его соответствие manifest.

Чрезмерная конфигурация тоже стоит денег: большой environment передаётся каждому process, слишком частая смена checksum создаёт лишние ReplicaSets/pulls/starts. Измеряйте число rollout на бизнес-изменение, время готовности и churn, а не только объём YAML. Для ConfigMap/Secret существуют ограничения размера; большие бинарные наборы данных должны жить в подходящем artifact/object storage, не в etcd.

Три пространства адресов

Node IP нужен для связи machines и control plane. Pod IP назначается сетевой реализацией внутри PodCIDR/pool и относится к текущему Pod. Service ClusterIP берётся из ServiceCIDR и обычно не назначен реальному интерфейсу приложения в iptables-модели. Kubernetes network model требует соответствующей связи Pod→Pod и node→Pod, но CNI выбирает routing/overlay и особенности реализации. Нельзя вывести физический маршрут только из API YAML.

В нашем VM-профиле node private IP 192.168.56.10/.11, Calico pool 10.244/16, ServiceCIDR 10.96/16, single-stack IPv4. У kind свои defaults, и он не наследует эти маршруты из главы о VM. На node изучите ip route и адреса Calico interfaces; внутри Pod — его eth0/default route. IP одного Pod после удаления не является постоянным адресом службы. Клиент, кеширующий этот IP бесконечно, обойдёт lifecycle Service и будет обращаться к несуществующему либо другому объекту.

Service описывает выбор, EndpointSlice — адреса

Service selector app=ledger-api выбирает Pods по labels. Контроллер EndpointSlice публикует адреса/порты/conditions выбранных endpoints с разбиением на slices. kube-proxy наблюдает Service и EndpointSlice, программирует dataplane. Сам HTTP-запрос не идёт через API server или процесс kube-proxy в нормальном iptables-пути. EndpointSlice discovery.k8s.io/v1 — основной API endpoint-наборов; старый Endpoints deprecated с Kubernetes 1.33, его ограничения и отсечение больших наборов не следует использовать как нормальную модель масштабирования.

Service.port=80 — порт виртуального Service, targetPort=http ссылается на именованный container port 8080. containerPort лишь описывает порт; он не заставляет Go слушать и не открывает firewall. Пустой EndpointSlice может означать несовпадение selector/labels; addresses с ready=false — проблему готовности; правильные endpoints с timeout — вопрос пакета/policy/listener. Service без selector допустим для ручных endpoints, но автоматического выбора Pods тогда нет.

kubectl --context "$LAB_CONTEXT" -n lab get service ledger-api -o wide
kubectl --context "$LAB_CONTEXT" -n lab get endpointslice -l kubernetes.io/service-name=ledger-api -o yaml
kubectl --context "$LAB_CONTEXT" -n lab get pod -l app=ledger-api --show-labels -o wide

Тип Service и headless

ClusterIP предназначен для внутренней виртуальной точки. NodePort дополнительно задаёт порт на допустимых адресах nodes; в VM-кластере это не готовый интернет load balancer. LoadBalancer просит поддерживающую реализацию предоставить внешний балансировщик; на bare-metal без controller внешний IP может оставаться Pending. ExternalName возвращает DNS CNAME к внешнему имени и не создаёт TCP-прокси/health check. Headless Service с clusterIP=None возвращает адреса endpoints для discovery; клиент сам выбирает и балансирует соединения. Долгоживущий TCP не перебалансируется на каждый HTTP-запрос только потому, что replicas выросли.

DNS-запрос до HTTP

CoreDNS обслуживает кластерные имена, например ledger-api.lab.svc.cluster.local. kubelet формирует resolv.conf Pod по dnsPolicy/dnsConfig, включая search domains и ndots. Короткое ledger-api из namespace lab разрешается иначе, чем из helm-lab; полное имя явно задаёт область. DNS возвращает ClusterIP, затем клиент открывает TCP к нему. NXDOMAIN, timeout DNS и TCP connection refused — разные результаты. При большом ndots внешнее имя без завершающей точки может вызвать дополнительные search-запросы; снижать ndots нужно после измерения запросов и понимания имён, а не как универсальный tuning.

В поставляемом diagnostic.yaml используется закреплённый BusyBox: в нём есть nslookup, wget, cat и sh; наличие dig и curl этот образ не обещает. Полный опыт из следующей главы сравнивает DNS, прямой IP и HTTP именно этими средствами. Для других инструментов заранее выберите и доставьте другой проверенный образ, а затем запишите его точную ссылку. Scratch-образ Go не содержит даже shell: отказ exec … -- sh в нём объясняется отсутствием файла программы.

Измеряйте задержку DNS, долю ответов из кэша, NXDOMAIN и тайм-ауты отдельно от HTTP. Увеличение числа Pods приложения не исправляет недоступный DNS Service. Внешний рекурсивный DNS и кластерный модуль CoreDNS отвечают за разные имена и участки запроса.

Фиксируем наблюдаемый эксперимент

Пусть клиент Pod A на cp1 имеет 10.244.1.2:41000, backend Pod B на wk1 — 10.244.2.3:8080, Service S — 10.96.10.20:80. Это условные адреса внутри объявленных подсетей; фактические берите из get pod/service. cp1 и wk1 соединены underlay 192.168.56.10/.11 с MTU 1500. У клиента нет hostNetwork, у Service нет session affinity и специальных traffic policies, выбирается B на другом node. Фиксируем один первый TCP SYN, затем conntrack ведёт это соединение.

Pod→Pod без Service

Прямой пакет A→B выходит через eth0 Pod к host-side veth. Calico применяет установленные policy/routing правила, node определяет удалённый endpoint. VXLAN, Virtual Extensible LAN, инкапсулирует внутренний Ethernet/IP пакет в UDP между node IP, в данном профиле UDP 4789. Underlay переносит внешний пакет 192.168.56.10→192.168.56.11, а внутренние Pod IP остаются A→B. На wk1 VXLAN decapsulation снимает оболочку и маршрутизация доставляет внутренний пакет к veth B с применимой policy. В той же VM удалённого tunnel hop нет: host routes ведут к peer veth.

Нельзя заключить из этого, что в любом CNI есть bridge cni0 или что каждый Pod проходит Docker bridge. Calico использует собственные interfaces/routes. VXLAN Always в выбранном pool требует инкапсуляции для межузлового Pod-трафика даже в общей underlay подсети; CrossSubnet имел бы иные условия. BGP/native routing, IPIP и WireGuard изменили бы оболочку/маршруты. Схема описывает логические границы; точные netfilter chain names/порядок подсистем проверяют на реальном node конкретной версии.

Service добавляет DNAT и состояние соединения

При обращении A→S первый пакет на node клиента попадает в правила Service, установленные kube-proxy. Из готовых endpoints выбирается B, destination NAT, DNAT, меняет destination 10.96.10.20:80 на 10.244.2.3:8080. Для этого внутрикластерного не-hairpin сценария исходный Pod IP обычно сохраняется; специальные masquerade настройки/исключения меняют условия. Затем маршрутизация Calico доставляет пакет к B через VXLAN. Service IP не должен появляться на eth0 Go-процесса как адрес listener: процесс принимает на PodIP:8080/0.0.0.0:8080.

Conntrack — отслеживание состояния соединений Linux/netfilter — сохраняет соответствие исходного и переведённого tuple. Ответ B→A возвращается по предусмотренному маршруту к node, где применялась трансляция; обратное NAT представляет клиенту ответ от Service IP:80. Если ответ ушёл в обход необходимого stateful узла, асимметрия и filtering могут сломать соединение. TCP keepalive, long-lived соединения и UDP timeouts имеют последствия для удаления endpoint: обновление списка endpoints не переписывает магически все старые соединения.

# Read-only, only on your prepared VM nodes:
sudo ip -details link show vxlan.calico
sudo ip route get 10.244.2.3
sudo iptables-save -t nat
sudo conntrack -L -p tcp
sudo tcpdump -ni any 'udp port 4789 or (host 10.244.2.3 and tcp port 8080)'

iptables-save читает правила, iptables -F их разрушает и здесь не нужен. Ubuntu iptables может использовать nf_tables backend; это не означает kube-proxy mode=nftables. Узнайте iptables --version и kube-proxy ConfigMap. conntrack/tcpdump требуют средств и прав внутри личной VM; capture содержит данные трафика. Снимайте короткий отрезок и сверяйте четыре tuple: до DNAT, после DNAT, outer VXLAN, обратный ответ. Вывод здесь не подделывается заранее.

Текстовое описание и границы схемы

У Pod A своё сетевое пространство имён Linux: отдельные интерфейсы, маршруты и сетевые настройки. Это не namespace lab в API Kubernetes. Два конца veth соединяют eth0 Pod с сетевым пространством узла cp1. Имя узлового конца берут из реальной VM, а не угадывают.

До трансляции источник — 10.244.1.2:41000, назначение — 10.96.10.20:80. Правила iptables, заранее установленные kube-proxy, выбирают готовый backend B. Ядро выполняет DNAT: байты IPv4 назначения 0a 60 0a 14 заменяются на 0a f4 02 03, порт TCP 00 50 — на 1f 90. Исходные IP и порт в этой модели сохраняются; это надо проверить при своих настройках masquerade. kube-proxy не пересылает SYN через свой пользовательский процесс.

Маршрут Calico ведёт к удалённому B через VXLAN. В UDP-пакете от 192.168.56.10 к 192.168.56.11:4789 находится VXLAN-заголовок, затем внутренний Ethernet-кадр с уже переведённым IPv4/TCP-пакетом. UDP source port и VNI берут из настройки и трассы. MAC, TTL, прочие поля и контрольные суммы здесь не заданы; при DNAT соответствующие контрольные суммы корректируются, а маршрутизация также меняет TTL. Внешние заголовки не заменяют внутренние адреса A и B.

На wk1 ядро снимает VXLAN-оболочку и доставляет внутренний пакет через veth в Pod B с применимой policy. SYN обрабатывает TCP-стек ядра; приложение получает установленное соединение через accept — приём готового соединения. У Go-процесса нет listener на ClusterIP. В ответном направлении conntrack на cp1 обеспечивает обратную трансляцию: ответ B:8080 → A:41000 клиент видит как S:80 → A:41000. Ответный маршрут на рисунке не показан.

Сверяйте поля с короткой трассой в своей VM. Формат оболочки: RFC 7348, раздел 5; трансляция Service: kube-proxy iptables, Kubernetes 1.36. Поля и байты на рисунке — проверяемый расчёт из условных адресов главы.

nftables, IPVS и eBPF — разные реализации

В Kubernetes 1.36 nftables proxy mode уже stable (с 1.33), iptables остаётся поддерживаемым; IPVS deprecated с 1.35. Stable не означает default. Наша конфигурация явно pin mode=iptables. Нативный nftables режим использует другие правила/API ядра и имеет отличия NodePort/localhost/firewall; миграция требует проверки kernel/tooling и документации версии. IPVS использует Linux IPVS вместе с другими сетевыми механизмами, но deprecated путь не выбираем для нового учебного стенда. Не смешивайте chain names iptables с maps nftables в одной воображаемой трассе.

eBPF dataplane может заменить kube-proxy: программы ядра и maps реализуют load balancing и policy, иногда выполняя service translation на другой точке, включая socket-level hook. eBPF, extended Berkeley Packet Filter, — механизм безопасно проверяемых программ в kernel, а не протокол сети. Сравнение с iptables требует выбранной CNI версии/mode, включённых optimizations, conntrack/DSR и измерения. Нельзя обещать «eBPF всегда без NAT и быстрее»; путь и выгода зависят от сценария.

MTU, fragments и измерение

При underlay 1500 и IPv4 VXLAN overhead около 50 байт внутренний MTU 1450 предотвращает фрагментацию в этом профиле. Внешний IPv6 или дополнительный VPN уменьшают бюджет. Симптом MTU — маленький HTTP работает, большой response/TLS зависает; это отличается от полного отсутствия маршрута. Проверяют path MTU, ICMP Packet Too Big/fragmentation needed и captures, а не только ping по умолчанию. Измеряйте packets/s, bytes/s, retransmits, conntrack occupancy/drops, node softirq CPU и p95 latency при одинаковом числе endpoints. Увеличение Service replicas не исправляет заполненную conntrack table.

Как разместить диагностический клиент на cp1

В базовом VM-кластере control-plane taint сохраняется, поэтому обычный application Pod туда не попадёт. diagnostic.yaml размещает только client-allowed на cp1 через явные nodeSelector и toleration; это административная подготовка учебного эксперимента, а не снятие taint со всего node. Backend ledger-api остаётся на wk1. Так можно исследовать cross-node путь на двух небольших VM без третьего worker. IP из схемы замените фактическими из get pod -o wide. В kind этот VM-specific файл с cp1 не применяют: имя node и CNI там другие.

Названия сетевых механизмов

iptables — пользовательский интерфейс управления определёнными netfilter правилами Linux; nftables — другая инфраструктура правил и интерфейс ядра. IPVS (IP Virtual Server) — механизм виртуальных сервисов/балансировки Linux, который использует соответствующий proxy mode. IPIP (IP in IP) помещает IP-пакет в другой IP-пакет и отличается от выбранного VXLAN с UDP. Эти имена описывают разные уровни реализации. Netfilter hooks, routing decisions и CNI policy изучают в заданном стеке, а не через одну универсальную стрелку «Kubernetes network».

Как policy меняет состояние доступа

До policy обычный Pod не изолирован этим API в соответствующем направлении. NetworkPolicy выбирает Pods через podSelector и отдельно объявляет Ingress/Egress. Как только Pod выбран применимой ingress policy, допускается объединение всех разрешающих ingress rules для него; egress изоляция включается отдельно. Правила аддитивны: новая «запрещающая» policy не отменяет широкое allow другой. Для соединения должны разрешать обе изолированные стороны: egress источника и ingress назначения. Reply трафик установленных разрешённых соединений обрабатывается реализацией stateful policy по её документированной семантике.

Файл 30-policy выбирает только ledger-api и разрешает ingress TCP 8080 от Pods namespace lab с label access=ledger. podSelector внутри from без namespaceSelector относится к тому же namespace. Если один элемент содержит и namespaceSelector, и podSelector, они сочетаются как AND; два разных элемента списка — OR. Это маленькое различие YAML способно открыть доступ всему namespace вместо одной группе. ipBlock описывает IP-префиксы, но packet rewrite до/после policy и node-originated трафик зависят от CNI; для Pod identities предпочитают selectors с контролируемыми labels.

kubectl --context "$LAB_CONTEXT" -n lab apply -f manifests/30-policy.yaml
kubectl --context "$LAB_CONTEXT" -n lab get networkpolicy ledger-ingress -o yaml
kubectl --context "$LAB_CONTEXT" -n lab get pod --show-labels
# Test from two prepared diagnostic Pods in lab: one with access=ledger,
# one without. Use Service DNS and direct Pod IP, record both outcomes.

Важны два наблюдения: allowed client действительно получает HTTP, denied client действительно получает ожидаемый timeout/reject по implementation. Одно отсутствие ответа может быть сломанным DNS/listener, поэтому baseline до policy обязателен. Проверка через kubectl port-forward не проходит обычный Pod→Service dataplane и не доказывает policy. На default kindnet API-объект policy может сохраниться без enforcement; это не нарушение schema и не защита.

Egress и DNS требуют явного проекта

Default deny egress часто ломает DNS. Для DNS нужны UDP и TCP 53 к реальному кластерному resolver с namespace/pod selectors, если CNI обрабатывает эту точку соответствующим образом. NodeLocal DNSCache при наличии меняет адрес resolver и путь, поэтому нельзя скопировать правило к kube-dns Pod и считать его универсальным. Доступ к внешнему API требует IP/port по политике; стандартный NetworkPolicy не выражает HTTP path, пользователя, TLS certificate identity или динамический FQDN по доменному имени. Такие функции — extensions конкретной CNI/прокси, с отдельной моделью и совместимостью.

Диагностируем DNS по слоям

Сначала зафиксируйте /etc/resolv.conf клиента, имя запроса, search/ndots, сервер и точный результат. Полное ledger-api.lab.svc.cluster.local. с конечной точкой исключает добавление search suffix. Если DNS timeout — проверьте resolver Service endpoints, UDP/TCP путь и egress; NXDOMAIN — имя/namespace/тип Service и CoreDNS plugin; правильный IP плюс TCP timeout — переходите к packet/policy; connection refused — listener/port/конкретный маршрут с reject. Readiness исключила endpoint? Тогда DNS ClusterIP может оставаться корректным, а за ним нет готового backend.

Не рестартуйте CoreDNS первым действием. Посмотрите его logs, config, ready replicas, API-доступ и upstream. При DNS query storm измерьте qps по имени/типу, cache hit, response codes, request duration и CPU. Увеличить replicas имеет смысл, если есть нагрузка/очередь и обеспечено распределение; это не исправит ошибочный upstream DNS IP. На ноутбуке каждое дополнительное системное приложение отнимает RAM у workload, поэтому cache/ndots/client retry исследуются до масштабирования.

Namespace и label как границы доверия

Пользователь, которому разрешено изменять label access=ledger или создавать Pods под нужной identity, может получить сетевой доступ по правилу. RBAC, admission и policy должны поддерживать общий контракт. Namespace сам по себе не запрещает пакеты и не изолирует host kernel. hostNetwork Pods, node traffic, DNS, external NAT и policy extensions имеют особые условия. Документируйте, какие угрозы правило закрывает, а какие требуют workload/node isolation.

Два конкретных клиента и сравнимые запуски

Диагностические Pods используют официальный BusyBox1.37.0 по проверенному 01.11.2026 OCI index digest a7dbc319…; source log содержит полный digest. Он один и тот же в client и storage Job. Образ не исполнялся автором. Staging/import должен сохранить content именно под этой ссылкой на каждом нужном node. Клиент без label и клиент access=ledger сначала должны оба проходить до установки policy, иначе сравнение не отделяет policy от исходного сетевого отказа.

kubectl --context "$LAB_CONTEXT" apply -f vm/diagnostic.yaml
kubectl --context "$LAB_CONTEXT" -n lab wait --for=condition=Ready pod/client-allowed pod/client-denied --timeout=120s

kubectl --context "$LAB_CONTEXT" -n lab exec client-allowed -- wget -T 3 -qO- http://ledger-api.lab.svc.cluster.local/api/hello
kubectl --context "$LAB_CONTEXT" -n lab exec client-denied -- wget -T 3 -qO- http://ledger-api.lab.svc.cluster.local/api/hello
kubectl --context "$LAB_CONTEXT" -n lab apply -f manifests/30-policy.yaml
# Repeat both wget commands after policy convergence; record exit codes/body.

После policy expected outcome: allowed получает JSON, denied не устанавливает допустимый HTTP-путь при работающем Calico enforcement. Wget -T3 ограничивает время ожидания, -q убирает служебный прогресс, -O- выводит body в stdout без записи read-only rootfs. Повторите запрос по фактическому ServiceIP и PodIP, чтобы отделить DNS. По окончании исследования эти два диагностических Pods можно явно удалить; namespace, release и данные сохраняются. Investigator роли не хватает exec/create: сетевой опыт выполняет администратор, а ограниченная заявка остаётся отдельной проверкой прав.

Как клиент входит в сеть

Внешнему клиенту нужен достижимый IP/порт: node private IP через разрешённую сеть, load balancer либо reverse proxy. Service type LoadBalancer — запрос реализации, а не встроенная покупка облака. NodePort в VM-кластере требует маршрута и firewall допуска; на Windows с kind может потребоваться port mapping engine. Для первого локального доступа достаточно port-forward с bind 127.0.0.1, но production path и policy этим не проверяются.

externalTrafficPolicy=Cluster допускает маршрутизацию на endpoints других nodes и может требовать SNAT для корректного обратного пути, скрывая исходный IP от backend. Local направляет к локальным готовым endpoints и позволяет сохранять client source IP в поддерживающем path, но node без local endpoint может не обслуживать этот Service; балансировщик должен правильно проверять health и распределение. Нельзя обещать одновременно равномерный load по всем Pods, любой node и сохранение IP без описания реализации. internalTrafficPolicy относится к внутреннему выбору и имеет отдельные последствия.

Ingress — API маршрута, controller — исполнитель

Ingress networking.k8s.io/v1 описывает HTTP(S) host/path→Service и TLS reference. IngressClass указывает предусмотренный класс controller; конкретный controller наблюдает объекты и настраивает proxy/load balancer. Без установленного подходящего controller манифест может быть принят и ничего не обслуживать. pathType Exact/Prefix/ImplementationSpecific имеет значение; annotations часто привязаны к конкретному controller и не являются переносимой Kubernetes функцией. Ingress API заморожен: он остаётся поддерживаемым, но новые сетевые возможности развиваются через Gateway API.

Исторический community ingress-nginx не следует выбирать по старому tutorial: проект объявил retirement на март 2026, дальнейшие security releases не обещаны. Это не тождественно всем продуктам с именем NGINX. Перед выбором изучите актуальный lifecycle конкретного controller и compatibility matrix, не только красивый пример YAML. В этой книге не устанавливаем устаревший controller ради одной страницы hello.

Gateway API распределяет роли

Gateway API — набор отдельно устанавливаемых CRDs и договоров реализации, не встроенный синоним Service. GatewayClass задаёт тип/реализацию, Gateway описывает listeners и инфраструктурную точку, HTTPRoute — маршруты приложения. AllowedRoutes и ReferenceGrant ограничивают attachment и меж namespace references. Существование HTTPRoute без Accepted/ResolvedRefs и готового Gateway не доказывает рабочий путь. На 01.11.2026 официальный latest Gateway API — v1.7.0; пример концептуального baseline использует stable gateway.networking.k8s.io/v1, но совместимость конкретного controller и установленного CRD bundle должна быть проверена отдельно.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: ledger
  namespace: lab
spec:
  parentRefs:
  - name: lab-gateway
    namespace: lab
  hostnames: [ledger.lab.internal]
  rules:
  - backendRefs:
    - name: ledger-api
      port: 80

Это форма маршрута к lab/lab-gateway, совпадающая по именам с поставляемым vm/gateway.yaml. Сам фрагмент Gateway не создаёт. Listener должен разрешать Routes из lab; наш полный файл разрешает только тот же namespace, а Service ledger-api тоже находится в lab. Если перенести Gateway в другую область, придётся согласованно изменить parentRef и allowedRoutes, а при ссылке на backend или сертификат из другой области — требуемый ReferenceGrant. Это разные направления разрешения, их нельзя заменить одним переименованием namespace.

В обычном режиме выбранного Envoy Gateway объекты Gateway и HTTPRoute остаются в lab, а создаваемые контроллером proxy Deployment и Service находятся в envoy-gateway-system. Namespace объекта-намерения не обязан совпадать с namespace его исполняющего прокси. Поэтому ниже proxy ищут по меткам owning-gateway-namespace и owning-gateway-name в envoy-gateway-system; NetworkPolicy разрешает трафик оттуда. Режим развёртывания proxy в namespace Gateway существует отдельно и этим набором не включается. Официальное описание: Gateway Namespace Mode, линия 1.9.

Проверка формы CRD не подтверждает существование всех ссылок: контроллер сообщает об этом через conditions. Версия API также не обещает реализации каждой экспериментальной возможности; проверяют совместимость контроллера и поддерживаемые им функции.

TLS и исходная личность

TLS termination — место завершения защищённого соединения. Сертификат должен покрывать DNS hostname, клиент должен доверять CA, private key хранится как секрет с ограниченным доступом. HTTPS client→Gateway и HTTP Gateway→Pod — разные сегменты; если нужна защита backend-сегмента, настройте поддерживаемый backend TLS/mTLS с проверкой identity, не только https в браузере. X-Forwarded-For — данные уровня HTTP от доверенного proxy, а не доказанный kernel source IP. Приложение должно доверять только известным proxies и корректно разбирать цепочку; внешний пользователь может сам прислать такой заголовок.

Проверка и стоимость входа

Проверяйте последовательно: DNS внешнего имени, TCP, TLS chain/SAN/expiry, listener route conditions, Service endpoints, HTTP body. Измеряйте handshake latency отдельно от keepalive request p95, bytes/s, active connections, queue, 4xx/5xx по причине. Retry proxy способен увеличить нагрузку на уже медленный backend; один клиентский запрос может дать несколько upstream attempts. Timeout/retry budget должен согласоваться с idempotency и временем завершения Pod. В локальном учебном стенде лишний Gateway controller может стоить больше памяти, чем весь Go-сервис; это оправдано изучением маршрутизации, но не обязательным усложнением каждого приложения.

Сохраните digests и импортируйте на каждый допустимый node. Для trusted source перечня смотрите air-gapped guide и release notes, а не случайный blog.

Начальный reserve не меньше 384Mi requests и дополнительный runtime/CRD/API overhead, реальное idle/peak измеряется. На 8GiB не включайте весь набор лабораторных служб одновременно; Gateway optional и включается после базового приложения. Удаление CRDs не является обычной остановкой controller: оно удаляет API/resources и может разрушить другие routes. Сохраняйте установленную инфраструктуру между упражнениями, либо выполняйте отдельное документированное удаление после backup.

От запроса ёмкости к mount

PersistentVolumeClaim, PVC, — запрос workload на объём, access modes и storage class. PersistentVolume, PV, — объект предоставленного storage ресурса с политикой возврата и сведениями о backend. StorageClass задаёт способ provisioning и параметры; это не сам диск. При dynamic provisioning внешний provisioner наблюдает PVC, вызывает CSI CreateVolume, создаёт PV и binding. Static provisioning означает, что администратор заранее создал PV. PVC Bound подтверждает связь объектов, но не доказывает успешный mount на node и прикладной read/write.

CSI, Container Storage Interface, разделяет controller и node операции драйвера. В зависимости от драйвера controller attach через ControllerPublishVolume подключает volume к машине, node stage/publish готовит mount и предъявляет его Pod. Некоторые драйверы не требуют attach; отсутствие VolumeAttachment тогда не ошибка. External provisioner/attacher/resizer/snapshotter — отдельные controllers с нужными версиями/правами, а node plugin — отдельный агент. Нельзя объявить storageclass.provisioner произвольной строкой и ждать встроенной файловой системы.

Управляющий объект, смонтированный путь и сохранённые байты

В нашем static local PV нет удалённого storage API и нет CSI-контроллера, который создаёт диск. Администратор заранее выделяет каталог на wk1. PV описывает этот путь и узел, PVC связывается с подходящим PV, а kubelet предоставляет путь контейнеру. Если каталог пустой, корректное Bound не заполнит его данными; если права запрещают запись UID 65532, связанный PVC не устранит ошибку доступа.

Заявленная capacity.storage: 256Mi и запрос PVC 128Mi участвуют в выборе подходящего PV. Для обычного каталога local volume они сами не устанавливают файловую квоту 256 MiB: доступное место ограничивает настоящий файловый раздел и отдельно настроенные квоты. Поэтому проверяют свободные байты и inode именно на wk1, учитывая соседние потребители этого раздела. Заполнение раздела способно затронуть и другие данные узла.

Job записывает ledger-v1, только если файла ещё нет. Его успешное повторное чтение и тот же hash показывают, что замена потребителя сохранила эти байты. Команда printf в этом упражнении не выполняет отдельный протокол fsync и не доказывает сохранность при внезапном обесточивании. Проверка существования и запись также не образуют атомарной дедупликации двух параллельных писателей. Для базы данных нужны её журнал, синхронизация и согласованный backup; этот небольшой файл показывает срок жизни тома, а не реализует хранилище транзакций.

2. Выбран node и домен

Действует: Scheduler.

Изменение состояния: Topology неизвестна → Известна допустимая зона. Immediate мог бы выделить volume в неподходящем домене.

3. PV связан с PVC

Backend вернул volume identity, а binding сохранён в API.

PVC: Bound; Scheduler: Pod назначен; CSIcontroller: создал volume; PV/backend: IDv1; CSInode/kubelet: mount ещё нет; Приложение: нет write

Изменение состояния: Есть backend volume → Путь виден внутри Pod. Права доступа и filesystem всё ещё могут вызвать отказ.

Приложение записало данные и выполнило требуемый протокол сохранения.

Действует: Application.

PVC: Bound; Scheduler: готов; CSIcontroller: готов; PV/backend: blocksupdated; CSInode/kubelet: I/O работает; Приложение: record+hash

До нового писателя нужны корректные detach, fencing и attach по правилам backend.

Действует: Operator/controllers.

Изменение состояния: Старый node недоступен → Безопасная передача доступа. Force-delete Pod не останавливает прежнего писателя.

Access modes и topology

ReadWriteOnce, RWO, означает предусмотренный read-write доступ с одного node, а не строго один Pod: несколько Pods на том же node могут использовать volume при допустимых условиях. ReadOnlyMany и ReadWriteMany требуют backend/driver поддержки. ReadWriteOncePod, RWOP, ограничивает использование одним Pod в кластере для поддерживающего CSI пути. Эти modes не заменяют POSIX locks, транзакции БД и application fencing. Если два процесса пишут один файл без протокола, Kubernetes не сделает их записи атомарными.

Topology описывает, где volume может быть доступен: zone/node и ограничения backend. WaitForFirstConsumer откладывает provisioning/binding до учёта потребностей первого Pod, чтобы не выделить диск в неподходящей зоне. Immediate может создать volume до выбора node и потом конфликтовать с affinity. Local PV привязан к конкретному node через nodeAffinity. Наш 50-storage.yaml использует no-provisioner и заранее созданный каталог на wk1: данные переживают Pod, но не потерю диска/VM. Это отдельная честная лаборатория, а не «CSI как папка».

Разобранный опыт с локальным PV

В своей wk1 VM создайте /srv/handbook/ledger-data с владельцем uid/gid 65532 и ограниченными правами. Это осознанная подготовка локального диска администратора, а не действие Pod с hostPath. Примените 50-storage: PVC может оставаться Pending до первого consumer из-за WaitForFirstConsumer. После 51-data-job scheduler учитывает nodeAffinity PV и размещает writer на wk1; kubelet монтирует путь, BusyBox записывает ledger-v1 и читает его. Из-за проверки существования файла повторный Job с новым именем не должен перезаписывать содержимое. BusyBox image заранее staged и перед опытом закрепляется реальным digest.

kubectl --context "$LAB_CONTEXT" apply -f manifests/50-storage.yaml
kubectl --context "$LAB_CONTEXT" -n lab get pvc ledger-data
kubectl --context "$LAB_CONTEXT" -n lab apply -f manifests/51-data-job.yaml
kubectl --context "$LAB_CONTEXT" -n lab wait --for=condition=complete job/ledger-write-once --timeout=120s
kubectl --context "$LAB_CONTEXT" -n lab logs job/ledger-write-once
kubectl --context "$LAB_CONTEXT" get pv ledger-local -o yaml

Сначала докажите запись и сохраните hash файла внутри VM. Удалите только завершённый Job, создайте второй с новым metadata.name и тем же claim, проверьте тот же hash. Затем остановите wk1: новый consumer не должен «найти данные» на cp1; он останется без допустимого volume/node. Это демонстрация topology и цены local disk, а не fault-tolerant storage. Не меняйте PV nodeAffinity на cp1: новый пустой каталог с таким же путём не содержит прежних байтов.

Один локальный файл виден через два пути
На диске wk1 файл /srv/handbook/ledger-data/record.txt. PV ledger-local хранит путь и привязку к wk1, PVC lab/ledger-data связан с PV. В Pod writer этот же каталог виден как /data, а файл как /data/record.txt. Замена Pod сохраняет диск, перенос Pod на другой node не переносит файл.

Что переживает каждое изменение

Новый контейнер с тем же смонтированным PVC читает прежний файл. Новый Pod на wk1 также может получить этот PV по ограничениям доступа. Утраченный диск wk1 не восстанавливается новым UID Pod; запуск на cp1 не создаёт там прежние байты. Поэтому проверка hash после обычной замены потребителя и восстановление после потери диска — разные опыты.

Reclaim, expansion, snapshot и backup

Reclaim policy Retain оставляет backend после освобождения claim и требует ручного безопасного разбора/повторного использования; Delete поручает поддерживающему provisioner удаление storage. PVC protection/finalizers предотвращают некоторые опасные удаления, но не являются backup. У StatefulSet есть отдельная PVC retention policy; удаление workload и удаление данных нужно обсуждать независимо. Перед delete PVC выясните драйвер, reclaim, финализаторы, активных consumers и резерв.

Expansion требует allowVolumeExpansion StorageClass и поддержки драйвера; изменение requests.storage запускает расширение, но не уменьшение. Controller resize и filesystem resize могут происходить в разных фазах; наблюдайте conditions/events и реальную ёмкость fs. Snapshot через VolumeSnapshot CRDs/controller/CSI driver создаёт snapshot по возможностям backend. Crash-consistent snapshot фиксирует состояние storage, но не обязательно application-consistent транзакцию. Backup должен находиться в независимой зоне отказа, иметь retention/encryption и доказанный restore. Копия snapshot metadata в том же etcd не сохраняет потерянные blocks backend.

Что измерять, прежде чем менять диск

Нужны объём/рост, IOPS (операции ввода-вывода в секунду), throughput MiB/s, fsync latency p95/p99, queue depth, inode consumption и latency приложения. Для маленьких синхронных записей быстрый sequential MB/s не гарантирует хороший commit latency. Пример: 1000 транзакций/s с одним fsync на транзакцию требуют порядка 1000 fsync/s при заданном concurrency; повышение размера PVC не обязательно повышает IOPS у локального диска. Сначала отличите filesystem-full, quota, permissions, attachment limit, backend latency и application lock contention. У каждого другая корректировка и другой риск.

Как запрос получает личность

kubeconfig содержит clusters с API endpoint/CA, users с credentials/exec plugin и contexts, связывающие их. Он может включать client private key или команду exec, которая запускает локальную программу получения token. Поэтому чужой kubeconfig нельзя считать пассивным безопасным текстом: изучите server, CA, insecure flags и exec до использования. config view --minify показывает текущую связку; --raw способен раскрыть credentials. Context rename меняет локальное имя, но не privileges на сервере.

При client certificate authentication API server проверяет CA/срок/назначение и отображает subject в username/groups по правилам. Private key подтверждает владение identity; CA private key позволяет выпускать новые доверенные credentials и требует более строгой защиты. Token authentication использует свои механизмы, например OIDC или ServiceAccount tokens. Rotation сертификатов kubelet и expiry admin/control-plane certificates — эксплуатационные задачи, а не результат смены пароля Linux.

RBAC задаёт действия над ресурсами

RBAC, Role-Based Access Control, — авторизация через роли и привязки. Role разрешает verbs над apiGroups/resources в namespace; ClusterRole задаёт повторно используемый или cluster-scoped набор. RoleBinding связывает роль с users/groups/ServiceAccounts в namespace, ClusterRoleBinding — на cluster scope. В правилах пишут resource names во множественном числе: deployments, pods/log. get одного Pod не даёт list всех, pods/log отдельно от pods/exec; exec — subresource с потенциальным доступом к данным приложения.

Правила аддитивны и обычно не содержат отрицательного deny, поэтому дополнительная широкая binding может отменить вашу идею «ограниченной роли» своим allow. Wildcards захватывают будущие ресурсы/verbs. Права bind/escalate/impersonate, создание workloads, изменение RoleBindings и чтение Secrets требуют особого внимания: они позволяют расширять доступ косвенно. Namespace administrator, способный создать privileged Pod на обычном node, может пересечь границу namespace и получить node-доверие без cluster-admin названия.

Реальная заявка с ограниченными правами

Файл 20-rbac создаёт investigator: чтение Pods/Services/Events/ReplicaSets/Deployments/EndpointSlices и logs в lab. Нет Secret, exec, patch, delete и cluster-wide Nodes. Администратор проверяет разрешения через SubjectAccessReview/имперсонацию. --as требует собственного impersonate-разрешения и не является входом обычного пользователя без credentials. Для отдельного реального клиента выпустите короткоживущий token с предназначенным audience через разрешённый процесс, положите его в приватный kubeconfig и проверьте server request; не записывайте его в опубликованный пример.

kubectl --context "$LAB_CONTEXT" -n lab apply -f manifests/20-rbac.yaml
kubectl --context "$LAB_CONTEXT" auth can-i get pods --as=system:serviceaccount:lab:investigator -n lab
kubectl --context "$LAB_CONTEXT" auth can-i get secrets --as=system:serviceaccount:lab:investigator -n lab
kubectl --context "$LAB_CONTEXT" auth can-i create pods --subresource=exec --as=system:serviceaccount:lab:investigator -n lab
kubectl --context "$LAB_CONTEXT" -n lab get pods --as=system:serviceaccount:lab:investigator

Ожидаем yes для get pods, no для secrets и pods/exec при отсутствии иных bindings. Это предсказание политики, не выполненный вывод. Проверка can-i отвечает про авторизацию конкретного запроса, не про admission и прикладной успех. Прочитать logs можно и без exec в scratch-контейнере; если нужен новый ephemeral debug container, это отдельная выдача полномочий и admission.

Secrets at rest и аудит

EncryptionConfiguration API server задаёт providers для шифрования выбранных ресурсов перед записью в etcd; KMS позволяет вынести ключевой материал в отдельную систему. Чтение через API всё равно выдаёт расшифрованные данные разрешённой identity. Нужно учитывать все API server instances, порядок providers, ключи для чтения старых записей и controlled rewrite существующих Secrets. Потеря decryption keys делает backup etcd недостаточным; ключи сохраняют защищённо отдельно с проверкой восстановления.

Audit policy определяет, какие API-события и на каком уровне сохраняются. Request/Response bodies могут содержать Secret, поэтому объём и confidentiality важнее лозунга «логировать всё». Нужны actor, verb, resource, namespace, response code, timestamp и correlation с инцидентом; retention и целостность журнала. API audit и stdout приложения отвечают на разные вопросы. Измеряйте audit disk growth и latency, иначе сама наблюдаемость может исчерпать control-plane диск.

Restricted как воспроизводимый baseline

Pod Security Standards задаёт профили Privileged/Baseline/Restricted; Pod Security Admission применяет enforce/audit/warn на namespace согласно labels. Это встроенный admission-механизм, а не старый PodSecurityPolicy: PSP удалён с Kubernetes 1.25. Наш lab pin enforce-version=v1.36, чтобы изменение cluster minor не меняло правила молча. Audit/warn помогают видеть нарушения, enforce отклоняет неподходящий Pod. Labels не настраивают NetworkPolicy и не шифруют volume.

ledger-api запускается runAsNonRoot с uid65532, не допускает privilege escalation, drop ALL capabilities, readOnlyRootFilesystem и seccomp RuntimeDefault. Linux capability — разделённое привилегированное полномочие, например NET_ADMIN; uid0 без capabilities слабее полного root, но его не следует считать достаточной защитой. allowPrivilegeEscalation=false препятствует соответствующему получению дополнительных privileges при exec, а не исправляет уже выданный privileged режим. Seccomp фильтрует системные вызовы, RuntimeDefault выбирает runtime-профиль; это не proof того, что любое Go-приложение безопасно.

Почему нужен именно такой image

Scratch image содержит только статически собранный Go binary. Поэтому отсутствуют shell/curl/package manager и CA trust bundle. Наш сервис не делает внешний HTTPS, но если добавится такой клиент, потребуется осознанно доставить CA roots либо иной доверенный механизм; отсутствие /bin/sh не должно внезапно ломать exec probe. HTTP probes выполняет kubelet снаружи контейнера, так что curl внутри не нужен. Read-only rootfs требует отдельные writable mounts для программ, которые пишут tmp/cache; ledger-api этого не делает.

Image provenance — свидетельство происхождения от source/build/release. Digest закрепляет содержимое, но сам не говорит, кто его собрал и прошёл ли review. Подпись/attestation проверяется доверенным policy/controller по конкретному формату и issuer identity; встроенный imagePullPolicy=Always не выполняет такую проверку. Always означает resolve/pull policy по правилам kubelet/runtime и допускает content cache, а не «безопасный image». Private registry credentials ограничиваются scope и хранятся как чувствительные данные.

Где проходит node trust

Кластер доверяет kubelet/runtime узла исполнять назначенные Pods и обращаться к нужным Secrets/volumes. Компрометированный node может наблюдать colocated workloads и их данные; RBAC одного namespace не устраняет этот риск. Node authorizer/NodeRestriction ограничивают некоторые API-действия kubelet, но не превращают root на node в слабого пользователя. Не запускайте взаимно недоверенные privileged workloads вместе без отдельного threat model; нужны dedicated nodes/VM/runtime isolation и policy.

hostPath даёт доступ к файловой системе node, hostNetwork/hostPID/hostIPC разделяют host namespaces, privileged расширяет доступ к устройствам/ядру. Это функции для инфраструктурных агентов с повышенным доверием, а не быстрый fix PermissionDenied. Наш local PV лабораторный путь подготовлен администратором и ограничен topology; произвольный mount / в приложение полностью меняет границу. Не выдавайте cluster-admin CI, который нужен только для изменения одного Deployment.

Разобрать отказ admission

Создайте отдельный dry-run пример Pod без runAsNonRoot/seccomp/drop capabilities в lab. API должен сообщить, какие Restricted требования нарушены. Добавьте поля согласно смыслу и повторите server dry-run. Если после admission Pod всё равно Waiting из-за permission на volume, это уже runtime/filesystem, а не RBAC. Добавлять privileged, чтобы «заработало», значит убрать проверяемую гарантию вместо исправления ownership/mount mode. Для каждого исключения запишите нужный syscall/device/path, narrow privilege и способ контроля.

Измерение overhead security также предметное: latency syscalls, CPU, memory runtime sandbox, startup, число отклонений admission и time-to-fix. Снимайте baseline с одинаковой программой/нагрузкой. Гипотеза «seccomp тормозит» не заменяет профиль, а выключение защиты без измерения не является оптимизацией. Самый дешёвый первый шаг для нашей службы — не монтировать API token, не иметь writable rootfs и не включать лишние network listeners.

Сначала context/namespace и время, затем workload conditions/revision, Pod phase/conditions/container state, Events, logs, Service/EndpointSlice и прикладной запрос. Центральный log store — отдельная система с retention и доступом, её наличие здесь не предполагается.

kubectl --context "$LAB_CONTEXT" -n lab get deployment ledger-api -o wide
kubectl --context "$LAB_CONTEXT" -n lab describe pod POD_NAME
kubectl --context "$LAB_CONTEXT" -n lab logs POD_NAME -c api --since=10m --timestamps
kubectl --context "$LAB_CONTEXT" -n lab logs POD_NAME -c api --previous --tail=100
kubectl --context "$LAB_CONTEXT" -n lab get events --sort-by=.metadata.creationTimestamp

Сравните logs без --previous и с ним: первый относится к текущему container instance, второй — к доступному предыдущему. --tail=100 ограничивает строки, --since — время. kubectl debug и scratch

Ephemeral container — добавляемый контейнер диагностики в существующем Pod через специальный subresource. Это позволяет использовать tools, которых нет в scratch image; меняет объект/среду и требует прав/admission, а image должен быть проверен и доступен offline. kubectl debug POD --image=... --target=api просит подходящий процессный target, но поддержка namespace-target зависит от runtime. Наличие debug container не гарантирует видимость всех процессов. Debug node создаёт ещё более доверенную среду с доступом к node; это администраторский рецепт, не разрешение роли investigator.

Metrics API и границы kubectl top

kubectl top pod читает resource metrics API, обычно предоставляемый metrics-server. Upstream kubeadm не устанавливает metrics-server автоматически. Top даёт недавние CPU/memory usage, не исторический p99, не дисковую latency и не бизнес-SLO. HPA с CPU utilization зависит от этих данных и requests. Prometheus и другой historical monitoring могут хранить системные/прикладные ряды; способы scrape/retention/query относятся к отдельному тому, здесь контракт: измерять конкретный ресурс и соответствующую задержку/ошибку.

OOM, throttling, eviction — разные механизмы

Memory cgroup OOM (out of memory, нехватка памяти) kill может завершить container при достижении memory limit; status lastState.terminated.reason=OOMKilled вместе с node/cgroup данными — сильная подсказка. Exit137 означает SIGKILL-подобный результат по shell convention, но сам по себе не доказывает OOM: возможна принудительная остановка. Go heap меньше RSS: stacks, runtime, mappings и kernel accounting добавляют расход. GOMEMLIMIT помогает Go управлять памятью runtime как мягким бюджетом, но не является cgroup limit и не гарантирует отсутствие OOM.

CPU throttling ограничивает доступное CPU-время при quota; процесс может оставаться живым и показывать высокий p99 из-за ожидания. Смотрите throttled seconds/periods и CPU saturation вместе с latency, а не только средний usage. Node-pressure eviction — kubelet освобождает ресурс при давлении memory/disk/PID и выбирает Pods по условиям requests/priority/usage; это не то же, что container memory OOM. QoS (quality of service, класс обслуживания) Guaranteed/Burstable/BestEffort выводятся из resource specifications и влияют на обработку давления, но не дают абсолютной гарантии не быть убитым.

Эксперимент, который различает узкое место

Начните с настоящего ответа нашего сервиса, а не с вымышленного тела 1 KiB: /api/hello возвращает короткий JSON, длина которого зависит от MESSAGE. Поставляемый http_measure.py посылает GET несколькими потоками, читает тело до конца, проверяет HTTP 200 и поле service=ledger-api, затем считает успешные ответы, ошибки, байты и задержки. Используется только стандартная библиотека Python. В каждом потоке следующий запрос начинается после окончания предыдущего; это закрытая модель нагрузки, в которой замедление сервера само уменьшает частоту отправки.

cd "$K8S_LAB_ROOT" || exit 1
python3 http_measure.py --url http://127.0.0.1:18080/api/hello --concurrency 8 --warmup 5 --seconds 10 --rounds 5 --timeout 2 --max-requests 20000

URL выше требует работающего loopback port-forward из первого запуска. Если вы выбрали другой локальный порт, измените URL. Этот путь включает клиент Python, туннель kubectl, API/kubelet и один выбранный Pod. Он полезен для знакомства с методом измерения, но не является измерением Service-балансировки или предельной производительности кластера. Не сравнивайте его число с прямым loopback Go как «накладные расходы только Kubernetes». Для проверки сетевого dataplane нужен отдельно подготовленный генератор в сети клиента, правильные NetworkPolicy и записанный маршрут до Service; BusyBox-клиенты из сетевого опыта не содержат Python.

--warmup задаёт отдельный прогрев; его результат помечен warmup и не смешивается с пятью окнами measurement. --seconds — срок начала новых запросов в окне, --max-requests — дополнительный конечный бюджет, распределённый между потоками. Последние начатые запросы могут закончиться позже окна; elapsed_seconds включает их завершение, а requests/s вычисляется по этому фактическому времени. Флаг stopped_at_request_budget показывает раннюю остановку по числу запросов. Сетевой timeout относится к операциям сокета, а не обещает жёсткий общий срок всего опыта; не запускайте этот клиент против неизвестного сервера с бесконечной медленной передачей тела.

p50, p95 и p99 вычисляются по полным успешным ответам методом ближайшего ранга: после сортировки берётся элемент с номером ceil(q × N), начиная с единицы. Например, для 100 задержек 1…100 ms получим p95 = 95 ms. Ошибки в эти квантили не входят и показаны отдельными счётчиками; ненулевой код завершения 2 либо failed больше нуля запрещают выдавать красивый p95 за успешный опыт. При отсутствии успехов квантили равны null, а не нулевой задержке. Клиент сохраняет выборку в памяти только до конца окна и выводит JSON в stdout; перенаправление в файл журнала — отдельное действие читателя.

Повторяйте опыт при одинаковых image, MESSAGE, маршруте, числе потоков и других нагрузках. Клиент сам расходует CPU и может стать ограничением; без независимого наблюдения нельзя объявлять измеренную частоту мощностью сервера. Для исследования quota сопоставьте задержку с CPU usage и throttled periods контейнера за то же окно, затем измените один limit и повторите. Этот скрипт не измеряет CPU-seconds, диски, fsync или память. Наш stateless Go не обращается к диску на запросе: объяснять его задержку придуманным fsync было бы ошибкой. Работа с реальной базой и её измерениями — отдельный опыт.

Числа нашего YAML 50m/32Mi request и 500m/128Mi limit — учебные исходные гипотезы, не результат нагрузочного измерения автора. Локальные Go tests подтверждают routes и shutdown, но не capacity кластера. Изменения ресурсов делайте после данных и учитывайте rollout: слишком высокий request может сделать новый Pod Pending, оставив старый на месте.

QoS и квантили без подмены измерения

В наших примерах используются container-level resources без Pod-level resource overrides. Для Guaranteed у всех рассматриваемых контейнеров заданы и равны requests/limits CPU и памяти; BestEffort получается без CPU/memory requests и limits; остальные такие Pod попадают в Burstable. Точное вычисление для init/sidecars и дополнительных возможностей версии сверяют по документации. Guaranteed не означает физически выделенную RAM навсегда или иммунитет к отказу node. Usage выше request — существенный вход выбора при node pressure, поэтому один label QoS не объясняет конкретный eviction без остальных условий.

p95 — 95-й процентиль измеренной выборки: примерно 95% наблюдений не больше этого значения при выбранном определении квантиля. Он не среднее и не обещание каждого будущего запроса. При 100 запросах оценка p99 определяется буквально несколькими хвостовыми наблюдениями и нестабильна. Сохраняйте число samples, окно, workload, cold/warm conditions и error count; не сравнивайте p95 успешных ответов одного опыта с общей latency другого, где timeout был исключён. SLO (service level objective, целевой уровень услуги) связывает измеренный показатель с требованием пользователя.

Измеряем потребность, считаем резерв

Пусть один экземпляр при целевой нагрузке устойчиво обслуживает 100 запросов/s с p95≤100ms, потребляя 0.4 CPU и 70Mi working set в заданном опыте. Ожидаемый пик 160 запросов/s требует минимум ceil(160/100)=2 экземпляра по пропускной способности. Чтобы выдержать потерю одного при том же пике, нужно минимум 3 с достаточным распределением и запасом остальных ресурсов. Это условная арифметика, а не характеристика ledger-api: фактическое q измеряют с нужными payload/errors/dependencies. При нелинейной БД-зависимости 3×q не обязано получиться.

Теперь считаем node: два worker с allocatable 1.5 CPU/2GiB каждый. Три app replicas requests0.5CPU/128Mi суммарно требуют 1.5CPU/384Mi, но после потери одного worker оставшийся должен разместить все три плюс CNI/system Pods и surge. Если после резервов доступно 1.2CPU, N+1 не выполняется. Номинальные 2vCPU VM не равны allocatable. Нельзя доказывать failover только общей суммой ресурсов без placement/volume topology/taints. На одном worker можно исследовать process recovery, но не node failure availability.

PDB и добровольное обслуживание

PodDisruptionBudget, PDB, ограничивает добровольные disruptions через eviction API для выбранного набора Pods: minAvailable или maxUnavailable. Он не предотвращает падение VM, kernel OOM, прямое delete Pod и не является счётчиком SLA. Наш 40-availability задаёт maxUnavailable1; при одном replica это допускает его добровольную остановку и честно не обещает availability. Для двух готовых replicas и minAvailable1 разрешён один disruption при условиях контроллера. Неготовые Pods и policy unhealthyPodEvictionPolicy влияют на drain, поэтому PDB может осмысленно блокировать обслуживание.

kubectl --context "$LAB_CONTEXT" cordon wk1
kubectl --context "$LAB_CONTEXT" drain wk1 --ignore-daemonsets --timeout=180s
# After maintenance and actual node readiness:
kubectl --context "$LAB_CONTEXT" uncordon wk1

Cordon запрещает новые обычные назначения на node, не выселяет существующие. Drain пытается эвакуировать Pods, учитывает ограничения, не управляет static mirror Pods как обычными, требует решения о DaemonSet и локальных данных. --ignore-daemonsets разрешает процедуре продолжить при DaemonSet Pods, а не удаляет сам DaemonSet навсегда. Не добавляйте --delete-emptydir-data или --force автоматически: первый разрешает потерю local emptyDir data, второй меняет условия unmanaged Pods и не является ответом на PDB. Если один worker и local PV, drain закономерно оставляет приложение без места; сначала подготовьте другой допустимый capacity/storage.

HPA, VPA и node autoscaling

HorizontalPodAutoscaler, HPA, меняет scale target replicas по метрикам. Для CPU utilization базовая мысль — текущие replicas×current/target с допусками, readiness/отсутствующими данными, stabilization и policies; это управляющий цикл, не мгновенная формула каждого запроса. При request 50m и averageUtilization70% целевой usage около 35m на Pod, а не 70% физического node. Неправильный request меняет знаменатель и решение. HPA autoscaling/v2 требует доступных metrics APIs и не создаёт node, когда новые replicas Pending.

Vertical Pod Autoscaler, VPA, — отдельный компонент рекомендаций/изменения resources с собственной совместимостью и режимами; не встроенная подкоманда kubeadm. Он может менять requests и приводить к пересозданию по своему режимму. Одновременный HPA CPU utilization и VPA CPU requests меняют numerator/denominator и требуют осмысленной настройки. Node autoscaler управляет числом машин через конкретный infrastructure provider; kubeadm в двух личных VM сам не покупает и не создаёт третью. Autoscaling имеет пределы quotas, availability и времени bootstrap, поэтому запас нужен до реакции.

HA control plane отдельно

HA control plane требует нескольких API server, load-balanced endpoint, согласованного etcd quorum, доступных scheduler/controller leaders и сертификатов/сети. Три API server с одним etcd не устраняют single point datastore. Три etcd члена в одной физической машине переживут отказ процесса, но не её питание/диск. Availability приложения зависит от workers, network edge, DNS, storage и внешних dependencies. После потери control plane работающий HTTP может продолжаться, но новый rollout/перепланирование не гарантированы.

Цена kube-system idle CPU/RAM, дисков, upgrades, on-call и backups должна быть видна рядом с ценой приложения. Для одного stateless Go-процесса с небольшим потоком systemd и reverse proxy могут дать меньше отказных переходов. Доказательство выбирается экспериментом: одинаковая нагрузка, измеренный recovery, задачи policy/team scale и стоимость обслуживания в часах. Kubernetes нужен, когда эти возможности дают выгоду, а не когда YAML умещается в README.

Полный optional путь HPA: metrics-server 0.9.1

Выбран metrics-server 0.9.1, matrix0.9.x поддерживает Kubernetes 1.34+, API metrics.k8s.io/v1beta1. Он собирает resource metrics с kubelets для autoscaling, не заменяет исторический мониторинг. Требуются API aggregation layer, kubelet webhook authentication/authorization и проверяемые serving certificates. В kubeadm aggregation обычно подготовлена, но это проверяют по APIService и kube-apiserver flags; не отключайте TLS из-за первого x509 error.

В личной VM для доверенного kubelet serving cert включите serverTLSBootstrap: true в KubeletConfiguration и примените через предусмотренную node-конфигурацию/restart kubelet. Каждый node запросит CSR signerName=kubernetes.io/kubelet-serving. Встроенные controllers не обязаны автоматически approve такой serving CSR. Администратор читает CSR, проверяет username system:node:имя, groups, DNS/IP SAN из реальной node identity и possession/назначение, затем approve только конкретного проверенного CSR. Не одобряйте все Pending пачкой. Сертификат должен покрывать адрес, который metrics-server выберет по preferred-address-types.

kubectl --context "$LAB_CONTEXT" get csr
kubectl --context "$LAB_CONTEXT" get csr CSR_NAME -o yaml
kubectl --context "$LAB_CONTEXT" get csr CSR_NAME -o jsonpath='{.spec.request}' | base64 -d | openssl req -noout -text
# Only after checking signer, requester, SANs and node identity:
kubectl --context "$LAB_CONTEXT" certificate approve CSR_NAME

Проверка CSR — security-sensitive административный шаг, не формальность. Две TLS-проверки: upstream aggregation default не усиливается от CSR kubelet

Точный официальный components.yaml metrics-server0.9.1 содержит APIService.spec.insecureSkipTLSVerify=true. Версия компонента и обслуживаемый API

Minor версия Kubernetes меняет доступные APIs/feature gates/defaults, patch исправляет ошибки внутри линии. Version skew policy ограничивает сочетания: kubelet не должен быть новее kube-apiserver; поддерживаемый отрыв kubelet обычно до трёх minor при условиях политики, kubectl — в пределах одного minor, scheduler/controller-manager — в пределах разрешённого отрыва и не новее API. При смешанных API server в HA пересечение допустимых версий сужается. Поэтому учебный baseline использует одинаковый patch для kubeadm/kubelet/kubectl вместо максимального разрешённого расхождения.

Перед upgrade соберите API usage по manifests, clients, CRDs/webhooks/controllers и audit/metrics. Deprecated значит ещё обслуживается с предупреждением, removed — сервер больше не принимает endpoint. Смена YAML apiVersion требует проверить schema/semantics; CRD storage migration и conversion availability — отдельная работа. IPVS deprecated с 1.35 не значит удалён в 1.36; Ingress frozen не значит removed; PSP действительно removed и не должен появляться в новой инструкции.

Порядок upgrade kubeadm

Сначала изучите notes целевой minor/patch и совместимость CNI/CSI/runtime/Gateway/metrics. Сохраните etcd snapshot, PKI/config, application backup и офлайн-набор обеих версий. На первом control-plane node обновите kubeadm выбранного допустимого перехода, выполните kubeadm upgrade plan, затем kubeadm upgrade apply vX.Y.Z; следующие control-plane используют предусмотренный upgrade node. Затем по одному drain node, обновление kubelet/kubectl/config и restart kubelet, readiness и uncordon. Нельзя перескакивать minor через kubeadm просто потому, что apt предлагает новый пакет.

Это порядок, не готовая команда на неопределённую будущую версию. Для каждого перехода журнал должен содержать исходную/целевую версии и точный guide. Upgrade apply меняет static manifests и cluster configuration; он не проверяет все business endpoints. После каждого node проверяйте API readyz, system Pods, DNS, CNI across nodes, volume operations и ledger-api. При нехватке capacity rolling upgrade сам становится источником downtime, значит окно/ресурсы планируются заранее.

Согласованный backup etcd

etcd snapshot save получает consistent snapshot через etcd endpoint с TLS credentials. Для kubeadm local etcd файлы CA/server/client-healthcheck находятся в PKI, endpoint обычно loopback2379 на control-plane VM; используйте именно поддерживаемые matching etcdctl/etcdutl версии и защищённый output path. Snapshot status проверяет структуру/hash по инструменту, но полноценный restore-тест нужен отдельно. PKI, encryption config/decryption keys, static manifests, kubeadm config и внешний endpoint/DNS сохраняются отдельно от snapshot. Application PVC blocks туда не входят.

sudo etcdutl snapshot status /var/backups/handbook/etcd-before-maintenance.db -w table

Snapshot содержит Secrets и конфигурацию кластера; защищайте права, encryption и независимую копию. Копирование живого /var/lib/etcd обычным cp не заявляется эквивалентом consistent snapshot. Для application backup определите pause/quiesce либо native database backup, consistency point и restore procedure. Record image digests и migration version, иначе восстановите данные, к которым новый бинарник уже несовместим.

Quorum loss и новая логическая история

Потеря одного члена из трёх обычно лечится предусмотренной заменой member при живом quorum, а не restore всего кластера. Потеря quorum требует disaster recovery. Сначала fencing: убедиться, что старые члены/писатели не вернутся параллельно. Restore snapshot формирует новый etcd cluster/member identity в новом data-dir по официальному guide; не накладывайте его поверх работающего каталога. Kubernetes watchers могли видеть более поздние revisions, поэтому etcd guide для Kubernetes рекомендует revision bump и mark-compacted при восстановлении, чтобы клиенты переинициализировали cache. Конкретные флаги etcdutl snapshot restore --bump-revision ... --mark-compacted проверяют по matching3.6 документации и рассчитывают запас revision, а не копируют случайное число.

После restore API clients/controllers снова list/watch, reconciliation сравнит восстановленное желаемое состояние с реальными процессами/дисками. Внешние volumes и side effects не откатились синхронно с etcd; возможны старые/new objects и расходящиеся ожидания. Проверьте UID, owners, attach, Secrets, endpoints и бизнес-целостность. Snapshot недельной давности задаёт RPO, Recovery Point Objective, допустимую потерю данных во времени; фактическое время восстановления задаёт RTO, Recovery Time Objective. Оба нужны отдельно для control plane и приложения.

Worker NotReady и опасность двойного писателя

Control plane узнаёт состояние через Node status/Lease heartbeat. При пропаже node срабатывают taints/eviction по настройкам и ограничениям; это не мгновенное доказательство, что старый процесс остановлен. Network partition может отрезать kubelet от API при живом приложении/storage. Перед force delete stateful Pod и запуском замены убедитесь в fencing старого node/volume. Stateless HTTP переносится проще, но дубликаты in-flight запросов всё равно требуют идемпотентности. Local PV на упавшем worker не переезжает от изменения spec.nodeName.

DNS и policy после нового правила

Сначала подтвердите direct PodIP и ServiceIP до DNS. Если direct проходит, ServiceIP нет — endpoints/dataplane. Если оба проходят, hostname нет — resolver/search/policy53. Если после ingress policy denied и allowed оба не работают, проверьте labels/port и общую readiness, а не объявляйте «deny победил». Если оба работают на default kindnet, проверьте enforcement реализации: API validation это не докажет. Удаление только своей policy в lab возвращает её вклад; другая широкая allow policy может менять итог.

Этап 1: installation и приёмка

Выберите kubeadm VM либо kind, запишите решение и ограничения. Выполните соответствующую главу и сохраните cluster/context. Приёмка: API version и readyz, nodes Ready, system Pods, DNS и межузловой путь для VM. Перезагрузите nodes последовательно, не выполняя init заново, и повторите приёмку. Проверьте офлайн-полноту в отдельном опыте отключённого upstream. Если нет ресурсов для кластера, оставайтесь на этапе 0: файл проверок не должен говорить, что остальные этапы завершены.

Этап 2: первый workload и четыре доказательства

Если вы уже прошли первый запуск перед главой API, этап продолжает те же объекты и тот же image: сначала читайте их status и журнал. Для первого запуска следуйте FIRST-WORKLOAD.txt, а не применяйте весь каталог manifests: NetworkPolicy, HPA и storage подключаются позднее по отдельности. При новом согласованном изменении сначала выполните diff и прочтите результат: код 0 — различий нет, 1 — есть различия, больше 1 — ошибка, после которой apply останавливают.

Дождитесь rollout status и сопоставьте Deployment → ReplicaSet → Pod по ownerReferences и UID; затем containerID, Ready и EndpointSlice. Через loopback port-forward получите /api/hello и сохраните публичный JSON. Отдельный запрос diagnostic Pod к Service DNS проверяет другой путь — кластерный dataplane; результат туннеля не заменяет его. Запишите время сохранения API, назначения Pod, старта контейнера, готовности и HTTP. Отсутствующее наблюдение помечают как неизвестное, а не достраивают из одной итоговой таблицы.

Этап 3: заявка «процесс жив, но клиент не получает endpoint»

Сначала запишите стабильную конфигурацию, revision и UID готового Pod. В этом опыте меняем только readiness через strategic merge по имени контейнера, не меняя image, MESSAGE и liveness:

kubectl --context "$LAB_CONTEXT" -n lab patch deployment ledger-api --type=strategic -p '{"spec":{"template":{"spec":{"containers":[{"name":"api","readinessProbe":{"httpGet":{"path":"/missing-readyz"}}}]}}}}'
kubectl --context "$LAB_CONTEXT" -n lab get pods -l app=ledger-api -o wide
kubectl --context "$LAB_CONTEXT" -n lab get endpointslices -l kubernetes.io/service-name=ledger-api -o yaml

Выберите новое фактическое имя Pod из таблицы и прочтите его describe: ожидаются HTTP 404 readiness, Ready=false, но успешная liveness и отсутствие обязательного роста restartCount. Если хватает surge-ёмкости, при maxUnavailable: 0 старый готовый Pod остаётся обслуживать. При нехватке места новый может вообще не запуститься — это другая причина, её нельзя назвать отказом readiness. Клиентский timeout rollout не откатывает сохранённый template.

kubectl --context "$LAB_CONTEXT" -n lab patch deployment ledger-api --type=strategic -p '{"spec":{"template":{"spec":{"containers":[{"name":"api","readinessProbe":{"httpGet":{"path":"/readyz"}}}]}}}}'
kubectl --context "$LAB_CONTEXT" -n lab rollout status deployment/ledger-api --timeout=120s
kubectl --context "$LAB_CONTEXT" -n lab get pods -l app=ledger-api -o wide

Вторая узкая правка возвращает исходный путь, сохраняя остальные настройки. Затем подтвердите HTTP, новый UID и состав готовых endpoints. Императивный patch может изменить managedFields; если последующий SSA хочет изменить уже принадлежащее другому manager поле, разбирайте конкретный конфликт, а не добавляйте force ко всему приложению. В поддерживаемом desired-файле путь также должен остаться /readyz. Namespace и старые доказательства не удаляют.

Этап 4: конфигурация и ownership

Измените MESSAGE в ConfigMap, проверьте старый ответ без restart, затем выполните осмысленный rollout и получите новый. На отдельном ConfigMap пройдите SSA conflict двух managers: managerB меняет поле managerA без force, получает conflict; затем возвращает исходный договор. На отдельной копии объекта сделайте устаревший resourceVersion replace и получите 409, reread/recompute/retry. Не включайте force-conflicts как постоянный флаг. Все изменения возвращайте к файлам и журналу, а не к новому пустому namespace.

Этап 5: ограниченный расследователь и сеть

Примените 20-rbac и работайте как investigator через подготовленный ограниченный клиент/администраторскую impersonation-проверку. Требуется прочитать Pod logs и Service endpoints, получить отказ secrets/exec/update. На VM Calico profile установите 30-policy, сравните allowed/denied clients и directIP/ServiceDNS. Ошибка label access объясняется наблюдениями. В kindnet отметьте отсутствие поддерживаемой проверки policy, не рисуйте зелёный результат. Снимите короткий packet capture только в своей VM, запишите tuple и отделите outer VXLAN от внутреннего NAT.

Этап 6: данные, обслуживание и восстановление

Локальный PV/Job опыт выполняйте отдельно на wk1 с явно подготовленным каталогом и image. Докажите тот же record hash после замены consumer, затем объясните Pending после остановки wk1. Для PDB/drain сначала создайте достаточное число ready replicas и допустимые nodes; один worker не обеспечивает failover. HPA подключайте только после metrics API и понимания владения replicas; не смешивайте его с ручным scale без журнала. Backup etcd/application и restore проверяют в изолированном clone, не поверх рабочего учебного cluster. Recovery должен подтвердить исходный dataset, а не только новый hello.

Условия завершения и переход к Helm

У вас есть install/version inventory, сохранённый кластер, образ 0.1.0, namespace lab, API/process/packet evidence, ограниченная identity, backup plan и честные непроверенные пункты. Helm получает тот же HTTP/env контракт и byte-identical исходники в отдельном namespace helm-lab. Он управляет своим release, а не перехватывает созданный kubectl Deployment. В журнале сравнивайте одинаковый image digest и разные object UID. Финальное уничтожение kubectl delete namespace lab — отдельное решение после проверки reclaim и резервов, его нет в обычном reset задания.

Том XXII · Источники и справочник

Словарь · KubernetesПонятия и их связь с наблюдаемыми механизмами · 2295 слов

Словарь в боковой панели также ищет определения во всех остальных томах.

Kubernetes

Система управления контейнерными workloads через API-объекты и независимые циклы согласования. Успешная запись намерения не равна запуску процесса или успеху приложения.

Control plane

Управляющие компоненты Kubernetes: API server, etcd, scheduler и controllers. Их доступность отличается от доступности уже работающего приложения.

Node

Вычислительная машина, зарегистрированная в Kubernetes, с kubelet и runtime. В kind node является контейнером с общим kernel, в основном стенде — отдельной VM.

Pod

API-объект единицы совместного размещения контейнеров с общей Pod-сетью и указанными томами. Не равен одному процессу; новый одноимённый Pod имеет новый UID.

API server

HTTPS-сервер Kubernetes API: authentication, authorization, admission, validation/conversion и доступ к сохранённому состоянию. Обычно controllers работают с ним, а не напрямую с etcd.

etcd

Согласованное распределённое key-value хранилище управляющего состояния. Snapshot etcd не содержит blocks прикладного PVC backend.

Raft

Протокол согласования реплицированного журнала, используемый etcd. Подтверждение записи требует предусмотренного большинства, а не любой одной копии.

Quorum

Большинство участников: floor(N/2)+1. Три члена переживают потерю одного, два требуют обоих и не дают такой отказоустойчивости.

kubeadm

Средство bootstrap/присоединения/обслуживания upstream Kubernetes. Не создаёт VM, не выбирает CNI и не заменяет общий lifecycle дистрибутива ОС.

kubelet

Node agent, согласующий исполнение назначенных Pods через CRI и публикующий status. Static Pods также могут приходить из локальных manifests.

CRI

Container Runtime Interface: API между kubelet и контейнерным runtime для sandbox, images и containers. Не является CNI или OCI image format.

CNI

Container Network Interface: договор конфигурации сетевой среды sandbox между runtime и плагинами. Конкретная реализация задаёт routes/overlay/IPAM и возможный policy enforcement.

CSI

Container Storage Interface: договор controller/node операций управления storage. Нужны реальный driver и controllers; имя provisioner само диск не создаёт.

containerd

Служба image/content/snapshot/container/task lifecycle с CRI plugin. Metadata namespace k8s.io отличается от Kubernetes namespace lab.

runc

Низкоуровневая реализация OCI runtime, создающая Linux-process с namespaces/cgroups/mounts. Не является scheduler или registry.

Shim

Промежуточный runtime-процесс, поддерживающий задачи/stdio/reaping и связь runtime lifecycle с containerd. Не равен самому application process.

OCI

Open Container Initiative: семейство спецификаций. Image spec описывает упаковку образа, runtime spec — конфигурацию исполнения, distribution spec — передачу content.

Sandbox

Подготовленная среда Pod, в обычном Linux containerd-пути связанная с pause task и общей сетевой областью. Успех sandbox не доказывает запуск app container.

Namespace Linux

Изоляция представления определённого ресурса kernel: network, mount, PID, UTS и других. Отличается от Kubernetes namespace — области API-имён.

Namespace Kubernetes

Область имён namespaced API resources и применения части политик. Само имя не создаёт network/kernel/security isolation.

cgroup

Иерархия Linux учёта и ограничения ресурсов. В Ubuntu24 cgroupv2 и systemd driver должны быть согласованы между kubelet и runtime.

GVK

Group Version Kind: идентификация формы API-объекта, например apps/v1 Deployment. Для URL коллекции используется GVR с множественным resource.

GVR

Group Version Resource: API group/version/имя коллекции для маршрутизации запроса, например apps/v1/deployments.

Schema

Структурное описание типов/полей API. Локальная schema validation не подтверждает authorization, admission, наличие зависимостей или исполнение.

Defaulting

Добавление предусмотренных значений отсутствующих полей сервером. Возвращённый API-объект может содержать больше полей, чем входной YAML.

Admission

Политика допуска/изменения API-объекта после установления личности/разрешения запроса. Webhook может изменить либо отклонить write, не запуская приложение.

Storage version

Версия представления resource, используемая для сохранения. Обслуживаемые API representations могут конвертироваться; смена apiVersion локального файла не мигрирует все объекты.

CRD

CustomResourceDefinition: регистрация собственного API-ресурса и schema. CRD без controller не реализует бизнес-поведение ресурса.

UID

Уникальная идентичность экземпляра API-объекта. Имя может использоваться повторно после удаления, UID — другая идентичность.

resourceVersion

Непрозрачный маркер версии состояния для concurrency/list/watch. Не timestamp и не допустимый для арифметики бизнес-счётчик.

generation

Счётчик изменений желаемой спецификации поддерживающего ресурса. observedGeneration в status показывает обработанную контроллером generation.

Optimistic concurrency

Согласование конкурентной записи через проверку увиденной версии. Устаревший update получает409, клиент перечитывает и пересчитывает intent.

List/watch

Получение текущего набора и продолжение наблюдения изменений от допустимой resourceVersion. История ограничена;410 требует relist, а не выдумывание событий.

Informer

Механизм client-go list/watch с локальным cache и обработчиками. Его cache может отставать; reconcile должен выдерживать повторы и конфликты.

Server-side apply

Декларативное управление полями на API server с managedFields, schema merge semantics и проверкой конфликтов владельцев.

Field manager

Имя участника управления полями SSA. Не заменяет identity/RBAC и отличается от ownerReferences жизненного цикла.

managedFields

Серверные сведения о том, какие managers управляют полями объекта и какими операциями. Полезны при конфликте SSA, но не являются журналом всех значений.

Reconciliation

Повторяемый цикл чтения desired/observed state, вычисления разницы и ограниченного действия. Не общая атомарная транзакция API→процесс.

Idempotency

Свойство операции корректно переносить повтор без неправильного дополнительного эффекта. Повтор Job не гарантирует exactly-once внешнюю запись.

ownerReferences

Ссылки API-объекта на владельцев с их UID для lifecycle/garbage collection. Общий label сам не создаёт ownership.

Finalizer

Ключ, удерживающий окончательное удаление до cleanup ответственным controller. Ручное снятие может оставить внешние ресурсы или снять защиту данных.

Garbage collection

Сборка зависимых API-объектов по owner graph и политике удаления. Не произвольное удаление всех объектов с похожим именем.

Scheduler

Компонент выбора node для ещё не назначенного Pod: eligibility/filter, score и bind с другими фазами framework. Сам Linux-process не запускает.

Request

Заявленная потребность ресурса, используемая при планировании/распределении. Не фактический CPU/RSS и не обязательно верхняя граница использования.

Limit

Граница исполнения конкретного ресурса. CPU quota может throttle, memory limit может привести к OOM; эффекты отличаются.

Allocatable

Бюджет node для workloads после системных резервов/ограничений. Не вся физическая RAM или номинальные vCPU VM.

Affinity

Условия/предпочтения выбора node и размещения относительно других Pods. Required исключает неподходящие nodes, preferred влияет на сравнение допустимых.

Taint

Метка node, отталкивающая Pods без подходящей toleration по эффекту NoSchedule/PreferNoSchedule/NoExecute.

Toleration

Разрешение Pod терпеть определённый taint. Не приказ выбрать именно этот node.

Topology spread

Ограничение/предпочтение распределения выбранных Pods по topology domains. Не создаёт новые зоны или nodes.

Preemption

Возможное вытеснение менее приоритетных Pods ради допустимого размещения более приоритетного. Не обходит все ограничения и не гарантирует мгновенный старт.

Readiness

Готовность экземпляра получать предназначенный трафик. Неудача обычно влияет на endpoint readiness, сама не перезапускает container.

Liveness

Проверка жизнеспособности контейнера, устойчивый отказ которой может вызвать restart. Проверка внешней зависимости может создать бессмысленную restart storm.

Startup probe

Проверка первоначального запуска, до успеха которой не выполняются обычные liveness/readiness проверки.

Sidecar

Сопутствующий контейнер; native restartable sidecar задаётся initContainer с restartPolicy Always в поддерживающей версии. Отличается от обычного второго app container.

Grace period

Общий бюджет штатного завершения Pod, включающий preStop и ожидание остановки. По исчерпании возможен принудительный kill.

Deployment

Контроллер rollout и количества взаимозаменяемых Pods через ReplicaSets. API success не означает готовность новых replicas.

ReplicaSet

Контроллер числа подходящих Pods по selector. Обычно им управляет Deployment, не приложение напрямую.

StatefulSet

Контроллер устойчивой identity ordinal Pods и связей с PVC. Не реализует репликацию/consensus приложения автоматически.

DaemonSet

Контроллер Pod на каждом подходящем node. Подходит node-агентам; его privileges требуют повышенного доверия.

Job

Контроллер конечной работы и нужных успешных completions. Повторы/дубли возможны; внешние эффекты должны быть идемпотентны.

CronJob

Контроллер создания Jobs по schedule/timezone/concurrency policy. Не гарантия exactly-once периодического бизнес-действия.

ConfigMap

API-объект не секретной конфигурации. Env читается при старте процесса, volume обновляется eventual с отдельными условиями.

Secret

API-объект чувствительных данных и conventions доставки. Base64 не шифрует; encryption at rest и доступ настраивают отдельно.

ServiceAccount

Workload identity для Kubernetes API. Не Linux uid; token mount не нужен сервису, не использующему API.

Service

Стабильная точка/политика выбора endpoints. ClusterIP в iptables-профиле виртуален и не означает отдельный HTTP-proxy process.

EndpointSlice

API-набор адресов/портов/conditions endpoints Service с масштабируемым разбиением. Primary API discovery.k8s.io/v1.

CoreDNS

DNS-сервер кластерных имён и предусмотренного forwarding. Он отвечает адресом, не пересылает каждый HTTP-запрос приложения.

CIDR

Запись IP-префикса адрес/число фиксированных бит. PodCIDR/ServiceCIDR/underlay должны быть совместимы и не пересекаться с внешними маршрутами.

IPAM

IP address management: выделение/освобождение адресов. Часть выбранного сетевого решения, не стандартная функция Service selector.

DNAT

Destination network address translation: изменение destination IP/port, например ServiceVIP80→PodIP8080.

SNAT

Source network address translation: изменение source IP/port для предусмотренного маршрута/masquerade. Может скрывать client source IP.

Conntrack

Учёт состояния соединений Linux/netfilter и соответствий NAT tuple. Нужен корректный return path и ресурсы таблицы.

VXLAN

Virtual Extensible LAN: overlay с UDP инкапсуляцией внутреннего пакета между nodes. В выбранном IPv4-профиле overhead учитывается в MTU.

MTU

Maximum transmission unit: допустимый размер пакета/link payload на участке. Overlay/VPN уменьшают бюджет внутреннего пакета.

eBPF

Механизм проверяемых программ kernel и maps, который сетевые реализации используют для policy/load balancing. Не универсальный протокол без NAT.

NetworkPolicy

API L3/L4 разрешённых связей выбранных Pods по ingress/egress. Нужен поддерживающий CNI; правила аддитивны.

Ingress

Встроенный API HTTP(S)-маршрутов к Services, исполняемый отдельным controller. API frozen, но не автоматически removed.

Gateway API

Отдельно выпускаемые CRDs и contracts GatewayClass/Gateway/Routes. Controller, CRD version и conformance проверяются совместно.

TLS termination

Граница завершения TLS. HTTPS до Gateway не автоматически шифрует Gateway→backend участок.

PV

PersistentVolume: объект предоставленного storage с capacity/access/reclaim/backend/topology. Не сами bytes резервной копии.

PVC

PersistentVolumeClaim: запрос на storage. Bound означает связь объектов, а не завершённый mount/проверенный write.

StorageClass

Параметры provisioner и политики выделения storage. Произвольное имя provisioner не устанавливает driver.

RWO

ReadWriteOnce: предусмотренный read-write доступ с одного node, а не всегда один Pod. Для одного Pod существует поддерживаемый CSI RWOP.

Reclaim policy

Политика backend после освобождения claim: Retain либо предусмотренное Delete. Не заменяет application backup.

Fencing

Надёжное исключение старого писателя/node из доступа перед запуском замены. Важно при partition и stateful workload.

RBAC

Role-Based Access Control: разрешения verbs/resources через роли и bindings. Authentication и admission — отдельные проверки.

Kubeconfig

Конфигурация endpoints/CA/credentials/contexts клиента. Может содержать private keys и exec plugin, поэтому требует доверия и защиты.

CA

Certification Authority: доверенная удостоверяющая сторона/корневой материал. Public CA cert и private signing key имеют разные риски.

SAN

Subject Alternative Name: имена/IP, на которые распространяется сертификат. Смена URL клиента не расширяет SAN сервера.

CSR

Certificate Signing Request: запрос подписи ключа/identity/SAN. Approval должен проверять requester, signer и соответствие node, а не все Pending сразу.

Pod Security Admission

Встроенный admission-контроль Pod Security Standards по namespace labels enforce/audit/warn и выбранной версии.

Capability

Отдельное привилегированное полномочие Linux. Drop ALL и отсутствие privileged уменьшают доверие, но не заменяют защиту kernel.

Seccomp

Фильтрация системных вызовов Linux. RuntimeDefault выбирает runtime baseline, а не доказывает безопасность программы.

Provenance

Сведения о происхождении артефакта из source/build/release. Digest закрепляет bytes, подпись требует отдельной доверенной identity/policy.

OOM

Out Of Memory: нехватка памяти и механизм выбора kill. Exit137 сам по себе не доказывает OOM; нужны status/cgroup/node свидетельства.

Throttling

Ограничение выделенного CPU-времени по quota. Может увеличивать latency живого процесса без restart.

Eviction

Выселение Pod: добровольное через eviction API либо node-pressure по условиям. Отличается от рестарта одного контейнера.

QoS

Quality of Service классы Guaranteed/Burstable/BestEffort по resource specs. Участвуют в обработке давления, но не дают абсолютной гарантии сохранения Pod.

PDB

PodDisruptionBudget: ограничение добровольных disruptions через eviction для выбранных Pods. Не защищает от физической потери node.

HPA

HorizontalPodAutoscaler: цикл изменения replicas по метрикам. Не добавляет nodes, зависит от requests/metrics и времени реакции.

VPA

Vertical Pod Autoscaler: отдельно устанавливаемый компонент рекомендаций/изменения resources с собственными режимами/риском пересоздания.

RPO

Recovery Point Objective: допустимая потеря данных во времени/точка, до которой восстанавливаем. Для etcd и приложения рассматривается отдельно.

RTO

Recovery Time Objective: целевой срок восстановления услуги. Должен проверяться restore опытом, не только наличием backup файла.

Digest

Идентификатор content, обычно sha256 manifest для OCI image. Tag изменяем, а digest закрепляет конкретное содержимое, но не личность издателя.

Idempotency key

Стабильный ключ бизнес-операции, позволяющий дедуплицировать её повторы. Полезен при Job retry/сетевой неопределённости.

RSS

Resident set size: объём резидентных страниц памяти процесса. Отличается от Go heap и cgroup memory usage; требуется согласованный метод суммирования.

WAL

Write-ahead log: журнал предварительной записи для восстановления/согласования хранилища. Не заменяет consistent snapshot и restore test.

veth

Пара виртуальных Ethernet-интерфейсов Linux, соединяющая сетевые границы. В Calico Pod имеет свой конец, node — peer.

IPVS

IP Virtual Server: Linux-механизм виртуальных сервисов. Соответствующий kube-proxy mode deprecated с Kubernetes 1.35.

IPIP

IP in IP: инкапсуляция IP-пакета в другой IP-пакет. Отличается от VXLAN по протоколу, overhead и условиям MTU.

iptables

Пользовательский интерфейс определённых netfilter правил Linux. iptables-nft backend не равен native kube-proxy nftables mode.

nftables

Инфраструктура правил Linux. Native kube-proxy nftables mode имеет собственные условия и поведение; stable не означает default.

IOPS

Операции ввода-вывода в секунду при заданных размере операции, queue depth и latency. Не равны MiB/s и не доказывают быстрый fsync.

TTL

Time to live: срок жизни в конкретном механизме. TTL завершённого Job управляет очисткой объектов, не гарантирует exactly-once выполнение.

SLO

Service level objective: целевой уровень услуги по заданному показателю и окну. Отличается от инфраструктурного признака Pods Ready.

Manifest

Файл с описанием одного или нескольких API-объектов, обычно YAML. Это вход клиента; после принятия сервер может добавить поля, а исполнение выполняется отдельными компонентами.

Label selector

Условие выбора API-объектов по парам меток ключ/значение. В нашем Service app=ledger-api выбирает Pods; общая метка не создаёт ownerReference и не выдаёт право доступа.

Pod template

Шаблон будущего Pod внутри Deployment, Job и других контроллеров. Изменение template Deployment ведёт к другой ревизии и новым Pods, а не к произвольной правке старого процесса.

Condition

Именованный признак состояния API-объекта с status True, False или Unknown и поясняющими полями reason/message. Ready и PodScheduled отвечают на разные вопросы.

Event

Диагностический объект Kubernetes о наблюдённом событии, например FailedScheduling. Может агрегироваться и удаляться; не равен отдельному событию watch и не является полным историческим журналом.

Webhook

Отдельный HTTPS-обработчик, вызываемый API server по настроенным правилам. Admission webhook возвращает решение либо допустимые изменения объекта; его недоступность обрабатывается по failurePolicy.

JSON Patch

Последовательность операций add/remove/replace/test и других над путями JSON Pointer. Индекс элемента списка зависит от его текущего порядка.

JSON Merge Patch

Форма patch, где переданные значения объединяются по правилам JSON Merge Patch, null удаляет поле, а массив заменяется целиком. Не использует схему списка containers как strategic merge.

Strategic merge patch

Поддерживаемый некоторыми встроенными типами Kubernetes patch со сведениями схемы. Например, элементы containers сопоставляются по name. Не универсален для произвольного CRD.

Port-forward

Локальный TCP-туннель kubectl через API/kubelet к выбранному Pod. Его listener и локальный порт отличаются от ClusterIP и не доказывают путь сетевой балансировки Service.

ImagePullPolicy

Политика kubelet получения образа. IfNotPresent использует подходящий локальный image либо пытается загрузить отсутствующий; наличие tar на другом компьютере этим не проверяется.

Closed-loop load

Закрытая модель нагрузки: клиент начинает следующий запрос только после окончания предыдущего. При росте задержки частота запросов сама падает, поэтому результат не равен испытанию фиксированной внешней частоты.

Inode

Объект файловой системы с метаданными файла. Свободные байты не гарантируют возможность создать новый файл, если исчерпаны доступные inode.

Image ID

Идентификатор образа в конкретном инструменте/runtime. Docker image ID относится к конфигурации image; его нельзя без проверки выдавать за registry manifest digest либо hash экспортированного tar.
