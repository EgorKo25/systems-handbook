Обновление, deprecation и восстановление control plane

Перед изменением версии надо доказать возможность прочитать старые данные, сохранить ключи и восстановить прикладное состояние. Upgrade и rollback не симметричны.

Версия компонента и обслуживаемый API

Minor версия Kubernetes меняет доступные APIs/feature gates/defaults, patch исправляет ошибки внутри линии. Version skew policy ограничивает сочетания: kubelet не должен быть новее kube-apiserver; поддерживаемый отрыв kubelet обычно до трёх minor при условиях политики, kubectl — в пределах одного minor, scheduler/controller-manager — в пределах разрешённого отрыва и не новее API. При смешанных API server в HA пересечение допустимых версий сужается. Поэтому учебный baseline использует одинаковый patch для kubeadm/kubelet/kubectl вместо максимального разрешённого расхождения.

Перед upgrade соберите API usage по manifests, clients, CRDs/webhooks/controllers и audit/metrics. Deprecated значит ещё обслуживается с предупреждением, removed — сервер больше не принимает endpoint. Смена YAML apiVersion требует проверить schema/semantics; CRD storage migration и conversion availability — отдельная работа. IPVS deprecated с 1.35 не значит удалён в 1.36; Ingress frozen не значит removed; PSP действительно removed и не должен появляться в новой инструкции.

Порядок upgrade kubeadm

Сначала изучите notes целевой minor/patch и совместимость CNI/CSI/runtime/Gateway/metrics. Сохраните etcd snapshot, PKI/config, application backup и офлайн-набор обеих версий. На первом control-plane node обновите kubeadm выбранного допустимого перехода, выполните kubeadm upgrade plan, затем kubeadm upgrade apply vX.Y.Z; следующие control-plane используют предусмотренный upgrade node. Затем по одному drain node, обновление kubelet/kubectl/config и restart kubelet, readiness и uncordon. Нельзя перескакивать minor через kubeadm просто потому, что apt предлагает новый пакет.

Это порядок, не готовая команда на неопределённую будущую версию. Для каждого перехода журнал должен содержать исходную/целевую версии и точный guide. Upgrade apply меняет static manifests и cluster configuration; он не проверяет все business endpoints. После каждого node проверяйте API readyz, system Pods, DNS, CNI across nodes, volume operations и ledger-api. При нехватке capacity rolling upgrade сам становится источником downtime, значит окно/ресурсы планируются заранее.

Согласованный backup etcd

etcd snapshot save получает consistent snapshot через etcd endpoint с TLS credentials. Для kubeadm local etcd файлы CA/server/client-healthcheck находятся в PKI, endpoint обычно loopback2379 на control-plane VM; используйте именно поддерживаемые matching etcdctl/etcdutl версии и защищённый output path. Snapshot status проверяет структуру/hash по инструменту, но полноценный restore-тест нужен отдельно. PKI, encryption config/decryption keys, static manifests, kubeadm config и внешний endpoint/DNS сохраняются отдельно от snapshot. Application PVC blocks туда не входят.

# Recipe only, inside the personal control-plane VM, using matched etcd tools:
sudo etcdctl --endpoints=https://127.0.0.1:2379   --cacert=/etc/kubernetes/pki/etcd/ca.crt   --cert=/etc/kubernetes/pki/etcd/healthcheck-client.crt   --key=/etc/kubernetes/pki/etcd/healthcheck-client.key   snapshot save /var/backups/handbook/etcd-before-maintenance.db
sudo etcdutl snapshot status /var/backups/handbook/etcd-before-maintenance.db -w table

Snapshot содержит Secrets и конфигурацию кластера; защищайте права, encryption и независимую копию. Копирование живого /var/lib/etcd обычным cp не заявляется эквивалентом consistent snapshot. Для application backup определите pause/quiesce либо native database backup, consistency point и restore procedure. Record image digests и migration version, иначе восстановите данные, к которым новый бинарник уже несовместим.

Quorum loss и новая логическая история

Потеря одного члена из трёх обычно лечится предусмотренной заменой member при живом quorum, а не restore всего кластера. Потеря quorum требует disaster recovery. Сначала fencing: убедиться, что старые члены/писатели не вернутся параллельно. Restore snapshot формирует новый etcd cluster/member identity в новом data-dir по официальному guide; не накладывайте его поверх работающего каталога. Kubernetes watchers могли видеть более поздние revisions, поэтому etcd guide для Kubernetes рекомендует revision bump и mark-compacted при восстановлении, чтобы клиенты переинициализировали cache. Конкретные флаги etcdutl snapshot restore --bump-revision ... --mark-compacted проверяют по matching3.6 документации и рассчитывают запас revision, а не копируют случайное число.

После restore API clients/controllers снова list/watch, reconciliation сравнит восстановленное желаемое состояние с реальными процессами/дисками. Внешние volumes и side effects не откатились синхронно с etcd; возможны старые/new objects и расходящиеся ожидания. Проверьте UID, owners, attach, Secrets, endpoints и бизнес-целостность. Snapshot недельной давности задаёт RPO, Recovery Point Objective, допустимую потерю данных во времени; фактическое время восстановления задаёт RTO, Recovery Time Objective. Оба нужны отдельно для control plane и приложения.

Границы rollback

Deployment rollback возвращает template, Helm rollback возвращает release manifests по своей семантике, binary downgrade меняет код, etcd restore возвращает управляющее состояние, application restore возвращает данные. Это пять разных операций. После необратимой schema migration старый image может не читать новые данные. «Откатим VM snapshot» тоже не возвращает внешние платежи и удалённый storage backend. Успешный план восстановления включает критерий остановки, журнал шагов и проверку в отдельной сети до инцидента.

Завершённый restore опыт для baseline single cp1

INSTALL.txt отдельно получает matching etcdctl/etcdutl3.6.8 из официального release, проверяет сумму, устанавливает только maintenance tools в личную VM и создаёт защищённый backup directory. Конкурирующий host etcd service не создаётся. RECOVERY.txt даёт полный рецепт: backup с TLS, изолированный выключенный clone, fencing original, перенос static manifests ВНЕ watched directory, проверка фактической остановки containers через CRI, restore в новый data-dir с new identity/revision bump/mark-compacted, сохранение старого каталога и перенос нового под прежний /var/lib/etcd mount, запуск сначала etcd затем API/controllers и приёмка dataset.

В примере bump 150000000 выведен из допущения не более 200 revisions/s и не более 7 суток после snapshot:200×7×86400=120960000, остаток — запас. Это не универсальное значение; при большем интервале/скорости bound пересчитывается. На single cp1 static manifest hostPath и data-dir остаются /var/lib/etcd, потому что восстановленный каталог подставляется только после остановки старого. Одно stop kubelet не останавливает уже живой etcd: рецепт отдельно проверяет CRI tasks. Restore control plane без clone wk1 не обещает автоматически поднять localPV приложение — требуется изолированный worker с сохранёнными bytes и topology. Автор не выполнял этот destructive VM опыт и не объявляет его успешным.
