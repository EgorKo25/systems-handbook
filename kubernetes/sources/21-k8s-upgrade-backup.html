Обновление кластера и восстановление из снимка etcd

После обновления API снова отвечает, но приложение не читает базу: новый выпуск успел изменить её схему. Возврат старого образа этого не исправит. Разберём, какие данные сохранять перед обновлением, как выбрать поколение снимка и по каким результатам принимать восстановленный кластер.

Версия компонента и обслуживаемый API

При переходе между minor-версиями могут измениться доступные API, экспериментальные возможности и настройки по умолчанию. Совместимость компонентов проверяют по Version Skew Policy. Например, kubelet не должен быть новее kube-apiserver, а kubectl поддерживается в пределах одной minor-версии от него. Для kubelet допускается отставание до трёх minor с оговорками политики; scheduler и controller-manager имеют более узкие ограничения. Если одновременно работают API-серверы разных версий, каждый клиент должен подходить ко всем. В учебной конфигурации kubeadm, kubelet и kubectl закреплены на одном patch: разрешённое отставание не требуется для самого опыта.

Перед обновлением найдите используемые API в манифестах и клиентах, включая операторы, CRD и webhooks. Сопоставьте их с руководством по миграции целевой версии; обращения старых клиентов видны также в аудите и метриках API-сервера. Предупреждение об устаревании даёт время на переход. После удаления API запрос по прежнему адресу уже не обслуживается. Одной замены apiVersion в YAML может не хватить: поля и поведение ресурса тоже меняются. Для CRD отдельно проверяют преобразование версий и миграцию сохранённых объектов.

Порядок upgrade kubeadm

Сначала изучите примечания к целевой версии и совместимость сетевого плагина, драйвера хранения, среды контейнеров, Gateway и средств сбора метрик. Сохраните снимок etcd, PKI и конфигурацию, копию данных приложения и офлайн-набор обеих версий. На первом управляющем узле обновите kubeadm для выбранного перехода, выполните kubeadm upgrade plan, затем kubeadm upgrade apply vX.Y.Z; на следующих управляющих узлах выполняют предусмотренный upgrade node. Затем обслуживают узлы по одному: drain переносит допускающие перенос Pod, после чего обновляют kubelet, kubectl и конфигурацию, перезапускают kubelet, проверяют готовность и выполняют uncordon. kubeadm требует последовательного перехода между minor-версиями; наличие более нового пакета в apt не отменяет этого ограничения.

vX.Y.Z здесь обозначает выбранную целевую версию. До выполнения запишите исходную и целевую версии и откройте руководство именно для этого перехода. upgrade apply меняет статические манифесты и конфигурацию кластера. Проверку приложения выполняет оператор: после каждого узла проверяет API readyz, системные Pod, DNS, связь между узлами, работу томов и запрос к ledger-api. Предыдущая глава показывает, как оценить свободные ресурсы: после drain оставшиеся узлы должны вместить перенесённые Pod, иначе обновление остановит часть нагрузки.

Сохранить отдельное поколение снимка

etcdctl snapshot save получает согласованный снимок базы через API etcd. В нашем kubeadm-кластере etcd слушает https://127.0.0.1:2379 внутри cp1. Клиент проверяет сертификат сервера по CA и предъявляет свой сертификат с ключом. Пути в блоке относятся к PKI этой VM. Нужны совместимые с сервером версии etcdctl и etcdutl; их подготовка описана в INSTALL.txt. В снимке находятся объекты Kubernetes, включая Secrets. Данные прикладных PVC, сертификаты и ключи из файловой системы cp1 надо сохранять отдельно.

Выполняйте блок на своей control-plane VM. Подготовьте закрытый каталог для резервных копий и установите согласованные инструменты по рецепту подготовки. Для другого расположения заранее задайте абсолютные пути etcd_pki_dir и etcd_backup_root. Корневой каталог копий уже должен существовать, принадлежать root и иметь режим 0700; его родительские каталоги тоже не должны разрешать посторонним заменять пути. Один оператор выполняет сохранение без параллельного изменения этих каталогов. Каждая попытка получает новый закрытый каталог. При отказе snapshot save остановитесь и сохраните сообщение об ошибке; частичный каталог оставьте для разбора.

(
  etcd_pki_dir="${etcd_pki_dir:-/etc/kubernetes/pki/etcd}"
  etcd_backup_root="${etcd_backup_root:-/var/backups/handbook}"
  for path in "$etcd_pki_dir" "$etcd_backup_root"; do
    case "$path" in
      /*) ;;
      *) printf '%s\n' 'Нужны абсолютные пути PKI и каталога копий.' >&2; exit 1 ;;
    esac
  done
  backup_set="$(sudo mktemp -d "$etcd_backup_root/etcd-before-maintenance.XXXXXXXX")" || exit 1
  sudo etcdctl --endpoints=https://127.0.0.1:2379 \
    --cacert="$etcd_pki_dir/ca.crt" \
    --cert="$etcd_pki_dir/healthcheck-client.crt" \
    --key="$etcd_pki_dir/healthcheck-client.key" \
    snapshot save "$backup_set/etcd.db" || exit 1
  sudo etcdutl snapshot status "$backup_set/etcd.db" -w table || exit 1
  sudo sha256sum "$backup_set/etcd.db"
)

При успехе сохраните путь, время получения снимка, ревизию из таблицы и SHA-256 файла в частном журнале. Ревизия — номер изменения базы, а не отметка времени. Для восстановления выберите именно записанное поколение. Прежние поколения остаются доступны. Внутренний хеш из snapshot status и SHA-256 файла решают разные задачи: первый описывает содержимое базы, второй позволяет сравнить точные байты файла после переноса. Команда status сама по себе не подтверждает успешное восстановление. etcdutl snapshot restore проверяет сохранённый в снимке контрольный хеш; эту проверку не отключают.

Храните копию отдельно от исходного диска, с ограниченным доступом и шифрованием. Для восстановления понадобятся также PKI, конфигурация шифрования Secrets с ключами расшифровки, статические манифесты, конфигурация kubeadm и адрес API/DNS. Живой каталог /var/lib/etcd нельзя копировать обычным cp как замену этому рецепту. Прикладную БД сохраняют её штатным средством либо после согласованной остановки писателей. Запишите digest образа и версию миграции схемы, чтобы выбрать код, способный прочитать восстановленные данные.

Что меняется при восстановлении etcd

Если в кластере etcd из трёх членов потерян один, оставшиеся два ещё образуют quorum. В этом случае применяют процедуру замены члена. Если большинство недоступно и вернуть его нельзя, выбирают восстановление из снимка. Сначала изолируют старые члены и писателей, чтобы они не возобновили работу параллельно с восстановленным кластером. Затем etcdutl snapshot restore создаёт новый каталог данных и новые идентификаторы кластера и члена. Работающий каталог базы сохраняют отдельно. Клиенты Kubernetes могли уже увидеть ревизии новее снимка: возврат к меньшему номеру мешает продолжению наблюдения. Флаг --bump-revision поднимает номер, а --mark-compacted завершает прежние наблюдения и вынуждает клиентов заново получить список объектов. Приращение рассчитывают по возможному числу изменений после снимка; пример расчёта приведён ниже.

После восстановления контроллеры заново получают объекты через list/watch и приводят реальные процессы к сохранённым спецификациям. Данные внешних томов при этом остаются на своих дисках. Например, снимок etcd хранит прежнюю конфигурацию Deployment, а прикладная БД на PVC уже прошла новую миграцию. Проверьте UID объектов, владельцев, привязку томов, Secrets, адреса сервисов и чтение прикладных записей. Успешный ответ API подтверждает только часть восстановления.

Проверить свежесть копии и время возврата услуги

Пусть RPO приложения равен одному часу. Снимок сделан в 11:00, отказ произошёл в 11:40: при отсутствии более свежих копий потеря изменений после снимка может составить 40 минут. Такая свежесть укладывается в выбранную цель. Время снимка надо измерять и записывать; получить его из номера ревизии нельзя. Отдельно зададим RTO в 45 минут и будем считать простой от отказа до приёма запросов с проверенными данными. Возврат услуги в 12:50 занимает 70 минут и превышает эту цель на 25 минут.

Для etcd и приложения фиксируют собственные цели и результаты: их копии могут относиться к разным моментам. Расшифровки RPO и RTO находятся в словаре; первичные определения доступны в статье NIST о RPO и статье о RTO.

Проверка: API вернулся за 20 минут. Можно ли записать RTO = 20 минут?

Запишите 20 минут как измеренное время возврата API и сравните его с заранее заданным RTO для API. Для приложения надо дождаться обработки запросов и проверки данных. Если это заняло 70 минут, в приведённом опыте измеренный простой приложения равен 70 минутам; RTO остаётся заданной целью 45 минут.

Границы rollback

Возврат предыдущей версии Deployment меняет шаблон Pod; Helm восстанавливает манифесты выбранного выпуска. Замена бинарного файла меняет исполняемый код. Восстановление etcd возвращает объекты управляющего состояния, а восстановление прикладной БД — её данные. Выберите нужную операцию по тому, что успело измениться. После необратимой миграции схемы прежний образ может уже не прочитать БД. Возврат снимка VM также не отменяет внешние платежи и изменения удалённого хранилища. До обслуживания подготовьте журнал шагов и критерии остановки; процедуру проверьте в отдельной сети.

План опыта с одним cp1 в изолированном клоне

INSTALL.txt получает совместимые etcdctl/etcdutl 3.6.8 из официального выпуска, проверяет сумму, устанавливает инструменты обслуживания в личную VM и создаёт закрытый каталог копий. Дополнительную службу etcd на хосте рецепт не создаёт. RECOVERY.txt проводит опыт по этапам: снимок с TLS, выключенный клон в отдельной сети, изоляция оригинала, перенос статических манифестов из отслеживаемого каталога, проверка остановки контейнеров через CRI. Затем база восстанавливается в новый каталог с новыми идентификаторами и поднятой ревизией. Старый каталог сохраняют, новый перемещают под прежний путь /var/lib/etcd, запускают etcd, API и контроллеры, после чего проверяют набор данных.

В RECOVERY.txt переменная ETCD_SNAPSHOT должна указывать на выбранный файл etcd.db по абсолютному пути. Перед restore сравните его SHA-256 с журналом. Рецепт отдельно запускает etcd и только после успешной проверки его здоровья возвращает манифесты API и контроллеров. При ошибке переноса выполнение останавливается; уже перемещённые файлы сохраняются для разбора.

Приращение 150000000 рассчитано для прироста ревизии etcd не более 200 в секунду и возраста снимка не более 7 суток: 200×7×86400=120960000. Разность до 150 миллионов оставляет запас. При большей скорости или интервале эту оценку пересчитывают. На единственном cp1 пути hostPath и data-dir остаются /var/lib/etcd: новый каталог подставляют после остановки старого etcd. Остановка kubelet сама по себе не останавливает уже запущенный контейнер etcd, поэтому рецепт проверяет задачи CRI. Для приложения с локальным PV нужен также изолированный клон wk1 с сохранёнными данными и соответствующим расположением тома. Этот опыт с восстановлением VM не выполнялся при подготовке главы; его результат предстоит проверить отдельно.
