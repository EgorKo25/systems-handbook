Scheduler: найти допустимый node, сравнить и назначить

Планирование использует заявленные потребности и ограничения. Оно не измеряет будущую бизнес-нагрузку и не резервирует отдельное физическое ядро каждому Pod.

Filter, score, reserve, bind

Scheduler наблюдает Pods без spec.nodeName. Scheduling cycle получает снимок cluster state и выполняет фильтры допустимости: ресурсы, selector/affinity, taints, доступность томов и другие plugins. Score ранжирует прошедшие nodes; выбранный node может участвовать в Reserve/Permit и binding cycle. Bind записывает назначение через API, после чего kubelet этого node замечает Pod. Если ни один node не прошёл filter, высокий score не поможет. Pending — фаза Pod, она включает также подготовку после назначения; для точной причины смотрите PodScheduled condition и Events.

Requests и limits имеют разные адресаты

Request — заявка для планирования и распределения ресурса; limit — верхняя граница исполнения, применяемая runtime/Linux при соответствующем ресурсе. CPU 50m означает 0.05 CPU единицы, где одна CPU примерно соответствует одному логическому ядру доступной машины. Memory 32Mi — 32×2²⁰ байт; 32M — 32×10⁶, это разные величины. Scheduler суммирует requests вместе с накладными расходами и особыми правилами init/sidecars, а не текущий RSS процесса. Allocatable node — доступный workloads бюджет после резервов и ограничений, не вся физическая RAM.

Пример: node allocatable 1500m CPU и 2 GiB, уже назначено requests 1200m/1.5 GiB. Новый Pod 400m/128Mi не проходит CPU даже при фактической загрузке 5%. Уменьшить request без измерения — риск переподписать CPU; добавить память не решит CPU filter. Limits CPU может приводить к throttling, ограничениям доступного CPU-времени, без перезапуска. Memory limit при невозможности освободить память может привести к OOM kill. Реальное потребление, request и limit надо видеть тремя отдельными рядами.

Affinity, taints и topology

nodeSelector требует совпадения labels node. Required node affinity — логическое условие обязательного выбора; preferred — предпочтение при scoring. Pod affinity/anti-affinity выражает отношение к размещению других Pods с учётом topologyKey. Taint помечает node нежелательным/недопустимым для Pods без подходящей toleration. Toleration разрешает терпеть taint, но не направляет Pod именно на этот node. NoSchedule влияет на новые назначения, NoExecute может также эвакуировать уже назначенные Pods по условиям/tolerationSeconds. Control-plane taint оставляем в VM-профиле с worker; не убираем его просто ради доступного места без пересчёта резерва.

Topology spread constraints задают допустимый skew распределения по доменам, например kubernetes.io/hostname. Два replicas на одном node переживают сбой одного процесса, но не его VM. Required anti-affinity на двух replicas при одном допустимом worker закономерно оставляет один Pending. Называть это «ошибкой Kubernetes» неверно: требования несовместимы с топологией. Для небольшого стенда используйте preferred или второй реальный worker и объясните компромисс. Labels topology — вход доверия: kubelet не должен иметь возможность сам назначить себе защищённую метку изоляции.

Preemption и граница исправления

Priority определяет относительную важность Pod при очереди и возможной preemption, вытеснении менее приоритетных Pods ради допустимого размещения. Это не мгновенное получение CPU и не гарантированный обход всех constraints. Affinity/volume topology могут оставлять задачу невыполнимой после вытеснения; PDB учитывается best effort при preemption, не даёт абсолютного запрета. Не выдавайте обычному учебному приложению системный priorityClass ради ускорения.

kubectl --context "$LAB_CONTEXT" describe node wk1
kubectl --context "$LAB_CONTEXT" -n lab describe pod POD_NAME
kubectl --context "$LAB_CONTEXT" -n lab get pod POD_NAME -o jsonpath='{.spec.nodeName}{"\n"}{.status.conditions}'

Для наблюдаемого отказа используется отдельный Deployment из scheduling-probe.yaml. Он просит 100 CPU, не выбирает системный приоритет и не совпадает с selector рабочего Service. Сначала убедитесь через kubectl --context "$LAB_CONTEXT" get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu, что ни один допустимый узел не имеет такого бюджета. Иначе это условие опыта не выполнено: число нельзя считать универсальным способом получить Pending.

kubectl --context "$LAB_CONTEXT" -n lab create -f vm/scheduling-probe.yaml
kubectl --context "$LAB_CONTEXT" -n lab get pods -l app=scheduling-probe -o wide
kubectl --context "$LAB_CONTEXT" -n lab describe deployment scheduling-probe
# Скопируйте фактическое имя Pod из первой таблицы:
kubectl --context "$LAB_CONTEXT" -n lab describe pod ACTUAL_PROBE_POD

В Events ищите FailedScheduling и недостаточный CPU; пустое spec.nodeName и условие PodScheduled=False отличают отсутствие назначения от ошибки загрузки образа после назначения. До запуска контейнер не потребляет запрошенные 100 CPU. Теперь исправьте template контроллера, а не уже созданный Pod:

kubectl --context "$LAB_CONTEXT" -n lab patch deployment scheduling-probe --type=strategic -p '{"spec":{"template":{"spec":{"containers":[{"name":"api","resources":{"requests":{"cpu":"50m","memory":"32Mi"},"limits":{"cpu":"500m","memory":"128Mi"}}}]}}}}'
kubectl --context "$LAB_CONTEXT" -n lab rollout status deployment/scheduling-probe --timeout=120s
kubectl --context "$LAB_CONTEXT" -n lab get pods -l app=scheduling-probe -o wide

Strategic merge сопоставляет container по имени api. Изменение template создаёт другую ревизию и Pod с другим UID; это не доказательство допустимости произвольной правки полей старого Pod. Если новый экземпляр тоже Pending, исследуйте оставшиеся constraints, а не уменьшайте request вслепую. Для повторения выполните такую же strategic-правку этого Deployment, задав CPU request и limit равными строке "100"; память оставьте прежней. Это снова намеренно сломает только scheduling-probe. Повторный create существующего объекта должен отказать, а не незаметно начать опыт заново. После разбора удаляют именно этот дополнительный Deployment, если надо освободить его 50m и 32Mi, а рабочий ledger-api и namespace оставляют.

Замерьте отдельно создание Pod → PodScheduled и PodScheduled → ContainersReady. Первая задержка связана с очередью и выбором узла, вторая — с образами, томами, процессом и проверками. Поэтому медленную загрузку image нельзя объяснять одним временем scheduler.
