Отказ как расследование: API, node, DNS, storage и программа

Неисправность изучается от наблюдаемого симптома к минимальной проверяемой гипотезе. Сброс кластера уничтожает именно те сведения, которые нужны для объяснения.

Первый протокол

Запишите время UTC, context/namespace, конкретную операцию, последний успешный результат, UID/revision/image и изменения. Отдельно отметьте доступность клиента к API и пользователя к HTTP. Если kubectl timeout, это не доказывает падение приложения; если HTTP500, API может быть полностью здоров. Сохраняйте только нужные redacted сведения без Secret/keys и приватных адресов. Работайте с ограниченными правами investigator до действия, которое требует администратора.

Control plane потерян, приложение ещё отвечает

С личного node VM проверьте systemd kubelet/containerd, static manifests, crictl и журналы. Если API static Pod CrashLoop из-за заполненного диска, выясните, чем занят filesystem, и освободите безопасно предусмотренные rotated logs/внешний capacity; не удаляйте etcd db. Если etcd без quorum, процесс API может существовать, но writes не подтверждаются. Если сертификат истёк, правьте PKI предусмотренным kubeadm renewal guide и обновляйте нужные kubeconfigs, а не дату системы. Recovery quorum и backup — отдельная процедура предыдущей главы.

Worker NotReady и опасность двойного писателя

Control plane узнаёт состояние через Node status/Lease heartbeat. При пропаже node срабатывают taints/eviction по настройкам и ограничениям; это не мгновенное доказательство, что старый процесс остановлен. Network partition может отрезать kubelet от API при живом приложении/storage. Перед force delete stateful Pod и запуском замены убедитесь в fencing старого node/volume. Stateless HTTP переносится проще, но дубликаты in-flight запросов всё равно требуют идемпотентности. Local PV на упавшем worker не переезжает от изменения spec.nodeName.

DNS и policy после нового правила

Сначала подтвердите direct PodIP и ServiceIP до DNS. Если direct проходит, ServiceIP нет — endpoints/dataplane. Если оба проходят, hostname нет — resolver/search/policy53. Если после ingress policy denied и allowed оба не работают, проверьте labels/port и общую readiness, а не объявляйте «deny победил». Если оба работают на default kindnet, проверьте enforcement реализации: API validation это не докажет. Удаление только своей policy в lab возвращает её вклад; другая широкая allow policy может менять итог.

Recovery завершается проверкой смысла

После исправления запишите, что именно изменили, когда condition сменилась, какой экземпляр отвечает и сохранились ли данные. API readyz и Pods Ready — необходимые инфраструктурные сигналы, а HTTP JSON/record hash — прикладные. Повторите исходную операцию ограниченное число раз, проверьте ошибки/latency и отсутствие растущей очереди. Не считайте новый чистый кластер восстановленным старым: сопоставьте UID, Secrets, PVC backend и business records. Если причина неизвестна, так и запишите вместо выдуманной истории.
