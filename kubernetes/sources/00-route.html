Kubernetes: от сохранённого намерения до работающего процесса

Самостоятельный том для Go-разработчика и инженера эксплуатации. Один сохраняемый кластер и сервис ledger-api проходят путь от установки до отказа, измерения и восстановления.

Что именно мы хотим получить

Kubernetes — система управления контейнерными нагрузками через API, то есть программный интерфейс операций над объектами. Автор описывает желаемое состояние, а независимые управляющие циклы сближают с ним наблюдаемое. Это не удалённый вызов «запусти Linux-процесс». Запись Deployment может уже находиться в хранилище, пока Pod ещё не назначен машине; Pod может быть назначен, но образ недоступен; процесс может работать, но Service не направляет к нему трафик. Поэтому доказательство проходит четыре границы: API принял объект, контроллер создал нужные объекты, node исполнил программу, клиент получил правильный ответ.

Control plane — управляющая часть: API server принимает запросы, etcd хранит состояние, scheduler выбирает node, controllers выполняют согласование. Node — зарегистрированная вычислительная машина, где kubelet организует исполнение Pods через container runtime. Контейнерный runtime — служба управления образами и контейнерами; здесь containerd. Pod — объект совместно размещаемых контейнеров с общей сетевой средой и указанными томами. Он не равен одному процессу, образу, VM или серверу приложения. Эти различия будут выводиться из конкретных изменений файлов, объектов и пакетов.

Какие объекты встретятся в первом запуске

Deployment — сохранённое описание взаимозаменяемых экземпляров программы и правил их обновления. Его контроллер создаёт ReplicaSet, а тот поддерживает нужное число Pods. Service — отдельный объект с постоянным именем и портом; его selector, условие выбора по меткам, связывает этот адрес с готовыми Pods. Метка app: ledger-api в наших файлах — обычная пара «ключ: значение», а не имя процесса. ConfigMap хранит несекретные настройки, которые программа получает при запуске. Это краткое знакомство позволит прочитать первые файлы; далее мы разберём, кто именно выполняет каждый переход.

Предполагаются уже разобранные Linux-процесс, TCP-соединение, файловая система, права и контейнерный образ. Если эти слова пока обозначают лишь знакомые названия, сначала вернитесь к томам Linux, Сети, Bash и Go. Образ — упакованные файлы и описание запуска; контейнер — их конкретное исполнение на узле. Kubernetes управляет такими исполнениями, но не собирает Go-код вместо компилятора.

Маршрут по внутренним книгам

Сначала выбираем стенд и сохраняем его состояние. Книга API объясняет идентичность, хранение, watch и конфликты управления. Книга исполнения проходит от scheduler до сигналов процессу Go. Сеть рассматривается отдельно: адреса, конкретный VXLAN/iptables путь, DNS, политики и внешний вход. Данные и доверие объясняют две границы, которые не спасает автоматический перезапуск. Эксплуатация связывает наблюдение, бюджет ресурсов, обновление и восстановление. Сквозные заявки требуют исправлять свой стенд, сохраняя UID, версии и данные между опытами.

Два честных стенда и один договор приложения

Основной путь — Ubuntu 24.04 в личных Linux-VM, kubeadm 1.36.6, containerd 2.4.2, Calico 3.33.0 в режиме VXLAN, kube-proxy iptables. Компактный путь — kind 0.33.0 с node image Kubernetes 1.36.4. Это разные patch и разные сетевые реализации. На машине с 8 GiB разумны один небольшой node или локальные тесты без кластера; несколько VM с резервом для ОС и IDE обычно требуют 16 GiB и последовательного включения других служб. Три control-plane и база на том же ноутбуке не превращаются в независимые зоны отказа.

ledger-api слушает TCP 8080 и предоставляет GET /livez, /readyz, /api/hello. Манифесты Kubernetes живут в namespace lab; Helm использует отдельный helm-lab и release ledger. Namespace — область имён и часть области действия политик, а не самостоятельная VM или автоматическая стена безопасности. Каждая команда явно получает выбранный context: handbook-admin либо kind-handbook. Context в kubeconfig связывает кластер, личность и namespace; он не является отдельным кластером.

Одна рабочая копия и сохранённые результаты

Скопируйте каталог kubernetes/labs из книги в собственную постоянную папку, например $HOME/handbook-lab/kubernetes/labs, вместе со всеми вложенными файлами. Книга может лежать на флэшке или открываться по HTTP; путь веб-страницы не становится рабочим каталогом терминала. Файлы стенда надо получить отдельно из исходников книги либо её полного офлайн-набора. Папку labs копируют один раз; при продолжении занятия возвращаются в неё, сохраняя изменённые файлы и журнал.

export K8S_LAB_ROOT="$HOME/handbook-lab/kubernetes/labs"
cd "$K8S_LAB_ROOT" || exit 1
test -f vm/kubeadm.yaml && test -f manifests/10-app.yaml && test -f service/main.go

Если проверка файлов неуспешна, следующий шаг не выполняют. В новой оболочке повторяют export и cd, а не копирование поверх старого каталога. Дальнейшие относительные пути vm/…, manifests/…, service/… отсчитываются от этой папки. Команды здесь записаны для Bash в личной Linux-среде. На рабочей Windows браузер читает книгу, а VM-команды исполняются через SSH в вашей машине стенда. Не направляйте их в системную оболочку рабочего компьютера.

Выбранный LAB_CONTEXT задаётся после установки кластера. K8S_LAB_ROOT хранит путь к файлам, LAB_CONTEXT — имя подключения; одна переменная не заменяет другую. При переносе компьютера переменные создают заново, а kubeconfig, исходники и состояние кластера сохраняют предусмотренным для них способом.

Как читать команды и доказательства

Выделение команды вроде kubectl get открывает штатную карточку справочника; карточки содержат аргументы, флаги, эффекты и ошибки. Команды с sudo, systemctl, swapoff, mount, iptables, crictl, ctr и сетевыми изменениями в этой книге предназначены исключительно для своей подготовленной VM. При создании книги они не исполнялись на компьютере пользователя. Локально действительно проверены Go, разобран YAML, проверена форма объектов по официальному OpenAPI и байты офлайн-набора. Это не свидетельства работы кластера; точный протокол находится в ПРОВЕРКИ.txt.

Интерактивные схемы — автономные пошаговые модели фиксированных сценариев. Они показывают инициатора, направление и переход состояния, не устанавливают службы и не отправляют запросов.
