Сквозной практикум: один кластер, один выпуск и журнал доказательств

Ни одно задание не требует учебной инфраструктуры сторонней организации. Локальные проверки исполнимы без кластера, cluster-задания имеют отдельные критерии.

Этап 0: безопасный локальный фундамент

Откройте README лаборатории. В service выполните go test -race -count=1 и go vet, затем CGO_ENABLED=0 go build -trimpath. Исходники stdlib-only, внешних Go modules нет. Тесты проверяют routes, JSON, независимость liveness/readiness, атомарный concurrent counter и graceful drain активного реального loopback request при отмене context. validate.py разбирает YAML с запретом duplicate keys, сверяет 15 объектов с подмножеством официального OpenAPI1.36.6 и отвергает два неверных случая. Bundle test обнаруживает corruption/path escape. Это реальные локальные действия, не API server simulation.

cd service
go test -race -count=1 ./...
go vet ./...
GOTOOLCHAIN=local CGO_ENABLED=0 go build -trimpath -o ledger-api-check .
sha256sum ledger-api-check
cd ..
python3 validate.py
python3 test_bundle.py

Здесь ledger-api-check — локальный артефакт проверки, а не готовый контейнерный выпуск. Одна сборка образа ledger-api:0.1.0 и его доставка подробно приведены в FIRST-WORKLOAD.txt перед главой API. Там выбирают GOOS=linux и архитектуру узла: бинарник Windows нельзя запускать в Linux scratch. Если образ уже создан и используется в сохраняемом кластере, этот этап не даёт разрешения пересобрать под тем же tag другой код. Сохраните revision, версию Go, флаги, hash бинарника и соответствующий image; Helm затем получает тот же выпуск.

Этап 1: installation и приёмка

Выберите kubeadm VM либо kind, запишите решение и ограничения. Выполните соответствующую главу и сохраните cluster/context. Приёмка: API version и readyz, nodes Ready, system Pods, DNS и межузловой путь для VM. Перезагрузите nodes последовательно, не выполняя init заново, и повторите приёмку. Проверьте офлайн-полноту в отдельном опыте отключённого upstream. Если нет ресурсов для кластера, оставайтесь на этапе 0: файл проверок не должен говорить, что остальные этапы завершены.

Этап 2: первый workload и четыре доказательства

Если вы уже прошли первый запуск перед главой API, этап продолжает те же объекты и тот же image: сначала читайте их status и журнал. Для первого запуска следуйте FIRST-WORKLOAD.txt, а не применяйте весь каталог manifests: NetworkPolicy, HPA и storage подключаются позднее по отдельности. При новом согласованном изменении сначала выполните diff и прочтите результат: код 0 — различий нет, 1 — есть различия, больше 1 — ошибка, после которой apply останавливают.

Дождитесь rollout status и сопоставьте Deployment → ReplicaSet → Pod по ownerReferences и UID; затем containerID, Ready и EndpointSlice. Через loopback port-forward получите /api/hello и сохраните публичный JSON. Отдельный запрос diagnostic Pod к Service DNS проверяет другой путь — кластерный dataplane; результат туннеля не заменяет его. Запишите время сохранения API, назначения Pod, старта контейнера, готовности и HTTP. Отсутствующее наблюдение помечают как неизвестное, а не достраивают из одной итоговой таблицы.

Этап 3: заявка «процесс жив, но клиент не получает endpoint»

Сначала запишите стабильную конфигурацию, revision и UID готового Pod. В этом опыте меняем только readiness через strategic merge по имени контейнера, не меняя image, MESSAGE и liveness:

kubectl --context "$LAB_CONTEXT" -n lab patch deployment ledger-api --type=strategic -p '{"spec":{"template":{"spec":{"containers":[{"name":"api","readinessProbe":{"httpGet":{"path":"/missing-readyz"}}}]}}}}'
kubectl --context "$LAB_CONTEXT" -n lab get pods -l app=ledger-api -o wide
kubectl --context "$LAB_CONTEXT" -n lab get endpointslices -l kubernetes.io/service-name=ledger-api -o yaml

Выберите новое фактическое имя Pod из таблицы и прочтите его describe: ожидаются HTTP 404 readiness, Ready=false, но успешная liveness и отсутствие обязательного роста restartCount. Если хватает surge-ёмкости, при maxUnavailable: 0 старый готовый Pod остаётся обслуживать. При нехватке места новый может вообще не запуститься — это другая причина, её нельзя назвать отказом readiness. Клиентский timeout rollout не откатывает сохранённый template.

kubectl --context "$LAB_CONTEXT" -n lab patch deployment ledger-api --type=strategic -p '{"spec":{"template":{"spec":{"containers":[{"name":"api","readinessProbe":{"httpGet":{"path":"/readyz"}}}]}}}}'
kubectl --context "$LAB_CONTEXT" -n lab rollout status deployment/ledger-api --timeout=120s
kubectl --context "$LAB_CONTEXT" -n lab get pods -l app=ledger-api -o wide

Вторая узкая правка возвращает исходный путь, сохраняя остальные настройки. Затем подтвердите HTTP, новый UID и состав готовых endpoints. Императивный patch может изменить managedFields; если последующий SSA хочет изменить уже принадлежащее другому manager поле, разбирайте конкретный конфликт, а не добавляйте force ко всему приложению. В поддерживаемом desired-файле путь также должен остаться /readyz. Namespace и старые доказательства не удаляют.

Этап 4: конфигурация и ownership

Измените MESSAGE в ConfigMap, проверьте старый ответ без restart, затем выполните осмысленный rollout и получите новый. На отдельном ConfigMap пройдите SSA conflict двух managers: managerB меняет поле managerA без force, получает conflict; затем возвращает исходный договор. На отдельной копии объекта сделайте устаревший resourceVersion replace и получите 409, reread/recompute/retry. Не включайте force-conflicts как постоянный флаг. Все изменения возвращайте к файлам и журналу, а не к новому пустому namespace.

Этап 5: ограниченный расследователь и сеть

Примените 20-rbac и работайте как investigator через подготовленный ограниченный клиент/администраторскую impersonation-проверку. Требуется прочитать Pod logs и Service endpoints, получить отказ secrets/exec/update. На VM Calico profile установите 30-policy, сравните allowed/denied clients и directIP/ServiceDNS. Ошибка label access объясняется наблюдениями. В kindnet отметьте отсутствие поддерживаемой проверки policy, не рисуйте зелёный результат. Снимите короткий packet capture только в своей VM, запишите tuple и отделите outer VXLAN от внутреннего NAT.

Этап 6: данные, обслуживание и восстановление

Локальный PV/Job опыт выполняйте отдельно на wk1 с явно подготовленным каталогом и image. Докажите тот же record hash после замены consumer, затем объясните Pending после остановки wk1. Для PDB/drain сначала создайте достаточное число ready replicas и допустимые nodes; один worker не обеспечивает failover. HPA подключайте только после metrics API и понимания владения replicas; не смешивайте его с ручным scale без журнала. Backup etcd/application и restore проверяют в изолированном clone, не поверх рабочего учебного cluster. Recovery должен подтвердить исходный dataset, а не только новый hello.

Условия завершения и переход к Helm

У вас есть install/version inventory, сохранённый кластер, образ 0.1.0, namespace lab, API/process/packet evidence, ограниченная identity, backup plan и честные непроверенные пункты. Helm получает тот же HTTP/env контракт и byte-identical исходники в отдельном namespace helm-lab. Он управляет своим release, а не перехватывает созданный kubectl Deployment. В журнале сравнивайте одинаковый image digest и разные object UID. Финальное уничтожение kubectl delete namespace lab — отдельное решение после проверки reclaim и резервов, его нет в обычном reset задания.
