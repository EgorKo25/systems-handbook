Пакет через Calico VXLAN и kube-proxy iptables

Точный сценарий: Linux VM, single-stack IPv4, Calico 3.33 VXLAN Always, eBPF выключен, kube-proxy 1.36 iptables. Для другого стека этот путь нельзя копировать механически.

Фиксируем наблюдаемый эксперимент

Пусть клиент Pod A на cp1 имеет 10.244.1.2:41000, backend Pod B на wk1 — 10.244.2.3:8080, Service S — 10.96.10.20:80. Это условные адреса внутри объявленных подсетей; фактические берите из get pod/service. cp1 и wk1 соединены underlay 192.168.56.10/.11 с MTU 1500. У клиента нет hostNetwork, у Service нет session affinity и специальных traffic policies, выбирается B на другом node. Фиксируем один первый TCP SYN, затем conntrack ведёт это соединение.

Pod→Pod без Service

Прямой пакет A→B выходит через eth0 Pod к host-side veth. Calico применяет установленные policy/routing правила, node определяет удалённый endpoint. VXLAN, Virtual Extensible LAN, инкапсулирует внутренний Ethernet/IP пакет в UDP между node IP, в данном профиле UDP 4789. Underlay переносит внешний пакет 192.168.56.10→192.168.56.11, а внутренние Pod IP остаются A→B. На wk1 VXLAN decapsulation снимает оболочку и маршрутизация доставляет внутренний пакет к veth B с применимой policy. В той же VM удалённого tunnel hop нет: host routes ведут к peer veth.

Нельзя заключить из этого, что в любом CNI есть bridge cni0 или что каждый Pod проходит Docker bridge. Calico использует собственные interfaces/routes. VXLAN Always в выбранном pool требует инкапсуляции для межузлового Pod-трафика даже в общей underlay подсети; CrossSubnet имел бы иные условия. BGP/native routing, IPIP и WireGuard изменили бы оболочку/маршруты. Схема описывает логические границы; точные netfilter chain names/порядок подсистем проверяют на реальном node конкретной версии.

Service добавляет DNAT и состояние соединения

При обращении A→S первый пакет на node клиента попадает в правила Service, установленные kube-proxy. Из готовых endpoints выбирается B, destination NAT, DNAT, меняет destination 10.96.10.20:80 на 10.244.2.3:8080. Для этого внутрикластерного не-hairpin сценария исходный Pod IP обычно сохраняется; специальные masquerade настройки/исключения меняют условия. Затем маршрутизация Calico доставляет пакет к B через VXLAN. Service IP не должен появляться на eth0 Go-процесса как адрес listener: процесс принимает на PodIP:8080/0.0.0.0:8080.

Conntrack — отслеживание состояния соединений Linux/netfilter — сохраняет соответствие исходного и переведённого tuple. Ответ B→A возвращается по предусмотренному маршруту к node, где применялась трансляция; обратное NAT представляет клиенту ответ от Service IP:80. Если ответ ушёл в обход необходимого stateful узла, асимметрия и filtering могут сломать соединение. TCP keepalive, long-lived соединения и UDP timeouts имеют последствия для удаления endpoint: обновление списка endpoints не переписывает магически все старые соединения.

# Read-only, only on your prepared VM nodes:
sudo ip -details link show vxlan.calico
sudo ip route get 10.244.2.3
sudo iptables-save -t nat
sudo conntrack -L -p tcp
sudo tcpdump -ni any 'udp port 4789 or (host 10.244.2.3 and tcp port 8080)'

iptables-save читает правила, iptables -F их разрушает и здесь не нужен. Ubuntu iptables может использовать nf_tables backend; это не означает kube-proxy mode=nftables. Узнайте iptables --version и kube-proxy ConfigMap. conntrack/tcpdump требуют средств и прав внутри личной VM; capture содержит данные трафика. Снимайте короткий отрезок и сверяйте четыре tuple: до DNAT, после DNAT, outer VXLAN, обратный ответ. Вывод здесь не подделывается заранее.

nftables, IPVS и eBPF — разные реализации

В Kubernetes 1.36 nftables proxy mode уже stable (с 1.33), iptables остаётся поддерживаемым; IPVS deprecated с 1.35. Stable не означает default. Наша конфигурация явно pin mode=iptables. Нативный nftables режим использует другие правила/API ядра и имеет отличия NodePort/localhost/firewall; миграция требует проверки kernel/tooling и документации версии. IPVS использует Linux IPVS вместе с другими сетевыми механизмами, но deprecated путь не выбираем для нового учебного стенда. Не смешивайте chain names iptables с maps nftables в одной воображаемой трассе.

eBPF dataplane может заменить kube-proxy: программы ядра и maps реализуют load balancing и policy, иногда выполняя service translation на другой точке, включая socket-level hook. eBPF, extended Berkeley Packet Filter, — механизм безопасно проверяемых программ в kernel, а не протокол сети. Сравнение с iptables требует выбранной CNI версии/mode, включённых optimizations, conntrack/DSR и измерения. Нельзя обещать «eBPF всегда без NAT и быстрее»; путь и выгода зависят от сценария.

MTU, fragments и измерение

При underlay 1500 и IPv4 VXLAN overhead около 50 байт внутренний MTU 1450 предотвращает фрагментацию в этом профиле. Внешний IPv6 или дополнительный VPN уменьшают бюджет. Симптом MTU — маленький HTTP работает, большой response/TLS зависает; это отличается от полного отсутствия маршрута. Проверяют path MTU, ICMP Packet Too Big/fragmentation needed и captures, а не только ping по умолчанию. Измеряйте packets/s, bytes/s, retransmits, conntrack occupancy/drops, node softirq CPU и p95 latency при одинаковом числе endpoints. Увеличение Service replicas не исправляет заполненную conntrack table.

Как разместить диагностический клиент на cp1

В базовом VM-кластере control-plane taint сохраняется, поэтому обычный application Pod туда не попадёт. diagnostic.yaml размещает только client-allowed на cp1 через явные nodeSelector и toleration; это административная подготовка учебного эксперимента, а не снятие taint со всего node. Backend ledger-api остаётся на wk1. Так можно исследовать cross-node путь на двух небольших VM без третьего worker. IP из схемы замените фактическими из get pod -o wide. В kind этот VM-specific файл с cp1 не применяют: имя node и CNI там другие.

Названия сетевых механизмов

iptables — пользовательский интерфейс управления определёнными netfilter правилами Linux; nftables — другая инфраструктура правил и интерфейс ядра. IPVS (IP Virtual Server) — механизм виртуальных сервисов/балансировки Linux, который использует соответствующий proxy mode. IPIP (IP in IP) помещает IP-пакет в другой IP-пакет и отличается от выбранного VXLAN с UDP. Эти имена описывают разные уровни реализации. Netfilter hooks, routing decisions и CNI policy изучают в заданном стеке, а не через одну универсальную стрелку «Kubernetes network».
