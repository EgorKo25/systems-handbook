ConfigMap, Secret, ServiceAccount и выпуск конфигурации

Конфигурация имеет собственную идентичность и момент доставки в процесс. Изменив объект API, вы не обязательно изменили уже работающий Go-процесс.

Environment и projected files

ConfigMap хранит не секретные key/value данные. Наш ledger-config содержит MESSAGE; envFrom подставляет его в environment контейнера при создании процесса. Уже запущенный процесс не получает новое значение от обновления ConfigMap. Чтобы применить новую environment-конфигурацию, создают новые Pods через осмысленный rollout. Если ConfigMap смонтирован как volume, kubelet обновляет projected content с eventual задержкой по своему sync/cache механизму; приложение должно перечитать файл и обработать атомарную смену. SubPath mount не получает обычных автоматических обновлений ConfigMap. Это три разных механизма, у них разное доказательство успеха.

kubectl --context "$LAB_CONTEXT" -n lab get configmap ledger-config -o yaml
kubectl --context "$LAB_CONTEXT" -n lab patch configmap ledger-config --type=merge -p '{"data":{"MESSAGE":"second configuration"}}'
# Existing env still carries the previous value; observe /api/hello first.
kubectl --context "$LAB_CONTEXT" -n lab rollout restart deployment/ledger-api
kubectl --context "$LAB_CONTEXT" -n lab rollout status deployment/ledger-api --timeout=120s

Patch меняет отдельный объект, restart меняет template workload и создаёт новые процессы; только прикладной ответ подтверждает, что процесс прочитал MESSAGE. Для воспроизводимых выпусков удобно versioned/immutable ConfigMap с именем от содержимого и обновлением ссылки в template. Тогда rollback template возвращает ссылку на старую конфигурацию, пока старый объект сохранён. Checksum annotation в Helm — способ инициировать rollout, но его вводит chart; Kubernetes не вычисляет её автоматически.

Secret и чувствительные байты

Secret — API-объект для небольших чувствительных данных с особыми conventions/types и механизмами доставки. Base64 в data — кодирование, не шифрование. stringData удобно для ввода plaintext, но его применение с SSA имеет особенности; не помещайте настоящие секреты в примеры/Git/лог diff. По умолчанию Kubernetes Secret не означает шифрование etcd at rest: администратор отдельно настраивает EncryptionConfiguration/KMS и выполняет миграцию уже записанных объектов. Backup etcd без такой защиты также содержит чувствительные данные.

Environment секрет читается процессом и может утечь через diagnostics, crash dump, exec, логирование конфигурации. Volume требует прав и защиты node. Доступ create Pods часто позволяет получить namespace Secrets косвенно, даже без прямого get secrets. Секрет не становится безопасным от создания второго namespace с тем же паролем. Для лаборатории используйте явное выдуманное значение и изучите форму; реальный API token выпускайте ограниченным и короткоживущим, не сохраняйте в тексте книги.

ServiceAccount — identity, не Linux uid

ServiceAccount представляет workload identity для API. Поле serviceAccountName выбирает её, а Linux runAsUser задаёт совсем другую личность внутри ОС. Современные projected ServiceAccount tokens выдаются TokenRequest API с audience и временем действия; это не обязательно вечный Secret token старых версий. Audience ограничивает предназначенный получатель, expiration — срок, но похищенный допустимый token до отзыва/истечения остаётся credential. Наша служба вообще не обращается к Kubernetes API, поэтому automountServiceAccountToken=false задан и на ServiceAccount, и в Pod.

Конфигурация как часть контракта выпуска

Зафиксируйте image digest, config identity, public ports, Service selectors, resource settings и требуемые API. Отдельно опишите migration/rollback данных. Image tag 0.1.0 должен обозначать одни подготовленные байты в нашем учебном переходе Kubernetes→Helm; нельзя собрать другой бинарник с другим environment-контрактом под тем же tag и считать это тем же выпуском. В registry предпочтителен digest; локальный kind tag допустим как явно ограниченная доставка, пока вы контролируете его соответствие manifest.

Чрезмерная конфигурация тоже стоит денег: большой environment передаётся каждому process, слишком частая смена checksum создаёт лишние ReplicaSets/pulls/starts. Измеряйте число rollout на бизнес-изменение, время готовности и churn, а не только объём YAML. Для ConfigMap/Secret существуют ограничения размера; большие бинарные наборы данных должны жить в подходящем artifact/object storage, не в etcd.
