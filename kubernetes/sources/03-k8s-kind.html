Компактный kind: настоящий API в контейнерных nodes

kind помогает изучить Kubernetes API без набора VM. Его сеть, диски и общий kernel не следует принимать за устройство отдельной Linux-машины.

Создание одного сохраняемого кластера

kind, Kubernetes IN Docker, запускает node-контейнеры со средствами Kubernetes. Используйте уже подготовленный личный container engine; эта книга его не устанавливает на host. На Windows Linux engine обычно работает внутри своей VM/WSL2, поэтому память и адреса надо смотреть также там. Скачайте kind 0.33.0 под свою ОС/архитектуру и проверьте официальный sha256sum. Не выбирайте latest node image: release 0.33.0 публикует 1.36.4 с конкретным digest. Рецепт намеренно отличается от kubeadm VM patch 1.36.6, сохраняя ту же API minor-линию.

kind version
kind create cluster --config vm/kind.yaml --wait 180s
export LAB_CONTEXT=kind-handbook
kubectl --context "$LAB_CONTEXT" version -o yaml
kubectl --context "$LAB_CONTEXT" get nodes -o wide
kind get clusters

--config выбирает точный node image и bind API на 127.0.0.1:16443; --wait ждёт предусмотренную готовность control plane, а не тестирует ваше приложение. Если offline, node image сначала импортируют в engine, а все нужные workload images — в nodes. kind load docker-image ledger-api:0.1.0 --name handbook переносит локальный image в runtime kind, но не публикует его в registry. На многонодовом кластере инструмент загружает image в nodes; окончательно проверьте crictl/статус Pod при расписании на другую машину.

Границы сетевого опыта

В базовом kind используется kindnet для Pod-сети. Это не выбранный VM Calico VXLAN, а NetworkPolicy без поддерживающего plugin может существовать в API без блокировки пакета. Для упражнений policy нужен отдельный осознанный kind-профиль с отключённым default CNI и установленным совместимым CNI; не устанавливайте Calico поверх работающего kindnet. Вместо скрытой замены основная книга проверяет policy на VM-профиле. Для kind остаются API, workload, probes, rollout, RBAC и port-forward.

ClusterIP доступен из кластерной сети, NodePort относится к адресу node-контейнера, а не автоматически к физическому Windows. port-forward --address=127.0.0.1 даёт локальный туннель для клиента. Он проходит через API/kubelet к выбранному Pod и не доказывает Service dataplane, source IP или NetworkPolicy. Для доступного с хоста NodePort нужна заранее настроенная extraPortMappings; открытие произвольного host порта не является свойством манифеста Service.

Сохранение, остановка и честный отказ

Сохраняйте один cluster handbook весь практикум. kind delete cluster --name handbook уничтожает nodes и их локальные данные; повторное create создаёт новый cluster с новыми UID, сертификатами и пустым etcd. Это не восстановление. Перезапуск container engine сохраняет его volumes по его правилам, но не гарантирует application-consistent snapshot. Перед обслуживанием сохраняйте нужные object manifests, секреты безопасно и отдельные backup данных, проверяйте restart. Не обещаем прозрачную приостановку Kubernetes кнопкой «пауза VM»: часы, токены и соединения продолжают иметь последствия.

Стоимость измеряйте в idle RSS (resident set size, объём резидентных страниц памяти процесса) и CPU engine и node-контейнеров, диске images, времени API и свободной памяти хоста. Если увеличение replicas на одном node уменьшает общую пропускную способность из-за CPU contention, «распределённая архитектура» не дала аппаратного параллелизма. Полезный контроль — тот же Go-бинарник на loopback: сравните p50/p95, CPU-sec на запрос и расход RAM при одинаковом workload. Цена kind часто оправдана изучением API, а не ускорением маленького сервиса.
