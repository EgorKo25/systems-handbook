Постоянный кластер kubeadm в личных Ubuntu-VM

Цель опыта — запустить управляющие компоненты на cp1, подключить рабочий узел wk1 и проверить восстановление их работы после перезагрузки. Этот рецепт предназначен для своих VM. Реальный кластер по нему при подготовке тома не запускался; рабочий хост для опыта не подходит.

Сначала карта адресов, прав и дисков

Создайте cp1 и wk1 из проверенного Ubuntu 24.04 ISO. У каждой уникальны hostname, MAC и product_uuid. Пример private-сети: cp1 192.168.56.10, wk1 192.168.56.11, имя cp1.lab.internal разрешается на обеих VM и клиенте. Это пример, который надо проверить на пересечение с домашней LAN/VPN/WSL/Docker. PodCIDR 10.244.0.0/16 и ServiceCIDR 10.96.0.0/16 тоже не должны пересекаться с внешними маршрутами и друг с другом. CIDR — адресный префикс; /16 обозначает фиксированные первые 16 бит IPv4, а не количество машин.

Сделайте снимок чистых выключенных VM и запишите ресурсы, версии ядра, диски, время, DNS, routes и свободное место. Снимки работающих VM не заменяют согласованную резервную копию etcd и данных приложения. В выбранном базовом варианте один cp1: его потеря останавливает новые API-изменения и согласование, хотя уже запущенное приложение на wk1 может некоторое время отвечать. Порт TCP 6443 доступен только доверенным клиентам/nodes, kubelet TCP 10250 — control plane; etcd 2379/2380 только соответствующим control-plane членам. VXLAN UDP 4789 — только между nodes. Не открывайте все порты всем ради прохождения join.

Подготовить node, не меняя рабочий компьютер

Внутри обеих VM включают нужные kernel modules overlay и br_netfilter, IPv4 forwarding и согласуют netfilter с CNI; проверяют синхронизацию времени и отсутствие конфликтующего firewall/NetworkManager. Файл системных параметров в VM должен пережить reboot. Для этого учебного профиля swap отключён в VM и исключён из её fstab; failSwapOn: true делает неожиданно включённый swap явным отказом. Kubernetes поддерживает отдельные режимы Linux swap при условиях версии, но эта книга не смешивает их с базовым стендом. swapon --show — чтение; swapoff -a — меняющая операция только на своей VM после проверки RAM.

uname -r
stat -fc %T /sys/fs/cgroup
swapon --show
ip -brief address
ip route
sudo modprobe overlay
sudo modprobe br_netfilter
# Only inside the personal VM; persist reviewed equivalents in /etc/sysctl.d/.
sudo sysctl -w net.ipv4.ip_forward=1
sudo sysctl -w net.bridge.bridge-nf-call-iptables=1

Ожидаем cgroup2fs на Ubuntu с cgroup v2. cgroup — иерархия учёта и ограничения ресурсов Linux. kubelet и containerd используют systemd-драйвер, иначе две программы могут считать ресурсную иерархию по-разному. Файл containerd.toml использует config version 3 и plugin path containerd 2.x, а не старую секцию 1.x. CRI не должен быть в disabled_plugins. sandbox image pause:3.10.2 согласован с исходником kubeadm v1.36.6. Служба containerd хранит persistent content/snapshots в /var/lib/containerd, runtime socket/state — в /run/containerd; kubelet state — /var/lib/kubelet. Не удаляйте эти каталоги как «кэш», пока не понимаете владельцев и mounts.

Установите заранее проверенные containerd/runc/CNI и пакеты kubelet/kubeadm/kubectl внутри VM. Upstream containerd tar обычно распаковывается под /usr/local, runc помещается в /usr/local/sbin; unit возьмите из того же tag и проверьте ExecStart. Упаковка .deb может использовать другие пути и не должна одновременно владеть теми же файлами. systemctl enable --now containerd меняет автозагрузку и запускает службу. systemctl status, journalctl -u containerd, crictl --runtime-endpoint unix:///run/containerd/containerd.sock info подтверждают процесс, CRI и согласование cgroup. Даже при работающей службе создание Pod может завершиться ошибкой: отдельно проверяются CRI и доступность образов.

Точная установка выбранных пакетов в VM

Полная последовательность команд находится в INSTALL.txt: получение, проверка, systemd unit, paths, scoped apt keyring, Debian package revision и cold offline проверка. Здесь проследим важные переходы. Upstream tar containerd 2.4.2-linux-amd64 содержит bin/containerd и shims; runc.amd64 поставляется отдельно. После проверки tar распаковывают в /usr/local, runc устанавливают в /usr/local/sbin/runc, официальный unit того же tag — в /usr/local/lib/systemd/system. Его ExecStart должен ссылаться именно на установленный binary. Затем размещают нашу конфигурацию формата 3, daemon-reload перечитывает unit, enable создаёт автозагрузку, start запускает процесс. Состояние службы, журналы и ctr plugins list помогают различить остановленный процесс и ошибку загрузки CRI-плагина.

В полном рецепте раздел 1 заканчивается проверкой архивов и отдельных файлов. После успеха раздел 2 переносит проверенные файлы в системные каталоги вашей VM, устанавливает containerd.toml из $K8S_LAB_ROOT/vm и запускает службу. На этом этапе сравните путь ExecStart с установленным файлом и откройте sudo ctr plugins list, чтобы увидеть CRI-плагин.

Перед установкой создаются нужные каталоги; полный рецепт показывает их явно. Не распаковывайте tar поверх package-managed containerd другой версии. У unit есть полномочия root VM: проверка URL/hash/содержимого unit столь же важна, как проверка binary. Краткая успешная status строка не означает, что runc найден в PATH systemd или что CRI plugin исправен. После kubelet пакетов проверяется crictl info по заданному socket.

Официальный minor repository для этого baseline — pkgs.k8s.io/core:/stable:/v1.36/deb/. Release.key сначала сохраняется в файл и сверяется по официальной цепочке поставщика, затем превращается gpg --dearmor в отдельный keyring. Signed-By ограничивает доверие этим source. На 01.11.2026 Packages.gz действительно содержит amd64 версии kubeadm/kubelet/kubectl1.36.6-1.1; это конкретная Debian revision, а не догадка из SemVer.

apt-cache madison kubeadm kubelet kubectl
sudo apt-get install -y kubeadm=1.36.6-1.1 kubelet=1.36.6-1.1 kubectl=1.36.6-1.1
sudo apt-mark hold kubeadm kubelet kubectl
dpkg-query -W kubeadm kubelet kubectl kubernetes-cni
sudo systemctl enable kubelet

apt разрешает транзитивные package dependencies, которые фиксируются в inventory. Hold препятствует обычному автоматическому обновлению этих трёх пакетов, но не является backup или заморозкой всей ОС. Для offline чистый staging clone скачивает download-only набор до установки, переносит .deb и metadata/key record, а offline clone выполняет --no-download install локальных .deb. Если staging уже имел зависимость, download-only мог её пропустить; поэтому cold offline acceptance обязателен. CNI reference archive1.9.1 сохранён отдельно, а в данном пути /opt/cni/bin получает kubernetes-cni package и затем предусмотренные Calico installer components: не перезаписывайте package files произвольным tar поверх работающего node.

Постоянные VM-настройки modules/sysctl помещают после проверки в /etc/modules-load.d/handbook.conf и /etc/sysctl.d/90-handbook.conf, перечитывают и проверяют после reboot. Swap выключают в своём VM fstab с копией до правки, а не sed по всем строкам на хосте. Firewall правила сохраняют по модели своей VM-сети; список разрешённых направлений выше не означает полное отключение firewall. Конкретные команды изменения рабочей сети намеренно не выдаются за безопасный локальный тест автора.

Bootstrap: какие файлы рождаются

Перед init должны работать CRI и выбранный runtime. Для офлайн-запуска заранее импортируйте все требуемые образы по INSTALL.txt и проверьте их наличие командой crictl --runtime-endpoint unix:///run/containerd/containerd.sock images. Команда kubeadm config images list только перечисляет имена: она не загружает образы и не проверяет, что runtime уже имеет их.

На cp1 изучите kubeadm.yaml и сравните с kubeadm config print init-defaults. InitConfiguration задаёт node/CRI, ClusterConfiguration — версию, endpoint и подсети; KubeletConfiguration — cgroup/swap; KubeProxyConfiguration явно фиксирует iptables. kubeadm API v1beta4 — версия конфигурации bootstrap, не apps/v1 workload API. API endpoint должен присутствовать в SAN (subject alternative name, списке допустимых имён/IP) сертификата; подмена адреса в kubeconfig не расширяет сертификат.

Выполните блок один раз на подготовленной cp1 с сохранённой переменной K8S_LAB_ROOT. K8S_LAB_ROOT должен быть абсолютным путём к вашей копии каталога labs из тома; внутри него находятся vm/kubeadm.yaml и customize_calico.py. Не выполняйте параллельную инициализацию и не меняйте целевой файл kubeconfig во время блока. Выбранный каталог должен быть доступен для записи только вам. Для копии kubeconfig по умолчанию используется $HOME/.kube/handbook.conf. Если нужен другой путь, заранее задайте handbook_kubeconfig полным именем нового файла.

handbook_kubeconfig="${handbook_kubeconfig:-$HOME/.kube/handbook.conf}"
bootstrap_handbook() {
  case "${K8S_LAB_ROOT:-}" in
    /*) ;;
    *) printf '%s\n' 'Нужен абсолютный K8S_LAB_ROOT.' >&2; return 1 ;;
  esac
  case "$handbook_kubeconfig" in
    /*) ;;
    *) printf '%s\n' 'Нужен абсолютный путь kubeconfig.' >&2; return 1 ;;
  esac
  config="$K8S_LAB_ROOT/vm/kubeadm.yaml"
  test -f "$config" || return 1
  if test -e "$handbook_kubeconfig" || test -L "$handbook_kubeconfig"; then
    printf '%s\n' 'Файл для учебного kubeconfig уже существует.' >&2
    return 1
  fi
  sudo kubeadm config validate --config "$config" || return 1
  sudo kubeadm config images list --config "$config" || return 1
  sudo kubeadm init --config "$config" || return 1
  mkdir -p -- "$(dirname -- "$handbook_kubeconfig")" || return 1
  sudo install -m 0600 -o "$(id -u)" -g "$(id -g)" \
    /etc/kubernetes/admin.conf "$handbook_kubeconfig" || return 1
  kubectl --kubeconfig "$handbook_kubeconfig" \
    config rename-context kubernetes-admin@handbook handbook-admin
}
bootstrap_handbook &&
export KUBECONFIG="$handbook_kubeconfig" LAB_CONTEXT=handbook-admin

Каждый шаг запускается после успеха предыдущего. Ошибка проверки или списка образов останавливает блок до init. Если ошибка возникла внутри init, часть сертификатов и манифестов уже могла появиться, а часть компонентов — запуститься. Запишите последнюю фазу из вывода и проверьте файлы, журналы kubelet и состояние API до решения о повторе. Если отказало только копирование kubeconfig или переименование контекста, восстановите этот шаг отдельно: повторный init для него не нужен. Переменные для следующих команд устанавливаются после успешной подготовки файла и контекста.

validate проверяет конфигурацию, images list — перечень, init создаёт PKI (public key infrastructure, инфраструктуру ключей и сертификатов) в /etc/kubernetes/pki, kubeconfig и static Pod manifests в /etc/kubernetes/manifests. kubelet замечает manifests и запускает etcd/API/scheduler/controller-manager через CRI. В /var/lib/etcd находятся WAL (write-ahead log, журнал предварительной записи) и база etcd, а не YAML-файлы по одному объекту. admin.conf — файл kubeconfig с адресом API, данными доверия и административными учётными данными. Нельзя публиковать его, отправлять в Git или использовать ежедневно для чтения журнала приложения.

Локальный манифест сообщает kubelet, какой Pod поддерживать на узле. Для управляющих компонентов kubeadm задаёт сеть самого узла, hostNetwork: true: им не требуется сначала получить обычный адрес Pod из Calico. Поэтому готовность API ещё не доказывает готовность сети обычных Pod. CoreDNS и прикладным Pod потребуется работающий CNI. Это свойство выбранных манифестов kubeadm, а не всех локально заданных Pod. Создание Pod управляющих компонентов в v1.36.6.

CNI, join и приёмка после reboot

Продолжайте только после успешной подготовки kubeconfig и контекста. Если предыдущий блок отказал, не переходите к apply. Сверьте в выбранном kubeconfig адрес API https://cp1.lab.internal:6443 и данные доверия с паспортом своего кластера: одно имя handbook-admin не доказывает, к какому API пойдёт запрос. Переименование контекста меняет локальное имя, не адрес и не права. Команды ниже продолжают работу из сохранённого K8S_LAB_ROOT. Исходный официальный файл и преобразованный calico-lab.yaml имеют разные имена. Helper отказывается перезаписывать существующий output, поэтому при повторном занятии сначала сравнивают уже подготовленный файл и текущий кластер; новую генерацию сохраняют под другим именем. После ошибки checksum или transform apply не выполняется. На офлайн-машину переносят уже проверенный source вместе с image-набором; наличие YAML не доказывает наличие образов.

До установки CNI CoreDNS может быть Pending, nodes — NotReady. Скачайте точный официальный calico.yaml, проверьте SHA из журнала источников; customize_calico.py офлайн изменяет только staged manifest: VXLAN Always, IPIP Never, pool 10.244/16, выбор IP из private-сети, MTU 1450 для underlay 1500, eBPF выключен, BIRD-проверки убраны из VXLAN-профиля. Этот MTU правильный лишь при IPv4 VXLAN с overhead 50 байт и underlay MTU 1500. Если поверх VPN есть меньший MTU, 1450 тоже может оказаться слишком большим.

prepare_calico() {
  cd "$K8S_LAB_ROOT" || return 1
  mkdir -p staged || return 1
  if test ! -e staged/calico-v3.33.0.yaml; then
    curl -fL -o staged/calico-v3.33.0.yaml https://raw.githubusercontent.com/projectcalico/calico/v3.33.0/manifests/calico.yaml || return 1
  fi
  printf '%s  staged/calico-v3.33.0.yaml\n' 2de8f47595fb9c41b3f47d7b767a1f8e72ecf84057af834738ff12689a234da5 | sha256sum -c - || return 1
  python3 customize_calico.py staged/calico-v3.33.0.yaml staged/calico-lab.yaml || return 1
}
prepare_calico && kubectl --context "$LAB_CONTEXT" apply -f staged/calico-lab.yaml

После успешного apply попросите cp1 напечатать команду подключения. Выполните её с указанным отпечатком CA только на wk1. После подключения вернитесь на cp1 и проверьте состояния узлов и системных Pod.

sudo kubeadm token create --print-join-command
kubectl --context "$LAB_CONTEXT" get nodes -o wide
kubectl --context "$LAB_CONTEXT" -n kube-system get pods -o wide
kubectl --context "$LAB_CONTEXT" get --raw='/readyz?verbose'

Join token — короткоживущий bootstrap credential, CA hash закрепляет доверие к кластеру. Не используйте skip-ca-verification. Join регистрирует kubelet identity; controller проверяет CSR (certificate signing request, запрос подписи сертификата) по настроенному bootstrap-процессу. Не копируйте admin.conf в Pod или на все workers. Приёмка: оба node Ready, system Pods готовы, DNS разрешает service, межузловой HTTP проходит, IP/pool/MTU совпадают с профилем, после последовательного reboot VM всё возвращается без повторного init. Запишите images digest, конфигурацию и состояния. Не выполняйте kubeadm reset между задачами: это разбор node, а не универсальное исправление CNI.

Два интерфейса VM: API address и kubelet InternalIP

У VM часто есть NAT-интерфейс для download и private-интерфейс для cluster traffic. Default route может указывать на NAT; тогда kubelet без явного выбора опубликует не тот InternalIP. advertiseAddress API server не задаёт IP всех kubelets, а Calico autodetection относится к CNI и тоже не заменяет kubelet node-ip. В InitConfiguration fixture cp1 явно задан kubeletExtraArgs node-ip=192.168.56.10. На wk1 перед join создайте /etc/default/kubelet со строкой KUBELET_EXTRA_ARGS=--node-ip=192.168.56.11, как показано в INSTALL.txt, и проверьте package systemd drop-in через systemctl cat kubelet. После join Node.status.addresses обеих nodes должен показывать private IP. Иначе metrics-server, API→kubelet и межузловые обращения могут пойти по неверному адресу.

В bootstrap KubeletConfiguration также сразу включён serverTLSBootstrap=true для последующего безопасного metrics пути. Это порождает serving CSR, которые администратор проверяет и одобряет по разделу capacity; они не должны автоматически подписываться вслепую. Эти постоянные настройки перед init/join отличаются от редактирования уже применённой локальной YAML-копии.
