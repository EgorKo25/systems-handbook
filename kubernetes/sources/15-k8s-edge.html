Внешний клиент, source IP, Ingress и Gateway API

Маршрут, сертификат и фактический controller образуют один контракт. Один объект Ingress или HTTPRoute не запускает прокси сам.

Как клиент входит в сеть

Внешнему клиенту нужен достижимый IP/порт: node private IP через разрешённую сеть, load balancer либо reverse proxy. Service type LoadBalancer — запрос реализации, а не встроенная покупка облака. NodePort в VM-кластере требует маршрута и firewall допуска; на Windows с kind может потребоваться port mapping engine. Для первого локального доступа достаточно port-forward с bind 127.0.0.1, но production path и policy этим не проверяются.

externalTrafficPolicy=Cluster допускает маршрутизацию на endpoints других nodes и может требовать SNAT для корректного обратного пути, скрывая исходный IP от backend. Local направляет к локальным готовым endpoints и позволяет сохранять client source IP в поддерживающем path, но node без local endpoint может не обслуживать этот Service; балансировщик должен правильно проверять health и распределение. Нельзя обещать одновременно равномерный load по всем Pods, любой node и сохранение IP без описания реализации. internalTrafficPolicy относится к внутреннему выбору и имеет отдельные последствия.

Ingress — API маршрута, controller — исполнитель

Ingress networking.k8s.io/v1 описывает HTTP(S) host/path→Service и TLS reference. IngressClass указывает предусмотренный класс controller; конкретный controller наблюдает объекты и настраивает proxy/load balancer. Без установленного подходящего controller манифест может быть принят и ничего не обслуживать. pathType Exact/Prefix/ImplementationSpecific имеет значение; annotations часто привязаны к конкретному controller и не являются переносимой Kubernetes функцией. Ingress API заморожен: он остаётся поддерживаемым, но новые сетевые возможности развиваются через Gateway API.

Исторический community ingress-nginx не следует выбирать по старому tutorial: проект объявил retirement на март 2026, дальнейшие security releases не обещаны. Это не тождественно всем продуктам с именем NGINX. Перед выбором изучите актуальный lifecycle конкретного controller и compatibility matrix, не только красивый пример YAML. В этой книге не устанавливаем устаревший controller ради одной страницы hello.

Gateway API распределяет роли

Gateway API — набор отдельно устанавливаемых CRDs и договоров реализации, не встроенный синоним Service. GatewayClass задаёт тип/реализацию, Gateway описывает listeners и инфраструктурную точку, HTTPRoute — маршруты приложения. AllowedRoutes и ReferenceGrant ограничивают attachment и меж namespace references. Существование HTTPRoute без Accepted/ResolvedRefs и готового Gateway не доказывает рабочий путь. На 01.11.2026 официальный latest Gateway API — v1.7.0; пример концептуального baseline использует stable gateway.networking.k8s.io/v1, но совместимость конкретного controller и установленного CRD bundle должна быть проверена отдельно.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: ledger
  namespace: lab
spec:
  parentRefs:
  - name: lab-gateway
    namespace: lab
  hostnames: [ledger.lab.internal]
  rules:
  - backendRefs:
    - name: ledger-api
      port: 80

Это форма маршрута к lab/lab-gateway, совпадающая по именам с поставляемым vm/gateway.yaml. Сам фрагмент Gateway не создаёт. Listener должен разрешать Routes из lab; наш полный файл разрешает только тот же namespace, а Service ledger-api тоже находится в lab. Если перенести Gateway в другую область, придётся согласованно изменить parentRef и allowedRoutes, а при ссылке на backend или сертификат из другой области — требуемый ReferenceGrant. Это разные направления разрешения, их нельзя заменить одним переименованием namespace.

В обычном режиме выбранного Envoy Gateway объекты Gateway и HTTPRoute остаются в lab, а создаваемые контроллером proxy Deployment и Service находятся в envoy-gateway-system. Namespace объекта-намерения не обязан совпадать с namespace его исполняющего прокси. Поэтому ниже proxy ищут по меткам owning-gateway-namespace и owning-gateway-name в envoy-gateway-system; NetworkPolicy разрешает трафик оттуда. Режим развёртывания proxy в namespace Gateway существует отдельно и этим набором не включается. Официальное описание: Gateway Namespace Mode, линия 1.9.

Проверка формы CRD не подтверждает существование всех ссылок: контроллер сообщает об этом через conditions. Версия API также не обещает реализации каждой экспериментальной возможности; проверяют совместимость контроллера и поддерживаемые им функции.

TLS и исходная личность

TLS termination — место завершения защищённого соединения. Сертификат должен покрывать DNS hostname, клиент должен доверять CA, private key хранится как секрет с ограниченным доступом. HTTPS client→Gateway и HTTP Gateway→Pod — разные сегменты; если нужна защита backend-сегмента, настройте поддерживаемый backend TLS/mTLS с проверкой identity, не только https в браузере. X-Forwarded-For — данные уровня HTTP от доверенного proxy, а не доказанный kernel source IP. Приложение должно доверять только известным proxies и корректно разбирать цепочку; внешний пользователь может сам прислать такой заголовок.

Проверка и стоимость входа

Проверяйте последовательно: DNS внешнего имени, TCP, TLS chain/SAN/expiry, listener route conditions, Service endpoints, HTTP body. Измеряйте handshake latency отдельно от keepalive request p95, bytes/s, active connections, queue, 4xx/5xx по причине. Retry proxy способен увеличить нагрузку на уже медленный backend; один клиентский запрос может дать несколько upstream attempts. Timeout/retry budget должен согласоваться с idempotency и временем завершения Pod. В локальном учебном стенде лишний Gateway controller может стоить больше памяти, чем весь Go-сервис; это оправдано изучением маршрутизации, но не обязательным усложнением каждого приложения.

Полный optional путь: Envoy Gateway1.9.3 на том же стенде

Выберем одну поддерживаемую реализацию: Envoy Gateway1.9.3. Официальная matrix линии 1.9 тестирует Kubernetes 1.33–1.36 и Gateway API1.6.1; EOL линии указан 14.02.2027. Поэтому не устанавливаем автоматически latest Gateway API1.7 поверх выбранного controller. Официальный install.yaml1.9.3 уже содержит согласованные Gateway API и Envoy CRDs, namespace/RBAC/config/controller/certgen. На кластере с provider-managed CRDs этот all-in-one путь не применяют: конфликт владения нужно решить по guide, а не force-conflicts. Для наших чистых kubeadm/kind CRDs ещё не было.

В release notes есть конкретное security исправление: default distroless-v1.39.5 ещё содержит недоверенные eMudhra roots; upstream предписывает Envoy Proxy distroless-v1.39.6. Поэтому наш EnvoyProxy явно задаёт 1.39.6 в той же поддерживаемой minor1.39. Это не произвольное «обновим всё latest». Control-plane controller остаётся 1.9.3, data-plane image проверяется отдельно. Скачайте install.yaml на staging, проверьте зафиксированный SHA и включите его в bundle.

curl -fL -o staged/eg-install-v1.9.3.yaml https://github.com/envoyproxy/gateway/releases/download/v1.9.3/install.yaml
printf '%s  staged/eg-install-v1.9.3.yaml
' ac89b0b564e52c97c97a3f8b4d82bb594a0fbc810431fb2e6ffd91702aabebfb | sha256sum -c -
kubectl --context "$LAB_CONTEXT" apply --server-side --field-manager=handbook-eg -f staged/eg-install-v1.9.3.yaml
kubectl --context "$LAB_CONTEXT" wait --for=condition=Established crd/gateways.gateway.networking.k8s.io --timeout=120s
kubectl --context "$LAB_CONTEXT" -n envoy-gateway-system rollout status deployment/envoy-gateway --timeout=300s
kubectl --context "$LAB_CONTEXT" apply -f vm/gateway.yaml

gateway.yaml задаёт EnvoyProxy в lab, GatewayClass с parametersRef на него, Gateway listener80 и HTTPRoute к существующему ledger-api. Сервис proxy выбран ClusterIP, поэтому не нужен MetalLB/покупка cloud LB. Внешний test выполняется локальным port-forward к proxy Service: в отличие от port-forward прямо ledger-api он проверяет Envoy HTTP routing, но всё ещё не доказывает внешний node/NAT/LB path. Если 30-policy уже изолировала backend, дополнительно примените gateway-policy.yaml: он разрешает ingress от envoy-gateway-system по 8080, иначе исправно настроенный proxy закономерно получит timeout.

kubectl --context "$LAB_CONTEXT" -n lab get gateway lab-gateway -o yaml
kubectl --context "$LAB_CONTEXT" -n lab get httproute ledger -o yaml
kubectl --context "$LAB_CONTEXT" -n envoy-gateway-system get deployment,service,pod -l gateway.envoyproxy.io/owning-gateway-namespace=lab,gateway.envoyproxy.io/owning-gateway-name=lab-gateway
# Select the actual proxy Service from the previous output:
kubectl --context "$LAB_CONTEXT" -n envoy-gateway-system port-forward service/ACTUAL_PROXY_SERVICE 18888:80 --address=127.0.0.1
# A separate client terminal:
curl -fsS -H 'Host: ledger.lab.internal' http://127.0.0.1:18888/api/hello

Проверяйте GatewayClass Accepted, Gateway Accepted/Programmed и HTTPRoute Accepted/ResolvedRefs, затем proxy Deployment image 1.39.6, endpoints и тело JSON. При пропущенном hostname Host header маршрут может не совпасть и вернуть 404, хотя backend жив. ImagePullBackOff требует offline image/auth, Accepted=false — controller/class/spec, ResolvedRefs=false — references/permissions,502/503/timeout — backend/policy/endpoints. Нельзя лечить все эти случаи рестартом Envoy.

Офлайн нужны images, упомянутые в install.yaml, и создаваемые динамически: envoyproxy/gateway:v1.9.3 для controller/certgen/shutdown-manager и docker.io/envoyproxy/envoy:distroless-v1.39.6 для dataplane. RateLimit image из конфигурации требуется лишь при включении соответствующей функции, здесь она не включена. Точный итоговый список получают в staging-кластере после materialization Gateway и проверяют на чистом offline clone; один grep image в install.yaml пропускает динамический proxy. Сохраните digests и импортируйте на каждый допустимый node. Для trusted source перечня смотрите air-gapped guide и release notes, а не случайный blog.

Память: официальный controller manifest requests256Mi/100m CPU, memory limit1024Mi; наш proxy requests128Mi/100m и limit512Mi плюс shutdown sidecar. Начальный reserve не меньше 384Mi requests и дополнительный runtime/CRD/API overhead, реальное idle/peak измеряется. На 8GiB не включайте весь набор лабораторных служб одновременно; Gateway optional и включается после базового приложения. Удаление CRDs не является обычной остановкой controller: оно удаляет API/resources и может разрушить другие routes. Сохраняйте установленную инфраструктуру между упражнениями, либо выполняйте отдельное документированное удаление после backup.
