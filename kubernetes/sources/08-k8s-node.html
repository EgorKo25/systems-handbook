От назначения Pod до Linux-процесса: kubelet, CRI и CNI

API хранит описание. На конкретном node несколько программ создают sandbox, файловую среду, cgroups и процесс; у каждой свой отказ.

kubelet не является scheduler

kubelet — node agent. Он наблюдает назначенные этому node Pods, также читает локальные static Pod manifests, согласует их исполнение и публикует status/Node conditions. Scheduler выбрал wk1, но не запустил там процесс сам. Static Pods control plane kubeadm запускаются kubelet из /etc/kubernetes/manifests; mirror Pod в API показывает их состояние, но удаление mirror-объекта не удаляет локальный manifest и не останавливает систему навсегда. Не кладите backup YAML в эту директорию: kubelet может попытаться исполнять и его.

Граница CRI и sandbox

Для нового Pod kubelet подготавливает credentials/volumes, вызывает CRI runtime service. RunPodSandbox создаёт среду Pod, включая сетевой namespace и инфраструктурную pause-задачу в обычном Linux containerd-профиле. Network namespace — отдельные interfaces/routes/ports Linux, а не обязательно отдельное ядро. Контейнеры Pod обычно разделяют Pod network namespace, поэтому localhost:8080 одного контейнера доступен соседу в том же Pod. Два контейнера, слушающие тот же адрес/порт в одном Pod, конфликтуют. PID namespace не разделяется между обычными контейнерами автоматически; shareProcessNamespace — отдельная настройка.

Runtime вызывает CNI ADD с container ID, namespace path, interface name и сетевой конфигурацией. Плагин/IPAM выделяет IP, создаёт veth (парный виртуальный Ethernet-интерфейс), routes и возвращает результат. IPAM, IP address management, — управление выдачей адресов. containerd не придумывает всю сеть сам, kube-proxy не создаёт Pod veth. Если CNI отсутствует, sandbox может не подготовиться, хотя image приложения уже лежит на диске. FailedCreatePodSandBox направляет диагностику к kubelet/runtime/CNI, а не к функции main Go.

Образ, rootfs, shim и runc

Image pull обращается к registry, получает manifest и blobs по digest, проверяет content и распаковывает filesystem snapshots. Tag — изменяемое имя, digest — идентичность конкретного содержимого manifest. Snapshotter containerd, здесь overlayfs, подготавливает rootfs из слоёв и writable layer. Затем runtime v2 shim поддерживает жизнь задачи и stdio/reaping независимо от краткоживущего вызова runc. runc использует OCI runtime specification — описание процесса, namespaces, mounts, capabilities и cgroups — для создания Linux-процесса. OCI image specification описывает другой объект: упаковку образа. Не называйте оба формата одним Dockerfile.

От контейнера к процессу ведут PID и cgroup path. От Pod к контейнеру — containerStatuses.containerID. В контейнере PID 1 относится к его PID namespace; на node у того же процесса другой PID. Mount namespace определяет видимость mounts, UTS — hostname, IPC — механизмы межпроцессного обмена, user namespace при поддержке меняет отображение UID. Эти границы не заменяют seccomp, capabilities и защиту ядра. Один hostPath или privileged может существенно разрушить ожидаемую изоляцию.

# Read-only diagnostics inside your own node VM:
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock pods
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps -a
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock inspect CONTAINER_ID
sudo ctr --namespace k8s.io images list
sudo journalctl -u kubelet --since '-10 min'
sudo journalctl -u containerd --since '-10 min'

crictl разговаривает с CRI и показывает взгляд kubelet-compatible runtime. ctr — низкоуровневый клиент containerd; обход kubelet при ручном удалении task не становится корректным Kubernetes rollout. Inspect/logs могут раскрывать environment и пути. Разделяйте ImagePullBackOff, CreateContainerConfigError, sandbox/network, runtime create и terminated exit code. Одинаковый красный Pod в интерфейсе может иметь пять разных причин.

Измеряем холодный и тёплый старт

Разделите время: очередь scheduler, pull manifest/blobs, unpack, sandbox CNI, mounts CSI, create/start process, startup/readiness probes. В «холодном» опыте образ отсутствует только в личном подготовленном node; в «тёплом» уже сохранён. Не очищайте весь /var/lib/containerd ради теста. Для image 80 MiB при фактических 20 MiB/s нижняя оценка передачи 4 s, но TLS, decompression и диск добавятся. Уменьшение Go binary может улучшить pull/unpack; оно не исправляет 30 s timeout недоступного DNS registry.
