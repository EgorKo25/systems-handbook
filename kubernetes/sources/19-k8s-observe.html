Диагностика по объекту, процессу и ресурсу

Нужны три независимых взгляда: намерение и status API, локальное исполнение node и результат запроса приложения. Метрика использования не объясняет причину сама.

Короткая лестница наблюдений

Сначала context/namespace и время, затем workload conditions/revision, Pod phase/conditions/container state, Events, logs, Service/EndpointSlice и прикладной запрос. Describe собирает удобные сведения, но не полный исторический протокол; Events могут агрегироваться и удаляться. Логи stdout/stderr node хранит и ротирует kubelet/runtime по политике; после потери node они не обязаны быть доступны. Центральный log store — отдельная система с retention и доступом, её наличие здесь не предполагается.

kubectl --context "$LAB_CONTEXT" -n lab get deployment ledger-api -o wide
kubectl --context "$LAB_CONTEXT" -n lab describe pod POD_NAME
kubectl --context "$LAB_CONTEXT" -n lab logs POD_NAME -c api --since=10m --timestamps
kubectl --context "$LAB_CONTEXT" -n lab logs POD_NAME -c api --previous --tail=100
kubectl --context "$LAB_CONTEXT" -n lab get events --sort-by=.metadata.creationTimestamp

Сравните logs без --previous и с ним: первый относится к текущему container instance, второй — к доступному предыдущему. --tail=100 ограничивает строки, --since — время. Никакой флаг не восстанавливает уже ротированный файл. --all-containers может смешать app/init/sidecar; всегда отмечайте Pod UID, container name, timestamps и timezone. Не помещайте credentials в журнал ради диагностики.

kubectl debug и scratch

Ephemeral container — добавляемый контейнер диагностики в существующем Pod через специальный subresource. Это позволяет использовать tools, которых нет в scratch image; меняет объект/среду и требует прав/admission, а image должен быть проверен и доступен offline. kubectl debug POD --image=... --target=api просит подходящий процессный target, но поддержка namespace-target зависит от runtime. Наличие debug container не гарантирует видимость всех процессов. Debug node создаёт ещё более доверенную среду с доступом к node; это администраторский рецепт, не разрешение роли investigator.

Metrics API и границы kubectl top

kubectl top pod читает resource metrics API, обычно предоставляемый metrics-server. Upstream kubeadm не устанавливает metrics-server автоматически. Top даёт недавние CPU/memory usage, не исторический p99, не дисковую latency и не бизнес-SLO. HPA с CPU utilization зависит от этих данных и requests. Prometheus и другой historical monitoring могут хранить системные/прикладные ряды; способы scrape/retention/query относятся к отдельному тому, здесь контракт: измерять конкретный ресурс и соответствующую задержку/ошибку.

OOM, throttling, eviction — разные механизмы

Memory cgroup OOM (out of memory, нехватка памяти) kill может завершить container при достижении memory limit; status lastState.terminated.reason=OOMKilled вместе с node/cgroup данными — сильная подсказка. Exit137 означает SIGKILL-подобный результат по shell convention, но сам по себе не доказывает OOM: возможна принудительная остановка. Go heap меньше RSS: stacks, runtime, mappings и kernel accounting добавляют расход. GOMEMLIMIT помогает Go управлять памятью runtime как мягким бюджетом, но не является cgroup limit и не гарантирует отсутствие OOM.

CPU throttling ограничивает доступное CPU-время при quota; процесс может оставаться живым и показывать высокий p99 из-за ожидания. Смотрите throttled seconds/periods и CPU saturation вместе с latency, а не только средний usage. Node-pressure eviction — kubelet освобождает ресурс при давлении memory/disk/PID и выбирает Pods по условиям requests/priority/usage; это не то же, что container memory OOM. QoS (quality of service, класс обслуживания) Guaranteed/Burstable/BestEffort выводятся из resource specifications и влияют на обработку давления, но не дают абсолютной гарантии не быть убитым.

Эксперимент, который различает узкое место

Начните с настоящего ответа нашего сервиса, а не с вымышленного тела 1 KiB: /api/hello возвращает короткий JSON, длина которого зависит от MESSAGE. Поставляемый http_measure.py посылает GET несколькими потоками, читает тело до конца, проверяет HTTP 200 и поле service=ledger-api, затем считает успешные ответы, ошибки, байты и задержки. Используется только стандартная библиотека Python. В каждом потоке следующий запрос начинается после окончания предыдущего; это закрытая модель нагрузки, в которой замедление сервера само уменьшает частоту отправки.

cd "$K8S_LAB_ROOT" || exit 1
python3 http_measure.py --url http://127.0.0.1:18080/api/hello --concurrency 8 --warmup 5 --seconds 10 --rounds 5 --timeout 2 --max-requests 20000

URL выше требует работающего loopback port-forward из первого запуска. Если вы выбрали другой локальный порт, измените URL. Этот путь включает клиент Python, туннель kubectl, API/kubelet и один выбранный Pod. Он полезен для знакомства с методом измерения, но не является измерением Service-балансировки или предельной производительности кластера. Не сравнивайте его число с прямым loopback Go как «накладные расходы только Kubernetes». Для проверки сетевого dataplane нужен отдельно подготовленный генератор в сети клиента, правильные NetworkPolicy и записанный маршрут до Service; BusyBox-клиенты из сетевого опыта не содержат Python.

--warmup задаёт отдельный прогрев; его результат помечен warmup и не смешивается с пятью окнами measurement. --seconds — срок начала новых запросов в окне, --max-requests — дополнительный конечный бюджет, распределённый между потоками. Последние начатые запросы могут закончиться позже окна; elapsed_seconds включает их завершение, а requests/s вычисляется по этому фактическому времени. Флаг stopped_at_request_budget показывает раннюю остановку по числу запросов. Сетевой timeout относится к операциям сокета, а не обещает жёсткий общий срок всего опыта; не запускайте этот клиент против неизвестного сервера с бесконечной медленной передачей тела.

p50, p95 и p99 вычисляются по полным успешным ответам методом ближайшего ранга: после сортировки берётся элемент с номером ceil(q × N), начиная с единицы. Например, для 100 задержек 1…100 ms получим p95 = 95 ms. Ошибки в эти квантили не входят и показаны отдельными счётчиками; ненулевой код завершения 2 либо failed больше нуля запрещают выдавать красивый p95 за успешный опыт. При отсутствии успехов квантили равны null, а не нулевой задержке. Клиент сохраняет выборку в памяти только до конца окна и выводит JSON в stdout; перенаправление в файл журнала — отдельное действие читателя.

Повторяйте опыт при одинаковых image, MESSAGE, маршруте, числе потоков и других нагрузках. Клиент сам расходует CPU и может стать ограничением; без независимого наблюдения нельзя объявлять измеренную частоту мощностью сервера. Для исследования quota сопоставьте задержку с CPU usage и throttled periods контейнера за то же окно, затем измените один limit и повторите. Этот скрипт не измеряет CPU-seconds, диски, fsync или память. Наш stateless Go не обращается к диску на запросе: объяснять его задержку придуманным fsync было бы ошибкой. Работа с реальной базой и её измерениями — отдельный опыт.

Числа нашего YAML 50m/32Mi request и 500m/128Mi limit — учебные исходные гипотезы, не результат нагрузочного измерения автора. Локальные Go tests подтверждают routes и shutdown, но не capacity кластера. Изменения ресурсов делайте после данных и учитывайте rollout: слишком высокий request может сделать новый Pod Pending, оставив старый на месте.

QoS и квантили без подмены измерения

В наших примерах используются container-level resources без Pod-level resource overrides. Для Guaranteed у всех рассматриваемых контейнеров заданы и равны requests/limits CPU и памяти; BestEffort получается без CPU/memory requests и limits; остальные такие Pod попадают в Burstable. Точное вычисление для init/sidecars и дополнительных возможностей версии сверяют по документации. Guaranteed не означает физически выделенную RAM навсегда или иммунитет к отказу node. Usage выше request — существенный вход выбора при node pressure, поэтому один label QoS не объясняет конкретный eviction без остальных условий.

p95 — 95-й процентиль измеренной выборки: примерно 95% наблюдений не больше этого значения при выбранном определении квантиля. Он не среднее и не обещание каждого будущего запроса. При 100 запросах оценка p99 определяется буквально несколькими хвостовыми наблюдениями и нестабильна. Сохраняйте число samples, окно, workload, cold/warm conditions и error count; не сравнивайте p95 успешных ответов одного опыта с общей latency другого, где timeout был исключён. SLO (service level objective, целевой уровень услуги) связывает измеренный показатель с требованием пользователя.
