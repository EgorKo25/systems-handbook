kubeconfig, сертификаты, RBAC и границы выдачи прав

Имя context помогает выбрать подключение. Реальное разрешение определяет server по удостоверенной identity и политике, а не по названию файла на ноутбуке.

Как запрос получает личность

kubeconfig содержит clusters с API endpoint/CA, users с credentials/exec plugin и contexts, связывающие их. Он может включать client private key или команду exec, которая запускает локальную программу получения token. Поэтому чужой kubeconfig нельзя считать пассивным безопасным текстом: изучите server, CA, insecure flags и exec до использования. config view --minify показывает текущую связку; --raw способен раскрыть credentials. Context rename меняет локальное имя, но не privileges на сервере.

При client certificate authentication API server проверяет CA/срок/назначение и отображает subject в username/groups по правилам. Private key подтверждает владение identity; CA private key позволяет выпускать новые доверенные credentials и требует более строгой защиты. Token authentication использует свои механизмы, например OIDC или ServiceAccount tokens. Rotation сертификатов kubelet и expiry admin/control-plane certificates — эксплуатационные задачи, а не результат смены пароля Linux.

RBAC задаёт действия над ресурсами

RBAC, Role-Based Access Control, — авторизация через роли и привязки. Role разрешает verbs над apiGroups/resources в namespace; ClusterRole задаёт повторно используемый или cluster-scoped набор. RoleBinding связывает роль с users/groups/ServiceAccounts в namespace, ClusterRoleBinding — на cluster scope. В правилах пишут resource names во множественном числе: deployments, pods/log. get одного Pod не даёт list всех, pods/log отдельно от pods/exec; exec — subresource с потенциальным доступом к данным приложения.

Правила аддитивны и обычно не содержат отрицательного deny, поэтому дополнительная широкая binding может отменить вашу идею «ограниченной роли» своим allow. Wildcards захватывают будущие ресурсы/verbs. Права bind/escalate/impersonate, создание workloads, изменение RoleBindings и чтение Secrets требуют особого внимания: они позволяют расширять доступ косвенно. Namespace administrator, способный создать privileged Pod на обычном node, может пересечь границу namespace и получить node-доверие без cluster-admin названия.

Реальная заявка с ограниченными правами

Файл 20-rbac создаёт investigator: чтение Pods/Services/Events/ReplicaSets/Deployments/EndpointSlices и logs в lab. Нет Secret, exec, patch, delete и cluster-wide Nodes. Администратор проверяет разрешения через SubjectAccessReview/имперсонацию. --as требует собственного impersonate-разрешения и не является входом обычного пользователя без credentials. Для отдельного реального клиента выпустите короткоживущий token с предназначенным audience через разрешённый процесс, положите его в приватный kubeconfig и проверьте server request; не записывайте его в опубликованный пример.

kubectl --context "$LAB_CONTEXT" -n lab apply -f manifests/20-rbac.yaml
kubectl --context "$LAB_CONTEXT" auth can-i get pods --as=system:serviceaccount:lab:investigator -n lab
kubectl --context "$LAB_CONTEXT" auth can-i get secrets --as=system:serviceaccount:lab:investigator -n lab
kubectl --context "$LAB_CONTEXT" auth can-i create pods --subresource=exec --as=system:serviceaccount:lab:investigator -n lab
kubectl --context "$LAB_CONTEXT" -n lab get pods --as=system:serviceaccount:lab:investigator

Ожидаем yes для get pods, no для secrets и pods/exec при отсутствии иных bindings. Это предсказание политики, не выполненный вывод. Проверка can-i отвечает про авторизацию конкретного запроса, не про admission и прикладной успех. Прочитать logs можно и без exec в scratch-контейнере; если нужен новый ephemeral debug container, это отдельная выдача полномочий и admission.

Secrets at rest и аудит

EncryptionConfiguration API server задаёт providers для шифрования выбранных ресурсов перед записью в etcd; KMS позволяет вынести ключевой материал в отдельную систему. Чтение через API всё равно выдаёт расшифрованные данные разрешённой identity. Нужно учитывать все API server instances, порядок providers, ключи для чтения старых записей и controlled rewrite существующих Secrets. Потеря decryption keys делает backup etcd недостаточным; ключи сохраняют защищённо отдельно с проверкой восстановления.

Audit policy определяет, какие API-события и на каком уровне сохраняются. Request/Response bodies могут содержать Secret, поэтому объём и confidentiality важнее лозунга «логировать всё». Нужны actor, verb, resource, namespace, response code, timestamp и correlation с инцидентом; retention и целостность журнала. API audit и stdout приложения отвечают на разные вопросы. Измеряйте audit disk growth и latency, иначе сама наблюдаемость может исчерпать control-plane диск.
