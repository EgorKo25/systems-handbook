API server, etcd и смысл принятого объекта

HTTP-успех означает выполнение конкретной операции API. Согласование, запуск и прикладной ответ происходят независимо и позже.

Подготовить объекты, которые будем исследовать

Эта глава начинается после приёмки kubeadm или kind: API отвечает, узлы готовы, выбран личный context. Теперь один раз выполните полный первый запуск ledger-api из сохранённого каталога labs. Рецепт собирает Linux-бинарник, объясняет доставку образа каждому допустимому узлу, создаёт namespace lab и применяет поставляемые ServiceAccount, ConfigMap, Deployment и Service. Это реальное изменение вашего кластера; синтаксические проверки книги его не выполняют.

После успешного запуска должны существовать Deployment lab/ledger-api, хотя бы один готовый Pod с меткой app=ledger-api и Service с портом 80, ведущим на порт 8080 контейнера. Через локальный туннель /api/hello возвращает JSON с service: ledger-api и сообщением из ConfigMap. Эти объекты остаются с нами дальше. Если стенд уже запущен, сначала прочтите ветвь продолжения в рецепте: повторное применение исходного файла способно вернуть настройки, которые вы сознательно меняли в упражнении.

Запрос начинается раньше YAML

kubectl apply читает YAML, преобразует в структурированные значения, определяет Group/Version/Resource и отправляет HTTPS-запрос. apiVersion задаёт представление, kind — тип объекта, metadata.name — имя в области ресурса. Для Deployment ledger-api путь включает /apis/apps/v1/namespaces/lab/deployments/ledger-api. Group apps группирует API; namespaced resource и cluster-scoped Node имеют разные URL и права. GVK, Group Version Kind, — идентификатор формы, GVR, Group Version Resource, — маршрутизируемая коллекция.

Webhook — отдельный HTTPS-обработчик, к которому API server обращается в предусмотренной точке admission. Он получает описание запрашиваемого действия и возвращает решение, а mutating webhook может также предложить изменение объекта. Вызов webhook добавляет ещё одно соединение, задержку и возможный отказ; код приложения ledger-api на этом этапе ещё не запускается. Политика failurePolicy: Fail требует отклонить запрос, когда соответствующий вызов webhook не выполнен, а не считать отсутствие ответа разрешением.

API server проверяет TLS/аутентификацию, устанавливает username/groups, выполняет авторизацию операции и admission, то есть предусмотренную политику допуска/изменения объекта. Authentication, установление личности, не равно RBAC-разрешению. Для mutating-запроса decoding/conversion/defaulting, mutating admission и validating admission/validation образуют pipeline; точные внутренние точки зависят от вида запроса и resource strategy. Не считайте их одной общей shell-командой. Mutating webhook может добавить поля, validating webhook может отказать, недоступный webhook с Fail может остановить изменения. Поэтому схема API→etcd намеренно не обещает один сетевой запрос и универсальный порядок всех внутренних функций.

Schema, defaulting и storage version

Schema — описание допустимой структуры/типов полей; validation проверяет структурные и смысловые ограничения. Defaulting добавляет предусмотренные значения отсутствующих полей. Строка "80" в Service.port не становится автоматически числом 80 только от знакомого смысла. kubectl explain deployment.spec.template показывает серверную схему; локальный YAML parser знает лишь синтаксис. Сохранённый объект может иметь defaulted поля, admission mutations, UID, timestamps, resourceVersion и managedFields, которых не было во входном файле.

Storage version — версия представления, в которой API server хранит данный вид ресурса; запросить объект можно в другой обслуживаемой версии через conversion. Для встроенных ресурсов это внутренняя реализация API server, для CRD важны served/storage версии и conversion webhook. CRD, CustomResourceDefinition, регистрирует новый API-тип; установка CRD не запускает контроллер и не обеспечивает его семантику. Перед удалением обслуживаемой версии надо обновить клиентов и сохранённые объекты по supported migration path. Смена apiVersion в одном локальном YAML не переписывает всё хранилище.

Идентичность и конкурентная запись

UID — уникальная идентичность экземпляра объекта. Удалённый и созданный заново Pod с тем же name имеет новый UID; ссылки владельца и контроль удаления должны различать их. resourceVersion — непрозрачный маркер версии состояния, предназначенный для concurrency/watch, а не число секунд, глобальный счётчик бизнес-событий или пригодное для арифметики поле. PUT с устаревшим resourceVersion обычно получает 409 Conflict: другой клиент уже изменил объект. Клиент перечитывает, заново вычисляет изменение и повторяет, не перезаписывает чужую работу вслепую. generation отражает изменения желаемой спецификации для поддерживающих ресурсов; observedGeneration в status показывает, какую generation обработал контроллер.

etcd и quorum

etcd — распределённое согласованное key-value хранилище. API server сериализует ресурсы и выполняет операции с ним; обычный controller не пишет напрямую в etcd. Raft — протокол согласования журнала между членами etcd. Quorum, большинство, для N членов равен floor(N/2)+1. Три члена допускают потерю одного, пять — двух; два всё ещё требуют два и не дают выигрыша доступности над одним. Лидер подтверждает запись после предусмотренного согласования большинства; медленный fsync/сеть влияют на задержку записи и выборы лидера. Больше членов может ухудшать latency, а копии на одном диске не дают независимости отказов.

Один cp1 содержит один etcd: нет quorum-запаса. API server может обслуживать чтение из cache в предусмотренных режимах, но отсутствие достаточного etcd не делает кластер надёжно изменяемым. Уже запущенные контейнеры не обязаны остановиться от потери API; новые назначения и восстановление контроллерами будут недоступны. Не редактируйте etcd ключи руками: обойдёте validation, ownership и версии. Backup etcd нужен для управляющего состояния, application backup — для байтов в PVC и внешних системах.

kubectl --context "$LAB_CONTEXT" -n lab get deployment ledger-api -o yaml
kubectl --context "$LAB_CONTEXT" -n lab get pod -l app=ledger-api -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.metadata.uid}{" "}{.metadata.resourceVersion}{"\n"}{end}'
kubectl --context "$LAB_CONTEXT" explain deployment.spec.template.spec.containers

Снимите UID и resourceVersion до и после rollout. Новый ReplicaSet/Pod и новый process PID — три разные идентичности. Вывод YAML может содержать credentials и environment, поэтому сохраняйте только осмысленный диагностический фрагмент. API latency измеряют отдельно от времени rollout status: первый отражает принятие/чтение, второй включает scheduler, images, process и probes.

Один optimistic-concurrency конфликт, разобранный до ответа

На отдельном ConfigMap concurrency-demo клиент A прочитал data.mode=blue и opaque resourceVersion R1. Клиент B прочитал тот же R1, записал mode=green и получил новую версию R2. Если A отправит PUT с R1 и новым data.note, server не может предположить, что A видел green: ответ 409 Conflict защищает последнюю запись. Это не обязательно RBAC403 или schema422. HTTP-форма ниже — условный разбор протокола, буквы R1/R2 не настоящие numeric resourceVersions и не готовый curl token.

A: GET /api/v1/namespaces/lab/configmaps/concurrency-demo
   <- 200 {metadata:{name:"concurrency-demo",resourceVersion:"R1"},data:{mode:"blue"}}
B: PUT same URL, resourceVersion="R1", data.mode="green"
   <- 200, resourceVersion="R2"
A: PUT same URL, resourceVersion="R1", data.note="checked"
   <- 409 Conflict, Status.reason="Conflict"
A: GET same URL -> R2, recompute intent while preserving mode="green"
A: PUT with current resourceVersion and recomputed fields -> success if no new writer

Практический опыт выполняется на отдельном ConfigMap, чтобы не затронуть конфигурацию приложения. Ниже функция Bash создаёт только новый lab/concurrency-demo и отдельный каталог доказательств. Если объект уже есть после прошлого опыта, create откажет: сначала прочтите его текущее значение и старый журнал, затем либо продолжайте разбор, либо осознанно удалите только этот учебный ConfigMap. Namespace и приложение не пересоздают.

concurrency_demo() {
  : "${LAB_CONTEXT:?Сначала выберите context личного стенда}"
  : "${K8S_LAB_ROOT:?Сначала задайте путь к сохранённым файлам}"
  cd "$K8S_LAB_ROOT" || return 1
  mkdir -p evidence || return 1
  local work
  work=$(mktemp -d "$K8S_LAB_ROOT/evidence/concurrency.XXXXXXXX") || return 1
  kubectl --context "$LAB_CONTEXT" -n lab create configmap concurrency-demo --from-literal=mode=blue || return 1
  kubectl --context "$LAB_CONTEXT" -n lab get configmap concurrency-demo -o json > "$work/a.json" || return 1
  kubectl --context "$LAB_CONTEXT" -n lab patch configmap concurrency-demo --type=merge -p '{"data":{"mode":"green"}}' || return 1
  printf 'Старая полная версия: %s\n' "$work/a.json"
  if kubectl --context "$LAB_CONTEXT" -n lab replace -f "$work/a.json"; then
    printf 'Неожиданный успех: остановитесь и проверьте, менялся ли объект.\n' >&2
    return 1
  fi
  printf 'Прочтите отказ: нужен Conflict из-за устаревшей версии, а не любая ошибка.\n'
  kubectl --context "$LAB_CONTEXT" -n lab get configmap concurrency-demo -o yaml || return 1
}
concurrency_demo

В a.json осталось значение blue и старая metadata.resourceVersion; patch сохранил green и новую версию. Replace посылает прежний снимок целиком, поэтому сервер должен отклонить его как устаревший. Forbidden означает отсутствие прав, NotFound — другое имя или отсутствие объекта, ошибка проверки структуры — неверную форму. Ни один из этих отказов не доказывает проверку конкурентной записи. Файл и текущий объект сохраняются для сравнения.

После подтверждённого конфликта перечитайте объект и заново вычислите своё изменение. Если намерение — добавить note=checked, не меняя mode, узкий merge patch kubectl --context "$LAB_CONTEXT" -n lab patch configmap concurrency-demo --type=merge -p '{"data":{"note":"checked"}}' сохранит green при отсутствии другого писателя этого ключа. Для изменения, зависящего от прочитанного значения, нужен повтор read → проверка условия → update с текущей версией; при новом конфликте повтор ограничивают числом попыток и задержкой. Разные объекты Kubernetes не образуют общей транзакции приложения.

Ответ success содержит server object, а не обещание Pod: после 200 Deployment change контроллер ещё только увидит generation. Временная линия принятия хранится отдельно от линии observedGeneration/PodScheduled/containerStarted/Ready. Так можно объяснить пользователю «изменение сохранено, доставка ещё ждёт registry» без ложного утверждения о работающем процессе.
