Адреса Pod и Service, EndpointSlice и DNS-имена

Pod IP указывает сетевую среду экземпляра, Service IP — виртуальную точку выбора endpoint. DNS лишь сообщает адрес и не пересылает HTTP сам.

Три пространства адресов

Node IP нужен для связи machines и control plane. Pod IP назначается сетевой реализацией внутри PodCIDR/pool и относится к текущему Pod. Service ClusterIP берётся из ServiceCIDR и обычно не назначен реальному интерфейсу приложения в iptables-модели. Kubernetes network model требует соответствующей связи Pod→Pod и node→Pod, но CNI выбирает routing/overlay и особенности реализации. Нельзя вывести физический маршрут только из API YAML.

В нашем VM-профиле node private IP 192.168.56.10/.11, Calico pool 10.244/16, ServiceCIDR 10.96/16, single-stack IPv4. У kind свои defaults, и он не наследует эти маршруты из главы о VM. На node изучите ip route и адреса Calico interfaces; внутри Pod — его eth0/default route. IP одного Pod после удаления не является постоянным адресом службы. Клиент, кеширующий этот IP бесконечно, обойдёт lifecycle Service и будет обращаться к несуществующему либо другому объекту.

Service описывает выбор, EndpointSlice — адреса

Service selector app=ledger-api выбирает Pods по labels. Контроллер EndpointSlice публикует адреса/порты/conditions выбранных endpoints с разбиением на slices. kube-proxy наблюдает Service и EndpointSlice, программирует dataplane. Сам HTTP-запрос не идёт через API server или процесс kube-proxy в нормальном iptables-пути. EndpointSlice discovery.k8s.io/v1 — основной API endpoint-наборов; старый Endpoints deprecated с Kubernetes 1.33, его ограничения и отсечение больших наборов не следует использовать как нормальную модель масштабирования.

Service.port=80 — порт виртуального Service, targetPort=http ссылается на именованный container port 8080. containerPort лишь описывает порт; он не заставляет Go слушать и не открывает firewall. Пустой EndpointSlice может означать несовпадение selector/labels; addresses с ready=false — проблему готовности; правильные endpoints с timeout — вопрос пакета/policy/listener. Service без selector допустим для ручных endpoints, но автоматического выбора Pods тогда нет.

kubectl --context "$LAB_CONTEXT" -n lab get service ledger-api -o wide
kubectl --context "$LAB_CONTEXT" -n lab get endpointslice -l kubernetes.io/service-name=ledger-api -o yaml
kubectl --context "$LAB_CONTEXT" -n lab get pod -l app=ledger-api --show-labels -o wide

Тип Service и headless

ClusterIP предназначен для внутренней виртуальной точки. NodePort дополнительно задаёт порт на допустимых адресах nodes; в VM-кластере это не готовый интернет load balancer. LoadBalancer просит поддерживающую реализацию предоставить внешний балансировщик; на bare-metal без controller внешний IP может оставаться Pending. ExternalName возвращает DNS CNAME к внешнему имени и не создаёт TCP-прокси/health check. Headless Service с clusterIP=None возвращает адреса endpoints для discovery; клиент сам выбирает и балансирует соединения. Долгоживущий TCP не перебалансируется на каждый HTTP-запрос только потому, что replicas выросли.

DNS-запрос до HTTP

CoreDNS обслуживает кластерные имена, например ledger-api.lab.svc.cluster.local. kubelet формирует resolv.conf Pod по dnsPolicy/dnsConfig, включая search domains и ndots. Короткое ledger-api из namespace lab разрешается иначе, чем из helm-lab; полное имя явно задаёт область. DNS возвращает ClusterIP, затем клиент открывает TCP к нему. NXDOMAIN, timeout DNS и TCP connection refused — разные результаты. При большом ndots внешнее имя без завершающей точки может вызвать дополнительные search-запросы; снижать ndots нужно после измерения запросов и понимания имён, а не как универсальный tuning.

В поставляемом diagnostic.yaml используется закреплённый BusyBox: в нём есть nslookup, wget, cat и sh; наличие dig и curl этот образ не обещает. Полный опыт из следующей главы сравнивает DNS, прямой IP и HTTP именно этими средствами. Для других инструментов заранее выберите и доставьте другой проверенный образ, а затем запишите его точную ссылку. Scratch-образ Go не содержит даже shell: отказ exec … -- sh в нём объясняется отсутствием файла программы.

Измеряйте задержку DNS, долю ответов из кэша, NXDOMAIN и тайм-ауты отдельно от HTTP. Увеличение числа Pods приложения не исправляет недоступный DNS Service. Внешний рекурсивный DNS и кластерный модуль CoreDNS отвечают за разные имена и участки запроса.
