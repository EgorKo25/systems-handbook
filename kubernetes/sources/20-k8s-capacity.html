Доступность, PDB, drain и масштабирование без магических чисел

HA приложения, HA control plane и защита данных — три разных бюджета. Число replicas полезно только вместе с местом, отказами и нагрузкой.

Измеряем потребность, считаем резерв

Пусть один экземпляр при целевой нагрузке устойчиво обслуживает 100 запросов/s с p95≤100ms, потребляя 0.4 CPU и 70Mi working set в заданном опыте. Ожидаемый пик 160 запросов/s требует минимум ceil(160/100)=2 экземпляра по пропускной способности. Чтобы выдержать потерю одного при том же пике, нужно минимум 3 с достаточным распределением и запасом остальных ресурсов. Это условная арифметика, а не характеристика ledger-api: фактическое q измеряют с нужными payload/errors/dependencies. При нелинейной БД-зависимости 3×q не обязано получиться.

Теперь считаем node: два worker с allocatable 1.5 CPU/2GiB каждый. Три app replicas requests0.5CPU/128Mi суммарно требуют 1.5CPU/384Mi, но после потери одного worker оставшийся должен разместить все три плюс CNI/system Pods и surge. Если после резервов доступно 1.2CPU, N+1 не выполняется. Номинальные 2vCPU VM не равны allocatable. Нельзя доказывать failover только общей суммой ресурсов без placement/volume topology/taints. На одном worker можно исследовать process recovery, но не node failure availability.

PDB и добровольное обслуживание

PodDisruptionBudget, PDB, ограничивает добровольные disruptions через eviction API для выбранного набора Pods: minAvailable или maxUnavailable. Он не предотвращает падение VM, kernel OOM, прямое delete Pod и не является счётчиком SLA. Наш 40-availability задаёт maxUnavailable1; при одном replica это допускает его добровольную остановку и честно не обещает availability. Для двух готовых replicas и minAvailable1 разрешён один disruption при условиях контроллера. Неготовые Pods и policy unhealthyPodEvictionPolicy влияют на drain, поэтому PDB может осмысленно блокировать обслуживание.

kubectl --context "$LAB_CONTEXT" cordon wk1
kubectl --context "$LAB_CONTEXT" drain wk1 --ignore-daemonsets --timeout=180s
# After maintenance and actual node readiness:
kubectl --context "$LAB_CONTEXT" uncordon wk1

Cordon запрещает новые обычные назначения на node, не выселяет существующие. Drain пытается эвакуировать Pods, учитывает ограничения, не управляет static mirror Pods как обычными, требует решения о DaemonSet и локальных данных. --ignore-daemonsets разрешает процедуре продолжить при DaemonSet Pods, а не удаляет сам DaemonSet навсегда. Не добавляйте --delete-emptydir-data или --force автоматически: первый разрешает потерю local emptyDir data, второй меняет условия unmanaged Pods и не является ответом на PDB. Если один worker и local PV, drain закономерно оставляет приложение без места; сначала подготовьте другой допустимый capacity/storage.

HPA, VPA и node autoscaling

HorizontalPodAutoscaler, HPA, меняет scale target replicas по метрикам. Для CPU utilization базовая мысль — текущие replicas×current/target с допусками, readiness/отсутствующими данными, stabilization и policies; это управляющий цикл, не мгновенная формула каждого запроса. При request 50m и averageUtilization70% целевой usage около 35m на Pod, а не 70% физического node. Неправильный request меняет знаменатель и решение. HPA autoscaling/v2 требует доступных metrics APIs и не создаёт node, когда новые replicas Pending.

Vertical Pod Autoscaler, VPA, — отдельный компонент рекомендаций/изменения resources с собственной совместимостью и режимами; не встроенная подкоманда kubeadm. Он может менять requests и приводить к пересозданию по своему режимму. Одновременный HPA CPU utilization и VPA CPU requests меняют numerator/denominator и требуют осмысленной настройки. Node autoscaler управляет числом машин через конкретный infrastructure provider; kubeadm в двух личных VM сам не покупает и не создаёт третью. Autoscaling имеет пределы quotas, availability и времени bootstrap, поэтому запас нужен до реакции.

HA control plane отдельно

HA control plane требует нескольких API server, load-balanced endpoint, согласованного etcd quorum, доступных scheduler/controller leaders и сертификатов/сети. Три API server с одним etcd не устраняют single point datastore. Три etcd члена в одной физической машине переживут отказ процесса, но не её питание/диск. Availability приложения зависит от workers, network edge, DNS, storage и внешних dependencies. После потери control plane работающий HTTP может продолжаться, но новый rollout/перепланирование не гарантированы.

Цена kube-system idle CPU/RAM, дисков, upgrades, on-call и backups должна быть видна рядом с ценой приложения. Для одного stateless Go-процесса с небольшим потоком systemd и reverse proxy могут дать меньше отказных переходов. Доказательство выбирается экспериментом: одинаковая нагрузка, измеренный recovery, задачи policy/team scale и стоимость обслуживания в часах. Kubernetes нужен, когда эти возможности дают выгоду, а не когда YAML умещается в README.

Полный optional путь HPA: metrics-server 0.9.1

Выбран metrics-server 0.9.1, matrix0.9.x поддерживает Kubernetes 1.34+, API metrics.k8s.io/v1beta1. Он собирает resource metrics с kubelets для autoscaling, не заменяет исторический мониторинг. Требуются API aggregation layer, kubelet webhook authentication/authorization и проверяемые serving certificates. В kubeadm aggregation обычно подготовлена, но это проверяют по APIService и kube-apiserver flags; не отключайте TLS из-за первого x509 error.

В личной VM для доверенного kubelet serving cert включите serverTLSBootstrap: true в KubeletConfiguration и примените через предусмотренную node-конфигурацию/restart kubelet. Каждый node запросит CSR signerName=kubernetes.io/kubelet-serving. Встроенные controllers не обязаны автоматически approve такой serving CSR. Администратор читает CSR, проверяет username system:node:имя, groups, DNS/IP SAN из реальной node identity и possession/назначение, затем approve только конкретного проверенного CSR. Не одобряйте все Pending пачкой. Сертификат должен покрывать адрес, который metrics-server выберет по preferred-address-types.

kubectl --context "$LAB_CONTEXT" get csr
kubectl --context "$LAB_CONTEXT" get csr CSR_NAME -o yaml
kubectl --context "$LAB_CONTEXT" get csr CSR_NAME -o jsonpath='{.spec.request}' | base64 -d | openssl req -noout -text
# Only after checking signer, requester, SANs and node identity:
kubectl --context "$LAB_CONTEXT" certificate approve CSR_NAME

Проверка CSR — security-sensitive административный шаг, не формальность. При kind self-signed kubelet cert без такой настройки secure путь также нужно подготовить; популярный --kubelet-insecure-tls выключает authentication сервера и не включён в наш основной рецепт. Если выбрали временное исключение в изолированном disposable kind опыте, оно должно быть явно помечено как ослабление, а не стандартная установка. Для kubeadm VM сохраняем доверенный сертификат.

curl -fL -o staged/metrics-server-v0.9.1.yaml https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.9.1/components.yaml
printf '%s  staged/metrics-server-v0.9.1.yaml
' 3c7f57cdbee0f57fb0259a150e8f6d6cb4f29d72d1aa5dce8803151dd6d4c2a1 | sha256sum -c -
kubectl --context "$LAB_CONTEXT" apply -f staged/metrics-server-v0.9.1.yaml
kubectl --context "$LAB_CONTEXT" -n kube-system rollout status deployment/metrics-server --timeout=180s
kubectl --context "$LAB_CONTEXT" get apiservice v1beta1.metrics.k8s.io -o yaml
kubectl --context "$LAB_CONTEXT" get --raw='/apis/metrics.k8s.io/v1beta1/nodes'
kubectl --context "$LAB_CONTEXT" -n lab top pods
kubectl --context "$LAB_CONTEXT" -n lab apply -f manifests/40-availability.yaml
kubectl --context "$LAB_CONTEXT" -n lab describe hpa ledger-api

Офлайн image registry.k8s.io/metrics-server/metrics-server:v0.9.1 сохраняется с digest и импортируется в nodes; manifest/CA/CSR-процедура входят в inventory. Официальные requests100m CPU/200Mi RAM добавляются к capacity до установки. HPA controller обращается к kube-apiserver /apis/metrics.k8s.io, затем aggregation layer kube-apiserver направляет запрос через Service к metrics-server PodIP:10250. Отдельно metrics-server собирает samples с каждого kubelet по выбранному NodeIP:10250. Это разные акторы, направления и TLS-границы. APIService Available=false с FailedDiscoveryCheck указывает на aggregation/service/endpoints/TLS; logs x509 — на kubelet trust/SAN; timeout — на route/firewall; Forbidden — webhook authorization/RBAC. Не лечите 403 флагом insecure-tls: он относится к другому слою.

После успешной выдачи samples HPA conditions ScalingActive/AbleToScale и current/desired metrics объясняют решение. Missing metrics временно дают <unknown>; отсутствие CPU request делает utilization неприменимым для нужных контейнеров. Задайте небольшой контролируемый поток к приложению, снимите usage/request, desiredReplicas, actualReady и latency по времени. Не нагружайте общий host бесконечным busy loop. На завершении опыта удалите только HPA, если возвращаетесь к ручному replicas, и восстановите desired через исходный manifest; PDB имеет отдельный lifecycle и не обязан удаляться вместе.

Если кластер уже создан без serverTLSBootstrap

Фикстура нового baseline уже содержит serverTLSBootstrap=true. Для ранее созданного kubeadm-кластера одной правки vm/kubeadm.yaml и restart недостаточно: это файл bootstrap intent, а не автоматически читаемая текущим kubelet конфигурация. Сохраните копию и отредактируйте kube-system ConfigMap kubelet-config: в значении data.kubelet, которое само является YAML KubeletConfiguration, установите serverTLSBootstrap: true. Затем на КАЖДОМ личном node сохраните и измените /var/lib/kubelet/config.yaml тем же полем, проверьте systemctl cat kubelet на фактический --config path и перезапустите kubelet. Общий ConfigMap нужен для будущих join/upgrade, local file — для текущего процесса. После этого исследуйте конкретные CSR, SAN/identity и approve по процедуре выше. Rotation serving certificates тоже требует процесса одобрения с проверкой, а не забывается после первой установки.

Две TLS-проверки: upstream aggregation default не усиливается от CSR kubelet

Точный официальный components.yaml metrics-server0.9.1 содержит APIService.spec.insecureSkipTLSVerify=true. Это значит, что в этом поставляемом профиле aggregation kube-apiserver→metrics-server не проверяет serving certificate по CA. Наше включение serverTLSBootstrap и approval kubelet-serving CSR относится к другому участку: metrics-server→kubelet. Оно не закрывает доверие к агрегируемому API. Authentication front-proxy/delegated authorization и TLS certificate verification — также разные механизмы; успешный RBAC не заменяет проверку server identity.

Для базового опыта надо честно зафиксировать upstream default. Для усиления дан законченный optional METRICS-TLS.txt: приватная CA, leaf с Service DNS SAN/serverAuth, локальная openssl verify, Secret, read-only mount и явные --tls-cert-file/--tls-private-key-file, затем APIService caBundle этой CA и insecureSkipTLSVerify=false. metrics_tls_patch.py офлайн готовит узкие manifests из exact upstream SHA; он не применяет их и не содержит private keys. Сначала готовится новый listener и проверяется rollout, затем усиливается доверие агрегатора, затем проверяются APIService Available и настоящие samples. Для следующего upgrade сохраняйте это изменение: повторный apply исходного upstream manifest может вернуть insecure default.

Hardening recipe и выпущенные читателем сертификаты автором не исполнялись; остаются требования к самостоятельной приёмке и renewal. Здесь не утверждается, что оба TLS-сегмента уже защищены только от выполнения базового HPA-рецепта. Секреты/CA private key не входят в публикуемую лабораторию.
