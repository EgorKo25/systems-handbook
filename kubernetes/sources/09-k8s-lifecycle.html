Pod lifecycle, probes, sidecars и завершение Go-сервиса

Состояние Running слабее готовности, перезапуск контейнера отличается от замены Pod, а rollback спецификации не отменяет сделанные запросы.

Фазы, состояния и restart

Pod phase Pending/Running/Succeeded/Failed/Unknown — грубая сводка, не полный state machine всех процессов. У каждого container state Waiting/Running/Terminated есть reason, exit code и timestamps; Pod conditions показывают отдельные признаки PodScheduled, Initialized, ContainersReady, Ready и предусмотренные readiness gates. Running допускает контейнер, который стартует, перезапускается или не готов. CrashLoopBackOff — отображаемая причина задержки повторных стартов, а не отдельная Pod phase.

restartPolicy на обычном Pod задаёт Always/OnFailure/Never для соответствующих контейнеров. Deployment использует Always; Job — Never или OnFailure по своей семантике. kubelet может перезапустить контейнер в том же Pod UID и сетевой среде, увеличив restartCount. Если VM потеряна, controller создаёт другой Pod на другом допустимом node: старый UID не переносится. Путь writable layer контейнера и emptyDir имеют разные сроки: emptyDir переживает рестарт контейнера внутри живого Pod, но не удаление самого Pod. PersistentVolume существует по отдельному lifecycle.

Startup, readiness и liveness задают разные вопросы

Startup probe даёт программе время первоначально стать работоспособной и блокирует liveness/readiness до своего успеха. Liveness — свидетельство, что контейнеру нужен перезапуск при систематическом отказе выбранной проверки. Readiness — готовность получать трафик данного Service; отрицательная readiness обычно исключает endpoint из готовых, но сама не перезапускает контейнер. Если API зависимости временно недоступен, liveness, зависящий от него, может устроить restart storm без пользы. Readiness проверяет только необходимые для обещанной операции зависимости, иначе частичный сбой выключит весь сервис.

Наш Go /livez возвращает 200, пока handler может исполняться; /readyz управляется готовностью приложения. Это учебный stateless сервис без внешней БД. HTTP 200 не доказывает отсутствие deadlock в другой goroutine или корректность бизнес-данных. Порог startup 30×2s в YAML — приблизительный бюджет числа неудач с периодом, а не точная гарантия запуска ровно через 60s; scheduling/timeout и фазирование влияют на время. failureThreshold и periodSeconds должны быть выведены из измеренного распределения старта и допустимого recovery, не скопированы как универсальные числа.

Именованный порт http в каждой проверке разрешается в containerPort: 8080. Указание containerPort само не создаёт listener: его открывает Go через net.Listen. Поле timeoutSeconds не задано, поэтому сервер добавляет стандартное значение 1 секунда. В общем случае HTTP-коды от 200 до 399 считаются успехом такой проверки; наши обработчики возвращают 200 либо, у выключенной readiness, 503. Probe проверяет ответ узлу, а не внешний путь клиента через DNS и Gateway.

В опыте с неверным /missing-readyz Go отвечает 404 только readiness. У нового Pod можно одновременно увидеть Running, успешную liveness, нулевой restartCount и Ready=false. Если заменить также liveness на неверный путь, появится другой механизм — рестарт после порога ошибок. Сравнивайте timestamp начала контейнера, restartCount и UID Pod: эти поля покажут, какой именно переход произошёл.

Init и restartable sidecar в выбранной линии

Обычные initContainers выполняются до application containers последовательно и должны завершиться успешно. Они удобны для короткой подготовки файла/проверки, но бесконечное ожидание внешней БД может удерживать Pod в Init без видимого процесса приложения. Native sidecar определяется как initContainer с restartPolicy: Always; эта возможность stable с Kubernetes 1.33 и действует в 1.36. Такой контейнер может продолжать работать после инициализации и участвует в определённом порядке запуска/остановки и учёте ресурсов. Это отличается от «просто второго обычного container».

Не вычисляйте request Pod простым сложением всех init и main: Kubernetes учитывает последовательные init, перекрывающиеся restartable sidecars, overhead и поддерживаемые resource semantics. Сначала посмотрите итоговый объект и документацию версии. Sidecar log-agent нужен лишь при наличии подтверждённой задачи: kubelet уже собирает stdout/stderr контейнеров. Ещё один контейнер добавляет память, images, startup и доверие, даже если его конфигурация занимает три строки.

SIGTERM, endpoint и grace period

Удаление устанавливает deletionTimestamp и запускает завершение. Kubelet выполняет preStop, если он предусмотрен и применим, затем посылает stop signal процессу; по окончании grace period оставшиеся процессы принудительно убиваются. preStop расходует тот же общий бюджет, поэтому sleep 20 при grace 15 не создаёт ещё 20 секунд. EndpointSlice отмечает terminating endpoint и readiness меняется по правилам; распространение до всех dataplanes и внешних load balancers не мгновенно. Удаление Pod и прекращение всех клиентских соединений — разные события.

Go-бинарник запускается напрямую как ENTRYPOINT, получает SIGTERM через signal.NotifyContext, снимает внутреннюю readiness и вызывает http.Server.Shutdown с бюджетом 8s; YAML даёт 15s grace. Shutdown закрывает listeners и ожидает активные запросы, но не откатывает уже записанные данные и не ждёт бесконечные hijacked/WebSocket соединения автоматически. Здесь нет preStop: мы не маскируем механикой sleep неопределённый внешний drain. Для настоящих долгих операций измерьте длительность, ограничьте deadline, обеспечьте idempotency и согласуйте максимальное время запроса с grace.

kubectl --context "$LAB_CONTEXT" -n lab get pod -l app=ledger-api -w
kubectl --context "$LAB_CONTEXT" -n lab logs POD_NAME -c api --previous
kubectl --context "$LAB_CONTEXT" -n lab rollout restart deployment/ledger-api
kubectl --context "$LAB_CONTEXT" -n lab rollout status deployment/ledger-api --timeout=120s

Previous читает доступный журнал предыдущего экземпляра контейнера, а не все версии приложения за месяц. Rollout restart меняет Pod template annotation и вызывает замену Pods, даже если image tag прежний; данные/внешние операции от этого не возвращаются. Сравните UID, restartCount и ReplicaSet до/после: рестарт контейнера и rollout дают различную картину.
