ЛИЧНЫЙ АДМИНИСТРАТОРСКИЙ СТЕНД
Подготовка 1 ноября 2026. Никаких установок или изменений рабочей сети не выполнено.

Идея: продолжаем один мир, а не начинаем каждую главу с пустого терминала.
В знакомой сети появляется Linux-сервер, свой Go-сервис, PostgreSQL, кэш,
доставка через Git/Jenkins и измерения. Можно сломать копию и вернуться
к выключенной контрольной точке. Код и рецепты здесь, личные данные отдельно.

Выбранная основа
----------------
Один Linux-гость QEMU, внутри него Docker Engine/Compose и инструменты.
С Ubuntu он запускается с KVM, если доступно ускорение. На разрешённом
Windows тот же закрытый диск пробуем через QEMU/TCG, без установки Docker
на рабочий ПК. Контейнеры делят ядро гостя, поэтому экономнее группы VM.
Для загрузчика, ядра, разных ОС и настоящей границы машин дополнительные
VM подключаем по одному упражнению, не держим все роли включёнными.

Это подготовленный код и программа приёмки, пока не готовая скачанная VM.
Контроллер не устанавливает QEMU/Packet Tracer. Реальный seed испытывается
отдельно; fake API тесты не выдают его за готовый пользовательский образ.
Измерен доступный домашний ресурс; бюджеты учебных профилей ещё оценочные.
Начальная VM: 1 GiB/1 vCPU/20 GiB; профиль Docker: 3 GiB/2 vCPU/40 GiB.
Точный расход проверим на реальной ОС и выбранных контейнерах.

Два разных сетевых инструмента
-----------------------------
Packet Tracer — наглядная модель устройств Cisco. Сохраняемый .pkt содержит
топологию и настройки, его переносим между установленными версиями PT.
Первый рецепт: два 2911, три 2960, VLAN, запасная L2-линия с STP, два
маршрута OSPF, DHCP/DNS, NAT и ACL. Все CLI-конфиги подготовлены, но пока
не прогнаны в самом PT. Не выдаём .txt за бинарный .pkt.

Linux-netlab — настоящие ip/tcpdump/nft в отдельных network namespaces
внутри одной VM. У каждого свой сетевой стек, общее ядро. Здесь проверяем,
как реальная ОС принимает/маршрутизирует пакеты и как к ней привязана
прикладная служба. Это не Cisco IOS, команды отличаются. Повторение одной
задачи позволяет увидеть общее понятие за разными конфигурациями.

Путь изучения инструментов
-------------------------
1. Packet Tracer: сначала предсказываем пакет и объясняем настройки.
2. Linux namespaces + tcpdump: повторяем тот же случай в настоящем ядре.
3. GNS3 либо EVE-NG: отдельный последующий профиль с настоящими образами
   сетевых ОС, если доступны лицензии и ресурсы. Эти образы здесь не лежат.
4. containerlab: настоящие контейнерные сетевые ОС/сервисы в Linux-госте,
   когда уже понятны topology, интерфейс, маршрутизация и lifecycle.
Wireshark/tcpdump — средства наблюдения в каждом подходящем опыте,
а не ещё один заменитель маршрутизатора. Пока не устанавливаем все GUI
одновременно: способность объяснить ARP, маршрут и фильтр важнее меню.

Что объединяем по главам
-----------------------
Сети + Linux + Bash: маршрут, namespace, реальный сокет, процесс сервера,
файловые дескрипторы, захват, pipeline обработки логов и exit status.
Git + Bash: конфиги и скрипты в личном repo, фиксация исходного состояния,
дифф после поломки, повторяемое применение, rollback.
Go + Linux: свой HTTP-сервис, build/link/debug, systemd, CPU/RAM/GC,
разница холодной сборки, прогрева и рабочего запроса.
PostgreSQL + сеть + Linux: Unix socket/TCP, роль, pg_hba, права каталога,
WAL/копии, ввод-вывод, locks, EXPLAIN и наблюдение.
Кэш + Go + PostgreSQL: один запрос до/после, hit rate, stale data,
вытеснение, invalidation и выигрыш под одинаковой нагрузкой.
Jenkins + Git + Go: автоматизируем уже понятную ручную сборку и доставку,
отдельно credentials, agents, артефакт, плохой выпуск и возврат.
Реплики/кластер: только после измерения исходного сервиса; больше машин
нужно обосновать доступностью/нагрузкой, а не количеством красивых узлов.
Полная карта этапов, текущая готовность и ссылки: chapter-map.json.

Одно состояние дома и на работе: PRIVATE GitHub
---------------------------------------------
VM больше не переносится на флэшке. lab start получает последнюю принятую
холодную VM, lab stop подтверждает выключение и фоном загружает поколение.
lab status показывает текущую фазу, lab retry сверяет незаконченный перенос.
Пока загрузка/CAS не завершились, server lease запрещает другому ПК начать
старое состояние. Нет автоотъёма по таймеру и слияния двух writable-дисков.
В Git лежат только metadata; qcow2 разбит на release assets≤512MiB с SHA256.
Файлы/БД на диске сохраняются; RAM/сеансы/временные namespace не переносятся.
Книгу читают офлайн, но получить актуальную VM/передать прогресс нужен интернет.
До отдельно принятого образа/доступов команды честно сообщают setup-required.
Точный запуск, начальный seed, роли и реальные пределы: vm/TRANSPORT.txt.

Windows и ограничения рабочего компьютера
----------------------------------------
Нативный Packet Tracer требует разрешённой установки или уже установленной
копии. У Cisco не найдено обещания официальной portable-версии без следов.
QEMU/TCG можно готовить как переносимый комплект, только если запуск
такого ПО разрешён. Наличие exe само по себе разрешением не является.
Docker на Windows — отдельный продукт с системными компонентами/данными;
он не становится переносимым простым копированием docker.exe.
В нашем варианте Docker работает ВНУТРИ переносимой Linux VM.

Все собственные диски, ключи, журналы и progress держим в runtime/private,
которые исключены из Git. Однако Windows/EDR/антивирус могут регистрировать
запуск, а ОС — использовать подкачку. Абсолютного «нулевого следа» на
чужом компьютере нельзя обещать. Не чистим системные журналы и не обходим
политику. Если запуск запрещён, остаются книга/модели либо разрешённый
удалённый доступ; локальный гость тогда недоступен.

Если всё-таки выбрать VPS
------------------------
Это дополнительный режим для доступа к одному постоянно сохраняемому
миру, а не условие чтения/оффлайн-упражнений. Для команд предпочитаем SSH:
передаётся текст, задержка влияет на отклик клавиши, вычисляет сервер.
VNC передаёт изображение GUI: расход сети и субъективная плавность зависят
от RTT, качества канала, разрешения/кодека, нагрузки. Универсально обещать
«как локально» нельзя; сначала краткое испытание с тем же GUI.

Ресурсный ориентир для такого испытания: 2 vCPU/4 GiB/40 GiB SSD для
последовательного мира. Для GUI + нескольких эмулируемых ОС вероятно
понадобится больше; 4 vCPU/8 GiB — только следующий проверяемый бюджет,
не гарантированный минимум GNS3/EVE. Кластер/CI не держим включёнными
одновременно на самом дешёвом тарифе. Считаем диски/копии/IP/трафик отдельно.
Покупок, регистрации сервера, открытия портов или настройки VPN сейчас нет.

Для GUI возможен VNC через SSH либо защищённый web-VNC на сервере.
Не публикуем открытый VNC в интернет и не зашиваем пароль в книгу.
На рабочем ПК проверяем разрешённый клиент/браузер и исходящий доступ.
При отсутствии интернета такой режим прекращается, поэтому нужен заранее
заранее полученный через GitHub локальный мир для дороги, если запуск локальных программ разрешён.

В VPS можно разместить Docker напрямую в Linux, а отдельные VM требуют
поддержки nested virtualization либо отдельных серверов. Само слово KVM
в тарифе не обещает /dev/kvm ВНУТРИ гостя. Импорт нашего qcow2 как загрузочного
диска также зависит от провайдера и формата firmware/образа. Контейнерные
рецепты и backup данных переносимы легче, чем весь live VM-процесс.
Смена VPS/локального режима — отдельный cold export/import, не магическая
синхронизация запущенных Docker Engine.

Где начать сейчас
----------------
  vm/TRANSPORT.txt                   — lab start/stop/status/retry и GitHub;
  vm/README.txt                      — инструкторская установка гостя;
  vm/world.py doctor                 — read-only инвентаризация;
  vm/world.example.json              — экономная Bash/Linux VM;
  vm/world.docker.example.json       — VM с Docker внутри;
  vm/guest/bootstrap.sh              — подготовка пакетов внутри гостя;
  vm/guest/netlab.sh                 — реальная маленькая сеть в госте;
  vm/guest/NETWORK-EXERCISES.txt      — пакет → маршрут → HTTP → NAT;
  packet-tracer/README.txt           — сборка схемы и шесть упражнений;
  packet-tracer/configs/             — исходные и добавочные конфиги;
  assets.example.json, check_assets.py — список/хеши офлайн-зависимостей;
  chapter-map.json                   — одна связанная программа практики;
  sources.json                      — проверенные официальные источники.

Перед следующим этапом выбираем реальную разрешённую среду Windows,
принимаем cold seed и проходим GitHub handoff на двух разрешённыхПК. До него
статус честный: управляющий прототип и учебные рецепты, не готовая VM.
