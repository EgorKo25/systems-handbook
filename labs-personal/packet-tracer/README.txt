CISCO PACKET TRACER: ЛИЧНАЯ УЧЕБНАЯ ТОПОЛОГИЯ
1 ноября 2026. Оригинальный рецепт; файл .pkt пока не создан в приложении.

Что это за инструмент
--------------------
Packet Tracer моделирует выбранные устройства, команды и протоколы Cisco.
Это удобная лаборатория для пути кадра/пакета и настройки, а не виртуальная
машина с настоящим Cisco IOS и не точный измеритель производительности.
Поддерживается часть CLI; команда в реальном устройстве может существовать,
а в модели отсутствовать. Сверять надо именно установленную версию.

В официальном Resource Hub при проверке указан Packet Tracer 9.0.1,
Windows 11, Ubuntu 22.04/24.04 LTS amd64, 4 GB свободной RAM, 1.4 GB диска.
Старый встроенный help на сайте перечисляет и Windows 10; при выборе
установщика приоритет у требований текущего Resource Hub. 4 GB — указание
Cisco для приложения, а не наш замер потребления этой маленькой схемы.
Ссылка и дата проверки — ../sources.json. Конкретный установщик не скачан.

Официальный путь — загрузка и установка из NetAcad с учётной записью
и принятием лицензии. Подготовку первого входа и проверку открытия
сохранённой схемы без интернета надо сделать дома заранее. Не обещаем,
что любой выпуск навсегда работает без повторной авторизации. Состояние
входа зависит от конкретного выпуска и учётной записи.
Официальной гарантии «portable, ничего не пишет в Windows» не найдено.
Не переносите установленную папку вместо разрешённой установки на работе
и не загружайте репаки. Если Packet Tracer на работе недоступен, остаются
разбор .cfg/схемы и настоящий Linux-гость, если его запуск разрешён.

Создание: одинаковые модели и версия на двух компьютерах
------------------------------------------------------
Пока нет настоящего .pkt: текстовый файл под таким расширением был бы
обманом. В установленном Packet Tracer создаём схему по этому рецепту,
вводим конфиги, проходим проверки, сохраняем личный master.pkt в saves/.
В Git и публичную книгу он автоматически не попадает.

Устройства:
  R1, R2: Routers → 2911, по три порта GigabitEthernet0/0..0/2.
  SW1, SW2, SW3: Switches → 2960-24TT.
  PC-A, PC-B, PC-C: End Devices → PC-PT.
  Server: End Devices → Server-PT.

Сборка кабелями; имена интерфейсов важнее расположения на экране:
  PC-A FastEthernet0 — SW1 FastEthernet0/1: Copper Straight-Through.
  PC-B FastEthernet0 — SW1 FastEthernet0/2: Copper Straight-Through.
  PC-C FastEthernet0 — SW2 FastEthernet0/1: Copper Straight-Through.
  SW1 GigabitEthernet0/1 — R1 GigabitEthernet0/0: Straight-Through.
  SW1 FastEthernet0/23 — SW2 FastEthernet0/23: Copper Cross-Over.
  SW1 FastEthernet0/24 — SW2 FastEthernet0/24: Copper Cross-Over.
  R1 GigabitEthernet0/1 — R2 GigabitEthernet0/1: Cross-Over (путь A).
  R1 GigabitEthernet0/2 — R2 GigabitEthernet0/2: Cross-Over (путь B).
  R2 GigabitEthernet0/0 — SW3 GigabitEthernet0/1: Straight-Through.
  SW3 FastEthernet0/1 — Server FastEthernet0: Straight-Through.
Параллельные линии между SW1/SW2 сначала физически есть, но порт
SW1 F0/24 административно выключен базовым конфигом. Во время сборки
пока нет конфигов: не включайте быструю перемотку на большой L2-петле.
Либо сначала подключите лишь F0/23, второй кабель добавьте после STP.

Адреса, вводятся в Desktop → IP Configuration:
  PC-A:   10.44.10.10 /24, gateway 10.44.10.1, DNS 10.44.30.10.
  PC-C:   10.44.10.11 /24, gateway 10.44.10.1, DNS 10.44.30.10.
  PC-B:   10.44.20.20 /24, gateway 10.44.20.1, DNS 10.44.30.10.
  Server: 10.44.30.10 /24, gateway 10.44.30.1, DNS 10.44.30.10.
  Маска /24 в графическом поле: 255.255.255.0.

R1/R2 transit A: 10.44.250.1 и .2, маска 255.255.255.252.
R1/R2 transit B: 10.44.250.5 и .6, маска 255.255.255.252.
Ни один этот адрес не берём с рабочего роутера/корпоративной сети.
Все сети существуют только в файле модели.

Вкладка CLI каждого устройства: откажитесь от initial configuration dialog,
дождитесь `Router>`/`Switch>`, вставьте соответствующий *-base.cfg.
Последняя команда copy running-config startup-config спросит имя файла:
нажмите Enter. Не вставляйте следующий конфиг до ответа на этот запрос.
Имена .cfg показывают устройство, не загружайте R1.cfg на коммутатор.

Server → Services: HTTP On; DNS On, A-запись app.study.test → 10.44.30.10.
Домен .test зарезервирован для тестирования. Мы не используем чужой домен.

Сначала контроль исходного состояния
----------------------------------
На SW1: show vlan brief; show interfaces trunk.
  Порты F0/1 и F0/2 в VLAN 10/20. G0/1 и F0/23 — trunk, VLAN 10/20.
На R1: show ip interface brief; show ip route; show ip ospf neighbor.
  G0/0.10/.20 и transit up/up. По двум транзитам должны появиться
  два соседства с router-id 2.2.2.2; состояние FULL может иметь /DR/BDR
  на Ethernet. Выбор DR/BDR не нужен для проверки связности.
  10.44.30.0/24 изучается как OSPF через путь A, его стоимость меньше B.
На R2: show ip route 10.44.10.0 — маршрут обратно к LAN клиента.
На PC-A: ping 10.44.10.11; ping 10.44.30.10.
  Первый echo может потеряться, пока идёт ARP; повторите и объясните его.
Desktop → Web Browser: http://app.study.test.
  Проверяем отдельно DNS-имя и HTTP по http://10.44.30.10; удача одного
  не доказывает исправность другого. Сохраните 00-baseline.pkt.

Упражнение 1. Путь одного запроса, не «зелёный конвертик»
------------------------------------------------------
Откройте Simulation, очистите список событий, оставьте ARP и ICMP.
PC-A посылает один ping Server. До шага заполните четыре значения:
отправитель/получатель MAC, IP-источник/IP-назначение, TTL, порт выхода.
На PC-A назначение IP — Server, назначение MAC — шлюз R1, а не Server.
В коммутаторе IPv4 TTL не уменьшается. R1 и R2 на каждой IP-пересылке
уменьшают TTL; Ethernet-заголовок собирается для следующего участка.
MAC конкретной машины прочитайте из модели, не выдумывайте по рисунку.
На trunk дополнительно отметьте VLAN tag; access-кадр к PC без него.
Обратный Echo Reply исследуйте отдельно: это новый IP-пакет.
Итог: таблица участков и объяснение, почему PC-A не ARP-ит Server.

Упражнение 2. VLAN и запасная линия без широковещательной бури
------------------------------------------------------------
Сохраните копию перед опытом. На SW1:
  configure terminal
  interface FastEthernet0/24
  no shutdown
  end
На SW1/SW2: show spanning-tree vlan 10.
  SW1 — root; у SW2 один из двух равных uplink станет alternate/discarding.
  Какой именно, определите по Bridge ID/Port ID, не по цвету линии.
  В выводе CLI состояние может называться BLK при отображении модели.
Выключите forwarding uplink со стороны SW1, дождитесь перехода резервного
и повторите ping PC-A→PC-C. Затем верните исходное состояние.
PortFast включён только к оконечным устройствам, не на межкоммутаторных
trunk. Не выключайте STP для получения «настоящей петли»; сначала научимся
объяснять, почему физический цикл не стал циклом пересылки данных.

Упражнение 3. Выбор маршрута и отказ
----------------------------------
Сравните show ip route 10.44.30.0, show ip ospf interface GigabitEthernet0/1
и аналогичный G0/2. Стоимость пути A меньше; это выбор OSPF для префикса.
Затем в R1 на G0/1 выполните shutdown; дождитесь пересчёта, проверьте
маршрут через 10.44.250.6 на G0/2 и доступ к Server. Замерьте наблюдаемое
в модели время, но не выдавайте его за SLA настоящего маршрутизатора.
Верните G0/1 no shutdown. Отдельно объясните: longest-prefix match
выбирает самый точный префикс в таблице; метрика сравнивает кандидатов
одного протокола к префиксу. Это разные стадии, не одна «лучшая цифра».

Упражнение 4. DHCP и DNS
----------------------
Добавьте R1-dhcp-add.cfg. Переключите PC-A/PC-B на DHCP, наблюдайте
Discover/Offer/Request/Ack. show ip dhcp binding на R1 покажет выдачу.
Предскажите broadcast/unicast и адреса на каждой стадии, а не только DORA.
Получив адрес, проверьте DNS-запрос app.study.test и HTTP. Сломайте только
DNS server в настройке клиента: IP-связность останется. Верните конфиг.
DHCP живёт на R1 в VLAN клиента, relay в этом первом опыте не нужен.

Упражнение 5. NAT — отдельное преобразование
-----------------------------------------
Вернитесь к точке до NAT или сохраните новую копию. R1-nat-add.cfg
выключает путь B намеренно: обратный маршрут здесь должен проходить
через один предсказуемый NAT-router. Посмотрите R1 show ip nat statistics,
show ip nat translations. Запустите ping или HTTP PC-A→Server.
Внутренний source PC-A (10.44.10.10 при исходной статической настройке
либо текущий адрес DHCP) заменится на 10.44.250.1; при PAT
различаются порты TCP/UDP либо ICMP identifier. Server остаётся тем же.
В Simulation сопоставьте до/после, обратный lookup и пересчёт контрольных
сумм. Запишите реальный вывод: идентификатор/порт заранее не фиксируем.
NAT здесь не даёт доступ в интернет, сервер находится в модели.
Этот же доступ работал без NAT благодаря обратным маршрутам: объясните,
зачем преобразование может понадобиться и какую связность само не создаёт.

Упражнение 6. ACL и NAT — разные правила
-------------------------------------
Добавьте R1-acl-add.cfg. PC-B→PC-A теперь запрещён, PC-B→Server разрешён.
show access-lists покажет совпадения. Убедитесь, что deny стоит до permit:
порядок ACL значим. Числовая ACL 10 в NAT выбирает адреса для трансляции,
а VLAN20_BOUNDARY фильтрует пакеты на входе интерфейса; не путайте их.
Правило не stateful: при ping PC-A→PC-B ответ PC-B→PC-A тоже попадает
под deny. Это ожидаемый эффект статической ACL, не «сломался ping».

Сохранение между компьютерами
----------------------------
copy running-config startup-config сохраняет конфиг внутри виртуального
устройства, File → Save сохраняет .pkt со всей схемой на носитель.
Нужно сделать ОБА действия. Последовательные файлы 00-baseline.pkt,
01-packet-walk.pkt, 02-stp.pkt и т.д. — понятные точки, а не одинаковое
пустое упражнение каждый раз. Запишите точную версию PT в личном журнале.
Открывайте и проверяйте перенос на той же версии; формат новых выпусков
может быть несовместим со старыми. Это не перенос Linux qcow2.

Что этим опытом нельзя доказать
-------------------------------
Реальные электрические сигналы, BER/FEC, оптический бюджет, точную
производительность TCP, NIC offload, драйверы ядра и поведение эфира
исследуем отдельными измерениями/моделями. Packet Tracer не превращаем
в доказательство этих деталей. Повторяем путь пакета в настоящем Linux
с ip/tcpdump/nft, затем сравниваем команды и наблюдаемые инварианты.

Статус проверки
---------------
Сверены адресный план, пары интерфейсов, порядок дополнений и ожидаемая
логика. Packet Tracer в этой среде не установлен; конфиги не прогнаны
в его CLI, STP/OSPF/NAT/ACL не объявляются реально испытанными.
Приёмка: собрать в PT 9.0.1 или выбранной общей версии, проверить каждую
команду и каждый ожидаемый результат, только затем отметить готовность.
