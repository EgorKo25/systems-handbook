ОДИН СТЕНД ДОМА И НА РАБОТЕ: PRIVATE GITHUB, БЕЗ ФЛЭШКИ
Source candidate,2 ноября 2026. Настоящие GitHub/VM/Windows здесь не испытывались.

Обычный цикл после первоначальной приёмки
---------------------------------------
Рабочий каталог — labs-personal/vm. В своей локальной защищённой конфигурации
указаны PRIVATE служебный repo, default branch и отдельный локальный state.
Библиотеку можно читать без интернета. Получить актуальную VM и передать новое
поколение можно при наличии сети. Между start и stop обучение идёт локально.

  ./lab start
  ./lab access
  ./lab stop
  ./lab status
  ./lab status --remote
  ./lab retry
  ./lab vnc

Эквивалент без shell: python3 -B lab.py start. --config задаётся ДО команды:
  python3 -B lab.py --config /свой/защищённый/config.json status
На разрешённом Windows: .\Lab.ps1 --config C:\свой\config.json status,
либо существующий Python3.10+ с lab.py. PowerShell5.1 достаточно. Изменять
execution policy, устанавливать Python/QEMU/гипервизор или обходить ограничения
компьютера этот код не умеет. Windows-прогон не выполнен.

start читает remote current, получает серверное исключительное владение,
скачивает и сверяет manifest/части/SHA, собирает самостоятельный qcow2 в НОВУЮ
локальную папку, проверяет qemu-img info/check и запускает свой supervisor.
При отсутствии принятого current, QEMU или конфигурации он отказывает:
setup-required. Файлы образа и работающие службы этот source не создаёт.

start ждёт supervisor handshake не более 5 секунд. Если он ещё не получен,
сообщает starting/unavailable и предлагает lab access. После handshake
выводится отдельный student profile: учётная роль, SSH,
RDP-адрес и команда VNC. По умолчанию все services=false: setup-required.
Даже после подготовки это выданные endpoints, не активная проверка здоровья
каждой службы. QMP running не означает, что SSH уже завершил загрузку.
Для рабочего SSH нужен проверенный гостевой пользователь/sshd и авторизация:
пароль либо заранее разрешённый ключ/agent. Optional ssh_identity — путь
к имеющемуся private key в защищённом ЛОКАЛЬНОМ config, не его содержимое.
Ключ программа не читает, не копирует и не загружает. Каждый ПК отдельно
получает разрешённую авторизацию. Эфемерный ключ технической seed-пробы
сам по себе не предоставляет доступ будущему Windows-клиенту.

Для SSH создаётся свой пустой ssh_config и свой known_hosts внутри state;
команда не правит конфигурацию/known_hosts компьютера. В дальнейшем это
вход только в разрешённый management/bastion: скрытые узлы не получают
hostforward. Их ищут изнутри изолированного стенда по условиям задания.
Фактические маршруты/межсетевые правила/права должны быть созданы и проверены
в госте. Надпись role=student не запрещает sudo и не настраивает firewall.
Нынешний source ещё не принуждает все ограничения будущих 23 заданий.

RDP относится только к отдельно подготовленной Linux desktop-службе
гостя:127.0.0.1:13389→3389. Windows-образ/лицензия не предполагаются.
VNC — гостевая служба 127.0.0.1:15901→5901, не экран гипервизора.
lab vnc откроет имеющийся vncviewer только при выданном services.vnc=true;
при false/отсутствующем viewer откажет, ничего не установит. Формат команды:
  vncviewer 127.0.0.1::15901
SSH использует loopback-порт из world config, обычно 2222→22. Ни один из
этих forwards не слушает LAN. По умолчанию исходящая сеть гостя ограничена.
Разрешение egress — отдельное явное allow_network=true владельца стенда.

Instructor lifecycle хранит gh-авторизацию и supervisor на хосте, не в госте.
QMP идёт по private stdio pipe, без сетевого порта или гостевого socket.
Резервная GUI-консоль включается владельцем через instructor_console=true
перед следующим запуском; это отдельный rescue/bootstrap, не тайный путь
student-задания. Владелец своего гипервизора технически может обойти учебные
ограничения: этот проект не изолирует человека от его собственного хоста.

Что означает stop
-----------------
Команда stop лишь записывает запрос собственному supervisor и сразу возвращает
управление. Она работает без сети. Supervisor посылает QMP system_powerdown,
затем ждёт guest SHUTDOWN с guest=true/reason=guest-shutdown И exit0 своего
QEMU. Закрытие окна, сигнал, guest-reset, один POWERDOWN или ненулевой код
этот тест не проходят. По тайм-ауту нет принудительного quit/kill и нет копии:
VM может ещё работать, lease сохраняется, status сообщает причину.
Сон на диск (гибернация, ACPI S4) также не принимается. QEMU может выдать
SUSPEND_DISK, а затем SHUTDOWN с reason=guest-shutdown; одного этого reason
недостаточно. Событие SUSPEND_DISK сохраняется в квитанции и запрещает upload. Повторный
stop разрешён как новый запрос, не как принудительное отключение питания.
При сломанном QMP supervisor ждёт выхода своего ребёнка и не отпускает
world.lock, пока тот способен писать диск. Ошибки протокола не маскируются
последующим подходящим событием.

QMP сообщает причину остановки виртуальной машины. Он не читает внутренние
журналы всех приложений и не доказывает, что ошибочно настроенный гость
сохранил каждую БД. Нужна предварительно испытанная штатная остановка ОС/
служб. После неё qemu-img check проверяет qcow2 без ремонта. Если проверка
отказала, статус shutdown-observed сохраняется, upload не начинается.

Только после подтверждённого выхода и проверки формата controller создаёт
отдельную холодную копию через qemu-img convert, без backing chain/-U.
Она и части становятся local pending. Затем собственный фоновый процесс
отправляет поколение. Надпись stop-requested/pending/uploading не означает
«синхронизировано». До remote CAS в конце другой ПК остаётся заблокированным.
Дождитесь phase=synced в status --remote, прежде чем выключать хост/терять сеть.
При обрыве остаётся pending и исключительное владение; lab retry продолжает
сверку. Локальный новый прогресс не перезаписывается старым remote current.

GitHub-протокол
---------------
В Git хранится маленький lab-control.json: format/revision/current/lease.
current — tag+SHA256 manifest; lease — случайный owner nonce и active/uploading.
Contents API PUT передаёт точный предыдущий blob SHA: два start не могут оба
успешно заменить одну версию. Revision растёт, новый nonce не переиспользуется.
Никакого отъёма по TTL/часам/«PID другого компьютера» нет. Потерянный ответ
после PUT перепроверяется чтением того же содержимого, не слепым повтором.

Если gh завершился с ошибкой и совсем не вернул HTTP-ответ на GET, чтение
метаданных повторяется не более трёх раз, с паузами 1 и 2 секунды. Ответ с
HTTP-кодом или непустой неверный ответ этим правилом не повторяется. Запросы
POST/PUT/PATCH/DELETE автоматически не дублируются. При отказе программа
сохраняет уже подготовленные локальные части и удерживаемое владение.
Восстановите сеть и выполните lab retry.

Диск НЕ коммитится в Git, не кладётся в Git LFS или публичную книгу. Один
qcow2 без backing files режется на последовательные disk-0000.part и т.д.,
не более 512MiB каждая. Manifest содержит общий SHA/байты, SHA/байты каждой
части, конфигурацию, world_id, cold provenance и access profile. Прогресс
в файловых данных VM сохраняется, RAM/живые соединения при этом не переносятся.

Для поколения создаётся собственный draft release world-<nonce>. Все части
и manifest загружаются без --clobber. Каждая удалённая часть ЧИТАЕТСЯ ОБРАТНО
и сравнивается по длине/SHA. Только потом draft публикуется и один CAS меняет
current вместе с lease=null. Это также учитывает repositories с immutable
releases: публикация идёт после наполнения. Указатель не использует «latest».
Опубликованные поколения не меняются и не удаляются этим кодом.

После потерянного ответа upload retry проверяет уже имеющиеся assets. Только
пустой state=starter из СВОЕГО draft release с точной меткой owner может
удаляться и загружаться вновь. Любой чужой/неизвестный asset, несовпадающий
загруженный файл или повреждённый local pending вызывает отказ. Ничего не
перетирается ради продолжения. Даже успешная загрузка всех байтов без
конечного CAS не освобождает lease и не разрешает start старой версии.

После успешной обратной проверки скачанные байты сохраняются в локальном
каталоге verification/readback-v1. При retry программа проверяет владельца
поколения, репозиторий, идентификатор выпуска и удалённого файла, его имя,
состояние и размер. Затем заново считает SHA локальной копии. Если всё
совпало, повторно скачивать эту часть не требуется. Другой идентификатор
файла требует новой загрузки; повреждённый кэш останавливает публикацию.
Старые случайно названные .check не содержат такой привязки и не используются
как кэш. Это экономит трафик повторных попыток; полные копии на диске остаются.

При потерянном ответе последнего CAS retry распознаёт тот же current и
не снимает новую чужую lease. Если другой полный цикл уже успел передвинуть
current ещё дальше, неизвестную ветку нельзя автоматически «примирить»:
оператор сравнивает историю metadata/release, не перезаписывает control.
Слияния двух изменённых файловых систем нет. При потере owning-компьютера
lease восстанавливает instructor после проверки всех писателей/pending;
автоматической force-unlock команды намеренно нет.

Цена переноса
-------------
Полная копия экономит сложность зависимых overlays, но требует времени,
места и трафика. На диске временно есть рабочий qcow2, холодный snapshot,
его части, загруженные части предыдущего поколения и read-back verification.
Безопасная верхняя оценка этой реализации — несколько размеров занятого
qcow2, а не только виртуальный disk_gib. Verify-файлы/старые папки сохраняются;
автоматической сборки мусора нет. Перед реальным запуском нужен запас места.
Это ограниченный первый backend, не разностный файловый синхронизатор.
При диске 8GiB и канале 20MiB/s один проход занимает около 410 с; отдельный
read-back и скачивание на втором ПК добавляют ещё передачи. Это вычисление,
не измеренный канал. GitHub SHA не является шифрованием: читающий PRIVATE
repo может получить содержимое учебного диска. Внутри нельзя оставлять
производственные секреты; gh credentials хоста в образ не копируются.

Подготовка владельцем, пока образ ещё setup-required
-------------------------------------------------
Нужны существующие Python3.10+, gh и QEMU/qemu-img с подходящими firmware/DLL.
gh уже должен быть авторизован разрешённым пользователем с достаточными
правами PRIVATE repo. Код не читает токены и не меняет auth/scopes.
QEMU ищется прежним world.py в разрешённых tools/linux|windows либо PATH.

Создание PRIVATE repo и выбор владельца выполняются отдельно после приёмки.
Репозиторий создают ПУСТЫМ: без auto-init коммита с неизвестным email.
Скопируйте transport.example.json в ~/.personal-lab/config.json, задайте свой
PRIVATE repo/default branch и отдельный личный root. На Windows используйте
свой закрытый каталог пользователя/ACL. Не коммитьте конфигурацию, runtime,
ключи или диски. Затем только осознанный instructor вызов:
  python3 -B lab.py init
Первый metadata commit и все последующие Contents commits задают ЯВНО оба
author/committer EgorKo25 <77259232+EgorKo25@users.noreply.github.com>.
Пустой current не является готовым образом: start честно откажет.

После отдельной реальной приёмки своей cold VM с world.json и независимым
active_disk начальное поколение можно допустить ТОЛЬКО один раз:
  python3 -B lab.py seed /свой/закрытый/world --guest-stopped --accept-initial-image --access /свой/access.json
Это два осознанных подтверждения человека первоначальной приёмки, а не
автоматическое доказательство выключения. В manifest навсегда указан
operator-asserted-initial-only. Протокол не даёт таким флагом публиковать
следующие рабочие поколения: дальше только наблюдаемый QMP shutdown.
Подготовленный SSH-пользователь/авторизация/ограничения и их реальный proof
должны быть приняты владельцем ДО services.ssh=true. RDP/VNC остаются false,
пока соответствующая Linux-служба и клиент не подготовлены/не испытаны.
В этой работе настоящего seed/remote init/create/upload ещё не выполнено.

world.py остаётся низкоуровневым инструментом первоначальной установки и
локальных опытов. НЕ запускайте им вручную уже зарегистрированную рабочую
ветку и не экспортируйте её для параллельного продолжения на другом ПК:
иначе вы обходите lease нового протокола. Инструкторские локальные точки
и возврат сохраняют предыдущий диск; их дальнейшая remote публикация
требует заново подтверждённой остановки, без ремонта активного qcow2.

Проверки этого source
--------------------
  python3 -B -m unittest discover -s ../tests -p 'test_*.py'
Fake API, tiny fake disk, свои TEMP, подставные QEMU children. Никаких
настоящих GitHub repo/release или VM эти тесты не создают. Native gh --help
проверяет только синтаксис установленного CLI. Linux boot и Windows/TCG,
GitHub CAS в реальной сети, права/службы/SSH/RDP/VNC ещё требуют отдельного
сквозного прогона; успешный fake API их не заменяет.
