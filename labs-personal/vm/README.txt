ЛИЧНЫЙ МИР: ОДНА LINUX-МАШИНА, КОТОРУЮ МОЖНО ПРОДОЛЖИТЬ
1 ноября 2026. Подготовлен управляющий код; загрузка настоящего гостя ещё не испытана.

Что именно готово
-----------------
world.py — небольшой контроллер жизненного цикла, а не эмулятор Linux.
Он вызывает отдельно подготовленный QEMU. ОС и её команды настоящие.
Контроллер не устанавливает ПО, не скачивает образы, не меняет маршруты,
не подключает каталоги хоста к гостю, не включает Hyper-V/WSL и не создаёт
службы. Из HTML команды не запускаются автоматически.
Его собственные данные находятся в выбранном --root; export пишет только
в явно заданный новый каталог. Это не гарантия отсутствия других следов:
QEMU, графическая библиотека, Python и сама ОС могут вести свои журналы,
кэш и подкачку. Переносимый диск не превращает чужую ОС в систему без следов.

Есть создание диска, подключение подготовленного базового образа, запуск,
сухой показ команды, выключенные контрольные точки, возврат новой веткой
без удаления прежнего диска и независимый экспорт. Одновременный запуск
через контроллер блокируется. Блокировка не является распределённой:
две уже скопированные ветки на двух ПК она не синхронизирует.

Требования
----------
Ubuntu: Python 3.10+, qemu-system-x86_64 и qemu-img. KVM используется,
если текущему пользователю доступен /dev/kvm. Само наличие устройства
ещё не доказывает успешный запуск. При ошибке ускорителя явный --accel tcg
включает программную эмуляцию; это не средство обойти запрет запуска ПО.

Windows: разрешение на запуск выбранных программ, QEMU x86_64, его DLL
и firmware, Python 3.10+. Start-Lab.ps1 совместим с обычным Windows
PowerShell 5.1, PowerShell 7 не требуется. Если Python не установлен,
заранее подготовленный официальный Windows embeddable Python размещается
в ../tools/python/python.exe. Библиотек сторонних Python-пакетов нет.
Не меняйте execution policy ради стенда. Если запуск ps1 запрещён,
но разрешён сам интерпретатор, можно вызвать python.exe world.py напрямую.
Если запрещено выполнение программ с USB, этот режим не подходит.

QEMU ищется в ../tools/windows/ либо ../tools/linux/, затем в PATH.
Одного exe обычно недостаточно: состав DLL и каталог firmware зависят
от сборки. Путь tools расположен внутри labs-personal, а не внутри vm.
Нужно проверить весь комплект дома на целевой Windows до поездки.

Программный TCG — базовый переносимый вариант Windows. Он существенно
медленнее аппаратного ускорения на тяжёлых задачах; реальных цифр пока
нет. WHPX требует уже доступной Windows Hypervisor Platform и отдельной
проверки: этот контроллер её не включает и пока не выбирает.

Версии и виртуальное железо
--------------------------
Manifest фиксирует x86_64, pc-i440fx-8.2, BIOS, qemu64, virtio-диск и сеть.
У выбранной сборки QEMU проверьте `-machine help` и `-cpu help`. Тип
машины 8.2 не означает, что обязательно нужен ровно QEMU 8.2: обе сборки
должны поддерживать указанный тип. Совместимость Linux/Windows, CPU и
загрузка одинакового диска — ещё не пройденный приёмочный тест.

world.example.json: один гость 1024 MiB, 1 vCPU, виртуальный диск 20 GiB.
Это исходная экономная конфигурация для Bash/Linux, не измеренный минимум.
world.docker.example.json: 3072 MiB, 2 vCPU, диск 40 GiB, Docker в госте.
Это проектный бюджет для последовательных небольших служб, не для всего
стека одновременно. Jenkins, сборку, реплики запускаем отдельно по нужде.
Контроллер оставляет минимум 768 MiB запаса доступной RAM; он не оценивает
будущий рост процессов хоста и не закрывает пользовательские программы.
На медленной флэшке узким местом легко станет случайный ввод-вывод.

Первый запуск дома: установка из официального ISO
------------------------------------------------
1. Сначала выполните только проверку:
   python3 world.py doctor
   Она ничего не создаёт. Здесь не должно оказаться «QEMU отсутствует».
   Официальные источники загрузок: ../sources.json.

2. Получите Ubuntu Server 24.04 LTS amd64 с releases.ubuntu.com, проверьте
   подпись SHA256SUMS и сумму файла по руководству Ubuntu. Установщик
   сюда не включён. Образы и лицензированные программы не публикуются
   вместе с книгой. Создайте новый каталог мира:
   python3 world.py create --config world.example.json
   Или для будущего Docker: --config world.docker.example.json.
   Повторный create существующий мир не перезаписывает.

3. Запустите установку. Установщик всегда открывает окно экрана QEMU:
   python3 world.py start --installer /путь/ubuntu-server-amd64.iso --allow-network
   Сетевой доступ включён здесь явно для загрузки пакетов. На рабочем ПК
   установку не делаем. Путь к ISO с пробелами заключите в кавычки.
   Установка получает 2048 MiB; диски реального компьютера гостю не видны.

4. Внутри установщика выберите весь виртуальный диск, пользователя student.
   Пароль задайте свой. Основной маршрут вводит OpenSSH отдельно в P01;
   до него достаточно консоли. Если это повторная техническая подготовка,
   OpenSSH можно выбрать в установщике, записав это решение в паспорт.
   Данные диска хоста не подключены.
   Имя student — учебное, не учётная запись организации. Установите BIOS,
   не добавляйте UEFI/TPM/passthrough: этот профиль их не переносит.
   После установки выберите завершение работы. -no-reboot закрывает QEMU
   при попытке перезагрузки; запустите следующий этап уже без ISO.

5. После установки можно открыть окно консоли, даже если сеть сломана:
   python3 world.py start --console window
   Это экран VM с обычным текстовым входом Ubuntu Server, не установленная
   графическая рабочая среда. В выбранной сборке QEMU нужен рабочий оконный
   backend и доступная графическая сессия хоста. Наличие окна не проверено
   в этой среде. Не закрывайте окно вместо корректного poweroff гостя.

   Для чтения вывода в том же терминале используется обычный start либо
   явный --console serial. Последовательный терминал Ubuntu Server обычно
   включён в поддерживаемых профилях; не полагайтесь на это молча.
   Сначала подключитесь по SSH из второго терминала:
   ssh -o UserKnownHostsFile=../runtime/known_hosts -p 2222 student@127.0.0.1
   В госте включите `sudo systemctl enable serial-getty@ttyS0.service`.
   Если загрузочный вывод тоже нужен, в гостевом /etc/default/grub добавьте
   console=tty0 console=ttyS0,115200 к GRUB_CMDLINE_LINUX и выполните
   sudo update-grub. Это команды гостя, не домашнего компьютера.
   Пока serial/SSH не подготовлены, используйте start --console window.

6. Основной учебный путь ставит инструменты по мере первого появления
   в practicum/index.html. guest/bootstrap.sh — дополнительная пакетная
   подготовка для повторного опыта, не обязательный шаг и не готовое
   решение задач установки. Только если осознанно выбран такой вариант,
   передайте его В ГОСТЬ, проверьте текст и выполните:
   sudo bash bootstrap.sh --inside-lab-vm
   Он ставит инструменты только внутри QEMU/KVM-гостя, требует интернет.
   Установку Docker делайте по официальной инструкции Ubuntu в госте;
   на хосте и рабочем Windows Docker для этого варианта не нужен.
   Все нужные контейнерные образы загружаются дома заранее. Docker
   автоматически не установлен и нигде в этой сессии не запускался.

   Не выполняйте весь скрипт заранее, если проходите первоначальное
   получение и установку каждого инструмента самостоятельно. Сохраните
   соответствующие пакеты для офлайн-этапа, а установку и настройку
   выполняйте в его задании с записью результата в паспорт.

7. В госте выполните `sudo poweroff`, дождитесь выхода QEMU. Сохраните:
   python3 world.py checkpoint clean-base --guest-stopped
   Флаг подтверждает, что вы действительно выключили гостя. Контроллер
   не умеет самостоятельно доказать согласованность завершения всех БД.

Если готовый самостоятельный образ уже есть
-----------------------------------------
python3 world.py adopt-base /путь/подготовленный.qcow2
Исходник остаётся без изменений, рабочий диск конвертируется в новый файл.
Нужен qcow2 без backing file, уже с ОС, SSH и известным личным доступом.
Скачанный cloud image сам по себе не гарантирует пароль/SSH: ему обычно
нужен cloud-init seed. Не пытайтесь войти в него «заводским паролем».
Сначала подготовьте его дома либо используйте установку из ISO выше.

Изменить память существующего мира
----------------------------------
Новый профиль create/adopt-base не нужен для следующей задачи.
Сначала штатно выключите гостя и сохраните холодную контрольную точку.
Скопируйте его world.json в приватный резерв. В существующем world.json
можно изменить только config.memory_mib (512..8192) и config.vcpus (1..4),
сохранив world_id, active_disk и прочую конфигурацию без изменений.
Проверьте start --dry-run, бюджет свободной памяти хоста и затем запуск.
Редактирование выполняется только при остановленной VM без world.lock;
команды отдельного автоматизированного изменения ресурсов пока нет.
Транспортный SHA256 старого экспорта после изменения JSON устаревает:
для переноса создаётся новый полный export, а не исправляется чужая сумма.
Размер disk_gib в JSON не расширяет существующий qcow2 или файловую систему.
Рост диска — самостоятельный опыт со своей копией и проверкой всех слоёв.

Обычный цикл
------------
python3 world.py start --dry-run
python3 world.py start
При сломанном сетевом доступе: python3 world.py start --console window.
Предварительный просмотр: python3 world.py start --console window --dry-run.
Консоль выбирается на каждый запуск, содержимое диска и его состояние
от этого не сбрасываются. Установочный ISO всегда включает оконный режим,
даже если явно указан --console serial.
Окно — локальный экран QEMU. Контроллер не запускает VNC/web-VNC и не
открывает для него дополнительный сетевой порт.
Второй терминал: SSH на 127.0.0.1:2222, known_hosts внутри runtime.
По умолчанию user-mode сеть запрещает исходящие соединения гостя наружу;
только явно проброшенный localhost SSH остаётся доступным.
Внутри гостя будут DHCP 10.0.2.15, gateway 10.0.2.2, DNS 10.0.2.3.
Это служебная сеть QEMU, не модель изучаемого Ethernet/NAT. Исследуемые
сегменты создаём отдельно внутри Linux или Packet Tracer.

В serial-режиме Ctrl+A, затем C переключает в монитор; Ctrl+A, затем H
показывает помощь. Для нормального выключения — sudo poweroff в госте.
В monitor команда system_powerdown посылает ACPI-запрос, но не гарантирует
завершения ОС. quit и Ctrl+A X — выключение питания, не корректный shutdown.
Закрывать окно/выдёргивать USB вместо poweroff нельзя считать сохранением.

Контрольная точка и возврат
--------------------------
python3 world.py checkpoint before-nat --guest-stopped
python3 world.py restore before-nat --guest-stopped --confirm before-nat
Возврат создаёт новый самостоятельный диск и переключает active_disk.
Предыдущий диск сохраняется в disks/. Никаких rm/reset/destroy нет.
Полные независимые копии проще переносить, но требуют места и времени.
Не делаем цепочек overlay в первой версии: случайно забытый backing file
не должен превратить флэшку в незагружаемый комплект. Оптимизацию по
разностным слоям добавим только после проверенного переноса целой цепочки.

Если после сбоя остался world.lock: проверьте процессы QEMU на текущем
компьютере, что USB не занят другим запуском и гость действительно выключен.
Только после этого вручную переименуйте lock в диагностическую копию.
Автоматическое удаление блокировки по PID другого компьютера небезопасно.

Дом ↔ работа: один прогресс, два способа транспорта
-------------------------------------------------
А. Самый простой: один выключенный runtime целиком переносится на USB.
   Книга, инструменты и этот же каталог едут вместе. На другом ПК:
   python3 world.py --root /путь/к/runtime start --dry-run
   Затем start. Windows: Start-Lab.ps1 --root E:\Study\runtime start.
   Не держите writable-диск одновременно открытым на двух компьютерах.

Б. Если домашний диск быстрее USB, сделайте холодный экспорт:
   python3 world.py export /путь/на/флэшке/world-trip --guest-stopped
   Экспорт только в новый каталог, с SHA256.json. Он содержит текущий диск
   и manifest, но не всю историю контрольных точек. Суммы проверьте после
   передачи. Чтобы не раздвоить прогресс, зафиксируйте, какая копия теперь
   главная. У компьютера дома старую ветку не продолжайте параллельно.
   После поездки — новый экспорт обратно в новый каталог; старый оставьте
   как резерв до проверки. Автоматического слияния двух ФС нет.

Через интернет можно передавать такой закрытый пакет в личное хранилище,
но этот код не выбирает сервис, не загружает файлы и не публикует секреты.
Не синхронизируйте live qcow2 облачным клиентом: получите промежуточные
состояния. Отправляйте после shutdown и завершения хеширования, скачивайте
полностью, затем проверяйте суммы. Диски, ключи и личный прогресс не Git.

Docker внутри того же гостя
--------------------------
Контейнеры не эмулируют отдельное ядро. Linux-гость даёт ядро, Docker
экономно запускает службы на нём. Его /var/lib/docker и named volumes
лежат на виртуальном диске и едут с ним при холодном переносе.
Образы — программы; volumes — изменяемые данные. docker save/load
переносит образы, но не заменяет перенос volumes/всего выключенного мира.
Перед контрольной точкой: остановить сценарий штатно, затем poweroff.

Публикуйте учебные сервисы на 127.0.0.1 ГОСТЯ. С хоста используйте
SSH -L, например -L 8080:127.0.0.1:8080. Не добавляйте незаметно host mounts,
Docker socket, привилегированные контейнеры и доступ к LAN компьютера.
Для сетевых namespace, дисков/LVM и ядра полноценный гостевой root уместен,
но действия должны оставаться внутри выделенного мира.

Ограничения готовности
---------------------
Проверены логика файлов/путей/блокировок/возврата и сухая команда.
В этой сессии нет установленного QEMU и образа гостя: ни загрузка ОС,
ни производительность TCG, ни Windows-комплект, ни Docker в госте пока
не испытаны. Подготовка рецепта не должна выглядеть как готовая VM.
Приёмка перед поездкой: два упражнения подряд → poweroff → точка →
поломка копии → возврат → холодный перенос → запуск без интернета.
Все этапы должны пройти на двух конкретных компьютерах, а не только в CI.
