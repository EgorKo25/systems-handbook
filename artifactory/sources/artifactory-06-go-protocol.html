Go modules: адреса протокола и идентичность исходников

Правильный ZIP в Generic repository ещё не обслуживает договор GOPROXY.

Координата, путь запроса и путь внутри ZIP

Модуль — единица версионирования Go с go.mod, объявляющим module path. Package, пакет Go, — каталог компилируемых исходников с собственным import path; один модуль может содержать несколько пакетов. Наша зависимость объявлена как example.invalid/BuildLab/checkdigit v1.0.0. Consumer receipt требует её без replace. Replace подменил бы путь получения локальным каталогом и скрыл бы отсутствие настоящего разрешения через прокси, поэтому в основном опыте его нет.

GOPROXY задаёт базу протокола. Для сервера это https://aft.lab.example/artifactory/api/go/go-virtual. Клиент добавляет escaped module path, /@v/ и элемент версии. Большие ASCII-буквы кодируются в ! плюс маленькую букву: BuildLab становится !build!lab. Символ ! может быть передан в URL как %21; это ещё один уровень URL-кодирования, не другая координата модуля. Слэши остаются границами пути: вложенный example.invalid/Team/tools/checkdigit/v2 не превращается в один basename. Major suffix /v2 относится к модулю и должен согласовываться с go.mod и v2.x.y.

.../example.invalid/!build!lab/checkdigit/@v/v1.0.0.info
.../example.invalid/!build!lab/checkdigit/@v/v1.0.0.mod
.../example.invalid/!build!lab/checkdigit/@v/v1.0.0.zip
.../example.invalid/!build!lab/checkdigit/@v/list

.Info — JSON с обязательным Version и необязательным Time в формате RFC3339; .mod — содержимое go.mod; .zip — исходное дерево определённой версии; list перечисляет версии, но фиксированный запрос не обязан сначала читать list. Внутри ZIP префикс, наоборот, использует исходный регистр module path: example.invalid/BuildLab/checkdigit@v1.0.0/. Наш allowlist-упаковщик создаёт только три известных файла маленького примера. Он не является универсальным валидатором всех модулей: ограничения путей, размера, case collision, symlink и вложенных модулей промышленного ZIP требуют проверенной реализации x/mod/zip.

Разобрать один протокольный ответ

После выбора HTTPS-источника Go запрашивает конкретный ресурс. Ниже показано текстовое представление HTTP/1.1 для .mod; это не TLS-запись на проводе и не гарантированная версия HTTP реального клиента. У настоящего запроса также могут быть заголовки аутентификации, здесь они опущены.

GET /artifactory/api/go/go-virtual/example.invalid/!build!lab/checkdigit/@v/v1.0.0.mod HTTP/1.1
Host: aft.lab.example

Host выбирает имя сервера, go-virtual — административный источник, escaped path — модуль, суффикс v1.0.0.mod — вид объекта и фиксированную версию. В нашем fixture успешное тело .mod имеет ровно 54 байта: это поставленный go.mod, включая переводы строк. Content-Length считает байты тела, а не весь HTTP-ответ и не размер извлечённого модуля. Тело .info отдельно содержит Version и UTC-время Time; .zip содержит дерево с префиксом module@version. Эти объекты должны согласовываться. Ошибка JSON, чужой Version или неправильный префикс ZIP не исправляются успешным получением остальных объектов. Порядок и параллелизм запросов выбирает клиент; перечень трёх ресурсов не задаёт обязательной последовательности.

Для фиксированной канонической v1.0.0 поле Version должно вернуть ту же версию. Списки версий и сведения .info не защищены суммами go.sum так же, как содержимое .mod и .zip; время не является подписью выпуска. В нашем fixture Time задан явно, но его отсутствие само по себе не нарушает протокол.

Почему .zip SHA256 и go.sum h1 различаются

SHA256 файла ZIP хеширует его точные байты, включая сериализацию архива. Сумма h1 в go.sum относится к канонизированным именам и содержимому файлов модуля. Перепаковка того же дерева с другими временем, порядком и сжатием может изменить ZIP SHA256, сохранив h1. GoModSum хеширует go.mod в своём определённом представлении. Поэтому серверный checksum ZIP нельзя просто вставить вместо h1, а совпадение go.sum не является обещанием идентичности упаковочных байтов. Проверка каждого уровня имеет отдельный объект.

Go сохраняет доверенные суммы в go.sum и может сверять публичные модули с checksum database, журналом контрольных сумм с проверяемой криптографической структурой. Это отдельный сервис и цепочка доверия, а не SQL-таблица вашего Artifactory. Частный модуль нельзя посылать публичной sumdb ради проверки: настройка GONOSUMDB исключает только его собственный частный префикс. Исключение не добавляет нового независимого подтверждения. Первая встреча с подменённым содержимым без прежней доверенной суммы и без sumdb может быть принята. Нужен доверенный источник выпуска и сохранённый проверенный go.sum.

Как вычисляется h1 на нашем наборе

В закреплённой реализации Hash1 сначала сортируются полные имена файлов. Для каждого берётся SHA256 содержимого; из шестнадцатеричной суммы, двух ASCII-пробелов, имени и LF собирается строка. SHA256 объединённых строк кодируется Base64 и получает префикс h1:. В ZIP-случае имена включают example.invalid/BuildLab/checkdigit@v1.0.0/; метки времени и способ сжатия ZIP в эти строки не входят. Для GoModSum Hash1 получает отдельное имя go.mod и его содержимое.

Расчёт Python в памяти по трём неизменённым файлам labs дал ZIP длиной 1076 байт, ZIP SHA256 4dffbd44038124d82ddc27883031c00e15bd2e0c9af9314fa68aa4943aef0d59, сумму дерева h1:LTAoKXMBmOmv99QOELo/H5Zlr/qORFHhIv+0vpEwILk= и GoModSum h1:7N6+AU5JcOv5eZDVSGmtdeJUkCnPDIn8AwnDWlQ9VeM=. При обратном порядке ZIP-записей и дате 2 ноября вместо 1 ноября ZIP SHA256 стал 87cbcf12a4437037559901acac8058b7f05fb8abc249e05b4351bfd7a2e83421, а h1 сохранилась. Это модель алгоритма над конкретными fixtures, без нового запуска Go или Artifactory.

Предскажите два изменения по отдельности: перестановка записей сохраняет h1; добавление комментария в checkdigit.go меняет сумму содержимого и h1, даже если программа ведёт себя так же. Использовать новую h1 как ожидаемую можно только после принятия новых исходников. Закреплённый Hash1/HashZip определяет формат расчёта; наш пример не проверяет все ограничения промышленного ZIP.

Что означает клиент с новыми кэшами

GOMODCACHE хранит полученные исходники и служебные сведения модулей. GOCACHE хранит результаты компиляции. Чистый GOCACHE не означает чистого скачивания, а новый GOMODCACHE не стирает старый go.sum проекта. Для проверки происхождения пути создайте новую рабочую клиентскую папку, новые оба кэша и явно выбранный Go. Не выполняйте go clean -modcache в общем пользовательском окружении: это удалит чужой кэш и всё равно не изменит серверный remote.

Наш настоящий Go1.27.3 показал полезную последовательность. Mod tidy получил два протокольных объекта, первый build потребовал ещё один запрос, а второй идентичный build не создал новых HTTP-обращений. Значит, слово «прогрет» надо привязывать к конкретному набору действий. Новый GOMODCACHE снова потребовал сеть к fixture; GOPROXY=off с другим пустым кэшем завершился ненулевым кодом. Счётчик — обращения к авторскому loopback-источнику, а не измерение cache hit Artifactory.

Как модуль попадает в Artifactory

Обычный go build получает зависимости, но не публикует их в произвольный сервер. В принятом современном пути сначала jf go-config записывает resolver/deployer для проекта, затем jf go-publish v1.0.0 публикует исходный модуль в Go local. Resolver — выбранный источник зависимостей; deployer — выбранная цель публикации. Старые страницы встречают другую грамматику jf rt go-publish с явным аргументом репозитория; книга не смешивает её с современной корневой командой. Справка настоящего CLI2.129.0 и проверки собственных карточек фиксируют используемую форму.

На настоящем сервере после публикации запросите точную версию новым обычным клиентом Go, сравните принятые h1, содержимое go.mod и результат программы. Не заменяйте этот опыт PUT ZIP в Generic и не рисуйте «сервер создал метаданные» по одному успешному запросу к имитации. Автор не публиковал модуль в настоящий Artifactory; обе серверные стороны этой проверки остаются шагами читателя с действительной лицензией.
