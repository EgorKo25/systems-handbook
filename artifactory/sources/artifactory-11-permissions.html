Личность, permission target и право на конкретное действие

Эта глава стоит перед клиентскими операциями: необходимые учётные записи создаются заранее.

Кто проверяет запрос

Authentication, установление личности, отвечает на вопрос, кому соответствует предъявленный материал. Authorization, проверка полномочий, определяет, разрешена ли этой личности операция над данным ресурсом. Access управляет пользователями, группами, разрешениями и токенами платформы. Успешная проверка подписи токена не выдаёт права на любой репозиторий; успешный login не доказывает право overwrite. Scope — указанная область действия токена; audience — допустимый получатель; expiry — время истечения. Их проверяют вместе с актуальной моделью прав.

Permission target — именованное назначение прав на набор ресурсов и путей для пользователей или групп. Права складываются. Если один target не даёт delete, но другая группа его даёт, ожидаемого запрета нет. Virtual repository не имеет собственного permission target: запрос через него подчиняется правам на входящие local/remote. Поэтому скрыть ссылку на local в UI недостаточно; проверяйте чтение через virtual и прямой разрешённый путь отдельной личностью.

Подготовить своих читателя, издателя и принимающего

После первичного HTTPS-входа собственный администратор открывает Administration/User Management, создаёт три обычных локальных пользователя: receipt-reader, receipt-publisher, receipt-promoter. Они не администраторы. Случайные пароли задаются частно, никаких опубликованных рабочих credentials нет. Создайте три одноимённые группы назначения, включите каждого только в нужную группу и проверьте унаследованные grants. До создания репозиториев из главы разрешения сохраните план, затем назначьте physical repositories сразу после их создания; клиентские команды не выполняются, пока таблица ниже не реализована и не проверена.

В современном UI Permissions создайте target с понятным именем, добавьте физические repositories в Resources, затем пользователей/группы и действия. Для первого отдельного учебного Go repository используем всю его область, чтобы не угадать неверный внутренний layout по URL /api/go. Для Generic ограничьте path receipt/**, а для build ресурса — только собственный receipt. На шаге ограничения сверяйте реальное совпадение путей версии: URL пакета, storage path и build resource не одно и то же. Сначала попробуйте разрешённый и запрещённый собственные примеры. Если Go repository обслуживает ещё чужие модули, переход к узким путям требует отдельного такого теста.

Deploy/Cache у remote разрешает создание кэшированного объекта из upstream; это не разрешение публиковать новый файл в remote. Отсутствие Delete/Overwrite препятствует перезаписи выпущенных объектов по соответствующему договору; не распространяйте эту фразу на специальные изменяемые Maven snapshots или администратора. Annotate позволяет менять свойства и потому тоже является влиянием на сведения о выпуске. Manage позволяет раздавать некоторые права и не нужен обычной сборке. Права build-info и бинарных файлов выдаются отдельно: запись JSON не должна нечаянно открыть весь filestore.

Проверить сумму разрешений на одном пути

Пусть receipt-publisher имеет Deploy/Cache на generic-candidates/receipt/** и состоит ещё в группе release-maintainers с Delete/Overwrite на generic-releases/receipt/**. Отсутствующая галочка Delete/Overwrite в первом target не запрещает действие, разрешённое второй группой. Для отказа нужно убрать лишний grant или членство, затем новым запросом той же личности проверить существующий собственный release. Нельзя проверять издателя административной сессией браузера: она отвечает за другого субъекта.

Различайте три результата: новый кандидат разрешён; изменение его свойств разрешено Annotate; замена существующего release запрещена. Читатель, которому разрешено наполнять go-public cache, не получает от этого Deploy в go-local. Если сборочный издатель тоже должен получать новые публичные зависимости, ему отдельно нужны Read и Deploy/Cache на go-public; одной записи publisher→go-local из минимальной таблицы недостаточно. Для поставленного checkdigit без внешних зависимостей этот дополнительный путь не используется. Аддитивные permissions и физические ресурсы определяют эти проверки.

Токены имеют разные часы

В User Management/Access Tokens администратор создаёт короткоживущий scoped token для нужной обычной личности и сохраняет его только в защищённом клиентском store. Не выдавайте admin token CI. Reference token — короткая непрозрачная ссылка на токен на сервере; JWT содержит подписанные поля. Оба являются секретом предъявления. В Go/JFrog CLI конфигурации укажите username, чтобы клиент не должен был выводить его из формата непрозрачной строки.

Не обещайте мгновенный отзыв любого JWT. В текущем Access revocable-expiry-threshold по умолчанию 6 часов: токен с меньшим сроком не отзывается этой операцией и доживает до expiry; с достаточным сроком отзыв поддержан. Persistent-expiry-threshold имеет отдельное назначение хранения в БД и по умолчанию 3 часа; параметры связаны. Уменьшать их до 0 ради удобного теста означает менять нагрузку и поведение всех токенов. Для опыта отзыва выберите заведомо revocable token по фактической конфигурации, используйте только dummy lab identity и зафиксируйте повторный отказ нового запроса. Для краткого CI-доступа отдельно принят ограниченный срок и риск до истечения.

Изменение группы, отзыв токена, смена пользовательского пароля и удаление файла конфигурации CLI — разные действия. Удалённый локальный profile не отзывает уже скопированный секрет. Выданный refresh token способен продлевать доступ; не делайте его refreshable без необходимости. Проверка отзыва требует нового клиента без старого результата в кэше; чтение уже скачанного бинарника ничего не говорит о состоянии сервера.

Project и две границы инфраструктуры

Project, проект платформы, группирует ресурсы и роли команды. Он не является Git project и не создаётся из поля module path. Квоты проекта и общий storage — разные ограничения; число доступных проектов зависит от редакции. Наш малый опыт использует явно именованные repositories и группы без дополнительной project migration. Если ваш стенд уже project-scoped, каждый CLI/API запрос получает тот же project key, а доступ и sharing проверяются отдельно. Нельзя механически вставить --project в одну команду и считать все созданные вне проекта ресурсы перенесёнными.

Входящий client token не должен копироваться в поля remote credentials. Последние нужны серверу для upstream и имеют отдельную область, ротацию и доверие. Сеть ограничивает, к каким адресам вообще может обращаться сервер; repository configuration доступна только администратору, иначе remote URL способен стать каналом к внутренним сервисам. HTTPS client→Router не защищает автоматически SQL или upstream connection. Каждому соединению нужны собственные проверка адреса и права.

Журнал безопасности не равен доказательству происхождения

Audit trail — журнал значимых административных событий. Текущая документация указывает var/log/access-security-audit.log для изменений безопасности; логи запросов и событий других служб имеют другой состав. В нашем Pro X рецепте используются документированные self-managed логи, а не обещание Cloud log streaming, платного Evidence либо внешнего неизменяемого архива. Перед включением интеграции проверьте поддержку своей редакции и события собственной версии. Храните журналы вне прав обычного издателя, с временем и ограниченным сроком; отсутствие записи в выбранном файле не доказывает отсутствия операции.

Негативная приёмка: reader не может PUT в candidates, publisher не может заменить существующий release и не может стать администратором, отозванный revocable token не получает новый разрешённый GET. Сохраните только path/status/время/обезличенную личность. Ни эти серверные проверки, ни реальный аудит автором не запускались. Локальный fixture подтверждает передачу credentials и 401 при их отсутствии, но не исполняет permission model Access.
