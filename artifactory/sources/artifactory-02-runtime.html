Несколько процессов, одна платформа и несколько видов готовности

Порт, HTTP-статус и журнал показывают, какой компонент уже обработал запрос и где искать отказ.

Не переносить модель монолитного WAR

WAR — архив Java web-приложения. Установленная 7.x не сводится к одному старому WAR в вашем Tomcat. Поставка запускает несколько служб: Router маршрутизирует запросы между компонентами, Frontend обслуживает интерфейс, Access устанавливает личность и выдаёт токены, Artifactory обслуживает операции над репозиториями. Metadata, Event и Observability имеют свои обязанности по сведениям, событиям и наблюдению. Набор процессов зависит от версии и лицензии; не считайте список этой главы обещанием отдельного активного платного сервиса.

Router — маршрутизатор прикладных запросов, а не маршрутизатор IP вашей VM. Он принимает клиентский запрос на 8082, по пути выбирает службу и пересылает запрос внутрь. Access — служба идентификации и управления материалами доступа; она не является таблицей ACL в NGINX. База метаданных содержит логические связи, а filestore — файловое хранилище содержимого — сохраняет бинарные объекты. Перезапуск Frontend не восстанавливает пропавшие байты; расширение filestore не устраняет задержку SQL.

Один GET проходит через разных владельцев состояния

Пусть читатель запрашивает известный файл Generic по HTTPS. NGINX принимает TLS и передаёт HTTP на Router внутри этой VM; проверенное имя сертификата относится к первому соединению. Router выбирает Artifactory по пути /artifactory/…. Компонент, обслуживающий репозиторий, должен установить личность, проверить право Read, найти метаданные логического пути и получить связанное содержимое. Схема проверки Access в книге показывает зависимость от его модели безопасности; она не утверждает отдельный сетевой вызов Access на каждый GET. Внутренние проверки и кэширование зависят от реализации версии.

Если NGINX не соединился с Router, его 502 ещё не означает ошибку SQL. Если Router не нашёл готовый компонент, исследуют маршрутизацию и журнал компонента. Если запрос дошёл до проверки личности, 401 отделяют от отсутствия Read. Если ссылка нашлась, но файл хранилища недоступен, повторный login не создаст содержимое. Для разбора сопоставляют время, method, путь, статус и идентификатор запроса из доступных журналов обеих сторон; названия полей и включённый формат берут из своей версии. Саму строку Authorization в опись не включают.

Каталоги с разным сроком жизни

JFROG_HOME в нашем рецепте /opt/jfrog. Подкаталог artifactory/app содержит программы, сценарии и поставляемые компоненты. Подкаталог artifactory/var содержит изменяемую конфигурацию, данные и журналы. System.yaml находится в var/etc; ключи платформы — в защищённой области var/etc/security; default filestore — var/data/artifactory/filestore. Человек видит в UI путь generic-releases/receipt/1.0.0/receipt-linux-amd64, но такого дерева имён в filestore ожидать нельзя: соответствие хранит база.

«Неизменяемая app» — назначение поставки, а не автоматическая защита всех файлов chmod. Установка archive и vendor service scripts задают свои права; при ужесточении проверьте, что служба может писать нужные var, PID и журналы. Публичный образец system.yaml не содержит рабочего пароля. После первого старта платформа может заменить открыто заданный секрет в конфигурации зашифрованным представлением. Поэтому система управления конфигурацией не должна бесконечно возвращать файл назад, а резерв должен сохранять соответствующий ключ расшифрования.

Какие порты наблюдать

Внешние стандартные 8081 и 8082 не равноценны.8081 связан с Artifactory API,8082 с Router/UI/platform paths. Frontend обычно использует внутренний 8070, Access8040/8045, Metadata8086; дополнительные порты смотрят в network matrix своей версии. Клиенту не следует обходить маршрутизатор и открывать каждый внутренний порт наружу. Для личного single-node стенда внешний маршрут проходит SSH либо HTTPS reverse proxy; внутренние соединения остаются в VM. Прокси — принимающий запрос посредник, который передаёт его дальше, — не заменяет права Artifactory.

Администратор VM смотрит sudo ss -ltnp, состояние службы и sudo journalctl -u artifactory.service -n100 --no-pager. Ss показывает слушатели, не успешную обработку. Journalctl показывает ограниченный конец журнала службы; подробные события отдельных компонентов остаются в var/log. Перед публикацией фрагмента удалите секреты, реальные имена пользователей и инфраструктурные адреса. Запишите конкретный процесс, порт и время, а не только «Java работает».

Приёмка слоями

В VM обычный пользователь сначала проверяет curl --fail http://127.0.0.1:8082/artifactory/api/system/ping. Ожидается OK и код 0. Это не доказывает действительную лицензию Go или способность писать в БД. После настройки профиля в главе о CLI тот же смысл проверки имеет jf rt ping, использующий выбранные адрес и личность клиента. Он также не проверяет чтение всех репозиториев. Затем через защищённый UI подтвердите версию, редакцию, созданного своего администратора и готовность служб. После TLS и настройки читателя проверяется разрешённый GET известного файла. После выдачи отдельному издателю узких прав — публикация собственного объекта и его чтение новой клиентской конфигурацией. Последний шаг проверяет уже цепочку байтов, а не только health endpoint.

Health, readiness и бизнес-проверка отвечают на разные вопросы. Процесс может отвечать ping при недоступном удалённом источнике конкретного пакета. Readiness, готовность к предусмотренной работе, должна учитывать нужную зависимость; значение из одной версии API нельзя угадывать по другой. Ошибка 503 от Router требует выяснить доступность целевого компонента. Ошибка 401 после успешного TLS относится к установлению личности. Ошибка checksum после 200 переносит расследование к идентичности содержимого. Эти наблюдения не исправляются одной общей командой restart.

Остановка сохраняет экземпляр

Штатный stop прекращает процессы и соединения, но не удаляет репозитории, токены или файлы. Остановите службу через systemctl stop, дождитесь inactive и отсутствия процессов, которые ещё пишут var, затем обслуживайте хранилище. Не удаляйте var ради чистого запуска: так теряется идентичность и связь с БД. Ошибка первого старта не означает, что БД осталась пустой. Перед повтором исследуйте логи и уже созданные таблицы, сохраните диагностику; другая случайная master.key поверх прежней базы не является ремонтом.

На обновлении app можно заменить по поддержанному маршруту, но var и PostgreSQL имеют историю. Миграция схемы БД может лишить старую программу возможности читать новую базу. Поэтому возврат старого каталога app сам по себе не откат. Точный согласованный резерв и отдельный запуск восстановления разобраны позже. Уже сейчас журнал должен связывать исходную поставку, версию схемы, местоположение данных и время последней принятой публикации.
