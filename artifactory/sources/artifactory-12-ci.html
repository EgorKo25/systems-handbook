Go и CI: что передаётся между проверкой, хранилищем и выпуском

Один исполнитель производит кандидата, другой имеет право принять его.

Договор входов важнее названия плагина

CI, continuous integration, — автоматическое выполнение проверок интеграции изменений. Сборочный агент получает исходники определённого commit, проверенные Go/CLI, доступ к разрешённым репозиториям и ограниченные учётные данные. Commit — идентификатор состояния Git, но не идентификатор бинарника. Кандидат состоит из целевых байтов, manifest, сведений о фактической сборке и журнала проверок. Artifactory принимает эти объекты по своим API; он сам не выполняет ваши Go tests только потому, что поле build.status называется Passed.

В томе Go зафиксировано отличие отчёта от скомпилированного результата; GitLab cache/artifacts описывает транспорт между заданиями; Jenkins data flow — движение файлов на агенте. Кэш зависимостей ускоряет повтор, но не является release repository. Артефакт CI с коротким сроком хранения удобен для диагностики, но не заменяет принятый выпуск и его резерв.

Подготовленный исполнитель

Рецепты предполагают уже подготовленное личное окружение: известные версии Go и CLI по абсолютным путям JF_BIN/GO_BIN, Linux нужной архитектуры, доверенная CA, корректный HTTPS JF_URL и Go resolver go-virtual. Никакой скрипт не скачивает latest бинарник в каждой сборке. Для закрытой сети образ агента, runtime dependencies и полный набор модулей доставляются заранее и проверяются на новой клиентской GOMODCACHE. Наличие прогретого runner не считается доказательством полноты отключённой поставки.

Секрет выдаётся только защищённой ветке/тегу и доверенному коду задания. Masked variable скрывает известную строку в журнале, но вредоносный job может вывести преобразованный секрет либо переслать его: это не граница допуска недоверенного кода. Pull request из чужого fork не получает publisher token. Короткий срок токена уменьшает окно, но имеет описанную в главе прав границу отзыва. Для организации с принятым OIDC, обменом удостоверения задания на токен платформы, нужно отдельно настроить проверку issuer/audience/claims; книга не заявляет, что произвольный JF_TOKEN автоматически стал OIDC.

Рецепт GitLab

GitLab example копируется в собственный project только после адаптации пути исходников. Он рассчитан на service как корень рабочего проекта; в учебном монорепозитории надо сначала явно перейти в его каталог. JF_TOKEN задаётся защищённой переменной, JF_USER — обычный издатель, JF_CA_FILE — защищённая file variable с публичной CA, JF_URL — адрес личного стенда. Config home и временные части находятся в отдельной защищённой области рабочего каталога и не входят в artifacts.

CI_PIPELINE_ID становится номером build; path кандидата включает его, поэтому два повтора выпуска не перезаписывают одно и то же имя файла кандидата. Версия программы 1.0.0 при этом не меняется автоматически с номером задания. Рецепт выбирает только защищённый тегv1.0.0 и не публикует сам Go исходный модуль повторно при каждом запуске. Зависимость checkdigit v1.0.0 должна быть принята заранее. Ненулевой exit любого шага останавливает дальнейшие команды через set -e; это не транзакция над уже загруженными объектами.

After_script удаляет только два заранее выделенных своих клиентских каталога при непустом CI_PROJECT_DIR. Он не удаляет серверный build-info или опубликованные файлы. При требовании сохранения непубликованных частей для расследования сначала доставьте их в закрытую область по принятому процессу, а затем очищайте агент. Временные credentials не следует сохранять вместе с parts. Публичная часть журнала содержит обезличенные суммы и коды, не полную конфигурацию CLI.

Рецепт Jenkins

Jenkins example требует личного подготовленного агента receipt-prepared-linux и уже настроенного Credentials Binding. Credentials IDs создаёт владелец Jenkins; книга не обращается к реальному хранилищу секретов. Тройные одинарные кавычки Groovy передают shell-код без ранней интерполяции секретов Groovy. Shell получает JF_TOKEN в ограниченном блоке и передаёт его stdin. Многоарендный недоверенный агент всё равно не становится безопасным от этой формы кавычек; права на процесс/файлы и размещение заданий остаются частью стенда.

BUILD_NUMBER однозначен только в области выбранного Jenkins job. Если два независимых job используют Artifactory build name receipt и одинаковый номер, они способны смешать сведения. В реальном общем экземпляре включайте согласованную область команды/job в build name либо project key. Наши рецепты — альтернативные личные исполнения, не две независимые службы, одновременно пишущие один build. Для одного курса выберите одну CI и сохраняйте договор номера.

В обоих файлах реальные вызовы проходят через проверенный путь JF_BIN. Открываемые карточки разбирают их канонические формы: jf config add, jf go-config, jf go, jf rt upload и jf rt build-publish. Перед передачей токена трассировка shell отключена через set +x, поскольку Jenkins может запускать sh с -x; маскирование журнала не заменяет этого ограничения. Эти минимальные рецепты передают один бинарник и build-info. Полный набор с manifest, независимой приёмкой и отдельным promotion выполняется по главе о продвижении выпуска; автоматизация этих условий в CI остаётся осознанным расширением, а не приписанным свойством примера.

Почему promotion отдельно

Издатель имеет write только на candidates; отдельный принимающий получает право записи в releases. Его шаг использует те же candidate bytes и проверенный manifest, а не повторный build с похожими флагами. Отчёт качества, SBOM, список компонентов, либо provenance могут быть дополнительными условиями; каждый имеет собственный формат и доверенный источник. Включение --collect-env со всем окружением не является полезным дополнительным доказательством и способно утечь секретами.

Материальный отказ: кандидат загружен, а build-publish оборвался. Это ещё не подтверждённая связь выпуска. Другой отказ: build-info принят, а копирование второго файла в releases не завершилось. Это частичный promotion, даже если статус виден. Журнал должен позволять прочитать и сопоставить каждый объект, повторить только безопасную часть и отличить новое выполнение сборки от повторного HTTP-запроса. Автоматический uninstall/reset всей лаборатории таких причин не объясняет. Ни GitLab pipeline, ни Jenkins job автором не исполнялись; они требуют своего сервера, агента и выданных прав.
