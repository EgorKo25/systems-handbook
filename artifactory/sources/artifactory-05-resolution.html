Local, remote и virtual: кто решает, откуда получить имя

Порядок разрешения, отрицательный кэш и разрешения источников влияют на результат.

Три объекта создаёт администратор

Local repository, локальный репозиторий, хранит опубликованные в этот экземпляр объекты. Remote repository, удалённый репозиторий-посредник, описывает внешний источник и его кэш. Upstream — этот исходный внешний сервер. Virtual repository, виртуальный репозиторий, объединяет подходящие источники под одним адресом разрешения пакетов. Виртуальный адрес не является копией их содержимого. Создание remote не скачивает все существующие версии: он получает требуемые объекты по запросу.

В Administration/Repositories своего лицензированного экземпляра создайте Go local go-local. Создайте Go remote go-public с URL https://proxy.golang.org и Git Provider Artifactory: это выбор протокольного зеркала Go, а не GitHub VCS. VCS, version control system, — система контроля версий; Go proxy и VCS имеют разные запросы. Затем Go virtual go-virtual объединяет go-local/go-public, default deployment repository указывает go-local. В описанном маршруте Artifactory 7.x обычный Go-клиент получает зависимости через local или virtual. Наш go-public включён в go-virtual; native Go не направляем на его remote URL. Наличие строки remote=yes в общей таблице package types не отменяет эту специальную границу клиента.

Репозитории Generic generic-candidates/generic-releases создаются отдельно. OCI oci-local добавляется только в соответствующей главе. Файлы JSON в fixtures сохраняют минимальные задуманные настройки local/virtual для API, но здесь настройка через UI требует сопоставить ключи и фактическую принятую конфигурацию. Сам факт разбора JSON локально не доказывает серверную схему, лицензию или созданный репозиторий. Не включайте remote для частного префикса без необходимости; include/exclude patterns, шаблоны отбора путей, не заменяют права доступа.

Порядок не сводится к одному списку

Для обычного виртуального разрешения документирован общий порядок: local repositories, затем remote caches, затем сами remotes. Порядок внутри категорий определяется выбранным списком. Поэтому перестановка remote над local в UI не обязательно делает сетевой источник первым. Для запросов latest, динамических метаданных и специфических package types существуют дополнительные правила; не переносите модель фиксированного пути на поиск самой свежей версии. Priority Resolution, приоритетное разрешение, — отдельная настройка ограниченного формата, не универсальная гарантия безопасности. Наш выпуск использует фиксированную версию и не создаёт две разные реализации под одной координатой.

Исключение частного префикса из публичного remote снижает риск отправки имени наружу и случайного получения одноимённого чужого пакета. Оно не освобождает от проверки GONOPROXY на клиенте: клиент способен обойти Artifactory раньше, чем сервер увидит запрос. И наоборот, клиентская защита не запрещает администратору remote отправлять обращения другому upstream. Обе стороны цепочки должны соответствовать договору.

Положительный и отрицательный кэш

Содержимое запрошенного immutable ZIP сохраняется отдельно от изменяемых метаданных списка версий. Immutable означает договор неизменности конкретной версии; серверная политика и права должны его поддерживать. Metadata Retrieval Cache Period определяет период повторной проверки истекающих метаданных, а не время жизни каждого файла. Missed Retrieval Cache Period сохраняет факт 404: уже отсутствующий объект не запрашивается заново до истечения этого окна. По текущей документации срок отрицательного ответа по умолчанию1800 секунд; фактическую принятую настройку своего remote запишите в журнал.

Издатель опубликовал новую версию upstream через секунду после 404? Запрос Artifactory может ещё видеть отрицательный кэш. Чистка GOMODCACHE клиента не меняет состояние remote. Повтор команды десять раз не ускоряет срок. Сначала установите, какой источник и какой слой отвечает: клиент, virtual, remote-cache или upstream. Смена upstream URL при прежнем кэше также не гарантирует немедленную смену всех метаданных. Zap cache — инвалидирование определённых метаданных, а не удаление всех бинарных объектов. Без понимания этого различия оператор способен и потерять нужные файлы, и сохранить причину отказа.

Посчитать обращения при отрицательном ответе

Возьмём один точный путь версии, одну личность и неизменную конфигурацию; в local этой версии нет. В условном опыте Missed Retrieval Cache Period равен 30 с. В t=0 запрос дошёл до upstream и получил 404. В t=5 издатель добавил объект upstream. В t=7 новый клиент снова запросил тот же путь: сервер ещё может вернуть сохранённый 404 без второго обращения наружу. В t=31 истекший отрицательный результат уже не запрещает новую попытку; успешный ответ наполняет кэш содержимым. Здесь три клиентских запроса, два запроса upstream и один успешный download. Это расчёт состояния, не замер работающего Artifactory; 30 с не меняют документированное умолчание 1800 с.

Теперь измените ровно одно условие: в t=6 опубликуйте требуемую координату в доступный go-local. Общая модель local→cache→remote позволяет найти её до обращения к отрицательному remote cache. Если при этом Go вообще не отправил запрос из-за своего GOMODCACHE, вы наблюдаете другой опыт. Поэтому журнал содержит точный путь каждого объекта .info/.mod/.zip и источник ответа; общего счётчика «сборка успешна» недостаточно для диагноза кэша.

Offline имеет несколько значений

Флаг Offline у remote запрещает попытки получения отсутствующего удалённого объекта и позволяет выдачу сохранённого. Assumed offline — временное предположение после сетевого отказа, имеющее свой период повторной проверки. Это разные состояния. Оба не гарантируют, что все .mod/.info/.zip, запросы sumdb, нужные версии Go, OCI platform manifests и их blobs уже присутствуют. Одна удачная сборка при отключённом интернете может использовать только заполненный клиентский кэш, вообще не проверив сервер.

Приёмка отключённого набора начинается с полного перечня входов выпуска и новой клиентской GOMODCACHE, отдельной от авторской. Сохраните журнал серверных/upstream обращений, отключите только предусмотренный upstream по плану своей VM и повторите фиксированный запрос. Проверьте также намеренно отсутствующую версию: её ошибка подтверждает границу, а не неисправность стенда. В книгу не включены ОС-пакеты, исполняемые файлы клиентов, registry images или все публичные Go modules; автономное чтение не равно готовой air-gap поставке.

Отказ выбора и отказ доступа

Путь может существовать в одном local, но быть недоступен конкретному читателю; virtual не должен превращаться в обход его прав. Общая ошибка ответа об отсутствии объекта не доказывает отсутствие байтов у администратора. Используйте специально ограниченную личность, сохраните статус и путь, сопоставьте policy.403 не повод добавить direct fallback в публичный интернет. Неисправный TLS upstream, upstream401 и cached404 имеют разные причины. Ремонт начинается с минимального собственного запроса и журналов на точной границе, не с расширения всех разрешений.
