OCI: другой протокол, другой манифест и отдельная приёмка

Передадим файл как OCI-артефакт, не называя его готовым контейнерным образом.

Какие объекты передаются

OCI, Open Container Initiative, задаёт семейство форматов и протоколов. Registry — сервер передачи объектов по протоколу распределения. Blob — сохраняемый объект содержимого; descriptor, дескриптор, связывает mediaType, размер и digest; digest — идентификатор, включающий алгоритм и хеш точных байтов. Манифест перечисляет конфигурацию и слои. Тег — именованная ссылка на манифест, которую политика может позволять заменить. Это не идентичность содержимого. Индекс способен перечислять несколько платформенных манифестов; его digest отличается от digest Linux amd64 варианта.

Наш исполняемый файл можно передать как произвольный OCI-артефакт с заданным типом, но это не создаёт image config/root filesystem/entrypoint для запуска контейнера. Для контейнерного варианта следуйте сборке образа Go с теми же принятыми байтами и затем проверяйте отдельный image digest. Поле architecture=amd64 в произвольном JSON не превращает arm64 binary в amd64. В этом томе ОС и архитектура файла записаны в manifest выпуска, а формат OCI переносит этот файл отдельно.

Получить ORAS до его использования

ORAS — клиент передачи произвольных артефактов в OCI. Он не требует Docker daemon для локального формата OCI layout. Выбрана версия 1.3.6 от 24 октября 2026. Сценарий получения работает в отдельном Bash с set -euo pipefail и не устанавливает ничего глобально. Из собственной labs выполните bash recipes/get-oras.sh "$HOME/artifactory-handbook/tools". Он получает Linux amd64 tar, проверяет SHA256 66fb0ad7206f3f6fa77ed5b552049d364ccf4b50b1684554f731f76302b52ca0, извлекает только oras и запускает version. При ошибке получение/извлечение/запуск прекращаются. Для иной ОС нужен другой проверенный архив.

Автор фактически получил архив, сравнил его с опубликованным checksum и исполнил клиент. Подпись release key и GitHub provenance этого архива дополнительно не проверялись; это явно ограниченная проверка происхождения. Перед опытом команда oras version должна показать 1.3.6; другой файл нельзя принять только по имени. ORAS_BIN далее указывает на проверенный файл, а функция oras() { "$ORAS_BIN" "$@"; } сокращает запись только в текущей оболочке. Секреты registry не наследуются из случайного общего docker/config.json: выбираем свой --registry-config.

Локальный OCI layout — настоящий формат без сервера

OCI layout — каталог с oci-layout, index.json и blobs по digest, определённый спецификацией хранения на диске. Это не Artifactory filestore и не его резервная копия. После создания release/ предыдущей главы можно в своей постоянной папке выполнить блок ниже; здесь файл не отправляется в сеть. Подкаталог oci-layout должен быть новым либо принадлежать этому же продолжаемому опыту, а не случайным чужим данным.

(
  set -eu
  cd "$LAB_WORK/release"
  "$ORAS_BIN" push --oci-layout "$LAB_WORK/oci-layout:1.0.0" \
    --artifact-type application/vnd.handbook.receipt.v1 \
    --annotation org.opencontainers.image.created=2026-11-01T00:00:00Z \
    receipt-linux-amd64:application/octet-stream manifest.json:application/json
  "$ORAS_BIN" manifest fetch --oci-layout --descriptor "$LAB_WORK/oci-layout:1.0.0"
)

Буквальные команды справочника: oras push создаёт/передаёт артефакт, oras manifest fetch читает манифест или его дескриптор. Сдвиг digest после изменения даты аннотации допустим: изменились байты манифеста. Зафиксированная дата здесь лишь делает опыт сравнимым, а не утверждает фактическое время production build. Публичный тест использует две маленькие собственные текстовые fixture, не включает бинарник книги.

Настоящий ORAS в авторском тесте создал 753-байтовый manifest и два слоя, Python независимо сравнил длины и SHA256, а oras pull по digest восстановил точные файлы. После намеренной порчи слоя pull завершился ошибкой; после удаления слоя — тоже. Смена прав 0444 на собственном временном blob потребовалась только для отрицательного опыта. Не переносите такую порчу на живое хранилище. Эти результаты подтверждают работу локального формата и клиента, не совместимость Artifactory или готовый registry.

Подготовить registry route в своём Artifactory

В Administration/Repositories создайте Local с Package Type OCI и ключом oci-local: без больших букв и underscore. Выдайте издателю Read/Deploy/Annotate, читателю Read, не выдавайте overwrite. Для Pro X выбранный тип входит в универсальную поддержку; JCR также имеет OCI, но остаётся непригодным для нашей Go-части. Нельзя подменить native OCI repository Generic-каталогом с JSON.

Для self-managed reverse proxy используйте документированный Repository Path Method. В Administration/HTTP Settings задайте Nginx, внутренние Artifactory8081/Router8082, Public Server Name aft.lab.example, HTTPS443 и Docker Reverse Proxy Method Repository Path. Сохраните и скачайте сгенерированную конфигурацию. Сопоставьте в ней реальные пути server.crt/server.key из главы об адресах и TLS, upstream и внешнюю базу. Сделайте защищённую копию прежнего своего конфигурационного файла, затем замените единственный /etc/nginx/conf.d/artifactory.conf новым, а не добавляйте второй конфликтующий server. После nginx -t и только при успехе reload применяет его. Если generator вашей версии отличается, сверяйте официальный раздел path method до передачи токена; базовый nginx-api.conf сам по себе здесь не выдаётся за завершённую registry-настройку.

Внешняя ссылка выглядит как aft.lab.example/oci-local/receipt:1.0.0. Клиент сначала обращается к /v2/, получает указание авторизации с областью репозитория, получает пригодный токен и передаёт blobs/manifest. Адрес выдачи токена должен указывать на ваш принятый HTTPS-host. Переадресация к неожиданному host или localhost — ошибка конфигурации, не повод автоматически отключать защиту realm. ORAS1.3.6 различает допустимые частные адреса и опасные loopback/link-local endpoints.

По каким байтам клиент проверяет граф

После авторизации чтение манифеста использует GET /v2/ИМЯ/manifests/ССЫЛКА; ссылка — тег либо digest. Ответ сообщает тип содержимого, а тело — точные байты JSON. Получение по сохранённому sha256 требует сравнить его с SHA256 этих байтов, без повторной сериализации JSON. Затем каждый descriptor задаёт mediaType, size и digest дочернего объекта; blob читают по /v2/ИМЯ/blobs/DIGEST и проверяют отдельно. HEAD позволяет проверить наличие и сведения об объекте, но не заменяет проверку тела.

В историческом локальном ORAS-опыте manifest имел размер 753 байта и digest sha256:558a8bd177436de7e76b9e345fd6bee3ddb8a7c40fdb6ddca21cc8ea22779c62; эти числа относятся к двум маленьким текстовым fixtures, не к вашему executable. Перенос строки в JSON может изменить manifest digest при тех же дочерних файлах. Для push клиент обычно передаёт blobs до манифеста; незавершённая загрузка не делает тег пригодным выпуском. Потерянный ответ проверяют чтением ожидаемого digest. Distribution 1.1.1 описывает запросы; конкретную поддержку Artifactory принимает отдельный серверный опыт.

Настоящая публикация и получение остаются рецептом

В защищённой оболочке publisher передайте scoped token через stdin в oras login aft.lab.example --username receipt-publisher --password-stdin --ca-file "$LAB_WORK/private/ca.crt" --registry-config "$LAB_WORK/private/oras-publisher.json". После успеха из release выполните push к aft.lab.example/oci-local/receipt:1.0.0 с теми же файлами, artifact-type, ca-file и registry-config. Сохраните полученный digest манифеста. Отдельный reader profile и пустой принимающий каталог выполняют pull по @sha256:ФАКТИЧЕСКИЙ_DIGEST; имя digest не копируют буквально из примера.

Приёмка сравнивает полученные файлы с доверенным manifest и сам сохранённый descriptor. Запрос по тегу удобен, но не закрепляет объект навсегда. Для многоплатформенного образа проверьте индекс, выбранный platform manifest и полное множество blobs, а не только один успешный pull на своей архитектуре. Локальный OCI layout не доказывает наличие этого множества в отключённом registry. Push/pull/login к настоящему Artifactory, его rights и конкретная NGINX-конфигурация автором не исполнялись.
