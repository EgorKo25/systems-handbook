Согласованный резерв: PostgreSQL, filestore, ключи и отдельная цель

Файлы должны описывать один принимаемый момент, а не несколько случайных состояний.

Что необходимо вернуть вместе

База хранит отображение логических путей на содержимое, права и другие необходимые сведения платформы. Filestore сохраняет байты. Конфигурация определяет, где они находятся и как соединяются службы. Master key, главный ключ шифрования, необходим для чтения зашифрованных секретов; join key участвует во внутреннем доверии служб. Подписывающие ключи, идентичность Access и принятые отношения доверия тоже имеют срок жизни. Новый случайный ключ не расшифрует старые credentials. Поэтому «у нас остались SHA1-файлы» и «у нас осталась только PostgreSQL» — две неполные копии: в первой нет имён и прав, во второй нет содержимого артефактов.

Встроенная system backup/export и резерв компонентов — разные способы. Текущая документация рекомендует раздельные компоненты для больших экземпляров; полная выгрузка логических файлов способна потерять экономию дедупликации и потребовать больше места, чем основной filestore. В 7.66+путь встроенного backup не должен начинаться с JFROG_HOME/artifactory. Каталог резерва не является местом для чужих файлов: автоматический retention способен их удалить. Наличие Export Exclude Content прямо означает отсутствие бинарного содержимого, а не магическую компактную полную копию.

Малый холодный резерв нашего стенда

Холодный резерв создаётся при остановленных писателях. У нашего single-node Pro X default filestore лежит внутри var, а PostgreSQL artifactory — единственная выделенная приложению база. Это проверяемые предпосылки, не универсальный скрипт для HA/S3/дополнительных databases. До запуска опишите все переопределённые service databases, binary providers и внешние пути. Если они есть, приведённый сценарий неполон и не запускается как принятая процедура.

Владелец VM закрывает новые публикации в своём процессе, сохраняет последнюю опись release/build-info/hash и выбирает новый каталог на независимом носителе вне /opt/jfrog. Затем из labs выполняет bash recipes/backup-vm.sh /ПУТЬ_СВОЕГО_НОВОГО_РЕЗЕРВА. Сценарий остановит Artifactory, проверит отсутствие активной службы и процессов выделенного пользователя, оставит PostgreSQL работающим, сделает pg_dump и архив var. Он работает с set -euo pipefail и не продолжает после отказа. Он не запускает сервер обратно автоматически: результат и состояние читает владелец, затем отдельно принимает start.

Pg_dump --format=custom создаёт согласованную логическую выгрузку выбранной SQL-базы. Pg_dumpall --globals-only сохраняет кластерные роли и может содержать хеши паролей: весь комплект конфиденциален. Tar сохраняет var вместе с default filestore, конфигурацией, ключами и журналами. Между остановкой и завершением копии не должно быть другого узла, процесса, scheduled cleanup или ручного изменения, влияющего на тот же набор. Живая копия каталога PostgreSQL без принятого DB snapshot/WAL-процесса здесь не используется.

SHA256SUMS внутри резерва проверяет сохранённые файлы; опись также должна иметь доверенную отдельно защищённую сумму или подпись. Если злоумышленник может заменить весь комплект вместе с описью, одна sha256sum --check не установит происхождение. Сохраните version/edition, system.yaml, полный список external paths, времена остановки/начала/конца и согласованный журнал. Вторая копия master key хранится отдельно защищённо. Не включайте этот резерв в публичную книгу или обычные artifacts CI.

Восстановить в изолированной машине

Цель — новая собственная VM без доступа к исходной БД, replication peers и внешним получателям. Изоляция устанавливается до первого старта: копия несёт прежние ключи и идентичности, поэтому два таких узла не должны случайно соединиться. Не направляйте restore в исходную /opt/jfrog и не используйте те же внешние storage credentials. Внутри отдельной сети можно сохранить принятую модель имени, но клиентский DNS явно указывает только на clone. Запишите решение о первоначальном fencing, отключении исходной стороны от целевого потока записи.

Установите ту же 7.161.20 из проверенного архива без старта и PostgreSQL16 совместимой принятой версии. Создайте только роль artifactory: откройте sudo -u postgres psql --set ON_ERROR_STOP=1, выполните CREATE ROLE artifactory LOGIN;, затем \password artifactory и \q. Команду CREATE DATABASE из главы об установке пока пропустите: новая база создаётся один раз в блоке восстановления ниже. Используйте сохранённый секрет роли либо осознанно замените DB credentials в восстановленной частной конфигурации. Не импортируйте globals.sql вслепую поверх чужого кластера: он содержит другие роли, в том числе уже существующего postgres. Для этой выделенной новой цели требуются именно роли и владельцы приложения из описи.

Далее в оболочке VM проверьте внешнюю доверенную сумму комплекта, затем его SHA256SUMS. До извлечения вновь подтвердите отсутствие процесса Artifactory. Первоначальный var из свежей незапущенной поставки переместите в отдельный quarantine-каталог, не накладывайте две истории. Извлеките artifactory-var.tar.gz под /opt/jfrog, сохраните владельца artifactory и закрытые права ключей. Измените только необходимые адреса изолированной цели, в частности shared.node.ip и JDBC URL; не генерируйте master/join заново ради исчезновения ошибки.

Обычный владелец закрытой копии в своей оболочке Bash задаёт PRIVATE_BACKUP действительным путём уже проверенного каталога. Именно его оболочка открывает dump до смены личности sudo; пользователь postgres читает стандартный ввод и не получает доступ ко всему частному каталогу.

(
set -euo pipefail
PRIVATE_BACKUP='/ПУТЬ_СВОЕГО_ПРОВЕРЕННОГО_РЕЗЕРВА'
test -r "$PRIVATE_BACKUP/artifactory.dump"
sudo -u postgres createdb --owner=artifactory --encoding=UTF8 artifactory
sudo -u postgres pg_restore --exit-on-error --dbname=artifactory \
  < "$PRIVATE_BACKUP/artifactory.dump"
)

Этот блок применяется только к новой пустой выделенной БД после роли. Existing database error останавливает план: не добавляйте --clean наугад. При ошибке pg_restore зависимый start запрещён; сохраните лог частно, восстановление повторяется в новой пустой цели по принятому плану, не поверх частично восстановленной. В PostgreSQL custom dump возвращает владельцев объектов, поэтому нужные роли должны существовать. Если реальные данные распределены по нескольким databases, восстановите согласованный полный набор из их отдельной описи; наш минимальный рецепт этого не угадывает.

Как принять результат

На clone служба запускается только после DB+var+keys и сетевой изоляции. Проверяйте status/logs, расшифрование конфигурации, собственный вход и отрицательные права, затем build-info receipt/1, логические пути и точные SHA256. Новый Go client должен получить прежний модуль, новый reader — прежние бинарник и manifest; OCI проверяется по прежнему digest и всем его слоям. Запуск UI без этих чтений не является восстановлением выпуска. При ошибке не запускайте GC/repair, чтобы «удалить битые записи»: сначала выясните полноту и соответствие копий.

RPO — допускаемая потеря последних данных; RTO — целевое время возврата функции. Запишите фактический диапазон принятых записей и время до успешной клиентской приёмки. Любая запись после контрольной точки требует решения о переносе/повторе; откат к резерву их автоматически не сохраняет. Авторская SQLite-модель действительно восстановила пару метаданные/байты и отклонила отсутствующий blob, но не проверяла PostgreSQL, Access keys, миграции либо настоящий Artifactory restore. Серверный опыт этой главы остаётся неисполненным.
