Чередование потоков и потерянное обновление

Как два правильных по отдельности вычисления теряют одно изменение.

Два потока увеличивают один счётчик

Пусть A и B обслуживают по одному увеличению общего счётчика. На одном ядре планировщик может отдать процессор B сразу после чтения A. A продолжит позже с прежним значением в своей переменной. На двух ядрах оба чтения могут выполняться параллельно. В обоих случаях проверим, что именно каждый поток прочитал до первой записи.

В counter.bin лежат четыре байта 2a 00 00 00. Младший байт записан первым, поэтому число равно 42. Программа загрузила его в общий объект с учебным адресом 0x00403124. После одного запроса ожидаем 43 (2b 00 00 00), после двух — 44 (2c 00 00 00). Пока будем менять только общий объект в памяти.

Прибавление скрывает несколько разных изменений

Каждый поток выполняет три шага по порядку: читает общее число, прибавляет единицу в личной переменной, записывает личный результат обратно. Назовём их A1, A2, A3 и B1, B2, B3. В модели отдельное чтение и отдельная запись атомарны. Все видят их в одном порядке. Между чтением и записью A планировщик может пропустить любое допустимое число шагов B.

На шаге B2 общее число ещё 42, хотя оба уже приготовили 43. На шаге B3 запись A цела, но B пишет то же число, вычисленное по своей старой копии. Один запрос потерян. Перенесите B1 после A3: B прочитает 43 и дойдёт до 44. В последовательном варианте лаборатории поменяется только порядок шагов.

Гонка результата и data race — разные утверждения

Здесь гонка результата сохранилась при атомарных обращениях. Если заменить общий объект обычной переменной в C++, те же обращения без синхронизации могут образовать data race, гонку данных. Для неё нужны конфликтующие потенциально конкурентные действия, среди которых хотя бы одно неатомарно, и ни одно не предшествует другому в смысле happens-before, необходимого порядка по правилам языка. В этом примере гонка данных приводит к неопределённому поведению по правилам C++. Ограничивать исходы цифрами 43 и 44 уже нельзя.

Например, в C++ показанный путь можно воспроизвести с отдельными последовательными атомарными load и store одного счётчика. Несколько таких обращений подряд остаются отдельными действиями: B способен прочитать значение между A1 и A3. Браузер дальше перебирает именно этот договор, без моделирования компилятора и аппаратной перестановки. Модель гонки данных в рабочем проекте C++.

Что именно защищаем

Пока нет переполнения, после N завершившихся прибавлений, когда других прибавлений в работе нет, счётчик должен быть равен 42 + N. В схеме с двумя чтениями 42 после B3 получаем 43 при N=2. Этот инвариант проверяет результат операции целиком. Сделать только A3 и B3 неделимыми недостаточно, потому что устаревание началось на B1.

Если считать каждое успешное увеличение одной логической операцией, два завершения должны выглядеть как «A, затем B» либо «B, затем A». Обе последовательности дают 44. Итог 43 невозможно расположить таким образом. При поиске линеаризации действует и временное условие: если A успел ответить до вызова B, логический порядок обязан поставить A первым.

Изменение общей памяти ещё не изменило файл

Когда counter.bin читают два процесса, у каждого может остаться собственный буфер с 42. Если открытие начало чтение с нуля и получило четыре байта, его текущее смещение стало 4. Запись нового числа в начало потребует, например, позиционной записи на смещение 0. Это исправит место записи. Но если оба вычислили 43 до первой позиционной записи, второй по-прежнему сохранит 43 поверх 43.

Чтобы проверить этот путь в программе, удержите оба потока в тесте после A1 и B1, затем разрешите продолжить. В модели результат можно предсказать заранее: оба личных значения уже 42, поэтому без повторного чтения выбор последней записи ничего не меняет. Один произвольный запуск с итогом 44 не проверяет этот разрыв.

Вычислить все порядки нашей модели

Внутри A порядок A1 → A2 → A3 фиксирован, как и B1 → B2 → B3 внутри B. Чтобы задать общую историю, выберите три из шести позиций для A. На оставшихся стоят шаги B в своём порядке. Поэтому вариантов 6!/(3!×3!) = 720/(6×6) = 20. Факториал n! перемножает числа от 1 до n.

Итог 44 требует, чтобы одна запись 43 произошла раньше чтения второго участника. Для этого все три шага первого должны стоять до начала второго. Подходят два порядка: A1 A2 A3 B1 B2 B3 и B1 B2 B3 A1 A2 A3. Во всех остальных 18 историях оба читают 42. Порядки реального планировщика не обязаны встречаться одинаково часто, поэтому доля 18/20 сама по себе не является вероятностью ошибки.

Для трёх потоков с тремя шагами было бы уже 9!/(3!×3!×3!) = 1680 общих порядков. Это количество расписаний при заданных шагах, без учёта более слабых правил видимости памяти. Если проверяемая реализация допускает наблюдения вне одного общего порядка, перебор именно этих последовательностей их пропустит.

От личной переменной до сохранённого файла

Проследим 43 за пределами таблицы. После A2 оно есть только у A. После A3 оно уже в общей памяти, а в файле ещё могут оставаться байты 2a 00 00 00. Когда позиционная запись отправит 2b 00 00 00 в файловую систему, новое содержимое может быть видно через кэш. Чтобы обещать восстановление после сбоя, нужно отдельно выполнить и проверить требуемую синхронизацию файла и, если менялась запись каталога, соответствующие шаги для неё.

Если в каждом процессе свой mutex, оба могут войти в защищаемый участок одновременно. Для изменения файла всем писателям нужен общий механизм исключения либо один уполномоченный писатель. Во втором варианте два запроса стоят в одной очереди. Тогда место второй операции видно явно, но приходится выбирать размер очереди, момент подтверждения приёма и порядок восстановления при отказе писателя.

Обновление разных счётчиков в одной линии кэша

Представьте два независимых атомарных счётчика рядом в памяти. A обновляет только первый, B только второй. Если оба лежат в одной линии кэша и потоки работают на разных ядрах, владение этой линией может переходить между ядрами при каждой смене писателя. Так выглядит ложное совместное использование (false sharing). Размер линии нужно брать из характеристик конкретной машины.

Для проверки сравните одну и ту же работу с соседними и разнесёнными счётчиками, сохранив ядра и объём обновлений. Сравнивайте число обновлений за секунду и, если доступны счётчики платформы, передачи линий. Дополнительно проверьте рабочий объём памяти: разнесение, ускорившее обновления, может ухудшить другие обходы массива.

Проверяемая модель

Откройте лабораторию чередований. В опыте «Два увеличения» выберите «Потерянное обновление» и нажимайте «Дальше». Сверьте A2 и B2 с таблицей: в обеих личных переменных уже 43, а общее число ещё 42. Дойдите до конца и получите 43. В «Последовательном пути» проверьте, что B читает после A3 и в итоге записывает 44. Затем выберите «Одна атомарная прибавка»: общее число меняется 42 → 43 → 44, а текст показывает, какое прежнее число получил каждый поток. «Сводка всех 20 порядков» покажет 2 истории с 44 и 18 с 43. В схеме над упражнением локальная прибавка и запись сгруппированы в один показанный шаг, поэтому промежуточное состояние после B2 видно отдельно именно в таблице и лаборатории.

Предскажите результат

A прочитал 42, B целиком закончил увеличение до 43, затем A записал свою прибавку. Поможет ли сделать только запись A атомарной?

Разбор

A всё равно запишет 43: его чтение осталось прежним. Общая блокировка должна охватить чтение и запись обоих участников. Другой путь — атомарная операция «прочитать, изменить и записать», которая на втором шаге возьмёт текущее 43.

В следующей главе проверим, где проходит граница атомарной прибавки и какие дополнительные условия нужны, если A вместе с числом передаёт B другие данные.
