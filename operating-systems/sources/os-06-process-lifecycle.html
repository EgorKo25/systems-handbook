Создание, загрузка и завершение экземпляра

В предыдущей главе T1 уже могла вызвать read. Вернёмся к моменту, когда P0 только запросил запуск. На каких шагах появляется T1, когда она получает CPU и что остаётся после завершения?

Запросить запуск ещё не значит получить готовую работу

P0 хочет запустить counter-reader. Для этого ОС нужна область памяти, куда попадут код и данные, начальный стек и запись первого потока с точкой входа. Пока эти части готовятся, пользовательский код T1 ещё не исполняется. После публикации T1 готова получить процессор. Только при исполнении она сможет открыть counter.bin, подготовить буфер 0x00403124 и вызвать чтение, с которого началась предыдущая глава.

Частичное создание: кому убирать уже выделенное

В учебной модели P0 сначала просит создать P1 с подготовительной программой launcher. Состояние читается по полям «Объекты операции создания» и «Опубликованные объекты». Первая показывает, что уже выделено для работы, вторая — что продолжит жить после самой операции.

При уборке сначала снимают приобретённые ссылки и отображения, затем освобождают основные записи. Если P0 уже удерживает общий открытый объект, отмена убирает только ссылку, добавленную для P1. В сцене частные записи исчезают одним шагом. Он показывает передачу владения, а порядок блокировок и публикации настоящего ядра здесь не моделируется.

Начальная среда тоже является входом

Пусть P0 дважды запускает один и тот же образ с аргументом counter.bin, но в разных текущих каталогах. Относительный путь может открыть разные файлы. Окружение тоже влияет на результат, например если программа выбирает локаль или ищет вспомогательные файлы по переданным параметрам. При переносе запуска из оболочки в менеджер служб сверяйте эти значения у самого экземпляра, который получил управление.

Уже открытый файл может перейти к ребёнку по унаследованному дескриптору. Тогда текущий каталог не участвует в повторном выборе объекта. Если P1 удерживает ссылку, закрытие соответствующего дескриптора в P0 ещё не освобождает общее открытие.

Создать ещё один процесс и заменить текущую программу

После публикации в сцене видны P1 и образ launcher. На следующем шаге в той же записи P1 появляется counter-reader. Следите за двумя полями. «Ребёнок» остаётся P1, «Образ» меняется. Метка AS1 относится к адресной среде этого экземпляра. Прежние страницы, стек и переменные подготовительной программы не переносятся в новый образ из-за сохранения этой метки.

Чтобы запустить новый код из уже работающего процесса, нужна предусмотренная операция замены. Обновление файла программы по прежнему пути на диске само по себе такой операции не выполняет.

Названный пример: fork, exec и wait

В Linux оболочка может создать ребёнка через fork. Затем ребёнок вызывает execve с путём, аргументами и окружением новой программы. P0 может ждать через waitpid. В отличие от ветви LOAD_FAILED учебного создания, после успешного fork ребёнок уже существует, даже если следующий execve в нём не удался.

Текстовый путь. P0 запрашивает создание, P1 с образом launcher публикуется с T1, затем P1 получает образ counter-reader. После выхода P1 остаётся результат 7 до получения его P0. При отказе до публикации результатом самой операции является LOAD_FAILED.

В ветви «Создание → замена → ожидание» пройдите до «P1 прекратил исполнение». Поле результата показывает 7, а в опубликованных удержаниях остаются результат P1 и ссылка P0→P1. На шаге «P0 получил результат» эти удержания исчезают, число 7 на экране остаётся как уже полученный итог. В ветви «Отказ до публикации» дождитесь «Образ не принят» и проверьте, что записи очистились и ожидать ребёнка некого.

Разобрать два возврата fork и один отказ exec

Успешный fork возвращает P0 положительный PID ребёнка, а продолжению P1 — ноль. При ошибке только P0 получает -1 и errno. Кто исполнится первым после успеха, из возвращённого числа не следует. В execve успешная замена начинает новую программу. Обычный отказ возвращается старому коду. Например, файл существует, но указанный в нём интерпретатор отсутствует. Linux допускает редкий отказ после разрушения прежнего образа, когда ядро уже завершает процесс вместо возврата в старый код.

Логическая копия частной памяти может сначала использовать те же физические страницы. Изменение частной страницы вызывает копирование при записи. Так изменение переменной P1 остаётся частным, даже если позиция общего открытия изменилась у обоих.

Флаг FD_CLOEXEC позволяет устроить служебный канал. При обычном отказе execve ребёнок сообщает причину через ещё открытый конец записи. При успехе этот конец закрывается при замене образа. Когда остальные копии конца записи закрыты, родитель читает конец потока. Ребёнок мог также завершиться до отправки сообщения, поэтому отсутствие сообщения само по себе не доказывает успешный запуск. Готовность службы проверяют отдельным сигналом.

Почему запуск из многопоточной программы сложнее

Предположим, другой поток P0 держал замок библиотеки в момент fork. В ребёнке остаётся один вызывавший поток, а скопированный замок может остаться занятым. Прежнего владельца, который его отпустит, там уже нет. До execve после такого fork дочерний путь ограничен функциями, безопасными для вызова в обработчике сигнала (async-signal-safe). Это условие для кода запуска, а не общее требование ко всей работе новой программы.

Другая организация: создание процесса Windows

CreateProcessW получает имя приложения, изменяемую строку запуска и параметры окружения, каталога и наследования. За один вызов Windows создаёт процесс и первичный поток. В результате вызывающий получает два идентификатора и две управляемые ссылки (handles). Даже после успешного возврата последующая инициализация, например загрузка требуемой DLL, может закончиться отказом. Наблюдайте процесс по возвращённой ссылке и закрывайте полученные ссылки, когда работа с ними закончена.

Разбор изменяемой командной строки и массива argv устроен по-разному. В отчёте о запуске полезно записать, как переданы имя исполнимого файла и аргументы. Учебная сцена Windows API не исполняет.

Когда исполнение кончилось, а объекты ещё существуют

Нормальный выход с числом 7 и выход после сигнала различают по результату ожидания. В Linux проверяют WIFEXITED перед WEXITSTATUS, а случай сигнала проверяют отдельно. Пока запись завершения обычного ребёнка ещё не получена, в типичном случае её удерживает ОС. Эту стадию называют зомби. P1 уже не выполняет пользовательский код, но P0 ещё может узнать исход.

В локальном опыте книги Python запускает собственного ребёнка. В ответе видны его PID, текущий каталог и переданный параметр среды, затем родитель получает код 7. Это проверка наблюдаемых входов и выхода, без вывода о том, каким системным вызовом библиотека реализовала запуск.

Открытый объект может пережить P1, если его удерживает другой процесс. Для counter.bin после отказа отдельно выясняют, успела ли измениться запись. Повтор всего вычисления может прибавить единицу снова. К этому вернёмся в главе об отказах жизненного цикла. Теперь проследим T1, которая уже запущена, но остановилась внутри read, и увидим, что именно продолжится после переключения.
