Открытые файлы и общая позиция чтения

Прочитаем файл через два дескриптора одного открытия, затем сравним их с независимым открытием того же имени.

Что произошло при открытии

Вызов open получает путь counter.bin. Ядро находит объект через каталог, создаёт для него открытое описание O1 и выдаёт процессу дескриптор (file descriptor, fd). В нашем рисунке это номер 3. При read(3, …) ядро берёт O1 из записи 3 таблицы процесса, поэтому заново разбирать имя не требуется.

Через O1 ядро одновременно знает, откуда начать очередное чтение и к какому объекту обратиться. После двух прочитанных байтов позиция O1 станет 2. При переименовании объекта изменятся записи каталога, а 3 по-прежнему ведёт через O1 к тому же объекту и той же позиции.

В Linux открытому описанию соответствует структура struct file, а метаданным файла — индексный узел (inode). Оба участвуют в работе общего файлового слоя VFS. Далее используем Linux и обычный локальный файл. Правила совместного открытия и удаления у дескрипторов Windows (handles) задаёт другой интерфейс.

Позиция относится к открытию

Открытие без O_APPEND начинает с позиции 0. Прочитаем четыре байта в буфер с учебным адресом 0x00403124. Получим 2a 00 00 00, а O1 продвинется на 4. При следующем запросе ненулевой длины read на той же позиции вернёт 0 байт, потому что дошёл до конца файла (EOF). Четыре байта с нулевым значением, будь они там, дали бы результат 4.

Если теперь обычным write передать 2b 00 00 00, запись из O1 начнётся с позиции 4 и при полном успехе даст файл длиной 8 байт. Для замены числа используем позиционную запись pwrite со смещением 0. Для чтения начала без перемещения O1 подходит pread со смещением 0. Оба вызова оставят позицию 4.

Даже при позиционной записи два потока могут отдельно прочитать 42 и оба записать 43. Вызов с явным смещением устраняет гонку за общей позицией, но для двух прибавлений всё равно нужен протокол из книги синхронизации.

Дубликат ссылки и второе открытие

Начнём с нового O1 на позиции 0. dup(3) даёт условный номер 4. В таблице две строки, но обе ведут к O1. Прочитаем по два байта через 3 и 4. Через 3 вернутся 2a 00, затем через 4 — 00 00. Оба чтения продвигают одну позицию, в конце она 4.

Второй самостоятельный open того же имени даёт O2 и номер 5. Его позиция остаётся 0, пока O1 продвигается, но оба открытия ссылаются на один inode. Поэтому изменение первых байтов через O1 будет видно и через O2.

После fork у дочернего процесса своя таблица дескрипторов. Унаследованные записи всё ещё ссылаются на те же O1 и O2. Если ребёнок читает через унаследованный 4, изменение позиции O1 видно и родителю. Флаг закрытия при замене программы разбирается ниже, поскольку он относится к записи таблицы, а не к O1. Договор fork в Linux.

Флаги принадлежат разным объектам

Для временного counter.bin при первоначальном создании годится сочетание O_CREAT | O_EXCL: если имя занято, открытие откажет вместо работы со старым объектом. O_TRUNC при записывающем открытии обычного файла, напротив, обрежет его в момент open. У O_APPEND другая роль: перед каждой обычной записью выбирается конец файла. O_NONBLOCK меняет ожидание только там, где интерфейс поддерживает этот флаг. Для обычного файла Linux такой флаг не обещает завершение без ожидания накопителя.

В опыте включили O_APPEND через номер 4 командой fcntl для статусных флагов. Его увидел номер 3 на том же O1, но не номер 5 на O2. Изменение FD_CLOEXEC через 3 не изменило этот флаг у 4. Он управляет закрытием конкретной записи при успешной замене программы. В многопоточной программе O_CLOEXEC ставит этот флаг уже при open, иначе другой поток может успеть вызвать fork и exec до отдельной установки.

Наш pwrite-пример явно открывает файл без O_APPEND. В Linux документировано отличие для pwrite на append-открытии: данные могут добавиться в конец вопреки заданному offset. Поэтому нельзя молча добавлять O_APPEND к лаборатории и ожидать перезапись нулевого смещения. Точный договор и оговорка Linux позволяют проверить эту границу до работы с настоящими данными.

Чтение после unlink

После чтения ребёнка удалим единственное имя counter.bin вызовом unlink. Попытка нового открытия по этому пути вернёт ENOENT. У существующего дескриптора 4 вызов fstat показывает прежний inode и нулевое число имён. Закроем также 3. Через оставшийся 4 pread всё ещё возвращает 2b 00 00 00. Если бы у файла было другое жёсткое имя, оно осталось бы доступным. После последнего имени и последней удерживающей ссылки файловая система получает возможность освободить объект. Поэтому удаление имени открытого журнала может не вернуть место сразу. Договор unlink в Linux.

В Windows возможность удалить или переименовать открытый файл зависит от режима совместного доступа и выбранного API. Описание Linux не устанавливает этих правил. Кроме того, удаление записи каталога не гарантирует физического исчезновения байтов, например у объекта может остаться копия в снимке.

Дескриптор может стать другим объектом

Закрыв 3, приложение больше не вправе использовать его как прежнюю ссылку. Следующий open может выдать тот же номер для другого файла. Поэтому поток, передающий дескриптор в фоновую задачу, либо удерживает его до конца операции, либо передаёт отдельную ссылку и обязанность её закрыть.

Тот же способ передачи номера встречается у сокетов, каналов и устройств. От этого канал не получает позицию для произвольного lseek. У сокета с потоком байтов временное отсутствие данных и закрытие другой стороной различаются по результатам вызова и режиму. Сначала установите тип объекта, затем читайте договор его операций.

Как читать результат операции

Если для числа требуются четыре байта, а read вернул два, сохраните эти два и запросите недостающие. Вызов, вернувший ноль при ненулевой длине запроса к обычному файлу, не допишет в буфер два нуля. Если больше данных нет, у вас неполная запись. Декодировать число можно после чтения всех четырёх байтов.

Если write принял только два первых байта, повтор отправляет оставшиеся два. При позиционной записи сдвигают и начало оставшегося буфера, и передаваемое смещение на фактически записанную длину. Обработайте ошибку и остановите цикл при недопустимом отсутствии прогресса. После записи проверяют нужную синхронизацию отдельно: успех close сам по себе не даёт гарантии сохранности.

Опыт с двумя открытиями

На схеме нажмите «Дальше» до шагов чтения через 3 и 4. Проверьте, что O1 меняет позицию 0 → 2 → 4, а O2 остаётся на 0. Шаг закрытия 3 показывает, почему O1 ещё доступно через 4. В лаборатории с собственным временным файлом действие descriptors воспроизводит дубликат, отдельное открытие, позиционную запись и чтение после удаления имени. Разбор fork выше добавляет чтение ребёнка и наблюдение позиции родителем.

Повторный open после unlink не находит имя, хотя прежние дескрипторы ещё читают байты. В следующей главе пройдём путь от записи каталога к inode и дальше к размещению этих байтов.
