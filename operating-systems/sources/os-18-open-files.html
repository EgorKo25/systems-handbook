Открытый файл: имя, объект, ссылка и текущая позиция

Число 3 не является файлом. Между программой и содержимым стоят таблица ссылок процесса, состояние открытия и объект файловой системы. Их разные времена жизни объясняют многие неожиданные эффекты.

Что произошло при открытии

Пусть программа открыла counter.bin для чтения и записи. В POSIX-подобной модели успешный open возвращает файловый дескриптор, fd — file descriptor. Это небольшой неотрицательный индекс таблицы процесса. Предположим, вернулось 3; число выбрано для примера, а не гарантируется программой. Таблица по этому индексу хранит ссылку на описание открытого файла, open file description.

Описание открытия содержит состояние этого открытия: в частности, текущую позицию и предусмотренные флаги операций. Оно ссылается на файловый объект. Сам объект содержит сведения о содержимом и метаданных и может существовать независимо от конкретного открытия. Путь служил для поиска объекта; после открытия последующие read используют уже полученную ссылку. Переименование пути не заставляет дескриптор заново искать файл по новому написанию.

В обычной Unix-файловой системе объект метаданных файла называется inode, индексный узел. Он хранит размер, права и сведения о размещении данных; имя находится в каталоге. Два независимых открытия одного inode поэтому видят один файл, но сохраняют разные позиции.

В Linux этим слоям соответствуют конкретные структуры VFS — virtual filesystem switch, общего интерфейса файловых систем. В Windows приложению обычно возвращается handle, дескриптор другого интерфейса объектов. Он тоже не равен имени файла или физическому адресу, но правила прав, совместного открытия и конкретных флагов отличаются. Дальнейшие числовые примеры относятся к POSIX-подобной модели.

Позиция относится к открытию

Изначально позиция обычного открытого файла равна нулю. Успешный read четырёх байт копирует 2a 00 00 00 в наш буфер 0x00403124 и сдвигает позицию на фактически прочитанные четыре байта. Следующий read с той же позиции увидит конец четырёхбайтного файла и вернёт ноль. Этот результат называют EOF, end of file — конец файла. Он не сообщает «пришли четыре нулевых байта».

Если теперь обычным write записать 2b 00 00 00, позиция всё ещё равна 4: запись начнётся после прежних данных и может увеличить длину до 8 байт. Чтобы заменить исходное число, надо явно писать со смещения 0 либо сначала переместить позицию на 0. Positioned I/O, позиционный ввод-вывод, задаёт смещение отдельным аргументом: POSIX pread/pwrite не меняют общую текущую позицию. У Linux комбинация pwrite с открытием O_APPEND имеет известное отклонение от ожидаемой POSIX-семантики; наш пример специально не открывает файл с O_APPEND.

Флаг O_APPEND означает выбор конца файла для каждой записи по договору интерфейса. Он нужен журналам, но не превращает произвольную последовательность read–изменить–write в атомарное увеличение счётчика. Два процесса способны прочитать 42 и оба записать 43. Нужно отдельно согласовать всю логическую операцию, как разбирается в книге синхронизации.

Дубликат ссылки и второе открытие

Если dup(3) вернул 4, две записи таблицы ссылаются на одно описание открытия. Они разделяют позицию. Прочитайте два байта через 3, затем два через 4: во втором случае будут прочитаны байты 2 и 3, а не повтор первого участка. Закрытие 3 оставляет ссылку 4 действительной. Последняя ссылка освобождает описание, когда остальные владельцы и операции тоже позволяют закончить его жизнь.

Если вместо dup выполнить второй open того же пути, обычно получится отдельное описание открытия со своей позицией. Оба описания всё ещё ведут к одному файловому объекту. Поэтому изменения содержимого могут быть общими, а последовательность чтения — независимой. Общая позиция и общие данные являются разными свойствами.

При наследовании дескрипторов дочерним процессом в POSIX-модели также может разделяться описание открытия. Поэтому предсказать позиции по одному списку fd каждого процесса недостаточно. Флаги самого дескриптора, например закрытие при замене программы, отличаются от флагов общего описания. Если не закрывать ненужные ссылки, они способны удерживать ресурсы и неожиданно передавать доступ новому исполняемому коду.

Три таблицы вместо одного слова «файл»

Запишем конкретное состояние в POSIX-подобной модели. Таблица процесса содержит fd3→O1, fd4→O1, fd5→O2. O1 и O2 — два открытых описания, оба ссылаются на inode 7 файла counter.bin. В O1 хранится offset 4, в O2 — offset 0; режим обоих read/write, без append. В inode 7 находятся размер 4 и сведения о содержимом. Число 3 не является ни адресом inode, ни номером дискового блока.

После fork дочерняя таблица обычно получает ссылки на те же открытые описания: независимость памяти процесса не делает независимой позицию такого открытия. Следовательно, «прочитать со старого места» требует отдельного открытия либо операции с явным offset. Последовательность seek(0), затем write не заменяет positioned write при конкурентных пользователях общей позиции: между двумя вызовами другой поток может её сдвинуть. При этом pwrite не решает гонку двух конкурентных изменений одного содержимого: отдельные позиции не являются транзакционной блокировкой.

Флаги принадлежат разным объектам

Режим открытия выбирает чтение, запись либо оба направления. O_CREAT просит создать отсутствующий файл; O_EXCL вместе с ним требует исключительного создания, чтобы не затереть существующий. O_TRUNC при подходящем открытии обрезает существующий обычный файл — это действие над содержимым, а не просто разрешение. O_APPEND задаёт добавление каждой обычной записи в конец по договору интерфейса; это не синоним сохранённой позиции 4. O_NONBLOCK меняет поведение поддерживающих его операций при ожидании, но не превращает обычный файл в обязательно неблокирующий доступ к накопителю.

Статусные флаги открытого описания, например append, разделяются дубликатами. FD_CLOEXEC относится к конкретному дескриптору: закрыть эту ссылку при успешной замене исполняемой программы. O_CLOEXEC позволяет установить его одновременно с созданием дескриптора; отдельная установка позже оставляет окно утечки при конкурентном fork/exec. Это различие важно для сервиса, который не должен передавать дочерней программе случайный файл или сокет. В современных языковых библиотеках могут быть собственные безопасные значения по умолчанию; их надо проверять, а не угадывать по C-примеру.

Наш pwrite-пример явно открывает файл без O_APPEND. В Linux документировано отличие для pwrite на append-открытии: данные могут добавиться в конец вопреки заданному offset. Поэтому нельзя молча добавлять O_APPEND к лаборатории и ожидать перезапись нулевого смещения. Точный договор и оговорка Linux позволяют проверить эту границу до работы с настоящими данными.

Удалённое имя не всегда означает удалённые данные

Представим обычную Unix-подобную файловую систему. Открыли файл, затем удалили запись его имени из каталога. У открытого описания остаётся ссылка на объект; процесс может продолжать чтение, хотя повторный open по старому имени уже не находит его. Место обычно освобождается после исчезновения последних необходимых ссылок и завершения соответствующих операций. Это объясняет, почему удаление большого журнала не всегда сразу возвращает ожидаемое пространство.

Такое поведение не следует автоматически переносить на Windows: там возможность удаления или переименования зависит в том числе от режима совместного доступа и выбранных API. Даже на Unix удаление пути не является протоколом безопасного очищения носителя. Копии, снимки и физическое размещение могут сохранять байты; это отдельная задача управления данными.

Дескриптор может стать другим объектом

После close число 3 может быть снова выдано для нового открытия. Если другой поток сохранил только старое число и позднее начал операцию, он способен обратиться уже к другому объекту. Защита памяти здесь не спасает: число корректно, но его логическое время жизни закончилось. Обёртка программы должна согласовывать закрытие, отмену ожидающих операций и передачу владения.

Открытый объект не обязан быть обычным файлом. Сокет, канал и устройство могут использовать похожую таблицу ссылок, но поддерживают другие операции. У канала нет обычного произвольного seek; у сокета нельзя считать ноль результата тем же событием, что временное отсутствие данных; у каталога свои правила. Унифицированный интерфейс упрощает передачу ссылок, а не стирает свойства объектов.

Как читать результат операции

Запрошенные четыре байта и возвращённые четыре байта — не одно утверждение. Read может завершиться коротким результатом. Программа, ожидающая ровно четырёхбайтное число, накапливает прочитанное, корректно обрабатывает конец и ошибки и декодирует число только после получения всего формата. Важен фактический прогресс, а не число вызовов.

Аналогично write может принять только часть данных. Если приняли два байта из четырёх, повторять надо оставшиеся два по правильному адресу и смещению, а не весь исходный буфер. Ошибка, прерывание и нулевой прогресс требуют отдельных решений; бесконечный цикл без продвижения превращает отказ в зависание. Успешный close не является универсальным подтверждением устойчивой записи, а ошибки отложенной записи могут появиться позже первоначального write.

Проверить связи, а не угадать по номеру

В модели дескрипторов проследите: fd3 → O1 → файл, после dup ещё fd4 → O1, после второго open fd5 → O2 → тот же файл. Read двух байт через 3 сдвигает O1, но не O2. Предсказание проверяется безопасным нативным опытом в собственном каталоге: условия и команды. Опыт не исследует чужие fd и не удаляет файлы пользователя.
