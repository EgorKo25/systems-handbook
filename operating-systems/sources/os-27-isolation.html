Изоляция процессов и контейнеров

Разделить видимость, полномочия, ресурсы и доверие — четыре разные задачи.

Что именно отделено

Изоляция ограничивает, какие объекты и действия одной программы доступны другой. Адресные пространства отделяют обычные обращения к памяти, проверки доступа ограничивают действия с объектами, отдельные таблицы имён меняют то, что видно при поиске, а ресурсные ограничения ограничивают расход. Ни одно из этих свойств нельзя получить из одного общего слова «изолировано». Для каждой границы называют нарушителя, защищаемое свойство и доверенную часть системы.

Для счётчика есть несколько разных требований: чужой процесс не читает буфер по 0x00403124; чужой пользователь не меняет counter.bin; приложение не видит файлы вне выбранного дерева; оно не занимает всю память; ошибка в нём не даёт управлять ядром. Один только другой каталог решает лишь часть вопроса. Безопасность данных также зависит от уже открытых ссылок, наследования и доступных управляющих интерфейсов.

Имена меняются, объект может оставаться общим

Пространство имён задаёт представление некоторого набора объектов: идентификаторов процессов, точек монтирования, сетевых интерфейсов и других ресурсов в конкретной ОС. Два процесса могут видеть разные списки и одинаковые локальные имена. Но различие имени не доказывает физическую копию ресурса. Один и тот же файл нижнего хранилища может быть доступен через несколько путей; один накопитель обслуживает многие изолированные деревья.

В Linux namespaces — набор конкретных механизмов такого разделения. Отдельное сетевое пространство не выдаёт само по себе произвольный объём CPU и не меняет приложение в безопасную программу. Пользовательское пространство имён сопоставляет идентичности по определённым правилам; «root внутри» не следует автоматически отождествлять с неограниченными полномочиями в исходной системе. OCI Linux-конфигурация отдельно описывает namespaces, ограничения и полномочия в Runtime Specification. Это Linux-поставка, не определение любой ОС.

Ограничить интерфейс и ограничить ресурс

Фильтрация системных вызовов может уменьшить доступную поверхность ядра. Например, Linux seccomp-фильтр рассматривает номер вызова и доступные поля его аргументов по установленному договору. Это не универсальный анализ смысла пути по указателю: разрешённое открытие либо запись всё ещё требуют корректных проверок объекта. В документации прямо отделено уменьшение поверхности вызовов от готовой полной песочницы: Seccomp BPF.

Ресурсная группа объединяет процессы для учёта и управления расходом. Она может ограничивать CPU-время, память или I/O в зависимости от реализации. Это отдельная ось: процессу можно запретить чужой файл, но оставить возможность забить общий диск журналом. Можно ограничить память и всё равно случайно выдать секрет через разрешённый общий сокет. Граница безопасности не выводится из достижения численного лимита.

Как из этих механизмов получается контейнер

Контейнер в привычном OS-подходе — группа процессов с подготовленным представлением окружения и набором ограничений, использующая ядро соответствующей среды. Образ содержит пользовательские файлы, а не обязательно отдельное работающее ядро. Запуск образа сам по себе не создаёт аппаратную виртуальную машину. Конкретный продукт может дополнительно размещать контейнеры внутри VM, поэтому видимое слово container ещё не описывает весь нижний слой.

Совместное ядро означает общую доверенную реализацию системных вызовов и часть общих отказов. Ошибка ядра, лишний управляющий сокет, слишком широкая передача устройства либо ненужные полномочия могут разрушить предполагаемую границу. Уменьшение образа и запрет записи корневого дерева полезны для конкретных угроз, но не исключают ошибки оставшегося ядра и разрешённых управляющих интерфейсов. Название продукта не заменяет карту фактически выданного доступа.

Другие ОС не обязаны повторять Linux

FreeBSD jails разделяют окружение по своему набору правил и возможностям; их конфигурация и сеть имеют собственные границы. Это родственный подход изоляции ОС, а не список Linux namespaces под другим именем. Основы и современные варианты описаны в FreeBSD Handbook. Windows использует собственные механизмы безопасности, процессов, job objects и контейнерные режимы; гарантии определяют по выбранному режиму и версии.

Для переносимой системы сначала формулируют требуемое свойство: доступ только к открытому набору объектов, конечный расход памяти, независимое ядро либо невозможность видеть соседние процессы. Затем выбирают механизм конкретной ОС и проверяют отрицательный случай. Сходные имена интерфейсов без такой проверки не обеспечивают одинаковую изоляцию.

Скрытый в списке процесс может оставаться доступным через ранее выданную ссылку; ограниченный CPU не скрывает секретный файл; отдельный IP не отделяет одно физическое устройство. Для каждого запрета называют интерфейс, поскольку «не видно через этот список» слабее, чем «никакое разрешённое действие не раскрывает».

Наследование и уже открытый доступ

Изоляция нового процесса начинается не с пустоты: он может получить открытые ссылки, окружение, память исходного шаблона и каналы связи по правилам создания. Если подготовить отдельное дерево имён, но передать управляющий сокет хоста, приложение получает действие в обход ожидаемой карты. Если закрыть путь, но сохранить открытый читаемый объект, запрет нового поиска не обязан отозвать чтение через эту ссылку. Выбор начального набора ресурсов является частью запуска.

Поэтому протокол подготовки перечисляет нужные ресурсы, исключает ненужное наследование и устанавливает ограничения до исполнения недоверенного кода в предусмотренном порядке. Ошибка между частичной настройкой и запуском должна вести к отказу запуска, а не к успешному старту с половиной обещанных границ. Это проверяется по фактическому состоянию, а не только по намерению в конфигурационном файле.

Вычислить отображение личности, а не сравнивать имя root

В отдельном Linux-примере выберем вложенное пользовательское пространство с уже разрешённым отображением идентификаторов. Строка таблицы 0 100000 65536 означает: начальный ID внутри равен 0, соответствующий начальный ID снаружи равен 100000, длина диапазона 65536. Для внутреннего ID i из этого диапазона наружный ID равен 100000+i. Поэтому внутренний 0 соответствует наружному 100000, внутренний 1 — наружному 100001, внутренний 65535 — наружному 165535. Число 65536 уже за пределом этой строки. Отдельная таблица сопоставляет группы.

Пусть файл нижнего хранилища принадлежит наружному 100001 и имеет права 0640. Внутри согласованного отображения его владелец представлен как 1. Программа с внутренним ID0 не стала наружным владельцем 0; право конкретного действия всё ещё определяется применимыми проверками и областью полномочий. Внутренние привилегии не дают произвольного управления родительским пространством. Правила выдачи и записи такого отображения зависят от полномочий создающего; эту строку нельзя просто потребовать для любых чужих ID. Linux-механизм описан в user_namespaces(7). Мы вычисляем уже разрешённую таблицу, не создаём пространство на компьютере.

Какие ссылки хранит запущенная программа

Для собственной модели запуска обозначим состояние процесса как набор ссылок: U на контекст личности, M на представление точек монтирования, N на сетевое окружение, R на ресурсную группу и H на открытые объекты. Они разделены: смена N не меняет автоматически R, а смена M не удаляет H. У Linux виды пространств перечислены в namespaces(7); набор U/M/N/R/H здесь придуман для объяснения и не объявляется точной структурой ядра.

Последовательность подготовки в этой модели такова. Доверенный запускатель получает нужные полномочия; создаёт либо выбирает U/M/N/R; связывает разрешённое дерево с M; добавляет только требуемые открытые ссылки H; устанавливает ограничения; проверяет каждую операцию настройки. Лишь после успешной подготовки передаёт управление коду службы. Если настройка R отвергнута, запуск прерывается до этого перехода. Иначе программа могла бы успеть занять ресурс до применения лимита. Реальный порядок вызовов выбирается по конкретной ОС и связям полномочий, поэтому эта последовательность не является готовым универсальным скриптом контейнерного запуска.

Изменим одно поле: оставим отдельные M и N, но добавим в H управляющую ссылку на сервис родительской системы. Теперь скрытое имя этого сервиса не мешает обращаться через уже выданную ссылку. Убирать нужно саму лишнюю возможность при подготовке, а не только запись из списка видимых объектов. Такое сравнение двух состояний объясняет, почему проверка наследуемых ресурсов нужна вместе с проверкой дерева файлов.

Общая ёмкость и общий отказ

Два контейнера с разными каталогами могут заполнять одну файловую систему. Отказ места у одного затронет соседа, если не установлены соответствующие границы. Учёт I/O одного процесса также может отличаться от учёта отложенной общей записи ядра. Политику выбирают по поддерживаемому интерфейсу, измеряют фактическую область начисления и проверяют наиболее неудобный путь, например фоновое сохранение после завершения пользовательской операции.

Общее ядро и аппаратные ресурсы оставляют также зависимости по времени: конкурент может изменить задержки кэшей, памяти и устройств. Изоляция имён не является обещанием отсутствия всех временных побочных каналов. Для конкретной угрозы нужны отдельные механизмы и проверка; обычный учебный контейнерный пример не следует выдавать за полный анализ такой безопасности. VM меняет карту доверия, но по-прежнему использует общую нижнюю платформу.

Проверяемая модель

Схема показывает два приложения с разными деревьями имён, но одним ядром и общим физическим устройством. Проследите четыре байта: скрытое имя файла ещё не означает, что отсутствует уже открытая ссылка на этот объект. Никаких новых пространств имён на компьютере схема не создаёт. На бумаге отметьте общие части одним словом «общий» и выпишите последствия отказа каждой. Следующая глава добавит отдельное гостевое ядро.
