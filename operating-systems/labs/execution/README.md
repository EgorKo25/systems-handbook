# Практика исполнения

Основной путь работает прямо в книге. Модели `models.js` и состояния `traces.json`
не запускают ядро, виртуальную машину, команды оболочки или сетевые службы.
Они исполняют явно заданные правила над числами и очередями. Нужен браузер с
JavaScript; всё загружается из сохранённой копии, без запросов в интернет.
Если JavaScript выключен, исходные условия и ключевые расчёты остаются в тексте
и в полном текстовом ходе пошаговых схем.

## Что изменять в браузере

В главе о входе в ядро выберите чтение доступных данных либо чтение с ожиданием.
До нажатия «Дальше» предскажите поток, режим, PC/SP, очередь и место сохранённого
продолжения. В ветви IRQ исполняется T2, но готовой становится ожидавшая T1.
Раскройте «Регистры и сохранённые продолжения»: 32-байтный кадр модели
показывает адрес каждого поля и little-endian байты. Учебный READ=7 отличается
от реального Linux x86-64 read=0; место результата до завершения недействительно.
Попробуйте исправимый fault: возвращается PC повторяемой команды. Сопоставьте
с ошибкой неподходящего буфера: файл не прочитан и позиция остаётся 0.

В планировщике сравните FCFS и круговой обход с квантом 2 мс. Затем меняйте квант
между 1, 2, 4 и 8 мс; при FCFS это поле отключено, поскольку данная политика
не вытесняет работу по кванту. Сначала используйте
поступления A0/B1/C2 и потребности 8/2/1 мс. Затем выберите нагрузку с вводом:
A исполняется 2 мс, ждёт 3 мс, исполняется ещё 1 мс; B требует 5 мс; C приходит
в момент 4 и требует 1 мс. Вывод показывает собственное CPU-время, ожидание
в очереди готовых, внешнее ожидание и полное время. Их сумма проверяется моделью.
Все интервалы — учебные, прямая цена управления равна нулю.

В SMP-модели меняется только допустимый набор CPU двух работ. Свободный CPU1
не помогает, если обеим разрешён только CPU0. Это проверка причины, а не совет
изменять привязку на вашей машине. Модели жизненного цикла и службы разделяют
частную подготовку, публикацию, готовность, активные запросы и завершение.

`traces.json` содержит исходные модельные состояния, из которых строятся
иллюстрации. Это не записанная трасса настоящей ОС. Тест сравнивает эти состояния
с результатом того же публичного JavaScript, который загружен в книгу.

## Необязательный нативный путь

Этот путь требует своей Linux и установленного Python 3. Он полезен после
знакомства с запуском программы в терминале; для чтения основных глав он не нужен.
На рабочей Windows можно пользоваться браузерными моделями без установки.

`python3` — программа-интерпретатор Python. Следующее слово выбирает наш сценарий.
`--directory` задаёт абсолютный собственный учебный каталог; после него идёт
действие. Все примеры выполняются из папки тома `operating-systems`, рядом с
`index.html`. Из другого места укажите абсолютный путь к `labs/execution/native.py`.
Переменная оболочки `$HOME` здесь обозначает ваш домашний каталог; кавычки
сохраняют выбранный путь одним аргументом.

```sh
python3 labs/execution/native.py --directory "$HOME/admin-lab/os-execution" init
python3 labs/execution/native.py --directory "$HOME/admin-lab/os-execution" show
python3 labs/execution/native.py --directory "$HOME/admin-lab/os-execution" increment
python3 labs/execution/native.py --directory "$HOME/admin-lab/os-execution" show
```

`init` получает новую или пустую папку, создаёт `counter.bin` с четырьмя байтами
`2a000000` и маркер `execution-lab.json`. Если там уже есть данные, действие
отказывает. Оно не возвращает ваш счётчик в 42 и не удаляет прежнее занятие.
Если первоначальная подготовка оборвалась между созданием двух файлов,
сначала исследуйте оставшееся состояние; автоматического стирания нет.

`show` проверяет маркер и длину, затем печатает число и байты. Первый `increment`
читает 42, получает позицию 4, явно перемещает её в 0, записывает `2b000000`,
проверяет количество и выполняет `fsync`. Последующее чтение показывает 43.
Ещё один `increment` продолжает тот же мир и получает 44. Переполнение uint32
на предельном значении этот конкретный опыт отвергает вместо неявного оборота.

Сценарий рассчитан на доверенный каталог и файлы, созданные его `init`.
Не заменяйте их ссылками на другие объекты и не создавайте вторых жёстких
имён вне этого каталога. Проверки отвергают символические ссылки, но не
проверяют все жёсткие связи: два имени одного inode обозначают один файл,
поэтому запись изменит и содержимое, видимое через второе имя. Каталог
не является защитной песочницей от враждебных изменений файловой системы.

Это последовательный опыт одного писателя. Два одновременно запущенных
`increment` не получают гарантии атомарного увеличения. Операции с обычным файлом
не являются автоматически транзакцией; неизвестный исход и конкуренция разобраны
в книге. Успех `fsync` проверяет возврат системного интерфейса на нашей системе,
а не физический эксперимент с потерей питания или сертификацию накопителя.

Другие действия используют только свой процесс и созданного им ребёнка:

```sh
python3 labs/execution/native.py --directory "$HOME/admin-lab/os-execution" child
python3 labs/execution/native.py --directory "$HOME/admin-lab/os-execution" clocks
```

`child` создаёт отдельный собственный процесс Python, явно задаёт ему рабочий
каталог и единственный учебный параметр окружения, получает JSON и ждёт выход
со статусом 7. Этот статус намеренный; полезный результат опыта — различие PID,
правильный родитель и получение завершения. Внутреннюю реализацию запуска
`subprocess` этот опыт не объявляет измеренной последовательностью fork/exec.
В исходнике ребёнок получает `-I` (изолированный режим Python, ограничивающий
влияние пользовательских настроек) и `-c` (следующий аргумент содержит программу).
`LC_ALL=C` фиксирует локаль; `OS_EXECUTION_MARKER=child` — наш учебный параметр,
который ребёнок должен вернуть. Родитель не передаёт ему весь свой набор окружения.

`clocks` сравнивает прошедшее и собственное CPU-время короткого сна, затем короткого
вычисления с проверяемой суммой. Секунды и границы подписаны. Конкретные значения
зависят от системы и конкурентов; универсального предела или вывода о скорости
чужой службы здесь нет. Сценарий не меняет приоритеты, привязку CPU, службы,
пользователей, сеть, диски или настройки ядра.

## Самопроверки переносимой копии

Эти три команды работают и в экспортированной копии сайта. Для Node-проверок
нужен отдельно доступный Node.js; для нативной — Python 3 и личная Linux/POSIX
среда, подготовленная выше. Запускайте из корня копии библиотеки, где лежит
папка `operating-systems`:

```sh
node operating-systems/tests/execution-models.cjs
node operating-systems/tests/execution-browser.cjs
python3 operating-systems/tests/execution_native.py
```

Node — интерпретатор JavaScript; он нужен только для автоматической проверки
моделей, браузеру установленный Node не нужен. Python-тесты используют свои TEMP
каталоги; это отдельные самопроверки, а не сохранённая продолжаемая практика.
Модели проверяются отдельно от нативного чтения, записи и запуска ребёнка.
Эти команды не проверяют внешний вид читателя и не измеряют быстродействие
вашего компьютера.

`execution-browser.cjs` исполняет тот же скрипт с небольшим макетом DOM: проверяет
загрузку, выбор сценария, квант, шаги, возврат к началу и отсутствие дублирования.
Он не проверяет внешний вид, поведение Safari или CSS на узком экране.
В нативных тестах отдельно помечены заглушки короткой записи и ошибки fsync;
они проверяют обработку отказа, а не моделируют физический сбой устройства.

## Проверка исходных глав — только полная исходная копия репозитория

`execution_source.py` читает HTML-главы и модули из `operating-systems/sources/`.
Исходники и этот source-тест отсутствуют в переносимой копии сайта. Если у вас
полный исходный репозиторий, из его корня можно отдельно выполнить:

```sh
python3 operating-systems/tests/execution_source.py
```

Это проверка структуры глав, ссылок и соответствия таблиц; она не нужна
для работы моделей и сама не запускает ядро, MMU или оборудование.
