Один запрос через весь стенд

Теперь соединим слои на примере ДО. Есть Windows-ноутбук, промежуточная машина с SSH, Apache на spo1, PostgreSQL на db и FreeIPA на контроллере. Ошибка в интерфейсе — конечное наблюдение. Для ремонта нужно выяснить, какую границу запрос уже прошёл и какой контекст использовался на следующей.

1. Четыре личности одного запроса

 | Слой | Пример | Как подтвердить

 | HTTP/Kerberos | student@LAB.EXAMPLE.TEST | REMOTE_USER, access log, principal в проверенном ответе

 | Процесс ОС | UID 706800070 и группы | UID процесса CGI; id в сопоставимом контексте, а не просто root shell

 | Мандатный контекст | Текущая метка сеанса | Штатные средства Astra и журнал отказа

 | PostgreSQL / приложение | SQL role и user_roles ДО | session_user/current_user, связи в БД, api/session

Значения связаны настройкой, но не равны автоматически. Успешный вход доменного пользователя не создаёт прикладную роль по одному факту наличия uid. Наличие роли admin в ДО не превращает Linux-процесс в root. Успешный GRANT не меняет метку файла на Ceph. Когда эти четыре слоя смешивают, возникает соблазн выдать chmod 777, superuser и admins одновременно; это скрывает место ошибки и меняет слишком много условий.

2. HTTP-запрос до запуска CGI

GET /api/session HTTP/1.1
Host: app.lab.example.test:7000

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Negotiate

GET /api/session HTTP/1.1
Host: app.lab.example.test:7000
Authorization: Negotiate [токен SPNEGO]

HTTP/1.1 200 OK
Content-Type: application/json

Это упрощённый обмен без реального токена. Первоначальный 401 может быть приглашением к Negotiate; окончательный 401 после попытки аутентификации — другой результат. Браузер может заранее отправлять credentials, а соединение переиспользоваться, поэтому не каждый успешный запрос обязан сопровождаться новым 401. В access log смотрят последовательность и principal, а не считают любое число 401 аварией.

Apache выбирает слушающий адрес/порт, virtual host и правила обработки URI. Для HTTP/1.1 Host влияет на выбор именованного vhost. Для TLS SNI участвует ещё до HTTP и помогает выбрать сертификат. Проверка по IP может попасть в default vhost и дать совершенно другой сайт. Поэтому curl к правильному IP без правильного имени — не эквивалент пользовательского URL.

apache2ctl -S
apache2ctl -M
apache2ctl configtest
curl --negotiate -u : --delegation always \
  --connect-timeout 10 --max-time 30 -sS \
  -o /tmp/do-session-check.json -w 'HTTP %{http_code}\n' \
  'http://app.lab.example.test:7000/api/session'

Первые команды на сервере читают разбор vhost, список модулей и синтаксис. Они не перезапускают Apache. Curl выполняется из пользовательского Kerberos-сеанса; -o сохраняет тело отдельно от статуса, -w печатает результат. Delegation always запрашивает передачу credentials этому доверенному стенду; не используйте её на произвольном URL. Файл ответа может содержать персональные данные — после проверки его удаляют.

3. Что CGI получает на вход и что обязан вернуть

Классический CGI — отдельный процесс на запрос. Сервер передаёт метаданные в окружении, тело запроса — через stdin. CONTENT_LENGTH определяет длину тела, CONTENT_TYPE — его формат, QUERY_STRING — параметры после вопросительного знака. REMOTE_USER относится к аутентифицированной личности. KRB5CCNAME — имя выбранного хранилища credentials. Переменная из вашей интерактивной shell не появляется в Apache автоматически.

stdin: байты тела запроса
environment: REQUEST_METHOD, CONTENT_TYPE, QUERY_STRING, ...

stdout CGI:
Status: 200 OK
Content-Type: application/json

{"result":"ok"}

stderr CGI: диагностический журнал, не тело HTTP

CGI не должен печатать отладочную строку перед заголовками. Panic до записи заголовков даёт Apache сообщение End of script output before headers. Это следствие, а причина обычно находится несколькими строками выше в stderr. В нашем старом случае причиной была отсутствующая POSTGRES_PORT, в другом — недоступный xvfb-run. Они требуют разных исправлений, хотя конечный HTTP-код одинаковый.

Go-бинарник может запускаться быстро, но каждый CGI снова выполняет инициализацию процесса, конфигурации, библиотек и подключений. Пул PostgreSQL внутри короткоживущего CGI не превращается в общий пул между HTTP-запросами. Это архитектурная стоимость, которую учитывают при оценке задержки. Оптимизация начинается с измерения времени DNS/Kerberos/соединения/SQL/конвертации, а не с увеличения max_connections наугад.

4. TLS, доверие и почему нельзя лечить всё ключом -k

В типичном TLS 1.3 клиент отправляет ClientHello с поддерживаемыми параметрами, именем SNI и key share. Сервер выбирает параметры, доказывает владение ключом сертификата и вместе с клиентом получает сеансовые ключи. Проверка сертификата включает цепочку к доверенному CA, срок и имя. Сертификат на ipa.lab.test не становится правильным для IP только потому, что этот IP принадлежит той же машине.

У HTTPS два уровня: зашифрованный транспорт и HTTP внутри. Kerberos Negotiate аутентифицирует пользователя на прикладном уровне, а TLS защищает канал и идентичность сервера. Один не следует считать полной заменой другого. Cookie сессии FreeIPA действует после Kerberos-входа; утечка cookie также даёт доступ в пределах его полномочий и срока.

openssl s_client -connect ipa.lab.example.test:443 \
  -servername ipa.lab.example.test \
  -CAfile /etc/ipa/ca.crt \
  -verify_hostname ipa.lab.example.test -verify_return_error < /dev/null

Команда читает сертификат и проверяет TLS, не выполняя IPA user_find. -connect выбирает TCP endpoint; -servername задаёт SNI; -verify_hostname проверяет имя; -verify_return_error делает ошибку проверки значимой для завершения. Параметры проверяют по openssl version/help установленной сборки. Curl --insecure отключил бы существенную часть доказательства, поэтому его результат не считается успешной проверкой доверия.

5. Windows → промежуточная машина → spo1

В MobaXterm вкладка SSH — терминал удалённой Linux-машины. Локальный PowerShell — другая среда. Левая SFTP-панель обычно относится к текущему SSH-сеансу, но после вложенного ssh внутри shell она не обязана переключиться на второй сервер. Именно так архив легко оказывается «на сервере», но не на том сервере, где запускается deploy.

# PowerShell на ноутбуке: пример точки входа учебной сети
ssh -p 50024 user@192.0.2.30

# Уже в Linux-сеансе:
hostname -f
id
pwd
sudo -i
hostname -f
pwd

После sudo -i меняются пользователь, HOME и рабочая директория. Относительный путь к архиву из /home/user больше не указывает на тот же файл из /root. Для критичных шагов используйте абсолютные пути и перед записью проверяйте hostname. Адрес/порт выше — пример точки входа; адрес и порт определяются вашей сетью.

ProxyJump вместо вложенных ручных SSH

# Учебная форма: замените jump и target согласованными адресами.
ssh -J user@jump.example.test operator@target.example.test
scp -J user@jump.example.test .\release.tar.gz operator@target.example.test:/home/operator/

ProxyJump строит соединение к target через SSH-канал jump, не копируя приватный ключ на jump. Имя target обычно должно быть разрешимо с промежуточной стороны туннеля. Аутентификация и проверка host key target остаются отдельными. -A (agent forwarding) для этого обычно не требуется. Разрешение forwarding зависит от sshd-политики; не обходите её изменением чужой конфигурации.

Проброс только для просмотра HTTP через свой SSH

ssh -p 50024 -N \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 \
  -L 127.0.0.1:17000:127.0.0.1:7000 \
  user@192.0.2.30

Это синтаксис Bash; в PowerShell ту же команду пишут одной строкой или используют его собственный перенос. -N не запускает remote shell; -L создаёт локальный listener; первое 127.0.0.1 — адрес прослушивания ноутбука, второе — адрес назначения со стороны удалённой машины. ExitOnForwardFailure проверяет создание forwarding, но не гарантирует доступность каждого будущего целевого соединения. Keepalive помогает обнаружить оборванный транспорт.

Открытие http://localhost:17000 может дать неправильный Host и Kerberos service principal. Туннель обеспечивает TCP, но не адаптирует имена сертификатов и SPNEGO. Для диагностики транспорта это полезно; для доказательства штатной аутентификации используют правильное имя и согласованную схему доступа. Не назначайте рабочее имя IPA на localhost глобально ради одного туннеля.

6. Почему «скопировал те же файлы» даёт разный результат

 | Различие | Внешне незаметно | Последствие

 | Другая машина в SFTP-панели | Имя архива совпадает | Deploy читает старый архив на настоящем target

 | Содержимое каталога против каталога целиком | Те же файлы в дереве | Лишний уровень frontend/frontend, неверный DocumentRoot

 | Неполный перенос | Файл уже существует | Обрезанный tar/CGI или смесь версий

 | Права/владелец/ACL/xattr | Байты совпадают | Apache не читает или Astra запрещает выполнение

 | Подпись до/после изменения | Имя и размер похожи | Подпись относится к другим байтам

# PowerShell, локальный ноутбук:
Get-FileHash -Algorithm SHA256 -LiteralPath .\release.tar.gz
scp -P 50024 .\release.tar.gz user@192.0.2.30:/home/user/release.tar.gz.part

# Linux, получатель:
sha256sum /home/user/release.tar.gz.part
tar -tzf /home/user/release.tar.gz.part | head -n 20

У scp порт задаётся заглавной -P; у ssh — строчной -p. Расширение .part отделяет незавершённую доставку от готового архива. Сначала сравнивают полный SHA-256 с отправителем, затем просматривают структуру tar. После совпадения переименовывают и распаковывают в новый staging-каталог. tar -t только перечисляет, -z означает gzip, -f задаёт файл. Для обычного .tar флаг -z не нужен.

Tar переносит имена, содержимое и часть метаданных; поддержка ACL/xattr требует соответствующих параметров и совместимой ФС. FAT/exFAT на флешке не хранит Linux ACL как обычные файловые свойства, но архив может хранить их внутри. Мандатные атрибуты при развёртывании всё равно проверяют на целевой Astra. Совпадение SHA файла не доказывает совпадения его внешних xattr.

7. Файловый доступ: пройти по пути, затем открыть объект

namei -l /mnt/ceph/public/document-flow/templates
getfacl -cp /mnt/ceph/public/document-flow/templates
findmnt -T /mnt/ceph/public/document-flow/templates
pdp-ls -Mld /mnt/ceph/public/document-flow/templates
pdp-id

Первые три команды Linux, последние две — Astra. Namei показывает права каждого компонента пути. Для прохода по каталогу нужно x, для просмотра имён — r; создание дочернего объекта требует соответствующих прав записи и прохода по родителю. Findmnt -T показывает файловую систему, которая обслуживает данный путь: наличие каталога не доказывает, что Ceph действительно смонтирован. Иначе приложение начнёт писать на локальный диск под точкой монтирования.

ACL mask ограничивает эффективные права именованных пользователей/групп. Umask задаёт начальные POSIX-права новых файлов; это не мандатная метка. На Astra конфиденциальность и целостность проверяются отдельно. Возможность читать объект младшей метки не означает разрешение его редактировать из старшей. Именно поэтому интерфейс должен учитывать допустимость конкретной операции, а сервер обязан проверять её независимо от видимости кнопки.

CCNR относится к особенностям мандатной обработки каталога в Astra. Его нельзя описывать как «дать всем запись» и нельзя назначать на весь Ceph рекурсивно по аналогии с chmod. Для данного стенда используется согласованная корневая область и отдельные подкаталоги уровней; актуальные команды назначения и проверки находятся в прикладной главе Ceph. Перед применением сверяется man pdpl-file именно установленного выпуска и существующие атрибуты родителя. Здесь мы изучаем модель, не меняем политику объекта.

8. Что математически проверяет цифровая подпись

Хеш преобразует сообщение произвольной длины в фиксированное значение. Коллизии математически существуют, но выбранный криптографический алгоритм должен делать поиск подходящей коллизии практически трудным. Хеш без доверенного канала не доказывает автора: подменивший файл может подменить и лежащий рядом SHA256SUMS.

Подпись создаётся приватным ключом над определённым представлением сообщения/его хеша с параметрами алгоритма и формата. Проверяется публичным ключом. Это не универсальное «зашифровать файл приватным ключом»: такая формулировка не описывает корректно ни современные схемы RSA-подписи, ни подписи на эллиптических кривых. Подпись обеспечивает проверку целостности и происхождения относительно доверенного ключа, но не скрывает содержимое файла.

Файл и формат подписиточно определённые байтыКриптопроверкапубличный ключ + подписьПолитика доверияразрешён ли этот ключ?Верная подпись неизвестным ключом ещё не разрешение запуска.Разрешение запуска ещё не успешное выполнение CGI.

Отпечаток ключа — идентификатор ключевого материала, а не сама подпись. Присланная строка из 40 шестнадцатеричных цифр представляет 20 байт fingerprint соответствующего формата ключа. Она не сообщает размер RSA-модуля, длину файла или уровень секретности. Short key ID короче полного fingerprint и хуже подходит для однозначного выбора. Форматы новых версий OpenPGP могут иметь другую длину fingerprint; правило «всегда 40 цифр» не универсально.

9. bsign в вашем процессе подготовки CGI

Встроенная ELF-подпись хранится в структуре ELF. У файла есть заголовок, program headers для загрузчика и sections для инструментов; bsign должен корректно разместить служебные данные, сохранив исполняемость. Полный SHA-256 файла после подписи обычно отличается от SHA до подписи. Проверяющий bsign знает, какие части и каким способом входят в защищаемое представление; нельзя заменить его сравнением полного SHA с хешем неподписанного файла.

bsign --version
bsign --help
gpg --version
gpg --with-colons --fingerprint --list-secret-keys "$key_id"

bsign -v -N -E -s \
  --pgoptions="--batch --pinentry-mode=loopback --passphrase-file=$pass_file --default-key=$key_id" \
  "$elf"
bsign -V -E "$elf"

Переменные заранее задаются только на сервере подписи: key_id — согласованный fingerprint, pass_file — защищённый файл пароля, elf — рабочая копия одного CGI. Это разбор вашей команды, а не инструкция генерировать новый корпоративный ключ. -v включает подробности, -N отключает собственный запрос пароля bsign, -E выбирает встроенную ELF-форму, -s создаёт подпись. --pgoptions передаёт параметры криптографическому инструменту; --batch и loopback относятся к способу взаимодействия GPG, а не к стойкости подписи. Поддержка флагов проверяется на sign-srv: Astra bsign отличается от одноимённых сторонних сборок.

-V выполняет проверку подписи. Просто «good hash» или вывод сведений не равны подтверждённой подписи доверенным ключом. Импорт публичного ключа в личную GPG-связку root не означает автоматически доверие ядра в замкнутой программной среде. Системное доверие, режимы ЗПС, разрешённые способы хранения подписи и обновление соответствующих системных структур определяются конкретным выпуском Astra и политикой объекта.

Почему исходный sign.sh опасно воспринимать как атомарную операцию

Цикл for elf in `find ...` делит вывод по пробелам и переводам строк. Имя с пробелом становится несколькими аргументами. Команда без кавычек вокруг $elf добавляет glob expansion. Отсутствие проверки каждого exit code позволяет упаковать смесь подписанных и неподписанных файлов. Финальный rm -R рабочего каталога после неудачной упаковки уничтожает материал для расследования. Проверка bash -n ловит синтаксис, но не эти логические ошибки.

Практический защищённый сценарий уже находится в главе подписи: отдельная рабочая копия, отказ на первой ошибке, проверка каждого ELF, manifest до/после, архив и проверка его хеша. Исходники не удаляются до подтверждения результата. Приватный ключ и файл пароля не копируются на флешку с релизом.

10. Последовательность доставки подписанного релиза

Зафиксировать commit backend/frontend и собрать CGI для правильной архитектуры/ABI.

Проверить количество файлов и manifest неподписанного результата.

На сервере подписи подписать рабочую копию одного CGI, проверить bsign и запуск на согласованной тестовой Astra.

Подписать остальные CGI; любой отказ останавливает выпуск.

Сформировать новый manifest подписанных файлов и архив. Зафиксировать SHA архива.

На объекте сравнить SHA полученного архива, распаковать в staging, проверить подписи, владельцев, права и метки.

Переключить файлы по инструкции deploy и проверить штатные HTTP-запросы.

Пересборка CGI после подписи создаёт новый файл, которому нужна новая подпись. Frontend HTML/JS обычно не является ELF: проход ELF-цикла bsign не подписывает автоматически весь веб-интерфейс. Подпись архива и подпись исполняемых файлов — разные объекты контроля. Наличие файла cgi-signed.tar.gz с правильным названием само по себе ничего не доказывает о версии внутри.

11. Один отказ, одна проверяемая гипотеза

 | Наблюдение | Доказанная граница | Следующее действие

 | Connection refused | Получен отказ TCP от узла/сети | Адрес/порт, listener, NAT; ещё не SQL и не пароль

 | 401 после Negotiate | HTTP достигнут | Service principal, keytab, клиентская политика и серверный журнал

 | 500 + executable not found | CGI запустился и вызвал программу | PATH CGI и наличие нужной программы, например xvfb-run

 | mkdir permission denied | Обработка дошла до файловой операции | Родительские права, ACL, метки, состояние mount и UID процесса

 | column does not exist | SQL дошёл до разбора на сервере | Реальная БД/схема/колонка и журнал миграции

 | Счётчик не совпадает со списком | Система отвечает, но результат логически неверен | Одинаковые фильтры пользователя/метки/статуса и снимок данных

Фиксируйте время, principal, метку, URL и идентификатор операции. Смотрите узкий временной диапазон журнала, затем повторяйте ровно один запрос. После исправления проверяйте исходный сценарий, а не только исчезновение строки в логе. Если сменили три независимые настройки сразу, вы получили менее полезный эксперимент, даже когда стало работать.

12. Уборка без потери возможности отката

Временный файл — тот, у которого известны создатель, назначение и условие ненужности. После успешного развёртывания можно удалить загрузочные .part, распакованные промежуточные копии и диагностические ответы с персональными данными. Резервная копия до обновления, журнал deploy, manifest и сведения о версии ещё нужны для отката и не являются мусором в момент первого HTTP 200.

du -h --max-depth=1 /root/document-flow-releases
find /tmp -maxdepth 1 -type f -name 'do-session-check.json' -ls
ls -ld /absolute/path/to/confirmed-staging

Это сначала обзор. Удаление выполняют по конкретному подтверждённому пути, не по глобальному /tmp/* и не по всем файлам старше суток: там могут работать чужие приложения. Подробный порядок для данного комплекта находится в разделе очистки основного справочника. В PowerShell используйте LiteralPath для известных путей, особенно с пробелами и квадратными скобками; не передавайте найденные пути в другой shell для удаления.

Дополнительные первичные материалы: OpenSSH ssh, scp, Apache CGI, TLS 1.3, bsign Astra, замкнутая программная среда. Обязательные объектовые команды остаются в основном справочнике; эта глава объясняет, почему они выполняются в таком порядке.
