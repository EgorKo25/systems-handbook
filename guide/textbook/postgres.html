Работающая база — это не только процесс postgres и открытый 5432. Клиент должен попасть в нужный кластер, пройти аутентификацию, получить права на базу, схему и объекты, работать с подходящей меткой, выполнить изменения и успешно зафиксировать транзакцию. Разберём каждый переход и затем проверим его на отдельной учебной базе.

1. Что происходит до первого SELECT

Сеанс PostgreSQL поверх TCP

Текст всех шагов схемы
  1. TCP, затем SSLRequest при TLS. DNS и TCP уже должны работать. При классическом согласовании TLS клиент сначала спрашивает поддержку SSL, затем выполняется TLS handshake.
  2. StartupMessage. Версия протокола, user, database, параметры сеанса. У начального StartupMessage нет обычного однобайтового типа последующих сообщений.
  3. Authentication request. Первое подходящее правило HBA определяет метод. Это может быть GSSAPI, SCRAM и другие варианты, разрешённые сборкой.
  4. Ответы аутентификации. GSSAPI использует Kerberos-контекст; SCRAM использует свой challenge-response. Это разные протоколы, не две формы одного пароля.
  5. AuthenticationOk → ReadyForQuery. Сервер также сообщает параметры и данные для отмены запросов. ReadyForQuery показывает состояние транзакции: idle, transaction или failed transaction.
  6. Query либо Parse / Bind / Execute. Только теперь начинается SQL. Успешная аутентификация не гарантирует SELECT на нужной таблице.

При обычном протоколе v3 многие сообщения имеют байт типа, 32-битную длину и содержимое. Length включает себя, но не байт типа. Simple Query передаёт SQL-текст; extended protocol разделяет подготовку, привязку параметров и выполнение. Параметризованный запрос не собирается экранированием пользовательского текста в SQL: значения передаются отдельно. На уровне сети это всё ещё поток TCP, а не «один SQL равен одному пакету».

У PostgreSQL 11 GSSAPI-аутентификация не означает GSS-шифрование всего SQL-трафика. Возможности GSS encryption появились в следующих версиях. Для TLS sslmode=verify-full проверяет цепочку доверия и имя сервера; require не тождественен полной проверке идентичности. Существующие настройки объекта не меняют попутно с диагностикой: сначала фиксируют реальную версию и принятый способ защиты.

2. В какой кластер вы попали

psql -X -h db.lab.example.test -p 5432 -U postgres -d document_flow
\conninfo
SELECT version(), current_database(), session_user, current_user;
SELECT inet_server_addr(), inet_server_port(), pg_backend_pid();
SHOW config_file;
SHOW hba_file;
SHOW data_directory;
SHOW search_path;

Первая строка выполняется в Linux shell; остальные — в psql. -X запрещает загрузку персонального psqlrc, чтобы чужие настройки не меняли поведение диагностики. -h задаёт именно сервер; без него libpq может выбрать локальный Unix socket. -p — порт, -U — роль, -d — база. Если GSS не настроен для такого principal, понадобится разрешённый способ административного входа. Некоторые SHOW доступны только привилегированным ролям.

Session_user отражает первоначальную роль сеанса, current_user — текущую, например после SET ROLE. Имя базы не определяет кластер: на двух серверах могут существовать одинаковые document_flow. Если дамп снят с одного, а миграция применена на другом, SQL может завершиться успешно и всё равно не исправить приложение. Поэтому адрес, порт, база и версия входят в протокол работ.

3. HBA проверяется сверху вниз без запасного пароля

# Учебный пример строк, не конфигурация действующего объекта:
local   course_db   course_reader                         peer
hostssl course_db   course_reader   198.18.0.0/24          scram-sha-256
host    course_db   all             0.0.0.0/0             reject

Local означает Unix socket; host — TCP; hostssl — TCP с TLS. В примере первый подходящий тип/база/роль/адрес выбирает способ входа. Если пароль по этой строке неверен, PostgreSQL не пробует следующую строку как запасной метод. Peer сверяет локальную ОС-личность и применимые mappings; он не действует на удалённое TCP-соединение. GSS сверяет Kerberos principal и разрешённое сопоставление роли, а не POSIX-группу пользователя на клиенте.

SELECT line_number, type, database, user_name, address, auth_method, error
FROM pg_hba_file_rules ORDER BY line_number;
SELECT name, setting, source, context, pending_restart
FROM pg_settings
WHERE name IN ('listen_addresses','port','ssl','max_connections','shared_buffers');
SELECT pg_reload_conf();

Первые два запроса читают состояние. Последний просит reload конфигурации и является изменением; его выполняют только после проверенной правки. Успех pg_reload_conf означает доставку сигнала, а не успешность каждой новой строки: смотрят журнал и pg_hba_file_rules.error. Параметры с pending_restart требуют перезапуска; reload не меняет postmaster-параметр магически. Глобальный restart ради одной строки HBA не нужен.

Ни роль в таблице приложения user_roles, ни группа atomic_users_manage не являются сами по себе GRANT PostgreSQL. Они используются на других уровнях. Мандатный контроль Astra добавляет ещё одно условие поверх SQL-привилегий. Выдача SELECT не должна рассматриваться как способ обойти метки.

SELECT has_database_privilege('course_reader','course_db','CONNECT');
SELECT has_schema_privilege('course_reader','course','USAGE');
SELECT has_table_privilege('course_reader','course.documents','SELECT');
SELECT has_sequence_privilege('course_reader','course.documents_id_seq','USAGE');
\du
\dn+
\dp course.*

Эти команды относятся к лаборатории ниже. has_* проверяет эффективное право с учётом членства и PUBLIC. ACL-строка в \dp — компактное представление прямых назначений, и её отсутствие не всегда означает отсутствие всех прав. Поиск только в information_schema.table_privileges может не дать полной картины наследования. Для конкретного действия полезнее эффективная проверка и пробный запрос под целевой ролью.

5. Учебная база, которую можно разобрать без риска для ДО

Используйте отдельный PostgreSQL для упражнений. Администратор создаёт course_db, затем запускает postgres-lab.sql. Скрипт проверяет имя базы, отказывается работать при существующей схеме course и создаёт только свою схему, таблицы и роли course_owner/course_reader/course_writer. Роли кластерные, поэтому при конфликте имён создание завершится ошибкой и транзакция откатится.

createdb -h 127.0.0.1 -U postgres course_db
psql -X -h 127.0.0.1 -U postgres -d course_db \
  -v ON_ERROR_STOP=1 -f labs/postgres-lab.sql
psql -X -h 127.0.0.1 -U postgres -d course_db

Пример предполагает настроенный административный доступ к отдельному локальному тестовому кластеру. -v ON_ERROR_STOP=1 заставляет psql прекратить скрипт на SQL-ошибке. Без него psql может напечатать ошибку, продолжить следующие команды и закончить с кодом, который неверно трактуют как полный успех. Транзакция в самом файле объединяет создание объектов. Создание базы отдельное, поскольку CREATE DATABASE нельзя выполнять внутри обычного transaction block.

SET ROLE course_reader;
SELECT * FROM course.documents ORDER BY id;
INSERT INTO course.documents(title) VALUES ('Запрещённая запись');
RESET ROLE;
SET ROLE course_writer;
INSERT INTO course.documents(title) VALUES ('Разрешённая запись') RETURNING id;
RESET ROLE;

Это интерактивный опыт: ошибка INSERT у reader ожидаема и не означает поломку лаборатории. SET ROLE проверяет SQL-права, но не повторяет сеть и аутентификацию нового соединения. Для полного login-теста дополнительно нужна LOGIN-роль, пароль/билет и HBA. В этой лаборатории роли NOLOGIN, чтобы не добавлять новые способы внешнего входа.

Почему новые таблицы иногда не получают старые права

ALTER DEFAULT PRIVILEGES FOR ROLE course_owner IN SCHEMA course
  GRANT SELECT ON TABLES TO course_reader;

Это правило для будущих объектов, создаваемых course_owner. Оно не исправляет существующие таблицы и не применяется к таблице, которую создал postgres лишь потому, что postgres состоит в нужной группе. Скрипт использует SET ROLE course_owner при создании объектов. Если миграции запускаются разными ролями, права по умолчанию могут различаться. Исправление состоит в понятном владельце миграций и явных GRANT, а не в повторном запуске того же ALTER DEFAULT PRIVILEGES наугад.

6. Почему два SELECT могут честно видеть разные данные

PostgreSQL хранит версии строк. У версии есть служебные поля создания/завершения, но видимость нельзя вычислить только сравнением xmin и xmax с текущим номером: нужны состояние транзакций, снимок активных транзакций, специальные значения и особенности блокировок. UPDATE обычно создаёт новую версию, а старая остаётся, пока может понадобиться другим снимкам. Читатель обычно не ждёт обычного писателя строки, потому что может читать подходящую старую версию.

Видимость в двух транзакциях

В Read Committed новый SQL statement получает новый снимок. В Repeatable Read снимок фиксируется для транзакции при первом соответствующем запросе. Нажмите SELECT, затем COMMIT в B, затем снова SELECT: отличие видно в модели. Модель намеренно показывает только чтение; реальные конфликтующие UPDATE дополнительно проверяют блокировки и могут завершиться serialization failure.

ШагТерминал AТерминал B
1BEGIN ISOLATION LEVEL REPEATABLE READ;
2SELECT value FROM course.counter WHERE id=1;
3UPDATE course.counter SET value=20 WHERE id=1;
4SELECT value FROM course.counter WHERE id=1;В autocommit UPDATE уже зафиксирован
5COMMIT; затем повторить SELECT

После первого SELECT ожидается 10, после шага 4 всё ещё 10, после COMMIT и нового SELECT — 20. Для повторного опыта сначала верните значение 10 вне транзакции A и замените REPEATABLE READ на READ COMMITTED. Не сравнивайте два теста, оставив предыдущую транзакцию открытой: именно это часто портит ручную диагностику.

Sequence не откатывает выданные номера как обычная таблица. INSERT, завершившийся ошибкой или ROLLBACK, может оставить пропуск id. Это нормально и не является доказательством потерянного сотрудника. Требование «без пропусков» — отдельная бизнес-задача с иной синхронизацией, а не настройка SERIAL.

7. Блокировки и ожидания без перезапуска базы

-- Терминал A, учебная база:
BEGIN;
UPDATE course.counter SET value=value+1 WHERE id=1;
-- Пока не делайте COMMIT.

-- Терминал B:
SET lock_timeout='3s';
UPDATE course.counter SET value=value+1 WHERE id=1;

В B ожидается lock timeout примерно через три секунды: обе операции хотят изменить одну строку. Обычный SELECT в третьем терминале может читать предыдущую зафиксированную версию. Завершите A через ROLLBACK, затем повторите B. Разница между ожиданием блокировки и медленным чтением диска принципиальна: индексы не устраняют забытый открытый transaction.

SELECT pid, usename, state, wait_event_type, wait_event,
       clock_timestamp()-xact_start AS transaction_age,
       pg_blocking_pids(pid) AS blockers,
       left(query,160) AS query_sample
FROM pg_stat_activity
WHERE datname=current_database()
ORDER BY xact_start NULLS LAST;

Запрос читает статистику. Для чужих сеансов нужны соответствующие права мониторинга. Query может содержать чувствительные значения, поэтому выгрузку просматривают перед отправкой. Idle in transaction означает незакрытую транзакцию, а не активное выполнение SQL. Сначала связывают PID с конкретным приложением. pg_cancel_backend отменяет текущий запрос; pg_terminate_backend разрывает сеанс и откатывает его незавершённую транзакцию. Это разные по последствиям действия, ни одно не запускается по всем PID «на всякий случай».

8. Как COMMIT переживает падение питания

Изменённая страница сначала оказывается в памяти. WAL описывает изменения так, чтобы после аварии их можно было воспроизвести. Правило write-ahead требует необходимую запись журнала на устойчивом носителе до записи соответствующей изменённой страницы данных. При обычном synchronous_commit подтверждение COMMIT связано с сохранением WAL, а не с записью каждой страницы таблицы на своё окончательное место.

Checkpoint задаёт точку и условия, ограничивающие объём последующего восстановления; он не является COMMIT всех пользовательских транзакций. Crash recovery выполняет REDO необходимых WAL-записей. Незавершённые изменения не становятся видимыми просто потому, что их байты были записаны: видимость учитывает состояние транзакции. Отключение fsync ради скорости меняет гарантию целостности и не относится к нормальному ремонту медленного деплоя.

VACUUM убирает версии, которые больше никому не нужны, и поддерживает служебные структуры. Долгая транзакция может удерживать старый снимок и мешать освобождению. Обычный VACUUM обычно не уменьшает размер файла ОС до исходного; место становится повторно используемым внутри таблицы. VACUUM FULL переписывает таблицу и требует сильной блокировки и дополнительного места. Это не первая команда при нехватке диска.

9. План запроса и цена ошибки оценки

CREATE TABLE course.measurements AS
SELECT n AS id, n % 100 AS bucket, repeat('x',80) AS payload
FROM generate_series(1,10000) AS n;
ANALYZE course.measurements;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM course.measurements WHERE id=7777;
CREATE INDEX measurements_id_idx ON course.measurements(id);
ANALYZE course.measurements;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM course.measurements WHERE id=7777;

Выполняется администратором только в course_db. До индекса ожидается последовательное чтение; после индекса планировщик обычно выбирает индекс для одной строки. Фактический выбор зависит от версии, статистики и стоимости. Cost в EXPLAIN — условная оценка, не миллисекунды. Actual time — измерение этого запуска; rows и loops помогают понять, сколько раз выполнялся внутренний узел. Buffers различает попадания в буферный кеш и чтение, но чтение блока не всегда равно физическому чтению диска: ниже есть кеш ОС.

Сравнивайте estimated rows и actual rows. Большое расхождение размножается на join и может привести к неудачному плану. Индекс не обязан помогать запросу, который возвращает половину таблицы. Больше индексов — больше работы при записи и больше занимаемого места. EXPLAIN ANALYZE действительно исполняет запрос, включая UPDATE/DELETE; не запускайте его на изменяющем рабочие данные запросе ради безобидного просмотра. ROLLBACK не отменяет внешние эффекты вызываемых функций.

10. Служебные каталоги для расследования пропавшей колонки

SELECT schemaname, tablename, tableowner
FROM pg_tables WHERE schemaname='document-flow' ORDER BY tablename;

SELECT n.nspname, c.relname, c.relkind, pg_get_userbyid(c.relowner) AS owner
FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='document-flow' ORDER BY c.relname;

SELECT a.attnum, a.attname, format_type(a.atttypid,a.atttypmod) AS type,
       a.attnotnull, pg_get_expr(d.adbin,d.adrelid) AS default_value
FROM pg_attribute a
LEFT JOIN pg_attrdef d ON d.adrelid=a.attrelid AND d.adnum=a.attnum
WHERE a.attrelid='"document-flow".documents'::regclass
  AND a.attnum>0 AND NOT a.attisdropped
ORDER BY a.attnum;

pg_tables — удобное представление таблиц. pg_class содержит больше типов отношений: обычные таблицы, индексы, последовательности, представления и др.; relkind различает их. pg_namespace хранит схемы. pg_attribute описывает колонки, включая системные и удалённые, поэтому фильтры attnum>0 и NOT attisdropped здесь необходимы. Regclass разрешает точное имя объекта; кавычки вокруг document-flow нужны из-за дефиса. Search_path не должен случайно направить проверку в одноимённую таблицу другой схемы.

SELECT conname, contype, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid='"document-flow".documents'::regclass;
SELECT indexname, indexdef FROM pg_indexes
WHERE schemaname='document-flow' AND tablename='documents';
SELECT obj_description('"document-flow".documents'::regclass);

Эти запросы читают фактическое состояние, а не файл миграции. COMMENT на таблице — документация объекта; это не прикладной комментарий сотрудника и не мандатная метка. Нативная MAC-версия PostgreSQL Astra может добавлять собственные поля, команды и системные объекты. Их проверяют по конкретной сборке и существующему дампу, не выдумывают универсальное имя колонки security_label. Для обычных стандартных security labels есть отдельные каталоги pg_seclabel, но это не основание считать их полным описанием нативного MAC.

11. Почему транзакция не спасает от неверного сценария миграции

Транзакция гарантирует атомарность тех команд, которые действительно вошли в неё и дошли до успешного COMMIT. Она не гарантирует, что выбран правильный файл, база, схема и версия. IF NOT EXISTS не проверяет тип существующей колонки. Скрипт может пропустить шаг по неверному условию и совершенно успешно зафиксировать оставшиеся. Поэтому после миграции проверяют целевую структуру отдельно.

psql -X -h db.lab.example.test -p 5432 -U postgres -d document_flow \
  -v ON_ERROR_STOP=1 -f checked-migration.sql > migration.log 2>&1
result=$?
cat migration.log
printf 'psql exit=%s\n' "$result"
test "$result" -eq 0

Это шаблон запуска уже проверенного файла, а не готовая миграция. 2>&1 сохраняет stderr вместе со stdout. Код возврата снимается немедленно после psql: последующий cat изменит $?. При pipe через tee нужен Bash pipefail или PIPESTATUS, иначе результатом будет успех tee. Если SQL сам содержит BEGIN/COMMIT, не добавляют внешнюю транзакционную обёртку без проверки. CREATE INDEX CONCURRENTLY, CREATE DATABASE и ряд других команд имеют ограничения на transaction block.

Проверка после COMMIT должна подтвердить не только наличие поля, но и тип, default, nullability, ограничения и необходимые права. Затем проверяется реальный CGI новым запросом. Таблица миграций показывает заявленную историю, а служебные каталоги — фактическую структуру. Их расхождение нужно объяснить, а не скрыть ручной вставкой «миграция выполнена».

12. Резервная копия и проверяемое восстановление

pg_dump -h 127.0.0.1 -U postgres -d course_db -Fc -f course.dump
pg_restore --list course.dump
createdb -h 127.0.0.1 -U postgres course_restore
pg_restore -h 127.0.0.1 -U postgres -d course_restore \
  --exit-on-error --single-transaction course.dump

Команды относятся к учебной БД и тому же тестовому кластеру, где роли уже существуют. -Fc создаёт custom archive; --list читает оглавление, но не доказывает восстанавливаемость всех данных. Настоящий тест — восстановление в отдельную новую базу и проверки строк, ограничений и прав. --single-transaction обеспечивает атомарность совместимого восстановления; для больших баз оценивают размер и длительность. Пользователи/роли кластерного уровня не входят в обычный дамп одной базы.

На Astra учитываются мандатные метки самого файла и объектов архива. Ошибка установки cluster maclabel не исправляется автоматически выключением всех меток. В нашем выезде потребовалось различать вывод pg_dump в файл через -f и через stdout; итоговый архив всё равно требует проверки. Универсальную лабораторию обычного PostgreSQL нельзя выдавать за доказательство восстановления нативной MAC-базы.

Для удаления учебных данных сначала закройте сеансы course_db/course_restore, затем в отдельном тестовом кластере удалите эти две базы. После этого можно удалить три созданные NOLOGIN-роли. Не используйте DROP OWNED/REASSIGN OWNED по рабочим ролям и не делайте TRUNCATE всех таблиц как способ вернуть исходную схему: TRUNCATE удаляет данные, а не структуру.

13. SQL-права, RLS и мандатные метки — разные фильтры видимости

Прикладная колонка privacy_level хранит число, которое понимает ДО. Нативная мандатная метка Astra — атрибут безопасности, применяемый соответствующим механизмом ОС/СУБД. Наличие числа 2 в колонке само по себе не доказывает, что файловый объект, строка БД и текущий процесс имеют согласованные метки. Связь обеспечивается реализацией приложения и механизмами конкретной сборки, а не совпадением названия поля.

Row-Level Security стандартного PostgreSQL — ещё один механизм. Политики RLS добавляют условия доступа к строкам на основании SQL-выражений и ролей. Это не универсальное имя мандатного контроля Astra. Таблица может иметь выключенный relrowsecurity и при этом подчиняться нативному MAC; обратное тоже требует отдельного понимания окружения.

SELECT n.nspname, c.relname, c.relrowsecurity, c.relforcerowsecurity
FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='document-flow' AND c.relkind IN ('r','p');

SELECT schemaname, tablename, policyname, roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname='document-flow';

Это чтение стандартных RLS-настроек, не проверка всех мандатных условий. USING определяет допустимые существующие строки для применимых операций, WITH CHECK — допустимые новые версии при записи. Владелец таблицы обычно обходит RLS, если не включено принуждение; superuser и BYPASSRLS требуют отдельного учёта. Поэтому проверка под postgres может показывать больше, чем реальное подключение CGI. Не меняйте RLS ради совпадения с результатом root-проверки.

Чтобы исследовать неверный счётчик документов, сравнивают список и count в одинаковых условиях: роль, метка, пользователь приложения, фильтры статуса, видимость удалённых строк и момент снимка. Если count запускается другим подключением с расширенными полномочиями, он может честно посчитать недоступные пользователю строки. Если count и список выполнены в Read Committed разными statement, параллельное изменение также может дать краткое расхождение. Постоянное расхождение после прекращения записей указывает на иной класс проблемы.

Рабочая последовательность расследования

  1. Зафиксировать api/session и текущую метку процесса, под которым воспроизведён запрос. Пароль и токен в отчёт не включать.
  2. Записать точные URL списка и счётчика, включая query parameters. Отдельно проверить переключатель «только мои» и статусные фильтры.
  3. На стороне SQL подтвердить current_database, session_user и current_user соответствующего подключения. Не подменять его административным сеансом.
  4. Сравнить SQL-условия и применимые политики. Проверить soft delete, доступность по маршруту и участие пользователя.
  5. Повторить в том же контексте после завершения параллельных изменений. Затем проверить другую метку как отдельный тест.

Факт, что документ читается на более высокой метке, не является разрешением редактировать его оттуда. Направление чтения и записи определяется политикой. Сервер должен отклонять запрещённое действие, даже если фронтенд случайно оставил кнопку. Скрытие кнопки улучшает интерфейс, но не заменяет проверку. Эта разница связывает устройство БД с требованиями к форме ДО, а не остаётся отвлечённой теорией безопасности.

Подробности версий: протокол v3, HBA, default privileges, изоляция, блокировки, WAL, EXPLAIN. Сетевые причины отказов разобраны в первой главе, GSS — в главе Kerberos.
