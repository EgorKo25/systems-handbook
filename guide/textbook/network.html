Представим конкретное действие: браузер отправляет небольшой JSON в ДО. Вызов JavaScript ещё не является пакетом. Браузер выбирает соединение, библиотека TLS формирует записи, TCP принимает поток байтов, IP выбирает следующий узел, Ethernet доставляет кадр соседу, а физический интерфейс превращает последовательность символов в электрический или оптический сигнал. На другом конце происходят обратные преобразования. На каждом уровне собственные границы, адреса, очереди и причины отказа.

1. Что физически проходит по проводу

В медном кабеле передаётся меняющееся напряжение между проводниками пары. Приёмник измеряет сигнал и восстанавливает символы относительно своего тактового генератора. «Один вольт означает единицу» — плохая модель Ethernet: способ кодирования зависит от физического стандарта. В 10BASE-T используется манчестерское кодирование с переходом в середине битового интервала. Для гигабитной медной линии применяются несколько уровней сигнала и одновременно четыре пары. Символ может нести информацию более чем об одном бите; служебное кодирование, коррекция и распределение по парам мешают приравнять частоту символов к полезным битам приложения.

Скремблер распределяет комбинации сигнала, чтобы линия не зависела от длинной серии одинаковых битов. Это не шифрование: секретного ключа у скремблера нет. Приёмник должен восстановить тактовую частоту, границы символов и кадра. Ошибки линии могут обнаруживаться раньше, чем ОС увидит кадр; поэтому пустой tcpdump не доказывает, что на кабеле ничего не происходило. Счётчики PHY/MAC смотрят отдельно.

ip -s link show dev eth0
ethtool eth0
ethtool -S eth0

Это команды чтения на Linux. -s у ip выводит статистику интерфейса; у ethtool заглавная -S запрашивает драйверные счётчики. Имена вроде CRC, alignment, missed, no_buffer различаются у драйверов. Рост CRC при нагрузке наводит на кабель, разъём, трансивер; рост пропусков из-за отсутствия буферов — на приёмный тракт или перегрузку. ethtool eth0 показывает согласованные скорость и дуплекс. Два конца линии должны согласовать совместимый режим; принудительное изменение только одного конца может ухудшить ситуацию.

2. Скорость, задержка и очереди — три разных величины

Передача 1500 байт при 100 Мбит/с требует минимум 1500 × 8 / 100 000 000 = 120 мкс сериализации, ещё до учёта Ethernet-служебных байтов. Распространение по кабелю добавляет время, зависящее от длины и среды. Коммутатор добавляет обработку и возможное ожидание в очереди. Приложение добавляет ожидание CPU, диска, базы и собственных блокировок. Ускорение линка не сокращает все эти составляющие одинаково.

При RTT 40 мс и скорости 100 Мбит/с в пути может находиться около 500 000 байт данных. Это произведение полосы на задержку — bandwidth-delay product. Если TCP может держать неподтверждёнными только 64 КиБ, он не заполнит такой канал даже при идеальном диске. Но увеличение буферов без измерения не лечит потери: слишком большая очередь добавляет секунды задержки интерактивным запросам. Именно поэтому «ping хороший без нагрузки» не исключает проблемы при копировании архива.

3. Кадр Ethernet по полям

На среде:
преамбула 7 | SFD 1 | MAC назначения 6 | MAC источника 6 |
EtherType 2 | данные 46…1500 | FCS 4 | межкадровый интервал

Обычно в pcap:
MAC назначения | MAC источника | EtherType | данные

Пример заголовка:
02 00 00 00 00 02  02 00 00 00 00 01  08 00
└ назначение   ┘  └ источник      ┘  └ IPv4

Размеры здесь в байтах, интервал — время простоя линии, а не поле кадра. Для обычного Ethernet без VLAN минимальный кадр от MAC назначения до FCS имеет 64 байта. Короткое содержимое дополняется padding. Пакет IPv4 может иметь длину 40 байт, а данных Ethernet будет минимум 46; эти лишние байты не становятся частью IP. IP Total Length позволяет отделить настоящий пакет от дополнения.

EtherType 0x0800 обозначает IPv4, 0x0806 — ARP, 0x86dd — IPv6. Метка 802.1Q вставляет дополнительные 4 байта после MAC источника: TPID обычно 0x8100 и TCI с PCP (3 бита приоритета), DEI (1 бит) и VLAN ID (12 бит). После неё идёт исходный EtherType. MTU 1500 относится к полезной нагрузке Ethernet, а не к полному размеру на проводе; VLAN меняет размер кадра, не обязательно уменьшая IP MTU интерфейса.

Коммутатор запоминает MAC источника на входном порту в своей forwarding database, отдельно по VLAN. Известный MAC назначения направляет на соответствующий порт. Неизвестный unicast и broadcast распространяются по разрешённым портам данного VLAN. Таблица MAC не знает, какой IP принадлежит компьютеру. ARP-кеш узла и MAC-таблица коммутатора решают разные задачи. Их таймеры тоже независимы.

Access-порт обычно принимает/передаёт пользовательский трафик без тега в назначенном VLAN; trunk переносит несколько VLAN с тегами, иногда с отдельным нетегированным native VLAN. Несовпадение native VLAN может выглядеть как странная односторонняя доступность. Петля между коммутаторами размножает широковещательные кадры, поскольку Ethernet не имеет аналога IP TTL. STP/RSTP строит топологию без активных петель; отключать защиту ради исчезновения предупреждения — значит убрать механизм, который сдерживал аварию.

4. Как узнаётся MAC следующего узла

Пусть клиент 198.18.1.2/24 обращается к 198.18.2.2. Таблица маршрутов выбирает шлюз 198.18.1.1. Клиент ищет MAC шлюза, а не удалённого сервера. ARP-запрос отправляется на ff:ff:ff:ff:ff:ff в локальном сегменте. Router не пересылает этот broadcast в другой сегмент. Он принимает IP-пакет, затем самостоятельно выясняет MAC следующего соседа со своей стороны.

Поле ARP для Ethernet/IPv4БайтыЗначение запроса
Hardware type / protocol type2 + 21 / 0x0800
Hardware length / protocol length1 + 16 / 4
Operation21 запрос, 2 ответ
Sender hardware / protocol address6 + 4MAC и IPv4 спрашивающего
Target hardware / protocol address6 + 4MAC пока неизвестен, IPv4 искомого соседа

ARP-сообщение занимает 28 байт; Ethernet дополнит короткий кадр до минимального размера. ARP-ответ обычно идёт unicast. Кеш соседей Linux проходит состояния INCOMPLETE, REACHABLE, STALE, DELAY, PROBE и FAILED. STALE не означает поломку: запись существует, но подтверждение достижимости уже старое. При использовании ядро может сначала отправить данные и затем проверить соседа. FAILED после попытки обращения — существеннее: MAC не удалось разрешить либо сосед не подтвердился.

ip route get 198.18.2.2
ip neigh show
tcpdump -ni eth0 -e -vv 'arp or icmp'

route get вычисляет маршрут для данного назначения; это точнее просмотра только default. У tcpdump -n отключает разрешение имён, -i выбирает интерфейс, -e показывает канальный заголовок, -vv увеличивает детализацию. Захват требует соответствующих прав. DNS при диагностике ARP не нужен и способен сам задержать вывод, поэтому здесь используется -n.

5. IPv4: двадцать байт, которые меняют смысл доставки

Биты:  0           8          16          24          31
       +----+----+------------+------------------------+
  0    |Ver |IHL | DSCP | ECN |      Total Length      |
  4    |     Identification   |Flags| Fragment Offset   |
  8    | TTL      | Protocol  |    Header Checksum      |
 12    |              Source Address                  |
 16    |            Destination Address                |
 20    |      Options, если IHL больше пяти            |
       +-----------------------------------------------+

Version = 4. IHL измеряется 32-битными словами: 5 означает 20 байт, не 5 байт. Total Length включает заголовок и данные IP. Protocol = 6 у TCP, 17 у UDP, 1 у ICMP. TTL уменьшается на маршрутизаторах; при исчерпании узел обычно возвращает ICMP Time Exceeded. IPv4 checksum защищает только IP-заголовок; изменение TTL требует её пересчёта. Она не доказывает целостность HTTP-тела.

DSCP предназначен для классов обслуживания, но маркировка сама по себе не создаёт приоритет: оборудование должно применять соответствующую политику очередей. ECN позволяет сообщать о перегрузке без обязательной потери пакета, если транспорт и сеть поддерживают механизм. Identification, MF и Fragment Offset нужны при фрагментации. Offset измеряется блоками по 8 байт. DF запрещает фрагментирование IPv4-пакета маршрутизатором; при слишком маленьком выходном MTU требуется ICMP об этом ограничении. Если такое ICMP блокируется, маленькие запросы могут работать, а большой TLS-ответ зависать.

При каждом маршрутизируемом переходе меняется канальный заголовок, уменьшается TTL и пересчитывается IPv4 checksum. IP-адреса источника/назначения сохраняются, если нет NAT. TCP sequence не должен изменяться обычным маршрутизатором. Эти инварианты позволяют сравнивать два захвата на разных сторонах сети и искать место преобразования.

6. Маска, маршрут и выбор исходного адреса

Запись /24 означает 24 старших бита сетевой части. Побитовое AND адреса и маски даёт префикс. Для 198.18.1.130/25 маска 255.255.255.128, сеть 198.18.1.128, последний адрес 198.18.1.255. Адреса 198.18.1.10 и 198.18.1.130 находятся в разных /25, хотя первые три десятичных числа совпадают. «Одинаковые первые три числа» работает только для /24.

Побитовый калькулятор подсети

Сначала выбирается наиболее длинный подходящий префикс. Маршрут /32 к конкретному узлу сильнее /24 и default /0. Метрика сравнивается не вместо длины префикса. В Linux policy routing может сначала выбрать таблицу по правилам, исходному адресу или отметке пакета. Поэтому наличие правильной записи в main не всегда определяет реальный путь.

ip -br address
ip rule show
ip route show table all
ip route get 198.18.2.2 from 198.18.1.2

-br даёт компактный список адресов. table all показывает все таблицы, включая local. from задаёт предполагаемый источник для расчёта маршрута; адрес должен соответствовать проверяемой ситуации. На многосетевом сервере ответ может уйти через другой интерфейс. Проверка reverse path filtering способна отбросить входящий пакет при несоответствии обратного пути. Менять rp_filter вслепую не надо: сначала доказывают асимметрию захватом и маршрутами.

7. Чем принципиально отличается IPv6

Базовый заголовок IPv6 фиксированного размера 40 байт: Version, Traffic Class, Flow Label, Payload Length, Next Header, Hop Limit, затем два адреса по 16 байт. Next Header может указывать транспорт либо следующий extension header. Заголовочной checksum нет. Маршрутизаторы IPv6 не фрагментируют проходящий пакет: слишком большой пакет требует ICMPv6 Packet Too Big, а решение об уменьшении или фрагментации принимает источник.

ARP заменён Neighbor Discovery поверх ICMPv6. Router Advertisement сообщает префиксы и параметры маршрутизатора; SLAAC позволяет сформировать адрес, DHCPv6 решает свои задачи выдачи конфигурации. Наличие DHCPv6 само по себе не заменяет RA для обычного изучения default router. Link-local fe80::/10 требует зоны интерфейса при неоднозначности, например fe80::1%eth0. Блокировка всего ICMPv6 ломает не только ping, но и базовые механизмы сети.

Если имя имеет A и AAAA, клиент может пробовать несколько адресов. Браузер с Happy Eyeballs способен обойти неработающий IPv6 быстрее, чем другая библиотека. Поэтому «в браузере работает, curl ждёт» иногда связано с выбором адреса, а не HTTP. Сравнение curl -4 и curl -6 — диагностический эксперимент, не основание навсегда выключать IPv6 на контроллере FreeIPA.

8. TCP: поток байтов и независимые номера в двух направлениях

TCP, минимум 20 байт:
source port 16 | destination port 16
sequence number 32
acknowledgment number 32
data offset 4 | reserved | flags | window 16
checksum 16 | urgent pointer 16
options, затем данные

Основные флаги: SYN ACK FIN RST PSH URG ECE CWR

Порт — 16-битное число. Соединение различается по протоколу, паре адресов и паре портов; одинаковый серверный порт обслуживает множество клиентов. Sequence обозначает номер первого байта данных сегмента в данном направлении. ACK обычно указывает следующий ожидаемый байт противоположного направления. SYN и FIN занимают по одному номеру последовательности, хотя не несут байт пользовательского потока. Номера вычисляются по модулю 2³².

Нажимайте «Следующий шаг» и следите за номерами

Текст всех шагов схемы
  1. SYN seq=1000. Клиент выбирает начальный номер. В SYN согласуются MSS, Window Scale, SACK Permitted и другие поддерживаемые опции.
  2. SYN ACK seq=7000 ack=1001. Сервер подтвердил SYN клиента и объявил свой независимый начальный номер.
  3. ACK seq=1001 ack=7001. Обе стороны знают начальные номера. Этот ACK без данных не расходует номер последовательности.
  4. 5 байт seq=1001 ack=7001. Байты занимают номера 1001–1005. Граница write() не является границей TCP-сообщения.
  5. ACK ack=1006. Подтверждено получение в TCP, но не обработка JSON приложением и не COMMIT в PostgreSQL.

Window показывает доступное окно приёмника; согласованный Window Scale расширяет эффективный диапазон. Congestion window отправителя ограничивает нагрузку на сеть. Фактический объём неподтверждённых данных ограничивается обоими окнами. MSS относится к полезным данным TCP в сегменте, а не к полному Ethernet-кадру. TCP options уменьшают место для данных при том же MTU. SACK сообщает о полученных диапазонах за дырой; накопительный ACK всё ещё указывает первый недостающий байт.

Потеря может обнаружиться по таймеру повторной передачи или подтверждениям следующих данных. Повторная передача — не всегда новая проблема: сеть допускает потери. Существенны их частота, задержка восстановления и связь с нагрузкой. RST закрывает соединение аварийно, FIN завершает направление передачи штатно. После FIN в одну сторону обратное направление ещё может работать. TIME_WAIT защищает новое соединение от старых сегментов и помогает повторно подтвердить FIN; это не «утечка открытых файлов» по определению.

ss -tin dst 198.18.2.2
tcpdump -ni eth0 -s 0 -w tcp-lab.pcap 'host 198.18.2.2 and tcp port 8080'

ss -t выбирает TCP, -i добавляет внутренние показатели, -n оставляет числовые адреса. В tcpdump -s 0 сохраняет пакет полностью, -w пишет двоичный pcap. Такой файл может содержать прикладные данные: лабораторный захват делается на учебном трафике. В Wireshark относительные sequence numbers обычно включены для удобства; они отличаются от абсолютных 32-битных чисел в исходном заголовке.

9. Почему tcpdump иногда показывает невозможные пакеты

Сетевой стек может передать драйверу большой буфер, а NIC разделит его на кадры позже. При захвате до сегментации виден «пакет больше MTU». Checksum также может быть рассчитана адаптером после точки захвата, и анализатор напишет incorrect checksum. На приёме GRO объединяет связанные сегменты до части обработчиков. Это не отменяет ограничений на реальные кадры в кабеле.

Проверяйте место захвата. Для вопроса «что ушло по проводу» захват на независимом зеркальном порту полезнее исходящего tcpdump на отправителе. Для вопроса «что увидело приложение» важны сокет и ядро получателя. Виртуальные veth и bridge добавляют свои точки наблюдения. Подробности реализации offload описаны в документации ядра Linux; наличие конкретной функции смотрят через ethtool -k eth0, не отключая всё на рабочем сервере.

10. NAT как таблица соответствий, а не магия интернета

Клиент 198.18.1.2:45000 отправляет SYN к 198.18.2.2:8080. Router делает SNAT и заменяет источник на 198.18.2.1:45000. При конфликте портов он может выделить другой исходный порт. Conntrack хранит соответствие исходного и обратного направлений. Ответ на 198.18.2.1:45000 преобразуется обратно к 198.18.1.2:45000. Сервер не обязан знать маршрут в 198.18.1.0/24, потому что видит соседа 198.18.2.1.

ТочкаИсточникНазначение

DNAT меняет назначение, например внешний порт 50024 на внутренний SSH-порт 22. Наличие DNAT не разрешает FORWARD автоматически и не включает маршрутизацию. Для работы нужны согласованные маршрут, filter-правила и обратный путь. Masquerade — разновидность SNAT с выбором адреса выходного интерфейса, удобная при динамическом адресе. Для постоянного адреса явный snat проще для чтения.

При hairpin NAT клиент из внутренней сети обращается к внешнему адресу своего же сервера. DNAT приводит запрос к внутреннему серверу, но сервер может ответить клиенту напрямую с внутреннего адреса. Клиент ожидал другой endpoint. Дополнительный SNAT или отдельное внутреннее DNS-имя обеспечивают согласованный обратный путь. Это объясняет, почему проброшенный порт работает из другой сети, но не из соседнего кабинета.

Conntrack — состояние, поэтому существующее соединение не обязательно применит только что изменённое правило NAT: соответствие обычно определяется первым пакетом. Проверяют новым соединением. Таблица NAT не является списком пользователей. Один внешний IP может представлять множество машин; по IP нельзя надёжно назначать роль сотруднику в ДО. Механика nftables описана в официальном руководстве NAT.

11. Собрать три машины внутри одной учебной Linux ВМ

Network namespace имеет собственные интерфейсы, маршруты, сокеты и сетевые правила. Пара veth похожа на виртуальный кабель: запись в один конец принимается другим. Лаборатория создаёт только namespaces course-c, course-r, course-s. Она не меняет адрес физического интерфейса и firewall основной ВМ. Требуются root, iproute2, nftables, ping, tcpdump и Python 3. В контейнере этих прав часто нет; используйте отдельную учебную ВМ.

sudo bash labs/network-up.sh
sudo ip netns exec course-c ping -c 3 198.18.2.2
sudo ip netns exec course-r ip route
sudo ip netns exec course-r nft list ruleset

network-up.sh содержит все команды с пояснениями. Повторный запуск при существующих пространствах имён завершается ошибкой, а не присваивает чужую лабораторию. ip netns exec NAME COMMAND запускает команду в выбранной сетевой среде; ping -c 3 ограничивает опыт тремя запросами. Маршрутизация включается через sysctl внутри course-r. На сервере есть обратный маршрут через 198.18.2.1, поэтому исходный опыт работает вообще без NAT.

В отдельном терминале запустите захват на маршрутизаторе, затем повторите ping. В -i any некоторые платформы дают Linux cooked header вместо Ethernet; для просмотра MAC выбирайте конкретные left или right.

sudo ip netns exec course-r tcpdump -ni left -e 'arp or icmp'
sudo ip netns exec course-r tcpdump -ni right -e 'arp or icmp'

Опыт: убрать обратный маршрут, затем включить SNAT

sudo ip -n course-s route del default
sudo ip netns exec course-c ping -c 2 -W 1 198.18.2.2
sudo ip netns exec course-r nft add table ip course_nat
sudo ip netns exec course-r nft 'add chain ip course_nat postrouting { type nat hook postrouting priority 100; policy accept; }'
sudo ip netns exec course-r nft add rule ip course_nat postrouting ip saddr 198.18.1.0/24 oifname right snat to 198.18.2.1
sudo ip netns exec course-c ping -c 3 198.18.2.2

Первый ping ожидаемо перестаёт получать ответы: запрос доходит, но сервер не знает путь к исходному 198.18.1.2. После SNAT сервер отвечает локальному соседу. -W 1 ограничивает ожидание ответа ping. В nft таблица семейства ip обрабатывает IPv4; postrouting выполняется после выбора выходного интерфейса; приоритет 100 соответствует типичному этапу source NAT. Здесь нет правил основного сетевого пространства ВМ.

Откат опыта и уборка

sudo ip netns exec course-r nft delete table ip course_nat
sudo ip -n course-s route add default via 198.18.2.1
sudo bash labs/network-down.sh

network-down.sh удаляет только три учебных namespace и отказывается делать это при работающих внутри процессах. Сначала завершите tcpdump клавишами Ctrl+C. Удаление namespace удаляет его маршруты, интерфейсы и nft-таблицы. Настройки основной ВМ возвращать не требуется: они не менялись.

12. От браузера до провода — собранная последовательность

  1. Браузер определяет адрес. Это может быть собственный кеш, системный резолвер или DoH; подробности в главе DNS.
  2. Для нового соединения ядро выбирает маршрут и исходный адрес. При необходимости узнаёт MAC следующего соседа.
  3. TCP устанавливает соединение. TLS проверяет сервер и создаёт ключи сеанса. Эти этапы могут отсутствовать у повторно используемого соединения.
  4. Байты HTTP попадают в send buffer. TCP разрезает поток с учётом MSS, окна и перегрузки. Шифротекст TLS не обязан совпадать по границам с сегментами.
  5. IP и Ethernet добавляют заголовки. Драйвер ставит дескриптор в очередь NIC; DMA позволяет адаптеру прочитать буфер без побайтового копирования CPU.
  6. PHY передаёт символы. Следующие коммутаторы и маршрутизаторы обрабатывают свои уровни.
  7. Приёмник проверяет кадр, передаёт пакет стеку, собирает поток TCP. TLS проверяет целостность записи. HTTP-сервер получает запрос и только теперь запускает прикладную обработку.

Если на сервере виден SYN, но нет SYN-ACK, DNS на клиенте уже отработал достаточно для этой попытки. Если TLS установился и сервер вернул 500, поиски неисправного кабеля обычно не первый шаг. Если приложение ответило 200, это всё ещё не доказывает корректность бизнес-операции — нужен её результат. Диагностика эффективна, когда каждый следующий тест проверяет ближайшую ещё не доказанную границу.

Контрольный разбор: ping работает, SSH через 50024 нет. Почему?

Ping проверяет ICMP к адресу. SSH может зависеть от DNAT внешнего 50024 к внутреннему 22, filter-правила, слушающего sshd, обратного маршрута и аутентификации. Успешный ping не проверил ни один TCP-порт. Начните с TCP-соединения к точному адресу и порту, затем ssh -vv, а не с изменения пароля или DNS всех машин.

13. Весь кадр целиком: самостоятельно проверить каждый байт

Ниже один синтетический DNS-запрос, упакованный в UDP, IPv4 и Ethernet. Он создан локально, не перехвачен у сотрудника и не отправлен в сеть. Откройте готовый pcap в Wireshark или соберите его сами. Timestamp намеренно нулевой, поэтому анализатор покажет начало эпохи; это учебный файл, не журнал события.

python3 labs/packet-example.py example-dns.pcap

0000  02 00 00 00 00 35 02 00 00 00 00 02 08 00 45 00
0010  00 3b 42 42 40 00 40 11 6a 14 c6 12 01 02 c6 12
0020  01 35 cf 08 00 35 00 27 30 ac 12 34 01 00 00 01

Числа слева — смещения в кадре в шестнадцатеричном виде. Строка 0010 начинается с байта номер 16, а не с отдельного заголовка. Заголовок IPv4 начинается на смещении 14, поэтому пересекает границу строк. Это типичная причина ошибочного чтения дампа глазами.

PCAP добавляет собственный глобальный заголовок и заголовок записи; эти байты не являются частью Ethernet. В Wireshark поле Frame Length относится к записанному кадру, а не полному размеру pcap-файла на диске.

Посчитать checksum без магии библиотеки

Для Internet checksum байты разбиваются на 16-битные слова в сетевом порядке. Поле checksum при расчёте нулевое. Слова складываются, переносы за 16 бит возвращаются в младшую часть, затем результат инвертируется. Если длина нечётная, для расчёта добавляется нулевой байт. Проверка готового сообщения тем же алгоритмом даёт ноль. В исходнике генератора этот алгоритм занимает несколько строк и проверяется assert.

UDP checksum включает pseudo-header: IP источника, IP назначения, нулевой байт, номер протокола и UDP length. Pseudo-header не передаётся отдельным куском сети — он логически составляется из уже известных полей. Это защищает от доставки транспортного содержимого не тем endpoint. Поэтому NAT меняет не только IP-адрес и IPv4 checksum, но и соответствующую транспортную checksum. В IPv4 нулевая UDP checksum означает отсутствие проверки; вычисленный нулевой результат кодируется 0xffff. Для обычного UDP по IPv6 требования строже, переносить правило IPv4 нельзя.

Упражнение с обоснованием

Поменяли TTL с 64 на 63. Какие checksum изменятся?

IPv4 header checksum изменится, потому что TTL входит в заголовок IPv4. UDP checksum не изменится: TTL не входит в UDP pseudo-header. FCS реального Ethernet-кадра изменится, поскольку байты кадра стали другими. Но в данном pcap FCS не сохранена, и генератор её не добавляет.

Поменяли адрес назначения с 198.18.1.53 на 198.18.1.54?

Нужно пересчитать IPv4 checksum и UDP checksum, поскольку адрес назначения входит в обе проверяемые структуры. DNS payload при этом не меняется. При отправке в другой сегмент также потребуется корректный MAC следующего узла; из одного изменения IP это автоматически не следует в ручном генераторе.

14. Откуда взялись IP, шлюз и DNS после включения компьютера

DHCPv4 переносит параметры конфигурации поверх UDP. Клиент до получения адреса может отправлять с 0.0.0.0:68 на 255.255.255.255:67. Типичная последовательность DISCOVER → OFFER → REQUEST → ACK выбирает предложение и подтверждает аренду. DHCP не является ARP: он распределяет конфигурацию, а ARP находит канального соседа. DNS из DHCP также не гарантирует, что сервер DNS знает нужный корпоративный домен.

DHCPv4, наследование BOOTP:
op 1 | htype 1 | hlen 1 | hops 1
xid 4
secs 2 | flags 2
ciaddr 4 | yiaddr 4 | siaddr 4 | giaddr 4
chaddr 16 | sname 64 | file 128
magic cookie 4 = 63 82 53 63
options: type / length / value, до End option

Xid помогает связать ответы с обменом клиента; chaddr содержит аппаратный адрес, но идентичность клиента может задаваться отдельной option 61. Yiaddr — предлагаемый адрес клиента, giaddr — адрес relay в соответствующем сценарии. Relay позволяет обслуживать DHCP для сети, в которой сам сервер не находится: broadcast через маршрутизатор сам по себе не проходит. Relay знает, из какого сегмента пришёл запрос, и помогает серверу выбрать пул.

До истечения аренды клиент пытается её продлить. На T1 обычно обращается к выбранному серверу; на T2 переходит к более широкому поиску доступного сервера. Конкретные значения могут быть переданы сервером, поэтому механическое «всегда ровно половина» неверно как универсальная диагностика. После истечения аренды клиент не должен продолжать считать адрес своим на основании старого ACK.

# Linux, чтение состояния NetworkManager:
nmcli device show
ip address show
ip route show

# PowerShell/CMD на Windows, чтение:
ipconfig /all
Get-NetIPConfiguration
Get-DnsClientServerAddress

Смотрите DHCP server, lease times, DNS и gateway вместе. Команды release/renew не включены в обычный диагностический набор для удалённого доступа: release может немедленно оборвать SSH/RDP. Сначала сохраняют текущую конфигурацию и обеспечивают консоль. Если два DHCP-сервера раздают разные шлюзы, проблема может быть случайной от загрузки к загрузке — победит разное предложение.

15. VLAN на Linux: что именно создаёт подинтерфейс

Следующий пример — только для отдельной учебной ВМ, где eth1 подключён к лабораторному trunk с разрешённым VLAN 100. Он не применяется к интерфейсу текущего SSH-соединения. Linux-подинтерфейс добавляет/снимает тег для соответствующего трафика; он не настраивает коммутатор автоматически.

sudo ip link add link eth1 name eth1.100 type vlan id 100
sudo ip address add 198.18.100.2/24 dev eth1.100
sudo ip link set eth1 up
sudo ip link set eth1.100 up
ip -d link show dev eth1.100
ip route get 198.18.100.1
sudo tcpdump -ni eth1 -e 'vlan 100'

# Уборка созданного подинтерфейса:
sudo ip link delete eth1.100

link eth1 указывает нижележащий интерфейс, name задаёт имя нового, type vlan id 100 выбирает тип и тег. ip -d показывает подробности, включая vlan id. Адрес назначается eth1.100, а не физическому eth1. Эти runtime-команды не обещают сохранения после перезагрузки: постоянная настройка выполняется штатным сетевым менеджером ОС. На приёме VLAN offload может повлиять на вид тега в захвате — это ещё один случай из раздела про точки наблюдения.

Если на коммутаторе порт access VLAN 100, а Linux отправляет tagged VLAN 100, трактовка зависит от конфигурации порта и может привести к отбрасыванию. Если обе стороны trunk, но VLAN 100 не разрешён на одном промежуточном линке, локальные интерфейсы будут UP без сквозной связности. Link UP говорит о физическом/виртуальном линке, а не о разрешённых VLAN и маршрутах.

Дополнительные стандарты: UDP, Internet checksum, DHCPv4, DHCP options. После этих опытов возвращайтесь к DNS: теперь видно, кто выдал адрес резолвера и как пакет вообще до него дошёл.

Для углубления: IPv4, RFC 791, ARP, RFC 826, IPv6, RFC 8200, TCP, RFC 9293, Traditional NAT, RFC 3022. Практические примеры выше авторские; модель одного пути намеренно не включает ECMP, MPLS и туннельные оверлеи.
