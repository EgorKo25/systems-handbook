FreeIPA: собрать домен

FreeIPA объединяет каталог идентичностей, Kerberos, управление сертификатами и политики доступа. Сервер отвечает на несколько разных протоколов. Успешное ipa user-find доказывает работу HTTP API под текущим principal, но не доказывает корректность SSH-входа, HBAC, sudo, мандатных меток или роли оператора в ДО. В этой главе мы проследим связи и соберём отдельный учебный домен.

1. Какие процессы образуют домен

Клиент SSSD / IPA CLINSS · PAM · APIApache HTTPSRPC · веб-интерфейсDogtag CAсертификаты389 Directory ServerLDAP · записи · ACIKerberos KDCTGT · service ticketsBIND, если установленA · PTR · SRVcertmonger следит за сертификатами; chrony — за временем.Схема ответственности, а не полный перечень внутренних RPC и портов.

 | Компонент | Данные / ответственность | Отдельная проверка

 | 389 Directory Server | Пользователи, группы, узлы, сервисы, политики; LDAP schema и ACI | LDAP bind/search, состояние экземпляра dirsrv

 | MIT KDC с IPA backend | Выдача билетов; ключи principal связаны с каталогом | kinit, kvno, журнал KDC

 | Apache и IPA API | Административные команды и веб-интерфейс | Kerberos login и JSON RPC с error:null

 | Dogtag CA | Выпуск сертификатов и инфраструктура доверия | Сроки сертификатов, состояние CA, запросы certmonger

 | SSSD на клиенте | Получение и кеширование identity; PAM access и authentication | getent, id, sssctl, отдельный PAM/SSH-вход

 | DNS | Поиск адресов и служб; может быть внешним | dig A/PTR/SRV к конкретному серверу

SSSD — не маленький контроллер домена. Он хранит клиентский кеш и обслуживает локальные запросы. NSS отвечает на вопрос «какие UID/GID и группы у имени», PAM участвует в аутентификации и допуске к сеансу. id user может работать из кеша, когда KDC недоступен. Существующая SSH-сессия тоже может продолжать работать после отказа контроллера. Поэтому для проверки домена нужен новый вход и отдельная проверка получения билета.

2. Как выглядит LDAP изнутри

dc=lab,dc=test
└── cn=accounts
    ├── cn=users
    │   └── uid=student
    ├── cn=groups
    ├── cn=computers
    └── cn=services

dn: uid=student,cn=users,cn=accounts,dc=lab,dc=test
uid: student
givenName: Иван
sn: Учебный
mail: student@lab.test
uidNumber: 120000001
gidNumber: 120000001
krbPrincipalName: student@LAB.TEST
nsAccountLock: FALSE

DN — distinguished name, адрес записи в дереве каталога. Левая часть наиболее конкретная; родитель читается вправо. UID здесь строковый login, uidNumber — числовой Unix UID. Это разные поля. Значения атрибутов в LDAP часто многозначные: несколько email или principal aliases допустимы по схеме соответствующего атрибута. Порядок набора значений не обязан выражать «основной». Canonical principal помогает выбрать основное имя; у некоторых записей его может не быть, как у admin с alias root.

ObjectClass определяет допустимые и обязательные атрибуты. Нельзя ожидать, что у каждой записи заполнены телефон, должность, подразделение и отчество. Даже существующий атрибут может быть недоступен читающему principal по ACI. «Поля нет в ответе» означает отсутствие полученного значения, но не всегда отсутствие значения на сервере. Клиент должен различать бизнес-обязательность для формы ДО и обязательность LDAP schema.

LDAP работает сообщениями с messageID и операциями bind/search/modify и т. д., закодированными BER. У search есть base DN, scope (base, one-level, subtree), filter, список атрибутов и limits. Несколько SearchResultEntry завершаются SearchResultDone с кодом результата. Поэтому «получили пять записей» не означает «нашли всех»: завершение может сообщить sizeLimitExceeded. Paged Results использует cookie продолжения, но поддержка и ограничения сервера всё равно важны.

ldapsearch -LLL -Y GSSAPI -H ldap://ipa.lab.test \
  -b 'cn=users,cn=accounts,dc=lab,dc=test' \
  -s sub '(uid=student)' uid givenName sn mail uidNumber krbPrincipalName

Команда выполняется на enrolled-клиенте после kinit. -LLL убирает часть служебного LDIF-оформления; -Y GSSAPI выбирает SASL Kerberos; -H задаёт LDAP URI; -b задаёт корень поиска; -s sub разрешает вложенные записи. Набор атрибутов в конце ограничивает ответ. Проверяйте согласованный SASL security layer; ldap:// само по себе не означает TLS, а применение GSSAPI не повод игнорировать фактический SSF. Для LDAPS проверяются имя и CA сертификата.

LDAP filter и DN имеют разные правила escaping. В фильтре пользовательская звёздочка должна экранироваться как литерал, если поиск не предполагает wildcard. В DN особое значение имеют запятые, плюсы и ведущие/замыкающие пробелы. Ни SQL escaping, ни URL encoding не заменяют эти правила. В коде применяют функции LDAP-библиотеки; подстановка строки из формы в готовый фильтр создаёт LDAP injection.

3. Четыре имени, которые надо согласовать до установки

 | Сущность | Учебный пример | Второй учебный пример

 | FQDN сервера | ipa.lab.test | ipa.lab.example.test

 | DNS domain | lab.test | lab.example.test

 | Kerberos realm | LAB.TEST | LAB.EXAMPLE.TEST

 | LDAP base DN | dc=lab,dc=test | dc=lab,dc=example,dc=test

Realm обычно записывают в верхнем регистре по соглашению, но это отдельное имя, а не DNS-запрос. Смена realm после установки — не редактирование одной строки конфигурации. FQDN входит в service principals, сертификаты, DNS и записи хоста. DHCP не должен неожиданно переименовывать контроллер. Нельзя создавать второй независимый IPA/AD realm с тем же доменным пространством, надеясь, что DNS сам выберет правильный.

До установки выберите также диапазон UID/GID, внутренний источник времени, способ DNS-делегации, адреса, резервирование и место резервных копий. Существующие файлы принадлежат числовым UID, поэтому новый домен с похожими логинами, но другими UID не становится автоматически владельцем старых файлов.

4. Полная учебная установка сервера

Это создание нового учебного домена на чистой ВМ, не ремонт office.example.test. Пример пакетных команд рассчитан на семейство Enterprise Linux 9 с доступными репозиториями IPA. Astra использует свои пакеты, интеграцию безопасности и установочные процедуры; переносить на неё dnf-команды нельзя. Пакеты этой лаборатории на флешку не включены.

Выделим серверу 198.18.0.10/24, клиенту 198.18.0.20/24 в отдельной виртуальной сети. Это учебный диапазон, его не маршрутизируют в рабочий контур. Статический адрес задаётся средствами вашей ВМ/ОС до установки. Нужны hostname ipa.lab.test и согласованное прямое/обратное разрешение. Если до установки DNS ещё нет, временная запись hosts помогает проверить имя самого сервера, но не заменяет будущие SRV-записи для клиентов.

hostnamectl set-hostname ipa.lab.test
hostname -f
ip -br address
timedatectl
chronyc tracking
dnf install ipa-server ipa-server-dns
ipa-server-install --help

Команды выполняются root на новой ВМ сервера. hostnamectl меняет постоянное имя; hostname -f проверяет результат через локальное разрешение. chronyc tracking показывает выбранную синхронизацию, смещение и состояние chrony. Наличие процесса chronyd ещё не значит, что часы синхронизированы. В закрытой сети нужен внутренний NTP, а не надежда на интернет. IPv6-стек на IPA не отключают полностью, даже если пользователи работают по IPv4.

ipa-server-install \
  --hostname=ipa.lab.test \
  --domain=lab.test \
  --realm=LAB.TEST \
  --ip-address=198.18.0.10 \
  --setup-dns \
  --no-forwarders

Инсталлятор задаст вопросы о Directory Manager, admin и DNS. Это две разные административные личности; пароли вводятся интерактивно. --setup-dns включает интегрированный DNS; --no-forwarders не настраивает пересылку внешних запросов. Это не firewall и не гарантия отсутствия попыток рекурсии через root hints. Для закрытой лаборатории ограничьте сетевой выход топологией и проверяйте только собственную зону. Обратную зону можно создать по предложению инсталлятора, предварительно убедившись, что она относится к вашей учебной сети.

Если используется внешний DNS, не указывают --setup-dns и заранее публикуют требуемые записи. Это отдельный вариант установки; нельзя одновременно считать IPA владельцем зоны и вручную поддерживать её независимую несовпадающую копию на другом сервере.

firewall-cmd --get-services
firewall-cmd --permanent --add-service=freeipa-4
firewall-cmd --permanent --add-service=dns
firewall-cmd --reload
ipactl status
kinit admin
ipa ping
dig @198.18.0.10 ipa.lab.test A
dig @198.18.0.10 _ldap._tcp.lab.test SRV
dig @198.18.0.10 _kerberos._udp.lab.test SRV

Firewall-команды применимы при работающем firewalld и наличии названных service definitions; сначала их проверяют. Изменяется учебная ВМ. --permanent сохраняет правило, reload применяет постоянную конфигурацию. На рабочем узле сначала выбирают нужную zone и изучают действующие правила: здесь показан простой случай новой ВМ. ipactl собирает состояние служб IPA, ipa ping проверяет API, dig проверяет записи DNS. Ни одна из этих проверок не заменяет остальные.

5. Подключить чистый клиент и увидеть созданные файлы

Клиент должен использовать DNS, который знает lab.test. Установите его адрес через NetworkManager или штатный механизм ОС, а не редактированием автоматически генерируемого resolv.conf. FQDN клиента — client.lab.test, адрес — 198.18.0.20. Сервер и клиент должны видеть друг друга по согласованным именам. Нужна синхронизация времени.

hostnamectl set-hostname client.lab.test
dnf install ipa-client
dig _ldap._tcp.lab.test SRV
ipa-client-install --domain=lab.test --mkhomedir

--domain указывает область discovery, --mkhomedir настраивает создание домашнего каталога при первом входе. Уполномоченные enrollment credentials вводятся по запросу. Явный --server=ipa.lab.test используется при необходимости фиксировать сервер; это осознанное изменение discovery, не обязательная настройка для каждого клиента. Не переносите keytab уже зарегистрированного хоста на новую машину с другим именем.

 | Файл/система клиента | Что появилось | Чего это не даёт автоматически

 | /etc/ipa/default.conf | Домен, realm, сервер/API, base DN | Пароль администратора

 | /etc/ipa/ca.crt | Доверенный CA IPA | Отключение проверки имени TLS

 | /etc/krb5.conf и includedir | Настройка Kerberos | Пользовательский TGT в каждом процессе

 | /etc/krb5.keytab | Ключ host/client.lab.test | Ключ HTTP/client.lab.test, если сервис не зарегистрирован

 | /etc/sssd/sssd.conf | Identity/auth/access provider и домен | Роль admin в приложении ДО

 | NSS/PAM | Интеграция поиска пользователей и входа | Право sudo для всех доменных пользователей

grep -E '^[[:space:]]*(server|realm|domain|basedn|xmlrpc_uri)[[:space:]]*=' /etc/ipa/default.conf
getent passwd student
id student
kinit student
klist
sssctl domain-status lab.test

Student должен быть создан на сервере, как в следующем разделе. sssctl может требовать пакет sssd-tools и права root. Не публикуйте полный sssd.conf: в иных конфигурациях там бывают секреты. Кеш SSSD не очищают удалением всей /var/lib/sss на работающей машине. Для конкретного пользователя применяют штатное истечение кеша sss_cache -u student, затем повторный запрос; это не смена пароля и не очистка Kerberos-билетов.

6. Учётная запись, группа, право и роль

kinit admin
ipa user-add student --first=Иван --last=Учебный --email=student@lab.test --password
ipa group-add course-users --desc='Учебные пользователи'
ipa group-add-member course-users --users=student
ipa user-show student --all --raw
ipa group-show course-users --all

Создание пароля может требовать смены при первом пользовательском входе; проверьте этот сценарий отдельно. Команды меняют только учебный домен. --all просит расширенный набор атрибутов, --raw оставляет технические имена. ipa user-show student принимает login записи; student@LAB.TEST — principal, и он не обязан быть ключом команды user-show.

В административной модели IPA permission описывает разрешённые действия над объектами/атрибутами, privilege объединяет permissions, role объединяет privileges и назначается участникам. Группа users — удобное множество сотрудников, но сама по себе не равна role. Группа admins имеет особые полномочия в домене. Приложение ДО отдельно хранит отношения users/roles; доменный admin не должен автоматически становиться администратором каждого приложения без согласованной политики.

ipa role-find
ipa privilege-find
ipa permission-find
ipa user-find --sizelimit=5
ipa user-find --all --raw --sizelimit=0

Ноль в sizelimit просит отсутствие клиентского лимита этого вызова, но серверные ограничения и права всё равно учитываются. Всегда проверяйте признак усечения. Для формы выбора сотрудника нужен поиск с ограничением и явная обработка неполноты, а не молчаливое «нашли всех» после первых пяти записей. Служебные аккаунты не следует определять только по наличию ФИО: это бизнес-критерий отдельного фильтра.

7. HBAC: разрешить вход конкретной группе на конкретный узел

ipa hbacrule-add course-ssh
ipa hbacrule-add-user course-ssh --groups=course-users
ipa hbacrule-add-host course-ssh --hosts=client.lab.test
ipa hbacrule-add-service course-ssh --hbacsvcs=sshd
ipa hbactest --user=student --host=client.lab.test --service=sshd --rules=course-ssh

Правило связывает пользователя/группу, host/hostgroup и PAM service. Оно не проверяет пароль и не выдаёт sudo. hbactest моделирует правило на сервере; успешный результат не заменяет фактический SSH-вход через клиентский PAM/SSSD. Имена PAM services должны соответствовать использующему их приложению.

После установки может действовать широкое правило allow_all. Пока оно включено, новое узкое правило не ограничивает остальных: достаточно любого подходящего разрешения. В этой лаборатории сначала проверяют новое правило и сохраняют доступ через консоль локального администратора. Только в отдельной учебной среде, где учтены остальные входы, можно выключить allow_all и проверить положительный и отрицательный сценарии. На рабочем домене это изменение общей политики, а не локальная проверка формы ДО.

ipa hbacrule-show allow_all
ipa hbacrule-disable allow_all
# Проверка нового входа student на client.lab.test из другого терминала.
# Возврат исходной учебной политики:
ipa hbacrule-enable allow_all

Sudo-политики — отдельный слой. Успешный SSH без sudo является нормальным результатом, если sudo не выдавали. Диагностика выполняется sudo -l из сеанса нужного пользователя. Не выдавайте ALL:ALL только для того, чтобы проверить чтение каталога через API.

8. HTTP API: Kerberos login, cookie, JSON-ошибка

Команда ipa — клиент API. Для ДО удобен тот же HTTP-интерфейс: аутентифицироваться делегированным кешем, сохранить cookie в рамках одного CGI-вызова и выполнить user_find. Общий cookie одного администратора для всех пользователей изменил бы модель полномочий. Сырой LDAP остаётся другим интерфейсом с другой схемой ответов и контролем доступа.

(
  set -eu
  umask 077
  cookie=$(mktemp)
  trap 'rm -f -- "$cookie"' EXIT
  ipa_host=ipa.lab.test
  curl --silent --show-error --fail \
    --connect-timeout 10 --max-time 30 \
    --cacert /etc/ipa/ca.crt --negotiate -u : \
    -H "Referer: https://$ipa_host/ipa" \
    -c "$cookie" -X POST -o /dev/null \
    "https://$ipa_host/ipa/session/login_kerberos"
  curl --silent --show-error --fail \
    --connect-timeout 10 --max-time 30 \
    --cacert /etc/ipa/ca.crt -b "$cookie" \
    -H "Referer: https://$ipa_host/ipa" \
    -H 'Content-Type: application/json' \
    --data '{"method":"user_find","params":[["student"],{"sizelimit":5}],"id":1}' \
    "https://$ipa_host/ipa/session/json"
  printf '\n'
)

Подоболочка ограничивает переменные и trap. umask 077 закрывает cookie от других пользователей; mktemp создаёт уникальный файл; trap удаляет его и при ошибке. --negotiate -u : запускает SPNEGO без передачи парольной пары. --cacert сохраняет проверку TLS по CA домена. -c записывает cookie, -b читает. Таймаут соединения и общий таймаут ограничивают разные этапы. --fail проверяет HTTP-код, но не JSON-поле error — его приложение обязано разобрать отдельно.

API version — версия контракта команд, а не версия HTTP или установленной ОС. Сервер может предупредить VersionMissing и назвать свой API, например 2.239. Это не повод зашить 2.239 как вечную константу всех FreeIPA. Выбор версии должен соответствовать совместимости клиента и сервера; server product version 4.8.10 — другое число. Аналогично result.truncated=true означает, что список неполный, даже при error:null и HTTP 200.

9. Как приложение определяет IPA динамически

Enrolled-машина уже знает параметры домена. Для нашего CGI опорная точка — локальный /etc/ipa/default.conf и доверенный CA. Это позволяет одному комплекту работать на office.example.test и lab.example.test без адреса контроллера, зашитого в Go. Конфигурация относится к машине, credentials — к текущему пользователю. Их нельзя смешивать: KRB5CCNAME не является адресом IPA, а server из default.conf не доказывает наличие действующего TGT.

DNS SRV нужен для discovery/failover соответствующих клиентов. Один параметр server в файле не равен полноценному алгоритму перебора реплик; если приложению нужен failover, его поведение проектируют явно. При выборе другого контроллера всё равно проверяется CA и имя сертификата. Произвольный URL из пользовательского запроса использовать нельзя: это одновременно риск утечки credentials и запросов сервера к нежелательным адресам.

dig _ldap._tcp.lab.example.test SRV
dig _kerberos._tcp.lab.example.test SRV
grep -E '^[[:space:]]*(server|xmlrpc_uri|realm|basedn)[[:space:]]*=' /etc/ipa/default.conf
openssl x509 -in /etc/ipa/ca.crt -noout -subject -issuer -dates

Первые команды показывают DNS-публикацию; grep — настройку именно этого клиента; openssl читает метаданные локального сертификата, не его приватный ключ. Если они расходятся, сначала выясняют историю enrollment и адрес DNS. Переписывание hosts не исправляет неправильный realm или чужой CA.

10. Репликация, сертификаты и резервное восстановление

Реплика IPA — ещё один контроллер того же домена, а не новый сервер с таким же названием realm. У него согласованные каталожные данные и ключевая инфраструктура. Топология каталога и наличие CA-роли требуют отдельных проверок. Отказ единственного CA может не остановить выдачу TGT немедленно, но позже сломает выпуск и продление сертификатов. Поэтому «пользователи входят» не означает, что все роли реплики здоровы.

ipa server-find
ipa topologysegment-find domain
ipa topologysegment-find ca
ipa-healthcheck --failures-only
getcert list

Команды чтения выполняются с подходящими правами на IPA; ipa-healthcheck должен быть установлен и поддерживаться сборкой. CA suffix может отсутствовать, если встроенная CA не развёрнута. getcert list показывает заявки certmonger, состояние и сроки; файл сертификата проверяют также openssl x509. Не удаляют каталоги сертификатов ради устранения просрочки — сначала выясняют, кто должен их продлевать.

Снимок ВМ удобен в одиночной лаборатории. Возврат старого снимка одного контроллера в живой реплицируемый домен — другой риск: время, пароли, сертификаты и репликационное состояние уже изменились. Для домена используют поддерживаемый порядок ipa-backup/ipa-restore с планом реплик и проверкой восстановления. Резервная копия содержит ключи и каталог; её доступ защищают как административный доступ к домену.

11. Проверка снизу вверх и уборка лаборатории

 | Что не работает | Что уже доказано | Следующая проверка

 | getent есть, kinit нет | Identity могла прийти из кеша | KDC discovery, время, principal и состояние учётной записи

 | kinit есть, ipa ping нет | Получен TGT | HTTP principal, TLS CA/имя, порт 443, API

 | ipa user-find есть, SSH нет | API доступен данному principal | PAM, HBAC, sshd, домашний каталог, локальные ограничения

 | SSH есть, sudo нет | Вход разрешён | Sudo policy и членство групп, а не пароль от FreeIPA

 | CGI не видит IPA, shell видит | Работает только shell-контекст | UID, метка, FILE-кеш, окружение CGI, CA и сетевой доступ этого контекста

После обучения чистые ВМ можно удалить вместе с учебным realm. Если сохраняете сервер, удалите созданные правила/аккаунты штатными ipa-командами, учитывая их зависимости. ipa-client-install --uninstall меняет регистрацию и локальную конфигурацию клиента; это не команда очистки кеша. Не запускайте её на spo1 для проверки списка пользователей. Практический порядок восстановления рабочего ДО находится в основном справочнике, вне лабораторного домена.

Источники: планирование FreeIPA, параметры установки 4.8, клиент и discovery 4.8, HBAC и allow_all, LDAP protocol, DN, фильтры LDAP. Для основания механизмов см. DNS и Kerberos.
