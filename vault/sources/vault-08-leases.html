TTL, renewal и отзыв

Время жизни ограничивает следующий доступ, но разные сроки относятся к разным объектам.

Сначала объект, затем часы

TTL, time to live, — оставшееся время допустимого действия объекта. У token есть срок API-доступа. У динамического credential есть lease, «аренда»: Vault хранит идентификатор выдачи, срок и обработчик продления/отзыва движка. У сертификата есть notAfter, проверяемое TLS-участниками, и отдельная процедура revocation. У статического KV-пароля внешний срок может вообще отсутствовать. Число lease_duration в одном JSON нельзя переносить на все эти объекты.

Lease ID связывает выдачу с обработчиком, но не заменяет username/password. Renewal просит продлить пригодный объект до истечения; ответ сервера содержит фактически выданный срок, который может быть короче запрошенного increment. Renewal не обязан менять строку пароля. Revoke инициирует прекращение полномочий и cleanup во внешней системе. Если PostgreSQL недоступен, отзыв может не завершиться с первой попытки; наличие просроченной записи в очереди требует диагностики, а не утверждения «всё уже недействительно».

Как составляется предел

Есть server defaults, tune mount/auth method, параметры роли, собственный запрос token/credential и max TTL движка. Это не простое правило «последний флаг побеждает»: каждый слой может ограничивать результат. Explicit max TTL закрепляет абсолютный предел токена; его нельзя обойти периодическими renewals. Periodic token при соблюдении renewal может продолжать жить периодами, но требует специального полномочия выдачи и не должен случайно стать бессрочным приложению. Batch token не предоставляет тот же renewal-контракт, что service token.

Обычный дочерний token связан с родителем. Отзыв родителя каскадно отзывает детей и связанные leases; expiration имеет аналогичные последствия в соответствующем дереве. Orphan token отделяет эту родительскую связь, а не отменяет policy, TTL и возможность прямого revoke. Бесконтрольное использование orphan затрудняет остановку целого deploy. В нашем bootstrap orphan нужен строго для того, чтобы отзыв первоначального root не уничтожил ограниченного оператора; приложения получают обычный auth method token.

В момент выдачи t=0 срок 8h означает истечение в t=8h. Если сервер принимает increment 8h при t=6h, новый срок отсчитывается от renewal: до t=14h. Следующие успешные renew при t=12h и 18h дадут концы 20h и 24h, причём последний оставит только 6h до абсолютного предела. Здесь предполагаются renewable=true и отсутствие более строгого ограничения auth/mount. Проверяйте возвращённый TTL, а не одну эту формулу. Если убрать renew в 6h, следующего шага в 12h уже не будет: token истечёт в 8h и потребует нового получения доступа. Для нашего Shamir-оператора это явная recovery-процедура.

Опыт в секундах

В главе KV уже выполнен единственный комплексный checks; здесь читаем его checks.json и разбираем этапы, повторять сценарий нельзя. На исходном состоянии он создаёт отдельный reader token с TTL 3s, сразу проверяет HTTP 200, ждёт четыре секунды и получает HTTP 403 на том же пути. Затем другой token отзывается через API и тоже получает 403. Секретное тело и credential не печатаются. Ожидаемый summary перечисляет обе ветви; это настоящий серверный тест, не изменение часов browser-модели.

Ручной renewal ниже по маршруту доступен только после AppRole09/Agent12: сначала получите свежий application token в private/agent.token, затем используйте отдельный блок ниже. До этого места разберите результат checks.json; bootstrap root для опыта не нужен. С пригодным application token vault token lookup показывает ttl/renewable/explicit_max_ttl, vault token renew -increment=30s просит новый срок. Оба действия выполняют только после загрузки адреса/CA из env.sh и чтения токена из private. Renew печатает токен в стандартном табличном выводе ряда CLI версий, поэтому настоящий результат перенаправляют в частный 0600 файл или используют helper/Go-клиент, который не выводит credential. Ошибка renewable=false или истечение означает новый login по доверенному механизму, а не повторное чтение старой строки.

Этот необязательный блок выполняется после успешного Agent12, cwd vault/labs, stand прежний, application token ещё действует. umask 077 закрывает новые файлы от других UID, env.sh выбирает TLS/CA и свой token helper. Два JSON результата могут содержать token, поэтому остаются в private.

set -euo pipefail
umask 077
. "$stand/env.sh"
read -r VAULT_TOKEN < "$stand/private/agent.token"
export VAULT_TOKEN
vault token lookup -format=json > "$stand/private/application-lookup.json"
vault token renew -increment=30s -format=json > "$stand/private/application-renew.json"
unset VAULT_TOKEN

Код 0 означает успешные lookup/renew; -format=json сохраняет машинные поля, -increment=30s запрашивает 30 секунд от момента renewal, не добавляет 30 к старому остатку. Сверьте auth.renewable/auth.lease_duration в private ответе. При 403/ошибке зависимая команда не идёт дальше; получите новый Agent token, не меняя CA/KV. После неуспеха очищают VAULT_TOKEN в той же shell, если она осталась открытой.

Приложение и граница отказа

Клиент начинает renewal заранее с запасом под сеть и jitter. Jitter, случайное смещение времени, распределяет одновременные обращения многих экземпляров. Если остаток 30s, интервал повтора 60s бессмыслен. Перед новой попыткой проверяют общий deadline и context cancellation. Ошибки 403 и неподдержанный renewal не лечат бесконечной экспоненциальной паузой; временную сетевую ошибку можно повторить в ограниченном окне, пока credential ещё действует.

После нового динамического credential приложение создаёт новый connection pool, проверяет доступность, постепенно выводит старые соединения и только затем отзывает старую аренду по процедуре приложения. Строка connection URL в environment процесса сама не обновит уже открытые соединения. Если процесс продолжает работать со старым pool, «Vault успешно обновил секрет» не равняется «приложение перешло на новый доступ».

Отзыв не стирает полученный пароль из памяти. Его смысл — принимающая система перестаёт давать новые полномочия и, если реализован специальный контракт, ограничивает существующие сессии. PostgreSQL VALID UNTIL проверяет срок пароля при установлении соединения, не закрывает работающий TCP-сеанс. Сертификат в established TLS-session также не проверяется заново на каждый байт. Поэтому измеряют отдельно время успешной revocation-команды, время запрета нового login и время прекращения старой работы.

Первоисточники: lease, renew, revoke; родители, orphan, periodic и explicit max TTL; lease API.
