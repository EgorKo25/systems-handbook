Integrated storage и HA: согласованная история

Raft помогает пережить потерю участника при сохранённом большинстве, но не заменяет резерв и не превращает один host в несколько зон отказа.

Откуда берётся единственный writer

Integrated storage хранит защищённое состояние Vault внутри процессов Vault. Raft — алгоритм согласования последовательности записей. Каждый участник имеет устойчивый node_id, текущий term, журнал и применённое состояние. Term — монотонный номер эпохи выборов; он помогает отвергать решения старого лидера, но не является временем wall clock. Участник бывает follower, candidate или leader. Клиентские роли Vault active/standby и роль Raft в этой конфигурации связаны: active узел является лидером, обычные standby — followers.

Follower получает heartbeat лидера и новые log entries. При длительном отсутствии допустимого лидера он может стать candidate и запросить голоса следующего term. Для выбора нужен quorum — большинство голосующих. Для трёх voters большинство 2, для пяти 3, для двух 2. Поэтому добавление второго узла к одному не создаёт способность пережить потерю одного voter. Разные процессы на одной машине позволяют изучать протокол, но потеря общей ОС, питания или диска затрагивает их вместе.

Что подтверждает write

Лидер добавляет запись в durable log и передаёт followers. После достаточного подтверждения запись считается committed, затем применяется к state machine, «машине состояния», которая одинаково исполняет одинаковую упорядоченную историю. Vault блокирует writes до commit и apply. Ответ клиенту ещё должен пройти аудит и сеть. Наличие неподтверждённой записи в локальном log старого лидера не даёт права выдать её как общекластерный успех после разделения сети.

Наш одиночный voter имеет quorum из самого себя и не ждёт второй машины. Нативный опыт snapshot/restart подтверждает сохранение данного экземпляра, а не сетевое согласование. На диске у Raft есть журнал и применённые данные; их внутренние файлы не следует копировать по одному во время работы и считать согласованной копией. Автоматическая compaction/snapshot протокола ограничивает журнал, но отличается от экспортированного оператором backup.

В конфигурации 1.21 default Raft log storage и альтернативный экспериментальный WAL надо рассматривать отдельно. Удаление логических значений не обещает немедленного уменьшения файла BoltDB: свободные страницы могут переиспользоваться внутри файла. Быстрый рост/fragmentation и snapshot передачи влияют на задержки диска. Измеряют реальные файлы, apply lag и I/O, прежде чем менять storage library или performance_multiplier.

Куда идёт запрос standby

Обычный standby Community не становится независимым writer и не является Enterprise performance standby. Он может переслать запрос active через внутренний канал; при невозможности forwarding применяется предусмотренный redirect к объявленному api_addr. Клиенту нужны допустимый адрес, доверие TLS и политика переноса token. Наш Go-пример отклоняет redirect и требует принятого active endpoint, поэтому при HA его дорабатывают по явному контракту, а не предполагают успех любой URL.

Load balancer — отдельный маршрутизатор перед кластером. Health endpoint 200 обычно указывает active, 429 — standby; query-параметры health могут менять коды для интеграции. Они не меняют роль сервера. Если балансировщик считает любой 503 поводом уничтожить storage, ошибка операционной политики усилит отказ. Sealed узел, standby и uninitialized узел имеют разные состояния; liveness не должна автоматически переинициализировать кластер.

Join и восстановление большинства

Новый узел получает свою конфигурацию/listener/TLS/storage, но не отдельный init данных. Join требует доверия к leader API и прохождения криптографического challenge; при Shamir понадобятся пригодные unseal keys для присоединённого состояния. Для реального multi-host рецепта заранее задают маршрутизируемые адреса, CA/SAN, разные data directories, ports, access controls, сохранение shares и ресурсы диска. Здесь это описанный план, не запуск чужой сети.

Оператор в собственном active stand, cwd labs, с operator token может выполнить vault operator raft list-peers. Ожидается единственная строка handbook-one, state leader, voter true. Код 0 и одна строка являются доказательством peer list этого стенда, а не тестом HA. Ошибка sealed/403 требует проверки unseal/ACL, пустое ожидание других узлов не лечат повторным init.

При partition3 узлов на 2+1 только сторона 2 способна сохранять quorum. Сторона 1 не должна обслуживать согласованные writes. После возврата лидер согласует историю, а неподтверждённый хвост может быть заменён. Утрата quorum не исправляется произвольным remove-peer на каждом острове: неверная emergency peers-конфигурация способна создать конфликтующие истории. Сначала останавливают клиентские записи по аварийной процедуре, собирают данные узлов и резерв, затем выполняют документированную recovery-процедуру с выбранной авторитетной историей.

Свой проверяемый HA-план содержит fault matrix: остановка одного follower, лидера, разрыв одного направления, заполнение диска, потеря двух voters; для каждой ветви — ожидаемая доступность, число успешных writes, время до ready и исход каждого request ID. До его реального исполнения нельзя публиковать «переключение за N секунд» или «без потерь». Replication Enterprise между кластерами — ещё один протокол и граница лицензии; Raft followers одного кластера не являются DR replication.
