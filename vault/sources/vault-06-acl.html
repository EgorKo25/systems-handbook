ACL: право на путь и реальный отказ

Проверим ровно тот путь и ту операцию, которые исполняет сервер, и сохраним разрешения приложения отдельно от оператора.

Capabilities до первой policy

Capability — имя разрешённой операции API. read читает, list перечисляет имена, delete удаляет, create создаёт, update меняет, patch частично обновляет поддерживающий это endpoint. Не каждый endpoint различает create и update: движок должен уметь определить существование объекта. sudo даёт допуск к root-protected операции только вместе с требуемой capability; это не shell sudo и не самостоятельное «разрешить всё». deny запрещает, а отсутствие подходящего разрешения тоже приводит к отказу.

Policy — именованный набор ACL-правил HCL, который оператор загружает в Vault; файл на диске клиента сам не влияет на сервер. Токен ссылается на имена policy, а не хранит вечную копию текста всех правил. Обновление policy может изменить доступ уже выданного токена. Исключение особого root policy требует особого обращения: root не является удобным способом диагностики того, что разрешено приложению.

Три субъекта нашего стенда

Среда: предыдущие главы приняты, unsealed active, cwd vault/labs, обычный владелец. Provision — одноразовый шаг над пустым учебным secret/. Не повторяйте его поверх изменённых данных: первая запись использует CAS 0 и специально завершится ошибкой, сохранив имеющийся ключ.

set -euo pipefail
python3 lab.py --root "$stand" provision
. "$stand/env.sh"
read -r VAULT_TOKEN < "$stand/private/reader.token"
export VAULT_TOKEN
vault kv get -mount=secret handbook/config
if vault kv put -mount=secret handbook/config message=blocked \
    > "$stand/private/expected-acl.out" 2> "$stand/private/expected-acl.err"; then
  echo "Неожиданный успех writer для reader" >&2
  exit 1
else
  result=$?
  test "$result" -eq 2
  grep -q 'Code: 403' "$stand/private/expected-acl.err"
fi

Provision включает KVv2, загружает reader, writer и application, записывает два синтетических значения, выдаёт reader/writer tokens на 10 минут и включает локальный аудит. Shell read -r читает token из 0600-файла без печати; export передаёт его дочернему CLI, не записывая в исходники. Cекреты всё равно доступны процессу этого UID: после опыта выполните unset VAULT_TOKEN. Не включайте shell tracing set -x.

Первый get имеет код 0. Второй put должен получить permission denied и ненулевой код: reader имеет read на secret/data/handbook/config, но не update/create. В shell с остановкой на ошибке проверяйте отказ в отдельном условии; следующие меняющие действия не должны автоматически исполняться после неожиданного кода. Чтобы увидеть ACL на стороне API без изменения, оператор может применить vault token capabilities secret/data/handbook/config со своим или тестовым token, но окончательный критерий — реальный запрос в тех же условиях.

LIST не равен READ

path "secret/data/handbook/config" {
  capabilities = ["read"]
}
path "secret/metadata/handbook/*" {
  capabilities = ["list"]
}
path "secret/data/handbook/forbidden" {
  capabilities = ["deny"]
}

Это содержимое reader policy, уже созданное комплектом. Чтение KVv2 использует data, перечисление ключей — metadata. Разрешение list на metadata не даёт read содержимого соседних секретов, а имена ключей сами могут быть чувствительными. Нельзя считать LIST ответ отфильтрованным перечнем всего, что клиент может прочитать: модель выдаёт имена по праву перечисления родительского пути. Поэтому в именах не размещают пароли, email и полезные атакующему персональные данные.

Явный deny на forbidden подготовлен для демонстрации. В обычной reader policy он совпадает с отсутствием allow; более сильная проверка добавляет второй policy с allow на тот же точный путь и убеждается, что deny сохраняет приоритет. Сценарий tests включает отдельную такую пробу. Это отличается от ситуации двух различных wildcard-путей: для разных совпавших шаблонов Vault выбирает приоритетный шаблон, а capabilities одинакового пути объединяет с приоритетом deny. Нельзя безусловно суммировать всё, что когда-либо совпало.

Wildcard имеет собственную грамматику

* в конце шаблона разрешает произвольный остаток после указанного префикса; это glob, не регулярное выражение. + заменяет один сегмент, разделённый косой чертой: secret/data/+/config отличается от secret/data/*. Политика secret/* охватывает и служебные KVv2 пути, если capability применима. Последовательность приоритета включает положение первого wildcard, наличие конечного glob, число +, длину и лексикографию; при спорном правиле проверяют точный путь capabilities и реальной операцией, не угадывают по зрительной длине.

В 1.21 изменена оценка list-valued параметров в allowed_parameters/denied_parameters. Эти ограничения не следует применять к вложенной KVv2 data как к универсальному фильтру отдельных полей: API KVv2 имеет специальный envelope, а ACL обычно ограничивает путь. Если два поля требуют разных читателей, разместите их по разным путям или выберите другую схему контроля. Default значения endpoint тоже не выводятся ACL evaluator автоматически: отсутствие параметра может отличаться от явно переданного false.

Безопасная проверка всех ветвей

В следующей главе комплексная команда checks из того же cwd использует подготовленные короткие токены, проверяет HTTP 403 для update и forbidden, HTTP 200 для LIST metadata и 403 для LIST data. Комплексный запуск выполняется один раз в следующей главе после выдачи свежих тестовых tokens; здесь рассматриваем эти ветви без нового исполнения. Ожидается summary с 13 checks и код 0; повторно на изменённом ключе этот одноразовый сценарий закономерно не подходит. Для независимого повтора создают другой root, а сохраняемый исходник продолжают осознанно. Не исправляют расхождение повторной provision или удалением всего mount.

Первоисточники: capabilities, wildcard и приоритет; KVv2 пути; token capabilities.
