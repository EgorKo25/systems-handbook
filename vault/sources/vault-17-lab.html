Продолжаемый стенд и независимый повтор

Один маршрут исполнения сохраняет историю. Повторные проверки выполняются на новой отдельной цели.

Контроль состояния до продолжения

Основной cwd — vault/labs личной копии книги, обычный владелец. Переменная stand содержит $HOME/handbook-vault. В главах 02–06 уже получены проверенная поставка, конфигурация, active Vault, revoked bootstrap root и provision: config version1, reader/writer tokens, audit. Если эти шаги уже сделаны, не повторяйте prepare/init/provision. При restart выполните start/unseal и проверьте status. Если прошло более 10 минут, тестовые reader/writer tokens могли истечь: новый операторский выпуск short-lived тестовых токенов — осознанное действие, описанное ниже.

Ручные примеры KV07 являются альтернативой комплексной ветви: они тоже меняют version1→3. Если прошли их вручную, не исполняйте checks над тем же ключом. Сохранённые state и metadata расскажут результат, а fresh automated suite запускается на другом stand. Идея лаборатории — видеть переходы, а не снова и снова получать пустой сервер.

Отчёт единственного запуска

По основному маршруту test-tokens/checks уже один раз выполнены в главе KV07. Здесь читают $stand/checks.json и metadata config, не вызывают checks снова. Должны быть 13 assertions, version3/message second/added yes, version2 destroyed. Если выбран ручной KV маршрут, сверяют его наблюдения с теми же критериями; автоматического отчёта тогда не выдумывают.

test-tokens выдаёт свежие reader/writer на 10m без изменения данных, но не возвращает исходный version1. Unseal тоже не продлевает token. Оператор без renewal истечёт уже через 8h; 24h — абсолютный предел с продлениями. Если lookup получил 403, используйте recover-operator с порогом Shamir. Init при продолжении запрещён. Для свежего целого автоматического повторения используют отдельный work-root ниже.

Продолжение выдачи

AppRole09, PKI11 и Agent12 имеют собственные точки исполнения. Если они уже выполнены, проверяйте сохранённые файлы/серверное состояние и summary, не создавайте повторно CA или новый credential ради галочки. Последовательность для ещё не выполненного: approle создаёт роль и один token; pki создаёт chain/leaf/revoke; agent выдаёт новый SecretID для своего one-shot login. Go-клиент собирают в private bin и запускают с действующим application token. Agent sink token может быть новым пригодным приложению token после однократного первого теста.

PostgreSQL — дополнительный независимый backend: prepare/start/bootstrap только при новом собственном PGDATA, затем единственный check с vault-root. Существующий общий с Flyway сервер требует согласованной подготовки SQL, не второго initdb. Код не запускает другую книгу. Snapshot/restore и measure находятся в своих главах и продолжают этот же Vault. Восстановленная цель — отдельное состояние, не «новое имя исходника».

Что считать принятым

  • Version и signature/hash поставки закреплены; listener принимает правильную CA и отвергает неправильную.
  • Init сделан один раз, shares доступны только хранителям, bootstrap root отозван; restart требует unseal и сохраняет config.
  • Полномочия reader/writer/application различаются реальным allow/deny, а не названием файла.
  • CAS защищает конкурентную запись; destroy не выдаётся за обратимый delete.
  • Новый PostgreSQL login после revoke запрещён; уже открытая сессия проверена отдельно.
  • PKI chain/SAN и serial в CRL проверены; внешнее распространение CRL не выдумано.
  • Snapshot принят отдельным restore, source не перезаписан; проверено отсутствие записей после точки.

Независимый автоматический повтор

native_repeat.py принимает путь уже проверенного бинарника и новый выделенный work-root, создаёт отдельные source/restore directories, выбирает свободные loopback порты, исполняет основные безопасные ветви и останавливает только собственные PID в finally. Он не скачивает runtime и не меняет системные службы. Это тестовый stand, отличающийся от продолжаемого reader stand; он не удаляет результаты автоматически. Команды и ограничения перечислены в README. Отдельный --pg-bin добавляет свой PostgreSQL; без него PG-ветвь не объявляется проверенной.

После опыта серверы останавливают helper stop, сохраняя state и snapshot. Удаление личных данных — отдельное принятое решение; ни книга, ни тест не делают автоматический reset. Для offline-чтения нужны только локальные HTML/assets, для запуска — заранее подготовленные runtimes и доверие. Иллюстрации показывают объясняемые состояния, а не подключаются к настоящему Vault из браузера.
