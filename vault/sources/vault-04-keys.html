Init, unseal и разные значения слова «ключ»

Разблокирование криптографического барьера и получение прав через токен — разные операции с разными хранителями.

Ключ шифрования не является root token

Barrier, «криптографический барьер», — слой, через который Vault шифрует сохраняемые защищённые значения перед передачей storage backend и расшифровывает их после чтения. Хранилище видит зашифрованные байты и служебные структуры; оно не должно знать секреты прикладного API. В оперативной памяти (RAM) unsealed процесса доступны ключи для работы barrier. В модели 1.21 данные шифруются ключами keyring, «набора ключей». Root key защищает этот набор, а unseal key защищает root key. Поэтому одна доля Shamir не является ключом, который можно подставить в AES и прочитать raft.db.

Init, «инициализация», создаёт первоначальное криптографическое состояние пустого storage и первичный административный токен. Init выполняют один раз на кластер, не при каждом запуске и не отдельно для каждого joining узла. Vault сохраняет защищённое состояние ключей в storage, а материал разблокирования передаёт хранителям. Повторный init существующего storage отклоняется; удаление каталога ради устранения этой ошибки было бы уничтожением данных.

Shamir secret sharing делит unseal key на доли. При трёх долях и пороге две нужны две разные пригодные доли. Две копии одной доли не образуют две части. Порядок подачи не важен; прогресс накапливается в памяти данного sealed узла. На нескольких узлах Shamir seal разблокируют каждый узел, не складывая «одну долю на первом + одну на втором» в общий порог. После restart прогресс и расшифрованные ключи теряются, данные storage остаются.

Какие байты защищает barrier

Версионная security model задаёт AES-256-GCM: AES использует 256-битный ключ, GCM добавляет проверку целостности/подлинности шифротекста. Для каждого шифруемого объекта генерируется случайный 96-битный nonce, дополнительное значение алгоритма; это не пароль клиента и не очередная доля Shamir. Повтор nonce с тем же ключом опасен для GCM, поэтому произвольное ручное переиспользование значения недопустимо. При чтении проверяется authentication tag, «тег аутентичности»: подмена защищённых байтов приводит к ошибке проверки, а не к тихому доверию изменённому plaintext.

Корректный tag доказывает целостность данного защищённого объекта относительно ключа, но не свежесть всей истории. Старый корректно зашифрованный snapshot тоже имеет правильные tags. Владелец произвольного storage-доступа способен удалить данные или вернуть прежнее согласованное состояние; barrier не является независимым защищённым счётчиком последнего backup. Поэтому защита от rollback требует контроля storage/операторов, внешнего журнала контрольных точек и проверки последствий restore. Шифрование защищённого значения и файловый формат Raft — разные уровни; схема ниже не задаёт байтовый layout raft.db.

Официальная security model1.21.x: AES/GCM, nonce, tag и границы storage rollback.

Сначала порог долей даёт unseal key; им получают root key, затем keyring и ключ для защищённого значения. В строке 2 keyring содержит ключи данных, включая нужный для строки 3. Seal убирает пригодные расшифрованные ключи из памяти; правые записи сохраняются. Отдельный root token предъявляется в API и не участвует в этой последовательности. При auto-unseal верхний способ открытия меняется на seal provider; нижняя задача защиты данных остаётся.

Контролируемая учебная церемония

Предпосылки: TLS listener работает, status показал initialized false, cwd vault/labs, владелец тот же. В лаборатории helper собирает доли в одном частном каталоге для повторяемости; это явно не разделение хранителей production. В реальной церемонии доли доставляют разным уполномоченным людям, часто с PGP-шифрованием ответа для каждого, и проверяют независимость хранения.

set -euo pipefail
python3 lab.py --root "$stand" init
python3 lab.py --root "$stand" status

init вызывает vault operator init -key-shares=3 -key-threshold=2 -format=json, перехватывает вывод, пишет private/init.json mode 0600 и подаёт две доли через локальный HTTPS API. Доли не идут в argv, журнал или публичный stdout. Затем создаётся broad учебная policy оператора, orphan token с TTL (time to live, текущим сроком действия) 8 часов и explicit max TTL 24 часа, и bootstrap root отзывается. Orphan означает отсутствие родителя в дереве токенов: отзыв root не отзовёт этого оператора каскадно. Это не свойство «неограниченных прав»: время и policy проверяются отдельно.

Ожидается initialized true, sealed false, standby false, HTTP 200. Helper отдельно проверяет, что прежний root получил HTTP 403. Если init завершился после создания состояния, но до сохранения долей, не запускайте init снова и не стирайте storage. Остановитесь, найдите частный результат церемонии и выясните, какие данные реально получены; без пригодных долей сохранённые шифротексты могут оказаться недоступны. Печать init JSON в CI artifact превращает резерв в утечку ключей и административного доступа.

Seal и restart

Seal удаляет доступ к расшифрованному ключевому материалу из памяти узла. API чтения секретов прекращается; TCP listener и часть health API продолжают отвечать. Копии уже выданных паролей не исчезают и существующие PostgreSQL соединения не закрываются от seal Vault. После restart наш Shamir сервер sealed независимо от того, сохранился ли операторский token. Token доказывает право API, но не заменяет unseal key.

set -euo pipefail
python3 lab.py --root "$stand" stop
python3 lab.py --root "$stand" start
python3 lab.py --root "$stand" status
python3 lab.py --root "$stand" unseal

Это действие сохраняет state. После start ожидается sealed true и HTTP 503, после unseal — HTTP 200. Если доли не подходят, проверьте, не относятся ли они к свежему restore-target до импорта снимка. Неправильный набор не исправляют пересозданием source. Ручная CLI-команда vault operator unseal без аргумента спрашивает долю скрытым вводом в tty; не ставьте её значение после команды в истории shell.

Auto-unseal и recovery keys

Auto-unseal передаёт функцию защиты ключевого материала доверенному внешнему KMS/HSM или другому поддержанному seal provider. Процесс при запуске получает право дешифрования у этой системы. Поэтому bootstrap переносится к идентичности машины и полномочиям на конкретный KMS key; проблема не исчезает. Recovery keys разрешают некоторые административные церемонии, например generate-root, но не могут сами расшифровать root key при навсегда потерянном KMS key. Даже хороший snapshot тогда недостаточен.

Rekey меняет материал/распределение долей; rotate меняет ключи шифрования keyring для новых записей. Ни одно слово не означает «сменить все уже выданные пароли». Ротацию CA и динамических PostgreSQL credentials выполняют соответствующие engines. Оператор этого стенда без renewal истечёт через 8h; explicit max TTL 24h ограничивает даже успешно продлеваемый token. После потери доступа выполните явно описанную ниже церемонию. Unseal не продлевает token и не создаёт новый.

Если оператор истёк: восстановление через порог долей

Этот путь предназначен только для собственного Shamir-стенда 1.21.4. Предпосылки: cwd vault/labs, тот же обычный владелец, проверенный TLS endpoint, сервер уже unsealed, в $stand/private/init.json есть пригодные доли именно этого storage. После restart сначала выполните start/unseal из предыдущего блока. Helper проверяет lookup-self: действующий оператор означает отказ от лишней церемонии, HTTP 403 или отсутствующий файл допускают восстановление, неоднозначная сетевая ошибка останавливает его. Наличие двух долей у одного владельца удобно для лаборатории, но не доказывает согласие двух независимых хранителей.

set -euo pipefail
python3 lab.py --root "$stand" recover-operator
python3 lab.py --root "$stand" status

--root выбирает существующий частный стенд; action recover-operator не вызывает init и не меняет KV. Сначала GET sys/generate-root/attempt должен вернуть started=false и required=2. POST туда с пустым объектом создаёт попытку: nonce связывает последующие ответы, otp — одноразовую маску, otp_length — её длину. Две разные доли передаются в JSON-полях key/nonce по HTTPS в sys/generate-root/update. На пороге ответ содержит complete=true и encoded_token; helper декодирует base64 и XOR с OTP, получая временный root token. Это API-credential, не root key из иерархии шифрования.

Временным этот root делает обязательный отзыв: не полагайтесь на автоматическое короткое истечение. Он создаёт policy handbook-operator и orphan operator с TTL 8h/explicit max 24h; policy широкая административная, но без специальной policy root. Новый token атомарно заменяет private/operator.token. В блоке finally helper отзывает временный root и проверяет HTTP 403. Ожидаются код 0 и сообщение Recovered bounded orphan operator. Shares/OTP/encoded token/root не выводятся и не идут в argv: частный 0600 журнал operator-recovery-*.json сохраняет материал на случай прерывания и поля operator_saved/root_revoked. Его нельзя публиковать или хранить рядом с общими отчётами.

Уже начатая чужая попытка означает STOP без cancel. Собственную незавершённую попытку helper отменяет только при совпадении nonce. Ошибка после выдачи root требует проверить частный журнал: если root_revoked не подтверждён, временный root остаётся чувствительным административным доступом; завершите его отзыв через auth/token/revoke-self по проверенному HTTPS API, не печатая token, и подтвердите lookup403. Не начинайте следующую попытку, чтобы скрыть эту неопределённость. При потере нужных долей helper не восстанавливает их. Для auto-unseal этот учебный путь неприменим: нужны recovery shares и работающий seal provider по процедуре конкретной поставки.

В отдельном native опыте 1.21.4 проверены отказ при живом операторе и занятом nonce, новый orphan operator после revoke старого, explicit max 86400s и фактический HTTP 403 временного root. Многопользовательская доставка долей, KMS и production quorum этим опытом не проверены.

Generate-root API 1.21.x: attempt/update/OTP/nonce; CLI 1.21.x: threshold, stdin, decode и cancel.
