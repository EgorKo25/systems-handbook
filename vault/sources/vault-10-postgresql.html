Динамический PostgreSQL: новая роль на выдачу

Vault управляет учётными данными, а PostgreSQL исполняет SQL и проверяет права. Их состояния связаны, но не образуют одну резервную копию.

Договор БД до настройки plugin

PostgreSQL 18.6, личный сервер $HOME/handbook-lab/pg18, loopback15432, база handbook. Прикладная schema app содержит данные. Отдельная flyway_meta предназначена для истории миграций; её владелец flyway_owner. Schema — пространство SQL-имён, не каталог Linux и не Vault namespace. Этот договор совпадает с томом Flyway, но Vault-комплект не запускает Flyway, не читает его private state и не требует уже исполненных миграций.

Роль PostgreSQLНазначение
lab_adminSuperuser только bootstrap личного кластера.
flyway_ownerLOGIN, владелец app/flyway_meta и объектов; DDL, без CREATEROLE.
app_runtimeNOLOGIN, USAGE app и нужный DML, без DDL и доступа flyway_meta.
vault_bootstrapLOGIN CREATEROLE, управляет своими динамическими ролями, не владеет таблицами.
Выданная v-рольLOGIN, пароль и VALID UNTIL, член app_runtime; короткий срок.

DML — чтение/изменение строк SELECT/INSERT/UPDATE/DELETE. DDL — создание/изменение объектов. GRANT app_runtime TO vault_bootstrap WITH ADMIN TRUE, INHERIT FALSE, SET FALSE позволяет выдавать членство, но не наследовать прикладные права и не делать SET ROLE в app_runtime. Просто CREATEROLE не означает право выдать любую чужую роль. Эта грамматика и поведение приняты на PG 18.6; старые версии имеют другие возможности управления членством.

Default privileges назначает создатель будущих объектов flyway_owner в schema app. Они не меняют старые таблицы и не распространяются на таблицы другого владельца. Для уже существующих объектов нужен отдельный GRANT. Служебная история вынесена из app, чтобы default grants приложению случайно не открыли миграционную metadata. Пример bootstrap SQL создаёт небольшую app.vault_probe независимо от Flyway и отдельный объект для проверки отказа.

Подготовка личного PostgreSQL

Предпосылки: обычный владелец, cwd vault/labs, отдельно установленный проверенный PostgreSQL18.6 с OpenSSL, его bin указан в переменной PG_BIN. Получение/сборка PostgreSQL объясняются в его томе; этот helper не скачивает и не устанавливает системные пакеты. pg — новый частный каталог. Если уже читаете Flyway на одном общем сервере, не запускайте prepare поверх его PGDATA: применяйте согласованный SQL к существующему личному серверу после проверки владельцев и доступа. Helper — маршрут только для своего нового экземпляра.

set -euo pipefail
pg="$HOME/handbook-lab/pg18"
python3 pg_lab.py --root "$pg" prepare --pg-bin "$PG_BIN"
python3 pg_lab.py --root "$pg" start
python3 pg_lab.py --root "$pg" bootstrap

Prepare проверяет точный номер, OpenSSL и свободный порт 15432, создаёт TLS CA/SAN127.0.0.1, SCRAM-SHA-256 и запрет plaintext TCP. SCRAM — парольный протокол с серверным verifier вместо хранения открытого пароля. Пароли трёх ролей случайно создаются только в private 0600, pgpass тоже 0600; argv не содержит пароль. Start ждёт готовность. Bootstrap создаёт handbook/roles/schemas и проверяет, что plugin роль не читает app. Ошибка о существующем PGDATA останавливает подготовку; автоматического reset и остановки чужого сервера нет.

Путь выдачи

Database engine хранит конфигурацию соединения с административной ролью vault_bootstrap. Это credential внешней БД, защищённое barrier Vault; оно отличается от Vault token клиента. Встроенный postgresql-database-plugin устанавливает TLS с проверкой CA/SAN к PG, входит по SCRAM и проверяет соединение. allowed_roles ограничивает, какие роли Vault могут использовать этот config. Vault database role handbook-runtime задаёт SQL шаблоны и сроки; это ещё один логический объект, не готовая PostgreSQL роль.

При GET database/creds/handbook-runtime ACL сначала разрешает read. Plugin генерирует имя/пароль, подставляет их и expiration в creation_statements, выполняет CREATE ROLE и GRANT app_runtime, после чего Vault возвращает username/password и lease_id. Клиент получает новое полномочие на каждом таком чтении. Повтор после потерянного ответа способен создать ещё одну роль; безусловный polling creds раз в секунду увеличивает churn и число невостребованных leases.

CREATE ROLE "{{name}}" WITH LOGIN
  PASSWORD '{{password}}' VALID UNTIL '{{expiration}}';
GRANT app_runtime TO "{{name}}";

Это шаблон, который обрабатывает plugin, а не SQL для ручного запуска с буквальными скобками. Шаблоны из файла передают в private JSON config через vault write database/roles/handbook-runtime @...; пароли не ставят в shell key=value. После первого подключения API database/rotate-root/handbook меняет plugin credential и сохраняет его новое значение в Vault. Слово root здесь означает управляющий credential engine, а не PG superuser. Старый bootstrap пароль перестаёт работать; совместное использование его с другим потребителем поэтому ломает того потребителя.

Нативная проверка и граница существующей сессии

На собственном сервере из предыдущего блока, Vault active и operator.token ещё действует: python3 pg_lab.py --root "$pg" check --vault-root "$stand". Это одноразовый сценарий проверки config/выдачи/отзыва; после успешного прогона читайте pg/checks.json, не повторяйте его как идемпотентный bootstrap. Он проверяет TLS plugin, rotate-root, динамический read app, запрет DDL/flyway_meta, renewal и revoke lease. Возвращает только названия checks, не credentials.

Принятые revocation statements сначала отнимают app_runtime, затем удаляют LOGIN-роль. Новый login после revoke запрещён. Уже открытая psql-сессия при этом ещё выполняет SELECT1: соединение не уничтожено удалением role. Но следующий SELECT из app.vault_probe получает отказ после потери членства. Это два разных наблюдения. Текущая транзакция, уже прочитанные строки и иной механизм полномочий могут дать другую границу; не следует обещать отзыв каждого ранее полученного результата.

Остановка существующих backend требует отдельного полномочия PostgreSQL и принятой процедуры. Мы не выдаём plugin superuser или pg_signal_backend, чтобы скрыть это различие, и не заявляем, что pg_terminate_backend успешно исполняется ролью без прав. VALID UNTIL ограничивает вход по паролю, не срок уже открытого соединения. Временное исчезновение PG задерживает cleanup; ошибки lease revoke расследуют по Vault audit и PG logs, не делают force-revoke ради «зелёного счётчика», оставляя живую роль незамеченной.

Две системы при восстановлении

Snapshot Vault сохраняет config, policies и внутренние leases, но не SQL-данные и не актуальный список ролей внешнего PG. После restore старый lease может ссылаться на уже удалённую роль; наоборот, PG может сохранить роль, о выдаче которой восстановленный Vault больше не знает. Требуется перечень orphan credentials, сверка timestamps/префиксов, управляемый отзыв/переиздание и проверка приложения. Восстановление БД и Vault не образует общую атомарную точку по умолчанию. Для приложения важны отдельные RPO/RTO обеих систем и порядок восстановления доверия.
