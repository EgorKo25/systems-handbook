Измерение: где заканчивается ожидание

Отделим стоимость TLS, policy, storage, внешней БД и renewal, сохраняя известный исходный режим.

Операция, окно и единицы

Latency — задержка от выбранного события начала до конца. В клиентском измерении HTTPS KV read это может включать TCP/TLS, запрос, серверное исполнение и чтение JSON. Серверный histogram может охватывать иной участок. Throughput — число завершённых операций в секунду; его читают вместе с долей ошибок и concurrency. Высокий req/s при почти всех 403 не является полезной пропускной способностью выдачи.

Для reproducible опыта фиксируют release/commit, число voters, источник хранения, состояние audit, размер KV, число policies, CPU/RAM/диск, сетевой RTT, connections и окно. Baseline — состояние до выбранного изменения. Одинаковый ключ, одинаковая длительность и одинаковая доля выдач нужны для сравнения. Опыт с 100 запросами после уже прогретого cache и опыт с первыми 100 запросами не обязательно измеряют одинаковый режим.

Нативный малый профиль этой редакции

После complex exercise, active Vault, config существует в version3, cwd labs, operator ещё действует: python3 lab.py --root "$stand" measure --count 100. Флаг count ограничен 10..1000, чтобы helper не стал непреднамеренным stress test. Он делает последовательные GET secret/data/handbook/config, каждый с новым urllib TLS-соединением и проверенной CA, считает ошибки и миллисекунды monotonic clock. Результат сохраняется private/stand measure.json; данные секрета не печатаются.

На авторском loopback stand1.21.4, один Raft voter, file audit включён, 100 запросов/0 ошибок: median 3.346ms, p95 4.343ms, p99 5.122ms, max 5.804ms. Машина автора: x86_64, 12 видимых логических CPU, около 14.8GiB RAM; отдельные cgroup CPU/RAM limits недоступны, тип/гарантии storage не определялись. Это конкретное наблюдение машины автора, не capacity рекомендация и не универсальная «норма p99». Окно мало, нагрузка последовательная и включает Python/новый TLS; по нему нельзя прогнозировать сервер с тысячами параллельных клиентов. Повтор на той же машине может дать иное распределение из-за соседних процессов и page cache.

p99 nearest-rank — элемент отсортированной выборки с индексом ceil(0.99N), считая с 1. При N=100 это 99-й элемент; один выброс сильно меняет результат, а ошибки нужно учитывать отдельно. Не прячьте timed-out запросы, считая только успешные, и не усредняйте p99 разных окон как общий p99. Для нагрузочного заключения нужны более длинные серии и распределение по категориям операций.

Диагностика симптома

Сначала определяют, где заканчивается запрос: DNS/TCP/TLS, health, token lookup/ACL, mount/backend, audit или клиентский timeout. Затем сопоставляют clock timestamps/request ID и системные наблюдения CPU, resident memory, disk latency/space, network retransmits. Telemetry endpoint требует собственной policy и защищённого доступа; root не раздают Prometheus ради удобства. Token/lease ID/username в labels создают опасную кардинальность и утечку идентификаторов.

Важна также нагрузка эксплуатации. Частые SecretID/PKI выдачи, renewals тысяч клиентов в одну секунду, snapshot и audit rotation могут совпасть. Jitter снижает пик, но его эффект оценивают вместе с max TTL и запасом восстановления. Отказ Vault не всегда немедленно останавливает приложение: оно может использовать уже выданный credential, пока тот действителен. Для SLO отдельно измеряют готовность выдавать новый доступ и способность сервиса обслуживать текущую работу.
