Bootstrap приложения: AppRole и внешняя идентичность

Метод login выбирают по происхождению доказательства, способу доставки и способности повторить вход после отказа.

AppRole без постоянного root

AppRole — auth method для машин. RoleID указывает роль, SecretID является дополнительным секретным доказательством, если bind_secret_id включён. Эти названия не обещают независимых факторов: если CI положил оба значения в один открытый artifact, компрометация одной папки даёт весь вход. Оператор создаёт role и выдаёт identity-материал по принятому каналу. Приложение получает только право login этой роли, а не право создавать arbitrary SecretID и policies.

Роль задаёт token_policies, token_ttl/max_ttl, SecretID ttl/число использований и, при необходимости, сетевые ограничения. SecretID ttl — время возможности login; token_ttl — жизнь уже выданного token. Исчерпание SecretID не отзывает автоматически полученный token; отзыв конкретного SecretID также не равен отзыву всех прежде выданных токенов. Эти связи проверяют по accessor, token tree и политике отзыва deploy.

Response wrapping как однократная доставка

Wrapping, «обёртывание ответа», сохраняет настоящий ответ в cubbyhole краткоживущего wrapping token. Cubbyhole — изолированное хранилище, привязанное к token. Посредник доставляет wrapping token, конечный клиент проверяет creation_path/TTL через lookup и делает unwrap. Успешный unwrap расходует обёртку. Повторный unwrap должен отказать. Это даёт обнаружимый факт преждевременного чтения, но не мешает вору первым успешно unwrap и затем использовать извлечённый SecretID; защищённый канал доставки всё равно нужен.

В личном стенде после provision выполните из labs python3 lab.py --root "$stand" approle. Helper включает auth/approle, создаёт role handbook с token TTL 5m/max 20m и SecretID TTL 5m/num_uses1; запрашивает SecretID с vault write -wrap-ttl=60s -f -format=json auth/approle/role/handbook/secret-id. -f разрешает write без key=value; -wrap-ttl относится к обёртке ответа. Проверяется creation_path, затем unwrap и login через HTTPS API без secret argv. Вторые unwrap/login отклоняются, application.token сохраняется 0600. SecretID в private уже использован, не подходит для следующего Agent login.

В production генератор SecretID и рабочий процесс разделены. Policy генератора может требовать min_wrapping_ttl/max_wrapping_ttl на endpoint выдачи. Следует различать эту policy и policy полученного приложения: application не получает create/update на auth/approle/role/*/secret-id. Нельзя просто убрать bind_secret_id, чтобы «исправить» потерянный bootstrap; это меняет доказательство личности.

Kubernetes: доверяем проверенному ServiceAccount

ServiceAccount — учётная запись workload Kubernetes. Kubernetes auth method принимает JWT этой записи, проверяет его по настроенной связи с API и ролью Vault и выдаёт собственный token. JWT, JSON Web Token, содержит подписанные claims — поля утверждений о субъекте и назначении token; подпись, issuer, audience, namespace и service account bindings имеют отдельный смысл. Namespace Kubernetes и Enterprise namespace Vault — разные области.

Предпосылки внешнего рецепта: существующий личный кластер, TLS CA API, reviewer credential с правом TokenReview и принятый lifecycle projected tokens. В конфигурации Vault задают kubernetes_host/CA и модель reviewer; в role ограничивают конкретные bound_service_account_names/namespaces и audience. Не следует копировать бессрочный старый service account token из чужого кластера. Истечение reviewer token ломает последующие login даже при ещё живых Vault tokens; это наблюдают отдельно. Рецепт не выполнен в локальном стенде и не запускает Kubernetes за читателя.

OIDC/JWT: пользователь, issuer и аудитория

OIDC, OpenID Connect, даёт интерактивный вход через провайдера личности; JWT auth может обслуживать машинный token без browser flow. Настройка предполагает зарегистрированный client, точные redirect URI, доверие к issuer/JWKS, проверку audience и связывание claims с role. JWKS — набор открытых ключей проверки подписи, а не список пользователей. Вход с правильной подписью, но предназначенный другому приложению, не должен приниматься только потому, что «наш issuer».

Для человеческого CLI vault login -no-store -method=oidc запускают лишь после настройки IdP и разрешённого localhost callback. Предпосылки и секрет client остаются private; это не исполнимая команда первого стенда. Группы IdP сопоставляются с Vault identity groups по определённым claims, не по похожему display name. Ошибку audience/redirect исправляют настройкой обеих сторон, не ослаблением всех bound claims.

Cert auth: доказательство владения ключом

Cert auth проверяет предъявленный клиентский сертификат и соответствующий private key. Listener должен запросить client certificate; у метода отдельно задают доверенный CA/сертификат и допустимые имена, ограничения и policy. Успешный TLS к серверу ещё не означает login клиентского cert auth. Наличие в файле публичного сертификата без закрытого ключа не позволяет доказать владение. Отзыв клиентского сертификата и отзыв уже выданного Vault token требуют отдельных мер; для выпуска собственных сертификатов служит PKI engine главы 11.
