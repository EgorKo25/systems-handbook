От запроса клиента до байтов storage

Проследим конкретное чтение KVv2 и отделим ошибки транспорта, личности, ACL и движка.

Как появляется запрос

Клиент — CLI, Go-программа или Agent. Agent — отдельный процесс около приложения, который может получать и продлевать token и готовить файл по шаблону. Сначала клиент выбирает адрес Vault, устанавливает TCP-соединение, проводит TLS handshake и проверяет цепочку CA и SAN. Только затем в зашифрованный канал отправляется HTTP-запрос. Например, CLI vault kv get -mount=secret handbook/config адресует KVv2 API GET /v1/secret/data/handbook/config. Символическая команда CLI скрывает слово data; ACL проверяется на настоящем API-пути без префикса /v1.

Token — предъявляемый серверу материал API-доступа. Обычный HTTP-клиент кладёт его в X-Vault-Token; это не TLS client certificate и не unseal share. При login запрос к настроенному auth method содержит иное доказательство личности, например role_id и secret_id. Успешный auth method создаёт token с policy, сроком, metadata и при необходимости entity. Дальнейшие запросы обычно предъявляют уже token, а не повторяют AppRole login перед каждой KV-операцией.

Проверки внутри сервера

Сервер принимает операцию, привязывает её к token и проверяет срок, отзыв, допустимое число использований и связанные ограничения. Service token имеет серверное состояние и accessor — идентификатор для административного управления без раскрытия самого token. Accessor не является запасным credential и его знание не даёт read секретов. Batch token — иной, компактный тип с другими возможностями управления и renewal; нельзя переносить на него все свойства service token.

Entity — внутренняя запись личности Vault. Alias — связь конкретного имени/идентификатора во внешнем auth mount с entity; одного совпадения строк «alice» в двух auth methods недостаточно. Mount accessor связывает alias с правильным источником личности. Group — набор entity или внешне отображённых групп с дополнительными policy. Администратор может явно объединить alias одной личности, но ошибочное объединение склеит полномочия. У токена есть собственные token policies и identity policies; последняя часть может меняться при изменении групп. Печатный список имён policy не заменяет проверку конкретного запроса.

ACL, access control list, — правила пути и операций. Проверка использует внешний API-путь. При маршрутизации mount выбирается по префиксу; движок получает путь без этой внешней части. Для нашего запроса это mount secret/ и относительный путь data/handbook/config. KVv2 загружает metadata выбранного ключа, проверяет существование запрошенной версии и её deleted/destroyed состояние. Barrier расшифровывает нужные сохранённые значения. Обычное KV-чтение не создаёт динамическую PostgreSQL LOGIN-роль; у разных engines разные эффекты даже при одном HTTP GET.

Запись имеет больше этапов, чем ответ

При CLI kv put (HTTP POST в примере KVv2 API) движок сравнивает CAS, если задан, формирует следующую версию и сохраняет данные/metadata через storage transaction. Integrated storage передаёт изменение в Raft; запись должна быть согласована и применена перед успешным завершением. При database credential движок сначала взаимодействует с внешней БД, создаёт роль, затем возвращает credential вместе с lease. Внешняя система и Vault не являются одной распределённой SQL-транзакцией. Если ответ потерян после создания роли, клиент не должен считать, что выдачи не было, и бесконечно повторять GET без контроля количества leases.

Audit device получает запись запроса и запись ответа согласно своей семантике. Для конфиденциальных полей обычно сохраняются HMAC, а не исходные значения. HMAC, keyed hash, позволяет сопоставлять известное значение с журналом в рамках конкретного устройства, но не является шифрованием, которое потом просто «декодируют». Возврат ответа также может завершиться сетевым обрывом после фактического изменения. Request ID связывает наблюдения; отсутствие успешной строки в приложении не доказывает отсутствие серверного эффекта.

Для читателя: после provision следующей главы можно выполнить vault kv get -mount=secret -format=json handbook/config из vault/labs с адресом/CA из env.sh и short-lived reader token из private. Ожидается JSON с data.data и data.metadata.version. Поле lease_duration=0 не даёт KV-паролю волшебного внешнего срока жизни. При любой ошибке не выполняйте зависящий put: сначала определите, на каком этапе закончился запрос.
