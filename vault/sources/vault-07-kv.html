KVv2: версия, CAS и необратимость

Одинаковое слово «удалить» скрывает разные переходы: новая версия, soft-delete, destroy и удаление metadata.

CAS, compare and set, — условие записи: ожидаемый номер должен совпасть с текущей версией. Версия — сохранённый выпуск значения с собственным номером; metadata хранит эти номера и состояния. Soft-delete скрывает выпуск с возможностью возврата, destroy необратимо удаляет его содержимое через API. Ниже увидим каждый переход на одном синтетическом ключе.

Единственный основной запуск комплексной проверки

По основному маршруту после provision config ещё version1. Из cwd labs, с действующим оператором, выполните две команды блока ниже один раз. Первый выдаёт свежие reader/writer tokens на 10m без изменения KV; второй проводит всю цепочку ACL/KV/TTL и сохраняет checks.json. Это снимает зависимость от времени чтения предыдущих глав. Ожидается passed13/code0, current version3 с message=second и added=yes, version2 destroyed. Дальше до Agent/Go используем именно это состояние. После выполнения ручные меняющие команды этой главы читаются как разбор уже сделанных шагов.

set -euo pipefail
python3 lab.py --root "$stand" test-tokens
python3 lab.py --root "$stand" checks

Повторно checks не запускают: читают checks.json. Если выбрали ручную альтернативу ниже, автоматический checks в этом же stand пропускают, а в итоге достигают той же version3. При неожиданном отказе dependent writes остановлены; source сохраняют, выясняют token TTL/текущую metadata, не запускают provision/init заново.

KVv1 и KVv2 имеют разные контракты

KV, key/value, хранит введённые клиентом пары. KVv1 сохраняет текущее значение по пути без истории KVv2. KVv2 хранит версии значения и metadata: номер текущей и старейшей версий, времена, deletion state, destroyed state, пользовательскую metadata и настройки. В API v1 путь plain/handbook/config, в API v2 — secret/data/handbook/config. Цифра в HTTP-префиксе /v1/ не выбирает KVv1: это версия общей оболочки API.

Нельзя решить, какой KV подключён, по имени secret. Оператор читает vault secrets list -detailed и options mount. CLI -mount=secret явно отделяет mount от относительного ключа; устаревшая запись secret/handbook/config скрывает это различие. Включение vault secrets enable -path=plain -version=1 kv в личном стенде создало бы другой mount, но не преобразовало существующий v2. Переход версии — отдельное изменение с изучением путей, policies, блокировки upgrade и клиентской совместимости.

Put заменяет документ, patch сохраняет соседние поля

KVv2 put сохраняет новый набор полей как новую версию; при передаче только message прежнее поле другого имени не обязано сохраниться. Patch применяет частичное изменение существующего значения. Родной метод HTTP PATCH использует capability patch; CLI fallback -method=rw сначала читает, затем пишет и имеет другой набор прав и окно гонки. Мы исполняем native PATCH и объясняем это явно. JSON Merge Patch может удалять поле значением null; строка «null» и JSON null — разные входы, поэтому для сложных типов используют подготовленный JSON-файл с mode 0600.

Версионная история требует ограничения роста. max_versions ограничивает число сохранённых версий; вытесненная старая версия может быть уничтожена. delete_version_after планирует soft-delete новых версий, не делает внешний пароль недействительным. cas_required требует compare-and-set. Меняя настройки после накопления истории, оператор сначала оценивает, какую старую информацию потеряет и что было принято backup.

В version1 записан message=first, в version2 — message=second, в version3 — message=second и added=yes. Устаревший CAS1 получил 400 до новой записи. Затем операции с исторической version2 не меняют current_version=3: read v2 даёт 404 после delete, снова 200 после undelete и 404 с destroyed=true после destroy. Read без version продолжает читать 3. Если изменить пример и удалить текущую 3, такое чтение тоже перестанет возвращать значение: движок не выбирает автоматически прежнюю живую версию. Новую запись после soft-delete всё ещё сравнивают с текущим номером 3, не с CAS0.

Сравнить до записи

При двух writer условие CAS предотвращает потерю уже принятой записи. Клиент A прочитал version1; клиент B уже записал version2. Без CAS A может перезаписать смысл изменения B. -cas=1 вместо этого отклоняется. -cas=0 требует ещё не существовавший ключ. CAS — контроль конкуренции, не проверка подлинности данных и не контроль доступа.

Предпосылки: после provision config в version1; cwd labs; адрес/CA из env.sh; сначала выпущены свежие reader/writer tokens командой ниже (она не меняет KV). Эти команды выполняются вручную вместо ветви checks над тем же ключом.

set -euo pipefail
python3 lab.py --root "$stand" test-tokens
read -r VAULT_TOKEN < "$stand/private/writer.token"
export VAULT_TOKEN
vault kv put -mount=secret -cas=1 handbook/config message=second
if vault kv put -mount=secret -cas=1 handbook/config message=stale \
    > "$stand/private/expected-cas.out" 2> "$stand/private/expected-cas.err"; then
  echo "Неожиданно принят устаревший CAS" >&2
  exit 1
else
  result=$?
  test "$result" -eq 2
  grep -q 'check-and-set parameter did not match' "$stand/private/expected-cas.err"
fi
vault kv patch -mount=secret -cas=2 handbook/config added=yes
vault kv get -mount=secret -version=3 handbook/config

Первый put создаёт version2. Второй имеет ненулевой код/HTTP 400 CAS mismatch, значение остаётся second. После подтверждённого ожидаемого отказа patch с CAS2 создаёт version3 с message=second и added=yes. Если patch тоже получил mismatch, другой writer уже изменил состояние: читают новое значение, решают, совместимы ли изменения, и только затем выбирают новый CAS. Автоматическое «ещё раз без CAS» снимает защиту.

Удаление версии и уничтожение байтов

Следующие команды нужны оператору, потому что writer policy не даёт delete/destroy. В cwd labs прочитайте private/operator.token через shell read, не печатая его. Предпосылка — version2 и version3 существуют. Действия изменяют историю конкретного учебного ключа, не чужих данных.

set -euo pipefail
read -r VAULT_TOKEN < "$stand/private/operator.token"
export VAULT_TOKEN
vault kv delete -mount=secret -versions=2 handbook/config
vault kv undelete -mount=secret -versions=2 handbook/config
vault kv destroy -mount=secret -versions=2 handbook/config
vault kv metadata get -mount=secret handbook/config

Delete помечает version2 удалённой: read этой версии получает 404, но undelete ещё может вернуть её. Destroy делает содержимое version2 необратимо недоступным через KV, а metadata показывает destroyed=true. Undo/undelete не восстановит её; нужен независимый резерв с прежним состоянием, если правила хранения разрешают такое возвращение. Удаление metadata удалило бы всю историю ключа и настройки, поэтому эта команда не включена в основной опыт.

Шифрованные страницы, старые backup и копии в приложении имеют свой жизненный цикл. Destroy KV не доказывает физическое стирание всех дисковых секторов и внешних архивов. Если поле было настоящим паролем, смените его у системы, которая принимает этот пароль; просто скрыть версию в Vault недостаточно. После restore старый KV может вновь существовать, но внешний credential уже мог быть отозван — это нужно проверять отдельно.
