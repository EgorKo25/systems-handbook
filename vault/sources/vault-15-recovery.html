Резерв, отдельное восстановление и обновление

Копия становится принятой только после возвращения функции на другой цели и проверки того, какие данные исчезли после точки.

Что находится внутри snapshot

Raft snapshot сохраняет согласованное состояние Vault: защищённые значения, mount/auth/policy configuration и внутренние записи, включая leases. Он не копирует бинарник, server.hcl, listener TLS key/certificate, внешние audit files, unseal shares или внешний KMS. Он также не сохраняет таблицы и роли PostgreSQL. Для восстановления нужны не только bytes snapshot, но и совместимая поставка, конфигурация, доверие TLS, материал seal и процедура запуска.

Snapshot сам чувствителен: содержимое зашифровано, но у обладателя пригодного ключевого материала и серверного доступа появляется возможность восстановить секреты и старые политики. Его хранят отдельно от shares и с контролем чтения/целостности. RPO, recovery point objective, — допустимая потеря изменений по времени или выбранной метрике; RTO, recovery time objective, — допустимое время до принятой функции. Наличие файла snapshot не измеряет ни один показатель.

Явная контрольная точка

В cwd labs, active Vault, действующий оператор, KV version3 после упражнений: python3 lab.py --root "$stand" snapshot --name checkpoint-v3.snap. Команда выполняет vault operator raft snapshot save, создаёт snapshots/checkpoint-v3.snap mode 0600 и отказывается перезаписывать прежний файл. Код 0 означает сохранение, не проверенный restore. Сохраните отдельно ожидаемые version/поля, список mounts и время точки без секрета. Изменения после точки должны быть известны, иначе непонятно, что обязан вернуть restore.

Нативная приёмка этой редакции вернула version3 на отдельном сервере. Для собственного опыта потери истории после точки можно после snapshot явно записать version4 с новым синтетическим message, затем проверить source4/restore3. Этот необязательный write выполняют только оператором с CAS3 и сохраняют факт; не добавляют автоматически каждый раз при открытии книги. Уже сделанные внешние операции PG snapshot не отменит.

Восстановление на другой цели

Новая цель — $HOME/handbook-vault-restore, другие loopback порты 18210/18211. Среда та же, обычный владелец, проверенный source bin уже есть. Target должен быть uninitialized и не содержать полезных данных. Каталог state может уже содержать служебные файлы Raft после start: пустота каталога не является тестом initialized. Helper отвергает source==target и уже инициализированную цель, а -force применяется внутри только к новому отдельному экземпляру.

set -euo pipefail
target="$HOME/handbook-vault-restore"
python3 lab.py --root "$target" prepare --vault "$stand/bin/vault" \
  --port 18210 --cluster-port 18211
python3 lab.py --root "$target" start
python3 lab.py --root "$target" restore --source "$stand" \
  --name checkpoint-v3.snap
python3 lab.py --root "$target" status

Сначала target создаёт собственные временные init/shares и ограниченного оператора. vault operator raft snapshot restore -force ... разрешает импорт snapshot с другим seal material в этот явно новый target. Возврат CLI означает приём snapshot, а не завершение фоновой замены storage. Helper ждёт sealed state импортированного состояния, затем unseal/active/API-проверку. После импорта используются source unseal shares: новые shares target больше не соответствуют импортированным данным. Helper подаёт source shares по HTTPS, переносит source operator token в частный target и проверяет KV metadata version. Source остаётся нетронутым. До временного target init helper проверяет наличие snapshot и source custody; отдельный GET sys/init должен подтвердить initialized=false. Уже initialized target отклоняется и при отсутствующем operator.token. Для следующего target restart учебный helper сохраняет пригодные source shares в target private/init.json, а исходный временный target init помечает obsolete в отдельном 0600 файле. Это удобство одного учебного владельца, а не production разделение хранителей.

После импорта появляется restore-imported.json; restore-complete.json с version3 появляется только после успешного API-чтения. Текущий source operator мог истечь, быть отозван или быть выдан уже после snapshot: копирование его строки не добавляет запись token store в старый снимок. При таком HTTP 403 helper сообщает об импортированном состоянии и останавливается без false success. Не повторяйте restore: на уже unsealed target выполните два следующих действия. Для полной приёмки затем проверьте значение, reader/writer ACL, mounts, audit и работу приложения. Если snapshot от auto-unseal, необходим исходный/совместимо мигрированный seal provider и доступ к ключу — recovery shares не заменяют потерянный KMS. Ни одна ошибка не оправдывает overwrite source.

Ветка только после сообщения snapshot imported/unsealed и отказа operator lookup. Предпосылки прежние; target хранит уже source shares, а процедура восстановления разобрана в главе ключей. Это не команды для ещё не импортированного или произвольного production target.

set -euo pipefail
python3 lab.py --root "$target" recover-operator
python3 lab.py --root "$target" verify-restore

Ожидаются отзыв временного root с HTTP 403 и затем Separate restore accepted. verify-restore читает config и записывает номер версии в restore-complete.json; его можно повторить для проверки, он не импортирует storage. В новом узком native опыте снимок version1 предшествовал выдаче нового source operator; восстановление потребовало именно этой ветки, после неё target вернул 1, source сохранил свою последующую 2. Старый опыт version3 остаётся отдельным результатом.

Что случилось с данными после точки

Восстановленный Vault видит историю до snapshot. Внешнее приложение могло уже использовать новый пароль, получить сертификат или создать SQL-роль после этой точки. Эти эффекты не откатились. Старые tokens/leases из snapshot могут снова оказаться представлены в хранилище, но их TTL оценивается с текущим временем, а внешний credential может уже отсутствовать. Поэтому restore в изоляции до соединения с production backends позволяет сверить и переиздать доступ, а не сразу начать повторный cleanup внешних систем по старым данным.

Учебный helper на loopback не подключён к рабочим backends. Для реального recovery план включает ограничение исходящих связей, инвентаризацию выданных ролей/сертификатов, восстановление PG отдельно, reconciliation leases, принятые новые credentials и только затем включение приложения. Отдельно учитывают CA rotation и trust stores, которые snapshot на клиентах не меняет.

Обновление — миграция состояния

Выбор нового релиза начинается с official release notes, version-specific upgrade guidance, security advisories, plugin/auth/storage compatibility и лицензии. Сначала проверяют backup восстановлением тем же и предполагаемым новым binary на изолированной копии. Изменения внутреннего формата могут сделать простую замену нового binary старым неподдержанной; возврат исполняемого файла не является rollback storage.

Для многосерверного HA порядок обновления followers/active, leadership handoff и допустимые смешанные версии берут из документации конкретного перехода. В одиночном стенде restart означает окно недоступности, затем Shamir unseal. Приёмка после upgrade проверяет номер/ревизию, health, ACL, выдачу и отзыв, audit, snapshot/restore и приложение. Никакое «zero downtime» здесь не заявляется: сам HA переход в редакции не исполнялся. Для отмены неудачной миграции нужны проверенный прежний snapshot, поддержанный binary и явное решение о потере записей после контрольной точки.
