Agent и Go: кто обновляет секрет у процесса

Успешная выдача должна дойти до приложения, а отказ renewal должен стать управляемым состоянием.

Agent заканчивает один lifecycle и начинает другой

Vault Agent — процесс из той же поставки, выполняющий auto-auth, renewal и шаблонизацию в поддержанной конфигурации. Он не создаёт первичную идентичность из ничего: AppRole требует нового SecretID, Kubernetes — подходящего JWT, cert auth — клиентского key/cert. Token sink сохраняет полученный token в выбранное назначение. File sink сокращает необходимость собственного login-кода, но получивший файл UID всё равно обладает token; mode 0600 и отдельный владелец являются частью доверия.

Template, «шаблон», читает secret через Vault и создаёт текстовый файл. Содержимое готового файла уже расшифровано. Оно не должно попадать в Git, stdout, общую artifact-папку и произвольные access logs. Обновление файла не меняет environment уже работающего процесса: environment копируется при запуске. Нужен принятый reload/restart/exec-контракт приложения, а для database pool — явная смена credential и вывод старых соединений.

Нативный одноразовый Agent

Предпосылки: AppRole handbook уже создан, KV дошёл до version3/message=second, cwd labs, оператор имеет право выдать новый SecretID. python3 lab.py --root "$stand" agent создаёт отдельный wrapped single-use SecretID, проверяет creation_path, доставляет его в private/agent-secret-id и запускает vault agent -config .../private/agent.hcl. Agent читает роль из private/role-id, делает login, удаляет использованный SecretID file и создаёт private/rendered.env с mode 0600. Никакого listener Agent в этом опыте нет.

Конфигурация имеет exit_after_auth = true. Поэтому фактически проверены auto-auth, sink, шаблон и завершение, а не многосуточная автоматическая renewal/re-auth. Текст template с {{ with secret "secret/data/handbook/config" }} обращается к настоящему KVv2 пути; значение находится в .Data.data.message. error_on_missing_key прекращает тихое создание неполной конфигурации. Если поле отсутствует или policy даёт 403, приложение не должно считать пустой файл корректным секретом. Логи Agent сохраняются private; helper печатает только факт результата.

Для непрерывного режима удаляют exit_after_auth, задают условия повтора и завершения, роль с пригодным повторным auth и критерии готовности приложения. Single-use SecretID уже израсходован; при полной потере возможности renew нужен новый bootstrap. Нельзя лечить это num_uses=0 и бесконечным TTL без анализа компрометации. Система доставки нового SecretID — самостоятельная часть эксплуатации, а не свойство template.

Go через HTTPS API

Пример Go использует стандартную net/http библиотеку, не сторонний SDK. Это позволяет отдельно увидеть адрес, TLS RootCAs, timeout, заголовок token, JSON envelope и cancellation. Официальный github.com/hashicorp/vault/api SDK может сократить типовой код и имеет собственные версии; его модуль здесь не загружается и не объявлен проверенным только из-за совпадения номера server.

Перед сборкой уже установлен Go 1.27.3, cwd vault/labs/go-client. Кэши и бинарник направляем в частный stand, module dependencies отсутствуют; readonly запрещает незаметную правку go.mod. Go не устанавливается из этого блока. Предпосылка запуска — свежий agent.token только что получен предыдущим блоком Agent и имеет read на config.

set -euo pipefail
GOTOOLCHAIN=local GOFLAGS=-mod=readonly \
  GOCACHE="$stand/go-cache" GOMODCACHE="$stand/go-mod-cache" \
  go build -o "$stand/bin/go-vault-client" .
"$stand/bin/go-vault-client" -address https://127.0.0.1:18200 \
  -ca "$stand/tls/ca.crt" -token-file "$stand/private/agent.token"

Ожидается код 0 и номер KVv2 version без secret body. Если чтение главы заняло дольше tokenTTL 5m, вернитесь из vault/labs/go-client командой cd .. в vault/labs и выполните python3 lab.py --root "$stand" agent. После успешного обновления sink повторите уже собранный клиент по абсолютному пути из блока, без сброса KV/CA. Такой повтор Agent допустим, потому что не пересоздаёт AppRole и PKI. Token file должен быть regular 0600 или строже; CA проверяется, InsecureSkipVerify не включён. HTTP timeout 5s и request context ограничивают ожидание, тело ответа ограничено 1MiB. Redirect не передаёт token неизвестному адресу: этот пример требует принятого active endpoint; HA forwarding/discovery обсуждается отдельно. Ошибки возвращают transport/HTTP status без тела credential. В CI нельзя печатать struct Response, весь config или connection URL ради диагностики.

Renewal и cancel

Опция -watch после чтения вызывает auth/token/renew-self с increment 30s, использует фактически выданный lease_duration и ждёт половину этого срока. SIGINT/SIGTERM отменяет context и останавливает timer. Если token не renew-able, response неполон, получен 403 или транспортный отказ, пример завершает процесс с ошибкой. Повтор с задержкой и jitter потребует отдельной реализации с общим deadline; данный клиент завершает работу, поэтому временная потеря Vault видна оператору.

Пример обновляет token для доступа к Vault; он не обновляет PostgreSQL credential и не управляет pool. Для динамической БД дополнительно нужен отдельный lifecycle lease, новый login при maxTTL, проверка соединения и отзыв прежнего credential. Для KV статического пароля таймер token renewal не меняет значение password. Эти различия полезно сохранить и при переходе на SDK или Agent.

Первоисточники: auto-auth; template lifecycle; renew-self API; официальный Go API module.
