PKI: право подписывать и срок сертификата

Построим цепочку root → intermediate → leaf и отделим подпись, имя, доверие и отзыв.

Участники до первой выдачи

PKI, public key infrastructure, — организация удостоверений открытых ключей. Private key, «закрытый ключ», доказывает владение при подписи; certificate, «сертификат», связывает открытый ключ с именами и ограничениями, подписанными CA. CA, certification authority, — удостоверяющий центр. Root CA является опорой доверия, которую verifier принимает заранее. Intermediate CA, промежуточный центр, получает право подписывать в пределах своей цепочки и ограничений. Leaf — конечный сертификат приложения, не имеющий права подписывать другие CA.

CSR, certificate signing request, — запрос подписи с открытым ключом, именами и подписью владельца соответствующего private key. CSR не содержит закрытый ключ. Подписывающий центр проверяет запрос, свою policy и ограничения; сам факт корректной подписи CSR не означает, что заявитель имеет право на любое DNS-имя. SAN содержит удостоверяемые DNS/IP. Срок notAfter, key usage и extended key usage задают применимость сертификата; сертификат на api.lab.example.invalid не удостоверяет 127.0.0.1.

Учебная цепочка и настоящий production root

В production root часто держат offline вне online Vault, а Vault получает промежуточный сертификат из внешней церемонии. В учебном loopback опыте два независимых mount pki-root и pki-int находятся на одном сервере; компрометация этого оператора может затронуть оба. Разделение имён mount не даёт физической изоляции. Оба private CA keys создаются internal в Vault и не экспортируются в исходники. Генерация leaf через issue может вернуть его новый private key клиенту; более строгий путь генерирует ключ у workload и передаёт CSR в sign endpoint.

Среда: сохранённый Vault после init, активный оператор, cwd labs. python3 lab.py --root "$stand" pki выполняют один раз, когда mount pki-root/pki-int ещё отсутствуют. Если хотя бы один из двух mounts уже существует, helper откажет до создания другого или замены CA: случайно пересоздать центр и потерять историю доверия helper не позволяет. Ожидается успешный summary. Сертификаты, leaf key и CSR сохраняются только private 0600, корневые keys остаются за barrier. При отказе нельзя продолжить к issue, предполагая, что set-signed уже принят.

Что именно происходит

В pki-root генерируется internal CA с TTL 8760h, в pki-int — internal key и CSR. Root signing endpoint подписывает этот CSR с TTL 720h; pki-int импортирует подписанную цепочку через intermediate/set-signed. Role handbook разрешает subdomains lab.example.invalid, запрещает bare domain и IP SAN, ограничивает max TTL 1h. Запрос issue на api.lab.example.invalid TTL 10m получает leaf, запрос outside.example.invalid — HTTP 400. Это проверка policy имён, не проверка владения публичным DNS; .invalid использован специально для учебной области.

TTL выдачи ограничен не только запросом клиента: учитываются role, mount и срок issuer. При завершении жизни intermediate нельзя обещать новый leaf на год. Приёмка проверяет openssl verify цепочки, SAN leaf, даты и назначение ключа. Проверка только «файл начинается с BEGIN CERTIFICATE» устанавливает формат PEM, но не доверенную цепочку. В независимом прогоне цепочка и SAN проверены OpenSSL, а не визуальной моделью.

Отзыв: список должен дойти до проверяющего

CRL, certificate revocation list, — подписанный список отозванных серийных номеров от CA. Serial number идентифицирует конкретный выпуск; повторная выдача с тем же CN даёт другой сертификат. PKI revoke добавляет serial в данные отзыва; клиент должен получить актуальный CRL и применять его при верификации. Нативный опыт отзывает leaf и получает pki-int/cert/crl; независимая проверка подтверждает присутствие точного serial в CRL. Это не доказательство, что каждый внешний TLS-клиент уже загрузил список.

Адреса AIA/issuing certificates и CRL distribution должны быть доступны реальным потребителям до истечения/отзыва. Наш локальный опыт не публикует их в рабочую сеть и не заявляет готовую внешнюю инфраструктуру распространения CRL. Не указывайте фиктивный публичный URL только для заполнения поля. Для production измеряют размер CRL, период обновления, кэш клиента, недоступность distribution и поведение fail-open/fail-closed. OCSP — отдельный протокол запроса статуса; наличие PKI mount не означает, что клиенты автоматически его используют.

Rotation без внезапного разрыва доверия

Ротация leaf: получить новый cert/key, проверить цепочку/SAN, атомарно доставить приложение, переключить listener или pool, проверить новые handshake, затем отозвать старый выпуск по процедуре смены сертификата. В существующем TLS-session сервер может продолжать работу со старым контекстом; сертификат не перепроверяется на каждый HTTP byte. Renewal сертификата в прикладном смысле обычно является новой выдачей с новым serial, а не продлением notAfter старого подписанного объекта.

Ротация intermediate/root: подготовить новый issuer, распространить новый trust chain с перекрытием, проверить старые и новые leaf, переключить default issuer, дождаться согласованного окна и удалить старую опору только после проверки потребителей. Multi-issuer возможности 1.21 позволяют представить несколько issuer, но не решают доставку trust store за приложение. Слишком раннее удаление старого CA ломает ещё действующие сертификаты, слишком долгое перекрытие сохраняет избыточное доверие. Снимок Vault не возвращает автоматически старые trust stores на клиентах.
