Сохраняемый сервер: процесс, пути и TLS

Сначала получим корректно проверяемый listener и понятное состояние, затем перейдём к разблокированию.

Какие файлы живут дольше команды

Исполняемый файл запускает обычный владелец стенда; тот же UID должен читать tls/server.key, писать state/ и logs/. UID — числовой идентификатор пользователя ОС, по которому Linux проверяет доступ. API-пользователь Vault не является Linux-пользователем. Удаление токена не изменяет chmod каталога, а chmod не выдаёт capability на API-путь.

Путь в частном standНазначение и права
bin/vault, downloads/Поставка и доказательства происхождения; бинарник 0700.
server.hcl, stand.json, env.shКонфигурация, порты и env клиента; client.hcl задаёт отдельный private token helper; 0600, без токена в env.sh.
tls/Локальная CA, ключ сервера и цепочка. Каталог 0700, ключи 0600.
state/Сохраняемое Raft-состояние. Не править работающие db-файлы вручную.
private/Учебные доли unseal и ограниченные токены. 0700/0600; не Git и не public backup.
logs/, snapshots/Серверный журнал, аудит и явные контрольные точки; частные.

HCL, HashiCorp Configuration Language, задаёт конфигурационные блоки. listener "tcp" задаёт адрес приёма; api_addr — объявляемый клиентский адрес, а не дополнительный bind. cluster_addr сообщает адрес внутреннего взаимодействия; у listener есть соответствующий cluster_address. Основной API здесь 18200, внутренний порт 18201; оба bind только на 127.0.0.1. Кластерный транспорт имеет собственную модель TLS Vault и не равен простому копированию клиентского HTTPS. Для реального кластера loopback разных машин друг друга не соединит.

Создание без переустановки

Среда и cwd те же vault/labs, обычный владелец, поставка из предыдущей главы принята. Shell-переменная stand содержит собственный путь. Helper создаёт частные файлы, проверяет свободные непривилегированные порты и отказывается повторно выполнять prepare поверх stand.json.

set -euo pipefail
python3 lab.py --root "$stand" prepare --vault "$stand/bin/vault"
python3 lab.py --root "$stand" start
python3 lab.py --root "$stand" status
. "$stand/env.sh"
if vault status; then :; else
  status_code=$?
  test "$status_code" -eq 2 || exit "$status_code"
fi

prepare ещё не запускает сервер. Создаёт учебную CA на 30 дней и сертификат listener на 14 дней с SAN IP 127.0.0.1 и DNS localhost. SAN, subject alternative name, — удостоверяемое имя или адрес; CN «localhost» сам по себе не покрывает IP. CA key нужен только для нашего учебного bootstrap и остаётся private. start запускает vault server -config .../server.hcl в cwd самого stand, сохраняет собственный PID и проверяет listener через TLS с этой CA. Готовый TCP не означает готовый unsealed Vault.

До init здоровье ожидается HTTP 501, initialized false, sealed true. Для vault status коды различаются: 0 — unsealed, 2 — sealed, 1 — ошибка. В shell с set -e ожидаемый код 2 нужно принять явно; нельзя продолжить меняющие действия после произвольной ошибки. Отказ TLS о неизвестной CA исправляют правильным VAULT_CACERT и сертификатом, ошибка SAN требует перевыпуска с правильным адресом. VAULT_SKIP_VERIFY не является приёмкой TLS.

Почему параметры выбраны так

storage "raft" хранит состояние под абсолютным state/; node_id стабилен между restart. disable_mlock = true используется для Raft и непривилегированного учебного процесса: mlock удерживает страницы от swap и имеет цену/пределы ОС, а Raft с memory-mapped файлами требует отдельного внимания к памяти. Этот параметр не превращает swap в безопасное хранилище. На реальной машине отдельно принимают политику swap, core dumps, диска и доступа к процессу; здесь не меняют sysctl, capabilities и системные службы.

CLI получает адрес из VAULT_ADDR, CA из VAULT_CACERT, token из VAULT_TOKEN или token helper после login. Helper в книге передаёт токен только процессу конкретной операции и не пишет root в ~/.vault-token. Сгенерированный env.sh выбирает через VAULT_CONFIG_PATH собственный client.hcl с helper, который возвращает пустой get и отказывается от store; ручной CLI не читает прежний host token helper. Env.sh также убирает прежние token/namespace/client-cert настройки; HOME не меняется. Затем reader/operator token передают явно из нужного private файла. Флаги HTTP находятся после выбранной команды: vault kv get -address=... -mount=secret .... Мы не объявляем их универсальными флагами перед kv; фактическая CLI-грамматика проверяется отдельно.

Повторное включение того же экземпляра

После следующих глав остановка выглядит так: python3 lab.py --root "$stand" stop. Перед SIGTERM helper проверяет командную строку и cwd сохранённого PID; чужой процесс с повторно использованным номером не останавливает. Данные и ключи остаются. Следующий start поднимает тот же storage sealed; нужен unseal, а не второй init. Если порт занят, находят владельца и выбирают собственный свободный порт до создания стенда; чужую службу не завершают. Если сертификат истёк, данные Raft от этого не исчезли: заменяют listener certificate через принятый процесс, сохраняя состояние и ключи.

Первоисточники: TCP listener; Raft configuration; status exit codes.
