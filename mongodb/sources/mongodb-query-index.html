План запроса и цена индекса

Одинаковые данные, один запрос и объяснимое различие исследованной работы

От предиката к доступу

Планировщик выбирает способ найти документы и выполнить сортировку. COLLSCAN означает просмотр коллекции с проверкой предиката; IXSCAN — обход индексных ключей, FETCH — получение самих документов по ссылкам. SORT означает отдельную сортировку кандидатов, LIMIT прекращает выдачу после нужного числа результатов, но не отменяет уже проделанную работу. В slot-based execution, или SBE, отдельные имена/вложенность отличаются: смысл работы не надо выводить из одного названия верхней стадии.

Индекс — поддерживаемая сервером упорядоченная структура ключей и ссылок на документы. Для запроса по tenant,state и сортировки createdAt DESC,_id ASC создаём {tenant:1,state:1,createdAt:-1,_id:1}. Первые два поля равны константам: план ограничивает узкий непрерывный диапазон их сочетания; внутри этого диапазона ключи уже имеют нужный порядок. Index bounds — границы диапазонов обхода. Равенство tenant даёт точку, а отсутствие ограничения по первому полю может заставить прочитать гораздо больше ключей. Это причина важности порядка compound index, а не мнемоническое «индексируйте каждое поле».

Индекс не обязательно устраняет FETCH: сервис запрашивает title и version, которых в ключе нет. Covered query возвращает только данные из индекса и может показать docsExamined=0, но добавление большого title в индекс увеличит размер и write cost. Узкий индекс и 20 FETCH могут быть лучшим договором. Обратный обход переворачивает весь порядок; произвольное смешение направлений полей не всегда подходит. Префиксы и направления сверяют по правилам compound indexes.

Измерение до и после на том же состоянии

После seed, но до migrate, Bash/cwd тома: ACTION=explain mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js. Скрипт исполняет read query с explain("executionStats"): это настоящий запуск плана без изменения jobs. Сохраните nReturned, totalKeysExamined, totalDocsExamined и winningPlan. Затем выполните migrate из главы сервиса и точно тот же explain. Не добавляйте новые документы между двумя пробами. При отказе первой пробы не создавайте индекс «на удачу»; сначала найдите причину.

На авторском наборе 20 000 документов первый план изучал 20 000 документов и сортировал кандидатов, после индекса — 20 ключей и 20 документов для 20 результатов. Это измерение объёма логической работы, не универсальное ускорение latency в тысячу раз. executionTimeMillis округлено, зависит от прогрева и может быть 0. Explain не является репрезентативным p99 всего приложения и имеет особое отношение к plan cache: он не заменяет повторные обычные запросы.

От сохранённого explain к порядку конкретных ключей

Для этого разбора jobs ещё не закрывались: после seed и migrate все 20 000 заданий open, по 200 на tenant. В исходнике номер i задаёт tenant=i%100, строковый ID seed-%06d и дату 1700000000+i секунд UTC. Поэтому tenant-01 соответствует i=1,101,…,19901. Сортировка по убыванию createdAt начинает с seed-019901, затем seed-019801; двадцатый — seed-018001, следующий — seed-017901. При равных датах сравнивается _id по возрастанию. Это логический порядок ключей, не схема расположения страниц B-tree на диске.

Сохранённый explain 1 ноября содержит точечные bounds tenant=["tenant-01","tenant-01"], state=["open","open"], полный createdAt=[MaxKey,MinKey] и _id=[MinKey,MaxKey]. MinKey/MaxKey — крайние BSON-типы ниже/выше обычных значений; они обозначают неограниченные концы здесь, не реальные даты. Перевёрнутый порядок концов createdAt следует из направления −1. Равенства двух первых полей позволяют начать с нужной группы; LIMIT обрывает её после 20 результатов, хотя подходящих ключей 200.

Разбор без рисунка. Внутри tenant-01/open ключи идут от i=19901 вниз с шагом 100; дата первого 2023-11-15T03:45:01Z, двадцатого — 03:13:21Z, следующего — 03:11:41Z. Поле _id уже находится в индексе, но title и version отсутствуют. Вместе с ключом индекс хранит ссылку на запись, RecordId: это внутренний идентификатор движка, не адрес RAM и не строковое поле _id. FETCH по ссылке получает документ, в том числе title="job 19901" и version=1 у первой записи. Затем LIMIT возвращает 20. Конкретное значение RecordId тут не снималось и не выдумывается.

В прежнем native explain верхний план без индекса был SORT над COLLSCAN: проверены 20 000 документов, найдены 200 подходящих, выданы 20. После индекса — LIMIT → FETCH → IXSCAN с totalKeysExamined=20 и totalDocsExamined=20. Это логические счётчики плана: поиск начала диапазона всё равно проходит внутренние страницы индекса, а физическое чтение зависит от кэшей. Двадцать keys не означают двадцать дисковых IO. После транзакции один старый документ будет closed, поэтому данные для сравнения фиксируют до неё.

Изменяемый опыт без MongoDB: в том же Bash/cwd выполните python3 tests/mechanisms.py --limit 5. Флаг принимает 1…200 и ограничивает арифметическую выдачу: последний ID станет seed-019501, следующий — seed-019401. Скрипт проверяет также разрешение равенства дат по _id. Это модель порядка, не новый запуск explain с limit=5 и не измерение latency. Уменьшение limit без хорошего пути доступа само по себе не отменило бы COLLSCAN.

Массив, уникальность, частичность и время жизни

Multikey index возникает, когда индексируемое поле содержит массив: один документ создаёт несколько ключей. Это помогает поиску элементов, но увеличивает write amplification — число дополнительных операций на каждую прикладную запись. Например, индекс {state:1,tags:1} для state=open и tags=["red","urgent"] создаёт ключи (open,red) и (open,urgent) с одной ссылкой на документ. Compound multikey не допускает два независимых массива tags и parts в одном документе, если оба их пути включены в тот же индекс: это не декартово произведение всех пар. Неиндексируемый массив parts этому индексу не мешает. Условия через $elemMatch меняют и смысл совпадения, и допустимое объединение границ. Для a=[1,8] запрос a>5 и a<3 подходит разными элементами; пересечение этих двух границ было бы пусто и потеряло бы правильный результат. С $elemMatch требуется один элемент, и такой документ уже не подходит. Выбор одной границы без $elemMatch не обещан заранее; см. multikey bounds 8.0.

Unique index запрещает повтор ключа между документами. Обычный unique по необязательному email может отказать из-за нескольких missing/null; partial unique с фильтром {email:{$type:"string"}} охватывает только строки. Он не проверяет каждую перестановку/дубликат элемента внутри одного массива как отдельную сущность. Построение unique на уже конфликтующих данных завершится ошибкой; сначала найдите и согласованно разберите конфликты. Ограничения объясняет unique reference.

Partial index содержит только документы, удовлетворяющие фильтру. Планировщик должен доказать, что запрос не потеряет результаты, поэтому запрос без нужного ограничения может его не использовать. Это меньше места и работы обновления, но дополнительное условие доступа; см. partial index semantics. TTL — time to live: специальный single-field индекс по дате, по которому фоновый механизм удаляет просроченные документы. Это асинхронная уборка, не точный таймер запрета доступа: приложение само проверяет expiresAt. Резкое включение TTL на большом прошлом наборе создаст поток удалений, oplog и IO; предварительная уборка порциями снижает пик. Наш jobs не имеет TTL: задания должны пережить учебный день; TTL reference задаёт ограничения.

Каждый дополнительный индекс требует памяти, места и изменения ключей при записи. Сравнивайте размер индексов, latency записи, cache misses и чтение до/после; скрытый индекс исключается из выбора плана, но продолжает обслуживаться при записи. Удаление индекса экономит обслуживание, однако обратное построение имеет цену и окно нагрузки. Автоматического drop/reset в лабораториях нет.
