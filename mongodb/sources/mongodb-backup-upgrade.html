Резерв, восстановление и обновление без выдуманного отката

Принята только копия, из которой получены проверенные данные на другой цели

Какую точку хотим вернуть

Backup — независимая сохраняемая копия состояния. RPO — допустимый возраст потерянных данных, RTO — допустимое время восстановления до принятого сервиса. Сначала определите точку и список объектов: jobs, ledger, индексы, validators, пользователи/роли, ключи, версии бинарников и конфигурация. Обычный logical dump выбранной БД не копирует все секреты ОС и не делает автоматически полноценную копию прав сервера. Шифрование резервов и хранение ключей отдельно — часть вашей политики; наш архив содержит только синтетические данные.

Logical dump читает документы и метаданные через MongoDB API. Snapshot — согласованный снимок физических томов по правилам storage/filesystem/платформы; live-копирование отдельных .wt файлов не является snapshot. PIT, point in time restore, требует базовой копии и непрерывной проверенной истории до выбранного времени. Один файл dump с --oplog охватывает лишь определённое окно операции, а не бесконечный PIT-сервис. Управляемый Atlas backup/PIT — отдельная availability/edition; локальные Tools не дают его автоматически.

Проверенный небольшой dump на остановленной прикладной записи

Предпосылки: main.go остановлен Ctrl+C, shell не меняет workshop, репликация/миграции не выполняют прикладных изменений; mongod продолжает работать. Так мы получаем согласованное по приложению неподвижное состояние. Bash/cwd тома, Tools уже установлены. Сохраните число jobs и индексы, выберите новое имя файла. Tools читает пароль из private/tools.yml (0600), а не argv. При любом ненулевом коде dump файл считается непригодным до расследования; restore не запускают.

set -euo pipefail
ACTION=backup-count mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js
test ! -e "$LAB/backups/workshop-1.archive.gz"
mongodump --config "$LAB/private/tools.yml" --db workshop --archive="$LAB/backups/workshop-1.archive.gz" --gzip

--db ограничивает namespace областью workshop; --archive пишет единый контейнер dump, --gzip сжимает. Это бинарный архив Tools, не tar и не JSON. В авторском опыте jobs=20001, ledger=1, индекс tenant_state_recent присутствовал. Копирование файла на другой независимый носитель ещё требуется для защиты от потери исходного диска; данные в backups/ того же host не получают независимость одним названием.

Новая цель вместо перезаписи живой базы

Далее один новый каталог и другой loopback-порт. Никаких --drop или переиспользования прежнего dataPath. Restore-instance — временный standalone только для проверки, без auth и без сети за пределами loopback; полноценное production-восстановление требует вернуть доступ и topology до выдачи трафика. Если каталог restore-1 или порт заняты, блок останавливается. EXPECTED_JOBS задайте по сохранённому backup-count, не подгоняйте под обнаруженный результат.

set -euo pipefail
test ! -e "$LAB/restore-1"
mkdir -p "$LAB/restore-1/data"
mongod --dbpath "$LAB/restore-1/data" --port 27118 --bind_ip 127.0.0.1 --nounixsocket --wiredTigerCacheSizeGB 0.25 --logpath "$LAB/restore-1/mongod.log" --pidfilepath "$LAB/restore-1/mongod.pid" --fork
mongorestore --uri 'mongodb://127.0.0.1:27118/?directConnection=true' --archive="$LAB/backups/workshop-1.archive.gz" --gzip --stopOnError
EXPECTED_JOBS=20001 mongosh 'mongodb://127.0.0.1:27118/workshop?directConnection=true' --quiet --norc --file labs/restore-accept.js
mongod --shutdown --dbpath "$LAB/restore-1/data"

--stopOnError прекращает дальнейший импорт при ошибке, но уже импортированные документы не отменяются: цель частична до расследования. Скрипт приёмки сверяет count, наличие seed-000001, BSON Date и индекс. Полный native test дополнительно сравнивает SHA-256 всех jobs в каноническом Extended JSON, упорядоченных по _id, а также ledger и состояние после restart. Только равенство количества было бы недостаточно. Архив и восстановленная data остаются; выключение не удаляет их.

Живая нагрузка, oplog и ограничения Tools

При продолжающихся изменениях dump без подходящей согласованности может собрать разные коллекции из разных моментов. Full replica set dump с --oplog и соответствующим mongorestore --oplogReplay имеет строгие ограничения: нельзя просто добавить --oplog к scoped --db dump или произвольному шардированному экспорту и объявить консистентность. Окно oplog должно покрывать всю операцию, DDL и namespaces имеют ограничения; для sharded backup нужно согласование всех shards и config metadata. Здесь живой full oplog/PIT/snapshot не исполнялись. Источник и цель должны иметь совместимые server/FCV, а версии dump/restore лучше совпадать; Tools behavior объясняет пределы переносимости.

Бинарник и FCV меняются отдельно

FCV — featureCompatibilityVersion: сохранённый сервером режим совместимости форматов и возможностей. Замена executable и повышение FCV — разные этапы обновления; прежний FCV не означает, что любой старый бинарник безопасно запустится на новом dataPath. Сначала проверяют поддержанный путь, совместимость драйверов и изменённые параметры, восстанавливают backup в репетиционное окружение, прогоняют запросы/миграции/отказ. Для replica set обновляют участников в установленном документацией порядке, проверяя health и достаточность копий, затем отдельным решением повышают FCV. Команда setFeatureCompatibilityVersion не должна быть случайным шагом «ускорить старт».

Для перехода на 8.0 официальная процедура требует предыдущую major ветку 7.0; перескакивать несколько major нельзя. Документация 8.0 также ограничивает binary downgrade и указывает необходимость support, поэтому этот том не обещает простой откат установкой старого tarball. Точная процедура — upgrade replica set to 8.0. Здесь проверен restart той же 8.0.34, а не upgrade между major.

Возврат восстановленного backup теряет записи после контрольной точки, если нет согласованного replay/прикладного восстановления. Старый Go binary не удаляет новые поля/индексы и не откатывает новые бизнес-действия. Перед переключением фиксируют последнюю принятую запись, способ остановки новых write, судьбу отложенных запросов и решение о постконтрольных данных. Restore, rollback репликации и rollback релиза — разные процессы.
