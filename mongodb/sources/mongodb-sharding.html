Sharding: распределить диапазоны, сохранить управляемость

Ключ, маршрутизация и балансировка — ответ на измеренное ограничение

Что разделяется

Sharding — разделение коллекции на части, хранящиеся на разных группах серверов. Shard — одна такая часть инфраструктуры, обычно replica set, а не отдельная «таблица». Shard key — индексируемый набор полей документа, определяющий размещение. Пространство значений делится на диапазоны; chunk — единица описания диапазона в метаданных. Это логические границы ключей, не фиксированный диск-файл. Mongos — маршрутизатор, который по ключу и метаданным направляет команды; config server replica set хранит управляющую информацию. Новые варианты topology 8.0 имеют дополнительные режимы, но основной разбор использует выделенный config replica set.

Драйвер обращается к mongos, а тот по метаданным определяет нужные shards. Запрос с полным полезным ключом часто адресный; без него нужен scatter-gather — рассылка нескольким shards и сбор результатов. Limit=20 у клиента не означает 20 просмотренных документов на всём кластере: каждый shard может сделать существенную работу, затем mongos объединит/сортирует. Старая routing cache требует обновления при смене владельца диапазона; временный stale-config ответ — часть согласования маршрута, а не повод игнорировать ошибку.

Выбор ключа для нашей мастерской

Шардирование только по tenant локализует запросы одного клиента, но один огромный tenant становится горячей неделимой нагрузкой. Монотонный createdAt направляет новые записи к одному краю range-key. Hash — вычисленное распределяющее значение — помогает равномерным insert, но запрос по диапазону исходного времени уже не соответствует смежному диапазону hash. Compound key tenant+суффикс может делить большого клиента, сохраняя часть адресности; конкретный суффикс выбирают по распределению нагрузки и типичным запросам. Высокая cardinality означает много различных значений, но сама по себе не обещает равномерную нагрузку: 90% запросов могут обращаться к одному значению.

Прежде чем выбирать, измерьте распределение объёма и запросов по tenant, частоту изменений ключа, долю запросов с префиксом и цену межшардовой транзакции. Наш dataset из 100 равных tenant специально прост и не доказывает пригодность ключа для настоящей мастерской. Официальные ограничения ключей и различие refine/reshard — в shard key reference.

Маршрут на одном объявленном разделении ключей

Возьмём только объяснительную карту: ключ {tenant:1,_id:1}, простое двоичное сравнение строк, tenant-01 разделён по _id="seed-010000". Условный shard A владеет частью tenant-01 с меньшим ID, B — с этим и большими ID; другие tenant могут находиться также на C. Оба интервала вместе покрывают tenant-01, их граница не включена в A и включена в B. Это выбранные метаданные модели, не результат включения sharding в нашем одноузловом стенде.

tenant-01, _id=seed-000001AПолный ключ ниже границы.
tenant-01, _id=seed-019901BПолный ключ выше границы.
tenant-01, state=openA и BПрефикс ограничил tenant, но не суффикс ключа.
Только state=openВсе shards коллекции, включая CПо этому условию карта ключей не исключает ни один shard.

По формуле seed у tenant-01 ровно 100 ID ниже этой границы и 100 выше. Полный ключ поэтому может направить один запрос в одну группу, а префикс — лишь сузить множество групп. Получив ответ каждого адресата, mongos объединяет выдачу и применяет общий limit; локальный индекс нужен каждому shard отдельно. Измените только границу на seed-015000 и посчитайте размещение: 150/50 записей. Эта арифметика не предсказывает долю нагрузки. Официальный механизм выбора адресатов описан в Routing with mongos 8.0, Targeted/Broadcast Operations.

Балансировка и изменение размещения

Balancer — управляющая работа, переносящая диапазоны между shards согласно политике и распределению. Миграция диапазона копирует данные, догоняет текущие изменения, согласует смену владельца и очищает старые копии. В момент переноса появляются IO, сеть, рабочее место и короткие критические участки. Добавление shard не переносит мгновенно все старые данные и не исправляет горячий неделимый ключ. Zones — правила соответствия диапазонов разрешённым группам shards; они добавляют требования, которые могут мешать простой равномерности.

Refine shard key добавляет поля к существующему ключу, не является произвольным перераспределением по новому началу ключа. Resharding меняет ключ и требует построения нового размещения с запасом ресурса, временем выполнения, проверкой ошибок и cutover. Не обещайте «бесплатную смену»: большие коллекции и продолжающиеся записи создают реальные очереди и потребность в диске. Наблюдайте прогресс, lag, ошибку приложения и план остановки. Процедура зависит от версии/редакции и не исполнялась в этом стенде.

Уникальность и эксплуатационная цена

Уникальный _id вне shard key не всегда означает глобальную уникальность между shards: когда _id не является shard key, серверная уникальность _id может обеспечиваться только внутри shard. Для unique indexes в sharded collections нужны условия к префиксу shard key. Прикладной request ID нашего сервиса поэтому нельзя просто объявить глобальным дедупликатором после любого reshard: нужно выбрать размещение/ограничение или отдельный договор маршрутизации запросов. Проверка uniqueness — часть проекта ключа, а не поздний индекс.

Каждый shard добавляет replica set, monitoring, backup, upgrade и отказные сценарии; config servers и mongos тоже требуют управления. На одном небольшом host это чаще усложнение без выигрыша. Сначала исправляют неизбирательный запрос, индекс, неограниченный массив, pool pressure и модель данных, затем измеряют предел одного replica set. В этой главе нет команд запуска полного sharded cluster и нет заявления о его приёмке. Схема показывает последовательность адресного и рассеянного чтения, а для реального переноса данных нужен отдельный испытанный runbook.
