Документ, коллекция и граница одной записи

У открытого задания версия 1. При закрытии MongoDB меняет состояние на closed и увеличивает версию до 2 одной командой.

Какие объекты создаёт сервер

Мастерская хранит задания в коллекции jobs базы workshop. Одно задание — один документ. В записи ниже видны его идентификатор, текущее состояние и два разных счётчика. Это задание старой формы с schemaVersion=1, до миграции; остальные поля для краткости опущены. Текущий HTTP-обработчик создаёт новые задания уже с schemaVersion=2.

{_id: "job-42", state: "open", version: 1, schemaVersion: 1}

Серверный процесс mongod хранит эти документы в своём каталоге данных. Go-сервис обращается к нему через драйвер, а для административного опыта мы используем клиент mongosh. Оба клиента выбирают одну и ту же коллекцию по имени workshop.jobs. Название базы и коллекции ещё не говорит, по какому адресу доступен сервер; адрес задаётся в настройках подключения.

Go-обработчик закрывает один документ командой UpdateOne. Она ищет задание по _id и проверяет state=open и version=1. При совпадении одно обновление устанавливает state=closed и увеличивает version до 2. Читатель не увидит новый статус со старой версией от этого обновления. Такой переход называют атомарным. Если тот же запрос приходит снова, документ уже не соответствует фильтру и версия остаётся 2. Согласование нескольких документов, сохранность после сбоя и видимость записи на разных узлах разберём отдельно.

version проверяет, что закрывается ожидаемое состояние задания. Отдельное поле schemaVersion отмечает форму документа: позже миграция добавит priority и изменит именно его. Закрытие задания оставляет schemaVersion прежним.

Почему вложение иногда полезнее связи

Небольшой адрес выполнения можно вложить в задание: читаемое вместе состояние придёт одной записью и изменится одним обновлением. Историю миллионов событий в массив задания помещать нельзя: один BSON-документ ограничен 16 MiB, а растущий объект повышает стоимость передачи, обновления и конкуренции. Для неограниченной истории создают коллекцию job_events с полем jobId, индексом и понятной политикой удаления. Ссылка — обычное значение, сервер автоматически не проверяет существование связанного документа как внешний ключ SQL.

Допустим, в задание нужно добавить название клиента на момент заказа. Тогда сохранённое в самом задании customerName останется прежним после переименования клиента. Если же экран должен всегда показывать актуальное имя, можно хранить в задании customerId, а имя читать из отдельной коллекции клиентов. Выбор меняет и запрос чтения, и то, какие записи придётся обновлять при переименовании. Если изменение задания должно одновременно создавать отдельную запись журнала, понадобятся транзакция и обработка её повторов; этот случай разобран в главе о транзакциях.

Уникальность и договор формы

_id — обязательный идентификатор документа, уникальный в обычной коллекции без шардинга. Сервер создаёт для _id уникальный индекс: вставка второй записи с тем же значением будет отвергнута. Если клиент не дал значение, драйвер обычно генерирует ObjectId. Наш сервис передаёт строковый ID запроса, потому что повтор HTTP после потерянного ответа должен обращаться к той же записи. Случайно новый ID при повторе создаст ещё одно задание. Для sharded collection глобальная уникальность имеет дополнительные условия, разобранные позднее.

Наш сервис ожидает строковые tenant и title, состояние open или closed и целочисленную version. Эти требования заданы Go-типом и проверкой HTTP; серверный validator может дополнительно отвергать неправильную запись от другого клиента. Во время перехода в коллекции могут сосуществовать записи с schemaVersion=1 и schemaVersion=2. Приложение должно читать обе формы, пока миграция не обработает старые записи. Поле version при этом продолжает защищать изменение состояния каждого задания.

Проверьте модель без запуска: где хранить один текущий статус и где растущие комментарии? Что означает отсутствие priority у старого задания? Как отличить повтор создания от попытки изменить заголовок под старым ID?

Сверить рассуждение о задании

Текущий статус помещается в jobs: одно ограниченное значение меняется вместе с версией. Растущую историю комментариев можно вынести в job_events с jobId; для чтения истории одного задания понадобится индекс по этому полю. У записей исходного набора с schemaVersion=1 поля priority ещё нет; миграция добавляет priority=0 и ставит маркер 2. Но текущий POST создаёт задания сразу с маркером 2, а в Go-структуре Job поля priority нет. Поэтому отсутствие priority само по себе не определяет версию формы: сверяйте schemaVersion и код, который создаёт запись.

Стабильный _id позволяет найти задание при повторе создания. Наш обработчик сопоставляет также клиента и заголовок: тот же запрос получает прежнюю запись, другой заголовок под тем же ID — конфликт. Предикат закрытия проверяет уже состояние этой найденной записи.
