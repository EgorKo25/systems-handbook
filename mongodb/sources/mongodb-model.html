Документ, коллекция и граница одной записи

Модель начинается с совместно изменяемого состояния, а не с команды insert

Какие объекты создаёт сервер

Поле — имя и значение внутри документа; значение может быть строкой, числом, датой, вложенным документом или массивом. Коллекция объединяет документы одного назначения, например jobs. База данных — именованная область коллекций и доступа, у нас workshop. Экземпляр — запущенный процесс mongod со своим каталогом данных; один экземпляр хранит несколько баз. Имя workshop.jobs называется namespace: оно определяет конкретную коллекцию, а не сетевой адрес.

Клиентская программа отправляет команды серверу. mongosh — отдельная интерактивная программа, исполняющая JavaScript и вызывающая команды через драйвер. Go-драйвер — библиотека в нашем приложении, превращающая вызовы Go в обмен с сервером. Старый shell mongo и mongosh различаются; наличие mongod не доказывает наличие любого shell. mongos — маршрутизатор для распределённых по частям данных, его пока не запускаем.

В терминах приложения одно задание — документ. Его поля состояния и версии меняются атомарно: другой читатель не увидит половину одного обновления. Атомарно значит «либо весь предусмотренный переход этого объекта, либо ни одна его часть». Из этого не следует, что два независимых документа изменятся вместе, что диск уже устойчиво сохранил запись или что любой следующий читатель на другом узле увидит результат. Эти три вопроса книга разбирает отдельно.

Почему вложение иногда полезнее связи

Небольшой адрес выполнения можно вложить в задание: читаемое вместе состояние придёт одной записью и изменится одним обновлением. Историю миллионов событий в массив задания помещать нельзя: BSON — двоичная кодировка типизированных полей; один BSON-документ ограничен 16 MiB, а растущий объект повышает стоимость передачи, обновления и конкуренции. Для неограниченной истории создают коллекцию job_events с полем jobId, индексом и понятной политикой удаления. Ссылка — обычное значение, сервер автоматически не проверяет существование связанного документа как внешний ключ SQL.

Копирование названия клиента в задание делает чтение дешевле, но рождает договор: это историческое название на момент заказа или актуальное имя, которое надо массово менять? Если требование неизвестно, оптимизация преждевременна. Частые совместные обновления подсказывают границу документа; частые независимые обновления и неограниченный рост — повод разделить объекты. Транзакция — блок операций с общим решением фиксации или отмены — умеет согласовать несколько документов, но добавляет согласование, удержание снимка и обработку повторов.

Уникальность и договор формы

_id — обязательный идентификатор документа, уникальный в обычной коллекции данного экземпляра. Индекс — поддерживаемая сервером поисковая структура, которая может одновременно проверять ограничение уникальности. Сервер создаёт для _id такой уникальный индекс; если клиент не дал значение, драйвер обычно генерирует ObjectId. Наш сервис передаёт строковый ID запроса, потому что повтор HTTP после потерянного ответа должен обращаться к той же записи. Случайно новый ID при повторе создаст ещё одно задание. Для sharded collection глобальная уникальность имеет дополнительные условия, разобранные позднее.

Гибкость формы не равна отсутствию схемы. Схема — наш договор имён, типов, обязательных полей и допустимых переходов. Сначала он задан Go-типом и проверкой HTTP; серверный validator затем может запретить неправильный тип. В коллекции могут сосуществовать версии документа 1 и 2, поэтому приложение обязано явно читать обе во время перехода. Миграция — управляемое изменение существующих записей; резервирование и совместимость важнее самого $set.

Проверьте модель без запуска: где хранить один текущий статус и где растущие комментарии? Что означает отсутствие priority у старого задания? Как отличить повтор создания от попытки изменить заголовок под старым ID? Ответы понадобятся при изучении типов и обработчика HTTP.
