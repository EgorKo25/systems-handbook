Read concern, write concern и причинный порядок

Куда читать, что видно и какого подтверждения ждать — три независимых решения

Три ручки одного запроса

Read preference — предпочтение выбора роли узла для чтения: primary, secondary, primaryPreferred, secondaryPreferred или nearest с дополнительными условиями. Оно отвечает на вопрос «с какого узла», а не «насколько свежо». Secondary может отставать даже при малом сетевом round trip; nearest выбирает допустимый близкий узел, не самый новый документ.

Read concern — требование к видимости читаемых данных. local допускает локально видимые изменения, которые при смене primary могут исчезнуть. majority возвращает данные, прошедшие majority commit, но не обещает самый последний результат всех клиентов. snapshot даёт согласованный снимок в поддержанных операциях; linearizable для подходящих чтений на primary обеспечивает более сильное согласование с успешными предшествующими majority-записями, требуя дополнительной координации и ограничений. Слово «consistent» без выбранного concern и порядка операций недостаточно.

Write concern — требование к подтверждению записи. w:0 не ждёт ответа о принятии, w:1 ждёт primary, число больше 1 — нужное число data-bearing участников, w:"majority" — вычисленное большинство голосующих участников с данными. j:true требует journal по правилам concern. Успешная операция и удовлетворённый concern — разные части ответа. В 8.0 majority подтверждает устойчивую запись соответствующих oplog на нужных участниках; secondary ещё может не применить её к своей коллекции. Чтение на secondary поэтому может ждать нужной causal отметки. Условия и исключения — в write concern reference.

Для обычной конфигурации writeMajorityCount вычисляется как min(floor(allVotingMembers/2)+1, dataBearingVotingMembers); election quorum остаётся floor(allVotingMembers/2)+1. Арбитр (arbiter) — голосующий участник без прикладной копии данных. PSS: три голоса, три копии, оба порога 2. PSA: три голоса, две копии, оба порога 2, но голос arbiter не подтверждает данные, поэтому явный majority требует P и S. PSSS+A: пять голосов, четыре копии, оба порога 3. Буква P означает primary, S secondary, A arbiter; голос и копия — разные ресурсы. В PSA implicit default при отсутствии явного глобального значения может стать w:1: исключение defaults не меняет смысл явно заданного w:"majority".

Defaults и ожидание при отказе

В MongoDB 8.0 implicit default write concern — majority у большинства конфигураций, но наличие arbiter при определённом числе голосующих data-bearing узлов даёт исключение w:1. Arbiter — участник голосования без копии прикладных данных; он не может подтвердить запись данных. Явно заданный global default и параметры операции также влияют на итог. Не переносите наблюдение одного узла на все topology. Проверяйте фактический default и конфигурацию, особенно при добавлении arbiter; формула дана в MongoDB defaults. В нашем Go-коде majority и Journal=true заданы явно.

writeConcernMajorityJournalDefault определяет, подразумевает ли majority ожидание journal: у обычного WiredTiger-набора default true. Изменение этого параметра меняет договор durability, а не скорость «без последствий». j:true в одиночку не предотвращает rollback расходящейся истории. Не путайте majority voting quorum выборов и условие подтверждения записи: первые считают голоса, второе требует участников с данными.

wtimeout — предел ожидания выполнения concern после успешного изменения на primary, в миллисекундах; он не откатывает сделанное изменение. Клиентский timeout может истечь ещё раньше и оставить исход неизвестным. Например, запись принята primary, второй data-bearing узел недоступен, concern не достигнут за 3000 ms. Клиент получает ошибку, но документ может позже реплицироваться или оказаться rollback. Удаление документа «для компенсации ошибки» способно удалить успешно принятый заказ. Сначала сверяют прикладной ID и разрешают неопределённость.

Сессия и причинная зависимость

Логическая сессия — идентификатор связанной последовательности клиентских операций, обычно обозначаемый lsid. Он не равен TCP-соединению: pool может использовать другие сокеты, сохраняя логическую связь. Causal consistency — причинная согласованность: если приложение знает, что чтение зависит от своей записи, оно передаёт временную отметку зависимости и требует не читать состояние раньше неё. В causal session с majority reads/writes поддерживаются read-your-writes, монотонные чтения/записи и writes-follow-reads в заявленных условиях. Сессии нельзя одновременно использовать из нескольких goroutine; между клиентами причинный контекст нужно передавать осознанно.

Majority concern без causal связи сам по себе не означает, что произвольное чтение на отстающей secondary немедленно увидит именно вашу запись. Наш основной HTTP-путь читает primary с majority и не объявляет распределённый causal workflow между независимыми процессами. Границы объясняет модель видимости и причинности. Для checkout после записи tenant настройка предпочтения secondary ради разгрузки требует отдельной политики ожидания и допустимого отставания, а не смены одного слова URI.

Одноузловой набор удовлетворяет majority одним участником. На нём нельзя опытно доказать переживание потери primary или работу арбитра: соответствующие ветки схемы — объяснительная модель. Реальный тест здесь доказывает только настройку, корректность ответов и сохранение собственных файлов после перезапуска.
