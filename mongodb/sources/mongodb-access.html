Пути, конфигурация, пользователи и границы сети

Доступ к файлам, удостоверение клиента и защита транспорта решают разные задачи

Кто владеет файлами и процессом

В нашем стенде обычный пользователь создал LAB/data, поэтому запущенный им mongod может изменять этот каталог. Ни shell, ни Go не открывают файлы WiredTiger напрямую: они обращаются к процессу. В log/ остаётся структурированный журнал сервера, в run/ — PID-файл с номером процесса, в private/ — ключ и пароли. PID-файл не даёт полномочий и после аварии может устареть. Каталог data и отдельные файлы WiredTiger*, collection-*.wt, index-*.wt, journal/ составляют единое управляемое сервером состояние; выборочное копирование «нужной коллекции» по имени файла некорректно.

YAML — текст вложенных ключей с отступами. storage.dbPath задаёт каталог данных; systemLog.path — файл журнала; logAppend: true сохраняет старые строки при старте. net.bindIp: 127.0.0.1 и port: 27117 ограничивают listener. Unix-сокет отключён явно, чтобы все точки доступа были видны в договоре. cacheSizeGB: 0.25 ограничивает только WiredTiger cache, а не весь RSS процесса: ещё нужны память исполнения, соединения и кэш файлов ОС. Нельзя обещать, что mongod потребит ровно 256 MiB.

Приоритет не заменяет проверку действующей конфигурации

Для совпадающих серверных параметров CLI имеет приоритет над конфигурационным файлом. mongod --config ... --port 27119 меняет порт этого запуска; переменная shell сама не подставляется внутрь YAML. Экземпляр не перечитывает все настройки при редактировании файла: большинство стартовых опций требуют контролируемого перезапуска, а поддержанные runtime-параметры меняют отдельной административной командой. Не используйте --configExpand exec/rest для простой установки: это отдельное исполнение или получение содержимого, отсутствующее в нашем стенде.

Доказательство — команда getCmdLineOpts, которую вызывает ACTION=accept, и фактические listeners; файл на диске может уже отличаться от действующего процесса. При смене порта одновременно меняются URI, адрес члена replica set и ожидания приёмки. Конфигурация клиента — другой уровень: Go получает адрес через MONGO_URI и права через MONGO_AUTH_FILE; административный shell читает private/operator.json. Не пишите пароль в URI командной строки: он попадает в историю и список процессов.

Аутентификация, авторизация и TLS

Аутентификация проверяет, кто обращается; наш механизм SCRAM-SHA-256 доказывает знание пароля через согласованный обмен. Пользователь определяется именем вместе с authentication database: operator@admin и app@workshop — разные записи. Авторизация проверяет, какие операции этому пользователю разрешены; роль readWrite не даёт приложению управлять чужой базой или выключать сервер. Ключ security.keyFile служит внутренней аутентификации членов replica set, а не паролем HTTP-приложения. Утечка ключа требует своей процедуры ротации.

TLS защищает транспорт и проверяет личность сервера по доверенному CA — удостоверяющему центру. Он не выдаёт права записи. Наш loopback-стенд использует SCRAM без TLS и не выдаётся за сетевую production-конфигурацию. Для отдельной личной VM до открытия сети готовят сертификат с SAN нужного DNS-имени/IP, приватный ключ с узкими правами, доверие клиента и net.tls.mode: requireTLS, certificateKeyFile, CAFile. Клиенту передают tls=true и CA; проверяют положительное подключение, отказ с чужим CA и отказ по неверному имени. Флаги allowInvalidCertificates/allowInvalidHostnames снимают проверку, а не исправляют PKI.

Проверяемый личный TLS-профиль до работы с данными

Профиль ниже временно переводит тот же остановленный экземпляр на TLS, сохраняя пользователей и dataPath, затем возвращает основной loopback-режим учебного маршрута. Это транспортный опыт на личной машине; сетевую production-службу назад в plaintext не переводят. Нужен уже доступный OpenSSL CLI. labs/tls-profile.py создаёт новую личную CA и серверный сертификат, действительные семь дней, с единственным SAN IP 127.0.0.1. SAN — список имён/адресов, которым сертификат действительно соответствует. CN в Subject не подменяет SAN. Ключи CA/сервера остаются в private/tls с правами 0600; такая CA нужна лишь этому опыту и не добавляется в системное доверие.

Bash/cwd тома, сервер принят, Go ещё не нужен, private/tls отсутствует. Linux-команда --shutdown адресует свой dataPath локально, не требует передачи пароля и ждёт остановку; ненулевой код останавливает последовательность. Если сервер уже остановлен, не запускайте второй shutdown вслепую: проверьте журнал и перейдите к созданию профиля. Перезапуск с TLS не требует повторного bootstrap.

set -euo pipefail
mongod --config "$LAB/mongod.yml" --shutdown
python3 labs/tls-profile.py "$LAB"
mongod --config "$LAB/mongod-tls.yml" --fork
ACTION=accept mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --tls --tlsCAFile "$LAB/private/tls/ca.pem" --file labs/admin.js

Ожидается прежнее writeRead:true и код 0. Профиль использует requireTLS, server.pem и ca.pem. AllowConnectionsWithoutCertificates=true разрешает клиенту не предъявлять собственный сертификат: он всё равно проходит SCRAM и authorization. Проверка сервера клиентом остаётся обязательной. Это server-auth TLS с password auth, а не взаимная X.509-аутентификация. KeyFile сохраняет межузловое удостоверение, а TLS защищает его транспорт.

Следующие три запроса намеренно должны отказать, поэтому их оборачиваем в if: ожидаемый exit1 не прерывает Bash, неожиданный успех немедленно завершает эксперимент с кодом 1. Wrong CA — другой самостоятельно созданный удостоверяющий ключ; wrong name — localhost вместо разрешённого IP; третий запрос вообще не включает TLS. Короткий selection timeout ограничивает ожидание. Если диагностический текст у первых двух не связан с проверкой сертификата/имени, сетевой отказ не доказывает нужный сценарий: остановитесь и разберите его.

set -euo pipefail
if mongosh 'mongodb://127.0.0.1:27117/?directConnection=true&serverSelectionTimeoutMS=1500' --quiet --norc --tls --tlsCAFile "$LAB/private/tls/wrong-ca.pem" --eval 'db.runCommand({ping:1})'; then echo 'STOP: wrong CA accepted'; exit 1; fi
if mongosh 'mongodb://localhost:27117/?directConnection=true&serverSelectionTimeoutMS=1500' --quiet --norc --tls --tlsCAFile "$LAB/private/tls/ca.pem" --eval 'db.runCommand({ping:1})'; then echo 'STOP: wrong name accepted'; exit 1; fi
if mongosh 'mongodb://127.0.0.1:27117/?directConnection=true&serverSelectionTimeoutMS=1500' --quiet --norc --eval 'db.runCommand({ping:1})'; then echo 'STOP: plaintext accepted'; exit 1; fi
mongod --config "$LAB/mongod-tls.yml" --shutdown
mongod --config "$LAB/mongod.yml" --fork
ACTION=accept mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js

В реальном авторском опыте положительная проверка, оба certificate/name отказа и plaintext отказ пройдены. Отдельный TLS acceptance test после сборки сервиса проверяет также Go и Database Tools. Для Go профиль уже записал несекретный percent-encoded URI в private/tls/uri.txt: future MONGO_URI берётся из этого файла, MONGO_AUTH_FILE остаётся прежним. URI содержит tls=true и tlsCAFile; адрес 127.0.0.1 совпадает с SAN. Для Tools прежний private/tools.yml дополняют --ssl --sslCAFile "$LAB/private/tls/ca.pem"; это исторические реальные имена флагов Tools 100.20.0, у shell имена --tls/--tlsCAFile. Тест создаёт отдельный diagnostic dump и не объявляет его принятым backup. Полный dump/restore вводится позже.

CA/privatekey не экспортируются и не распространяются с книгой. Принятый профиль нельзя считать бессрочным: сертификат истекает через семь дней, а помощник намеренно не переписывает уже созданные ключи. Для повторения через неделю создайте новый личный стенд; production-ротация требует собственной процедуры выдачи, доверия и перезапуска, не удаления каталога данных.

Доказательство отказа и штатная остановка

Bash, cwd тома, server уже принят. Неаутентифицированное чтение ниже должно напечатать Unauthorized и вернуть 0 только потому, что ожидаемый отказ проверяется внутри выражения. Любой иной исход даёт код 1 и останавливает дальнейшие изменения. Затем operator может штатно остановить собственный экземпляр; данные остаются в data. После остановки повторяют только запуск и ACTION=accept, а не prepare/bootstrap.

set -euo pipefail
mongosh 'mongodb://127.0.0.1:27117/workshop?directConnection=true' --quiet --norc --eval 'try { db.jobs.findOne(); throw Error("unexpected access") } catch (e) { if (e.code !== 13) throw e; print("Unauthorized as expected") }'
mongod --config "$LAB/mongod.yml" --shutdown
mongod --config "$LAB/mongod.yml" --fork
ACTION=accept mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js

Остановка может завершить соединение shell в момент shutdown; не трактуйте любой сетевой отказ как удачную остановку. Сверьте журнал Shutdown complete и недоступность именно своего listener, затем запускайте снова. Нельзя лечить отказ доступа отключением authorization в существующем стенде.
