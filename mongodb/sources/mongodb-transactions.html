Транзакция, повтор операции и прикладной ID

Где заканчивается помощь драйвера и начинается договор сервиса

Повторяемая запись не равна повтору HTTP

Retryable writes — протокол повторения определённых подтверждаемых записей драйвером после подходящего сетевого отказа или потери primary. Для него нужны replica set/sharded topology, поддержанная версия и storage engine. Standalone его не поддерживает. В обычном случае драйвер делает один повтор; сервер использует session ID, номер транзакции и идентификатор операции, чтобы распознать уже исполненную запись. Новый InsertOne после перезапуска приложения с новым логическим номером — новая операция, даже если текст BSON совпадает. UpdateMany не превращается в атомарный retryable batch; список поддержанного задан retryable writes.

Поэтому сервис принимает стабильный ID от клиента, хранит его в _id и на DuplicateKey читает старый документ. Совпали tenant/title — вернёт ранее созданное состояние; не совпали — 409, конфликт ключа и payload. При 503 после потери ответа клиент повторяет тот же ID. Эта политика переживает новый HTTP-запрос и рестарт сервиса; она не доставляет внешнее письмо ровно один раз. Для внешних эффектов нужна дополнительная долговечная очередь/журнал намерений и идемпотентность получателя.

Согласованный переход двух документов

Транзакция — последовательность операций, чьи изменения становятся видимыми вместе при commit или отбрасываются при abort. Наш пример закрывает seed-000001 и создаёт ledger с ID transaction-example-1. Ledger — прикладной журнал завершённых действий, обычная коллекция, не journal WiredTiger и не oplog. Без транзакции авария между update и insert оставит несогласованность: закрытое задание без записи действия либо действие без перехода.

В -mode=transaction создаётся Session, затем WithTransaction получает callback. Все MongoDB-вызовы внутри используют переданный sc context.Context; использование внешнего ctx случайно вынесет операцию за транзакцию. В начале callback читает ledger: если ID уже принят, повтор не закрывает задание снова. Иначе update требует open, увеличивает version и вставляет ledger. Snapshot read concern и majority write concern заданы на уровне transaction, а не каждой внутренней записи. Вызов writeconcern.Majority() в параметрах транзакции не содержит явного Journal=true из настроек Database: внутри транзакции применяются её параметры. В нашем стандартном WiredTiger-наборе majority подразумевает journal при writeConcernMajorityJournalDefault=true; для иной конфигурации это нужно проверить отдельно. Серверная модель и ограничения описаны в transactions.

Callback может исполняться повторно после ошибки с меткой TransientTransactionError, а commit может повторяться после UnknownTransactionCommitResult. Сетевая ошибка commit не доказывает abort: commit уже мог завершиться. Не отправляйте HTTP-платёж, email и не меняйте локальные счётчики внутри callback без отдельного протокола. Не глотайте ошибку внутреннего вызова: верните её callback, чтобы драйвер мог обработать состояние. Сессия принадлежит создавшему Client, используется последовательно и завершается; см. Go transaction API.

Границы изоляции и цена

Snapshot даёт согласованное чтение выбранного момента, но не автоматически serializable-поведение для всех бизнес-инвариантов. Если два врача в разных документах читают «дежурит двое» и каждый снимает только себя, отсутствие конфликта одной записи может нарушить общий инвариант. Можно хранить общий счётчик/версию в одном совместно обновляемом документе, заставив конкурирующие решения пересечься, или изменить модель. Unique index защищает уникальность конкретного ключа; транзакция не заменяет правильное ограничение.

Держать транзакцию открытой во время запроса пользователя или сетевого вызова дорого: она удерживает snapshot/history, может ждать locks, конфликтовать и превышать лимиты времени. Большой backfill обычно выполняют ограниченными идемпотентными порциями, а не одной транзакцией на всю коллекцию. Между shards commit требует распределённого согласования, увеличивая цену и поверхности отказа. Outside local reads при distributed commit не обязаны видеть все shards в один момент: для собственного согласованного чтения выбирают подходящий concern.

Практика выполняется после seed и migrate: Bash/cwd тома, переменные клиента из главы сервиса: "$LAB/bin/job-service" -mode=transaction, затем тот же вызов ещё раз. Код 0 и одно ledger при двух вызовах — ожидаемый результат. Если seed-000001 уже закрыт без ledger, скрипт останавливается; он не сбрасывает состояние. Так обнаруживается нарушенная предпосылка, а не маскируется тест.
