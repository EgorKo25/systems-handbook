BSON: какие байты получает сервер

Драйвер получает число 42 и букву «я». Разложим 22 байта, которые он запишет, а затем сравним, что запрос увидит в поле со значением null и в поле с массивом.

От объекта к последовательности байтов

BSON — двоичное представление упорядоченных пар «имя–типизированное значение». JSON — текстовый формат именованных значений; в HTTP это текстовый вход, BSON в драйвере — другой формат. Длина документа записана int32 в little-endian: младший байт первым. Далее для каждого поля идут байт типа, UTF-8 имя с нулевым окончанием и значение по правилам типа; весь документ заканчивается нулём. Строка хранит свою длину в байтах вместе с конечным нулём. Это объясняет, почему число букв не равно длине BSON.

В -mode=bson сервис сериализует упорядоченный bson.D с int32(42) и строкой «я». Результат: 16 00 00 00 10 6e 00 2a 00 00 00 02 73 00 03 00 00 00 d1 8f 00 00. Первые четыре байта означают 22 байта всего; 10 — int32, имя n занимает два байта, число 42 — четыре. 02 — строка; имя s — два; её длина 3 означает два UTF-8 байта d1 8f и завершающий 00. Последний 00 закрывает документ. Это собственный минимальный пример по грамматике BSON, не перехват реального пакета.

Структура Go с тегами bson:"createdAt" задаёт имена полей, time.Time превращается в BSON Date, int64 версии — в 64-битное целое. bson.D сохраняет заданный порядок и нужен для compound key и команд, где порядок значим. bson.M — карта Go без обещанного порядка обхода. Дублирующиеся имена полей не допускайте: инструменты могут интерпретировать их неодинаково. Сервер может перемещать _id первым, а операции — менять расположение полей; BSON-порядок не является контрактом форматирования ответа HTTP.

Числа, время и ObjectId

В примере 42 задано как int32. Если выбрать int64, само число займёт восемь байтов вместо четырёх, а байт типа сменится с 10 на 12. При чтении JSON приложению нужно выбрать тип числа до отправки в драйвер. Разные числовые типы сравниваются численно в предусмотренных операциях, но остаются разными BSON-типами для проверки схемы и сериализации. В JavaScript Number не представляет точно все int64: в mongosh используйте NumberLong("9007199254740993"), а не уже округлённый числовой литерал.

Поле createdAt нашего задания записывается как BSON Date. Из него можно получить момент времени, но исходный часовой пояс понадобится хранить отдельным полем. Для истории репликации сервер использует другой тип — BSON Timestamp. Его устройство и формат ObjectId разобраны в словаре. У ObjectId есть исключение из правила little-endian: метка времени и счётчик записываются старшим байтом вперёд. Порядок таких идентификаторов не даёт строгого порядка завершения запросов.

Упорядоченная форма важна и при сравнении вложенного документа целиком: равенство встроенному объекту учитывает порядок его полей; для независимых условий используйте dotted paths. При большинстве сравнительных предикатов сервер ограничивает сравнение подходящими типами (type bracketing), объединяя числовые типы по установленным правилам: строка "42" не становится автоматически числом42. Порядок BSON-типов при sort и правила сравнения чисел нужно отличать от автоматического преобразования входа JSON.

Как запрос различает null, массив и отсутствие поля

Для сравнения null возьмём три из пяти документов опыта с разными _id. У null поле a хранит null, у missing этого поля нет, у array-null поле хранит массив [null]. Фильтр {a:null} находит все три документа.

Условиеa:nullНет поля aa:[null]
{a:null}дадада
{a:{$exists:false}}нетданет
{a:{$type:10}}данетда
{$expr:{$eq:[{$type:"$a"},"null"]}}данетнет

В обычном фильтре $type:10 ищет также по элементам массива. В выражении $expr одноимённый оператор проверяет тип всего значения и вернёт "array" для массива, "missing" для отсутствующего поля. У Go-тега omitempty есть последствие для этой проверки: если поле опущено при сериализации, сервер видит именно отсутствие. Сверено 15 ноября 2026 с документацией MongoDB 8.0. Предикат запроса · Выражение агрегации.

Массив хранится как вложенный документ с именами 0,1,… . Условие {a:{$gt:5,$lt:3}} может совпасть с [1,8]: разные элементы удовлетворяют разным частям. $elemMatch требует один элемент, удовлетворяющий обеим частям. Условие {"address.city":"Тула"} проходит по пути вложенного поля; имя с точкой внутри данных создаёт неоднозначность для части инструментов. В примерах избегаем таких имён.

Проверить запросы на своём экземпляре

Продолжайте после приёмки сервера в Bash из каталога тома mongodb/. Должны быть выбраны mongosh нужной версии, MONGOSH_CONFIG_DIR и MONGOSH_DISABLE_TELEMETRY из установки; переменная LAB указывает на ваш существующий стенд, где доступен файл $LAB/private/operator.json. В новом окне сначала восстановите эти переменные, сохранив прежний каталог данных. Скрипт создаст записи в отдельной коллекции semantics и проверит группы идентификаторов.

set -euo pipefail
: "${LAB:?Укажите каталог своего существующего стенда}"
test -r "$LAB/private/operator.json"
export LAB
ACTION=types mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' \
  --quiet --norc --file labs/admin.js
nullOrMissing: ['array-null', 'missing', 'null']
missingOnly: ['missing']
queryTypeNull: ['array-null', 'null']
exactScalarNull: ['null']
differentElements: ['array']
sameElement: []

array в двух последних проверках обозначает документ с [1,8]. При совпадении результатов скрипт завершится с кодом 0. Если semantics уже содержит результаты прежнего опыта, повтор остановится. Проверьте существующие документы, прежде чем начинать этот опыт в новом экземпляре.
