WiredTiger: что значит «записано»

Версии в памяти, журнал восстановления и согласованный checkpoint

Страница, cache и конкурирующие версии

Storage engine — подсистема хранения, которую сервер вызывает после проверки команды. В Community этого стенда используется WiredTiger. Коллекции и индексы имеют свои структуры на диске; страницы — блоки этих структур, читаемые и изменяемые через cache в памяти. BSON документа и дисковая страница не совпадают один к одному. Соседние документы, служебные данные, сжатие и размещение принадлежат внутренней реализации; редактировать .wt файлы вручную нельзя.

Кэш WiredTiger содержит рабочие страницы и версии изменений. MVCC — multi-version concurrency control, управление несколькими версиями: читатель выбирает допустимый снимок, пока писатель подготавливает новую версию. Это уменьшает прямое блокирование, но не делает конфликты невозможными. При конкурирующем изменении одного документа storage engine может вернуть write conflict; сервер повторит поддержанную операцию либо транзакция потребует повторного запуска. Долгий снимок удерживает старые версии и увеличивает объём истории, иногда вызывая snapshot-too-old или давление на ресурсы.

Dirty page — страница, содержимое которой отличается от её дисковой копии. Её изменения уже могут быть защищены дисковым журналом восстановления, разобранным ниже. Eviction — вытеснение страниц, освобождающее место cache; оно не всегда означает простое удаление копии: грязную страницу надо согласованно обработать, а активные версии могут помешать. Когда фоновая работа не успевает, обслуживающие запросы потоки тратят время на освобождение памяти. Рост latency может происходить при невысокой загрузке CPU, если ограничение — диск, cache pressure или очередь. Кэш файлов ОС — ещё один уровень, поэтому рост RSS и занятости RAM не равен утечке.

Два снимка одного задания и удержание старой версии

Разделим прикладное поле version и внутренние версии WiredTiger. version=1 — наше число в BSON для условного update; само оно не управляет MVCC. Движок отдельно хранит сведения о том, какой внутренней транзакции принадлежит изменение и каким снимкам оно доступно. В примере R1 — читатель внутри snapshot-транзакции с уже выбранным старым снимком; W — писатель; R2 начинает чтение со снимком, допускающим завершённое изменение W. Обычные два независимых HTTP-чтения не закрепляют один снимок на всё время между запросами.

Поэтому вытеснение dirty-страницы сложнее записи последнего BSON поверх старого. Движок согласует дисковую страницу и версии, ещё нужные чтениям. История старых изменённых значений может находиться в cache и в WiredTigerHS.wt, файле history store; он не является резервной копией коллекции. Параметр minSnapshotHistoryWindowInSeconds задаёт минимальное окно поддерживаемой истории: его увеличение удерживает больше данных и занимает диск. Очистка старых версий зависит также от активных снимков. Самостоятельно удалить этот файл для освобождения места нельзя. WiredTiger 8.0, Snapshots and Checkpoints / Snapshot History Retention описывает назначение окна.

Измените только длительность R1: если он удерживает снимок дольше, писатели могут продолжать создавать версии, которые нельзя немедленно отбросить. Измеряемые последствия — объём истории/cache, очередь и длительность операций; один рост dirtyBytes не показывает, какой читатель удерживает историю. Таблица объясняет видимость при заданных снимках; конкретные внутренние transaction IDs, timestamp и страницы здесь не считывались. Наблюдать историю напрямую по нашему полю version нельзя.

Изменение, journal и checkpoint

Во время update сервер меняет документ и соответствующие индексные ключи как одно внутреннее изменение. Журнал WiredTiger, или write-ahead log, записывает материал для восстановления этой работы раньше, чем она станет частью нового согласованного checkpoint. Это бинарный журнал в data/journal; текстовый log/mongod.log служит диагностике и не восстанавливает коллекции. Начиная с MongoDB 6.1 journaling всегда включён: старые --nojournal и storage.journal.enabled не подходят для 8.0. Условия синхронизации и группирование записей определяет процесс journaling.

Checkpoint — согласованная сохранённая точка файлов данных. Пока создаётся новая, предыдущая остаётся пригодной; переключение метаданных завершает публикацию новой точки. При аварийном старте движок находит checkpoint и переигрывает нужную устойчивую часть journal. Восстановление не воспроизводит произвольный HTTP-запрос: оно восстанавливает внутренние изменения. Запись с j:true ждёт journal согласно выбранному write concern, а не очередного checkpoint. Частота checkpoint не является допустимым RPO подтверждённых journaled-записей. Этот путь следует из модели WiredTiger.

По умолчанию обычные коллекции используют snappy block compression, индексы — prefix compression. Сжатие уменьшает дисковый объём за цену CPU; изменение defaults не переписывает автоматически старые коллекции. Измерять надо реальный dataset и write pattern, а не число байтов одного BSON. Шифрование транспортного канала, сжатие страниц и шифрование диска решают разные задачи.

Границы сохранности и наблюдение

Ответ на w:1 может прийти до устойчивой синхронизации journal; локальные новые значения уже могут быть видны другим чтениям. w:1,j:true защищает выбранную локальную запись по договору диска, но она может быть rollback при потере primary до репликации. Даже majority не исправляет одновременную потерю всех дисков или ошибку удаления operator. Контроллер/VM/файловая система должны честно исполнять синхронизацию; этот том не проводил испытание физического отключения питания.

Bash, cwd тома, собственный принятый сервер: ACTION=stats mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js. Ожидается код 0 и числа cacheBytes/dirtyBytes/maxCacheBytes в байтах, connections и queues. Снимите два результата с известным интервалом, сохраните вместе с нагрузкой. Накопительные counters сравнивают разностью, gauges — уровнями. Один снимок грязных байтов не измеряет скорость записи. При отказе auth или отсутствии нужного поля не продолжайте настройку cache наугад; сначала сохраните версию и фактическую структуру serverStatus.
