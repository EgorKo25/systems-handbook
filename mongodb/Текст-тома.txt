Что подготовить и что считается успехом

Порядок чтения

MongoDB — серверная система хранения документов. В этом томе документ означает именованные поля с типизированными значениями: заказу можно дать номер, время и массив позиций, сохранив их одним объектом. Документ не отменяет проектирование данных: сначала решают, что должно изменяться вместе, затем выбирают представление, индексы и гарантии ответа.

Наш сервис — программа, принимающая запросы клиентов по HTTP, протоколу запроса и ответа, — хранит задания мастерской. У задания есть клиент tenant, заголовок, состояние open/closed, дата создания и версия изменения. Данные переживают остановку приложения и сервера. Начальное наполнение, или seed, создаёт собственные воспроизводимые данные. Первая поставка создаёт документы версии 1; следующая добавляет приоритет и индекс; затем мы разбираем повтор запроса, транзакцию с журналом действий и восстановление в отдельный экземпляр. Это учебные имена и данные, без реальных заказчиков.

Что подготовить и что считается успехом

Для исполнения нужен личный Linux Ubuntu 24.04 x86-64 с уже доступными Python 3.12+, GnuPG, подходящей системной OpenSSL и Go 1.25+. Никакая команда не требует root или установки службы. На рабочем Windows путь этой книги — чтение; для практики выделяют собственную Linux VM и переносят туда исходники. Установка VM меняет состояние компьютера и не является «работой без следов».

Постоянный каталог читателя — $HOME/handbook-lab/mongodb. В нём живут данные, журналы, конфигурация и приватные пароли. Книга и её переносимая копия содержат только исходники. Все команды выполняет ваш обычный пользователь в каталоге тома mongodb/, если явно не написано иначе. Сначала откройте Bash и выполните set -euo pipefail: отказ останавливает зависимую последовательность. Каждое новое окно требует повторного выбора LAB, MONGOSH_CONFIG_DIR и прочих переменных, показанных в лаборатории.

Нужны свободные порты 127.0.0.1:27117 для данных, 127.0.0.1:18089 для HTTP сервиса и позднее 127.0.0.1:27118 для восстановления. Loopback — адрес только этой машины. Он ограничивает сетевую достижимость, но процессы того же пользователя читают ваши файлы. Проверка занятости и отказ запуска лучше смены чужой службы. Все службы книги одновременно на 8–16 GiB не нужны: один небольшой MongoDB и один Go-процесс достаточны для основного пути.

Replica set — набор реплик: экземпляров, согласующих роль ведущего и историю изменений; вначале у нас один участник. Restore — восстановление сохранённой копии на отдельную цель. Native-проверка означает настоящее исполнение установленной программы, а не модель. Приёмка — подтверждённая версия и конфигурация, аутентификация (проверка личности), успешная запись/чтение, сохранение после перезапуска и отдельный restore. Открытый TCP-порт доказывает только приём соединения. Один узел такого replica set позволяет изучать связанные операции, но не даёт резервной копии или защиты от потери машины.

Какие объекты создаёт сервер

Поле — имя и значение внутри документа; значение может быть строкой, числом, датой, вложенным документом или массивом. Коллекция объединяет документы одного назначения, например jobs. База данных — именованная область коллекций и доступа, у нас workshop. Экземпляр — запущенный процесс mongod со своим каталогом данных; один экземпляр хранит несколько баз. Имя workshop.jobs называется namespace: оно определяет конкретную коллекцию, а не сетевой адрес.

Клиентская программа отправляет команды серверу. mongosh — отдельная интерактивная программа, исполняющая JavaScript и вызывающая команды через драйвер. Go-драйвер — библиотека в нашем приложении, превращающая вызовы Go в обмен с сервером. Старый shell mongo и mongosh различаются; наличие mongod не доказывает наличие любого shell. mongos — маршрутизатор для распределённых по частям данных, его пока не запускаем.

В терминах приложения одно задание — документ. Его поля состояния и версии меняются атомарно: другой читатель не увидит половину одного обновления. Атомарно значит «либо весь предусмотренный переход этого объекта, либо ни одна его часть». Из этого не следует, что два независимых документа изменятся вместе, что диск уже устойчиво сохранил запись или что любой следующий читатель на другом узле увидит результат. Эти три вопроса книга разбирает отдельно.

Почему вложение иногда полезнее связи

Небольшой адрес выполнения можно вложить в задание: читаемое вместе состояние придёт одной записью и изменится одним обновлением. Историю миллионов событий в массив задания помещать нельзя: BSON — двоичная кодировка типизированных полей; один BSON-документ ограничен 16 MiB, а растущий объект повышает стоимость передачи, обновления и конкуренции. Для неограниченной истории создают коллекцию job_events с полем jobId, индексом и понятной политикой удаления. Ссылка — обычное значение, сервер автоматически не проверяет существование связанного документа как внешний ключ SQL.

Копирование названия клиента в задание делает чтение дешевле, но рождает договор: это историческое название на момент заказа или актуальное имя, которое надо массово менять? Если требование неизвестно, оптимизация преждевременна. Частые совместные обновления подсказывают границу документа; частые независимые обновления и неограниченный рост — повод разделить объекты. Транзакция — блок операций с общим решением фиксации или отмены — умеет согласовать несколько документов, но добавляет согласование, удержание снимка и обработку повторов.

Уникальность и договор формы

_id — обязательный идентификатор документа, уникальный в обычной коллекции данного экземпляра. Индекс — поддерживаемая сервером поисковая структура, которая может одновременно проверять ограничение уникальности. Сервер создаёт для _id такой уникальный индекс; если клиент не дал значение, драйвер обычно генерирует ObjectId. Наш сервис передаёт строковый ID запроса, потому что повтор HTTP после потерянного ответа должен обращаться к той же записи. Случайно новый ID при повторе создаст ещё одно задание. Для sharded collection глобальная уникальность имеет дополнительные условия, разобранные позднее.

Гибкость формы не равна отсутствию схемы. Схема — наш договор имён, типов, обязательных полей и допустимых переходов. Сначала он задан Go-типом и проверкой HTTP; серверный validator затем может запретить неправильный тип. В коллекции могут сосуществовать версии документа 1 и 2, поэтому приложение обязано явно читать обе во время перехода. Миграция — управляемое изменение существующих записей; резервирование и совместимость важнее самого $set.

Проверьте модель без запуска: где хранить один текущий статус и где растущие комментарии? Что означает отсутствие priority у старого задания? Как отличить повтор создания от попытки изменить заголовок под старым ID? Ответы понадобятся при изучении типов и обработчика HTTP.

Версии и происхождение

Воспроизводимая линия тома — MongoDB Community 8.0.34, патч поддерживаемой основной ветки 8.0 от 13 октября 2026. Это выбранная учебная ветка, а не утверждение, что 8.0 — новейшая основная версия. На 1 ноября 2026 отдельно получены mongosh 2.14.1, Database Tools 100.20.0 и Go-драйвер v2.9.2. Номера этих продуктов независимы. Актуальные предупреждения и путь обновления проверяют перед новой установкой по release notes 8.0 и реестру поставки.

Community — доступная в исходниках самостоятельная редакция под SSPL-1.0; это не лицензия Apache и не обозначение OSI-approved open source. Enterprise Advanced — отдельная коммерческая подписка; Atlas — управляемый сервис. Самостоятельное использование Community, распространение программы и предоставление её функциональности как сервиса — разные случаи текста лицензии. Сам текст сохранён в licenses/; юридические обязательства определяет он. Бесплатный учебный стенд не получает автоматически Enterprise audit, встроенное шифрование at rest или управляемый Atlas PIT restore. Приложение с Apache-2.0 драйвером не меняет лицензию сервера.

У закреплённой ветки есть также требования к ядру Linux: актуальные release notes предупреждают о несовместимости TCMalloc с ядрами 6.19…7.0.13; исправление указано для 7.0.14 и новее. Названия Ubuntu 24.04 недостаточно для проверки этого условия. На затронутом ядре не обходите startup-отказ флагами; выберите отдельно подготовленное совместимое личное окружение. Эта лаборатория ядро и host-пакеты не меняет.

Подготовка каталога до скачивания

Следующий блок — Bash обычного пользователя, cwd mongodb/, Python и GnuPG уже установлены; каталог LAB ещё не существует. umask 077 ограничивает права новых файлов. prepare.py создаёт только новый личный каталог, случайный межузловой ключ, два пароля и конфигурацию YAML (текст вложенных ключей с отступами) с абсолютными путями. Код 0 и строка prepared означают подготовленные файлы, но не запущенный сервер. При отказе не удаляйте старый стенд: выберите новое имя или исследуйте существующее состояние.

set -euo pipefail
umask 077
export LAB="$HOME/handbook-lab/mongodb"
python3 labs/prepare.py "$LAB"
python3 labs/install.py "$LAB"
export PATH="$LAB/tools/server/bin:$LAB/tools/shell/bin:$LAB/tools/dbtools/bin:$PATH"
export MONGOSH_CONFIG_DIR="$LAB/shell-config"
export MONGOSH_DISABLE_TELEMETRY=1
mongod --version
mongosh --version
mongodump --version

install.py рассчитан только на Ubuntu 24.04 x86-64, скачивает закреплённые tgz в downloads/, сравнивает SHA-256 и проверяет подпись сервера до распаковки. SHA-256 — отпечаток байтов, его совпадение проверяет целостность относительно доверенного ожидаемого значения. Подпись связывает архив с ключом выпуска. Для этого релиза фактически подтверждён fingerprint 4B07 52C1 BCA2 38C0 B4EE 14DC 41DE 058A 4E7D CA05. В старом примере документации встречается другой fingerprint: не заменяйте проверку под копируемый вывод. Новая ротация ключа требует отдельной проверки официального объявления, а не автоматического принятия любого ключа по URL.

Архивы распаковываются в tools/server, tools/shell, tools/dbtools, не в /usr/bin. Ожидаются версии из начала главы, modules: [] у Community и код 0. Ошибка загрузчика, CPU или OpenSSL — остановка; нельзя считать скачанный файл установленной программой. Для другой ОС выбирают её официальный вариант и заново фиксируют хеши. Server tarball содержит mongod и mongos; shell и dump/restore получены отдельно.

Запуск до первого пользователя

Primary — ведущая роль участника набора, принимающая обычные записи. URI — строка адреса с параметрами подключения; наш URI указывает только loopback. В том же Bash и cwd mongodb/ выполните блок по частям. --config читает созданный YAML; --fork оставляет процесс в фоне после успешного первоначального запуска, с журналом в LAB. Код 0 не заменяет последующую приёмку. Если порт занят или путь недоступен, читайте $LAB/log/mongod.log; не переходите к bootstrap. Локальное исключение — временная возможность создать первого пользователя на ещё не инициализированном сервере с access control; оно не действует после создания пользователя.

set -euo pipefail
mongod --config "$LAB/mongod.yml" --fork
PHASE=init mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/bootstrap.js
mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --eval 'if (!db.hello().isWritablePrimary) { throw Error("STOP: wait for primary, repeat only this probe") }'
PHASE=users mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/bootstrap.js
ACTION=accept mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js

После init первичные выборы могут ещё не закончиться: probe с кодом 1 означает остановить последовательность и повторить только чтение готовности через несколько секунд. PHASE=users создаёт operator в admin с MongoDB-ролью root (полное администрирование БД, не OS-пользователь root), затем app с ролью readWrite только в workshop. Не запускайте его повторно при частичном успехе: сначала выясните, какой пользователь уже создан. --norc запрещает стартовый пользовательский JavaScript, --quiet сокращает приветствие, --file исполняет конкретный файл. Скрипт принимает у db.auth и старое число 1, и реальный ответ mongosh {ok:1}. Приёмка записывает пробный документ с write concern majority — подтверждением нужного большинства участников с данными — и j:true, ожиданием дискового журнала. В одном участнике это он сам; распределённые условия разобраны в книге III. Приёмка выводит версию, primary, bind и writeRead: true, код 0; пароли не печатаются.

Кто владеет файлами и процессом

В нашем стенде обычный пользователь создал LAB/data, поэтому запущенный им mongod может изменять этот каталог. Ни shell, ни Go не открывают файлы WiredTiger напрямую: они обращаются к процессу. В log/ остаётся структурированный журнал сервера, в run/ — PID-файл с номером процесса, в private/ — ключ и пароли. PID-файл не даёт полномочий и после аварии может устареть. Каталог data и отдельные файлы WiredTiger*, collection-*.wt, index-*.wt, journal/ составляют единое управляемое сервером состояние; выборочное копирование «нужной коллекции» по имени файла некорректно.

YAML — текст вложенных ключей с отступами. storage.dbPath задаёт каталог данных; systemLog.path — файл журнала; logAppend: true сохраняет старые строки при старте. net.bindIp: 127.0.0.1 и port: 27117 ограничивают listener. Unix-сокет отключён явно, чтобы все точки доступа были видны в договоре. cacheSizeGB: 0.25 ограничивает только WiredTiger cache, а не весь RSS процесса: ещё нужны память исполнения, соединения и кэш файлов ОС. Нельзя обещать, что mongod потребит ровно 256 MiB.

Приоритет не заменяет проверку действующей конфигурации

Для совпадающих серверных параметров CLI имеет приоритет над конфигурационным файлом. mongod --config ... --port 27119 меняет порт этого запуска; переменная shell сама не подставляется внутрь YAML. Экземпляр не перечитывает все настройки при редактировании файла: большинство стартовых опций требуют контролируемого перезапуска, а поддержанные runtime-параметры меняют отдельной административной командой. Не используйте --configExpand exec/rest для простой установки: это отдельное исполнение или получение содержимого, отсутствующее в нашем стенде.

Доказательство — команда getCmdLineOpts, которую вызывает ACTION=accept, и фактические listeners; файл на диске может уже отличаться от действующего процесса. При смене порта одновременно меняются URI, адрес члена replica set и ожидания приёмки. Конфигурация клиента — другой уровень: Go получает адрес через MONGO_URI и права через MONGO_AUTH_FILE; административный shell читает private/operator.json. Не пишите пароль в URI командной строки: он попадает в историю и список процессов.

Аутентификация, авторизация и TLS

Аутентификация проверяет, кто обращается; наш механизм SCRAM-SHA-256 доказывает знание пароля через согласованный обмен. Пользователь определяется именем вместе с authentication database: operator@admin и app@workshop — разные записи. Авторизация проверяет, какие операции этому пользователю разрешены; роль readWrite не даёт приложению управлять чужой базой или выключать сервер. Ключ security.keyFile служит внутренней аутентификации членов replica set, а не паролем HTTP-приложения. Утечка ключа требует своей процедуры ротации.

TLS защищает транспорт и проверяет личность сервера по доверенному CA — удостоверяющему центру. Он не выдаёт права записи. Наш loopback-стенд использует SCRAM без TLS и не выдаётся за сетевую production-конфигурацию. Для отдельной личной VM до открытия сети готовят сертификат с SAN нужного DNS-имени/IP, приватный ключ с узкими правами, доверие клиента и net.tls.mode: requireTLS, certificateKeyFile, CAFile. Клиенту передают tls=true и CA; проверяют положительное подключение, отказ с чужим CA и отказ по неверному имени. Флаги allowInvalidCertificates/allowInvalidHostnames снимают проверку, а не исправляют PKI.

Проверяемый личный TLS-профиль до работы с данными

Профиль ниже временно переводит тот же остановленный экземпляр на TLS, сохраняя пользователей и dataPath, затем возвращает основной loopback-режим учебного маршрута. Это транспортный опыт на личной машине; сетевую production-службу назад в plaintext не переводят. Нужен уже доступный OpenSSL CLI. labs/tls-profile.py создаёт новую личную CA и серверный сертификат, действительные семь дней, с единственным SAN IP 127.0.0.1. Bash/cwd тома, сервер принят, Go ещё не нужен, private/tls отсутствует. Следующие три запроса намеренно должны отказать, поэтому их оборачиваем в if: ожидаемый exit1 не прерывает Bash, неожиданный успех немедленно завершает эксперимент с кодом 1. От объекта к последовательности байтов

BSON — двоичное представление упорядоченных пар «имя–типизированное значение». JSON — текстовый формат именованных значений; в HTTP это текстовый вход, BSON в драйвере — другой формат. Длина документа записана int32 в little-endian: младший байт первым. Далее для каждого поля идут байт типа, UTF-8 имя с нулевым окончанием и значение по правилам типа; весь документ заканчивается нулём. Строка хранит свою длину в байтах вместе с конечным нулём. Это объясняет, почему число букв не равно длине BSON.

В -mode=bson сервис сериализует упорядоченный bson.D с int32(42) и строкой «я». Результат: 16 00 00 00 10 6e 00 2a 00 00 00 02 73 00 03 00 00 00 d1 8f 00 00. Первые четыре байта означают 22 байта всего; 10 — int32, имя n занимает два байта, число 42 — четыре. 02 — строка; имя s — два; её длина 3 означает два UTF-8 байта d1 8f и завершающий 00. Последний 00 закрывает документ. Это собственный минимальный пример по грамматике BSON, не перехват реального пакета.

Структура Go с тегами bson:"createdAt" задаёт имена полей, time.Time превращается в BSON Date, int64 версии — в 64-битное целое. bson.D сохраняет заданный порядок и нужен для compound key и команд, где порядок значим. bson.M — карта Go без обещанного порядка обхода. Дублирующиеся имена полей не допускайте: инструменты могут интерпретировать их неодинаково. Сервер может перемещать _id первым, а операции — менять расположение полей; BSON-порядок не является контрактом форматирования ответа HTTP.

Числа, время и ObjectId

Int32 — целое со знаком на 32 бита, int64 — на 64; double — двоичная плавающая точка, decimal128 — десятичное представление на 128 бит. Не храните денежные копейки как случайно декодированный JSON double: задайте int64 минимальных денежных единиц либо decimal128 с договором округления. Разные числовые типы сравниваются численно в предусмотренных операциях, но остаются разными BSON-типами для проверки схемы и сериализации. В JavaScript Number не представляет точно все int64: в mongosh используйте NumberLong("9007199254740993"), а не уже округлённый числовой литерал.

BSON Date — int64 миллисекунд UTC от эпохи Unix, без исходного часового пояса. Нужный локальный пояс хранится отдельно. BSON Timestamp — внутренний тип времени и порядкового счётчика для репликации, не замена дате задания. ObjectId — 12 байт: четыре байта секунд времени, пять случайных байтов процесса и трёхбайтовый счётчик. В отличие от большинства BSON-чисел компоненты timestamp/counter ObjectId имеют big-endian порядок. Это удобный уникальный ID, но не строгие часы завершения операций и не последовательный глобальный номер заказа.

Упорядоченная форма важна и при сравнении вложенного документа целиком: равенство встроенному объекту учитывает порядок его полей; для независимых условий используйте dotted paths. При большинстве сравнительных предикатов сервер ограничивает сравнение подходящими типами (type bracketing), объединяя числовые типы по установленным правилам: строка "42" не становится автоматически числом42. Порядок BSON-типов при sort и правила сравнения чисел нужно отличать от автоматического преобразования входа JSON.

Null, missing и массив

null — присутствующее поле с пустым значением; missing означает, что пары с таким именем нет. Запрос {a:null} подходит обоим случаям. {a:{$type:10}} выбирает BSON null, {a:{$exists:false}} — отсутствие поля. Go-тег omitempty способен удалить нулевое значение при сериализации: решите, должно ли отсутствие означать default, «не известно» или ошибку. Для миграции не заменяйте все missing на null без анализа читателей.

Массив хранится как вложенный документ с именами 0,1,… . Условие {a:{$gt:5,$lt:3}} может совпасть с [1,8]: разные элементы удовлетворяют разным частям. $elemMatch требует один элемент, удовлетворяющий обеим частям. Условие {"address.city":"Тула"} проходит по пути вложенного поля; имя с точкой внутри данных создаёт неоднозначность для части инструментов. В примерах избегаем таких имён.

После приёмки, Bash/cwd тома: ACTION=types mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js. Оно создаёт отдельную коллекцию semantics, ожидает nullOrMissing=[missing,null], differentElements=[array], sameElement=[] и код 0. Порядок первых двух ID не важен. Второй запуск намеренно откажет, если коллекция уже наполнена: исходное состояние нужно изучить, а не автоматически стереть.

CRUD сокращает Create, Read, Update, Delete — создание, чтение, изменение, удаление. Предикат — условие, которое должен выполнить документ; сервер проверяет его при выборе записи. {tenant:"tenant-01",state:"open"} связывает условия логическим И. Find не обязан сразу получить все документы: следующая порция может потребовать getMore, а ошибку проверяют и после чтения курсора.

Условие сортировки определяет порядок до limit. Сортировать лишь по createdAt недостаточно, если даты совпадают; добавляем _id как однозначное разрешение равенства. Операторы обновления и защита от потери изменения

$set меняет указанные поля, $unset удаляет поле, $inc увеличивает числовое значение, $push добавляет элемент массива. Оператор — именованное правило изменения, которое исполняет сервер. replaceOne заменяет весь документ, кроме требований к _id; забытые приложением поля могут исчезнуть. Upsert означает создать документ, если предикат никого не нашёл; это не «всегда update». Несколько конкурирующих upsert без уникального ключа могут создать логические дубликаты.

Наш HTTP close отправляет предикат {_id:id,state:"open",version:1} и одновременно {$set:{state:"closed"},$inc:{version:1}}. Успешный первый вызов даёт version=2; второй не соответствует предикату и modified=0. Сравнение версии — optimistic concurrency: клиент меняет только известное ему состояние. Чтение версии в Go, потом update лишь по _id оставляет окно гонки и способно затереть конкурента. Атомарность одиночного update закрывает окно только для проверки внутри самого предиката.

matchedCount — сколько документов подошло, modifiedCount — сколько реально изменено. Ноль modified не всегда ошибка: новое значение уже могло совпадать со старым. updateMany атомарен по каждому документу, но между документами могут вклиниться другие операции. После отказа часть уже изменена. Миграция нашего сервиса фильтрует schemaVersion=1 и ставит 2 вместе с priority=0; повтор обрабатывает остаток. Он не возвращает старые значения и не является обратной миграцией.

Валидация и массовое исполнение

Серверный validator задаёт правила формы; $jsonSchema может требовать строковый tenant, дату createdAt и целочисленную version. Он проверяет будущие записи согласно validationLevel/action, а не переписывает существующие документы. Backfill — дозаполнение ранее созданных документов по новому договору формы. Вводить жёсткую обязательность priority до backfill сломает старое приложение. Сначала код читает обе версии и пишет новую, затем порциями преобразуются старые, проверяются остатки и только потом ужесточается правило.

BulkWrite позволяет передать драйверу несколько операций одним вызовом. Драйвер делит их на команды и пакеты по ограничениям сервера; один вызов не гарантирует один сетевой пакет. По умолчанию ordered-пакет останавливается на первой ошибке записи; уже исполненные не отменяет. Unordered позволяет продолжать независимые операции и требует разобрать ошибки по индексам входа. В seed используем batches по 500 и deterministic _id: $setOnInsert добавляет документ только при первом upsert, повтор не меняет ранее принятые данные. Это конкретная идемпотентность начального наполнения, а не гарантия exactly once для любой бизнес-операции.

Практика CRUD выполняется через собственный HTTP-сервис в книге IV: сначала он будет собран и запущен. Сейчас полезно прочитать InsertOne, обработку DuplicateKey, предикат close и cur.All в исходнике. Вызов InsertOne(ctx, job) не является прямой записью файла. Сначала драйвер кодирует Go-значения в BSON, определяет тип операции и выбирает сервер. Топология — известная драйверу картина узлов и их ролей; мониторинг поддерживает её отдельными служебными соединениями. mongo.Connect создаёт клиент и запускает обнаружение, но не гарантирует готовое подключение; наш сервис до HTTP-listener вызывает Ping с требованием primary и ограничением времени.

Server selection — выбор допустимого узла по виду операции, read preference и текущей топологии. Для записи нужен primary; адрес seed в URI — начальная точка обнаружения, а не обещание, что все операции останутся на ней. В hello сервер сообщает имя replica set, роли, адреса членов и wire versions. Имена из конфигурации набора должны разрешаться и быть доступны клиенту: успешное соединение с одним seed ещё не гарантирует доступность остальных. directConnection=true в административном URI фиксирует один учебный узел; Go URI использует replicaSet=study и обычное обнаружение.

После выбора узла операция получает соединение из pool — набора готовых к повторному использованию TCP-соединений этого Client к этому серверу. При свободном соединении не нужны новый TCP, TLS и SCRAM на каждый запрос. При исчерпании pool операция ждёт в очереди; увеличение maxPoolSize может лишь перенести очередь в сервер и ухудшить хвост задержки. Наш maxPoolSize=12 ограничивает рабочие соединения к каждому серверу, maxConnecting=2 — параллельное создание новых. Мониторинговые сокеты учитываются отдельно. Один Client переиспользуется всеми HTTP-запросами. Эти механизмы описаны в контракте pools.

Новый сокет до команды

Если соединения ещё нет, драйвер разрешает DNS-имя, соединяет TCP, при включённом TLS проверяет цепочку сертификата и имя, обменивается приветствием и проходит аутентификацию. В нашем literal loopback URI DNS и TLS отсутствуют, но SCRAM остаётся. URI mongodb+srv добавляет DNS SRV/TXT обнаружение и имеет другие defaults: его нельзя подставить в офлайн-лабораторию как обычную строковую замену.

Контекст Go несёт deadline — конечный момент ожидания и сигнал отмены. У нас выбор сервера ограничен 3 секундами, создание соединения 2 секундами, общий клиентский timeout 5 секундами, а HTTP-операция получает контекст 3 секунды. Не складывайте эти числа как обещанное время ответа: эффективный остаток бюджета и более ранний deadline могут закончить работу раньше. Timeout ожидания не доказывает, что удалённая запись отменена. Если сеть оборвалась после server commit и до получения ответа, клиент знает об ошибке обмена, но не знает исход операции.

Сообщение и ответ

Современная команда идёт в OP_MSG. Заголовок имеет общую длину, requestID, responseTo и номер opcode 2013; затем flags и секции. Секция kind 0 содержит тело команды BSON с именем команды и $db; kind 1 позволяет передать последовательность документов, например batch insert. Запрос может включать session ID, transaction number и writeConcern. Это транспортные поля и договор исполнения, не дополнительные поля нашего job. Согласованное сжатие может завернуть сообщение в OP_COMPRESSED. TLS, если включён, шифрует этот обмен. Схема ниже объясняет обычную подтверждаемую команду, не реализует сетевой клиент; точные форматы — в официальной спецификации.

Сервер проверяет сообщение, BSON и размер, удостоверение соединения, права операции и требования к роли узла. Затем получает коллекцию, выбирает план и выполняет чтение/изменение через storage engine, подсистему хранения. Ответ OP_MSG с responseTo связывает результат с запросом. ok:1 означает успех команды верхнего уровня, но writeErrors/writeConcernError могут содержать отказ отдельных записей или ожидания подтверждения. Драйвер превращает их в ошибки Go и результат; приложение должно проверить ошибку прежде чем печатать «создано».

CommandMonitor наблюдает имена команд и их выполнение на драйверном уровне. Он не является packet capture и сам по себе не доказывает запись на диск или полное время ожидания pool/selection. В коде счётчик сохраняет только число успешных команд: полные BSON payload не логируются, чтобы данные и пароли не оказались в диагностике.

Разобранный запрос: 51 байт без скрытых полей

Возьмём отдельный минимальный пример команды {ping:int32(1),$db:"admin"}, которая проверяет ответ сервера, не читая jobs. Это самостоятельно составленные байты формата OP_MSG, а не перехват соединения нашего Go-сервиса. Выбраны ровно одна секция kind 0, нулевые флаги, отсутствие сжатия и контрольной суммы. Реальный драйвер может добавить lsid, временные отметки и другие поля; TLS скроет их на сетевом соединении. Числа смещений ниже десятичные и считаются с нуля, байты записаны шестнадцатерично; LE означает уже введённый little-endian.

Четыре поля заголовка занимают по 4 B: длина 51, идентификатор запроса 17, нулевой responseTo и код 2013. Затем идут 4 B flagBits и один байт kind=0. BSON начинается с байта 21, занимает 30 B и заканчивается байтом 50: 16+4+1+30=51. Внутренняя длина 30 включает собственные четыре байта длины BSON, но не kind и заголовок OP_MSG. requestID связывает сообщения одного обмена; он не равен нашему строковому _id задания и не является номером сессии.

Разбор без рисунка. В смещениях 0…3 стоят 33 00 00 00, то есть 51. В 4…7 — 11 00 00 00, то есть requestID=17; в 8…11 четыре нуля; в 12…15 — DD 07 00 00, то есть 0x07DD=2013. Флаги в 16…19 нулевые, kind в 20 равен 0. Нулевые флаги здесь означают, что нет checksumPresent и moreToCome; обычный ответ ожидается. checksumPresent обозначает наличие контрольной суммы. moreToCome сообщает получателю, что следующее сообщение придёт без его действия: до сообщения с нулевым флагом получатель не должен отправлять новое. Минимальный модельный ответ с {ok:double(1)} занимает 38 B: 16+4+1+17. Его собственный requestID пусть равен 90, а responseTo обязан указывать 17 из запроса. Успех ping не доказывает доступ к workshop или устойчивость записи. Формат сверяется с Wire protocol 8.0, Header/OP_MSG/Sections и BSON 1.1; изображение и значения придуманы для этого разбора.

Страница, cache и конкурирующие версии

Storage engine — подсистема хранения, которую сервер вызывает после проверки команды. В Community этого стенда используется WiredTiger. Коллекции и индексы имеют свои структуры на диске; страницы — блоки этих структур, читаемые и изменяемые через cache в памяти. BSON документа и дисковая страница не совпадают один к одному. Соседние документы, служебные данные, сжатие и размещение принадлежат внутренней реализации; редактировать .wt файлы вручную нельзя.

Кэш WiredTiger содержит рабочие страницы и версии изменений. MVCC — multi-version concurrency control, управление несколькими версиями: читатель выбирает допустимый снимок, пока писатель подготавливает новую версию. Это уменьшает прямое блокирование, но не делает конфликты невозможными. При конкурирующем изменении одного документа storage engine может вернуть write conflict; сервер повторит поддержанную операцию либо транзакция потребует повторного запуска. Долгий снимок удерживает старые версии и увеличивает объём истории, иногда вызывая snapshot-too-old или давление на ресурсы.

Dirty page — страница, содержимое которой отличается от её дисковой копии. Её изменения уже могут быть защищены дисковым журналом восстановления, разобранным ниже. Eviction — вытеснение страниц, освобождающее место cache; оно не всегда означает простое удаление копии: грязную страницу надо согласованно обработать, а активные версии могут помешать. Когда фоновая работа не успевает, обслуживающие запросы потоки тратят время на освобождение памяти. Рост latency может происходить при невысокой загрузке CPU, если ограничение — диск, cache pressure или очередь. Кэш файлов ОС — ещё один уровень, поэтому рост RSS и занятости RAM не равен утечке.

Два снимка одного задания и удержание старой версии

Разделим прикладное поле version и внутренние версии WiredTiger. version=1 — наше число в BSON для условного update; само оно не управляет MVCC. Движок отдельно хранит сведения о том, какой внутренней транзакции принадлежит изменение и каким снимкам оно доступно. В примере R1 — читатель внутри snapshot-транзакции с уже выбранным старым снимком; W — писатель; R2 начинает чтение со снимком, допускающим завершённое изменение W. Обычные два независимых HTTP-чтения не закрепляют один снимок на всё время между запросами.

 | Шаг | Действие и версия документа | Что может прочитать R1/R2

 | 0 | Видимая версия: open, version=1. R1 выбирает снимок. | R1 читает open/1.

 | 1 | W подготавливает closed/2 и изменение индексных ключей. | Незавершённое изменение W не выдаётся R1 как его собственный результат.

 | 2 | W фиксирует изменение. Для запроса может ещё ожидаться concern. | R1 сохраняет open/1; R2 с допустимым новым снимком видит closed/2.

 | 3 | R1 завершает транзакцию. | Его снимок больше не удерживает open/1, но другие читатели и окно истории ещё могут требовать её.

Поэтому вытеснение dirty-страницы сложнее записи последнего BSON поверх старого. Движок согласует дисковую страницу и версии, ещё нужные чтениям. История старых изменённых значений может находиться в cache и в WiredTigerHS.wt, файле history store; он не является резервной копией коллекции. Параметр minSnapshotHistoryWindowInSeconds задаёт минимальное окно поддерживаемой истории: его увеличение удерживает больше данных и занимает диск. Очистка старых версий зависит также от активных снимков. Самостоятельно удалить этот файл для освобождения места нельзя. WiredTiger 8.0, Snapshots and Checkpoints / Snapshot History Retention описывает назначение окна.

Измените только длительность R1: если он удерживает снимок дольше, писатели могут продолжать создавать версии, которые нельзя немедленно отбросить. Измеряемые последствия — объём истории/cache, очередь и длительность операций; один рост dirtyBytes не показывает, какой читатель удерживает историю. Таблица объясняет видимость при заданных снимках; конкретные внутренние transaction IDs, timestamp и страницы здесь не считывались. Наблюдать историю напрямую по нашему полю version нельзя.

Изменение, journal и checkpoint

Во время update сервер меняет документ и соответствующие индексные ключи как одно внутреннее изменение. Журнал WiredTiger, или write-ahead log, записывает материал для восстановления этой работы раньше, чем она станет частью нового согласованного checkpoint. Это бинарный журнал в data/journal; текстовый log/mongod.log служит диагностике и не восстанавливает коллекции. Начиная с MongoDB 6.1 journaling всегда включён: старые --nojournal и storage.journal.enabled не подходят для 8.0. Условия синхронизации и группирование записей определяет процесс journaling.

Checkpoint — согласованная сохранённая точка файлов данных. Пока создаётся новая, предыдущая остаётся пригодной; переключение метаданных завершает публикацию новой точки. При аварийном старте движок находит checkpoint и переигрывает нужную устойчивую часть journal. Восстановление не воспроизводит произвольный HTTP-запрос: оно восстанавливает внутренние изменения. Запись с j:true ждёт journal согласно выбранному write concern, а не очередного checkpoint. Частота checkpoint не является допустимым RPO подтверждённых journaled-записей. Этот путь следует из модели WiredTiger.

По умолчанию обычные коллекции используют snappy block compression, индексы — prefix compression. Сжатие уменьшает дисковый объём за цену CPU; изменение defaults не переписывает автоматически старые коллекции. Измерять надо реальный dataset и write pattern, а не число байтов одного BSON. Шифрование транспортного канала, сжатие страниц и шифрование диска решают разные задачи.

Границы сохранности и наблюдение

Ответ на w:1 может прийти до устойчивой синхронизации journal; локальные новые значения уже могут быть видны другим чтениям. w:1,j:true защищает выбранную локальную запись по договору диска, но она может быть rollback при потере primary до репликации. Даже majority не исправляет одновременную потерю всех дисков или ошибку удаления operator. Контроллер/VM/файловая система должны честно исполнять синхронизацию; этот том не проводил испытание физического отключения питания.

Bash, cwd тома, собственный принятый сервер: ACTION=stats mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js. Накопительные counters сравнивают разностью, gauges — уровнями. Один снимок грязных байтов не измеряет скорость записи. При отказе auth или отсутствии нужного поля не продолжайте настройку cache наугад; сначала сохраните версию и фактическую структуру serverStatus.

Планировщик выбирает способ найти документы и выполнить сортировку. COLLSCAN означает просмотр коллекции с проверкой предиката; IXSCAN — обход индексных ключей, FETCH — получение самих документов по ссылкам. SORT означает отдельную сортировку кандидатов, LIMIT прекращает выдачу после нужного числа результатов, но не отменяет уже проделанную работу. В slot-based execution, или SBE, отдельные имена/вложенность отличаются: смысл работы не надо выводить из одного названия верхней стадии.

Индекс — поддерживаемая сервером упорядоченная структура ключей и ссылок на документы. Для запроса по tenant,state и сортировки createdAt DESC,_id ASC создаём {tenant:1,state:1,createdAt:-1,_id:1}. Первые два поля равны константам: план ограничивает узкий непрерывный диапазон их сочетания; внутри этого диапазона ключи уже имеют нужный порядок. Index bounds — границы диапазонов обхода. Равенство tenant даёт точку, а отсутствие ограничения по первому полю может заставить прочитать гораздо больше ключей. Это причина важности порядка compound index, а не мнемоническое «индексируйте каждое поле».

Индекс не обязательно устраняет FETCH: сервис запрашивает title и version, которых в ключе нет. Covered query возвращает только данные из индекса и может показать docsExamined=0, но добавление большого title в индекс увеличит размер и write cost. Узкий индекс и 20 FETCH могут быть лучшим договором. Обратный обход переворачивает весь порядок; произвольное смешение направлений полей не всегда подходит. Префиксы и направления сверяют по правилам compound indexes.

Измерение до и после на том же состоянии

После seed, но до migrate, Bash/cwd тома: ACTION=explain mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js. Скрипт исполняет read query с explain("executionStats"): это настоящий запуск плана без изменения jobs. Сохраните nReturned, totalKeysExamined, totalDocsExamined и winningPlan. Затем выполните migrate из главы сервиса и точно тот же explain. Не добавляйте новые документы между двумя пробами. При отказе первой пробы не создавайте индекс «на удачу»; сначала найдите причину.

На авторском наборе 20 000 документов первый план изучал 20 000 документов и сортировал кандидатов, после индекса — 20 ключей и 20 документов для 20 результатов. Это измерение объёма логической работы, не универсальное ускорение latency в тысячу раз. executionTimeMillis округлено, зависит от прогрева и может быть 0. Explain не является репрезентативным p99 всего приложения и имеет особое отношение к plan cache: он не заменяет повторные обычные запросы.

От сохранённого explain к порядку конкретных ключей

Для этого разбора jobs ещё не закрывались: после seed и migrate все 20 000 заданий open, по 200 на tenant. В исходнике номер i задаёт tenant=i%100, строковый ID seed-%06d и дату 1700000000+i секунд UTC. Поэтому tenant-01 соответствует i=1,101,…,19901. Сохранённый explain 1 ноября содержит точечные bounds tenant=["tenant-01","tenant-01"], state=["open","open"], полный createdAt=[MaxKey,MinKey] и _id=[MinKey,MaxKey]. Равенства двух первых полей позволяют начать с нужной группы; LIMIT обрывает её после 20 результатов, хотя подходящих ключей 200.

Это модель порядка, не новый запуск explain с limit=5 и не измерение latency. Уменьшение limit без хорошего пути доступа само по себе не отменило бы COLLSCAN.

Массив, уникальность, частичность и время жизни

Multikey index возникает, когда индексируемое поле содержит массив: один документ создаёт несколько ключей. Это помогает поиску элементов, но увеличивает write amplification — число дополнительных операций на каждую прикладную запись. Например, индекс {state:1,tags:1} для state=open и tags=["red","urgent"] создаёт ключи (open,red) и (open,urgent) с одной ссылкой на документ. Compound multikey не допускает два независимых массива tags и parts в одном документе, если оба их пути включены в тот же индекс: это не декартово произведение всех пар. Неиндексируемый массив parts этому индексу не мешает. Условия через $elemMatch меняют и смысл совпадения, и допустимое объединение границ. Для a=[1,8] запрос a>5 и a<3 подходит разными элементами; пересечение этих двух границ было бы пусто и потеряло бы правильный результат. С $elemMatch требуется один элемент, и такой документ уже не подходит. Выбор одной границы без $elemMatch не обещан заранее; см. multikey bounds 8.0.

Unique index запрещает повтор ключа между документами. Обычный unique по необязательному email может отказать из-за нескольких missing/null; partial unique с фильтром {email:{$type:"string"}} охватывает только строки. Он не проверяет каждую перестановку/дубликат элемента внутри одного массива как отдельную сущность. Построение unique на уже конфликтующих данных завершится ошибкой; сначала найдите и согласованно разберите конфликты. Ограничения объясняет unique reference.

Partial index содержит только документы, удовлетворяющие фильтру. Планировщик должен доказать, что запрос не потеряет результаты, поэтому запрос без нужного ограничения может его не использовать. Это меньше места и работы обновления, но дополнительное условие доступа; см. partial index semantics. TTL — time to live: специальный single-field индекс по дате, по которому фоновый механизм удаляет просроченные документы. Это асинхронная уборка, не точный таймер запрета доступа: приложение само проверяет expiresAt. Резкое включение TTL на большом прошлом наборе создаст поток удалений, oplog и IO; предварительная уборка порциями снижает пик. Наш jobs не имеет TTL: задания должны пережить учебный день; TTL reference задаёт ограничения.

Каждый дополнительный индекс требует памяти, места и изменения ключей при записи. Сравнивайте размер индексов, latency записи, cache misses и чтение до/после; скрытый индекс исключается из выбора плана, но продолжает обслуживаться при записи. Удаление индекса экономит обслуживание, однако обратное построение имеет цену и окно нагрузки. Автоматического drop/reset в лабораториях нет.

Стадия меняет поток

Aggregation pipeline — последовательность стадий обработки документов. Стадия получает поток и выдаёт следующий; результат не записывается обратно, пока явно не выбрана записывающая стадия. $match фильтрует, $project формирует поля, $unwind разворачивает элементы массива в отдельные строки потока, $group накапливает значения по ключу, $sort упорядочивает. Один входной документ после unwind может породить сотни выходных; цена pipeline определяется промежуточными объёмами, а не только размером итоговой таблицы.

В упражнении выбираем одного tenant, группируем по state и считаем jobs через {$sum:1}. После group документ уже имеет _id, равный состоянию, и jobs, равный счётчику: исходных title/createdAt в нём нет. Поздняя сортировка по createdAt потому бессмысленна. Для суммы копеек агрегируют int64-поле amountMinor, а не преобразуют строки на каждом запросе. Неодинаковые типы и missing меняют результаты выражений; перед расчётом проверяйте распределение типов.

Чтение через индекс и блокирующая работа

Ранний match с полями индекса может сократить поток до group. Сортировка иногда обслуживается индексом, если предшествующие стадии и порядок позволяют. Оптимизатор способен перенести часть match перед project, но это не обещание, что любой порядок стадий одинаков. Group и sort могут требовать удерживать состояние, а большой $lookup — обращаться к другой коллекции. Lookup означает соединение с foreign collection по условиям, а не ссылочную целостность. Индекс на внешнем ключе помогает lookup, но поток из миллионов повторяющихся запросов всё равно дорог.

Промежуточное использование памяти может привести к spill — выгрузке рабочего состояния во временные файлы, если операция и настройки разрешают. allowDiskUse не превращает диск в бесплатную RAM и не отменяет остальные ограничения; время IO и место становятся частью цены. Итоговый BSON-документ по-прежнему не должен превышать 16 MiB. Ограничения и варианты стадий сверяют с pipeline limits; для конкретного плана используйте aggregate explain. Это особенно важно перед $facet и группировкой неограниченных массивов.

Пример и отличие materialized result

В принятый стенд уже загружены seed-данные. В Bash, cwd тома: ACTION=aggregate mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js. Скрипт ставит maxTimeMS=3000, ожидает код 0 и одну группу open=200 до транзакции, две группы open=199/closed=1 после неё. Изменение результата объясняется закрытием seed-000001, а не случайной потерей записи. При timeout исходный jobs не изменён этим pipeline; причину исследуют через план и нагрузку.

$merge и $out сохраняют результат в коллекцию и требуют отдельного договора об именах, ключах и доступе. Они не являются частью выполненного read-only упражнения. Для витрины со счётчиками решите, допустимо ли отставание и как опознать поколение расчёта. Инкрементальный счётчик «openJobs» без транзакции между изменением задания и счётчиком может разойтись при аварии. Полное пересчитывание дешевле логики восстановления только на небольшом наборе: измеряйте объём и окно обновления.

Контрольный вопрос: если добавить unwind events перед group state, будет ли $sum:1 считать задания? Уже нет — он посчитает элементы развёрнутого потока. Сначала восстановите уникальность задания или измените постановку метрики. Ошибку единицы измерения индекс не исправляет.

Read concern, write concern и причинный порядокКуда читать, что видно и какого подтверждения ждать — три независимых решения · 683 словСодержание главы

Сессия и причинная зависимость

Три ручки одного запроса

Read preference — предпочтение выбора роли узла для чтения: primary, secondary, primaryPreferred, secondaryPreferred или nearest с дополнительными условиями. Оно отвечает на вопрос «с какого узла», а не «насколько свежо». Secondary может отставать даже при малом сетевом round trip; nearest выбирает допустимый близкий узел, не самый новый документ.

Read concern — требование к видимости читаемых данных. local допускает локально видимые изменения, которые при смене primary могут исчезнуть. majority возвращает данные, прошедшие majority commit, но не обещает самый последний результат всех клиентов. snapshot даёт согласованный снимок в поддержанных операциях; linearizable для подходящих чтений на primary обеспечивает более сильное согласование с успешными предшествующими majority-записями, требуя дополнительной координации и ограничений. Слово «consistent» без выбранного concern и порядка операций недостаточно.

Write concern — требование к подтверждению записи. w:0 не ждёт ответа о принятии, w:1 ждёт primary, число больше 1 — нужное число data-bearing участников, w:"majority" — вычисленное большинство голосующих участников с данными. j:true требует journal по правилам concern. Успешная операция и удовлетворённый concern — разные части ответа. В 8.0 majority подтверждает устойчивую запись соответствующих oplog на нужных участниках; secondary ещё может не применить её к своей коллекции. Чтение на secondary поэтому может ждать нужной causal отметки. Условия и исключения — в write concern reference.

Для обычной конфигурации writeMajorityCount вычисляется как min(floor(allVotingMembers/2)+1, dataBearingVotingMembers); election quorum остаётся floor(allVotingMembers/2)+1. Арбитр (arbiter) — голосующий участник без прикладной копии данных. PSS: три голоса, три копии, оба порога 2. PSA: три голоса, две копии, оба порога 2, но голос arbiter не подтверждает данные, поэтому явный majority требует P и S. PSSS+A: пять голосов, четыре копии, оба порога 3. Буква P означает primary, S secondary, A arbiter; голос и копия — разные ресурсы. В PSA implicit default при отсутствии явного глобального значения может стать w:1: исключение defaults не меняет смысл явно заданного w:"majority".

Defaults и ожидание при отказе

В MongoDB 8.0 implicit default write concern — majority у большинства конфигураций, но наличие arbiter при определённом числе голосующих data-bearing узлов даёт исключение w:1. Arbiter — участник голосования без копии прикладных данных; он не может подтвердить запись данных. Явно заданный global default и параметры операции также влияют на итог. Не переносите наблюдение одного узла на все topology. Проверяйте фактический default и конфигурацию, особенно при добавлении arbiter; формула дана в MongoDB defaults. В нашем Go-коде majority и Journal=true заданы явно.

writeConcernMajorityJournalDefault определяет, подразумевает ли majority ожидание journal: у обычного WiredTiger-набора default true. Изменение этого параметра меняет договор durability, а не скорость «без последствий». j:true в одиночку не предотвращает rollback расходящейся истории. Не путайте majority voting quorum выборов и условие подтверждения записи: первые считают голоса, второе требует участников с данными.

wtimeout — предел ожидания выполнения concern после успешного изменения на primary, в миллисекундах; он не откатывает сделанное изменение. Клиентский timeout может истечь ещё раньше и оставить исход неизвестным. Например, запись принята primary, второй data-bearing узел недоступен, concern не достигнут за 3000 ms. Клиент получает ошибку, но документ может позже реплицироваться или оказаться rollback. Удаление документа «для компенсации ошибки» способно удалить успешно принятый заказ. Сначала сверяют прикладной ID и разрешают неопределённость.

Сессия и причинная зависимость

Логическая сессия — идентификатор связанной последовательности клиентских операций, обычно обозначаемый lsid. Он не равен TCP-соединению: pool может использовать другие сокеты, сохраняя логическую связь. Causal consistency — причинная согласованность: если приложение знает, что чтение зависит от своей записи, оно передаёт временную отметку зависимости и требует не читать состояние раньше неё. В causal session с majority reads/writes поддерживаются read-your-writes, монотонные чтения/записи и writes-follow-reads в заявленных условиях. Сессии нельзя одновременно использовать из нескольких goroutine; между клиентами причинный контекст нужно передавать осознанно.

Majority concern без causal связи сам по себе не означает, что произвольное чтение на отстающей secondary немедленно увидит именно вашу запись. Наш основной HTTP-путь читает primary с majority и не объявляет распределённый causal workflow между независимыми процессами. Границы объясняет модель видимости и причинности. Для checkout после записи tenant настройка предпочтения secondary ради разгрузки требует отдельной политики ожидания и допустимого отставания, а не смены одного слова URI.

Одноузловой набор удовлетворяет majority одним участником. На нём нельзя опытно доказать переживание потери primary или работу арбитра: соответствующие ветки схемы — объяснительная модель. Retryable writes — протокол повторения определённых подтверждаемых записей драйвером после подходящего сетевого отказа или потери primary. Транзакция — последовательность операций, чьи изменения становятся видимыми вместе при commit или отбрасываются при abort. Наш пример закрывает seed-000001 и создаёт ledger с ID transaction-example-1. Ledger — прикладной журнал завершённых действий, обычная коллекция, не journal WiredTiger и не oplog. Без транзакции авария между update и insert оставит несогласованность: закрытое задание без записи действия либо действие без перехода.

В -mode=transaction создаётся Session, затем WithTransaction получает callback. Все MongoDB-вызовы внутри используют переданный sc context.Context; использование внешнего ctx случайно вынесет операцию за транзакцию. Границы изоляции и цена

Snapshot даёт согласованное чтение выбранного момента, но не автоматически serializable-поведение для всех бизнес-инвариантов. Если два врача в разных документах читают «дежурит двое» и каждый снимает только себя, отсутствие конфликта одной записи может нарушить общий инвариант. Можно хранить общий счётчик/версию в одном совместно обновляемом документе, заставив конкурирующие решения пересечься, или изменить модель. Unique index защищает уникальность конкретного ключа; транзакция не заменяет правильное ограничение.

Держать транзакцию открытой во время запроса пользователя или сетевого вызова дорого: она удерживает snapshot/history, может ждать locks, конфликтовать и превышать лимиты времени. Большой backfill обычно выполняют ограниченными идемпотентными порциями, а не одной транзакцией на всю коллекцию. Между shards commit требует распределённого согласования, увеличивая цену и поверхности отказа. Outside local reads при distributed commit не обязаны видеть все shards в один момент: для собственного согласованного чтения выбирают подходящий concern.

Практика выполняется после seed и migrate: Bash/cwd тома, переменные клиента из главы сервиса: "$LAB/bin/job-service" -mode=transaction, затем тот же вызов ещё раз. Так обнаруживается нарушенная предпосылка, а не маскируется тест.

Rollback и судьба принятого w:1

Представим A primary, B/C secondary. A принял X с w:1, но X ещё не достиг B/C. Связь разделилась, B получил голос C и стал primary новой эпохи, записал Y. Когда A возвращается, группа не может просто объединить X и Y: это расходящиеся истории. A находит общую точку, откатывает свою неподтверждённую ветку, затем догоняет победившую. Клиент уже мог получить «успех X». Локальный j:true сохранил X на диске A, но не сделал его частью принятой большинством истории.

Rollback files могут помочь расследованию, но не являются полным backup: для удаления/collection drop материал не сохраняется таким же образом, а отдельные w:1 случаи имеют ограничения. Не копируйте removed BSON обратно автоматически: это может воскресить отменённые бизнес-операции или конфликтующие ID. Сначала сопоставляют прикладные запросы, подтверждения и внешние эффекты; см. границы rollback data.

Для отдельного личного опыта нужны три dataPath, три loopback-порта, собственный ключ, конфигурация из трёх членов, последовательная проверка secondary/primary и запись с выбранным concern до/во время/после остановки одного своего процесса. В этом томе такой набор не запускался.

Три процесса на одном хосте показывают голосование и отказ процесса, но не защищают от выключения хоста, потери его диска, общей VM или ошибочного удаления каталога. Арбитр не заменяет третью копию данных. В production выбирают независимые failure domains — границы общего отказа, проверяют вместимость оставшихся участников и допустимость записи при их потере. Репликация переносит ошибочное удаление столь же старательно, как полезное изменение: нужна независимая резервная копия.

Sharding — разделение коллекции на части, хранящиеся на разных группах серверов. Shard — одна такая часть инфраструктуры, обычно replica set, а не отдельная «таблица». Это логические границы ключей, не фиксированный диск-файл. Mongos — маршрутизатор, который по ключу и метаданным направляет команды; config server replica set хранит управляющую информацию. Запрос с полным полезным ключом часто адресный; без него нужен scatter-gather — рассылка нескольким shards и сбор результатов. Выбор ключа для нашей мастерской

Шардирование только по tenant локализует запросы одного клиента, но один огромный tenant становится горячей неделимой нагрузкой. Монотонный createdAt направляет новые записи к одному краю range-key. Hash — вычисленное распределяющее значение — помогает равномерным insert, но запрос по диапазону исходного времени уже не соответствует смежному диапазону hash. Compound key tenant+суффикс может делить большого клиента, сохраняя часть адресности; конкретный суффикс выбирают по распределению нагрузки и типичным запросам. Высокая cardinality означает много различных значений, но сама по себе не обещает равномерную нагрузку: 90% запросов могут обращаться к одному значению.

Прежде чем выбирать, измерьте распределение объёма и запросов по tenant, частоту изменений ключа, долю запросов с префиксом и цену межшардовой транзакции. Наш dataset из 100 равных tenant специально прост и не доказывает пригодность ключа для настоящей мастерской. Официальные ограничения ключей и различие refine/reshard — в shard key reference.

Маршрут на одном объявленном разделении ключей

Возьмём только объяснительную карту: ключ {tenant:1,_id:1}, простое двоичное сравнение строк, tenant-01 разделён по _id="seed-010000". Условный shard A владеет частью tenant-01 с меньшим ID, B — с этим и большими ID; другие tenant могут находиться также на C. Оба интервала вместе покрывают tenant-01, их граница не включена в A и включена в B. Это выбранные метаданные модели, не результат включения sharding в нашем одноузловом стенде.

 | Предикат чтения | Маршрут по карте | Причина

 | tenant-01, _id=seed-000001 | A | Полный ключ ниже границы.

 | tenant-01, _id=seed-019901 | B | Полный ключ выше границы.

 | tenant-01, state=open | A и B | Префикс ограничил tenant, но не суффикс ключа.

 | Только state=open | Все shards коллекции, включая C | По этому условию карта ключей не исключает ни один shard.

По формуле seed у tenant-01 ровно 100 ID ниже этой границы и 100 выше. Полный ключ поэтому может направить один запрос в одну группу, а префикс — лишь сузить множество групп. Получив ответ каждого адресата, mongos объединяет выдачу и применяет общий limit; локальный индекс нужен каждому shard отдельно. Измените только границу на seed-015000 и посчитайте размещение: 150/50 записей. Эта арифметика не предсказывает долю нагрузки. Официальный механизм выбора адресатов описан в Routing with mongos 8.0, Targeted/Broadcast Operations.

Балансировка и изменение размещения

Balancer — управляющая работа, переносящая диапазоны между shards согласно политике и распределению. Миграция диапазона копирует данные, догоняет текущие изменения, согласует смену владельца и очищает старые копии. В момент переноса появляются IO, сеть, рабочее место и короткие критические участки. Добавление shard не переносит мгновенно все старые данные и не исправляет горячий неделимый ключ. Zones — правила соответствия диапазонов разрешённым группам shards; они добавляют требования, которые могут мешать простой равномерности.

Refine shard key добавляет поля к существующему ключу, не является произвольным перераспределением по новому началу ключа. Resharding меняет ключ и требует построения нового размещения с запасом ресурса, временем выполнения, проверкой ошибок и cutover. Не обещайте «бесплатную смену»: большие коллекции и продолжающиеся записи создают реальные очереди и потребность в диске. Наблюдайте прогресс, lag, ошибку приложения и план остановки. Процедура зависит от версии/редакции и не исполнялась в этом стенде.

Уникальность и эксплуатационная цена

Уникальный _id вне shard key не всегда означает глобальную уникальность между shards: когда _id не является shard key, серверная уникальность _id может обеспечиваться только внутри shard. Для unique indexes в sharded collections нужны условия к префиксу shard key. Прикладной request ID нашего сервиса поэтому нельзя просто объявить глобальным дедупликатором после любого reshard: нужно выбрать размещение/ограничение или отдельный договор маршрутизации запросов. Проверка uniqueness — часть проекта ключа, а не поздний индекс.

Каждый shard добавляет replica set, monitoring, backup, upgrade и отказные сценарии; config servers и mongos тоже требуют управления. На одном небольшом host это чаще усложнение без выигрыша. Сначала исправляют неизбирательный запрос, индекс, неограниченный массив, pool pressure и модель данных, затем измеряют предел одного replica set. В этой главе нет команд запуска полного sharded cluster и нет заявления о его приёмке. Схема показывает последовательность адресного и рассеянного чтения, а для реального переноса данных нужен отдельный испытанный runbook.

set -euo pipefail
test ! -e "$LAB/service"

GOTOOLCHAIN=local запрещает фоновое получение другого Go. Последний вызов не подключается к серверу, печатает ровно 22 bytes: 16000000106e002a00000002730003000000d18f0000. Выпуск 1, затем совместимая миграция

В том же Bash вызовите seed. Он создаёт 20 000 job с заранее определёнными ID и датами, по 200 на каждого tenant. Используется upsert с $setOnInsert, поэтому повтор должен вывести new=0 и сохранить даты/состояния. Значение n — размер ожидаемого диапазона, не команда привести коллекцию к этому числу: дополнительные HTTP-задания не удаляются.

set -euo pipefail

job-service -mode=check
ACTION=explain mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js

ACTION=explain mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js

Первая миграция на чистом seed: matched=20000 modified=20000 и индекс tenant_state_recent; повтор: matched=0 modified=0. Мигрированный документ версии 2 получает priority=0; договор новой формы также допускает отсутствие priority как значение 0, поэтому новый HTTP-документ может не содержать физического поля. Старый Go-читатель игнорирует неизвестное поле, новый понимает отсутствие priority как 0. В этом учебном main.go поле priority не возвращается HTTP: оно показывает безопасное добавление серверного состояния без изменения старого ответа. SchemaVersion сохраняется явно. Индекс строится после backfill; если его создание отказало, уже преобразованные документы не откатываются. Повтор миграции обработает остаток и снова проверит индекс. Удаление priority и откат старого бинарника не возвращают историю значений.

Для большого production-набора UpdateMany этого урока слишком груб: разделите диапазоны ID на batches, сохраните checkpoint выполнения вне памяти, замеряйте latency и oplog и проверяйте остаток по schemaVersion. Добавление обязательного validator выполняют после совместимого выпуска и backfill, не до. Пока серверный validator здесь не включён, прямой mongosh может обойти HTTP-проверку формы; readWrite-пользователь приложения — учебное упрощение полномочий, не защита от злонамеренного изменения любых jobs.

HTTP: устойчивый ID и условный переход

HTTP — протокол запросов и ответов приложения. В первом терминале с теми же переменными и cwd запустите job-service -mode=serve: он остаётся в foreground, проверяет primary до listener и слушает только 127.0.0.1:18089. Не закрывайте окно, пока нужны HTTP-запросы. Во втором Bash, cwd произвольный, Python уже доступен; блок ниже обращается только к этому адресу и проверяет статус до следующего действия.

set -euo pipefail
python3 - <<'PY'
import json, urllib.request, urllib.error
base = 'http://127.0.0.1:18089'
def post(path, body):
    r = urllib.request.Request(base+path, data=json.dumps(body).encode(),
          headers={'Content-Type':'application/json'}, method='POST')
    try:
        with urllib.request.urlopen(r, timeout=5) as x:
            return x.status, json.loads(x.read())
    except urllib.error.HTTPError as x:
        return x.code, json.loads(x.read())
payload = {'id':'http-example-1','tenant':'handmade','title':'Проверить часы'}
a = post('/jobs', payload); assert a[0] == 201, a
b = post('/jobs', payload); assert b[0] == 200 and a[1] == b[1], b
c = post('/jobs', dict(payload, title='Другое')); assert c[0] == 409, c
assert post('/jobs/http-example-1/close', {}) == (200, {'modified':1})
assert post('/jobs/http-example-1/close', {}) == (200, {'modified':0})
print('201 → 200, conflict 409, close 1 → 0')
PY

Это исходное состояние нового ID: если он уже существует, первый assert остановит последовательность; исследуйте запись или выберите новый собственный ID, не стирайте данные. Дата первого ответа обрезается до миллисекунд перед BSON-сохранением, чтобы повтор возвращал ту же точность. JSON — текстовый формат именованных значений во входе/ответе HTTP. Обработчик принимает ровно один JSON-объект и дочитывает тело до EOF, конца входного потока. Второй объект, мусор и whitespace-хвост сверх 4096 байт дают 400 до InsertOne. Поля ID/tenant/title ограничены 80/80/200 байтами UTF-8, поэтому 100 букв «Я» занимают 200 байт. Штатный Go-пакет httptest проверяет reader в памяти без listener и БД в 13 случаях; go test перед сборкой требует код 0. Неизвестные JSON-поля также отвергаются; полноценная многоарендная авторизация HTTP в урок не входит. Поле tenant — критерий запроса, не удостоверенная личность пользователя.

Историческая native-проверка 1 ноября конкурентного договора использовала Go-исходник SHA-256 712ee2ec…59fc5, до уточнений JSON-reader и завершения HTTP 2 ноября, с детектором гонок -race и 16 клиентов, стартующих через общий барьер. Для одного нового ID и одинакового payload получены один 201 и пятнадцать 200, одна MongoDB-запись с version=1. В другой группе восемь запросов payload A и восемь payload B конкурировали за один новый ID: один 201, семь 200 победившего payload и восемь 409 другого; сохранены tenant/title/date/schemaVersion победителя. При 16 параллельных close все ответы 200, modified=1 ровно у одного, у остальных 0; состояние closed/version2, остальные поля неизменны. BSON-тип версии остался int64 (Long). Процесс штатно завершился с кодом 0, race diagnostic не обнаружен; stderr сохранён только приватно. После правок новые 13 JSON cases и один shutdown case пройдены отдельно; полный старый seed/restore и 16-клиентный опыт не объявляются повторёнными на новом SHA. MongoDB-операции создания/чтения/close сохранены. Это проверка конкретной конкуренции без искусственной потери ответа; она не доказывает отсутствие всех гонок или exactly-once при любом отказе.

Какую точку хотим вернуть

Backup — независимая сохраняемая копия состояния. RPO — допустимый возраст потерянных данных, RTO — допустимое время восстановления до принятого сервиса. Сначала определите точку и список объектов: jobs, ledger, индексы, validators, пользователи/роли, ключи, версии бинарников и конфигурация. Обычный logical dump выбранной БД не копирует все секреты ОС и не делает автоматически полноценную копию прав сервера. Шифрование резервов и хранение ключей отдельно — часть вашей политики; наш архив содержит только синтетические данные.

Logical dump читает документы и метаданные через MongoDB API. Snapshot — согласованный снимок физических томов по правилам storage/filesystem/платформы; live-копирование отдельных .wt файлов не является snapshot. PIT, point in time restore, требует базовой копии и непрерывной проверенной истории до выбранного времени. Один файл dump с --oplog охватывает лишь определённое окно операции, а не бесконечный PIT-сервис. Управляемый Atlas backup/PIT — отдельная availability/edition; локальные Tools не дают его автоматически.

Проверенный небольшой dump на остановленной прикладной записи

Предпосылки: main.go остановлен Ctrl+C, shell не меняет workshop, репликация/миграции не выполняют прикладных изменений; mongod продолжает работать. Так мы получаем согласованное по приложению неподвижное состояние. Bash/cwd тома, Tools уже установлены. Сохраните число jobs и индексы, выберите новое имя файла. Tools читает пароль из private/tools.yml (0600), а не argv. При любом ненулевом коде dump файл считается непригодным до расследования; restore не запускают.

set -euo pipefail
ACTION=backup-count mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js

mongodump --config "$LAB/private/tools.yml" --db workshop --archive="$LAB/backups/workshop-1.archive.gz" --gzip

--db ограничивает namespace областью workshop; --archive пишет единый контейнер dump, --gzip сжимает. Это бинарный архив Tools, не tar и не JSON. В авторском опыте jobs=20001, ledger=1, индекс tenant_state_recent присутствовал. Копирование файла на другой независимый носитель ещё требуется для защиты от потери исходного диска; данные в backups/ того же host не получают независимость одним названием.

Новая цель вместо перезаписи живой базы

Далее один новый каталог и другой loopback-порт. Никаких --drop или переиспользования прежнего dataPath. Restore-instance — временный standalone только для проверки, без auth и без сети за пределами loopback; полноценное production-восстановление требует вернуть доступ и topology до выдачи трафика. Если каталог restore-1 или порт заняты, блок останавливается. EXPECTED_JOBS задайте по сохранённому backup-count, не подгоняйте под обнаруженный результат.

set -euo pipefail
test ! -e "$LAB/restore-1"
mkdir -p "$LAB/restore-1/data"
mongod --dbpath "$LAB/restore-1/data" --port 27118 --bind_ip 127.0.0.1 --nounixsocket --wiredTigerCacheSizeGB 0.25 --logpath "$LAB/restore-1/mongod.log" --pidfilepath "$LAB/restore-1/mongod.pid" --fork
mongorestore --uri 'mongodb://127.0.0.1:27118/?directConnection=true' --archive="$LAB/backups/workshop-1.archive.gz" --gzip --stopOnError
EXPECTED_JOBS=20001 mongosh 'mongodb://127.0.0.1:27118/workshop?directConnection=true' --quiet --norc --file labs/restore-accept.js
mongod --shutdown --dbpath "$LAB/restore-1/data"

--stopOnError прекращает дальнейший импорт при ошибке, но уже импортированные документы не отменяются: цель частична до расследования. Скрипт приёмки сверяет count, наличие seed-000001, BSON Date и индекс. Полный native test дополнительно сравнивает SHA-256 всех jobs в каноническом Extended JSON, упорядоченных по _id, а также ledger и состояние после restart. Только равенство количества было бы недостаточно. Архив и восстановленная data остаются; выключение не удаляет их.

Живая нагрузка, oplog и ограничения Tools

При продолжающихся изменениях dump без подходящей согласованности может собрать разные коллекции из разных моментов. Full replica set dump с --oplog и соответствующим mongorestore --oplogReplay имеет строгие ограничения: нельзя просто добавить --oplog к scoped --db dump или произвольному шардированному экспорту и объявить консистентность. Окно oplog должно покрывать всю операцию, DDL и namespaces имеют ограничения; для sharded backup нужно согласование всех shards и config metadata. Здесь живой full oplog/PIT/snapshot не исполнялись. Источник и цель должны иметь совместимые server/FCV, а версии dump/restore лучше совпадать; Tools behavior объясняет пределы переносимости.

Бинарник и FCV меняются отдельно

FCV — featureCompatibilityVersion: сохранённый сервером режим совместимости форматов и возможностей. Замена executable и повышение FCV — разные этапы обновления; прежний FCV не означает, что любой старый бинарник безопасно запустится на новом dataPath. Сначала проверяют поддержанный путь, совместимость драйверов и изменённые параметры, восстанавливают backup в репетиционное окружение, прогоняют запросы/миграции/отказ. Для replica set обновляют участников в установленном документацией порядке, проверяя health и достаточность копий, затем отдельным решением повышают FCV. Команда setFeatureCompatibilityVersion не должна быть случайным шагом «ускорить старт».

Для перехода на 8.0 официальная процедура требует предыдущую major ветку 7.0; перескакивать несколько major нельзя. Документация 8.0 также ограничивает binary downgrade и указывает необходимость support, поэтому этот том не обещает простой откат установкой старого tarball. Точная процедура — upgrade replica set to 8.0. Здесь проверен restart той же 8.0.34, а не upgrade между major.

Возврат восстановленного backup теряет записи после контрольной точки, если нет согласованного replay/прикладного восстановления. Старый Go binary не удаляет новые поля/индексы и не откатывает новые бизнес-действия. Перед переключением фиксируют последнюю принятую запись, способ остановки новых write, судьбу отложенных запросов и решение о постконтрольных данных. Restore, rollback репликации и rollback релиза — разные процессы.

Что измеряем и в каких единицах

Throughput — число законченных операций в секунду; latency — время одной операции. p50/p95/p99 — значения, ниже которых лежит соответствующая доля наблюдений, а не процент CPU. Укажите число samples, окно и способ расчёта квантиля. В main.go берётся отсортированный ряд микросекундных длительностей и нижний индекс (n−1)·q/100, вывод в ms. При 200 наблюдениях p99 описывает почти хвост двухсот измерений и не даёт достоверной модели редкого отказа раз в миллион.

Измерение сервиса -mode=measure включает выбор/ожидание драйвера, сервер, передачу и декодирование 20 документов; это не HTTP latency, потому что HTTP-слоя в этой команде нет. Запросы идут последовательно одним клиентом, concurrency=1. Max pool=12 не означает 12 одновременных запросов. Серверная executionTimeMillis из explain — другой интервал и более грубое округление. Оба числа нужны, но не взаимозаменяемы.

Последовательные 200 запросов не доказывают договор при конкуренции за один ID или версию. Такой договор отдельно проверен 16 одновременными HTTP-клиентами в главе сервиса; там изучается корректность записей/ответов, а не p99 под большой нагрузкой. Проход детектора гонок на этом наборе не является доказательством отсутствия всех возможных гонок.

Контролируемое сравнение на одинаковых документах

После migrate, до transaction и HTTP-записи, выполняйте в исходном Bash/cwd тома. Между пробами не меняйте jobs. Флаг -hint действует только в режиме measure: natural заставляет полный обход, имя индекса — выбранный индекс. Ошибка неизвестного индекса завершает программу ненулевым кодом и останавливает сравнение. Это диагностическое принуждение плана, не рекомендация закреплять hint в пользовательском запросе навсегда.

job-service -mode=measure -n=200 -hint=tenant_state_recent
ACTION=stats mongosh 'mongodb://127.0.0.1:27117/admin?directConnection=true' --quiet --norc --file labs/admin.js

Контрольный авторский опыт: Ubuntu 24.04 x86-64, Community 8.0.34, WT cache 0.25 GiB, 20 000 уже мигрированных jobs, tenant-01, state=open, sort createdAt DESC/_id ASC, limit20, локальный TCP без TLS, serial1, один процесс Go 1.27.3/driver2.9.2. До проб данные уже читались; холодный диск не моделировался. На одном и том же post-migration наборе в сохранённом повторе 1 ноября natural p50=6.773, p95=9.204, p99=10.080 ms; принудительный индекс p50=0.270, p95=0.463, p99=0.587 ms. Первый отдельный controlled опыт имел другие числа, приведённые в ПРОВЕРКИ.txt; серии не объединяются. Обе серии завершили 200 запросов, successfulCommands=201 включает стартовый ping.

Раннее before/after без hint дало p99 7.156 → 0.533 ms, но между пробами добавлялось поле priority и строился индекс. Поэтому для строгого сравнения плана выше сохранён отдельный опыт с одинаковыми документами. Explain показал docsExamined 20000→20, keysExamined 0→20 и возвращённые 20; это более прямое объяснение снижения работы. Числа не относятся к вашему диску, облаку, холодному cache, TLS, конкуренции или production p99. CPU quota/RAM bandwidth/IOPS этого общего авторского host не закреплялись, поэтому вывод — про конкретный путь доступа, а не сертифицированный benchmark аппаратуры.

Разделяйте очереди

Рост времени до команды при нормальном command duration указывает на selection, pool checkout, DNS/TLS/auth или сам клиент. Рост command duration вместе с docsExamined/returned может указывать на план; cache misses, dirty pressure и диск — на storage; apply/durable lag и majority wait — на репликацию. Не каждая медленная запись означает медленный индекс: majority может ждать другой узел. Нужна временная корреляция, а не случайный скриншот после нагрузки.

Наблюдайте число открытых/используемых соединений и их создание, время checkout, частоту server selection failure, процент ошибок/timeout, pool cleared events. На сервере сопоставляйте serverStatus, slow-query log, explain и фактический IO/CPU/RSS. Profiler — механизм сохранения диагностических сведений об операциях в БД — сам имеет цену и может записывать значения запросов; включайте ограниченно, с явными правами и сроком хранения. В этом стенде profiler и нагрузка на рабочую сеть не включались.

Цена изменения и следующий опыт

Чтобы измерить индексную цену записи, нужны две новые собственные коллекции с одинаковым seed, одна с _id, другая с тем же дополнительным индексом; одинаковые batches/concern/concurrency, отдельные прогревы и несколько чередующихся окон. Сравнивайте accepted writes/s, latency, размер индекса, journal/oplog bytes и CPU/IO. Удалять индекс живого jobs ради измерения не требуется. Такой опыт здесь описан, но не выдаётся за выполненный.

При деградации сначала сохраните версию, URI без секрета, concern, форму запроса, план и окно времени; остановите новые изменяющие эксперименты. Уменьшение pool или объёма batch может вернуть предсказуемость, но требует повторного измерения под исходной нагрузкой. Универсального «нормального p99 MongoDB» нет: целевое время задаёт пользовательский процесс, а допустимая цена — ресурсы и гарантии данных.

Набор переиспользуемых соединений одного Client к конкретному серверу; мониторинговые сокеты считаются отдельно.

SCRAM

Механизм удостоверения знания пароля с проверяемым обменом; сам не шифрует весь прикладной транспорт.

TLS

Защита транспорта с проверкой личности по сертификатам и доверию CA; не выдаёт права доступа к коллекции.

SAN

Список имён/IP сертификата, с которыми клиент сравнивает адрес сервера.

OP_MSG

Формат современных команд и ответов MongoDB с заголовком, флагами и секциями BSON.

WiredTiger

Движок хранения с cache, версиями, journal и checkpoint; не название сетевого протокола.

MVCC

Хранение нескольких версий для чтения допустимого снимка при конкурирующих изменениях.

Dirty page

Страница, содержимое которой отличается от её дисковой копии; изменения уже могут быть защищены journal. Отдельная метрика от размера всего cache.

Eviction

Освобождение места cache с необходимой обработкой страниц и версий; при давлении может затронуть рабочие потоки.

Journal WiredTiger

Локальный write-ahead log для восстановления; не текстовый mongod.log и не oplog репликации.

Checkpoint WiredTiger

Согласованная сохранённая точка файлов данных, от которой можно начать journal recovery.

Индекс MongoDB

Поддерживаемая сервером структура ключей и ссылок, ускоряющая определённый доступ за цену обслуживания при записи.

Compound index

Упорядоченный индекс по нескольким полям; порядок и префикс определяют полезные границы обхода.

Multikey index

Индекс с несколькими ключами для массива в документе; имеет ограничения для составных массивных полей.

Partial index

Индекс только документов, удовлетворяющих фильтру; запрос должен гарантировать полноту использования такого поднабора.

TTL index

Single-field индекс для асинхронного удаления просроченных данных; не точный deadline доступа.

IXSCAN / FETCH / COLLSCAN

Обход ключей, получение документов и полный просмотр коллекции; работа объясняется метриками плана.

Aggregation pipeline

Последовательность стадий преобразования потока документов; group/unwind меняют смысл единицы счёта.

Spill

Выгрузка промежуточного состояния операции на диск, если поддержана и разрешена; имеет цену IO и места.

Read preference

Правило выбора роли/узла чтения; не гарантия свежести его данных.

Read concern

Требование к видимости читаемых данных, например local, majority или snapshot.

Write concern

Требование подтверждения записи участниками и journal; ошибка ожидания не отменяет уже сделанное изменение.

Causal consistency

Согласование порядка зависимых операций в поддержанных session/concern условиях; не глобальная последовательность всех клиентов.

Session MongoDB

Логическая связь операций с lsid, независимая от конкретного TCP-соединения; используется последовательно.

Retryable writes

Протокол распознаваемого сервером повтора поддержанных подтверждаемых операций драйвером; не повтор произвольного HTTP с новым ID.

Транзакция MongoDB

Совместная фиксация/отмена изменений нескольких документов в рамках заданных concerns и ограничений.

Replica set

Группа mongod с согласованной ролью primary и общей историей; один участник не защищает от потери host.

Primary / secondary

Роль принимающего обычные записи лидера и роль копирующего/применяющего историю участника.

Arbiter

Голосующий участник без прикладной копии данных; не подтверждает durable data write.

Term MongoDB

Номер эпохи выборов, различающий старое и новое лидерство.

Oplog

Скользящий журнал операций replica set в local.oplog.rs; окно зависит от объёма и скорости изменений.

Majority commit point

Граница истории, принятая большинством по протоколу; не утверждение, что все secondary уже применили её.

Rollback репликации

Отмена расходящейся ветки бывшего primary при присоединении к принятой истории; не restore backup и не возврат версии приложения.

Shard key

Индексируемые поля, определяющие размещение документов по диапазонам shards.

Chunk

Логический диапазон shard key в управляющих метаданных, не отдельный фиксированный disk-файл.

Balancer MongoDB

Управляющая работа переноса диапазонов в соответствии с распределением и политиками.

Resharding

Изменение shard key с построением нового размещения и согласованием перехода.

FCV

FeatureCompatibilityVersion: сохранённый режим совместимости возможностей/форматов; не версия драйвера и не универсальный разрешённый downgrade.

Restore / PIT

Восстановление сохранённой копии / восстановление к заданному моменту при наличии базы и непрерывной истории.

RPO / RTO

Допустимая потеря истории и допустимое время возврата принятой функции; подтверждаются восстановлением и измерением.

Native test

Настоящее исполнение конкретных бинарников; отличается от статической проверки, модели и неисполненного runbook.

RecordId MongoDB

Внутренняя ссылка индекса на запись storage engine; не адрес RAM и не BSON-поле _id.

MinKey / MaxKey

Крайние BSON-типы ниже/выше обычных значений; в indexBounds обозначают неограниченные концы диапазона.

History store WiredTiger

Файл WiredTigerHS.wt и механизм сохранения старых изменённых значений, нужных снимкам; не резервная копия.

OpTime MongoDB

Положение в истории replica set с BSON Timestamp ts и term t; durable/applied/committed отмечают разные стадии.

EOF JSON body

Конец потока после единственного JSON-объекта; проверяется отдельным чтением, чтобы не принять скрытый второй объект или длинный хвост.
