Один выпуск как нить всей книги

Разработчик отправил коммит. Через некоторое время GitLab показывает зелёный значок, а приложение отвечает пользователям. Между этими событиями нет одной волшебной операции. Сервер принял объекты Git и обновил ссылку, приложение проверило разрешения и разобрало описание CI, создало граф заданий, Runner получил подходящую работу, исполнитель подготовил окружение, оболочка запустила Go, а результаты пришлось сохранить и затем доставить. Каждый переход способен завершиться отдельно. Можно сохранить коммит без создания конвейера, создать конвейер без свободного исполнителя, собрать бинарник без его загрузки в хранилище и успешно завершить доставку без проверки работоспособности службы.

CI — continuous integration, непрерывная интеграция: изменения регулярно объединяются и проверяются автоматизированным набором действий. Pipeline, далее «конвейер», — отдельный запуск графа таких действий. Job, далее «задание», — единица работы в нём. Runner — программа, которая получает задания от GitLab и организует их исполнение. Executor, далее «исполнитель», — способ, которым Runner создаёт среду и запускает команды: непосредственно в оболочке, в контейнере либо в другом окружении. Эти слова нужны уже на первом экране; ниже каждое получает наблюдаемый механизм.

Сначала разбираем платформу, её данные, установку и доступ. Затем внутри тома идёт связная книга об исполнении CI: описание превращается в граф, граф — в назначенное задание, задание — в процессы и файлы. После этого собираем Go-приложение, сохраняем доказательства проверок и организуем выпуск. Эксплуатационная часть объясняет измерения, диагностику, резерв и обновление. Практикум связывает причины с наблюдениями на своём проекте, не требует учебных серверов сторонней организации.

Для механики объектов, индекса и слияния есть отдельный том Git. Компилятор и линковщик раскрыты в томе Go. Здесь важно то, как платформа управляет этими инструментами, кто выбирает их входы и кто получает результат. Jenkins остаётся самостоятельной системой с иной моделью управления; его том пригодится для сравнения конкретных решений, например агентского канала и сохранения состояния.

Что можно делать без развёрнутой платформы

Файлы практикума содержат оригинальный Go-проект, сценарии его локальной проверки и образец .gitlab-ci.yml. Локальные команды действительно проверяют Go-код и передачу одного и того же бинарника. Они не изображают GitLab: без сервера нельзя подтвердить создание настоящего конвейера, подбор Runner, правила доступа, загрузку артефактов или обработку отчёта интерфейсом. Для этих шагов даны отдельные критерии наблюдения на личном экземпляре.

На домашнем компьютере с 8–16 ГБ памяти не требуется одновременно держать GitLab, Jenkins, Kubernetes, базы и несколько сборочных машин. В первую очередь можно использовать один личный экземпляр GitLab и небольшой отдельный Runner, включая нужный профиль только для упражнения. Решение о совместном домашнем стенде рассматривается отдельно; книга не устанавливает службу при открытии страницы. Рабочий компьютер служит клиентом к тому же личному стенду, если такой доступ разрешён; флэшка с HTML не превращает Windows в сервер GitLab.

Почему GitLab не равен Git-серверу

Git умеет хранить объекты и ссылки, передавать их между репозиториями и проверять допустимость обновлений через серверные механизмы. У него нет встроенного понятия «обсуждение изменения номер 37», списка участников группы или интерфейса запуска тестов. GitLab добавляет прикладную модель вокруг репозиториев. Один проект содержит не только Git-историю: есть задачи, запросы на слияние, права, параметры CI, выпуски, пакеты и сведения о заданиях. Поэтому резервная копия каталога bare-репозитория сохраняет существенную часть исходников, но не весь проект.

Bare-репозиторий — хранилище Git без обычного рабочего дерева для редактирования файлов. GitLab хранит такие репозитории и обслуживает доступ к ним через Gitaly. Gitaly — отдельная служба Git-операций с программным интерфейсом: приложение просит получить файл, сравнить коммиты или обслужить передачу объектов. Файлы Git не становятся строками PostgreSQL от того, что сайт показывает их рядом с задачами. Совместное представление в браузере собирается из нескольких источников.

Путь обычной страницы

Браузер устанавливает HTTPS-соединение с внешним адресом. TLS завершает выбранный входной сервер: встроенный NGINX либо внешний обратный прокси. Обратный прокси принимает клиентский запрос и передаёт его внутренней службе. В типовой поставке дальше участвует Workhorse — компонент GitLab для обработки и передачи определённых HTTP-потоков, в том числе больших файлов; прикладную логику исполняет Rails-приложение в сервере Puma. Rails здесь — среда веб-приложения, Puma — процесс, который обслуживает его запросы. Это разные уровни исполнения.

Для страницы запроса на слияние приложению могут потребоваться пользователь и разрешения из PostgreSQL, сведения о репозитории через Gitaly и кэшированные данные из Redis. HTTP-ответ возвращается через входные компоненты к браузеру. Запись 502 Bad Gateway означает проблему на границе посредника и следующей службы, а не автоматически повреждение Git. Если сам прокси отвечает, порт доступен, но Puma ещё загружается, транспортная проверка порта даст слишком слабое свидетельство готовности.

Unix domain socket, локальный сокет Unix, позволяет процессам одной машины обмениваться данными через адрес в файловой системе. Он не требует IP-маршрута, но требует правильного пути, владельца и прав. В разнесённой установке вместо него могут использовать TCP. Смена локального сокета на TCP не убирает необходимость аутентификации и разграничения доступа между компонентами: меняется канал и набор возможных причин отказа.

Как отличается Git по SSH

При git fetch по SSH клиент подключается к SSH-службе GitLab. GitLab Shell связывает ключ клиента с учётной записью и проверяет допустимость запрошенной Git-операции через платформу; Gitaly обслуживает сами операции с репозиторием. Имя пользователя git в SSH-адресе обычно обозначает общий транспортный вход, а личность пользователя устанавливается ключом. Участник не получает от этого интерактивную системную оболочку на сервере.

Успех аутентификации ключом ещё не подтверждает право читать конкретный проект или изменять защищённую ветку. Можно увидеть приветствие проверки ssh -T, а затем получить отказ при push: ключ узнаётся, но правило обновления не выполнено. Проверка внешнего SSH-порта, отпечатка ключа сервера, ключа пользователя, пути проекта и полномочия на ветку — последовательные вопросы к разным слоям. Их объединение в один совет «пересоздайте ключ» теряет причину.

Фоновая очередь и CI — два разных вида работы

Sidekiq — система фоновых заданий приложения GitLab. Она выполняет операции, которые не следует удерживать внутри одного короткого веб-запроса: обработку события, часть обслуживания и отправку уведомления. Очереди используют Redis. Это не значит, что Sidekiq компилирует ваш Go-код. CI-задание получает GitLab Runner; он запускает пользовательский процесс в выбранной среде. Перезапуск Runner не равен перезапуску фоновой очереди сервера.

После принятого push приложение может запланировать дальнейшую обработку и построить конвейер. Если фоновая обработка отстаёт, исходники уже видны, а следующие события появляются позднее. Если задание создано, но подходящий Runner отсутствует, оно ждёт в другой точке. Полезная диагностика сначала находит последнюю завершённую границу: принята ссылка, зарегистрирован pipeline, создан job, назначен Runner, запущена оболочка. Только затем выбирает журнал и метрику.

Карта состояния для собственного экземпляра

 | Данные | Что там живёт | Что проверять при восстановлении

 | PostgreSQL | Пользователи, проекты, разрешения, задачи, метаданные CI | Согласованность с остальными сохранёнными данными и совместимость схемы

 | Репозитории Gitaly | Git-объекты, ссылки, связанные репозитории проекта | Доступность нужных ссылок и получение объектов через платформу

 | Файловое либо объектное хранилище | Артефакты, вложения, LFS, пакеты; состав зависит от настройки | Байты, метаданные, ссылки и права; каждый тип хранилища учитывается явно

 | Container Registry | Манифесты и слои образов, собственные метаданные согласно версии | Получение образа по сохранённому digest, состояние метаданных и политики очистки

Object storage, объектное хранилище, выдаёт объект по ключу через API. Оно не является обычным смонтированным каталогом только потому, что в ключе есть косая черта. GitLab может сохранять там большой объём файлов, оставляя сведения о них в БД. Потеря одного из двух слоёв способна дать либо «файл есть, но платформа о нём не знает», либо «запись видна, но скачать нечего». Поэтому локальная копия PostgreSQL и общий снимок одного диска не считаются универсальным резервом любой конфигурации.

Пакет, контейнер и Kubernetes

Linux package, исторически называемый Omnibus, доставляет согласованный набор компонентов и средства их настройки. Официальный Docker-образ GitLab также упаковывает многокомпонентную поставку. Один контейнер в таком варианте не означает один процесс или малый расход памяти. Службы по-прежнему имеют разные журналы, файлы и причины перегрузки. Образ относится к программной поставке, а вынесенные тома — к постоянному состоянию.

Helm chart описывает развёртывание компонентов в Kubernetes. Это полезно при соответствующей инфраструктуре, но требует понимать внешние PostgreSQL, Redis, Gitaly, объектное хранилище и резерв. Перемещение компонентов в разные Pod не делает данные автоматически отказоустойчивыми. Для личного первого экземпляра дополнительный Kubernetes часто увеличивает число систем, которые приходится одновременно обслуживать, без полезной учебной необходимости.

Опыт чтения архитектуры

Возьмите три операции: открыть задачу, клонировать репозиторий, скачать артефакт. Для каждой нарисуйте клиент, входной компонент, проверку личности, источник данных и возвращаемые байты. Затем мысленно отключите только один источник. Поведение не обязано быть одинаковым: недоступный артефакт не доказывает недоступность Git. Если схема объясняет такие различия и подсказывает место наблюдения, она стала инструментом диагностики.

Разобрать по шагам

Коммит уже сохранён, а процесс Go ещё не запущен

Один push проходит разные границы: Git, приложение, граф, Runner, среда и процесс. Следующий шаг не считается выполненным от одного существования предыдущего.
Условия этого примера

Личный приватный проект; коммит C17; подходящий Runner имеет один слот и сначала занят. HTTPS/SSH и разрешения уже подготовлены. События и длительности условные; стрелки показывают логические действия, а не каждый пакет. Gitaly, Rails и очередь свернуты до нужной здесь границы; это не полный протокол GitLab.

1. Сервер принял C17

Ссылка ветки обновлена на C17. Это подтверждает Git-операцию, но пока не выполнение CI.

Действует: Git-службы.

Git-хранилище: C17 сохранён; Приложение: событие впереди; Конвейер: нет; Runner: другой job; Среда job: не создана; Go-процесс: нет

Исходники: клиентская копия → серверная ссылка → C17. Существование коммита не означает создания pipeline.

2. Создан pipeline №81

Приложение разрешило событие, разобрало конфигурацию и создало задания.

Действует: GitLab.

Git-хранилище: C17; Приложение: правила разрешили; Конвейер: unit готов; Runner: слот занят; Среда job: нет; Go-процесс: нет

Pipeline: не существовал → №81, unit ожидает. Правила и конфигурация обрабатываются до shell.

3. Готовое задание ждёт

Единственный подходящий слот занят. Несоответствующий Runner не помогает.

Действует: Планирование.

Git-хранилище: C17; Приложение: №81; Конвейер: unit pending; Runner: занято 1/1; Среда job: нет; Go-процесс: нет

Время: job создан → растёт очередь. Задержка ожидания отличается от длительности Go-теста.

4. Runner получил unit

После освобождения слота manager получил работу и начал подготовку executor.

Действует: Runner manager.

Git-хранилище: C17; Приложение: №81; Конвейер: unit назначен; Runner: unit, слот 1/1; Среда job: подготовка; Go-процесс: ещё нет

Слот: занят прежней работой → отдан unit. Получение работы ещё не гарантирует успешного создания контейнера.

5. Готовы входы C17

Получены исходники, допустимый кэш и нужные артефакты; затем запускается основная часть.

Что следует выбрать заранее

Self-Managed означает экземпляр под вашим управлением: вы отвечаете за ОС, данные, обновления, доступ и восстановление. GitLab.com — управляемый сервис с иной границей ответственности. CE, Community Edition, и EE, Enterprise Edition, — варианты поставки; наличие EE само по себе не предоставляет любую платную функцию. В личном стенде выбирают доступный набор возможностей и поддерживаемый выпуск. Для повторяемого запуска записывают полное имя версии, редакцию, архитектуру процессора и digest образа либо контрольную сумму пакета.

Digest образа — хеш его содержимого в реестре. Тег, например имя версии, служит указателем; одна только строка latest не закрепляет байты. Получение поставки выполняют при наличии сети и затем сохраняют нужные образы и сведения об их происхождении для автономного периода. Контрольная сумма обнаруживает различие байтов; доверие к ожидаемой сумме или подписи устанавливается отдельно через официальный источник.

Объём памяти распределяется между GitLab, ОС, дисковым кэшем и сборками. Установка сервера и запуск нескольких компиляторов на одном домашнем ПК конкурируют за одни ресурсы. Для первой собственной среды разумнее один Runner и одна одновременная работа с известным набором процессов. Это исходная конфигурация опыта, а не обещание достаточности фиксированных 4 или 8 ГБ для любой нагрузки. После первого запуска измеряют фактическую память и время отклика.

Постоянные каталоги и контейнер

В контейнерной Linux-поставке важны три точки: /etc/gitlab для конфигурации и чувствительных ключевых материалов, /var/opt/gitlab для состояния приложения и /var/log/gitlab для журналов. Их выносят в явно выбранное постоянное хранилище. Удаление контейнера тогда не означает удаление платформы. При этом данные PostgreSQL внутри постоянного каталога ещё требуют согласованной процедуры резерва; копирование файлов работающей БД не подменяет её.

Следующий Compose-фрагмент — шаблон для отдельной Linux-машины личного стенда. Он не выполняется при чтении. GITLAB_IMAGE должен содержать одобренный конкретный образ; GITLAB_HOST — ваше разрешаемое DNS-имя. TLS в этом варианте завершает отдельный входной прокси, а внутренний HTTP-порт связан только с петлевым адресом той же машины. Прокси, сертификат и DNS нужно подготовить до проверки полного маршрута.

services:
  gitlab:
    image: ${GITLAB_IMAGE:?choose a supported pinned image}
    hostname: ${GITLAB_HOST:?set the personal lab hostname}
    restart: "no"
    shm_size: "256m"
    environment:
      GITLAB_OMNIBUS_CONFIG: |
        external_url 'https://${GITLAB_HOST}'
        letsencrypt['enable'] = false
        nginx['listen_port'] = 80
        nginx['listen_https'] = false
        nginx['proxy_set_headers'] = {
          "Host" => "$$http_host",
          "X-Real-IP" => "$$remote_addr",
          "X-Forwarded-For" => "$$proxy_add_x_forwarded_for",
          "X-Forwarded-Proto" => "https",
          "X-Forwarded-Ssl" => "on"
        }
        gitlab_rails['gitlab_shell_ssh_port'] = 2222
    ports:
      - "127.0.0.1:18080:80"
      - "127.0.0.1:2222:22"
    volumes:
      - ./state/config:/etc/gitlab
      - ./state/data:/var/opt/gitlab
      - ./state/logs:/var/log/gitlab

restart: "no" оставляет личную учебную службу без автоматического старта после перезагрузки Docker. shm_size относится к общей памяти /dev/shm, а не к полному лимиту RAM контейнера. Слева в записи порта находится адрес и порт хоста, справа — порт контейнера. Привязка SSH к 127.0.0.1 намеренно делает его доступным лишь с этой машины: для первого упражнения с другого компьютера используйте Git по HTTPS через подготовленный вход. Не открывайте SSH-порт на всех интерфейсах ради совпадения красивого clone URL.

Двойной знак доллара в $$http_host нужен потому, что Compose сам выполняет подстановку переменных. После его разбора GitLab должен получить NGINX-переменную с одним долларом. Это пример двух последовательных языков конфигурации: YAML/Compose сначала, Ruby-настройки GitLab и затем NGINX. Перед запуском docker compose config показывает итоговое описание; проверяют адреса и пути, не публикуют вывод, если в конфигурацию добавлены секреты.

Один адрес виден из разных сетевых пространств

external_url — канонический внешний адрес GitLab. Он влияет на ссылки, перенаправления и представление платформы о своей схеме. Публикация Docker-порта сама не переписывает этот адрес. Если сервер считает себя http://localhost, а пользователь входит через другое HTTPS-имя, могут появиться неверные ссылки, проблемы обратных вызовов и несовпадение безопасных cookie. Лечение начинается с согласования маршрута, а не с отключения проверок.

localhost всегда относится к сетевому пространству того процесса, который его использует. Для браузера дома это домашний ПК, для контейнера задания — сам контейнер, для Runner в отдельной VM — та VM. Поэтому URL, который открывается в браузере, может быть недоступен при загрузке артефакта из задания. Проверяют DNS, маршрут, порт и доверенный сертификат отдельно из каждого участника. Внутренний адрес БД не обязан совпадать с публичным адресом сайта.

TLS-прокси должен передавать корректные заголовки исходной схемы и адреса, а GitLab — доверять только известным прокси. Принимаемый от любого клиента X-Forwarded-For нельзя считать доказанным источником запроса. Сертификат проверяют по имени в URL и цепочке доверия. В личной сети можно использовать свою удостоверяющую инфраструктуру, но её корневой сертификат должен быть доверенно установлен у действительных клиентов; curl -k не превращается в нормальный способ аутентифицированного общения.

Разбор адресов одной личной установки

Возьмём конкретную учебную карту. На личной Linux-VM стоит GitLab-контейнер; входной TLS-прокси работает на той же VM и слушает 443. Имя gitlab.lab.example у клиентов и Runner разрешается в адрес VM. Эти адреса и домен условные, не принадлежат чужой площадке. Прокси передаёт запрос на 127.0.0.1:18080; Docker переводит его на порт 80 контейнера. Внешний external_url равен https://gitlab.lab.example. TLS-сертификат содержит это имя, а клиенты доверяют его издателю. Встроенное автоматическое получение Let's Encrypt в шаблоне отключено, потому что сертификат обслуживает внешний прокси.

 | Кто начинает обращение | Адрес назначения | Что устанавливает доверие

 | Браузер | https://gitlab.lab.example/ | DNS и маршрут к VM, TLS к прокси, затем браузерная сессия и права

 | Git HTTPS | https://gitlab.lab.example/study/echo.git | Та же TLS-граница, затем допустимый credential и права Git

 | Runner manager | https://gitlab.lab.example/ | Его собственные DNS/CA, затем runner authentication token

 | Helper и контейнер job | Git, artifacts, registry и API по своим URL | Их сеть и доверенный CA, краткоживущий job credential или иной узкий доступ

 | Прокси | http://127.0.0.1:18080 | Петлевая граница этой VM и согласованные передаваемые заголовки

 | Git SSH с самой VM | ssh://git@127.0.0.1:2222/study/echo.git | Ключ SSH-сервера, личный ключ клиента, затем права проекта

Последняя строка — только локальный диагностический транспорт. Для неё ожидаемый SSH host key всё равно проверяют; имя 127.0.0.1 не делает удалённый через переадресацию процесс автоматически доверенным. Настройка gitlab_shell_ssh_port = 2222 определяет объявляемый порт SSH, но loopback-привязка шаблона намеренно не делает его доступным с рабочего Windows. Объявленный UI clone URL поэтому ещё не является готовым удалённым SSH-маршрутом. Удалённый Git в этом варианте использует HTTPS. Если позднее появится частный VPN-доступ к SSH, его проектируют отдельно и согласуют привязку/URL/ключи.

Предположим браузер открыл сайт, а job не может получить artifact и пишет x509: certificate signed by unknown authority. Сертификат проверяет процесс, выполняющий именно этот запрос. Успешное доверие браузера не означает доверие Runner helper. Нужно добавить доверенный CA предусмотренным способом в соответствующую среду и проверить имя назначения. Если ошибка вместо этого no such host, сначала исправляют разрешение DNS в этой среде. Если TLS прошёл, а HTTP вернул 403, исследуют уже полномочия и URL. Одинаковая ссылка проходит несколько независимых границ.

Другой опыт: замените в URL внешнее имя на localhost, но только в своей отдельной тестовой конфигурации. Браузер на сервере может по-прежнему что-то открыть, а Runner в другой VM направится к себе. Возвратите исходную карту адресов. Этот отказ объясняется выбранным пространством имён, а не паролем. Чтобы не получить такую ловушку в настоящей установке, проверяют полный путь с тех процессов, которые будут пользоваться платформой.

Первый запуск не заканчивается статусом контейнера

docker compose up -d создаёт и запускает описанные контейнеры в фоне. GitLab затем разворачивает конфигурацию, готовит компоненты и схему данных; статус работающего контейнера означает только существование его основного процесса. Проверяют журнал, состояние служб и readiness, то есть готовность обслуживать работу с зависимостями. Liveness проверяет более слабое свойство жизнеспособности процесса; это не то же самое, что способность принять push или сохранить артефакт.

docker compose ps
docker compose logs --tail=100 gitlab
docker compose exec gitlab gitlab-ctl status
docker compose exec gitlab gitlab-rake gitlab:check SANITIZE=true

ps показывает контейнеры проекта Compose. logs --tail=100 ограничивает вывод последними ста строками и не меняет уровень журналирования. exec запускает команду внутри уже работающего контейнера. gitlab-ctl status исследует службы поставки, а задача gitlab:check — набор прикладных проверок. SANITIZE=true уменьшает показ чувствительных деталей в этой задаче, но любой журнал перед публикацией всё равно просматривают.

Первичная учётная запись и следующий вход

Начальные данные администратора извлекают только в личном терминале согласно выбранной поставке и версии. Файл первоначального пароля в Linux-пакете имеет ограниченный срок жизни; это не постоянное хранилище учётных данных. Создайте отдельную обычную учётную запись для работы с проектом, ограничьте саморегистрацию и проверьте доступ из отдельной приватной сессии. В томе нет настоящих паролей, токенов или инструкции публиковать их в issue.

До приглашения других участников пройдите маленький полный цикл: вход обычным пользователем, создание приватного учебного проекта, push собственного файла, чтение его другим разрешённым клиентом и подтверждение отказа без полномочий. Затем штатно остановите контейнер через docker compose stop, запустите снова и проверьте тот же проект. Эта проверка связывает выбранные постоянные каталоги с реальным сохранением состояния. Команда down -v для обычного завершения обучения не нужна: удаление томов является отдельным действием с данными.

Аутентификация и решение о действии

Аутентификация устанавливает, кто обращается: браузерная сессия после входа, SSH-ключ, персональный токен либо короткоживущий токен задания. Авторизация определяет, что этой личности разрешено над выбранным объектом. Объектом может быть проект, ветка, пакет, переменная, Runner или окружение. Даже у одного человека разные способы доступа могут иметь разные ограничения: токен с чтением API не превращается в универсальную копию всех полномочий интерактивной сессии.

Git-коммит содержит имя и email автора, но эти строки не являются подтверждением личности пользователя GitLab, выполнившего push. Клиент может записать произвольный авторский адрес. Сервер устанавливает транспортную личность отдельно, а подпись коммита — ещё одно свидетельство с собственной моделью доверия. Поэтому правило «разработчик отправляет только свой email» нельзя обеспечить одним просмотром автора в интерфейсе. Для публичного проекта также независимо настраивают безопасный адрес автора и коммитера, например GitHub noreply.

Namespace: адрес и область управления

Namespace, пространство имён, организует расположение проектов и групп. В пути study/payments/api группа study может содержать подгруппу payments, а она — проект api. Такая структура влияет не только на URL: в ней наследуется членство, могут задаваться групповые переменные и распространяться правила. Перемещение проекта меняет часть внешних договорённостей: clone URL, адреса пакетов и интеграции. Числовой идентификатор проекта и его читаемый путь — разные свойства.

Проект принадлежит пространству имён, но его Git-репозиторий — лишь один из ресурсов проекта. В нём могут отдельно существовать wiki-репозиторий, большие файлы LFS и реестры пакетов. Скопированный Git-каталог не переносит автоматически всех этих сущностей. Прежде чем менять структуру групп, составляют перечень потребителей адреса: разработчики, Runner, deploy-скрипты, внешние webhook, модульные пути и документация.

Членство и роли

Роль задаёт набор полномочий в определённой области. Обычные имена Guest, Reporter, Developer, Maintainer, Owner полезны как ориентир, но проверять нужно конкретную таблицу разрешений установленного выпуска. Owner относится к управлению группой; роль администратора экземпляра находится на другом уровне. Возможность читать исходники, создавать ветку, принимать изменение и управлять настройками CI не тождественна. Не следует раздавать Maintainer всем участникам только потому, что им нужен запуск тестов.

Участник может одновременно получить прямое членство проекта и наследованное членство группы. Удаление более слабого прямого назначения не уберёт полномочие, пришедшее сверху. У приглашённой группы также есть собственные условия доступа. При диагностике ищут все пути получения прав, их сроки и область. Удобен маленький журнал решения: личность, целевой объект, требуемое действие, фактические пути членства, применившееся правило.

Visibility, видимость, регулирует общую доступность проекта. Private означает доступ разрешённым участникам, Public — публичную доступность согласно возможностям экземпляра; Internal имеет особые условия и доступен не в любой поставке. Но даже приватный проект может передать секрет через публичное внешнее хранилище или журнал. И наоборот: публичный исходный код не требует открывать анонимное управление Runner и выпуском.

Защищённая ветка и право менять политику

Protected branch, защищённая ветка, накладывает правила push и merge на подходящие имена веток. Если в main должен попадать только проверенный код, недостаточно создать MR: нужно ограничить прямое обновление и определить условия принятия. Совпадение нескольких шаблонов и доступность групповых правил зависят от версии и тарифа. Проверяют итог на учебном проекте с обычной ролью, а не только по настройкам, видимым администратору.

Merge request, запрос на слияние, — объект обсуждения и принятия изменения. Успешный pipeline свидетельствует о выполненных проверках над конкретными входами. Он не доказывает, что ревью прошло, что конвейер нельзя было заменить и что проверялось состояние после объединения с текущей main. Право изменить .gitlab-ci.yml способно менять сами проверки. Защищать нужно и путь изменения политики, общие шаблоны и выдачу полномочий, которыми пользуется выпуск.

Ключи и токены по назначению

 | Материал доступа | Назначение | На что смотреть

 | SSH-ключ пользователя | Git-операции от установленной личности | Владелец закрытого ключа, срок, ключ сервера, права на проект и ветку

 | Personal access token | API или Git over HTTPS в пределах выбранных scopes | Полномочия владельца, scope, срок и отзыв; не вставлять в URL

 | Project/group access token | Автоматизация ограниченной области через отдельную служебную личность | Доступность в тарифе, роль, scope и фактический охват

 | Deploy token | Ограниченные операции получения/публикации определённых ресурсов | Какие именно scopes поддерживаются; это не общий API-токен

 | Runner authentication token | Связь Runner с зарегистрированной конфигурацией GitLab | Защита config.toml; это не пароль проекта и не CI_JOB_TOKEN

Scope — именованное ограничение вида действий токена, например чтение определённого API или репозитория. Оно действует вместе с правами личности, а не вместо них. Долгоживущий персональный токен администратора в обычной сборке даёт слишком широкую связь между пользовательским кодом и управлением платформой. Сначала выясняют, может ли действие выполнить встроенный токен задания либо узкая служебная учётная запись.

Проверка прав без раскрытия секретов

Создайте собственный приватный проект с двумя тестовыми ролями и запишите ожидаемые операции: прочитать Git, отправить новую ветку, изменить main, скачать артефакт, запустить ручную доставку, изменить переменную. Выполните проверки в отдельных клиентских контекстах. Не переключайте только имя автора коммита: оно не меняет аутентифицированного отправителя. Для отрицательного результата сохраняйте код и смысл отказа, а токен и полный заголовок запроса не включайте в заметки.

После отзыва доступа проверяют новые обращения и отдельно судьбу уже выданных копий. Отзыв ключа запрещает дальнейшее использование данного ключа; он не стирает исходники, однажды склонированные участником. Политика доступа, управление секретом и контроль распространённых данных решают связанные, но разные задачи. Это особенно важно для архивов артефактов и контейнерных образов, которые могли попасть в локальные кэши.

Локальный Git хранит объекты, ссылки, конфигурацию и рабочие файлы. GitLab дополнительно хранит задачи, комментарии, участников, правила, CI-переменные, артефакты, пакеты и webhooks. Webhook — исходящий HTTP-вызов, которым платформа уведомляет выбранную систему о событии. При смене Git remote комментарии не превращаются в Git-объекты. Поэтому миграция начинается с перечня сохраняемых сущностей, а не с одной команды push.

Есть разные механизмы: перенос Git-истории, импорт из поддерживаемой площадки и экспорт/импорт проекта GitLab. Полнота импорта зависит от пары источника и назначения, версий, настроек и разрешений. Секреты и некоторые интеграции могут требовать отдельного переноса. Прежде чем выключать старую систему, на копии проверяют заранее выбранные ссылки, крупные файлы, wiki, нужные обсуждения и фактическую работу автоматизации. Число видимых проектов не является проверкой полноты.

Обычный перенос собственной ветки

git remote -v
git remote add destination ssh://git@gitlab.example.invalid/study/api.git
git push destination main
git push destination --tags

Адрес example.invalid — намеренно неработающий пример, его заменяют адресом своего проекта. Новый remote destination позволяет сначала проверить получателя, сохранив прежний origin. Отправка main переносит нужные для неё объекты и предложение обновить одно имя; отдельная --tags передаёт теги. Эти команды не обещают перенести все существующие ветки или большие объекты LFS. Выберите явный набор веток и убедитесь, что их вершины совпали с ожидаемыми идентификаторами.

git push --mirror — другой договор: зеркальная синхронизация ссылок, включая возможное удаление или принудительное изменение ссылок назначения. Это не синоним «отправить всё аккуратно». Её используют только для подготовленной цели и понятного набора ссылок, обычно из отдельной bare-копии. Наличие локальных remote-tracking refs и служебных refs платформы дополнительно меняет смысл. Для простого собственного проекта явные ветки легче проверить.

После подтверждения приёма можно изменить обычный origin через git remote set-url origin .... Это локальная настройка адреса, а не команда сервера мигрировать данные. Проверяют также отдельный push URL, если он настроен. Бывший секретный токен в URL не следует переносить в новый конфигурационный файл или публичный журнал: способы хранения доступа настраивают отдельно.

LFS, подмодули и адреса внутри исходников

Git LFS хранит в обычной истории указатели на большие объекты, а сами байты передаёт отдельным механизмом. Успешное клонирование указателей не доказывает, что все большие файлы доступны на новом сервере. Нужно получить требуемый набор LFS-объектов с прежнего источника и перенести его в подготовленную цель, затем проверить чистую копию, не использующую старый локальный LFS-кэш. Отсутствие сети после миграции быстро выявляет, какие данные считались сохранёнными лишь по внешнему виду каталога.

Подмодуль записывает конкретный коммит другого репозитория и адрес в .gitmodules. Перенос родительского проекта не переносит историю подмодуля. Аналогично Go module path и private dependency URL могут сохранять прежний домен. Составьте карту зависимостей и проверяйте получение из чистой среды Runner. Запуск на старой машине с прогретым кэшем способен скрыть отсутствующий доступ и неправильное имя.

Что именно проверяет запрос на слияние

У MR есть исходная и целевая ветки. Обычный merge request pipeline проверяет состояние, которое GitLab определил для соответствующего типа конвейера; оно не автоматически равно будущему результату объединения с последней main. Merged results pipeline строит специальный результат объединения для проверки, когда функция доступна и включена. Merge train организует очередь принятия с учётом предшествующих изменений. Доступность этих механизмов проверяют по тарифу и выпуску.

Рассмотрим два MR: один меняет контракт ответа, другой — обработку того же поля. Каждый проходит тесты относительно прежней main. После последовательного слияния второму может понадобиться проверка обновлённого сочетания. Зелёный значок относится к конкретному набору входов; пересозданная ветка или изменившаяся цель могут сделать свидетельство устаревшим. Полезно показывать коммит конвейера, источник запуска и состояние принятия рядом, а не сводить всё к одному цвету.

Задачи, обсуждения и жизненный цикл выпуска

Issue — запись о работе, проблеме или решении. Label — метка для классификации, milestone — обозначенная веха, доска — представление отобранных задач. Перетаскивание карточки не является техническим переключением трафика и само по себе не меняет код. Для небольшой команды достаточно малого числа статусов, если понятны критерии переходов. Увеличивать число колонок без различимых решений не полезнее, чем добавлять лишние стадии CI.

Связь MR с issue может быть обычной ссылкой либо специальной закрывающей ссылкой. Автоматическое закрытие зависит от поддерживаемого синтаксиса, целевой ветки и состояния принятия; простое закрытие MR без слияния не следует считать успешным выполнением задачи. В собственном процессе отдельно фиксируют «код принят», «артефакт проверен», «выпуск доставлен» и «результат подтверждён». Одна issue может собирать эти свидетельства, не подменяя их.

Контрольная точка миграции

В новой чистой копии проверьте вершины нужных веток и тегов, присутствие больших файлов, подмодулей и самостоятельную сборку. Затем проверьте read-only и изменяющее действие обычного участника, доступ CI к зависимостям, сохранение артефакта и ссылки внешних систем. Только после сравнения договорённого набора решают, что прежний источник больше не нужен для текущей работы. Его резерв и условия хранения определяются отдельно от смены рабочего URL.

Для учебного опыта достаточно двух собственных локальных bare-репозиториев и личного GitLab-проекта. Введите контрольный тег, отдельную неслитую ветку и обычный файл, который отсутствует в main. Простой push main предсказуемо не переносит эту отдельную ветку. Этот опыт показывает границы операции без обращения к чужому учебному сервису и без разрушительного зеркального push в существующий рабочий проект.

Три языка и три момента

В типичном конвейере встречаются YAML, выражения GitLab и язык оболочки. YAML определяет структуру данных: отображения, списки и строки. GitLab интерпретирует ключи workflow, rules, needs и другие согласно своей модели. Позднее Runner передаёт строки script оболочке, а та разбирает кавычки, переменные, перенаправления и запускает программы. Равные символы доллара в разных местах не гарантируют одинаковый момент подстановки.

В результате возможны три разных отказа: файл не является допустимым YAML; YAML допустим, но конфигурация CI противоречива; граф создан, но команда вернула неуспех. Для первой причины нужен структурный разбор, для второй — CI Lint и понимание графа, для третьей — журнал исполненного процесса. Перебор версий Go при ошибке отсутствующей зависимости в графе не касается того слоя, где произошёл отказ.

Что сервер сохраняет для запуска

Создание конвейера связано с событием, проектом, выбранной ссылкой и коммитом. Конфигурация собирается из корневого файла и разрешённых подключений. Include — подключение другого файла описания. Он может находиться в том же репозитории, в другом проекте или в поддерживаемом внешнем источнике. Внешняя конфигурация становится входом вычисления графа; её изменение способно изменить проверки, даже если Go-код остался прежним.

Для повторяемости удалённые шаблоны связывают с конкретным неизменяемым коммитом либо другим проверенным идентификатором. Имя ветки main у общего шаблона — движущаяся цель. Новый pipeline может получить другую конфигурацию. Retry отдельного задания в уже созданном конвейере и создание нового pipeline — разные действия; они не обязаны заново разрешать внешние входы одинаковым образом. При разборе сохраняют ссылку на фактическую объединённую конфигурацию данного запуска.

Этапы задают барьеры

stages: [check, build, verify]

unit:
  stage: check
  script: ["go test -count=1 ./..."]

vet:
  stage: check
  script: ["go vet ./..."]

build:
  stage: build
  script: ["go build -o dist/echo ./cmd/echo"]

smoke:
  stage: verify
  script: ["./dist/echo -version"]

stages задаёт порядок этапов. В обычной модели без дополнительных зависимостей следующий этап ждёт допустимого завершения предыдущих. unit и vet могут быть готовы одновременно, но реальная параллельность зависит от доступных исполнителей. YAML не создаёт процессорные ядра. Фрагмент пока намеренно неполон: файлы dist между заданиями не передаются автоматически. Для smoke нужен артефакт build; передача будет добавлена в главе о хранении.

Needs задаёт конкретные зависимости

needs описывает зависимости задания от других заданий. Такой DAG, directed acyclic graph, ориентированный граф без циклов, позволяет запускать готовые вершины, не ожидая весь предыдущий этап. Если документация строится десять минут, а бинарник готов за минуту, проверка бинарника может начать работу сразу после нужной сборки. Ускорение возникает от удаления лишнего ожидания, а не от ускорения компилятора.

smoke:
  stage: verify
  needs:
    - job: build
      artifacts: true
  script:
    - ./dist/echo -version

Здесь зафиксированы две связи: smoke ждёт build и получает его артефакт. Без needs загрузка артефактов по умолчанию может охватывать предыдущие этапы; с needs важно явно понимать выбранных поставщиков. Не смешивайте на одном задании needs и dependencies без понимания поддерживаемой семантики: это разные средства выбора исполнения и передачи файлов. Лучше оставить один ясный договор.

needs: [] означает отсутствие таких ожиданий и может разрешить ранний старт. Пустой список не означает «зависит от всех». Если upstream-задание исключается правилами, обычная обязательная связь способна сделать граф несоздаваемым. optional: true допускает отсутствие вершины, но не доказывает, что потребителю действительно можно работать без её данных. Отсутствующий обязательный артефакт нельзя вылечить одним словом optional.

Повторное использование без скрытой подмены

Задание с именем, начинающимся с точки, например .go-defaults, служит скрытым шаблоном и само не запускается. extends наследует конфигурацию по правилам GitLab; списки не следует считать автоматически склеиваемыми. Переопределённый script или rules может заменить родительский список целиком. default задаёт поддерживаемые значения по умолчанию для заданий, но также не является произвольным глубоким объединением любого вложенного поля.

YAML-якорь и alias работают на уровне YAML-документа; extends — на уровне конфигурации GitLab и может использовать подключённые определения. Разница важна для нескольких файлов. При сомнении исследуют расширенное описание, а не визуальное сходство исходников. Разумный шаблон сокращает повторение и оставляет видимыми версию образа, полномочия, передачу данных и условия запуска конкретного задания.

Пройти объединение двух файлов на конкретных значениях

Пусть корень подключает ci/go.yml того же коммита и задаёт default: {image: "tools:approved"}. Подключённый файл содержит шаблон .base с script: ["go test ./..."] и rules: [{if: '$CI_COMMIT_BRANCH'}]. Задание unit делает extends: .base, но задаёт свой script: ["python3 tools/ci.py test"]. Итоговый unit получает образ по default и свой script; родительский go test не становится дополнительной первой командой. Список script заменён, а не склеен.

Теперь добавим unit собственные rules только для merge_request_event. Родительский список условий не остаётся «на всякий случай»: итоговая политика unit стала MR-only. Если build существует на push обычной ветки и требует обязательный needs: [unit], такой push может получить ошибку создания графа из-за отсутствующей вершины. Это происходит до запуска Runner, поэтому журнал Python здесь не появится. Исправление — согласовать области существования обязательных producer/consumer, а не вслепую поставить optional. Если build допустим без unit, это уже другое инженерное требование, которое нужно назвать явно.

Проследите четыре снимка: исходные файлы коммита C17; объединённое описание после include и наследования; набор вершин после rules данного события; доступные к выполнению вершины после зависимостей. На каждом снимке найдите unit, его script, образ и правило. В CI Lint/редакторе своего проекта сохраните итоговое expanded-представление и сравните с прогнозом. Так обнаруживаются скрытые замены списков и отличия удалённого шаблона без единого исполнения пользовательского кода.

Include и дочерний конвейер имеют разные жизненные циклы

integration-child:
  stage: check
  trigger:
    include:
      - local: ci/integration-child.yml
    strategy: mirror

Этот фрагмент для поддерживающей strategy: mirror версии создаёт отдельный child pipeline. Его include находится внутри trigger: это описание нового графа, а не простое включение job в родительский. Child обычно использует тот же проект, ref и commit; source у него parent_pipeline. Если его собственный workflow допускает только push, он может отвергнуть создание, хотя родитель был создан push. Серверная фаза нового конвейера снова имеет свои условия.

Bridge, связующее trigger-задание, без явно выбранной подходящей стратегии может считать достаточным успешное создание downstream. Тогда зелёный родитель ещё не свидетельствует об окончании проверок потомка. mirror связывает результат с downstream по предусмотренной семантике текущей версии; на старой версии проверяют поддерживаемый вариант, а не заменяют ключ наугад. Ручные блокирующие job потомка и правила допустимого неуспеха тоже влияют на итог.

Multi-project pipeline, межпроектный конвейер, выполняется в другом проекте, со своими правами, ref и конфигурацией. Он не получает автоматически артефакты родителя от одного существования связи trigger. Передача переменных, inputs, CI_JOB_TOKEN-допуск и получение файлов задаются отдельно. Не передавайте весь набор pipeline variables без анализа: так параметр или секрет, предназначенный одному графу, может попасть в иной контекст. Для простого личного Go-проекта один понятный граф предпочтительнее искусственного дерева, но при независимых компонентах это различение становится необходимым.

Как проверять ещё не исполнявшийся конвейер

CI Lint — серверная проверка конфигурации GitLab, доступная через интерфейс и API. Она умеет больше обычного YAML-парсера, но её результат также зависит от режима проверки, выбранной ссылки и доступа к подключаемым файлам. При необходимости используют моделирование создания конвейера в контексте своего проекта. Разбор PyYAML в локальном практикуме доказывает лишь структуру YAML и наши собственные инварианты примера; он честно не выдаётся за CI Lint.

Для каждого задания ответьте: почему оно существует в этом событии, каких завершений ждёт, какие файлы получает, какой Runner подходит и какие полномочия будут переданы. Затем нарисуйте один неуспех. Если обязательный тест исчезает из графа без видимого нарушения, конфигурация недостаточно описывает намерение. Если артефакт нужен, но связь содержит лишь порядок этапов, нужно проверить и передачу данных. Граф управления и граф данных связаны, но не совпадают автоматически.

Pipeline source — причина запуска

CI_PIPELINE_SOURCE — предопределённое значение, описывающее вид события конвейера. push охватывает push ветки или тега; merge_request_event относится к MR-конвейеру; schedule — расписание; web — запуск через интерфейс. Внешний API, trigger и downstream-конвейеры имеют собственные значения. Имя ветки не заменяет источник: main может участвовать и в расписании, и в ручном запуске.

Предопределённые переменные появляются на разных фазах. Часть известна до создания pipeline, часть — при вычислении его состава, часть — только внутри задания. Переменная, записанная программой в dotenv-артефакт, ещё не существует, когда выбираются задания этого конвейера. Нельзя заставить уже выполненную программу задним числом решить, создавать ли её предшественника.

Сначала разрешается конвейер, затем его задания

workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS && $CI_PIPELINE_SOURCE == "push"'
      when: never
    - if: '$CI_PIPELINE_SOURCE == "push"'
    - if: '$CI_PIPELINE_SOURCE == "web"'
    - when: never

workflow:rules отвечает за существование pipeline целиком. В примере MR разрешён; push в ветку с уже открытым MR исключён из branch pipeline; остальные push, включая теги, и ручной web-запуск разрешены. Остальные источники намеренно запрещены. Условие CI_PIPELINE_SOURCE == "push" во втором правиле важно: иначе можно случайно исключить другой нужный запуск, у которого также есть имя ветки.

Условия идут сверху вниз до первого совпадения. Это не набор независимых обработчиков, исполняющих все подходящие действия. Последнее безусловное when: never делает политику закрытой по умолчанию. Если расписание потребуется позже, для него добавляют осмысленную ветвь. Случайный общий when: always в конце способен разрешить и те события, которые автор не рассматривал.

Правила конкретного задания

release-check:
  script: ["./dist/echo -version"]
  rules:
    - if: '$CI_COMMIT_TAG'
      when: on_success
    - if: '$CI_PIPELINE_SOURCE == "web"'
      when: manual
      allow_failure: false
    - when: never

В первом совпадении назначается обычный запуск после допустимого завершения зависимостей. При web-запуске создаётся ручное блокирующее задание. allow_failure: false здесь указано явно: его отсутствие может иметь разные значения по умолчанию в зависимости от того, где задано when: manual. В остальных событиях задания нет. Отсутствующая вершина и вершина со статусом skipped — разные наблюдения; по одному серому значку не восстанавливают семантику всего графа.

allow_failure: true разрешает учитывать неуспех задания как допустимый для продвижения pipeline. Это свойство политики результата, а не превращение неуспешной команды в корректную. Для экспериментального анализатора такая настройка может быть разумна. Для единственного теста обязательного свойства она способна скрыть нарушение. В отчёте отдельно показывают, что именно было обязательным и что оставалось информативным.

Изменившиеся файлы и база сравнения

rules:changes выбирает задание на основе изменений путей. «Файл изменился» требует второй точки: относительно какого дерева? У MR используется его контекст сравнения; у обычной ветки и у события без push условия отличаются. Новая ветка, расписание и тег способны дать неожиданное поведение, если автор молча предполагал предыдущий коммит. compare_to позволяет явно указать базу в поддерживаемых случаях; она становится ещё одним входом правила.

Список путей должен охватывать зависимости результата. Для Go-сервиса изменение go.mod, общего пакета, генератора, конфигурации сборки или шаблона CI может требовать проверки, даже когда cmd/api не менялся. В монорепозитории неполный список приводит к ложному ускорению: нужная работа исчезает. Сначала доказывают достаточность выбранной карты зависимостей, затем измеряют выигрыш.

Один коммит, два разных допустимых события

 | Случай | Source | Ветка / открытый MR | Первое решившее правило | Итог workflow

 | Push C17 в topic до MR | push | topic / нет | Разрешить остальные push | Один branch pipeline

 | Push C18 в topic после открытия MR | push | topic / есть | Запретить branch push с MR | Branch pipeline не создаётся

 | MR-событие для C18 | merge_request_event | MR-контекст | Первое MR-правило | MR pipeline создаётся

 | Push тега v0.1.0 на C18 | push | Тег; CI_COMMIT_BRANCH пуст | Разрешить остальные push | Tag pipeline создаётся

 | Расписание над main | schedule | main / значение MR не решает | Последний when: never | Не создаётся по данному договору

C18 может участвовать в нескольких допустимых запусках с разным source. Удаление дубля branch/MR не означает запрета tag pipeline для тех же байтов исходников: это отдельное намерение выпуска. После workflow каждый job ещё вычисляет свои rules. Поэтому pipeline может существовать, но отдельная release-check появится только для тега или ручного web-контекста. Прежде чем смотреть Runner, пройдите пальцем по конкретной строке этой таблицы и первому совпадению.

Регулярные выражения и кавычки

Выражения if используют синтаксис GitLab, а не произвольный Bash. Для регулярного сопоставления поддерживается RE2 с собственными ограничениями; нельзя автоматически переносить сюда конструкции PCRE или JavaScript. Условие в одинарных YAML-кавычках остаётся строкой для серверного разбора. Двойные кавычки YAML имеют собственные правила escape, а кавычки оболочки понадобятся только позже внутри script.

Пример if: '$CI_COMMIT_TAG =~ /^v[0-9]+\.[0-9]+\.[0-9]+$/' отбирает тег по форме. Он не проверяет, что тег подписан, что версия не опубликована ранее или что бинарник безопасен. Regex — проверка строки, а решение о выпуске содержит дополнительные договоры. Если нужно SemVer со всеми условиями предрелизных частей, лучше использовать явно выбранный валидатор и не выдавать короткий шаблон за полную грамматику.

Таблица событий как проверяемая спецификация

Возьмите пять строк: push обычной ветки без MR, push той же ветки с MR, событие MR, тег, ручной запуск. Для каждой заранее запишите ожидаемое число pipeline и обязательных заданий. Затем сравните с GitLab. Если есть расписание, добавьте отдельную строку. Такая таблица лучше десятка счастливых push в одну ветку: она проверяет разветвления, на которых чаще всего теряются проверки и удваивается расход Runner.

В практикуме приложена маленькая исходная модель этой политики. Она позволяет менять событие и видеть, что существует до запуска команды. Модель не реализует весь язык GitLab, не обращается к проекту и не объявляется серверной валидацией. Её назначение — проследить конкретный договор, затем подтвердить его в CI Lint и на собственном экземпляре. Условные состояния имеют смысл только при явно названных предположениях.

Отдельный Runner для выпуска

Одна запись Runner и несколько процессов

В интерфейсе GitLab Runner представлен зарегистрированной конфигурацией с областью использования и свойствами. На машине работает runner manager — процесс программы GitLab Runner, который аутентифицируется, запрашивает работу и организует исполнение. У одной зарегистрированной конфигурации могут быть несколько менеджеров; одна программа-менеджер может обслуживать несколько конфигурационных записей. Поэтому число строк в UI нельзя напрямую превращать в число VM, CPU или одновременно работающих заданий.

Runner обычно сам обращается к GitLab по исходящему HTTP(S). Доступность сайта из браузера не подтверждает возможность такого обращения с машины Runner. Long polling, длинное ожидание ответа, позволяет серверу удерживать запрос получения задания до появления подходящей работы или окончания ожидания. Это не постоянный SSH-канал от GitLab к машине. Дополнительные служебные подключения определяются выбранным executor, хранилищами и инструментами задания.

Регистрация в актуальной модели

Сначала в своём проекте или группе создают Runner с необходимой областью и свойствами. Полученный runner authentication token связывает установленную программу с этой записью. У таких токенов используется префикс glrt-. Старые инструкции с общим registration token относятся к другому, устаревающему процессу и не должны механически переноситься на новый выпуск. Версию Runner выбирают совместимой с GitLab и закрепляют отдельно.

gitlab-runner register --config "$LAB_RUNNER_CONFIG"
gitlab-runner verify --config "$LAB_RUNNER_CONFIG"
gitlab-runner run --config "$LAB_RUNNER_CONFIG"

Это действия внутри отдельной личной Runner-машины с уже установленной официальной программой. LAB_RUNNER_CONFIG задаёт полный путь к её выделенному конфигурационному файлу. register интерактивно спрашивает адрес, токен и executor; секрет вводится в своём терминале и не включается в книгу. verify проверяет связь зарегистрированных Runner с GitLab; она не доказывает доступность образа, Docker или успешность будущей команды. run запускает обработчик в переднем плане; сервисный вариант имеет другой жизненный цикл.

Файл config.toml содержит чувствительный материал аутентификации и настройки допуска к ресурсам. Его не коммитят в репозиторий проекта. Удаление файла на одной машине не равно отзыву записи на сервере, а удаление регистрации не стирает рабочие данные на диске. При переносе машины отдельно решают судьбу токенов, кэшей, образов и накопленных файлов. Неправильную копию config легко принять за «старый Runner снова ожил».

Почему свободный Runner может не подходить

Задание с tags: [linux, go] требует Runner, у которого присутствуют все перечисленные метки. Runner с одной меткой linux не удовлетворяет этому требованию. Метка — заявленное свойство допуска; она не устанавливает Go и не доказывает архитектуру процессора. Это ответственность администратора среды. Отдельно проверяются область Runner, разрешение untagged jobs, protected-настройка, состояние paused и доступность менеджера.

Если задание остаётся pending, сначала сопоставляют его требования с разрешёнными кандидатами. Увеличение числа исполнителей у неподходящей машины не исправит неверную метку или отсутствие доступа к проекту. Если кандидат есть, но свободных слотов нет, причина уже в ёмкости. Если слот получен и задание зависло на подготовке, переходят к executor, сети образов и монтированию. Разные состояния могут одинаково выглядеть как «долго не идёт сборка», но требуют разных действий.

Три независимых ограничения параллелизма

concurrent — общий верхний предел одновременно исполняемых заданий процесса Runner. limit внутри записи [[runners]] ограничивает конкретную конфигурацию; ноль у этого параметра обычно означает отсутствие дополнительного собственного ограничения. request_concurrency ограничивает одновременные запросы получения новой работы, а не количество CPU и не размер графа. Неподходящие значения способны оставить ресурсы простаивающими при длинном ожидании запросов.

concurrent = 1

[[runners]]
  name = "personal-go"
  url = "https://gitlab.example.invalid"
  token = "REPLACE_ONLY_IN_PRIVATE_CONFIG"
  executor = "docker"
  limit = 1
  request_concurrency = 1
  [runners.docker]
    image = "REPLACE_WITH_PINNED_GO_IMAGE"
    privileged = false
    memory = "2g"
    cpus = "2"

Это поясняющий фрагмент, не готовый файл регистрации. На маленьком личном стенде один слот позволяет сначала измерить расходы одной работы. memory и cpus задают ограничения контейнера задания в данном executor, но внешние службы GitLab и Docker требуют своей памяти. Увеличение concurrent до восьми не добавляет восьми независимых бюджетов памяти. Параллелизм внутри go test дополнительно накладывается на число одновременно выполняемых job.

Shell, Docker и Kubernetes — разные границы

Shell executor выполняет команды с правами пользователя Runner на его ОС. Файлы домашнего каталога, доступная сеть и оставшиеся процессы становятся частью доверия к коду проекта. Он удобен в полностью личной выделенной VM для понимания процессов; его нельзя считать изолированным только потому, что job имеет свой каталог. Очистка workspace после выполнения не отменяет действий, уже совершённых за его пределами.

Docker executor создаёт контейнеры задания и служебных компонентов. Он отделяет файловые и процессные пространства согласно конфигурации, но ядро остаётся общим с хостом. Переданный Docker socket даёт управление Docker-хостом в пределах его полномочий и резко меняет границу доверия. privileged = true, host network, host PID и чувствительные bind mount также способны разрушить ожидаемую изоляцию. Для обычной Go-сборки эти возможности не обязательны.

Kubernetes executor создаёт окружение в кластере и использует его API, планировщик и политики. Теперь важны service account, namespace, ресурсы, сетевые правила, тома и admission-контроль. Если Pod создаётся под широко привилегированной учётной записью, слово Kubernetes не уменьшает полномочия кода. Отдельная одноразовая VM на недоверенную работу даёт другую границу ядра и очистки, но стоит времени запуска и ресурсов. Выбор определяется доверием и угрозами конкретной среды.

Разобрать назначение трёх заданий по одному слоту

У manager есть concurrent=2. Конфигурация A: метки linux/go, limit=1; конфигурация B: метки linux/docs, limit=1. Приходят U с меткой go, V с меткой go и D с меткой docs. U занимает A, D занимает B. V ждёт, хотя общий предел два и в интерфейсе видны два Runner. Если D завершится, V всё равно не сможет занять B: кандидат не соответствует метке. Свободное глобальное место и подходящее свободное место — разные условия.

Теперь администратор меняет A limit на 2, оставляя global concurrent=2. Если D ещё работает, одновременно U+V+D всё равно не начнутся: общий предел запрещает третью работу. После завершения D менеджер сможет дать A второй слот. Если при этом каждой Go-работе требуется 1,5 ГБ памяти, два слота требуют уже примерно 3 ГБ только для них, плюс executor и ОС. Это модель значений, а не измеренный профиль нашего маленького приложения; реальный RSS/лимит измеряют отдельно.

request_concurrency=1 описывает ещё другую границу. Один долгий запрос без подходящей работы может задерживать получение другой работы в определённых сочетаниях конфигурации и лимитов. Увеличение request_concurrency исследуют по метрикам и предупреждениям Runner, а не принимают за увеличение допуска процессов. После изменения полезно построить ту же временную шкалу: сколько запросов ждёт, сколько job назначено, сколько реально исполняется и где лимит достигнут.

Отдельный Runner для выпуска

Проверки MR и доставка в личный сервис имеют разные полномочия. MR может содержать ещё не принятый код; deploy получает доступ к рабочей среде. Их полезно разводить по Runner и правилам выдачи секретов. Одна защищённая метка не является секретом: автор YAML способен написать такое же имя. Реальный допуск обеспечивается серверными ограничениями Runner и защищённых ссылок, членством, правилами окружений и доступом к секретам.

При первом запуске выполните задание, которое показывает только несекретные свойства: версию Go, ОС, архитектуру, UID и путь проекта. Затем проверьте передачу артефакта и повторный запуск после остановки менеджера. Не выводите весь env ради любопытства: среди переменных будут данные доступа. Остановленный личный Runner должен оставлять созданное задание ожидающим; возвращение менеджера должно разрешать именно эту границу, не требуя повторного push исходников.

Рабочий каталог не равен вашей копии

Runner готовит каталог проекта и нужную ревизию Git согласно стратегии. CI_PROJECT_DIR обозначает путь проекта в среде job. Его значение задаёт реальная конфигурация Runner; путь на домашнем ПК разработчика сюда не переносится. Обычно checkout представляет конкретный коммит, а не интерактивную локальную ветку. Код, который полагается на имя текущей ветки из git symbolic-ref, может получить не то, что ожидалось. Для сведения о событии используют соответствующие CI-переменные.

GIT_STRATEGY влияет на получение исходников: clone создаёт копию, fetch старается использовать подходящую существующую, none пропускает обычное получение. Последнее не даёт гарантии чистого каталога. GIT_DEPTH ограничивает глубину истории. Малая глубина уменьшает передачу, но влияет на поиск тегов, сравнение с далёкими предками и вычисление версии. Ошибка git describe в CI может означать недостаточный набор ссылок и истории, а не отсутствие тега на сервере.

Файлы появляются в определённом порядке

После подготовки executor и источников Runner восстанавливает кэш, затем получает нужные артефакты и запускает основную часть сценария. Поэтому совпадающие пути кэша и артефактов могут перезаписывать друг друга ещё до первой вашей команды. Избегайте одного каталога для ускоряющего кэша и обязательного выпускного результата. Разделяйте .cache/, reports/ и dist/ по назначению.

before_script и script основной части выполняются в одном предусмотренном shell-контексте задания, поэтому сделанный там cd или export обычно влияет на последующие команды этой части. after_script выполняется отдельно: нельзя полагаться на сохранение произвольной локальной переменной, функции или текущего каталога. Файлы при этом могут сохраняться в общей файловой среде job. Не следует переносить вывод «разные оболочки» на предположение «все файлы исчезли».

script:
  - export CHECK_NAME="unit"
  - mkdir -p reports
  - printf '%s\n' "$CHECK_NAME" > reports/name.txt
after_script:
  - cat reports/name.txt

Передача через файл здесь намеренная. printf '%s\n' печатает значение как данные, не интерпретируя его как формат. Перенаправление создаёт либо заменяет файл; каталог уже подготовлен. Отдельной оболочке не требуется знать CHECK_NAME, чтобы прочитать сохранённые байты. Если имя находится во внешнем рабочем каталоге, путь делают явным через CI_PROJECT_DIR.

Код завершения важнее удачного сообщения

Процесс сообщает ОС небольшой числовой код завершения. Ноль обычно означает успешное выполнение договора команды, ненулевой код — отказ; конкретные значения определяет программа. Shell собирает из нескольких процессов общий результат. Runner оценивает его согласно своему сгенерированному сценарию и конфигурации. Строка «все тесты завершены» в журнале не исправляет последовавшую ошибку загрузки артефакта.

set +e
go test -json -count=1 ./... > reports/tests.jsonl 2>&1
test_status=$?
set -e
python3 tools/check-test-log.py reports/tests.jsonl
exit "$test_status"

Этот фрагмент иллюстрирует сохранение результата; в практикуме используется собственный Python-обёртыватель без зависимости от особенностей shell. set +e временно разрешает обработать неуспех, $? немедленно сохраняет код последней команды, 2>&1 направляет stderr в тот же файл, что stdout. После промежуточной команды читать $? уже поздно: это будет код другой операции. При ошибке самого обработчика отчёта требуется сохранить и этот неуспех, а не объявить результат полноценным.

Конструкция go test ./... | tee test.log без подходящего pipefail может вернуть код последней команды tee и скрыть неуспех теста. Это свойство оболочки и конвейера процессов, а не недостаток тестов Go. Ещё один источник ошибок — многострочный YAML: знак | сохраняет переводы строк, > сворачивает их по правилам YAML. Для сложной логики проще отслеживаемый файл сценария с явной оболочкой и отдельной локальной проверкой.

After_script не является транзакцией

В нормальном пути after_script выполняется до загрузки кэша и артефактов; поэтому созданные им файлы могут попасть в эти наборы. У него есть отдельные ограничения времени и условия запуска. Принудительное завершение машины, потеря executor или исчерпанный общий timeout способны не дать ожидаемой очистке выполниться. Ошибка after_script обычно не меняет уже успешный основной script; от него нельзя делать единственный обязательный тест корректности.

Cleanup, завершающая очистка, удаляет предусмотренные временные материалы, включая файловые переменные, но не откатывает вызов внешнего API, отправленное письмо или применённую миграцию БД. Отменённое job могло уже изменить службу. Для внешних действий нужны собственные идентификаторы операции, проверка фактического состояния и идемпотентность — свойство повторения без нежелательного повторного эффекта. Эти вопросы важнее выбора красивого цвета статуса cancelled.

Сервисы задания и готовность зависимости

services может добавить к Docker-заданию отдельную службу, например PostgreSQL. Имя service становится сетевым адресом в предусмотренной сети; localhost основного контейнера не обозначает этот PostgreSQL. Созданный контейнер не обязательно уже принимает SQL и содержит нужную схему. Тест должен ждать осмысленного признака готовности с ограничением времени, затем отдельно готовить данные и выполнять проверку.

Между основным процессом, helper-контейнером Runner, служебной БД и Docker-хостом несколько сетевых и файловых границ. Вывод «psql отсутствует» говорит о наборе программ основного образа; «connection refused» — о сокете или маршруте; «permission denied for table» — о правах внутри БД. Добавление sleep 30 может случайно скрыть медленный старт, но не объяснит эти разные причины и не задаст проверяемую готовность.

Одинаковый красный значок на разных фазах

 | Последнее наблюдение | Чего ещё не произошло | Проверяемая следующая гипотеза

 | Preparing executor: образ не получен | Go и before_script не запускались | Доступ daemon к Registry, credential и digest; наличие нужной платформы образа

 | Getting source: SSH/HTTPS отказ | Исходники C17 не подготовлены | URL clone, ключ/CA, допустимость job credential и права на Git

 | Restoring cache: miss | Это не обязательно отказ job | Должен ли проект правильно выполниться без кэша; почему выбран данный key/backend

 | Downloading artifacts: файл недоступен | Основной script ещё не получил обязательный вход | Точный producer, needs, срок, права, загрузка и наличие артефакта

 | Executing script: go test вернул 1 | Успешная проверка кода не завершена | Ошибка теста, сборки пакета, среды либо нестабильное условие; сохранить настоящий код

 | Uploading artifacts: сервер недоступен | Результат не стал надёжно доступен потребителю | HTTP/TLS, место/лимиты backend, состав и размер архива

Это порядок исследования, а не таблица «один текст ошибки — одна причина». Например permission denied на этапе получения Git и при записи локального dist относится к разным сторонам соединения. Наличие файла reports на Runner не подтверждает его приём сервером. В отдельной личной ветке можно намеренно сломать путь artifact и убедиться, что прошедший тест не создаёт файл у следующего job магически.

Ситуация с отменой ещё тоньше. Job отправил внешний запрос X, целевой сервер применил X, а Runner потерял связь до ответа. GitLab видит cancelled или инфраструктурный неуспех, но внешний эффект уже существует. После возврата связи проверьте результат X по его идентификатору. Без этой проверки команда retry превращает неизвестный результат в риск повторного действия. Даже идеально очищенный workspace не меняет такой ход событий.

Что сохранять для воспроизведения

Минимальная карточка неуспеха содержит pipeline/job ID, commit SHA, источник события, точную конфигурацию, Runner и executor, digest образа, версии инструментов, фазу отказа и последние безопасные диагностические строки. Для Go полезны выбранные GOOS, GOARCH, режим CGO и число одновременных работ. Полный дамп окружения и домашнего каталога не нужен: он увеличивает утечку, часто не прибавляя причинной информации.

Повтор локально начинают с той же команды в чистой копии, но не объявляют этот результат тождественным job. Локальная ОС может иметь другую сеть, доверенные сертификаты, историю Git и права. Затем приближают именно различающиеся условия. Такой маршрут делает CI источником воспроизводимого свидетельства о программе, а не мистическим местом, где команда иногда работает.

Runner: загрузка; Workspace: name.txt существует; Основная shell: закончена; After shell: закончена; GitLab artifacts: архив с name.txt; Итог job: финализация

Хранение: локальный workspace → скачиваемый артефакт. Готовность локального файла и успешная передача различаются.

6. Получен итог

Итог учитывает выполнение и применимые ошибки фаз. After_script не подменяет обязательную проверку основной части.

Действует: Runner и GitLab.

Runner: слот освобождён; Workspace: согласно очистке executor; Основная shell: 0; After shell: 0; GitLab artifacts: сохранён; Итог job: success

Смысл: процесс завершился → job завершён. Внешние действия не откатываются от очистки файлов.

Окружение процесса — материальная передача данных

При запуске процесса ОС передаёт ему массив строк окружения. Программа и дочерние процессы способны читать полученные значения. Записав пароль в переменную, мы не спрятали его от выполняемого кода: мы дали коду способ его использовать. Секрет в задании может утечь через stdout, HTTP-запрос, артефакт, core dump или кэш. Ограничение доступа к настройке переменной — только одна граница из нескольких.

Обычные настройки — имя среды, целевая архитектура, путь выходного каталога — удобно хранить в versioned YAML. Секреты туда не помещают: даже удалённая позднее строка останется в доступной истории и копиях. При случайной публикации сначала отзывают или заменяют материал доступа у получателя, а затем разбирают распространение и историю. Один новый commit без пароля не отзывает уже прочитанный токен.

Значение выбирается из нескольких областей

Переменные бывают предопределёнными, instance/group/project, заданными в YAML, переданными при запуске, взятыми из отчёта dotenv и добавленными политикой. У них есть документированный порядок приоритетов. Важно знать не только итоговую строку, но и источник: ручная pipeline variable может переопределить то, что автор YAML считал фиксированной политикой. Для повторяемого выпуска набор входов фиксируют и ограничивают право задавать опасные параметры запуска.

Environment scope ограничивает применимость переменной к именам окружений, но его нельзя путать с правом запускать произвольный код. Protected-переменная предназначена для допустимых защищённых контекстов; поведение MR и доступа к protected-материалам имеет дополнительные условия, зависящие от версии и настроек. Флаг protected не означает «безопасно при любом script». Если доверенный контекст разрешает скрипту получить секрет, скрипт способен передать его дальше.

Masked, hidden и file означают разные свойства

Masked просит GitLab скрывать подходящие значения при отображении журнала. Это снижает случайный вывод, но преобразованное значение, отдельные символы, архив либо сетевой запрос могут обойти такое отображение. Hidden ограничивает последующее чтение значения через интерфейс при поддерживаемой настройке. Оно не делает значение недоступным процессу job. Обе настройки полезны, если не принимать их за изоляцию от кода.

File type variable создаёт временный файл со значением, а переменная окружения содержит путь к нему. Это удобно для сертификата или конфигурации инструмента, который принимает имя файла. Но содержимое файла по-прежнему чувствительно; путь не надо включать в архив всего workspace. Права, жизненный цикл и очистка важны, особенно при повторном использовании shell-машины. Приватный ключ в file variable не становится публичным сертификатом от своего формата.

script:
  - test -r "$LAB_CA_FILE"
  - curl --fail --show-error --cacert "$LAB_CA_FILE" "$LAB_HEALTH_URL"

В этом поясняющем фрагменте LAB_CA_FILE указывает на доверенный CA-файл, а URL — на ваш разрешённый сервис. test -r проверяет доступность чтения, --cacert задаёт набор доверенных сертификатов, --fail делает HTTP-ошибку неуспехом. Сертификат CA обычно не является секретным ключом. Даже при шифрованном соединении URL и адрес получателя нужно выбирать осмысленно; не отправляйте токен на произвольный адрес из недоверенной переменной.

Подстановка на стороне GitLab и внутри shell

Одна строка может пройти несколько обработчиков: YAML-парсер, подстановку GitLab для поддерживаемого поля, Runner и оболочку. Не все переменные доступны во всех ключах, а рекурсивное раскрытие зависит от типа и настройки. Файловая переменная в script — путь; эта же конструкция не обязательно применима при вычислении include до создания job. Заменить всё одним объяснением «доллар раскрывается» недостаточно.

Для переменных-параметров всегда задавайте строки явно: GOFLAGS: "-mod=readonly", RETRIES: "3". Так YAML не переинтерпретирует значение как число, булево или специальное представление. В shell используйте кавычки вокруг раскрытий, если не требуется намеренное разбиение. "$TOKEN" передаёт один аргумент, но не предотвращает видимость секрета в списке аргументов при диагностике процессов. Способ передачи выбирают с учётом поведения конкретной программы.

Встроенный токен задания

CI_JOB_TOKEN выдаётся для работы задания и поддерживает ограниченный набор API и ресурсов. В межпроектном доступе участвуют список допуска целевого проекта и полномочия пользователя, от которого идёт запуск, вместе с настройками версии. Список допуска не следует воспринимать как выдачу любых прав всему проекту-источнику. Для действия вне разрешённой модели понадобится иной специально выданный доступ; сначала проверьте, что действие действительно нужно.

Удобно разделять получение зависимостей, публикацию пакета и доставку. Проверкам может не требоваться право публикации вообще. Токен доставки не должен попадать в job проверки чужого MR или в образ, созданный этой проверкой. Адрес с ?token=... попадает в логи, историю и сообщения. Передавайте секрет предусмотренным заголовком или credential-механизмом и не копируйте его в публичные ссылки на артефакт.

OIDC: доверие к заданию без постоянного общего пароля

OIDC, OpenID Connect, позволяет внешней службе принять подписанное утверждение о личности задания. GitLab выдаёт ID token в формате JWT. В нём есть issuer iss, получатель aud, срок exp, субъект sub и дополнительные claims — поля утверждения. Служба-получатель проверяет подпись, допустимого издателя, аудиторию, время и ограничения конкретного проекта и ссылки. Декодировать Base64 и прочитать JSON недостаточно для проверки подлинности.

publish:
  id_tokens:
    PERSONAL_LAB_ID_TOKEN:
      aud: https://secrets.example.invalid
  script:
    - ./tools/exchange-identity-for-short-lease

Это схема интеграции, не готовая команда: обмен реализует выбранный официальный клиент внешней службы с её настроенной политикой. ID token не предоставляет доступ сам по себе; принимающая система решает, какие краткоживущие полномочия выдать подходящему субъекту. Ограничение только на iss доверяло бы слишком широкому кругу заданий одного GitLab. Ограничение на project, ref и назначение токена делает договор значительно точнее.

Сквозной пример: MR из fork и публикация пакета

Есть проект A с выпускной переменной и отдельный fork F участника. Из F открыт MR в A. Код MR ещё не принят; включая CI-файл, он может содержать команды отправки любого доступного значения наружу. Обычный pipeline в F использует конфигурацию и ресурсы своего проекта. Запуск MR-проверки в родительском A меняет контекст доступных ресурсов и требует внимательной проверки кода. Само слово MR не является защитной границей от script.

Договорим политику личного примера: unit/vet не получают выпускных секретов; публикация package разрешена только из защищённой основной ссылки после обязательных проверок и использует отдельный Runner. Для A→B получения артефакта сначала проверяют, что B допускает A в CI_JOB_TOKEN-области, инициатор имеет нужный доступ, а используемый API действительно принимает такой токен. Если хотя бы одно условие не выполнено, добавление широкого персонального admin token лишь обходит исходный замысел. Нужно понять конкретно отсутствующее право.

Пусть читатель видит 403 на URL артефакта B. У него три разные личности: браузерный пользователь, job A и Runner manager. Успешное скачивание в браузере проверяет только первую. Runner authentication token удостоверяет связь менеджера с его записью и не предназначен для произвольного чтения артефакта B. Для job проверяют его краткоживущий credential в самом разрешённом запросе, не выводя значение. Таким образом фактическое решение строится по субъекту, операции и объекту, а не по общей фразе «я же вошёл в GitLab».

Тот же принцип действует с OIDC: разрешение iss = наш GitLab слишком широко для секрета среды A. Получатель должен связывать доверие с ожидаемым project ID/path, видом и именем ссылки, защищённостью и назначением операции в доступной модели claims. Если release-владелец переименовал группу, политика по пути может перестать соответствовать, хотя числовой project ID остался прежним. Такой отказ сначала объясняют изменением утверждения, а не отключают проверку claim.

Проверять нужно и отказ

Для личного секретного сервиса используйте учебное значение, не открывающее рабочую сеть. Проверьте получение из разрешённой защищённой ссылки, отказ из обычной ветки, истёкший срок, неверную аудиторию и отзыв. В журнале сохраняйте причину решения без самого токена. Если положительный тест прошёл, а отрицательные не выполнялись, установлен только факт доступности одного маршрута; граница доверия ещё не проверена.

Когда кэш действительно ускоряет

Что считается обязательным результатом

Кэш — восстанавливаемые данные для ускорения. Его отсутствие не должно лишать сборку способности выполнить правильную работу. Артефакт job — сохранённые файлы конкретного задания, которыми пользуется следующий шаг или человек. Package Registry хранит именованные версионированные пакеты для дальнейшего потребления; Container Registry — образы контейнеров с манифестами и слоями. Release — объект описания выпуска, часто со ссылками. Ссылка release не содержит бинарник автоматически.

Бинарник для доставки нельзя передавать только через cache. Кэш может отсутствовать на другом Runner, быть вытеснен, оказаться недоступным или перезаписанным подходящим ключом. Если доставка молча берёт «что нашлось», система теряет связь между проверенной сборкой и выпускаемыми байтами. Обязательные данные передают через артефакт известного задания либо через зафиксированный пакет с проверяемым digest.

Два кэша Go и один внешний архив

GOMODCACHE хранит полученные модули, GOCACHE — результаты вычислений сборочного инструмента. Сам Go определяет пригодность кэшированного результата по своим входам. GitLab cache — внешняя доставка выбранных файлов между работами. У этих слоёв разные ключи и проверки: наличие архива CI не означает, что Go повторно использует каждую его запись. Подробная внутренняя модель Go-кэша находится в отдельном томе Go.

variables:
  GOPATH: "$CI_PROJECT_DIR/.cache/gopath"
  GOMODCACHE: "$CI_PROJECT_DIR/.cache/gopath/pkg/mod"
  GOCACHE: "$CI_PROJECT_DIR/.cache/go-build"

cache:
  key: "go-lab-${CI_COMMIT_REF_SLUG}"
  paths:
    - .cache/gopath/pkg/mod/
    - .cache/go-build/
  policy: pull-push

Пути cache находятся внутри проекта, поэтому каталоги инструментов явно перенесены туда. CI_COMMIT_REF_SLUG — нормализованное имя ссылки, пригодное для ограниченных имён, но не уникальный идентификатор содержимого: разные исходные имена могут нормализоваться сходно. В примере кэш допускается как ускорение. Для сложной матрицы в ключ добавляют версию toolchain, платформу и другие границы совместного использования. Версионный идентификатор Go задают своим обычным CI-параметром; CI_JOB_IMAGE не следует считать безопасной универсальной строкой для любого ключа.

policy: pull только получает кэш, push только сохраняет, pull-push делает оба действия в допустимом пути. Несколько параллельных писателей одного ключа могут сохранять разные снимки; это не общая согласованная файловая система. Часто один подготовительный job пишет, остальные читают. Отдельно проверяют разделение protected/non-protected контекстов, backend Runner и политику срока хранения. Случайный общий архив нельзя превращать в канал доверенной передачи кода между проектами.

Артефакт создаётся загрузкой, а не существованием файла

build:
  stage: build
  script:
    - python3 tools/ci.py build
  artifacts:
    name: "echo-${CI_COMMIT_SHA}"
    paths:
      - dist/echo
      - dist/manifest.json
    expire_in: 7 days

verify:
  stage: verify
  needs:
    - job: build
      artifacts: true
  script:
    - python3 tools/ci.py verify

После успешной основной работы Runner собирает подходящие файлы и загружает их в GitLab. Ошибка загрузки, превышение лимита, неверный путь или окончание срока создают отдельные причины отсутствия результата. Имя архива помогает человеку, но не заменяет привязку к job ID и SHA. expire_in задаёт желаемый срок согласно правилам экземпляра; удержание последних успешных артефактов может продлить фактическое хранение. Для обязательного длительного выпуска заранее выбирают подходящее реестровое хранение.

Потребитель получает только перечисленный договором набор. Проверка читает manifest и вычисляет SHA-256 бинарника перед запуском. Manifest связывает имя файла, размер, хеш, исходную ревизию, toolchain и выбранную цель. Хеш доказывает соответствие байтам, а подлинность manifest требует собственной доверенной цепочки. Если злоумышленник способен заменить и файл, и контрольную сумму в том же недоверенном месте, одно равенство SHA не доказывает происхождение.

Отчёты и обычные файлы

artifacts:paths даёт доступ к файлам, а artifacts:reports сообщает GitLab, какой поддерживаемый формат нужно обработать и показать как отчёт. go test -json выдаёт поток JSON-событий, а JUnit ожидает XML определённой структуры. Переименование tests.jsonl в junit.xml не меняет формат. Нужен корректный преобразователь с явной обработкой неуспеха и незавершённого прогона.

Отчёт покрытия, лог теста и бинарник имеют разные права и сроки. В тестовом выводе могут оказаться данные запроса, а в core dump — память процесса. Не сохраняйте весь рабочий каталог через untracked: true без анализа состава. Чётко перечисленные пути делают результат понятнее и уменьшают риск захватить временный credential-файл. Маскирование журнала не редактирует байты приложенного архива.

Registry, теги и неизменяемость

У образа контейнера тег stable или latest обозначает перемещаемое имя, digest — конкретное содержимое манифеста. Доставка по digest лучше фиксирует точную сборку; проверка архитектуры остаётся отдельным шагом для multi-platform образа. Слои могут разделяться несколькими образами, поэтому сумма видимых размеров тегов не равна физическому расходу диска. Удаление тега и освобождение неиспользуемых слоёв также могут быть разными этапами политики очистки.

Generic Package Registry позволяет сохранять собственные файлы под именем и версией пакета. Политика повторной публикации той же версии должна быть явной: иначе красивое имя релиза может позднее соответствовать другим байтам. Сохраняйте SHA, происхождение и права на изменение; защищённый тег Git не автоматически защищает внешний пакет от любого разрешённого издателя. Путь загрузки и срок учётных данных также входят в договор.

Два одновременных pipeline и один изменяемый ключ

Pipeline P81 собирает C17, P82 — C18. Оба используют cache key go-main и pull-push. Каждый получает доступную старую копию кэша, затем изменяет свои локальные файлы. Если P82 загрузил архив первым, а медленный P81 позже, последняя сохранённая копия может относиться к более старому набору. Это допустимо для корректного восстановимого кэша: Go повторно проверяет свои входы. Но если cache содержит единственный dist/echo для доставки, поздний P81 способен заменить результат, который автор ошибочно считал новым.

Теперь заменим передачу результата: verify P82 ссылается на artifact build из собственного P82, содержащий H18 и manifest C18. P81 не может просто последним push того же cache key изменить эту привязку. Если artifact истёк или недоступен, verify должен явно отказать, а не взять случайный бинарник по общей ветке. Целостность SHA и правильное происхождение producer — два проверяемых утверждения. При использовании межпроектных/межконвейерных артефактов правила выбора job/ref дополнительно исследуют: слово latest не связывает результат с произвольным текущим потребителем.

Retry build P82 может повторно получить moving image tag, другую внешнюю зависимость или изменённое содержимое незакреплённого источника. Commit C18 при этом тот же, но результат способен стать H18b. Поэтому для выпуска сохраняют идентичность конкретного producer/job и digest, а не только коммит. Если нужны доказуемо повторяемые байты, повторяемость проверяют отдельным сравнением с зафиксированными входами; её нельзя вывести из одинакового имени файла.

Когда кэш действительно ускоряет

Пусть без кэша работа занимает 70 с. Получение архива занимает 9 с, распаковка 4 с, полезная работа с ним 20 с, повторная упаковка и загрузка 12 с. Полное время 45 с, выигрыш 25 с. Если зависимости малы и исходная работа занимала 15 с, тот же архив может всё замедлить. Это придуманные числа для расчёта, не обещание GitLab. Измеряют весь путь и отдельно составляющие, а не только время компилятора.

Сравнивайте одинаковые входы, число параллельных job, сеть и состояние ОС. Отдельно нужен холодный прогон без CI-кэша и без локального Go-кэша. Удалять общий кэш других проектов ради измерения не требуется: используйте выделенные каталоги и ключ. Успешная повторная работа при пустом кэше — проверка корректности договора, а ускорение прогретого пути — отдельная проверка эффективности.

1. Кэш отсутствует

Build обязан уметь получить правильный результат из подготовленных исходников и инструментов без CI-cache.

Действует: Build.

C17: C17; Go-cache: miss; Build workspace: полная работа; Artifact build: нет; Verify workspace: не запущен; Versioned package: нет

Корректность: нет cache → сборка всё равно возможна. В этом проекте нет внешних модулей; toolchain уже подготовлен.

2. Получены байты H17

Go завершил сборку; manifest записал размер и SHA. Пока всё только в build workspace.

Действует: Go и ci.py.

C17: C17; Go-cache: можно обновить; Build workspace: echo, SHA H17; Artifact build: нет; Verify workspace: нет; Versioned package: нет

Идентичность: исходный C17 → результат H17. SHA бинарника и commit SHA описывают разные объекты.

3. Артефакт сохранён

Runner загрузил echo и manifest как результат build.

Действует: Runner.

C17: C17; Go-cache: необязателен; Build workspace: успешен; Artifact build: H17, срок 7 дней; Verify workspace: готов к получению; Versioned package: нет

Договор: локальные байты → обязательный artifact job. Успех только компилятора не гарантирует этот переход.

4. Другая среда получила H17

Verify скачал artifact, а не использовал случайный общий cache.

Действует: Runner verify.

C17: C17; Go-cache: может быть пуст; Build workspace: закончен; Artifact build: H17; Verify workspace: echo + manifest H17; Versioned package: нет

Граница: другой workspace → конкретный artifact build. Изоляция job требует явной передачи нужных файлов.

5. Проверена целостность и версия

Verify вычислил SHA, сравнил размер и запустил echo -version. Повреждение приводит к отказу до запуска.

Действует: ci.py verify.

C17: C17; Go-cache: не участвует; Build workspace: закончен; Artifact build: H17; Verify workspace: H17 проверен; Versioned package: ещё нет

Доказательство: файл загружен → байты совпали, версия отвечает. Это ограниченная проверка, не доказательство отсутствия всех ошибок.

6. Продвигается тот же H17

Для длительного выпуска публикуют фиксированный package с политикой неизменности и доверенным происхождением.

Действует: Система выпуска.

C17: C17; Go-cache: можно очистить; Build workspace: закончен; Artifact build: может позднее истечь; Verify workspace: проверен H17; Versioned package: версия v0.1.0 → H17

Срок: временный artifact → версионированный package. Ссылка latest и новый независимый build не равны продвижению H17.

Состав учебного проекта

В каталоге labs лежит оригинальное маленькое HTTP-приложение echo. Оно использует только стандартную библиотеку Go, поэтому первая локальная сборка не требует получать сторонние модули. Вход /ready служит простой проверкой ответа процесса, /echo?value=... возвращает переданную строку в JSON, -version печатает встроенную версию. Это учебная служба, не готовая система хранения данных.

Сценарий tools/ci.py выполняет три действия: test запускает настоящие Go-тесты и формирует отчёт, build компилирует программу и записывает manifest, verify проверяет целостность и запускает именно сохранённый бинарник. Он использует Python standard library, не устанавливает инструменты и не общается с GitLab API. Возможности платформы описаны в .gitlab-ci.yml и требуют собственного сервера для проверки.

Образ инструментов — самостоятельный вход

Для CI нужен подготовленный образ, содержащий совместимый Go и Python 3. Его переменная LAB_GO_PYTHON_IMAGE задаётся обычным несекретным параметром проекта как полное зафиксированное имя. Обычный образ golang не следует молча считать содержащим любую нужную Python-программу. Для первого shell Runner можно запустить те же сценарии в выделенной VM с уже известными версиями, убрав неподдерживаемый executor ключ image из своего варианта CI.

Описание образа и его контрольная сумма входят в запись опыта. Внутри job выполняют go version и python3 --version; совпадение тега образа при разных фактических инструментах — повод исследовать поставку и кэш Docker. Версия Go в go.mod задаёт требования к модулю и языку, но не заменяет закрепление выбранного toolchain среды. Для автономного стенда его и базовый образ получают заранее.

Исходная версия конвейера

stages: [check, build, verify]
default:
  image: $LAB_GO_PYTHON_IMAGE
  tags: [personal-go]

unit:
  stage: check
  script:
    - python3 tools/ci.py test
  artifacts:
    when: always
    paths: [reports/]
    reports:
      junit: reports/junit.xml
    expire_in: 7 days

build:
  stage: build
  script:
    - python3 tools/ci.py build
  artifacts:
    paths: [dist/]
    expire_in: 7 days

verify:
  stage: verify
  needs:
    - job: build
      artifacts: true
  script:
    - python3 tools/ci.py verify

Полный файл в практикуме добавляет workflow, обычные переменные, ограничение времени и явные предположения. В приведённом графе build ждёт этап check. Verify получает артефакт конкретной build. Job проверки не компилирует программу заново. Это позволяет утверждать, что проверенный SHA относится к переданным байтам. Если вместо этого verify сделал новый go build, мы получили бы свидетельство о другой сборке, даже при совпадающих исходниках.

Команда Go и выбранные флаги

Тест выполняется как go test -json -count=1 ./.... -json даёт поток структурированных событий, -count=1 требует нового исполнения тестов вместо подходящего сохранённого успешного результата, ./... выбирает пакеты текущего дерева по правилам Go. Кэш компиляции при этом не отключается. Чтобы измерить полную холодную стоимость, нужны другие выделенные условия; каждый обычный CI-прогон не обязан уничтожать полезный сборочный кэш.

Сборка использует -trimpath, чтобы нормализовать записываемые файловые пути, и -buildvcs=false, чтобы выбранная политика происхождения не зависела от автоматического VCS-встраивания. Идентификатор исходников сохраняется явно в manifest. -ldflags передаёт аргумент линковщику, где -X main.Version=... устанавливает строковую переменную версии. Для версии допускается ограниченный безопасный набор символов, а не произвольный shell-текст. Глубокая механика этих флагов находится в томе Go.

CGO_ENABLED=0 в данном проекте выбирает Go-вариант без C-зависимости; это подходит нашему составу, но может менять поведение другого проекта. Цель по умолчанию — нативная ОС и архитектура текущего Go. Для CI примера ожидается Linux Runner. Если вы намеренно кросс-компилируете Windows-бинарник на Linux, локальный verify не должен пытаться запускать его как Linux-программу. Отдельный целевой исполнитель — часть проверки такого выпуска.

Привязка к исходникам и проверкам

В CI manifest получает CI_COMMIT_SHA; в локальной копии сценарий пробует прочитать собственный Git HEAD и иначе явно пишет local-unversioned. Последняя строка честно говорит об отсутствии Git-свидетельства. Она не означает, что деревья двух копий одинаковы. SHA коммита также не доказывает чистоту изменённого рабочего каталога вне CI: локальный опыт должен учитывать непроиндексированные изменения. Для учебного проекта тесты запускаются в временных копиях.

Проверка целостности сравнивает размер и SHA-256, затем получает -version из того же файла. Она не удостоверяет отсутствие всех ошибок программы. Функциональные тесты HTTP-обработчика проверяют отдельные свойства, а запуск бинарника проверяет ещё одну границу сборки и исполнения. Ни одна из проверок не переименовывается в полное доказательство качества. Существенно, что каждая даёт точное проверяемое утверждение.

Неуспех как часть примера

В собственной копии поменяйте ожидание одного теста. Unit должен завершиться ненулевым кодом, отчёт обязан сохраниться, build не должен продвинуться обычным путём. Затем исправьте тест. Отдельно поменяйте один байт уже собранного файла: verify должен отвергнуть его до запуска. Наконец, удалите cache и повторите правильный исходный прогон. Он должен работать медленнее либо так же, но не терять корректность.

Следующий опыт — остановить личный Runner после создания pipeline и вернуть его. Это проверяет назначение работы, а не Go. Ещё один — изменить только правила workflow и проверить таблицу событий. Так одинаковый внешний симптом «нет зелёного выпуска» раскладывается на отсутствие графа, ожидание ресурса, неуспех теста, ошибку сборки, отсутствие артефакта и нарушение целостности.

Свидетельство имеет вход и границу

Фраза «тесты прошли» неполна без указания коммита, платформы, набора тестов и конфигурации. Модульный тест обработчика через httptest проверяет Go-код без настоящего сетевого маршрута. Интеграционный тест с PostgreSQL проверяет дополнительно протокол и выбранную конфигурацию БД. Проверка из браузера через прокси включает ещё DNS, TLS, маршрутизацию и HTTP-посредников. Один уровень не объявляют свидетельством обо всех остальных.

Ожидаемый неуспех должен сохраняться через оболочку, обёртку, Runner и правила pipeline. Если тест вернул 1, а Python перехватил исключение и завершился 0, GitLab увидит успех. Если job имеет allow_failure: true, UI может показать предупреждение и разрешить продвижение. Если обязательный job не появился из-за rules, его нечему проваливать. Проверка механизма неуспеха — самостоятельный необходимый опыт.

Go JSON и JUnit XML

go test -json выдаёт последовательность событий. У события есть пакет, иногда имя теста, действие и выходной текст. Успех отдельного теста и итог пакета различаются: пакет может завершиться ошибкой вне именованного теста, например при сборке или в TestMain. Поток может оборваться до итогового события. Преобразователь, который сохраняет только увиденные pass, способен превратить незавершённую работу в красивый пустой отчёт.

JUnit XML ожидает test case с именем, группировкой и описанием failure, error либо skipped. В учебном преобразователе завершённые события становятся случаями, а неуспех пакета без обычного test failure создаёт отдельную диагностическую запись. Ненулевой код go test остаётся ненулевым кодом сценария. XML нужен для представления данных, а код процесса — для политики job. Серверная обработка JUnit сама по себе не должна считаться механизмом завершения script с ошибкой.

Отчёт нужно сохранить и при ошибке

artifacts:
  when: always
  paths:
    - reports/tests.jsonl
    - reports/junit.xml
  reports:
    junit: reports/junit.xml
  expire_in: 7 days

when: always у artifacts относится к условиям загрузки файлов, а не к запуску job после любых ошибок графа. При уничтоженной VM файл всё равно может не попасть на сервер. paths позволяет скачать исходные данные, reports:junit задаёт обработку поддерживаемого формата. Установленный GitLab имеет ограничения размера и принимаемых полей; действующий отчёт проверяют в UI собственного проекта. Наличие корректного XML в локальном каталоге — более узкое свидетельство.

Имена тестов должны различаться в пределах нужной группировки. Повторные имена могут быть объединены или проигнорированы обработчиком. Динамический случай, где имя содержит секрет, переносит секрет в долговременные метаданные MR даже при маскированном логе. Для параметризованных проверок используйте безопасные осмысленные названия и сохраняйте подробности только в разрешённом наборе диагностических данных.

Покрытие не равно полноте требований

Coverage, покрытие, измеряет исполнение инструментированных участков выбранным набором тестов. Высокое значение показывает достижение кода, но не силу проверяемых утверждений. Тест, который вызвал функцию и не проверил ответ, способен повысить процент. Нужно знать знаменатель: какие пакеты и файлы включены, исключены ли генераторы, как учитываются разные варианты сборки и какой набор тестов реально запускался.

Простой процент из лога и структурированный отчёт покрытия — разные каналы GitLab. Regex поля coverage извлекает число из текста; изменение формата вывода может сломать извлечение при исправных тестах. Форматы coverage_report требуют подходящего преобразования. Уменьшение знаменателя ради роста процента изменяет метрику, не улучшая тестирование. В MR полезнее связывать изменение покрытия с риском конкретной логики.

Статический анализ, зависимости и среда

Статический анализ исследует код без обычного исполнения всех его путей. go vet находит определённые подозрительные конструкции; анализатор уязвимостей связывает выбранные зависимости и вызовы с известной базой. Каждый инструмент имеет охват, версию правил и собственную цену ложных результатов. Отсутствие предупреждения не доказывает отсутствие всех уязвимостей, особенно неизвестных или не попавших в выбранную модель.

SAST — static application security testing, статическое исследование безопасности приложения. Dependency scanning исследует зависимости, secret detection ищет похожие на секреты данные, DAST проверяет работающее приложение извне. Эти термины описывают разные способы наблюдения. Встроенные функции и представления GitLab могут зависеть от тарифа; запуск своей команды в job и специальный коммерческий интерфейс результатов — разные возможности. Для автономной работы нужны заранее сохранённые инструменты и актуальная на известную дату база.

Граница SonarQube

SonarQube — отдельная платформа анализа: сканер готовит и отправляет данные, сервер хранит проект, обрабатывает анализ и вычисляет свои показатели и quality gate — политику условий качества. Успешная отправка отчёта ещё не означает, что сервер завершил обработку и gate принят. Асинхронная очередь, версия анализатора, ветка, база сравнения нового кода и права интеграции влияют на результат.

Полный разбор SonarQube требует самостоятельного тома: установка, БД и индексы, версии сканеров, модель анализа, языковые правила, новые/существующие нарушения, политика качества и эксплуатация. Здесь он обозначен как внешняя зависимость CI, а не свёрнут до одной команды скачивания. Для текущего собственного Go-практикума достаточно настоящих тестов, vet, отчёта и явно записанной границы качества; полноценная интеграция SonarQube ещё не заявлена выполненной.

Когда проверка полезна и когда мешает

Измеряйте время до первого полезного сигнала, частоту воспроизводимого неуспеха, долю нестабильных проверок и время разбора. Flaky test — тест, который при одинаковых существенных входах нестабильно меняет исход из-за неконтролируемых условий. Безусловный retry снижает видимость проблемы и увеличивает расход, но не устанавливает причину. Разбирайте время, порядок, внешнюю службу, случайность и ограничения ресурсов.

Быстрые определяющие проверки удобно выполнять раньше, дорогие — после них или параллельно в достаточной среде. Обязательное свойство нельзя убрать ради красивого среднего времени. Сравнивайте медиану и высокие квантили на сопоставимых входах; один прогон после загрузки образа не представляет весь день работы. Полезная метрика помогает принять действие, например изолировать нестабильную внешнюю зависимость, а не просто накапливает графики.

Окружение описывает цель

Environment, окружение GitLab, — именованный объект, к которому привязываются действия развёртывания. Например personal/staging и personal/production. Deployment, развёртывание, — запись конкретного такого действия. Поле environment помогает организовать историю и интерфейс, но не запускает сервер само: внешний эффект выполняет ваш script или интеграция. Отсутствие ошибки curl недостаточно считать проверенной всю службу.

Одна физическая VM может содержать несколько логических сред, а одно окружение — несколько узлов. Граница определяется конфигурацией доставки, данными, доменом и полномочиями. Имя production в YAML не гарантирует изоляцию от staging. Если обе среды используют одну таблицу БД и один секрет, переименованные job не разделят их последствия. В личном стенде сначала полезен один отдельный учебный сервис с понятной точкой восстановления.

Один раз построить, затем продвинуть

Promotion, продвижение, означает доставку уже выбранного и проверенного результата в следующую среду. Удобная идентичность: коммит исходников, ID сборки, SHA-256 бинарника, версия пакета и конфигурация окружения. Если staging и production независимо пересобирают один тег, они могут получить разные байты из-за toolchain, базы образов или внешних зависимостей. Повторяемость сборки полезна, но продвижение тех же байтов позволяет избежать лишнего вопроса именно на границе доставки.

Manifest практикума хранит хеш и размер, а проверка выполняется перед запуском. Для длительного выпуска артефакт переносят в версионированное хранилище, не полагаясь на «последний успешный job ветки». Такая ссылка движется при новом запуске. Retry старой доставки должен либо получить тот же зафиксированный пакет, либо явно отказаться, если данных больше нет. Молчаливый выбор нового latest нарушает проверяемость.

Ручная кнопка — часть политики

deploy-personal:
  stage: deploy
  environment:
    name: personal/staging
  resource_group: personal-staging
  interruptible: false
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
      when: manual
      allow_failure: false
    - when: never
  script:
    - ./tools/deploy-to-personal-lab

Фрагмент иллюстрирует политику и не входит в готовый локальный пример: конкретная команда зависит от личного стенда. when: manual добавляет ручной допуск, allow_failure: false делает ожидание значимым для продвижения. Реальное право нажать кнопку, получить секрет и использовать целевой Runner определяется отдельно. Автор, способный заменить script в доверенном контексте, потенциально способен заменить и действие выпуска.

interruptible: false говорит, что работа не предназначена для автоматической отмены как устаревшая при поддерживаемой политике auto-cancel. Оно не даёт гарантии бессмертия: пользовательская отмена, timeout, отказ узла и ошибка внешнего сервиса всё ещё возможны. Поэтому доставка должна знать, что успело выполниться, и уметь сверять фактическое состояние после прерывания.

Resource group упорядочивает доступ к одному ресурсу

resource_group ограничивает одновременное выполнение связанных job в рамках поддерживаемой области GitLab. Два pipeline могут параллельно компилироваться, но их доставка в один учебный сервис не должна одновременно заменять один файл и переключать один указатель. Имя группы — ключ сериализации, последовательного допуска. Одинаковые имена в разных независимых проектах не следует считать универсальным распределённым замком всей организации.

У группы есть режим порядка: unordered, oldest_first, newest_first и newest_ready_first имеют разные правила выбора. «Только по одному» ещё не означает «новая версия обязательно останется последней». Например новая доставка завершилась раньше, а затем в очередь пришёл старый pipeline и вернул старую версию. Политика порядка и запрет устаревшей доставки дополняют блокировку. Новые-first режимы требуют особенно ясно определить идемпотентность и судьбу пропущенных изменений.

Retry и неизвестный результат

Retry — повтор job после неуспеха. Для теста это ещё один опыт с теми же заявленными входами, для платежа или миграции — возможно второе внешнее действие. Если сеть оборвалась после принятия запроса целевой службой, клиент не знает, был ли эффект. Автоматический retry по любой ошибке способен повторить действие. Внешний протокол должен поддерживать идентификатор операции либо проверку фактического состояния, а не угадывать по последней видимой строке.

В GitLab можно ограничить retry классами инфраструктурных неуспехов и количеством попыток. Это снижает случайный шум, но класс отказа не доказывает отсутствие внешнего эффекта. Выпускной сценарий сначала читает, что реально установлено, сверяет желаемый digest, применяет недостающее и проверяет результат. Если операция необратима, повтор должен явно учитывать предыдущие шаги. Успешный повтор не стирает причину первого отказа из эксплуатационной картины.

Переключение и проверка работающего результата

У простого бинарного сервиса можно сохранить версии в отдельных каталогах, проверить новый бинарник и конфигурацию, затем сменить выбранную версию и штатно перезапустить службу. Реальная процедура зависит от systemd, процесса и файловой системы. Замена исполняемого файла не переносит автоматически состояние текущих запросов. Graceful shutdown, штатное ограниченное завершение, прекращает приём и даёт нужной работе завершиться в известное время.

Readiness проверяет готовность принимать нужную работу, а endpoint версии связывает ответ с ожидаемым выпуском. Проверка только TCP-порта доказывает значительно меньше: на порту может отвечать старый процесс, другой сервер или неполностью готовая новая версия. После смены трафика смотрят долю ошибок, распределение задержек и критические операции. Маленькое число удачных проб не доказывает отсутствие редкого сбоя под нагрузкой.

Возврат к прежнему бинарнику и данные

Rollback, возврат, относительно прост, если менялись только байты приложения и конфигурация совместима. Изменение БД может нарушить это условие. Новый процесс мог записать данные нового формата, удалить столбец или запустить необратимое преобразование. Возврат старого файла не возвращает прежнюю схему и потерянные записи. Резерв БД также не является бесплатным мгновенным rollback: восстановление может потерять новые записи и потребовать остановки.

Для совместимого перехода используют последовательность расширить — перевести — сократить: сначала добавить совместимые возможности данных, затем обновить процессы и перевести обращения, затем удалить старое после проверки. Этот путь подробно развивается в томе PostgreSQL. GitLab координирует job и сохраняет свидетельства, но не знает семантику ваших таблиц. Решение о возврате должно учитывать данные и внешние эффекты, а не только статус конвейера.

Начинать с границы наблюдения

Для пользователя важно время от отправки изменения до полезного результата. Оно включает обработку события, создание графа, очередь каждого задания, подготовку среды, полезную работу и передачу результатов. Сумма durations всех job не равна длительности pipeline: часть работ выполняется параллельно, часть ждёт зависимостей. Критический путь — самая длинная необходимая цепочка по графу с учётом реального допуска к ресурсам.

При быстром получении слота и десятиминутной распаковке архива добавление Runner создаст больше той же передачи. Сначала определяют фазу, затем гипотезу.

Пропускная способность и параллелизм

Пусть одно задание занимает в среднем 60 с чистого слота, а входящий поток в устойчивом режиме — 0,02 job/с, то есть 1,2 job в минуту. Один последовательный слот способен завершать около одного такого job в минуту, и очередь будет расти. Это идеализированная модель с одинаковыми работами и без накладных затрат; она показывает невозможность обслужить устойчивый поток, а не предсказывает точную задержку. Для реального планирования учитывают распределение длительностей и всплески.

Закон Литтла для устойчивой системы связывает среднее число работ L, среднюю интенсивность завершений λ и среднее время в системе W: L = λ × W. Он требует согласованной границы и устойчивости наблюдения. Если считать только работающие job, нельзя подставить время вместе с очередью. Если поток растёт без ограничения и завершений меньше поступлений, короткое среднее окно способно скрыть нарастающую проблему.

Увеличение слотов помогает до насыщения CPU, памяти, диска, сети либо общей внешней зависимости. Go внутри job также параллелит пакеты и тесты. Четыре job по четыре активных сборочных процесса на четырёх CPU создают другое расписание, чем один job. Память компиляторов, тестов и служебных контейнеров суммируется. Наблюдаемый OOM — завершение из-за недостатка памяти — может быть следствием общего параллелизма, а не утечки одного приложения.

Числовой опыт: где второй слот экономит время

Создадим четыре одинаковых готовых job A, B, C, D в момент t=0. Каждый занимает слот ровно 30 с, сети и накладных расходов в этой модели нет. На одном слоте они заканчиваются в 30, 60, 90, 120 с; ожидания равны 0, 30, 60, 90 с, среднее ожидание — 45 с. На двух действительно независимых слотах A/B заканчиваются в 30 с, C/D — в 60 с; ожидания 0, 0, 30, 30, среднее — 15 с. Сумма полезной работы остаётся 120 slot-seconds. Меньшая задержка получена ресурсом параллельного исполнения, а не исчезновением работы.

Теперь предположим оба слота делят насыщенный диск, поэтому каждая пара job занимает 50 с. Последняя работа заканчивается уже в 100 с, а суммарно занятые слоты — 200 slot-seconds. Это всё ещё быстрее одного слота по времени окончания всей пачки, но дороже по занятости и слабее первоначальной гипотезы. Если память приводит к OOM и retry, результат способен стать хуже исходного. Изменение concurrency проверяют одновременно по задержке, расходу и ошибкам.

Для графа unit 8 с, vet 3 с, build 5 с, verify 1 с при двух слотах и описанных зависимостях идеальное окончание — 14 с: max(8,3)+5+1. Ускорение vet до 1 с не сократит этот критический путь, пока unit занимает 8 с. Сокращение unit до 4 с уменьшит идеальное время до 10 с. Но если все 17 с полезной работы ждут перед этим 120 с подходящий Runner, главный пользовательский выигрыш сейчас в доступности слота. Так числа помогают выбрать действие и не путать разные границы эффективности.

Проценты, квантили и сравнимые серии

Медиана показывает центральную часть серии, p95 — значение, ниже которого лежат примерно 95% наблюдений в выбранном наборе. Для малой серии оценка нестабильна. p95 длительности всех job, где смешаны секундные lint и часовые интеграционные проверки, отвечает другому вопросу, чем p95 unit для одного проекта. Группируйте по типу работы, toolchain, executor, значимому размеру входа и состоянию кэша.

Частота ошибок требует знаменателя и окна: 5 неуспехов из 10 запусков и из 10 тысяч имеют разный смысл. Разделяйте ошибки кода, нестабильность теста, инфраструктуру Runner и отмену устаревших pipeline. Последняя может быть полезной экономией, а не отказом сервиса. Измерение стоимости включает занятые slot-seconds, передачу, хранение и труд разбора; уменьшение одного числа не обязано уменьшить всё сразу.

Сервер GitLab и сборочные мощности

Веб-латентность, задержка фоновой обработки Sidekiq, PostgreSQL, Gitaly и Runner относятся к разным слоям. Репозиторий с большим числом объектов способен нагрузить Git-обработку даже при небольшом числе пользователей. Частый опрос API автоматизацией может дать существенный поток без человеческих открытий страниц. Поэтому число зарегистрированных аккаунтов само по себе плохо описывает требуемую мощность.

Официальные reference architectures используют нагрузочные модели и различают компоненты. Они являются отправной точкой, а не обещанием, что любое сочетание запросов уложится в одно число RPS, requests per second, запросов в секунду. Сравнивают состав потока: API, web, Git fetch/push, размеры, время CPU и объём передачи. Решение разнести Gitaly, PostgreSQL или Runner принимается по наблюдаемому узкому месту и требованиям восстановления.

Диск: место, скорость и срок жизни

Свободные гигабайты и задержка операций — разные свойства. На одном диске могут одновременно работать PostgreSQL, Git-упаковка, распаковка артефакта и Docker. Рост очереди I/O увеличивает время даже при умеренной загрузке CPU. Исследуйте конкретный каталог и поток: Git-объекты, образы, кэш, artifacts, журналы, временный резерв. Не удаляйте вручную файлы из служебного хранилища ради быстрого освобождения места: у платформы есть метаданные и штатные механизмы обслуживания.

План ёмкости включает скорость роста, срок хранения, резерв перед обновлением и временный пик восстановления. Файл архива может распаковаться значительно больше собственного размера. Очистка артефактов и Registry должна согласоваться с тем, какие версии требуются для возврата. Экономия диска, которая удаляет единственную доступную сборку, меняет операционные гарантии. Резерв рядом на том же заполненном диске не решает его отказ.

Выбор следующего улучшения

Перед изменением сформулируйте проверяемую гипотезу: «добавление второго отдельного Runner уменьшит p95 очереди unit, не увеличив OOM и время самой работы». Сохраните исходную серию, измените одну существенную границу и соберите сопоставимые наблюдения. Если гипотеза не подтвердилась, верните экспериментальную настройку и исследуйте другое ограничение. Покупка RAM, новый кластер и больше concurrency — решения, которые должны следовать из причин, а не из одного медленного запуска.

Резерв — договор о возвращаемом состоянии

Начните с перечня: PostgreSQL, репозитории, LFS, вложения, artifacts, packages, Registry, Pages, конфигурация, секреты шифрования и внешние хранилища. Реальный набор зависит от установки. Некоторые данные стандартная команда включает, некоторые требуют отдельного действия либо собственного механизма backend. Для object storage особенно важно проверить границы: сохранение ссылок в БД не является копией каждого объекта внешнего хранилища.

/etc/gitlab/gitlab-secrets.json в Linux-поставке содержит ключевые материалы, необходимые для расшифровки ряда чувствительных данных. Архив приложения намеренно не заменяет резерв конфигурации и секретов. Если восстановить БД без соответствующего ключа, видимые строки могут существовать, но сохранённые credentials не станут пригодными. Совместное хранение копии и ключа в одном общедоступном месте, наоборот, снижает защиту. Нужно одновременно обеспечить доступ владельцу и ограничить доступ посторонним.

Что делает штатная команда

gitlab-backup create
gitlab-ctl backup-etc

Команды относятся к обслуживанию своего Linux-package экземпляра и выполняются с требуемыми правами в его среде. Первая создаёт прикладной backup согласно конфигурации и версии, вторая сохраняет содержимое /etc/gitlab. Это разные выходы. У container-поставки их вызывают внутри соответствующего контейнера, а полученные файлы должны оказаться в постоянном каталоге и затем вне отказового домена исходного диска. Во время создания нужны временное место, доступ ко всем backend и наблюдение результата.

Backup может завершиться частично или не охватить исключённые параметры. Запишите полный идентификатор, точную версию и редакцию GitLab, время, список включённых/отдельно сохранённых данных и контрольные суммы. Успех команды и возможность читать архив не доказывают полноту будущего возврата. Снимок контейнера также не заменяет согласование БД и внешнего object storage. Для активного экземпляра нужен поддерживаемый способ координации записи согласно его архитектуре.

RPO и RTO задают требование

RPO, recovery point objective, — допустимая потеря последних данных по времени относительно отказа. RTO, recovery time objective, — допустимое время до требуемого восстановления сервиса. Ежесуточный резерв не даёт нулевой RPO, а быстрое копирование архива не даёт короткой RTO, если установка старой версии и распаковка занимают часы. Обе величины требуют явной границы: вернуть чтение Git или всю платформу с CI, пакетами и интеграциями.

Для личного стенда разумный первый договор может допускать потерю одного учебного вечера, если исходники и записи опытов отдельно сохранены. Это личное решение, а не промышленный стандарт. Чтобы его проверить, измерьте время получения нужной версии, доставки backup, восстановления, проверки данных и открытия клиентского доступа. Автономная работа добавляет требование заранее иметь все необходимые пакеты, образы и ключи.

Изолированная репетиция возврата

Восстанавливают на подготовленной совместимой установке той же точной версии и соответствующей редакции, что backup, согласно актуальным требованиям. Старую БД нельзя считать универсально читаемой произвольным новым образом. На копии отключают исходящие действия, которые могли бы повторно разослать письма, выполнить webhook или доставку. Совпадение прежнего hostname не должно случайно направить пользователей или Runner к экспериментальному экземпляру.

Репетиция имеет заранее выбранные контрольные объекты: Git-тег и файл, issue с обсуждением, скачиваемый артефакт, package, LFS-объект и нужная интеграционная настройка. Проверяют вход обычного участника, отказ неразрешённого действия и работу расшифровки чувствительных полей предусмотренными проверками. Только логин администратора — слишком слабый набор. Точное воспроизведение необязательных старых job не требуется, если договор отдельно фиксирует судьбу Runner.

Операция restore заменяет состояние целевого экземпляра и требует штатной остановки определённых служб записи по инструкции версии. Поэтому в книге нет безусловной команды, которую читатель случайно выполнит на живой системе. Сначала должен существовать изолированный известный target и понятный путь возврата. Время и место измеряют на этой репетиции, а не предполагают из размера сжатого архива.

Последовательность восстановления небольшой Linux-поставки

Рассмотрим учебный target, который точно не обслуживает пользователей и не разделяет изменяемые хранилища с источником. Сначала по metadata backup выбирается та же полная версия и тип CE/EE. На чистом target устанавливается и один раз успешно конфигурируется эта поставка: restore ожидает уже существующие роли и БД. До импорта возвращают соответствующий gitlab-secrets.json и согласованную конфигурацию, корректируя только заранее обоснованные различия адресов и изоляции. Сохраняются требуемые имена repository storage, а не только визуально похожие каталоги.

Дальше архив помещают в настроенный backup path с владельцем, ожидаемым служебной программой. Проверяют достаточно места и извлечение, а отдельные object storage данные возвращают своим предусмотренным путём. Затем по инструкции точной версии останавливают Puma и Sidekiq, сохраняя необходимые restore-зависимости, и убеждаются через status, что прикладная запись прекращена. В этом явно изолированном контексте вызывается gitlab-backup restore BACKUP=ИДЕНТИФИКАТОР; идентификатор берётся из имени сохранённой копии без служебного суффикса архива. Это заменяющая операция, поэтому команда не является диагностикой живого исходного экземпляра.

После успешного импорта применяют требуемую конфигурацию и запускают службы в предусмотренном порядке. Выполняют gitlab-rake gitlab:check SANITIZE=true и применимую проверку расшифровки gitlab-rake gitlab:doctor:secrets. Последняя проверяет сохранённые зашифрованные данные и не должна публиковать сами значения. Затем идут контрольные операции чтения/записи собственного проекта, скачивание H17, LFS/package, вход обычной роли и отказ запрещённого действия. Лишь после этого меняют реальный клиентский маршрут, если восстановление предназначено для возврата услуги.

Результат «Git clone работает, но переменная CI не расшифровывается» предсказуемо указывает на другую часть состояния, чем «репозиторий не найден». Проверка исходников не покрывает секреты. При другом FQDN, полном доменном имени, также изменятся свойства привязанных к origin средств WebAuthn; такие различия учитывают по официальной процедуре версии. Изолированная репетиция с новым именем полезна, но её условия нельзя механически перенести на восстановление с прежним именем.

Временная шкала поможет измерить RTO: 10 минут получить образ, 5 минут подготовить конфигурацию, 18 минут вернуть данные, 7 минут контрольных операций дают 40 минут до готовности в этой придуманной модели. Запуск контейнера занял лишь часть этого времени. Если нужного старого образа нет без интернета, время становится неопределённым. Поэтому автономная готовность включает поставки и инструкции возврата, а не один архив.

Обновление проходит маршрут, а не прыжок тега

GitLab публикует upgrade path — маршрут с обязательными промежуточными версиями. На них завершаются необходимые изменения схемы и фоновые миграции. Конкретные остановки определяются исходной/целевой версией и условиями экземпляра; в тексте нельзя навсегда закрепить список для всех будущих переходов. Перед работой проверяют официальный путь и release notes выбранных версий, получают подходящие patch-релизы, а не произвольную первую сборку minor.

Миграция БД меняет структуру либо данные. Background migration выполняет часть изменений после основного обновления через фоновые механизмы. Открывающийся сайт не доказывает её окончания. Переходить к следующей обязательной остановке следует после требуемого завершения и проверок. В этом пути учитывают также PostgreSQL, Redis, Gitaly, Runner и совместимые интерфейсы; отдельный rollout Runner не заменяет миграцию Server.

План возврата после неуспешного обновления

Если новая версия уже изменила схему, вернуть прежний образ поверх изменённой БД часто недостаточно и может быть неподдерживаемо. Реальный rollback может требовать восстановления pre-upgrade backup на прежней версии с прежними секретами и внешними данными. При этом записи, принятые после контрольной копии, требуют отдельного решения. Нулевую потерю нельзя обещать без соответствующего механизма согласования.

Последовательность подготовки: зафиксировать исходный состав, проверить восстановление, выбрать окно и остановить лишнюю изменяющую активность, создать согласованный контрольный резерв, пройти одну остановку, проверить миграции и контрольные операции, затем продолжить. Сначала выполняют весь маршрут на копии. На домашнем ПК не требуется бессмысленно копировать большой GitLab ради каждого абзаца, но перед реальным обновлением собственных важных данных репетиция имеет ясный смысл.

Резерв и реплика решают разные задачи

Реплика повышает доступность при определённых отказах, но может быстро воспроизвести ошибочное удаление или логическую порчу. Backup сохраняет возможность вернуться к прошлой точке. Geo и многокомпонентная HA, high availability, высокая доступность, требуют собственного разбора лагов, переключения и согласования. Их наличие не отменяет отдельного защищённого резерва и проверки восстановления. Для личного обучения сначала достаточно понять эти разные договоры и один раз полностью вернуть собственную небольшую платформу.

Опыт A: настоящий Go и статус неуспеха

python3 tools/ci.py test
python3 tools/ci.py build --version 0.1.0-lab
python3 tools/ci.py verify

Запускайте из собственной копии service. После первой команды существуют reports/tests.jsonl и reports/junit.xml, а код выхода равен нулю. После второй — бинарник и manifest в dist. Третья сверяет файл и запускает его с -version. Она не открывает TCP-порт и не проверяет удалённую сеть. Ключ --version относится к нашему Python-сценарию и задаёт встраиваемую строку, а echo -version — к собранной Go-программе.

Измените ожидание "ready\n" в тесте на заведомо неверное и повторите test. Должен сохраниться отчёт с failure, а код завершения — стать ненулевым. Исправьте ожидание и повторите. Это проверяет всю локальную цепочку «Go → Python → код процесса → XML». Правила GitLab и загрузка отчёта этим ещё не проверены. Скрипт python3 ../check.py, запускаемый из service, выполняет такие проверки в временных копиях и не меняет вашу рабочую программу.

Опыт B: не перепутать результат и имя

Сохраните SHA из manifest. Поменяйте один байт копии бинарника либо добавьте байты в конец и запустите verify: ожидается отказ целостности до исполнения. Затем пересоберите исходную версию. Измените только --version и сравните прежний/новый SHA. Версия — реальный вход линковки, а не декоративная подпись JSON. Сравнение одинаковых версий в разных каталогах можно делать отдельным опытом с одинаковым toolchain и явными остальными входами.

Удалите только выделенные файлы кэша этой копии и повторите правильный путь. Он должен сохранить правильность. Если результат зависит от случайного старого файла вне договорённого входа, сначала исправьте это, а затем измеряйте ускорение. Не очищайте общий Docker или чужие Go-каталоги ради этого упражнения. Пустой кэш — нормальное допустимое состояние, потерянный обязательный артефакт — отдельный отказ.

Опыт C: собственный приватный проект и pipeline

На подготовленном личном GitLab создайте приватный проект и отправьте в него содержимое service. Подготовьте отдельный Runner и метку personal-go. Для Docker executor нужен заранее сохранённый образ Go+Python с зафиксированным идентификатором; задайте его в несекретной project variable LAB_GO_PYTHON_IMAGE. Используйте CI Lint проекта, чтобы проверить итоговую конфигурацию и контекст. Локальный общий YAML-парсер — более узкая проверка.

Первый push ветки без MR должен дать один pipeline: unit и vet, затем build, затем verify. Найдите в каждом job commit SHA и версии инструментов. Скачайте build artifact, сверьте manifest и размер файла, затем проверьте, что verify получил тот же SHA. Не ограничивайтесь одним зелёным значком pipeline. Отдельно откройте JUnit-представление и исходный лог: платформа должна обработать формат, а не просто сохранить архив с названием junit.

Опыт D: таблица событий и границы планирования

Откройте MR и отправьте новый коммит в его исходную ветку. В соответствии с workflow образца должен появиться MR pipeline, а дублирующий branch pipeline — не создаться. Затем создайте учебный тег и отдельно web-запуск. Запишите source и состав каждого графа. Расписание текущая политика намеренно не разрешает. Если нужен schedule, добавьте его как новое явно проверенное правило, а не случайный общий allow в конце.

Остановите только свой менеджер Runner до следующего события. Job должен остаться pending. Верните процесс с тем же частным config: появление выполнения подтверждает границу получения работы. Отдельно попробуйте в своей ветке несуществующую метку и увидите pending даже при свободном Runner. Верните метку. Это другой вид ожидания: нет подходящего кандидата, а не занят подходящий слот.

Опыт E: отказ после тестов

В отдельной учебной ветке исключите путь dist из artifacts build, сохранив команду сборки. Build может успешно скомпилировать файл, но verify не получит обязательный результат и должен завершиться отказом. Исправьте передачу. Затем сломайте тест: build в обычной последовательности не должен стартовать. Эти два опыта дают разные последние успешные границы и не должны лечиться одинаковым retry.

Для проверки прав используйте отдельный неразрешённый клиентский контекст. Приватный проект и его артефакт не должны стать доступны от одного знания URL. Не публикуйте токен в параметрах ссылки. Если понадобится межпроектное получение, настройте минимальный допустимый CI_JOB_TOKEN-маршрут и подтвердите отказ из другого проекта. Сервисный токен с полным API-доступом не нужен для демонстрации принципа.

Опыт F: измерение и возвращение состояния

Соберите несколько сопоставимых прогонов и раздельно запишите очередь, подготовку, script и передачу. Затем измените только один фактор: например добавьте допустимый Go-cache или второй слот при достаточной памяти. Сравните полное время и расход. Размер выборки и холодность первого запуска обозначьте явно; придуманные «нормативы» в секундах здесь не нужны.

Последний отдельный опыт — резерв маленького личного GitLab и восстановление на изолированной совместимой копии. Сохраните исходники и конфигурацию проекта независимо, подготовьте прежнюю точную версию, конфигурацию/секреты и нужные хранилища. Подтвердите вход, Git, issue, artifact и расшифровку предусмотренных данных. До такой репетиции резерв существует как набор файлов, а проверенное восстановление ещё не выполнено.

Итоговая запись, которую полезно оставить себе

Сохраните собственный commit, pipeline/job IDs, SHA артефакта, версии, список проверенных положительных и отрицательных сценариев, измерения и способ вернуть исходную точку. Настоящие токены, private config.toml и архив секретов находятся отдельно от публичных заметок. Следующая глава практикума может использовать тот же проект и стенд: состояние не требуется обнулять, если текущая контрольная точка понятна.

В этой редакции локальные проверки Go, отчёта и артефакта исполнялись автоматически. Реальный GitLab Server, регистрация Runner, серверное применение YAML и JUnit UI здесь не запускались и не заявляются проверенными. При своём прохождении помечайте эти пункты по факту наблюдения. Это позволяет расширять реальную среду постепенно, сохраняя точность учебных выводов.

Словарь в боковой панели также ищет определения во всех остальных томах.

YAML

Текстовый формат структурированных данных с отображениями, списками и скалярами. Сначала парсер получает структуру, затем GitLab интерпретирует её ключи; YAML сам не выполняет shell-команды.

JSON

Текстовый формат структурированных значений: объекты, массивы, строки, числа и другие определённые типы. Совпадение расширения файла с .json не доказывает корректность его содержимого.

XML

Текстовый формат с вложенными элементами и атрибутами. Для JUnit важна поддерживаемая структура и экранирование данных, а не только корректная общая XML-грамматика.

RE2

Семейство реализации регулярных выражений с определённым синтаксисом и ограничениями сложности. В условиях GitLab нельзя автоматически использовать все конструкции PCRE либо JavaScript regex.

FQDN

Fully qualified domain name — полное доменное имя. Имя в URL связано с DNS, проверкой TLS и иногда origin-привязанными средствами входа.

RSS

Resident set size — наблюдаемый объём резидентных страниц процесса в памяти. Он не равен только Go-куче или лимиту одного контейнера и требует осмысленного суммирования общих страниц.

NGINX

Веб-сервер и обратный прокси, используемый в типовой поставке GitLab. Его сокет, передаваемые заголовки и TLS-настройки относятся к входной границе платформы.

Helm

Инструмент получения Kubernetes-манифестов и управления релизами из пакетов chart. Chart GitLab требует понимания компонентов и внешнего состояния, а не автоматически даёт готовую HA-платформу.

Chart

Пакет шаблонов и параметров Helm для описания Kubernetes-ресурсов. Версия chart и версия приложения связаны таблицей совместимости, но не обязаны совпадать численно.

Pod

Единица совместно планируемых контейнеров Kubernetes с определёнными сетевыми и файловыми границами. Временный Pod не делает внешние данные временными и не отменяет выданных ему прав.

SHA-256

Криптографический хеш, отображающий содержимое в 256-битное значение. Сравнение с доверенно ожидаемым хешем проверяет байты; произвольно заменяемая рядом сумма не доказывает происхождение.

Digest

Идентификатор содержимого на основе криптографического хеша в определённом формате. У контейнерного образа относится к манифесту; это другой объект, чем SHA Git-коммита.

SemVer

Semantic Versioning — соглашение о форме и смысле версий major.minor.patch с дополнительными частями. Короткая регулярка для трёх чисел не реализует всю грамматику и политику совместимости.

Minor release

Выпуск с изменением средней части номера в выбранной модели версий. Для GitLab допустимый переход и миграции определяются официальным upgrade path, а не лишь сходством цифр.

Patch release

Исправляющий выпуск внутри выбранной major.minor ветки. При обновлении учитывают актуальные исправления и notes именно целевой ветки.

WebAuthn

Механизм аутентификации с криптографической привязкой к origin сервиса. Восстановление GitLab под другим доменным именем может требовать переоформления таких средств входа.

GitLab

Платформа вокруг Git-репозиториев: пользователи, проекты, обсуждение изменений, CI, пакеты и эксплуатационные данные. Репозиторий Git — лишь одна часть её состояния.

Self-Managed GitLab

Экземпляр, установкой и состоянием которого управляет владелец. Он обслуживает ОС, компоненты, доступ, обновления и резерв; сайт в браузере не переносит эти обязанности поставщику.

GitLab.com

Управляемый сервис GitLab. Его граница ответственности отличается от своего Self-Managed сервера; правила и лимиты сервиса не автоматически равны параметрам домашнего экземпляра.

CE

Community Edition — вариант поставки GitLab. Выбор редакции и конкретной версии влияет на доступные возможности и требования восстановления.

EE

Enterprise Edition — вариант поставки GitLab с моделью доступности функций по подписке. Установка EE не означает получения всех платных возможностей.

Omnibus

Историческое имя комплексной Linux-поставки GitLab: согласованный набор компонентов и средств настройки. Контейнер такой поставки по-прежнему содержит несколько служб.

Gitaly

Служба Git-операций GitLab. Через её интерфейс компоненты получают содержимое и сведения репозитория и выполняют нужные операции; она отличается от PostgreSQL с метаданными платформы.

GitLab Shell

Компонент пути Git over SSH. Связывает запрос Git с установленной ключом личностью и прикладной проверкой разрешений, затем взаимодействует с Git-службами.

Workhorse

HTTP-компонент GitLab, который участвует в передаче запросов и больших данных и разгружает прикладной сервер. Его отказ отличается от ошибки процесса компиляции Runner.

Puma

Сервер Ruby-приложения, обслуживающий прикладные HTTP-запросы GitLab. Рабочие процессы Puma не являются CI-исполнителями пользовательских Go-тестов.

Rails

Среда веб-приложения, на которой построена существенная часть прикладной логики GitLab. Её запросы, фоновые действия и схема БД имеют разные жизненные циклы.

Sidekiq

Механизм фоновых работ приложения GitLab с очередями через Redis. Его служебные задания не следует путать с пользовательскими CI job, которые получает Runner.

Redis GitLab

Компонент для предусмотренных кэшей и очередей платформы. Его роль, сохранение и восстановление определяют по конкретной архитектуре; это не место хранения всех Git-объектов.

Bare repository

Git-репозиторий без обычного рабочего дерева. Серверные объекты и ссылки существуют, хотя каталога редактируемых файлов как в локальной копии разработчика нет.

Unix domain socket

Локальная адресуемая точка обмена между процессами одной ОС. Для pathname-сокета важны путь и права файловой системы; IP-маршрут к другому серверу ему не требуется.

Обратный прокси

Сервер-посредник, принимающий клиентское обращение и направляющий его внутреннему приложению. Правильные внешняя схема, Host, доверенные заголовки и TLS входят в его договор.

external_url

Канонический внешний URL GitLab в конфигурации поставки. Используется платформой при формировании адресов и связанных настроек; Docker port mapping сам его не изменяет.

Loopback

Локальная сетевая область процесса, например 127.0.0.1 для IPv4. В контейнере localhost относится к этому контейнеру, а не автоматически к Docker-хосту.

Port mapping

Переадресация порта хоста к порту контейнера. Не изменяет автоматически канонический URL приложения и не доказывает его готовность.

TLS termination

Место, где завершается клиентское защищённое TLS-соединение. Внутренний участок после прокси требует собственной осмысленной границы доверия.

CA

Certification Authority — удостоверяющая сторона или доверенный корневой материал проверки сертификатов. Публичный сертификат CA и закрытый ключ CA имеют разное назначение и чувствительность.

Liveness

Проверка жизнеспособности процесса по выбранному признаку. Обычно слабее проверки готовности приложения со всеми нужными зависимостями.

Readiness

Проверка готовности экземпляра принимать определённую работу. Состав проверяемых зависимостей должен соответствовать цели; один открытый TCP-порт даёт более слабое свидетельство.

Namespace GitLab

Пространство имён пользователя или группы, организующее проекты и наследование управления. Путь namespace влияет на адреса и границы членства.

Group GitLab

Группа с проектами и возможными подгруппами. Членство и часть политик распространяются вниз согласно настройкам и версии.

Project GitLab

Объект платформы, объединяющий Git-репозиторий, доступ, issue, MR, CI и другие ресурсы. Экспорт одной истории Git не сохраняет все сущности проекта.

Аутентификация

Установление обращающейся личности через сессию, ключ или другой материал. Успешный вход не равен разрешению на любую операцию над любым проектом.

Авторизация

Решение о допустимости конкретного действия установленной личности над конкретным объектом. В нём могут участвовать членство, роль, scope и дополнительные правила.

Scope токена

Именованное ограничение вида действий, доступных материалу аутентификации. Применяется вместе с правами личности; узкое имя токена не заменяет проверку фактического охвата.

Guest

Одна из базовых ролей GitLab с ограниченными полномочиями. Точный доступ зависит от объекта, версии и настроек; роли проверяют по таблице конкретных действий.

Reporter

Базовая роль GitLab для предусмотренного чтения и участия. Она не тождественна праву публиковать любые изменения или управлять CI-секретами.

Developer

Базовая роль GitLab с возможностями разработки в разрешённой области. Допуск к runner-коду при этой роли является существенным доверием к выполняемому script.

Maintainer

Роль с расширенным управлением проектом. Её не следует выдавать только ради обычного запуска тестов; фактические полномочия проверяют отдельно.

Owner

Роль владельца группы с широким управлением её областью. Не является синонимом роли администратора всего экземпляра GitLab.

Protected branch

Ветка, подходящая под настроенные правила ограничения push и merge. Защита имени Git не автоматически защищает все внешние пакеты и среды доставки.

Protected variable

CI-переменная с ограничением выдачи допустимым защищённым контекстам. Получивший её script способен читать значение, поэтому доверие к коду всё равно необходимо.

Merge request

Объект предложения объединить изменение с обсуждением, проверками и условиями принятия. Отличается от Git-коммита и от фактической доставки приложения.

MR pipeline

Конвейер события запроса на слияние. Обычный вариант проверяет исходную ветку, а не автоматически будущий результат объединения с последней целью.

Merged results pipeline

Проверка специально сформированного результата объединения MR с целью, когда функция доступна и включена. Имеет иной набор входов, чем обычный MR pipeline.

Merge train

Механизм очереди принятия изменений с проверками, учитывающими предшествующие изменения. Возможности и условия зависят от выпуска и подписки.

Issue

Запись платформы о задаче, проблеме или решении. Её закрытие и техническая доставка имеют разные условия и свидетельства.

Label

Метка классификации объектов GitLab. Помогает отбору и представлению, но сама не доказывает выполнение внешнего технического действия.

Milestone

Именованная веха организации работы. Связывает задачи с планом и сроком, не заменяя версию бинарника и идентичность артефакта.

Webhook

Исходящий HTTP-вызов для уведомления внешней системы о событии. URL, секрет подписи, повторы и обработка результата требуют отдельного контроля.

Git LFS

Механизм хранения больших файлов отдельно от обычных Git-объектов, где остаются указатели. Копия указателя не доказывает наличие соответствующих байтов на новом сервере.

Подмодуль

Ссылка родительского Git-проекта на конкретный коммит другого репозитория с отдельным получением. Миграция родителя не переносит историю зависимого репозитория автоматически.

CI

Continuous integration — регулярное объединение изменений с автоматизированными проверками. Конкретный зелёный результат относится к выполненному набору входов и условий.

Pipeline

Отдельный конвейер GitLab: созданный по событию граф заданий с выбранным коммитом и конфигурацией. Существование pipeline не означает, что его команды уже исполняются.

Job

Единица работы конвейера с условиями, зависимостями, средой, script и результатом. Несколько job одного pipeline не разделяют автоматически один рабочий каталог.

Stage

Этап CI, задающий обычные барьеры продвижения между группами заданий. Возможная параллельность внутри этапа ограничивается реальными подходящими ресурсами.

DAG

Directed acyclic graph — ориентированный граф без циклов. В CI вершины обозначают задания, а направленные зависимости определяют возможность начала работы.

Needs

Явные зависимости CI-задания. Позволяют начать работу по готовности нужных поставщиков и управляют получением их артефактов в поддерживаемой модели.

Dependencies CI

Ключ выбора артефактов предшествующих заданий. Его назначение отличается от needs, которое влияет и на порядок исполнения.

Workflow rules

Упорядоченные правила создания pipeline целиком. Вычисляются раньше правил отдельных заданий и способны исключить запуск независимо от их script.

Job rules

Упорядоченные правила добавления задания и выбора его свойств. Применяется первое совпадение; данные будущего script ещё не существуют.

CI_PIPELINE_SOURCE

Предопределённый вид события конвейера: push, MR, расписание, web и другие поддерживаемые значения. Имя ветки не заменяет источник события.

CI_COMMIT_SHA

Идентификатор коммита, выбранного для CI-контекста. Полезен для происхождения результата, но отдельно учитывают изменённые после checkout файлы.

CI_COMMIT_REF_SLUG

Нормализованная строка имени ссылки для ограниченных имён. Не является уникальным хешем исходников и может совпасть у разных исходных написаний.

Include CI

Подключение файлов конфигурации при вычислении pipeline. Это получение входов графа, а не создание дочернего конвейера во время исполнения.

Extends

Наследование CI-конфигурации согласно правилам GitLab. Списки не обязательно объединяются; замена rules или script может целиком заменить соответствующее поведение.

Default CI

Поддерживаемые значения по умолчанию для заданий. Не является универсальным глубоким объединением любых полей YAML.

CI Lint

Серверная проверка конфигурации GitLab с предусмотренными режимами. Локальный общий YAML-парсер не подтверждает ту же семантику и контекст доступа.

Child pipeline

Отдельный дочерний конвейер того же проекта, запускаемый родительским trigger. Имеет собственный граф и статус; обычный include только подключает конфигурацию в один граф.

Downstream pipeline

Конвейер, запускаемый другим конвейером; может быть дочерним или межпроектным. Передача статуса, переменных, разрешений и артефактов должна быть задана явно.

Bridge job

Связующее trigger-задание, создающее downstream pipeline. Его успешное создание не всегда означает успешное завершение всей downstream-работы.

Runner

Программа получения и исполнения CI-работ от GitLab. Её полномочия и executor определяют, какие файлы, сеть и ресурсы получит script.

Runner manager

Работающий процесс управления Runner на машине. Его не следует автоматически отождествлять с одной строкой регистрации, одной VM или одним CPU.

Executor

Способ подготовки среды и запуска процессов Runner: shell, Docker, Kubernetes и другие. Каждый задаёт свои границы файлов, ядра, сети и доверия.

Shell executor

Исполнение команд с правами пользователя Runner в его ОС. Отдельный рабочий каталог не изолирует остальные доступные пользователю данные и сеть.

Docker executor

Подготовка job в контейнерной среде Docker согласно настройкам Runner. Общее ядро, privileges, socket и bind mount определяют реальную изоляцию.

Kubernetes executor

Создание среды job через Kubernetes. Права API, service account, namespace, тома и сетевые политики становятся частью доверия.

Runner tags

Метки подбора Runner для job. Требуются все перечисленные метки задания; метка не устанавливает программу и не доказывает фактическое свойство машины.

Concurrent

Общий предел одновременно исполняемых job процесса Runner. Его увеличение не добавляет CPU и RAM и не равно request_concurrency.

Runner limit

Собственное ограничение одновременной работы одной конфигурационной записи Runner. Действует вместе с общим concurrent и реальными ресурсами executor.

Request concurrency

Предел одновременных запросов Runner за новой работой. Описывает получение job, а не число ядер и не прямой предел внутренней параллельности Go.

Long polling

Длительное ожидание ответа на запрос получения работы. Снижает частоту пустого опроса, но взаимодействует с лимитами одновременно ожидающих запросов.

Runner authentication token

Секрет связи Runner с зарегистрированной конфигурацией. Хранится в частном config.toml; отличается от токена CI-задания и персонального пароля.

Config.toml Runner

Конфигурация менеджера GitLab Runner: регистрации, executor, лимиты и секреты связи. Не предназначена для публикации в репозитории проекта.

Workspace

Рабочая файловая среда конкретной работы. Её сохранение и очистка зависят от Runner и executor; она не является долговременным реестром выпуска.

CI_PROJECT_DIR

Полный путь каталога проекта в контексте job. Не обязан совпадать с каталогом разработчика и определяется подготовленной средой Runner.

GIT_STRATEGY

Политика получения исходников Runner. Clone, fetch и none имеют разные предусловия и не дают одинаковых гарантий чистоты рабочего каталога.

GIT_DEPTH

Ограничение глубины получаемой Git-истории. Влияет на передачу и операции с предками/тегами; небольшой clone не содержит автоматически всю историю проекта.

Before_script

Подготовительные команды основной shell-части job. Обычно разделяют контекст с script, в отличие от отдельной части after_script.

After_script

Отдельная shell-часть завершения job с собственными условиями и лимитами. Не является транзакционным откатом и не гарантируется при любом уничтожении машины.

Exit status

Код завершения процесса. Он должен сохраняться через обёртки и shell; текст успешного сообщения или корректный XML не заменяют ненулевой статус ошибки.

Pipefail

Режим поддерживающей оболочки, позволяющий учесть неуспех компонентов shell-конвейера. Без него успешный tee может скрыть ошибку предшествующего теста.

Service CI

Дополнительная служба задания, например контейнер PostgreSQL. Её сетевое имя, готовность и исходные данные требуют проверки отдельно от создания контейнера.

Privileged container

Контейнер с существенно расширенными полномочиями. Меняет границу изоляции и не требуется для обычного выполнения Go-компилятора.

Docker socket

Интерфейс управления Docker daemon. Передача его job может дать управление контейнерами, томами и доступными ресурсами хоста, несмотря на внешний контейнерный вид задания.

Service account

Служебная личность выполнения, например в Kubernetes. Выданные ей разрешения определяют действия кода и не уменьшаются от краткого срока жизни Pod.

Masked variable

Переменная, значение которой стараются скрывать при отображении журнала. Не защищает от кода, преобразующего значение или передающего его по сети/в артефакте.

Hidden variable

Настройка ограничения последующего просмотра значения в UI. Получающий переменную процесс по-прежнему может прочитать и использовать её.

File variable

CI-переменная, материализованная в временный файл; значение окружения указывает путь. Сам файл требует защиты и не должен случайно попадать в архив.

Environment scope

Ограничение применимости переменной к именам окружений. Не является самостоятельной изоляцией от произвольного кода разрешённого задания.

Dotenv report

Поддерживаемый отчёт с данными переменных для последующих работ. Возникает после исполнения producer и не способен менять уже вычисленные rules этого pipeline.

CI_JOB_TOKEN

Ограниченный токен работающего job для поддерживаемых операций GitLab. Учитываются права инициатора, время жизни, разрешённые endpoints и допуск целевого проекта.

Allowlist

Явный список разрешённых источников или целей доступа. Он задаёт одну границу решения и не должен восприниматься как автоматическое предоставление всех прав.

OIDC

OpenID Connect — протокол установления доверия к личности через подписанные утверждения издателя. В CI позволяет запрашивать краткоживущие внешние полномочия для определённого job.

ID token

Подписанное удостоверяющее утверждение GitLab о job для выбранного получателя. Требует проверки подписи, издателя, аудитории, срока и нужных ограничений.

JWT

JSON Web Token — формат представления утверждений и связанной защиты. Чтение закодированного JSON без криптографической проверки не доказывает подлинность.

Claim

Поле утверждения токена, например проект, ссылка, издатель или срок. Политика получателя должна проверять нужные поля, а не только существование токена.

Audience

Поле aud с назначенным получателем токена. Ограничивает, какая служба должна принимать это утверждение; проверяется вместе с подписью и остальными условиями.

Issuer

Поле iss, обозначающее доверенного издателя токена. Одного совпадения iss недостаточно, если разрешение должно относиться лишь к конкретному проекту и ссылке.

Cache CI

Набор восстанавливаемых файлов для ускорения. Его отсутствие не должно ломать правильную сборку; это не обязательный канал передачи выпускного бинарника.

Cache key

Идентификатор набора CI-кэша. Совпадение ключа допускает совместное использование архива согласно backend и политике, но не является доказательством пригодности каждого внутреннего файла.

Cache policy

Направление использования кэша: pull, push или pull-push. Несколько писателей общего ключа не образуют согласованную общую файловую систему.

GOCACHE

Каталог кэшированных вычислений инструментов Go. Правильность повторного использования определяет Go; CI может дополнительно доставлять файлы каталога как внешний архив.

GOMODCACHE

Каталог загруженных Go-модулей. Отличается от выбранного графа зависимостей и кэша компиляции.

Artifact

Сохранённый набор файлов определённого job. Его получение, срок и права важны отдельно от создания исходного файла в workspace.

Expire_in

Заявленный срок артефакта в конфигурации CI. Дополнительные правила удержания экземпляра могут влиять на фактическое удаление.

Package Registry

Реестр именованных и версионированных пакетов. Подходит для потребляемых после pipeline результатов с явной политикой публикации и хранения.

Generic package

Файловый пакет GitLab с выбранными именем и версией. Повторная публикация и контроль целостности требуют явной политики.

Container Registry

Хранилище контейнерных манифестов и слоёв. Не запускает контейнеры само; хранение образа и работа процесса являются разными действиями.

Image digest

Хеш конкретного содержимого образа/манифеста. Позволяет фиксировать результат точнее, чем изменяемый tag; выбранная целевая платформа всё равно имеет значение.

Image tag

Именованный указатель контейнерного реестра. Имя latest или stable может позже указывать на другие байты.

Manifest выпуска

Сохранённая запись об идентичности артефакта: файл, размер, SHA, версия, исходники и инструменты. Его подлинность требует собственного доверия к источнику.

Provenance

Сведения о происхождении результата: из каких входов, каким инструментом и в каком процессе он получен. Хеш файла подтверждает байты, но сам по себе не доказывает эту историю.

JUnit XML

Поддерживаемое структурированное представление результатов тестов. Обработка отчёта интерфейсом не заменяет сохранение ненулевого кода ошибки script.

JSONL

Последовательность независимых JSON-значений по строкам. Вывод go test -json имеет событийную семантику и не является JUnit XML после переименования файла.

Coverage

Покрытие выбранных инструментированных участков исполнением тестов. Знаменатель и набор входов важны; высокий процент не доказывает полноту требований.

Flaky test

Проверка с нестабильным исходом при одинаковых существенных входах из-за неконтролируемого времени, порядка, внешнего состояния или ресурсов. Retry не устанавливает её причину.

SAST

Static application security testing — статический анализ определённых свойств безопасности кода. Имеет ограниченный охват и зависит от правил/версии анализатора.

DAST

Dynamic application security testing — исследование работающего приложения внешними действиями. Требует известной цели, её состояния и допустимого набора проверок.

Dependency scanning

Проверка выбранных зависимостей относительно поддерживаемой базы и модели использования. Версия базы и реальные входы ограничивают вывод.

Secret detection

Поиск признаков опубликованных секретов. Отсутствие находки не является разрешением помещать токены в исходники, лог или артефакты.

SonarQube

Отдельная платформа анализа кода с сервером, хранилищем, сканером и собственной политикой качества. Отправка отчёта и итог асинхронной обработки — разные события.

Quality gate

Набор условий решения о допустимости показателей качества. Имеет смысл вместе с областью анализа, базой сравнения и завершённой обработкой отчёта.

Environment GitLab

Именованная цель развёртывания с историей соответствующих действий. Само поле environment не создаёт инфраструктуру и не меняет работающий процесс.

Deployment

Запись действия доставки в окружение. Требуется отдельно подтвердить фактическую версию, готовность и свойства работающего сервиса.

Release GitLab

Объект описания выпуска с метаданными и ссылками. Не содержит автоматически все бинарники и не гарантирует неизменность внешнего latest.

Promotion

Продвижение ранее выбранных проверенных байтов в следующую среду. Отличается от независимой пересборки того же тега.

Resource group

Механизм последовательного допуска связанных CI-заданий к одному логическому ресурсу. Сериализация не задаёт автоматически порядок версий и межпроектный глобальный замок.

Interruptible

Свойство допуска автоматической отмены устаревшей CI-работы по поддерживаемой политике. false не защищает от отказа машины, timeout или ручной отмены.

Retry

Повтор job согласно заданной политике. Для внешнего изменяющего действия требует проверки уже выполненного эффекта и пригодности повторения.

Идемпотентность

Свойство повторного действия приводить к тому же желаемому состоянию без нежелательного дополнительного эффекта. Не следует предполагать его у любого deploy или API-запроса.

Rollback

Возврат к выбранному прежнему состоянию. Для приложения и данных это разные операции; прежний бинарник не возвращает автоматически старую схему БД.

Graceful shutdown

Ограниченное штатное завершение процесса с прекращением новой работы и ожиданием нужных текущих операций. Один сигнал не гарантирует завершения всех внешних действий.

Критический путь

Самая длинная необходимая цепочка зависимостей выполнения. Время pipeline определяется не суммой всех параллельных job, а графом и фактическим доступом к ресурсам.

RPS

Requests per second — число запросов в секунду в определённой границе. Состав и тяжесть запросов важны; один RPS не означает одинаковой работы CPU или диска.

Throughput

Пропускная способность: число завершённых единиц работы за интервал при известных условиях. Не равна задержке одной работы или размеру очереди.

p95

Оценка 95-го процентиля выбранного набора наблюдений. Требует достаточной серии, одинаковой границы и понимания смешанных типов работ.

Закон Литтла

Связь L=λW между средним числом работ, устойчивой интенсивностью и средним временем внутри одной согласованной границы. Не заменяет анализ растущей неустойчивой очереди.

OOM

Out of memory — отказ выделения или завершение процесса при исчерпании соответствующего бюджета памяти. Общий параллелизм job и внутренних процессов влияет на него.

Correlation ID

Идентификатор сопоставления связанных записей нескольких компонентов. Помогает восстановить путь запроса при согласованном времени и сохранённых журналах.

RPO

Recovery point objective — допустимая потеря последних данных по времени. Периодичность backup и фактическая согласованность определяют достижимое значение.

RTO

Recovery time objective — допустимое время восстановления заданной услуги. Включает получение инструментов, возврат данных, проверки и открытие клиентского доступа.

Gitlab-secrets.json

Чувствительный файл ключевых материалов Linux-поставки GitLab. Для расшифровки соответствующих сохранённых полей нужна согласованная копия; стандартный прикладной backup не заменяет её.

Upgrade path

Поддерживаемый маршрут обновления с обязательными промежуточными версиями и проверками. Смена тега прямо на произвольную новую версию не гарантирует допустимости миграции.

Background migration

Фоновое преобразование данных после основного обновления GitLab. Открытый UI не доказывает его окончания и готовности к следующей обязательной остановке.

GitLab Geo

Механизмы географически разделённой репликации/восстановления платформы. Имеют собственные лаги и условия переключения и не заменяют защищённые копии прошлых состояний.

HA

High availability — высокая доступность при определённых отказах. Конкретная гарантия зависит от доменов отказа и процедуры переключения; это не синоним наличия backup.
