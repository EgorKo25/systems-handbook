Перенос проекта и принятие изменений: что едет вместе с Git

Смена адреса origin переносит направление обмена, а импорт платформы — набор прикладных сущностей. Проследим эти операции отдельно и свяжем результат ревью с точным состоянием, которое проверяет CI.

Переносится репозиторий или рабочий процесс

Локальный Git хранит объекты, ссылки, конфигурацию и рабочие файлы. GitLab дополнительно хранит задачи, комментарии, участников, правила, CI-переменные, артефакты, пакеты и webhooks. Webhook — исходящий HTTP-вызов, которым платформа уведомляет выбранную систему о событии. При смене Git remote комментарии не превращаются в Git-объекты. Поэтому миграция начинается с перечня сохраняемых сущностей, а не с одной команды push.

Есть разные механизмы: перенос Git-истории, импорт из поддерживаемой площадки и экспорт/импорт проекта GitLab. Полнота импорта зависит от пары источника и назначения, версий, настроек и разрешений. Секреты и некоторые интеграции могут требовать отдельного переноса. Прежде чем выключать старую систему, на копии проверяют заранее выбранные ссылки, крупные файлы, wiki, нужные обсуждения и фактическую работу автоматизации. Число видимых проектов не является проверкой полноты.

Обычный перенос собственной ветки

git remote -v
git remote add destination ssh://git@gitlab.example.invalid/study/api.git
git push destination main
git push destination --tags

Адрес example.invalid — намеренно неработающий пример, его заменяют адресом своего проекта. Новый remote destination позволяет сначала проверить получателя, сохранив прежний origin. Отправка main переносит нужные для неё объекты и предложение обновить одно имя; отдельная --tags передаёт теги. Эти команды не обещают перенести все существующие ветки или большие объекты LFS. Выберите явный набор веток и убедитесь, что их вершины совпали с ожидаемыми идентификаторами.

git push --mirror — другой договор: зеркальная синхронизация ссылок, включая возможное удаление или принудительное изменение ссылок назначения. Это не синоним «отправить всё аккуратно». Её используют только для подготовленной цели и понятного набора ссылок, обычно из отдельной bare-копии. Наличие локальных remote-tracking refs и служебных refs платформы дополнительно меняет смысл. Для простого собственного проекта явные ветки легче проверить.

После подтверждения приёма можно изменить обычный origin через git remote set-url origin .... Это локальная настройка адреса, а не команда сервера мигрировать данные. Проверяют также отдельный push URL, если он настроен. Бывший секретный токен в URL не следует переносить в новый конфигурационный файл или публичный журнал: способы хранения доступа настраивают отдельно.

LFS, подмодули и адреса внутри исходников

Git LFS хранит в обычной истории указатели на большие объекты, а сами байты передаёт отдельным механизмом. Успешное клонирование указателей не доказывает, что все большие файлы доступны на новом сервере. Нужно получить требуемый набор LFS-объектов с прежнего источника и перенести его в подготовленную цель, затем проверить чистую копию, не использующую старый локальный LFS-кэш. Отсутствие сети после миграции быстро выявляет, какие данные считались сохранёнными лишь по внешнему виду каталога.

Подмодуль записывает конкретный коммит другого репозитория и адрес в .gitmodules. Перенос родительского проекта не переносит историю подмодуля. Аналогично Go module path и private dependency URL могут сохранять прежний домен. Составьте карту зависимостей и проверяйте получение из чистой среды Runner. Запуск на старой машине с прогретым кэшем способен скрыть отсутствующий доступ и неправильное имя.

Что именно проверяет запрос на слияние

У MR есть исходная и целевая ветки. Обычный merge request pipeline проверяет состояние, которое GitLab определил для соответствующего типа конвейера; оно не автоматически равно будущему результату объединения с последней main. Merged results pipeline строит специальный результат объединения для проверки, когда функция доступна и включена. Merge train организует очередь принятия с учётом предшествующих изменений. Доступность этих механизмов проверяют по тарифу и выпуску.

Рассмотрим два MR: один меняет контракт ответа, другой — обработку того же поля. Каждый проходит тесты относительно прежней main. После последовательного слияния второму может понадобиться проверка обновлённого сочетания. Зелёный значок относится к конкретному набору входов; пересозданная ветка или изменившаяся цель могут сделать свидетельство устаревшим. Полезно показывать коммит конвейера, источник запуска и состояние принятия рядом, а не сводить всё к одному цвету.

Задачи, обсуждения и жизненный цикл выпуска

Issue — запись о работе, проблеме или решении. Label — метка для классификации, milestone — обозначенная веха, доска — представление отобранных задач. Перетаскивание карточки не является техническим переключением трафика и само по себе не меняет код. Для небольшой команды достаточно малого числа статусов, если понятны критерии переходов. Увеличивать число колонок без различимых решений не полезнее, чем добавлять лишние стадии CI.

Связь MR с issue может быть обычной ссылкой либо специальной закрывающей ссылкой. Автоматическое закрытие зависит от поддерживаемого синтаксиса, целевой ветки и состояния принятия; простое закрытие MR без слияния не следует считать успешным выполнением задачи. В собственном процессе отдельно фиксируют «код принят», «артефакт проверен», «выпуск доставлен» и «результат подтверждён». Одна issue может собирать эти свидетельства, не подменяя их.

Контрольная точка миграции

В новой чистой копии проверьте вершины нужных веток и тегов, присутствие больших файлов, подмодулей и самостоятельную сборку. Затем проверьте read-only и изменяющее действие обычного участника, доступ CI к зависимостям, сохранение артефакта и ссылки внешних систем. Только после сравнения договорённого набора решают, что прежний источник больше не нужен для текущей работы. Его резерв и условия хранения определяются отдельно от смены рабочего URL.

Для учебного опыта достаточно двух собственных локальных bare-репозиториев и личного GitLab-проекта. Введите контрольный тег, отдельную неслитую ветку и обычный файл, который отсутствует в main. Простой push main предсказуемо не переносит эту отдельную ветку. Этот опыт показывает границы операции без обращения к чужому учебному сервису и без разрушительного зеркального push в существующий рабочий проект.
