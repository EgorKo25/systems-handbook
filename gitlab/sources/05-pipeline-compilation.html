Описание CI превращается в граф, а не исполняется построчно

Между YAML-файлом и первой командой есть отдельная стадия вычисления конфигурации. На ней выбираются входы, подключаются шаблоны, вычисляются правила и создаются зависимости. Здесь исправляют ошибки, которым ещё неоткуда появиться в журнале оболочки.

Три языка и три момента

В YAML запись stage: check связывает ключ stage со строковым значением check. Отступ помещает эту пару внутрь задания; список пишется строками с - или в квадратных скобках, например [check, build]. Это данные для GitLab, а не последовательность исполняемых инструкций YAML. Имя задания, например unit, выбирает автор; ключ script имеет заданный GitLab смысл — список команд. Эти различия понадобятся уже для первого фрагмента.

В типичном конвейере встречаются YAML, выражения GitLab и язык оболочки. YAML определяет структуру данных: отображения, списки и строки. GitLab интерпретирует ключи workflow, rules, needs и другие согласно своей модели. Позднее Runner передаёт строки script оболочке, а та разбирает кавычки, переменные, перенаправления и запускает программы. Равные символы доллара в разных местах не гарантируют одинаковый момент подстановки.

В результате возможны три разных отказа: файл не является допустимым YAML; YAML допустим, но конфигурация CI противоречива; граф создан, но команда вернула неуспех. Для первой причины нужен структурный разбор, для второй — CI Lint и понимание графа, для третьей — журнал исполненного процесса. Перебор версий Go при ошибке отсутствующей зависимости в графе не касается того слоя, где произошёл отказ.

Что сервер сохраняет для запуска

Создание конвейера связано с событием, проектом, выбранной ссылкой и коммитом. Конфигурация собирается из корневого файла и разрешённых подключений. Include — подключение другого файла описания. Он может находиться в том же репозитории, в другом проекте или в поддерживаемом внешнем источнике. Внешняя конфигурация становится входом вычисления графа; её изменение способно изменить проверки, даже если Go-код остался прежним.

Для повторяемости удалённые шаблоны связывают с конкретным неизменяемым коммитом либо другим проверенным идентификатором. Имя ветки main у общего шаблона — движущаяся цель. Новый pipeline может получить другую конфигурацию. Retry отдельного задания в уже созданном конвейере и создание нового pipeline — разные действия; они не обязаны заново разрешать внешние входы одинаковым образом. При разборе сохраняют ссылку на фактическую объединённую конфигурацию данного запуска.

Этапы задают барьеры

Первые фрагменты ниже — разбор построения графа, не законченная инструкция запуска CI. Для выполнения ещё потребуются зарегистрированный Runner, доступный ему Go, рабочая копия учебного проекта и передача файлов между заданиями. Получение среды и регистрация идут в главе Runner, полный проверяемый Go-конвейер — в главе о сборке. Пока предскажите только, какая вершина имеет право начать работу.

stages: [check, build, verify]

unit:
  stage: check
  script: ["go test -count=1 ./..."]

vet:
  stage: check
  script: ["go vet ./..."]

build:
  stage: build
  script: ["go build -o dist/echo ./cmd/echo"]

smoke:
  stage: verify
  script: ["./dist/echo -version"]

stages задаёт порядок этапов. В обычной модели без дополнительных зависимостей следующий этап ждёт допустимого завершения предыдущих. unit и vet могут быть готовы одновременно, но реальная параллельность зависит от доступных исполнителей. YAML не создаёт процессорные ядра. Фрагмент пока намеренно неполон: файлы dist между заданиями не передаются автоматически. Для smoke нужен артефакт build; передача будет добавлена в главе о хранении.

Needs задаёт конкретные зависимости

needs описывает зависимости задания от других заданий. Такой DAG, directed acyclic graph, ориентированный граф без циклов, позволяет запускать готовые вершины, не ожидая весь предыдущий этап. Если документация строится десять минут, а бинарник готов за минуту, проверка бинарника может начать работу сразу после нужной сборки. Ускорение возникает от удаления лишнего ожидания, а не от ускорения компилятора.

smoke:
  stage: verify
  needs:
    - job: build
      artifacts: true
  script:
    - ./dist/echo -version

Здесь зафиксированы две связи: smoke ждёт build и получает его артефакт. Без needs загрузка артефактов по умолчанию может охватывать предыдущие этапы; с needs важно явно понимать выбранных поставщиков. Не смешивайте на одном задании needs и dependencies без понимания поддерживаемой семантики: это разные средства выбора исполнения и передачи файлов. Лучше оставить один ясный договор.

Есть обязательная обратная сторона этой связи: производитель build должен объявить сохраняемый файл. К нему из первого фрагмента нужно добавить artifacts: {paths: [dist/echo]}. Иначе needs: artifacts: true разрешит получение существующих артефактов, но не создаст файл в хранилище сам. Артефакт — сохранённый выход задания; после завершения build Runner загрузит объявленные файлы, а перед smoke скачает их в его рабочую копию. На этой границе возможен отдельный отказ загрузки или скачивания при уже успешной компиляции. Срок хранения и подробный путь файла раскрыты в главе хранения.

needs: [] означает отсутствие таких ожиданий и может разрешить ранний старт. Пустой список не означает «зависит от всех». Если upstream-задание исключается правилами, обычная обязательная связь способна сделать граф несоздаваемым. optional: true допускает отсутствие вершины, но не доказывает, что потребителю действительно можно работать без её данных. Отсутствующий обязательный артефакт нельзя вылечить одним словом optional.

Повторное использование без скрытой подмены

Задание с именем, начинающимся с точки, например .go-defaults, служит скрытым шаблоном и само не запускается. extends наследует конфигурацию по правилам GitLab; списки не следует считать автоматически склеиваемыми. Переопределённый script или rules может заменить родительский список целиком. default задаёт поддерживаемые значения по умолчанию для заданий, но также не является произвольным глубоким объединением любого вложенного поля.

YAML-якорь и alias работают на уровне YAML-документа; extends — на уровне конфигурации GitLab и может использовать подключённые определения. Разница важна для нескольких файлов. При сомнении исследуют расширенное описание, а не визуальное сходство исходников. Разумный шаблон сокращает повторение и оставляет видимыми версию образа, полномочия, передачу данных и условия запуска конкретного задания.

Пройти объединение двух файлов на конкретных значениях

Пусть корень подключает ci/go.yml того же коммита и задаёт default: {image: "tools:approved"}. Подключённый файл содержит шаблон .base с script: ["go test ./..."] и rules: [{if: '$CI_COMMIT_BRANCH'}]. Задание unit делает extends: .base, но задаёт свой script: ["python3 tools/ci.py test"]. Итоговый unit получает образ по default и свой script; родительский go test не становится дополнительной первой командой. Список script заменён, а не склеен.

Теперь добавим unit собственные rules только для merge_request_event. Родительский список условий не остаётся «на всякий случай»: итоговая политика unit стала MR-only. Если build существует на push обычной ветки и требует обязательный needs: [unit], такой push может получить ошибку создания графа из-за отсутствующей вершины. Это происходит до запуска Runner, поэтому журнал Python здесь не появится. Исправление — согласовать области существования обязательных producer/consumer, а не вслепую поставить optional. Если build допустим без unit, это уже другое инженерное требование, которое нужно назвать явно.

Проследите четыре снимка: исходные файлы коммита C17; объединённое описание после include и наследования; набор вершин после rules данного события; доступные к выполнению вершины после зависимостей. На каждом снимке найдите unit, его script, образ и правило. В CI Lint/редакторе своего проекта сохраните итоговое expanded-представление и сравните с прогнозом. Так обнаруживаются скрытые замены списков и отличия удалённого шаблона без единого исполнения пользовательского кода.

Include и дочерний конвейер имеют разные жизненные циклы

integration-child:
  stage: check
  trigger:
    include:
      - local: ci/integration-child.yml
    strategy: mirror

Этот фрагмент для поддерживающей strategy: mirror версии создаёт отдельный child pipeline. Его include находится внутри trigger: это описание нового графа, а не простое включение job в родительский. Child обычно использует тот же проект, ref и commit; source у него parent_pipeline. Если его собственный workflow допускает только push, он может отвергнуть создание, хотя родитель был создан push. Серверная фаза нового конвейера снова имеет свои условия.

Bridge, связующее trigger-задание, без явно выбранной подходящей стратегии может считать достаточным успешное создание downstream. Тогда зелёный родитель ещё не свидетельствует об окончании проверок потомка. mirror связывает результат с downstream по предусмотренной семантике текущей версии; на старой версии проверяют поддерживаемый вариант, а не заменяют ключ наугад. Ручные блокирующие job потомка и правила допустимого неуспеха тоже влияют на итог.

Multi-project pipeline, межпроектный конвейер, выполняется в другом проекте, со своими правами, ref и конфигурацией. Он не получает автоматически артефакты родителя от одного существования связи trigger. Передача переменных, inputs, CI_JOB_TOKEN-допуск и получение файлов задаются отдельно. Не передавайте весь набор pipeline variables без анализа: так параметр или секрет, предназначенный одному графу, может попасть в иной контекст. Для простого личного Go-проекта один понятный граф предпочтительнее искусственного дерева, но при независимых компонентах это различение становится необходимым.

Как проверять ещё не исполнявшийся конвейер

CI Lint — серверная проверка конфигурации GitLab, доступная через интерфейс и API. Она умеет больше обычного YAML-парсера, но её результат также зависит от режима проверки, выбранной ссылки и доступа к подключаемым файлам. При необходимости используют моделирование создания конвейера в контексте своего проекта. Разбор PyYAML в локальном практикуме доказывает лишь структуру YAML и наши собственные инварианты примера; он честно не выдаётся за CI Lint.

Для каждого задания ответьте: почему оно существует в этом событии, каких завершений ждёт, какие файлы получает, какой Runner подходит и какие полномочия будут переданы. Затем нарисуйте один неуспех. Если обязательный тест исчезает из графа без видимого нарушения, конфигурация недостаточно описывает намерение. Если артефакт нужен, но связь содержит лишь порядок этапов, нужно проверить и передачу данных. Граф управления и граф данных связаны, но не совпадают автоматически.
