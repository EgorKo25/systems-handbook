Кэш, артефакт, пакет и образ: четыре разных договора хранения

Ускорение повторной работы и сохранение выпускного результата требуют разных гарантий. Пройдём путь одного бинарника и кэша Go, чтобы файл не исчез после удачного job и не подменился при следующем запуске.

Что считается обязательным результатом

Кэш — восстанавливаемые данные для ускорения. Его отсутствие не должно лишать сборку способности выполнить правильную работу. Артефакт job — сохранённые файлы конкретного задания, которыми пользуется следующий шаг или человек. Package Registry хранит именованные версионированные пакеты для дальнейшего потребления; Container Registry — образы контейнеров с манифестами и слоями. Release — объект описания выпуска, часто со ссылками. Ссылка release не содержит бинарник автоматически.

Бинарник для доставки нельзя передавать только через cache. Кэш может отсутствовать на другом Runner, быть вытеснен, оказаться недоступным или перезаписанным подходящим ключом. Если доставка молча берёт «что нашлось», система теряет связь между проверенной сборкой и выпускаемыми байтами. Обязательные данные передают через артефакт известного задания либо через зафиксированный пакет с проверяемым digest.

Два кэша Go и один внешний архив

GOMODCACHE хранит полученные модули, GOCACHE — результаты вычислений сборочного инструмента. Сам Go определяет пригодность кэшированного результата по своим входам. GitLab cache — внешняя доставка выбранных файлов между работами. У этих слоёв разные ключи и проверки: наличие архива CI не означает, что Go повторно использует каждую его запись. Подробная внутренняя модель Go-кэша находится в отдельном томе Go.

variables:
  GOPATH: "$CI_PROJECT_DIR/.cache/gopath"
  GOMODCACHE: "$CI_PROJECT_DIR/.cache/gopath/pkg/mod"
  GOCACHE: "$CI_PROJECT_DIR/.cache/go-build"

cache:
  key: "go-lab-${CI_COMMIT_REF_SLUG}"
  paths:
    - .cache/gopath/pkg/mod/
    - .cache/go-build/
  policy: pull-push

Пути cache находятся внутри проекта, поэтому каталоги инструментов явно перенесены туда. CI_COMMIT_REF_SLUG — нормализованное имя ссылки, пригодное для ограниченных имён, но не уникальный идентификатор содержимого: разные исходные имена могут нормализоваться сходно. В примере кэш допускается как ускорение. Для сложной матрицы в ключ добавляют версию toolchain, платформу и другие границы совместного использования. Версионный идентификатор Go задают своим обычным CI-параметром; CI_JOB_IMAGE не следует считать безопасной универсальной строкой для любого ключа.

policy: pull только получает кэш, push только сохраняет, pull-push делает оба действия в допустимом пути. Несколько параллельных писателей одного ключа могут сохранять разные снимки; это не общая согласованная файловая система. Часто один подготовительный job пишет, остальные читают. Отдельно проверяют разделение protected/non-protected контекстов, backend Runner и политику срока хранения. Случайный общий архив нельзя превращать в канал доверенной передачи кода между проектами.

Артефакт создаётся загрузкой, а не существованием файла

build:
  stage: build
  script:
    - python3 tools/ci.py build
  artifacts:
    name: "echo-${CI_COMMIT_SHA}"
    paths:
      - dist/echo
      - dist/manifest.json
    expire_in: 7 days

verify:
  stage: verify
  needs:
    - job: build
      artifacts: true
  script:
    - python3 tools/ci.py verify

После успешной основной работы Runner собирает подходящие файлы и загружает их в GitLab. Ошибка загрузки, превышение лимита, неверный путь или окончание срока создают отдельные причины отсутствия результата. Имя архива помогает человеку, но не заменяет привязку к job ID и SHA. expire_in задаёт желаемый срок согласно правилам экземпляра; удержание последних успешных артефактов может продлить фактическое хранение. Для обязательного длительного выпуска заранее выбирают подходящее реестровое хранение.

Потребитель получает только перечисленный договором набор. Проверка читает manifest и вычисляет SHA-256 бинарника перед запуском. Manifest связывает имя файла, размер, хеш, исходную ревизию, toolchain и выбранную цель. Хеш доказывает соответствие байтам, а подлинность manifest требует собственной доверенной цепочки. Если злоумышленник способен заменить и файл, и контрольную сумму в том же недоверенном месте, одно равенство SHA не доказывает происхождение.

Отчёты и обычные файлы

artifacts:paths даёт доступ к файлам, а artifacts:reports сообщает GitLab, какой поддерживаемый формат нужно обработать и показать как отчёт. go test -json выдаёт поток JSON-событий, а JUnit ожидает XML определённой структуры. Переименование tests.jsonl в junit.xml не меняет формат. Нужен корректный преобразователь с явной обработкой неуспеха и незавершённого прогона.

Отчёт покрытия, лог теста и бинарник имеют разные права и сроки. В тестовом выводе могут оказаться данные запроса, а в core dump — память процесса. Не сохраняйте весь рабочий каталог через untracked: true без анализа состава. Чётко перечисленные пути делают результат понятнее и уменьшают риск захватить временный credential-файл. Маскирование журнала не редактирует байты приложенного архива.

Registry, теги и неизменяемость

У образа контейнера тег stable или latest обозначает перемещаемое имя, digest — конкретное содержимое манифеста. Доставка по digest лучше фиксирует точную сборку; проверка архитектуры остаётся отдельным шагом для multi-platform образа. Слои могут разделяться несколькими образами, поэтому сумма видимых размеров тегов не равна физическому расходу диска. Удаление тега и освобождение неиспользуемых слоёв также могут быть разными этапами политики очистки.

Generic Package Registry позволяет сохранять собственные файлы под именем и версией пакета. Политика повторной публикации той же версии должна быть явной: иначе красивое имя релиза может позднее соответствовать другим байтам. Сохраняйте SHA, происхождение и права на изменение; защищённый тег Git не автоматически защищает внешний пакет от любого разрешённого издателя. Путь загрузки и срок учётных данных также входят в договор.

Два одновременных pipeline и один изменяемый ключ

Pipeline P81 собирает C17, P82 — C18. Оба используют cache key go-main и pull-push. Каждый получает доступную старую копию кэша, затем изменяет свои локальные файлы. Если P82 загрузил архив первым, а медленный P81 позже, последняя сохранённая копия может относиться к более старому набору. Это допустимо для корректного восстановимого кэша: Go повторно проверяет свои входы. Но если cache содержит единственный dist/echo для доставки, поздний P81 способен заменить результат, который автор ошибочно считал новым.

Теперь заменим передачу результата: verify P82 ссылается на artifact build из собственного P82, содержащий H18 и manifest C18. P81 не может просто последним push того же cache key изменить эту привязку. Если artifact истёк или недоступен, verify должен явно отказать, а не взять случайный бинарник по общей ветке. Целостность SHA и правильное происхождение producer — два проверяемых утверждения. При использовании межпроектных/межконвейерных артефактов правила выбора job/ref дополнительно исследуют: слово latest не связывает результат с произвольным текущим потребителем.

Retry build P82 может повторно получить moving image tag, другую внешнюю зависимость или изменённое содержимое незакреплённого источника. Commit C18 при этом тот же, но результат способен стать H18b. Поэтому для выпуска сохраняют идентичность конкретного producer/job и digest, а не только коммит. Если нужны доказуемо повторяемые байты, повторяемость проверяют отдельным сравнением с зафиксированными входами; её нельзя вывести из одинакового имени файла.

Когда кэш действительно ускоряет

Пусть без кэша работа занимает 70 с. Получение архива занимает 9 с, распаковка 4 с, полезная работа с ним 20 с, повторная упаковка и загрузка 12 с. Полное время 45 с, выигрыш 25 с. Если зависимости малы и исходная работа занимала 15 с, тот же архив может всё замедлить. Это придуманные числа для расчёта, не обещание GitLab. Измеряют весь путь и отдельно составляющие, а не только время компилятора.

Сравнивайте одинаковые входы, число параллельных job, сеть и состояние ОС. Отдельно нужен холодный прогон без CI-кэша и без локального Go-кэша. Удалять общий кэш других проектов ради измерения не требуется: используйте выделенные каталоги и ключ. Успешная повторная работа при пустом кэше — проверка корректности договора, а ускорение прогретого пути — отдельная проверка эффективности.
