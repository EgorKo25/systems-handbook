Установка: версия, постоянные данные, адреса и первый проверяемый вход

Развёртывание начинается до команды запуска. Нужно выбрать поставку, зафиксировать её происхождение, отделить состояние от программы и обеспечить один согласованный адрес для браузера, Git-клиента, Runner и служебных ссылок.

Что следует выбрать заранее

Self-Managed означает экземпляр под вашим управлением: вы отвечаете за ОС, данные, обновления, доступ и восстановление. GitLab.com — управляемый сервис с иной границей ответственности. CE, Community Edition, и EE, Enterprise Edition, — варианты поставки; наличие EE само по себе не предоставляет любую платную функцию. В личном стенде выбирают доступный набор возможностей и поддерживаемый выпуск. Для повторяемого запуска записывают полное имя версии, редакцию, архитектуру процессора и digest образа либо контрольную сумму пакета.

Digest образа — хеш его содержимого в реестре. Тег, например имя версии, служит указателем; одна только строка latest не закрепляет байты. Получение поставки выполняют при наличии сети и затем сохраняют нужные образы и сведения об их происхождении для автономного периода. Контрольная сумма обнаруживает различие байтов; доверие к ожидаемой сумме или подписи устанавливается отдельно через официальный источник.

Объём памяти распределяется между GitLab, ОС, дисковым кэшем и сборками. Установка сервера и запуск нескольких компиляторов на одном домашнем ПК конкурируют за одни ресурсы. Для первой собственной среды разумнее один Runner и одна одновременная работа с известным набором процессов. Это исходная конфигурация опыта, а не обещание достаточности фиксированных 4 или 8 ГБ для любой нагрузки. После первого запуска измеряют фактическую память и время отклика.

Постоянные каталоги и контейнер

В контейнерной Linux-поставке важны три точки: /etc/gitlab для конфигурации и чувствительных ключевых материалов, /var/opt/gitlab для состояния приложения и /var/log/gitlab для журналов. Их выносят в явно выбранное постоянное хранилище. Удаление контейнера тогда не означает удаление платформы. При этом данные PostgreSQL внутри постоянного каталога ещё требуют согласованной процедуры резерва; копирование файлов работающей БД не подменяет её.

Следующий Compose-фрагмент — шаблон для отдельной Linux-машины личного стенда. Он не выполняется при чтении. GITLAB_IMAGE должен содержать одобренный конкретный образ; GITLAB_HOST — ваше разрешаемое DNS-имя. TLS в этом варианте завершает отдельный входной прокси, а внутренний HTTP-порт связан только с петлевым адресом той же машины. Прокси, сертификат и DNS нужно подготовить до проверки полного маршрута.

services:
  gitlab:
    image: ${GITLAB_IMAGE:?choose a supported pinned image}
    hostname: ${GITLAB_HOST:?set the personal lab hostname}
    restart: "no"
    shm_size: "256m"
    environment:
      GITLAB_OMNIBUS_CONFIG: |
        external_url 'https://${GITLAB_HOST}'
        letsencrypt['enable'] = false
        nginx['listen_port'] = 80
        nginx['listen_https'] = false
        nginx['proxy_set_headers'] = {
          "Host" => "$$http_host",
          "X-Real-IP" => "$$remote_addr",
          "X-Forwarded-For" => "$$proxy_add_x_forwarded_for",
          "X-Forwarded-Proto" => "https",
          "X-Forwarded-Ssl" => "on"
        }
        gitlab_rails['gitlab_shell_ssh_port'] = 2222
    ports:
      - "127.0.0.1:18080:80"
      - "127.0.0.1:2222:22"
    volumes:
      - ./state/config:/etc/gitlab
      - ./state/data:/var/opt/gitlab
      - ./state/logs:/var/log/gitlab

restart: "no" оставляет личную учебную службу без автоматического старта после перезагрузки Docker. shm_size относится к общей памяти /dev/shm, а не к полному лимиту RAM контейнера. Слева в записи порта находится адрес и порт хоста, справа — порт контейнера. Привязка SSH к 127.0.0.1 намеренно делает его доступным лишь с этой машины: для первого упражнения с другого компьютера используйте Git по HTTPS через подготовленный вход. Не открывайте SSH-порт на всех интерфейсах ради совпадения красивого clone URL.

Двойной знак доллара в $$http_host нужен потому, что Compose сам выполняет подстановку переменных. После его разбора GitLab должен получить NGINX-переменную с одним долларом. Это пример двух последовательных языков конфигурации: YAML/Compose сначала, Ruby-настройки GitLab и затем NGINX. Перед запуском docker compose config показывает итоговое описание; проверяют адреса и пути, не публикуют вывод, если в конфигурацию добавлены секреты.

Один адрес виден из разных сетевых пространств

external_url — канонический внешний адрес GitLab. Он влияет на ссылки, перенаправления и представление платформы о своей схеме. Публикация Docker-порта сама не переписывает этот адрес. Если сервер считает себя http://localhost, а пользователь входит через другое HTTPS-имя, могут появиться неверные ссылки, проблемы обратных вызовов и несовпадение безопасных cookie. Лечение начинается с согласования маршрута, а не с отключения проверок.

localhost всегда относится к сетевому пространству того процесса, который его использует. Для браузера дома это домашний ПК, для контейнера задания — сам контейнер, для Runner в отдельной VM — та VM. Поэтому URL, который открывается в браузере, может быть недоступен при загрузке артефакта из задания. Проверяют DNS, маршрут, порт и доверенный сертификат отдельно из каждого участника. Внутренний адрес БД не обязан совпадать с публичным адресом сайта.

TLS-прокси должен передавать корректные заголовки исходной схемы и адреса, а GitLab — доверять только известным прокси. Принимаемый от любого клиента X-Forwarded-For нельзя считать доказанным источником запроса. Сертификат проверяют по имени в URL и цепочке доверия. В личной сети можно использовать свою удостоверяющую инфраструктуру, но её корневой сертификат должен быть доверенно установлен у действительных клиентов; curl -k не превращается в нормальный способ аутентифицированного общения.

Разбор адресов одной личной установки

Возьмём конкретную учебную карту. На личной Linux-VM стоит GitLab-контейнер; входной TLS-прокси работает на той же VM и слушает 443. Имя gitlab.lab.example у клиентов и Runner разрешается в адрес VM. Эти адреса и домен условные, не принадлежат чужой площадке. Прокси передаёт запрос на 127.0.0.1:18080; Docker переводит его на порт 80 контейнера. Внешний external_url равен https://gitlab.lab.example. TLS-сертификат содержит это имя, а клиенты доверяют его издателю. Встроенное автоматическое получение Let's Encrypt в шаблоне отключено, потому что сертификат обслуживает внешний прокси.

Браузерhttps://gitlab.lab.example/DNS и маршрут к VM, TLS к прокси, затем браузерная сессия и права

Последняя строка — только локальный диагностический транспорт. Для неё ожидаемый SSH host key всё равно проверяют; имя 127.0.0.1 не делает удалённый через переадресацию процесс автоматически доверенным. Настройка gitlab_shell_ssh_port = 2222 определяет объявляемый порт SSH, но loopback-привязка шаблона намеренно не делает его доступным с рабочего Windows. Объявленный UI clone URL поэтому ещё не является готовым удалённым SSH-маршрутом. Удалённый Git в этом варианте использует HTTPS. Если позднее появится частный VPN-доступ к SSH, его проектируют отдельно и согласуют привязку/URL/ключи.

Предположим браузер открыл сайт, а job не может получить artifact и пишет x509: certificate signed by unknown authority. Сертификат проверяет процесс, выполняющий именно этот запрос. Успешное доверие браузера не означает доверие Runner helper. Нужно добавить доверенный CA предусмотренным способом в соответствующую среду и проверить имя назначения. Если ошибка вместо этого no such host, сначала исправляют разрешение DNS в этой среде. Если TLS прошёл, а HTTP вернул 403, исследуют уже полномочия и URL. Одинаковая ссылка проходит несколько независимых границ.

Другой опыт: замените в URL внешнее имя на localhost, но только в своей отдельной тестовой конфигурации. Браузер на сервере может по-прежнему что-то открыть, а Runner в другой VM направится к себе. Возвратите исходную карту адресов. Этот отказ объясняется выбранным пространством имён, а не паролем. Чтобы не получить такую ловушку в настоящей установке, проверяют полный путь с тех процессов, которые будут пользоваться платформой.

Первый запуск не заканчивается статусом контейнера

docker compose up -d создаёт и запускает описанные контейнеры в фоне. GitLab затем разворачивает конфигурацию, готовит компоненты и схему данных; статус работающего контейнера означает только существование его основного процесса. Проверяют журнал, состояние служб и readiness, то есть готовность обслуживать работу с зависимостями. Liveness проверяет более слабое свойство жизнеспособности процесса; это не то же самое, что способность принять push или сохранить артефакт.

docker compose ps
docker compose logs --tail=100 gitlab
docker compose exec gitlab gitlab-ctl status
docker compose exec gitlab gitlab-rake gitlab:check SANITIZE=true

ps показывает контейнеры проекта Compose. logs --tail=100 ограничивает вывод последними ста строками и не меняет уровень журналирования. exec запускает команду внутри уже работающего контейнера. gitlab-ctl status исследует службы поставки, а задача gitlab:check — набор прикладных проверок. SANITIZE=true уменьшает показ чувствительных деталей в этой задаче, но любой журнал перед публикацией всё равно просматривают.

Первичная учётная запись и следующий вход

Начальные данные администратора извлекают только в личном терминале согласно выбранной поставке и версии. Файл первоначального пароля в Linux-пакете имеет ограниченный срок жизни; это не постоянное хранилище учётных данных. Создайте отдельную обычную учётную запись для работы с проектом, ограничьте саморегистрацию и проверьте доступ из отдельной приватной сессии. В томе нет настоящих паролей, токенов или инструкции публиковать их в issue.

До приглашения других участников пройдите маленький полный цикл: вход обычным пользователем, создание приватного учебного проекта, push собственного файла, чтение его другим разрешённым клиентом и подтверждение отказа без полномочий. Затем штатно остановите контейнер через docker compose stop, запустите снова и проверьте тот же проект. Эта проверка связывает выбранные постоянные каталоги с реальным сохранением состояния. Команда down -v для обычного завершения обучения не нужна: удаление томов является отдельным действием с данными.
