Go-конвейер: проверить исходники, собрать однажды, испытать те же байты

Теперь соединим граф, исполнение и хранение на собственном проекте. Цель — прослеживаемый бинарник: понятные входы, реальные тесты, сохранённый статус и проверка артефакта в отдельном задании.

Состав учебного проекта

В каталоге labs лежит оригинальное маленькое HTTP-приложение echo. Оно использует только стандартную библиотеку Go, поэтому первая локальная сборка не требует получать сторонние модули. Вход /ready служит простой проверкой ответа процесса, /echo?value=... возвращает переданную строку в JSON, -version печатает встроенную версию. Это учебная служба, не готовая система хранения данных.

Сценарий tools/ci.py выполняет три действия: test запускает настоящие Go-тесты и формирует отчёт, build компилирует программу и записывает manifest, verify проверяет целостность и запускает именно сохранённый бинарник. Он использует Python standard library, не устанавливает инструменты и не общается с GitLab API. Возможности платформы описаны в .gitlab-ci.yml и требуют собственного сервера для проверки.

Образ инструментов — самостоятельный вход

Для CI нужен подготовленный образ, содержащий совместимый Go и Python 3. Его переменная LAB_GO_PYTHON_IMAGE задаётся обычным несекретным параметром проекта как полное зафиксированное имя. Обычный образ golang не следует молча считать содержащим любую нужную Python-программу. Для первого shell Runner можно запустить те же сценарии в выделенной VM с уже известными версиями, убрав неподдерживаемый executor ключ image из своего варианта CI.

Описание образа и его контрольная сумма входят в запись опыта. Внутри job выполняют go version и python3 --version; совпадение тега образа при разных фактических инструментах — повод исследовать поставку и кэш Docker. Версия Go в go.mod задаёт требования к модулю и языку, но не заменяет закрепление выбранного toolchain среды. Для автономного стенда его и базовый образ получают заранее.

Исходная версия конвейера

Продолжим тот же экземпляр, который зарегистрировали в главе Runner. У него есть метка personal-go. Если первый вариант использует shell, в своей копии полного .gitlab-ci.yml удалите только строку image: $LAB_GO_PYTHON_IMAGE из default: остальные условия, метки, команды и передача артефактов сохраняются. Go и Python тогда берутся из ОС этой выделенной VM; до push подтвердите их версии тем пользователем и в том окружении, где запущен Runner. При Docker executor оставьте image и сначала задайте реальный подготовленный образ: имя переменной само его не собирает. Смену executor делайте как отдельное последующее изменение, а не как скрытую предпосылку этого опыта.

stages: [check, build, verify]
default:
  image: $LAB_GO_PYTHON_IMAGE
  tags: [personal-go]

unit:
  stage: check
  script:
    - python3 tools/ci.py test
  artifacts:
    when: always
    paths: [reports/]
    reports:
      junit: reports/junit.xml
    expire_in: 7 days

build:
  stage: build
  script:
    - python3 tools/ci.py build
  artifacts:
    paths: [dist/]
    expire_in: 7 days

verify:
  stage: verify
  needs:
    - job: build
      artifacts: true
  script:
    - python3 tools/ci.py verify

Полный файл в практикуме добавляет workflow, обычные переменные, ограничение времени и явные предположения. В приведённом графе build ждёт этап check. Verify получает артефакт конкретной build. Job проверки не компилирует программу заново. Это позволяет утверждать, что проверенный SHA относится к переданным байтам. Если вместо этого verify сделал новый go build, мы получили бы свидетельство о другой сборке, даже при совпадающих исходниках.

Команда Go и выбранные флаги

Тест выполняется как go test -json -count=1 ./.... -json даёт поток структурированных событий, -count=1 требует нового исполнения тестов вместо подходящего сохранённого успешного результата, ./... выбирает пакеты текущего дерева по правилам Go. Кэш компиляции при этом не отключается. Чтобы измерить полную холодную стоимость, нужны другие выделенные условия; каждый обычный CI-прогон не обязан уничтожать полезный сборочный кэш.

Сборка использует -trimpath, чтобы нормализовать записываемые файловые пути, и -buildvcs=false, чтобы выбранная политика происхождения не зависела от автоматического VCS-встраивания. Идентификатор исходников сохраняется явно в manifest. -ldflags передаёт аргумент линковщику, где -X main.Version=... устанавливает строковую переменную версии. Для версии допускается ограниченный безопасный набор символов, а не произвольный shell-текст. Глубокая механика этих флагов находится в томе Go.

CGO_ENABLED=0 в данном проекте выбирает Go-вариант без C-зависимости; это подходит нашему составу, но может менять поведение другого проекта. Цель по умолчанию — нативная ОС и архитектура текущего Go. Для CI примера ожидается Linux Runner. Если вы намеренно кросс-компилируете Windows-бинарник на Linux, локальный verify не должен пытаться запускать его как Linux-программу. Отдельный целевой исполнитель — часть проверки такого выпуска.

Привязка к исходникам и проверкам

Manifest получает source_revision только из самостоятельно прочитанного Git HEAD, если корень репозитория точно равен корню service. Вложенность в другой репозиторий не позволяет приписать проекту чужую историю: записываются local-unversioned и source_dirty=true. CI_COMMIT_SHA сохраняется отдельно как заявленное значение. В CI сборка разрешена только при его совпадении с наблюдаемым HEAD и чистом рабочем состоянии. Переменная окружения сама по себе не является аттестацией происхождения. Manifest также записывает хеш фактического сценария tools/ci.py, toolchain и параметры сборки.

Verify сравнивает размер и SHA-256, наблюдаемую ревизию/dirty, записанные флаги, хеш собственного сценария и toolchain; затем получает -version из того же файла. Это проверяемая цепочка учебной сборки, не криптографическая аттестация доверенного исполнителя. Она не удостоверяет отсутствие всех ошибок программы. Функциональные HTTP-тесты проверяют отдельные свойства, а запуск бинарника — ещё одну границу сборки и исполнения. Существенно, что каждое свидетельство имеет точный охват.

Неуспех как часть примера

В собственной копии поменяйте ожидание одного теста. Unit должен завершиться ненулевым кодом, отчёт обязан сохраниться, build не должен продвинуться обычным путём. Затем исправьте тест. Отдельно поменяйте один байт уже собранного файла: verify должен отвергнуть его до запуска. Наконец, удалите cache и повторите правильный исходный прогон. Он должен работать медленнее либо так же, но не терять корректность.

Следующий опыт — остановить личный Runner после создания pipeline и вернуть его. Это проверяет назначение работы, а не Go. Ещё один — изменить только правила workflow и проверить таблицу событий. Так одинаковый внешний симптом «нет зелёного выпуска» раскладывается на отсутствие графа, ожидание ресурса, неуспех теста, ошибку сборки, отсутствие артефакта и нарушение целостности.

Границы результатов практикума

Проверки файла labs/check.py исполняют настоящие Go-команды в изолированных временных каталогах и тестируют преобразование отчёта, отказ на повреждённом бинарнике и исходную модель выбора события. Они не заменяют интеграционный запуск GitLab Server и Runner. До получения такого запуска не объявляйте проверенными его регистрацию, серверную YAML-семантику или вывод JUnit в интерфейсе. Для них в финальной главе есть отдельная запись ожидаемых наблюдений.
