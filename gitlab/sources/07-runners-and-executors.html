Runner: как задание получает машину и насколько ей доверяет

GitLab хранит и планирует работу; Runner под своим управлением превращает её в процессы. В этой главе регистрация, выбор задания, лимиты и изоляция рассматриваются как одна цепочка допуска пользовательского кода к ресурсам.

Одна запись Runner и несколько процессов

В интерфейсе GitLab Runner представлен зарегистрированной конфигурацией с областью использования и свойствами. На машине работает runner manager — процесс программы GitLab Runner, который аутентифицируется, запрашивает работу и организует исполнение. У одной зарегистрированной конфигурации могут быть несколько менеджеров; одна программа-менеджер может обслуживать несколько конфигурационных записей. Поэтому число строк в UI нельзя напрямую превращать в число VM, CPU или одновременно работающих заданий.

Runner обычно сам обращается к GitLab по исходящему HTTP(S). Доступность сайта из браузера не подтверждает возможность такого обращения с машины Runner. Long polling, длинное ожидание ответа, позволяет серверу удерживать запрос получения задания до появления подходящей работы или окончания ожидания. Это не постоянный SSH-канал от GitLab к машине. Дополнительные служебные подключения определяются выбранным executor, хранилищами и инструментами задания.

Регистрация в актуальной модели

Сначала в своём проекте или группе создают Runner с необходимой областью и свойствами. Полученный runner authentication token связывает установленную программу с этой записью. У таких токенов используется префикс glrt-. Старые инструкции с общим registration token относятся к другому, устаревающему процессу и не должны механически переноситься на новый выпуск. Версию Runner выбирают совместимой с GitLab и закрепляют отдельно.

gitlab-runner register --config "$LAB_RUNNER_CONFIG"
gitlab-runner verify --config "$LAB_RUNNER_CONFIG"
gitlab-runner run --config "$LAB_RUNNER_CONFIG"

Это действия внутри отдельной личной Runner-машины с уже установленной официальной программой. LAB_RUNNER_CONFIG задаёт полный путь к её выделенному конфигурационному файлу. register интерактивно спрашивает адрес, токен и executor; секрет вводится в своём терминале и не включается в книгу. verify проверяет связь зарегистрированных Runner с GitLab; она не доказывает доступность образа, Docker или успешность будущей команды. run запускает обработчик в переднем плане; сервисный вариант имеет другой жизненный цикл.

Файл config.toml содержит чувствительный материал аутентификации и настройки допуска к ресурсам. Его не коммитят в репозиторий проекта. Удаление файла на одной машине не равно отзыву записи на сервере, а удаление регистрации не стирает рабочие данные на диске. При переносе машины отдельно решают судьбу токенов, кэшей, образов и накопленных файлов. Неправильную копию config легко принять за «старый Runner снова ожил».

Почему свободный Runner может не подходить

Задание с tags: [linux, go] требует Runner, у которого присутствуют все перечисленные метки. Runner с одной меткой linux не удовлетворяет этому требованию. Метка — заявленное свойство допуска; она не устанавливает Go и не доказывает архитектуру процессора. Это ответственность администратора среды. Отдельно проверяются область Runner, разрешение untagged jobs, protected-настройка, состояние paused и доступность менеджера.

Если задание остаётся pending, сначала сопоставляют его требования с разрешёнными кандидатами. Увеличение числа исполнителей у неподходящей машины не исправит неверную метку или отсутствие доступа к проекту. Если кандидат есть, но свободных слотов нет, причина уже в ёмкости. Если слот получен и задание зависло на подготовке, переходят к executor, сети образов и монтированию. Разные состояния могут одинаково выглядеть как «долго не идёт сборка», но требуют разных действий.

Три независимых ограничения параллелизма

concurrent — общий верхний предел одновременно исполняемых заданий процесса Runner. limit внутри записи [[runners]] ограничивает конкретную конфигурацию; ноль у этого параметра обычно означает отсутствие дополнительного собственного ограничения. request_concurrency ограничивает одновременные запросы получения новой работы, а не количество CPU и не размер графа. Неподходящие значения способны оставить ресурсы простаивающими при длинном ожидании запросов.

concurrent = 1

[[runners]]
  name = "personal-go"
  url = "https://gitlab.example.invalid"
  token = "REPLACE_ONLY_IN_PRIVATE_CONFIG"
  executor = "docker"
  limit = 1
  request_concurrency = 1
  [runners.docker]
    image = "REPLACE_WITH_PINNED_GO_IMAGE"
    privileged = false
    memory = "2g"
    cpus = "2"

Это поясняющий фрагмент, не готовый файл регистрации. На маленьком личном стенде один слот позволяет сначала измерить расходы одной работы. memory и cpus задают ограничения контейнера задания в данном executor, но внешние службы GitLab и Docker требуют своей памяти. Увеличение concurrent до восьми не добавляет восьми независимых бюджетов памяти. Параллелизм внутри go test дополнительно накладывается на число одновременно выполняемых job.

Shell, Docker и Kubernetes — разные границы

Shell executor выполняет команды с правами пользователя Runner на его ОС. Файлы домашнего каталога, доступная сеть и оставшиеся процессы становятся частью доверия к коду проекта. Он удобен в полностью личной выделенной VM для понимания процессов; его нельзя считать изолированным только потому, что job имеет свой каталог. Очистка workspace после выполнения не отменяет действий, уже совершённых за его пределами.

Docker executor создаёт контейнеры задания и служебных компонентов. Он отделяет файловые и процессные пространства согласно конфигурации, но ядро остаётся общим с хостом. Переданный Docker socket даёт управление Docker-хостом в пределах его полномочий и резко меняет границу доверия. privileged = true, host network, host PID и чувствительные bind mount также способны разрушить ожидаемую изоляцию. Для обычной Go-сборки эти возможности не обязательны.

Kubernetes executor создаёт окружение в кластере и использует его API, планировщик и политики. Теперь важны service account, namespace, ресурсы, сетевые правила, тома и admission-контроль. Если Pod создаётся под широко привилегированной учётной записью, слово Kubernetes не уменьшает полномочия кода. Отдельная одноразовая VM на недоверенную работу даёт другую границу ядра и очистки, но стоит времени запуска и ресурсов. Выбор определяется доверием и угрозами конкретной среды.

Разобрать назначение трёх заданий по одному слоту

У manager есть concurrent=2. Конфигурация A: метки linux/go, limit=1; конфигурация B: метки linux/docs, limit=1. Приходят U с меткой go, V с меткой go и D с меткой docs. U занимает A, D занимает B. V ждёт, хотя общий предел два и в интерфейсе видны два Runner. Если D завершится, V всё равно не сможет занять B: кандидат не соответствует метке. Свободное глобальное место и подходящее свободное место — разные условия.

Теперь администратор меняет A limit на 2, оставляя global concurrent=2. Если D ещё работает, одновременно U+V+D всё равно не начнутся: общий предел запрещает третью работу. После завершения D менеджер сможет дать A второй слот. Если при этом каждой Go-работе требуется 1,5 ГБ памяти, два слота требуют уже примерно 3 ГБ только для них, плюс executor и ОС. Это модель значений, а не измеренный профиль нашего маленького приложения; реальный RSS/лимит измеряют отдельно.

request_concurrency=1 описывает ещё другую границу. Один долгий запрос без подходящей работы может задерживать получение другой работы в определённых сочетаниях конфигурации и лимитов. Увеличение request_concurrency исследуют по метрикам и предупреждениям Runner, а не принимают за увеличение допуска процессов. После изменения полезно построить ту же временную шкалу: сколько запросов ждёт, сколько job назначено, сколько реально исполняется и где лимит достигнут.

Отдельный Runner для выпуска

Проверки MR и доставка в личный сервис имеют разные полномочия. MR может содержать ещё не принятый код; deploy получает доступ к рабочей среде. Их полезно разводить по Runner и правилам выдачи секретов. Одна защищённая метка не является секретом: автор YAML способен написать такое же имя. Реальный допуск обеспечивается серверными ограничениями Runner и защищённых ссылок, членством, правилами окружений и доступом к секретам.

При первом запуске выполните задание, которое показывает только несекретные свойства: версию Go, ОС, архитектуру, UID и путь проекта. Затем проверьте передачу артефакта и повторный запуск после остановки менеджера. Не выводите весь env ради любопытства: среди переменных будут данные доступа. Остановленный личный Runner должен оставлять созданное задание ожидающим; возвращение менеджера должно разрешать именно эту границу, не требуя повторного push исходников.

Первичные источники

Регистрация; Лимиты и config.toml; Модель доверия исполнителей; Варианты executor; Метки, область и protected. Личная конфигурация на один слот — исходный учебный выбор, а не рекомендация для любой команды.
