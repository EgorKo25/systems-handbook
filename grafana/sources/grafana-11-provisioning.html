Provisioning: постоянные UID, файлы, база и один владелец

Provisioning — применение сохранённых файлов конфигурации сервером. Правка через интерфейс не становится автоматически изменением этих исходников.

Что происходит при запуске и просмотре файлов

YAML источника с apiVersion1 описывает подключение prom-local и открытые параметры jsonData. Grafana читает paths.provisioning/datasources, создаёт или обновляет запись базы и отмечает управление конфигурацией. editable=false ограничивает изменение через интерфейс. YAML поставщика досок задаёт папку, folderUid, тип file, путь JSON, период проверки, allowUiUpdates и disableDeletion. При запуске и очередной проверке сервер сопоставляет UID и обновляет сохранённое описание по правилам поставщика. Это не дамп базы и не git pull.

Наш folderUid=handbook-go, путь state/dashboards, allowUiUpdates=false, disableDeletion=true. UID go-service-lab сохраняет адрес доски при переносе. Два файла с одинаковым UID не создают независимые доски: они конфликтуют за идентичность. updateIntervalSeconds15 относится к обнаружению файлов, а не обновлению метрических запросов. После правки JSON нужно дождаться применения, перечитать доску и сверить фактические заголовок и выражение.

Три похожих изменения с разной судьбой

Правка исходного JSON и последующее применение меняют сохраняемую доску. Правка через UI/API при allowUiUpdates=false отвергается: это фактически проверено. При allowUiUpdates=true интерфейс может записать базу, но не исходный файл; следующее обновление из файла способно затереть правку. Такой режим требует явного экспорта, проверки и переноса в управляемый исходник. Одновременное редактирование файлами, Terraform, API и интерфейсом без договора создаёт drift — расхождение ожидаемого и фактического состояния.

disableDeletion=true сохраняет запись доски при исчезновении её файла. Это не резерв остальных ресурсов и секретов. При разрешённом удалении судьба объекта меняется при согласовании с файлом. У источников prune и deleteDatasources имеют отдельные правила: наш prune=false не означает автоматическую очистку всех отсутствующих объектов. Удаление проверяют отдельно с известным UID и зависимостями.

Секреты и подстановка окружения

jsonData хранит открытые настройки, например HTTP-метод и timeInterval. secureJsonData содержит чувствительные поля вроде httpHeaderValue1/basicAuthPassword; сервер шифрует их, а API показывает secureJsonFields как признак наличия. Отсутствующее поле и пустое значение в обновлении не обязательно имеют один смысл. Не отправляйте пустой secureJsonData ради косметического экспорта без проверки семантики. Если исходный YAML содержит открытый секрет до записи базы, сам файл тоже должен быть закрыт.

Подстановка $VAR/${VAR} в YAML имеет особенности при долларе внутри значения. Официальная документация рекомендует форму $VAR для соответствующего случая, чтобы избежать повторной интерполяции. Это не ini-механизм $__file. Окружение доступно наблюдателю с нужными правами и может попасть в диагностику: его нельзя автоматически называть тайным хранилищем. Поставщик Vault редакции Enterprise не обещан OSS. Наш тест с искусственным заголовком проверяет доставку и скрытие конкретного секрета, а не работу с производственными ключами.

Проверка и офлайн-перенос

Сохраняют дерево файлов, UID, типы и версии модулей, выражения, единицы, преобразования, параметры поставщика и лицензии. Закрытые файлы и база личного стенда не входят в публичный архив. JSON доски не доставляет секрет источника, бинарный файл внешнего модуля или историю Prometheus. Копия SQLite без нужного ключа не гарантирует расшифровку. Для «перенесено» называйте критерий: JSON разобран, сервер принял файл, API прочитал UID, запрос вернул таблицу, числа подтверждены источником.

История версий доски в базе помогает сравнению и возврату правок, но не заменяет управление версиями файлов и резерв. version в JSON управляемой доски не является универсальным запретом переписать более новую правку базы. Окончательное владение определяется правилами поставщика. В нашем стенде изменяют исходный JSON, проверяют его и затем применяют; самопроизвольная правка базы не считается новой принятой редакцией.
