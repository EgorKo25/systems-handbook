Сбросы счётчика, пропуски и оценка процентиля

Рассчитаем скорость счётчика и оценку p90 по небольшим таблицам, а затем разберём, что означают полученные числа.

Пропуск в ряду активных обработчиков

Измерим число активных обработчиков — ряд типа gauge. При начале новой обработки оно растёт, при завершении уменьшается. В таблице заданы учебные значения; живой сервис для неё не опрашивали.

В этой таблице null означает отсутствие значения. В момент 45s, напротив, измерен ноль: активных обработчиков нет. Среднее четырёх известных точек равно (2+3+0+4)/4=2.25. Если заменить пропуск нулём, получится 9/5=1.8, но для этого пришлось бы считать, что в 30s обработчиков точно не было. Соединение линии через разрыв тоже ничего не измеряет: оно лишь проводит линию между соседними значениями. Настройка Connect null values / Span nulls управляет таким отображением; в учебной доске задано spanNulls=false и точки видимы.

Среднее с весом по времени не обязано совпадать со средним перечисленных значений: при нерегулярной сетке надо определить действие значения между точками. Last not null, последнее непустое, может показать старую цифру после исчезновения текущих данных. Для вопроса «сейчас» рядом нужен возраст или признак здоровья. Если пропуск может означать отказ сбора, метка «нет данных» позволит отличить его от измеренного нуля.

Counter со сбросом

Пусть процесс увеличивает счётчик запросов при каждом принятом запросе. После его замены новый процесс начинает счёт с нуля. В таблице к моменту 45s новый процесс уже принял пять запросов: при вычислении прироста придётся учесть переход 30→5.

Пусть таблица — значения одного ряда lab_requests_total. Рассмотрим мгновенный запрос rate(lab_requests_total[1m]) на T=60s. Селектор выбирает интервал (0, 60]: точка в 0s исключена, поэтому остаются 15, 30, 5, 20. Первая и последняя точки различаются на 20−15=5; чтобы учесть падение 30→5, добавляем значение перед падением, 30. Оценённый прирост между t=15 и t=60 равен 35 за 45s. События между последним сбором до сброса и самим сбросом могли потеряться: по этим измерениям их число не восстановить.

До левой границы окна от первой точки 15s, до правой от последней — 0s. Средний промежуток между выбранными точками тоже 15s. Для этого набора алгоритм продолжает оценку до обеих границ; ограничение по возможному нулю счётчика её не сокращает. Получаем 35×60/45≈46.67 событий за окно и rate = 46.67/60 = 35/45 ≈ 0.778 событий/s. increase(lab_requests_total[1m]) для тех же данных даст оценку около 46.67. Дробная величина возникает при продолжении оценки к границе окна; это не точное число реально произошедших событий.

check_samples.py проверяет выбор точек, поправку на сброс и арифметику при заранее заданном коэффициенте 60/45. Он не разбирает запрос и не исполняет алгоритм Prometheus: например, сам не решает, надо ли ограничивать продолжение оценки у границы. Значение выше — расчёт для указанных условий, а не результат запуска Prometheus. Для других данных алгоритм нужно проверять через promtool или API соответствующей версии. Линия исходного счётчика полезна для монотонности и сбросов, но не отвечает на вопрос нагрузки в секунду. Несколько процессов сначала обрабатывают rate по каждому ряду, затем складывают: иначе сброс одного процесса способен выглядеть падением общего счётчика.

Гистограмма и p90

Классическая гистограмма хранит накопительные количества по верхним границам корзин, buckets. Четыре длительности 0.04,0.08,0.24,0.7s дают le0.1→2,le0.3→3,le1→4,le+Inf→4. Накопительный счётчик означает «не больше границы»: сумма 2+3+4+4 не является числом событий.

p90 — оценка границы, ниже которой находится примерно 90% наблюдений. Ранг 0.9×4=3.6 превышает накопленный счётчик 3 для границы 0.3s, но не превышает 4 для границы 1s. Значит, искомая корзина — от 0.3 до 1s. Для неё интерполяция классической гистограммы предполагает равномерное распределение внутри корзины и даёт 0.3+(1−0.3)×(3.6−3)/(4−3)=0.72s. Результат даже больше настоящего максимума 0.7: движок не знает точное положение наблюдений внутри корзины. Шесть знаков после запятой не сделают эту оценку точной длительностью. Рядом нужны число наблюдений и разумные границы корзин; p99 по четырём событиям особенно неустойчив.

В запросе классической гистограммы сохраняют le при sum by (le,instance). Среднее p90 разных экземпляров не является p90 общей совокупности. Нативная гистограмма имеет другую упаковку и интерполяцию, поэтому данный пример её не подменяет. Повышение частоты обновления не добавляет исходных наблюдений.

Редкие точки и интервалы

Если событие возникает раз 10min, окно rate(...[1m]) часто показывает 0 при живом счётчике, а новый ряд может иметь недостаточно измерений. Более широкое окно отвечает другому вопросу и сглаживает редкость. Таблица или столбцы за явные периоды иногда понятнее непрерывной линии. Число событий за период, частота/s, накопительный итог и число недавних измерений имеют разные единицы. Исчезновение одного набора меток не равно отсутствию всех данных правила.

samples.json сохраняет все числа для офлайн-повторения. Результат привязан к таблице, окну и обращению с пропуском. Это позволяет проверить смысл независимо от снимка экрана и скрытых настроек панели.
