Перенос изменений и переписывание истории

Почему cherry-pick и rebase создают новые объекты, как выбирать основание и проверять полученную последовательность

Переносится изменение, а не старый объект

Коммит C содержит снимок и родителя B. Изменение C относительно B можно попытаться применить к другому снимку M. Если удалось, получится новый снимок и новый коммит C′ с родителем M. Даже при похожих строках идентификатор обычно другой: родитель является частью содержимого коммита. Такое воспроизведение делает git cherry-pick C. Английское cherry-pick, выбор отдельных ягод, здесь означает перенос выбранных изменений без обязательного переноса всей боковой истории.

До:       A ─ B ─ C       topic
           \
            M             main
После:    A ─ B ─ C       topic
           \
            M ─ C′        main

C и C′ не стали одним объектом. Если позднее сливать линии, Git будет работать с графом и снимками, а не с человеческой фразой «это уже переносили». Некоторые команды умеют обнаруживать эквивалентные заплатки, но такая эвристика не означает общую родительскую связь. Перенос исправления полезен для поддерживаемого выпуска, однако требует проверки совместимости с его старым окружением.

Cherry-pick в проверяемой последовательности

git switch maintenance
git show --stat topic
git cherry-pick topic
# при конфликте: редактирование, затем git add -- путь
git cherry-pick --continue
# либо отмена текущей операции:
git cherry-pick --abort

Здесь topic обозначает конкретную вершину с нужным исправлением, а не всю ветку. Если надо перенести несколько коммитов, их набор и порядок задают явно. --continue продолжает остановленную последовательность после подготовки разрешений, --abort отменяет операцию с возвратом к её исходному состоянию. --no-commit применяет изменения к индексу и рабочему дереву без немедленного создания коммита: это позволяет объединить результаты, но усиливает необходимость проверить итоговый снимок.

Коммит слияния имеет несколько родителей, поэтому его «изменение» неоднозначно. Параметр -m 1 у cherry-pick выбирает первого родителя как основную линию для расчёта переносимого различия. Это не флаг сообщения, как -m у commit. Перенос результата merge не воспроизводит всю топологию двух веток. Перед таким действием выясняют, какие файлы и договоры итог слияния получил от каждой стороны.

Rebase переносит последовательность на другое основание

Rebase означает смену основания. В простом случае Git находит собственные коммиты topic после ответвления, временно начинает с нового main и последовательно воспроизводит изменения. Было A→B→C в topic и A→M в main; станет A→M→B′→C′ в topic. Старые B и C не редактируются: имя ветки перемещается к новой линии. Поэтому чужие клоны сами собой не превращают старые объекты в новые.

git switch topic
git rebase main
# если последовательность остановилась:
git status
git rebase --show-current-patch
# исправить, подготовить файлы
git rebase --continue

--show-current-patch показывает переносимый сейчас коммит. Это помогает отличить ошибку новой базы от вашего изменения. --skip пропускает текущий перенос: использовать его как универсальное «убрать ошибку» нельзя, потому что изменение может исчезнуть из результата. --abort возвращает ветку в исходное состояние операции, а --quit завершает служебный режим, не выполняя тот же возврат. Эти варианты различаются состоянием ветки, индекса и файлов.

Точный выбор участка через --onto

Пусть topic основан на старой базе old-base, и переносить нужно только собственные коммиты после неё. git rebase --onto main old-base topic задаёт три роли: main — новое основание, old-base — граница исключаемой старой части, topic — переносимая ветка. Флаг --onto буквально называет, куда поставить новую последовательность. Это особенно полезно для ветки, которую когда-то начали от другой незавершённой ветки, но затем хотят отделить от чужой работы.

Границу проверяют журналом до запуска. Если указать слишком старое основание, в перенос попадут посторонние изменения; слишком новое — потеряются нужные. Уже имеющиеся на новой базе эквивалентные изменения могут быть пропущены в зависимости от режима rebase. Коммиты, становящиеся пустыми, тоже требуют внимания: «пустой» может означать, что изменение уже есть, либо что выбран не тот набор. Пустой итог не заменяет чтение журнала операции.

Редактирование последовательности

git rebase -i HEAD~3 открывает план для трёх последних коммитов по выбранной границе. -i означает интерактивный режим. В плане pick сохраняет перенос изменения, reword предлагает новое сообщение, edit останавливает выполнение для правки, squash соединяет изменение с предыдущим и редактирует общее сообщение, fixup соединяет без сохранения отдельного сообщения исправления. Порядок строк задаёт порядок воспроизведения; перестановка может вызвать конфликт или сломать зависимость.

Обычный rebase не следует считать точным сохранением всех узлов старых слияний. Для работы с топологией существует --rebase-merges, но и он пересоздаёт коммиты и требует повторной оценки разрешений. Если задача — добавить общую историю без замены опубликованных объектов, merge часто соответствует этому смыслу прямее. Выбор определяется договором команды и нужной историей, а не требованием получить красивую прямую линию любой ценой.

Проверка результата

Перед сложным переписыванием можно создать локальное имя git branch before-rebase. Оно удержит исходную вершину. После операции git range-diff old-base..before-rebase main..topic сопоставит старую и новую серии изменений. Range diff — различие диапазонов: это обзор того, как изменились отдельные заплатки, а не только конечное дерево. Затем проверяют конечный diff и выполняют сборку и тесты сохранённого состояния. Даже одинаковое конечное дерево не доказывает, что каждый промежуточный коммит пригоден для отдельной сборки.

Разбор

Новое сообщение меняет идентификатор заменённого коммита. Его потомок должен записать новый идентификатор родителя, значит тоже становится новым объектом; это распространяется далее. Объекты не меняются на месте, пересоздаются зависимости.
