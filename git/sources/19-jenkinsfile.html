Jenkinsfile: описание конвейера, которое можно объяснить

Составим последовательность получения исходников, тестирования, упаковки и сохранения результата. У каждой директивы будет причина, а у примера — обозначенная среда, чтобы его можно было перенести без догадок о скрытых плагинах.

Предпосылки перед копированием файла

Пример использует Declarative Pipeline — декларативную форму описания конвейера Jenkins. Нужны Jenkins с совместимыми установленными компонентами Pipeline, включая поддержку Declarative, шагов SCM и долговременного запуска команд, а также Git plugin для checkout scm. Задание создаётся как Multibranch Pipeline: Jenkins обнаруживает ветки репозитория и даёт контекст, по которому работает условие branch. Нужен Linux-агент с меткой linux-python, Git, Python 3 и доступом к репозиторию. Метку назначает администратор; Jenkins не создаёт подходящую машину по самому слову в файле.

Здесь репозиторием задания является самостоятельная копия учебного проекта из git/labs/template, а не корень всей энциклопедии. В ней предполагаются каталог tests, работающий стандартным unittest, и tools/build.py, создающий комплект dist/handbook-demo.zip, dist/manifest.json и dist/source-commit.txt. Это интерфейс учебного проекта следующего практикума. Сторонние Python-пакеты, Docker и JUnit plugin в основном варианте не требуются. Файл ниже разобран по официальной документации; настоящий сервер Jenkins для этого текста не запускался. Перед применением проверяют совместимость на своём сервере и его генератором шагов, затем выполняют пробный запуск в тестовом задании.

Полный пример

pipeline {
    agent { label 'linux-python' }
    options {
        timeout(time: 10, unit: 'MINUTES')
        disableConcurrentBuilds()
        skipDefaultCheckout(true)
        buildDiscarder(logRotator(numToKeepStr: '20'))
    }
    environment {
        PYTHONDONTWRITEBYTECODE = '1'
        PYTHONUTF8 = '1'
    }
    stages {
        stage('Исходники') {
            steps {
                deleteDir()
                checkout scm
            }
        }
        stage('Тесты') {
            steps {
                sh 'python3 -m unittest discover -s tests -v'
            }
        }
        stage('Сборка') {
            steps {
                sh 'python3 tools/build.py'
            }
        }
        stage('Проверка комплекта') {
            steps {
                sh '''python3 - <<'PY'
import hashlib, json, stat, subprocess, zipfile
from pathlib import Path

def require(condition, message):
    if not condition:
        raise SystemExit(message)

output = Path('dist')
archive_path = output / 'handbook-demo.zip'
manifest = json.loads((output / 'manifest.json').read_text(encoding='utf-8'))
names = ['README.txt', 'app.py']
require(manifest['format'] == 1 and manifest['archive'] == archive_path.name,
        'Неизвестный формат комплекта')
require([r['name'] for r in manifest['members']] == names, 'Неверный перечень входов')
require(hashlib.sha256(archive_path.read_bytes()).hexdigest() == manifest['sha256'],
        'Хеш ZIP отличается от manifest.json')
with zipfile.ZipFile(archive_path) as archive:
    require(archive.namelist() == names, 'Неверный состав ZIP')
    require(archive.testzip() is None, 'Повреждён элемент ZIP')
    for name, record in zip(names, manifest['members']):
        body = archive.read(name)
        info = archive.getinfo(name)
        require(body == Path(name).read_bytes(), 'ZIP отличается от текущего входа')
        require(record['bytes'] == len(body)
                and record['sha256'] == hashlib.sha256(body).hexdigest(),
                'Метаданные входа отличаются от его байтов')
        require(info.date_time == (2000, 1, 1, 0, 0, 0)
                and info.compress_type == zipfile.ZIP_STORED
                and info.create_system == 3
                and info.external_attr >> 16 == (stat.S_IFREG | 0o644),
                'Метаданные ZIP не соответствуют правилу сборки')
head = subprocess.check_output(['git', 'rev-parse', '--verify', 'HEAD'], text=True).strip()
require(manifest['provenance']['head'] == head
        and (output / 'source-commit.txt').read_text(encoding='ascii') == head + chr(10),
        'Сведения о происхождении относятся к другому коммиту')
require(manifest['provenance']['tracked_and_untracked_dirty'] is False,
        'Сборщик зафиксировал изменения рабочей копии')
PY
'''
            }
        }
        stage('Сохранение основной ветки') {
            when { branch 'main' }
            steps {
                archiveArtifacts(
                    artifacts: 'dist/handbook-demo.zip,dist/manifest.json,dist/source-commit.txt',
                    allowEmptyArchive: false,
                    onlyIfSuccessful: true,
                    fingerprint: true
                )
            }
        }
    }
    post {
        always {
            echo "Итог: ${currentBuild.currentResult}"
        }
        cleanup {
            deleteDir()
        }
    }
}

Где выделяется агент и где начинается таймер

Один верхнеуровневый agent даёт стадиям общую выделенную среду и рабочий каталог. Это простая схема для небольшого проекта. timeout задаёт предел времени выполнения после выделения верхнеуровневого агента; ожидание этого агента в общий лимит данного варианта не входит. При агенте и options на уровне отдельной стадии таймер может включать выделение её агента. Поэтому перенос одинаковых строк на другой уровень способен изменить наблюдаемую длительность до прерывания.

disableConcurrentBuilds() запрещает одновременно исполнять несколько запусков данного задания; следующий ждёт. Это помогает с общей инфраструктурой, но не заменяет корректную изоляцию. В Multibranch каждая ветка представлена своим заданием, поэтому настройка не является глобальным замком для всех веток и всех проектов. buildDiscarder с numToKeepStr: '20' ограничивает историю по политике ротации; существенные выпуски следует хранить в предназначенном для них хранилище, а не рассчитывать на бесконечность истории задания.

skipDefaultCheckout(true) отключает неявное получение исходников. Мы делаем его явно после deleteDir(), чтобы старые файлы не участвовали в тестах. checkout scm использует настройку SCM и ревизию контекста задания; самостоятельно вставленная команда «клонировать последнюю main» могла бы проверить другой код, чем тот, из-за которого начался запуск. Очистка удаляет содержимое текущего workspace; она не очищает домашний каталог агента, общий кэш пакетов и внешнюю базу.

Что проверяют команды и что попадает в архив

Тестовая команда использует -m для запуска модуля Python, discover для обнаружения тестов, -s tests для начального каталога, -v для подробного вывода. Сборка запускает собственный сценарий, где описаны входы и нормализация архива. При проверке комплекта аргумент - просит Python читать программу со стандартного ввода; конструкция оболочки <<'PY' передаёт текст до отдельной строки PY без подстановок оболочки. require — наша небольшая функция, завершающая действие с ошибкой при нарушении условия; это не встроенная команда Jenkins. Проверяются SHA-256 ZIP, состав, исходные байты, нормализованные метаданные и согласованность обоих внешних файлов с фактическим HEAD. Сборщик записывает признак изменённого рабочего дерева, а этот пример не допускает такой комплект к сохранению.

testzip() возвращает имя повреждённого элемента либо None; мы явно превращаем повреждение в ненулевое завершение. Ошибки открытия архива и разбора JSON также не подавляются. Сравнение HEAD требует установленного Git; флаг --verify требует корректного разрешения указанной ссылки. Проверка проверяет контракт нашего формата, но не объявляется универсальным валидатором произвольных чужих архивов. Она не заменяет запуск доставленного приложения и не устанавливает доверие к поставщику файла.

Почему здесь не ограничились удобным python3 -m zipfile -t? В проверенном CPython 3.12 интерфейс командной строки может напечатать имя элемента с неверной CRC и закончить с нулевым кодом. Поэтому человекочитаемую диагностику нельзя без опыта объявлять надёжным барьером CI. Явная проверка результата библиотечной функции делает договорённость понятной и проверяемой.

PYTHONDONTWRITEBYTECODE=1 запрещает обычную запись Python-кэша .pyc при импорте; это уменьшает мусор рабочего дерева. PYTHONUTF8=1 включает режим UTF-8 интерпретатора. Ни одна переменная не фиксирует версию Python и не делает преобразования пользовательского кода автоматически воспроизводимыми. Среда агента всё равно должна иметь известный интерпретатор, а бинарные входы читают как байты.

Условие when { branch 'main' } выбирает политику сохранения: остальные ветки проходят проверки и упаковку, но в этой схеме не архивируются. Это поведение опирается на контекст Multibranch. В обычном Pipeline нельзя ожидать, что такая проверка сама определит ветку по произвольному локальному репозиторию. archiveArtifacts сохраняет все три перечисленных через запятую файла: ZIP и оба внешних описания. allowEmptyArchive: false делает отсутствие совпадений ошибкой, но само по себе не требует присутствия каждого из трёх имён; для этого перед архивированием и выполнена отдельная проверка комплекта. onlyIfSuccessful: true ограничивает архивирование успешным состоянием; fingerprint: true добавляет механизм отслеживания Jenkins. Fingerprint Jenkins не следует выдавать за криптографическую подпись выпуска или современный SHA-256-манифест.

Ошибки и завершающие действия

Ненулевой код обычного sh завершает шаг ошибкой; последующие обычные стадии не продолжаются как успешные. В post условие always выполняет завершающее действие при разных исходах, а cleanup предназначено для окончательной уборки после остальных условий. Если агент потерян, операция, требующая его workspace, тоже может оказаться невыполнимой; нельзя обещать абсолютную очистку удалённой машины одним блоком. В рабочем варианте нужные диагностические файлы сохраняют перед удалением и контролируют срок жизни временных агентов.

Не добавляйте || true к тестам ради зелёного интерфейса: это меняет договорённость об ошибке. Если требуется получить код вручную, у sh есть returnStatus: true; после этого автор обязан сам сравнить результат и вызвать error при недопустимом исходе. Когда одно действие повторяется, проверьте его побочные эффекты. Повтор компиляции обычно безопаснее повторной публикации под изменяемым именем.

Где уместны credentials

Основной конвейер не обращается к закрытому сервису публикации, поэтому ему не нужен такой секрет. Если позднее появляется отдельный издатель, секрет передают только на время соответствующего шага через Credentials Binding. Минимальная форма выглядит так:

withCredentials([string(credentialsId: 'release-token', variable: 'TOKEN')]) {
    sh '''
        set +x
        python3 tools/publish.py dist/handbook-demo.zip
    '''
}

Это фрагмент интеграции, а не часть автономного стенда: publish.py потребуется отдельно реализовать для выбранного хранилища и он должен читать TOKEN из окружения, проверять ответ и возвращать ошибку при неуспехе. string связывает запись типа secret text с переменной; credentialsId — идентификатор записи Jenkins, не сам токен. Тройные одинарные кавычки передают текст оболочке без подстановки Groovy. set +x отключает трассировку команд оболочки. Маскирование журнала не защищает от программы, которая сама отправит секрет наружу, и от другого недоверенного процесса под тем же пользователем. Недоверенный код не запускают на агенте с секретами выпуска.
