Хранилище и производительность Git

Упаковка объектов, дельты, обслуживание, граф коммитов и измерение настоящего узкого места

Логический объект и его физическое представление

Чтение blob по идентификатору не обязано означать открытие одноимённого отдельного файла. Git может хранить много объектов в packfile, упаковочном файле. Часть объектов сжата самостоятельно, часть представлена через другую базу и набор инструкций получения результата. Такое различие, delta, здесь является способом физического хранения, а не текстовым diff коммита. После восстановления канонического содержимого идентификатор остаётся прежним.

Дельта может сказать «скопировать диапазон байтов базы, затем вставить новые байты». База не обязана быть непосредственной предыдущей версией файла в истории. Выбор делает упаковщик по сходству и ограничениям поиска. Объект-база сам может быть дельтой; чтобы прочитать конечный объект, придётся восстановить цепочку. Меньший размер на диске иногда достигается ценой большего CPU и чтений. Поэтому лозунг «максимальное сжатие всегда ускоряет Git» не выдерживает сравнения разных задач.

Что находится в pack и idx

Упаковочный файл начинается сигнатурой ASCII PACK, затем идут версия формата и число объектов в двоичной записи. После записей объектов есть контрольная сумма. Упакованная запись имеет собственный заголовок типа и длины; обычный текстовый заголовок blob 6\0 не лежит перед каждым сжатым объектом в прежнем виде. Для проверки идентификатора он логически восстанавливается. У дельты база указывается идентификатором либо относительным смещением внутри упаковки.

Соседний файл .idx служит индексом поиска: он связывает имена объектов с позициями в pack. Это не тот же индекс, который готовит следующий коммит; одинаковое слово относится к разным структурам. При нескольких упаковках общий multi-pack-index позволяет не искать объект отдельно во всех индексах. Вспомогательные битовые карты ускоряют некоторые проверки достижимости и составления передаваемого набора. Они экономят работу, не меняя логического графа объектов.

Небольшой опыт с похожими версиями

В отдельном репозитории создайте текст из нескольких тысяч одинаковых строк и меняйте одну добавленную строку в двадцати коммитах. Содержимое каждого blob будет различаться, но версии хорошо похожи. После обычной упаковки можно увидеть, что часть хранится дельтами. В собственном опыте на Git 2.43.0 двадцать таких состояний были упакованы, найдены дельта-записи, а fsck подтвердил корректность объектов. Это проверка механизма, а не измерение скорости большого рабочего проекта.

git count-objects -vH
git repack -ad
git count-objects -vH
git verify-pack -v .git/objects/pack/pack-ИМЯ.idx
git fsck --full

count-objects считает объекты и размеры служебного хранения; -v включает подробности, -H — удобные единицы размера. У repack флаг -a собирает подходящие объекты в новую упаковку, -d удаляет ставшие избыточными старые упаковки после успешного создания новой. Это не удаление всей недостижимой истории по обещанию читателя. В verify-pack -v подробный вывод показывает тип, восстановленный размер, размер записи, смещение, а для дельт — глубину и базу. Вместо условного ИМЯ выбирают существующий .idx, полученный в своём опыте.

Достижимость и сборка мусора

Garbage collection, сборка мусора, рассматривает данные, которые больше не нужны выбранным корням достижимости, и выполняет обслуживание. git gc объединяет несколько задач: упаковку, обработку журналов и других служебных структур. Какие объекты удерживаются, зависит от ссылок, журналов, возраста объектов и настроек. Удалённое имя ветки не означает немедленного уничтожения её объектов; истёкший журнал и последующее обслуживание могут изменить возможность восстановления.

Существуют cruft packs, упаковки недостижимых объектов с дополнительными сведениями о времени. Они позволяют эффективнее держать ещё не подлежащие окончательному удалению данные. Точные политики зависят от версии и конфигурации. Параметр немедленного удаления, например --prune=now у gc, меняет запас на восстановление и взаимодействие с параллельно создаваемыми объектами; его не подставляют в рецепт «ускорить всё». Задача измерения скорости обычно не требует стирать последние шансы восстановления.

Граф коммитов как ускоритель

Без дополнительного индекса обход истории должен читать объекты коммитов, распаковывать их и разбирать родителей. Файл commit-graph хранит нужные для многих обходов сведения компактнее: идентификаторы, деревья, родителей, даты и числа поколений. Число поколения помогает раньше исключить невозможное родство и уменьшить обход. Это кэш структуры графа, а не альтернативная истинная история. Его можно проверять и пересоздавать по объектам.

git commit-graph write --reachable --changed-paths
git commit-graph verify
git log --oneline -- path/to/file

write записывает вспомогательный граф, --reachable выбирает достижимые коммиты. --changed-paths добавляет фильтры изменённых путей для подходящих поисков истории файла. Это фильтры Блума: компактная структура может дать ложное «возможно менялся», но не должна давать ложное «точно не менялся». Подходящий отрицательный ответ позволяет пропустить дорогую проверку дерева. verify проверяет согласованность структуры. Возможность и детали ускорения зависят от версии Git и формы запроса.

Что измерять перед оптимизацией

Медленный status часто связан с числом файлов, обходом неизвестных каталогов и задержками метаданных. Медленный log -- путь — с глубиной истории и определением изменённых путей. Медленный fetch может упираться в сеть, серверное построение pack, клиентскую распаковку или запись диска. Большая папка .git не сообщает, какой из этих этапов дорог. Нужны время конкретной команды, объём обмена, CPU, операции диска и повторяемые условия опыта.

Сравнивайте одинаковую команду на одинаковой ревизии, отдельно отмечая холодный и прогретый кэш операционной системы. Первый запуск читает больше с диска, повторный может получать те же страницы из памяти. Запишите версию Git, файловую систему, расположение каталога, число путей и наличие фонового обслуживания. Изменение среднего времени с 0,8 до 0,4 секунды полезно только вместе с разбросом и условиями; одна удачная попытка не доказывает двукратное устойчивое ускорение.

Для подробной диагностики у Git есть Trace2, структурированные события выполнения. Переменная GIT_TRACE2_PERF включает сведения об этапах в соответствующем формате. В собственном учебном каталоге можно направить их в отдельный файл и сопоставить участки времени. Диагностические журналы реального проекта могут содержать пути и аргументы команд; при публикации примеров используют вымышленные каталоги и очищенные данные. После измерения выбирают воздействие на обнаруженную затрату, затем повторяют тот же опыт.

Меньше мегабайт, больше секунд

После более дорогой упаковки размер уменьшился, но чтение некоторых старых файлов стало медленнее. Возможно ли это без повреждения?

Разбор

Да. Для восстановления объекта может понадобиться больше работы по цепочке дельт, а условия кэша тоже могли различаться. Размер и задержка — разные метрики. Сначала сравнивают воспроизводимый запрос и проверяют целостность, затем выбирают баланс CPU, ввода-вывода и места.
