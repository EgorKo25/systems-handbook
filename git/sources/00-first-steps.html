Первый вход: от папки с файлом к понятной истории

Получим Git для своей учебной машины и проследим один текст через редактирование, подготовку и сохранение. В конце станет видно, почему открытый файл, выбранная версия и записанная история могут различаться.

Зачем хранить историю, если файл уже сохранён

Пусть мы пишем приветствие будущего приложения. Вначале оно обращается к читателю, затем к миру, а потом меняет форму обращения. Обычный редактор умеет сохранить последний текст в файл. Но при следующем сохранении прежние байты обычно заменяются. Чтобы выяснить, что было вчера и почему мы это изменили, приходится надеяться на память, резервную копию или папки с именами «последняя», «точно-последняя», «до-исправления».

Теперь представьте проект с программой, описанием запуска и примером настроек. Исправление часто затрагивает несколько файлов вместе. Возвращать каждый независимо опасно: старая программа может не понимать новые настройки. Нужна возможность записать выбранное состояние проекта как целое, снабдить его объяснением и связать со следующим состоянием. Система управления версиями организует такую историю. Версия здесь — определённое состояние сохраняемых файлов; она не обязана называться номером выпуска вроде 1.0.

Git — программа для ведения этой истории. Мы управляем тем, что в неё входит и когда появляется очередная запись. Поэтому Git не превращает случайную папку в правильный проект: он способен аккуратно сохранить и хорошее решение, и ошибку. Польза в том, что выбранные данные и последовательность решений становятся проверяемыми. Можно сравнить состояния, исследовать причину изменения и получить нужный сохранённый вариант, не угадывая его по имени папки.

Git, GitHub и GitLab — какие участники нам нужны

Git работает на вашем компьютере. GitHub и GitLab предоставляют платформы, на которых удобно размещать проекты, обсуждать изменения и организовывать дополнительные проверки. GitLab также можно развернуть на собственном сервере. Ни регистрация на сайте, ни доступ к интернету не требуются для сохранения истории в собственной папке установленным Git.

Если позже передадим историю на сервер, на нём появится ещё одна её копия. После этого местная правка сама не оказывается на сервере, а серверная сама не переписывает наши файлы. Обмен выполняется отдельными командами. Первую историю ниже создадим целиком локально — на своей машине. Так наблюдение не зависит от наличия аккаунта, сети и чужих разрешений.

Вместе с тем единственный диск не становится резервной системой от наличия Git. Потеряв диск вместе с сохранённой на нём историей, мы потеряем и её. Отдельная проверенная копия нужна для защиты от такого отказа. Различайте два вопроса: «как записаны и связаны состояния?» и «где ещё есть доступные копии этих данных?».

Получение и установка в личной Ubuntu-VM

VM, виртуальная машина, — отдельная гостевая операционная система на выделенных ей виртуальных ресурсах. Следующие команды установки предназначены для вашей собственной Ubuntu 24.04 внутри такой машины. На рабочем Windows для чтения книги установка не нужна. В ходе подготовки этой главы пакеты на компьютере пользователя не устанавливались.

Откройте терминал именно гостевой Ubuntu. Терминал показывает ввод и вывод; оболочка, например Bash, разбирает введённые команды и запускает программы. Сначала запросим установленную версию:

git --version
command -v git

git — имя программы. Параметр --version просит её напечатать версию и завершиться. command -v git показывает, что найдёт оболочка под этим именем: обычно путь вроде /usr/bin/git. Путь задаёт расположение файла в файловой системе. Это проверка выбранной программы, а не существования какого-либо проекта. Если оболочка сообщает, что команды нет, Git ещё нужно установить либо найти его предусмотренный каталог.

Отправная точка — официальная страница установки Git для Linux, затем пакетный механизм Ubuntu. Пакет — подготовленный для системы набор файлов программы и сведений о необходимых ей компонентах. В своей учебной Ubuntu используйте настроенные официальные источники пакетов:

sudo apt update
sudo apt install git
git --version
apt-cache policy git

sudo запускает выбранную команду с административными полномочиями после предусмотренной проверки пользователя. apt update обновляет сведения о доступных пакетах; это не массовое обновление всех установленных программ. apt install git получает и устанавливает пакет и требуемые зависимости. Перед подтверждением прочитайте предложенные изменения. apt-cache policy git показывает установленный вариант, доступный кандидат и настроенные источники; эта команда не устанавливает пакет.

Источник пакетов распространяет метаданные, то есть сведения о доступных версиях и файлах. Ubuntu проверяет подлинность этих сведений и соответствие полученных файлов ожидаемым контрольным суммам — значениям, вычисленным из их байтов. Доверие не возникает от похожего имени скачанного файла. Ошибку проверки источника не обходят отключением проверки: сначала выясняют состояние часов, адреса и настройки источников. Версия пакета Ubuntu может отличаться от последнего номера на сайте Git: Ubuntu сопровождает собственный выпуск и исправления. Для базового опыта достаточно Git 2.28 или новее; фактическая авторская проверка ниже выполнена на 2.43.0. Установка и проверка происхождения пакетов разобраны также в документации Ubuntu.

После установки Git не требуется запускать сетевую службу. Для этой главы нужны программа и место для собственных файлов. Пока интернет доступен, подготовьте их; дальше весь показанный опыт выполняется без сети. Если пакет уже установлен и подходит, повторная установка ради первого сохранения не нужна.

Сначала просто папка и текст

Выберите в своей VM место для учебных проектов. Все дальнейшие блоки выполняются последовательно в одной оболочке. Создадим новую папку git-first-steps-lab; если такое имя уже занято, возьмите другое и продолжайте с ним. Не подставляйте существующий рабочий проект. Команда pwd напечатает текущий каталог и поможет подтвердить место работы.

mkdir git-first-steps-lab
cd git-first-steps-lab
pwd
printf 'Привет, читатель!\n' > message.txt
cat message.txt

mkdir создаёт папку, cd меняет текущий каталог оболочки. printf выводит заданный текст; \n в его формате означает перевод строки. Знак > направляет этот вывод в файл, создавая его или заменяя прежнее содержимое. cat читает файл. В только что созданной папке такое перенаправление создаёт наш первый message.txt; при следующих шагах оно намеренно будет менять только этот учебный файл.

Пока есть обычная папка и обычные байты на диске. Git не начал записывать их историю от того, что программа установлена. Сохранение в редакторе и запись в историю Git — разные действия. На следующих шагах добавим к этой же папке служебное хранилище и выберем, какое состояние в него записать.

Репозиторий, снимок и запись о сохранении

Репозиторий — служебное хранилище Git с данными истории и необходимыми для работы сведениями. В нашем простом случае оно будет находиться в каталоге .git внутри проекта. Начальная точка в имени делает его скрытым для обычного списка файлов Linux; это не признак нахождения данных в интернете. Рядом остаётся message.txt, который мы читаем и редактируем.

Снимок — логически полное выбранное состояние сохраняемой части проекта: какие пути в неё входят и какое содержимое у каждого. Коммит, от английского commit, — записанная фиксация такого снимка вместе с объяснением, авторскими сведениями и связью с предыдущими фиксациями. Сейчас полезно различать выбранные данные и запись об их сохранении. Внутренние способы хранения и переиспользования одинаковых данных разберём в следующей главе; «полный снимок» не означает физическое копирование всего проекта заново при каждом действии.

Ещё одно имя потребуется уже при создании хранилища. Ветка — именованная линия развивающейся истории; нашу начальную ветку назовём main. Пока её история пуста. После получения первых фиксаций мы увидим точнее, на какую запись указывает это имя и почему оно не является ещё одной папкой. Создадим служебное хранилище:

git init -b main
git status

init означает инициализацию: Git создаёт необходимые служебные данные. -b main задаёт имя начальной ветки, чтобы оно не зависело от чужой настройки по умолчанию. Команда не отправляет проект на сайт и не сохраняет имеющийся текст в коммит. status сообщает состояние проекта. В свежем примере он покажет отсутствие коммитов и новый файл message.txt.

Если интерфейс Git английский, No commits yet означает «фиксаций пока нет», Untracked files — «файлы ещё не отслеживаются». Последнее означает, что файл существует, но ещё не выбран для сохранения Git. Наличие его имени в выводе status не равно наличию его содержимого в истории. Если показываются посторонние файлы, остановитесь и проверьте pwd: состав нашего примера пока ограничен одним собственным файлом.

Кто сделал запись: только необходимые местные настройки

Фиксация содержит имя и адрес автора. Для вымышленного учебного автора зададим их только в созданном репозитории. Это первые настройки, и их назначение уже понятно: они относятся к будущим записям истории, а не ко входу в GitHub или к паролю компьютера.

git config --local user.name 'Учебный читатель'
git config --local user.email 'reader@example.invalid'

config читает и записывает настройки. В показанной форме после имени параметра передано его новое значение. --local ограничивает запись текущим репозиторием; настройки других проектов и общая конфигурация пользователя не меняются. user.name и user.email — имена двух параметров, а кавычки сохраняют имя из двух слов одним аргументом, то есть одной передаваемой программе частью команды. Домен .invalid специально предназначен для условных адресов; этот адрес не является вашим настоящим ящиком.

Самостоятельно записанные имя и адрес не доказывают личность автора. Можно намеренно указать чужое имя, поэтому установление доверия требует других механизмов. Сейчас нам достаточно не переносить в учебные фиксации рабочий адрес. Остальные источники настроек и их приоритеты разберём позже, после устройства истории.

Подготовка: какой текст попадёт в первый коммит

Между редактированием и фиксацией Git позволяет выбрать состав следующего снимка. Этот выбранный вариант называется индексом; английское staging area означает область подготовки. Это не отдельная папка для ручного перекладывания файлов и не обещание «потом взять самую новую версию». Git сохраняет выбранное содержимое в служебных данных, а индекс связывает пути с этим подготовленным содержимым.

Такой промежуточный выбор нужен, когда в рабочей папке одновременно есть законченное исправление и незавершённая работа. Мы можем подготовить первое, проверить его и зафиксировать отдельно. Слово «рабочая» относится к файлам, с которыми непосредственно работают редактор и другие программы. Их совокупность внутри проекта называют рабочим деревом. Теперь подготовим наш единственный файл:

git add -- message.txt
git status

add обновляет подготовленную версию указанного пути по его текущему содержимому. -- отделяет параметры команды от путей: следующий аргумент — имя файла. На первом шаге так выбирается ранее не отслеживаемый файл. В дальнейшем той же командой можно подготовить новое содержимое уже известного файла. Название add, «добавить», не ограничивает её первым появлением файла.

После команды текст в редакторе не поменяется. Изменится служебное состояние: для будущего снимка выбрано Привет, читатель! с переводом строки. В status раздел Changes to be committed, «изменения для фиксации», покажет new file, «новый файл». Это подготовленный материал, а ещё не завершённая запись истории. Файл уже взят под отслеживание, хотя первого коммита всё ещё нет.

Первая фиксация и чтение истории

git commit -m 'Сохранить первое приветствие'
git status
git log --oneline

commit создаёт запись выбранного снимка. -m передаёт текст сообщения сразу, без запуска редактора. Сообщение объясняет смысл решения: позднее его будут читать вместе с изменением. Оно не является именем файла, именем ветки или командой для сервера. В нашем примере записывается подготовленное приветствие.

log читает историю; --oneline выводит по одной краткой строке на коммит. В строке будут сокращённый идентификатор и сообщение. Идентификатор — вычисляемое по содержимому обозначение сохранённой записи; его точные символы зависят в том числе от авторских данных и времени. Не нужно ожидать одинаковой строки идентификатора на разных машинах. Важно, что можно сослаться на определённую запись, а не на меняющееся выражение «последнее сохранение».

После первого коммита в нашей папке ничего не редактировалось: рабочий файл, подготовленная версия и выбранный сохранённый снимок совпадают. Status сообщит nothing to commit, working tree clean: «нечего фиксировать, рабочее дерево чистое». Это не утверждение о правильности приложения или наличии резервной копии. Оно описывает отсутствие отличий в рассматриваемом состоянии файлов.

Опыт, который отличает подготовку от последующего редактирования

Продолжим в той же папке. Заменим приветствие, подготовим его и после подготовки отредактируем ещё раз. Для краткости назовём первый текст вариантом A, второй B, третий C. Это метки нашего объяснения, а не настоящие идентификаторы Git.

printf 'Привет, мир!\n' > message.txt
git add -- message.txt
printf 'Здравствуйте, читатель!\n' > message.txt
git status
git show :message.txt
cat message.txt

show читает выбранные сохранённые данные. Здесь двоеточие перед путём в :message.txt специально выбирает подготовленное содержимое из индекса. Это обозначение для Git, не имя нового файла на диске. Вы увидите Привет, мир!. Обычный cat message.txt прочитает рабочий файл с другим текстом: Здравствуйте, читатель!.

МоментВыбранный сохранённый снимокПодготовленный вариантРабочий файл
После первого коммитаA: Привет, читатель!AA
Переписали файлAAB: Привет, мир!
Выполнили addABB
Переписали ещё разABC: Здравствуйте, читатель!

Git status теперь может показать один путь сразу в двух разделах. Он отличается между первым снимком и подготовкой, а также между подготовкой и рабочим файлом. Здесь нет двух независимых файлов с одинаковым именем: есть три разных состояния одного пути. Выполненный ранее add не следит за последующим вводом в редакторе.

Предскажите второй коммит

Если сейчас выполнить commit без нового add, какая из трёх строк попадёт в историю? Изменится ли открытый файл?

Показать переход состояния

В историю попадёт B, Привет, мир!. Рабочий файл сохранит C, Здравствуйте, читатель!. Commit читает уже подготовленный вариант; он не заменяет рабочие байты подготовленными и не подготавливает позднее изменение автоматически.

git commit -m 'Изменить адресата приветствия'
git status
git show :message.txt
cat message.txt

После второго коммита сохранённый и подготовленный варианты равны B, рабочий равен C. Неподготовленная правка осталась. Сообщение об успешной фиксации не обещало сохранение всего, что вы в этот момент видели в редакторе. Если повторить обычный commit без add, нового изменения для фиксации не будет: незаписанная рабочая правка сама в подготовку не переместится.

Ветка и HEAD: как Git выбирает место продолжения

У нас уже две записи. Вторая содержит связь с первой; предыдущую запись называют родителем коммита. Для простой последовательной работы возникает цепочка. Имя main указывает на её текущий конец, то есть на второй коммит. При следующей фиксации в этой ветке новое состояние получит связь со вторым, а имя main переместится на новую запись. Старые записи от этого не переписываются.

Теперь можно уточнить определение ветки: это имя, выбирающее конечный коммит линии истории. Ветка не является полной второй папкой проекта. Коммиты могут совместно входить в историю нескольких веток. Особое обозначение HEAD показывает текущий выбор Git. В нашем обычном режиме оно ссылается на имя выбранной ветки, а имя ветки — на коммит. Поэтому через HEAD можно обратиться к текущему сохранённому снимку.

HEAD → main → второй коммит → первый коммит

Рабочий message.txt: C
Подготовленный message.txt: B
message.txt в выбранном через HEAD снимке: B

Стрелки показывают «ссылается на», а не направление движения времени. HEAD и main не означают «последние байты на диске». Рабочее редактирование меняет файл, но само по себе не перемещает эти обозначения. После git init -b main имя начальной ветки уже было выбрано, однако до первого коммита готового конечного коммита ещё не существовало. Это объясняет, почему Git тогда сообщал об отсутствии истории.

git branch --show-current
git symbolic-ref --short HEAD
git show HEAD:message.txt

branch --show-current спрашивает имя текущей ветки: ожидаем main. symbolic-ref читает именованную ссылку, которая указывает на другую ссылку; --short просит краткое имя. В нашей ситуации вторая команда тоже покажет main. Здесь передан только один аргумент HEAD, поэтому команда читает связь, а не переназначает её. Третья команда показывает файл в выбранном коммите: часть HEAD: задаёт сохранённый снимок, часть после двоеточия — путь внутри него. Её результат B отличается от рабочего C.

Есть и режим, в котором HEAD выбирает сам коммит непосредственно, без имени ветки. Он понадобится при исследовании прошлых состояний и будет разобран отдельно. Сейчас важен наблюдаемый обычный путь: выбранная ветка main продолжает нашу историю, а рабочая правка C ещё не вошла ни в один коммит.

Второе имя без второй папки и следующее сохранение

Создадим дополнительное имя experiment, «эксперимент», для нынешнего сохранённого состояния. Это позволит увидеть разницу между созданием имени и продолжением выбранной ветки:

git branch experiment
git branch --show-current
cat message.txt

В форме git branch experiment команда создаёт ветку с этим именем на текущем коммите. Она не переключает наш текущий выбор: остаётся main. Рабочий файл также остаётся C. Теперь main и experiment выбирают один и тот же второй коммит, хотя ни дополнительных копий message.txt, ни дополнительного сохранения C не возникло. Имя experiment должно быть свободно; при повторном опыте не удаляйте прежнюю работу ради одинакового имени, а используйте сохранённую папку или другое новое имя.

Закончим позднюю правку: подготовим C, создадим третий коммит и прочтём историю с подписями имён.

git add -- message.txt
git commit -m 'Изменить форму обращения'
git log --oneline --decorate
git status
git show HEAD:message.txt

Параметр --decorate у log добавляет к строкам истории известные имена. Точные идентификаторы будут вашими, но отношения должны быть такими: HEAD выбирает main на третьем коммите, experiment остаётся на втором, за вторым следует первый. Стрелка HEAD -> main в выводе обозначает текущую ветку; отдельное имя experiment около предыдущей строки не является сообщением о второй папке.

HEAD → main → третий коммит → второй коммит → первый коммит
                              ↑
                          experiment

Третий снимок, индекс и рабочий файл: C

Рабочее состояние снова чистое: поздняя правка подготовлена и зафиксирована. Имя experiment не переместилось вслед за main, потому что мы не продолжали эту ветку. Так Git позволяет нескольким направлениям работы разделять прежние записи и развиваться дальше независимо. Переключение между направлениями и согласование их изменений потребуют своих действий; само наличие второй ветки их не выполняет.

Как продолжить, сохранив сделанное

Оставьте git-first-steps-lab со служебной папкой .git и рабочим файлом. На следующем занятии перейдите в неё через cd и начните с status и log. Повторно выполнять весь маршрут сверху не нужно: он уже изменил состояние. История и дополнительные имена сохраняются между запусками Git; это не временная сессия терминала. Коммит не зависит от открытого окна оболочки, пока сохраняется сам репозиторий.

Для чтения текущего файла нужен рабочий message.txt; для чтения истории нужны служебные данные. Перенос одного message.txt оставляет только выбранные текущие байты. Способ передачи репозитория на другой носитель/сервер разберём отдельно, включая проверку копии. Пока не удаляйте .git и не пытайтесь «почистить» его содержимое вручную: оно и есть необходимая часть нашего опыта.

Перед переходом дальше проверьте четыре наблюдения: у проекта три фиксации; main выбирает последнюю; experiment остаётся на предыдущей; рабочий текст совпадает с последним сохранённым. В следующей главе модель будет уточнена до устройства хранилища и трёх областей; отдельный опыт с note.txt будет явно отделён от сохранённого здесь message.txt. Вопрос «откуда взялся этот автор или редактор?» разберём в конфигурации после базовой модели.

Показанные действия с файлами и историей проверены на Git 2.43.0 в отдельной временной папке без сети. Проверка проследила все три снимка, сохранение поздней правки, связь HEAD с main и неподвижность experiment после продолжения main; соседний опыт note.txt не изменил первый проект. Использовались отдельные пустые источники конфигурации и учебная личность. Установка пакетов Ubuntu, Windows и обмен с сервером этой проверкой не охвачены.
