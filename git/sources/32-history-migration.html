32. Перенос проекта и изменение опубликованной истории

Удалённый файл исчезает из нового снимка, но продолжает существовать в старых объектах. Разберём, как спланировать перенос, доказать границы очистки и сохранить работоспособный проект, не принимая опасную команду за законченную миграцию.

Сначала определить, что именно переносится

Перенос исходников, перенос полной истории и удаление нежелательных данных из истории решают разные задачи. В первом случае достаточно выбранного дерева файлов. Во втором нужно сохранить граф коммитов, ветки, метки и необходимые внешние зависимости. В третьем придётся создать другой граф, потому что содержимое прежнего уже связано с идентификаторами объектов. Выбор влияет и на трудоёмкость, и на то, какие утверждения можно сделать после проверки.

Возьмём собственный учебный проект с приложением app.py, тестами и файлом config/private-demo.txt. В этом файле находится только заведомо выдуманная строка DEMO_CREDENTIAL_NOT_REAL. В первом коммите она записана в историю, во втором файл удалён. Рабочий каталог второго коммита выглядит чистым, но запрос к первому снимку по-прежнему вернёт строку. Не подставляйте действующие пароли для проверки этого механизма: нужное свойство полностью воспроизводится на искусственных данных.

git log --all --oneline -- config/private-demo.txt
git show HEAD~1:config/private-demo.txt
git ls-tree -r --name-only HEAD

Первая команда ищет изменения выбранного пути среди доступных ссылок. Вторая читает прежний объект непосредственно из дерева родителя. Третья показывает только имена текущего снимка. Ожидаемое различие и составляет главный опыт: отсутствие пути в последнем выводе не опровергает наличие старого содержимого. Удаление через git rm создаёт новый снимок; оно не переписывает уже существующие объекты.

Почему изменятся последующие идентификаторы

Пусть история имеет вид A — B — C: в A появился учебный файл, в B менялось приложение, в C файл удалён. После исключения файла дерево A изменится, следовательно, изменится идентификатор соответствующего коммита A′. Коммит B содержит идентификатор родителя A, поэтому для связи с A′ потребуется B′, даже если исходники приложения в B и B′ совпадают побайтно. То же рассуждение распространяется дальше по цепочке.

до:     A ── B ── C
после: A′ ── B′ ── C′

старый родитель внутри B ≠ новый родитель внутри B′

Ветви слияния усложняют форму графа, но не отменяют правило. Изменяются ссылки на родителей, иногда исчезают опустевшие коммиты, обновляются целевые объекты меток. Подпись прежнего объекта удостоверяла прежние байты и не превращается в подпись нового объекта. Поэтому миграция затрагивает выпуски, ссылки в документации, результаты проверок и сохранённые идентификаторы сборок. Сводка «удалили один файл» скрывает важную часть работы.

Исходное состояние нужно зафиксировать отдельно

Перед репетицией составляют перечень веток и меток, текущих идентификаторов, объёма объектов и правил внешнего хранения. Отдельно учитывают незаписанные изменения и локальные ветки участников: обычное клонирование сервера не захватывает неизвестную ему работу. Для чисто учебного опыта достаточно одного известного репозитория. Для организации потребуется определить, кто владеет каждым источником данных и какой именно набор считается полным.

git for-each-ref --format='%(refname) %(objectname)'
git status --porcelain=v1
git count-objects -vH
git rev-parse --is-shallow-repository

Формат for-each-ref делает имена и идентификаторы явными. Машинный формат status помогает заметить незаписанную работу. count-objects описывает хранение объектов, но не включает все внешние данные проекта. Проверка поверхностной истории нужна потому, что обрезанный граф не годится для доказательства очистки отсутствующих у проверяющего предков. Частичная копия тоже требует отдельного решения о получении отложенных объектов.

Резервная копия должна оставаться вне области последующего удаления и публикации. Если задача связана с действительной утечкой, копия содержит прежние чувствительные данные и требует соответствующего доступа. Наличие резервного bundle полезно для восстановления ссылок и объектов Git, но не означает резервирования Git LFS, рабочих незаписанных файлов, конфигурации сервера и вложенных проектов. Границы резервирования описывают заранее.

Репетиция выполняется на самостоятельной копии

Для известного локального учебного источника можно создать отдельную полную зеркальную копию. Здесь источник demo-origin.git — специально созданный репозиторий опыта. Путь назначения выбирают новым; личную рабочую копию не используют как место эксперимента.

git clone --mirror --no-local demo-origin.git migration-copy.git
git -C migration-copy.git fsck --full
git -C migration-copy.git for-each-ref --format='%(refname) %(objectname)'

Опция --mirror переносит пространство ссылок источника в зеркальную копию, а не создаёт обычное рабочее дерево. Опция --no-local для соседнего источника выбирает обычный механизм передачи вместо локальной оптимизации с возможными жёсткими ссылками на объекты. Это помогает отделить эксперимент от исходного хранения. Зеркало при этом переносит только то, что источник имеет и предоставляет; слово mirror не даёт знания о чужих ноутбуках и скрытых серверных хранилищах.

Первый fsck устанавливает исходную техническую целостность копии. Если уже здесь обнаружены ошибки объектов, переписывание и восстановление следует разбирать как разные задачи. Иначе отказ фильтра легко приписать неверному правилу отбора, хотя повреждение существовало раньше. Сохранённый перечень ссылок позволит позже объяснить, какие цели изменились и какие исчезли.

Внешний инструмент и точное правило отбора

git-filter-repo — отдельный инструмент, а не гарантированная часть установленного Git. В данной проверке он не устанавливался и переписывание им не запускалось. Следующий пример является рецептом будущей репетиции после проверки версии и официальной инструкции инструмента. Механизмы объектов и контрольные операции Git в этой главе отделены от этого непроведённого этапа.

cd migration-copy.git
git filter-repo --path config/private-demo.txt --invert-paths

Параметр --path задаёт выбранный путь от корня истории, а --invert-paths обращает отбор: этот путь исключается, остальные сохраняются. Если файл раньше назывался иначе, одного текущего имени недостаточно. Для учебного проекта следует заранее добавить переименование и проверить оба имени. Если такая проверка обнаружила старый путь, правило уточняют в новой репетиционной копии, сохраняя понятную последовательность действий.

Инструмент имеет защиту, рассчитанную на работу со свежей копией. Отказ этой защиты — повод разобраться, какой каталог выбран и какие данные в нём существуют. Привычное добавление --force превращает контрольную границу в пустую формальность. Перед использованием конкретной версии нужно прочитать её договор: набор обрабатываемых ссылок, обращение с origin, подписью, журналами и недостижимыми объектами влияет на дальнейший маршрут. Пересказ команды не заменяет проверку установленного выпуска.

Как доказать результат без печати содержимого

Проверка начинается с нового перечня ссылок и поиска исключённых путей во всех нужных историях. Но путь и содержимое — разные критерии. Та же строка могла оказаться в другом файле, сообщении коммита или внешнем артефакте. На учебном проекте это легко проверить, заранее добавив второй искусственный экземпляр. Контроль должен найти его и тем самым показать предел правила, которое удаляло только один путь.

Для собственного искусственного маркера можно написать сканер, который перечисляет достижимые объекты через rev-list --objects --all, читает их через cat-file и сообщает только идентификатор совпавшего объекта. Он не обязан печатать найденные байты. Для большого проекта удобен пакетный режим cat-file --batch: один процесс обслуживает много запросов. Если проверяются только blob-объекты, сообщения коммитов и меток останутся за пределами проверки; это ограничение должно быть явно записано.

Слова «совпадений нет» имеют смысл только вместе с описанием набора: какие ссылки являлись корнями обхода, какие типы объектов читались, какой критерий искался и какие внешние системы исключены. Поиск точной строки подтверждает отсутствие именно этой строки в исследованном наборе. Он не распознаёт автоматически преобразованный пароль, закодированную копию или неизвестные персональные сведения.

После содержательной проверки запускают fsck, тесты приложения и сборку на свежей копии преобразованного результата. Проверяют сохранённые полезные файлы, выбранные конечные деревья и доступность зависимостей. Нулевая ошибка fsck означает согласованность объектов, но ничего не сообщает о том, правильно ли программа отвечает на запрос. Успешный тест приложения, в свою очередь, не доказывает отсутствие нежелательных старых объектов.

Карта перехода и повторное принятие выпусков

Внешний инструмент сохраняет служебные карты соответствия прежних и новых идентификаторов. Их используют для перевода ссылок в задачах, документации и протоколах сборки. Если коммит исчез, нельзя выдумывать ему точного преемника: карта должна отражать этот факт. До использования карты проверьте её формат по документации выбранной версии и сохраните рядом описание выполненного преобразования.

Метки выпусков и подписи разбирают отдельно. Если выпуск должен продолжать существовать, проверяющий сравнивает полезное дерево, повторяет необходимые проверки и создаёт новое свидетельство принятия по действующей политике. Старый подписанный объект не стоит молча подменять новым под тем же историческим утверждением. В журнале переноса должно быть понятно, какая версия существовала до миграции и какое отношение к ней имеет новый выпуск.

Почему действительный секрет сначала отзывают

Удаление из истории не отзывает уже увиденный пароль. Если бы учебная строка была действующим ключом, первым самостоятельным действием стали бы отзыв или замена полномочия и проверка зависимых систем. Историю очищают для сокращения дальнейшего распространения, а не для доказательства того, что никто не успел получить доступ. Серверные журналы, резервные копии, форки, архивы и старые клоны имеют собственный жизненный цикл.

Публикация преобразованного графа требует согласованного переключения участников. На время перехода фиксируют, от какого состояния выполнена репетиция, приостанавливают конфликтующие изменения и определяют новый источник. После принятия результата безопаснее получить новую копию и переносить нужную незаписанную работу осознанно. Слияние старой ветки целиком способно вернуть удалённую историю обратно. Изолированный перенос выбранных изменений тоже проверяют на нежелательные данные.

Когда достаточно экспорта выбранного снимка

Для передачи только текущих исходников иной раз нужен обычный архив выбранного дерева. В нашем учебном проекте экспорт второго коммита исключает удалённый учебный файл и каталог .git. При этом он не очищает исходный репозиторий и не переносит историю. Выбор полезен, когда получателю история не требуется, а задача состоит именно в выпуске проверенного набора файлов.

git archive --format=tar --prefix=demo/ --output=../demo-source.tar HEAD

Формат tar выбирает контейнер архива, prefix помещает файлы в общий верхний каталог, output записывает результат за пределы дерева исходников. HEAD указывает конкретный экспортируемый снимок. Атрибуты export-ignore и export-subst могут влиять на состав и байты; проверьте их до сравнения. Вложенные репозитории и внешние LFS-данные требуют отдельного маршрута упаковки. Не следует обещать полную готовность сборки по одному наличию tar-файла.

Оценка затрат и критерий завершения

Измеряйте время чтения исходной истории, преобразования, проверки и повторной доставки отдельно. Размер pack-файлов после переписывания зависит от упаковки и не обязан немедленно уменьшиться в ожидаемой пропорции. Переписывание ради экономии нескольких мегабайт может оказаться дороже хранения, если оно ломает множество долговечных ссылок. Для утечки данных критерий иной: уменьшение размера вообще не является главным доказательством результата.

Миграция закончена, когда определённый набор данных перенесён, проверки воспроизведены на новой копии, внешние зависимости учтены и участники знают правила дальнейшей работы. Команда фильтра — один этап этого процесса. Практическая самостоятельная задача: на искусственном проекте предсказать различие между удалением файла, экспортом нового снимка и переписыванием графа; затем объяснить, какие старые данные каждый вариант оставляет доступными.

Первичные источники для продолжения: руководство git-filter-repo, семантика clone, обход объектов rev-list, чтение объектов cat-file, экспорт archive, проверка объектов fsck. Реальное преобразование внешним фильтром и публикация изменённой истории здесь не выполнялись.
