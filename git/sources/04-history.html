История: граф родителей и выбор ревизий

Как читать log, различать время и порядок происхождения и выбирать нужное множество коммитов

Стрелка направлена к прошлому

Коммит хранит идентификаторы родителей. У первого коммита родителей нет, у обычного следующего один, у коммита слияния обычно два. Дочерние коммиты в объекте не перечислены: чтобы узнать потомков, нужно исследовать другие объекты или вспомогательный индекс. Получается направленный ациклический граф, DAG — directed acyclic graph. Направленность означает определённое направление связи; ацикличность — невозможность пройти по родителям и вернуться к исходному объекту.

Родители в объектах: D → B → A
                    D → C → A

Обычное рисование «вперёд во времени»:
        B ──┐
       /    D
      A ─ C┘

В текстовых схемах авторы часто рисуют линии слева направо от предка к потомку, хотя внутри объекта ссылки смотрят обратно. Не путайте соглашение рисунка с форматом хранения. Из D достижимы B, C и A: последовательность переходов по родителям существует. Из B коммит C недостижим. Ветка указывает на вершину, а её прошлое определяется достижимостью. Поэтому ветка не содержит отдельной физической папки со всеми своими коммитами.

Достижимость определяется стартовыми вершинами

Один и тот же набор объектов можно исследовать от разных корней. git log main обходит предков main, git log topic — предков topic. Отсутствие коммита в первом выводе не доказывает его отсутствие на диске. Ветка могла переместиться, другой коммит мог остаться только под меткой, а прежний потомок — в журнале ссылки. Это различие важно после reset: команда изменила точку начала привычного обхода, а не обязательно удалила объект.

Граф коммитов связан с графом остальных объектов: каждый коммит ведёт к дереву, дерево — к поддеревьям и blob. git rev-list --objects --all перечисляет объекты, достижимые из всех выбранных этим режимом ссылок. --objects расширяет вывод за пределы одних коммитов; --all добавляет ссылки как стартовые точки. Это не простой список всех файлов каталога objects: там могут лежать недостижимые объекты. Для включения журналов в соответствующий обход предусмотрен --reflog. Набор корней нужно называть явно, иначе слово «всё» вводит в заблуждение.

Связь с родителем записана в неизменяемом объекте, а имя ветки изменяемо. Новая ветка на старом коммите не добавляет ребро. Удаление имени не разрезает родительские связи в самих коммитах. Эти инварианты позволяют мысленно разбирать граф независимо от текущих красочных подписей log. Подпись помогает найти вершину, но не становится отдельной копией её прошлого.

Время не задаёт происхождение

В коммите есть даты автора и создателя. Часы могли отставать; при переносе старого изменения авторская дата может быть намного раньше даты создания нового объекта. Два независимых автора работают параллельно. Следовательно, дата не доказывает, что один коммит является предком другого. Родительская связь доказывается идентификаторами, а не сортировкой времён. Это особенно важно при поиске «последнего изменения»: последняя показанная строка журнала зависит от режима обхода и отбора.

git log --graph --oneline --decorate --all
git log --first-parent --oneline main
git show --stat HEAD

--graph рисует связи символами, --oneline сокращает представление коммита до строки, --decorate добавляет известные имена ссылок, --all начинает обход от всех ссылок, а не только текущей. --first-parent при встрече слияния продолжает путь только через первого родителя: так удобно видеть последовательность интеграции в выбранную ветку. Это фильтр обхода, а не удаление боковой истории. show --stat показывает выбранную фиксацию и сводку её файловых изменений.

Порядок обхода и порядок показа

git log --topo-order --graph --oneline упорядочивает показ с учётом топологии: родители не появляются раньше своих показываемых потомков, и боковые линии удобнее читать как связанные участки. --date-order также уважает отношение родителей, но сильнее следует датам среди допустимых вариантов. Это не изменение графа, а выбор линейного представления частичного порядка. У параллельных B и C может вообще не существовать отношения «раньше по происхождению», хотя экран вынужден вывести одну строку первой.

Фильтры и форматирование тоже разделены. --max-count=5 ограничивает выбранный вывод пятью коммитами; --reverse обращает порядок выдачи. Не следует ожидать, что такая комбинация автоматически найдёт «первые пять коммитов с начала всего проекта»: сначала нужно установить правила отбора. Датовые фильтры особенно чувствительны к немонотонным часам. У --since-as-filter другой договор обхода, чем у обычного раннего ограничения по дате: оно исследует весь выбранный диапазон и затем фильтрует подходящее. Проверяйте наличие режима в установленной версии.

Как обозначают предков

HEAD^ означает первого родителя, HEAD^2 — второго родителя слияния. HEAD~2 означает два перехода по первому родителю. У обычного линейного участка HEAD^^ и HEAD~2 совпадают; у слияния HEAD^2 выбирает другую сторону и вовсе не значит «два коммита назад». Запись HEAD^{commit} требует разыменовать объект до коммита, например проходя через аннотированную метку. Не каждый объект обязан быть коммитом: Git умеет адресовать и деревья, и содержимое файлов.

Сокращённого идентификатора достаточно, пока он однозначен в данном репозитории. Рост истории может сделать прежнее сокращение неоднозначным. Для внешней записи результата выпуска сохраняют полный идентификатор. Для машинного сценария git rev-parse --verify HEAD^{commit} проверяет, что указанная ревизия существует и разрешается в коммит. Флаг --verify требует проверку ожидаемого аргумента, а не просто печать чего-то похожего на имя.

Разыменование типа и разрешение неоднозначности

v1.0^{} последовательно снимает слои аннотированных меток до объекта, который уже не является меткой. v1.0^{commit} дополнительно требует коммит, v1.0^{tree} получает соответствующее дерево. Лёгкая метка уже может прямо указывать на коммит. Поэтому нельзя считать результат rev-parse v1.0 всегда идентификатором коммита: для аннотированной метки это может быть сам объект tag.

Полное имя refs/heads/release точнее короткого release, когда существуют одноимённые ветка и метка. Git имеет порядок разрешения коротких имён и может предупредить о неоднозначности. В сценарии выпуска лучше указать требуемое пространство имён и тип объекта явно. Если аргумент поступил как данные, разделяйте параметры и ревизию предусмотренным режимом команды; строка, начинающаяся с дефиса, не должна неожиданно становиться флагом.

git show HEAD:path/to/file читает объект по пути в снимке. Это не переход оболочки в каталог и не путь внутри текущей файловой системы. Путь ./file в синтаксисе ревизий может иметь специальную интерпретацию относительно текущего места; для воспроизводимого машинного чтения удобнее явно установить корень и полный путь внутри дерева. Имя пути с двоеточием также требует внимательного отделения обозначения объекта от буквального имени.

Диапазон — операция над множеством

Пусть история разошлась после A: основная линия дошла до B, боковая до C и E. git log B..E покажет коммиты, достижимые из E, но недостижимые из B: C и E. Две точки не означают непрерывный отрезок календаря. git log B...E выбирает симметрическую разность: коммиты, достижимые только с одной из сторон. Здесь это B, C и E. Общий предок A исключён.

       B       main
      /
     A
      \
       C ─ E   topic

main..topic   = {C, E}
topic..main   = {B}
main...topic  = {B, C, E}

Порядок показа выбранного множества задаётся отдельно. git log --left-right --oneline main...topic помечает сторону каждого коммита: знак < для левого аргумента и > для правого. Это позволяет отличать «наша ветка отстаёт» от «обе стороны независимо продвинулись». Число впереди и позади в статусе рассчитывается относительно локально известной отслеживаемой ссылки; без свежего получения данных оно не сообщает текущее состояние сервера.

Проверить множество числом и списком

git rev-list --left-right --count main...topic
git log --left-right --oneline main...topic
git rev-list topic --not main

Первый вызов печатает два количества: только слева и только справа. --count заменяет перечень подсчётом; --left-right сохраняет раздельность сторон. Второй раскрывает конкретные элементы. Третий выражает main..topic в явной форме: --not меняет смысл следующих стартовых ревизий на исключение их достижимого прошлого. Несколько положительных вершин сначала образуют объединение, а исключаемые вычитаются. Это операции над множествами, а не последовательное «пройти от main к topic».

Форма M^! выбирает M, исключая прошлое всех его родителей; для задачи получения только этого коммита она удобнее ручного перечисления. M^@ обозначает набор родителей M. При слияниях такие сокращения особенно полезно раскрывать через rev-list и сравнивать с git show --no-patch --format='%H %P' M. --no-patch скрывает файловый diff, --format задаёт поля: полный идентификатор и упорядоченные полные идентификаторы родителей.

История пути и история решения

git log -- path ограничивает показ изменениями указанного пути. Разделитель -- отделяет путь от ревизий. Но файл могли переименовать; для одного файла --follow пытается продолжить историю через обнаруженные переименования. Обнаружение основано на сопоставлении содержимого и имеет ограничения: имя файла не является неизменной личностью, сохранённой внутри blob. История отдельного пути и полный граф интеграций отвечают на разные вопросы.

Для поиска причины полезно читать саму разницу и соседние связанные файлы. Коммит с исправлением программы мог одновременно изменить конфигурацию; просмотр только одного файла скрывает договор между ними. git log -p -- path добавляет заплатки к журналу: -p здесь означает показ различий, а не подготовку, как в add -p. Значение короткого флага определяется командой. Отсюда правило чтения справки: нельзя переносить смысл буквы из одной команды Git в другую автоматически.

Упрощение истории может скрыть важную развилку

Когда указан путь, Git оценивает, где его содержимое изменялось, и может упростить граф. Коммит слияния, чей результат для этого пути совпадает с одним родителем, способен исчезнуть из краткого представления истории пути. Это полезно для чтения, но опасно для вывода «этого merge вообще не было». --full-history меняет правила обхода и упрощения для истории с путями; его не следует понимать как включение вообще всех объектов репозитория независимо от фильтра.

Для поиска изменения числа вхождений строки используют git log -S 'listen_port' -- config.ini. -S выбирает коммиты, где поменялось количество вхождений указанной строки в сравнении. -G 'port[[:space:]]*=' ищет подходящие строки добавления или удаления по регулярному выражению. Замена одной строки другой может удовлетворять -G, сохраняя общее количество слова и не удовлетворяя -S. Это разные гипотезы о происхождении изменения.

git blame -L 10,20 -- server.py относит текущие строки 10–20 к последним найденным изменившим их коммитам. -L ограничивает участок. Это не поиск человека, который придумал решение: форматирование, перенос блока или сгенерированный файл могут изменить атрибуцию. Для понимания переходят из найденного коммита к его родителю и читают полный diff. Автоматическая привязка строки — отправная точка исследования, а не окончательное объяснение причины.

Проверить предположение о родстве

git merge-base --is-ancestor A B завершится кодом 0, если A является предком B, кодом 1 — если нет; другие ошибки нужно отличать от отрицательного ответа. --is-ancestor превращает поиск общего основания в проверку конкретного отношения. Это полезнее визуального угадывания по длинному журналу. Например, перед переносом серверной ветки можно точно установить, является ли новая вершина продолжением старой. Проверка не обещает совместимости программы: достижимость графа и работоспособность кода остаются разными свойствами.

Когда привычное родство меняется из-за границы чтения

У неглубокого клона есть специальная граница истории. Коммит на ней может содержать имена родителей в исходном объекте, но обычный обход рассматривает его как ограничение доступной истории: нужных родителей локально нет. Поэтому отсутствие найденного общего основания не всегда доказывает независимое происхождение проектов. Сначала проверяют полноту локальной истории и настройки получения. Для исследования старых причин требуется загрузить соответствующие объекты и снять либо углубить границу предусмотренной командой fetch.

Дополнительная особенность — заменяющие ссылки из пространства refs/replace. Они позволяют некоторым операциям читать один объект вместо другого без физического переписывания исходного. Если родство или содержимое неожиданно различаются между машинами, проверяют такие локальные условия наряду с версиями Git. Для обычного воспроизводимого опыта в новом репозитории их нет. Смысл проверки не в подозрении ко всем настройкам, а в точном вопросе: какой именно граф увидела конкретная команда с её окружением?

Результат merge-base --is-ancestor также требует аккуратного чтения кода завершения. Код 1 — отрицательное отношение для успешно исследованного запроса; ошибка неизвестной ревизии или повреждённого объекта не должна превращаться в тот же бизнес-ответ. В сценарии автоматизации сначала подтверждают разрешение ревизий и доступность нужной истории, затем принимают решение по отношению вершин.

Второй родитель

У D родители B и C, а у B родитель A. Чему равны D^2 и D~2? Что произойдёт, если у A нет родителей?

Разбор

D^2 выбирает C. D~2 проходит через первого родителя B к A. Попытка взять родителя корневого A завершится ошибкой: Git не создаёт условный «нулевой коммит» перед началом истории.

К дополнительным механизмам: blame, локальная замена объектов, порядок, фильтры и поиск строк.

Первоисточники: обозначения ревизий и диапазоны, обход истории, множества коммитов, проверка родства.
