Подмодули: два хранилища и один закреплённый коммит

Подмодуль позволяет внешнему проекту ссылаться на точное состояние другого репозитория. На диске это выглядит как вложенная папка, но сохранённые данные, подготовка изменения и публикация распределены между двумя историями. Разберём, где находится каждая часть и как получить воспроизводимое состояние на новой машине.

Что хранит основной проект

Обычное дерево связывает имя файла с blob или имя подкаталога с другим tree. Для подмодуля используется запись gitlink: режим 160000 и идентификатор коммита другого репозитория. Внешний проект запоминает этот идентификатор. Из этого не следует, что все объекты дочерней истории автоматически скопированы в его собственное хранилище.

Рядом обычно находится отслеживаемый файл .gitmodules. Он описывает имя подмодуля, путь и адрес получения. Это часть версионируемых данных проекта, которую увидит следующий читатель. Локальная конфигурация может дополнительно содержать настройки и переопределения. Адрес помогает найти объекты, а gitlink определяет нужный коммит; эти роли полезно исследовать отдельно.

основной коммит
  дерево
    .gitmodules → обычный blob с настройками
    deps/library → gitlink 160000 → коммит L1

дочернее хранилище
  L1 → своё дерево → свои файлы

Если L1 недоступен из дочернего хранилища на новой машине, одного внешнего коммита недостаточно для сборки. Поэтому проверка автономной поставки должна проверять наличие всех закреплённых объектов. Знакомое имя ветки библиотеки не заменяет конкретную цель: ветка способна переместиться после выпуска приложения.

Собственный локальный пример

Подготовьте два отдельных учебных репозитория в соседних каталогах: library с файлом lib.txt и outer с файлом app.txt. В каждом уже должен существовать первый коммит. Используйте учебную личность и изоляцию настроек предыдущих опытов. Дальнейшие команды выполняются в outer.

git -c protocol.file.allow=always submodule add ../library deps/library
git status --short
git ls-files --stage -- deps/library
git diff --cached -- .gitmodules
git commit -m "Attach the library version"

Здесь разрешение файлового транспорта передано только этой команде и относится к известному соседнему учебному репозиторию. Его не следует записывать глобально ради неизвестного проекта. В индекс попадают описание модуля и gitlink. Команда ls-files --stage показывает режим 160000, идентификатор и стадию ноль. В реальном опыте идентификатор совпал с HEAD исходной library.

Наблюдение отличается от простого копирования каталога с исходниками. Если изменить lib.txt внутри подмодуля, внешнее дерево не начнёт хранить этот файл как собственный blob. Чтобы сохранить изменение библиотеки, нужно сначала создать коммит в дочернем репозитории. Затем внешний проект сможет закрепить уже другую цель.

Где физически расположена .git

git -C deps/library rev-parse --git-dir
git -C deps/library rev-parse --show-toplevel
git -C deps/library status --short --branch

В современном обычном размещении deps/library/.git может быть текстовым файлом перенаправления, а основное дочернее хранилище находится внутри служебного каталога внешнего проекта, например в области modules. Поэтому программа, безусловно ожидающая каталог путь/.git/objects, работает ненадёжно. Надёжнее запросить расположение у Git.

Ключ -C меняет каталог работы подкоманды. После этого status относится к библиотеке. Внешний status описывает отношение своей записи gitlink к состоянию вложенного проекта. Два вывода отвечают на разные вопросы и могут одновременно сообщать разные виды изменений.

Не переносите вручную внутренние каталоги modules, пытаясь «починить ссылку». В этой структуре есть отношения путей и метаданных. Сначала определите, где находятся собственные неотправленные коммиты библиотеки, и сохраните их через подходящие ссылки или отдельную копию. Манипуляции расположением без понимания этих данных затрудняют восстановление.

Новая копия и явная инициализация

git clone ../outer outer-copy
cd outer-copy
git submodule status
git -c protocol.file.allow=always submodule update --init
git -C deps/library branch --show-current
git -C deps/library rev-parse HEAD

Обычный clone внешнего проекта не обязан сразу получить рабочие данные всех подмодулей. --init подготавливает их локальную конфигурацию, update получает нужные объекты и приводит рабочую копию к закреплённому коммиту. В нашем опыте после этого дочерний HEAD был отделён от имени ветки: branch --show-current не вывел имени.

Такое состояние ожидаемо для обычного checkout-обновления подмодуля. Внешний проект просил конкретный коммит, а не бесконечно движущуюся текущую версию библиотеки. Если собираетесь развивать её код, сначала создайте или выберите осознанную дочернюю ветку. Иначе новые коммиты окажутся в отделённой линии, которой нужно дать имя перед уходом.

Для вложенных зависимостей можно добавить --recursive, а при первоначальном clone — --recurse-submodules. Эти параметры расширяют область обращения к другим репозиториям. Сначала прочитайте адреса и ожидаемую структуру: рекурсия способна потребовать дополнительных прав, сети, места и времени.

Изменение библиотеки и изменение внешнего индекса

Создайте в дочернем репозитории новый коммит L2, например заменив v1 на v2 в lib.txt. Внешний проект теперь наблюдает другую позицию вложенного HEAD. Но его индекс пока продолжает ссылаться на L1. Это проверено отдельным опытом: новая дочерняя фиксация не обновила внешний gitlink автоматически.

git -C deps/library switch -c lab-change
printf 'v2\n' > deps/library/lib.txt
git -C deps/library add lib.txt
git -C deps/library commit -m "Library version two"
git status --short
git rev-parse :deps/library
git -C deps/library rev-parse HEAD
git add deps/library
git diff --cached --submodule=log
git commit -m "Use library version two"

До внешнего add два запроса идентификаторов дают L1 и L2. После него индекс внешнего проекта выбирает L2. Параметр --submodule=log просит показать изменения подмодуля через сведения о коммитах, а не ограничиться малообъяснимой заменой одной строки идентификатора. Чтобы понять смысл поставки, всё равно нужно прочитать саму дочернюю правку.

Внешний dirty-статус может быть связан и с несохранённым содержимым библиотеки, когда её HEAD ещё не менялся. Поэтому различайте три уровня: дочерние рабочие файлы, дочерний коммит и внешний индекс. Подавление показа изменений подмодуля скрывает наблюдение, но не делает незавершённые данные воспроизводимыми.

Порядок публикации и проверка с чистой машины

Для общей работы сначала публикуют дочерний коммит в доступное другим хранилище библиотеки. Затем публикуют внешний коммит, который на него ссылается. В противном порядке читатель может получить приложение, но не найти требуемую библиотеку. Наличие L2 в вашем локальном modules не доказывает его доступности получателю.

Полезная приёмочная проверка — свежая копия внешнего проекта с явным получением всех нужных модулей и сборкой. Она обнаруживает зависимость от незаписанных рабочих файлов, личных адресов и случайно оставшихся локальных объектов. Если сервер не отдаёт нужный коммит, сначала проверяют публикацию ссылки и правила доступа. Ослабление ограничений сервера не является универсальным способом исправить пропущенный этап публикации.

Ключ push --recurse-submodules=check позволяет дополнительно проверять некоторые условия доступности подмодульных изменений перед отправкой. Режимы рекурсивной отправки зависят от настроенных адресов и отношений веток. Перед использованием на важном проекте нужно испытать собственный порядок работы, а не считать один флаг распределённой транзакцией двух серверов.

Закреплённый коммит и update --remote

Обычное обновление следует записи внешнего проекта. Вариант git submodule update --remote получает цель на основе настроенной удалённой ветки библиотеки. Поле branch в конфигурации может участвовать именно в таком выборе. Оно не превращает уже записанный gitlink в символическую ссылку на ветку.

После перехода на более новый дочерний коммит внешний проект должен отдельно решить, принимает ли он эту версию. Проверка совместимости и внешний add остаются необходимыми действиями. Иначе сборка «последнего» состояния на двух машинах может различаться во времени, хотя оба пользователя начинали с одной внешней ревизии.

Адреса, относительность и доверие

Относительный адрес в .gitmodules разрешается с учётом адреса внешнего репозитория, а не произвольной папки, из которой человек сегодня запустил команду. Это удобно для соседних проектов на одном сервере. При перемещении зеркала или автономной копии нужно проверить, куда реально ведёт такое отношение. Имя каталога на флэшке и адрес исходного сервера — разные системы размещения.

После изменения общего описания может потребоваться git submodule sync --recursive, чтобы согласовать локальные адреса с опубликованными. Эта команда не доказывает доступности новых адресов и не проверяет доверие их владельцу. Локальное переопределение иногда специально нужно для учебного зеркала, поэтому перед синхронизацией полезно сохранить и сравнить текущие значения.

При разборе неизвестного проекта сначала изучите .gitmodules, пути, транспорт и рекурсивный состав. Запуск дополнительных протоколов и включение обновляющих сценариев — самостоятельные решения. Учебный пример разрешает file только для известных временных репозиториев; глобальное разрешение всех транспортов меняет границу для других проектов и здесь не требуется.

Удаление, восстановление и стоимость устройства

Слияние разных закреплённых версий

Две внешние ветки могут изменить один gitlink на разные дочерние коммиты. Если одна версия продолжает другую и нужные объекты доступны, Git способен использовать это отношение. При разошедшихся дочерних историях требуется отдельное решение: выбрать подходящий коммит либо сначала объединить библиотеку в её собственном репозитории. Текстовое объединение .gitmodules само по себе не объединяет код библиотеки.

Исследуйте идентификаторы сторон через конфликтные стадии внешнего индекса, затем изучите их граф внутри дочернего хранилища. После согласованного дочернего слияния проверьте библиотеку, опубликуйте её результат и подготовьте новую внешнюю ссылку обычным add пути подмодуля. Внешний коммит сохранит выбранную цель, а причины решения должны быть понятны из сообщения и проверок.

При отсутствии дочернего объекта Git может не иметь данных для проверки отношений предков. Получение недостающей истории решает именно эту нехватку сведений. Оно не доказывает функциональную совместимость двух версий. Сначала восстановите наблюдаемость графа, затем принимайте решение по поведению приложения.

Команда deinit снимает локальную регистрацию и может убрать рабочие данные подмодуля. Удаление gitlink из истории текущего проекта — другой шаг. Принудительный вариант, как и удаление каталога вручную, опасен для несохранённых дочерних правок. Сначала исследуйте дочерний status, ветки и неотправленные коммиты, затем выбирайте нужный уровень очистки.

Исторические коммиты внешнего проекта могут продолжать ссылаться на старые версии библиотеки. Поэтому удаление актуального подмодуля не означает, что его объекты больше никому не нужны. Для воспроизведения старого релиза требуется политика хранения зависимостей. Архив только внешних исходников может не включать содержимое всех подмодулей автоматически; состав поставки проверяется отдельно.

Распараллеливание получения через параметры jobs способно сократить ожидание независимых модулей, но увеличивает число соединений и нагрузку. У каждого подмодуля своё хранилище и история. Перед дроблением проекта оцените, нужна ли независимость версий и прав, насколько сложен согласованный выпуск и как часто изменения должны фиксироваться атомарно. Измеряйте полную подготовку чистой сборочной среды, а не только время clone внешнего репозитория.

Проверены режим 160000, совпадение gitlink с дочерним коммитом, файл перенаправления .git, закреплённая цель новой копии и отдельная подготовка L2 внешним add. Источники: устройство подмодулей, команды submodule, формат .gitmodules, Pro Git: Submodules.
