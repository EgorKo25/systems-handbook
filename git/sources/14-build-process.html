Что происходит между исходником и работающей программой

Сборка — управляемое превращение входных данных в результат, который можно проверить, сохранить и запустить. Чтобы понимать её сбои, проследим путь от файла в Git до процессов операционной системы и разберём, какие результаты вообще стоит называть собранной программой.

У сборки есть входы, исполнители и выходы

Пусть в репозитории лежит app.py. Git хранит байты этого файла и историю изменений. Команда запуска Python обращается уже к файловой системе: наличие коммита само по себе ничего не исполняет. Оболочка находит интерпретатор, создаётся процесс с аргументами, переменными окружения и рабочим каталогом. Интерпретатор открывает файл, разбирает текст, создаёт внутреннее представление программы и выполняет его. Именно процесс запрашивает память, открывает сокеты, читает конфигурацию и возвращает код завершения. Исходник, процесс и сохранённый результат сборки — разные объекты с разным временем жизни.

Артефакт — сохранённый выход определённого действия: архив приложения, исполняемый файл, пакет установки, отчёт тестов. Название не означает, что файл уже годится для выпуска. Исполняемый файл с ошибкой и повреждённый отчёт тоже являются результатами действий. Готовность устанавливает процедура проверки и принятия. В учебном проекте доставляемым артефактом будет ZIP с исходниками маленькой Python-службы; для его работы на целевой машине понадобится подходящий Python. Архив не превращает интерпретируемую программу в самостоятельный машинный код.

Полезно записать модель выход = действие(входы, инструмент, параметры, среда). «Входы» включают больше, чем видимые исходники: шаблон генератора, файл зависимостей, словарь переводов, конфигурацию компилятора. Инструмент тоже является входом: новая версия упаковщика способна иначе записать архив. Среда становится скрытым входом, когда программа читает текущий часовой пояс, имя компьютера или случайный файл из домашнего каталога. Воспроизводимость начинается с превращения таких зависимостей в явные условия.

Компиляция, связывание и интерпретация

В обычной сборке C сначала препроцессор обрабатывает директивы и включаемые заголовки. Компилятор анализирует полученный текст, проверяет допустимость конструкций и формирует код следующего представления; ассемблер создаёт объектный файл. В объектном файле ещё могут оставаться обращения к символам других модулей. Компоновщик, или linker, объединяет объектные файлы и необходимые библиотеки, разрешает ссылки и формирует исполняемый файл либо библиотеку. Динамические зависимости могут окончательно подключаться загрузчиком уже при запуске. Таким образом, успешная компиляция одного модуля не доказывает успешное связывание всей программы и доступность библиотек на другом компьютере.

gcc -E hello.c -o hello.i
gcc -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc hello.o -o hello

Это иллюстрация этапов для среды с установленным GCC и обычным файлом C, а не обязательная подготовка Python-практикума. -E останавливается после препроцессора; -S оставляет ассемблерный текст; -c создаёт объектный файл без связывания; -o задаёт имя выхода. При последнем вызове отдельного флага остановки нет, поэтому GCC организует связывание. Заголовок, который включён в C-файл, влияет на его объектный файл даже тогда, когда сам hello.c не менялся. Это первая причина строить граф зависимостей, а не проверять только дату одного файла.

Разделение языков на «компилируемые» и «интерпретируемые» слишком грубо для диагностики. CPython компилирует Python в байтовый код и исполняет его своей виртуальной машиной; файл .pyc является кэшем такого представления, а не переносимым исполняемым файлом для любого процессора и любого Python. У Java промежуточное представление исполняется JVM; у других сред часть кода дополнительно переводится в машинный во время работы. У сайта сборка вообще может состоять из обработки шаблонов и копирования изображений. В каждом случае следует спрашивать, какой инструмент преобразовал данные, что сохранено на диске и какой исполнитель нужен при запуске.

Граф действий вместо длинного списка команд

Сборку удобно представлять ориентированным ациклическим графом, сокращённо DAG. «Ориентированный» означает, что у стрелки есть направление зависимости; «ациклический» — что действие не может через цепочку зависеть само от себя. Узлы бывают действиями и данными; в упрощённой схеме рисуют только действия, а на стрелках подразумевают передаваемые результаты.

app.py ───────────┐
                 ├── упаковка ── ZIP ── проверка запуска ZIP
шаблоны ─────────┘
app.py + tests ────── тесты ──────────── решение о выпуске
tools/build.py ────── упаковка
конфигурация ──────── проверка конфигурации

Граф описывает необходимые предпосылки, а не обязательно единственное расписание. Проверку форматирования и модульные тесты часто можно выполнять одновременно. Проверка запуска ZIP обязана ждать упаковку. Решение о выпуске должно дождаться всех обязательных проверок, даже если они не производят вход для упаковщика. Так различаются зависимость данных и управляющее условие. Если нарисовать только движение файлов, легко случайно разрешить публикацию раньше окончания тестов.

Порядок строк в скрипте сам по себе не создаёт достоверную зависимость. Команда упаковки способна взять прошлый архив из оставшегося каталога; тесты способны импортировать модуль из установленного пакета вместо текущего репозитория. Поэтому узлу графа нужны определённый рабочий каталог, список входов, свежие выходы и явное правило успеха. Чистый временный каталог полезен как эксперимент: если только в старом рабочем каталоге всё проходит, обнаружен незаявленный вход или зависимость от предыдущего запуска.

Maven: кто организует сборку Java

Для Java полезно различать три уровня. JDK — комплект разработки, включающий компилятор и другие инструменты; JVM исполняет Java-программу. Maven организует действия проекта по описанию, но сам не заменяет компилятор языка. Плагины Maven выполняют конкретную работу: компиляцию, тестирование, упаковку. Maven Compiler Plugin управляет вызовом компилятора; Surefire организует запуск выбранных тестов; JAR Plugin формирует архив. Наличие Java runtime на машине ещё не доказывает наличие полного нужного JDK и работающего компилятора.

Описание проекта находится в XML-файле POM — Project Object Model, то есть модели проекта. В нём задаются координаты проекта, зависимости, свойства и настройки сборочных плагинов. Например, свой собственный учебный проект можно назвать org.example.training:reading-service:1.0.0. Эти три части обозначают группу, имя артефакта и версию; они не являются сетевым адресом работающей службы. Тип упаковки jar описывает выход сборки, но не обещает, что архив самодостаточен или запускается командой Java без дополнительных параметров.

Содержимое одного видимого POM не всегда является окончательной конфигурацией. Часть свойств наследуется от родительской модели, часть задаётся стандартными правилами, активными профилями и параметрами запуска. Effective POM — результирующая модель после такого объединения. Когда в локальном файле не видно версии плагина, следует выяснить, откуда она пришла; отсутствие строки не означает отсутствие значения. Родитель проекта тоже является входом сборки. Для диагностики используют цель help:effective-pom, а при необходимости включают сведения о происхождении значений.

Жизненный цикл, фаза и цель

Жизненный цикл задаёт последовательность фаз. Фаза — именованная ступень, например compile, test, package или verify. Цель плагина, goal, — конкретное действие, которое можно привязать к фазе. Указав фазу, мы просим пройти необходимые предыдущие фазы этого цикла; указав непосредственно цель, мы не обязаны получить весь такой же маршрут. Поэтому mvn package и отдельный вызов цели упаковщика не следует считать тождественными.

mvn -B -ntp -f reading-service/pom.xml clean verify
mvn -B -ntp -f reading-service/pom.xml help:effective-pom

Команды показывают интерфейс отдельного Maven-проекта; они не запускаются в Python-стенде. -B выбирает пакетный, неинтерактивный режим. -ntp убирает индикаторы прогресса передачи, сохраняя полезные сообщения; флаг доступен в рассматриваемой ветке Maven 3.9. -f указывает альтернативный POM: путь к нему сначала разрешается от текущего каталога запуска. Maven определяет базовый каталог выбранного проекта, и обычный target относится к этому проекту, а не обязательно к каталогу, из которого запустили команду. Пользовательские сценарии и плагины могут иметь дополнительные правила путей; их параметры проверяют отдельно.

clean относится к отдельному циклу очистки и обычно удаляет производные данные проекта, включая target, через соответствующий плагин. verify — более поздняя фаза основного цикла: до неё проходят компиляция, тесты и упаковка, а также привязанные промежуточные действия. package завершает маршрут раньше: получить JAR ещё не означает пройти проверки, привязанные к следующим фазам. clean не очищает весь локальный репозиторий Maven и не удаляет удалённые пакеты. Слово «чистый» всегда требует уточнения области очистки.

Почему имя теста не определяет способ его запуска

Метод тестирования определяется проверяемой границей, а обнаружение теста — конфигурацией исполнителя. По стандартным маскам Surefire выбирает, в частности, имена с окончанием Test и Tests. Поэтому класс DatabaseIntegrationTest вполне может попасть в обычную фазу test: слово Integration внутри имени не переключает механизм. Если такой тест требует настоящую базу, сборка может обратиться к ней задолго до подготовленной автором интеграционной стадии.

Failsafe предназначен для маршрута интеграционных проверок; его обычные маски включают IT*, *IT и *ITCase. Но одного переименования класса недостаточно: плагин должен присутствовать в конфигурации с нужными выполнениями и целями. Разделяют исполнение integration-test и принятие результата verify, чтобы между ними могла пройти фаза освобождения подготовленной среды. Поэтому часто вызывают весь маршрут до verify, а не обрывают его на integration-test. Это не гарантирует уборку при убийстве процесса или обрыве питания; внешние ресурсы требуют собственного срока жизни.

Смотрите фактический журнал плагина, число обнаруженных случаев и созданные отчёты. Зелёный результат при нуле обнаруженных тестов может означать неправильные маски, отсутствующий провайдер или профиль, а не доказанную правильность программы. Обычный target/classes содержит скомпилированные классы приложения; target/test-classes — тестовые; отчёты и JAR являются другими результатами. Маска target/*.jar выбирает файлы по расположению, но не устанавливает, какой из нескольких архивов предназначен для доставки.

Этот раздел проверен по документации Apache. В среде подготовки тома обнаружена JVM, но отсутствовали mvn и javac; поэтому реальная Maven-сборка здесь не заявляется. При повторении нужны согласованные Maven, JDK и версии плагинов. Свойство maven.compiler.release у совместимого Compiler Plugin задаёт целевой выпуск Java и доступный API; оно не скачивает нужный JDK и не исправляет несовместимую библиотеку автоматически. Наш основной автономный стенд остаётся Python-проектом без этих дополнительных установок.

Как увидеть действие глазами операционной системы

python3 -m unittest discover -s tests -v
python3 tools/build.py

Здесь python3 — программа, найденная по PATH. -m просит запустить модуль, а не файл по указанному пути. В первом вызове unittest — стандартный модуль тестирования; discover выбирает поиск тестов; -s tests задаёт начальный каталог; -v включает подробные названия проверок. Второй вызов передаёт интерпретатору путь к сценарию сборки. Успешное завершение первого процесса не передаёт его память второму: связывают их только явно сохранённые файлы и договорённости о путях.

Стандартный вывод предназначен для обычных сообщений, стандартный поток ошибок — для диагностических, но факт записи в любой поток не определяет успех. Программа может напечатать слово ERROR и вернуть ноль либо молча завершиться с ненулевым кодом. Автоматизация прежде всего читает код завершения и затем проверяет ожидаемые выходы. Если файл обязателен, его отсутствие должно завершать действие ошибкой. Иначе получится зелёный запуск без доставляемой программы.

Когда «у меня собирается» перестаёт быть аргументом

Допустим, у разработчика установлен сторонний модуль, а в репозитории он не объявлен. Локальный импорт проходит, на агенте сборки возникает исключение. Это не особая «ошибка CI»: процесс на агенте получил иной набор входов. Другой пример — программа открывает config.json по относительному пути. Такой путь отсчитывается от рабочего каталога процесса, а не автоматически от файла программы. Запуск из корня проходит, запуск из каталога обслуживания ломается. Исправлять следует договорённость о конфигурации и вычисление пути, а не добавлять случайные команды перехода во все места запуска.

Для расследования сохраните команду, рабочий каталог, версии инструментов, код исходников и безопасную часть окружения. Не выгружайте весь набор переменных в общий журнал: там могут находиться пароли. Затем повторите действие в новом каталоге с минимальными нужными входами. Сравнение следует вести по одному фактору: другая версия Python, другой каталог, отсутствие сети. Если одновременно переустановить инструменты, очистить кэш и поменять код, успешный результат почти ничего не скажет о причине.

Граница сборки выбирается по продукту. Для маленького Python-приложения разумно отделить упаковку, проверку и доставку; для библиотеки понадобится формат пакета и проверка установки; для машинного кода — целевая архитектура и совместимость библиотек. Главное свойство хорошей границы: по сохранённым входам и описанию действия другой человек способен получить и проверить конкретный выход. В следующей главе разберём, как зафиксировать ту часть входов, которую поставляют чужие проекты.
