Объекты: от точных байтов до снимка проекта

Blob, дерево, коммит и метка как проверяемая цепочка содержимого

Имя, вычисленное из данных

Объект Git имеет тип, длину и содержимое. Его идентификатор, object ID, вычисляется хеш-функцией: алгоритм превращает произвольное количество входных байтов в значение фиксированной длины. В обычном репозитории SHA-1 это 20 байт, записываемых как 40 шестнадцатеричных цифр. В репозитории SHA-256 это 32 байта и 64 цифры. Здесь разбираем SHA-1, поскольку на нём проще сопоставлять распространённые репозитории; выбор алгоритма не меняет смысл снимков, но меняет форматы ссылок внутри объектов и совместимость инструментов.

Хешируется не только содержимое файла. Перед ним добавляется ASCII-заголовок: тип, пробел, десятичное число байтов, нулевой байт. Для файла hello\n длина содержимого равна шести. Обозначения \n и \0 ниже показывают один перевод строки и один нулевой байт, а не два печатных символа каждое.

Каноническая последовательность: blob 6\0hello\n
Шестнадцатерично: 62 6c 6f 62 20 36 00 68 65 6c 6c 6f 0a
SHA-1: ce013625030ba8dba906f756967f9e9ca394464a

Это собственный проверяемый пример: независимое вычисление SHA-1 указанной последовательности совпадает с git hash-object. Длина считается в байтах, поэтому русская строка в UTF-8 часто длиннее количества её букв. Изменение перевода строки с LF на CRLF меняет байты и идентификатор. Файл с тем же текстом под другим именем, напротив, имеет тот же объект содержимого: имя не входит в blob, «сгусток» байтов.

Почему адрес не является номером записи

Адресация по содержимому означает, что одинаковые канонические байты дают одинаковое имя независимо от места и времени записи. В объекте нет отдельного поля с его собственным именем: оно вычисляется снаружи. Если два одинаковых файла добавлены в разных каталогах одного репозитория, дополнительная запись содержимого не нужна. Если же различается один нулевой байт, хвостовой пробел или режим обрамляющего дерева, соответствующая цепочка имён меняется. Это позволяет проверять полученные данные повторным вычислением, а не доверять имени файла упаковки.

Конечная длина хеша означает математическую возможность коллизии: разных входов с одинаковым результатом. Поэтому фраза «хеш абсолютно исключает любые подмены» неверна. Выбранный алгоритм, проверки известных атак и проверка подписей решают разные части доверия. Для нашей лаборатории полезно более узкое утверждение: мы знаем точные входные байты и независимо воспроизводим ожидаемый результат. Нельзя вывести достоверность авторства только из того, что чужой объект успешно прошёл проверку контрольной суммы.

Посмотреть объект без догадок

Создайте ещё один пустой учебный репозиторий. Здесь формат SHA-1 задан явно, чтобы байты совпадали с разбором даже при иной пользовательской настройке по умолчанию. Параметры локального имени и адреса имеют тот же смысл, что в первом опыте. Команда hash-object без -w только рассчитывает имя. --no-filters запрещает применять проектные преобразования содержимого, чтобы мы исследовали именно байты файла. -w записывает объект в хранилище. Команда cat-file читает объекты: -t печатает тип, -s — длину содержимого, -p — пригодное для чтения представление.

mkdir git-object-lab
cd git-object-lab
git init -b main --object-format=sha1
git config user.name 'Учебный читатель'
git config user.email reader@example.invalid
printf 'hello\n' > hello.txt
git hash-object --no-filters hello.txt
git hash-object -w --no-filters hello.txt
git cat-file -t ce013625030ba8dba906f756967f9e9ca394464a
# blob
git cat-file -s ce013625030ba8dba906f756967f9e9ca394464a
# 6
git cat-file -p ce013625030ba8dba906f756967f9e9ca394464a
# hello

Отдельный, ещё не упакованный объект называют loose object. В простом SHA-1-репозитории его файл находится по пути .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a: две первые цифры выделены в каталог. Содержимое файла сжато zlib. После распаковки в нашем опыте получены ровно 13 байт из примера. Хеш вычисляется до сжатия; изменение уровня сжатия не меняет идентификатор объекта. Когда объект переместят в общий упаковочный файл, отдельный путь может исчезнуть, но cat-file продолжит его читать.

Прочитать канонические байты самостоятельно

python3 - <<'PY'
import hashlib, pathlib, zlib
oid = 'ce013625030ba8dba906f756967f9e9ca394464a'
stored = pathlib.Path('.git/objects') / oid[:2] / oid[2:]
raw = zlib.decompress(stored.read_bytes())
print(raw.hex())
print(hashlib.sha1(raw).hexdigest())
PY

Этот код относится только к отдельному неупакованному объекту из текущего опыта. Срезы [:2] и [2:] строят описанный путь; read_bytes читает сжатое представление без декодирования в текст, decompress возвращает каноническую последовательность. Ожидаются строка 626c6f6220360068656c6c6f0a и известное имя blob. Если объект уже упакован, отсутствие этого отдельного файла не является повреждением; универсально читать его следует через Git.

git cat-file blob ИДЕНТИФИКАТОР выводит сырое содержимое blob без заголовка. Вариант cat-file tree выводит двоичное содержимое дерева; -p форматирует дерево для человека. Это принципиально разные представления. Для автоматической последовательности запросов существует --batch: процесс читает обозначения объектов со стандартного ввода и возвращает заголовки с размерами и содержимое. Получатель обязан читать объявленное количество байтов, а не делить произвольное содержимое blob на строки. В файле допустим и LF, и NUL.

Где живёт имя файла

Дерево, tree, связывает имя с режимом и идентификатором объекта. Для единственного обычного файла hello.txt двоичная запись состоит из ASCII-байтов 100644 hello.txt, нулевого байта и 20 сырых байт идентификатора blob. Последние не являются строкой из 40 символов. Видимый вывод git ls-tree HEAD удобнее двоичного формата: он подписывает тип, показывает полный шестнадцатеричный идентификатор и отделяет имя табуляцией. Формат вывода не нужно путать с содержимым объекта tree.

commit C → tree T
             ├─ 100644 hello.txt → blob H
             └─ 040000 src      → tree S
                                    └─ 100755 run.sh → blob R

Подкаталог представлен другим деревом. Два снимка могут ссылаться на один и тот же blob и на неизменившиеся поддеревья. Изменение одного файла требует нового blob, новых деревьев вдоль его пути к корню и нового коммита, но остальные объекты можно переиспользовать. Переименование меняет запись дерева; если байты не менялись, содержимое blob остаётся тем же. Пустого подкаталога в такой модели нет: у него нет записи, которую нужно сохранить ради файла.

Режим — тоже часть снимка

Запись 100644 означает обычный неисполняемый файл, 100755 — обычный исполняемый. Это не сохранение всех возможных прав Unix. Символическая ссылка имеет режим 120000, а её blob содержит текст цели ссылки, а не байты файла по этой цели. Запись подмодуля с режимом 160000 указывает на коммит другого репозитория. Такие различия меняют дерево даже при внешне похожем содержимом каталога.

У единственного файла hello.txt описанная запись tree занимает 37 байт: шесть цифр режима, пробел, девять байт имени, нулевой разделитель и двадцать байт SHA-1. Канонический объект дерева дополнительно получает заголовок tree 37\0 перед вычислением собственного идентификатора. Это помогает самостоятельно проверить цепочку: изменили байт blob → изменилось его имя в tree → изменилось имя дерева в commit. Ссылка ветки хранит имя нового коммита; именно так изменение одного байта становится новым снимком всей выбранной структуры.

Собрать дерево без рабочего файла

Низкоуровневая команда mktree читает записи в текстовом формате ls-tree и строит объект дерева. Следующие команды используют уже записанный blob hello; переменная оболочки blob_oid хранит его настоящее полное имя. В printf последовательность \t создаёт табуляцию между служебной частью и именем пути. Текст blob указывает ожидаемый тип объекта, 100644 — режим обычного файла.

blob_oid=$(git hash-object -w --no-filters hello.txt)
tree_oid=$(printf '100644 blob %s\thello.txt\n' "$blob_oid" | git mktree)
git cat-file -p "$tree_oid"
git cat-file tree "$tree_oid" | od -An -tx1
git write-tree

Подстановка $(...) берёт стандартный вывод команды; кавычки вокруг переменных сохраняют его единым аргументом. od -An -tx1 показывает байты шестнадцатерично: -An убирает колонку адресов, -tx1 выбирает однобайтные шестнадцатеричные числа. Начало дерева будет 31 30 30 36 34 34 20 68 65 6c 6c 6f 2e 74 78 74 00, затем 20 байт идентификатора. Команда write-tree строит дерево из текущего индекса. Если индекс содержит только этот файл с тем же режимом, она вернёт то же имя дерева, что mktree. Рабочие файлы при этом не перечитываются как новая подготовка.

Инвариант важен: дерево записывает выбранную таблицу, а не «всё, что сейчас вижу в папке». mktree без специального ослабления проверяет существование объектов требуемых типов. write-tree откажет при неразрешённых стадиях индекса. Не следует обходить эти проверки ради получения красивого хеша: недостающее содержимое либо незавершённый выбор ещё не образуют обычный завершённый снимок.

Имена в UTF-8 и порядок записей

Дерево хранит байты компонента имени, а не абсолютный путь. У имени план.txt в UTF-8 байты d0 bf d0 bb d0 b0 d0 bd 2e 74 78 74: двенадцать байт. Каталог задаёт вложенное дерево, поэтому слеш не появляется как часть одного компонента. Нулевой байт запрещён в имени и служит разделителем; содержимое следующего идентификатора, напротив, может содержать нули и читается по фиксированной длине алгоритма хеша.

Git в основном сохраняет имена как байтовые последовательности; отображение зависит от настроек цитирования и среды. На файловой системе, нечувствительной к регистру, два различных дерева с путями Readme и README могут существовать как объекты, но не извлекаться в одновременно различимые рабочие файлы. У Unicode также бывают разные последовательности кодовых точек с похожим отображением. Это ограничение сопоставления хранилища с файловой системой, а не повод считать байтовые имена одинаковыми.

Порядок записей дерева определяется специальным побайтовым сравнением: при сравнении имени каталога учитывается виртуальный завершающий слеш. Поэтому вручную сортировать дерево языковым алфавитом недостаточно. mktree нормализует порядок входных записей самостоятельно; для имён с табуляцией или LF предусмотрен нулевой формат -z. Такой режим меняет разделение записей ввода, а не допустимость NUL внутри имени.

Что добавляет коммит

Объект commit содержит строку tree с именем корневого дерева, ноль или несколько строк parent, строки автора и создателя фиксации, пустую строку и сообщение. Автор, author, относится к исходному изменению; создатель, committer, — к созданию этого конкретного объекта. При переносе изменения автор может сохраниться, а создатель и дата фиксации поменяться. Временная метка записывается вместе со смещением часового пояса. Подпись, если она добавлена, тоже становится частью содержимого объекта.

git add -- hello.txt
git commit -m 'Сохранить объектный опыт'
git cat-file -p HEAD
git rev-parse HEAD^{tree}
git ls-tree HEAD
git show HEAD:hello.txt

Первые две команды создают снимок: одно лишь hash-object -w записало blob, но не добавило его путь в индекс и не создало HEAD. HEAD^{tree} просит разыменовать текущую фиксацию до её дерева. HEAD:hello.txt выбирает путь внутри снимка, не рабочий файл. Вывод коммита в каждом опыте будет иметь свой идентификатор, если различаются имя, адрес, дата, родитель или сообщение. Поэтому совпадение всех файлов ещё не означает совпадение коммитов. Напротив, совпадение полного идентификатора предполагает совпадение канонических байтов объекта в рамках выбранной хеш-функции; проверка хеша не устанавливает авторство человека.

Создать объект коммита, не перемещая ветку

tree_oid=$(git write-tree)
parent_oid=$(git rev-parse HEAD)
new_oid=$(printf 'Проверить тот же снимок\n' |
  git commit-tree "$tree_oid" -p "$parent_oid")
git cat-file -p "$new_oid"
git rev-parse HEAD
git branch object-lab-result "$new_oid"

commit-tree принимает готовое дерево и создаёт объект фиксации; -p добавляет указанного родителя, сообщение читается со стандартного ввода. Ветка сама не перемещается: напечатанный затем HEAD останется прежним. Последняя команда создаёт отдельное имя для нового объекта, не переключая файлы. Именно разделение «сформировать объект» и «обновить ссылку» объясняет, почему ошибка позднего этапа не обязана означать отсутствие уже записанных объектов.

Без -p получился бы новый корневой коммит, даже если в репозитории уже есть история. Два параметра -p создают два родителя в указанном порядке; сам commit-tree не выполняет слияние файлов и не доказывает совместимость этих линий. Можно дать ему дерево, совершенно не связанное с содержимым родителей. Высокоуровневая merge сначала вычисляет результат, а затем записывает его происхождение; низкоуровневое создание объекта этих вычислений не заменяет.

В метаданных автор описывает происхождение изменения, а создатель — изготовление данной фиксации. Переменные GIT_AUTHOR_NAME, GIT_AUTHOR_EMAIL, GIT_AUTHOR_DATE и соответствующие GIT_COMMITTER_... позволяют в изолированном опыте задать их явно. Дата включает число секунд от эпохи и смещение часового пояса. Два одинаковых дерева с разными авторами, сообщениями или родителями дают разные коммиты; при полностью одинаковом каноническом содержимом новый запуск не создаёт новый независимый идентификатор только потому, что его запустили второй раз.

Метки и переход к другому алгоритму

Лёгкая метка — ссылка из пространства refs/tags/ на существующий объект. Аннотированная метка создаёт отдельный объект tag: внутри целевой объект, его тип, имя, данные поставившего метку и сообщение; возможно, подпись. Таким образом, два одинаково названных выпуска могут ссылаться на разные объекты, если ссылки разрешили заменить. Для проверки выпуска важно фиксировать идентификатор и политику проверки подписи, а не полагаться на красивое имя.

Алгоритм хеша выбирают при создании нового репозитория, например git init --object-format=sha256. Этот флаг проверен в Git 2.43.0 для нового пустого каталога. Он не переводит готовый SHA-1-репозиторий в новый формат простой перенастройкой. Объекты tree и commit содержат имена других объектов, поэтому переход затрагивает всю цепочку. Поддержка обмена между форматами развивается: перед использованием проверяют версии клиента, сервера, хостинга и вспомогательных инструментов; нельзя предполагать, что любой SHA-1-сервер примет SHA-256-клон.

Один blob — два пути

Скопируйте hello.txt в copy.txt, добавьте оба и сделайте коммит. Сравните идентификаторы в git ls-tree HEAD. Затем поменяйте сообщение последнего коммита через git commit --amend -m 'Другое описание'.

Разбор

Оба пути с одинаковыми байтами используют один blob. --amend создаёт заменяющий последний коммит, а -m задаёт новое сообщение. Идентификатор коммита изменится, хотя дерево может остаться прежним. Это опыт только с собственной неопубликованной учебной историей.
