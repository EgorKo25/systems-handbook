Автономная лаборатория: от первого изменения до проверенной сборки

Здесь Git работает по-настоящему: с объектами, индексом, ветками, конфликтом и локальным серверным репозиторием. Семь опытов связаны одним небольшим проектом. Состояние между ними сохраняется; намеренно сломанный учебный стенд можно восстановить в известную точку.

Что именно запускается

Нужны установленный Git версии 2.28 или новее и Python 3.8 или новее. Docker, загрузка пакетов, регистрация и сетевой доступ не требуются. Командный маршрут ниже написан для Bash. Он подходит для домашнего Linux; на Windows Python называется иначе в зависимости от установки, а синтаксис оболочки может отличаться. Самопроверка выполнена на Linux с Git 2.43.0; запуск на Windows не проверялся. На рабочем компьютере, где нельзя устанавливать программы, остаются чтение и встроенные модели книги.

Стенд содержит repo — вашу рабочую копию, peer — копию условного коллеги и remote.git — общий репозиторий без рабочих файлов. Последний называется голым, или bare: он хранит историю и ссылки, а редактирование исходников выполняется в рабочих копиях. Все три находятся в отдельном учебном каталоге. Команды push и fetch обращаются к соседнему каталогу, не к интернету.

Исходники проекта — маленькая служба на стандартной библиотеке Python. Тренажёр её не запускает. По умолчанию python3 app.py только печатает приветствие. Необязательный запуск python3 app.py --serve --port 8087 включает сервер только на адресе 127.0.0.1: флаг --serve выбирает режим, --port задаёт порт. Завершение — Ctrl+C. Для упражнений слушающий порт вообще не нужен.

Подготовка без изменения личных проектов

Откройте терминал в корне копии библиотеки, где расположены папки git, linux и остальные тома. Нужна вся папка git/labs, включая template, а не один файл программы. Следующие переменные сохраняют путь к программе и отдельному соседнему каталогу стенда. Они нужны, чтобы после перехода между рабочими копиями обращаться к одной программе проверки.

git --version
python3 --version
HANDBOOK_LAB_TOOL="$(pwd)/git/labs/trainer.py"
HANDBOOK_LAB_SPACE="$(pwd)/../git-workshop"
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" init
cd "$HANDBOOK_LAB_SPACE/repo"

--version выводит версию программы; --workspace указывает единственный каталог, которым управляет тренажёр. Команда init принимает отсутствующий либо пустой каталог. Чужая непустая папка будет отвергнута. Повторная инициализация существующего стенда тоже запрещена: случайный повтор команды не должен уничтожать сделанные упражнения.

Программа проверки изолирует свои вызовы Git от глобальной и системной конфигурации и удаляет унаследованные переменные расположения репозитория. В созданных копиях задаются учебные имя и адрес автора, отключаются подписи коммитов и выбирается отдельный пустой каталог обработчиков Git. Личные настройки и переменная HOME не изменяются. Вручную вводимый вами Git остаётся обычной установленной программой; необычные персональные настройки могут влиять на его вывод.

Как извлекать пользу из опыта

Перед каждой командой сформулируйте ожидаемое изменение: какие байты должны поменяться, какой указатель сдвинется, а что останется прежним. Затем сравните предположение с наблюдением. Если вывод отличается, сначала выясните текущую ветку и состояние файлов. Одно и то же действие в разных исходных состояниях может дать разный результат, поэтому повторять последнюю команду наугад обычно менее полезно, чем восстановить причинную цепочку.

Проверка результата не пытается узнать, какие кнопки или команды вы использовали. Она исследует полученное состояние. Пройденный контроль означает выполнение конкретных условий, а не полное понимание темы. Полезно после успеха самостоятельно изменить одно условие: например, отредактировать файл повторно, оставить ветки разошедшимися или поменять вход сборки. Предскажите, какая проверка теперь должна отказать и почему. Так лаборатория становится инструментом исследования, а не перечнем строк для копирования.

Опыт 1. Три разные версии одного файла

Файл notes.txt в исходном коммите содержит строку first. Создадим вторую версию, подготовим её к коммиту, а затем запишем третью. printf здесь выводит заданную строку; \n означает перевод строки. Перенаправление > заменяет содержимое указанного учебного файла.

printf 'prepared\n' > notes.txt
git add -- notes.txt
printf 'working\n' > notes.txt
git status --short
git diff -- notes.txt
git diff --cached -- notes.txt
git show HEAD:notes.txt
git show :notes.txt
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check index

Ожидаются два признака изменения: первая позиция короткого статуса относится к индексу, вторая — к рабочему файлу. --short включает этот компактный формат. Обычный diff сравнивает индекс и рабочую копию: prepared заменено на working. Флаг --cached выбирает другое сравнение — HEAD и индекс: first заменено на prepared. Двойной дефис завершает разбор параметров и отделяет имя файла. Он полезен, когда имя похоже на флаг.

Запись HEAD:notes.txt выбирает файл из текущего коммита; начальное двоеточие в :notes.txt выбирает запись индекса. Таким образом, add подготовил определённые байты, а последующее редактирование не обновило их автоматически. Проверка читает все три состояния, не исправляя результат за вас.

Дополнительно спросите себя, что произойдёт после ещё одной подготовки файла. Оба сравнения не обязаны показывать изменения одновременно: индекс может совпасть с рабочей копией и при этом отличаться от коммита. Пустой вывод отдельного сравнения утверждает равенство его сторон, а не отсутствие любой несохранённой работы. Именно поэтому перед восстановлением недостаточно посмотреть только один привычный вывод.

git cat-file -t :notes.txt
git cat-file -p :notes.txt
git ls-tree HEAD
git restore --source=HEAD --staged --worktree -- notes.txt

У cat-file ключ -t показывает тип объекта, а -p — его представление: здесь типом будет blob, содержимым — подготовленная строка. ls-tree связывает имена файлов с типами и идентификаторами объектов дерева. Последняя команда завершает опыт: явно выбирает источник HEAD, восстанавливает индекс через --staged и рабочий файл через --worktree. Обе экспериментальные версии исчезнут из привычных мест, поэтому переносить этот приём на несохранённую личную работу нельзя.

Опыт 2. Ветка как указатель, а не копия папки

Находясь в чистой main, создайте ветку. Дополнительный файл будет обозначать собственный небольшой результат работы, не меняя поведения службы.

git switch -c feature
printf 'feature ready\n' > feature.txt
git add -- feature.txt
git commit -m "Add a feature marker"
git switch main
git merge --ff-only feature
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check branch

Ключ -c создаёт ветку и сразу переключает на неё. Параметр -m передаёт сообщение коммита, поэтому редактор не открывается. Возврат в main временно убирает файл из рабочей копии: его версия существует в другой истории. После merge файл появляется снова.

Флаг --ff-only разрешает только продвижение указателя вперёд по существующей истории. Если ветки уже разошлись, команда откажется вместо создания коммита слияния. В нашем случае обе ветки после операции указывают на один коммит. Проверьте гипотезу через git rev-parse main feature: два идентификатора должны совпасть. Это объясняет, почему для такого объединения не потребовалась третья версия содержимого.

Опыт 3. Конфликт как три входа для решения

Теперь изменим одну строку message.txt независимо в двух ветках. Исходный общий коммит у них один, но результаты разные. Значения этого файла служат демонстрацией слияния; действующий код приложения находится отдельно.

git switch -c feature-conflict
printf 'Hello from feature\n' > message.txt
git add -- message.txt
git commit -m "Change the feature greeting"
git switch main
printf 'Hello from main\n' > message.txt
git add -- message.txt
git commit -m "Change the main greeting"
git merge feature-conflict
git ls-files --unmerged
git show :1:message.txt
git show :2:message.txt
git show :3:message.txt

Неуспешный код завершения merge здесь ожидаем: автоматическое решение не найдено. --unmerged показывает неразрешённые записи индекса. Номера стадий 1, 2 и 3 обозначают общего предка, нашу сторону и присоединяемую сторону обычного слияния. Перед именем каждой версии можно увидеть режим файла, идентификатор объекта и номер стадии. Это существующие данные для сравнения, а не три независимо редактируемых файла в каталоге.

Не выбирайте сторону только потому, что она названа «нашей». Сначала прочитайте оба изменения и решите, что должно сохраниться. Для учебного результата запишем согласованную строку:

printf 'Hello from both branches\n' > message.txt
git add -- message.txt
git commit -m "Resolve the greeting conflict"
git rev-list --parents -n 1 HEAD
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check merge

Подготовка файла заменяет конфликтные стадии обычной записью индекса. Коммит завершает слияние. В выводе rev-list параметр --parents добавляет идентификаторы родителей, а -n 1 ограничивает число показанных коммитов одним. Здесь будут три идентификатора: сам результат и два родителя. При незавершённом опыте git merge --abort пробует отменить слияние; лучше начинать его с чистыми файлами, чтобы не смешивать эксперимент с другой работой.

Маркеры конфликта помогают найти участки, но их удаление само по себе не доказывает правильность программы. Два изменения могут автоматически объединиться в синтаксически допустимый, но логически неверный результат. После объединения требуется проверить ожидаемое поведение. В этом опыте проверяется согласованная строка; при работе со службой понадобятся проверки её функций и взаимодействий. Сначала устанавливается смысл результата, затем выбирается способ его проверки.

Опыт 4. Найти коммит, потеряв привычный указатель

git switch --detach HEAD
printf 'recovered\n' > recovery.txt
git add -- recovery.txt
git commit -m "A detached experiment"
git log -1 --oneline
git switch main
git reflog --oneline

--detach отделяет HEAD от имени ветки: новые коммиты не продвигают main. У log ключ -1 оставляет одну запись, а --oneline делает её компактной. После переключения файл исчезает, но коммит некоторое время остаётся доступен по идентификатору. Журнал перемещений ссылок, reflog, помогает найти его.

Найдите запись с сообщением об эксперименте и подставьте её идентификатор в команду ниже. Угловые скобки обозначают место подстановки; вводить их буквально не нужно.

git branch rescued <идентификатор-коммита>
git show rescued:recovery.txt
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check recovery

Создание ветки сохраняет обычную ссылку на найденную историю. Текущая main при этом не меняется. Проверка требует именно отдельной ветки с файлом, а не случайно оставшегося файла в рабочем каталоге. Журнал ссылок локален, может очищаться и не заменяет резервирование. Объяснение восстановления ограничено созданным стендом: обещания восстановить любую когда-либо удалённую работу здесь нет.

Опыт 5. Передача объектов и обновление файлов — разные события

Отправьте завершённую main в общий локальный репозиторий. Затем перейдите в копию коллеги, получите историю и добавьте его вклад.

git push origin main
cd "$HANDBOOK_LAB_SPACE/peer"
git fetch origin
git merge --ff-only origin/main
printf 'from peer\n' > peer.txt
git add -- peer.txt
git commit -m "A peer contribution"
git push origin main
cd "$HANDBOOK_LAB_SPACE/repo"
git fetch origin
git show origin/main:peer.txt
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check fetched

origin — настроенное имя соседнего общего репозитория. В push origin main явно названы получатель и отправляемая ветка. При fetch поступают нужные объекты и обновляется наблюдаемая локальная ссылка origin/main. Это знание о полученной версии другой стороны, а не ваша рабочая ветка.

Проверьте важное расхождение: show уже читает новый файл из origin/main, но файла peer.txt в вашей рабочей копии ещё нет. Промежуточная проверка fetched специально требует такого состояния. Она не запускает получение данных вместо вас. После наблюдения явно обновите main:

git merge --ff-only origin/main
git status --short --branch
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check remote

--branch добавляет сведения о ветке к короткому статусу. Теперь файл присутствует и идентификаторы локальной и полученной веток совпадают. Если вы сделали собственный несовместимый коммит, продвижение указателя может оказаться невозможно: сначала исследуйте расхождение. Не заменяйте разбор принудительной отправкой. В этом опыте сеть не участвует, но различие ссылок и рабочих файлов остаётся таким же принципиальным.

Опыт 6. Собрать результат с явными входами

python3 -m unittest discover -s tests -v
python3 tools/build.py
python3 -m zipfile -l dist/handbook-demo.zip
python3 -m json.tool dist/manifest.json
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check build

Параметр Python -m запускает модуль как программу. У unittest команда discover ищет проверки, -s tests задаёт начальный каталог, а -v выводит их отдельные имена. Шесть проверок относятся к поведению функции: обычному и русскому имени, пробелам, недопустимому пустому значению и версии. Они не требуют запущенной службы. У модуля zipfile ключ -l показывает содержимое архива; json.tool удобно форматирует метаданные.

Сборщик берёт только README.txt и app.py. Он создаёт dist/handbook-demo.zip с фиксированным порядком записей, датой 1 января 2000 года, типом обычного файла и режимом 0644 в метаданных. Метод ZIP_STORED сохраняет байты без сжатия: результат не зависит от версии библиотеки сжатия. Это учебный выбор, увеличивающий размер архива, а не универсальный совет для больших поставок.

Файл manifest.json рядом содержит состав, размеры и хеши входов, хеш архива и сведения о HEAD. Отдельный source-commit.txt сохраняет идентификатор коммита. Они намеренно не включены в архив: изменение только происхождения сборки не должно менять байты приложения. Если рабочие файлы отличаются от сохранённых, метаданные показывают этот факт; один идентификатор HEAD не доказывает чистоту входов. Проверка сверяет архив с текущими файлами и повторяет тесты, но не пересобирает устаревший результат тайком.

Обратите внимание на границу входов: заметки и демонстрационная строка слияния существуют в проекте, но в поставляемый архив не входят. Их изменение влияет на историю и признак изменённого дерева, однако не обязано менять поставку. Такое исключение должно быть явным решением сборщика. В настоящем проекте забытый нужный файл был бы ошибкой: одинаковые архивы могут одинаково не содержать необходимую часть программы.

Опыт 7. Отделить неизменные байты от нового происхождения

Запишите хеш, который печатает сборщик. Затем создайте коммит без изменения файлов и повторите сборку:

git commit --allow-empty -m "Change only provenance"
python3 tools/build.py
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check build
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" check reproducible

--allow-empty разрешает коммит без изменения дерева. Новый родительский переход и сообщение создают другую запись истории, но объявленные входы архива прежние. Поэтому хеш ZIP должен совпасть, а внешний идентификатор происхождения измениться. Если добавить байт в app.py, ожидание уже другое: архив обязан измениться. Пустой коммит и изменение исходника проверяют разные гипотезы.

Последняя проверка требует чистого рабочего дерева. Она создаёт две временные независимые копии, меняет времена файлов и собирает результат в разных каталогах. Затем сравнивает полные байты архивов и повторяет опыт с пустым коммитом. Временные копии удаляются после проверки; основные repo, peer и их история сохраняются.

Это свидетельство для данного состава, сборщика и проверенной среды. Оно не доказывает воспроизводимость любого приложения, компилятора или будущей версии Python. Здесь не проверяются взаимодействие с настоящим Jenkins, удалённая аутентификация и сетевые отказы. Они требуют отдельных опытов. Зато граница эксперимента ясна: исходные байты, метаданные ZIP и сведения о коммите можно исследовать независимо.

Продолжение и восстановление

python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" status
python3 "$HANDBOOK_LAB_TOOL" --workspace "$HANDBOOK_LAB_SPACE" reset-checkpoint merge --yes

status показывает состояние, не возвращая его к началу. Название контрольной точки в маркере означает исходную подготовку, а не автоматически вычисленный прогресс. Результат упражнения проверяется в тот момент, когда его состояние ещё существует: после дальнейшего изменения истории ранний контроль закономерно может не проходить.

Сброс — отдельное явное действие. --yes подтверждает удаление учебных копий и потерю их несохранённых изменений. Сначала проверяются общий маркер, принадлежность дочерних каталогов, пустота каталога обработчиков и отсутствие символических ссылок. Посторонний файл на верхнем уровне останавливает сброс. Не подменяйте маркеры и не запускайте сброс одновременно с работой Git в этом стенде.

Что восстанавливает каждая точка

start — исходный проект. index — три подготовленные версии первого опыта. branch — завершённое продвижение main до feature. merge — разошедшиеся ветки перед конфликтным слиянием. recovery — завершённое слияние перед отдельным экспериментом. remote — вклад коллеги уже получен, но main ещё не обновлена. build — обновлённая чистая main перед сборкой. Во всех случаях учебные каталоги создаются заново; это восстановление известного сценария, а не сохранение ваших собственных промежуточных решений.

Для независимой проверки самой лаборатории из корня библиотеки выполняется python3 git/labs/check_lab.py. Она использует временные каталоги и проверяет реальные операции Git, байты архива и отказы опасных сбросов. Машинный отчёт лежит в git/labs/lab-results.json; результаты этой проверки не означают, что ваше отдельное упражнение выполнено. Учебный проект остаётся вашим пространством для повторных гипотез и наблюдений.
