Различия: как читать и проверять заплатку

Две стороны сравнения, номера строк, контекст, бинарные данные и предположения о переименовании

Сначала назвать два состояния

Git хранит снимки, а различие вычисляет по запросу. Поэтому у любой заплатки нужно установить левую и правую стороны. git diff сравнивает индекс с рабочими файлами; git diff --cached — текущий коммит с индексом; git diff HEAD — текущий снимок с рабочими файлами. Подготовленная и неподготовленная правки одного пути могут компенсироваться, и последний вызов покажет меньше, чем сумма двух первых. Это не потеря данных, а другое сравнение.

git diff A B сравнивает деревья коммитов A и B. В этом контексте A..B также обозначает сравнение двух концов, а не множество коммитов как у log. Запись git diff A...B обычно сравнивает общее основание A и B с B: она удобна для просмотра того, что боковая работа внесла со времени ответвления. Три точки в diff и log имеют связанную, но разную операционную семантику. Не переносите вывод о списке коммитов на сравнение файлов.

Два diff могут отвечать на противоположные вопросы

Пусть A содержит одну строку mode=old. В main поверх A добавили файл мониторинга, а в topic заменили mode на new. git diff main topic покажет и изменение mode, и исчезновение файла мониторинга: в конечном снимке topic его нет. git diff main...topic начнёт с общего основания A и покажет только вклад topic. Для оценки полного результата переключения нужен первый вопрос; для обзора предлагаемой работы после ответвления часто второй. Игнорирование этой разницы создаёт ощущение, что Git «удалил чужие файлы в запросе», хотя был выбран другой способ сравнения.

Порядок сторон определяет знак изменения. Если переставить A и B, добавления станут удалениями, а координаты участков поменяются местами. Флаг -R явно обращает сравнение. Это полезно при исследовании обратного изменения, но не делает текстовую заплатку семантически правильной отменой программы: после неё могли появиться новые зависимости. Идентификаторы сторон и их смысл стоит фиксировать до обсуждения количества плюсов.

Из чего состоит участок

diff --git a/service.conf b/service.conf
index 1234567..89abcde 100644
--- a/service.conf
+++ b/service.conf
@@ -2,3 +2,4 @@
 host=127.0.0.1
-port=8000
+port=8080
+timeout=5
 workers=2

Идентификаторы в этом учебном рисунке условные. Строки --- и +++ обозначают старый и новый пути. Заголовок @@ -2,3 +2,4 @@ говорит: участок охватывает три строки старой стороны, начиная со второй, и четыре строки новой стороны, тоже со второй. Пробел в начале строки отмечает неизменный контекст; минус — строку только старой стороны, плюс — только новой. Номер новой строки вычисляют с учётом контекста и добавлений, старой — контекста и удалений. Символы начала строки не входят в исходный файл.

Участок называют hunk, фрагментом заплатки. Контекст помогает человеку понять место правки и программе найти его при небольшом смещении строк. git diff -U5 запрашивает пять строк контекста вокруг изменений; -U0 оставляет только изменённые участки. Больший контекст удобен для оценки условия и обработчика ошибки; нулевой меньше по объёму, но легче скрывает смысл. Отсутствие перевода строки в конце файла выводится отдельной служебной пометкой, а не новой строкой программы.

Нулевой диапазон и собственные счётчики сторон

У записи диапазона start,count count — число затронутых строк этой стороны, включая контекст. При count=1 запятая и число могут опускаться. Заголовок @@ -0,0 +1 @@ описывает добавление первой строки в пустой файл: на старой стороне взято ноль строк. Это не существование строки с номером ноль. Заголовок @@ -3,0 +4,2 @@ без контекста означает вставку двух строк после третьей старой строки.

Заголовок: @@ -10,3 +10,4 @@
Строка заплатки        старый счётчик     новый счётчик
 контекст             10 → 11            10 → 11
-удалённая            11 → 12            остаётся 11
+новая первая         остаётся 12        11 → 12
+новая вторая         остаётся 12        12 → 13
 контекст             12 → 13            13 → 14

Старая сторона израсходовала три строки, новая четыре. Если вручную редактировать заголовок, не учитывая эти счётчики, получится повреждённая заплатка. Пометка отсутствующего финального LF не увеличивает их: это метаданные представления. Применяющая программа должна также различать строку, начинающуюся знаком плюс в исходном файле, и плюс как индикатор: в первом случае в заплатке будут индикатор и сам символ исходного текста.

Алгоритм выбирает представление, а не истину о замысле

Одинаковое содержимое до и после может быть представлено разными допустимыми последовательностями удалений и добавлений. Особенно это заметно среди повторяющихся скобок, пустых строк и одинаковых блоков. Git предлагает разные алгоритмы сопоставления, например --patience, который стремится опереться на уникальные строки, и --histogram, использующий информацию о частоте строк. Они могут улучшить читаемость сложной перестановки, но не доказывают, что блок «перенесли с таким-то намерением».

git diff --word-diff подсвечивает изменения на уровне слов по правилам выбранного режима. Это удобно для текста, но при коде пунктуация и границы токенов имеют собственную роль. git diff -w игнорирует изменения пробельных символов при сравнении. Он помогает увидеть смысловую правку среди форматирования, но способен скрыть значимое изменение отступов, например в Python. Для окончательной проверки возвращаются к полным байтам и требованиям языка.

Зачем несколько алгоритмов поиска

В простейшей построчной модели нужно найти последовательность удалений и вставок, превращающую старый список строк в новый. Общую неизменившуюся подпоследовательность можно оставить контекстом. Если в старом тексте N строк, в новом M, а выбранная общая подпоследовательность имеет длину L, соответствующая стоимость вставок и удалений равна N+M−2L. Повторяющиеся строки дают несколько допустимых способов сопоставления, иногда одинаковой длины. Кратчайший путь правок не обязан лучше всего передавать человеческую границу функции.

Алгоритм Myers ищет подходящее сопоставление на такой структуре различий; дополнительные эвристики ограничивают затраты и сдвигают границы фрагментов. Режим --minimal просит потратить больше времени на минимальность результата. Patience сначала использует редкие однозначные опоры, histogram допускает более широкий поиск редких общих строк. Они особенно заметны при перестановке похожих блоков. Это способы решить задачу отображения, а не разные содержимые коммита.

Для собственной проверки сохраните два файла с повторяющимися блоками и сравните git diff --no-index --diff-algorithm=myers old.txt new.txt с вариантом --diff-algorithm=histogram. --no-index сравнивает два файловых пути без требования репозитория. Прочитайте не только размер заплатки, но и то, видны ли изменения условия и обработчика ошибки. По результату одного маленького примера нельзя объявить один алгоритм всегда лучшим: цена зависит от структуры входа.

Переименование определяется по похожести

В снимке есть старый путь, которого больше нет, и новый, которого раньше не было. Отдельной универсальной записи «переименовать X в Y» коммит не хранит. git diff -M включает обнаружение переименований по сходству содержимого. -M90% задаёт порог сходства 90 процентов. Это порог алгоритма, а не вероятность истинности переименования. Если одновременно сильно переписать файл, связь может не обнаружиться; если два файла похожи, алгоритм может подобрать связь, не совпадающую с замыслом автора.

Для чтения полезно разделять чистые перемещения и функциональные изменения, если это не ломает целостность работы. Для инструментов важно не полагаться на нарисованную стрелку переименования как на постоянную личность файла. Режим поиска копий -C также вычисляет сходство и может требовать больше сравнений. На крупной массовой переработке поиск похожих пар потребляет заметные CPU и память; время diff иногда связано с этим поиском, а не с чтением самого журнала.

Что происходит до поиска похожих пар

Сначала из двух деревьев получают пары существующих путей, добавлений и удалений. Затем преобразователь различий может сопоставить удалённый путь с добавленным и представить пару как rename. При полном совпадении содержимого и подходящих условиях вывод покажет similarity index 100%. На следующем коммите той же ветки это снова вычисление, а не чтение сохранённого события. git mv удобно меняет рабочий путь и индекс, но не создаёт особый объект постоянной личности файла.

Порог -M относится к внутренней оценке похожести, которую не следует заменять формулой «процент совпавших строк» на глаз. Тип данных, размеры и организация совпавших фрагментов влияют на оценку. Поиск по многим кандидатам может стать дорогим: сотни удалений и сотни добавлений создают большое пространство пар. Флаг -l число ограничивает затратную часть поиска переименований/копий при слишком большом числе кандидатов. Тогда отсутствие стрелки rename может отражать выбранный предел работы, а не отсутствие логической связи.

git diff --raw даёт служебные режимы, тип изменения и идентификаторы сторон. --full-index нужен прежде всего для полных имён в выводе заплатки; сокращение иных форматов управляется отдельно предусмотренными параметрами. Изменение режима или типа пути — тоже изменение дерева: символическая ссылка и обычный файл с одинаковыми печатными байтами могут иметь разные смыслы. Для диагностики «почему файл выглядит тем же, но Git видит правку» сначала прочитайте режимы и окончания строк.

Текст и бинарные файлы

У бинарного файла построчная модель может не иметь смысла. Git обычно выводит факт различия, а не нечитаемую заплатку. Атрибуты пути могут задавать принудительный режим и специальный драйвер сравнения. git diff --binary включает переносимое представление изменения бинарных данных для применения средствами Git; это не изображение или PDF-предпросмотр. git diff --numstat показывает машинную сводку добавленных и удалённых строк; у бинарных путей вместо чисел могут быть дефисы.

Для машинного разбора имена путей нельзя бездумно делить по пробелам и переводам строк. В имени допустимы такие символы. У подходящих сводных форматов флаг -z включает нулевые разделители, которые не встречаются внутри имени пути. Текстовое цитирование необычных имён предназначено для человека и не равно исходным байтам имени.

Почему бинарная заплатка не выглядит как дамп

Представление GIT binary patch может содержать блок literal, то есть буквальное восстановленное содержимое, или delta — инструкции восстановления относительно базы. Объявленный размер относится к соответствующему восстановлению; переносимые строки содержат кодированное сжатое представление, а не непосредственно байты изображения. Читать такую запись как привычные добавленные строки файла нельзя. Git проверяет и применяет её по отдельным правилам.

Преобразователь textconv способен показать текстовое извлечение из бинарного документа, например набор метаданных. Такой удобочитаемый diff не обязательно является применимой заплаткой для исходного бинарного файла: извлечение может быть односторонним и терять информацию. При передаче изменений нужен формат, сохраняющий исходные данные, а при обзоре — представление, помогающее понять смысл. Эти цели могут обслуживаться разными вызовами.

У git apply --index change.patch проверяются и рабочие файлы, и их соответствующая исходная версия в индексе; результат подготавливается. --3way разрешает попытку трёхстороннего применения при наличии нужных идентификаторов и базовых объектов и может остановиться с конфликтом. Это не обход несовпадения «любой ценой». Даже текст, находящий подходящий контекст после сдвига строк, может изменить уже другую логику; смысл результата проверяет читатель и программа тестирования.

Проверить применимость и смысл

git diff --cached --check
git diff --cached --stat
git diff --cached -- service.conf

--check проверяет некоторые ошибки пробелов и маркеры конфликта; код завершения сообщает о найденных проблемах. Это узкая проверка качества заплатки. Она не проверяет синтаксис программы, корректность миграции или наличие нужной зависимости. Если готовую заплатку передают файлом, git apply --check change.patch проверяет применимость без записи изменений. --check здесь относится к применению, а не к тому же набору действий, что у diff.

Код завершения — отдельный канал результата

Обычный git diff может успешно напечатать изменения и завершиться кодом 0: его задача состояла в показе. --exit-code включает договор 0 при отсутствии разницы и 1 при её наличии. --quiet подавляет вывод и также включает проверочный исход. Ошибку чтения или неверный аргумент нужно обрабатывать отдельно, а не считать любой ненулевой код доказательством найденной правки. У --no-index сравнительный код завершения включён самим режимом.

Команда git diff --cached --check исследует подготовленную заплатку на предусмотренные ошибки пробелов и маркеры; это другой вопрос, чем «существует ли разница». Для автоматической проверки состава выпуска полезно выполнить раздельно: есть ли неподготовленная правка, есть ли подготовленная, совпадает ли выбранный HEAD с ожидаемым и что именно было собрано. Пустой diff не перечисляет неизвестные файлы, поэтому один этот тест не гарантирует чистоту всех возможных входов сборки.

Почему пустой diff недостаточен

Рабочий файл совпадает с индексом, но отличается от HEAD. Обычный git diff пуст. Потеряны ли изменения?

Разбор

Нет: они подготовлены. Посмотрите git diff --cached. Пустой результат сравнения доказывает равенство только названных сторон, а не всех трёх областей.

К дополнительным механизмам: алгоритмы и коды завершения, применение к индексу и три стороны.
