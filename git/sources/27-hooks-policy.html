Обработчики Git: события, входные данные и границы политики

Hook — программа, которую Git вызывает в определённой точке операции. Польза зависит от точного договора: аргументов, стандартного ввода, каталога, кода завершения и момента изменения данных. Разберём локальную помощь разработчику и проверку принимающей стороны на одном контролируемом обмене.

Что делает обработчик исполняемым

Обычно программы обработчиков расположены в hooks внутри служебного каталога репозитория. Настройка core.hooksPath может выбрать другое место, поэтому сначала исследуют её происхождение. Имя файла соответствует событию, например pre-commit. Пример с окончанием .sample не включается просто из-за существования. В Linux необходимы исполняемый режим и пригодный способ запуска программы.

Само содержимое может быть сценарием оболочки, Python или другой доступной программой. Здесь важно различать язык и механизм вызова. Первая строка сценария выбирает интерпретатор, а её работоспособность зависит от среды. На другой операционной системе правила запуска и наличие интерпретатора проверяют отдельно. Реальные опыты главы выполнялись в Linux на Git 2.43.

Используйте отдельные учебные репозитории, а не каталог обработчиков личного проекта. Лаборатория основной книги намеренно задаёт пустой hooks-каталог; изучение обработчиков проводится в дополнительной копии. Получение обычного клона не копирует чужие локальные hooks как готовую организационную политику. Если проект хранит сценарии в отслеживаемой папке, их включение является отдельным действием.

Точка проверки и момент фиксации результата

При обычном создании коммита pre-commit получает возможность проверить подготовленный результат до оформления сообщения. prepare-commit-msg работает с файлом сообщения и сведениями о способе его подготовки. Затем commit-msg может проверить готовый текст сообщения. После успешного создания вызывается post-commit. Эти точки имеют разные входы и разные возможности остановить действие.

pre-commit
prepare-commit-msg ПУТЬ_СООБЩЕНИЯ [ИСТОЧНИК [КОММИТ]]
commit-msg ПУТЬ_СООБЩЕНИЯ
post-commit

Это схема аргументов, а не четыре команды для ввода подряд. Ненулевой результат проверяющего обработчика способен остановить создание коммита в соответствующей ранней точке. post-commit выполняется уже после него и подходит для последующего уведомления или локального учёта. Возврат ошибки на этой стадии не означает автоматического исчезновения сохранённого коммита.

В нашем реальном опыте маленькие обработчики записывали только имена событий в отдельный журнал. Относительный порядок pre-commit, prepare-commit-msg, commit-msg и post-commit подтвердился. Внутри операции могли происходить дополнительные события обновления ссылок; линейный рисунок четырёх имён не является полным описанием всех внутренних вызовов Git.

Проверять подготовленное состояние

Предположим, разработчик подготовил одну исправленную функцию, а затем продолжил редактирование того же файла. Если pre-commit запускает проверку обычных рабочих файлов, он исследует уже другую версию, чем будущий коммит. Возможны оба неприятных исхода: проверка проходит на исправленной рабочей копии при плохом индексе либо падает на незаконченной работе, которая в коммит не входит.

Для простой проверки пробелов подходит git diff --cached --check: она обращается к подготовленному изменению. Для полноценной сборки требуется получить согласованное дерево подготовленных файлов в отдельном каталоге и явно решить судьбу неотслеживаемых зависимостей. Временное переписывание рабочей копии усложняет восстановление при прерывании. Изоляция проверяемого состояния должна быть частью проекта проверки.

Не добавляйте автоматическое массовое исправление и повторный add без объяснения. Тогда оператор получает в коммите байты, которые отличаются от просмотренных им. Полезнее сообщить конкретную проблему и дать осознанно подготовить исправленный результат. Небольшой локальный обработчик должен быстро давать понятную обратную связь; тяжёлая проверка может выполняться на отдельном исполнителе с теми же определёнными входами.

Как локальная проверка обходится

git commit --no-verify -m "Controlled hook experiment"

У обычного commit ключ --no-verify позволяет пропустить pre-commit и commit-msg. Он не означает отключения вообще всех обработчиков. В выполненном опыте prepare-commit-msg всё равно был вызван. Поэтому нельзя описывать этот параметр как универсальный выключатель событий либо полагаться на него для отладки неизвестной цепочки.

Пользователь контролирует локальные файлы и может изменить выбранный hooks-каталог. Автоматическое задание тоже может получить другой набор настроек. Из этого следует архитектурное решение: локальный обработчик помогает рано заметить ошибку, а обязательные правила принятия проверяются на стороне, которая действительно управляет приёмом. Обе проверки полезны, но отвечают за разные границы.

Приём нескольких ссылок одним push

Пусть отправитель предлагает две новые ветки. Получатель сначала получает необходимые объекты, проверяет предложенные обновления и только затем меняет ссылки. Серверный pre-receive запускается один раз для предложенного набора. Он читает со стандартного ввода строки с прежним идентификатором, новым идентификатором и полным именем ссылки.

СТАРЫЙ_OID НОВЫЙ_OID refs/heads/lab/topic
СТАРЫЙ_OID НОВЫЙ_OID refs/heads/main

Создание и удаление обозначаются нулевым идентификатором на соответствующей стороне. Длину нельзя бездумно закреплять равной сорока: она связана с форматом объектов. Порядок строк не должен быть основой политики. Сначала прочитайте и проверьте весь набор; отказ pre-receive отвергает его целиком.

У update иной договор: отдельный вызов для каждой ссылки с аргументами «имя, старое значение, новое значение». Без требования атомарной отправки одна ссылка может быть принята, а другая отвергнута. Это проверено реальным локальным push: учебная accept появилась у получателя, reject была отвергнута, а общая команда завершилась неуспешно. Неуспешный код всего push поэтому не гарантирует отсутствия любых изменений у получателя.

Минимальная собственная политика

Ниже самостоятельный пример pre-receive для одноразового голого репозитория: разрешать только создание или обновление имён внутри refs/heads/lab/ и отвергать удаление. Сценарий не решает все вопросы качества кода. Он показывает договор входа и единую проверку предложенного набора.

#!/usr/bin/env python3
import sys

updates = []
for line in sys.stdin:
    old, new, ref = line.rstrip('\n').split(' ', 2)
    updates.append((old, new, ref))

for old, new, ref in updates:
    if not ref.startswith('refs/heads/lab/'):
        print('Allowed namespace: refs/heads/lab/', file=sys.stderr)
        sys.exit(1)
    if set(new) == {'0'}:
        print('Deletion is disabled in this exercise', file=sys.stderr)
        sys.exit(1)
sys.exit(0)

В Linux файл сохраняют с точным именем pre-receive в выделенном hooks-каталоге получателя и делают исполняемым. Интерпретатор должен существовать в его среде. При отправке только lab/topic проверка пропустит набор; добавление main приведёт к отказу всего предложения. Пользовательская диагностика выводится в стандартный поток ошибок, откуда передаётся отправителю. Не печатайте содержимое секретных файлов или внутренние данные проверки.

В выполненном опыте более простой pre-receive записывал три входных поля и возвращал один. Получатель остался без предложенных ссылок. Отдельно обработчик update отклонил лишь одно имя. Конкретная Python-политика выше дана как читаемый пример проектирования; перед реальным включением её нужно проверить на создании, обновлении, удалении, нескольких ссылках и некорректном входе в собственной тестовой среде.

Транзакция ссылок и атомарность

Событие reference-transaction относится к обновлению ссылок и может возникать при разных командах Git. В проверенной версии 2.43 наблюдались состояния prepared и committed. Также предусмотрено aborted для соответствующего завершения. Стандартный ввод описывает затрагиваемые ссылки и их значения. Этот договор ближе к фиксации набора ссылок, чем к абстрактной проверке текста сообщения.

В состоянии prepared ссылки уже подготовлены и заблокированы для изменения. Ненулевой ответ может остановить транзакцию. Поздний обработчик committed получает уже совершившийся результат; его ошибку нельзя трактовать как откат. Условия вызова aborted имеют особенности, поэтому сценарий не должен рассчитывать, что любое собственное отклонение обязательно сопровождается отдельным уведомлением об отмене.

Текущие руководства могут описывать дополнительные состояния, которых нет в установленной старой версии. Для обработки событий сначала сверяйте версию и испытайте договор маленькой командой обновления учебной ссылки. Запрос отправителя push --atomic относится к атомарному принятию перечисленных ссылок на поддерживающей стороне. Сам факт наличия update-обработчика не создаёт такую гарантию.

Новые объекты во временном хранилище

При приёме Git может размещать поступившие объекты в карантинном каталоге до окончательного принятия. Это изолирует неудавшийся приём от обычного объектного хранилища. Проверяющий обработчик должен читать объекты через Git с переданным ему окружением. Самовольное удаление служебных переменных внутри такого обработчика способно сделать новые объекты невидимыми.

Здесь проявляется важная граница предыдущей главы: изоляция окружения внешнего учебного теста полезна, а очистка нужного служебного контекста работающего receive-обработчика меняет смысл операции. Если обработчику нужно обратиться к другому репозиторию, это отдельный подпроцесс с осознанно выбранной конфигурацией. Смешивание двух хранилищ через случайные переменные приводит к особенно трудным ошибкам.

Стоимость политики и проверяемое внедрение

Договор pre-push и обработка ошибок

Клиентский pre-push получает сведения о назначении как аргументы, а по стандартному вводу — локальную ссылку, локальный идентификатор, удалённую ссылку и удалённый идентификатор. Это четыре поля и другой смысл сторон, чем у pre-receive. Копирование одного анализатора ввода в другой обработчик без изменения договора создаёт ошибку политики, которая может проявиться только при удалении или необычном соответствии имён.

Вход нужно читать полностью, проверять структуру и сохранять связь ошибки с конкретным предложением. Отдельно определите, что произойдёт при внутреннем исключении. Сценарий, который успел напечатать предупреждение, но завершился нулём, сообщает Git об успехе. Поэтому диагностический текст и код завершения рассматриваются как две части ответа. Повторение проверки после изменения ссылки также не должно запускаться по бесконечной цепочке собственных событий.

Обработчик с сетевым запросом добавляет зависимость доступности принимающей стороне. Время ожидания, повтор запроса и политика при недоступности должны быть частью проектирования. Хранить открытый приём в ожидании неопределённого внешнего ответа дорого для пользователя и сервера. Для части правил достаточно проверяемых локальных данных, тогда как тяжёлая сборка может требовать отдельного этапа до разрешения публикации.

Изменение самого сценария тоже нужно выпускать контролируемо: хранить проверяемую версию, иметь способ вернуть предыдущую и проверять одинаковые примеры после обновления интерпретатора. Сначала прогоняют принятие допустимого имени, отказ смешанному набору и удаление. В нашем дополнительном опыте политика имён приняла единственную lab/topic и отвергла общий набор с main; обработчик prepared отдельно остановил изменение учебной ссылки.

Проверять всю историю при каждом push может оказаться очень дорого. Сначала определите свойство: проверяются только новые объекты, новые достижимые коммиты или полное состояние каждой предлагаемой вершины. Эти множества различаются при повторной отправке и замене истории. Общие коммиты нескольких ссылок нужно учитывать один раз, а лимиты времени и объёма — задавать явно.

Практический маршрут внедрения: сначала наблюдающий режим в учебном получателе, затем проверка положительных и отрицательных случаев, после этого отказ на нужной границе. Измеряйте длительность приёма отдельно от времени передачи, чтобы понимать цену правила. Зафиксируйте поведение при падении интерпретатора и недоступности внешней системы: незаметное принятие по ошибке проверяющего кода обычно противоречит назначению обязательной политики.

Источники договора: githooks для Git 2.43, приём объектов и карантин, режимы push. Общая карта клиентских и серверных событий есть в Pro Git: Git Hooks. Реальный сетевой сервер и организационная система прав в этой главе не развёртывались.
