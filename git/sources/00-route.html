От изменения файла до проверенного выпуска

В этом томе одно изменение проходит весь путь: байты файла, индекс Git, коммит, общая история, сборка, проверка, сохранённый артефакт и выпуск. На каждом переходе установим, кто действует, какие данные он читает и чем подтверждается результат.

Что именно мы будем прослеживать

Представьте небольшую службу, которая отвечает на запрос приветствием. Нужно изменить ответ и доставить новую версию другому человеку. Сначала это выглядит как редактирование одной строки. Но другой человек должен получить именно нужные байты, знать их происхождение, повторить проверку и запустить программу в подходящей среде. Между этими требованиями лежат разные механизмы. Git отвечает за представление и передачу истории; инструмент сборки превращает выбранные входы в выход; система автоматизации запускает действия и сохраняет наблюдения; процедура выпуска связывает полученный результат с работающей средой.

Полезно сразу различать три утверждения. «Изменение сохранено» означает, что создан доступный нам объект истории. «Изменение проверено» означает, что конкретные проверки дали ожидаемый результат для определённых входов и среды. «Изменение работает у пользователей» требует отдельного наблюдения после запуска. Ни одно из этих утверждений автоматически не следует из другого. Поэтому зелёный значок задания будем читать как запись об исходе определённых действий, а не как универсальное доказательство качества программы.

Наш сквозной пример — собственная маленькая программа на Python, её тесты и упаковщик. Она намеренно проста: при изучении Git не нужно сначала разбираться в большом приложении. При этом история, конфликт, передача объектов и проверка байтов архива будут настоящими. В некоторых главах появляются C, Java и Maven: они показывают отличия технологических цепочек, но не являются обязательными зависимостями практикума.

Маршрут чтения

Главы 1–4 создают модель репозитория: три состояния файла, объекты, индекс и граф коммитов. Не торопитесь запоминать команды. Сначала добейтесь возможности заранее сказать, какие байты прочитает следующая команда и какие указатели изменит. В главе об индексе один файл одновременно существует в трёх версиях. Этот небольшой опыт объясняет больше, чем привычка всегда вводить одну последовательность add и commit.

Главы 5–9 разбирают ветки, сравнения, слияние, переписывание и восстановление. У каждой операции будут исходное состояние, действие и наблюдаемый результат. Конфликт рассматривается как доступные версии для принятия решения, а восстановление — через сохранённые объекты и ссылки. После этого главы 10–13 добавляют вторую копию репозитория, правила совместной работы, преобразования файлов и стоимость хранения. Здесь становится ясно, почему получение истории и изменение рабочей папки — отдельные события.

Главы 14–17 переводят внимание с истории на сборку. Входы, версии инструментов, зависимости и среда определяют выходные байты. Мы отделим повторяемость запуска от совпадения результата и построим архив с контролируемыми метаданными. В главе о кэше сборки станет видно, как забытый вход превращает ускорение в выдачу старого результата. Это связывает том с общей теорией кэширования, но ключом здесь служит описание действия, а значением — его сохранённый выход.

Главы 18–21 показывают Jenkins изнутри: управляющий процесс, агент, очередь, исполнитель, рабочий каталог и журнал. Затем разберём описание конвейера, смысл проверок и измерение времени. Глава 22 соединяет знания в последовательную лабораторию; глава 23 доводит результат до выпуска и восстановления. Большой объём про выпуск и непрерывную проверку появится также в следующих томах библиотеки; здесь дана завершённая основа, необходимая для понимания судьбы одного артефакта.

Как пользоваться схемами, справками и лабораторией

Пошаговые рисунки показывают выбранный пример, а не все возможные режимы инструмента. Перед переключением шага прочитайте условия: начальные ветки, содержимое файлов, доступность удалённой стороны. Стрелка означает конкретное действие между участниками; нижняя таблица объясняет изменение значений. Если действие меняет только ссылку, не следует мысленно приписывать ему копирование всех файлов. Полная текстовая последовательность остаётся под рисунком и доступна при печати.

Нажатие на название известной команды в тексте открывает встроенную справку. В ней есть назначение, форма вызова и отдельное объяснение каждого включённого параметра: что меняется, когда это полезно и как прочитать результат. Поиск принимает составные имена, например git diff --cached. Это справочник по использованным механизмам, а не обещание охватить все параметры всех версий Git. В каждой карточке есть ссылка на первичную документацию; для работы без сети сохранены сами объяснения.

Команды Git выполняются в отдельном настоящем учебном репозитории. Браузер не получает доступ к вашим файлам и не запускает Git при чтении. В практикуме описан локальный тренажёр: две рабочие копии и общий репозиторий без сети. Состояние сохраняется между упражнениями. Проверка читает результат, а явный возврат к контрольной точке пересоздаёт только помеченный учебный стенд. Данные личных репозиториев в задания не входят.

Для чтения достаточно открыть библиотеку обычным браузером. Для практики нужны уже установленные Git и Python 3.10 или новее; проверенная среда — Linux, Git 2.43.0 и Python 3.12.3. Работа на Windows не проверялась: особенности путей, прав и символических ссылок могут отличаться. На рабочем компьютере с запретом установки и изменения среды используйте текст и схемы; запускайте лабораторию только там, где разрешены отдельные учебные файлы. Jenkins и Maven здесь объясняются с примерами конфигурации, но их серверный запуск не входил в фактическую проверку тома.

Обратная связь как наблюдаемый процесс

Жизненный цикл программы удобнее понимать через решения и свидетельства. Появилась потребность — записали проверяемое ожидаемое поведение. Предложили изменение — получили различия и происхождение файлов. Выполнили проверку — сохранили входы, среду и результат. Запустили выпуск — наблюдаем работу службы и возможность восстановления. Названия организационных подходов полезны только тогда, когда помогают сократить неопределённость на этих переходах. Короткий цикл сам по себе не делает ошибочную проверку содержательной.

Измерять стоит уже тогда, когда появляется конкретное решение: долго ли ждать результата, что ограничивает сборку, поможет ли ещё один исполнитель. Одно число без условий мало полезно. Отмечайте размер изменения, холодный или прогретый кэш, время в очереди, длительность действий и разброс повторов. Ускорение задания с десяти до пяти минут не обязательно вдвое ускорит получение результата, если перед ним час очереди. Эти связи подробно разберём на графе зависимостей и примерах распределения ресурсов.

Хорошая проверка понимания — предсказать изменение состояния до запуска команды и затем объяснить расхождение с прогнозом. В конце опыта запишите: что существовало до действия, что прочитал инструмент, что он изменил и чем это подтверждено. Когда ответ получается без магических слов «синхронизировалось» и «сохранилось куда-то», появляется основа для самостоятельной диагностики.

Связи с остальными томами

Linux объясняет процессы, файлы, права и ресурсы, на которых работают Git и агент сборки. Bash нужен для точных аргументов, кавычек, каналов и кодов завершения. Сети раскрывают транспорт подключения, DNS и проверку удалённой стороны. PostgreSQL понадобится при обсуждении изменения данных во время выпуска: возврат программы не отменяет автоматически записанные транзакции. Общий словарь доступен из каждого тома, поэтому термин можно уточнить по ходу чтения.
