Конфигурация и окружение: откуда взялось поведение Git

Одинаковая команда в двух терминалах иногда выбирает разных авторов, редакторы, каталоги и способы обмена. Чтобы объяснить различие, нужно восстановить путь выбора параметра: источник, область, порядок чтения и специальные переменные конкретной операции. Здесь этот путь исследуется на отдельных учебных файлах.

Команда начинается раньше, чем чтение .git/config

Оболочка сначала находит программу и формирует аргументы. Процесс получает текущий каталог и окружение. Затем Git определяет служебное хранилище, рабочее дерево и применимую конфигурацию. Только после этого подкоманда решает, какие объекты или файлы читать. Поэтому расследование странного commit следует начинать с определения места работы, а не с повторной записи предполагаемого имени автора.

git --version
git rev-parse --show-toplevel
git rev-parse --git-dir
git rev-parse --git-common-dir
git config --show-origin --show-scope --list

--show-toplevel показывает корень рабочего дерева, --git-dir — служебный каталог данной рабочей копии. У связанного рабочего дерева он может отличаться от общего каталога объектов и ссылок, который показывает --git-common-dir. Последняя команда добавляет к значениям область и происхождение. Её полный вывод может содержать адреса с данными доступа: для обсуждения проблемы выбирайте нужные ключи и удаляйте чувствительные значения.

Служебные переменные GIT_DIR, GIT_WORK_TREE и GIT_INDEX_FILE способны изменить объекты исследования даже при знакомом приглашении оболочки. Перед опытами проверьте их наличие и используйте отдельную лабораторную среду. Ключ -C КАТАЛОГ, помещённый перед подкомандой, меняет рабочий каталог самого Git. Относительные пути после него интерпретируются уже с учётом этого перехода.

Область хранения и источник значения

Системная конфигурация относится к установленному Git и пользователям машины. Глобальная — к пользователю. Локальная находится в служебном каталоге конкретного репозитория. Возможна также отдельная конфигурация рабочего дерева. Параметры одного запуска образуют командную область. Это описание порядка чтения; точный выбор для многозначного ключа зависит от назначения самого параметра.

Обычное одиночное значение, прочитанное позже, перекрывает прежнее. Но список правил получения веток может состоять из нескольких записей. Поэтому при исследовании неизвестного параметра полезно сначала запросить все значения. Команда --get-all сохраняет видимость нескольких источников, тогда как --get выбирает значение по правилам чтения. Запись через --local явно ограничивает изменение учебным репозиторием.

git config --local demo.value local
git config --show-origin --show-scope --get-all demo.value
git -c demo.value=command config --show-origin --show-scope --get demo.value

Ключ demo.value в этом опыте придуман нами и не управляет поведением Git. Он позволяет изучить чтение безопасной строки. Параметр -c действует на один запуск: последнее значение будет command, а локальный файл по-прежнему содержит local. В проверенном Git 2.43 это сопровождалось командной областью и указанием источника командной строки.

Учебная глобальная конфигурация без изменения личной

Для полного опыта создайте рядом с одноразовым репозиторием файл demo-global.cfg с секцией ниже. Переменная GIT_CONFIG_GLOBAL позволяет одному процессу читать этот файл вместо персональной глобальной конфигурации. Значения существующего HOME менять не требуется. Системный источник можно исключить для опыта через GIT_CONFIG_NOSYSTEM=1; не переносите такую изоляцию автоматически в рабочие процедуры, где системные правила могут быть необходимы.

[demo]
    value = global
GIT_CONFIG_GLOBAL=../demo-global.cfg GIT_CONFIG_NOSYSTEM=1 \
  git config --show-origin --show-scope --get-all demo.value

Команду выполняют из корня учебного репозитория. Теперь видны глобальное и локальное значения, а обычное чтение даёт local. Префикс окружения перед командой в Bash задаёт значения только этому запуску. Смена каталога меняет смысл относительного имени конфигурационного файла, поэтому в повторяемом автоматическом опыте лучше заранее вычислить абсолютный путь к учебному файлу.

Следующая ступень — конфигурация через окружение. Пара GIT_CONFIG_KEY_0 и GIT_CONFIG_VALUE_0 описывает запись номер ноль, а GIT_CONFIG_COUNT задаёт количество таких пар. Нумерация должна быть непрерывной; пропущенная часть вызывает ошибку. В нашем опыте это значение перекрыло файлы, но явный git -c demo.value=command перекрыл уже его.

GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=demo.value \
GIT_CONFIG_VALUE_0=environment git config --get demo.value

Предсказание результата — строка environment. Если вы увидели другое, проверьте оставшиеся переменные и дополнительные параметры оболочки. В книге этот порядок проверен реальным запуском. Он относится к передаваемым конфигурационным парам; из него нельзя вывести универсальное правило для всех переменных окружения, встречающихся в Git.

Почему имя из config может отличаться от автора коммита

Создание коммита имеет собственные входы: имя и адрес автора, имя и адрес создающего коммит, временные отметки. Переменные GIT_AUTHOR_NAME и родственные им напрямую участвуют в формировании этих полей. Они не обязаны менять результат запроса git config --get user.name. Поэтому исправление конфигурации может оставить неожиданную личность в новом объекте, если в окружении сохранилось явное значение.

Проверяйте фактический объект через git show --no-patch --format=fuller HEAD. Формат fuller выводит обе роли и обе даты. Имя в этих полях является утверждением создавшего объект процесса. Установление личности через подпись и доверенный ключ разобрано отдельно. Согласованная учебная личность с адресом example.invalid позволяет проводить опыты без использования личной подписи.

Редактор тоже выбирается по отдельной цепочке: явные переменные и параметры могут влиять на запуск независимо от привычного редактора рабочего стола. Для интерактивного rebase существует отдельный выбор редактора последовательности. Когда автоматический запуск неожиданно зависает, выясните, не ждёт ли он редактор или ввод сообщения. Флаг -m передаёт сообщение commit непосредственно, но не решает произвольные ожидания других операций.

Включаемые файлы и условие includeIf

Обычный include.path подключает ещё один конфигурационный файл в месте чтения. Относительный путь отсчитывается от содержащего include файла. Это удобно для общих учебных настроек, но порядок включения становится частью выбора значения. Перенос одного фрагмента вверх или вниз способен изменить итог, даже если строки внутри него прежние.

[includeIf "gitdir:/path/to/demo/.git"]
    path = demo-extra.cfg

Это образец, где /path/to/demo/.git нужно заменить фактическим учебным служебным каталогом. Условие gitdir: сопоставляет расположение Git-каталога, а не произвольный текущий подкаталог с исходниками. Для подмодуля или связанного рабочего дерева учитывается фактическое место хранения метаданных. Поэтому полезно сначала прочитать --git-dir и --git-common-dir, затем писать правило.

В проверенном опыте подключённый файл задавал demo.selected=conditional. Чтение внутри нужного репозитория возвращало эту строку; содержание самого файла приложения не менялось. У шаблона с завершающей косой чертой есть рекурсивный смысл, у gitdir/i: — сопоставление без учёта регистра. Для переносимой политики нужно учитывать реальное устройство путей и файловой системы, а не полагаться на похожее написание двух имён.

В новых версиях документации появляются дополнительные виды условий. Совместимость книги опирается на проверенный Git 2.43; наличие условия на текущем сайте ещё не означает его поддержки установленной программой. Неизвестный или ошибочный шаблон лучше обнаружить контрольным ключом и проверкой происхождения, чем первым же настоящим коммитом с неверными данными.

Общая конфигурация нескольких рабочих деревьев

Связанные рабочие деревья используют общее хранилище и часть общих настроек. Для раздельных настроек предусмотрено расширение extensions.worktreeConfig и чтение config.worktree. После осознанного включения расширения git config --worktree обращается к конфигурации конкретного дерева. Здесь важно различать общий каталог и собственный Git-каталог связанной копии.

В существующем репозитории включение расширения требует проверки расположения core.worktree и значения core.bare: некоторые параметры нужно переносить из общего файла в конфигурацию основного дерева. Поэтому это описание механизма, а не команда массового ремонта неизвестных репозиториев. Для исследования создают свежий отдельный проект и измеряют итог внутри каждой рабочей копии.

Псевдоним команды и его текущий каталог

git config --local alias.short 'status --short'
git short
git config --local alias.where '!pwd'
git where

Первый alias, то есть короткое имя команды, разворачивается в аргументы Git. Он не является отдельной встроенной подкомандой и не добавляет собственную проверку безопасности. Второй начинается с восклицательного знака и запускает оболочку. В проверенном опыте запуск git where из вложенной папки напечатал корень рабочего дерева: оболочечный псевдоним стартовал оттуда.

Git передаёт исходный префикс пути через GIT_PREFIX, если он нужен сценарию. Простое добавление переменных и аргументов в текст shell-alias быстро создаёт несколько уровней кавычек. Для сложной обработки предпочтительнее отдельная проверяемая программа с явными аргументами. Псевдоним с ! следует читать как исполняемый код, особенно если настройка получена из внешнего фрагмента.

Маршрут расследования и цена проверки

Несколько значений и проверка типа

У конфигурации есть ещё одна важная ось: способ интерпретации значения. Ключ может быть одиночной строкой, булевым переключателем или последовательностью правил. Добавим две учебные записи:

git config --local --add demo.list alpha
git config --local --add demo.list beta
git config --show-origin --get-all demo.list
git config --local demo.enabled yes
git config --type=bool --get demo.enabled

--add сохраняет дополнительную запись, а --get-all показывает обе. Последний запрос нормализует распознанное логическое значение и возвращает true. Если вместо допустимого значения записана произвольная строка, проверка типа завершится ошибкой. Успешное чтение строки без проверки типа и успешное использование параметра конкретной командой — разные наблюдения.

Для очистки именно этих пробных записей подходят git config --local --unset-all demo.list и git config --local --unset demo.enabled. Вторая форма рассчитана на выбранное одиночное значение; несколько совпадающих записей требуют осознанного выбора. После удаления локального значения может снова проявиться глобальное. Поэтому фраза «я удалил параметр, но он остался» часто означает существование другого источника, а не отказ записи файла.

Отдельно различайте обычный поиск конфигурации и чтение одного файла через --file. При явном выборе файла правила автоматического раскрытия include могут отличаться от обычного объединённого чтения. Параметр --includes явно просит обработать подключения. Если условный ключ виден в обычной работе, но не появился при исследовании одного файла, проверьте этот режим, расположение подключаемого файла и контекст репозитория.

Такая диагностика требует фиксировать не только искомую строку, но и сам запрос. Команды с --local, --global и обычным чтением исследуют разные наборы источников. Сравнение их вывода без учёта этого различия легко создаёт видимость противоречия там, где программа последовательно выполняет разные указания.

Представим, что сборочный исполнитель пишет чужой адрес автора. Сначала фиксируем версию Git, каталог и фактические поля последнего коммита. Затем читаем конкретные ключи с происхождением и областью, проверяем переменные автора и параметры запуска. Если значение пришло из include, устанавливаем условие его включения. Только после этого меняем минимальный нужный источник и повторяем маленький контрольный коммит в учебной копии.

Большой список всех настроек удобен один раз, но для постоянной диагностики лучше узкие запросы: они уменьшают объём вывода и вероятность раскрыть лишнее. Чтение локальной конфигурации обычно намного дешевле полной сборки. Однако оболочечные псевдонимы и внешние редакторы могут выполнять произвольную работу, поэтому длительность такой «короткой команды» нужно объяснять по фактической цепочке процессов.

Проверены: приоритет файлов, окружения и -c, вывод scope/origin, условное подключение, обычный alias, каталог оболочечного alias и выбор репозитория через -C. Политики организации, персональные обработчики и настройка существующих связанных деревьев не менялись. Первичные подробности: git-config, git и окружение, раздел Pro Git о конфигурации.
