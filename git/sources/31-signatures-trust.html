Подпись и доверие: кто подтвердил какие байты

Контрольная сумма связывает имя с содержимым, подпись связывает данные с ключом, а политика доверия определяет, чьё подтверждение приемлемо. Для воспроизводимой поставки нужно явно пройти все три шага. Проверим их на одноразовом SSH-ключе, не используя личные ключи или учётные данные.

Сначала определить подписываемое утверждение

Обычный идентификатор коммита получается из его содержимого по правилам Git. Если вы получили ожидаемый идентификатор по доверенному каналу, он помогает проверить, что рассматривается нужный объект. Но отправитель может создать новый объект с любым именем автора в метаданных. Само совпадение поля email с известным человеком не удостоверяет его участие.

Цифровая подпись создаётся закрытым ключом и проверяется соответствующим открытым ключом. Проверка устанавливает связь конкретных данных с этим ключом в рамках используемой схемы. Чтобы назвать владельца, дополнительно нужен проверенный источник сведений о ключе и правило, какие действия ему разрешено подтверждать. Это внешний по отношению к обычному полю автора контекст.

Даже принятая подпись не утверждает автоматически, что программа безопасна, тесты выполнены или зависимости доступны. Нужно читать точное подписанное утверждение. Коммит, метка, файл архива и свидетельство о сборке — разные объекты. Политика выпуска определяет, какие из них проверяются совместно.

Что подписывается внутри Git

Подписанный коммит включает сведения подписи в своём представлении. Проверяемые данные строятся по предусмотренным правилам без самоссылочного включения подписи в её собственный вход. Другие значимые поля коммита — дерево, родители, роли и даты — остаются частью защищаемого содержания. Изменение родителей при rebase создаёт другое утверждение, даже если прикладные файлы прежние.

Аннотированная метка имеет собственный объект с целью и сообщением. Подпись такой метки подтверждает этот объект. Она помогает зафиксировать выбранный коммит выпуска, но не означает наличие отдельной действительной подписи у каждого его предка. Нужно различать доверие выбранной вершине и требование подписывать каждое изменение основной линии.

git cat-file -t release
git cat-file -p release
git show --no-patch --show-signature HEAD
git verify-commit HEAD
git verify-tag release

Первые команды помогают понять тип и содержание, последующие запускают проверку соответствующей подписи. Имя release здесь обозначает вашу аннотированную учебную метку. Неподписанная облегчённая метка не становится подписанной из-за подходящего имени. Для автоматического решения важно учитывать код завершения и конкретную диагностику выбранного проверяющего механизма.

Форматы и внешние средства проверки

Git поддерживает разные форматы подписи, включая OpenPGP, X.509 и SSH. Настройка gpg.format выбирает формат, а соответствующая программа выполняет создание и проверку. Имя настройки gpg встречается также при SSH-подписях; его нельзя интерпретировать как доказательство, что фактически вызвана одна конкретная программа OpenPGP.

Наличие Git ещё не гарантирует доступности всех средств подписи. Возможны отсутствующий исполняемый файл, неподдерживаемая версия, недоступный закрытый ключ или ошибка доверенного списка. Это разные причины неуспеха. В книге выполнен один ограниченный опыт SSH-подписи на Git 2.43 с доступным ssh-keygen. Полноценные инфраструктуры сертификатов и OpenPGP здесь не развёртывались.

Одноразовый учебный ключ

Создайте новый отдельный каталог опыта и ключ с новым именем вне рабочего дерева. Команды ниже относятся только к этой временной среде. Пустая парольная фраза используется для автоматизируемого одноразового упражнения; полученный ключ не предназначен для личного входа или настоящего выпуска.

ssh-keygen -q -t ed25519 -N '' -f ../lab-signing-key
git config --local user.name 'Demo Student'
git config --local user.email student@example.invalid
git config --local gpg.format ssh
git config --local user.signingkey "$(pwd)/../lab-signing-key"
git config --local gpg.ssh.allowedSignersFile "$(pwd)/../allowed-signers"

-q сокращает сообщения создания, -t выбирает тип ключа, -N передаёт парольную фразу, -f задаёт конкретный новый файл. Рядом появляется открытая часть с окончанием .pub. Все настройки Git записываются локально. Абсолютный учебный путь делает назначение понятным при последующих переходах в подкаталоги.

Закрытая часть остаётся за пределами отслеживаемых исходников. В настоящей инфраструктуре дополнительно определяют защиту хранения, выдачу прав, использование аппаратного средства или агента и отзыв при компрометации. В этом упражнении важна лишь воспроизводимая связь своих данных с временным ключом. Личный каталог .ssh и персональная конфигурация не изменяются.

Allowed signers: имя и разрешённый ключ

Файл allowed-signers содержит записи доверенных подписантов. Для нашего опыта он состоит из учебного имени, ограничения пространства имён и открытого ключа. Полная строка открытого ключа получается из созданного .pub; руками сокращать её нельзя. Следующая программа сохраняет только тип ключа и его данные, отбрасывая необязательный комментарий.

python3 - <<'PY'
from pathlib import Path
parts = Path('../lab-signing-key.pub').read_text().split()
line = 'student@example.invalid namespaces="git" '
line += ' '.join(parts[:2]) + '\n'
Path('../allowed-signers').write_text(line)
PY

Имя подписанта называют principal: это идентификатор, с которым проверяющий связывает разрешённый открытый ключ. Ограничение namespaces="git" относится к назначению подписи. Оно помогает не смешивать подтверждения разных протоколов, но не заменяет проверку владельца ключа. Авторский email в коммите и разрешённое имя в этом файле не нужно считать автоматически одной и той же доказанной личностью.

Подписать и проверить свой коммит

printf 'signed demonstration\n' > demo.txt
git add demo.txt
git commit -S -m "Signed local demonstration"
git verify-commit HEAD
git log -1 --show-signature

Флаг -S у commit запрашивает подпись выбранным форматом. Он отличается от строчного -s, который добавляет строку Signed-off-by в сообщение и сам по себе не создаёт криптографическую подпись. В реальном опыте verify-commit завершился нулём, когда созданный открытый ключ находился в разрешённом списке.

Сохраните идентификатор и не меняйте коммит. Затем временно сделайте учебный allowed-signers пустым и повторите проверку. В выполненном опыте команда завершилась неуспешно при тех же байтах объекта и той же подписи. Изменилось только основание доверия. После возврата исходной разрешённой записи снова появляется нужный контекст проверки.

Таким образом, человеческое сообщение о хорошей математической подписи и итоговое принятие Git могут различаться. Для SSH Git учитывает присутствие ключа в разрешённом списке; без него доверие не достигает требуемого уровня. Не исправляйте такой отказ включением произвольного ключа из того же непроверенного письма. Сначала установите, откуда должен происходить доверенный список.

Кто управляет правилом доверия

Если атакующий способен одновременно заменить данные, ключ и правила его принятия, проверка покажет согласованный, но бессмысленный для владельца системы результат. Поэтому источник allowed-signers должен быть частью политики: например, проверяемая организационная выдача либо заранее установленный личный доверенный набор. Хранение файла в проекте возможно только при понятной цепочке принятия изменений самого доверия.

Удаление ключа, ограничение срока и отзыв — разные операции. У поддерживающих версий есть параметры сроков допустимости и отдельный файл отозванных ключей. Проверка старой подписи может зависеть от времени и выбранного правила оценки. Зафиксируйте версию инструмента и политики при подготовке аудиторского результата. Эти дополнительные варианты в нашем простом опыте не исполнялись.

Дата внутри коммита является подписанным утверждением создателя, а не автоматически доказанной внешним источником отметкой времени. Если задача требует надёжного времени выпуска, нужно отдельно определить, каким свидетельствам доверяет проверяющий. Перестановка часов системы и повторная подпись не должны незаметно подменять этот договор.

Подпись, транспорт и результат сборки

SSH-соединение с Git-сервером подтверждает и защищает транспортную сессию по своим правилам. SSH-подпись коммита подтверждает конкретные сохранённые данные. Проверка ключа сервера, разрешение пользователю отправлять ветки и доверие подписанту кода остаются отдельными слоями. Разделение помогает расследовать случай, когда push разрешён, а подпись принятого коммита не соответствует политике.

Подписанный push, где используется соответствующий механизм протокола, описывает ещё один вид утверждения об отправке. Его тоже нельзя автоматически заменить требованием подписывать каждое содержимое. Перед введением правила нужно сформулировать, что именно требуется подтвердить: выбранный выпуск, каждое изменение либо действие публикации определённого набора ссылок.

У ZIP из нашей лаборатории отдельная контрольная сумма. Подписанная метка исходников ещё не устанавливает, что данный ZIP построен именно из них. Нужны проверка состава, объявленных входов и сведения о сборке; при необходимости подписывается и соответствующее свидетельство. Воспроизводимая сборка даёт дополнительный способ независимо сопоставить исходную версию с байтами результата.

Как принять конкретный выпуск

Представим, что сопровождающий прислал подписанную метку lab-release и архив приложения. Сначала проверяющий получает сам объект метки, устанавливает его тип и проверяет подпись по заранее выбранному правилу доверия. Затем разрешает метку до коммита и фиксирует полный идентификатор. Только после этого сравнивает объявленный исходный коммит архива с выбранным объектом. Совпадение имени lab-release в двух сообщениях недостаточно: имя ссылки можно переставить, поэтому в протоколе проверки сохраняют и идентификатор объекта метки.

git cat-file -t lab-release
git verify-tag lab-release
git rev-parse --verify 'lab-release^{commit}'

Первый вывод должен соответствовать аннотированной метке, если именно такой формат предусмотрен договором выпуска. verify-tag проверяет её подпись, а выражение с фигурными скобками требует получить коммит после раскрытия метки. Неподписанная лёгкая метка не становится подписанной от того, что целевой коммит имеет собственную подпись. Здесь команды показывают дополнительный маршрут проверки; в автоматическом опыте этой главы исполнялась подпись коммита, создание подписанной метки отдельно не проверялось.

Если проверка завершается ошибкой, разбирайте слои по очереди. Найден ли объект, правильный ли у него тип, доступно ли средство проверки, корректен ли формат ключа, соответствует ли назначение подписи разрешённому пространству имён, доверяет ли политика найденному ключу? Подстановка нового ключа сразу после первого отказа стирает различие между технической поломкой и отказом доверия. Сохраните код завершения и диагностическое сообщение, исправьте установленную причину и повторите тот же опыт над тем же идентификатором.

Полезный итог проверки формулируется конкретно: выбранный объект принят таким средством и такой версией политики. Из этого ещё не следует, что программа лишена ошибок или что подписант имел право выпускать любую версию продукта. Криптографическое свидетельство становится эксплуатационным решением только вместе с явно определёнными полномочиями подписанта.

Стоимость проверки и пригодность автоматизации

Проверка тысяч подписей может запускать внешние процессы и читать хранилища ключей. Измеряйте время разрешения объектов отдельно от времени криптографической проверки и поиска доверия. Для выпуска часто сначала ограничивают проверяемый набор выбранной историей и политикой. Пропуск непроверенной части нужно описывать явно, а не маскировать общей надписью «всё проверено».

Кэш результата проверки должен учитывать не только идентификатор объекта, но и используемую политику доверия, средство проверки и существенные условия времени. Неизменный коммит после отзыва ключа может получить другой итог принятия. Поэтому бессрочное сохранение одного булева значения «подпись хорошая» обычно недостаточно для эксплуатационного решения.

Проверено: создание временного Ed25519-ключа, собственный SSH-подписанный коммит, принятие с разрешённой записью и отказ с пустым списком. Закрытые ключи существовали только во временном каталоге опыта. Источники: формат подписей Git, настройки gpg.format и SSH-доверия, verify-commit, договор ssh-keygen и allowed signers.
