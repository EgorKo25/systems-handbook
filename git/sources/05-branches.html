Ветки, HEAD и несколько рабочих деревьев

Что перемещается при commit и switch и почему отдельный каталог ещё не означает отдельную историю

Ветка — имя вершины

Ветка Git — изменяемая ссылка на коммит. Имя main обычно соответствует полному имени refs/heads/main. В простом формате хранения ссылка может выглядеть как файл с идентификатором, но Git умеет упаковывать ссылки, а новые версии поддерживают и другие служебные представления. Программа должна читать их через команды Git. Отсутствие отдельного файла .git/refs/heads/main не доказывает отсутствие ветки.

HEAD отвечает на вопрос «из какого состояния работает этот рабочий каталог». В обычном случае это символическая ссылка, содержащая имя текущей ветки. Коммит читает подготовленное дерево, создаёт новый объект с текущим коммитом в качестве родителя и перемещает текущую ветку к новому объекту. Остальные ветки остаются на прежних вершинах. Создание ветки не копирует файлы и всю историю: достаточно добавить ещё одно имя существующему коммиту.

До фиксации:  HEAD → refs/heads/topic → B → A
                                    ↑
                            refs/heads/main
После:        HEAD → refs/heads/topic → C → B → A
                                         ↑
                                 refs/heads/main

Прямая и символическая ссылка

Прямая ссылка содержит идентификатор объекта. Символическая, symbolic ref, содержит имя другой ссылки, например ref: refs/heads/main. При обычной работе HEAD — второй случай. Во время commit Git узнаёт выбранную ветку и обновляет именно её. Если напрямую изменить только текст служебного файла без правил Git, можно обойти проверку конкурентного изменения, испортить формат или забыть журнал. Ссылки читают и меняют специальными командами, а не случайным перенаправлением в .git/refs.

git symbolic-ref --quiet HEAD печатает имя текущей ветки, если HEAD символический; при отсоединённом HEAD завершится особым ненулевым исходом без обычного сообщения. --quiet подавляет эту ожидаемую диагностику, но не превращает любой сбой в успешный ответ. git branch --show-current удобнее для человека, однако пустое имя тоже требует интерпретации контекста. Для точной автоматизации отдельно проверяют, есть ли коммит и является ли HEAD символическим.

У ещё не родившейся ветки HEAD уже содержит имя, а соответствующая прямая ссылка на коммит ещё отсутствует. Поэтому команда показа текущего имени может быть успешной, когда git rev-parse --verify HEAD ещё не находит коммит. Первый commit создаёт корневой объект и первое значение этой ветки. Это нормальная стадия нового репозитория, а не повреждённый указатель на нули.

Создание и переключение — разные операции

git branch topic
git switch topic
git symbolic-ref --short HEAD
# topic
git rev-parse HEAD
git show-ref --heads

git branch topic создаёт ссылку на текущий коммит, но не переключает рабочий каталог. git switch topic выбирает ветку и приводит индекс и необходимые рабочие файлы к выбранному снимку. git switch -c other совмещает создание новой ветки other и переключение: -c означает create, создать. symbolic-ref читает символическую ссылку; --short сокращает полное имя. show-ref --heads перечисляет локальные ветки и их идентификаторы, не обращаясь к серверу.

Переключение не является безусловным уничтожением текущих правок. Git может перенести незакоммиченные изменения в новый контекст, если операция не должна перезаписать их конфликтующим содержимым. В противном случае команда откажет и перечислит мешающие пути. Следовательно, «я переключился на main» ещё не означает «каталог в точности равен main». Сразу посмотрите статус. Для воспроизводимой проверки нужен чистый снимок, а не только ожидаемая подпись ветки в приглашении оболочки.

Условное обновление не теряет конкурентное изменение

Низкоуровневое git update-ref ИМЯ НОВОЕ СТАРОЕ меняет ссылку лишь при совпадении её текущего значения с ожидаемым старым. Это локальная форма сравнения и замены. Два процесса могли оба прочитать A, затем изготовить B и C. Если первый обновил ссылку A→B, второй запрос A→C должен отказать, а не молча переписать B. После отказа второй процесс заново выясняет состояние и выбирает интеграцию.

old_oid=$(git rev-parse HEAD)
git branch conditional-example "$old_oid"
tree_oid=$(git write-tree)
new_oid=$(printf 'Объект для условного обновления\n' |
  git commit-tree "$tree_oid" -p "$old_oid")
git update-ref refs/heads/conditional-example "$new_oid" "$old_oid"
git update-ref refs/heads/conditional-example "$old_oid" "$old_oid"

Последний вызов ожидаемо откажет: ссылка уже содержит new_oid, а ожидание всё ещё old_oid. В опыте изменяется только специально созданная, невыбранная ветка conditional-example; рабочий HEAD и индекс остаются прежними. Прямое низкоуровневое перемещение выбранной ветки не следует считать полноценным переключением рабочих файлов. Ссылка и её материализация в каталоге — разные уровни.

Для нескольких связанных ссылок у update-ref предусмотрен ввод транзакционных инструкций через --stdin. Читатель задаёт ожидаемые значения и запрашивает согласованное обновление. Эта атомарность касается таблицы ссылок данного репозитория; она не делает общую транзакцию с базой приложения или другим сервером. Именно такой ограниченный смысл полезно приписывать словам «атомарно обновили ветки».

Отсоединённый HEAD

git switch --detach HEAD~1 выбирает конкретный предыдущий коммит, не локальную ветку. Флаг --detach означает отсоединение HEAD: он непосредственно указывает на объект. Можно читать файлы, собирать программу и даже создавать новые коммиты. Новые объекты будут нормальными, но при переходе на другую ветку привычного имени у получившейся линии может не остаться.

git switch --detach HEAD~1
# работа и, при необходимости, учебный commit
git switch -c investigation

Последняя команда создаёт имя investigation на текущем состоянии, сохраняя удобную достижимость этой линии. Отсоединённый режим часто возникает в автоматической сборке: системе нужен конкретный неизменный коммит, а не имя ветки, способное сдвинуться во время работы. Ошибка не в самом режиме, а в предположении, что новый коммит уже прикреплён к известной ветке.

Почему после переключения новые коммиты теряют привычное имя

В отсоединённом режиме новый commit записывает родителем прежний выбранный коммит и обновляет прямое значение HEAD. Если затем выбрать main, HEAD снова станет символическим и будет вести к main. Неименованная линия не исчезла из хранилища мгновенно, но из обычного обхода main может быть недостижима. Reflog HEAD часто удерживает место недавней работы. Порядковый номер HEAD@{1} отражает последнее перемещение HEAD, которое могло быть именно переключением, а не созданием родителя.

Создать ветку на проверенной неименованной вершине можно без изменения её объектов. Это дешёвое действие: оно добавляет стабильную стартовую точку обхода. Если же требовалось только проверить старую версию, отсоединённый режим экономит лишние временные имена. В обоих случаях нужно точно знать, должна ли созданная работа пережить последующее переключение и под каким именем её искать.

Удаление имени не равняется удалению объектов

git branch -d topic удаляет локальное имя с проверкой предусмотренного Git условия слитости. -d — обычное удаление, -D — принудительное, обходящее эту проверку. Это не команда немедленного стирания коммитов. Пока на объекты указывает другая ветка, метка, журнал ссылок или иная учитываемая точка достижимости, они могут оставаться доступными. И наоборот, удаление ветки не удаляет одноимённую ветку на сервере: пространства имён разных репозиториев независимы.

Перед удалением линия может быть проверена через git log main..topic --oneline: если есть вывод, у topic есть коммиты, недостижимые из main. Это характеристика графа. Даже если одинаковое изменение перенесено другим коммитом, идентичность объектов не появилась. Поэтому «изменения уже есть» и «ветка является предком» — разные формулировки с разными проверками.

Переименование ветки не переименовывает чужие ссылки

git branch -m old-name new-name меняет локальное имя ветки и связанные локальные настройки и журнал по правилам Git. -m означает перемещение имени, а не сообщение. Серверная old-name при этом остаётся прежней, если её отдельно не изменили. Участник с другим клоном продолжает видеть собственные локальные имена. Поэтому изменение принятой основной ветки на площадке — несколько согласованных настроек: имя ссылки, отслеживание, цель сборок и правила защиты.

Проверка слитости при branch -d относится к достижимости относительно предусмотренной опорной линии, а не к тестам программы. Ветка может содержать ненужное изменение, которое уже отменили обратным коммитом: её объекты всё ещё входят в историю. Или нужные строки могли перенести cherry-pick, так что содержимое совпадает, но родства нет. Перед удалением явно определяют критерий: сохранить все объекты линии, сохранить только итоговое поведение либо оставить удобное имя для будущей поддержки.

Worktree: вторая рабочая область с общим хранилищем

Связанное рабочее дерево, linked worktree, даёт отдельный каталог, индекс и HEAD при общем хранилище объектов и большинстве ссылок. Это удобно, когда в одном каталоге находится незаконченная работа, а в другом надо проверить выпуск. Отдельный клон тоже решает изоляцию рабочих файлов, но создаёт отдельное хранилище и собственные отслеживаемые ссылки. Worktree экономит место и делает общие ветки сразу видимыми.

git worktree add -b release-check ../release-check main
git worktree list
git -C ../release-check status --short
git worktree remove ../release-check

У worktree add флаг -b release-check создаёт новую ветку на коммите main и выбирает её в новом каталоге. list показывает зарегистрированные рабочие деревья. Параметр самого Git -C выполняет команду после перехода в указанный каталог, не меняя текущий каталог вашей оболочки. remove удаляет чистое связанное дерево и его регистрацию; при оставшихся правках команда обычно откажет. Исходное основное дерево этой командой не удаляют.

Одну ветку Git обычно не позволяет одновременно выбрать в двух рабочих деревьях: два независимых индекса не должны незаметно конкурировать за одну текущую ветку. Конфигурация по умолчанию общая, поэтому изменение локального параметра в одном каталоге может повлиять на другой. При этом незакоммиченные правки и индекс у каждого свои. Перед перемещением основного каталога или копированием worktree на флэшку нужно учитывать служебные связи путей; самостоятельный клон переносится иначе. Для чтения учебника Git вообще не нужен: готовые HTML-файлы остаются обычными файлами.

Что разделяется между рабочими деревьями

Общее хранилище содержит неизменяемые объекты, большинство ссылок и обычную конфигурацию. У каждого рабочего дерева отдельны HEAD, индекс и связанные с текущими операциями служебные состояния. Поэтому незавершённый merge в одном каталоге не должен становиться незавершённым merge другого. Но созданная там ветка видна второму, а изменение общей конфигурации может поменять поведение обоих. Команда git rev-parse --git-common-dir показывает общий служебный каталог, --git-dir — каталог текущего рабочего контекста.

Второе дерево экономит копию истории, но не отменяет затраты рабочих файлов и сборок. Если в обоих каталогах собрать многогигабайтный результат, он будет занимать место дважды, если сам инструмент сборки не использует общий кэш. Напротив, ошибочно выбранный общий выходной каталог способен смешать результаты двух ревизий. Для точного опыта каталоги входов и выходов должны соответствовать выбранной рабочей области; сам Git не отслеживает произвольный внешний кэш компилятора.

Правило «одна выбранная ветка — одно дерево» защищает от независимых индексов, каждый из которых считает себя продолжением одной ссылки. Обойти проверку принудительным флагом технически возможно в предусмотренных случаях, но это не создаёт согласование между редакторами. Если один каталог создаст коммит и сдвинет общую ссылку, другой каталог может остаться материализацией старого снимка. Локальный статус и выбранное имя станут недостаточным описанием ожиданий второго процесса.

Регистрация связанного дерева содержит пути. Если каталог временно находится на отключаемом носителе, git worktree lock --reason 'Съёмный носитель' ПУТЬ удерживает его административную запись от предусмотренной автоматической очистки. lock здесь защищает регистрацию, а не запрещает все редактирования файлов. Для перемещения используют worktree move, а для восстановления служебных связей после переноса — repair. Копирование только видимых файлов linked worktree не создаёт самостоятельный переносимый клон: внутри маленького .git остаётся указатель к общему хранилищу.

Три имени одного состояния

Создайте две ветки на текущем коммите и сделайте новый коммит только в одной. Изменится ли идентификатор второй ветки? Изменится ли её прошлое?

Разбор

Нет: вторая ссылка останется на старом объекте. Общие предки сохранятся общими. Новый коммит не дописывает данные в старый объект и не рассылается автоматически всем веткам.

Проверяемая граница изоляции выглядит так: в первом дереве измените файл без add и посмотрите индекс обоих каталогов через git -C ПУТЬ show :имя. Подготовка в первом дереве не должна заменить индекс второго. Затем создайте в первом новую ветку и проверьте git branch во втором: имя уже общее. После коммита новый объект читается из второго через git show ИДЕНТИФИКАТОР:путь, даже если его рабочие файлы не переключались. Так один маленький опыт разделяет общую базу объектов, общие ссылки, отдельную подготовку и отдельную материализацию. Увидеть новый объект и выбрать его для сборки — два последовательных решения.

К дополнительным механизмам: условная запись ссылок, общие и отдельные служебные данные.

Первоисточники: branch, switch, symbolic-ref, разделение служебных данных worktree.
