Обмен репозиториями: fetch, push и сетевой протокол

Как независимые хранилища договариваются об объектах и ссылках и что на самом деле означает origin/main

Remote — именованный набор настроек

Remote, удалённая сторона, — настройка с именем, адресом и правилами сопоставления ссылок. Имя origin условное: Git обычно создаёт его при клонировании, но это не особый центральный сервер. У репозитория могут быть разные источники чтения и отправки, несколько удалённых сторон или вообще ни одной. Сам Git распределён: каждая сторона хранит собственные объекты и ссылки. Политика «этот сервер главный» устанавливается людьми и инфраструктурой.

main — наша локальная ветка. origin/main — локальная отслеживаемая ссылка, обычно refs/remotes/origin/main, отражающая последнее полученное состояние чужой main. Она не обновляется непрерывно по сети. На сервере тем временем могла появиться новая вершина. Команда git remote -v показывает настроенные адреса чтения и отправки; -v означает подробный вывод. Наличие адреса не доказывает доступность или право записи.

Refspec связывает пространства имён

Правило ссылок, refspec, имеет базовую форму источник:назначение. Для обычного получения веток часто настроено +refs/heads/*:refs/remotes/origin/*. Слева ветки удалённого репозитория, справа наши отслеживаемые ссылки. Звёздочка сопоставляет имена. Знак плюс разрешает предусмотренное принудительное обновление отслеживаемой ссылки, например если серверную ветку переписали; он не переписывает нашу рабочую main.

git config --get-all remote.origin.fetch
git fetch origin
git log --left-right --oneline main...origin/main
git merge --ff-only origin/main

--get-all печатает все значения указанного ключа, поскольку правил может быть несколько. fetch получает нужные объекты и обновляет соответствующие ссылки, но сам по себе не сливает их в текущие рабочие файлы. merge --ff-only отдельно разрешает только продвижение по одной линии. Если обе стороны продвинулись, отказ заставляет выбрать осмысленное объединение. pull объединяет получение и последующую интеграцию по настройкам; для понимания и диагностики полезно сначала выполнить эти шаги явно.

Удалённая ветка исчезла, локальная запись осталась

git fetch --prune origin дополнительно убирает ставшие устаревшими отслеживаемые ссылки в рамках правил получения. --prune означает отсечение: оно не является удалением всех ваших локальных веток. Однако при нестандартном refspec назначения могут включать и другие пространства имён, поэтому область действия определяют по настройке, а не по одному имени флага. Удаление серверной topic и удаление нашей рабочей topic остаются разными событиями.

Клон с сокращённой историей, полученный через clone --depth=1, имеет специальную границу родителей. Часть предыдущих коммитов просто отсутствует локально. Такой клон пригоден для некоторых сборок, но запрос общего предка, поиска старого изменения или вычисления версии по меткам может дать другой результат либо потребовать углубления. Флаг --depth ограничивает глубину истории, а не число файлов в снимке. Частичное клонирование с фильтрами объектов — другой механизм: недостающие объекты могут дозагружаться позднее, что нужно учитывать при подготовке работы без интернета.

Отправка — запрос изменения чужой ссылки

git push -u origin HEAD:refs/heads/topic
git branch -vv

Здесь источник HEAD — наш выбранный коммит, назначение refs/heads/topic — ветка на сервере. Флаг -u, полная форма --set-upstream, записывает для успешно отправленной ветки настройку отслеживания. Upstream, вышестоящая линия, используется командами без явного аргумента и показом расхождения. branch -vv выводит более подробную информацию о локальных ветках, включая настройку отслеживания. Эти данные остаются локальной конфигурацией.

Обычный push отказывает, если новая серверная вершина не продолжает существующую: это проверка fast-forward для веток с обычными правилами приёма. Причиной отказа может быть и серверный запрет, обработчик проверки, отсутствие прав или невозможность записать объект. Отказ не лечат автоматически принуждением. Сначала получают серверную вершину и сравнивают линии. Получение данных не уничтожает ваши коммиты, потому что локальная ветка и отслеживаемая ссылка различаются.

Какие данные идут по проводу

При получении серверный процесс upload-pack сообщает доступные данные и согласует передачу с клиентом; при отправке серверный receive-pack принимает объекты и запросы обновления ссылок. Стороны обсуждают известные вершины и общие объекты, чтобы не передавать всю историю заново. Конкретные сообщения зависят от версии протокола и согласованных возможностей. Переносимые объекты обычно упакованы и сжаты, а не отправлены отдельным запросом на каждый файл рабочего каталога.

Управляющие сообщения используют, среди прочего, формат pkt-line: четыре ASCII-цифры шестнадцатеричной длины, затем полезные байты; длина включает сами четыре цифры. Например строка 000eversion 2\n содержит 14 байт: четыре цифры и десять байт текста с переводом строки. 0000 — специальная отметка завершения группы сообщений. В протоколе версии 2 есть и другие специальные разделители. Это прикладное обрамление Git поверх потока транспорта, а не границы TCP-пакетов. Один вызов чтения может вернуть часть строки или несколько строк сразу.

Объекты получены, но ссылка ещё не принята

Передача данных и обновление имени — разные этапы. Принимающая сторона должна иметь необходимые объекты и проверить допустимость обновления; затем она принимает либо отклоняет изменение ссылки. Если проверка запретила ветку, часть переданных байтов уже могла попасть во временное или служебное хранение. Это не означает, что новый коммит стал опубликованной вершиной. Клиенту важен результат для конкретной ссылки, а не только строка о завершении передачи процентов.

Сжатая передача также не обязана равняться размеру каталога исходников. Два снимка могут разделять почти все объекты, а упаковка использует сходство байтов. Напротив, изменение одного большого уже сжатого архива может потребовать заметного объёма. Для оценки медленного push разделяют время подготовки упаковки на клиенте, фактическую передачу и серверную проверку. Наращивание скорости сети помогает только тому этапу, который действительно упирается в неё.

Транспорт и проверка личности

Адрес по HTTPS использует HTTP с TLS; сервер может запрашивать токен или другой поддерживаемый способ авторизации. Адрес SSH сначала устанавливает сеанс SSH, проверяет сервер по его ключу и подтверждает доступ пользователя, затем запускает соответствующий процесс Git. Проверка ключа сервера и право записи в конкретную ветку — разные этапы. Пароль или токен не является частью объекта коммита: имя автора и адрес в истории не дают доступ к серверу.

Помощник учётных данных, credential helper, предоставляет и хранит данные входа согласно собственной реализации. Встраивать токен прямо в URL проекта неудобно: такой адрес может оказаться в конфигурации и диагностическом выводе. Для учебного обмена достаточно двух локальных репозиториев; там можно изучить refs и отказы без настоящих учётных данных.

Локальный сервер для опыта

git init --bare --initial-branch=main ../training-remote.git
git remote add training ../training-remote.git
git push training HEAD:refs/heads/main
git ls-remote training refs/heads/main

--bare создаёт хранилище без рабочего дерева, --initial-branch=main задаёт начальное имя ветки. remote add записывает ещё одну сторону с именем training. ls-remote читает опубликованные ссылки без обновления наших рабочих файлов. Этот опыт проверяет механику обмена и приёма; он не измеряет задержку интернета или реальные ограничения GitHub. Клонирование такого локального хранилища в третий каталог позволяет безопасно воспроизвести конкурирующие отправки двух участников.
