Слияние: общий предок, три стороны и конфликт

Как Git получает совместный снимок и почему отсутствие красных маркеров ещё не означает правильную программу

Быстрое перемещение и настоящее объединение

Пусть main указывает на A, а topic продолжает его коммитами B и C. При слиянии topic в main Git может просто передвинуть main с A на C. Это fast-forward, быстрое перемещение: отдельный объединяющий объект не нужен, потому что вся исходная история уже лежит на одной линии. Флаг --ff-only разрешает только такой случай. Если линии действительно разошлись, команда откажет, вместо того чтобы молча выбрать иной способ интеграции.

Если после A в main появился M, а в topic — T, нужны три снимка: основание A, наша сторона M и присоединяемая T. Git сравнивает A→M и A→T, затем пытается совместить изменения. Это трёхстороннее слияние, three-way merge. Вычисленное основание — не обязательно «самый старый коммит, который я помню». Сложная история может иметь несколько лучших общих предков; стратегия слияния умеет строить виртуальное основание из них.

       M ──── R   main
      /      /
     A ──── T     topic

R содержит итоговое дерево и родителей M, T.
Первый родитель — прежний HEAD принимающей стороны.

Несколько лучших оснований: перекрёстное слияние

Общий предок называется лучшим, если среди других общих предков нет его потомка, который ближе к обеим вершинам. Это не сравнение дат. В обычном ответвлении лучший предок один. Но две стороны могут независимо объединить одни и те же линии, а затем продолжить работу. Такой граф называют criss-cross merge, перекрёстным слиянием. Простая команда «возьми последнее общее по времени» больше не определяет корректное основание.

Родители заданных вершин:
A: нет
B: A                 C: A
X: B, C              Y: C, B
P: X                 Q: Y

Лучшие общие предки P и Q: B и C.
B не является предком C; C не является предком B.

Даже если X и Y содержат одинаковые деревья, это разные коммиты из-за порядка родителей или других метаданных. git merge-base --all P Q для именованных так вершин возвращает два идентификатора. Флаг --all здесь существенен: без него не нужно полагаться на случайно выбранное одно основание как на единственное. Для проверки родства разворачивают родителей, а не угадывают по двум соседним строкам log.

Стратегия ort, обычная в проверенной версии Git 2.43.0 при слиянии двух голов, строит объединённое дерево из подходящих оснований и использует его как виртуальную базу. Если B добавил b.txt, C — c.txt, их промежуточное объединение содержит оба пути. Далее сравниваются изменения от этой базы к P и Q. В собственном опыте отдельные добавления p.txt и q.txt в продолжениях успешно совместились без повторного конфликта по уже объединённым файлам.

Виртуальная база — вычислительное состояние алгоритма, а не автоматически созданная пользовательская ветка с гарантией правильности. Слияние самих оснований тоже может требовать представления конфликтов. При сложном графе важно видеть, откуда взялись сравниваемые варианты; нельзя приписать любое содержимое stage 1 одному удобному историческому коммиту. Изменения алгоритмов между версиями могут влиять на представление и разрешение трудных случаев, поэтому воспроизводимый разбор фиксирует версию Git и стратегию.

Минимальный воспроизводимый конфликт

В новом учебном репозитории сохраните port=8000 в файле service.conf. Создайте topic, замените значение на 9000 и зафиксируйте. Вернитесь в main, замените исходное значение на 8080 и зафиксируйте. Теперь один и тот же участок независимо изменён по-разному. git merge topic обычно остановится с конфликтом содержимого. Имена и значения здесь вымышленные; ни один сетевой сервис запускать не нужно.

git merge topic
git status --short
git ls-files --unmerged
git show :1:service.conf
git show :2:service.conf
git show :3:service.conf

--unmerged у ls-files показывает конфликтные записи индекса. Стадия 1 содержит основание, 2 — текущую сторону HEAD, 3 — присоединяемую. Синтаксис :2:service.conf выбирает конкретную стадию. Для удаления/добавления или других типов конфликтов какой-то стадии может не быть; «всегда три файла» — неверное обещание. В проверенном собственном опыте три стадии вернули ровно исходные байты трёх вариантов.

<<<<<<< HEAD
port=8080
=======
port=9000
>>>>>>> topic

Маркеры помещены в рабочий файл для человека. Реальные варианты хранятся в индексе отдельно, поэтому удаление маркеров не уничтожает исходные стороны. Можно выбрать одно значение или написать третье, например обоснованный параметрами системы порт. После редактирования git add -- service.conf заменяет конфликтные стадии разрешённой стадией 0 с вашим результатом. Git доверяет этому действию: он не знает, случайно ли вы сохранили оба несовместимых значения.

Показать основание прямо в конфликте

Для учебного репозитория можно задать git config merge.conflictStyle diff3. Это локальная настройка представления: при последующих конфликтах в рабочем файле дополнительно показывается участок основания под маркером |||||||. По трём вариантам легче увидеть, что именно изменила каждая сторона. Настройка не меняет родительский граф и не разрешает конфликт автоматически.

Если обе стороны заменили одинаковое исходное значение, сравнение с основанием показывает конкурирующие решения. Если одна сторона оставила исходное, а другая изменила его, выбор часто однозначен. При конфликте удаления и изменения вопрос уже иной: нужен ли путь вообще и где теперь расположен его смысл. Здесь «взять все строки слева» не отвечает на вопрос архитектуры. После разрешения просматривают целый файл и связанные места использования, а не только исчезнувшие маркеры.

Конфликт может касаться имени и существования пути

Текстовые маркеры — лишь один вид остановки. Одна сторона могла удалить файл, другая изменить его содержимое: modify/delete, изменение против удаления. Или одна переименовала файл, другая удалила: rename/delete. Или обе переименовали один исходный путь в разные назначения: rename/rename. В таких случаях сначала решают, какой путь должен существовать и какое назначение теперь несёт документ, а затем редактируют байты. В конфликте удаления отсутствующая стадия — осмысленная информация, а не нулевой файл.

В собственном опыте settings.ini был переименован в service.ini на topic и удалён на main. Слияние остановилось на rename/delete, а ls-files --unmerged показал для оставленного пути основание и присоединяемую версию без нашей stage 2: у нашей стороны файла нет. Точное размещение стадий зависит от вида конфликта и выбранного имени. Поэтому команды из опыта с тремя версиями одной строки нельзя механически применять ко всем конфликтам.

Каталоги в tree представлены вложенными объектами, но операция «переименовали каталог» не записана как отдельное событие истории. Алгоритм может вывести перемещение каталога из обнаруженных переименований его файлов и перенести добавленный другой стороной путь в подходящее место. При неоднозначном распределении файлов появляются дополнительные решения. Диагностика должна отвечать на вопрос, что произошло с конкретным исходным путём, а не только на вопрос, какие строки помечены красным.

Исследование без выбора стороны

git diff --name-only --diff-filter=U перечисляет пути с неразрешённым состоянием: --name-only оставляет имена, --diff-filter=U выбирает unmerged, то есть неслитые. Для произвольных имён добавляют предусмотренный нулевой вывод. git ls-files --unmerged раскрывает записи и стадии. Эти инструменты отвечают на структурный вопрос даже там, где рабочего файла с привычными маркерами нет.

Для ort при текстовом конфликте может существовать ссылка AUTO_MERGE на дерево первоначального рабочего результата с маркерами. git diff AUTO_MERGE помогает увидеть, что человек изменил во время разрешения. Это не готовый коммит и не замена исходных стадий; служебное состояние связано с текущей операцией и версией Git. Для чтения каждой исходной стороны по-прежнему используют индекс и его стадии.

Завершение и отмена

Проверьте подготовленный итог, выполните проверку программы и затем git merge --continue. --continue завершает остановленное слияние, создавая предусмотренный коммит. У коммита будут оба родителя. Если решение откладывается, git merge --abort пытается вернуть состояние до начала операции. Поэтому начинать сложное слияние удобнее из чистого рабочего состояния: при смешении прежних незакоммиченных правок и правок разрешения восстановить намерение существенно труднее.

git merge --no-ff topic требует отдельный коммит слияния даже там, где возможно быстрое перемещение. --no-ff фиксирует в графе событие интеграции. Оно не добавляет тестирование и не сохраняет «правильный порядок» автоматически. git merge --squash topic подготавливает объединённый файловый результат без записи связи с topic как родителем следующего коммита. Последующий обычный коммит будет иметь одного родителя; граф не будет знать, что вся боковая линия слита именно как история.

Продолжение, забывание и повторное использование решения

merge --abort пытается восстановить состояние до начала операции, merge --quit лишь забывает служебный режим, оставляя текущий индекс и рабочие файлы. После quit подготовленный результат может существовать, но обычный commit уже не обязан записать прежнюю вторую родительскую связь. Это разные исходы. Сообщение «операция больше не выполняется» ещё не доказывает возвращение исходного снимка.

Механизм rerere, reuse recorded resolution — повторное использование записанного разрешения, запоминает ранее встреченное конфликтное представление и выбранный результат. При похожем конфликте он может восстановить правку в рабочем файле. Это экономит повторное ручное редактирование, но совпадение формы конфликта не доказывает совпадение прикладного смысла. Режим без автоматической подготовки позволяет сначала прочитать восстановленное и только затем выполнить add. Повторно использованное решение тоже должно пройти проверку результата.

Структурный и смысловой конфликт

Одна сторона переименовала функцию, другая добавила её вызов в другом файле. Построчные изменения могут прекрасно объединиться, но программа перестанет запускаться. Другая сторона изменила единицы измерения тайм-аута с секунд на миллисекунды, а первая увеличила число, исходя из секунд. Файлы могут не пересекаться вообще, однако договор нарушен. Автоматическое слияние доказывает только успех выбранного алгоритма совмещения содержимого.

Обратная ситуация: обе стороны одинаково заменили строку. Это часто объединяется без конфликта, поскольку общий итог однозначен. Если одна сторона внесла изменение, а затем отменила его, сравнение конечных снимков с основанием может считать её не изменявшей строку; отдельные намерения промежуточных коммитов не превращаются в дополнительные голоса при трёхстороннем слиянии. Для понимания результата полезно смотреть A, M и T, а не считать число коммитов за каждое решение.

Проверяется именно итоговый снимок

Проверки каждой ветки по отдельности исследовали M и T, а выпуск может содержать R. Если обе ветки изменили договор разных частей системы, тесты M и T могли пройти и ничего не сказать о сочетании. Например, одна сторона обновила формат результата функции, другая добавила потребителя старого формата. Объединение не обязано конфликтовать текстово. Полезно проверить и итоговое дерево, и связи между изменёнными интерфейсами, и те требования, ради которых правка вообще делалась.

Диагностическая последовательность строится от модели: какие родители у R, какое основание использовано, какие пути изменились относительно каждого родителя, чем отличается итог от ожидаемого. git diff R^1 R показывает вклад результата относительно принимающей линии, git diff R^2 R — относительно присоединённой. Это два разных обзора одного дерева. Один короткий объединённый diff может скрыть изменения, уже присутствовавшие у одного из родителей.

Что означает «наша сторона»

При обычном merge «наша», ours, — текущий HEAD, «их», theirs, — присоединяемая вершина. Но при rebase Git временно воспроизводит ваши изменения поверх выбранного основания, и интуитивные названия сторон легко перепутать. Перед применением команды, выбирающей целую сторону, прочитайте стадии и текущий контекст. Стратегия -s ours и параметр стратегии -X ours также различаются: первая может сохранить целиком наше дерево, вторая влияет на выбор в конфликтующих участках при обычном объединении. Одинаковое слово не делает действия взаимозаменяемыми.

Два значения ours с разными последствиями

Пусть обе стороны по-разному изменили service.conf, а topic дополнительно добавила metrics.txt. git merge -s ours --no-ff topic выбирает стратегию ours: итоговое дерево совпадёт с нашим текущим деревом, включая отсутствие metrics.txt. В истории появится родительская связь с topic, хотя её содержимое не принято. Это осмысленно лишь при таком договоре интеграции; дальнейший Git будет видеть историю topic как уже включённую.

git merge -X ours topic передаёт параметр ours обычной стратегии: конфликтующие участки предпочитают нашу сторону, но неконфликтное добавление metrics.txt войдёт. Собственный опыт подтвердил оба разных результата. Для бинарного конфликтующего файла выбор относится к целому содержимому; для текстового — к конфликтующим участкам. Параметр не разрешает автоматически любой структурный конфликт переименования или существования пути. Полная стратегия и параметр стратегии относятся к разным уровням алгоритма.

При rebase текущая принимающая линия временно представляет новую базу и уже воспроизведённые изменения; переносимый старый коммит становится присоединяемым изменением. Поэтому stage 2, называемая ours, может соответствовать выбранной новой базе, а stage 3 — вашему собственному прежнему изменению. Перед restore --ours или похожим выбором смотрят show :2:путь и show :3:путь. Названия сторон относятся к текущей операции Git, а не к тому, кто лично написал строку. Это предотвращает особенно неприятную ошибку: выбрав «наше» по человеческому имени, убрать именно то изменение, которое хотели перенести.

Разрешено, но не сохранено

Вы удалили маркеры, файл запускается, но git commit сообщает о неразрешённых путях. Почему?

Разбор

Индекс ещё содержит конфликтные стадии. Нужно подготовить выбранный результат через git add -- путь, затем проверить и завершить слияние. Отсутствие маркеров в рабочем файле не заменяет обновление индекса.

К дополнительным механизмам: стратегии и их параметры, повтор разрешения, AUTO_MERGE.
