Проверки, отчёты и артефакты: как не получить ложный зелёный запуск

Успешный конвейер должен подтверждать определённые свойства продукта. Разделим проверки по наблюдаемому поведению, сохраним смысл ошибок через оболочку и разберём, почему файл отчёта не равен выполненному тесту.

Каждая проверка отвечает на определённый вопрос

Проверка синтаксиса устанавливает, что инструмент смог разобрать программу. Модульный тест исследует небольшую часть логики в выбранных условиях. Интеграционный тест проверяет совместную работу компонентов: например, приложение действительно подключилось к тестовой базе и выполнило запрос. Проверка упаковки исследует полученный файл, а проверка запуска из пакета — возможность воспользоваться доставляемым содержимым. Эти уровни дополняют друг друга, потому что наблюдают разные границы.

Можно успешно протестировать исходный каталог и забыть положить в архив шаблон ответа. Можно получить корректный ZIP с программой, которая использует отсутствующую системную библиотеку. Можно проверить HTTP-код 200 и не заметить неверный результат расчёта в теле. Поэтому формулируют конкретное утверждение: какой вход подаётся, какое наблюдение ожидается, что завершает действие ошибкой. Количество тестов само по себе не описывает силу этих утверждений.

Для небольшой Python-службы полезна короткая цепочка: тесты логики; проверка состава и целостности архива; распаковка в новый временный каталог; запуск оттуда с тестовой конфигурацией; запрос к локальному адресу и проверка ответа; гарантированное завершение дочернего процесса. Последний шаг важен: забытые процессы занимают порты, и следующий запуск может проверить старую программу. Тестовая база, если она нужна, получает отдельное имя и предсказуемую очистку.

Три канала результата

Автоматизация получает код завершения, машинный отчёт и человекочитаемый журнал. Код сообщает общий успех действия. Отчёт позволяет показать, какие проверки выполнялись и как менялись их длительности. Журнал объясняет причину. Если код нулевой, но обязательный отчёт отсутствует, это может означать, что тесты вообще не стартовали. Если отчёт есть, но принадлежит прошлому запуску, интерфейс покажет красивую чужую историю. Поэтому отчёты создают заново в известном каталоге и связывают с текущим запуском.

JUnit XML — распространённый формат обмена сведениями о тестах. Слово JUnit в имени не требует, чтобы приложение было написано на Java. Один производитель отчёта записывает XML, другой инструмент читает случаи, длительности и ошибки. У разных производителей есть расширения и различия, поэтому совместимость проверяют на реальном парсере. Стандартный unittest Python сам по себе не превращает обычный подробный вывод в JUnit XML; для этого нужен явно выбранный производитель отчёта.

<testsuite name="demo" tests="2" failures="1" errors="0" skipped="0">
  <testcase classname="test_app.Response" name="test_health" time="0.003" />
  <testcase classname="test_app.Response" name="test_total" time="0.002">
    <failure message="expected 12, received 11">Проверка суммы не прошла</failure>
  </testcase>
</testsuite>

Это иллюстрация контракта, а не настоящий отчёт выполненных здесь тестов. testcase описывает отдельный случай; failure — несоответствие ожиданию; errors обычно отделяют от таких несоответствий, но точное сопоставление задаёт производитель. XML должен быть корректно экранирован: сырые символы из исключения могут сломать отчёт. Число в атрибуте tests нельзя считать доказательством исполнения без доверия к производителю и проверки целостности процесса.

Как Jenkins читает отчёт

При установленном JUnit plugin шаг junit testResults: 'reports/*.xml', allowEmptyResults: false читает совпавшие отчёты из workspace. Маска должна выбирать именно XML данного формата, а не все файлы проекта. Запрет пустого результата помогает заметить неверный путь и ситуацию, когда тестовая программа не создала отчёт. Обнаруженные неуспешные тесты могут дать состояние UNSTABLE; это требует явной политики допуска выпуска. UNSTABLE не следует автоматически трактовать как «всё нормально».

Шаг публикации отчёта удобно выполнять в завершающем блоке, чтобы детали сохранились и при неуспехе тестовой команды. Но основное решение об ошибке нельзя потерять: неудачные тесты и ошибка публикации отчёта — разные события. Для самого простого конвейера предыдущей главы достаточно честного ненулевого завершения unittest и журнала. Добавлять JUnit стоит, когда нужны история случаев и удобная навигация, вместе с настоящим поддерживаемым генератором, а не фиктивным XML с заранее проставленным успехом.

Оболочка умеет скрывать ошибку

python3 -m unittest discover -s tests -v 2>&1 | tee tests.log

Такая запись выглядит удобной: 2>&1 направляет поток ошибок туда же, куда направлен обычный вывод; | передаёт объединённый поток в tee; tee копирует его на экран и в файл. Но в обычной POSIX-оболочке код конвейера определяется последней командой. Тесты могут завершиться ошибкой, а tee успешно запишет журнал и вернёт ноль. Jenkins увидит успех, если автор не сохранил нужный статус.

В простом случае уберите трубу и используйте уже имеющийся журнал Jenkins. Если копия обязательна и на агенте есть Bash, можно явно выбрать его и включить соответствующее поведение:

sh '''#!/usr/bin/env bash
set -euo pipefail
python3 -m unittest discover -s tests -v 2>&1 | tee tests.log
'''

Строка выбора интерпретатора должна идти первой, без предшествующей пустой строки. -e завершает сценарий при ряде необработанных ошибок; у него есть исключения по синтаксическому контексту, поэтому это не универсальное доказательство. -u считает обращение к незаданной переменной ошибкой. -o pipefail меняет код конвейера: ненулевой статус участника больше не теряется за успешным tee. Это возможность Bash; нельзя без проверки переносить её в любой /bin/sh. Флаг -v выше принадлежит unittest, а не Bash.

Отделяем сохранённый продукт от ускорителя

Кэш позволяет восстановить вычислимые промежуточные результаты. Артефакт выпуска — конкретные утверждённые байты, на которые ссылаются доставка и восстановление. Сроки хранения отличаются: кэш удаляют ради места, выпуск сохраняют по принятой политике поддержки. Отчёт тестов тоже артефакт запуска, но он не заменяет сам пакет. В описании выпуска нужно знать, где находятся оба и какой пакет проверялся.

Сохраняйте разумный минимальный комплект: доставляемый файл, его SHA-256, идентичность исходников и зависимостей, описание конфигурации сборки, результаты обязательных проверок. Диагностические журналы могут иметь иной срок хранения и более узкий доступ. Не архивируйте весь workspace автоматически: там бывают токены, локальные ключи, временные данные и огромные кэши. Явный список файлов понятнее и уменьшает риск случайной публикации.

Наконец, проверьте сам механизм отказа. Измените ожидаемый результат одного учебного теста и убедитесь, что конвейер не допускает выпуск. Уберите обязательный файл из упаковки и убедитесь, что проверка пакета это замечает. Такой опыт показывает, что барьер действительно работает. Он ценнее ещё одного повторения неизменного успешного запуска, которое только подтверждает уже известный счастливый путь.

Первичные источники

Jenkins JUnit plugin: чтение результатов и пустые отчёты; Jenkins sh: ошибка шага и returnStatus; Bash: коды завершения конвейеров и pipefail; Python unittest: исполнитель тестов. Пример XML описывает формат данных, не выдаёт искусственно созданный файл за выполненную проверку.
