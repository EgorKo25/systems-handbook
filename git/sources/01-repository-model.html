Репозиторий: что именно сохраняет Git

От обычного каталога к трём независимым состояниям, снимку и проверяемой истории

В первом входе мы уже получили три фиксации одного message.txt и увидели, как различаются рабочее редактирование, подготовка и записанное состояние. Сохранённая папка git-first-steps-lab остаётся вашим основным примером. Здесь уточним эту модель, а для короткой проверяемой ситуации создадим отдельную папку с note.txt; её данные не заменяют и не сбрасывают первое упражнение.

Сохранённый файл и сохранённое состояние проекта

Пусть приложение состоит из программы, конфигурации и описания запуска. Вчера программа читала параметр port, сегодня — listen_port. Если вернуть только программу, оставив сегодняшнюю конфигурацию, получим сочетание, которого разработчик никогда не проверял. Система управления версиями связывает файлы в состояния проекта и объясняет отношения между состояниями. Git хранит снимки — логически полные наборы путей, содержимого и поддерживаемых режимов файлов. Физически одинаковые данные переиспользуются, поэтому полный снимок не означает полную копию всех байтов на каждый шаг.

Репозиторий — хранилище объектов и именованных ссылок на них. Рабочий каталог — обычные файлы, которые редактируют программы. Это разные сущности: рабочие файлы можно удалить, оставив сохранённую историю; можно иметь репозиторий без рабочих файлов. Такой репозиторий называют bare, «голым»: он удобен как принимающая сторона обмена. Клон — самостоятельный репозиторий с полученной историей, а не сетевое окно в чужую папку. Сохранение коммита обычно не требует интернета, отправка на сервер выполняется отдельно.

Что является единицей согласованности

В каталоге могут лежать server.py, config.ini, requirements.txt и описание запуска. Состояние проекта — соответствие каждому сохраняемому пути его содержимого и режима. Если программа переименовала настройку, согласованное изменение включает программу и пример конфигурации. Если появилась зависимость, оно включает и описание зависимости. Git способен сохранить любое сочетание, в том числе заведомо неработающее. Слово «снимок» говорит о форме записи данных, а не о логической согласованности программы.

Представьте, что в коммит попал новый server.py, а подготовленный config.ini остался старым. В хранилище не возникло повреждения: оно корректно сохранило именно выбранный набор. Ошибка находится на уровне состава изменения. Проверка контрольных сумм здесь бесполезна для поиска неправильного имени параметра: суммы подтвердят сохранность неверного сочетания. Нужно сопоставить поведение программы с конфигурацией и проверить выбранный снимок целиком.

Отсюда различают целостность представления и корректность результата. Целостность означает, что объекты читаются, ссылки ведут к существующим данным, а вычисленные идентификаторы соответствуют байтам. Корректность означает выполнение требований задачи. Восстановимость дополнительно требует доступной копии нужных объектов. Даже идеальная локальная история не помогает после физической потери единственного носителя. Эти свойства проверяются разными действиями; одна команда не превращает их в одно обещание.

Три области одного изменения

Рабочее дерево, working tree, содержит текущие файлы на диске. Индекс, index, хранит подготовленный вариант следующего снимка. Текущий коммит, достигаемый через HEAD, задаёт последний выбранный снимок истории. Commit переводится как фиксация: это объект с корневым деревом, родителями, авторскими данными и сообщением. Индекс часто называют staging area, областью подготовки. Это не очередь имён «когда-нибудь сохранить эти файлы»: после добавления в ней уже указан конкретный вариант содержимого.

После редактирования: HEAD = A, индекс = A, рабочий файл = B
После git add:      HEAD = A, индекс = B, рабочий файл = B
После новой правки: HEAD = A, индекс = B, рабочий файл = C
После git commit:   HEAD = B, индекс = B, рабочий файл = C

Буквы здесь обозначают содержимое одного пути, а не имена объектов. Последняя строка объясняет частую неожиданность: успешный коммит не обещает чистый рабочий каталог. Git мог сохранить подготовленную версию B, а более поздняя правка C осталась незаписанной. Это позволяет разделить исправление ошибки и незаконченную переработку, даже когда обе правки затрагивают один файл. Ответственность за осмысленный снимок лежит на том, кто выбирает его содержимое.

Почему снимок не является фотографией каталога в одну наносекунду

Когда add обходит несколько файлов, чтения происходят последовательно или в рамках конкретного алгоритма обхода, а не как атомарная транзакция всей файловой системы. Другая программа может менять файлы между чтениями. Например, генератор записал новую таблицу в data.csv, но ещё не обновил её описание. Если в этот момент подготавливать оба пути, можно захватить промежуточное сочетание. Сам Git не знает, что два файла составляют единый прикладной документ.

Чтобы исследовать такой отказ, сначала отделяют неизменяемые входы от изменяемых результатов. Останавливают соответствующий генератор либо получают его завершённый выход в отдельном каталоге. Затем подготавливают конкретные пути и читают индекс, а не доверяют виду редактора. В сервисе с большой базой данных обычный git add файлов базы вообще не является протоколом согласованной резервной копии: её механизмы фиксации и восстановления имеют собственный договор.

Индекс полезен именно как самостоятельная выбранная версия, однако он изменяем. Два последовательных add могут заменить запись одного пути более поздним вариантом. Подготовленные байты не становятся неизменяемым выпуском, пока не создан и не выбран соответствующий коммит. Если после чтения diff помощник редактора автоматически дописал файл и повторно выполнил add, проверяли вы уже другой индекс. Для строгой проверки фиксируют идентификатор созданного коммита и строят результат из него.

Отдельный проверочный опыт трёх состояний

Для этого опыта сначала перейдите из git-first-steps-lab в родительскую учебную папку. Новый git-snapshot-lab создаётся рядом, а не внутри уже существующего репозитория. Первый проект с message.txt сохраняется без изменений. Если имя новой папки занято, выберите другое; не выполняйте опыт внутри рабочего проекта. mkdir и cd создают каталог и переходят в него. Флаг -b main у git init задаёт имя начальной ветки. Изначально она ещё не указывает на коммит: первый объект фиксации в этой отдельной истории пока не создан.

mkdir git-snapshot-lab
cd git-snapshot-lab
git init -b main
git config user.name 'Учебный читатель'
git config user.email reader@example.invalid
printf 'first\n' > note.txt
git add -- note.txt
git commit -m 'Сохранить первую версию'

git config без --global меняет конфигурацию этого репозитория. Имя и адрес записываются в метаданные будущих коммитов; они не являются входом в сервер и не проверяют личность. Домен example.invalid выбран для вымышленных примеров. printf записывает пять букв и перевод строки, а оболочка направляет вывод в файл. Разделитель -- завершает параметры Git: следующий аргумент рассматривается как путь. Флаг -m передаёт сообщение коммита непосредственно, без открытия редактора.

printf 'staged\n' > note.txt
git add -- note.txt
printf 'worktree\n' > note.txt
git status --short
# MM note.txt
git show :note.txt
# staged
git diff -- note.txt
git diff --cached -- note.txt

--short включает краткий статус с двумя колонками. Первая буква M, от modified — изменён, описывает индекс относительно текущего коммита. Вторая описывает рабочее дерево относительно индекса. Поэтому MM — два разных сравнения одного пути. Запись :note.txt в git show обращается к подготовленному содержимому. Обычный diff показывает переход из индекса к рабочему файлу; --cached переключает сравнение на переход из текущего коммита к индексу. Слово diff означает различие, а не ещё одну область хранения.

Проследить один путь из трёх источников

git show HEAD:note.txt
git show :note.txt
cat note.txt
git diff --cached -- note.txt
git diff -- note.txt

Первое чтение обходит текущий коммит и его дерево. Второе берёт объект, указанный записью индекса. Третье — обычное чтение операционной системы из рабочего каталога; Git в нём не участвует. Последние два вызова вычисляют различия выбранных пар. Если редактор показывает C, это доказывает лишь наличие C в его представлении файла; индекс мог сохранить B, а HEAD — A. В недоумённой ситуации полезно сначала получить эти три значения, а уже потом выбирать отмену или повторное добавление.

У git commit -a -m 'Сообщение' флаг -a автоматически подготавливает изменения и удаления уже отслеживаемых путей перед фиксацией. Он не означает «все существующие новые файлы». Если рядом создан helper.py, который ещё не отслеживался, программа может работать в вашем каталоге благодаря ему, но коммит его не получит. Обычный commit без -a, напротив, опирается на заранее подготовленное. Выбор удобного сокращения должен соответствовать модели, а не подменять её.

Что находится в .git

В простом репозитории .git — каталог. В нём находятся объекты, ссылки, конфигурация, индекс и журналы перемещения ссылок. Но в связанном рабочем дереве .git может быть маленьким текстовым файлом, указывающим на служебный каталог в другом месте. Поэтому инструменты узнают расположение через Git, а не конструируют пути вручную. git rev-parse --git-dir показывает служебный каталог; git rev-parse --show-toplevel — верх рабочего дерева. Обе команды лишь печатают сведения. rev-parse — историческое имя команды разбора обозначений ревизий, то есть версий.

Индекс не хранится в каждом коммите и не отправляется коллеге как ваша незавершённая подготовка. Конфигурация репозитория тоже не превращается автоматически в проектный файл. Файл .gitignore, напротив, обычный отслеживаемый документ, если его добавили. В дальнейшем это различие объяснит, почему одинаковая история может давать разное рабочее поведение при разных локальных настройках.

Как команда выбирает репозиторий и настройки

Обычно Git ищет служебный каталог, поднимаясь от текущего рабочего каталога к родителям. Поэтому команда из вложенной папки относится к тому же проекту, но некоторые пути и режимы обхода интерпретируются с учётом текущего места. Параметр git -C каталог status сначала выбирает рабочий каталог для команды. Переменные окружения вроде GIT_DIR, GIT_WORK_TREE и GIT_INDEX_FILE способны переопределить служебный каталог, рабочие файлы и индекс. Это полезно для низкоуровневых инструментов, но объясняет ситуацию «я смотрю не тот индекс».

git config --show-origin --show-scope --list показывает значения, их источник и область действия. --list перечисляет параметры, --show-origin добавляет файл или иной источник, --show-scope — уровень настройки: системный, пользовательский, репозиторий, рабочее дерево либо командный. Одно имя параметра может встречаться несколько раз; приоритет и допустимость нескольких значений зависят от параметра. Поэтому читать только .git/config недостаточно, если преобразование строк или выбор редактора задаёт пользовательская конфигурация.

Настройки не являются скрытыми коммитами. Если включить core.autocrlf, а затем передать коллеге только историю проекта, эта личная настройка сама не переедет. Если проект требует конкретного преобразования путей, его описывают подходящими отслеживаемыми атрибутами и проверяют результат. Если команда запущена автоматизацией, учитывают и переданные ей аргументы -c имя=значение: такой параметр действует для данного запуска, не обязательно записываясь в файл конфигурации.

Граница снимка

Обычный Git сохраняет байты файлов, имена путей, различие обычного файла и символической ссылки, а для обычных файлов — признак исполняемости. Он не является резервной копией всех свойств файловой системы: времена изменения, владелец, произвольные права, расширенные атрибуты и пустые каталоги не восстанавливаются как часть обычного дерева Git. Содержимое подмодуля представлено ссылкой на определённый коммит другого репозитория, а не всеми его файлами внутри родительского дерева. Поэтому фраза «всё лежит в Git» нуждается в проверке: входные данные сборки, внешние пакеты и секреты могут находиться за пределами снимка.

Снимок пригоден для воспроизводимой работы, если известны также условия интерпретации: версия компилятора, зависимости, настройки преобразования файлов и команда сборки. Git отвечает на вопрос «какие записанные данные выбраны», но результат запуска зависит ещё от окружающей системы. В следующих главах разберём, как проверить саму запись, а затем свяжем её с изготовлением программного артефакта.

Где проходит граница успешной фиксации

Создание коммита требует прочитать индекс, иметь доступные объекты содержимого, записать новые объекты и изменить ссылку. Дополнительно могут запускаться настроенные обработчики — hooks, программы, вызываемые в определённые моменты. Обработчик проверки сообщения может отказать; запись объекта может столкнуться с заполненным диском; обновление ссылки может встретить параллельное изменение. Поэтому после ошибки не делают вывод «ничего нигде не появилось»: данные могли быть записаны до отказа последнего этапа.

Наблюдаемая проверка — код завершения команды, выбранная вершина через git rev-parse HEAD и статус трёх областей. Существование свежего объекта само по себе ещё не означает, что ветка на него перемещена. И наоборот, успешный коммит не запускает отправку на сервер, сборку или тесты по общему правилу Git. Такие дополнительные действия появляются только через явно настроенный процесс. Это позволяет разбирать сбой по этапам: что уже записано, какой указатель изменён, что осталось лишь рабочими байтами.

В обычном процессе новый объект доступен по своему имени после записи, а имя ветки обновляется отдельно с проверкой ожидаемого прежнего состояния. Долговечность при внезапном отключении питания зависит также от настроек синхронизации и файловой системы. Успешный выход пользовательской команды нельзя без дополнительного договора превращать в обещание, что любые подтверждённые байты выдержат любой отказ носителя. Для исследования такого свойства нужен отдельный отказный опыт; в этом томе мы проверяем логические состояния и чтение объектов после обычного завершения.
