33. Расследование: пропавший коммит, повреждённый объект и медленная команда

Диагностика Git начинается с разделения наблюдений. Исчезнувшая ссылка, нечитаемый объект и долгое чтение рабочего каталога требуют разных доказательств. Пройдём маршрут от сохранения исходного состояния до проверяемого восстановления и измерения затрат.

Не превращать наблюдение в преждевременный вывод

Пользователь сообщает: «После переключения ветки пропал файл, а status стал работать медленно». Здесь пока нет доказательства ни потери данных, ни повреждения базы, ни нехватки процессора. Файл мог принадлежать другой ветке, оставаться незаписанным, скрываться разреженным рабочим деревом или храниться во вложенном проекте. Задержка может быть связана с количеством файлов, внешним фильтром, файловой системой либо вложенными проверками. Одновременность событий не устанавливает общую причину.

Первое действие — записать наблюдаемый результат, выполненную перед ним команду, выбранный каталог и версию Git. До чистки и переупаковки следует сохранить самостоятельную копию важных данных, включая незаписанные файлы. Обычный clone не является резервированием рабочего каталога, а bundle не захватывает все локальные недостижимые объекты. При расследовании потенциальной потери эти ограничения особенно существенны.

git --version
git rev-parse --show-toplevel
git rev-parse --git-dir
git rev-parse --git-common-dir
git status --porcelain=v1
git branch --show-current
git log -5 --oneline --decorate

Корень рабочего дерева помогает исключить ошибочный каталог. Различие git-dir и общего каталога важно для дополнительных рабочих деревьев. Пустое имя текущей ветки может означать отделённый HEAD; это допустимое состояние, но новые коммиты в нём легко потерять из виду. Машинный status показывает отличие рабочей копии и индекса, короткий журнал — достижимую от текущего положения историю.

Собственный опыт с исчезнувшей вершиной

Создайте отдельный учебный репозиторий с двумя коммитами: первый содержит строку one, второй — two. Сохраните полные идентификаторы вне рабочего дерева. В этой одноразовой копии верните main на первый коммит через reset --hard. Эта команда действительно заменяет индекс и рабочие файлы выбранным снимком; её нельзя переносить в случайный личный каталог. Для понимания механизма достаточно специально подготовленного стенда.

git reflog --date=iso --format='%H %gd %gs'
git show --stat HEAD@{1}
git fsck --unreachable --no-reflogs

В исполненном опыте второй идентификатор исчез из обычного журнала main, но остался в reflog и среди объектов, которые fsck показал недостижимыми без учёта reflog. Это разные представления одной ситуации: ссылка уже не ведёт к вершине, однако её объект пока существует. В журнале reflog найдите запись по полному идентификатору и смыслу операции. Номер HEAD@{1} здесь лишь удобство сразу после опыта; последующие команды и переходы могут изменить соответствие номеров.

Для восстановления сначала создайте новую ветку rescue от найденного полного идентификатора, затем изучите её дерево и родителей. Создание ссылки закрепит нужную историю, не перезаписывая текущее рабочее дерево. Лишь после проверки выбирайте, нужно ли переключиться на rescue, перенести отдельное изменение или восстановить файл. Сохранение новой ветки позволяет отделить обнаружение данных от решения, как встроить их обратно.

git branch rescue FOUND_COMMIT
git log --oneline --graph rescue
git diff main rescue --
git show rescue:a

FOUND_COMMIT здесь заменяют проверенным полным идентификатором найденного коммита. Команда branch создаёт имя, log показывает историю, diff сравнивает снимки, show читает нужный файл. Перед действием нужно предсказать, какой вывод подтвердит гипотезу: в нашем случае rescue:a содержит two, а main:a — one. Случайное совпадение имени файла ещё не доказывает, что найдена вся нужная работа.

Что именно проверяет fsck

fsck исследует связность и корректность хранимых объектов. Недостижимый объект может быть совершенно исправен: ни одна выбранная корневая ссылка просто не приводит к нему. Термин dangling относится к объекту, который непосредственно не используется другим рассматриваемым объектом; его не нужно автоматически переводить как «повреждённый». Повреждение — отдельное наблюдение о невозможности корректно прочитать данные или согласовать ссылки.

Опция --unreachable просит вывести недостижимые объекты. Опция --no-reflogs исключает журналы перемещений ссылок из корней обхода; именно поэтому ещё упомянутый журналом коммит появляется в нашем опыте. Она не стирает reflog. Вариант --full проверяет также упакованное хранение и доступные альтернативные пулы; в обычной современной установке такой полный охват уже является стандартным.

Режим --connectivity-only сокращает работу, проверяя прежде всего наличие нужных связей. Он не заменяет чтение и проверку содержимого blob-объектов. Поэтому успешная ускоренная проверка не доказывает, что каждый байт каждого файла исправен. При выборе режима сформулируйте, какое утверждение требуется получить, и оценивайте стоимость именно соответствующей проверки.

Если нужного объекта уже нет, reflog не восстановит его байты из одного имени. Возможными источниками становятся другие клоны, резервные копии и сохранённые артефакты, причём состав каждого источника проверяют. До завершения поиска не следует запускать prune или уменьшать сроки хранения журналов: удаление оставшихся кандидатов ухудшит исходные условия расследования.

Контролируемое повреждение только в одноразовой копии

В автоматическом опыте созданный учебный blob существовал отдельным свободным объектом. Его сжатые байты были сохранены в памяти проверки, затем файл объекта временно заменялся заведомо неверными данными. После этого fsck --full завершался ошибкой. Возврат исходных байтов восстанавливал успешную проверку. Ни один объект настоящего проекта не изменялся.

Этот опыт показывает причинную связь между повреждённым хранилищем и диагностикой. Он не предлагает вручную исправлять неизвестные файлы в .git. В реальном репозитории объект может находиться внутри pack-файла, использоваться несколькими ссылками или читаться из альтернативного пула. Предполагаемое «исправление» переименованием под другой идентификатор уничтожает смысл проверки содержимого. Для восстановления нужна достоверная копия именно требуемых байтов либо корректный источник объектов.

Отсутствие части объектов бывает предусмотрено форматом работы. Частичная копия может иметь обещанные сервером blob-объекты, получаемые по запросу; поверхностная копия имеет известную границу предков. Поэтому перед выводом о повреждении посмотрите параметры promisor и shallow-состояние. Если обещанный объект не получается из-за недоступной сети, это ещё один самостоятельный отказ, отличный от повреждения имеющегося файла.

Разложить медленный status на проверяемые составляющие

status сравнивает индекс, снимок и рабочие файлы, а также может перечислять неотслеживаемые пути и учитывать вложенные проекты. Сотни тысяч генерируемых файлов способны сделать обход дороже чтения небольшой истории. Медленный накопитель, проверка файлов защитным программным обеспечением, сетевой каталог и холодный файловый кэш меняют стоимость одинаковых вызовов. Поэтому число коммитов само по себе слабо объясняет задержку status.

git status --porcelain=v1
git status --porcelain=v1 --untracked-files=no
git count-objects -vH

Второй status исключает перечисление неотслеживаемых файлов. Если он заметно быстрее, появляется конкретная гипотеза о дорогом обходе; семантика ответа при этом изменилась, поэтому такая команда не является полной заменой обычного status. count-objects характеризует базу объектов. Маленький pack не опровергает дорогую проверку рабочего дерева, потому что эти команды измеряют разные части проекта.

Для измерения используйте несколько повторов на одном состоянии. Первый запуск часто отличается из-за кэшей. Запишите отдельные результаты, медиану и, если выборка достаточно большая, верхние квантили, отражающие редкие задержки. Укажите накопитель, версию, число файлов, выбранные параметры и фоновые операции. Универсального порога «пять секунд означает нужен новый сервер» не существует: решение зависит от частоты вызовов, ожиданий пользователя и найденной причины.

Trace2: где процесс потратил время

Trace2 — механизм событий внутреннего выполнения Git. Для конкретной команды можно записать события JSON в новый файл вне репозитория. Следующий вариант подходит оболочке Bash; назначение переменной действует только для одного вызова. На Windows командная оболочка задаёт переменные иначе, поэтому этот синтаксис нельзя выдавать за проверенный универсальный.

GIT_TRACE2_EVENT="$PWD/../status-trace.json" git status --porcelain=v1

В нашем исполненном опыте файл содержал события начала и завершения. Возможны также записи областей выполнения и дочерних процессов. Сначала сгруппируйте события по идентификатору сеанса, затем сопоставьте начало, завершение и вложенность. Вложенные интервалы перекрываются: простое суммирование всех длительностей может дать число больше полного времени процесса. Сравнивать разные прогоны следует при одинаковом вопросе и одинаковом уровне детализации.

Если журнал показывает длительный дочерний процесс, проверьте его назначение: это может быть внешний помощник, фильтр или вложенная команда. Если основная задержка связана с обходом файлов, сначала измените воспроизводимый фактор количества путей. Не включайте все ускорители одновременно: тогда после улучшения невозможно установить причину. Выберите одно изменение, повторите измерение и проверьте, что результат команды сохранил требуемый смысл.

Журнал обмена: что он показывает и чего в нём нет

GIT_TRACE_PACKET записывает сообщения протокола Git. В проверке он включался только при fetch между специально созданными соседними репозиториями; журнал действительно содержал строки packet. Работа с bundle не воспроизводит обычный обмен клиента и сервера, поэтому отсутствие таких строк при чтении bundle не доказывает поломку трассировки. Название packet здесь относится к обрамлению протокольных сообщений Git, а не к IP-пакетам сетевого интерфейса.

Для реального сетевого случая отдельно рассматривают разрешение имени, установление транспорта, аутентификацию, объявление ссылок, согласование объектов и передачу pack. Если задержка произошла до начала протокола Git, его журнал не объяснит всю предшествующую работу. Если передача завершилась, а checkout долго материализует файлы или фильтры, проблема тоже может находиться за пределами собственно обмена.

Диагностические журналы способны содержать пути, аргументы, имена ссылок, идентификаторы и сообщения. Поэтому учебная проверка не обращается к рабочим адресам и не публикует необработанный журнал. Для обращения за помощью оставляют минимальный очищенный фрагмент с нужными событиями. Нельзя считать любой файл trace автоматически безопасным только потому, что он создан средством диагностики. Дополнительную HTTP-трассировку включают лишь при отдельном понимании её состава и обращения с данными.

Закрытие расследования

Хороший итог связывает симптом, наблюдение, проверенную причину и ограниченное действие. Для пропавшего коммита это найденный полный идентификатор, созданная rescue и проверенные файлы. Для повреждения — подтверждённая ошибка чтения и восстановленные из достоверного источника байты. Для задержки — сопоставимые прогоны и изменение, которое уменьшило конкретную стоимость без потери нужной проверки.

Практическое продолжение: выполните эти три сценария раздельно и составьте для каждого короткий протокол с исходным предположением и опровергающим его опытом. Затем соедините два симптома в одном стенде и объясните, какие наблюдения по-прежнему независимы. Это развивает навык расследования лучше, чем запоминание универсальной команды очистки. Реальные SSH/HTTP-серверы и Windows в данной серии опытов не исполнялись; измерения здесь подтверждают механизм, а не обещают производительность чужой машины.

Источники: журналы ссылок, проверка объектов fsck, состав работы status, события Trace2, переменные трассировки Git, официальная книга о восстановлении.
