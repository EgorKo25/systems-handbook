Индекс: подготовка снимка и проверка файлов

Почему add сохраняет конкретное содержимое, status бывает дорогим, а одинаковое время изменения ещё ничего не доказывает

Индекс как таблица будущего дерева

В обычном состоянии индекс содержит запись для каждого отслеживаемого пути: режим, идентификатор blob, имя и служебные признаки. Записи отсортированы по байтам пути; это помогает находить файл и строить деревья каталогов. В отличие от готового дерева индекс дополнительно держит сведения файловой системы, чтобы не перечитывать каждый файл при каждой проверке. Неподготовленный новый файл отсутствует в индексе; удалённый с диска отслеживаемый файл может оставаться в нём, пока удаление не подготовлено.

Посмотреть логическое содержимое можно командой git ls-files --stage. Флаг --stage добавляет к именам режим, идентификатор и номер стадии. У разрешённого пути стадия равна нулю. При конфликте один путь может иметь записи стадий 1, 2 и 3: это специальные варианты общего предка и двух сторон, а не три версии «на потом». С ними подробно разберёмся при слиянии. Файл индекса имеет собственный бинарный формат; правка его текстовым редактором не является способом подготовки снимка.

Заголовок DIRC: двенадцать байтов перед записями

Для формата индекса версии 2 в SHA-1-репозитории первые четыре байта — ASCII DIRC, сокращение исторического directory cache, кэша каталогов. Затем два четырёхбайтовых целых: версия и количество записей. Числа хранятся старшим байтом вперёд, как принято в сетевом порядке. Для единственной записи заголовок имеет вид 44 49 52 43 00 00 00 02 00 00 00 01. Это не содержимое tree: индекс нужен для подготовки и проверки рабочего дерева, а tree — неизменяемая сохранённая таблица имён.

В Git 2.43.0 поддерживаются версии индекса 2, 3 и 4. Версия 3 допускает расширенные флаги; версия 4 сжимает повторяющиеся префиксы путей и иначе оформляет их длины, без прежнего выравнивания записей. Поэтому нельзя написать разбор «пропусти 62 байта и найди нуль» и считать его универсальным для любого индекса. Нужны версия, выбранная хеш-функция и поддержка обязательных расширений. Низкоуровневый разбор ниже намеренно ограничен одной простой записью версии 2.

Одна запись по смещениям

Перед именем находятся десять четырёхбайтовых полей: секунды и наносекунды ctime, то же для mtime, идентификаторы устройства и inode, режим, uid, gid и размер. Inode — номер файлового объекта внутри файловой системы; uid и gid — числовые владельцы. Далее в SHA-1-репозитории идут 20 байт имени blob и два байта флагов. Итого 62 байта фиксированной части. После имени и завершающего нуля запись версии 2 дополняется нулями до границы восьми байтов.

Индекс с одним hello.txt имеет девять байт имени: 62 + 9 + 1 = 72 байта записи. Вместе с заголовком 12 и заключительной контрольной суммой 20 это 104 байта, если расширений нет. Дополнительная запись дерева-кэша может увеличить файл после последующих операций, поэтому 104 — результат конкретного ограниченного опыта, а не универсальный размер индекса с одним файлом.

git update-index --index-version=2
python3 - <<'PY'
import hashlib, pathlib, struct, subprocess
name = subprocess.check_output(
    ['git', 'rev-parse', '--git-path', 'index'], text=True).strip()
data = pathlib.Path(name).read_bytes()
signature, version, count = struct.unpack('>4sII', data[:12])
print(signature, version, count)
assert signature == b'DIRC' and version == 2 and count == 1
mode = struct.unpack('>I', data[12 + 24:12 + 28])[0]
oid = data[12 + 40:12 + 60].hex()
flags = struct.unpack('>H', data[12 + 60:12 + 62])[0]
print(oct(mode), oid, 'stage=', (flags >> 12) & 3)
print(data[12 + 62:data.index(b'\0', 12 + 62)])
print('checksum=', hashlib.sha1(data[:-20]).digest() == data[-20:])
PY

Выполняйте это только после опыта с одним файлом из главы об объектах. --index-version=2 у update-index задаёт формат служебной записи, не переписывая коммиты. --git-path index получает правильный путь даже при особом расположении служебных данных. В Python префикс > задаёт старший байт первым, I — 32-битное беззнаковое число, H — 16-битное. Последнее сравнение вычисляет хеш всех байтов до хвостовой суммы. Эти проверки обнаруживают неверное чтение или повреждение, но не доказывают соответствие рабочего файла индексу.

В двухбайтовых флагах два бита стадии выбирают значения 0–3, нижние двенадцать обычно задают длину пути до предельного обозначения 0xfff, старшие служат другим признакам. Длина не заменяет нулевое завершение и правила версии. В SHA-256-репозитории имена объектов и контрольная сумма длиннее; прежние смещения после имени объекта применять нельзя. Читая реальный формат, всегда сначала устанавливают его договор.

Какие именно пути подготавливает add

git add -- path берёт текущее содержимое указанного пути с учётом применимых преобразований. Подготовить удаление отслеживаемого пути тоже можно через add. git add -u обновляет уже отслеживаемые пути, включая удаления, но не добавляет новые неизвестные файлы. git add -A охватывает добавления, изменения и удаления; без ограничивающего пути это весь рабочий репозиторий. Это существенная разница, когда рядом с исправлением лежит сгенерированный файл, который вы ещё не решили сохранять.

git status --short
git add -u
git diff --cached --stat
git diff --cached
git ls-files --stage

--stat показывает сводку по именам и числу изменённых строк, а следующий вызов без него раскрывает содержимое. Сводка удобна для оценки масштаба, но не доказывает правильность: одна изменённая строка может выключить проверку доступа. После подготовки полезно проверять именно --cached, поскольку обычный diff смотрит оставшуюся неподготовленную разницу. При пустом текущем дереве, до первого коммита, Git может сравнить индекс с пустым снимком.

Путь, шаблон и разделитель аргументов

Аргумент пути в Git может быть pathspec, правилом выбора путей. Это шире одного буквального имени: есть шаблоны и специальный синтаксис. Разделитель -- прекращает разбор параметров, но не выключает смысл pathspec. Файл с необычным именем, начинающимся двоеточием, лучше адресовать буквальным режимом, например git --literal-pathspecs add -- ':example'. --literal-pathspecs относится к самому Git и запрещает трактовать последующие спецификации как шаблоны.

Оболочка тоже умеет раскрывать звёздочки, ещё до запуска Git. В git add '*.txt' кавычки оставляют звёздочку для Git; без кавычек Bash сначала может заменить её списком существующих путей. Для большого машинного списка у add есть --pathspec-from-file и --pathspec-file-nul: первый читает выбор путей из файла, второй задаёт нулевые разделители. Это позволяет передать имя с LF без ошибочного разбиения на два файла. Перед подготовкой такой список проверяют как данные, а не склеивают в выполняемую оболочкой строку.

Подготовить часть файла

git add -p -- file включает выбор фрагментов, patch — текстовой заплатки. Git показывает участок различий и спрашивает, добавлять ли его. Ответ y принимает участок, n пропускает, s пытается разделить его на меньшие части, q завершает сеанс. Возможность разделения зависит от расположения изменений. Две соседние взаимообусловленные строки могут оказаться одним участком; механическое дробление не знает логики программы.

После выбора часть изменений существует только в индексе, хотя рабочий файл содержит их все. Компиляция непосредственно из рабочего каталога тогда проверяет другой вариант, чем будущий коммит. Если разделяете крупную правку, сначала рассмотрите подготовленную разницу, а затем проверьте именно сохранённое состояние в отдельном рабочем дереве или после фиксации. Нельзя считать «у меня сейчас запускается» доказательством работоспособности произвольно выбранной половины файла.

Как status избегает чтения каждого байта

Вызов операционной системы stat возвращает метаданные: размер файла, время изменения данных, время изменения служебных свойств и другие поля. Git запоминает такие сведения в индексе. Если поддерживаемые поля совпадают и нет дополнительных оснований сомневаться, файл можно признать неизменившимся без полного хеширования. Если размер или время поменялись, Git исследует содержимое. На конкретные сравниваемые поля влияют файловая система и настройки; формула «сравнивается только дата» неверна.

Представьте файл размером 20 Мбайт, который редактор переписал без изменения байтов. Метаданные изменились, но после чтения хеш совпадёт. Следующая проверка может стать дешёвой после обновления сохранённых сведений. Обратная ситуация опаснее: файл переписан другим содержимым той же длины так быстро, что грубые временные отметки совпали. Проверка только размера и времени пропустила бы изменение. Это гонка по времени, racy Git: запись индекса и изменение файла попадают в неразличимый временной интервал.

Сравнение метаданных является фильтром работы

Запомненный размер в индексе — не авторитетная длина blob: её можно получить из самого объекта. Это часть ускорителя проверки рабочего файла. Когда редактор атомарно заменяет файл новым inode, содержимое может остаться тем же, но дешёвая проверка метаданных потребует уточнения. Когда меняется только время, Git способен перечитать файл и обновить служебное представление без нового коммита. Поэтому изменение самого файла индекса не обязательно означает изменение подготовленного дерева.

git update-index --refresh обновляет подходящие сведения stat для уже совпадающего содержимого; он не является заменой add для новой версии. При реальном изменении команда может сообщить, что путь требует обновления, вместо подготовки его байтов. Если перепутать эти задачи, будущий коммит сохранит прежний blob. Для проверки гипотезы сравните git show :путь, git hash-object путь с нужными правилами преобразования и обычный diff; не выводите состояние подготовки из одного времени .git/index.

Откуда берётся защита от временной гонки

Git учитывает потенциально неоднозначные записи, в частности сопоставляет время файла со временем записи индекса и при необходимости сравнивает содержимое. При записи индекса подозрительная запись может получать особое значение размера, вынуждающее следующую проверку исследовать файл. Это защита оптимизации, а не криптографическая гарантия достоверности произвольно подделанных метаданных. Файловые мониторы и кэш неизвестных файлов добавляют свои способы уменьшить обход каталогов; их корректность опирается на договор с операционной системой.

Файл действительно тот же:
  метаданные совпали → можно пропустить чтение
Файл мог измениться:
  метаданные различаются → прочитать и сравнить содержимое
Время двусмысленно:
  возможная гонка → не доверять одному совпадению stat

На сетевом диске задержки получения метаданных могут доминировать над самим вычислением хеша. Миллион маленьких файлов часто обходить дороже, чем прочитать один крупный файл той же общей длины: каждый путь требует операций поиска и проверки. Отсюда появляются индекс с разделением на общую основу и изменения, кэш неизвестных файлов, файловый монитор и разреженное рабочее дерево. Это разные оптимизации разных затрат. Сначала измеряют, что занимает время: обход неизвестных каталогов, проверка отслеживаемых файлов или запись индекса.

Разобрать гонку на временной шкале

t0: файл содержит AAAA, размер 4; Git записал его в индекс
t1: файл заменён на BBBB, размер по-прежнему 4
t2: файловая система сообщает неразличимую временную отметку
    простое сравнение «размер + mtime» ошибочно дало бы «тот же»

Racy Git — не утверждение, что современный status обязательно пропустит BBBB. Это описание случая, который оптимизация обязана распознать как подозрительный. Временная отметка файла, попадающая в опасную границу относительно записи индекса, вынуждает проверять содержимое. При последующей записи индекса Git может обнулить сохранённый размер такой записи, чтобы следующее сравнение не получило ложную уверенность. Нулевой размер здесь может быть служебным сигналом, а не доказательством пустого blob.

Демонстрировать гонку простым touch недостаточно: поле ctime, точность отметок и поведение файловой системы могут отличаться. Корректный опыт фиксирует фактически полученные stat-поля и наблюдает результат Git, а не обещает воспроизведение по одной задержке в миллисекунду. Исторический документ о racy Git полезен для инварианта, но упомянутые в нём платформенные настройки компиляции не следует автоматически считать текущими настройками любого установленного бинарного Git.

Расширения дополняют таблицу, а не создают другую историю

После записей могут идти блоки расширений с четырёхбайтовой сигнатурой и длиной. Начальная заглавная латинская буква означает необязательное расширение, которое старый читатель может пропустить; обязательное незнакомое расширение игнорировать нельзя. TREE кэширует соответствие групп путей готовым деревьям, экономя повторное построение неизменившихся подкаталогов. REUC сохраняет сведения прежних конфликтных стадий после разрешения, чтобы можно было восстановить конфликт. Они не подменяют основные разрешённые записи индекса.

Разделённый индекс, split index, хранит большую общую основу и небольшой набор изменений; это уменьшает объём переписывания. Разреженный индекс, sparse index, может представлять невыбранный подкаталог одной записью дерева вместо всех файлов внутри. Признак skip-worktree связан с такой рабочей выборкой. Его не следует применять как надёжный общий способ «больше не замечать правки конфигурации»: команды, обновляющие рабочее состояние, имеют собственные условия обращения с этими путями. assume-unchanged — ещё одна подсказка проверке метаданных, а не договор долговременного исключения файла из истории.

Блокировка и незавершённое состояние

Обновляя индекс, Git обычно создаёт соседний файл блокировки index.lock, записывает новое состояние и затем заменяет основной индекс. Так два процесса не должны одновременно перезаписывать одну таблицу. Сообщение о существующей блокировке означает, что изменение индекса занято либо прежний процесс оборвался. Прежде чем считать файл забытым, выясняют, нет ли работающего Git или редактора. Удаление активной блокировки не «ускоряет очередь», а разрушает предпосылку взаимного исключения.

Команда git add -N -- new.txt, где -N означает intent to add, намерение добавить, создаёт специальную запись о новом пути без обычной подготовки его содержимого. Это помогает показать новый файл в некоторых сравнениях и выбрать части через add -p. Такой путь не нужно принимать за уже сохранённую резервную копию. Для проверки того, какие байты действительно подготовлены, используйте обычное добавление и просмотр индекса.

Разбор

Удаление отслеживаемого пути подготовится, новый файл останется неизвестным. git status --short покажет подготовленное D в первой колонке и ?? у нового пути. git add -A добавил бы и новый файл. Сам физически удалённый файл всё ещё читается из предыдущего коммита, пока его история доступна.
