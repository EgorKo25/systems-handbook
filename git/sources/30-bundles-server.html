Передача истории: автономный bundle и работа Git-сервера

Обмен Git состоит из выбора ссылок, передачи необходимых объектов и обновления имён у получателя. Bundle позволяет заранее упаковать согласованный набор для переноса без соединения. Серверный транспорт выполняет часть выбора интерактивно. Проследим обе цепочки и их разные условия полноты.

Получатель должен получить достаточно данных

Новый коммит ссылается на дерево и родителей, дерево — на вложенные деревья и содержимое. Чтобы исследовать полученную историю, нужны соответствующие объекты либо явно известные условия их последующего получения. Передача только сорока знаков коммита не передаёт эти данные. Обновление ссылки на недоступное содержимое не создаёт полноценной копии.

Во время обычного fetch стороны могут выяснить, какие объекты уже есть у получателя. При переносе на флэшке такой беседы нет: отправитель заранее выбирает полный набор либо указывает обязательную основу. Поэтому автономная передача требует особенно явного описания исходного состояния получателя.

Полный учебный bundle

В отдельном маленьком репозитории sender создайте первый коммит с файлом a и отметьте его меткой v1. Путь файла передачи должен находиться за пределами рабочего дерева, чтобы очередной add не включил саму копию истории в проект.

git tag v1
git bundle create ../full.bundle --all
git bundle list-heads ../full.bundle
git bundle verify ../full.bundle
git clone ../full.bundle ../receiver

create записывает выбранный набор, --all задаёт имеющиеся ссылки. list-heads показывает опубликованные в файле имена и идентификаторы. verify проверяет пригодность передачи в контексте текущего репозитория. Для такого вызова нужен Git-контекст; ошибка запуска вне репозитория сама по себе не свидетельствует о повреждении файла.

В выполненном опыте receiver успешно появился из полного файла и получил исходный коммит. Программа clone выбирает рабочую позицию по доступным сведениям источника. Для повторяемой процедуры полезно явно записать ожидаемую ветку и проверить её полный идентификатор после получения. Человеческое имя файла full.bundle не является проверкой состава.

Добавочная передача и обязательная основа

Вернитесь в sender, измените a и создайте следующий коммит. Теперь можно подготовить только продолжение после v1:

git bundle create ../next.bundle v1..main
git bundle list-heads ../next.bundle
cd ../receiver
git bundle verify ../next.bundle

Диапазон исключает историю, уже достижимую из v1. В файле появляется требование к имеющейся основе. В нашем опыте новый пустой репозиторий не прошёл verify этого добавочного набора, а receiver с полученной v1 прошёл. Одни и те же байты передачи оказались пригодны для одного исходного состояния и недостаточны для другого.

Это ожидаемое свойство добавочного обмена. Для удалённой машины полезно вести согласованную контрольную ссылку на последнюю подтверждённую основу. Отправитель не должен переносить её вперёд лишь потому, что записал файл: сначала получатель должен подтвердить получение нужных объектов. Иначе следующая порция может опираться на ещё недоставленную историю.

Unbundle и изменение ссылок

git rev-parse main
git bundle unbundle ../next.bundle
git rev-parse main
git fetch ../next.bundle \
  refs/heads/main:refs/remotes/offline/main
git merge --ff-only refs/remotes/offline/main

unbundle извлекает объекты и сообщает сведения о ссылках из передачи. В проверенном опыте локальная main после этого осталась на прежнем коммите. Новое содержимое уже можно было исследовать по идентификатору, но рабочая ветка не изменилась. Это точное наблюдение, позволяющее отделить наличие объекта от выбора текущего состояния.

Явный fetch связывает полученную main с отдельной локальной ссылкой refs/remotes/offline/main. Затем --ff-only разрешает только простое продолжение текущей ветки. Если receiver успел создать собственную разошедшуюся историю, этот шаг откажется. Сначала исследуйте различия и согласуйте объединение; добавочная передача не выбирает решение за человека.

После успешного обновления повторите чтение файла и сравнение ожидаемого идентификатора. Для двустороннего автономного обмена каждой стороне нужны собственные правила имён и подтверждения основы. Файл bundle не переносит сообщения о том, что другая сторона уже приняла ветку, если это отдельно не зафиксировано процедурой.

Основа определяется объектами

Предположим, у получателя тоже существует метка v1, но она указывает на другой коммит. Совпадение названия не удовлетворяет требование добавочной передачи. Указанная отправителем основа определяется объектом и его связями. Поэтому согласование последней полученной версии должно сохранять полный идентификатор, а не только удобное короткое имя.

Добавочная упаковка может использовать уже имеющиеся данные как основу восстановления объектов. Это экономит передачу, но связывает пригодность файла с исходным состоянием. После отказа verify не нужно принудительно обновлять ветку на новый идентификатор: сначала найдите недоставленную основу либо попросите полный набор. Изменение имени локальной метки не создаст недостающих байтов.

Для практического журнала переноса запишите имя файла, его контрольную сумму, объявленные вершины и требуемую основу. На принимающей стороне добавьте результат проверки и фактический итоговый идентификатор. Такой маленький протокол помогает восстановить порядок нескольких флэшек или файлов с похожими именами. Историю передачи лучше хранить отдельно от предположений о том, что было успешно прочитано.

Проверка файла и доверие поставке

Проверка пригодности bundle исследует формат и необходимые отношения объектов. Она не удостоверяет личность отправителя. Контрольная сумма файла помогает заметить изменение байтов, если ожидаемое значение получено из доверенного источника. Для доверия выбранному коммиту или метке пригодны отдельные проверки подписей и политики ключей.

Полный набор по ссылкам не является образом всей рабочей машины. В нём нет обычных неотслеживаемых файлов, личной конфигурации, всех локальных журналов и произвольных обработчиков. Внешние полезные данные LFS и отдельные хранилища подмодулей также требуют собственной подготовки. Перечень того, что нужно восстановить, составляют до выбора резервного формата.

Передача всех ссылок способна включить больше истории, чем предполагает имя основного проекта. Для публичной поставки выбирайте состав осознанно. Временные исследовательские ветки и старые данные могут оставаться достижимыми. Проверка полного списка имён и выбранных объектов дополняет проверку текущих рабочих файлов.

Голый репозиторий как общая точка обмена

git init --bare --initial-branch=main ../demo-remote.git
git remote add local-demo ../demo-remote.git
git push local-demo main
git fetch local-demo

Команды remote и push выполняются из собственного учебного проекта, рядом с новым хранилищем. Голый репозиторий хранит объекты, ссылки и настройки, но не обычное рабочее дерево приложения. Это удобная точка приёма: отправка не должна незаметно переписывать чужие открытые рабочие файлы. Выбор транспорта добавляет способ запустить операции чтения и приёма этого хранилища.

HEAD голого хранилища также имеет значение: она помогает новому clone выбрать начальную ветку. Если получатель создан с именем main, а отправлена только ветка с другим именем, выбранная по умолчанию ссылка может ещё не существовать. При этом объекты успешно приняты. Диагностика «невозможно извлечь удалённую HEAD» требует проверить опубликованные имена и настройку начальной ссылки, а не повторять передачу всех данных.

Внешний адрес не определяет права автоматически. Сначала транспорт устанавливает соединение и, где предусмотрено, проверяет участника. Затем действуют доступ к хранилищу и правила обновления ссылок. Проверка имени ветки на принимающей стороне из предыдущей главы относится к этой второй части цепочки.

Что запускается через SSH

При получении клиенту нужна серверная операция выдачи объектов, обычно git-upload-pack. При отправке используется git-receive-pack. Через SSH они запускаются на другой машине с выбранным путём репозитория, а их вход и выход связываются с клиентским Git. Шифрованное соединение переносит протокол Git, но само не решает все правила истории.

Проверка ключа сервера отвечает на вопрос, с каким сервером установлено соединение. Проверка учётных данных пользователя отвечает на вопрос, кому разрешён вход. Разрешение обновить конкретную ветку и доверие подписи коммита — ещё отдельные проверки. Похожее слово «ключ» в нескольких слоях не делает эти решения взаимозаменяемыми.

Реальный SSH-сервер в этом материале не развёртывался. Нет инструкции менять службу рабочего компьютера или открывать внешние порты. Исследуемая цепочка помогает правильно локализовать отказ: невозможность SSH-соединения, отказ запуска Git-команды, отсутствие пути, запрет чтения объектов или отклонение обновления ссылки.

Smart HTTP и уровни протокола

При smart HTTP сначала обнаруживаются возможности сервиса, затем клиент отправляет запрос соответствующей операции. В распространённой форме участвуют запрос к info/refs с выбранным сервисом и обращения к git-upload-pack либо git-receive-pack. HTTP обеспечивает перенос запросов и ответов; внутри находится собственный договор Git.

Версия протокола влияет на порядок объявления возможностей и запроса ссылок. Например, во второй версии отдельная команда ls-refs участвует в получении сведений об именах, а fetch описывает нужные объекты. Поэтому нельзя принять один увиденный сетевой дамп за неизменную последовательность для всех версий. Серверные ограничения, прокси и способ аутентификации добавляют свои наблюдаемые отказы.

Есть и статический, «dumb» HTTP, где опубликованы служебные сведения и файлы объектов без такой интерактивной серверной обработки Git. Его цена запросов и обновления метаданных отличается. Настройка веб-сервера и доступов требует отдельного проекта; здесь это описание архитектуры, а не обещание готового публичного сервиса.

Git pkt-line не является IP-пакетом

В части разговора Git применяет собственное кадрирование pkt-line. Начальные четыре шестнадцатеричных знака задают длину вместе с этими четырьмя байтами. Например, запись ниже содержит восемь байтов: четыре знака длины и четыре байта NAK с переводом строки.

0008NAK\n
0000

Это объясняющая запись: \n обозначает один байт перевода строки, а не два печатных символа. Специальная длина 0000 означает границу flush. В некоторых версиях и фазах есть дополнительные управляющие формы. Такой кадр приложения может быть разделён между несколькими чтениями потока; одна порция TCP или одно чтение процесса не обязаны совпадать с границей pkt-line.

После согласования клиент может сообщать желаемые объекты и имеющиеся основы. Сервер формирует подходящую упаковку, клиент проверяет и индексирует её. Отдельные данные упаковки имеют собственное двоичное устройство; текстовый пример pkt-line не является описанием каждого байта packfile. Важно сохранять границу между кадрированием беседы, представлением объектов и транспортной сетью.

Цена обмена и диагностические наблюдения

Время зависит от обнаружения ссылок, согласования общих объектов, поиска и упаковки недостающих данных, передачи, проверки и записи. Большой процессорный расход сервера может возникать до заметной передачи. Повторный fetch с общей историей обычно передаёт другой объём, чем первый clone. Сравнивайте одинаковые исходные состояния и записывайте, какие объекты уже были у клиента.

Выполненные опыты подтвердили основу добавочного bundle, отсутствие перемещения main после unbundle и явное обновление через fetch. Также проверено полезное диагностическое различие: чтение bundle не создало обычной протокольной трассы пакетов, а fetch из соседнего репозитория через серверную операцию создал. Формат автономного файла и интерактивная беседа требуют разных способов наблюдения.

Источники: git-bundle, протокол передачи объектов, HTTP-транспорт, upload-pack, receive-pack, Pro Git: серверные протоколы. Реальный HTTP/SSH-сервис и внешняя аутентификация здесь не испытывались.
