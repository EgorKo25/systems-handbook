Общая ветка — договор о проверках

Git допускает много способов организации веток. Короткие тематические линии, долгая интеграционная ветка, поддержка нескольких выпусков — это способы распределить работу и момент проверки. Название модели не гарантирует работоспособности main. Гарантию ограничивают реальные условия: какой снимок проверяется, какие тесты обязательны, кто имеет право обновить ссылку, не изменилась ли основа между проверкой и приёмом. Зелёная проверка вчерашней вершины не доказывает корректность сегодняшнего слияния.

Pull request или merge request — запрос на рассмотрение и объединение, функция площадки совместной работы, а не отдельный объект Git. Площадка связывает обсуждение, коммиты, проверки и права. Сам результат может быть обычным merge, быстрым перемещением, одним объединённым коммитом или пересозданной последовательностью. Для восстановления происхождения полезно знать, каким способом площадка интегрирует принятый запрос.

Два автора и один сервер

Алиса и Борис получили серверную main на A. Борис отправил B, продолжение A. Алиса создала C, тоже продолжение A, и пытается заменить серверную main на C. Обычный push отклонится: B не является предком C. Это не случайная помеха, а обнаруженная потеря известной линии B при предполагаемом обновлении. Алиса получает B, изучает изменения, затем объединяет или переносит свою работу согласно договору и проверяет результат.

Сервер:  A ─ B
Алиса:   A ─ C

После согласованного merge: A ─ B ─ M
                            \     /
                             C ──┘

Принудительная отправка, --force, разрешает обход обычной проверки продолжения, но не доказывает сохранение чужой работы. Бывают обоснованные переписывания своей опубликованной тематической ветки. Для них нужен явный ожидаемый старый идентификатор: новая ссылка принимается только при совпадении фактического прежнего значения с ожидаемым. Это сравнение и замена, близкое по смыслу к compare-and-swap, условному обновлению состояния.

Что именно проверяет force-with-lease

git fetch origin
git rev-parse origin/topic
# сохраните проверенный полный идентификатор, обозначим его OLD
# выполните согласованное переписывание своей topic
git push --force-with-lease=refs/heads/topic:OLD origin HEAD:refs/heads/topic

OLD в рисунке — подстановка реального полного идентификатора, а не буквальное имя. Флаг --force-with-lease=refs/heads/topic:OLD требует, чтобы серверная topic всё ещё указывала на OLD. Если другой участник успел отправить новый коммит, операция откажет. В изолированном опыте с локальным bare-сервером такой отказ подтверждён. Проверка защищает только указанную ссылку от изменения относительно ожидания; она не анализирует смысл новой программы и не удерживает блокировку на всё время вашей работы.

Короткая форма --force-with-lease без явного OLD обычно использует локальную отслеживаемую ссылку как ожидание. Если редактор в фоне выполняет fetch, эта ссылка могла незаметно продвинуться до чужой новой вершины. Проверка пройдёт относительно уже обновлённого значения, хотя вы не исследовали чужую работу. Явное сохранённое ожидание отделяет «последнее полученное» от «проверенное и согласованное». Серверные правила защиты веток при этом по-прежнему могут запретить переписывание.

Метка выпуска и содержимое результата

git tag -a v1.0.0 -m 'Учебный выпуск 1.0.0'
git show v1.0.0
git rev-parse v1.0.0^{commit}
git push origin refs/tags/v1.0.0

-a создаёт аннотированную метку с отдельным объектом, -m задаёт сообщение. show показывает метаданные метки и целевой объект, а ^{commit} получает коммит под меткой. Обычный push ветки не следует считать отправкой всех меток. Подпись метки создают отдельным режимом, а проверяют доверие к ключу, а не только наличие поля подписи. Имя v1.0.0 становится устойчивым ориентиром лишь при договоре не переставлять опубликованные метки.

Для выпуска связывают полный коммит, точные входы сборки, итоговый артефакт и его контрольную сумму. Метка на правильных исходниках не гарантирует, что опубликованный архив собран из них: в рабочей папке могли остаться незаписанные файлы или другой пакет зависимости. Служба сборки должна указывать фактически выбранную ревизию и проверять именно изготовленный результат. Эта цепочка понадобится в главах о воспроизводимой сборке.

Несколько ссылок и атомарный push

git push --atomic origin main refs/tags/v1.0.0 запрашивает обновление нескольких ссылок как единой транзакции: либо принимаются все, либо ни одна. --atomic требует поддержки на принимающей стороне; если сервер её не поддерживает, команда откажет. Собственный локальный опыт подтвердил: при отказе обновить main новая ветка из того же атомарного запроса не появилась. Без атомарного режима разные ссылки одного запроса могут иметь разные результаты.

Граница атомарности — обновление ссылок этого сервера. Она не объединяет в одну транзакцию загрузку образа в реестр, выкладку сайта и изменение базы. Проверочный обработчик тоже может иметь побочные внешние действия, которые обычная транзакция ссылок не откатывает. Поэтому процесс выпуска должен уметь распознавать частичный внешний результат и повторять допустимые шаги. Даже успешный push не равен успешной публикации Pages: последующая задача сборки может завершиться ошибкой.

Как читать результат отправки

Проверяют код завершения, строки результатов по ссылкам и идентификатор фактической серверной вершины. git ls-remote origin refs/heads/main даёт текущее опубликованное значение для сопоставления. Для сайта дополнительно проверяют выполнение сборки на этом коммите и версию полученного сайта. Повторять отправку без понимания состояния не нужно: объект уже мог попасть в хранилище, а ссылка не обновиться, либо ссылка обновилась, но внешнее развёртывание ещё выполняется.

Зелёный тест и новая основа

Тематическая ветка прошла тесты относительно A. Пока её проверяли, main перешла на B. Достаточно ли прежнего результата?

Разбор

Он относится к конкретному проверенному снимку. Результат объединения с B может быть другим, даже без текстового конфликта. Нужна проверка предполагаемого итогового снимка либо эквивалентная процедура, установленная процессом интеграции.
