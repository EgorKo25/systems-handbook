Язык ревизий и путей: выбрать ровно те данные

Имя ветки, номер родителя, путь внутри дерева и набор коммитов — разные виды указаний. Ошибка выбора может показать убедительный, но относящийся к другой версии результат. Построим маленький граф и научимся заранее вычислять смысл каждого выражения.

У выражения есть тип и контекст

Когда команда получает main, Git пытается разрешить это имя через правила ссылок и объектов. Результатом может быть коммит. Выражение main^{tree} выбирает дерево этого коммита, а main:src/app.py — объект файла внутри него. Путь в текущем каталоге — ещё одна сущность. Совпадение текстовых имён не объединяет их в один объект.

Полный идентификатор зависит от формата хранилища. В обычном SHA-1-репозитории он состоит из сорока шестнадцатеричных знаков; у SHA-256 другая длина. Для программного обмена полезен полный идентификатор с известным форматом. Короткая запись является локально однозначным префиксом: появление новых объектов способно изменить достаточную длину. Поэтому число семь или двенадцать не является универсальной гарантией.

git rev-parse --verify HEAD
git rev-parse --verify 'HEAD^{commit}'
git cat-file -t HEAD
git cat-file -t 'HEAD^{tree}'

--verify требует подходящего единственного разрешения. Суффикс ^{commit} дополнительно требует коммит после допустимого разыменования, а cat-file -t показывает фактический тип. Получение строки, похожей на хеш, ещё не доказывает, что следующая команда получила именно нужный тип данных.

Граф, который можно вычислить вручную

Создайте отдельный одноразовый проект. В базовом коммите A пусть будет src/a.txt. От A создайте ветку side и добавьте в ней отдельный side.txt, получив C. Вернувшись в main, добавьте main.txt, получив B. Файлы разные, поэтому слияние не требует текстового конфликта. Объедините side в main через git merge --no-ff side, получив M, затем сделайте обычный коммит N.

A---B---M---N  main, HEAD
 \     /
  C---/       side

На рисунке линии направлены от предков к потомкам для чтения человеком. В самих объектах коммит хранит ссылки на родителей. У M первым родителем будет B, потому что main была текущей стороной, вторым — C. У N только один родитель M. Вычисляйте выражения по связям, а не по горизонтальному положению картинки или времени автора.

git log --graph --all --oneline --decorate
git rev-parse HEAD^ HEAD~2 'HEAD~1^2'
git rev-list --parents -n 1 HEAD~1

HEAD^ выбирает первого родителя N, то есть M. HEAD~2 дважды идёт по первому родителю и приходит в B. HEAD~1^2 сначала попадает в M, затем выбирает второго родителя C. У самого N выражение HEAD^2 завершится ошибкой: второго родителя у него нет. Такая ошибка полезнее случайного подбора похожего имени.

В проверенном Git 2.43 оба вида перехода были сопоставлены с сохранёнными полными идентификаторами родителей. Количество верхних индексов и число после тильды не означают «второй последний коммит по дате». В истории слияний это различие меняет и выбранные данные, и объяснение происхождения изменения.

Команды для построения именно этого графа

Используйте отдельную учебную папку и подготовленную учебную личность. Не выполняйте этот маршрут внутри действующего проекта. Создание файлов ниже намеренно разделено по веткам, чтобы различие структуры графа не смешивалось с разрешением текстового конфликта.

git init --template= -b main revision-demo
cd revision-demo
git config --local user.name 'Demo Student'
git config --local user.email student@example.invalid
git config --local commit.gpgSign false
mkdir -p src
printf 'base\n' > src/a.txt
git add src/a.txt
git commit -m A
git switch -c side
printf 'side\n' > side.txt
git add side.txt
git commit -m C
git switch main
printf 'main\n' > main.txt
git add main.txt
git commit -m B
git merge --no-ff side -m M
printf 'after merge\n' > after.txt
git add after.txt
git commit -m N

--template= исключает копирование файлов каталога шаблонов при инициализации; обработчики, настроенные другими источниками, проверяют отдельно. -b задаёт имя начальной ветки. Локальные значения личности относятся только к этому проекту, а выключение автоматической подписи предотвращает неявный выбор личного ключа. Общие настройки и окружение исследуются предыдущей главой.

Сообщения A, B, C, M и N служат подписями рисунка. Это не специальные имена ревизий: команда git show B не обязана их понимать. Для точного обращения сохраните полученные идентификаторы либо создайте осознанно названные учебные метки. Различие между сообщением коммита и ссылкой на него — отдельная причина частых ошибок начинающего исследования.

Метка как объект и разыменование

git tag -a release -m "Revision experiment" HEAD~1
git cat-file -t release
git rev-parse release 'release^{}' 'release^{commit}'
git cat-file -t 'release^{tree}'

Аннотированная метка имеет собственный объект. Обычное разрешение release даёт его идентификатор. Пустые фигурные скобки после ^ просят разыменовывать цепочку меток до объекта другого типа. В нашем случае это M. Уточнение ^{commit} требует именно коммит, а ^{tree} позволяет получить его дерево. Объект метки и помеченный коммит различаются даже тогда, когда обе записи в разговоре называют «версией release».

Это особенно важно при подписи и сравнении поставок. Подпись аннотированной метки относится к её объекту с сообщением и целевым объектом. Сравнение одного имени метки без проверки её типа и ожидаемой цели может скрыть замену. Прежде чем строить архив или публиковать исходную версию, сохраните полный разрешённый коммит и используйте его в последующих проверках.

Один объект, набор коммитов и две точки сравнения

У журнала git log A..N смысл задаётся достижимостью: взять доступные из N коммиты и исключить достижимые из A. Слово «между» здесь может ввести в заблуждение, особенно при слиянии нескольких линий. Для симметричной разности служит A...N: исключаются общие достижимые предки, остаются стороны различия истории.

git log --oneline --left-right side...main
git log --oneline side..main
git diff side..main
git diff side...main

--left-right помечает принадлежность коммита левой или правой стороне. Однако для diff две точки являются обозначением сравнения двух конечных состояний. Три точки выбирают общую основу и правую сторону. Таким образом, одинаковые знаки в log и diff участвуют в разных задачах. Чтение списка коммитов нельзя механически подменить сравнением содержимого двух деревьев.

Полезный контроль: сначала найдите git merge-base side main, затем сравните полученный идентификатор с main обычным diff. Для данного графа это даёт объяснимую пару состояний. При нескольких подходящих общих предках нужно исследовать структуру отдельно: простой рисунок с одним основанием не покрывает все возможные истории.

Двоеточие выбирает содержимое сохранённого дерева

git show HEAD:src/a.txt
cd src
git show HEAD:./a.txt
git cat-file -s HEAD:./a.txt

Первая форма использует путь от корня сохранённого дерева. Вторая явно начинает путь с текущего каталога и преобразует его относительно корня рабочего дерева. В нашем опыте обе формы показали одни байты. Размер из cat-file -s относится к содержимому объекта, а не к сжатому файлу в хранилище и не к числу букв на экране.

В выражении после двоеточия нельзя ожидать автоматического разворачивания шаблона в несколько файлов. HEAD:*.txt является попыткой найти конкретный путь с такими знаками в дереве. Для перечисления дерева используют ls-tree, а для поиска внутри выбранного состояния — git grep. У этих команд свои формы выбора набора путей.

Начальное двоеточие без имени ревизии обращается к индексу: :src/a.txt означает обычную запись стадии ноль. Во время конфликта доступны формы :1:путь, :2:путь и :3:путь. Они выбирают сохранённые входы решения конфликта; после подготовки разрешённого файла конфликтные стадии заменяются обычной записью.

Кавычки оболочки и правила выбора путей Git

Кавычки сначала защищают аргумент от оболочки. Когда аргумент дошёл до Git, его ещё могут интерпретировать правила pathspec — выражений выбора путей. Поэтому строка в кавычках с квадратными скобками способна оставаться шаблоном для Git. Разделитель -- заканчивает разбор параметров и отделяет пути, но не отключает собственный язык шаблонов.

git ls-files -- ':(literal)src/x[1].txt'
git ls-files -- ':(top,glob)src/*.txt'
git ls-files -- ':(top,glob)src/*.txt' \
  ':(exclude,literal)src/x1.txt'

Первое выражение требует буквального имени x[1].txt. Второе задаёт сопоставление от корня рабочего дерева и явный режим glob: звёздочка выбирает имена внутри указанного уровня. Третье добавляет исключение буквального пути. В нашем наборе были a.txt, x1.txt и x[1].txt; последняя команда оставила первый и третий.

Особенность, обнаруженная реальным опытом: запуск второй команды из каталога src всё равно выводил имена относительно src. Признак top изменил базу сопоставления, а не автоматически формат вывода ls-files. Сценарий, который собирает пути из текста команды, должен знать обе эти системы отсчёта. Для машинного обмена произвольными именами обычно выбирают нулевые разделители.

Рекурсивные правила требуют собственного рассмотрения: в режиме glob последовательность ** может обозначать несколько уровней каталогов. Признак icase изменяет сопоставление без учёта регистра, но не меняет возможности файловой системы хранить похожие имена. Проверяйте выражение сначала командой перечисления, прежде чем использовать его в массовом восстановлении или очистке.

Неоднозначность имени и безопасный ввод

Пусть в проекте есть файл side и ветка side. У команды истории этот аргумент может иметь два возможных назначения. Запись git log side -- явно оставляет side ревизией, а git log -- side выбирает путь. Для чтения файла из конкретного дерева существует ещё более явная форма git show HEAD:side. Форму выбирают по вопросу, который исследуют.

git rev-parse --verify --end-of-options 'release^{commit}'

--end-of-options нужен, когда имя получено извне и может начинаться с дефиса: оно должно оставаться данными. Кавычки предотвращают разбивку и преобразования оболочки, а требование типа отсеивает подходящий по имени объект неправильного назначения. Проверенный полный идентификатор затем можно передать дальше. Это не проверка доверия содержимому коммита, а точное ограничение выбираемой сущности.

Селектор main@{yesterday} обращается к локальному журналу перемещения main. Он не означает «коммит с авторской датой вчера» и зависит от имеющегося reflog. Порядковый вариант также может измениться после новых перемещений. Для сохранённого отчёта об исследовании запишите разрешённый идентификатор вместе с исходным выражением и временем наблюдения.

Контроль результата и эффективность

Перед дорогой сборкой или большой выборкой сначала разрешите ревизию, проверьте тип и перечислите небольшой набор путей. Такие действия обычно намного дешевле извлечения всех файлов и полезны для раннего обнаружения ошибки выбора. На большом репозитории ограничение путей сокращает объём рассматриваемых данных, но история изменений конкретного пути всё равно может требовать существенного обхода графа.

В книге проверены разыменование аннотированной метки, оба родителя слияния, цепочка первых родителей, относительное обращение к сохранённому файлу и три варианта pathspec. Верификация blob как коммита завершилась отказом. Эти наблюдения относятся к созданному учебному графу; команды просмотра не переименовывали ветки и не меняли чужую историю.
