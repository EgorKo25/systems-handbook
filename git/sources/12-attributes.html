Игнорирование, атрибуты и точные байты файлов

Почему ignore не удаляет историю, CRLF меняет содержимое, а LFS хранит указатель вместо большого файла

Ignore действует на намеренно неотслеживаемые пути

.gitignore задаёт шаблоны путей, которые обычные операции не должны предлагать как новые отслеживаемые файлы. Это удобно для результатов сборки, временных журналов и локальных настроек. Но уже присутствующий в индексе файл не перестаёт отслеживаться после добавления правила. Его изменения по-прежнему видны, и обычный add может подготовить новую версию. Если файл успешно добавлен и записан в коммит, правило ignore не объясняет его отсутствие в этом коммите: нужно проверить выбранный индекс, путь, ветку и результат команды.

# Пример .gitignore в корне учебного проекта
/build/
*.tmp
!important.tmp

Ведущий слеш привязывает build к расположению этого файла правил; завершающий выбирает каталог. *.tmp соответствует именам с таким окончанием, ! отменяет подходящее правило для указанного пути. Правила вложенных каталогов и источники исключений имеют порядок приоритета. Если родительский каталог исключён целиком, вернуть отдельный файл внутри него одним отрицательным правилом обычно не получится: Git может вовсе не обходить исключённый каталог.

git check-ignore -v -- path показывает применившийся источник и правило: -v включает подробности. Для изучения уже отслеживаемого пути можно добавить --no-index, чтобы проверить сами правила независимо от факта отслеживания. Общие проектные правила сохраняют в .gitignore; личные локальные исключения можно держать в .git/info/exclude или пользовательском файле правил. Последние не передаются обычным клонированием.

Прекратить отслеживание — отдельное изменение снимка

git rm --cached -- local.conf удаляет путь из индекса, оставляя рабочий файл. --cached здесь выбирает только область подготовки. После коммита новый снимок не содержит путь; старые коммиты всё ещё содержат его прежние байты. В другом клоне получение и применение такого удаления может убрать ранее отслеживаемую рабочую копию согласно состоянию файлов. Поэтому перед изменением общих правил согласуют, где участники сохранят нужные локальные данные. Ignore не является ни шифрованием, ни стиранием истории.

Атрибуты определяют обработку пути

.gitattributes — другой файл правил: он задаёт свойства обработки содержимого, сравнения, слияния и экспорта. У атрибута возможны состояния «включён», «выключен», «задано значение» и «не определён». Например text включает текстовую нормализацию, -text выключает её, text=auto просит определять подходящие текстовые файлы. Это не правила видимости файла в статусе.

*.sh  text eol=lf
*.cmd text eol=crlf
*.png -text
*.dat -text

eol — end of line, окончание строки. LF — один байт 0a; CRLF — два, 0d 0a. Для текстового пути при добавлении Git может нормализовать окончания до LF в сохраняемом содержимом, а при извлечении — сформировать нужный рабочий вариант. Поэтому байты рабочего файла и blob могут различаться без логической правки. Для файла с договором «сохранить побайтово» выбирают -text, если это соответствует назначению данных.

Проверить преобразование на малом примере

В собственном опыте Git 2.43.0 файл с байтами 61 0d 0a 62 0d 0a добавлялся двумя путями. Для a.txt действовало text eol=lf, для a.dat — -text. Подготовленный первый blob содержал 61 0a 62 0a, второй сохранил все шесть исходных байтов. Физическая рабочая копия после add ещё могла иметь прежние окончания: подготовка не обязана переписывать её сразу.

git check-attr text eol -- a.txt a.dat
git ls-files --eol
git show :a.txt
git diff --cached -- a.txt

check-attr показывает эффективные атрибуты указанных путей. ls-files --eol выводит сведения об окончаниях в индексе и рабочей копии. Набор букв вывода зависит от реального содержимого, поэтому его читают вместе с атрибутом, а не как оценку качества файла. Параметр core.autocrlf — локальная конфигурация, взаимодействующая с атрибутами. Явный проектный договор обычно проще воспроизвести, чем разные личные настройки без описания.

Нормализация существующего проекта

git add --renormalize . заново применяет подходящие преобразования к отслеживаемым путям и подготавливает результат. --renormalize не является косметической настройкой: идентификаторы содержимого могут измениться у множества файлов. Это делают отдельным осмысленным изменением из понятного состояния, затем читают подготовленную разницу и проверяют бинарные и подписанные данные. Массовая замена CRLF на LF внутри подписанного архива меняет архив, даже если текстовый просмотр кажется прежним.

Пользовательские фильтры clean и smudge преобразуют содержимое соответственно на пути к хранению и при извлечении. Они могут зависеть от внешней программы. Если её нет, разные рабочие места получают разные результаты или ошибку — в зависимости от настройки обязательности фильтра. Воспроизводимость требует знать такие внешние преобразователи и их версии. Само наличие blob в Git не гарантирует, что рабочий файл получается без дополнительного инструмента.

Большие файлы и LFS

Git LFS — Large File Storage, отдельная система хранения больших файлов, связанная с Git через фильтры и протокол. В обычном дереве Git сохраняется небольшой файл-указатель с версией формата, идентификатором содержимого и размером. Сами большие байты загружаются из другого хранилища. Это уменьшает давление больших версий на обычную историю, но создаёт ещё один обязательный вход для автономной работы.

Если скопировать репозиторий без загруженных LFS-объектов, на компьютере без сети вместо документа может оказаться указатель. Если получить исходный архив с площадки, поведение включения больших файлов зависит от площадки и её настроек; проверяют фактический архив. Для флэшки сначала формируют готовое автономное дерево, затем проверяют размеры, контрольные суммы и открытие файлов. Обычная отметка «клонирование завершилось» не равна проверке всех внешних данных.

Разбор

Путь уже отслеживался, поэтому ignore его не исключает из индекса. Удаление из индекса изменит будущий снимок, но не прежние объекты. История и действительность текущего рабочего дерева рассматриваются отдельно.

Первоисточники: область действия ignore, преобразования и атрибуты, проверка атрибутов, удаление из индекса, официальная спецификация Git LFS.
