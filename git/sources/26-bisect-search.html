Поиск причины: содержимое, происхождение строк и bisect

Увидеть место с подозрительным кодом и найти изменение, после которого возник наблюдаемый сбой, — разные задачи. В этой главе поиск движется от выбранных байтов к истории, затем к проверяемой гипотезе. Автоматическое деление истории полезно только при точно определённом результате опыта.

Сначала сформулировать наблюдаемый признак

Фраза «после обновления стало плохо» не задаёт проверку. Нужны вход, ожидаемое свойство, фактический результат и условия запуска. Для ошибки ответа это могут быть конкретный запрос и неправильное значение. Для производительности — ограниченная нагрузка, известная среда и правило сравнения серии измерений. Номер версии или сообщение коммита не заменяют наблюдение.

Сначала повторите проверку на двух концах исследуемой истории. Хорошая версия должна действительно проходить, плохая — воспроизводимо нарушать выбранное свойство. Если различие исчезает при повторе, автоматический поиск может исследовать случайность среды. Сохраните исходники теста отдельно от переключаемой истории, чтобы переход на старый коммит не удалил средство проверки.

Выбрать, в каких байтах искать

git grep -n -F -e token -- '*.py'
git grep --cached -n -F -e token -- '*.py'
git grep -n -F -e token HEAD -- '*.py'

Первая команда ищет в подходящих отслеживаемых рабочих файлах. --cached выбирает подготовленные версии индекса. Явный HEAD задаёт сохранённое дерево. Поэтому один запуск способен ничего не найти, пока другой покажет строку того же имени файла: их источники содержимого различаются. В реальном опыте рабочая строка уже была заменена на число, а индекс всё ещё содержал token.

-n добавляет номер строки, -F выбирает буквальное сопоставление вместо регулярного выражения, -e явно отделяет искомый образец. Шаблон пути заключён в кавычки, чтобы его передали Git. Для более сложных наборов используйте явные правила pathspec предыдущей главы. Само совпадение последовательности букв не знает смысла программы: оно может находиться в комментарии или другом контексте.

Для ответа «какие файлы содержат образец» подходит -l, для счёта совпавших строк — --count. Ограничение выдачи снижает объём данных, но не всегда устраняет чтение файлов. При расследовании большого проекта полезно сначала выбрать нужное дерево и каталог, а затем усложнять регулярное выражение. Это одновременно экономит время и уменьшает число случайных совпадений.

История изменения количества и история подходящих строк

Создадим два последовательных состояния одного файла. В первом строка имеет вид value = token + token, во втором — value = token * token. Оператор изменился, количество вхождений token осталось равным двум. Этот маленький пример отделяет два распространённых вопроса к истории.

git log --oneline -S token -- math.py
git log --oneline -G token -- math.py
git log -p -G 'token.*token' -- math.py

-S отбирает изменения количества вхождений указанной строки. Поэтому коммит замены плюса на умножение не появляется в первом результате. -G проверяет регулярное выражение в добавленных или удалённых строках различия. Оба изменённых варианта подходят под token, и коммит попадает во второй результат. Это было проверено на реальных объектах Git, а не на имитации вывода.

Ключ -p добавляет текст изменения, чтобы проверить причину отбора. Если нужно увидеть также остальные правки выбранного коммита, предусмотрен --pickaxe-all. Он расширяет показываемый состав уже выбранного изменения. Нельзя трактовать отсутствие результата -S как доказательство, что строка никогда не менялась: количество могло сохраниться, область поиска могла быть ограничена либо нужная история отсутствует.

Blame: последнее изменение строки и происхождение решения

git blame -L 2,5 HEAD -- app.py
git blame -w -M -C HEAD -- app.py
git log --follow -p -- app.py

blame сопоставляет строкам выбранного состояния найденные изменившие их коммиты. Параметр -L 2,5 ограничивает номера строк. Он полезен, когда уже найден небольшой участок. Флаг -w позволяет игнорировать некоторые различия пробелов, -M исследует перемещения внутри файла, -C — также подходящие копирования из других файлов. Дополнительный поиск стоит процессорного времени и опирается на правила распознавания.

Вывод отвечает на вопрос о происхождении отображаемых строк по выбранным правилам. Причина дефекта могла появиться в вызывающей функции, конфигурации, данных либо давнем предположении, которое последняя правка только проявила. Поэтому имя автора в blame служит указателем для чтения изменения. Оно не является доказательством ответственности за весь наблюдаемый сбой.

--follow помогает прослеживать историю одного файла через распознанные переименования. Это отдельная ограниченная форма исследования, а не обещание безошибочно восстановить любые перемещения и копирования каталога. После перехода к интересующему коммиту полезно прочитать сообщение, полный состав правки, тесты и родительское состояние.

Своя история из шестнадцати состояний

Для деления истории создайте отдельный чистый учебный репозиторий с личностью example.invalid. В каждом коммите будем сохранять номер шага и значение признака. До шага двенадцать читаемые состояния хорошие, начиная с него — плохие. Шаг десять намеренно нельзя проверить. Используются только маленькие текстовые файлы.

for HANDBOOK_N in {1..16}; do
  printf '%s\n' "$HANDBOOK_N" > number.txt
  if [ "$HANDBOOK_N" -eq 10 ]; then
    printf 'SKIP\n' > state.txt
  elif [ "$HANDBOOK_N" -lt 12 ]; then
    printf '0\n' > state.txt
  else
    printf '1\n' > state.txt
  fi
  git add number.txt state.txt
  git commit -m "step $HANDBOOK_N"
done
git tag known-good HEAD~15
git tag known-bad HEAD

Цикл показан для Bash; -eq и -lt сравнивают числа. Метка known-good указывает на первый шаг, known-bad — на шестнадцатый. Это собственный искусственный сценарий, а не тест реальной производительности. Его преимущество — заранее известная правильная граница, с которой можно сопоставить вывод инструмента.

Проверочная программа как измерительный прибор

Сохраните следующий файл как check-state.py рядом с репозиторием, за его пределами. Он не меняет проверяемые файлы. Значение ноль означает хороший результат, единица — выбранный плохой признак, 125 — невозможность проверки. Ошибка чтения или неизвестный формат дают 128, чтобы остановить поиск вместо ложной классификации.

from pathlib import Path
import sys

try:
    state = Path('state.txt').read_text().strip()
except (OSError, UnicodeError):
    sys.exit(128)
if state == 'SKIP':
    sys.exit(125)
if state not in {'0', '1'}:
    sys.exit(128)
sys.exit(int(state))

Такое соглашение существенно. Необработанное исключение Python обычно завершает программу кодом один. Для bisect run это означало бы плохую версию, хотя фактическая причина могла быть в отсутствующем файле теста. Аналогично ошибка запуска инструмента способна дать 126 или 127. Поэтому доступность интерпретатора и пригодность теста проверяются до автоматического обхода.

Для реальной проверки сборки разделите «исходник не собирается в данной среде» и «исследуемое поведение нарушено». Код 125 полезен для первой ситуации, если это осознанное ограничение опыта. Но массовый пропуск всех неудобных состояний может оставить несколько возможных виновников. Тогда честный результат — множество кандидатов и причина неопределённости.

Запуск и чтение результата

git bisect start known-bad known-good
git bisect run python3 ../check-state.py
git bisect log
git show --stat HEAD
git bisect reset

Порядок аргументов start: сначала известная плохая позиция, затем хорошая. Git выбирает проверяемые состояния, меняет рабочее дерево и запускает заданную программу. Код ноль помечает хороший результат, значения от одного до 127, кроме 125, — плохой. Код 125 пропускает состояние. Другие коды прерывают автоматическое исследование.

В выполненном опыте проверялись шаги 8, 12, 10 и 11. Десятый вернул 125. Восьмой и одиннадцатый были хорошими, двенадцатый плохим; Git определил именно коммит шага двенадцать. Эти номера относятся к нашей линейной истории и не являются обещанием фиксированного порядка для любого графа. Журнал bisect сохраняет принятые решения, а reset вернул main и исходное положение работы.

Перед reset сохраните нужные идентификаторы и журнал исследования. Команда заканчивает сеанс, а не исправляет найденную программу. После определения кандидата отдельно повторите исходный тест на его родителе и на нём самом, прочитайте правку и сформулируйте причинную связь. Затем создавайте исправление и добавляйте проверку, которая воспроизводит проблему.

Границы метода на настоящем проекте

Проверять измеритель до доверия его ответам

Представим, что проверочная программа запускает ранее собранный исполняемый файл. Git меняет исходники, но старый файл лежит в игнорируемом каталоге и продолжает успешно отвечать. Получается правдоподобный быстрый поиск, который классифицирует один и тот же результат сборки вместо разных ревизий. Поэтому каждый шаг должен устанавливать связь между выбранным коммитом, входами сборки и проверяемым результатом.

Самый простой учебный вариант — свежий отдельный каталог результата для каждой проверки. Более экономный использует кэш с полным ключом входов. Тогда в ключ входят существенные версии инструментов, параметры и зависимости. Выбор компромисса измеряют: сколько занимает чистая подготовка, сколько экономится и какие данные подтверждают корректность повторного использования. Бездумная очистка всех неотслеживаемых файлов не является обязательным условием поиска и может уничтожить полезные локальные данные.

Заведите краткую запись на каждый исследованный коммит: полный идентификатор, код результата, версию теста, параметры среды и продолжительность. Не сохраняйте только последнюю строку «первый плохой». При спорном результате такая запись показывает, какая посылка привела к выбору. Для повторения последовательности пригоден сохранённый журнал bisect; фактическую доступность объектов и зависимостей нужно обеспечить отдельно.

Аналогичная дисциплина нужна обычному поиску строк. Отсутствие совпадения в текущей main не исключает его существования в другой ветке. Ограничение одним путём может скрыть прежнее расположение файла, а одинаковое число вхождений — замену контекста. Начинайте с самого дешёвого точного вопроса, но при отрицательном ответе расширяйте область осознанно: другое дерево, другие ссылки, другой критерий выбора изменения. Каждый такой шаг меняет проверяемую гипотезу.

История может содержать временно сломанные сборки, смену зависимостей и условия, которых уже нет. Поведение иногда появляется, исчезает и появляется снова. Простое ожидание одной устойчивой границы тогда не описывает всю задачу. Уточняйте исследуемый интервал и смысл хорошей отметки; не выдавайте результат автоматического выбора за доказательство всей истории дефекта.

В графе слияний можно исследовать отдельные коммиты либо последовательность первых родителей. Режим --first-parent полезен, когда вопрос звучит «после какого включения изменения в основную ветку возник сбой». Он может указать на merge, тогда как первоначальный ошибочный код находился внутри объединённой линии. Это два полезных, но разных уровня расследования.

Если ошибка зависит от нагрузки, один запуск недостаточен. Нужны прогрев, известное число повторов и правило классификации с запасом относительно шума. Дорогой тест повышает цену каждого шага: сравнивайте время подготовки среды и собственно проверки. Логарифмическая идея сокращает число решений, но не делает дорогую сборку дешёвой и не исправляет плохой измеритель.

Подробности и ограничения: git-bisect, git-grep, выбор изменений в git-log, git-blame. Разделы Searching и Debugging with Git в Pro Git помогают сопоставить эти инструменты с общей картой Git.
