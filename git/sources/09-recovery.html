Отмена и восстановление: reset, restore, revert и reflog

Сначала определить потерянное состояние, затем выбрать действие над ссылкой, индексом или файлами

Слово «отменить» скрывает четыре задачи

Можно захотеть убрать файл из подготовки, заменить его рабочие байты, перенести ветку к старому коммиту или записать новое изменение, обращающее прежнее. Это разные операции. Команда reset в форме с коммитом перемещает текущую ветку либо непосредственно HEAD в отсоединённом режиме, а затем по выбранному режиму меняет индекс и рабочие файлы. Она не редактирует прошлый объект коммита и не является немедленным удалением объекта с диска.

Команда в учебном репозиторииТекущая ссылкаИндексРабочие файлы
git reset --soft HEAD^На родителяСохраняетсяСохраняются
git reset --mixed HEAD^На родителяИз выбранного коммитаСохраняются
git reset --hard HEAD^На родителяИз выбранного коммитаПриводятся к выбранному состоянию с перезаписью мешающих данных

HEAD^ требует существующего родителя; на первом коммите такого объекта нет. --mixed — режим по умолчанию, но в обучении лучше писать его явно. Таблица описывает форму reset с целевой ревизией. Форма git reset HEAD -- file с путём меняет выбранные записи индекса и не перемещает ветку: одинаковое имя команды имеет два семейства действий.

Точный опыт с soft и mixed

Пусть A содержит строку old, B — new, рабочее дерево чистое, HEAD указывает на B. После reset --soft A ветка окажется на A, а индекс и файл сохранят new. Статус покажет подготовленную разницу A→B. Теперь можно создать другой коммит с тем же содержимым, например с исправленным описанием. После reset --mixed A индекс содержал бы old, рабочий файл — new; та же разница стала бы неподготовленной.

До:          HEAD=B   индекс=new   файл=new
--soft A:    HEAD=A   индекс=new   файл=new
--mixed A:   HEAD=A   индекс=old   файл=new
--hard A:    HEAD=A   индекс=old   файл=old

--hard может безвозвратно убрать несохранённые рабочие байты. Неотслеживаемые пути тоже могут пострадать, если мешают записи отслеживаемого пути из целевого снимка. При этом команда не является общей очисткой всех неизвестных файлов: посторонний файл, не мешающий приведению дерева, может остаться. Фраза «hard удаляет всё лишнее» одновременно преувеличивает полноту очистки и скрывает конкретный риск перезаписи.

Restore выбирает источник и место назначения

git restore --staged -- service.conf
git restore -- service.conf
git restore --source=HEAD~1 --worktree -- service.conf

Первый вызов восстанавливает запись индекса из HEAD и оставляет рабочий файл; --staged выбирает область подготовки. Второй без дополнительных флагов копирует из индекса в рабочее дерево, убирая неподготовленную правку. Третий явно задаёт источник --source=HEAD~1 и назначение --worktree. Историческое содержимое станет рабочей правкой относительно нынешнего снимка; текущая ветка не сдвинется. Сочетание --staged --worktree меняет оба назначения. Если путь отсутствует в источнике, восстановление может означать удаление пути, а не создание пустого файла.

Revert записывает обратное изменение

git revert C пытается обратить изменение, внесённое C, поверх текущего состояния и создать новый коммит. Старый C остаётся в истории. Это удобно для уже опубликованной линии: коллегам не нужно угадывать, куда исчезли известные объекты. Но операция не гарантирует бесконфликтного успеха. Если C заменил 8000 на 8080, а позднее кто-то заменил ту же строку на 9000, обратная заплатка может не иметь однозначного применения.

При остановке изучают конфликт, редактируют результат, выполняют git add -- путь и git revert --continue. --abort отменяет незавершённую операцию. Для merge-коммита требуется выбрать основную родительскую сторону через -m; отмена слияния влияет и на смысл последующих слияний, потому что история интеграции остаётся. Поэтому «revert безопаснее, значит можно не читать» — неверный вывод: он сохраняет граф, но итоговый код всё равно требует проверки.

Reflog сохраняет движения ссылок

Журнал ссылок, reflog, записывает прежние и новые значения локальных ссылок. После ошибочного reset старую вершину часто можно найти в git reflog show HEAD. Обозначение HEAD@{1} означает предыдущее записанное положение в этом локальном журнале, а не обязательно предыдущий коммит по первому родителю. Переключения веток тоже меняют HEAD. У коллеги другой журнал; обычный clone не переносит вашу историю перемещений.

git reflog show HEAD
git show --stat HEAD@{1}
git branch recovered HEAD@{1}

Сначала проверяют объект, затем создают удерживающую ветку. Если после просмотра выполнить другие операции, порядковый номер журнала может сдвинуться; для записи результата используйте проверенный полный идентификатор. В нашем изолированном опыте после soft reset старая вершина нашлась в журнале и была закреплена новой веткой. Наличие объекта также можно исследовать через git fsck --full, проверку связности и корректности хранилища, но поиск среди недостижимых объектов сложнее, чем создание понятного имени заранее.

ORIG_HEAD и временное сохранение работы

Перед некоторыми операциями Git записывает прежнюю вершину в ORIG_HEAD. Это удобно для быстрой проверки после reset или merge, но следующая подходящая операция может заменить значение. Поэтому это не постоянное имя резервной копии. Удерживающая ветка с понятным названием и проверенным идентификатором надёжнее для длинного исследования, а внешний резервный снимок нужен для данных, вообще не входящих в Git.

git stash push -m 'Незавершённый учебный опыт' сохраняет временное состояние отслеживаемой работы в специальных объектах и убирает соответствующие рабочие изменения. stash означает отложенный запас; -m подписывает запись. Неизвестные файлы требуют отдельного режима, например -u, и игнорируемые данные по умолчанию туда не входят. Перед предположением «я всё сохранил» читают статус и список. git stash apply применяет сохранённое без удаления записи, git stash pop при успехе ещё и убирает её из списка. Применение поверх нового состояния может конфликтовать: это перенос изменения, а не гарантированная вставка файла.

Граница восстановления и очистка

Объект может быть недостижим из текущих веток, но оставаться удержанным журналом либо ещё не удалённым обслуживанием. Сроки очистки настраиваются; журнал — полезный запас восстановления, а не бессрочная резервная копия. Если файл никогда не добавляли и не фиксировали, его рабочие байты могли вообще не стать объектом Git. Восстановить их по журналу коммитов невозможно.

git clean -n -d показывает неизвестные файлы и каталоги, которые обычная очистка затронула бы; -n означает пробный просмотр без удаления, -d включает каталоги. -f разрешает реальное удаление, -x добавляет также игнорируемые пути, -X выбирает только игнорируемые. Игнорируемый каталог может содержать единственный локальный набор данных, поэтому критерий «не отслеживается» не означает «не нужен». Учебные опыты с удалением выполняют только в отдельном созданном для них каталоге.

Коммит исчез из log

После reset предыдущий коммит не виден обычным git log. Достаточно ли этого, чтобы объявить его физически удалённым?

Разбор

Нет. Log начал обход с новой вершины и больше не достигает старого потомка. Нужно отдельно проверить идентификатор, другие ссылки и reflog. Графовая недостижимость и физическая очистка — разные события.
