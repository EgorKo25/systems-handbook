Большой репозиторий: LFS, частичная история и разрежённые файлы

Размер рабочей папки, объём объектного хранилища и полнота доступной истории — разные величины. Несколько механизмов сокращают разные части этой системы. Выбор начинается с определения нужных данных и условий работы без сети, а заканчивается проверкой фактически доступных объектов.

Четыре независимых вопроса

Сначала установите, какие коммиты доступны, какие объекты этих коммитов уже находятся локально, какие отслеживаемые файлы развёрнуты на диске и где хранятся крупные полезные данные. Один флаг clone редко отвечает на все четыре вопроса. Пустая папка в рабочем дереве может означать разрежённую выборку, неинициализированный подмодуль либо ошибку получения; причины требуют разных действий.

Shallow clone ограничивает историю на уровне коммитов. Partial clone допускает отсутствие части объектов с возможностью получения по требованию. Sparse checkout ограничивает развёртываемые рабочие пути. Git LFS меняет представление определённых файлов: внутри обычной истории остаётся маленький указатель, а полезные байты сохраняются отдельно. Эти решения можно сочетать, если понимать сумму их условий.

Выполненные далее опыты используют Git 2.43 и локальные временные репозитории. Настоящий Git LFS в среде проверки отсутствовал: его фильтры и сервер не запускались. Для LFS показаны устройство и собственный проверенный пример указателя. Поддержка конкретных версий и серверов должна проверяться отдельно, особенно перед подготовкой автономной копии.

Цена крупного файла в обычной истории

Большой двоичный файл становится объектом blob так же, как маленький исходник. Новое содержимое создаёт новое логическое состояние. Упаковка способна экономить место за счёт сжатия и отличий, но результат зависит от самих данных. Уже сжатые архивы или существенно изменившиеся изображения могут храниться дорого даже при небольшом числе файлов текущей версии.

Удаление файла новым коммитом не вырезает его из старых деревьев. Поэтому чистая текущая папка способна сопровождаться большим объёмом истории. Перед выбором решения измерьте размер рабочих данных, объектного хранилища и число нужных версий. Перепаковка и переписывание истории — разные действия с разными последствиями для читателей и восстановления.

git count-objects -vH
git rev-list --count HEAD
git rev-parse --is-shallow-repository

Первая команда показывает сведения об объектах и упаковках в читаемых единицах. Она не описывает автоматически весь внешний кэш LFS, рабочие копии подмодулей и результаты сборки. Число коммитов тоже не является оценкой размера: один коммит способен добавить очень большой blob. Сопоставляйте показатели с вопросом, который хотите решить.

LFS: указатель и полезные байты

Для нашего собственного содержимого из шестнадцати байтов demo large bytes указатель формата LFS выглядит так:

version https://git-lfs.github.com/spec/v1
oid sha256:7647292a308442841d1b61b2bec2b89ffec1d6b47eb4c7b2b76f69f731581368
size 16

В конце каждой строки находится перевод строки. Поле version обозначает формат указателя, oid — алгоритм и хеш полезного содержимого, size — его длину в байтах. Этот SHA-256 относится к внешнему содержимому. Идентификатор Git-объекта, хранящего сам текст указателя, вычисляется отдельно по правилам Git и может использовать другой формат хеширования.

Фильтр подготовки, clean, получает обычные байты, сохраняет их в локальном LFS-хранилище и отдаёт Git текст указателя. При извлечении smudge или соответствующий длительно работающий фильтр получает указатель и возвращает полезные байты, при необходимости получая их с сервера. В результате рабочий файл и сохранённый blob могут намеренно различаться.

Передача большого объекта имеет собственный договор: клиент сообщает идентификатор и размер, а сервер возвращает действия загрузки или получения с адресами и необходимыми данными запроса. Сам коммит с указателем не доказывает успешного сохранения полезных данных у получателя. Поэтому проверка релиза должна проверять оба хранилища и возможность чтения результата в чистой среде.

Если фильтр отключён или содержимое недоступно, поведение зависит от режима: в папке может остаться указатель либо извлечение завершится ошибкой. Наличие файла ожидаемого имени недостаточно. Проверяйте ожидаемый формат, размер и хеш полезных данных. Статус Git может при этом корректно описывать сохранённый указатель, а приложению нужен совсем другой набор байтов.

Закрепить границу истории: shallow clone

git clone --no-local --depth=1 ../source shallow-demo
git -C shallow-demo rev-parse --is-shallow-repository
git -C shallow-demo rev-list --count HEAD

В проверенном двухкоммитном источнике результат содержал одну доступную вершину в обходе истории и признак shallow, равный true. Ключ --depth=1 задаёт глубину от выбранной вершины. --no-local здесь исключает местную оптимизацию клонирования, которая иначе могла бы проигнорировать ограничение глубины при копировании соседнего пути.

У границы истории Git знает о специальном ограничении обхода. Это не то же самое, что случайно потерянный родительский объект в обычной копии. Для некоторых исследований предков, сравнения со старой версией и поиска причины понадобится расширение полученной истории. Команда fetch --deepen=ЧИСЛО увеличивает имеющуюся глубину, а --unshallow используется при подходящем полном источнике для снятия ограничения.

Ограничение истории полезно для одноразовой задачи, которой действительно нужны только свежие состояния. Если последующие шаги регулярно догружают предков, первоначальная экономия может превратиться в дополнительные запросы и задержки. Не используйте короткое число коммитов как доказательство полноты резерва.

Получить дерево, отложить содержимое: partial clone

Для реального локального опыта создайте голое зеркало учебного source и включите поддержку фильтра только в нём. В source должны быть два коммита, файл src/app.txt и отдельный docs/guide.txt. Все адреса относятся к известным соседним папкам.

git clone --bare source filter-remote.git
git -C filter-remote.git config --local uploadpack.allowFilter true
git clone --no-local --no-checkout --filter=blob:none \
  filter-remote.git partial-demo
git -C partial-demo config --get remote.origin.promisor
git -C partial-demo rev-list --objects --all --missing=print

Фильтр blob:none просит изначально не передавать содержимое файлов. Коммиты и нужные деревья позволяют исследовать структуру. Параметр --no-checkout не разворачивает сразу рабочие файлы, для которых иначе могли бы немедленно понадобиться отложенные blob. Настройка promisor обозначает источник, обещающий предоставить такие объекты позднее.

В выполненном опыте настройка была true, а список обхода содержал записи с начальным вопросительным знаком — отсутствующие объекты в режиме --missing=print. Это существенно сильнее предположения «флаг принят, значит всё сработало». Если сервер не поддерживает фильтрацию или игнорирует запрос, фактический объём может оказаться иным.

git -C partial-demo show main:docs/guide.txt

При чтении нужного blob Git получил его из локального обещающего источника и показал guide. Это lazy fetch — получение в момент необходимости. Пример не требовал интернета, но дополнительное обращение к другому процессу и хранилищу действительно произошло. На удалённом сервере к нему добавились бы сеть, проверка доступа и доступность сервиса.

Обещанное отсутствие требует отличать от повреждения полной копии. У partial clone есть служебные признаки, позволяющие Git учитывать намеренно недополученные данные. Простое ручное удаление blob из обычного репозитория такую модель не создаёт. Также нельзя превратить неполную копию в полную одним удалением настройки promisor: от этого отсутствующие байты не появляются.

Развернуть только нужные рабочие пути

git clone source sparse-demo
git -C sparse-demo sparse-checkout init --cone
git -C sparse-demo sparse-checkout set src
git -C sparse-demo sparse-checkout list
git -C sparse-demo show HEAD:docs/guide.txt

Здесь исходный clone обычный и полный для полученных ссылок. Sparse checkout задаёт, какую часть отслеживаемого дерева представить рабочими файлами. Режим cone описывает выбор каталогами с определёнными правилами включения их предков и соседних файлов. Его не следует понимать как произвольный набор исключений .gitignore.

В нашем опыте рабочий docs/guide.txt исчез из развёрнутого набора, а чтение через show HEAD:docs/guide.txt по-прежнему успешно возвращало содержимое. Нужный объект уже был в хранилище. Исчезновение этого рабочего файла не было подготовленным удалением из истории. Служебные признаки индекса и конфигурация sparse позволяют Git различать эти ситуации.

Для возврата полного рабочего дерева предусмотрено sparse-checkout disable. На полном клоне это требует места для дополнительных файлов. В сочетании с partial clone разворачивание может также запросить отсутствующие объекты. Сначала сохраните собственные правки и проверьте status: переключение набора путей не должно становиться способом потерять незавершённую работу.

Как сочетать механизмы и измерять результат

Результат выборки и требования инструментов

Представим, что рабочая папка после sparse стала значительно меньше, а служебное хранилище почти не изменилось. Это ожидаемое наблюдение для полного клона: настройка выбрала развёрнутые пути, но не переписала коммиты и не удалила их blob. Сначала измерьте отдельно каждую область. Удаление объектов ради совпадения двух размеров нарушило бы модель полного хранилища.

Есть дополнительная оптимизация sparse index: он способен описывать часть исключённых каталогов компактнее, чем отдельная запись на каждый файл. Это уменьшает некоторые затраты работы с индексом. При этом инструменты, предполагающие полностью развёрнутый индекс, могут иметь ограничения или потребовать его расширения. Совместимость внешних средств проверяется на используемой версии; сама настройка разрежённого рабочего дерева не доказывает готовности всей цепочки сборки.

Проект может собирать один компонент, но читать общие заголовки, генераторы или правила из другого каталога. Набор sparse должен покрывать фактические зависимости. Если сборка перестала находить файл, исследуйте её объявленные входы и выбранные пути. Автоматическое получение blob не создаст рабочий файл вне выбранного набора там, где инструмент ожидает обычный путь файловой системы.

Похожая ловушка возникает при первом включении LFS для уже существующего большого файла. Новое правило атрибутов управляет дальнейшим представлением, но старые обычные blob могут оставаться в истории. Чтобы изменить прошлые версии, требуется отдельная миграция с проверкой ссылок, хранения и доступности данных. Сначала определите, нужна ли экономия будущих копий или только более удобная текущая рабочая версия.

Можно иметь полный граф коммитов, частично полученные blob и маленькое рабочее дерево одновременно. Можно иметь неглубокую историю с полностью полученными файлами выбранной вершины. LFS добавляет ещё один слой внешнего содержимого. Для эксплуатационного решения полезно выписать каждый слой и отдельно отметить, какие действия потребуют повторного обращения к источнику.

Измеряйте полную стоимость задачи: первоначальное получение, последующее извлечение файлов, обращение к старой версии, сборку и подготовку следующего запуска. Сравнивайте объём переданных данных, размер на диске и время ожидания при одинаковом наборе действий. Меньший первый clone может сопровождаться большим суммарным ожиданием при множестве мелких отложенных запросов.

Перед поездкой без сети проверьте сценарий в условиях отсутствующего источника: нужные версии, подмодули и крупные данные должны уже находиться локально. Подготовленное рабочее дерево не гарантирует доступности старой истории, а полная обычная история указателей LFS не гарантирует полезного содержимого. Для надёжной автономной копии часто проще заранее получить полный нужный набор и проверить его чтение.

Первичные источники: модель partial clone, параметры clone, sparse checkout, формат и фильтры LFS, договор передачи LFS. LFS-сервер и его фильтры здесь не испытаны; свойства partial, shallow и sparse подтверждены собственными локальными Git-опытами.
