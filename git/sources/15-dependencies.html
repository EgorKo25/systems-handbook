Зависимости: от диапазона версий до установки без сети

Версия исходников ещё не определяет весь состав программы. Разберём, кто выбирает сторонние пакеты, чем решение отличается от его фиксации и почему одинаковые названия версий могут приводить к разным окружениям.

Разрешение зависимостей — задача с ограничениями

Предположим, наше приложение использует библиотеку A и библиотеку B. A требует C версии не ниже 2, но ниже 4; B требует C не ниже 3, но ниже 5. Пересечение допускает C третьей основной версии. Пакетный менеджер должен найти совместимый набор, учитывая опубликованные версии и их метаданные. Этот процесс называют разрешением зависимостей, а выполняющий его компонент — решателем. Он не угадывает, какая версия наиболее удобна бизнесу: он удовлетворяет формальным ограничениям и собственной стратегии выбора.

Зависимость A является прямой, когда её объявляет приложение. C является транзитивной: её потребовал кто-то из выбранных пакетов. Если A обновилась и изменила требования к C, фактический состав программы меняется через два ребра графа. Поэтому проверять только прямые зависимости недостаточно. Несовместимые ограничения нельзя надёжно исправить случайной очередностью установки: окружение, в котором один пакет перезаписал другой, не становится логически совместимым. Следует обновить согласованный набор, выбрать другую допустимую версию либо изолировать несовместимые компоненты в разные процессы.

При разрешении учитывается среда назначения. Пакет может предоставлять готовую сборку для одной архитектуры и только исходники для другой. Условная зависимость способна действовать лишь на Windows или лишь в определённой версии Python. Поэтому фраза «у нас один файл зависимостей» ещё не означает, что две платформы получат одинаковые файлы. Для каждой поддерживаемой среды нужен определённый результат решения и проверка его установки.

Файл фиксации полезен, потому что отделяет выбор новых версий от обычной установки. Но форматы разных менеджеров не взаимозаменяемы. В Python файл требований с точными версиями и хешами может играть роль зафиксированного набора для определённой среды; это ещё не универсальный lockfile, который описывает все платформы и сам механизм разрешения. Установка должна использовать поддерживаемую конкретным инструментом процедуру, а не просто наличие файла с обнадёживающим именем.

Зеркало — локальная копия или посредник хранилища. Оно улучшает доступность и контроль доступа, однако изменяемое зеркало, продолжающее подтягивать «самое новое», не фиксирует версии. Хеш SHA-256 проверяет соответствие файла ожидаемым байтам, но подменённые пакет и список его хешей согласуются между собой. Одобрение списка должно происходить отдельно: через проверяемое изменение в репозитории, контролируемого поставщика либо принятую процедуру подписи.

Пример установки из подготовленного набора

В учебном Python-практикуме сторонних зависимостей нет: это позволяет исследовать сборку без скрытого доступа к сети. Следующая схема нужна для отдельного проекта, у которого зависимости уже есть. Пусть requirements.lock содержит весь разрешённый набор с точными версиями и настоящими SHA-256 каждого разрешённого файла. Хеши следует получать от проверенных файлов; строки с выдуманными значениями применять нельзя.

python3 -m pip download --only-binary=:all: --require-hashes \
  -r requirements.lock -d wheelhouse
python3 -m pip install --no-index --find-links=wheelhouse \
  --only-binary=:all: --require-hashes -r requirements.lock

-m pip связывает запуск менеджера с выбранным Python. download только получает файлы; -r читает требования из указанного файла; -d задаёт каталог скачивания. --only-binary=:all: разрешает только готовые пакеты wheel для всех имён; если подходящего wheel нет, команда должна завершиться ошибкой. Это сознательное ограничение примера: сборка из исходного дистрибутива потребовала бы дополнительно зафиксировать её инструменты и зависимости.

Во второй строке install выполняет установку. --no-index запрещает искать пакеты в индексах; --find-links=wheelhouse указывает локальный источник файлов. --require-hashes требует проверки разрешённых хешей; в таком режиме все зависимости должны быть описаны достаточно строго. Этот флаг не заполняет пропущенные хеши автоматически. Команды предполагают, что pip уже доступен, а набор готовился для совместимой среды назначения. Подготовка на Linux x86-64 не обещает готовности набора для Windows ARM.

Проверять автономность следует на свежем окружении, без ранее установленных пакетов и с отключённым доступом к сети. Установка на привычной машине способна молча использовать уже установленную зависимость и создать ложное ощущение полноты. Сохраните рядом с набором версию Python, платформу, версию установщика и команду подготовки. После установки python3 -m pip check проверяет заявленную совместимость установленных требований; она не запускает поведенческие тесты приложения и не доказывает отсутствие уязвимостей.

Сборочные зависимости тоже являются зависимостями

Готовый wheel и исходный пакет — разные входы. Из исходников может запускаться сборочный механизм, которому нужны свои библиотеки, компилятор, заголовки системы и сетевые ресурсы. Отдельное изолированное окружение сборки помогает избежать случайных локальных пакетов, но само по себе не делает набор инструментов неизменным и не запрещает сеть. Если сборщик в процессе получает актуальный вспомогательный пакет без фиксации, заявленный состав приложения остаётся неполным.

Тот же принцип действует вне Python. Генератор документации, модуль сборки интерфейса, версия компилятора и системная библиотека входят в причинную цепочку результата. Контейнер с тегом latest не фиксирует среду: завтра по этому имени могут оказаться другие байты. Даже идентификатор образа не фиксирует внешний URL, к которому обращается запущенная внутри сборка. Сначала перечисляют используемые источники, затем решают, какие из них можно убрать, сохранить локально либо включить в проверяемый состав.

Отдельный случай Maven: управление версией не добавляет библиотеку

В POM секция dependencies объявляет используемые зависимости. Секция dependencyManagement задаёт управляемые версии и параметры для случаев, когда зависимость действительно понадобится; одно присутствие там обычно не добавляет библиотеку в набор проекта. Родительский POM или импортируемая согласованная модель версий могут централизовать правила. Это помогает согласовать модули, но не делает видимый POM полным списком получаемых байтов. Изучают результирующую модель и фактическое дерево разрешённых зависимостей.

Нужно различать библиотеку приложения и плагин сборки. Оба могут скачиваться из репозиториев Maven и иметь свои зависимости, но выполняют разную роль. Для автономной компиляции может хватить JAR библиотек приложения, а для тестирования не хватить самого Surefire, его провайдера, родительского POM или другого плагина. Профиль, активируемый только в выпускном запуске, способен добавить новый набор. Поэтому заполнение локального репозитория одним удачным вызовом compile ещё не доказывает автономность clean verify с другими профилями.

Флаг Maven -o, или --offline, запрещает сетевое разрешение репозиториев самим Maven; он не создаёт недостающие файлы. Цель Dependency Plugin dependency:go-offline предназначена для предварительного разрешения зависимостей проекта, плагинов и отчётов. Её применение — подготовка, после которой проверяют именно нужный маршрут в отключённой среде с выбранными профилями. Пользовательский тест или плагин всё ещё может самостоятельно открывать сетевое соединение: офлайн-режим менеджера не является общесистемным сетевым запретом. Адреса зеркал и права доступа в настройках также сохраняют и объясняют отдельно от исходного кода.

Как обновлять зависимости без замораживания навсегда

Фиксация отделяет предсказуемую повседневную сборку от контролируемого обновления. Для обновления создают отдельное изменение: пересчитывают решение, сравнивают добавленные и удалённые пакеты, проверяют совместимость и прогоняют тесты. Один прямой пакет способен привести десятки транзитивных изменений; полезно объяснять эту разницу в обзоре. Проверяют и изменение формата данных, сетевого поведения, лицензий и требований к платформе, если они существенны для продукта.

После утверждения сохраняют новый набор и делают его доступным всем агентам. Старый набор не удаляют раньше срока, в течение которого требуется воспроизвести или восстановить старый выпуск. Иначе история Git останется, а получение нужных зависимостей станет невозможным. При этом хранить бесконечно все промежуточные кэши не требуется: сохраняют одобренные исходные материалы и доставленные артефакты по установленной политике, а производные ускоряющие данные можно пересоздать.

Полезный диагностический вопрос звучит так: «Изменилась ли программа, если коммит остался прежним?» Ответ может быть положительным, когда поменялись разрешённые зависимости, настройки установки или доступный системный пакет. Поэтому идентичность выпуска связывает коммит с точным набором зависимостей и описанием среды. Следующая глава добавит более строгую цель: одинаковыми должны оказаться не только названия пакетов, но и байты результата.
