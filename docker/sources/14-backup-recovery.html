Резерв и восстановление: образ, конфигурация и согласованные данные

Архив полезен, когда из него можно получить проверенное состояние на отдельной цели. Разделим идентичность программы, постоянные данные, конфигурацию и допустимую потерю времени.

Сначала определить договор восстановления

RPO, recovery point objective, — допустимая потеря истории данных по времени. RTO, recovery time objective, — целевое время возврата нужной функции. Если копия сделана в 12:00, а последняя запись перед отказом — в 12:17, восстановление только этой копии может потерять 17 минут. RTO включает получение среды, файлов и секретов, восстановление, запуск и проверки, а не одну длительность распаковки tar.

Для нашего счётчика определим простой договор: копия содержит все подтверждённые записи до остановки единственного писателя. После восстановления GET /counter возвращает сохранённое значение, одна новая запись увеличивает его на единицу, /version соответствует записанному образу. Такой набор сильнее проверки наличия файла, но не является тестом любой будущей схемы приложения.

Какие части сохраняют отдельно

Образ сохраняет исполняемые файлы и настройки по умолчанию. Compose и паспорт задают runtime-конфигурацию: environment, mounts, порты, лимиты, политику запуска. Volume содержит постоянные данные. Ключи и пароли хранят отдельно с соответствующими правами и резервом. Наконец, процедура восстановления определяет порядок и критерии. Потеря любого обязательного элемента может сделать остальные архивы бесполезными.

Полная копия VM может быть удобной точкой возврата, если VM корректно остановлена либо применяется согласованный механизм снимка. Но она не заменяет понимание прикладной копии: может оказаться слишком большой, несовместимой с новой платформой или содержащей ненужные секреты. Восстановление одной службы из её данных требует меньшего объёма и даёт отдельное доказательство.

Подготовить инструменты и каталог назначения

Для примера нужен заранее полученный доверенный TOOLS_IMAGE с sh, GNU tar и средствами назначения владельцев. Его выбирают, закрепляют по digest и проверяют до автономного дня. Это вспомогательный административный образ, а не скрытая зависимость scratch-службы. Для каждого поколения выбирают новый каталог внутри /srv/study/docker-world/backups, например с зафиксированным временем копии, и создают его на daemon-хосте в своей VM; в удалённом context локальный каталог клиента не подставляется автоматически.

BACKUP_DIR ниже содержит абсолютный путь на этом сервере, TOOLS_IMAGE — закреплённый административный образ. Сначала убедитесь, что оба значения относятся к вашему стенду. Если используется Compose, останавливают через него именно сервис echo, чтобы не перепутать с похожим контейнером. Для запуска из команд предыдущих глав применяют эквивалентную остановку конкретного имени.

docker --context study compose -f labs/echo/compose.yaml stop echo

docker --context study run --rm --network none --user 0:0 \
  --mount type=volume,src=study-data,dst=/data,readonly \
  --mount type=bind,src="$BACKUP_DIR",dst=/backup \
  "$TOOLS_IMAGE" sh -ceu \
  'test ! -e /backup/counter.tar; cd /data; tar --numeric-owner -cf /backup/counter.tar .'

docker --context study compose -f labs/echo/compose.yaml start echo

Перед архивированием писатель остановлен, поэтому копируемый набор не меняется от штатной работы. Источник смонтирован readonly, сеть вспомогательному процессу не предоставляется. Административный UID нужен для сохранения нужных метаданных; приложению эти права не выдаются. sh -c выполняет строку, -e прекращает цепочку при ошибке, -u считает обращение к незаданной переменной ошибкой. У tar -c создаёт архив, -f задаёт файл. Предварительное test требует отсутствия прежнего counter.tar, сохраняя хорошую копию от случайной перезаписи. Про GNU tar и другой tar нельзя обещать одинаковые опции без проверки.

Архив образуется на сервере через bind mount. Его проверяют там: список записей, размер, контрольная сумма и возможность чтения. Затем копируют во второе независимое место, сохраняя доверенную ожидаемую сумму. Единственная копия рядом с томом на том же диске не защищает от потери этого диска. Конкретный перенос по SSH выполняют на уровне отдельного защищённого канала.

Восстановить на другую цель

docker --context study volume create study-restore-data

docker --context study run --rm --network none --user 0:0 \
  --mount type=volume,src=study-restore-data,dst=/data \
  --mount type=bind,src="$BACKUP_DIR",dst=/backup,readonly \
  "$TOOLS_IMAGE" sh -ceu \
  'cd /data; tar --numeric-owner -xpf /backup/counter.tar'

docker --context study run -d --name study-restore-check \
  --pull=never --env APP_DATA_DIR=/data \
  --mount type=volume,src=study-restore-data,dst=/data \
  --publish 127.0.0.1:18081:8080 "$APP_IMAGE"

Целевой том должен быть новым и пустым именно для этой проверки; существующее содержимое не смешивают с архивом. Флаг tar -x извлекает, -p восстанавливает права, numeric-owner опирается на числовые идентификаторы. Восстанавливают только собственный проверенный архив: распаковка произвольного чужого tar административным процессом добавляет риски путей и метаданных.

Основная служба продолжает использовать study-data, проверочная — study-restore-data и другой внешний порт 18081. Запросы выполняют с Docker-хоста либо через заранее настроенный SSH-туннель. Сверяют /version, начальный GET /counter и следующий POST. Полученные при проверке изменения относятся только к восстановленной цели. Записывают длительность всей процедуры и отклонение от договора RPO/RTO.

Проверить отрицательные варианты

Нечисловое содержимое, пустой файл или число вне диапазона uint64 обнаруживаются при старте, а не молча обнуляют историю. Изменение допустимого числа 12 на 13 синтаксически корректно; приложение без собственного контрольного эталона его не распознаёт. Для такого случая нужна сверка с доверенной записью и проверка целостности копии. Неправильный владелец может позволить чтение и запретить последующую запись; поэтому одной проверки GET мало. Не тот image может успешно стартовать, но читать другой формат. Запуск в другой context способен показать пустой объект с тем же именем. Каждому такому варианту соответствует проверка идентичности, прав или данных.

Нельзя тренировать повреждение на единственном основном томе: копия для негативного опыта имеет собственное имя и паспорт. Это не автоматический сброс продолжаемого стенда — основное состояние сохраняется, а отдельный опыт намеренно изолирует предмет проверки. Проверочный контейнер после записи результата можно остановить; удаление вспомогательных объектов выполняется адресно после подтверждения, что они больше не нужны.

Если внутри PostgreSQL

Для работающей БД приведённая копия произвольного каталога недостаточна. Используют согласованный pg_dump либо физический backup с непрерывным набором WAL в соответствии с целью. Сохраняют необходимые роли и параметры доступа; при физическом восстановлении учитывают совместимость версии и формат данных. Volume решает размещение, а PostgreSQL — протокол согласованности и восстановления. Эти границы разобраны в отдельном томе.

Если несколько сервисов должны восстановиться к общему логическому состоянию, два корректных отдельных дампа ещё не гарантируют согласованную пару. Нужна определённая точка остановки операций, журнал, идемпотентное повторение либо иной договор приложения. Формулировка «все контейнеры поднялись» не является конечным критерием возврата системы.

Первичные источники: копии volumes, GNU tar, прикладное и физическое восстановление PostgreSQL.
