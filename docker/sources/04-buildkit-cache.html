BuildKit: граф сборки, контекст, кэш и секреты

Сборка выполняет вычисление над набором входов. Скорость растёт, когда неизменившиеся результаты используются повторно; правильность сохраняется, только если понятны границы этих входов.

Dockerfile — вход системы сборки

Dockerfile описывает шаги получения образа. BuildKit, современная подсистема сборки, преобразует описание в граф операций: получение базовых образов, чтение контекста, исполнение команд, копирование результатов и экспорт. Buildx — клиентский интерфейс управления такими сборками и builders, экземплярами сборщика. Наличие нового клиента ещё не доказывает, что выбранный builder имеет нужные возможности и локальное состояние.

docker --context study buildx ls
docker --context study buildx inspect --bootstrap
docker --context study buildx build --progress=plain \
  --load --tag study/echo:lesson1 .

ls показывает builders и их драйверы. inspect --bootstrap может запустить компоненты builder и потому является действием, а не только чтением метаданных. --progress=plain даёт последовательный текст для сравнения шагов; --load выбирает загрузку результата в хранилище выбранного Engine в поддерживаемом варианте. При удалённом context этот Engine находится на сервере, а не обязательно на компьютере клиента. У отдельного builder с драйвером docker-container результат иначе может остаться только в кэше сборщика. --tag назначает имя, точка выбирает контекст текущего каталога.

Контекст — отдельная граница файлов

Build context, контекст сборки, — предоставляемый набор входных файлов. Указание -f deploy/Dockerfile выбирает описание, но не переносит автоматически корень контекста в deploy. Команда docker build -f deploy/Dockerfile . по-прежнему использует текущий каталог. Путь источника COPY рассматривается относительно доступного контекста или явно выбранной стадии, а не произвольного домашнего каталога клиента.

Файл .dockerignore исключает ненужные входы до их использования сборщиком. В собственном Go-проекте исключают .git, временные результаты, локальные журналы и файлы с секретами, если они не являются обязательными входами. Передача секретного файла уже является нарушением выбранной границы даже тогда, когда финальная стадия его не копирует. Удалённый builder получает входы на другой машине.

.git
out/
backups/
*.log
.env
secrets/

Этот пример не универсален: если сборка намеренно читает Git-метаданные, исключение .git требует другого способа передать зафиксированную версию. Правильный критерий — явный перечень нужных входов. Большой контекст увеличивает передачу и вероятность лишних изменений; оценка сборки должна отдельно показывать время передачи, получения баз и собственно компиляции.

Почему одинаковая команда может использовать старый результат

Для обычного RUN система не проверяет каждый раз, изменился ли внешний сайт, к которому обращалась команда. Если команда и релевантные входы совпали, прежний результат может быть повторно использован. Поэтому RUN apt-get update, взятый из кэша через месяц, не означает получение сегодняшнего списка пакетов. Если обновление списка и установка находятся в разных слоях, можно объединить устаревший список и новый запрос установки. Осмысленная операция получения пакетов должна иметь согласованные входы и политику обновления.

Для COPY содержимое и существенные метаданные входных файлов участвуют в проверке кэша; одно изменение mtime, времени модификации, не обязано сбрасывать кэш. Не следует делать вывод «файл обновлён» только по touch. При изменении ранней зависимости линейной цепочки последующие результаты требуют пересчёта; независимые ветви многостадийного графа при этом могут оставаться пригодными.

В Go полезно сначала копировать go.mod и имеющийся go.sum, получить зависимости, затем копировать исходники и компилировать. Тогда изменение обработчика не заставляет заново получать весь набор модулей. Однако команда должна соответствовать реальному проекту: проект без сторонних модулей может не иметь go.sum; слепой COPY отсутствующего файла завершится ошибкой ещё до Go.

Три разных кэша

Кэш результата операции BuildKit позволяет вообще не повторять шаг. Cache mount, временно подключаемый сохраняемый кэш, помогает внутри повторно выполняемого шага: например, Go может использовать ранее скомпилированные пакеты. Наконец, кэш модулей Go хранит полученные входы зависимостей. Очистка одного уровня не обязательно очищает другие. --no-cache запрещает использование результатов шагов, но не означает автоматическую загрузку нового базового образа и не обязан обнулить содержимое cache mounts.

RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -mod=readonly -trimpath -o /out/echo ./cmd/echo

Оба mount существуют для сборочного шага и не становятся каталогами финального образа от самого факта подключения. -mod=readonly запрещает требуемое изменением разрешения зависимостей редактирование go.mod; -trimpath убирает пути файловой системы из определённых метаданных бинарника. Эти флаги Go не делают внешние входы автоматически доверенными. Подробности выбора пакетов и ключей Go-кэша разобраны в томе Go.

Внешний cache-to/cache-from переносит пригодные записи между сборщиками. Он требует собственных прав доступа, формата, платформы и бюджета хранения. Кэш ускорения не должен быть единственной копией выпускаемого образа. Более того, доступ на запись в общий кэш и доступ на выполнение недоверенного Dockerfile требуют отдельной модели доверия; экономия минут не оправдывает безусловное смешивание чужих входов.

Секрет не равен build argument

ARG TOKEN и ENV TOKEN=... подходят для несекретных параметров, но не для передачи пароля. Значения могут попасть в метаданные, историю, происхождение сборки или журнал команды. Secret mount передаёт чувствительный файл определённому RUN на время исполнения. Он устраняет необходимость сохранять этот файл в обычном слое, но команда всё равно способна напечатать секрет или скопировать его в результат.

RUN --mount=type=secret,id=repo_token,required=true \
    /usr/local/bin/fetch-private-input /run/secrets/repo_token

docker buildx build --secret id=repo_token,src=/ЛИЧНЫЙ/ПУТЬ \
  --load --tag study/echo:lesson1 .

Это схема интеграции: fetch-private-input обозначает собственную проверенную программу и в готовом лабораторном проекте отсутствует. required=true требует источник секрета. Нельзя рассчитывать, что изменение значения секрета само сбросит кэш: для повторного получения изменённого результата используют явный несекретный идентификатор версии входа или ограниченную отмену кэша. SSH mount передаёт возможность обращаться к агенту SSH; он также требует доверия к выполняемой команде.

Как измерить ускорение без самообмана

Сравнивают четыре режима: холодный builder, повтор без изменений, изменение одного Go-файла и изменение зависимостей. Для каждого фиксируют builder, версии, платформу, наличие базовых образов и кэшей, сеть, лимиты CPU/памяти и итоговый digest. Одна «сборка за 2 секунды» может целиком состоять из повторного использования результата, ничего не говоря о скорости компилятора.

Пример: передача контекста 18 с, получение базы 30 с и компиляция 12 с дают 60 с без перекрытия. Уменьшение компиляции вдвое экономит 6 с, а удаление лишних архивов из контекста может сэкономить 15 с. В реальном графе часть операций перекрывается; итог определяется критическим путём, а не суммой всех строк. Сначала находят этот путь, затем меняют один фактор и сравнивают серии запусков.
