Образ по частям: OCI, манифест, слои и изменяемая файловая система

Разберём, какие байты передаются при pull, почему tag может измениться, как удаление выглядит в слое и почему образ не является резервной копией контейнера.

Ссылка, содержимое и выбранная платформа

В ссылке registry.example.invalid/team/echo:lesson1 есть адрес реестра, имя репозитория и tag — метка. Реестр, registry, хранит и выдаёт объекты образов по протоколу. Tag — изменяемая ссылка на объект: сегодня lesson1 может указывать на одни байты, завтра на другие. Ссылка ...@sha256:... закрепляет digest, криптографический идентификатор содержимого определённого объекта. Один и тот же tag на двух хостах после разных моментов загрузки не гарантирует одинаковый результат.

Digest необходимо читать вместе с типом объекта. OCI index — индекс вариантов — содержит дескрипторы манифестов для разных платформ. Манифест одного варианта указывает конфигурацию и упорядоченные слои. Дескриптор включает media type, digest и размер. Media type сообщает формат содержимого, digest проверяет байты, размер помогает обнаружить несоответствие передачи. У многоархитектурной ссылки digest индекса и digest выбранного linux/amd64-манифеста различаются.

Платформа включает ОС, архитектуру и, когда нужно, вариант. Индекс может дать linux/arm64 и linux/amd64, но ни один из этих Linux-вариантов не обещает работать как Windows-процесс. На Windows с Linux-контейнерами выбирается Linux-окружение Desktop. Эмуляция набора команд процессора — отдельная технология с другой ценой исполнения; наличие индекса не включает её автоматически.

Конфигурация — тоже содержимое образа

Конфигурационный JSON хранит настройки по умолчанию: окружение, рабочий каталог, пользователя, Entrypoint, Cmd и сведения о корневой файловой системе. Эти параметры участвуют в идентичности объекта. Одинаковые файлы с разным пользователем запуска — уже различающиеся образы. Параметр EXPOSE описывает предполагаемый порт, но не создаёт правило публикации на хосте. Значение ENV доступно запущенному процессу и не должно использоваться как защищённое хранилище пароля.

docker --context study image inspect study/echo:lesson1
docker --context study image inspect --format \
  '{{json .Config}}' study/echo:lesson1
docker --context study image inspect --format \
  '{{json .RootFS.Layers}}' study/echo:lesson1
docker --context study image history --no-trunc study/echo:lesson1

Inspect показывает локально известный объект выбранного сервера. --no-trunc не сокращает поля history; история полезна для понимания сборки, но сама по себе не является полным достоверным исходником Dockerfile. У некоторых инструкций меняется только конфигурация, без нового файлового слоя. Поэтому число строк history, число архивных слоёв и число инструкций не обязаны совпадать.

Слой описывает изменение

Представим нижний слой с /app/config.txt=A и /app/old.txt=B. Следующий слой заменяет config на C, создаёт new и удаляет old. Это не копия всего диска: архив изменения содержит новые версии нужных объектов и обозначение удаления. OCI использует whiteout — специальное имя, указывающее, что нижний объект должен быть скрыт; для old это .wh.old.txt. Непрозрачный каталог, opaque directory, дополнительно скрывает прежних нижних потомков каталога.

Применение слоёв идёт снизу вверх. Whiteout не является обычным пользовательским файлом в готовой объединённой файловой системе. Он сообщает сборщику этой системы, что прежняя запись больше не видна. При этом байты old остаются в более раннем неизменяемом слое. Поэтому удаление секрета следующей инструкцией не удаляет его из истории образа и не уменьшает уже опубликованный нижний архив до нуля.

Команда RUN install-tool && use-tool && remove-temporary в одном шаге может не оставить временный файл в итоговом изменении, если файл появился и исчез внутри шага. Отдельные RUN сначала сохраняют нижний результат. Но объединять всё в один гигантский шаг тоже не самоцель: теряются удобные границы кэша и диагностики. Разделяют частоту изменения входов, размеры результатов и потребность в повторном использовании.

Сжатый digest и diff ID отвечают на разные вопросы

Слой часто передаётся как сжатый tar-архив. Digest дескриптора проверяет именно передаваемый blob, двоичный объект. Diff ID в конфигурации вычисляется по несжатому потоку слоя. Разные параметры сжатия могут изменить digest blob при одинаковом несжатом содержимом. Нельзя сравнивать эти два поля как доказательство порчи лишь потому, что оба начинаются с sha256.

Tar содержит не только содержимое файлов, но и метаданные: пути, типы, права, владельцев, ссылки и временные отметки согласно формату. Повторная сборка одинаковой программы может дать другое содержимое архива из-за метаданных. Доказательство одинакового бинарника и доказательство одинакового образа имеют разный охват. Это подробно связывается с воспроизводимостью Go в главе доставки.

Из слоёв получается корень процесса

В типичном Linux-пути OverlayFS объединяет нижние неизменяемые каталоги и верхнюю изменяемую область. Чтение неизменённого файла получает нижние данные. При модификации нижнего файла может понадобиться copy-up — перенос нужной версии в верхнюю область, после чего запись идёт туда. Реальная гранулярность и оптимизации зависят от файловой системы и параметров; нельзя обещать, что изменение одного байта всегда записывает ровно один байт на диск.

Поэтому база данных в изменяемом слое — плохая исходная эксплуатационная привычка: жизненный цикл данных становится связан с удалением контейнера, а путь записи получает дополнительные особенности снимков. Именованный volume позволяет вынести данные за этот жизненный цикл, но не автоматически обеспечивает резерв, распределённость или согласованность. Отдельное монтирование также может скрыть каталог образа: файл существует в нижнем корне, но процесс видит другой каталог поверх него.

Overlay2 и containerd snapshotter

Overlay2 — классический драйвер хранения Docker. Snapshotter, механизм снимков containerd, — другой интерфейс управления файловыми состояниями; один из его вариантов использует overlayfs. Поэтому слова overlayfs и overlay2 не обозначают взаимозаменяемые уровни конфигурации. В Engine 29 свежая установка по умолчанию использует containerd image store; обновлённая с прежней версии может сохранить прежнюю подсистему (backend).

Containerd store способен хранить как передаваемые сжатые объекты, так и распакованные снимки; расчёт свободного места должен учитывать оба представления. Переключение backend может скрыть старые образы и контейнеры из текущего представления, хотя байты остаются на диске. Такое наблюдение не лечат немедленной очисткой каталога: сначала сверяют конфигурацию и предыдущий backend. Перенос data-root Docker не является доказательством переноса отдельного корня containerd.

В проверенной документации containerd image store также указан как несовместимый с daemon-режимом userns-remap. Это отдельный rootful-режим отображения идентификаторов; из такого ограничения не следует общий запрет rootless. Перед сочетанием опций сверяют таблицу поддержки конкретной версии.

Что именно занимает место

docker system df -v показывает учёт Docker с детализацией. Сумма виртуальных размеров нескольких образов завышает фактическое место, если у них общие слои. Наоборот, сумма только скачанных сжатых архивов может занижать распакованное хранилище. К этому добавляются изменяемые слои контейнеров, журнал, BuildKit cache, тома и сама файловая система. Показатель reclaimable означает потенциально освобождаемое в выбранном представлении, а не обещание точно такого прироста свободных байтов после любого prune.

Учебный расчёт: три образа разделяют базу 80 МиБ и добавляют по 12 МиБ. Без дополнительных копий полезный объём уникальных распакованных слоёв — 80 + 3 × 12 = 116 МиБ; сумма размеров образов — 276 МиБ. Эти числа не включают сжатые blobs, метаданные и верхние записи. Отдельно измеряют фактическую занятость файловой системы и inode — её записи о файлах. Миллион маленьких файлов может исчерпать inode раньше байтов.

Спецификации: манифест OCI, формат изменений, OverlayFS, containerd image store.
