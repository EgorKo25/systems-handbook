Доставка: registry, digest, платформы и происхождение

Готовый образ нужно доставить, узнать среди других и связать с проверенными исходниками. Целостность, происхождение и допустимость запуска отвечают на разные вопросы.

Что передаёт push

Registry принимает объекты по определённому протоколу: содержимое слоёв, конфигурацию, манифесты и индексы. Благодаря адресации по содержимому уже имеющийся blob не обязательно загружать заново. Финальная ссылка tag указывает на выбранный опубликованный объект. Повторный push под тем же tag может изменить его назначение, если политика реестра это допускает; поэтому «проверяли lesson1 вчера» недостаточно для сегодняшнего запуска.

Pull получает описание и нужные объекты выбранной платформы, проверяя их digest. В обычном полном pull локальное наличие образа устраняет необходимость снова скачивать те же данные, но не доказывает вечную доступность remote tag. Lazy pulling, отложенное получение содержимого некоторыми snapshotters, имеет дополнительные условия и не подходит как молчаливое обещание офлайн-готовности. Автономный комплект проверяют реальной загрузкой на отключённой тестовой среде.

docker --context study image inspect --format \
  '{{json .RepoDigests}}' study/echo:lesson1
docker --context study buildx imagetools inspect \
  registry.example.invalid/team/echo:lesson1

RepoDigests показывает известные локальному серверу связи с опубликованными digest. У локально собранного, ещё не опубликованного образа список может быть пуст. Его локальный image ID и удалённый manifest/index digest нельзя автоматически считать одним объектом. imagetools inspect обращается к образу в реестре и показывает платформенную структуру; это не то же самое, что исследовать только локальные слои.

Проверить digest — ещё не выбрать доверенного автора

Хеш обнаруживает несоответствие байтов ожидаемому содержимому. Если злоумышленник заменил и образ, и присланный рядом ожидаемый digest, сравнение может успешно подтвердить чужой образ. Нужен доверенный канал получения ожидаемой идентичности, политика подписей или другой явно выбранный механизм происхождения. Подпись также имеет смысл только при доверии к ключу, личности и допустимому процессу выпуска.

Не путайте аутентификацию при login с доказательством безопасности содержимого. Успешный вход в реестр разрешает операции определённой учётной записи. Образ этой учётной записи может содержать уязвимую библиотеку, неверную конфигурацию или намеренно вредную программу. Доверие к издателю, результаты анализа и ограничения runtime остаются независимыми слоями решения.

Для автоматизации применяют минимальный scope токена, область разрешённых действий и docker login --password-stdin с защищённым источником ввода; не помещают токен в аргументы процесса, журнал или общедоступный .env. Выбранное credential store, хранилище данных доступа клиента, проверяют отдельно. Кодирование значения в base64 в конфигурационном файле не является шифрованием.

Provenance и SBOM

Provenance, сведения о происхождении сборки, описывают входы и процесс получения результата: исходник, инструмент, параметры и связанные идентичности в объёме выбранного формата. SBOM, software bill of materials, — перечень компонентов программного состава. Они помогают расследовать, какие зависимости вошли в выпуск, но не доказывают автоматически отсутствие вредного поведения и не заменяют тесты приложения.

docker --context study buildx build \
  --build-arg GO_IMAGE="$GO_IMAGE" \
  --platform linux/amd64,linux/arm64 \
  --provenance=mode=min --sbom=true \
  --tag registry.example.invalid/team/echo:lesson1 --push labs/echo

Это дальнейший сетевой вариант при подготовленном личном registry и нужных возможностях builder. --push экспортирует результат в реестр, --provenance выбирает представление происхождения, --sbom запрашивает соответствующую аттестацию. Сканер SBOM может сам требовать дополнительных образов и сети; его готовность входит в автономный комплект. Наш базовый лабораторный запуск такой реестр не разворачивает.

Attestation, сопровождающее утверждение о результате, может изменить структуру опубликованного index. Поддержка сохранения таких объектов зависит от image store и экспортера: старое классическое хранилище имеет ограничения. Успешная локальная сборка с --load не подтверждает, что все сопутствующие аттестации доступны потребителю. Проверяют фактически опубликованную структуру и политику её чтения.

Несколько архитектур — несколько доказательств исполнения

Многоархитектурный образ связывает несколько платформенных манифестов. Для Go без cgo перекрёстная компиляция часто проста: compiler работает нативно, а GOOS/GOARCH выбирают машинный код цели. Но успешно созданный arm64-файл ещё не проверил системные вызовы, возможности CPU, поведение сети и файловой системы реального arm64-сервера.

Эмуляция может помочь выполнить проверки, но она добавляет программный слой и может заметно замедлять сборку либо скрывать аппаратные различия. Если требуется сравнить скорость, используют нативные машины и фиксируют семейство CPU, лимиты и фон. Сопоставление времени build под QEMU со временем нативного amd64 не измеряет только качество компилятора.

Подготовить автономную доставку

docker --context study image save --output echo-lesson1.tar \
  study/echo:lesson1
sha256sum echo-lesson1.tar > echo-lesson1.tar.sha256
docker --context target image load --input echo-lesson1.tar
docker --context target image inspect study/echo:lesson1

save передаёт архив образов в файл на стороне клиента; load читает его оттуда и загружает на выбранный target. Это отличается от bind mount, чей путь относится к daemon-хосту. До переноса проверяют вместимость носителя, особенности файловой системы и контрольную сумму. Сумма, лежащая рядом с архивом, удобна для обнаружения случайной порчи; подлинность ожидаемого значения фиксируется доверенным паспортом.

Сохранённый архив не включает именованные volumes, активные соединения и память процесса. docker export снимает файловое представление контейнера с иными свойствами, не сохраняя полный исходный договор image metadata и mounts. Его не подставляют вместо save/load для воспроизводимого выпуска. После переноса сверяют не только tag, но конфигурацию, платформу, ожидаемый локальный ID и контрольный запуск без сети.

Продвинуть тот же результат

Выпуск связывает исходный коммит, проверенный digest, runtime-конфигурацию, миграцию данных и запись о принятии. Повторно собрать «из тех же исходников» в рабочей среде — другой процесс с возможными новыми внешними входами. Предпочтительнее продвигать уже проверенный образ по идентичности, затем отдельно применять нужную конфигурацию. При возврате версии надо иметь доступ к прежнему образу и знать совместимость прежнего кода с текущими данными.

Хранение в registry не является резервом пользовательского тома, а локальный кэш образов не является политикой сохранения выпусков. Сроки хранения, неизменность нужных идентичностей, права удаления и проверка восстановления должны быть явными. Самостоятельная эксплуатация реестров артефактов разбирается в отдельном томе.
