Данные: volume, bind mount, tmpfs и согласованная запись

Размещение файла определяет, что переживёт пересоздание. Согласованность определяет, можно ли использовать пережившие байты. Разберём обе стороны без предположения, что постоянный том уже является резервом.

Три файла с одинаковым содержимым

Пусть приложение записало строку в /root-note, /data/note и /tmp/note. Первый путь находится в изменяемом слое контейнера, второй — в именованном томе, третий — в tmpfs. При обычном stop/start того же объекта первый и второй сохраняются, а tmpfs при остановке теряет содержимое. При удалении и создании нового объекта первый исчезает, второй доступен при повторном подключении того же тома. Поведение определяется монтированиями, а не словами root, data и tmp в имени.

Volume — управляемый Docker объект хранения, bind mount — подключение явно выбранного пути на хосте, tmpfs — временная файловая область в памяти с возможными особенностями swap. Именованный volume локального драйвера обычно привязан к одному серверу; одинаковое имя study-data на двух серверах обозначает две разные области. Само слово volume не обещает репликацию, отдельный физический диск или резервирование.

Блок разбирает один вариант настройки. Перед реальным выполнением нужны подготовленный образ и свободные выбранные имя/порт; связный маршрут без конфликтующих повторных запусков находится в заключительном практикуме.

docker --context study volume create study-data
docker --context study volume inspect study-data
docker --context study run -d --name study-echo --pull=never \
  --mount type=volume,src=study-data,dst=/data \
  --publish 127.0.0.1:18080:8080 study/echo:lesson1

src именует объект на сервере, dst выбирает видимый процессу путь. Inspect показывает драйвер и место/параметры подключения. Локальный путь Mountpoint используют для понимания размещения и процедур администратора, а не для произвольного редактирования внутренностей работающей БД. Если приложение non-root, каталог должен иметь подходящего владельца заранее; Docker не угадывает нужный UID из содержимого Go-кода.

Монтирование скрывает прежний каталог

В образе может существовать /data/example.txt. Подключение непустого тома поверх /data скрывает прежнее содержимое этого пути. Оно не было обязательно удалено из образа, просто другое монтирование стало видимым сверху. Для пустого тома Docker по умолчанию может первоначально скопировать содержимое каталога образа в том. Опция volume-nocopy запрещает такое заполнение. Bind mount не обещает той же инициализации.

Отсюда диагностический случай: приложение после обновления «не видит новый конфиг из образа». Если конфиг находится под прежним volume, новый нижний файл скрыт старым сохранённым содержимым. Пересборка образа не является миграцией пользовательских данных. Процедура должна отдельно решить, какие файлы являются значениями по умолчанию, какие — постоянной конфигурацией, и кто имеет право их изменять.

Bind mount находится на daemon-хосте

docker --context study run --pull=never \
  --mount type=bind,src=/srv/study/docker-world/config,dst=/config,readonly \
  study/echo:lesson1

Источник этого mount ищется на машине сервера study. Если клиент запущен в Windows, Docker не отправляет автоматически содержимое такого Linux-пути с клиентского диска. Интеграция Desktop с файловой системой основной ОС — отдельная функция. Для обычного remote daemon чтение файла проекта клиентом и монтирование пути сервером являются разными операциями.

В обычном режиме --mount type=bind требует существующего источника и при ошибке пути сообщает отказ; сокращённый -v может создать каталог вместо ожидаемого отсутствующего файла. Новые версии добавляют и специальные варианты создания для --mount, поэтому ориентируются на явно выбранные опции. Для учебных конфигов полезнее предварительно проверить тип, права и хеш файла и не скрывать опечатку автоматическим созданием.

Bind mount на запись позволяет контейнерному процессу изменять данные хоста в пределах эффективных прав. readonly задаёт режим этого подключения. Существующие вложенные монтирования и рекурсивная read-only-семантика имеют условия ядра и параметров; один флаг не заменяет чтение реального дерева mount. Объяснять защиту следует на фактически используемом простом каталоге.

Пользователь и первый доступ

Для локального volume сначала выбирают числовой UID приложения. В новом пустом учебном томе подготовительный контейнер с известным инструментом может создать нужный каталог и назначить владельца 10001:10001. Это отдельная административная операция над этим томом, а не постоянный запуск приложения от root. После неё основной процесс получает только нужный каталог и свои обычные права.

Не исправляйте любой permission denied через chmod -R 777. Сначала проверяют эффективный UID/GID, права каждого компонента пути, режим mount и возможную LSM-политику. Если rootless использует отображение идентификаторов, внешний владелец может выглядеть иначе. Сравнение имён пользователей по отдельности не определяет итоговое право.

Записано в приложение — не значит сохранено на носителе

Успешный write обычно подтверждает передачу байтов ядру. Они могут находиться в page cache, файловом кэше памяти. Системный вызов fsync запрашивает предусмотренное файловой системой доведение данных и метаданных до устойчивого состояния. Его цена зависит от накопителя, очередей, файловой системы и гарантий нижнего уровня. Наличие SSD не делает эту операцию бесплатной, а Docker volume не меняет договор write в договор fsync.

Для замены одного небольшого файла часто используют последовательность: записать временный файл в том же каталоге; fsync временного файла; закрыть; atomically rename — атомарно заменить имя; fsync каталога. Атомарность имени означает отсутствие промежуточного частично заменённого имени для наблюдателя, но не универсальную транзакцию сразу нескольких файлов. Сбой между шагами может оставить разные допустимые состояния; приложение должно знать, какие из них оно принимает.

Даже после устойчивой записи HTTP-ответ может потеряться. Клиент увидит ошибку и повторит запрос, хотя первый уже изменил данные. Это проблема идемпотентности операции: повтор с тем же смыслом должен иметь определённую судьбу. Тестовый счётчик следующей главы намеренно показывает эту границу; он не выдаётся за транзакционную БД.

Согласованность резервной копии

Архив каталога работающей PostgreSQL может смешать файлы разных моментов. Том сохраняет доступ к файлам, но не сообщает архиватору границы транзакции и нужные WAL. Для БД применяют собственный протокол дампа, физического backup и журнала из тома PostgreSQL. Для простой службы можно остановить запись на известной границе и копировать неподвижный набор. Snapshot файловой системы без прикладной координации в лучшем случае приближает аварийную копию в соответствии с гарантиями всех слоёв.

Согласованная копия двух сервисов сложнее двух отдельных архивов: ссылка на объект и сам объект должны соответствовать допустимому моменту. Копия конфигурации, учётных данных, данных и журнала восстановления имеет совместный договор. Именно поэтому объектное хранение и распределённые БД требуют самостоятельного разбора, а не инструкции «подключите volume».

Ресурсная цена и перенос

Измеряют скорость и задержку того типа операций, который выполняет приложение: последовательное чтение, случайную запись, fsync, создание множества маленьких файлов. Сравнение большой последовательной копии с транзакционным журналом неверно. В Desktop bind mount может проходить через дополнительный протокол обмена между ОС, тогда как именованный volume остаётся внутри Linux-VM; результат теста одного пути не переносится на другой.

Перенос на другой компьютер включает содержимое тома, права и метаданные, версию приложения, совместимую схему и проверенный способ восстановления. docker image save не содержит volume. docker export не превращает контейнер с mounts в согласованный полный backup. Практика восстановления должна завершаться чтением ожидаемых данных на отдельной цели, а не строкой «архив создан».
