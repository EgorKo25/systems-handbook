Полномочия: пользователь, capabilities, seccomp и rootless

Изолированное представление системы не означает отсутствия доступа к ней. Защита строится из нескольких независимых ограничений, каждое из которых нужно связать с действиями приложения.

Права процесса и права управляющего

Управляющий API Docker способен запускать процессы и подключать к ним данные хоста. Поэтому сокет daemon — чувствительный объект. Передать контейнеру /var/run/docker.sock означает передать возможность управления соответствующим сервером, если процесс имеет права обращения. Даже подключение сокета с файловым флагом read-only не превращает API в интерфейс только чтения: ограничение монтирования файла не фильтрует отправляемые по сокету запросы.

Граница контейнера не заменяет границу доверия между участниками. Выполнение чужого Dockerfile даёт чужому коду возможность исполняться в сборочной среде; выдача BuildKit-секрета позволяет этому коду его прочитать. Если CI-задание имеет управляющий сокет rootful Engine, считать его безопасным только из-за запуска «в контейнере» нельзя. VM, отдельный сервер и ограниченные учётные данные решают другие части этой задачи.

USER задаёт идентификаторы, а не новую личность хоста

USER 10001:10001 в Dockerfile задаёт пользователя по умолчанию. --user при запуске может его переопределить. UID, user identifier, — числовой идентификатор пользователя; GID аналогично идентифицирует группу. Этот идентификатор проверяется ядром при доступе к файлу; имя из /etc/passwd — удобное отображение и источник дополнительных сведений. Файл в bind mount с владельцем UID 1000 не становится доступным UID 10001 от одинакового человеческого имени student в двух системах.

В обычном rootful режиме без remapping root контейнера имеет UID 0 в общей идентификационной системе хоста, хотя дополнительные ограничения существенно сужают его действия. User namespace создаёт отображение внутреннего UID на иной внешний диапазон. Userns-remap оставляет daemon привилегированным, отображая идентификаторы контейнеров. Rootless помещает также сам daemon в непривилегированную пользовательскую границу. Эти режимы различаются последствиями возможного захвата управляющего процесса.

Capabilities дробят полномочия root

Linux capabilities, наборы отдельных привилегий, разделяют некоторые исторические полномочия суперпользователя: например, управление сетевой конфигурацией или специальные файловые операции. --cap-drop=ALL убирает предусмотренный набор возможностей, --cap-add возвращает конкретную необходимую. Обычная HTTP-служба на порту 8080 часто обходится без дополнительных capabilities. Из этого не следует, что любой бинарник корректно работает с тем же набором: потребность проверяется по системным действиям.

Порт 80 часто называют привилегированным, но соответствующий порог и разрешения зависят от сетевого namespace и конфигурации Linux. Поэтому объяснение «non-root всегда запрещён любой порт ниже 1024» слишком категорично. Для учебной службы выбираем 8080 и не делаем низкий порт условием работы. Публикация внешнего 18080 вообще не требует, чтобы приложение слушало 18080 внутри.

Seccomp и LSM проверяют другую грань

Seccomp — механизм ограничения системных вызовов процесса по выбранному фильтру. Штатный профиль Docker допускает определённый набор вызовов и ограничивает опасные варианты. Он не проверяет бизнес-смысл HTTP-запроса и не шифрует данные. Отказ Operation not permitted может быть связан с seccomp, capability, LSM или обычными правами; одинаковый текст не определяет причину.

LSM, Linux Security Module, — интерфейс дополнительных механизмов контроля доступа, например AppArmor или SELinux. Их правила могут запрещать действие, разрешённое обычными правами файла. --security-opt no-new-privileges=true ограничивает получение дополнительных привилегий через последующее исполнение, например setuid-программы. Он дополняет USER, но не заменяет выбор доступных файлов и сокетов.

Блок разбирает один вариант настройки. Перед реальным выполнением нужны подготовленный образ и свободные выбранные имя/порт; связный маршрут без конфликтующих повторных запусков находится в заключительном практикуме.

docker --context study run -d --name study-echo \
  --pull=never --user 10001:10001 \
  --cap-drop ALL --security-opt no-new-privileges=true \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  --memory 256m --cpus 1 --pids-limit 128 \
  --publish 127.0.0.1:18080:8080 study/echo:lesson1

Эта конфигурация подходит только варианту службы без записи в корень. Для записи счётчика дополнительно подключают подготовленный /data. --read-only запрещает запись в корневую файловую систему контейнера, но не делает автоматически read-only все отдельные mounts. Tmpfs предоставляет временный каталог с ограниченным размером; noexec запрещает предусмотренный прямой запуск с него, nosuid отключает эффект setuid на этой области. Временные данные всё равно занимают ресурсы и могут оказаться в swap в зависимости от системы.

Не используем --privileged как средство «пока заработает». Он существенно расширяет права и доступ к устройствам, меняя модель безопасности. Точный набор эффектов зависит от платформы. Для диагностики сначала устанавливают, какое действие получает отказ, затем выбирают минимальное конкретное изменение и проверяют отрицательный сценарий: ненужное действие всё ещё должно быть запрещено.

Rootless начинается с другой установки

По официальной инструкции rootless проверяют uidmap, программы newuidmap/newgidmap и назначенные диапазоны /etc/subuid и /etc/subgid. Эти программы позволяют сформировать допустимое отображение нескольких идентификаторов; обычное совпадение имени пользователя не создаёт такой диапазон. Ограничения дистрибутива на user namespaces также входят в предусловия.

После подготовки поставки dockerd-rootless-setuptool.sh install выполняют от выбранного обычного пользователя. Она создаёт пользовательскую systemd-службу и context rootless. Управляют ею через systemctl --user; системная systemctl status docker проверяет другой сервис. Типичные пути — сокет в /run/user/UID/docker.sock, конфигурация в ~/.config/docker, данные в ~/.local/share/docker. Их записывают фактически, с учётом XDG-переменных и версии.

Запуск пользовательской службы после выхода пользователя требует отдельного решения о lingering — сохранении пользовательского менеджера systemd. Его настройка меняет поведение машины и выполняется осознанно в своей VM. Rootless не является флагом, который моментально превращает текущие rootful-контейнеры и их диски в новый сервер. Рядом могут существовать два daemon с независимыми объектами и одинаковыми именами контейнеров.

Что rootless меняет для упражнения

Управление памятью и CPU требует поддерживаемого cgroup v2 и корректного делегирования контроллеров; без этого некоторые параметры могут не работать как ожидается. Публикация низких портов, ICMP, host network и пропускная способность пользовательской сети имеют дополнительные условия. Проверяют docker info, фактические ограничения и путь пакетов, а не копируют rootful-вывод как эталон.

Rootless сокращает последствия захвата daemon до доступных ему пользовательских прав, но домашний каталог этого пользователя, его ключи и доступные сервисы всё равно ценны. Изоляция не оправдывает подключение всего домашнего каталога на запись. Для Go-службы перечисляют конкретные файлы конфигурации, каталог данных и сетевые зависимости; всё остальное остаётся недоступным без отдельной потребности.

Проверить конфигурацию на отказ

После ограничения прав проверяют нормальный запрос, запись только в разрешённый /data и отказ записи в корень. Затем проверяют отсутствие управляющего сокета, ненужных устройств и внешней публикации. Наличие сканера уязвимостей не подтверждает эти свойства: сканер анализирует известные проблемы содержимого, а dangerous mount может использовать полностью обновлённый образ.
