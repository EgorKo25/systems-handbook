Docker: понимать границы, сохранять состояние и доказывать результат

Контейнер начинается с обычного процесса, но его запуск связывает формат образа, ядро Linux, сеть, хранение и полномочия управляющего сервиса. Том последовательно разбирает эту цепочку на собственной Go-службе.

Что именно предстоит собрать

Цель — получить личную среду, в которой можно объяснить происхождение работающих байтов, путь запроса, место записи данных и последствия остановки. Образ служит входом запуска; контейнер добавляет собственное изменяемое состояние и конфигурацию. Если заново создать контейнер, эти части могут получить разные судьбы. Фраза «всё лежит в Docker» скрывает именно те различия, которые важны при отказе.

Чтение начинается с установки, а не с готового приглашения терминала. Дома с интернетом читатель находит официальный источник, выбирает поддерживаемую комбинацию ОС и архитектуры, готовит пакеты, образы и контрольные суммы. Перед следующим упражнением используется тот же экземпляр Engine — серверной части Docker — и тот же каталог учебного проекта. Новый раздел не подразумевает очистку прежних ошибок. Исправление ошибки становится частью истории стенда.

Основной путь — Docker Engine в выделенной Linux-машине Ubuntu 24.04, настоящей либо виртуальной. Виртуальная машина, VM, исполняет собственное ядро гостевой ОС; Linux-контейнеры одного Engine используют ядро того Linux, где работает сервер. Docker Desktop на Windows обычно предоставляет такое Linux-окружение через дополнительный слой виртуализации. Это полезный продукт, но он не превращает Docker Engine в переносимую программу без установки и следов. На рабочем компьютере действуют разрешения владельца компьютера. Книга на флэшке открывается без Engine; реальные опыты требуют заранее разрешённой среды.

Команды в теоретических главах показывают отдельные варианты конфигурации. Единственная последовательность реального развёртывания собрана в заключительном практикуме; повторно запускать все варианты с одним именем и портом подряд не требуется. Сначала устанавливают инструмент, затем читают механизм, потом выполняют связный маршрут с сохранением состояния.

Три масштаба одного объяснения

Сначала рассматриваем объект: например, манифест образа с перечнем слоёв. Затем механизм: как снимок файлов становится корнем процесса. После этого наблюдение: какой вывод покажет docker image inspect, что останется после docker rm и как отличить отсутствие файла от неверного монтирования. Так команды получают смысл, а название технологии перестаёт подменять причинную цепочку.

Сокращения раскрываются при появлении и повторяются в словаре. OCI, Open Container Initiative, — семейство открытых спецификаций образа, доставки и запуска; эти спецификации не определяют всю прикладную политику Docker. API, application programming interface, — программный интерфейс сообщений между компонентами. CLI, command-line interface, — интерфейс командной строки. Конкретный CLI обращается к выбранному серверу; местонахождение приглашения Bash ещё не доказывает местонахождение данных контейнера.

Часть оснований уже разобрана глубже в других томах: изоляция Linux, NAT и фильтрация пакетов, компилятор и сборка Go, согласованное восстановление PostgreSQL. Здесь эти механизмы соединяются в работающую систему. Kubernetes, объектные хранилища и управление секретами получат собственные тома: знание запуска контейнера не заменяет знания их протоколов и состояния.

Что фиксировать перед первым запуском

Паспорт технологии хранится рядом с учебными заметками, а секреты — отдельно с ограниченными правами. В паспорт записывают источник и время загрузки, полные версии клиента, сервера, containerd и плагинов, архитектуру, способ проверки пакетов, имя Docker context, адрес сервера, тип хранения и пути данных. Следующие поля — команды запуска, остановки, журналы, контрольные проверки и способ восстановления. Контрольная сумма одного архива проверяет его байты; достоверность ожидаемой суммы зависит от источника.

Нужен и паспорт приложения: Git-коммит, версия Go, платформа сборки и исполнения, идентификатор образа, внешний порт, каталоги или тома данных, владелец файлов, ожидаемый ответ и доступные зависимости. Два проекта с одинаковым YAML и разными переменными окружения могут описывать разные системы. Поэтому сохраняют также результат нормализации конфигурации, предварительно исключив чувствительные значения.

Граница проверок этого издания

Текст опирается на официальные спецификации и документацию, проверенные при подготовке. Docker на компьютере читателя не устанавливался, реальные контейнеры и сетевые правила этого тома автоматически не запускались. Проверяемые локальные модели в labs/ демонстрируют ограниченные алгоритмы; они не являются эмулятором ядра и не измеряют скорость будущего хоста. Команды реального стенда сопровождаются предусловиями и наблюдениями, которые читатель должен получить сам.

Версионные примеры ориентированы на Linux Engine 29 и современный плагин docker compose; конкретные исправляющие выпуски выбирают в официальном репозитории перед установкой. Свежая установка и обновление старого сервера могут использовать разные подсистемы хранения. Именно поэтому вывод docker info важнее предположения по одному номеру версии.
