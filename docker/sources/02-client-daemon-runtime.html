Клиент, сервер и runtime: кто действительно запускает процесс

Проследим docker run от разбора аргументов до процесса Linux, затем отделим соединение клиента, состояние контейнера и жизнь приложения.

Команда обращается к конкретному серверу

Исполняемый файл docker — клиент. Он разбирает параметры и отправляет запрос управляющему сервису dockerd. Протокол API содержит операции создания, запуска и исследования контейнеров. Если клиент находится на ноутбуке, а context указывает на VM, процесс и файлы возникают на VM. Каталог, из которого набрана команда, не меняет этой границы.

Блок разбирает один вариант настройки. Перед реальным выполнением нужны подготовленный образ и свободные выбранные имя/порт; связный маршрут без конфликтующих повторных запусков находится в заключительном практикуме.

docker context ls
docker context inspect study
docker --context study version
docker --context study info

context ls перечисляет локально сохранённые точки управления; звёздочка отмечает выбранную. inspect показывает параметры подключения. Глобальный --context study относится к клиенту и ставится перед подкомандой. version разделяет Client и Server: версия клиента может выводиться даже при недоступном сервере. info требует ответа сервера и описывает его окружение. Ошибка Cannot connect ещё не говорит, что Engine не установлен: возможны неверный context, сокет, права, SSH или остановленная служба.

Для своего уже доступного по SSH Linux-хоста можно создать docker context create study --docker host=ssh://student@lab.example.invalid. Адрес здесь учебный, его заменяют адресом личного сервера. Сначала отдельно проверяют SSH и отпечаток ключа узла. Учётная запись на сервере должна иметь разрешение обращаться к его Docker; SSH не отменяет эту проверку. Перед командами смотрят также DOCKER_HOST и DOCKER_CONTEXT в окружении: они могут изменить выбор назначения. Явный --context в опытах делает выбор обозримым, но пароль и закрытый ключ в команды не подставляют.

От create к start

docker run в обычном пути объединяет создание и запуск. Сначала сервер разрешает ссылку образа с учётом политики pull — получения из реестра. Затем создаёт объект контейнера: идентификатор, конфигурацию процесса, монтирования, сеть, политику перезапуска и изменяемую файловую область. После этого запускает процесс. Между созданием и исполнением может случиться ошибка; наличие строки в docker ps -a не доказывает, что приложение работало.

docker --context study create --name study-echo \
  --pull=never --publish 127.0.0.1:18080:8080 \
  study/echo:lesson1
docker --context study start study-echo
docker --context study ps -a --filter name=study-echo
docker --context study inspect study-echo

Образ study/echo:lesson1 будет собран в главе о Go. --pull=never запрещает неожиданную загрузку; при отсутствии образа команда завершается ошибкой. --name закрепляет удобное имя объекта на этом сервере. --publish описывает порт хоста 18080 и контейнера 8080, ограничивая вход адресом loopback хоста. create ещё не запускает приложение; start запускает тот же объект с прежней конфигурацией и изменяемой файловой областью. Для смены образа обычно создают новый объект.

Управление исполнением имеет несколько уровней

Dockerd координирует пользовательские объекты, сеть, тома и интерфейс управления. Containerd обслуживает жизненный цикл контейнерных задач и, в соответствующей конфигурации, содержимое образов и снимки файловой системы. Низкоуровневый runtime, обычно runc, применяет описание исполнения OCI: готовит изоляцию, монтирования, ограничения и запускает процесс. Shim — промежуточный служебный процесс — помогает наблюдать задачу и её потоки, не превращая основной daemon в непосредственного родителя, от которого должна зависеть вся жизнь приложения.

Это функциональная цепочка, а не требование увидеть ровно одну одинаковую строку ps во всех версиях. Реальные имена shim, runtime и дополнительные прокси зависят от поставки и режима. Нельзя на основании наличия процесса containerd объявить, что именно им управляет выбранный Docker: на машине могут работать несколько независимых экземпляров. Сопоставляют сокеты, конфигурацию, systemd unit и идентификатор контейнера.

OCI Runtime Specification описывает окружение процесса, а не готовую политику безопасности приложения. Можно корректно запустить контейнер с опасным монтированием хоста. Runtime исполнил конфигурацию; ошибку допустили при выборе полномочий. Аналогично сохранённый OCI-образ не содержит работающее TCP-соединение или состояние памяти уже запущенного процесса.

Потоки, терминал и фон

Стандартный ввод, вывод и поток ошибок — файловые дескрипторы 0, 1 и 2. -i сохраняет stdin открытым; -t выделяет псевдотерминал. Это разные действия: -it подходит интерактивной shell, но машинному обмену двоичными данными терминал может мешать из-за преобразований и объединения потоков. Фоновый режим -d отсоединяет клиент; внутри контейнера приложение по-прежнему должно оставаться основным процессом переднего плана.

Команда docker run -d IMAGE sh -c 'service app start' может завершить shell сразу после запуска фонового дочернего процесса. Жизненный цикл контейнера привязан к основному процессу; сервис не должен рассчитывать на фоновый режим установочного скрипта. Для Go обычно правильнее непосредственно выполнить бинарник. Отсоединение клиента attach, завершение SSH-сеанса, остановка приложения и удаление объекта — четыре разных события.

docker exec запускает дополнительный процесс в существующем работающем контейнере; docker attach подключает потоки основного. Exec не создаёт новый образ и не записывает исправление в Dockerfile. Изменённый через exec файл может исчезнуть при пересоздании. Контейнер без shell не становится неисправным от отказа exec ... sh: такой исполняемой программы в его файловой системе может не быть.

Состояния, коды и наблюдения

Created означает, что объект создан; running — основная задача считается работающей; exited — она закончилась; restarting — применяется политика перезапуска. Состояние процесса и health status различаются: приложение может работать, но не проходить проверку работоспособности. Docker сам по себе не обязан перезапускать контейнер лишь за статус unhealthy.

docker --context study inspect --format \
  '{{json .State}}' study-echo
docker --context study logs --tail 50 --timestamps study-echo
docker --context study wait study-echo

--format применяет шаблон клиента к объекту; json сохраняет структуру. В .State ищут ExitCode, Error, OOMKilled и временные отметки, но связывают их с журналом ОС. logs --tail 50 ограничивает объём, --timestamps добавляет время. wait ждёт окончания контейнера и выводит его код. Код 125 у docker run обычно относится к ошибке запуска со стороны Docker, 126 — к невозможности исполнить выбранную команду, 127 — к ненайденной команде; прочие коды часто приходят от приложения.

Число 137 обычно соответствует завершению сигналом SIGKILL по соглашению 128 + номер сигнала 9. Само по себе оно не доказывает нехватку памяти: контейнер могли принудительно остановить. Нужны OOMKilled, счётчики cgroup и системный журнал. Код 0 подтверждает успешное завершение в принятом приложением смысле, но не наличие обязательного файла в постоянном хранилище.

Что считать подтверждением

После запуска собственной службы нужны четыре независимые проверки: сервер знает нужный контейнер и образ; процесс действительно работает; нужный сокет доступен по ожидаемому пути; запрос приложения возвращает осмысленный результат. При записи нужна пятая: данные переживают предусмотренный сценарий остановки и восстановления. Один вывод идентификатора от docker run -d подтверждает только успешную начальную операцию управления.
