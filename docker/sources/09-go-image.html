Go в образе: стадии, ABI, сигналы и границы воспроизводимости

Создадим образ своей программы, понимая каждый переход от исходников до процесса. Маленький финальный образ полезен лишь тогда, когда сохранены нужные зависимости и возможности диагностики.

Исходники доступны целиком

Каталог labs/echo содержит собственную службу без внешних Go-модулей. /health отвечает на локальную проверку, /version возвращает версию, /greet формирует JSON, /counter при настроенном APP_DATA_DIR читает и увеличивает сохраняемый счётчик. Приложение не подключается к PostgreSQL или Redis. Это намеренно небольшой предмет изучения; добавление БД в дальнейшей практике требует настоящей прикладной интеграции.

Режим /echo check сам выполняет HTTP-запрос к локальному /health с тайм-аутом. Поэтому финальному scratch-образу не нужны curl и shell для проверки здоровья. Пригодность этой проверки ограничена: она подтверждает ответ HTTP-обработчика, но не доказывает возможность следующей записи на диск или доступность внешней зависимости. Содержание probe, проверки, выбирается по конкретной цели.

ABI, application binary interface, — двоичный договор передачи аргументов, размещения значений и вызовов. Совпадение архитектуры само по себе не доказывает совместимость всех внешних библиотек и загрузчика.

Выбрать и закрепить сборочную среду

На официальной странице образа Go выбирают поддерживаемый toolchain и вариант платформы. До автономного дня получают образ, записывают digest и проверяют go version внутри выбранной среды. Пример Dockerfile принимает GO_IMAGE явно и не имеет скрытого latest по умолчанию. Если нет согласованного аргумента, сборка должна дать понятный отказ вместо случайного выбора компилятора.

docker --context study buildx build --progress=plain \
  --build-arg GO_IMAGE="$GO_IMAGE" \
  --platform linux/amd64 --load \
  --tag study/echo:lesson1 labs/echo

Переменная GO_IMAGE содержит подготовленную ссылку на доверенный образ, предпочтительно с digest. Она не является секретом. --platform задаёт целевую платформу; --load выбирает локальный экспорт; последний путь — контекст исходников. Команда показана из каталога тома docker; при работе внутри labs/echo последним аргументом будет точка. Путь -f и корень контекста нельзя менять независимо без проверки COPY.

Почему две стадии

В стадии build находятся Go toolchain и исходники. Она использует --platform=$BUILDPLATFORM, то есть исполняет компилятор на платформе builder, а TARGETOS и TARGETARCH задают целевую программу. Тесты сначала выполняются в нативной сборочной среде. Это не тест целевого arm64-исполнения, если builder amd64. Для такого доказательства нужен отдельный запуск на реальном целевом CPU либо явно учтённая эмуляция.

CGO_ENABLED=0 отключает путь cgo, взаимодействия с программами и библиотеками на C, для данной сборки. Программа использует только поддерживаемую стандартную библиотеку, поэтому её Linux-бинарник можно перенести в scratch — пустую начальную файловую систему. Для программы с cgo и внешними библиотеками такой вывод был бы неверен: понадобятся динамический загрузчик, согласованная стандартная библиотека C, libc и другие зависимости либо сознательно настроенная статическая линковка. Архитектуру и зависимости бинарника проверяют средствами изучения ELF, формата исполняемых объектов Linux, из тома Go.

Scratch не содержит /bin/sh, пакетного менеджера, сертификатов CA, часовых поясов и пользовательских баз автоматически. Наш сервер отдаёт обычный HTTP и не требует внешней проверки TLS. Если добавить HTTPS-клиент, потребуется доверенное хранилище CA и выбранная стратегия его обновления. Если добавить именованные часовые пояса или поиск пользователя, нужно исследовать соответствующие входы. «Статический» не означает «вообще не читает файлов».

Пользователь и данные

Финальный USER 10001:10001 задаёт непривилегированный числовой идентификатор. В простом запуске без APP_DATA_DIR доступны /health и /greet; счётчик отвечает 503, потому что постоянное хранилище не настроено. Для счётчика нужен /data с правом записи этого UID. Подключение пустого тома не обязано автоматически назначить владельца, особенно когда образ не создавал внутри него подходящий каталог.

Инициализацию прав выполняют один раз над новым учебным volume подготовленным административным инструментом с известным образом и digest. Например, контейнер с командой chown 10001:10001 /data получает только этот volume, сеть none и ограниченное время. После этого приложение всегда запускается со своими узкими правами. Восстановление архива должно сохранить либо осознанно восстановить те же идентификаторы.

Корректное завершение входит в код

Приложение подписывается на SIGTERM и SIGINT через signal.NotifyContext. Когда сигнал получен, http.Server.Shutdown прекращает приём новых соединений и ждёт предусмотренного завершения текущих обработчиков с бюджетом 10 секунд. Внешняя среда получает 15 секунд stop_grace_period, оставляя небольшой запас на завершение. Бюджеты согласованы, но при зависшем хранилище возможен принудительный предел.

Программа запускается непосредственно через JSON ENTRYPOINT. Лишняя shell не получает роль промежуточного PID 1. В журнале при штатной остановке ожидается stopped; отсутствие этой записи совместно с кодом 137 повод проверить, не истёк ли внешний тайм-аут. При непредвиденном падении до установки обработчиков штатный протокол не выполняется: резерв данных нужен независимо от него.

Счётчик демонстрирует пределы простой записи

POST /counter сериализует изменения mutex, пишет временный файл в том же каталоге, вызывает Sync, заменяет имя и синхронизирует каталог. После перезапуска читается сохранённое число. При ошибке после замены имени результат устойчивости может быть неизвестен; программа блокирует следующие записи до разбора и перезапуска, не продолжая молча со старым значением в памяти. Повреждённое число при старте вызывает отказ, а не автоматическое обнуление.

Служба не реализует распределённый доступ нескольких процессов к одному счётчику, идентификаторы повторных запросов или транзакцию нескольких объектов. Запуск двух копий с общим /data нарушает предпосылку единственного писателя. Это полезный отрицательный опыт с явно обозначенным результатом, а не способ получить кластер. Для совместной записи нужен соответствующий протокол приложения или БД.

Одинаковый бинарник и одинаковый образ

-trimpath и -buildvcs=false делают некоторые входы бинарника явнее: убирают пути сборочной машины и автоматическое включение определённых сведений системы контроля версий (VCS). Они не закрепляют версию toolchain, базу, окружение, cgo или часы, если программа использует их при генерации. Номер версии, внедрённый -ldflags, тоже является входом и изменяет байты.

Чтобы сравнить две сборки, фиксируют Git-коммит, отсутствие незаписанных изменений, Go image digest, Dockerfile, платформу, параметры и способ получения зависимостей. Затем отдельно сравнивают хеш бинарника и digest образа. Отличие упаковки или attestations может изменить внешний digest при одинаковом исполняемом файле. Совпадение бинарника не доказывает одинаковую runtime-конфигурацию, а одинаковый образ — одинаковые данные тома.

Первичные источники: стадии, целевые платформы, флаги Go, Shutdown. Полные исходники находятся рядом с книгой и доступны офлайн.
