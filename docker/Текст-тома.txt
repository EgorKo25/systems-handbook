Что именно предстоит собрать

Цель — получить личную среду, в которой можно объяснить происхождение работающих байтов, путь запроса, место записи данных и последствия остановки. Образ служит входом запуска; контейнер добавляет собственное изменяемое состояние и конфигурацию. Если заново создать контейнер, эти части могут получить разные судьбы. Фраза «всё лежит в Docker» скрывает именно те различия, которые важны при отказе.

Чтение начинается с установки, а не с готового приглашения терминала. Дома с интернетом читатель находит официальный источник, выбирает поддерживаемую комбинацию ОС и архитектуры, готовит пакеты, образы и контрольные суммы. Перед следующим упражнением используется тот же экземпляр Engine — серверной части Docker — и тот же каталог учебного проекта. Новый раздел не подразумевает очистку прежних ошибок. Исправление ошибки становится частью истории стенда.

Основной путь — Docker Engine в выделенной Linux-машине Ubuntu 24.04, настоящей либо виртуальной. Виртуальная машина, VM, исполняет собственное ядро гостевой ОС; Linux-контейнеры одного Engine используют ядро того Linux, где работает сервер. Docker Desktop на Windows обычно предоставляет такое Linux-окружение через дополнительный слой виртуализации. Это полезный продукт, но он не превращает Docker Engine в переносимую программу без установки и следов. На рабочем компьютере действуют разрешения владельца компьютера. Книга на флэшке открывается без Engine; реальные опыты требуют заранее разрешённой среды.

Команды в теоретических главах показывают отдельные варианты конфигурации. Единственная последовательность реального развёртывания собрана в заключительном практикуме; повторно запускать все варианты с одним именем и портом подряд не требуется. Сначала устанавливают инструмент, затем читают механизм, потом выполняют связный маршрут с сохранением состояния.

Три масштаба одного объяснения

Сначала рассматриваем объект: например, манифест образа с перечнем слоёв. Затем механизм: как снимок файлов становится корнем процесса. После этого наблюдение: какой вывод покажет docker image inspect, что останется после docker rm и как отличить отсутствие файла от неверного монтирования. Так команды получают смысл, а название технологии перестаёт подменять причинную цепочку.

Сокращения раскрываются при появлении и повторяются в словаре. OCI, Open Container Initiative, — семейство открытых спецификаций образа, доставки и запуска; эти спецификации не определяют всю прикладную политику Docker. API, application programming interface, — программный интерфейс сообщений между компонентами. CLI, command-line interface, — интерфейс командной строки. Конкретный CLI обращается к выбранному серверу; местонахождение приглашения Bash ещё не доказывает местонахождение данных контейнера.

Часть оснований уже разобрана глубже в других томах: изоляция Linux, NAT и фильтрация пакетов, компилятор и сборка Go, согласованное восстановление PostgreSQL. Здесь эти механизмы соединяются в работающую систему. Kubernetes, объектные хранилища и управление секретами получат собственные тома: знание запуска контейнера не заменяет знания их протоколов и состояния.

Что фиксировать перед первым запуском

Паспорт технологии хранится рядом с учебными заметками, а секреты — отдельно с ограниченными правами. В паспорт записывают источник и время загрузки, полные версии клиента, сервера, containerd и плагинов, архитектуру, способ проверки пакетов, имя Docker context, адрес сервера, тип хранения и пути данных. Следующие поля — команды запуска, остановки, журналы, контрольные проверки и способ восстановления. Контрольная сумма одного архива проверяет его байты; достоверность ожидаемой суммы зависит от источника.

Нужен и паспорт приложения: Git-коммит, версия Go, платформа сборки и исполнения, идентификатор образа, внешний порт, каталоги или тома данных, владелец файлов, ожидаемый ответ и доступные зависимости. Два проекта с одинаковым YAML и разными переменными окружения могут описывать разные системы. Поэтому сохраняют также результат нормализации конфигурации, предварительно исключив чувствительные значения.

Граница проверок этого издания

Текст опирается на официальные спецификации и документацию, проверенные при подготовке. Docker на компьютере читателя не устанавливался, реальные контейнеры и сетевые правила этого тома автоматически не запускались. Проверяемые локальные модели в labs/ демонстрируют ограниченные алгоритмы; они не являются эмулятором ядра и не измеряют скорость будущего хоста. Команды реального стенда сопровождаются предусловиями и наблюдениями, которые читатель должен получить сам.

Версионные примеры ориентированы на Linux Engine 29 и современный плагин docker compose; конкретные исправляющие выпуски выбирают в официальном репозитории перед установкой. Свежая установка и обновление старого сервера могут использовать разные подсистемы хранения. Именно поэтому вывод docker info важнее предположения по одному номеру версии.

Сначала определить место установки

На странице официальной установки Engine для Ubuntu проверяют поддерживаемый выпуск и архитектуру. На учебной гостевой машине выполняют cat /etc/os-release, uname -m и dpkg --print-architecture. Последняя команда показывает имя архитектуры пакетов Debian, например amd64; имя ядра x86_64 обозначает ту же аппаратную семью другим соглашением. Пакет для arm64 не становится исполнимым на amd64 от одинакового имени Ubuntu.

Выберите один основной путь: rootful Engine в личной VM, rootless Engine либо Desktop. Rootful означает, что управляющий сервис имеет системные полномочия root. Rootless означает исполнение самого сервиса и контейнеров от непривилегированного пользователя с отображением идентификаторов. Эти пути имеют разные сокеты, конфигурацию и ограничения. Основные примеры книги используют первый вариант внутри выделенной VM; глава о защите объясняет переход ко второму.

Docker Desktop для Windows включает интеграцию с Windows и Linux-средой; его установка, WSL 2, служебные данные и журналы относятся к состоянию рабочего компьютера. Запуск файлов с USB-накопителя сам по себе не обеспечивает отсутствие изменений в Windows. Для чтения и встроенных моделей достаточно браузера. Для реальной практики используют разрешённую VM либо удалённый личный Linux-хост. SSH, защищённый удалённый доступ, переносит управление, но не переносит диски сервера на флэшку.

Подготовить доверенный источник пакетов

Перед добавлением репозитория посмотрите установленные пакеты dpkg-query -W 'docker*' 'containerd*' 'runc*' и действующие службы. Дистрибутивный docker.io и официальная поставка docker-ce имеют разные пути обновления. Удалять найденный containerd на общем сервере без выяснения владельца нельзя: его может использовать другая система. В пустой учебной VM конфликтующие пакеты заменяют по официальной инструкции; в продолжаемом стенде сначала сохраняют конфигурацию и выясняют зависимости.

sudo apt update
sudo apt install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

curl -f считает ошибочный HTTP-статус ошибкой команды, -s убирает индикатор передачи, -S сохраняет сообщение об ошибке при тихом режиме, -L следует перенаправлениям. -o выбирает файл, поэтому ответ не попадает случайно в терминал. install -d создаёт каталог, -m задаёт права. Сертификаты CA нужны для проверки HTTPS. Загруженный ключ связывает пакеты с выбранным репозиторием; его происхождение и отпечаток сверяют с официальными материалами, а не с произвольным форумом.

В отдельном файле /etc/apt/sources.list.d/docker.sources для этой машины задают Deb822-поля. Архитектура ниже подходит только проверенной amd64; для arm64 меняется именно она. Ubuntu 24.04 использует кодовое имя noble.

Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc

Signed-By ограничивает ключ данным источником. APT проверяет подпись метаданных репозитория и хеши пакетов, указанные в этих метаданных. Это цепочка доверия, а не волшебное свойство расширения .deb. После sudo apt update команда apt-cache policy docker-ce показывает кандидата и источники, apt list --all-versions docker-ce — доступные строки версий. Сохраняют полную строку с эпохой и суффиксом дистрибутива, а не только «29».

Закрепить комплект, а не одну цифру

sudo apt install docker-ce=ПОЛНАЯ_ВЕРСИЯ \
  docker-ce-cli=ПОЛНАЯ_ВЕРСИЯ containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl status docker --no-pager
docker version
docker buildx version
docker compose version

Это образец команды: ПОЛНАЯ_ВЕРСИЯ заменяется выбранной строкой, вводить слово буквально не нужно. Клиент и Engine часто выпускаются согласованно; у containerd и плагинов собственные номера. Для воспроизводимого комплекта записывают также их полные версии и зависимости. systemctl status сообщает состояние службы, --no-pager печатает напрямую. Успешная служба ещё не означает успешный pull образа: это отдельные DNS, TLS, доступ к реестру и свободное место.

Для автономной установки готовят комплект на машине с теми же Ubuntu, архитектурой и близким исходным набором пакетов. Простого apt download docker-ce недостаточно: он скачивает один пакет, не полное замыкание зависимостей. В одноразовой подготовительной VM сначала получают и проверяют весь необходимый набор через APT, сохраняют подписанные метаданные и пакеты либо создают подписанный локальный репозиторий. Затем проверяют установку комплекта во второй такой же VM без сети. Критерий — успешная установка и запуск, а не существование нескольких deb-файлов на USB.

В паспорт входят список dpkg-query -W нужных пакетов, sha256sum сохранённых файлов, источник ожидаемых сумм, архитектура и время подготовки. При установке из локальных файлов sudo apt install ./имя.deb разрешает зависимости по доступным источникам; без заранее собранных зависимостей офлайн-успех не гарантирован. Загруженные образы также понадобятся отдельно: пакеты Engine не содержат все будущие приложения.

Служба, сокет и полномочия

Системная поставка обычно создаёт службу Docker и Unix-сокет /var/run/docker.sock. Сокет — локальная конечная точка обмена сообщениями, а не каталог образов. Проверка sudo docker info использует полномочия root для доступа к нему. Добавление пользователя в группу docker не даёт «чуть более удобное чтение»: доступ к управляющему API позволяет попросить сервер смонтировать хостовый каталог и запустить привилегированный процесс. Поэтому членство в такой группе рассматривают как широкое доверие к серверу.

Не открывайте TCP-порт демона ради первого упражнения. Для удалённого личного сервера проще использовать Docker context с SSH в следующей главе. Демон без аутентификации на 0.0.0.0:2375 предоставляет управление всем доступным ему окружением. Отдельный внешний порт приложения и порт API Docker имеют совершенно разные назначения.

Настроить хранение и журналы до нагрузки

Конфигурация rootful Docker обычно находится в /etc/docker/daemon.json. Сначала читают существующий файл, затем добавляют необходимые ключи в один корректный JSON-объект. Два самостоятельных JSON-объекта рядом не являются объединённой конфигурацией. Одновременное задание одного параметра в аргументах systemd и JSON может вызвать ошибку запуска.

{
  "log-driver": "local",
  "log-opts": {"max-size": "10m", "max-file": "3"}
}

Драйвер local хранит поток журналов с ограничением размера и служебной обработкой; значения log-opts записываются строками. Новые настройки журнала по умолчанию применяются к новым контейнерам, а не автоматически переписывают уже созданные. Проверяют JSON и dockerd --validate --config-file=/etc/docker/daemon.json, если установленная версия поддерживает этот режим; затем планируют перезапуск и проверяют journalctl -u docker -b --no-pager. До перезапуска выясняют судьбу действующих контейнеров.

В Engine 29 свежие установки по умолчанию используют хранилище образов containerd; обновлённые установки могут продолжить legacy overlay2. Docker data-root не обязан переносить данные containerd. Поэтому записывают фактические пути обеих подсистем, свободное место и тип файловой системы; не перемещают работающую БД копированием одного привычного каталога. Подробности будут в главах о слоях и восстановлении.

Приёмка и продолжение того же экземпляра

После подготовки читают docker info: имя сервера, версии, архитектуру, драйвер хранения, cgroup и предупреждения. docker run hello-world полезен как начальная проверка загрузки и запуска, но требует заранее доступного образа. Для автономного дня образ заранее скачивают, сохраняют и пробно загружают без сети. Проверяют также создание своего именованного тома и небольшой записи, остановку/запуск того же контейнера и повторное чтение. Каждая проверка имеет отдельный смысл.

Сохраняют паспорт в /srv/study/docker-world/ внутри учебной VM; это каталог проекта, не принудительный путь внутренней базы Docker. При следующей главе сравнивают паспорт, текущий context и docker info. Ошибку доступа разбирают на уровне пользователя/сокета, ошибку pull — на уровне сети/реестра, ошибку запуска — по runtime и процессу. Переустановка при первом непонятном сообщении уничтожает полезное свидетельство.

Первичные источники: пакеты Ubuntu, демон и конфигурация, журналирование, Desktop для Windows.

Команда обращается к конкретному серверу

Исполняемый файл docker — клиент. Он разбирает параметры и отправляет запрос управляющему сервису dockerd. Протокол API содержит операции создания, запуска и исследования контейнеров. Если клиент находится на ноутбуке, а context указывает на VM, процесс и файлы возникают на VM. Каталог, из которого набрана команда, не меняет этой границы.

Блок разбирает один вариант настройки. Перед реальным выполнением нужны подготовленный образ и свободные выбранные имя/порт; связный маршрут без конфликтующих повторных запусков находится в заключительном практикуме.

docker context ls
docker context inspect study
docker --context study version
docker --context study info

context ls перечисляет локально сохранённые точки управления; звёздочка отмечает выбранную. inspect показывает параметры подключения. Глобальный --context study относится к клиенту и ставится перед подкомандой. version разделяет Client и Server: версия клиента может выводиться даже при недоступном сервере. info требует ответа сервера и описывает его окружение. Ошибка Cannot connect ещё не говорит, что Engine не установлен: возможны неверный context, сокет, права, SSH или остановленная служба.

Для своего уже доступного по SSH Linux-хоста можно создать docker context create study --docker host=ssh://student@lab.example.invalid. Адрес здесь учебный, его заменяют адресом личного сервера. Сначала отдельно проверяют SSH и отпечаток ключа узла. Учётная запись на сервере должна иметь разрешение обращаться к его Docker; SSH не отменяет эту проверку. Перед командами смотрят также DOCKER_HOST и DOCKER_CONTEXT в окружении: они могут изменить выбор назначения. Явный --context в опытах делает выбор обозримым, но пароль и закрытый ключ в команды не подставляют.

От create к start

docker run в обычном пути объединяет создание и запуск. Сначала сервер разрешает ссылку образа с учётом политики pull — получения из реестра. Затем создаёт объект контейнера: идентификатор, конфигурацию процесса, монтирования, сеть, политику перезапуска и изменяемую файловую область. После этого запускает процесс. Между созданием и исполнением может случиться ошибка; наличие строки в docker ps -a не доказывает, что приложение работало.

docker --context study create --name study-echo \
  --pull=never --publish 127.0.0.1:18080:8080 \
  study/echo:lesson1
docker --context study start study-echo
docker --context study ps -a --filter name=study-echo
docker --context study inspect study-echo

Образ study/echo:lesson1 будет собран в главе о Go. --pull=never запрещает неожиданную загрузку; при отсутствии образа команда завершается ошибкой. --name закрепляет удобное имя объекта на этом сервере. --publish описывает порт хоста 18080 и контейнера 8080, ограничивая вход адресом loopback хоста. create ещё не запускает приложение; start запускает тот же объект с прежней конфигурацией и изменяемой файловой областью. Для смены образа обычно создают новый объект.

Управление исполнением имеет несколько уровней

Dockerd координирует пользовательские объекты, сеть, тома и интерфейс управления. Containerd обслуживает жизненный цикл контейнерных задач и, в соответствующей конфигурации, содержимое образов и снимки файловой системы. Низкоуровневый runtime, обычно runc, применяет описание исполнения OCI: готовит изоляцию, монтирования, ограничения и запускает процесс. Shim — промежуточный служебный процесс — помогает наблюдать задачу и её потоки, не превращая основной daemon в непосредственного родителя, от которого должна зависеть вся жизнь приложения.

Это функциональная цепочка, а не требование увидеть ровно одну одинаковую строку ps во всех версиях. Реальные имена shim, runtime и дополнительные прокси зависят от поставки и режима. Нельзя на основании наличия процесса containerd объявить, что именно им управляет выбранный Docker: на машине могут работать несколько независимых экземпляров. Сопоставляют сокеты, конфигурацию, systemd unit и идентификатор контейнера.

OCI Runtime Specification описывает окружение процесса, а не готовую политику безопасности приложения. Можно корректно запустить контейнер с опасным монтированием хоста. Runtime исполнил конфигурацию; ошибку допустили при выборе полномочий. Аналогично сохранённый OCI-образ не содержит работающее TCP-соединение или состояние памяти уже запущенного процесса.

Потоки, терминал и фон

Стандартный ввод, вывод и поток ошибок — файловые дескрипторы 0, 1 и 2. -i сохраняет stdin открытым; -t выделяет псевдотерминал. Это разные действия: -it подходит интерактивной shell, но машинному обмену двоичными данными терминал может мешать из-за преобразований и объединения потоков. Фоновый режим -d отсоединяет клиент; внутри контейнера приложение по-прежнему должно оставаться основным процессом переднего плана.

Команда docker run -d IMAGE sh -c 'service app start' может завершить shell сразу после запуска фонового дочернего процесса. Жизненный цикл контейнера привязан к основному процессу; сервис не должен рассчитывать на фоновый режим установочного скрипта. Для Go обычно правильнее непосредственно выполнить бинарник. Отсоединение клиента attach, завершение SSH-сеанса, остановка приложения и удаление объекта — четыре разных события.

docker exec запускает дополнительный процесс в существующем работающем контейнере; docker attach подключает потоки основного. Exec не создаёт новый образ и не записывает исправление в Dockerfile. Изменённый через exec файл может исчезнуть при пересоздании. Контейнер без shell не становится неисправным от отказа exec ... sh: такой исполняемой программы в его файловой системе может не быть.

Состояния, коды и наблюдения

Created означает, что объект создан; running — основная задача считается работающей; exited — она закончилась; restarting — применяется политика перезапуска. Состояние процесса и health status различаются: приложение может работать, но не проходить проверку работоспособности. Docker сам по себе не обязан перезапускать контейнер лишь за статус unhealthy.

docker --context study inspect --format \
  '{{json .State}}' study-echo
docker --context study logs --tail 50 --timestamps study-echo
docker --context study wait study-echo

--format применяет шаблон клиента к объекту; json сохраняет структуру. В .State ищут ExitCode, Error, OOMKilled и временные отметки, но связывают их с журналом ОС. logs --tail 50 ограничивает объём, --timestamps добавляет время. wait ждёт окончания контейнера и выводит его код. Код 125 у docker run обычно относится к ошибке запуска со стороны Docker, 126 — к невозможности исполнить выбранную команду, 127 — к ненайденной команде; прочие коды часто приходят от приложения.

Число 137 обычно соответствует завершению сигналом SIGKILL по соглашению 128 + номер сигнала 9. Само по себе оно не доказывает нехватку памяти: контейнер могли принудительно остановить. Нужны OOMKilled, счётчики cgroup и системный журнал. Код 0 подтверждает успешное завершение в принятом приложением смысле, но не наличие обязательного файла в постоянном хранилище.

Что считать подтверждением

После запуска собственной службы нужны четыре независимые проверки: сервер знает нужный контейнер и образ; процесс действительно работает; нужный сокет доступен по ожидаемому пути; запрос приложения возвращает осмысленный результат. При записи нужна пятая: данные переживают предусмотренный сценарий остановки и восстановления. Один вывод идентификатора от docker run -d подтверждает только успешную начальную операцию управления.

Ссылка, содержимое и выбранная платформа

В ссылке registry.example.invalid/team/echo:lesson1 есть адрес реестра, имя репозитория и tag — метка. Реестр, registry, хранит и выдаёт объекты образов по протоколу. Tag — изменяемая ссылка на объект: сегодня lesson1 может указывать на одни байты, завтра на другие. Ссылка ...@sha256:... закрепляет digest, криптографический идентификатор содержимого определённого объекта. Один и тот же tag на двух хостах после разных моментов загрузки не гарантирует одинаковый результат.

Digest необходимо читать вместе с типом объекта. OCI index — индекс вариантов — содержит дескрипторы манифестов для разных платформ. Манифест одного варианта указывает конфигурацию и упорядоченные слои. Дескриптор включает media type, digest и размер. Media type сообщает формат содержимого, digest проверяет байты, размер помогает обнаружить несоответствие передачи. У многоархитектурной ссылки digest индекса и digest выбранного linux/amd64-манифеста различаются.

Платформа включает ОС, архитектуру и, когда нужно, вариант. Индекс может дать linux/arm64 и linux/amd64, но ни один из этих Linux-вариантов не обещает работать как Windows-процесс. На Windows с Linux-контейнерами выбирается Linux-окружение Desktop. Эмуляция набора команд процессора — отдельная технология с другой ценой исполнения; наличие индекса не включает её автоматически.

Конфигурация — тоже содержимое образа

Конфигурационный JSON хранит настройки по умолчанию: окружение, рабочий каталог, пользователя, Entrypoint, Cmd и сведения о корневой файловой системе. Эти параметры участвуют в идентичности объекта. Одинаковые файлы с разным пользователем запуска — уже различающиеся образы. Параметр EXPOSE описывает предполагаемый порт, но не создаёт правило публикации на хосте. Значение ENV доступно запущенному процессу и не должно использоваться как защищённое хранилище пароля.

docker --context study image inspect study/echo:lesson1
docker --context study image inspect --format \
  '{{json .Config}}' study/echo:lesson1
docker --context study image inspect --format \
  '{{json .RootFS.Layers}}' study/echo:lesson1
docker --context study image history --no-trunc study/echo:lesson1

Inspect показывает локально известный объект выбранного сервера. --no-trunc не сокращает поля history; история полезна для понимания сборки, но сама по себе не является полным достоверным исходником Dockerfile. У некоторых инструкций меняется только конфигурация, без нового файлового слоя. Поэтому число строк history, число архивных слоёв и число инструкций не обязаны совпадать.

Слой описывает изменение

Представим нижний слой с /app/config.txt=A и /app/old.txt=B. Следующий слой заменяет config на C, создаёт new и удаляет old. Это не копия всего диска: архив изменения содержит новые версии нужных объектов и обозначение удаления. OCI использует whiteout — специальное имя, указывающее, что нижний объект должен быть скрыт; для old это .wh.old.txt. Непрозрачный каталог, opaque directory, дополнительно скрывает прежних нижних потомков каталога.

Применение слоёв идёт снизу вверх. Whiteout не является обычным пользовательским файлом в готовой объединённой файловой системе. Он сообщает сборщику этой системы, что прежняя запись больше не видна. При этом байты old остаются в более раннем неизменяемом слое. Поэтому удаление секрета следующей инструкцией не удаляет его из истории образа и не уменьшает уже опубликованный нижний архив до нуля.

Команда RUN install-tool && use-tool && remove-temporary в одном шаге может не оставить временный файл в итоговом изменении, если файл появился и исчез внутри шага. Отдельные RUN сначала сохраняют нижний результат. Но объединять всё в один гигантский шаг тоже не самоцель: теряются удобные границы кэша и диагностики. Разделяют частоту изменения входов, размеры результатов и потребность в повторном использовании.

Сжатый digest и diff ID отвечают на разные вопросы

Слой часто передаётся как сжатый tar-архив. Digest дескриптора проверяет именно передаваемый blob, двоичный объект. Diff ID в конфигурации вычисляется по несжатому потоку слоя. Разные параметры сжатия могут изменить digest blob при одинаковом несжатом содержимом. Нельзя сравнивать эти два поля как доказательство порчи лишь потому, что оба начинаются с sha256.

Tar содержит не только содержимое файлов, но и метаданные: пути, типы, права, владельцев, ссылки и временные отметки согласно формату. Повторная сборка одинаковой программы может дать другое содержимое архива из-за метаданных. Доказательство одинакового бинарника и доказательство одинакового образа имеют разный охват. Это подробно связывается с воспроизводимостью Go в главе доставки.

Из слоёв получается корень процесса

В типичном Linux-пути OverlayFS объединяет нижние неизменяемые каталоги и верхнюю изменяемую область. Чтение неизменённого файла получает нижние данные. При модификации нижнего файла может понадобиться copy-up — перенос нужной версии в верхнюю область, после чего запись идёт туда. Реальная гранулярность и оптимизации зависят от файловой системы и параметров; нельзя обещать, что изменение одного байта всегда записывает ровно один байт на диск.

Поэтому база данных в изменяемом слое — плохая исходная эксплуатационная привычка: жизненный цикл данных становится связан с удалением контейнера, а путь записи получает дополнительные особенности снимков. Именованный volume позволяет вынести данные за этот жизненный цикл, но не автоматически обеспечивает резерв, распределённость или согласованность. Отдельное монтирование также может скрыть каталог образа: файл существует в нижнем корне, но процесс видит другой каталог поверх него.

Overlay2 и containerd snapshotter

Overlay2 — классический драйвер хранения Docker. Snapshotter, механизм снимков containerd, — другой интерфейс управления файловыми состояниями; один из его вариантов использует overlayfs. Поэтому слова overlayfs и overlay2 не обозначают взаимозаменяемые уровни конфигурации. В Engine 29 свежая установка по умолчанию использует containerd image store; обновлённая с прежней версии может сохранить прежнюю подсистему (backend).

Containerd store способен хранить как передаваемые сжатые объекты, так и распакованные снимки; расчёт свободного места должен учитывать оба представления. Переключение backend может скрыть старые образы и контейнеры из текущего представления, хотя байты остаются на диске. Такое наблюдение не лечат немедленной очисткой каталога: сначала сверяют конфигурацию и предыдущий backend. Перенос data-root Docker не является доказательством переноса отдельного корня containerd.

В проверенной документации containerd image store также указан как несовместимый с daemon-режимом userns-remap. Это отдельный rootful-режим отображения идентификаторов; из такого ограничения не следует общий запрет rootless. Перед сочетанием опций сверяют таблицу поддержки конкретной версии.

Что именно занимает место

Показатель reclaimable означает потенциально освобождаемое в выбранном представлении, а не обещание точно такого прироста свободных байтов после любого prune.

Учебный расчёт: три образа разделяют базу 80 МиБ и добавляют по 12 МиБ. Dockerfile — вход системы сборки

Dockerfile описывает шаги получения образа. BuildKit, современная подсистема сборки, преобразует описание в граф операций: получение базовых образов, чтение контекста, исполнение команд, копирование результатов и экспорт. Buildx — клиентский интерфейс управления такими сборками и builders, экземплярами сборщика. Наличие нового клиента ещё не доказывает, что выбранный builder имеет нужные возможности и локальное состояние.

docker --context study buildx ls
docker --context study buildx inspect --bootstrap
docker --context study buildx build --progress=plain \
  --load --tag study/echo:lesson1 .

ls показывает builders и их драйверы. inspect --bootstrap может запустить компоненты builder и потому является действием, а не только чтением метаданных. --progress=plain даёт последовательный текст для сравнения шагов; --load выбирает загрузку результата в хранилище выбранного Engine в поддерживаемом варианте. При удалённом context этот Engine находится на сервере, а не обязательно на компьютере клиента. У отдельного builder с драйвером docker-container результат иначе может остаться только в кэше сборщика. --tag назначает имя, точка выбирает контекст текущего каталога.

Контекст — отдельная граница файлов

Build context, контекст сборки, — предоставляемый набор входных файлов. Указание -f deploy/Dockerfile выбирает описание, но не переносит автоматически корень контекста в deploy. Команда docker build -f deploy/Dockerfile . по-прежнему использует текущий каталог. Путь источника COPY рассматривается относительно доступного контекста или явно выбранной стадии, а не произвольного домашнего каталога клиента.

Файл .dockerignore исключает ненужные входы до их использования сборщиком. В собственном Go-проекте исключают .git, временные результаты, локальные журналы и файлы с секретами, если они не являются обязательными входами. Передача секретного файла уже является нарушением выбранной границы даже тогда, когда финальная стадия его не копирует. Удалённый builder получает входы на другой машине.

.git
out/
backups/
*.log
.env
secrets/

Этот пример не универсален: если сборка намеренно читает Git-метаданные, исключение .git требует другого способа передать зафиксированную версию. Правильный критерий — явный перечень нужных входов. Большой контекст увеличивает передачу и вероятность лишних изменений; оценка сборки должна отдельно показывать время передачи, получения баз и собственно компиляции.

Почему одинаковая команда может использовать старый результат

Для обычного RUN система не проверяет каждый раз, изменился ли внешний сайт, к которому обращалась команда. Если команда и релевантные входы совпали, прежний результат может быть повторно использован. Поэтому RUN apt-get update, взятый из кэша через месяц, не означает получение сегодняшнего списка пакетов. Если обновление списка и установка находятся в разных слоях, можно объединить устаревший список и новый запрос установки. Осмысленная операция получения пакетов должна иметь согласованные входы и политику обновления.

Для COPY содержимое и существенные метаданные входных файлов участвуют в проверке кэша; одно изменение mtime, времени модификации, не обязано сбрасывать кэш. Не следует делать вывод «файл обновлён» только по touch. При изменении ранней зависимости линейной цепочки последующие результаты требуют пересчёта; независимые ветви многостадийного графа при этом могут оставаться пригодными.

В Go полезно сначала копировать go.mod и имеющийся go.sum, получить зависимости, затем копировать исходники и компилировать. Тогда изменение обработчика не заставляет заново получать весь набор модулей. Однако команда должна соответствовать реальному проекту: проект без сторонних модулей может не иметь go.sum; слепой COPY отсутствующего файла завершится ошибкой ещё до Go.

Три разных кэша

Кэш результата операции BuildKit позволяет вообще не повторять шаг. Cache mount, временно подключаемый сохраняемый кэш, помогает внутри повторно выполняемого шага: например, Go может использовать ранее скомпилированные пакеты. Наконец, кэш модулей Go хранит полученные входы зависимостей. Очистка одного уровня не обязательно очищает другие. --no-cache запрещает использование результатов шагов, но не означает автоматическую загрузку нового базового образа и не обязан обнулить содержимое cache mounts.

RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -mod=readonly -trimpath -o /out/echo ./cmd/echo

Оба mount существуют для сборочного шага и не становятся каталогами финального образа от самого факта подключения. -mod=readonly запрещает требуемое изменением разрешения зависимостей редактирование go.mod; -trimpath убирает пути файловой системы из определённых метаданных бинарника. Эти флаги Go не делают внешние входы автоматически доверенными. Подробности выбора пакетов и ключей Go-кэша разобраны в томе Go.

Внешний cache-to/cache-from переносит пригодные записи между сборщиками. Он требует собственных прав доступа, формата, платформы и бюджета хранения. Кэш ускорения не должен быть единственной копией выпускаемого образа. Более того, доступ на запись в общий кэш и доступ на выполнение недоверенного Dockerfile требуют отдельной модели доверия; экономия минут не оправдывает безусловное смешивание чужих входов.

Секрет не равен build argument

ARG TOKEN и ENV TOKEN=... подходят для несекретных параметров, но не для передачи пароля. Значения могут попасть в метаданные, историю, происхождение сборки или журнал команды. Secret mount передаёт чувствительный файл определённому RUN на время исполнения. Он устраняет необходимость сохранять этот файл в обычном слое, но команда всё равно способна напечатать секрет или скопировать его в результат.

RUN --mount=type=secret,id=repo_token,required=true \
    /usr/local/bin/fetch-private-input /run/secrets/repo_token

docker buildx build --secret id=repo_token,src=/ЛИЧНЫЙ/ПУТЬ \
  --load --tag study/echo:lesson1 .

Это схема интеграции: fetch-private-input обозначает собственную проверенную программу и в готовом лабораторном проекте отсутствует. required=true требует источник секрета. Нельзя рассчитывать, что изменение значения секрета само сбросит кэш: для повторного получения изменённого результата используют явный несекретный идентификатор версии входа или ограниченную отмену кэша. SSH mount передаёт возможность обращаться к агенту SSH; он также требует доверия к выполняемой команде.

Как измерить ускорение без самообмана

Сравнивают четыре режима: холодный builder, повтор без изменений, изменение одного Go-файла и изменение зависимостей. Для каждого фиксируют builder, версии, платформу, наличие базовых образов и кэшей, сеть, лимиты CPU/памяти и итоговый digest. Одна «сборка за 2 секунды» может целиком состоять из повторного использования результата, ничего не говоря о скорости компилятора.

Пример: передача контекста 18 с, получение базы 30 с и компиляция 12 с дают 60 с без перекрытия. Уменьшение компиляции вдвое экономит 6 с, а удаление лишних архивов из контекста может сэкономить 15 с. В реальном графе часть операций перекрывается; итог определяется критическим путём, а не суммой всех строк. Сначала находят этот путь, затем меняют один фактор и сравнивают серии запусков.

Первичные источники: BuildKit, пригодность кэша, границы кэшей, секреты сборки.

Один процесс виден по-разному

Namespace, пространство имён Linux, меняет представление определённого класса объектов для группы процессов. PID namespace изолирует номера процессов; network namespace — интерфейсы, адреса, маршруты и сокеты; mount namespace — дерево монтирований. UTS namespace отделяет имя узла, IPC namespace — определённые механизмы межпроцессного обмена. User namespace задаёт отображение идентификаторов пользователей и групп. Cgroup namespace меняет видимость пути к группе ресурсов, но сам не создаёт ограничение памяти.

Процесс может иметь номер 1 внутри своего PID namespace и номер 24718 во внешнем. Это один процесс, а не два синхронизируемых экземпляра. Внешнее ядро планирует его потоки, учитывает страницы памяти и обрабатывает системные вызовы. Разные файлы /etc/os-release в двух контейнерах говорят о пользовательском окружении образов, а uname -r — о ядре среды исполнения. Alpine и Debian в контейнерах на одном Linux Engine не загружают два независимых ядра.

Можно совместно использовать отдельное пространство: --network=host меняет сетевую границу, --pid=host — видимость процессов. Из этого не следует автоматическое снятие всех остальных ограничений. Но каждое такое действие расширяет доступный процессу мир и требует причины. Для первого Go-сервиса ни host PID, ни доступ ко всем устройствам не нужны.

Корень файлов — результат монтирований

Подготовленный root filesystem становится видимым корнем процесса. Это не отдельная копия всего компьютера: специальные файловые системы, каталоги из образа, тома и tmpfs собираются в дерево монтирований. Файл по пути /data/item может лежать на том же диске хоста, что журнал Docker, либо на другом подключённом устройстве. Изолированное имя пути не сообщает физическое размещение.

chroot, смена корневого каталога процесса, сам по себе не равен контейнеру и не обеспечивает полную защитную границу. Полномочия, открытые файловые дескрипторы, монтирования и другие пространства остаются самостоятельными вопросами. Практическая конфигурация runtime сочетает эти механизмы и дополнительные ограничения. Подробный путь имени к inode разобран в томе Linux.

Ресурсная группа не является виртуальным железом

Cgroup, control group, организует процессы и учёт ресурсов в иерархию. Ограничение предка влияет на потомков: контейнер с заявленными двумя CPU внутри VM с одним фактически доступным CPU не получает второй процессор. В cgroup v2 контроллеры подключаются к единой иерархии; доступность зависит от ядра, systemd, делегирования и режима Engine. Текст команды ещё не доказывает, что соответствующий контроллер действительно применён.

docker run --memory=256m --cpus=1.5 --pids-limit=128 ... задаёт разные ограничения. Memory ограничивает учитываемую память группы; cpus выражает квоту процессорного времени; pids ограничивает количество задач ядра, включая потоки в принятом контроллером смысле. Число goroutine в Go не совпадает с числом потоков ОС, поэтому pids-limit не является прямым лимитом горутин.

В типичном cgroup v2 поле cpu.max содержит quota и period в микросекундах. Значения 150000 100000 разрешают до 150 мс совокупного CPU-времени за период 100 мс, то есть 1,5 CPU по времени. На нескольких CPU процесс может быстро израсходовать квоту параллельно и затем ждать нового периода. Это объясняет скачки задержки при формально невысоком среднем использовании хоста. --cpuset-cpus выбирает допустимые логические CPU, а не выделяет приложению эксклюзивные ядра.

Память: давление, предел и OOM

memory.current показывает текущий учёт cgroup, memory.max — жёсткую границу, memory.high — порог давления и усиленного освобождения. High не следует представлять как безусловный второй hard limit. В учёт могут входить файловый кэш и служебная память ядра, а не только Go-куча. Поэтому GOMEMLIMIT, мягкая цель управления памятью runtime Go, оставляет запас для памяти вне управляемой им области и не заменяет ограничение cgroup.

Когда освободить память недостаточно, возможен OOM, out of memory, — ситуация нехватки памяти с принудительным завершением процесса. Исследуют memory.events, журнал ядра и состояние контейнера. docker stats использует своё представление метрик, включая особенности вычитания кэша на Linux; одинаковый заголовок MEMORY не делает его численно равным RSS процесса или memory.current. Нельзя ставить лимит ровно равным единственному удачному наблюдению stats.

--memory-swap в интерфейсе Docker задаёт сочетание разрешённой памяти и swap по правилам конкретной опции; это не просто объём дополнительной оперативной памяти. При --memory=256m --memory-swap=256m дополнительный swap для группы не разрешается, если хост и контроллер поддерживают ограничение. Задержки при подкачке и поведение без поддержки проверяют отдельно. Совет «включить swap и забыть об OOM» скрывает цену ожидания и ограничения приложения.

Как читать действующие границы

docker --context study info
docker --context study inspect --format \
  '{{json .HostConfig}}' study-echo
docker --context study stats --no-stream study-echo
docker --context study top study-echo

HostConfig показывает запрошенные настройки. Info сообщает cgroup version/driver и предупреждения. Stats даёт снимок учёта, top — процессы. Это разные свидетельства: декларация, возможности среды и наблюдаемое исполнение. На реальном Linux-хосте администратор может сопоставить PID с /proc/PID/cgroup и файлами соответствующей группы. В контейнере часть путей может выглядеть иначе из-за cgroup namespace; в scratch-образе утилиты cat может вообще не быть.

Почему PID 1 требует внимания

Первый процесс PID namespace выполняет роль init для этой области: принимает осиротевшие дочерние процессы и имеет особые правила доставки сигналов. Zombie, зомби-процесс, — уже завершившийся потомок, код которого родитель ещё не забрал через wait. Он не продолжает исполнять Go-код, но занимает запись. Если приложение запускает внешние программы и теряет их завершение, проблема не решается увеличением памяти.

JSON-форма ENTRYPOINT ["/echo"] запускает бинарник напрямую. Shell-форма может добавить /bin/sh -c как промежуточного владельца сигналов; корректная оболочка должна передать управление через exec либо явно пересылать сигналы и собирать потомков. --init добавляет маленький init-процесс для предусмотренной обработки потомков и сигналов, но не реализует прикладное завершение запросов вместо приложения.

Остановить — значит дать приложению протокол завершения

docker stop --timeout 15 study-echo отправляет основной сигнал остановки, обычно SIGTERM, затем после тайм-аута применяет SIGKILL к оставшейся задаче. STOPSIGNAL образа и параметры запуска могут изменить первый сигнал. SIGKILL нельзя перехватить для сохранения данных. Поэтому Go-программа должна установить обработку SIGTERM, прекратить приём новых запросов, дать текущим закончиться в установленном бюджете и закрыть нужные ресурсы.

Допустим, обычный запрос занимает 200 мс, но загрузка файла — 40 с. Тайм-аут 15 с не гарантирует завершение каждого такого запроса. Нужно решить, допускается ли отмена, как клиент узнает результат и безопасен ли повтор операции. Graceful shutdown, корректное завершение по протоколу, — свойство совместной работы приложения и среды; сам факт наличия SIGTERM ничего не обещает.

После stop контейнер и его изменяемые файлы существуют; после start запускается новый процесс в том же объекте. После rm изменяемая область объекта удаляется, а независимо управляемый именованный том обычно остаётся. Эти переходы станут основной осью следующих практических упражнений.

Первичные источники: namespaces, PID 1, cgroup v2, параметры ограничений Docker.

В собственном network namespace контейнер имеет отдельные интерфейсы, loopback, маршруты и набор сокетов. Адрес 127.0.0.1 из процесса Go относится к loopback этого пространства. Если Go слушает только 127.0.0.1:8080, соединение к IP контейнера на eth0 может не попасть в слушающий сокет. Публикация порта Docker не меняет привязку (bind) программы к локальному адресу. Для обращения через сетевой интерфейс приложение слушает :8080 либо конкретный нужный адрес.

У rootful Linux bridge-сети одна сторона veth-пары находится в контейнере, другая связана с программным мостом хоста. Veth — пара виртуальных Ethernet-интерфейсов: переданное в один конец появляется на другом. Bridge, мост, пересылает кадры между портами по MAC-адресам; IP-маршрутизация хоста действует на другом уровне. Само наличие моста ещё не объясняет доступ наружу: там понадобятся маршруты, разрешённая пересылка и часто NAT.

Блок разбирает один вариант настройки. Перед реальным выполнением нужны подготовленный образ и свободные выбранные имя/порт; связный маршрут без конфликтующих повторных запусков находится в заключительном практикуме.

docker --context study network create --driver bridge \
  --subnet 172.30.50.0/24 study-net
docker --context study run -d --name study-echo --pull=never \
  --network study-net --ip 172.30.50.10 \
  --publish 127.0.0.1:18080:8080 study/echo:lesson1
docker --context study network inspect study-net
docker --context study port study-echo

Перед созданием проверяют, что подсеть не пересекается с реальными маршрутами хоста, VPN и другими сетями стенда. Адреса здесь учебные, а не гарантированно свободные. Фиксированный IP выбран только для пошагового расследования; прикладная конфигурация обычно должна использовать стабильное имя сервиса. Команды меняют только явно подготовленный учебный Engine, их не выполняют автоматически при открытии книги.

Имя сервиса и внешнее имя разрешаются разными путями

Пользовательская bridge-сеть предоставляет разрешение имён контейнеров и сетевых псевдонимов. В такой среде Docker обычно даёт встроенный DNS по адресу 127.0.0.11 внутри контейнера. Он знает относящиеся к сети имена и передаёт внешние вопросы настроенным серверам. Отсутствие записи контейнера в публичном DNS ожидаемо: это область имён Docker-сети, а не глобальный домен.

Автоматическая сеть bridge, появившаяся при запуске Engine, имеет другие свойства: имена контейнеров в ней не получают автоматически тот же механизм взаимного обнаружения. Поэтому старый пример «контейнеры всегда общаются по имени» без указания пользовательской сети неполон. Параметр --dns задаёт адрес DNS-сервера с точки зрения контейнера; значение 127.0.0.1 не означает DNS на физическом хосте.

Проверка из диагностического контейнера на той же сети отделяет разрешение имени, маршрут и приложение. Если scratch-образ не содержит nslookup, это не отказ DNS. Для проверки используют заранее подготовленный диагностический образ с явным digest и известными инструментами, а не добавляют пакетный менеджер в работающую боевую службу. Проверяют также выбор IPv4/IPv6, суффиксы автодополнения неполных имён, search domains и реальные адреса в ответе.

Два контейнера одной сети

Пусть клиент 172.30.50.20 обращается к имени study-echo, получая 172.30.50.10. Таблица маршрутов говорит, что адрес находится в непосредственно подключённой подсети. Для IPv4 ARP находит MAC соседа; кадр идёт через veth и bridge к интерфейсу сервера. TCP устанавливает соединение от временного порта клиента к 8080. В обычном пути одной bridge-сети приложение видит адрес контейнера-клиента; внешняя публикация 18080 здесь не участвует.

Запрос на study-echo:18080 неверен, если приложение внутри слушает 8080: 18080 — порт хоста, а не дополнительный слушатель Go. Отказ connection refused означает, что на выбранном адресе и порту не нашлось подходящего принимающего приложения либо пришёл активный отказ. Тайм-аут оставляет больше вариантов: потеря, фильтр, неверный путь или зависшая обработка.

Клиент снаружи через опубликованный порт

Пример -p 127.0.0.1:18080:8080 открывает предусмотренный путь на loopback Docker-хоста. С другого компьютера его 127.0.0.1 обозначает уже другой компьютер. У выпусков до Engine 28.0.0 существовал дополнительный край: опубликованный на localhost порт мог быть доступен соседям того же канального сегмента. Наш пример относится к выбранному Engine 29; версию проверяют до применения вывода о доступности. Для удалённого чтения можно использовать разрешённый SSH-туннель к loopback сервера, либо осознанно выбрать внешний bind и межсетевой экран. Простое удаление 127.0.0.1 из параметра обычно расширяет доступ до адресов хоста, а не только до одной доверенной сети.

В Linux bridge-пути публикация использует правила преобразования адреса назначения, DNAT, и фильтрацию; дополнительные пути с userland proxy зависят от режима и семейства адресов. Сетевое соединение может отображаться между HOST:18080 и 172.30.50.10:8080. Механизм conntrack, учёт состояния соединений, связывает прямые и обратные пакеты с этим преобразованием. Это не HTTP reverse proxy: Docker не обязан разбирать URL или добавлять прикладной заголовок запроса.

Источник внешнего соединения и локального соединения с хоста могут проходить разные точки обработки, а hairpin — обращение обратно через опубликованный адрес — добавляет особенности. Поэтому нельзя обещать один неизменный source IP для всех вариантов Desktop, rootless, IPv6 и proxy. Если политика приложения зависит от IP клиента, проверяют реальное наблюдение именно выбранного пути.

1. Клиент обращается к хосту

Порт назначения — опубликованный 18080, исходный временный порт — 53000.

Действует: TCP-клиент.

Клиент: 53000 → 18080; Хост: получен SYN; NAT/conntrack: ещё нет записи; Bridge/veth: не участвовал; Go: ждёт 8080

TCP tuple: нет потока → 198.51.100.20:53000 → 192.0.2.10:18080. Клиент не обращается напрямую к 172.30.50.10.

2. DNAT выбирает контейнер

Назначение становится 172.30.50.10:8080; в этом выбранном пути источник сохраняется. Проверки пакета корректируются.

Действует: Netfilter.

Клиент: ждёт; Хост: правило совпало; NAT/conntrack: оригинал↔переведённый; Bridge/veth: цель 172.30.50.10; Go: ещё не принял

Назначение: 192.0.2.10:18080 → 172.30.50.10:8080. Меняется сетевой путь, а не URL HTTP.

3. Маршрутизация и фильтр разрешают путь

Хост выбирает bridge-интерфейс, затем кадр проходит veth. Мост не является дополнительным IP-маршрутизатором на каждом порту.

Действует: Linux.

Клиент: ждёт; Хост: FORWARD разрешён; NAT/conntrack: запись активна; Bridge/veth: кадр к veth; Go: SYN на 8080

Доставка: пакет на хосте → сокет контейнера. Одного правила DNAT без допустимой пересылки мало.

4. Сервер отвечает клиентскому адресу

Ответ имеет источник 172.30.50.10:8080 и назначение 198.51.100.20:53000 до обратного преобразования.

Действует: TCP-сервер.

Клиент: ждёт SYN-ACK; Хост: обратный маршрут; NAT/conntrack: узнаёт поток; Bridge/veth: обратный кадр; Go: ответ отправлен

Ответ: входящий SYN → 172.30.50.10:8080 → 198.51.100.20:53000. Состояние соединения связывает направления.

5. Клиент получает ожидаемый источник

Обратное преобразование представляет ответ как пришедший от 192.0.2.10:18080.

Действует: Conntrack/NAT.

Клиент: согласованный поток; Хост: 192.0.2.10:18080; NAT/conntrack: обратная запись; Bridge/veth: передача завершена; Go: 8080

Источник ответа: 172.30.50.10:8080 → 192.0.2.10:18080. Без согласованного обратного пути клиент не получает ожидаемую пару.

Выход из контейнера

Для адреса вне подсети пакет отправляется шлюзу bridge-сети. Хост маршрутизирует его на внешний интерфейс. В типичном NAT-режиме masquerading заменяет частный адрес источника адресом внешнего интерфейса хоста; обратное преобразование обслуживает conntrack. Наличие маршрута по умолчанию в контейнере не доказывает наличие работающего NAT, разрешения FORWARD или внешнего DNS.

При ошибке сначала проверяют, установлен ли интерфейс и адрес, затем маршрут к цели, разрешение имени, доступность TCP и прикладной протокол. Ping проверяет ICMP и может быть запрещён отдельно; его отказ не доказывает отказ HTTPS. Для MTU, максимального размера пакета на канале, важны также туннели VPN: маленький ответ может проходить, а большая передача — зависать. Глубокий разбор TCP и обнаружения MTU находится в томе сетей.

Межсетевой экран — часть пути

Docker создаёт правила для bridge-сетей. При стандартном iptables backend политика оператора обычно включается через предусмотренную цепочку DOCKER-USER; на этом этапе адрес назначения уже может быть преобразован, поэтому проверка исходного опубликованного адреса требует понимания conntrack. Нельзя переносить обычное правило INPUT для веб-сервера на контейнерную пересылку без анализа пути. Опубликованный порт может обходить ожидаемые правила ufw.

Iptables-nft — совместимый интерфейс iptables поверх механизма nf_tables ядра. Собственный Docker nftables backend — другая конфигурация; в документации Engine 29 он экспериментален, имеет другую организацию таблиц и не предоставляет цепочку DOCKER-USER. Он также отличается поведением включения IP forwarding. Не смешивайте две модели правил и не правьте автоматически созданные Docker-таблицы как постоянный источник своей конфигурации.

Host, rootless и Desktop

--network=host на обычном Linux использует сетевое пространство хоста. Публикация -p в таком пути не создаёт прежнюю отдельную мостовую границу, а порт приложения конфликтует с уже занятыми портами хоста. Этот режим полезен в определённых задачах, но не является универсальным лечением ошибки DNS или bind.

Rootless-сеть может использовать дополнительный пользовательский механизм передачи, а Desktop добавляет границу Linux-VM и интеграцию с основной ОС. В этих случаях мост и правила находятся в другом месте, чем ожидает администратор физического Windows-хоста. Числа производительности одного rootful Linux bridge нельзя автоматически переносить на передачу через Desktop bind mount или пользовательскую сеть. Точка измерения должна сопровождать число.

Первичные источники: bridge, публикация, фильтрация, версионные границы nftables.

Права процесса и права управляющего

Управляющий API Docker способен запускать процессы и подключать к ним данные хоста. Поэтому сокет daemon — чувствительный объект. Передать контейнеру /var/run/docker.sock означает передать возможность управления соответствующим сервером, если процесс имеет права обращения. Даже подключение сокета с файловым флагом read-only не превращает API в интерфейс только чтения: ограничение монтирования файла не фильтрует отправляемые по сокету запросы.

Граница контейнера не заменяет границу доверия между участниками. Выполнение чужого Dockerfile даёт чужому коду возможность исполняться в сборочной среде; выдача BuildKit-секрета позволяет этому коду его прочитать. Если CI-задание имеет управляющий сокет rootful Engine, считать его безопасным только из-за запуска «в контейнере» нельзя. VM, отдельный сервер и ограниченные учётные данные решают другие части этой задачи.

USER задаёт идентификаторы, а не новую личность хоста

USER 10001:10001 в Dockerfile задаёт пользователя по умолчанию. --user при запуске может его переопределить. UID, user identifier, — числовой идентификатор пользователя; GID аналогично идентифицирует группу. Этот идентификатор проверяется ядром при доступе к файлу; имя из /etc/passwd — удобное отображение и источник дополнительных сведений. Файл в bind mount с владельцем UID 1000 не становится доступным UID 10001 от одинакового человеческого имени student в двух системах.

В обычном rootful режиме без remapping root контейнера имеет UID 0 в общей идентификационной системе хоста, хотя дополнительные ограничения существенно сужают его действия. User namespace создаёт отображение внутреннего UID на иной внешний диапазон. Userns-remap оставляет daemon привилегированным, отображая идентификаторы контейнеров. Rootless помещает также сам daemon в непривилегированную пользовательскую границу. Эти режимы различаются последствиями возможного захвата управляющего процесса.

Capabilities дробят полномочия root

Linux capabilities, наборы отдельных привилегий, разделяют некоторые исторические полномочия суперпользователя: например, управление сетевой конфигурацией или специальные файловые операции. --cap-drop=ALL убирает предусмотренный набор возможностей, --cap-add возвращает конкретную необходимую. Обычная HTTP-служба на порту 8080 часто обходится без дополнительных capabilities. Из этого не следует, что любой бинарник корректно работает с тем же набором: потребность проверяется по системным действиям.

Порт 80 часто называют привилегированным, но соответствующий порог и разрешения зависят от сетевого namespace и конфигурации Linux. Поэтому объяснение «non-root всегда запрещён любой порт ниже 1024» слишком категорично. Для учебной службы выбираем 8080 и не делаем низкий порт условием работы. Публикация внешнего 18080 вообще не требует, чтобы приложение слушало 18080 внутри.

Seccomp и LSM проверяют другую грань

Seccomp — механизм ограничения системных вызовов процесса по выбранному фильтру. Штатный профиль Docker допускает определённый набор вызовов и ограничивает опасные варианты. Он не проверяет бизнес-смысл HTTP-запроса и не шифрует данные. Отказ Operation not permitted может быть связан с seccomp, capability, LSM или обычными правами; одинаковый текст не определяет причину.

LSM, Linux Security Module, — интерфейс дополнительных механизмов контроля доступа, например AppArmor или SELinux. Их правила могут запрещать действие, разрешённое обычными правами файла. --security-opt no-new-privileges=true ограничивает получение дополнительных привилегий через последующее исполнение, например setuid-программы. Он дополняет USER, но не заменяет выбор доступных файлов и сокетов.

Блок разбирает один вариант настройки. Перед реальным выполнением нужны подготовленный образ и свободные выбранные имя/порт; связный маршрут без конфликтующих повторных запусков находится в заключительном практикуме.

docker --context study run -d --name study-echo \
  --pull=never --user 10001:10001 \
  --cap-drop ALL --security-opt no-new-privileges=true \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  --memory 256m --cpus 1 --pids-limit 128 \
  --publish 127.0.0.1:18080:8080 study/echo:lesson1

Эта конфигурация подходит только варианту службы без записи в корень. Для записи счётчика дополнительно подключают подготовленный /data. --read-only запрещает запись в корневую файловую систему контейнера, но не делает автоматически read-only все отдельные mounts. Tmpfs предоставляет временный каталог с ограниченным размером; noexec запрещает предусмотренный прямой запуск с него, nosuid отключает эффект setuid на этой области. Временные данные всё равно занимают ресурсы и могут оказаться в swap в зависимости от системы.

Не используем --privileged как средство «пока заработает». Он существенно расширяет права и доступ к устройствам, меняя модель безопасности. Точный набор эффектов зависит от платформы. Для диагностики сначала устанавливают, какое действие получает отказ, затем выбирают минимальное конкретное изменение и проверяют отрицательный сценарий: ненужное действие всё ещё должно быть запрещено.

Rootless начинается с другой установки

По официальной инструкции rootless проверяют uidmap, программы newuidmap/newgidmap и назначенные диапазоны /etc/subuid и /etc/subgid. Эти программы позволяют сформировать допустимое отображение нескольких идентификаторов; обычное совпадение имени пользователя не создаёт такой диапазон. Ограничения дистрибутива на user namespaces также входят в предусловия.

После подготовки поставки dockerd-rootless-setuptool.sh install выполняют от выбранного обычного пользователя. Она создаёт пользовательскую systemd-службу и context rootless. Управляют ею через systemctl --user; системная systemctl status docker проверяет другой сервис. Типичные пути — сокет в /run/user/UID/docker.sock, конфигурация в ~/.config/docker, данные в ~/.local/share/docker. Их записывают фактически, с учётом XDG-переменных и версии.

Запуск пользовательской службы после выхода пользователя требует отдельного решения о lingering — сохранении пользовательского менеджера systemd. Его настройка меняет поведение машины и выполняется осознанно в своей VM. Rootless не является флагом, который моментально превращает текущие rootful-контейнеры и их диски в новый сервер. Рядом могут существовать два daemon с независимыми объектами и одинаковыми именами контейнеров.

Что rootless меняет для упражнения

Управление памятью и CPU требует поддерживаемого cgroup v2 и корректного делегирования контроллеров; без этого некоторые параметры могут не работать как ожидается. Публикация низких портов, ICMP, host network и пропускная способность пользовательской сети имеют дополнительные условия. Проверяют docker info, фактические ограничения и путь пакетов, а не копируют rootful-вывод как эталон.

Rootless сокращает последствия захвата daemon до доступных ему пользовательских прав, но домашний каталог этого пользователя, его ключи и доступные сервисы всё равно ценны. Изоляция не оправдывает подключение всего домашнего каталога на запись. Для Go-службы перечисляют конкретные файлы конфигурации, каталог данных и сетевые зависимости; всё остальное остаётся недоступным без отдельной потребности.

Проверить конфигурацию на отказ

После ограничения прав проверяют нормальный запрос, запись только в разрешённый /data и отказ записи в корень. Затем проверяют отсутствие управляющего сокета, ненужных устройств и внешней публикации. Наличие сканера уязвимостей не подтверждает эти свойства: сканер анализирует известные проблемы содержимого, а dangerous mount может использовать полностью обновлённый образ.

Три файла с одинаковым содержимым

Пусть приложение записало строку в /root-note, /data/note и /tmp/note. Первый путь находится в изменяемом слое контейнера, второй — в именованном томе, третий — в tmpfs. При обычном stop/start того же объекта первый и второй сохраняются, а tmpfs при остановке теряет содержимое. При удалении и создании нового объекта первый исчезает, второй доступен при повторном подключении того же тома. Поведение определяется монтированиями, а не словами root, data и tmp в имени.

Volume — управляемый Docker объект хранения, bind mount — подключение явно выбранного пути на хосте, tmpfs — временная файловая область в памяти с возможными особенностями swap. Именованный volume локального драйвера обычно привязан к одному серверу; одинаковое имя study-data на двух серверах обозначает две разные области. Само слово volume не обещает репликацию, отдельный физический диск или резервирование.

Блок разбирает один вариант настройки. Перед реальным выполнением нужны подготовленный образ и свободные выбранные имя/порт; связный маршрут без конфликтующих повторных запусков находится в заключительном практикуме.

docker --context study volume create study-data
docker --context study volume inspect study-data
docker --context study run -d --name study-echo --pull=never \
  --mount type=volume,src=study-data,dst=/data \
  --publish 127.0.0.1:18080:8080 study/echo:lesson1

src именует объект на сервере, dst выбирает видимый процессу путь. Inspect показывает драйвер и место/параметры подключения. Локальный путь Mountpoint используют для понимания размещения и процедур администратора, а не для произвольного редактирования внутренностей работающей БД. Если приложение non-root, каталог должен иметь подходящего владельца заранее; Docker не угадывает нужный UID из содержимого Go-кода.

Монтирование скрывает прежний каталог

В образе может существовать /data/example.txt. Подключение непустого тома поверх /data скрывает прежнее содержимое этого пути. Оно не было обязательно удалено из образа, просто другое монтирование стало видимым сверху. Для пустого тома Docker по умолчанию может первоначально скопировать содержимое каталога образа в том. Опция volume-nocopy запрещает такое заполнение. Bind mount не обещает той же инициализации.

Отсюда диагностический случай: приложение после обновления «не видит новый конфиг из образа». Если конфиг находится под прежним volume, новый нижний файл скрыт старым сохранённым содержимым. Пересборка образа не является миграцией пользовательских данных. Процедура должна отдельно решить, какие файлы являются значениями по умолчанию, какие — постоянной конфигурацией, и кто имеет право их изменять.

Bind mount находится на daemon-хосте

docker --context study run --pull=never \
  --mount type=bind,src=/srv/study/docker-world/config,dst=/config,readonly \
  study/echo:lesson1

Источник этого mount ищется на машине сервера study. Если клиент запущен в Windows, Docker не отправляет автоматически содержимое такого Linux-пути с клиентского диска. Интеграция Desktop с файловой системой основной ОС — отдельная функция. Для обычного remote daemon чтение файла проекта клиентом и монтирование пути сервером являются разными операциями.

В обычном режиме --mount type=bind требует существующего источника и при ошибке пути сообщает отказ; сокращённый -v может создать каталог вместо ожидаемого отсутствующего файла. Новые версии добавляют и специальные варианты создания для --mount, поэтому ориентируются на явно выбранные опции. Для учебных конфигов полезнее предварительно проверить тип, права и хеш файла и не скрывать опечатку автоматическим созданием.

Bind mount на запись позволяет контейнерному процессу изменять данные хоста в пределах эффективных прав. readonly задаёт режим этого подключения. Существующие вложенные монтирования и рекурсивная read-only-семантика имеют условия ядра и параметров; один флаг не заменяет чтение реального дерева mount. Объяснять защиту следует на фактически используемом простом каталоге.

Пользователь и первый доступ

Для локального volume сначала выбирают числовой UID приложения. В новом пустом учебном томе подготовительный контейнер с известным инструментом может создать нужный каталог и назначить владельца 10001:10001. Это отдельная административная операция над этим томом, а не постоянный запуск приложения от root. После неё основной процесс получает только нужный каталог и свои обычные права.

Не исправляйте любой permission denied через chmod -R 777. Сначала проверяют эффективный UID/GID, права каждого компонента пути, режим mount и возможную LSM-политику. Если rootless использует отображение идентификаторов, внешний владелец может выглядеть иначе. Сравнение имён пользователей по отдельности не определяет итоговое право.

Записано в приложение — не значит сохранено на носителе

Успешный write обычно подтверждает передачу байтов ядру. Они могут находиться в page cache, файловом кэше памяти. Системный вызов fsync запрашивает предусмотренное файловой системой доведение данных и метаданных до устойчивого состояния. Его цена зависит от накопителя, очередей, файловой системы и гарантий нижнего уровня. Наличие SSD не делает эту операцию бесплатной, а Docker volume не меняет договор write в договор fsync.

Для замены одного небольшого файла часто используют последовательность: записать временный файл в том же каталоге; fsync временного файла; закрыть; atomically rename — атомарно заменить имя; fsync каталога. Атомарность имени означает отсутствие промежуточного частично заменённого имени для наблюдателя, но не универсальную транзакцию сразу нескольких файлов. Сбой между шагами может оставить разные допустимые состояния; приложение должно знать, какие из них оно принимает.

Даже после устойчивой записи HTTP-ответ может потеряться. Клиент увидит ошибку и повторит запрос, хотя первый уже изменил данные. Это проблема идемпотентности операции: повтор с тем же смыслом должен иметь определённую судьбу. Тестовый счётчик следующей главы намеренно показывает эту границу; он не выдаётся за транзакционную БД.

Согласованность резервной копии

Архив каталога работающей PostgreSQL может смешать файлы разных моментов. Том сохраняет доступ к файлам, но не сообщает архиватору границы транзакции и нужные WAL. Для БД применяют собственный протокол дампа, физического backup и журнала из тома PostgreSQL. Для простой службы можно остановить запись на известной границе и копировать неподвижный набор. Snapshot файловой системы без прикладной координации в лучшем случае приближает аварийную копию в соответствии с гарантиями всех слоёв.

Согласованная копия двух сервисов сложнее двух отдельных архивов: ссылка на объект и сам объект должны соответствовать допустимому моменту. Копия конфигурации, учётных данных, данных и журнала восстановления имеет совместный договор. Именно поэтому объектное хранение и распределённые БД требуют самостоятельного разбора, а не инструкции «подключите volume».

Ресурсная цена и перенос

Измеряют скорость и задержку того типа операций, который выполняет приложение: последовательное чтение, случайную запись, fsync, создание множества маленьких файлов. Сравнение большой последовательной копии с транзакционным журналом неверно. В Desktop bind mount может проходить через дополнительный протокол обмена между ОС, тогда как именованный volume остаётся внутри Linux-VM; результат теста одного пути не переносится на другой.

Перенос на другой компьютер включает содержимое тома, права и метаданные, версию приложения, совместимую схему и проверенный способ восстановления. docker image save не содержит volume. docker export не превращает контейнер с mounts в согласованный полный backup. Практика восстановления должна завершаться чтением ожидаемых данных на отдельной цели, а не строкой «архив создан».

Первичные источники: volumes, bind mounts, tmpfs, fsync, rename.

Каталог labs/echo содержит собственную службу без внешних Go-модулей. /health отвечает на локальную проверку, /version возвращает версию, /greet формирует JSON, /counter при настроенном APP_DATA_DIR читает и увеличивает сохраняемый счётчик. Приложение не подключается к PostgreSQL или Redis. Это намеренно небольшой предмет изучения; добавление БД в дальнейшей практике требует настоящей прикладной интеграции.

Режим /echo check сам выполняет HTTP-запрос к локальному /health с тайм-аутом. Поэтому финальному scratch-образу не нужны curl и shell для проверки здоровья. Пригодность этой проверки ограничена: она подтверждает ответ HTTP-обработчика, но не доказывает возможность следующей записи на диск или доступность внешней зависимости. Содержание probe, проверки, выбирается по конкретной цели.

ABI, application binary interface, — двоичный договор передачи аргументов, размещения значений и вызовов. Совпадение архитектуры само по себе не доказывает совместимость всех внешних библиотек и загрузчика.

Выбрать и закрепить сборочную среду

На официальной странице образа Go выбирают поддерживаемый toolchain и вариант платформы. До автономного дня получают образ, записывают digest и проверяют go version внутри выбранной среды. Пример Dockerfile принимает GO_IMAGE явно и не имеет скрытого latest по умолчанию. Если нет согласованного аргумента, сборка должна дать понятный отказ вместо случайного выбора компилятора.

docker --context study buildx build --progress=plain \
  --build-arg GO_IMAGE="$GO_IMAGE" \
  --platform linux/amd64 --load \
  --tag study/echo:lesson1 labs/echo

Переменная GO_IMAGE содержит подготовленную ссылку на доверенный образ, предпочтительно с digest. Она не является секретом. --platform задаёт целевую платформу; --load выбирает локальный экспорт; последний путь — контекст исходников. Команда показана из каталога тома docker; при работе внутри labs/echo последним аргументом будет точка. Путь -f и корень контекста нельзя менять независимо без проверки COPY.

Почему две стадии

В стадии build находятся Go toolchain и исходники. Она использует --platform=$BUILDPLATFORM, то есть исполняет компилятор на платформе builder, а TARGETOS и TARGETARCH задают целевую программу. Тесты сначала выполняются в нативной сборочной среде. Это не тест целевого arm64-исполнения, если builder amd64. Для такого доказательства нужен отдельный запуск на реальном целевом CPU либо явно учтённая эмуляция.

CGO_ENABLED=0 отключает путь cgo, взаимодействия с программами и библиотеками на C, для данной сборки. Программа использует только поддерживаемую стандартную библиотеку, поэтому её Linux-бинарник можно перенести в scratch — пустую начальную файловую систему. Для программы с cgo и внешними библиотеками такой вывод был бы неверен: понадобятся динамический загрузчик, согласованная стандартная библиотека C, libc и другие зависимости либо сознательно настроенная статическая линковка. Архитектуру и зависимости бинарника проверяют средствами изучения ELF, формата исполняемых объектов Linux, из тома Go.

Scratch не содержит /bin/sh, пакетного менеджера, сертификатов CA, часовых поясов и пользовательских баз автоматически. Наш сервер отдаёт обычный HTTP и не требует внешней проверки TLS. Если добавить HTTPS-клиент, потребуется доверенное хранилище CA и выбранная стратегия его обновления. Если добавить именованные часовые пояса или поиск пользователя, нужно исследовать соответствующие входы. «Статический» не означает «вообще не читает файлов».

Пользователь и данные

Финальный USER 10001:10001 задаёт непривилегированный числовой идентификатор. В простом запуске без APP_DATA_DIR доступны /health и /greet; счётчик отвечает 503, потому что постоянное хранилище не настроено. Для счётчика нужен /data с правом записи этого UID. Подключение пустого тома не обязано автоматически назначить владельца, особенно когда образ не создавал внутри него подходящий каталог.

Инициализацию прав выполняют один раз над новым учебным volume подготовленным административным инструментом с известным образом и digest. Например, контейнер с командой chown 10001:10001 /data получает только этот volume, сеть none и ограниченное время. После этого приложение всегда запускается со своими узкими правами. Восстановление архива должно сохранить либо осознанно восстановить те же идентификаторы.

Корректное завершение входит в код

Приложение подписывается на SIGTERM и SIGINT через signal.NotifyContext. Когда сигнал получен, http.Server.Shutdown прекращает приём новых соединений и ждёт предусмотренного завершения текущих обработчиков с бюджетом 10 секунд. Внешняя среда получает 15 секунд stop_grace_period, оставляя небольшой запас на завершение. Бюджеты согласованы, но при зависшем хранилище возможен принудительный предел.

Программа запускается непосредственно через JSON ENTRYPOINT. Лишняя shell не получает роль промежуточного PID 1. В журнале при штатной остановке ожидается stopped; отсутствие этой записи совместно с кодом 137 повод проверить, не истёк ли внешний тайм-аут. При непредвиденном падении до установки обработчиков штатный протокол не выполняется: резерв данных нужен независимо от него.

Счётчик демонстрирует пределы простой записи

POST /counter сериализует изменения mutex, пишет временный файл в том же каталоге, вызывает Sync, заменяет имя и синхронизирует каталог. После перезапуска читается сохранённое число. При ошибке после замены имени результат устойчивости может быть неизвестен; программа блокирует следующие записи до разбора и перезапуска, не продолжая молча со старым значением в памяти. Повреждённое число при старте вызывает отказ, а не автоматическое обнуление.

Служба не реализует распределённый доступ нескольких процессов к одному счётчику, идентификаторы повторных запросов или транзакцию нескольких объектов. Запуск двух копий с общим /data нарушает предпосылку единственного писателя. Это полезный отрицательный опыт с явно обозначенным результатом, а не способ получить кластер. Для совместной записи нужен соответствующий протокол приложения или БД.

Одинаковый бинарник и одинаковый образ

-trimpath и -buildvcs=false делают некоторые входы бинарника явнее: убирают пути сборочной машины и автоматическое включение определённых сведений системы контроля версий (VCS). Они не закрепляют версию toolchain, базу, окружение, cgo или часы, если программа использует их при генерации. Номер версии, внедрённый -ldflags, тоже является входом и изменяет байты.

Чтобы сравнить две сборки, фиксируют Git-коммит, отсутствие незаписанных изменений, Go image digest, Dockerfile, платформу, параметры и способ получения зависимостей. Затем отдельно сравнивают хеш бинарника и digest образа. Отличие упаковки или attestations может изменить внешний digest при одинаковом исполняемом файле. Совпадение бинарника не доказывает одинаковую runtime-конфигурацию, а одинаковый образ — одинаковые данные тома.

Первичные источники: стадии, целевые платформы, флаги Go, Shutdown. Полные исходники находятся рядом с книгой и доступны офлайн.

Что передаёт push

Registry принимает объекты по определённому протоколу: содержимое слоёв, конфигурацию, манифесты и индексы. Благодаря адресации по содержимому уже имеющийся blob не обязательно загружать заново. Финальная ссылка tag указывает на выбранный опубликованный объект. Повторный push под тем же tag может изменить его назначение, если политика реестра это допускает; поэтому «проверяли lesson1 вчера» недостаточно для сегодняшнего запуска.

Pull получает описание и нужные объекты выбранной платформы, проверяя их digest. В обычном полном pull локальное наличие образа устраняет необходимость снова скачивать те же данные, но не доказывает вечную доступность remote tag. Lazy pulling, отложенное получение содержимого некоторыми snapshotters, имеет дополнительные условия и не подходит как молчаливое обещание офлайн-готовности. Автономный комплект проверяют реальной загрузкой на отключённой тестовой среде.

docker --context study image inspect --format \
  '{{json .RepoDigests}}' study/echo:lesson1
docker --context study buildx imagetools inspect \
  registry.example.invalid/team/echo:lesson1

RepoDigests показывает известные локальному серверу связи с опубликованными digest. У локально собранного, ещё не опубликованного образа список может быть пуст. Его локальный image ID и удалённый manifest/index digest нельзя автоматически считать одним объектом. imagetools inspect обращается к образу в реестре и показывает платформенную структуру; это не то же самое, что исследовать только локальные слои.

Проверить digest — ещё не выбрать доверенного автора

Хеш обнаруживает несоответствие байтов ожидаемому содержимому. Если злоумышленник заменил и образ, и присланный рядом ожидаемый digest, сравнение может успешно подтвердить чужой образ. Нужен доверенный канал получения ожидаемой идентичности, политика подписей или другой явно выбранный механизм происхождения. Подпись также имеет смысл только при доверии к ключу, личности и допустимому процессу выпуска.

Не путайте аутентификацию при login с доказательством безопасности содержимого. Успешный вход в реестр разрешает операции определённой учётной записи. Образ этой учётной записи может содержать уязвимую библиотеку, неверную конфигурацию или намеренно вредную программу. Доверие к издателю, результаты анализа и ограничения runtime остаются независимыми слоями решения.

Для автоматизации применяют минимальный scope токена, область разрешённых действий и docker login --password-stdin с защищённым источником ввода; не помещают токен в аргументы процесса, журнал или общедоступный .env. Выбранное credential store, хранилище данных доступа клиента, проверяют отдельно. Кодирование значения в base64 в конфигурационном файле не является шифрованием.

Provenance и SBOM

Provenance, сведения о происхождении сборки, описывают входы и процесс получения результата: исходник, инструмент, параметры и связанные идентичности в объёме выбранного формата. SBOM, software bill of materials, — перечень компонентов программного состава. Они помогают расследовать, какие зависимости вошли в выпуск, но не доказывают автоматически отсутствие вредного поведения и не заменяют тесты приложения.

docker --context study buildx build \
  --build-arg GO_IMAGE="$GO_IMAGE" \
  --platform linux/amd64,linux/arm64 \
  --provenance=mode=min --sbom=true \
  --tag registry.example.invalid/team/echo:lesson1 --push labs/echo

Это дальнейший сетевой вариант при подготовленном личном registry и нужных возможностях builder. --push экспортирует результат в реестр, --provenance выбирает представление происхождения, --sbom запрашивает соответствующую аттестацию. Сканер SBOM может сам требовать дополнительных образов и сети; его готовность входит в автономный комплект. Наш базовый лабораторный запуск такой реестр не разворачивает.

Attestation, сопровождающее утверждение о результате, может изменить структуру опубликованного index. Поддержка сохранения таких объектов зависит от image store и экспортера: старое классическое хранилище имеет ограничения. Успешная локальная сборка с --load не подтверждает, что все сопутствующие аттестации доступны потребителю. Проверяют фактически опубликованную структуру и политику её чтения.

Несколько архитектур — несколько доказательств исполнения

Многоархитектурный образ связывает несколько платформенных манифестов. Для Go без cgo перекрёстная компиляция часто проста: compiler работает нативно, а GOOS/GOARCH выбирают машинный код цели. Но успешно созданный arm64-файл ещё не проверил системные вызовы, возможности CPU, поведение сети и файловой системы реального arm64-сервера.

Эмуляция может помочь выполнить проверки, но она добавляет программный слой и может заметно замедлять сборку либо скрывать аппаратные различия. Если требуется сравнить скорость, используют нативные машины и фиксируют семейство CPU, лимиты и фон. Сопоставление времени build под QEMU со временем нативного amd64 не измеряет только качество компилятора.

Подготовить автономную доставку

docker --context study image save --output echo-lesson1.tar \
  study/echo:lesson1
sha256sum echo-lesson1.tar > echo-lesson1.tar.sha256
docker --context target image load --input echo-lesson1.tar
docker --context target image inspect study/echo:lesson1

save передаёт архив образов в файл на стороне клиента; load читает его оттуда и загружает на выбранный target. Это отличается от bind mount, чей путь относится к daemon-хосту. До переноса проверяют вместимость носителя, особенности файловой системы и контрольную сумму. Сумма, лежащая рядом с архивом, удобна для обнаружения случайной порчи; подлинность ожидаемого значения фиксируется доверенным паспортом.

Сохранённый архив не включает именованные volumes, активные соединения и память процесса. docker export снимает файловое представление контейнера с иными свойствами, не сохраняя полный исходный договор image metadata и mounts. Его не подставляют вместо save/load для воспроизводимого выпуска. После переноса сверяют не только tag, но конфигурацию, платформу, ожидаемый локальный ID и контрольный запуск без сети.

Продвинуть тот же результат

Выпуск связывает исходный коммит, проверенный digest, runtime-конфигурацию, миграцию данных и запись о принятии. Повторно собрать «из тех же исходников» в рабочей среде — другой процесс с возможными новыми внешними входами. Предпочтительнее продвигать уже проверенный образ по идентичности, затем отдельно применять нужную конфигурацию. При возврате версии надо иметь доступ к прежнему образу и знать совместимость прежнего кода с текущими данными.

Хранение в registry не является резервом пользовательского тома, а локальный кэш образов не является политикой сохранения выпусков. Сроки хранения, неизменность нужных идентичностей, права удаления и проверка восстановления должны быть явными. Самостоятельная эксплуатация реестров артефактов разбирается в отдельном томе.

Спецификация, плагин и имя проекта

Современная команда docker compose работает как плагин Docker CLI и читает Compose Specification. Старую отдельную программу docker-compose не следует считать автоматически той же реализацией. Перед первым использованием фиксируют docker compose version и поддерживаемые команды. Поле version в старых примерах YAML не закрепляет версию установленного плагина и не является механизмом получения нужных возможностей.

Project, проект Compose, объединяет ресурсы одного развёртывания. Его имя влияет на имена автоматически создаваемых объектов и labels, служебные метки. Если случайно сменить имя проекта, можно увидеть новые пустые volumes и решить, что данные пропали. В лабораторном файле name: study-docker, а данные вынесены в явно именованный внешний volume study-data. Слово external означает, что объект должен существовать и его жизненным циклом управляют отдельно.

Сначала увидеть итоговую конфигурацию

export APP_IMAGE=study/echo:lesson1
docker --context study compose -f labs/echo/compose.yaml config
docker --context study compose -f labs/echo/compose.yaml up -d
docker --context study compose -f labs/echo/compose.yaml ps

Глобальный --context выбирает Engine, -f — файл проекта, config проверяет и выводит нормализованное описание с учётом подстановок. Оно может содержать чувствительные значения: не публикуют результат без проверки. up -d создаёт или согласует нужные ресурсы и запускает процессы, отсоединяясь от вывода. Статус running ещё не подтверждает прохождение healthcheck.

Выражение ${APP_IMAGE:?... в файле требует непустой выбранный образ. Переменная shell, файл .env для подстановки Compose, service env_file и environment имеют разные роли и правила приоритета. Значение, доступное Compose при разборе YAML, не всегда автоматически становится переменной процесса. Для передачи приложению его явно задают в environment или предусмотренном механизме. Файл .env не является защищённым хранилищем.

Из чего состоит наш сервис

Файл рядом с исходниками задаёт APP_ADDR=:8080 и APP_DATA_DIR=/data, публикацию только loopback хоста и volume study-data. read_only: true ограничивает корень, tmpfs даёт временный /tmp, cap_drop удаляет capabilities, security_opt включает no-new-privileges. Mem_limit, cpus и pids_limit ограничивают разные ресурсы обычного локального контейнера. После запуска сравнивают действующий HostConfig, а не считают YAML достаточным доказательством.

Сервис использует готовый image и pull_policy: never: он должен быть заранее получен либо собран на выбранном сервере. В файле нет автоматической сборки. Это отделяет изменение конфигурации запуска от получения новых исполняемых байтов. Неудачный pull не должен неожиданно подменяться другим latest, а проверка офлайн-комплекта должна явно подтвердить локальное наличие нужного образа.

Готовность по выбранному признаку

Healthcheck запускает ["CMD", "/echo", "check"], то есть непосредственную команду без shell. Interval задаёт период проверок, timeout ограничивает длительность одной, retries определяет число последовательных учитываемых неуспехов, start_period даёт стартовое окно с особым учётом. Успешная проверка внутри start_period может завершить стартовое послабление раньше. Нельзя просто сложить эти числа и обещать одну точную секунду обнаружения: важны моменты начала проверок, их длительность и правила версии.

Наша /health подтверждает ответ сервера. При недоступной записи /counter ещё может отвечать 503, хотя health остаётся успешным. Если потребителю нужна готовность к записи, нужен отдельный осмысленный probe. Но выполнять реальную пользовательскую запись на каждой probe нельзя без проверки побочных эффектов. Проверка здоровья не должна сама создавать нагрузочный инцидент.

Для нескольких сервисов depends_on задаёт зависимости запуска. Условие service_healthy может дождаться здоровья зависимости на предусмотренном этапе. Это не постоянная транзакция «все зависимости всегда готовы»: база может упасть после запуска приложения. Приложение всё равно должно иметь тайм-ауты, повторное соединение и политику ошибок. Health status unhealthy сам по себе не означает автоматический restart обычного Docker-контейнера.

Running, healthy и готовая запись не совпадают

Один сервис проходит нормальную работу, отказ записи и явную остановку. Разделите признаки управления и приложения.

Compose: нормализован; Engine: ещё не создан; Go: нет; Health: не запускалась; Данные: том сохранён; Оператор: проверяет входы

Доказательство: YAML → модель принята. Разбор конфигурации не запускает приложение.

2. Go работает

Engine создал и запустил задачу. Приложение ещё не прошло ни одной предусмотренной проверки.

Действует: Engine.

Compose: применена; Engine: running; Go: слушает 8080; Health: starting; Данные: доступ проверяется; Оператор: ждёт

Состояние: created → running. Running описывает задачу, а не все функции.

3. Health прошёл

Команда /echo check получила 200. Этот признак не обращался к counter.

Действует: Probe.

Compose: та же; Engine: running; Go: ответил health; Health: healthy; Данные: запись не проверена; Оператор: ограниченный признак

Проверка: starting → healthy. Состав probe определяет силу вывода.

4. Запись получила отказ

Неправильные права или ошибка диска дали 503 у counter; процесс и /health остаются живыми.

Действует: Go.

Compose: та же; Engine: running; Go: обслуживает HTTP; Health: healthy; Данные: POST503; Оператор: фиксирует ошибку

Функция: ожидается запись → отказ записи. Healthy не доказывает готовность конкретной операции.

5. Оператор остановил сервис

Штатный stop запрашивает завершение; unless-stopped не обязан немедленно отменять осознанную остановку. Данные остаются.

Действует: Оператор.

Compose: сохранена; Engine: stopped; Go: закончился; Health: нет новых; Данные: volume на месте; Оператор: исследует права

Жизненный цикл: running → остановлен вручную. Исправление причины выполняется в том же мире.

Restart не равен ремонту

restart: unless-stopped задаёт поведение перезапуска с учётом ручной остановки. on-failure ориентируется на неуспешное завершение процесса, always и unless-stopped по-разному переживают ручную остановку и возврат daemon. Точные условия периода мониторинга и ручных действий сверяют с установленной версией; обещание «любая ошибка всегда сразу перезапустит» неверно.

Если процесс продолжает работать и выдаёт неверные данные, restart policy этого не узнает. Если ошибка вызвана повреждённым конфигом, бесконечные перезапуски повторят её, увеличив журнал и задержав диагностику. Сначала читают причину завершения, число рестартов и первые значимые сообщения. Автоматическая попытка полезна для временного сбоя, но не заменяет осмысленное условие восстановления.

Stop, start, restart, up и down

compose stop останавливает задачи, сохраняя контейнеры. start снова запускает существующие. restart останавливает и запускает их, но не обязан применять изменения YAML к сохранённому объекту. Для изменения конфигурации используют up и проверяют, какие сервисы он пересоздал. Это важная причина не проверять новое environment одним restart.

down удаляет контейнеры и предусмотренные сети проекта. Именованные volumes без специального запроса удаления не обязательно удаляются, external volumes остаются вне такого управления. down --volumes меняет границу удаления для управляемых томов и требует осознанного решения; в продолжаемом стенде это не финальная строка каждого упражнения. Мы не обнуляем состояние переходом к новой главе.

docker --context study compose -f labs/echo/compose.yaml logs \
  --tail 40 --timestamps echo
docker --context study compose -f labs/echo/compose.yaml stop echo
docker --context study compose -f labs/echo/compose.yaml start echo

Имя echo здесь — имя сервиса в проекте, а не гарантированное точное имя контейнера Engine. Для одного сервиса могут быть несколько экземпляров, если это допустимо конфигурацией. Наша служба с единственным файловым писателем и фиксированным опубликованным портом не поддерживает бездумное увеличение числа экземпляров. Удвоение процессов не превращает файл в распределённое хранилище.

Устойчивое продолжение и несколько машин

Перед новым опытом сохраняют исходный Compose-файл, безопасные параметры его нормализованного представления, image identity и контрольное значение счётчика. Если конфигурация испорчена, исправляют её в том же проекте; не меняют имя, чтобы скрыть старые объекты. При переносе на другой компьютер восстанавливают тот же договор данных, но осознают, что новый Engine имеет самостоятельные объекты.

Compose на одном Engine не предоставляет автоматический распределённый планировщик работ, scheduler, согласование общего решения между узлами, consensus или отказоустойчивость диска. Для задач нескольких узлов нужны дополнительные механизмы. Знакомые сервисные имена и YAML в Kubernetes не делают обе системы взаимозаменяемыми: устройство управления желаемым состоянием будет отдельным предметом.

Первичные источники: модель Compose, подстановка переменных, зависимости запуска, restart policy, down.

Четыре уровня вопроса

На уровне управления проверяют: создан ли нужный контейнер, каков его образ и restart count. На уровне процесса: выполняется ли программа, сколько потоков и памяти она использует, какие ошибки сообщает. На уровне сети: установлен ли нужный путь и где заканчивается соединение. На прикладном уровне: выполнена ли операция и сколько времени она заняла. Один зелёный индикатор Docker не отвечает сразу на четыре вопроса.

Начинают с конкретного наблюдения: например, запросы POST /counter с одного и того же клиента стали занимать 800 мс вместо обычных 8 мс. Записывают окно времени, долю ошибок, число запросов, интенсивность и изменения среды. Объяснение «контейнер медленный» ничего не говорит о механизме. У этого примера возможны очередь fsync на диске, ограничение CPU, проблема клиента или зависшее логирование.

Стандартные потоки и драйвер журналов

Приложение пишет диагностические события в stdout/stderr. Engine передаёт их настроенному logging driver, драйверу журналирования. docker logs читает поддерживаемое представление этих потоков; это не универсальный читатель всех файлов приложения. Если программа пишет только в /var/log/app.log внутри своего слоя, команда logs не обязана показать эти строки.

docker --context study logs --since 15m --tail 200 \
  --timestamps study-echo
docker --context study inspect --format \
  '{{json .HostConfig.LogConfig}}' study-echo

--since 15m ограничивает окно относительно текущего времени, --tail ограничивает число строк, --timestamps показывает время. Часы клиента, хоста, приложения и внешней системы должны быть сопоставимы. Указанный вывод — события, сохранившиеся выбранным драйвером, а не доказательство отсутствия всех прочих событий. Ротация и сетевой сборщик имеют собственные потери и задержки.

Наша Go-служба журналирует метод из ограниченного набора, известный шаблон маршрута и длительность в микросекундах. Сырые query strings и пароль не печатаются. Это уменьшает риск утечки и произвольного роста размерности. Не следует использовать произвольный URL с пользовательским идентификатором как метку метрики: миллион значений создаст миллион рядов вместо одного полезного распределения.

Когда журнал сам задерживает приложение

Блокирующий путь записи журнала может заставить приложение ждать, если принимающая сторона не успевает. Неблокирующий режим с ограниченным буфером уменьшает эту связь, но допускает потерю сообщений при переполнении. Выбор — часть договора: для диагностического потока допустима одна потеря, для журнала обязательных финансовых событий нужна другая архитектура. Переключение флага не создаёт одновременно бесконечный буфер и нулевую задержку.

Ограничение max-size/max-file предотвращает неограниченный рост в рамках выбранного драйвера и настроек, но не ограничивает любой файл контейнера. Проверяют реальные настройки уже созданного контейнера и фактическую занятость диска. Если root partition заполнен, одновременно могут отказать журнал, создание контейнеров и запись данных, хотя первопричина одна.

Метрики: состояние и скорость

docker --context study stats --no-stream study-echo
docker --context study system df -v
docker --context study inspect --format '{{json .State}}' study-echo
docker --context study events --since 30m --filter container=study-echo

Stats показывает текущую агрегированную нагрузку; один снимок может пропустить короткий пик. Счётчик CPU-времени требует разности за известное окно, а число использованных байтов памяти — наблюдения текущего состояния. Events помогает сопоставить start, die, kill и другие действия; это ограниченный механизм событий сервера, а не гарантированный долговременный аудит. Последняя команда продолжает ожидать новые события; её останавливают отдельно.

Число CPU% зависит от принятой нормировки. В интерфейсах, где 100% соответствует одному логическому CPU, 180% означает около 1,8 CPU по времени, а не невозможное состояние «больше всего компьютера». В VM с двумя доступными CPU это уже большая доля её ресурса. Уточняют определение метрики и ограничения cgroup до сравнения разных панелей.

Задержка не складывается из одних вычислений

Время пользовательского запроса включает ожидание клиента, соединение, очередь сервера, исполнение Go, ожидание блокировки и хранилища, сериализацию и передачу ответа. Измеряемый сервером elapsed не включает все сетевые фазы клиента. Если клиент видит 800 мс, а сервер в тот же момент стабильно журналирует 5 мс, нужно искать до входа либо после выхода обработчика, а не немедленно переписывать Go-код.

Для counter mutex сериализует запись, включая fsync. Если одна запись занимает в среднем 5 мс, теоретическая предельная пропускная способность единственного такого пути около 200 записей/с при сильных упрощениях. При приближении нагрузки к пределу очередь и хвост задержки растут. Это не обещанная производительность любого SSD: измеряют реальное распределение и работу других пользователей диска.

Практическое расследование

Сначала воспроизводят маленькое безопасное окно нагрузки известным клиентом. Отделяют GET /health от POST /counter: первый почти не использует диск, второй требует устойчивой записи. Если health остаётся быстрым, а counter замедляется, гипотеза «вся сеть сломана» ослабевает. Затем сравнивают CPU throttling, память, ошибки диска и длительности fsync доступными средствами хоста. Отказ записи и медленная запись требуют разных действий.

Далее проверяют, не изменился ли image, конфигурация, volume, владелец или контекст. Перезапуск может убрать накопленную очередь, но также уничтожить момент для наблюдения. Сохраняют достаточный безопасный фрагмент журнала и метрик до изменения. После исправления повторяют то же окно и проверяют отрицательные признаки: не выросли ошибки, потерянные записи или потребление соседней службы.

Какие средства ещё понадобятся

Engine metrics описывают работу самого daemon и не заменяют прикладные метрики. Prometheus и Grafana дают хранение и представление рядов; приложение должно экспортировать осмысленные значения. Наша базовая служба пока не реализует /metrics и histogram. Добавление такой интеграции — отдельное упражнение с явным контрактом меток и единиц, а не уже существующая функция образа.

Для профилирования Go используют pprof и трассировку при осознанном контроле доступа; открывать отладочные порты наружу ради удобства не требуется. Метрики контейнера, профили runtime и трассировка запроса дополняют друг друга. Набор графиков полезен, когда по нему можно проверить конкретную гипотезу и оценить результат изменения.

Первичные источники: драйверы журналов, local, семантика stats, events, метрики daemon.

Опишите тип запроса, размер входа, долю чтений/записей, интенсивность, длительность опыта и допустимые ошибки. Для /greet и fsync-счётчика одинаковые 100 запросов/с означают разную работу. Важен договор, по которому сравнивают варианты.

Квота CPU и время ожидания

При квоте 1 CPU за 100-миллисекундный период группе доступно около 100 мс процессорного времени в этом периоде в рассматриваемом механизме. Четыре параллельных потока могут израсходовать её примерно за 25 мс и затем ждать обновления бюджета. На графике среднего CPU хоста может оставаться запас, а приложение будет получать throttling, принудительное ожидание квоты. Это один из механизмов длинного хвоста задержки.

Из cpu.stat рассматривают изменение числа периодов, throttled periods и времени throttling за известное окно; поля и единицы сверяют для cgroup v2. Одно ненулевое значение с момента запуска не показывает текущую тяжесть проблемы. Сопоставляют дельту с интенсивностью и хвостом latency. Увеличение cpus может помочь при реальном CPU-дефиците, но не ускоряет последовательное ожидание fsync само по себе.

Go runtime должен видеть осмысленный параллелизм

GOMAXPROCS ограничивает доступный runtime параллелизм исполнения Go-кода, а не число всех потоков ОС или всех goroutine. Начиная с Go 1.25 появились container-aware defaults, учитывающие ограничения CPU в предусмотренном Linux-окружении. Поведение также связано с версией языка модуля и GODEBUG-настройками; явное GOMAXPROCS меняет автоматическое управление. В нашем go.mod явно выбран язык Go 1.25, а toolchain должен быть поддерживающим эти настройки; при отсутствии ручного переопределения действует соответствующий новый набор defaults. Для сравнения со старым модулем можно отдельно исследовать GODEBUG=containermaxprocs=1,updatemaxprocs=1, сохранив исходную конфигурацию. Поэтому нельзя объявлять любое Go-приложение «само всегда правильно подстроится» по одному установленному Docker.

Квота может быть дробной, а число P runtime — целым. Преобразование и минимальные значения определяются правилами версии. Сравнивают реальное значение, доступные CPU, квоту, метрики scheduler и p99. Механическое выставление GOMAXPROCS=1 в любом контейнере может уменьшить часть throttling, но также сократить полезный параллелизм и пропускную способность. Проверяют обе стороны обмена.

Память не заканчивается на куче

В нашем Compose лимит контейнера 256 МиБ, а GOMEMLIMIT задан 160MiB как исходный учебный бюджет runtime. Разница не является вычисленной гарантией достаточного резерва: туда должны поместиться управляемые и неуправляемые накладные расходы, память ядра в учёте cgroup, файловый кэш и пики. Сначала измеряют характерную и пиковую нагрузку, затем уменьшают или увеличивают бюджет по свидетельствам.

GOMEMLIMIT — мягкая цель Go, которая усиливает сборку мусора в доступных пределах. Слишком низкое значение может тратить много CPU на GC, garbage collection, не приводя к желаемой задержке. Жёсткая граница cgroup в итоге может завершить процесс. Важно сравнивать не только пик памяти, но и CPU GC, частоту сборок, размер живых данных и ошибки OOM. Копирование настройки соседнего сервиса скрывает различия в данных.

Очередь и закон сохранения запросов

В устойчивом окне без бесконечного роста очереди закон Литтла связывает среднее число работ в системе L, интенсивность λ и среднее время W: L = λW. При 120 запросах/с и среднем времени 0,05 с получается около 6 одновременно находящихся в системе запросов. Это средняя связь при согласованных границах, а не формула p99 и не расчёт максимального числа пользователей.

Для единственного пути записи со средним обслуживанием 5 мс предельная скорость при непрерывной занятости около 200/с. Если поступает 230/с и нет потерь или торможения отправителей, очередь растёт примерно на 30 запросов/с; дополнительная память не меняет этот дефицит обслуживания. При буфере на 600 запросов запас до заполнения около 20 с в этой идеальной постоянной модели. В реальности всплески и распределения требуют запаса и измерений.

Сравните две меры: улучшить обслуживание до 4 мс, то есть около 250/с, либо ограничить вход на допустимом уровне с честной ошибкой перегрузки. Выбор зависит от устойчивости данных и допустимого отказа. Запуск второй копии нашего файлового писателя поверх того же файла не является третьим корректным вариантом: нарушается его алгоритм согласования.

Почему среднее скрывает плохой опыт

Из 10 000 запросов 9 900 заняли 5 мс, 90 — 100 мс и 10 — 2 с. Среднее равно (49 500 + 9 000 + 20 000) / 10 000 = 7,85 мс. Оно выглядит спокойным, хотя десять клиентов ждали по две секунды. При определении nearest rank, ближайшего ранга, p99 — значение на позиции ceil(0,99N), то есть здесь 5 мс; p99.9 на позиции 9 990 равен 100 мс. Число процентиля читают вместе с N, методом и распределением ошибок.

Опыт на 50 запросах не даёт устойчивого представления о редком событии 0,1%. При сравнении нужны серии, прогрев по выбранной цели и известная политика тайм-аутов. Исключение всех неуспешных запросов из отчёта может искусственно улучшить latency: самые медленные просто исчезнут из выборки. Одновременно показывают долю ошибок и отказов по перегрузке.

Ресурс стоит денег и возможностей

Для домашней машины с 8–16 ГБ памяти не требуется одновременно держать GitLab, Jenkins, несколько БД и тяжёлый кластер. Начинают с одного Engine в VM и одной небольшой службы, сохраняя данные остановленных экземпляров. Лимит VM, память ОС хоста, файловый кэш и нужды браузера входят в общий бюджет. Выделенные контейнеру 256 МиБ не означают, что весь стек занимает только 256 МиБ.

У варианта A может быть 1 CPU, p99 180 мс и условная стоимость 10 единиц/день; у B — 2 CPU, p99 70 мс и 18 единиц. Если цель 200 мс при ожидаемом росте, A дешевле сейчас, но его запас нужно измерить; B может дать место для всплеска, но не решает отказ одного диска. Масштабирование, доступность и резерв решают разные задачи, поэтому нельзя оправдывать любой кластер просто желанием ускорения.

Принять изменение по повторяемому опыту

Записывают исходный image/config, окно нагрузки и признаки дефицита. Меняют один существенный параметр, повторяют тот же профиль, проверяют ожидаемый механизм и отрицательные последствия. Если увеличили CPU, должен измениться соответствующий дефицит, а не только один удачный замер. Результат — обоснованный бюджет с запасом и критерием пересмотра при росте нагрузки.

Первичные источники: Go и квоты CPU, мягкая цель памяти, счётчики cgroup. Математические примеры используют явно оговорённые учебные распределения.

RPO, recovery point objective, — допустимая потеря истории данных по времени. RTO, recovery time objective, — целевое время возврата нужной функции. Если копия сделана в 12:00, а последняя запись перед отказом — в 12:17, восстановление только этой копии может потерять 17 минут. RTO включает получение среды, файлов и секретов, восстановление, запуск и проверки, а не одну длительность распаковки tar.

Для нашего счётчика определим простой договор: копия содержит все подтверждённые записи до остановки единственного писателя. После восстановления GET /counter возвращает сохранённое значение, одна новая запись увеличивает его на единицу, /version соответствует записанному образу. Такой набор сильнее проверки наличия файла, но не является тестом любой будущей схемы приложения.

Какие части сохраняют отдельно

Образ сохраняет исполняемые файлы и настройки по умолчанию. Compose и паспорт задают runtime-конфигурацию: environment, mounts, порты, лимиты, политику запуска. Volume содержит постоянные данные. Ключи и пароли хранят отдельно с соответствующими правами и резервом. Наконец, процедура восстановления определяет порядок и критерии. Потеря любого обязательного элемента может сделать остальные архивы бесполезными.

Полная копия VM может быть удобной точкой возврата, если VM корректно остановлена либо применяется согласованный механизм снимка. Но она не заменяет понимание прикладной копии: может оказаться слишком большой, несовместимой с новой платформой или содержащей ненужные секреты. Восстановление одной службы из её данных требует меньшего объёма и даёт отдельное доказательство.

Подготовить инструменты и каталог назначения

Для примера нужен заранее полученный доверенный TOOLS_IMAGE с sh, GNU tar и средствами назначения владельцев. Его выбирают, закрепляют по digest и проверяют до автономного дня. Это вспомогательный административный образ, а не скрытая зависимость scratch-службы. Для каждого поколения выбирают новый каталог внутри /srv/study/docker-world/backups, например с зафиксированным временем копии, и создают его на daemon-хосте в своей VM; в удалённом context локальный каталог клиента не подставляется автоматически.

BACKUP_DIR ниже содержит абсолютный путь на этом сервере, TOOLS_IMAGE — закреплённый административный образ. Сначала убедитесь, что оба значения относятся к вашему стенду. Если используется Compose, останавливают через него именно сервис echo, чтобы не перепутать с похожим контейнером. Для запуска из команд предыдущих глав применяют эквивалентную остановку конкретного имени.

docker --context study compose -f labs/echo/compose.yaml stop echo

docker --context study run --rm --network none --user 0:0 \
  --mount type=volume,src=study-data,dst=/data,readonly \
  --mount type=bind,src="$BACKUP_DIR",dst=/backup \
  "$TOOLS_IMAGE" sh -ceu \
  'test ! -e /backup/counter.tar; cd /data; tar --numeric-owner -cf /backup/counter.tar .'

docker --context study compose -f labs/echo/compose.yaml start echo

Перед архивированием писатель остановлен, поэтому копируемый набор не меняется от штатной работы. Источник смонтирован readonly, сеть вспомогательному процессу не предоставляется. Административный UID нужен для сохранения нужных метаданных; приложению эти права не выдаются. sh -c выполняет строку, -e прекращает цепочку при ошибке, -u считает обращение к незаданной переменной ошибкой. У tar -c создаёт архив, -f задаёт файл. Предварительное test требует отсутствия прежнего counter.tar, сохраняя хорошую копию от случайной перезаписи. Про GNU tar и другой tar нельзя обещать одинаковые опции без проверки.

Архив образуется на сервере через bind mount. Его проверяют там: список записей, размер, контрольная сумма и возможность чтения. Затем копируют во второе независимое место, сохраняя доверенную ожидаемую сумму. Единственная копия рядом с томом на том же диске не защищает от потери этого диска. Конкретный перенос по SSH выполняют на уровне отдельного защищённого канала.

docker --context study volume create study-restore-data

docker --context study run --rm --network none --user 0:0 \
  --mount type=volume,src=study-restore-data,dst=/data \
  --mount type=bind,src="$BACKUP_DIR",dst=/backup,readonly \
  "$TOOLS_IMAGE" sh -ceu \
  'cd /data; tar --numeric-owner -xpf /backup/counter.tar'

docker --context study run -d --name study-restore-check \
  --pull=never --env APP_DATA_DIR=/data \
  --mount type=volume,src=study-restore-data,dst=/data \
  --publish 127.0.0.1:18081:8080 "$APP_IMAGE"

Целевой том должен быть новым и пустым именно для этой проверки; существующее содержимое не смешивают с архивом. Флаг tar -x извлекает, -p восстанавливает права, numeric-owner опирается на числовые идентификаторы. Восстанавливают только собственный проверенный архив: распаковка произвольного чужого tar административным процессом добавляет риски путей и метаданных.

Основная служба продолжает использовать study-data, проверочная — study-restore-data и другой внешний порт 18081. Запросы выполняют с Docker-хоста либо через заранее настроенный SSH-туннель. Сверяют /version, начальный GET /counter и следующий POST. Полученные при проверке изменения относятся только к восстановленной цели. Записывают длительность всей процедуры и отклонение от договора RPO/RTO.

Проверить отрицательные варианты

Нечисловое содержимое, пустой файл или число вне диапазона uint64 обнаруживаются при старте, а не молча обнуляют историю. Изменение допустимого числа 12 на 13 синтаксически корректно; приложение без собственного контрольного эталона его не распознаёт. Для такого случая нужна сверка с доверенной записью и проверка целостности копии. Неправильный владелец может позволить чтение и запретить последующую запись; поэтому одной проверки GET мало. Не тот image может успешно стартовать, но читать другой формат. Запуск в другой context способен показать пустой объект с тем же именем. Каждому такому варианту соответствует проверка идентичности, прав или данных.

Нельзя тренировать повреждение на единственном основном томе: копия для негативного опыта имеет собственное имя и паспорт. Это не автоматический сброс продолжаемого стенда — основное состояние сохраняется, а отдельный опыт намеренно изолирует предмет проверки. Проверочный контейнер после записи результата можно остановить; удаление вспомогательных объектов выполняется адресно после подтверждения, что они больше не нужны.

Если внутри PostgreSQL

Для работающей БД приведённая копия произвольного каталога недостаточна. Используют согласованный pg_dump либо физический backup с непрерывным набором WAL в соответствии с целью. Сохраняют необходимые роли и параметры доступа; при физическом восстановлении учитывают совместимость версии и формат данных. Volume решает размещение, а PostgreSQL — протокол согласованности и восстановления. Эти границы разобраны в отдельном томе.

Если несколько сервисов должны восстановиться к общему логическому состоянию, два корректных отдельных дампа ещё не гарантируют согласованную пару. Нужна определённая точка остановки операций, журнал, идемпотентное повторение либо иной договор приложения. Формулировка «все контейнеры поднялись» не является конечным критерием возврата системы.

Первичные источники: копии volumes, GNU tar, прикладное и физическое восстановление PostgreSQL.

Для нового выпуска получают новый образ, проверяют его идентичность и создают новую задачу с нужной конфигурацией. docker restart запускает прежний объект и сам по себе не выбирает свежий digest по tag.

Перед сменой фиксируют текущий образ, параметры, контрольное состояние данных и резерв. Проверяют новый выпуск на отдельной восстановленной цели, если он меняет данные. После приёмки применяют конкретный образ к тому же учебному проекту. Для нашего Compose APP_IMAGE изменяют осознанно, затем выполняют config и up. Нельзя выдавать случайную перезапись .env за записанный выпуск.

Rollback, возврат версии, включает совместимость данных. Если новая программа необратимо изменила формат volume, возврат старого образа может дать отказ или порчу. Выбирают стратегию: совместимые расширения схемы, отдельная миграция с обратным путём либо восстановление согласованной копии с принятой потерей последующих записей. Контейнеризация не отменяет миграции.

Обновить Engine

Сначала читают release notes исходной и целевой версии, совместимость ОС, storage backend, runtime и API. Сохраняют полный список пакетов и конфигурации, объём свободного места и проверенный путь восстановления. Обновление docker-ce, CLI, containerd.io и плагинов не следует сводить к одному номеру Docker. Имена объектов на сервере не заменяют резерв пользовательских томов.

В лабораторной VM удобна корректно остановленная независимая копия виртуального диска плюс прикладной резерв. Образ VM хранит больше состояния и позволяет вернуть стек, но требует места и совместимости гипервизора. Перед экспериментом проверяют, что копия открывается отдельно и не может одновременно стать вторым писателем к тому же внешнему диску.

Что даёт live restore

Опция live-restore позволяет поддерживаемым Linux-контейнерам продолжить работу при недоступности daemon в предусмотренных условиях. Она уменьшает часть остановок управления, но не является обещанием бесшовного major-upgrade, смены graph driver, параметров bridge или падения хоста. Поддержка привязана к условиям версии; документация ограничивает сценарии обновления совместимыми исправляющими выпусками.

Если daemon долго отсутствует, поток журналов может заполнить служебный буфер и заблокировать дальнейшее логирование приложения. Сохранение PID само по себе не доказывает сохранение пользовательской доступности. Перед применением live-restore тренируют именно нужный путь на своём стенде: завершение daemon, запросы приложения, журналы и возврат управления после запуска.

Отказ запуска daemon

sudo systemctl status docker --no-pager
sudo journalctl -u docker -b --no-pager
sudo systemctl cat docker
dockerd --validate --config-file=/etc/docker/daemon.json

Примеры выполняются внутри личной Linux-VM. Unit показывает команду запуска и drop-ins, дополнительные системные настройки. JSON может быть синтаксически корректным, но конфликтовать с тем же параметром в ExecStart. Также проверяют права каталогов, заполнение диска, доступность containerd и поддержку выбранного backend. Запуск второго dockerd поверх тех же путей ради диагностики создаёт дополнительную опасность; сначала разбирают существующий экземпляр.

Если пропали образы после включения containerd store, проверяют, не сменилось ли представление хранения. Прежние данные могут оставаться на диске и стать видимыми при возврате старого backend. Немедленный prune или ручное удаление каталогов уничтожает возможность такого возврата. План миграции должен отдельно предусмотреть экспорт/импорт поддерживаемым способом и свободное место.

Контейнер создан, приложение не отвечает

Собирают последовательность: правильный context → ожидаемый image/config → состояние процесса → его журнал → слушающий адрес → маршрут и публикация → HTTP-результат. Если процесс exited, бессмысленно начинать с браузерного кэша. Если /health доступен внутри, но нет с хоста, исследуют сетевой путь. Если health проходит, а запись даёт 503, проверяют данные и журнал файловой операции.

Ошибки exec format error, no such file и permission denied могут возникать на разных границах. Бинарник иной архитектуры не становится исполнимым от chmod. У динамического ELF «не найден» может относиться к интерпретатору, отсутствующему в scratch, хотя сам файл существует. Неверный UID даёт отказ данных при полностью исправном HTTP. Причина определяется проверяемой гипотезой, а не наиболее знакомой командой.

Место закончилось

Сравнивают Docker system df, фактическую файловую систему, журналы, volumes и cache builder. Отдельно смотрят inode. Docker не обязан учитывать любой bind mount или посторонний файл в том же разделе. Удаление образов не освобождает место, занятое пользовательской БД. Архив резервной копии на том же разделе во время копирования может временно удвоить объём и сорвать процедуру.

Prune удаляет объекты по своей модели неиспользования; «не используется сейчас» не означает «не понадобится для отката или восстановления». Перед очисткой записывают имена/идентичности и причину удаления, подтверждают независимый резерв нужных данных. В продолжаемом учебном мире не выполняют общий сброс ради красивого исходного вывода следующего упражнения.

Конечный результат обновления

После перехода проверяют версии всех компонентов, фактический store и cgroup, сеть, действующие контейнеры и health. Затем прикладные чтение/запись, корректное завершение и способность восстановить данные на отдельной цели. Сравнивают ресурсы и задержки на прежнем профиле. Успех менеджера пакетов подтверждает изменение пакетов, но не этот полный договор.

В журнале стенда сохраняют исходный симптом, факты, выбранное изменение, результат и критерий возврата. Такой журнал позволяет продолжить обучение через неделю с теми же ошибками и исправлениями, не пытаясь вспомнить, что было сделано вручную внутри контейнера.

Первичные источники: release notes Engine, условия live restore, смена store, диагностика daemon.

Подготовка перед автономным днём

Установите Engine по первой главе в собственной Linux-VM, выберите context study и запишите паспорт. Найдите официальные источники Go-образа и вспомогательного инструмента, выберите версии и закрепите digest. Заранее получите нужные образы и зависимости, сохраните их для переноса и проверьте без сети. Скачивание нельзя откладывать до рабочего места без интернета.

Каталог labs/echo содержит реальные исходники, Dockerfile и Compose. Engine и эти файлы автоматически книгой не запускаются. На машине с 8–16 ГБ памяти достаточно начать с одного небольшого Go-сервиса; тяжёлые платформы могут быть остановлены с сохранением их состояния. На рабочей Windows реальные опыты требуют разрешённой установленной среды либо доступа к своей VM; само открытие HTML запускает только браузерные модели.

Первый образ и первый запрос

Из каталога тома выполните сборку главы Go с выбранным GO_IMAGE и платформой своего сервера. Сохраните журнал build и результат inspect. Для первого опыта запустите один контейнер study-echo без APP_DATA_DIR, с --pull=never и публикацией 127.0.0.1:18080:8080. Имя и порт должны быть свободны на выбранном Engine; если вы ранее запускали пример, сначала установите его действительное состояние и назначение.

docker --context study run -d --name study-echo --pull=never \
  --publish 127.0.0.1:18080:8080 study/echo:lesson1
curl --fail --silent --show-error http://127.0.0.1:18080/health
curl --fail --silent --show-error http://127.0.0.1:18080/version
curl --silent --show-error --include http://127.0.0.1:18080/counter

Curl-команды выполняются на Docker-хосте либо через подготовленный туннель. Ожидаются ok, lesson1 и HTTP 503 для ненастроенного counter. --fail превращает ошибочные HTTP-статусы в ошибку команды; в последнем запросе его намеренно нет, чтобы увидеть диагностический ответ вместе с --include, печатающим заголовки. Запишите различие живого процесса и готовности конкретной операции.

Остановка и правильный адрес

Изучите inspect, logs и результат docker stop --timeout 15 study-echo. В штатном журнале ожидается stopped. Затем start того же объекта и повторный health. Изменение APP_ADDR в уже существующем shell клиента не меняет environment сохранённого объекта; этот отрицательный опыт отделяет клиентскую переменную от конфигурации процесса.

Для сетевого опыта используйте отдельное явно названное временное имя и другой внешний порт либо осознанно пересоздайте основной объект с сохранённым паспортом. Вариант с APP_ADDR=127.0.0.1:8080 покажет различие локальной внутренней проверки и доступа через IP контейнера. Сначала предскажите результат по маршруту, затем проверьте. В scratch нет shell; используйте встроенный /echo check и заранее подготовленный диагностический образ в соответствующей сети.

Подключить постоянные данные

Создайте study-data. На новом пустом томе подготовьте владельца UID/GID 10001 с административным TOOLS_IMAGE, предоставив ему только этот volume, сеть none и необходимые для операции полномочия. Перед пересозданием остановите прежнюю службу, сохраните inspect и удалите только прежний объект без постоянных данных. Это адресная смена конфигурации, а не сброс среды.

docker --context study volume create study-data
docker --context study run --rm --network none --user 0:0 \
  --mount type=volume,src=study-data,dst=/data \
  "$TOOLS_IMAGE" chown 10001:10001 /data

docker --context study stop --timeout 15 study-echo
docker --context study rm study-echo
export APP_IMAGE=study/echo:lesson1
docker --context study compose -f labs/echo/compose.yaml config
docker --context study compose -f labs/echo/compose.yaml up -d

Если том уже существует, chown и инициализацию не повторяют вслепую: проверяют его владельца и содержимое. Compose использует этот external volume. Запрос GET /counter сначала возвращает 0, каждый успешный POST увеличивает на единицу. Выполните несколько, запишите подтверждённое число, затем stop/start сервиса. Число должно сохраниться. После пересоздания контейнера с тем же volume оно также сохраняется.

Проверить ограничения и цену операции

Сравните HostConfig с Compose: лимит 256 МиБ, CPU 1, pids 128, read-only корень и отдельный writable /data. Проверьте нормальные запросы. Повторите короткую серию GET health и POST counter при известной интенсивности, фиксируя время клиента, ошибки и вывод stats. Цель первого опыта — различить путь без дисковой записи и путь с fsync, а не объявить производительность сервера по десяти запросам.

Меняйте один бюджет за раз и возвращайте прежнее значение после записи результата, сохраняя историю конфигурации в Git. Не создавайте искусственный OOM на общей машине. Для риска используйте отдельную ограниченную VM с резервом. Если приложение неожиданно завершилось, сначала соберите State, журнал и данные cgroup; повторный up без расследования может скрыть причину.

Резерв и отдельное восстановление

Пройдите процедуру главы резервирования: остановить писателя, архивировать volume, запустить основной сервис, проверить архив и вторую копию. Восстановите в study-restore-data и проверьте на порту 18081. Контрольное число в резерве соответствует моменту остановки; основная служба после этого может продвинуться дальше. Различие чисел тогда ожидаемо и должно быть объяснено временем копии.

Отрицательные опыты выполняйте только на восстановленной цели: неправильный UID, повреждённая строка, не тот образ, отсутствие нужного тома. Для каждого предскажите, на каком этапе появится отказ. Исходный мир не сбрасывайте и основной архив не перезаписывайте повреждённой копией. Результат практики — способность доказать, какая версия и какие данные реально восстановлены.

Связь с остальными томами

Дальше можно поместить в образ собственный Go-сервис из сквозного практикума, затем связать с уже установленным PostgreSQL и кэшем по их паспортам. У каждого экземпляра сохраняются прежние данные и правила доступа. Подключение сети Docker не должно незаметно создавать новую БД вместо той, которую вы уже научились обслуживать.

Перед переходом к Kubernetes полезно уметь вручную объяснить image, command, environment, user, limits, mount, port, health и shutdown одной службы. Оркестратор добавит цикл управления и несколько узлов, но не исправит неизвестную причину отказа записи или бесконтрольный повтор POST. Эти знания переносятся как договор приложения, а не как набор совпадающих имён YAML.

Завершить день, сохранив мир

Остановите нужные сервисы и VM штатно, сохраните passport, Git-конфигурацию, резерв и журнал проверок. Отметьте, что осталось непроверенным. Не удаляйте volumes по общему шаблону очистки. При следующем запуске сначала сверяйте context, версию, состояние и контрольное число, затем продолжайте следующую задачу. Ошибка, найденная вчера, должна либо воспроизводиться, либо иметь записанное объяснение исправления.

Словарь · DockerПонятия и их связь с наблюдаемыми механизмами · 2715 слов

Словарь в боковой панели также ищет определения во всех остальных томах.

Docker Engine

Управляющий стек запуска контейнеров. Клиент обращается к серверу, а сервер использует runtime, сеть и хранение своего хоста; это не отдельное ядро для каждого контейнера.

Docker Desktop

Продукт с графическим управлением и интеграцией основной ОС с контейнерной средой. Для Linux-контейнеров на Windows участвует Linux-окружение виртуализации; установка и рабочие данные оставляют состояние на компьютере.

Контейнер

Объект конфигурации и исполнения процессов с выбранными границами Linux, монтированиями и ресурсами. Остановленный объект может существовать без работающего процесса.

Образ · image

Набор неизменяемых объектов файлового содержимого и конфигурации, используемых как вход создания контейнера. Не содержит автоматически данные подключённых volumes и память работающего процесса.

Виртуальная машина · VM

Гостевая вычислительная среда с собственным ядром ОС. Linux-контейнеры внутри одной такой VM используют ядро этой VM.

Гипервизор

Средство исполнения и управления виртуальными машинами. Его ресурсы и гарантии диска входят в общий договор контейнерного стенда.

CLI

Command-line interface — интерфейс командной строки. Docker CLI является клиентом выбранного управляющего сервера.

API

Application programming interface — интерфейс программного взаимодействия. Docker API позволяет не только читать состояние, но и создавать процессы и подключать данные в пределах полномочий сервера.

Daemon · демон

Долгоживущая служба, принимающая запросы и выполняющая управление. Dockerd и приложение внутри контейнера имеют разные обязанности и жизненные циклы.

Docker context

Сохранённое описание точки управления сервером, включая адрес и параметры подключения. Переключение context меняет сервер операций, а не переносит его данные.

Endpoint

Адрес конечной точки взаимодействия: Unix-сокет, SSH-назначение или сетевой адрес. Его доступность не равна готовности всех приложений.

Unix socket

Локальная точка обмена между процессами через адрес ОС. Сокет Docker даёт интерфейс управления, а не просто доступ к файлу журнала.

SSH

Протокол защищённого удалённого доступа с проверкой личности сервера и клиента. SSH-context переносит команды управления к серверу, но bind mounts остаются на daemon-хосте.

TLS

Протокол защиты транспортного обмена с проверкой выбранной модели доверия. HTTPS к registry и подключение приложения к его зависимости могут иметь разные сертификаты и удостоверяющие центры.

CA

Certification Authority — удостоверяющая сторона и доверенный материал проверки сертификатов. Scratch-образ не получает хранилище CA автоматически.

GPG

Семейство инструментов OpenPGP, используемое в том числе для проверки подписанных метаданных репозиториев. Проверка требует доверенного ключа и правильной области его применения.

APT

Менеджер получения и установки пакетов Debian/Ubuntu. Проверяет подпись метаданных и хеши пакетов по цепочке доверия настроенного источника.

Deb822

Формат полей файлов источников пакетов, например Types, URIs, Suites и Signed-By. Не является исполняемым shell-скриптом.

SHA-256

Криптографический хеш содержимого. Проверяет совпадение с ожидаемыми байтами; доверие к ожидаемому значению обеспечивается отдельно.

Digest

Идентификатор содержимого с указанием алгоритма. Может относиться к индексу, манифесту, конфигурации или слою; одинаковый префикс sha256 не делает их одним объектом.

Tag

Именованная ссылка на объект образа в репозитории. Может быть переназначена по политике реестра и потому сама не закрепляет байты.

Repository образов

Именованная область реестра, в которой публикуются манифесты и ссылки. Отличается от Git-репозитория исходников.

Registry

Сервис хранения и передачи объектов образов по определённому протоколу. Его доступность и сохранение выпущенных объектов требуют собственной эксплуатационной политики.

OCI

Open Container Initiative — семейство спецификаций образа, распределения и исполнения. Совместимость формата не обещает одинаковую безопасность любой конфигурации.

Manifest · манифест

Описание одного образа или другого предусмотренного артефакта с дескрипторами конфигурации и слоёв. Его digest относится к байтам этого описания.

Image index

Индекс дескрипторов, позволяющий связать платформенные варианты и другие предусмотренные объекты. Вариант linux/arm64 и индекс всей публикации имеют разные идентичности.

Descriptor · дескриптор OCI

Запись с типом содержимого, размером и digest. Помогает выбрать формат и проверить полученный объект.

Media type

Обозначение формата содержимого объекта. Одного размера и хеша недостаточно, чтобы правильно интерпретировать произвольные байты.

Blob

Двоичный объект, адресуемый и передаваемый как содержимое, например сжатый архив слоя. Его внутренний смысл определяется форматом.

Layer · слой

Сериализованное изменение файловой системы. Порядок применения слоёв определяет итоговое представление файлов.

Whiteout

Маркер удаления нижнего объекта при применении слоёв. Архивное представление OCI и внутренний механизм OverlayFS относятся к разным уровням реализации.

Opaque directory

Непрозрачный каталог слоя, скрывающий прежних нижних потомков каталога по правилам формата. Не означает шифрование содержимого.

Diff ID

Хеш несжатого потока слоя, используемый в конфигурации образа. Может отличаться от digest передаваемого сжатого blob при тех же распакованных данных.

OverlayFS

Файловая система объединённого представления нижних слоёв и верхних изменений. Слои образа и отдельные подключённые volumes имеют разные пути записи.

Overlay2

Классический драйвер хранения Docker на основе OverlayFS. Не тождествен имени overlayfs snapshotter в containerd.

Copy-up

Подготовка верхнего изменяемого объекта при изменении нижнего файла в объединённой файловой системе. Цена зависит от реализации и размера/метаданных файла.

Containerd

Служба управления контейнерными задачами и, в соответствующей конфигурации, содержимым и снимками. На одном хосте могут существовать независимые экземпляры для разных систем.

Snapshotter

Интерфейс управления файловыми снимками containerd и его реализация. Выбор snapshotter влияет на хранение и получение данных.

Backend

Подсистема реализации определённой функции: например, storage backend или firewall backend. Одинаковое слово без указания функции неоднозначно.

Lazy pulling

Отложенное получение части содержимого через поддерживающий snapshotter. Работоспособность онлайн не доказывает наличие всех данных для автономного запуска или полного экспорта.

Runtime

Среда или исполнитель контейнерной задачи; в узком OCI-смысле применяет описание процесса и запускает его. Go runtime — другой уровень, встроенная поддержка исполнения Go-программы.

Runc

Распространённая реализация низкоуровневого OCI runtime. Применяет заданные границы, но не выбирает прикладную политику доверия вместо оператора.

Shim

Промежуточный процесс управления задачей и её потоками, помогающий отделить жизнь приложения от непосредственного родительства основного daemon.

BuildKit

Подсистема вычисления графа сборки с повторным использованием результатов, mounts и экспортерами. Кэш сборки и runtime-данные приложения различаются.

Buildx

Клиентский интерфейс Docker для builders и расширенных сборок. Возможности определяются также builder, драйвером, экспортером и хранилищем.

Builder

Выбранный экземпляр среды сборки со своими возможностями и состоянием. Может находиться на другой машине и иметь отдельный кэш.

Build context

Набор входов, предоставленный сборщику. Путь Dockerfile и корень контекста задаются независимо.

Dockerfile frontend

Компонент, интерпретирующий язык Dockerfile в операции сборки. Внешний frontend из строки syntax также нужно подготовить для автономного дня.

Cache hit

Повторное использование пригодного результата. Оно ускоряет операцию, но не доказывает актуальность внешнего сайта или пакета, не включённого в ключ.

Cache mount

Сохраняемая область ускорения, подключаемая на время сборочного шага. Не включается автоматически в финальный образ и не заменяет обязательный артефакт.

Multi-stage build

Сборка с несколькими стадиями, где финальная выбирает результаты предыдущих. Позволяет не включать toolchain, но требует осознанно перенести runtime-зависимости.

Build argument · ARG

Параметр сборки. Не является защищённым каналом секрета и может влиять на идентичность результата и метаданные.

Secret mount

Временная передача чувствительного входа сборочному шагу. Не препятствует самой выполняемой программе скопировать или напечатать этот вход.

Namespace Linux

Граница представления определённого класса объектов ОС. Сетевая изоляция, номера процессов и дерево mounts являются разными пространствами.

PID

Process identifier — номер процесса в определённом PID namespace. Один процесс может иметь разные видимые номера снаружи и внутри.

PID 1

Первый процесс PID namespace с особыми обязанностями init и правилами сигналов. Его завершение влияет на остальные процессы этой области.

Zombie

Завершившийся процесс, сведения о котором родитель ещё не забрал через wait. Не исполняет пользовательский код, но занимает запись процесса.

UID/GID

Числовые идентификаторы пользователя и группы. Права к файлу проверяются по действующим идентификаторам и отображениям, а не по совпадению человеческих имён.

User namespace

Пространство отображения идентификаторов пользователей и групп. Позволяет различать внутренний root и внешний непривилегированный диапазон.

Rootful

Режим, в котором daemon имеет системные полномочия root. Внутренний USER приложения и полномочия daemon остаются разными границами.

Rootless

Режим запуска daemon и контейнеров от непривилегированного пользователя с соответствующими пространствами имён и ограничениями. Требует поддержанного окружения.

Userns-remap

Режим отображения идентификаторов контейнеров при продолжающем работать от root daemon. Отличается от rootless последствиями захвата управляющей службы.

Capability

Отдельная привилегия Linux из разделённого набора полномочий. Удаление capabilities дополняет обычные права и другие механизмы.

Seccomp

Фильтрация доступных системных вызовов и некоторых аргументов Linux. Не анализирует корректность бизнес-операции и не заменяет права данных.

LSM

Linux Security Module — интерфейс дополнительного контроля доступа, например AppArmor/SELinux. Может запретить операцию, разрешённую обычными файловыми правами.

No-new-privileges

Ограничение получения дополнительных привилегий при последующем исполнении, в том числе через определённые setuid-механизмы. Не убирает уже выданный доступ к данным.

Cgroup

Control group — иерархическая организация процессов и контроллеров ресурсов Linux. Учёт, ограничения и видимость пути группы имеют разные настройки.

CPU quota

Бюджет совокупного процессорного времени за период. Дробная квота не является выделением дробной физической микросхемы.

CPU throttling

Ожидание после исчерпания предусмотренного бюджета CPU. Может увеличивать хвост задержки при свободных ресурсах вне группы.

Cpuset

Набор разрешённых логических CPU/узлов памяти в соответствующем контроллере. Сам по себе не даёт эксклюзивного владения ядрами.

RSS

Resident set size — объём резидентных страниц процесса в принятой метрике. Не равен только Go-куче и не обязан совпадать с памятью cgroup.

OOM

Out of memory — нехватка памяти, способная привести к принудительному завершению. Код 137 сам не доказывает OOM без дополнительных признаков.

Swap

Подкачка страниц на дополнительное хранилище. Увеличивает набор возможных состояний, но имеет цену задержки и не является быстрой оперативной памятью.

GOMAXPROCS

Параметр доступного runtime параллелизма исполнения Go-кода. Не равен числу всех потоков ОС или goroutine; defaults зависят от toolchain и настроек.

GOMEMLIMIT

Мягкая цель управления памятью Go runtime. Требует запаса до жёсткого лимита cgroup и не учитывает автоматически всю память системы.

GC

Garbage collection — автоматическое обнаружение и освобождение недостижимых объектов. Слишком тесный бюджет может увеличить затраты CPU на сборку.

Bind сетевого сокета

Привязка сокета приложения к локальному адресу и порту. Отличается от bind mount файлового каталога.

Loopback

Локальный сетевой интерфейс пространства имён. 127.0.0.1 контейнера и хоста могут относиться к разным областям.

Veth

Пара виртуальных Ethernet-интерфейсов: отправка в один конец появляется на другом. Часто соединяет namespace контейнера с мостом хоста.

Bridge

Программный канальный мост, пересылающий кадры между портами. Не заменяет IP-маршрутизацию и NAT выхода наружу.

DNS

Domain Name System — система разрешения имён. Встроенные имена Docker-сети имеют собственную область и не становятся публичными DNS-записями.

Search domains

Суффиксы, используемые resolver при дополнении неполных имён. Могут изменить фактическую последовательность вопросов DNS.

Port publishing

Создание пути от выбранного порта хоста к порту контейнера. Не изменяет адрес слушателя внутри приложения.

NAT

Network Address Translation — преобразование сетевых адресов и при необходимости портов. Для ответов важно состояние соответствующего соединения.

DNAT/SNAT

Преобразование адреса назначения/источника. В типичном bridge-пути публикация использует первое, выход наружу — второе или masquerading.

Conntrack

Механизм учёта соединений в сетевом стеке Linux, участвующий в фильтрации и обратном преобразовании NAT. Имеет собственные таблицы и ресурсный бюджет.

Masquerading

Вариант преобразования исходного адреса с использованием адреса выходного интерфейса. Частный адрес контейнера тогда не является наблюдаемым внешним источником.

Iptables-nft

Совместимый интерфейс iptables, использующий nf_tables ядра. Не тождествен отдельному Docker nftables firewall backend.

MTU

Maximum transmission unit — максимальный размер пакета определённого канала. Туннельные накладные расходы могут изменить допустимый размер пути.

Volume

Управляемый объект постоянного хранения, подключаемый в файловое дерево. Локальное имя на двух серверах не означает один общий диск.

Bind mount

Подключение конкретного пути daemon-хоста в контейнер. На запись может менять данные хоста в пределах действующих полномочий.

Tmpfs

Временная файловая система в памяти с особенностями учёта и возможной подкачки. Потеря содержимого при завершении предусмотрена договором.

Inode

Запись файловой системы о файловом объекте и его метаданных. Их число может исчерпаться раньше доступных байтов.

Page cache

Файловый кэш ядра. Успешная запись в него не равна гарантии устойчивого сохранения на физическом носителе.

Fsync

Запрос синхронизации данных и нужных метаданных файла по договору файловой системы. Для устойчивой замены имени важна также синхронизация каталога.

Atomic rename

Атомарная смена имени в предусмотренных условиях файловой системы. Не является транзакцией над произвольным набором файлов.

Идемпотентность

Определённое поведение повторного применения операции без нежелательного дополнительного эффекта. Потерянный ответ после записи требует осмысленного протокола повтора.

ABI

Application binary interface — двоичный договор вызовов, передачи аргументов и размещения данных. Одной одинаковой архитектуры недостаточно для любых внешних библиотек.

ELF

Executable and Linkable Format — формат исполняемых файлов и объектов Linux. Может задавать интерпретатор-загрузчик, которого нет в пустом образе.

Cgo

Механизм взаимодействия Go с C и внешней цепочкой сборки. Меняет предпосылки переносимости и линковки.

Libc

Стандартная библиотека C и связанное системное окружение. Разные реализации и ABI требуют согласования при динамической линковке.

VCS

Version control system — система контроля версий. Сведения VCS в бинарнике являются одним из входов его идентичности.

Provenance

Сведения о происхождении сборки и входах в объёме формата. Требуют проверки доверия к процессу, который сделал утверждение.

SBOM

Software bill of materials — перечень программных компонентов. Помогает анализу состава и известных проблем, но не доказывает отсутствие вредного поведения.

Attestation

Сопровождающее утверждение о результате, например его происхождении или составе. Сохранение зависит от экспортера, image store и потребителя.

Scope

Разрешённая область действий токена. Выбирается вместе с правами личности и конкретным объектом доступа.

Credential store

Средство хранения чувствительных данных доступа клиента. Base64 в обычном файле конфигурации не является шифрованием.

Compose project

Группа ресурсов одного развёртывания модели Compose. Имя проекта влияет на идентичность ресурсов; его смена может создать другой набор данных.

Healthcheck

Команда проверки определённого признака состояния. Успешная проверка HTTP не доказывает каждую внешнюю зависимость или возможность записи.

Probe

Один запуск проверки. Её длительность, эффект и критерий успеха входят в договор наблюдения.

Readiness/Liveness

Готовность к определённой работе и жизнеспособность процесса — разные цели проверок. Перезапуск по одному признаку может не исправить другую проблему.

Restart policy

Правило повторного запуска после предусмотренного завершения. Не исправляет неверные данные и не обязано реагировать на unhealthy.

Graceful shutdown

Корректное завершение по протоколу приложения: прекратить новый приём, завершить или отменить текущую работу, закрыть ресурсы в заданном бюджете.

Scheduler

Планировщик работ или ресурсов. Нужно уточнять уровень: Go goroutine, потоки Linux или размещение сервисов между узлами.

Consensus

Согласование общего решения между участниками распределённой системы при оговорённых отказах. Наличие нескольких контейнеров само этот протокол не создаёт.

Кардинальность метки

Число различных значений/комбинаций в наборе измерений. Произвольные URL и идентификаторы могут сделать хранение метрик непрактичным.

Latency

Задержка определённой операции между выбранными точками времени. Клиентская и серверная метрики могут охватывать разные участки.

Throughput

Число завершённых операций за единицу времени при известных условиях и доле ошибок. Не эквивалент максимальному числу пользователей.

Перцентиль p99

99-й процентиль по выбранному правилу. В методе ближайшего ранга не меньше 99% наблюдений лежит не выше найденного значения; интерполяция может дать иной порог. Читается вместе с размером выборки, окном и правилами ошибок.

SLO

Service level objective — измеримая цель качества обслуживания с явным знаменателем, окном и допустимым результатом.

RPO/RTO

Целевая допустимая потеря истории данных и целевое время возврата функции. Создание архива само не подтверждает достижение этих целей.

Rollback

Возврат версии с учётом совместимости данных и конфигурации. Старый образ не отменяет автоматически новую схему volume.

Live restore

Поддерживаемое продолжение Linux-контейнеров при недоступности daemon в оговорённых условиях. Не является универсальным бесшовным обновлением или защитой от отказа хоста.

Prune

Удаление объектов по правилам неиспользования конкретной команды. Неиспользуемый сейчас образ может всё ещё быть нужен для возврата выпуска.

HTTP

Hypertext Transfer Protocol — прикладной протокол запроса и ответа. Успешное TCP-соединение ещё не означает успешный HTTP-результат или запись данных.

TCP

Transmission Control Protocol — транспорт надёжного упорядоченного потока байтов. Не определяет, какая прикладная операция уже зафиксирована до потерянного ответа.

UDP

User Datagram Protocol — транспорт отдельных датаграмм с иным договором, чем TCP. Публикации порта TCP и UDP задаются отдельно.

ARP

Address Resolution Protocol — разрешение IPv4-адреса соседа в канальный адрес в соответствующей локальной среде. Нужен не вместо маршрута, а после выбора непосредственного соседа.

IPv4/IPv6

Семейства сетевой адресации и доставки пакетов. У bridge-сети и публикации для каждого семейства могут быть отдельные настройки и маршруты.

CIDR

Classless Inter-Domain Routing — запись сети через адрес и длину префикса, например 172.30.50.0/24. Префикс участвует в проверке принадлежности и выборе маршрута.

IPAM

IP address management — распределение адресов и подсетей. В Docker его конфигурация зависит от сетевого драйвера и выбранных параметров.

UTS

Название пространства Linux, отделяющего определённые сведения об имени системы, в частности hostname. Отдельное имя не является отдельным ядром.

IPC

Inter-process communication — обмен между процессами. IPC namespace изолирует определённые IPC-объекты, но не любой мыслимый канал взаимодействия.

Systemd unit

Описание управляемого systemd объекта, например службы Docker. Основной файл и drop-ins совместно определяют фактическую команду запуска.

WSL 2

Среда Windows Subsystem for Linux с Linux-ядром в виртуализированном окружении. Её установка, диски и службы являются состоянием компьютера, а не свойством HTML на флэшке.

AppArmor/SELinux

Реализации дополнительного контроля доступа Linux. Политики могут запрещать действия независимо от обычных прав UID/GID и mode файла.

Setuid

Механизм изменения эффективных идентификаторов при исполнении определённых файлов по правилам Linux. Взаимодействует с no-new-privileges и режимом mount.

Hostname

Имя узла в выбранной области представления. Не создаёт автоматически глобальную DNS-запись и не гарантирует маршрут к приложению.

Build platform / target platform

Платформа исполнения сборочных инструментов и платформа создаваемого результата. Они могут различаться при перекрёстной компиляции.

Nearest rank

Ближайший ранг — один из способов определения перцентиля: элемент отсортированной выборки на позиции ceil(pN), считая позиции с 1. Другие методы интерполяции могут дать иное число.

JSON

Текстовый формат структурированных данных с объектами, списками и скалярами. Корректная JSON-грамматика не доказывает корректность конкретной конфигурации daemon.

YAML

Текстовый формат структурированных значений, используемый Compose. После разбора формата приложение ещё должно проверить смысл ключей и подстановок.
